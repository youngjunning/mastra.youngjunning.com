# `MastraAuthNeon` 和 `MastraRBACNeon`

[`MastraAuthNeon`](https://github.com/mastra-ai/mastra/tree/main/auth/neon) 将 Mastra 认证接入 [Neon Auth](https://neon.com/docs/guides/neon-auth)。它通过 Neon Auth 的 JWKS 端点验证作为 Bearer Token 发送的 JWT，并通过会话 API 验证 Neon Auth 会话 Cookie。该提供者还支持邮箱密码登录、注册和会话管理。

`MastraRBACNeon` 将 Neon Auth 组织角色映射为 Mastra 权限。如果应用使用 Neon Auth 组织成员身份进行基于角色的访问控制，需要单独注册它。

:::note

RBAC 在生产环境中需要 Mastra 企业版 (EE) 许可证；在开发环境中无需许可证即可使用。参阅[需要 EE 许可证的功能](/docs/license#what-requires-an-ee-license)。如需了解更多，请[联系销售团队](https://mastra.ai/contact)。

:::

## 用法 {/* #usage */}

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { MastraAuthNeon, MastraRBACNeon } from '@mastra/auth-neon'

const auth = new MastraAuthNeon()

const rbac = new MastraRBACNeon({
  roleMapping: {
    admin: ['*'],
    member: ['agents:read', 'workflows:read'],
    _default: [],
  },
})

export const mastra = new Mastra({
  server: {
    auth,
    rbac,
  },
})
```

将 `NEON_AUTH_BASE_URL` 设为 Neon Console 中显示的 Neon Auth URL，例如 `https://ep-example-123456.neonauth.us-east-2.aws.neon.tech/neondb/auth`。也可以直接向两个构造函数传入 `baseUrl`。

设置步骤请参阅 [Neon 集成指南](/integrations/auth/neon)。

### 认证方法 {/* #authentication-methods */}

#### `authenticateToken()` {/* #authenticatetoken */}

```typescript
await auth.authenticateToken(token, request)
```

使用配置的 JWKS 端点验证 JWT 格式的令牌，检查签名、签发者、受众和有效期。否则，通过会话 API 验证请求中的 Neon Auth 会话 Cookie。即使 JWT 验证失败，仍会尝试接受会话 Cookie，因此过期的 Bearer Token 不会让同时发送 Cookie 的客户端退出登录。若请求没有会话 Cookie，非 JWT 令牌会被当作会话 Cookie 值。认证成功时返回 `NeonAuthUser`，验证失败时返回 `null`。

`NeonAuthUser` 包含顶层的 `id`、`email` 和 `name`，Neon Auth 的 `user` 对象，以及 `session`（Cookie 认证）或已验证的 `jwt` 声明（Bearer 认证）。

#### `authorizeUser()` {/* #authorizeuser */}

```typescript
await auth.authorizeUser(user, request)
```

若配置了自定义授权函数，就运行该函数。否则，要求提供 Neon Auth 用户 ID，并拒绝已过期的 JWT 载荷。

### 凭据认证方法 {/* #credentials-methods */}

#### `signIn()` {/* #signin */}

```typescript
const result = await auth.signIn(email, password, request)
```

通过 Neon Auth 验证邮箱密码凭据。返回已认证用户、作为 `token` 的 Neon Auth JWT，以及 Neon Auth 会话 Cookie。Neon Auth 必须信任传入请求的源。

#### `signUp()` {/* #signup */}

```typescript
const result = await auth.signUp(email, password, name, request)
```

使用邮箱密码凭据创建 Neon Auth 账号。`name` 为可选参数。若未提供，提供者会从邮箱地址生成显示名称。返回值与 `signIn()` 相同。

#### `isSignUpEnabled()` {/* #issignupenabled */}

```typescript
const enabled = auth.isSignUpEnabled()
```

返回配置的 `signUpEnabled` 值。

### 会话方法 {/* #session-methods */}

#### `createSession()` {/* #createsession */}

```typescript
const session = await auth.createSession(userId, metadata)
```

创建 ID 自动生成、有效期为七天的标准化 Mastra 会话，不会创建远程 Neon Auth 会话。

#### `validateSession()` {/* #validatesession */}

```typescript
const session = await auth.validateSession(sessionId)
```

验证 Neon Auth 会话令牌并返回标准化的 Mastra 会话；若会话无效，则返回 `null`。

#### `refreshSession()` {/* #refreshsession */}

```typescript
const session = await auth.refreshSession(sessionId)
```

通过 Neon Auth 验证会话。达到配置的更新间隔时，Neon Auth 会自动刷新会话。

#### `destroySession()` {/* #destroysession */}

```typescript
const sessionId = auth.getSessionIdFromRequest(request)
if (sessionId) await auth.destroySession(sessionId)
```

传入 `getSessionIdFromRequest()` 获取的已签名会话 Cookie 值，而不是 `validateSession()` 返回的 `id`。`destroySession()` 会尝试通过 Neon Auth 退出登录端点撤销该会话。网络错误或非 2xx 响应可能使会话保持有效，而且该方法不会为这些失败抛出错误。Mastra 发送 `getClearSessionHeaders()` 返回的标头时，只会清除 Mastra 主机上匹配的 Cookie，不会清除另一台 Neon Auth 主机上的 Cookie。因此，从 Studio 退出登录后，独立的 Neon Auth 会话可能仍然有效。

撤销会话不会使已签发的 JWT 失效。通过 JWT 验证的 Bearer Token 仍可用于认证，因为验证过程不会检查 Neon Auth 会话。JWT 验证也不要求包含过期时间声明，因此没有该声明的令牌可能在退出登录后继续可用。

### 方法 {/* #methods */}

#### `getRoles()` {/* #getroles */}

```typescript
const roles = await rbac.getRoles(user)
```

若提供了 `getUserRoles`，则返回该函数给出的角色。否则，如果设置了 `organizationId` 或会话有活跃组织，就使用用户的会话 Cookie 从 Neon Auth 读取并返回该用户在组织中的角色；非成员没有角色。没有组织时，返回用户在 Neon Auth 中的角色，例如 `user` 或 `admin`。

Bearer JWT 请求没有会话，因此除非提供 `getUserRoles`，否则不会获得角色。JWT 的 `role` 声明（`authenticated`）绝不会被用作 Mastra 角色。

#### `hasRole()` {/* #hasrole */}

```typescript
const allowed = await rbac.hasRole(user, 'admin')
```

检查用户是否具有指定角色。

#### `getPermissions()` {/* #getpermissions */}

```typescript
const permissions = await rbac.getPermissions(user)
```

通过 `roleMapping` 解析用户角色，并返回 Mastra 权限模式。

#### `hasPermission()` {/* #haspermission */}

```typescript
const allowed = await rbac.hasPermission(user, 'agents:read')
```

检查解析出的权限是否允许请求的权限。

#### `hasAllPermissions()`和`hasAnyPermission()` {/* #hasallpermissions-and-hasanypermission */}

```typescript
const canReadAndRun = await rbac.hasAllPermissions(user, ['agents:read', 'agents:execute'])
const canReadAnything = await rbac.hasAnyPermission(user, ['agents:read', 'workflows:read'])
```

检查用户是否具有请求的全部权限或至少一项权限。

#### `getAvailableRoles()` {/* #getavailableroles */}

```typescript
const roles = await rbac.getAvailableRoles()
```

返回除 `_default` 外配置的所有角色名称。

#### `getRolePermissions()` {/* #getrolepermissions */}

```typescript
const permissions = await rbac.getRolePermissions('member')
```

解析为角色配置的权限模式。
