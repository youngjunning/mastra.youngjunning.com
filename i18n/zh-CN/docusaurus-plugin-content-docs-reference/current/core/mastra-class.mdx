# Mastra 类

`Mastra` 类是 Mastra 应用的中央编排器，负责管理 Agent、Workflow、存储、日志、可观测性等。通常只需创建一个 `Mastra` 实例来协调整个应用。

`Mastra` 是顶层注册表，可在其中注册需要供整个应用访问的 Agent、Workflow、工具及其他组件。

## 使用示例 {/* #usage-example */}

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { PinoLogger } from '@mastra/loggers'
import { LibSQLStore } from '@mastra/libsql'
import { weatherWorkflow } from './workflows/weather-workflow'
import { weatherAgent } from './agents/weather-agent'

export const mastra = new Mastra({
  workflows: { weatherWorkflow },
  agents: { weatherAgent },
  storage: new LibSQLStore({
    id: 'mastra-storage',
    url: ':memory:',
  }),
  logger: new PinoLogger({
    name: 'Mastra',
    level: 'info',
  }),
})
```

如果希望通过 Workflow 调度器自动发送延迟通知记录及通知摘要，请启用定时通知分发：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  agents: { supportAgent },
  storage,
  notifications: {
    dispatch: {
      enabled: true,
      cron: '*/1 * * * *',
      batchSize: 100,
    },
  },
})
```

`notifications.dispatch.enabled` 允许运行内部通知分发 Workflow，默认 Cron 表达式为 `*/1 * * * *`。分发器从存储中读取到期的通知记录，按 `agentId`、`resourceId` 和 `threadId` 汇总摘要，并通过 Agent 线程运行时发出信号。它不是面向用户的入口。首次出现延迟通知或摘要通知时，分发计划及其底层 Workflow 调度器才会延迟启动；从不延迟通知的应用完全不会运行调度器。

## 方法 {/* #methods */}

### `recoverAllDurableAgents()` {/* #recoveralldurableagents */}

重新驱动所有已注册持久化 Agent 中处于 `running` 状态的孤立运行。`recovery.durableAgents` 设为 `'auto'` 时，会在启动时自动调用。也可直接调用以手动恢复，或从定时任务中调用。

需要持久化存储。若使用内存存储，进程重启后便没有可恢复的数据。

恢复流程最多同时处理五个 Agent，每个 Agent 最多同时等待五次运行，独立于 `recovery.workflowConcurrency`。每次内置的 `recoverActiveRuns()` 尝试，会为 `recover()` 初始化及整个恢复后 Workflow 的结束合计等待最多 30 秒，之后释放名额供其他运行使用。这些限制约束的是等待，不是仍在执行的任务。它们也不是整个恢复流程的截止时间：发现过程及被覆盖的自定义恢复方法不受此预算限制。

超时的尝试会在后台继续。其结果为 `status: 'skipped'`、`reason: 'recovery-timeout'`，并带有未来的 `retryAt`。它只计入 `skipped`，不计入 `recovered`、`succeeded` 或 `failed`。Mastra 会自动安排重新检查，但会等原尝试结束后再检查，以免启动第二次执行。随后恢复流程会在重试前检查持久化快照和所有权，并跳过已结束或暂停的运行。迟到的结果不会改变已返回的计数。

开始关闭时，恢复流程不再调度新的 Agent 和运行。恢复遍历及原有尝试（包括初始化或执行超时的尝试）与活跃执行共用同一个关闭排空过程。恢复等待超时不会取消原尝试，也不会获得独立的关闭排空时段。

Mastra 会将运行留在当前执行的控制下，并计入 `skipped`。一旦该执行的所有权声明可能失效，便会自动重新检查，使进程崩溃后的恢复无须再次调用。`shutdown()` 会取消待执行的重新检查。参见[运行所有权](/docs/harness/durable-agents#run-ownership)。

```typescript
const result = await mastra.recoverAllDurableAgents()
// { agents: 2, recovered: 3, succeeded: 3, failed: 0, skipped: 1 }
```
