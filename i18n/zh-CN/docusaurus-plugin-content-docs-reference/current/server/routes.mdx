# 服务器路由

调用 `server.init()` 时，服务器适配器会注册这些路由。如果配置了 `prefix` 选项，所有路由都会加上该前缀。

## Agent {/* #agents */}

|方法|路径|描述 |
| - | - | - |
| `GET` | `/api/agents` | 列出所有 Agent |
| `GET` | `/api/agents/:agentId` | 按 ID 获取 Agent（支持版本查询参数） |
| `POST` | `/api/agents/:agentId/generate` | 生成 Agent 响应 |
| `POST` | `/api/agents/:agentId/stream` | 流式返回 Agent 响应 |
| `POST` | `/api/agents/:agentId/send-message` | 向活跃或空闲的线程发送用户消息 |
| `POST` | `/api/agents/:agentId/queue-message` | 将用户消息加入队列，留待线程的下一轮处理 |
| `POST` | `/api/agents/:agentId/queue-signal` | 将带类型的信号加入队列，留待线程的下一轮处理 |
| `POST` | `/api/agents/:agentId/signals` | 向活跃或空闲的线程发送底层信号 |
| `POST` | `/api/agents/:agentId/threads/subscribe` | 订阅线程的事件流 |
| `POST` | `/api/agents/:agentId/threads/abort` | 中止线程，可同时清除待处理的信号 |
| `POST` | `/api/agents/:agentId/threads/signals/cancel` | 取消线程中指定的待处理信号 |
| `POST` | `/api/agents/:agentId/send-tool-approval` | 批准或拒绝 Tool 调用，并通过线程订阅继续接收输出 |
| `POST` | `/api/agents/:agentId/resume-stream` | 使用自定义数据恢复已挂起的 Agent 流 |
| `GET` | `/api/agents/:agentId/tools` | 列出 Agent 的 Tool |
| `POST` | `/api/agents/:agentId/tools/:toolId/execute` | 执行 Agent 的 Tool |

### 获取 Agent 的查询参数 {/* #get-agent-query-parameters */}

`GET /api/agents/:agentId` 接受以下可选查询参数，用于选择已保存的配置版本，以覆盖代码中定义的 Agent 配置。

|参数|类型 |默认 |描述 |
| - | - | - | - |
| `status` | `'draft' \| 'published'` | `'published'` | 选择要使用的已保存版本。`draft` 返回最新版本，`published` 返回当前生效的版本。 |
| `versionId` | `string` | 无 | 指定要使用的版本 ID，优先于 `status`。 |

```bash
# Get agent with active published overrides (default)
GET /api/agents/my-agent

# Get agent with latest draft overrides
GET /api/agents/my-agent?status=draft

# Get agent with a specific version's overrides
GET /api/agents/my-agent?versionId=abc123
```

### Agent 消息路由 {/* #agent-message-routes */}

使用 `POST /api/agents/:agentId/send-message` 向正在运行的 Agent 循环发送用户消息，或唤醒空闲线程。如果需要等当前运行结束后再由 Mastra 发起下一次运行，请使用 `POST /api/agents/:agentId/queue-message`。

要按相同顺序将带类型的信号加入队列，请使用 `POST /api/agents/:agentId/queue-signal`，并用 `signal` 字段替代 `message`。`signal` 字段的结构与 `POST /api/agents/:agentId/signals` 所用的结构相同。

两条消息路由使用相同的请求体：

```typescript oxfmt:false
{
  message: string | Array<TextPart | FilePart> | {
    contents: string | Array<TextPart | FilePart>;
    attributes?: Record<string, JSONValue>;
    metadata?: Record<string, unknown>;
    providerOptions?: ProviderMetadata;
  };
  runId?: string;
  resourceId?: string;
  threadId?: string;
  ifActive?: {
    behavior?: 'deliver' | 'persist' | 'discard';
    attributes?: Record<string, string | number | boolean>;
  };
  ifIdle?: {
    behavior?: 'wake' | 'persist' | 'discard';
    streamOptions?: Omit<AgentExecutionOptions, 'messages'>;
    attributes?: Record<string, string | number | boolean>;
  };
}
```

省略 `runId` 时，必须提供 `resourceId` 和 `threadId`。`ifIdle` 仅用于以线程为目标的请求。

#### 发送消息 {/* #send-a-message */}

```bash
curl -X POST http://localhost:4111/api/agents/supportAgent/send-message \
  -H 'Content-Type: application/json' \
  -d '{
    "message": {
      "contents": "Show the shorter version.",
      "attributes": { "sentFrom": "web" }
    },
    "resourceId": "user_123",
    "threadId": "thread_456"
  }'
```

#### 将消息放入队列 {/* #queue-a-message */}

```bash
curl -X POST http://localhost:4111/api/agents/supportAgent/queue-message \
  -H 'Content-Type: application/json' \
  -d '{
    "message": "Also check whether the tests need updates.",
    "resourceId": "user_123",
    "threadId": "thread_456"
  }'
```

两条路由均返回以下响应：

```typescript oxfmt:false
{
  accepted: true;
  runId: string;
  signal?: CreatedAgentSignal;
}
```

### 中止线程与取消信号的路由 {/* #thread-cancellation-routes */}

`POST /api/agents/:agentId/threads/abort` 接受 `{ resourceId?: string, threadId: string, clearPendingSignals?: boolean }`，返回 `{ aborted: boolean }`。只有将 `clearPendingSignals` 设为 `true` 才会清除待处理输入。接收请求的进程会先在本地清除输入，再中止线程，并在需要时将清除操作转发给当前持有线程的进程。如果线程由远程进程持有，`aborted: true` 仅表示请求已发出。

`POST /api/agents/:agentId/threads/signals/cancel` 只取消指定的待处理输入，线程会继续运行。JSON 请求体包含以下字段：

<PropertiesTable
  content={[
{ name: 'resourceId', type: 'string', isOptional: true, description: '记忆线程对应的资源 ID。' },
{ name: 'threadId', type: 'string', description: '包含待处理信号的线程 ID。' },
{ name: 'signalIds', type: 'string[]', description: '要取消的信号 ID，共 1 至 1,000 个，每个 ID 均不能为空。' },
]}
/>

响应为 `{ cancelledSignalIds: string[] }`，只包含处理请求的服务器进程已取消的信号 ID。每个 ID 只出现一次。未知 ID，以及已交付执行或移交给其他持有者的信号 ID，均不会出现在响应中。请求体无效时返回 HTTP 400。

两条路由都要求 `agents:execute` 权限，并根据经过身份验证的请求上下文检查线程归属。配置细粒度授权后，还需要该线程的 `memory:write` 权限，即使线程尚未保存。取消操作适用于共享该记忆线程的所有 Agent。它不会撤销已持久化的消息、状态更新、通知记录或接收确认，也不影响由 `continueWithMessages()` 发起的后续执行。

即使本地没有待处理的匹配项，服务器也会通过共享的 PubSub 后端发布请求中的所有 ID，让订阅该线程的其他进程可以移除匹配的待处理输入。传播是异步的，不保证送达，HTTP 响应也不确认远程取消是否成功。中止时的清除操作只作用于接收请求的进程和当前持有线程的进程。SDK 的用法见[客户端取消方法](/reference/client-js/agents#cancelqueuedmessages)。

同时升级 `@mastra/core` 和 `@mastra/server`，即可使用线程范围的取消功能和中止时清除信号的功能。在多进程部署中，请升级所有可能持有该线程的工作进程。如果 Agent 使用的核心版本不支持这些行为，服务器会返回 HTTP 501，待处理输入会保留。支持中止线程的旧版核心仍可处理未设置 `clearPendingSignals: true` 的普通中止请求。

### 通过线程订阅处理 Tool 审批 {/* #subscription-tool-approval-routes */}

客户端已有活跃的线程订阅时，请使用 `POST /api/agents/:agentId/send-tool-approval`。该路由会恢复运行并返回 JSON 确认。恢复后的流式数据块通过 `POST /api/agents/:agentId/threads/subscribe` 传送。

该路由接受以下请求体：

```typescript oxfmt:false
{
  resourceId: string;
  threadId: string;
  toolCallId: string;
  approved: boolean;
  requestContext?: Record<string, unknown>;
}
```

该路由返回以下响应：

```typescript oxfmt:false
{
  accepted: true;
  runId: string;
  toolCallId?: string;
}
```

### 运行次数统计响应 {/* #run-counts-response */}

`/api/workflows/run-counts` 返回每个已注册 Workflow 处于 `running` 和 [`suspended`](/docs/workflows/suspend-and-resume) 状态的运行数量。返回的对象以 Mastra 配置中的 Workflow 注册键为键，服务器可能会缓存该响应几秒钟。

```typescript oxfmt:false
{
  [workflowRegistryKey: string]: {
    running: number;
    suspended: number;
  };
}
```

### 动态 Workflow {/* #dynamic-workflows */}

动态 Workflow 定义（测试版）以 JSON 表示，通过 `workflowDefinitions` 存储域持久化，并在正在运行的实例中动态注册。参见[动态 Workflow](/docs/workflows/dynamic-workflows)。

|方法|路径|描述 |
| - | - | - |
| `GET` | `/api/stored/workflows` | 列出动态 Workflow 定义，可按 `status` 和 `authorId` 筛选 |
| `GET` | `/api/stored/workflows/:dynamicWorkflowId` | 按 ID 获取动态 Workflow 定义 |
| `POST` | `/api/stored/workflows` | 新增或更新定义（可附带辅助 `dependencies`），并在运行中的实例注册 |
| `DELETE` | `/api/stored/workflows/:dynamicWorkflowId` | 删除动态 Workflow 定义，并取消注册正在运行的实例中的对应 Workflow |

在启用身份验证的服务器上，读取路由需要 `stored-workflows:read` 权限，写入路由需要 `stored-workflows:write` 权限。注册后，可通过上文的常规 `/api/workflows/:workflowId` 路由执行动态 Workflow。

### 运行结果 {/* #run-result */}

`POST /api/workflows/:workflowId/start-async` 会等待 `run.start()` 完成并返回执行结果。`status` 区分成功、失败、触发警戒条件、挂起和暂停。`steps` 对象以步骤 ID 为键，每个步骤都有自己的状态，并在有输出时包含 `output`。运行成功时，顶层的 `result` 就是 Workflow 的输出。

执行结果包含以下字段。其中，适用于特定状态的字段仅在对应状态下出现：

```typescript oxfmt:false
{
  status: 'success' | 'failed' | 'tripwire' | 'suspended' | 'paused';
  input: unknown;                      // The inputData the run started with
  state?: unknown;                     // Workflow state
  result?: unknown;                    // Workflow output on success
  error?: unknown;                     // Error on failure
  tripwire?: unknown;                  // Tripwire details
  suspendPayload?: unknown;           // Payload returned on suspension
  suspended?: string[][];              // Suspended step paths
  steps: {
    [stepId: string]: {
      status: string;
      output?: unknown;
      error?: unknown;
      startedAt: number;               // Unix time in milliseconds
      endedAt?: number;
    };
  };
}
```

`GET /api/workflows/:workflowId/runs/:runId` 返回运行元数据和执行状态，优先使用已持久化的快照，没有快照时使用内存中的运行记录。此路由用 `payload` 表示运行输入，用 `initialState` 表示状态。`workflowName` 是 Workflow 的 `id`，可能与路径中的注册键不同。

```typescript oxfmt:false
{
  runId: string;
  workflowName: string;
  resourceId?: string | null;
  createdAt: string;                   // ISO date string
  updatedAt: string;                   // ISO date string
  status: string;                      // Includes active states such as 'running' and 'waiting'
  initialState?: Record<string, unknown>;
  result?: unknown;
  error?: unknown;
  payload?: unknown;                   // The inputData the run started with
  steps?: {
    [stepId: string]: {
      payload?: unknown;               // This step's input
      status: string;
      output?: unknown;
      error?: unknown;                 // Present when the step failed
      startedAt: number;
      endedAt?: number;
    } | {
      payload?: unknown;
      status: string;
      output?: unknown;
      error?: unknown;
      startedAt: number;
      endedAt?: number;
    }[];                              // forEach iteration results
  };
  activeStepsPath?: Record<string, number[]>;
  serializedStepGraph?: unknown[];
  suspendedPaths?: Record<string, number[]>;
  resumeLabels?: Record<string, unknown>;
  waitingPaths?: Record<string, number[]>;
}
```

对于已持久化的运行，可用 `fields` 查询参数缩减响应，只需从 `result`、`error`、`payload`、`steps`、`activeStepsPath` 和 `serializedStepGraph` 中选取所需字段，用逗号分隔。传入其他字段名会返回 HTTP 400。元数据字段和 `status` 始终保留，`initialState` 非空时也会保留。

```bash
curl 'http://localhost:4111/api/workflows/my-workflow/runs/1faf6f91-b9ac-4db0-9fb3-326687ba1972?fields=result'
```

`steps` 中的条目可以是单个步骤的结果，也可以是 `forEach` 步骤的迭代结果数组。读取 `status` 或 `output` 之前，请先判断该条目是否为数组。

传入 `withNestedWorkflows=false` 可跳过在 `steps` 中展开嵌套 Workflow 的执行详情。当前 Workflow 自身的步骤条目仍会保留。

使用内存记录时，响应会带有 `isFromInMemory: true`，并返回运行元数据、`status` 和空的 `steps`，省略 `result`、`payload` 和 `error`。`createdAt` 和 `updatedAt` 均使用当前时间。此类响应不支持字段筛选或展开嵌套 Workflow。

## 知识 {/* #knowledge */}

这些路由默认不注册。将 `@mastra/server/server-adapter` 中的 `KNOWLEDGE_ROUTES` 添加到 `server.apiRoutes`，并在 `Mastra` 的 `knowledge` 下注册实例。这些路由要求 `@mastra/core` 1.81.0 或更高版本，其中两条链接路由要求 1.82.0 或更高版本。配置 RBAC Provider 后，所有路由都要求 `knowledge:read` 权限。未配置时会跳过此检查。配置步骤见 [Studio 知识](/docs/studio/knowledge)。

| 方法 | 路径 | 说明 |
| - | - | - |
| `GET` | `/api/knowledge` | 列出已注册的知识实例。配置 FGA 时按权限筛选 |
| `GET` | `/api/knowledge/:knowledgeKey/tree` | 列出根作用域，或列出 `parentId` 下的子作用域 |
| `GET` | `/api/knowledge/:knowledgeKey/pages/:pageId` | 获取页面及其祖先页面、笔记、置顶信息和引用的页面 |
| `GET` | `/api/knowledge/:knowledgeKey/link-counts` | 统计 `pageId` 指定的每个页面的入站和出站链接数 |
| `GET` | `/api/knowledge/:knowledgeKey/pages/:pageId/links` | 列出单个页面的入站和出站链接 |
| `GET` | `/api/knowledge/:knowledgeKey/graph` | 获取大小受限的页面关系图，其中包含父子关系边、提及关系边和作用域授权 |
| `GET` | `/api/knowledge/:knowledgeKey/search` | 搜索页面名称、描述、正文和笔记 |
| `GET` | `/api/knowledge/:knowledgeKey/activity` | 列出近期变更，可限定到单个作用域或页面 |
| `GET` | `/api/knowledge/:knowledgeKey/events` | 通过服务器发送事件（SSE）推送调用方有权读取的写入事件。参见[知识事件](#knowledge-events) |

`:knowledgeKey` 是实例在 `knowledge: { ... }` 中注册时使用的键。

### 知识查询参数 {/* #knowledge-query-parameters */}

| 路由 | 参数 |
| - | - |
| `tree` | `parentId`（查询根作用域时省略）、`cursor`、`limit`（1 到 100） |
| `pages/:pageId` | `noteCursor`、`noteLimit`（1 到 100） |
| `link-counts` | `pageId`（每个页面传一次，可指定 1 到 200 个页面） |
| `pages/:pageId/links` | `direction` 可取 `in`、`out` 或 `both`（默认值） |
| `graph` | `rootId`（省略时遍历所有根作用域）、`maxPages`（1 到 500） |
| `search` | `q`（1 到 200 个字符）、`scopeId`（可重复传入，最多指定 20 个作用域）、`limit`（1 到 100） |
| `activity` | `scopeId`、`pageId`、`cursor`、`limit`（1 到 100） |

### 知识访问权限和错误 {/* #knowledge-access-and-errors */}

如果 `server.auth` 和 `studio.auth` 均未配置，路由会以实例所有者的身份读取并返回全部内容。配置身份验证后，路由只读取请求上下文键 `MASTRA_KNOWLEDGE_PRINCIPALS_KEY` 所指定的作用域能访问的内容。将该键的值设为作用域数组或 `'all'`。

| 状态码 | 返回条件 |
| - | - |
| `403` | 已配置身份验证，但未设置 `MASTRA_KNOWLEDGE_PRINCIPALS_KEY`。`GET /api/knowledge` 不读取此键，因此不会因此返回 `403` |
| `404` | 实例不存在，或 FGA Provider 拒绝对该实例授予 `knowledge:read` 权限，或页面不存在，或调用方无权读取该页面。对于无权读取的页面，链接路由会返回计数为零或空链接列表 |
| `500` | `MASTRA_KNOWLEDGE_PRINCIPALS_KEY` 的值既不是数组也不是 `'all'`，或其中的某个作用域不匹配任何已声明的作用域类型 |
| `501` | `@mastra/core` 的版本低于路由要求，或存储没有链接索引（仅适用于链接路由） |

配置 FGA Provider 后，系统会以 `knowledge` 为资源类型、以注册键为资源标识，检查每个实例的 `knowledge:read` 权限。`GET /api/knowledge` 只列出调用方有权读取的实例。启用 `requireForProtectedRoutes` 后，系统会拒绝 `GET /api/knowledge` 请求，因为这条路由和其他列表路由一样没有 FGA 元数据。未配置 RBAC Provider 时会跳过 `knowledge:read` 检查。

NestJS 适配器尚不支持这些路由。

### 知识事件 {/* #knowledge-events */}

对于每次已提交且涉及调用方可读内容的写入，`GET /api/knowledge/:knowledgeKey/events` 会发送一个事件，结构如下。

```typescript oxfmt:false
{
  kind: 'scope' | 'page' | 'note' | 'pin';
  op: string;       // such as 'create', 'update', 'delete' or 'merge'
  pageId?: string;  // left out when the caller can't read the page, including a deleted one
  scopeId?: string; // left out when the caller can't read the scope
  at: string;       // ISO timestamp
}
```

如果一次写入未涉及调用方可读的内容，服务器就不会发送事件。事件只包含 ID，请通过其他路由获取变更内容。如果没有 `pageId`，请刷新 `scopeId` 指定的作用域。

服务器每 25 秒发送一条保活注释，并在五分钟后关闭事件流。事件流关闭后请重新连接。新的事件流会重新读取调用方的作用域，因此权限被撤销后，调用方将不再收到相应的更新。断开期间的写入不会重放，请在重新连接后刷新显示的内容。

### 删除实验 {/* #delete-an-experiment */}

两条删除路由都会删除实验及其结果记录。如果存储支持可观测性和删除 Trace，Mastra 会先删除实验产生的 Trace，以及其中的 Span 和关联到这些 Trace 的信号，再删除实验。

知道实验属于哪个数据集时，请使用限定到该数据集的路由。

```bash
curl -X DELETE http://localhost:4111/api/datasets/dataset-id/experiments/experiment-id
```

该路由接受可选的 `organizationId` 和 `projectId` 查询参数。如果数据集不在指定的租户范围内、实验不存在，或实验不属于该数据集，路由会返回 `404`。

没有数据集引用时，请使用顶层路由。例如，所属数据集被删除后，实验的 `datasetId` 被清除，实验就会失去与数据集的关联。

```bash
curl -X DELETE http://localhost:4111/api/experiments/experiment-id
```

顶层路由接受可选的 `organizationId` 和 `projectId` 查询参数。只要传入其中一个，删除操作就限于指定的租户范围。租户范围不匹配时，路由会返回 `{ "success": true }`，实验会保留。如果未传入租户参数且实验不存在，路由会返回 `404`。

删除成功时返回 `{ "success": true }`。顶层路由在租户范围不匹配时也返回相同响应，所有数据会保留。如果安装的 `@mastra/core` 没有通过 `experiment-deletion` 功能标志声明支持，两条路由都会返回 `501`，尚未支持此功能的旧版本也会如此。如果存储不支持可观测性或删除 Trace，Mastra 会记录警告并保留 Trace，同时删除实验及其结果记录。如果因其他原因无法删除 Trace，路由会返回 `500`，并保留实验及其结果记录。Trace 按每批 1,000 条删除，因此此时可能已经删除了一部分。重新发送请求即可完成删除。

### 永久清除数据项 {/* #purge-a-dataset-item */}

`DELETE /api/datasets/:datasetId/items/:itemId/purge` 会从所有历史版本、删除标记和关联的实验结果中永久清除该数据项存储的内容。此操作不会创建新的数据集版本，也无法撤销。有关完整的清除行为，请参阅 [`dataset.purgeItem()`](/reference/datasets/purgeItem)。

```bash
curl -X DELETE http://localhost:4111/api/datasets/dataset-id/items/item-id/purge
```

此路由接受可选的查询参数 `organizationId` 和 `projectId`。如果数据集不属于指定的租户范围，或该数据项在数据集中没有历史记录，则返回 `404`。如果已安装的 `@mastra/core` 未通过 `dataset-item-purge` 功能标志声明支持此操作，则返回 `501`。如果 MongoDB 存储不支持事务，则在修改任何数据之前返回 `500`。彻底清除成功后返回 `{ "success": true }`。

### 调用方驱动的实验路由 {/* #caller-driven-experiment-routes */}

如果由您自己的编排器（例如 Temporal Workflow）控制实验循环，并由 Mastra 保存权威记录，请使用这些路由。运行实验项、提交结果和结束实验这三种操作均可安全重试。创建请求只有包含调用方提供的 `id` 时才可安全重试。未提供该值时，每次重试都会创建一个新实验。运行实验项和提交结果时，以 `(experimentId, itemId, attempt)` 为键更新或插入结果。若实验已结束，结束操作会返回已存储的实验记录。

#### 创建实验的请求体 {/* #create-experiment-request-body */}

向 `/api/datasets/:datasetId/experiments` 发送包含 `start: false` 的 POST 请求，即可创建实验而不启动它。如果需要 Mastra 通过运行实验项的路由执行各项，请同时提供 `targetType` 和 `targetId`。如果只通过结果路由导入结果，则省略这两个字段。

```typescript oxfmt:false
{
  start?: boolean;              // false creates the experiment without running it. Defaults to true.
  id?: string;                  // Caller-supplied experiment id (e.g. a workflow run id) for idempotent creates
  targetType?: 'agent' | 'workflow' | 'scorer'; // Provide with targetId, or omit both
  targetId?: string;
  scorerIds?: string[];         // Run-level scorer ids, resolved server-side. Requires a target when start is false.
  name?: string;
  description?: string;
  metadata?: Record<string, unknown>;
  version?: number;             // Pin to a specific dataset version (defaults to latest)
  provenance?: {
    source?: string;
    sourceId?: string;
    sourceVersion?: string;
    metadata?: Record<string, unknown>;
  };
  grouping?: {                  // Stable grouping dimensions for comparisons and repeated trials
    experimentSetId?: string;
    comparisonId?: string;
    variantId?: string;
    trialIndex?: number;
  };
}
```

当 `start` 为 `false` 时，返回 `{ experimentId, status, totalItems, datasetVersion }`。

#### 运行实验项的请求体 {/* #run-experiment-item-request-body */}

`POST /api/datasets/:datasetId/experiments/:experimentId/items/:itemId/run` 对单个实验项执行实验目标，再运行解析出的评分器，最后更新或插入结果。创建该实验时必须指定目标。

```typescript oxfmt:false
{
  attempt?: number;             // Zero-based repetition index. Defaults to 0.
  requestContext?: Record<string, unknown>; // Merged with the item's own request context (item wins)
}
```

返回 `{ result, scores }`，其中包含已持久化的结果记录和该实验项的评分。

#### 提交实验结果的请求体 {/* #submit-experiment-result-request-body */}

```typescript oxfmt:false
{
  itemId: string;               // Dataset item this result belongs to
  attempt?: number;             // Zero-based repetition index. Defaults to 0.
  input?: unknown;              // Defaults to the dataset item input
  output?: unknown;             // Output produced by the external runner
  groundTruth?: unknown;        // Defaults to the dataset item groundTruth
  error?: {                     // Failure info when the item run failed
    message: string;
    stack?: string;
    code?: string;
  } | null;
  startedAt?: string;           // ISO date
  completedAt?: string;         // ISO date
  traceId?: string;
  scores?: Array<{              // Externally computed scores, persisted keyed by runId = experimentId
    scorerId: string;
    scorerName?: string;
    score: number;
    reason?: string;
    metadata?: Record<string, unknown>;
  }>;
}
```

返回已持久化的实验结果记录。

#### 完成实验 {/* #finalize-experiment */}

`POST /api/datasets/:datasetId/experiments/:experimentId/finalize` 无需请求体。服务器根据已持久化的结果记录按实验项统计，将实验标记为 `completed`，并返回更新后的实验记录。`succeededCount` 统计至少有一次尝试未出错的项，`failedCount` 统计每次尝试都出错的项，`skippedCount` 统计从未提交结果的项。

#### 调用方驱动的实验的错误响应 {/* #caller-driven-experiment-error-responses */}

|状态 |触发条件 |
| - | - |
|`400` | 向已指定目标的实验提交结果（`EXPERIMENT_HAS_TARGET`）、请求运行未指定目标的实验项（`EXPERIMENT_HAS_NO_TARGET`）、未同时提供 `targetType` 和 `targetId`（`EXPERIMENT_INVALID_TARGET`），或实验锁定的数据集版本不含任何数据项（`EXPERIMENT_NO_ITEMS`） |

### 评分器列表响应 {/* #list-scorers-response */}

响应是一个键值映射，包含通过 [`Mastra` 类](/reference/core/mastra-class)的 `scorers` 选项注册的评分器，以及关联到 Agent 和 Workflow 的评分器。Agent 关联的评分器和通过选项注册的评分器以评分器 ID 为键。Workflow 关联的评分器目前以评分器名称为键。调用 `/api/scores/scorers/:scorerId` 时使用响应中的键，按评分器 ID 查询已保存的评分时使用 `scorer.config.id`。


## 常用查询参数 {/* #common-query-parameters */}

### 分页 {/* #pagination */}

大多数用于列出资源的端点支持以下分页参数：

```typescript oxfmt:false
{
  page?: number;   // Page number (0-indexed)
  perPage?: number; // Items per page (default: 10)
}
```

### 过滤 {/* #filtering */}

查询 Workflow 运行记录时，可以使用以下筛选参数：

```typescript oxfmt:false
{
  fromDate?: string;  // ISO date string
  toDate?: string;    // ISO date string
  status?: string;    // Run status filter
  resourceId?: string; // Filter by resource
}
```

## 错误响应 {/* #error-responses */}

所有路由都返回以下格式的错误：

```typescript oxfmt:false
{
  error: string;      // Error message
  details?: unknown;  // Additional details
}
```

常见状态码：

|状态码|含义|
| - | - |
| 400 | 请求无效：参数无效 |
| 401 | 未授权：缺少身份验证信息或验证信息无效 |
| 403 | 禁止访问：权限不足 |
| 404 | 未找到：资源不存在 |
| 500 | 服务器内部错误 |
