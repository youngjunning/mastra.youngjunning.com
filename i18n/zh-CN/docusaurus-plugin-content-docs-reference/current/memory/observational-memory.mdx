# 观察记忆

**引入版本：** `@mastra/memory@1.1.0`

观察记忆（OM）是 Mastra 面向长上下文智能体的记忆系统。**Observer** 追踪对话并生成观察记录；**Reflector** 将相关记录合并，并提炼贯穿对话的规律，对这些记录进行重组。两者共同维护观察日志。随着对话增长，这份日志会取代原始消息历史。

## 用法 {/* #usage */}

```typescript title="src/mastra/agents/agent.ts"
import { Memory } from '@mastra/memory'
import { Agent } from '@mastra/core/agent'

export const agent = new Agent({
  id: 'my-agent',
  name: 'my-agent',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  memory: new Memory({
    options: {
      observationalMemory: true,
    },
  }),
})
```

## 配置 {/* #configuration */}

`observationalMemory` 选项接受 `true`、配置对象或 `false`。设为 `true` 时，OM 会启用自动模型选择。传入配置对象时，可以在顶层设置 `model`，也可以设置 `observation.model` 和／或 `reflection.model`。如果省略所有模型字段，每个角色默认使用 `'auto'`。

Observer 的输入支持多模态。OM 为 Observer 构建对话记录时，会保留 `[Image #1: screenshot.png]` 这样的文本占位符，并在可行时一并发送底层图像内容。单线程观察和多线程批量观察均如此。非图像文件只以占位符呈现。

OM 使用快速的本地 token 估算来判断是否达到阈值。文本由 `tokenx` 估算；对于图像类输入，则采用针对不同提供商的启发式规则，并在元数据不完整时使用确定性的后备规则。

```typescript title="src/mastra/agents/agent.ts"
const memory = new Memory({

      model: '__GATEWAY_OPENAI_MODEL_LUNA__',
      observation: {
        extract: [
          new Extractor({
            name: 'User profile',
            instructions: 'Extract stable user profile facts that should be remembered.',
            schema: z.object({
              name: z.string().optional(),
              timezone: z.string().optional(),
            }),
          }),
        ],
      },
    },
  },
})
```

### 提取行为 {/* #extraction-behavior */}

- 提取的值保存在该线程 OM 元数据的 `om.extracted` 下。
- 内置提取器的值也会镜像到兼容性元数据字段 `currentTask`、`suggestedResponse` 和 `threadTitle`。
- `thread-title` 只有在启用 `observation.threadTitle` 后才会更新线程标题。
- `observation.extract` 在观察期间运行；`reflection.extract` 在反思期间运行。
- 带 schema 的提取器会追加一次结构化输出请求。
- 无 schema 的提取器是直接在 Observer 或 Reflector 输出中产生的内联字符串提取器。
- 动态提取器函数会在可用时收到运行时上下文，包括 `source`、`threadId`、`resourceId`、`mainAgent`、`memory` 和 `requestContext`。
- `WorkingMemoryExtractor` 使用常规提取器流程，通过当前 `Memory` 实例更新工作记忆。工作记忆带有 JSON schema 时，它会执行结构化提取，并跳过 OM 元数据持久化，避免工作记忆内容在 OM 提取元数据中重复保存。
- 设置 `workingMemory.schema` 后，`WorkingMemoryExtractor` 会在保存每次更新前按该 schema 验证。不匹配的更新会被跳过并报告为提取失败，原有工作记忆保持不变。schema 不会作为结构化输出约束发送给模型，因此一次无效的工作记忆更新不会使其他提取器失败。可选字段中的 `null` 会被视为未提供。
- `observationalMemory.observation.manageWorkingMemory` 会添加 `WorkingMemoryExtractor`，并将 `workingMemory.agentManaged` 默认设为 `false`。启用工作记忆时，还会将 `workingMemory.useStateSignals` 默认设为 `true`。
- 提取失败会在 OM 标记数据中报告，不会丢弃其他成功提取的值。

### 共享 token 预算 {/* #shared-token-budget */}

启用 `shareTokenBudget` 后，总预算为 `observation.messageTokens + reflection.observationTokens`，本例中即 100k。若观察记录只使用 30k token，消息最多可使用 70k；消息较短时，观察记录也有更多空间，直到触发反思。使用共享预算时，必须关闭异步缓冲。

```typescript title="src/mastra/agents/agent.ts"
import { Memory } from '@mastra/memory'
import { Agent } from '@mastra/core/agent'

export const agent = new Agent({
  id: 'my-agent',
  name: 'my-agent',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  memory: new Memory({
    options: {
      observationalMemory: {
        shareTokenBudget: true,
        observation: {
          messageTokens: 20_000,
          bufferTokens: false,
        },
        reflection: {
          observationTokens: 80_000,
        },
      },
    },
  }),
})
```

### 异步缓冲 {/* #async-buffering */}

默认情况下，异步缓冲处于启用状态，设置如下：

- `observation.bufferTokens: 0.2`：每达到 `messageTokens` 的 20% 就缓冲一次。
- `observation.bufferActivation: 0.8`：激活后保留阈值对应内容的 20%。
- `reflection.bufferActivation: 0.5`：观察记录达到反思阈值的一半时，开始后台反思。

缓冲的 Observer 调用不会产生后续提示，激活时也会清除已存储的提示。关于阈值与 `blockAfter` 之间的行为，参见[后台缓冲跟不上时](#when-buffering-falls-behind)。

设置 `observation.bufferTokens: false` 可同时关闭观察与反思的缓冲。两者随后都会在达到各自阈值时同步运行。

```typescript oxfmt:false
observationalMemory: {
  observation: {
    bufferTokens: false,
  },
}
```

已弃用的 `scope: 'resource'` 不支持异步缓冲。

## 早期激活 {/* #early-activation */}

默认情况下，消息历史达到 `observation.messageTokens` 时，缓冲的观察记录会激活。OM 也可以提前激活它们，这对提示词缓存即将过期或智能体切换模型提供商的情况有帮助。两种情况下，下次请求都无法复用缓存的提示词，因此发送经过压缩的较短上下文不会增加额外成本。

- `activateAfterIdle`：线程空闲达到指定时长后激活。接受毫秒数（`300_000`）、时长字符串（`'5m'`、`'1hr'`）、根据提供商确定提示词缓存 TTL 的 `'auto'`，或按提供商指定 TTL 的对象（参见[按提供商设置空闲 TTL](#per-provider-idle-ttls)）。
- `activateOnProviderChange`：若下一步骤使用的 `provider/model` 与上一个智能体步骤所用的不同，则激活。默认为 `false`。

```typescript title="src/mastra/memory.ts"
import { Memory } from '@mastra/memory'

const memory = new Memory({
  options: {
    observationalMemory: {
      activateAfterIdle: 'auto',
      activateOnProviderChange: true,
    },
  },
})
```

顶层设置只适用于观察。反思须通过嵌套的 `reflection` 设置单独启用：

```typescript title="src/mastra/memory.ts"
import { Memory } from '@mastra/memory'

const memory = new Memory({
  options: {
    observationalMemory: {
      activateAfterIdle: '5m',
      observation: {
        activateAfterIdle: false,
      },
      reflection: {
        activateAfterIdle: '10m',
        activateOnProviderChange: true,
      },
    },
  },
})
```

在此示例中，观察忽略顶层空闲设置，而反思启用空闲激活和提供商变化时激活。

### 自动空闲 TTL {/* #automatic-idle-ttls */}

设置 `activateAfterIdle: 'auto'` 后，Mastra 会根据当前模型提供商选择空闲 TTL：

| 提供商 | 自动 TTL |
| - | - |
| Anthropic、OpenRouter、未知提供商、xAI | 5 分钟 |
| DeepSeek | 1 小时 |
| Google Gemini | 24 小时 |
| Groq | 2 小时 |
| OpenAI，且 `providerOptions.openai.promptCacheRetention: "24h"` | 1 小时 |
| OpenAI，且 `providerOptions.openai.promptCacheRetention: "in_memory"` | 5 分钟 |
| OpenAI `gpt-4*`、`gpt-5`、`gpt-5-*`，以及 `gpt-5.1` 至 `gpt-5.4`（含带 `-` 后缀的变体） | 5 分钟 |
| 其他 OpenAI 模型 | 1 小时 |

如需固定 TTL，请使用 `'5m'` 或 `300_000`。

### 按提供商设置空闲 TTL {/* #per-provider-idle-ttls */}

`'auto'` 无法识别为单条消息设置的缓存 TTL，例如 Anthropic 的 `cacheControl: { type: 'ephemeral', ttl: '1h' }`。它仍会使用该提供商默认的 5 分钟 TTL，因此缓冲的观察记录可能在 1 小时缓存尚未失效时就激活。若需按提供商指定 TTL，请传入对象：

```typescript title="src/mastra/memory.ts"
import { Memory } from '@mastra/memory'

const memory = new Memory({
  options: {
    observationalMemory: {
      activateAfterIdle: { default: 'auto', anthropic: '1h' },
    },
  },
})
```

将 `anthropic` 条目设为与 `cacheControl.ttl` 相同的 TTL。Mastra 不会读取单条消息的缓存设置，因此这两个值需要手动保持一致。

对象按以下规则解析：

- 键为提供商名称。Mastra 会取模型提供商 ID 中第一个 `.` 之前的部分，不区分大小写地进行比较。因此 `anthropic` 同时匹配 `anthropic` 和 `anthropic.messages`。如果 Claude 由其他提供商提供，则使用该提供商的键，例如 `amazon-bedrock`。键不能包含 `.` 或 `/`。
- 每个值接受与单个 TTL 相同的形式：毫秒数、时长字符串、`'auto'`，或用于关闭该提供商空闲激活的 `false`。
- `default` 适用于未单独指定键的所有提供商。如果没有 `default`，这些提供商不会在空闲时激活。
- `observation.activateAfterIdle` 和 `reflection.activateAfterIdle` 也接受相同的对象。`observation.activateAfterIdle` 对象会替换顶层值，不与其合并。

## 空闲时缓冲 {/* #buffer-on-idle */}

设置 `observation.bufferOnIdle: true` 后，智能体轮次结束并进入空闲状态时，系统会在后台缓冲观察记录。这样，短轮次无需等待下一轮或达到 `messageTokens` 阈值即可被观察。

```typescript title="src/mastra/memory.ts"
import { Memory } from '@mastra/memory'

const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        bufferOnIdle: true,
      },
    },
  },
})
```

`bufferOnIdle` 默认关闭，且独立于 `bufferTokens`：`bufferTokens` 控制步骤执行期间的缓冲，`bufferOnIdle` 控制空闲轮次结束时的缓冲。

## 后台缓冲跟不上时 {/* #when-buffering-falls-behind */}

如果消息到达速度超过 Observer 的缓冲速度，消息历史可能在缓冲片段准备好之前越过 `messageTokens`。在 `messageTokens` 与 `observation.blockAfter` 之间（后者默认值为 `1.2`，按默认阈值计算为 36,000 token），Mastra 会继续在后台缓冲，并在后续步骤激活片段，智能体无需等待。

如果缓冲片段激活后，待处理 token 数仍达到 `blockAfter`，例如较大的工具结果留下尚未覆盖的尾部消息，就会执行同步观察。达到 `blockAfter` 时，激活流程会先限时等待仍在生成的缓冲观察记录；若等待超时，Mastra 会同步观察剩余消息。迟到的观察结果若对应消息已被观察，则会被丢弃。由空闲 TTL 或提供商变化触发的激活不会等待。

超过 `blockAfter` 后，激活流程可能选择更多片段，从而越过保留目标。缓冲激活通常会至少保留一部分上下文（约 1,000 token 与配置的保留下限中的较小值）；但若单个片段覆盖整个待处理窗口，它仍会激活，并可能留下更少内容。

异步缓冲的 Observer 调用不会生成后续提示，因为延迟生成的提示在激活时可能已经过时。缓冲片段激活后，已存储的建议回复和当前任务都会被清除。

反思也以相同方式缓冲。观察记录达到 `reflection.bufferActivation`（默认 `0.5`）所指定的 `reflection.observationTokens` 比例时，后台反思开始运行；若超过 `reflection.blockAfter`（默认 `1.2`）仍没有可用的缓冲反思，则同步运行。

## 重试和失败策略 {/* #retries-and-failure-policy */}

Observer 和 Reflector 的模型调用遇到暂时性提供商错误时会重试。每个阶段都有两项设置：

- `maxRetries`：首次模型调用后的重试次数，默认为 `8`。这是该阶段唯一的重试设置；底层模型调用不会执行提供商级重试。
- `failurePolicy`：重试耗尽后的处理方式。`'abort'`（默认）使当前轮次失败；`'continue'` 允许当前轮次继续。

```typescript title="src/mastra/memory.ts"
import { Memory } from '@mastra/memory'

const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        maxRetries: 8,
        failurePolicy: 'continue',
      },
      reflection: {
        maxRetries: 8,
        failurePolicy: 'continue',
      },
    },
  },
})
```

提供商故障通常会同时影响两个阶段。如果希望当前轮次在故障时继续，应为两个阶段都设置此策略。

使用 `'continue'` 时，Mastra 通过 OM 诊断报告失败，将失败输入保留到后续周期，并允许当前轮次继续。系统不会推进观察边界或丢弃未观察的消息。Reflector 失败时，已持久化的观察记录仍会保留，并在下次达到阈值时重试反思。

该策略只处理同步运行期间 Observer 和 Reflector 的模型或提供商故障，包括达到 `blockAfter`、关闭异步缓冲，以及资源作用域中的观察。持久化、索引、转换、锁定、不变量和显式中止相关的失败仍属致命错误。

无论策略如何，后台缓冲失败都不会中断当前轮次。失败会以 `om_buffering_failed` 报告，相关输入仍待处理。如果待处理内容持续增长并达到 `blockAfter`，同步观察就会应用 `failurePolicy`。

:::warning

`'continue'` 无法为长时间故障兜底。未观察的消息会一直待处理，并不断累积在主智能体的上下文中，直到达到模型的上下文上限。

:::

## 时间间隔标记 {/* #temporal-gap-markers */}

如果线程中上一条消息距新用户消息至少已过 10 分钟，时间间隔标记会在新消息前插入简短提醒。默认关闭。

```typescript title="src/mastra/memory.ts"
import { Memory } from '@mastra/memory'

const memory = new Memory({
  options: {
    observationalMemory: {
      temporalMarkers: true,
    },
  },
})
```

标记会存入记忆，同时以临时提醒事件形式发出，方便客户端将其显示为时间线提示。Observer 也能看到这些标记，因此观察记录可以注明事件发生的时间，例如“用户在间隔 2 天后询问部署问题”。

## token 估算 {/* #token-estimates */}

OM 根据本地 token 估算决定何时进行观察，而不是依据提供商的用量报告。文本使用 `tokenx` 估算；图像采用针对不同提供商的启发式规则，图像类 `file` 内容也遵循该规则。提供商实际计算的 token 数可能高于估算值，因此需要[上下文溢出恢复](/docs/memory/observational-memory#context-overflow-recovery)。

### token 数缓存 {/* #token-count-cache */}

OM 会把估算值缓存在消息元数据中，避免每次检查阈值时都重新计算相同内容：

- 每个内容部分的估算值存储在 `part.providerMetadata.mastra` 中；只要缓存版本和分词器来源一致，就会复用。
- 只有字符串内容、没有分段内容的消息使用消息级缓存。
- 每轮都会重新计算消息和对话的额外开销；只缓存内容本身的估算值。
- `data-*` 和 `reasoning` 内容部分会被跳过，也不会缓存。

### 为文件提供自定义估算值 {/* #supplying-your-own-estimate-for-a-file */}

可以为 `image` 或 `file` 内容部分通过 `providerMetadata.mastra.tokenEstimate` 附加 token 估算值。计数器会直接使用该值：

```typescript
const filePart = {
  type: 'file',
  data: 'storage://bucket/large-report.pdf',
  mimeType: 'application/pdf',
  filename: 'large-report.pdf',
  providerMetadata: {
    mastra: {
      tokenEstimate: {
        v: 0,
        source: 'client',
        key: 'client',
        tokens: 100_000,
      },
    },
  },
}
```

- `v`：缓存 schema 版本。设为 `0`。OM 不会读取调用方提供的此字段。
- `source`：必须是 `'client'`。这表示该条目具有权威性，不会被重新计算或覆盖。
- `key`：设为 `'client'`。框架生成的条目会在此放置内容哈希；使用 `'client'` 可使估算值在多次写入后保持稳定。
- `tokens`：要使用的 token 数，必须是有限的非负数。

只有 `image` 和 `file` 内容部分会采用自定义估算值。`text` 和 `tool-invocation` 内容部分始终会计数。

## 限制 Observer 重读的内容 {/* #limiting-what-the-observer-re-reads */}

默认情况下，每批新消息都会连同完整的观察日志，以及先前的 `current-task` 和 `suggested-response` 值，一起作为上下文发送给 Observer。日志变大时，可设置 `observation.previousObserverTokens` 限制其大小：

```typescript title="src/mastra/memory.ts"
import { Memory } from '@mastra/memory'

const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        previousObserverTokens: 10_000,
      },
    },
  },
})
```

- `false`（默认）：发送完整日志。
- 数字，例如 `2000`：保留最近约相应 token 数的观察记录。
- `0`：不发送先前的观察记录。

如果有缓冲的反思尚待处理，其已覆盖的观察记录行会在截断前由反思结果替换。

## 让 Observer 管理工作记忆 {/* #let-the-observer-manage-working-memory */}

设置 `observation.manageWorkingMemory: true` 后，由 Observer 持续更新[工作记忆](/docs/memory/working-memory)，无需依赖主智能体调用工作记忆工具。

```typescript title="src/mastra/memory.ts"
import { Memory } from '@mastra/memory'

const memory = new Memory({
  options: {
    workingMemory: {
      enabled: true,
    },
    observationalMemory: {
      observation: {
        manageWorkingMemory: true,
      },
    },
  },
})
```

这会添加 `WorkingMemoryExtractor`，并改变两项工作记忆的默认值：

- `workingMemory.agentManaged` 默认为 `false`，因此主智能体不再收到工作记忆工具和指令。如需保留，请设为 `true`。
- `workingMemory.useStateSignals` 默认为 `true`，将工作记忆从系统提示词移至状态信号中，使更新不致使提示词缓存失效。

## 挂钩 {/* #hooks */}

`observationalMemory.hooks` 接受两类钩子：

- **生命周期钩子**（`onObservationStart`、`onObservationEnd`、`onReflectionStart`、`onReflectionEnd`）用于遥测。它们会收到 `threadId`、`resourceId` 和 `trigger`；结束钩子还会收到模型调用的 `usage`、`providerMetadata` 和可能发生的 `error`。它们不会改变 OM 保存的内容。
- **转换钩子**（`beforeObservation`、`afterObservation`、`beforeReflection`、`afterReflection`）用于改变周期中流转的数据。不返回内容则原样传递输入，也可返回替换值。

```typescript
const memory = new Memory({
  options: {
    observationalMemory: {
      hooks: {
        // Drop or redact messages before the Observer sees them.
        beforeObservation: ({ messages }) => ({
          messages: messages.filter(m => !isSensitive(m)),
        }),
        // Rewrite observations before they are persisted.
        afterObservation: ({ observations }) => ({
          observations: redact(observations),
        }),
        // Rewrite the text the Reflector condenses.
        beforeReflection: ({ observations }) => ({
          observations: stripInternalNotes(observations),
        }),
        afterReflection: async ({ observations, resourceId }) => {
          await syncToExternalStore(resourceId, observations)
        },
      },
    },
  },
})
```

所有路径都会等待转换钩子完成，包括手动 `observe()` 和 `reflect()`、轮次中的同步观察，以及异步缓冲。如果 `beforeObservation` 返回空的 `messages` 数组，就会跳过 Observer 调用，但这些消息仍标记为已观察。若转换钩子抛出错误，周期会在提交转换后的文本前失败；已运行的提取器回调和其他副作用不会回滚。

`afterObservation` 和 `afterReflection` 只替换观察或反思文本，不会修改线程元数据中的结构化提取值；反思提取也在 `afterReflection` 之前运行。不要把后置钩子当作整个周期的数据脱敏边界。

钩子会收到 `threadId` 和 `resourceId`，因此也可通过 `memory.updateWorkingMemory()` 更新工作记忆。这些更新与 OM 提交不是原子操作。

若不希望 Observer 读取技能指令，请使用 [`skillResultRedactor`](#skillresultredactor)。

## 迁移现有线程 {/* #migrating-existing-threads */}

无需迁移。线程首次超过 `observation.messageTokens` 时，OM 会读取并观察现有消息，一并处理积压内容。在已弃用的资源作用域下，同一资源各线程中所有未观察的消息会一起处理；线程较多的用户可能需要等待较长时间。

## 流式数据部分 {/* #streaming-data-parts */}

观察记忆会在智能体执行期间发出带类型的数据部分，客户端可据此实时展示 UI 反馈。这些数据与智能体响应一起流式传输。

### 读取提取器结果 {/* #read-extractor-results */}

两个完成事件的 `data` 负载都包含提取器输出。提取器字段如下：

```typescript
interface DataOmObservationEndPart {
  type: 'data-om-observation-end'
  data: {
    /** Whether the completed work was an observation or reflection */
    operationType: 'observation' | 'reflection'
    /** Values extracted during this OM operation, keyed by extractor slug */
    extractedValues?: Record<string, unknown>

```

两个提取器字段均可选。完成事件可能包含提取值、失败信息、两者都有，或两者都没有。`data-om-observation-end` 报告同步完成；`data-om-buffering-end` 报告已完成但尚待激活的后台缓冲工作，此时提取器元数据已经持久化。`DataOmBufferingEndPart` 带有相同的提取器字段，这两种类型都从 `@mastra/memory/processors` 导出。客户端示例参见[从流中读取提取值](/docs/memory/observational-memory#read-extracted-values-from-a-stream)。

### `data-om-status` {/* #data-om-status */}

每个智能体循环步骤在模型生成前发出一次。它提供当前记忆状态的快照，包括两个上下文窗口的 token 用量，以及异步缓冲内容的状态。

```typescript
interface DataOmStatusPart {
  type: 'data-om-status'
  data: {
    windows: {
      active: {
        /** Unobserved message tokens and the threshold that triggers observation */
        messages: { tokens: number; threshold: number }
        /** Observation tokens and the threshold that triggers reflection */
        observations: { tokens: number; threshold: number }
      }
      buffered: {
        observations: {
          /** Number of buffered chunks staged for activation */
          chunks: number
          /** Total message tokens across all buffered chunks */
          messageTokens: number
          /** Projected message tokens that would be removed if activation happened now (based on bufferActivation ratio and chunk boundaries) */
          projectedMessageRemoval: number
          /** Observation tokens that will be added on activation */
          observationTokens: number
          /** idle: no buffering in progress. running: background observer is working. complete: chunks are ready for activation. */
          status: 'idle' | 'running' | 'complete'
        }
        reflection: {
          /** Observation tokens that were fed into the reflector (pre-compression size) */
          inputObservationTokens: number
          /** Observation tokens the reflection will produce on activation (post-compression size) */
          observationTokens: number
          /** idle: no reflection buffered. running: background reflector is working. complete: reflection is ready for activation. */
          status: 'idle' | 'running' | 'complete'
        }
      }
    }
    recordId: string
    threadId: string
    stepNumber: number
    /** Increments each time the Reflector creates a new generation */
    generationCount: number
  }
}
```

`buffered.reflection.inputObservationTokens` 表示发送给 Reflector 的观察记录大小。`buffered.reflection.observationTokens` 表示压缩结果的大小，即反思激活后将取代这些观察记录的内容大小。客户端可以用这两个值展示压缩率。

客户端可以根据原始值计算百分比和激活后的估算值：

```typescript
// Message window usage %
const msgPercent = status.windows.active.messages.tokens / status.windows.active.messages.threshold

// Observation window usage %
const obsPercent =
  status.windows.active.observations.tokens / status.windows.active.observations.threshold

// Projected message tokens after buffered observations activate
// Uses projectedMessageRemoval which accounts for bufferActivation ratio and chunk boundaries
const postActivation =
  status.windows.active.messages.tokens -
  status.windows.buffered.observations.projectedMessageRemoval

// Reflection compression ratio (when buffered reflection exists)
const { inputObservationTokens, observationTokens } = status.windows.buffered.reflection
if (inputObservationTokens > 0) {
  const compressionRatio = observationTokens / inputObservationTokens
}
```

## 独立使用 {/* #standalone-usage */}

大多数应用应使用 `Memory` 类。若要进行基准测试、实验，或必须让 OM 按特定顺序与[护栏](/docs/agents/guardrails)等处理器一起运行，则可直接使用 `ObservationalMemory` 引擎。

将引擎包装在 `ObservationalMemoryProcessor` 中。它需要 `Memory` 实例来加载和持久化消息。存储适配器上的 `stores.memory` 类型是可选的，因此需要断言或检查它：

```typescript title="src/mastra/agents/agent.ts"
import { Agent } from '@mastra/core/agent'
import { LibSQLStore } from '@mastra/libsql'
import { Memory } from '@mastra/memory'
import { ObservationalMemory, ObservationalMemoryProcessor } from '@mastra/memory/processors'

const storage = new LibSQLStore({
  id: 'my-storage',
  url: 'file:./memory.db',
})

const memory = new Memory({ storage })

const om = new ObservationalMemory({
  storage: storage.stores.memory!,
  memory,
  model: '__GATEWAY_GOOGLE_MODEL_FLASH__',
  observation: {
    messageTokens: 20_000,
  },
  reflection: {
    observationTokens: 60_000,
  },
})

const omProcessor = new ObservationalMemoryProcessor(om, memory)

export const agent = new Agent({
  id: 'my-agent',
  name: 'My Agent',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  inputProcessors: [omProcessor],
  outputProcessors: [omProcessor],
})
```

引擎接受与 `observationalMemory` 配置相同的选项，另加 `storage`、`onDebugEvent` 和 `obscureThreadIds`。参见[独立配置](#standalone-config)。

`om.observe()` 只在待处理 token 达到阈值时执行观察。传入 `force: true` 可立即观察待处理消息；跳过阈值只对本次调用有效。

```typescript
const result = await om.observe({ threadId, resourceId, force: true })
// result.observed is true when pending messages were observed
```

智能体无需通过此方式从上下文窗口错误中恢复；[上下文溢出恢复](/docs/memory/observational-memory#context-overflow-recovery)会处理这种情况。

## 回忆工具 {/* #recall-tool */}

`retrieval` 为真值时，Mastra 会注册 `recall` 工具，用于分页浏览观察记录组所对应的原始消息。在默认资源作用域下，该工具可列出线程（`mode: "threads"`），并通过 `threadId` 浏览其他线程；它也支持跨线程搜索。设置 `retrieval: { vector: true }` 可启用语义搜索（`mode: "search"`）；设置 `scope: 'thread'` 则将工具限制在当前线程。该工具会自动添加到智能体。

启用检索后，OM 还会注入说明，指导智能体何时核对细节、如何搜索和翻页，以及何时读取原始消息。这些说明从首轮开始就会提供，包括只读运行，并且只描述已配置的模式。反思后的记录组会标为 `_kind: reflection_`，提醒智能体将其视为有信息损失的摘要。可通过 `retrieval: { instructions: '...' }` 在内置说明后追加自定义指引。

### 观察记录分页 {/* #observation-pages */}

配置向量搜索后，`mode: "observations"` 可读取搜索命中附近的原始观察记录组，包括已被反思压缩掉的组和尚未激活的缓冲组。请原样复制命中结果中的 `groupId`；在资源作用域下还需复制其 `threadId`：

```json
{
  "mode": "observations",
  "threadId": "source-thread-id",
  "groupId": "group-id-from-search",
  "direction": "after",
  "limit": 5
}
```

设置 `direction: "before"` 可向前翻页；省略 `direction` 则会包含锚定组本身。分页结果和后续调用会返回 `{ results, count, hasMore }`，并提示是否存在尚未观察的较新消息。

### 搜索结果 {/* #search-results */}

搜索结果按日期列出，共用 2,000 token 的文本限额。因此，较长的记录组会从最符合查询的行开始缩短。已在智能体上下文中的结果会返回简短引用，排名较低的命中则可利用腾出的空间。`limit` 统计的是摘录而非引用，因此 `count` 可能大于 `limit`。

### 存储要求 {/* #storage-requirements */}

搜索结果中的组 ID 包含承载它的记录（`groupId@recordId`），因此翻页时只需读取单条记录。变更之前已建立索引的组仍可使用，但翻页时需要扫描线程的观察历史。翻页要求存储适配器支持观察历史筛选，因此应与 `@mastra/memory` 一同升级。Convex 用户还需重新部署 Mastra 服务端函数。

### ModelByInputTokens {/* #modelbyinputtokens */}

`ModelByInputTokens` 根据输入 token 数选择模型。它会选择能覆盖实际输入大小的最小阈值对应的模型。

#### 构造函数 {/* #constructor */}

```typescript
new ModelByInputTokens(config)
```

`config` 是一个对象，其 `upTo` 键将 token 阈值（数字）映射到目标模型。每个层级都必须指定具体模型 ID，不能使用 `"auto"`。

#### 例子 {/* #example */}

```typescript
import { ModelByInputTokens } from '@mastra/memory'

const selector = new ModelByInputTokens({
  upTo: {
    10_000: 'google/gemini-2.5-flash', // Fast for small inputs
    40_000: '__GATEWAY_OPENAI_MODEL_LUNA__', // Stronger for medium inputs
    1_000_000: '__GATEWAY_OPENAI_MODEL__', // Most capable for large inputs
  },
})
```

#### 行为 {/* #behavior */}

- 系统会在内部排序阈值，因此配置对象中的顺序无关紧要。
- `inputTokens ≤ smallest threshold` → 使用该阈值对应的模型。
- `inputTokens > largest threshold` → `resolve()` 抛出错误。如果发生在 OM 的 Observer 或 Reflector 运行期间，OM 会通过 TripWire 中止，因此调用方收到的是空的 `text` 结果或流式 `tripwire`，而不是正常的智能体回复。
- OM 计算 Observer 或 Reflector 调用的输入 token 数，并直接确定匹配的模型层级。

### skillResultRedactor {/* #skillresultredactor */}

`skillResultRedactor` 会创建一个 `beforeObservation` 转换钩子，在 Observer 模型读取内置 Agent Skills 工具（`skill`、`skill_search` 和 `skill_read`）的结果前将其遮盖。每个结果会替换成占位符，但工具调用仍会保留。因此 Observer 仍能记录使用了哪个技能、传入了哪些参数，而不会接触技能正文。

```typescript
import { Memory } from '@mastra/memory'
import { skillResultRedactor } from '@mastra/memory/hooks'

const memory = new Memory({
  options: {
    observationalMemory: {
      model: '__GATEWAY_GOOGLE_MODEL_FLASH__',
      hooks: {
        beforeObservation: skillResultRedactor(),
      },
    },
  },
})
```

传入 `toolNames` 可遮盖另一组工具的结果。若要与自定义转换组合，请串联两个钩子的输出，并等待每个钩子完成：

```typescript oxfmt:false
const dropSkillResults = skillResultRedactor()

hooks: {
  beforeObservation: async input => {
    const messages = (await dropSkillResults(input))?.messages ?? input.messages
    return { messages: messages.filter(m => m.role !== 'signal') }
  },
}
```

#### 参数 {/* #parameters-1 */}

<PropertiesTable
  content={[
{
  name: 'toolNames',
  type: 'readonly string[]',
  description:
    '要遮盖其结果的工具名称。默认是内置技能工具：`skill`、`skill_search` 和 `skill_read`。可通过此项指定其他工具。',
  isOptional: true,
},
]}
/>

#### 返回值 {/* #returns */}

`(input: { messages: MastraDBMessage[] } & ObserveHookContext) => { messages: MastraDBMessage[] } | undefined`

钩子返回的消息中，匹配的工具结果会被占位符替换。如果没有消息匹配，则返回 `undefined`，负载会原样传递。工具调用、参数及其他所有消息保持不变。
