# 反馈

**添加于：** `@mastra/core@1.18.0`

反馈 API 存储和查询人机交互可观察性信号，例如评级、点赞、评论和更正。使用[feedback guide](/docs/observability/feedback) for usage patterns.

## 使用示例 {/* #usage-example */}

以下示例通过可观察性入口点记录持久跟踪的评级。`addFeedback()` is optional on the entrypoint, so check that the active observability implementation supports it before calling it.

```typescript
if (!mastra.observability.addFeedback) {
  throw new Error('Feedback is not supported by the active observability implementation')
}

await mastra.observability.addFeedback({
  traceId: 'trace-123',
  spanId: 'span-456',
  feedback: {
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
    comment: 'Helpful answer.',
  },
})
```

## 创建反馈 {/* #create-feedback */}

### `addFeedback(args)` {/* #addfeedbackargs */}

向配置的导出器发送有关跟踪或跨度的反馈。

```typescript
await mastra.observability.addFeedback?.({
  traceId: 'trace-123',
  spanId: 'span-456',
  feedback: {
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
    comment: 'Helpful answer.',
  },
})
```

<PropertiesTable
  content={[
{ name: 'traceId', type: 'string', description: 'Trace that anchors the feedback target.', isOptional: true },
{ name: 'spanId', type: 'string', description: 'Span that anchors the feedback target.', isOptional: true },
{
  name: 'correlationContext',
  type: 'CorrelationContext',
  description: 'Live span or trace context to emit from without rehydrating the target from storage.',
  isOptional: true,

{ name: 'feedback', type: 'FeedbackInput', description: 'Feedback payload to add.' },

没有`correlationContext`, each exporter handles the target trace or span at its own destination. `MastraStorageExporter` resolves it from local storage. A failed local lookup doesn't block other exporters. `MastraPlatformExporter` doesn't require local storage. Use `flush()` or `shutdown()`耗尽待交付的货物。

本地查找需要目标跨度的父链通过其根，因此反馈继承正确的根标签。如果重试后仍然缺少任何祖先，则存储导出器会记录警告并跳过本地写入。其他出口商仍然收到反馈。

### `createFeedback(args)` {/* #createfeedbackargs */}

通过Observability存储域创建一条反馈记录。存储级调用直接写入存储，因此包括`timestamp`.

```typescript
await observability.createFeedback({
  feedback: {
    feedbackId: 'feedback-1',
    timestamp: new Date(),
    traceId: 'trace-123',
    spanId: 'span-456',
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
    comment: 'Helpful answer.',
  },
})
```

HTTP 和客户端 SDK 创建路由接受`CreateFeedbackBody`, which requires a nonblank `feedback.traceId` and allows an optional `spanId`. The client supplies a missing `feedbackId` and ISO `timestamp` before retries. Direct OSS HTTP calls can omit them for server defaults. An optional top-level `contextMode` selects supplied context or stored-span resolution. OSS defaults to `"provided"`。平台默认为`"resolve"`。看[信号写入选项](/reference/client-js/observability#signal-write-options):

```typescript
await mastraClient.createFeedback({
  feedback: {
    traceId: 'trace-123',
    spanId: 'span-456',
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
  },
})
```

对于OSS HTTP请求，认证用户的ID优先`feedbackUserId`. Without an authenticated user, supply `feedbackUserId` explicitly or leave it null for anonymous feedback. `userId` describes the span user and isn't used as the HTTP feedback author. Direct storage calls retain the deprecated `userId` author alias when `feedbackUserId` is omitted. An explicit null author stays null.

### `batchCreateFeedback(args)` {/* #batchcreatefeedbackargs */}

通过Observability存储域创建多条反馈记录。此方法不会被 HTTP 路由公开，或者`@mastra/client-js`.

```typescript
await observability.batchCreateFeedback({
  feedbacks: [
    {
      feedbackId: 'feedback-1',
      timestamp: new Date(),
      traceId: 'trace-123',
      feedbackSource: 'user',
      feedbackType: 'rating',
      value: 1,
    },
    {
      feedbackId: 'feedback-2',
      timestamp: new Date(),
      traceId: 'trace-123',
      feedbackSource: 'qa',
      feedbackType: 'comment',
      value: 'Needs a citation before shipping.',
    },
  ],
})
```

## 删除反馈 {/* #delete-feedback */}

### `deleteFeedback(args)` {/* #deletefeedbackargs */}

按 ID 最多删除 1,000 条反馈记录。该操作是幂等的：不存在的 id 将被忽略，并且空的`feedbackIds` array is a no-op. When `organizationId` or `resourceId` is provided, only records matching that scope are deleted.

```typescript
await mastraClient.deleteFeedback({
  feedbackIds: ['feedback-1', 'feedback-2'],
})
```

<PropertiesTable
  content={[
{
  name: 'feedbackIds',
  type: 'string[]',
  description: 'Ids of the feedback records to delete. Accepts at most 1,000 ids.',
},
{
  name: 'organizationId',
  type: 'string',
  description: 'Restricts the delete to records with this organization id.',
  isOptional: true,
},
{
  name: 'resourceId',
  type: 'string',
  description: 'Restricts the delete to records with this resource id.',
  isOptional: true,
},
]}
/>

OSS HTTP路由返回`{ success: boolean }`. `mastraClient.deleteFeedback()` returns `Promise<{ success: boolean } | { accepted: true }>` to also support Platform backends with queued batch deletion. An accepted response means cleanup is queued, and records can remain readable until cleanup runs. See [client deletion response handling](/reference/client-js/observability#deleting-traces). The storage domain method returns `Promise<void>`. Requests with more than 1,000 ids return `400`, and a server running `@mastra/core` older than `1.66.0` returns `501`. ClickHouse vNext, PostgreSQL vNext, DuckDB, and the in-memory store implement deletion. Every other adapter, including LibSQL and MongoDB, throws `OBSERVABILITY_STORAGE_DELETE_FEEDBACK_NOT_IMPLEMENTED`.

在 ClickHouse 上，删除使用主反馈事件表上的轻量级删除来删除读取中的行，包括 OLAP 查询，但不能保证立即物理删除，因此开源部署必须配置一个[observability retention period](/reference/storage/retention) to physically purge them. Each request is marked applied once its delete succeeds; if the delete fails, the request stays unapplied, doesn't block `updateFeedbackReviewStatus()` on the still-visible feedback, and you retry by calling `deleteFeedback()` again. `updateFeedbackReviewStatus()` also retries the delete and throws a not-found error if the retry succeeds, or saves the new status and throws the delete's error if it fails again. Open-source deployments have no background reconciler. ClickHouse applies a TTL to deletion requests only when all five signals have finite retention. See [ClickHouse native TTL](/reference/storage/retention#clickhouse-native-ttl). Delete APIs leave the separate delta cursor table untouched. Its rows contain identifiers rather than feedback payloads and expire within two days.

### `deleteScores(args)` {/* #deletescoresargs */}

按 id 最多删除 1,000 条分数记录。它的行为就像`deleteFeedback()` with `scoreIds` in place of `feedbackIds`, and Oracle Database also implements it. Unsupported adapters throw `OBSERVABILITY_STORAGE_DELETE_SCORES_NOT_IMPLEMENTED`.

```typescript
await mastraClient.deleteScores({
  scoreIds: ['score-1', 'score-2'],
})
```

## 更换反馈 {/* #replace-feedback */}

`PUT /api/observability/feedback/:feedbackId`接受完整的`{ feedback: { ... } }` replacement. Keep the original `feedbackId`, `traceId`, and `timestamp`, and include every field you want to retain. Omitted optional fields are cleared. The URL and body IDs must match. See [the client example](/reference/client-js/observability#replacing-feedback).

OSS 在返回成功之前写入其配置的存储，并独立通知支持导出器。`contextMode` has the same meaning as on create. In `"resolve"` mode, the local trace or span must exist. A missing feedback record is created from the full replacement. Changing an existing record's trace or timestamp returns `409`.

内存中、PostgreSQL vNext、DuckDB 和 ClickHouse vNext 存储支持替换。查看`capabilities.feedbackReplacement` on the server. Unsupported versions return `501`. Sequential retries of the original HTTP create don't undo a replacement. Direct storage `createFeedback()` calls retain upsert behavior. Pass `onConflict: 'ignore'` to keep an existing record.

ClickHouse 支持使用现有架构，无需迁移。来自不同进程的并发写入可能会发生竞争，因此它不能保证重叠创建和替换之间的顺序。使用此适配器时，将编辑序列化到同一反馈记录。

要在不依赖本地存储的情况下将替换发送到配置的导出器，请使用可观察性入口点：

```typescript
await mastra.observability.replaceFeedback?.({
  traceId: 'trace-123',
  feedback: {
    feedbackId: 'feedback-1',
    timestamp: new Date('2026-11-11T12:00:00.123Z'),
    feedbackType: 'thumbs',
    value: -1,
  },
})
```

每个出口商独立处理其目的地。`MastraStorageExporter` resolves local span context when needed, and `MastraPlatformExporter` sends a PUT to Platform. Exporters without a replacement handler skip the event. `flush()` and `shutdown()` wait for pending deliveries.

## 更新审核状态 {/* #updating-review-status */}

要更改已配置的导出器目标的审核状态，请传递反馈 ID 和`"reviewed"` or `"needs-review"`:

```typescript
await mastra.observability.updateFeedbackReviewStatus?.({
  feedbackId: 'feedback-123',
  reviewStatus: 'reviewed',
})
await mastra.observability.flush()
```

即使反馈未存储在本地，也会将更新审核发送给支持它们的每个导出器。称呼`flush()` or `shutdown()` to wait for pending deliveries.

## HTTP 路由 {/* #http-routes */}

这些路由属于 Mastra 运行时并使用其配置的可观察性存储。它们与[unversioned Mastra Platform Feedback API](/docs/mastra-platform/api#feedback-api), which doesn't provide a feedback creation route.

|方法|路径|目的|许可 |
| - | - | - | - |
|`GET` | `/api/observability/feedback` | List feedback records | `observability:read` |
| `POST` | `/api/observability/feedback` | Create a feedback record | `observability:write` |
| `PUT` | `/api/observability/feedback/:feedbackId` | Replace a complete feedback record | `observability:write` |
| `DELETE` | `/api/observability/feedback` | Delete feedback records by id | `observability:delete` |
| `DELETE` | `/api/observability/scores` | Delete score records by id | `observability:delete` |
| `PATCH` | `/api/observability/feedback/:feedbackId/review-status` | Update review status | `observability:write` |
| `POST` | `/api/observability/feedback/aggregate` | Return one aggregate value | `observability:read` |
| `POST` | `/api/observability/feedback/breakdown` | Group feedback by dimensions | `observability:read` |
| `POST` | `/api/observability/feedback/timeseries`|按间隔进行铲斗反馈 |`observability:read` |

### 列出查询参数 {/* #list-query-parameters */}

`GET /api/observability/feedback`将其参数作为 URL 查询参数。这[Mastra Platform Feedback API](/docs/mastra-platform/api#feedback-api) accepts the same parameters on its `GET /feedback` endpoint.

```bash
curl -sS "http://localhost:4111/api/observability/feedback?traceId=trace-123&environment=production&feedbackType=rating&page=0&perPage=20"
```

每一个领域[`FeedbackFilter`](#feedbackfilter) is accepted as a top-level query parameter with the same name, for example `traceId`, `spanId`, `feedbackType`, `feedbackSource`, `feedbackUserId`, `reviewStatus`, `entityName`, `environment`, `experimentId`, or `tags`. Repeat a parameter to pass multiple values where the filter accepts an array, such as `feedbackType=rating&feedbackType=thumbs`. Pass object-valued filters such as `timestamp` as JSON, for example `timestamp={"start":"2026-01-01T00:00:00Z"}` URL-encoded.
