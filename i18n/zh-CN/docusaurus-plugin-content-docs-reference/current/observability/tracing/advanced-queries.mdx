# 查询 Trace 和 Span

使用结构化过滤条件查询已完成的 Trace 或 Span，也可以聚合统计数量、错误率、延迟百分位数、token 用量和成本。每项操作都可通过客户端 SDK、HTTP API 和 CLI 使用：

| 操作 | 用途 | 客户端 SDK | HTTP 端点 | CLI 命令 |
| - | - | - | - | - |
| [查询 Trace](#query-traces) | 根据根 Span 字段或关联 Span 的条件列出匹配的 Trace。 | `queryTraces()` | `POST /api/observability/traces/query` | `mastra api trace query` |
| [查询 Span](#query-spans) | 列出各个 Trace 中的 Span，包括嵌套的 Agent 运行和 Tool 调用。 | `querySpans()` | `POST /api/observability/spans/query` | `mastra api span query` |
| [聚合 Trace](#aggregate-traces) | 计算匹配 Trace 的指标，可按字段分组或按时间分桶。 | `aggregateTraces()` | `POST /api/observability/traces/aggregate` | `mastra api trace aggregate` |
| [聚合 Span](#aggregate-spans) | 计算任意层级中匹配的各个 Span 的指标。 | `aggregateSpans()` | `POST /api/observability/spans/aggregate` | `mastra api span aggregate` |

Trace 操作共用一组 [Trace 选择条件](#select-traces)：根 Span 谓词以及 `spans.some` / `spans.none` 子句。Span 操作共用直接作用于 Span 的谓词，不支持嵌套的 `spans` 子句。查询与聚合同一类记录时，可以复用选择条件。

| 选项 | 查询 Trace | 查询 Span | 聚合 Trace 或 Span |
| - | - | - | - |
| 时间范围的最大长度 | 无上限 | 无上限 | 365 天 |
| 分页 | 键集分页、页码分页或增量轮询 | 仅支持键集分页 | 不分页；`limit` 指定返回的分组数 |
| `orderBy` 的形式 | 单元素数组 | 单元素数组 | 单个对象 |

CLI 命令将过滤条件和请求选项合并为一个 JSON 参数，并把响应包在 `data` 中。要查看查询结果的详情，可用其 `traceId` [获取完整 Trace](/reference/client-js/observability#getting-a-specific-trace)，或调用 `getSpan(traceId, spanId)` 获取单个 Span。

这些端点采用与其他可观测性路由相同的身份验证机制，并要求 `observability:read` 权限。每个请求都必须指定时间范围。

这些 API 的时间范围限制与数据保留期限互不相关。托管 Trace 适用当前 Platform 套餐的保留期限。保留期限、项目凭据和区域端点详见 [在 Mastra Platform 上查询可观测性数据](/docs/mastra-platform/observability#query-observability-data)。

## 检查能力 {/* #check-capabilities */}

| - | - | - |
|`traceQuery` | `trace-query` | `queryTraces()` |
| `spanQuery` | `span-query` | `querySpans()` |
| `spanQueryDurationSort` | `span-query-duration-sort` | 在 `querySpans()` 中通过 `orderBy` 按 `durationMs` 排序 |
| `spanQueryModelProviderSort` | `span-query-model-provider-sort` | 在 `querySpans()` 中通过 `orderBy` 按 `model` 或 `provider` 排序 |
| `spanQueryContextFields` | `span-query-context-fields` | 在 Span 查询和聚合中增加身份、上下文及父级或根实体谓词 |
| `spanQueryModelFields` | `span-query-model-fields` | 在 Span 查询和聚合中使用 `model` 与 `provider` 谓词 |
|`traceAggregate` | `trace-aggregate` | `aggregateTraces()` |
| `spanAggregate` | `span-aggregate` | `aggregateSpans()` |
| `traceQueryRootDuration` | `trace-query-root-duration` | Trace 范围内的 `durationMs` 谓词 |
| `traceQueryTimeToFirstChunk` | `trace-query-time-to-first-chunk` | `timeToFirstChunkMs` 谓词及结果 |
| `traceQueryTimeToFirstChunkSort` | `trace-query-time-to-first-chunk-sort` | 通过 `orderBy` 按 `timeToFirstChunkMs` 排序 |
| `traceQueryTimeToFirstToken` | `trace-query-time-to-first-token` | `timeToFirstTokenMs` 谓词及结果 |
| `traceQueryTimeToFirstTokenSort` | `trace-query-time-to-first-token-sort` | 通过 `orderBy` 按 `timeToFirstTokenMs` 排序 |
| `aggregateTimeToFirstMeasures` | `aggregate-time-to-first-measures` | 在 `aggregateTraces()` 和 `aggregateSpans()` 中使用 `timeToFirstToken.*` 与 `timeToFirstChunk.*` 指标 |
| `traceQueryContextIds` | `trace-query-context-ids` | `runId`、`sessionId`、`userId` 和 `organizationId` 谓词 |
| `traceQueryContextFields` | `trace-query-context-fields` | `requestId`、`serviceName` 和 `experimentId` 谓词 |

| `traceQueryOutcomeFields` | `trace-query-outcome-fields` | Trace 和 `spans.some` / `spans.none` 谓词中的 `outcome` 与 `stopReason`、Trace 维度和值发现，以及 Trace 结果中的根 Span 结果字段 |

## 选择 Trace {/* #select-traces */}

每个请求使用以下两个字段选择 Trace：

| 字段 | 必填 | 说明 |
| - | - | - |
| `timeRange` | 是 | Trace 开始时间范围。`from` 为闭区间端点，`to` 为开区间端点。两者必须是 ISO 时间戳，且 `from` 必须早于 `to`。 |
| `where` | 否 | 递归的 Trace 谓词，支持标量条件及 `spans.some` 或 `spans.none` 子句。 |

以下选择条件匹配 8 月第一周内包含出错 Tool 调用的 Trace：

```typescript
const selection = {
  timeRange: {
    from: '2026-08-01T00:00:00.000Z',
    to: '2026-08-08T00:00:00.000Z',
  },
  where: {
    spans: {
      some: {
        op: 'and',
        args: [
          { op: 'eq', left: { path: 'spanType' }, right: { literal: 'tool_call' } },
          { op: 'exists', path: 'error' },
        ],
      },
    },
  },
}
```

同一组选择条件在两个 API 中匹配相同的 Trace。聚合统计的正是查询会列出的那些 Trace。

`spans.some` 子句要求同一个 Span 满足其全部条件。在此例中，该 Span 既必须是 Tool 调用，又必须包含错误。使用 `spans.none` 可查找不存在符合条件的 Span 的 Trace。

Span 子句检查当前根 Span 和当前子 Span。根级 `timeRange` 仅约束所选当前根 Span 的 `startedAt`；关联 Span 自身的时间戳即使落在该范围外，仍可参与匹配。关联记录仅通过相同且非空的 `traceId` 关联。

### 字段和运算符 {/* #fields-and-operators */}

| 谓词范围 | 字段 | 运算符 |
| - | - | - |
| Trace | `traceId`, `threadId`, `resourceId`, `runId`, `sessionId`, `userId`, `organizationId`, `requestId`, `serviceName`, `experimentId`, `entityId`, `entityName`, `entityType`, `name`, `spanType`, `environment`, `status`, `outcome`, `stopReason` | `eq`, `ne`, `in`, `notIn`, `exists`, `notExists` |
| Trace 元数据 | `metadata.<key>` | `eq`, `ne`, `in`, `notIn`, `exists`, `notExists` |
| Trace | `startedAt`, `endedAt`, `durationMs`, `timeToFirstChunkMs`, `timeToFirstTokenMs` | `eq`, `ne`, `in`, `notIn`, `lt`, `lte`, `gt`, `gte`, `exists`, `notExists` |
| Trace | `tags` | `includes`, `notIncludes`, `exists`, `notExists` |
| Span | `name` | `eq`, `ne`, `in`, `notIn`, `exists`, `notExists`, `matches`, `notMatches` |
| Span | `spanType`, `model`, `provider`, `status`, `outcome`, `stopReason`, `entityType`, `entityId`, `entityName`, `entityVersionId`, `parentEntityVersionId`, `rootEntityVersionId`, `runId`, `sessionId`, `userId`, `organizationId`, `requestId`, `serviceName`, `experimentId` | `eq`, `ne`, `in`, `notIn`, `exists`, `notExists` |
| Span | `startedAt`, `endedAt`, `durationMs`, `timeToFirstChunkMs`, `timeToFirstTokenMs` | `eq`, `ne`, `in`, `notIn`, `lt`, `lte`, `gt`, `gte`, `exists`, `notExists` |
| Span | `error` | `exists`, `notExists` |

Trace 范围内的 `name`、`spanType` 和 `entityId` 读取当前根 Span，因此 `{ op: 'eq', left: { path: 'spanType' }, right: { literal: 'workflow_run' } }` 会选择由 Workflow 运行启动的 Trace。在 `spans.some` 或 `spans.none` 内，相同字段可以匹配 Trace 中的任意 Span。

使用 `{ op: 'and', args: [...] }`、`{ op: 'or', args: [...] }` 和 `{ op: 'not', arg: ... }` 组合谓词。比较谓词将字段引用放在左侧、字面值放在右侧。成员谓词在 `value` 中使用字段引用，在 `set` 中使用同类型字面值数组。标签谓词通过 `path` 指定存储的标签集合。`includes` 和 `notIncludes` 还需在 `value` 中指定一个标签，而 `exists` 和 `notExists` 只需 `op` 与 `path`。参阅[按标签过滤](#filter-by-tags)。文本谓词采用比较谓词的形式，字面值为字符串。参阅[按文本过滤](#filter-by-text)。

字符串比较区分大小写，且不会强制转换字面值。`matches` 和 `notMatches` 例外：它们不区分大小写地比较单词。标准字符串字段按存储的原值精确比较；元数据字符串值在比较前会去掉首尾空白，详见下文。耗時、首个数据块耗时及首个 token 耗时谓词要求数字，时间戳谓词要求 ISO 时间戳字符串。缺失值既不满足正向谓词，也不满足有序比较，但满足否定运算符 `ne` 和 `notIn`。如果字段也必须存在，应将否定谓词与 `exists` 组合。

#### 按根 Span 耗时过滤 {/* #filter-by-root-duration */}

在 Trace 范围内，`durationMs` 是当前已完成根 Span 的耗时，单位为毫秒。查询执行时根据 `endedAt - startedAt` 计算：

```typescript
const slowRootTraces = {
  op: 'gt',
  left: { path: 'durationMs' },
  right: { literal: 5000 },
}
```

这个顶层谓词不检查子 Span。相比之下，`spans.some` 中的 `durationMs` 谓词会检查当前根 Span 和当前子 Span；即使根 Span 较短，耗时较长的子 Span 也能满足该子句。

Trace 查询在评估谓词前会排除未完成的根 Span。因此，`{ op: 'notExists', path: 'durationMs' }` 找不到运行中的 Trace，也找不到缺少可用 `endedAt` 的异常根 Span。

#### 按首个数据块或 token 的耗时过滤和排序 {/* #filter-and-sort-by-time-to-first-chunk-or-token */}

`timeToFirstChunkMs` 记录 Span 的[首个数据块耗时（TTFC）](#time-to-first-chunk-ttfc)，`timeToFirstTokenMs` 记录其[首个 token 耗时（TTFT）](#time-to-first-token-ttft)。在 Trace 范围内，这些字段读取根 Span 的值；在 `spans.some` 或 `spans.none` 内，则读取各关联 Span 的值。两个字段也都可用于 `orderBy`。

以下谓词查找根 Agent 等待模型首个 token 超过 2 秒的 Trace：

```typescript
const slowFirstToken = { op: 'gt', left: { path: 'timeToFirstTokenMs' }, right: { literal: 2000 } }
```

关于 `null`、`0` 以及各项操作所需的能力，请参阅[缺失的首个数据块与 token 耗时值](#missing-first-chunk-and-token-values)。

#### 按结束结果过滤 {/* #filter-by-outcome */}

`outcome` 记录 Span 如何结束，例如 `success`、`error`、`abort`、`limit` 或 `unknown`。`stopReason` 记录结束原因，例如 `max_steps`。两者都是自由格式字符串，因此自定义 Span 可以记录自己的值。它们不同于 `status`；后者只表示 Span 是否记录了错误。

在 Trace 范围内，这两个字段读取启动该 Trace、没有父 Span 的当前根 Span。在 `spans.some` 或 `spans.none` 内，它们读取各关联 Span。若根 Span 成功，但某次 Tool 调用触及步骤上限，该 Trace 不会匹配 Trace 范围内值为 `limit` 的 `outcome`；应通过 `spans.some` 查找：

```typescript
const hitALimit = {
  spans: {
    some: { op: 'eq', left: { path: 'outcome' }, right: { literal: 'limit' } },
  },
}
```

由尚不支持这些字段的旧版 SDK 写入的 Span，以及仍在运行的根 Span，都没有结束结果。缺少 结束结果表示“未记录”，绝不表示成功。可用 `{ op: 'notExists', path: 'outcome' }` 选择此类 Span。与其他可选字符串字段一样，`ne` 和 `notIn` 也会匹配缺失值的 Span。

两个字段都支持 `eq`、`ne`、`in`、`notIn`、`exists` 和 `notExists`，可用于 Trace 和 Span 聚合分组，并可通过值发现返回取值。它们不能用于单条 Trace 或 Span 查询结果的排序。在聚合中，只要字段包含在 `groupBy` 中，就能用于 `orderBy`。结果还会返回 `stopReasonContext`，其中包含结束原因的细节，例如 `{ maxSteps: 5 }`。`stopReasonContext` 只供读取，不能用于过滤、分组或排序。

存储通过 `trace-query-outcome-fields` 功能声明支持 Trace 查询和聚合，通过 `span-query-outcome-fields` 声明支持 Span 查询和聚合。服务器将它们报告为 `traceQueryOutcomeFields` 和 `spanQueryOutcomeFields` 能力。使用旧版存储时，结果会省略这些字段；使用这些字段的请求会在执行存储操作前返回 `501`。

#### 按上下文标识符过滤 {/* #filter-by-context-identifiers */}

`runId`、`sessionId`、`userId` 和 `organizationId` 可在 Trace 范围内及 `spans.some` / `spans.none` 内使用。Trace 范围的谓词读取当前根 Span；Span 范围的谓词绑定到单个关联的当前 Span。因此，只记录在子 Span 上的运行可以通过 `spans.some` 找到：

```typescript
const sessionTracesWithRun = {
  op: 'and',
  args: [
    { op: 'eq', left: { path: 'organizationId' }, right: { literal: 'org-123' } },
    { op: 'eq', left: { path: 'sessionId' }, right: { literal: 'session-123' } },
    {
      spans: {
        some: { op: 'eq', left: { path: 'runId' }, right: { literal: 'run-42' } },
      },
    },
  ],
}
```

这些标识符支持 `eq`、`ne`、`in`、`notIn`、`exists` 和 `notExists`。字段发现会列出它们，但值发现不会返回其记录值。存储通过 `trace-query-context-ids` 功能声明支持。对旧版存储中的这些字段使用谓词，会在执行存储操作前返回 `501`；字段发现也会省略它们。

`requestId`、`serviceName` 和 `experimentId` 采用相同语义，可在 Trace 范围内及 `spans.some` / `spans.none` 内使用。以下谓词查找某个子 Span 到达 `payments` 服务的结账请求。子 Span 记录 `metadata: { serviceName: 'payments' }`，根 Span 则保留 `checkout`：

```typescript
const checkoutRequestsThroughPayments = {
  op: 'and',
  args: [
    { op: 'eq', left: { path: 'serviceName' }, right: { literal: 'checkout' } },
    { op: 'exists', path: 'requestId' },
    {
      spans: {
        some: { op: 'eq', left: { path: 'serviceName' }, right: { literal: 'payments' } },
      },
    },
  ],
}
```

存储通过 `trace-query-context-fields` 功能声明对这三个字段的支持，服务器将其报告为 `traceQueryContextFields` 能力。对旧版存储中的任一字段使用谓词，会在执行存储操作前返回 `501`；字段发现也会省略它们。

#### 按 Span 属性过滤 {/* #filter-by-span-properties */}

同一 `spans.some` 或 `spans.none` 子句中的所有条件都作用于同一个当前 Span。例如，下列谓词查找名为 `medication_lookup` 的失败 Tool Span；一个 Span 名称匹配、另一个 Span 含有错误，并不能满足条件：

```typescript
const failedMedicationLookup = {
  spans: {
    some: {
      op: 'and',
      args: [
        { op: 'eq', left: { path: 'name' }, right: { literal: 'medication_lookup' } },
        { op: 'eq', left: { path: 'spanType' }, right: { literal: 'tool_call' } },
        { op: 'exists', path: 'error' },
      ],
    },
  },
}
```

使用 `status` 判断派生出的 `success` 或 `error` 状态；如果只需检查是否存在错误详情，则使用 `error`。

`durationMs` 是 Span 的耗时，单位为毫秒。Span 的 `startedAt` 与 `endedAt` 条件独立于顶层根 Span 的 `timeRange`，用于过滤关联 Span：

```typescript
const slowModelCalls = {
  spans: {
    some: {
      op: 'and',
      args: [
        { op: 'eq', left: { path: 'spanType' }, right: { literal: 'model_generation' } },
        { op: 'gt', left: { path: 'durationMs' }, right: { literal: 5000 } },
        {
          op: 'gte',
          left: { path: 'startedAt' },
          right: { literal: '2026-07-15T00:00:00.000Z' },
        },
      ],
    },
  },
}
```

`model` 和 `provider` 读取 Span 对应的 `model` 与 `provider` 列。若列为空，则回退到旧版 `@mastra/observability` 导出的字符串值 `attributes.model` 和 `attributes.provider`，使现有过滤条件仍能匹配旧 Span。Trace 结果不返回 `model` 和 `provider`，因为 Trace 可能通过某个 Span 匹配，而其他 Span 使用了不同模型。

```typescript
const selectedModel = {
  spans: {
    some: {
      op: 'and',
      args: [
        {
          op: 'eq',
          left: { path: 'model' },
          right: { literal: '__AI_SDK_ANTHROPIC_MODEL_SONNET__' },
        },
        { op: 'eq', left: { path: 'provider' }, right: { literal: 'anthropic' } },
      ],
    },
  },
}
```

用通用实体字段标识 Tool 和检索操作。版本字段使同一子句能够按实体谱系限定同一个 Span：

```typescript
const versionedRetrieval = {
  spans: {
    some: {
      op: 'and',
      args: [
        { op: 'eq', left: { path: 'entityType' }, right: { literal: 'rag_ingestion' } },
        { op: 'eq', left: { path: 'entityId' }, right: { literal: 'medication-index' } },
        { op: 'eq', left: { path: 'entityVersionId' }, right: { literal: 'index-v3' } },
        { op: 'eq', left: { path: 'rootEntityVersionId' }, right: { literal: 'agent-v2' } },
      ],
    },
  },
}
```

#### 按元数据过滤 {/* #filter-by-metadata */}

使用 `metadata.<key>` 路径过滤当前根 Span 上存储的自定义维度。元数据谓词对去除首尾空白后的非空字符串进行精确且区分大小写的比较；存储值中的首尾空白会被忽略。去除空白后为空的值视为缺失。null、数字、布尔值、对象和数组也视为缺失。

```typescript
const messageTrace = {
  op: 'and',
  args: [
    { op: 'eq', left: { path: 'metadata.messageId' }, right: { literal: 'message-123' } },
    { op: 'in', value: { path: 'metadata.actorRole' }, set: ['assistant', 'tool'] },
    { op: 'exists', path: 'metadata.protocolVersion' },
    {
      op: 'or',
      args: [
        { op: 'eq', left: { path: 'metadata.temporalRunId' }, right: { literal: 'run-456' } },
        { op: 'eq', left: { path: 'metadata.externalTraceId' }, right: { literal: 'trace-789' } },
      ],
    },
    { op: 'not', arg: { op: 'exists', path: 'metadata.parentMessageId' } },
  ],
}
```

键必须指向一个顶层属性；空键和嵌套路径会被拒绝。元数据键不会去除空白，因此首尾空白仍属于键标识的一部分。如果元数据与 `resourceId`、`threadId` 或 `environment` 等标准 Trace 字段重复，优先使用标准字段，因为它使用专用存储列。仅当需要元数据对象中的值时，才使用 `metadata.<key>`；元数据值与标准字段值可能不同。

Trace 查询的字段发现会返回在所选时间范围内观察到、可用于查询的顶层字符串元数据字段。

#### 按标签过滤 {/* #filter-by-tags */}

标签是存储在当前根 Span 上的字符串列表，因此使用集合运算符，而不是标量 `in` 和 `notIn`。以下查询查找带有人工审核标签、且不含 `archived` 标签的生产环境 Trace：

```typescript
const manualReview = {
  op: 'and',
  args: [
    { op: 'eq', left: { path: 'environment' }, right: { literal: 'production' } },
    { op: 'includes', path: 'tags', value: 'manual-review' },
    { op: 'notIncludes', path: 'tags', value: 'archived' },
  ],
}
```

| 运算符 | 匹配条件 |
| - | - |
| `includes` | Trace 含有指定标签 |
| `notIncludes` | Trace 至少含有一个标签，但不含指定标签 |
| `exists` | Trace 至少含有一个标签 |
| `notExists` | Trace 不含任何标签 |

标签按完整字符串精确比较，且区分大小写。`value` 必须是至少包含一个非空白字符的字符串。可用 `and` 或 `or` 组合多个 `includes` 谓词，分别要求同时具备或允许具备多个标签。未记录标签的 Trace 与标签列表为空的 Trace 行为相同：两者都满足 `notExists`，都不满足 `includes`、`notIncludes` 或 `exists`。如果未标记的 Trace 也应匹配，请使用 `{ op: 'not', arg: { op: 'includes', ... } }`。

`tags` 只能用于 Trace 谓词。对 `tags` 使用 `in`、`notIn` 或比较运算符会被拒绝。对 `tags` 进行值发现时，会返回每个观察到的标签，以及带有该标签的符合条件 Trace 数量。

#### 按文本过滤 {/* #filter-by-text */}

除精确比较外，Span 名称还支持按单词匹配。当字面值中的单词按原顺序、以完整单词形式出现在字段中时，`matches` 成立；字段存在但不包含这些单词时，`notMatches` 成立。以下查询查找名称包含“document search”两个单词的 Span 所属的 Trace：

```typescript
const documentSearch = {
  spans: {
    some: {
      op: 'matches',
      left: { path: 'name' },
      right: { literal: 'document search' },
    },
  },
}
```

字面值和存储值都会先转为小写，再拆分为单词。单词由连续的字母、数字及组合标记组成；标点、空格或 `_` 等其他字符会分隔单词。因此，`incorrect` 匹配 `This answer is incorrect.`，但不匹配 `This was incorrectly formatted.`；`gpt 5` 匹配 `llm: 'gpt-5'`。多个单词的字面值必须按顺序连续出现。字母保留重音：`café` 不匹配 `cafe`。文本先归一化为 Unicode NFC，因此无论重音作为字母的一部分存储，还是单独存储为标记，`café` 都能匹配；组合标记仍属于对应单词，所以 `नमस` 不匹配 `नमस्ते`。土耳其语 `İ` 会折叠为 `i`，希腊语词尾 `ς` 与 `σ` 等同。PostgreSQL 按数据库区域设置将字母转为小写；使用 `C` 区域设置创建的数据库不会折叠 ASCII 以外字母的大小写。为获得一致结果，请使用 `en_US.UTF-8` 等 UTF-8 区域设置。

| 运算符 | 匹配条件 |
| - | - |
| `matches` | 字段包含字面值的单词，且这些单词构成连续、完整的词组 |
| `notMatches` | 字段存在，但不包含该词组 |

字面值必须至少包含一个字母或数字，否则请求以 `422 TRACE_QUERY_INVALID` 失败。字段缺失时，两个运算符都不匹配。如果缺少该字段的记录也应匹配，请使用 `{ op: 'not', arg: { op: 'matches', ... } }`。文本运算符仅适用于 Span 的 `name`；其他字符串字段、数字、时间戳、标签及元数据都不支持。不支持子字符串、通配符、正则表达式或模糊匹配，也不能跨多个字段搜索。

### 查询限制 {/* #query-limits */}

若查询超出以下任一限制，规划器会在执行存储操作前拒绝：

| 输入 | 上限 |
| - | - |
| 谓词嵌套深度 | 12 层 |
| 谓词节点数 | 100 |
| 关联的 `spans` 子句数 | 共 8 个 |
| 单个 `in` 或 `notIn` 集合中的值 | 100 个 |
| 比较字面值与成员值 | 共 1,000 个 |
| 字符串字面值 | 4,096 UTF-8 字节 |
| 原始谓词路径 | 128 UTF-8 字节 |
| `page.limit` | 1,000 |
| HTTP 请求体 | 256 KiB |

每个比较字面值计为一个字面值。`in` 或 `notIn` 集合中的每个成员也各计一个，即使该集合未超过自身的数量上限。

Hono 和 Fastify 在解析 JSON 前强制执行请求体大小限制。Express 和 Elysia 会在路由处理程序或存储执行前拒绝过大的请求体，但如果没有可靠的 `Content-Length` 标头，宿主框架可能已经解析了请求。若需要严格的解析前内存上限，请配置宿主应用的 JSON 解析器或请求体大小限制。

## 查询 Trace {/* #query-traces */}

使用 `queryTraces()`、`mastra api trace query` 或 `POST /api/observability/traces/query` 列出所选 Trace。三种方式接受相同的请求；该请求在 [Trace 选择条件](#select-traces) 上增加排序和分页。

### 使用客户端 SDK 查询 Trace {/* #query-traces-with-the-client-sdk */}

以下查询查找包含出错 Tool 调用的 Trace：

```typescript
import { MastraClient } from '@mastra/client-js'

const mastraClient = new MastraClient({ baseUrl: 'http://localhost:4111' })

const result = await mastraClient.queryTraces({
  timeRange: {
    from: '2026-08-01T00:00:00.000Z',
    to: '2026-08-08T00:00:00.000Z',
  },
  where: {
    spans: {
      some: {
        op: 'and',
        args: [
          { op: 'eq', left: { path: 'spanType' }, right: { literal: 'tool_call' } },
          { op: 'exists', path: 'error' },
        ],
      },
    },
  },
  orderBy: [{ field: 'startedAt', direction: 'desc' }],
  page: { limit: 25 },
})
```

### 使用 CLI 查询 Trace {/* #query-traces-with-the-cli */}

将查询作为单个 JSON 参数传给 `mastra api trace query`。过滤条件和分页选项都放在 JSON 输入中。以下命令与 SDK 示例执行相同的失败 Tool 查询：

```bash

    "from": "2026-08-01T00:00:00.000Z",
    "to": "2026-08-08T00:00:00.000Z"
  },

    "spans": {
      "some": {
        "op": "and",
        "args": [
          { "op": "eq", "left": { "path": "spanType" }, "right": { "literal": "tool_call" } },
          { "op": "exists", "path": "error" }

      }

```

显式指定的 `--url` 指向本地 Mastra 服务器。如果省略，即使本地服务器正在运行，可观测性命令仍默认连接 `https://observability.mastra.ai`。身份验证和区域端点详见 [CLI 目标解析](/reference/cli/mastra#target-resolution)。目标服务器及配置的存储必须支持所请求的查询能力。

使用以下命令检查该命令：

```bash

```

```bash
mastra api --url http://localhost:4111 trace query --schema
```

Mastra Platform 目前不提供 `--schema` 使用的 schema 端点。针对任一目标构造查询时，请参阅[请求字段](#request-fields)及[字段和运算符](#fields-and-operators)。要查找项目中已记录的字段和值，请使用[字段和值发现](#discover-fields-and-values)。

### 发送 HTTP 请求 {/* #send-an-http-request */}

将同一查询作为 JSON 请求体发送：

```bash
curl --request POST \
  --url http://localhost:4111/api/observability/traces/query \
  --header 'Authorization: Bearer <token>' \
  --header 'Content-Type: application/json' \
  --data '{
    "timeRange": {
      "from": "2026-08-01T00:00:00.000Z",
      "to": "2026-08-08T00:00:00.000Z"
    },
    "where": {
      "spans": {
        "some": {
          "op": "and",
          "args": [
            { "op": "eq", "left": { "path": "spanType" }, "right": { "literal": "tool_call" } },
            { "op": "exists", "path": "error" }
          ]
        }
      }
    },
    "orderBy": [{ "field": "startedAt", "direction": "desc" }],
    "page": { "limit": 25 }
  }'
```

### 请求字段 {/* #request-fields */}

| 字段 | 必填 | 说明 |
| - | - | - |
| `timeRange` | 是 | Trace 开始时间范围。`from` 为闭区间端点，`to` 为开区间端点。两者必须是 ISO 时间戳，且 `from` 必须早于 `to`。 |
| `where` | 否 | 递归的 Trace 谓词，支持标量条件及 `spans.some` 或 `spans.none` 子句。 |
| `orderBy` | 否 | 单元素数组，按 `startedAt`、`endedAt`、`timeToFirstChunkMs` 或 `timeToFirstTokenMs` 以 `asc` 或 `desc` 排序。默认为 `startedAt desc`。增量模式不接受此字段。 |
| `page` | 否 | `{ limit, after }`。`limit` 默认为 100，最大为 1000。将不透明的 `page.next` 值作为 `after` 传入。 |
| `pagination` | 否 | 页码分页：`{ page, perPage }`。默认第 0 页、每页 10 条结果。`perPage` 最大为 100。 |
| `mode` | 否 | 设为 `'delta'`，使用增量游标轮询，代替 `page` 或 `pagination`。 |
| `after` | 否 | 仅用于增量模式。传入页码分页结果或上次轮询返回的不透明 `deltaCursor`；省略时建立当前水位。 |
| `limit` | 否 | 仅用于增量模式。每批结果的上限，默认 10，最大 100。 |

未知字段会被拒绝。请求不能选择投影、声明连接、请求计数或指标，也不能控制授权。计数和指标请使用 [`aggregateTraces()`](#aggregate-traces)。请求体上限为 256 KiB。

使用键集分页的查询会返回已完成 Trace 的简要信息，以及下一页游标：

```json
      "traceId": "trace-123",
      "rootSpanId": "span-123",
      "name": "agent run: support-agent",
      "entityId": "support-agent",
      "parentSpanId": null,
      "createdAt": "2026-08-03T10:00:00.000Z",

      "entityName": "support-agent",
      "entityType": "agent",
```

响应包含 `name`、`createdAt`、身份字段、`metadata`，以及输入、输出和错误的预览。受支持的可空字段即使没有记录值，也会以 `null` 出现。若存储缺少可选功能，依赖该功能的字段会被省略。预览仅概括数据内容；完整输入、输出和错误详情需获取完整 Trace。

#### CLI 响应 {/* #cli-responses */}

CLI 将 API 响应包在 `data` 中：

```json
{
  "data": {
    "traces": [],
    "page": { "next": null }
  }
}
```

从 `data.traces` 读取结果。键集查询的分页元数据位于 `data.page.next`，页码分页位于 `data.pagination`；增量轮询则使用 `data.deltaCursor` 和 `data.delta.hasMore`。

每次 CLI 调用只执行一次查询。要获取下一键集页，在下次请求中将 `data.page.next` 作为 `page.after` 传入。增量轮询时，重复执行命令，并将 `data.deltaCursor` 作为顶层 `after` 值。保持相同的时间范围和谓词。各模式的行为及轮询限制详见[分页与错误](#pagination-and-errors)。

要查看所选 Trace，使用 `mastra api --url http://localhost:4111 trace get <traceId> --verbose`。目标和身份验证方式应与查询相同。

### 分页与错误 {/* #pagination-and-errors */}

#### 选择分页模式 {/* #choose-a-pagination-mode */}

Trace 查询支持三种互斥模式：

| 模式 | 请求字段 | 响应元数据 |
| - | - | - |
| 键集分页（默认） | `page: { limit, after }` | `page: { next }` |
| 页码分页 | `pagination: { page, perPage }` | `pagination: { total, page, perPage, hasMore }`；支持增量轮询时还包含 `deltaCursor` |
| 增量轮询 | `mode: 'delta'`，可选顶层 `after` 和 `limit` | `delta: { limit, hasMore }` 和 `deltaCursor` |

页码从 0 开始计数。每个请求内读取的总数与各行保持一致。不要混用 `page`、`pagination` 或增量模式。顶层 `after` 和 `limit` 只在增量模式中接受。

#### 加载页码分页结果后轮询 {/* #poll-after-loading-a-numbered-page */}

使用页码分页响应中的 `deltaCursor`，取代 `listTracesLight()` 从页码分页切换到增量轮询的流程。结果使用 `traces` 而不是 `spans`，且仅包含已完成的 Trace。配置的存储必须支持增量轮询。

```typescript
const timeRange = {
  from: '2026-08-01T00:00:00.000Z',
  to: '2026-08-08T00:00:00.000Z',
}
const initial = await mastraClient.queryTraces({
  timeRange,
  pagination: { page: 0, perPage: 100 },
})
if (!initial.deltaCursor) throw new Error('Delta polling is unavailable')

const traces = new Map(initial.traces.map(trace => [trace.traceId, trace]))
let after = initial.deltaCursor

async function poll() {
  let hasMore: boolean
  do {
    const result = await mastraClient.queryTraces({
      timeRange,
      mode: 'delta',
      after,
      limit: 100,
    })
    for (const trace of result.traces) traces.set(trace.traceId, trace)
    after = result.deltaCursor
    hasMore = result.delta.hasMore
  } while (hasMore)
}

await poll()
```

保留 `after`，按应用的轮询间隔再次调用 `poll()`。同一个 Trace 可能同时出现在初始页和后续批次，或出现在多个批次，因此应按 `traceId` 合并结果。若需加载初始页未包含的历史 Trace，请继续请求剩余页码。

不带 `after` 的增量请求会返回空数组，并建立当前游标；它不会返回历史匹配结果。始终保留返回的游标，即使该批次为空。`hasMore` 表示超过本批上限后仍有匹配的 Trace；为 `true` 时应立即继续请求。

增量排序使用存储摄取水位及适配器特定的并列排序规则，因此相同时间戳不会使游标产生歧义。增量模式中不要传入 `orderBy`。键集游标与增量游标不可互换，增量游标也不能跨存储适配器使用。

每次轮询都应保持相同的规范化 `where` 谓词和完全一致的 `timeRange` 边界。即使 Trace 后来才完成，时间范围仍按根 Span 的 `startedAt` 选择记录。将 `timeRange.to` 改为当前时间会使游标失效。选择条件或授权范围变化时，应重新加载页码分页结果并使用新游标。批次上限可以调整，无需重新开始。

游标建立后新增的已完成根 Span，以及之后才完成的根 Span，都可能返回。关联 Span 在选择根 Span 时参与评估，但后续写入关联记录并不保证该 Trace 再次返回。已删除或不再匹配的 Trace 不会以删除事件或墓碑记录形式返回。如需对账这些变化，请刷新页码分页结果。

ClickHouse 轮询尽力而为。增量索引与 Trace 记录使用不同的物化视图表。并发查询可能先看到一张表中的插入，再看到另一张表中的插入，详见 [ClickHouse 的物化视图可见性规则](https://github.com/ClickHouse/clickhouse-docs/blob/main/knowledgebase/are_materialized_views_inserted_asynchronously.mdx)。轮询可能在匹配 Trace 可见前越过索引条目，导致后续轮询漏掉该 Trace。应定期重新加载页码分页结果，以弥补这些缺口。

ClickHouse 增量索引保留两天事件，且不会回填历史行。轮询中断超过该保留窗口后，应重新加载页码分页结果。增量轮询并非持久变更流，无法保证交付每个匹配的 Trace。

#### 键集排序与错误 {/* #keyset-ordering-and-errors */}

排序是确定性的。Trace 排序会追加按 `traceId` 升序排列作为并列时的次级排序条件。

键集游标绑定操作、已接受的规范化查询和排序规则。更改 Trace 选择条件、谓词或排序后复用游标，会返回 `409`。

页码分页交接游标与增量游标也绑定授权状态。调用者的角色或权限变化会使这些游标失效并返回 `409`。若增量轮询返回 `409`，请重新加载页码分页结果，并使用新的 `deltaCursor` 恢复轮询。格式错误的游标返回 `400`。

游标分页的顺序是确定的，但它并非数据库快照。两次分页请求之间写入的 Trace 或替换信号，可能改变后续页面。

PostgreSQL 和 ClickHouse 默认在 15 秒后终止 Trace 查询，超过数据库超时时间则返回 `504`。可在 `PostgresStoreVNext` 上设置 `observability.traceQueryTimeoutMs`，或在 `ClickhouseStoreVNext` 上设置 `observability.traceQuery.timeoutMs`，以 1 至 300,000 毫秒的整数调整超时时间。DuckDB 的驱动封装目前不支持查询级超时或取消，因此上述 `504` 保证不适用于 DuckDB。

| 状态码 | 含义 |
| - | - |
| `400` | JSON 或游标格式错误。 |
| `409` | 游标与查询不匹配。 |
| `413` | 请求体超过 256 KiB。 |
| `422` | JSON 格式正确，但请求在结构或语义上无效。响应包含稳定的问题代码及路径。发现接口的校验使用 `TRACE_QUERY_INVALID`。 |
| `501` | 已安装的 Core 或配置的可观测性存储不支持请求的操作。除非 Core 提供发现契约且存储同时实现字段和值发现，否则发现接口返回 `TRACE_QUERY_DISCOVERY_UNSUPPORTED`。 |
| `503` | 发现接口超出后端内存或资源预算，返回 `TRACE_QUERY_RESOURCE_LIMIT`。 |
| `504` | PostgreSQL 或 ClickHouse 查询超出配置的数据库执行超时时间。发现接口返回 `TRACE_QUERY_EXECUTION_TIMEOUT`。 |

## 查询 Span {/* #query-spans */}

使用 `querySpans()`、`mastra api span query` 或 `POST /api/observability/spans/query`，可跨 Trace 返回已完成 Span 的摘要。请求必须提供针对 Span 开始时间的有效 ISO 时间戳范围，并支持游标分页。以下示例查找耗时至少一秒的 Tool 调用：

```typescript
const result = await mastraClient.querySpans({
  timeRange: {
    from: '2026-10-01T00:00:00.000Z',
    to: '2026-10-02T00:00:00.000Z',
  },
  where: {
    op: 'and',
    args: [
      { op: 'eq', left: { path: 'spanType' }, right: { literal: 'tool_call' } },
      { op: 'gte', left: { path: 'durationMs' }, right: { literal: 1000 } },
    ],
  },
  orderBy: [{ field: 'startedAt', direction: 'desc' }],
  page: { limit: 100 },
})

// Pass result.page.next as page.after to continue with the same filters and ordering.
console.log(result.spans)
```

每页默认 100 行，最多 1,000 行。响应格式为 `{ spans, page: { next } }`，不包含总数。排序必须且只能指定 `startedAt`、`endedAt`、`durationMs`、`timeToFirstChunkMs`、`timeToFirstTokenMs`、`model` 或 `provider` 中的一项，并可选择升序或降序；默认按开始时间降序。缺失的排序值在两个方向上都排在最后。按模型和提供商排序时区分大小写。

| 字段 | 运算符 |
| - | - |
|`traceId`, `spanId`, `parentSpanId`, `threadId` | `eq`, `ne`, `in`, `notIn`, `exists`, `notExists` |
| `organizationId`, `resourceId`, `runId`, `sessionId`, `userId`, `requestId`, `serviceName`, `experimentId`, `environment`, `executionSource` | 同上所列字符串运算符 |
| 实体、父实体和根实体的 `Type`、`Id`、`Name`、`VersionId` 字段，例如 `parentEntityId` | 同上所列字符串运算符 |
| `name`, `spanType`, `status` | 同上所列字符串运算符；`name` 还支持 `matches` / `notMatches`，用于匹配归一化的完整单词和词组 |
| `model`, `provider`, `outcome`, `stopReason` | 同上所列字符串运算符 |
| `startedAt`, `endedAt`, `durationMs`, `timeToFirstChunkMs`, `timeToFirstTokenMs` | 比较、成员关系及是否存在 |
| `error` | `exists`, `notExists` |

使用 `and`、`or` 和 `not` 组合谓词。成员关系使用 `{ op: 'in', value: { path: 'spanType' }, set: ['agent_run', 'tool_call'] }`。Span 有错误时，其状态为 `error`；否则为 `success`。

每条摘要包含身份、上下文、实体谱系、状态、时间戳、`durationMs`、模型和提供商，以及输入、输出和错误的预览。

过滤 `traceId`、`spanId`、`parentSpanId`、`threadId`、`resourceId`、`requestId`、`serviceName`、`experimentId`、`environment`、`executionSource` 或父级／根实体的 `Type`、`Id`、`Name` 字段前，请检查 `getObservabilityCapabilities()` 返回的 `capabilities.spanQueryContextFields`。如果该能力缺失或为 false，使用这些过滤条件会返回结构化的 `422` 错误。此能力不限制 `runId`、`sessionId`、`userId`、`organizationId` 或实体的 `VersionId` 过滤条件。

按 `model` 或 `provider` 过滤前，请检查 `capabilities.spanQueryModelFields`。这些过滤条件只读取 Span 的 `model` 和 `provider` 列。只有 Span 同时具有 `model` 和 `provider` 时，`@mastra/observability` 才会填充这些列；更早版本写入的 Span 对应列为空。过滤时，空列视为缺失，因此 `eq`、`in` 和 `exists` 不匹配此类 Span，而 `ne`、`notIn` 和 `notExists` 会匹配。结果仍可从 Span 属性中返回其 `model` 和 `provider`。Trace 查询中的 `spans.some` 过滤条件会回退读取属性，因此可以匹配此类 Span。旧版适配器收到使用这些过滤条件的请求时返回 `501`。

按 `outcome` 和 `stopReason` 过滤 Span 或对其分组前，请检查 `capabilities.spanQueryOutcomeFields`。随后结果行也会包含 `outcome`、`stopReason` 和 `stopReasonContext`。这些字段记录 Span 的结束方式及原因，与 `status` 不同；未记录时为 `null`。缺少 结束結果表示“未记录”，不表示成功。`stopReasonContext` 不能用于过滤，且存储缺少 `span-query-outcome-fields` 时会被省略。对于 Trace，`capabilities.traceQueryOutcomeFields` 在 `queryTraces()` 和 `aggregateTraces()` 中启用相同字段，读取根 Span 的值。旧版适配器收到使用这些字段的请求时返回 `501`：

```typescript
const { capabilities } = await mastraClient.getObservabilityCapabilities()

if (capabilities.spanQueryOutcomeFields) {
  const limited = await mastraClient.querySpans({
    timeRange: { from: '2026-10-01T00:00:00.000Z', to: '2026-10-02T00:00:00.000Z' },
    where: { op: 'eq', left: { path: 'outcome' }, right: { literal: 'limit' } },
  })
  console.log(limited.spans.map(span => [span.stopReason, span.stopReasonContext]))
}
```

Trace 范围和 `spans.some` 的语义详见[按结束结果过滤](/reference/observability/tracing/advanced-queries#filter-by-outcome)。

对于 `@mastra/duckdb` 开始存储父级／根实体类型、ID 和名称之前写入的 Span，DuckDB 会对这些字段返回 `null`。这些字段的相等过滤条件不会匹配此类 Span。

CLI 在 `data` 中返回相同响应：从 `data.spans` 读取结果，并将 `data.page.next` 作为 `page.after` 传入。Span 查询只支持键集分页，因此沿游标翻页时须复用相同的时间范围、谓词和排序。格式错误的游标返回 `400`；与查询或范围不匹配的游标返回 `409`。

使用 `mastra api trace span <traceId> <spanId>` 或 `getSpan(traceId, spanId)` 获取所选 Span 的完整详情。

## 聚合 Trace {/* #aggregate-traces */}

使用 `aggregateTraces()` 或 `POST /api/observability/traces/aggregate` 统计所选 Trace 并计算指标。通过 `groupBy` 最多按两个维度分组，通过 `interval` 将每组划分为时间桶。响应中每组一行；使用时间桶时，每组每桶一行。

### 使用客户端 SDK 聚合 Trace {/* #aggregate-traces-with-the-client-sdk */}

以下请求比较一周内各 Agent 的调用量、错误率和延迟：

```typescript
import { MastraClient } from '@mastra/client-js'

const mastraClient = new MastraClient({ baseUrl: 'http://localhost:4111' })

const { capabilities } = await mastraClient.getObservabilityCapabilities()

if (capabilities.traceAggregate) {
  const { rows, truncated } = await mastraClient.aggregateTraces({
    timeRange: {
      from: '2026-08-01T00:00:00.000Z',
      to: '2026-08-08T00:00:00.000Z',
    },
    where: { op: 'eq', left: { path: 'entityType' }, right: { literal: 'agent' } },
    groupBy: ['entityName'],
    measures: ['count', 'errorRate', 'duration.p95'],
    orderBy: { field: 'errorRate', direction: 'desc' },
    limit: 10,
  })
}
```

客户端会像 `queryTraces()` 一样重试服务器错误，但不会重试 `422` 校验错误。

### 发送聚合 HTTP 请求 {/* #send-an-aggregate-http-request */}

将同一请求作为 JSON 请求体发送：

```bash
curl --request POST \
  --url http://localhost:4111/api/observability/traces/aggregate \
  --header 'Authorization: Bearer <token>' \
  --header 'Content-Type: application/json' \
  --data '{
    "timeRange": {
      "from": "2026-08-01T00:00:00.000Z",
      "to": "2026-08-08T00:00:00.000Z"
    },
    "where": { "op": "eq", "left": { "path": "entityType" }, "right": { "literal": "agent" } },
    "groupBy": ["entityName"],
    "measures": ["count", "errorRate", "duration.p95"],
    "orderBy": { "field": "errorRate", "direction": "desc" },
    "limit": 10
  }'
```

### 聚合请求字段 {/* #aggregate-request-fields */}

| 字段 | 必填 | 说明 |
| - | - | - |
| `timeRange` | 是 | Trace 开始时间范围，与[选择 Trace](#select-traces)相同。最长 365 天。 |
| `where` | 否 | Trace 谓词，与[选择 Trace](#select-traces)相同。 |
| `measures` | 是 | 一个或多个互不重复的[指标名称](#measures)。 |
| `groupBy` | 否 | 最多两个互不重复的[维度](#dimensions)。默认为 `[]`，即把所有选中 Trace 视为一组。设置 `interval` 后，该组的每个非空时间桶各有一行；没有匹配 Trace 时不返回任何行。 |
| `interval` | 否 | 时间桶宽度：`'1m'`、`'5m'`、`'15m'`、`'1h'` 或 `'1d'`。参阅[时间桶](#time-buckets)。 |
| `having` | 否 | 根据指标过滤分组的标量谓词，在分组后执行。参阅[过滤和排序分组](#filter-and-order-groups)。 |
| `orderBy` | 否 | `{ field, direction }`。`field` 可以是请求的指标、`count` 或 `groupBy` 维度；`direction` 为 `asc` 或 `desc`。默认为 `count desc`。 |
| `limit` | 否 | 最多返回的分组数。默认 100，最大 1,000。 |

未知字段会被拒绝。聚合结果不支持分页。若 `truncated` 为 `true`，请缩小选择范围或改用其他指标排序。

### 维度 {/* #dimensions */}

维度读取每个所选 Trace 的当前根 Span：

| 维度 | 说明 |
| - | - |
| `entityType`, `entityName`, `environment`, `status`, `serviceName`, `executionSource` | 根 Span 属性。 |
| `threadId`, `resourceId`, `userId`, `sessionId`, `organizationId`, `experimentId` | 记录在根 Span 上的上下文标识符。 |
| `name`, `spanType` | 根 Span 的名称和类型。需要 `traceQueryRootSpanFields` 能力。 |
| `entityId` | 根 Span 的实体 ID。可对缺少 `entityName` 的 Trace（如评分器运行）分组。需要 `traceQueryRootEntityId` 能力。 |
| `outcome`, `stopReason` | 根 Span 的结束方式和原因。根 Span 未记录值的 Trace 会归入值为 `null` 的分组。需要 `traceQueryOutcomeFields` 能力。 |
| `metadata.<key>` | 单个非空的顶层元数据键。值会去除首尾空白；缺失、空值或非字符串值归为 `null`。 |

除 `executionSource` 外，每个维度也是 Trace 范围的 `where` 字段，因此可将其值加入谓词，深入查看某个分组。`traceId`、`spanId`、`runId` 和 `requestId` 不能用于分组。维度无值的 Trace 会形成一个值为 `null` 的独立分组。若要在查询中选择该分组，请对该维度使用 `notExists`，不要对 `literal: null` 使用 `eq`。

### 指标 {/* #measures */}

| 指标 | 值 |
| - | - |
| `count` | 所选 Trace 的数量。 |
| `countDistinct.<field>` | 某个维度或 `traceId` 中不同非 null 值的数量，例如 `countDistinct.userId`。 |
| `duration.avg`, `duration.min`, `duration.max` | 根 Span 耗时，单位为毫秒。 |
| `duration.p50`, `duration.p90`, `duration.p95`, `duration.p99` | 根 Span 耗时的百分位数，单位为毫秒；具体存储可能返回近似值。 |
| `timeToFirstChunk.avg`, `timeToFirstChunk.min`, `timeToFirstChunk.max` | 根 Span 的首个数据块耗时，单位为毫秒。需要 `aggregateTimeToFirstMeasures` 能力。 |
| `timeToFirstChunk.p50`, `timeToFirstChunk.p90`, `timeToFirstChunk.p95`, `timeToFirstChunk.p99` | 根 Span 首个数据块耗时的百分位数，单位为毫秒。需要 `aggregateTimeToFirstMeasures` 能力。 |
| `timeToFirstChunk.count` | 记录了首个数据块耗时的根 Span 所属 Trace 数量。需要 `aggregateTimeToFirstMeasures` 能力。 |
| `timeToFirstToken.avg`, `timeToFirstToken.min`, `timeToFirstToken.max` | 根 Span 的首个 token 耗时，单位为毫秒。需要 `aggregateTimeToFirstMeasures` 能力。 |
| `timeToFirstToken.p50`, `timeToFirstToken.p90`, `timeToFirstToken.p95`, `timeToFirstToken.p99` | 根 Span 首个 token 耗时的百分位数，单位为毫秒。需要 `aggregateTimeToFirstMeasures` 能力。 |
| `timeToFirstToken.count` | 记录了首个 token 耗时的根 Span 所属 Trace 数量。需要 `aggregateTimeToFirstMeasures` 能力。 |
| `errorCount` | 根 Span 记录了错误的 Trace 数量。 |
| `errorRate` | `errorCount` 除以 `count`，范围为 0 到 1。 |
| `tokens.input.sum`, `tokens.input.avg` | 输入 token 数。 |
| `tokens.output.sum`, `tokens.output.avg` | 输出 token 数。 |
| `tokens.total.sum`, `tokens.total.avg` | 输入与输出 token 总数。 |
| `tokens.reasoning.sum`, `tokens.reasoning.avg` | 推理输出 token 数。 |
| `tokens.cached.sum`, `tokens.cached.avg` | 从提供商缓存读取的输入 token 数。 |
| `cost.sum`, `cost.avg` | 模型预估成本。 |

不支持对元数据计算数值指标。

#### Token 与成本指标 {/* #token-and-cost-measures */}

Token 与成本指标读取每个 Trace 记录的模型用量指标，因此仅当存储保留所选时间范围内的用量指标时才可使用。指标与 Trace 的 `traceId` 相同，且记录时间不早于 `timeRange.from`，就归属于该 Trace。所有这类指标都会计入，包括在 `timeRange.to` 之后记录的用量，以及暂停和恢复之前记录的用量。重试导出的指标只计一次。

至少记录一项用量指标的 Trace 称为有用量的 Trace。`tokens.<kind>.sum` 汇总某组中有用量的 Trace 的 token 数；`tokens.<kind>.avg` 用该总数除以有用量的 Trace 数量，而不是 `count`。若该组没有有用量的 Trace，两者均为 `null`。

成本取自输入和输出 token 总量指标中记录的预估费用。`cost.sum` 汇总至少有一项已计价指标的 Trace 成本；`cost.avg` 用总成本除以这类 Trace 的数量。如果一次调用只有部分 token 类型成功计价，仍会计入已计价部分的成本；任何其他计价失败的指标都不计入成本。

请求任意 `cost.*` 指标时，每行还会包含一个 `cost` 对象：

| 字段 | 说明 |
| - | - |
| `coverage` | 用量已全部计价的 Trace 占所有有用量 Trace 的比例，范围为 0 到 1。部分计价的调用不算全部计价，因此即使已知成本计入 `cost.sum`，仍会降低覆盖率。若该组没有有用量的 Trace，则为 `null`。 |
| `unit` | 已计价指标的成本单位，如 `USD`。若使用多个单位，则为 `'mixed'`；没有已计价指标时为 `null`。 |

若该组没有已计价 Trace，或 `unit` 为 `'mixed'`，`cost.sum` 和 `cost.avg` 均为 `null`。覆盖率低于 1 表示该成本低估了分组的实际支出。`cost` 对象不是指标，不能在 `having` 或 `orderBy` 中引用。

### 首个数据块耗时（TTFC） {/* #time-to-first-chunk-ttfc */}

首个数据块耗时（TTFC）指调用方等待流式响应首个数据块的时间。`timeToFirstChunkMs` 从 Span 开始时计至模型响应首个数据块到达时。模型以流式方式响应时，Agent 运行和模型 Span 会记录该值。对于 Agent 运行，计时从运行开始，包含首次模型调用前的工作，例如输入处理器和记忆检索。

`timeToFirstChunk.*` 指标聚合根 Span 的 `timeToFirstChunkMs`，与 [`queryTraces()`](#query-traces) 返回的值相同。过滤和排序方式详见[按首个数据块或 token 的耗时过滤和排序](#filter-and-sort-by-time-to-first-chunk-or-token)。

```typescript
const { capabilities } = await mastraClient.getObservabilityCapabilities()

if (capabilities.traceAggregate && capabilities.aggregateTimeToFirstMeasures) {
  const { rows } = await mastraClient.aggregateTraces({
    timeRange: {
      from: '2026-08-01T00:00:00.000Z',
      to: '2026-08-02T00:00:00.000Z',
    },
    where: { op: 'eq', left: { path: 'entityType' }, right: { literal: 'agent' } },
    groupBy: ['entityName'],
    measures: ['timeToFirstChunk.p50', 'timeToFirstChunk.p95', 'timeToFirstChunk.count'],
    orderBy: { field: 'timeToFirstChunk.p95', direction: 'desc' },
  })
}
```

### 首个 token 耗时（TTFT） {/* #time-to-first-token-ttft */}

首个 token 耗时（TTFT）是从模型调用开始（即提供商请求发起时）到该调用流式输出首个数据块的毫秒数。与 TTFC 不同，它不包含 Mastra 在调用模型前所做的工作，例如输入处理器。

`timeToFirstToken.*` 指标聚合根 Span 的 `timeToFirstTokenMs`。过滤和排序方式详见[按首个数据块或 token 的耗时过滤和排序](#filter-and-sort-by-time-to-first-chunk-or-token)。对比 TTFC 与 TTFT，可以判断 Agent 的等待时间有多少来自模型调用前的工作。

### 记录首个数据块和 token 耗时的 Span 类型 {/* #first-chunk-and-token-span-types */}

以下 Span 类型记录 TTFC 和 TTFT：

- `model_inference`：每次提供商调用。
- `model_step`：生成过程中的每一步，取该步骤首次流式输出数据块的推断值。
- `model_generation`：整个生成过程，只取首次流式输出的推断值。多步骤生成（如 Tool 循环）只报告首次调用。
- `agent_run`：Agent 运行，取其自身循环中首次模型生成的值。TTFC 从运行开始时计时。

Tool 调用和 Workflow 运行等其他 Span 不记录这两个值。若 Trace 的根 Span 是 Workflow，则 Trace 范围内没有 TTFC 或 TTFT。

TTFT 只在流式输出该数据块的 `model_inference` Span 上测量一次。使用回退模型或重试的步骤，取其首次流式输出数据块的推断值。失败的回退尝试只有在失败前输出过数据块时才有值。进程内 Agent 在同一个推断 Span 内重试失败的模型调用，因此其 TTFT 包含失败尝试及重试等待时间。持久化 Agent 则为每次尝试创建一个推断 Span。

Mastra 存储把 TTFT 放在专用列中，而非存储的 `attributes` 中。应从 Span 的 `timeToFirstTokenMs` 字段读取。

### 缺失的首个数据块与 token 耗时值 {/* #missing-first-chunk-and-token-values */}

Span 未流式输出数据块时，该值为 `null`。`0` 并非缺失值，而是表示首个数据块与 Span 开始发生在同一毫秒。

- 在谓词中，`null` 视为缺失：它匹配 `notExists`，但不匹配有序比较谓词。
- 在 `orderBy` 中，无论升序还是降序，缺失值都排在最后；`0` 按实际值排序。
- 在聚合中，缺失值的 Span 和 Trace 会被跳过，不会按 0 计算。

过滤、排序和聚合分别需要对应的存储功能。各项操作所需的 `traceQueryTimeToFirstChunk`、`traceQueryTimeToFirstChunkSort`、`traceQueryTimeToFirstToken`、`traceQueryTimeToFirstTokenSort` 和 `aggregateTimeToFirstMeasures` 标志见[检查能力](#check-capabilities)。使用旧版存储时，结果会省略不支持的字段；引用这些字段的请求会在执行存储操作前返回 `501`；[字段发现](#discover-fields-and-values)也会省略它们。

对于 `timeToFirstChunk.*` 和 `timeToFirstToken.*`，若组内没有任何 Trace 记录值，`avg`、`min`、`max` 和百分位数均为 `null`；`.count` 则为有值的 Trace 数量。百分位数是否为近似值取决于存储。使用这些指标需要 `aggregateTimeToFirstMeasures` 能力。

### 过滤和排序分组 {/* #filter-and-order-groups */}

每组对应一种不同的 `groupBy` 值组合。`having`、`orderBy` 和 `limit` 作用于分组；即使设置了 `interval`，也使用整段时间范围内的分组指标。服务器先执行 `having`，再排序剩余分组并保留前 `limit` 个。如果剩余分组数超过 `limit`，`truncated` 为 `true`。

`having` 采用标量谓词格式，以指标名称作为路径，例如 `{ op: 'gt', left: { path: 'duration.p95' }, right: { literal: 5000 } }`。它可以引用请求的指标和 `count`，即使未请求 `count` 也可以。支持数字字面值的比较运算符、`in` 和 `notIn`，并可通过 `and`、`or` 和 `not` 组合；不支持存在性、标签和文本运算符。值为 `null` 的指标不会满足任何 `having` 比较，因此相应分组会被移除。

以下请求保留第 95 百分位耗时超过五秒的 Workflow：

```typescript
const slowWorkflows = await mastraClient.aggregateTraces({
  timeRange: {
    from: '2026-08-01T00:00:00.000Z',
    to: '2026-08-08T00:00:00.000Z',
  },
  where: { op: 'eq', left: { path: 'entityType' }, right: { literal: 'workflow_run' } },
  groupBy: ['entityName'],
  measures: ['count', 'duration.p95', 'duration.p99'],
  having: { op: 'gt', left: { path: 'duration.p95' }, right: { literal: 5000 } },
  orderBy: { field: 'duration.p95', direction: 'desc' },
})
```

排序是确定性的。若排序值相同，按维度值升序决定先后。无论排序方向，值为 `null` 的指标和维度都排在最后。

### 时间桶 {/* #time-buckets */}

设置 `interval` 后，通过 `having` 和 `limit` 的每组会展开为每个非空时间桶一行。时间桶按 UTC 对齐，因此 `1d` 时间桶从 UTC 零点开始；每行的 `bucket` 是该桶开始时间的 ISO 格式。Trace 归入其根 Span 的 `startedAt` 所在时间桶。结果先按分组、再按 `bucket` 升序排列。

不含 Trace 的时间桶会被省略，而非返回值为零的行。绘制图表时，应在客户端补齐空档。由于分组先按整个时间范围排序，每个返回分组都包含其所有非空时间桶的完整序列。

以下请求返回每个 Agent 每天的 token 用量和成本：

```typescript
const dailyCost = await mastraClient.aggregateTraces({
  timeRange: {
    from: '2026-08-01T00:00:00.000Z',
    to: '2026-08-08T00:00:00.000Z',
  },
  where: { op: 'eq', left: { path: 'entityType' }, right: { literal: 'agent' } },
  groupBy: ['entityName'],
  interval: '1d',
  measures: ['count', 'tokens.total.sum', 'cost.sum', 'cost.avg'],
  orderBy: { field: 'cost.sum', direction: 'desc' },
  limit: 5,
})
```

### 聚合响应 {/* #aggregate-responses */}

```json
{
  "rows": [
    {
      "dimensions": { "entityName": "supportAgent" },
      "bucket": "2026-08-01T00:00:00.000Z",
      "measures": {
        "count": 412,
        "tokens.total.sum": 1830442,
        "cost.sum": 4.21,
        "cost.avg": 0.0103
      },
      "cost": { "coverage": 0.99, "unit": "USD" }
    }
  ],
  "truncated": false

```

`dimensions` 以 `groupBy` 字段为键，仅在 `groupBy` 非空时出现。设置 `interval` 时会出现 `bucket`。`measures` 以请求的指标名称为键。若没有匹配的 Trace，或 `having` 移除了全部分组，`rows` 为空。

### 聚合限制与错误 {/* #aggregate-limits-and-errors */}

| 限制 | 上限 |
| - | - |
| 时间范围 | 365 天 |
| `groupBy` 维度数 | 2 |
| `limit` | 1,000 个分组 |
| 时间范围内的桶数 | 1,000 |
| `limit` × 桶数 | 10,000 行 |

[查询限制](#query-limits)中的谓词限制同时适用于 `where` 和 `having`；请求体上限为 256 KiB。如果时间范围未从时间桶边界开始，则触及的桶数会比“时长除以间隔”多一个。桶数过多时，请加大 `interval`；若 `limit` × 桶数超过 10,000，请降低 `limit` 或加大间隔。

PostgreSQL 和 ClickHouse 聚合使用与 Trace 查询相同的[执行超时](#keyset-ordering-and-errors)，默认 15 秒。此超时不适用于 DuckDB。

| 状态码 | 含义 |
| - | - |
| `400` | JSON 格式错误。 |
| `413` | 请求体超过 256 KiB。 |
| `422` | 请求无效，返回 `TRACE_QUERY_INVALID` 及问题详情。时间范围超过 365 天会产生 `invalid_request` 问题。其他问题代码包括 `too_many_buckets`、`too_many_rows`、`field_not_allowed`、`invalid_metadata_key` 和 `operator_not_allowed`。 |
| `501` | 已安装的 Core 或配置的可观测性存储不支持聚合或所请求字段。返回 `TRACE_AGGREGATE_UNSUPPORTED`。 |
| `504` | PostgreSQL 或 ClickHouse 聚合超出执行超时时间。返回 `TRACE_QUERY_EXECUTION_TIMEOUT`，不包含部分结果。 |

## 聚合 Span {/* #aggregate-spans */}

使用 `aggregateSpans()` 或 `POST /api/observability/spans/aggregate`，可以针对各个 Span 而非 Trace 计算指标。Trace 聚合只查看每个 Trace 的根 Span，因此不会统计 Workflow 中嵌套的 Agent 运行。Span 聚合则统计任意层级中所有匹配的 Span。

请求格式与 [`aggregateTraces()`](#aggregate-request-fields) 相同，固定指标、`having`、`orderBy`、`interval` 和共同限制也相同。`where`、维度及 `countDistinct` 字段遵循下述 Span 约定。不支持 Span 聚合时返回 `501 SPAN_AGGREGATE_UNSUPPORTED`。

### 使用客户端 SDK 聚合 Span {/* #aggregate-spans-with-the-client-sdk */}

以下请求按天、按状态统计 Agent 运行，包括嵌套运行：

```typescript
const { capabilities } = await mastraClient.getObservabilityCapabilities()

if (capabilities.spanAggregate) {
  const { rows } = await mastraClient.aggregateSpans({
    timeRange: {
      from: '2026-08-01T00:00:00.000Z',
      to: '2026-08-08T00:00:00.000Z',
    },
    where: { op: 'eq', left: { path: 'spanType' }, right: { literal: 'agent_run' } },
    groupBy: ['status'],
    interval: '1d',
    measures: ['count', 'duration.p95'],
  })
}
```

要直接使用 HTTP，请将相同请求体发送到 `POST /api/observability/spans/aggregate`。

### Span 选择条件 {/* #span-selection */}

聚合使用与 [`querySpans()`](#query-spans) 相同的 Span 谓词，但 ClickHouse 的选择行为有以下差异：

- `timeRange` 限制每个 Span 的 `startedAt`，时间跨度最长 365 天。
- `where` 接受 `querySpans()` 的字段和运算符，例如 `spanType`、`name`、`status`、`durationMs`、`model`、`provider`、实体及父级／根实体字段，还有上下文标识符。与 `querySpans()` 一样，`model` 和 `provider` 过滤条件只读取 Span 的列，不读取属性。
- 只统计已完成的 Span。若同一 Span 导出多次，只统计最新副本。

`count` 统计每组或每个时间桶中选中的 Span。分桶依据各 Span 的 `startedAt`。`duration.*` 指标读取 Span 自身耗时，`errorCount` 和 `errorRate` 则取决于该 Span 自身是否记录了错误。

`timeToFirstToken.*` 和 `timeToFirstChunk.*` 读取 Span 自身的 `timeToFirstTokenMs` 与 `timeToFirstChunkMs`。哪些 Span 会记录这些值，详见[记录首个数据块和 token 耗时的 Span 类型](#first-chunk-and-token-span-types)。如需每次调用的 TTFT，按 `model_inference` 过滤；如需 Agent 调用方感受到的延迟，按 `agent_run` 过滤。不指定 `spanType` 时，一次 Agent 调用会计入 Agent 运行、模型生成，以及所有模型步骤和模型推断。

在 ClickHouse 中，直接使用 `spanType` 的 `eq` 或 `in` 谓词，或将该谓词直接放在 `and` 中，可选用更小的分支表。所有选定类型都必须是分支类型：`agent_run`、`workflow_run`、`processor_run`、`scorer_run`、`rag_ingestion`、`tool_call` 或 `mcp_tool_call`。请求的每个字段也必须在该表中可用。等价的 `or` 谓词不能触发此优化。分支路径的结果可能与 `querySpans()` 不同：

- 升级前由 `@mastra/clickhouse` 1.4、1.5 或 1.6 写入的 Span 不在分支表中，因此旧时间窗口统计的 Span 数量可能较少。
- ClickHouse 合并同一 Span 的多个导出副本后，分支表保留最后写入的副本，而非最后结束的副本。保留版本的状态和耗时可能不同；即使 Span 标识未变，也可能改变过滤后的计数和分组归属。

### Span 维度 {/* #span-dimensions */}

| 维度 | 说明 |
| - | - |
| `name`, `spanType`, `status` | Span 自身的名称、类型和状态。记录错误时 `status` 为 `error`，否则为 `success`。 |
| `outcome`, `stopReason` | Span 的结束方式和原因。未记录值的 Span 归入 `null` 分组。需要 `spanQueryOutcomeFields` 能力。 |
| `entityType`, `entityId`, `entityName` | 产生该 Span 的实体。 |
| `parentEntityType`, `parentEntityName`, `rootEntityType`, `rootEntityName` | 调用方实体和 Trace 的根实体，例如发起模型调用的 Agent。 |
| `environment`, `serviceName`, `executionSource` | 记录在 Span 上的部署属性。 |
| `threadId`, `resourceId`, `userId`, `sessionId`, `organizationId`, `experimentId` | 记录在 Span 上的上下文标识符。 |
| `model`, `provider` | Span 的 `model` 与 `provider` 列所记录的模型和提供商，例如 `__AI_SDK_ANTHROPIC_MODEL_SONNET__` 和 `anthropic`。需要 `spanAggregateModelDimensions` 能力。 |

`countDistinct.<field>` 接受这些维度及 `traceId`，因此 `countDistinct.traceId` 统计所选 Span 所属的不同 Trace 数量。Span 聚合不能按 `metadata.<key>`，也不能按 `traceId`、`spanId` 或 `runId` 等身份字段分组。

与 `model` 和 `provider` 过滤条件一样，`model` 和 `provider` 维度只读取 Span 对应的列，不读取属性。现有 Span 不会回填，因此在 `@mastra/observability` 开始填充这些列之前导出的 Span 会归入 `null` 分组，也不会被 `countDistinct.model` 统计。

存储通过 `span-aggregate-model-dimensions` 功能声明支持，服务器将其报告为 `spanAggregateModelDimensions` 能力。旧版存储在收到按 `model` 或 `provider` 分组、或统计其不同值的请求时，会在执行存储操作前返回 `501`。

### Span 的 token 与成本 {/* #span-tokens-and-cost */}

Token 与成本指标使用每个 Span 记录的用量指标，通过 `traceId` 和 `spanId` 匹配。[Trace token 规则](#token-and-cost-measures)分别适用于各 Span：从 `timeRange.from` 起记录的指标会计入，重试导出只计一次，平均值以有用量的 Span 数量为除数。

用量不会汇总到父 Span。模型调用在 `model_generation` Span 上记录用量，因此 `agent_run` Span 自身没有 token，除非其下的模型调用未被导出。若某个 `model_generation` Span 未导出，其用量会改记在最近的已导出祖先 Span 上。要统计每个 Agent 的 token 总量，请选择 `model_generation` Span 并按调用方 Agent 分组：

```typescript
const tokensByAgent = await mastraClient.aggregateSpans({
  timeRange: {
    from: '2026-08-01T00:00:00.000Z',
    to: '2026-08-08T00:00:00.000Z',
  },
  where: { op: 'eq', left: { path: 'spanType' }, right: { literal: 'model_generation' } },
  groupBy: ['parentEntityName'],
  measures: ['tokens.total.sum', 'cost.sum'],
  orderBy: { field: 'cost.sum', direction: 'desc' },
})
```

如果要比较模型，则将相同 Span 按 `model` 分组：

```typescript
const { capabilities } = await mastraClient.getObservabilityCapabilities()

if (capabilities.spanAggregateModelDimensions) {
  const { rows } = await mastraClient.aggregateSpans({
    timeRange: {
      from: '2026-08-01T00:00:00.000Z',
      to: '2026-08-08T00:00:00.000Z',
    },
    where: { op: 'eq', left: { path: 'spanType' }, right: { literal: 'model_generation' } },
    groupBy: ['provider', 'model'],
    measures: ['count', 'tokens.total.sum', 'cost.sum'],
  })
  // rows[0]: { dimensions: { provider: 'anthropic', model: '__AI_SDK_ANTHROPIC_MODEL_SONNET__' }, measures: { ... } }
}
```

### 列出某组对应的 Span {/* #list-the-spans-behind-a-group */}

聚合不会返回 Span 记录。要查看某组，将相同的 `timeRange` 和 `where` 传给 `querySpans()`，并把非 null 的维度值添加为 `eq` 条件。若维度为 null，则使用 `notExists`，例如 `{ op: 'notExists', path: 'entityName' }`；使用 `literal: null` 的 `eq` 会被拒绝。例如，添加 `{ op: 'eq', left: { path: 'status' }, right: { literal: 'error' } }`，即可列出首个示例中的失败 Agent 运行。

## 可信租户范围 {/* #trusted-tenant-scope */}

服务多个租户的宿主在查询文档之外提供可信范围。服务器读取保留的 `organizationId` 请求上下文键；只有服务端身份验证可以设置该键，并将 `{ organizationId }` 传给规划器。可信规划会携带此范围，并将其作为 AND 条件应用到每次扫描：当前根 Span、关联 Span、token 与成本指标读取的用量指标、Span 聚合及两个发现路由。其他租户的关联记录即使共享相同的 `traceId`，也不能使 Trace 匹配。

直接调用存储的宿主，可以向 `planTraceQuery()`、`planTraceAggregate()`、`planSpanAggregate()`、`planTraceQueryObservedFields()` 和 `planTraceQueryValues()` 传入更完整的范围：

```typescript
const plan = planTraceQuery(parseTraceQueryRequest(request), {
  scope: { organizationId: 'org_123', resourceId: 'project_456' },
})
```

`resourceId` 可选，用于在组织内进一步缩小范围。键集和增量游标都绑定该范围。在一个范围下创建的游标若用于另一个范围，会在执行存储操作前返回 `409`。若带范围的请求发给尚不支持租户范围的可观测性存储或 `@mastra/core`，会返回 `501`，而不是在无范围限制下运行。存储通过 `trace-query-tenant-scope` 功能声明支持。调用方不能在谓词中指定 `projectId`。`organizationId` 谓词比较记录的数据，并与可信范围取 AND，因此只能缩小租户自身的 Trace 范围，不能扩大范围。没有可信范围时，路由维持原有行为，自托管部署可继续使用自己的租户模型。

## 发现字段和值 {/* #discover-fields-and-values */}

使用 Trace 查询的发现功能构建字段和值的自动补全，无需扫描 Trace 数据内容，也无需把查询语法复制到客户端。配置的可观测性存储必须支持 `trace-query-discovery`。

CLI 没有专门的发现命令；请使用下文的 SDK 方法，或 HTTP 端点 `POST /api/observability/traces/query/fields` 和 `POST /api/observability/traces/query/values`。

针对一个谓词范围调用 `getTraceQueryFields()`：

```typescript
const timeRange = {
  from: '2026-08-01T00:00:00.000Z',
  to: '2026-08-08T00:00:00.000Z',
}

const fields = await mastraClient.getTraceQueryFields({
  timeRange,
  predicateScope: 'trace',
  search: 'region',
  limit: 25,
})
```

响应将标准字段与观察到的元数据字段分开：

```json
{
  "canonicalFields": [],
  "observedFields": [
    {
      "path": "metadata.region",
      "valueKind": "string",
      "operators": ["eq", "ne", "in", "notIn", "exists", "notExists"],
      "valueSuggestions": true,
      "occurrences": 125
    }
  ],
  "observedFieldsTruncated": false
}
```

标准字段来自用于校验 Trace 查询的同一个注册表，不占用 `limit`。其顺序与注册表一致。`observedFields` 包含从符合条件的当前根 Span 上找到的顶层字符串 `metadata.<key>` 路径。这些字段先按 `occurrences` 降序、再按路径排序。嵌套元数据、包含 `.` 的键、空键、非字符串值和过长路径均被省略。

`predicateScope` 选择局部谓词语法，它不是授权范围：

| `predicateScope` | 返回路径示例 | 查询用法 |
| - | - | - |
| `trace` | `environment` 或 `metadata.region` | 根级 `where` 谓词 |
| `spans` | `model` | 用于 `spans.some` 或 `spans.none` 内 |

字段选择器可以并行请求 `trace` 和 `spans` 范围，并标注每个字段所属的范围。返回的每个路径都可在相应范围内直接用于 `queryTraces()`。`metadata` 本身不是字段。界面可以另行提供手动输入元数据键的选项。

对于 `trace` 范围，如果服务器和存储支持聚合，字段响应还会包含 `aggregate` 对象，用于描述 `aggregateTraces()` 接受的内容：

```json
{
  "aggregate": {
    "dimensions": [{ "path": "entityName", "valueKind": "string" }],
    "measures": [
      {
        "name": "duration.p95",
        "kind": "duration",
        "statistic": "p95",
        "unit": "milliseconds",
        "approximate": true
      }
    ]
  }
}
```

`dimensions` 列出存储支持的标准维度。每个观察到的 `metadata.<key>` 字段也都是维度；`countDistinct.<field>` 接受任意维度或 `traceId`。`measures` 列出每个固定指标，以及其 `kind`、`unit` 和是否为 `approximate`。

用户选中 `valueSuggestions: true` 的字段后，调用 `getTraceQueryValues()`：

```typescript
const abortController = new AbortController()
const suggestions = await mastraClient.getTraceQueryValues(
  {
    timeRange,
    predicateScope: 'trace',
    path: 'metadata.region',
    search: 'west',
    limit: 25,
  },
  { signal: abortController.signal },
)
```

```json
{
  "values": [
    { "value": "eu-west-1", "count": 82 },
    { "value": "us-west-2", "count": 43 }
  ],
  "valuesTruncated": false
}
```

发现接口只返回字符串值。缺失值、空字符串，以及超过 4,096 UTF-8 字节的字符串都会被省略。取值先按 `count` 降序、再按值排序。建议值仅供参考：即使发现接口未返回某个有效字面值，`queryTraces()` 仍接受手动输入。

以下标准字段支持值建议：

| 范围 | 字段 |
| - | - |
| Trace | `entityName`, `entityType`, `name`, `spanType`, `environment`, `status`, `outcome`, `stopReason`, `tags` |
| Span | `name`, `spanType`, `model`, `provider`, `status`, `outcome`, `stopReason`, `entityType`, `entityName` |

`outcome` 和 `stopReason` 的建议值需要 `traceQueryOutcomeFields` 能力。在 `trace` 范围内，每个可执行的顶层字符串 `metadata.<key>` 字段也支持值建议。标识符、时间戳、耗时、首个数据块耗时、首个 token 耗时、错误和版本 ID 则不支持。字段响应仍包含 `valueSuggestions: false` 的标准字段。值端点会以 `422 TRACE_QUERY_INVALID` 拒绝这些路径。

两个发现请求都要求半开时间范围。它们采用与 `queryTraces()` 相同的当前记录语义：符合条件的已完成根 Span 满足 `from <= startedAt < to`；关联值只来自通过 `traceId` 连接到这些根 Span 的当前记录。发现接口不接受，也不应用尚在草拟的 `where` 谓词。

`search` 默认为空字符串，会去除首尾空白，并按不区分大小写的字面子字符串匹配。`%` 和 `_` 等字符不具有通配符含义。空搜索返回出现频率最高的结果。`limit` 默认为 25，最大为 100。两个端点都会多取一条结果以设置截断标志，但不提供游标。当标志为 `true` 时，请缩小 `search` 范围；它不表示存在下一页。无匹配时返回空数组，截断标志为 `false`。

若发现请求超出执行超时，路由返回 `504 TRACE_QUERY_EXECUTION_TIMEOUT`；若后端超出内存或资源预算，则返回 `503 TRACE_QUERY_RESOURCE_LIMIT`。两种失败都不返回部分建议，也不设置截断标志。截断只表示完整排序结果被截取至请求的响应上限。

ClickHouse 发现请求默认超时为 5 秒，每次查询的内存上限为 256 MiB。可在 `ClickhouseStoreVNext` 上通过 `observability.traceQuery.discovery.timeoutMs` 和 `observability.traceQuery.discovery.memoryLimitBytes` 配置。若未配置发现超时，则回退使用 `observability.traceQuery.timeoutMs`，但不改变普通 `queryTraces()` 的执行限制。

两个路由都要求 `observability:read` 权限，并使用配置的可观测性存储边界。不要在请求中发送组织或项目授权字段。发现的路径、取值和计数均应视为可观测性数据。

## 限制 {/* #limitations */}

查询和聚合 API 只处理已完成的 Trace 与 Span，不处理运行中的记录。Trace 查询不能返回自定义投影、嵌入的证据或摘要；页码分页结果包含总数。Trace 聚合不能按根 Span 的 `name`、`spanType`、`entityId` 以外的 Span 字段分组，也不能按 `traceId` 或 `attributes.*` 分组。聚合不能计算元数据的数值指标、对分组分页或把空时间桶补为零。Span 聚合不能按 `model` 或 `provider` 分组，而且只会把 token 归到记录该用量的 Span。CLI 中，`mastra api trace aggregate` 支持 Trace 聚合，`mastra api span query` 和 `mastra api span aggregate` 分别支持 Span 查询与聚合。
