# 计划任务

基于文件的 Agent 会从自己的 `schedules/` 目录发现**计划任务**。每个文件声明一个周期任务：cron 表达式，以及触发时 Agent 要执行的操作。Mastra 在启动时将这些任务注册到计划任务存储中，无需编写运行时注册代码。

本页介绍基于文件的约定。若要在运行时创建计划任务，请参阅[计划任务](/reference/schedules/overview)。

`defineSchedule` 从 `@mastra/core/agent` 重新导出，基于文件的 Agent 因而只需一个导入路径。`@mastra/core/schedules` 也会导出它。

## 快速入门 {/* #quickstart */}

在 Agent 的 `schedules/` 目录下添加文件：

```typescript title="src/mastra/agents/support/schedules/heartbeat.ts"
import { defineSchedule } from '@mastra/core/agent'

export default defineSchedule({
  cron: '*/5 * * * *',
  prompt: 'Check system health and report any failures.',
})
```

Mastra 每五分钟会用该提示词运行一次 `support` Agent。

## 计划任务 ID {/* #schedule-identity */}

计划任务的 ID 是去掉扩展名后、相对于 `schedules/` 的路径。因此，可以用嵌套目录对相关任务分组：

```text title="Schedule layout"
src/mastra/agents/
└── support/
    ├── config.ts
    ├── instructions.md
    └── schedules/
        ├── heartbeat.ts      # id: heartbeat
        ├── cleanup.md        # id: cleanup
        └── billing/
            └── sweep.ts      # id: billing/sweep
```

此 ID 在多次构建之间保持稳定，Mastra 因而能区分修改过的计划任务和新任务。重命名或移动文件等同于删除旧任务并创建新任务。

`heartbeat.ts` 和 `heartbeat.md` 会得到相同的 ID，因此同时声明这两个文件会导致构建失败。

## 执行模式 {/* #execution-modes */}

一个计划任务必须且只能设置一种执行模式；两种都设置或两种都不设置，构建都会失败。

### Prompt 模式 {/* #prompt-mode */}

`prompt` 会用固定消息运行所属 Agent。若计划任务以线程为目标，触发时会发送唤醒信号并立即返回，不等待运行结束，因为线程流运行时会继续驱动运行直至完成。无线程的计划任务则会等待 `agent.generate`，直到运行完成才结束。

```typescript title="src/mastra/agents/support/schedules/digest.ts"
import { defineSchedule } from '@mastra/core/agent'

export default defineSchedule({
  cron: '0 9 * * 1',
  timezone: 'America/New_York',
  prompt: 'Summarize last week and post the digest.',
})
```

### Handler 模式 {/* #handler-mode */}

`handler` 在计划任务触发时计算本次触发的参数。如果提示词取决于当前状态、某些触发应跳过，或运行需要频道投递上下文，请使用它。

```typescript title="src/mastra/agents/support/schedules/billing/sweep.ts"
import { defineSchedule } from '@mastra/core/agent'

export default defineSchedule({
  cron: '0 3 * * *',
  handler: async ({ mastra, agentId }) => {
    const overdue = await findOverdueInvoices()

    // Returning null skips this fire; nothing runs and the trigger is
    // recorded with outcome 'skipped'.
    if (overdue.length === 0) return null

    return {
      prompt: `Chase these overdue invoices: ${overdue.join(', ')}`,
      threadId: 'billing-ops',
      resourceId: agentId,
    }
  },
})
```

Handler 的返回值会覆盖计划任务中对应的已存储字段。返回 `undefined` 表示不覆盖，本次触发会继续使用已存储字段。由于 Handler 模式不能声明 `prompt`，这样会因缺少提示词而使本次触发失败。要运行就返回 `prompt`；要跳过则返回 `null`。

Handler 是函数，无法持久化到计划任务的存储记录中。Mastra 在计划任务触发时，会在当前进程中查找对应函数。Handler 模式既未提供也不能声明提示词时，本次触发会带原因失败，而不会向 Agent 发送空消息。

进程内查找意味着运行调度器的进程必须注册所属 Agent。常规部署使用单一入口启动，自然满足这一条件。独立 Worker 则需要与服务端使用相同的入口；若用精简入口启动而没有对应 Handler，触发会失败，任务不会运行。

### Markdown 计划任务 {/* #markdown-schedules */}

`.md` 计划任务使用 frontmatter 设置 cron，并以文档正文作为提示词。它属于 Prompt 模式，更适合编写较长的提示词：

```markdown title="src/mastra/agents/support/schedules/cleanup.md"
---
cron: '0 3 * * *'
timezone: 'UTC'
name: 'nightly cleanup'
---

Review tickets untouched for 30 days.

Close the ones that are clearly resolved and summarize the rest.
```

cron 表达式始终要加引号。开头的 `*` 会被 YAML 解释为别名，因此 `cron: */5 * * * *` 会解析失败，而 `cron: "*/5 * * * *"` 可以正常解析。

Frontmatter 接受下列所有选项，但不接受 `handler`：它需要函数，只能写在 `.ts` 或 `.js` 计划任务模块中。`prompt` 也不能设置，因为文档正文就是提示词。未知的 frontmatter 字段会使构建失败，而不是被悄悄忽略，因此像 `ifIdel` 这样的拼写错误会在构建时暴露。

## 在开发环境中测试计划任务 {/* #testing-a-schedule-in-development */}

计划任务按 cron 周期触发，迭代开发时等待周期很不方便。可改为按 ID 手动触发：

```bash
# List schedules to find the id
curl http://localhost:4111/api/schedules

# Fire one now, out-of-band from its cron
curl -X POST http://localhost:4111/api/schedules/<scheduleId>/run
```

这会记录一个 `triggerKind: "manual"` 的触发，但不会推进 `nextFireAt`，因此不影响正常的触发周期。Studio 也会列出这些计划任务及其触发历史。

存储的 ID 带命名空间并经过 URL 编码。`billing/sweep` 在 `support` Agent 上会变成 `fsa_support__billing%2Fsweep`；请从列表响应中复制 ID，不要自行拼接。

## 注册和生命周期 {/* #registration-and-lifecycle */}

Mastra 启动时会将声明的计划任务同步到存储；之后每注册一个 Agent，也会再次同步。声明计划任务即可启动调度器，无需设置 `scheduler: { enabled: true }`。

同步会对照每个声明的计划任务及其存储记录，只写入发生变化的字段：

- 新增计划任务文件会创建一条记录。
- 修改 `cron` 或 `timezone` 会更新记录并重新计算下次触发时间，因此修改后的任务不会再按旧周期触发。
- 删除或重命名计划任务文件会删除对应记录。
- 通过 API 暂停的任务在重新部署后仍保持暂停。同步会刻意保留 `status`。

同步只会删除当前进程中已注册 Agent 所属的记录，因此只加载部分 Agent 的进程不会删除其他 Agent 的计划任务。若从项目中彻底移除某个 Agent，其残留记录会在下次触发时清理，因为调度器届时找不到可运行的 Agent。

通过 `mastra.schedules.create(...)` 在运行时创建的计划任务位于单独的命名空间，不受这项同步影响。

## 限制 {/* #limits */}

**仅限根 Agent。** 请在顶层 Agent 上声明计划任务。若将 `schedules/` 目录放在 `subagents/` 下，构建会失败：Subagent 由父 Agent 连接，不会注册到 Mastra 实例，调度器因而无法将其识别为目标。请将计划任务交给父 Agent，再由它委派。

**需要存储。** 计划任务以记录形式持久化，而内存存储中的记录无法在重启后保留，因此必须为实例配置[存储](/reference/file-based-agents/storage)。

**托管环境。** 调度器作为 Mastra 进程内的后台 Worker 运行，因此宿主必须让该进程保持运行。长期运行的 Node 服务和容器都适用。若环境在请求之间冻结或回收进程（大多数 Serverless 函数平台都如此），就会错过计划任务触发。此时应改用平台自身的 cron 调用运行端点。

**代码定义的 Agent。** 如果 Agent 目录中的 `config.ts` 直接导出 `new Agent({...})`，Mastra 会原样使用该 Agent，并在警告后忽略其 `schedules/` 目录。此类 Agent 请使用 `mastra.schedules.create(...)` 创建计划任务。

## 示例 {/* #example */}

以下 Support Agent 有两个计划任务：固定的每周摘要，以及仅在有待处理事项时运行的夜间清理。

```text title="Scheduled support agent"
src/mastra/agents/
└── support/
    ├── config.ts
    ├── instructions.md
    └── schedules/
        ├── weekly-digest.md
        └── billing/
            └── sweep.ts
```

```typescript title="src/mastra/agents/support/config.ts"
import { agentConfig } from '@mastra/core/agent'

export default agentConfig({
  model: '__GATEWAY_OPENAI_MODEL__',
})
```

```markdown title="src/mastra/agents/support/schedules/weekly-digest.md"
---
cron: '0 9 * * 1'
timezone: 'America/New_York'
---

Summarize the past week's tickets and post the digest to the team channel.
```

```typescript title="src/mastra/agents/support/schedules/billing/sweep.ts"
import { defineSchedule } from '@mastra/core/agent'

export default defineSchedule({
  cron: '0 3 * * *',
  timezone: 'America/New_York',
  handler: async () => {
    const overdue = await findOverdueInvoices()
    if (overdue.length === 0) return null
    return { prompt: `Draft reminders for ${overdue.length} overdue invoices.` }
  },
})
```
