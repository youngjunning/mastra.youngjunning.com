# PlatformSandbox

用于在 Mastra Platform 环境中创建 Sandbox 的客户端。每个 `PlatformSandbox` 实例管理一个远程 Sandbox：`start()` 创建它，`executeCommand()` 在其中运行命令，`destroy()` 将其销毁。要管理更多远程 Sandbox，可创建更多实例，也可使用 `clone()` 从已配置的模板派生实例（参见[克隆多个 Sandbox](#cloning-for-a-fleet-of-sandboxes)）。

Sandbox 从预构建的 Provider 模板启动，模板已安装 Python 3、Node 22、TypeScript、tsx 和常用构建工具。你也可以使用可移植的 `Template()` 构建器创建[可复用模板](#reusable-templates)。传入稳定的 `id` 可启用[检查点恢复](#checkpoint-recovery)，使新 Sandbox 从上一个 Sandbox 的文件系统启动。

相关 Provider：用于自行托管 Railway Sandbox 的 [`RailwaySandbox`](/integrations/sandboxes/railway)，以及用于本地 Sandbox 的 [`LocalSandbox`](/reference/workspace/local-sandbox)。

:::note

接口详情参见 [WorkspaceSandbox 接口](/reference/workspace/sandbox)。

:::

## 安装 {/* #installation */}

```bash npm2yarn
npm install @mastra/platform-workspace
```

配置平台凭据。访问令牌、项目 ID 和环境 ID 均可从环境变量读取，因此部署到 Mastra Platform 时可以不传构造函数选项。

<Tabs>
  <TabItem value="env-file" label=".env 文件">
    ```bash
    MASTRA_PLATFORM_ACCESS_TOKEN=your-platform-access-token
    MASTRA_PROJECT_ID=your-project-id
    MASTRA_ENVIRONMENT_ID=your-environment-id
    ```
  </TabItem>

  <TabItem value="constructor" label="构造函数">
    ```typescript
    new PlatformSandbox({
      accessToken: 'your-platform-access-token',
      projectId: 'your-project-id',
      environmentId: 'your-environment-id',
    })
    ```
  </TabItem>
</Tabs>

部署到 Mastra Platform 时，系统会自动注入 `MASTRA_PLATFORM_ACCESS_TOKEN`、`MASTRA_PROJECT_ID` 和 `MASTRA_ENVIRONMENT_ID`，因此可以不传构造函数选项。本地开发时，`MASTRA_PLATFORM_ACCESS_TOKEN` 可以使用组织设置页面 **API Tokens** 下以 `sk_` 开头的 API 令牌。

Sandbox Provider 优先使用构造函数中的 `sandboxProvider` 选项，其次使用 `SANDBOX_PROVIDER` 环境变量，默认使用 `e2b`。

## 用法 {/* #usage */}

将 `PlatformSandbox` 添加到 Workspace，并将其分配给 Agent：

```typescript
import { Agent } from '@mastra/core/agent'
import { Workspace } from '@mastra/core/workspace'
import { PlatformSandbox } from '@mastra/platform-workspace'

const workspace = new Workspace({
  sandbox: new PlatformSandbox({
    // accessToken, projectId, environmentId all fall back to env vars
    idleTimeoutMinutes: 30,
  }),
})

const agent = new Agent({
  id: 'code-agent',
  name: 'Code Agent',
  instructions: 'You are a coding assistant working in this workspace.',
  model: '__GATEWAY_ANTHROPIC_MODEL_SONNET__',
  workspace,
})

const response = await agent.generate(
  'Print "Hello, world!" and show the current working directory.',
)

console.log(response.text)
```

### 私有网络 {/* #private-networking */}

将 `networkIsolation` 设为 `PRIVATE`，即可加入环境的私有网络，访问同一 Mastra Platform 环境中运行的其他服务：

```typescript
const workspace = new Workspace({
  sandbox: new PlatformSandbox({
    networkIsolation: 'PRIVATE',
  }),
})
```

默认的 `ISOLATED` 模式仅允许访问外部互联网，不提供私有网络连接。

### 公共端口 {/* #public-ports */}

端口默认是私有的：访问端口需要使用已登录的预览链接。设置 `publicPorts` 后，任何持有端口 URL 的人都可以访问，例如访问 webhook 接收服务：

```typescript
const workspace = new Workspace({
  sandbox: new PlatformSandbox({
    publicPorts: true,
  }),
})
```

两种情况下的端口 URL 相同，区别仅在于是否需要登录。此设置在创建 Sandbox 时确定，重新连接时传入新值不会改变已有 Sandbox。克隆实例使用传入的 `publicPorts` 选项，不沿用重新连接的 Sandbox 的设置。

### 重新连接到运行中的 Sandbox {/* #reattaching-to-a-running-sandbox */}

传入已有的 `sandboxId`，即可重新连接到运行中的 Sandbox，而非创建新 Sandbox：

```typescript
const sandbox = new PlatformSandbox({
  sandboxId: 'sbx_abc123',
})
await sandbox.start()

const result = await sandbox.executeCommand('cat', ['/workspace/state.json'])
```

设置 `sandboxId` 后，Sandbox 已经存在，因此无需提供 `environmentId`。

调用 `start()` 后，从 `sandboxId` 属性读取运行中 Sandbox 的平台 ID，并保存以供下次重新连接。在当前进程中启动 Sandbox 之前，该属性为 `undefined`。传给构造函数的选项只是供 `start()` 使用的提示；在 `start()` 执行前，`getInfo()` 仅返回本地状态，不会向平台查询该提示。默认使用 `reattach: 'best-effort'` 时，如果平台已找不到该 ID，`start()` 会根据 Sandbox 的逻辑 `id` 创建新 Sandbox。此回退操作需要 `environmentId`（或 `MASTRA_ENVIRONMENT_ID`）；如果提示可能失效，请一并提供，否则 `start()` 会抛出 `environmentId is required`。

重新连接时，`start()` 返回 `{ outcome: 'connected' }`；创建新 Sandbox 时返回 `{ outcome: 'created' }`。从检查点恢复也属于新建：即使恢复了文件系统，虚拟机仍是新的。通用约定参见 [`start()`](/reference/workspace/sandbox#start)。

如果创建新 Sandbox 会使应用依赖的状态悄然丢失，请设置 `reattach: 'required'`：

```typescript
const sandbox = new PlatformSandbox({
  sandboxId: 'sbx_abc123',
  reattach: 'required',
})
```

设置 `reattach: 'required'` 后，如果平台报告目标不存在（404）、已消失（410）或已销毁，`start()` 会抛出 `code` 为 `SANDBOX_REATTACH_FAILED` 的 `SandboxError`，且不会创建 Sandbox。错误的 `details` 包含 `provider`、`sandboxId`、`logicalId`（Sandbox 的逻辑 `id`）和 `reason`。其他错误会原样传递。若要重新创建，请清除已保存的 `sandboxId`，并在构造 Sandbox 时不再传入它。克隆实例会继承 `reattach` 设置。

### 可复用模板 {/* #reusable-templates */}

将可复用的模板构建器传给 `PlatformSandbox`。每次创建新的 Sandbox 时，都会向 Mastra Platform 发送序列化后的模板定义。平台根据内容为定义生成标识，并启动或复用对应的 Provider 构建。创建 Sandbox 不会等待构建完成。如果目标模板尚未构建完成，平台会用当前可用的最佳回退模板启动 Sandbox，同时在后台构建目标模板。回退时，平台优先使用同一系列中资源配置匹配的旧模板；如果没有，则使用 Provider 的基础模板：

```typescript
import { PlatformSandbox, Template } from '@mastra/platform-workspace'

const commitSha = process.env.REPOSITORY_COMMIT_SHA!
const template = Template()
  .cpuCount(4)
  .memoryMB(8_192)
  .setWorkdir('/workspace/repo')
  .setEnvs({ BUILD_CONFIG_MARKER: 'template-v1' })
  .aptInstall(['git', 'jq'])
  .runCmd('git clone https://github.com/mastra-ai/mastra.git /workspace/repo')
  .runCmd(`git checkout ${commitSha}`)
  .runCmd('pnpm install --frozen-lockfile')

const sandbox = new PlatformSandbox({
  environmentId: 'env_abc',
  sandboxProvider: 'e2b',
  template,
})
await sandbox.start()
```

`Template()` 支持 `cpuCount`、`memoryMB`、`docker`、`runCmd`、`setWorkdir`、`setEnvs`、`aptInstall`、`pipInstall` 和 `npmInstall`。平台会在内部序列化构建器并计算内容哈希。调用 `await template.build(options)` 可以启动或复用对应的 Provider 构建，而无需创建 Sandbox。返回结果包含 `ready`、`pending` 或 `failed` 状态、模板 ID，以及可选的重试提示或错误。

对于 E2B，`cpuCount()` 和 `memoryMB()` 设置模板构建资源。使用目标模板或资源配置匹配的旧模板创建的 Sandbox 会继承这些设置。两个方法都接受正的安全整数，默认值分别为 2 个 CPU 和 1,024 MB。重复设置时以最后一次的值为准，最终值也参与计算模板的内容标识。两个方法都不调用，等同于显式指定默认值。如果待构建的模板回退到 Provider 基础模板，Sandbox 可能使用该 Provider 的默认资源。可检查 `templatePending` 来识别这种情况。

`docker()` 会在 E2B 模板中安装 Docker Engine 和 Compose。守护进程首次使用 Docker 时才会启动，因此不使用 Docker 的 Sandbox 不会承担这部分开销。只有启用 Docker 时，它才会参与计算模板的内容标识；未启用 Docker 的模板 ID 不受影响。使用 Docker 时，内存至少应设为 2,048 MB。

Railway 会将命令、工作目录、环境变量和包安装操作转换为 Railway 模板指令。由于 Railway 的 Sandbox 模板 API 尚未提供对应的资源设置，Railway 目前会忽略 `cpuCount()` 和 `memoryMB()`。

对于公开的 GitHub 仓库，当 `start()` 需要创建新 Sandbox 时，`createRepoTemplate()` 可以按需解析并构建锁定到特定提交的模板定义：

```typescript
import { createRepoTemplate, PlatformSandbox } from '@mastra/platform-workspace'

const sandbox = new PlatformSandbox({
  environmentId: 'env_abc',
  template: createRepoTemplate({
    getRepositoryAccess: async () => ({ cloneUrl: 'https://github.com/mastra-ai/mastra.git' }),
    setupCommand: 'pnpm install --frozen-lockfile',
    memoryMB: 2048,
  }),
})
await sandbox.start()
```

`createRepoTemplate()` 接受普通选项形式的 `cpuCount`、`memoryMB` 和 `docker`，其含义与 `Template()` 构建器中的同名方法相同，包括上述内容标识和旧模板回退规则。省略这些选项即可使用 Provider 默认值。

`setupCommand` 也接受数组，每个条目会作为独立的可缓存构建步骤运行。`workingDirectory` 设置构建和 Sandbox 的工作目录，仓库会被克隆到 `<workingDirectory>/<repo>`。`buildEnv` 中的环境变量只传给构建步骤，不会写入序列化后的定义。`buildEnvRevision` 是一个不透明的标识，会在克隆和初始化步骤之前写入；更改该标识会重新构建这些步骤。每次修改 `buildEnv` 时都应更改 `buildEnvRevision`，但不要根据 `buildEnv` 的值生成它。

`getRepositoryAccess` 与 Factory Sandbox 上下文中的仓库访问解析器采用相同形式，因此宿主程序可以直接传入该上下文。若未提供解析器，`createRepoTemplate()` 会返回 `undefined`，Sandbox 则从 Provider 默认模板启动。重新连接已有 `sandboxId` 时不会运行解析器；创建新 Sandbox 时，解析器会先取得仓库默认分支的最新提交，然后平台才会启动或复用对应的模板构建。如果无法解析仓库的最新提交，或 Provider 构建失败，Sandbox 仍会使用 Provider 默认模板创建，以便运行时初始化流程从头检出仓库。对于私有仓库，短期有效的授权令牌会作为临时构建环境变量传入，不会写入序列化后的定义或持久化的模板记录，也不会影响内容标识。

#### 在一个模板中使用多个仓库 {/* #several-repositories-in-one-template */}

要在一个 Sandbox 中克隆多个仓库，请使用 `repos` 代替 `getRepositoryAccess`。每个仓库都可以指定自己的访问解析器和 `setupCommand`；后者可以是字符串或数组，数组中的每个条目都是独立的构建步骤：

```typescript
const template = createRepoTemplate({
  repos: [
    {
      getRepositoryAccess: async () => ({ cloneUrl: 'https://github.com/mastra-ai/mastra' }),
      setupCommand: 'pnpm install --frozen-lockfile',
    },
    {
      getRepositoryAccess: async () => ({
        cloneUrl: 'https://github.com/mastra-ai/template-docs-expert',
      }),
      setupCommand: 'npm install',
    },
  ],
  workspaceSetupCommand: 'npm install --global @mastra/mcp-docs-server',
  continueOnSetupFailure: true,
  workingDirectory: '/home/user/repos',
})
```

每个仓库都会被克隆到 `<workingDirectory>/<repo>`。公开仓库先于私有仓库构建，每组内部保持传入时的顺序。私有仓库凭据是临时构建环境变量，所有构建步骤都能读取；因此，一个仓库的初始化命令也能读取其他仓库的令牌。请只将初始化命令可以相互信任的仓库放在同一列表中。

所有仓库完成初始化后，`workspaceSetupCommand` 会在工作目录中运行。`continueOnSetupFailure` 默认为 `false`；启用后，初始化命令失败时会将对应仓库记录到 `.mastra-sandbox/setup-failed`，然后继续构建，而不是让整个构建失败。

标记文件可让会话判断镜像已完成哪些步骤：每个仓库对应 `.mastra-sandbox/repos/<repo>`，Workspace 初始化命令完成后对应 `.mastra-sandbox/workspace-setup`。这些标记都位于工作目录下。启用 `continueOnSetupFailure` 时，应先检查 `.mastra-sandbox/setup-failed`。

工作目录和按顺序排列的仓库列表共同决定系列键。更改其中任一项都会产生新系列；在该系列首次构建完成前，Sandbox 会从基础模板启动。修改初始化命令或凭据则仍属于原系列。如果任一仓库的访问信息无法解析，模板会退化为仅包含资源配置的模板，直到下次解析成功。如果无法解析某个仓库的最新提交，克隆该仓库时便不会锁定提交，其他仓库仍保持各自的提交锁定。

`createRepoTemplate()` 还会在定义中加入与提交无关的 `family` 键。单个仓库使用 `repo:<cloneUrl>:<workingDirectory>/<repo>`；多个仓库则根据工作目录和按顺序排列的克隆 URL 计算 `repos:<hash>`。`family` 将同一对象的历次构建归为一组，因此同一仓库的不同提交都属于同一系列。平台会查找该系列中先前已就绪的构建，让新提交先从已有的文件系统启动，同时在后台构建锁定到目标提交的模板。对于 E2B，查找旧模板时还会按实际 CPU 和内存配置区分，以免回退过程悄然改变请求的机器规格。直接使用 `Template()` 构建器时，可以通过 `.withFamily(key)` 指定系列键；`key` 可以是最多 200 个字符的任意非空字符串。不指定系列键则不会回退到同系列旧模板。系列键不影响按内容生成的模板标识：如果两个定义只有 `family` 不同，它们会共用同一个缓存位置。

在选定的环境和 Provider 范围内，平台会以服务端根据定义计算的内容哈希为键保存构建状态。

#### 查看尚未完成的模板构建 {/* #observing-a-pending-template-build */}

当 Sandbox 从回退模板启动时，无论使用的是同一系列中资源配置匹配的旧模板，还是 Provider 基础模板，平台响应都会包含 `templatePending` 字段；`PlatformSandbox` 会公开该字段，供你查看构建状态：

```typescript
await sandbox.start()
if (sandbox.templatePending) {
  // The sandbox is running on a fallback template.
  // A later start() of a sandbox with the same template definition
  // will pick up the exact template once the background build finishes.
  console.log('exact template still baking:', sandbox.templatePending.templateId)
}
```

如果 Sandbox 从目标模板启动，`templatePending` 为 `undefined`。`PlatformSandbox` 不会在运行中的 Sandbox 内重新执行模板操作。与使用新模板启动时一样，你需要在自己的运行时初始化流程中处理与特定提交相关的文件系统状态，例如在 `onStart` 钩子中运行 `git fetch && git checkout <sha>`。待目标模板构建完成后，可在后续调用 `start()` 时重新创建 Sandbox，以使用该模板。

:::warning

默认情况下，所有模板操作都会序列化后发送到平台，由平台根据所选 Provider 的能力执行。短期有效的构建凭据应通过 `setEnvs(values, { ephemeral: true })` 传入：这些值会单独发送，不参与计算内容标识，也不会持久化。它们在运行时不可用；如果与序列化的环境变量同名，则优先使用这些临时值。每次可能触发构建的构建请求或新建 Sandbox 操作，都需要重新提供这些值。在 Railway 上，Provider 缓存包含临时构建变量。因此，即使平台模板 ID 不变，更换变量值也可能触发新的 Provider 构建。

:::

### 检查点恢复 {/* #checkpoint-recovery */}

构造函数中的 `id`（显式指定或自动生成）会通过 `POST /sandbox` 发送到平台，作为供恢复时参考的键：

* 如果平台识别出该 `id` 属于先前的会话，新 Sandbox 会从先前 Sandbox 文件系统的最新检查点启动，而不是从基础配置启动。
* 如果平台不识别该 `id`，则会从基础配置创建新 Sandbox。自动生成的 ID 不会与已有 ID 匹配，因此省略 `id` 就相当于关闭检查点恢复。

传入固定的 `id`，即可在不同会话之间，或在一次 `destroy()`/`start()` 周期之后，保留 Sandbox 的文件系统：

```typescript
const sandbox = new PlatformSandbox({
  id: `project-${projectId}`,
})
await sandbox.start() // Boots from the most recent checkpoint for this id, or fresh if unknown
```

检查点恢复的粒度比通过 `sandboxId` 重新连接更粗。通过 `sandboxId` 重新连接时，应用会接入原来仍在运行的 Sandbox 及其中的进程。检查点恢复则会创建全新的 Sandbox，并从平台为具有相同 `id` 的上一个 Sandbox 保存的最新检查点恢复文件系统。运行中的进程，以及最后一次检查点之后写入的文件，都不会恢复。

更新文件系统后，调用 `snapshot()` 可立即保存用于恢复的检查点。如果调用方未提供 `id`，或 Sandbox 尚未运行，该方法会直接完成，不会保存检查点。

```typescript
await sandbox.snapshot()
```

每个 `id` 对应一个独立的文件系统。如果无关的 Sandbox 共用同一个 `id`，平台可能会让它们从彼此的检查点启动。

设置 `seedCheckpointName`，可在对应 `id` 的检查点尚不存在时，提供仅供启动使用的回退检查点。如果两种检查点都存在，平台会优先恢复 `id` 对应的检查点。此后创建的快照仍会写入 `id` 对应的检查点，不会修改初始检查点。

```typescript
const sandbox = new PlatformSandbox({
  id: `project-session-${sessionId}`,
  seedCheckpointName: 'project-base',
})
```

### 克隆多个 Sandbox {/* #cloning-for-a-fleet-of-sandboxes */}

`clone()` 会返回一个独立的 `PlatformSandbox` 实例。它会继承原实例的凭据和默认设置，包括访问令牌、项目、环境、Provider、模板、网络隔离、超时设置、指令、环境变量、空闲超时和公共端口；你也可以为每个实例覆盖这些设置。返回的 Sandbox 尚未启动，只有调用其自身的 `start()` 时才会创建，因此 `clone()` 不会执行 I/O 操作：

```typescript
const template = new PlatformSandbox({
  networkIsolation: 'PRIVATE',
  idleTimeoutMinutes: 30,
})

const perProject = template.clone({ id: `project-${projectId}` })
await perProject.start()
```

为 `clone()` 创建的每个实例分别指定固定的 `id`，即可让它们各自启用[检查点恢复](#checkpoint-recovery)。

### 执行命令 {/* #executing-commands */}

`executeCommand` 会在远程 Sandbox 中运行命令并返回输出。通过 `args` 传入参数，可确保参数经过安全的 shell 引号处理：

```typescript
const result = await sandbox.executeCommand('python', ['analyze.py'], {
  timeout: 30_000,
  cwd: '/workspace',
  env: { INPUT: 'repo' },
})

console.log(result.stdout)
console.log(result.exitCode)
```

:::warning

`command` 参数是 shell 字符串，会原样拼接到远程 shell 命令中。这允许你使用管道、重定向和命令串联（`ls -la | grep foo`），但不可信输入必须通过 `args` 传入以进行安全的引号处理，或由调用方自行进行 shell 引号处理。将不可信内容用作 `command`，可能导致在 Sandbox 中执行任意 shell 命令。

:::

### 后台进程 {/* #background-processes */}

`sandbox.processes` 可在后台运行命令。命令运行期间会持续输出；你可以列出这些进程、连接到进程并将其停止：

```typescript
const handle = await sandbox.processes.spawn('pnpm dev', {
  onStdout: data => console.log(data),
})

// Everything running in the sandbox, plus exited processes not read yet
const running = await sandbox.processes.list()

await handle.kill()
```

进程默认没有时间限制，除非你通过 `spawn()` 或构造函数传入 `timeout`。调用 `get(pid)` 可以连接到当前管理器未启动的进程，例如应用重启后仍在运行的进程。连接前产生的输出无法获取。

长时间运行的进程会定期重新连接输出流，进程在重新连接期间仍会继续运行。重新连接期间产生的输出会丢失；如果进程恰好在输出流重新连接期间退出，`wait()` 会返回退出码 `1`，而非进程的实际退出码。

### 端口 URL {/* #port-urls */}

`sandbox.networking.getPortUrl(port)` 返回应用在 Sandbox 中监听的端口 URL，例如开发服务器的 URL：

```typescript
await sandbox.processes.spawn('pnpm dev --host 0.0.0.0 --port 3000')

const url = await sandbox.networking?.getPortUrl(3000)
// https://3000-<sandbox id>.sandbox.us.mastra.cloud/
```

端口默认不公开：Sandbox 所属组织的成员登录 Mastra 后，可以在浏览器中打开该 URL。设置 [`publicPorts: true`](#public-ports) 后，任何持有 URL 的人都无需登录即可访问。这个 URL 永不过期，可以分享；打开它还会唤醒已暂停的 Sandbox。

如果 Sandbox 的端口无法开放，`networking` 为 `undefined`。Sandbox 未运行或已销毁、端口号不是 1 到 65535 之间的整数，或指定的是 Sandbox 保留的控制端口时，`getPortUrl()` 会返回 `null`，且不会启动 Sandbox。访问令牌无效等其他平台错误会直接抛出。

由你控制的浏览器（例如 Agent 使用的浏览器）无法自行登录。`getPortAuthCookie(port)` 会返回一个 Cookie，让该浏览器在一小时内无需登录即可打开端口 URL。不要分享这个 Cookie：任何持有它的人都能访问该端口。

```typescript
const cookie = await sandbox.getPortAuthCookie(3000)
if (cookie) await browserContext.addCookies([cookie])
```

## 错误 {/* #errors */}

平台 API 请求失败时会抛出 `PlatformApiError`。结构化的 `{ error: { message, type } }` 响应会解析为 `.code`（机器可读的错误类型）和 `.proxyMessage`（供人阅读的消息）；原始响应体仍可通过 `.body` 获取：

```typescript
import { PlatformApiError } from '@mastra/platform-workspace'

try {
  await sandbox.executeCommand('cat', ['/missing.txt'])
} catch (err) {
  if (err instanceof PlatformApiError) {
    if (err.code === 'not_found') {
      // handle missing resource
    } else if (err.code === 'authentication_error') {
      // refresh token
    }
    console.error(err.status, err.code, err.proxyMessage)
  }
}
```

如果响应体不是 JSON，例如负载均衡器返回 HTML 格式的 502 页面，`code` 和 `proxyMessage` 都是 `undefined`。

`executeCommand` 通过 direct-exec 数据平面（连接 Railway tcp-proxy 的 WebSocket）运行命令；发生无法恢复的故障时，还可能抛出以下两种 Sandbox 错误：

```typescript
import { SandboxDestroyedError, SandboxExecTransportError } from '@mastra/platform-workspace'

try {
  await sandbox.executeCommand('pytest')
} catch (err) {
  if (err instanceof SandboxDestroyedError) {
    // /exec-lease returned 410; the sandbox has been destroyed.
    // The cached sandbox id and lease have already been cleared,
    // so reusing the instance will reprovision on the next call.
  } else if (err instanceof SandboxExecTransportError) {
    // Both the initial WebSocket attempt and the built-in retry
    // closed without an exit frame against a live sandbox.
    console.error(err.closeCode, err.closeReason, err.wsEndpoint)
  }
}
```

`SandboxExecTransportError` 包含诊断字段 `opened`、`closeCode`、`closeReason`、`wsEndpoint`、`sandboxId`、`command` 和 `attempts`，便于运维人员区分 Railway 数据平面故障与命令执行失败。
