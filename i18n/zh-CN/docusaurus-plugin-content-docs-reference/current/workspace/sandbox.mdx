# WorkspaceSandbox

**引入版本：** `@mastra/core@1.1.0`

`WorkspaceSandbox` 接口定义 Workspace 如何执行命令和管理后台进程。

## 方法 {/* #methods */}

### `start()` {/* #start */}

启动 Sandbox。调用 `workspace.init()` 或首次调用 `executeCommand()` 时会自动执行此方法。

```typescript
const result = await sandbox.start()
// { outcome: 'created' } — a fresh VM was created
// { outcome: 'connected' } — reconnected to an existing VM
// undefined — the provider does not report
```

**返回：** `void | Promise<SandboxStartResult | void>`

如果构造 Sandbox 时提供了已知的 `id`，`start()` 会解析该 ID：已有 Sandbox 则重新连接或恢复，否则创建一个（获取或创建）。支持此机制的 Provider 会返回 `SandboxStartResult`：

<PropertiesTable
  content={[
{
  name: 'outcome',
  type: "'created' | 'connected'",
  description:
    "创建全新的 Sandbox 虚拟机（或工作目录）时为 `'created'`；重新连接或恢复已有实例时为 `'connected'`。",
},
]}
/>

在此契约引入之前实现的 Provider 返回 `void`，基类会将结果视为未知。

Provider 可按以下优先顺序选择一种方式实现启动生命周期。基类负责处理并发启动调用、状态管理、`onStart` 钩子和挂载：

1. **获取原语**：实现受保护的 `find()`（按逻辑 ID 查询，不产生副作用，返回 Provider 原生句柄或 `undefined`）、`connect(handle)`（唤醒、恢复或接管）和 `create()`（创建新实例），无须覆盖 `start()`。基类执行 find → connect → `{ outcome: 'connected' }`；未找到时执行 create → `{ outcome: 'created' }`。结果由实际执行的分支确定。`E2BSandbox`、`DaytonaSandbox` 和 `LocalSandbox` 使用此方式。
2. **覆盖 `start()` 并返回 `SandboxStartResult`**：适用于 Provider API 将获取和创建合为一次调用、拆分后会增加请求往返的情况（`PlatformSandbox`、`RailwaySandbox`）。
3. **覆盖 `start()` 并返回 `void`**：适用于旧版 Provider，启动结果未知。

同一实例上的并发 `start()` 调用会合并为一次启动尝试，所有调用方共享其结果（如果这次尝试创建了虚拟机，所有调用方都会看到 `outcome: 'created'`）。尝试结束后会清除进行中的记录，因此启动失败后可以重试。对于已处于 `running` 状态的 Sandbox，`start()` 直接返回 `{ outcome: 'connected' }`，不会再次调用 Provider。

启动结果还会以 `{ sandbox, outcome }` 的形式传给 `onStart` 生命周期钩子。

### `onStart`（构造函数选项） {/* #onstart-constructor-option */}

`onStart` 在启动生命周期内运行：此时 Sandbox 已达到 `running` 状态，但待处理的挂载尚未执行。无论是显式调用、命令触发的惰性 `ensureRunning()`，还是 Provider 更换虚拟机后的恢复，每次启动都会触发此钩子。可用它完成每台虚拟机的初始化，并根据 `outcome` 判断需要执行初始化，还是检查初始化是否已完成。

```typescript
new E2BSandbox({
  id: sessionId,
  onStart: async ({ sandbox, outcome }) => {
    if (outcome === 'created') {
      // Fresh VM: run the full setup.
      await runSetup(sandbox)
      return
    }
    // Reconnected: probe, and self-heal if setup never completed.
    const probe = await sandbox.executeCommand('test -d ~/repo/.git')
    if (probe.exitCode !== 0) await runSetup(sandbox)
  },
})
```

语义：

* 钩子抛出的错误会使启动失败：`start()` 会以该错误拒绝，Sandbox 状态变为 `error`。调用方不会看到初始化钩子执行失败但仍在运行的 Sandbox。失败不会被锁定；下一次 `start()`（包括下一条惰性命令触发的启动）会重试钩子。`onStop` 和 `onDestroy` 仍是非致命的观察钩子，因为清理会尽力继续。
* `outcome` 用于区分启动路径：`'created'` 表示此次启动创建了新虚拟机，应执行初始化；`'connected'` 表示重新连接或恢复，初始化通常已完成。如果钩子需要处理创建后、初始化完成前发生的崩溃，此时应先探测状态。`undefined` 表示 Provider 未报告结果。
* 保持初始化操作的幂等性。探测结果表明需要初始化时，钩子可能再次运行；从检查点恢复出的新虚拟机会报告 `outcome: 'created'`。
* Sandbox 会在钩子执行前变为 `running`，以便钩子通过 Sandbox 自身的命令路径执行命令。因此，经 `ensureRunning()` 并发发出的命令可能与钩子交错执行。等待原始 `start()` 调用完成的调用方则一定会看到钩子已执行完毕。
* 钩子在待处理的文件系统挂载执行前运行，因此不能依赖已挂载的路径。

### `setOnStart(update)` {/* #setonstartupdate */}

在构造之后附加启动钩子，供运行时接收并非由自身构造的 Sandbox 使用。否则，每个构造 Sandbox 的宿主都必须接收钩子并将其传给 Provider 构造函数；某个宿主如果遗漏传递，初始化就会悄然缺失。

更新函数接收当前已安装的钩子（可能来自构造函数的 `onStart` 选项，也可能由先前调用安装），并返回要安装的钩子。这样组合钩子，就不会无意中丢弃调用方不知道的既有钩子：

```typescript
sandbox.setOnStart?.(previous => async args => {
  await previous?.(args) // whatever prepared the sandbox runs first
  await mySetup(args)
})
```

语义：

* 与构造函数选项一样，错误仍会使启动失败。各钩子依次等待前一个钩子，因此某个钩子抛错后，后续钩子不会执行。
* 调用方决定执行顺序。如果自己的钩子依赖 `previous` 准备的 Workspace，就先等待 `previous`；如果自己的钩子负责准备工作，就最后执行 `previous`。
* 忽略 `previous` 会替换已安装的钩子。此行为受支持，可用于接管运行时安装的初始化逻辑。
* 每次调用都会包装当前钩子，因此每个 Sandbox 实例只应附加一次。若在每次请求都会经过的路径上附加钩子，每次启动都会重复执行累积的任务。
* 新钩子只对调用之后开始的启动生效。

### `workingDirectory`（构造函数选项） {/* #workingdirectory-constructor-option */}

设置执行命令和启动进程时的默认目录。如果命令未指定自己的 `cwd`，Sandbox 就从此目录运行；命令指定的 `cwd` 始终优先。如果两者都未指定，则使用各 Provider 的默认目录（例如 E2B 主目录、Docker 的 `/workspace` 或 Vercel Serverless 的 `/tmp`）。

```typescript
const sandbox = new E2BSandbox({ workingDirectory: '/home/user/my-repo' })
await sandbox.executeCommand('pwd') // /home/user/my-repo
await sandbox.executeCommand('pwd', [], { cwd: '/tmp' }) // /tmp
```

可通过 `sandbox.workingDirectory` getter 读取实际生效的目录。Daytona 自动探测所得的目录、Docker 默认的 `/workspace` 等 Provider 计算出的目录，也会通过同一 getter 返回。

语义：

* 该值会原样传给 Provider，Sandbox 不会创建目录。建议使用绝对路径；以 `~` 开头的路径仅在 Provider 明确支持展开时才有效。
* 部分 Provider 保留了指向同一字段的旧选项名，现已弃用：Docker 和 Apple container 使用 `workingDir`，Modal 使用 `workdir`。如果同时设置旧选项和 `workingDirectory`，以后者为准。

### `stop()` {/* #stop */}

停止 Sandbox。

```typescript
await sandbox.stop?.()
```

### `destroy()` {/* #destroy */}

清理 Sandbox 资源。`workspace.destroy()` 会调用此方法。

```typescript
await sandbox.destroy()
```

### `snapshot()` {/* #snapshot */}

如果 Provider 支持快照，则保存 Sandbox 的当前状态。其他 Provider 会直接返回，不执行任何操作。

```typescript
await sandbox.snapshot()
```

**返回：** `Promise<void>`

### `setEnv(update)` {/* #setenvupdate */}

更新 Sandbox 的运行时环境。这些变量会合并到 Sandbox 执行的每条命令中，包括通过 `executeCommand()` 和 `processes.spawn()` 启动的命令。因此，在构造 Sandbox 后新增或轮换的凭据也会用于后续命令。此方法为可选方法，请先检查是否支持，或使用可选链调用。

```typescript
sandbox.setEnv?.(env => ({ ...env, GH_TOKEN: token }))
```

更新函数接收当前环境的副本，并返回替换后的环境，因此一次调用即可设置、移除或批量更新变量。删除某个键只会将其从 Sandbox 的运行时环境中移除；Provider 自行提供的同名变量仍可能生效。初始值可通过构造函数的 `env` 选项设置。

运行时环境作用于通过 Sandbox 执行的命令，而非虚拟机自身的环境，因此不会写入虚拟机，并且在 Provider 暂停、恢复后仍会保留。执行命令时，先应用 Provider 的默认值，再由 Sandbox 的运行时环境覆盖；`executeCommand()` 单次调用的 `env` 选项优先级最高。

### `getEnv()` {/* #getenv */}

此方法可用于 `MastraSandbox`，但未在 `WorkspaceSandbox` 接口中声明。它返回 Sandbox 当前运行时环境的副本；修改返回的对象不会改变 Sandbox，请使用 `setEnv()` 更新环境。

```typescript
const token = sandbox.getEnv().GH_TOKEN
```

**返回：** `Record<string, string | undefined>`

## 原生文件系统 {/* #native-filesystem */}

如果 Provider 提供文件 API，Sandbox 会通过可选的 `filesystem` 属性将其暴露出来。读取、写入和列出文件各只需一次请求；通过 `executeCommand()` 完成相同操作则每一步都需要执行一条命令。路径必须是 Sandbox 内的绝对路径。

路径范围由 Provider 负责控制：`filesystem` 本身不会将路径或符号链接限制在 Workspace 根目录内。如果没有此属性，可改用 `executeCommand()`：

```typescript
const pkg = sandbox.filesystem
  ? await sandbox.filesystem.readFile('/workspace/app/package.json', { encoding: 'utf-8' })
  : (await sandbox.executeCommand?.('cat', ['/workspace/app/package.json']))?.stdout
```

`E2BSandbox` 始终提供 `filesystem`。对于 `PlatformSandbox`，只有使用 `e2b` Provider 时才提供此属性；其他情况下返回 `undefined`。要在 Workspace 中使用它，可将其显式传入 Workspace 的 `filesystem`，也可以直接调用。

import { supportsComputer } from '@mastra/core/workspace'

}
