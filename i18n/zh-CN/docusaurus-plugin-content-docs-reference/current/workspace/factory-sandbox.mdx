# FactorySandbox

`FactorySandbox` 是主机提供给 `MastraFactory` 的对象，用于描述会话的运行位置。它负责创建会话 Sandbox、提供会话所用的仓库模板和用户可按项目调整的设置 Schema，还可以选择支持提前构建模板。

Factory 保存每个项目的设置，并在每次启动会话时将其传给 `create`。项目未设置的值会使用 Provider 的默认值。`factory.sandboxDescription` 会报告 Provider、以 JSON Schema 表示的设置 Schema，以及可用能力。Provider 的具体实现都封装在该对象中：Factory 只调用契约，并读取 `provider` 用于显示。

## 用法 {/* #usage */}

将某个 Provider 类的实例传给 `sandbox` 选项：

```typescript title="src/mastra/index.ts"
import { MastraFactory } from '@mastra/factory'
import { PlatformFactorySandbox } from '@mastra/platform-workspace'

export const factory = new MastraFactory({
  sandbox: new PlatformFactorySandbox({
    // Provider defaults for an environment that sets nothing.
    defaults: { cpuCount: 4, memoryMb: 8192 },
  }),
})
```

## Provider 类 {/* #provider-classes */}

| 类 | 包 | 设置 | 构建 |
| - | - | - | - |
|`PlatformFactorySandbox` | `@mastra/platform-workspace` | `cpuCount`, `memoryMb`, `idleTimeoutMinutes`, `publicPorts` | `start`, `get` |
| `E2BFactorySandbox` | `@mastra/e2b` | `cpuCount`, `memoryMb`, `idleTimeoutMinutes` | `start`, `get`, `list` |
| `DockerFactorySandbox` | `@mastra/docker` | `baseImage`, `owner` | `start`, `get` |
| `LocalFactorySandbox` | `@mastra/factory` | 无 | 不支持 |

每个 Provider 类都接受与对应 Sandbox 类相同的运行时选项，但不包括由该类按会话填写的 `id`、`sandboxId` 和 `template`。此外，它还接受用于配置仓库模板的 `template` 选项，以及为环境中未设置的值指定默认值的 `defaults`。

```typescript
import { PlatformFactorySandbox } from '@mastra/platform-workspace'
import { E2BFactorySandbox } from '@mastra/e2b'
import { DockerFactorySandbox } from '@mastra/docker'
import { LocalFactorySandbox } from '@mastra/factory'

new PlatformFactorySandbox() // reads MASTRA_PLATFORM_ACCESS_TOKEN and MASTRA_ENVIRONMENT_ID
new E2BFactorySandbox() // reads E2B_API_KEY
new DockerFactorySandbox({ defaults: { baseImage: 'node:22-slim' } })
new LocalFactorySandbox() // reads MASTRACODE_LOCAL_SANDBOX_ROOT, defaults to ~/.mastracode/web/sandboxes
```

`LocalFactorySandbox` 在主机上的 `join(root, sessionId)` 路径下运行每个会话。未设置 `env` 时，命令只能访问 `PATH`，以及 git 和 TLS 所需的主机变量白名单，例如 `HOME`、`USER`、`SHELL` 和 `SSL_CERT_FILE`。这样，在仓库检出目录中运行的命令无法获取应用密钥。

### 将 env 限定到单个 Factory {/* #scope-env-to-one-factory */}

每个 Provider 的 `env` 选项都接受一个记录对象，或一个以会话的 `FactorySandboxContext` 为参数的函数。如果同一部署托管多个 Factory，而某项凭据只属于其中一个，请使用函数形式：

```typescript
new PlatformFactorySandbox({
  env: ctx => (ctx.factoryId === PLATFORM_FACTORY_ID ? { PLATFORM_TOKEN } : {}),
})
```

应比较 `factoryId`，而非 `factoryName`：名称可以修改，也不保证唯一。

Platform 和 Docker 仅在创建 Sandbox 时应用 `env`。恢复运行的 Sandbox 会保留启动时的环境。如果从某些 Factory 中移除凭据，请重新创建它们正在运行的 Sandbox，以清除其中的凭据。

## 默认 Sandbox {/* #default-sandbox */}

如果省略 `sandbox` 选项，且已设置 Platform 凭据（`MASTRA_PLATFORM_ACCESS_TOKEN` 或 `MASTRA_PLATFORM_SECRET_KEY`），`MastraFactory` 会自行配置 Sandbox：

* 运行 `mastra dev` 或设置 `NODE_ENV=development` 时，使用 `LocalFactorySandbox`，避免开发期间启动远程机器。
* 在构建后的部署环境中，使用 `PlatformFactorySandbox`。这需要 `MASTRA_PROJECT_ID` 和 `MASTRA_ENVIRONMENT_ID`；缺少任一变量时，Factory 会记录警告并关闭仓库 Sandbox。

显式传入的 `sandbox` 选项始终优先。如果既没有 Platform 凭据，也没有 `sandbox` 选项，仓库 Sandbox 将关闭。

对于未设置的值，Provider 会采用自身的默认值：Platform 和 E2B 默认使用 2 个 CPU、1024 MB 内存和 5 分钟空闲超时，可通过 `defaults` 覆盖。在 Platform 上，如果 `defaults` 未指定相应值，顶层的 `idleTimeoutMinutes` 和 `publicPorts` 选项也会生效。`publicPorts` 默认关闭；启用后，任何持有端口 URL 的人都无需登录即可访问。修改此选项只影响之后创建的 Sandbox。Schema 中的 `default` 值反映最终生效的默认值。

Platform 通过启动构建的构建器轮询构建状态。主机重启后，先前构建的状态会显示为 `unknown`。

Schema 变更应保持增量兼容：新增字段；重命名字段时，在一个发布版本内同时读取新旧名称。已保存的设置文档可能比写入它的 Schema 存续更久，因此其中可能包含当前 Schema 不再声明的键，例如主机切换 Provider 后留下的键。如果这类键导致更新验证失败，Factory 会删除未声明的键并重试，之后才拒绝更新。更新请求本身设置的键绝不会被删除。

### 回调形式 {/* #callback-form */}

也支持直接传入回调 `sandbox: ctx => new E2BSandbox({ id: ctx.sessionId })`。Factory 会将其包装为 `provider: 'custom'` 的 Sandbox。Sandbox 的所有细节都留在回调中，环境不会暴露可调整的设置。

要编写自己的 Provider，请继承 `@mastra/core/workspace` 中的 `FactorySandbox`。Factory 通过基类设置的标记识别子类，因此不接受形状相同的普通对象。

```typescript
import { FactorySandbox } from '@mastra/core/workspace'
import type { FactorySandboxContext } from '@mastra/core/workspace'
import type { PublicSchema } from '@mastra/core/schema'

interface Settings {
  region?: 'us' | 'eu'
}

class MyFactorySandbox extends FactorySandbox<Settings> {
  readonly provider = 'my-cloud'
  readonly settings: PublicSchema<Settings> = {
    type: 'object',
    properties: { region: { type: 'string', enum: ['us', 'eu'], default: 'us' } },
    additionalProperties: false,
  }

  create(ctx: FactorySandboxContext, settings: Settings) {
    return new MyCloudSandbox({
      id: ctx.sessionId,
      sandboxId: ctx.sandboxId,
      template: this.template(ctx, settings),
      workingDirectory: ctx.workingDirectory,
      region: settings.region ?? 'us',
    })
  }

  // Optional: the sandbox template image Factory can build ahead of time
  template(ctx: FactorySandboxContext, settings: Settings) {
    return myCloudTemplate(ctx, settings)
  }

  // Optional: build that template ahead of time and report on it
  readonly builds = {
    start: async (ctx: FactorySandboxContext, settings: Settings) =>
      myCloud.startBuild(this.template(ctx, settings)),
    get: async (ctx: FactorySandboxContext, settings: Settings, buildId: string) =>
      myCloud.buildStatus(buildId),
    list: async (ctx: FactorySandboxContext, settings: Settings) =>
      myCloud.builds(this.template(ctx, settings).name),
  }
}
```

用户重新创建卡住的会话 Sandbox 时，Factory 可能只传入 `sessionId` 和已保存的 `sandboxId` 来调用 `create`（没有仓库访问权限，设置为空），随后不启动返回的 Sandbox，直接调用其 `destroy()`。服务器重启或会话在另一副本上打开时会出现这种情况。要支持重新创建，`destroy()` 必须能仅凭 `sandboxId` 或会话 ID 找到并删除该会话的 VM。Factory 不为 `LocalFactorySandbox` 提供重新创建功能，因为它的 `destroy()` 会保留会话目录。

## 构建状态 {/* #build-status */}

`FactorySandboxBuild.status` 的值为 `pending`、`building`、`ready`、`failed` 或 `unknown`。`unknown` 表示 Provider 无法读取并非由当前进程启动的构建状态。

## 环境构建 {/* #environment-builds */}

Sandbox 声明 `builds` 后，Factory 会在会话启动前构建环境模板，并通过 `prepare()` 注册 `factory-environment-build` Workflow。构建会在以下情况运行：

* 调用 `POST /web/factory/projects/:id/environment/build` 时，即在 Environment 页面点击 Build now，或运行 `mastra api factory project environment build <project-id>`。
* 按 core 中 `Schedules` 保存的 cron 计划运行；通过 `PATCH { buildTriggers: { schedule: { enabled: true, cron, timezone } } }` 启用。需要支持 schedules 域的存储适配器，否则路由会报告 `scheduleAvailable: false`。
* 向关联仓库的默认分支推送后，且已设置 `buildTriggers.push.enabled` 时运行；每个 `debounceMinutes` 内最多运行一次。
* 保存模板输入的变更后运行，前提是项目已有模板；构建进行期间保存的变更会在该构建结束后构建。

如果保存操作没有改变任何模板输入，就不会启动构建。如果上次构建已就绪、仓库 HEAD 未变化，且模板输入（设置、仓库及其顺序、设置命令、工作目录或 Factory 的 Build 变量）也未变化，计划构建和推送触发的构建都会跳过。Factory 只保存上次构建的 ID 和当前模板。状态和历史记录通过 Provider 的 `GET …/environment/builds/:buildId` 和 `GET …/environment/builds` 获取；如果 Provider 不保存历史记录，后者返回 404 `no_history`。

如果一次构建的启动从未被记录，且 Provider 无法列出构建，Factory 就无法判断该构建是否仍在运行。启动租约过期后的 30 分钟内，触发器会以 `unresolved` 为原因跳过；之后 Factory 会将这次启动视为失败，由下一次触发器启动构建。

## 环境变量 {/* #environment-variables */}

Factory 成员可以在 **Settings › Manage Factory › Environment variables** 中，为该 Factory 的每个 Sandbox 添加环境变量。每个变量可用于以下范围之一：

* **Runtime**：用于每个会话 Sandbox 中的每条命令。新增、修改或删除变量后，正在运行的 Sandbox 会从下一条命令起使用新值，无需重启。其他 Factory 服务器会在该 Factory 的 `pubsub` 传递变更时看到新值；如果未配置跨进程 `pubsub`，则会在一秒内看到。已经运行的进程会保留启动时的环境。
* **Build**：仅用于模板构建和 Factory 自行运行的设置命令，不用于运行时命令。Factory 通过 `buildEnv` 和 `buildEnvRevision` 将变量传给 Provider。修改变量后，模板会在下一次构建时重新构建。正在运行的 Sandbox 不会重新执行设置步骤。新 Sandbox 从重建后的模板启动；模板包含使用新值完成设置后的产物，但 Sandbox 自身的命令无法读取这些变量。在 Docker 上，模板构建目前不会收到 Build 变量，修改变量也不会重建镜像，因此只有 Factory 自行运行的设置步骤能读取它们。
* **Both**：同时用于 Runtime 和 Build。

如果 Runtime 变量与 Provider 的 `env` 选项中的键同名，它会覆盖该值；删除变量后会恢复主机提供的值。Factory 自行设置的名称（例如 `GH_TOKEN`）为保留名称。

变量值使用 Factory 的凭据加密密钥进行静态加密，无法通过 API 或 UI 读回。Sandbox 内运行的任何程序都可以读取这些值。启用登录但未配置加密密钥时，Factory 会拒绝保存变量，设置页面会说明原因。相关路由为 `GET /web/factory/projects/:id/sandbox-envs`，以及 `PUT`、`PATCH` 和 `DELETE /web/factory/projects/:id/sandbox-envs/:name`。
