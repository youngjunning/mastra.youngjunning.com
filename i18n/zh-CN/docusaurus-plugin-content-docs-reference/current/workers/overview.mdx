# 工人

:::测试版

在 API 稳定之前，可能会在没有重大版本更新的情况下发生重大更改。

:::

有关使用模式和部署拓扑，请参阅[Workers](/docs/deployment/workers).

## 环境变量 {/* #environment-variables */}

### `MASTRA_WORKERS` {/* #mastra_workers */}

控制哪些工作进程在当前进程中启动。

|价值|行为 |
| - | - |
|*(not set)* | Default workers are auto-created based on configuration |
| `"false"` | Disables worker event processing. The process serves HTTP requests and can still publish events to PubSub (e.g., workflow starts) without consuming them. |
| `"orchestration"` | Only the orchestration worker starts |
| `"scheduler"`|仅调度程序工作者启动 |
|`"backgroundTasks"`|仅后台任务worker启动|
|`"orchestration,scheduler"`|多个工人（逗号分隔）|

使用它可以在同一构建工件的不同容器中运行不同的工作程序类型。

环境`MASTRA_WORKERS` to any value, including `"false"`, also makes `createWorkflow` build workflows that declare `schedule` on the evented engine. Set it on every process in a split deployment. See [Scheduled workflows](/docs/workflows/scheduled-workflows#execution-engine).

### `MASTRA_STEP_EXECUTION_URL` {/* #mastra_step_execution_url */}

API 服务器的基本 URL，供编排工作人员用来远程执行Workflow步骤。当编排工作线程在与 API 不同的进程中运行时需要。

```bash
MASTRA_STEP_EXECUTION_URL=http://api:4111/api
```

在生产中使用 HTTPS URL。看[Security recommendations](/docs/auth/workers#security-recommendations).

编排工作人员将步骤执行请求发送至：

```text
${MASTRA_STEP_EXECUTION_URL}/workflows/:workflowId/runs/:runId/steps/execute
```

### `MASTRA_WORKER_AUTH_TOKEN` {/* #mastra_worker_auth_token */}

调用 API 的步骤执行端点时，编排工作线程发送的承载令牌。 API 的已配置身份验证提供程序必须识别此令牌。看[Worker authentication](/docs/auth/workers).

```bash
MASTRA_WORKER_AUTH_TOKEN=sk-worker-secret-token
```

## 工人类型 {/* #worker-types */}

### 编排工作者 {/* #orchestrationworker */}

处理来自 PubSub 的Workflow事件`workflows` topic. Requires a pull-capable PubSub like `@mastra/redis-streams` or `@mastra/google-cloud-pubsub` configured with a pull subscription.

* **姓名**: `orchestration`
* **发布订阅主题**: `workflows`
* **消费群体**: `mastra-orchestration`

### 调度工作者 {/* #schedulerworker */}

轮询存储以获取到期的 cron 计划并发布`workflow.start` event to the `workflows` topic for each fire. The orchestration worker runs default-engine workflows in-process and evented workflows step by step.

* **姓名**: `scheduler`
* **仅单个实例**：仅运行一个实例以避免重复火灾

### 后台任务工作者 {/* #backgroundtaskworker */}

执行Agent分派的后台Tool调用。

* **姓名**: `backgroundTasks`
* **发布订阅主题**: `background-tasks`
* **消费群体**: `background-task-workers`
* **支持多个副本**：实例共享消费组

## 支持的存储后端 {/* #supported-storage-backends */}

运行所有工作线程类型的部署需要一个实现以下功能的存储后端`workflows`, `backgroundTasks`, and `schedules` domains. The `schedules` domain is specifically required by the SchedulerWorker. If you don't use scheduled workflows, backends without it can still support orchestration and background tasks. The following backends support all three:

|后端 |套餐 |
| - | - |
| PostgreSQL |[`@mastra/pg`](/integrations/databases/postgresql) |
| LibSQL | [`@mastra/libsql`](/integrations/databases/libsql) |
| MySQL | `@mastra/mysql` |
| MongoDB | [`@mastra/mongodb`](/integrations/databases/mongodb) |
| Spanner | [`@mastra/spanner`](/integrations/databases/spanner) |
| Convex | [`@mastra/convex`](/integrations/databases/convex) |

其他存储后端（Upstash、DynamoDB、Cloudflare D1、ClickHouse、Redis）支持Workflow程和一些工作人员功能，但缺少`schedules` domain. They can still be used for orchestration and background task workers if you don't deploy the scheduler.
