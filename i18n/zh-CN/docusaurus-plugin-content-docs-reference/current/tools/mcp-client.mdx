# MCPClient

`MCPClient` 类用于在 Mastra 应用中管理多个 MCP 服务器连接及其 Tool。它负责连接的生命周期和 Tool 命名空间，并提供对所有已配置服务器上的 Tool 的访问。

:::note
正在从 `@mastra/mcp` 1.x 升级？请参阅[迁移指南](/reference/migrations/mcp-v2)。
:::


### 类型化客户端契约 {/* #typed-client-contracts */}

向 `MCPClient<TServers>` 传入明确的服务器映射类型，即可检查配置中的服务器名称、发现的 Tool 名称以及直接调用的参数。`MCPClientOptions<TServers>` 接受相同的映射类型。声明的服务器均为必填项；如需只配置其中一部分，可使用 `Pick<TServers, 'weather'>`。不传入类型参数时，发现结果仍使用原有的宽泛类型。

该映射通过 `tools` 描述各服务器的 Tool，并为每个 Tool 指定 `input` 和 `output` 类型。以下示例假设 `WEATHER_MCP_URL` 指向一台正在运行的天气服务器：

```typescript
import { MCPClient } from '@mastra/mcp'

interface MCPServers {
  weather: {
    tools: {
      get_weather: {
        input: { location: string }
        output: { temperature: number; conditions: string }
      }
    }
  }
}

const mcp = new MCPClient<MCPServers>({
  servers: { weather: { url: new URL(process.env.WEATHER_MCP_URL!) } },
})

try {
  const tools = await mcp.listTools()
  const weather = tools.weather_get_weather
  if (weather?.execute) {
    const result = await weather.execute({ location: 'Paris' })
    if (result && 'temperature' in result && typeof result.temperature === 'number') {
      console.log(result.temperature)
    }
  }
} finally {
  await mcp.disconnect()
}
```

`listTools()` 和 `listToolsWithErrors().tools` 提供精确的 `server_tool` 键。`listToolsets()` 和 `listToolsetsWithErrors().toolsets` 则以服务器键组织未经前缀处理的 Tool 名称。两种结果都可能不完整：服务器或 Tool 可能不存在。调用 Tool 前请检查其是否可用。错误映射、错误详情及可选的发现耗时仍保持原有类型。

执行结果可能是结构化输出、协议结果封装对象、验证错误或 `undefined`。读取成功结果的字段前，请检查结果形状和属性类型。协议封装对象可能包含其他属性。对于没有输出 schema 的 Tool，请设置 `output: unknown`。

这些契约描述的是 schema 快照，实际运行的服务器可能与快照不同。服务器的 schema 发生变化时，请使用具有同等权限的凭据更新契约。服务器新增的 Tool 在运行时仍可使用，但不会出现在快照的已知键中。运行时发现、验证和执行行为不变。

### 生成客户端类型 {/* #generate-client-types */}

使用 `@mastra/mcp` 提供的命令，根据在线 Tool 的输入和输出 schema 生成具体的 TypeScript 接口。导出已有客户端，并设置 `typegen.outFile`：

```typescript title="src/mcp/client.ts"
import { MCPClient } from '@mastra/mcp'
import type { MCPServers } from './mcp-types.generated'

export const mcp = new MCPClient<MCPServers>({
  id: 'weather-client',
  servers: { weather: { url: new URL(process.env.WEATHER_MCP_URL!) } },
  typegen: { outFile: 'src/mcp/mcp-types.generated.ts' },
})
```

设置模块所需的环境变量和身份验证凭据，然后从项目根目录运行以下命令：

```bash npm2yarn
npx @mastra/mcp generate ./src/mcp/client.ts
```

首次运行时，仅用于导入类型的生成文件可能尚不存在。加载器处理 TypeScript 及其间接导入的模块时会跳过类型检查。生成完成后，请运行类型检查。

请使用生成的名称，并在运行时检查 Tool 是否可用以及结果的结构。下面的示例假设服务器提供 `get_weather`，它接受必填的字符串参数 `location`，并输出数值 `temperature`：

```typescript title="src/mcp/call-weather.ts"
import { mcp } from './client'

try {
  const tools = await mcp.listTools()
  const weather = tools.weather_get_weather
  if (weather?.execute) {
    const result = await weather.execute({ location: 'Paris' })
    if (result && 'temperature' in result && typeof result.temperature === 'number') {
      console.log(result.temperature)
    }
  }
} finally {
  await mcp.disconnect()
}
```

该命令接受一个或多个文件路径。输入文件和 `outFile` 的路径均相对于命令的工作目录。命令只选取以命名导出或默认导出直接导出的客户端，并且这些客户端必须启用类型生成。命令不会扫描源码目录树、调用工厂函数或检查导出对象的嵌套成员。重复指定同一文件、通过符号链接指向同一文件或多次导出同一客户端时，只处理一次。如果某个文件没有符合条件的客户端，命令会报错。

对于具有相同服务器配置的独立客户端，请使用不同的 ID 和输出路径：

```typescript title="src/mcp/clients.ts"
import { MCPClient } from '@mastra/mcp'

const servers = { weather: { url: new URL(process.env.WEATHER_MCP_URL!) } }
export const first = new MCPClient({
  id: 'first',
  servers,
  typegen: { outFile: 'first.generated.ts' },
})
export const second = new MCPClient({
  id: 'second',
  servers,
  typegen: { outFile: 'second.generated.ts' },
})
```

```bash npm2yarn
npx @mastra/mcp generate ./src/mcp/clients.ts
```

实例缓存仍然生效。构造客户端时，如果显式指定的 ID、服务器配置和 `typegen.outFile` 都相同，就会返回已有对象。如果服务器配置或 `outFile` 不同，则会替换缓存中的实例，避免后续构造客户端时沿用本次未指定的输出文件。

生成过程只列出 Tool 定义，不调用 Tool。发现出错、缺少身份验证、超时、输出路径冲突、输出会覆盖指定的输入文件，或架构完全无法表示（例如存在循环引用、嵌套过深或本地引用无法解析）时，生成会失败。每条错误都会指出涉及的客户端文件、服务器或 Tool。命令会先准备好所有要生成的源码，再替换文件。无论成功还是失败，都会断开所选客户端的连接。发现或预检查失败时，现有输出会保留。单个文件的替换是原子操作，多个文件的替换则各自生效。替换过程中如果出现文件系统故障，先前替换的文件可能已经更新。

没有输出架构的 Tool 使用 `unknown`。字符串格式、长度限制和数值范围等约束在生成的 TypeScript 中仍使用相应的基础类型，具体约束继续由运行时验证。不支持的架构部分（包括条件架构和 `prefixItems` 元组）会放宽为 `unknown`，并发出警告。如果关键字的值不符合规定的结构，相应架构也会放宽为 `unknown` 并发出警告，避免单个不可用的 Tool 阻断其他服务器的类型生成。警告会标明服务器、Tool 和架构中的具体位置。生成器不会获取外部架构引用。本地引用无法解析或存在循环引用时，生成会失败。架构嵌套超过协议规定的 128 层上限时，生成也会失败。架构超过协议规定的 10,000 个节点上限时，会放宽为 `unknown` 并发出警告。生成器对原始 JSON 值设有更宽松的限额，超出该限额的架构或目录也会按同样方式处理。生成器会在复制或转换架构前检查这些限额，避免服务器公布的大型架构卡住命令。

:::note 模块执行和凭证

该命令会执行指定的模块及其导入的模块。请使用可信且不会在导入时启动应用或触发其他启动副作用的模块，并在运行命令前提供凭据。命令不会加载 dotenv 文件，也不会启动交互式身份验证。客户端现有的超时和发现设置仍然有效。

生成器的诊断信息不会包含原始架构、传输错误或凭据。导入的应用、自定义日志处理函数或服务器子进程输出的日志不在此保证范围内。

:::

### `MastraMCPServerDefinition` {/* #mastramcpserverdefinition */}

`servers` 映射中的每台服务器都使用 `MastraMCPServerDefinition` 类型配置。客户端根据提供的参数选择传输方式：

* 提供 `command` 时，使用 Stdio 传输。
* 提供 `url` 时，使用 Streamable HTTP 传输。

客户端支持 MCP `2026-07-28` 版。连接时，客户端查询服务器支持的版本（`server/discover`）。如果服务器尚未升级，客户端会回退到 2026 年以前的 `initialize` 握手，因此两种情况下都可以使用 Tool、资源和提示词。旧版缺少的功能（`resources.subscribe()`、`inputRequests`）会报错，并注明协商出的版本。`onListChanged()` 处理函数在新旧版本中均可使用，因为旧版服务器无需 `subscriptions/listen` 流也会发送列表变更通知。设置 `protocolVersion` 可跳过探测。

## Tool 审批 {/* #tool-approval */}

在服务器定义中设置 `requireToolApproval`，可要求该服务器的 Tool 在执行前获得人工批准。此设置沿用现有的[人工参与审批](/docs/workflows/human-in-the-loop)流程。

### 要求审批所有 Tool {/* #require-approval-for-all-tools */}

将 `requireToolApproval` 设为 `true`，该服务器上的所有 Tool 均须通过审批才能执行：

```typescript
const mcp = new MCPClient({
  servers: {
    github: {
      url: new URL('http://localhost:3000/mcp'),
      requireToolApproval: true,
    },
  },
})
```

### 通过函数动态决定是否审批 {/* #dynamic-approval-with-a-function */}

传入函数可逐次判断调用是否需要审批。函数接收 Tool 名称、模型传入的参数、传入请求所带的上下文，以及服务器声明的 MCP Tool `annotations`（如有）：

```typescript
const mcp = new MCPClient({
  servers: {
    github: {
      url: new URL('http://localhost:3000/mcp'),
      requireToolApproval: ({ toolName, args, requestContext }) => {
        // Read-only tools don't need approval
        if (toolName === 'list_repos') return false
        // Destructive tools with force flag always need approval
        if (toolName === 'delete_repo') return args.force === true
        // Non-admin users need approval for everything else
        return requestContext?.userRole !== 'admin'
      },
    },
  },
})
```

该函数也可以是异步函数。它接收传入请求的 `requestContext`，可用于鉴权或其他按请求执行的逻辑。

### 使用可信服务器的 Tool 注解 {/* #use-tool-annotations-from-a-trusted-server */}

如果信任该 MCP 服务器，可以依据其 [Tool 注解](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#tool-annotations)（`readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint`、`title`）决定是否需要审批：

```typescript
const mcp = new MCPClient({
  servers: {
    github: {
      url: new URL('http://localhost:3000/mcp'),
      requireToolApproval: ({ annotations }) => {
        // Skip approval for tools the server has marked read-only
        if (annotations?.readOnlyHint) return false
        // Always require approval for destructive tools
        if (annotations?.destructiveHint) return true
        return true
      },
    },
  },
})
```

按照 MCP 规范，**除非 Tool 注解来自可信服务器，否则客户端必须将其视为不可信**。注解仅供参考，无法提供安全隔离。恶意或存在缺陷的服务器可能把能写入数据的 Tool 标记为只读。只有对于可信服务器，才可依据注解放宽审批要求。

`listTools()` 和 `listToolsets()` 返回的 Tool 也会在 `tool.mcp.annotations` 中提供这些注解，可在为 Agent 配置 Tool 时查看。

每个 Tool 还带有 `tool.title`，优先取服务器提供的 Tool `title`，其次取 `annotations.title`。两者均未提供时，`tool.title` 为 `undefined`，界面改用 Tool 名称，符合 MCP 的显示名称优先顺序。

## 服务器指令 {/* #server-instructions */}

如果 MCP 服务器在初始化时提供指令，`MCPClient` 会按服务器保存这些指令。将指令转发到 Agent 的系统提示词需要**显式启用**。为服务器设置 `forwardInstructions: true` 后，通过 `listTools()` 或 `listToolsets()` 使用该服务器 Tool 的 Agent 会自动收到这些指令。

指令按服务器名称分组，每台服务器的指令最多保留 `instructionsMaxLength` 个字符。

```typescript
const mcp = new MCPClient({
  servers: {
    db: {
      url: new URL('http://localhost:3000/mcp'),
      forwardInstructions: true,
      instructionsMaxLength: 512,
    },
  },
})

const agent = new Agent({
  id: 'db-agent',
  name: 'DB Agent',
  instructions: 'Help with database changes.',
  model,
  tools: await mcp.listTools(),
})
```

默认省略 `forwardInstructions` 时，客户端仍会缓存指令，可通过 [`getServerInstructions()`](#getserverinstructions) 查看。此时指令不会加入任何 Agent 的系统提示词。

> **安全说明：** 服务器指令会原样加入 Agent 的系统提示词，仅按长度限制截断。恶意或遭入侵的 MCP 服务器可借此注入会被 Agent 当作可信系统指令的内容。仅为可信服务器启用 `forwardInstructions`。建议先用 `getServerInstructions()` 审查第三方服务器的指令，再启用转发。

## 安全 {/* #security */}

### Stdio 服务器的子进程环境 {/* #subprocess-environment-for-stdio-servers */}

Stdio 子进程不会继承父进程的全部环境变量。默认情况下，客户端仅继承 MCP SDK 允许列表中的变量（POSIX：`HOME`、`LOGNAME`、`PATH`、`SHELL`、`TERM`、`USER`；Windows：`APPDATA`、`HOMEDRIVE`、`HOMEPATH`、`LOCALAPPDATA`、`PATH`、`PROCESSOR_ARCHITECTURE`、`SYSTEMDRIVE`、`SYSTEMROOT`、`TEMP`、`USERNAME`、`USERPROFILE`），并与 `env` 中设置的变量合并。API 密钥等敏感变量只有显式传入才会进入子进程环境。

如需更严格的隔离，请设置 `inheritDefaultEnv: false`，使子进程仅接收 `env` 中配置的变量：

```typescript
const mcp = new MCPClient({
  servers: {
    myTool: {
      command: '/usr/local/bin/my-mcp-server',
      inheritDefaultEnv: false,
      env: { MY_TOOL_API_KEY: process.env.MY_TOOL_API_KEY! },
    },
  },
})
```

`env` 中的变量会原样传入子进程，因此应将来源不可信的服务器配置（例如用户提供的配置文件）视为不可信输入。

### 使用 `allowedHosts` 限制出站请求的目标主机 {/* #restricting-outbound-hosts-with-allowedhosts */}

HTTP 服务器的 URL 若来自不可信配置，攻击者可通过控制 URL 诱使客户端访问内部服务，造成服务端请求伪造。为此类服务器设置 `allowedHosts`，可限制客户端访问的主机：

```typescript
const mcp = new MCPClient({
  servers: {
    remote: {
      url: new URL(untrustedConfig.serverUrl),
      allowedHosts: ['api.example.com'],
    },
  },
})
```

主机校验规则如下：

* 使用默认请求机制时，客户端会在请求**发出前**拦截任何发往未获准主机的请求，包括每次重定向产生的请求。客户端自行处理最多 5 次重定向并逐次校验。重定向跨源时，客户端不会转发 `Authorization` 请求头。协议、主机或端口任一项变化都会移除该请求头，与标准 fetch 行为一致。
* 如果提供自定义 `fetch`，客户端仍会在发出请求前检查初始 URL，但要等收到响应后才通过 `response.url` **事后校验**重定向。出站请求可能已经发出。如果最终 URL 指向未获准主机，客户端会丢弃响应。自行构造的 `Response` 若将 `response.url` 留空，则会跳过事后校验。
* 通过 `authProvider` 发出的 OAuth 请求也会接受校验，包括发现授权服务器的元数据、交换令牌和刷新令牌。如果授权服务器与 MCP 服务器不在同一主机上，也要把授权服务器的主机加入 `allowedHosts`。
* 目标主机未获准时，连接会失败并返回明确的错误，重连逻辑不会重试。

`allowedHosts` 仅精确匹配主机名，不支持通配符或 URL 协议校验。如果需要检查协议或设置 IP 地址范围等规则，可提供自定义 `fetch` 实现。客户端发出的每个请求都会调用该实现。

### 将 Tool 响应视为不可信输入 {/* #treat-tool-responses-as-untrusted-input */}

MCP 服务器返回的 Tool 结果会作为模型输入进入 Agent 的上下文。恶意或遭入侵的服务器可能借 Tool 输出进行提示词注入。传输客户端不会清理 Tool 响应。可在 Agent 层使用 Mastra 的[输入和输出处理器](/docs/agents/processors)，在内容送入模型前和模型输出后检查、转换或拦截内容。接入第三方服务器时，请结合使用 `requireToolApproval`，并遵循上文关于 `forwardInstructions` 的安全说明。

## 方法 {/* #methods */}

### `listTools()` {/* #listtools */}

获取所有已配置服务器的 Tool，并在 Tool 名称前加上服务器名称（格式为 `serverName_toolName`），以避免名称冲突。
可将返回值传给 Agent 定义。

结果不包含仅供应用使用的 Tool，即 `_meta.ui.visibility` 中不含 `"model"` 的 Tool。`listToolsets()` 和 `listToolDefinitions()` 也会排除这些 Tool。

服务器名称和 Tool 名称均可包含 `_`，因此不同组合可能生成同一个键。例如，服务器 `local` 的 Tool `x_status` 和服务器 `local_x` 的 Tool `status` 都会生成 `local_x_status`。该键会保留 `servers` 中排在后面的服务器所提供的 Tool，客户端会记录警告并列出两个组合。重命名其中一台服务器即可保留两个 Tool。

```ts
new Agent({ id: 'agent', tools: await mcp.listTools() })
```

### `listToolsWithErrors(options?)` {/* #listtoolswitherrorsoptions */}

获取所有已配置服务器的 Tool，并以服务器名称作为 Tool 名称的前缀。对于连接失败或无法列出 Tool 的服务器，还会逐一返回对应错误。

设置 `perServerTimeoutMs` 可限制发现过程等待每台服务器的时间。按时完成的服务器所提供的 Tool 会保留在 `tools` 中，超时的服务器会列在 `errors` 中。`durations` 以毫秒为单位记录每台服务器的发现耗时。

```typescript
const { tools, errors, errorDetails, durations } = await mcp.listToolsWithErrors({
  perServerTimeoutMs: 3_000,
})

new Agent({ id: 'agent', tools })
console.log(errors, errorDetails, durations)
```

为保持向后兼容，`errors` 仍是字符串映射。`errorDetails` 提供相同的错误消息，并在底层错误提供相关信息时附带可供程序读取的 `httpStatus` 和传输错误 `code` 字段。如果有 HTTP 状态码，旧格式的错误消息也会附加 `(HTTP nnn)` 后缀。

不传入选项时，仅省略 `durations`。该方法始终返回 `tools`、`errors` 和 `errorDetails`。

### `listToolsets()` {/* #listtoolsets */}

返回以服务器名称为键的对象，每个值包含对应服务器的 Tool。Tool 保留原始名称，不加服务器前缀。
可在运行时将返回值传给生成或流式输出方法。

```typescript
const res = await agent.stream(prompt, {
  toolsets: await mcp.listToolsets(),
})
```

Agent 按 Tool 名称合并各组 Tool。如果两台服务器提供同名 Tool，例如 `search`，模型只会收到 `servers` 中排在后面的服务器所提供的 Tool，Agent 会记录警告。要保留两个 Tool，可将 `listTools()` 返回的带前缀 Tool 作为一组传入：

```typescript
const res = await agent.stream(prompt, {
  toolsets: { mcp: await mcp.listTools() }, // docs_search, tickets_search
})
```

### `listToolsetsWithErrors(options?)` {/* #listtoolsetswitherrorsoptions */}

返回按服务器名称分组的 Tool 集合，以及各服务器的发现错误。设置 `perServerTimeoutMs` 可为每台服务器单独计时，并在 `durations` 中以毫秒为单位记录各服务器的发现耗时。

```typescript
const { toolsets, errors, errorDetails, durations } = await mcp.listToolsetsWithErrors({
  perServerTimeoutMs: 3_000,
})

const res = await agent.stream(prompt, { toolsets })
console.log(errors, errorDetails, durations)
```

不传入选项时，仅省略 `durations`。该方法始终返回 `toolsets`、`errors` 和 `errorDetails`。

#### 逐台处理服务器的发现结果 {/* #report-each-server-as-it-settles */}

返回的 Promise 要等所有服务器的发现过程结束才会兑现，因此一台慢服务器就可能拖延整体结果。传入 `onServerSettled` 可在任一服务器发现成功、失败或超时后立即处理结果。回调接收服务器名称、`value`（以该服务器的原始 Tool 名称为键的 Tool 集合）或 `error`，以及以毫秒计的 `duration`。`listToolsWithErrors()` 和 `listToolDefinitionsWithErrors()` 也支持此选项。

```typescript
await mcp.listToolsetsWithErrors({
  perServerTimeoutMs: 60_000,
  onServerSettled: (serverName, { value, error, duration }) => {
    if (error) {
      console.error(`${serverName} failed after ${duration}ms: ${error.message}`)
    } else {
      console.log(`${serverName} ready with ${Object.keys(value).length} tools`)
    }
  },
})
```

回调抛出的错误会记入日志，发现过程会继续。`async` 回调返回的 Promise 若被拒绝，也会记入日志并得到处理，不会产生未处理的拒绝。

#### 仅对指定服务器执行发现 {/* #discover-only-some-servers */}

传入 `serverNames` 可仅对指定服务器执行发现，例如只重试超时的服务器，无需重新启动其余服务器。未配置的服务器名称会被忽略。`listToolsWithErrors()` 和 `listToolDefinitionsWithErrors()` 也支持此选项。

```typescript
const { errorDetails } = await mcp.listToolsetsWithErrors({ perServerTimeoutMs: 3_000 })

// Only servers that timed out are worth retrying. A server that failed for
// another reason (bad config, auth refused) will just fail again.
const timedOut = Object.entries(errorDetails)
  .filter(([, details]) => details.code === MCP_DISCOVERY_TIMEOUT_CODE)
  .map(([serverName]) => serverName)

const retry = await mcp.listToolsetsWithErrors({ serverNames: timedOut })
```

`MCP_DISCOVERY_TIMEOUT_CODE` 由 `@mastra/mcp` 导出，用于标识 `perServerTimeoutMs` 触发的错误，以区分服务器响应超时和其他故障。

### `listToolDefinitions()` {/* #listtooldefinitions */}

以普通的可序列化定义返回各服务器的 Tool，按服务器名称分组，并以服务器提供的原始 Tool 名称为键，不采用 `listTools()` 使用的 `serverName_toolName` 格式。

与 `listTools()` 一样，该方法会排除仅供应用使用的 Tool，即 `_meta.ui.visibility` 中不含 `"model"` 的 Tool。MCP 应用通过宿主调用这些 Tool，因此它们不会提供给 Agent。

此方法与 `listTools()` 的区别在于，结果不含函数或对运行中客户端的引用，因此可通过 `JSON.stringify` 序列化，缓存到 Redis 或数据库，也可保存为构建产物。每条定义包含 MCP `tools/list` 响应中的名称、标题、描述、输入模式、输出模式、注解和 `_meta`，以及发现时记录的服务器名称、版本和指令。

```typescript
const definitions = await mcp.listToolDefinitions()

await cache.set('mcp-tools', JSON.stringify(definitions))
```

### `listToolDefinitionsWithErrors(options?)` {/* #listtooldefinitionswitherrorsoptions */}

在 `listToolDefinitions()` 的返回结果基础上，此方法还会为每台连接失败的服务器返回对应错误。缓存目录时可使用此方法，避免因服务器在发现时不可用而保存缺项的清单。

设置 `perServerTimeoutMs` 可分别限制每台服务器的发现时间。传入选项后，`durations` 会以毫秒为单位记录每台服务器的发现耗时。

```typescript
const { definitions, errors, errorDetails, durations } = await mcp.listToolDefinitionsWithErrors({
  perServerTimeoutMs: 3_000,
})

if (Object.keys(errors).length === 0) {
  await cache.set('mcp-tools', JSON.stringify(definitions))
}

console.log(errorDetails, durations)
```

不传入选项时，仅省略 `durations`。该方法始终返回 `definitions`、`errors` 和 `errorDetails`。

### `toolFromDefinition()` {/* #toolfromdefinition */}

从缓存的定义重建单个可执行的 Tool。重建时不建立连接，客户端等到首次执行该 Tool 时才连接。

返回的 Tool 与 `listTools()` 返回的 Tool 行为一致，包括严格模式的元数据、审批策略、结构化内容处理、Tool 错误处理和重连行为。两种方式都会按服务器声明的 `outputSchema` 校验成功调用返回的结构化结果。校验失败会使 Tool 调用被拒绝。MCP 错误结果会跳过输出校验。

未声明 `$schema` 的 MCP 模式使用 JSON Schema 2020-12。支持本地 `$ref` 和 `$defs` 引用、组合关键字及布尔子模式。为限制校验不可信 Tool 目录时的开销，输入和输出模式最多允许 128 层嵌套子模式和 10,000 个子模式节点。

`structuredContent` 可以是任意 JSON 值，包括字符串、数字、布尔值和 `null`。对象和数组结果还会通过不可枚举的 Mastra 元数据属性提供 MCP 内容和 `_meta` 封装。标量及 `null` 无法附带这些属性，因此直接原样返回。

```typescript
const definitions = JSON.parse(await cache.get('mcp-tools'))

const tool = await mcp.toolFromDefinition({
  serverName: 'weather',
  definition: definitions.weather.getForecast,
})
```

### `toolsFromDefinitions()` {/* #toolsfromdefinitions */}

无需连接服务器，即可从整个缓存目录重建带服务器前缀的 Tool 映射。它与 `listTools()` 生成相同的 `serverName_toolName` 键，可在冷启动时恢复 Agent 的 Tool 映射。只有实际调用某台服务器上的 Tool 时，客户端才会连接该服务器。

如果缓存目录中仍有客户端已移除配置的服务器，重建时会跳过这些服务器，继续处理其余条目。

```typescript
const definitions = JSON.parse(await cache.get('mcp-tools'))

new Agent({ id: 'agent', tools: await mcp.toolsFromDefinitions({ definitions }) })
```

### `getServerInstructions()` {/* #getserverinstructions */}

返回各已配置 MCP 服务器当前已知的指令。尚未连接或未提供指令的服务器对应值为 `undefined`。

```typescript oxfmt:false
getServerInstructions(): Record<string, string | undefined>
```

示例：

```typescript
await mcp.listTools()

const instructionsByServer = mcp.getServerInstructions()
console.log(instructionsByServer.db)
```

### `getServerInfo()` {/* #getserverinfo */}

返回各已配置 MCP 服务器在连接时提供的标识信息，即 `server/discover` 结果中的 `serverInfo`，旧版服务器则从 `initialize` 握手中获取。信息包括 `name` 和 `version`，以及服务器提供的 `title`、`description`、`websiteUrl` 和 `icons`（如有）。如果服务器尚未连接，或按 `2026-07-28` 版协议连接时未提供该版本允许省略的标识信息，对应值为 `undefined`。请勿用此方法判断服务器是否已连接。这些值来自远程服务器，未经校验，因此应将图标和网站 URL 视为不可信。

```typescript oxfmt:false
getServerInfo(): Record<string, MCPServerImplementation | undefined>
```

示例：

```typescript
await mcp.listTools()

const info = mcp.getServerInfo()
console.log(info.myServer?.title, info.myServer?.version)
```

### `authenticate()` {/* #authenticate */}

如果服务器的 `MCPOAuthClientProvider` 使用回环重定向 URL，此方法会运行交互式 OAuth 授权码流程。本地回调服务器将授权 URL 传给 Provider 的 `onRedirectToAuthorization` 回调，并等待浏览器返回授权码。随后用授权码交换令牌并重新连接。参见[交互式浏览器身份验证](#interactive-browser-authentication)。

可选参数 `timeoutMs` 指定等待浏览器返回授权码的最长时间，默认为 5 分钟。超时后调用会被拒绝。

```typescript oxfmt:false
async authenticate(serverName: string, options?: { timeoutMs?: number }): Promise<void>
```

### `getServerAuthState()` {/* #getserverauthstate */}

返回已配置服务器的 OAuth 授权状态。连接因授权错误被拒绝时为 `'needs-auth'`，服务器接受 Provider 的凭据后为 `'authorized'`。未配置 `authProvider` 或尚未尝试连接时为 `undefined`。

```typescript oxfmt:false
getServerAuthState(serverName: string): 'needs-auth' | 'authorized' | undefined
```

### `cancelAuthentication()` {/* #cancelauthentication */}

取消指定服务器正在进行的 `authenticate()` 流程，避免用户放弃浏览器授权后客户端一直等待。此操作会中止流程，包括回调服务器绑定端口前的准备阶段，并关闭正在监听的本地回调服务器（如有）。等待中的 `authenticate()` 调用会被拒绝。成功取消流程时返回 `true`，没有进行中的流程时返回 `false`。

取消后 `getServerAuthState()` 的返回值取决于流程进度。如果在收到 `401` 拒绝后取消，状态仍为 `'needs-auth'`，可以立即重试。如果在准备阶段取消且尚未尝试连接，状态保持原值，通常为 `undefined`。

```typescript oxfmt:false
async cancelAuthentication(serverName: string): Promise<boolean>
```

### `events` 属性（实验性） {/* #events-property-experimental */}

通过 `events` 属性，可以列出并订阅实现了 [MCP 事件扩展（SEP-3415）](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415)的服务器事件。借助它可以响应推送到仓库等服务器端事件，无需轮询 Tool。每次事件至少投递一次。重新连接或恢复订阅后，服务器可能重复发送同一次事件，客户端会根据 `eventId` 在 `dedupWindow` 保留的近期 ID 中查找并丢弃重复事件。

完整操作示例见 [MCP 事件](/docs/connections/mcp#mcp-events)。

:::warning
SEP-3415 仍处于草案阶段。此 API 可能在任何版本中变更。
:::

```typescript
const events = await mcpClient.events.list('github')

const subscription = await mcpClient.events.subscribe(
  'github',
  'repo.push',
  { repo: 'mastra-ai/mastra' },
  { cursor: await loadCursor() },
)

for await (const event of subscription) {
  await handlePush(event.data)
  // Safe to persist after each handled occurrence
  await saveCursor(subscription.cursor)
}
```

客户端不会向未声明支持 `io.modelcontextprotocol/events` 扩展的服务器发送 `events/*` 请求。`list()` 返回的 Promise 会以 ID 为 `MCP_CLIENT_LIST_EVENTS_FAILED` 的 `MastraError` 拒绝，`subscribe()` 则会以 `MCP_CLIENT_SUBSCRIBE_EVENT_FAILED` 拒绝。两种情况下，`error.cause.id` 均为 `MCP_EVENTS_NOT_SUPPORTED`。`list()` 和 `subscribe()` 因其他原因失败时，也分别使用这两个错误 ID，具体原因见 `error.cause`。

#### `events.list(serverName: string)` {/* #eventslistservername-string */}

逐页获取并返回服务器提供的所有事件类型。每个事件描述符都包含 `name`、可选的 `description`、服务器支持的 `delivery` 模式，以及可选的 `inputSchema` 和 `payloadSchema`。

```typescript oxfmt:false
async list(serverName: string): Promise<MCPEventDescriptor[]>
```

目前，服务器的事件列表变更时，客户端不会收到通知。再次调用 `list()` 即可获取新增的事件类型。

#### `events.subscribe(serverName, eventName, args?, options?)` {/* #eventssubscribeservername-eventname-args-options */}

发起订阅，返回的 Promise 在服务器确认后兑现。遇到未知事件、参数无效或无权订阅等错误时，Promise 会被拒绝。新订阅从服务器接受订阅时开始。若要接收之前发生的事件，请用 `options.cursor` 从更早的位置恢复订阅。使用 webhook 投递时，Promise 可能在服务器接受订阅之后才兑现。对于尚无法路由的投递，客户端会返回 `503`，服务器随后会重试。

```typescript oxfmt:false
async subscribe(
  serverName: string,
  eventName: string,
  args?: Record<string, unknown>,
  options?: MCPEventSubscribeOptions,
```

返回的 `MCPEventSubscription` 是一个异步可迭代对象，逐条提供事件（`eventId`、`name`、`timestamp`、`data`），并包含以下成员：

* `cursor`：可以安全持久化的最新位置，不会越过循环尚未收到的事件。该事件类型不支持重放时，值为 `null`。
* `truncated`：如果服务器报告循环刚收到的事件之前存在缺口，例如保存的游标早于服务器的保留窗口，则为 `true`。请在循环内读取此属性。缺口后的第一条事件对应 `true`，之后的事件对应 `false`。
* `mode`：当前投递模式，取值为 `'webhook'`、`'push'` 或 `'poll'`。
* `deliveryStatus`：仅适用于 Webhook 模式。包含服务器最近一次报告的 Webhook URL 投递状态（`active`、`lastDeliveryAt`、`lastError`、`failedSince`），每次续订时更新。
* `onError(handler)`：接收可恢复的错误，例如事件流中断而客户端正在重新打开它。返回用于移除处理函数的函数。
* `cancel()`：取消订阅并结束迭代。提前退出 `for await` 循环也会取消订阅。

订阅无法继续时，迭代器直接抛出 `MastraError`，不做额外包装。服务器返回不可重试的错误时，错误码为 `MCP_EVENTS_SUBSCRIPTION_FAILED`。服务器结束推送或 Webhook 订阅时，错误码为 `MCP_EVENTS_SUBSCRIPTION_TERMINATED`。连续失败 `retry.maxAttempts` 次时，错误码为 `MCP_EVENTS_RETRIES_EXHAUSTED`。重连后，客户端会重新打开中断的事件流，并从上一个游标恢复轮询。通过 `reconnectServer()` 重连时也是如此。`disconnect()` 会结束所有订阅。

#### `events.handleWebhook(request: Request)` {/* #eventshandlewebhookrequest-request */}

处理一次 Webhook 投递并返回应发给服务器的响应。请将此处理函数挂载到 `webhook.url` 指向的路由。

```typescript oxfmt:false
async handleWebhook(request: Request): Promise<Response>
```

此方法先根据原始请求体验证 Standard Webhooks 签名，再解析请求体。它会响应服务器的验证握手，并根据 `X-MCP-Subscription-Id` 请求头将事件分发到对应的订阅。响应状态码如下：

* `200`：事件已交给对应的订阅。对于验证请求，响应会原样返回质询值。
* `401`：签名无效，或时间戳距今超过 5 分钟。
* `503`：客户端尚未识别该订阅 ID。服务器会重试，以处理在订阅响应之前到达的投递。
* `400`：请求已签名，但请求体格式无效。对于 `POST` 以外的请求方法，返回 `405`。
* `413`：请求体超过 1 MiB。其他检查开始前，最多只读取此上限允许的数据量。
* `404`：客户端未配置 `webhook`。

#### Webhook 投递 {/* #webhook-delivery */}

配置 `webhook` 后，客户端通过 `events/subscribe` 注册每个订阅，服务器向指定 URL 发送 POST 请求来投递事件。服务器必须验证客户端身份，且该 URL 必须可通过 `https` 从公网访问。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { registerApiRoute } from '@mastra/core/server'
import { MCPClient } from '@mastra/mcp'

export const mcpClient = new MCPClient({
  servers: {
    github: {
      url: new URL('https://mcp.example.com/mcp'),
      requestInit: { headers: { Authorization: `Bearer ${process.env.GITHUB_MCP_TOKEN}` } },
    },
  },
  webhook: { url: 'https://agent.example.com/mcp/webhook' },
})

export const mastra = new Mastra({
  server: {
    apiRoutes: [
      registerApiRoute('/mcp/webhook', {
```

客户端会在每个订阅到期前携带最新游标再次调用 `events/subscribe`，以续订该订阅。如果服务器在 `deliveryStatus` 中报告投递失败，例如接收端点响应超时，`onError` 会收到 `MCP_EVENTS_WEBHOOK_DELIVERY_FAILING`，其错误详情包含 `lastError`。每次 Webhook 投递中的 `cursor` 只涵盖接收端点已确认的事件，所以从保存的游标恢复时，最后处理的事件可能再次送达。下一次续订会恢复已暂停的订阅。`cancel()` 会发送 `events/unsubscribe`。

Webhook 状态保存在当前进程中。接收路由必须与发起订阅的 `MCPClient` 在同一进程中运行。

Webhook 投递要求客户端通过经过身份验证的 HTTP 连接访问服务器，因为服务器会将每个 Webhook 订阅绑定到调用方。通过 stdio 或未经身份验证的 HTTP 连接发起的 `events/subscribe` 会被服务器拒绝。达到 Webhook 订阅数量上限后，服务器也会拒绝新订阅（`-32025`）。未强制指定投递模式的订阅会回退到 `push` 或 `poll`，首个 `onError` 处理函数会收到 `MCP_EVENTS_WEBHOOK_UNAVAILABLE`，其错误详情包含拒绝码 `code` 和回退模式 `fallback`。若强制指定了 `delivery: 'webhook'`，订阅请求会失败。

同一服务器上，事件名称和参数相同的订阅共享一个服务器端 Webhook 订阅。各订阅通过各自的迭代器接收每一条事件。客户端仅在最后一个订阅取消时发送 `events/unsubscribe`。

### Agent 和 Workflow 中的事件（实验性） {/* #events-in-agents-and-workflows-experimental */}

`MCPEventsSignalProvider` 将 MCP 服务器事件以通知形式发送给 Agent 的线程。将它添加到 Agent 的 `signals`，然后为线程订阅事件。Agent 需要通知存储域，`InMemoryStore` 和标准存储适配器均提供此功能。

SEP-3415 仍处于草案阶段。此 API 可能在任何版本中变更。
:::

```typescript title="src/mastra/agents/repo-agent.ts"
import { Agent } from '@mastra/core/agent'
```

Provider 提供以下方法：

* `subscribeThread(thread, { server, event, args? })`：为线程订阅事件，从已保存的游标恢复，并在 MCP 订阅得到确认后完成。如果服务器拒绝请求，线程不会订阅，Promise 也会被拒绝。线程的订阅关系仅保存在内存中。重启后，请为每个仍需接收事件的线程再次调用 `subscribeThread()`。
* `unsubscribeThread(thread, { server, event, args? })`：如果线程原先已订阅，则返回的 Promise 以 `true` 完成。最后一个线程退订时，会取消 MCP 订阅并删除已保存的游标。

### `tasks` 属性（实验性） {/* #tasks-property-experimental */}

有些 Tool 的执行时间超过单个 HTTP 请求能保持打开的时长。实现了 [MCP Tasks 扩展（SEP-2663）](https://modelcontextprotocol.github.io/ext-tasks/specification/2026-07-28/tasks.html) 的服务器可以用任务响应这类调用，客户端随后再获取结果。要接收任务，请在服务器配置中设置 `tasks`：

```typescript
const mcpClient = new MCPClient({
  servers: {
    reports: {
      url: new URL('https://reports.example.com/mcp'),
      tasks: { maxWaitMs: 30 * 60_000 },
      inputRequests: async ({ params }) => askUser(params),
    },
  },
})
```

:::警告
此 API 可能在任何版本中变更。
:::

设置 `tasks` 后，客户端会告知服务器自己可以接收任务。服务器针对每次调用决定是直接响应，还是返回任务。未设置 `tasks` 时，客户端不会收到任务，Tool 调用行为保持不变。

Tool 调用返回任务时，Tool 的调用接口保持不变，客户端按以下方式处理任务：

* 客户端按服务器建议的间隔轮询任务，直到任务完成，然后返回 Tool 的结果。
* 如果任务需要输入，客户端通过 `inputRequests` 为每个请求键获取一次答复，用 `tasks/update` 提交答复，并继续轮询同一个任务。客户端不会再次发送 `tools/call`。未配置处理函数时，Agent 或 Workflow 中的 Tool 调用会挂起，等待用户答复（见[在 Agent 聊天中响应任务的输入请求](#answering-task-input-from-the-agent-chat)）。直接调用 `tool.execute()` 会以 `MCP_CLIENT_TOOL_TASK_INPUT_UNHANDLED` 失败，任务会留在服务器上，直到其 TTL 到期。
* 中止 Tool 调用时会发送 `tasks/cancel`。达到 `maxWaitMs` 时也会发送该请求，并以 `MCP_CLIENT_TOOL_TASK_TIMEOUT` 结束调用。即使轮询或输入处理函数仍在运行，这两种情况也会立即结束调用，并丢弃此后返回的响应或答复。
* 客户端轮询期间若发生断开连接操作，调用会以 `MCP_CLIENT_TOOL_TASK_POLL_FAILED` 失败，客户端不会重新连接。
* 如果轮询期间服务器不可达，例如正在重启或部署，客户端会重新连接并继续轮询，等待间隔逐步增加到最多 30 秒。连接被拒绝或代理返回 HTTP 502、503 或 504，均视为服务器不可达。如果 5 分钟内没有响应，或者先达到 `maxWaitMs` 或任务的 TTL，调用会以 `MCP_CLIENT_TOOL_TASK_POLL_FAILED` 失败。任务仍可能在服务器上完成。TTL 从任务的 `createdAt` 开始计算。如果客户端无法读取该时间戳，则从开始等待时计算。
* Tool 调用的 span 带有 `mcpTaskKey` 元数据，其值为任务 ID 的 SHA-256 哈希。Mastra 服务器会用相同的键标记该任务的 span，以便关联两端的记录，同时避免将任务 ID 写入任一端的 Trace。
* 已完成任务中的 Tool 错误与 Tool 直接返回的错误一样，按 `onToolError` 处理。如果服务器取消任务，调用会以 `MCP_CLIENT_TOOL_TASK_CANCELLED` 失败。如果服务器将任务标记为 `failed`，调用会以 `MCP_CLIENT_TOOL_TASK_FAILED` 失败。
* 已返回任务的调用不会重试，因为重试会创建第二个任务。
* 调用转为任务时，以及任务状态每次变化时，Tool 都会向输出流写入一条 `MCPTaskProgress` 记录（`{ type: 'mcp-task', taskId, status, createdAt, serverName }`）。Studio 的 Tool 调用卡片据此显示运行中任务的状态、已用时间和 MCP 任务 ID。Tool 输出不会随线程保存，重新加载后卡片只显示结果。

Agent 启用[后台任务](/docs/harness/background-tasks)后，来自已配置 `tasks` 的服务器的 Tool 会作为延后执行的后台任务运行，且不会重试。远程任务运行期间，Agent 可以继续工作。取消后台任务也会取消远程任务。可以通过 Agent 的 `backgroundTasks.tools` 按 Tool 覆盖此行为。

#### 在 Agent 聊天中响应任务的输入请求 {/* #answering-task-input-from-the-agent-chat */}

如果任务需要输入、未配置 `inputRequests` 处理函数，并且 Tool 在 Agent 或 Workflow 中运行，该 Tool 调用会像调用了 `suspend()` 一样挂起。远程任务会在服务器上保持打开。挂起载荷（`MCPInputRequestSuspendPayload`）包含仍待答复的请求：

```typescript
const payload: MCPInputRequestSuspendPayload = {
  type: 'mcp-input-request',
  serverName: 'reports',
  toolName: 'approve_and_send',
  taskId: 'Zx81…', // the MCP task the answers go to
  createdAt: '2026-10-30T10:00:00.000Z', // when the task was created
  requestedAt: '2026-10-30T10:00:04.000Z', // when the call suspended; new each time the task asks again
  requests: {
    approve: {
      method: 'elicitation/create',
      params: {
        mode: 'form',
        message: 'Send it?',
        requestedSchema: {
          type: 'object',
          properties: { ok: { type: 'boolean' } },
          required: ['ok'],
        },
      },
    },
  },
}
```

为每个请求键提供一条答复（`MCPInputRequestResumeData`），即可恢复 Tool 调用。例如，前台调用可通过 `agent.resumeStream()` 恢复，延后执行的后台任务可通过 `backgroundTaskManager.resume()` 恢复：

```typescript
await agent.resumeStream(
  { inputResponses: { approve: { action: 'accept', content: { ok: true } } } },
  { runId, toolCallId },
)
```

恢复时，客户端使用 `tasks/update` 将答复提交给同一个任务，并继续轮询该任务，不会再次发送 `tools/call`。如果服务器再次请求输入，调用会再次挂起，并附带新的请求。如果任务已在此期间结束，调用会返回相应的任务错误，例如 `MCP_CLIENT_TOOL_TASK_CANCELLED`。如果服务器已找不到该任务，则返回 `MCP_CLIENT_TOOL_TASK_POLL_FAILED`。如果恢复数据不符合 `{ inputResponses: { [key]: { action: 'accept' | 'decline' | 'cancel', content? } } }` 格式，或有请求未获答复，调用会直接以 `MCP_CLIENT_TOOL_TASK_RESUME_INVALID` 失败，不会联系服务器。

已配置的 `inputRequests` 处理函数优先执行，此时调用不会挂起。

载荷包含可用于访问任务的 MCP 任务 ID。该 ID 会随挂起的 Tool 调用一同保存，请按照处理其他线程数据的方式处理它。

#### `tasks.get(serverName: string, taskId: string)` {/* #tasksgetservername-string-taskid-string */}

返回任务的当前状态（`MCPDetailedTask`）。状态为 `completed` 时包含 `result`，状态为 `input_required` 时包含 `inputRequests`。调用失败时返回 `MCP_CLIENT_GET_TASK_FAILED`。如果任务未知或由其他调用方创建，`error.cause.code` 为 `-32602`。

#### `tasks.update(serverName: string, taskId: string, inputResponses: MCPTaskInputResponses)` {/* #tasksupdateservername-string-taskid-string-inputresponses-mcptaskinputresponses */}

为处于 `input_required` 状态的任务提交 `inputRequests` 的答复，答复使用与请求相同的键。服务器会忽略未请求或已经答复的键。调用失败时返回 `MCP_CLIENT_UPDATE_TASK_FAILED`。

#### `tasks.cancel(serverName: string, taskId: string)` {/* #taskscancelservername-string-taskid-string */}

请求服务器停止任务。任务仍有可能在服务器上完成。调用失败时返回 `MCP_CLIENT_CANCEL_TASK_FAILED`。

## 回答输入请求 {/* #answering-input-requests */}

服务器上的 Tool、资源或提示需要用户提供信息时，会以 `input_required` 结果结束调用。该结果包含一个或多个内嵌请求，每个请求都有一个由服务器指定的 `key`，并附带一个表单（`requestedSchema`）或用户必须访问的 URL。要答复这些请求，请在服务器定义中配置 `inputRequests`。客户端会为每个内嵌请求调用一次处理函数，携带答复重试原始调用，并以最终结果完成 Tool 调用。未配置处理函数时，`input_required` 结果会作为错误返回。

```typescript
import { MCPClient } from '@mastra/mcp'

const mcpClient = new MCPClient({
  servers: {
    interactiveServer: {
      url: new URL('http://localhost:3000/mcp'),
      inputRequests: async ({ key, params, signal }) => {
        if (params.mode === 'url') {
          return { action: 'decline' }
        }
        const content = await collectUserInput(params.message, params.requestedSchema, { signal })
        return { action: 'accept', content }
      },
    },
  },
})
```

### `MCPInputRequest` {/* #mcpinputrequest */}

处理函数接收以下字段：

* `key`：由服务器指定，用于关联答复。同一轮收到多个请求时，请将此键传给用户界面。
* `params`：请求参数。表单模式包含 `message` 和 `requestedSchema`，其中 `requestedSchema` 是一个扁平的 JSON Schema 对象，各字段均为基本类型。URL 模式包含 `message` 和 `url`。
* `signal`：发起该请求的调用被取消或超时时，此信号会触发中止。

配置处理函数后，客户端会向服务器声明支持表单模式。要同时接受 URL 模式的请求，请在同一服务器定义中扩展 `capabilities.elicitation` 的配置。

### 响应类型 {/* #response-types */}

返回一个 `ElicitResult`：

* **接受**：用户提供数据并确认提交。`content` 必须符合 `requestedSchema`。

  ```typescript
  return {
    action: 'accept',
    content: { name: 'John Doe', email: 'john@example.com' },
  }
  ```

* **拒绝**：用户明确拒绝提供所请求的信息。

  ```typescript
  return { action: 'decline' }
  ```

* **取消**：用户关闭了该请求。
  ```typescript
  return { action: 'cancel' }
  ```

用户拒绝或取消请求时，Tool 调用会以错误结束。服务器收到用户确认提交的答复后仍可再次请求输入，因此一次 Tool 调用可能多次执行处理函数。

### 按 Schema 收集输入 {/* #schema-based-input-collection */}

遍历 `requestedSchema`，逐个提示用户填写字段：

```typescript
inputRequests: async ({ params }) => {
  if (params.mode === 'url') return { action: 'decline' }

  const { properties, required = [] } = params.requestedSchema
  const content: Record<string, string | number | boolean> = {}

  for (const [fieldName, fieldSchema] of Object.entries(properties)) {
    const value = await promptUser({
      name: fieldName,
      title: fieldSchema.title,
      description: fieldSchema.description,
      required: required.includes(fieldName),
    })

    if (value !== null) {
      content[fieldName] = value
    }
  }

  return { action: 'accept', content }
}
```

### 最佳实践 {/* #best-practices */}

* **预先配置处理函数**：在服务器定义中配置处理函数，确保请求用户输入的 Tool 始终有处理函数可用。
* **验证输入**：检查是否提供了必填字段。
* **尊重用户选择**：妥善处理用户拒绝或取消的情况。
* **清晰的用户界面**：说明需要哪些信息，以及为什么需要这些信息。
* **安全**：切勿自动接受索取敏感信息的请求。将 URL 模式请求中的链接视为指向不受信任的网站。

## OAuth 身份验证 {/* #oauth-authentication */}

如需连接遵循 [MCP 2026-07-28 授权规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)且要求 OAuth 身份验证的 MCP 服务器，请使用 `MCPOAuthClientProvider`。该 Provider 不会在运行时注册客户端。请通过 `clientInformation` 提供已在授权服务器上预先注册的客户端信息，或通过 `clientMetadataUrl` 提供[客户端 ID 元数据文档](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration#client-id-metadata-documents)的 URL：

```typescript
import { MCPClient, MCPOAuthClientProvider } from '@mastra/mcp'

// Create an OAuth provider
const clientMetadataUrl = 'https://app.example.com/oauth/client-metadata.json'

const oauthProvider = new MCPOAuthClientProvider({
  redirectUrl: 'http://localhost:3000/oauth/callback',
  clientMetadataUrl,
  clientMetadata: {
    client_id: clientMetadataUrl,
    redirect_uris: ['http://localhost:3000/oauth/callback'],
    client_name: 'My MCP Client',
    grant_types: ['authorization_code', 'refresh_token'],
    response_types: ['code'],
  },
  onRedirectToAuthorization: url => {
    // Handle authorization redirect (open browser, redirect response, etc.)
    console.log(`Please visit: ${url}`)
  },
})

// Use the provider with MCPClient
const client = new MCPClient({
  servers: {
    protectedServer: {
      url: new URL('https://mcp.example.com/mcp'),
      authProvider: oauthProvider,
    },
  },
})
```

通过 `clientMetadataUrl` 提供的文档必须包含相同的 `client_id`、`client_name` 和 `redirect_uris`。如果使用环回回调，请在托管的文档中列出 `getCallbackUrlCandidates()` 返回的所有备用 URL。Provider 会将文档 URL 作为 `client_id` 发送，且不会调用注册端点。如果授权服务器既不接受元数据文档，也不接受预先注册的 `clientInformation`，授权流程会明确报错。客户端身份只能配置一种，同时设置 `clientInformation` 和 `clientMetadataUrl` 会使构造函数抛出错误。

`MCPOAuthClientProvider` 保存的令牌与授权服务器经验证的 `issuer` 绑定。Provider 会持久化发现状态，确保只向发出重定向的服务器发送授权码交换请求。环回回调也会将 RFC 9207 定义的 `iss` 参数转发给 SDK。如果该参数与预期值不符，SDK 会在交换授权码之前拒绝请求。

为每台服务器创建独立的 `MCPOAuthClientProvider` 实例。授权期间，Provider 会保存对应服务器的会话和凭据状态。如果多台服务器共用同一个实例，各自的授权流程可能覆盖彼此的状态。配置多台受保护的服务器时，请分别创建 Provider。若这些 Provider 共用同一个持久化存储后端，请为每个 Provider 分配独立的 `OAuthStorage` 命名空间，因为存储变更的顺序只在单个 Provider 实例内协调。

### 交互式浏览器身份验证 {/* #interactive-browser-authentication */}

服务器因需要授权而拒绝连接时，客户端会记录 `'needs-auth'` 状态，等待进一步处理。调用 `authenticate()` 可完成授权流程。它会在 Provider 的环回重定向 URL 上启动一次性回调服务器。如果端口已被占用，就按顺序尝试后续端口。随后，SDK 会执行发现流程，并使用已配置的客户端身份。`onRedirectToAuthorization` 会收到授权 URL，应用可在用户的浏览器中打开该 URL。浏览器返回授权码后，流程会完成令牌交换：

```typescript
import { MCPClient, MCPOAuthClientProvider } from '@mastra/mcp'

const clientMetadataUrl = 'https://app.example.com/oauth/client-metadata.json'

const oauthProvider = new MCPOAuthClientProvider({
  redirectUrl: 'http://127.0.0.1:5533/oauth/callback',
  clientMetadataUrl,
  clientMetadata: {
    client_id: clientMetadataUrl,
    redirect_uris: ['http://127.0.0.1:5533/oauth/callback'],
    client_name: 'My MCP Client',
    grant_types: ['authorization_code', 'refresh_token'],
    response_types: ['code'],
  },
  onRedirectToAuthorization: url => {
    // Open the user's browser at the consent page
    console.log(`Please visit: ${url}`)
  },
})

const mcp = new MCPClient({
  servers: {
    protectedServer: {
      url: new URL('https://mcp.example.com/mcp'),
      authProvider: oauthProvider,
    },
  },
})

try {
  await mcp.listTools()
} catch {
  if (mcp.getServerAuthState('protectedServer') === 'needs-auth') {
    await mcp.authenticate('protectedServer')
  }
}
```

针对同一台服务器并发调用 `authenticate()` 时，各调用会加入正在进行的授权流程。不同服务器分别进行身份验证。如果已保存有效令牌，调用会直接重新连接，无需打开浏览器。

自行控制授权流程的应用可以通过导出的辅助函数 `createOAuthCallbackServer` 获取授权码。该函数会启动一次性环回服务器，先验证 OAuth 的 `state` 参数，再以授权码兑现 Promise。该服务器使用明文 HTTP，因此只应处理本地环回重定向。使用 HTTPS 重定向 URL 的 Web 应用必须自行托管回调端点，并直接控制 Provider：

```typescript
import { createOAuthCallbackServer, getCallbackUrlCandidates } from '@mastra/mcp'

// getCallbackUrlCandidates() lists every URL the helper may bind, so list all
// of them as redirect_uris in your pre-registration or metadata document.
const redirectUris = getCallbackUrlCandidates('http://127.0.0.1:5533/oauth/callback').map(url =>
  url.toString(),
)

const server = await createOAuthCallbackServer({
  redirectUrl: 'http://127.0.0.1:5533/oauth/callback',
  state: expectedState,
})

// server.url reflects the port actually bound — use it as the redirect_uri.
try {
  const { code, iss } = await server.waitForCode()
  // Exchange the code here, passing `iss` so the SDK validates the issuer.
} finally {
  await server.close()
}
```

### 自定义令牌存储 {/* #custom-token-storage */}

如需跨会话持久保存令牌，请实现 `OAuthStorage` 接口。Provider 使用字符串键保存令牌（最新的一组令牌，以及每个授权服务器签发者各一条记录）、发现状态和 PKCE 验证器。后端只需提供键值存储接口：

```typescript
import { MCPOAuthClientProvider, OAuthStorage } from '@mastra/mcp'

class DatabaseOAuthStorage implements OAuthStorage {
  constructor(
    private db: Database,
    private userId: string,
  ) {}

  async set(key: string, value: string): Promise<void> {
    await this.db.query(
      'INSERT INTO oauth_tokens (user_id, key, value) VALUES (?, ?, ?) ON CONFLICT DO UPDATE SET value = ?',
      [this.userId, key, value, value],
    )
  }

  async get(key: string): Promise<string | undefined> {
    const result = await this.db.query(
      'SELECT value FROM oauth_tokens WHERE user_id = ? AND key = ?',
      [this.userId, key],
    )
    return result?.[0]?.value
  }

  async delete(key: string): Promise<void> {
    await this.db.query('DELETE FROM oauth_tokens WHERE user_id = ? AND key = ?', [
      this.userId,
      key,
    ])
  }
}

const provider = new MCPOAuthClientProvider({
  redirectUrl: 'http://localhost:3000/callback',
  clientMetadata: {/* ... */},
  clientInformation: { client_id: 'my-registered-client' },
  storage: new DatabaseOAuthStorage(db, 'user-123'),
})
```

### 静态 Tool 配置 {/* #static-tool-configuration */}

如果整个应用共用一条到 MCP 服务器的连接，请用 `listTools()` 获取 Tool，并将它们传给 Agent：

```typescript
import { MCPClient } from '@mastra/mcp'
import { Agent } from '@mastra/core/agent'

const mcp = new MCPClient({
  servers: {
    stockPrice: {
      command: 'npx',
      args: ['tsx', 'stock-price.ts'],
      env: {
        API_KEY: 'your-api-key',
      },
      logger: logMessage => {
        console.log(`[${logMessage.level}] ${logMessage.message}`)
      },
    },
    weather: {
      url: new URL('http://localhost:8080/mcp'),
    },
  },
  timeout: 30000, // Global 30s timeout
})

// Create an agent with access to all tools
const agent = new Agent({
  id: 'multi-tool-agent',
  name: 'Multi-tool Agent',
  instructions: 'You have access to multiple tool servers.',
  model: '__GATEWAY_OPENAI_MODEL__',
  tools: await mcp.listTools(),
})

// Example of using resource methods
async function checkWeatherResource() {
  try {
    const weatherResources = await mcp.resources.list()
    if (weatherResources.weather && weatherResources.weather.length > 0) {
      const currentWeatherURI = weatherResources.weather[0].uri
      const weatherData = await mcp.resources.read('weather', currentWeatherURI)
      console.log('Weather data:', weatherData.contents[0].text)
    }
  } catch (error) {
    console.error('Error fetching weather resource:', error)
  }
}
checkWeatherResource()

// Example of using prompt methods
async function checkWeatherPrompt() {
  try {
    const weatherPrompts = await mcp.prompts.list()
    if (weatherPrompts.weather && weatherPrompts.weather.length > 0) {

      if (currentWeatherPrompt) {

      } else {

      }

  } catch (error) {
    console.error('Error fetching weather prompt:', error)
  }
}
checkWeatherPrompt()
```

## 实例管理 {/* #instance-management */}

`MCPClient` 类内置了防止多个实例引发内存泄漏的机制：

1. 如果未指定 `id` 就用同一份配置创建多个实例，系统会抛出错误以防止内存泄漏。
2. 如需使用同一份配置创建多个实例，请为每个实例指定唯一的 `id`。
3. 用同一份配置重新创建实例之前，请先执行 `await configuration.disconnect()`。
4. 如果只需要一个实例，可以把配置移到外层作用域，避免重复创建。

例如，以下代码尝试用同一份配置创建多个实例，但未指定 `id`：

```typescript
// First instance - OK
const mcp1 = new MCPClient({
  servers: {/* ... */},
})

// Second instance with same config - Will throw an error
const mcp2 = new MCPClient({
  servers: {/* ... */},
})

// To fix, either:
// 1. Add unique IDs
const mcp3 = new MCPClient({
  id: 'instance-1',
  servers: {/* ... */},
})

// 2. Or disconnect before recreating
await mcp1.disconnect()
const mcp4 = new MCPClient({
  servers: {/* ... */},
})
```

## 服务器生命周期 {/* #server-lifecycle */}

MCPClient 按以下方式管理服务器连接：

1. 自动管理与多个服务器的连接
2. 有序关闭服务器，避免开发过程中出现错误消息
3. 断开连接时清理资源

### 由应用程序管理退出流程 {/* #handle-shutdown-yourself */}

默认情况下，客户端建立连接后会注册 `SIGINT`、`SIGTERM`、`SIGHUP` 和 `beforeExit` 钩子，用于断开与服务器的连接并结束进程。这些钩子可能会中断应用程序正在等待完成的清理操作，例如等待尚未处理完的 HTTP 请求结束。

设置 `registerProcessHooks: false`，由应用程序接管退出流程。等所有使用该客户端的请求处理完毕后，再调用 `disconnect()`：

```typescript
import { MCPClient } from '@mastra/mcp'

const mcp = new MCPClient({
  servers: { weather: { url: new URL('https://example.com/mcp') } },
  registerProcessHooks: false,
})

process.once('SIGTERM', async () => {
  // Finish your application's cleanup before disconnecting the client.
  await mcp.disconnect()
  process.exit(0)
})
```

进程中的每个 `MCPClient` 都应在连接前设置此选项。只要有一个客户端注册了默认钩子，全局的 `SIGINT` 和 `SIGTERM` 监听器就会一直保留到进程退出，即使已经调用 `disconnect()`。

禁用钩子后，由应用程序负责关闭 MCP 连接。在 Mastra 服务器中，请根据服务器的关闭流程安排 `disconnect()` 的调用时机，确保正在处理的请求能继续使用客户端直至完成。

## 使用自定义 `fetch` 在运行时进行身份验证 {/* #using-custom-fetch-for-runtime-defined-authentication */}

连接 HTTP 服务器时，可以提供自定义 `fetch` 函数，在运行时处理身份验证、拦截请求或执行其他自定义逻辑。例如，可以在每次请求时刷新令牌，或将入站请求中的用户凭据转发给 MCP 服务器。

自定义 `fetch` 函数接受可选的第三个参数 `requestContext`，可通过它读取当前请求的数据，例如中间件设置的身份验证 Cookie，或执行 Agent 或 Tool 时传入的持有者令牌。对于并非由 Tool 调用发出的请求，例如 `listTools()` 发出的请求及其触发的连接握手，`requestContext` 为 `null`。如果 Tool 调用建立了连接，握手就会收到该调用的 `requestContext`。这包括用 `toolsFromDefinitions()` 或 `toolFromDefinition()` 重建的 Tool 首次执行时建立的连接，以及 Tool 调用触发的重新连接。握手后仍保持打开的流（例如从服务器发往客户端的事件流）会继续使用同一个 `requestContext`。客户端在这些流上响应服务器请求时也会沿用该参数，例如回复输入请求。自己的代码收到这些流上的服务器日志或通知后主动发出的请求，其 `requestContext` 为 `null`。

因此，如果服务器对每个请求都进行身份验证，发现 Tool 和调用 Tool 都需要提供凭据。以下示例在 Tool 调用提供 `requestContext` 时转发用户的 Cookie，在缺少该参数时（例如 `listTools()` 发出的请求）发送应用程序自己的令牌。所有没有 `requestContext` 的请求都会携带该令牌，因此应在服务器端将它的权限限制在发现操作，例如只允许列出 Tool。

提供 `fetch` 后，`requestInit` 和 `authProvider` 就是可选项，因为自定义函数可以处理请求配置和身份验证。

```typescript
const mcpClient = new MCPClient({
  servers: {
    apiServer: {
      url: new URL('https://api.example.com/mcp'),
      fetch: async (url, init, requestContext) => {
        const headers = new Headers(init?.headers)
        if (requestContext) {
          // A tool call: forward the auth cookie from the incoming request
          const cookie = requestContext.get('cookie')
          if (cookie) {
            headers.set('cookie', cookie)
          }
        } else {
          // No requestContext, as in listTools(): a token the server only accepts for discovery
          headers.set('authorization', `Bearer ${process.env.MCP_DISCOVERY_TOKEN}`)
        }
        return fetch(url, { ...init, headers })
      },
    },
  },
})

// Use with an agent — requestContext is automatically forwarded
const agent = new Agent({
  id: 'my-agent',
  name: 'My Agent',
  instructions: 'You are a helpful assistant.',
  model: openai('gpt-5.4'),
  tools: await mcpClient.listTools(),
})

await agent.generate('Hello!', {
  requestContext: myRequestContext, // forwarded to the custom fetch
})
```

如果服务器只接受各用户自己的凭据，请在启动时跳过 `listTools()`。使用拥有独立凭据的客户端调用 [`listToolDefinitions()`](#listtooldefinitions)，生成并保存 Tool 目录。例如，可以在构建阶段通过 `requestInit` 设置静态请求头。运行时用 [`toolsFromDefinitions()`](#toolsfromdefinitions) 重建 Tool。每个重建的 Tool 会在首次调用时建立连接，因此握手会携带该调用的 `requestContext`。

## 在自定义 `fetch` 中处理身份验证失败 {/* #handling-auth-failures-inside-custom-fetch */}

无法进行身份验证时，自定义 `fetch` 不应使用 `throw` 抛出异常。`tools/call` 等 JSON-RPC 请求使用 `POST`，SDK 会将非 2xx 响应作为错误报告给 `listTools()`、`tools/call` 等操作的调用方。如果 `fetch` 抛出异常，SDK 也会报告错误，但会丢失服务器返回的状态码和响应体。连接使用 2025-11-25 版协议的服务器时，客户端还会在握手后发送不带请求体的 `GET`，以打开从服务器发往客户端的事件流。因此，请检查 `init.method`，不要假定请求一定带有 `POST` 请求体。长时间保持打开的流发生故障后会重新打开，包括客户端为 `resources.subscribe()` 发起的 `subscriptions/listen` `POST` 流，以及中断的 `GET` 事件流。未经身份验证的 `subscriptions/listen` 流可能反复重连。请先等待令牌，再转发请求：

```typescript
async function waitForToken(timeoutMs = 5000): Promise<string | null> {
  // Replace with your token lookup. Return null if no token is available.
  return getAuthToken({ timeoutMs })
}

const mcpClient = new MCPClient({
  servers: {
    apiServer: {
      url: new URL('https://api.example.com/mcp'),
      fetch: async (url, init) => {
        const token = await waitForToken()
        if (!token) {
          // Forward the request without a token and let the server reject it.
          return fetch(url, init)
        }

        const headers = new Headers(init?.headers)
        headers.set('authorization', `Bearer ${token}`)
        return fetch(url, { ...init, headers })
      },
    },
  },
})
```

## 发送请求头 {/* #sending-request-headers */}

在 `requestInit` 中配置静态请求头。每个请求都会携带这些请求头，包括用于建立 `subscriptions/listen` 流的请求：

```ts
const client = new MCPClient({
  servers: {
    exampleServer: {
      url: new URL('https://your-mcp-server.com/mcp'),
      requestInit: {
        headers: {
          Authorization: 'Bearer your-token',
        },
      },
    },
  },
})
```

如果请求头的值因请求而异，请使用自定义 `fetch`。
