# MCP客户端

这`MCPClient`类提供了一种在 Mastra 应用程序中管理多个 MCP 服务器连接及其Tool的方法。它处理连接生命周期和Tool命名空间，同时提供对所有已配置服务器上的Tool的访问。

:::注意
升级自`@mastra/mcp` 1.x? See the [migration guide](/reference/migrations/mcp-v2).
:::

### 键入客户合同 {/* #typed-client-contracts */}

将显式服务器映射类型传递给`MCPClient<TServers>` to check configured server names, discovered tool names, and direct-call arguments. `MCPClientOptions<TServers>` accepts the same map. All declared servers are required. Use `Pick<TServers, 'weather'>` to configure a subset. Without a type argument, discovery keeps its existing broad types.

该地图描述了每个服务器的`tools`, with `input` and `output` types for each tool. This example assumes a running weather server at `WEATHER_MCP_URL`:

```typescript
import { MCPClient } from '@mastra/mcp'

interface MCPServers {
  weather: {
    tools: {
      get_weather: {
        input: { location: string }
        output: { temperature: number; conditions: string }
      }
    }
  }
}

const mcp = new MCPClient<MCPServers>({
  servers: { weather: { url: new URL(process.env.WEATHER_MCP_URL!) } },
})

try {
  const tools = await mcp.listTools()
  const weather = tools.weather_get_weather
  if (weather?.execute) {
    const result = await weather.execute({ location: 'Paris' })
    if (result && 'temperature' in result && typeof result.temperature === 'number') {
      console.log(result.temperature)
    }
  }
} finally {
  await mcp.disconnect()
}
```

`listTools()`和`listToolsWithErrors().tools` expose exact `server_tool` keys. `listToolsets()` and `listToolsetsWithErrors().toolsets` expose server keys containing raw tool names. Both forms are partial: a server or tool can be absent. Check availability before calling a tool. Error maps, error details, and optional discovery durations keep their existing types.

执行可以返回结构化输出、协议结果信封、验证错误或`undefined`. Check the shape and property types before reading success fields. Protocol envelopes can have additional properties. Set `output: unknown` for tools without an output schema.

These contracts describe a schema snapshot. Live servers can differ from that snapshot.当服务器架构更改时，使用等效权限更新它们。额外的实时Tool在运行时仍然可用，但不包含在快照的已知键中。运行时发现、验证和执行保持不变。

### 生成客户端类型 {/* #generate-client-types */}

使用包含在中的命令从实时Tool输入和输出模式生成具体的 TypeScript 接口`@mastra/mcp`. Export your existing client and set `typegen.outFile`:

```typescript title="src/mcp/client.ts"
import { MCPClient } from '@mastra/mcp'
import type { MCPServers } from './mcp-types.generated'

export const mcp = new MCPClient<MCPServers>({
  id: 'weather-client',
  servers: { weather: { url: new URL(process.env.WEATHER_MCP_URL!) } },
  typegen: { outFile: 'src/mcp/mcp-types.generated.ts' },
})
```

设置模块所需的环境变量和身份验证凭据，然后从项目根目录运行以下命令：

```bash npm2yarn
npx @mastra/mcp generate ./src/mcp/client.ts
```

第一次运行时生成的仅类型导入可能会丢失。加载器无需类型检查即可处理 TypeScript 和传递导入。生成后运行类型检查。

使用生成的名称并检查运行时可用性和结果形状。此示例假设服务器发布`get_weather` with a required string `location` and a numeric `temperature` output:

```typescript title="src/mcp/call-weather.ts"
import { mcp } from './client'

try {
  const tools = await mcp.listTools()
  const weather = tools.weather_get_weather
  if (weather?.execute) {
    const result = await weather.execute({ location: 'Paris' })
    if (result && 'temperature' in result && typeof result.temperature === 'number') {
      console.log(result.temperature)
    }
  }
} finally {
  await mcp.disconnect()
}
```

该命令接受一个或多个文件路径。输入文件和`outFile` paths are relative to the command's working directory. It selects direct named and default exports of typegen-enabled clients. It doesn't scan your source tree, invoke factories, or inspect nested exported objects. Repeated files, symlink aliases, and exports of the same client are processed once. A file without an eligible client fails.

对于具有相同服务器配置的独立客户端，请使用不同的 ID 和输出路径：

```typescript title="src/mcp/clients.ts"
import { MCPClient } from '@mastra/mcp'

const servers = { weather: { url: new URL(process.env.WEATHER_MCP_URL!) } }
export const first = new MCPClient({
  id: 'first',
  servers,
  typegen: { outFile: 'first.generated.ts' },
})
export const second = new MCPClient({
  id: 'second',
  servers,
  typegen: { outFile: 'second.generated.ts' },
})
```

```bash npm2yarn
npx @mastra/mcp generate ./src/mcp/clients.ts
```

现有实例缓存仍然适用。使用相同的显式 ID、服务器配置和`typegen.outFile` returns the existing object. A different server configuration or `outFile` replaces the cached instance instead, so a later constructor never silently keeps an output file it wasn't given.

生成列出Tool定义而不调用Tool。它会因发现错误、缺少身份验证、超时、输出冲突、覆盖提供的输入文件的输出以及根本无法表示的模式（例如引用循环、深度过大或未解析的本地引用）而失败。每个故障都会命名它所涉及的客户端文件、服务器或Tool。它在替换文件之前准备好所有源，并在成功或失败时断开选定的客户端。发现和预检失败会保留现有输出。每个替换都是原子的，但多个替换不是一个事务。替换期间的文件系统故障可能会使较早的文件更新。

使用没有输出模式的Tool`unknown`. Constraints such as string formats, length limits, and numeric bounds retain their base TypeScript types and remain runtime validation rules. Unsupported schema portions, including conditional schemas and `prefixItems` tuples, widen to `unknown` with a warning. A keyword whose value is outside its allowed shape widens that schema to `unknown` with a warning too, so one unusable tool doesn't stop generation for other servers. Warnings name the server, tool, and schema position they concern. External schema references aren't fetched. Unresolved local references and reference cycles fail generation. Schemas nested deeper than 128 levels fail generation too, matching the protocol depth limit. A schema that exceeds the protocol node budget of 10,000 widens to `unknown` with a warning, as does any schema or catalogue that exceeds the larger budgets generation applies to raw JSON values. Generation measures those budgets before it copies or converts a schema, so a server that advertises large schemas can't stall the command.

:::note 模块执行和凭证

该命令执行提供的模块及其导入。使用可信模块，不会对应用程序启动产生副作用。在调用命令之前提供凭据。它不会加载 dotenv 文件或启动交互式身份验证。现有的客户端超时和发现设置适用。

生成器诊断忽略原始模式、传输错误和凭据。由导入的应用程序、自定义日志处理程序或服务器子进程发出的日志仍不受此保证。

:::

### `MastraMCPServerDefinition` {/* #mastramcpserverdefinition */}

中的每个服务器`servers` map is configured using the `MastraMCPServerDefinition` type. The transport type is detected based on the provided parameters:

* 如果`command` is provided, it uses the Stdio transport.
* 如果`url` is provided, it uses the Streamable HTTP transport.

客户端讲 MCP`2026-07-28` revision. On connect it asks the server which revisions it offers (`server/discover`) and falls back to the pre-2026 `initialize` handshake for servers that haven't upgraded, so tools, resources and prompts keep working against either. Features the older revisions lack (`resources.subscribe()`, `inputRequests`) fail with an error naming the negotiated revision. `onListChanged()` handlers work against either revision, since older servers send list-changed notifications without a `subscriptions/listen` stream. Set `protocolVersion` to skip the probe.

## Tool审批 {/* #tool-approval */}

使用`requireToolApproval` on a server definition to require human approval before any tool from that server is executed. This works with the existing [human-in-the-loop](/docs/workflows/human-in-the-loop) approval flow.

### 所有Tool都需要批准 {/* #require-approval-for-all-tools */}

放`requireToolApproval` to `true` to require approval for every tool on the server:

```typescript
const mcp = new MCPClient({
  servers: {
    github: {
      url: new URL('http://localhost:3000/mcp'),
      requireToolApproval: true,
    },
  },
})
```

### 动态审批功能 {/* #dynamic-approval-with-a-function */}

传递一个函数来决定每次调用是否需要批准。该函数接收Tool名称、模型传递的参数、传入请求的任何请求上下文以及Tool的 MCP`annotations` (when the server advertises them):

```typescript
const mcp = new MCPClient({
  servers: {
    github: {
      url: new URL('http://localhost:3000/mcp'),
      requireToolApproval: ({ toolName, args, requestContext }) => {
        // Read-only tools don't need approval
        if (toolName === 'list_repos') return false
        // Destructive tools with force flag always need approval
        if (toolName === 'delete_repo') return args.force === true
        // Non-admin users need approval for everything else
        return requestContext?.userRole !== 'admin'
      },
    },
  },
})
```

该函数也可以是异步的。它接收`requestContext` from the incoming request, which you can use for auth checks or other per-request logic.

### 使用来自受信任服务器的Tool注释 {/* #use-tool-annotations-from-a-trusted-server */}

如果您信任 MCP 服务器，您可以使用它[tool annotations](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#tool-annotations) (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`, `title`) to drive approval decisions:

```typescript
const mcp = new MCPClient({
  servers: {
    github: {
      url: new URL('http://localhost:3000/mcp'),
      requireToolApproval: ({ annotations }) => {
        // Skip approval for tools the server has marked read-only
        if (annotations?.readOnlyHint) return false
        // Always require approval for destructive tools
        if (annotations?.destructiveHint) return true
        return true
      },
    },
  },
})
```

根据 MCP 规范：**clients MUST consider tool annotations to be untrusted unless they come from trusted servers**. Annotations are advisory hints and provide no security boundary. A malicious or buggy server can claim a tool is read-only when it isn't. Only use annotations to relax approval requirements for servers you trust.

相同的注释也暴露在返回的Tool上`listTools()` and `listToolsets()` under `tool.mcp.annotations`, so you can inspect them when wiring tools into an agent.

每个Tool还带有`tool.title`, set from the server's tool `title` and falling back to `annotations.title`. When the server provides neither, `tool.title` is `undefined` and the tool name is the display fallback, matching the MCP display-name precedence.

## 服务器说明 {/* #server-instructions */}

当MCP服务器在初始化期间通告指令时，`MCPClient` stores them for that server. Forwarding those instructions into an agent's system prompt is **opt-in**: set `forwardInstructions: true` on a server to have agents that use its tools (via `listTools()` or `listToolsets()`) receive its instructions automatically.

该指南按服务器名称分组并截断为`instructionsMaxLength` characters per server.

```typescript
const mcp = new MCPClient({
  servers: {
    db: {
      url: new URL('http://localhost:3000/mcp'),
      forwardInstructions: true,
      instructionsMaxLength: 512,
    },
  },
})

const agent = new Agent({
  id: 'db-agent',
  name: 'DB Agent',
  instructions: 'Help with database changes.',
  model,
  tools: await mcp.listTools(),
})
```

什么时候`forwardInstructions` is omitted (the default), instructions are still cached and can be inspected via [`getServerInstructions()`](#getserverinstructions), but aren't added to any agent's system prompt.

> **安全说明：**&#x670D;务器指令被逐字转发（仅受长度截断）到Agent的系统提示符中。恶意或受损的 MCP 服务器可以使用它们注入指令，Agent将其视为可信的系统指导。仅启用`forwardInstructions` for servers you trust, and prefer reviewing instructions with `getServerInstructions()` before forwarding instructions from third-party servers.

## 安全 {/* #security */}

### Stdio 服务器的子进程环境 {/* #subprocess-environment-for-stdio-servers */}

Stdio 子进程不会继承完整的父进程环境。默认情况下，子进程环境从 MCP SDK 的策划白名单（POSIX：`HOME`, `LOGNAME`, `PATH`, `SHELL`, `TERM`, `USER`; Windows: `APPDATA`, `HOMEDRIVE`, `HOMEPATH`, `LOCALAPPDATA`, `PATH`, `PROCESSOR_ARCHITECTURE`, `SYSTEMDRIVE`, `SYSTEMROOT`, `TEMP`, `USERNAME`, `USERPROFILE`), merged with any variables you set in `env`. Sensitive variables such as API keys aren't inherited unless you pass them explicitly.

为了更严格的隔离，设置`inheritDefaultEnv: false` so only your configured `env` entries reach the subprocess:

```typescript
const mcp = new MCPClient({
  servers: {
    myTool: {
      command: '/usr/local/bin/my-mcp-server',
      inheritDefaultEnv: false,
      env: { MY_TOOL_API_KEY: process.env.MY_TOOL_API_KEY! },
    },
  },
})
```

您放入的变量`env` are forwarded verbatim, so treat server configurations that come from untrusted sources (for example, user-supplied config files) as untrusted input.

### 限制出站主机`allowedHosts` {/* #restricting-outbound-hosts-with-allowedhosts */}

当 HTTP 服务器 URL 来自不受信任的配置时，攻击者控制的 URL 可以将客户端指向内部服务（服务器端请求伪造）。放`allowedHosts` on such servers to restrict which hosts the client will contact:

```typescript
const mcp = new MCPClient({
  servers: {
    remote: {
      url: new URL(untrustedConfig.serverUrl),
      allowedHosts: ['api.example.com'],
    },
  },
})
```

执行详情：

* 在默认获取路径上，对不允许的主机的请求（包括每个重定向跃点）都会被阻止**before** they're sent. Redirects are followed manually (up to 5 hops) so each hop is validated, and the `Authorization` header isn't carried across hops to a different origin (any scheme, host, or port change drops it, matching standard fetch behavior).
* 当您提供定制`fetch`, the initial URL is still checked before the request, but redirect hops are validated **after the fact** using `response.url`: the outbound hop may occur, and the response is discarded when its final URL points at a disallowed host. A hand-built `Response` with an empty `response.url` skips this post-hoc check.
* 通过以下方式发出 OAuth 请求`authProvider` (authorization server metadata discovery, token exchange, refresh) are also validated. If your authorization server runs on a different host than the MCP server, add that host to `allowedHosts` too.
* 被阻止的主机因明显错误而导致连接失败，并且重新连接逻辑永远不会重试。

`allowedHosts`有意最小化：它匹配精确的主机并且不支持通配符或方案检查。如果您需要更丰富的策略（方案检查、IP 范围规则），请提供自定义`fetch` implementation, which is invoked for every request the client makes.

### 将Tool响应视为不受信任的输入 {/* #treat-tool-responses-as-untrusted-input */}

MCP 服务器返回的Tool结果作为模型输入流入Agent的上下文中。恶意或受感染的服务器可以使用Tool输出进行提示注入。传输客户端不会清理Tool响应：清理策略属于Agent层，其中 Mastra 的[input and output processors](/docs/agents/processors) let you inspect, transform, or block content before and after it reaches the model. Combine this with `requireToolApproval` and the `forwardInstructions` security note above when working with third-party servers.

## 方法 {/* #methods */}

### `listTools()` {/* #listtools */}

从所有配置的服务器中检索所有Tool，Tool名称按其服务器名称命名（格式为`serverName_toolName`) to prevent conflicts.
Intended to be passed onto an Agent definition.

仅限应用程序的Tool，其`_meta.ui.visibility` omits `"model"`, are left out. `listToolsets()` and `listToolDefinitions()` leave them out too.

服务器名称和Tool名称都可以包含`_`, so two different pairs can produce the same key. For example, server `local` with tool `x_status` and server `local_x` with tool `status` both produce `local_x_status`. The tool from the server listed later in `servers` keeps the key, and the client logs a warning that names both pairs. Rename one of the servers to keep both tools.

```ts
new Agent({ id: 'agent', tools: await mcp.listTools() })
```

### `listToolsWithErrors(options?)` {/* #listtoolswitherrorsoptions */}

从所有已配置的服务器检索所有Tool，Tool名称按其服务器名称命名。对于无法连接或列出Tool的服务器，还会返回每个服务器的错误。

放`perServerTimeoutMs` to limit how long discovery waits for each server. Servers that finish within the limit remain in `tools`. Timed-out servers appear in `errors`, and `durations` reports each server's discovery time in milliseconds.

```typescript
const { tools, errors, errorDetails, durations } = await mcp.listToolsWithErrors({
  perServerTimeoutMs: 3_000,
})

new Agent({ id: 'agent', tools })
console.log(errors, errorDetails, durations)
```

`errors`保留字符串映射以实现向后兼容性。`errorDetails` provides the same message plus machine-readable `httpStatus` and transport `code` fields when the underlying error exposes them. When an HTTP status is available, the legacy message also includes an `(HTTP nnn)` suffix.

当不带选项调用时，该方法仅省略`durations`; `tools`, `errors`, and `errorDetails` are always returned.

### `listToolsets()` {/* #listtoolsets */}

返回一个对象，该对象将每个服务器名称映射到该服务器的Tool。Tool保留其原始名称，没有服务器前缀。
旨在在运行时传递到生成或流方法中。

```typescript
const res = await agent.stream(prompt, {
  toolsets: await mcp.listToolsets(),
})
```

该Agent按Tool名称组合Tool集。当两个服务器暴露同名的Tool时，例如`search`, only the tool from the server listed later in `servers` reaches the model, and the agent logs a warning. To keep both tools, pass the prefixed tools from `listTools()` as a single toolset:

```typescript
const res = await agent.stream(prompt, {
  toolsets: { mcp: await mcp.listTools() }, // docs_search, tickets_search
})
```

### `listToolsetsWithErrors(options?)` {/* #listtoolsetswitherrorsoptions */}

返回按服务器名称分组的Tool集以及每个服务器的发现错误。放`perServerTimeoutMs` to limit each server independently and include per-server `durations` in milliseconds.

```typescript
const { toolsets, errors, errorDetails, durations } = await mcp.listToolsetsWithErrors({
  perServerTimeoutMs: 3_000,
})

const res = await agent.stream(prompt, { toolsets })
console.log(errors, errorDetails, durations)
```

当不带选项调用时，该方法仅省略`durations`; `toolsets`, `errors`, and `errorDetails` are always returned.

#### 报告每台服务器的稳定状态 {/* #report-each-server-as-it-settles */}

返回的承诺只有在每台服务器完成后才会解析，因此一台速度较慢的服务器会延迟整个结果。经过`onServerSettled` to handle each server as soon as its discovery succeeds, fails, or times out. The callback receives the server name and either `value` (that server's tools, keyed by the server's own tool names) or `error`, plus `duration` in milliseconds. This option is also available on `listToolsWithErrors()` and `listToolDefinitionsWithErrors()`.

```typescript
await mcp.listToolsetsWithErrors({
  perServerTimeoutMs: 60_000,
  onServerSettled: (serverName, { value, error, duration }) => {
    if (error) {
      console.error(`${serverName} failed after ${duration}ms: ${error.message}`)
    } else {
      console.log(`${serverName} ready with ${Object.keys(value).length} tools`)
    }
  },
})
```

回调抛出的错误会被记录下来，并且不会影响发现。对于一个来说也是如此`async` callback that rejects: the rejection is logged and never becomes an unhandled rejection.

#### {/* #discover-only-some-servers */}

经过`serverNames` to discover only the named servers, for example to retry the ones that timed out without starting every other server again. Names that aren't configured are ignored. This option is also available on `listToolsWithErrors()` and `listToolDefinitionsWithErrors()`.

```typescript
const { errorDetails } = await mcp.listToolsetsWithErrors({ perServerTimeoutMs: 3_000 })

// Only servers that timed out are worth retrying. A server that failed for
// another reason (bad config, auth refused) will just fail again.
const timedOut = Object.entries(errorDetails)
  .filter(([, details]) => details.code === MCP_DISCOVERY_TIMEOUT_CODE)
  .map(([serverName]) => serverName)

const retry = await mcp.listToolsetsWithErrors({ serverNames: timedOut })
```

`MCP_DISCOVERY_TIMEOUT_CODE`导出自`@mastra/mcp`. It marks the errors that `perServerTimeoutMs` produced, so you can tell a slow server apart from a broken one.

### `listToolDefinitions()` {/* #listtooldefinitions */}

以简单的、可序列化的定义形式返回每个服务器的Tool，按服务器名称分组并按服务器自己的Tool名称键入（不带`serverName_toolName` namespacing that `listTools()` applies).

喜欢`listTools()`, it leaves out app-only tools, whose `_meta.ui.visibility` omits `"model"`. An MCP App calls those through its host, so they never reach an agent.

不像`listTools()`, the result contains no functions or references to a live client, so it can be passed through `JSON.stringify` and cached in Redis or a database, as well as a build artifact. Each definition holds the data from the MCP `tools/list` response (name, title, description, input schema, output schema, annotations, and `_meta`), plus the server name, version, and instructions captured at discovery time.

```typescript
const definitions = await mcp.listToolDefinitions()

await cache.set('mcp-tools', JSON.stringify(definitions))
```

### `listToolDefinitionsWithErrors(options?)` {/* #listtooldefinitionswitherrorsoptions */}

喜欢`listToolDefinitions()`, but also returns per-server errors for servers that failed to connect. Use this when caching a catalog, so you don't persist a partial manifest that omits a server that was down at discovery time.

放`perServerTimeoutMs` to limit each server independently. When options are provided, `durations` reports each server's discovery time in milliseconds.

```typescript
const { definitions, errors, errorDetails, durations } = await mcp.listToolDefinitionsWithErrors({
  perServerTimeoutMs: 3_000,
})

if (Object.keys(errors).length === 0) {
  await cache.set('mcp-tools', JSON.stringify(definitions))
}

console.log(errorDetails, durations)
```

当不带选项调用时，该方法仅省略`durations`; `definitions`, `errors`, and `errorDetails` are always returned.

### `toolFromDefinition()` {/* #toolfromdefinition */}

从缓存的定义重建单个可执行Tool。这里没有打开连接。第一次执行该Tool时，客户端会延迟连接。

`listTools()`, with the same strict-mode metadata, approval policy, structured content handling, tool error handling, and reconnect behavior. Successful structured results are validated against the advertised `outputSchema` on both paths. Invalid results reject the tool call. MCP error results skip output validation.

没有 MCP 模式`$schema` declaration use JSON Schema 2020-12. Local `$ref` and `$defs` references, composition keywords, and boolean subschemas are supported. To bound validation work from untrusted tool catalogs, input and output schemas are limited to 128 nested subschema levels and 10,000 subschema nodes.

`structuredContent`可以是任何 JSON 值，包括字符串、数字、布尔值和`null`. Object and array results also expose the MCP content and `_meta` envelopes through non-enumerable Mastra metadata properties. Scalar and `null` results can't carry those properties and remain unchanged rather than being wrapped.

```typescript
const definitions = JSON.parse(await cache.get('mcp-tools'))

const tool = await mcp.toolFromDefinition({
  serverName: 'weather',
  definition: definitions.weather.getForecast,
})
```

### `toolsFromDefinitions()` {/* #toolsfromdefinitions */}

将整个缓存目录重建为命名空间Tool映射，无需连接。这是缓存的对应项`listTools()`. It produces the same `serverName_toolName` keys, so you can reconstruct an agent's tool map on a cold start, and connections only open for the servers whose tools are actually called.

目录中存在但不再在客户端上配置的服务器将被跳过，因此陈旧的缓存清单会正常降级。

```typescript
const definitions = JSON.parse(await cache.get('mcp-tools'))

new Agent({ id: 'agent', tools: await mcp.toolsFromDefinitions({ definitions }) })
```

### `authenticate()` {/* #authenticate */}

为服务器运行交互式 OAuth 授权代码流`MCPOAuthClientProvider` uses a loopback redirect URL. A local callback server passes the authorization URL to the provider's `onRedirectToAuthorization` callback and waits for the browser to return the code. It then exchanges the code for tokens and reconnects. See [Interactive browser authentication](#interactive-browser-authentication).

可选的`timeoutMs` bounds how long the flow waits for the browser to return the authorization code before rejecting, and defaults to 5 minutes.

```typescript oxfmt:false
async authenticate(serverName: string, options?: { timeoutMs?: number }): Promise<void>
```

### `getServerAuthState()` {/* #getserverauthstate */}

返回已配置服务器的 OAuth 授权状态：`'needs-auth'` after a connection attempt was rejected with an authorization error, `'authorized'` once the server accepted the provider's credentials, or `undefined` for servers without an `authProvider` or that haven't attempted a connection yet.

```typescript oxfmt:false
getServerAuthState(serverName: string): 'needs-auth' | 'authorized' | undefined
```

### `cancelAuthentication()` {/* #cancelauthentication */}

取消正在进行的操作`authenticate()` flow for a server, so an abandoned browser authorization doesn't leave the client waiting indefinitely. It aborts the flow (including its setup phase, before the callback server binds), closes the local callback server if one is listening, and the pending `authenticate()` call rejects. Returns `true` if a flow was cancelled, or `false` when no flow was in progress.

由此产生的`getServerAuthState()` depends on how far the flow progressed. A flow cancelled after a `401` rejection stays at `'needs-auth'` and can be retried immediately. Cancellation during setup leaves the state unchanged (typically `undefined`) if no connection was attempted.

```typescript oxfmt:false
async cancelAuthentication(serverName: string): Promise<boolean>
```

### `events`性质（实验） {/* #events-property-experimental */}

这`events` property lists and subscribes to server events from servers that implement the [MCP Events extension (SEP-3415)](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415). Use it to react to things that happen on the server, such as a push to a repository, without polling a tool. Delivery is at least once. After a reconnect or a resume, the server can resend an occurrence, and the client drops repeats by `eventId` within `dedupWindow` of recent ids.

有关端到端演练，请参阅[MCP events](/docs/connections/mcp#mcp-events).

:::警告
SEP-3415 是草案。此 API 可能会在任何版本中发生更改。
:::

```typescript
const events = await mcpClient.events.list('github')

const subscription = await mcpClient.events.subscribe(
  'github',
  'repo.push',
  { repo: 'mastra-ai/mastra' },
  { cursor: await loadCursor() },
)

for await (const event of subscription) {
  await handlePush(event.data)
  // Safe to persist after each handled occurrence
  await saveCursor(subscription.cursor)
}
```

不做广告的服务器`io.modelcontextprotocol/events` extension receive no `events/*` requests. `list()` rejects with a `MastraError` whose id is `MCP_CLIENT_LIST_EVENTS_FAILED`, and `subscribe()` rejects with `MCP_CLIENT_SUBSCRIBE_EVENT_FAILED`. In both cases `error.cause.id` is `MCP_EVENTS_NOT_SUPPORTED`. Other `list()` and `subscribe()` failures use the same two ids, with the specific reason in `error.cause`.

#### `events.list(serverName: string)` {/* #eventslistservername-string */}

分页后返回服务器提供的每种事件类型。每个描述符都有一个`name`, an optional `description`, the `delivery` modes the server supports, and optional `inputSchema` and `payloadSchema`.

```typescript oxfmt:false
async list(serverName: string): Promise<MCPEventDescriptor[]>
```

当服务器的事件列表发生更改时，客户端不会收到通知。称呼`list()` again to pick up new event types.

#### `events.subscribe(serverName, eventName, args?, options?)` {/* #eventssubscribeservername-eventname-args-options */}

启动订阅并在服务器确认后解析。未知事件、无效参数或禁止订阅等错误会拒绝返回的 Promise。新的订阅从服务器接受它的那一刻开始，因此不会传递该点之前的事件，除非`options.cursor` resumes from an earlier position. Under webhook delivery the promise can resolve after that point: the client answers `503` for a delivery it can't route yet, and the server retries it.

```typescript oxfmt:false
async subscribe(
  serverName: string,
  eventName: string,
  args?: Record<string, unknown>,
  options?: MCPEventSubscribeOptions,
): Promise<MCPEventSubscription>
```

客户端按以下顺序选择事件提供的第一个模式：`webhook` (only when the client has [`webhook` settings](#webhook-delivery)), `push` (a long-lived `events/stream` request), then `poll` (repeated `events/poll` requests). Pass `options.delivery` to force a mode.

返回的`MCPEventSubscription` is an async iterable of occurrences (`eventId`, `name`, `timestamp`, `data`) with these members:

* `cursor`：可以安全坚持的最新立场。它永远不会越过循环尚未收到的事件。它是`null` when the event type doesn't support replay.
* `truncated`: `true` when the server reported a gap right before the occurrence your loop received last, for example because the saved cursor was older than its retention window. Read it inside the loop: it's `true` for the first occurrence after the gap and `false` for the ones after it.
* `mode`：正在使用的交付模式，`'webhook'`, `'push'`, or `'poll'`.
* `deliveryStatus`：仅限 Webhook 模式。服务器关于传送到您的 webhook URL 的最新报告 (`active`, `lastDeliveryAt`, `lastError`, `failedSince`), updated on each refresh.
* `onError(handler)`：接收可恢复的错误，例如客户端重新打开已删除的流。返回一个删除处理程序的函数。
* `cancel()`：停止订阅并结束迭代器。突破一个`for await` loop also cancels it.

迭代器抛出一个`MastraError` directly (not wrapped) when the subscription can't continue: `MCP_EVENTS_SUBSCRIPTION_FAILED` for a non-retryable server error, `MCP_EVENTS_SUBSCRIPTION_TERMINATED` when the server ends a push or webhook subscription, or `MCP_EVENTS_RETRIES_EXHAUSTED` after `retry.maxAttempts` failed attempts in a row. The client reopens dropped streams and resumes polling from the last cursor after a reconnect, including after `reconnectServer()`. `disconnect()` ends all subscriptions.

#### `events.handleWebhook(request: Request)` {/* #eventshandlewebhookrequest-request */}

处理一个 Webhook 传递并返回要发回的响应。将其安装在以下路线上`webhook.url` points at.

```typescript oxfmt:false
async handleWebhook(request: Request): Promise<Response>
```

它在解析原始主体之前验证标准 Webhooks 签名，应答服务器的验证握手，并将事件路由到其订阅`X-MCP-Subscription-Id` header. It responds with:

* `200`在事件被交给其订阅之后，或者带有验证请求的回显质询。
* `401`当签名无效或时间戳超过 5 分钟时。
* `503`当订阅 ID 还不知道时。在这种情况下，服务器会重试，覆盖在订阅响应之前到达的交付。
* `400`对于一个签名但畸形的身体，以及`405` for methods other than `POST`.
* `413`对于超过 1 MiB 的主体。在进行任何其他检查之前，主体只能读取该限制。
* `404`当客户没有`webhook` settings.

#### Webhook 交付 {/* #webhook-delivery */}

和`webhook` settings, the client registers each subscription with `events/subscribe` and the server POSTs occurrences to your URL. The server must authenticate the client, and the URL must be publicly reachable over `https`.

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { registerApiRoute } from '@mastra/core/server'
import { MCPClient } from '@mastra/mcp'

export const mcpClient = new MCPClient({
  servers: {
    github: {
      url: new URL('https://mcp.example.com/mcp'),

export const mastra = new Mastra({
  server: {

        method: 'POST',

        requiresAuth: false,
        handler: c => mcpClient.events.handleWebhook(c.req.raw),

    ],
  },
})
```

### Agent和Workflow中的事件（实验） {/* #events-in-agents-and-workflows-experimental */}

`MCPEventsSignalProvider`将 MCP 服务器事件作为通知传递给Agent线程。将其添加到Agent中`signals`, then subscribe threads to events. The agent needs a notifications storage domain, which `InMemoryStore` and the standard storage adapters provide.

:::警告
SEP-3415 是草案。此 API 可能会在任何版本中发生更改。
:::

```typescript title="src/mastra/agents/repo-agent.ts"
import { Agent } from '@mastra/core/agent'
import { MCPClient, MCPEventsSignalProvider } from '@mastra/mcp'

const mcp = new MCPClient({
  servers: { github: { url: new URL('https://example.com/mcp') } },
})

export const repoEvents = new MCPEventsSignalProvider({
  client: mcp,
  subscribeOptions: { maxAgeMs: 60 * 60 * 1000 },
})

export const repoAgent = new Agent({
  id: 'repo-agent',
  name: 'Repo Agent',
  instructions: 'Triage repository activity.',
  model: '__GATEWAY_OPENAI_MODEL__',
  signals: [repoEvents],
})

await repoEvents.subscribeThread(
  { resourceId: 'user-1', threadId: 'thread-1' },
  { server: 'github', event: 'repo.push', args: { repo: 'mastra-ai/mastra' } },
)
```

订阅同一服务器、事件和参数的线程共享一个 MCP 订阅，无论参数键顺序如何。每次发生都会成为一个通知`kind: 'mcp-event'` and `attributes: { server, event }`. The raw occurrence is in `payload`. The notification `summary`, which is the only part the model reads, labels the event as untrusted and wraps its data, together with the server-advertised event name, in an `<untrusted-mcp-event-data>` block that the content can't close. When the server reports a gap, `attributes.truncated` is `true` and the summary says that events may have been skipped.

如果订阅结束，例如因为服务器终止它，则每个订阅线程都会收到一个`high` priority notification with `kind: 'mcp-event-subscription-ended'` and the threads are unsubscribed.

提供者有以下方法：

* `subscribeThread(thread, { server, event, args? })`：订阅一个线程，并在 MCP 订阅确认后解析。它从存储的游标恢复。如果服务器拒绝订阅，则该线程不会被订阅并且 Promise 会被拒绝。线程订阅仅保存在内存中：重启后，调用`subscribeThread()` again for each thread that should keep receiving events.
* `unsubscribeThread(thread, { server, event, args? })`: 决定`true` when the thread was subscribed. When the last thread leaves, the MCP subscription is cancelled and its stored cursor is deleted.

```typescript title="src/mastra/triggers/repo-push.ts"
const subscription = await mcp.events.subscribe(

process.once('SIGTERM', () => void subscription.cancel())

for await (const event of subscription) {
  const run = await triagePushWorkflow.createRun()
  await run.start({ inputData: { eventId: event.eventId, push: event.data } })
  if (subscription.cursor) await saveCursor(subscription.cursor)
}
```

### `tasks`性质（实验） {/* #tasks-property-experimental */}

有些Tool需要比一个 HTTP 请求保持打开状态更长的时间。一个服务器实现了[MCP Tasks extension (SEP-2663)](https://modelcontextprotocol.github.io/ext-tasks/specification/2026-07-28/tasks.html) can answer such a call with a task, and the client fetches the result later. Set `tasks` on a server to accept them:

```typescript
const mcpClient = new MCPClient({
  servers: {
    reports: {
      url: new URL('https://reports.example.com/mcp'),
      tasks: { maxWaitMs: 30 * 60_000 },
      inputRequests: async ({ params }) => askUser(params),
    },
  },
})
```

:::警告
此 API 可能会在任何版本中发生更改。
:::

和`tasks` set, the client tells the server it accepts tasks. The server decides per call whether to answer directly or with a task. Without `tasks`, the client never receives one and tool calls behave as before.

当Tool调用返回任务时，该Tool保持其通常的形状：

* 客户端按照服务器建议的时间间隔轮询任务，直到任务完成，然后返回Tool结果。
* 需要输入的任务通过以下方式回答`inputRequests`, once per request key. The client sends the answers with `tasks/update` and keeps polling the same task. It never sends `tools/call` again. Without a handler, a tool call from an agent or workflow suspends so the user can answer (see [Answering task input from the agent chat](#answering-task-input-from-the-agent-chat)). A direct `tool.execute()` call fails with `MCP_CLIENT_TOOL_TASK_INPUT_UNHANDLED`, and the task stays open on the server until its TTL ends.
* 中止Tool调用发送`tasks/cancel`. Reaching `maxWaitMs` sends it too, and fails the call with `MCP_CLIENT_TOOL_TASK_TIMEOUT`. Both end the call right away, even while a poll or your input handler is still running. A late answer from either is dropped.
* 客户端轮询时断开连接结束通话`MCP_CLIENT_TOOL_TASK_POLL_FAILED` and doesn't reconnect.
* 如果在客户端轮询期间（例如在重新启动或部署期间）无法访问服务器，则客户端会重新连接并继续轮询，延迟会不断增加，最多可达 30 秒。来自Agent的拒绝连接以及 HTTP 502、503 和 504 被视为无法访问。 5 分钟后没有得到答复，或者当`maxWaitMs` or the task's TTL ends first, the call fails with `MCP_CLIENT_TOOL_TASK_POLL_FAILED`. The task may still finish on the server. The TTL counts from the task's `createdAt`. If the client can't read that timestamp, it counts from when it started waiting.
* Tool调用跨度得到`mcpTaskKey` metadata: a SHA-256 hash of the task id. A Mastra server tags its spans for the task with the same key, so you can match both sides and the task id stays out of both traces.
* 已完成任务中的Tool错误的处理方式与直接Tool错误类似，如下`onToolError`. A task the server cancelled fails with `MCP_CLIENT_TOOL_TASK_CANCELLED`, and a task the server marked `failed` fails with `MCP_CLIENT_TOOL_TASK_FAILED`.
* 返回任务的调用永远不会重试，因为重试将启动第二个任务。
* 当调用作为任务继续进行时，并且只要任务的状态发生变化，该Tool就会写入一个`MCPTaskProgress` entry (`{ type: 'mcp-task', taskId, status, createdAt, serverName }`) to its output stream. Studio's tool-call card uses it to show the task's status, elapsed time and MCP task id while it runs. Tool output isn't saved with the thread. After a reload, the card shows only the result.

在Agent上[background tasks](/docs/harness/background-tasks) enabled, tools from a server with `tasks` set run as deferred background tasks with no retries. The agent keeps working while the remote task runs, and cancelling the background task cancels the remote task. Override this per tool with the agent's `backgroundTasks.tools`.

#### 回答客服人员聊天中输入的任务 {/* #answering-task-input-from-the-agent-chat */}

当任务需要输入时，不`inputRequests` handler is configured, and the tool runs in an agent or workflow, the tool call suspends like any tool that calls `suspend()`. The remote task stays open on the server. The suspend payload (`MCPInputRequestSuspendPayload`) carries the requests still waiting for an answer:

```typescript
const payload: MCPInputRequestSuspendPayload = {
  type: 'mcp-input-request',
  serverName: 'reports',
  toolName: 'approve_and_send',
  taskId: 'Zx81…', // the MCP task the answers go to
  createdAt: '2026-10-30T10:00:00.000Z', // when the task was created
  requestedAt: '2026-10-30T10:00:04.000Z', // when the call suspended; new each time the task asks again
  requests: {
    approve: {
      method: 'elicitation/create',
      params: {
        mode: 'form',
        message: 'Send it?',
        requestedSchema: {
          type: 'object',
          properties: { ok: { type: 'boolean' } },
          required: ['ok'],
        },
      },
    },
  },
}
```

使用每个请求密钥一个答案来恢复Tool调用 (`MCPInputRequestResumeData`), for example through `agent.resumeStream()` in the foreground, or `backgroundTaskManager.resume()` for a deferred background task:

```typescript
await agent.resumeStream(
  { inputResponses: { approve: { action: 'accept', content: { ok: true } } } },
  { runId, toolCallId },
)
```

在恢复时，客户端发送同一任务的答案`tasks/update` and keeps polling it. It never sends `tools/call` again. If the server asks again, the call suspends again with the new requests. If the task ended meanwhile, the call fails with the usual task error, such as `MCP_CLIENT_TOOL_TASK_CANCELLED`, or `MCP_CLIENT_TOOL_TASK_POLL_FAILED` when the server no longer knows the task. Resume data that isn't `{ inputResponses: { [key]: { action: 'accept' | 'decline' | 'cancel', content? } } }`, or that leaves a request unanswered, fails with `MCP_CLIENT_TOOL_TASK_RESUME_INVALID` without contacting the server.

已配置的`inputRequests` handler takes precedence: the call then never suspends.

有效负载保存 MCP 任务 ID，该 ID 授予对任务的访问权限。它与挂起的Tool调用一起存储，因此请像对待线程的其余数据一样对待它。

#### `tasks.get(serverName: string, taskId: string)` {/* #tasksgetservername-string-taskid-string */}

返回任务的当前状态（`MCPDetailedTask`), including `result` once it's `completed` and `inputRequests` while it's `input_required`. Fails with `MCP_CLIENT_GET_TASK_FAILED`; an unknown task, or one created by another caller, has `error.cause.code` `-32602`.

#### `tasks.update(serverName: string, taskId: string, inputResponses: MCPTaskInputResponses)` {/* #tasksupdateservername-string-taskid-string-inputresponses-mcptaskinputresponses */}

回答了`inputRequests` of an `input_required` task, keyed like the requests. The server ignores keys it didn't ask for or that are already answered. Fails with `MCP_CLIENT_UPDATE_TASK_FAILED`.

#### `tasks.cancel(serverName: string, taskId: string)` {/* #taskscancelservername-string-taskid-string */}

要求服务器停止任务。服务器可能仍会完成它。失败与`MCP_CLIENT_CANCEL_TASK_FAILED`.

## 回答输入请求 {/* #answering-input-requests */}

需要用户提供某些信息的服务器Tool、资源或提示以`input_required` result instead of a value. The result carries one or more embedded requests, each with a server-chosen `key` and either a form (`requestedSchema`) or a URL the user must visit. Configure `inputRequests` on the server definition to answer them: the client calls the handler once per embedded request, retries the original call with the answers, and resolves the tool call with the final result. Without a handler an `input_required` result surfaces as an error.

```typescript
import { MCPClient } from '@mastra/mcp'

const mcpClient = new MCPClient({
  servers: {
    interactiveServer: {
      url: new URL('http://localhost:3000/mcp'),
      inputRequests: async ({ key, params, signal }) => {
        if (params.mode === 'url') {
          return { action: 'decline' }
        }
        const content = await collectUserInput(params.message, params.requestedSchema, { signal })
        return { action: 'accept', content }
      },
    },
  },
})
```

### `MCPInputRequest` {/* #mcpinputrequest */}

处理程序接收：

* `key`：服务器选择的密钥，答案被归档。当一轮中有多个请求到达时，将其传递到您的 UI。
* `params`: 请求。在表单模式下它有`message` and `requestedSchema`, a flat JSON Schema object of primitive fields. In url mode it has `message` and `url`.
* `signal`：当发起呼叫取消或超时时中止。

配置处理程序向服务器通告表单支持。要同时接受 url 模式请求，请扩大`capabilities.elicitation` on the same server definition.

### 响应类型 {/* #response-types */}

返回一个`ElicitResult`:

* **接受**：用户提供数据并确认提交。`content` must match `requestedSchema`.

  ```typescript
  return {
    action: 'accept',
    content: { name: 'John Doe', email: 'john@example.com' },
  }
  ```

* **衰退**：用户明确拒绝提供该信息。

  ```typescript
  return { action: 'decline' }
  ```

* **取消**：用户拒绝了请求。
  ```typescript
  return { action: 'cancel' }
  ```

拒绝或取消的请求会结束Tool调用并出现错误。服务器可以在接受答案后再次询问，因此处理程序可能会针对一个Tool调用运行多次。

### 基于模式的输入收集 {/* #schema-based-input-collection */}

走`requestedSchema` to prompt for each field:

```typescript
inputRequests: async ({ params }) => {
  if (params.mode === 'url') return { action: 'decline' }

  const { properties, required = [] } = params.requestedSchema
  const content: Record<string, string | number | boolean> = {}

  for (const [fieldName, fieldSchema] of Object.entries(properties)) {
    const value = await promptUser({
      name: fieldName,
      title: fieldSchema.title,
      description: fieldSchema.description,
      required: required.includes(fieldName),
    })

    if (value !== null) {
      content[fieldName] = value
    }
  }

  return { action: 'accept', content }
}
```

### 最佳实践 {/* #best-practices */}

* **预先配置处理程序**：它是服务器定义的一部分，因此要求输入的Tool永远不会在没有输入的情况下运行。
* **验证输入**：检查是否提供了必填字段。
* **尊重用户选择**：优雅地处理拒绝和取消回复。
* **清晰的用户界面**：明确要求提供哪些信息以及原因。
* **安全**：永远不要自动接受敏感信息的请求，并将 url 模式请求视为指向不受信任站点的链接。

## OAuth认证 {/* #oauth-authentication */}

用于连接到需要 OAuth 身份验证的 MCP 服务器[MCP 2026-07-28 authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), use the `MCPOAuthClientProvider`. The provider never registers a client at runtime: give it either `clientInformation` for a client pre-registered with the authorization server, or a [Client ID Metadata Document](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration#client-id-metadata-documents) URL as `clientMetadataUrl`:

```typescript
import { MCPClient, MCPOAuthClientProvider } from '@mastra/mcp'

// Create an OAuth provider
const clientMetadataUrl = 'https://app.example.com/oauth/client-metadata.json'

const oauthProvider = new MCPOAuthClientProvider({
  redirectUrl: 'http://localhost:3000/oauth/callback',
  clientMetadataUrl,
  clientMetadata: {
    client_id: clientMetadataUrl,
    redirect_uris: ['http://localhost:3000/oauth/callback'],
    client_name: 'My MCP Client',
    grant_types: ['authorization_code', 'refresh_token'],
    response_types: ['code'],
  },
  onRedirectToAuthorization: url => {
    // Handle authorization redirect (open browser, redirect response, etc.)
    console.log(`Please visit: ${url}`)
  },
})

// Use the provider with MCPClient
const client = new MCPClient({
  servers: {
    protectedServer: {
      url: new URL('https://mcp.example.com/mcp'),
      authProvider: oauthProvider,
    },
  },
})
```

该文件送达于`clientMetadataUrl` must contain the same `client_id`, `client_name`, and `redirect_uris`. For loopback callbacks, include every fallback URL returned by `getCallbackUrlCandidates()` in the hosted document. The URL is sent as the `client_id`; the provider never calls a registration endpoint, so an authorization server that accepts neither the metadata document nor a pre-registered `clientInformation` fails the flow explicitly. Configure exactly one identity: the constructor throws when both `clientInformation` and `clientMetadataUrl` are set.

保存的令牌`MCPOAuthClientProvider` are bound to the authorization server's validated `issuer`, and discovery state is persisted so the code exchange is only sent to the server that issued the redirect. The loopback callback also forwards the RFC 9207 `iss` parameter to the SDK, which rejects a mismatch before exchanging the authorization code.

给每个服务器自己的`MCPOAuthClientProvider` instance. A provider holds per-server session and credential state during authorization, so sharing one instance across multiple servers lets their flows overwrite each other. When configuring several protected servers, construct a separate provider for each. If those providers use the same persistent backend, give each provider a separate `OAuthStorage` namespace because storage mutation ordering is coordinated only within one provider instance.

### 交互式浏览器身份验证 {/* #interactive-browser-authentication */}

当服务器因为需要授权而拒绝连接时，客户端会记录一个`'needs-auth'` state instead of failing outright. Calling `authenticate()` completes the flow. It starts a one-shot callback server on the provider's loopback redirect URL, falling back to the next sequential ports when it's in use. The SDK then performs discovery and uses the configured client identity. `onRedirectToAuthorization` receives the authorization URL so your application can open it in the user's browser. The token exchange finishes after the browser returns the authorization code:

```typescript
import { MCPClient, MCPOAuthClientProvider } from '@mastra/mcp'

const clientMetadataUrl = 'https://app.example.com/oauth/client-metadata.json'

const oauthProvider = new MCPOAuthClientProvider({
  redirectUrl: 'http://127.0.0.1:5533/oauth/callback',
  clientMetadataUrl,
  clientMetadata: {
    client_id: clientMetadataUrl,
    redirect_uris: ['http://127.0.0.1:5533/oauth/callback'],
    client_name: 'My MCP Client',
    grant_types: ['authorization_code', 'refresh_token'],
    response_types: ['code'],
  },
  onRedirectToAuthorization: url => {
    // Open the user's browser at the consent page
    console.log(`Please visit: ${url}`)
  },
})

const mcp = new MCPClient({
  servers: {
    protectedServer: {
      url: new URL('https://mcp.example.com/mcp'),
      authProvider: oauthProvider,
    },
  },
})

try {
  await mcp.listTools()
} catch {
  if (mcp.getServerAuthState('protectedServer') === 'needs-auth') {
    await mcp.authenticate('protectedServer')
  }
}
```

并发`authenticate()` calls for the same server join the pending flow. Different servers authenticate independently. With valid stored tokens the call reconnects without opening a browser.

驱动流量的主机可以通过导出的内容捕获授权代码`createOAuthCallbackServer` helper. It creates a one-shot loopback server that validates the OAuth `state` parameter before resolving with the code. Because the server uses plain HTTP, use it only for local loopback redirects. Web applications with an HTTPS redirect URL must host their own callback endpoint and drive the provider directly:

```typescript
import { createOAuthCallbackServer, getCallbackUrlCandidates } from '@mastra/mcp'

// getCallbackUrlCandidates() lists every URL the helper may bind, so list all
// of them as redirect_uris in your pre-registration or metadata document.
const redirectUris = getCallbackUrlCandidates('http://127.0.0.1:5533/oauth/callback').map(url =>
  url.toString(),
)

const server = await createOAuthCallbackServer({
  redirectUrl: 'http://127.0.0.1:5533/oauth/callback',
  state: expectedState,
})

// server.url reflects the port actually bound — use it as the redirect_uri.
try {
  const { code, iss } = await server.waitForCode()
  // Exchange the code here, passing `iss` so the SDK validates the issuer.
} finally {
  await server.close()
}
```

### 自定义令牌存储 {/* #custom-token-storage */}

对于跨会话的持久令牌存储​​，请实现`OAuthStorage` interface. The provider stores tokens (both the latest set and one entry per authorization-server issuer), discovery state, and the PKCE verifier under string keys. The backend only needs a key-value contract:

```typescript
import { MCPOAuthClientProvider, OAuthStorage } from '@mastra/mcp'

class DatabaseOAuthStorage implements OAuthStorage {
  constructor(
    private db: Database,
    private userId: string,
  ) {}

  async set(key: string, value: string): Promise<void> {
    await this.db.query(
      'INSERT INTO oauth_tokens (user_id, key, value) VALUES (?, ?, ?) ON CONFLICT DO UPDATE SET value = ?',
      [this.userId, key, value, value],
    )
  }

  async get(key: string): Promise<string | undefined> {
    const result = await this.db.query(
      'SELECT value FROM oauth_tokens WHERE user_id = ? AND key = ?',
      [this.userId, key],
    )
    return result?.[0]?.value
  }

  async delete(key: string): Promise<void> {
    await this.db.query('DELETE FROM oauth_tokens WHERE user_id = ? AND key = ?', [
      this.userId,
      key,
    ])
  }
}

const provider = new MCPOAuthClientProvider({
  redirectUrl: 'http://localhost:3000/callback',
  clientMetadata: {/* ... */},
  clientInformation: { client_id: 'my-registered-client' },
  storage: new DatabaseOAuthStorage(db, 'user-123'),
})
```

## 实例管理 {/* #instance-management */}

这`MCPClient` class includes built-in memory leak prevention for managing multiple instances:

1. 创建具有相同配置的多个实例，无需`id` will throw an error to prevent memory leaks
2. 如果您需要具有相同配置的多个实例，请提供唯一的`id` for each instance
3. 称呼`await configuration.disconnect()` before recreating an instance with the same configuration
4. 如果您只需要一个实例，请考虑将配置移至更高的范围以避免重新创建

例如，如果您尝试创建具有相同配置的多个实例而不使用`id`:

```typescript
// First instance - OK
const mcp1 = new MCPClient({
  servers: {/* ... */},
})

// Second instance with same config - Will throw an error
const mcp2 = new MCPClient({
  servers: {/* ... */},
})

// To fix, either:
// 1. Add unique IDs
const mcp3 = new MCPClient({
  id: 'instance-1',
  servers: {/* ... */},
})

// 2. Or disconnect before recreating
await mcp1.disconnect()
const mcp4 = new MCPClient({
  servers: {/* ... */},
})
```

## 服务器生命周期 {/* #server-lifecycle */}

MCPClient 优雅地处理服务器连接：

1. 多服务器自动连接管理
2. 优雅地关闭服务器以防止开发过程中出现错误消息
3. 断开连接时正确清理资源

### 自行处理关机 {/* #handle-shutdown-yourself */}

默认情况下，连接的客户端安装钩子`SIGINT`, `SIGTERM`, `SIGHUP`, and `beforeExit` that disconnect its servers and end the process. These hooks can interrupt your application's awaited cleanup, such as draining HTTP requests.

放`registerProcessHooks: false` to let your application own shutdown. Call `disconnect()` after requests that use the client have finished:

```typescript
import { MCPClient } from '@mastra/mcp'

const mcp = new MCPClient({
  servers: { weather: { url: new URL('https://example.com/mcp') } },
  registerProcessHooks: false,
})

process.once('SIGTERM', async () => {
  // Finish your application's cleanup before disconnecting the client.
  await mcp.disconnect()
  process.exit(0)
})
```

设置每个选项`MCPClient` in the process before connecting. Once any client registers the default hooks, the global `SIGINT` and `SIGTERM` listeners remain until the process exits, even after `disconnect()`.

禁用挂钩后，您的应用程序负责关闭 MCP 连接。在 Mastra 服务器中，协调`disconnect()` with your server's shutdown lifecycle so in-flight requests can finish using the client.

## 使用自定义获取进行运行时定义的身份验证 {/* #using-custom-fetch-for-runtime-defined-authentication */}

对于 HTTP 服务器，您可以提供自定义`fetch` function to handle runtime-defined authentication or request interception. It can also handle other custom behavior. This is particularly useful when you need to refresh tokens on each request or forward user credentials from the incoming request to the MCP server.

习俗`fetch` function receives an optional third `requestContext` parameter, which provides access to request-scoped data (e.g., authentication cookies, bearer tokens) set by middleware or passed during agent/tool execution. The `requestContext` is `null` for requests that no tool call sends, such as `listTools()` and the connection handshake it opens. When a tool call opens the connection, either because a tool rebuilt with `toolsFromDefinitions()` or `toolFromDefinition()` connects on its first execution or because the call reconnects, the handshake receives that call's `requestContext`. Streams the connection keeps open afterward, such as the server-to-client event stream, keep using that same `requestContext`, and so do the client's replies to server requests on them, such as an answer to an input request. A request your own code starts from a server log or notification on those streams gets `null`.

因此，对每个请求进行身份验证的服务器需要一个用于发现和Tool调用的凭据。以下示例在Tool调用提供以下信息时转发用户的 cookie`requestContext`, and sends the app's own token when there's none, as in `listTools()`. Any request without a `requestContext` gets that token, so have the server limit it to discovery, for example listing tools but not calling them.

什么时候`fetch` is provided, `requestInit` and `authProvider` become optional, as you can handle these concerns within your custom fetch function.

```typescript
const mcpClient = new MCPClient({
  servers: {
    apiServer: {
      url: new URL('https://api.example.com/mcp'),
      fetch: async (url, init, requestContext) => {
        const headers = new Headers(init?.headers)
        if (requestContext) {
          // A tool call: forward the auth cookie from the incoming request
          const cookie = requestContext.get('cookie')
          if (cookie) {
            headers.set('cookie', cookie)
          }
        } else {
          // No requestContext, as in listTools(): a token the server only accepts for discovery
          headers.set('authorization', `Bearer ${process.env.MCP_DISCOVERY_TOKEN}`)
        }
        return fetch(url, { ...init, headers })
      },
    },
  },
})

// Use with an agent — requestContext is automatically forwarded
const agent = new Agent({
  id: 'my-agent',
  name: 'My Agent',
  instructions: 'You are a helpful assistant.',
  model: openai('gpt-5.4'),
  tools: await mcpClient.listTools(),
})

await agent.generate('Hello!', {
  requestContext: myRequestContext, // forwarded to the custom fetch
})
```

如果服务器仅接受每用户凭据，请跳过`listTools()` at startup. Build the catalog with [`listToolDefinitions()`](#listtooldefinitions) from a client that has a credential of its own, for example in a build step with a static `requestInit` header, and store it. At runtime, rebuild the tools with [`toolsFromDefinitions()`](#toolsfromdefinitions). Each rebuilt tool opens the connection on its first call, so the handshake carries that call's `requestContext`.

## 处理自定义获取中的身份验证失败 {/* #handling-auth-failures-inside-custom-fetch */}

定制`fetch` shouldn't `throw` when authentication is unavailable. JSON-RPC requests such as `tools/call` are `POST`s, and the SDK surfaces a non-2xx response as an error to the caller of `listTools()`, `tools/call` and so on, which is the behavior you want. A thrown `fetch` is reported the same way but loses the server's status and body. On a 2025-11-25 server, the client also sends a `GET` with no body after the handshake to open the server-to-client event stream, so check `init.method` rather than assuming a `POST` body. Long-lived streams are reopened after a failure: the `subscriptions/listen` `POST` the client opens for `resources.subscribe()` and the `GET` event stream if it drops. An unauthenticated `subscriptions/listen` stream can loop. Wait for the token, then forward the request:

```typescript
async function waitForToken(timeoutMs = 5000): Promise<string | null> {
  // Replace with your token lookup. Return null if no token is available.
  return getAuthToken({ timeoutMs })
}

const mcpClient = new MCPClient({
  servers: {
    apiServer: {
      url: new URL('https://api.example.com/mcp'),
      fetch: async (url, init) => {
        const token = await waitForToken()
        if (!token) {
          // Forward the request without a token and let the server reject it.
          return fetch(url, init)
        }

        const headers = new Headers(init?.headers)
        headers.set('authorization', `Bearer ${token}`)
        return fetch(url, { ...init, headers })
      },
    },
  },
})
```
