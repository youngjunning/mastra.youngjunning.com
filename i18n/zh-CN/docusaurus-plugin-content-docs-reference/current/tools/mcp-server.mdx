# MCPServer

`MCPServer` 类可通过模型上下文协议（MCP）服务器对外提供现有的 Mastra Tool 和 Agent。Cursor、Windsurf、Claude Desktop 等 MCP 客户端都可以连接到服务器，让 Agent 使用这些功能。

如果只在 Mastra 应用中直接使用 Tool 或 Agent，可以省去创建 MCP 服务器的步骤。此 API 专门用于向*外部* MCP 客户端提供 Mastra Tool 和 Agent。

要直接公开 Mastra 应用中的所有 Agent、Workflow 和 Tool，可以使用 `/api/mcp` 上的[内置 MCP 服务器](/docs/server/mcp)。它为每个调用方生成 Tool 列表，并对每次调用执行对应 HTTP 路由的身份验证和权限检查。要发布选定的 Tool 和 Agent 并附上自定义提示和资源，或通过 stdio 提供服务，请使用 `MCPServer`。

它支持 MCP `2026-07-28` 版本的两种[传输方式：stdio（子进程）和 Streamable HTTP](https://modelcontextprotocol.io/docs/concepts/transports)。

:::note
如果要从 `@mastra/mcp` 1.x 升级，请参阅[迁移指南](/reference/migrations/mcp-v2)。
:::

## 构造函数 {/* #constructor */}

创建 `MCPServer` 时，需要提供服务器的基本信息和要公开的 Tool，也可以指定要作为 Tool 公开的 Agent。

```typescript
import { Agent } from '@mastra/core/agent'
import { createTool } from '@mastra/core/tools'
import { MCPServer } from '@mastra/mcp'
import { z } from 'zod'
import { dataProcessingWorkflow } from '../workflows/dataProcessingWorkflow'

const myAgent = new Agent({
  id: 'my-example-agent',
  name: 'MyExampleAgent',
  description: 'A generalist to help with basic questions.',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

const weatherTool = createTool({
  id: 'getWeather',
  description: 'Gets the current weather for a location.',
  inputSchema: z.object({ location: z.string() }),
  execute: async inputData => `Weather in ${inputData.location} is sunny.`,
})

const server = new MCPServer({
  id: 'my-custom-server',
  name: 'My Custom Server',
  version: '1.0.0',
  description: 'A server that provides weather data and agent capabilities',
  instructions:
    'Use the available tools to help users with weather information and data processing tasks.',
  tools: { weatherTool },
  agents: { myAgent }, // this agent will become tool "ask_myAgent"
  workflows: {
    dataProcessingWorkflow, // this workflow will become tool "run_dataProcessingWorkflow"
  },
})
```

## Tool 的模式与结构化结果 {/* #tool-schemas-and-structured-results */}

MCP Tool 的输入和输出模式以 JSON Schema 2020-12 发布，并在 `$schema` 中声明所用方言。对外发布的 Mastra Tool 模式保留受支持的引用、组合关键字和元组结构（`prefixItems`）。

定义了 `outputSchema` 的 Tool 可以返回任意 JSON 值，包括对象、数组、字符串、数字、布尔值或 `null`。服务器直接将该值作为 `structuredContent` 发送，无需再用对象包裹。调用成功时，服务器会按照 Tool 的输出模式验证结构化输出，再返回结果。

## Tool 结果 {/* #tool-results */}

默认情况下，服务器将 Tool 的输出作为单个文本块发送给 MCP 客户端。字符串原样发送，其他值以 JSON 形式发送。Tool 定义了 `outputSchema` 时，还会将该值作为 `structuredContent` 返回。

可使用 `toolResult` 选项发送 Tool 提供给模型的输出，或在发送前改写结果。

```typescript title="src/mastra/mcp/server.ts"
import { MCPServer } from '@mastra/mcp'
import { screenshotTool } from '../tools/screenshot'

const server = new MCPServer({
  id: 'media-server',
  name: 'Media Server',
  version: '1.0.0',
  tools: { screenshotTool },
  toolResult: {
    modelOutput: true,
  },
})
```

:::warning

在 `@mastra/mcp` 的下一个主版本中，`modelOutput` 的默认值将改为 `true`。如果 MCP 客户端会解析定义了 `toModelOutput` 的 Tool 所返回的原始 JSON 文本，请现在设置 `modelOutput: false`，以保留当前行为。

:::

设置 `modelOutput: true` 后，服务器按下表将 `toModelOutput` 的值映射为 MCP 内容：

| `toModelOutput` 的值 | MCP 结果 |
| - | - |
| `{ type: 'text', value }` | 文本块 |
| `{ type: 'json', value }` | 包含 JSON 值的文本块 |
| `{ type: 'error-text' }` 或 `{ type: 'error-json' }` | 带有 `isError: true` 的文本块 |
| `content` 中的 `text` 部分 | 文本块 |
| `content` 中的 `media`、`image-data` 或 `file-data` 部分 | `image/*` 对应 `image` 块，`audio/*` 对应 `audio` 块，其他类型对应含有 `blob` 的嵌入式 `resource` |
| `content` 中含 `data:` URI 的 `image-url` 或 `file-url` 部分 | 与媒体数据的处理方式相同 |
| `content` 中含远程 URL 的 `image-url` 或 `file-url` 部分 | 包含 URL 的文本块 |

对于定义了 `outputSchema` 的 Tool，结果会保留 `structuredContent`，并将其 JSON 文本块放在映射生成的内容块之前。如果 `toModelOutput` 或 `transform` 抛出异常，客户端会收到 Tool 的错误结果。

可用 `transform` 转发已符合 MCP 格式的结果，例如通过 `MCPClient` 代理的 Tool 返回的结果：

```typescript title="src/mastra/mcp/proxy-server.ts"
import { MCPClient, MCPServer, type MCPServerToolResultContext } from '@mastra/mcp'

const upstream = new MCPClient({
  servers: { files: { url: new URL('https://files.example.com/mcp') } },
})

const server = new MCPServer({
  id: 'proxy-server',
  name: 'Proxy Server',
  version: '1.0.0',
  tools: await upstream.listTools(),
  toolResult: {
    // Unstructured upstream tools return the upstream MCP result as their output
    transform: ({ output }) => {
      const upstreamResult = output as MCPServerToolResultContext['result']
      return Array.isArray(upstreamResult?.content) ? upstreamResult : undefined
    },
  },
})
```

## 将 Agent 作为 Tool 公开 {/* #exposing-agents-as-tools */}

在配置的 `agents` 属性中提供 Mastra Agent 后，`MCPServer` 会自动将它们公开为可调用的 Tool。

* **Tool 命名**。每个 Agent 都会转换为名为 `ask_<agentKey>` 的 Tool，其中 `<agentKey>` 是该 Agent 在 `agents` 对象中的键。例如，配置 `agents: { myAgentKey: myAgentInstance }` 会创建名为 `ask_myAgentKey` 的 Tool。

* **Tool 的行为**
  * **描述**采用“向 Agent `<AgentName>` 提问。Agent 的原始指令：`<agent description>`”这一格式。
  * **输入**为单个对象参数，其中 `message` 属性是字符串，例如 `{ message: "Your question for the agent" }`。
  * **执行**时，Tool 将传入的 `query` 交给对应 Agent 的 `generate()` 方法。
  * **输出**直接采用 Agent 的 `generate()` 方法返回的结果。

* **名称冲突**。如果 `tools` 配置中显式定义的 Tool 与 Agent 生成的 Tool 同名，例如同时存在名为 `ask_myAgentKey` 的 Tool 和键为 `myAgentKey` 的 Agent，则*显式定义的 Tool 优先*。服务器会跳过该 Agent 的转换并记录警告。

MCP 客户端可以像调用其他 Tool 一样，通过自然语言查询与 Agent 交互。

### 将 Agent 转换为 Tool {/* #agent-to-tool-conversion */}

在配置的 `agents` 属性中提供 Agent 后，`MCPServer` 会为每个 Agent 自动创建相应的 Tool。Tool 名称为 `ask_<agentIdentifier>`，其中 `<agentIdentifier>` 是 `agents` 对象中的键。

生成的 Tool 描述采用“向 Agent `<agent.name>` 提问。Agent 描述：`<agent.description>`”这一格式。

要将 Agent 转换为 Tool，实例化 Agent 时**必须**在配置中设置非空的 `description` 字符串，例如 `new Agent({ id: 'my-agent', name: 'myAgent', description: 'This agent does X.', ... })`。如果传入 `MCPServer` 的 Agent 缺少 `description` 或该值为空，实例化 `MCPServer` 时会抛出错误，导致服务器无法完成设置。

客户端可通过 MCP 使用 Agent 的生成能力，直接向 Agent 提问。

### 在 Tool 中访问 MCP 上下文 {/* #accessing-mcp-context-in-tools */}

通过 `MCPServer` 公开的 Tool 可从 `context.mcp` 获取当前请求的协议上下文：

| 成员 | 说明 |
| - | - |
| `context.mcp.extra.signal` | 客户端取消请求或断开连接时触发中止信号 |
| `context.mcp.extra.requestId` | 请求的 JSON-RPC ID |
| `context.mcp.extra.authInfo` | 传输层验证得到的身份信息，详见身份验证上下文一节 |
| `context.mcp.extra._meta` | 请求元数据，包括追踪请求头、客户端选择接收的日志级别和进度令牌 |
| `context.mcp.log()` | 向发起调用的客户端发送日志消息，详见日志记录一节 |
| `context.mcp.progress()` | 向发起调用的客户端报告进度，详见进度通知一节 |
| `context.mcp.protocolVersion` | `'2026-07-28'` |

同一请求还会将 `authInfo`、`mapAuthInfoToUser` 返回的 `user` 和客户端发送的 W3C `traceContext` 写入受信任的应用上下文 `context.requestContext`。MCP 客户端通过 `ask_<agent>` 请求 Agent 时，请求上下文会转发给该 Agent，而 Agent 调用的 Tool 不会收到 `context.mcp`。如果 Tool 既可以由客户端直接调用，也可以经 Agent 调用，可按以下方式从请求上下文读取身份验证数据：

```typescript
const authInfo = context.mcp?.extra.authInfo ?? context.requestContext?.get('authInfo')
```

#### 示例：在 Tool 中识别调用方并使用独立凭据 {/* #example-tool-that-uses-caller-identity-with-a-separate-credential */}

```typescript
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

import { apiCredentials } from '../lib/api-credentials'

const fetchUserData = createTool({
  id: 'fetchUserData',
  description: 'Fetches data for the authenticated MCP caller',
  inputSchema: z.object({
    resourceId: z.string().describe('The ID of the record to fetch'),
  }),
  execute: async (inputData, context) => {
    const authInfo = context.mcp?.extra.authInfo ?? context.requestContext?.get('authInfo')
    const user = authInfo?.extra?.user as { id?: string } | undefined

    if (!user?.id) {
      throw new Error('Authentication required')
    }

    // Resolve the owner from trusted context, not from model input
    const credential = await apiCredentials.getForUser(user.id)

    const response = await fetch(
      `https://api.example.com/users/${encodeURIComponent(user.id)}/records/${encodeURIComponent(inputData.resourceId)}`,
      {
        headers: {
          Authorization: `Bearer ${credential.token}`,
        },
        signal: context.mcp?.extra.signal,
      },
    )

    return response.json()
  },
})
```

通过 `authInfo` 确定调用者身份，再为 Tool 要调用的服务选择相应的凭据。模型提供 `resourceId` 等业务参数，由可信代码选择凭据。MCP 访问令牌仅供你的 MCP 服务器使用，不得转发给其他 API。参见[安全访问上游服务](/docs/guides/mcp-authentication-authorization#access-upstream-services-safely)。

#### `authInfo` 的来源 {/* #where-authinfo-comes-from */}

当 Mastra 服务器托管 MCP 服务器时，系统会根据 `server.auth` 解析出的身份主体填充 `extra.authInfo`，无需额外配置：

```typescript
export const mastra = new Mastra({
  mcpServers: { myServer },
  server: {
    auth: new MastraJwtAuth({ secret: process.env.JWT_SECRET! }),
  },
})
```

通过身份验证的用户按以下规则映射到 `authInfo`：

| `authInfo` 字段 | 值 |
| - | - |
| `token` | 请求使用的持有者令牌或会话 Cookie 的值 |
| `clientId` | 按 `user.id`、`user.sub`、`user.userId`、`user.email` 的顺序取第一个存在的值 |
| `scopes` | 将 `user.scopes`、`user.scope` 或 `user.permissions` 统一转换为数组 |
| `extra.user` | 身份验证 Provider 返回的完整用户对象 |

如果由自定义中间件执行身份验证，请设置 `server.mcpOptions.setRequestAuth` 来构造 `authInfo`。该钩子会替代默认映射：

```typescript
export const mastra = new Mastra({
  mcpServers: { myServer },
  server: {
    middleware: [verifyBearerToken], // stores the payload on the request context
    mcpOptions: {
      setRequestAuth: (req, requestContext) => {
        const payload = requestContext.get('bearerPayload')
        req.auth = {
          token: payload.token,
          clientId: payload.sub,
          scopes: payload.scope.split(' '),
        }
      },
    },
  },
})
```

如果钩子未设置 `req.auth`，该请求将完全不携带身份验证信息。

## 向调用者请求输入 {/* #asking-the-caller-for-input */}

如果 Tool 需要用户补充信息才能完成调用，就像在 Agent 或 Workflow 中一样，调用 `context.suspend(payload)` 后返回。服务器以 `input_required` 结果结束请求，其中附有 Tool 的 `resumeSchema` 定义的表单。客户端答复后，服务器会再次运行 Tool，并通过 `context.resumeData` 传入答复，通过 `context.suspendPayload` 传入挂起时的载荷。每一轮都是独立请求，服务器不会重放前面的轮次。请在载荷中保存下一轮所需的状态，并据此选择执行分支。

```typescript
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

export const bookDelivery = createTool({
  id: 'bookDelivery',
  description: 'Books a delivery for an order after confirming the address.',
  inputSchema: z.object({ orderId: z.string() }),
  outputSchema: z.object({ confirmed: z.boolean() }),
  suspendSchema: z.object({ phase: z.literal('address'), message: z.string() }),
  resumeSchema: z.object({ address: z.string() }),
  execute: async ({ orderId }, context) => {
    if (!context.resumeData) {
      await context.suspend?.({ phase: 'address', message: 'Delivery address?' })
      return
    }
    await book(orderId, context.resumeData.address)
    return { confirmed: true }
  },
})
```

服务器根据 `resumeSchema` 生成供调用者填写的表单，因此它必须描述一个扁平对象，字段仅支持字符串、数字、布尔值和枚举。调用者拒绝填写或取消表单时，调用以错误结束，Tool 不会再次运行。Tool 可以更新载荷中的阶段，以便多次挂起。

### 恢复状态 {/* #continuation-state */}

恢复调用所需的状态通过不透明的 `requestState` 字符串传递，客户端在答复时原样回传。服务器使用 `requestState.key` 为状态签名，并在运行处理函数前拒绝已篡改、已过期或不匹配的状态，包括 Tool、参数或调用者不一致的情况。调用者身份优先取授权层提供的令牌主体，其次取 `mapAuthInfoToUser` 返回的用户 `id`，最后使用持有者令牌本身。因此，使用同一个 OAuth 客户端的两个用户无法恢复彼此挂起的调用。

未启用授权的服务器上的所有调用者共用一个匿名主体。在 `ttlSeconds` 指定的期限内，`requestState` 相当于持有者凭据，任何拿到它的人都可以答复这一轮请求。能在恢复后执行写入、购买或账户变更等操作的 Tool 应受授权保护。

载荷只有签名，没有加密。请控制载荷大小，只放 ID、阶段等非机密数据。通过环境配置设置 `requestState.key`，让所有可能处理恢复请求的实例共用密钥。如果未配置，服务器会为每个进程生成自己的密钥，调用只能在原进程上恢复。

```typescript
const server = new MCPServer({
  id: 'booking',
  name: 'Booking',
  version: '1.0.0',
  tools: { bookDelivery },
  requestState: { key: process.env.MCP_REQUEST_STATE_KEY!, ttlSeconds: 600 },
})
```

资源和提示的回调也可以用相同方式挂起。参见[资源处理](#resource-handling)和[提示处理](#prompt-handling)。

### `startHTTP()` {/* #starthttp */}

将 MCP 服务器集成到现有 Web 服务器中，通过 Streamable HTTP 通信。Web 服务器收到 HTTP 请求时，在请求处理函数中调用此方法。

```typescript oxfmt:false
async startHTTP({
  url,
  httpPath,
  req,
  res,
  options,
}: {
  url: URL;
  httpPath: string;
  req: http.IncomingMessage;
  res: http.ServerResponse<http.IncomingMessage>;
  options?: MCPServerHTTPRequestOptions;
}): Promise<void>
```

每个请求都独立处理，无需创建或恢复会话，因此 `options` 仅用于配置请求检查。

| 选项 | 行为 |
| - | - |
| `enableDnsRebindingProtection` | 为 `true` 时，在处理请求前分别对照 `allowedHosts` 和 `allowedOrigins` 检查 `Host` 和 `Origin` 请求头。仅当对应列表非空时才执行检查。被拒绝的请求会收到 `403` JSON-RPC 错误。 |
| `allowedHosts` | `Host` 请求头允许使用的主机名。匹配时忽略端口，因此列表中的 `localhost:3000` 允许 `localhost` 上的任何端口。IPv6 地址需用方括号括起，例如 `[::1]`。 |
| `allowedOrigins` | `Origin` 请求头允许使用的来源。只比较主机名，因此 `https://app.example.com:8443` 允许 `app.example.com` 上的任何协议和端口。没有 `Origin` 请求头的请求可以通过，因为非浏览器 MCP 客户端不会发送该请求头。 |

无需检查请求时，可以省略 `options`。

下面的示例在 HTTP 服务器的请求处理函数中调用 `startHTTP`。MCP 客户端可以通过 `http://localhost:1234/mcp` 连接到该 MCP 服务器：

```typescript
import http from 'http'

const httpServer = http.createServer(async (req, res) => {
  await server.startHTTP({
    url: new URL(req.url || '', 'http://localhost:1234'),
    httpPath: `/mcp`,
    req,
    res,
  })
})

httpServer.listen(PORT, () => {
  console.log(`HTTP server listening on port ${PORT}`)
})
```

每个请求都独立处理，调用之间无需保留状态，因此 `startHTTP` 可以在无服务器环境中运行，例如 Supabase Edge Functions、Cloudflare Workers、Vercel Edge、AWS Lambda 和 Deno Deploy。此方法接收 Node 风格的 `http.IncomingMessage` 和 `http.ServerResponse` 对象。在基于 Fetch 的运行时中，需要用 `fetch-to-node` 等适配器转换 `Request`，再将结果转换回 `Response`：

```typescript
// Supabase Edge Function example

// Note: You will need to convert req/res format from Deno to Node

  id: 'my-serverless-mcp',
  name: 'My Serverless MCP',
  version: '1.0.0',
  tools: {/* your tools */},
})

  const url = new URL(req.url)

  if (url.pathname === '/mcp') {
    // Convert Deno Request to Node.js-compatible format

    await server.startHTTP({ url, httpPath: '/mcp', req: nodeReq, res: nodeRes })

    return toFetchResponse(nodeRes)
```

## 资源处理 {/* #resource-handling */}

### 什么是 MCP 资源？ {/* #what-are-mcp-resources */}

MCP 资源向客户端提供服务器数据，客户端可读取这些数据并用作与 LLM 交互的上下文。例如：

* 文件内容
* 数据库记录
* API 响应
* 实时系统数据
* 屏幕截图和图像
* 日志文件

每项资源都有唯一的 URI，例如 `file:///home/user/documents/report.pdf` 或 `postgres://database/customers/schema`。资源可以包含 UTF-8 编码的文本或 Base64 编码的二进制数据。



1. **直接资源**：服务器通过 `resources/list` 端点公开具体资源的列表。
2. **资源模板**：对于在运行时确定的资源，服务器可以公开 URI 模板（RFC 6570），供客户端构造资源 URI。

要读取资源，客户端需发送带有资源 URI 的 `resources/read` 请求。服务器还可以通知客户端资源列表发生变化（`notifications/resources/list_changed`）。如果客户端正在监听某项资源，服务器也可以通知它该资源的内容已更新（`notifications/resources/updated`）。

详情请参阅 [MCP 官方资源文档](https://modelcontextprotocol.io/docs/concepts/resources)。

### `MCPServerResources` 类型 {/* #mcpserverresources-type */}

`resources` 选项接受 `MCPServerResources` 类型的对象。该类型定义服务器处理资源请求时使用的回调：

```typescript
export type MCPServerResources = {
  // Callback to list available resources
  listResources: (params: {
    extra: MCPRequestHandlerExtra
    requestContext: RequestContext
  }) => Promise<Resource[]>

  // Callback to get the content of a specific resource
  getResourceContent: (
    params: { uri: string } & MCPServerRequest,
  ) => Promise<MCPServerResourceContent | MCPServerResourceContent[] | void>

  // Optional callback to list available resource templates
  resourceTemplates?: (params: {
    extra: MCPRequestHandlerExtra
    requestContext: RequestContext
  }) => Promise<ResourceTemplate[]>

  // Shape of the answer a suspended getResourceContent expects
  resumeSchema?: StandardSchemaWithJSON
}

export type MCPServerResourceContent = { text?: string } | { blob?: string }
```

每个回调都会收到 `extra` 和 `requestContext`。`extra` 与 Tool 通过 `context.mcp.extra` 获取的协议上下文相同，其中包含用于取消操作的 `signal`，以及 `requestId`、`authInfo` 和 `_meta`。`requestContext` 是可信的应用上下文，包含 `authInfo` 和通过 `mapAuthInfoToUser` 映射得到的用户。可借助这两个上下文限制调用方可以列出和读取的资源。

处理 `resources/read` 请求时，服务器先在 `listResources` 返回的列表中查找 URI。如果列表中没有匹配的资源，服务器就将 URI 与调用方的 `resourceTemplates` 匹配，并将展开后的 URI 传给 `getResourceContent`。URI 可以省略 `{?format}` 或 `{/section}` 等可选表达式。变量值必须按 RFC 6570 的展开规则进行百分号编码，因此 `file://data?format=a/b` 无法匹配 `file://data{?format}`。响应使用匹配资源或模板的 `mimeType` 和 `_meta`。如果 URI 未匹配任何资源或模板，请求将以 `Resource not found` 失败。

`getResourceContent` 还会收到 `MCPServerRequest` 的 `suspend`、`resumeData` 和 `suspendPayload` 成员。声明 `resumeSchema` 后即可使用 `suspend`，用法与 Tool 完全相同。

例子：

```typescript
import { MCPServer } from '@mastra/mcp'
import type {
  MCPServerResourceContent,
  MCPServerResources,
  Resource,
  ResourceTemplate,
} from '@mastra/mcp'

// Resources/resource templates will generally be dynamically fetched.
const myResources: Resource[] = [
  { uri: 'file://data/readme', name: 'Readme', mimeType: 'text/plain' },
]

const myResourceContents: Record<string, MCPServerResourceContent> = {
  'file://data/readme': { text: 'Read this first.' },
  // Not listed; readable as an expansion of the `file://data/{id}` template
  'file://data/123': { text: 'This is the content of data file 123.' },
}

const myResourceTemplates: ResourceTemplate[] = [
  {
    uriTemplate: 'file://data/{id}',
    name: 'Data File',
    description: 'A file containing data.',
    mimeType: 'text/plain',
  },
]

const myResourceHandlers: MCPServerResources = {
  listResources: async () => myResources,
  getResourceContent: async ({ uri, extra }) => {
    if (myResourceContents[uri]) {
      return myResourceContents[uri]
    }
    throw new Error(`Resource content not found for ${uri}`)
  },
  resourceTemplates: async () => myResourceTemplates,
}

const serverWithResources = new MCPServer({
  id: 'resourceful-server',
  name: 'Resourceful Server',
  version: '1.0.0',
  tools: {/* ... your tools ... */},
  resources: myResourceHandlers,
})
```

### 向客户端通知资源变更 {/* #notifying-clients-of-resource-changes */}

```typescript oxfmt:false

```

例子：

```typescript

```

## 提示处理 {/* #prompt-handling */}

### 什么是 MCP 提示？ {/* #what-are-mcp-prompts */}

提示是 MCP 服务器向客户端公开的可复用模板或 Workflow。提示可以接受参数并包含资源上下文，用于规范与大语言模型的交互。

每个提示都有唯一的名称，可以静态定义，也可以在运行时定义。

### `MCPServerPrompts` 类型 {/* #mcpserverprompts-type */}

`prompts` 选项接受 `MCPServerPrompts` 类型的对象。该类型定义了服务器处理提示请求时使用的回调。

```typescript
export type MCPServerPrompts = {
  // Callback to list available prompts
  listPrompts: (params: {
    extra: MCPRequestHandlerExtra
    requestContext: RequestContext
  }) => Promise<Prompt[]>

  // Callback to get the messages for a specific prompt
  getPromptMessages?: (
    params: { name: string; args?: Record<string, unknown> } & MCPServerRequest,
  ) => Promise<PromptMessage[] | void>

  // Shape of the answer a suspended getPromptMessages expects
  resumeSchema?: StandardSchemaWithJSON
}
```

提示回调收到的 `extra` 和 `requestContext` 与资源回调相同。声明 `resumeSchema` 后，`getPromptMessages` 也可以用同样的方式调用 `suspend`。服务器会先验证提示的必填参数，再调用 `getPromptMessages`。

例子：

```typescript
import { MCPServer } from '@mastra/mcp'
import type { Prompt, PromptMessage, MCPServerPrompts } from '@mastra/mcp'

const prompts: Prompt[] = [
  {
    name: 'analyze-code',
    description: 'Analyze code for improvements',
    arguments: [{ name: 'code', description: 'The code to analyze', required: true }],
  },
]

const myPromptHandlers: MCPServerPrompts = {
  listPrompts: async () => prompts,
  getPromptMessages: async ({ name, args }) => {
    if (name === 'analyze-code') {
      return [
        {
          role: 'user',
          content: {
            type: 'text',
            text: `Analyze this code: ${args?.code}`,
          },
        },
      ]
    }
    throw new Error('Prompt not found')
  },
}

const serverWithPrompts = new MCPServer({
  id: 'prompt-server',
  name: 'Prompt Server',
  version: '1.0.0',
  tools: {/* ... your tools ... */},
  prompts: myPromptHandlers,
})
```

### 向客户端通知提示变更 {/* #notifying-clients-of-prompt-changes */}

可用提示发生变化时，服务器可以通知正在监听的客户端。

#### `server.prompts.notifyListChanged()` {/* #serverpromptsnotifylistchanged */}

添加或删除提示等操作导致可用提示列表变化时，调用此方法。正在监听的客户端会收到 `notifications/prompts/list_changed` 消息，从而重新获取提示列表。

```typescript oxfmt:false
await serverWithPrompts.prompts.notifyListChanged();
```

### 提示处理的最佳实践 {/* #best-practices-for-prompt-handling */}

* 为提示取一个能体现其用途的名称，并清楚说明用途。
* 在 `getPromptMessages` 中验证所有必填参数。
* 请求中的提示不存在或缺少必填参数时，返回错误。
* 每次提示发生变化时都通知客户端。

## 动态管理 Tool {/* #dynamic-tool-management */}

服务器运行期间可以添加或移除 Tool。已连接的客户端会收到 `notifications/tools/list_changed` 通知。

用于管理 Tool 的属性名为 `toolActions`。`tools()` 方法用于返回已注册的 Tool。

### `toolActions.add(tools)` {/* #toolactionsaddtools */}

在运行中的服务器上注册新 Tool，并通知已连接的客户端。与传给构造函数的 Tool 一样，注册使用输入对象中对应条目的键。如果该键已存在，新 Tool 会替换原有 Tool。

```typescript oxfmt:false
async server.toolActions.add(tools: ToolsInput): Promise<void>
```

例子：

```typescript
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

const searchTool = createTool({
  id: 'search',
  description: 'Searches the knowledge base.',
  inputSchema: z.object({ query: z.string() }),
  execute: async ({ query }) => ({ results: [] }),
})

await server.toolActions.add({ searchTool })
```

### `toolActions.remove(toolIds)` {/* #toolactionsremovetoolids */}

按 Tool ID 从运行中的服务器移除 Tool，并通知已连接的客户端。服务器会忽略未知的 Tool ID，且仅在实际移除至少一个 Tool 时发送通知。

```typescript oxfmt:false
async server.toolActions.remove(toolIds: string[]): Promise<void>
```

例子：

```typescript
await server.toolActions.remove(['searchTool'])
```

### `toolActions.notifyListChanged()` {/* #toolactionsnotifylistchanged */}

向已连接的客户端发送 `notifications/tools/list_changed` 消息，注册表保持原样。如果授权调整等其他因素改变了 Tool 的可用性，请调用此方法。

```typescript oxfmt:false
async server.toolActions.notifyListChanged(): Promise<void>
```

### Mastra 注册表同步 {/* #mastra-registry-synchronization */}

服务器注册到 Mastra 实例后，`toolActions.add()` 和 `toolActions.remove()` 也会更新该实例的 Tool 注册表，与启动时自动注册 Tool 的行为一致。可以通过 `mastra.listTools()` 获取新增的 Tool。如果 Tool 自带 `id`，就以该 ID 为键。移除的 Tool 会从注册表中删除。

## 日志 {/* #logging */}

Tool 通过 `notifications/message` 向发起调用的客户端发送结构化日志。客户端必须在每个请求的元数据中加入 `io.modelcontextprotocol/logLevel` 键才能接收日志。服务器仅针对该请求发送达到或超过所指定严重程度的日志，级别顺序遵循 RFC 5424。同一次 Tool 调用的后续轮次属于新请求，必须重新声明要接收日志。启用 `enableServerLogs` 后，Mastra 的 `MCPClient` 会在每个请求中发送此键。

`context.mcp.log()` 只控制 MCP 客户端收到的日志，不影响 Mastra 的日志记录器或可观测性。

### `context.mcp.log()` {/* #contextmcplog */}

在 Tool 的 `execute` 函数中，使用 `context.mcp.log()` 向调用该 Tool 的客户端发送日志消息。

```typescript oxfmt:false
async context.mcp.log(
  level: LoggingLevel,
  message: string,
  data?: Record<string, unknown>
): Promise<void>
```

例子：

```typescript
execute: async ({ location }, context) => {
  await context.mcp?.log?.('debug', 'Fetching weather', { location })
  const weather = await fetchWeather(location)
  await context.mcp?.log?.('info', 'Weather fetched')
  return weather
}
```

## 进度通知 {/* #progress-notifications */}

长时间运行的 Tool 可以通过 `notifications/progress` 向发起调用的客户端报告进度。调用方必须在请求的 `_meta` 中加入 `progressToken` 来启用进度跟踪，才能收到通知。设置 `enableProgressTracking` 后，Mastra 的 `MCPClient` 会加入该令牌。如果请求没有携带令牌，`context.mcp.progress()` 不执行任何操作。

### `context.mcp.progress()` {/* #contextmcpprogress */}

```typescript oxfmt:false
async context.mcp.progress(params: {
  progress: number;
  total?: number;
  message?: string;
}): Promise<void>
```

例子：

```typescript
execute: async ({ items }, context) => {
  for (const [index, item] of items.entries()) {
    await processItem(item)
    await context.mcp?.progress?.({
      progress: index + 1,
      total: items.length,
      message: `Processed ${item.name}`,
    })
  }
  return { done: true }
}
```

## 追踪 {/* #tracing */}

当服务器注册到已配置可观测性的 `Mastra` 实例后，处理 `tools/list`、`tools/call`、`resources/*` 和 `prompts/*` 请求时，每个请求都会生成一个 `MCP_SERVER_REQUEST` 根 span。`executeTool()` 也会生成同样的 span，因此 Studio 的 MCP 服务器页面上的调用会和 MCP 客户端发起的调用一样受到追踪。

span 以方法和目标命名，例如 `tools/call lookupOrder`。它以请求参数为输入，以响应为输出，并记录服务器名称和版本、协商后的协议版本，以及客户端上报的名称和版本。若 `tools/call` 返回 `isError: true`，该 span 会被标记为失败。作为 Tool 对外提供的 Agent 和 Workflow 会分别在该 span 下挂载 `AGENT_RUN` 和 `WORKFLOW_RUN` span。服务器直接提供的 Tool 不会单独生成 `TOOL_CALL` span，但 Agent 在请求过程中调用的 Tool 仍会生成。

未关联 `mastra` 实例的独立 `MCPServer` 不会生成 span。

### 关联调用方的 Trace {/* #linking-to-the-callers-trace */}

携带 W3C `traceparent` 的请求保留自己的 Trace、根 span 和 Trace 摘要。请求 span 链接到调用方的 span，可沿着该链接从调用方的 Trace 找到 Tool 调用触发的请求。

使用追踪桥接时，请求 span 会在请求到达时处于活动状态的 span 下启动。如果服务器的 HTTP 插桩根据 `traceparent` 请求头延续调用方的 Trace，请求就会加入该 Trace。此时，链接指向同一 Trace 中的 span。

服务器按以下顺序从两个位置读取 `traceparent` 和 `tracestate`。

1. 请求的 `_meta`。Agent 或 Workflow 通过 HTTP 或 stdio 发起受追踪的 Tool 调用时，`MCPClient` 会在此处发送 `traceparent`。
2. HTTP 请求头。非 Mastra 调用方的 OpenTelemetry HTTP 插桩会通过请求头发送这两个字段。

请求 span 还会将有效的 `traceparent` 记为 `callerTraceparent` 属性，并将一同发送的 `tracestate` 记为 `callerTracestate`，后者最多保留 512 个字符。不支持 span 链接的导出器仍可携带这些属性。请求缺少有效的 `traceparent` 时，不会生成链接或调用方属性。span 的输入不包含这些追踪字段。

链接也支持从调用方指向服务器。如果 `tools/call` 请求携带 `traceparent`，响应中的 `_meta.mastra.traceparent` 会标识请求 span，`MCPClient` 会在自己的 Tool 调用 span 中添加指向该 span 的链接。调用方未发送追踪上下文时，响应不会返回此追踪信息。

Mastra 将链接与 span 一同保存。OpenTelemetry 导出器、[`OtelBridge`](/integrations/observability/opentelemetry#bridge)、`DatadogBridge`、`DatadogExporter` 和 `SentryExporter` 都会将它们作为 span 链接发送。`DatadogExporter` 和 `SentryExporter` 会为 span 分配自己的 ID，因此相应的后端无法解析两个 Mastra span 之间的链接。

## 通知传递 {/* #notification-delivery */}

请求内的通知（`context.mcp.log()`、`context.mcp.progress()`）通过触发通知的请求流传输，因此只有发起该请求的调用方会收到。独立于请求生命周期的通知（`resources.notifyListChanged()`、`prompts.notifyListChanged()`、`toolActions.notifyListChanged()`、`resources.notifyUpdated()`）通过相关客户端各自保持打开的 `subscriptions/listen` 流传递。`resources.notifyUpdated()` 只会通知订阅流中包含该资源 URI 的客户端。列表变更通知会发送给监听该列表的所有客户端。使用 stdio 时，由连接本身承载该流。

## OAuth 保护 {/* #oauth-protection */}

使用 `createOAuthMiddleware` 函数，可以按照 [MCP 授权规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)，通过 OAuth 身份验证保护 MCP 服务器。

```typescript
import http from 'node:http'
import { MCPServer, createOAuthMiddleware, createStaticTokenValidator } from '@mastra/mcp'

const mcpServer = new MCPServer({
  id: 'protected-server',
  name: 'Protected MCP Server',
  version: '1.0.0',
  tools: {/* your tools */},
})

// Create OAuth middleware
const oauthMiddleware = createOAuthMiddleware({
  oauth: {
    resource: 'https://mcp.example.com/mcp',
    authorizationServers: ['https://auth.example.com'],
    scopesSupported: ['mcp:read', 'mcp:write'],
    resourceName: 'My Protected MCP Server',
    validateToken: createStaticTokenValidator(['allowed-token-1']),
  },
  mcpPath: '/mcp',
})

// Create HTTP server with OAuth protection
const httpServer = http.createServer(async (req, res) => {
  const url = new URL(req.url || '', 'https://mcp.example.com')

  // Apply OAuth middleware first
  const result = await oauthMiddleware(req, res, url)
  if (!result.proceed) return // Middleware handled response (401, metadata, etc.)

  // Token is valid, proceed to MCP handler
  await mcpServer.startHTTP({ url, httpPath: '/mcp', req, res })
})

httpServer.listen(3000)
```

中间件会自动执行以下操作。

* 在 `/.well-known/oauth-protected-resource` 提供**受保护资源元数据**（RFC 9728）。
* 需要身份验证时，返回 `401 Unauthorized` 和相应的 `WWW-Authenticate` 响应头。
* 使用您提供的验证器验证持有者令牌。

### 令牌验证 {/* #token-validation */}

在生产环境中，请对令牌执行适当的验证：

```typescript
import { createOAuthMiddleware, createIntrospectionValidator } from '@mastra/mcp'

// Option 1: Token introspection (RFC 7662)
const middleware = createOAuthMiddleware({
  oauth: {
    resource: 'https://mcp.example.com/mcp',
    authorizationServers: ['https://auth.example.com'],
    validateToken: createIntrospectionValidator('https://auth.example.com/oauth/introspect', {
      clientId: 'mcp-server',
      clientSecret: 'secret',
    }),
  },
})

// Option 2: Custom validation (JWT, database lookup, etc.)
const customMiddleware = createOAuthMiddleware({
  oauth: {
    resource: 'https://mcp.example.com/mcp',
    authorizationServers: ['https://auth.example.com'],
    validateToken: async (token, resource) => {
      const decoded = await verifyJWT(token)
      if (!decoded) {
        return { valid: false, error: 'invalid_token' }
      }
      return {
        valid: true,
        scopes: decoded.scope?.split(' ') || [],
        subject: decoded.sub,
      }
    },
  },
})
```

如果验证函数能够确定用户标识，请返回 `subject`。服务器会将 `input_required` 的续接状态绑定到该标识，确保使用同一个 OAuth 客户端的不同用户各自拥有独立的续接状态。

## 身份验证上下文 {/* #authentication-context */}

使用 HTTP 传输时，Tool 可以通过 `context.mcp.extra` 访问请求元数据。你可以将身份验证信息、用户上下文和 HTTP 中间件中的自定义数据传给 MCP Tool。

### 数据如何传递 {/* #how-it-works */}

在 HTTP 中间件中写入 `req.auth` 的数据，可以在 Tool 中通过 `context.mcp.extra.authInfo` 读取，也可以在资源和提示词的回调中通过 `requestContext.get('authInfo')` 读取：

```text
req.auth = { ... }  →  context.mcp.extra.authInfo = { ... }
```

### 为 FGA 映射身份验证数据 {/* #map-auth-data-for-fga */}

将 `MCPServer` 注册到配置了细粒度授权（FGA）Provider 的 Mastra 实例后，Mastra 会在列出或调用 Tool 之前检查 `requestContext.get('user')`。HTTP 传输层通过 `extra.authInfo` 传递经验证的身份数据，因此请使用 `mapAuthInfoToUser` 将其映射为 FGA Provider 所需的用户数据结构。

```typescript
const server = new MCPServer({
  id: 'my-server',
  name: 'My Server',
  version: '1.0.0',
  tools: { getUserData },
  mapAuthInfoToUser: ({ authInfo }) => {
    const user = authInfo as {
      extra?: {
        userId?: string
        organizationMembershipId?: string
      }
    }

    if (!user.extra?.userId) {
      return null
    }

    return {
      id: user.extra.userId,
      organizationMembershipId: user.extra.organizationMembershipId,
    }
  },
})
```

### 为 MCP Tool 单独设置 FGA 范围 {/* #scope-mcp-tool-fga-separately */}

如果 MCP 客户端所需的授权范围与内部 Agent 或 Workflow 执行 Tool 时所用的范围不同，请设置 `fga.resourceMapping` 和 `fga.permissionMapping`。这两项覆盖设置仅适用于此 MCP 服务器对 `tools/list` 和 `tools/call` 执行的授权检查。

```typescript
import { MastraFGAPermissions } from '@mastra/core/auth/ee'

const server = new MCPServer({
  id: 'my-server',
  name: 'My Server',
  version: '1.0.0',
  tools: { getUserData },
  mapAuthInfoToUser: ({ authInfo }) => {
    const user = authInfo as {
      extra?: {
        userId?: string
        organizationMembershipId?: string
      }
    }

    if (!user.extra?.userId) {
      return null
    }

    return {
      id: user.extra.userId,
      organizationMembershipId: user.extra.organizationMembershipId,
    }
  },
  fga: {
    resourceMapping: {
      tool: {
        fgaResourceType: 'user',
        deriveId: ({ user }) => (user as { id: string }).id,
      },
    },
    permissionMapping: {
      [MastraFGAPermissions.TOOLS_EXECUTE]: 'read',
    },
  },
})
```

### 设置身份验证中间件 {/* #setting-up-authentication-middleware */}

要将数据传给 Tool，请在调用 `server.startHTTP()` 之前，在 HTTP 服务器中间件中为 Node.js 请求对象的 `req.auth` 赋值。

```typescript
import express from 'express'

type MCPAuthenticatedRequest = express.Request & {
  auth?: {
    token: string
    clientId: string
    scopes: string[]
    expiresAt?: number
    extra?: Record<string, unknown>
  }
}

const app = express()

// Auth middleware - set req.auth before the MCP handler
app.use('/mcp', async (req, res, next) => {
  const authorization = req.headers.authorization

  if (!authorization?.startsWith('Bearer ')) {
    res.status(401).json({ error: 'Missing bearer token' })
    return
  }

  const token = authorization.slice('Bearer '.length)

  try {
    const user = await verifyToken(token)

    // This entire object becomes context.mcp.extra.authInfo
    const authenticatedRequest = req as MCPAuthenticatedRequest
    authenticatedRequest.auth = {
      token,
      clientId: user.clientId,
      scopes: user.scopes,
      expiresAt: user.expiresAt,
      extra: {
        sub: user.userId,
        email: user.email,
      },
    }
    next()
  } catch {
    res.status(401).json({ error: 'Invalid or expired token' })
  }
})

app.all('/mcp', async (req, res) => {
  const url = new URL(req.url, `http://${req.headers.host}`)
  await server.startHTTP({ url, httpPath: '/mcp', req, res })
})
```

将 `extra.sub`（或 `extra.subject`）设为用户标识。服务器会用该标识将 `input_required` 的续接状态绑定到对应用户。

### 在 Tool 中读取身份验证数据 {/* #accessing-auth-data-in-tools */}

在 Tool 的执行函数中，可以通过 `context.mcp.extra.authInfo` 读取 `req.auth` 对象：

```typescript
execute: async (inputData, context) => {
  // Access the auth data you set in middleware
  const authInfo = context.mcp?.extra.authInfo

  if (!authInfo?.extra?.sub) {
    return { error: 'Authentication required' }
  }

  // Use the auth data
  console.log('User ID:', authInfo.extra.sub)
  console.log('Email:', authInfo.extra.email)

  // Use a credential intended for the API being called, not the MCP token.
  // See https://mastra.ai/docs/guides/mcp-authentication-authorization#access-upstream-services-safely
  const credential = await apiCredentials.getForUser(authInfo.extra.sub as string)

  const response = await fetch('/api/data', {
    headers: { Authorization: `Bearer ${credential.token}` },
    signal: context.mcp?.extra.signal,
  })

  return response.json()
}
```

### 将 `RequestContext` 传给 Agent {/* #passing-requestcontext-through-to-agent */}

`context.requestContext` 已包含 `authInfo` 和映射后的 `user`。Tool 调用 Agent 时，可以直接传入该上下文：

```typescript
execute: async (inputData, context) => {
  const authInfo = context.mcp?.extra.authInfo

  if (!authInfo?.extra?.sub) {
    return { error: 'Authentication required' }
  }

  const agent = context.mastra?.getAgentById('some-agent-id')

  if (!agent) {
    return { error: "Agent 'some-agent-id' not found" }
  }

  const response = await agent.generate(prompt, { requestContext: context.requestContext })

  return response.text
}
```

### `extra` 对象 {/* #the-extra-object */}

`context.mcp.extra` 对象包含以下属性：

| 属性 | 描述 |
| - | - |
| `authInfo` | 在中间件中写入 `req.auth` 的数据 |
| `requestId` | 当前请求的 JSON-RPC ID |
| `signal` | 用于取消请求的 AbortSignal |
| `_meta` | 客户端发送的请求元数据，包括 W3C 跟踪字段、用于显式指定日志级别的 `io.modelcontextprotocol/logLevel` 和 `progressToken` |
| `sendNotification`, `sendRequest` | 已弃用。协议不支持由服务器发起请求，因此调用任一方法都会抛出错误，并在错误消息中指出应改用 `context.mcp.log()`、`context.mcp.progress()` 或 `context.suspend()`。 |

### 完整示例 {/* #complete-example */}

安装 [`jose`](https://github.com/panva/jose)，以便使用身份 Provider 的 JSON Web 密钥集（JWKS）验证 JSON Web 令牌（JWT）：

```shell npm2yarn
npm install jose
```

以下示例先验证令牌的签名、签发者、受众、算法、过期时间和必需的声明，再将令牌中的用户数据传给 Tool：

```typescript
import express from 'express'
import { createRemoteJWKSet, jwtVerify } from 'jose'
import { MCPServer } from '@mastra/mcp'
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

type MCPAuthenticatedRequest = express.Request & {
  auth?: {
    token: string
    clientId: string
    scopes: string[]
    expiresAt?: number
    extra?: Record<string, unknown>
  }
}

const issuer = process.env.JWT_ISSUER
const audience = process.env.JWT_AUDIENCE
const jwksUri = process.env.JWT_JWKS_URI

if (!issuer || !audience || !jwksUri) {
  throw new Error('JWT_ISSUER, JWT_AUDIENCE, and JWT_JWKS_URI are required')
}

const jwks = createRemoteJWKSet(new URL(jwksUri))

const verifyToken = async (token: string) => {
  const { payload } = await jwtVerify(token, jwks, {
    issuer,
    audience,
    algorithms: ['RS256'],
    requiredClaims: ['exp'],
  })

  const clientId =
    typeof payload.client_id === 'string'
      ? payload.client_id
      : typeof payload.azp === 'string'
        ? payload.azp
        : undefined

  if (!payload.sub || typeof payload.email !== 'string' || !clientId || !payload.exp) {
    throw new Error('Token must contain sub, email, exp, and client_id or azp claims')
  }

  return {
    userId: payload.sub,
    clientId,
    email: payload.email,
    expiresAt: payload.exp,
    scopes: typeof payload.scope === 'string' ? payload.scope.split(' ') : [],
  }
}

// 1. Define your tool that uses auth context
const getUserData = createTool({
  id: 'get-user-data',
  description: 'Fetches data for the authenticated user',
  inputSchema: z.object({}),
  execute: async (inputData, context) => {
    const authInfo = context.mcp?.extra.authInfo

    if (!authInfo?.extra?.sub) {
      return { error: 'Authentication required' }
    }

    // Access the data you set in middleware
    return {
      userId: authInfo.extra.sub,
      email: authInfo.extra.email,
    }
  },
})

// 2. Create the MCP server with your tools
const server = new MCPServer({
  id: 'my-server',
  name: 'My Server',
  version: '1.0.0',
  tools: { getUserData },
})

// 3. Set up Express with auth middleware
const app = express()

app.use('/mcp', async (req, res, next) => {
  const authorization = req.headers.authorization

  if (!authorization?.startsWith('Bearer ')) {
    res.status(401).json({ error: 'Missing bearer token' })
    return
  }

  const token = authorization.slice('Bearer '.length)

  try {
    const user = await verifyToken(token)

    // This entire object becomes context.mcp.extra.authInfo
    const authenticatedRequest = req as MCPAuthenticatedRequest
    authenticatedRequest.auth = {
      token,
      clientId: user.clientId,
      scopes: user.scopes,
      expiresAt: user.expiresAt,
      extra: {
        sub: user.userId,
        email: user.email,
      },
    }
    next()
  } catch {
    res.status(401).json({ error: 'Invalid or expired token' })
  }
})

app.all('/mcp', async (req, res) => {
  const url = new URL(req.url, `http://${req.headers.host}`)
  await server.startHTTP({ url, httpPath: '/mcp', req, res })
})

app.listen(3000)
```

## 事件（实验性） {/* #events-experimental */}

:::warning

事件功能实现了 MCP 扩展草案 [SEP-3415](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415)。传输格式和此 API 可能在任何版本中变更。

:::

完整操作示例请参阅 [MCP 事件](/docs/connections/mcp#mcp-events)。

`events` 选项允许客户端订阅服务器上发生的事件，例如工单创建或构建完成。服务器声明支持 `io.modelcontextprotocol/events` 扩展，并通过 stdio 和 Streamable HTTP 响应 `events/list`、`events/poll` 和 `events/stream`。配置 [`eventsOptions.webhook`](#webhook-delivery) 后，服务器还会响应 `events/subscribe` 和 `events/unsubscribe`，并通过 POST 将事件发送到客户端的 Webhook URL。

用 `defineEvent()` 声明每种事件类型，再用 `server.events.emit()` 发布事件：

```typescript
import { MCPServer, defineEvent } from '@mastra/mcp'
import { z } from 'zod'

const server = new MCPServer({
  id: 'tickets',
  name: 'Tickets',
  version: '1.0.0',
  tools: {},
  events: {
    'ticket.created': defineEvent({
      description: 'A ticket was created',
      inputSchema: z.object({ project: z.string().optional() }),
      payloadSchema: z.object({ id: z.string(), project: z.string() }),
      match: (args, data) => !args.project || data.project === args.project,
    }),
  },
})

await server.events.emit('ticket.created', { id: 't-1', project: 'web' })
```

使用 `{ project: 'web' }` 订阅的客户端会收到这次事件，使用 `{ project: 'api' }` 订阅的客户端则不会。

`match` 根据客户端选择的参数筛选事件，无法控制订阅权限。要限制调用方，请添加 `authorize`。它接收经过验证的参数以及调用方的 `requestContext`。设置 `mapAuthInfoToUser` 后，该上下文会包含 `user`：

```typescript
const ticketCreated = defineEvent({
  inputSchema: z.object({ project: z.string() }),
  payloadSchema: z.object({ id: z.string(), project: z.string() }),
  match: (args, data) => data.project === args.project,
  authorize: ({ arguments: args, requestContext }) => {
    const user = requestContext.get('user') as { projects: string[] } | undefined
    return user?.projects.includes(args.project) ?? false
  },
})
```

每次调用 `events/poll`、打开 `events/stream` 或通过 `events/subscribe` 创建或续订 Webhook 订阅时，都会执行 `authorize`。已打开的流要等到重新连接才会再次检查，Webhook 订阅则要等到下次续订。调用方失去权限后，在再次检查前仍会收到事件。FGA 不适用于事件，请使用 `authorize` 限制事件访问权限。

### 投递模式 {/* #delivery-modes */}

事件类型可用的投递模式取决于事件来源：

| 定义 | 公布的 `delivery` | 事件来源 |
| - | - | - |
| 未定义 `poll` | `['push', 'poll']`，配置 `eventsOptions.webhook` 后另有 `'webhook'` | `server.events.emit()`。轮询读取内存缓冲区。 |
| `poll` | `['poll']` | 每次 `events/poll` 请求都会调用你提供的 `poll` 函数。 |

使用 `poll` 数据源的类型不支持推送。不能通过 `delivery` 为其添加 `'push'`，对其调用 `server.events.emit()` 也会抛出异常。客户端只能通过 `events/list` 获取支持的模式，因此服务器启动后公布的模式不会改变。要推送事件，请定义不含 `poll` 的类型并发布该类型的事件。

请求该类型未公布的模式会返回 `-32026`。请求未知事件名称会返回 `-32023`。

### 推送流 {/* #push-streams */}

每个 `events/stream` 请求对应一个订阅。服务器先发送 `notifications/events/active`，之后每次发生匹配的事件都会发送一条 `notifications/events/event`。每条通知都在 `_meta["io.modelcontextprotocol/subscriptionId"]` 中携带请求 ID。如果请求包含 `cursor`，服务器会先重放缓冲区中位于游标之后的事件，再发送实时事件。如果游标早于缓冲区中最早的事件，`active` 会报告 `truncated: true`。

如果流在 `heartbeatIntervalMs` 内没有发送其他消息，就会发送携带当前游标的 `notifications/events/heartbeat`。取消请求或调用 `server.close()` 会结束流，并释放监听器和定时器。

### Webhook 投递 {/* #webhook-delivery */}

配置 `eventsOptions.webhook` 后，客户端可以通过 `events/subscribe` 注册回调 URL。服务器使用客户端的密钥，按照 [Standard Webhooks](https://www.standardwebhooks.com/) 规范以 HMAC-SHA256 对每个匹配的事件签名，再通过 POST 发送到该 URL。

```typescript
const server = new MCPServer({
  id: 'tickets',
  name: 'Tickets',
  version: '1.0.0',
  tools: {},
  events: {
    'ticket.created': defineEvent({ payloadSchema: z.object({ id: z.string() }) }),
  },
  eventsOptions: {
    webhook: { ttl: { defaultMs: 30 * 60_000 } },
  },
})
```

服务器执行以下规则：

* **身份验证：** Webhook 订阅要求调用方通过身份验证。如果请求缺少 `authInfo`，`events/subscribe` 会返回 `-32024`。订阅由调用方、URL、事件名称和参数共同标识，因此使用相同条件再次调用 `events/subscribe` 会续订原有订阅，并返回相同的 `id`。
* **授权：** 每次订阅和续订都会执行 `authorize`。如果续订被拒绝，服务器会移除订阅，并停止通过 POST 发送后续事件。Mastra 客户端无法区分此处的 `-32024` 和调用方未通过身份验证时的同名错误，因此在默认投递模式下会报告 `MCP_EVENTS_WEBHOOK_UNAVAILABLE`，尝试推送，随后以同一个 `-32024` 拒绝请求。
* **回调 URL：** URL 必须使用 `https`。解析得到的每个地址都必须可在公网路由。环回、私有、链路本地及其他特殊用途地址段会被拒绝，并返回 `-32602` 和 `data.reason`。每次投递前都会重新检查，投递请求会连接到通过检查的地址，以防止 DNS 重绑定。请求不会跟随重定向。
* **端点验证：** 首次向 URL 投递前，服务器会通过 POST 发送带签名的验证质询，端点必须原样返回。端点验证失败或无法访问时，`events/subscribe` 会返回 `-32027`，并通过 `data.reason` 给出原因，例如 `challenge_failed` 或 `timeout`。验证结果按调用方和 URL 缓存。`allowedUrls` 接受的 URL 会跳过此步骤。
* **有效期：** 如果客户端未续订，订阅会在返回的 `refreshBefore` 时间到期。请求中的 `ttlMs` 会被限制在 `ttl` 指定的范围内。
* **重试：** 每次事件投递都采用指数退避重试，直到收到 `2xx` 确认、达到 `retry.maxAttempts` 次尝试，或超过 `retry.maxWindowMs`。收到 `410` 或 `413` 响应时，停止重试该事件。每个请求体中的 `cursor` 只会越过已确认收讫或已放弃投递的事件。
* **暂停：** 如果某个订阅在 `suspend.windowMs` 内的大部分投递失败，服务器会暂停该订阅的投递，并在下次续订时于 `deliveryStatus` 中报告 `active: false`。续订会恢复投递。
* **错误：** 客户端只能看到 `timeout` 或 `http_5xx` 等失败类别，无法看到端点的响应体或响应头。

### `server.events.emit(name, data, options?)` {/* #servereventsemitname-data-options */}

记录事件，将其投递到匹配的推送流和 webhook 订阅，并返回事件及其 `eventId`、`timestamp` 和 `cursor`。`options.eventId` 和 `options.timestamp` 分别覆盖默认的随机 UUID 和当前时间。如果 `name` 未配置、`data` 未通过 `payloadSchema` 验证，或该事件类型配置了 `poll` 来源，此方法会抛出错误。

`server.events.list()` 返回 `events/list` 提供的事件描述符。

### 限制 {/* #limits */}

* 发出的事件保留在发出它们的进程中。推送流、webhook 订阅和基于缓冲区的轮询只能获取同一个 `MCPServer` 实例发出的事件。因此，无服务器部署或多实例部署需要由共享存储支持的 `poll` 来源。
* 缓冲区位于内存中。服务器重启后会将旧游标视为存在事件缺口，并报告 `truncated: true`。
* Webhook 投递状态（待重试的投递、暂停状态和验证结果）保存在内存中，并在客户端刷新订阅时重建。
* 事件列表变更通知依赖 `subscriptions/listen` 上的 `eventsListChanged` 筛选条件。`@mastra/mcp` 所用的 MCP TypeScript SDK 版本尚不支持此筛选条件。在获得支持之前，服务器不会声明 `listChanged`，也不会发送 `notifications/events/list_changed`。客户端应重新调用 `events/list` 以获取更新后的事件类型。

## 任务（实验） {/* #tasks-experimental */}

:::warning

任务功能实现了 SEP-2663 定义的 MCP 扩展 `io.modelcontextprotocol/tasks`。此 API 可能在任何版本中发生变化。

:::

`tasks` 选项允许 Tool、Workflow（`run_*`）或 Agent（`ask_*`）以任务响应 `tools/call`。客户端会立即收到任务句柄，然后轮询 `tasks/get`，直到任务完成。请求结束后仍可获取结果，任务也不受 HTTP 超时限制。只要其中至少一项可以用任务响应，服务器就会声明支持该扩展，并通过 stdio 和 Streamable HTTP 处理 `tasks/get`、`tasks/update` 和 `tasks/cancel`。如果未设置 `tasks` 选项，服务器既不声明支持该扩展，也不处理这些请求。

只有在请求中声明该扩展的客户端才会收到任务。其他客户端会收到同步响应，但列在 `required` 中的 Tool 除外。

```typescript
import { MCPServer } from '@mastra/mcp'

const server = new MCPServer({
  id: 'reports',
  name: 'Reports',
  version: '1.0.0',
  tools: { buildReport, lookupCustomer },
  tasks: {
    tools: {
      buildReport: 'always',
      lookupCustomer: { mode: 'auto', syncWindowMs: 1000 },
    },
  },
})
```

### 模式 {/* #modes */}

| 模式 | 客户端已声明扩展 | 客户端未声明扩展 |
| - | - | - |
| `'off'` | 同步响应。 | 同步响应。 |
| `'always'` | 立即返回任务句柄。 | 同步响应。如果 Tool 列在 `required` 中，则返回错误 `-32021`。 |
| `'auto'` | 如果 Tool 在 `syncWindowMs` 内执行完毕，则同步响应。否则返回任务句柄，当前运行继续执行。 | 同步响应。如果 Tool 列在 `required` 中，则返回错误 `-32021`。 |

服务器会在响应前创建任务，因此客户端收到任务句柄后可以立即成功调用 `tasks/get`。

### 访问任务 {/* #access-to-tasks */}

任务 ID 是无法猜测的持有者令牌，每个任务都绑定到创建它的调用者。识别调用者的方式与[续接状态](#continuation-state)相同，依据 OAuth 主体、映射得到的 `user` 或持有者令牌的哈希值。其他调用者请求此任务，或调用者被 `authorize` 拒绝时，都会收到错误 `-32602`，与请求不存在的任务 ID 时相同。客户端无法通过 MCP 列出任务。

### Studio 中的任务 {/* #tasks-in-studio */}

配置了 `tasks` 的服务器会在 Studio 页面显示哪些 Tool 以任务方式运行（`always` 或 `auto`），以及 `required` 和 `recover` 设置。页面按从新到旧的顺序列出所有调用者的任务，并显示状态、发起任务的客户端、待答复的输入请求和过期时间。你可以按状态、Tool 或客户端筛选，加载更早的任务，或粘贴客户端显示的 MCP 任务 ID 来打开任务。打开后可以查看结果或错误、取消任务，或答复它正在等待的输入请求。取消和答复分别执行与 `tasks/cancel` 和 `tasks/update` 相同的代码，但会跳过 `authorize`。

* Studio 通过其 ID 的哈希值来识别任务，并通过其身份的哈希值来识别调用者。两者都不能通过 MCP 使用，并且原始值永远不会发送到 Studio。您粘贴的任务 ID 将在请求正文中发送并在服务器上进行哈希处理。
* 客户端显示为其客户端 ID 以及令牌的主题或用户 ID。仅通过其令牌标识的调用者会显示令牌哈希的短前缀。标签从来都不是凭证。
* 使用 RBAC Provider 时，列出和查找任务需要 `mcp:read`。取消任务和答复输入请求需要 `mcp:write`。默认角色中只有 `admin` 拥有此权限，`member` 和 `viewer` 均无此权限。缺少此权限时，Studio 仍会显示任务，但不会提供这两项操作。
* 只有没有资源范围的 Studio 会话才能获取列表。 MCP 调用者和 Mastra 资源是独立的身份，因此资源范围内的会话不会获取任何任务，也无法取消或应答任务。
* 内置任务存储支持列出任务。自定义 `store` 也必须实现 `MCPTaskStoreAdmin`（`list`、`updateByKey`、`cancelByKey`），否则 Studio 会提示无法列出该存储中的任务。

### 打开任务上限 {/* #open-task-caps */}

任务处于 `working` 或 `input_required` 状态时计为未完成任务。完成、失败、取消或过期后，不再计入。如果一次调用会超出 `maxOpenTasksPerClient` 或 `maxOpenTasks`，服务器就不会创建任务：

* `'always'` 模式的 Tool 不会运行。调用返回 `isError: true`，以及类似 `Too many open tasks for this client (limit 100). Wait for one to finish or cancel one.` 的消息。
* 如果 `'auto'` 模式的 Tool 在同步窗口结束时仍在运行，它会继续在原请求中运行并同步返回结果，行为与未启用任务时相同。取消请求仍会中止运行。
* `run_<workflow>` 和 `ask_<agent>` 任务同样计入这些上限和[保留任务上限](#retained-task-caps)。`'always'` 模式的 Workflow 和 Agent 都不会启动。暂停的 `'auto'` 模式 Workflow 运行只能通过任务接收答复，因此达到上限时，服务器会取消运行并返回 `isError: true`。

两个值都必须是正整数。服务器通过 `limits` 将它们传给 `store.create()`，存储在超限时抛出 `MCPTaskLimitError`。忽略 `limits` 的自定义存储不会限制未完成任务的数量。

### 保留的任务上限 {/* #retained-task-caps */}

内存存储会将已结束任务的结果保留到 `ttlMs` 到期后再过一分钟，供客户端读取。结束任务会腾出一个未完成任务名额，但结果仍占用内存。若不限制保留数量，客户端连续运行大量短任务可能导致内存占用持续增长。`maxRetainedTasksPerClient` 和 `maxRetainedTasks` 限制存储中保留的任务数量，包括未完成和已结束的任务。

* 超出保留上限的调用与超出未完成任务上限时处理相同。`'always'` 模式的 Tool 返回 `isError: true` 和类似 `Too many recent tasks for this client (limit 1000). Try again once older tasks expire.` 的消息。`'auto'` 模式的 Tool 同步返回结果。
* 已创建的任务保留完整的 `ttlMs`。存储不会为了腾出名额而提前删除结果。移除任务后才会腾出名额。
* 未完成的任务也计入保留数量。每对上限只设置其中一项时，另一项的默认值会相应调整。将 `maxRetainedTasksPerClient` 降至 100 以下时，默认的 `maxOpenTasksPerClient` 会降至相同数值。将 `maxOpenTasks` 提高到 10000 以上时，默认的 `maxRetainedTasks` 会相应提高。如果同时设置两项且保留上限低于未完成上限，创建服务器时会抛出错误。

只有内存存储会执行保留上限。Mastra 存储将已结束任务的结果保存在数据库中，参见[跨实例任务](#tasks-across-instances)。这些任务仍受未完成任务上限约束，但不受保留上限约束。将已结束任务的结果另行保存的自定义存储也可以忽略保留上限。

### 在任务中请求输入 {/* #asking-for-input-inside-a-task */}

Tool 在任务中调用 `suspend()` 后，任务进入 `input_required` 状态。输入请求使用 Tool 的 `resumeSchema` 生成表单，与同步调用时相同。客户端通过 `tasks/update` 答复后，服务器会带上 `resumeData` 再次运行 `execute`，与同步调用时一样。请确保 `suspend()` 之前的操作可以安全地重复执行。

输入请求被拒绝或取消时，任务以 `isError: true` 结束。任务会忽略未请求的字段。

### 任务运行收到什么 {/* #what-a-task-run-receives */}

服务器根据创建任务时保存的信息重建任务运行，因此重启后可以重新运行任务。每次运行都会获得保存的请求上下文，且没有 `context.mcp`。唯一的例外是 `'auto'` 模式 Tool 的首次运行，它在同步窗口结束前就已在原请求中启动。

* 保存请求上下文前，服务器会从 `authInfo` 中移除持有者令牌。其他内容原样保存，包括 `authInfo.extra` 和 `mapAuthInfoToUser` 返回的 `user`。不要在其中放入不应由任务存储保留的凭据。
* 值以 JSON 格式保存。运行时读回的是普通对象，因此 `user` 即使原本是类实例，读回后也只是具有相同字段的普通对象。
* 无法保存为 JSON 的字段会被省略，服务器会在创建任务时记录警告。如果省略的是 `user`，后续运行的授权检查会失败。
* 通过 `context.abortSignal` 检测取消，因为任务运行无法使用 `context.mcp`。
* 每次运行都会针对存储的请求上下文再次进行授权，就像每轮同步调用一样。

### 取消和错误 {/* #cancellation-and-errors */}

* `tasks/cancel` 会触发 Tool 的 `abortSignal`，任务以 `cancelled` 结束。Tool 负责自行停止，之后返回的结果会被丢弃。
* Tool 抛出错误时，任务返回 `isError: true` 和序列化后的错误，与同步调用相同。
* 只有服务器无法运行任务时，任务才会以 `failed` 结束，例如 TTL 到期时。

### Workflow 任务 {/* #workflow-tasks */}

每个 `run_<key>` 任务跟踪一次 Workflow 运行。创建任务的 `tools/call` 只启动一次运行，运行有独立的 ID，与任务 ID 不同。

```typescript
const server = new MCPServer({
  id: 'reports',
  name: 'Reports',
  version: '1.0.0',
  workflows: { nightly },
  tasks: {
    workflows: { nightly: { mode: 'auto', syncWindowMs: 1000 } },
  },
})
```

* 运行以 `success` 或 `bailed` 结束时，任务返回与同步调用相同的文本，包含 `status`、`input`、`steps` 和 `result`。
* 运行以 `failed`、`tripwire` 或 `canceled` 结束时，任务返回 `isError: true` 和错误消息。在 `'auto'` 模式下，如果运行在 `syncWindowMs` 内失败，服务器会直接返回相同结果，不创建任务。只有客户端不支持任务扩展或 Workflow 模式为 `'off'` 时，才会收到普通的 `run_` 响应，其中失败的运行不带 `isError`。
* 在 `'auto'` 模式下，如果运行在 `syncWindowMs` 内暂停，它会以任务形式继续，以便请求输入。
* 参数无效时，在创建运行或任务之前就会返回 `isError: true`。
* 步骤暂停后，任务进入 `input_required` 状态。服务器根据该步骤的 `resumeSchema` 生成表单，并使用暂停时的载荷作为提示消息。服务器一次只为一个暂停步骤请求输入。`tasks/update` 将答复作为 `resumeData` 恢复运行。恢复运行需要 Mastra 存储。
* 每次暂停最多恢复一次运行。如果它已经恢复，例如从 Studio 或另一个实例，则答案将被删除，任务将继续运行：当运行再次暂停时，即使在循环中的同一步骤上，任务也会再次询问新的输入请求。从任务外部与任务本身同时到达运行的恢复仍然可以让过时的答案恢复同一步骤的下一个暂停。
* 如果步骤的 `resumeSchema` 无法显示为表单，例如它包含嵌套对象，任务会保持 `working` 状态。可以通过 Studio 等其他方式恢复运行，任务会继续跟踪。在此之前，任务每秒读取一次运行状态。如果使用 Mastra 后台任务，它还会占用一个后台任务名额，跟踪其他实例执行的运行时也是如此。
* 拒绝输入请求、调用 `tasks/cancel` 或 TTL 到期，都可以从任一实例取消运行，包括正在等待输入的运行。如果运行就在处理取消的实例上执行，它会就地停止。如果运行在另一个实例上执行，它会在该实例下次续租任务时停止，约在一个租约周期内。
* 关闭或将任务交给另一个工作线程的服务器会停止跟踪运行，但仍保持运行。另一个实例拾取该任务并跟踪运行直至结束。
* 在 `tasks` 中传入 `store` 时，服务器只会在客户端拒绝输入请求时取消运行。存储处理取消和过期时，应使用 `isWorkflowTaskContext()` 检查任务上下文，然后调用 `mastra.getWorkflow(context.workflowKey).createRun({ runId: context.runId })`，再对返回的运行调用 `run.cancel()`。在执行该运行的进程中，这个句柄指向正在执行的运行，因此 `cancel()` 会将其停止。

执行 Workflow 任务的服务器停止后，Mastra 的 [Workflow 恢复机制](/reference/core/mastra-class)会在下一个启动的实例上继续运行，任务也会在那里继续跟踪。此机制要求 `recovery.workflows` 为默认值 `'auto'`。若设为 `'off'`，任务会保持 `working` 直到 TTL 到期。服务器停止时正在执行的步骤会重新执行，因此请确保步骤可安全重复执行。如果运行从未保存，或跟踪运行的实例再次停止，任务会以 `failed` 结束。

### Agent任务 {/* #agent-tasks */}

`ask_<key>` 任务执行 Agent 的 `generate()`，行为与 Tool 任务相同。`tasks/cancel` 会触发 Agent 的 `abortSignal`，发生错误时任务以 `isError: true` 结束，`recover` 设置同样适用。

如果 Agent 暂停以等待批准调用 Tool 或等待其他输入，任务会以 `isError: true` 结束。任务目前无法答复 Agent 的批准请求。

### 跨实例的任务 {/* #tasks-across-instances */}

在启用了[后台任务](/docs/harness/background-tasks)的 Mastra 实例上注册服务器后，任务会保存在 Mastra 存储中。共享该存储的任一实例都可以运行任务，并响应针对该任务的 `tasks/get`、`tasks/update` 和 `tasks/cancel`。

```typescript
import { Mastra } from '@mastra/core/mastra'
import { LibSQLStore } from '@mastra/libsql'

export const mastra = new Mastra({
  // A local file is only shared by instances on the same host. Use a database every instance can reach.
  storage: new LibSQLStore({ id: 'mastra', url: 'file:./mastra.db' }),
  backgroundTasks: {
    enabled: true,
    // MCP tasks share the per-agent limit (5) unless their owner gets its own
    perOwnerConcurrency: { 'mcp-server:reports': 50 },
  },
  mcpServers: { reports: server },
})
```

* 存储适配器必须支持为每个任务保存 TTL。使用较旧的适配器时，服务器会在注册时退回到内存存储并记录警告。在 `tasks` 中传入的 `store` 始终优先。
* 在注册之前提供任务的服务器将这些任务保存在内存中。注册后，它仍然从该实例的内存中为它们提供服务，并将新任务保留在 Mastra 存储中。
* 在每个实例上注册具有相同 ID 和 Tool 的同一服务器。未注册该服务器的实例无法运行它的任务，会将任务标记为失败。请通过 `id` 设置 ID，或用固定键在 `mcpServers` 中注册服务器。自动生成的 ID 每次启动都会变化，服务器也会记录警告。
* 每项任务同时计入 `mcp-server:<server id>` 的 `perOwnerConcurrency`（未设置时使用 `perAgentConcurrency`）和 `globalConcurrency`。请保留 `backpressure` 的默认值 `'queue'`。使用其他值时，队列已满会导致调用失败。
* 服务器先保存 `tasks/update` 提交的答复，再确认收到。即使接收答复的实例在运行任务前停止，任务仍会恢复。
* 已结束任务的 `ttlMs` 到期约一分钟后，服务器会删除记录，无需启用 `backgroundTasks.cleanup`。服务器只删除自己的记录。`ttlMs: null` 的任务记录会一直保留，直到你删除它。
* 通过对每个实例进行定期扫描，过期任务将失败，而仍在等待的已应答任务将恢复。扫描在服务器注册后开始。甚至在任何客户端向实例发送任务请求之前，实例就会进行扫描。每次扫描最多处理 100 个过期任务并检查 100 个其他打开的任务，然后在下一次扫描中继续处理下一个 100 个任务。仅当插槽空闲时，它才会重新启动已停止实例等待的任务。其余的等待稍后的扫荡。
* `maxOpenTasksPerClient` 和 `maxOpenTasks` 统计所有实例在存储中的未完成任务，因此适用于整个部署。每次调用都在添加任务之前计数，因此同时抵达不同实例的调用可能导致超限，超出的数量最多等于这些并发调用的数量。
* `tasks/cancel` 可以由任一实例接收。如果任务的首次尝试仍在启动它的实例上等待名额，该实例会在下次扫描时停止任务，最多等待一个租约周期（`leaseDurationMs`）。

任务是后台任务存储中的记录，归属的 Agent ID 为 `mcp-server:<server id>`，资源 ID 为 `mcp-server:<server id>:<caller>`：

* 它们不属于任何Agent、线程或内存，因此它们永远不会出现在Agent的对话中。
* `/background-tasks` 路由不会向限定在某个资源范围内的调用者返回这些任务。未限定资源范围的调用者可以列出它们，全局 `onTaskComplete` 和 `onTaskFailed` 钩子也可以。如果钩子只处理 Agent 任务，请检查 `task.agentId.startsWith('mcp-server:')`。
* 服务器通过任务 ID 和调用者主体的哈希值查找记录。记录不保存这两个值的原文，也不保存持有者令牌。记录保存去掉持有者令牌的请求上下文，以及可读的 `metadata.clientLabel`，其中包含客户端 ID 和主体或用户 ID，见下一项。`authInfo.extra` 和 `user` 原样保存，因此任何能读取记录的人都可以看到它们。
* 为了标明发起任务的客户端，`metadata.clientLabel` 保存 OAuth 客户端 ID 和令牌主体（`<client id>:sub:<subject>`），或客户端 ID 和 `mapAuthInfoToUser` 返回的用户 ID（`<client id>:user:<user id>`）。两者均不可用时，保存客户端 ID 和令牌哈希值的前 8 个字符（`<client id>:token:<hash prefix>`）。此标签仅用于调试。服务器根据调用者主体的哈希值匹配调用者。

### 崩溃后恢复 {/* #recovery-after-a-crash */}

当运行任务的实例停止时，另一个实例会在下一次扫描时注意到它：如果实例崩溃，则在任务的租约失效后，或者如果实例关闭并交还租约，则立即停止。在具有后台任务扫描的 Mastra 实例上注册的服务器的每个实例，无论它是否已服务于任务请求。将任务保留在内存中或未注册服务器的实例则不会。接下来会发生什么取决于`recover`:

* `recover: false`（默认）：任务以 `failed` 结束，错误消息为 `task lost: the server restarted while it was running`。`execute` 不会执行第二次。
* `recover: true`：另一个实例会从头重新运行一次 `execute`。仅对可安全重复运行的 Tool 启用此选项。

设置 `recover: true` 后，Tool 之外的原因导致执行失败时也适用同一次重试，例如记录任务需要输入时写入存储失败。Tool 自身报错时不会重试，任务会返回带有 `isError` 的结果。

`recover`不会影响等待输入的任务：无论哪种方式，回答它都会在任何实例上恢复它。

### 追踪 {/* #tracing-1 */}

每个任务对应一条 Trace。创建任务的 `tools/call` 是根 Span，在任务启动后正常结束。Tool 的每次运行都是根 Span 下的一个 `task attempt <tool> #<n>` Span，包括在其他实例上继续或恢复的运行。Tool 自身的 Span 嵌套在对应的尝试中。`tasks/update` 和 `tasks/cancel` 请求加入同一条 Trace，`tasks/get` 轮询不会被追踪。

同样的规则适用于 `run_<workflow>` 和 `ask_<agent>` 任务。Workflow 任务的运行位于首次尝试下，在 `'auto'` 模式下则位于根 Span 下。经 `tasks/update` 恢复的每次运行都位于恢复它的尝试下，无论该尝试在哪个实例上执行。Agent 任务的 `agent run` 位于对应的尝试下。Mastra 在崩溃后恢复 Workflow 时，重新启动的运行会创建独立的 Trace。持久化 Workflow 和 Agent 支持跨崩溃追踪。任务中跟踪重启运行的尝试仍留在该任务的 Trace 中。

Span 元数据包含任务详情：`mcpTaskKey`（任务 ID 的 SHA-256 哈希值）、`attempt`、`resumed`、`recovered` 和 `mcpTaskStatus`。Span 不会记录任务 ID 原文。服务器在任务启动时立即写出根 Span。缺少根 Span 的 Trace 不会出现在列表中，因此立即写出可确保实例即使在下次导出前停止，Trace 仍会显示。尝试次数跨实例连续编号，因此即使崩溃时丢失了那次尝试的 Span，恢复后的运行仍会显示为 `#2`。

### 限制 {/* #limits-1 */}

* 未启用 Mastra 后台任务时，任务保存在内存中，进程重启后会丢失。在多实例部署中，针对同一任务的所有 `tasks/*` 请求都必须发往创建该任务的实例。Streamable HTTP 请求通过 `Mcp-Name` 请求头携带任务 ID，负载均衡器可以据此路由。
* 任务句柄应答后发送的进度和日志通知将被丢弃。
