# 动态 Workflow 定义

:::beta

在 API 稳定之前，即使不提升主版本号，也可能出现破坏性变更。

:::

动态 Workflow 定义是兼容 JSON 的 `DynamicWorkflowGraph`，可供 [`Mastra.addDynamicWorkflow()`](/reference/core/addDynamicWorkflow)、存储式 Workflow 的服务器路由及 Client SDK Workflow API 使用。

完整的配置和使用示例见[动态 Workflow](/docs/workflows/dynamic-workflows)。

## 定义字段 {/* #definition-fields */}

|字段 |类型 |必填|描述 |
| - | - | - | - |
|`id` | `string` |是 |唯一的 Workflow ID，也是检索和运行该 Workflow 时使用的 ID。 |
| `description` | `string`|没有 |人类可读的描述 |
|`inputSchema` | `JsonSchema`|是的 |Workflow 输入的 JSON Schema |
|`outputSchema` | `JsonSchema`|是的 |Workflow 输出的 JSON Schema |
|`stateSchema` | `JsonSchema`|没有 |共享 Workflow 状态的 JSON Schema |
|`requestContextSchema` | `JsonSchema`|没有 |从请求上下文读取值的 JSON 架构 |
|`metadata` | `Record<string, unknown>`|没有 |通过存储保存任意 JSON 元数据 |
|`graph` | `SerializedStepFlowEntry[]`|是的 |组成 Workflow 的步骤条目 |

Schema 使用 JSON Schema 而非 Zod，使定义可以经过 JSON 序列化和反序列化。Mastra 在注册 Workflow 时会将每个 Schema 转换为 Zod。

```json
{
  "id": "greeting-workflow",
  "description": "Returns a greeting for the supplied name",
  "inputSchema": {
    "type": "object",
    "properties": { "name": { "type": "string" } },
    "required": ["name"]
  },
  "outputSchema": {
    "type": "object",
    "properties": { "message": { "type": "string" } },
    "required": ["message"]
  },
  "graph": [
    {
      "type": "mapping",
      "id": "create-greeting",
      "mapConfig": "{\"message\":{\"template\":\"Hello, ${initData.name}!\"}}"
    }
  ]
}
```

## 图条目 {/* #graph-entries */}

`graph` 中的条目按顺序运行。每个条目接收前一个条目的输出，第一个条目接收 Workflow 的输入。

|条目类型 |描述 |
| - | - |
|`agent` |调用已注册的 Agent |
| `classifier` |使用已注册的分类器评估数据 |
| `tool` |调用已注册的 Tool |
| `mapping` |在步骤之间重组数据 |
| `workflow` |将已注册的 Workflow 作为嵌套步骤调用 |
| `parallel` |并发运行多个步骤并合并其输出 |
| `conditional` |并发运行所有谓词为真的分支 |
| `foreach` |针对数组输入中的每个元素运行一次步骤 |
| `loop` |在谓词成立期间或直到谓词成立，重复运行步骤 |
| `sleep` |暂停固定时长 |
| `sleepUntil` |暂停到指定日期 |

使用 [`.agent()`](/reference/workflows/workflow-methods/agent)、[`.classifier()`](/reference/workflows/workflow-methods/classifier) 和 [`.tool()`](/reference/workflows/workflow-methods/tool) 的代码定义 Workflow，在序列化后会生成相同的声明式条目。

### 身份和显示字段 {/* #identity-and-display-fields */}

控制流条目接受可选字段来标识和描述条目而不影响执行：

|字段 |类型 |描述 |
| - | - | - |
|`id` | `string` |在编辑和序列化前后用于定位条目的稳定标识。对于 `parallel`、`conditional`、`foreach` 和 `loop` 是可选字段；对于 `mapping`、`sleep` 和 `sleepUntil` 是必填字段。 |
| `description` | `string` |对控制流操作意图的易读描述 |
| `metadata` | `Record<string, unknown>` |存储时保留的任意 JSON 元数据，例如可视化编辑器中的显示标题 |

```json
{
  "type": "parallel",
  "id": "independent-enrichment",
  "description": "Run independent document enrichment tasks concurrently",
  "metadata": { "title": "Independent enrichment" },
  "steps": [
    { "type": "tool", "id": "extract-entities", "toolId": "entity-tool" },
    { "type": "tool", "id": "classify", "toolId": "classify-tool" }
  ]
}
```

这三个字段在存储和重新加载后都会保留，并出现在供 API 和 Studio 使用的 `serializedStepGraph` 中。Agent 和 Tool 步骤分别通过自身的 `description` 和 `options.metadata` 字段携带同类信息。

### Agent步骤 {/* #agent-steps */}

`agent` 条目通过 ID 调用已注册的 Agent。Agent 步骤接受 `{ prompt: string }` 作为输入，默认返回 `{ text: string }`。

```json
{
  "type": "agent",
  "id": "summarize",
  "agentId": "support-agent"
}
```

此处的 `id` 标识 Workflow 中的调用位置。无论 Agent 自身的 ID 是什么，后续步骤都通过 `stepResults.summarize` 访问结果。

添加 `outputSchema`，请求 Agent 返回结构化输出：

```json
{
  "type": "agent",
  "id": "extract-subtopics",
  "agentId": "support-agent",
  "outputSchema": {
    "type": "array",
    "items": {
      "type": "object",
      "properties": { "title": { "type": "string" } },
      "required": ["title"]
    }
  }
}
```

在 Agent 之前使用 `mapping` 条目，从 Workflow 数据构建其 `{ prompt }` 输入。

Agent 条目接受 `options` 对象：

```json
{
  "type": "agent",
  "id": "summarize",
  "agentId": "support-agent",
  "options": { "retries": 2, "metadata": { "team": "support" } }
}
```

步骤描述来自已注册的 Agent。重新加载 Workflow 时，`agent` 条目上设置的 `description` 会被忽略。

只有 `retries` 和 `metadata` 会持久化。存储代码定义的 Workflow 时，函数值选项（如 `onFinish` 和函数值的 `toolChoice`）会被拒绝。其他 Agent 调用选项不会持久化。

### 分类器步骤 {/* #classifier-steps */}

`classifier` 条目使用在 `Mastra` 实例上注册的分类器评估 Workflow 数据。分类器必须在构造时配置问题。

```json
{
  "type": "classifier",
  "id": "classify-ticket",
  "classifierId": "ticket-router",
  "options": {
    "maxRetries": 2,
    "retries": 1,
    "metadata": { "team": "support" }
  }
}
```

分类器评估条目的完整输入。如果需要选取或重组输入，请在前面添加 `mapping` 条目。

分类器输出有两条稳定路径：

* `answers.<question>` 包含带类型的答案。根据问题类型，通过其 `choice`、`score` 或 `probability` 字段进行路由。选项和评分答案可能包含分布信息。被拒绝的问题返回 `{ "type": "refusal" }`，没有 `choice`、`score` 或 `probability`，因此不会匹配针对这些字段的条件。若要明确处理拒绝情况，请将 `answers.<question>.type` 与 `"refusal"` 比较。
* `usage` 包含标准化的 token 用量。

使用现有的 `conditional` 条目根据分类器输出进行路由。例如，后续条件可以将 `{ "path": "stepResults.classify-ticket.answers.route.choice" }` 与 `{ "literal": "billing" }` 比较。

`options` 对象可以包含分类器模型调用的 `maxRetries`、可安全序列化为 JSON 的 `providerOptions`、Workflow 步骤的 `retries` 以及 `metadata`。分类器出错会导致该 Workflow 步骤失败。

### Tool步骤 {/* #tool-steps */}

`tool` 条目通过 `Mastra` 的 `tools` 对象中的注册键调用 Tool。Mastra 注册 Workflow 时，会从注册表中解析该 Tool 的输入和输出 Schema。

```json
{
  "type": "tool",
  "id": "lookup",
  "toolId": "lookup-customer"
}
```

Tool 条目与 Agent 条目一样，接受可选的 `description` 和 `options` 字段。只有 `retries` 和 `metadata` 会持久化。

### 绘图步骤 {/* #mapping-steps */}

`mapping` 条目用于重组数据。其 `mapConfig` 是编码了一个对象的 JSON 字符串。对象的每个键都会成为步骤输出中的键，每个描述符指定一个数据来源。

直接调用 [`Mastra.addDynamicWorkflow()`](/reference/core/addDynamicWorkflow) 时，`mapConfig` 也可以接收对象本身。Mastra 会在注册和存储定义前将其编码为 JSON 字符串，因此两种写法最终存储的记录相同。已存储的定义始终使用 JSON 字符串形式。

|描述符|描述 |
| - | - |
|`{ "value": ... }` |固定的 JSON 值 |
| `{ "template": "..." }` |由 `${...}` 占位符构成的字符串 |
| `{ "initData": true, "path": "a.b" }` |来自 Workflow 输入的值 |
| `{ "step": "step-id", "path": "a.b" }` |来自前面步骤输出的值 |
| `{ "requestContextPath": "a.b" }` |来自请求上下文的值 |

`step` 数据来源也接受由步骤 ID 组成的数组：

```json
{ "step": ["escalate", "auto-reply"], "path": "text" }
```

数组中第一个具有非空结果的步骤提供该值。这样可以选取在 `conditional` 条目之后实际运行的分支。

模板会根据 `initData`、`inputData`、`state`、`requestContext` 和 `stepResults.<step-id>` 解析占位符：

```json
{
  "type": "mapping",
  "id": "build-prompt",
  "mapConfig": "{\"prompt\":{\"template\":\"Summarize this request: ${initData.request}\"}}"
}
```

模板解析得到的对象和数组会转为 JSON 字符串。已有结果中的 `null` 值会呈现为空字符串。如果模板引用了没有成功输出的步骤，运行将失败。

映射条目必须位于图的顶层，不能放在 `parallel`、`conditional`、`foreach` 或 `loop` 容器内。

### 嵌套 Workflow 步骤 {/* #nested-workflow-steps */}

`workflow` 条目调用另一个已注册的 Workflow。目标 Workflow 可以由代码定义，也可以是已存储的定义。

```json
{
  "type": "workflow",
  "id": "lookup-first",
  "workflowId": "lookup-customer-workflow"
}
```

`id` 标识调用位置。同一个嵌套 Workflow 可以使用不同的调用位置 ID 多次出现，后续步骤可通过 `stepResults.<id>` 访问各次调用的结果。`workflow` 条目还接受可选的 `description`。

### 并行条目 {/* #parallel-entries */}

`parallel` 条目并发运行多个单独步骤，并将输出合并为以步骤 ID 为键的对象。

```json
{
  "type": "parallel",
  "steps": [
    { "type": "tool", "id": "first", "toolId": "lookup-customer" },
    { "type": "tool", "id": "second", "toolId": "lookup-customer" }
  ]
}
```

每个子条目必须是 `agent`、`classifier`、`tool` 或 `workflow` 条目。所有子条目都直接接收并行条目的输入。

### 有条件条目 {/* #conditional-entries */}

`conditional` 条目为每个步骤配对一个声明式谓词，并运行所有谓词为真的分支。

```json
{
  "type": "conditional",
  "steps": [
    { "type": "agent", "id": "escalate", "agentId": "support-agent" },
    { "type": "agent", "id": "auto-reply", "agentId": "support-agent" }
  ],
  "predicates": [
    { "op": "eq", "left": { "path": "inputData.priority" }, "right": { "literal": "urgent" } },
    { "op": "ne", "left": { "path": "inputData.priority" }, "right": { "literal": "urgent" } }
  ]
}
```

每个子条目必须是 `agent`、`classifier`、`tool` 或 `workflow` 条目，且各自需要一个谓词。所有子条目都直接接收条件条目的输入。

### 谓词 {/* #predicates */}

条件条目和循环使用 JSON 谓词 DSL。操作数可以是 `{ "path": "..." }` 引用或 `{ "literal": ... }` 值。路径基于 `initData`、`inputData`、`stepResults` 和 `state` 解析。

|运算符|结构|
| - | - |
|`eq`, `ne`, `lt`, `lte`, `gt`, `gte` | `{ "op": "eq", "left": ..., "right": ... }` |
| `in`, `notIn` | `{ "op": "in", "value": ..., "set": [...] }` |
| `exists`, `notExists` | `{ "op": "exists", "path": "..." }` |
| `truthy`, `falsy` | `{ "op": "truthy", "value": ... }` |
| `and`, `or` | `{ "op": "and", "args": [...] }` |
| `not` | `{ "op": "not", "arg": ... }` |

路径不存在时不会抛出异常。无法解析路径时，基于路径的运算符返回 `false`。使用 `exists` 或 `notExists` 区分缺失值与假值。

### Foreach 条目 {/* #foreach-entries */}

`foreach` 条目针对数组输入中的每个元素运行一次内部步骤。前一个条目必须输出原始数组。结果保持输入顺序，并发数默认为 `1`。

```json
{
  "type": "foreach",
  "step": { "type": "workflow", "id": "write-blurb", "workflowId": "blurb-workflow" },
  "opts": { "concurrency": 3 }
}
```

内部步骤可以是 `agent`、`tool` 或 `workflow` 条目，但不能是 `mapping` 条目。

### 循环条目 {/* #loop-entries */}

`loop` 条目在谓词成立期间（`dowhile`）或直到谓词成立（`dountil`），重复运行一个步骤。

```json
{
  "type": "loop",
  "loopType": "dountil",
  "step": { "type": "tool", "id": "poll", "toolId": "check-status" },
  "predicate": {
    "op": "eq",
    "left": { "path": "inputData.status" },
    "right": { "literal": "done" }
  }
}
```

循环体必须是单步，并且存储循环需要声明性谓词。

### 睡眠条目 {/* #sleep-entries */}

`sleep` 条目暂停固定毫秒数。`sleepUntil` 条目暂停到由 ISO 日期字符串表示的指定日期。已存储的定义要求使用字面值。

```json
{ "type": "sleep", "id": "wait", "duration": 5000 }
```

```json
{ "type": "sleepUntil", "id": "wait-for-launch", "date": "2027-01-01T00:00:00.000Z" }
```

当必须在运行时计算持续时间或日期时，请使用代码定义的Workflow。

## 验证 {/* #validation */}

Mastra 在保留或注册定义之前验证定义：

* 结构：条目形状和必填字段，包括放置规则，例如仅顶级映射。
* 引用：每个 `agentId` 和 `workflowId` 都必须能在当前注册表或同一捆绑定义中解析。`toolId` 必须与 Tool 的注册键匹配。
* 模式流：每个条目的输入必须与前面的输出兼容，包括推断的映射输出。

验证错误包含点分隔路径，例如 `graph.2.steps.0`，用于标识无效条目。
