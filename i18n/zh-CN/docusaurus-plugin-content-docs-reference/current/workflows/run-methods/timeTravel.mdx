# Run.timeTravel()

`.timeTravel()` 方法从指定步骤重新执行 Workflow，可使用已存储的快照数据或您提供的自定义上下文。它适用于调试失败的 Workflow、用不同输入测试单个步骤，以及在不重新执行整个 Workflow 的情况下从错误中恢复。

## 使用示例 {/* #usage-example */}

```typescript
const run = await workflow.createRun()

const result = await run.timeTravel({
  step: 'step2',
  inputData: { value: 10 },
})
```

## 扩展使用示例 {/* #extended-usage-examples */}

### 使用自定义上下文重新执行 {/* #time-travel-with-custom-context */}

```typescript
const result = await run.timeTravel({
  step: 'step2',
  context: {
    step1: {
      status: 'success',
      payload: { value: 0 },
      output: { step1Result: 2 },
      startedAt: Date.now(),
      endedAt: Date.now(),
    },
  },
})
```

### 从嵌套 Workflow 的步骤重新执行 {/* #time-travel-to-nested-workflow-step */}

```typescript
// Using dot notation
const result = await run.timeTravel({
  step: 'nestedWorkflow.step3',
  inputData: { value: 10 },
})

// Using array of step IDs
const result = await run.timeTravel({
  step: ['nestedWorkflow', 'step3'],
  inputData: { value: 10 },
})
```

### 使用初始状态重新执行 {/* #time-travel-with-initial-state */}

```typescript
const result = await run.timeTravel({
  step: 'step2',
  inputData: { value: 10 },
  initialState: {
    counter: 5,
    metadata: { source: 'time-travel' },
  },
})
```

### 使用嵌套 Workflow 的上下文重新执行 {/* #time-travel-with-nested-workflows-context */}

```typescript
const result = await run.timeTravel({
  step: 'nestedWorkflow.step3',
  context: {
    step1: {
      status: 'success',
      payload: { value: 0 },
      output: { step1Result: 2 },
      startedAt: Date.now(),
      endedAt: Date.now(),
    },
    nestedWorkflow: {
      status: 'running',
      payload: { step1Result: 2 },
      startedAt: Date.now(),
    },
  },
  nestedStepsContext: {
    nestedWorkflow: {
      step2: {
        status: 'success',
        payload: { step1Result: 2 },
        output: { step2Result: 3 },
        startedAt: Date.now(),
        endedAt: Date.now(),
      },
    },
  },
})
```

## 并发调用 timeTravel() {/* #concurrent-time-travel-calls */}

同一次 Workflow 运行在同一时间只能执行一个 `timeTravel()` 调用。在执行任何步骤之前，`timeTravel()` 会以原子方式将已存储的状态从读取时的状态（例如 `suspended` 或 `success`）改为 `running`，从而占用这次运行。如果其他调用已占用它，当前调用会抛出 `WORKFLOW_TIME_TRAVEL_ALREADY_CLAIMED`，且不会执行任何步骤。如果读取时运行已处于 `running` 状态，则会抛出 `WORKFLOW_TIME_TRAVEL_RUN_RUNNING`。

如果同一次运行可能被重复触发重新执行，例如用户连续两次点击“从此步骤重试”，或 API 请求被重试，就需要处理这两种情况。

```typescript
try {
  await run.timeTravel({ step: 'step2' })
} catch (error) {
  if (
    error.id === 'WORKFLOW_TIME_TRAVEL_ALREADY_CLAIMED' ||
    error.id === 'WORKFLOW_TIME_TRAVEL_RUN_RUNNING'
  ) {
    // Another caller is already re-running this workflow. Re-read the run
    // state instead of time travelling again.
  }
}
```

通过 HTTP 调用时，未能占用运行的 `POST /api/workflows/:workflowId/time-travel-async` 请求会返回 `409 Conflict`。`time-travel` 和 `time-travel-stream` 端点会在重新执行完成前响应，因此后续未能占用运行的调用不会改变它们已经返回的状态码。

上一次调用结束后，仍可再次调用 `timeTravel()`，重新执行目标步骤。

:::note

报告支持 `supportsConcurrentUpdates()` 的存储适配器会以原子方式处理运行占用。这要求适配器支持原子读改写；ClickHouse、Cloudflare D1、Cloudflare KV、Cloudflare Durable Objects、LanceDB 和 Redis 等适配器不具备此能力。如果 `shouldPersistSnapshot` 排除了 `running` 状态，或使用尚不支持此机制的 Inngest Workflow runner，也会跳过运行占用。

:::

## 注意事项 {/* #notes */}

* 从指定步骤重新执行需要配置存储，因为它依赖持久化的 Workflow 快照
* 重新执行 Workflow 时，会从存储中加载现有快照（如果有）
* 根据快照或提供的上下文重建目标步骤之前的步骤结果
* 从指定步骤开始执行，使用提供的输入数据或重建的输入数据
* 如果当前 Workflow 定义中，目标步骤之前的某个步骤在快照中没有记录（例如记录运行后该步骤被重命名，或运行从未到达该步骤），`timeTravel` 会在执行任何步骤前拒绝调用并给出说明性错误；已存储的快照保持不变
* Workflow 会从该步骤继续执行直至完成
* 对于尚未运行的 Workflow，也可以提供自定义上下文或起始步骤的输入数据，从指定步骤开始执行
