# Run.timeTravel()

这`.timeTravel()`方法使用存储的快照数据或您提供的自定义上下文从任何特定步骤开始重新执行Workflow。使用它来调试失败的Workflow程并使用不同的输入测试各个步骤。它还可以从错误中恢复，而无需重新运行整个Workflow程。

## 使用示例 {/* #usage-example */}

```typescript
const run = await workflow.createRun()

const result = await run.timeTravel({
  step: 'step2',
  inputData: { value: 10 },
})
```

## 扩展使用示例 {/* #extended-usage-examples */}

### 具有自定义上下文的时间旅行 {/* #time-travel-with-custom-context */}

```typescript
const result = await run.timeTravel({
  step: 'step2',
  context: {
    step1: {
      status: 'success',
      payload: { value: 0 },
      output: { step1Result: 2 },
      startedAt: Date.now(),
      endedAt: Date.now(),
    },
  },
})
```

### 时间旅行到嵌套Workflow程步骤 {/* #time-travel-to-nested-workflow-step */}

```typescript
// Using dot notation
const result = await run.timeTravel({
  step: 'nestedWorkflow.step3',
  inputData: { value: 10 },
})

// Using array of step IDs
const result = await run.timeTravel({
  step: ['nestedWorkflow', 'step3'],
  inputData: { value: 10 },
})
```

### 初始状态的时间旅行 {/* #time-travel-with-initial-state */}

```typescript
const result = await run.timeTravel({
  step: 'step2',
  inputData: { value: 10 },
  initialState: {
    counter: 5,
    metadata: { source: 'time-travel' },
  },
})
```

### 具有嵌套Workflow上下文的时间旅行 {/* #time-travel-with-nested-workflows-context */}

```typescript
const result = await run.timeTravel({
  step: 'nestedWorkflow.step3',
  context: {
    step1: {
      status: 'success',
      payload: { value: 0 },
      output: { step1Result: 2 },
      startedAt: Date.now(),
      endedAt: Date.now(),
    },
    nestedWorkflow: {
      status: 'running',
      payload: { step1Result: 2 },
      startedAt: Date.now(),
    },
  },
  nestedStepsContext: {
    nestedWorkflow: {
      step2: {
        status: 'success',
        payload: { step1Result: 2 },
        output: { step2Result: 3 },
        startedAt: Date.now(),
        endedAt: Date.now(),
      },
    },
  },
})
```

## 并发时间旅行通话 {/* #concurrent-time-travel-calls */}

只有一个`timeTravel()` call can run for a workflow run at a time. Before it runs anything, `timeTravel()` atomically claims the run by moving its stored status from the status it loaded (for example `suspended` or `success`) to `running`. If another caller already claimed it, this call throws `WORKFLOW_TIME_TRAVEL_ALREADY_CLAIMED` and executes no steps. A call that loads the run while it's already `running`投掷`WORKFLOW_TIME_TRAVEL_RUN_RUNNING`.

每当时间旅行可以在同一运行中多次触发时，例如按两次“从步骤重试”按钮或重试 API 请求，这一点就很重要。

```typescript
try {
  await run.timeTravel({ step: 'step2' })
} catch (error) {
  if (
    error.id === 'WORKFLOW_TIME_TRAVEL_ALREADY_CLAIMED' ||
    error.id === 'WORKFLOW_TIME_TRAVEL_RUN_RUNNING'
  ) {
    // Another caller is already re-running this workflow. Re-read the run
    // state instead of time travelling again.
  }
}
```

通过 HTTP，`POST /api/workflows/:workflowId/time-travel-async` returns `409 Conflict` for a losing call. The `time-travel` and `time-travel-stream` endpoints respond before the time travel finishes, so a losing call doesn't change their status code.

呼唤`timeTravel()` again after the previous call finished is still allowed and re-runs the target step.

：：：笔记

报告的存储适配器`supportsConcurrentUpdates()` enforce the claim atomically. This requires atomic read-modify-write support, which is unavailable in adapters such as ClickHouse, Cloudflare D1, Cloudflare KV, Cloudflare Durable Objects, LanceDB, and Redis. Claims are also skipped when `shouldPersistSnapshot` excludes the `running` status or when using the Inngest workflow runner, which doesn't support them yet.

:::

## 笔记 {/* #notes */}

* 时间旅行需要配置存储，因为它依赖于持久的Workflow快照
* 重新执行Workflow时，Workflow从存储加载现有快照（如果可用）
* 目标步骤之前的步骤结果是根据快照或提供的上下文重建的
* 使用提供的或重构的输入数据从指定步骤开始执行
* 如果当前Workflow定义中目标之前的步骤在快照中没有记录的条目（例如，自记录运行以来该步骤被重命名，或者运行从未到达该步骤），`timeTravel` rejects with a descriptive error before anything executes and the stored snapshot is left unchanged
* Workflow程从那时起继续完成
* 通过为起始步骤提供自定义上下文或输入数据，时间旅行可用于尚未运行的Workflow。
