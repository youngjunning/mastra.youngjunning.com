# Tool

Tool 的执行函数现分别接收输入和上下文参数，上下文属性也已重新组织。

## 变更内容 {/* #changed */}

### `createTool` 的执行函数签名改为 `(inputData, context)` {/* #createtool-execute-signature-to-inputdata-context-format */}

所有 `createTool` 的执行函数现在分别接收 `inputData` 和 `context` 两个参数，不再接收单个解构对象。Tool 输入和执行上下文因此分别传入。

此签名变更仅适用于 `createTool`。Workflow 中的 `createStep` 调用仍保留 `async (inputData, context)` 签名。

迁移时，请将 `createTool` 的执行函数签名改为：第一个参数是 `inputData`（类型由 `inputSchema` 确定），第二个参数是 `context`。

```diff
  createTool({
    id: 'weather-tool',
-   execute: async ({ context, requestContext, mastra }) => {
-     const location = context.location;
-     const userTier = requestContext.get('userTier');
-     return getWeather(location, userTier);
-   },
+   execute: async (inputData, context) => {
+     const location = inputData.location;
+     const userTier = context?.requestContext?.get('userTier');
+     return getWeather(location, userTier);
+   },
  });
```

### `createTool` 上下文属性的组织方式 {/* #createtool-context-properties-organization */}

`createTool` 的上下文属性现在按命名空间组织：Agent 专属属性位于 `context.agent`，Workflow 专属属性位于 `context.workflow`，MCP 专属属性位于 `context.mcp`。这样可以更清晰地呈现这些属性的 API 结构。

在 Agent 内执行的 Tool，应通过 `context.agent` 访问 Agent 专属属性。

```diff
  createTool({
    id: 'suspendable-tool',
    suspendSchema: z.object({ message: z.string() }),
    resumeSchema: z.object({ approval: z.boolean() }),
-   execute: async ({ context, suspend, resumeData }) => {
-     if (!resumeData) {
-       return await suspend({ message: 'Waiting for approval' });
-     }
-     if (resumeData.approval) {
-       return { success: true };
-     }
-   },
+   execute: async (inputData, context) => {
+     if (!context?.agent?.resumeData) {
+       return await context?.agent?.suspend({
+         message: 'Waiting for approval',
+       });
+     }
+     if (context.agent.resumeData.approval) {
+       return { success: true };
+     }
+   },
  });
```

在 Workflow 内执行的 Tool，应通过 `context.workflow` 访问 Workflow 专属属性。

```diff
  createTool({
    id: 'workflow-tool',
-   execute: async ({ workflowId, runId, state, setState }) => {
-     const currentState = state;
-     setState({ step: 'completed' });
-     return { result: 'done' };
-   },
+   execute: async (inputData, context) => {
+     const currentState = context?.workflow?.state;
+     context?.workflow?.setState({ step: 'completed' });
+     return { result: 'done' };
+   },
  });
```

执行 Tool 时，会根据 `suspendSchema` 验证 `suspendPayload`。如果 `suspendPayload` 不符合 `suspendSchema`，处理方式取决于 Tool 的运行方式：

* **Agent**：验证错误作为 Tool 输出返回，并记录一条警告，但暂停过程会继续。
* **直接调用 `execute()`**：验证错误作为 Tool 输出返回，不记录警告。
* **Workflow 步骤**：该步骤因暂停数据验证错误而失败，Workflow 运行也会失败。

此外，恢复 Tool 时，会根据 `resumeSchema` 验证 `resumeData`。如果 `resumeData` 不符合 `resumeSchema`，Tool 将返回 `ValidationError`，无法继续恢复。

若要跳过 `suspendSchema` 或 `resumeSchema` 验证，创建 Tool 时不要定义相应的 `suspendSchema` 或 `resumeSchema`。

:::note
有关 MCP 专属 Tool 上下文的变更，请参阅 [MCP 迁移指南](/reference/migrations/upgrade-to-v1/mcp)。
:::

### `RuntimeContext` 更名为 `RequestContext` {/* #runtimecontext-to-requestcontext */}

在整个 Tool 执行上下文中，`RuntimeContext` 类已更名为 `RequestContext`。新名称表明此类存储的是与请求相关的数据。

迁移时，请将 Tool 执行函数中对 `runtimeContext` 的引用改为 `requestContext`。

```diff
  createTool({
    id: 'my-tool',
    execute: async (inputData, context) => {
-     const userTier = context?.runtimeContext?.get('userTier');
+     const userTier = context?.requestContext?.get('userTier');
      return { result: userTier };
    },
  });
```

:::tip[Codemod]

可以使用 Mastra 的 codemod CLI 自动更新导入：

```bash
npx @mastra/codemod@latest v1/runtime-context .
```

:::

这一变更适用于所有 Tool 执行方式，包括直接调用以及通过 Agent 或 Workflow 调用。通过收窄结果类型，可以正确处理验证错误，并避免访问输出属性时发生运行时错误。

### 使用 `outputSchema` 验证 Tool 输出 {/* #tool-output-validation-with-outputschema */}

定义了 `outputSchema` 的 Tool 现在会在运行时验证返回值。此前，`outputSchema` 仅用于类型推断，不会实际验证输出。

如果 Tool 的返回数据不符合其 `outputSchema`，现在会返回 `ValidationError`，而不是无效数据。这是默认的 `outputValidation: 'strict'` 行为。使用 [`outputValidation: 'warn'`](/reference/tools/create-tool) 时，Mastra 会记录不匹配情况，并原样返回输出。

若要修复验证错误，请确保 Tool 输出符合 schema 定义：

```diff
  const getUserTool = createTool({
    id: "get-user",
    outputSchema: z.object({
      id: z.string(),
      name: z.string(),
      email: z.string().email(),
    }),
    execute: async (inputData) => {
-     return { id: "123", name: "John" }; // Missing email
+     return { id: "123", name: "John", email: "john@example.com" };
    },
  });
```

验证失败时，Tool 会返回 `ValidationError`：

```diff
+ // Before v1 - invalid output would silently pass through
  await getUserTool.execute({});
- // { id: "123", name: "John" } - missing email
+ // {
+ //   error: true,
+ //   message: "Tool output validation failed for get-user. The tool returned invalid output:\n- email: Required\n\nReturned output: {...}",
+ //   validationErrors: { ... }
+ // }
```

### `tool.execute` 的返回类型包含 `ValidationError` {/* #toolexecute-return-type-includes-validationerror */}

为处理验证失败，`tool.execute` 的返回类型现在包含 `ValidationError`。访问输出 schema 中定义的属性前，必须先收窄结果类型，才能通过 TypeScript 类型检查。

调用 `tool.execute` 时，请先检查结果是否包含错误，再访问输出属性：

```typescript
const result = await getUserTool.execute({})

// Type-safe check for validation errors
if ('error' in result && result.error) {
  console.error('Validation failed:', result.message)
  console.error('Details:', result.validationErrors)
  return
}

// TypeScript knows result is valid here
console.log(result.id, result.name, result.email)
```

也可以更新 `outputSchema`，使其与实际输出一致；如果不需要验证，则可以完全移除 `outputSchema`。

### 直接执行 Tool {/* #direct-tool-execution */}

为支持由其他代码单独处理执行逻辑的客户端 Tool 定义，`tool.execute` 属性在类型系统中是可选的。直接在 Tool 实例上调用 `execute`（而非通过 Agent 或 Workflow 调用）时，请使用可选链或非空断言：

```typescript
// Optional chaining (recommended)
const result = await weatherTool.execute?.({ location: 'New York' }, {})

// Non-null assertion (when you know execute exists)
const result = await weatherTool.execute!({ location: 'New York' }, {})
```
