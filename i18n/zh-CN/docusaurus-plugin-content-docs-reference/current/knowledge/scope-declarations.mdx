# Scope 声明

`scopes` 选项在 [`Knowledge`](/reference/knowledge/knowledge-class) 中声明一次运行可以持有哪些 Scope 类型，以及谁对这些类型的 Scope 具有什么角色。每个键是模式或具体地址，值是对应的声明。构造 Knowledge 时会检查整个对象，因此拼写错误会在启动时暴露，不会悄然导致权限未授予。逐步示例参见 [Scope 与访问权限](/docs/knowledge/scopes-and-access)。

:::alpha

Knowledge 目前处于 alpha 阶段，其 API 可能在不同版本之间变化。

:::

## 使用示例 {/* #usage-example */}

```typescript title="src/mastra/knowledge.ts"
import { Knowledge, knowledgeMemoryScopes } from '@mastra/core/knowledge'

export const knowledge = new Knowledge({
  id: 'company',
  tools: true,
  scopes: {
    ...knowledgeMemoryScopes(),
    'team:$orgId:$teamId': {
      description: 'A team',
      displayLabel: '$teamId team',
      belongsTo: 'org:$orgId',
      access: [
        { principal: 'self', role: 'editor' },
        { principal: 'org:$orgId', role: 'viewer' },
      ],
      pages: [{ key: 'handbook', name: 'Team Handbook' }],
    },
  },
})
```

`scopes` 是必填项。如果实例不需要任何 Scope 类型，请传入 `{}`。[`knowledgeMemoryScopes()`](/reference/knowledge/knowledge-memory-scopes) 返回 Memory 的 `resource:`、`thread:` Scope 及一个租户 Scope 的声明。

## 模式和参数 {/* #patterns-and-params */}

`team:$orgId:$teamId` 这样的键是模式。第一个 `:` 前的文本是类型，每个 `$name` 片段是参数。地址 `team:acme:support` 与该模式匹配，其中 `$orgId = acme`、`$teamId = support`。

每个参数恰好匹配一个片段，因此地址的片段数必须与模式相同。`resource:user:123` 不匹配 `resource:$resourceId`。包含 `:`、`/`、`#` 或 `%` 的 ID 会编码为一个片段，例如用户 ID `user:123` 对应 `resource:user%3A123`。请用 [`encodeKnowledgeScopeId()` 或 `knowledgeScopeAddress()`](/reference/knowledge/knowledge-memory-scopes#encodeknowledgescopeid) 构建地址；Memory ID 会自动编码。

:::warning[早期 alpha 版本存储的 Scope]

早期版本允许最后一个参数吸收地址的剩余部分，包括未编码的冒号。例如，`resource:slack:U123` 曾是 Memory 资源 `slack:U123` 的地址，现在的新地址是 `resource:slack%3AU123`。运行会访问新的空 Scope。旧地址下的页面、固定内容和笔记仍在存储中，但使用该 Memory 资源的运行已无法访问，Knowledge 也不会自动迁移。

如果已存储 Scope 的地址如今匹配另一个模式，也不会继承新模式的规则。例如，`org:acme:viewer` 曾按 `org:$orgId` 存储，之后才声明了 `org:$orgId:viewer`；将其作为新模式的 Scope 使用会抛出错误。

:::

同一类型可以有多个模式，但前提是任何地址都不会同时匹配其中两个。片段数不同的模式不会重叠；片段数相同的模式，必须在同一位置有不同的字面文本：

```typescript oxfmt:false
scopes: {
  'role:$orgId:admin': { description: 'Org administrators' },
  'role:$orgId:support': { description: 'Support agents' },
}
```

模式重叠会导致启动失败，模式之间没有优先级：

```text
Knowledge scope patterns "role:$orgId:$role" and "role:$orgId:admin" overlap; patterns of a type must be pairwise disjoint.
```

`kb:$orgId` 和 `kb:$orgId:public` 可以同时声明，因为 `kb:acme` 与 `kb:acme:public` 的片段数不同。两者是各自拥有独立规则的 Scope。持有 `kb:acme` 不会自动获得 `kb:acme:public` 的角色，除非 `kb:$orgId:public` 上有规则指定 `kb:$orgId`。

## 规则 {/* #rules */}

`access` 列出访问规则。每条规则指定一个 principal，即运行为使规则生效而必须持有的 Scope，以及运行获得的角色。principal 是已声明的 Scope 模式，或代表当前被访问 Scope 的 `self`：

```typescript oxfmt:false
scopes: {
  ...knowledgeMemoryScopes(),
  'team:$orgId:$teamId': {
    description: 'A team',
    access: [
      { principal: 'self', role: 'editor' },
      { principal: 'org:$orgId', role: 'viewer' },
    ],
  },
}
```

- `self` 指声明规则的 Scope。持有 `team:acme:support` 的运行在该 Scope 上具有 editor 角色。
- `org:$orgId` 从团队地址绑定 `$orgId`。持有 `org:acme` 的运行可以读取 `team:acme:support`；持有 `org:globex` 的运行则完全无法看到它。

角色依次为 `viewer`、`contributor`、`editor` 和 `owner`，后一个角色包含前面角色的权限。各角色的能力如下：

| 角色 | 可执行的操作 |
| - | - |
|`viewer` | 搜索和读取页面及笔记 |
| `contributor` | 创建页面和添加笔记 |
| `editor` | 编辑页面名称、描述和正文；在同一 Scope 内移动页面；重新标记或移除笔记；固定页面 |
| `owner` | 将页面移至其他 Scope；合并移除页面；删除页面 |

各工具操作检查的角色详见[操作所需权限](/reference/knowledge/knowledge-tools#what-each-operation-needs)。

principal 的参数必须通过以下两种方式之一绑定：

- **来自地址前缀。** principal 的参数是目标模式的前几个参数，例如 `org:$orgId` 在 `team:$orgId:$teamId` 上的用法。
- **通过 `belongsTo`。** 目标的 `belongsTo` 模式提供这些参数，如下一节所示。

其他绑定方式都会在启动时失败：

```text
Knowledge rule principal "y:$b" on "x:$a:$b" would reach scopes that aren't an address prefix; reorder "x:$a:$b"'s params so the bound ones come first, or bind them through belongsTo.
```

每个 principal 也必须属于已声明的类型：

```text
Knowledge rule principal "org:$orgId" on "policy:$orgId" is not a declared scope type; declare it or fix the typo.
```

角色不会继续传递。持有 `org:acme` 的运行可读取 `team:acme:support`，因为它匹配 `org:$orgId` 的 viewer 规则；但不会因此获得 `team:acme:support` 对其他 Scope 授予的角色。角色也不会沿层级继承：除非有相应规则，在 `org:acme` 上拥有角色并不意味着能访问其下的 Scope。

## 用 `belongsTo` 放置 Scope {/* #place-scopes-with-belongsto */}

`belongsTo` 将一个 Scope 放在树中另一个 Scope 之下。它本身不授予权限，但规则可以通过它绑定参数：

```typescript oxfmt:false
'project:$projectId': {
  belongsTo: 'org:$orgId',
  access: [
    { principal: 'self', role: 'editor' },
    { principal: 'org:$orgId', role: 'viewer' },
  ],
},
```

地址 `project:p1` 不包含 `$orgId`，因此 `org:$orgId` 规则从项目在树中的位置绑定该参数。第一次写入 Knowledge、同时持有 `project:p1` 和恰好一个 `org:` Scope 的运行，会将项目放在该组织 Scope 下；之后位置保持不变。此后，持有 `org:acme` 的运行可以读取 `project:p1`，持有 `org:globex` 的运行则不能。

只读运行不会创建或放置任何内容。在写入运行放置 `project:p1` 之前，`org:$orgId` 规则不会授予其权限。如果运行持有多个 `org:` Scope，会记录警告并保持现有位置不变；如果持有的 `org:` Scope 与已存储的位置不同，也会记录警告且不改变位置。

## 子 Scope 与带键页面 {/* #child-scopes-and-keyed-pages */}

`children` 声明随此类型每个 Scope 一同创建的子 Scope，地址为 `<address>/<name>`。`pages` 声明模板页面，即此类型每个 Scope 都拥有的带键页面。模板可在自己的 `pages` 中嵌套页面：

```typescript oxfmt:false
'team:$orgId:$teamId': {
  access: [
    { principal: 'self', role: 'editor' },
    { principal: 'org:$orgId', role: 'viewer' },
  ],
  children: [
    {
      name: 'private',
      description: 'Only the team can read this',
      access: [{ principal: 'team:$orgId:$teamId', role: 'editor' }],
    },
  ],
  pages: [
    {
      key: 'handbook',
      name: 'Team Handbook',
      pages: [{ key: 'on-call', name: 'On-call rota' }],
    },
  ],
},
```

现在每个团队都有 `team:acme:support/private` 子 Scope，以及工具可通过 `team:acme:support#handbook` 指定的页面；该页面下还有 `team:acme:support#handbook/on-call`。

同级页面的键必须唯一，且不能包含 `/`、`#` 或 `%`。键重复或无效会导致启动失败。

模板页面由配置定义：

- 写入运行会创建其 Scope 尚缺少的模板页面，包括之后添加到配置中的页面。只读运行不会创建页面。若该路径已存在页面，则会将其纳入配置并作为模板页面。
- 工具可在通常的角色权限下编辑模板页面的名称、描述和正文，为其添加笔记，以及将其他页面合并到该页面。
- 工具不能移动模板页面，也不能通过合并将其移除；否则会收到 `"team:acme:support#handbook" is declared in config; change the scope's pages to move it.`。
- 从 `pages` 移除的页面会变为普通页面并保留其键。重新加入模板时，会将该路径上的页面及其正文和笔记纳入配置；若页面已被移动，下次写入运行会在原路径创建新页面。
- 如果宿主代码通过存储层删除模板页面，下次写入运行会在该路径创建一个新的空页面。

子 Scope 不会继承父 Scope 的规则。必须列出它所需的每条规则，参数从父 Scope 地址绑定。在子 Scope 的规则中，`self` 指子 Scope，但运行不会持有它，因此应像上例那样将父 Scope 的模式指定为 principal。持有 `org:acme` 的运行可以读取团队页面，却无法读取其私有子 Scope。

## 为界面设置 Scope 标签 {/* #label-scopes-for-uis */}

`displayLabel` 为 Studio 等界面提供 Scope 类型的简短名称，模型不会看到它。模型读取的是 `description`。`$params` 从地址填充；具体地址自带的标签优先：

```typescript oxfmt:false
scopes: {
  'org:$orgId': {
    displayLabel: '$orgId organization',
    access: [{ principal: 'self', role: 'editor' }],
    children: [{ name: 'private', displayLabel: 'Private', access: [{ principal: 'org:$orgId', role: 'owner' }] }],
  },
  'org:acme': { displayLabel: 'Acme HQ' },
}
```

`knowledge.scopeLabel('org:globex')` 返回 `globex organization`，`knowledge.scopeLabel('org:acme')` 返回 `Acme HQ`。参见 [`scopeLabel()`](/reference/knowledge/knowledge-class#scopelabel)。

## 共享单个 Scope {/* #share-one-scope */}

不含参数的键是具体地址，可为它所匹配的模式下的单个 Scope 添加规则：

```typescript oxfmt:false
'feature:$orgId:$featureId': { description: 'Product features' },
'feature:acme:a': {
  access: [
    { principal: 'team:acme:eng', role: 'editor' },
    { principal: 'team:acme:support', role: 'contributor' },
  ],
},
```

工程团队可以编辑功能 A，支持团队可以在该 Scope 中添加笔记和页面，但不能编辑工程团队的页面。其他功能 Scope 只使用模式本身的规则。

必须先声明模式。若具体地址没有匹配的模式，启动时会失败：

```text
Knowledge scope "feature:acme:a" doesn't match a declared pattern; declare its pattern first.
```

具体地址可以添加 `description`、`displayLabel`、`access`、`pinnedContext` 和 `pinnedContextPriority`；`belongsTo`、`children` 和 `pages` 则必须在模式上声明。

## 运行持有的 Scope {/* #run-scopes */}

运行持有的 Scope 由宿主代码提供：请求上下文中的 `MASTRA_SCOPES_KEY`、调用时的 `scopes` 选项，以及 Agent 的 `scopes` 选项。Agent 上的列表会与其他来源合并；Agent 上的函数则接收这些 Scope 并返回最终集合。启用 Memory 时，运行还会持有 `resource:<resourceId>` 和 `thread:<threadId>`。参见[设置运行的 Scope](/docs/knowledge/scopes-and-access#set-a-runs-scopes)。

附加 Knowledge 后，运行持有的每个 Scope 都必须匹配已声明的类型。即使某个类型只用于标识运行的身份，也必须声明，空声明如 `'role:$orgId:support': {}` 即可。

一次运行恰好有一个 Memory 资源和一个线程。`knowledgeMemoryScopes()` 会将用户的 `resource:` Scope 放在其首次写入运行所持有的组织 Scope 下，此位置之后不会改变。若用户在多个组织工作，应为每个组织分配不同的资源 ID，例如 `acme-dana` 和 `globex-dana`。

`MASTRA_SCOPES_KEY` 是保留键：服务器会忽略请求正文中的该键。需要使用已将其设为保留键的 `@mastra/server` 版本。

### 错误 {/* #errors */}

| 错误 | 原因 |
| - | - |
|`Knowledge run scope "project:x" does not match a declared scope type. …` | Knowledge 未声明运行持有的某个 Scope。 |
| ``Knowledge tools need run scopes: give the agent or the call `scopes`, or run it with Memory.`` | 运行没有 Scope，也未启用 Memory。 |
| `Agent request context "mastra__scopes" must be an array of "<type>:<value>" strings.` | 某个 Scope 条目不是字符串。 |
| `Invalid agent scope "Org:acme" in request context "mastra__scopes". …` | 某个 Scope 不符合小写类型的 `<type>:<value>` 格式。 |
| `The agent's scopes function dropped "resource:dana". …` | Agent 的 `scopes` 函数遗漏了 `resource:` 或 `thread:` Scope。 |
| `Agent scopes contain more than one resource: …` | 运行持有两个 `resource:`（或 `thread:`）Scope。 |
| `Agent scope "resource:cust-7" conflicts with option "memory.resource" "spec-1". …` | `resource:` Scope 与 `memory.resource` 不一致。 |
| `AGENT_SCOPES_SERVER_OUTDATED` | Scope 来自请求上下文，或是在使用旧版 `@mastra/server` 的调用中传入。 |

## 重命名或停用范围类型 {/* #rename-or-retire-a-scope-type */}

每个已存储的 Scope 都会记住创建它的声明键，地址前缀规则和 `belongsTo` 规则均按该键匹配。如果在 `scopes` 中把键从 `'team:$org:$team'` 改为 `'team:$orgId:$teamId'`，现有团队 Scope 将失去这些规则。为避免这种情况，Knowledge 首次使用时会对照 `scopes` 检查已存储的键；只要缺少任一键，就会拒绝运行：

```text
Knowledge storage has scopes created from declarations this config doesn't declare: "team:$org:$team" (12 scopes). Restore each key in scopes, rename it with knowledge.renameScopeDeclaration(from, to), or keep the key with no access rules to retire it.
```

在 `scopes` 中重命名键后，还要把已存储的 Scope 迁移到新键。`team:$org:$team/internal` 等子 Scope 键也会一起迁移：

```typescript
await knowledge.renameScopeDeclaration('team:$org:$team', 'team:$orgId:$teamId')
```

重命名是一次性操作；若操作被拒绝，不会更改任何内容。旧键仍在 `scopes` 中、新键不存在，或已存储的地址不匹配新模式时，都会拒绝操作。

滚动部署期间，使用新配置的实例在重命名完成前会拒绝运行。重命名后，仍使用旧配置的实例会失去这些 Scope 上的地址前缀和 `belongsTo` 规则。因此应先部署新配置，再立即执行重命名。

若要停用某个类型而不迁移其 Scope，请在 `scopes` 中保留该键，但移除 `access` 规则。Scope 仍留在存储中，却不会被任何规则访问。
