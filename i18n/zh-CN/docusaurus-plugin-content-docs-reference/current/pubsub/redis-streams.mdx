# RedisStreamsPubSub

`RedisStreamsPubSub` 是基于 [`PubSub`](/reference/pubsub/base) 契约、以 [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/) 为底层的实现。它能跨进程、跨主机传递事件，支持持久化、消费者组和失败重投递；同时实现了 [`LeaseProvider`](/reference/pubsub/lease-provider)。信号层可在多个实例间为每个资源选出唯一持有者，使分布式和 Serverless 部署中的信号能够协调运行。

多个服务共享事件流时，适合在分布式部署中使用。单进程事件传递请使用 [`EventEmitterPubSub`](/reference/pubsub/event-emitter)；Google Cloud 环境请使用 [`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub)。

每个主题对应一个 Redis Stream 键。指定组的订阅使用 Redis 消费者组，组内成员轮流分担事件；未指定组的订阅会创建专用消费者组，因此每位订阅者都能收到所有事件。

`RedisStreamsPubSub` 采用拉取式传输：消费者通过 `XREADGROUP` 读取事件，因此 Mastra 会启动编排 worker 代为读取。

## 安装 {/* #installation */}

```bash npm2yarn
npm install @mastra/redis-streams
```

需要 Redis 7.0 或更高版本。回收循环依赖 `XCLAIM` 将已裁剪的条目从待处理列表移除；旧版本不会这样处理。

## 使用示例 {/* #usage-example */}

提供 Redis 连接 URL。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'

export const mastra = new Mastra({
  pubsub: new RedisStreamsPubSub({
    url: 'redis://localhost:6379',
  }),
})
```

### Redis 集群 {/* #redis-cluster */}

连接 Redis 集群（例如启用集群模式的 AWS ElastiCache）时，传入 `cluster`，而非 `url`/`redisOptions`。这些选项会原样传给 `createCluster()`（来自 `redis`）。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'

export const mastra = new Mastra({
  pubsub: new RedisStreamsPubSub({
    cluster: {
      rootNodes: [{ url: 'redis://node-1:6379' }, { url: 'redis://node-2:6379' }],
    },
  }),
})
```

### 自行提供客户端 {/* #bring-your-own-client */}

如需自行控制客户端创建方式（例如 TLS 或凭据提供方），请将尚未连接的 `redis` 客户端作为 `client` 传入。PubSub 将其用作写入端，并为每个订阅调用 `client.duplicate()` 创建独立的阻塞读取连接。PubSub 负责此客户端的生命周期：首次使用时连接，调用 `close()` 时退出。因此不要与应用其他部分共用该客户端。

```typescript title="src/mastra/index.ts"
import { RedisStreamsPubSub } from '@mastra/redis-streams'
import { createClient } from 'redis'

const pubsub = new RedisStreamsPubSub({
  client: createClient({ url: process.env.REDIS_URL, socket: { tls: true } }),
})
```

## 方法 {/* #methods */}

`RedisStreamsPubSub` 实现 [`PubSub`](/reference/pubsub/base) 契约。以下方法具有该实现特有的行为。

### `subscribe(topic, cb, options?)` {/* #subscribetopic-cb-options */}

订阅主题。指定 `options.group` 时，组内成员通过 Redis 消费者组分担事件；未指定组时，订阅者通过专用消费者组接收每个事件。

创建 Redis 消费者组时，将 `options.startFrom` 设为 `"latest"` 可跳过保留的旧条目。默认值 `"earliest"` 会先读取旧条目。此选项不会重置现有组的消费进度。

```typescript
await pubsub.subscribe(
  'workflow.events',
  (event, ack, nack) => {
    console.log(event)
  },
  { group: 'live-workers', startFrom: 'latest' },
)
```

### `flush()` {/* #flush */}

等待进行中的发布操作完成。

```typescript
await pubsub.flush()
```

### `clearTopic(topic)` {/* #cleartopictopic */}

删除主题的 Stream 及其所有消费者组，释放已结束主题占用的内存。Mastra 的运行生命周期（持久化 Agent 和事件驱动 Workflow 引擎）会在运行进入终态时自动调用。仅在确定不会再有读取方时自行调用。此操作尽力而为、不会抛出异常；失败会以 warn 级别记录。Stream 删除时仍保持订阅的客户端可自行恢复，但会错过已删除的条目。

自动清理要求 `@mastra/core` 和 `@mastra/redis-streams` 都使用支持 `clearTopic` 的版本。运行时会通过缓存层转发调用，因此要同时升级这两个包，才能在运行结束时删除 Stream。

并非所有主题都会调用 `clearTopic`。每段对话的 Stream、应用信息流等没有明确终点的主题不会自动清理；若某次清理未执行（例如运行崩溃），也不会重试。默认 7 天的 `streamIdleTtlMs` 滑动 TTL 会在它们闲置后回收。删除线程时，`Memory.deleteThread()` 也会清理该线程的 Stream。

```typescript
await pubsub.clearTopic('workflow.events.run-123')
```

### `trimTopic(topic, { runId, producedBefore? })` {/* #trimtopictopic--runid-producedbefore- */}

使用 `XRANGE` 分页扫描 Stream，并执行 `XDEL` 删除每个由 `runId` 发布的条目。指定 `producedBefore` 时，只删除在该时间点或之前产生的条目，跳过审批和暂停提示。Mastra 每次保存长时间运行的消息时会用此方法裁剪 Stream；线程运行的消息持久化后也会调用，使闲置线程的 Stream 清空，而不是增长至 `maxLen`。由于按 `runId` 匹配，重启后恢复的运行也会删除重启前发布的条目。其他运行（包括其他进程）的条目不受影响。操作尽力而为；失败以 warn 级别记录。

```typescript
await pubsub.trimTopic('agent.thread.thread-abc', { runId: 'run-123' })
```

### `close()` {/* #close */}

关闭 Redis 连接并停止所有订阅。在正常关闭期间调用此方法。

```typescript
await pubsub.close()
```

## Redis 配置 {/* #redis-configuration */}

将 Redis 实例的 `maxmemory-policy` 设为 `noeviction`。消费者组、未确认条目和[租约键](#distributed-leasing)属于运行中的状态，不能当作缓存。在任何逐出策略下，Redis 达到 `maxmemory` 时都可能删除这些数据：`volatile-*` 策略可能逐出带 TTL 的租约键和 Stream，`allkeys-*` 策略则可能逐出任意键。租约丢失会使两个进程同时运行同一线程；Stream 被逐出则会无声地丢弃事件。

使用 `noeviction` 时，内存耗尽后 Redis 会拒绝写入，而非删除数据。请按流量设置足够的 `maxmemory`，并依靠 `streamIdleTtlMs` 回收闲置 Stream。托管服务常默认采用逐出策略（Amazon ElastiCache 默认为 `volatile-lru`），因此应显式检查此配置。

若已设置 `maxmemory`，但策略不是 `noeviction`，`RedisStreamsPubSub` 会在首次连接后记录一次警告。它通过 `INFO memory` 读取策略，因为许多托管服务会禁用 `CONFIG GET`。

```bash
redis-server --maxmemory-policy noeviction
```

### 回收创建时未设 TTL 的 Stream {/* #reclaim-streams-created-without-a-ttl */}

在 `streamIdleTtlMs` 为 `0` 时写入的 Stream（包括 7 天默认值引入之前的版本所写入的）没有 TTL。它们会一直留在 Redis 中，直到后续写入为其设置 TTL。回收步骤如下：

1. 先将实例切换为 `noeviction`。在 `volatile-*` 策略下，为运行中的 Stream 增加 TTL 会使其成为可逐出的对象。
1. 将所有向此 Redis 写入的进程升级到默认启用 TTL 的版本，或显式设置`streamIdleTtlMs` 大于 `0`。关闭过期功能的写入不会刷新现有 TTL；若旧版写入进程仍在使用该 Stream，它可能在使用中途过期。
1. 为每个没有 TTL 的 Stream 设置原本应有的过期时间：最后一次写入后 7 天。闲置超过 7 天的 Stream 会立即过期并释放内存。即使实例因内存耗尽而拒绝写入，`PEXPIRE` 仍可执行。

```bash
# Replace mastra:topic with your keyPrefix, and add your connection flags
# (-h, -p, -a, --tls) to every redis-cli call. On a cluster, run it against each primary.
TTL_MS=604800000
NOW_MS=$(redis-cli time | awk 'NR == 1 { s = $1 } NR == 2 { printf "%.0f", s * 1000 + $1 / 1000 }')
redis-cli --scan --pattern 'mastra:topic:*' | while read -r key; do
  [ "$(redis-cli type "$key")" = "stream" ] || continue
  [ "$(redis-cli pttl "$key")" = "-1" ] || continue
  last_ms=$(redis-cli --raw xinfo stream "$key" | awk 'prev == "last-generated-id" { split($0, id, "-"); print id[1]; exit } { prev = $0 }')
  [ -n "$last_ms" ] || continue
  if [ "$last_ms" = "0" ]; then
    remaining=$TTL_MS # never written to, only subscribed
  else
    remaining=$(( TTL_MS - (NOW_MS - last_ms) ))
    [ "$remaining" -lt 1 ] && remaining=1
    [ "$remaining" -gt "$TTL_MS" ] && remaining=$TTL_MS
  fi
  redis-cli pexpire "$key" "$remaining" > /dev/null
done
```

循环只处理没有 TTL 的 Stream，因此可以重复运行。完成第 2 步后，仍在使用的 Stream 会在每次写入时刷新 TTL，数据得以保留。

## 重新投递与回收 {/* #redelivery-and-reclaim */}

订阅者调用 `nack` 时，事件会以递增的 `deliveryAttempt` 重新发布，原事件则被确认。达到 `maxDeliveryAttempts` 后，事件会被丢弃，不再重新投递。除此之外，每个订阅还会定期回收组内先前消费者已读取但未确认的事件；频率和闲置门槛由 `reclaimIntervalMs` 与 `reclaimIdleMs` 控制。

订阅不会回收自身处理器仍在处理的事件，因此处理缓慢不会让同一事件在该处理器上执行两次。若处理器卡住，组内其他消费者可在事件闲置达到 `reclaimIdleMs` 后回收。单消费者组没有其他成员，因此应设置 `inFlightTimeoutMs`，让订阅在超时后自行对事件执行 nack。

### 事件驱动 Agent 的 worker 接管 {/* #evented-agent-worker-takeover */}

使用 Postgres 存储时，分布式事件驱动 Agent 会通过 Redis 发布 worker 编排事件。若 worker 在确认事件前退出，其他 worker 可回收事件并完成运行，而原 API 进程保持在线。API 进程应设置 `MASTRA_WORKERS=false`，worker 进程应设置 `MASTRA_WORKERS=orchestration`。所有进程必须共用同一个 Postgres 数据库、Redis 连接配置及 `keyPrefix`。

将 `reclaimIdleMs` 保持在 30 秒以上（默认 60 秒）。若设得过低，已停止的 worker 仍持有步骤时事件就可能被回收，导致事件被确认却未执行。

旧版本启动的运行升级后仍可完成，但不保证崩溃恢复。没有 occurrence 标识符的已保存步骤继续按原先的无保护方式运行。其他存储适配器仍将分布式内部编排保留在 worker 进程上。

中断的步骤可能再次执行，因此外部副作用应具备幂等性。已完成的步骤 occurrence 不会受过时的重投递影响；已完成的循环迭代会复用保存的结果与循环决策。即使 `shouldPersistSnapshot` 返回 `false`，受保护的执行仍会持久化恢复所需的记录。恢复、时间旅行、重启竞态及单个 `foreach` 项目不受这些 occurrence 保护。Agent 工具可参见[让工具能够安全地重复执行](/docs/harness/durable-agents#make-tools-safe-to-repeat)。

## 分布式租赁 {/* #distributed-leasing */}

`RedisStreamsPubSub` 基于同一 Redis 连接实现 [`LeaseProvider`](/reference/pubsub/lease-provider) 契约。[信号运行时](/docs/signals/overview)通过它选出唯一持有者（通常按线程键），确保跨实例只有一个进程唤醒并运行 Agent，其他进程则把后续工作交给该持有者。共享租约使信号能够在 Serverless 和多实例部署中工作；若没有它，每个实例都会启动相互竞争的运行。

租约键与主题共用 `keyPrefix` 命名空间，格式为 `<keyPrefix>:lease:<key>`。所有操作都是原子性的：`acquireLease` 使用 `SET NX PX`，并以幂等方式刷新自身 TTL；`releaseLease`、`renewLease` 和 `transferLease` 使用先检查所有权再修改的 Lua 脚本，因此不会覆盖其他持有者的并发续约。

无需直接调用这些方法。只要将 `RedisStreamsPubSub` 配置为 `pubsub` 后端，运行时就会检测并使用该能力。完整方法契约请参见 [`LeaseProvider`](/reference/pubsub/lease-provider)。
