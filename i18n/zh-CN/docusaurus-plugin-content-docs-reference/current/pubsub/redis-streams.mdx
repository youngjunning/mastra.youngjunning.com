# RedisStreamsPubSub

`RedisStreamsPubSub`是一个[`PubSub`](/reference/pubsub/base)实施支持[Redis 流](https://redis.io/docs/latest/develop/data-types/streams/)。它跨进程和主机传递事件，具有持久性、消费者组和失败时的重新传递。它还实现了[`LeaseProvider`](/reference/pubsub/lease-provider)。信号层可以为跨实例的每个资源选择一个所有者，这可以让信号在分布式和无服务器部署中协调运行。

将其用于多个服务共享事件流的分布式部署。对于单进程交付，请使用[`EventEmitterPubSub`](/reference/pubsub/event-emitter). For Google Cloud, use [`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub).

每个主题映射到一个 Redis 流键。组订阅使用 Redis 使用者组。成员循环分担工作。没有组的订阅会创建一个私人消费者组。每个订阅者都会收到每个事件。

`RedisStreamsPubSub`是一种拉式传输：消费者使用以下方式读取事件`XREADGROUP`, so Mastra runs an orchestration worker to read on its behalf.

## 安装 {/* #installation */}

```bash npm2yarn
npm install @mastra/redis-streams
```

需要 Redis 7.0 或更高版本。回收循环依赖于`XCLAIM` removing trimmed entries from the pending list, which earlier versions don't do.

## 使用示例 {/* #usage-example */}

提供 Redis 连接 URL。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'

export const mastra = new Mastra({
  pubsub: new RedisStreamsPubSub({
    url: 'redis://localhost:6379',
  }),
})
```

### Redis集群 {/* #redis-cluster */}

经过`cluster` instead of `url`/`redisOptions` to connect to a Redis Cluster (for example, AWS ElastiCache with cluster mode enabled). The options are forwarded to `createCluster()` from `redis`.

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'

export const mastra = new Mastra({
  pubsub: new RedisStreamsPubSub({
    cluster: {
      rootNodes: [{ url: 'redis://node-1:6379' }, { url: 'redis://node-2:6379' }],
    },
  }),
})
```

### 带上你自己的客户 {/* #bring-your-own-client */}

要自己控制客户端构造（TLS、凭据提供程序等），请传递未连接的`redis` client as `client`. The pubsub uses it as its writer and calls `client.duplicate()` for each subscription's blocking reader. Every connection stays distinct. The pubsub owns the client's lifecycle (it connects on first use and quits it on `close()`), so don't share it with the rest of your app.

```typescript title="src/mastra/index.ts"
import { RedisStreamsPubSub } from '@mastra/redis-streams'
import { createClient } from 'redis'

const pubsub = new RedisStreamsPubSub({
  client: createClient({ url: process.env.REDIS_URL, socket: { tls: true } }),
})
```

## 方法 {/* #methods */}

`RedisStreamsPubSub`实施[`PubSub`](/reference/pubsub/base) contract. The methods below have behavior specific to this implementation.

### `subscribe(topic, cb, options?)` {/* #subscribetopic-cb-options */}

订阅主题。和`options.group`, members of the group share events through a Redis consumer group. Without a group, the subscriber receives every event through a private consumer group.

放`options.startFrom` to `"latest"` to skip retained entries when Redis creates the consumer group. The default, `"earliest"`, reads retained entries first. This option doesn't reset an existing group's checkpoint.

```typescript
await pubsub.subscribe(
  'workflow.events',
  (event, ack, nack) => {
    console.log(event)
  },
  { group: 'live-workers', startFrom: 'latest' },
)
```

### `flush()` {/* #flush */}

等待正在进行的发布完成。

```typescript
await pubsub.flush()
```

### `clearTopic(topic)` {/* #cleartopictopic */}

删除主题的流及其上的每个使用者组，从而释放已完成的主题否则将保留的内存。当运行达到最终状态时，Mastra 的运行生命周期（持久Agent和事件Workflow引擎）会自动调用此函数。只有当没有人会再次阅读该主题时才调用它。这是尽最大努力并且从不抛出。故障记录在警告级别。当流被删除时仍然附加的订户可以自行恢复，但会丢失已删除的条目。

自动清理需要`@mastra/core` and `@mastra/redis-streams` versions that both support `clearTopic`: the runtime routes the call through its caching layer, so upgrade the two packages together to get end-of-run stream deletion.

并非每个主题都能达到`clearTopic` call. Topics without a defined end of life (per-conversation streams, application feeds) are never cleared, and a stream that misses its cleanup (for example, a crashed run) is never retried. The `streamIdleTtlMs` sliding TTL (7 days by default) reclaims those streams once they go idle. Deleting a thread with `Memory.deleteThread()` also clears that thread's stream.

```typescript
await pubsub.clearTopic('workflow.events.run-123')
```

### `trimTopic(topic, { runId, producedBefore? })` {/* #trimtopictopic--runid-producedbefore- */}

通过流进行分页`XRANGE` and runs `XDEL` for every entry published with `runId`. With `producedBefore`, only entries produced at or before that time are deleted, skipping approval and suspension prompts. Mastra uses this to trim a long run each time its messages are saved. Mastra calls this once a thread run's messages are persisted, so an idle thread's stream empties instead of growing to `maxLen`. Because entries are matched by `runId`, a run resumed after a restart also removes the entries it published before the restart. Entries from other runs, including those from other processes, are never touched. Best-effort. Failures are logged at warn level.

```typescript
await pubsub.trimTopic('agent.thread.thread-abc', { runId: 'run-123' })
```

### `close()` {/* #close */}

关闭 Redis 连接并停止所有订阅。在正常关闭期间调用此方法。

```typescript
await pubsub.close()
```

## Redis配置 {/* #redis-configuration */}

放`maxmemory-policy` to `noeviction` on the Redis instance. Consumer groups, unacknowledged entries, and [lease keys](#distributed-leasing) are live state, not cache. Under any evicting policy, Redis deletes them when it reaches `maxmemory`: lease keys and streams with a TTL are eviction candidates under `volatile-*` policies, and every key is a candidate under `allkeys-*` policies. Lost leases let two processes run the same thread, and evicted streams silently drop events.

和`noeviction`, Redis rejects writes instead of deleting data when memory runs out, so size `maxmemory` for your traffic and rely on `streamIdleTtlMs` to reclaim idle streams. Managed services often default to an evicting policy (Amazon ElastiCache defaults to `volatile-lru`), so check the setting explicitly.

什么时候`maxmemory` is set and the policy isn't `noeviction`, `RedisStreamsPubSub` logs a warning once after it first connects. It reads the policy with `INFO memory`, because many managed services block `CONFIG GET`.

```bash
redis-server --maxmemory-policy noeviction
```

### 回收没有 TTL 创建的流 {/* #reclaim-streams-created-without-a-ttl */}

写入的流`streamIdleTtlMs` was `0`, including by versions before the 7-day default, have no TTL. They stay in Redis until a new write gives them one. To reclaim them:

1. 将实例切换到`noeviction` first. Under a `volatile-*` policy, adding a TTL makes a live stream an eviction candidate.
2. 使用默认 TTL 的版本或显式部署写入此 Redis 的每个进程`streamIdleTtlMs` greater than `0`. A write with expiry turned off doesn't refresh an existing TTL, so a stream that an old writer still uses would expire mid-use.
3. 为没有 TTL 的每个流指定其应有的到期时间：上次写入后 7 天。空闲时间超过该时间的流会立即过期，从而立即释放内存。`PEXPIRE` runs even on an instance that's rejecting writes because it's out of memory.

```bash
# Replace mastra:topic with your keyPrefix, and add your connection flags
# (-h, -p, -a, --tls) to every redis-cli call. On a cluster, run it against each primary.
TTL_MS=604800000
NOW_MS=$(redis-cli time | awk 'NR == 1 { s = $1 } NR == 2 { printf "%.0f", s * 1000 + $1 / 1000 }')
redis-cli --scan --pattern 'mastra:topic:*' | while read -r key; do
  [ "$(redis-cli type "$key")" = "stream" ] || continue
  [ "$(redis-cli pttl "$key")" = "-1" ] || continue
  last_ms=$(redis-cli --raw xinfo stream "$key" | awk 'prev == "last-generated-id" { split($0, id, "-"); print id[1]; exit } { prev = $0 }')
  [ -n "$last_ms" ] || continue
  if [ "$last_ms" = "0" ]; then
    remaining=$TTL_MS # never written to, only subscribed
  else
    remaining=$(( TTL_MS - (NOW_MS - last_ms) ))
    [ "$remaining" -lt 1 ] && remaining=1
    [ "$remaining" -gt "$TTL_MS" ] && remaining=$TTL_MS
  fi
  redis-cli pexpire "$key" "$remaining" > /dev/null
done
```

该循环仅涉及没有 TTL 的流，因此重复运行是安全的。在第 2 步之后，仍在使用的流会保留其数据，因为每次写入都会刷新 TTL。

## 重新投递和回收 {/* #redelivery-and-reclaim */}

当订户呼叫时`nack`, the event is republished with an incremented `deliveryAttempt` and the original is acknowledged. Once an event reaches `maxDeliveryAttempts`, it's dropped instead of redelivered. Separately, each subscription periodically reclaims events that an earlier consumer in the group read but never acknowledged, controlled by `reclaimIntervalMs` and `reclaimIdleMs`.

订阅永远不会回收其自己的处理程序仍在处理的事件，因此不会为同一事件调用两次慢速处理程序。如果处理程序挂起，则该组中的另一个使用者会在该事件闲置一段时间后回收该事件`reclaimIdleMs`. In a single-consumer group there's no sibling to do that, so set `inFlightTimeoutMs` to have the subscription nack the event itself after that long.

### Agent工人接管事件 {/* #evented-agent-worker-takeover */}

使用 Postgres 存储，分布式事件Agent通过 Redis 发布工作人员编排事件。如果一个工作线程在确认事件之前退出，另一个工作线程可以回收该事件并完成运行，同时原始 API 进程保持活动状态。配置 API 流程`MASTRA_WORKERS=false` and worker processes with `MASTRA_WORKERS=orchestration`. All processes must share the same Postgres database, Redis connection settings, and `keyPrefix`.

保持`reclaimIdleMs` above 30 seconds (the default is 60 seconds). A lower value can reclaim an event while the stopped worker still holds the step, causing the event to be acknowledged without running.

在旧版本上启动的运行可以在升级后完成，但不保证崩溃恢复。没有发生标识符的已保存步骤将保留其现有的不受保护的行为。其他存储适配器在工作进程上保留分布式内部编排。

被中断的步骤可以再次执行，因此使外部副作用具有幂等性。已完成的步骤发生受到保护，不会发生过时的重新交付，并且已完成的循环迭代会重用其保存的结果和循环决策。即使在以下情况下，受保护的执行也会保留恢复所需的记录：`shouldPersistSnapshot` returns `false`. Resume, time travel, restart races, and individual `foreach` items aren't covered by these occurrence guards. See [make tools safe to repeat](/docs/harness/durable-agents#make-tools-safe-to-repeat) for agent tools.

## 分布式租赁 {/* #distributed-leasing */}

`RedisStreamsPubSub`实施[`LeaseProvider`](/reference/pubsub/lease-provider) contract on top of the same Redis connection. The [signals runtime](/docs/signals/overview) uses it to elect a single owner (usually per thread key) so that across instances only one process wakes and runs the agent, and others route follow-up work to the holder. This is what makes signals work on serverless and multi-instance deployments; without a shared lease, each instance would start its own competing run.

租赁密钥在相同的命名空间下`keyPrefix` as topics, as `<keyPrefix>:lease:<key>`. All operations are atomic: `acquireLease` uses `SET NX PX` and refreshes its own TTL idempotently, while `releaseLease`, `renewLease`, and `transferLease` use Lua scripts that check ownership before mutating, so a concurrent renewal from another owner is never clobbered.

您不直接调用这些方法。配置`RedisStreamsPubSub` as the `pubsub` backend is enough for the runtime to detect and use the capability. See [`LeaseProvider`](/reference/pubsub/lease-provider) for the full method contract.
