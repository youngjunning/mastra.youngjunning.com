# 存储保留

由于存储默认情况下无限增长，Mastra 提供了一个可选择加入的、基于年龄的保留系统。声明每个表`maxAge`的政策`retention`配置，然后调用`storage.prune()`删除早于其配置年龄的行。未配置的数据将永久保留，因此在您选择加入之前，行为不会改变。

`prune()`删除有界批次中的行。运行是可恢复和取消的，因此您可以限制每个维护时段执行的工作量。修剪本身不会回收磁盘空间。当您需要将释放的空间返回给操作系统时，请使用下面特定于数据库的维护指南。

固定盖**growth tables** only: tables that accumulate rows unbounded as a side effect of normal operation (conversation history, telemetry, job and run records, schedule fire history, event feeds). User-authored artifacts and config (agents, skills, workspaces, prompt blocks, datasets, schedule definitions, channel installations, and so on) grow with user intent and are edited or deleted explicitly, so they're not valid retention keys.

存储适配器使用共享核心保留合同`prune()`, or a database-native mechanism when that better matches the backend.

## 时间表修剪 {/* #schedule-pruning */}

跑步`prune()` from a scheduler or maintenance worker, not from application startup or shutdown hooks. For deployments that share a database, prefer a single active scheduler or worker for pruning.

修剪大型表时优先选择流量较低的时段。使用`maxBatches`, `maxRows`, and `pauseMs` to bound each run, and pass an `AbortSignal` when the maintenance process needs to stop promptly. These recommendations apply to adapters that expose `prune()`. ClickHouse applies its native time to live (TTL) policy within the database.

## 使用示例 {/* #usage-example */}

宣布`retention` on any `MastraCompositeStore` (or an adapter that extends it, such as `LibSQLStore`), then call `prune()` from your own scheduler.

```typescript title="src/mastra/index.ts"
import { LibSQLStore } from '@mastra/libsql'

const storage = new LibSQLStore({
  id: 'mastra-storage',
  url: 'file:./mastra.db',
  retention: {
    memory: {
      messages: { maxAge: '30d' },
      threads: { maxAge: '90d', batchSize: 500 },
    },
    observability: {
      spans: { maxAge: '7d' },
    },
  },
})

// Wire this to your own cron/scheduler: Mastra never runs it for you.
const results = await storage.prune()
```

`retention`已完全键入。域键必须存在，并且它们的表键必须声明为具有保留资格。存储配置类型检查直接传递的对象。单独构建对象时，使用`satisfies RetentionConfig` so unknown domains or tables produce compile errors:

```typescript
import type { RetentionConfig } from '@mastra/core/storage'

const retention = {
  memory: {
    messages: { maxAge: '30d' }, // ok
    bogus: { maxAge: '30d' }, // Error: not a memory retention table
  },
  bogusDomain: {}, // Error: not a storage domain
} satisfies RetentionConfig
```

### 符合保留资格的表 {/* #retention-eligible-tables */}

每个域指定其年龄可修剪表和锚定比较的时间戳列，如此选择`maxAge` matches the meaning of the data. Append-only logs use creation time, live state uses last activity, and jobs or runs use completion time so in-flight work isn't pruned.

|域名 |表键|锚柱|`maxAge` measures |
| - | - | - | - |
| `memory` | `threads` | `createdAt` | Thread age |
| `memory` | `messages` | `createdAt` | Message age |
| `memory` | `resources` | `createdAt` | Resource age |
| `memory` | `runFences` | `retiredAt` | Time since the durable agent execution holding the fence settled. Fences of running executions (`NULL`) are never pruned |
| `threadState` | `threadState` | `updatedAt` | Inactivity: state for still-active threads survives |
| `observability` | `spans` | `startedAt` | Span age |
| `observability` | `metrics` | `timestamp` | Metric event age (vNext only) |
| `observability` | `logs` | `timestamp` | Log event age (vNext only) |
| `observability` | `scores` | `timestamp` | Score event age (vNext only) |
| `observability` | `feedback` | `timestamp` | Feedback event age (vNext only) |
| `scores` | `scorers` | `createdAt` | Score record age |
| `workflows` | `workflowSnapshot` | `updatedAt`|不活动、暂停或长时间运行的Workflow程仍然存在 |
|`workflows` | `runOwnership` | `updatedAt`|不活动。正在运行的持久Agent执行每 10 秒更新一次其声明，因此请保持`maxAge`远高于其 30 秒租约 |
|`backgroundTasks` | `backgroundTasks` | `completedAt`|完成后的时间，正在进行的任务（`NULL`) 永远不会被修剪 |
|`experiments` | `experiments` | `completedAt`|自完成以来，正在运行的实验从未被删减|
|`notifications` | `notifications` | `createdAt`|通知年龄 |
|`harness` | `sessions` | `createdAt`|会话记录年龄 |
|`schedules` | `triggers` | `actual_fire_at`|火史年代（epoch-ms专栏）|

：：：笔记

* 记忆`observational_memory` table has no timestamp anchor, so it can't be age-pruned and isn't a valid retention key.
* 实验作为整个单元进行修剪：老化实验的结果行将与其一起删除（结果与其父级级联），因此运行永远不会被部分删除。保留没有单独的`results` key.
* `runOwnership`和`runFences` hold the run fencing records of durable agents, one small record per run in each. If the `runOwnership` `maxAge` is too short, a running execution can lose its run, but an execution that lost a run still can't write. A fence is retired only when its execution settles, so the fence of a run that crashed and was never recovered is never pruned.
* 为了`schedules`, the growth table is the fire history (`schedule_triggers`, one row per fire): schedule definitions are config and aren't pruned.
* 在 PostgreSQL 上，时间戳锚点使用时区感知镜像列（例如`createdAtZ`, `completedAtZ`).
* DuckDB 可观察性存储所有五个信号的仅附加事件。它是`spans` policy uses the event `timestamp` column rather than `startedAt`.
* LibSQL 和 PostgreSQL 支持上述所有域，除了`harness`, which PostgreSQL doesn't implement. MongoDB supports all except `threadState` and `harness`. DuckDB, MySQL, Microsoft SQL Server, Oracle Database, Amazon Aurora DSQL, and Google Cloud Spanner currently support retention only in their `observability` domains, with the signal coverage shown in the support matrix.
* vNext PostgreSQL Observability域将信号事件存储在按天分区的表中（`spans`, `metrics`, `logs`, `scores`, `feedback`). For it, `prune()` drops whole day partitions (or TimescaleDB chunks) that are entirely older than the cutoff instead of deleting rows: effective level of detail is one day, and a partition is only dropped once its entire day is past `maxAge`. `PruneResult.deleted` reports the number of rows in the dropped partitions.

## 方法 {/* #methods */}

### 保留 {/* #retention */}

#### `prune(options?)` {/* #pruneoptions */}

删除早于其配置的行`maxAge` across every domain that has a policy in `retention`. Returns one `PruneResult` per table touched. With no `retention` configured it's a no-op returning `[]`.

`prune()`设计为在具有数百万行的表上是安全的。它以有界的、批量的块进行删除（每个批次都是它自己的事务），因此它永远不会需要长时间的锁定或使事务日志膨胀。它从不运行`VACUUM`.

经过`options.retention` to replace the configured policies for that call only: for example to skip a domain (keep chat history) or prune more aggressively than the standing config. The store's configured `retention` is unchanged.

使用锚列索引的适配器在第一个索引上延迟创建它们`prune()` call for each table with a policy (never at `init()`) so deployments that don't configure retention pay no extra index write or disk overhead. The first prune of an existing large table pays a one-time index build. Subsequent prunes reuse the index. DuckDB uses its built-in zone maps instead of creating retention indexes.

```typescript
const results = await storage.prune({
  maxRows: 50_000, // cap work this call
  pauseMs: 50, // breathe between batches
})

for (const r of results) {
  console.log(`${r.domain}.${r.table}: deleted ${r.deleted}, done=${r.done}`)
}

// One-off pass with different policies (configured retention untouched):
await storage.prune({
  retention: {
    observability: { spans: { maxAge: '1d' } },
  },
})
```

返回：`Promise<PruneResult[]>`

##### 修剪结果 {/* #pruneresult */}

每个结果描述一个表的进度：

```typescript
interface PruneResult {
  domain: string // e.g. 'memory'
  table: string // physical table name, e.g. 'mastra_messages'
  deleted: number // rows deleted during this call
  done: boolean // false => eligible rows remain; call prune() again
}
```

## 按计划运行修剪 {/* #running-prune-on-a-schedule */}

`prune()`没有内置调度程序，因此您可以决定它何时运行。有界调用可能会留下符合条件的行，由任何结果指示`done: false`. Call it again on the next tick. Short invocations let a large backlog drain over several runs.

```typescript
// Runs on your own cron (node-cron, a workflow schedule, an external job, etc.).
async function retentionTick() {
  const results = await storage.prune({ maxRows: 100_000, pauseMs: 25 })
  const incomplete = results.filter(r => !r.done)
  if (incomplete.length) {
    // Rows remain; the next scheduled tick will continue where this one stopped.
    console.log(
      'retention still draining:',
      incomplete.map(r => `${r.domain}.${r.table}`),
    )
  }
}
```

您还可以使用以下命令取消长时间运行的修剪`AbortSignal`: the loop stops between batches and returns partial results with `done: false`. The next run resumes cleanly.

## ClickHouse 原生 TTL {/* #clickhouse-native-ttl */}

ClickHouse 可观察性存储使用本机表 TTL，而不是`prune()`. Configure retention as days per signal. `init()` applies the TTLs to new and existing tables and skips `ALTER TABLE` statements when the configured TTL is already present.

省略的信号以及设置为零或更低的信号不会获得 TTL。当您从以下位置移除信号时`retention`, the next `init()` or `applyRetention()` removes that table's TTL. If Mastra can't read the current TTLs from `system.tables`, it applies the configured TTLs and leaves the others unchanged.

对于需要更新 TTL 配置而不运行完整初始化路径的部署，请调用`applyRetention()` on the vNext observability store:

```typescript
import { ObservabilityStorageClickhouseVNext } from '@mastra/clickhouse'

const observability = new ObservabilityStorageClickhouseVNext({
  client,
  retention: {
    tracing: 30,
    logs: 7,
    metrics: 14,
    scores: 90,
    feedback: 60,
  },
})

await observability.applyRetention()
```

删除请求会保留足够长的时间，以便在信号行过期后继续执行擦除操作。 Mastra 将 TTL 应用到`mastra_deletion_requests` only when tracing, logs, metrics, scores, and feedback all have finite retention. The deletion-request TTL is the longest of those periods plus 30 days. For example, if score retention is the longest period at 90 days, deletion requests expire after 120 days. When any signal is unbounded, deletion requests remain unbounded because trace deletion requests cover rows across all five signals.

## MongoDB TTL 索引（修剪的替代方案） {/* #mongodb-ttl-indexes-alternative-to-prune */}

MongoDB 提供原生[TTL (Time-To-Live) indexes](https://www.mongodb.com/docs/manual/core/index-ttl/) that automatically delete expired documents without requiring manual `prune()` calls. This is a database-level feature that runs as a background thread.

:::注意\[何时使用 TTL 与 prune()]

**在以下情况下使用 MongoDB TTL 索引：**

* 您想要自动、零维护的删除
* 您的保留期是固定的（例如“始终 30 天”）
* 您更喜欢数据库本机解决方案

**使用`prune()` when:**

* 您需要对删除时间进行细粒度控制
* 您想要限制工作时间内的删除率
* 您需要可恢复、可取消的清理操作
* 您正在使用具有多个数据库的复合存储

两种方法都是有效的。 TTL 更简单。`prune()` gives more control.
:::

### 在 MongoDB 上设置 TTL 索引 {/* #setting-up-ttl-indexes-on-mongodb */}

TTL 索引适用于日期字段。 MongoDB 每 60 秒检查一次索引，并删除日期字段 + TTL 持续时间 \< 当前时间的文档。

```typescript
import { MongoDBStore } from '@mastra/mongodb'

const storage = new MongoDBStore({
  id: 'mongodb-storage',
  uri: process.env.MONGODB_URI!,
  dbName: process.env.MONGODB_DB_NAME!,
  indexes: [
    // Messages expire after 30 days
    {
      collection: 'mastra_messages',
      keys: { createdAt: 1 },
      options: { expireAfterSeconds: 30 * 24 * 60 * 60 }, // 30 days
    },
    // Threads expire after 90 days
    {
      collection: 'mastra_threads',
      keys: { createdAt: 1 },
      options: { expireAfterSeconds: 90 * 24 * 60 * 60 }, // 90 days
    },
    // Spans expire after 7 days
    {
      collection: 'mastra_ai_spans',
      keys: { startedAt: 1 },
      options: { expireAfterSeconds: 7 * 24 * 60 * 60 }, // 7 days
    },
  ],
})
```

:::提示
TTL 索引会在文档过期后不久删除文档（后台线程每约 60 秒运行一次），但不能保证确切的时间。为了精确、立即清理，请使用`prune()` instead.
:::

## 回收磁盘 {/* #reclaiming-disk */}

`prune()`删除行但不收缩数据库文件。在 SQLite/libSQL 上，释放的页面会进入空闲列表以供将来的写入重用。对于大多数用户来说，重复使用这些页面可以防止文件无限增长。

将可用空间交还给操作系统是 Mastra 无法管理的另一个问题。如果您特别需要收缩文件，请运行底层数据库的压缩（例如`VACUUM` on self-hosted libSQL) yourself in a maintenance window. A full `VACUUM` locks the file and needs roughly twice the file size in free disk. On PostgreSQL, autovacuum reclaims dead tuples for reuse automatically. A manual `VACUUM FULL` is only needed if you must return disk to the OS.

对于 MongoDB，已删除的文档可在以后的插入中重用。要回收磁盘空间，请运行[`db.runCommand({ compact: "collection_name" })`](https://www.mongodb.com/docs/manual/reference/command/compact/) during a maintenance window.

:::注意\[libSQL 和 Turso][Turso Cloud](/integrations/databases/libsql) manages storage compaction for you, so there's nothing to reclaim manually. This applies only to self-hosted libSQL files.
:::
