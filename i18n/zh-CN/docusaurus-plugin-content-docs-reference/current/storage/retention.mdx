# 存储保留

默认情况下，存储数据会持续增长。Mastra 提供可选的按数据年龄保留机制：为各表声明 `maxAge` 策略，写入 `retention` 配置，再调用 `storage.prune()` 删除早于设定期限的行。未配置的数据会永久保留，因此在启用前现有行为不变。

`prune()` 分批限量删除行。任务可恢复、可取消，便于限制每个维护时段的工作量。修剪本身不会回收磁盘空间；如需将空闲空间归还操作系统，请参见下文针对各数据库的维护建议。

保留策略仅适用于**增长型表**：这些表会因正常运行而不断累积数据，例如对话历史、遥测数据、任务与运行记录、计划触发历史和事件流。用户主动创建的内容及配置（Agent、Skill、工作区、提示块、数据集、计划定义、渠道安装等）随用户操作增长，并由用户显式编辑或删除，因此不能作为保留策略的键。

存储适配器会为 `prune()` 使用共享的核心保留契约；如果数据库原生机制更适合对应后端，也可以采用原生机制。

| 适配器 | 机制 | 保留策略支持范围 |
| - | - | - |
| libSQL | `prune()` | 所有受支持的增长型数据域 |
| PostgreSQL | `prune()` | 所有受支持的增长型数据域；vNext 可观测性通过删除过期分区或数据块清理 |
| MongoDB | `prune()` 或原生 TTL | 所有受支持的增长型数据域；也可使用原生 TTL 索引 |
| DuckDB | `prune()` | 可观测性 Span、指标、日志、评分及反馈 |
| MySQL | `prune()` | 可观测性 Span、持久化 Agent 运行隔离记录（`runOwnership`、`runFences`） |
| Microsoft SQL Server | `prune()` | 可观测性 Span、持久化 Agent 运行隔离记录（`runOwnership`、`runFences`） |
| Oracle Database | `prune()` | 可观测性 Span 与日志、持久化 Agent 运行隔离记录（`runOwnership`、`runFences`） |
| Amazon Aurora DSQL | `prune()` | 可观测性 Span、持久化 Agent 运行隔离记录（`runOwnership`、`runFences`） |
| Google Cloud Spanner | `prune()` | 可观测性 Span；启用指标存储时还包括指标。另支持持久化 Agent 运行隔离记录（`runOwnership`、`runFences`） |
| DynamoDB | `prune()` | 持久化 Agent 运行隔离记录（`runOwnership`、`runFences`） |
| Convex | `prune()` | 持久化 Agent 运行隔离记录（`runOwnership`、`runFences`）；升级后须重新部署 Convex 函数 |
| Cloudflare D1 和 Durable Objects | `prune()` | 持久化 Agent 运行隔离记录（`runOwnership`、`runFences`） |
| ClickHouse | 原生 TTL | 可观测性 Span、指标、日志、评分及反馈。五种信号均设置有限保留期时，删除请求记录会在最长信号保留期加 30 天后过期 |

## 各存储后端的维护建议 {/* #storage-specific-maintenance */}

| 适配器 | 维护建议 |
| - | - |
| SQLite 和 libSQL | 删除后释放的页面可供后续写入重用，从而阻止数据库文件继续增长。若要回收磁盘空间，需要执行数据库级维护。 |
| DuckDB | 对文件存储，修剪后运行 `CHECKPOINT` 以回收已删除行占用的空间。DuckDB 的 `VACUUM` 不会回收这些空间。 |

## 定期修剪 {/* #schedule-pruning */}

应从调度器或维护 Worker 调用 `prune()`，不要在应用启动或关闭钩子中调用。多个部署共用数据库时，最好只由一个活跃的调度器或 Worker 执行修剪。

修剪大表时，尽量选择低流量时段。使用 `maxBatches`、`maxRows` 和 `pauseMs` 限制每次运行的工作量；维护进程需要及时停止时，传入 `AbortSignal`。这些建议适用于提供 `prune()` 的适配器。ClickHouse 则在数据库内部执行原生 TTL 策略。

## 使用示例 {/* #usage-example */}

声明 `retention` 时，可以使用 `MastraCompositeStore`（或其子类适配器，例如 `LibSQLStore`），再从自有调度器调用 `prune()`。

```typescript title="src/mastra/index.ts"
import { LibSQLStore } from '@mastra/libsql'

const storage = new LibSQLStore({
  id: 'mastra-storage',
  url: 'file:./mastra.db',
  retention: {
    memory: {
      messages: { maxAge: '30d' },
      threads: { maxAge: '90d', batchSize: 500 },
    },
    observability: {
      spans: { maxAge: '7d' },
    },
  },
})

// Wire this to your own cron/scheduler: Mastra never runs it for you.
const results = await storage.prune()
```

`retention` 具有完整的类型约束：数据域键必须存在，表键必须被声明为可设置保留策略。直接传入存储配置的对象会接受类型检查；单独构造对象时，请使用 `satisfies RetentionConfig`，以便未知的数据域或表在编译时触发错误：

```typescript
import type { RetentionConfig } from '@mastra/core/storage'

const retention = {
  memory: {
    messages: { maxAge: '30d' }, // ok
    bogus: { maxAge: '30d' }, // Error: not a memory retention table
  },
  bogusDomain: {}, // Error: not a storage domain
} satisfies RetentionConfig
```

### 可设置保留策略的表 {/* #retention-eligible-tables */}

每个数据域都指定可按年龄修剪的表，以及作为比较基准的时间戳列，使 `maxAge` 符合数据的实际含义。只追加的日志使用创建时间，实时状态使用最近活动时间，任务或运行使用完成时间，以避免删掉仍在执行的工作。

| 数据域 | 表键 | 基准时间戳列 | `maxAge` 衡量的时间 |
| - | - | - | - |
| `memory` | `threads` | `createdAt` | 线程创建至今的时间 |
| `memory` | `messages` | `createdAt` | 消息创建至今的时间 |
| `memory` | `resources` | `createdAt` | 资源创建至今的时间 |
| `memory` | `runFences` | `retiredAt` | 持有隔离记录的持久化 Agent 执行结束后的时间；运行中执行的隔离记录（`NULL`）不会被修剪 |
| `threadState` | `threadState` | `updatedAt` | 未活动时长；活跃线程的状态会保留 |
| `observability` | `spans` | `startedAt` | Span 创建至今的时间 |
| `observability` | `metrics` | `timestamp` | 指标事件的年龄（仅 vNext） |
| `observability` | `logs` | `timestamp` | 日志事件的年龄（仅 vNext） |
| `observability` | `scores` | `timestamp` | 评分事件的年龄（仅 vNext） |
| `observability` | `feedback` | `timestamp` | 反馈事件的年龄（仅 vNext） |
| `scores` | `scorers` | `createdAt` | 评分记录的年龄 |
| `workflows` | `workflowSnapshot` | `updatedAt` | 未活动时长；暂停或长时间运行的 Workflow 会保留 |
| `workflows` | `runOwnership` | `updatedAt` | 未活动时长。运行中的持久化 Agent 执行每 10 秒续租一次，因此 `maxAge` 应远大于其 30 秒租约 |
| `backgroundTasks` | `backgroundTasks` | `completedAt` | 任务完成后的时间；进行中的任务（`NULL`）不会被修剪 |
| `experiments` | `experiments` | `completedAt` | 实验完成后的时间；运行中的实验不会被修剪 |
| `notifications` | `notifications` | `createdAt` | 通知创建至今的时间 |
| `harness` | `sessions` | `createdAt` | 会话记录创建至今的时间 |
| `schedules` | `triggers` | `actual_fire_at` | 触发历史的年龄（该列为 epoch 毫秒值） |

:::note

- memory 数据域的 `observational_memory` 表没有时间戳基准列，因此无法按年龄修剪，也不能作为保留策略键。
- 实验作为整体修剪：过期实验的结果行会随实验一起删除（结果与父记录级联删除），不会出现部分删除的运行。保留策略没有单独的 `results` 键。
- `runOwnership` 和 `runFences` 保存持久化 Agent 的运行隔离记录，每次运行在两个表中各有一条小记录。如果 `runOwnership` 的 `maxAge` 太短，正在执行的任务可能失去运行所有权；但失去所有权的执行仍无法写入。隔离记录只有在对应执行结束时才会退役，因此崩溃且未恢复的运行对应的记录不会被修剪。
- 对于 `schedules`，增长型表是触发历史（`schedule_triggers`，每次触发一行）；计划定义属于配置，不会修剪。
- PostgreSQL 的基准时间戳使用感知时区的镜像列（例如 `createdAtZ`、`completedAtZ`）。
- DuckDB 可观测性存储以只追加方式保存五种信号的事件。其 `spans` 策略使用事件的 `timestamp` 列，而非 `startedAt`。
- libSQL 和 PostgreSQL 支持上述所有数据域，但 PostgreSQL 尚未实现 `harness`。MongoDB 不支持 `threadState` 和 `harness`。DuckDB、MySQL、Microsoft SQL Server、Oracle Database、Amazon Aurora DSQL 与 Google Cloud Spanner 目前仅在 `observability` 数据域提供保留策略，具体信号范围见上方支持矩阵。
- vNext PostgreSQL 可观测性数据域将信号事件按天分区存储（`spans`、`metrics`、`logs`、`scores`、`feedback`）。其 `prune()` 不逐行删除，而是删除完全早于截止时间的整日分区（或 TimescaleDB 数据块）；有效粒度为一天，只有分区整日均超过 `maxAge` 后才会删除。`PruneResult.deleted` 会报告被删分区中的行数。

:::

## 方法 {/* #methods */}

### 保留 {/* #retention */}

#### `prune(options?)` {/* #pruneoptions */}

删除年龄超过相应 `maxAge` 的行，范围涵盖 `retention` 中配置了策略的所有数据域。每个涉及的表返回一个 `PruneResult`。未配置 `retention` 时不执行操作，返回 `[]`。

`prune()` 专为数百万行的大表设计。它按有界批次删除数据（每批都是独立事务），避免长时间锁表或使事务日志过度增长。它不会运行 `VACUUM`。

传入 `options.retention` 可仅在本次调用中替换已配置策略，例如跳过某个数据域以保留聊天历史，或比常规配置更积极地修剪。存储实例上的 `retention` 配置保持不变。

使用基准时间戳列索引的适配器，只在首次对有策略的表调用 `prune()` 时延迟创建索引，而不会在 `init()` 时创建。因此未启用保留策略的部署不会产生额外的索引写入或磁盘开销。现有大表首次修剪时需一次性建立索引；后续修剪复用该索引。DuckDB 使用内置 Zone Map，不创建保留策略索引。

```typescript
const results = await storage.prune({
  maxRows: 50_000, // cap work this call
  pauseMs: 50, // breathe between batches
})

for (const r of results) {
  console.log(`${r.domain}.${r.table}: deleted ${r.deleted}, done=${r.done}`)
}

// One-off pass with different policies (configured retention untouched):
await storage.prune({
  retention: {
    observability: { spans: { maxAge: '1d' } },
  },
})
```

返回：`Promise<PruneResult[]>`

##### 修剪结果 {/* #pruneresult */}

每个结果描述一个表的处理进度：

```typescript
interface PruneResult {
  domain: string // e.g. 'memory'
  table: string // physical table name, e.g. 'mastra_messages'
  deleted: number // rows deleted during this call
  done: boolean // false => eligible rows remain; call prune() again
}
```

## 定期运行修剪 {/* #running-prune-on-a-schedule */}

`prune()` 没有内置调度器，运行时间由你决定。受限的单次调用可能仍有符合删除条件的行，任何返回 `done: false` 的结果都表示这种情况。请在下次调度时再次调用。通过多次短时运行，可以逐步清理大量积压数据。

```typescript
// Runs on your own cron (node-cron, a workflow schedule, an external job, etc.).
async function retentionTick() {
  const results = await storage.prune({ maxRows: 100_000, pauseMs: 25 })
  const incomplete = results.filter(r => !r.done)
  if (incomplete.length) {
    // Rows remain; the next scheduled tick will continue where this one stopped.
    console.log(
      'retention still draining:',
      incomplete.map(r => `${r.domain}.${r.table}`),
    )
  }
}
```

也可以传入 `AbortSignal` 取消长时间运行的修剪：循环会在批次之间停止，返回带 `done: false` 的部分结果。下次运行可继续处理。

## ClickHouse 原生 TTL {/* #clickhouse-native-ttl */}

ClickHouse 的可观测性存储使用表原生 TTL，而不是 `prune()`。按信号配置保留天数。`init()` 会将 TTL 应用于新旧表；若已配置相同 TTL，则跳过 `ALTER TABLE` 语句。

未配置的信号以及保留天数设为零或负数的信号不会设置 TTL。从 `retention` 移除某个信号后，下次调用 `init()` 或 `applyRetention()` 会移除对应表的 TTL。如果 Mastra 无法从 `system.tables` 读取当前 TTL，它只会应用已配置的 TTL，其余保持不变。

若部署需要更新 TTL 配置，但不想执行完整初始化流程，可在 vNext 可观测性存储上调用 `applyRetention()`：

```typescript
import { ObservabilityStorageClickhouseVNext } from '@mastra/clickhouse'

const observability = new ObservabilityStorageClickhouseVNext({
  client,
  retention: {
    tracing: 30,
    logs: 7,
    metrics: 14,
    scores: 90,
    feedback: 60,
  },
})

await observability.applyRetention()
```

删除请求记录会保留足够久，以便信号行过期后仍能执行删除。只有追踪、日志、指标、评分和反馈均设置有限保留期时，Mastra 才会为 `mastra_deletion_requests` 设置 TTL。该 TTL 等于五种信号中最长保留期再加 30 天。例如评分的 90 天为最长保留期时，删除请求记录会在 120 天后过期。只要有一种信号无限期保留，删除请求记录也会无限期保留，因为追踪删除请求覆盖这五种信号的行。

## MongoDB TTL 索引（修剪的替代方案） {/* #mongodb-ttl-indexes-alternative-to-prune */}

MongoDB 提供原生 [TTL（存活时间）索引](https://www.mongodb.com/docs/manual/core/index-ttl/)，可自动删除过期文档，无须手动调用 `prune()`。这是在数据库后台线程中运行的功能。

:::note[何时使用 TTL，何时使用 prune()]

**以下情况适合使用 MongoDB TTL 索引：**

- 希望自动删除，且无须维护
- 保留期限固定（例如始终为 30 天）
- 倾向使用数据库原生机制

**以下情况适合使用 `prune()`：**

- 需要精细控制删除时间
- 希望限制业务时段的删除速率
- 需要可恢复、可取消的清理操作
- 使用跨多个数据库的复合存储

两种方式都可行。TTL 更简单，`prune()` 控制更细。
:::

### 在 MongoDB 上设置 TTL 索引 {/* #setting-up-ttl-indexes-on-mongodb */}

TTL 索引适用于日期字段。MongoDB 每 60 秒检查一次索引，并删除满足“日期字段值 + TTL 时长 \< 当前时间”的文档。

```typescript
import { MongoDBStore } from '@mastra/mongodb'

const storage = new MongoDBStore({
  id: 'mongodb-storage',
  uri: process.env.MONGODB_URI!,
  dbName: process.env.MONGODB_DB_NAME!,
  indexes: [
    // Messages expire after 30 days
    {
      collection: 'mastra_messages',
      keys: { createdAt: 1 },
      options: { expireAfterSeconds: 30 * 24 * 60 * 60 }, // 30 days
    },
    // Threads expire after 90 days
    {
      collection: 'mastra_threads',
      keys: { createdAt: 1 },
      options: { expireAfterSeconds: 90 * 24 * 60 * 60 }, // 90 days
    },
    // Spans expire after 7 days
    {
      collection: 'mastra_ai_spans',
      keys: { startedAt: 1 },
      options: { expireAfterSeconds: 7 * 24 * 60 * 60 }, // 7 days
    },
  ],
})
```

:::tip
TTL 索引通常在文档过期后不久删除它们（后台线程约每 60 秒运行一次），但不保证准确时间。如需精确、即时清理，请改用 `prune()`。
:::

## 回收磁盘空间 {/* #reclaiming-disk */}

`prune()` 删除行，但不会缩小数据库文件。在 SQLite/libSQL 中，释放的页面进入空闲列表，供后续写入重用。对大多数用户而言，复用页面可避免文件无限增长。

将空闲空间归还操作系统是独立的维护工作，Mastra 不会代为执行。如果确需缩小文件，请在维护时段自行运行底层数据库的压缩操作（例如对自行托管的 libSQL 运行 `VACUUM`）。完整的 `VACUUM` 会锁定文件，并需要约为文件大小两倍的可用磁盘空间。在 PostgreSQL 中，autovacuum 会自动回收失效元组以供重用；只有必须把磁盘空间归还操作系统时，才需要手动运行 `VACUUM FULL`。

MongoDB 会在后续插入中复用已删除文档的空间。如需回收磁盘空间，请在维护时段运行 [`db.runCommand({ compact: "collection_name" })`](https://www.mongodb.com/docs/manual/reference/command/compact/)。

:::note[libSQL 和 Turso]
[Turso Cloud](/integrations/databases/libsql) 会自动管理存储压缩，无需手动回收空间。本节仅适用于自行托管的 libSQL 文件。
:::
