# DurableAgent

:::beta

在 API 稳定之前，即使没有提高主版本号，也可能发生破坏性变更。

:::

`DurableAgent` 为现有 [`Agent`](/reference/agents/agent) 添加持久化执行和可恢复的 stream。它运行 Agent 循环，使客户端断开并重新连接后仍不会错过事件，并通过 [PubSub](/docs/server/pubsub) 流式传输这些事件。当运行需要超过单次请求的生命周期，或需要在连接断开后继续时，请使用它。

可以使用 [`createDurableAgent`](#createdurableagentoptions) 工厂方法创建，或使用 [`createEventedAgent`](#createeventedagentoptions) 在内置 Workflow 引擎上启动后无需等待结果的执行。若需由 Inngest 驱动执行，请使用 `@mastra/inngest` 提供的 [`createInngestAgent`](/reference/agents/inngest-agent)。

## 使用示例 {/* #usage-example */}

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Agent } from '@mastra/core/agent'
import { createDurableAgent } from '@mastra/core/agent/durable'

const agent = new Agent({
  id: 'my-agent',
  name: 'My Agent',
  instructions: 'You are a helpful assistant',
  model: '__GATEWAY_OPENAI_MODEL__',
})

const durableAgent = createDurableAgent({ agent })

export const mastra = new Mastra({
  agents: { myAgent: durableAgent },
})
```

以流式方式生成响应并读取结果。运行结束且不再需要时，`cleanup` 函数会取消 PubSub 订阅：

```typescript
const { output, runId, cleanup } = await durableAgent.stream('Hello!')

const text = await output.text

cleanup()
```

### 普通 Agent 的 stream 配置 {/* #plain-agent-stream-configuration */}

普通 `Agent` 的 `durable` 选项只控制 stream 是否可恢复，不会包装 Agent，也不会启用检查点。要实现持久化执行，请显式使用 `createDurableAgent({ agent })`，并将 `maxSteps`、`shouldPersistSnapshot` 等执行选项传给该工厂方法。

## `createDurableAgent(options)` {/* #createdurableagentoptions */}

```typescript
import { createDurableAgent } from '@mastra/core/agent/durable'

const durableAgent = createDurableAgent({ agent })
```

## `createEventedAgent(options)` {/* #createeventedagentoptions */}

在内置事件驱动 Workflow 引擎上，为 `Agent` 添加启动后无需等待结果的持久化执行能力。与 `createDurableAgent` 一样，它返回可供流式读取的结果，但启动运行时不等待其完成：Mastra 实例上的 PubSub 事件会独立于调用方驱动执行。要使用事件驱动执行，需将 Agent 注册到配置了存储的 `Mastra` 实例；否则 Agent 会回退到默认的进程内引擎并记录警告。不支持覆盖 `id` 或 `name`。

```typescript
import { createEventedAgent } from '@mastra/core/agent/durable'

const eventedAgent = createEventedAgent({ agent })
```

返回：`EventedAgent`（`DurableAgent` 的子类）

## 方法 {/* #methods */}

### 执行 {/* #execution */}

#### `stream(messages, options?)` {/* #streammessages-options */}

以持久化执行方式流式生成响应。立即返回结果，其 `output` 会随着运行推进持续产生事件。

```typescript
const { output, runId, cleanup } = await durableAgent.stream('Hello!', {
  onChunk: chunk => console.log(chunk),
  onFinish: result => console.log('done', result),
})

const text = await output.text
cleanup()
```

返回：[`Promise<DurableAgentStreamResult>`](#durableagentstreamresult)

#### `resume(runId, resumeData, options?)` {/* #resumerunid-resumedata-options */}

恢复暂停的运行，例如等待 Tool 审批后的运行。传入原 stream 的 `runId` 及运行正在等待的数据。如果运行没有注册表条目，会抛出错误。如果其他执行仍持有该运行，`resume()` 最多等待 5 秒，随后抛出 `DURABLE_AGENT_EXECUTION_CONFLICT`。参阅[运行所有权](/docs/harness/durable-agents#run-ownership)。

```typescript
const { output, cleanup } = await durableAgent.resume(runId, {
  approved: true,
})

await output.text
cleanup()
```

返回：[`Promise<DurableAgentStreamResult>`](#durableagentstreamresult)

#### `observe(runId, options?)` {/* #observerunid-options */}

重新连接现有运行。网络断开后可使用此方法。对于通常支持的重连流程，请省略 `offset`：先重放所有可用的缓存事件，再接收实时事件。

无论是同一进程内观察实时运行，还是从另一进程观察持久化运行，执行观察的 Agent 的有效 `id` 都必须与启动该运行的 Agent 相同。有效 ID 指 DurableAgent 的 `id`（包括覆盖后的 ID），而不是被包装 Agent 的原始 ID。具有相同有效 ID 的不同 DurableAgent 实例可以观察同一次运行。

如果实时或持久化运行记录了不同的 owner Agent ID，`observe()` 会抛出 `DURABLE_AGENT_OBSERVE_AGENT_MISMATCH`。没有 owner 元数据的旧版实时条目保持原有行为。

对于配置了 `structuredOutput` 的运行，另一进程中的观察者会根据已保存的 schema 和重放的文本重建 `output.object`。

```typescript
const { output } = await durableAgent.observe(runId, {
  onChunk: chunk => console.log(chunk),
})

await output.text
```

`offset` 是从零开始、包含该位置的 PubSub 事件索引。它计数的是发布到该运行主题的所有已缓存事件（包括生命周期事件），而不是数据块数。从运行日志读取的数据块会在 `chunk.index` 中携带所属事件的索引；`stream()`、`observe()` 及 HTTP `/stream`、`/observe` 端点均如此。断线后要继续接收，可传入最后一个带索引的数据块的 `index + 1`；若尚未收到任何数据块，则省略 `offset`。生命周期事件也占用索引，却不产生数据块，因此索引可能不连续，不能用数据块数量作为 offset。

有些数据块没有 `index`。客户端自行构造 `object` 数据块，而不是从日志读取。`abort` 数据块与同一运行日志条目的 `finish` 一起发送，但只有 `finish` 携带索引，因此客户端若在两者之间重新连接，会再次收到 `abort`。

使用独立结构化模型的运行会将 `object-result` 发布到运行日志，因此该数据块带有 `index`，可以像其他数据块一样重放。持有 schema 的 core `observe()` 调用方也可以从重放的文本重建结构化输出，但只有重放了生成该结果的文本，才会得到 `object-result`。HTTP `/observe` 只重放日志，不会重建该结果。要在重连后重建结果，请不传 `offset` 进行观察，并跳过已处理过的 `index` 对应的数据块。重放过程也会重新构造之前收到的 `object` 数据块；它们没有 `index` 可供跳过。每个 `object` 数据块都是当时对象的快照，因此应保留最新的一个。索引来自重放缓存，所以缓存写入失败的数据块，或关闭缓存时的任何数据块，都没有 `index`，也无法通过 offset 从该处恢复。省略 `offset` 会重放传输层自身保留的内容（例如 Redis stream），可能重复收到已处理的数据块。下文介绍超出末尾的 offset 及不支持数字 offset 的传输。

`index` 是新增的字段，而 `offset` 的含义未变，因此已经传入日志位置或从 `0` 开始重放的代码无需修改。若代码传入的是已接收数据块的数量，则应改为最后一个数据块的 `index + 1`。

以下示例会在流式传输期间记录恢复用 offset，并在重连后传给 `observe()`：

```typescript
let offset: number | undefined
const { output } = await durableAgent.stream(messages, { runId })
for await (const chunk of output.fullStream) {
  if (chunk.index === undefined) continue
  offset = chunk.index + 1
}

// After a dropped connection:
const { output: resumed } = await durableAgent.observe(runId, { offset })
```

非零 offset 可能跳过较早的事件。聚合值只根据该观察者实际收到的数据块构建。若 offset 跳过了先前的文本增量，`output.text` 就只包含部分文本，结构化输出也可能不完整，或无法通过验证或解析。

当 PubSub 传输支持数字 offset 时，观察者只会在已发布事件的索引达到请求的 offset 后收到带编号的事件。若 offset 超过已保留的最大索引，既不会重放任何事件，也会跳过索引更小的实时事件。

没有 `index` 的事件（例如缓存写入失败的事件）无论 offset 是多少，都会在到达时交给观察者。

如果观察者已连接，而保留的日志过期或被清除，编号从 `0` 重新开始，该观察者会与新日志重新同步，并收到其中的事件，包括索引低于所请求 offset 的事件。检测采用尽力而为的方式。如果当时无法读取缓存，或新日志在首个事件到达前已编号超过观察者的位置，观察者可能无法识别这次重启，反而跳过这些事件。若观察者在重启后带着旧日志的 offset 重新连接，它无法区分新旧日志，会跳过新日志中低于该 offset 的事件；因此应省略 `offset`，以重放新日志。

对于不支持数字 offset 的传输（例如关闭缓存后的 `RedisStreamsPubSub`），`observe()` 只要传入 offset，包括 `0`，就会从新的实时事件开始接收，而不会重放保留的事件。core API 和 HTTP `/observe` 均如此。若要重放保留的事件，请省略 `offset`。（普通 `Agent` 的 HTTP `/observe` 则会重放保留的事件，因此可能重复收到已处理的事件。）

按索引重放仅限于配置的缓存中仍可用的事件。如果关闭缓存、`shouldCache` 排除了运行主题，或保留的事件已清除，缓存就没有可重放的内容。此时省略 `offset`，只会重放传输层自身保留的事件（如果有）。

缓存写入失败，只会使该事件无法从缓存读取。它没有 `index`；如果缓存能一步完成编号和追加，前后写入的事件仍可重放。内存缓存和 Valkey 缓存始终如此。`RedisServerCache` 在 Redis 脚本可用时也是一步完成；如果客户端没有 `eval`，或 Redis Cluster 以 `CROSSSLOT` 拒绝脚本，就会改为两步。保留默认 `listPushIndexed()` 的自定义缓存也采用两步。两步写入可能留下索引空档，导致按 offset 重放时跳过后续事件；因此遇到这种日志应不传 `offset` 重放，并跳过已处理的索引。缓存重放无法找回从未保存的事件；但如果传输层（如 `RedisStreamsPubSub`）保留了该事件，仍可在不带 `index` 的情况下将其送达。

使用跨进程 PubSub（如 Redis Streams）的事件驱动 Agent（`createEventedAgent()`），如果其步骤在启动运行的进程中执行，可以使用默认的内存 server cache，由该进程为事件编号。若步骤在另一进程中执行，例如以 `workers: true` 启动的专用 worker，请在 `Mastra` 实例上使用 `RedisServerCache` 等共享缓存。另一个进程无法共享内存计数器，因此其事件不会编号，offset 也无法跳过它们；发生这种情况时，Mastra 会在 worker 中记录警告。观察者若经由另一个进程（例如另一台服务器副本）重新连接，也应使用共享缓存，因为它无法从启动进程的内存缓存中重放事件。

默认情况下，`observe()` 会无限期等待事件。如果运行所在的进程意外停止，运行不再产生事件，也不会发出完成事件，因此观察用的 stream 会一直等待。可传入 `idleTimeoutMs`，让 stream 在限定的静默时间后结束。超时前，`observe()` 可调用可选的 `isAlive` 检查。工作仍在继续时（例如 Tool 调用耗时较长，或正在等待人工输入），应返回 `true`。返回 `false` 会使 stream 以错误结束；省略 `isAlive` 时也如此。`isAlive` 偶发抛错会被视为“仍在运行”，因此一次短暂的检查失败不会结束活动 stream。

```typescript
const { output } = await durableAgent.observe(runId, {
  idleTimeoutMs: 30_000,
  isAlive: () => runHeartbeat.isFresh(runId),
})
```

因空闲超时而结束运行，会执行与运行出错时相同的清理操作（参阅下方警告），因此缓存状态会被释放，而非保留。这两个选项都需要主动设置。省略它们可保留过去无限期等待的行为。

返回：`Promise<DurableAgentStreamResult>`

:::warning

`observe()` 返回的 `cleanup()` 会删除此次运行的注册表条目和缓存事件。只有在不再需要此次运行时才调用它。如果运行仍处于暂停状态，且你打算稍后恢复，请勿调用 `cleanup()`；应让自动清理计时器在运行结束或出错后处理。暂停事件不会触发自动清理。

:::

#### `prepare(messages, options?)` {/* #preparemessages-options */}

```typescript
const { runId, messageId, workflowInput, threadId, resourceId } = await durableAgent.prepare(

  },
```


### 取消运行 {/* #cancellation */}

#### `abortRunStream(runId)` {/* #abortrunstreamrunid */}

可在任何共享该 Agent 的 [PubSub](/docs/server/pubsub) 的进程中，通过 ID 停止运行。只需提供 `stream()` 或 `prepare()` 返回的 `runId`，因此后续请求也可以停止并非由它启动的运行。停止后的结果与在 stream 结果上调用 `abort()` 相同：stream 发出 `abort` 数据块、触发 `onAbort`，`observe()` 的消费者也会看到 stream 结束。

```typescript
const { runId } = await durableAgent.stream('Summarize the document')

// later, from a different request handler
durableAgent.abortRunStream(runId)
```

在多进程部署中，要通过 PubSub 发布中止请求，必须使用共享后端，例如 [`RedisStreamsPubSub`](/reference/pubsub/redis-streams)。默认的 `EventEmitterPubSub` 只能触达同一进程中的运行。若运行正在等待 Tool 审批，此方法只会在当前进程取消它；其他共享存储的进程仍可批准该调用。要在所有服务器上取消等待中的运行，请调用服务端的 `POST /agents/:agentId/runs/:runId/abort` 路由。它会将取消状态记录到存储中，使之后的审批或恢复以 `409 Conflict`（`AGENT_RESUME_ABORTED_RUN`）拒绝。

`InngestAgent` 未实现此方法。要取消 Inngest 运行，请使用其 `stream()` 返回的 `abort()`。

通过 `abortRunStream()` 或 `abortThreadStream()` 停止持久化运行，需要 `@mastra/core@1.62.0` 或更高版本。较早版本只记录中止请求，不会停止运行。

返回：`boolean`。如果当前进程在本地中止了运行，或能看到运行正在执行，则为 `true`。无论返回值如何，都会发布中止请求。

#### `abortThreadStream({ threadId, resourceId?, expectedRunId? })` {/* #abortthreadstream-threadid-resourceid-expectedrunid- */}

使用与 `abortRunStream()` 相同的中止请求，取消 memory thread 中正在运行的任务。运行从当前进程的 thread runtime 中解析，因此必须由当前进程启动，或由当前进程通过 `subscribeToThread()` 观察。服务端的 `POST /agents/:agentId/threads/abort` 路由使用此方法。

如果请求只能停止指定运行，请传入 `expectedRunId`。若处理请求前另一项排队运行变为活动状态，方法会返回 `false`，而不会中止接替的运行。省略 `expectedRunId` 则会中止请求处理时正在运行的任务。

```typescript
const aborted = durableAgent.abortThreadStream({
  resourceId: 'user-1',
  threadId: 'thread-1',
  expectedRunId: runId,
})
```

返回：`boolean`。如果当前进程没有记录该 thread 的活动运行，或活动运行与 `expectedRunId` 不匹配，则为 `false`；两种情况下都不会发送中止请求。

### 恢复运行 {/* #recovery */}

:::warning

恢复会从最后一次持久化的快照重新驱动运行。Mastra 将子 Agent 委派视为一个生成的 `agent-<name>` Tool 步骤，不会单独为其中的 LLM 或 Tool 调用建立检查点。如果恢复重放了该步骤，整个子 Agent 运行可能再次执行，包括已经完成的 Tool 副作用。应确保子 Agent 使用的 Tool 具有幂等性，或对其外部副作用去重。操作建议参阅[崩溃恢复](/docs/harness/durable-agents#crash-recovery)。

:::

#### `listActiveRuns(options?)` {/* #listactiverunsoptions */}

列出此 Agent 中持久化快照状态为 `running` 的运行，即 Workflow 引擎上次保存状态时 Agent 循环仍在执行的运行。在正常进程中，它们会转为 `suspended` 或终态；崩溃或重启后，它们会停留在 `running`，却没有执行驱动，`recoverActiveRuns()` 可重新驱动它们。不包括同一存储中其他 DurableAgent 启动的运行。

只有 `recovery.durableAgents` 为 `'auto'`，或自定义的 `shouldPersistSnapshot` 包含 `running` 时，才会写入 `running` 快照。否则此方法不会返回任何运行。参阅[快照持久化](/docs/harness/durable-agents#snapshot-persistence)。

```typescript
const { runs, total } = await durableAgent.listActiveRuns({ resourceId: 'user-1' })

for (const run of runs) {
  await durableAgent.recoverActiveRuns({ runId: run.runId })
}
```

只返回状态为 `running` 的运行。暂停的运行会保留快照，但不会列出；已完成的运行不会保留。可用 `resourceId` 将列表限定为单个用户。

#### `recoverActiveRuns(options?)` {/* #recoveractiverunsoptions */}

查找此 Agent 中停留在 `running` 状态的运行，并从最后一个持久化快照重新驱动它们。接受与 `listActiveRuns()` 相同的筛选条件和分页选项，另可传入 `runId`。返回每次运行的处理结果。

最多同时等待五次运行恢复，结果按发现顺序返回。每次尝试只有一个 30 秒的等待预算，涵盖 `recover()` 初始化及整个恢复后 Workflow 的完成过程。预算耗尽时，另一个运行可以占用该等待名额。超时会返回 `status: 'skipped'` 和 `reason: 'recovery-timeout'`，并将 `retryAt` 设为 30 秒后；它不会取消初始化或执行，不会释放有效的所有权声明，也不计为成功或失败。原尝试仍在后台继续，最终结果不会改变已返回的结果。并发上限限制的是等待数，不是仍在执行的运行数。

[`mastra.recoverAllDurableAgents()`](/reference/core/mastra-class#recoveralldurableagents) 会自动安排超时后的复查。直接调用 `recoverActiveRuns()` 时，调用方必须自行安排在 `retryAt` 之后再次调用。原批量恢复尝试仍未结束时，复查会通过另一个 `recovery-timeout` 和未来的 `retryAt` 延后，而不会再次调用 `recover()`。原尝试结束后，恢复流程会先检查持久化快照及归属权，再决定是否重试。已完成或已暂停的运行不会重新启动。

该预算只适用于 `recoverActiveRuns()` 中的每次运行恢复尝试，不适用于发现过程、直接调用 `recover()` 或被覆盖的自定义恢复方法。开始关闭时，恢复过程会停止分派新运行。即使等待超时，原尝试仍会被 Mastra 跟踪，参与共享的关闭排空流程。

```typescript
const result = await durableAgent.recoverActiveRuns()
// {
//   recovered: [
//     { runId: 'run-1', status: 'success' },
//     { runId: 'run-2', status: 'skipped', reason: 'run-active', retryAt: 1760123456789 },
//   ],
//   succeeded: 1,
//   failed: 0,
// }
```

传入 `runId` 可恢复单个已知运行：

```typescript
await durableAgent.recoverActiveRuns({ runId: 'run-abc-123' })
```

如果其他执行仍在驱动某个运行，`recoverActiveRuns()` 会返回 `status: 'skipped'` 和相应 `reason`，并让原执行继续控制该运行。要再次检查，必须另行调用。若运行由另一进程持有，`retryAt` 表示其所有权声明在未续期时失效的时间。若持有它的进程已崩溃，可在该时间之后调用 `recoverActiveRuns({ runId })` 恢复运行。[`mastra.recoverAllDurableAgents()`](/reference/core/mastra-class#recoveralldurableagents) 会自行安排这些复查。

| `reason` | 含义 |
| - | - |
| `run-active` | 其他执行（可能在另一进程）持有该运行。会设置 `retryAt`。 |
| `run-active-locally` | 当前进程正在执行该运行。 |
| `already-in-progress` | 当前进程已在恢复该运行。 |
| `recovery-timeout` | 等待已超时，或此前的批量恢复尝试仍在进行。设置 `retryAt`；复查时不会重复启动仍在进行的尝试。 |

返回：

```typescript

    retryAt?: number
  }>

  failed: number
}
```

#### `recover(runId, options?)` {/* #recoverrunid-options */}

按 ID 恢复单个运行，返回与 `stream()` 结构相同、可流式读取的结果。需要实时观察恢复 stream 时使用。

```typescript
const { output, cleanup } = await durableAgent.recover('run-abc-123', {
  onChunk: chunk => console.log(chunk),
  onError: ({ error }) => console.error(error),
})

await output.text
cleanup()
```

恢复从已持久化的 `durable-agentic-loop` 检查点重新开始。仅有嵌套执行记录是不够的。启动运行前，需在 `Mastra` 上启用 `recovery: { durableAgents: 'auto' }`，或提供包含 `'running'` 的 `shouldPersistSnapshot` 策略。即使已启用持久化，在首个运行中检查点保存之前，仍无法恢复。崩溃后才启用持久化，也无法重建缺失的检查点。

检查点之后的模型和 Tool 调用可能再次执行。请确保 Tool 的副作用具有幂等性；恢复不保证恰好执行一次。

检查点不可用或运行并未失去执行驱动时，`recover()` 会抛出以下错误：

| 错误 ID | 抛出条件 |
| - | - |
| `DURABLE_AGENT_RECOVER_CHECKPOINT_NOT_AVAILABLE` | 循环记录仍为 `pending`，且没有 Workflow 输入。没有可用于重新启动的检查点；不会启动恢复执行，已取得的恢复所有权声明也会释放。 |
| `DURABLE_AGENT_RUN_ACTIVE` | 其他执行持有该运行，且未设置 `force`。 |
| `DURABLE_AGENT_RECOVER_RUN_ACTIVE_LOCALLY` | 当前进程正在执行该运行；`force` 也不能覆盖。 |
| `DURABLE_AGENT_RECOVER_ALREADY_IN_PROGRESS` | 当前进程已在恢复该运行。 |
| `DURABLE_AGENT_RECOVER_RUN_SUSPENDED` | 运行已暂停；请使用 `resume()` 继续。 |
| `DURABLE_AGENT_RECOVER_RUN_NOT_ACTIVE` | 快照无法用于重启，且运行并非暂停状态。 |
| `DURABLE_AGENT_EXECUTION_CONFLICT` | 设置了 `force`，但接管期间其他执行声明了该运行的所有权。 |

服务端的 `POST /agents/:agentId/recover` 路由会针对所有权冲突、已在恢复、暂停运行和非活动运行返回 `409 Conflict`；检查点不可用时返回 `500 Internal Server Error`。
