# CLI 命令

您可以使用 Mastra 提供的命令行界面 (CLI) 来开发、构建和启动您的 Mastra 项目。

## `mastra dev` {/* #mastra-dev */}

启动一个暴露的服务器[Studio](/docs/studio/overview) and REST endpoints for your agents, tools, and workflows. You can visit [http://localhost:4111/swagger-ui](http://localhost:4111/swagger-ui)一次了解所有可用端点的概览`mastra dev`正在运行。

您还可以[configure the server](/reference/configuration#server-options).

### 旗帜 {/* #flags */}

该命令接受[common flags][common-flags] and the following additional flags:

#### `--https` {/* #--https */}

启用本地 HTTPS 支持。[Learn more](/reference/configuration#serverhttps).

#### `--inspect` {/* #--inspect */}

以检查模式启动开发服务器，有助于调试。 （可选）指定自定义主机和端口（例如，`--inspect=0.0.0.0:9229` for Docker). This can't be used together with `--inspect-brk`.

#### `--inspect-brk` {/* #--inspect-brk */}

以检查模式启动开发服务器并在脚本开头处中断。 （可选）指定自定义主机和端口（例如，`--inspect-brk=0.0.0.0:9229`). This can't be used together with `--inspect`.

#### `--custom-args` {/* #--custom-args */}

要传递给 Node.js 进程的以逗号分隔的自定义参数列表，例如`--require=newrelic` or `--experimental-transform-types`.

#### `--request-context-presets` {/* #--request-context-presets */}

包含以下内容的 JSON 文件的路径[request context](/docs/server/request-context) presets. When provided, a dropdown displays in Studio's request context editor, letting you quickly switch between preset configurations.

```bash
mastra dev --request-context-presets ./presets.json
```

该文件必须是 JSON 对象，其中每个键都是预设名称，每个值都是一个对象：

```json
{
  "development": { "userId": "dev-user", "env": "development" },
  "production": { "userId": "prod-user", "env": "production" }
}
```

### 配置 {/* #configs */}

您可以设置环境变量来修改`mastra dev`.

#### 跳过对等依赖性检查 {/* #skip-peer-dependency-check */}

放`MASTRA_SKIP_PEERDEP_CHECK=1` to skip the peer dependency version mismatch check at startup:

```bash
MASTRA_SKIP_PEERDEP_CHECK=1 mastra dev
```

这在 monorepo 开发过程中非常有用，因为此时对等依赖关系可能会发生冲突，但包尚未发布。

#### 禁用构建缓存 {/* #disable-build-caching */}

放`MASTRA_DEV_NO_CACHE=1` to force a full rebuild rather than using the cached assets under `.mastra/`:

```bash
MASTRA_DEV_NO_CACHE=1 mastra dev
```

当您调试捆绑器插件或怀疑过时的输出时，这会有所帮助。

#### 限制并行度 {/* #limit-parallelism */}

`MASTRA_CONCURRENCY`限制并行运行的昂贵操作数量（主要是构建和评估步骤）。例如：

```bash
MASTRA_CONCURRENCY=4 mastra dev
```

将其保留为未设置，以便 CLI 为计算机选择合理的默认值。

#### 自定义提供者端点 {/* #custom-provider-endpoints */}

使用 Vercel AI SDK 支持的提供程序时，您可以通过设置基本 URL 通过Agent或内部网关重定向请求。对于 OpenAI：

```bash
OPENAI_API_KEY=<your-api-key> \
OPENAI_BASE_URL=https://openrouter.example/v1 \
mastra dev
```

对于人择：

```bash
ANTHROPIC_API_KEY=<your-api-key> \
ANTHROPIC_BASE_URL=https://anthropic.internal \
mastra dev
```

这些被转发到 Mastra 型号路由器，并且可以与任何`"openai/..."`
or `"anthropic/..."` model selections.

## `mastra factory dev` {/* #mastra-factory-dev */}

启动开发服务器[Agent Builder](https://agent-builder.mastra.ai/) development. It uses the same dev runtime and flags as [`mastra dev`](#mastra-dev) and writes to the same `.mastra/output` directory.

```bash
npx mastra factory dev
```

两个命令共享相同的开发锁，因此`mastra dev` and `mastra factory dev` can't run simultaneously in the same project. If one is already running, the other exits with a duplicate development server error.

使用`mastra factory dev` when developing Agent Builder features. It accepts the same flags as [`mastra dev`](#mastra-dev), including `--https`, `--inspect`, `--inspect-brk`, `--custom-args`, and `--request-context-presets`.

## `mastra build` {/* #mastra-build */}

这`mastra build` command bundles your Mastra project into a production-ready Hono server. [Hono](https://hono.dev/) is a lightweight, type-safe web framework that makes it straightforward to deploy Mastra agents as HTTP endpoints with middleware support.

在幕后，Mastra 的 Rollup 服务器会找到您的 Mastra 条目文件并将其捆绑到生产就绪的 Hono 服务器。在捆绑过程中，它会摇动您的代码并生成用于调试的源映射。

输出在`.mastra` can be deployed to any cloud server using [`mastra start`](#mastra-start).

如果您要部署到[serverless platform](/docs/deployment/cloud-providers) you need to install the correct deployer to receive the correct output in `.mastra`.

它接受[common flags][common-flags].

### 旗帜 {/* #flags-1 */}

#### `--studio` {/* #--studio */}

将 Studio UI 与构建捆绑在一起。

### 配置 {/* #configs-1 */}

您可以设置环境变量来修改`mastra build`.

#### 跳过对等依赖性检查 {/* #skip-peer-dependency-check-1 */}

放`MASTRA_SKIP_PEERDEP_CHECK=1` to skip the peer dependency version mismatch check:

```bash
MASTRA_SKIP_PEERDEP_CHECK=1 mastra build
```

#### 限制并行度 {/* #limit-parallelism-1 */}

对于 CI 或在资源受限环境中运行时，您可以通过设置来限制一次运行的昂贵任务数量`MASTRA_CONCURRENCY`.

```bash
MASTRA_CONCURRENCY=2 mastra build
```

## `mastra start` {/* #mastra-start */}

:::

启动本地服务器以在生产模式下为您构建的 Mastra 应用程序提供服务。默认情况下，[OTEL Tracing](/docs/observability/tracing/overview) is enabled.

### 旗帜 {/* #flags-2 */}

该命令接受[common flags][common-flags] and the following additional flags:

#### `--dir` {/* #--dir */}

您构建的 Mastra 输出目录的路径。默认为`.mastra/output`.

#### `--custom-args` {/* #--custom-args-1 */}

要传递给 Node.js 进程的以逗号分隔的自定义参数列表，例如`--require=newrelic` or `--experimental-transform-types`.

## `mastra worker build` {/* #mastra-worker-build */}

捆绑您的 Mastra 应用程序以进行工作人员部署。产生相同的输出`mastra build`: a self-contained `.mastra/output/` directory.

```bash
mastra worker build [options]
```

### 旗帜 {/* #flags-3 */}

#### `--dir` {/* #--dir-1 */}

Mastra 源目录的路径。默认为`src/mastra`.

#### `--root` {/* #--root */}

项目根目录。默认为当前目录。

#### `--tools` {/* #--tools */}

要包含在捆绑包中的以逗号分隔的Tool路径。

#### `--output-dir` {/* #--output-dir */}

自定义输出目录。默认为`.mastra/output`.

#### `--debug` {/* #--debug */}

在构建期间启用调试日志记录。

## `mastra experiment build` {/* #mastra-experiment-build */}

构建一个独立的同伴工作线程，可以在不暴露 HTTP 服务器的情况下运行实验。工人装载你的出口`Mastra` instance and accepts versioned newline-delimited JSON (NDJSON) protocol messages on standard input. It writes protocol events to standard output.

```bash
mastra experiment build [options]
```

该命令将工作人员写入`.mastra/experiment-worker` by default. The directory contains the executable entry point, production dependencies, and `experiment-worker-manifest.json`. Treat standard output as protocol-only output. Worker diagnostics are written to standard error.

### 神器契约 {/* #artifact-contract */}

`experiment-worker-manifest.json`将工件标识为`mastra-experiment-worker` version `1` and provides:

* 可执行文件中嵌入的 CLI 版本、创建时间和唯一构建 ID。
* 支持的协议和数据集规范化版本。
* 启动工作程序所需的可执行文件、参数和工作目录。
* 依赖项清单和生成的锁定文件路径。
* 每个工件文件的排序 SHA-256 摘要。
* 从这些文件路径和摘要派生的 SHA-256 内容摘要。

内容摘要不包括`experiment-worker-manifest.json` to avoid a self-referential digest. Package the manifest with the rest of the directory. Use an outer package digest when the manifest itself must be attested.

### 协议合约 {/* #protocol-contract */}

工作人员实现固定实验同伴工作人员协议版本`1`. It reads strict UTF-8 NDJSON frames from standard input and requires every frame, including the last one, to end with a newline. Frames larger than 1 MiB, malformed or truncated frames, unsupported protocol or canonicalization versions, and messages that don't match the active experiment correlation are rejected as protocol failures.

运行请求必须与工件的嵌入式构建 ID 匹配，并包含有序数据集项目计数和 SHA-256 证明。工作进程发出连续的序列号，从`0`, timer-driven heartbeats, awaited experiment lifecycle events, and exactly one terminal event. Cancellation must match the active protocol version and experiment ID, plus the job ID, attempt, and idempotency key.

协议退出代码为：

|代码|意义|
| - | - |
|`0` | Completed |
| `10` | Completed with item errors |
| `20` | Fatal failure |
| `21` | Retryable failure |
| `30` | Cancelled |
| `31` | Timed out |
| `70` | Protocol failure |

### 数据包字段处理 {/* #packet-field-handling */}

工作人员将目标身份、有序内联数据集项、记分器 ID、并发性、超时、实验元数据、请求上下文、Tool模拟和取消传递给`runExperiment`. Scorer versions and artifact provenance are retained as experiment metadata. Scorer code provenance is enforced by artifact admission rather than runtime scorer lookup.

版本`1` uses deterministic undeclared-tool denial. Non-empty network allowlists and secret references are rejected with a policy failure because network enforcement and secret materialization belong to the process sandbox. Dataset item source and expected-trajectory fields are preserved as item metadata when passed to `runExperiment`.

### 旗帜 {/* #flags-4 */}

#### `--dir` {/* #--dir-2 */}

Mastra 源目录的路径。默认为`src/mastra`.

#### `--root` {/* #--root-1 */}

项目根目录。默认为当前目录。

#### `--output-dir` {/* #--output-dir-1 */}

自定义工件目录。相对路径是从项目根解析的。默认为`.mastra/experiment-worker`.

#### `--debug` {/* #--debug-1 */}

在构建期间启用调试日志记录。

## `mastra worker start` {/* #mastra-worker-start */}

：：：笔记

你需要跑`mastra worker build` or `mastra build` before using `mastra worker start`.

:::

从先前构建的包启动工作进程。可选的`name` argument sets `MASTRA_WORKERS` in the spawned process, controlling which worker starts.

```bash
mastra worker start [name] [options]
```

### 旗帜 {/* #flags-5 */}

#### `--dir` {/* #--dir-3 */}

构建输出目录的路径。默认为`.mastra/output`.

#### `--env` {/* #--env */}

环境文件的路径。默认为`.env.production`, falling back to `.env`.

### 示例 {/* #examples */}

```bash
# Start only the orchestration worker
mastra worker start orchestration

# Start only the scheduler
mastra worker start scheduler

# Start from a custom build directory
mastra worker start orchestration --dir ./dist
```

看[Workers](/docs/deployment/workers) for deployment topologies and configuration.

## `mastra studio` {/* #mastra-studio */}

开始[Studio](/docs/studio/overview) as a static server. After starting, you can enter your Mastra instance URL (e.g. `http://localhost:4111`) to connect Studio to your Mastra backend. Looks for `.env` and `.env.production` files in the current working directory for configuration.

该命令接受[common flags][common-flags] and the following additional flags:

运行 Studio 的端口。默认为`3000`.

要连接的 Mastra API 服务器的主机。默认为`localhost`.

#### `--server-protocol` {/* #--server-protocol */}

#### `--request-context-presets` {/* #--request-context-presets-1 */}

包含以下内容的 JSON 文件的路径[request context](/docs/server/request-context) presets. Works the same as the [`mastra dev` flag](#--request-context-presets).

```bash
mastra studio --request-context-presets ./presets.json
```

## `mastra deploy` {/* #mastra-deploy */}

构建您的项目并将其部署到由以下人员选择的 Mastra 平台环境`--env`. This is the recommended command for all new deploys and replaces both [`mastra studio deploy`](#mastra-studio-deploy) and [`mastra server deploy`](#mastra-server-deploy), which continue to work but should no longer be used for new setups.

需要通过身份验证[`mastra auth login`](#mastra-auth-login) or a `MASTRA_API_TOKEN` environment variable.

```bash
mastra deploy
mastra deploy --env staging
mastra deploy --env production --region eu
```

命令运行`mastra build` and zips the output before uploading it to the selected environment. It then polls the deploy status while streaming build logs until the deploy reaches a terminal state.

组织、项目和环境按以下顺序解析：环境变量 (`MASTRA_ORG_ID`, `MASTRA_PROJECT_ID`), CLI flag (`--org`, `--project`, `--env`), `.mastra-project.json` config file, current org from credentials, and lastly interactive prompt. On first deploy, the CLI saves the resolved org and project IDs to `.mastra-project.json` so subsequent deploys skip the prompts.

确认后，CLI 将创建一个缺失的项目`package.json` `name` field and creates a missing target environment, defaulting to `type: staging` for anything other than `production`. Combined with `--yes`, this creates and deploys everything in one non-interactive command:

```bash
mastra deploy --env staging --yes
```

什么时候`--env <name>` is set and `--env-file` isn't, the CLI auto-selects `.env.<name>` from the project directory if present (for example `.env.staging`). The `<name>` value is validated against a strict allowlist before being interpolated into a file path.

### 论点 {/* #arguments */}

#### `[dir]` {/* #dir */}

项目目录。默认为当前目录。

### 旗帜 {/* #flags-7 */}

#### `--env` {/* #--env-1 */}

目标环境名称。默认为`production`. Auto-selects `.env.<name>` from the project directory when `--env-file` isn't set. If the environment doesn't exist, the CLI creates it after confirmation.

#### `--org` {/* #--org */}

组织 ID。也可以通过设置`MASTRA_ORG_ID` environment variable.

#### `--project` {/* #--project */}

项目 ID、slug 或名称。也可以通过设置`MASTRA_PROJECT_ID` environment variable. If no project matches, the value is used as the name of a new project to create on deploy.

#### `-y, --yes` {/* #-y---yes */}

自动接受默认设置，无需确认提示，包括创建项目和环境。

#### `-c, --config` {/* #-c---config */}

项目配置文件的路径。默认为`.mastra-project.json`.

#### `--env-file` {/* #--env-file */}

与部署捆绑在一起的 env 文件的路径（相对于项目目录）。设置后，禁用`.env.<name>` auto-selection based on `--env`.

```bash
mastra deploy --env staging --env-file .env.staging.local
```

#### `--region` {/* #--region */}

新创建环境的区域（例如`eu`). Applied only when the CLI creates the environment.

#### `--skip-build` {/* #--skip-build */}

跳过构建步骤并部署现有的`.mastra/output` directory. The CLI warns if the existing build is stale relative to the current source.

#### `--skip-preflight` {/* #--skip-preflight */}

跳过构建输出的预上传验证。

#### `--debug` {/* #--debug-2 */}

在构建步骤期间启用调试日志。

### CI/CD 使用 {/* #cicd-usage */}

放`MASTRA_API_TOKEN`, `MASTRA_ORG_ID`, and `MASTRA_PROJECT_ID` as environment variables for headless deploys. Interactive prompts are skipped automatically when `MASTRA_API_TOKEN` is set. Combine with `--yes` to auto-accept environment creation.

```bash
export MASTRA_API_TOKEN="..."
export MASTRA_ORG_ID="..."
export MASTRA_PROJECT_ID="..."
mastra deploy --env staging --yes
```

## `mastra env` {/* #mastra-env */}

管理 Mastra 平台上的环境。环境是部署目标（例如`production`, `staging`, `preview-42`) that belong to a project. The current organization is resolved from stored credentials.

每个子命令都以固定顺序解析其项目。它首先检查`--project <name|slug|id>` flag, then the `MASTRA_PROJECT_ID` environment variable. It then reads the `.mastra-project.json` file written by [`mastra deploy`](#mastra-deploy) in the current directory. Run from your project directory and you never need to name the project.

### `mastra env list` {/* #mastra-env-list */}

列出项目的环境。每个环境都会显示其最新部署（带有`(active)` marker when it's serving traffic) and the env var names injected by managed resources such as attached databases.

```bash
mastra env list
```

#### `--json` {/* #--json */}

发出机器可读的 JSON。仅包含非敏感元数据（id、名称、slug、类型、区域、分支、URL、托管环境变量名称和最新部署状态），因此输出可以安全地登录 CI。

### `mastra env create` {/* #mastra-env-create */}

为项目创建新环境。

```bash
mastra env create staging --type staging --region eu
```

#### `-t, --type` {/* #-t---type */}

环境类型。之一`production`, `staging`, or `preview`. Defaults to `staging`.

#### `-r, --region` {/* #-r---region */}

环境区域（例如`eu`).

#### `--json` {/* #--json-1 */}

发出机器可读的 JSON。敏感字段被省略，如[`mastra env list`](#mastra-env-list).

### `mastra env delete` {/* #mastra-env-delete */}

删除环境。

```bash
mastra env delete <env>
```

`<env>`可以是环境名称、slug 或 ID。 CLI 会提示确认，除非`--yes` is passed.

#### `-y, --yes` {/* #-y---yes-1 */}

跳过确认提示。

### `mastra env restart` {/* #mastra-env-restart */}

重新启动环境的正在运行的服务，以便保存的环境变量（包括附加数据库中的托管变量）立即生效，而无需进行新的部署。

```bash
mastra env restart <env>
```

`<env>`可以是环境名称、slug 或 ID。如果环境从未部署过，则会失败并出现冲突错误。

### `mastra env vars pull` {/* #mastra-env-vars-pull */}

将环境的环境变量拉入本地环境文件（默认值：`.env`). The file contains the set a deploy of that environment runs with: the vars stored on the environment itself (for example, added in the dashboard's environment editor). Each environment is pulled on its own, and values stored on another environment are never merged in. Projects still on the [legacy pipeline](/docs/mastra-platform/deploy#migrating-from-server-and-studio-deploys) run from project-level vars instead, so pulling any of their environments returns those shared project-level values. Managed vars injected by attached databases are listed as comments (names only) since their values are platform-managed secrets.

```bash
mastra env vars pull
mastra env vars pull <env> --output .env.staging
```

`<env>`可以是环境名称、slug 或 ID，并且当项目只有一个环境时可以省略。该文件是用`0600` permissions. The command stops if the output file already exists. Pass `--force` to replace it.

#### `-o, --output` {/* #-o---output */}

要写入的文件。默认为`.env`.

#### `-f, --force` {/* #-f---force */}

替换现有的输出文件。

### `mastra env db` {/* #mastra-env-db */}

管理附加到 Mastra 平台上的项目的数据库。数据库由托管Provider（例如 Turso 或 Neon）进行配置，并将其连接环境变量自动注入到部署中。

数据库是**environment-scoped** (its env vars only go to one environment) or **shared** (project-scoped: its env vars go to all environments). Environment-scoped is the default for `mastra env db create`: pass an environment argument, or let the CLI pick or prompt for one. Pass `--shared` on create to attach a shared database instead. For other subcommands (`list`, `delete`, `keys`), pass the environment argument to work with environment-scoped databases and omit it for shared databases.

创建和删除数据库需要`admin` role in the organization.

### `mastra env db list` {/* #mastra-env-db-list */}

列出附加到项目的数据库，包括提供程序、配置状态、范围（每个数据库提供的环境）以及每个数据库注入的环境变量名称。传递环境以仅显示提供该环境的数据库（环境范围内的加上共享的）。

```bash
mastra env db list
mastra env db list <env>
```

#### `--json` {/* #--json-2 */}

发出机器可读的 JSON。

### `mastra env db create` {/* #mastra-env-db-create */}

配置并附加托管数据库，然后轮询直至其准备就绪。配置错误与提供者的错误详细信息一起打印。

默认情况下，数据库的范围仅限于单个环境。传递一个环境参数来选择它。如果省略该参数，CLI 将使用项目的唯一环境或在多个可用时提示您。在非交互式环境中（CI、`--json`) an environment argument is required. Pass `--shared` to attach a project-scoped database that's shared by every environment instead.

环境范围的数据库从环境继承其提供者区域。共享数据库接受`--region`.

```bash
mastra env db create --kind turso                                    # picks or prompts for an environment
mastra env db create staging --kind turso                            # scoped to the "staging" environment
mastra env db create --kind turso --shared                           # shared by all environments
mastra env db create --kind neon --name my-app-db --region aws-us-east-1 --shared
mastra env db create production --kind postgres                      # VPC-isolated Postgres, private to the environment
```

#### `--kind` {/* #--kind */}

数据库Provider（必需）。之一`turso`, `neon` (public serverless Postgres), or `postgres` (VPC-isolated Postgres that runs on the same private network as the deployed environment).

#### `--name` {/* #--name */}

数据库名称。默认为从项目 slug 和提供程序派生的名称（例如`my-app-turso`, `my-app-pg` for Neon, or `my-app-postgres` for VPC Postgres).

#### `--region` {/* #--region-1 */}

共享数据库的Provider区域 ID。对于环境范围的数据库将被忽略。

#### `--shared` {/* #--shared */}

作为由每个环境共享的项目范围数据库附加。不能与环境参数结合使用。

#### `--no-wait` {/* #--no-wait */}

连接排队后立即返回，而不是轮询直到数据库准备就绪。稍后检查进度`mastra env db show`.

#### `--json` {/* #--json-3 */}

发出机器可读的 JSON。在此模式下，环境参数或`--shared` is required when the project has more than one environment (no interactive prompt).

### `mastra env db show` {/* #mastra-env-db-show */}

显示数据库详细信息，一旦数据库准备就绪，就会显示其连接环境变量。默认情况下，秘密值会被屏蔽。

```bash
mastra env db show <database>
```

`<database>`可以是数据库 ID 或名称。

#### `--show-secrets` {/* #--show-secrets */}

打印秘密连接值而不是屏蔽它们。

#### `--json` {/* #--json-4 */}

发出机器可读的 JSON。秘密值被屏蔽，除非`--show-secrets` is passed.

### `mastra env db delete` {/* #mastra-env-db-delete */}

永久删除提供程序的数据库，包括其所有数据。这无法撤消。 CLI 会提示确认，除非`--yes` is passed. After deletion, deploys no longer receive the database's env vars.

```bash

```

#### `-y, --yes` {/* #-y---yes-2 */}

跳过确认提示。

### `mastra env deploys` {/* #mastra-env-deploys */}

列出项目的部署，最新的在前。为流量提供服务的部署已被标记`(active)`.

```bash
mastra env deploys [environment]
```

忽略`[environment]` to show deploys across all environments; pass an environment name, slug, or ID to filter to one.

#### `--json` {/* #--json-5 */}

发出机器可读的 JSON。

### `mastra env diagnosis` {/* #mastra-env-diagnosis */}

诊断失败的部署并打印修复建议。每项建议都包含描述、建议的操作和适用时的文档链接，后跟仪表板中部署日志的链接。

```bash
mastra env diagnosis
mastra env diagnosis <deploy-id>
mastra env diagnosis --environment staging
```

忽略`<deploy-id>` to diagnose the environment's latest deploy. The environment comes from `--environment`, or from the project when it has exactly one environment. Projects with several environments require `--environment` or a deploy ID. A deploy ID passed on its own works without a linked project.

如果部署成功运行，该命令会报告不需要建议并退出。否则，当诊断尚不存在时，它会开始诊断，并进行轮询，直到结果准备就绪，最多持续五分钟。重新运行该命令会重复使用正在进行的诊断，而不是重新启动它。当诊断本身失败时，该命令会以非零代码退出。

一次失败后`mastra deploy`, the CLI prints the exact `mastra env diagnosis <deploy-id>` command to run.

#### `--project` {/* #--project-1 */}

项目名称、slug 或 ID。默认为链接的项目，如中所述[`mastra env`](#mastra-env).

#### `--environment` {/* #--environment */}

环境名称、slug 或 ID。默认为项目的唯一环境。当项目有多个且未传递部署 ID 时需要。

## `mastra studio deploy` {/* #mastra-studio-deploy */}

：：：笔记

`mastra studio deploy`继续工作但被取代[`mastra deploy`](#mastra-deploy), which supports environments (`--env staging`, `--env production`) on a single project. New setups should use `mastra deploy`.

:::

构建您的项目并将其部署到 Mastra 平台。需要通过身份验证[`mastra auth login`](#mastra-auth-login) or a `MASTRA_API_TOKEN` environment variable.

```bash
mastra studio deploy
```

命令运行`mastra build` and zips the output. It reads an env file from the project directory before uploading everything to the platform. After uploading, it polls the deploy status and streams build logs until the deploy reaches a terminal state.

部署命令会自动加载项目的`.env` file. If `MASTRA_PROJECT_ID` points to a project that was provisioned for Observability, the deploy links to that project instead of creating a new one. Deploying Studio to an observability-only project converts it into a Studio project on the platform side.

CLI 至少需要一个`.env` or `.env.*` file (excluding `.env.example`) in the project directory and fails with `Error: No env file found for deploy.` if none exists. When multiple env files are present, the CLI prompts you to pick one (defaulting to `.env.production`). Pass `--env-file` to choose explicitly. With `--yes` and multiple env files, you must pass `--env-file` or the deploy errors.

组织和项目按以下顺序解析：环境变量标志，`.mastra-project.json` config file, current org from credentials, and lastly interactive prompt. On first deploy, the CLI saves the resolved IDs to `.mastra-project.json` so subsequent deploys skip the prompts.

如果`--project <value>` doesn't match an existing project (by ID or slug), the CLI treats `<value>` as a new project name and creates it after confirmation. Combined with `--yes`, this creates and deploys a new project in one non-interactive command:

```bash
mastra studio deploy --project "my-new-project" --yes
```

#### `[dir]` {/* #dir-1 */}

### 旗帜 {/* #flags-8 */}

#### `--org` {/* #--org-1 */}

#### `--project` {/* #--project-2 */}

项目 ID 或 slug。也可以通过设置`MASTRA_PROJECT_ID` environment variable. If no project matches, the value is used as the name of a new project to create on deploy.

#### `-y, --yes` {/* #-y---yes-3 */}

自动接受默认值，无需确认提示。

#### `-c, --config` {/* #-c---config-1 */}

项目配置文件的路径。默认为`.mastra-project.json`.

#### `--env-file` {/* #--env-file-1 */}

与部署捆绑在一起的 env 文件的路径（相对于项目目录）。使用它可以通过指向不同的 env 文件（例如`.env.staging`, `.env.production`).

```bash
mastra studio deploy --env-file .env.staging --yes
```

#### `--skip-build` {/* #--skip-build-1 */}

跳过构建步骤并部署现有的`.mastra/output` directory.

#### `--debug` {/* #--debug-3 */}

在构建步骤期间启用调试日志。

### CI/CD 使用 {/* #cicd-usage-1 */}

#### `--watch, -w` {/* #--watch--w */}

#### `--follow, -f` {/* #--follow--f */}

实时传输日志。

#### `--tail` {/* #--tail */}

### `mastra studio deploy suggestions` {/* #mastra-studio-deploy-suggestions */}

```bash

```

当你省略`deploy-id`, the command uses the latest deploy for the linked project and starts a diagnosis if needed, polling until the results are ready. Suggestions appear only when the diagnosis finds a problem.

## `mastra auth` {/* #mastra-auth */}

管理 Mastra 平台的身份验证。凭证存储在`~/.mastra/credentials.json`. You can also set the `MASTRA_API_TOKEN` environment variable as an alternative to interactive login.

### `mastra auth login` {/* #mastra-auth-login */}

打开浏览器进行登录并在本地存储凭据。

当需要浏览器登录并且没有交互式终端时（在 CI 中，当输入或输出通过管道传输时，或者在Agent的 shell 中），该命令首先打印如何验证无头 shell，然后仍然等待浏览器登录。在同一台机器上，您可以运行`mastra auth login` once in your own terminal so later commands reuse the saved session. In CI or on another machine, set `MASTRA_API_TOKEN` and `MASTRA_ORG_ID` instead. Create the token from a signed-in terminal with [`mastra auth tokens create`](#mastra-auth-tokens-create) or in the dashboard. If the browser sign-in wait times out, the command exits with status 1. If `MASTRA_API_TOKEN` is already set in a non-interactive shell, the command skips browser sign-in: it verifies the token and checks that an organization is selected (from `MASTRA_ORG_ID` or saved credentials), then exits with status 0. If either check fails, it exits with status 1 and names what's missing.

### `mastra auth logout` {/* #mastra-auth-logout */}

删除存储的凭据。如果`MASTRA_API_TOKEN` is still set in the environment, the CLI warns that it will continue to be used.

### `mastra auth whoami` {/* #mastra-auth-whoami */}

显示当前用户电子邮件、用户 ID 和活动组织。

### `mastra auth orgs` {/* #mastra-auth-orgs */}

列出所有组织以及您在每个组织中的角色。当前组织已被标记。

#### `mastra auth orgs switch` {/* #mastra-auth-orgs-switch */}

通过交互式提示切换活动组织。无法使用时`MASTRA_API_TOKEN` or `MASTRA_ORG_ID` environment variables are set.

### `mastra auth tokens` {/* #mastra-auth-tokens */}

列出所有 API 令牌及其上次使用日期。

#### `mastra auth tokens create` {/* #mastra-auth-tokens-create */}

创建一个新的 API 令牌。该秘密仅显示一次，无法再次检索。

```bash
mastra auth tokens create <name>
```

使用`--permission` to grant the token extra access. The available permission is `databases:write`, which lets the token create and delete managed databases, for example from CI. Only organization admins can create tokens with permissions. Repeat the flag to grant more than one.

如果平台在没有请求权限的情况下创建令牌，则该命令将撤销该令牌并退出并出现错误。如果撤销也失败，则错误显示`mastra auth tokens revoke` command to run.

```bash
mastra auth tokens create ci --permission databases:write
```

#### `mastra auth tokens revoke` {/* #mastra-auth-tokens-revoke */}

撤销 API 令牌。

```bash
mastra auth tokens revoke <token-id>
```

## `mastra connect` {/* #mastra-connect */}

管理链接平台项目的Provider连接，以便Agent使用`@mastra/connect` pick up provider toolsets without leaving the terminal.

命令使用您登录的组织`mastra auth login`. Switch organizations with `mastra auth orgs switch`.

目标项目由`--project` flag, the `MASTRA_PROJECT_ID` environment variable, or the `.mastra-project.json` written by `mastra deploy`, in that order. All subcommands accept `--project <name|slug|id>`.

### `mastra connect list` {/* #mastra-connect-list */}

首先列出具有连接的Provider的Provider。活动连接显示为绿色，需要重新授权的连接显示为黄色，未连接的Provider显示为灰色。尚不可用的Provider被标记为即将推出。

```bash
mastra connect list
```

### `mastra connect add` {/* #mastra-connect-add */}

将提供者连接到项目。当组织已拥有未附加到项目的提供者连接时，该命令会列出它们并允许您附加现有连接或创建新连接。由于没有现有连接，它会直接进入Provider的身份验证流程。

OAuth Provider会在您的浏览器中打开Provider的同意屏幕，并打印其 URL（如果您需要手动打开它）。 API 密钥和基本身份验证提供程序会在终端中提示输入凭据，并在完成连接之前对其进行验证。具有其他身份验证类型的Provider会打开托管连接页面。该命令会等到连接变为活动状态后再退出。

凭据提示需要交互式终端，即使使用`--yes`. Run the command outside CI or connect through the platform UI. Each provider's [integration page](/docs/mastra-platform/connect#providers) lists its API key and permission requirements.

一旦新连接处于活动状态，该命令就会提供设置显示名称的功能，以便您可以区分与同一Provider的连接。它列出了提供者的现有连接，建议一个不与它们冲突的名称，并要求确认所选名称是否与另一个连接的名称重复。将该字段留空以跳过命名。设置显示名称需要组织管理员角色；如果命名失败，连接仍保持活动状态。

```bash
mastra connect add <provider>
```

经过`--yes` to skip all prompts. This always creates a new connection without a display name, even when existing connections could be reused.

### `mastra connect remove` {/* #mastra-connect-remove */}

取消Provider与项目的连接。组织级别的连接将被保留，并可以在以后重新连接。

```bash
mastra connect remove <provider>
```

当提供程序有多个连接时，命令会提示删除哪一个连接。经过`--yes` to skip confirmation. Without a terminal, or with `--yes`, removing several connections at once requires `--all`, and `--connection <id>` removes a single one.

### 替换需要重新授权的连接 {/* #replace-a-connection-that-needs-reauthorization */}

`mastra connect list`标记需要重新授权的连接，例如在撤销Provider API 密钥后。连接Tool解析会跳过这些连接并发出警告。

取消受影响连接的链接，然后添加一个新连接：

```bash
mastra connect remove posthog
mastra connect add posthog
```

如果项目有多个连接，请在删除时选择受影响的连接。什么时候`add` offers to reuse an organization connection, choose **Create a new connection** and authorize it with valid credentials.

## `mastra migrate` {/* #mastra-migrate */}

运行数据库迁移以更新您的存储架构。当升级包含存储架构更改的 Mastra 版本时，此命令非常有用。

该命令捆绑您的项目并连接到您配置的存储后端。然后它执行任何挂起的迁移。目前支持：

* **重复跨度迁移**：删除重复的`(traceId, spanId)` entries and adds a unique constraint to ensure data integrity.
* **ClickHouse 旧版到 vNext 跨度迁移**：从遗产中复制历史跨度`mastra_ai_spans` table to the vNext `mastra_span_events` schema. Runs in batches to stay within memory limits. See the [ClickHouse storage reference](/integrations/databases/clickhouse#migrating-from-legacy-to-vnext) for details.

```bash
mastra migrate
```

请参阅[Storage migration guide](/reference/migrations/upgrade-to-v1/storage#duplicate-spans-migration) for details on when migrations are needed.

它接受[common flags][common-flags].

## `mastra traces import` {/* #mastra-traces-import */}

将历史跟踪从受支持的ObservabilityProvider导入到现有的 Mastra 平台项目中。该命令在本地准备完整的跟踪，批量上传整个跟踪，支持恢复，并通过 Mastra 平台验证样本。

```bash
mastra traces import <provider> [options]
```

目前支持以下Provider：

|Provider|论证|要求|
| - | - | - |
|朗福斯|`langfuse` | Langfuse Cloud or self-hosted Langfuse v4 or later |

看[Import existing traces](/docs/mastra-platform/observability#import-existing-traces) for the complete workflow, data mapping, local-file lifecycle, and limits.

### 选项 {/* #options */}

#### `--target-project <name|slug|id>` {/* #--target-project-nameslugid */}

选择接收跟踪的目标 Mastra 平台项目。优先于`MASTRA_PROJECT_ID`. Without either value, the command uses the project linked in `.mastra-project.json`. The source project comes from the provider credentials, such as `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY`.

#### `--since <date>` {/* #--since-date */}

将导入窗口的起始时间设置为 ISO 8601 日期或时间戳。默认为30天前`--until`, clamped to the current 30-day Platform retention boundary. `--from` is accepted as an alias.

#### `--until <date>` {/* #--until-date */}

将导入窗口的独占结束设置为 ISO 8601 日期或时间戳。默认为导入开始的时间，不能是将来的时间。`--to` is accepted as an alias.

完整的窗口必须在当前 30 天的平台保留期内，`--since` must be earlier than `--until`, and the window can't exceed 30 days.

#### `--dry-run` {/* #--dry-run */}

读取源代码并在本地准备有效的跟踪，而无需上传它们。该命令写入报告并打印恢复准备导入的命令。

#### `--resume <import-id>` {/* #--resume-import-id */}

使用保存的提供程序、目标项目、日期窗口和确认的进度恢复准备好的导入。使用生成的恢复命令中显示的相同目标项目。该选项不能与`--since`, `--until`, or `--dry-run`.

#### `-y, --yes` {/* #-y---yes-4 */}

无需确认即可上传。

### 环境变量 {/* #environment-variables */}

该命令加载`.env` and `.env.local` from the current directory.

|变量|必填|描述 |
| - | - | - |
|`LANGFUSE_PUBLIC_KEY` | For new Langfuse imports | Public project API key. Together with the secret key, it selects the source Langfuse project. |
| `LANGFUSE_SECRET_KEY` | For new Langfuse imports | Secret project API key. |
| `LANGFUSE_BASE_URL` | No | Langfuse host. Defaults to `https://cloud.langfuse.com`. |
| `MASTRA_API_TOKEN` | For headless authentication | Mastra Platform API token. Without it, the command uses credentials from `mastra auth login`. |
| `MASTRA_ORG_ID` | With `MASTRA_API_TOKEN` | Organization that owns the destination project. |
| `MASTRA_PLATFORM_ACCESS_TOKEN` | For upload and read-back with interactive login | Mastra Platform access token for the destination. Not required for `--dry-run` or when `MASTRA_API_TOKEN` is set. |
| `MASTRA_PROJECT_ID` | When no project is otherwise linked | Destination project ID. The `--target-project` flag takes precedence over it. |

### 示例 {/* #examples-1 */}

预览默认的 30 天窗口而不上传：

```bash
mastra traces import langfuse --target-project my-mastra-project --dry-run
```

导入较小的日期窗口而不显示确认提示：

```bash
mastra traces import langfuse \
  --target-project my-mastra-project \
  --since "$SINCE" \
  --until "$UNTIL" \
  --yes
```

恢复现有导入：

```bash
mastra traces import langfuse \
  --resume 00000000-0000-0000-0000-000000000000 \
  --target-project my-mastra-project
```

## `mastra api` {/* #mastra-api */}

使用 JSON 输入和 JSON 输出调用 Mastra 运行时服务器。将其用于本地开发服务器、部署的 Mastra 平台项目、自托管 Mastra 服务器或托管的 Mastra 平台Observability API。

```bash
mastra api agent list
mastra api agent run weather-agent '{"messages":"What is the weather in London?"}'
mastra api tool execute get-weather '{"location":"San Francisco"}'
mastra api trace list '{"page":0,"perPage":20}'
```

使用`mastra api <resource> <action> --help` to see examples for a command.

### 输出 {/* #output */}

成功响应将写入`stdout` as JSON. Single-resource commands return:

```json
{ "data": {} }
```

列表命令返回一个`data` array and pagination metadata:

```json
{ "data": [], "page": { "total": 0, "page": 0, "perPage": 0, "hasMore": false } }
```

错误被写入`stderr` as JSON and return a non-zero exit code:

```json
{
  "error": {
    "code": "SERVER_UNREACHABLE",
    "message": "Could not connect to target server",
    "details": {}
  }
}
```

退出代码反映请求是否成功，而不是响应的内容：

* `0`：服务器返回成功的响应。这包括空结果和报告现有状态的有效负载，例如表明记录已存在的Tool结果。返回带有以下内容的对象的Tool`error` field still exits `0`, so check the `data` payload when the tool reports its own failures.
* `1`: 请求失败。这包括无法访问的服务器、无效的 JSON 输入、丢失的资源或引发错误的Tool。

如果读取输出的命令提前退出，如`| head`, the exit code still reflects whether the request succeeded.

### 目标分辨率 {/* #target-resolution */}

对于运行时命令，该命令按以下顺序解析目标服务器：

1. `--url <url>`对于显式远程或自托管服务器。
2. `http://localhost:4111`对于当地人来说`mastra dev` server.
3. `.mastra-project.json`对于 Mastra 平台项目。

当 CLI 解析项目时，将使用自动平台身份验证`.mastra-project.json` or recognizes an explicit Mastra-hosted Studio, Factory, or observability URL. Localhost and arbitrary explicit `--url` targets don't receive automatic credentials. Headers passed with `--header` are sent to any target, including localhost.

对于Observability命令（`trace`, `log`, `score`, and `metric`), the CLI targets the United States endpoint at `https://observability.mastra.ai` by default instead of a project deployment URL. Trace Intelligence commands (`learning`) work the same way but target `https://output.signals.mastra.ai`. When the CLI selects either hosted target automatically, it resolves credentials in this order:

1. 显式的`Authorization` and `X-Mastra-Project-Id` headers passed with `--header`.
2. `MASTRA_PLATFORM_ACCESS_TOKEN`和`MASTRA_PROJECT_ID` from your environment.
3. 项目元数据来自`.mastra-project.json` for the project ID.
4. 您的 Mastra CLI 登录令牌作为身份验证后备。

学习命令也发送`X-Mastra-Organization-Id`, resolved from an explicit `--header`, `MASTRA_ORGANIZATION_ID` in your environment, or `.mastra-project.json`, in that order.

欧盟Observability数据存储在`https://observability.eu.mastra.ai`. Pass that trusted host with `--url`; it uses the same Platform credential resolution as the default United States endpoint:

```bash
mastra api --url https://observability.eu.mastra.ai trace list
```

使用`--url` and `--header` when you need to override another target or its credentials.

### 工厂命令 {/* #factory-commands */}

使用`mastra api factory` to manage Factory projects, work items, decisions, attention items, and queue health. These commands use the same JSON input, output, authentication, headers, timeout, and target resolution as other `mastra api` commands.

列出当前组织可用的 Factory 项目：

```bash
mastra api factory project list
```

在发送受控工作项转换之前检查生成的请求架构：

```bash
mastra api factory work-item transition --schema
```

使用其当前版本移动工作项：

```bash
mastra api factory work-item transition <project-id> <work-item-id> '{"board":"work","stage":"planning","requestId":"00000000-0000-4000-8000-000000000000","cause":"manual","expectedRevision":1}'
```

使用以下命令部署项目后`mastra deploy`, the resulting non-secret `.mastra-project.json` lets the CLI find the hosted Factory instance, apply your Mastra CLI credentials, and select the deployed project's organization automatically. For an explicit hosted Factory `--url`, the CLI uses `MASTRA_ORG_ID` when set, then the organization selected by `mastra auth orgs switch`. An explicit `X-Mastra-Organization-Id` header takes precedence over both. Before deployment, or to target a specific local, remote, or self-hosted Factory server, pass `--url` instead:

```bash
mastra api --url http://localhost:4111 factory project list
```

工厂端点使用其根级别`/web/factory/...` paths. `--server-api-prefix` still controls local target probing, but it isn't prepended to Factory requests.

### 旗帜 {/* #flags-13 */}

#### `--url <url>` {/* #--url-url */}

定位特定的 Mastra 服务器 URL。

```bash

```

Use this when the server is mounted under a custom prefix (for example a `@mastra/fastify` `MastraServer` with `prefix: "/api/mastra-studio"`), the same way `mastra studio` accepts `--server-api-prefix`. ```


设置请求超时（以毫秒为单位）。默认为`30000`. Workflow run start and resume commands default to `120000`.

漂亮打印的 JSON 输出。默认为`false`.

#### `--schema` {/* #--schema */}

打印接受 JSON 输入的命令的面向 CLI 的请求架构。该模式来自目标服务器的路由契约，包括命令形状、位置、示例、请求模式和响应形状。

`--schema`在接受 JSON 输入的叶命令上可用。它不能作为顶级使用`mastra api` flag.

```bash

```

### 输入模型 {/* #input-model */}

接受输入的命令采用一个内联 JSON 参数。不要传递文件路径或标准输入。

```bash
mastra api workflow run start data-pipeline '{"inputData":{"source":"s3://bucket/data.csv"}}'
```

使用位置参数作为稳定 ID，使用 JSON 作为过滤器或负载。对于同时需要查询参数和请求正文的路由，请传递一个 JSON 对象。 CLI 根据服务器路由架构分割输入。

```bash
mastra api thread create '{"agentId":"weather-agent","resourceId":"user_123","threadId":"thread_abc123","title":"Support conversation"}'
```

列表命令接受`page` and `perPage` in the JSON input when the target route supports pagination:

```bash
mastra api score list '{"page":0,"perPage":50}'
mastra api trace list '{"page":0,"perPage":20}'
```

支持过滤器的路由在同一 JSON 输入中接受它们。例如，可观察性跟踪列表支持分页和路由支持的过滤器：

```bash
mastra api trace list '{"page":0,"perPage":20,"filters":{"spanType":"agent"}}'
```

有关支持的字段、运算符和请求选项，请参阅[Query traces](/reference/observability/tracing/advanced-queries#query-traces). For a local Mastra server, you can also inspect its request and response schemas:

```bash
mastra api --url http://localhost:4111 trace query --schema
```

Mastra 平台当前不公开所使用的架构端点`--schema`. To find fields and values recorded in your project, use [field and value discovery](/reference/observability/tracing/advanced-queries#discover-fields-and-values).

响应仍然嵌套在`data` to preserve cursor pagination:

```json
{
  "data": {
    "traces": [],
    "page": { "next": "opaque-cursor" }
  }
}
```

每次调用都会进行一次查询。传递一个非空值`data.page.next` value back as `page.after` in the next query. See [Pagination and errors](/reference/observability/tracing/advanced-queries#pagination-and-errors) for pagination modes, cursor handling, and errors.

要加载编号页面然后轮询，请在两个请求中保持相同的时间范围和谓词：

```bash
mastra api trace query '{"timeRange":{"from":"2026-08-01T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"pagination":{"page":0,"perPage":100}}'
mastra api trace query '{"timeRange":{"from":"2026-08-01T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"mode":"delta","after":"CURSOR_FROM_NUMBERED_RESPONSE","limit":100}'
```

代替`CURSOR_FROM_NUMBERED_RESPONSE` with `data.deltaCursor` from the first response. Delta results remain under `data`, with `traces`, `delta: { limit, hasMore }`, and `deltaCursor`. Merge traces by `traceId`, retain each returned cursor, and continue immediately while `data.delta.hasMore` is `true`. Don't combine delta mode with `page`, `pagination`, or `orderBy`.

省略`after` establishes a cursor and returns no historical traces. Changing the time range or predicate requires a fresh numbered request. See [Delta polling limitations](/reference/observability/tracing/advanced-queries#poll-after-loading-a-numbered-page) before using this workflow to maintain a local trace list.

#### `mastra api trace aggregate` {/* #mastra-api-trace-aggregate */}

对按时间范围和可选选项选择的轨迹进行分组`where` predicate, and returns one row of measures per group, or per group and non-empty time bucket when `interval` is set. The inline JSON input is required and accepts the same predicates as `trace query`. Like other observability commands, it targets `https://observability.mastra.ai` by default.

```bash
mastra api trace aggregate <input>
mastra api trace aggregate '{"timeRange":{"from":"2026-08-01T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"groupBy":["entityName"],"measures":["count","errorRate"]}'
```

放`interval` to `1m`, `5m`, `15m`, `1h`, or `1d` to split each group into time buckets:

```bash
mastra api trace aggregate '{"timeRange":{"from":"2026-08-01T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"where":{"op":"eq","left":{"path":"entityName"},"right":{"literal":"weather-agent"}},"interval":"1d","measures":["count","duration.p95"]}'
```

有关维度、度量和请求选项，请参阅[Aggregate traces](/reference/client-js/observability#aggregate-traces). Run `mastra api trace aggregate --help` for more examples.

响应仍然嵌套在下面`data` so `truncated` is preserved. `truncated` is `true` when more groups matched than `limit`:

```json
{
  "data": {
    "rows": [
      {
        "dimensions": { "entityName": "weather-agent" },
        "measures": { "count": 42, "errorRate": 0.05 }
      }
    ],
    "truncated": false
  }
}
```

可观察性存储不支持跟踪聚合返回的服务器`501`. The CLI prints it like other request failures, as an `HTTP_ERROR` with the server response in `error.details.body`.

#### `mastra api span query` {/* #mastra-api-span-query */}

查询完成的可观察性跨越跟踪，包括嵌套在其他跟踪内的Agent运行和Tool调用。内联 JSON 输入是必需的，并且使用与以下相同的请求[`querySpans()`](/reference/observability/tracing/advanced-queries#query-spans). Its `where` predicate filters span fields directly. Like other observability commands, it targets `https://observability.mastra.ai` by default.

```bash
mastra api span query <input>
mastra api span query '{"timeRange":{"from":"2026-08-07T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"where":{"op":"and","args":[{"op":"eq","left":{"path":"spanType"},"right":{"literal":"tool_call"}},{"op":"eq","left":{"path":"status"},"right":{"literal":"error"}}]}}'
```

响应仍然嵌套在下面`data` as `{ "spans": [], "page": { "next": "opaque-cursor" } }`. Pass a non-null `data.page.next` value back as `page.after` in the next query, keeping the same time range, predicate, and ordering. Run `mastra api span query --help` for more examples.

Observability存储不支持跨度查询的服务器返回`501`. Filters on identity, context, and parent or root entity fields return `422` when the store doesn't support them. Check `spanQueryContextFields` in the server's observability capabilities before using them. The CLI prints both as an `HTTP_ERROR` with the server response in `error.details.body`.

#### `mastra api span aggregate` {/* #mastra-api-span-aggregate */}

对按时间范围和可选选项选择的跨度进行分组`where` predicate, and returns one row of measures per group, or per group and non-empty time bucket when `interval` is set. It accepts the same fixed measures, `interval`, `having`, `orderBy`, and `limit` as `trace aggregate`. Its `where` filters spans directly, and its dimensions and `countDistinct` fields follow the span contract. It groups by span fields such as `spanType`, `entityName`, `status`, and `rootEntityName`.


令牌和成本度量计算记录它的跨度的使用情况，通常是`model_generation` span. They aren't added to parent spans such as `agent_run`. For span dimensions, measures, and limits, see [Aggregate spans](/reference/observability/tracing/advanced-queries#aggregate-spans). Run `mastra api span aggregate --help` for more examples.

喜欢`trace aggregate`, the command prints `rows` and `truncated` under `data`, and if the observability store can't aggregate spans, the CLI prints the server's `501` response as an `HTTP_ERROR`.

## 遥测 {/* #telemetry */}

默认情况下，Mastra 收集有关您的项目的遥测数据，包括您的操作系统、Mastra 版本和 Node.js 版本。服务器事件还包括下述项目标识符。您可以阅读[CLI telemetry source code](https://github.com/mastra-ai/mastra/blob/main/packages/cli/src/analytics/index.ts) to check what's collected by the CLI.

当服务器启动时`mastra dev`, `mastra start`, or a `mastra build` output has observability configured, Mastra counts the input and output tokens each model call uses in that server process. Every 15 minutes, and once more when the server shuts down, it sends a `mastra_model_token_usage_v2` event per provider and model used since the previous report. If no model calls finished since then, nothing is sent. Each event contains the tokens used since the previous report, the report window's start and end times, the reason for the report (`interval` or `shutdown`), the command (`dev`, `start`, or `server` when the build output runs directly), and `NODE_ENV`. No prompts, responses, or other message content is sent. You can read the [model usage telemetry source code](https://github.com/mastra-ai/mastra/blob/main/packages/core/src/telemetry/model-usage-telemetry.ts) to check what's collected.

为了与较早的分析兼容，服务器还发送较早的分析`mastra_model_token_usage` event at startup. It reads token totals from observability storage and sends the usage added since a cursor saved in `~/.mastra/usage-telemetry.json`. You can read the [startup usage telemetry source code](https://github.com/mastra-ai/mastra/blob/main/packages/core/src/telemetry/usage-telemetry.ts) to check what's collected.

服务器启动时，Mastra 发送项目表面快照，其中包含组件计数、功能标志和粗略存储后端类别，但没有组件名称或组件标识符。您可以阅读[feature telemetry source code](https://github.com/mastra-ai/mastra/blob/main/packages/core/src/telemetry/feature-telemetry.ts) to check what's collected.

服务器事件`mastra_feature_usage`, `mastra_model_token_usage`, and `mastra_model_token_usage_v2` include:

* `project_id`： SHA-256 哈希值的前 16 个十六进制字符`MASTRA_PROJECT_ROOT`, or the current working directory when unset. This identifier also keys the local model-usage cursor.
* `project_id2`：用于跨机器和部署关联的可选标识符。如果修剪过`MASTRA_PROJECT_ID` value has UUID format, the value is sent **unhashed**, prefixed with `mp_`. Search for `mp_<platform-project-id>` to find that project's telemetry. Names, slugs, and other non-UUID values aren't sent as Platform identifiers.

当没有UUID形状的平台ID可用时，`project_id2` uses the first 16 hexadecimal characters of the SHA-256 hash of the normalized Git `origin` remote. Normalization keeps the lowercase host and repository path, excluding the scheme, credentials, port, query, fragment, trailing slashes, and `.git` suffix. Equivalent SSH and HTTPS remotes produce the same identifier. Remotes with the same host and path share an identifier even if different ports or SSH users refer to different repositories. Local filesystem remotes aren't used. Git discovery runs asynchronously and is cached for the process, including when unavailable. If neither source is available, `project_id2` is omitted.

这些服务器事件不是匿名的：平台 ID 将它们链接到该项目，并且可以对已知存储库 URL 进行规范化和哈希处理以匹配 Git 派生的事件。对 Git 身份进行哈希处理可以避免发送原始存储库 URL 或凭据，但不会阻止与公共或其他已知存储库的关联。

Studio UI 还收集匿名浏览器端使用情况分析，例如页面视图和 UI 交互。您可以阅读[source code](https://github.com/mastra-ai/mastra/blob/main/packages/playground/src/lib/analytics.tsx) to check what's collected. Setting `MASTRA_TELEMETRY_DISABLED` disables this too: the value is injected into the served page, so it applies to `mastra dev` and self-hosted builds alike.

您可以通过在启动 Mastra 之前设置此环境变量来选择退出 CLI、服务器和 Studio 使用情况分析。禁用后，服务器遥测不会查找 Git 远程或发送项目标识符：

```bash
MASTRA_TELEMETRY_DISABLED=1
```

您也可以在使用其他设备时进行设置`mastra` commands:

```bash
MASTRA_TELEMETRY_DISABLED=1 mastra dev
```
