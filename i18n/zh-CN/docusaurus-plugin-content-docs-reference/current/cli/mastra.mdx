# CLI 命令

Mastra 提供的命令行界面（CLI）可用于开发、构建和启动 Mastra 项目。

## `mastra dev` {/* #mastra-dev */}

启动服务器，对外提供 [Studio](/docs/studio/overview) 以及 Agent、工具和 Workflow 的 REST 端点。运行 `mastra dev` 后，可访问 [http://localhost:4111/swagger-ui](http://localhost:4111/swagger-ui) 查看所有可用端点。

还可以[配置服务器](/reference/configuration#server-options)。

### 选项 {/* #flags */}

除[通用选项][common-flags]外，此命令还支持以下选项：

#### `--https` {/* #--https */}

启用本地 HTTPS。[了解详情](/reference/configuration#serverhttps)。

#### `--inspect` {/* #--inspect */}

以调试检查模式启动开发服务器。可指定主机和端口，例如 Docker 中的 `--inspect=0.0.0.0:9229`。不能与 `--inspect-brk` 同时使用。

#### `--inspect-brk` {/* #--inspect-brk */}

以调试检查模式启动开发服务器，并在脚本开始时中断。可指定主机和端口，例如 `--inspect-brk=0.0.0.0:9229`。不能与 `--inspect` 同时使用。

#### `--custom-args` {/* #--custom-args */}

以逗号分隔、传给 Node.js 进程的自定义参数，例如 `--require=newrelic` 或 `--experimental-transform-types`。

#### `--request-context-presets` {/* #--request-context-presets */}

包含[请求上下文](/docs/server/request-context)预设的 JSON 文件路径。提供后，Studio 的请求上下文编辑器会显示下拉菜单，可快速切换预设配置。

```bash
mastra dev --request-context-presets ./presets.json
```

该文件必须是 JSON 对象，其中每个键都是预设名称，每个值都是一个对象：

```json
{
  "development": { "userId": "dev-user", "env": "development" },
  "production": { "userId": "prod-user", "env": "production" }
}
```

### 配置 {/* #configs */}

可通过环境变量调整 `mastra dev` 的行为。

#### 跳过对等依赖版本检查 {/* #skip-peer-dependency-check */}

设置 `MASTRA_SKIP_PEERDEP_CHECK=1`，可在启动时跳过对等依赖版本不匹配检查：

```bash
MASTRA_SKIP_PEERDEP_CHECK=1 mastra dev
```

在 monorepo 开发中，对等依赖可能已升级但包尚未发布，此设置很有用。

#### 禁用构建缓存 {/* #disable-build-caching */}

设置 `MASTRA_DEV_NO_CACHE=1` 可强制完整重建，不使用 `.mastra/` 下的缓存资源：

```bash
MASTRA_DEV_NO_CACHE=1 mastra dev
```

调试打包插件或怀疑输出过旧时可使用此设置。

#### 限制并行度 {/* #limit-parallelism */}

`MASTRA_CONCURRENCY` 限制并行执行的高开销操作数量，主要包括构建和评估步骤。例如：

```bash
MASTRA_CONCURRENCY=4 mastra dev
```

不设置时，CLI 会根据机器选择合适的默认值。

#### 自定义 Provider 端点 {/* #custom-provider-endpoints */}

使用 Vercel AI SDK 支持的 Provider 时，可设置基础 URL，让请求经过代理或内部网关。OpenAI 示例：

```bash
OPENAI_API_KEY=<your-api-key> \
OPENAI_BASE_URL=https://openrouter.example/v1 \
mastra dev
```

Anthropic 示例：

```bash
ANTHROPIC_API_KEY=<your-api-key> \
ANTHROPIC_BASE_URL=https://anthropic.internal \
mastra dev
```

这些设置会传给 Mastra 模型路由器，并适用于任何选择了 `"openai/..."`
或 `"anthropic/..."` 的模型。

## `mastra factory dev` {/* #mastra-factory-dev */}

为开发 [Agent Builder](https://agent-builder.mastra.ai/) 启动开发服务器。此命令与 [`mastra dev`](#mastra-dev) 使用相同的开发运行时和选项，并写入同一个 `.mastra/output` 目录。

```bash
npx mastra factory dev
```

两个命令共用开发锁，因此 `mastra dev` 和 `mastra factory dev` 不能在同一项目中同时运行。如果其中一个已在运行，另一个会因开发服务器重复而退出。

开发 Agent Builder 功能时使用 `mastra factory dev`。它支持与 [`mastra dev`](#mastra-dev) 相同的选项，包括 `--https`、`--inspect`、`--inspect-brk`、`--custom-args` 和 `--request-context-presets`。

## `mastra build` {/* #mastra-build */}

`mastra build` 命令将 Mastra 项目打包为可用于生产环境的 Hono 服务器。[Hono](https://hono.dev/) 是轻量且类型安全的 Web 框架，支持通过中间件将 Mastra Agent 作为 HTTP 端点部署。

Mastra 底层使用 Rollup 服务器定位项目入口文件，再打包为生产就绪的 Hono 服务器。打包过程会进行 tree shaking，并生成便于调试的 source map。

`.mastra` 中的输出可通过 [`mastra start`](#mastra-start) 部署到任意云服务器。

部署到[无服务器平台](/docs/deployment/cloud-providers)时，需要安装相应的 Deployer，才能在 `.mastra` 中生成正确的输出。

此命令支持[通用选项][common-flags]。

### 选项 {/* #flags-1 */}

#### `--studio` {/* #--studio */}

构建时一并打包 Studio UI。

### 配置 {/* #configs-1 */}

可通过环境变量调整 `mastra build` 的行为。

#### 跳过对等依赖版本检查 {/* #skip-peer-dependency-check-1 */}

设置 `MASTRA_SKIP_PEERDEP_CHECK=1` 可跳过对等依赖版本不匹配检查：

```bash
MASTRA_SKIP_PEERDEP_CHECK=1 mastra build
```

#### 限制并行度 {/* #limit-parallelism-1 */}

在 CI 或资源受限的环境中，可设置 `MASTRA_CONCURRENCY`，限制同时执行的高开销任务数量。

```bash
MASTRA_CONCURRENCY=2 mastra build
```

## `mastra start` {/* #mastra-start */}

:::note

先运行 `mastra build`，再使用 `mastra start`。

:::

启动本地服务器，以生产模式提供已构建的 Mastra 应用。默认启用 [OTEL 追踪](/docs/observability/tracing/overview)。

### 选项 {/* #flags-2 */}

除[通用选项][common-flags]外，此命令还支持以下选项：

#### `--dir` {/* #--dir */}

已构建的 Mastra 输出目录路径，默认为 `.mastra/output`。

#### `--custom-args` {/* #--custom-args-1 */}

以逗号分隔、传给 Node.js 进程的自定义参数，例如 `--require=newrelic` 或 `--experimental-transform-types`。

## `mastra worker build` {/* #mastra-worker-build */}

将 Mastra 应用打包用于 Worker 部署。输出与 `mastra build` 相同，都是自包含的 `.mastra/output/` 目录。

```bash
mastra worker build [options]
```

### 选项 {/* #flags-3 */}

#### `--dir` {/* #--dir-1 */}

Mastra 源码目录路径，默认为 `src/mastra`。

#### `--root` {/* #--root */}

项目根目录，默认为当前目录。

#### `--tools` {/* #--tools */}

打包时要包含的工具路径，以逗号分隔。

#### `--output-dir` {/* #--output-dir */}

自定义输出目录，默认为 `.mastra/output`。

#### `--debug` {/* #--debug */}

构建期间启用调试日志。

## `mastra experiment build` {/* #mastra-experiment-build */}

构建独立的配套 Worker，无需暴露 HTTP 服务器即可运行实验。Worker 会加载导出的 `Mastra` 实例，从标准输入接收带版本号的逐行 JSON（NDJSON）协议消息，并将协议事件写入标准输出。

```bash
mastra experiment build [options]
```

默认将 Worker 写入 `.mastra/experiment-worker`。该目录包含可执行入口、生产依赖和 `experiment-worker-manifest.json`。标准输出只能用于协议内容；Worker 诊断信息写入标准错误。

### 制品契约 {/* #artifact-contract */}

`experiment-worker-manifest.json` 将制品标识为 `mastra-experiment-worker`，版本为 `1`，并提供：

* 嵌入可执行文件的 CLI 版本、创建时间和唯一构建 ID。
* 支持的协议版本和数据集规范化版本。
* 启动 Worker 所需的可执行文件、参数和工作目录。
* 依赖清单与生成的锁文件路径。
* 按顺序列出的每个制品文件的 SHA-256 摘要。
* 根据文件路径和摘要计算的 SHA-256 内容摘要。

内容摘要不包含 `experiment-worker-manifest.json`，以避免自引用。打包时仍须包含清单文件；若清单本身也需要证明，请使用外层包摘要。

### 协议契约 {/* #protocol-contract */}

Worker 实现固定版本 `1` 的实验配套 Worker 协议。它从标准输入读取严格的 UTF-8 NDJSON 帧，且每一帧（包括最后一帧）都必须以换行符结尾。超过 1 MiB 的帧、格式错误或截断的帧、不受支持的协议或规范化版本，以及与当前实验关联信息不符的消息，都会因协议错误而被拒绝。

运行请求必须匹配制品中嵌入的构建 ID，并包含有序数据集条目数量和 SHA-256 证明。Worker 会发出从 `0` 开始连续递增的序号、由计时器驱动的心跳、等待完成的实验生命周期事件，以及恰好一个终止事件。取消请求必须匹配当前协议版本和实验 ID，以及作业 ID、尝试次数和幂等键。

协议退出码如下：

| 代码 | 含义 |
| - | - |
| `0` | 已完成 |
| `10` | 已完成，但部分条目出错 |
| `20` | 致命故障 |
| `21` | 可重试故障 |
| `30` | 已取消 |
| `31` | 已超时 |
| `70` | 协议故障 |

### 数据包字段处理 {/* #packet-field-handling */}

Worker 将目标身份、有序的内联数据集条目、评分器 ID、并发数、超时、实验元数据、请求上下文、工具模拟和取消信号传给 `runExperiment`。评分器版本和制品来源保留为实验元数据。评分器代码来源由制品准入检查保证，而非在运行时查找评分器。

版本 `1` 对未声明工具采用确定性的拒绝策略。非空网络允许列表和密钥引用会因策略失败而被拒绝，因为网络限制与密钥注入由进程沙箱负责。传给 `runExperiment` 时，数据集条目的来源和预期轨迹字段会保留为条目元数据。

### 选项 {/* #flags-4 */}

#### `--dir` {/* #--dir-2 */}

Mastra 源码目录路径，默认为 `src/mastra`。

#### `--root` {/* #--root-1 */}

项目根目录，默认为当前目录。

#### `--output-dir` {/* #--output-dir-1 */}

自定义制品目录。相对路径以项目根目录为基准解析，默认为 `.mastra/experiment-worker`。

#### `--debug` {/* #--debug-1 */}

构建期间启用调试日志。

## `mastra worker start` {/* #mastra-worker-start */}

:::note

先运行 `mastra worker build` 或 `mastra build`，再使用 `mastra worker start`。

:::

从已有的构建包启动 Worker 进程。可选的 `name` 参数会在子进程中设置 `MASTRA_WORKERS`，以决定启动哪个 Worker。

```bash
mastra worker start [name] [options]
```

### 选项 {/* #flags-5 */}

#### `--dir` {/* #--dir-3 */}

构建输出目录路径，默认为 `.mastra/output`。

#### `--env` {/* #--env */}

环境文件路径，默认为 `.env.production`；若不存在则回退到 `.env`。

### 示例 {/* #examples */}

```bash
# Start only the orchestration worker
mastra worker start orchestration

# Start only the scheduler
mastra worker start scheduler

# Start from a custom build directory
mastra worker start orchestration --dir ./dist
```

有关部署拓扑和配置，请参阅 [Workers](/docs/deployment/workers)。

## `mastra studio` {/* #mastra-studio */}

以静态服务器方式启动 [Studio](/docs/studio/overview)。启动后，可输入 Mastra 实例 URL（例如 `http://localhost:4111`），让 Studio 连接到 Mastra 后端。命令会在当前目录查找 `.env` 和 `.env.production` 文件。

### 选项 {/* #flags-6 */}

除[通用选项][common-flags]外，此命令还支持以下选项：

#### `--port` {/* #--port */}

Studio 使用的端口，默认为 `3000`。

#### `--server-host` {/* #--server-host */}

要连接的 Mastra API 服务器主机，默认为 `localhost`。

#### `--server-port` {/* #--server-port */}

要连接的 Mastra API 服务器端口，默认为 `4111`。

#### `--server-protocol` {/* #--server-protocol */}

要连接的 Mastra API 服务器协议，默认为 `http`。

#### `--server-api-prefix` {/* #--server-api-prefix */}

Mastra API 服务器的路由前缀，默认为 `/api`。

#### `--request-context-presets` {/* #--request-context-presets-1 */}

包含[请求上下文](/docs/server/request-context)预设的 JSON 文件路径。行为与 [`mastra dev` 选项](#--request-context-presets)相同。

```bash
mastra studio --request-context-presets ./presets.json
```

## `mastra deploy` {/* #mastra-deploy */}

构建项目并部署到 `--env` 指定的 Mastra 平台环境。这是新部署推荐使用的命令，取代 [`mastra studio deploy`](#mastra-studio-deploy) 和 [`mastra server deploy`](#mastra-server-deploy)；后两者仍可运行，但不再建议用于新项目。

需要先通过 [`mastra auth login`](#mastra-auth-login) 登录，或设置 `MASTRA_API_TOKEN` 环境变量。

```bash
mastra deploy
mastra deploy --env staging
mastra deploy --env production --region eu
```

命令会运行 `mastra build`，将输出压缩后上传到目标环境。随后持续查询部署状态并流式显示构建日志，直至部署进入终止状态。

组织、项目和环境按以下优先级确定：环境变量（`MASTRA_ORG_ID`、`MASTRA_PROJECT_ID`）、CLI 选项（`--org`、`--project`、`--env`）、`.mastra-project.json` 配置文件、凭据中的当前组织，最后才是交互式提示。首次部署时，CLI 会将确定的组织和项目 ID 保存至 `.mastra-project.json`，后续部署即可跳过提示。

确认后，CLI 会根据 `package.json` 中的 `name` 字段创建尚不存在的项目，并创建缺失的目标环境；环境类型默认为 `type: staging`，但目标为 `production` 时除外。加上 `--yes` 后，可通过一条非交互命令完成创建与部署：

```bash
mastra deploy --env staging --yes
```

设置 `--env <name>` 且未设置 `--env-file` 时，CLI 会自动选取项目目录中存在的 `.env.<name>`（例如 `.env.staging`）。将 `<name>` 插入文件路径前，会先按严格的允许列表验证其值。

### 参数 {/* #arguments */}

#### `[dir]` {/* #dir */}

项目目录，默认为当前目录。

### 选项 {/* #flags-7 */}

#### `--env` {/* #--env-1 */}

目标环境名称，默认为 `production`。如果项目目录中存在 `.env.<name>` 且未设置 `--env-file`，CLI 会自动选择该文件。环境不存在时，CLI 会在确认后创建。

#### `--org` {/* #--org */}

组织 ID，也可以通过环境变量 `MASTRA_ORG_ID` 设置。

#### `--project` {/* #--project */}

项目 ID、slug 或名称，也可以通过环境变量 `MASTRA_PROJECT_ID` 设置。如果没有匹配的项目，部署时会以该值为名称创建新项目。

#### `-y, --yes` {/* #-y---yes */}

无需确认提示，自动接受默认设置，包括创建项目和环境。

#### `-c, --config` {/* #-c---config */}

项目配置文件路径，默认为 `.mastra-project.json`。

#### `--env-file` {/* #--env-file */}

随部署一同打包的环境文件路径（相对于项目目录）。设置后，会禁用 `.env.<name>` 基于 `--env` 的自动选择。

```bash
mastra deploy --env staging --env-file .env.staging.local
```

#### `--region` {/* #--region */}

新建环境所在的区域，例如 `eu`。仅在 CLI 创建环境时生效。

#### `--skip-build` {/* #--skip-build */}

跳过构建步骤，直接部署已有的 `.mastra/output` 目录。如果现有构建相对当前源码已过期，CLI 会发出警告。

#### `--skip-preflight` {/* #--skip-preflight */}

跳过上传前对构建输出的验证。

#### `--debug` {/* #--debug-2 */}

构建步骤期间启用调试日志。

### CI/CD 使用 {/* #cicd-usage */}

为无交互部署设置环境变量 `MASTRA_API_TOKEN`、`MASTRA_ORG_ID` 和 `MASTRA_PROJECT_ID`。设置 `MASTRA_API_TOKEN` 后会自动跳过交互式提示；结合 `--yes` 可自动确认创建环境。

```bash
export MASTRA_API_TOKEN="..."
export MASTRA_ORG_ID="..."
export MASTRA_PROJECT_ID="..."
mastra deploy --env staging --yes
```

## `mastra env` {/* #mastra-env */}

管理 Mastra 平台上的环境。环境是项目的部署目标，例如 `production`、`staging`、`preview-42`。当前组织从已保存的凭据中确定。

每个子命令都按固定顺序确定所属项目：先检查 `--project <name|slug|id>` 选项，再检查环境变量 `MASTRA_PROJECT_ID`，最后读取当前目录中的 `.mastra-project.json`（由 [`mastra deploy`](#mastra-deploy) 写入）。在项目目录运行命令，就无需重复指定项目。

### `mastra env list` {/* #mastra-env-list */}

列出项目的环境。每个环境显示最新部署；正在服务流量的部署会标记为 `(active)`。还会显示附加数据库等托管资源注入的环境变量名称。

```bash
mastra env list
```

#### `--json` {/* #--json */}

输出机器可读的 JSON。只包含非敏感元数据（ID、名称、slug、类型、区域、分支、URL、托管环境变量名称和最新部署状态），因此可安全写入 CI 日志。

### `mastra env create` {/* #mastra-env-create */}

为项目创建新环境。

```bash
mastra env create staging --type staging --region eu
```

#### `-t, --type` {/* #-t---type */}

环境类型，可为 `production`、`staging` 或 `preview`，默认为 `staging`。

#### `-r, --region` {/* #-r---region */}

环境所在区域，例如 `eu`。

#### `--json` {/* #--json-1 */}

输出机器可读的 JSON。与 [`mastra env list`](#mastra-env-list) 一样，会省略敏感字段。

### `mastra env delete` {/* #mastra-env-delete */}

删除环境。

```bash
mastra env delete <env>
```

`<env>` 可为环境名称、slug 或 ID。除非传入 `--yes`，否则 CLI 会要求确认。

#### `-y, --yes` {/* #-y---yes-1 */}

跳过确认提示。

### `mastra env restart` {/* #mastra-env-restart */}

重启环境中的运行服务，使已保存的环境变量（包括附加数据库注入的托管变量）立即生效，无需重新部署。

```bash
mastra env restart <env>
```

`<env>` 可为环境名称、slug 或 ID。如果该环境从未部署过，会返回冲突错误。

### `mastra env vars pull` {/* #mastra-env-vars-pull */}

将环境变量拉取到本地环境文件（默认 `.env`）。文件包含该环境部署时使用的变量集合，即环境本身保存的变量（例如在控制台环境编辑器中添加的变量）。每个环境独立拉取，不会合并其他环境保存的值。仍使用[旧版流水线](/docs/mastra-platform/deploy#migrating-from-server-and-studio-deploys)的项目改用项目级变量，因此拉取其任一环境都会得到共享的项目级值。附加数据库注入的托管变量仅以注释列出名称，因为其值是平台管理的密钥。

```bash
mastra env vars pull
mastra env vars pull <env> --output .env.staging
```

`<env>` 可为环境名称、slug 或 ID。项目只有一个环境时可省略。文件以 `0600` 权限写入；若输出文件已存在，命令会停止。传入 `--force` 可覆盖。

#### `-o, --output` {/* #-o---output */}

写入的文件，默认为 `.env`。

#### `-f, --force` {/* #-f---force */}

覆盖已有的输出文件。

### `mastra env db` {/* #mastra-env-db */}

管理 Mastra 平台项目附加的数据库。数据库由托管 Provider（如 Turso 或 Neon）创建，连接环境变量会自动注入部署。

数据库可以是**环境级**（环境变量只提供给一个环境），也可以是**共享**（项目级，提供给所有环境）。`mastra env db create` 默认创建环境级数据库：可传入环境参数，也可由 CLI 自动选择或提示。创建时传入 `--shared` 则改为附加共享数据库。其他子命令（`list`、`delete`、`keys`）中，传入环境参数可操作环境级数据库，省略则操作共享数据库。

创建和删除数据库需要组织内的 `admin` 角色。

### `mastra env db list` {/* #mastra-env-db-list */}

列出项目附加的数据库，包括 Provider、创建状态、作用范围（每个数据库供给的环境）以及注入的环境变量名称。传入环境可只显示供该环境使用的数据库，包括环境级和共享数据库。

```bash
mastra env db list
mastra env db list <env>
```

#### `--json` {/* #--json-2 */}

输出机器可读的 JSON。

### `mastra env db create` {/* #mastra-env-db-create */}

创建并附加托管数据库，然后持续查询直至就绪。如果创建失败，会打印 Provider 提供的错误详情。

默认情况下，数据库仅归属单个环境。可传入环境参数指定；省略时，CLI 会选择项目中唯一的环境，或在有多个环境时提示选择。在非交互场景（CI、`--json`）中，必须传入环境参数。也可使用 `--shared` 附加供所有环境共用的项目级数据库。

环境级数据库的 Provider 区域继承自对应环境。共享数据库可通过 `--region` 指定区域。

```bash
mastra env db create --kind turso                                    # picks or prompts for an environment
mastra env db create staging --kind turso                            # scoped to the "staging" environment
mastra env db create --kind turso --shared                           # shared by all environments
mastra env db create --kind neon --name my-app-db --region aws-us-east-1 --shared
mastra env db create production --kind postgres                      # VPC-isolated Postgres, private to the environment
```

#### `--kind` {/* #--kind */}

数据库 Provider，必填。可为 `turso`、`neon`（公开的无服务器 Postgres）或 `postgres`（与部署环境位于同一私有网络的 VPC 隔离 Postgres）。

#### `--name` {/* #--name */}

数据库名称，默认根据项目 slug 和 Provider 生成，例如 `my-app-turso`、Neon 的 `my-app-pg` 或 VPC Postgres 的 `my-app-postgres`。

#### `--region` {/* #--region-1 */}

共享数据库的 Provider 区域 ID。环境级数据库会忽略此选项。

#### `--shared` {/* #--shared */}

以项目级数据库的形式附加，供所有环境共用。不能同时传入环境参数。

#### `--no-wait` {/* #--no-wait */}

附加任务进入队列后立即返回，无需等待数据库就绪。之后可用 `mastra env db show` 查看进度。

#### `--json` {/* #--json-3 */}

输出机器可读的 JSON。项目有多个环境时，此模式要求提供环境参数或 `--shared`，不会出现交互提示。

### `mastra env db show` {/* #mastra-env-db-show */}

显示数据库详情；就绪后还会显示连接环境变量。默认隐藏密钥值。

```bash
mastra env db show <database>
```

`<database>` 可为数据库 ID 或名称。

#### `--show-secrets` {/* #--show-secrets */}

显示连接密钥的实际值，而不进行隐藏。

#### `--json` {/* #--json-4 */}

输出机器可读的 JSON。除非传入 `--show-secrets`，否则会隐藏密钥值。

### `mastra env db delete` {/* #mastra-env-db-delete */}

通过 Provider 永久删除数据库及其全部数据，无法撤销。除非传入 `--yes`，否则 CLI 会要求确认。删除后，部署不再接收该数据库的环境变量。

```bash
mastra env db delete <database>
```

#### `-y, --yes` {/* #-y---yes-2 */}

跳过确认提示。

### `mastra env deploys` {/* #mastra-env-deploys */}

按时间从新到旧列出项目的部署。正在服务流量的部署标记为 `(active)`。

```bash
mastra env deploys [environment]
```

省略 `[environment]` 可显示所有环境的部署；传入环境名称、slug 或 ID 可只查看指定环境。

#### `--json` {/* #--json-5 */}

输出机器可读的 JSON。

### `mastra env diagnosis` {/* #mastra-env-diagnosis */}

诊断失败的部署并给出修复建议。每项建议包含说明、推荐操作和适用时的文档链接，最后附上控制台中的部署日志链接。

```bash
mastra env diagnosis
mastra env diagnosis <deploy-id>
mastra env diagnosis --environment staging
```

省略 `<deploy-id>` 时，会诊断该环境最近一次部署。环境由 `--environment` 指定；项目只有一个环境时可自动确定。项目有多个环境时，必须提供 `--environment` 或部署 ID。单独传入部署 ID 时，无需关联项目。

如果部署运行正常，命令会报告无需建议并退出。否则，若还没有诊断任务，命令会启动诊断，最长轮询五分钟直至结果就绪。再次运行会复用进行中的诊断，不会重新开始。若诊断本身失败，命令以非零状态码退出。

`mastra deploy` 失败后，CLI 会打印可直接运行的 `mastra env diagnosis <deploy-id>` 命令。

#### `--project` {/* #--project-1 */}

项目名称、slug 或 ID。默认使用[ `mastra env` ](#mastra-env)所述的已关联项目。

#### `--environment` {/* #--environment */}

环境名称、slug 或 ID。默认使用项目中唯一的环境。项目有多个环境且未传入部署 ID 时必填。

## `mastra studio deploy` {/* #mastra-studio-deploy */}

:::note

`mastra studio deploy` 仍可使用，但已由 [`mastra deploy`](#mastra-deploy) 取代；新命令支持在同一项目中使用多个环境（`--env staging`、`--env production`）。新项目应使用 `mastra deploy`。

:::

构建项目并部署到 Mastra 平台。须通过 [`mastra auth login`](#mastra-auth-login) 登录，或设置 `MASTRA_API_TOKEN` 环境变量。

```bash
mastra studio deploy
```

命令运行 `mastra build` 并压缩输出。上传到平台前会读取项目目录中的环境文件。上传后，持续查询部署状态并流式显示构建日志，直到部署进入终止状态。

部署命令会自动加载项目的 `.env` 文件。如果 `MASTRA_PROJECT_ID` 指向已为 Observability 创建的项目，部署会关联该项目，而非新建项目。将 Studio 部署到仅启用可观测性的项目时，平台会将其转换为 Studio 项目。

项目目录中必须至少有一个 `.env` 或 `.env.*` 文件（不包括 `.env.example`），否则 CLI 报错 `Error: No env file found for deploy.`。存在多个环境文件时，CLI 会提示选择，默认选中 `.env.production`。可传入 `--env-file` 显式指定。如果同时使用 `--yes` 且有多个环境文件，则必须传入 `--env-file`，否则部署会失败。

组织和项目依次从环境变量选项、`.mastra-project.json` 配置文件、凭据中的当前组织，最后的交互提示中确定。首次部署时，CLI 会将确定的 ID 保存至 `.mastra-project.json`，后续部署即可跳过提示。

如果 `--project <value>` 与现有项目的 ID 或 slug 均不匹配，CLI 会将 `<value>` 视为新项目名称，确认后创建。加上 `--yes` 后，可用一条非交互命令创建并部署新项目：

```bash
mastra studio deploy --project "my-new-project" --yes
```

### 参数 {/* #arguments-1 */}

#### `[dir]` {/* #dir-1 */}

项目目录，默认为当前目录。

### 选项 {/* #flags-8 */}

#### `--org` {/* #--org-1 */}

组织 ID，也可以通过环境变量 `MASTRA_ORG_ID` 设置。

#### `--project` {/* #--project-2 */}

项目 ID 或 slug，也可以通过环境变量 `MASTRA_PROJECT_ID` 设置。如果没有匹配的项目，部署时会以该值为名称创建新项目。

#### `-y, --yes` {/* #-y---yes-3 */}

无需确认提示，自动接受默认值。

#### `-c, --config` {/* #-c---config-1 */}

项目配置文件路径，默认为 `.mastra-project.json`。

#### `--env-file` {/* #--env-file-1 */}

随部署一同打包的环境文件路径（相对于项目目录）。指向不同环境文件（如 `.env.staging`、`.env.production`）可将同一项目部署到多个环境。

```bash
mastra studio deploy --env-file .env.staging --yes
```

#### `--skip-build` {/* #--skip-build-1 */}

跳过构建步骤，部署已有的 `.mastra/output` 目录。

#### `--debug` {/* #--debug-3 */}

构建步骤期间启用调试日志。

### CI/CD 使用 {/* #cicd-usage-1 */}

为无交互部署设置环境变量 `MASTRA_API_TOKEN`、`MASTRA_ORG_ID` 和 `MASTRA_PROJECT_ID`。设置 `MASTRA_API_TOKEN` 后会自动跳过交互式提示。

列出所有项目及其最近一次部署的状态和 URL。

### `mastra studio deploy status` {/* #mastra-studio-deploy-status */}

#### `--watch, -w` {/* #--watch--w */}

#### `--follow, -f` {/* #--follow--f */}

## `mastra server restart` {/* #mastra-server-restart */}

重启已关联项目中暂停或停止的 Server 实例。平台接受重启后，CLI 会从 API 响应取得部署 ID；若响应未提供 ID，则轮询项目和部署元数据。随后按 [`mastra server deploy`](#mastra-server-deploy) 的方式流式显示构建与部署日志，直到部署进入终止状态。

### 选项 {/* #flags-10 */}

```bash
mastra server restart
```

## `mastra server env` {/* #mastra-server-env */}

```bash
mastra server env set <key> <value>
```


### `mastra server env pull` {/* #mastra-server-env-pull */}


## `mastra auth` {/* #mastra-auth */}

管理 Mastra 平台身份认证。凭据保存在 `~/.mastra/credentials.json`。也可设置环境变量 `MASTRA_API_TOKEN`，代替交互式登录。

### `mastra auth login` {/* #mastra-auth-login */}

打开浏览器登录，并将凭据保存在本地。

需要浏览器登录但没有交互终端时（例如 CI、输入或输出被管道接管、或在 Agent 的 shell 中），命令会先打印无头 shell 的认证方法，然后仍等待浏览器登录。在同一台机器上，可先在自己的终端运行一次 `mastra auth login`，后续命令便能复用保存的会话。在 CI 或另一台机器上，应改为设置 `MASTRA_API_TOKEN` 和 `MASTRA_ORG_ID`。可在已登录的终端通过 [`mastra auth tokens create`](#mastra-auth-tokens-create) 或在控制台创建令牌。如果等待浏览器登录超时，命令以状态码 1 退出。如果非交互 shell 中已有 `MASTRA_API_TOKEN`，命令会跳过浏览器登录：验证令牌并检查是否已选择组织（来自 `MASTRA_ORG_ID` 或已保存凭据），成功时以状态码 0 退出；任一检查失败时以状态码 1 退出，并指出缺失内容。

### `mastra auth logout` {/* #mastra-auth-logout */}

删除已保存的凭据。如果环境中仍设置了 `MASTRA_API_TOKEN`，CLI 会提示该令牌仍将继续使用。

### `mastra auth whoami` {/* #mastra-auth-whoami */}

显示当前用户的邮箱、用户 ID 和活动组织。

### `mastra auth orgs` {/* #mastra-auth-orgs */}

列出所有组织及用户在各组织中的角色，并标记当前组织。

#### `mastra auth orgs switch` {/* #mastra-auth-orgs-switch */}

通过交互式提示切换活动组织。若已设置 `MASTRA_API_TOKEN` 或 `MASTRA_ORG_ID` 环境变量，则无法使用。

### `mastra auth tokens` {/* #mastra-auth-tokens */}

列出所有 API 令牌及其最近使用日期。

#### `mastra auth tokens create` {/* #mastra-auth-tokens-create */}

创建新的 API 令牌。密钥只显示一次，之后无法再次获取。

```bash
mastra auth tokens create <name>
```

使用 `--permission` 为令牌授予额外权限。目前可用的权限是 `databases:write`，可用于在 CI 等环境中创建和删除托管数据库。只有组织管理员能创建带权限的令牌。重复传入此选项可授予多项权限。

如果平台创建的令牌缺少所请求的权限，命令会撤销该令牌并报错退出。如果撤销也失败，错误信息会给出需要运行的 `mastra auth tokens revoke` 命令。

```bash
mastra auth tokens create ci --permission databases:write
```

#### `mastra auth tokens revoke` {/* #mastra-auth-tokens-revoke */}

撤销 API 令牌。

```bash
mastra auth tokens revoke <token-id>
```

## `mastra connect` {/* #mastra-connect */}

管理已关联平台项目的 Provider 连接，使使用 `@mastra/connect` 的 Agent 无需离开终端即可获取 Provider 工具集。

命令使用你通过 `mastra auth login` 登录的组织。可用 `mastra auth orgs switch` 切换组织。

目标项目依次从 `--project` 选项、环境变量 `MASTRA_PROJECT_ID`，或 `.mastra-project.json`（由 `mastra deploy` 写入）中确定。所有子命令均支持 `--project <name|slug|id>`。

### `mastra connect list` {/* #mastra-connect-list */}

列出 Provider，已连接的排在前面。活动连接显示为绿色，需重新授权的显示为黄色，未连接的 Provider 显示为灰色。尚不可用的 Provider 标记为即将推出。

```bash
mastra connect list
```

### `mastra connect add` {/* #mastra-connect-add */}

将 Provider 连接到项目。如果组织内已有该 Provider 的连接但尚未附加到项目，命令会列出连接，供你选择附加现有连接或创建新连接。若没有现有连接，则直接进入 Provider 认证流程。

OAuth Provider 会在浏览器中打开授权同意页面，并打印 URL 供手动打开。使用 API Key 或 Basic Auth 的 Provider 会在终端提示输入凭据，验证后才完成连接。其他认证类型的 Provider 会打开托管连接页面。命令会等待连接变为活动状态后退出。

即使使用 `--yes`，输入凭据仍需要交互式终端。请在 CI 外运行此命令，或通过平台界面连接。各 Provider 的[集成页面](/docs/mastra-platform/connect#providers)列出了所需的 API Key 和权限。

新连接激活后，命令会提供设置显示名称的选项，便于区分同一 Provider 的不同连接。它会列出现有连接，建议一个不冲突的名称；若所选名称重复，则要求确认。留空可跳过命名。设置显示名称需要组织管理员角色；命名失败不会使连接失效。

```bash
mastra connect add <provider>
```

传入 `--yes` 可跳过所有提示。即使已有连接可以复用，此选项仍会创建一个没有显示名称的新连接。

### `mastra connect remove` {/* #mastra-connect-remove */}

解除 Provider 连接与项目的关联。组织级连接会保留，之后可重新附加。

```bash
mastra connect remove <provider>
```

如果一个 Provider 有多个连接，命令会提示选择要移除的连接。传入 `--yes` 可跳过确认。没有终端或使用 `--yes` 时，若要一次移除多个连接，必须传入 `--all`；`--connection <id>` 只移除一个。

### 替换需要重新授权的连接 {/* #replace-a-connection-that-needs-reauthorization */}

`mastra connect list` 会标记需要重新授权的连接，例如 Provider API Key 被撤销后。解析 Connect 工具时会跳过这些连接并发出警告。

先解除受影响连接，再添加新连接：

```bash
mastra connect remove posthog
mastra connect add posthog
```

如果项目有多个连接，移除时请选择受影响的连接。当 `add` 提示复用组织连接时，选择 **Create a new connection**，并使用有效凭据授权。

## `mastra traces import` {/* #mastra-traces-import */}

将受支持的可观测性 Provider 的历史追踪导入现有 Mastra Platform 项目。命令会在本地准备完整追踪，按完整追踪批量上传，支持续传，并通过 Mastra Platform 抽样验证。

```bash
mastra traces import <provider> [options]
```

目前支持以下 Provider：

| Provider | 参数 | 要求 |
| - | - | - |
| Langfuse | `langfuse` | Langfuse Cloud 或自行托管的 Langfuse v4 及以上版本 |

完整流程、数据映射、本地文件生命周期与限制，请参阅[导入现有追踪](/docs/mastra-platform/observability#import-existing-traces)。

### 选项 {/* #options */}

#### `--target-project <name|slug|id>` {/* #--target-project-nameslugid */}

选择接收追踪的目标 Mastra Platform 项目，优先于 `MASTRA_PROJECT_ID`。两者均未提供时，命令使用 `.mastra-project.json` 中关联的项目。来源项目由 Provider 凭据确定，例如 `LANGFUSE_PUBLIC_KEY` 和 `LANGFUSE_SECRET_KEY`。

#### `--since <date>` {/* #--since-date */}

将导入时间窗口的起点（含）设为 ISO 8601 日期或时间戳。默认是 `--until` 前 30 天，但不会早于平台当前 30 天的保留边界。`--from` 是别名。

#### `--until <date>` {/* #--until-date */}

将导入时间窗口的终点（不含）设为 ISO 8601 日期或时间戳。默认是导入开始时间，不能晚于当前时间。`--to` 是别名。

整个时间窗口必须位于平台当前 30 天的保留期内，`--since` 必须早于 `--until`，且窗口不得超过 30 天。

#### `--dry-run` {/* #--dry-run */}

读取来源并在本地准备有效追踪，不上传。命令会写入报告，并打印用于继续已准备导入的命令。

#### `--resume <import-id>` {/* #--resume-import-id */}

使用已保存的 Provider、目标项目、日期窗口和已确认进度，继续已准备的导入。目标项目必须与生成的续传命令中显示的一致。不能与 `--since`、`--until` 或 `--dry-run` 同时使用。

#### `-y, --yes` {/* #-y---yes-4 */}

无需确认即可上传。

### 环境变量 {/* #environment-variables */}

命令从当前目录加载 `.env` 和 `.env.local`。

| 变量 | 必填条件 | 说明 |
| - | - | - |
| `LANGFUSE_PUBLIC_KEY` | 新建 Langfuse 导入时 | 项目的公开 API Key。与密钥配合，用于选择来源 Langfuse 项目。 |
| `LANGFUSE_SECRET_KEY` | 新建 Langfuse 导入时 | 项目的私有 API Key。 |
| `LANGFUSE_BASE_URL` | 否 | Langfuse 主机，默认为 `https://cloud.langfuse.com`。 |
| `MASTRA_API_TOKEN` | 无交互认证时 | Mastra Platform API 令牌。未设置时，命令使用 `mastra auth login` 保存的凭据。 |
| `MASTRA_ORG_ID` | 使用 `MASTRA_API_TOKEN` 时 | 目标项目所属的组织。 |
| `MASTRA_PLATFORM_ACCESS_TOKEN` | 交互登录后上传和回读时 | 目标 Mastra Platform 的访问令牌。使用 `--dry-run` 或已设置 `MASTRA_API_TOKEN` 时无需提供。 |
| `MASTRA_PROJECT_ID` | 未通过其他方式关联项目时 | 目标项目 ID。`--target-project` 选项优先于此变量。 |

### 示例 {/* #examples-1 */}

预览默认的 30 天窗口，不上传数据：

```bash
mastra traces import langfuse --target-project my-mastra-project --dry-run
```

无需确认提示，导入较短的时间窗口：

```bash
mastra traces import langfuse \
  --target-project my-mastra-project \
  --since "$SINCE" \
  --until "$UNTIL" \
  --yes
```

继续已有的导入：

```bash
mastra traces import langfuse \
  --resume 00000000-0000-0000-0000-000000000000 \
  --target-project my-mastra-project
```

## `mastra api` {/* #mastra-api */}

以 JSON 输入和输出调用 Mastra 运行时服务器。适用于本地开发服务器、已部署的 Mastra 平台项目、自托管 Mastra 服务器，以及托管的 Mastra Platform Observability API。

```bash
mastra api agent list
mastra api agent run weather-agent '{"messages":"What is the weather in London?"}'
mastra api tool execute get-weather '{"location":"San Francisco"}'
mastra api trace list '{"page":0,"perPage":20}'
```

使用 `mastra api <resource> <action> --help` 查看某个命令的示例。

### 输出 {/* #output */}

成功响应以 JSON 写入 `stdout`。单资源命令返回：

```json
{ "data": {} }
```

列表命令返回 `data` 数组和分页元数据：

```json
{ "data": [], "page": { "total": 0, "page": 0, "perPage": 0, "hasMore": false } }
```

错误以 JSON 写入 `stderr`，并返回非零退出码：

```json
{
  "error": {
    "code": "SERVER_UNREACHABLE",
    "message": "Could not connect to target server",
    "details": {}
  }
}
```

退出码反映请求是否成功，而非响应内容：

* `0`：服务器返回成功响应，包括空结果和报告现有状态的载荷，例如工具结果提示记录已存在。即使工具返回含 `error` 字段的对象，命令仍以 `0` 退出，因此工具自行报告失败时应检查 `data` 载荷。
* `1`：请求失败，例如服务器不可达、JSON 输入无效、资源不存在，或工具抛出错误。

即使读取输出的命令提前退出（如 `| head`），退出码仍反映请求是否成功。

### 目标解析 {/* #target-resolution */}

对于运行时命令，目标服务器按以下顺序确定：

1. `--url <url>`：显式指定远程或自托管服务器。
1. `http://localhost:4111`：本地的 `mastra dev` 服务器。
1. `.mastra-project.json`：Mastra 平台项目。

CLI 从 `.mastra-project.json` 解析项目，或识别显式指定的 Mastra 托管 Studio、Factory 或可观测性 URL 时，会自动使用平台认证。localhost 和任意显式指定的 `--url` 目标不会自动获得凭据。通过 `--header` 传入的请求头会发送到任何目标，包括 localhost。

可观测性命令（`trace`、`log`、`score` 和 `metric`）默认使用美国端点 `https://observability.mastra.ai`，而非项目部署 URL。Trace Intelligence 命令（`learning`）的方式相同，但使用 `https://output.signals.mastra.ai`。CLI 自动选择任一托管目标时，按以下顺序查找凭据：

1. 显式指定的 `Authorization` 和 `X-Mastra-Project-Id` 请求头（通过 `--header` 传入）。
1. 环境变量 `MASTRA_PLATFORM_ACCESS_TOKEN` 和 `MASTRA_PROJECT_ID`。
1. `.mastra-project.json` 中的项目元数据，用于确定项目 ID。
1. 最后使用 Mastra CLI 登录令牌作为认证回退。

Learning 命令还会发送 `X-Mastra-Organization-Id`，依次从显式 `--header`、环境变量 `MASTRA_ORGANIZATION_ID` 或 `.mastra-project.json` 中获取。

欧盟可观测性数据保存在 `https://observability.eu.mastra.ai`。通过 `--url` 指定该可信主机时，它与默认美国端点采用相同的平台凭据解析方式：

```bash
mastra api --url https://observability.eu.mastra.ai trace list
```

需要覆盖其他目标或凭据时，使用 `--url` 和 `--header`。

### Factory 命令 {/* #factory-commands */}

使用 `mastra api factory` 管理 Factory 项目、工作项、决策、待关注项和队列健康状态。这些命令与其他 `mastra api` 命令使用相同的 JSON 输入输出、认证、请求头、超时和目标解析规则。

列出当前组织可用的 Factory 项目：

```bash
mastra api factory project list
```

发送受治理的工作项状态转换前，先检查生成的请求 Schema：

```bash
mastra api factory work-item transition --schema
```

使用工作项当前修订版本转移它：

```bash
mastra api factory work-item transition <project-id> <work-item-id> '{"board":"work","stage":"planning","requestId":"00000000-0000-4000-8000-000000000000","cause":"manual","expectedRevision":1}'
```

使用 `mastra deploy` 部署项目后，生成的不含密钥的 `.mastra-project.json` 可让 CLI 定位托管的 Factory 实例、使用 Mastra CLI 凭据，并自动选择已部署项目所属组织。若显式指定托管 Factory 的 `--url`，CLI 会先使用 `MASTRA_ORG_ID`（如果已设置），否则使用通过 `mastra auth orgs switch` 选中的组织。显式的 `X-Mastra-Organization-Id` 请求头优先于两者。部署前，或要指定本地、远程、自托管 Factory 服务器时，请使用 `--url`：

```bash
mastra api --url http://localhost:4111 factory project list
```

Factory 端点使用根路径 `/web/factory/...`。`--server-api-prefix` 仍控制本地目标探测，但不会加到 Factory 请求路径前。

### 选项 {/* #flags-13 */}

#### `--url <url>` {/* #--url-url */}

指定 Mastra 服务器 URL。

```bash
mastra api --url https://example.com agent list
```

#### `--server-api-prefix <prefix>` {/* #--server-api-prefix-prefix */}

设置目标服务器的 API 路由前缀，默认为 `/api`。服务器挂载在自定义前缀下时可使用此选项，例如 `@mastra/fastify` 的 `MastraServer` 使用 `prefix: "/api/mastra-studio"`。其用法与 `mastra studio` 的 `--server-api-prefix` 相同。也可改设环境变量 `MASTRA_API_PREFIX`。

```bash
mastra api --url https://example.com --server-api-prefix /api/mastra-studio agent list
```

#### `--header <"Key: Value">` {/* #--header-key-value */}

发送自定义 HTTP 请求头。可重复传入以发送多个请求头。

```bash
mastra api --url https://example.com --header "Authorization: Bearer $TOKEN" agent list
```

#### `--timeout <ms>` {/* #--timeout-ms */}

设置请求超时，单位为毫秒，默认为 `30000`。Workflow 运行的启动和恢复命令默认使用 `120000`。

#### `--pretty` {/* #--pretty */}

美化 JSON 输出，默认为 `false`。

#### `--schema` {/* #--schema */}

打印接受 JSON 输入的命令所对应的 CLI 请求 Schema。Schema 来自目标服务器的路由契约，包含命令结构、位置参数、示例、请求 Schema 和响应结构。

`--schema` 可用于接受 JSON 输入的叶子命令，不能作为顶层 `mastra api` 选项使用。

```bash
mastra api agent run --schema
mastra api tool execute --schema
```

### 输入模型 {/* #input-model */}

接受输入的命令只接收一个内联 JSON 参数，不支持文件路径或标准输入。

```bash
mastra api workflow run start data-pipeline '{"inputData":{"source":"s3://bucket/data.csv"}}'
```

稳定的 ID 使用位置参数；筛选条件或载荷使用 JSON。路由同时需要查询参数和请求体时，传入单个 JSON 对象。CLI 会根据服务器路由 Schema 拆分输入。

```bash
mastra api thread create '{"agentId":"weather-agent","resourceId":"user_123","threadId":"thread_abc123","title":"Support conversation"}'
```

目标路由支持分页时，列表命令可在 JSON 输入中使用 `page` 和 `perPage`：

```bash
mastra api score list '{"page":0,"perPage":50}'
mastra api trace list '{"page":0,"perPage":20}'
```

支持筛选的路由可在同一个 JSON 输入中提供筛选条件。例如，可观测性追踪列表同时支持分页和该路由提供的筛选条件：

```bash
mastra api trace list '{"page":0,"perPage":20,"filters":{"spanType":"agent"}}'
```

### 命令 {/* #commands */}

#### `mastra api agent list` {/* #mastra-api-agent-list */}

列出目标服务器上注册的 Agent。可传入可选的 JSON，指定路由支持的筛选条件。

```bash

```

#### `mastra api agent get` {/* #mastra-api-agent-get */}

获取某个已注册 Agent 的元数据。

#### `mastra api trace query` {/* #mastra-api-trace-query */}

使用对追踪字段和相关 span 的递归谓词，查询已完成的可观测性追踪。内联 JSON 输入必填，结构与 SDK 和 HTTP API 相同。与其他可观测性命令一样，默认目标为 `https://observability.mastra.ai`。可传入 `--url http://localhost:4111` 查询本地服务器。

```bash
mastra api trace query <input>
mastra api trace query '{"timeRange":{"from":"2026-08-01T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"}}'
```

可用以下命令查看该命令：

```bash
mastra api trace query --help
```

支持的字段、运算符和请求选项详见[查询追踪](/reference/observability/tracing/advanced-queries#query-traces)。对于本地 Mastra 服务器，还可检查请求与响应 Schema：

```bash
mastra api --url http://localhost:4111 trace query --schema
```

Mastra Platform 目前不提供 `--schema` 使用的 Schema 端点。若要查找项目中记录的字段和值，请使用[字段和值发现功能](/reference/observability/tracing/advanced-queries#discover-fields-and-values)。

响应继续嵌套在 `data` 下，以保留游标分页信息：

```json
{
  "data": {
    "traces": [],
    "page": { "next": "opaque-cursor" }
  }
}
```

每次调用只执行一次查询。下一次查询时，将非空的 `data.page.next` 值作为 `page.after` 传回。分页模式、游标处理与错误详见[分页与错误](/reference/observability/tracing/advanced-queries#pagination-and-errors)。

先加载编号分页结果，再轮询增量时，两次请求须使用相同的时间范围和谓词：

```bash
mastra api trace query '{"timeRange":{"from":"2026-08-01T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"pagination":{"page":0,"perPage":100}}'
mastra api trace query '{"timeRange":{"from":"2026-08-01T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"mode":"delta","after":"CURSOR_FROM_NUMBERED_RESPONSE","limit":100}'
```

将 `CURSOR_FROM_NUMBERED_RESPONSE` 替换为第一次响应中的 `data.deltaCursor`。增量结果仍位于 `data` 下，包含 `traces`、`delta: { limit, hasMore }` 和 `deltaCursor`。按 `traceId` 合并追踪，保留每次返回的游标；当 `data.delta.hasMore` 为 `true` 时立即继续。增量模式不能与 `page`、`pagination` 或 `orderBy` 混用。

省略 `after` 会建立游标，但不会返回历史追踪。改变时间范围或谓词时必须重新发起编号分页请求。若用此流程维护本地追踪列表，请先阅读[增量轮询限制](/reference/observability/tracing/advanced-queries#poll-after-loading-a-numbered-page)。

#### `mastra api trace aggregate` {/* #mastra-api-trace-aggregate */}

按时间范围和可选的 `where` 谓词对追踪分组，返回每组一行度量值；设置 `interval` 时，每组每个非空时间桶返回一行。内联 JSON 输入必填，支持与 `trace query` 相同的谓词。与其他可观测性命令一样，默认目标为 `https://observability.mastra.ai`。

```bash
mastra api trace aggregate <input>
mastra api trace aggregate '{"timeRange":{"from":"2026-08-01T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"groupBy":["entityName"],"measures":["count","errorRate"]}'
```

将 `interval` 设为 `1m`、`5m`、`15m`、`1h` 或 `1d`，可将每组拆分为时间桶：

```bash
mastra api trace aggregate '{"timeRange":{"from":"2026-08-01T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"where":{"op":"eq","left":{"path":"entityName"},"right":{"literal":"weather-agent"}},"interval":"1d","measures":["count","duration.p95"]}'
```

维度、度量和请求选项详见[聚合追踪](/reference/client-js/observability#aggregate-traces)。更多示例可运行 `mastra api trace aggregate --help`。

响应保持嵌套在 `data` 下，以保留 `truncated`。当 `truncated` 为 `true` 时，表示匹配组数超过 `limit`：

```json
{
  "data": {
    "rows": [
      {
        "dimensions": { "entityName": "weather-agent" },
        "measures": { "count": 42, "errorRate": 0.05 }
      }
    ],
    "truncated": false
  }
}
```

如果服务器的可观测性存储不支持追踪聚合，会返回 `501`。CLI 会像处理其他请求失败一样，打印 `HTTP_ERROR`，并将服务器响应放在 `error.details.body` 中。

#### `mastra api span query` {/* #mastra-api-span-query */}

跨追踪查询已完成的可观测性 span，包括嵌套在其他追踪中的 Agent 运行和工具调用。内联 JSON 输入必填，结构与 [`querySpans()`](/reference/observability/tracing/advanced-queries#query-spans) 相同。`where` 谓词直接筛选 span 字段。与其他可观测性命令一样，默认目标为 `https://observability.mastra.ai`。

```bash
mastra api span query <input>
mastra api span query '{"timeRange":{"from":"2026-08-07T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"where":{"op":"and","args":[{"op":"eq","left":{"path":"spanType"},"right":{"literal":"tool_call"}},{"op":"eq","left":{"path":"status"},"right":{"literal":"error"}}]}}'
```

响应保持嵌套在 `data` 下，结构为 `{ "spans": [], "page": { "next": "opaque-cursor" } }`。下一次查询时，将非空的 `data.page.next` 作为 `page.after` 传回，并保持相同的时间范围、谓词和排序。更多示例可运行 `mastra api span query --help`。

不支持 span 查询的可观测性存储会返回 `501`。若存储不支持身份、上下文、父级或根实体字段的筛选，会返回 `422`。使用前可查看服务器可观测性能力中的 `spanQueryContextFields`。CLI 会将两者打印为 `HTTP_ERROR`，服务器响应位于 `error.details.body`。

#### `mastra api span aggregate` {/* #mastra-api-span-aggregate */}

按时间范围和可选的 `where` 谓词对 span 分组，返回每组一行度量值；设置 `interval` 时，每组每个非空时间桶返回一行。支持固定度量以及 `interval`、`having`、`orderBy` 和 `limit`，与 `trace aggregate` 一致。其 `where` 直接筛选 span，维度和 `countDistinct` 字段遵循 span 契约。可按 `spanType`、`entityName`、`status` 和 `rootEntityName` 等 span 字段分组。

```bash
mastra api span aggregate <input>
mastra api span aggregate '{"timeRange":{"from":"2026-08-01T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"where":{"op":"eq","left":{"path":"spanType"},"right":{"literal":"tool_call"}},"groupBy":["entityName"],"measures":["count","errorRate","duration.p95"],"orderBy":{"field":"errorRate","direction":"desc"},"limit":10}'
```

Token 与成本度量只统计记录用量的 span，通常是 `model_generation`；不会累加到 `agent_run` 等父 span。span 维度、度量和限制详见[聚合 span](/reference/observability/tracing/advanced-queries#aggregate-spans)。更多示例可运行 `mastra api span aggregate --help`。

与 `trace aggregate` 一样，命令会将 `rows` 和 `truncated` 输出在 `data` 下。如果可观测性存储不支持 span 聚合，CLI 会将服务器的 `501` 响应打印为 `HTTP_ERROR`。

#### `mastra api score create` {/* #mastra-api-score-create */}

为追踪创建评分。记录须包装在 `score` 中，其中 `traceId` 必填、`spanId` 可选。省略 ID 和时间戳时，CLI 会自动生成，并在重试间保持不变。传入 `--schema` 可查看请求字段。

创建评分和反馈时，可传入可选的顶层 `contextMode`。设为 `"resolve"` 会从已存储的追踪或 span 查找上下文；设为 `"provided"` 则直接写入提供的字段，不进行查找。省略 `contextMode` 时，无论提供了哪些上下文字段，OSS 使用 `provided`，Platform 使用 `resolve`。

Platform 上写入成功表示记录已被接受并待存储，未必立即可读。输出会保留服务器的成功响应，以及返回的 ID 和时间戳。旧版服务器可能只返回 `success`。

#### `mastra api feedback replace` {/* #mastra-api-feedback-replace */}


创建和替换操作会在命令超时范围内重试缺失追踪或 span 的响应和暂时性故障，最多尝试六次或持续 30 秒。每次被接受的替换重试都算一次新的替换。旧版服务器若不支持 PUT，会返回错误。

## 遥测 {/* #telemetry */}

默认情况下，Mastra 会收集项目遥测数据，包括操作系统、Mastra 版本和 Node.js 版本。服务器事件还包含下述项目标识符。可阅读 [CLI 遥测源码](https://github.com/mastra-ai/mastra/blob/main/packages/cli/src/analytics/index.ts)了解 CLI 收集的内容。

通过 `mastra dev`、`mastra start` 或 `mastra build` 输出启动的服务器如果配置了可观测性，Mastra 会统计该服务器进程内每次模型调用消耗的输入与输出 token。每隔 15 分钟，以及服务器关闭时，会按自上次报告以来使用过的 Provider 和模型分别发送 `mastra_model_token_usage_v2` 事件。如果期间没有完成模型调用，则不发送。每个事件包含自上次报告以来的 token 用量、报告时间窗口的起止时间、报告原因（`interval` 或 `shutdown`）、命令（`dev`、`start`，或直接运行构建输出时的 `server`）以及 `NODE_ENV`。不会发送提示词、响应或其他消息内容。可阅读[模型用量遥测源码](https://github.com/mastra-ai/mastra/blob/main/packages/core/src/telemetry/model-usage-telemetry.ts)了解收集内容。

为兼容旧版分析，服务器启动时还会发送旧的 `mastra_model_token_usage` 事件。它从可观测性存储读取 token 总量，并发送自 `~/.mastra/usage-telemetry.json` 中保存的游标以来新增的用量。可阅读[启动用量遥测源码](https://github.com/mastra-ai/mastra/blob/main/packages/core/src/telemetry/usage-telemetry.ts)了解收集内容。

服务器启动时，Mastra 会发送项目功能概况快照，包含组件数量、功能开关和粗略的存储后端类别，但不包含组件名称或标识符。可阅读[功能遥测源码](https://github.com/mastra-ai/mastra/blob/main/packages/core/src/telemetry/feature-telemetry.ts)了解收集内容。

服务器事件 `mastra_feature_usage`、`mastra_model_token_usage` 和 `mastra_model_token_usage_v2` 包含：

* `project_id`：`MASTRA_PROJECT_ROOT` 的 SHA-256 哈希值前 16 位十六进制字符；未设置时使用当前工作目录。此标识符也作为本地模型用量游标的键。
* `project_id2`：用于跨机器和部署关联的可选标识符。若去除首尾空格后的 `MASTRA_PROJECT_ID` 是 UUID 格式，会在前面加上 `mp_` 并**未经哈希**发送。搜索 `mp_<platform-project-id>` 可查找该项目的遥测。名称、slug 和其他非 UUID 值不会作为平台标识符发送。

没有 UUID 格式的平台 ID 时，`project_id2` 使用规范化 Git `origin` 远端的 SHA-256 哈希值前 16 位十六进制字符。规范化保留小写主机名和仓库路径，去除协议、凭据、端口、查询参数、片段、末尾斜杠和 `.git` 后缀。等价的 SSH 与 HTTPS 远端会生成相同标识符。即使不同端口或 SSH 用户指向不同仓库，只要主机和路径相同，也会共用标识符。本地文件系统远端不参与计算。Git 探测异步进行，结果会在进程内缓存，包括不可用的情况。两种来源均不可用时，省略 `project_id2`。

这些服务器事件并非匿名：平台 ID 可将事件关联到项目；已知仓库 URL 也可规范化并哈希后与 Git 派生事件匹配。对 Git 身份哈希可避免发送原始仓库 URL 或凭据，但无法阻止与公开或其他已知仓库进行关联。

Studio UI 也会收集匿名的浏览器端使用分析，如页面浏览和界面交互。可阅读[源码](https://github.com/mastra-ai/mastra/blob/main/packages/playground/src/lib/analytics.tsx)了解收集内容。设置 `MASTRA_TELEMETRY_DISABLED` 也会禁用此项：该值注入服务页面，因此对 `mastra dev` 和自托管构建均有效。

在启动 Mastra 前设置此环境变量，可退出 CLI、服务器和 Studio 的使用分析。禁用后，服务器遥测不会查找 Git 远端，也不会发送任何项目标识符：

```bash
MASTRA_TELEMETRY_DISABLED=1
```

使用其他 `mastra` 命令时，也可设置此变量：

```bash
MASTRA_TELEMETRY_DISABLED=1 mastra dev
```
