# FileUploadProcessor

`FileUploadProcessor` 将用户发送的文件上传到[工作空间沙箱](/reference/workspace/sandbox)，并在发送给模型的文本说明中，用沙箱路径代替每个文件。模型始终不会收到文件内容；Agent 会使用沙箱 Tool 处理文件。

只有发送给模型的提示词发生变化。存储的消息仍保留文件，因此线程、Studio 等客户端以及其他 Agent 仍可取得原始文件。

过滤器接受的文件不会传给模型：如果当前回合的文件无法上传，处理器会停止该回合，而不会让文件直接通过。Memory 是可选的。

## 使用示例 {/* #usage-example */}

向 Agent 和处理器传入同一个工作空间：

```typescript
import { Agent } from '@mastra/core/agent'
import { FileUploadProcessor } from '@mastra/core/processors'
import { LocalSandbox, Workspace } from '@mastra/core/workspace'

const workspace = new Workspace({
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
})

export const agent = new Agent({
  id: 'file-agent',
  name: 'file-agent',
  instructions: 'Work on the files the user uploads to the sandbox.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  workspace,
  inputProcessors: [
    new FileUploadProcessor({
      workspace,
      filter: ({ extension }) => extension === 'xlsx' || extension === 'docx',
    }),
  ],
})
```

使用 `maxFileSize` 设置每个文件的大小限制。该函数返回字节数：

```typescript
import { FileUploadProcessor } from '@mastra/core/processors'

const megabyte = 1024 * 1024

const fileUpload = new FileUploadProcessor({
  workspace,
  maxFileSize: ({ mimeType }) => (mimeType.startsWith('image/') ? 5 * megabyte : 25 * megabyte),
})
```

处理器停止回合时，应读取停止原因。Tripwire 元数据的类型为 `unknown`，因此需要将其断言为 `FileUploadTripwireMetadata`：

```typescript
import { FILE_UPLOAD_ERROR_CODES } from '@mastra/core/processors'
import type { FileUploadTripwireMetadata } from '@mastra/core/processors'

const result = await agent.generate(messages)

if (result.tripwire?.processorId === 'file-upload') {
  const { code, fileName } = result.tripwire.metadata as FileUploadTripwireMetadata

  if (code === FILE_UPLOAD_ERROR_CODES.FILE_TOO_LARGE) {
    console.error(`${fileName} is too large`)
  }
}
```

## 文件选择 {/* #file-selection */}

`filter` 函数接收用户发送的每个文件，并返回 `true` 表示上传。被拒绝的文件保持原样，照常传给模型。未设置 `filter` 时，所有文件都会上传。

以下过滤器会上传除模型能够自行读取的类型以外的所有文件：

```typescript
import { FileUploadProcessor } from '@mastra/core/processors'

const readByModel = ['image/', 'audio/', 'video/', 'text/']

const fileUpload = new FileUploadProcessor({
  workspace,
  filter: ({ mimeType }) =>
    mimeType !== 'application/pdf' && !readByModel.some(prefix => mimeType.startsWith(prefix)),
})
```

`filter` 和 `maxFileSize` 接收相同的 `FileUploadFileInfo` 对象：

处理器会检查模型收到的每条用户消息中的文件，包括线程历史，以及随 signal 发送的文件。它会忽略 Agent 生成或 Tool 返回的文件。

以内联二进制、base64 或 data URL 形式发送的文件都会上传。处理器自身不会下载任何内容，因此服务器发起的请求无法借此指向内部地址：

* 模型自行获取的链接或 Provider 文件 ID 会留在提示词中，且不会调用 `filter`。
* 模型无法获取的链接会由 Mastra 在模型调用前下载。处理器会像处理其他将传给模型的文件一样处理下载后的字节。

## 上传位置 {/* #upload-location */}

文件写入沙箱执行命令的目录下，路径为 `uploads/<directory>/<sha256>.<extension>`。`<directory>` 优先使用线程 ID；没有线程时使用资源 ID；两者都没有时使用 `shared`。因此，不同线程中内容相同的文件也不会共用路径。

处理器通过 `pwd` 读取命令目录，然后写入文件并报告其绝对路径。Provider 对写入和命令的相对路径解析方式不同，因此命令 Tool 需要使用绝对路径才能找到文件。无法执行命令的沙箱会改用其 `workingDirectory`；如果两者都无法确定，路径将保持相对形式。

文件名取自内容的 SHA-256 哈希值，因此相同的字节始终写入同一路径：

* 沙箱中已存在的文件不会再次写入。后续回合只需检查它是否仍在。
* 从沙箱删除的文件，或因沙箱被回收而丢失的文件，会在下一回合重新写入。
* 同一请求中，无论调用模型多少次，每个文件只会放置一次。

路径仅保留原始文件名的扩展名。若路径看起来像原文件名，模型可能据此重新拼写路径，并向沙箱请求一个不存在的文件。原始名称仍会写在说明中。

| 发送时的名称 | 命令目录下的写入路径 |
| - | - |
|`report Q3 (final).pdf` | `uploads/<directory>/<sha256>.pdf` |
| `résumé.PDF` | `uploads/<directory>/<sha256>.pdf` |
| `../../etc/passwd` | `uploads/<directory>/<sha256>` |
| 无名称，`image/png` | `uploads/<directory>/<sha256>.png` |

未提供名称的文件，如果 MIME 类型属于常见类型，就会据此获得扩展名。

线程或资源 ID 会被重写，以确保目录名可安全用于 shell 命令。重音符号会被移除；除 `A-Z`、`a-z`、`0-9`、`.`、`_` 和 `-` 以外的每个字符都会替换为 `_`。路径分隔符和 `..` 也会替换，因此文件始终位于 `uploads/` 内。

每个文件先以临时名称写入，再移到目标位置，因此写入中断不会留下被后续回合误认为完整文件的残缺文件。如果沙箱支持 `writeFiles`，处理器会在一次调用中写入所有待写文件；否则通过 `executeCommand` 分块发送 base64 数据，此时沙箱需要提供 `base64` 和 `printf`。能执行命令的沙箱还需要提供 `sh`、`mkdir`、`pwd` 和 `mv`。无法执行命令的沙箱无法检查或移动文件，因此每个回合都会在目标位置重新写入所有文件。

## 上传后提示内容 {/* #prompt-content-after-upload */}

在发送给模型的提示词中，消息里的文件部分会在原位置被文本部分替换：

```text
[File uploaded to the sandbox]
path: /home/user/uploads/thread-1/0b2f4c6e8a1d3f5b7c9e2a4d6f8b1c3e5a7d9f2b4c6e8a1d3f5b7c9e2a4d6f8b.pdf
name: report.pdf
type: application/pdf
size: 1258291 bytes
```

存储的消息仍保留文件发送时的原样。Studio 和其他客户端会将其显示为附件，模型则会在每个回合重新收到这段说明。

## 错误行为 {/* #error-behavior */}

如果缺少 `workspace`，或它未配置沙箱，构造函数会抛出 ID 为 `FILE_UPLOAD_PROCESSOR_NO_SANDBOX` 的 `MastraError`。`error.details.code` 为 `NO_SANDBOX`。

在写入任何内容前，处理器会按当前回合文件发送时的形式检查它们。无法上传的文件会停止该回合，且不会上传任何文件。

对于线程历史中太大或无法解码的文件，处理器会用说明问题的文本替换文件，并让回合继续。这可防止已存储的文件阻塞之后的每个回合：

```text
[File not uploaded]
name: report.pdf
reason: File "report.pdf" is 31457280 bytes, over the 10485760 byte limit.
```

如果沙箱无法接收文件，例如没有沙箱、无法写入或写入失败，当前回合的文件会使该回合停止；线程历史中的文件则会被替换为说明原因的文本，回合继续。若 `filter` 或 `maxFileSize` 失败，无论影响哪个文件，回合都会停止。存储内容保持不变，修复配置后线程即可继续工作。没有待上传文件的回合不会进行检查，因此 scorer、Agent 网络以及没有线程的调用仍可正常工作。

处理器通过调用 `abort()` 并设置 `retry: false` 来停止回合。模型不会被调用。`agent.generate()` 不会拒绝 Promise，而是返回设置了 `result.tripwire` 的结果；`agent.stream()` 会发出一个 `tripwire` 块。

`FILE_UPLOAD_ERROR_CODES` 列出全部错误代码：

| 代码 | 发生条件 |
| - | - |
| `NO_SANDBOX` | 请求没有解析到沙箱，或解析失败 |
| `NO_WRITE_CAPABILITY` | 沙箱既不支持 `writeFiles`，也不支持 `executeCommand` |
| `INVALID_MAX_FILE_SIZE` | `maxFileSize` 抛出错误，或返回的不是非负数 |
| `INVALID_FILTER` | `filter` 抛出错误，或返回的不是 `true` 或 `false` |
| `INVALID_FILE_DATA` | 当前回合文件的内联数据无法解码 |
| `FILE_TOO_LARGE` | 当前回合的文件超过大小限制 |
| `UPLOAD_FAILED` | 写入沙箱失败 |

写入失败时，处理器会在停止回合前使用 `rm -f` 删除本次调用中已写入的文件。如果删除失败，或沙箱无法执行命令，`orphanPaths` 会列出可能残留的路径。

## 通过信号发送的文件 {/* #files-sent-with-signals */}

处理器会处理通过 `agent.sendMessage()` 和 `agent.sendSignal()` 发送的文件：

* 唤醒空闲 Agent 的 signal 按 `agent.stream()` 的输入处理。
* 传给正在运行的 Agent 的 signal，会在该次运行的下一次模型调用前接受检查并上传。
* 如果 signal 在持久化 Agent 首次调用模型前到达，它会在当前回合的检查后加入提示词。其文件按线程历史中的文件上传。

## 局限性 {/* #limitations */}

* **处理器 Workflow。**上传发生在 `processLLMRequest` 中；处理器嵌套在处理器 Workflow 时不会运行该方法。在这种情况下，处理器只会检查文件，文件会原样传给模型。请将 `FileUploadProcessor` 直接添加到 `inputProcessors`。
* **跨线程共享的沙箱。**各线程的目录可隔离文件，但不能提供访问保护。在其他线程或用户共用的沙箱中，任何线程的命令 Tool 都能读取所有上传文件。若文件是私有的，请[为每个用户或线程单独分配沙箱](/docs/sandbox/overview#sandboxes-per-user-or-thread)。
* **通过 Studio 发送的文本文件。**Studio 会将 CSV、JSON、Markdown 或源码等文本文件作为文本插入消息，而非附加为文件。处理器看不到它们，因此不会上传，完整内容会进入提示词。通过 API 以文件部分发送的文件则照常上传。
