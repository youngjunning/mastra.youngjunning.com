# TokenCostControl

`TokenCostControl` 在 Agent 执行循环中实施费用上限，超过可配置的费用阈值时阻止执行或发出警告。

它通过 `processInputStep` 在每次 LLM 调用前检查费用上限。所有作用范围的费用数据都通过可观测性存储 API（`getMetricAggregate`）查询。除 `run` 外，其他范围会汇总可配置时间窗口内多次运行的费用（默认窗口为 7 天）；`run` 范围查询当前 Trace 的费用。

如需按 Token 数量限制，请改用 `TokenLimiterProcessor`。

> **原名为 `CostGuardProcessor`。** `CostGuardProcessor` 导出及其 `CostGuard*` 选项和详情类型仍可用，作为同一类的已弃用别名，处理器 ID 仍为 `'token-cost-control'`。请将导入改为 `TokenCostControl`。

支持以下六种作用范围：

- **单次运行**：通过 Trace ID 追踪一次 Agent 运行的费用
- **资源**（默认）：按 `resourceId` 追踪跨运行的累计费用
- **线程**：按 `threadId` 追踪跨运行的累计费用
- **用户**：按 `userId` 追踪跨运行的累计费用
- **组织**：按 `organizationId` 追踪跨运行的累计费用
- **会话**：按 `sessionId` 追踪跨运行的累计费用

> **费用控制是近似值。** 可观测性流水线通过缓冲导出器异步保存费用数据。运行速度较快的 Agent 可能在指标可供查询之前就超过配置的上限。请将 `maxCost` 视为可能被快速运行的 Agent 超出的近似阈值。

> **仅归属 Agent 的费用。** 费用通过 `entityType: 'agent'` 指标筛选器归属。Agent 运行之外的模型调用（例如 Workflow 步骤直接使用模型）没有 Agent 父级 Span，因此不会计入此防护器。

## 使用示例 {/* #usage-example */}

按资源追踪累计费用（默认范围）：

```typescript
import { TokenCostControl } from '@mastra/core/processors'

const tokenCostControl = new TokenCostControl({
  maxCost: 1.0,
})
```

按线程追踪 24 小时窗口内的累计费用，并在达到上限的 80% 时发出软性警告：

```typescript
import { TokenCostControl } from '@mastra/core/processors'

const tokenCostControl = new TokenCostControl({
  maxCost: 5.0,
  scope: 'thread',
  window: '24h',
  warnAtPercent: 80,
})
```

将函数传给 `maxCost`，为不同等级设置预算：

```typescript
import { TokenCostControl } from '@mastra/core/processors'

const tokenCostControl = new TokenCostControl({
  maxCost: requestContext => (requestContext?.get('tier') === 'pro' ? 10.0 : 1.0),
  scope: 'user',
})
```

将处理器附加到 Agent，并设置 `onViolation` 回调及按 Provider/模型细分的费用数据：

```typescript
import { Agent } from '@mastra/core/agent'
import { TokenCostControl } from '@mastra/core/processors'

const tokenCostControl = new TokenCostControl({
  maxCost: 5.0,
  scope: 'resource',
  window: '30d',
  strategy: 'warn',
  includeBreakdown: true,
})

tokenCostControl.onViolation = ({ detail }) => {
  console.log(
    `Cost ${detail.threshold} threshold for ${detail.scopeKey}: $${detail.usage}/$${detail.limit}`,
  )
  for (const entry of detail.breakdown ?? []) {
    console.log(`  ${entry.provider}/${entry.model}: $${entry.estimatedCost}`)
  }
}

const agent = new Agent({
  id: 'my-agent',
  name: 'my-agent',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  inputProcessors: [tokenCostControl],
})
```

## 错误行为 {/* #error-behavior */}

使用 `block` 策略（默认）时，费用超过上限后，`TokenCostControl` 会以 `retry: false` 调用 `abort()`。TripWire 元数据包含：

- `processorId`：`'token-cost-control'`
- `usage`：当前累计用量（`estimatedCost`、`costUnit`）
- `maxCost`：为请求解析出的费用上限
- `scope`：当前作用范围
- `scopeKey`：非 run 范围的标识符（如适用）
- `threshold`：始终为 `'hard'`，因为只有硬性上限会中止执行
- `breakdown`：按 Provider/模型细分的费用条目（仅当启用 `includeBreakdown` 且明细查询成功时）

使用 `warn` 策略时，每个请求至多触发一次硬性上限警告和 `onViolation` 回调。同一请求的后续步骤继续执行，不会重复发出警告。

插入违规消息的数字最多保留 6 位小数，因此消息不会出现浮点精度造成的尾数。

## 作用范围行为 {/* #scoping-behavior */}

| 范围 | 是否跨运行追踪 | 筛选条件 | 所需上下文 |
| - | - | - | - |
| `run` | 否 | 当前 Span 的 `traceId` | Trace 上下文（自动提供） |
| `resource` | 是 | `resourceId` + 时间窗口 | `RequestContext` 中的 `resourceId` |
| `thread` | 是 | `threadId` + 时间窗口 | `RequestContext` 中的 `threadId` |
| `user` | 是 | `userId` + 时间窗口 | `RequestContext` 中的 `userId` 键 |
| `organization` | 是 | `organizationId` + 时间窗口 | `RequestContext` 中的 `organizationId` 键 |
| `session` | 是 | `sessionId` + 时间窗口 | `RequestContext` 中的 `sessionId` 键 |

所有作用范围都要求可观测性存储支持 `getMetricAggregate`；如果未配置可观测性存储，Mastra 实例会在注册时抛出错误。

对于 `run` 范围，处理器从当前 Span 的 Trace 上下文读取 Trace ID。如果没有 Trace 上下文，就会跳过检查（开放失败）。

对于其他范围，如果运行时缺少所需的上下文 ID，也会跳过检查。可观测性查询失败时同样采用开放失败策略：通过 Mastra 日志记录警告，然后继续执行该步骤。

> **`user`、`organization` 和 `session` 范围需要带有标注的 Trace。** 这些范围通过指标记录中的 `userId`、`organizationId` 和 `sessionId` 字段匹配费用，字段值来自 Trace 中的 Span 元数据（例如通过 Trace 选项中的 metadata 设置）。如果 Trace 元数据不匹配，就不会匹配到任何记录，防护器也不会触发。仅设置 RequestContext 键并不够：必须同时提供 RequestContext 键（用于确定范围）和 Span 元数据（用于归属费用）。

> **关于指标持久化延迟。** 可观测性流水线使用缓冲导出器异步写出指标。LLM 调用结束后，其费用指标需要短暂时间才能供查询。在高频运行 Agent 时，费用控制可能要到实际超过阈值之后的一步或多步才检测到超限。
