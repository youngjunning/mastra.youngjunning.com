# ProviderHistoryCompat

`ProviderHistoryCompat` 处理不同模型 Provider 之间的消息历史兼容问题。它可以在调用 Provider 前重写发往模型的提示词，也可以在 API 报错后修复消息历史并重试。

当 Agent 可能切换模型 Provider，或跨 Provider 复用消息历史时，请使用此处理器。它也能处理 Provider 拒绝其他 Provider 产生的字段的情况。

## 使用示例 {/* #usage-example */}

如果列表中没有相同 `id` 的处理器，Mastra 默认会将此处理器加入每个 Agent 的 `errorProcessors`。在新增的默认处理器中，它排在首位；其发往模型的提示词规则先于其他默认处理器运行，包括重试处理器直接重发请求的逻辑。如需添加自定义规则或自行决定顺序，请传入自己的实例：

```typescript title="src/mastra/agents/my-agent.ts"
import { Agent } from '@mastra/core/agent'
import { ProviderHistoryCompat } from '@mastra/core/processors'

export const agent = new Agent({
  id: 'my-agent',
  name: 'my-agent',
  instructions: 'You are a helpful assistant.',
  model: 'anthropic/claude-sonnet-4-5',
  errorProcessors: [new ProviderHistoryCompat({ additionalRules: [/* ... */] })],
})
```

传入自己的 `ProviderHistoryCompat` 实例会取代默认实例。只有列表中没有相同 `id` 的处理器时，才会加入默认实例。如果希望重写提示词的规则在输入处理阶段运行，可将实例放在 `inputProcessors` 中。

注册位置决定处理器的哪些功能会运行：

* **响应式规则需要注册到 `errorProcessors`。** Agent 会将输入处理器包装成单个处理器 Workflow，而 API 错误处理阶段只会在错误处理器上调用 `processAPIError`。因此，只注册到 `inputProcessors` 的实例不会运行响应式规则。
* **预先处理的规则可以在任一列表运行。** `processLLMRequest` 会遍历输入处理器和解析后的错误处理器，因此注册到 `errorProcessors` 的 `ProviderHistoryCompat` 既会重写提示词，也能进行响应式恢复。注册到 `inputProcessors` 的实例则会在输入位置运行一次。

如上例所示，仅注册到 `errorProcessors` 就能覆盖两类功能。重复注册不会导致重试两次：运行器会在第一个请求重试的处理器处停止；每条响应式规则在 `retryCount` 大于零时也会退出，因此修复后的轮次只会再尝试一次。

## 内置规则 {/* #built-in-rules */}

`ProviderHistoryCompat` 包含以下内置兼容规则：

| 规则 | Provider | 执行时机 | 行为 |
| - | - | - | - |
| `strip-foreign-provider-executed-tools` | Anthropic, OpenAI, Azure OpenAI, Google/Vertex | 预先重写提示词 | 若 Provider 执行的工具调用及配对结果来自另一类 Provider，就从发往模型的提示词中移除，因为接收方无法解析其他 Provider 的工具 ID。已保存的历史不变。 |
| `anthropic-tool-id-format` | Anthropic | 预先重写提示词 | 在提示词中重写工具调用及其结果里不符合 `[a-zA-Z0-9_-]` 的 ID。若清理后的 ID 与现有 ID 冲突，就依次加上 `_2`、`_3` 等后缀。这样可避免 Provider 拒绝；已保存的历史仍保留原始 ID。对于预先检查无法识别的 Provider（如 Vertex 托管的 Claude），还有响应式回退。 |
| `cerebras-strip-reasoning-content` | Cerebras | 预先重写提示词 | 从发往模型的提示词中移除助手的 `reasoning` 片段，避免序列化成不支持的 `reasoning_content` 字段。 |
| `anthropic-strip-empty-signed-reasoning-content` | Anthropic | 响应式（匹配 Anthropic 因思维块被修改而返回的 400 错误） | 从较早的消息中移除带 Anthropic 签名、但文本为空的助手 `reasoning` 片段；旧记录可能包含此类片段。仅在 Anthropic 拒绝历史后执行，因为 Claude 5.x 也会正常返回带签名的空文本片段，必须原样重放才能维持提示词缓存。 |
| `anthropic-strip-foreign-reasoning-content` | Anthropic | 预先重写提示词 | 从发往模型的提示词中移除非 Anthropic 来源的助手 `reasoning` 片段，保留 Anthropic 原生的思维历史。 |
| `anthropic-strip-foreign-signed-reasoning` | Anthropic-compatible | 预先重写提示词 | 当原始轮次标记为另一 Provider（如 Kimi For Coding ↔ `__GATEWAY_ANTHROPIC_MODEL_SONNET__`）时，从发往模型的提示词中移除带签名的思维内容，因为接收方无法验证其他 Provider 的签名。移除后为空的轮次也会被删除；未标记来源的历史不受影响。 |
| `azure-system-reminder-transform` | Azure OpenAI | 预先重写提示词 | 在发往模型的请求中，将用户文本和系统指令里的 `<system-reminder>` 包装标签改为 `<memory-context>`。已保存的历史不变。 |
| `openai-orphan-item-id` | OpenAI, Azure OpenAI (Responses) | 响应式 API 错误恢复 | 修复 OpenAI 以 `Item 'msg_…' of type 'message' was provided without its required 'reasoning' item` 拒绝的历史。对于包含 `itemId`、但没有 `reasoning` 片段的助手消息，移除其每个带条目 ID 的片段上的 Responses `itemId`，然后重试。消息于是按值重放，而不是作为无法满足的 `item_reference`。修复只应用于当前轮次的内存消息列表。 |
| `anthropic-orphaned-thinking-step` | Anthropic | 响应式 API 错误恢复 | 修复 Anthropic 因最新助手消息中的 `thinking` 或 `redacted_thinking` 块不可修改而拒绝的历史。若纯推理步骤之后还有其他助手内容，就移除这些步骤并重试。适用于旧版 `@mastra/memory` 保存的历史（[#22798](https://github.com/mastra-ai/mastra/issues/22798)）。 |
| `tool-call-empty-input` | 所有 Provider | 预先重写提示词 | 当已保存的助手工具调用缺少输入（`undefined` 或 `null`）时，在发往模型的提示词中将其作为 `{}` 发送，因为 Provider 会拒绝无输入的工具调用（Anthropic：`tool_use.input: Field required`）。参数无法解析的调用会以这种方式保存。调用仍保留配对的错误结果，已保存的历史不变。空字符串是真实的已保存值，会原样发送。 |
| `ensure-user-first-turn` | Amazon Bedrock, Google/Vertex Gemini | 预先重写提示词 | 在开头的助手轮次前插入最简用户轮次（`.`），因为这些 Provider 会拒绝第一个非系统轮次来自助手的对话。Agent 先打招呼或 `lastMessages` 截取线程中段时会出现这种情况。此规则最后执行，因此会看到其他规则移除空轮次后的提示词。 |

Mastra 将消息转换成模型提示词格式后、发送给 Provider 前，会通过 `processLLMRequest` 运行预先处理的规则。这些重写只影响当前 Provider 调用；已保存的历史始终不变，因此记忆和 Studio 中的 ID 与内容保持原样。

Provider 拒绝请求后，会通过 `processAPIError` 运行响应式规则。这些规则可以更新持久化的 `messageList` 并请求重试。

`anthropic-tool-id-format` 同时实现两类规则。其预先处理的钩子通常能避免请求被拒绝，因此响应式钩子不会运行。详见下文[工具调用 ID 的修复仅影响提示词](#tool-call-id-repair-is-prompt-scoped)。

## `CompatRule` {/* #compatrule */}

一个 `CompatRule` 定义一项 Provider 历史兼容性修复：

```typescript
import type { CompatRule } from '@mastra/core/processors'

const removeUnsupportedPromptParts: CompatRule = {
  name: 'remove-unsupported-prompt-parts',
  applyToPrompt({ prompt, model }) {
    // Return a modified LanguageModelV2Prompt, or undefined to leave it unchanged.
    return undefined
  },
}
```

## 自定义规则 {/* #custom-rules */}

通过 `additionalRules` 传入自定义规则。自定义规则在内置规则之后运行：

```typescript title="src/mastra/agents/custom-provider-compat.ts"
import { Agent } from '@mastra/core/agent'
import { ProviderHistoryCompat, type CompatRule } from '@mastra/core/processors'

const stripUnsupportedAssistantMetadata: CompatRule = {
  name: 'strip-unsupported-assistant-metadata',
  applyToPrompt({ prompt, model }) {
    if (typeof model !== 'string' || !model.startsWith('example-provider/')) {
      return undefined
    }

    let changed = false
    const nextPrompt = prompt.map(message => {
      if (message.role !== 'assistant' || typeof message.content === 'string') {
        return message
      }

      const nextContent = message.content.map(part => {
        if (!('providerOptions' in part)) return part
        changed = true
        const { providerOptions: _providerOptions, ...rest } = part
        return rest
      })

      return { ...message, content: nextContent }
    })

    return changed ? nextPrompt : undefined
  },
}

export const agent = new Agent({
  id: 'custom-provider-agent',
  name: 'custom-provider-agent',
  instructions: 'You are a helpful assistant.',
  model: 'example-provider/model',
  inputProcessors: [
    new ProviderHistoryCompat({
      additionalRules: [stripUnsupportedAssistantMetadata],
    }),
  ],
})
```

对于不应写入记忆的 Provider 专属重写，请使用 `applyToPrompt`。新规则通常应使用此钩子，内置规则也是如此。只有在修复后的历史必须保存并供后续轮次复用，且无法提前避免 Provider 拒绝时，才应将 `fix` 与 `errorPatterns` 配合使用。

## 工具调用 ID 的修复仅影响提示词 {/* #tool-call-id-repair-is-prompt-scoped */}

Anthropic 要求 `tool_use.id` 符合 `^[a-zA-Z0-9_-]+$`。来自其他 Provider 的工具调用 ID 若包含 `.` 或 `:`，就会被拒绝。此规则会在发往模型的请求中清理这些 ID：

```typescript oxfmt:false
// What the provider receives
tool_use.id: 'call_abc_1'
// What stays in memory, in the returned messages, and in the Studio
toolCallId: 'call.abc:1'
```

`tool-call` 与配对的 `tool-result` 使用同一映射重写，因此不会破坏两者的对应关系。替换 ID 按出现顺序分配，且不会与提示词中已有的 ID 冲突：如果 `a.b` 清理后变成 `a_b`，但提示词中已有 `a_b`，重写后的 ID 就会是 `a_b_2`。

由于没有保存任何改动，调用方在后续轮次复用同一消息列表时，仍会看到原始 ID；该请求会再次执行修复。

### 响应式回退 {/* #reactive-fallback */}

Provider 拒绝请求后，该规则的 `errorPatterns` 和 `fix` 钩子会修复同一类错误。预先重写仅在 `isMaybeAnthropic(model)` 匹配时运行；对于检查未识别的 Provider 所提供的 Claude（例如 Vertex 托管的 Claude），响应式路径仍是回退方案。一旦调用已经被拒绝，也只能通过该路径修复。规则可以同时使用两种钩子；`CompatRule` 接口上的 `fix` 本身并未弃用，自定义规则仍可合理使用。
