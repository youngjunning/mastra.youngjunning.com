# Tool搜索处理器

这`ToolSearchProcessor`是一个**输入处理器**允许运行时定义的Tool发现和加载。它不是预先向Agent提供所有Tool，而是为Agent提供两个元Tool（`search_tools`和`load_tool`）让它按需查找并加载Tool。这减少了使用大型Tool库时上下文令牌的使用。

## 使用示例 {/* #usage-example */}

```typescript
import { ToolSearchProcessor } from '@mastra/core/processors'

const toolSearch = new ToolSearchProcessor({
  tools: {
    createIssue: githubTools.createIssue,
    sendEmail: emailTools.send,
    getWeather: weatherTools.forecast,
    // ... many more tools
  },
  search: {
    topK: 5,
    minScore: 0.1,
  },
})
```

## 方法 {/* #methods */}

### 国家检查（遗留`'in-memory'` store) {/* #state-inspection-legacy-in-memory-store */}

这些方法在默认情况下运行`'in-memory'` store only. They're no-ops for the `'context'` store, whose state lives in the conversation messages rather than an in-process map.

#### `clearState(threadId)` {/* #clearstatethreadid */}

清除单个线程的加载Tool状态。

```typescript
processor.clearState('thread-123')
```

#### `clearAllState()` {/* #clearallstate */}

清除每个线程的加载Tool状态。

```typescript
processor.clearAllState()
```

#### `getStateStats()` {/* #getstatestats */}

返回跟踪的线程数和最旧的访问时间，用于调试内存中的增长。

```typescript
const { threadCount, oldestAccessTime } = processor.getStateStats()
```

返回：`{ threadCount: number; oldestAccessTime: number | null }`

#### `cleanupNow()` {/* #cleanupnow */}

立即运行 TTL 清理，而不是等待计划的扫描。

```typescript
const cleaned = processor.cleanupNow()
```

返回：`number`: the count of threads cleaned up.

## 请求感知过滤 {/* #request-aware-filtering */}

使用`filter` to apply request-specific policy to runtime-defined tools. The hook receives the resolved tool ID as `toolName`, the tool, request context, and phase. `toolName` is the ID returned by `search_tools`, which may differ from the key used in the `tools` object.

```typescript
import { ToolSearchProcessor } from '@mastra/core/processors'

const toolSearch = new ToolSearchProcessor({
  tools: allTools,
  filter: ({ toolName, requestContext, phase }) => {
    const plan = requestContext?.get('plan')

    if (phase === 'search') {
      return true
    }

    return plan === 'pro' || !toolName.startsWith('premium_')
  },
})
```

这`phase` value describes where the filter is being applied:

* `search`：过滤返回的结果`search_tools`.
* `load`：块`load_tool` from loading disallowed tools.
* `active`：如果不再允许，则隐藏当前请求中已加载的Tool。

如果钩子抛出或拒绝，`ToolSearchProcessor` treats the tool as disallowed for that request. The hook may run for every matching search candidate, so keep async policy checks cheap or cached. The `search_tools` meta-tool is always available. `load_tool` is available unless `search.autoLoad` is enabled. Tools passed directly through the agent or `processInputStep` remain available unless you filter them outside `ToolSearchProcessor`, or enable `includeResolvedTools`.

## 搜索请求解决Tool {/* #searching-request-resolved-tools */}

这`tools` option is fixed at construction, so you can't list tools that only exist per request (MCP tools that need the caller's credentials, or anything returned by a dynamic `tools` function). By default those tools bypass search and occupy prompt space on every turn.

放`includeResolvedTools: true` to index them for the request and withhold them from the prompt until the agent loads them:

```typescript title="src/mastra/agents/mcp-agent.ts"
import { Agent } from '@mastra/core/agent'
import { ToolSearchProcessor } from '@mastra/core/processors'

const toolSearch = new ToolSearchProcessor({
  tools: staticTools,
  includeResolvedTools: true,
})

const agent = new Agent({
  id: 'mcp-agent',
  name: 'mcp-agent',
  instructions: 'Search for a tool when you need a capability you do not have.',
  model: '__GATEWAY_OPENAI_MODEL__',
  // Resolved per request, then searchable alongside staticTools
  tools: async ({ requestContext }) => mcpClient.getTools(requestContext.get('userToken')),
  inputProcessors: [toolSearch],
})
```

每个请求都单独索引，因此一个调用者加载的Tool永远不会解析为另一个调用者具有相同Tool名称的实例。

此选项适用于为请求解析的每个Tool，包括内存、Workspace、技能和浏览器Tool。只有`search_tools` and `load_tool` meta-tools stay in the prompt, so any tool the agent relies on implicitly must be found through search before it can be called, unless `injectCatalog` is enabled and `search.autoLoad` is `false`, in which case the agent can load it directly with `load_tool`. With `search.autoLoad: true`, `load_tool` isn't exposed and `search_tools` activates matching tools.

## 扩展使用示例 {/* #extended-usage-example */}

```typescript title="src/mastra/agents/dynamic-tools-agent.ts"
import { Agent } from '@mastra/core/agent'
import { ToolSearchProcessor } from '@mastra/core/processors'

// Tools from various integrations
import { githubTools } from './tools/github'
import { slackTools } from './tools/slack'
import { dbTools } from './tools/database'

const toolSearch = new ToolSearchProcessor({
  tools: {
    ...githubTools, // createIssue, listPRs, mergePR, ...
    ...slackTools, // sendMessage, createChannel, ...
    ...dbTools, // query, insert, update, ...
  },
  search: {
    topK: 5,
    minScore: 0.1,
  },
})

const agent = new Agent({
  id: 'dynamic-tools-agent',
  name: 'dynamic-tools-agent',
  instructions:
    'You are a helpful assistant with access to many tools. Use search_tools to find relevant tools, then load_tool to make them available.',
  model: '__GATEWAY_OPENAI_MODEL__',
  inputProcessors: [toolSearch],
})
```

AgentWorkflow程为：

1. Agent收到用户消息
2. Agent来电`search_tools` with keywords (e.g., "github issue")
3. Agent审查结果和通话`load_tool` with the tool name
4. 加载的Tool在下一回合可用
5. Agent正常使用加载的Tool

## 单步发现`autoLoad` {/* #single-step-discovery-with-autoload */}

放`search.autoLoad` to `true` to skip the separate load step. The tools returned by `search_tools` are activated immediately, and the `load_tool` meta-tool isn't exposed. This removes one model turn per discovery, which lowers token usage and latency, and works the same across providers.

```typescript
const toolSearch = new ToolSearchProcessor({
  tools: allTools,
  search: {
    topK: 3,
    autoLoad: true,
  },
})
```

和`autoLoad` the workflow becomes:

1. Agent收到用户消息
2. Agent来电`search_tools` with keywords
3. 匹配Tool会自动激活并在下一回合可用
4. Agent正常使用该Tool

每场比赛都已激活，所以请保持`topK` small (for example, `3`) to avoid adding tools the agent didn't need. Activated tools are appended after existing tools, which keeps the cached prompt prefix stable for providers that support prompt caching.

## 装载Tool存储 {/* #loaded-tool-storage */}

这`storage` option controls where the set of loaded tools is tracked. The default is `'in-memory'`. The `'context'` store is opt-in.

### `'in-memory'`（默认） {/* #in-memory-default */}

加载的Tool在每个线程的内存映射中进行跟踪，并通过基于 TTL 的清理来控制`ttl` option (default one hour). This is the original behavior:

* 无需内存配置。
* 进程重新启动时状态会丢失。
* 没有线程ID的请求共享一个`'default'` entry.

使用`clearState`, `clearAllState`, `getStateStats`, and `cleanupNow` to inspect or reset this store.

### `'context'` {/* #context */}

加载状态源自对话消息：Tool已加载，而Tool已加载`search_tools` or `load_tool` result naming it remains in the messages. This mode:

* 无需内存配置即可工作。如果没有内存，加载的Tool将仅保留用于当前进程，并且仅用于具有真实线程 ID 的请求。匿名请求要求调用者重新发送相关消息，以在调用之间保留已加载的Tool。
* 只要消息再次可用，就可以在重新启动后继续运行：从具有消息历史记录的内存中，或者因为呼叫者重新发送对话。如果没有内存，重新启动只能恢复调用者发送的消息中的内容。
* 一旦结果不再出现在消息中，就会自动卸载Tool。

```typescript
import { ToolSearchProcessor } from '@mastra/core/processors'

const toolSearch = new ToolSearchProcessor({
  tools: allTools,
  storage: 'context',
})
```

加载Tool在两种模式下都是缓存友好的：加载是仅附加的，因此对于支持提示缓存的提供程序来说，缓存的提示前缀保持稳定。

卸载Tool会更改发送到模型的定义，移动缓存的前缀，以便下一回合支付缓存写入费用，而不是接收缓存命中。在`'in-memory'` mode, this happens when `ttl` evicts a thread's state; in `'context'` mode, it happens when older-message trimming removes the tool's discovery result. The model must then search for the unloaded tool before reuse. This expected tradeoff exchanges one cache write for a smaller prefix on later turns.

## 与其他处理器结合 {/* #combining-with-other-processors */}

```typescript
import { Agent } from '@mastra/core/agent'
import { ToolSearchProcessor, TokenLimiter } from '@mastra/core/processors'

const agent = new Agent({
  id: 'my-agent',
  name: 'my-agent',
  model: '__GATEWAY_OPENAI_MODEL__',
  inputProcessors: [
    new ToolSearchProcessor({
      tools: allTools,
      search: { topK: 5 },
    }),
    // Place TokenLimiter last to ensure context fits
    new TokenLimiter(127000),
  ],
})
```
