# ToolSearchProcessor

`ToolSearchProcessor` 是一种**输入处理器**，支持在运行时发现并加载动态定义的工具。它不会预先向 Agent 提供所有工具，而是提供 `search_tools` 和 `load_tool` 两个元工具，让 Agent 按需查找和加载工具。处理大型工具库时，这有助于减少上下文 Token 用量。

## 使用示例 {/* #usage-example */}

```typescript
import { ToolSearchProcessor } from '@mastra/core/processors'

const toolSearch = new ToolSearchProcessor({
  tools: {
    createIssue: githubTools.createIssue,
    sendEmail: emailTools.send,
    getWeather: weatherTools.forecast,
    // ... many more tools
  },
  search: {
    topK: 5,
    minScore: 0.1,
  },
})
```

## 方法 {/* #methods */}

### 状态检查（旧版 `'in-memory'` 存储） {/* #state-inspection-legacy-in-memory-store */}

这些方法只作用于默认的 `'in-memory'` 存储。对于 `'context'` 存储，它们不会产生效果；后者的状态保存在对话消息中，而非进程内映射中。

#### `clearState(threadId)` {/* #clearstatethreadid */}

清除单个线程中已加载工具的状态。

```typescript
processor.clearState('thread-123')
```

#### `clearAllState()` {/* #clearallstate */}

清除所有线程中已加载工具的状态。

```typescript
processor.clearAllState()
```

#### `getStateStats()` {/* #getstatestats */}

返回已追踪线程的数量和最早访问时间，可用于排查内存增长。

```typescript
const { threadCount, oldestAccessTime } = processor.getStateStats()
```

返回：`{ threadCount: number; oldestAccessTime: number | null }`

#### `cleanupNow()` {/* #cleanupnow */}

立即执行 TTL 清理，无需等待计划中的扫描。

```typescript
const cleaned = processor.cleanupNow()
```

返回值：`number`，表示已清理的线程数量。

## 请求感知筛选 {/* #request-aware-filtering */}

使用 `filter` 为运行时定义的工具实施针对请求的策略。Hook 会收到解析后的工具 ID（`toolName`）、工具、请求上下文和阶段。`toolName` 是 `search_tools` 返回的 ID，可能与 `tools` 对象中的键不同。

```typescript
import { ToolSearchProcessor } from '@mastra/core/processors'

const toolSearch = new ToolSearchProcessor({
  tools: allTools,
  filter: ({ toolName, requestContext, phase }) => {
    const plan = requestContext?.get('plan')

    if (phase === 'search') {
      return true
    }

    return plan === 'pro' || !toolName.startsWith('premium_')
  },
})
```

`phase` 的值表示筛选器的应用阶段：

- `search`：筛选 `search_tools` 返回的结果。
- `load`：阻止 `load_tool` 加载不允许的工具。
- `active`：如果已加载的工具对当前请求不再允许，则将其隐藏。

如果 Hook 抛出错误或拒绝 Promise，`ToolSearchProcessor` 会将该工具视为对当前请求不可用。Hook 可能对每个匹配的搜索候选工具运行，因此异步策略检查应尽量轻量，或使用缓存。`search_tools` 元工具始终可用；除非启用 `search.autoLoad`，否则 `load_tool` 也可用。直接通过 Agent 或 `processInputStep` 传入的工具仍然可用，除非你在 `ToolSearchProcessor` 之外对其进行筛选，或启用 `includeResolvedTools`。

## 搜索针对请求解析的工具 {/* #searching-request-resolved-tools */}

`tools` 选项在构造时就固定下来，因此无法列出仅在单次请求中存在的工具（例如需要调用者凭证的 MCP 工具，或动态 `tools` 函数返回的工具）。默认情况下，这些工具会绕过搜索，在每一轮占用提示空间。

设置 `includeResolvedTools: true`，可为这些工具按请求建立索引，并在 Agent 加载前不将它们加入提示：

```typescript title="src/mastra/agents/mcp-agent.ts"
import { Agent } from '@mastra/core/agent'
import { ToolSearchProcessor } from '@mastra/core/processors'

const toolSearch = new ToolSearchProcessor({
  tools: staticTools,
  includeResolvedTools: true,
})

const agent = new Agent({
  id: 'mcp-agent',
  name: 'mcp-agent',
  instructions: 'Search for a tool when you need a capability you do not have.',
  model: '__GATEWAY_OPENAI_MODEL__',
  // Resolved per request, then searchable alongside staticTools
  tools: async ({ requestContext }) => mcpClient.getTools(requestContext.get('userToken')),
  inputProcessors: [toolSearch],
})
```

每个请求分别建立索引，因此一个调用者加载的工具不会解析为另一个调用者同名工具的实例。

此选项适用于为请求解析的所有工具，包括 Memory、Workspace、Skill 和浏览器工具。提示中只保留 `search_tools` 和 `load_tool` 元工具，因此 Agent 隐式依赖的工具也必须先通过搜索找到，才能调用。不过，如果启用了 `injectCatalog` 且 `search.autoLoad` 为 `false`，Agent 可以直接通过 `load_tool` 加载该工具。`search.autoLoad: true` 时不会暴露 `load_tool`，而由 `search_tools` 激活匹配工具。

## 扩展示例 {/* #extended-usage-example */}

```typescript title="src/mastra/agents/dynamic-tools-agent.ts"
import { Agent } from '@mastra/core/agent'
import { ToolSearchProcessor } from '@mastra/core/processors'

// Tools from various integrations
import { githubTools } from './tools/github'
import { slackTools } from './tools/slack'
import { dbTools } from './tools/database'

const toolSearch = new ToolSearchProcessor({
  tools: {
    ...githubTools, // createIssue, listPRs, mergePR, ...
    ...slackTools, // sendMessage, createChannel, ...
    ...dbTools, // query, insert, update, ...
  },
  search: {
    topK: 5,
    minScore: 0.1,
  },
})

const agent = new Agent({
  id: 'dynamic-tools-agent',
  name: 'dynamic-tools-agent',
  instructions:
    'You are a helpful assistant with access to many tools. Use search_tools to find relevant tools, then load_tool to make them available.',
  model: '__GATEWAY_OPENAI_MODEL__',
  inputProcessors: [toolSearch],
})
```

Agent 的工作流程如下：

1. Agent 收到用户消息
1. Agent 使用关键词调用 `search_tools`（例如“github issue”）
1. Agent 查看结果，并使用工具名称调用 `load_tool`
1. 已加载的工具在下一轮可用
1. Agent 正常使用已加载的工具

## 通过 `autoLoad` 一步发现工具 {/* #single-step-discovery-with-autoload */}

将 `search.autoLoad` 设为 `true`，可跳过单独的加载步骤。`search_tools` 返回的工具会立即激活，同时不再暴露 `load_tool` 元工具。每次发现工具可少用一轮模型调用，从而降低 Token 用量和延迟；不同 Provider 的行为一致。

```typescript
const toolSearch = new ToolSearchProcessor({
  tools: allTools,
  search: {
    topK: 3,
    autoLoad: true,
  },
})
```

启用 `autoLoad` 后，流程变为：

1. Agent 收到用户消息
1. Agent 使用关键词调用 `search_tools`
1. 匹配工具自动激活，并在下一轮可用
1. Agent 正常使用该工具

每个匹配工具都会激活，因此应将 `topK` 设得较小（例如 `3`），避免加入不需要的工具。新激活的工具会追加在现有工具之后，使支持提示缓存的 Provider 能维持稳定的缓存前缀。

## 已加载工具的状态存储 {/* #loaded-tool-storage */}

`storage` 选项控制已加载工具集合的状态存放位置。默认值为 `'in-memory'`；`'context'` 存储需要主动启用。

### `'in-memory'`（默认） {/* #in-memory-default */}

已加载的工具按线程保存在内存映射中，由 `ttl` 选项控制基于 TTL 的清理（默认一小时）。其行为如下：

- 无需配置 Memory。
- 进程重启后状态会丢失。
- 没有线程 ID 的请求共享一个 `'default'` 条目。

使用 `clearState`、`clearAllState`、`getStateStats` 和 `cleanupNow` 检查或重置此存储。

### `'context'` {/* #context */}

加载状态由对话消息推导：只要消息中仍有命名该工具的 `search_tools` 或 `load_tool` 结果，就认为该工具已加载。此模式具有以下特点：

- 无需配置 Memory。没有 Memory 时，已加载工具只在当前进程保留，且请求必须具有真实线程 ID。匿名请求若要在多次调用之间保留已加载工具，调用者必须重新发送相关消息。
- 只要消息再次可用，重启后即可恢复：消息可能来自具有消息历史的 Memory，也可能由调用者重新发送。没有 Memory 时，重启只能恢复调用者所发送消息中的状态。
- 一旦相应结果不再包含在消息中，就会自动卸载工具。

```typescript
import { ToolSearchProcessor } from '@mastra/core/processors'

const toolSearch = new ToolSearchProcessor({
  tools: allTools,
  storage: 'context',
})
```

两种模式都便于使用缓存：加载操作只会追加工具，因此支持提示缓存的 Provider 能保持稳定的缓存前缀。

卸载工具会改变发送给模型的定义，使缓存前缀发生变化，下一轮需要写入缓存，而无法命中已有缓存。在 `'in-memory'` 模式下，`ttl` 清理线程状态时会发生这种情况；在 `'context'` 模式下，裁剪较早的消息、移除工具发现结果时也会发生。此后模型必须重新搜索该工具才能复用。这是预期的取舍：增加一次缓存写入，以换取后续轮次更短的前缀。

## 与其他处理器配合 {/* #combining-with-other-processors */}

```typescript
import { Agent } from '@mastra/core/agent'
import { ToolSearchProcessor, TokenLimiter } from '@mastra/core/processors'

const agent = new Agent({
  id: 'my-agent',
  name: 'my-agent',
  model: '__GATEWAY_OPENAI_MODEL__',
  inputProcessors: [
    new ToolSearchProcessor({
      tools: allTools,
      search: { topK: 5 },
    }),
    // Place TokenLimiter last to ensure context fits
    new TokenLimiter(127000),
  ],
})
```
