# 处理器接口

这`Processor`接口定义了 Mastra 中所有处理器的合约。处理器可以实现一种或多种方法来处理Agent执行管道的不同阶段。

## 当处理器方法运行时 {/* #when-processor-methods-run */}

有关准备、Agent循环、Tool执行和最终确定的概念演练，请参阅[agent lifecycle guide](/docs/guides/agent-lifecycle).

## 回调时机 {/* #callback-timing */}

|回调或操作|频率|位置和知名度|
| - | - | - |
|`processInput` | Once per initial request | During input preparation before the loop. Resuming from a durable snapshot may skip it. |
| `processInputStep` | Once per model step | Before the provider request. It sees messages and tool results accumulated so far. |
| `processLLMRequest` | Once per provider call | Last processor stage for rewriting the provider-facing prompt. Its prompt changes aren't written back to the message list. |
| `processOutputStream`|每个流式块 |在模型输出到达时运行。当处理器选择加入时，将包括数据块。
|`processLLMResponse`|每个完成的Provider流一次 |接收当前模型步骤的完整响应。 |
|`processOutputStep`|每个模型步骤一次 |在模型响应之后、本地执行Tool之前运行。 |
|Tool[`onInputStart`](/reference/tools/create-tool#oninputstart)|流式Tool输入何时开始 |在完整的Tool参数可用之前运行。 |
|Tool[`onInputDelta`](/reference/tools/create-tool#oninputdelta)|每个流式Tool输入块 |观察增量Tool参数。 |
|Tool[`onInputAvailable`](/reference/tools/create-tool#oninputavailable)|Tool输入完成后一次 |在解析和验证参数之后、执行之前运行。 |
|Tool执行 |每次本地Tool调用一次 |接收直播[`RequestContext`](/docs/server/request-context)。批准或暂停可能会延迟执行。 |
|Tool[`onOutput`](/reference/tools/create-tool#onoutput)|本地执行成功后一次 |接收Tool输出。 |
|`processToolResult`|每个本地/客户端结果，或当延迟的提供者结果到达时 |可以在原始Tool结果进入消息列表之前进行检查、编辑或中止。 |
|`processAPIError`|关于符合条件的Provider API 错误 |可以更新请求状态并请求另一个提供者尝试。 |
|[`onIterationComplete`](/reference/agents/generate#parameters)|每次完成循环迭代后一次 |观察迭代结果并可以影响是否继续执行。 |
|`processOutputResult`|一旦完成 |在返回之前对完成的Agent结果进行后处理。 |

## 接口定义 {/* #interface-definition */}

```typescript
interface Processor<TId extends string = string, TTripwireMetadata = unknown> {
  readonly id: TId
  readonly name?: string
  readonly description?: string
  /** Index of this processor in the workflow (set at runtime when combining processors). */
  processorIndex?: number
  /** When true, processOutputStream also receives `data-*` chunks. Default: false. */
  processDataParts?: boolean

  /** Span type to trace this processor as. Defaults to `PROCESSOR_RUN`. */
  readonly spanType?: ProcessorSpanType
  /** Span name, or a function returning one per pipeline phase. */
  readonly spanName?: string | ((phase: ProcessorSpanPhase) => string)
  /** Attributes set when the span is created, or a function returning them per phase. */
  readonly spanAttributes?:
    | Partial<SpanTypeMap[ProcessorSpanType]>
    | ((phase: ProcessorSpanPhase) => Partial<SpanTypeMap[ProcessorSpanType]>)

  /** Callback invoked when this processor detects a violation, regardless of strategy. */
  onViolation?: (violation: ProcessorViolation) => void | Promise<void>

  processInput?(
    args: ProcessInputArgs<TTripwireMetadata>,
  ): Promise<ProcessInputResult> | ProcessInputResult

  processInputStep?(
    args: ProcessInputStepArgs<TTripwireMetadata>,
  ):
    | Promise<ProcessInputStepResult | MessageList | MastraDBMessage[] | undefined | void>
    | ProcessInputStepResult
    | MessageList
    | MastraDBMessage[]
    | void
    | undefined

  /** State lane id for `computeStateSignal`. Defaults to the processor id. */
  stateId?: string

  computeStateSignal?(
    args: ComputeStateSignalArgs<TTripwireMetadata>,
  ): Promise<ComputeStateSignalResult> | ComputeStateSignalResult

  processLLMRequest?(
    args: ProcessLLMRequestArgs<TTripwireMetadata>,
  ): Promise<ProcessLLMRequestResult> | ProcessLLMRequestResult

  processLLMResponse?(
    args: ProcessLLMResponseArgs<TTripwireMetadata>,
  ): Promise<ProcessLLMResponseResult> | ProcessLLMResponseResult

  processAPIError?(
    args: ProcessAPIErrorArgs<TTripwireMetadata>,
  ): Promise<ProcessAPIErrorResult | void> | ProcessAPIErrorResult | void

  processOutputStream?(
    args: ProcessOutputStreamArgs<TTripwireMetadata>,
  ): Promise<ChunkType | null | undefined>

  processOutputStep?(args: ProcessOutputStepArgs<TTripwireMetadata>): ProcessorMessageResult

  processToolResult?(args: ProcessToolResultArgs<TTripwireMetadata>): ProcessorMessageResult

  processOutputResult?(args: ProcessOutputResultArgs<TTripwireMetadata>): ProcessorMessageResult
}
```

## 追踪 {/* #tracing */}

每个处理器都会获得一个以其运行的管道阶段命名的跨度，例如`input step processor: my-processor`. That name describes how Mastra ran the processor rather than what it does, which is unhelpful for a processor a user didn't configure as one. Mastra's own built-ins declare their subsystem instead: workspace skills trace as `skill:inject`, message history as `memory: recall` and `memory: save`.

宣布`spanType` to do the same in your own processor. A processor that runs in more than one phase usually does something different in each, so `spanName` and `spanAttributes` also accept a function of the phase:

```typescript title="src/mastra/processors/session-cache.ts"
import { SpanType } from '@mastra/core/observability'
import type { Processor, ProcessorSpanPhase } from '@mastra/core/processors'

const OPERATION: Partial<Record<ProcessorSpanPhase, 'recall' | 'save'>> = {
  inputStep: 'recall',
  output: 'save',
}

export class SessionCacheProcessor implements Processor<'session-cache'> {
  readonly id = 'session-cache' as const

  readonly spanType = SpanType.MEMORY_OPERATION
  readonly spanName = (phase: ProcessorSpanPhase) => `memory: ${OPERATION[phase] ?? 'recall'}`
  readonly spanAttributes = (phase: ProcessorSpanPhase) => ({
    operationType: OPERATION[phase] ?? 'recall',
  })
}
```

声明的跨度类型替换`PROCESSOR_RUN`, but the span keeps its entity type and the runtime's own attributes, so it still records which phase the processor ran in, its position in the chain, and the changes it made to the message list. Processors that declare nothing are unaffected.

要记录仅在运行时已知的值，请从方法内部更新处理器自己的范围：

```typescript oxfmt:false
async processInputStep({ messageList, tracingContext }: ProcessInputStepArgs) {
  tracingContext?.currentSpan?.update({ attributes: { messageCount: messageList.get.all.db().length } });
  return { messageList };
}
```

## 消息参数 {/* #message-arguments */}

大多数处理器方法都接收`messages` and `messageList`. They point to the same underlying conversation but expose it differently.

### `messages`与`messageList` {/* #messages-vs-messagelist */}

* `messages`：阶段范围的数组`MastraDBMessage` objects. For input processing, `processInput` and `processInputStep` exclude system messages. For output processing, `processOutputResult` and `processOutputStep` include the latest LLM response. The array is backed by `messageList`, so in-place edits to a message's `content.parts` remain visible to downstream processors and persistence.
* `messageList`: 现场直播`MessageList` instance backing the run. It exposes filtered views (input, response, remembered, all), multiple output formats (db, ui, core), and methods for mutating the conversation.

使用`messages` when you only need to read, map over, or lightly edit fields on the current stage's messages. Use `messageList` when you need to:

* 从另一个阶段读取消息，例如在处理输出时输入消息。
* 添加、删除或替换整个消息。
* 转换为其他格式，例如第三方 API 的 UI 或核心消息。

`messages`总是源自`messageList`, so mutating `messageList` is the canonical way to add, remove, or reorder messages. For in-place edits to a message's content (for example, rewriting `content.parts`), mutating `messages` directly is equivalent. If you return a new array from `messages`, Mastra reconciles it against `messageList` for the current stage.

### 坚持 {/* #persistence */}

当内存被启用时，只有最终的内容`messageList` after all processors finish is persisted to storage. Both return styles are equivalent for persistence:

* 当你变异时`messageList` directly (or return the same `MessageList` instance), recorded mutations are applied in place. The saved conversation reflects your changes.
* 当您返回一个`MastraDBMessage[]` or `{ messages, systemMessages }`, Mastra reconciles the returned array against `messageList` for the current stage, removing missing messages and replacing system messages.

返回不同的`MessageList` instance is an error. Always mutate the one passed to your processor.

### 从消息中读取文本 {/* #reading-text-from-a-message */}

`MastraDBMessage.content`使用结构化对象。不支持字符串。阅读用户或助理文本的规范方法是`content.parts`:

```typescript
import type { MastraDBMessage } from '@mastra/core/memory'

function getText(message: MastraDBMessage): string {
  let text = ''

  if (message.content.parts) {
    for (const part of message.content.parts) {
      if (part.type === 'text' && typeof part.text === 'string') {
        text += part.text
      }
    }
  }

  // Fallback for legacy messages that only have the flattened `content` string
  if (!text && typeof message.content.content === 'string') {
    text = message.content.content
  }

  return text
}
```

要点：

* `message.content.parts`是主要来源。一条消息可以包含多个部分。非文本部分包括Tool调用和Tool结果以及文件部分。过滤依据`part.type === 'text'` before reading `part.text`.
* `message.content.content`是为了向后兼容而保留的扁平字符串。仅在以下情况下将其用作后备`parts` is empty or missing.
* `message.content`它本身从来都不是一个普通的字符串`MastraDBMessage`. Legacy `CoreMessage` shapes may be strings, but processors always receive `MastraDBMessage`.

### `processInputStep` {/* #processinputstep */}

在将输入消息发送到 LLM 之前，在Agent循环的每个步骤中处理输入消息。不像`processInput` which runs once at the start, this runs at every step including tool call continuations.

```typescript oxfmt:false
processInputStep?<TTripwireMetadata = unknown>(
  args: ProcessInputStepArgs<TTripwireMetadata>,
):
  | Promise<ProcessInputStepResult | MessageList | MastraDBMessage[] | void | undefined>
  | ProcessInputStepResult
  | MessageList
  | MastraDBMessage[]
  | void
  | undefined;
```

#### Agent循环中的执行顺序 {/* #execution-order-in-the-agentic-loop */}

1. `processInput`（开始时一次）
2. `processInputStep`来自 inputProcessors（在每一步，在 LLM 调用之前）
3. `prepareStep`回调（作为 processInputStep 管道的一部分在 inputProcessors 之后运行）
4. `computeStateSignal`来自 inputProcessors （之后`processInputStep`, before the LLM request)
5. `processLLMRequest`来自 inputProcessors（提示转换之后，提供程序调用之前）
6. 法学硕士执行
7. `processOutputStream`来自outputProcessors（在每个流块上）
8. `processLLMResponse`来自 inputProcessors （流完成后，与`processLLMRequest`)
9. `processOutputStep`来自outputProcessors（LLM响应之后，Tool执行之前）
10. Tool执行（如果需要）
11. 如果调用了Tool，则从步骤 2 开始重复

#### 处理器链接 {/* #processor-chaining */}

当多个处理器实现`processInputStep`, they run in order and changes chain through:

```text
Processor 1: receives { model: 'gpt-5.4' } → returns { model: 'gpt-5.4-mini' }
Processor 2: receives { model: 'gpt-5.4-mini' } → returns { toolChoice: 'none' }
Final: model = 'gpt-5.4-mini', toolChoice = 'none'
```

#### 系统消息隔离 {/* #system-message-isolation */}

系统消息有**reset to their original values** at the start of each step. Modifications made in `processInputStep` only affect the current step, not subsequent steps.

#### 使用案例 {/* #use-cases */}

* 基于步骤数或上下文的动态模型切换
* 在配置的步骤数后禁用Tool
* 根据对话上下文动态添加或替换Tool
* 在提供者之间转换消息部分类型（例如，`reasoning` → `thinking` for Anthropic)
* 根据步骤号或累积的上下文修改消息
* 添加特定于步骤的系统指令
* 每一步调整提供程序选项（例如缓存控制）
* 根据步骤上下文修改结构化输出模式

### `computeStateSignal` {/* #computestatesignal */}

每个模型输入步骤计算一次线程范围的状态信号，之后`processInputStep()` and before the LLM request is finalized. This method requires an agent with memory and an active `resourceId` and `threadId`.

```typescript oxfmt:false
computeStateSignal?(
  args: ComputeStateSignalArgs,
): Promise<ProcessorStateSignal | undefined | void> | ProcessorStateSignal | undefined | void;
```

返回一个状态信号来存储它，或者`undefined` or `void` when nothing changed. The returned `id` defaults to the processor's `stateId`, which itself defaults to the processor `id`. `mode` defaults to `snapshot`.

```typescript title="src/mastra/processors/error-recovery.ts"
export class ErrorRecoveryProcessor implements Processor {
  id = 'error-recovery'

  processAPIError({
    error,
    messageList,
    retryCount,
  }: ProcessAPIErrorArgs): ProcessAPIErrorResult | void {
    // Only retry once
    if (retryCount > 0) return

    // Check for a specific API error
    if (APICallError.isInstance(error) && error.message.includes('context length exceeded')) {
      // Trim older messages to fit within context
      const messages = messageList.get.all.db()
      if (messages.length > 4) {
        messageList.removeByIds([messages[1]!.id, messages[2]!.id])
        return { retry: true }
      }
    }
  }
}
```

#### 发出第二个块 {/* #emitting-a-second-chunk */}

`processOutputStream`返回一个块，但处理器有时需要为一个输入发出两个块，例如它保留的文本，然后是释放它的块。返回第一个块并将第二个块设置为 on`state` under `REPROCESS_PART_KEY`. Mastra emits the stashed chunk right after the returned one.

隐藏的块再次通过输出处理器，包括隐藏它的处理器，因此处理器必须在第二遍时将其原封不动地通过：

```typescript title="src/mastra/processors/sign-off.ts"
import { REPROCESS_PART_KEY } from '@mastra/core/processors'
import type { ChunkType } from '@mastra/core/stream'
import type { ProcessOutputStreamArgs, Processor } from '@mastra/core/processors'

export class SignOff implements Processor<'sign-off'> {
  readonly id = 'sign-off'

  async processOutputStream({ part, state }: ProcessOutputStreamArgs): Promise<ChunkType> {
    if (part.type !== 'text-end' || state.signed) return part
    state.signed = true
    state[REPROCESS_PART_KEY] = part
    return { ...part, type: 'text-delta', payload: { id: part.payload.id, text: '\n\nCheers!' } }
  }
}
```

### `processToolResult` {/* #processtoolresult */}

Use this method to enforce security policies on tool output. For example, scan for prompt injection or redact sensitive fields. Call `abort('reason', { retry: true })` to abort and retry the same step.

要替换Tool的结果，请进行变异`messageList` in place via `messageList.updateToolInvocation`. The runtime re-reads the post-processor result from the message list and overwrites the downstream tool-result stream chunk before it's enqueued, so streaming clients see the processed value.

当以下情况时此方法不会触发`tool.execute()` throws. It's called only for successful tool executions where a result is available.

#### 示例：在Tool输出中阻止提示注入 {/* #example-block-prompt-injection-in-tool-output */}

```typescript title="src/mastra/processors/scan-tool-result.ts"
import type { Processor } from '@mastra/core/processors'

export class ScanToolResult implements Processor {
  id = 'scan-tool-result'

  async processToolResult({ result, abort }) {
    const text = typeof result === 'string' ? result : JSON.stringify(result)
    if (containsPromptInjection(text)) {
      abort('blocked by scan-tool-result: suspected prompt injection')

  return /ignore (all )?(previous|prior) instructions/i.test(text)
}
```

## 处理器类型 {/* #processor-types */}

Mastra 提供类型别名以确保处理器实现所需的方法：

```typescript
// Must implement processInput, processInputStep, processLLMRequest, or processLLMResponse (or any combination)
type InputProcessor = Processor &
  (
    | { processInput: required }
    | { processInputStep: required }
    | { processLLMRequest: required }
    | { processLLMResponse: required }
  )

// Must implement processOutputStream, processOutputStep, OR processOutputResult (or any combination)
type OutputProcessor = Processor &
  (
    | { processOutputStream: required }
    | { processOutputStep: required }
    | { processOutputResult: required }
  )

// Must implement processAPIError
type ErrorProcessor = Processor & { processAPIError: required }
```

配置实现的处理器`processAPIError` in `errorProcessors`:

```typescript
const agent = new Agent({
  id: 'agent',
  errorProcessors: [new PrefillErrorHandler()],
})
```

### 每步处理器`processInputStep` {/* #per-step-processor-with-processinputstep */}

```typescript title="src/mastra/processors/dynamic-model.ts"
import type {
  Processor,
  ProcessInputStepArgs,
  ProcessInputStepResult,
} from '@mastra/core/processors'

export class DynamicModelProcessor implements Processor {
  id = 'dynamic-model'

  async processInputStep({
    stepNumber,
    steps,
    toolChoice,
  }: ProcessInputStepArgs): Promise<ProcessInputStepResult> {
    // Use a fast model for initial response
    if (stepNumber === 0) {
      return { model: '__GATEWAY_OPENAI_MODEL_LUNA__' }
    }

    // Switch to powerful model after tool calls
    if (steps.length > 0 && steps[steps.length - 1].toolCalls?.length) {
      return { model: '__GATEWAY_OPENAI_MODEL__' }
    }

    // Disable tools after 5 steps to force completion
    if (stepNumber > 5) {
      return { toolChoice: 'none' }
    }

    return {}
  }
}
```

### 消息转换器`processInputStep` {/* #message-transformer-with-processinputstep */}

```typescript title="src/mastra/processors/reasoning-transformer.ts"
import type { Processor } from '@mastra/core/processors'
import type { MastraDBMessage } from '@mastra/core/memory'

export class ReasoningTransformer implements Processor {
  id = 'reasoning-transformer'

  async processInputStep({ messages, messageList }) {
    // Transform reasoning parts to thinking parts at each step
    // This is useful when switching between model providers
    for (const msg of messages) {
      if (msg.role === 'assistant' && msg.content.parts) {
        for (const part of msg.content.parts) {
          if (part.type === 'reasoning') {
            ;(part as any).type = 'thinking'
          }
        }
      }
    }
    return messageList
  }
}
```

### 混合处理器（输入和输出） {/* #hybrid-processor-input-and-output */}

```typescript title="src/mastra/processors/content-filter.ts"
import type { Processor } from '@mastra/core/processors'
import type { MastraDBMessage } from '@mastra/core/memory'
import type { ChunkType } from '@mastra/core/stream'

export class ContentFilter implements Processor {
  id = 'content-filter'
  private blockedWords: string[]

  constructor(blockedWords: string[]) {
    this.blockedWords = blockedWords
  }

  async processInput({ messages, abort }): Promise<MastraDBMessage[]> {
    for (const msg of messages) {
      const text = msg.content.parts
        ?.filter(p => p.type === 'text')
        .map(p => p.text)
        .join(' ')

      if (this.blockedWords.some(word => text?.includes(word))) {
        abort('Blocked content detected in input')
      }
    }
    return messages
  }

  async processOutputStream({ part, abort }): Promise<ChunkType | null> {
    if (part.type === 'text-delta') {
      if (this.blockedWords.some(word => part.payload.text.includes(word))) {
        abort('Blocked content detected in output')
      }
    }
    return part
  }
}
```

### 带状态的流累加器 {/* #stream-accumulator-with-state */}

```typescript title="src/mastra/processors/word-counter.ts"
import type { Processor } from '@mastra/core/processors'
import type { ChunkType } from '@mastra/core/stream'

export class WordCounter implements Processor {
  id = 'word-counter'

  async processOutputStream({ part, state }): Promise<ChunkType> {
    // Initialize state on first chunk
    if (!state.wordCount) {
      state.wordCount = 0
    }

    // Count words in text chunks
    if (part.type === 'text-delta') {
      const words = part.payload.text.split(/\s+/).filter(Boolean)
      state.wordCount += words.length
    }

    // Log word count on finish
    if (part.type === 'finish') {
      console.log(`Total words: ${state.wordCount}`)
    }

    return part
  }
}
```

## 状态生命周期 {/* #state-lifecycle */}

每个处理器都会收到一个`state` object in `processLLMRequest`, `processLLMResponse`, `processOutputStream`, `processOutputStep`, `processOutputResult`, and `processAPIError`. State has three important properties:

* **每个处理器**：每个处理器都有自己的`state` object, keyed by the processor's `id`. Processors with different ids can't read or overwrite each other's state.
* **按请求**：在每次开始时都会创建一个新的状态对象`agent.generate()` or `agent.stream()` call. State doesn't leak between requests or between users.
* **跨方法共享**：在一个请求内，相同`state` object is passed to `processLLMRequest` (before the provider call), `processLLMResponse` (after the step completes), `processOutputStream` (for every chunk), `processOutputStep` (after every LLM step), `processOutputResult` (once at the end), and `processAPIError` (when an LLM call fails). For example, `processLLMRequest` can stash a cache key and `processLLMResponse` can read it back to write the response.

在第一次访问时防御性地初始化字段，因为`state` starts as an empty object:

```typescript
import type { Processor } from '@mastra/core/processors'

export class WordCounter implements Processor {
  id = 'word-counter'

  async processOutputStream({ part, state }) {
    state.wordCount ??= 0
    if (part.type === 'text-delta') {
      state.wordCount += part.payload.text.split(/\s+/).filter(Boolean).length
    }
    return part
  }
}
```

## 中止和绊线块 {/* #aborting-and-tripwire-chunks */}

这`abort` function on each method throws a `TripWire` error that stops processing and emits a `tripwire` chunk on the output stream. Clients can detect the chunk to distinguish a blocked response from a normal finish.

```typescript
abort('Blocked content detected', { retry: false, metadata: { category: 'pii' } })
```

* `reason`：人类可读的解释。显示为`tripwire.payload.reason`.
* `retry`： 什么时候`true`, the agent retries the same step with `reason` fed back as feedback. Retries only run when `maxProcessorRetries` is set on the agent or call; otherwise the request aborts. The safety cap of `3` that applies when no cap is set covers only error-processor retries from `processAPIError`. It doesn't give abort retries a budget.
* `metadata`：附加到的可选结构化数据`tripwire` chunk for downstream consumers.

发射的`tripwire` chunk has the shape:

```typescript
type TripwireChunk = {
  type: 'tripwire'
  runId: string
  from: 'AGENT'
  payload: {
    reason: string
    retry?: boolean
    metadata?: unknown
    processorId: string
  }
}
```

在非流式通话中（`agent.generate()`), the result exposes the same information as `result.tripwire` and `result.finishReason === 'other'`.

## 发出自定义数据块 {/* #emitting-custom-data-chunks */}

有权访问的处理器`writer` can stream custom `data-*` chunks to the client by calling `writer.custom(chunk)`. Tools can do the same through their own writer. This is the only way for a processor to emit content outside of normal text and tool chunks.

```typescript
await writer.custom({
  type: 'data-moderation',
  runId,
  from: 'AGENT',
  data: { level: 'warn', reason: 'Possibly unsafe' },
})
```

配置内存后，自定义`data-*` chunks emitted from `processOutputStream` or `processOutputResult` are saved as parts of the assistant message. Set `transient: true` on the chunk object to stream it without saving it to memory:

```typescript {4}
await writer.custom({
  type: 'data-progress',
  data: { status: 'Processing' },
  transient: true,
})
```

经过`transient` as a property of the chunk, not as the second argument to `writer.custom()`. The second argument contains writer options such as `messageId`.

默认情况下，处理器**don't** see `data-*` chunks in `processOutputStream` so they don't accidentally process tool telemetry or their own output. Opt in by setting `processDataParts: true` on the processor:

```typescript
class ModerationCollector implements Processor {
  id = 'moderation-collector'
  processDataParts = true

  async processOutputStream({ part, state }) {
    if (part.type === 'data-moderation') {
      state.warnings ??= []
      state.warnings.push(part.data)
    }
    return part
  }
}
```

大块`type` must start with `data-` to be treated as a custom data chunk. Returning `null` or `undefined` from `processOutputStream` still drops the chunk, so a processor can inspect, modify, or filter custom data the same way it filters text chunks.

## 在Agent上配置处理器 {/* #configuring-processors-on-an-agent */}

处理器通过三个阵列连接到Agent：

```typescript
import { Agent } from '@mastra/core/agent'
import { PrefillErrorHandler } from '@mastra/core/processors'

const agent = new Agent({
  id: 'support-agent',
  name: 'support-agent',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  instructions: '...',
  inputProcessors: [new ContentFilter(['secret'])],
  outputProcessors: [new WordCounter()],
  errorProcessors: [new PrefillErrorHandler()],
  maxProcessorRetries: 3,
})
```

* `inputProcessors`：在LLM之前运行。接收输入消息。
* `outputProcessors`：在 LLM 响应期间或之后运行。接收输出块或消息。
* `errorProcessors`：LLM API 调用抛出时运行。接收原始错误。

每个数组还接受一个函数，因此可以根据请求构建处理器`RequestContext`:

```typescript
new Agent({
  id: 'processor-interface-agent',
  inputProcessors: ({ requestContext }) => {
    const blockedWords = requestContext.get('blockedWords') ?? []
    return [new ContentFilter(blockedWords)]
  },
})
```

### 每次调用覆盖 {/* #per-call-overrides */}

`agent.generate()`和`agent.stream()` accept `inputProcessors`, `outputProcessors`, `errorProcessors`, and `maxProcessorRetries`. When any processor array is set on the call, it **replaces** the matching array configured on the agent for that request. Memory, workspace, skill, channel, and browser processors that Mastra adds automatically are always preserved and run around your array.

```typescript
await agent.stream('Summarize this', {
  outputProcessors: [new StreamFilter()],
  maxProcessorRetries: 5,
})
```

`maxProcessorRetries`传递的呼叫将覆盖Agent默认值。如果两者均未设置，则输入和输出处理器请求的重试将被视为中止，而错误处理器（例如[`StreamErrorRetryProcessor`](/reference/processors/stream-error-retry-processor)) are capped at 3 retries.
