# Processor 接口

`Processor` 接口定义了 Mastra 中所有处理器都须遵循的约定。处理器可以实现一种或多种方法，以处理 Agent 执行流程的不同阶段。

## 处理器方法的执行时机 {/* #when-processor-methods-run */}

如需了解准备阶段、Agent 循环、工具执行和收尾阶段的整体流程，请参阅 [Agent 生命周期指南](/docs/guides/agent-lifecycle)。

## 回调时机 {/* #callback-timing */}

| 回调或操作 | 频率 | 执行位置与可见内容 |
| - | - | - |
| `processInput` | 每次初始请求执行一次 | 在循环开始前的输入准备阶段执行。从持久化快照恢复时可能跳过。 |
| `processInputStep` | 每个模型步骤执行一次 | 在请求 Provider 之前执行，可读取此前累积的消息和工具结果。 |
| `processLLMRequest` | 每次调用 Provider 执行一次 | 是改写发给 Provider 的提示词的最后一个处理器阶段。对提示词的改动不会写回消息列表。 |
| `processOutputStream` | 每个流式输出块执行一次 | 在模型输出到达时执行。处理器选择接收数据块后，也会处理数据块。 |
| `processLLMResponse` | 每次 Provider 流完成后执行一次 | 接收当前模型步骤的完整响应。 |
| `processOutputStep` | 每个模型步骤执行一次 | 在模型响应之后、本地工具执行之前运行。 |
| 工具的 [`onInputStart`](/reference/tools/create-tool#oninputstart) | 流式工具输入开始时 | 在完整工具参数可用之前运行。 |
| 工具的 [`onInputDelta`](/reference/tools/create-tool#oninputdelta) | 每个流式工具输入块 | 观察逐步到达的工具参数。 |
| 工具的 [`onInputAvailable`](/reference/tools/create-tool#oninputavailable) | 工具输入完整时执行一次 | 在参数解析、验证之后，执行工具之前运行。 |
| 工具执行 | 每次本地工具调用执行一次 | 接收实时的 [`RequestContext`](/docs/server/request-context)。审批或挂起可能延迟执行。 |
| 工具的 [`onOutput`](/reference/tools/create-tool#onoutput) | 本地执行成功后执行一次 | 接收工具输出。 |
| `processToolResult` | 每个本地或客户端结果，以及延迟到达的 Provider 结果 | 可在原始工具结果进入消息列表前检查、脱敏或中止处理。 |
| `processAPIError` | 出现符合条件的 Provider API 错误时 | 可更新请求状态并要求再次调用 Provider。 |
| [`onIterationComplete`](/reference/agents/generate#parameters) | 每次循环迭代完成后执行一次 | 观察迭代结果，并可影响是否继续执行。 |
| `processOutputResult` | 收尾时执行一次 | 在返回完整 Agent 结果前对其进行后处理。 |

## 接口定义 {/* #interface-definition */}

```typescript
interface Processor<TId extends string = string, TTripwireMetadata = unknown> {
  readonly id: TId
  readonly name?: string
  readonly description?: string
  /** Index of this processor in the workflow (set at runtime when combining processors). */
  processorIndex?: number
  /** When true, processOutputStream also receives `data-*` chunks. Default: false. */
  processDataParts?: boolean

  /** Span type to trace this processor as. Defaults to `PROCESSOR_RUN`. */
  readonly spanType?: ProcessorSpanType
  /** Span name, or a function returning one per pipeline phase. */
  readonly spanName?: string | ((phase: ProcessorSpanPhase) => string)
  /** Attributes set when the span is created, or a function returning them per phase. */
  readonly spanAttributes?:
    | Partial<SpanTypeMap[ProcessorSpanType]>
    | ((phase: ProcessorSpanPhase) => Partial<SpanTypeMap[ProcessorSpanType]>)

  /** Callback invoked when this processor detects a violation, regardless of strategy. */
  onViolation?: (violation: ProcessorViolation) => void | Promise<void>

  processInput?(
    args: ProcessInputArgs<TTripwireMetadata>,
  ): Promise<ProcessInputResult> | ProcessInputResult

  processInputStep?(
    args: ProcessInputStepArgs<TTripwireMetadata>,
  ):
    | Promise<ProcessInputStepResult | MessageList | MastraDBMessage[] | undefined | void>
    | ProcessInputStepResult
    | MessageList
    | MastraDBMessage[]
    | void
    | undefined

  /** State lane id for `computeStateSignal`. Defaults to the processor id. */
  stateId?: string

  computeStateSignal?(
    args: ComputeStateSignalArgs<TTripwireMetadata>,
  ): Promise<ComputeStateSignalResult> | ComputeStateSignalResult

  processLLMRequest?(
    args: ProcessLLMRequestArgs<TTripwireMetadata>,
  ): Promise<ProcessLLMRequestResult> | ProcessLLMRequestResult

  processLLMResponse?(
    args: ProcessLLMResponseArgs<TTripwireMetadata>,
  ): Promise<ProcessLLMResponseResult> | ProcessLLMResponseResult

  processAPIError?(
    args: ProcessAPIErrorArgs<TTripwireMetadata>,
  ): Promise<ProcessAPIErrorResult | void> | ProcessAPIErrorResult | void

  processOutputStream?(
    args: ProcessOutputStreamArgs<TTripwireMetadata>,
  ): Promise<ChunkType | null | undefined>

  processOutputStep?(args: ProcessOutputStepArgs<TTripwireMetadata>): ProcessorMessageResult

  processToolResult?(args: ProcessToolResultArgs<TTripwireMetadata>): ProcessorMessageResult

  processOutputResult?(args: ProcessOutputResultArgs<TTripwireMetadata>): ProcessorMessageResult
}
```

## 追踪 {/* #tracing */}

每个处理器都会获得一个按其运行阶段命名的 span，例如 `input step processor: my-processor`。这个名称说明 Mastra 如何运行处理器，却不能说明处理器的用途；对于用户并非以处理器形式配置的功能尤其不直观。因此，Mastra 内置处理器会标明所属子系统：workspace skill 的追踪名称是 `skill:inject`，消息历史的追踪名称是 `memory: recall` 和 `memory: save`。

在自定义处理器中声明 `spanType`，也可以采用这种命名方式。处理器在多个阶段运行时，各阶段通常执行不同任务，因此 `spanName` 和 `spanAttributes` 也接受以阶段为参数的函数：

```typescript title="src/mastra/processors/session-cache.ts"
import { SpanType } from '@mastra/core/observability'
import type { Processor, ProcessorSpanPhase } from '@mastra/core/processors'

const OPERATION: Partial<Record<ProcessorSpanPhase, 'recall' | 'save'>> = {
  inputStep: 'recall',
  output: 'save',
}

export class SessionCacheProcessor implements Processor<'session-cache'> {
  readonly id = 'session-cache' as const

  readonly spanType = SpanType.MEMORY_OPERATION
  readonly spanName = (phase: ProcessorSpanPhase) => `memory: ${OPERATION[phase] ?? 'recall'}`
  readonly spanAttributes = (phase: ProcessorSpanPhase) => ({
    operationType: OPERATION[phase] ?? 'recall',
  })
}
```

声明 span 类型会替换 `PROCESSOR_RUN`，但 span 仍保留实体类型和运行时属性，因此仍能记录处理器运行阶段、在处理器链中的位置，以及对消息列表所做的更改。未声明这些属性的处理器不受影响。

如果某些值只有运行时才能确定，可在方法内部更新该处理器自己的 span：

```typescript oxfmt:false
async processInputStep({ messageList, tracingContext }: ProcessInputStepArgs) {
  tracingContext?.currentSpan?.update({ attributes: { messageCount: messageList.get.all.db().length } });
  return { messageList };
}
```

## 消息参数 {/* #message-arguments */}

大多数处理器方法同时接收 `messages` 和 `messageList`。两者指向同一段会话，但提供不同的访问方式。

### `messages` 与 `messageList` {/* #messages-vs-messagelist */}

- `messages`：当前阶段的 `MastraDBMessage` 数组。处理输入时，`processInput` 和 `processInputStep` 不包含系统消息；处理输出时，`processOutputResult` 和 `processOutputStep` 包含最新的 LLM 响应。该数组由 `messageList` 支撑，因此就地修改消息的 `content.parts` 后，下游处理器和持久化结果也能看到更改。
- `messageList`：支撑本次运行的实时 `MessageList` 实例。它提供按输入、响应、记忆和全部消息筛选的视图，db、ui、core 等输出格式，以及修改会话的方法。

仅需读取、映射或小幅修改当前阶段的消息字段时，使用 `messages`。以下情况使用 `messageList`：

- 读取其他阶段的消息，例如处理输出时读取输入消息。
- 添加、删除或替换整条消息。
- 将消息转换为 UI 或 core 等格式，以供第三方 API 使用。

`messages` 始终从 `messageList` 派生，因此添加、删除或重新排序消息的规范做法是修改 `messageList`。如果只是就地修改消息内容（例如改写 `content.parts`），直接修改 `messages` 效果相同。若返回新的 `messages` 数组，Mastra 会针对当前阶段将其与 `messageList` 协调同步。

### 持久化 {/* #persistence */}

启用 memory 后，只有所有处理器执行完毕后留在 `messageList` 中的内容才会存入存储。以下两种返回方式在持久化方面效果相同：

- 直接修改 `messageList`（或返回同一个 `MessageList` 实例）时，记录的修改会就地生效，保存的会话会反映这些更改。
- 返回 `MastraDBMessage[]` 或 `{ messages, systemMessages }` 时，Mastra 会针对当前阶段将返回的数组与 `messageList` 协调同步，删除缺失的消息并替换系统消息。

返回另一个 `MessageList` 实例会报错。始终修改传入处理器的实例。

### 从消息中读取文本 {/* #reading-text-from-a-message */}

`MastraDBMessage.content` 使用结构化对象，不支持字符串。读取用户或助手文本的规范方式是访问 `content.parts`：

```typescript
import type { MastraDBMessage } from '@mastra/core/memory'

function getText(message: MastraDBMessage): string {
  let text = ''

  if (message.content.parts) {
    for (const part of message.content.parts) {
      if (part.type === 'text' && typeof part.text === 'string') {
        text += part.text
      }
    }
  }

  // Fallback for legacy messages that only have the flattened `content` string
  if (!text && typeof message.content.content === 'string') {
    text = message.content.content
  }

  return text
}
```

要点：

- `message.content.parts` 是主要数据来源。一条消息可以包含多个 part。非文本 part 包括工具调用、工具结果和文件 part。读取 `part.text` 前，先用 `part.type === 'text'` 过滤。
- `message.content.content` 是为了向后兼容而保留的扁平化字符串。仅当 `parts` 为空或缺失时才用作回退方案。
- 对 `MastraDBMessage` 而言，`message.content` 本身绝不是纯字符串。旧版 `CoreMessage` 可能使用字符串内容，但处理器接收的始终是 `MastraDBMessage`。

### `processInputStep` {/* #processinputstep */}

在 Agent 循环的每一步，将输入消息发送给 LLM 前进行处理。`processInput` 只在开始时运行一次，而此方法每一步都会运行，包括工具调用后的继续执行。

```typescript oxfmt:false
processInputStep?<TTripwireMetadata = unknown>(
  args: ProcessInputStepArgs<TTripwireMetadata>,
):
  | Promise<ProcessInputStepResult | MessageList | MastraDBMessage[] | void | undefined>
  | ProcessInputStepResult
  | MessageList
  | MastraDBMessage[]
  | void
  | undefined;
```

#### Agent 循环中的执行顺序 {/* #execution-order-in-the-agentic-loop */}

1. `processInput`（开始时执行一次）
2. 来自 inputProcessors 的 `processInputStep`（每一步调用 LLM 前）
3. `prepareStep` 回调（作为 processInputStep 流程的一部分，在 inputProcessors 之后运行）
4. 来自 inputProcessors 的 `computeStateSignal`（在 `processInputStep` 之后、LLM 请求之前）
5. 来自 inputProcessors 的 `processLLMRequest`（提示词转换之后、调用 Provider 之前）
6. 执行 LLM
7. 来自 outputProcessors 的 `processOutputStream`（处理每个流式输出块）
8. 来自 inputProcessors 的 `processLLMResponse`（流结束后，与 `processLLMRequest` 配合）
9. 来自 outputProcessors 的 `processOutputStep`（LLM 响应之后、工具执行之前）
10. 执行工具（如有需要）
11. 如果调用了工具，从第 2 步重新开始

#### `ProcessInputStepResult` {/* #processinputstepresult */}

`processInputStep` 可以返回以下几种形式：

- **`ProcessInputStepResult` 对象**：覆盖当前步骤下列属性的任意组合（详见下文）。
- **`MessageList`**：返回同一个 `messageList` 实例，表示消息已就地修改。
- **`MastraDBMessage[]`**：返回转换后的消息数组，替换当前步骤的消息。
- **`void` 或 `undefined`**：不返回内容，当前步骤保持不变。

#### 处理器串联 {/* #processor-chaining */}

多个处理器实现 `processInputStep` 时，会依次运行，前一个处理器的改动会传给下一个：

```text
Processor 1: receives { model: 'gpt-5.4' } → returns { model: 'gpt-5.4-mini' }
Processor 2: receives { model: 'gpt-5.4-mini' } → returns { toolChoice: 'none' }
Final: model = 'gpt-5.4-mini', toolChoice = 'none'
```

#### 系统消息隔离 {/* #system-message-isolation */}

每一步开始时，系统消息都会**重置为原始值**。`processInputStep` 中的修改只影响当前步骤，不会延续到后续步骤。

#### 适用场景 {/* #use-cases */}

- 根据步骤编号或上下文动态切换模型
- 达到配置的步骤数后停用工具
- 根据会话上下文动态添加或替换工具
- 在不同 Provider 之间转换消息 part 类型（例如将 `reasoning` 转为 Anthropic 的 `thinking`）
- 根据步骤编号或累积的上下文修改消息
- 添加当前步骤专用的系统指令
- 逐步调整 Provider 选项（例如缓存控制）
- 根据当前步骤的上下文修改结构化输出 schema

#### 去重 {/* #deduplication */}

```typescript title="src/mastra/processors/error-recovery.ts"
import { APICallError } from '@ai-sdk/provider'
import type { Processor, ProcessAPIErrorArgs, ProcessAPIErrorResult } from '@mastra/core/processors'

export class ErrorRecoveryProcessor implements Processor {
  id = 'error-recovery'

  processAPIError({
    error,
    messageList,
    retryCount,
  }: ProcessAPIErrorArgs): ProcessAPIErrorResult | void {
    // Only retry once
    if (retryCount > 0) return

    // Check for a specific API error
    if (APICallError.isInstance(error) && error.message.includes('context length exceeded')) {
      // Trim older messages to fit within context
      const messages = messageList.get.all.db()
      if (messages.length > 4) {
        messageList.removeByIds([messages[1]!.id, messages[2]!.id])
        return { retry: true }
      }
    }
  }
}
```

丢弃一个块只影响该块；流会继续，后续块仍会被处理。若要彻底停止流，请调用 `abort()`。

#### 发出第二个块 {/* #emitting-a-second-chunk */}

`processOutputStream` 一次只返回一个块，但处理器有时需要针对一个输入发出两个块，例如先发出暂存的文本，再发出触发释放它的块。返回第一个块，并将第二个块以 `REPROCESS_PART_KEY` 为键存入 `state`。Mastra 会紧接着返回的块发出暂存块。

暂存块会再次经过输出处理器，包括暂存它的处理器，因此该处理器必须在第二次处理时原样放行：

```typescript title="src/mastra/processors/sign-off.ts"
import { REPROCESS_PART_KEY } from '@mastra/core/processors'
import type { ChunkType } from '@mastra/core/stream'
import type { ProcessOutputStreamArgs, Processor } from '@mastra/core/processors'

export class SignOff implements Processor<'sign-off'> {
  readonly id = 'sign-off'

  async processOutputStream({ part, state }: ProcessOutputStreamArgs): Promise<ChunkType> {
    if (part.type !== 'text-end' || state.signed) return part
    state.signed = true
    state[REPROCESS_PART_KEY] = part
    return { ...part, type: 'text-delta', payload: { id: part.payload.id, text: '\n\nCheers!' } }
  }
}
```

`processOutputStep` 返回 `MessageList` 或 `MastraDBMessage[]`，可直接返回，也可通过 Promise 返回。

  id = 'quality-guardrail'

  async processOutputStep({ messages, text, abort, retryCount }) {
    const score = await evaluateResponseQuality(text)

    if (score < 0.7) {
      if (retryCount < 3) {

        abort('Response quality too low. Please provide more detail.', {
          retry: true,
          metadata: { qualityScore: score },

  }

## 处理器类型 {/* #processor-types */}

Mastra 提供类型别名，以确保处理器实现必需的方法：

```typescript
// Must implement processInput, processInputStep, processLLMRequest, or processLLMResponse (or any combination)
type InputProcessor = Processor &
  (
    | { processInput: required }
    | { processInputStep: required }
    | { processLLMRequest: required }
    | { processLLMResponse: required }
  )

// Must implement processOutputStream, processOutputStep, OR processOutputResult (or any combination)
type OutputProcessor = Processor &
  (
    | { processOutputStream: required }
    | { processOutputStep: required }
    | { processOutputResult: required }
  )

// Must implement processAPIError
type ErrorProcessor = Processor & { processAPIError: required }
```

  id = 'dynamic-model'

  async processInputStep({
    stepNumber,
    steps,
    toolChoice,
  }: ProcessInputStepArgs): Promise<ProcessInputStepResult> {
    // Use a fast model for initial response
    if (stepNumber === 0) {

    // Switch to powerful model after tool calls
    if (steps.length > 0 && steps[steps.length - 1].toolCalls?.length) {

    // Disable tools after 5 steps to force completion

      return { toolChoice: 'none' }
    }

    return {}

### 同时处理输入和输出的处理器 {/* #hybrid-processor-input-and-output */}

```typescript title="src/mastra/processors/content-filter.ts"
import type { Processor } from '@mastra/core/processors'
import type { MastraDBMessage } from '@mastra/core/memory'
import type { ChunkType } from '@mastra/core/stream'

export class ContentFilter implements Processor {
  id = 'content-filter'
  private blockedWords: string[]

  constructor(blockedWords: string[]) {
    this.blockedWords = blockedWords
  }

  async processInput({ messages, abort }): Promise<MastraDBMessage[]> {
    for (const msg of messages) {
      const text = msg.content.parts
        ?.filter(p => p.type === 'text')
        .map(p => p.text)
        .join(' ')

      if (this.blockedWords.some(word => text?.includes(word))) {
        abort('Blocked content detected in input')
      }
    }
    return messages
  }

  async processOutputStream({ part, abort }): Promise<ChunkType | null> {
    if (part.type === 'text-delta') {
      if (this.blockedWords.some(word => part.payload.text.includes(word))) {
        abort('Blocked content detected in output')
      }
    }
    return part
  }
}
```

## 状态生命周期 {/* #state-lifecycle */}

每个处理器在 `processLLMRequest`、`processLLMResponse`、`processOutputStream`、`processOutputStep`、`processOutputResult` 和 `processAPIError` 中都会收到一个 `state` 对象。状态有三个重要特性：

- **处理器独立**：每个处理器都有以其 `id` 为键的独立 `state` 对象。不同 ID 的处理器无法读取或覆盖彼此的状态。
- **请求独立**：每次调用 `agent.generate()` 或 `agent.stream()` 时都会创建新的状态对象，不会在请求或用户之间泄漏。
- **跨方法共享**：同一请求中，同一个 `state` 对象会传给 `processLLMRequest`（调用 Provider 前）、`processLLMResponse`（步骤完成后）、`processOutputStream`（每个输出块）、`processOutputStep`（每个 LLM 步骤后）、`processOutputResult`（结束时一次），以及 `processAPIError`（LLM 调用失败时）。例如，`processLLMRequest` 可存入缓存键，`processLLMResponse` 再读取它并写入响应。

`state` 初始为空对象，因此首次访问字段时应做好初始化：

```typescript
import type { Processor } from '@mastra/core/processors'

export class WordCounter implements Processor {
  id = 'word-counter'

  async processOutputStream({ part, state }) {
    state.wordCount ??= 0
    if (part.type === 'text-delta') {
      state.wordCount += part.payload.text.split(/\s+/).filter(Boolean).length
    }
    return part
  }
}
```

## 中止与 tripwire 块 {/* #aborting-and-tripwire-chunks */}

每个方法的 `abort` 函数都会抛出 `TripWire` 错误，停止处理，并在输出流中发出 `tripwire` 块。客户端可据此区分被阻止的响应与正常结束的响应。

```typescript
abort('Blocked content detected', { retry: false, metadata: { category: 'pii' } })
```

- `reason`：易于理解的原因说明，显示在 `tripwire.payload.reason` 中。
- `retry`：设为 `true` 时，Agent 会将 `reason` 作为反馈并重试同一步骤。只有在 Agent 或单次调用中设置了 `maxProcessorRetries` 才会重试，否则请求会中止。未设置上限时的 `3` 次安全限制仅适用于 `processAPIError` 的错误处理器重试，不为 中止操作的重试提供次数。
- `metadata`：附加到 `tripwire` 块的可选结构化数据，供下游使用。

发出的 `tripwire` 块结构如下：

```typescript
type TripwireChunk = {
  type: 'tripwire'
  runId: string
  from: 'AGENT'
  payload: {
    reason: string
    retry?: boolean
    metadata?: unknown
    processorId: string
  }
}
```

非流式调用（`agent.generate()`）的结果通过 `result.tripwire` 和 `result.finishReason === 'other'` 提供相同信息。

## 发出自定义数据块 {/* #emitting-custom-data-chunks */}

可以访问 `writer` 的处理器可调用 `writer.custom(chunk)`，将自定义 `data-*` 块以流式方式发送给客户端。工具也可以通过自己的 writer 执行同样操作。处理器若要发出常规文本块和工具块之外的内容，只能通过这种方式。

```typescript
await writer.custom({
  type: 'data-moderation',
  runId,
  from: 'AGENT',
  data: { level: 'warn', reason: 'Possibly unsafe' },
})
```

配置 memory 后，`processOutputStream` 或 `processOutputResult` 发出的自定义 `data-*` 块会作为助手消息的一部分保存。若只想流式发送而不保存到 memory，请在块对象上设置 `transient: true`：

```typescript {4}
await writer.custom({
  type: 'data-progress',
  data: { status: 'Processing' },
  transient: true,
})
```

将 `transient` 作为块的属性传入，而不是作为 `writer.custom()` 的第二个参数。第二个参数用于传入 `messageId` 等 writer 选项。

默认情况下，处理器在 `processOutputStream` 中**不会**看到 `data-*` 块，以免误处理工具遥测数据或自身输出。若要接收这些块，请在处理器上设置 `processDataParts: true`：

```typescript
class ModerationCollector implements Processor {
  id = 'moderation-collector'
  processDataParts = true

  async processOutputStream({ part, state }) {
    if (part.type === 'data-moderation') {
      state.warnings ??= []
      state.warnings.push(part.data)
    }
    return part
  }
}
```

块的 `type` 必须以 `data-` 开头，才会被视为自定义数据块。从 `processOutputStream` 返回 `null` 或 `undefined` 仍会丢弃该块，因此处理器可以像处理文本块一样检查、修改或过滤自定义数据。

## 在 Agent 上配置处理器 {/* #configuring-processors-on-an-agent */}

通过三个数组将处理器附加到 Agent：

```typescript
import { Agent } from '@mastra/core/agent'
import { PrefillErrorHandler } from '@mastra/core/processors'

const agent = new Agent({
  id: 'support-agent',
  name: 'support-agent',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  instructions: '...',
  inputProcessors: [new ContentFilter(['secret'])],
  outputProcessors: [new WordCounter()],
  errorProcessors: [new PrefillErrorHandler()],
  maxProcessorRetries: 3,
})
```

- `inputProcessors`：在调用 LLM 前运行，接收输入消息。
- `outputProcessors`：在 LLM 响应期间或之后运行，接收输出块或消息。
- `errorProcessors`：LLM API 调用抛出错误时运行，接收原始错误。

每个数组也接受函数，以便根据 `RequestContext` 为每次请求创建处理器：

```typescript
new Agent({
  id: 'processor-interface-agent',
  inputProcessors: ({ requestContext }) => {
    const blockedWords = requestContext.get('blockedWords') ?? []
    return [new ContentFilter(blockedWords)]
  },
})
```

### 单次调用覆盖配置 {/* #per-call-overrides */}

`agent.generate()` 和 `agent.stream()` 接受 `inputProcessors`、`outputProcessors`、`errorProcessors` 及 `maxProcessorRetries`。只要在单次调用中设置了某个处理器数组，它就会为该请求**替换** Agent 上配置的对应数组。Mastra 自动添加的 memory、workspace、skill、channel 和 browser 处理器始终保留，并在你的数组前后运行。

```typescript
await agent.stream('Summarize this', {
  outputProcessors: [new StreamFilter()],
  maxProcessorRetries: 5,
})
```

单次调用传入的 `maxProcessorRetries` 会覆盖 Agent 的默认值。如果两处都未设置，输入和输出处理器要求的重试会被视为中止；错误处理器（如 [`StreamErrorRetryProcessor`](/reference/processors/stream-error-retry-processor)）则最多重试 3 次。
