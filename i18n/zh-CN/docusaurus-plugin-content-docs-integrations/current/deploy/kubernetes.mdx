# Kubernetes

在 [Kubernetes](https://kubernetes.io/) 的多个 Pod 中运行 Mastra 应用，就能在负载均衡器后面水平扩展。每个 Pod 都是一个独立进程，因此必须共享发布/订阅后端和数据库。否则，其他 Pod 无法得知某个 Pod 上启动的任务。

:::note
本指南介绍如何用手写清单部署 [Mastra 服务器](/docs/server/overview)。如果要用托管的 Chart 部署 Mastra Server 和 Studio，请参阅 [Kubernetes (Helm)](/integrations/deploy/kubernetes-helm)。如果使用[服务器适配器](/docs/server/server-adapters)或 [Web 框架](/docs/deployment/web-framework)，请按该框架的常规方式部署。
:::

:::beta
多 Pod 支持依赖[持久化 Agent](/docs/harness/durable-agents)。在 API 稳定前，即使主版本号没有变化，也可能引入不兼容变更。在生产环境中使用前，请阅读[已知限制](#known-limitations)。
:::

## 开始之前 {/* #before-you-begin */}

请准备以下资源：

* 一个 [Mastra 应用](/docs)
* 一个 [Kubernetes](https://kubernetes.io/docs/setup/) 集群和 [`kubectl`](https://kubernetes.io/docs/tasks/tools/)
* 一个集群可从中拉取镜像的容器镜像仓库
* 一个所有 Pod 均可访问的共享 [Redis](https://redis.io/) 实例
* 一个所有 Pod 均可访问的共享 [PostgreSQL](https://www.postgresql.org/) 数据库

## 为什么多个 Pod 需要共享基础设施 {/* #why-multiple-pods-need-shared-infrastructure */}

只有一个 Pod 时，所有请求都由同一进程处理，把运行状态保存在该 Pod 的内存中就够了。有多个 Pod 时，浏览器可能正在接收 Pod A 的流式输出，而用户的下一个请求被路由到 Pod B。Pod B 没有 Pod A 上的运行记录。

Redis 和 Postgres 分别负责事件传递和状态存储：

* **发布/订阅**在 Pod 之间传递事件。一个 Pod 发布事件后，其他 Pod 都会收到。Mastra 使用 [`RedisStreamsPubSub`](/reference/pubsub/redis-streams)，它还为每个线程提供租约，确保同一时间只有一个 Pod 持有该对话。参阅[发布/订阅](/docs/server/pubsub)。
* **存储**将运行状态持久化。[持久化 Agent](/docs/harness/durable-agents) 将每次运行保存为 Workflow 快照。即使 Pod 重启或请求被路由到其他 Pod，任意 Pod 都能从数据库恢复该次运行。

## 配置共享基础设施 {/* #configure-shared-infrastructure */}

让 `Mastra` 实例连接到 Redis 和 Postgres。从环境变量读取连接信息，这样所有 Pod 都可以使用同一镜像。

安装后端依赖：

```bash npm2yarn
npm install @mastra/redis-streams @mastra/pg @mastra/redis ioredis
```

在 `Mastra` 实例中配置发布/订阅、存储和共享缓存：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'
import { RedisServerCache } from '@mastra/redis'
import { PostgresStore } from '@mastra/pg'
import Redis from 'ioredis'

export const mastra = new Mastra({
  // Carries events between pods, and provides
  // per-thread leases so one pod owns a conversation at a time.
  pubsub: new RedisStreamsPubSub({
    url: process.env.REDIS_URL!,
  }),
  // Persists run state so any pod can resume a run.
  storage: new PostgresStore({
    id: 'mastra-storage',
    connectionString: process.env.DATABASE_URL!,
  }),
  // Shared event cache so a reconnecting client can replay missed chunks
  // from any pod, not only the one that started the run.
  cache: new RedisServerCache({ client: new Redis(process.env.REDIS_URL!) }),
})
```

`cache` 让客户端能够跨 Pod 续接数据流。客户端重连时会从缓存中重放错过的事件，因此所有 Pod 必须共享缓存。默认的内存缓存只能在同一进程内重放事件。

## 使用持久化 Agent {/* #use-durable-agents */}

普通 [`Agent`](/docs/agents/overview) 将流式输出和审批状态保存在单个 Pod 的内存中。请求落到另一个 Pod 时，那个 Pod 无法访问这些数据。[持久化 Agent](/docs/harness/durable-agents) 在 Workflow 中执行 Agent 循环并持久化状态，因此任意 Pod 都能观察或恢复同一次运行。

用 `createDurableAgent()` 包装 Agent：

```typescript title="src/mastra/agents/assistant.ts"
import { Agent } from '@mastra/core/agent'
import { createDurableAgent } from '@mastra/core/agent/durable'

const agent = new Agent({
  id: 'assistant',
  name: 'Assistant',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

export const durableAssistant = createDurableAgent({ agent })
```

将持久化 Agent 注册到上面配置的 `Mastra` 实例中。运行状态存入 Postgres，事件通过 Redis 传递，所有 Pod 都可访问这次运行。

## 部署 {/* #deploy */}

<Steps>
  <StepItem>
    按照 [Mastra 服务器](/docs/server/overview)指南构建服务器，将其打包成容器镜像并推送到镜像仓库。确保服务器从 `process.env.PORT` 读取端口，并在 `0.0.0.0` 上监听。
  </StepItem>

  <StepItem>
    将各 Pod 共用的连接字符串存入 Secret：

    ```bash
    kubectl create secret generic mastra-secrets \
      --from-literal=REDIS_URL='redis://redis:6379' \
      --from-literal=DATABASE_URL='postgresql://user:pass@postgres:5432/mastra'
    ```
  </StepItem>

  <StepItem>
    应用 Deployment，让容器运行该镜像并读取共享的 Secret。先启动一个副本，让第一个 Pod 独立创建数据库模式，下一步再增加副本：

    ```yaml title="deployment.yaml"
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: mastra
    spec:
      replicas: 1
      selector:
        matchLabels:
          app: mastra
      template:
        metadata:
          labels:
            app: mastra
        spec:
          containers:
            - name: mastra
              image: your-registry/mastra:latest
              ports:
                - containerPort: 8080
              env:
                - name: PORT
                  value: '8080'
              envFrom:
                - secretRef:
                    name: mastra-secrets
              readinessProbe:
                tcpSocket:
                  port: 8080
              livenessProbe:
                tcpSocket:
                  port: 8080
              resources:
                requests:
                  cpu: 500m
                  memory: 512Mi
    ```

    后面的 HorizontalPodAutoscaler 需要 `resources.requests.cpu`。Kubernetes 用实际 CPU 用量除以请求量来计算利用率。未设置 CPU 请求量时，自动扩缩容控制器无法计算目标副本数，也就不会扩缩容。

    ```bash
    kubectl apply -f deployment.yaml
    ```

    等第一个 Pod 就绪后，增加副本：

    ```bash
    kubectl wait --for=condition=available deployment/mastra
    kubectl scale deployment/mastra --replicas=3
    ```

    :::note
    每个副本都使用同一镜像，并连接到同一套 Redis 和 Postgres。仅增加 Pod 数量无法让运行跨 Pod 继续，还需要共享基础设施。
    :::
  </StepItem>

  <StepItem>
    通过 Service 暴露 Deployment：

    ```yaml title="service.yaml"
    apiVersion: v1
    kind: Service
    metadata:
      name: mastra
    spec:
      selector:
        app: mastra
      ports:
        - port: 80
          targetPort: 8080
    ```

    ```bash
    kubectl apply -f service.yaml
    ```
  </StepItem>

  <StepItem>
    用 HorizontalPodAutoscaler 自动调整副本数：

    ```yaml title="hpa.yaml"
    apiVersion: autoscaling/v2
    kind: HorizontalPodAutoscaler
    metadata:
      name: mastra
    spec:
      scaleTargetRef:
        apiVersion: apps/v1
        kind: Deployment
        name: mastra
      minReplicas: 3
      maxReplicas: 10
      metrics:
        - type: Resource
          resource:
            name: cpu
            target:
              type: Utilization
              averageUtilization: 70
    ```

    ```bash
    kubectl apply -f hpa.yaml
    ```

    :::note
    按 CPU 利用率自动扩缩容要求集群中运行 [metrics-server](https://github.com/kubernetes-sigs/metrics-server)。GKE、EKS 和 AKS 等托管集群包含它。kind 和 minikube 等本地集群不自带该组件，需要先启用，例如运行 `minikube addons enable metrics-server`。
    :::
  </StepItem>

  <StepItem>
    确认 Pod 已运行：

    ```bash
    kubectl get pods -l app=mastra
    ```

    在一个终端中将 Service 的端口转发到本地。该命令会持续在前台运行：

    ```bash
    kubectl port-forward service/mastra 8080:80
    ```

    打开另一个终端，调用 API：

    ```bash
    curl http://localhost:8080/api/agents
    ```

    如果返回的 JSON 中列出了 Agent，就说明部署已能处理请求。

    :::warning
    向公众开放端点前，请先配置[身份验证](/docs/auth/overview)。
    :::
  </StepItem>
</Steps>

## 流式传输与重连 {/* #streaming-and-reconnection */}

持久化 Agent 通过共享的发布/订阅后端，将流式数据块发布到该次运行专用的主题。客户端断线后，传入运行 ID 调用 `observe()` 即可重连，并从共享缓存中重放错过的数据块：

```typescript title="src/server/reconnect.ts"
const { output, detach } = await durableAssistant.observe(runId)

request.signal.addEventListener('abort', detach, { once: true })

if (request.signal.aborted) detach()

for await (const chunk of output.fullStream) {
  // Chunks from the run, including any missed while disconnected
}
```

运行状态保存在 Postgres，事件保存在 Redis，因此任意 Pod 都能处理重连请求，即使该次运行是在其他 Pod 上启动的。参阅[可恢复的流式传输](/docs/harness/durable-agents#resumable-streams)。

多个客户端可以同时观察同一次运行。每次调用 `observe()` 都会收到完整的数据流，因此同一用户在两台设备上查看，或两位用户同时查看时，看到的内容会保持同步。某个客户端退出循环或调用 `detach()` 时，只有该客户端会停止接收。观察端不要调用 `cleanup()`，否则会清除其他客户端重连所需的缓存事件。

## 跨 Pod 审批 Tool 调用 {/* #tool-approval-across-pods */}

持久化 Agent 会在调用 Tool 前暂停，等待人工批准。暂停的运行保存在 Postgres，因此任意 Pod 都能处理批准请求。

启动一次需要审批的运行：

```typescript title="src/server/approval.ts"
const { runId } = await durableAssistant.stream('Delete the archived records', {
  requireToolApproval: true,
  memory: { thread: 'thread-1', resource: 'user-1' },
})
```

运行会在执行 Tool 前暂停。稍后可以通过任意 Pod 批准此次调用：

```typescript
await durableAssistant.resume(runId, { approved: true })
```

处理审批的 Pod 从 Postgres 加载暂停的运行，执行获批的 Tool 调用，再通过共享的发布/订阅后端发布结果。正在观察该次运行的客户端会继续收到后续输出。参阅 [Tool 审批](/docs/harness/durable-agents#tool-approval)。

## 已知限制 {/* #known-limitations */}

* 默认配置将运行状态保存在单个 Pod 的进程内存中，其他 Pod 无法访问。配合共享的 Redis 和 Postgres 使用[持久化 Agent](/docs/harness/durable-agents)，即可跨 Pod 进行流式传输、审批和重连。
* 跨 Pod 的流式传输、审批和重连必须使用持久化 Agent。普通 Agent 将运行状态保存在内存中，无法在另一个 Pod 上恢复运行。
* 多个 Pod 同时启动并连接到尚未初始化的数据库时，可能争相创建数据库模式，导致某个 Pod 启动失败。先启动一个副本，等数据库模式创建完成后再增加副本。
* 如果需要更严格地控制初始化，请在应用之外初始化数据库模式，例如运行一次性的 Kubernetes Job，并在每个 Pod 的 `PostgresStore` 中设置 `disableInit: true`。
