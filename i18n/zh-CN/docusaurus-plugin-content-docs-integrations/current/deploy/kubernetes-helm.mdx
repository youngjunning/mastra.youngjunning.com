# Kubernetes (Helm)

:::info 仅限企业版
Helm Chart 仅供 Mastra Enterprise 客户使用。Chart 通过私有仓库分发：您的企业版许可证可兑换短期有效的拉取凭据。[联系我们](https://mastra.ai/contact)以获取企业版许可证。
:::

使用官方 `mastra-projects` Helm Chart，可在任意 Kubernetes 集群上部署 Mastra 平台，包括 Mastra Server（Agent 运行环境）和 Mastra Studio（管理界面）。该 Chart 适用于 GKE、EKS、AKS、通用集群和本地集群，并负责配置服务对外访问、TLS 和 Secret 引用。

该 Chart 遵循两项设计原则：

- **使用自己的镜像。** 通过 `mastra build` 构建 Mastra 项目的镜像，并将其推送到镜像仓库。该 Chart 不会构建镜像。
- **使用自己的数据存储。** 为 Chart 指定 PostgreSQL 数据库，并可选择指定兼容 S3 的对象存储。Chart 不包含有状态服务。

本指南介绍 Helm Chart；它会管理 Deployment、Service、Ingress 或 Gateway 资源以及 Secret。如需自行编写 Kubernetes 清单，或通过共享 pub/sub 运行多个 Server Pod，请参阅 [Kubernetes](/integrations/deploy/kubernetes)。

## 开始之前 {/* #before-you-begin */}

您需要：

- Kubernetes 1.27 或更高版本的集群，以及 [`kubectl`](https://kubernetes.io/docs/tasks/tools/)
- [Helm](https://helm.sh/docs/intro/install/) 3.8 或更高版本（支持 OCI 仓库）
- 集群能够从中拉取镜像的容器镜像仓库
- 集群可访问的 PostgreSQL 数据库
- Mastra Enterprise 许可证密钥；拉取 Chart 和在生产环境运行时都需要
- 使用 `ingress` 模式时：Ingress 控制器，或由 Chart 安装一个
- 使用 `gateway` 模式时：Gateway API CRD 和 Gateway 控制器（例如 GKE 托管的 Gateway）

## 部署 {/* #deploy */}

:::warning
构建并安装镜像之前，请在 Mastra 应用中配置[身份验证](/docs/auth/overview)。默认的 `loadBalancer` 模式会创建可从外部访问的 Service；根据集群和云服务商的配置，Server 和 Studio 可能会暴露在互联网上。
:::

<Steps>
  <StepItem>
    构建 Mastra 项目，并将构建产物制作成容器镜像。传入 `--studio`，使同一个镜像能够同时运行 Server 和 Studio：

    ```bash
    mastra build --studio
    ```

    ```dockerfile title="Dockerfile"
    FROM node:22-slim
    WORKDIR /app
    # Install dependencies inside the image: native modules (for example libsql)
    # are platform-specific, so node_modules built on your machine must not be
    # copied into the image (see .dockerignore below).
    COPY .mastra/output/package.json .mastra/output/package-lock.json* ./
    RUN npm install --force --prefer-offline --no-audit --no-fund
    COPY .mastra/output ./
    EXPOSE 4111
    CMD ["node", "index.mjs"]
    ```

    ```text title=".dockerignore"
    .mastra/output/node_modules
    ```

    :::warning
    不要将主机上构建的 `node_modules` 通过 `COPY` 放进镜像。`mastra build` 会为本机平台安装原生模块；例如，在 Apple Silicon Mac 上构建镜像并部署到 amd64 集群时，应用启动可能因 `Cannot find module '@libsql/linux-x64-gnu'` 等错误而崩溃。像上面那样在镜像内安装依赖，才能与目标平台匹配。
    :::

    将镜像推送到镜像仓库。如果本机与集群节点的架构不同（例如从 arm64 Mac 部署到 amd64 节点），构建时请使用 `--platform`：

    ```bash
    docker buildx build --platform linux/amd64 \
      -t your-registry/my-mastra-app:1.0.0 --push .
    ```

    有关构建过程的详细信息，请参阅 [Mastra Server](/docs/deployment/mastra-server)。
  </StepItem>

  <StepItem>
    将应用凭据存储在 Helm Release 所在的命名空间中。该 Chart 会从您管理的 Secret 读取数据库、许可证和模型 Provider 凭据：

    ```bash
    kubectl create namespace mastra
    kubectl create secret generic mastra-app-env -n mastra \
      --from-literal=DATABASE_URL='postgresql://user:pass@host:5432/mastra' \
      --from-literal=MASTRA_EE_LICENSE='<your-license-key>' \
      --from-literal=OPENAI_API_KEY='<provider-key>' \
      --from-literal=CLICKHOUSE_URL='https://your-instance.clickhouse.cloud:8443' \
      --from-literal=CLICKHOUSE_USERNAME='<clickhouse-username>' \
      --from-literal=CLICKHOUSE_PASSWORD='<clickhouse-password>'
    ```

    还应加入 Agent 所需的其他环境变量，例如模型 Provider 的 API 密钥。如果不使用 ClickHouse 进行可观测性监测，请省略 `CLICKHOUSE_*` 变量。
  </StepItem>

  <StepItem>
    创建 values 文件，指定镜像和 Secret：

    ```yaml title="mastra-values.yaml"
    global:
      cloud: generic # gke | eks | aks | generic | local

    mastra-server:
      image:
        repository: your-registry/my-mastra-app
        tag: '1.0.0'
      existingSecret: mastra-app-env

    mastra-studio:
      image:
        repository: your-registry/my-mastra-app
        tag: '1.0.0'
      existingSecret: mastra-app-env
    ```

    两个组件引用同一个 Secret，因为本指南使用同一个应用镜像运行 Server 和 Studio。只有当 Studio 部署不会执行需要应用 Provider 凭据的路由时，才使用不同的 Secret。

    将 `global.cloud` 设为所用平台，使 Chart 生成适用于该云平台的 LoadBalancer 和 Ingress 注解。

    如果集群尚不能访问应用镜像仓库，请创建镜像拉取 Secret：

    ```bash
    kubectl create secret docker-registry mastra-registry -n mastra \
      --docker-server=your-registry \
      --docker-username='<username>' \
      --docker-password='<access-token>'
    ```

    在两个组件中引用该 Secret：

    ```yaml title="mastra-values.yaml"
    mastra-server:
      imagePullSecrets:
        - name: mastra-registry

    mastra-studio:
      imagePullSecrets:
        - name: mastra-registry
    ```

    公共镜像以及已与集群集成的镜像仓库不需要镜像拉取 Secret。

    以上只是最简配置。执行 `helm registry login` 后，请查看所选 Chart 版本附有说明的默认值和 README，了解所有可用配置项：

    ```bash
    CHART_VERSION=0.2.0
    CHART=oci://us-central1-docker.pkg.dev/mastra-cloud/mastra-helm-ee/mastra-projects

    helm show values "$CHART" --version "$CHART_VERSION"
    helm show readme "$CHART" --version "$CHART_VERSION"
    ```
  </StepItem>

  <StepItem>
    使用企业版许可证密钥换取短期有效的仓库访问令牌，登录私有 Chart 仓库，然后安装 Chart：

    ```bash
    CHART_VERSION=0.2.0
    CHART=oci://us-central1-docker.pkg.dev/mastra-cloud/mastra-helm-ee/mastra-projects

    TOKEN=$(curl -s https://license.mastra.ai/v1/registry-token \
      -H "Authorization: Bearer $MASTRA_EE_LICENSE" | jq -r .token)

    printf '%s' "$TOKEN" | helm registry login us-central1-docker.pkg.dev \
      --username oauth2accesstoken \
      --password-stdin

    helm install mastra "$CHART" \
      --version "$CHART_VERSION" \
      -n mastra -f mastra-values.yaml
    ```

    令牌有效期较短。如果之后升级时遇到授权错误，请获取新令牌并重新登录。

    默认情况下，每个组件都通过 `LoadBalancer` 类型的 Service 对外提供访问。
  </StepItem>

  <StepItem>
    验证 Release。等待 Pod 就绪，然后检查 Server 的健康检查端点：

    ```bash
    kubectl -n mastra rollout status deployment -l app.kubernetes.io/instance=mastra
    kubectl -n mastra get svc
    ```

    ```bash
    curl http://<server-external-ip>:4111/health
    ```

    返回 `{"success":true}` 表示 Server 已运行。在浏览器中打开 Studio 的 Service 地址，即可访问 Mastra Studio 界面。
  </StepItem>
</Steps>

## 对外访问模式 {/* #exposure-modes */}

该 Chart 支持三种 Server 和 Studio 对外访问方式，通过 `global.exposure.mode` 统一选择：

| 模式 | 提供的资源 | 必填配置 |
| - | - | - |
| `loadBalancer`（默认） | 每个组件各有一个 `LoadBalancer` Service，并附带对应云平台的注解 | — |
| `ingress` | ClusterIP Service，以及每个组件各有一个 Ingress | `mastra-server.ingress.host`, `mastra-studio.ingress.host` |
| `gateway` | ClusterIP Service、一个共享 Gateway，以及每个组件各有一个 HTTPRoute | `mastra-server.httpRoute.host`, `mastra-studio.httpRoute.host` |

### 通过 Ingress 使用 Let's Encrypt TLS {/* #ingress-with-lets-encrypt-tls */}

使用 `ingress` 模式和 cert-manager，通过 HTTPS 提供两个组件的服务。Chart 可以安装 ingress-nginx 和 cert-manager，也可以使用您已经运行的控制器：

```yaml title="mastra-values.yaml"
global:
  exposure:
    mode: ingress
  tls:
    clusterIssuer: letsencrypt

ingressController:
  install: true # omit if you already run an ingress controller

tls:
  certManager:
    install: true # omit if cert-manager is already installed
  letsEncrypt:
    email: ops@example.com

mastra-server:
  ingress:
    host: api.example.com

mastra-studio:
  ingress:
    host: studio.example.com
```

设置 `tls.letsEncrypt.email` 后，Chart 会生成 `ClusterIssuer`，并为每个 Ingress 添加注解，以便自动签发证书。HTTP 请求会重定向到 HTTPS。

在 `generic` 集群上，除非您显式配置，否则 Chart 不会设置 `ingressClassName`，因此会使用集群的默认 Ingress 类。

### Gateway API {/* #gateway-api */}

在支持 Gateway API 的集群上使用 `gateway` 模式。在 GKE 上，Chart 会自动选择托管的 `gke-l7-global-external-managed` 类；在其他云平台上，请显式设置 `global.gateway.className`：

```yaml title="mastra-values.yaml"
global:
  exposure:
    mode: gateway
  tls:
    clusterIssuer: letsencrypt

mastra-server:
  httpRoute:
    host: api.example.com

mastra-studio:
  httpRoute:
    host: studio.example.com
```

Chart 会创建一个共享 Gateway，包含 HTTP 监听器和每个组件各自的 HTTPS 监听器。如需接入已有的 Gateway，请改为设置 `global.gateway.name`。

## 云平台预设 {/* #cloud-presets */}

Chart 为各平台提供 values 预设，用于设置 `global.cloud` 及该平台适用的默认值：

| 平台 | 预设 | 说明 |
| - | - | - |
| GKE | `values-gke.yaml` | 推荐使用 Gateway API；可通过 `serviceAccount.annotations` 配置 Workload Identity |
| EKS | `values-eks.yaml` | 默认使用 NLB；可通过 Ingress 注解使用 ALB；支持 IRSA |
| AKS | `values-aks.yaml` | Azure LoadBalancer 注解 |
| 本地（kind/minikube） | `values-local.yaml` | 在 `api.localhost` / `studio.localhost` 上使用 Ingress |

## 对象存储 {/* #object-storage */}

要连接兼容 S3 的对象存储（S3、支持 HMAC 互操作的 GCS 或 MinIO），请在 Server 上设置通用对象存储配置：

```yaml title="mastra-values.yaml"
mastra-server:
  externalServices:
    objectStore:
      endpoint: https://storage.googleapis.com
      bucket: my-mastra-bucket
      region: us-central1
```

请将 `S3_ACCESS_KEY_ID` 和 `S3_SECRET_ACCESS_KEY` 放入现有 Secret，不要写入 values。在 EKS 和 GKE 上，优先使用 IRSA 或 Workload Identity，而非静态密钥。

## ClickHouse 可观测性 {/* #clickhouse-observability */}

要在 ClickHouse 中持久化追踪、日志、指标、评分和反馈，请将 `CLICKHOUSE_URL`、`CLICKHOUSE_USERNAME` 和 `CLICKHOUSE_PASSWORD` 添加到 `mastra-server.existingSecret` 引用的 Secret。上面的 Secret 示例已包含用于 ClickHouse Cloud 的这些变量。

Chart 只会将这些变量提供给应用，本身不会配置可观测性或发送遥测数据。请为 `observability` 存储域配置 `ObservabilityStorageClickhouseVNext`，并在 Mastra 应用中添加 `MastraStorageExporter`。完整的应用配置请参阅 [ClickHouse](/integrations/databases/clickhouse#observability-with-vnext-recommended)。

启用 `mastra-workers` 后，worker Pod 会挂载 Server 的 Secret。如果单独安装 `mastra-workers` Chart，请将 `mastra-workers.server.existingSecret` 设为同一个 Secret 名称。`mastra-projects` Chart 会验证两个名称是否一致。

## 扩展 Server 副本 {/* #scale-server-replicas */}

Chart 默认启动一个 Server 副本。HorizontalPodAutoscaler 可以增加 Pod，但不会让 Mastra 的进程内状态在 Pod 之间共享。

将 `replicaCount` 设为大于 1，或启用 `mastra-server.autoscaling` 之前：

- 配置共享存储后端（例如 `PostgresStore`），以持久化运行状态。
- 配置分布式 PubSub 后端和共享缓存。[Kubernetes 指南](/integrations/deploy/kubernetes#configure-shared-infrastructure)使用 `RedisStreamsPubSub` 和 `RedisServerCache`，并将 `REDIS_URL` 存储在应用 Secret 中。
- 对于请求可能到达不同 Pod、但流式输出、审批和运行仍须持续的场景，使用[持久化 Agent](/docs/harness/durable-agents)。
- 先用一个副本初始化数据库 Schema，再扩展副本。对于要求更严格的部署，可通过 Kubernetes Job 初始化 Schema，并禁用每个 Pod 中的初始化。
- 查看 [worker 角色](/docs/deployment/workers#select-workers)。运行多个 scheduler 实例是安全的，因为每次调度只会被一个实例认领。

满足上述要求后，设置资源请求并启用自动扩缩容：

```yaml title="mastra-values.yaml"
mastra-server:
  resources:
    requests:
      cpu: 250m
      memory: 512Mi
  autoscaling:
    enabled: true
    minReplicas: 2
    maxReplicas: 5
    targetCPUUtilizationPercentage: 80
```

## 后台 worker {/* #background-workers */}

默认情况下，Server 在自身进程中运行 Mastra 的后台 worker。`mastra-workers` 子 Chart 将它们移至独立的 Deployment（每个角色一个），使 Workflow 编排、定时 Workflow 和后台任务能够独立于 API 扩缩容。各角色的作用见 [Workers](/docs/deployment/workers)。

worker **需要显式启用**：未启用时不会部署任何 worker。

### 前提条件 {/* #requirements */}

启用 worker 之前：

- **在 Mastra 应用中配置支持拉取事件的 PubSub 后端**，例如 Redis Streams、Valkey Streams 或 Google Cloud Pub/Sub。worker 会从消息代理拉取事件，因此仅支持请求/响应的后端无法使用。将连接字符串（如 `REDIS_URL`）放入 Server 使用的同一个 Secret。
- **如果启用 scheduler，配置支持 `schedules` 域的存储后端**：PostgreSQL、LibSQL、MySQL、MongoDB、Spanner 或 Convex。Redis 和 ClickHouse 不支持该域，scheduler 无法从中找到到期的调度。
- **设置 `mastra-server.workers.splitDeployment: true`。** 否则 API 仍会在进程内运行 worker，导致每个 worker 除了在独立 Deployment 中运行，还会在 API Pod 中运行。启用 worker 却未设置此项时，Chart 会拒绝渲染。

:::warning Redis 淘汰策略
请将 Redis 或 Valkey 的 `maxmemory-policy` 设为 `noeviction`。任何允许淘汰的策略都会在内存不足时删除仍在使用的 Mastra 状态：`allkeys-*` 策略会淘汰尚未确认的 Workflow 事件，`volatile-*` 策略则会淘汰租约键和流；后两者默认带有 TTL。之后运行可能停滞，却不会产生运行错误。当策略允许淘汰时，`RedisStreamsPubSub` 和 `ValkeyStreamsPubSub` 会在首次连接后记录一次警告。在托管 Redis 中，此项通常通过参数组设置；Amazon ElastiCache 的默认值是 `volatile-lru`。
:::

### 将 worker 构建产物加入镜像 {/* #build-the-worker-artifact-into-your-image */}

worker 使用与 Server **相同的镜像**，但使用镜像中的另一入口程序。单独执行 `mastra build` 不会生成该入口程序，因此还需执行一次构建，并将输出写入其他目录：

```bash
mastra build --studio
mastra worker build --output-dir .mastra/worker
```

必须指定 `--output-dir`。否则，`mastra worker build` 会写入 `.mastra/output`，**覆盖 Server 构建产物**，最终镜像中只剩 worker 产物。

两个构建产物声明的依赖不同：worker 会引入 Server 产物未列出的 `bufferutil`、`pg` 等包。因此，两者都需要分别执行 `npm install`。Node 从入口程序所在目录向上查找模块，因此 worker 能在 `.mastra/worker/node_modules` 中找到自己的依赖：

```dockerfile title="Dockerfile"
FROM node:22-slim
WORKDIR /app

# Server bundle and its dependencies.
COPY .mastra/output/package.json .mastra/output/package-lock.json* ./
RUN npm install --force --prefer-offline --no-audit --no-fund
COPY .mastra/output ./

# Worker bundle and its dependencies, which differ from the server's.
COPY .mastra/worker/package.json .mastra/worker/package-lock.json* ./.mastra/worker/
RUN cd .mastra/worker && npm install --force --prefer-offline --no-audit --no-fund
COPY .mastra/worker ./.mastra/worker

EXPOSE 4111
CMD ["node", "index.mjs"]
```

```text title=".dockerignore"
.mastra/output/node_modules
.mastra/worker/node_modules
```

Server 仍通过 `CMD ["node", "index.mjs"]` 启动，Studio 资源仍位于 `/app/studio`，所以 Server 和 Studio 的部署方式无需改变。worker 入口程序位于 `/app/.mastra/worker/index.mjs`，对应 Chart 默认的 `mastra-workers.command`。如果镜像目录布局不同，请覆盖该配置项。

:::warning 每次构建使用新标签
每次构建都应使用独立的镜像标签。Chart 默认将 `imagePullPolicy` 设为 `IfNotPresent`；如果重新推送已有标签，节点可能继续运行缓存的镜像摘要，worker Pod 也会因旧构建产物而持续崩溃。
:::

### 启用 worker {/* #enable-workers */}

worker 使用与 Server **相同的镜像**；`mastra build` 会在生成 Server 入口程序的同时生成 worker 入口程序。只需设置一次 `global.image`，就能使所有组件使用同一构建版本：

```yaml title="mastra-values.yaml"
global:
  image:
    repository: your-registry/my-mastra-app
    tag: '1.0.0'

mastra-server:
  existingSecret: mastra-app-env
  # Required: stop the API from also running workers in-process.
  workers:
    splitDeployment: true

mastra-workers:
  enabled: true
  server:
    # Must match mastra-server.existingSecret; the chart verifies this.
    existingSecret: mastra-app-env
  roles:
    orchestration:
      enabled: true
      replicaCount: 2
    scheduler:
      enabled: true
    backgroundTasks:
      enabled: true
```

worker Pod 挂载 **Server 的** ConfigMap 和 Secret，而不是定义自己的配置，因此它们与 API 的配置天然一致，无需维护两份相同的环境配置。

### 角色和扩缩容 {/* #roles-and-scaling */}

| 角色 | 可扩容 | 说明 |
| - | - | - |
| `orchestration` | 可以 | 消费 `workflows` 主题，并回调 API 执行步骤。消费者组将工作分配给各个副本。 |
| `scheduler` | **不可以，始终为 1 个副本** | 轮询存储，查找已到执行时间的 cron 调度。Chart 将副本数固定为 1，并使用 `Recreate` 策略。额外的 scheduler 虽然安全，但只会增加轮询负载，不会提高吞吐量。 |
| `backgroundTasks` | 可以 | 在请求处理路径之外执行标记为 `background: { enabled: true }` 的 Agent Tool 调用。 |

两个可扩容角色都支持自动扩缩容。利用率目标必须有对应的资源请求；如果缺少资源请求却启用了自动扩缩容，Chart 将无法渲染：

```yaml title="mastra-values.yaml"
mastra-workers:
  roles:
    orchestration:
      resources:
        requests:
          cpu: 200m
          memory: 512Mi
      autoscaling:
        enabled: true
        minReplicas: 2
        maxReplicas: 5
        targetCPUUtilizationPercentage: 80
```

CPU 利用率只能粗略反映队列积压程度。如需根据待处理事件数扩缩容，请使用 [KEDA](https://keda.sh/) 的 Redis Streams scaler，并指向同一个消费者组。

### 单独使用 worker 镜像 {/* #separate-worker-images */}

如果构建分别生成 API 镜像和 worker 镜像，而不是生成同时包含两个入口程序的镜像，Chart 默认的版本一致性检查会拒绝这种差异。请显式关闭该检查：

```yaml title="mastra-values.yaml"
mastra-workers:
  image:
    tag: worker
    # Server and workers intentionally run different builds; keeping them on the
    # same source commit becomes your responsibility.
    allowServerSkew: true
  command: ['node', 'index.mjs'] # match your worker image's entrypoint
```

这项检查用于防范 API 与 worker 的版本不一致，因为双方都不会显式报错：worker 仍会启动并消费队列，却会针对新的 API 运行旧的步骤代码。

### 配置更改后重启 worker {/* #restarting-workers-after-a-config-change */}

Server 的 ConfigMap 或 Secret 更改后，worker Pod 不会自动重启。Helm 的校验和注解只覆盖 Chart 自身管理的对象，而这些对象属于 `mastra-server`。请手动滚动重启 worker：

```bash
kubectl rollout restart deploy -n mastra   -l app.kubernetes.io/name=mastra-workers,app.kubernetes.io/instance=mastra
```

## 生产环境检查清单 {/* #production-checklist */}

- 使用 `existingSecret` 引用凭据，不要在 values 中写入明文。
- 通过 `mastra-server.resources` 和 `mastra-studio.resources` 设置资源请求。
- 优先单独安装 cert-manager 和 Ingress 控制器，而不是使用 Chart 内置的安装开关；在总括 Chart 中管理 CRD 生命周期会使升级更复杂。
- 配置共享存储、分布式 PubSub、共享缓存及所需的进程角色后，再启用多个副本。
- 运行后台 worker 时，设置 `mastra-server.workers.splitDeployment: true`，并将 Redis 或 Valkey 的 `maxmemory-policy` 设为 `noeviction`。
- Chart 默认采用安全加固配置：容器以非 root 用户运行、根文件系统只读、seccomp 使用 `RuntimeDefault`，且不自动挂载 ServiceAccount 令牌。

## 升级和卸载 {/* #upgrade-and-uninstall */}

使用同一条命令即可升级 Chart 版本或部署新镜像标签：

```bash
CHART_VERSION=0.2.0
CHART=oci://us-central1-docker.pkg.dev/mastra-cloud/mastra-helm-ee/mastra-projects

helm upgrade mastra "$CHART" \
  --version "$CHART_VERSION" \
  -n mastra -f mastra-values.yaml
```

Chart 会将配置和 Secret 内容的哈希值写入 Pod 注解，因此配置更改会自动触发滚动重启。

卸载 Release：

```bash
helm uninstall mastra -n mastra
```

数据库和对象存储不受影响，因为 Chart 不管理有状态服务。

## 故障排查 {/* #troubleshooting */}

- **`helm install` 或 `upgrade` 报 `401 Unauthorized` 或 `UNAUTHORIZED`。** 仓库访问令牌缺失或已过期。使用企业版许可证从 `https://license.mastra.ai/v1/registry-token` 获取新令牌，再次运行 `helm registry login`。
- **Pod 因 `Cannot find module '@libsql/linux-x64-gnu'`（或类似错误）而崩溃。** 镜像包含为其他平台构建的 `node_modules`。请在镜像内部安装依赖，通过 `.dockerignore` 排除主机上构建的 `node_modules`，然后使用与集群节点匹配的 `--platform` 重新构建。
- **Pod 因许可证错误反复崩溃。** 配置企业版功能后，生产模式要求 Secret 中包含有效的 `MASTRA_EE_LICENSE`。
- **Studio 显示 Server API，而不是界面。** 构建镜像时未包含 Studio 资源。请使用 `mastra build --studio` 重新构建。
- **worker Pod 因 `Cannot find module '/app/.mastra/worker/index.mjs'` 反复崩溃。** 镜像未包含 worker 构建产物。请运行 `mastra worker build --output-dir .mastra/worker` 并将产物复制到镜像中，或覆盖 `mastra-workers.command` 以匹配镜像布局。
- **Workflow 停滞且没有错误。** 编排 worker 无法访问 API，或 Redis 淘汰了尚未确认的事件。请核对 `mastra-workers.server.port` 与 `mastra-server.service.port`，确认限制性 NetworkPolicy 允许 worker Pod 通行，并检查 `maxmemory-policy` 是否为 `noeviction`。
- **worker Pod 一直处于 `CreateContainerConfigError`。** 它们会挂载 Server 的 ConfigMap 和 Secret，因此 `mastra-workers.server.existingSecret` 必须与 `mastra-server.existingSecret` 一致，而且不能将 `mastra-workers` 作为独立 Release 安装。
- **Ingress 没有地址。** 确认 Ingress 控制器正在运行，或设置 `ingressController.install=true`。
- **在 gateway 模式下，证书一直处于待签发状态。** 某些 Gateway 控制器在监听器已有证书之前无法处理 ACME 质询。请查看 Chart 的各云平台预设和发行说明，了解对应平台的初始化步骤。
