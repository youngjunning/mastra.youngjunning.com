# Inngest

[Inngest](https://www.inngest.com/docs) 是一个用于构建和运行后台 Workflow 的开发平台，无需自行管理基础设施。

如需查看包含高级流量控制功能的完整示例，请参阅 [Inngest Workflow 示例](https://github.com/mastra-ai/mastra/tree/main/examples/inngest)。

## Inngest 如何与 Mastra 协同工作 {/* #how-inngest-works-with-mastra */}

Inngest 与 Mastra 通过对应各自的 Workflow 模型实现集成：Inngest 将逻辑组织为由步骤构成的函数，而使用 `createWorkflow()` 和 `createStep()` 定义的 Mastra Workflow 可直接映射到这一结构。每个 Mastra Workflow 都会成为一个具有唯一标识符的 Inngest 函数，其中的每个步骤则对应一个 Inngest 步骤。

`serve()` 通过将 Mastra Workflow 注册为 Inngest 函数，并设置执行和监控所需的事件处理程序，连接这两个系统。

事件触发 Workflow 后，Inngest 会逐步执行并缓存每一步的结果。重试或恢复时，它会根据已保存的结果跳过完成的步骤。循环、条件分支和嵌套 Workflow 等 Mastra 控制流原语也映射到同一套 Inngest 函数与步骤模型，同时保留组合、分支和暂停能力。

Inngest 的发布订阅系统和控制台支持实时监控、暂停与恢复，以及步骤级可观测性。每个步骤执行时，其状态和输出都会通过 Mastra 存储进行跟踪，并可在需要时恢复。

## 配置 {/* #setup */}

安装所需依赖：

```bash npm2yarn
npm install @mastra/inngest@latest inngest
```

:::note
需要 `inngest@^4` 和 `v1.18.0` 或更高版本的 Inngest Dev Server。v4 SDK 已内置实时功能，因此不再使用 `@inngest/realtime` 和 `realtimeMiddleware`。
:::

## 构建 Inngest Workflow {/* #building-an-inngest-workflow */}

本指南通过一个将数值逐次递增至 10 的计数器应用，介绍如何使用 Inngest 和 Mastra 创建 Workflow。

### 初始化 Inngest {/* #inngest-initialization */}

初始化 Inngest 集成，以获取与 Mastra 兼容的 Workflow 辅助函数。`createWorkflow()` 和 `createStep()` 用于创建同时兼容 Mastra 和 Inngest 的 Workflow 与步骤对象。

开发环境：

```ts title="src/mastra/inngest/index.ts"
import { Inngest } from 'inngest'

export const inngest = new Inngest({
  id: 'mastra',
  baseUrl: 'http://localhost:8288',
  isDev: true,
})
```

生产环境：

```ts title="src/mastra/inngest/index.ts"
import { Inngest } from 'inngest'

export const inngest = new Inngest({
  id: 'mastra',
})
```

#### 使用 `INNGEST_DEV` 选择开发模式或云端模式 {/* #selecting-dev-or-cloud-mode-with-inngest_dev */}

Inngest SDK 可在开发模式或云端模式下运行。从 v4 起，SDK 默认使用云端模式，并要求提供 `INNGEST_EVENT_KEY` 和 `INNGEST_SIGNING_KEY`。上面的示例通过代码中的 `isDev: true` 设置模式。你也可以设置 [`INNGEST_DEV` 环境变量](https://www.inngest.com/docs/sdk/environment-variables#inngest-dev)，让同一份客户端代码适用于不同环境：

- `INNGEST_DEV=1`：强制使用开发模式。SDK 连接本地 Inngest Dev Server，并关闭签名验证。
- `INNGEST_DEV=0`：强制使用云端模式。SDK 连接 Inngest Cloud，并要求提供事件密钥和签名密钥。
- `INNGEST_DEV=<url>`：强制使用开发模式，并让 SDK 连接 `<url>` 指定的 Dev Server，例如 `http://localhost:8288`。
- 未设置：默认使用云端模式。

设置 `INNGEST_DEV` 后，可以从客户端配置中移除 `isDev` 和 `baseUrl`：

```ts title="src/mastra/inngest/index.ts"
import { Inngest } from 'inngest'

export const inngest = new Inngest({
  id: 'mastra',
})
```

:::warning
不要在生产环境中设置 `INNGEST_DEV`。它会关闭签名验证，而安全接收 Inngest Cloud 事件必须进行签名验证。
:::

如果同时设置了两者，`new Inngest()` 的 `isDev` 选项优先于 `INNGEST_DEV`。

### 创建步骤 {/* #creating-steps */}

定义组成 Workflow 的各个步骤：

```ts title="src/mastra/workflows/index.ts"
import { z } from 'zod'
import { inngest } from '../inngest'
import { init } from '@mastra/inngest'

// Initialize Inngest with Mastra, pointing to your local Inngest server
const { createWorkflow, createStep } = init(inngest)

// Step: Increment the counter value
const incrementStep = createStep({
  id: 'increment',
  inputSchema: z.object({
    value: z.number(),
  }),
  outputSchema: z.object({
    value: z.number(),
  }),
  execute: async ({ inputData }) => {
    return { value: inputData.value + 1 }
  },
})
```

### 创建 Workflow {/* #creating-the-workflow */}

使用 `dountil` 循环模式将步骤组合成 Workflow。`createWorkflow()` 会在 Inngest 服务器上创建一个可调用的函数。

```ts title="src/mastra/workflows/index.ts"
// workflow that is registered as a function on inngest server
const workflow = createWorkflow({
  id: 'increment-workflow',
  inputSchema: z.object({
    value: z.number(),
  }),
  outputSchema: z.object({
    value: z.number(),
  }),
}).then(incrementStep)

workflow.commit()

export { workflow as incrementWorkflow }
```

### 配置 Mastra 实例 {/* #configuring-the-mastra-instance */}

向 Mastra 注册 Workflow，并配置 Inngest API 端点：

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { serve } from '@mastra/inngest'
import { incrementWorkflow } from './workflows'
import { inngest } from './inngest'
import { PinoLogger } from '@mastra/loggers'

export const mastra = new Mastra({
  workflows: { incrementWorkflow },
  server: {
    host: '0.0.0.0',
    apiRoutes: [
      {
        path: '/inngest/api',
        method: 'ALL',
        createHandler: async ({ mastra }) => {
          return serve({ mastra, inngest })
        },
      },
    ],
  },
  logger: new PinoLogger({ name: 'Mastra', level: 'info' }),
})
```

:::note
这里的路径是 `/inngest/api`，不是 `/api/inngest`。Mastra 将 `/api` 前缀保留给内置路由（Agent、Workflow、memory）。如果自定义 `apiRoutes` 路径以服务器的 `apiPrefix`（默认为 `/api`）开头，启动时会报错。背景信息参见 [#15743](https://github.com/mastra-ai/mastra/pull/15743)；如果需要保留 `/api/inngest`，请参阅[使用自定义 `apiPrefix`](#using-a-custom-apiprefix)。
:::

## 运行 Workflow {/* #running-workflows */}

### 在本地运行 {/* #running-locally */}

1. 运行 `npx mastra dev`，在本地的 4111 端口启动 Mastra 服务器

2. 启动 Inngest Dev Server。在新的终端窗口中运行：

   ```bash
   npx inngest-cli@latest dev -u http://localhost:4111/inngest/api
   ```

   :::note
   `-u` 后面的 URL 告诉 Inngest Dev Server 在哪里访问 Mastra 的 `/inngest/api` 端点
   :::

3. 在 [http://localhost:8288](http://localhost:8288) 打开 Inngest 控制台，进入侧边栏的 **Apps**，确认 Mastra Workflow 已注册

4. 在 **Functions** 中打开你的 Workflow，选择 **Invoke**，并输入以下内容：

   ```json
   {
     "data": {
       "inputData": {
         "value": 5
       }
     }
   }
   ```

5. 在 **Runs** 标签页监控 Workflow 的执行，查看各步骤的进度

### 在生产环境中运行 {/* #running-in-production */}

开始前，请确保已具备：

- Vercel 账号，并已安装 Vercel CLI（`npm i -g vercel`）
- Inngest 账号
- Vercel 令牌

1. 在环境中设置 Vercel 令牌：

   ```bash title=".env"
   export VERCEL_TOKEN=your_vercel_token
   ```

2. 在 Mastra 实例中添加 `VercelDeployer`

   ```ts title="src/mastra/index.ts"
   import { VercelDeployer } from '@mastra/deployer-vercel'
   import { Mastra } from '@mastra/core'

   export const mastra = new Mastra({
     deployer: new VercelDeployer({
       teamSlug: 'your_team_slug',
       projectName: 'your_project_name',
       // you can get your vercel token from the vercel dashboard by clicking on the user icon in the top right corner
       // and then clicking on "Account Settings" and then clicking on "Tokens" on the left sidebar.
       token: process.env.VERCEL_TOKEN,
     }),
   })
   ```

3. 构建 Mastra 实例

   ```bash
   npx mastra build
   ```

4. 部署到 Vercel

   ```bash
   cd .mastra/output
   vercel login
   vercel --prod
   ```

5. 在 [Inngest 控制台](https://app.inngest.com/env/production/apps)选择 **Sync new app with Vercel**，按照提示同步应用

   :::warning
   Inngest 的自动发现约定使用 `/api/inngest`。本指南使用 `/inngest/api`，因此请将 Inngest 应用的 **URL** 字段设为部署后的源站地址加上 `/inngest/api`，例如 `https://your-app.vercel.app/inngest/api`。如果保留默认值，Inngest 控制台将无法发现应用中的函数。
   :::

6. 在 **Functions** 中打开 `workflow.increment-workflow`，选择 **All actions** > **Invoke**，并输入以下内容：

   ```json
   {
     "data": {
       "inputData": {
         "value": 5
       }
     }
   }
   ```

7. 在 **Runs** 标签页监控执行，查看各步骤的进度

## 添加自定义 Inngest 函数 {/* #adding-custom-inngest-functions */}

通过 `serve()` 的可选 `functions` 参数，你可以在提供 Mastra Workflow 的同时提供其他 Inngest 函数。

### 创建自定义函数 {/* #creating-custom-functions */}

首先，创建自定义 Ingest 函数：

```ts title="src/inngest/custom-functions.ts"
import { inngest } from '../inngest'

// Define custom Inngest functions
export const customEmailFunction = inngest.createFunction(
  { id: 'send-welcome-email' },
  { event: 'user/registered' },
  async ({ event }) => {
    // Custom email logic here
    console.log(`Sending welcome email to ${event.data.email}`)
    return { status: 'email_sent' }
  },
)

export const customWebhookFunction = inngest.createFunction(
  { id: 'process-webhook' },
  { event: 'webhook/received' },
  async ({ event }) => {
    // Custom webhook processing
    console.log(`Processing webhook: ${event.data.type}`)
    return { processed: true }
  },
)
```

### 同时提供自定义函数和 Workflow {/* #serving-custom-functions-with-workflows */}

更新 Mastra 配置，导入并加入自定义函数。高亮行是新增内容：

```ts title="src/mastra/index.ts" {5-8,23}
import { Mastra } from '@mastra/core'
import { serve } from '@mastra/inngest'
import { incrementWorkflow } from './workflows'
import { inngest } from './inngest'
import { customEmailFunction, customWebhookFunction } from './inngest/custom-functions'
import { PinoLogger } from '@mastra/loggers'

export const mastra = new Mastra({
  workflows: { incrementWorkflow },
  server: {
    host: '0.0.0.0',
    apiRoutes: [
      {
        path: '/inngest/api',
        method: 'ALL',
        createHandler: async ({ mastra }) => {
          return serve({
            mastra,
            inngest,
            functions: [customEmailFunction, customWebhookFunction],
          })
        },
      },
    ],
  },
  logger: new PinoLogger({ name: 'Mastra', level: 'info' }),
})
```

### 函数注册 {/* #function-registration */}

加入自定义函数后：

1. Mastra Workflow 会自动转换为 Inngest 函数，ID 形如 `workflow.${workflowId}`
2. 自定义函数保留指定的 ID，例如 `send-welcome-email`、`process-webhook`
3. 所有函数都通过同一个 `/inngest/api` 端点提供

这样就能将 Mastra 的 Workflow 编排与现有 Inngest 函数结合使用。

## 与其他框架一起使用 {/* #using-with-other-frameworks */}

默认的 `serve` 函数内部使用 Hono。如果使用 Express、Fastify 或 Koa 等其他 Web 框架，请将 `createServe` 工厂函数与相应的 Inngest 适配器配合使用。

### Express {/* #express */}

```ts title="src/server.ts"
import express from 'express'
import { createServe } from '@mastra/inngest'
import { serve as expressAdapter } from 'inngest/express'
import { mastra, inngest } from './mastra'

const app = express()

// Body parsing middleware required for Inngest
app.use(express.json())

const handler = createServe(expressAdapter)({ mastra, inngest })
app.use('/inngest/api', handler)

app.listen(3000)
```

### Fastify {/* #fastify */}

```ts title="src/server.ts"
import Fastify from 'fastify'
import { createServe } from '@mastra/inngest'
import { serve as fastifyAdapter } from 'inngest/fastify'
import { mastra, inngest } from './mastra'

const fastify = Fastify()

// JSON parsing is handled by Fastify's default content-type parser
const handler = createServe(fastifyAdapter)({ mastra, inngest })

fastify.route({
  method: ['GET', 'POST', 'PUT'],
  url: '/inngest/api',
  handler,
})

fastify.listen({ port: 3000 })
```

### Koa {/* #koa */}

```ts title="src/server.ts"
import Koa from 'koa'
import Router from '@koa/router'
import bodyParser from 'koa-bodyparser'
import { createServe } from '@mastra/inngest'
import { serve as koaAdapter } from 'inngest/koa'
import { mastra, inngest } from './mastra'

const app = new Koa()
const router = new Router()

// Body parsing middleware required for Inngest
app.use(bodyParser())

const handler = createServe(koaAdapter)({ mastra, inngest })
router.all('/inngest/api', handler)

app.use(router.routes())
app.use(router.allowedMethods())

app.listen(3000)
```

### Next.js {/* #nextjs */}

```ts title="app/inngest/api/route.ts"
import { createServe } from '@mastra/inngest'
import { serve as nextAdapter } from 'inngest/next'
import { mastra, inngest } from '@/mastra'

const handler = createServe(nextAdapter)({ mastra, inngest })

export { handler as GET, handler as POST, handler as PUT }
```

### 可用适配器 {/* #available-adapters */}

`createServe` 可与任何 Inngest 适配器配合使用。完整列表（包括 AWS Lambda、Cloudflare Workers 等）请参阅 [Inngest serve 文档](https://www.inngest.com/docs/reference/serve)。

## 作为 Connect worker 运行 {/* #running-as-a-connect-worker */}

`serve()` 提供供 Inngest 调用的 HTTP 端点。另一种方式是使用 `connect()`，让 worker 主动与 Inngest 建立长期连接，这样 worker 就无需公开可访问的端点。此方式适用于 Kubernetes、Docker、ECS、Fly.io 或 Render 等运行环境中的常驻 worker 进程。

:::note
Inngest Connect 目前处于公开测试阶段。Vercel 和 AWS Lambda 等无服务器运行环境不支持 Connect worker。
:::

### 何时使用 `connect()` 而不是 `serve()` {/* #when-to-use-connect-instead-of-serve */}

- worker 进程运行在只允许出站连接的私有网络中。
- 你希望将耗费资源的 Workflow 执行与处理用户 HTTP 请求的进程分开。
- 你希望独立于 Mastra HTTP 服务器扩缩容 worker，并分别限制每个 worker 的并发量。

`serve()` 和 `connect()` 可使用相同的 Mastra Workflow 定义。对于普通 Workflow、嵌套 Workflow、cron Workflow 和额外的 Inngest 函数，两者的收集行为相同。

### 环境要求 {/* #requirements */}

- `inngest@^4`
- Node.js `22.13.0` 或更高版本
- 用于运行 worker 的常驻进程

### 配置 {/* #setup-1 */}

将 Mastra 服务器和 Connect worker 作为两个进程运行。采用此配置时，Mastra 服务器无需公开 `/inngest/api`：

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { incrementWorkflow } from './workflows'
import { PinoLogger } from '@mastra/loggers'

export const mastra = new Mastra({
  workflows: { incrementWorkflow },
  logger: new PinoLogger({ name: 'Mastra', level: 'info' }),
})
```

```ts title="src/worker.ts"
import { connect } from '@mastra/inngest/connect'
import { mastra } from './mastra'
import { inngest } from './mastra/inngest'

await connect({
  mastra,
  inngest,
  instanceId: process.env.INNGEST_CONNECT_INSTANCE_ID,
  maxWorkerConcurrency: Number(process.env.INNGEST_CONNECT_MAX_WORKER_CONCURRENCY ?? 10),
})
```

本地开发时，运行 `INNGEST_DEV=1 node --import tsx src/worker.ts` 启动 worker。Inngest Dev Server 会通过 worker 的出站连接发现它，因此不需要 `-u` 参数。

在生产环境中设置 `INNGEST_EVENT_KEY` 和 `INNGEST_SIGNING_KEY`。将 `Inngest` 客户端的 `appVersion` 设为提交 SHA 或镜像标签等部署标识，以便 Inngest 管理滚动部署。

将现有生产应用从 `serve()` 迁移到 `connect()` 时，应先使用单独的 Inngest 应用测试 worker，再切换流量。

### 选项 {/* #options */}

`connect()` 接受与 Inngest [`connect`](https://www.inngest.com/docs/setup/connect) 相同的选项，另加 Mastra 专用字段。常用选项如下：

- `mastra`：需要提供其 Workflow 的 Mastra 实例。
- `inngest`：Inngest 客户端。使用与传给 `serve()` 时相同的客户端。
- `functions`：可选的额外 Inngest 函数数组，与 Mastra Workflow 一同注册。
- `instanceId`：worker 的稳定标识符，显示在 Inngest 控制台中。默认为机器主机名。
- `maxWorkerConcurrency`：worker 同时运行的最大步骤数。默认不设上限。
- `registerOptions`：应用注册时转发给 Inngest 的选项，例如 `signingKey`。如果同一字段同时在此处和顶层设置，以 `registerOptions` 为准；这与 `serve()` 的行为一致。

`connect()` 返回 Inngest 的 `WorkerConnection`。Inngest SDK 默认处理 `SIGINT` 和 `SIGTERM`。只有 worker 需要自定义关闭流程时，才应保存返回的连接并调用 `.close()`。

如果 Mastra 实例中没有 `InngestWorkflow`，且未提供额外的 `functions`，`connect()` 会记录警告，因为 worker 否则会保持连接却无事可做。请在 Mastra 中至少注册一个 Workflow，或传入 `functions: [...]`。

## 使用自定义 `apiPrefix` {/* #using-a-custom-apiprefix */}

如果需要保留 `/api/inngest`（例如为了符合 Inngest 的自动发现约定，而不修改控制台中的 URL），请设置 `server.apiPrefix`，将 Mastra 的内置路由移至其他前缀：

```ts title="src/mastra/index.ts" {7,10}
import { Mastra } from '@mastra/core'
import { serve } from '@mastra/inngest'
import { inngest } from './inngest'

export const mastra = new Mastra({
  server: {
    apiPrefix: '/_mastra',
    apiRoutes: [
      {
        path: '/api/inngest',
        method: 'ALL',
        createHandler: async ({ mastra }) => serve({ mastra, inngest }),
      },
    ],
  },
})
```

Mastra 的内置路由此时位于 `/_mastra/agents`、`/_mastra/workflows` 等路径下，`/api/inngest` 因而可供自定义路由使用。

:::warning
默认身份验证配置会保护 `/api/*`，并将 `/api`、`/api/auth/*` 视为公开路径。修改 `apiPrefix` 后，这些默认规则不再匹配，内置路由也就不在受保护的路径范围内。请更新 `server.auth.protected` 和 `server.auth.public`，使其指向新前缀；同时更新访问 `/api/*` 的客户端代码，包括 [`MastraClient`](/docs/server/mastra-client) 的 `apiPrefix`。
:::

## 流量控制 {/* #flow-control */}

Inngest Workflow 支持并发限制、速率限制、节流、去抖和优先级排队等流量控制功能。这些选项在 `createWorkflow()` 调用中配置，有助于管理大规模 Workflow 执行。

### 并发限制 {/* #concurrency */}

控制可同时运行的 Workflow 实例数：

```ts
const workflow = createWorkflow({
  id: 'user-processing-workflow',
  inputSchema: z.object({ userId: z.string() }),
  outputSchema: z.object({ result: z.string() }),
  steps: [processUserStep],
  // Limit to 10 concurrent executions, scoped by user ID
  concurrency: {
    limit: 10,
    key: 'event.data.userId',
  },
})
```

### 速率限制 {/* #rate-limiting */}

限制指定时间段内的 Workflow 执行次数：

```ts
const workflow = createWorkflow({
  id: 'api-sync-workflow',
  inputSchema: z.object({ endpoint: z.string() }),
  outputSchema: z.object({ status: z.string() }),
  steps: [apiSyncStep],
  // Maximum 1000 executions per hour
  rateLimit: {
    period: '1h',
    limit: 1000,
  },
})
```

### 节流 {/* #throttling */}

确保两次 Workflow 执行之间至少间隔指定时长：

```ts
const workflow = createWorkflow({
  id: 'email-notification-workflow',
  inputSchema: z.object({ organizationId: z.string(), message: z.string() }),
  outputSchema: z.object({ sent: z.boolean() }),
  steps: [sendEmailStep],
  // Only one execution per 10 seconds per organization
  throttle: {
    period: '10s',
    limit: 1,
    key: 'event.data.organizationId',
  },
})
```

### 去抖 {/* #debouncing */}

延迟执行，直到指定时间窗口内不再有新事件到达：

```ts
const workflow = createWorkflow({
  id: 'search-index-workflow',
  inputSchema: z.object({ documentId: z.string() }),
  outputSchema: z.object({ indexed: z.boolean() }),
  steps: [indexDocumentStep],
  // Wait 5 seconds of no updates before indexing
  debounce: {
    period: '5s',
    key: 'event.data.documentId',
  },
})
```

### 优先级 {/* #priority */}

设置 Workflow 的执行优先级：

```ts
const workflow = createWorkflow({
  id: 'order-processing-workflow',
  inputSchema: z.object({
    orderId: z.string(),
    priority: z.number().optional(),
  }),
  outputSchema: z.object({ processed: z.boolean() }),
  steps: [processOrderStep],
  // Higher priority orders execute first
  priority: {
    run: 'event.data.priority ?? 50',
  },
})
```

### 重试 {/* #retries */}

设置 `retries`，可使一次运行在请求应用失败后继续恢复，例如进程重启、重新部署或内存不足导致崩溃时。Inngest 会再次调用该函数，跳过已完成的步骤，并从中断的步骤继续：

```ts
const workflow = createWorkflow({
  id: 'long-running-workflow',
  inputSchema: z.object({ jobId: z.string() }),
  outputSchema: z.object({ done: z.boolean() }),
  steps: [longRunningStep],
  // Re-invoke up to 3 times after a failed request
  retries: 3,
})
```

`retries` 默认为 `0`。步骤代码抛出的错误通过 `retryConfig` 或步骤自身的 `retries` 选项按步骤重试，而不是在函数级别重试。`createInngestAgent()` 也接受 `retries` 选项，并将其应用于持久化 Agent 创建的每个 Inngest 函数。所有持久化 Agent 共用这些函数，因此首先向 Mastra 注册的 Agent 所设置的 `retries` 值会作用于所有持久化 Agent。请为每个 Agent 设置相同的值，以免产生混淆。

嵌套 Workflow 作为独立的 Inngest 函数运行，并使用自己的 `retries` 设置。它不会继承父 Workflow 的值，因此需要从请求失败中恢复的嵌套 Workflow 都应分别设置 `retries`。

### 组合流量控制选项 {/* #combining-flow-control-options */}

一个 Workflow 可以组合使用多个流量控制选项：

```ts
const workflow = createWorkflow({
  id: 'comprehensive-workflow',
  inputSchema: z.object({
    userId: z.string(),
    organizationId: z.string(),
    priority: z.number().optional(),
  }),
  outputSchema: z.object({ result: z.string() }),
  steps: [comprehensiveStep],
  concurrency: {
    limit: 5,
    key: 'event.data.userId',
  },
  rateLimit: {
    period: '1m',
    limit: 100,
  },
  throttle: {
    period: '10s',
    limit: 1,
    key: 'event.data.organizationId',
  },
  priority: {
    run: 'event.data.priority ?? 0',
  },
})
```

所有流量控制选项均为可选项。未设置时，Workflow 按 Inngest 的默认行为运行。详情请参阅 [Inngest 流量控制文档](https://www.inngest.com/docs/guides/flow-control)。

## Cron 定时调度 {/* #cron-scheduling */}

使用 cron 表达式按计划触发 Inngest Workflow。常见用途包括生成每日报告、每小时同步数据以及执行维护任务。

### 基本 cron 调度 {/* #basic-cron-scheduling */}

为 Workflow 添加 `cron` 属性，即可配置定时运行：

```ts
const workflow = createWorkflow({
  id: 'daily-report-workflow',
  inputSchema: z.object({ reportType: z.string() }),
  outputSchema: z.object({ generated: z.boolean() }),
  steps: [generateReportStep],
  // Run daily at midnight
  cron: '0 0 * * *',
})
```

### Cron 表达式格式 {/* #cron-schedule-format */}

`cron` 属性接受标准 cron 表达式，格式为：`minute hour day month dayOfWeek`

- **分钟**：0–59
- **小时**：0–23
- **日期**：1–31
- **月份**：1–12 或 JAN–DEC
- **星期**：0–6（星期日为 0）或 SUN–SAT

常见的 cron 表达式：

```ts
// Every 15 minutes
cron: '*/15 * * * *'

// Every hour at minute 0
cron: '0 * * * *'

// Every 6 hours
cron: '0 */6 * * *'

// Daily at midnight
cron: '0 0 * * *'

// Daily at 9 AM
cron: '0 9 * * *'

// Every weekday at 9 AM
cron: '0 9 * * 1-5'

// First day of every month at midnight
cron: '0 0 1 * *'

// Every Monday at 8 AM
cron: '0 8 * * 1'
```

### 为定时运行提供输入数据 {/* #providing-input-data-for-scheduled-runs */}

你可以提供静态输入数据，供每次定时执行使用：

```ts
const workflow = createWorkflow({
  id: 'scheduled-data-sync',
  inputSchema: z.object({
    source: z.string(),
    destination: z.string(),
  }),
  outputSchema: z.object({ synced: z.boolean() }),
  steps: [syncDataStep],
  cron: '0 */6 * * *', // Every 6 hours
  // Input data provided to each scheduled run
  inputData: {
    source: 'production-db',
    destination: 'analytics-warehouse',
  },
})
```

### 为定时运行提供初始状态 {/* #providing-initial-state-for-scheduled-runs */}

你还可以为定时运行的 Workflow 设置初始状态：

```ts
const workflow = createWorkflow({
  id: 'scheduled-aggregation',
  inputSchema: z.object({ date: z.string() }),
  outputSchema: z.object({ aggregated: z.boolean() }),
  stateSchema: z.object({
    processedCount: z.number(),
    lastProcessedDate: z.string(),
  }),
  steps: [aggregateDataStep],
  cron: '0 0 * * *', // Daily at midnight
  inputData: {
    date: new Date().toISOString().split('T')[0], // Today's date
  },
  initialState: {
    processedCount: 0,
    lastProcessedDate: '',
  },
})
```

### 将 cron 与流量控制结合使用 {/* #combining-cron-with-flow-control */}

Cron 调度可与流量控制选项结合使用：

```ts
const workflow = createWorkflow({
  id: 'scheduled-api-sync',
  inputSchema: z.object({ endpoint: z.string() }),
  outputSchema: z.object({ synced: z.boolean() }),
  steps: [syncApiStep],
  cron: '*/30 * * * *', // Every 30 minutes
  inputData: {
    endpoint: 'https://api.example.com/data',
  },
  // Limit concurrent executions even for scheduled runs
  concurrency: {
    limit: 5,
  },
  // Rate limit scheduled executions
  rateLimit: {
    period: '1h',
    limit: 100,
  },
})
```

### cron 函数的工作方式 {/* #how-cron-functions-work */}

为 Workflow 配置 `cron` 属性后：

1. 系统会自动创建一个 ID 为 `workflow.${workflowId}.cron` 的独立 Inngest 函数
2. 该函数会注册到 Inngest，并按指定的时间安排触发
3. 每次定时执行都会使用所提供的 `inputData` 和 `initialState` 创建一次新的 Workflow 运行
4. 调用 `serve()` 时，cron 函数与主 Workflow 函数会一同提供服务

你可以在 Inngest 控制台的 **Functions** 和 **Runs** 中监控定时执行。cron 函数会作为独立函数显示在主 Workflow 函数旁。

有关 cron 调度的更多信息，请参阅 [Inngest cron 文档](https://www.inngest.com/docs/guides/scheduled-functions)。
