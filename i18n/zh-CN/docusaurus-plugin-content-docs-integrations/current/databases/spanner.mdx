# Google Cloud Spanner

Google Cloud Spanner 存储适配器为 Mastra 提供可横向扩展容量的强一致性存储后端，使用 Cloud Spanner 的 GoogleSQL 方言。

## 安装 {/* #installation */}

```bash npm2yarn
npm install @mastra/spanner@latest
```

## 使用方法 {/* #usage */}

```typescript
import { SpannerStore } from '@mastra/spanner'

const storage = new SpannerStore({
  id: 'spanner-storage',
  projectId: process.env.SPANNER_PROJECT_ID!,
  instanceId: process.env.SPANNER_INSTANCE_ID!,
  databaseId: process.env.SPANNER_DATABASE_ID!,
})
```

实例和数据库必须事先创建。适配器会在首次使用时创建所需的表，因此 Spanner 客户端使用的凭据必须具有修改数据库架构的权限。也可以在部署时使用权限更高的凭据调用一次 `storage.init()`。

## 构造函数示例 {/* #constructor-examples */}

可以通过以下几种方式创建 `SpannerStore` 实例：

```typescript
import { Spanner } from '@google-cloud/spanner'
import { SpannerStore } from '@mastra/spanner'

// Using projectId / instanceId / databaseId
const store1 = new SpannerStore({
  id: 'spanner-storage-1',
  projectId: 'my-gcp-project',
  instanceId: 'my-instance',
  databaseId: 'mastra',
})

// Reusing an existing Spanner Database handle
const spanner = new Spanner({ projectId: 'my-gcp-project' })
const database = spanner.instance('my-instance').database('mastra')

const store2 = new SpannerStore({
  id: 'spanner-storage-2',
  database,
})

// Using the local Spanner emulator (set the SPANNER_EMULATOR_HOST env var)
process.env.SPANNER_EMULATOR_HOST = 'localhost:9010'
const store3 = new SpannerStore({
  id: 'spanner-storage-emulator',
  projectId: 'test-project',
  instanceId: 'test-instance',
  databaseId: 'test-db',
  spannerOptions: { servicePath: 'localhost', port: 9010, sslCreds: undefined },
})
```

## 附加说明 {/* #additional-notes */}

### 数据库架构管理 {/* #schema-management */}

存储适配器使用 GoogleSQL 方言创建以下表：

* `mastra_workflow_snapshot`：Workflow 状态和执行数据
* `mastra_threads`：会话线程
* `mastra_messages`：单条消息
* `mastra_resources`：资源工作记忆
* `mastra_scorers`：评估分数
* `mastra_background_tasks`：后台 Tool 执行状态
* `mastra_agents`：Agent 的精简记录（ID、状态和当前生效版本）
* `mastra_agent_versions`：按版本保存的 Agent 配置快照
* `mastra_mcp_clients` / `mastra_mcp_client_versions`：MCP 客户端配置及其版本历史
* `mastra_mcp_servers` / `mastra_mcp_server_versions`：MCP 服务端配置及其版本历史
* `mastra_skills` / `mastra_skill_versions`：Skill 记录和各版本的快照（指令、参考资料、脚本、资源和内容树）
* `mastra_skill_blobs`：以 SHA-256 哈希为键的内容寻址 Blob 存储，用于保存各版本的 Skill 内容
* `mastra_prompt_blocks` / `mastra_prompt_block_versions`：提示词块记录和各版本的内容快照（模板内容、规则和请求上下文结构）
* `mastra_scorer_definitions` / `mastra_scorer_definition_versions`：评分器定义记录和各版本的配置快照（评判指令、模型、分数范围、预设配置和默认采样设置）
* `mastra_schedules` / `mastra_schedule_triggers`：由 cron 驱动的 Workflow 调度计划和触发历史，供 Mastra 内置的 `WorkflowScheduler` 使用
* `mastra_workspaces` / `mastra_workspace_versions`：Workspace 记录和各版本的配置快照（文件系统、Sandbox、挂载、搜索、Skill 和 Tool）
* `mastra_datasets` / `mastra_dataset_items` / `mastra_dataset_versions`：评估数据集、按 SCD-2 保留版本的条目和版本快照
* `mastra_experiments` / `mastra_experiment_results`：实验运行记录和每个条目的结果
* `mastra_favorites`：各用户收藏的 Agent 和 Skill。冗余字段 `favoriteCount` 维护在父记录上
* `mastra_channel_installations` / `mastra_channel_config`：多平台渠道安装记录和各平台的配置
* `mastra_ai_spans`：用于可观测性的 AI 追踪 Span，按 Trace 和 Span 分别记录，为 Studio 的追踪界面提供数据

表中使用 `STRING(MAX)` 存储文本和 JSON 载荷，还使用 `INT64`、`FLOAT64`、`BOOL` 和 `TIMESTAMP` 类型。

以下表包含 Spanner 特有的 `STORED` 生成列。适配器根据 JSON 载荷填充这些列，使常用筛选条件可以利用普通二级索引，避免通过 `JSON_VALUE` 扫描：

* `mastra_workflow_snapshot.snapshotStatus`：从 `snapshot` 提取 `$.status`，供 `listWorkflowRuns({ status })` 使用。
* `mastra_schedules.target_workflow_id`：从 `target` 提取 `$.workflowId`，供 `listSchedules({ workflowId })` 使用。

适配器在 `init()` 期间通过 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 添加这两列。设为 `initMode: 'validate'` 时，架构由外部流程管理，适配器跳过添加步骤。如果相应的列不存在，适配器会在运行时改用 `JSON_VALUE` 筛选。

适配器不创建或使用独立的 schema 命名空间。如需隔离，请使用专用数据库。

### 初始化 {/* #initialization */}

将存储实例传给 `Mastra` 类后，Mastra 会在执行任何存储操作前自动调用 `init()`：

```typescript
import { Mastra } from '@mastra/core'
import { SpannerStore } from '@mastra/spanner'

const storage = new SpannerStore({
  id: 'spanner-storage',
  projectId: process.env.SPANNER_PROJECT_ID!,
  instanceId: process.env.SPANNER_INSTANCE_ID!,
  databaseId: process.env.SPANNER_DATABASE_ID!,
})

const mastra = new Mastra({
  storage, // init() is called automatically
})
```

如果直接使用存储实例，请在首次操作前调用一次 `init()`。Spanner 不允许并发修改数据库架构，因此 `SpannerStore.init()` 会依次初始化各个存储域。

```typescript
const storage = new SpannerStore({
  id: 'spanner-storage',
  projectId: process.env.SPANNER_PROJECT_ID!,
  instanceId: process.env.SPANNER_INSTANCE_ID!,
  databaseId: process.env.SPANNER_DATABASE_ID!,
})

await storage.init()
const memory = await storage.getStore('memory')
const thread = await memory?.getThreadById({ threadId: '...' })
```

:::warning
如果 `disableInit` 为 true 且未调用 `init()`，所需的表将不存在，存储操作也会失败。
:::

### GoogleSQL 特有行为 {/* #googlesql-specifics */}

此适配器在以下方面与其他关系型数据库适配器不同：

* 插入或更新使用 `INSERT OR UPDATE`。Spanner 不支持在此类操作中使用 `RETURNING` 子句，因此调用方需要另行读取才能获得写入后的状态。
* Spanner 不支持 `TRUNCATE`。`dangerouslyClearAll()` 会执行 `DELETE WHERE TRUE`。
* 标识符用反引号括起来。
* 通过 `database.updateSchema(...)` 执行 DDL。这是一个异步的长时间运行操作。
* Spanner 不支持 `NULLS FIRST/LAST`。适配器使用 `IS NULL` 作为排序键来模拟 NULL 值的排序行为。
* Spanner 不原生支持 JSON 包含匹配。适配器将 `listTraces` 的 `metadata` 和 `scope` 筛选条件转换为逐键执行的 `JSON_VALUE(...) = @v` 等值判断，并将 `tags` 筛选条件转换为对 `JSON_QUERY_ARRAY(...)` 结果执行的 `EXISTS` 检查。Postgres 的 `@>` 包含运算符可以在一次索引扫描中匹配嵌套结构。Spanner 中的这种转换仍支持大多数单次查询，但无法表达深层嵌套的结构匹配。

### 直接访问数据库 {/* #direct-database-access */}

`SpannerStore` 提供对底层 Spanner 客户端对象的访问：

```typescript
store.database // @google-cloud/spanner Database
store.instance // @google-cloud/spanner Instance (when created internally)
store.spanner // @google-cloud/spanner Spanner client (when created internally)
```

这些对象适用于自定义事务或检查数据库架构等高级场景。直接使用数据库对象会绕过适配器的验证和 JSON 转换逻辑。

### 使用模拟器进行本地开发 {/* #local-development-with-the-emulator */}

使用 Docker 在本地运行 Cloud Spanner 模拟器：

```bash
docker run -p 9010:9010 -p 9020:9020 gcr.io/cloud-spanner-emulator/emulator
```

设置 `SPANNER_EMULATOR_HOST=localhost:9010`，并在运行应用前创建实例和数据库：

```bash
gcloud spanner instances create test-instance --config=emulator-config --nodes=1
gcloud spanner databases create test-db --instance=test-instance
```

连接时，在 Node.js 进程中设置同一个环境变量。`@google-cloud/spanner` 客户端会自动检测模拟器。
