# OpenTelemetry

Mastra 通过 OpenTelemetry (OTEL) 导出器将跟踪和日志发送到兼容平台，也可通过 Bridge 加入现有的 OTEL 跟踪上下文。

## 导出器 {/* #exporter */}

OpenTelemetry 导出器按照标准化的 [OpenTelemetry GenAI 语义约定](https://opentelemetry.io/docs/specs/semconv/gen-ai/)发送跟踪和日志，因此可广泛兼容 Datadog、New Relic、Sentry、SigNoz、MLflow、Latitude、Dash0、Traceloop、Laminar、telemetry.dev、Sazabi 等平台。

### 安装 {/* #installation */}

每个 Provider 都需要对应的协议包。请安装基础导出器，以及该 Provider 所需的协议包：

#### 对于 HTTP/Protobuf Provider（SigNoz、New Relic、Sentry、Laminar、MLflow、Latitude、telemetry.dev） {/* #for-httpprotobuf-providers-signoz-new-relic-sentry-laminar-mlflow-latitude-telemetrydev */}

```bash npm2yarn
npm install @mastra/otel-exporter@latest @opentelemetry/exporter-trace-otlp-proto
```

#### 适用于 `gRPC` Provider（Dash0、Datadog） {/* #for-grpc-providers-dash0-datadog */}

```bash npm2yarn
npm install @mastra/otel-exporter@latest @opentelemetry/exporter-trace-otlp-grpc @grpc/grpc-js
```

#### 对于 HTTP/JSON Provider（Traceloop、Sazabi） {/* #for-httpjson-providers-traceloop-sazabi */}

```bash npm2yarn
npm install @mastra/otel-exporter@latest @opentelemetry/exporter-trace-otlp-http
```

### 环境变量 {/* #environment-variables */}

所有 Provider 都支持通过环境变量进行零配置设置。设置相应变量后，导出器会自动使用它们：

| Provider | 环境变量 |
| - | - |
| Dash0 | `DASH0_API_KEY`（必填）、`DASH0_ENDPOINT`（必填）、`DASH0_DATASET`（可选） |
| SigNoz | `SIGNOZ_API_KEY`（必填）、`SIGNOZ_REGION`（可选）、`SIGNOZ_ENDPOINT`（可选） |
| New Relic | `NEW_RELIC_LICENSE_KEY`（必填）、`NEW_RELIC_ENDPOINT`（可选） |
| Traceloop | `TRACELOOP_API_KEY`（必填）、`TRACELOOP_DESTINATION_ID`、`TRACELOOP_ENDPOINT`（可选） |
| Laminar | `LMNR_PROJECT_API_KEY`（必填）、`LAMINAR_ENDPOINT`（可选） |

### Provider 配置 {/* #provider-configurations */}

#### Sentry {/* #sentry */}

[Sentry](https://sentry.io/) 通过 OTLP 端点接收 OpenTelemetry 跟踪和日志。在 Sentry 中打开 [**Project Settings** > **Client Keys (DSN)**](https://sentry.io/settings/projects/)，复制 OTLP 跟踪端点和身份验证标头，并将两者添加到环境变量中：

```bash title=".env"
SENTRY_OTLP_ENDPOINT=https://o000000.ingest.sentry.io/api/0000000/integration/otlp/v1/traces
SENTRY_OTLP_AUTH_HEADER="sentry sentry_key=..."
```

使用采用 HTTP/Protobuf 的 `custom` Provider：

```typescript title="src/mastra/index.ts"
new OtelExporter({
  provider: {
    custom: {
      endpoint: process.env.SENTRY_OTLP_ENDPOINT!,
      protocol: 'http/protobuf',
      headers: {
        'x-sentry-auth': process.env.SENTRY_OTLP_AUTH_HEADER!,
      },
    },
  },
})
```

有关端点设置、支持的信号及当前的数据接收限制，请参阅 [Sentry 的 OTLP 文档](https://docs.sentry.io/concepts/otlp/)。

根据你的部署方式选择导出器：

- `OtelExporter`：通过 OTLP 发送不依赖特定厂商的跟踪和日志。适用于已有 OpenTelemetry 管道，或需要在不同后端之间迁移的情况。
- [`SentryExporter`](/integrations/observability/sentry)：使用 Sentry SDK 将 Mastra span 类型映射到 Sentry 操作，添加 AI 监控属性，并将 span 错误记录为 Sentry 问题。

#### MLflow {/* #mlflow */}

[MLflow](https://mlflow.org/docs/latest/genai/tracing/integrations/listing/mastra) 通过 `/v1/traces` OTLP 端点原生支持 Mastra 跟踪。使用采用 HTTP/Protobuf 的 `custom` Provider，并提供实验标头，以便将跟踪路由到正确的 MLflow 实验：

```typescript title="src/mastra/index.ts"
new OtelExporter({
  provider: {
    custom: {
      endpoint: `${process.env.MLFLOW_TRACKING_URI}/v1/traces`,
      protocol: 'http/protobuf',
      headers: {
        'x-mlflow-experiment-id': process.env.MLFLOW_EXPERIMENT_ID,
      },
    },
  },
})
```

#### Latitude {/* #latitude */}

[Latitude](https://latitude.so) 是一个接收 OTLP 跟踪的开源 LLM 可观测性与评估平台。使用采用 HTTP/Protobuf 的 `custom` Provider，将端点指向 Latitude 的数据接收地址，并使用 API 密钥和项目 slug 进行身份验证：

```typescript title="src/mastra/index.ts"
new OtelExporter({
  provider: {
    custom: {
      endpoint: 'https://ingest.latitude.so/v1/traces',
      protocol: 'http/protobuf',
      headers: {
        Authorization: `Bearer ${process.env.LATITUDE_API_KEY}`,
        'X-Latitude-Project': process.env.LATITUDE_PROJECT,
      },
    },
  },
})
```

你可以在 [console.latitude.so](https://console.latitude.so/login) 注册，也可以自行托管，并将端点指向自己的数据接收主机。

#### telemetry.dev {/* #telemetrydev */}

[telemetry.dev](https://telemetry.dev) 接收 OTLP/HTTP Protobuf 跟踪，并将 OpenTelemetry GenAI 语义约定规范化为模型、Provider、token、延迟和成本字段。使用 `custom` Provider，并提供项目 API 密钥：

```bash title=".env"
TELEMETRY_DEV_API_KEY=td_live_...
```

```typescript title="src/mastra/index.ts"
new OtelExporter({
  provider: {
    custom: {
      endpoint: 'https://ingest.telemetry.dev/v1/traces',
      protocol: 'http/protobuf',
      headers: {
        Authorization: `Bearer ${process.env.TELEMETRY_DEV_API_KEY}`,
      },
    },
  },
})
```

#### Sazabi {/* #sazabi */}

[Sazabi](https://sazabi.com) 是一个接收 OTLP 跟踪的 AI 原生可观测性平台。在 Sazabi 中添加 Mastra 日志源，并复制其数据接收 URL。该 URL 已包含项目密钥，因此无需身份验证标头：

```bash title=".env"
SAZABI_INTAKE_URL=https://...
```

使用采用 HTTP/JSON 的 `custom` Provider：

```typescript title="src/mastra/index.ts"
new OtelExporter({
  provider: {
    custom: {
      endpoint: process.env.SAZABI_INTAKE_URL!,
      protocol: 'http/json',
    },
  },
})
```

完整设置步骤请参阅 [Sazabi 的 Mastra 指南](https://docs.sazabi.com/catalogs/log-sources/send-to-an-endpoint/mastra)。

#### Dash0 {/* #dash0 */}

[Dash0](https://www.dash0.com/) 提供实时可观测性和自动洞察。

##### 零配置设置 {/* #zero-config-setup */}

设置环境变量，然后以空配置使用导出器：

```bash title=".env"
# Required
DASH0_API_KEY=your-api-key
DASH0_ENDPOINT=ingress.us-west-2.aws.dash0.com:4317

# Optional
DASH0_DATASET=production
```

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'
import { OtelExporter } from '@mastra/otel-exporter'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      otel: {
        serviceName: 'my-service',
        exporters: [new OtelExporter({ provider: { dash0: {} } })],
      },
    },
  }),
})
```

##### 显式配置 {/* #explicit-configuration */}

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'
import { OtelExporter } from '@mastra/otel-exporter'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      otel: {
        serviceName: 'my-service',
        exporters: [
          new OtelExporter({
            provider: {
              dash0: {
                apiKey: process.env.DASH0_API_KEY,
                endpoint: process.env.DASH0_ENDPOINT, // e.g., 'ingress.us-west-2.aws.dash0.com:4317'
                dataset: 'production', // Optional dataset name
              },
            },
            resourceAttributes: {
              // Optional OpenTelemetry Resource Attributes for the trace
              ['deployment.environment']: 'dev',
            },
          }),
        ],
      },
    },
  }),
})
```

:::note

从 Dash0 控制台获取端点。其格式应为 `ingress.{region}.aws.dash0.com:4317`。

:::

#### Datadog {/* #datadog */}

[Datadog](https://www.datadoghq.com/) APM 通过分布式跟踪监控应用性能。要通过 OTLP 向 Datadog 发送跟踪，需要运行已启用 OTLP 数据接收的 Datadog Agent。

Datadog 通过 gRPC 接收 OTLP 数据。为确保正常运行，需要显式导入依赖并进行[打包器配置](/reference/configuration#bundlerexternals)：

```typescript title="src/mastra/index.ts"
// Explicitly import gRPC dependencies for the bundler
import '@grpc/grpc-js'
import '@opentelemetry/exporter-trace-otlp-grpc'
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'
import { OtelExporter, type ExportProtocol } from '@mastra/otel-exporter'

export const mastra = new Mastra({
  // Add grpc-js to externals so it's handled at runtime
  bundler: {
    externals: ['@grpc/grpc-js'],
  },
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-service',
        exporters: [
          new OtelExporter({
            provider: {
              custom: {
                endpoint: process.env.OTEL_EXPORTER_OTLP_ENDPOINT || 'http://localhost:4317',
                protocol: (process.env.OTEL_EXPORTER_OTLP_PROTOCOL || 'grpc') as ExportProtocol,
                headers: {},
              },
            },
          }),
        ],
      },
    },
  }),
})
```

:::note

必须在 Datadog Agent 中启用 OTLP 数据接收。将以下配置添加到 `datadog.yaml`：

```yaml
otlp_config:
  receiver:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
```

在本地运行 Datadog Agent 时，默认 OTLP 端点为 `http://localhost:4317`。

:::

:::warning

要让 gRPC 传输正常工作，必须在文件顶部显式导入 `@grpc/grpc-js` 和 `@opentelemetry/exporter-trace-otlp-grpc`，并配置 [`bundler.externals`](/reference/configuration#bundlerexternals)。缺少这些设置可能导致连接问题。

:::

:::tip Datadog 原生导出器

如果需要 Datadog 特有的功能，例如自动映射 span 类型、对 LLM span 分类，或希望简化设置而不配置 gRPC，可以考虑使用专用的 [`@mastra/datadog`](/integrations/observability/datadog) 导出器。它针对 Datadog APM 平台进行了优化。

:::

### 信号 {/* #signals */}

导出器发送两个 OpenTelemetry 信号：

- 跟踪：Mastra span，通过 `BatchSpanProcessor` 导出。
- 日志：Mastra 日志事件，通过 `BatchLogRecordProcessor` 导出。对于带有 `traceId` 和 `spanId` 的日志，系统会同时使用 OTEL 日志记录的原生跟踪上下文及 `mastra.traceId` / `mastra.spanId` 属性建立关联，让 Datadog、Grafana 和 Honeycomb 等后端能够自动关联日志与跟踪。

两个信号默认都启用，并共享同一套 Provider 配置。日志端点由跟踪端点派生：将末尾的 `/v1/traces` 替换为 `/v1/logs`。

要禁用某个信号，请设置 `signals` 选项：

```typescript title="src/mastra/index.ts"
new OtelExporter({
  provider: {/* ... */},
  signals: {
    traces: true, // default
    logs: false, // disable log export
  },
})
```

要导出日志，还需安装与所用协议匹配的 OTLP 日志导出器包：

```bash npm2yarn
# HTTP/JSON
npm install @opentelemetry/exporter-logs-otlp-http
# HTTP/Protobuf
npm install @opentelemetry/exporter-logs-otlp-proto
# gRPC
npm install @opentelemetry/exporter-logs-otlp-grpc @grpc/grpc-js
```

如果未安装匹配的日志导出器包，日志导出会静默禁用，跟踪导出仍可继续工作。

### 配置选项 {/* #configuration-options */}

#### 完整配置 {/* #complete-configuration */}

```typescript
new OtelExporter({
  // Provider configuration (required)
  provider: {
    // Use one of: dash0, signoz, newrelic, traceloop, laminar, custom
  },

  // Per-signal toggles. Both default to true.
  signals: {
    traces: true,
    logs: true,
  },

  // Export configuration
  timeout: 30000, // Export timeout in milliseconds
  batchSize: 100, // Number of spans/logs per batch

  // Debug options
  logLevel: 'info', // 'debug' | 'info' | 'warn' | 'error'
})
```

### `OpenTelemetry` 语义约定 {/* #opentelemetry-semantic-conventions */}

导出器遵循 [OpenTelemetry GenAI 语义约定 v1.38.0](https://github.com/open-telemetry/semantic-conventions/tree/v1.38.0/docs/gen-ai)，以兼容各类可观测性平台：

#### Span 命名 {/* #span-naming */}

- **模型调用**：`chat {model}`
- **生成循环**：`model_generation {model}`，每轮各有一个 `agent_step {agent_id}`
- **Tool 执行**：`execute_tool {tool_name}`
- **Agent 运行**：`invoke_agent {agent_id}`
- **Workflow 运行**：`invoke_workflow {workflow_id}`

Agent 每轮调用一次模型。`chat` span 对应这次调用，也是唯一包含 `gen_ai.request.model`、消息和 `gen_ai.usage.*` 的 span，因此后端汇总各 span 的用量时，每次调用只会计算一次。`model_generation` span 包含整个循环，`agent_step` 包含一轮操作（模型调用及 Tool 执行）；两者都不包含用量数据。

#### 关键属性 {/* #key-attributes */}

- `gen_ai.operation.name` — 操作类型（如 chat、tool.execute）
- `gen_ai.provider.name` — AI Provider（如 openai、anthropic）
- `gen_ai.request.model` — 模型标识符
- `gen_ai.input.messages` — 提供给模型的聊天记录
- `gen_ai.output.messages` — 模型返回的消息
- `gen_ai.usage.input_tokens` — 输入 token 数
- `gen_ai.usage.output_tokens` — 输出 token 数
- `gen_ai.request.temperature` — 采样温度
- `gen_ai.response.finish_reasons` — 完成原因

### 故障排除 {/* #troubleshooting */}

#### 缺少依赖错误 {/* #missing-dependency-error */}

如果您看到类似以下的错误：

```text
HTTP/Protobuf exporter is not installed (required for signoz).
To use HTTP/Protobuf export, install the required package:
  npm install @opentelemetry/exporter-trace-otlp-proto
```

请为所用 Provider 安装错误提示中建议的包。

#### 常见问题 {/* #common-issues */}

1. **协议包错误**：确认已为 Provider 安装正确的导出器包
2. **端点无效**：检查端点格式是否符合 Provider 的要求
3. **身份验证失败**：检查 API 密钥和标头是否正确

## Bridge {/* #bridge */}

:::warning

OpenTelemetry Bridge 目前仍处于**实验阶段**。API 和配置选项可能在未来版本中发生变化。

:::

OpenTelemetry (OTEL) Bridge 让 Mastra 的跟踪系统与现有 OpenTelemetry 基础设施双向集成。导出器负责将跟踪数据发送到外部平台；Bridge 则创建原生 OTEL span，使其加入现有的分布式跟踪上下文。

### 何时使用 Bridge {/* #when-to-use-the-bridge */}

以下情况适合使用 `OtelBridge`：

- 应用中已有 OTEL 插桩，例如 HTTP 服务器或数据库客户端
- 希望 Mastra 操作成为现有 OTEL 跟踪中的子 span
- 需要 Mastra Tool 内的 OTEL 插桩代码保持正确的父子关系
- 正在构建需要跨服务传播跟踪上下文的分布式系统

### 工作原理 {/* #how-it-works */}

`OtelBridge` 提供双向集成：

**从 OTEL 到 Mastra：**

- 自动读取 OTEL 环境上下文（AsyncLocalStorage）
- 从当前活动的 OTEL span 继承跟踪 ID 和父 span ID
- 遵循 OTEL 的采样决定：如果未采样某条跟踪，Mastra 也不会为它创建 span
- 启用 OTEL 自动插桩后，无需手动传递跟踪 ID

**从 Mastra 到 OTEL：**

- 为 Mastra 操作（Agent、LLM 调用、Tool、Workflow）创建原生 OTEL span
- 在分布式跟踪中保持正确的父子关系
- 使 Mastra 操作内已进行 OTEL 插桩的代码（如 HTTP 客户端和数据库调用）正确嵌套
- 将 Mastra 日志事件转发到全局注册的 OTEL `LoggerProvider`。在 Mastra span 内产生的日志会在该 span 的 OTEL 上下文中发出，以便后端关联日志与跟踪。如果未注册 `LoggerProvider`，日志发送会静默跳过。

### 安装 {/* #installation-1 */}

```bash npm2yarn
npm install @mastra/otel-bridge
```

Bridge 可与现有 OpenTelemetry 设置配合使用。根据具体配置，你可能还需要以下部分包：

- `@opentelemetry/sdk-node` — OTEL 的核心 Node.js SDK
- `@opentelemetry/auto-instrumentations-node` — 常见库的自动插桩
- `@opentelemetry/exporter-trace-otlp-proto` — OTLP 导出器（基于 HTTP 的 Protobuf）
- `@opentelemetry/exporter-trace-otlp-http` — OTLP 导出器（基于 HTTP 的 JSON）
- `@opentelemetry/exporter-trace-otlp-grpc` — OTLP 导出器（gRPC）
- `@opentelemetry/sdk-trace-base` — 基础跟踪 SDK（用于 `BatchSpanProcessor` 等）
- `@opentelemetry/core` — 核心工具（用于 `W3CTraceContextPropagator` 等）
- `@opentelemetry/sdk-logs` 和 OTLP 日志导出器（如 `@opentelemetry/exporter-logs-otlp-http`）— 如果还要通过 Bridge 转发 Mastra 日志事件，则需要安装

### 配置 {/* #configuration */}

使用 `OtelBridge` 需要两步：

1. 在应用中配置 OpenTelemetry 插桩
2. 将 `OtelBridge` 添加到 Mastra 可观测性配置中

#### 第 1 步：配置 OpenTelemetry 插桩 {/* #step-1-opentelemetry-instrumentation */}

创建用于初始化 OTEL 的插桩文件。该文件必须在应用代码之前运行：

```typescript title="instrumentation.ts"
import { NodeSDK } from '@opentelemetry/sdk-node'
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node'
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-proto'
import { BatchSpanProcessor } from '@opentelemetry/sdk-trace-base'
import { W3CTraceContextPropagator } from '@opentelemetry/core'

const sdk = new NodeSDK({
  serviceName: 'my-service',
  spanProcessors: [
    new BatchSpanProcessor(
      new OTLPTraceExporter({
        url: process.env.OTEL_EXPORTER_OTLP_ENDPOINT || 'http://localhost:4318/v1/traces',
      }),
    ),
  ],
  instrumentations: [getNodeAutoInstrumentations()],
  textMapPropagator: new W3CTraceContextPropagator(),
})

sdk.start()

export { sdk }
```

#### 第 2 步：Mastra 配置 {/* #step-2-mastra-configuration */}

将 `OtelBridge` 添加到 Mastra 可观测性配置中：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'
import { OtelBridge } from '@mastra/otel-bridge'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-service',
        bridge: new OtelBridge(),
      },
    },
  }),
  agents: {/* your agents */},
})
```

使用 Bridge 时无需配置 Mastra 导出器。跟踪会通过 OTEL SDK 的配置发送。如果还想将跟踪发送到其他目标，也可以添加 Mastra 导出器。

#### 转发日志（可选） {/* #forwarding-logs-optional */}

Bridge 还会将 Mastra 日志事件转发到全局注册的 OTEL `LoggerProvider`。要同时接入日志和跟踪，请在 `NodeSDK` 上注册日志记录处理器：

```typescript title="instrumentation.ts"
import { NodeSDK } from '@opentelemetry/sdk-node'
import { OTLPLogExporter } from '@opentelemetry/exporter-logs-otlp-http'
import { BatchLogRecordProcessor } from '@opentelemetry/sdk-logs'

const sdk = new NodeSDK({
  // ...trace config as usual
  logRecordProcessors: [
    new BatchLogRecordProcessor({
      exporter: new OTLPLogExporter({
        url: process.env.OTEL_EXPORTER_OTLP_LOGS_ENDPOINT || 'http://localhost:4318/v1/logs',
      }),
    }),
  ],
})
```

在 Mastra span 内产生的日志会在该 span 的 OTEL 上下文中发出，因此 Datadog、Grafana 和 Honeycomb 等后端可以自动将日志关联到对应跟踪。没有跟踪上下文的日志则使用当前活动的 OTEL 上下文。

如果未注册 `LoggerProvider`，日志发送会静默跳过。跟踪仍会按现有配置正常工作。

#### 运行您的应用程序 {/* #running-your-application */}

使用 `--import` 标志，确保插桩代码先于应用加载：

```bash
tsx --import ./instrumentation.ts ./src/index.ts
```

#### 退出前清空缓冲区 {/* #flushing-before-exit */}

Mastra 的 `flush()` 和 `shutdown()` 会请求已注册的 OTEL Provider 清空缓冲区，但 `BatchSpanProcessor` 可能仍持有一批已经开始导出的数据。在无服务器或短生命周期进程中，完成 Mastra 的 flush 后还应调用 `await sdk.shutdown()`，确保进程退出时 OTEL SDK 中没有残留 span。仅调用 Provider 自身的 `forceFlush()` 并不够：它不会等待导出器正在发送的批次。

### 语义约定 {/* #semantic-conventions */}

`OtelBridge` 按照 [OpenTelemetry GenAI 语义约定 v1.38.0](https://github.com/open-telemetry/semantic-conventions/tree/v1.38.0/docs/gen-ai) 导出 Mastra span，其中包括标准化的 span 名称（如 `chat {model}`、`execute_tool {tool_name}`）和属性（如 `gen_ai.usage.input_tokens`、`gen_ai.request.model`）。

有关 span 命名和属性的详情，请参阅[OpenTelemetry 导出器的语义约定](#opentelemetry-semantic-conventions)。

### 跟踪层次结构 {/* #trace-hierarchy */}

使用 `OtelBridge` 时，跟踪可以跨 OTEL 和 Mastra 的边界保持正确的层级关系：

```text
HTTP POST /api/chat (from Hono middleware)
└── agent.assistant (from Mastra via OtelBridge)
    └── model_generation __AI_SDK_OPENAI_MODEL_BASE__ (generation loop)
        ├── agent_step assistant (turn 1)
        │   ├── chat __AI_SDK_OPENAI_MODEL_BASE__ (LLM call)
        │   └── execute_tool search (tool execution)
        │       └── HTTP GET api.example.com (from OTEL auto-instrumentation)
        └── agent_step assistant (turn 2)
            └── chat __AI_SDK_OPENAI_MODEL_BASE__ (follow-up LLM call)
```

### 多服务分布式追踪 {/* #multi-service-distributed-tracing */}

`OtelBridge` 支持跨服务传播跟踪。当服务 A 通过 HTTP 调用服务 B 时，跟踪上下文会自动传播：

```text
Service A: HTTP POST /api/process
└── HTTP POST service-b/api/analyze (outgoing call)

Service B: HTTP POST /api/analyze (incoming call - same trace!)
└── agent.analyzer (Mastra agent inherits trace context)
    └── model_generation __AI_SDK_OPENAI_MODEL_BASE__
        └── agent_step analyzer
            └── chat __AI_SDK_OPENAI_MODEL_BASE__
```

两个服务都必须满足以下条件：

1. 已配置 OTEL 插桩
2. 已启用 W3C Trace Context 传播器
3. 已为 Mastra 配置 `OtelBridge`

通过 HTTP 发往 Mastra `MCPServer` 的请求也遵循同一规则。按上述方式配置后，它会加入调用方的跟踪；如果服务器没有 HTTP 插桩，每个请求则保留自己的跟踪。无论哪种情况，只要请求在 `_meta` 中或通过 HTTP 标头携带 W3C `traceparent`，请求 span 就会链接到调用方的 span，导出器和 Bridge 会将该链接作为 OpenTelemetry span link 发送。参阅[链接到调用方的跟踪](/reference/tools/mcp-server#linking-to-the-callers-trace)。

### 使用标签 {/* #using-tags */}

标签有助于在 OTEL 后端对跟踪进行分类和筛选。执行 Agent 或 Workflow 时可以添加标签：

```typescript
const result = await agent.generate('Hello', {
  tracingOptions: {
    tags: ['production', 'experiment-v2', 'user-request'],
  },
})
```

为了广泛兼容各类后端，标签会以 JSON 字符串形式导出到 `mastra.tags` span 属性中。常见用途包括：

- 环境标识：`"production"`、`"staging"`
- 实验跟踪：`"experiment-v1"`、`"control-group"`
- 优先级：`"priority-high"`、`"batch-job"`

### 故障排除 {/* #troubleshooting-1 */}

如果跟踪未按预期显示或关联：

- 确认 OTEL SDK 先于 Mastra 初始化（使用 `--import` 标志，或在入口文件顶部导入）
- 如果看到 `[OtelBridge] No OpenTelemetry tracer provider is registered globally`，说明 Bridge 找不到 tracer Provider。有些框架会创建 Provider，却没有将其注册到全局。此时可通过 `new OtelBridge({ tracerProvider })` 直接传入该 Provider。参阅[设置要求](/reference/observability/tracing/bridges/otel#setup-requirements)
- 确认已将 `OtelBridge` 添加到可观测性配置中
- 检查 OTEL 后端是否正在运行且可以访问
