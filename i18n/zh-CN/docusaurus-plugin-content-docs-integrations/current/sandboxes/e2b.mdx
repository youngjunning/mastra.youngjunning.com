# E2B

在隔离的 [E2B](https://e2b.dev) 云端 Sandbox 中执行命令。E2B 提供安全的临时环境，并支持挂载云存储。接口详情请参阅 [WorkspaceSandbox 接口](/reference/workspace/sandbox)。

## 安装 {/* #installation */}

```bash npm2yarn
npm install @mastra/e2b
```

## 用法 {/* #usage */}

将 `E2BSandbox` 添加到 Workspace，并将其分配给 Agent：

```typescript
import { Agent } from '@mastra/core/agent'
import { Workspace } from '@mastra/core/workspace'
import { E2BSandbox } from '@mastra/e2b'

const workspace = new Workspace({
  sandbox: new E2BSandbox({
    id: 'dev-sandbox',
    timeout: 60_000, // 60 second timeout (default: 5 minutes)
  }),
})

const agent = new Agent({
  id: 'dev-agent',
  name: 'dev-agent',
  model: '__GATEWAY_ANTHROPIC_MODEL_OPUS__',
  workspace,
})
```

## 要求重新连接 {/* #requiring-reattachment */}

传入已持久化的 `sandboxId`，但对应的 Sandbox 已不存在时，默认的 `reattach: 'best-effort'` 会继续按逻辑 ID 查找，可能重新连接到另一个具有相同 `id` 的 Sandbox，也可能创建新 Sandbox。如果换用其他 Sandbox 会使应用依赖的状态悄然丢失，请设置 `reattach: 'required'`：

```typescript title="src/mastra/workspaces.ts"
const sandbox = new E2BSandbox({
  id: 'session-123',
  sandboxId: persistedSandboxId,
  reattach: 'required',
})
```

使用 `reattach: 'required'` 时，如果 Sandbox 已不存在，`start()` 会以 `SandboxError` 拒绝，错误的 `code` 为 `SANDBOX_REATTACH_FAILED`，且不会执行查找或创建。错误的 `details` 包含 `provider`、`sandboxId` 和 `logicalId`（Sandbox 的逻辑 `id`）。其他错误与使用 `'best-effort'` 时一样，原样向上抛出。如需重新开始，请清除已持久化的 `sandboxId`，并在构造 Sandbox 时省略该选项。克隆实例会继承 `reattach` 设置。

## 后台进程 {/* #background-processes */}

`E2BSandbox` 内置进程管理器，可启动和管理后台进程。进程在 E2B 云端 Sandbox 中运行，使用 E2B SDK 的 `commands.run()`，并设置 `background: true`。

```typescript
const sandbox = new E2BSandbox({ id: 'dev-sandbox' })
await sandbox.start()

// Spawn a background process
const handle = await sandbox.processes.spawn('node server.js', {
  env: { PORT: '3000' },
  onStdout: data => console.log(data),
})

// Interact with the process
console.log(handle.stdout)
await handle.sendStdin('input\n')
await handle.kill()
```

`list()` 返回 Sandbox 中正在运行的进程，包括并非由此管理器启动的进程；它也返回输出尚未被读取的已退出进程。

E2B 进程管理器支持重新连接到外部启动的进程，以及重新连接之前启动的进程。传入 PID 调用 `get(pid)` 即可连接现有进程。连接前产生的输出无法获取：

```typescript
const handle = await sandbox.processes.get(existingPid)
if (handle) {
  console.log(handle.stdout)
}
```

完整 API 请参阅 [`SandboxProcessManager` 参考文档](/reference/workspace/process-manager)。

## 挂载云存储 {/* #mounting-cloud-storage */}

E2B Sandbox 可以挂载 S3、GCS 和 Azure Blob 文件系统，让 Sandbox 内的程序像访问本地目录一样访问云存储。这适用于：

- 处理存储在云存储桶中的大型数据集
- 将输出文件直接写入云存储
- 在 Sandbox 会话之间共享数据

### 使用 mounts 配置 {/* #using-the-mounts-config */}

挂载文件系统最简单的方法是使用 Workspace 的 `mounts` 配置：

```typescript
import { Workspace } from '@mastra/core/workspace'
import { S3Filesystem } from '@mastra/s3'
import { GCSFilesystem } from '@mastra/gcs'
import { E2BSandbox } from '@mastra/e2b'

const workspace = new Workspace({
  mounts: {
    '/s3-data': new S3Filesystem({
      bucket: 'my-s3-bucket',
      region: 'us-east-1',
      accessKeyId: process.env.AWS_ACCESS_KEY_ID,
      secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY,
    }),
    '/gcs-data': new GCSFilesystem({
      bucket: 'my-gcs-bucket',
      projectId: 'my-project',
      credentials: JSON.parse(process.env.GCS_SERVICE_ACCOUNT_KEY),
    }),
  },
  sandbox: new E2BSandbox({ id: 'dev-sandbox' }),
})
```

Sandbox 启动时，文件系统会自动挂载到指定路径。随后，Sandbox 中运行的代码可以像访问本地目录一样访问 `/s3-data` 和 `/gcs-data` 中的文件。

### 挂载原理 {/* #how-mounting-works */}

E2B Sandbox 使用 FUSE（用户空间文件系统）挂载云存储：

- **S3/R2**：通过 [s3fs-fuse](https://github.com/s3fs-fuse/s3fs-fuse) 挂载
- **GCS**：通过 [gcsfuse](https://github.com/GoogleCloudPlatform/gcsfuse) 挂载
- **Azure Blob**：通过 [blobfuse2](https://github.com/Azure/azure-storage-fuse) 挂载

使用挂载功能时，E2B Sandbox 会自动安装所需的 FUSE 工具。为获得更好的性能，请预先构建已安装这些工具的自定义模板。

## 自定义模板 {/* #custom-templates */}

未指定模板时，E2BSandbox 默认会自动构建模板：安装 `s3fs` 以支持挂载 S3，用当前的 Node.js LTS 版本替换基础镜像中的旧版本，并启用 corepack，使 `pnpm` 和 `yarn` 使用仓库 `packageManager` 字段指定的版本。此模板会被缓存，并供多个 Sandbox 实例复用。

Node.js 版本会精确固定，且是模板身份的一部分。向 `createDefaultMountableTemplate()` 传入 `nodeVersion` 可选择其他版本；更改版本会构建新模板。

挂载 GCS 时，如果尚未安装 `gcsfuse`，系统会自动安装。如需添加其他工具或缩短冷启动时间，请使用自定义模板。

### 使用现有模板 {/* #using-an-existing-template */}

如果已有预先构建的模板，请传入其 ID：

```typescript
const workspace = new Workspace({
  sandbox: new E2BSandbox({
    id: 'dev-sandbox',
    template: 'my-custom-template',
  }),
})
```

### 自定义默认模板 {/* #customizing-the-default-template */}

传入函数即可自定义默认的可挂载模板。函数接收 `TemplateBuilder`，并应返回修改后的模板：

```typescript
const workspace = new Workspace({
  sandbox: new E2BSandbox({
    template: base =>
      base
        .aptInstall(['ffmpeg', 'imagemagick', 'poppler-utils'])
        .pipInstall(['pandas', 'numpy'])
        .npmInstall(['sharp']),
  }),
})
```

模板构建器支持链式调用，例如：

- `aptInstall(packages)`：安装系统软件包
- `pipInstall(packages)`：安装 Python 包
- `npmInstall(packages)`：安装 Node.js 包
- `runCmd(command)`：运行 shell 命令
- `setEnvs(vars)`：设置环境变量
- `copy(src, dest)`：将文件复制到模板中

完整的方法列表请参阅 [E2B 模板文档](https://e2b.dev/docs/template/defining-template)。

### 预构建模板 {/* #pre-building-templates */}

默认模板会在首次使用时构建并缓存。如需缩短冷启动时间或加入 GCS 支持，可以预先构建模板：

```typescript
import { createDefaultMountableTemplate } from '@mastra/e2b'
import { Template } from 'e2b'

// Get the default mountable template (includes s3fs)
const { template, id } = createDefaultMountableTemplate()

// Build and save to E2B
const result = await Template.build(template, id)
console.log('Template ID:', result.templateId)

// Use this ID in your E2BSandbox config for instant startup
const sandbox = new E2BSandbox({
  template: result.templateId,
})
```

如需加快使用 GCS 时的冷启动，请在自定义模板中预先安装 `gcsfuse`：

```typescript
const workspace = new Workspace({
  sandbox: new E2BSandbox({
    id: 'dev-sandbox',
    template: base => base.aptInstall(['gcsfuse']),
  }),
})
```

此步骤可选：挂载时如果没有 `gcsfuse`，系统会自动安装。

### 仓库模板 {/* #repository-templates */}

`createRepoTemplate` 生成模板配置，在构建时克隆仓库并运行其设置命令。这样，每个 Sandbox 启动时已有准备好的检出内容和已安装的依赖，无须在每次会话中重新冷克隆：

```typescript
import { E2BSandbox, createRepoTemplate } from '@mastra/e2b'

const sandbox = new E2BSandbox({
  id: sessionId,
  template: createRepoTemplate({
    getRepositoryAccess: async () => ({
      cloneUrl: 'https://github.com/octocat/hello-world.git',
    }),
    setupCommand: 'pnpm install',
  }),
})
```

`getRepositoryAccess` 提供克隆 URL；对于私有仓库，还提供凭证。它是克隆 URL 的唯一来源，因此实际克隆的仓库与模板标识所依据的仓库不会不一致。如果它返回 `undefined`，`createRepoTemplate` 也返回 `undefined`。没有仓库的会话因此可以直接请求 Provider 的默认模板，无须在调用处添加条件判断。

每组仓库与设置命令恰好对应一个模板：模板名称包含仓库 slug 和输入内容的短哈希，提交 SHA 则作为该名称上的标签（`mastra-repo-<owner>-<repo>-<hash>:sha-<sha>`）。解析配置时，模板会固定到仓库当前默认分支的最新提交：查找模板前运行 `git ls-remote`（不克隆，约 100 毫秒），并以该 SHA 命名标签。默认分支更新后，下一个新 Sandbox 会以新标签原位重建同一模板；旧 SHA 标签作为可清理的构建历史保留，而不会堆积成过时模板。如果无法解析最新提交，引用会退回到稳定的 `current` 标签，构建时克隆默认分支当时的内容。

解析按需进行，只有模板首次构建会阻塞启动。每次成功构建也会更新稳定的 `current` 标签。因此，最新提交变化后，下一个 Sandbox 可以立即从上一次构建启动，而新的 SHA 引用会在 E2B 端后台构建；运行时设置会通过 `git fetch` 快进略旧的检出内容，代码是否为最新不取决于模板。设置命令变化后，其哈希会生成新的模板名称。

`setupCommand` 也接受数组，其中每个条目都是独立的、可缓存的构建步骤。`workingDirectory` 设置构建和 Sandbox 的当前工作目录，仓库会克隆到 `<workingDirectory>/<repo>`。

#### 在一个模板中包含多个仓库 {/* #several-repositories-in-one-template */}

使用 `repos` 代替 `getRepositoryAccess`，可将多个仓库克隆到同一个模板。每个仓库都有自己的凭证解析函数和设置命令；设置命令可以是字符串或数组，数组中的每项都是独立的构建步骤：

```typescript
const sandbox = new E2BSandbox({
  id: sessionId,
  template: createRepoTemplate({
    repos: [
      {
        getRepositoryAccess: async () => ({
          cloneUrl: 'https://github.com/mastra-ai/mastra.git',
        }),
        setupCommand: 'pnpm install --frozen-lockfile',
      },
      {
        getRepositoryAccess: async () => ({
          cloneUrl: 'https://github.com/mastra-ai/template-docs-expert.git',
        }),
        setupCommand: 'npm install',
      },
    ],
    workspaceSetupCommand: 'npm install --global @mastra/mcp-docs-server',
    continueOnSetupFailure: true,
    workingDirectory: '/home/user/repos',
  }),
})
```

每个仓库都会克隆到 `<workingDirectory>/<repo>`。公共仓库先于私有仓库构建，各组内保持调用方指定的顺序。私有仓库凭证作为构建环境变量，对所有构建步骤可见，因此任一仓库的设置命令都能读取其他仓库的令牌。请只将设置命令彼此可信的仓库放在同一个列表中。

所有仓库设置完成后，`workspaceSetupCommand` 会在工作目录中运行。`continueOnSetupFailure` 默认为 `false`；启用后，设置命令失败时会将对应仓库记录到 `.mastra-sandbox/setup-failed` 并继续执行，而非使构建失败。

标记文件让会话知道镜像中已执行的步骤：每个仓库对应 `.mastra-sandbox/repos/<repo>`，Workspace 命令执行后对应 `.mastra-sandbox/workspace-setup`；这些文件均位于工作目录下。启用 `continueOnSetupFailure` 时，请先检查 `.mastra-sandbox/setup-failed`。

添加或移除仓库、更改设置命令都会创建新模板；轮换凭证则复用现有模板。如果任一仓库的访问配置无法解析，Sandbox 会回退到默认模板。如果某个仓库的最新提交无法解析，它会在不固定提交的情况下被克隆，其他仓库仍保持各自固定的提交。

除非配置要求更高规格，否则模板按 E2B 的默认机器规格（2 个 vCPU、1024 MB）构建。传入 `cpuCount` 和 `memoryMB` 可设置由该模板创建的 Sandbox 所使用的机器规格：

```typescript
const sandbox = new E2BSandbox({
  id: sessionId,
  template: createRepoTemplate({
    getRepositoryAccess: async () => ({
      cloneUrl: 'https://github.com/octocat/hello-world.git',
    }),
    setupCommand: 'pnpm install',
    cpuCount: 4,
    memoryMB: 2048,
  }),
})
```

资源规格也是模板身份的一部分：它们与仓库和设置命令一起参与模板名称的哈希计算，因此调整规格会构建新模板，不会悄然复用按旧规格构建的模板。仓库模板构建失败、Sandbox 回退到默认可挂载模板时，后备模板也会按请求的规格构建，确保设置过程不会落到规格更低的机器上。E2B 接受的规格值仍受账户等级限制。

如需在合并后主动预热模板，而非等待第一个会话，可在定时任务或合并到主分支的事件处理程序中，使用相同选项调用 `refreshRepoTemplate`。它执行与 Sandbox 启动时相同的解析流程：解析当前最新提交，已有构建则复用，否则构建模板并更新 `current`；返回 `{ ref, action, sha }`：

```typescript
import { refreshRepoTemplate } from '@mastra/e2b'

const result = await refreshRepoTemplate({
  getRepositoryAccess: async () => ({
    cloneUrl: 'https://github.com/octocat/hello-world.git',
  }),
  setupCommand: 'pnpm install',
})
// { ref: 'mastra-repo-octocat-hello-world-…:sha-…', action: 'built' | 'reused', sha: '…' }
```

此模板构建在默认可挂载基础镜像之上，即 E2B 的 `base` 镜像；其中已有 git 和常用工具，也有用于挂载的 `s3fs`/FUSE。仓库克隆到构建用户主目录下的 `$HOME/<repo>`，仓库名由克隆 URL 得出。构建步骤和运行时命令都以 Sandbox 的非 root 用户 `user` 身份在其主目录中运行，因此无须预先准备目录，运行时文件所有权也保持正确；在运行时检查 `$HOME`，即可在模板留下的位置找到检出内容。

失败处理机制可避免损坏的模板阻塞会话：

- 构建失败时会回退到默认可挂载模板；会话仍可在运行时向 `$HOME` 冷克隆仓库。
- 对于失败构建的引用，E2B 仍会让 `Template.exists` 判断其存在，因此损坏的引用原本可能一直被复用。如果通过具名引用创建 Sandbox 失败，系统会丢弃缓存的解析结果，并沿后备流程重试创建。

如果缺少模板工具链的 Sandbox 比启动失败更不可接受，请在解析后的配置中设置 `fallbackTemplate: false`。此时构建失败，或引用无法创建 Sandbox，都会使 `start()` 以原始错误拒绝，而不会回退：

```typescript title="src/mastra/workspaces.ts"
const repoTemplate = createRepoTemplate({
  getRepositoryAccess: async () => ({ cloneUrl: 'https://github.com/acme/app.git' }),
  setupCommand: 'pnpm install',
})!

const sandbox = new E2BSandbox({
  template: {
    resolveSpec: async () => ({ ...(await repoTemplate.resolveSpec()), fallbackTemplate: false }),
  },
})
```

对于私有仓库，如果 `getRepositoryAccess` 在返回克隆 URL 的同时返回 `authorization`，即可构建预热模板。该凭证应在每次解析模板时新签发且有效期较短，例如 GitHub App 安装令牌。凭证通过 shell 中的 `http.extraheader` 对最新提交查询和构建时的克隆进行认证。它会进入模板定义的环境（构建步骤可见，但不会持久化到运行时 Sandbox 环境），且不会写入镜像文件系统，因此任何捕获的镜像层都不会包含它。凭证设置为 `GH_TOKEN`，与会话运行设置前注入的变量相同，所以调用 `gh` 或通过已认证 HTTPS 请求的命令，在构建和会话中的行为一致。

请只传入短期凭证：凭证值会保留在模板定义中，直到下次重建，因此其有效期决定了暴露时间。请注意，克隆的仓库内容会成为团队可见的模板镜像的一部分。访问函数未返回凭证时，会在不使用令牌的情况下克隆：公共仓库仍可正常构建；私有仓库的构建则回退，由会话在运行时通过注入的认证信息完成克隆。

如果设置命令需要自己的凭证，例如软件包仓库令牌或私有索引 URL，请通过 `buildEnv` 传入；它接受记录对象或异步解析函数。这些值是模板身份的一部分，更改任一值会生成新模板。若不希望值出现在模板名称中，还需传入 `buildEnvRevision`。值仍会像克隆凭证一样传给构建步骤，但模板仅以修订标识命名。每次更改值时，都应更新修订标识。

`repoTemplateRef` 可计算配置对应的带标签引用，而不执行构建；使用 E2B CLI 清理旧 SHA 标签时很有用。

### 每个会话独立使用 Sandbox {/* #per-session-sandboxes */}

对于每个会话构造一个 Sandbox 的宿主程序，例如使用 Mastra Factory 的 `sandbox` 配置，请使用 `E2BFactorySandbox`：Sandbox 以会话 ID 标识（按 ID 调用 getOrCreate，因此在 E2B 空闲超时后会暂停，并可按 ID 恢复）；仓库模板由 `createRepoTemplate` 根据该会话的仓库生成；项目的 `cpuCount` 和 `memoryMb` 设置会传入模板。参阅 [FactorySandbox 参考文档](/reference/workspace/factory-sandbox)。

```typescript
import { MastraFactory } from '@mastra/factory'
import { E2BFactorySandbox } from '@mastra/e2b'

new MastraFactory({
  sandbox: new E2BFactorySandbox({ apiKey: process.env.E2B_API_KEY }),
})
```

也支持直接使用回调：`sandbox: ctx => new E2BSandbox({ id: ctx.sessionId, template: createRepoTemplate(ctx) })`。Factory 会将其视为没有可调整设置的自定义 Provider。无论使用哪种方式，Factory 都会为返回的 Sandbox 附加自己的会话设置。

## 与 Code Mode 配合使用 {/* #using-with-code-mode */}

[Code Mode](/docs/agents/code-mode) 让 Agent 编写一个 TypeScript 程序来编排其 Tool。E2B 在远程微型虚拟机中运行该程序，因此需要将程序写入 Sandbox 文件系统，而非宿主机文件系统的传输方式。`@mastra/e2b` 为此提供 `E2BCodeModeTransport`。将它作为 `createCodeMode` 的第二个参数传入：

```typescript
import { createCodeMode } from '@mastra/core/tools'
import { E2BSandbox, E2BCodeModeTransport } from '@mastra/e2b'

const { tool, instructions } = createCodeMode(
  {
    tools: { getWeather, getForecast },
    sandbox: new E2BSandbox({ timeout: 60_000 }),
  },
  new E2BCodeModeTransport(),
)
```

`E2BCodeModeTransport` 会在 Sandbox 未运行时自动启动它，在宿主机上使用 esbuild 去除 TypeScript 语法（因此不受 Sandbox 中 Node 版本的影响），在虚拟机内运行 `node`，随后清理程序文件。`@mastra/core` 提供的默认 `StdioCodeModeTransport` 仅适用于与宿主机共享文件系统的 Sandbox，例如 `LocalSandbox`。
