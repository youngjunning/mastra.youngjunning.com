# Docker

在本机的 Docker 容器内执行命令。容器会长期运行，命令通过 `docker exec` 执行。适用于本地开发、CI/CD、隔离网络部署，以及不需要云端 Sandbox、注重成本的场景。接口详情请参阅 [WorkspaceSandbox 接口](/reference/workspace/sandbox)。

## 安装 {/* #installation */}

```bash npm2yarn
npm install @mastra/docker
```

主机上需要运行 [Docker Engine](https://docs.docker.com/engine/install/)。

## 用法 {/* #usage */}

将 `DockerSandbox` 添加到 Workspace，并将该 Workspace 分配给 Agent：

```typescript
import { Agent } from '@mastra/core/agent'
import { Workspace } from '@mastra/core/workspace'
import { DockerSandbox } from '@mastra/docker'

const workspace = new Workspace({
  sandbox: new DockerSandbox({
    image: 'node:22-slim',
  }),
})

const agent = new Agent({
  id: 'dev-agent',
  name: 'dev-agent',
  model: '__GATEWAY_ANTHROPIC_MODEL_OPUS__',
  workspace,
})
```

### 仓库模板 {/* #repository-templates */}

`createDockerRepoTemplate` 构建的镜像已包含检出的仓库和初始化命令的执行结果，因此会话启动时依赖项已经安装，无需从头克隆：

```typescript
import { DockerSandbox, createDockerRepoTemplate } from '@mastra/docker'

const sandbox = new DockerSandbox({
  id: sessionId,
  template: createDockerRepoTemplate({
    getRepositoryAccess: async () => ({
      cloneUrl: 'https://github.com/octocat/hello-world.git',
    }),
    setupCommand: 'npm ci',
  }),
})
```

`getRepositoryAccess` 提供克隆 URL；对于私有仓库，还提供短期凭证。凭证仅作为构建密钥传入克隆步骤，不会进入镜像、镜像层或镜像标识。如果 `getRepositoryAccess` 为 `undefined`，`createDockerRepoTemplate` 也会返回 `undefined`，从而选用 Provider 的默认镜像，调用处无需另写条件判断。

仓库会克隆到 `<workingDirectory>/<repo>`（默认为 `/workspace`），该路径随后成为 Sandbox 的工作目录。传入 `ref` 可指定默认分支以外的分支、标签或提交。构建开始前，解析器会运行 `git ls-remote`，将 ref 固定到某个提交；该提交也是镜像标识的一部分。因此，分支指向新提交后，下次创建新的 Sandbox 时会生成新镜像；分支未变化时则复用缓存镜像。如果无法解析分支头，解析器会拒绝继续，而不会缓存未固定提交的克隆结果。

`setupCommand` 也可以是数组，其中每条命令都是独立的可缓存构建步骤。命令不能包含未转义的换行符，否则会开始一条新的 Dockerfile 指令。可以在行尾使用 `\`，也可以将命令拆成多个条目。

#### 在一个镜像中放入多个仓库 {/* #several-repositories-in-one-image */}

使用 `repos` 代替 `getRepositoryAccess`，可以将多个仓库克隆到同一个镜像中。每个仓库都可单独配置访问解析器、`ref` 和初始化命令；初始化命令可以是字符串或数组，数组中的每个条目都是独立的构建步骤：

```typescript
const sandbox = new DockerSandbox({
  id: sessionId,
  template: createDockerRepoTemplate({
    repos: [
      {
        getRepositoryAccess: async () => ({
          cloneUrl: 'https://github.com/mastra-ai/template-docs-expert.git',
        }),
        setupCommand: 'npm install',
      },
      {
        getRepositoryAccess: async () => ({
          cloneUrl: 'https://github.com/mastra-ai/good-issue.git',
        }),
        ref: 'main',
      },
    ],
    workspaceSetupCommand: 'npm install --global @mastra/mcp-docs-server',
    continueOnSetupFailure: true,
    workingDirectory: '/workspace',
  }),
})
```

每个仓库都会克隆到 `<workingDirectory>/<repo>`，工作目录则成为 Sandbox 的当前目录。构建时先处理公开仓库，再处理私有仓库；每组内部保持调用方指定的顺序。私有仓库的凭证仅作为构建密钥传入该仓库的克隆步骤，初始化命令无法读取凭证。

所有仓库完成初始化后，`workspaceSetupCommand` 会在工作目录中运行。启用 `continueOnSetupFailure`（默认值为 `false`）后，某个初始化命令失败时会将对应仓库记录在 `.mastra-sandbox/setup-failed`，并继续构建，而不是让整个构建失败。

工作目录中的标记可供会话判断镜像已经执行了哪些步骤：每个仓库对应 `.mastra-sandbox/repos/<repo>`，Workspace 初始化命令执行后则有 `.mastra-sandbox/workspace-setup`。如果启用了 `continueOnSetupFailure`，请先检查 `.mastra-sandbox/setup-failed`。

如果任一仓库的访问方式或分支头无法解析，整个解析过程都会失败，Sandbox 将回退到默认模板。

## Docker Cloud Sandboxes {/* #docker-cloud-sandboxes */}

`DockerSandboxesSandbox` 在 Docker Cloud Sandboxes 的 microVM 中执行命令，而不是使用本地容器。要访问 Docker Cloud Sandboxes，请提供已完成身份验证的 `@docker/sandboxes` 客户端。

```typescript
import { Sandboxes, pat } from '@docker/sandboxes'
import { Workspace } from '@mastra/core/workspace'
import { DockerSandboxesSandbox } from '@mastra/docker'

const client = new Sandboxes({
  auth: pat({
    username: process.env.DOCKER_USERNAME!,
    personalAccessToken: process.env.DOCKER_PAT!,
  }),
})
const workspace = new Workspace({
  sandbox: new DockerSandboxesSandbox({
    id: sessionId,
    image: 'ubuntu:24.04',
    environment: { NODE_ENV: 'production' },
    client,
  }),
})
```

`id` 用作远程 Sandbox 的显示名称，以便重新连接时查找。新实例使用相同的 `id` 时，会重新连接到已有的 microVM；如果它已停止，还会将其重新启动。每个实例都使用独立的创建幂等键。传入 `sandboxId` 可直接重新连接到已知的远程 Sandbox。

命令通过 `sh -lc` 执行，因此命令字符串可以使用管道、重定向和 `&&`。单独传入的 `args` 会进行 shell 引号转义。`executeCommand` 支持 `timeout`、`abortSignal`、流式 `onStdout`/`onStderr` 回调，以及 `maxRetainedBytes`（每个输出流默认保留 1 MiB）。调用 `destroy()` 会删除远程 Sandbox。

## 后台进程 {/* #background-processes */}

`DockerSandbox` 内置进程管理器，可启动和管理后台进程。进程通过 `docker exec` 在容器内运行。

```typescript
const sandbox = new DockerSandbox({ id: 'dev-sandbox' })
await sandbox._start()

// Spawn a background process
const handle = await sandbox.processes.spawn('node server.js', {
  env: { PORT: '3000' },
  onStdout: data => console.log(data),
})

// Interact with the process and signal EOF
console.log(handle.stdout)
await handle.sendStdin('input\n')
await handle.closeStdin()
await handle.wait()
```

完整 API 请参阅 [`SandboxProcessManager` 参考文档](/reference/workspace/process-manager)。

## 环境变量 {/* #environment-variables */}

使用 `env` 设置容器级环境变量。启动进程时也可以为单条命令传入环境变量：

```typescript
const sandbox = new DockerSandbox({
  image: 'node:22-slim',
  env: {
    NODE_ENV: 'production',
    DATABASE_URL: 'postgres://localhost:5432/mydb',
  },
})
```

## 写入文件 {/* #write-files */}

使用 `writeFiles` 可在一次调用中上传多个文件。相对路径以工作目录为基准解析。可为每个文件单独设置可选的 `mode` 来控制 POSIX 权限；其值必须是 `0o001` 到 `0o777` 之间的整数。省略 `mode` 时，新文件以 `0644` 权限创建。

```typescript
await sandbox.writeFiles([
  { path: 'src/index.js', content: "console.log('hello')\n" },
  { path: 'run.sh', content: '#!/bin/sh\n', mode: 0o755 },
])
```

Docker 是唯一会应用显式 `mode` 的内置 Sandbox。无法遵循单文件权限设置的 Provider（Vercel、E2B、Daytona、Cloudflare）会拒绝包含 `mode` 的 `writeFiles` 调用，而不会悄悄忽略它。

## 绑定挂载 {/* #bind-mounts */}

使用 `volumes` 选项将主机目录挂载到容器中：

```typescript
const sandbox = new DockerSandbox({
  image: 'node:22-slim',
  volumes: {
    '/my/project': '/workspace/project',
    '/shared/data': '/data',
  },
})
```

绑定挂载在创建容器时生效。主机路径必须在 Sandbox 启动前存在。

## 安全加固 {/* #hardening */}

使用 Docker 专有的资源限制和安全加固选项约束 Sandbox 容器。以下示例限制内存和进程数，并通过相匹配的 `cpuPeriod` 与 `cpuQuota` 将 CPU 限制为单核；同时移除 Linux capabilities，将根文件系统设为只读，并把 `/tmp` 挂载为可写的临时空间：

```typescript
const sandbox = new DockerSandbox({
  image: 'node:22-slim',
  memory: 512 * 1024 * 1024,
  memorySwap: 512 * 1024 * 1024,
  cpuPeriod: 100_000,
  cpuQuota: 100_000,
  pidsLimit: 256,
  readonlyRootfs: true,
  capDrop: ['ALL'],
  capAdd: ['NET_BIND_SERVICE'],
  securityOpt: ['no-new-privileges:true'],
  ulimits: [{ name: 'nofile', soft: 1024, hard: 2048 }],
  tmpfs: {
    '/tmp': 'rw,noexec,nosuid,size=64m',
  },
})
```

这些选项直接映射到 Docker 的 `HostConfig` 字段；未传入时不会设置。

启用安全加固前，请考虑以下影响：

* `readonlyRootfs`：在容器内安装软件包，或使用会向挂载路径以外写入内容的 Tool，可能会失败。可为 `/tmp` 等临时写入路径添加 `tmpfs`；必要时也可为 `~/.npm` 等包管理器缓存挂载 tmpfs 或卷。
* `capDrop`：移除所有 capabilities 会禁用需要 Linux capabilities 的命令，包括 `ping` 和挂载操作。依赖 FUSE 的工具也会被禁用。只重新添加工作负载确实需要的 capabilities。
* `memory`：Docker 将 `0` 视为无限制。只有不需要内存上限时，才省略 `memory` 或传入 `0`。
* `memorySwap`：Docker 的内存和交换空间行为取决于主机及 Docker 守护进程的配置。设置 `memory` 但未设置 `memorySwap` 时，Docker 默认允许交换空间用量达到内存上限的两倍。若要禁用容器的交换空间，请将 `memorySwap` 设为与 `memory` 相同；Docker 也接受 `-1`，表示交换空间无限制。
* `pidsLimit`：值设得过低可能影响 `docker exec` 工作负载，因为长期运行的容器每执行一条命令都会启动额外进程。
* `privileged`：特权容器会绕过 capabilities 和安全选项的控制。除非工作负载确有需要，否则不要将 `privileged: true` 与 capabilities 或安全选项一起使用。
* 重新连接：Sandbox ID 匹配时，`DockerSandbox` 会复用现有容器。如果检查到的 `HostConfig` 加固值不同，它会发出警告。要应用修改后的加固选项，需销毁并重新创建 Sandbox。Docker 可能会规范化检查结果中的值；如果原容器使用 Docker 默认的交换空间行为，重新连接时修改 `memorySwap` 也可能触发警告。
* Docker Desktop：在 macOS 和 Windows 上，资源限制作用于 Docker Desktop 虚拟机内部，因此虚拟机分配到的资源可能进一步限制容器可用资源。

## 重连 {/* #reconnection */}

`DockerSandbox` 可以通过匹配标签重新连接到现有容器。调用 `start()` 时，它会查找 `mastra.sandbox.id` 标签与 Sandbox ID 匹配的容器。找到后：

* 直接复用正在运行的容器。
* 重新启动已停止的容器。

```typescript
// First run — creates a new container
const sandbox = new DockerSandbox({ id: 'persistent-sandbox' })
await sandbox._start()

// Later — reconnects to the existing container
const sandbox2 = new DockerSandbox({ id: 'persistent-sandbox' })
await sandbox2._start()
```

## Docker 连接选项 {/* #docker-connection-options */}

通过 `dockerOptions` 连接远程 Docker 主机，或使用自定义套接字路径：

```typescript
// Remote Docker host
const sandbox = new DockerSandbox({
  dockerOptions: {
    host: '192.168.1.100',
    port: 2376,
    ca: fs.readFileSync('ca.pem'),
    cert: fs.readFileSync('cert.pem'),
    key: fs.readFileSync('key.pem'),
  },
})

// Custom socket path
const sandbox = new DockerSandbox({
  dockerOptions: {
    socketPath: '/var/run/docker.sock',
  },
})
```
