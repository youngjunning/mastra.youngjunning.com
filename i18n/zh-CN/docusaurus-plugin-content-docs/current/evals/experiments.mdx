# 实验

**引入版本：** `@mastra/core@1.4.0`

实验会让数据集中的每个条目经由目标（Agent、Workflow 或 scorer）处理，再选择性地对输出评分。如果要评估 LLM 评审器本身，可将 scorer 设为目标。默认情况下，结果会持久化到存储中，便于比较不同提示词、模型或代码变更下的运行。

<Inject>
**供 AI Agent 使用：** 运行 `npx mastra api experiment run dataset_123 '{"name":"translation-baseline"}'`，无需打开 Studio 或编写临时脚本即可启动实验。请将示例 ID 换成 `npx mastra api dataset list` 返回的 ID。该命令需要一个正在运行的 Mastra 服务器，并且服务器已配置数据集存储、注册实验目标。可用 `npx mastra dev` 启动本地服务器，或通过 `--url` 指定可访问服务器的基础 URL。构造不同的输入前，先运行 `npx mastra api experiment run --schema`。实验可能调用模型，因此启动前应取得用户批准。安装 Mastra Skill：`npx skills add mastra-ai/skills --skill mastra`，可查看 API CLI 发现与目标指定、schema、认证和错误处理的完整指引。
</Inject>

## 基础实验 {/* #basic-experiment */}

调用 [`startExperiment()`](/reference/datasets/startExperiment)，传入目标和 scorer：

```typescript title="src/mastra/experiments/basic.ts"
import { mastra } from '../index'

const dataset = await mastra.datasets.get({ id: 'translation-dataset-id' })

const summary = await dataset.startExperiment({
  name: 'gpt-5.1-baseline',
  targetType: 'agent',
  targetId: 'translation-agent',
  scorers: ['accuracy', 'fluency'],
})

console.log(summary.status) // 'completed' | 'failed'
console.log(summary.succeededCount) // items that executed without an error
console.log(summary.failedCount) // items with execution errors
```

`startExperiment()` 会阻塞，直到所有条目完成。如需发起后立即返回，请参阅[异步实验](#async-experiments)。

## 在 Studio 中运行实验 {/* #run-experiments-in-studio */}

也可以在 [Studio](/docs/studio/overview) 中运行实验。添加数据集条目后，打开该条目，选择 **Run Experiment**，再配置目标、scorer 和选项。

要为单个条目配置 scorer，请编辑条目并启用 **Override dataset scorers**。可以选择一个或多个 scorer；若留空，则该条目不运行 scorer。

实验运行后，**Experiments** 标签页会列出该数据集的所有运行及其状态、计数和时间戳。选择某次实验，可查看各条目的结果、分数和执行追踪。

在 **Experiments** 标签页选择 **Compare**，再选择至少两次实验，即可并排比较分数和结果。

## 解读结果 {/* #interpret-results */}

实验状态和计数反映的是执行情况；输出质量应通过分数判断。状态为 `completed` 的实验仍可能包含执行错误，而 `failedCount: 0` 也不代表所有答案都达到质量要求。

| 结果 | 含义 |
| - | - |
| `succeededCount` 和 `failedCount` | 无错误执行的条目数与发生执行错误的条目数 |
| 每个条目的 `scores` | 输出符合各 scorer 标准的程度，以及 scorer 提供的原因 |
| 平均分 | 某个 scorer 的汇总表现；可能掩盖个别失败 |

例如，单条目实验的问题是 `2 + 2?`，返回 `5`。准确性 scorer 给出 `0` 分，但任务本身没有抛出异常，因此摘要包含：

```typescript
console.log(summary.status) // 'completed'
console.log(summary.succeededCount) // 1
console.log(summary.failedCount) // 0
console.log(summary.results[0].scores[0].score) // 0
```

在 Studio 中打开实验，查看各条目的输出、分数和原因，再判断变更是否改善了 Agent。也要检查 scorer 错误：缺失分数无法证明质量。

如果每个条目都必须达到要求，请逐一核对分数。对于以 `1` 表示达标的二元 scorer，五个 `1` 和一个 `0` 的平均分约为 `0.83`，但仍有一个条目不达标。

若要在 CI 中自动检查质量，[`runEvals()` 的 gate 和 verdict](/docs/evals/gates-and-verdicts) 可提供明确的通过／失败标准。这些选项属于 `runEvals()`；数据集实验的状态和计数仍表示执行结果。

## 删除实验 {/* #delete-experiments */}

在 Studio 的全局 **Experiments** 列表中，选择某行的 **Delete experiment**；也可以打开实验并选择 **Delete Experiment**。全局列表还可以删除因数据集被删除而失去关联、无法再通过数据集详情页访问的实验。

删除实验会永久移除其结果记录，以及实验产生的可观测性 Trace 和关联的 span、分数、反馈、指标与日志。如果存储适配器不支持删除 Trace，Trace 会保留，系统会记录警告，但实验和结果记录仍会被删除。

还可以通过 [Core API](/reference/datasets/deleteExperiment)、[Client SDK](/reference/client-js/datasets#deleteexperiment) 或[服务器路由](/reference/server/routes#delete-an-experiment)删除实验。

## 实验目标 {/* #experiment-targets */}

通过 `targetType` 和 `targetId` 选择已在 Mastra 实例中注册的 Agent、Workflow 或 scorer。目标会处理数据集中的每个条目，实验的 `scorers` 随后评估目标输出。

如需自定义执行过程，可改为传入内联 `task` 函数。参阅[使用内联任务的数据集实验](/docs/evals/evals-with-memory#dataset-experiments-with-an-inline-task)，了解如何控制每个条目的 Memory 线程。

### 已注册的 Agent {/* #registered-agent */}

指定在 Mastra 实例中注册的 Agent：

```typescript title="src/mastra/experiments/agent-target.ts"
const summary = await dataset.startExperiment({
  name: 'agent-v2-eval',
  targetType: 'agent',
  targetId: 'translation-agent',
  scorers: ['accuracy'],
})
```

每个条目的 `input` 会直接传给 Agent。可以使用受支持的消息格式，例如提示词字符串、消息对象或消息数组。可接受的输入详见 [`agent.generate()` 参考文档](/reference/agents/generate)。

#### 启用 Memory 的 Agent {/* #memory-enabled-agents */}

目标 Agent 配置了 Memory 时，实验运行器会为每个条目和每次重试注入新的 Memory 线程。如果请求上下文中没有资源 ID，每个线程都会获得一个隔离的、由实验拥有的资源。

要针对现有资源运行，请在实验的 `requestContext` 或条目的 `requestContext` 中设置 `MASTRA_RESOURCE_ID_KEY`；条目值优先于实验值。运行器仍会为每个条目和每次重试创建新线程，但使用同一资源 ID 的线程会共享该资源的 Memory。

注入的线程带有便于回溯运行的标签：线程元数据包含 `experimentId`，以及以 `experimentItemId` 保存的数据集条目 ID。系统不会为这些线程生成标题。

条目共享同一资源时，按资源范围工作的 Memory 功能可以读写同一状态：

- 按资源范围保存的工作记忆更新会持久化到该资源，并可能影响其他条目。条目默认并发运行，因此不要依赖执行顺序。
- 按资源范围进行的语义回忆可能将该资源此前的对话带入实验；实验对话记录也会在该资源后续的对话中被检索到。

这种方式可用于结合真实用户积累的上下文评估 Agent。若不希望实验触及真实用户状态，请改用专门的评估资源 ID。

以下情况会跳过线程注入：

- 如果请求上下文设置了 `MASTRA_THREAD_ID_KEY`，运行器会直接使用该线程。共用同一线程 ID 的条目和重试会共享一段对话。
- 如果 Agent 未配置 Memory，或者请求上下文明确将资源 ID 设为空字符串或 `null`，运行器会跳过线程注入。

### 已注册的 Workflow {/* #registered-workflow */}

指定在 Mastra 实例中注册的 Workflow：

```typescript title="src/mastra/experiments/workflow-target.ts"
const summary = await dataset.startExperiment({
  name: 'workflow-eval',
  targetType: 'workflow',
  targetId: 'translation-workflow',
  scorers: ['accuracy'],
})
```

Workflow 会在 `run.start()` 中以 `inputData` 接收每个条目的 `input`。请按 Workflow 的输入 schema 组织数据。

### 已注册的 scorer {/* #registered-scorer */}

将 scorer 作为目标可评估评审器本身。运行器会调用 `scorer.run(item.input)`，因此数据集条目的 `input` 必须包含该 scorer 所需的完整载荷。

下例假设已注册的 `accuracy` scorer 接收字符串类型的 `input`、`output` 和 `groundTruth` 字段。请按实际 scorer 所需的结构调整：

```typescript title="src/mastra/experiments/scorer-target.ts"
await dataset.addItem({
  input: {
    input: 'What is the capital of France?',
    output: 'Paris',
    groundTruth: 'Paris',
  },
  groundTruth: { score: 1 },
})

const summary = await dataset.startExperiment({
  name: 'judge-accuracy-eval',
  targetType: 'scorer',
  targetId: 'accuracy',
})
```

两个 `groundTruth` 字段的用途不同：

- `input.groundTruth` 是传给评审器的参考答案：`'Paris'`。
- 顶层 `groundTruth` 是期望评审器返回的结果：`{ score: 1 }`。它不会传给目标 scorer。

目标输出包含 `score` 和 `reason`。若要对照顶层标准答案评估该输出，请通过实验的 `scorers` 选项另加一个 scorer。没有额外的 scorer 时，实验只记录评审器输出，不会评价它与预期结果是否一致。


## 为各条目选择 scorer {/* #select-scorers-per-item */}

将已注册的 scorer ID 添加到数据集条目，可覆盖附在数据集上的 scorer：

```typescript title="src/mastra/datasets/items.ts"
await dataset.addItem({
  input: 'Translate "hello" to French.',
  scorerIds: ['accuracy', 'fluency'],
})
```

实验会按以下优先级为每个条目选择**唯一**的 scorer 来源：

1. 实验的 `scorers` 选项（如果提供）
1. 条目的 `scorerIds` 字段（如果提供）
1. 数据集的 `scorerIds` 字段
1. 不使用 scorer

Mastra 不会合并这些来源。在运行或条目级别显式设置空数组，表示不使用 scorer，且不会回退到下一来源。运行级别的空分类配置效果相同。重复的条目 ID 或数据集 ID 只运行一次，顺序按首次出现的位置确定。

以下更新展示如何在显式空覆盖和继承数据集配置之间切换：

```typescript title="src/mastra/datasets/items.ts"
// Run no scorers for this item
await dataset.updateItem({
  itemId: 'translation-item-id',
  scorerIds: [],
})

// Remove the item override and inherit the dataset's scorers
await dataset.updateItem({
  itemId: 'translation-item-id',
  scorerIds: null,
})
```

更新时省略 `scorerIds` 会保留其当前值。每个条目版本都会保存 scorer ID 列表，包括空列表。scorer 定义不会复制到条目版本中，而是继续使用已有的注册表或 Editor 行为。

Mastra 会在执行目标前解析各条目的 scorer ID：先查找已注册的 scorer，再请 Editor 加载已存储的 scorer。条目级别的过期 ID 会让该条目产生 `EXPERIMENT_ITEM_SCORER_NOT_FOUND` 错误码。Mastra 会跳过该条目的目标执行且不重试，实验中的其他条目仍继续运行。

如果选中的运行级别或数据集级别来源中存在缺失的 ID，实验设置会失败。对于按优先级被忽略的较低级别来源，Mastra 不会解析其中的 ID。

Workflow 步骤 scorer 只能通过运行级别的分类 `scorers` 配置使用。条目级别 ID 适用于平铺的 Agent、Workflow 和轨迹 scorer 分派。

## 按次控制持久化 {/* #control-persistence-per-run */}

使用 `persistence` 跳过某次运行的存储写入。实验记录和分数记录可以分别关闭：

```typescript title="src/mastra/experiments/no-persistence.ts"
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'translation-agent',
  scorers: ['accuracy'],
  persistence: {
    experiments: 'none',
    scores: 'none',
  },
})
```

目标和 scorer 仍会运行，`startExperiment()` 仍会在 `summary` 中返回条目结果和分数。两个设置相互独立，例如仅设 `scores: 'none'`，可以持久化实验及其条目结果，而不创建分数记录。

省略的设置默认为 `'default'`，即保留标准存储行为。该策略只控制本次运行创建的实验与分数记录，不会禁用目标使用的存储，例如 Agent Memory、向量、可观测性数据或自定义 Tool 存储。

`startExperimentAsync()` 配合 `experiments: 'none'` 运行时，不会持久化实验记录、进度更新或条目结果。分数是否持久化仍由 `persistence.scores` 单独控制。若没有实验事件观察器，此次运行会发起后即不再跟踪，实验 API 也无法报告其完成或失败状态。

调用方需要返回的摘要时，请使用同步的 `startExperiment()`。实验事件观察器也可以接收生命周期事件和最终摘要。

## 观察实验事件 {/* #observe-experiment-events */}

使用 `onEvent` 在实验运行期间接收带版本号、可安全序列化为 JSON 的生命周期事件。它适用于 `startExperiment()`、`startExperimentAsync()` 和 `runExperiment()`。

```typescript title="src/mastra/experiments/observe.ts"
import type { ExperimentEvent } from '@mastra/core/datasets'

const events: ExperimentEvent[] = []

await dataset.startExperimentAsync({
  task: async ({ input }) => processItem(input),
  persistence: { experiments: 'none' },
  onEvent: async event => {
    events.push(event)
    await publishEvent(event)
  },
})
```

观察器会收到以下事件类型：

- `experiment.run.started`：标识运行、目标、已解析的数据集版本和条目数量。
- `experiment.item.completed`：报告评分后已提交的条目结果，包括分数、错误、重试次数、Tool mock 详情和稳定的条目标识。
- `experiment.run.finished`：报告最终结果和摘要计数。

Mastra 会等待当前观察器调用完成后再传递下一个事件。这种串行传递会形成背压，并确保事件的 `sequence` 值与传递顺序一致；条目仍可并发执行。

如果观察器抛出异常或拒绝 Promise，Mastra 会中止剩余运行，并让 `runExperiment()` 以 `id` 为 `EXPERIMENT_EVENT_OBSERVER_FAILED` 的 `MastraError` 拒绝。失败的观察器不会收到终止事件。对于 `startExperimentAsync()`，独立运行的观察器失败时方法已经返回；若调用方需要直接获知传递错误，应在观察器内部处理。

Mastra 会先等待 `experiment.run.finished` 事件完成，再持久化实验的最终状态。禁用实验持久化时，应以该事件作为权威的终止信号；但不要把它当作存储写入后立即可读的信号。

导出的事件类型包括 `ExperimentEvent`、`ExperimentRunStartedEvent`、`ExperimentItemCompletedEvent` 和 `ExperimentRunFinishedEvent`。读取特定事件的属性前，请先根据判别字段 `type` 缩小类型范围。

## 生命周期钩子 {/* #lifecycle-hooks */}

生命周期钩子可在目标运行前准备状态，并在运行后清理。适用于无法在空白环境中评估条目的情况，例如需要先把 fixture 文件复制到 Agent 的 Workspace，或在 Agent 访问前准备 Sandbox。

钩子分两级执行：`beforeAll` 和 `afterAll` 每次实验各运行一次；`beforeEach` 和 `afterEach` 每个条目各运行一次：

```typescript title="src/mastra/experiments/hooks.ts"
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'document-agent',
  scorers: ['accuracy'],
  beforeAll: async ({ experimentId }) => {
    await createWorkspace(experimentId)
  },
  beforeEach: async ({ item }) => {
    await copyFixture(item.metadata?.fixture)
  },
  afterEach: async ({ item, result }) => {
    await clearWorkspaceFiles(item.id)
  },
  afterAll: async ({ summary }) => {
    await deleteWorkspace(summary.experimentId)
  },
})
```

所有钩子都可以是异步函数。每个钩子都会收到 `experimentId`、`mastra` 实例和运行级 `signal`，因此耗时的准备工作也能随实验一起取消。条目级钩子还会收到 `item`。清理钩子会收到它们所跟随的结果：`afterEach` 收到包含分数的条目 `result`，`afterAll` 收到即将返回的 `summary`。

传给钩子的条目只暴露 `id`、`input`、`groundTruth` 和 `metadata`。Tool mock 和 scorer 选择等控制执行的字段不会暴露，因此钩子无法改变条目的运行方式。

### 钩子失败 {/* #hook-failures */}

各钩子抛出异常时影响不同，取决于运行对它的依赖程度：

| 钩子 | 失败时 |
| - | - |
| `beforeAll` | 实验失败；不运行任何条目。 |
| `beforeEach` | 该条目以 `EXPERIMENT_ITEM_BEFORE_EACH_FAILED` 失败；其他条目继续。 |
| `afterEach` | 记录日志；不改变该条目已记录的结果。 |
| `afterAll` | 记录日志；不改变返回的摘要。 |

`beforeAll` 失败时，实验会标记为失败；错误向上传播前仍会发出 `experiment.run.finished` 事件。

`beforeEach` 失败时，该条目的前置条件尚未满足，因此会跳过其目标和 scorer，也不会运行该条目的 `afterEach`；未完成的准备工作应自行负责清理。

清理失败只记录日志，不向上传播。执行 `afterEach` 时目标已经产出真实结果；若因清理不完整而丢弃结果，就会失去实验原本要收集的数据。

`afterAll` 会在所有退出路径运行，包括实验失败、`beforeAll` 失败或[事件观察器](#observe-experiment-events)失败，因此即使出错也不会跳过清理。每次实验最多运行一次。

## Tool mock {/* #tool-mocks */}

实验运行调用有副作用 Tool 的 Agent 时，可以为各数据集条目附加静态 Tool mock，使运行结果可重现。实验期间，被 mock 的 Tool 会返回预设输出而不实际执行。条目没有提供 mock 的 Tool 默认仍会真实调用。

mock 会与数据集条目一起存储和版本化。每个 mock 都指定 Tool 名称、预期参数和要返回的输出：

```typescript title="src/mastra/experiments/tool-mocks.ts"
await dataset.addItem({
  input: 'What is the weather in Seattle?',
  toolMocks: [
    {
      toolName: 'getWeather',
      args: { city: 'Seattle' },
      output: { temperature: 60, conditions: 'rainy' },
    },
  ],
})
```

Tool mock 仅支持目标类型为 `agent` 的实验。

### 阻止未声明的 Tool {/* #block-undeclared-tools */}

将实验的 `unmockedToolPolicy: 'deny'` 设为拒绝，可阻止所有没有 mock 的 Tool 调用。适用于真实调用可能产生副作用的场景：

```typescript
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'weather-agent',
  unmockedToolPolicy: 'deny',
})
```

默认策略为 `'allow'`。可以在单个已存储或内联条目上覆盖实验策略：

```typescript
await dataset.addItem({
  input: 'What is the weather in Seattle?',
  unmockedToolPolicy: 'allow',
})
```

条目值优先于实验值。被拒绝的调用会在 Tool 执行前以 `TOOL_MOCK_NOT_DECLARED` 失败；该失败不会重试，也不会计入 `liveCalls`。

### 匹配与消费 {/* #matching-and-consumption */}

参数采用严格匹配：对象键的顺序不影响结果，数组元素顺序则有影响。值不会转换成其他类型。只有 Agent 调用 Tool 时的参数与 mock 的 `args` 深度相等，才会使用该 mock。

如果一个条目为相同 Tool 和参数声明了多个 mock，系统会按顺序消费：第一次调用使用第一个，第二次调用使用第二个，依此类推。顺序按 `(toolName, args)` 分组分别追踪，不同参数组之间互不影响。

### 匹配模式 {/* #matching-mode */}

默认情况下，mock 会严格匹配其 `args`。设置 `matchArgs: 'ignore'` 后，只按 Tool 名称匹配，不比较 mock 的 `args`；该 Tool 下一条尚未消费的 mock 会被使用，不论 Agent 传入了什么参数：

```typescript
const subAgentMock = {
  toolName: 'agent-balanceAgent',
  args: { prompt: 'look up the balance for YJ' },
  output: { text: "YJ's balance is $100." },
  matchArgs: 'ignore',
}
```

当 Tool 参数包含噪声或由模型生成时，这种方式很有用。最常见的场景是模拟**子 Agent 的响应**。父 Agent 将委派的子 Agent 视为 `agent-<name>` Tool，其参数包含 LLM 编写的 `prompt` 和运行时注入的字段。mock `agent-<name>` 会直接返回预设响应，不运行子 Agent 及其内部 Tool。若从 Trace 创建 mock，子 Agent 委派调用会自动采用 `matchArgs: 'ignore'`；可改为 `'strict'`，固定确切参数。

### 失败情形 {/* #failures */}

违反 mock 配置的 Tool 调用会使该条目失败：

- `TOOL_MOCK_MISMATCH`：调用参数与任何 mock 都不匹配。
- `TOOL_MOCK_EXHAUSTED`：所有匹配的 mock 都已消费。
- `TOOL_MOCK_NOT_DECLARED`：Tool 没有 mock，且有效的 `unmockedToolPolicy` 为 `'deny'`。

发生上述任一失败时，Agent 运行会立即中止，模型无法继续调用其他 Tool，包括原本会真实运行且可能产生副作用的未 mock Tool。这些失败是确定性的，不会重试。已声明但未使用的 mock 不会让条目失败，而是报告为未消费。

启用 mock 拦截时，Agent 的 Tool 会顺序执行，因此重复的 `(toolName, args)` mock 会按提供方的调用顺序消费。条目声明 mock 或其有效 `unmockedToolPolicy` 为 `'deny'` 时，拦截即生效。

### 诊断信息 {/* #diagnostics */}

每个条目的结果都包含 `toolMockReport`，列出已使用的 mock 和未经过 mock 的 Tool 调用：

```typescript
for (const item of summary.results) {
  const report = item.toolMockReport
  if (!report) continue

  console.log(report.served) // mocks matched and returned
  console.log(report.unconsumed) // mocks declared but never used
  console.log(report.liveCalls) // undeclared tools allowed to run live
  console.log(report.failure) // the first deterministic mock failure, if any
}
```

在 [Studio](/docs/studio/overview) 中，编辑数据集条目可用 JSON 数组编写 Tool mock；打开实验结果可查看同一份报告。

### 限制 {/* #limitations */}

- **被 mock 的 Tool span 是扁平的。** 已使用的 mock 会记录一个 `tool_call` span，包含模拟输出和 `mocked: true` 属性。mock 不匹配或已耗尽时，会记录 `success: false` 的 span。真实 Tool 不会运行，因此该 span 没有子 span，也没有 `toolDescription`。
- **存储支持情况。** LibSQL、PostgreSQL、MongoDB 和 Spanner 适配器会持久化 Tool mock 及其报告；MySQL 适配器会拒绝写入包含二者任意一个的记录。所有数据集存储适配器都会持久化 `unmockedToolPolicy`。

## 异步实验 {/* #async-experiments */}

`startExperiment()` 会阻塞直到所有条目完成。对于运行时间较长的数据集，可使用 [`startExperimentAsync()`](/reference/datasets/startExperimentAsync) 在后台启动实验：

```typescript title="src/mastra/experiments/async.ts"
const { experimentId, status } = await dataset.startExperimentAsync({
  name: 'large-dataset-run',
  targetType: 'agent',
  targetId: 'translation-agent',
  scorers: ['accuracy'],
})

console.log(experimentId) // UUID
console.log(status) // 'pending'
```

通过 [`getExperiment()`](/reference/datasets/getExperiment) 轮询完成状态：

```typescript
let experiment = await dataset.getExperiment({ experimentId })
if (!experiment) throw new Error('Experiment not found')

while (experiment.status === 'pending' || experiment.status === 'running') {
  await new Promise(resolve => setTimeout(resolve, 5000))
  experiment = await dataset.getExperiment({ experimentId })
  if (!experiment) throw new Error('Experiment not found')
}

console.log(experiment.status) // 'completed' | 'failed'
```

## 由调用方驱动的实验 {/* #caller-driven-experiments */}

`startExperiment()` 让 Mastra 管理整个运行过程。如果循环由持久化编排器（例如 Temporal、Airflow 或自定义 worker 集群）负责，可先创建实验，再由调用方按以下任一种方式驱动：

- **调用方控制循环，Mastra 运行各条目。** 创建带目标的实验，然后对每个条目调用一次 [`runExperimentItem()`](/reference/datasets/runExperimentItem)。Mastra 会执行目标和 scorer，再持久化结果。
- **调用方执行全部步骤。** 创建不带目标的实验，在自己的基础设施上执行条目并评分，再使用 [`submitExperimentResult()`](/reference/datasets/submitExperimentResult)写入每个结果。

两种方式都以 [`finalizeExperiment()`](/reference/datasets/finalizeExperiment) 结束，并写入与原生运行相同的表，因此 Studio 的视图、比较和审核摘要仍可照常使用。

### 在服务器端运行条目 {/* #run-items-server-side */}

调用 [`createExperiment()`](/reference/datasets/createExperiment)，传入目标和 scorer。提供自己的 `id`（例如 Workflow 运行 ID）可使创建操作具备幂等性：以相同 ID 重试会返回已有实验，而不是失败。

```typescript title="src/mastra/experiments/caller-driven.ts"
const dataset = await mastra.datasets.get({ id: 'translation-dataset-id' })

const { experimentId, totalItems, datasetVersion } = await dataset.createExperiment({
  id: 'temporal-wf-run-42', // optional: reuse your workflow run id for idempotent creates
  targetType: 'agent',
  targetId: 'translation-agent',
  scorers: ['accuracy'],
})
```

随后由编排器运行每个条目。Mastra 会在固定的数据集版本中解析条目，用解析出的 scorer 执行目标。结果写入以 `(experimentId, itemId, attempt)` 为键进行 upsert；重试的任务最终会收敛到一行：

```typescript
const { result, scores } = await dataset.runExperimentItem({
  experimentId,
  itemId: 'item-1',
})
```

重试和超时由编排器负责：每次调用 `runExperimentItem` 都只执行该条目一次。scorer 采用与原生运行相同的优先级：实验 `scorers` 高于条目 `scorerIds`，后者高于数据集 `scorerIds`。

### 写入外部结果 {/* #ingest-external-results */}

如果 worker 自行执行条目并评分，请创建不带目标的实验：

```typescript title="src/mastra/experiments/ingestion.ts"
const { experimentId } = await dataset.createExperiment({
  id: 'temporal-wf-run-42',
  name: 'external-eval',
})
```

使用 [`submitExperimentResult()`](/reference/datasets/submitExperimentResult) 为每个条目提交一份结果。提交以 `(experimentId, itemId, attempt)` 为键进行 upsert；worker 重试会收敛到同一行，不会产生重复结果：

```typescript
await dataset.submitExperimentResult({
  experimentId,
  itemId: 'item-1',
  output: { translation: 'Hola' },
  scores: [{ scorerId: 'accuracy', score: 0.92, reason: 'Faithful translation' }],
})
```

`input` 和 `groundTruth` 默认取自实验固定的数据集版本中的条目值。内联 `scores` 会持久化到该实验的分数存储中，因此可与原生 scorer 运行结果一起比较。带目标创建的实验会拒绝 `submitExperimentResult`，以免两个写入方争用同一批行。

### 完结实验 {/* #finalize */}

所有条目完成后，调用 [`finalizeExperiment()`](/reference/datasets/finalizeExperiment)。Mastra 会根据已持久化的行计算 `succeededCount`、`failedCount` 和 `skippedCount`，worker 无需自行统计完成情况。完结操作是幂等的；再次调用会返回已存储的记录：

```typescript
const experiment = await dataset.finalizeExperiment({ experimentId })

console.log(experiment.status) // 'completed'
console.log(experiment.succeededCount) // items with at least one attempt that didn't error
console.log(experiment.failedCount) // items where every attempt errored
console.log(experiment.skippedCount) // items never submitted
```

HTTP 也提供相同的生命周期：`POST /api/datasets/:datasetId/experiments` 搭配 `start: false`、`POST .../experiments/:experimentId/items/:itemId/run`、`POST .../experiments/:experimentId/results`、`POST .../experiments/:experimentId/finalize`；参阅[服务器路由](/reference/server/routes#datasets-and-experiments)。`@mastra/client-js` 中亦可使用，参阅[数据集 API](/reference/client-js/datasets)。

### 重试与幂等性约定 {/* #retry-and-idempotency-contract */}

由调用方驱动的调用可以积极重试，例如由 Temporal 重试策略触发。具体保证如下：

- **按 `id` 幂等创建。** 再次用调用方提供的相同 `id` 调用 `createExperiment`，会返回已有实验。如果该 `id` 属于其他数据集，或已有实验的目标不同，则以 `EXPERIMENT_ID_CONFLICT` 失败（HTTP `409`）。
- **结果按 `(experimentId, itemId, attempt)` upsert。** 再次提交相同键会更新已有行；所有可变字段均以最后一次写入为准。worker 重试不会产生重复行。
- **`attempt` 区分有意重复试验与重试。** 同一次运行的重试应复用相同 `attempt`（默认 `0`），使结果收敛。若要将同一条目的重复试验记录为不同行，可依次提交 `attempt: 0`、`attempt: 1` 等。
- **数据集版本在创建时固定。** 提交会按该版本中可见的条目验证，因此此后编辑或删除条目不会影响运行中的实验。如果提交的 `itemId` 在固定版本中不可见，会返回 `404`。
- **完结操作幂等且不可逆。** 对已完成的实验再次调用完结操作，会直接返回存储记录，不重新计算。完结后继续提交会被 `EXPERIMENT_ALREADY_FINALIZED` 拒绝（HTTP `409`）。
- **计数由服务器按条目计算。** 完结时，Mastra 会汇总每个条目的各次尝试：`succeededCount`（至少一次尝试无错误）、`failedCount`（所有尝试均出错）、`skippedCount`（从未提交）。始终满足 `succeededCount + failedCount + skippedCount === totalItems`，调用方无需自行维护完成计数。每次尝试的行仍可通过 `listExperimentResults` 查询。

## 配置选项 {/* #configuration-options */}

### 并发 {/* #concurrency */}

控制并行运行的条目数量（默认：5）：

```typescript
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'translation-agent',
  maxConcurrency: 10,
})
```

### 超时与重试 {/* #timeouts-and-retries */}

设置单个条目的超时时间（毫秒）和重试次数：

```typescript
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'translation-agent',
  itemTimeout: 30_000, // 30 seconds per item
  maxRetries: 2, // retry failed items up to 2 times
})
```

重试采用指数退避；中止错误不会重试。

### 中止实验 {/* #aborting-an-experiment */}

传入 `AbortSignal` 以取消正在运行的实验：

```typescript
const controller = new AbortController()

// Cancel after 60 seconds
setTimeout(() => controller.abort(), 60_000)

const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'translation-agent',
  signal: controller.signal,
})
```

摘要会将剩余条目标记为已跳过。

### 固定数据集版本 {/* #pinning-a-dataset-version */}

针对数据集的特定快照运行：

```typescript
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'translation-agent',
  version: 3, // use items from dataset version 3
})
```

## 理解摘要 {/* #understanding-the-summary */}

`startExperiment()` 返回包含计数和各条目结果的 `ExperimentSummary`：

- `completedWithErrors` 为 `true` 表示实验已完成，但部分条目失败。
- 通过 `signal` 取消的条目会计入 `skippedCount`。

完整参数和返回类型详见 [`startExperiment` 参考文档](/reference/datasets/startExperiment)。
