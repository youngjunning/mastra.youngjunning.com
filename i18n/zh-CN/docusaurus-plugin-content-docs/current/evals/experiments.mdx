# 实验

**添加于：** `@mastra/core@1.4.0`

实验通过目标（Agent、Workflow或评分器）运行数据集中的每个项目，然后可以选择对输出进行评分。当您想要评估 LLM 法官本身时，请使用记分员作为目标。默认情况下，结果会持久保存到存储中，以便您可以比较不同提示、模型或代码更改之间的运行情况。

<Inject>
  **对于人工智能Agent：**&#x8DD1;步`npx mastra api experiment run dataset_123 '{"name":"translation-baseline"}'` to start an experiment directly without opening Studio or writing a temporary script. Replace the sample ID with one returned by `npx mastra api dataset list`. This command needs a running Mastra server that has dataset storage and registered experiment targets. Start a local server with `npx mastra dev`，或使用`--url`传递可访问服务器的基本 URL。在构建不同的输入之前，运行`npx mastra api experiment run --schema`。在开始实验之前获得用户批准，因为它可以进行模型调用。安装 Mastra 的技能`npx skills add mastra-ai/skills --skill mastra`有关 API CLI 发现和定位以及架构、身份验证和错误处理的完整指南。
</Inject>

## 基础实验 {/* #basic-experiment */}

称呼[`startExperiment()`](/reference/datasets/startExperiment) with a target and scorers:

```typescript title="src/mastra/experiments/basic.ts"
import { mastra } from '../index'

const dataset = await mastra.datasets.get({ id: 'translation-dataset-id' })

const summary = await dataset.startExperiment({
  name: 'gpt-5.1-baseline',
  targetType: 'agent',
  targetId: 'translation-agent',
  scorers: ['accuracy', 'fluency'],
})

console.log(summary.status) // 'completed' | 'failed'
console.log(summary.succeededCount) // items that executed without an error
console.log(summary.failedCount) // items with execution errors
```

`startExperiment()`阻塞直到所有项目完成。对于即发即弃执行，请参阅[async experiments](#async-experiments).

## 在 Studio 中运行实验 {/* #run-experiments-in-studio */}

您还可以在以下位置运行实验[Studio](/docs/studio/overview). After you've added a dataset item, open it and select **Run Experiment** and configure the target, scorers, and options.

要为一项配置记分器，请编辑该项并启用**Override dataset scorers**. Select one or more scorers, or leave the selection empty to run no scorers for that item.

运行实验后，**Experiments** tab shows all runs for that dataset (with status, counts, and timestamps). Select an experiment to see per-item results, scores, and execution traces.

在**Experiments** tab, select **Compare** and choose two or more experiments to compare their scores and results side by side.

## 解释结果 {/* #interpret-results */}

实验的状态和计数描述了执行情况。使用分数来评估输出质量。一个`completed` experiment can contain execution errors, and `failedCount: 0` doesn't mean every answer meets your quality requirements.

|结果 |它告诉你什么 |
| - | - |
|`succeededCount` and `failedCount` | How many items executed without an error or ended with an execution error |
| Each item's `scores` | How the output performed against each scorer's criteria, with a reason when provided |
| Average score | Aggregate performance for a scorer, which can hide individual failures |

例如，一项针对某项的实验要求`2 + 2?` and returns `5`. An accuracy scorer assigns `0`, but the task itself returns without throwing. Its summary contains:

```typescript
console.log(summary.status) // 'completed'
console.log(summary.succeededCount) // 1
console.log(summary.failedCount) // 0
console.log(summary.results[0].scores[0].score) // 0
```

在 Studio 中，打开实验并检查每个项目的输出、分数和原因，然后再确定更改是否改进了您的Agent。还要检查记分器错误：缺失的分数不能提供质量证据。

如果每个项目都必须满足要求，请对照每个项目的分数进行检查。对于二元记分器，其中`1` means the requirement was met, five scores of `1` and one of `0` average about `0.83`, but one item still fails the requirement.

对于 CI 中的自动化质量检查，[`runEvals()` gates and verdicts](/docs/evals/gates-and-verdicts) provide explicit pass/fail criteria. Those options belong to `runEvals()`. Dataset experiment status and counts remain execution results.

## 删除实验 {/* #delete-experiments */}

在 Studio 中，打开全局**Experiments** list and select **Delete experiment** on a row, or open the experiment and select **Delete Experiment**. The global list also lets you delete experiments orphaned by dataset deletion, which no longer have a dataset details page.

删除实验会永久删除其结果记录，以及它产生的可观察性跟踪及其关联的跨度、分数、反馈、指标和日志。不支持跟踪删除的存储适配器会将跟踪保留在适当的位置，记录警告，并且仍然删除实验及其结果记录。

您还可以使用以下命令删除实验[Core API](/reference/datasets/deleteExperiment) or [Client SDK](/reference/client-js/datasets#deleteexperiment). The same operation is available through the [server routes](/reference/server/routes#delete-an-experiment).

## 实验目标 {/* #experiment-targets */}

使用`targetType` and `targetId` to select an agent, workflow, or scorer registered on your Mastra instance. The target processes each dataset item. The experiment's `scorers` evaluate the target's output afterward.

对于自定义执行，请传递内联`task` function instead. See [dataset experiments with an inline task](/docs/evals/evals-with-memory#dataset-experiments-with-an-inline-task) for an example that controls each item's memory thread.

### 注册Agent {/* #registered-agent */}

指向在您的 Mastra 实例上注册的Agent：

```typescript title="src/mastra/experiments/agent-target.ts"
const summary = await dataset.startExperiment({
  name: 'agent-v2-eval',
  targetType: 'agent',
  targetId: 'translation-agent',
  scorers: ['accuracy'],
})
```

每个项目的`input` is passed directly to the agent. Use a supported message format, such as a prompt string, a message object, or an array of messages. See the [`agent.generate()` reference](/reference/agents/generate) for accepted inputs.

#### 支持内存的Agent {/* #memory-enabled-agents */}

当目标Agent拥有自己的内存时，实验运行器会为每个项目注入一个新的内存线程并重试。如果请求上下文中没有资源 ID，每个线程都会获得一个独立的、实验拥有的资源。

要针对现有资源运行，请设置`MASTRA_RESOURCE_ID_KEY` in the experiment's `requestContext` or in an item's `requestContext`. Item values override experiment values. The runner still creates a fresh thread for each item and retry, but all threads using the same resource id share that resource's memory.

注入的线程被标记，以便您可以将它们映射回运行：线程元数据携带`experimentId` and the dataset item's id as `experimentItemId`. No thread title is generated for them.

当项目共享资源时，资源范围的内存功能可以读取和写入相同的状态：

* 资源范围的工作内存更新会持续到资源中并可能影响其他项目。默认情况下，项目同时运行，因此不要依赖执行顺序。
* 资源范围内的语义回忆可以将资源之前的对话呈现给实验，并且实验记录可以在该资源的后续对话中被回忆起来。

使用此方法根据真实用户积累的上下文来评估Agent。为了防止实验运行接触真实的用户状态，请改用专用的评估资源 ID。

在以下情况下会跳过线程注入：

* 如果请求上下文设置`MASTRA_THREAD_ID_KEY`, the runner uses that thread as-is. Items and retries using the same thread id share a conversation.
* 如果Agent没有内存，或者请求上下文显式地将资源 id 设置为空字符串或`null`, the runner skips thread injection.

### 注册Workflow程 {/* #registered-workflow */}

指向在您的 Mastra 实例上注册的Workflow程：

```typescript title="src/mastra/experiments/workflow-target.ts"
const summary = await dataset.startExperiment({
  name: 'workflow-eval',
  targetType: 'workflow',
  targetId: 'translation-workflow',
  scorers: ['accuracy'],
})
```

Workflow程接收每个项目的`input` as `inputData` in `run.start()`. Structure the input to match the workflow's input schema.

### 注册得分手 {/* #registered-scorer */}

以记分员为目标来评价裁判本身。跑步者呼叫`scorer.run(item.input)`, so the dataset item's `input` must contain the full payload the scorer expects.

此示例假设已注册`accuracy` scorer that accepts string `input`, `output`, and `groundTruth` fields. Adapt those fields to your scorer's expected shape:

```typescript title="src/mastra/experiments/scorer-target.ts"
await dataset.addItem({
  input: {
    input: 'What is the capital of France?',
    output: 'Paris',
    groundTruth: 'Paris',
  },
  groundTruth: { score: 1 },
})

const summary = await dataset.startExperiment({
  name: 'judge-accuracy-eval',
  targetType: 'scorer',
  targetId: 'accuracy',
})
```

两人`groundTruth` fields serve different purposes:

* `input.groundTruth`是传递给法官的参考答案：`'Paris'`.
* 顶层`groundTruth` is the expected result from the judge: `{ score: 1 }`. It isn't passed to the target scorer.

目标的输出包含其`score` and `reason`. To evaluate that output against the top-level ground truth, add another scorer through the experiment's `scorers` option. Without an additional scorer, the experiment records the judge's output but doesn't score its agreement with the expected result.

## 选择每个项目的评分者 {/* #select-scorers-per-item */}

将注册的记分器 ID 添加到数据集项目以覆盖附加到其数据集的记分器：

```typescript title="src/mastra/datasets/items.ts"
await dataset.addItem({
  input: 'Translate "hello" to French.',
  scorerIds: ['accuracy', 'fluency'],
})
```

实验对每个项目仅使用一个评分器源，按以下顺序：

1. 实验的`scorers` option, when provided
2. 该项目的`scorerIds` field, when provided
3. 数据集的`scorerIds` field
4. 没有得分手

Mastra 不会合并这些来源。运行或项目级别的显式空数组不会选择任何记分器并防止回退到下一个源。空的分类运行级别配置具有相同的效果。重复的项目或数据集 ID 按照首次出现的顺序运行一次。

以下更新在显式空覆盖和数据集继承之间切换：

```typescript title="src/mastra/datasets/items.ts"
// Run no scorers for this item
await dataset.updateItem({
  itemId: 'translation-item-id',
  scorerIds: [],
})

// Remove the item override and inherit the dataset's scorers
await dataset.updateItem({
  itemId: 'translation-item-id',
  scorerIds: null,
})
```

省略`scorerIds` from an update preserves its current value. Each item version stores its scorer ID list, including an empty list. Scorer definitions aren't copied into the item version and continue to use their existing registry or Editor behavior.

Mastra 在运行其目标之前解析每个项目的记分器 ID。它首先检查注册的记分器，然后要求编辑器补充存储的记分器。过时的项目级 ID 会产生`EXPERIMENT_ITEM_SCORER_NOT_FOUND` code for that item. Mastra skips target execution without retrying that item, while the rest of the experiment continues.

所选运行级别或数据集级别源中缺少 ID 会导致实验设置失败。 Mastra 不会解析来自优先级规则忽略的较低优先级源的 ID。

Workflow程步骤评分器只能通过运行级别分类来使用`scorers` configuration. Item-level IDs apply to the flat agent, workflow, and trajectory scorer dispatch.

## 控制每次运行的持久性 {/* #control-persistence-per-run */}

使用`persistence` to skip storage writes for a specific run. Experiment records and score records can be disabled independently:

```typescript title="src/mastra/experiments/no-persistence.ts"
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'translation-agent',
  scorers: ['accuracy'],
  persistence: {
    experiments: 'none',
    scores: 'none',
  },
})
```

目标和得分手仍在奔跑，并且`startExperiment()` still returns the item results and scores in `summary`. The settings are independent. For example, set only `scores: 'none'` to persist the experiment and its item results without creating score records.

省略的设置默认为`'default'`, which preserves the standard storage behavior. This policy only controls experiment and score records created by the run. It doesn't disable storage used by the target, such as agent memory, vectors, observability, or custom tool storage.

什么时候`startExperimentAsync()` runs with `experiments: 'none'`, it doesn't persist an experiment record, progress updates, or item results. Score persistence remains controlled separately by `persistence.scores`. Without an experiment event observer, the run is fire-and-forget, and the experiment API can't report whether it completed or failed.

使用同步`startExperiment()` when the caller needs the returned summary. An experiment event observer can receive lifecycle events and the terminal summary.

## 观察实验事件 {/* #observe-experiment-events */}

使用`onEvent` to receive versioned, JSON-safe lifecycle events while an experiment runs. This works with `startExperiment()`, `startExperimentAsync()`, and `runExperiment()`.

```typescript title="src/mastra/experiments/observe.ts"
import type { ExperimentEvent } from '@mastra/core/datasets'

const events: ExperimentEvent[] = []

await dataset.startExperimentAsync({
  task: async ({ input }) => processItem(input),
  persistence: { experiments: 'none' },
  onEvent: async event => {
    events.push(event)
    await publishEvent(event)
  },
})
```

观察者接收这些事件类型：

* `experiment.run.started`：标识运行、目标、解析的数据集版本和项目计数。
* `experiment.item.completed`：评分后报告提交的项目结果，包括分数、错误、重试次数、Tool模拟详细信息和稳定项目标识。
* `experiment.run.finished`：报告最终结果和摘要计数器。

Mastra 在传递下一个事件之前等待每个观察者的调用。这种串行交付施加背压并确保事件`sequence` values match delivery order, while item execution can remain concurrent.

如果观察者抛出或拒绝，Mastra 将中止剩余的运行并拒绝`runExperiment()` with a `MastraError` whose `id` is `EXPERIMENT_EVENT_OBSERVER_FAILED`. It doesn't send a terminal event through the failed observer. For `startExperimentAsync()`, the method has already returned when a detached observer fails, so handle delivery failures inside the observer when the caller needs direct error reporting.

这`experiment.run.finished` event is awaited before Mastra persists the final experiment status. Treat the event as the authoritative terminal signal when experiment persistence is disabled, but don't use it as a read-after-write signal for storage.

导出的事件类型是`ExperimentEvent`, `ExperimentRunStartedEvent`, `ExperimentItemCompletedEvent`, and `ExperimentRunFinishedEvent`. Use the discriminated `type` field to narrow an event before reading event-specific properties.

## 生命周期挂钩 {/* #lifecycle-hooks */}

使用生命周期挂钩在目标运行之前准备状态并在运行后清理它。当无法针对空环境评估项目时，这非常有用。运行可能需要将固定文件复制到Agent的Workspace中，或者在Agent可以接触它之前配置Sandbox。

钩子在两个级别上运行。`beforeAll` and `afterAll` run once per experiment, and `beforeEach` and `afterEach` run once per item:

```typescript title="src/mastra/experiments/hooks.ts"
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'document-agent',
  scorers: ['accuracy'],
  beforeAll: async ({ experimentId }) => {
    await createWorkspace(experimentId)
  },
  beforeEach: async ({ item }) => {
    await copyFixture(item.metadata?.fixture)
  },
  afterEach: async ({ item, result }) => {
    await clearWorkspaceFiles(item.id)
  },
  afterAll: async ({ summary }) => {
    await deleteWorkspace(summary.experimentId)
  },
})
```

每个钩子都可以是异步的。每一位都收到`experimentId`, the `mastra` instance, and the run-level `signal`, so long-running setup can be cancelled along with the experiment. The per-item hooks also receive `item`. The teardown hooks receive the result they follow: `afterEach` receives the item's `result` including scores, and `afterAll` receives the `summary` that's about to be returned.

传递给钩子的项目暴露`id`, `input`, `groundTruth`, and `metadata`. Fields that control execution, such as tool mocks and scorer selection, aren't exposed, so a hook can't change how the item runs.

### 吊钩故障 {/* #hook-failures */}

每个钩子在抛出时都会产生不同的结果，具体取决于运行对它的依赖程度：

|钩|失败时 |
| - | - |
|`beforeAll` | Fails the experiment. No items run. |
| `beforeEach` | Fails that item with `EXPERIMENT_ITEM_BEFORE_EACH_FAILED`. Other items continue. |
| `afterEach` | Logged. The item's recorded outcome doesn't change. |
| `afterAll` | Logged. The returned summary doesn't change. |

什么时候`beforeAll` fails, the experiment is marked failed and the `experiment.run.finished` event is still emitted before the error propagates.

什么时候`beforeEach` fails, the target and its scorers are skipped for that item, since the item's preconditions were never met. `afterEach` is also skipped for that item, on the basis that setup which didn't finish owns its own cleanup.

拆卸失败会被记录而不是传播。到......的时候`afterEach` runs, the target has already produced a real result, and discarding it because cleanup was untidy would lose the data the experiment was run to collect.

`afterAll`在每个退出路径上运行，包括实验失败时、`beforeAll` fails, and when an [event observer](#observe-experiment-events) fails, so teardown isn't skipped when something goes wrong. It runs at most once per experiment.

## Tool模拟 {/* #tool-mocks */}

当实验运行调用副作用Tool的Agent时，请将静态Tool模拟附加到各个数据集项目以使运行具有确定性。在实验期间，模拟Tool返回其声明的输出而不是执行。默认情况下，没有对项目进行模拟的Tool会实时运行。

模拟与数据集项一起存储和版本化。每个模拟指定Tool名称和预期参数，以及要返回的输出：

```typescript title="src/mastra/experiments/tool-mocks.ts"
await dataset.addItem({
  input: 'What is the weather in Seattle?',
  toolMocks: [
    {
      toolName: 'getWeather',
      args: { city: 'Seattle' },
      output: { temperature: 60, conditions: 'rainy' },
    },
  ],
})
```

支持Tool模拟`agent` targets only.

### 阻止未声明的Tool {/* #block-undeclared-tools */}

放`unmockedToolPolicy: 'deny'` on an experiment to block every tool call that doesn't have a mock. This is useful when a live call could cause side effects:

```typescript
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'weather-agent',
  unmockedToolPolicy: 'deny',
})
```

默认策略是`'allow'`. You can override the experiment policy on an individual stored or inline item:

```typescript
await dataset.addItem({
  input: 'What is the weather in Seattle?',
  unmockedToolPolicy: 'allow',
})
```

项目值优先于实验值。被拒绝的呼叫失败`TOOL_MOCK_NOT_DECLARED` before the tool executes. The failure isn't retried or added to `liveCalls`.

### 匹配与消费 {/* #matching-and-consumption */}

参数严格匹配：对象键顺序被忽略，但数组顺序很重要。值不会被强制转换为其他类型。仅当Agent使用深度等于模拟的参数调用Tool时，才会提供模拟`args`.

当一个项目为相同的Tool和参数声明多个模拟时，它们会按顺序使用，第一个调用获取第一个模拟，下一个调用获取第二个模拟，依此类推。订单跟踪按`(toolName, args)` group and is independent across different arguments.

### 匹配方式 {/* #matching-mode */}

默认情况下，每个模拟严格匹配其`args`. Set `matchArgs: 'ignore'` to match on the tool name only, the mock's `args` aren't compared and the next unconsumed mock for that tool is served regardless of how the agent called it:

```typescript
const subAgentMock = {
  toolName: 'agent-balanceAgent',
  args: { prompt: 'look up the balance for YJ' },
  output: { text: "YJ's balance is $100." },
  matchArgs: 'ignore',
}
```

当Tool的参数有噪声或由模型生成时，这非常有用。最常见的情况是嘲笑**sub-agent's response**. The parent sees a delegated sub-agent as an `agent-<name>` tool, and its arguments include an LLM-authored `prompt` plus runtime-injected fields. Mocking `agent-<name>` returns the canned response in place of running the sub-agent and its inner tools. When you create a mock from a trace, sub-agent delegation calls are derived with `matchArgs: 'ignore'` automatically. You can change it to `'strict'` to pin the exact arguments.

### 失败 {/* #failures */}

当Tool调用违反模拟配置时，该项目将失败：

* `TOOL_MOCK_MISMATCH`：调用该Tool时使用的参数没有模拟匹配。
* `TOOL_MOCK_EXHAUSTED`：每个匹配的模拟都已被消耗。
* `TOOL_MOCK_NOT_DECLARED`：该Tool没有模拟并且有效`unmockedToolPolicy` is `'deny'`.

如果发生任何这些故障，Agent运行都会立即中止，因此模型无法继续调用任何其他Tool，包括原本会实时运行的未模拟的副作用Tool。这些失败是确定性的，因此不会重试。已声明但从未使用过的模拟不会使该项目失败，它们会被报告为未使用。

当模拟拦截处于活动状态时，Agent的Tool会按顺序执行，如此重复`(toolName, args)` mocks are consumed in the provider's call order. Interception is active when the item declares mocks or its effective `unmockedToolPolicy` is `'deny'`.

### 诊断 {/* #diagnostics */}

每个项目结果包括一个`toolMockReport` listing which mocks were used and which tool calls ran without a mock:

```typescript
for (const item of summary.results) {
  const report = item.toolMockReport
  if (!report) continue

  console.log(report.served) // mocks matched and returned
  console.log(report.unconsumed) // mocks declared but never used
  console.log(report.liveCalls) // undeclared tools allowed to run live
  console.log(report.failure) // the first deterministic mock failure, if any
}
```

在[Studio](/docs/studio/overview), edit a dataset item to author tool mocks as a JSON array, and open an experiment result to see the same report.

### 局限性 {/* #limitations */}

* **模拟的Tool跨度是平坦的。**&#x4E00;个已服务的模拟记录了一个`tool_call` span with the mocked output and the attribute `mocked: true`. A mismatched or exhausted mock records one with `success: false`. The real tool never runs, so the span has no child spans and no `toolDescription`.
* **存储支持。**&#x4C;ibSQL、PostgreSQL、MongoDB 和 Spanner 适配器会保留Tool模拟和Tool模拟报告，而 MySQL 适配器会拒绝携带其中任何一种的写入。所有数据集存储适配器均保留`unmockedToolPolicy`.

## 异步实验 {/* #async-experiments */}

`startExperiment()`阻塞直到每个项目完成。对于长时间运行的数据集，请使用[`startExperimentAsync()`](/reference/datasets/startExperimentAsync) to start the experiment in the background:

```typescript title="src/mastra/experiments/async.ts"
const { experimentId, status } = await dataset.startExperimentAsync({
  name: 'large-dataset-run',
  targetType: 'agent',
  targetId: 'translation-agent',
  scorers: ['accuracy'],
})

console.log(experimentId) // UUID
console.log(status) // 'pending'
```

使用轮询完成[`getExperiment()`](/reference/datasets/getExperiment):

```typescript
let experiment = await dataset.getExperiment({ experimentId })
if (!experiment) throw new Error('Experiment not found')

while (experiment.status === 'pending' || experiment.status === 'running') {
  await new Promise(resolve => setTimeout(resolve, 5000))
  experiment = await dataset.getExperiment({ experimentId })
  if (!experiment) throw new Error('Experiment not found')
}

console.log(experiment.status) // 'completed' | 'failed'
```

## 调用者驱动的实验 {/* #caller-driven-experiments */}

`startExperiment()`让马斯特拉负责整个跑步过程。如果持久编排器（例如 Temporal、Airflow 或自定义工作队列）拥有循环，请首先创建实验并以以下形状之一自行驱动：

* **调用者驱动循环，Mastra 运行每个项目。**&#x4F7F;用目标创建实验，然后调用[`runExperimentItem()`](/reference/datasets/runExperimentItem) once per item. Mastra executes the target and runs the scorers, then persists the result.
* **调用者运行一切。**&#x521B;建没有目标的实验，在您自己的基础设施上执行项目并对其进行评分，并使用以下命令获取每个结果[`submitExperimentResult()`](/reference/datasets/submitExperimentResult).

两种形状均以[`finalizeExperiment()`](/reference/datasets/finalizeExperiment), and both write to the same tables as native runs, so Studio views, comparisons, and review summaries work unchanged.

### 在服务器端运行项目 {/* #run-items-server-side */}

创建实验[`createExperiment()`](/reference/datasets/createExperiment), passing the target and scorers. Pass your own `id` (for example a workflow run id) to make creation idempotent: retrying the call with the same id returns the existing experiment instead of failing.

```typescript title="src/mastra/experiments/caller-driven.ts"
const dataset = await mastra.datasets.get({ id: 'translation-dataset-id' })

const { experimentId, totalItems, datasetVersion } = await dataset.createExperiment({
  id: 'temporal-wf-run-42', // optional: reuse your workflow run id for idempotent creates
  targetType: 'agent',
  targetId: 'translation-agent',
  scorers: ['accuracy'],
})
```

然后从您的协调器运行每个项目。 Mastra 解析固定数据集版本的项目，并使用解析的记分器执行目标。结果更新插入的关键字为`(experimentId, itemId, attempt)`. A retried activity converges on a single row:

```typescript
const { result, scores } = await dataset.runExperimentItem({
  experimentId,
  itemId: 'item-1',
})
```

重试和超时属于您的协调器：每个`runExperimentItem` call executes the item exactly once. Scorers resolve with the same precedence as native runs: experiment `scorers` win over item `scorerIds`, which win over dataset `scorerIds`.

### 摄取外部结果 {/* #ingest-external-results */}

如果您的工作人员自己执行项目并对其进行评分，请创建没有目标的实验：

```typescript title="src/mastra/experiments/ingestion.ts"
const { experimentId } = await dataset.createExperiment({
  id: 'temporal-wf-run-42',
  name: 'external-eval',
})
```

每项提交一个结果[`submitExperimentResult()`](/reference/datasets/submitExperimentResult). Submissions are upserts keyed by `(experimentId, itemId, attempt)`. A retried worker converges on a single row instead of duplicating results:

```typescript
await dataset.submitExperimentResult({
  experimentId,
  itemId: 'item-1',
  output: { translation: 'Hola' },
  scores: [{ scorerId: 'accuracy', score: 0.92, reason: 'Faithful translation' }],
})
```

`input`和`groundTruth` default to the dataset item's values at the experiment's pinned dataset version. Inline `scores` are persisted to the scores store under the experiment, so they show up in comparisons alongside native scorer runs. Experiments created with a target reject `submitExperimentResult` so two writers can't race on the same rows.

### 最终确定 {/* #finalize */}

当所有项目完成后，致电[`finalizeExperiment()`](/reference/datasets/finalizeExperiment). Mastra computes `succeededCount`, `failedCount`, and `skippedCount` from the persisted rows, so your workers never track completion bookkeeping. Finalization is idempotent. Calling it again returns the stored record:

```typescript
const experiment = await dataset.finalizeExperiment({ experimentId })

console.log(experiment.status) // 'completed'
console.log(experiment.succeededCount) // items with at least one attempt that didn't error
console.log(experiment.failedCount) // items where every attempt errored
console.log(experiment.skippedCount) // items never submitted
```

通过 HTTP 可以获得相同的生命周期（`POST /api/datasets/:datasetId/experiments` with `start: false`, `POST .../experiments/:experimentId/items/:itemId/run`, `POST .../experiments/:experimentId/results`, `POST .../experiments/:experimentId/finalize`, see [Server routes](/reference/server/routes#datasets-and-experiments)) and through `@mastra/client-js` (see the [Datasets API](/reference/client-js/datasets)).

### 重试和幂等合约 {/* #retry-and-idempotency-contract */}

调用者驱动的调用被设计为主动重试（例如通过临时重试策略）。具体保证：

* **Create 是幂等的`id`.**&#x547C;唤`createExperiment` again with the same caller-supplied `id` returns the existing experiment. Reusing an `id` that belongs to another dataset or an experiment with a different target fails with `EXPERIMENT_ID_CONFLICT` (HTTP `409`).
* **结果更新插入于`(experimentId, itemId, attempt)`.**&#x91CD;新提交相同的键会更新现有行，并且所有可变字段的最后一次写入都会获胜。重试的工作人员永远不会创建重复项。
* **`attempt`将故意试验与重试分开。**&#x91CD;试相同的运行应该重用相同的`attempt` (default `0`) so they converge. To record repeated trials of an item as separate rows, submit with `attempt: 0`, `attempt: 1`, and so on.
* **数据集版本在创建时固定。**&#x63D0;交内容将根据该版本中可见的项目进行验证，因此之后编辑或删除项目不会影响正在进行的实验。提交一份`itemId` that isn't visible at the pinned version fails with `404`.
* **Finalize 是幂等的且是终结的。**&#x5B8C;成已完成的实验将返回存储的记录，而无需重新计算。最终确定后，进一步的提交将被拒绝`EXPERIMENT_ALREADY_FINALIZED` (HTTP `409`).
* **计数是服务器计算的并且按项目计算。**&#x5728;最终确定时，Mastra 会汇总每个项目的尝试次数：`succeededCount` (at least one attempt without an error), `failedCount` (every attempt errored), `skippedCount` (never submitted). `succeededCount + failedCount + skippedCount === totalItems` always holds, and callers keep no completion bookkeeping. Attempt-level rows remain available via `listExperimentResults`.

## 配置选项 {/* #configuration-options */}

### 并发性 {/* #concurrency */}

控制并行运行的项目数（默认值：5）：

```typescript
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'translation-agent',
  maxConcurrency: 10,
})
```

### 超时和重试 {/* #timeouts-and-retries */}

设置每个项目的超时（以毫秒为单位）和重试计数：

```typescript
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'translation-agent',
  itemTimeout: 30_000, // 30 seconds per item
  maxRetries: 2, // retry failed items up to 2 times
})
```

重试使用指数退避。中止错误永远不会重试。

### 中止实验 {/* #aborting-an-experiment */}

通过一个`AbortSignal` to cancel a running experiment:

```typescript
const controller = new AbortController()

// Cancel after 60 seconds
setTimeout(() => controller.abort(), 60_000)

const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'translation-agent',
  signal: controller.signal,
})
```

其余项目在摘要中标记为已跳过。

### 固定数据集版本 {/* #pinning-a-dataset-version */}

针对数据集的特定快照运行：

```typescript
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'translation-agent',
  version: 3, // use items from dataset version 3
})
```
