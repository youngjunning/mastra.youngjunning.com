# 多Agent系统

多Agent系统将任务分配给多个Agent，而不是要求一个Agent完成所有事情。在 Mastra 中，这通常意味着将Agent、Workflow程或两者结合起来，以便系统的每个部分都有明确的角色。

目标是将正确的上下文、Tool和职责分配给正确的组件。当这种划分清晰时，多智能体系统比一个背负着长提示和太多Tool或职责的智能体系统更容易推理。

## 何时使用多Agent系统 {/* #when-to-use-multi-agent-systems */}

当一个Agent不再是工作的良好边界时，请使用多Agent系统。

这种情况经常出现在以下情况：

* 任务涵盖不同类型的工作，例如研究、规划、写作或评论。
* 一个Agent需要太多的上下文或太多的Tool。
* 任务的各个部分应该并行运行。
* 不同的阶段需要不同的提示、模型或护栏。
* 您希望路由、执行和综合之间有清晰的界限。

尽可能从一名Agent开始。当添加的结构明显提高质量、速度或可靠性时，添加更多Agent。

当系统需要一种清晰的方式来跨组件划分上下文、决策和职责时，多Agent模式非常有用。在实践中，关键的设计问题是随着任务的进展哪个组件保持控制。

## 交接 {/* #handoffs */}

切换模式将控制权从一个Agent转移到另一个Agent。与主管模式不同，第一个Agent不会负责整个任务。相反，活跃的专家掌控了交互的下一部分。

当下一位专家应该直接继续交互而不是通过中央协调员报告时，请使用交接。权衡是上下文管理变得更加重要，因为系统必须决定下一个Agent继承什么以及保留什么范围。

在 Mastra 中，通过组合来实现此模式[agents](/docs/agents/overview), [workflows](/docs/workflows/overview), and [memory](/docs/memory/overview). A workflow can route the task, but the defining feature of the pattern is that ownership moves to the next agent.

## Workflow程 {/* #workflows */}

Workflow模式定义了代码中的执行路径。您无需要求Agent决定接下来会发生什么，而是通过步骤、分支、循环和并行块来定义序列。

当任务被很好地理解并且执行路径预先已知时，使用Workflow。主要优点是可预测性：显式结构使系统更易于调试和审计。代价是灵活性，因为当任务随着展开而发生变化时，Workflow程的适应性较差。

在马斯特拉，[workflows](/docs/workflows/overview) can implement coordination patterns such as handoffs and councils. A workflow is distinct because its control logic lives in the workflow itself, regardless of which agents it calls.

## 监事 {/* #supervisors */}

主管模式让一名首席Agent控制整个任务。主管决定何时委派、呼叫哪位专家、传递什么上下文以及如何组合结果。

当任务是开放式的并且事先不知道完整的序列时，请使用此模式。例如，一项研究任务可能需要根据早期步骤发现的内容进行不同的调查。主管可以随着任务的展开进行调整。
权衡是主管成为主要协调点。这使得模式变得灵活，但也意味着结果在很大程度上取决于良好的委派行为和明确的子Agent边界。

在 Mastra 中，这种模式直接映射到[supervisor agents](/docs/subagents). A supervisor defines subagents through the `agents` property, then coordinates them with `stream()` or `generate()`. Mastra helps control this pattern through delegation hooks and message filtering, with memory isolation between agents.

## 理事会 {/* #council */}

理事会模式要求多个Agent独立解决同一问题，然后比较或综合他们的输出，形成一个最终答案。与将问题分成几个部分的主管不同，理事会使问题保持​​共享，并对同一问题提出多种观点。

当问题不明确、评估性或高风险并且答案质量比速度更重要时，请使用此模式。权衡是成本，因为理事会故意重复工作，并且通常比其他模式花费更长的时间并使用更多的代币。

Mastra 不提供专用的议会原语。在 Mastra 中，使用以下命令实现此模式[agents](/docs/agents/overview) and [workflows](/docs/workflows/overview): Run multiple agents in parallel and collect their outputs. Then add a final synthesis or review step. Workflow control flow methods such as `.parallel()` provide the structure for this pattern.

## 选择图案 {/* #choosing-a-pattern */}

这些模式的主要区别在于它们如何分配控制权：

|图案|谁能掌控一切 |使用时 |权衡|马斯特拉实施 |
| - | - | - | - | - |
|交接 |现任专家|所有权应在专家之间转移|上下文迁移变得更加重要 |具有Workflow程和内存的Agent |
|Workflow程 |执行图 |路径是预先知道的 |任务变化时适应性较差 |[Workflows](/docs/workflows/overview) |
| Supervisor agents | One lead agent | Delegation must adapt during execution | Results depend on good coordination and clear boundaries | [Supervisor agents](/docs/subagents) |
| Council | Final synthesis step | The task needs multiple independent perspectives | Higher cost and latency | Agents with workflow parallelism |

在实践中，这些模式经常组合在一起：

* Workflow程可以包含一个或多个主管驱动的步骤。
* 切换流程可以从路由Workflow程开始。
* 委员会可以在Workflow程中运行并进入最终批准步骤。
* 主管可以将具有固定内部结构的任务委托给Workflow程。

根据协调问题而不是任务标签选择模式。
