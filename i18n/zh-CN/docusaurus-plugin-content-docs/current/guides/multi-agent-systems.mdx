# 多 Agent 系统

多 Agent 系统把任务分配给多个 Agent。在 Mastra 中，通常会组合多个 Agent、多个 Workflow 或两者，使系统各部分各司其职。

目标是将正确的上下文、Tool和职责分配给正确的组件。当这种划分清晰时，多智能体系统比一个背负着长提示和太多Tool或职责的智能体系统更容易推理。

## 何时使用多Agent系统 {/* #when-to-use-multi-agent-systems */}

单个 Agent 已不适合承担整项任务时，可以采用多 Agent 系统。

这种情况经常出现在以下情况：

* 任务涵盖不同类型的工作，例如研究、规划、写作或评论。
* 一个Agent需要太多的上下文或太多的Tool。
* 任务的各个部分应该并行运行。
* 不同的阶段需要不同的提示、模型或护栏。
* 您希望路由、执行和综合之间有清晰的界限。

尽可能从一名Agent开始。当添加的结构明显提高质量、速度或可靠性时，添加更多Agent。

当系统需要明确划分各组件的上下文、决策和职责时，多 Agent 模式很有用。设计时的关键问题是：任务推进到各个阶段时，由哪个组件掌握控制权？

## 交接 {/* #handoffs */}

切换模式将控制权从一个Agent转移到另一个Agent。与主管模式不同，第一个Agent不会负责整个任务。相反，活跃的专家掌控了交互的下一部分。

当下一位专家应该直接继续交互而不是通过中央协调员报告时，请使用交接。权衡是上下文管理变得更加重要，因为系统必须决定下一个Agent继承什么以及保留什么范围。

在 Mastra 中，可以组合 [Agent](/docs/agents/overview)、[Workflow](/docs/workflows/overview) 和 [Memory](/docs/memory/overview) 实现交接。Workflow 可以负责路由，但交接的关键是后续工作由下一个 Agent 接手。

## Workflow {/* #workflows */}

Workflow模式定义了代码中的执行路径。您无需要求Agent决定接下来会发生什么，而是通过步骤、分支、循环和并行块来定义序列。

当任务被很好地理解并且执行路径预先已知时，使用Workflow。主要优点是可预测性：显式结构使系统更易于调试和审计。代价是灵活性，因为当任务随着展开而发生变化时，Workflow程的适应性较差。

Mastra 的 [Workflow](/docs/workflows/overview) 可以实现交接和协同评议等协调模式。无论调用哪些 Agent，Workflow 的控制逻辑都由自身定义。

## 主管模式 {/* #supervisors */}

主管模式让一名首席Agent控制整个任务。主管决定何时委派、呼叫哪位专家、传递什么上下文以及如何组合结果。

当任务是开放式的并且事先不知道完整的序列时，请使用此模式。例如，一项研究任务可能需要根据早期步骤发现的内容进行不同的调查。主管可以随着任务的展开进行调整。
权衡是主管成为主要协调点。这使得模式变得灵活，但也意味着结果在很大程度上取决于良好的委派行为和明确的子Agent边界。

在 Mastra 中，这种模式对应[主管 Agent](/docs/subagents)。主管 Agent 通过 `agents` 属性定义子 Agent，再用 `stream()` 或 `generate()` 协调它们。Mastra 提供委派钩子和消息过滤功能，并隔离各 Agent 的 Memory。

:::tip

参阅[主管 Agent 教程](https://mastra.ai/blog/build-a-research-coordinator-with-supervisor-agents)，按步骤操作。

:::

## 协同评议 {/* #council */}

协同评议让多个 Agent 独立处理同一个问题，再比较或综合输出，形成最终答案。主管模式会拆分问题，协同评议则让多个 Agent 从不同角度处理同一个问题。

问题含糊、需要权衡判断或事关重大，且答案质量比速度更重要时，可以采用协同评议。代价是多个 Agent 会有意重复工作，通常比其他模式耗时更长、消耗更多 Token。

Mastra 没有专用的协同评议原语。可以用 [Agent](/docs/agents/overview) 和 [Workflow](/docs/workflows/overview) 实现：并行运行多个 Agent 并收集输出，然后增加最终的综合或审查步骤。`.parallel()` 等 Workflow 控制流方法可以组织这些步骤。

## 选择协调模式 {/* #choosing-a-pattern */}

这些模式的主要区别在于它们如何分配控制权：

| 模式 | 谁掌握控制权 | 适用情形 | 取舍 | 在 Mastra 中的实现 |
| - | - | - | - | - |
| 交接 | 当前负责的专家 Agent | 需要在专家 Agent 之间转交任务 | 更依赖上下文传递 | 结合 Agent、Workflow 和 Memory |
| Workflow | 执行图 | 预先知道执行路径 | 任务变化时灵活性较低 | [Workflow](/docs/workflows/overview) |
| Supervisor agents | One lead agent | Delegation must adapt during execution | Results depend on good coordination and clear boundaries | [Supervisor agents](/docs/subagents) |
| Council | Final synthesis step | The task needs multiple independent perspectives | Higher cost and latency | Agents with workflow parallelism |

在实践中，这些模式经常组合在一起：

* Workflow程可以包含一个或多个主管驱动的步骤。
* 切换流程可以从路由Workflow程开始。
- 可在 Workflow 中执行协同评议，再将结果交给最终审批步骤。
* 主管可以将具有固定内部结构的任务委托给Workflow程。

根据协调问题而不是任务标签选择模式。
