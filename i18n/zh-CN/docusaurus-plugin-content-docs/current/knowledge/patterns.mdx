# 用 Knowledge 构建应用

以下模式说明如何用 Knowledge 构建应用。每个示例都会交代各 Agent 的职责、各 scope 存放的内容，以及所需配置或工具调用。Knowledge 本身没有内置的 scope 类型。只有 `resource:` 和 `thread:` 来自 Memory，[`knowledgeMemoryScopes()`](/reference/knowledge/knowledge-memory-scopes) 会声明这两种 scope，并额外声明一个租户 scope。

:::alpha

Knowledge 目前处于 alpha 阶段，API 可能随版本变化。

:::

:::warning

每次调用工具都会检查访问权限，但 Knowledge 目前还无法保证数据始终只流向持有相应 scope 的运行，也无法保证 Agent 不会跨 scope 复述内容。以下示例展示的是设计用途，现阶段请勿依赖 Knowledge 隔离敏感数据。

:::

## 根据自己的文档回答问题 {/* #answer-from-your-own-docs */}

服务器用 [`upsertPage()`](/docs/knowledge/load-your-content) 将文档同步到 `product-docs:` scope，并只为文档 Agent 提供读取工具。Agent 会列出页面树，从长页面中读取匹配的行，搜索无结果时则明确回答不知道。

```typescript
const knowledge = new Knowledge({
  id: 'docs',
  storage,
  tools: { read: true },
  scopes: {
    ...knowledgeMemoryScopes({ org: 'workspace:$workspaceId' }),
    'product-docs:$workspaceId': {
      belongsTo: 'workspace:$workspaceId',
      access: [{ principal: 'workspace:$workspaceId', role: 'viewer' }],
    },
  },
})
```

要回答关于某个地区的问题，Agent 会请求匹配的行及每处匹配前后各一行。

```json
{ "page": "product-docs:initech#billing/refunds", "match": "region 42", "context": 1 }
```

## 一个 Agent 服务多个客户 {/* #one-agent-many-customers */}

一个支持 Agent 服务所有客户。每个客户的页面都存放在各自的 `tenant:` scope 中，由 `knowledgeMemoryScopes()` 声明为租户 scope。

```typescript oxfmt:false
scopes: { ...knowledgeMemoryScopes({ org: 'tenant:$tenantId' }) },
```

服务器运行 Agent 时，传入客户的 scope，以及用户和会话对应的 scope。

```typescript
await agent.generate(message, {
  scopes: ['tenant:globex', `resource:${userId}`, `thread:${threadId}`],
})
```

Globex 用户搜索“续约”时不会看到 `tenant:acme#renewals`，因为该次运行没有持有 `tenant:acme`。这与提示词无关。如果 Agent 配置了 Memory，`resource:` 和 `thread:` scope 还会告诉 Memory 这次运行属于哪个用户和 Thread。可用 [`explainAccess()`](/docs/knowledge/scopes-and-access#test-access-with-explainaccess) 测试规则。如页首警告所述，Knowledge 目前无法保证这种隔离，请勿依赖它保护敏感的客户数据。

## 所有 Agent 都必须遵守的政策 {/* #a-policy-every-agent-follows */}

合规团队负责制定各账户的数据处理规则。为该账户工作的销售、客服或账务 Agent 都需要在每一轮看到这些规则，无需等到主动搜索才发现。只有合规团队可以修改规则。

在账户的 scope 中声明页面，并在配置中固定它。只有 `Knowledge` 实例设置了 `pinnedContext: true`，且 Agent 配置了 Memory，固定的内容才会进入该次运行。以下所有固定示例均采用这两个设置。

```typescript oxfmt:false
'account:$accountId': {
  access: [
    { principal: 'self', role: 'viewer' },
    { principal: 'desk:$accountId:compliance', role: 'editor' },
  ],
  pages: [{ key: 'data-handling', name: 'Data handling rules' }],
  pinnedContext: ['account:$accountId#data-handling'],
},
```

合规团队写好页面后，持有 `account:umbrella` 的每次运行都会在开始时将该页面载入上下文。合规团队编辑页面时，已经在运行的 Agent 会在下一轮只收到变更内容。

以下规则保护合规团队配置的政策。

* **Agent 可以读取政策，但无法修改。** 该账户的运行只拥有查看权限。因此，销售 Agent 尝试编辑页面时会被拒绝。
* **Agent 无法取消固定。** 配置中的固定项由声明决定，不在存储中，因此固定工具无法移除它。
* **页面无法移动或删除。** 在 `pages` 中声明的页面归配置管理。
* **只有能读取页面的运行才会收到它。** 其他账户的运行不会收到该页面。固定页面不会扩大其可读范围。

参见 [固定上下文](/docs/knowledge/pinned-context)。

## 跨会话沿用编码约定 {/* #coding-conventions-that-carry-over */}

开发者的编码 Agent 按代码仓库共享 scope。固定编码约定页面，将决策作为笔记添加到该页面，并在笔记中链接到相关页面。

```typescript oxfmt:false
'repo:$repo': {
  access: [{ principal: 'self', role: 'editor' }],
  pages: [{ key: 'conventions', name: 'Conventions' }, { key: 'tooling', name: 'Tooling' }],
  pinnedContext: ['repo:$repo#conventions'],
},
```

例如，Agent 在约定页面添加一条“使用 pnpm workspaces，不用 npm”的笔记，并用 `[[repo:api#tooling]]` 链接到相关页面。

在 `repo:api` 中开启的下一次会话会看到编码约定，旁边标有“1 条笔记”。在 `repo:web` 中的会话看不到这些内容。

## 根据值班经验改进运维手册 {/* #runbooks-that-improve-on-call */}

值班工程师是所属服务 scope 的贡献者。他们的 Agent 可以在固定的运维手册上添加笔记，但无法改写手册。SRE 负责人拥有编辑权限，可以将笔记中的内容整合进手册。

```typescript oxfmt:false
'oncall:$orgId:$service': {
  belongsTo: 'org:$orgId',
  access: [
    { principal: 'self', role: 'contributor' },
    { principal: 'role:$orgId:sre-lead', role: 'editor' },
  ],
  pages: [{ key: 'runbook', name: 'Incident runbook' }],
  pinnedContext: ['oncall:$orgId:$service#runbook'],
},
```

值班 Agent 只有贡献者权限，尝试编辑页面时会被拒绝，但仍可添加笔记。

## 像文件夹一样组织页面 {/* #organize-pages-like-folders */}

页面可以在 scope 内嵌套。比如在手册中声明 `refunds` 页面，并将 `damaged-items` 设为其子页面。Agent 不知道确切名称时，可以先列出页面树，再读取所需页面。

```json
{ "from": "handbook:acme", "depth": 2 }
```

Agent 会收到各页面的引用（例如 `handbook:acme#refunds/damaged-items`）、名称和子页面数量，然后读取所需页面。

## 每个部门使用独立的 scope {/* #one-scope-per-department */}

各部门在全公司 scope 下拥有各自的 scope。人力资源部门的入职清单存放在 `dept:initech:hr`。服务器为员工的每次运行传入 `firm:initech` 和该员工的部门 scope。工程师搜索不到人力资源部门 scope 中的内容，但持有 `firm:initech` 的所有运行都能找到公司的假期页面。

```typescript
const scopes = {
  ...knowledgeMemoryScopes({ org: 'firm:$firmId', orgRole: 'contributor' }),
  'dept:$firmId:$dept': {
    belongsTo: 'firm:$firmId',
    access: [{ principal: 'self', role: 'editor' }],
  },
}
```

要调整谁能看到哪些内容，请更改配置和服务器传入的 scope，无需重写提示词。

## 让有需要的人看到笔记 {/* #notes-for-the-people-who-need-them */}

笔记的 `scope` 列出它标记的范围。一次运行必须能读取页面，且至少持有一个标记中的 scope，才能看到笔记。Dana 的 Agent 为一条笔记仅标记她个人的 scope，为另一条笔记同时标记她个人和小组的 scope。

```json
{
  "op": "add",
  "page": "office:hooli#coverage",
  "scope": ["resource:dana", "squad:hooli:support"],
  "text": "Dana is out Nov 10 to 14; Bea covers her queue."
}
```

客服小组的 Bea 只能看到第二条笔记。销售组的 Sam 两条都看不到，他的 Agent 也无法用自己无法访问的小组 scope 标记笔记。

## 在 Agent 之间交接工作 {/* #hand-work-between-agents */}

同一项目的调研、规划和编码 Agent 共用一个 scope。调研 Agent 写一个页面，规划 Agent 将计划写成它的子页面。编码 Agent 读取计划，每完成一步就添加一条笔记，例如“第 1 步已在 PR 412 中完成”。

Agent 无需直接通信，只需共享页面，并遵守相同的访问规则。
