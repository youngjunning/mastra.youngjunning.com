# 观察记忆

**添加于：** `@mastra/memory@1.1.0`

Observational Memory（OM）让 Agent 可以在同一个 thread 中持续工作，直到任务完成，同时保持上下文精简、聚焦且适合 prompt 缓存。**Observer** Agent 会在后台把较早的消息整理成带日期的简短观察记录；记录增多后，**Reflector** Agent 会进一步压缩。Agent 可以完整看到最近的消息，而将更早的内容以观察记录的形式读取。

只要 Agent 的工作超出一次性摘要或单个 Workflow 步骤，就适合使用 OM。多步骤 Agent 都能受益，包括聊天助手、编码 Agent、浏览器 Agent，以及持续数小时的支持对话。

## 快速入门 {/* #quickstart */}

安装 `@mastra/memory` 和[存储适配器](/docs/storage#supported-providers)。以下示例使用 `@mastra/libsql`，将数据存储在本地 `memory.db` 文件中。

```bash npm2yarn
npm install @mastra/memory@latest @mastra/libsql@latest
```

OM 需要支持它的存储（`@mastra/libsql`, `@mastra/pg`, `@mastra/mysql`, `@mastra/mongodb`, `@mastra/convex`或者`@mastra/oracledb`)，每个调用都有一个线程，以及`observationalMemory: true`。该脚本将内存存储在本地 LibSQL 文件中，并在一个线程上调用Agent两次：

```typescript title="src/observational-memory.ts"
import { Agent } from '@mastra/core/agent'
import { LibSQLStore } from '@mastra/libsql'
import { Memory } from '@mastra/memory'

const memory = new Memory({
  storage: new LibSQLStore({
    id: 'memory-storage',
    url: 'file:./memory.db',
  }),
  options: {
    // highlight-next-line
    observationalMemory: true,
  },
})

const agent = new Agent({
  id: 'memory-agent',
  name: 'Memory Agent',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  memory,
})

const memoryOptions = {
  resource: 'user-123',
  thread: 'conversation-123',
}

const first = await agent.generate('Remember that my favorite color is blue.', {
  memory: memoryOptions,
})
console.log(first.text)

const second = await agent.generate('What is my favorite color?', {
  memory: memoryOptions,
})
console.log(second.text)
```

`resource` 标识用户或实体，`thread` 标识对话。复用两者即可继续对话。这个简短对话尚未触发观察；当 thread 的消息历史超过 30,000 token 后，OM 才开始用观察记录替换较早的消息。

如果 Mastra 实例已配置存储，可以在 `Memory` 中省略 `storage`，它会沿用实例的配置。

要查看 OM 的工作过程，请在 [Studio](/docs/studio/overview) 打开 Agent 的 **Memory** 标签。进度条会显示消息和观察记录距离各自阈值还有多远；**Analyze observations** 可打开观察日志及其历史。

## 好处 {/* #benefits */}

* **长任务停留在一个线程中**：Agent继续工作超过其上下文限制，而不会压缩，也不会丢失早期的决策。
- **prompt 缓存**：观察记录会附在稳定的前缀之后，而不是每轮重新检索，因此 Provider 可从 prompt 缓存中提供每次请求的大部分内容。参见[成本与延迟](#cost-and-latency)。
* **较小的背景**：原始消息和Tool结果压缩为密集的观察日志，从而降低每次调用的成本和延迟。
* **更少的上下文腐烂**：Agent读取重要的内容，而不是陈旧的Tool输出和噪音，这使其能够在长时间会话中继续执行任务。

Mastra 自身的 Agent 也使用 OM。终端编码 Agent [Mastra Code](https://code.mastra.ai/) 借助它让会话连续运行数天而无须压缩上下文。[Mastra Factory](https://factory.mastra.ai/) 的规划、实现和审阅会话运行在 Mastra Code 上。每个 Agent 都能从头到尾保留长期任务的上下文。

## 它是如何运作的 {/* #how-it-works */}

每次Agent响应时，它都会读取一个上下文窗口，其中包含系统提示符、最近的消息和任何注入的上下文。它携带的原始历史越多，它的性能就越差，并且大多数代币不再需要继续执行任务。 OM 压缩了该历史。

### 观察结果 {/* #observations */}

当 thread 中未观察的消息超过 `observation.messageTokens`（默认 30,000）时，Observer 会写出观察记录：简短且带日期的事件笔记。

```md
Date: 2026-01-15

- 🔴 12:10 User is building a Next.js app with Supabase auth, due in 1 week (meaning January 22nd 2026)
  - 🔴 12:10 App uses server components with client-side hydration
  - 🟡 12:12 User asked about middleware configuration for protected routes
  - 🔴 12:15 User stated the app name is "Acme Dashboard"
```

观察到的消息离开上下文窗口，观察结果取代它们，通常小 5 到 40 倍。每个页面快照看到 50,000 个令牌的浏览器Agent最终会携带数百个有关页面上的内容及其用途的令牌。

同步观察期间，Observer 还会记录**当前任务**和**建议回复**，帮助 Agent 接续工作。启用 `observation.threadTitle` 后，话题变化时它还可建议新的 thread 标题。

Observer 可以看到所审阅历史中的附件。转录文本保留 `[Image #1: reference-board.png]` 等占位符，附件本身也会随文本一起传入。对于无法读取附件的 Observer，参见[选择模型](#choosing-models)。

### 反思 {/* #reflections */}

当观察记录超过 `reflection.observationTokens`（默认 40,000）时，Reflector 会重写整个日志：合并相关条目、进一步压缩较早条目，并保留近期细节。其输出成为新日志，后续观察记录追加在末尾。无论 thread 运行多久，日志大小都维持在反思阈值附近。

Agent的上下文分为三层：

1. **最近消息**：当前任务的确切对话。
2. **观察结果**：自上次反射以来观察者所看到的情况。
3. **反思**：之前所有内容的浓缩日志。

### 背景如何随时间变化 {/* #how-context-changes-over-time */}

在默认设置下，上下文窗口循环增大和缩小：

<OmContextOverTimeImage />

1. **0 到 30,000 个代币**：消息历史记录增长。在后台，观察者准备每 6,000 个令牌的观察结果（`observation.bufferTokens: 0.2`).
1. **达到 30,000 token**：已准备的观察记录激活。已观察的消息离开上下文，保留约 6,000 token 的近期消息（`observation.bufferActivation: 0.8` 表示保留阈值的 20%）。
3. **重复**：历史增长回到 30,000，然后再次缩小。每个周期都会向观察日志添加一点内容。
4. **观察次数达到 40,000**：Reflector 将日志重写为较小的日志。

阈值标记开始处理的时机。如果后台观察进度落后，历史消息可能超过 30,000 token。达到 `observation.blockAfter`（默认 `1.2`，即 36,000 token）时，Agent 会等待一次同步观察。参见[缓冲进度落后时](/reference/memory/observational-memory#when-buffering-falls-behind)。

token 数量是本地 `tokenx` 的估算值。Provider 自身的计数通常更高，尤其当消息包含附件时。

### 上下文溢出恢复 {/* #context-overflow-recovery */}

在 OM 估算值达到阈值前，Provider 可能就因请求超出上下文窗口而拒绝它。此时 OM 会启用已准备好的观察记录、观察所有仍待处理的内容，并以缩小后的上下文重试请求一次。该功能默认开启；设置 `observation.observeOnContextOverflow: false` 可改为将错误传给应用代码。

## 选择型号 {/* #choosing-models */}

Observer 和 Reflector 是与主 Agent 并行运行的模型调用。两者默认都使用 `model: 'auto'`，每次执行各自角色时重新选择模型：

1. 如果 Google 可用（已设置 `GOOGLE_GENERATIVE_AI_API_KEY`，或你的 `canUseProvider` 函数对 `'google'` 返回 `true`），使用 `google/gemini-2.5-flash`。
1. 否则使用与主模型同属一个 Provider 的低成本模型，例如 Anthropic Agent 使用 `anthropic/claude-haiku-4-5`。
3. 否则，主模型本身。

`auto` 会读取主模型的 `provider/model` ID。如果无法确定该 ID，例如模型使用自定义 URL、API key 或网关创建，`auto` 会沿用主模型，因为无法确定同一 Provider 的其他模型也能使用该访问路径。

设置 `model`，让两个角色使用同一模型：

```typescript
const memory = new Memory({
  options: {
    observationalMemory: {
      model: 'deepseek/deepseek-flash',
    },
  },
})
```

选择上下文窗口足够大（至少 128,000 token），且速度足以在后台运行的模型。Mastra 已测试 `google/gemini-2.5-flash`、`__GATEWAY_OPENAI_MODEL_LUNA__`、`__GATEWAY_ANTHROPIC_MODEL_HAIKU__` 和 `deepseek/deepseek-flash`。

如果两个角色要使用不同模型，应分别设置 `observation.model` 和 `reflection.model`，并省略顶层 `model`；同时设置会报错。有些模型保留过多细节，反思结果可能仍超过阈值；测试中 `google/gemini-2.5-flash` 就出现过这种情况。常见搭配是让 Observer 使用保留细节的模型，让 Reflector 使用更擅长压缩的模型，例如 `deepseek/deepseek-flash`。参见[为不同 Agent 指定模型](/reference/memory/observational-memory#different-models-per-agent)。

### 调整自动选择 {/* #tune-automatic-selection */}

以下 `observationalMemory` 选项会影响 `auto` 的选择：

* `autoModels`：例如，替换Provider的低成本选择`{ openai: '__GATEWAY_OPENAI_MODEL_LUNA__' }`.
- `canUseProvider`：当凭据按租户或请求提供，而非放在服务器环境中时，告诉 `auto` 当前请求是否可使用某个 Provider。函数接收 Provider ID 和 `{ requestContext }`。
* `resolveModel`：使用您自己的凭据或路由自行创建所选模型。它接收具体的模型 ID，从不`'auto'`.

```typescript
const memory = new Memory({
  options: {
    observationalMemory: {
      autoModels: { openai: '__GATEWAY_OPENAI_MODEL_LUNA__' },
      canUseProvider: (provider, { requestContext }) => hasCredentials(provider, requestContext),
      resolveModel: (modelId, { requestContext }) => createRoutedModel(modelId, requestContext),
    },
  },
})
```

`@mastra/memory` 中的 `resolveAutoModelId(mainModelId, { autoModels })` 会返回 `auto` 将选择的模型，可用于在设置界面显示实际生效的模型。

### 代币分层模型 {/* #token-tiered-models */}

**添加于：** `@mastra/memory@1.10.0`

`ModelByInputTokens`根据每个观察者或反射器调用的大小选择模型：

```typescript
import { Memory, ModelByInputTokens } from '@mastra/memory'

const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        model: new ModelByInputTokens({
          upTo: {
            5_000: 'openrouter/mistralai/ministral-8b-2512',
            20_000: 'openrouter/mistralai/mistral-small-2603',
            40_000: '__GATEWAY_OPENAI_MODEL_LUNA__',
            1_000_000: '__GATEWAY_GOOGLE_MODEL_FLASH__',
          },
        }),
      },
      reflection: {
        model: new ModelByInputTokens({
          upTo: {
            20_000: '__GATEWAY_OPENAI_MODEL_LUNA__',
            100_000: 'deepseek/deepseek-flash',
          },
        }),
      },
    },
  },
})
```

每一层都需要具体的模型 ID，不能使用 `'auto'`。每个 `upTo` 键都是含边界的上限。超过最大键的调用会报错，因此最后一层应覆盖预期的最大输入。

### 附件和纯文本Observer {/* #attachments-and-text-only-observers */}

默认情况下，Observer 会接收图像和 PDF（`observation.observeAttachments: ['image/*', 'application/pdf']`）。其他附件不会传入，但占位符仍保留在转录文本中。可根据 Observer 模型能处理的附件类型调整此设置：

* `false`: 不发送附件。将其用于纯文本观察者。
* `true`: 发送每个附件。
- MIME 类型列表，例如 `['image/*']`：只传入匹配的附件。匹配不区分大小写，`*` 匹配任意子类型。
* `'auto'`：当提供者注册表表示观察者模型接受多模式输入时发送附件。当没有模型数据时，所有内容都会被发送。

```typescript
const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        model: 'deepseek/deepseek-flash',
        observeAttachments: false,
      },
    },
  },
})
```

同样的过滤规则也适用于 Tool 结果中的图像和文件。Agent 标记为不可用的附件（因为已无法重新下载）不会传给 Observer。参见[附件下载失败](/docs/agents/processors#recover-from-attachment-download-failures)。

## 成本和延迟 {/* #cost-and-latency */}

每一次观察和反思都是一次模型调用。默认情况下，线程大约每 6,000 个新消息令牌就会调用一次 Observer 调用，而每当日志达到 40,000 个令牌时，线程就会调用一次 Reflector。作为回报，每个主Agent调用都会读取最多数万个令牌的上下文，而不是整个线程。观察前缀很少更改，因此提示缓存会继续工作：用户通常会看到 OM 的提示缓存命中率为 97% 到 99%。

观察者在后台提前运行（异步缓冲），因此Agent不会停下来等待它。这些设置控制时间：

|设置|默认 |它控制什么 |
| - | - | - |
| `observation.bufferTokens` | `0.2` | Observer 在后台运行的频率：可设为 `messageTokens` 的比例（默认阈值下，`0.2` 表示每 6,000 token 一次），也可设为 `5000` 等绝对 token 数。设为 `false` 可关闭后台缓冲。 |
| `observation.bufferActivation` | `0.8` | 激活观察记录时清除消息窗口的比例。`0.8` 会保留 `messageTokens` 的 20%；较低的值会保留更多近期消息。 |
| `observation.blockAfter` | `1.2` | 缓冲进度落后时，Agent 开始等待同步观察的阈值。可设为 `messageTokens` 的倍数（`1.2` 表示 36,000 token），也可设为不小于 100 的绝对数量。`1` 表示达到 `messageTokens` 时同步观察。 |

要更改 OM 观察和反映的时间，请设置阈值：

```typescript
const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        messageTokens: 30_000,
      },
      reflection: {
        observationTokens: 40_000,
      },
    },
  },
})
```

### 长时间运行Tool调用 {/* #long-runs-of-tool-calls */}

运行长链Tool调用的Agent（例如编码和浏览器Agent）会在每一步重新发送相同的不断增长的前缀，并且提供程序从提示缓存中提供大部分前缀。对于这些Agent，将观察阈值提高到远高于默认值，例如提高到 60,000 到 80,000 个令牌，这样 OM 压缩的频率就会降低，并且每次运行的更多内容都会被缓存：

```typescript
const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        messageTokens: 70_000,
      },
    },
  },
})
```

让阈值保持在主模型的上下文窗口以内。`bufferTokens`、`bufferActivation` 和 `blockAfter` 默认都是 `messageTokens` 的比例，因此会随它缩放。

### 提示缓存过期时激活 {/* #activate-when-the-prompt-cache-expires */}

prompt 缓存一旦过期，下一次请求仍要为整个上下文支付完整成本。`activateAfterIdle` 可在 thread 空闲达到指定时间后激活已准备好的观察记录，使暂停后的请求发送更小、已压缩的上下文。默认不设置。设为 `'auto'` 时，会采用当前 Provider 的 prompt 缓存 TTL（例如 Anthropic 为 5 分钟，DeepSeek 为 1 小时）：

```typescript
const memory = new Memory({
  options: {
    observationalMemory: {
      activateAfterIdle: 'auto',
    },
  },
})
```

固定时长、按 Provider 设置，以及 Provider 变化时激活的说明参见[提前激活](/reference/memory/observational-memory#early-activation)。

### 同步观察 {/* #synchronous-observation */}

如需改为同步观察，设置 `observation.bufferTokens: false`。这会关闭观察和反思的后台缓冲，Agent 会在每次操作期间暂停等待。

`shareTokenBudget: true` 允许消息历史借用未使用的观察预算，因此当日志较小时，观察开始前最多可保留约 70,000 token 的消息。它要求设置 `observation.bufferTokens: false`。参见[共享 token 预算](/reference/memory/observational-memory#shared-token-budget)。

## 线程和跨线程内存 {/* #threads-and-cross-thread-memory */}

### 线程范围（默认） {/* #thread-scope-default */}

每个 thread 都有独立的观察记录。每次调用都需要 thread；如果未提供，OM 会抛出 `OBSERVATIONAL_MEMORY_THREAD_ID_REQUIRED`，避免无关 thread 共用一份观察记录。

:::warning
客户端应用调用 Agent 时，只发送新消息，不要发送完整对话。OM 已从存储中加载 thread 历史。Mastra 如何处理重复发送的历史，以及何时使用 `retainFullInput`，参见[消息历史](/docs/memory/message-history)。
:::

OM 的记忆范围默认为单个 thread。若要让 Agent 访问同一用户的其他 thread，可启用[检索模式](#retrieval-mode)。它会提供 `recall` Tool，用于读取观察记录背后的原始消息，以及同一 resource 的其他 thread。

### 检索方式 {/* #retrieval-mode */}

观察记录不保留原文措辞。启用检索模式后，每组观察记录会继续关联来源消息，Agent 可用 `recall` Tool 读取原文，包括准确措辞和 Tool 输出。

`retrieval: true`让Agent浏览原始消息、列出资源的线程并读取其他线程。不需要矢量存储。

`retrieval: { vector: true }` 会使用 `Memory` 上配置的向量存储和 embedder，对观察记录分组增加语义搜索。如果向量存储自行生成 embedding，就不用设置 `embedder`。参见[服务端 embedding](/docs/memory/semantic-recall#server-side-embeddings)。新观察记录分组创建后会在后台建立索引。

```typescript
const memory = new Memory({
  storage,
  vector: myVectorStore,
  embedder: myEmbedder,
  options: {
    observationalMemory: {
      retrieval: { vector: true },
    },
  },
})
```

recall Tool 的默认 scope 为 `'resource'`，因此可访问该 resource 的所有 thread。设置 `retrieval: { scope: 'thread' }` 可限制为当前 thread。使用 `retrieval.instructions` 在内置 recall 指令后添加应用专属指引，例如“当前对话已有答案时优先使用当前对话”。

各模式、详细程度和分页说明参见 [recall Tool 参考](/reference/memory/observational-memory#recall-tool)。

### 资源范围（已弃用） {/* #resource-scope-deprecated */}

:::warning[Deprecated]

`scope: 'resource'` 已弃用，将在未来版本中移除。首次以 resource scope 创建 OM 时，Mastra 会记录警告。移除 `scope` 选项即可使用 thread scope；跨 thread 连续性请使用[检索模式](#retrieval-mode)。目前处于 alpha 阶段的 [Knowledge](/docs/knowledge/overview) 可供 Agent 跨 thread 共享信息，计划取代 resource scope。

:::

资源范围在资源的所有线程之间共享一个观察记录。它的工作效果比线程作用域差得多：

* **提示缓存**：观察任何线程都会更改每个其他线程的上下文，这会破坏其缓存的前缀。
* **Agent了解**：每个线程都可以看到来自其他线程的观察结果，并且Agent可以继续另一个线程启动的工作。
* **表现**：来自所有线程的未观察到的消息会一起处理，这对于具有多个线程的用户来说很慢。资源范围还会关闭异步缓冲。

切换到线程范围不会迁移资源范围的观察。每个线程都使用自己的线程范围记录（如果有的话），或者开始为空，并且不会再次观察到在资源范围下已观察到的消息。

## 提取器 {/* #extractors */}

提取器在观察的同时保留特定的值。内置当前任务、建议响应和线程标题使用相同的管道。此示例提取一个小的用户配置文件：

```typescript title="src/mastra/agents/assistant.ts"
import { Agent } from '@mastra/core/agent'
import { Extractor, Memory } from '@mastra/memory'
import { z } from 'zod'

const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        extract: [
          new Extractor({
            name: 'User profile',
            instructions: 'Extract stable user profile facts that should be remembered.',
            schema: z.object({
              preferredName: z.string().optional(),
              timezone: z.string().optional(),
              tools: z.array(z.string()).optional(),
            }),
          }),
        ],
      },
    },
  },
})

export const assistant = new Agent({
  id: 'assistant',
  name: 'Assistant',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  memory,
})
```

带 `schema` 的 extractor 会在后续结构化输出请求中运行。没有 schema 时则是内联字符串 extractor，直接在 Observer 或 Reflector 的响应中输出：

```typescript
new Extractor({
  name: 'Mood',
  instructions: 'Extract the user mood as a short phrase.',
})
```

默认情况下，extractor 在后续运行中能看到上次提取的值。设置 `includePreviousExtraction: false` 可隐藏该值：

```typescript
new Extractor({
  name: 'Latest blocker',
  instructions: 'Extract any blockers the agent is running into.',
  includePreviousExtraction: false,
})
```

当 `instructions` 和 `schema` 依赖 memory 实例或请求上下文等运行时环境时，也可将它们定义为函数：

```typescript
new Extractor({
  name: 'Workspace summary',
  instructions: ({ memory }) =>
    memory ? 'Extract workspace facts for this memory instance.' : 'Extract workspace facts.',
})
```

在值持久化前，使用 `onExtracted` 对其进行规范化：

```typescript
new Extractor({
  name: 'Project status',
  instructions: 'Extract the current project status.',
  schema: z.string(),
  onExtracted: ({ current }) => current.trim().toLowerCase(),
})
```

`onExtracted` 还会收到 `previous` 和 `sendSignal`，可在值变化时通知 Agent。该钩子每次提取都会运行，因此发送 signal 前应比较 `previous` 与 `current`；否则每次观察都会再次发送。

extractor 失败会在 OM 标记中报告，但不会清除其他成功 extractor 的值。完整结构参见 [Extractor API](/reference/memory/observational-memory#extractor-api)。

### 从流中读取提取的值 {/* #read-extracted-values-from-a-stream */}

当 OM 完成观察或反射时，提取器结果就会到达。从流中读取两个完成数据部分：

```typescript title="src/run.ts"
import { assistant } from './mastra/agents/assistant'

const stream = await assistant.stream('Remember that I prefer dark mode.', {
  memory: { resource: 'user-123', thread: 'conversation-123' },
})

for await (const chunk of stream.fullStream) {
  if (chunk.type === 'data-om-observation-end' || chunk.type === 'data-om-buffering-end') {
    const { operationType, extractedValues = {}, extractionFailures = [] } = chunk.data

    for (const [slug, value] of Object.entries(extractedValues)) {
      console.log(`${operationType} extractor ${slug}:`, value)
    }

    for (const failure of extractionFailures) {
      console.error(`Extractor ${failure.slug} failed:`, failure.error)
    }
  }
}
```

`extractedValues`由每个提取器的弹头键控。这两个字段都是可选的。

`data-om-observation-end` 表示同步观察完成。`data-om-buffering-end` 表示后台任务完成：其 extractor 值会立即持久化，但缓冲的观察记录在激活前仍不生效。`operationType` 指明本次操作是观察还是反思。payload 详见 [`data-om-observation-end`](/reference/memory/observational-memory#data-om-observation-end) 和 [`data-om-buffering-end`](/reference/memory/observational-memory#data-om-buffering-end)。
