# 细粒度授权 (FGA)

:::note

FGA 在生产环境中需要 Mastra 企业版 (EE) 许可证；开发环境无需许可证。参阅[需要 EE 许可证的功能](/docs/license#what-requires-an-ee-license)。如需了解更多信息，请[联系销售团队](https://mastra.ai/contact)。

:::

细粒度授权 (FGA) 为 Mastra 应用增加资源级权限检查。RBAC 回答“这个角色能执行这个操作吗？”，FGA 则回答**“这个用户能对这个特定资源执行这个操作吗？”**

## 何时使用 FGA {/* #when-to-use-fga */}

FGA 专为多租户 B2B 产品而设计，其中权限与上下文相关：

- 用户可能是团队 A 的**管理员**，但只是团队 B 的**成员**
- 对会话线程的访问应限制在用户所属组织内
- Workflow 的执行应限定在特定团队或项目内
- Tool 访问权限取决于用户与资源的关系

## 配置 {/* #configuration */}

在 Mastra 服务器配置中，将 FGA 与身份验证和 RBAC 一起配置：

```typescript
import { Mastra } from '@mastra/core/mastra'
import { MastraFGAPermissions } from '@mastra/core/auth/ee'
import { MastraAuthWorkos, MastraFGAWorkos } from '@mastra/auth-workos'

const mastra = new Mastra({
  server: {
    auth: new MastraAuthWorkos({
      /* ... */
      fetchMemberships: true,
      mapUserToResourceId: user => user.teamId,
    }),
    fga: new MastraFGAWorkos({
      resourceMapping: {
        agent: { fgaResourceType: 'team', deriveId: ctx => ctx.user.teamId },
        workflow: { fgaResourceType: 'team', deriveId: ctx => ctx.user.teamId },
        thread: { fgaResourceType: 'workspace-thread', deriveId: ({ resourceId }) => resourceId },
      },
      permissionMapping: {
        [MastraFGAPermissions.AGENTS_EXECUTE]: 'manage-workflows',
        [MastraFGAPermissions.WORKFLOWS_EXECUTE]: 'manage-workflows',
        [MastraFGAPermissions.MEMORY_READ]: 'read',
        [MastraFGAPermissions.MEMORY_WRITE]: 'update',
      },
    }),
    storedResources: {
      scope: true,
    },
  },
})
```

使用 `MastraFGAWorkos` 时，请在 `MastraAuthWorkos` 中设置 `fetchMemberships: true`。WorkOS FGA 检查需要用户的组织成员关系，才能解析用于授权的正确成员关系 ID。

对记忆进行授权时，使用 `thread` 作为资源映射键。`MastraFGAWorkos` 仍接受旧别名 `memory`，但新配置应优先使用 `thread`。

配置 `server.fga` 后，Mastra 会对受保护操作执行 FGA 检查。若操作没有经过身份验证的用户，Mastra 会拒绝执行。未配置 `server.fga` 时，这些检查会跳过，并保持原有行为。

### 资源映射 {/* #resource-mapping */}

`resourceMapping` 指定如何从请求上下文解析 FGA 资源类型和 ID。键是 Mastra 资源类型；值定义 FGA 资源类型及 ID 的派生方式：

```typescript oxfmt:false
resourceMapping: {
  // When checking "can user execute agent X?", resolve the FGA resource
  // as the user's team (type: 'team', id: user.teamId)
  agent: {
    fgaResourceType: 'team',
    deriveId: (ctx) => ctx.user.teamId,
  },
}
```

`deriveId()` 接收：

- `user`：已通过身份验证的用户
- `resourceId`：资源所属的 Mastra 资源 ID（若可用，例如线程的 `resourceId`）
- `requestContext`：当前请求上下文，可用于更复杂的租户解析

若 `deriveId()` 返回 `undefined`，则回退使用原始的 Mastra 资源 ID。

检查线程和记忆权限时，Mastra 仍将原始 `threadId` 作为待检查的资源，同时将线程所属的 `resourceId` 传入 `deriveId()`。因此可以将线程权限映射到 `userId-teamId-orgId` 等复合租户 ID。

### 权限映射 {/* #permission-mapping */}

`permissionMapping` 将 Mastra 内部权限字符串映射为 FGA Provider 使用的权限标识：

```typescript oxfmt:false
import { MastraFGAPermissions } from '@mastra/core/auth/ee';

permissionMapping: {
  [MastraFGAPermissions.AGENTS_EXECUTE]: 'manage-workflows', // Mastra permission -> WorkOS permission slug
  [MastraFGAPermissions.MEMORY_READ]: 'read',
}
```

如果权限不存在映射，则传递原始字符串。

使用 `validatePermissions()` 在启动时校验 Mastra 可能产生的全部权限。如果 Provider 要求每项 Mastra 权限都有明确的权限标识，就应使用此方法。

### 存储资源的范围限定 {/* #stored-resource-scoping */}

FGA 授权资源访问，但不会自动筛选共享存储中的记录。在多租户应用中使用内置存储资源 API 时，应启用存储资源的范围限定。

```typescript
const mastra = new Mastra({
  server: {
    auth: new MastraAuthWorkos({
      /* ... */
      mapUserToResourceId: user => user.teamId,
    }),
    storedResources: {
      scope: true,
    },
  },
})
```

启用 `scope: true` 后，Mastra 从请求上下文读取 `MASTRA_RESOURCE_ID_KEY`。`mapUserToResourceId()` 在身份验证后设置该值。存储资源处理程序将范围写入记录元数据，并按该范围筛选列表、读取、更新、发布和删除操作。

如果需要自定义请求逻辑来确定范围，请使用对象配置：

```typescript oxfmt:false
storedResources: {
  scope: {
    metadataKey: 'teamId',
    resolve: ({ user }) => user.teamId,
    requireScope: true,
  },
},
```

当 `requireScope` 为 `true` 或省略时，如果无法解析范围，限定范围的存储资源路由就会失败。

### 路由策略覆盖范围 {/* #route-policy-coverage */}

Mastra 为内置资源路由提供路由级 FGA 元数据，涵盖 Agent、Workflow、Tool、MCP Tool、记忆线程、响应、对话及存储资源。存储资源路由包括 `/stored/agents`、`/stored/mcp-clients`、`/stored/prompt-blocks`、`/stored/scorers`、`/stored/skills` 和 `/stored/workspaces`。路由具有 `fga` 元数据、Mastra 能为其推导内置元数据，或 Provider 通过 `resolveRouteFGA()` 提供元数据时，才会接受检查。

要拒绝未解析到 FGA 元数据的受保护路由，请在 FGA Provider 上配置路由策略覆盖范围：

```typescript
const fga = new MastraFGAWorkos({
  resourceMapping: {
    project: { fgaResourceType: 'project' },
  },
  permissionMapping: {
    'projects:read': 'read',
  },
  requireForProtectedRoutes: true,
  auditProtectedRoutes: 'warn',
  validatePermissions: async permissions => {
    // Throw if a Mastra permission is missing from permissionMapping.
  },
})
```

设置 `auditProtectedRoutes: 'error'`，可在受保护路由缺少内置 FGA 元数据时让启动失败。启用 `requireForProtectedRoutes` 时，Mastra 默认将此审计记录为警告。

对于自定义路由，优先使用路由级 `fga` 元数据，使授权策略与路由定义放在一起：

```typescript
import { createRoute } from '@mastra/server/server-adapter'

export const getProjectRoute = createRoute({
  method: 'GET',
  path: '/projects/:projectId',
  responseType: 'json',
  requiresAuth: true,
  fga: {
    resourceType: 'project',
    resourceIdParam: 'projectId',
    permission: 'projects:read',
  },
  handler: async () => {
    return { project: null }
  },
})
```

只有必须根据路由、参数或请求上下文集中推导路由元数据时，才使用 `resolveRouteFGA()`。路由映射比字符串前缀检查更适合扩展：

```typescript
import type { FGARouteConfig, FGARouteResolver } from '@mastra/core/auth/ee'

const routeFGA = {
  'GET /billing/:accountId': {
    resourceType: 'account',
    resourceIdParam: 'accountId',
    permission: 'billing:read',
  },
} satisfies Record<string, FGARouteConfig>

const resolveRouteFGA: FGARouteResolver = ({ route }) => routeFGA[`${route.method} ${route.path}`]

const fga = new MastraFGAWorkos({
  /* ... */
  resolveRouteFGA,
})
```

## 执行点 {/* #enforcement-points */}

配置 FGA Provider 后，Mastra 会在以下生命周期节点自动检查授权：

| 生命周期节点 | 检查的权限 | 资源类型 | 资源 ID |
| - | - | - | - |
| Agent 执行（`generate`、`stream`） | `agents:execute` | `agent` | `agentId` |
| 内置 Workflow HTTP 执行路由和 `Workflow.execute()` | `workflows:execute` | `workflow` | `workflowId` |
| 独立 Tool 执行 | `tools:execute` | `tool` | `toolName` |
| Agent Tool 执行 | `tools:execute` | `tool` | `${agentId}:${toolName}` |
| MCP Tool 执行 | `tools:execute` | 默认是 `tool`，也可由服务器级 `fga.resourceMapping` 覆盖 | 默认是 `JSON.stringify([serverName, toolName])`，也可使用服务器级派生 ID |
| 线程和记忆访问 | `memory:read`、`memory:write`、`memory:delete` | `thread` | `threadId` |
| 存储资源路由 | 路由操作对应的存储资源权限 | 存储资源类型 | 路由记录 ID；集合路由则使用存储资源范围 |
| HTTP 资源路由 | 按路由配置 | 按路由配置 | 按路由配置 |

对于受 OAuth 保护的 MCP 服务器，HTTP MCP 传输以 `extra.authInfo` 传递身份验证数据。如果在启用 FGA 的 Mastra 实例上注册了 `MCPServer`，请配置 `mapAuthInfoToUser`，以便 Mastra 在检查 `tools/list` 和 `tools/call` 前设置 `requestContext.get('user')`。如果 MCP Tool 检查所需的资源或权限映射与 Agent 和 Workflow 内部的 Tool 检查不同，请使用服务器级 `fga` 选项。参阅 [MCPServer 身份验证上下文](/reference/tools/mcp-server#map-auth-data-for-fga)。

本版本的核心 FGA 不会单独检查对 `createRun().start()`、`resume()` 或 `restart()` 的直接 SDK 调用。请从受保护路由发起这些调用，或在应用代码中进行保护。直接调用受保护入口时，传入包含已验证用户的 `requestContext`。

Agent、内部 Workflow、Tool 和记忆的核心检查还会向 FGA Provider 传递 `requestContext` 及操作元数据。路由检查会传递 `requestContext`。线程检查会在可用时传递所属的 `resourceId`。

## 自定义 FGA Provider {/* #custom-fga-provider */}

实现 `IFGAProvider`，即可使用任意 FGA 后端：

```typescript
import { FGADeniedError } from '@mastra/core/auth/ee'
import type { FGACheckParams, IFGAProvider, MastraFGAPermissionInput } from '@mastra/core/auth/ee'

class MyFGAProvider implements IFGAProvider {
  async check(user: any, params: FGACheckParams): Promise<boolean> {
    // Your authorization logic
    return true
  }

  async require(user: any, params: FGACheckParams): Promise<void> {
    const allowed = await this.check(user, params)
    if (!allowed) {
      throw new FGADeniedError(user, params.resource, params.permission)
    }
  }

  async filterAccessible<T extends { id: string }>(
    user: any,
    resources: T[],
    resourceType: string,
    permission: MastraFGAPermissionInput,
  ): Promise<T[]> {
    // Filter resources the user can access
    return resources
  }
}
```

:::note
有关全部方法、参数及 `ActorSignal` 类型，请参阅 [`IFGAProvider` 参考文档](/reference/auth/fga)。
:::

## 系统参与者 {/* #system-actors */}

自主运行或定时执行的 Agent 没有终端用户。请用 actor 信号标记这些调用，以便 FGA 将其与用户请求区分开：

- `true` 或 `{ actorKind: 'system' }` 表示匿名系统 actor。
- 对象形式还可包含 `agentId`、`permissions` 和 `scope`，用于标识并限制执行操作的 Agent。

默认情况下，受信任 actor 通过租户范围检查后，会跳过面向用户的 `require()` 检查。若要按 Agent 实施最小权限，请在 Provider 中实现可选的 `requireActor` 方法。该方法接收 actor 和与 `require` 相同的 `FGACheckParams`；拒绝访问时抛出 `FGADeniedError`。未实现 `requireActor` 的 Provider 会保留受信任 actor 的跳过行为，以兼容旧版本。

```typescript
import { FGADeniedError } from '@mastra/core/auth/ee'
import type { ActorSignal, FGACheckParams, IFGAProvider } from '@mastra/core/auth/ee'

class MyFGAProvider implements IFGAProvider {
  // ...check, require, filterAccessible...

  async requireActor(actor: ActorSignal, params: FGACheckParams): Promise<void> {
    const agentId = actor === true ? undefined : actor.agentId
    // Resolve the agent's real grants from a trusted source keyed by agentId.
    const granted = await this.grantsForAgent(agentId)
    const required = Array.isArray(params.permission) ? params.permission : [params.permission]
    if (!required.some(permission => granted.includes(permission))) {
      throw new FGADeniedError(null, params.resource, params.permission)
    }
  }
}
```

### 将 actor 传递至 Workflow 步骤 {/* #propagating-an-actor-into-workflow-steps */}

Workflow 运行的 `actor` 会传入各步骤的执行上下文，却不会自动传给步骤发起的 Agent 和 Tool 调用。若步骤调用 Agent 时未提供 `actor`，系统会回退到用户成员关系解析；没有用户的系统运行会因此失败。

为 actor 设置 `propagate: true` 后，框架会在运行中将其传给声明式 `.then(agent)` 和 `.then(tool)` 步骤所发起的 Agent 与 Tool 调用：

```typescript
await run.start({
  inputData: { city: 'London' },
  actor: { actorKind: 'system', sourceWorkflow: 'nightly-report', propagate: true },
})
```

传播需显式开启，且范围刻意受限：

- `true` 简写形式不会传播。请使用对象形式显式开启。
- 自定义步骤的 `execute` 函数不在覆盖范围内。请从步骤上下文读取 `actor` 并显式传入，以免代表用户执行的步骤悄然继承系统信任。
- 创建步骤时传入 `actor`，可覆盖该步骤的运行级 actor；传入 `actor: undefined` 则可在运行途中切回用户授权。

```typescript
// Runs as the system actor even though it loads user-supplied data.
workflow.then(createStep(reportAgent))
// Explicitly runs as the user instead.
workflow.then(createStep(summaryAgent, { actor: undefined }))
```

### 信任要求 {/* #trust-requirements */}

参与者信号是可信输入，因此在服务器端构建它：

- 将 `actor` 视为每次调用的信号。持久化 Workflow 会在运行开始时传递它，但恢复运行时不会还原初始 actor。每次以受信任身份恢复时都要显式传入，或通过 Agent 的 `defaultOptions` 解析新的 actor。若当前没有 actor，则应用用户授权；缺少用户时会拒绝访问。
- Mastra 会从内置 Agent HTTP 路由处理的执行选项中移除 `actor`。请在定时任务或 Workflow 等服务器端代码中设置，绝不可接受客户端输入。
- 在服务器端确立租户范围。内置 Agent HTTP 路由会忽略客户端在请求上下文中传入的 `organizationId`，而受信任 actor 路径要求设置 `organizationId`。
- 持久化恢复沿用现有的请求上下文恢复和合并行为。这不会使持久化的 actor 在后续 Workflow 阶段自动获得信任。
- 租户范围检查只确认存在受信任的 `organizationId`，不会验证 `actor.agentId` 是否属于该组织。如果这种关系很重要，应在 `requireActor` 中使用权威 Provider 数据验证。
- 将 `actor.permissions` 视为未经验证的声明。若要实施最小权限，请通过 `agentId` 从清单或 FGA 后端等可信来源解析 Agent 的权限，勿信任内联值。
- Provider 一旦实现 `requireActor`，该方法的错误就会中止执行。Mastra 不会回退到仅按组织授权。
