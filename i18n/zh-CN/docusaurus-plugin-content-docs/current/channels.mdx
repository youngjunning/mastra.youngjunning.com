# 渠道

**新增于：** `@mastra/core@1.22.0`

渠道将 Agent 连接到 Slack、Microsoft Teams、Discord、Telegram、WhatsApp、GitHub 和 Linear 等消息与协作平台。用户在平台上发送消息或评论时，Agent 会按常规流程接收并处理，再将回复以流式方式发送回原对话。Mastra 的渠道层基于 [Chat SDK](https://chat-sdk.dev/)。

请先阅读相应平台的页面：

<IntegrationGrid section="Channels" />

[其他适配器](#other-adapters)列出了更多平台。除本页列出的平台外，Mastra 渠道还支持兼容的 [Chat SDK 适配器](https://chat-sdk.dev/adapters)；各适配器使用相同的 Mastra 配置方式。

## 何时使用渠道 {/* #when-to-use-channels */}

当 Agent 需要完成以下任务时，使用渠道：

- 在用户日常交流或工作的平台上与他们互动。
- 在 Slack、Microsoft Teams、Discord、Telegram 和 WhatsApp 等聊天平台回复消息。
- 支持多人在共享渠道或线程中与同一个 Agent 互动。
- 接入 GitHub issue、拉取请求讨论和 Linear 评论等协作流程。

## 使用 Mastra Connect 快速配置渠道 {/* #configure-channels-faster-with-mastra-connect */}

如果不想为每个渠道分别配置机器人或应用并自行维护凭据，可以使用 [Mastra Connect](/docs/mastra-platform/connect#add-channels)。它会代为管理凭据，简化渠道的配置与维护。

## 配置 Agent {/* #configure-an-agent */}

渠道使用 Chat SDK 适配器，Mastra 侧的配置方式一致：创建渠道适配器，并将其添加到 Agent。

```typescript title="src/mastra/agents/your-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createSlackAdapter } from '@chat-adapter/slack'

export const yourAgent = new Agent({
  id: 'your-agent',
  name: 'Your Agent',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
  channels: {
    adapters: {
      slack: createSlackAdapter(),
    },
  },
})
```

:::note

渠道适配器需要平台专用的环境变量，用于提供凭据和验证请求，例如机器人令牌、签名密钥、应用 ID 和 webhook 验证令牌。具体变量名请参阅对应平台指南或 [Chat SDK 适配器目录](https://chat-sdk.dev/adapters)。

:::

建议为渠道配置[存储](/docs/storage)。存储可在重启后保留渠道与记忆状态，包括线程订阅和工具审批：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { LibSQLStore } from '@mastra/libsql'
import { yourAgent } from './agents/your-agent'

export const mastra = new Mastra({
  agents: { yourAgent },
  storage: new LibSQLStore({
    id: 'mastra-storage',
    url: process.env.DATABASE_URL,
  }),
})
```

## Webhook 路由 {/* #webhook-routes */}

平台通过 webhook 向 Mastra 发送渠道事件。Webhook 是平台在新消息、提及，或用户点击交互式工具审批卡片上的“批准”时调用的 HTTP 端点。它将消息交给 Agent 处理，Agent 随后在同一渠道回复。

Mastra 会为每个已配置的适配器注册 webhook 路由，并处理请求：

```text
/api/agents/<AGENT_ID>/channels/<PLATFORM>/webhook
```

例如，ID 为 `your-agent` 的 Agent 使用 Slack 适配器时，路由为：

```text
/api/agents/your-agent/channels/slack/webhook
```

将平台的 webhook、事件或交互 URL 指向该路径。具体配置请参阅平台指南或 [Chat SDK 文档](https://chat-sdk.dev/adapters)。Webhook 会在 Agent 完成回复前确认请求；验证或处理程序失败时的行为见[错误处理与投递](#error-handling-and-delivery)。

本地开发时，平台需要通过公网 URL 访问本地服务器。可以使用 [cloudflared](https://github.com/cloudflare/cloudflared) 或 [ngrok](https://ngrok.com/) 建立隧道，公开默认运行在 `localhost:4111` 的服务器：

```bash npm2yarn
npx cloudflared tunnel --url http://localhost:4111
```

将生成的公网 URL 作为 webhook 路径的基址，例如 `https://abc123.trycloudflare.com/api/agents/your-agent/channels/slack/webhook`。

:::note

隧道 URL 仅用于本地开发。部署 Mastra 服务器后，将平台的 webhook、事件或交互 URL 更新为生产环境 URL。

:::

## 线程上下文 {/* #thread-context */}

用户在渠道线程的对话中途提及 Agent 时，Agent 可能缺少之前的上下文。首次提及时，Mastra 会从平台获取较早的消息，并在处理此次提及前将其保存到 Agent 的记忆线程。

1. 首次在线程中提及时，Agent 获取线程的首条消息，以及提及之前最近的消息。`maxMessages`（默认 `10`）决定窗口大小：首条消息加上最多 `maxMessages - 1` 条最近消息。如果两者之间还有其他消息，会以 `[… N earlier Slack messages omitted]` 标记代替并保存；其中平台名称随渠道变化。
1. 获取到的每条消息会连同作者、平台消息 ID 和附件，分别作为用户消息保存到记忆中，并带有 `source: 'thread-history'` 属性。随后，此次提及按普通消息处理。
1. Agent 回复后会订阅该线程，并通过 Mastra 记忆保留完整历史。
1. 此线程中的后续消息不会再次从平台获取历史。

设置 `threadContext: { maxMessages: 0 }` 可关闭此行为。该设置仅适用于非私信线程。

没有记忆的 Agent 无法保存这些消息，因此会改为在提及消息中以上下文文本接收相同的历史。写入记忆失败时也会采用此方式。

记忆的 `lastMessages` 选项限制进入提示词的消息数量。默认值 `10` 会在 `maxMessages` 为 `10` 时裁掉首条消息和省略标记，因此应将 `lastMessages` 设为至少 `maxMessages + 1`。

Mastra 还会添加一条简短的系统消息，告知 Agent 请求来自哪个渠道和平台，以及它是私信还是公共渠道消息。设置 `threadContext: { addSystemMessage: false }` 可跳过这条消息。

## 工具审批 {/* #tool-approval */}

设置了 `requireApproval: true` 的 Tool 会显示带有 Approve 和 Deny 按钮的交互式卡片：

```typescript title="src/mastra/tools/delete-file.ts"
import { promises as fs } from 'node:fs'
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

export const deleteFile = createTool({
  id: 'delete-file',
  description: 'Delete a file from the system',
  inputSchema: z.object({
    path: z.string().describe('Path to the file to delete'),
  }),
  requireApproval: true,
  execute: async ({ path }) => {
    await fs.unlink(path)
    return { deleted: path }
  },
})
```

Agent 调用此 Tool 时，用户会看到包含工具名称、参数和 Approve、Deny 操作的卡片。只有获得审批后，工具才会执行。

若要用自定义消息替换卡片，例如本地化按钮，可从 `toolDisplay` 函数返回 `{ kind: 'post', message: card }`。自定义函数会接管所有工具事件的呈现，而不只是审批事件。Mastra 的默认操作处理程序只有在按钮保留预期 ID 时才会恢复运行。参阅[自定义审批卡片](/reference/agents/channels#custom-approval-cards)。

默认只有请求调用工具的用户可以批准或拒绝。若共享渠道允许其他成员操作，请在相应适配器上设置 `toolApprovers: 'anyone'`：

```typescript title="src/mastra/agents/your-agent.ts" oxfmt:false
channels: {
  adapters: {
    slack: {
      adapter: createSlackAdapter(),
      toolApprovers: 'anyone',
    },
  },
},
```

这仅跳过请求者检查：操作仍须对应待处理的工具审批和已映射的线程。如果运行没有记录请求者（例如定时运行），默认模式并不能严格保证只有请求者可以操作；此时其他渠道成员也可能响应。若重启后存储的消息指向多个可能的请求者，仅限请求者模式则会拒绝他们的点击。

在适配器上设置 `toolDisplay: 'text'`，可将工具调用显示为纯文本，而非交互式卡片。在 `'hidden'` 模式下，若同一线程随后收到用户消息，`autoResumeSuspendedTools` 可恢复携带数据的 `suspend()` 流程；这需要记忆支持。隐藏模式只会隐藏审批按钮，不会将消息视为同意。需要审批的 Tool 会继续暂停，直到通过 UI 或 API 操作明确批准或拒绝。

### 自定义操作处理 {/* #custom-action-handling */}

使用 `handlers.onAction` 处理自行发布的卡片中的按钮点击和选择变化。处理程序会收到 Chat SDK 操作事件、默认处理程序，以及其他渠道处理程序收到的同一个 `ctx`。委托给默认处理程序前写入 `ctx.requestContext` 的值会传递到恢复后的工具调用。默认处理程序只处理内置的 Approve 和 Deny 按钮，忽略其他操作 ID；因此，对未自行处理的事件应调用它，确保工具审批仍可用：

```typescript title="src/mastra/agents/your-agent.ts" oxfmt:false
channels: {
  adapters: {
    slack: createSlackAdapter(),
  },
  handlers: {
    onAction: async (event, defaultHandler, ctx) => {
      if (event.actionId === 'retry') {
        await event.thread?.post('Retrying...')
        return
      }
      await defaultHandler()
    },
  },
},
```

设置 `onAction: false` 会完全禁用操作处理，包括内置工具审批按钮。若要在渠道启动后注册更多 Chat SDK 处理程序，请使用 `agent.getChannels()?.sdk`。

## 回复格式 {/* #reply-formatting */}

Agent 默认以 Markdown 发布回复。Slack 等原生支持 Markdown 的平台会直接呈现粗体、链接和表格；其他平台会转换为自己的格式。Agent 编写标准 Markdown，即可在各平台正确呈现，效果与 Studio 中的相同。

在适配器上设置 `textFormat: 'plain'`，可将回复按原样作为纯文本发布：

```typescript title="src/mastra/agents/your-agent.ts" oxfmt:false
channels: {
  adapters: {
    slack: {
      adapter: createSlackAdapter(),
      textFormat: 'plain',
    },
  },
},
```

如果已指示 Agent 输出 Slack mrkdwn 等平台专用格式，而非标准 Markdown，可使用此选项。若之前为避免 Markdown 被原样显示而添加过此类提示词指令，应将其移除。默认行为现在会原生呈现标准 Markdown。`textFormat` 仅影响最终回复文本，不影响工具卡片、错误消息或原生流式文本。

### 仅通过 Tool 回复 {/* #reply-only-through-a-tool */}

设置 `textDisplay: 'hidden'` 可阻止发布 Agent 的回复文本。此后，Agent 自己的消息只有通过提供给它的 Tool（例如向线程发消息的工具）才能进入线程。这既能避免“Running the tests now”等中间说明出现在对话中，也让 Agent 自行决定何时发消息：

```typescript title="src/mastra/agents/your-agent.ts" oxfmt:false
channels: {
  adapters: {
    slack: {
      adapter: createSlackAdapter(),
      textDisplay: 'hidden',
    },
  },
},
```

工具显示、审批提示、错误消息和输入状态不受影响。回复文本仍会进入 Agent 的流和记忆。

Mastra 添加到 Agent 提示词中的渠道指令也会遵循此设置：文本隐藏时，Agent 会获知只有通过 Tool 发布的内容才能进入对话，并且可以选择不发布任何消息。

## 非消息触发的运行 {/* #runs-that-dont-start-from-a-message */}

从渠道发起的线程也可能由其他来源触发运行，例如定时任务、Studio 提示词或唤醒 Agent 的 Signal。这类运行会收到与消息触发的运行相同的渠道指令。Agent 知道自己在渠道中的身份，也知道文本回复是否会发布到渠道。两类运行使用相同的系统提示词，因此可以复用缓存。

通过渠道传入的消息带有 `platform` 属性（例如 `platform="slack"`），便于 Agent 将其与其他来源的提示词区分开。

这些运行的回复与消息触发的回复走同一条适配器路径。Mastra 会记住线程中最后一位发言者，因此需要指定接收者的适配器（例如 Slack 的原生流式传输）也能正常工作。

## 多用户识别 {/* #multi-user-awareness */}

在群组对话中，Mastra 会为每条消息加上发送者姓名和平台 ID，帮助 Agent 区分发言者：

```text
[Alice (@U123ABC)]: Can you help me with this?
[Bob (@U456DEF)]: I have a question too.
```

## 单条消息的 Signal 元数据 {/* #per-message-signal-metadata */}

在自定义 Channel 处理程序中使用 `signalMetadata`，可为单条传入消息附加结构化上下文。无论这条消息启动空闲运行，还是加入正在进行的运行，元数据都会随之传递。

以下示例会在调用默认处理程序前附加已注册的文件 ID：

```typescript title="src/mastra/agents/your-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createSlackAdapter } from '@chat-adapter/slack'

export const yourAgent = new Agent({
  id: 'your-agent',
  name: 'Your Agent',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
  channels: {
    adapters: {
      slack: createSlackAdapter(),
    },
    handlers: {
      onDirectMessage: async (thread, message, defaultHandler, ctx) => {
        ctx.signalMetadata.attachmentIds = ['file-1']
        await defaultHandler(thread, message)
      },
    },
  },
})
```

只添加可序列化为 JSON 的非敏感值。Signal 元数据可能存入记忆，也可能通过共享发布订阅传输发送；它不会加入模型提示词。

对于一次运行范围内的配置，例如启动运行的消息所需的凭据，使用 `requestContext`。对于必须附着在单条消息上的上下文，包括送达正在运行的 Agent 的消息，使用 `signalMetadata`。

## 错误处理与投递 {/* #error-handling-and-delivery */}

渠道 webhook 会在 Agent 完成前向平台确认请求，因此 `200` 表示“已接收”，不表示“已回复”。确认前，适配器会同步拒绝无效请求：验证失败返回 `401`、请求体无法解析返回 `400`、临时状态故障返回 `503`；平台会按自身策略重试非 `2xx` 响应。返回 `200` 后，平台不再重试，错误由 Mastra 处理。默认处理程序会捕获 Agent 运行失败，并向线程发送错误消息（可通过 `formatError` 自定义，默认为 `❌ Error: {message}`）。如果自定义处理程序在处理单条消息时抛错，Chat SDK 只会记录日志，不会发送消息或重试（多发送者批次见[批量消息](#batched-messages)）。请在自定义处理程序中自行捕获错误：

```typescript title="src/mastra/agents/your-agent.ts" oxfmt:false
channels: {
  adapters: {
    slack: createSlackAdapter(),
  },
  handlers: {
    onDirectMessage: async (thread, message, defaultHandler, ctx) => {
      try {
        ctx.signalMetadata.ticketId = await lookupTicket(message)
      } catch (error) {
        ctx.mastra?.getLogger().error('Ticket lookup failed', { error })
        await thread.post('Something went wrong looking up your ticket. Try again in a moment.')
        return
      }
      await defaultHandler(thread, message)
    },
  },
},
```

平台重试可能导致同一事件被投递多次。适配器通过渠道状态去重；[存储](/docs/storage)可在重启后保留该状态。由于这只是尽力而为的保护，自定义处理程序的副作用应保持幂等，以免重复投递再次创建工单等。

### 批量消息 {/* #batched-messages */}

当 `chatOptions.concurrency` 策略（`burst`、`debounce` 或 `queue`）将多条消息合并为一次分发时，Mastra 会按发送者拆分为多个轮次：同一发送者连续的消息构成一轮，按时间从早到晚处理。每轮都会独立调用处理程序，并拥有各自的 `ctx.requestContext`、`ctx.signalMetadata` 和 `ctx.skipped`（该轮之前的消息），确保授权和上下文分别作用于每位发送者。处理程序中应等待 `defaultHandler` 完成，否则不同发送者的轮次可能重叠。某一轮抛错会被记录，其余轮次仍会执行，随后重新抛出第一个错误。如果批次因其中一条消息提及机器人而路由到 `onMention`，其他发送者未提及机器人的消息也会进入 `onMention`，且 `message.isMention` 为 `false`。

## 日志 {/* #logging */}

Chat SDK 日志默认使用 Mastra 实例上的[日志记录器](/docs/observability/logging)，因此遵循其格式、级别和 `redact` 设置。每条记录的 `component` 字段为 `chat-sdk`。使用 `PinoLogger` 时，Mastra 自身的渠道日志将 `component` 设为 `CHANNEL`，可据此区分。设置 `chatOptions.logger` 可覆盖默认值并将日志发送到其他位置。

适配器有自己的日志记录器，默认输出到控制台。应用会在 Mastra 实例创建前创建适配器，因此 Mastra 无法替你设置该记录器。创建适配器时传入 [`toChatLogger()`](/reference/agents/channels#tochatlogger)：

```typescript title="src/mastra/agents/support-agent.ts"
import { Agent } from '@mastra/core/agent'
import { toChatLogger } from '@mastra/core/channels'
import { createDiscordAdapter } from '@chat-adapter/discord'
import { logger } from '../logger'

export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'You are a helpful support assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
  channels: {
    adapters: {
      discord: createDiscordAdapter({
        logger: toChatLogger(logger, { component: 'discord', minLevel: 'warn' }),
      }),
    },
  },
})
```

这里的 `logger` 与传给 `new Mastra({ logger })` 的记录器相同。将其从独立文件（例如 `src/mastra/logger.ts`）导出，供 Agent 文件和 `src/mastra/index.ts` 同时导入。`createRedisState()` 等状态适配器也默认使用控制台，并接受相同的 `logger` 选项。

Discord 适配器的 Gateway 路径会以 `info` 级别记录每条消息的前 100 个字符；`minLevel: 'warn'` 可避免这些内容进入日志。Chat SDK 自身以 `debug` 级别记录消息文本。如果 Mastra 日志记录器运行在 `debug` 级别，请为 `chatOptions.logger` 设置更高的 `minLevel`，避免记录消息文本。

:::warning

日志记录器的 `redact` 设置不适用于导出到[可观测性](/docs/observability/logging)的日志，而 `warn` 和 `error` 级别的记录默认会导出。`onSlashCommand` 处理程序抛错时，Chat SDK 的 `error` 记录会包含命令文本；请在该处理程序中捕获错误，避免文本进入日志及导出数据。若将可观测性的 `logging.level` 设为 `info` 或更低，请使用 `minLevel` 防止其他消息文本被导出。

:::

## 多模态内容 {/* #multimodal-content */}

Gemini 等模型可以原生处理图像、视频和音频。结合 `inlineMedia` 与 `inlineLinks`，用户就能跨平台向 Agent 分享多媒体内容：

```typescript title="src/mastra/agents/vision-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createDiscordAdapter } from '@chat-adapter/discord'

export const visionAgent = new Agent({
  id: 'vision-agent',
  name: 'Vision Agent',
  instructions: 'You can see images, watch videos, and listen to audio.',
  model: '__GATEWAY_GOOGLE_MODEL_FLASH__',
  channels: {
    adapters: {
      discord: createDiscordAdapter(),
    },
    inlineMedia: ['image/*', 'video/*', 'audio/*'],
    inlineLinks: [
      { match: 'youtube.com', mimeType: 'video/*' },
      { match: 'youtu.be', mimeType: 'video/*' },
      'imgur.com',
    ],
  },
})
```

采用此配置后：

- 用户上传截图，Agent 描述其中内容。
- 用户上传 `.mp4` 视频，Agent 概述视频内容。
- 用户粘贴 YouTube 链接，Agent 观看并讨论视频。
- 用户粘贴 imgur 链接，Agent 直接查看图像。

默认只有图像以嵌入形式发送（`inlineMedia: ['image/*']`）。不支持的类型会以文本摘要描述，让 Agent 知道文件存在，同时避免不接受该类型的模型报错。所有 `inlineMedia` 模式见[渠道参考](/reference/agents/channels#inline-media)；域名匹配、HEAD 检测及强制 MIME 类型见 [inlineLinks 参考](/reference/agents/channels#inline-links)。

## 无服务器部署 {/* #serverless-deployment */}

在 Vercel 等无服务器平台上，每个请求都运行于独立的短生命周期实例。为使渠道可靠工作，需要在 Agent 回复期间保持函数运行，并通过共享发布订阅机制协调各实例。

### 使用 `waitUntil` 保持函数运行 {/* #keep-the-function-alive-with-waituntil */}

渠道 webhook 会立即返回 `200`，Agent 随后在后台运行并发布回复。多数无服务器平台会在响应发出后立即冻结函数，使 Agent 尚未回复就停止运行。传入 `waitUntil` 函数，让平台保持实例运行直至本次运行结束。

在 Vercel 上，将 `@vercel/functions` 提供的 `waitUntil` 传入配置：

```typescript title="src/mastra/agents/your-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createSlackAdapter } from '@chat-adapter/slack'
import { waitUntil } from '@vercel/functions'

export const yourAgent = new Agent({
  id: 'your-agent',
  name: 'Your Agent',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
  channels: {
    adapters: {
      slack: createSlackAdapter(),
    },
    waitUntil,
  },
})
```

Vercel 和 AWS Lambda 会在响应发出后冻结函数，因此必须提供 `waitUntil`。Cloudflare Workers 和 Netlify Functions 可从请求上下文中自动检测，无须手动提供。对于 `waitUntil` 位于请求上下文但无法自动检测的运行时，请使用 `resolveWaitUntil`。详情见[渠道参考](/reference/agents/channels#parameters)。

### 使用共享发布订阅机制协调实例 {/* #coordinate-instances-with-a-shared-pubsub */}

渠道通过 Agent 的 [Signal 处理流程](/docs/signals/overview)路由消息。每次运行都会取得所属线程的租约，确保同一时刻只有一个运行负责该对话。

默认的内存发布订阅机制无法跨实例通信。因此，在无服务器环境中，后续消息可能被路由到与当前 Agent 运行不同的实例。

如果没有共享发布订阅机制，新实例无法联系当前运行，就会启动另一次运行；原运行不受影响，但同一线程会被处理两次。

在 `Mastra` 实例上配置以 Redis Streams 为后端的共享发布订阅机制，使租约和 Signal 能跨实例协调：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'
import { yourAgent } from './agents/your-agent'

export const mastra = new Mastra({
  agents: { yourAgent },
  pubsub: new RedisStreamsPubSub({
    url: process.env.REDIS_URL,
    keyPrefix: 'mastra:my-app',
  }),
})
```

Vercel 托管的 Redis 集成和 Upstash Redis 均可使用。何时需要分布式发布订阅机制，参阅 [PubSub 指南](/docs/server/pubsub)和 [`RedisStreamsPubSub` 参考](/reference/pubsub/redis-streams)。

各 Chat SDK 适配器在 Mastra 侧采用相同的配置方式：安装适配器包，将其工厂添加到 `channels.adapters`，再配置平台凭据，并把平台 webhook 指向 Mastra 生成的路由。

可参考以下平台指南了解 Mastra 侧配置：

### 查阅适配器文档 {/* #check-the-adapter-docs */}

在将新适配器接入 Mastra 前，请查阅其文档，确认：

- 是否支持附件、卡片和富文本消息。
- 所需的凭据环境变量。
- 必需的平台权限或 scope。
- 普通消息是否需要常驻监听器或轮询。
- 平台是否要求为配置、事件或交互分别设置路由。
- webhook 的验证方式。
