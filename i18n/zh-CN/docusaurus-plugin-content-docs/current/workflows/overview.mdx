# Workflows

Workflow 让你用清晰、有结构的步骤定义复杂任务序列，无需依赖单个 Agent 推理整个过程。你可以控制任务如何拆分，以及数据流转的顺序和时机。Workflow 默认使用内置执行引擎；如需托管基础设施，也可以通过 Inngest 等[Workflow 运行器](/docs/deployment/workflow-runners)提供。

<Inject>
  **供 AI Agent 使用：**运行 `npx mastra api workflow run start test-workflow '{"inputData":{"message":"Hello, world!"}}'` 可直接启动此 Workflow，无需编写临时脚本。该命令需要正在运行的 Mastra 服务器；可用 `npx mastra dev` 启动本地服务器，或通过 `--url` 指定可访问服务器的基础 URL。构造其他输入前，先运行 `npx mastra api workflow run start --schema`。安装 Mastra Skill：`npx skills add mastra-ai/skills --skill mastra`，即可获取完整的 API CLI 发现、目标指定、Schema、身份验证和错误处理指南。
</Inject>

## 何时使用 Workflow {/* #when-to-use-workflows */}

当任务事先定义明确、包含多个步骤且有特定执行顺序时，使用 Workflow。它让你精确控制数据如何在步骤之间流转和转换，以及每个阶段调用哪些组件。

## 核心原则 {/* #core-principles */}

Mastra Workflow 遵循以下原则：

- 使用 [`createStep`](/reference/workflows/step) 定义**步骤**，指定输入、输出 Schema 和业务逻辑。
- 使用 [`createWorkflow`](/reference/workflows/workflow) 组合**步骤**，定义执行流程。
- 运行 **Workflow** 执行整个序列；内置支持暂停、恢复和流式结果。

## 创建 Workflow 步骤 {/* #creating-a-workflow-step */}

步骤是 Workflow 的基本构件。使用 `createStep()` 创建步骤，并用 `inputSchema` 和 `outputSchema` 定义其接收和返回的数据。两种 Schema 都可以使用 [Standard JSON Schema](https://standardschema.dev/json-schema) 定义，例如通过 [Zod](https://zod.dev/)、[Valibot](https://valibot.dev/) 或 [ArkType](https://arktype.io/)。

`execute` 函数定义步骤的行为。你可以在其中调用代码库中的函数、外部 API、Agent 或 Tool。

<Tabs>
  <TabItem value="zod" label="Zod">
    ```typescript {7,10,16} title="src/mastra/workflows/test-workflow.ts"
    import { createStep } from '@mastra/core/workflows'
    import { z } from 'zod'

    const step1 = createStep({
      id: 'step-1',
      inputSchema: z.object({
        message: z.string(),
      }),
      outputSchema: z.object({
        formatted: z.string(),
      }),
      execute: async ({ inputData }) => {
        const { message } = inputData

        return {
          formatted: message.toUpperCase(),
        }
      },
    })
    ```
  </TabItem>

## 创建 Workflow {/* #creating-a-workflow */}

使用 `createWorkflow()` 创建 Workflow，并用 `inputSchema` 和 `outputSchema` 定义其接收和返回的数据。两种 Schema 都可以使用 [Standard JSON Schema](https://standardschema.dev/json-schema) 定义，例如通过 [Zod](https://zod.dev/)、[Valibot](https://valibot.dev/) 或 [ArkType](https://arktype.io/)。用 `.then()` 添加步骤，最后调用 `.commit()` 完成 Workflow。

### 理解控制流 {/* #understanding-control-flow */}

Workflow 可以通过多种方法组合。所选方法决定每个步骤的 Schema 应如何设计。详情请参阅[控制流](/docs/workflows/control-flow)。

## Studio {/* #studio */}

打开 [Studio](/docs/studio/overview)，在 **Workflows** 标签页中选择一个 Workflow。

- **图视图**：中央面板展示 Workflow 的步骤和执行流程。
- **输入表单**：右侧边栏根据 Workflow 的 `inputSchema` 生成表单。填写后即可启动运行。
- **实时状态**：运行期间，图中会实时更新每个步骤的状态。侧边栏显示 Workflow 的输入、输出、状态和日志。
- [**时间回溯**](/docs/workflows/time-travel)：运行完成后，重放单个步骤以检查或重试。

## Workflow 状态 {/* #workflow-state */}

Workflow 状态让你跨步骤共享值，无需在每个步骤的 inputSchema 和 outputSchema 中逐级传递。可用状态跟踪进度、累积结果，或在整个 Workflow 中共享配置。

```typescript title="src/mastra/workflows/test-workflow.ts"
import { createStep } from '@mastra/core/workflows'
import { z } from 'zod'

const step1 = createStep({
  id: 'step-1',
  inputSchema: z.object({ message: z.string() }),
  outputSchema: z.object({ formatted: z.string() }),
  stateSchema: z.object({ counter: z.number() }),
  execute: async ({ inputData, state, setState }) => {
    // Read from state
    console.log(state.counter)

    // Update state for subsequent steps
    setState({ ...state, counter: state.counter + 1 })

    return { formatted: inputData.message.toUpperCase() }
  },
})
```

有关状态 Schema、初始状态、暂停与恢复之间的持久化以及嵌套 Workflow 的完整说明，请参阅 [Workflow 状态](/docs/workflows/workflow-state)。

## 将 Workflow 用作步骤 {/* #workflows-as-steps */}

将 Workflow 用作步骤，可以在更大的流程中复用其逻辑。输入和输出遵循[核心原则](/docs/workflows/control-flow)中所述的相同 Schema 规则。

```typescript {29} title="src/mastra/workflows/test-workflow.ts" oxfmt:false
import { createWorkflow, createStep } from '@mastra/core/workflows';
import { z } from 'zod';

const step1 = createStep({...});
const step2 = createStep({...});

const childWorkflow = createWorkflow({
  id: "child-workflow",
  inputSchema: z.object({
    message: z.string()
  }),
  outputSchema: z.object({
    emphasized: z.string()
  })
})
  .then(step1)
  .then(step2)
  .commit();

export const testWorkflow = createWorkflow({
  id: "test-workflow",
  inputSchema: z.object({
    message: z.string()
  }),
  outputSchema: z.object({
    emphasized: z.string()
  })
})
  .then(childWorkflow)
  .commit();
```

### 克隆 Workflow {/* #cloning-a-workflow */}

如果需要复用 Workflow 逻辑，但以新 ID 单独跟踪它，请使用 `cloneWorkflow()`。每个克隆都会独立运行，并在日志和可观测性工具中显示为单独的 Workflow。

```typescript oxfmt:false {6} title="src/mastra/workflows/test-workflow.ts"
import { cloneWorkflow, createWorkflow, createStep } from "@mastra/core/workflows";

const step1 = createStep({...});

const parentWorkflow = createWorkflow({...})
const clonedWorkflow = cloneWorkflow(parentWorkflow, { id: "cloned-workflow" });

export const testWorkflow = createWorkflow({...})
  .then(step1)
  .then(clonedWorkflow)
  .commit();
```

## 注册 Workflow {/* #registering-a-workflow */}

在 Mastra 实例中注册 Workflow，供整个应用使用。注册后，Agent 或 Tool 可以调用它，它也能访问日志和可观测性等共享资源：

```typescript {5} title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { testWorkflow } from './workflows/test-workflow'

export const mastra = new Mastra({
  workflows: { testWorkflow },
})
```

## 引用 Workflow {/* #referencing-a-workflow */}

你可以从 Agent、Tool、Mastra Client 或命令行运行 Workflow。根据使用方式，在 `mastra` 或 `mastraClient` 实例上调用 `.getWorkflow()` 获取引用：

```typescript
const testWorkflow = mastra.getWorkflow('testWorkflow')
```

:::note

相比直接导入，推荐使用 `mastra.getWorkflow()`，原因有两个：

1. 它可以访问 Mastra 实例的配置，包括日志记录器、遥测、存储、已注册的 Agent 和向量存储。
1. 它能完整推断 Workflow 输入和输出 Schema 的 TypeScript 类型。

使用 Workflow 的**注册键**（添加到 Mastra 时使用的键）调用 `getWorkflow()`。`getWorkflowById()` 按 Workflow 的 `id` 属性检索，但无法提供同等程度的类型推断。
:::

## 运行 Workflow {/* #running-workflows */}

Workflow 有两种运行模式：start 会等待所有步骤完成后再返回，stream 则在运行期间发出事件。只需要最终结果时选择 start；需要监控进度或在步骤完成时触发操作时选择 stream。

<Tabs>
  <TabItem value="start" label=".start()">
    先用 `createRun()` 创建 Workflow 运行实例，再调用 `.start()`，传入符合 Workflow `inputSchema` 的 `inputData`。Workflow 会执行所有步骤并返回最终结果。

    ```typescript
    const run = await testWorkflow.createRun()

    const result = await run.start({
      inputData: {
        message: 'Hello world',
      },
    })

    if (result.status === 'success') {
      console.log(result.result)
    }
    ```
  </TabItem>

  <TabItem value="stream" label=".stream()">
    先用 `.createRun()` 创建 Workflow 运行实例，再调用 `.stream()`，传入符合 Workflow `inputSchema` 的 `inputData`。遍历 `fullStream` 跟踪进度，随后等待 `result` 获取最终结果。

    ```typescript
    const run = await testWorkflow.createRun()

    const stream = run.stream({
      inputData: {
        message: 'Hello world',
      },
    })

    for await (const chunk of stream.fullStream) {
      console.log(chunk)
    }

    // Get the final result (same type as run.start())
    const result = await stream.result

    if (result.status === 'success') {
      console.log(result.result)
    }
    ```
  </TabItem>
</Tabs>

### Workflow 结果类型 {/* #workflow-result-type */}

`run.start()` 和 `stream.result` 都会根据 `status` 返回可辨识联合类型；状态可能为 `success`、`failed`、`suspended`、`tripwire` 或 `paused`。无论状态如何，都可以安全访问 `result.status`、`result.input`、`result.steps`，以及可选的 `result.state`。

此外，不同状态还提供不同的属性：

| 状态 | 专有属性 | 说明 |
| - | - | - |
| `success` | `result` | Workflow 的输出数据 |
| `failed` | `error` | 导致失败的错误 |
| `tripwire` | `tripwire` | 包含 `reason`、`retry?`、`metadata?`、`processorId?` |
| `suspended` | `suspendPayload`、`suspended` | 暂停数据及已暂停步骤路径的数组 |
| `paused` | _（无）_ | 只有通用属性 |

要访问特定状态的属性，请先检查 `status`：

```typescript
const result = await run.start({ inputData: { message: 'Hello world' } })

if (result.status === 'success') {
  console.log(result.result) // Only available when status is "success"
} else if (result.status === 'failed') {
  console.log(result.error.message)
} else if (result.status === 'suspended') {
  console.log(result.suspendPayload)
}
```

## 流式传输 {/* #streaming */}

有关通用 `writer` API 的用法，请参阅[流式传输](/docs/guides/streaming#writer-api)。

### 检查 Workflow 流的载荷 {/* #inspecting-workflow-stream-payloads */}

写入流的事件会包含在发出的数据块中。检查这些数据块，可以读取事件类型、中间值或特定步骤的数据等自定义字段。

```typescript
const testWorkflow = mastra.getWorkflow('testWorkflow')

const run = await testWorkflow.createRun()

const stream = await run.stream({
  inputData: {
    value: 'initial data',
  },
})

for await (const chunk of stream) {
  console.log(chunk)
}

if (result!.status === 'suspended') {
  // if the workflow is suspended, we can resume it with the resumeStream method
  const resumedStream = await run.resumeStream({
    resumeData: { value: 'resume data' },
  })

  for await (const chunk of resumedStream) {
    console.log(chunk)
  }
}
```

### 恢复中断的 Workflow 流 {/* #resuming-an-interrupted-workflow-stream */}

如果 Workflow 流因任何原因关闭或中断，可以用 `resumeStream` 方法恢复。它会返回一个新的 `ReadableStream`，供你继续观察 Workflow 事件。

```typescript
const newStream = await run.resumeStream()

for await (const chunk of newStream) {
  console.log(chunk)
}
```

### 在 Workflow 中使用 Agent {/* #workflow-using-an-agent */}

将 Agent 的 `textStream` 传给 Workflow 步骤的 `writer`。这样可以流式传输部分输出，Mastra 也会自动将 Agent 的用量计入 Workflow 运行。

```typescript
import { createStep } from '@mastra/core/workflows'
import { z } from 'zod'

export const testStep = createStep({
  execute: async ({ inputData, mastra, writer }) => {
    const { city } = inputData

    const testAgent = mastra?.getAgent('testAgent')
    const stream = await testAgent?.stream(`What is the weather in ${city}?`)

    await stream!.textStream.pipeTo(writer!)

    return {
      value: await stream!.text,
    }
  },
})
```

## 重启运行中的 Workflow {/* #restarting-active-workflow-runs */}

如果 Workflow 运行失去与服务器的连接，可以从最后一个正在执行的步骤重启。这适用于服务器断开连接时可能仍在执行的长时间运行任务。重启后，Workflow 会从该步骤恢复并继续执行。

### 使用 `restartAllActiveWorkflowRuns()` 重启 Workflow 的所有活动运行 {/* #restarting-all-active-workflow-runs-of-a-workflow-with-restartallactiveworkflowruns */}

使用 `restartAllActiveWorkflowRuns()` 重启某个 Workflow 的所有活动运行，无需逐个遍历并手动重启。

```typescript
workflow.restartAllActiveWorkflowRuns()
```

多个运行会并发重启，并发数由 `recovery.workflowConcurrency` 控制，默认最多为 `5`。如果运行之间共享不能并行执行的副作用，请在 Mastra 配置中设为 `1`。

如需排除由 `Mastra.restartAllActiveWorkflowRuns()` 在启动时自动触发的重启，请在 Workflow 的 `options` 中设置 `autoRestartActiveRuns: false`。有副作用的 Workflow 可能不适合统一重启。持久化 Agent Workflow 会自动设置该选项，因为它们由显式启用的 `recovery.durableAgents: 'auto'` 路径负责恢复。

运行期间，Mastra 会持有该运行的存储租约，并在后台续租。若租约尚未到期，`restart()` 会拒绝接管、抛出 `WORKFLOW_RESTART_RUN_OWNED` 错误，扫描也会跳过该运行。租约只是协作约定，不能阻止写入。如果进程停止续租但仍在执行步骤，例如事件循环阻塞超过租约 TTL，恢复操作可能再次执行该步骤。`workflow.restartAllActiveWorkflowRuns()` 不会重新检查而直接跳过这类运行；如需恢复，请在租约到期后再次调用。未支持运行所有权的存储适配器沿用旧行为，会重启所有活动运行。

服务器启动时调用的 `mastra.restartAllActiveWorkflowRuns()` 只会在默认引擎的运行停止后重启它：没有实例持有其租约，且运行和租约在 `recovery.workflowGraceMs`（默认 2 秒）内均未变化。仍在执行或刚停止的运行交由[恢复循环](#recovery-loop)处理。

对于使用会重新投递未确认事件的消息代理（Redis Streams、Valkey Streams、Google Cloud Pub/Sub）的 pubsub，事件驱动运行由消息代理恢复：工作进程在步骤中途停止时，消息代理会把该步骤事件投递给另一工作进程，启动中的实例不会重启该运行。定时运行是例外，其事件保留在触发事件的进程中，因此会由恢复机制重启。对于其他 pubsub，包括默认的进程内 pubsub，恢复机制会立即重启所有活动的事件驱动运行。进程内 pubsub 仅在单个进程内投递事件，因此事件驱动 Workflow 不支持多个实例共用一个存储适配器并使用它。

重启后的运行会再次执行中断的步骤，即使该步骤在进程停止前已经完成，只要结果尚未保存。在事件驱动引擎上，如果步骤结果已经保存，那么即使事件晚到（例如消息代理重新投递，或保存结果时调用了 `restart()`），也不会再次执行该步骤，而是从已保存的结果继续。这需要支持运行所有权的存储适配器。设置了 `autoRestartActiveRuns: false` 的 Workflow（包括持久化 Agent Workflow）仍会再次执行步骤。因此，有副作用的步骤应具有幂等性，避免重复执行产生额外影响。

步骤的 `execute` 函数会收到 `runId` 和 `workflowId`。将它们与传给 `createStep()` 的步骤 `id` 组合；如果步骤执行多个副作用，再为每个副作用加上名称，即可构造幂等键。

有些步骤还需要从输入中获取幂等键的一部分：

- 嵌套 Workflow 在恢复或重新投递时可能获得新的 `runId`。将父 Workflow 的 `runId` 传入嵌套 Workflow 的输入，并用它代替嵌套运行的 `runId`。
- `foreach` 会为每个元素运行同一步骤一次。将能标识该元素的 ID 加入幂等键。
- 循环每轮都会运行同一步骤。从步骤返回轮次编号，并在下一轮从输入中读取。重复执行或恢复同一轮时输入相同，因此编号也不变。

有关 Agent 调用的 Tool，请参阅[让 Tool 可安全重复执行](/docs/harness/durable-agents#make-tools-safe-to-repeat)。

### 恢复循环 {/* #recovery-loop */}

`mastra.startWorkers()` 还会在运行编排工作进程的实例上启动恢复循环。每隔 `recovery.workflowScanIntervalMs`（默认 60 秒，可能上下浮动五分之一），循环会按 `restartAllActiveWorkflowRuns()` 的相同规则重启已停止的默认引擎运行。实例崩溃后，首次扫描须等该运行的租约到期（`MASTRA_AGENT_THREAD_LEASE_TTL_MS`，默认 15 秒）且超过 `recovery.workflowGraceMs`。如果扫描时运行仍在宽限期内，下一次扫描会在宽限期结束后执行，但不会早于 1 秒后。

共享存储适配器的实例通过存储中的租约行选出一个循环领导者。只有领导者的循环会列出运行；其他实例的循环只尝试接任。领导者会一直担任该角色，直到调用 `stopWorkers()` 或 `shutdown()` 交还领导权，或在崩溃后租约到期。无论谁是领导者，每个实例在启动时仍会通过 `restartAllActiveWorkflowRuns()` 重启自己已停止的默认引擎运行。两次启动之间，循环只恢复领导者已注册的 Workflow；如果多个实例在同一存储中注册不同 Workflow，只有领导者的 Workflow 能由循环恢复，其他实例的运行要等到下一次启动。循环重启的运行会在领导者实例上执行。

```typescript title="src/mastra/index.ts"
export const mastra = new Mastra({
  recovery: { workflowScanIntervalMs: 30_000 },
})
```

恢复循环不会重启事件驱动运行。会重新投递未确认事件的消息代理负责恢复这类运行；对于其他 pubsub，`restartAllActiveWorkflowRuns()` 会在启动时重启。循环也会跳过设置 `autoRestartActiveRuns: false` 的 Workflow；未注册其他默认引擎 Workflow 的实例不会争取领导者租约行。若 `recovery.workflows` 设为 `'off'`，或实例以 `workers: false` 启动，或 `MASTRA_WORKERS` 过滤器未包含 `orchestration`，或存储适配器不支持运行所有权，循环都不会运行。只调用 `restartAllActiveWorkflowRuns()` 而从未调用 `startWorkers()` 的进程，也不会运行恢复循环。

### 使用 `restart()` 重启活动运行 {/* #restarting-an-active-workflow-run-with-restart */}

使用 `restart()` 从最后一个活动步骤重启活动运行。运行会从该步骤恢复，并继续执行后续步骤。

```typescript
const run = await workflow.createRun()

const result = await run.start({ inputData: { value: 'initial data' } })

const restartedResult = await run.restart()
```

### 识别活动运行 {/* #identifying-active-workflow-runs */}

活动运行的 `status` 为 `running` 或 `waiting`。你可以检查 Workflow 的 `status`，确认它是否处于活动状态，并用 `active` 标识活动运行。

```typescript
const activeRuns = await workflow.listActiveWorkflowRuns()
if (activeRuns.runs.length > 0) {
  console.log(activeRuns.runs)
}
```

:::note

Mastra 服务器启动时，会重启不再由任何实例执行的活动运行；其恢复循环会继续处理默认引擎的运行。

:::

## 使用 `RequestContext` {/* #using-requestcontext */}

使用 [RequestContext](/docs/server/request-context) 读取请求特定的值，以便根据请求上下文调整行为。

```typescript title="src/mastra/workflows/test-workflow.ts"
import { createStep } from '@mastra/core/workflows'

export type UserTier = {
  'user-tier': 'enterprise' | 'pro'
}

const step1 = createStep({
  execute: async ({ requestContext }) => {
    const userTier = requestContext.get('user-tier') as UserTier['user-tier']

    const maxResults = userTier === 'enterprise' ? 1000 : 50

    return { maxResults }
  },
})
```

有关详情，请参阅[请求上下文](/docs/server/request-context)。

:::tip

有关类型安全的请求上下文 Schema 验证，请参阅[Schema 验证](/docs/server/request-context#schema-validation)。

:::
