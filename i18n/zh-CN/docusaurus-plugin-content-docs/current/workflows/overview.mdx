# Workflow程

Workflow可让您通过清晰、结构化的步骤定义复杂的任务序列，而不是依赖一个Agent来推理整个过程。您可以控制任务分解以及数据流和时间安排。Workflow程默认使用内置执行引擎，而托管基础架构可通过[workflow runners](/docs/deployment/workflow-runners)比如英格斯特。

<Inject>
  **对于人工智能Agent：**&#x8DD1;步`npx mastra api workflow run start test-workflow '{"inputData":{"message":"Hello, world!"}}'` to start this workflow directly instead of writing a temporary script. The command requires a running Mastra server; start the local server with `npx mastra dev`，或传递可访问服务器的基本 URL`--url`。跑步`npx mastra api workflow run start --schema`在构建不同的输入之前。安装 Mastra 的技能`npx skills add mastra-ai/skills --skill mastra`获取完整的 API CLI 发现、定位、架构、身份验证和错误处理指南。
</Inject>

## 何时使用Workflow程 {/* #when-to-use-workflows */}

将Workflow用于预先明确定义的任务，并涉及具有特定执行顺序的多个步骤。它们使您能够对数据在步骤之间流动和转换的方式以及每个阶段调用哪些原语进行细粒度控制。

## 核心原则 {/* #core-principles */}

Mastra Workflow程按照以下原则运行：

* 定义**steps** with [`createStep`](/reference/workflows/step), specifying input/output schemas and business logic.
* 构成**steps** with [`createWorkflow`](/reference/workflows/workflow) to define the execution flow.
* 跑步**workflows** to execute the entire sequence, with built-in support for suspension, resumption, and streaming results.

## 创建Workflow程步骤 {/* #creating-a-workflow-step */}

步骤是Workflow程的构建块。使用创建步骤`createStep()` with `inputSchema` and `outputSchema` to define the data it accepts and returns. You can define both schemas using [Standard JSON Schema](https://standardschema.dev/json-schema) ([Zod](https://zod.dev/), [Valibot](https://valibot.dev/), [ArkType](https://arktype.io/), etc.).

这`execute` function defines what the step does. Use it to call functions in your codebase, external APIs, agents, or tools.

## Workflow程状态 {/* #workflow-state */}

Workflow状态允许您跨步骤共享值，而无需将它们传递给每个步骤的 inputSchema 和 outputSchema。使用状态来跟踪进度或累积结果，或者在整个Workflow程中共享配置。

```typescript title="src/mastra/workflows/test-workflow.ts"
import { createStep } from '@mastra/core/workflows'
import { z } from 'zod'

const step1 = createStep({
  id: 'step-1',
  inputSchema: z.object({ message: z.string() }),
  outputSchema: z.object({ formatted: z.string() }),
  stateSchema: z.object({ counter: z.number() }),
  execute: async ({ inputData, state, setState }) => {
    // Read from state
    console.log(state.counter)

    // Update state for subsequent steps
    setState({ ...state, counter: state.counter + 1 })

    return { formatted: inputData.message.toUpperCase() }
  },
})
```

访问[Workflow State](/docs/workflows/workflow-state) for complete documentation on state schemas, initial state, persistence across suspend/resume, and nested workflows.

## Workflow程作为步骤 {/* #workflows-as-steps */}

使用Workflow作为在更大的组合中重用其逻辑的步骤。输入和输出遵循中描述的相同模式规则[Core principles](/docs/workflows/control-flow).

```typescript {29} title="src/mastra/workflows/test-workflow.ts" oxfmt:false
import { createWorkflow, createStep } from '@mastra/core/workflows';
import { z } from 'zod';

const step1 = createStep({...});
const step2 = createStep({...});

const childWorkflow = createWorkflow({
  id: "child-workflow",
  inputSchema: z.object({
    message: z.string()
  }),
  outputSchema: z.object({
    emphasized: z.string()
  })
})
  .then(step1)
  .then(step2)
  .commit();

export const testWorkflow = createWorkflow({
  id: "test-workflow",
  inputSchema: z.object({
    message: z.string()
  }),
  outputSchema: z.object({
    emphasized: z.string()
  })
})
  .then(childWorkflow)
  .commit();
```

### 克隆Workflow程 {/* #cloning-a-workflow */}

使用克隆Workflow程`cloneWorkflow()` when you want to reuse its logic but track it separately under a new ID. Each clone runs independently and shows up as a distinct workflow in logs and observability tools.

```typescript oxfmt:false {6} title="src/mastra/workflows/test-workflow.ts"
import { cloneWorkflow, createWorkflow, createStep } from "@mastra/core/workflows";

const step1 = createStep({...});

const parentWorkflow = createWorkflow({...})
const clonedWorkflow = cloneWorkflow(parentWorkflow, { id: "cloned-workflow" });

export const testWorkflow = createWorkflow({...})
  .then(step1)
  .then(clonedWorkflow)
  .commit();
```

## 引用Workflow程 {/* #referencing-a-workflow */}

您可以从Agent、Tool、Mastra 客户端或命令行运行Workflow程。通过致电获取参考`.getWorkflow()` on your `mastra` or `mastraClient` instance, depending on your setup:

```typescript
const testWorkflow = mastra.getWorkflow('testWorkflow')
```

：：：笔记`mastra.getWorkflow()` is preferred over a direct import for two reasons:

1. 它提供对 Mastra 实例配置的访问（记录器、遥测、存储、注册Agent和矢量存储）
2. 它为Workflow输入和输出模式提供完整的 TypeScript 类型推断

使用`getWorkflow()` with the workflow's **registration key** (the key used when adding it to Mastra). `getWorkflowById()` retrieves workflows by their `id` property, but it doesn't provide the same level of type inference.

## 运行Workflow程 {/* #running-workflows */}

Workflow可以以两种模式运行：开始等待所有步骤完成后再返回，而流在执行期间发出事件。选择适合您的用例的方法：当您只需要最终结果时开始，当您想要监控进度或在步骤完成时触发操作时进行流式传输。

<Tabs>
  <TabItem value="start" label=".start()">
    使用创建Workflow运行实例`createRun()`, then call `.start()` with `inputData` matching the workflow's `inputSchema`. The workflow executes all steps and returns the final result.

    ```typescript
    const run = await testWorkflow.createRun()

    const result = await run.start({
      inputData: {
        message: 'Hello world',
      },
    })

    if (result.status === 'success') {
      console.log(result.result)
    }
    ```
  </TabItem>

  <TabItem value="stream" label=".stream()">
    使用创建Workflow运行实例`.createRun()`, then call `.stream()` with `inputData` matching the workflow's `inputSchema`. Iterate over `fullStream` to track progress, then await `result` to get the final workflow result.

    ```typescript
    const run = await testWorkflow.createRun()

    const stream = run.stream({
      inputData: {
        message: 'Hello world',
      },
    })

    for await (const chunk of stream.fullStream) {
      console.log(chunk)
    }

    // Get the final result (same type as run.start())
    const result = await stream.result

    if (result.status === 'success') {
      console.log(result.result)
    }
    ```
  </TabItem>
</Tabs>

### Workflow程结果类型 {/* #workflow-result-type */}

两个都`run.start()` and `stream.result` return a discriminated union based on the `status` property, which can be `success`, `failed`, `suspended`, `tripwire`, or `paused`. You can always safely access `result.status`, `result.input`, `result.steps`, and optionally `result.state` regardless of the status.

此外，根据状态，可以使用不同的属性：

|状态 |独特的性能|描述 |
| - | - | - |
|`success` | `result` | The workflow's output data |
| `failed` | `error` | The error that caused the failure |
| `tripwire` | `tripwire` | Contains `reason`, `retry?`, `metadata?`, `processorId?` |
| `suspended` | `suspendPayload`, `suspended` | Suspension data and array of suspended step paths |
| `paused` | *(none)* | Only common properties available |

要访问特定于状态的属性，请检查`status` first:

```typescript
const result = await run.start({ inputData: { message: 'Hello world' } })

if (result.status === 'success') {
  console.log(result.result) // Only available when status is "success"
} else if (result.status === 'failed') {
  console.log(result.error.message)
} else if (result.status === 'suspended') {
  console.log(result.suspendPayload)
}
```

### 使用Agent的Workflow程 {/* #workflow-using-an-agent */}

import { createStep } from '@mastra/core/workflows'

## 重新启动活动Workflow程运行 {/* #restarting-active-workflow-runs */}

当Workflow运行失去与服务器的连接时，可以从最后一个活动步骤重新启动。这对于长时间运行的Workflow非常有用，这些工​​作流在服务器失去连接时可能仍在运行。重新启动Workflow程运行将从最后一个活动步骤恢复执行，并且Workflow程将从那里继续。

### 重新启动Workflow程的所有活动Workflow程运行`restartAllActiveWorkflowRuns()` {/* #restarting-all-active-workflow-runs-of-a-workflow-with-restartallactiveworkflowruns */}

使用`restartAllActiveWorkflowRuns()` to restart all active workflow runs of a workflow. This helps restart all active workflow runs of a workflow, without having to manually loop through each run and restart.

```typescript
workflow.restartAllActiveWorkflowRuns()
```

同时运行重新启动，最多`recovery.workflowConcurrency` at a time (default `5`). Set it to `1` in the Mastra config if your runs share side effects that must not run in parallel.

将Workflow程排除在由以下原因触发的自动启动时重新启动之外：`Mastra.restartAllActiveWorkflowRuns()`, set `autoRestartActiveRuns: false` in the workflow's `options`. This is useful for workflows with side effects that must not be re-driven by a blanket restart. Durable agent workflows set this automatically because their recovery is owned by the opt-in `recovery.durableAgents: 'auto'` path.

当运行执行时，Mastra 会保留其存储租约并在后台更新它。`restart()` refuses to take over a run whose lease hasn't expired: it throws a `WORKFLOW_RESTART_RUN_OWNED` error and the sweep skips the run. The lease is advisory and doesn't fence writes. If a process stops renewing its lease but keeps executing a step, for example because its event loop is blocked for longer than the lease TTL, recovery can run that step a second time. `workflow.restartAllActiveWorkflowRuns()` skips such a run without a recheck, so call it after the lease expires if you need to recover that run. Storage adapters without run-ownership support keep the previous behavior and restart every active run.

`mastra.restartAllActiveWorkflowRuns()`，服务器在启动时调用它，仅在默认引擎停止后重新启动它：没有实例保留其租约，并且运行及其租约都没有更改`recovery.workflowGraceMs` (2 seconds by default). A run that's still running, or stopped more recently, is left to the [recovery loop](#recovery-loop).

Evented 在 pubsub 上运行，其Agent重新传递未确认的事件（Redis Streams、Valkey Streams、Google Cloud Pub/Sub）留给Agent：当工作进程中途停止时，Agent将该步骤的事件重新传递给另一个工作进程，并且启动实例不会重新启动运行。计划运行是例外，因为它们的事件保留在触发它们的进程中，因此恢复会重新启动它们。在任何其他 pubsub 上，包括默认的进程内发布订阅，恢复都会立即重新启动每个活动的事件运行。进程内 pubsub 仅在一个进程内传递事件，因此事件Workflow不支持使用它在一个存储上运行多个实例。

重新启动的运行会再次运行中断的步骤，即使该步骤在进程停止之前完成，但其结果未保存。在事件引擎上，当事件延迟到达时，已保存其结果的步骤不会再次运行，例如在Agent重新交付或`restart()` that ran while the step was saving its result. The run continues from the saved result instead. This needs a storage adapter with run-ownership support. Workflows that set `autoRestartActiveRuns: false`, including durable agent workflows, run the step again. Make steps with side effects idempotent, so a repeated step has no additional effect.

一步的`execute` function receives `runId` and `workflowId`. Combine them with the `id` you gave the step in `createStep()`, plus a name for each side effect when the step performs more than one, to build an idempotency key.

有些步骤需要部分密钥来自其输入：

* 嵌套Workflow程可以接收新的`runId` when it's recovered or redelivered. Pass the parent's `runId` into the nested workflow's input and use it in place of the nested `runId`.
* `foreach`每个项目运行一次相同的步骤。从步骤的输入添加一个标识该项目的 ID。
* 循环在每次迭代中运行相同的步骤。从步骤中返回迭代编号，并在下一次迭代时从输入中读取它。重复或恢复的迭代接收相同的输入，因此数字不会改变。

有关Agent调用的Tool，请参阅[make tools safe to repeat](/docs/harness/durable-agents#make-tools-safe-to-repeat).

### 恢复循环 {/* #recovery-loop */}

`mastra.startWorkers()`还会在运行编排工作线程的实例上启动恢复循环。每一个`recovery.workflowScanIntervalMs` (60 seconds by default, give or take a fifth), it restarts the default-engine runs that stopped, by the same rule as `restartAllActiveWorkflowRuns()`. A run whose instance crashed is restarted at the first pass after its lease expired (`MASTRA_AGENT_THREAD_LEASE_TTL_MS`, 15 seconds by default) and `recovery.workflowGraceMs` passed. When a pass finds a run in its grace period, the next pass runs once that period ends, but no sooner than a second later.

共享存储适配器的实例通过存储中的租用行选择一个循环领导者。仅运行领导者的循环列表。其他实例的循环只是试图取代它的位置。领导者一直保持这个角色，直到其`stopWorkers()` or `shutdown()` hands it back, or until its lease expires after a crash. With `restartAllActiveWorkflowRuns()` at boot, each instance still restarts its own stopped default-engine runs, whichever instance leads. Between boots, the loop recovers only the workflows the leader registers, so instances that register different workflows on one storage get loop recovery for the leader's workflows only and the others' runs at their next boot. A run the loop restarts executes on the leader.

```typescript title="src/mastra/index.ts"
export const mastra = new Mastra({
  recovery: { workflowScanIntervalMs: 30_000 },
})
```

循环永远不会重新启动事件运行。重新传递未确认事件的Agent会恢复它们，并在其他 pubsub 上`restartAllActiveWorkflowRuns()` restarts them at boot. The loop also leaves workflows that set `autoRestartActiveRuns: false` alone, and an instance that registers no other default-engine workflow never claims the leader row. It doesn't run when `recovery.workflows` is `'off'`, on an instance started with `workers: false` or a `MASTRA_WORKERS` filter without `orchestration`, or on a storage adapter without run-ownership support. A process that calls `restartAllActiveWorkflowRuns()` but never `startWorkers()` runs no loop.

### 重新启动活动Workflow程运行`restart()` {/* #restarting-an-active-workflow-run-with-restart */}

使用`restart()` to restart an active workflow run from the last active step. This will resume execution from the last active step, and the workflow will continue from there.

```typescript
const run = await workflow.createRun()

const result = await run.start({ inputData: { value: 'initial data' } })

const restartedResult = await run.restart()
```

### 识别活动Workflow程运行 {/* #identifying-active-workflow-runs */}

当Workflow程运行处于活动状态时，它将有一个`status` of `running` or `waiting`. You can check the workflow's `status` to confirm it's active, and use `active` to identify the active workflow run.

```typescript
const activeRuns = await workflow.listActiveWorkflowRuns()
if (activeRuns.runs.length > 0) {
  console.log(activeRuns.runs)
}
```

：：：笔记

当 Mastra 服务器启动时，它会重新启动不再运行的实例的活动Workflow运行，并且其恢复循环会针对默认引擎运行继续执行此操作。

## 使用`RequestContext` {/* #using-requestcontext */}

使用[RequestContext](/docs/server/request-context) to access request-specific values. This lets you conditionally adjust behavior based on the context of the request.

```typescript title="src/mastra/workflows/test-workflow.ts"
import { createStep } from '@mastra/core/workflows'

export type UserTier = {
  'user-tier': 'enterprise' | 'pro'
}

const step1 = createStep({
  execute: async ({ requestContext }) => {
    const userTier = requestContext.get('user-tier') as UserTier['user-tier']

    const maxResults = userTier === 'enterprise' ? 1000 : 50

    return { maxResults }
  },
})
```

访问[Request Context](/docs/server/request-context) for more information.

对于类型安全的请求上下文架构验证，请参阅[Schema Validation](/docs/server/request-context#schema-validation).
