# 定时运行 Workflow

在 Workflow 中声明 `schedule` 字段，Mastra 就会按指定的 cron 表达式触发它。仍可通过 `workflow.start()` 直接调用同一个 Workflow；定时触发和手动运行走同一套执行流程。

## 快速入门 {/* #quickstart */}

以下 Workflow 每天纽约时间上午 9 点运行。像注册其他 Workflow 一样将它注册到 `Mastra`，调度器会自动发现它。

```typescript title="src/mastra/workflows/daily-report.ts"
import { createWorkflow, createStep } from '@mastra/core/workflows'
import { z } from 'zod'

const sendReport = createStep({
  id: 'send-report',
  inputSchema: z.object({ userId: z.string() }),
  outputSchema: z.object({ ok: z.boolean() }),
  execute: async ({ inputData }) => {
    // ...send the report for inputData.userId
    return { ok: true }
  },
})

export const dailyReport = createWorkflow({
  id: 'daily-report',
  inputSchema: z.object({ userId: z.string() }),
  outputSchema: z.object({ ok: z.boolean() }),
  schedule: {
    cron: '0 9 * * *',
    timezone: 'America/New_York',
    inputData: { userId: 'system' },
  },
})
  .then(sendReport)
  .commit()
```

无须单独注册定时任务。`Mastra` 启动时，调度器会直接读取 Workflow 上的 `schedule`。

## 投递保证 {/* #delivery-guarantees */}

Workflow 的定时启动事件按尽力而为的原则发布。调度器先领取本次触发，再尝试发布启动事件，最多尝试三次。如果尝试耗尽或发布端崩溃，本次触发可能被跳过。跳过的触发不会自动补发，但后续仍可按计划触发。状态为 `completed` 表示已无后续触发，并不确认 Workflow 已执行。失败报告和手动重跑注意事项见[定时任务投递保证](/reference/schedules/overview#delivery-guarantees)。

## 执行引擎 {/* #execution-engine */}

声明 `schedule` 不会改变 Workflow 的执行方式。和 `workflow.start()` 或 HTTP 触发一样，定时触发在运行调度器的宿主进程内执行。直接运行声明了 `schedule` 的 Workflow 不需要额外配置存储或 Worker。

分离部署 Worker 时例外。只要环境变量 [`MASTRA_WORKERS`](/reference/workers/overview#mastra_workers) 设了值，即使是 `false`，`createWorkflow` 也会使用**事件驱动执行引擎**构建定时 Workflow，使部署中的各个进程采用同样的执行方式。此时定时触发由[编排 Worker](/docs/deployment/workers#orchestration-worker)执行，Mastra 在创建 Workflow 时会在控制台记录警告。公共 API（`workflow.start()`、`workflow.startAsync()`、`resume()`）不变。

事件驱动的运行要求存储适配器能以原子方式处理并发更新，例如 `@mastra/libsql` 或 `@mastra/pg`。使用其他适配器时，`createRun()` 会抛出错误并列出受支持的适配器。

只有环境变量会触发切换，因为 `createWorkflow` 在 `Mastra` 读取 `workers` 选项之前执行。如果通过 `workers` 选项分离 Worker，请从 `@mastra/core/workflows/evented` 导入 `createWorkflow` 来创建定时 Workflow。

## 单个定时任务 {/* #single-schedule */}

若 Workflow 只按一个计划触发，请为 `schedule` 传入对象：

```typescript title="src/mastra/workflows/daily-report.ts"
import { createWorkflow } from '@mastra/core/workflows'

const dailyReport = createWorkflow({
  id: 'daily-report',
  schedule: {
    cron: '0 9 * * *',
    timezone: 'America/New_York',
    inputData: { userId: 'system' },
  },
  // ...
})
```

字段：

- `cron`：5、6 或 7 段的 cron 表达式，在构造 Workflow 时校验。`cron` 和 `runAt` 必须且只能提供其中一个。
- `runAt`（可选）：在指定时刻触发一次，用 Unix 纪元毫秒值或 `Date` 表示，无须 cron 表达式。触发后任务变为 `completed`，后续部署不会重新启用，除非修改 `runAt`。首次注册时如果 `runAt` 已过，则直接记为 `completed`，不会触发。
- `endAt`（可选）：仅与 `cron` 一起使用，指定触发截止时间。当下次触发时间晚于 `endAt`，任务变为 `completed`。
- `timezone`（可选）：IANA 时区，例如 `America/New_York`。默认使用宿主的本地时区。生产环境应显式设置，避免触发时间受服务器区域设置影响。
- `inputData`（可选）：每次触发时传给 Workflow 的输入数据。
- `initialState`（可选）：本次运行的初始状态。
- `requestContext`（可选）：附加到本次运行的请求上下文。
- `metadata`（可选）：随定时任务记录保存的任意元数据。

要在固定时刻运行一次 Workflow，请使用 `runAt`：

```typescript title="src/mastra/workflows/launch-announcement.ts"
const launchAnnouncement = createWorkflow({
  id: 'launch-announcement',
  schedule: {
    // Set this to a stable future ISO timestamp in your deployment environment.
    runAt: new Date(process.env.LAUNCH_ANNOUNCEMENT_AT!),
    inputData: { userId: 'system' },
  },
  // ...
})
```

## 多个定时任务 {/* #multiple-schedules */}

传入数组可让同一个 Workflow 按多个计划触发。每项都需要唯一且稳定的 `id`：

```typescript title="src/mastra/workflows/status-check.ts"
import { createWorkflow } from '@mastra/core/workflows'

const statusCheck = createWorkflow({
  id: 'status-check',
  schedule: [
    { id: 'morning', cron: '0 9 * * *', inputData: { window: 'morning' } },
    { id: 'evening', cron: '0 18 * * *', inputData: { window: 'evening' } },
  ],
  // ...
})
```

每项都会生成独立的任务记录，按各自的 cron 触发，并在 Studio 的 Schedules 视图中单独显示。

## 在 Studio 查看定时任务 {/* #viewing-schedules-in-studio */}

Studio 将定时任务放在独立的顶层页面，而非 Workflow 内部的选项卡中：

- **全部定时任务**：打开 `/workflows/schedules` 查看跨 Workflow 的列表。每行显示 Workflow ID、cron、下次触发时间和最近一次运行的状态，便于快速发现异常。
- **按 Workflow 筛选**：附加 `?workflowId=<id>`，仅显示某个 Workflow 的任务，例如 `/workflows/schedules?workflowId=daily-report`。
- **定时任务详情**：选中任意一行，打开 `/workflows/schedules/:scheduleId`。页面显示任务元数据、**Pause** / **Resume** 控件，以及完整的触发历史。

Workflow 至少有一个定时任务时，页首会显示 **Schedules** 操作入口：

- 只有一个任务时，入口直接指向任务详情。
- 有多个任务时，入口指向按 Workflow 筛选的列表 `/workflows/schedules?workflowId=<id>`。
- 没有任务时，入口隐藏。

### 触发历史 {/* #trigger-history */}

调度器会尝试写入一条触发记录，包含运行 ID、计划时间、实际触发时间和发布状态。发布端在领取本次触发之后，或传输层接受发布之后崩溃，都可能没有触发记录。任务详情页将已记录的触发与对应的 Workflow 运行关联，并显示：

- 运行状态徽标（`running`、`success`、`failed`、`suspended`、`canceled`）。
- 运行的开始时间和耗时。
- 指向完整运行图的链接 `/workflows/:workflowId/graph/:runId`。
- 如果发布触发事件和写入运行快照存在竞态，运行记录尚未写入时，会显示 `pending` 徽标。
- 三次发布都失败后，显示 `publish failed` 徽标和最后一次发布错误。实际结果未知，因为传输层可能在返回错误前已接受事件。

只要还有未进入终态的触发，面板就会每五秒轮询一次，直到这些触发全部进入终态。列表采用分页，长期运行的任务无须一次加载数千条记录。

## 在运行时暂停定时任务 {/* #pausing-a-schedule-at-runtime */}

如果生产环境的定时 Workflow 触发异常，不必重新部署或手动修改数据库，可通过 SDK 暂停：

```typescript
import { MastraClient } from '@mastra/client-js'

const client = new MastraClient({ baseUrl: 'http://localhost:4111' })

// Schedule ids are derived from the workflow id: `wf_<workflowId>` for a
// single declarative schedule, or `wf_<workflowId>__<scheduleId>` when you
// declare multiple schedules per workflow as an array.
await client.pauseSchedule('wf_daily-report')
// ...investigate, ship a fix, then:
await client.resumeSchedule('wf_daily-report')
```

在 Studio 中打开任务详情页，在页首选择 **Pause** 或 **Resume**。

暂停和恢复遵循以下规则：

- 暂停状态会写入定时任务表，在进程重启或重新部署后仍然保留。根据声明式配置新增或更新记录时，即使修改 `cron`、`timezone`、`runAt`、`endAt` 或其他字段，也不会覆盖用户设置的状态。
- 恢复 cron 任务时，以当前时间重新计算 `nextFireAt`。暂停一周的任务不会补跑七次积压的触发，而会在下一个正常的 cron 时刻触发。
- 恢复一次性任务时，保留原先配置的 `runAt`。如果暂停期间已过该时刻，任务会在调度器下一轮检查时触发。
- 通过 `resumeSchedule` 或 Studio 的 **Resume** 按钮恢复。编辑 Workflow 的 `schedule` 配置不会解除暂停。
- 暂停和恢复都是幂等操作。再次暂停已暂停的任务不会产生变化。
- 这些运行时操作针对已有任务。声明式任务通过代码中 `createWorkflow` 的 `schedule` 字段创建、删除和编辑。若要在运行时直接创建任务，请使用统一的 [`mastra.schedules`](/docs/harness/schedules) 服务，并传入 `workflowId`。

底层 HTTP 路由为 `POST /api/schedules/:scheduleId/pause` 和 `POST /api/schedules/:scheduleId/resume`，两者都要求 `schedules:write` 权限。

## 修改配置后重新部署 {/* #redeploying-with-changes */}

修改 `schedule` 配置并重新部署时，Mastra 会对比已有任务记录和新配置：

- 周期任务的 `cron`、`timezone` 或 `endAt` 发生变化时，重新计算 `nextFireAt`。没有未来触发时，任务变为完成；重新计算后仍可触发时，已完成的任务会重新启用。
- 一次性任务的 `runAt` 变化时，将 `nextFireAt` 更新为该时刻。未来的 `runAt` 会重新启用已完成的任务，过去的 `runAt` 则使其保持完成状态。
- 如果启用中的一次性任务在应用离线期间错过了未修改的 `runAt`，它仍然到期，会在调度器下一轮检查时触发。首次注册时 `runAt` 已过的任务则直接以 `completed` 状态创建，不会触发。
- 如果只改了 `inputData`、`initialState` 或 `metadata`，直接更新原记录，保留下次触发时间。
- 用户设置的状态（例如通过 `client.pauseSchedule` 暂停）和触发历史不会被覆盖，除非上述时间变更要求更新状态。

`completed` 表示任务已无剩余的自动触发：一次性触发已被领取、周期已耗尽，或配置的时间在注册或对齐配置时已经用尽。该状态不代表 Workflow 已成功运行完毕。

从 Workflow 的 `schedule` 数组移除一项后，对应记录会在下次启动时删除。

## 部署拓扑 {/* #deployment-topology */}

内置调度器使用 `setInterval` 定时轮询任务表并领取到期记录，通过进程内的发布订阅机制分发 Workflow 运行。它以宿主进程持续运行作为前提。

### 常驻宿主（推荐） {/* #long-lived-host-recommended */}

Fly Machines、Railway、Render、AWS ECS、GKE 或自有服务器等部署目标能让 Mastra 进程在两次 cron 触发之间保持运行。`mastra build` 生成的服务器会自动启动调度器，定时任务无须额外配置即可运行。

如果通过[服务器适配器](/docs/server/server-adapters)运行 Mastra，请在服务器开始监听后调用 `mastra.startWorkers()`。适配器不会自动启动调度器，缺少这次调用，定时任务就不会触发。参阅[启动后台 Worker](/docs/server/server-adapters#start-background-workers)。

在生产环境，可以将调度器放在[专用 Worker 进程](/docs/deployment/workers#scheduler-worker)中运行，与 API 层隔离。

### Serverless 平台 {/* #serverless-platforms */}

Vercel、Netlify、AWS Lambda 和 Cloudflare Workers 等函数即服务平台会在每个请求结束后关闭进程，因此定时循环没有下一轮，目前无法通过内置调度器触发在代码中声明的任务。直接运行仍然可用：从 HTTP 路由调用 `run.start()`，会像其他 Workflow 一样，在进程内运行声明了 `schedule` 的 Workflow。

若要在这些平台上按 cron 触发，请使用 [`@mastra/inngest`](#inngest-workflows)。Inngest 原生支持 Serverless，会代为保存 cron 状态。

## Inngest Workflow {/* #inngest-workflows */}

本页的 `schedule` 字段用于 Mastra 的内置调度器。如果使用 `@mastra/inngest`，请在 Inngest 的 `createFunction` 上通过它自己的 `cron` 字段配置定时 Workflow，由 Inngest 的调度器负责触发。

具体区别如下：

- Inngest 定时任务不会出现在 Studio 的 `/workflows/schedules` 视图中。
- Inngest Workflow 页首不显示 **Schedules** 入口。
- `client.pauseSchedule` 和 `client.resumeSchedule` 无法控制 Inngest 定时任务。

通过 [Inngest 控制台](https://www.inngest.com/docs/guides/scheduled-functions)管理 Inngest 定时任务。如果希望由 Mastra 管理整个调度流程，请使用 Mastra 定时任务。
