# 预定的Workflow程

声明一个`schedule`Workflow上的字段，Mastra 将在您指定的 cron 上触发它。相同的Workflow程仍然可以直接调用`workflow.start()`、计划火灾和手动运行共享单个执行路径。

## 快速入门 {/* #quickstart */}

以下Workflow程在纽约时间每天上午 9 点运行。注册于`Mastra` as you would any other workflow, the scheduler picks it up automatically.

```typescript title="src/mastra/workflows/daily-report.ts"
import { createWorkflow, createStep } from '@mastra/core/workflows'
import { z } from 'zod'

const sendReport = createStep({
  id: 'send-report',
  inputSchema: z.object({ userId: z.string() }),
  outputSchema: z.object({ ok: z.boolean() }),
  execute: async ({ inputData }) => {
    // ...send the report for inputData.userId
    return { ok: true }
  },
})

export const dailyReport = createWorkflow({
  id: 'daily-report',
  inputSchema: z.object({ userId: z.string() }),
  outputSchema: z.object({ ok: z.boolean() }),
  schedule: {
    cron: '0 9 * * *',
    timezone: 'America/New_York',
    inputData: { userId: 'system' },
  },
})
  .then(sendReport)
  .commit()
```

不会发生单独的“注册时间表”调用。调度程序读取`schedule` straight off the workflow when `Mastra` boots.

## 交货保证 {/* #delivery-guarantees */}

计划的Workflow程发布是尽力而为的。每个事件在其开始事件发布之前都会被声明，最多可尝试三次发布。耗尽尝试或发布者崩溃​​可以跳过该事件。跳过的事件不会自动重播，但稍后重复发生的火灾可以继续。已标记的时间表`completed` has exhausted its cadence, which doesn't confirm execution. See [Schedule delivery guarantees](/reference/schedules/overview#delivery-guarantees) for failure reporting and manual rerun precautions.

## 执行引擎 {/* #execution-engine */}

声明`schedule` doesn't change how the workflow runs. Scheduled fires run in-process on the host that runs the scheduler, the same way `workflow.start()` or an HTTP-triggered run does. A workflow that declares `schedule` needs no extra storage or worker setup to run directly.

拆分工作线程部署是例外。当[`MASTRA_WORKERS`](/reference/workers/overview#mastra_workers) environment variable is set to any value, including `false`, `createWorkflow` builds scheduled workflows on the **evented execution engine** so that every process in the deployment runs them the same way. Scheduled fires then run on the [orchestration worker](/docs/deployment/workers#orchestration-worker), and Mastra logs a warning to the console when the workflow is created. The public API (`workflow.start()`, `workflow.startAsync()`, `resume()`) 不变。

事件运行需要一个能够自动应用并发更新的存储适配器，例如`@mastra/libsql` or `@mastra/pg`. With any other adapter, `createRun()` throws an error that lists the supported adapters.

只有环境变量才会触发切换，因为`createWorkflow` runs before `Mastra` reads its `workers` option. If you split workers with the `workers` option instead, import `createWorkflow` from `@mastra/core/workflows/evented` for your scheduled workflows.

## 单一时间表 {/* #single-schedule */}

将对象传递给`schedule` for a workflow that fires on one cadence:

```typescript title="src/mastra/workflows/daily-report.ts"
import { createWorkflow } from '@mastra/core/workflows'

const dailyReport = createWorkflow({
  id: 'daily-report',
  schedule: {
    cron: '0 9 * * *',
    timezone: 'America/New_York',
    inputData: { userId: 'system' },
  },
  // ...
})
```

领域：

* `cron`：由 5、6 或 7 部分组成的 cron 表达式。在Workflow程构建时进行验证。准确提供以下之一`cron` or `runAt`.
* `runAt`（可选）：此时触发一次（纪元毫秒或`Date`) instead of on a cron. After it fires, the schedule moves to `completed` and later deploys don't re-arm it unless you change `runAt`. A `runAt` that has already passed when the schedule is first registered is recorded as `completed` without firing.
* `endAt`（可选）：仅与`cron`. Stop firing after this time. The schedule moves to `completed` once its next occurrence would fall after `endAt`.
* `timezone`（可选）：例如 IANA 时区`America/New_York`. Defaults to the host's local timezone. Set this explicitly in production so fire times don't depend on server locale.
* `inputData`（可选）：有效负载在每次火灾时作为Workflow程的输入传递。
* `initialState`（可选）：运行的初始状态。
* `requestContext`（可选）：附加到运行的请求上下文。
* `metadata`（可选）：任意元数据与计划行一起保留。

要在固定时间运行Workflow程一次，请使用`runAt`:

```typescript title="src/mastra/workflows/launch-announcement.ts"
const launchAnnouncement = createWorkflow({
  id: 'launch-announcement',
  schedule: {
    // Set this to a stable future ISO timestamp in your deployment environment.
    runAt: new Date(process.env.LAUNCH_ANNOUNCEMENT_AT!),
    inputData: { userId: 'system' },
  },
  // ...
})
```

## 多个时间表 {/* #multiple-schedules */}

传递一个数组以在多个节奏上触发相同的Workflow程。每个条目都需要一个独特的马厩`id`:

```typescript title="src/mastra/workflows/status-check.ts"
import { createWorkflow } from '@mastra/core/workflows'

const statusCheck = createWorkflow({
  id: 'status-check',
  schedule: [
    { id: 'morning', cron: '0 9 * * *', inputData: { window: 'morning' } },
    { id: 'evening', cron: '0 18 * * *', inputData: { window: 'evening' } },
  ],
  // ...
})
```

每个条目都会创建一个独立的计划行并在其自己的 cron 上触发，并且单独显示在 Studio Schedules 视图中。

## 在 Studio 中查看时间表 {/* #viewing-schedules-in-studio */}

Studio 将计划显示为顶级区域，而不是Workflow程中的选项卡：

* **所有时间表**： 打开`/workflows/schedules` for a cross-workflow list. Each row shows the workflow id, cron, next fire, and the most recent run's status. The list answers "is anything broken?" at a glance.
* **按Workflow程过滤**: 追加`?workflowId=<id>` to scope the list to a single workflow, for example `/workflows/schedules?workflowId=daily-report`.
* **日程详情**：选择任意行打开`/workflows/schedules/:scheduleId`. The page shows schedule metadata and **Pause** / **Resume** controls, followed by the full trigger history.

Workflow程的标头包括**Schedules** action when the workflow has at least one schedule:

* 当一个时间表匹配时，该操作会直接链接到其详细信息页面。
* 多个计划：操作链接到Workflow过滤列表`/workflows/schedules?workflowId=<id>`.
* 没有时间表：动作是隐藏的。

### 触发历史记录 {/* #trigger-history */}

调度程序尝试记录带有运行 ID、计划时间、实际触发时间和发布状态的触发器行。发布者在声明事件发生或发布被接受后崩溃不会留下任何触发行。计划详细信息页面将记录的触发器连接到相应的Workflow程运行并显示：

* 运行状态（`running`, `success`, `failed`, `suspended`, `canceled`) as a badge.
* 跑步的开始时间和持续时间。
* 运行完整图表视图的链接：`/workflows/:workflowId/graph/:runId`.
* 一个`pending` badge for triggers whose run record hasn't been written yet, due to a race between trigger publish and run snapshot.
* 一个`publish failed` badge with the final publish error after all three attempts fail. The outcome is unknown: the transport may have accepted the event before returning the error.

非终端状态下的触发器会导致面板每五秒轮询一次，直到达到终端状态。该列表分页，因此长时间运行的计划不会预先加载数千行。

## 在运行时暂停计划 {/* #pausing-a-schedule-at-runtime */}

当计划的Workflow程在生产中失败时，您无需重新部署或手动编辑数据库。从 SDK 暂停它：

```typescript
import { MastraClient } from '@mastra/client-js'

const client = new MastraClient({ baseUrl: 'http://localhost:4111' })

// Schedule ids are derived from the workflow id: `wf_<workflowId>` for a
// single declarative schedule, or `wf_<workflowId>__<scheduleId>` when you
// declare multiple schedules per workflow as an array.
await client.pauseSchedule('wf_daily-report')
// ...investigate, ship a fix, then:
await client.resumeSchedule('wf_daily-report')
```

在 Studio 中，打开日程详细信息页面并选择**Pause** or **Resume** in the header.

需要了解的一些规则：

* 暂停是持久的。状态将写入计划表并在进程重新启动和重新部署后继续存在。即使您更改，声明性配置 upsert 也不会覆盖用户设置的状态`cron`, `timezone`, `runAt`, `endAt`, or other fields.
* 恢复 cron 计划重新计算`nextFireAt` from now. A schedule paused for a week doesn't fire seven backlogged runs. It fires on the next regular cron tick.
* 恢复一次性保持其配置`runAt`. If that time passed while the schedule was paused, it fires on the next scheduler tick.
* 取消暂停`resumeSchedule` or the **Resume** button in Studio. Editing the workflow's `schedule` config doesn't unpause a paused row.
* 暂停和恢复是幂等的。对已经暂停的计划调用暂停是无操作的。
* 此操作覆盖控制现有计划。在代码中编写声明性时间表。声明性计划通过以下方式在代码中创建、删除和编辑`schedule` field on `createWorkflow`. To create schedules imperatively at runtime instead, use the unified [`mastra.schedules`](/docs/harness/schedules) service with a `workflowId`.

底层的 HTTP 路由是`POST /api/schedules/:scheduleId/pause` and `POST /api/schedules/:scheduleId/resume`. Both require the `schedules:write` permission.

## 重新部署并进行更改 {/* #redeploying-with-changes */}

当您更改`schedule` config and redeploy, Mastra diffs the existing schedule row against the new config:

* 如果`cron`, `timezone`, or `endAt` changes on a recurring schedule, `nextFireAt` is recomputed. A cadence with no future occurrence completes the schedule. A recomputed cadence that can still fire reactivates a completed schedule.
* 如果`runAt` changes on a one-off schedule, `nextFireAt` is updated to that time. A future `runAt` reactivates a completed one-off. A past `runAt` leaves it completed.
* 如果主动一次性未改变`runAt` passed while the app was offline, it remains due and fires on the next scheduler tick. A one-off first registered with a past `runAt` is instead created as `completed` and doesn't fire.
* 如果只是`inputData`, `initialState`, or `metadata` changed, the row is patched in place and the next fire time is preserved.
* 用户设置的状态（例如，通过暂停`client.pauseSchedule`) and fire history are never overwritten, unless a timing change above requires a status update.

这`completed` status means the schedule has no automatic fires remaining: its one-off fire was claimed, its recurring cadence was exhausted, or its configured timing was already exhausted during registration or reconciliation. It doesn't confirm that the workflow run completed successfully.

从Workflow程中删除计划条目`schedule` array deletes its row on the next boot.

## 部署拓扑 {/* #deployment-topology */}

内置调度程序使用`setInterval` tick loop to poll the schedules table and claim due rows. It dispatches workflow runs through the in-process pubsub. It assumes a long-lived host process.

### 长寿主机（推荐） {/* #long-lived-host-recommended */}

部署 Fly Machines、Railway、Render、AWS ECS、GKE 等目标或您自己的服务器，使 Mastra 进程在 cron 周期之间保持活动状态。服务器生成的`mastra build` starts the scheduler automatically, so schedules work without extra setup.

如果您运行 Mastra[server adapter](/docs/server/server-adapters), call `mastra.startWorkers()` after your server starts listening. Adapters don't start the scheduler, and schedules never fire without this call. See [Start background workers](/docs/server/server-adapters#start-background-workers).

对于生产部署，您可以将调度程序作为[dedicated worker process](/docs/deployment/workers#scheduler-worker) to isolate it from the API layer.

### 无服务器平台 {/* #serverless-platforms */}

Vercel、Netlify、AWS Lambda 和 Cloudflare Workers 等函数即服务平台会在每次请求后关闭进程，因此滴答循环不会获得第二次滴答，并且代码中声明的计划目前不会使用内置调度程序触发。直接运行仍然有效：调用`run.start()` from an HTTP route runs a workflow that declares `schedule` in-process, like any other workflow.

对于这些平台上的 cron 火灾，请使用[`@mastra/inngest`](#inngest-workflows) instead. Inngest is serverless-native and holds the cron state for you.

## 摄取Workflow程 {/* #inngest-workflows */}

这`schedule` field documented on this page drives Mastra's built-in scheduler. If you use `@mastra/inngest`, scheduled workflows are configured through Inngest's own `cron` field on `createFunction` and fire on Inngest's scheduler instead.

实际意义：

* Ingest 时间表不会出现在 Studio 中`/workflows/schedules` view.
* Workflow程标题**Schedules** action doesn't show for Inngest workflows.
* `client.pauseSchedule`和`client.resumeSchedule` don't control Inngest schedules.

管理 Ingest 日程[Inngest dashboard](https://www.inngest.com/docs/guides/scheduled-functions). Use Mastra schedules when you want Mastra to own scheduling end to end.
