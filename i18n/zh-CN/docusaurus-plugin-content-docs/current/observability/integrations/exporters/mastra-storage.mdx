# 存储出口商

这`MastraStorageExporter`将跟踪保留到您配置的存储后端，以便通过 Studio 访问它们。它不需要外部服务。

：：：笔记

`MastraStorageExporter`以前被称为`DefaultExporter`. The original `DefaultExporter`类仍然导出自`@mastra/observability`为了向后兼容，但它已被弃用。新代码应该使用`MastraStorageExporter`.

:::

:::警告\[生产可观察性]
可观察性数据很快就会压倒生产中的通用数据库。对于高流量应用程序，将Observability存储域路由到[ClickHouse](/integrations/databases/clickhouse) through [composite storage](/reference/storage/composite). See [Production Recommendations](#production-recommendations) for details.
:::

## 配置 {/* #configuration */}

### 先决条件 {/* #prerequisites */}

1. **存储后端**：配置存储提供者（libSQL、PostgreSQL等）
2. **工作室**：安装以在本地查看痕迹

### 基本设置 {/* #basic-setup */}

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability, MastraStorageExporter } from '@mastra/observability'
import { LibSQLStore } from '@mastra/libsql'

export const mastra = new Mastra({
  storage: new LibSQLStore({
    id: 'mastra-storage',
    url: 'file:./mastra.db', // Required for trace persistence
  }),
  observability: new Observability({
    configs: {
      local: {
        serviceName: 'my-service',
        exporters: [new MastraStorageExporter()],
      },
    },
  }),
})
```

### 推荐配置 {/* #recommended-configuration */}

在您的可观察性配置中包含 MastraStorageExporter：

```typescript
import { Mastra } from '@mastra/core'
import {
  Observability,
  MastraStorageExporter,
  MastraPlatformExporter,
  SensitiveDataFilter,
} from '@mastra/observability'
import { LibSQLStore } from '@mastra/libsql'

export const mastra = new Mastra({
  storage: new LibSQLStore({
    id: 'mastra-storage',
    url: 'file:./mastra.db',
  }),
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'mastra',
        exporters: [
          new MastraStorageExporter(), // Persists observability events to Mastra Storage
          new MastraPlatformExporter(), // Sends observability events to Mastra platform (requires MASTRA_PLATFORM_ACCESS_TOKEN)
        ],
        spanOutputProcessors: [new SensitiveDataFilter()],
      },
    },
  }),
})
```

## 导出到存储和平台 {/* #export-to-storage-and-platform */}

在 Mastra 平台上，一个非空`MASTRA_DEPLOYMENT_ID` disables `MastraStorageExporter` and the deprecated `DefaultExporter` by default. Other exporters remain enabled. The opt-in below applies only to `MastraStorageExporter`. Deprecated `DefaultExporter` stays disabled on Platform even with the flag set to `true`. Migrate to `MastraStorageExporter` to use this option.

:::警告即使选择加入，本地存储仍然被阻止

`retainStorageExporterOnPlatform: true` **doesn't** enable in-memory, local libSQL, or DuckDB observability writes on Platform. When the observability domain reports local persistence, the built-in storage exporter stays disabled: it won't persist traces, logs, metrics, scores, or feedback to that database. Other exporters continue to receive events.

:::

有了更新的适配器和`retainStorageExporterOnPlatform: true`, the behavior on Platform is:

|Observability数据库|平台存储导出 |
| - | - |
| PostgreSQL |允许 |
|远程 libSQL/Turso (`libsql://` or `https://`) | Allowed |
| Local libSQL (`file:` or `:memory:`) | Blocked |
| libSQL embedded replica with a remote sync URL | Blocked: it still writes locally |
| DuckDB, including in-memory databases | Blocked |
| `InMemoryStore`, including the fallback when no storage is configured | Blocked |

要继续写入您自己的远程数据库以及平台可观察性，请设置[`retainStorageExporterOnPlatform`](/reference/observability/tracing/configuration#observabilityinstanceconfig) to `true` on the observability config:

```typescript
import { Observability, MastraStorageExporter, MastraPlatformExporter } from '@mastra/observability'

const observability = new Observability({
  configs: {
    production: {
      serviceName: 'my-service',
      retainStorageExporterOnPlatform: true,
      exporters: [new MastraStorageExporter(), new MastraPlatformExporter()],
    },
  },
})
```

通过这个`observability` instance to `new Mastra()` alongside your configured `storage` provider. The option applies only to this config, including exporters registered later. It doesn't configure a database or add exporters automatically. Other configs keep the default suppression unless they also opt in.

该限制适用于**observability domain**, which can use a different provider from your default application storage. It doesn't disable other storage domains. Outside Platform, local observability storage continues to work.

要启用此防护，请升级`@mastra/core` and any `@mastra/libsql` or `@mastra/duckdb` adapters alongside `@mastra/observability`: older or custom adapters without the `persistenceLocation` capability retain the existing opt-in behavior and aren't checked for local persistence.

被阻止的导出器会在初始化期间记录警告，但即使您的日志记录设置隐藏了该警告，该限制仍然适用。如果双重导出未写入数据库，请根据上表检查可观察性提供程序并配置远程数据库。重试或增加批处理间隔不会启用被阻止的导出器。

## 追踪策略 {/* #tracing-strategies */}

MastraStorageExporter 根据您的存储Provider自动选择最佳跟踪策略。如果需要，您还可以覆盖此选择。

### 可用策略 {/* #available-strategies */}

|战略|描述 |使用案例|
| - | - | - |
|**realtime** | Process each event immediately | Development, debugging, low traffic |
| **batch-with-updates** | Buffer events and batch write with full lifecycle support | Low volume Production |
| **insert-only** | Only process completed spans, ignore updates | High volume Production |
| **event-sourced** | Write one row when a span starts and another when it ends, then collapse them on read | High volume Production, in-progress traces |

### 策略配置 {/* #strategy-configuration */}

```typescript
new MastraStorageExporter({
  strategy: 'auto', // Default - let storage provider decide
  // or explicitly set:
  // strategy: 'realtime' | 'batch-with-updates' | 'insert-only' | 'event-sourced'

  // Batching configuration (applies to both batch-with-updates and insert-only)
  maxBatchSize: 1000, // Max spans per batch
  maxBatchWaitMs: 5000, // Max wait before flushing
  maxBufferSize: 10000, // Max spans to buffer
})
```

## 存储Provider支持 {/* #storage-provider-support */}

不同的存储Provider支持不同的跟踪策略。一些Provider支持生产工作负载的可观察性，而其他Provider则主要用于本地开发。

如果您将策略设置为`'auto'`, the `MastraStorageExporter` automatically selects the optimal strategy for the storage provider. If you set an explicit strategy that the storage provider doesn't support, the exporter logs a warning and falls back to the provider's preferred strategy.

### 提供可观察性支持的Provider {/* #providers-with-observability-support */}

|存储Provider|首选策略 |支持的策略|推荐用途 |
| - | - | - | - |
|**[ClickHouse](/integrations/databases/clickhouse)** | insert-only | insert-only | Production (high-volume) |
| **[PostgresStore](/integrations/databases/postgresql)** | batch-with-updates | batch-with-updates, insert-only | Production (low volume) |
| **[PostgresStoreVNext](/integrations/databases/postgresql)** | event-sourced | event-sourced | Production (high-volume) |
| **[MSSQL](/integrations/databases/mssql)** | batch-with-updates | batch-with-updates, insert-only | Production (low volume) |
| **[MongoDB](/integrations/databases/mongodb)** | batch-with-updates | batch-with-updates, insert-only | Production (low volume) |
| **[OracleDB](/integrations/databases/oracledb)** | batch-with-updates | batch-with-updates, insert-only | Production (low volume) |
| **[libSQL](/integrations/databases/libsql)** | batch-with-updates | batch-with-updates, insert-only | Default storage, good for development |

：：：笔记

在下面`insert-only`, only completed spans are persisted, and span start and update events are ignored. A trace therefore becomes visible in Studio only after its root span ends, and filtering traces by `status: 'running'` returns no results. `PostgresStoreVNext` uses `event-sourced` tracing instead, so in-progress traces remain visible while preserving append-only writes.

:::

### 没有可观察性支持的Provider {/* #providers-without-observability-support */}

以下存储Provider**don't support** the observability domain. If you're using one of these providers and need observability, use [composite storage](/reference/storage/composite) to route observability data to a supported provider:

* [凸面](/integrations/databases/convex)
* [动态数据库](/integrations/databases/dynamodb)
* [Cloudflare D1](/integrations/databases/cloudflare-d1)
* [Cloudflare 耐用对象](/integrations/databases/cloudflare-kv)
* [乌普斯塔什](/integrations/databases/upstash)
* [兰斯数据库](/integrations/databases/lancedb)

### 策略优势 {/* #strategy-benefits */}

* **即时的**：立即可见，最适合调试
* **批量更新**：吞吐量提高 10-100 倍，全生命周期
* **仅插入**：数据库操作额外减少 70%，非常适合分析
* **事件源**：仅追加类似于仅插入，但在执行运行时，正在进行的跟踪在 Studio 中保持可见

## 制作建议 {/* #production-recommendations */}

Observability数据在生产环境中快速增长。单个Agent交互可以生成数百个跨度，高流量应用程序每天可以生成数千个跟踪。大多数通用数据库并未针对这种写入量大、仅追加的工作负载进行优化。

### 推荐：用于大批量生产的 ClickHouse {/* #recommended-clickhouse-for-high-volume-production */}

[克利克屋](/integrations/databases/clickhouse)是专为大容量分析工作负载而设计的列式数据库。这是生产可观察性的推荐选择，因为：

* **针对写入进行优化**：每秒处理数百万次插入
* **高效压缩**：降低跟踪数据的存储成本
* **快速查询**：列式存储可实现快速跟踪查找和聚合
* **时间序列原生**：内置支持基于时间的数据保留和分区

### 使用复合存储 {/* #using-composite-storage */}

如果您使用的提供程序没有Observability支持（例如 Convex 或 DynamoDB）或想要优化性能，请使用[composite storage](/reference/storage/composite#specialized-storage-for-observability) to route observability data to ClickHouse while keeping other data in your primary database.

## 批处理行为 {/* #batching-behavior */}

### 冲洗触发器 {/* #flush-triggers */}

对于两种批量策略（`batch-with-updates` and `insert-only`), traces are flushed to storage when any of these conditions are met:

1. **尺寸触发**: 缓冲区达到`maxBatchSize` spans
2. **时间触发**: `maxBatchWaitMs` elapsed since first event
3. **紧急冲洗**：缓冲方法`maxBufferSize` limit
4. **关闭**：强制刷新所有待处理事件

### 错误处理 {/* #error-handling */}

MastraStorageExporter 包括用于生产用途的可靠错误处理：

* **重试逻辑**：指数退避（500ms、1s、2s、4s）
* **瞬时故障**：带退避功能的自动重试
* **持续失败**: 4 次失败尝试后删除批次
* **缓冲区溢出**：防止存储中断期间出现内存问题

## 丢弃的Observability事件 {/* #dropped-observability-events */}

`DefaultExporter`当它无法持久保存可观察性数据时，会发出结构化的放置事件。注册出口商或桥梁`onDroppedEvent` to forward these drops to alerting or monitoring.



* `unsupported-storage`：存储提供者没有实现信号类型。
* `retry-exhausted`：出口商重试批次最多`maxRetries` times and then dropped it.
* `span-not-updatable`： 在下面`realtime` or `batch-with-updates`, a span update or end reached storage but didn't apply, because the span was never stored or had already ended. Ended spans don't change.

以下示例演示了将丢弃详细信息转发到监控端点：

```typescript title="src/mastra/observability.ts"
import { BaseExporter } from '@mastra/observability'
import type { ObservabilityDropEvent, TracingEvent } from '@mastra/core/observability'

class DropAlertExporter extends BaseExporter {
  name = 'drop-alerts'

  async onDroppedEvent(event: ObservabilityDropEvent) {
    await fetch('https://monitoring.example.com/observability-drops', {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({
        count: event.count,
        signal: event.signal,
        reason: event.reason,
        exporterName: event.exporterName,
      }),
    })
  }

  protected async _exportTracingEvent(_event: TracingEvent) {}
}
```

## 配置举例 {/* #configuration-examples */}

```typescript
// Zero config - recommended for most users
new MastraStorageExporter()

// Development override
new MastraStorageExporter({
  strategy: 'realtime', // Immediate visibility for debugging
})

// High-throughput production
new MastraStorageExporter({
  maxBatchSize: 2000, // Larger batches
  maxBatchWaitMs: 10000, // Wait longer to fill batches
  maxBufferSize: 50000, // Handle longer outages
})

// Low-latency production
new MastraStorageExporter({
  maxBatchSize: 100, // Smaller batches
  maxBatchWaitMs: 1000, // Flush quickly
})
```
