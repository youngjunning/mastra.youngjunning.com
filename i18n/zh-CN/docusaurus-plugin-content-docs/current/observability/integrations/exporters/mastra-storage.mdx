# 存储导出器

`MastraStorageExporter` 将 Trace 持久化到已配置的存储后端，以便在 Studio 中查看，无须外部服务。

:::note

`MastraStorageExporter` 以前叫作 `DefaultExporter`。为保持向后兼容，`@mastra/observability` 仍会导出原有的 `DefaultExporter` 类，但它已弃用。新代码应使用 `MastraStorageExporter`。

:::

:::warning[生产环境的可观测性]
在生产环境中，可观测性数据可能很快压垮通用数据库。流量较大的应用应通过[复合存储](/reference/storage/composite)，将可观测性存储域路由到 [ClickHouse](/integrations/databases/clickhouse)。详见[生产环境建议](#production-recommendations)。
:::

## 配置 {/* #configuration */}

### 前置条件 {/* #prerequisites */}

1. **存储后端**：配置存储 Provider（如 libSQL、PostgreSQL）。
1. **Studio**：安装 Studio，以便在本地查看 Trace。

### 基本设置 {/* #basic-setup */}

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability, MastraStorageExporter } from '@mastra/observability'
import { LibSQLStore } from '@mastra/libsql'

export const mastra = new Mastra({
  storage: new LibSQLStore({
    id: 'mastra-storage',
    url: 'file:./mastra.db', // Required for trace persistence
  }),
  observability: new Observability({
    configs: {
      local: {
        serviceName: 'my-service',
        exporters: [new MastraStorageExporter()],
      },
    },
  }),
})
```

### 推荐配置 {/* #recommended-configuration */}

将 MastraStorageExporter 加入可观测性配置：

```typescript
import { Mastra } from '@mastra/core'
import {
  Observability,
  MastraStorageExporter,
  MastraPlatformExporter,
  SensitiveDataFilter,
} from '@mastra/observability'
import { LibSQLStore } from '@mastra/libsql'

export const mastra = new Mastra({
  storage: new LibSQLStore({
    id: 'mastra-storage',
    url: 'file:./mastra.db',
  }),
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'mastra',
        exporters: [
          new MastraStorageExporter(), // Persists observability events to Mastra Storage
          new MastraPlatformExporter(), // Sends observability events to Mastra platform (requires MASTRA_PLATFORM_ACCESS_TOKEN)
        ],
        spanOutputProcessors: [new SensitiveDataFilter()],
      },
    },
  }),
})
```

## 同时导出到存储和 Platform {/* #export-to-storage-and-platform */}

在 Mastra Platform 上，`MASTRA_DEPLOYMENT_ID` 非空时，`MastraStorageExporter` 和已弃用的 `DefaultExporter` 默认禁用，其他导出器仍然启用。下述选项只对 `MastraStorageExporter` 生效。即使将开关设为 `true`，Platform 上的 `DefaultExporter` 仍然禁用。要使用此选项，请迁移到 `MastraStorageExporter`。

:::warning 启用选项后，本地存储仍被阻止

`retainStorageExporterOnPlatform: true` **不会**在 Platform 上启用内存、本地 libSQL 或 DuckDB 的可观测性写入。如果可观测性域报告数据会在本地持久化，内置存储导出器仍处于禁用状态，不会将 Trace、日志、指标、评分或反馈写入数据库。其他导出器继续接收事件。

:::

更新适配器并设置 `retainStorageExporterOnPlatform: true` 后，Platform 上的行为如下：

| 可观测性数据库 | Platform 上是否允许导出到存储 |
| - | - |
| PostgreSQL | 允许 |
| 远程 libSQL/Turso（`libsql://` 或 `https://`） | 允许 |
| 本地 libSQL（`file:` 或 `:memory:`） | 阻止 |
| 配有远程同步 URL 的 libSQL 嵌入式副本 | 阻止：仍会在本地写入 |
| DuckDB，包括内存数据库 | 阻止 |
| `InMemoryStore`，包括未配置存储时的回退方案 | 阻止 |

要在使用 Platform 可观测性的同时继续写入自有远程数据库，请在可观测性配置中把 [`retainStorageExporterOnPlatform`](/reference/observability/tracing/configuration#observabilityinstanceconfig) 设为 `true`：

```typescript
import { Observability, MastraStorageExporter, MastraPlatformExporter } from '@mastra/observability'

const observability = new Observability({
  configs: {
    production: {
      serviceName: 'my-service',
      retainStorageExporterOnPlatform: true,
      exporters: [new MastraStorageExporter(), new MastraPlatformExporter()],
    },
  },
})
```

将此 `observability` 实例与已配置的 `storage` Provider 一同传给 `new Mastra()`。该选项仅对此配置生效，包括之后向此配置注册的导出器。它不会自动配置数据库或添加导出器。其他配置除非也启用此选项，否则仍沿用默认的禁用行为。

这项限制只针对**可观测性域**，该域使用的 Provider 可以与应用默认存储不同。其他存储域不受影响。在 Platform 之外，本地可观测性存储仍可使用。

要启用这项保护，请在升级 `@mastra/observability` 的同时升级 `@mastra/core`，以及所用的 `@mastra/libsql` 或 `@mastra/duckdb` 适配器。缺少 `persistenceLocation` 能力的旧版或自定义适配器保留现有的按需启用行为，不会检查是否在本地持久化。

导出器被阻止时会在初始化期间记录警告，即使日志设置隐藏该警告，限制也仍然生效。如果双重导出没有写入数据库，请对照上表检查可观测性 Provider 并配置远程数据库。重试或增大批处理间隔都无法启用已被阻止的导出器。

## Studio {/* #studio */}

在 Studio 中查看 Trace：

1. 启动 Studio。
1. 打开 Observability。
1. 筛选和搜索本地 Trace。
1. 查看 Span 的详细信息。

## 追踪策略 {/* #tracing-strategies */}

MastraStorageExporter 会按所用的存储 Provider 自动选择最合适的追踪策略。需要时也可手动指定。

### 可用策略 {/* #available-strategies */}

| 策略 | 说明 | 适用场景 |
| - | - | - |
| **realtime** | 立即处理每个事件 | 开发、调试、低流量场景 |
| **batch-with-updates** | 缓冲事件后批量写入，支持完整生命周期 | 数据量较小的生产环境 |
| **insert-only** | 只处理已结束的 Span，忽略更新 | 数据量较大的生产环境 |
| **event-sourced** | Span 开始和结束时各写入一行，读取时合并 | 数据量较大的生产环境、进行中的 Trace |

### 配置策略 {/* #strategy-configuration */}

```typescript
new MastraStorageExporter({
  strategy: 'auto', // Default - let storage provider decide
  // or explicitly set:
  // strategy: 'realtime' | 'batch-with-updates' | 'insert-only' | 'event-sourced'

  // Batching configuration (applies to both batch-with-updates and insert-only)
  maxBatchSize: 1000, // Max spans per batch
  maxBatchWaitMs: 5000, // Max wait before flushing
  maxBufferSize: 10000, // Max spans to buffer
})
```

## 存储 Provider 的支持情况 {/* #storage-provider-support */}

不同的存储 Provider 支持不同的追踪策略。有些适合生产环境的可观测性工作负载，有些主要用于本地开发。

将策略设为 `'auto'` 时，`MastraStorageExporter` 会自动选择最适合该 Provider 的策略。显式指定不受支持的策略时，导出器会记录警告，并回退到该 Provider 的首选策略。

### 支持可观测性的 Provider {/* #providers-with-observability-support */}

| 存储 Provider | 首选策略 | 支持的策略 | 推荐用途 |
| - | - | - | - |
| **[ClickHouse](/integrations/databases/clickhouse)** | insert-only | insert-only | 生产环境（高数据量） |
| **[PostgresStore](/integrations/databases/postgresql)** | batch-with-updates | batch-with-updates, insert-only | 生产环境（低数据量） |
| **[PostgresStoreVNext](/integrations/databases/postgresql)** | event-sourced | event-sourced | 生产环境（高数据量） |
| **[MSSQL](/integrations/databases/mssql)** | batch-with-updates | batch-with-updates, insert-only | 生产环境（低数据量） |
| **[MongoDB](/integrations/databases/mongodb)** | batch-with-updates | batch-with-updates, insert-only | 生产环境（低数据量） |
| **[OracleDB](/integrations/databases/oracledb)** | batch-with-updates | batch-with-updates, insert-only | 生产环境（低数据量） |
| **[libSQL](/integrations/databases/libsql)** | batch-with-updates | batch-with-updates, insert-only | 默认存储，适合开发 |

:::note

`insert-only` 只持久化已结束的 Span，并忽略 Span 的开始和更新事件。因此，Trace 要到根 Span 结束后才会在 Studio 中显示，而且按 `status: 'running'` 筛选不会返回结果。`PostgresStoreVNext` 则使用 `event-sourced` 策略，在保持仅追加写入的同时，让进行中的 Trace 仍然可见。

:::

### 不支持可观测性的 Provider {/* #providers-without-observability-support */}

以下存储 Provider **不支持**可观测性域。如果正在使用其中之一且需要可观测性功能，请使用[复合存储](/reference/storage/composite)，将可观测性数据路由到受支持的 Provider：

- [Convex](/integrations/databases/convex)
- [DynamoDB](/integrations/databases/dynamodb)
- [Cloudflare D1](/integrations/databases/cloudflare-d1)
- [Cloudflare Durable Objects](/integrations/databases/cloudflare-kv)
- [Upstash](/integrations/databases/upstash)
- [LanceDB](/integrations/databases/lancedb)

### 各策略的优势 {/* #strategy-benefits */}

- **realtime**：立即可见，最适合调试。
- **batch-with-updates**：吞吐量提升 10–100 倍，支持 Span 的完整生命周期。
- **insert-only**：数据库操作量再减少 70%，适合分析。
- **event-sourced**：与 insert-only 一样仅追加写入，但运行期间仍可在 Studio 看到进行中的 Trace。

## 生产环境建议 {/* #production-recommendations */}

生产环境的可观测性数据增长很快。一次 Agent 交互就可能产生数百个 Span，高流量应用每天可生成数千条 Trace。多数通用数据库没有针对此类写入密集、仅追加的工作负载进行优化。

### 推荐：高数据量的生产环境使用 ClickHouse {/* #recommended-clickhouse-for-high-volume-production */}

[ClickHouse](/integrations/databases/clickhouse) 是为高数据量分析设计的列式数据库。生产环境推荐用它存储可观测性数据，原因如下：

- **写入优化**：每秒可处理数百万次插入。
- **高效压缩**：降低 Trace 数据的存储成本。
- **查询快速**：列式存储可以快速查找和聚合 Trace。
- **原生时序支持**：内置基于时间的数据保留和分区功能。

### 使用复合存储 {/* #using-composite-storage */}

如果存储 Provider 不支持可观测性（例如 Convex 或 DynamoDB），或希望优化性能，可通过[复合存储](/reference/storage/composite#specialized-storage-for-observability)把可观测性数据写入 ClickHouse，其他数据仍留在主数据库。

## 批处理行为 {/* #batching-behavior */}

### 触发批量写入的条件 {/* #flush-triggers */}

对于两种批处理策略（`batch-with-updates` 和 `insert-only`），满足以下任一条件时，就会将缓冲的 Trace 写入存储：

1. **达到批次大小**：缓冲区已累积 `maxBatchSize` 个 Span。
1. **达到等待时间**：从第一个事件起已过 `maxBatchWaitMs`。
1. **紧急写入**：缓冲区接近 `maxBufferSize` 上限。
1. **关闭**：强制将所有待处理事件写入存储。

### 错误处理 {/* #error-handling */}

MastraStorageExporter 提供适用于生产环境的错误处理：

- **重试逻辑**：指数退避（500 毫秒、1 秒、2 秒、4 秒）。
- **暂时性故障**：按退避策略自动重试。
- **持续性故障**：尝试失败 4 次后丢弃该批次。
- **缓冲区溢出**：防止存储不可用时出现内存问题。

## 丢弃的可观测性事件 {/* #dropped-observability-events */}

`DefaultExporter` 无法持久化可观测性数据时，会发出结构化的丢弃事件。可使用 `onDroppedEvent` 注册导出器或桥接组件，将丢弃事件转发给告警或监控系统。

事件可能因以下原因被丢弃：

- `unsupported-storage`：存储 Provider 未实现该信号类型。
- `retry-exhausted`：导出器已对该批次重试最多 `maxRetries` 次，随后将其丢弃。
- `span-not-updatable`：使用 `realtime` 或 `batch-with-updates` 时，Span 的更新或结束事件抵达了存储，但未能应用，因为该 Span 从未保存或已经结束。已结束的 Span 不会再变更。

以下示例展示如何将丢弃详情转发到监控端点：

```typescript title="src/mastra/observability.ts"
import { BaseExporter } from '@mastra/observability'
import type { ObservabilityDropEvent, TracingEvent } from '@mastra/core/observability'

class DropAlertExporter extends BaseExporter {
  name = 'drop-alerts'

  async onDroppedEvent(event: ObservabilityDropEvent) {
    await fetch('https://monitoring.example.com/observability-drops', {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({
        count: event.count,
        signal: event.signal,
        reason: event.reason,
        exporterName: event.exporterName,
      }),
    })
  }

  protected async _exportTracingEvent(_event: TracingEvent) {}
}
```

## 配置示例 {/* #configuration-examples */}

```typescript
// Zero config - recommended for most users
new MastraStorageExporter()

// Development override
new MastraStorageExporter({
  strategy: 'realtime', // Immediate visibility for debugging
})

// High-throughput production
new MastraStorageExporter({
  maxBatchSize: 2000, // Larger batches
  maxBatchWaitMs: 10000, // Wait longer to fill batches
  maxBufferSize: 50000, // Handle longer outages
})

// Low-latency production
new MastraStorageExporter({
  maxBatchSize: 100, // Smaller batches
  maxBatchWaitMs: 1000, // Flush quickly
})
```
