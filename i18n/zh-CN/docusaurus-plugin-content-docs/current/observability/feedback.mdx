# 反馈

反馈记录捕获人机交互信号，例如拇指、评级、评论和更正。当您需要将用户、QA、Studio 或系统审核数据附加到跟踪或范围并查询该数据以及其他可观察性信号时，请使用反馈。

与指标和分数不同，反馈通常由人员或审核Workflow程提供。数字反馈值可以随着时间的推移进行聚合、分组、绘制图表以及查询百分位数。

## 何时使用反馈 {/* #when-to-use-feedback */}

* 收集Agent响应的用户满意度评级。
* 将 QA 评论或更正存储在他们审查的跟踪旁边。
* 构建按Agent、环境或实验进行评级的仪表板。

## 添加反馈 {/* #add-feedback */}

使用`mastra.observability.addFeedback()` to annotate a trace or span from app code. The helper is optional on the observability entrypoint, so check that the active observability implementation supports it. See the [client SDK observability reference](/reference/client-js/observability) for all client methods.

```typescript title="src/mastra/feedback.ts"
if (!mastra.observability.addFeedback) {
  throw new Error('Feedback is not supported by the active observability implementation')
}

await mastra.observability.addFeedback({
  traceId: 'trace-123',
  spanId: 'span-456',
  feedback: {
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
    comment: 'The answer solved my issue.',
  },
})
```

反馈将发送至每个支持它的已配置导出器。每个出口商独立处理自己的目的地。本地存储中丢失的跟踪不会阻止反馈到达平台或其他导出器。

[`MastraStorageExporter`](/docs/observability/integrations/exporters/mastra-storage)在保存反馈之前，在您配置的存储中查找跟踪或跨度。如果重试后目标仍然不可用，则会记录警告并跳过本地写入。称呼`mastra.observability.flush()` or `shutdown()` before your process exits to finish pending delivery.

## 查找消息的踪迹 {/* #find-the-trace-for-a-message */}

反馈通常是针对用户已阅读的消息收集的，因此您需要`traceId` for that message. Assistant messages carry it in `content.metadata`, both in the stream result and when the message is recalled later from memory:

```typescript title="src/mastra/message-trace.ts"
const agent = mastra.getAgent('weatherAgent')
const memory = await agent.getMemory()

const { messages } = await memory!.recall({ threadId, perPage: false })

const message = messages.find(m => m.id === messageId)
const traceId = message?.content.metadata?.traceId
```

该值与运行报告的跟踪值相同`traceId` on its result, so feedback collected at generation time and feedback collected later against a stored message anchor to the same trace. Messages produced while tracing is disabled have no `traceId`.

### 读取跟踪 ID`useChat` {/* #read-the-trace-id-in-usechat */}

[`chatRoute()`](/reference/ai-sdk/chat-route)和[`handleChatStream()`](/reference/ai-sdk/handle-chat-stream) pass the run's `traceId` to your `messageMetadata` callback. Return it on the `start` part so the client has it on the live message without a server lookup:

```typescript title="src/mastra/index.ts"
chatRoute({
  path: '/chat/:agentId',
  messageMetadata: ({ part, traceId }) => (part.type === 'start' ? { traceId } : undefined),
})
```

```tsx title="app/chat.tsx"
const { messages } = useChat<UIMessage<{ traceId?: string }>>()

const lastMessage = messages.at(-1)
const traceId = lastMessage?.role === 'assistant' ? lastMessage.metadata?.traceId : undefined
```

如果您使用以下方式验证元数据`messageMetadataSchema`, add `traceId: z.string().optional()` to it. Send the `traceId` with the user's vote to your own route, then call `addFeedback()` there. Check that the caller owns a message with that `traceId` before adding feedback, because the value comes from the client.

## 创建反馈 {/* #create-feedback */}

每一个`createFeedback()` requires `feedbackType` and `value`. Add `traceId` or `spanId` when the feedback should be anchored to a trace or a specific span. Use `feedbackSource` as optional string metadata, such as `user`, `qa`, `studio`, or `system`.

对于存储级写入，包括`timestamp` because the method writes directly to the store.

```typescript
const observability = await mastra.getStorage()!.getStore('observability')

await observability!.createFeedback({
  feedback: {
    feedbackId: 'feedback-rating-1',
    timestamp: new Date(),
    traceId: 'trace-123',
    spanId: 'span-456',
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
    comment: 'The answer solved my issue.',
    tags: ['production'],
  },
})

await observability!.createFeedback({
  feedback: {
    feedbackId: 'feedback-comment-1',
    timestamp: new Date(),
    feedbackSource: 'qa',
    feedbackType: 'comment',
    value: 'Needs a citation before shipping.',
    experimentId: 'support-agent-eval',
  },
})
```

## 列出反馈 {/* #list-feedback */}

使用`listFeedback()` to page through raw records or poll with delta mode.

```typescript
const result = await observability!.listFeedback({
  filters: {
    feedbackType: 'rating',
    feedbackSource: 'user',
    timestamp: { start: new Date(Date.now() - 7 * 24 * 60 * 60 * 1000) },
  },
  pagination: { page: 0, perPage: 20 },
  orderBy: { field: 'timestamp', direction: 'DESC' },
})

console.log(result.feedback, result.pagination?.hasMore)
```

过滤器包括目标字段，例如`traceId` and `spanId`, feedback fields such as `feedbackType`, `feedbackSource`, and `feedbackUserId`, and shared context fields such as `entityName`, `environment`, `experimentId`, and `tags`. See [`FeedbackFilter`](/reference/observability/feedback#feedbackfilter) for every filter field. Over HTTP, the same fields are passed as query parameters, for example `GET /api/observability/feedback?traceId=trace-123&environment=production`. See [list query parameters](/reference/observability/feedback#list-query-parameters).

```typescript
await observability!.listFeedback({
  filters: {
    traceId: 'trace-123',
    feedbackType: ['rating', 'thumbs'],
    tags: ['production'],
  },
})
```

## 删除反馈 {/* #delete-feedback */}

使用`deleteFeedback()` to delete feedback records by id. This is useful when a comment contains sensitive data. Each request accepts at most 1,000 `feedbackIds`, and deletion is idempotent. The optional `organizationId` field filters by organization, and the optional `resourceId` field filters by resource. You can supply either filter independently or use both together. In Studio, each comment on a trace or span **Feedback** tab has a delete action. Deleting a trace with `deleteTraces()` also deletes the feedback linked to it. See [Deleting traces](/reference/client-js/observability#deleting-traces).

```typescript
await observability!.deleteFeedback({
  feedbackIds: ['feedback-1', 'feedback-2'],
})
```

删除的记录也会从反馈分析中消失。 ClickHouse 使用轻量级删除来隐藏行，但不保证立即物理删除，因此开源部署必须配置一个[observability retention period](/reference/storage/retention) to physically purge them. Each request is marked applied once its delete succeeds; if the delete fails, the request stays unapplied, doesn't block updates to the still-visible feedback, and you retry by calling the delete API again. On ClickHouse, the next review update also retries the delete and reports the feedback as not found if the retry succeeds, or saves the new status and returns the delete's error if it fails again. Open-source deployments have no background reconciler. Configure retention for every observability signal to expire deletion requests after the signal rows they protect. If any signal is unbounded, deletion requests also remain unbounded to prevent deleted data from being reintroduced. On ClickHouse, delete APIs leave the separate delta cursor table untouched. Its rows contain identifiers rather than feedback payloads and expire within two days.

## 查询反馈分析 {/* #query-feedback-analytics */}

OLAP 反馈查询对数字进行操作`value` fields. Use them for ratings, thumbs encoded as `1` and `-1`, numeric QA scores, or other numeric feedback types.

```typescript
const rating = await observability!.getFeedbackAggregate({
  feedbackType: 'rating',
  feedbackSource: 'user',
  aggregation: 'avg',
  comparePeriod: 'previous_day',
})

const byAgent = await observability!.getFeedbackBreakdown({
  feedbackType: 'rating',
  groupBy: ['entityName'],
  aggregation: 'avg',
  filters: { environment: 'production' },
})

const ratingsOverTime = await observability!.getFeedbackTimeSeries({
  feedbackType: 'rating',
  aggregation: 'avg',
  interval: '1h',
  groupBy: ['feedbackSource'],
})
```

请参阅[feedback reference](/reference/observability/feedback) for all fields, filters, return types, and percentile query parameters.

本地运行时公开列表路由`/api/observability/feedback` and analytics under its related paths. See the [HTTP routes table](/reference/observability/feedback#http-routes) and [list query parameters](/reference/observability/feedback#list-query-parameters). Mastra Platform provides a separate, unversioned hosted query API. See the [Feedback API](/docs/mastra-platform/api#feedback-api) for regional endpoints, authentication, and project scoping.

## 将反馈导出至 Mastra 平台 {/* #export-feedback-to-mastra-platform */}

[`MastraPlatformExporter`](/reference/observability/tracing/exporters/mastra-platform-exporter)向 Mastra 平台发送反馈，该平台在需要时查找目标轨迹或跨度。不需要本地跟踪存储。添加`MastraStorageExporter` only if you also want a local copy.

Studio 向为其跟踪读取提供服务的后端发送反馈。对于由 OSS 服务器处理的 HTTP 创建，服务器会在本地保存反馈并通知配置的导出器。由于导出器传送是异步的，因此成功的 HTTP 响应并不能保证记录在远程目标上已经可见。直接存储写入绕过导出器。

## 将反馈导出到外部平台 {/* #export-feedback-to-external-platforms */}

反馈流经可观察性事件总线，因此支持反馈的导出器会自动转发它。这[PostHog exporter](/reference/observability/tracing/exporters/posthog#feedback-export) sends feedback as native `$ai_feedback` events that appear on the linked trace in PostHog.
