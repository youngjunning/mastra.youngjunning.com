# 用法

跟踪是可观察信号，记录请求如何通过Agent、Workflow、Tool和模型调用移动。 Mastra 将每个操作表示为一个跨度，并将相关跨度分组到跟踪中，以便您可以检查完整的执行路径。

本页面重点介绍特定于跟踪的概念：执行结果、跨度层次结构、采样、元数据、过滤、跟踪 ID 和第三方跟踪上下文。

<Inject>
  **对于人工智能Agent：**&#x8DD1;步`npx mastra api trace list '{"page":0,"perPage":20}'` to inspect recent traces directly instead of opening Studio or writing a temporary script. The command requires a running Mastra server with observability configured; start the local server with `npx mastra dev`，或传递可访问服务器的基本 URL`--url`。跑步`npx mastra api trace list --schema`在构建不同的过滤器之前。安装 Mastra 的技能`npx skills add mastra-ai/skills --skill mastra`获取完整的 API CLI 发现、定位、架构、身份验证和错误处理指南。
</Inject>

## 何时使用追踪 {/* #when-to-use-tracing */}

* 通过检查完整的执行路径来调试意外的Agent或Workflow行为。
* 遵循单个请求内的模型调用、Tool调用和Workflow程步骤。
* 附加特定于跟踪的元数据和标签以进行过滤和调查。
* 将 Mastra 跟踪连接到第三方跟踪系统。

## 开始使用 {/* #get-started */}

要开始跟踪，请在 Mastra 实例中配置可观察性并运行Agent或Workflow程。您可以通过以下功能配置行为：

* [配置](/docs/observability/overview#configuration)：基本可观察性配置和多个配置，以及无服务器刷新
* [贮存](/docs/observability/overview#storage)：跟踪、日志和指标的存储路由

## 执行结果 {/* #execution-outcomes */}

Spans 通过三个本机字段报告单个执行的含义：

* `outcome`：执行结果，如`success`, `error`, `abort`, `interrupted`, `suspend`, `limit`, `blocked`, or `unknown`.
* `stopReason`：可选的机器可读原因，例如`max_steps`, `guardrail`, or `observer_failed`.
* `stopReasonContext`：有关该原因的可选紧凑事实，例如提供程序错误代码、处理器 ID、信号 ID 或相关跨度 ID。

一个`null` or absent outcome means no outcome has been recorded. Use `endTime` to determine whether a span has finished. Older observability versions can retain a `null` outcome on finished spans. Completing on the last allowed step is `success`. Needing another step after exhausting the allowance is `limit / max_steps`.

配置完成通过`stopWhen` or an iteration hook records `success` with `stop_condition` or `iteration_hook`. A successful delegation followed by a supervisor's `bail()` records `success / delegation_bail`. If the delegated worker fails and the hook bails, the worker retains its failure and the supervisor records `interrupted / delegation_bail` with `causeOutcome` and, when known, `causeStopReason` in `stopReasonContext`.

来电取消记录`abort / caller_cancelled` on the targeted run. Unfinished descendants stopped by that cancellation record `interrupted / caller_cancelled`. A run deadline records `limit / timeout` on the run; work interrupted by that deadline records `interrupted / timeout`. Completed spans retain their outcomes. Generic cleanup ends otherwise unclassified spans as `unknown`.

一个[guardrail](/docs/agents/guardrails) that stops execution by firing a tripwire reports `blocked / guardrail`. Its context identifies the processor:

```json
{
  "outcome": "blocked",
  "stopReason": "guardrail",
  "stopReasonContext": { "processorId": "moderation" }
}
```

对于 Mastra 产生的结果，`stopReasonContext` is a flat tooltip summary with at most three scalar fields. It excludes raw error messages, signal contents, tripwire metadata, and nested causes. Strings are limited to 128 characters. Oversized values are omitted. Missing facts are omitted, and a context with no available facts is `null`.

定制生产者可以提供自己的结果字符串、停止原因和上下文对象。这些值通过跨度更新、导出和重建来保留，并且与跨度元数据使用相同的序列化限制。框架允许列表适用于 Mastra 生成的上下文。

模型块跨度在输出处理器接受或编辑内容后捕获内容。提供者的时间和完成情况是单独记录的，而不捕获原始块内容。有意等待记录的Workflow程`suspend`; a stopped executor handing off unfinished work records `interrupted`, even when the persisted workflow status is `waiting`.

当观察者失败并停止主执行时，观察者跨度记录自己的结果，并且主跨度报告`interrupted / observer_failed`. The context links to the observer memory operation through `observerSpanId` and summarizes its result with `causeOutcome` and `causeStopReason`. For example, context-window exhaustion remains `limit / context_window_exceeded` on the observer. Read that span for its diagnostics. Signal interruptions retain only `signalId` and `signalType`.

如果配置的失败策略让主执行继续，它仍然可以成功。恢复的护栏重试还保留成功的最终结果和被拒绝的尝试的单独结果。

`MastraStorageExporter`和`MastraPlatformExporter` carry these fields in exported span records. Persisting them requires a storage implementation that supports the fields.

模型推理跨度 (`MODEL_INFERENCE`) measure provider execution and record usage. Model chunk spans (`MODEL_CHUNK`) capture content after output processors have accepted or transformed it. Chunks belong to the logical step (`MODEL_STEP`), so buffered output can arrive after provider execution ends without outliving its parent. In the agent streaming paths, inference spans no longer capture response output; use the processed chunk spans or the generation output instead.

## 抽样策略 {/* #sampling-strategies */}

采样允许您控制收集哪些跟踪，帮助您在可观察性需求和资源成本之间取得平衡。

在高流量的生产环境中，收集每条痕迹可能成本高昂且不必要。

采样策略可让您捕获具有代表性的跟踪子集，同时确保您不会错过有关错误或重要操作的关键信息。

您可以在可观察性配置级别配置采样：

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      '10_percent': {
        serviceName: 'my-service',
        // Sample 10% of traces
        sampling: {
          type: 'ratio',
          probability: 0.1,
        },
        exporters: [new MastraStorageExporter()],
      },
    },
  }),
})
```

这`sampling` option allows you to control which traces are collected, helping you balance between observability needs and resource costs. Mastra supports four sampling strategies:

1. **始终样品**：收集 100% 的痕迹。最适合需要完全可见性的开发、调试或低流量场景。

   ```ts
   sampling: {
     type: 'always'
   }
   ```

2. **从不取样**：完全禁用跟踪。对于跟踪没有任何价值的特定环境或当您需要暂时禁用跟踪而不删除配置时非常有用。

   ```ts
   sampling: {
     type: 'never'
   }
   ```

3. **基于比率的采样**：随机采样一定百分比的迹线。非常适合您需要统计洞察而无需完全跟踪成本的生产环境。概率值范围从 0（无痕迹）到 1（所有痕迹）。

   ```ts oxfmt:false
   sampling: {
     type: 'ratio',
     probability: 0.1  // Sample 10% of traces
   }
   ```

4. **定制取样**：根据请求上下文、元数据或业务规则实现您自己的采样逻辑。非常适合复杂的场景，例如基于用户层、请求类型或错误条件进行采样。

   ```ts oxfmt:false
   sampling: {
     type: 'custom',
     sampler: (options) => {
       // Sample premium users at higher rate
       if (options?.metadata?.userTier === 'premium') {
         return Math.random() < 0.5; // 50% sampling
       }

       // Default 1% sampling for others
       return Math.random() < 0.01;
     }
   }
   ```

## 添加自定义元数据 {/* #adding-custom-metadata */}

添加自定义元数据以在跟踪中记录特定于应用程序的上下文，以调试生产问题。

元数据可以包括业务逻辑和性能指标。它还可以携带用户上下文或解释执行期间发生的情况的任何其他信息。

您可以使用跟踪上下文将元数据添加到任何范围：

```ts
execute: async (inputData, context) => {
  const startTime = Date.now()
  const response = await fetch(inputData.endpoint)

  // Add custom metadata to the current span
  context?.tracingContext.currentSpan?.update({
    metadata: {
      apiStatusCode: response.status,
      endpoint: inputData.endpoint,
      responseTimeMs: Date.now() - startTime,
      userTier: inputData.userTier,
      region: process.env.AWS_REGION,
    },
  })

  return await response.json()
}
```

此处设置的元数据将显示在所有配置的导出器中。

### 使用部署环境标记跟踪 {/* #tagging-traces-with-the-deployment-environment */}

设置顶层`environment` field on Mastra to automatically attach the deployment environment to all observability signals without passing `tracingOptions.metadata.environment` on each call.

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'

export const mastra = new Mastra({
  environment: 'production',
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-service',
        exporters: [new MastraStorageExporter()],
      },
    },
  }),
})
```

如果`environment` isn't set, runs started through `mastra dev` resolve to `development` (even though the dev server itself runs with `NODE_ENV=production`); otherwise Mastra falls back to `process.env.NODE_ENV`. If none of these are set, the field is left undefined rather than guessed.

每次通话`tracingOptions.metadata.environment` always takes precedence, so individual calls can override the value when needed.

### 自动元数据来自`RequestContext` {/* #automatic-metadata-from-requestcontext */}

您可以将 Mastra 配置为自动从 RequestContext 中提取值并将它们作为元数据附加到跟踪中的所有范围，而不是手动将元数据添加到每个范围。这对于在整个跟踪中一致地跟踪用户标识符和环境信息以及功能标志或其他请求范围的数据非常有用。

#### 配置级提取 {/* #configuration-level-extraction */}

定义要在跟踪配置中提取哪些 RequestContext 键。这些键将自动包含为使用此配置创建的所有跨度的元数据：

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-service',
        requestContextKeys: ['userId', 'environment', 'tenantId'],
        exporters: [new MastraStorageExporter()],
      },
    },
  }),
})
```

现在，当您使用 RequestContext 执行Agent或Workflow时，会自动提取这些值：

```ts
const requestContext = new RequestContext()
requestContext.set('userId', 'user-123')
requestContext.set('environment', 'production')
requestContext.set('tenantId', 'tenant-456')

// All spans in this trace automatically get userId, environment, and tenantId metadata
const result = await agent.generate('Hello', {
  requestContext,
})
```

#### 按请求添加 {/* #per-request-additions */}

您可以使用添加特定于跟踪的键`tracingOptions.requestContextKeys`. These are merged with the configuration-level keys:

```ts
const requestContext = new RequestContext()
requestContext.set('userId', 'user-123')
requestContext.set('environment', 'production')
requestContext.set('experimentId', 'exp-789')

const result = await agent.generate('Hello', {
  requestContext,
  tracingOptions: {
    requestContextKeys: ['experimentId'], // Adds to configured keys
  },
})

// All spans now have: userId, environment, AND experimentId
```

#### 嵌套值提取 {/* #nested-value-extraction */}

使用点表示法从 RequestContext 中提取嵌套值：

```ts
export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      default: {
        requestContextKeys: ['user.id', 'session.data.experimentId'],
        exporters: [new MastraStorageExporter()],
      },
    },
  }),
})

const requestContext = new RequestContext()
requestContext.set('user', { id: 'user-456', name: 'John Doe' })
requestContext.set('session', { data: { experimentId: 'exp-999' } })

// Metadata will include: { user: { id: 'user-456' }, session: { data: { experimentId: 'exp-999' } } }
```

#### 它是如何运作的 {/* #how-it-works */}

1. **跟踪状态计算**：在跟踪开始时（根跨创建），Mastra 通过合并配置级密钥和每个请求密钥来计算要提取的密钥
2. **自动提取**：根跨度（Agent运行、Workflow执行）自动从 RequestContext 中提取元数据
3. **子跨度提取**：如果通过，子跨度也可以提取元数据`requestContext` when creating them
4. **元数据优先级**：传递给跨度选项的显式元数据始终优先于提取的元数据

### 向轨迹添加标签 {/* #adding-tags-to-traces */}

标签是字符串标签，可帮助您对跟踪进行分类和过滤。与元数据（包含结构化键值数据）不同，标签是专为快速过滤和组织而设计的纯字符串。

使用`tracingOptions.tags` to add tags when executing agents or workflows:

```ts
// With agents
const result = await agent.generate('Hello', {
  tracingOptions: {
    tags: ['production', 'experiment-v2', 'user-request'],
  },
})

// With workflows
const run = await mastra.getWorkflow('myWorkflow').createRun()
const result = await run.start({
  inputData: { data: 'process this' },
  tracingOptions: {
    tags: ['batch-processing', 'priority-high'],
  },
})
```

#### 标签如何工作 {/* #how-tags-work */}

* **仅根跨**：标签仅应用于跟踪的根范围（Agent运行或Workflow运行范围）
* **广泛支持**：大多数导出器都支持标签来过滤和搜索跟踪：
  * **智囊团**： 本国的`tags` field
  * **朗福斯**： 本国的`tags` field on traces
  * **阿里兹出口商**: `tag.tags` OpenInference attribute
  * **奥特尔出口商**: `mastra.tags` span attribute
  * **奥泰布里奇酒店**: `mastra.tags` span attribute
* **可与元数据结合**: 两个都可以用`tags` and `metadata` in the same `tracingOptions`

```ts
const result = await agent.generate([{ role: 'user', content: 'Analyze this' }], {
  tracingOptions: {
    tags: ['production', 'analytics'],
    metadata: { userId: 'user-123', experimentId: 'exp-456' },
  },
})
```

#### 常见标签模式 {/* #common-tag-patterns */}

* **环境**: `"production"`, `"staging"`, `"development"`
* **功能标志**: `"feature-x-enabled"`, `"beta-user"`
* **请求类型**: `"user-request"`, `"batch-job"`, `"scheduled-task"`
* **优先级**: `"priority-high"`, `"priority-low"`
* **实验**: `"experiment-v1"`, `"control-group"`, `"treatment-a"`

### 命名跟踪 {/* #naming-a-trace */}

例如，默认情况下，同一Agent或Workflow程的每次运行都会获得相同的根跨名称`workflow run: 'skill-analyze'`. When one workflow runs over many subjects, set `rootSpanName` in `tracingOptions` to label each run. The name replaces the root span name in Studio's trace list and in exporters that display span names.

```ts
const run = await mastra.getWorkflow('skillAnalyze').createRun()

await run.start({
  inputData: { skillId: 'typescript' },
  tracingOptions: {
    rootSpanName: 'skill-analyze: typescript',
  },
})
```

该名称仅适用于根跨度。子跨度保留其默认名称。实体过滤器继续工作，因为Workflow或Agent ID 单独存储为`entityId` and `entityName`.

基于 OpenTelemetry 的导出器和 Langfuse 导出器根据实体 ID 构建其跨度和跟踪名称，因此它们不受影响。要命名 Langfuse 迹线，请设置`metadata.traceName` as described in the [Langfuse integration](/integrations/observability/langfuse).

### 隐藏敏感输入/输出 {/* #hiding-sensitive-inputoutput */}

处理敏感数据时，您可能希望防止输入和输出值记录到可观察平台。使用`hideInput` and `hideOutput` in `tracingOptions` to exclude this data from all spans in a trace:

```ts
// Hide input data (e.g., user credentials, PII)
const result = await agent.generate([{ role: 'user', content: 'Process this sensitive data' }], {
  tracingOptions: {
    hideInput: true, // Input will be hidden from all spans
  },
})

// Hide output data (e.g., generated secrets, confidential results)
const result = await agent.generate([{ role: 'user', content: 'Generate API keys' }], {
  tracingOptions: {
    hideOutput: true, // Output will be hidden from all spans
  },
})

// Hide both input and output
const result = await agent.generate([{ role: 'user', content: 'Handle confidential request' }], {
  tracingOptions: {
    hideInput: true,
    hideOutput: true,
  },
})
```

#### 它是如何运作的 {/* #how-it-works-1 */}

* **全迹线效应**：当在根跨度上设置时，这些选项适用于跟踪中的所有子跨度（Tool调用，加上模型生成等）
* **导出时过滤**：数据在执行期间在内部保持可用，但在将跨度导出到可观察平台时被排除
* **可与其他选项结合使用**: 你可以用`hideInput`/`hideOutput` alongside `tags`, `metadata`, and other `tracingOptions`

```ts
const result = await agent.generate([{ role: 'user', content: 'Sensitive operation' }], {
  tracingOptions: {
    hideInput: true,
    hideOutput: true,
    tags: ['sensitive-operation', 'pii-handling'],
    metadata: { operationType: 'credential-processing' },
  },
})
```

要对敏感数据进行更细粒度的控制，请考虑使用[Sensitive Data Filter](/reference/observability/tracing/processors/sensitive-data-filter) processor, which can redact specific fields (like passwords, tokens, and keys) while preserving the rest of the input/output.

#### 子跨度和元数据提取 {/* #child-spans-and-metadata-extraction */}

在Tool或Workflow程步骤中创建子范围时，您可以传递`requestContext` parameter to enable metadata extraction:

```ts
execute: async (inputData, context) => {
  // Create child span WITH requestContext - gets metadata extraction
  const dbSpan = context?.tracingContext.currentSpan?.createChildSpan({
    type: 'generic',
    name: 'database-query',
    requestContext: context?.requestContext, // Pass to enable metadata extraction
  })

  const results = await db.query('SELECT * FROM users')
  dbSpan?.end({ output: results })

  // Or create child span WITHOUT requestContext - no metadata extraction
  const cacheSpan = context?.tracingContext.currentSpan?.createChildSpan({
    type: 'generic',
    name: 'cache-check',
    // No requestContext - won't extract metadata
  })

  return results
}
```

您可以对哪些子跨度包含 RequestContext 元数据进行细粒度控制。根跨度（Agent/Workflow执行）始终自动提取元数据，而子跨度仅在您显式传递时提取`requestContext`.

## 创建子跨度 {/* #creating-child-spans */}

子跨度允许您跟踪Workflow程步骤或Tool中的细粒度操作。它们提供对数据库查询和 API 调用等子操作以及文件操作或复杂计算的可见性。这种层次结构可帮助您识别性能瓶颈并了解操作的确切顺序。

在Tool调用或Workflow程步骤中创建子跨度以跟踪特定操作：

```ts
execute: async (inputData, context) => {
  // Create another child span for the main database operation
  const querySpan = context?.tracingContext.currentSpan?.createChildSpan({
    type: 'generic',
    name: 'database-query',
    input: { query: inputData.query },
    metadata: { database: 'production' },
  })

  try {
    const results = await db.query(inputData.query)
    querySpan?.end({
      output: results.data,
      metadata: {
        rowsReturned: results.length,
        queryTimeMs: results.executionTime,
        cacheHit: results.fromCache,
      },
    })
    return results
  } catch (error) {
    querySpan?.error({
      error,
      metadata: { retryable: isRetryableError(error) },
    })
    throw error
  }
}
```

子跨度自动从其父跨度继承跟踪上下文，从而在可观察性平台中维护关系层次结构。

## 跨度格式化 {/* #span-formatting */}

Mastra 提供了两种在跨度数据到达可观测平台之前对其进行转换的方法：**span processors** and **custom span formatters**. Both allow you to modify, filter, or enrich trace data, but they operate at different levels and serve different purposes.

|特色 |跨度处理器 |自定义 Span 格式化程序 |
| - | - | - |
|配置级别|可观察性配置 |每个出口商 |
|运行于 |内部的`Span` object | Exported `ExportedSpan` data |
| Applies to | All exporters | Single exporter |
| Async support | No | Yes |
| Use case | Security, filtering, enrichment | Platform-specific formatting, async enrichment |

使用**span processors** for synchronous transformations that should apply to all exporters (like redacting sensitive data). Use **custom span formatters** when different exporters need different representations of the same data (like plain text for one platform and structured data for another), or when you need to perform asynchronous operations like fetching data from external APIs.

### 跨度处理器 {/* #span-processors */}

Span 处理器在导出跟踪数据之前对其进行转换、过滤或丰富。它们充当跨度创建和导出之间的管道，使您能够出于安全性、合规性或调试目的修改跨度。处理器运行一次并影响所有导出器。

#### 内置处理器 {/* #built-in-processors */}

* [敏感数据过滤器](/reference/observability/tracing/processors/sensitive-data-filter)编辑敏感信息。它在默认的可观察性配置中启用。

#### 创建自定义处理器 {/* #creating-custom-processors */}

您可以通过实现来创建自定义跨度处理器`SpanOutputProcessor` interface. Here's a basic example that converts all input text in spans to lowercase:

```ts title="src/processors/lowercase-input-processor.ts"
import type { SpanOutputProcessor, AnySpan } from '@mastra/core/observability'
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'

export class LowercaseInputProcessor implements SpanOutputProcessor {
  name = 'lowercase-processor'

  process(span: AnySpan): AnySpan {
    span.input = `${span.input}`.toLowerCase()
    return span
  }

  async shutdown(): Promise<void> {
    // Cleanup if needed
  }
}

// Use the custom processor
export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      development: {
        spanOutputProcessors: [new LowercaseInputProcessor(), new SensitiveDataFilter()],
        exporters: [new MastraStorageExporter()],
      },
    },
  }),
})
```

`process()`必须改变它接收到的范围并返回相同的实例，或者返回`undefined` to drop the span. Don't return a copy (for example `{ ...span, input: '...' }`): `exportSpan()` and `isValid` are instance members of the live span, so a copy can't be exported. Mastra logs a processor error and drops the span in that case.

处理器按照定义的顺序执行，允许您链接多个转换。常见用例包括：

* 编辑敏感数据（密码、令牌、API 密钥）
* 添加特定于环境的元数据
* 根据条件过滤跨度
* 规范化数据格式
* 通过业务背景丰富跨度

## 量程过滤 {/* #span-filtering */}

跨度过滤可让您在数据到达可观测平台之前减少噪音和每个跨度的成本。每个可观察性实例进行配置，因此不同的导出器或环境可以保留不同级别的详细信息。

* 使用`excludeSpanTypes` to drop entire categories of spans with minimal configuration.
* 使用`spanFilter` when you need custom logic based on the exported span data.

以下示例演示了如何在单个配置中组合这两个选项：

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { SpanType } from '@mastra/core/observability'
import { Observability, MastraStorageExporter } from '@mastra/observability'
import { LangfuseExporter } from '@mastra/langfuse'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-app',
        exporters: [new MastraStorageExporter(), new LangfuseExporter()],
        excludeSpanTypes: [SpanType.MODEL_CHUNK, SpanType.MODEL_STEP],
        spanFilter: span => {
          if (span.type === SpanType.TOOL_CALL && span.attributes?.success) {
            return false
          }

          return true
        },
      },
    },
  }),
})
```

过滤在导出时按以下顺序进行：

1. 内部跨度将被丢弃，除非`includeInternalSpans` is `true`.
2. `excludeSpanTypes`删除匹配的跨度类型。
3. `spanOutputProcessors`变换剩余的跨度。
4. `spanFilter`决定是否保留最终导出的跨度。

如果`spanFilter` throws, Mastra keeps the span and logs the error to avoid silent data loss. For the full span type list and more examples, see the [Span filtering reference](/reference/observability/tracing/span-filtering).

### 自定义跨度格式化程序 {/* #custom-span-formatters */}

自定义跨度格式化程序改变跨度在特定可观察性平台中的显示方式。与跨度处理器不同，格式化程序是按导出器配置的，允许针对不同的目标进行不同的格式化。格式化程序支持同步和异步操作。

#### 使用案例 {/* #use-cases */}

* **从AI SDK消息中提取纯文本**：将结构化消息数组转换为可读文本
* **转换输入/输出格式**：自定义数据在特定平台的显示方式
* **特定于平台的字段映射**：根据平台要求添加或删除字段
* **异步数据丰富**：从外部 API 或数据库获取附加上下文

#### 配置 {/* #configuration */}

添加一个`customSpanFormatter` to any exporter configuration:

```ts title="src/mastra/index.ts"
import { BraintrustExporter } from '@mastra/braintrust'
import { LangfuseExporter } from '@mastra/langfuse'
import { SpanType } from '@mastra/core/observability'
import type { CustomSpanFormatter } from '@mastra/core/observability'
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'

// Formatter that extracts plain text from AI messages
const plainTextFormatter: CustomSpanFormatter = span => {
  if (span.type === SpanType.AGENT_RUN && Array.isArray(span.input)) {
    const userMessage = span.input.find(m => m.role === 'user')
    return {
      ...span,
      input: userMessage?.content ?? span.input,
    }
  }
  return span
}

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-service',
        exporters: [
          // Braintrust gets plain text formatting
          new BraintrustExporter({
            customSpanFormatter: plainTextFormatter,
          }),
          // Langfuse keeps the original structured format
          new LangfuseExporter(),
        ],
      },
    },
  }),
})
```

#### 链接多个格式化程序 {/* #chaining-multiple-formatters */}

使用`chainFormatters` to combine multiple formatters. Chains support both sync and async formatters:

```ts
import { chainFormatters } from '@mastra/observability'

const inputFormatter: CustomSpanFormatter = span => ({
  ...span,
  input: extractPlainText(span.input),
})

const outputFormatter: CustomSpanFormatter = span => ({
  ...span,
  output: extractPlainText(span.output),
})

const exporter = new BraintrustExporter({
  customSpanFormatter: chainFormatters([inputFormatter, outputFormatter]),
})
```

#### 异步格式化程序 {/* #async-formatters */}

自定义 Span 格式化程序支持异步操作，支持从外部 API 或数据库获取数据等用例来丰富您的 Span：

```ts
import type { CustomSpanFormatter } from '@mastra/core/observability'

// Async formatter that enriches spans with user data
const userEnrichmentFormatter: CustomSpanFormatter = async span => {
  const userId = span.metadata?.userId
  if (!userId) return span

  // Fetch user data from your API or database
  const userData = await fetchUserData(userId)

  return {
    ...span,
    metadata: {
      ...span.metadata,
      userName: userData.name,
      userEmail: userData.email,
      department: userData.department,
    },
  }
}

// Async formatter that looks up additional context
const contextEnrichmentFormatter: CustomSpanFormatter = async span => {
  if (span.type !== SpanType.AGENT_RUN) return span

  // Fetch experiment configuration
  const experimentConfig = await getExperimentConfig(span.metadata?.experimentId)

  return {
    ...span,
    metadata: {
      ...span.metadata,
      experimentVariant: experimentConfig?.variant,
      experimentGroup: experimentConfig?.group,
    },
  }
}

// Use async formatters with an exporter
const exporter = new BraintrustExporter({
  customSpanFormatter: userEnrichmentFormatter,
})

// Or chain sync and async formatters together
const exporter = new LangfuseExporter({
  customSpanFormatter: chainFormatters([
    plainTextFormatter, // sync
    userEnrichmentFormatter, // async
    contextEnrichmentFormatter, // async
  ]),
})
```

:::注意
异步格式化程序会增加跨度导出的延迟。保持异步操作快速（低于 100 毫秒）以避免减慢应用程序速度。考虑对经常访问的数据使用缓存。
:::

## 序列化选项 {/* #serialization-options */}

序列化选项控制在导出之前如何截断范围数据（输入、输出和属性）。当处理大型负载、深层嵌套对象或需要优化跟踪存储时，这非常有用。

### 配置 {/* #configuration-1 */}

添加`serializationOptions` to your observability configuration:

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-service',
        serializationOptions: {
          maxStringLength: 2048, // Maximum length for string values (default: 131072)
          maxDepth: 10, // Maximum depth for nested objects (default: 8)
          maxArrayLength: 100, // Maximum number of items in arrays (default: 50)
          maxObjectKeys: 75, // Maximum number of keys in objects (default: 50)
        },
        exporters: [new MastraStorageExporter()],
      },
    },
  }),
})
```

### 可用选项 {/* #available-options */}

|选项|默认 |描述 |
| - | - | - |
|`maxStringLength` | 131072 (128 KB) | Maximum length for string values. Longer strings are truncated. |
| `maxDepth` | 8 | Maximum depth for nested objects. Deeper levels are omitted. |
| `maxArrayLength` | 50 | Maximum number of items in arrays. Additional items are omitted. |
| `maxObjectKeys` | 50 | Maximum number of keys in objects. Additional keys are omitted. |

### 使用案例 {/* #use-cases-1 */}

**增加调试限制**：增加这些限制以捕获大型文档和 API 响应以及其他数据结构的更多上下文：

```ts oxfmt:false
serializationOptions: {
  maxStringLength: 262144, // Capture longer text content (256 KB)
  maxDepth: 12,            // Handle deeply nested JSON responses
  maxArrayLength: 200,     // Keep more items from large lists
}
```

**减少生产中的走线尺寸**：当您不需要完整的负载可见性时，降低这些值可以降低存储成本并提高性能：

```ts oxfmt:false
serializationOptions: {
  maxStringLength: 256,   // Truncate strings aggressively
  maxDepth: 3,            // Shallow object representation
  maxArrayLength: 10,     // Keep only first few items
  maxObjectKeys: 20,      // Limit object keys
}
```

所有选项都是可选的，如果未指定，它们将回退到上面显示的默认值。

## 检索跟踪 ID {/* #retrieving-trace-ids */}

当您在启用跟踪的情况下执行Agent或Workflow时，响应包括`traceId` that you can use to look up the full trace in your observability platform. This is useful for debugging or customer support, or alternatively correlating traces with other events in your system.

### Agent跟踪 ID {/* #agent-trace-ids */}

两个都`generate` and `stream` methods return the trace ID in their response:

```ts
// Using generate
const result = await agent.generate('Hello')

console.log('Trace ID:', result.traceId)

// Using stream
const streamResult = await agent.stream('Tell me a story')

console.log('Trace ID:', streamResult.traceId)
```

### Workflow程跟踪 ID {/* #workflow-trace-ids */}

Workflow执行还返回跟踪 ID：

```ts
// Create a workflow run
const run = await mastra.getWorkflow('myWorkflow').createRun()

// Start the workflow
const result = await run.start({
  inputData: { data: 'process this' },
})

console.log('Trace ID:', result.traceId)

// Or stream the workflow
const { stream, getWorkflowState } = run.stream({
  inputData: { data: 'process this' },
})

// Get the final state which includes the trace ID
const finalState = await getWorkflowState()
console.log('Trace ID:', finalState.traceId)
```

### 使用跟踪 ID {/* #using-trace-ids */}

获得跟踪 ID 后，您可以：

1. **在 Studio 中查找痕迹**：导航到轨迹视图并按 ID 搜索
2. **外部平台查询轨迹**：在 Langfuse、Braintrust、MLflow 或您的可观察平台中使用 ID
3. **与日志关联**：将跟踪 ID 包含在应用程序日志中以供交叉引用
4. **分享以供调试**：提供跟踪ID以支持团队或开发人员进行调查

仅当启用跟踪时，跟踪 ID 才可用。如果跟踪被禁用或采样排除了请求，`traceId` will be `undefined`.

## 与外部跟踪系统集成 {/* #integrating-with-external-tracing-systems */}

如果您的应用程序已使用分布式跟踪（例如 OpenTelemetry 或 Datadog），您可以将 Mastra 跟踪连接到父跟踪上下文。这使您可以通过应用程序及其 Mastra Agent或Workflow程调用来跟踪请求。

### 传递外部跟踪 ID {/* #passing-external-trace-ids */}

使用`tracingOptions` parameter to specify the trace context from your parent system:

```ts
// Get trace context from your existing tracing system
const parentTraceId = getCurrentTraceId() // Your tracing system
const parentSpanId = getCurrentSpanId() // Your tracing system

// Execute Mastra operations as part of the parent trace
const result = await agent.generate('Analyze this data', {
  tracingOptions: {
    traceId: parentTraceId,
    parentSpanId: parentSpanId,
  },
})

// The Mastra trace will now appear as a child in your distributed trace
```

### 开放遥测集成 {/* #opentelemetry-integration */}

与 OpenTelemetry 集成允许 Mastra 跟踪直接出现在您现有的可观测平台中：

```ts
import { trace } from '@opentelemetry/api'

// Get the current OpenTelemetry span
const currentSpan = trace.getActiveSpan()
const spanContext = currentSpan?.spanContext()

if (spanContext) {
  const result = await agent.generate(userMessage, {
    tracingOptions: {
      traceId: spanContext.traceId,
      parentSpanId: spanContext.spanId,
    },
  })
}
```

### Workflow程整合 {/* #workflow-integration */}

Workflow支持相同的跟踪传播模式：

```ts
const workflow = mastra.getWorkflow('data-pipeline')
const run = await workflow.createRun()

const result = await run.start({
  inputData: { data: '...' },
  tracingOptions: {
    traceId: externalTraceId,
    parentSpanId: externalSpanId,
  },
})
```

### 将运行嵌套在较早的 Mastra 运行下 {/* #nesting-a-run-under-an-earlier-mastra-run */}

一个`parentSpanId` can point at two kinds of spans. The span can belong to your own tracing system, as in the examples above. Mastra then treats the run as the top of the trace it exports, and the run sets the trace's name, input, output, and tags.

该跨度也可以是同一轨迹中较早的 Mastra 运行，例如 LLM 法官对完成的转弯进行评分。放`nestUnderParent: true` for this case. The new run becomes a child of that span, and the trace keeps the name, input, output, tags, user, and session of the run that started it.

```ts
const turn = await assistant.generate('When does my order ship?')

await judge.generate(`Grade this answer: ${turn.text}`, {
  tracingOptions: {
    traceId: turn.traceId,
    parentSpanId: turn.spanId,
    nestUnderParent: true,
  },
})
```

这`nestUnderRun()` helper builds the same options from the earlier run's result:

```ts
import { nestUnderRun } from '@mastra/core/observability'

await judge.generate(`Grade this answer: ${turn.text}`, {
  tracingOptions: nestUnderRun(turn),
})
```

两次运行可以在不同的进程中。马斯特拉无视`nestUnderParent` when `traceId` or `parentSpanId` is missing or not valid. It also ignores the option when a tracing bridge starts the run in a different trace. The [Langfuse](/integrations/observability/langfuse) and [Braintrust](/integrations/observability/braintrust) exporters use this option. In other exporters, only the tags rule applies.

### 身份证件格式要求 {/* #id-format-requirements */}

Mastra 验证跟踪和跨度 ID 以确保兼容性：

* **跟踪 ID**：1-32个十六进制字符（OpenTelemetry使用32）
* **跨度 ID**：1-16个十六进制字符（OpenTelemetry使用16）

无效 ID 得到妥善处理，Mastra 记录错误并继续：

* 无效的跟踪 ID → 生成新的跟踪 ID
* 父级跨度 ID 无效 → 忽略父级关系

因此，即使输入格式错误，跟踪也不会导致应用程序崩溃。

### 示例：Express 中间件 {/* #example-express-middleware */}

下面是一个完整的示例，显示了 Express 应用程序中的跟踪传播：

```ts
import { trace } from '@opentelemetry/api'
import express from 'express'

const app = express()

app.post('/api/analyze', async (req, res) => {
  // Get current OpenTelemetry context
  const currentSpan = trace.getActiveSpan()
  const spanContext = currentSpan?.spanContext()

  const result = await agent.generate(req.body.message, {
    tracingOptions: spanContext
      ? {
          traceId: spanContext.traceId,
          parentSpanId: spanContext.spanId,
        }
      : undefined,
  })

  res.json(result)
})
```

这将创建一个单一的分布式跟踪，其中包括 HTTP 请求处理和 Mastra Agent执行，可以在您选择的可观察性平台中查看。

### MCP 通话 {/* #mcp-calls */}

模型上下文协议 (MCP) 调用无需任何设置即可链接调用者的跟踪和服务器的跟踪。当Agent或Workflow通过以下方式调用Tool时`MCPClient`, the `MCPServer` that handles it keeps its own trace and records a link to the tool call span, and the tool call span links back to the server's span. Each side keeps its own trace, root span, and trace summary. When the server uses a tracing bridge and its HTTP instrumentation continues the caller's trace, the request joins that trace instead. Mastra storage saves the links with the spans, and exporters with span link support send them too.

这也适用于任何一方的非 Mastra 软件。请参阅[`MCPServer` reference](/reference/tools/mcp-server#linking-to-the-callers-trace) for details, and the [`MCPClient` reference](/reference/tools/mcp-client) to send your own trace context.

## 什么被追踪 {/* #what-gets-traced */}

Mastra 自动创建跨度：

### Agent经营 {/* #agent-operations */}

* **Agent运行**：使用说明和Tool完成执行
* **信号触发运行**： 这`AGENT_RUN` span records a starting signal's `id`, `type`, `tagName`, and `attributes` under `attributes.signal`
* **法学硕士来电**：模型与令牌和参数的交互
* **Tool执行**：带有输入和输出的函数调用
* **内存操作**：线索和语义回忆

### Workflow程操作 {/* #workflow-operations */}

* **Workflow程运行**：从头到尾完整执行
* **单独的步骤**：带有输入/输出的步骤处理
* **控制流程**：条件、循环、并行执行
* **等待操作**：延误和事件等待
