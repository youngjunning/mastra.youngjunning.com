# Knowledge

在 Studio 的 Knowledge 页面，你可以查看 Agent 掌握了哪些知识：有哪些范围和页面、它们如何关联，以及各项内容由谁编写。这个页面为只读，可用来核对已加载的内容，并实时查看 Agent 的编辑。

:::alpha

Knowledge 目前处于 alpha 阶段，API 可能随版本变化。

:::

## 启用路由 {/* #enable-the-routes */}

Knowledge 路由**默认关闭**。启用前，Studio 的 Knowledge 页面会提示尚未启用浏览功能。请在 `Mastra` 上注册 Knowledge 实例，并添加路由：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { KNOWLEDGE_ROUTES } from '@mastra/server/server-adapter'
import { knowledge } from './knowledge'
import { supportAgent } from './agents/support-agent'

export const mastra = new Mastra({
  agents: { supportAgent },
  knowledge: { company: knowledge },
  server: { apiRoutes: [...KNOWLEDGE_ROUTES] },
})
```

路由挂载在服务器的 API 前缀下，默认路径为 `/api/knowledge`，需要 `@mastra/core` 1.81.0 或更高版本。在 1.81.0 中，Studio 只统计已加载页面之间的链接。[服务器路由](/reference/server/routes#knowledge)列出了各条路由、参数和错误。

## 可以查看哪些内容 {/* #what-you-see */}

- **页面树**：按 Agent 组织的层级列出所有范围及其中的页面。
- **关系图**：展示同一批页面及其关系。连线表示父页面、备注提及的页面、正文中的链接，以及范围之间的访问授权。图例标明各类连线；在任一视图中选择页面即可打开它。
- **页面**：显示正文、版本、最后更新者、备注及其作者、子页面、其他页面中提及此页的备注，以及此页为谁置顶。
- **活动**：记录每个页面的创建、编辑、移动、合并、备注和置顶历史，并标明各次操作的作者和时间。
- **搜索**：按页面名称、描述、正文和备注文本搜索。

在窄屏幕上，页面树和关系图共用一个面板，切换视图时会保留所选页面。

Agent 写入时，页面树、关系图和已打开的页面会实时更新，无需刷新。Studio 会跟踪通过 Mastra 上注册的 Knowledge 实例执行的写入。如果是另一进程或使用同一存储的另一实例写入，则要刷新后才能看到。

在 Agent 的对话中，Knowledge Tool 调用会显示读写过的页面，置顶页面则显示本次运行收到的页面。两处都可以跳转到此视图中的对应页面。

## 控制访问范围 {/* #control-who-sees-what */}

路由返回哪些数据，取决于应用是否配置了身份验证（`server.auth` 或 `studio.auth`）：

- **未启用身份验证：**路由以实例所有者身份读取数据，能访问服务器的人都可获取所有范围、页面和备注。仅在本地或测试项目中使用此方式，并在部署前配置身份验证。
- **启用身份验证：**路由只返回已登录用户有权读取的内容。在 `authorize` 中，将请求上下文的 `MASTRA_KNOWLEDGE_PRINCIPALS_KEY` 设为该用户的 Knowledge 范围。Knowledge 使用与 Agent 相同的访问规则。alpha 阶段的规则不能作为[隔离边界](/docs/knowledge/scopes-and-access)，因此不要存储绝不能向其他用户公开的内容。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { KNOWLEDGE_ROUTES, MASTRA_KNOWLEDGE_PRINCIPALS_KEY } from '@mastra/server/server-adapter'
import { appAuthorize } from './auth' // your existing authorization

export const mastra = new Mastra({
  server: {
    apiRoutes: [...KNOWLEDGE_ROUTES],
    auth: {
      // authenticateToken, ...
      authorize: async (path, method, user, context) => {
        if (path.startsWith('/api/knowledge')) {
          context
            .get('requestContext')
            .set(
              MASTRA_KNOWLEDGE_PRINCIPALS_KEY,
              user.isAdmin ? 'all' : [`org:${user.orgId}`, `team:${user.orgId}:${user.teamId}`],
            )
          return true
        }
        return appAuthorize(path, method, user, context)
      },
    },
  },
})
```

如果使用其他前缀，请同步修改 `authorize` 中对 `/api/knowledge` 的检查。否则请求上下文不会设置该键，路由会返回 `403`。

`authorize` 函数会取代服务器对所有路由使用的规则和角色检查，因此其他路径应保留应用现有的授权判断，如上例所示。如果一律返回 `true`，任何已登录用户都能调用任意路由。

将该键的值设为范围数组；如果用户应能查看整个实例，则设为 `'all'`。空数组表示无法读取任何内容。其他取值的行为见 [Knowledge 访问权限与错误](/reference/server/routes#knowledge-access-and-errors)。如果配置了 `studio.auth`，Studio 请求会使用它而非 `server.auth`，请在前者的 `authorize` 中设置该键。

### 定义了 `authorizeUser` 的 Provider {/* #providers-with-authorizeuser */}

如果身份验证 Provider 定义了 `authorizeUser`，服务器就不会调用 `authorize`。这包括实现了该方法的任何 `MastraAuthProvider` 子类，以及所有 `CompositeAuth`。使用这些 Provider 时，请改在[服务器中间件](/docs/server/middleware)中设置该键：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { KNOWLEDGE_ROUTES, MASTRA_KNOWLEDGE_PRINCIPALS_KEY } from '@mastra/server/server-adapter'
import { auth, getSessionUser } from './auth' // your provider and session lookup

export const mastra = new Mastra({
  server: {
    apiRoutes: [...KNOWLEDGE_ROUTES],
    auth,
    middleware: [
      {
        path: '/api/knowledge/*',
        handler: async (c, next) => {
          const user = await getSessionUser(c.req.raw)
          if (user) {
            c.get('requestContext').set(
              MASTRA_KNOWLEDGE_PRINCIPALS_KEY,
              user.isAdmin ? 'all' : [`org:${user.orgId}`, `team:${user.orgId}:${user.teamId}`],
            )
          }
          await next()
        },
      },
    ],
  },
})
```

服务器中间件先于路由的身份验证检查执行，此时请求上下文中还没有已登录用户。请像上例一样，用应用自己的会话检查从请求中查找用户。路由随后仍会执行身份验证，并拒绝 Provider 不接受的调用方。若使用了不同前缀，请修改中间件的 `path`。

### 部署注意事项 {/* #deployment-notes */}

- **没有 RBAC Provider：**系统会跳过 `knowledge:read` 检查。在任何实例中，具备访问主体映射的已验证用户均可读取这些主体有权访问的页面。
- **有 FGA Provider：**每个 Knowledge 实例都会单独检查 `knowledge:read`。用户只能查看你授权的实例。详见 [Knowledge 访问权限与错误](/reference/server/routes#knowledge-access-and-errors)。
- **NestJS：**NestJS 适配器尚未提供 Knowledge 路由。

## 构建自定义视图 {/* #build-your-own-view */}

要在应用中显示 Knowledge 的变更，可用 [`knowledge.onChange()`](/reference/knowledge/knowledge-class#onchange) 订阅。事件只携带 ID，不包含内容。向用户显示页面前，请按其访问范围重新读取页面。收到 `page` 的 `delete` 事件后，无法再读取该页面，应将其从视图移除。对于 `page` 的 `merge` 事件，`pageId` 指向合并目标，还应移除 `sourceId` 指向的被合并页面。`scope` 事件只针对新范围发送，不会为其子范围或模板页面发送；要查找这些内容，请重新列出该范围的内容。
