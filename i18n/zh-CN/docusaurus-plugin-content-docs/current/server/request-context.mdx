# 请求上下文

Agent、Tool 和 Workflow 都可以接收 `RequestContext` 参数，让底层组件使用本次请求的值。

## 何时使用`RequestContext` {/* #when-to-use-requestcontext */}

当组件的行为需要随运行时条件变化时，使用 `RequestContext`。例如，可以根据用户属性切换模型或存储后端，也可以根据语言调整指令和 Tool 的选择。

:::note

`RequestContext` 主要用于向单次请求传递数据。它不同于 Agent memory；后者负责跨多次调用保存对话历史和状态。

:::

## 设定值 {/* #setting-values */}

在调用 Agent、network、Workflow 或 Tool 时传入 `requestContext`，执行期间所有底层组件便可使用其中的值。调用前用 `.set()` 设置值。

`.set()` 方法接收两个参数：

1. **key**：标识该值的名称。
1. **value**：与该键关联的数据。

```typescript
import { RequestContext } from '@mastra/core/request-context'

export type UserTier = {
  'user-tier': 'enterprise' | 'pro'
}

const requestContext = new RequestContext<UserTier>()
requestContext.set('user-tier', 'enterprise')

const agent = mastra.getAgent('weatherAgent')
await agent.generate("What's the weather in London?", {
  requestContext,
})

const routingAgent = mastra.getAgent('routingAgent')
routingAgent.network("What's the weather in London?", {
  requestContext,
})

const run = await mastra.getWorkflow('weatherWorkflow').createRun()
await run.start({
  inputData: {
    location: 'London',
  },
  requestContext,
})
await run.resume({
  resumeData: {
    city: 'New York',
  },
  requestContext,
})

await weatherTool.execute({ location: 'London' }, { requestContext })
```

### 使用仅限运行时的键 {/* #using-runtime-only-keys */}

提供类型或 `requestContextSchema` 后，`get`、`set`、`has` 和 `delete` 只接受已声明的键。这有助于发现拼写错误，并保留已声明值的类型。

对于不属于 schema 的基础设施或中间件键，使用 `getRaw`、`setRaw`、`hasRaw` 和 `deleteRaw`。原始值的类型是 `unknown`，使用前须先收窄类型。

```typescript
const requestContext = new RequestContext<{ userId: string }>()

requestContext.set('userId', 'user-123')
requestContext.setRaw('session.cache', { hits: 0 })

const cache = requestContext.getRaw('session.cache')

if (typeof cache === 'object' && cache !== null && 'hits' in cache) {
  console.log(cache.hits)
}
```

应用数据优先使用 schema 中声明的键。只有键必须留在请求上下文 schema 之外时，才使用 raw 方法。

### 根据请求标头设置值 {/* #setting-values-based-on-request-headers */}

可以在运行时服务器中间件中提取请求信息，填充 `requestContext`。此例根据 Cloudflare 的 `CF-IPCountry` 标头设置 `temperature-unit`，使响应符合用户所在地区。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RequestContext } from '@mastra/core/request-context'
import { testWeatherAgent } from './agents/test-weather-agent'

export const mastra = new Mastra({
  agents: { testWeatherAgent },
  server: {
    middleware: [
      async (context, next) => {
        const country = context.req.header('CF-IPCountry')
        const requestContext = context.get('requestContext')

        requestContext.set('temperature-unit', country === 'US' ? 'fahrenheit' : 'celsius')

        await next()
      },
    ],
  },
})
```

服务器中间件的用法参见 [Middleware](/docs/server/middleware)。

## Studio {/* #studio */}

本地开发时，可以在 JSON 文件中定义预设，并通过 [`--request-context-presets`](/reference/cli/mastra#--request-context-presets) CLI 标志加载到 [Studio](/docs/studio/overview)。Studio 的请求上下文编辑器会增加一个下拉菜单，方便切换配置，无须每次手动修改 JSON。

```bash
mastra dev --request-context-presets ./presets.json
```

```json title="presets.json"
{
  "development": { "userId": "dev-user", "env": "development" },
  "production": { "userId": "prod-user", "env": "production" }
}
```

从下拉菜单选择预设后，JSON 编辑器会填入相应的值。手动编辑 JSON 则会使下拉菜单切回 **"Custom"**。

## 从 Agent 读取值 {/* #accessing-values-with-agents */}

在 Agent 支持的配置选项中，可以访问 `requestContext` 参数。这些函数可以是同步函数，也可以是 `async` 函数。使用 `.get()` 从 `requestContext` 读取值。

```typescript title="src/mastra/agents/weather-agent.ts"
import { Agent } from '@mastra/core/agent'

export type UserTier = {
  'user-tier': 'enterprise' | 'pro'
}

export const weatherAgent = new Agent({
  id: 'weather-agent',
  name: 'Weather Agent',
  instructions: async ({ requestContext }) => {
    const userTier = requestContext.get('user-tier') as UserTier['user-tier']

    if (userTier === 'enterprise') {
    }
  },
  model: ({ requestContext }) => {},
  tools: ({ requestContext }) => {},
  memory: ({ requestContext }) => {},
})
```

`requestContext` 也可用于 `agents`、`workflows`、`scorers`、`inputProcessors` 和 `outputProcessors` 等选项。

### 读取已验证的用户 {/* #accessing-the-authenticated-user */}

配置[服务器身份验证](/docs/auth/overview)后，相同的配置回调还会收到可选的 `user` 参数。它代表已验证的终端用户，并统一为稳定的 `MastraUser` 结构（`{ id: string, name?: string, email?: string, avatarUrl?: string, role?: string }`）。可用它定制指令、模型或 Tool，无须自行从 `requestContext` 读取身份验证键。

```typescript title="src/mastra/agents/support-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createTool } from '@mastra/core/tools'
import { getRequestUser } from '@mastra/core/utils'
import { z } from 'zod'

const accountTool = createTool({
  id: 'get-account',
  description: "Look up the signed-in user's account",
  inputSchema: z.object({}),
  execute: async (inputData, context) => {
    const user = getRequestUser(context?.requestContext)
    return { userId: user?.id, email: user?.email }
  },
})

export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: ({ user }) =>
    user
      ? `You are helping ${user.name ?? user.id}. Be personable.`
      : 'You are a helpful assistant.',
  model: ({ user }) =>
    user?.role === 'admin' ? '__GATEWAY_OPENAI_MODEL__' : '__GATEWAY_OPENAI_MODEL_MINI__',
  tools: ({ user }) => (user ? { accountTool } : {}),
})
```

请求未通过身份验证或未配置身份验证提供程序时，`user` 为 `undefined`。该值由 Mastra 服务器的身份验证中间件填充，因此经 `MCPServer` 处理的请求不会收到它。统一后的结构由提供程序的 `toMastraUser()` 方法生成；你可以[在自定义提供程序中覆写](/docs/auth/custom-auth-provider)。提供程序原始的用户对象仍可通过 `requestContext.get('mastra__user')` 获取。

### 动态指令 {/* #dynamic-instructions */}

通过异步函数提供 Agent 指令，即可在运行时确定 prompt。结合 `requestContext`，可以实现：

* **个性化**：根据用户属性、偏好或等级定制说明
* **本土化**：根据区域设置调整语气、语言或行为
* **A/B 测试**：提供不同的提示变体进行实验
- **外部 prompt 管理**：从注册服务获取 prompt，无须重新部署

```typescript title="src/mastra/agents/dynamic-agent.ts"
import { Agent } from '@mastra/core/agent'

export const dynamicAgent = new Agent({
  id: 'dynamic-agent',
  name: 'Dynamic Agent',
  instructions: async ({ requestContext }) => {
    const userTier = requestContext?.get('user-tier')
    const locale = requestContext?.get('locale')

    // Personalize based on user tier
    const basePrompt =
      userTier === 'enterprise'
        ? 'You are a premium support agent. Provide detailed, thorough responses with technical depth.'
        : 'You are a helpful assistant. Be concise and friendly.'

    // Localize behavior
    const localeInstructions = locale === 'ja' ? 'Respond in Japanese using formal keigo.' : ''

    return `${basePrompt} ${localeInstructions}`.trim()
  },
  model: '__GATEWAY_OPENAI_MODEL__',
})
```

#### 从提示注册表中获取 {/* #fetching-from-a-prompt-registry */}

如果组织使用 prompt registry 服务集中管理 prompt，可以在运行时获取指令。这样既能在不重新部署的情况下更新 prompt、试验不同版本，也能跟踪各 Agent 的 prompt 使用情况。

```typescript title="src/mastra/agents/registry-agent.ts"
import { Agent } from '@mastra/core/agent'

// Your prompt registry client
import { promptRegistry } from '../lib/prompt-registry'

export const registryAgent = new Agent({
  id: 'registry-agent',
  name: 'Registry Agent',
  instructions: async ({ requestContext }) => {
    const prompt = await promptRegistry.getPrompt({
      promptId: 'customer-support-agent',
      // Pass context for variant selection or tracking
      variant: requestContext?.get('experiment-variant'),
      userId: requestContext?.get('user-id'),
    })

    return prompt.content
  },
  model: '__GATEWAY_OPENAI_MODEL__',
})
```

完整的配置选项参见 [Agent](/reference/agents/agent)。

## 从 Workflow 步骤读取值 {/* #accessing-values-from-workflow-steps */}

可以从 Workflow 步骤的 `execute` 函数访问 `requestContext` 参数。该函数可以同步或异步执行。使用 `.get()` 从 `requestContext` 读取值。

```typescript title="src/mastra/workflows/weather-workflow.ts"
export type UserTier = {
  'user-tier': 'enterprise' | 'pro'
}

const stepOne = createStep({
  id: 'step-one',
  execute: async ({ requestContext }) => {
    const userTier = requestContext.get('user-tier') as UserTier['user-tier']

    if (userTier === 'enterprise') {
    }
  },
})
```

完整的配置选项参见 [createStep()](/reference/workflows/step)。

## 从 Tool 读取值 {/* #accessing-values-with-tools */}

可以从 Tool 的 `execute` 函数访问 `requestContext` 参数。该函数是 `async` 函数。使用 `.get()` 从 `requestContext` 读取值。

```typescript title="src/mastra/tools/weather-tool.ts"
import { createTool } from '@mastra/core/tools'

export type UserTier = {
  'user-tier': 'enterprise' | 'pro'
}

export const weatherTool = createTool({
  id: 'weather-tool',
  execute: async (inputData, context) => {
    const userTier = context?.requestContext?.get('user-tier') as UserTier['user-tier'] | undefined

    if (userTier === 'enterprise') {
    }
  },
})
```

完整的配置选项参见 [createTool()](/reference/tools/create-tool)。

## 保留键 {/* #reserved-keys */}

Mastra 保留特殊的上下文键供服务器读取。资源和线程键优先于客户端提供的值：当用户尝试访问不属于他们的资源时，服务器会验证所有权并返回 403 错误。

设置 `MASTRA_RESOURCE_ID_KEY` 最简便的方式是在身份验证配置中使用 `mapUserToResourceId` 回调：

```typescript oxfmt:false
auth: {
  authenticateToken: async token => verifyToken(token),
  mapUserToResourceId: user => user.id,
}
```

以这种方式派生资源 ID 后，客户端在 Agent generate 和 stream 请求体中可以省略 `memory.resource`。服务器派生的值会被采用，并始终优先于客户端提供的值。如果请求使用 memory，而请求体和请求上下文均未提供资源 ID，服务器会返回 400 错误。

您还可以在中间件中手动设置这些键：

```typescript
import { MASTRA_RESOURCE_ID_KEY, MASTRA_THREAD_ID_KEY } from '@mastra/core/request-context'

// In middleware: force memory operations to use authenticated user's ID
requestContext.set(MASTRA_RESOURCE_ID_KEY, user.id)

// In middleware: set validated thread ID
requestContext.set(MASTRA_THREAD_ID_KEY, threadId)
```

|关键|目的|
| - | - |
| `MASTRA_RESOURCE_ID_KEY` | 强制所有 memory 操作使用此资源 ID。服务器会验证访问的 thread 是否属于该资源，否则返回 403。 |
| `MASTRA_THREAD_ID_KEY` | 强制 thread 操作使用此 thread ID，覆盖客户端提供的值。向 Agent 调用传入 `memory.thread` 不会设置此键；如果依赖它（如 workspace resolver），须自行设置。Tool 也可通过 `context.agent.threadId` 读取当前运行的 thread。 |
| `MASTRA_SCOPES_KEY` | 将 Agent 运行所用的 [scopes](/docs/memory/overview#identify-memory-with-scopes) 设置为 `<type>:<value>` 字符串数组。它与每次调用的 `scopes` 组合：Agent 的 `scopes` 列表会追加到其中，而 `scopes` 函数会替换它们。若 `resource:` 或 `thread:` scope 与其他资源或 thread 值冲突，会返回 400 错误。 |
| `MASTRA_MESSAGE_AUTHOR_KEY` | 以 `{ id, name?, avatarUrl? }` 标识用户消息的发送者。Agent controller 会话将其持久化在 `content.metadata.signal.author`，并为兼容性镜像到 `providerMetadata.mastra.author`，以便多人共享的 thread 显示每条消息的作者。 |

服务器的所有权检查只读取 `MASTRA_RESOURCE_ID_KEY` 和 `MASTRA_THREAD_ID_KEY`。如果中间件通过 `MASTRA_SCOPES_KEY` 设置身份，并且你需要这些检查，还须设置 `MASTRA_RESOURCE_ID_KEY`：

```typescript
import {
  MASTRA_RESOURCE_ID_KEY,
  MASTRA_THREAD_ID_KEY,
  MASTRA_SCOPES_KEY,
} from '@mastra/core/request-context'

requestContext.set(MASTRA_SCOPES_KEY, [`org:${user.orgId}`, `resource:${user.id}`])
requestContext.set(MASTRA_RESOURCE_ID_KEY, user.id)
```

`thread:` scope 也是如此：它设置运行的 thread 身份，但只有 `MASTRA_THREAD_ID_KEY` 会触发服务器的 thread 检查。因此，中间件固定 thread 时须同时设置两者：

```typescript
requestContext.set(MASTRA_SCOPES_KEY, [`resource:${user.id}`, `thread:${threadId}`])
requestContext.set(MASTRA_RESOURCE_ID_KEY, user.id)
requestContext.set(MASTRA_THREAD_ID_KEY, threadId)
```

请求上下文和单次调用中的 `scopes` 需要已支持这些保留值的 `@mastra/server` 版本。旧版服务器会将请求体中的这些值直接传给 Agent；只要注册了其中一个值，Agent 就会抛出 `AGENT_SCOPES_SERVER_OUTDATED`，而不会使用它们。Agent 自身的 `scopes` 选项仍然有效。

这些键用于实现多租户应用中的用户隔离。用法参见[授权中间件](/docs/server/middleware#authorization-user-isolation)。

## TypeScript 支持 {/* #typescript-support */}

向 `RequestContext` 提供类型参数后，所有方法都会具有完整的类型信息：

```typescript
import { RequestContext } from '@mastra/core/request-context'

type MyContext = {
  userId: string
  maxTokens: number
  isPremium: boolean
}

const ctx = new RequestContext<MyContext>()

// set() enforces correct value types
ctx.set('userId', 'user-123') // ✓ valid
ctx.set('maxTokens', 4096) // ✓ valid
ctx.set('maxTokens', 'wrong') // ✗ TypeScript error: expected number

// get() returns the correct type automatically
const tokens = ctx.get('maxTokens') // inferred as number
const id = ctx.get('userId') // inferred as string

// keys() returns typed keys
for (const key of ctx.keys()) {
  // key is "userId" | "maxTokens" | "isPremium"
}

// entries() supports type narrowing
for (const [key, value] of ctx.entries()) {
  if (key === 'maxTokens') {
    // TypeScript knows value is number here
    console.log(value.toFixed(2))
  }
  if (key === 'userId') {
    // TypeScript knows value is string here
    console.log(value.toUpperCase())
  }
}
```

## 模式验证 {/* #schema-validation */}

使用 `requestContextSchema` 定义 [Standard JSON Schema](https://standardschema.dev/json-schema)（如 [Zod](https://zod.dev/)、[Valibot](https://valibot.dev/) 或 [ArkType](https://arktype.io/)），在运行时验证请求上下文的值。这样可以及早发现缺失或无效的值，提供清晰的错误信息，并在组件中推断类型。

### Agent schema 验证 {/* #agent-schema-validation */}

在 Agent 上定义 `requestContextSchema` 后，上下文会在 `generate()` 或 `stream()` 开始时验证。验证失败时，Agent 会在调用 LLM 之前抛出 `MastraError`。

```typescript title="src/mastra/agents/validated-agent.ts"
import { Agent } from '@mastra/core/agent'
import { z } from 'zod'

export const validatedAgent = new Agent({
  id: 'validated-agent',
  name: 'Validated Agent',
  requestContextSchema: z.object({
    userId: z.string(),
    apiKey: z.string(),
  }),
  instructions: ({ requestContext }) => {
    // Access all values as a typed object
    const { userId, apiKey } = requestContext.all
    // { userId: string; apiKey: string }

    // Or retrieve individual values with .get()
    const id = requestContext.get('userId')
    // string

    return `You are helping user ${userId}`
  },
  model: '__GATEWAY_OPENAI_MODEL__',
})
```

当验证失败时，错误包括Agent ID 以及有关失败字段的详细信息：

```text
Request context validation failed for agent 'validated-agent':
- apiKey: Required
```

### Tool schema 验证 {/* #tool-schema-validation */}

在 Tool 上定义 `requestContextSchema` 后，会在运行 `execute()` 前验证上下文。与 Agent 不同，Tool 会返回验证错误对象，而不是抛出异常：

```typescript title="src/mastra/tools/validated-tool.ts"
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

export const validatedTool = createTool({
  id: 'validated-tool',
  description: 'A tool that requires authenticated context',
  inputSchema: z.object({
    query: z.string(),
  }),
  requestContextSchema: z.object({
    userId: z.string(),
  }),
  execute: async (inputData, context) => {
    // Access all values as a typed object
    const { userId } = context.requestContext?.all ?? {}
    // { userId: string }

    // Or retrieve individual values with .get()
    const id = context.requestContext?.get('userId')
    // string | undefined

    return { result: `Processed for ${userId}` }
  },
})
```

当验证失败时，该Tool返回一个错误对象而不是抛出：

```json
{
  "error": true,
  "message": "Request context validation failed for validated-tool. Please fix the following errors and try again:\n- userId: Required\n\nProvided context: {}"
}
```

### Workflow schema 验证 {/* #workflow-schema-validation */}

在 Workflow 上定义 `requestContextSchema` 后，会在 `run.start()` 开始时验证上下文。如果验证失败，Workflow 会在任何步骤执行前抛出错误。

```typescript title="src/mastra/workflows/validated-workflow.ts"
import { createWorkflow, createStep } from '@mastra/core/workflows'
import { z } from 'zod'

// Define schema once and share between workflow and steps
const workflowContextSchema = z.object({
  tenantId: z.string(),
})

const step1 = createStep({
  id: 'step-1',
  inputSchema: z.object({ message: z.string() }),
  outputSchema: z.object({ result: z.string() }),
  // Add schema to step for type inference
  requestContextSchema: workflowContextSchema,
  execute: async ({ inputData, requestContext }) => {
    // Access all values as a typed object
    const { tenantId } = requestContext.all
    // { tenantId: string }

    // Or retrieve individual values with .get()
    const id = requestContext.get('tenantId')
    // string

    return { result: `Processed for tenant ${tenantId}` }
  },
})

export const validatedWorkflow = createWorkflow({
  id: 'validated-workflow',
  inputSchema: z.object({ message: z.string() }),
  outputSchema: z.object({ result: z.string() }),
  requestContextSchema: workflowContextSchema,
})
  .then(step1)
  .commit()
```

当验证失败时，Workflow会抛出错误：

```text
Request context validation failed for workflow 'validated-workflow':
- tenantId: Required
```

步骤也可以定义自己的 `requestContextSchema`，进行步骤级验证。步骤验证会在该步骤的 `execute()` 函数运行前进行。

### 验证行为 {/* #validation-behavior */}

| 组件 | 属性 | 验证时机 | 失败时 |
| - | - | - | - |
| Agent | `requestContextSchema` | `generate()` / `stream()` 开始时 | 抛出 `MastraError` |
| Tool | `requestContextSchema` | `execute()` 运行前 | 返回错误对象 |
| Workflow | `requestContextSchema` | `run.start()` 开始时 | 抛出 `Error` |
| Step | `requestContextSchema` | 步骤的 `execute()` 运行前 | 步骤失败并报错 |

### 最佳实践 {/* #best-practices */}

**与中间件保持一致**：在 schema 中定义与中间件设置的必填字段相同的字段，使中间件与组件之间的契约明确且可验证。

```typescript
// Middleware sets these fields
requestContext.set('userId', user.id)
requestContext.set('tenantId', tenant.id)

// Schema validates they exist
requestContextSchema: z.object({
  userId: z.string(),
  tenantId: z.string(),
})
```

**条件上下文使用可选字段**：对不一定存在的值使用 `.optional()`。

```typescript
requestContextSchema: z.object({
  userId: z.string(), // Always required
  experimentVariant: z.string().optional(), // May not be set
})
```

**处理 Tool 验证错误**：Tool 返回错误对象而不是抛出异常；如果 Tool 的执行至关重要，应在 Agent 或 Workflow 逻辑中检查错误。
