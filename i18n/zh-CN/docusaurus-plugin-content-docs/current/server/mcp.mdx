# 内置 MCP 服务器

Mastra 服务器通过 `/api/mcp` 向 [Model Context Protocol (MCP)](https://modelcontextprotocol.io/introduction) 客户端开放你的 Agent、Workflow 和 Tool。无需为此定义 `MCPServer`：注册到 `Mastra` 实例的每个 Agent、Workflow 和 Tool 都可使用，之后新增的 Agent 也会自动出现。

每个 MCP Tool 都是现有 HTTP 路由的轻量封装。调用会经过与 HTTP 请求相同的参数校验、身份验证、RBAC、FGA 和所有权检查，并使用相同的 `RequestContext`。MCP 客户端能执行的操作不会超出同一用户通过 HTTP API 可执行的范围。

内置服务器可让编程助手和其他 MCP 客户端操作你正在运行的 Mastra 应用。如果要通过自己的提示词和资源发布一组精选能力，请另行创建 [`MCPServer`](/docs/connections/mcp#expose-a-mastra-mcp-server)。

## 安装 {/* #installation */}

此端点使用 `@mastra/mcp`，它是 `@mastra/server` 声明的可选 peer dependency。在项目中安装该包即可启用内置服务器：

```bash npm2yarn
npm install @mastra/mcp@latest
```

未安装时，服务器的其他功能仍可正常工作；`/api/mcp` 会返回 HTTP 501 和提示安装该包的 JSON-RPC 错误。只有项目安装了 `@mastra/mcp`，`mastra build` 才会将它加入构建产物。

## 何时提供端点 {/* #when-its-served */}

| 环境 | 是否提供 `/api/mcp` |
| - | - |
| `mastra dev` | 是，即使没有配置身份验证也会提供。为防止 DNS 重绑定，带有外来 `Origin` 或 `Host` 标头的请求会被拒绝；隧道和局域网 IP 地址也会受此限制。如需从其他机器访问，请将 `server.host` 设为客户端连接时使用的主机名或 IP 地址。仅绑定 `0.0.0.0` 不会允许其他主机。 |
| 配置了 `server.auth` 的生产构建 | 是。每个请求都需要 bearer token。 |
| 未配置 `server.auth` 的生产构建 | 否，端点返回 404。 |

设置 `server.mcp.enabled` 可覆盖默认行为。`false` 会在所有环境关闭端点。`true` 则会在没有 `server.auth` 时仍提供端点，并记录警告，因为任何能访问服务器的人都能调用你的 Agent、Workflow 和 Tool。

## 连接客户端 {/* #connect-a-client */}

启动开发服务器，然后让客户端连接该端点。以 Claude Code 为例：

```bash
claude mcp add --transport http mastra http://localhost:4111/api/mcp
```

配置身份验证后，传入 bearer token：

```bash
claude mcp add --transport http mastra https://my-app.example.com/api/mcp \
  --header "Authorization: Bearer $MASTRA_TOKEN"
```

如需在命令行查看 Tool，请使用 [MCP Inspector](https://github.com/modelcontextprotocol/inspector)：

```bash
npx @modelcontextprotocol/inspector --cli http://localhost:4111/api/mcp \
  --transport http --header "Authorization: Bearer $MASTRA_TOKEN" --method tools/list
```

Cursor 和 VS Code 从 JSON 文件读取服务器配置。对于 Cursor，请将配置写入 `.cursor/mcp.json`：

```json title=".cursor/mcp.json"
{
  "mcpServers": {
    "mastra": {
      "url": "http://localhost:4111/api/mcp",
      "headers": { "Authorization": "Bearer <your-token>" }
    }
  }
}
```

对于 VS Code，则写入 `.vscode/mcp.json`：

```json title=".vscode/mcp.json"
{
  "servers": {
    "mastra": {
      "type": "http",
      "url": "http://localhost:4111/api/mcp",
      "headers": { "Authorization": "Bearer <your-token>" }
    }
  }
}
```

服务器未配置 `server.auth` 时，省略 `headers`。某些客户端只接受 URL，无法发送 `Authorization` 标头，例如 Claude 应用中的自定义连接器；它们需要 [OAuth 发现机制](#oauth-discovery)以及支持登录的身份提供商。

端点使用无状态 Streamable HTTP，同时支持 MCP `2026-07-28` 和当前客户端使用的 2025 年版本，因此不会在请求之间保留会话。

### 在 Studio 中 {/* #in-studio */}

Studio 的 **MCP Servers** 页面会在你自行注册的 MCP 服务器上方，以 **Mastra (built-in)** 展示内置服务器。页面显示端点 URL（包括自定义的 `server.mcp.path` 或 `apiPrefix`）、端点是否开放或受 `server.auth` 保护、提供的 Tool 集（不反映 `include` 和 `exclude` 的设置），以及可复制的 Claude Code、Cursor、VS Code 和 MCP Inspector 配置。配置中使用 `<your-token>` 占位符，请将其替换为自己的 bearer token。如果端点已关闭或未安装 `@mastra/mcp`，卡片会说明原因和解决方法。

端点 URL 根据 Studio 访问服务器时使用的地址生成。如果 MCP 客户端通过另一个公开 URL（例如经由代理）访问服务器，请在客户端配置中改用该 URL。使用 [OAuth 发现机制](#oauth-discovery)时，能够登录的客户端无需设置 `Authorization` 标头。

Studio 通过 `GET /api/mcp/builtin` 读取这些信息，该请求需要 `mcp:read` 权限。由于 Tool 列表取决于调用者的 token，Studio 不会列出服务器的 Tool，也不提供试用功能。请连接客户端查看你可用的 Tool。

## Tool {/* #tools */}

服务器按 Tool 集对 Tool 分组。本节介绍 `agents`、`workflows` 和 `tools`；其他 Tool 集见[记忆、可观测性与 Agent 构建器](#memory-observability-and-agent-builder)。操作类 Tool 以 ID 为参数访问 Agent 和 Workflow，因此无论新增多少个 Agent，Tool 列表的长度都不变。

各 Tool 的参数、路由和权限见[内置 MCP Tool 参考](/reference/server/builtin-mcp-tools)。

| Tool 集 | Tool | 对应的 HTTP 路由 |
| - | - | - |
|`agents` | `list_agents`, `get_agent`, `call_agent` | `GET /agents`, `GET /agents/:agentId`, `POST /agents/:agentId/generate` |
| `workflows` | `list_workflows`, `get_workflow`, `start_workflow`, `get_workflow_run`, `resume_workflow_run`, `cancel_workflow_run` | `GET /workflows`, `GET /workflows/:workflowId`, `POST /workflows/:workflowId/start-async`, `GET /workflows/:workflowId/runs/:runId`, `POST /workflows/:workflowId/resume-async`, `POST /workflows/:workflowId/runs/:runId/cancel` |
| `tools` | 每个已注册 Tool 对应一个 `tool_<id>` | `POST /tools/:toolId/execute` |

- 如果调用者可见的 Agent 或 Workflow 数量不超过 `enumLimit`（默认 25），`agentId` 和 `workflowId` 参数会列出允许使用的 ID。超过上限时，这些参数是普通字符串，客户端需调用 `list_agents` 或 `list_workflows` 查找 ID。
- 如果调用者可见的 Tool 数量超过 `enumLimit`，`tool_<id>` 会由 `list_tools`、`get_tool` 和 `call_tool` 取代。
- `call_agent` 返回回复文本和 `threadId`。再次传入 `threadId` 可在该 Agent 的记忆中继续对话。不传入 `threadId` 时会创建新线程，因此始终不传入的客户端每次调用都会留下一个线程。
- `start_workflow` 等待运行完成或暂停。暂停时返回 `runId` 和暂停数据，可用 `resume_workflow_run` 继续运行。
- 未设置 `description` 的 Agent 会得到通用描述，日志中也会出现警告。请添加描述，方便客户端选择合适的 Agent。

### 精选 Agent 和 Workflow {/* #featured-agents-and-workflows */}

将 Agent 和 Workflow 列入 `featured`，可分别为它们提供专用 Tool。精选 Workflow 的 Tool 直接采用该 Workflow 的输入 schema：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  // ...agents, workflows, tools
  server: {
    mcp: {
      featured: { agents: ['support-agent'], workflows: ['refund'] },
    },
  },
})
```

这会在操作类 Tool 之外增加 `agent_support-agent` 和 `workflow_refund`。

## 选择要公开的内容 {/* #choose-what-to-expose */}

使用 `include` 和 `exclude` 按 ID 选择要开放的能力。每项既匹配能力自身的 `id`，也匹配它在 `new Mastra({ ... })` 中注册时使用的键，因此 `deleteAccountTool` 和 `delete-account` 会选中同一个 Tool。`exclude` 的优先级高于 `include`。被排除的能力不会出现在 Tool 列表中，以任一名称调用都会返回未找到；向记忆 Tool 传入被排除 Agent 的 ID 也一样。可观测性 Tool 不受此过滤：其结果仍可能包含被排除能力的 trace、日志和评分。此选择仅影响 MCP，不改变 HTTP 路由。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  server: {
    mcp: {
      toolsets: ['agents', 'tools'],
      include: { agents: ['support-agent', 'billing-agent'] },
      exclude: { tools: ['delete-account'] },
    },
  },
})
```

设置 `readOnly: true` 后，只提供对应路由需要 `read` 权限的 Tool，例如 `list_agents` 和 `get_workflow_run`。

客户端可通过 `?toolsets=agents,tools` 或 `X-MCP-Toolsets` 标头，以及 `?readonly=1` 或 `X-MCP-Readonly` 标头，进一步缩小单个连接可用的 Tool 范围。这些设置只能移除 Tool，不能添加服务器配置原本不提供的 Tool。

## 身份验证和权限 {/* #authentication-and-permissions */}

此端点只接受 `Authorization: Bearer` 标头中的凭据，并由 `server.auth` 验证。会话 Cookie、`apiKey` 查询参数和 Studio 的身份验证配置均不适用，因此无法利用浏览器会话从其他网站访问该端点。其他路由仍沿用各自的身份验证行为。

配置 [RBAC](/docs/auth/overview) 后，访问 MCP 除了需要对应路由的权限，还需要以下两项权限：

- `mcp:read`：连接并列出 Tool。
- `mcp:execute`：查看和调用任何 Tool。没有此权限的调用者会得到空列表，即使其可通过 HTTP 执行相同操作。

每次调用还需要对应 HTTP 路由的权限，例如 `call_agent` 需要 `agents:execute`，`start_workflow` 需要 `workflows:execute`。默认 `viewer` 角色有 `mcp:read`，但没有 `mcp:execute`；`member`、`admin` 和 `owner` 两者都有。这两项权限也保护你注册的 `MCPServer` 实例的路由，因此获准使用自建 MCP 服务器的角色也能使用内置服务器。

Tool 列表会按调用者过滤。只有调用者能在 `GET /agents` 或 `GET /workflows` 中看到的 Agent 和 Workflow 才会出现，其中包括 [FGA](/docs/auth/fga) 读取权限检查。调用后会返回 403 的 Tool 会被隐藏。实际执行每次调用时还会重新检查权限，过期的列表无法绕过权限限制。

线程和运行的所有权规则与 HTTP API 相同：用户不能继续其他用户的线程，也不能恢复其他用户的 Workflow 运行。

传入的 bearer token 不会作为参数交给 Tool，也不会转发给其他服务器。Tool 接收的 `RequestContext` 与对应 HTTP 请求相同。

## 记忆、可观测性与 Agent 构建器 {/* #memory-observability-and-agent-builder */}

这些 Tool 集默认启用。服务器只有具备相应支持时才会提供对应 Tool；每个 Tool 都会调用其对应的 HTTP 路由，并执行相同的权限和所有权检查。

| Tool 集 | Tool | 提供条件 |
| - | - | - |
| `memory` | `list_threads`, `get_thread`, `list_messages`, `search_memory`, `get_memory_status`, `get_observations`, `create_thread`, `update_thread`, `clone_thread`, `save_messages` | Agent 有记忆功能，或已配置存储型 Agent |
| `observability` | `query_traces`, `aggregate_traces`, `query_spans`, `aggregate_spans`, `query_threads`, `get_trace_query_fields`, `get_trace_query_values`, `get_trace`, `get_span`, `get_trace_trajectory`, `list_logs`, `list_traces` | 存储系统具备可观测性域 |
| `observability_analytics` | `analyze_metrics`, `analyze_scores`, `analyze_feedback`, `list_metric_names`, `list_scores`, `list_feedback` | 存储系统具备可观测性域 |
| `stored_agents` | `list_available_models`, `list_stored_agents`, `get_stored_agent`, `create_stored_agent`, `update_stored_agent` | 已配置[编辑器](/docs/studio/editor)和 Agent 存储域 |

- 记忆 Tool 需要 `agentId` 和 `threadId`。如果 `server.auth` 通过 `mapUserToResourceId` 将用户映射到资源，`resourceId` 默认取调用者的资源 ID，且调用者不能读写其他资源的线程、消息或 Observational Memory。未配置该映射时，传入的 `resourceId` 会像在 HTTP API 中一样直接使用。
- 可观测性 Tool 取决于存储系统支持的能力。支持 trace 查询的存储系统（如 DuckDB）会提供 `query_traces` 等查询 Tool；不支持的则提供 `list_traces`。只有存储系统实现相应能力时，日志、指标、评分和反馈 Tool 才会出现。
- `get_trace` 返回精简 trace，包含每个 span 的 ID、父级、名称、类型、时间、状态和实体。调用 `get_span` 可获取单个 span 的输入、输出及属性。列表和 trace 结果限制在约 40,000 个字符以内。截断的结果会提示如何获取其余内容：缩小分页大小，或用返回的 `nextOffset` 调用 `get_trace`。如果单个条目仍过大（例如带有内联图片的消息），其较长的值会被截断并标记。`get_span` 会返回完整 span；`get_observations` 也会以同样方式截断过大的记录。
- `analyze_metrics`、`analyze_scores` 和 `analyze_feedback` 的 `op` 可取 `aggregate`、`breakdown`、`timeseries` 或 `percentiles`；各操作调用对应的 `/observability/<source>/<op>` 路由。
- `create_stored_agent` 和 `update_stored_agent` 默认会发布变更，因此可立即用 `call_agent` 调用 Agent。传入 `autoPublish: false` 可保留草稿。`call_agent` 的 `agentId` 参数只列出客户端获取 Tool 列表时已存在的 Agent，因此要调用新建 Agent，客户端必须重新获取 Tool 列表。

在只读模式下，查询和聚合 Tool 仍可使用，因为其路由只需要 `observability:read` 权限，即使它们使用 `POST`。记忆和存储型 Agent 的写入 Tool 会被移除。`get_observations` 仍可使用，但不提供 `waitForPending` 选项，因为等待操作会调用需要 `memory:write` 的路由；没有 `memory:write` 权限的调用者使用 `get_observations` 时也看不到该选项。

:::warning

可观测性数据不按调用者隔离。任何拥有 `observability:read` 权限的人都可通过 MCP 或 HTTP 读取所有用户的 trace、日志、评分和反馈。默认 `viewer` 角色通过 `*:read` 获得此权限。对于不应查看其他用户数据的角色，请移除其 `observability:read` 权限，或不提供可观测性 Tool 集：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  server: {
    mcp: { toolsets: ['agents', 'workflows', 'tools', 'memory', 'stored_agents'] },
  },
})
```

:::

### Agent 创建 Agent {/* #agents-creating-agents */}

`create_stored_agent` 允许 MCP 客户端创建可供其他客户端调用的 Agent，需要 `stored-agents:write` 权限。新 Agent 归创建者所有，默认设为私有。如果没有调用者身份（例如未配置 `server.auth`），Agent 就没有所有者，即使设置 `visibility: 'private'` 也会公开。其他用户不会在 `list_agents` 或 `list_stored_agents` 中看到私有 Agent；除非是管理员或按 ID 获得该 Agent 的访问授权，否则调用时会像通过 HTTP 一样得到“未找到”响应。设置 `visibility: 'public'` 可让所有用户调用。无论是否公开，只有所有者、管理员和按 ID 获得授权的用户可以编辑；没有所有者的 Agent 则可由任何拥有 `stored-agents:write` 权限的用户编辑。参见[存储型 Agent 的可见性](/docs/studio/editor#visibility)。

当 Agent 构建器限制可用模型时，MCP Tool 只接受以下位置的获准模型：Agent 运行所用模型的 `provider` 和 `name`（包括每个条件分支）、`defaultOptions` 中指定的模型（如 `structuredOutput.model`）、回退 `modelList` 中每个已启用项、记忆模型（Observational Memory 的 observer 和 reflector 模型及标题模型），以及处理器图中任意深度的每个输入和输出处理步骤的 `model`。如果配置会使用策略无法检查的默认模型，也会被拒绝，例如 `observationalMemory: true`、未指定 `model` 的 Observational Memory 配置、创建时省略记忆配置（Agent 构建器会用默认模型补入 Observational Memory），或 `moderation` 这类需要模型却未指定模型的处理器。请显式设置获准的 `model`。

存储型 Agent 的 `model` 只接受 `provider`、`name` 及 `temperature` 等模型设置；`modelId`、`providerId` 等其他键会被拒绝。如果无法加载 Agent 构建器的策略，Tool 会返回错误，不会在未经检查的情况下保存。`list_available_models` 会返回允许使用的模型。HTTP 路由不执行此检查，因此能直接调用 `POST /stored/agents` 的用户仍可保存任意模型。嵌入模型（`memory.embedder`）不在构建器的模型列表中，也不会检查。保存 Agent 时也不会检查 Tool 白名单，所以新建 Agent 可使用服务器提供的任意 Tool；这些 Tool 以调用该 Agent 的用户的权限运行。

Observational Memory 只有在线程达到 token 阈值后才开始观察，默认阈值为 30,000 个 token。做简短演示时，可降低 `observation.messageTokens`，让 Agent 从少量消息中学习。Observational Memory 在后台处理消息，因此调用 `call_agent` 后应立即调用 `get_observations`，并设置 `waitForPending: true`，等待处理完成（最多 30 秒）后再读取。

## OAuth 发现 {/* #oauth-discovery */}

配置 `server.auth` 后，端点会按照 [MCP 授权规范](https://modelcontextprotocol.io/specification/draft/basic/authorization)告知 MCP 客户端如何获取 token。没有有效 token 的请求会收到 `401`，其 `WWW-Authenticate` 标头指向端点的受保护资源元数据（[RFC 9728](https://datatracker.ietf.org/doc/html/rfc9728)）：

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://my-app.example.com/.well-known/oauth-protected-resource/api/mcp"
```

如果请求携带了未通过验证的 token（例如已过期），标头还会包含 `error="invalid_token"`。其他路由返回 `401` 时不带此标头。

元数据公开提供于 `/.well-known/oauth-protected-resource/api/mcp` 和 `/.well-known/oauth-protected-resource`，不位于 API 前缀之下：

```json
{
  "resource": "https://my-app.example.com/api/mcp",
  "authorization_servers": ["https://my-tenant.us.auth0.com/"],
  "bearer_methods_supported": ["header"]
}
```

客户端读取 `authorization_servers`，在身份提供商处完成 OAuth 流程，再携带访问 token 重试。Mastra 本身不充当授权服务器。客户端能否在未预先注册 OAuth 应用的情况下登录，取决于身份提供商是否支持动态客户端注册或客户端 ID 元数据文档。

Mastra 根据 `server.mcp.oauth` 和身份验证提供商填充元数据：

- `resource` 默认是从请求推导出的端点 URL。代理或负载均衡器后的请求可能带有内部主机名，因此应将 `server.mcp.oauth.resource` 设为公开 URL。该值必须是没有片段的绝对 `https` URL（`localhost` 可使用 `http`）。无效值会记录错误并关闭 OAuth 发现机制，但 token 受众仍会按该值检查，因此修复前 MCP 请求会被拒绝。
- 认证质询中的元数据 URL 使用 `resource` 的来源和服务器上的端点路径，例如 `/.well-known/oauth-protected-resource/api/mcp`。如果代理通过不同的公开路径提供端点，也必须将这个 well-known URL 转发给 Mastra。
- 如果提供商知道自己的签发者，`authorization_servers` 会从提供商获取（见下表）；否则请设置 `server.mcp.oauth.authorizationServers`。两者都没有时，该字段会省略，客户端需手动配置 token。
- 只有设置 `server.mcp.oauth.scopesSupported` 后，元数据才包含 `scopes_supported`。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { MastraAuthWorkos } from '@mastra/auth-workos'

export const mastra = new Mastra({
  server: {
    auth: new MastraAuthWorkos(),
    mcp: {
      oauth: {
        resource: 'https://my-app.example.com/api/mcp',
        authorizationServers: ['https://my-app.authkit.app'],
      },
    },
  },
})
```

### 代币受众 {/* #token-audience */}

设置 `server.mcp.oauth.resource` 后，端点还会检查 token 是否为其签发：token 的 `aud` 声明必须包含 `resource` 的值。为其他 API 签发的 token 会收到带有 `error="invalid_token"` 的 `401`，因此从其他服务泄露的 token 无法重放到此 MCP 端点。未设置 `resource` 时，与此前一样，身份验证提供商接受的任何 token 都可使用。此检查仅适用于 `/api/mcp`；其他路由仍接受为其他 API 签发的 token。比较是精确匹配：带尾随斜杠的 `https://my-app.example.com/api/mcp/` 不匹配 `https://my-app.example.com/api/mcp`。

请配置身份提供商为该受众签发 token，例如在 Auth0 中将 `resource` URL 注册为 API 标识符。Auth0 还会验证自身的 `audience` 选项（`AUTH0_AUDIENCE`），因此应将该选项设为 `resource` URL，或签发 `aud` 同时包含两个值的 token。

| Provider | 公布的授权服务器 | 是否对 `resource` 检查受众 |
| - | - | - |
| [`MastraJwtAuth`](/reference/auth/jwt) | `issuer` 选项 | 是 |
| [Auth0](/reference/auth/auth0) | `https://<domain>/` | 是 |
| [Okta](/reference/auth/okta) | `issuer` 选项 | 否。Okta 会按自身的 `audience` 选项检查 token，因此请将该选项设为 `resource` URL。 |
| [Clerk](/reference/auth/clerk) | 从可发布密钥得到的前端 API URL。OAuth 应用必须签发 JWT 访问 token（2026 年 1 月以来创建的应用默认如此）；不透明 token 会被拒绝。 | 否 |
| [Supabase](/reference/auth/supabase) | `<url>/auth/v1`。只有为 Supabase 项目启用 OAuth 2.1 服务器后，客户端才能在此登录。 | 否 |
| [`CompositeAuth`](/docs/auth/composite-auth) | 所有内部提供商的服务器 | 交由验证 token 的提供商处理 |
| WorkOS、Google、Neon、Firebase、Better Auth、自定义提供商 | 设置 `authorizationServers` | 否 |

设置 `resource` 后，如果提供商无法检查受众，Mastra 会在启动时记录警告，并接受该提供商为任意受众签发的 token。这使 API key 和其他不透明 token 仍可使用。如果要在 `/api/mcp` 拒绝这些凭据，请设置 `requireAudience: true`：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { CompositeAuth, SimpleAuth } from '@mastra/core/server'
import { MastraJwtAuth } from '@mastra/auth'

const jwtAuth = new MastraJwtAuth({
  jwksUri: 'https://auth.example.com/.well-known/jwks.json',
  issuer: 'https://auth.example.com/',
})
const apiKeyAuth = new SimpleAuth({ tokens: { [process.env.API_KEY!]: { id: 'ci' } } })

export const mastra = new Mastra({
  server: {
    auth: new CompositeAuth([jwtAuth, apiKeyAuth]),
    mcp: {
      oauth: { resource: 'https://my-app.example.com/api/mcp', requireAudience: true },
    },
  },
})
```

启用 `requireAudience` 后，由 `SimpleAuth` 等无法检查受众的提供商验证的请求，会在 `/api/mcp` 收到带 `error="invalid_token"` 的 `401`。在 `CompositeAuth` 中，只有由这类提供商接受的请求会被拒绝。其他路由仍接受这些请求。`requireAudience` 需要配合 `resource` 使用；没有 `resource` 时不会执行检查。

自定义提供商可实现 `verifyAudience()` 和 `getOAuthMetadata()` 以支持此机制；参见[自定义身份验证提供商](/docs/auth/custom-auth-provider)。

### 连接 OAuth 客户端 {/* #connect-an-oauth-client */}

如果身份提供商支持动态客户端注册，可不带 token 添加服务器；客户端会在首次使用时启动登录流程：

```bash
claude mcp add --transport http mastra https://my-app.example.com/api/mcp
```

否则，请从身份提供商获取面向 `resource` 受众的访问 token，并通过标头传入：

```bash
claude mcp add --transport http mastra https://my-app.example.com/api/mcp \
  --header "Authorization: Bearer $MASTRA_TOKEN"
```

端点目前不会返回带有 `error="insufficient_scope"` 的 `403`。没有 `mcp:read` 权限的调用者只会收到普通的 `403`，因为 Mastra 权限不是客户端可以请求的 OAuth scope。

## 局限性 {/* #limitations */}

- Workflow 在 MCP 请求中同步运行。长时间运行的 Workflow 受服务器请求超时限制。
- `Agent`、`Workflow` 和 Tool 构造函数目前不支持逐项关闭 MCP 暴露。请使用 `server.mcp.include` 和 `server.mcp.exclude`。
- 工作记忆、删除线程或存储型 Agent，以及 scorer 和 Workspace 管理功能均未开放。
