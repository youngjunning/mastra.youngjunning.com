# 部署到Mastra平台

[`mastra deploy`](/reference/cli/mastra#mastra-deploy)是将 Mastra 应用程序发布到的单个命令[马斯特拉平台](/docs/mastra-platform/overview).

一个命令可以构建您的项目并在部署之前对其进行验证，此外还可以在首次运行时创建平台项目和环境、部署、流式传输构建日志，并在部署提供流量后打印您的公共 URL。

```bash
mastra deploy
```

:::注意
此页面涵盖统一部署流程。早期的 split 命令，[`mastra server deploy`](/docs/mastra-platform/server) and [`mastra studio deploy`](/docs/mastra-platform/studio), still work but `mastra deploy`是推荐路径。
:::

## 开始之前 {/* #before-you-begin */}

你需要一个[Mastra application](/docs) and a [Mastra platform](https://projects.mastra.ai) account. If you're not authenticated, the CLI prompts you to log in on first use.

本地人`.env` file is optional. Environment variables stored on the platform are used as-is at deploy time, and managed resources like [hosted databases](/docs/mastra-platform/database) inject their own variables. Pass `--env-file` only when you want to layer local values on top.

## 您的第一次部署 {/* #your-first-deploy */}

<Steps>
  <StepItem>
    从您的项目目录中，运行：

    ```bash
    mastra deploy
    ```

    第一次运行时，CLI 会提示您创建平台项目（以您的名称命名）`package.json`) and the `production` environment. Accept the prompts, or pass `--yes` to accept defaults without confirmation.
  </StepItem>

  <StepItem>
    CLI 在每次部署之前都会运行预检检查。回退到本地文件路径（无法在平台的临时文件系统上生存）的存储通常会阻止部署：

    ```text
    file:./mastra.db will be used at runtime because TURSO_DATABASE_URL is not set
    ```

    CLI 不会出错，而是会为您内联修复它：

    ```text
    Preflight needs TURSO_DATABASE_URL for the production environment. Create a managed turso database now and attach it? (Y/n)
    ```

    接受提示，配置需要几秒钟的时间。数据库的连接变量会自动注入到您的部署中，因此您无需将它们复制到`.env` file. If you decline the prompt or use a non-interactive shell (CI, `--yes`), the CLI falls back to printing the exact command for you to run.

    ```bash
    mastra env db create production --kind turso
    ```

    环境蛞蝓 (`production` above) matches the environment the CLI would have deployed to. The `mastra env db create` command requires an environment argument in non-interactive shells when the project has more than one environment.

    Preflight 还会捕获指向本地计算机的数据库 URL。一个`.env` file with `DATABASE_URL=postgres://localhost:5432/myapp` works during development, but the deployed server can't reach your laptop. The CLI therefore warns and offers the same managed provisioning. When both Neon and Postgres are available for your organization, the CLI prompts you to pick between them (public serverless Neon, or VPC-isolated Postgres) instead of the usual yes/no. If you decline, the deploy continues with your value as-is; if you accept, the managed database's connection variables take precedence at deploy time while your local `.env` keeps working for development.

    :::注意
    如果预检报告硬编码的本地路径（`Build contains a host-local storage URL`), it can't offer the inline fix. Guard the path with an environment variable first so the file is only used during local development:

    ```ts title="src/mastra/index.ts"
    import { LibSQLStore } from '@mastra/libsql'

    new LibSQLStore({
      id: 'mastra-storage',
      // Uses the hosted database when deployed, a local file during development
      url: process.env.TURSO_DATABASE_URL ?? 'file:./mastra.db',
      authToken: process.env.TURSO_AUTH_TOKEN,
    })
    ```

    :::

    如果构建静态发现`backgroundTasks.enabled: true`, the CLI decides whether to run background tasks on a dedicated worker service or in-process inside the API server container:

    * 专门的worker服务需要Redis来协调。没有可用的`REDIS_URL` in the deploy env, background tasks run in-process.
    * 在 Redis 可用的情况下，当环境已有专用工作服务时，CLI 将使用专用工作服务，当您通过`--yes`, or when the deploy runs headless. Otherwise it asks whether to provision one.
    * 经过`--workers dedicated` or `--workers in-process` to skip the decision. `--workers dedicated` fails if `REDIS_URL` is missing.
    * 专用工作人员服务正在逐步推出，因此对于无法访问的组织，CLI 会忽略工作人员清单和进程内运行的后台任务，即使使用 Redis 和`--workers dedicated`.

    当选择专用工作人员服务时，部署工件包括工作人员清单，Mastra Cloud 从同一工件配置或更新工作人员服务。

    去除`backgroundTasks` or setting `enabled: false` in a later deploy removes the manifest and spins down the existing worker service. Values that can't be determined statically are omitted from the manifest display, but the worker process still reads the complete configuration from your bundled code.
  </StepItem>

  <StepItem>
    跑步`mastra deploy` again. Preflight passes, the build uploads, and the CLI streams build logs until the deploy is
    live. Expect the full build and deploy to take between 30 seconds and a few minutes. The success message prints only
    when the new version is serving traffic.
  </StepItem>

  <StepItem>
    通过 CLI 打印的 URL 验证您的部署。附加`/api/agents` to confirm it returns a JSON list of your agents.

    :::警告
    设置[authentication](/docs/auth/overview) before exposing your endpoints publicly.
    :::
  </StepItem>
</Steps>

在每次部署期间替换正在运行的服务器进程可能会中断新版本上线时仍在流式传输的Agent轮次，因为 Mastra 平台目前不允许您配置或依赖终止前保证的额外时间。不要依赖提高`server.drainTimeout` for turns that may outlast the default drain window. Use [durable agents](/docs/harness/durable-agents) with persistent storage and cache when turns must survive a deploy, or handle an interrupted stream in the client. The available strategies are documented in [graceful shutdown and rolling deploys](/docs/deployment/mastra-server#graceful-shutdown-and-rolling-deploys).

第一次部署写了一个`.mastra-project.json` file linking your directory to the platform project. Commit it so later deploys, CI runs, and [`mastra env`](/docs/mastra-platform/environments) commands target the same project without extra flags.

## 部署到另一个环境 {/* #deploy-to-another-environment */}

`mastra deploy`目标是`production` environment by default. Pass `--env` to target a different one. If the environment doesn't exist yet, the CLI offers to create it:

```bash
mastra deploy --env staging
```

每个环境都有一个单独的 URL 和环境变量。也可以有自己的[hosted database](/docs/mastra-platform/database).

看[Environments](/docs/mastra-platform/environments) for the full model.

## 选择地区 {/* #choose-a-region */}

当部署以交互方式创建环境时，从区域提示中选择美国或欧洲。要跳过提示，请通过`--region` with the `us` or `eu` shorthand:

```bash
mastra deploy --env production --region eu
```

创建环境时区域是固定的。附加到环境的数据库会自动放置在该环境的区域附近，并且Observability数据将路由到与环境驻留区域匹配的摄取区域。看[Regions](/docs/mastra-platform/regions) for the full list of supported regions and database placement, along with observability co-location.

## 飞行前检查 {/* #preflight-checks */}

预检会在部署上传之前验证构建的输出，并且仅标记您自己的代码中的问题：

* **本地存储路径**: 硬块。文件支持的存储（例如`file:./mastra.db`) is lost on every deploy. Preflight passes when the path is guarded by an environment variable that's set locally or stored on the platform, including values provided by a managed database:

  ```ts title="src/mastra/storage.ts"
  import { LibSQLStore } from '@mastra/libsql'

  export const storage = new LibSQLStore({
    id: 'mastra-storage',
    // Uses the hosted database when deployed, a local file during development
    url: process.env.TURSO_DATABASE_URL ?? 'file:./mastra.db',
    authToken: process.env.TURSO_AUTH_TOKEN,
  })
  ```

* **缺少环境变量**：针对您的代码读取但没有源提供的变量的警告。仅由库代码引用的变量被排除。

对预检块的建议响应是修复原因，通常通过附加托管数据库或将变量存储在平台上。`--skip-preflight` exists as an escape hatch but skips the checks that prevent broken deploys.

运行检查而不部署：

```bash
mastra lint --preflight
```

`mastra lint`只能看到你的本地环境文件。存储在平台上或由托管数据库注入的变量对其不可见，因此部署可以通过预检，而 lint 仍会报告错误。

## 环境变量 {/* #environment-variables */}

从三个来源部署解析环境变量：

* **托管变量**：由托管数据库等平台资源注入（例如`TURSO_DATABASE_URL`). The platform defines these, and you can't edit them.
* **存储变量**：通过仪表板保存在项目或环境中。在每次部署时按原样使用，无需本地文件。
* **本地环境文件**：部署层明确`--env-file` or the ambient `.env` and `.env.local` files on top.

```bash
mastra deploy --env staging --env-file .env.staging
```

要更改正在运行的服务上的变量而不重新部署，请在仪表板中更新它们并运行[`mastra env restart`](/reference/cli/mastra#mastra-env-restart).

## 私有 npm 包 {/* #private-npm-packages */}

依赖于私有注册表中的包的项目在部署期间使用标准安装它们`NPM_TOKEN` contract.

<Steps>
  <StepItem>
    将只读注册表令牌存储​​为`NPM_TOKEN` on the project or environment through the dashboard.
  </StepItem>

  <StepItem>
    承诺无代币`.npmrc` that points your scope at the registry and reads the token from the environment:

    ```ini title=".npmrc"
    @your-org:registry=https://npm.pkg.github.com
    //npm.pkg.github.com/:_authToken=${NPM_TOKEN}
    ```

    保留`${NPM_TOKEN}` reference literal. The package manager resolves it at install time, so the token itself is never written to your repository.
  </StepItem>

  <StepItem>
    像往常一样部署：

    ```bash
    mastra deploy
    ```
  </StepItem>
</Steps>

在单一存储库中，`.npmrc` in your project directory takes precedence over one at the repository root.

`NPM_TOKEN`在依赖项安装期间可用。 Mastra 从它流式传输的 Mastra 源构建日志中编辑其值。生成的 Dockerfile 将其作为构建参数接收。运行时映像不受令牌影响。`NPM_TOKEN` is also injected into the running service as a regular environment variable, so treat it as a secret your application can read.

没有私有注册表的项目`.npmrc` need no changes. When your `.npmrc` references `${NPM_TOKEN}`, set the variable or the dependency install fails.

## 项目决议 {/* #project-resolution */}

每个部署都按以下顺序解析其目标项目：

1. 这`MASTRA_PROJECT_ID` environment variable
2. 这`--project <name|slug|id>` flag
3. 这`.mastra-project.json` file in the current directory

在 CI 中，设置`MASTRA_PROJECT_ID` and `MASTRA_API_TOKEN` and pass `--yes`:

```bash
mastra deploy --env production --yes
```

## 从服务器和工作室部署迁移 {/* #migrating-from-server-and-studio-deploys */}

`mastra server deploy`和`mastra studio deploy` are deprecated. They'll be removed in the next major version. Once removed, both commands will fail and legacy-pipeline projects can't deploy a new build until they migrate.

现有部署的服务继续运行。这只会影响您发布新部署的能力。

### 这会影响谁 {/* #who-this-affects */}

如果满足以下任一条件，您就处于旧版管道中：

* 您上次部署的结果是`mastra server deploy` or `mastra studio deploy` and the deploy log printed a **Deprecated** banner.
* 您的项目最近成功的部署已使用`@mastra/core` older than `1.44`.
* 您的组织尚未选择加入环境部署。

部署日志是事实的来源：遗留管道在每次部署时都会打印一个弃用横幅。

### 迁移 {/* #migrate */}

<Steps>
  <StepItem>
    升级`@mastra/core` in your project. The environment pipeline calls `setStudio` on the built artifact, which requires `@mastra/core` `>= 1.44`.

    ```bash npm2yarn
    npm install @mastra/core@latest
    ```

    如果您要跳转多个次要版本，请将以下内容粘贴到编码Agent（Claude Code、Cursor 等）中，以捕获您实际使用的 API 中的重大更改：

    ```text
    Check whether this project is ready for the Mastra Platform environment pipeline.

    1. Find the installed version of `@mastra/core` (check package.json and the
       lockfile for the version that actually resolved, rather than only the range).
    2. If it's >= 1.44.0, tell me I'm good. No further action is needed.
    3. If it's < 1.44.0:
       a. Fetch the `@mastra/core` changelog from
          https://github.com/mastra-ai/mastra/blob/main/packages/core/CHANGELOG.md
          and read every entry between my installed version and the latest release.
       b. Scan my project (agents, workflows, tools, memory, storage, deployers,
          telemetry, anywhere `@mastra/core`, `@mastra/*`, or `mastra` is imported)
          and list every Mastra API surface I actually use.
       c. For each used API, cross-reference the changelog and produce a table of:
          API I use → breaking change → severity (breaks build / breaks runtime /
          behavior change / none).
       d. For each "breaks build" or "breaks runtime" row, implement the fix in my
          codebase. For "behavior change" rows, leave a comment at the call site
          explaining what changed so I can decide.
       e. Bump `@mastra/core` (and any `@mastra/*` peers) to the latest matching
          versions, then run typecheck and tests. Report anything still failing.
    4. Search my scripts, package.json, Dockerfiles, and CI config for
       `mastra server deploy` and `mastra studio deploy`. Replace each
       occurrence with `mastra deploy`. This is the unified command required
       by the environment pipeline.

    don't restructure my CI, provision new infra, or change my environment
    variable values. Change only the Mastra usage in my code and the deploy command
    itself.
    ```
  </StepItem>

  <StepItem>
    将脚本和 CI 中的 split 命令替换为统一命令：

    ```diff
    - mastra server deploy
    - mastra studio deploy
    + mastra deploy
    ```

    `mastra deploy`构建一次并为目标环境部署服务器和 Studio UI shell。最近的每一个都支持它`mastra` CLI; otherwise, upgrade with `npm install -g mastra@latest`.
  </StepItem>

  <StepItem>
    部署一次。您的项目会自动采用到环境管道中，并且`production` environment is created on
    first deploy. See [Environments](/docs/mastra-platform/environments) for the full model.
  </StepItem>

  <StepItem>
    将任何项目级环境变量移至需要它们的环境（在仪表板下）**Environments → \<env> → Variables**. See [Environment variables](/docs/mastra-platform/environments#environment-variables).
  </StepItem>
</Steps>

### 常问问题 {/* #faq */}

**我的部署失败`MASTRA_CORE_TOO_OLD`.**&#x73AF;境管道要求`@mastra/core` `>= 1.44`. Upgrade `@mastra/core` and redeploy.

**我的组织尚未选择加入。**&#x8054;系支持人员。在下一个主要版本发布之前，选择加入将是自动的。

**我可以回滚吗？**&#x662F;的。环境保留部署历史记录，您可以从仪表板重新部署任何先前成功的工件。
