# 部署到 Mastra 平台

[`mastra deploy`](/reference/cli/mastra#mastra-deploy) 是将 Mastra 应用发布到 [Mastra 平台](/docs/mastra-platform/overview)的统一命令。

这条命令会在部署前构建并验证项目。首次运行时还会创建平台项目和环境，随后执行部署、实时输出构建日志，并在部署开始接收流量后显示公开 URL。

```bash
mastra deploy
```

:::note
本文介绍统一部署流程。此前分开的 [`mastra server deploy`](/docs/mastra-platform/server) 和 [`mastra studio deploy`](/docs/mastra-platform/studio) 命令仍可使用，但推荐使用 `mastra deploy`。
:::

## 开始之前 {/* #before-you-begin */}

你需要一个 [Mastra 应用](/docs)和一个 [Mastra 平台](https://projects.mastra.ai)账号。若尚未认证，CLI 会在首次使用时提示登录。

本地 `.env` 文件是可选的。平台存储的环境变量在部署时会直接使用，[托管数据库](/docs/mastra-platform/database)等托管资源也会注入自身变量。只有需要叠加本地值时才传入 `--env-file`。

## 首次部署 {/* #your-first-deploy */}

<Steps>
  <StepItem>
    在项目目录中运行：

    ```bash
    mastra deploy
    ```

    首次运行时，CLI 会提示创建平台项目（以 `package.json` 中的名称命名）和 `production` 环境。按提示确认，或传入 `--yes`，无需确认即接受默认值。
  </StepItem>

  <StepItem>
    CLI 每次部署前都会运行预检。若存储会回退到本地文件路径（平台的临时文件系统不会保留该文件），通常会阻止部署：

    ```text
    file:./mastra.db will be used at runtime because TURSO_DATABASE_URL is not set
    ```

    CLI 不会直接报错退出，而是提供即时修复选项：

    ```text
    Preflight needs TURSO_DATABASE_URL for the production environment. Create a managed turso database now and attach it? (Y/n)
    ```

    接受提示后，资源配置只需几秒钟。数据库连接变量会自动注入部署，无需复制到 `.env` 文件。若拒绝提示，或使用非交互式 Shell（CI、`--yes`），CLI 会改为输出准确的待执行命令。

    ```bash
    mastra env db create production --kind turso
    ```

    上例的环境标识 `production` 与 CLI 原本要部署的环境一致。如果项目有多个环境，在非交互式 Shell 中执行 `mastra env db create` 时必须传入环境参数。

    预检也会发现指向本机的数据库 URL。包含 `DATABASE_URL=postgres://localhost:5432/myapp` 的 `.env` 文件可用于开发，但部署后的服务器无法访问你的电脑。CLI 因此会发出警告，并提供同样的托管资源创建选项。如果组织同时提供 Neon 和 Postgres，CLI 会让你在公开的 Serverless Neon 与 VPC 隔离的 Postgres 之间选择，而非询问是或否。若拒绝，部署会沿用原值；若接受，托管数据库的连接变量在部署时优先，本地 `.env` 仍可供开发使用。

    :::note
    如果预检报告硬编码的本地路径（`Build contains a host-local storage URL`），就无法提供即时修复。请先用环境变量保护该路径，使文件仅用于本地开发：

    ```ts title="src/mastra/index.ts"
    import { LibSQLStore } from '@mastra/libsql'

    new LibSQLStore({
      id: 'mastra-storage',
      // Uses the hosted database when deployed, a local file during development
      url: process.env.TURSO_DATABASE_URL ?? 'file:./mastra.db',
      authToken: process.env.TURSO_AUTH_TOKEN,
    })
    ```

    :::

    如果构建静态检测到 `backgroundTasks.enabled: true`，CLI 会决定让后台任务运行在专用 Worker 服务上，还是运行在 API 服务器容器的进程内：

    - 专用 Worker 服务需要 Redis 协调。如果部署环境中没有可用的 `REDIS_URL`，后台任务会在进程内运行。
    - Redis 可用时，若环境已有专用 Worker 服务、传入 `--yes`，或以无交互方式部署，CLI 会使用专用 Worker 服务；否则会询问是否创建。
    - 传入 `--workers dedicated` 或 `--workers in-process` 可跳过选择。缺少 `REDIS_URL` 时，`--workers dedicated` 会失败。
    - 专用 Worker 服务正在逐步推出。尚未开放此功能的组织即使有 Redis 且传入 `--workers dedicated`，CLI 也会省略 Worker 清单，后台任务改为在进程内运行。

    选择专用 Worker 服务后，部署文件会包含 Worker 清单；Mastra Cloud 会依据同一文件创建或更新 Worker 服务。

    后续部署中移除 `backgroundTasks` 或设置 `enabled: false`，会移除清单并停止现有 Worker 服务。无法静态确定的值不会显示在清单中，但 Worker 进程仍会读取打包代码中的完整配置。
  </StepItem>

  <StepItem>
    再次运行 `mastra deploy`。预检通过后，构建产物会上传，CLI 会持续输出构建日志，直到部署开始
    接收流量。整个构建和部署通常需要 30 秒到几分钟。只有新版本开始接收流量时，
    才会显示成功消息。
  </StepItem>

  <StepItem>
    使用 CLI 输出的 URL 验证部署。在末尾追加 `/api/agents`，确认它返回 Agent 的 JSON 列表。

    :::warning
    公开端点前，请先配置[身份认证](/docs/auth/overview)。
    :::
  </StepItem>
</Steps>

每次部署替换正在运行的服务器进程时，新版本上线可能打断仍在流式输出的 Agent 调用，因为 Mastra 平台目前不支持配置或依赖可靠的终止前额外等待时间。对于可能超过默认排空窗口的调用，不要依赖调高的 `server.drainTimeout`。如果调用必须跨部署存活，请使用带持久化存储和缓存的[持久 Agent](/docs/harness/durable-agents)，或在客户端处理流中断。可用策略见[优雅关闭与滚动部署](/docs/deployment/mastra-server#graceful-shutdown-and-rolling-deploys)。

首次部署会写入 `.mastra-project.json`，将当前目录关联到平台项目。请将其提交，以便后续部署、CI 运行和 [`mastra env`](/docs/mastra-platform/environments) 命令无需额外参数即可指向同一项目。

## 部署到另一个环境 {/* #deploy-to-another-environment */}

`mastra deploy` 默认部署到 `production` 环境。传入 `--env` 可选择其他环境；如果该环境尚不存在，CLI 会提供创建选项：

```bash
mastra deploy --env staging
```

每个环境都有独立 URL 和环境变量，也可以拥有自己的[托管数据库](/docs/mastra-platform/database)。

完整说明请参阅[环境](/docs/mastra-platform/environments)。

## 选择地区 {/* #choose-a-region */}

交互式创建环境时，可在区域提示中选择美国或欧洲。若要跳过提示，请传入 `--region`，值为 `us` 或 `eu`：

```bash
mastra deploy --env production --region eu
```

环境创建后，区域不可更改。关联数据库会自动部署在该环境区域附近；可观测性数据则会路由到与环境数据驻留区域匹配的摄取区域。支持的区域、数据库位置及可观测性数据共址详情请参阅[区域](/docs/mastra-platform/regions)。

## 部署前检查 {/* #preflight-checks */}

预检会在上传部署文件前验证构建产物，且只报告你自己代码中的问题：

- **本地存储路径**：属于硬性阻断。基于文件的存储（例如 `file:./mastra.db`）在每次部署后都会丢失。若该路径受环境变量保护，且变量已在本地设置或存储于平台（包括托管数据库提供的值），预检就会通过：

  ```ts title="src/mastra/storage.ts"
  import { LibSQLStore } from '@mastra/libsql'

  export const storage = new LibSQLStore({
    id: 'mastra-storage',
    // Uses the hosted database when deployed, a local file during development
    url: process.env.TURSO_DATABASE_URL ?? 'file:./mastra.db',
    authToken: process.env.TURSO_AUTH_TOKEN,
  })
  ```

- **缺少环境变量**：如果代码读取了某个变量，但没有任何来源提供该值，则发出警告。仅由库代码引用的变量不计入。

预检阻断时，建议修复根因，通常是关联托管数据库或在平台存储变量。`--skip-preflight` 可作为应急选项，但会跳过用于防止故障部署的检查。

只运行检查、不执行部署：

```bash
mastra lint --preflight
```

`mastra lint` 只读取本地环境文件，看不到平台存储或托管数据库注入的变量。因此，即使 lint 报错，部署预检仍可能通过。

## 环境变量 {/* #environment-variables */}

部署时从以下三个来源解析环境变量：

- **托管变量**：由托管数据库等平台资源注入（例如 `TURSO_DATABASE_URL`）。这些变量由平台定义，不能编辑。
- **已存储变量**：通过控制台保存在项目或环境中。每次部署直接使用，无需本地文件。
- **本地环境文件**：部署会在上述值之上叠加显式 `--env-file` 或当前目录的 `.env`、`.env.local` 文件。

```bash
mastra deploy --env staging --env-file .env.staging
```

若要在不重新部署的情况下修改正在运行服务的变量，请在控制台更新变量，并运行 [`mastra env restart`](/reference/cli/mastra#mastra-env-restart)。

## 私有 npm 包 {/* #private-npm-packages */}

依赖私有注册表软件包的项目，会在部署期间按标准 `NPM_TOKEN` 约定安装依赖。

<Steps>
  <StepItem>
    通过控制台将只读注册表 Token 以 `NPM_TOKEN` 的名称存储在项目或环境中。
  </StepItem>

  <StepItem>
    提交不含 Token 的 `.npmrc`，将你的命名空间指向注册表，并从环境读取 Token：

    ```ini title=".npmrc"
    @your-org:registry=https://npm.pkg.github.com
    //npm.pkg.github.com/:_authToken=${NPM_TOKEN}
    ```

    请原样保留 `${NPM_TOKEN}` 引用。包管理器会在安装时解析它，因此 Token 本身不会写入仓库。
  </StepItem>

  <StepItem>
    按常规方式部署：

    ```bash
    mastra deploy
    ```
  </StepItem>
</Steps>

在 monorepo 中，项目目录内的 `.npmrc` 优先于仓库根目录的同名文件。

安装依赖期间可使用 `NPM_TOKEN`。Mastra 会从实时输出的源码构建日志中遮蔽其值。生成的 Dockerfile 会通过构建参数接收它；运行时镜像不包含该 Token。`NPM_TOKEN` 也会作为普通环境变量注入运行中的服务，因此应将其视为应用可读取的密钥。

没有私有注册表 `.npmrc` 的项目无需修改。如果 `.npmrc` 引用了 `${NPM_TOKEN}`，必须设置该变量，否则依赖安装会失败。

## 确定目标项目 {/* #project-resolution */}

每次部署按以下顺序确定目标项目：

1. 环境变量 `MASTRA_PROJECT_ID`
1. `--project <name|slug|id>` 参数
1. 当前目录中的 `.mastra-project.json` 文件

在 CI 中，设置 `MASTRA_PROJECT_ID` 和 `MASTRA_API_TOKEN`，并传入 `--yes`：

```bash
mastra deploy --env production --yes
```

## 从 Server 与 Studio 部署迁移 {/* #migrating-from-server-and-studio-deploys */}

`mastra server deploy` 和 `mastra studio deploy` 已弃用，将在下一个主版本移除。移除后，这两个命令都会失败，使用旧版流水线的项目在迁移前无法部署新构建。

现有服务会继续运行。受影响的只有发布新部署的能力。

### 这会影响谁 {/* #who-this-affects */}

符合以下任一条件，就表示你仍在使用旧版部署流程：

- 上次使用 `mastra server deploy` 或 `mastra studio deploy` 部署，且部署日志显示 **Deprecated** 横幅。
- 项目最近一次成功部署使用的 `@mastra/core` 版本低于 `1.44`。
- 组织尚未获准使用环境部署。

部署日志是判断依据：旧版部署流程每次部署都会显示弃用横幅。

### 迁移 {/* #migrate */}

<Steps>
  <StepItem>
    升级项目中的 `@mastra/core`。环境部署流程会对构建产物调用 `setStudio`，因此需要 `@mastra/core` `>= 1.44`。

    ```bash npm2yarn
    npm install @mastra/core@latest
    ```

    若跨越多个次版本升级，可将下面的提示词交给编码 Agent（如 Claude Code、Cursor），找出项目实际使用的 API 中可能存在的破坏性变更：

    ```text
    Check whether this project is ready for the Mastra Platform environment pipeline.

    1. Find the installed version of `@mastra/core` (check package.json and the
       lockfile for the version that actually resolved, rather than only the range).
    2. If it's >= 1.44.0, tell me I'm good. No further action is needed.
    3. If it's < 1.44.0:
       a. Fetch the `@mastra/core` changelog from
          https://github.com/mastra-ai/mastra/blob/main/packages/core/CHANGELOG.md
          and read every entry between my installed version and the latest release.
       b. Scan my project (agents, workflows, tools, memory, storage, deployers,
          telemetry, anywhere `@mastra/core`, `@mastra/*`, or `mastra` is imported)
          and list every Mastra API surface I actually use.
       c. For each used API, cross-reference the changelog and produce a table of:
          API I use → breaking change → severity (breaks build / breaks runtime /
          behavior change / none).
       d. For each "breaks build" or "breaks runtime" row, implement the fix in my
          codebase. For "behavior change" rows, leave a comment at the call site
          explaining what changed so I can decide.
       e. Bump `@mastra/core` (and any `@mastra/*` peers) to the latest matching
          versions, then run typecheck and tests. Report anything still failing.
    4. Search my scripts, package.json, Dockerfiles, and CI config for
       `mastra server deploy` and `mastra studio deploy`. Replace each
       occurrence with `mastra deploy`. This is the unified command required
       by the environment pipeline.

    don't restructure my CI, provision new infra, or change my environment
    variable values. Change only the Mastra usage in my code and the deploy command
    itself.
    ```
  </StepItem>

  <StepItem>
    将脚本和 CI 中原先分开的命令替换为统一命令：

    ```diff
    - mastra server deploy
    - mastra studio deploy
    + mastra deploy
    ```

    `mastra deploy` 只构建一次，并为目标环境同时部署服务器与 Studio UI 外壳。近期版本的 `mastra` CLI 均支持该命令；否则请运行 `npm install -g mastra@latest` 升级。
  </StepItem>

  <StepItem>
    部署一次。项目会自动采用环境部署流程，并在首次部署时创建 `production` 环境。完整说明请参阅
    [环境](/docs/mastra-platform/environments)。
  </StepItem>

  <StepItem>
    在控制台的 **Environments → \<env> → Variables** 下，将项目级环境变量移到需要它们的环境。参见[环境变量](/docs/mastra-platform/environments#environment-variables)。
  </StepItem>
</Steps>

### 常问问题 {/* #faq */}

**部署因 `MASTRA_CORE_TOO_OLD` 失败。** 环境部署流程要求 `@mastra/core` `>= 1.44`。请升级 `@mastra/core` 并重新部署。

**我的组织还未获准使用。** 请联系支持团队。下一个主版本发布前将自动开放。

**可以回滚吗？** 可以。环境会保留部署历史，你可以在控制台重新部署任何此前成功的构建产物。
