# 警报

当部署失败、正在运行的服务停止或停止响应或者组织使用量超过计划阈值时，警报会通知您的团队。您可以在组织级别配置警报，然后选择每个警报涵盖的项目和环境。

组织管理员可以创建和管理警报。其他组织角色对警报设置具有只读访问权限。

打开 [Mastra Platform 控制台](https://projects.mastra.ai)，进入组织设置，然后选择 **Alerts**。页面包含三个标签页：

* **警报**列出每个警报及其范围、目的地、状态以及启用或暂停开关。
* **目的地**列出了可以接收通知的 Slack 频道、Discord 频道、Microsoft Teams 频道、电子邮件组、Webhook 终结点、PagerDuty 服务和 Incident.io 警报源。
* **活动**显示事件以及与之相关的通知尝试。

## 添加目的地 {/* #add-a-destination */}

目的地定义了 Mastra 发送通知的位置。创建警报之前至少添加一个目的地。

|目的地 |配置|
| - | - |
| **Slack** | 连接 Slack Workspace 并选择一个或多个频道。Mastra 会为每个选中的频道分别创建目的地。 |
| **Discord** | 输入 Discord 频道的 Webhook URL。参见[向 Discord 发送警报](#send-alerts-to-discord)。 |
| **Microsoft Teams** | 输入向频道发帖的 Teams Workflow URL。参见[向 Microsoft Teams 发送警报](#send-alerts-to-microsoft-teams)。 |
| **Email** | 选择组织角色、单个成员，或最多 10 个邮箱地址。组织成员变更时，按角色设置的收件人组会随之更新。 |
| **Webhook**|输入 HTTPS 端点。 Mastra 对每个请求进行签名，并在创建目的地后显示签名密钥。 |
| **PagerDuty** | 输入 PagerDuty Events API v2 集成的 Integration key。参见[向 PagerDuty 发送警报](#send-alerts-to-pagerduty)。 |
| **Incident.io** | 输入 incident.io HTTP 警报源的配置 ID 和 Token。参见[向 incident.io 发送警报](#send-alerts-to-incidentio)。 |

<Steps>
  <StepItem>
    在 **Destinations** 标签页中选择 **Add destination**。
  </StepItem>

  <StepItem>
    选择 **Slack**、**Discord**、**Microsoft Teams**、**Email**、**Webhook**、**PagerDuty** 或 **Incident.io**，然后输入目的地名称。
  </StepItem>

  <StepItem>
    配置选定的目的地：

    - 对于 Slack，连接或选择 Workspace，并指定接收警报的频道。Mastra Alerts 应用会自动加入公开频道；选择私有频道前，请先邀请 `@Mastra Alerts`。
    * 对于 Discord，请输入频道的 Webhook URL。
    * 对于 Microsoft Teams，输入Workflow的 Webhook URL。
    - 对于邮件，选择 **All organization members**、一个或多个角色、单个成员或外部邮箱地址。
    - 对于 Webhook，输入以 `https://` 开头的端点地址。
    - 对于 PagerDuty，输入 **Integration key**。
    - 对于 incident.io，输入 **Alert source config ID** 和 **Token**。
  </StepItem>

  <StepItem>
    选择 **Create destination**。如果是 Webhook 目的地，请在关闭页面前复制签名密钥；之后无法再次查看。
  </StepItem>
</Steps>

目标表单根据所选类型而变化。 Slack 目标需要一个Workspace和至少一个通道。 Discord 和 Microsoft Teams 目标需要 Webhook URL。电子邮件目标需要至少一个收件人，该收件人可以是组织角色、成员或外部地址。 Webhook 目标需要 HTTPS 端点。 PagerDuty 和 Incident.io 目标需要来自其集成的凭据。每个目的地还需要一个在警报配置和活动历史记录中标识它的名称。

使用目标的操作菜单发送测试通知。您还可以编辑、暂停或删除目的地。暂停目的地会停止通知，但不会将其从现有警报中删除。

对于 Webhook 目的地，**Rotate secret** 会立即替换当前签名密钥。再次发送警报前，请更新接收端点使用的密钥。

Discord 和 Microsoft Teams 的 Webhook URL 自带凭据，因此 Mastra 会加密存储，并在创建目的地后只显示末尾四个字符。若要更换 URL，请编辑目的地并粘贴新 URL；留空则保留已存储的 URL。

## 创建警报 {/* #create-an-alert */}

警报结合了触发器、范围、目的地和重复警报节奏。

<Steps>
  <StepItem>
    在 **Alerts** 标签页中选择 **Create Alert**。
  </StepItem>

  <StepItem>
    输入警报名称。如果希望立即开始监控，请保持 **Enabled** 开启。
  </StepItem>

  <StepItem>
    选择一个或多个触发器：

    * **部署失败**：构建或部署未达到运行状态。
    * **服务崩溃**：正在运行的服务耗尽其重新启动策略并停止。
    * **服务内存不足**：服务在内存不足后停止。
    * **服务不可达**：已部署的服务连续 3 次运行状况检查失败。
    - **Usage threshold crossed**：组织用量超过套餐阈值或达到上限。此触发条件作用于整个组织，因此范围必须设为 **All projects**。
  </StepItem>

  <StepItem>
    将警报范围设为 **All projects** 或 **Specific projects**。选择特定项目后，可以进一步限定到单个环境。不选择环境则包含该项目的所有环境。
  </StepItem>

  <StepItem>
    选择一个或多个目的地。您可以添加或编辑目的地，而无需离开警报设置。
  </StepItem>

  <StepItem>
    在 **Repeat alerts** 下选择 Mastra 对同一事件重复发送警报的频率：每次事件、每 5 分钟、每 15 分钟或每小时。首次通知、恢复通知和严重程度升高时的通知会立即发送。
  </StepItem>

  <StepItem>
    选择**Create Alert**.
  </StepItem>
</Steps>

警报表单将设置分为 **Name**、**Trigger**、**Scope** 和 **Destinations**。选定的目的地和重复间隔适用于该警报涵盖的所有触发条件和项目。

## 管理警报 {/* #manage-alerts */}

**Alerts** 标签页显示每条警报的范围、目的地和当前状态。使用开关暂停或启用警报。

打开警报的操作菜单可以：

* **编辑**它的触发器、范围、目的地、节奏或名称。
* **测试**分配给警报的每个目的地。
* **删除**警报。现有事件和交付历史记录仍然可用。

## 查看警报活动 {/* #review-alert-activity */}

**Activity** 标签页按事件汇总通知尝试。条件持续存在时，事件保持 **Open**；服务或部署恢复后变为 **Resolved**。用量阈值事件例外，不会自动解决。

展开事件可查看发送到各目的地的通知。事件行显示发生时间、事件类型、项目或环境范围及当前状态；下方的发送记录显示每次通知尝试的触发条件、目的地和发送状态。发送状态包括 **Scheduled**、**Sent**、**Suppressed**、**Retrying**、**Exhausted** 和 **Config error**。活动过滤器可显示全部活动、仅事件或仅发送尝试。

## 向 Discord 发送警报 {/* #send-alerts-to-discord */}

Discord 目的地通过 Webhook 向频道发送嵌入消息。事件触发时发送红色嵌入消息；恢复时另发一条绿色的 **Resolved** 嵌入消息。Discord Webhook 无法更新旧消息，因此恢复通知是新消息，而非编辑旧消息。

<Steps>
  <StepItem>
    在 Discord 中打开接收警报的频道，依次选择 **Edit Channel**、**Integrations**、**Webhooks** 和 **New Webhook**，然后复制 Webhook URL。参见 Discord 文档中的 [Intro to Webhooks](https://support.discord.com/hc/en-us/articles/228383668-Intro-to-Webhooks)。
  </StepItem>

  <StepItem>
    在 Mastra 中添加目的地，选择 **Discord**，并将 URL 粘贴到 **Webhook URL**。URL 格式必须为 `https://discord.com/api/webhooks/<id>/<token>`。
  </StepItem>

  <StepItem>
    从目标的操作菜单发送测试通知。
  </StepItem>
</Steps>

嵌入消息的标题显示事件和项目，并链接到部署日志；若事件包含环境、分支和错误代码，这些信息会与错误摘录一起显示。如果 Discord 拒绝 Webhook URL，发送状态会显示 **Config error**。

## 向 Microsoft Teams 发送警报 {/* #send-alerts-to-microsoft-teams */}

Microsoft Teams 目的地通过 Teams Workflow 向频道发送 Adaptive Card。事件触发时发送红色卡片；恢复时另发一张绿色 **Resolved** 卡片。

<Steps>
  <StepItem>
    在 Teams 中打开接收警报的频道，依次选择 **More options**、**Workflows**，再选用 **Send webhook alerts to a channel** 模板。选择团队和频道，创建 Workflow，然后复制其 URL。参见 Microsoft 文档中的 [Create incoming webhooks with Workflows](https://support.microsoft.com/en-us/office/create-incoming-webhooks-with-workflows-for-microsoft-teams-8ae491c7-0394-4861-ba59-055e33f75498)。
  </StepItem>

  <StepItem>
    在 Mastra 中添加目的地，选择 **Microsoft Teams**，并将 URL 粘贴到 **Webhook URL**。
  </StepItem>

  <StepItem>
    从目标的操作菜单发送测试通知。
  </StepItem>
</Steps>

Microsoft 已停用旧版 Office 365 Connector，因此请使用 Teams Workflow，而非旧的 **Incoming Webhook** Connector。对于尚未迁移的租户，Mastra 仍接受旧版 `webhook.office.com` URL。

该卡在其标题中显示事件和项目，后面是环境、分支和错误代码（当事件包含这些代码时）、错误摘录以及用于打开部署日志的按钮。如果 Teams 拒绝Workflow URL，则交付显示**Config error**.

## 向 PagerDuty 发送警报 {/* #send-alerts-to-pagerduty */}

PagerDuty 目的地会将事件发送到 PagerDuty Events API v2。每个 Mastra 事件会创建一个 PagerDuty 事件，并在 Mastra 事件解决时由 PagerDuty 将其解决。

<Steps>
  <StepItem>
    在 PagerDuty 中打开接收警报的服务，在 **Integrations** 标签页添加 **Events API V2** 集成，并复制其 **Integration Key**。参见 PagerDuty 文档的 [Services and integrations](https://support.pagerduty.com/main/docs/services-and-integrations)。
  </StepItem>

  <StepItem>
    在 Mastra 中添加目的地，选择 **PagerDuty**，并将密钥粘贴到 **Integration key**。
  </StepItem>

  <StepItem>
    从目的地的操作菜单发送测试通知。测试会在 PagerDuty 中创建一个严重程度为 `info` 的事件；请在 PagerDuty 中将其解决。
  </StepItem>
</Steps>

Mastra 将其通知映射到 PagerDuty 事件，如下所示：

| PagerDuty 字段 |价值|
| - | - |
| `event_action` | 新通知或重复通知为 `trigger`，恢复通知为 `resolve` |
| `dedup_key` | Mastra 事件 ID。同一事件的重复通知会更新同一个 PagerDuty 事件 |
| `payload.summary` | 单行描述，例如 `Deploy failed on support-agent (production): Build failed` |
| `payload.severity` | Mastra 严重程度：`critical`、`error`、`warning` 或 `info` |
| `payload.source` | `mastra:<project>/<environment>` |
| `payload.custom_details` | [Webhook Payload](#webhook-payload) 中描述的事件数据 |

在 PagerDuty 中执行确认或解决等操作，不会更新 Mastra 事件。如果 PagerDuty 拒绝 Integration key，发送状态会显示 **Config error**。

## 向 incident.io 发送警报 {/* #send-alerts-to-incidentio */}

incident.io 目的地将警报事件发送到 incident.io HTTP 警报源。每个 Mastra 事件会在 incident.io 中创建一条警报；Mastra 事件解决时，该警报也会解决。

<Steps>
  <StepItem>
    在 incident.io 中创建来源类型为 **Default** 的 HTTP 警报源。Mastra 使用 incident.io 警报事件格式发送数据，因此无需自定义转换。参见 incident.io 文档中的 [Create an alert event](https://docs.incident.io/api-reference/alert-events-v2/create)。
  </StepItem>

  <StepItem>
    从来源的 Authorization Header 复制警报源配置 ID 和 Bearer Token。ID 是警报事件 URL `https://api.incident.io/v2/alert_events/http/<alert-source-config-id>` 的最后一段。
  </StepItem>

  <StepItem>
    在 Mastra 中添加目的地并选择 **Incident.io**。将 ID 或完整警报事件 URL 粘贴到 **Alert source config ID**，再将 Token 粘贴到 **Token**。
  </StepItem>

  <StepItem>
    从目的地的操作菜单发送测试通知。测试会在 incident.io 中创建一条触发中的警报。
  </StepItem>
</Steps>

Mastra 会向 incident.io 发送以下字段：

| incident.io 字段 | 值 |
| - | - |
| `status` | 新通知或重复通知为 `firing`，恢复通知为 `resolved` |
| `deduplication_key` | Mastra 事件 ID |
| `title` | 事件的单行描述 |
| `description` | 事件包含错误时的错误消息 |
| `metadata` | 事件数据，以及 `source`、`event_type`、`severity`、`project_id` 和 `environment` |

在警报属性和路由规则中使用 `metadata` 字段。在 incident.io 中的变更不会更新 Mastra 事件；如果 incident.io 拒绝 Token 或警报源 ID，发送状态会显示 **Config error**。

## 接收 Webhook 通知 {/* #receive-webhook-notifications */}

Webhook 目的地会为每次通知接收一个带 JSON 请求体的 HTTP `POST` 请求。可用 Webhook 连接 Mastra 未直接集成的工具。

### Webhook Payload {/* #webhook-payload */}

以下示例显示了失败的部署：

```json
{
  "id": "deploy.failed:dep_8c2f1a:triggered",
  "version": "2026-09-01",
  "type": "deploy.failed",
  "createdAt": "2026-09-24T14:03:11.000Z",
  "fingerprint": "deploy.failed|prj_41d9e2|server|production",
  "severity": "error",
  "status": "triggered",
  "summary": "Deploy failed on support-agent (production): Build failed",
  "source": "mastra",
  "data": {
    "deployId": "dep_8c2f1a",
    "projectName": "support-agent",
    "gitBranch": "main",
    "error": "Build failed",
    "errorCode": "BUILD_FAILED",
    "errorCategory": "build",
    "deployUrl": "https://projects.mastra.ai/..."
  },
  "links": []
}
```

| 字段 | 说明 |
| - | - |
| `id` | 通知 ID。Mastra 重试同一通知时保持不变 |
| `version` | Payload 版本。当前版本为 `2026-09-01` |
| `type` | 事件类型。参见下表 |
| `createdAt` | 事件发生时的 ISO 8601 时间 |
| `fingerprint` | 标识通知所属事件。同一失败的部署目标或服务的通知共享一个指纹 |
| `severity` | `critical`、`error`、`warning` 或 `info`；这些值与 PagerDuty 严重程度一致 |
| `status` | 新通知或重复通知为 `triggered`，事件恢复后为 `resolved` |
| `summary` | 事件的单行描述 |
| `source` | 始终为 `mastra` |
| `data` | 事件专有的详细信息；字段随事件类型而异 |
| `links` | 相关链接，每个链接包含 `href` 和 `text`；可以为空 |

`type` 字段可取以下值：

| 类型 | 触发条件 | 常见 `data` 字段 |
| - | - | - |
| `deploy.failed` | **Deploy failed** | `deployId`, `projectName`, `gitBranch`, `error`, `errorCode`, `errorCategory`, `deployUrl` |
| `service.crashed` | **Service crashed** | 同 `deploy.failed` |
| `service.oom` | **Service out of memory** | 同 `deploy.failed` |
| `service.unreachable` | **Service unreachable** | `projectName`, `probeUrl`, `error`, `consecutiveFailures` |
| `billing.usage_threshold` | **Usage threshold crossed** | `featureId`, `featureLabel`, `thresholdDisplay`, `error` |

同一服务的崩溃、内存不足和不可达事件共享指纹，因此一次服务中断只产生一个事件。用量阈值事件不会发送 `resolved` 通知。

测试通知使用 `type: "deploy.failed"`、`severity: "info"`，并在 `data` 中包含 `"test": true`。

### 请求标头 {/* #request-headers */}

| Header | 值 |
| - | - |
|`content-type` | `application/json` |
| `user-agent` | `Mastra-Alerts/1.0` |
| `x-mastra-signature` | 请求体签名。参见[验证 Webhook 签名](#verify-webhook-signatures) |
| `x-mastra-idempotency-key` | 与 Payload `id` 相同 |

### 验证 Webhook 签名 {/* #verify-webhook-signatures */}

信任请求前，先验证签名。`x-mastra-signature` Header 格式如下：

```text
t=1790258591,v1=5f0c9d3e...
```

`t` 是 Mastra 签署请求时的 Unix 时间戳（秒）。`v1` 是使用目的地签名密钥，对字符串 `<t>.<raw request body>` 计算出的十六进制 HMAC-SHA256。

要验证请求：

1. 在解析为 JSON 前读取原始请求体。重新解析和序列化可能改变其内容。
1. 计算 `<t>.<raw body>` 的 HMAC，并使用恒定时间比较将其与 `v1` 比对。
1. 拒绝 `t` 比当前时间早数分钟以上的请求，以防重放攻击。

<Tabs>
  <TabItem value="node" label="Node.js">
    ```typescript title="verify-mastra-signature.ts"
    import { createHmac, timingSafeEqual } from 'node:crypto'

    const TOLERANCE_SECONDS = 300

    export function verifyMastraSignature(
      rawBody: string,
      signatureHeader: string,
      signingSecret: string,
    ): boolean {
      const parts = new Map(signatureHeader.split(',').map(part => part.split('=') as [string, string]))
      const timestamp = Number(parts.get('t'))
      const signature = parts.get('v1')
      if (!Number.isInteger(timestamp) || !signature || !/^[0-9a-f]{64}$/.test(signature)) return false
      if (Math.abs(Date.now() / 1000 - timestamp) > TOLERANCE_SECONDS) return false

      const expected = createHmac('sha256', signingSecret)
        .update(`${timestamp}.${rawBody}`)
        .digest('hex')
      const expectedBytes = Buffer.from(expected, 'hex')
      const signatureBytes = Buffer.from(signature, 'hex')
      return (
        expectedBytes.length === signatureBytes.length && timingSafeEqual(expectedBytes, signatureBytes)
      )
    }
    ```
  </TabItem>

  <TabItem value="python" label="Python">
    ```python title="verify_mastra_signature.py"
    import hashlib
    import hmac
    import time

    TOLERANCE_SECONDS = 300


    def verify_mastra_signature(raw_body: bytes, signature_header: str, signing_secret: str) -> bool:
        parts = dict(part.partition("=")[::2] for part in signature_header.split(","))
        try:
            timestamp = int(parts["t"])
            signature = parts["v1"]
        except (KeyError, ValueError):
            return False
        if abs(time.time() - timestamp) > TOLERANCE_SECONDS:
            return False

        expected = hmac.new(
            signing_secret.encode(),
            f"{timestamp}.".encode() + raw_body,
            hashlib.sha256,
        ).hexdigest()
        return hmac.compare_digest(expected, signature)
    ```
  </TabItem>
</Tabs>

验证失败的请求应返回 `401` 状态。更换目的地密钥后，新请求会立即改用新密钥签名。

### 重试和重复通知 {/* #retries-and-duplicate-notifications */}

Mastra 将任何 `2xx` 响应视为已送达，不会重试。请在响应前持久化或可靠地入队通知；若该步骤失败，请返回 `5xx`，让 Mastra 重试。请在 10 秒内响应，耗时更长的处理可在响应后继续。Mastra 不会跟随重定向。

当请求失败时，Mastra 根据响应重试：

- **`4xx` 响应：**Mastra 停止重试，并将发送状态标为 **Config error**。修复端点后，请在目的地使用 **Test** 确认。
- **`5xx` 响应、超时或网络错误：**Mastra 会在几秒内重试两次。如果仍失败，状态显示 **Retrying**，约 30 秒后再次尝试，此后等待时间逐次翻倍，最多 15 分钟。失败 6 次后，状态显示 **Exhausted**。

Discord、Microsoft Teams、PagerDuty 和 incident.io 目的地遵循相同的重试计划。对于这些目的地，Mastra 还会重试 `408` 和 `429` 响应。

重试可能使同一通知送达多次。请保存每个已处理请求的 `x-mastra-idempotency-key`，并跳过已经出现过的键。使用 `fingerprint` 对属于同一事件的通知分组。
