# 警报

当部署失败、正在运行的服务停止或停止响应或者组织使用量超过计划阈值时，警报会通知您的团队。您可以在组织级别配置警报，然后选择每个警报涵盖的项目和环境。

组织管理员可以创建和管理警报。其他组织角色对警报设置具有只读访问权限。

打开[Mastra platform dashboard](https://projects.mastra.ai), go to your organization settings, then select **Alerts**。该页面有三个选项卡：

* **警报**列出每个警报及其范围、目的地、状态以及启用或暂停开关。
* **目的地**列出了可以接收通知的 Slack 频道、Discord 频道、Microsoft Teams 频道、电子邮件组、Webhook 终结点、PagerDuty 服务和 Incident.io 警报源。
* **活动**显示事件以及与之相关的通知尝试。

## 添加目的地 {/* #add-a-destination */}

目的地定义了 Mastra 发送通知的位置。创建警报之前至少添加一个目的地。

|目的地 |配置|
| - | - |
|**Slack** | Connect a Slack workspace and select one or more channels. Mastra creates a separate destination for each selected channel. |
| **Discord** | Enter a Discord channel webhook URL. See [Send alerts to Discord](#send-alerts-to-discord). |
| **Microsoft Teams** | Enter the URL of a Teams workflow that posts to a channel. See [Send alerts to Microsoft Teams](#send-alerts-to-microsoft-teams). |
| **Email** | Select organization roles, individual members, or up to 10 email addresses. Role-based recipient groups update when organization membership changes. |
| **Webhook**|输入 HTTPS 端点。 Mastra 对每个请求进行签名，并在创建目的地后显示签名密钥。 |
|**寻呼机任务**|输入 PagerDuty Events API v2 集成的集成密钥。看[向 PagerDuty 发送警报](#send-alerts-to-pagerduty). |
| **事件.io**|输入 Incident.io HTTP 警报源的警报源配置 ID 和令牌。看[向 event.io 发送警报](#send-alerts-to-incidentio). |

<Steps>
  <StepItem>
    上**Destinations** tab, select **Add destination**.
  </StepItem>

  <StepItem>
    选择**Slack**, **Discord**, **Microsoft Teams**, **Email**, **Webhook**, **PagerDuty**, or **Incident.io**, then enter a name for the destination.
  </StepItem>

  <StepItem>
    配置选定的目的地：

    * 对于 Slack，连接或选择一个Workspace，然后选择应接收警报的通道。 Mastra Alerts 应用程序会自动加入公共频道。邀请`@Mastra Alerts` before selecting a private channel.
    * 对于 Discord，请输入频道的 Webhook URL。
    * 对于 Microsoft Teams，输入Workflow的 Webhook URL。
    * 对于电子邮件，请选择**All organization members**, one or more roles, individual members, or external email addresses.
    * 对于 Webhook，输入以以下内容开头的端点`https://`.
    * 对于 PagerDuty，输入**Integration key**.
    * 对于 event.io，输入**Alert source config ID** and **Token**.
  </StepItem>

  <StepItem>
    选择**Create destination**. For a webhook destination, copy the signing secret before closing the page. The secret can't be shown again.
  </StepItem>
</Steps>

目标表单根据所选类型而变化。 Slack 目标需要一个Workspace和至少一个通道。 Discord 和 Microsoft Teams 目标需要 Webhook URL。电子邮件目标需要至少一个收件人，该收件人可以是组织角色、成员或外部地址。 Webhook 目标需要 HTTPS 端点。 PagerDuty 和 Incident.io 目标需要来自其集成的凭据。每个目的地还需要一个在警报配置和活动历史记录中标识它的名称。

使用目标的操作菜单发送测试通知。您还可以编辑、暂停或删除目的地。暂停目的地会停止通知，但不会将其从现有警报中删除。

对于 Webhook 目标，**Rotate secret** replaces the current signing secret immediately. Update the receiving endpoint with the new secret before sending another alert.

Discord 和 Microsoft Teams Webhook URL 包含自己的凭据，因此 Mastra 将它们加密存储，并在创建目标后仅显示最后四个字符。要旋转 URL，请编辑目标并粘贴新目标。将 URL 字段留空会保留存储的 URL。

## 创建警报 {/* #create-an-alert */}

警报结合了触发器、范围、目的地和重复警报节奏。

<Steps>
  <StepItem>
    上**Alerts** tab, select **Create Alert**.
  </StepItem>

  <StepItem>
    输入警报名称并离开**Enabled** on if the alert should start monitoring immediately.
  </StepItem>

  <StepItem>
    选择一个或多个触发器：

    * **部署失败**：构建或部署未达到运行状态。
    * **服务崩溃**：正在运行的服务耗尽其重新启动策略并停止。
    * **服务内存不足**：服务在内存不足后停止。
    * **服务不可达**：已部署的服务连续 3 次运行状况检查失败。
    * **已突破使用阈值**：组织使用量超过计划阈值或达到其限制。此触发器是组织范围内的，因此需要**All projects** scope.
  </StepItem>

  <StepItem>
    将警报范围设置为**All projects** or **Specific projects**. When you select specific projects, you can narrow the scope to individual environments. Leaving the environment selection empty includes every environment in that project.
  </StepItem>

  <StepItem>
    选择一个或多个目的地。您可以添加或编辑目的地，而无需离开警报设置。
  </StepItem>

  <StepItem>
    在下面**Repeat alerts**, choose how often Mastra can resend an alert for the same incident: every event, every 5 minutes, every 15 minutes, or every hour. The first notification, recovery notifications, and severity increases send immediately.
  </StepItem>

  <StepItem>
    选择**Create Alert**.
  </StepItem>
</Steps>

警报表单将这些设置分组为**Name**, **Trigger**, **Scope**, and **Destinations**. The selected destinations and repeat interval apply to every trigger and project included in that alert.

## 管理警报 {/* #manage-alerts */}

这**Alerts** tab shows each alert's scope, destinations, and current state. Use the switch to pause or enable an alert.

打开警报的操作菜单可以：

* **编辑**它的触发器、范围、目的地、节奏或名称。
* **测试**分配给警报的每个目的地。
* **删除**警报。现有事件和交付历史记录仍然可用。

## 查看警报活动 {/* #review-alert-activity */}

这**Activity** tab groups each incident with its delivery attempts. An incident stays **Open** while the condition is active and changes to **Resolved** after the service or deploy recovers, except for usage threshold incidents, which don't resolve automatically.

展开事件以检查发送到每个目的地的通知。每个事件行显示事件发生的时间、事件类型、其项目或环境范围及其当前状态。嵌套的传递行显示每个通知尝试的触发器、目标和传递状态。交付尝试可以是**Scheduled**, **Sent**, **Suppressed**, **Retrying**, **Exhausted**, or **Config error**. Use the activity filter to show all activity, incidents only, or delivery attempts only.

## 向 Discord 发送警报 {/* #send-alerts-to-discord */}

Discord 目标通过 Discord Webhook 将嵌入发布到频道。触发的事件会发布红色嵌入，恢复会发布单独的绿色**Resolved** embed. Discord webhooks can't update earlier messages, so the resolved notice is a new message rather than an edit.

<Steps>
  <StepItem>
    在 Discord 中，打开应接收警报的频道，然后选择**Edit Channel**, **Integrations**, **Webhooks**, and **New Webhook**. Copy the webhook URL. See [Intro to Webhooks](https://support.discord.com/hc/en-us/articles/228383668-Intro-to-Webhooks) in the Discord documentation.
  </StepItem>

  <StepItem>
    在 Mastra 中，添加目的地，选择**Discord**, and paste the URL into **Webhook URL**. The URL must have the form `https://discord.com/api/webhooks/<id>/<token>`.
  </StepItem>

  <StepItem>
    从目标的操作菜单发送测试通知。
  </StepItem>
</Steps>

嵌入在其标题中显示事件和项目，链接到部署日志，后面是错误摘录以及事件包含的环境、分支和错误代码。如果 Discord 拒绝 Webhook URL，则交付显示**Config error**.

## 向 Microsoft Teams 发送警报 {/* #send-alerts-to-microsoft-teams */}

Microsoft Teams 目标通过 Teams Workflow将自适应卡发布到频道。触发事件会张贴红牌，恢复事件会张贴单独的绿牌**Resolved** card.

<Steps>
  <StepItem>
    在 Teams 中，打开应接收警报的频道，选择**More options** and then **Workflows**, and choose the template **Send webhook alerts to a channel**. Select the team and channel, create the workflow, then copy the workflow URL. See [Create incoming webhooks with Workflows](https://support.microsoft.com/en-us/office/create-incoming-webhooks-with-workflows-for-microsoft-teams-8ae491c7-0394-4861-ba59-055e33f75498) in the Microsoft documentation.
  </StepItem>

  <StepItem>
    在 Mastra 中，添加目的地，选择**Microsoft Teams**, and paste the URL into **Webhook URL**.
  </StepItem>

  <StepItem>
    从目标的操作菜单发送测试通知。
  </StepItem>
</Steps>

Microsoft 已淘汰经典 Office 365 连接器，因此请使用 Teams Workflow程而不是旧版**Incoming Webhook** connector. Mastra still accepts legacy `webhook.office.com` URLs for tenants that haven't migrated.

该卡在其标题中显示事件和项目，后面是环境、分支和错误代码（当事件包含这些代码时）、错误摘录以及用于打开部署日志的按钮。如果 Teams 拒绝Workflow URL，则交付显示**Config error**.

## 向 PagerDuty 发送警报 {/* #send-alerts-to-pagerduty */}

PagerDuty 目标将事件发送到 PagerDuty 事件 API v2。每个 Mastra 事件都会打开一个 PagerDuty 事件，当 Mastra 事件解决时，PagerDuty 会解决该事件。

<Steps>
  <StepItem>
    在 PagerDuty 中，打开应接收警报的服务。就其**Integrations** tab, add an **Events API V2** integration and copy its **Integration Key**. See [Services and integrations](https://support.pagerduty.com/main/docs/services-and-integrations) in the PagerDuty documentation.
  </StepItem>

  <StepItem>
    在 Mastra 中，添加目的地，选择**PagerDuty**, and paste the key into **Integration key**.
  </StepItem>

  <StepItem>
    从目标的操作菜单发送测试通知。该测试打开一个事件`info` severity in PagerDuty. Resolve it in PagerDuty.
  </StepItem>
</Steps>

Mastra 将其通知映射到 PagerDuty 事件，如下所示：

| PagerDuty 字段 |价值|
| - | - |
|`event_action` | `trigger` for a new or repeated notification, `resolve` for a recovery |
| `dedup_key` | The Mastra incident ID. Repeated notifications for the same incident update one PagerDuty incident |
| `payload.summary` | A one-line description, for example `Deploy failed on support-agent (production): Build failed` |
| `payload.severity` | The Mastra severity: `critical`, `error`, `warning`, or `info` |
| `payload.source` | `mastra:<project>/<environment>` |
| `payload.custom_details` | The event data described in [Webhook payload](#webhook-payload) |

在 PagerDuty 中所做的更改（例如确认或解决事件）不会更新 Mastra 事件。如果 PagerDuty 拒绝集成密钥，则交付显示**Config error**.

## 向 event.io 发送警报 {/* #send-alerts-to-incidentio */}

Incident.io 目标将警报事件发送到 Incident.io HTTP 警报源。每个 Mastra 事件都会在 Incident.io 中创建一个警报，并且当 Mastra 事件解决时该警报也会解决。

<Steps>
  <StepItem>
    在 Incident.io 中，使用以下命令创建 HTTP 警报源**Default** source type. Mastra sends events in the incident.io alert event format, so a custom transform isn't needed. See [Create an alert event](https://docs.incident.io/api-reference/alert-events-v2/create) in the incident.io documentation.
  </StepItem>

  <StepItem>
    从源的授权标头中复制警报源配置 ID 和持有者令牌。 ID 是警报事件 URL 的最后一段，`https://api.incident.io/v2/alert_events/http/<alert-source-config-id>`.
  </StepItem>

  <StepItem>
    在 Mastra 中，添加目的地并选择**Incident.io**. Paste the ID, or the full alert events URL, into **Alert source config ID**, and the token into **Token**.
  </StepItem>

  <StepItem>
    从目标的操作菜单发送测试通知。该测试在 event.io 中创建触发警报。
  </StepItem>
</Steps>

Mastra 将这些字段发送到 event.io：

| event.io 领域 |价值|
| - | - |
|`status` | `firing` for a new or repeated notification, `resolved` for a recovery |
| `deduplication_key` | The Mastra incident ID |
| `title` | A one-line description of the event |
| `description` | The error message, when the event has one |
| `metadata` | The event data plus `source`, `event_type`, `severity`, `project_id`, and `environment` |

使用`metadata` fields in alert attributes and routing rules. Changes made in incident.io don't update the Mastra incident, and if incident.io rejects the token or alert source ID, the delivery shows **Config error**.

## 接收网络钩子通知 {/* #receive-webhook-notifications */}

Webhook 目标接收 HTTP`POST` request with a JSON body for each notification. Use a webhook to connect a tool that Mastra doesn't integrate with directly.

### Webhook 负载 {/* #webhook-payload */}

以下示例显示了失败的部署：

```json
{
  "id": "deploy.failed:dep_8c2f1a:triggered",
  "version": "2026-09-01",
  "type": "deploy.failed",
  "createdAt": "2026-09-24T14:03:11.000Z",
  "fingerprint": "deploy.failed|prj_41d9e2|server|production",
  "severity": "error",
  "status": "triggered",
  "summary": "Deploy failed on support-agent (production): Build failed",
  "source": "mastra",
  "data": {
    "deployId": "dep_8c2f1a",
    "projectName": "support-agent",
    "gitBranch": "main",
    "error": "Build failed",
    "errorCode": "BUILD_FAILED",
    "errorCategory": "build",
    "deployUrl": "https://projects.mastra.ai/..."
  },
  "links": []
}
```

|领域 |描述 |
| - | - |
|`id` | Notification ID. Stays the same when Mastra retries the same notification |
| `version` | Payload version. The current version is `2026-09-01` |
| `type` | Event type. See the table below |
| `createdAt` | ISO 8601 time when the event occurred |
| `fingerprint` | Identifies the incident the notification belongs to. Notifications for the same failing deploy target or service share a fingerprint |
| `severity` | `critical`, `error`, `warning`, or `info`. These values match PagerDuty severities |
| `status` | `triggered` for a new or repeated notification, `resolved` when the incident recovers |
| `summary` | One-line description of the event |
| `source` | Always `mastra` |
| `data` | Event-specific details. Fields vary by event type |
| `links` | Related links, each with `href` and `text`. Can be empty |

这`type` field has one of these values:

|类型 |触发|常见的`data` fields |
| - | - | - |
| `deploy.failed` | **Deploy failed** | `deployId`, `projectName`, `gitBranch`, `error`, `errorCode`, `errorCategory`, `deployUrl` |
| `service.crashed` | **Service crashed** | Same as `deploy.failed` |
| `service.oom` | **Service out of memory** | Same as `deploy.failed` |
| `service.unreachable` | **Service unreachable** | `projectName`, `probeUrl`, `error`, `consecutiveFailures` |
| `billing.usage_threshold` | **Usage threshold crossed** | `featureId`, `featureLabel`, `thresholdDisplay`, `error` |

同一服务的崩溃、内存不足和无法访问事件共享一个指纹，因此一次中断会产生一次事件。使用阈值事件不会发送`resolved` notification.

测试通知使用`type: "deploy.failed"`, `severity: "info"`, and include `"test": true` in `data`.

### 请求标头 {/* #request-headers */}

|标题|价值|
| - | - |
|`content-type` | `application/json` |
| `user-agent` | `Mastra-Alerts/1.0` |
| `x-mastra-signature` | Signature of the request body. See [Verify webhook signatures](#verify-webhook-signatures) |

### 验证 Webhook 签名 {/* #verify-webhook-signatures */}

在信任请求之前验证签名。这`x-mastra-signature` header has this format:

```text
t=1790258591,v1=5f0c9d3e...
```

`t`是 Mastra 签署请求时的 Unix 时间（以秒为单位）。`v1` is a hex-encoded HMAC-SHA256 of the string `<t>.<raw request body>`, using the destination's signing secret as the key.

要验证请求：

1. 在将原始请求正文解析为 JSON 之前读取它。再次解析和序列化主体可以改变它。
2. 计算 HMAC`<t>.<raw body>` and compare it with `v1` using a constant-time comparison.
3. 拒绝请求的位置`t` is more than a few minutes old to prevent replayed requests.

<Tabs>
  <TabItem value="node" label="Node.js">
    ```typescript title="verify-mastra-signature.ts"
    import { createHmac, timingSafeEqual } from 'node:crypto'

    const TOLERANCE_SECONDS = 300

    export function verifyMastraSignature(
      rawBody: string,
      signatureHeader: string,
      signingSecret: string,
    ): boolean {
      const parts = new Map(signatureHeader.split(',').map(part => part.split('=') as [string, string]))
      const timestamp = Number(parts.get('t'))
      const signature = parts.get('v1')
      if (!Number.isInteger(timestamp) || !signature || !/^[0-9a-f]{64}$/.test(signature)) return false
      if (Math.abs(Date.now() / 1000 - timestamp) > TOLERANCE_SECONDS) return false

      const expected = createHmac('sha256', signingSecret)
        .update(`${timestamp}.${rawBody}`)
        .digest('hex')
      const expectedBytes = Buffer.from(expected, 'hex')
      const signatureBytes = Buffer.from(signature, 'hex')
      return (
        expectedBytes.length === signatureBytes.length && timingSafeEqual(expectedBytes, signatureBytes)
      )
    }
    ```
  </TabItem>

  <TabItem value="python" label="Python">
    ```python title="verify_mastra_signature.py"
    import hashlib
    import hmac
    import time

    TOLERANCE_SECONDS = 300


    def verify_mastra_signature(raw_body: bytes, signature_header: str, signing_secret: str) -> bool:
        parts = dict(part.partition("=")[::2] for part in signature_header.split(","))
        try:
            timestamp = int(parts["t"])
            signature = parts["v1"]
        except (KeyError, ValueError):
            return False
        if abs(time.time() - timestamp) > TOLERANCE_SECONDS:
            return False

        expected = hmac.new(
            signing_secret.encode(),
            f"{timestamp}.".encode() + raw_body,
            hashlib.sha256,
        ).hexdigest()
        return hmac.compare_digest(expected, signature)
    ```
  </TabItem>
</Tabs>

返回一个`401` status for a request that fails verification. After you rotate a destination's secret, requests are signed with the new secret immediately.

### 重试和重复通知 {/* #retries-and-duplicate-notifications */}

Mastra 治疗任何`2xx` response as delivered and doesn't retry it. Persist or durably enqueue the notification before responding, and return a `5xx` response if that step fails so Mastra retries the delivery. Respond within 10 seconds and process the notification after responding if the work takes longer. Mastra doesn't follow redirects.

当请求失败时，Mastra 根据响应重试：

* **`4xx`回复：**&#x4D;astra 停止并标记交货**Config error**. Fix the endpoint, then use **Test** on the destination to confirm it works.
* **`5xx`响应、超时或网络错误：**&#x4D;astra 在几秒钟内重试两次。如果这些请求也失败，则交付显示**Retrying** and Mastra tries again after about 30 seconds, doubling the wait each time up to 15 minutes. After 6 failed attempts, the delivery shows **Exhausted**.

Discord、Microsoft Teams、PagerDuty 和 Incident.io 目的地遵循相同的时间表。对于这些目的地，Mastra 也会重试`408` and `429` responses.

重试可以多次发送相同的通知。存储`x-mastra-idempotency-key` value of each processed request and skip requests with a key you've already seen. Use `fingerprint` to group notifications that belong to the same incident.
