# 环境

每个平台项目都包含一个或多个环境。

环境是一个独立的部署目标，具有自己的 URL、环境变量和部署历史记录。也可以有自己的[hosted database](/docs/mastra-platform/database).

使用环境来运行`production`, `staging`，以及单个项目中相同代码库的预览版本。

你的第一个[`mastra deploy`](/docs/mastra-platform/deploy) creates the `production` environment. Create more with the CLI or by deploying to a name that doesn't exist yet.

## 创造环境 {/* #create-an-environment */}

显式创建环境：

```bash
mastra env create staging
```

或者让部署创建它，这会提示您确认：

```bash
mastra deploy --env staging
```

`mastra env create`默认为`staging` type. Pass `--type` to set `staging` or `preview` explicitly, and `--region`选择环境运行的位置：

```bash
mastra env create eu-preview --type preview --region eu
```

每个项目都有一个`production` environment, created by your first deploy. The region is fixed at creation. Attached databases are placed near the environment automatically, while observability data goes to the ingest region for the matching residency zone. See [Regions](/docs/mastra-platform/regions) for supported regions and database placement, along with observability co-location. The number of environments per project depends on your plan.

## 列出环境 {/* #list-environments */}

```bash
mastra env list
```

输出显示每个环境的名称、区域、活动部署状态以及附加数据库注入的托管环境变量。经过`--json` for machine-readable output in CI.

全部`mastra env` commands resolve their project from the `--project` flag, the `MASTRA_PROJECT_ID` environment variable, or the `.mastra-project.json` file written by your first deploy, in that order. Run them from your project directory and you never need to name the project.

## 环境变量 {/* #environment-variables */}

环境从两个范围解析其变量：

* **托管变量**：由附件注入[hosted databases](/docs/mastra-platform/database) (for example `TURSO_DATABASE_URL`) and by the platform itself. The platform defines these, and you can't edit them. See [System environment variables](/docs/mastra-platform/system-environment-variables) for the full list.
* **环境范围的变量**：通过仪表板存储在每个环境中。当您将一个变量应用于多个环境时，每个环境都会保留自己的副本。将这些值用于环境之间不同的值，例如用于登台和生产服务的 API 密钥。

环境范围的变量是描述的存储变量[Deploy](/docs/mastra-platform/deploy#environment-variables) page. A deploy of one environment uses only that environment's variables. Projects still on the [legacy pipeline](/docs/mastra-platform/deploy#migrating-from-server-and-studio-deploys) store their variables on the project instead, and every deploy of that project uses them.

部署开始时应用变量。要将更改的变量应用到正在运行的服务而不需要完全重新部署：

```bash
mastra env restart staging
```

要查看环境部署实际运行的设置，以及按名称列出的托管变量，请将它们拉入本地环境文件中。每个环境都是独立的。该文件永远不会混合在另一个环境的值中：

```bash
mastra env vars pull staging --output .env.staging
```

托管变量值在部署时注入，并且永远不会写入文件。它们仅显示为名称注释。

:::注意
环境变量不会覆盖托管数据库变量。要将环境指向不同的数据库，请附加[environment-scoped database](/docs/mastra-platform/database#attach-with-the-cli) instead.
:::

## 部署历史记录 {/* #deploy-history */}

列出跨所有环境的部署，或过滤到一个：

```bash
mastra env deploys
mastra env deploys staging
```

每行显示部署状态、环境、时间戳以及当前处于活动状态的部署。部署转换通过**queued → uploading → starting → deploying → running**, and the platform reports **running** only when the new version is serving traffic. Deploys triggered from GitHub first build from source, so they pass through **building** between **queued** and **uploading**.

## 隔离环境数据 {/* #isolate-an-environments-data */}

默认情况下，托管数据库的范围仅限于单个环境，因此生产和暂存每个​​数据库都会读取和写入自己的数据库：

```bash
mastra env db create production --kind turso --name my-project-production-db
mastra env db create staging --kind turso --name my-project-staging-db
```

如果您希望在每个环境中共享一个数据库，请将其附加到`--shared` instead: `mastra env db create --kind turso --shared`.

每个环境可以为每个Provider使用一个数据库。现有的共享 (`--shared`) database from the same provider creates a variable-name conflict with an environment-scoped database. Export any data you need to keep before running `mastra env db delete`, because this command destroys the shared provider database and its data. See [Hosted databases](/docs/mastra-platform/database) for the full scoping model.

## 删除环境 {/* #delete-an-environment */}

```bash
mastra env delete staging
```

CLI 在删除之前要求确认。删除环境会删除其部署和存储的变量。
