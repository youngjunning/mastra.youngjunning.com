# Mastra平台上的服务器

Mastra 平台上的服务器是一个生产部署目标，它将您的 Mastra 应用程序作为 API 服务器运行。当您希望平台构建、部署、托管和管理您的 Mastra 服务器时，请使用它。

您可以获得稳定的 API 端点，具有环境变量管理和自定义域支持，以及开箱即用的部署历史记录。

：：：笔记

服务器部署自动配置托管存储。如果您使用覆盖存储[LibSQLStore](/integrations/databases/libsql) and a file URL, switch to a remotely hosted database because Mastra platform uses an ephemeral filesystem.

:::

## 部署生命周期 {/* #deploy-lifecycle */}

每个项目在部署过渡时一次运行一个构建**queued → uploading → starting → deploying → running** (or **failed**, **cancelled**, **crashed**, or **stopped**). Deploys triggered from GitHub first build from source, so they pass through **building** between **queued** and **uploading**. When multiple deploys queue up, the latest proceeds and the rest are cancelled. Builds running longer than 15 minutes are automatically failed. The first deploy provisions infrastructure and seeds environment variables from your local `.env`. Your server URL remains stable across deploys.

## 闲置行为 {/* #idle-behavior */}

Mastra 平台上的服务器可以在一段时间不活动后休眠服务以节省资源。不活动状态是通过出站网络流量来衡量的。仅在大约 10 分钟且没有出站数据包的情况下，服务才会被视为空闲。任何重复出现的出站流量都会重置此计时器并使服务保持唤醒状态。

永不休眠的服务器通常具有后台任务或在计时器上发送流量的长期连接。检查以下常见原因。

### 持久数据库连接 {/* #persistent-database-connections */}

即使服务器空闲，保持打开状态的数据库客户端也能保持连接。许多驱动程序还会运行后台运行状况检查，定期对数据库进行 ping 操作，这也算作出站流量。例如，一个从未关闭的 MongoDB 客户端保持监控套接字打开，并大约每 10 秒发送一次心跳。

耗尽空闲连接的连接池设置本身是不够的，因为驱动程序的监视连接保持打开状态并保持 ping。要让服务器休眠，请在一段时间不活动后关闭客户端，并在下一个请求时重新连接。

:::注意
关闭客户端会为服务器唤醒后的第一个请求添加短暂的重新连接延迟。如果您的工作负载无法容忍这种延迟，请保持连接打开并且不要依赖空闲睡眠。
:::

### 计划任务和计时器 {/* #scheduled-tasks-and-timers */}

一个`setInterval`, cron job, or polling loop that makes network calls keeps the server awake. If you need scheduled work, run it as a separate service or use an external scheduler that wakes the server with a request.

### 外部 ping 和保持活动检查 {/* #external-pings-and-keep-alive-checks */}

正常运行时间监视器、运行状况检查或按一定时间间隔访问服务器的保持活动 ping 会重置空闲计时器。如果您希望服务器休眠，请删除这些检查或将其间隔增加到空闲窗口之外。

### 可观察性出口商 {/* #observability-exporters */}

将跟踪、日志或指标流式传输到远程端点的导出器会发送出站流量。确认导出器在服务器空闲时批量并停止发送，而不是按固定间隔刷新。

### 长寿的流 {/* #long-lived-streams */}

开放的服务器发送事件 (SSE) 流、WebSocket 或其他长期连接会保持流量开放，直至关闭。在后台保持订阅的流响应使连接保持活动状态。确认当客户端断开连接时流关闭，并且在服务器空闲时没有流保持打开状态。

### 聊天集成 {/* #chat-integrations */}

一些聊天集成保持持久连接并发送定期心跳，这使服务器保持唤醒状态。例如，套接字模式下的 Slack 应用程序会打开 WebSocket 并大约每 30 秒执行一次 ping 操作，而 Discord 机器人则通过计时器上的心跳保持其网关 WebSocket 打开。打开套接字和心跳都会阻止空闲。

如果您希望服务器休眠，请通过 HTTP Webhook 接收事件，而不是集成支持的持久连接。例如，Slack 应用程序可以使用带有请求 URL 的事件 API，而不是套接字模式。如果您的应用程序需要持久连接，请保持服务运行**Persistent Server add-on** described below.

### 检查活动连接 {/* #inspect-active-connections */}

要找出使服务器保持唤醒状态的原因，请在空闲期间检查进程的活动句柄。所有请求完成后保留的句柄是需要调查的原因。打开的套接字指向需要关闭的持久连接，活动的计时器指向`setInterval` or self-rescheduling `setTimeout`.

将以下帮助程序放入您的应用程序中，然后在流量停止后查看日志。服务器空闲后仍然列出的任何内容都会使其保持唤醒状态：

```typescript title="src/mastra/diagnose-idle.ts"
export function logActiveHandles() {
  // process._getActiveHandles is undocumented but useful for diagnosis.
  const handles = (process as any)._getActiveHandles() as Array<any>

  const summary = handles.map(handle => {
    const type = handle?.constructor?.name ?? typeof handle
    if (type === 'Socket') {
      return `Socket -> ${handle.remoteAddress}:${handle.remotePort}`
    }
    return type
  })

  console.log(`[idle] ${handles.length} active handles:`, summary)
}

// Log every 30 seconds so you can see what persists while the server is idle.
setInterval(logActiveHandles, 30_000).unref()
```

称呼`unref()` on the diagnostic interval so the helper itself doesn't keep the server awake.

### 保持服务运行 {/* #keep-a-service-running */}

某些应用程序实际上需要上述连接或任务，例如用于低首次请求延迟的持久数据库连接、后台调度程序或长期存在的流。如果您的应用程序需要其中任何一个，请不要强制该服务休眠。使用**Persistent Server add-on** to keep the service running continuously instead.

随着**Persistent Server add-on** enabled, the service stays awake even with no traffic, so persistent connections, scheduled tasks, and open streams keep working without being interrupted by idle sleep.

## 持续集成/持续交付 {/* #cicd */}

从 GitHub Actions、GitLab CI 或任何 CI Provider自动进行部署。首次交互式部署后，CI/CD 需要 API 令牌、您的组织和项目 ID 以及`.mastra-project.json` file committed to your repository.

:::提示
如果您的代码位于 GitHub 上，[GitHub integration](/docs/mastra-platform/github) gives you push-to-deploy without writing a workflow file. Use the CLI-based CI/CD flow below when you need GitLab, another CI provider, or custom build steps before deploy.
:::

### 创建 API 令牌 {/* #create-an-api-token */}

<Steps>
  <StepItem>
    在本地运行以下命令：

    ```bash
    mastra auth tokens create ci-deploy
    ```

    CLI 打印一次令牌。立即复制它，因为它无法再次检索。
  </StepItem>

  <StepItem>
    将令牌添加为 CI 提供程序中的机密。在 GitHub Actions 中，转到**Settings → Secrets and variables → Actions** and create the `MASTRA_API_TOKEN` secret.
  </StepItem>

  <StepItem>
    确保您的`.mastra-project.json` file is committed to the repository.
  </StepItem>

  <StepItem>
    添加`MASTRA_ORG_ID` and `MASTRA_PROJECT_ID` to your CI provider, using the `organizationId` and `projectId` values from `.mastra-project.json`. When `MASTRA_API_TOKEN` is set, `mastra deploy` runs headless and fails if either variable is missing.
  </StepItem>
</Steps>

### 这`--yes` flag {/* #the---yes-flag */}

经过`--yes` (or `-y`) to skip all confirmation prompts. Without it, the CLI waits for interactive input and your CI job hangs.

```bash
mastra deploy --yes
```

### GitHub 操作 {/* #github-actions */}

每次推送时都会部署以下Workflow程`main`:

```yaml title=".github/workflows/deploy-mastra.yml"
name: Deploy to Mastra platform

on:
  push:
    branches: [main]
    paths: ['src/mastra/**']

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'
      - name: Install dependencies
        run: npm install
      - name: Deploy to Mastra platform
        run: npx mastra deploy --yes
        env:
          MASTRA_API_TOKEN: ${{ secrets.MASTRA_API_TOKEN }}
          MASTRA_ORG_ID: ${{ secrets.MASTRA_ORG_ID }}
          MASTRA_PROJECT_ID: ${{ secrets.MASTRA_PROJECT_ID }}
```

调整`paths` filter and `working-directory` if your Mastra project is in a subdirectory (e.g. a monorepo).

### 亚搏体育appGitLab持续集成 {/* #gitlab-ci */}

以下管道部署在推送上`main`:

```yaml title=".gitlab-ci.yml"
deploy:
  image: node:22
  stage: deploy
  only:
    - main
  before_script:
    - npm install
  script:
    - npx mastra deploy --yes
```

添加`MASTRA_API_TOKEN`, `MASTRA_ORG_ID`, and `MASTRA_PROJECT_ID` as CI/CD variables in **Settings → CI/CD → Variables**.

### 其他 CI Provider {/* #other-ci-providers */}

任何运行 Node.js 和 shell 命令的 CI 系统都可以与 Mastra 配合使用：

1. 安装依赖项。
2. 放`MASTRA_API_TOKEN`, `MASTRA_ORG_ID`, and `MASTRA_PROJECT_ID` as environment variables.
3. 跑步`mastra deploy --yes`.

### 验证部署 {/* #verify-the-deploy */}

Workflow程完成后，通过点击运行状况端点来验证部署：

```bash
curl -f https://<your-project>.server.mastra.cloud/health
```

或者检查Agent端点，它返回Agent的 JSON 列表：

```bash
curl -f https://<your-project>.server.mastra.cloud/api/agents
```

以下示例向 GitHub Actions Workflow程添加验证步骤：

```yaml
- name: Verify deployment
  run: |
    sleep 30
    curl -f https://<your-project>.server.mastra.cloud/health
```

### 使用环境变量覆盖项目配置 {/* #override-project-config-with-environment-variables */}

对于交互式部署，CLI 读取`organizationId` and `projectId` from `.mastra-project.json` by default. When `MASTRA_API_TOKEN` is set, both variables below are required. To override these values (e.g. deploying to a different project from the same repository), set the following environment variables:

|变量|描述 |
| - | - |
|`MASTRA_ORG_ID` | Overrides the organization ID from `.mastra-project.json`. |
| `MASTRA_PROJECT_ID` | Overrides the project ID from `.mastra-project.json`. |
