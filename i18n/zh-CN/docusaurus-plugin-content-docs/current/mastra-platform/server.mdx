# Mastra 平台上的服务器部署

Mastra 平台的 Server 是一种生产部署方式，将 Mastra 应用作为 API 服务器运行。需要平台负责构建、部署、托管和管理 Mastra 服务器时，可以使用此方式。

平台提供稳定的 API 端点，支持管理环境变量和使用自定义域名，并自动保留部署历史。

:::note

部署服务器时，平台会自动预配托管存储。如果你用 [LibSQLStore](/integrations/databases/libsql) 和文件 URL 覆盖了存储配置，请改用远程托管数据库，因为 Mastra 平台使用的是临时文件系统。

:::

## 快速入门 {/* #quickstart */}

<Steps>
  <StepItem>
    按照[入门指南](/docs)创建你的第一个 Mastra 项目。
  </StepItem>

  <StepItem>
    全局安装 `mastra` CLI：

    ```bash npm2yarn
    npm install -g mastra
    ```
  </StepItem>

  <StepItem>
    部署项目：

    ```bash
    mastra deploy
    ```

    如果尚未登录，CLI 会提示你登录。凭据会保存在本地，后续 CLI 命令会继续使用这些凭据。

    该命令会运行 `mastra build` 并上传构建产物，然后构建并部署 Docker 镜像。首次部署时，CLI 会创建 `.mastra-project.json`，关联本地项目与平台上的项目。请提交此文件，让后续部署和 CI/CD 都以同一项目为目标。

    :::note
    CLI 从一个环境变量文件上传变量。若存在 `.env.<environment>`（如默认的 `production` 环境对应的 `.env.production`），就使用它。否则，如果只有一个 `.env` 或 `.env.*` 文件，就使用该文件。如果有多个文件且没有匹配项，CLI 会询问使用哪个文件。在非交互运行中（`--yes` 或 CI），请传入 `--env-file <file>`。也可以用 `--env-file` 覆盖默认选择。每次部署都会将文件中的变量合并到目标环境已保存的变量中。以文件中的值为准，但空值不会清除已保存的值。CLI 会列出将被覆盖的变量名并要求确认，使用 `--yes` 或在 CI 中运行时会跳过确认。若某个变量只想在控制台中管理，请将它从环境变量文件中删除。如果没有环境变量文件，则不会上传任何变量，已保存的变量会保留。
    部署前请检查并清理选定的文件，避免上传仅用于开发的密钥或个人凭据。
    :::

    完整的命令行选项见 [CLI 参考](/reference/cli/mastra#mastra-deploy)。
  </StepItem>

  <StepItem>
    访问 CLI 输出的 URL 验证部署。在 URL 后加上 `/api/agents`，确认它返回包含你的 Agent 的 JSON 列表。

    :::warning
    公开端点前，请先配置[身份验证](/docs/auth/overview)。
    :::
  </StepItem>
</Steps>

## 部署生命周期 {/* #deploy-lifecycle */}

每个项目同一时间只执行一次构建。部署依次经过 **queued → uploading → starting → deploying → running**，也可能进入 **failed**、**cancelled**、**crashed** 或 **stopped**。由 GitHub 触发的部署先从源码构建，因此会在 **queued** 和 **uploading** 之间经过 **building**。有多个部署排队时，只有最新的继续，其余会被取消。运行超过 15 分钟的构建会自动标记为失败。首次部署会预配基础设施，并用本地 `.env` 初始化环境变量。服务器 URL 在多次部署之间保持不变。

## 空闲休眠 {/* #idle-behavior */}

为节省资源，Mastra 平台可以让空闲一段时间的服务进入休眠。平台根据出站网络流量判断服务是否空闲。只有大约 10 分钟未发出任何数据包，服务才会被视为空闲。反复出现的出站流量会重置计时器，使服务保持运行。

服务器一直不休眠，通常是因为后台任务或长连接在定期发送流量。可以检查以下常见原因。

### 持久数据库连接 {/* #persistent-database-connections */}

即使服务器空闲，未关闭的数据库客户端仍会保持连接。许多驱动还会在后台定期 ping 数据库以检查健康状况，这也算出站流量。例如，未关闭的 MongoDB 客户端会保持监控套接字打开，约每 10 秒发送一次心跳。

仅配置连接池回收空闲连接还不够，因为驱动的监控连接仍然打开，会继续发送 ping。要让服务器休眠，请在空闲一段时间后关闭客户端，并在下一次请求到来时重新连接。

:::note
关闭客户端后，服务器唤醒时的第一个请求会有短暂的重连延迟。如果工作负载无法接受这段延迟，请保持连接打开，并避免依赖空闲休眠。
:::

### 定时任务和计时器 {/* #scheduled-tasks-and-timers */}

会发起网络请求的 `setInterval`、cron 任务或轮询循环会让服务器持续运行。如果需要定时执行任务，请将其作为独立服务运行，或使用外部调度器发送请求唤醒服务器。

### 外部 ping 和保活检查 {/* #external-pings-and-keep-alive-checks */}

定期访问服务器的可用性监控、健康检查或保活 ping 会重置空闲计时器。如果希望服务器休眠，请移除这些检查，或将检查间隔延长到空闲窗口之外。

### 可观测性导出器 {/* #observability-exporters */}

向远程端点持续发送 Trace、日志或指标的导出器会产生出站流量。请确认导出器会批量发送，并在服务器空闲时停止发送，避免按固定间隔刷出数据。

### 长时间保持的流 {/* #long-lived-streams */}

服务器发送事件（SSE）流、WebSocket 或其他长连接在关闭之前都会保持通信通道打开。如果流式响应在后台维持订阅，连接就会一直处于活跃状态。请确认客户端断开时会关闭流，并且服务器在其他方面已空闲时，没有流仍然打开。

### 聊天集成 {/* #chat-integrations */}

部分聊天集成会保持长连接，并定期发送心跳，让服务器持续运行。例如，使用 Socket Mode 的 Slack 应用会打开 WebSocket，约每 30 秒发送一次 ping。Discord 机器人则会保持网关 WebSocket 打开，并定时发送心跳。打开的套接字和心跳都会阻止服务器进入空闲状态。

如果希望服务器休眠，且集成支持 HTTP Webhook，可以改用它接收事件。例如，Slack 应用可以通过带请求 URL 的 Events API 接收事件，无需使用 Socket Mode。如果应用需要长连接，请使用下文的 **Persistent Server add-on** 保持服务运行。

### 检查活跃连接 {/* #inspect-active-connections */}

要找出服务器为何一直运行，请在空闲时检查进程中仍活跃的句柄。所有请求结束后仍存在的句柄值得排查。打开的套接字表示有需要关闭的长连接，活跃的计时器则指向 `setInterval` 或反复调度自身的 `setTimeout`。

将以下辅助代码加入应用，流量停止后查看日志。服务器空闲后仍列出的项目，就是使其持续运行的原因：

```typescript title="src/mastra/diagnose-idle.ts"
export function logActiveHandles() {
  // process._getActiveHandles is undocumented but useful for diagnosis.
  const handles = (process as any)._getActiveHandles() as Array<any>

  const summary = handles.map(handle => {
    const type = handle?.constructor?.name ?? typeof handle
    if (type === 'Socket') {
      return `Socket -> ${handle.remoteAddress}:${handle.remotePort}`
    }
    return type
  })

  console.log(`[idle] ${handles.length} active handles:`, summary)
}

// Log every 30 seconds so you can see what persists while the server is idle.
setInterval(logActiveHandles, 30_000).unref()
```

对诊断计时器调用 `unref()`，避免辅助代码本身阻止服务器休眠。

### 保持服务运行 {/* #keep-a-service-running */}

有些应用确实需要上述连接或任务，例如需要维持数据库连接来降低首个请求的延迟，或需要后台调度器、长时间保持的流。如果你的应用有这些需求，请使用 **Persistent Server add-on** 让服务持续运行，避免强制休眠。

启用 **Persistent Server add-on** 后，即使没有流量，服务也会保持运行，长连接、定时任务和已打开的流不会因空闲休眠而中断。

## CI/CD {/* #cicd */}

可以通过 GitHub Actions、GitLab CI 或任意 CI 服务自动部署。首次交互式部署完成后，CI/CD 需要 API 令牌、组织和项目 ID，以及已提交到仓库的 `.mastra-project.json` 文件。

:::tip
如果代码托管在 GitHub，[GitHub 集成](/docs/mastra-platform/github)支持推送即部署，无需编写工作流文件。如果使用 GitLab 或其他 CI 服务，或需要在部署前执行自定义构建步骤，请用下文基于 CLI 的 CI/CD 流程。
:::

### 创建 API 令牌 {/* #create-an-api-token */}

<Steps>
  <StepItem>
    在本地运行以下命令：

    ```bash
    mastra auth tokens create ci-deploy
    ```

    CLI 只显示一次令牌。请立即复制，之后无法再次查看。
  </StepItem>

  <StepItem>
    在 CI 服务中将令牌添加为机密。在 GitHub Actions 中，前往 **Settings → Secrets and variables → Actions**，创建 `MASTRA_API_TOKEN` 机密。
  </StepItem>

  <StepItem>
    确认已将 `.mastra-project.json` 提交到仓库。
  </StepItem>

  <StepItem>
    将 `MASTRA_ORG_ID` 和 `MASTRA_PROJECT_ID` 添加到 CI 服务，值分别取自 `.mastra-project.json` 中的 `organizationId` 和 `projectId`。设置 `MASTRA_API_TOKEN` 后，`mastra deploy` 会以非交互方式运行，缺少任一变量都会失败。
  </StepItem>
</Steps>

### `--yes` 选项 {/* #the---yes-flag */}

传入 `--yes`（或 `-y`）可跳过所有确认提示。省略此选项时，CLI 会等待交互输入，导致 CI 作业卡住。

```bash
mastra deploy --yes
```

### GitHub Actions {/* #github-actions */}

以下工作流会在每次推送到 `main` 时部署：

```yaml title=".github/workflows/deploy-mastra.yml"
name: Deploy to Mastra platform

on:
  push:
    branches: [main]
    paths: ['src/mastra/**']

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'
      - name: Install dependencies
        run: npm install
      - name: Deploy to Mastra platform
        run: npx mastra deploy --yes
        env:
          MASTRA_API_TOKEN: ${{ secrets.MASTRA_API_TOKEN }}
          MASTRA_ORG_ID: ${{ secrets.MASTRA_ORG_ID }}
          MASTRA_PROJECT_ID: ${{ secrets.MASTRA_PROJECT_ID }}
```

如果 Mastra 项目位于子目录中（例如 monorepo），请调整 `paths` 过滤器和 `working-directory`。

### GitLab CI {/* #gitlab-ci */}

以下流水线会在推送到 `main` 时部署：

```yaml title=".gitlab-ci.yml"
deploy:
  image: node:22
  stage: deploy
  only:
    - main
  before_script:
    - npm install
  script:
    - npx mastra deploy --yes
```

在 **Settings → CI/CD → Variables** 中，将 `MASTRA_API_TOKEN`、`MASTRA_ORG_ID` 和 `MASTRA_PROJECT_ID` 添加为 CI/CD 变量。

### 其他 CI 服务 {/* #other-ci-providers */}

任何能运行 Node.js 和 Shell 命令的 CI 系统都可用于部署 Mastra：

1. 安装依赖。
1. 将 `MASTRA_API_TOKEN`、`MASTRA_ORG_ID` 和 `MASTRA_PROJECT_ID` 设置为环境变量。
1. 运行 `mastra deploy --yes`。

### 验证部署 {/* #verify-the-deploy */}

工作流完成后，请访问健康检查端点验证部署：

```bash
curl -f https://<your-project>.server.mastra.cloud/health
```

也可以检查 Agent 端点，该端点会返回包含你的 Agent 的 JSON 列表：

```bash
curl -f https://<your-project>.server.mastra.cloud/api/agents
```

以下示例为 GitHub Actions 工作流添加了验证步骤：

```yaml
- name: Verify deployment
  run: |
    sleep 30
    curl -f https://<your-project>.server.mastra.cloud/health
```

### 使用环境变量覆盖项目配置 {/* #override-project-config-with-environment-variables */}

在交互式部署中，CLI 默认从 `.mastra-project.json` 读取 `organizationId` 和 `projectId`。设置 `MASTRA_API_TOKEN` 时，必须同时设置下列两个变量。要覆盖这些值，例如从同一仓库部署到其他项目，请设置以下环境变量：

| 变量 | 说明 |
| - | - |
| `MASTRA_ORG_ID` | 覆盖 `.mastra-project.json` 中的组织 ID。 |
| `MASTRA_PROJECT_ID` | 覆盖 `.mastra-project.json` 中的项目 ID。 |
