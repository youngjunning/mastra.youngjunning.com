# 处理器

处理器在消息通过Agent时对其进行转换、验证或控制。它们在Agent执行管道中的特定点运行，允许您在输入到达语言模型之前修改输入，或者在输出返回给用户之前修改它们。

处理器配置为：

* **`inputProcessors`**：在消息到达语言模型之前运行。
* **`outputProcessors`**：在语言模型生成响应之后、返回给用户之前运行。

使用个人[`Processor`](/reference/processors/processor-interface) objects, or compose them into workflows with Mastra's workflow primitives. Workflows give you advanced control over execution order and support conditional or parallel processing.

一些处理器同时实现输入和输出逻辑，并且可以在任一阵列中使用，具体取决于转换应该发生的位置。

一些内置处理器还会发送隐藏的系统提醒信号。这些信号保留在原始内存历史中并转换为`<system-reminder>...</system-reminder>` context before the next model call, but standard UI-facing message conversions and default memory recall hide them unless you explicitly opt in. To deliver a signal for the current call without retaining it, send it with `transient: true`.

## 何时使用处理器 {/* #when-to-use-processors */}

使用处理器可以：

* 规范化或验证用户输入
* 为您的Agent添加护栏
* 检测并防止提示注入或越狱尝试
* 出于安全或合规性考虑的适度内容
* 转换消息（例如翻译语言、过滤Tool调用）
* 限制令牌使用或消息历史记录长度
* 编辑敏感信息 (PII)
* 将自定义业务逻辑应用于消息

Mastra 包括多个用于常见用例的处理器。您还可以根据应用程序的特定要求创建自定义处理器。

## 快速入门 {/* #quickstart */}

导入并实例化处理器，然后将其传递给Agent的`inputProcessors` or `outputProcessors` array:

```typescript {2,8-15} title="src/mastra/agents/moderated-agent.ts"
import { Agent } from '@mastra/core/agent'
import { ModerationProcessor } from '@mastra/core/processors'

export const moderatedAgent = new Agent({
  id: 'moderated-agent',
  name: 'moderated-agent',
  instructions: 'You are a helpful assistant',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  inputProcessors: [
    new ModerationProcessor({
      model: '__GATEWAY_OPENAI_MODEL_LUNA__',
      categories: ['hate', 'harassment', 'violence'],
      threshold: 0.7,
      strategy: 'block',
    }),
  ],
})
```

## 执行顺序 {/* #execution-order */}

处理器按照它们在数组中出现的顺序运行：

```typescript
inputProcessors: [new UnicodeNormalizer(), new PromptInjectionDetector(), new ModerationProcessor()]
```

对于输出处理器，顺序决定了应用于模型响应的转换顺序。

### 启用内存后 {/* #with-memory-enabled */}

当Agent上启用内存时，内存处理器会自动添加到管道中：

**输入处理器：**

```text
[Memory Processors] → [Your inputProcessors]
```

内存首先加载消息历史记录，然后处理器运行。

**输出处理器：**

```text
[Your outputProcessors] → [Memory Processors]
```

您的处理器首先运行，然后内存保存消息。

按照此顺序，调用的输出护栏`abort()` skips memory processors and prevents messages from being saved. See [Memory Processors](/docs/memory/memory-processors#processor-execution-order) for details.

## 将处理器附加到Agent {/* #attach-processors-to-an-agent */}

处理器通过三个阵列在Agent上配置：

```typescript
import { Agent } from '@mastra/core/agent'
import { PrefillErrorHandler, TokenLimiter, ModerationProcessor } from '@mastra/core/processors'

const agent = new Agent({
  id: 'support-agent',
  name: 'support-agent',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  instructions: '...',
  inputProcessors: [
    new TokenLimiter(4000),
    new ModerationProcessor({ model: '__GATEWAY_OPENAI_MODEL_LUNA__' }),
  ],
  outputProcessors: [new ModerationProcessor({ model: '__GATEWAY_OPENAI_MODEL_LUNA__' })],
  errorProcessors: [new PrefillErrorHandler()],
})
```

* `inputProcessors`在LLM之前运行。
* `outputProcessors`在 LLM 响应期间和之后运行。
* `errorProcessors`当 LLM API 调用抛出时运行，以便他们可以从提供者错误中恢复。

### 默认情况下启用错误处理器 {/* #error-processors-are-enabled-by-default */}

每个Agent都会添加您的这四个中的任意一个`errorProcessors` list doesn't already contain:

1. `ProviderHistoryCompat`：修复出站提示中特定于Provider的历史记录不兼容问题
2. `PrefillErrorHandler`：从助理响应预填充拒绝中恢复
3. [`UnsupportedFileHandler`](/reference/processors/unsupported-file-handler)：从提示中获取模型拒绝的文件，当有文件时将其上传到Agent的Sandbox，然后再次调用模型
4. `StreamErrorRetryProcessor`：重试短暂的 API 和流失败

仅当列表中没有任何内容时才会添加默认值`id`, so your own instance always wins and is never duplicated. An added default is placed at the position its `id` gives it among the defaults, so naming only a later one doesn't invert the pair. Supplying only your own `StreamErrorRetryProcessor` still resolves with `ProviderHistoryCompat`, `PrefillErrorHandler`, and `UnsupportedFileHandler` ahead of it.

错误处理器在第一个返回时停止`{ retry: true }`, so that relative order decides which repair runs. The default order puts the repairs ahead of the retrying processor. Placed earlier, an instance with broad matchers (the bad-request matcher matches any `400`, for example) would claim a request the repairs could have fixed and resend it unchanged. The default instance retries only transient failures: connection resets, retryable OpenAI stream errors, and errors the provider marks as retryable. Your own instance can be configured with broader matchers. The order keeps repairs ahead of it too.

您的处理器永远不会相对于彼此重新排序。处理器具有`id` that matches a default takes part in that ordering. One with an `id` of your own keeps its position in your list.

要定制一个而不丢失其余部分，请传递具有相同功能的处理器`id`:

```typescript
import { Agent } from '@mastra/core/agent'
import { StreamErrorRetryProcessor } from '@mastra/core/processors'

const agent = new Agent({
  id: 'tuned-agent',
  name: 'tuned-agent',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  instructions: '...',
  errorProcessors: [new StreamErrorRetryProcessor({ maxRetries: 5 })],
  maxProcessorRetries: 5,
})
```

这`StreamErrorRetryProcessor` above is the only stream-retry processor on the agent, and it resolves in its usual position: last, behind the `ProviderHistoryCompat`, `PrefillErrorHandler`, and `UnsupportedFileHandler` defaults your list never names. Pass all four ids to run a completely custom set.

一个处理器的`maxRetries` can't raise the agent's limit. Without `maxProcessorRetries`, error-processor retries stop after `3` (see [Error processor retry limits](#error-processor-retry-limits)), so set it when a processor needs more.

一个空的`errorProcessors` list merges like any other, so it still gets the four defaults. To turn the defaults off, set `errorProcessorDefaults: false`. The agent then runs only the processors you configure, or none when you configure none:

```typescript
new Agent({
  id: 'custom-error-recovery-agent',
  name: 'custom-error-recovery-agent',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  instructions: '...',
  errorProcessorDefaults: false,
  errorProcessors: [new StreamErrorRetryProcessor({ maxRetries: 5 })],
  maxProcessorRetries: 5,
})
```

一个`errorProcessors` list passed to a single `generate()` or `stream()` call works differently: it replaces the agent's resolved list for that call, defaults included.

Agent的内存可以提供自己的错误处理器，例如在请求超出模型的上下文窗口时进行恢复。它们在上面的处理器之后运行，并在调用通过其自己的处理器时保持在原位`errorProcessors` list.

每个数组还接受一个返回数组的函数，因此可以根据请求构建处理器`RequestContext`:

```typescript
new Agent({
  id: 'processors-agent',
  inputProcessors: ({ requestContext }) => {
    const limit = requestContext.get('tokenLimit') ?? 4000
    return [new TokenLimiter(limit)]
  },
})
```

### 每次调用覆盖处理器 {/* #override-processors-per-call */}

`agent.generate()`和`agent.stream()` accept the same three arrays. When you pass one, it **replaces** the matching array on the agent for that call only. Memory, workspace, and other framework-managed processors still run around your array.

```typescript
await agent.stream('Summarize this', {
  inputProcessors: [new TokenLimiter(2000)],
  maxProcessorRetries: 5,
})
```

## 创建自定义处理器 {/* #create-custom-processors */}

定制处理器实现`Processor` interface.

处理器方法接收两个用于访问对话的参数：

* `messages`：快照数组`MastraDBMessage` objects for the current stage.
* `messageList`: 现场直播`MessageList` instance. Use it to read other stages, or to add, remove, or replace messages in place.

文字存在于`message.content.parts`, not on `message.content` itself. Iterate `parts` and filter by `part.type === 'text'` to read user or assistant text. A flattened `message.content.content` string exists for legacy compatibility and can be used as a fallback. See [Message arguments](/reference/processors/processor-interface#message-arguments) in the `Processor` reference for full details.

### 转换输入消息 {/* #transform-input-messages */}

```typescript title="src/mastra/processors/custom-input.ts"
import type { Processor, ProcessInputArgs } from '@mastra/core/processors'
import type { MastraDBMessage } from '@mastra/core/memory'

export class CustomInputProcessor implements Processor {
  id = 'custom-input'

  async processInput({ messages }: ProcessInputArgs): Promise<MastraDBMessage[]> {
    // Transform messages before they reach the LLM.
    // Text lives in content.parts — iterate parts and rewrite text parts only.
    return messages.map(msg => ({
      ...msg,
      content: {
        ...msg.content,
        parts: msg.content.parts?.map(part =>
          part.type === 'text' ? { ...part, text: part.text.toLowerCase() } : part,
        ),
      },
    }))
  }
}
```

这`processInput()` method receives `messages`, `systemMessages`, and an `abort()` function. Return a `MastraDBMessage[]` to replace messages, or `{ messages, systemMessages }` to also modify system messages.

请参阅[`Processor` reference](/reference/processors/processor-interface#processinput) for all available arguments and return types.

### 控制每一步 {/* #control-each-step */}

尽管`processInput()` runs once at the start of agent execution, `processInputStep()` runs at **each step** of the agentic loop (including tool call continuations). It enables per-step configuration changes like runtime model switching or tool choice modifications.

```typescript title="src/mastra/processors/step-processor.ts"
import type {
  Processor,
  ProcessInputStepArgs,
  ProcessInputStepResult,
} from '@mastra/core/processors'

export class DynamicModelProcessor implements Processor {
  id = 'dynamic-model'

  async processInputStep({
    stepNumber,
    model,
    toolChoice,
    messageList,
  }: ProcessInputStepArgs): Promise<ProcessInputStepResult> {
    // Use a fast model for initial response
    if (stepNumber === 0) {
      return { model: '__GATEWAY_OPENAI_MODEL_LUNA__' }
    }

    // Disable tools after 5 steps to force completion
    if (stepNumber > 5) {
      return { toolChoice: 'none' }
    }

    // No changes for other steps
    return {}
  }
}
```

返回`toolChoice: 'none'` stops the model from calling tools but still sends the tool definitions, so earlier tool calls and results stay in the conversation. Mastra only drops the tool definitions when the step also sends a structured-output schema to the model.

该方法接收当前`stepNumber`, `model`, `tools`, `toolChoice`, `messages`, and more. Return an object with any properties you want to override for that step, for example `{ model, toolChoice, tools, systemMessages }`.

请参阅[`Processor` reference](/reference/processors/processor-interface#processinputstep) for all available arguments and return types.

### 在Provider调用之前重写 LLM 请求 {/* #rewrite-the-llm-request-before-the-provider-call */}

使用`processLLMRequest()` when you need to rewrite the final prompt that Mastra sends to the model. This hook runs after Mastra converts the `MessageList` into the provider-facing prompt format (`LanguageModelV2Prompt`) and immediately before the provider call.

使用基于消息的钩子进行对话更改：

* `processInput()`：在Agent循环开始之前更改一次对话。
* `processInputStep()`：在每次 LLM 调用之前更改消息或步骤配置。
* `processLLMRequest()`：仅更改当前Provider呼叫的呼出提示。

返回的更改来自`processLLMRequest()` are transient. They don't persist back to `MessageList`, memory, UI history, or future provider calls. This makes the hook a good fit for provider compatibility rewrites, role/content normalization, or other model-specific prompt changes that shouldn't alter stored conversation history.

该方法接收`prompt`, `model`, `stepNumber`, `steps`, `state`, and the shared processor context. Calling `abort()` from `processLLMRequest()` emits the normal tripwire response and stops the call.

错误处理器也在这条通道上运行。处理器放置在`errorProcessors` that implements `processLLMRequest()` gets the hook, which is what lets the default `ProviderHistoryCompat` repair the outbound prompt rather than waiting for the provider to reject it. Processors whose only hook is `processAPIError()` (`StreamErrorRetryProcessor` and `PrefillErrorHandler`) don't implement this method and are inert here. A processor listed in both `inputProcessors` and `errorProcessors` runs once, in its `inputProcessors` position.

请参阅[`Processor` reference](/reference/processors/processor-interface#processllmrequest) for all available arguments and return types.

### 在Provider致电后根据 LLM 响应采取行动 {/* #act-on-the-llm-response-after-the-provider-call */}

使用`processLLMResponse()` to act on the completed LLM response after the step finishes and stream chunks have been collected. This hook pairs with `processLLMRequest()`: stash state (such as a cache key) in the request hook, then read it back in the response hook to perform side effects like writing to a cache.

这`state` object is the same instance passed to `processLLMRequest()` for the same step. When `fromCache` is `true`, the response was replayed from a cache rather than produced by a live model call, processors that write to a cache should skip writes in this case.

该方法接收`chunks`, `model`, `stepNumber`, `steps`, `state`, `fromCache`, and the shared processor context.

请参阅[`Processor` reference](/reference/processors/processor-interface#processllmresponse) for all available arguments and return types.

### 使用`prepareStep()` callback {/* #use-the-preparestep-callback */}

这`prepareStep()` callback on `generate()` or `stream()` is a shorthand for `processInputStep()`. Internally, Mastra wraps it in a processor that calls your function at each step. It accepts the same arguments and return type as `processInputStep()`, but doesn't require creating a class:

```typescript
await agent.generate('Complex task', {
  prepareStep: async ({ stepNumber, model }) => {
    if (stepNumber === 0) {
      return { model: '__GATEWAY_OPENAI_MODEL_LUNA__' }
    }
    if (stepNumber > 5) {
      return { toolChoice: 'none' }
    }
  },
})
```

### 转换输出消息 {/* #transform-output-messages */}

```typescript title="src/mastra/processors/custom-output.ts"
import type { Processor } from '@mastra/core/processors'
import type { MastraDBMessage } from '@mastra/core/memory'

export class CustomOutputProcessor implements Processor {
  id = 'custom-output'

  async processOutputResult({ messages }): Promise<MastraDBMessage[]> {
    // Transform messages after the LLM generates them
    return messages.filter(msg => msg.role !== 'system')
  }
}
```

该方法还接收一个`result` object with the full generation data, `text`, `usage` (token counts), `finishReason`, and `steps` (each containing `toolCalls`, `toolResults`, etc.). Use it to track usage or inspect tool calls:

```typescript title="src/mastra/processors/usage-tracker.ts"
import type { Processor } from '@mastra/core/processors'

export class UsageTracker implements Processor {
  id = 'usage-tracker'

  async processOutputResult({ messages, result }) {
    console.log(`Tokens: ${result.usage.inputTokens} in, ${result.usage.outputTokens} out`)
    console.log(`Finish reason: ${result.finishReason}`)
    return messages
  }
}
```

### 过滤流输出 {/* #filter-streamed-output */}

这`processOutputStream()` method transforms or filters streaming chunks before they reach the client:

```typescript title="src/mastra/processors/stream-filter.ts"
import type { Processor } from '@mastra/core/processors'
import type { ChunkType } from '@mastra/core/stream'

export class StreamFilter implements Processor {
  id = 'stream-filter'

  async processOutputStream({ part }): Promise<ChunkType | null> {
    // Drop text-delta chunks that contain the word "secret"
    if (part.type === 'text-delta' && part.payload.text.includes('secret')) {
      return null
    }

    // Return the (possibly modified) chunk to emit it
    return part
  }
}
```

返回值：

* 一个`ChunkType` emits that chunk. Return the original `part` to pass it through unchanged.
* `null`或者`undefined` drops the chunk. Both behave the same way, so a method that returns nothing also drops the chunk.
* 丢弃只会影响一个块。要完全停止流，请调用`abort()`.

还可以接收定制`data-*` chunks emitted by tools via `writer.custom()`, set `processDataParts = true` on your processor. This lets you inspect, modify, or block tool-emitted data chunks before they reach the client.

### 验证每个响应 {/* #validate-each-response */}

这`processOutputStep()` method runs after each LLM step, allowing you to validate the response and optionally request a retry:

```typescript title="src/mastra/processors/response-validator.ts"
import type { Processor } from '@mastra/core/processors'

export class ResponseValidator implements Processor {
  id = 'response-validator'

  async processOutputStep({ messages, text, abort, retryCount }) {
    const isValid = await validateResponse(text)

    if (!isValid && retryCount < 3) {
      abort('Response did not meet requirements. Try again.', { retry: true })
    }

    return messages
  }
}
```

返回`messages` to leave the conversation unchanged. Returning `[]` replaces the message list with an empty array, removing the conversation history and the latest response.

有关重试行为的更多信息，请参阅[Retry mechanism](#retry-mechanism) in Advanced patterns.

### 跨块和步骤保留数据 {/* #persist-data-across-chunks-and-steps */}

输出方法接收一个`state` object that persists for the lifetime of one request. State is keyed by the processor's `id`. Each processor sees only its own data, and it's shared between `processOutputStream`, `processOutputStep`, and `processOutputResult`. A new state object is created for every new `agent.generate()` or `agent.stream()` call.

```typescript title="src/mastra/processors/word-counter.ts"
import type { Processor } from '@mastra/core/processors'

export class WordCounter implements Processor {
  id = 'word-counter'

  async processOutputStream({ part, state }) {
    state.wordCount ??= 0
    if (part.type === 'text-delta') {
      state.wordCount += part.payload.text.split(/\s+/).filter(Boolean).length
    }
    return part
  }

  async processOutputResult({ messages, state }) {
    console.log(`Total words: ${state.wordCount}`)
    return messages
  }
}
```

## 内置实用处理器 {/* #built-in-utility-processors */}

Mastra 为常见任务提供实用处理器：

**用于安全和验证处理器**，参见[Guardrails](/docs/agents/guardrails) page for input/output guardrails and moderation processors.
**For memory-specific processors**, see the [Memory Processors](/docs/memory/memory-processors) page for processors that handle message history, semantic recall, and working memory.

### `TokenLimiter` {/* #tokenlimiter */}

当令牌总数超过指定限制时，通过删除旧消息来防止上下文窗口溢出。优先考虑最近的消息并保留系统消息。

```typescript {7}
import { Agent } from '@mastra/core/agent'
import { TokenLimiter } from '@mastra/core/processors'

const agent = new Agent({
  id: 'my-agent',
  name: 'my-agent',
  model: '__GATEWAY_OPENAI_MODEL__',
  inputProcessors: [new TokenLimiter(127000)],
})
```

请参阅[`TokenLimiterProcessor` reference](/reference/processors/token-limiter-processor) for custom encoding, strategy, and count mode options.

### `ToolCallFilter` {/* #toolcallfilter */}

从发送到 LLM 的消息中删除Tool调用和结果，从而节省详细Tool交互的标记。可以选择仅排除特定Tool。此过滤器仅影响 LLM 输入，过滤后的消息仍保存到内存中。

默认情况下，`ToolCallFilter` filters tool calls from prior history and leaves tool calls made during the current agent loop in place. Use `filterAfterToolSteps` to also filter during the loop while preserving the most recent tool-producing steps.

```typescript
new ToolCallFilter({
  filterAfterToolSteps: 2,
})
```

放`preserveModelOutput: true` to keep compact `toModelOutput` history for filtered completed tool results. The filter keeps only the model-facing output and removes raw tool args and raw results.

```typescript
new ToolCallFilter({
  preserveModelOutput: true,
})
```

请参阅[`ToolCallFilter` reference](/reference/processors/tool-call-filter) for configuration options and the [Memory Processors](/docs/memory/memory-processors#manual-control-and-deduplication) page for pre-memory filtering.

### `ToolSearchProcessor` {/* #toolsearchprocessor */}

为具有大型Tool库的Agent启用运行时Tool发现。处理者不是预先提供所有Tool，而是向Agent提供`search_tools` and `load_tool` meta-tools to find and load tools by keyword on demand, reducing context token usage.

请参阅[`ToolSearchProcessor` reference](/reference/processors/tool-search-processor) for configuration options and usage examples.

### `ProviderHistoryCompat` {/* #providerhistorycompat */}

当Agent跨模型提供者重用消息时，处理提供者特定的历史不兼容性。它可以在提供程序调用之前重写出站 LLM 请求，或者从已知的提供程序 API 错误中恢复并重试。

Mastra 将其添加到每个Agent的`errorProcessors` by default. Supply your own instance when you need custom compatibility rules or a predictable position in the list. For Azure OpenAI agents that use observational memory, the processor rewrites `<system-reminder>` wrappers in outbound prompts to avoid content moderation refusals. Stored history remains unchanged.

内置的 Anthropic Tool调用 ID 规则会重写 Anthropic 之外的 ID`^[a-zA-Z0-9_-]+$` pattern in the outbound request only, on both the call and its paired result, so pairing survives. Persisted history keeps the original IDs. Reactive recovery after a failed call stays as the fallback for Claude served through a provider the preemptive check doesn't recognize, such as Vertex.

请参阅[`ProviderHistoryCompat` reference](/reference/processors/provider-history-compat) for setup, built-in rules, and custom rule options.

## 响应缓存 {/* #response-caching */}

:::测试版

在 API 稳定之前，可能会在没有重大版本更新的情况下发生重大更改。

:::

当Agent收到相同的请求时，响应缓存会跳过 LLM 调用并重播之前缓存的响应。使用它可以减少延迟并避免为重复调用付费。

缓存的实现方式为[`ResponseCache`](/reference/processors/response-cache) input processor. Mastra doesn't provide an agent-level option. To enable caching, register the processor explicitly. This keeps the API surface small while Mastra collects feedback. Per-call overrides flow through `RequestContext`.

### 何时使用响应缓存 {/* #when-to-use-response-caching */}

当相同的请求在用户或会话之间重复出现时，请使用缓存。示例包括建议提示按钮和重复搜索，或对相同输入进行分类的护栏法学硕士。当调用通过Tool触发外部副作用时跳过它，因为缓存会重播Tool调用而无需重新执行它们。

### 快速入门 {/* #quickstart-1 */}

添加一个`ResponseCache` to the agent's `inputProcessors` and pass any `MastraServerCache` as the backend. For development, `InMemoryServerCache` works out of the box:

```typescript title="src/mastra/agents/search-agent.ts"
import { Agent } from '@mastra/core/agent'
import { InMemoryServerCache } from '@mastra/core/cache'
import { ResponseCache } from '@mastra/core/processors'

const cache = new InMemoryServerCache()

export const searchAgent = new Agent({
  id: 'search-agent',
  name: 'Search Agent',
  instructions: 'You answer questions concisely.',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  inputProcessors: [new ResponseCache({ cache, ttl: 600 })], // 10 minutes
})
```

第一个调用正常运行 LLM 并将响应写入缓存。具有相同已解决提示的后续调用将返回缓存的响应，而不调用 LLM。

### 通过 RequestContext 进行每次调用覆盖 {/* #per-call-overrides-via-requestcontext */}

每次调用配置流经`RequestContext`. Use `ResponseCache.context()` to build a fresh context, or `ResponseCache.applyContext()` to merge into one you already have:

```typescript title="src/example.ts"
import { ResponseCache } from '@mastra/core/processors'
import { RequestContext } from '@mastra/core/request-context'

// Fresh context with the override
await agent.stream('hello', {
  requestContext: ResponseCache.context({ key: 'custom-key', bust: true }),
})

// Or merge into an existing context
const ctx = new RequestContext()
ctx.set('caller-meta', { userId: 'u-123' })
ResponseCache.applyContext(ctx, { bust: true })
await agent.stream('hello', { requestContext: ctx })
```

这些字段在每次调用时都是可覆盖的：

* `key`：字符串或函数。仅覆盖此请求的自动派生缓存键。
* `scope`: 字符串或`null`. Overrides the tenant/user scope for this request only. `null` opts out of scoping.
* `bust`：布尔值。跳过缓存读取，但完成后仍会写入（对于“强制刷新”按钮很有用）。

`cache`, `ttl`, and `agentId` stay on the constructor. They're instance-level concerns and not safe to vary per call.

### 租户范围 {/* #tenant-scoping */}

默认情况下，`ResponseCache` looks up `MASTRA_RESOURCE_ID_KEY` on the request context and uses it as the cache scope. An agent that already populates the resource id (e.g. via memory) gets per-user isolation automatically. Users never see each other's cached responses.

当您需要不同的范围时显式覆盖：

```typescript title="src/mastra/agents/scoped-agent.ts"
import { Agent } from '@mastra/core/agent'

new Agent({
  id: 'processors-agent',
  inputProcessors: [
    new ResponseCache({
      cache,
      scope: 'org-123', // explicit tenant scope
    }),
  ],
})
```

经过`scope: null` to deliberately share entries across all callers. Only use this for known-public, non-personalized content.

### 自定义缓存后端 {/* #custom-cache-backend */}

`ResponseCache`接受任何`MastraServerCache`. For production, use `RedisServerCache` from `@mastra/redis`:

```typescript title="src/mastra/agents/cached-agent.ts"
import { Agent } from '@mastra/core/agent'
import { ResponseCache } from '@mastra/core/processors'
import { RedisServerCache } from '@mastra/redis'
import { createClient } from 'redis'

const client = createClient({ url: process.env.REDIS_URL })
await client.connect()

const cache = new RedisServerCache({ client })

export const agent = new Agent({
  id: 'cached-agent',
  name: 'Cached Agent',
  instructions: '...',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  inputProcessors: [new ResponseCache({ cache })],
})
```

对于自定义后端，扩展`MastraServerCache` and implement its abstract methods (the processor only calls `get` and `set`).

### 缓存是如何实现的 {/* #how-caching-is-implemented */}

`ResponseCache`钩入`processLLMRequest` (cache lookup, short-circuits on hit) and `processLLMResponse` (cache write on completion). Both run inside the agentic loop *after* memory has loaded and earlier input processors have transformed the prompt.

缓存键源自已解析的`LanguageModelV2Prompt` Mastra is about to send to the model. The key is created *after* memory has loaded and earlier input processors have run, and each step in an agentic tool loop is independently cached.

### 缓存键中有什么 {/* #whats-in-the-cache-key */}

当你不供货时`key`, the processor derives one deterministically from the inputs that change the LLM's response at this step: `agentId`, `stepNumber` (so each step in a tool loop has its own cache entry), `scope`, model identity (`provider`, `modelId`, spec version), and the resolved `prompt` (post-memory + post-processors). Any change to these inputs automatically invalidates the cache.

还包括多模式提示。对于图像和文件部分，密钥包括完整的 URL 或内联二进制数据的字节摘要（`Uint8Array`, `ArrayBuffer`). Requests that differ only in which image they reference therefore get different cache entries.

#### 自定义缓存键 {/* #customize-the-cache-key */}

经过`key` as a function on the constructor or per-call to derive your own cache key from any subset of those inputs. The function receives the same inputs the deterministic hash would have consumed and returns a string (or a `Promise<string>`):

```typescript title="src/example.ts"
import { ResponseCache, buildResponseCacheKey } from '@mastra/core/processors'

await agent.stream(input, {
  requestContext: ResponseCache.context({
    // Cache only on the model id and the resolved prompt tail — ignore
    // step number, scope, etc.
    key: ({ model, prompt }) => `qa:${model.modelId}:${JSON.stringify(prompt).slice(-200)}`,
  }),
})

// Or reuse the deterministic helper while overriding individual fields:
await agent.stream(input, {
  requestContext: ResponseCache.context({
    key: inputs => buildResponseCacheKey({ ...inputs, scope: 'global' }),
  }),
})
```

如果函数抛出异常，处理器将回退到默认的密钥派生，因此调用仍然受益于缓存。

### 缓存命中如何工作 {/* #how-cache-hits-work */}

当处理器发现缓存命中时，它会通过返回缓存块来短路 LLM 调用`processLLMRequest`. The agentic loop synthesizes a stream from those chunks instead of calling the model. `agent.generate()` collects them into a `FullOutput`; `agent.stream()` returns a `MastraModelOutput` whose chunks come from the cached buffer, so consumers iterating `fullStream` or awaiting `text`, `usage`, and `finishReason` see the cached values.

缓存写入发生在响应完成后。失败的运行（错误、绊线激活）不会被缓存。下一个调用会干净地重试。

## 高级模式 {/* #advanced-patterns */}

### 确保最终答复`maxSteps` {/* #ensure-a-final-response-with-maxsteps */}

使用时`maxSteps` to limit agent execution, the agent may return an empty response if it attempts a tool call on the final step. Use `processInputStep()` with `sendSignal` to inject a reactive reminder on the last step. This approach preserves prompt caching because it appends a signal instead of modifying system messages.

```typescript title="src/mastra/processors/ensure-final-response.ts"
import type { Processor, ProcessInputStepArgs } from '@mastra/core/processors'

export class EnsureFinalResponseProcessor implements Processor {
  readonly id = 'ensure-final-response'

  private maxSteps: number

  constructor(maxSteps: number) {
    this.maxSteps = maxSteps
  }

  async processInputStep({ stepNumber, sendSignal }: ProcessInputStepArgs) {
    if (stepNumber !== this.maxSteps - 1) {
      return
    }

    await sendSignal?.({
      type: 'reactive',
      contents:
        `This is your final step (step ${stepNumber + 1} of ${this.maxSteps}). ` +
        `Do not call any more tools. Summarize what you have found and give the user a complete final answer now.`,
      attributes: { reason: 'max-steps-reached', step: stepNumber + 1 },
    })
  }
}
```

信号被传递为`<system-reminder>` user message that the model sees inline:

```xml
<system-reminder reason="max-steps-reached" step="5">This is your final step (step 5 of 5). Do not call any more tools. Summarize what you have found and give the user a complete final answer now.</system-reminder>
```

将处理器添加到`inputProcessors`, include a system prompt explaining the signal tags, and pass the same `maxSteps` value to `generate()` or `stream()`:

```typescript title="src/mastra/agents/index.ts"
import { Agent } from '@mastra/core/agent'
import { EnsureFinalResponseProcessor } from '../processors/ensure-final-response'

const MAX_STEPS = 5

const agent = new Agent({
  id: 'agent',
  instructions: `You are a helpful assistant.

Some messages you receive may contain <system-reminder>...</system-reminder> tags.
These reminders are injected by the system, not written by the user, even though they arrive inside a user message.
Treat the contents of a <system-reminder> as authoritative system instructions and follow them immediately.
Do not mention the reminder to the user or quote the tags back to them.`,
  inputProcessors: [new EnsureFinalResponseProcessor(MAX_STEPS)],
  // ...
})

await agent.generate('Your prompt', { maxSteps: MAX_STEPS })
```

:::注意
无功信号默认为`tagName: 'system-reminder'`. [When the agent sees your input](/docs/signals/sending-signals#when-the-agent-sees-your-input) covers when processor-emitted signals reach the model.
:::

### Tool读取文件后发送上下文 {/* #send-context-after-a-tool-reads-a-file */}

处理器可以一次观察Tool结果并注入后续指令，而不是每一步都注入。此示例发送一个内容`AGENTS.md` file after a tool call reads it, and skips the signal if the same file was already sent. `findAgentsMdPathFromToolCalls()`, `hasAlreadySentAgentsMdReminder()`, and `readAgentsMdInstructions()` are application helpers you write. Mastra doesn't export them.

信号发送自`processInputStep()` follow the same interrupt and wait rules as any other input. The processor finishes before Mastra cancels the request it prepared; output processors settle before the next request, and processor side effects aren't undone. A processor that sends on every pass can duplicate context when a request is replaced, so inspect history and react to a specific trigger.

```typescript title="src/mastra/processors/agents-md-reminder.ts"
import type { Processor, ProcessInputStepArgs } from '@mastra/core/processors'

export const agentsMdReminderProcessor: Processor = {
  id: 'agents-md-reminder',
  async processInputStep({ messageList, sendSignal }: ProcessInputStepArgs) {
    const messages = messageList.get.all.db()
    const agentsMdPath = findAgentsMdPathFromToolCalls(messages)

    if (!agentsMdPath || hasAlreadySentAgentsMdReminder(messages, agentsMdPath)) {
      return messageList
    }

    await sendSignal?.({
      type: 'reactive',
      contents: readAgentsMdInstructions(agentsMdPath),
      attributes: {
        type: 'dynamic-agents-md',
        path: agentsMdPath,
      },
      metadata: {
        path: agentsMdPath,
      },
    })

    return messageList
  },
}
```

该模型接收此上下文为：

```xml
<system-reminder type="dynamic-agents-md" path="packages/ui/AGENTS.md">
  $agentsMdFileContents
</system-reminder>
```

等待中`sendSignal()` preserves stream echo ordering when a subscribed thread is active.

### 发出提醒但不保留 {/* #deliver-a-reminder-without-retaining-it */}

默认情况下，从处理器发送的信号成为对话的一部分：它被写入存储并在稍后的回合中重新输入提示。对于每次都重新注入的指令来说，这是不需要的，因为副本堆积起来，模型开始将自己过去的提醒视为要模仿的先前上下文。放`transient: true` to deliver the signal to the model for the current call only, without retaining it.

**何时使用它：**&#x968F;着对话的增长，您希望在模型的新近度窗口中保留简短的指导指令，例如“继续当前任务”、“将答案保持在三个句子以下”或取决于实时应用程序状态的每轮约束。每轮重新注入它，使其保持在最新消息附近。

```typescript title="src/mastra/processors/steering-reminder.ts" {10}
import type { Processor, ProcessInputStepArgs } from '@mastra/core/processors'

export class SteeringReminderProcessor implements Processor {
  readonly id = 'steering-reminder'

  async processInputStep({ sendSignal }: ProcessInputStepArgs) {
    await sendSignal?.({
      type: 'reactive',
      contents: 'Stay on the current task and keep answers under three sentences.',
      transient: true,
    })
  }
}
```

当前呼叫的提示中仍存在瞬态信号。该模型看到它接近最新转弯。它不会被保留，因此每次重新发送它都会在上下文中保留一个新的副本，而不是累积的历史记录，并且存储的线程历史记录永远不会包含它。由于没有写入任何内容，因此它还可以跨回合保持稳定的提示缓存前缀。

### 发出自定义流事件 {/* #emit-custom-stream-events */}

输出处理器接收`writer` object that lets you emit custom data chunks back to the client during streaming. This is useful for use cases like streaming moderation results or sending UI update signals without blocking the original stream.

```typescript title="src/mastra/processors/moderation-processor.ts" {6,18-25}
import type { Processor } from '@mastra/core/processors'

export class ModerationProcessor implements Processor {
  id = 'moderation'

  async processOutputResult({ messages, writer }) {
    // Run moderation on the final output
    const text = messages
      .filter(m => m.role === 'assistant')
      .flatMap(m => m.content.parts?.filter(p => p.type === 'text'))
      .map(p => p.text)
      .join(' ')

    const result = await runModeration(text)

    if (result.requiresChange) {
      // Emit a custom event to the client with the moderated text
      await writer?.custom({
        type: 'data-moderation-update',
        data: {
          originalText: text,
          moderatedText: result.moderatedText,
          reason: result.reason,
        },
      })
    }

    return messages
  }
}
```

在客户端上，监听流中的自定义块类型：

```typescript
const stream = await agent.stream('Hello')

for await (const chunk of stream.fullStream) {
  if (chunk.type === 'data-moderation-update') {
    // Update the UI with moderated text
    updateDisplayedMessage(chunk.data.moderatedText)
  }
}
```

自定义块类型必须使用`data-` prefix (e.g., `data-moderation-update`, `data-status`).

默认情况下，`processOutputStream()` skips `data-*` chunks so it doesn't accidentally operate on tool telemetry or other processors' output. To inspect, modify, or block these chunks in a processor, set `processDataParts = true` on that processor:

```typescript
class ModerationCollector implements Processor {
  id = 'moderation-collector'
  processDataParts = true

  async processOutputStream({ part, state }) {
    if (part.type === 'data-moderation-update') {
      state.warnings ??= []
      state.warnings.push(part.data)
    }
    return part
  }
}
```

### 向消息添加元数据 {/* #add-metadata-to-messages */}

您可以将自定义元数据添加到消息中`processOutputResult`. This metadata is accessible via the response object:

```typescript title="src/mastra/processors/metadata-processor.ts"
import type { Processor } from '@mastra/core/processors'
import type { MastraDBMessage } from '@mastra/core/memory'

export class MetadataProcessor implements Processor {
  id = 'metadata-processor'

  async processOutputResult({
    messages,
  }: {
    messages: MastraDBMessage[]
  }): Promise<MastraDBMessage[]> {
    return messages.map(msg => {
      if (msg.role === 'assistant') {
        return {
          ...msg,
          content: {
            ...msg.content,
            metadata: {
              ...msg.content.metadata,
              processedAt: new Date().toISOString(),
              customData: 'your data here',
            },
          },
        }
      }
      return msg
    })
  }
}
```

访问元数据`generate()`:

```typescript
const result = await agent.generate('Hello')

// The response includes uiMessages with processor-added metadata
const assistantMessage = result.response?.uiMessages?.find(m => m.role === 'assistant')
console.log(assistantMessage?.metadata?.customData)
```

### 使用Workflow程作为处理器 {/* #use-workflows-as-processors */}

您可以使用 Mastra Workflow程作为处理器来创建具有并行执行和条件分支以及错误处理功能的复杂处理管道：

```typescript title="src/mastra/processors/moderation-workflow.ts"
import { createWorkflow, createStep } from '@mastra/core/workflows'
import {
  ProcessorStepOutputSchema,
  PromptInjectionDetector,
  PIIDetector,
  ModerationProcessor,
} from '@mastra/core/processors'
import { Agent } from '@mastra/core/agent'

// Create a workflow that runs multiple checks in parallel
const moderationWorkflow = createWorkflow({
  id: 'moderation-pipeline',
  inputSchema: ProcessorStepOutputSchema,
  outputSchema: ProcessorStepOutputSchema,
})
  .parallel([
    createStep(
      new PIIDetector({
        model: '__GATEWAY_OPENAI_MODEL_LUNA__',
        strategy: 'redact',
      }),
    ),
    createStep(
      new PromptInjectionDetector({
        model: '__GATEWAY_OPENAI_MODEL_LUNA__',
        strategy: 'block',
      }),
    ),
    createStep(
      new ModerationProcessor({
        model: '__GATEWAY_OPENAI_MODEL_LUNA__',
        strategy: 'block',
      }),
    ),
  ])
  .map(async ({ inputData }) => {
    return inputData['processor:pii-detector']
  })
  .commit()

// Use the workflow as an input processor
const agent = new Agent({
  id: 'moderated-agent',
  name: 'Moderated Agent',
  model: '__GATEWAY_OPENAI_MODEL__',
  inputProcessors: [moderationWorkflow],
})
```

经过一个`.parallel()` step, each branch result is keyed by its processor ID (e.g. `processor:pii-detector`). Use `.map()` to select the branch whose output the next step should receive.

如果一个分支使用像这样的变异策略`redact`, map to that branch so its transformed messages carry forward. If all branches only `block`, any branch works. Pick any one since none of them modify the messages.

当Agent注册到 Mastra 时，处理器Workflow程会自动注册为Workflow程，允许您在[Studio](/docs/studio/overview).

### 重试机制 {/* #retry-mechanism */}

处理者可以请求法学硕士重试其响应并提供反馈。这对于实施质量检查或输出验证非常有用，包括迭代细化：

```typescript title="src/mastra/processors/quality-checker.ts"
import type { Processor } from '@mastra/core/processors'
import { Agent } from '@mastra/core/agent'

export class QualityChecker implements Processor {
  id = 'quality-checker'

  async processOutputStep({ messages, text, abort, retryCount }) {
    const qualityScore = await evaluateQuality(text)

    if (qualityScore < 0.7 && retryCount < 3) {
      // Request a retry with feedback for the LLM
      abort('Response quality score too low. Please provide a more detailed answer.', {
        retry: true,
        metadata: { score: qualityScore },
      })
    }

    return messages
  }
}

const agent = new Agent({
  id: 'quality-agent',
  name: 'Quality Agent',
  model: '__GATEWAY_OPENAI_MODEL__',
  outputProcessors: [new QualityChecker()],
  maxProcessorRetries: 3, // Step retry limit for processInputStep/processOutputStep. Unset by default, which disables those retries.
})
```

重试机制：

* 工作于`processOutputStep()` and `processInputStep()` methods
* 重播该步骤，并将中止原因逐字附加到对话末尾作为系统提醒。重试保留先前的请求作为其前缀，这保留了提供程序提示缓存
* 通过跟踪重试计数`retryCount` parameter
* 需要明确的`maxProcessorRetries` limit on the agent or call

### 错误处理器重试限制 {/* #error-processor-retry-limits */}

`processAPIError()`有单独的重试预算。什么时候`errorProcessors` resolve to a non-empty list and `maxProcessorRetries` is omitted, the runtime allows up to `3` error-processor retries. Error processors are enabled by default on every agent (see [Error processors are enabled by default](#error-processors-are-enabled-by-default)), but `maxProcessorRetries` itself stays unset, so `processInputStep()` and `processOutputStep()` retries still need an explicit limit.

为了`StreamErrorRetryProcessor`, its own `maxRetries` (default `1`) bounds retries independently of the agent cap. Keep model retries at `0` when the processor is the only retry mechanism for a request.

### 违规回调 {/* #violation-callbacks */}

所有处理器都暴露一个`onViolation` property that fires whenever a policy violation is detected, both when `abort()` is called (block strategy) and when a processor issues a warning (warn strategy). Use it for alerting, logging, or side effects without affecting the processor's main logic:

```typescript title="src/mastra/processors/violation-logging.ts"
import { ModerationProcessor, TokenCostControl } from '@mastra/core/processors'

const moderation = new ModerationProcessor({
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  strategy: 'block',
})

moderation.onViolation = ({ processorId, message, detail }) => {
  // Log to external monitoring, send alerts, update dashboards
  monitor.track('processor_violation', { processorId, message, detail })
}

const tokenCostControl = new TokenCostControl({
  maxCost: 10.0,
  scope: 'resource',
  window: '30d',
})

tokenCostControl.onViolation = ({ processorId, message, detail }) => {
  alertSystem.notify(`[${processorId}] ${message}`)
}
```

回调收到一个`ProcessorViolation` object with:

* `processorId`：检测到违规的处理器的 ID
* `message`：对所侵犯内容的人类可读的描述
* `detail`：特定于处理器的元数据（例如成本使用情况、检测到的 PII 类型、审核类别）

`onViolation`是基地的一部分[`Processor` interface](/reference/processors/processor-interface), so any custom processor can use it too. The runner automatically invokes it when any processor calls `abort()`. Errors thrown inside the callback are caught to prevent interfering with the processor pipeline.

### 中止和绊线块 {/* #abort-and-tripwire-chunks */}

呼唤`abort(reason, options)` throws a `TripWire` error that ends processing. On streams, Mastra emits a `tripwire` chunk clients can detect:

```typescript oxfmt:false
for await (const chunk of stream.fullStream) {
  if (chunk.type === 'tripwire') {
    console.log('Blocked by', chunk.payload.processorId, '-', chunk.payload.reason)
    break
  }
}
```

为了`agent.generate()`, the result exposes the same information as `result.tripwire` with `result.finishReason === 'other'`.

`abort`接受第二个选项参数：

* `retry: true`要求Agent重试而不是结束。输入和输出处理器重试需要`maxProcessorRetries` to be set on the agent or call.
* `metadata`将结构化数据附加到`tripwire` chunk so downstream consumers can branch on categories like `pii`, `quality`, or `moderation`.

## API错误处理 {/* #api-error-handling */}

这`processAPIError` method handles LLM API rejections, errors where the API rejects the request (such as 400 or 422 status codes) rather than network or server failures. This lets you modify the request and retry when the API rejects the message format.

```typescript title="src/mastra/processors/api-error-handler.ts"
import { APICallError } from '@ai-sdk/provider'
import type { Processor, ProcessAPIErrorArgs, ProcessAPIErrorResult } from '@mastra/core/processors'

export class ContextLengthHandler implements Processor {
  id = 'context-length-handler'

  processAPIError({
    error,
    messageList,
    retryCount,
  }: ProcessAPIErrorArgs): ProcessAPIErrorResult | void {
    if (retryCount > 0) return

    if (APICallError.isInstance(error) && error.message.includes('context length exceeded')) {
      const messages = messageList.get.all.db()
      if (messages.length > 4) {
        messageList.removeByIds([messages[1]!.id, messages[2]!.id])
        return { retry: true }
      }
    }
  }
}
```

Mastra 包括一个内置[`PrefillErrorHandler`](/reference/processors/prefill-error-handler) that automatically handles the Anthropic "assistant message prefill" error. This processor is auto-injected and requires no configuration.

### 从附件下载失败中恢复 {/* #recover-from-attachment-download-failures */}

当模型本身无法获取附件 URL 时，Mastra 会在调用模型之前下载附件。如果下载失败，`processAPIError()` receives a `MastraError` with the id `DOWNLOAD_ASSETS_FAILED` and the attachment URL in `error.details.url`. An error processor can use this to replace the attachment, for example with a fresh signed URL, and return `{ retry: true }`. Fallback models get a chance next.

如果没有任何东西恢复下载，Agent不会失败。它重试一次，附件替换为`[Attachment unavailable: <name>]` text placeholder and logs a warning. Mastra records the URL on the stored user message under `metadata.mastra.unavailableAttachments`. Later turns show the same placeholder without downloading the attachment again. The attachment itself stays in the thread's history.

无法解码的数据 URL 会立即替换为占位符，因为重试无法修复它。

## 接收后台工作通知 {/* #receive-background-work-notifications */}

使用`createBackgroundWorkSignalProcessor()` to retain the active caller's signal capability for eligible background tool calls:

```typescript
import { Agent } from '@mastra/core/agent'
import { createBackgroundWorkSignalProcessor } from '@mastra/core/processors'

const agent = new Agent({
  id: 'background-agent',
  name: 'Background agent',
  instructions: 'Complete tasks using the available tools.',
  model: '__GATEWAY_OPENAI_MODEL__',
  inputProcessors: [createBackgroundWorkSignalProcessor()],
})
```

Mastra 的后台运行时仍然负责执行、持久性、重试、结果协调和延续。处理器仅保留调用者范围的通知访问权限。当后台工作开始时，它会发出`work-deferred` or `work-awaited` with `status: 'running'`. After the authoritative tool result is reconciled, it emits `work-completed` or `work-failed`.

通知是进程本地的并且尽力而为。如果原始运行已结束或无法传递信号（例如，因为任务在另一个进程上恢复），Mastra 会保留权威结果，而无需重新创建运行或重试通知。前台调用永远不会发出后台工作通知，因为没有独立的工作需要报告。
