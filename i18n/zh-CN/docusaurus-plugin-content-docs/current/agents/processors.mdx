# 处理器

处理器用于在消息经过 Agent 时进行转换、验证或控制。它们在 Agent 执行流程的特定阶段运行，因此你可以在消息到达语言模型之前修改输入，或在响应返回用户之前修改输出。

处理器分为：

* **`inputProcessors`**：在消息到达语言模型前运行。
* **`outputProcessors`**：在语言模型生成响应后、返回用户前运行。

可以使用单个 [`Processor`](/reference/processors/processor-interface) 对象，也可以使用 Mastra 的 Workflow 原语将多个处理器组合为 Workflow。Workflow 能更细致地控制执行顺序，并支持条件处理或并行处理。

有些处理器同时实现了输入和输出逻辑；应根据转换发生的阶段，将其放入相应的数组。

有些内置处理器还会发送隐藏的系统提醒信号。信号会保存在原始 Memory 历史中，并在下次模型调用前转换为 `<system-reminder>...</system-reminder>` 上下文；标准的面向 UI 的消息转换和默认 Memory 召回会隐藏这些信号，除非你明确选择包含它们。若只需在本次调用中传递信号而不保留它，请设置 `transient: true`。

## 何时使用处理器 {/* #when-to-use-processors */}

使用处理器可以：

* 规范化或验证用户输入
* 为 Agent 添加防护规则
* 检测并阻止提示注入或越狱尝试
* 审核内容以满足安全或合规要求
* 转换消息（例如翻译语言、过滤工具调用）
* 限制 Token 用量或消息历史长度
* 脱敏个人身份信息（PII）
* 对消息应用自定义业务逻辑

Mastra 内置了适用于常见场景的处理器。你也可以根据应用需求创建自定义处理器。

## 快速开始 {/* #quickstart */}

导入并实例化处理器，然后将其传给 Agent 的 `inputProcessors` 或 `outputProcessors` 数组：

```typescript {2,8-15} title="src/mastra/agents/moderated-agent.ts"
import { Agent } from '@mastra/core/agent'
import { ModerationProcessor } from '@mastra/core/processors'

export const moderatedAgent = new Agent({
  id: 'moderated-agent',
  name: 'moderated-agent',
  instructions: 'You are a helpful assistant',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  inputProcessors: [
    new ModerationProcessor({
      model: '__GATEWAY_OPENAI_MODEL_LUNA__',
      categories: ['hate', 'harassment', 'violence'],
      threshold: 0.7,
      strategy: 'block',
    }),
  ],
})
```

## 执行顺序 {/* #execution-order */}

处理器按其在数组中的顺序运行：

```typescript
inputProcessors: [new UnicodeNormalizer(), new PromptInjectionDetector(), new ModerationProcessor()]
```

对于输出处理器，这个顺序决定模型响应经过各项转换的先后。

### 启用 Memory 时 {/* #with-memory-enabled */}

如果 Agent 启用了 Memory，Memory 处理器会自动加入执行流程：

**输入处理器：**

```text
[Memory Processors] → [Your inputProcessors]
```

Memory 先加载消息历史，再运行你的处理器。

**输出处理器：**

```text
[Your outputProcessors] → [Memory Processors]
```

你的处理器先运行，然后 Memory 保存消息。

按照这个顺序，如果输出防护处理器调用 `abort()`，后续 Memory 处理器就不会运行，消息也不会保存。详见 [Memory 处理器](/docs/memory/memory-processors#processor-execution-order)。

## 为 Agent 添加处理器 {/* #attach-processors-to-an-agent */}

通过三个数组为 Agent 配置处理器：

```typescript
import { Agent } from '@mastra/core/agent'
import { PrefillErrorHandler, TokenLimiter, ModerationProcessor } from '@mastra/core/processors'

const agent = new Agent({
  id: 'support-agent',
  name: 'support-agent',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  instructions: '...',
  inputProcessors: [
    new TokenLimiter(4000),
    new ModerationProcessor({ model: '__GATEWAY_OPENAI_MODEL_LUNA__' }),
  ],
  outputProcessors: [new ModerationProcessor({ model: '__GATEWAY_OPENAI_MODEL_LUNA__' })],
  errorProcessors: [new PrefillErrorHandler()],
})
```

* `inputProcessors` 在 LLM 调用之前运行。
* `outputProcessors` 在 LLM 响应生成期间及生成后运行。
* `errorProcessors` 在 LLM API 调用抛错时运行，可用于从 Provider 错误中恢复。

### 默认启用错误处理器 {/* #error-processors-are-enabled-by-default */}

每个 Agent 都会补上 `errorProcessors` 列表中缺少的以下四种默认处理器：

1. `ProviderHistoryCompat`：修复发往 Provider 的提示词中与其历史消息格式不兼容的问题
2. `PrefillErrorHandler`：处理 Provider 拒绝预填充助理响应的情况
3. [`UnsupportedFileHandler`](/reference/processors/unsupported-file-handler)：从提示词中移除模型拒绝的文件；如果 Agent 有 Sandbox，则将文件上传到其中，再次调用模型
4. `StreamErrorRetryProcessor`：重试暂时性的 API 和流式处理失败

只有列表中没有相同 `id` 的处理器时，Mastra 才会添加默认实例；因此自定义实例优先，且不会重复。新增的默认处理器会按其 `id` 在默认顺序中定位，所以只指定靠后的处理器不会颠倒前面处理器的顺序。例如，只提供自定义 `StreamErrorRetryProcessor` 时，`ProviderHistoryCompat`、`PrefillErrorHandler` 和 `UnsupportedFileHandler` 仍会排在它前面。

错误处理器在第一个返回 `{ retry: true }` 的处理器处停止，因此相对顺序决定由谁修复错误。默认顺序会先尝试修复，再执行重试。如果将匹配范围较广的实例放在前面（例如错误请求匹配器会匹配任意 `400`），它可能抢先处理本可修复的请求，并原样重发。默认重试实例只处理暂时性故障：连接重置、可重试的 OpenAI 流错误，以及 Provider 标记为可重试的错误。你可以为自己的实例配置更广泛的匹配规则；上述顺序仍会让修复处理器先运行。

你提供的处理器之间不会重新排序。`id` 与默认处理器相同的实例会参与默认顺序；使用自定义 `id` 的实例则保留在列表中的位置。

要替换某个默认处理器而保留其他默认处理器，请传入具有相同 `id` 的实例：

```typescript
import { Agent } from '@mastra/core/agent'
import { StreamErrorRetryProcessor } from '@mastra/core/processors'

const agent = new Agent({
  id: 'tuned-agent',
  name: 'tuned-agent',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  instructions: '...',
  errorProcessors: [new StreamErrorRetryProcessor({ maxRetries: 5 })],
  maxProcessorRetries: 5,
})
```

上面的 `StreamErrorRetryProcessor` 是 Agent 中唯一的流错误重试处理器，它仍排在通常的位置，即列表未指定的 `ProviderHistoryCompat`、`PrefillErrorHandler` 和 `UnsupportedFileHandler` 默认实例之后。若要完全自定义这组处理器，请显式提供全部四个 ID。

处理器自身的 `maxRetries` 不能提高 Agent 的重试上限。未设置 `maxProcessorRetries` 时，错误处理器最多重试 `3` 次（参阅[错误处理器的重试限制](#error-processor-retry-limits)）；需要更多重试时，请同时设置该参数。

空的 `errorProcessors` 列表也会与默认处理器合并，因此仍会得到四个默认实例。要关闭默认实例，设置 `errorProcessorDefaults: false`。此时 Agent 只运行显式配置的处理器；如果没有配置，则不会运行任何错误处理器：

```typescript
new Agent({
  id: 'custom-error-recovery-agent',
  name: 'custom-error-recovery-agent',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  instructions: '...',
  errorProcessorDefaults: false,
  errorProcessors: [new StreamErrorRetryProcessor({ maxRetries: 5 })],
  maxProcessorRetries: 5,
})
```

单次 `generate()` 或 `stream()` 调用传入的 `errorProcessors` 列表不同：它会替换该次调用中 Agent 已解析的完整列表，包括默认处理器。

Agent 的 Memory 也可能提供自己的错误处理器，例如在请求超出模型上下文窗口时恢复。这些处理器在上述处理器之后运行，即使单次调用传入自定义 `errorProcessors` 列表，也会保持原位。

每个数组也可以接受返回数组的函数，以便根据 `RequestContext` 为每次请求构建处理器：

```typescript
new Agent({
  id: 'processors-agent',
  inputProcessors: ({ requestContext }) => {
    const limit = requestContext.get('tokenLimit') ?? 4000
    return [new TokenLimiter(limit)]
  },
})
```

### 覆盖单次调用的处理器 {/* #override-processors-per-call */}

`agent.generate()` 和 `agent.stream()` 都接受上述三个数组。传入任一数组时，该数组只会在本次调用中**替换** Agent 上对应的数组。Memory、Workspace 及其他由框架管理的处理器仍会在其周围运行。

```typescript
await agent.stream('Summarize this', {
  inputProcessors: [new TokenLimiter(2000)],
  maxProcessorRetries: 5,
})
```

## 创建自定义处理器 {/* #create-custom-processors */}

自定义处理器需要实现 `Processor` 接口。

处理器方法接收两个用于访问对话的参数：

* `messages`：当前阶段的 `MastraDBMessage` 对象快照数组。
* `messageList`：实时的 `MessageList` 实例，可用于读取其他阶段的消息，或直接添加、删除、替换消息。

文本位于 `message.content.parts`，而非 `message.content` 本身。读取用户或助理文本时，应遍历 `parts` 并筛选 `part.type === 'text'`。为兼容旧版本，还可以在必要时使用扁平化的 `message.content.content` 字符串。完整说明见 `Processor` 参考文档中的[消息参数](/reference/processors/processor-interface#message-arguments)。

### 转换输入消息 {/* #transform-input-messages */}

```typescript title="src/mastra/processors/custom-input.ts"
import type { Processor, ProcessInputArgs } from '@mastra/core/processors'
import type { MastraDBMessage } from '@mastra/core/memory'

export class CustomInputProcessor implements Processor {
  id = 'custom-input'

  async processInput({ messages }: ProcessInputArgs): Promise<MastraDBMessage[]> {
    // Transform messages before they reach the LLM.
    // Text lives in content.parts — iterate parts and rewrite text parts only.
    return messages.map(msg => ({
      ...msg,
      content: {
        ...msg.content,
        parts: msg.content.parts?.map(part =>
          part.type === 'text' ? { ...part, text: part.text.toLowerCase() } : part,
        ),
      },
    }))
  }
}
```

`processInput()` 方法接收 `messages`、`systemMessages` 和 `abort()` 函数。返回 `MastraDBMessage[]` 可替换消息；返回 `{ messages, systemMessages }` 还能修改系统消息。

所有可用参数和返回类型见 [`Processor` 参考文档](/reference/processors/processor-interface#processinput)。

### 控制每一步 {/* #control-each-step */}

`processInput()` 只在 Agent 执行开始时运行一次，而 `processInputStep()` 会在 Agent 循环的**每一步**运行，包括工具调用后的续执行步骤。它可以逐步修改配置，例如在运行时切换模型或调整工具选择。

```typescript title="src/mastra/processors/step-processor.ts"
import type {
  Processor,
  ProcessInputStepArgs,
  ProcessInputStepResult,
} from '@mastra/core/processors'

export class DynamicModelProcessor implements Processor {
  id = 'dynamic-model'

  async processInputStep({
    stepNumber,
    model,
    toolChoice,
    messageList,
  }: ProcessInputStepArgs): Promise<ProcessInputStepResult> {
    // Use a fast model for initial response
    if (stepNumber === 0) {
      return { model: '__GATEWAY_OPENAI_MODEL_LUNA__' }
    }

    // Disable tools after 5 steps to force completion
    if (stepNumber > 5) {
      return { toolChoice: 'none' }
    }

    // No changes for other steps
    return {}
  }
}
```

返回 `toolChoice: 'none'` 会阻止模型调用工具，但工具定义仍会发送给模型，因此先前的工具调用及结果仍留在对话中。只有该步骤还向模型发送结构化输出 Schema 时，Mastra 才会移除工具定义。

该方法接收当前的 `stepNumber`、`model`、`tools`、`toolChoice`、`messages` 等参数。返回对象即可覆盖本步骤所需的属性，例如 `{ model, toolChoice, tools, systemMessages }`。

所有可用参数和返回类型见 [`Processor` 参考文档](/reference/processors/processor-interface#processinputstep)。

### 在调用 Provider 前重写 LLM 请求 {/* #rewrite-the-llm-request-before-the-provider-call */}

需要改写 Mastra 最终发送给模型的提示词时，使用 `processLLMRequest()`。这个 Hook 在 Mastra 将 `MessageList` 转换为面向 Provider 的提示词格式（`LanguageModelV2Prompt`）之后、调用 Provider 之前运行。

如需修改对话，可使用基于消息的 Hook：

* `processInput()`：在 Agent 循环开始前修改一次对话。
* `processInputStep()`：在每次 LLM 调用前修改消息或步骤配置。
* `processLLMRequest()`：只修改当前 Provider 调用的出站提示词。

`processLLMRequest()` 返回的更改是临时的，不会写回 `MessageList`、Memory、UI 历史或之后的 Provider 调用。因此，这个 Hook 适合处理 Provider 兼容性、规范化角色和内容，或进行无需改动已存储对话历史的模型专用提示词改写。

该方法接收 `prompt`、`model`、`stepNumber`、`steps`、`state` 和共享的处理器上下文。在 `processLLMRequest()` 中调用 `abort()` 会发出常规的 tripwire 响应并停止调用。

错误处理器也会经过这一阶段。放在 `errorProcessors` 中且实现了 `processLLMRequest()` 的处理器会收到该 Hook；默认的 `ProviderHistoryCompat` 因此可以在请求发出前修复提示词，而不必等 Provider 拒绝。只实现 `processAPIError()` 的处理器（`StreamErrorRetryProcessor` 和 `PrefillErrorHandler`）在此阶段不会起作用。若同一个处理器同时列于 `inputProcessors` 和 `errorProcessors`，它只会按 `inputProcessors` 中的位置运行一次。

所有可用参数和返回类型见 [`Processor` 参考文档](/reference/processors/processor-interface#processllmrequest)。

### 在调用 Provider 后处理 LLM 响应 {/* #act-on-the-llm-response-after-the-provider-call */}

在步骤结束、流块收集完毕后，可以通过 `processLLMResponse()` 处理完整的 LLM 响应。这个 Hook 与 `processLLMRequest()` 配合：先在请求 Hook 中保存状态（例如缓存键），再在响应 Hook 中读取，并执行写入缓存等副作用。

同一步骤中的 `state` 与传给 `processLLMRequest()` 的是同一个对象。如果 `fromCache` 为 `true`，响应是从缓存重放的，而非由实时模型调用产生；写缓存的处理器应跳过此次写入。

该方法接收 `chunks`、`model`、`stepNumber`、`steps`、`state`、`fromCache` 以及共享的处理器上下文。

所有可用参数和返回类型见 [`Processor` 参考文档](/reference/processors/processor-interface#processllmresponse)。

### 使用 `prepareStep()` 回调 {/* #use-the-preparestep-callback */}

`generate()` 或 `stream()` 的 `prepareStep()` 回调是 `processInputStep()` 的简便写法。Mastra 会在内部将其包装成逐步调用该函数的处理器。它接受与 `processInputStep()` 相同的参数并返回同类结果，无需创建类。

```typescript
await agent.generate('Complex task', {
  prepareStep: async ({ stepNumber, model }) => {
    if (stepNumber === 0) {
      return { model: '__GATEWAY_OPENAI_MODEL_LUNA__' }
    }
    if (stepNumber > 5) {
      return { toolChoice: 'none' }
    }
  },
})
```

### 转换输出消息 {/* #transform-output-messages */}

```typescript title="src/mastra/processors/custom-output.ts"
import type { Processor } from '@mastra/core/processors'
import type { MastraDBMessage } from '@mastra/core/memory'

export class CustomOutputProcessor implements Processor {
  id = 'custom-output'

  async processOutputResult({ messages }): Promise<MastraDBMessage[]> {
    // Transform messages after the LLM generates them
    return messages.filter(msg => msg.role !== 'system')
  }
}
```

该方法还会收到包含完整生成数据的 `result` 对象，包括 `text`、`usage`（Token 计数）、`finishReason` 和 `steps`（各步骤含 `toolCalls`、`toolResults` 等）。可用它跟踪用量或检查工具调用：

```typescript title="src/mastra/processors/usage-tracker.ts"
import type { Processor } from '@mastra/core/processors'

export class UsageTracker implements Processor {
  id = 'usage-tracker'

  async processOutputResult({ messages, result }) {
    console.log(`Tokens: ${result.usage.inputTokens} in, ${result.usage.outputTokens} out`)
    console.log(`Finish reason: ${result.finishReason}`)
    return messages
  }
}
```

### 过滤流式输出 {/* #filter-streamed-output */}

`processOutputStream()` 方法在流块到达客户端前进行转换或过滤：

```typescript title="src/mastra/processors/stream-filter.ts"
import type { Processor } from '@mastra/core/processors'
import type { ChunkType } from '@mastra/core/stream'

export class StreamFilter implements Processor {
  id = 'stream-filter'

  async processOutputStream({ part }): Promise<ChunkType | null> {
    // Drop text-delta chunks that contain the word "secret"
    if (part.type === 'text-delta' && part.payload.text.includes('secret')) {
      return null
    }

    // Return the (possibly modified) chunk to emit it
    return part
  }
}
```

返回值：

* 返回 `ChunkType` 会发出该流块。返回原始 `part` 则可原样传递。
* 返回 `null` 或 `undefined` 会丢弃流块。两者效果相同，因此方法没有返回值也会丢弃流块。
* 丢弃只影响当前流块。如需完全停止流，请调用 `abort()`。

若还需接收工具通过 `writer.custom()` 发出的自定义 `data-*` 流块，请在处理器上设置 `processDataParts = true`。这样可以在它们到达客户端前检查、修改或拦截。

### 验证每个响应 {/* #validate-each-response */}

`processOutputStep()` 在每个 LLM 步骤后运行，可用于验证响应，并按需请求重试：

```typescript title="src/mastra/processors/response-validator.ts"
import type { Processor } from '@mastra/core/processors'

export class ResponseValidator implements Processor {
  id = 'response-validator'

  async processOutputStep({ messages, text, abort, retryCount }) {
    const isValid = await validateResponse(text)

    if (!isValid && retryCount < 3) {
      abort('Response did not meet requirements. Try again.', { retry: true })
    }

    return messages
  }
}
```

返回 `messages` 会保持对话不变。返回 `[]` 则会将消息列表替换为空数组，清除对话历史和最新响应。

更多重试行为见高级模式中的[重试机制](#retry-mechanism)。

### 跨块和步骤保留数据 {/* #persist-data-across-chunks-and-steps */}

输出方法会收到一个在单次请求期间持续存在的 `state` 对象。状态按处理器的 `id` 隔离：每个处理器只能看到自己的数据，但同一处理器的 `processOutputStream`、`processOutputStep` 和 `processOutputResult` 会共享它。每次调用 `agent.generate()` 或 `agent.stream()` 都会创建新状态对象。

```typescript title="src/mastra/processors/word-counter.ts"
import type { Processor } from '@mastra/core/processors'

export class WordCounter implements Processor {
  id = 'word-counter'

  async processOutputStream({ part, state }) {
    state.wordCount ??= 0
    if (part.type === 'text-delta') {
      state.wordCount += part.payload.text.split(/\s+/).filter(Boolean).length
    }
    return part
  }

  async processOutputResult({ messages, state }) {
    console.log(`Total words: ${state.wordCount}`)
    return messages
  }
}
```

## 内置实用处理器 {/* #built-in-utility-processors */}

Mastra 为常见任务提供实用处理器：

**安全与验证处理器**：输入和输出防护规则及内容审核处理器见[防护规则](/docs/agents/guardrails)。
**Memory 专用处理器**：管理消息历史、语义召回和工作记忆的处理器见 [Memory 处理器](/docs/memory/memory-processors)。

### `TokenLimiter` {/* #tokenlimiter */}

当总 Token 数超过指定上限时，`TokenLimiter` 会删除较早的消息，以免超出上下文窗口。它优先保留近期消息和系统消息。

```typescript {7}
import { Agent } from '@mastra/core/agent'
import { TokenLimiter } from '@mastra/core/processors'

const agent = new Agent({
  id: 'my-agent',
  name: 'my-agent',
  model: '__GATEWAY_OPENAI_MODEL__',
  inputProcessors: [new TokenLimiter(127000)],
})
```

有关自定义编码、策略及计数模式的选项，请参阅 [`TokenLimiterProcessor` 参考文档](/reference/processors/token-limiter-processor)。

### `ToolCallFilter` {/* #toolcallfilter */}

`ToolCallFilter` 会从发送给 LLM 的消息中移除工具调用及其结果，减少冗长工具交互占用的 Token。也可以只过滤指定工具。该过滤器只影响 LLM 输入；过滤后的消息仍会保存到 Memory。

默认情况下，`ToolCallFilter` 过滤历史工具调用，但保留当前 Agent 循环中产生的调用。设置 `filterAfterToolSteps` 后，也可在循环期间过滤，同时保留最近几个产生工具结果的步骤。

```typescript
new ToolCallFilter({
  filterAfterToolSteps: 2,
})
```

设置 `preserveModelOutput: true`，可为已完成且被过滤的工具结果保留简短的 `toModelOutput` 历史。过滤器只保留面向模型的输出，移除原始工具参数和结果。

```typescript
new ToolCallFilter({
  preserveModelOutput: true,
})
```

有关配置选项，请参阅 [`ToolCallFilter` 参考文档](/reference/processors/tool-call-filter)；有关 Memory 处理前的过滤，请参阅 [Memory 处理器](/docs/memory/memory-processors#manual-control-and-deduplication)。

### `ToolSearchProcessor` {/* #toolsearchprocessor */}

`ToolSearchProcessor` 让拥有大量工具的 Agent 能在运行时发现工具。它不预先提供所有工具，而是提供 `search_tools` 和 `load_tool` 元工具，让 Agent 按关键词查找并按需加载，减少上下文中的 Token 用量。

有关配置和用法示例，请参阅 [`ToolSearchProcessor` 参考文档](/reference/processors/tool-search-processor)。

### `ProviderHistoryCompat` {/* #providerhistorycompat */}

当 Agent 在不同模型 Provider 之间复用消息时，`ProviderHistoryCompat` 会处理 Provider 特有的历史格式不兼容问题。它可以在调用 Provider 前改写出站 LLM 请求，也可以从已知的 Provider API 错误中恢复并重试。

Mastra 默认将它加入每个 Agent 的 `errorProcessors`。如果需要自定义兼容规则或控制它在列表中的位置，可以提供自己的实例。对于使用 Observational Memory 的 Azure OpenAI Agent，该处理器会改写出站提示词中的 `<system-reminder>` 包装标签，避免触发内容审核拒绝；已存储的历史不变。

内置的 Anthropic 工具调用 ID 规则只会在出站请求中改写不符合 Anthropic `^[a-zA-Z0-9_-]+$` 格式的 ID，并同步改写调用及其对应结果，以维持配对关系。持久化历史保留原始 ID。对于经由预检查无法识别的 Provider（如 Vertex）提供的 Claude，调用失败后的响应式恢复仍是兜底机制。

有关配置、内置规则和自定义规则选项，请参阅 [`ProviderHistoryCompat` 参考文档](/reference/processors/provider-history-compat)。

## 响应缓存 {/* #response-caching */}

:::beta

在 API 稳定之前，即使不升级主版本，也可能出现破坏性变更。

:::

当 Agent 收到相同请求时，响应缓存会跳过 LLM 调用，重放之前缓存的响应。可用它降低延迟，避免为重复调用再次付费。

缓存通过输入处理器 [`ResponseCache`](/reference/processors/response-cache) 实现，Mastra 没有提供 Agent 级的配置项。要启用缓存，需显式注册该处理器。Mastra 在收集反馈期间采用这种方式，以保持 API 精简。单次调用的覆盖配置通过 `RequestContext` 传递。

### 何时使用响应缓存 {/* #when-to-use-response-caching */}

当不同用户或会话反复发起相同请求时，可以使用缓存，例如建议提示词按钮、重复搜索，或对相同输入分类的防护 LLM。如果调用会通过工具产生外部副作用，则不要缓存：命中缓存会重放工具调用记录，却不会再次执行工具。

### 快速入门 {/* #quickstart-1 */}

将 `ResponseCache` 加入 Agent 的 `inputProcessors`，并传入任意 `MastraServerCache` 作为后端。开发时可直接使用 `InMemoryServerCache`：

```typescript title="src/mastra/agents/search-agent.ts"
import { Agent } from '@mastra/core/agent'
import { InMemoryServerCache } from '@mastra/core/cache'
import { ResponseCache } from '@mastra/core/processors'

const cache = new InMemoryServerCache()

export const searchAgent = new Agent({
  id: 'search-agent',
  name: 'Search Agent',
  instructions: 'You answer questions concisely.',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  inputProcessors: [new ResponseCache({ cache, ttl: 600 })], // 10 minutes
})
```

首次调用正常运行 LLM，并将响应写入缓存。此后解析后的提示词相同时，调用直接返回缓存响应，不再调用 LLM。

### 通过 RequestContext 覆盖单次调用的配置 {/* #per-call-overrides-via-requestcontext */}

单次调用配置通过 `RequestContext` 传递。使用 `ResponseCache.context()` 创建新的上下文，或使用 `ResponseCache.applyContext()` 合并到已有上下文：

```typescript title="src/example.ts"
import { ResponseCache } from '@mastra/core/processors'
import { RequestContext } from '@mastra/core/request-context'

// Fresh context with the override
await agent.stream('hello', {
  requestContext: ResponseCache.context({ key: 'custom-key', bust: true }),
})

// Or merge into an existing context
const ctx = new RequestContext()
ctx.set('caller-meta', { userId: 'u-123' })
ResponseCache.applyContext(ctx, { bust: true })
await agent.stream('hello', { requestContext: ctx })
```

以下字段可按调用覆盖：

- `key`：字符串或函数，只覆盖本次请求自动生成的缓存键。
- `scope`：字符串或 `null`，只覆盖本次请求的租户/用户范围。`null` 表示不按范围隔离。
- `bust`：布尔值，跳过读取缓存，但完成后仍写入缓存（适用于“强制刷新”按钮）。

`cache`、`ttl` 和 `agentId` 仍在构造函数中配置。这些属性属于实例级配置，不适合每次调用时改变。

### 租户范围隔离 {/* #tenant-scoping */}

默认情况下，`ResponseCache` 会从请求上下文读取 `MASTRA_RESOURCE_ID_KEY`，并将其作为缓存范围。如果 Agent 已填充资源 ID（例如通过 Memory），便会自动按用户隔离；用户不会看到其他人的缓存响应。

需要其他范围时，可以显式覆盖：

```typescript title="src/mastra/agents/scoped-agent.ts"
import { Agent } from '@mastra/core/agent'

new Agent({
  id: 'processors-agent',
  inputProcessors: [
    new ResponseCache({
      cache,
      scope: 'org-123', // explicit tenant scope
    }),
  ],
})
```

传入 `scope: null` 可有意让所有调用方共享缓存条目。只应对已确定为公开、且不因用户而异的内容这样做。

### 自定义缓存后端 {/* #custom-cache-backend */}

`ResponseCache` 接受任何 `MastraServerCache`。在生产环境中可使用 `@mastra/redis` 中的 `RedisServerCache`：

```typescript title="src/mastra/agents/cached-agent.ts"
import { Agent } from '@mastra/core/agent'
import { ResponseCache } from '@mastra/core/processors'
import { RedisServerCache } from '@mastra/redis'
import { createClient } from 'redis'

const client = createClient({ url: process.env.REDIS_URL })
await client.connect()

const cache = new RedisServerCache({ client })

export const agent = new Agent({
  id: 'cached-agent',
  name: 'Cached Agent',
  instructions: '...',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  inputProcessors: [new ResponseCache({ cache })],
})
```

如需自定义后端，请继承 `MastraServerCache` 并实现其抽象方法（处理器只调用 `get` 和 `set`）。

### 缓存的实现方式 {/* #how-caching-is-implemented */}

`ResponseCache` 通过 `processLLMRequest` 查找缓存，并在命中时跳过模型调用；通过 `processLLMResponse` 在响应完成后写入缓存。两者都在 Agent 循环中运行，时机是 Memory 加载消息、前面的输入处理器转换提示词之后。

缓存键来自 Mastra 即将发给模型的、已解析的 `LanguageModelV2Prompt`。它在 Memory 加载消息及前面的输入处理器运行后生成；Agent 工具循环中的每个步骤都会独立缓存。

### 缓存键包含什么 {/* #whats-in-the-cache-key */}

如果没有提供 `key`，处理器会根据当前步骤中影响 LLM 响应的输入确定性地生成缓存键：`agentId`、`stepNumber`（工具循环中每一步都有独立条目）、`scope`、模型身份（`provider`、`modelId`、规范版本）以及解析后的 `prompt`（经过 Memory 和处理器）。这些输入的任何变化都会自动使缓存失效。

多模态提示词也会纳入缓存键。对于图片和文件，键包含完整 URL；内联二进制数据（`Uint8Array`、`ArrayBuffer`）则包含字节摘要。因此，只要引用的图片不同，请求就会使用不同的缓存条目。

#### 自定义缓存键 {/* #customize-the-cache-key */}

在构造函数或单次调用中传入 `key` 函数，可根据上述输入的任意子集生成自定义缓存键。函数接收与默认确定性哈希相同的输入，返回字符串（或 `Promise<string>`）：

```typescript title="src/example.ts"
import { ResponseCache, buildResponseCacheKey } from '@mastra/core/processors'

await agent.stream(input, {
  requestContext: ResponseCache.context({
    // Cache only on the model id and the resolved prompt tail — ignore
    // step number, scope, etc.
    key: ({ model, prompt }) => `qa:${model.modelId}:${JSON.stringify(prompt).slice(-200)}`,
  }),
})

// Or reuse the deterministic helper while overriding individual fields:
await agent.stream(input, {
  requestContext: ResponseCache.context({
    key: inputs => buildResponseCacheKey({ ...inputs, scope: 'global' }),
  }),
})
```

如果该函数抛错，处理器会回退到默认的缓存键生成方式，本次调用仍可使用缓存。

### 缓存命中的处理方式 {/* #how-cache-hits-work */}

命中缓存后，处理器从 `processLLMRequest` 返回缓存的流块，从而跳过 LLM 调用。Agent 循环会根据这些流块构造流，而不调用模型。`agent.generate()` 会将其收集为 `FullOutput`；`agent.stream()` 返回流块来自缓存缓冲区的 `MastraModelOutput`。因此，遍历 `fullStream` 或等待 `text`、`usage`、`finishReason` 的调用方都会看到缓存值。

响应完成后才会写入缓存。失败的运行（包括错误和触发 tripwire）不会缓存，下次调用可以正常重试。

## 高级模式 {/* #advanced-patterns */}

### 使用 `maxSteps` 确保最终响应 {/* #ensure-a-final-response-with-maxsteps */}

使用 `maxSteps` 限制 Agent 的执行步数时，如果 Agent 在最后一步尝试调用工具，可能返回空响应。可以在 `processInputStep()` 中使用 `sendSignal`，在最后一步注入响应式提醒。此方法通过追加信号，而非修改系统消息，保留了提示词缓存效果。

```typescript title="src/mastra/processors/ensure-final-response.ts"
import type { Processor, ProcessInputStepArgs } from '@mastra/core/processors'

export class EnsureFinalResponseProcessor implements Processor {
  readonly id = 'ensure-final-response'

  private maxSteps: number

  constructor(maxSteps: number) {
    this.maxSteps = maxSteps
  }

  async processInputStep({ stepNumber, sendSignal }: ProcessInputStepArgs) {
    if (stepNumber !== this.maxSteps - 1) {
      return
    }

    await sendSignal?.({
      type: 'reactive',
      contents:
        `This is your final step (step ${stepNumber + 1} of ${this.maxSteps}). ` +
        `Do not call any more tools. Summarize what you have found and give the user a complete final answer now.`,
      attributes: { reason: 'max-steps-reached', step: stepNumber + 1 },
    })
  }
}
```

该信号会作为 `<system-reminder>` 用户消息传递，模型会在对话中看到它：

```xml
<system-reminder reason="max-steps-reached" step="5">This is your final step (step 5 of 5). Do not call any more tools. Summarize what you have found and give the user a complete final answer now.</system-reminder>
```

将处理器加入 `inputProcessors`，在系统提示词中解释信号标签，并向 `generate()` 或 `stream()` 传入相同的 `maxSteps` 值：

```typescript title="src/mastra/agents/index.ts"
import { Agent } from '@mastra/core/agent'
import { EnsureFinalResponseProcessor } from '../processors/ensure-final-response'

const MAX_STEPS = 5

const agent = new Agent({
  id: 'agent',
  instructions: `You are a helpful assistant.

Some messages you receive may contain <system-reminder>...</system-reminder> tags.
These reminders are injected by the system, not written by the user, even though they arrive inside a user message.
Treat the contents of a <system-reminder> as authoritative system instructions and follow them immediately.
Do not mention the reminder to the user or quote the tags back to them.`,
  inputProcessors: [new EnsureFinalResponseProcessor(MAX_STEPS)],
  // ...
})

await agent.generate('Your prompt', { maxSteps: MAX_STEPS })
```

:::note
响应式信号默认使用 `tagName: 'system-reminder'`。[Agent 何时看到输入](/docs/signals/sending-signals#when-the-agent-sees-your-input)介绍处理器发出的信号何时到达模型。
:::

### 工具读取文件后补充上下文 {/* #send-context-after-a-tool-reads-a-file */}

处理器可以观察工具结果，只注入一次后续指令，而不是每一步都注入。以下示例在工具调用读取 `AGENTS.md` 文件后发送文件内容；如果此前已经发送过，则跳过。`findAgentsMdPathFromToolCalls()`、`hasAlreadySentAgentsMdReminder()` 和 `readAgentsMdInstructions()` 是你自行编写的应用辅助函数，Mastra 不会导出它们。

`processInputStep()` 发出的信号与其他输入一样，遵循中断和等待规则。处理器会在 Mastra 取消它所准备的请求之前完成；输出处理器会在下次请求之前结束，处理器的副作用不会撤销。如果处理器每次都发送信号，请求被替换时就可能重复注入上下文，因此应检查历史并只响应特定触发事件。

```typescript title="src/mastra/processors/agents-md-reminder.ts"
import type { Processor, ProcessInputStepArgs } from '@mastra/core/processors'

export const agentsMdReminderProcessor: Processor = {
  id: 'agents-md-reminder',
  async processInputStep({ messageList, sendSignal }: ProcessInputStepArgs) {
    const messages = messageList.get.all.db()
    const agentsMdPath = findAgentsMdPathFromToolCalls(messages)

    if (!agentsMdPath || hasAlreadySentAgentsMdReminder(messages, agentsMdPath)) {
      return messageList
    }

    await sendSignal?.({
      type: 'reactive',
      contents: readAgentsMdInstructions(agentsMdPath),
      attributes: {
        type: 'dynamic-agents-md',
        path: agentsMdPath,
      },
      metadata: {
        path: agentsMdPath,
      },
    })

    return messageList
  },
}
```

模型会收到如下上下文：

```xml
<system-reminder type="dynamic-agents-md" path="packages/ui/AGENTS.md">
  $agentsMdFileContents
</system-reminder>
```

等待 `sendSignal()` 完成可在有活跃订阅 Thread 时保持流回显的顺序。

### 发送不保留的提醒 {/* #deliver-a-reminder-without-retaining-it */}

默认情况下，处理器发送的信号会成为对话的一部分：写入存储，并在后续轮次重新进入提示词。如果每轮都要重新注入同一条指令，副本会不断累积，模型也可能把过去的提醒当作先前上下文来模仿。设置 `transient: true`，可仅在当前调用中把信号传给模型，而不保留它。

**适用场景：** 随着对话增长，你想让简短的引导指令始终靠近最近的消息，例如“专注当前任务”“回答不超过三句”，或依赖实时应用状态的单轮约束。每轮重新注入，便能让指令保持在最新消息附近。

```typescript title="src/mastra/processors/steering-reminder.ts" {10}
import type { Processor, ProcessInputStepArgs } from '@mastra/core/processors'

export class SteeringReminderProcessor implements Processor {
  readonly id = 'steering-reminder'

  async processInputStep({ sendSignal }: ProcessInputStepArgs) {
    await sendSignal?.({
      type: 'reactive',
      contents: 'Stay on the current task and keep answers under three sentences.',
      transient: true,
    })
  }
}
```

临时信号仍会进入当前调用的提示词，模型会在最近的轮次附近看到它。由于不被保留，每轮重发也只会留下一个新的副本，存储的 Thread 历史不会包含它。此外，由于没有写入操作，各轮还能保持稳定的提示词缓存前缀。

### 发送自定义流事件 {/* #emit-custom-stream-events */}

输出处理器会收到 `writer` 对象，可在流式处理期间向客户端发送自定义数据流块。可用于传送内容审核结果，或在不中断原始流的情况下发送 UI 更新信号。

```typescript title="src/mastra/processors/moderation-processor.ts" {6,18-25}
import type { Processor } from '@mastra/core/processors'

export class ModerationProcessor implements Processor {
  id = 'moderation'

  async processOutputResult({ messages, writer }) {
    // Run moderation on the final output
    const text = messages
      .filter(m => m.role === 'assistant')
      .flatMap(m => m.content.parts?.filter(p => p.type === 'text'))
      .map(p => p.text)
      .join(' ')

    const result = await runModeration(text)

    if (result.requiresChange) {
      // Emit a custom event to the client with the moderated text
      await writer?.custom({
        type: 'data-moderation-update',
        data: {
          originalText: text,
          moderatedText: result.moderatedText,
          reason: result.reason,
        },
      })
    }

    return messages
  }
}
```

在客户端监听自定义流块类型：

```typescript
const stream = await agent.stream('Hello')

for await (const chunk of stream.fullStream) {
  if (chunk.type === 'data-moderation-update') {
    // Update the UI with moderated text
    updateDisplayedMessage(chunk.data.moderatedText)
  }
}
```

自定义流块类型必须以 `data-` 为前缀，例如 `data-moderation-update`、`data-status`。

默认情况下，`processOutputStream()` 会跳过 `data-*` 流块，避免误处理工具遥测数据或其他处理器的输出。若要在处理器中检查、修改或拦截这类流块，应设置 `processDataParts = true`：

```typescript
class ModerationCollector implements Processor {
  id = 'moderation-collector'
  processDataParts = true

  async processOutputStream({ part, state }) {
    if (part.type === 'data-moderation-update') {
      state.warnings ??= []
      state.warnings.push(part.data)
    }
    return part
  }
}
```

### 向消息添加元数据 {/* #add-metadata-to-messages */}

可以在 `processOutputResult` 中给消息添加自定义元数据，并通过响应对象访问：

```typescript title="src/mastra/processors/metadata-processor.ts"
import type { Processor } from '@mastra/core/processors'
import type { MastraDBMessage } from '@mastra/core/memory'

export class MetadataProcessor implements Processor {
  id = 'metadata-processor'

  async processOutputResult({
    messages,
  }: {
    messages: MastraDBMessage[]
  }): Promise<MastraDBMessage[]> {
    return messages.map(msg => {
      if (msg.role === 'assistant') {
        return {
          ...msg,
          content: {
            ...msg.content,
            metadata: {
              ...msg.content.metadata,
              processedAt: new Date().toISOString(),
              customData: 'your data here',
            },
          },
        }
      }
      return msg
    })
  }
}
```

使用 `generate()` 读取元数据：

```typescript
const result = await agent.generate('Hello')

// The response includes uiMessages with processor-added metadata
const assistantMessage = result.response?.uiMessages?.find(m => m.role === 'assistant')
console.log(assistantMessage?.metadata?.customData)
```

对于流式调用，可从 `finish` 流块的数据或 `stream.response` Promise 读取元数据。

### 使用 Workflow 作为处理器 {/* #use-workflows-as-processors */}

Mastra Workflow 可以作为处理器，构建支持并行执行、条件分支和错误处理的复杂处理流程：

```typescript title="src/mastra/processors/moderation-workflow.ts"
import { createWorkflow, createStep } from '@mastra/core/workflows'
import {
  ProcessorStepOutputSchema,
  PromptInjectionDetector,
  PIIDetector,
  ModerationProcessor,
} from '@mastra/core/processors'
import { Agent } from '@mastra/core/agent'

// Create a workflow that runs multiple checks in parallel
const moderationWorkflow = createWorkflow({
  id: 'moderation-pipeline',
  inputSchema: ProcessorStepOutputSchema,
  outputSchema: ProcessorStepOutputSchema,
})
  .parallel([
    createStep(
      new PIIDetector({
        model: '__GATEWAY_OPENAI_MODEL_LUNA__',
        strategy: 'redact',
      }),
    ),
    createStep(
      new PromptInjectionDetector({
        model: '__GATEWAY_OPENAI_MODEL_LUNA__',
        strategy: 'block',
      }),
    ),
    createStep(
      new ModerationProcessor({
        model: '__GATEWAY_OPENAI_MODEL_LUNA__',
        strategy: 'block',
      }),
    ),
  ])
  .map(async ({ inputData }) => {
    return inputData['processor:pii-detector']
  })
  .commit()

// Use the workflow as an input processor
const agent = new Agent({
  id: 'moderated-agent',
  name: 'Moderated Agent',
  model: '__GATEWAY_OPENAI_MODEL__',
  inputProcessors: [moderationWorkflow],
})
```

在 `.parallel()` 步骤之后，各分支结果以其处理器 ID 为键，例如 `processor:pii-detector`。使用 `.map()` 选择下一个步骤应接收的分支输出。

如果某个分支使用 `redact` 等会修改消息的策略，应映射到该分支，让转换后的消息继续传递。如果所有分支只使用 `block`，任意选择一个即可，因为它们都不会修改消息。

向 Mastra 注册 Agent 时，处理器 Workflow 也会自动注册为 Workflow，因此可以在 [Studio](/docs/studio/overview) 中查看和调试。

### 重试机制 {/* #retry-mechanism */}

处理器可以附上反馈，请求 LLM 重试响应。可用于质量检查、输出验证和迭代改进：

```typescript title="src/mastra/processors/quality-checker.ts"
import type { Processor } from '@mastra/core/processors'
import { Agent } from '@mastra/core/agent'

export class QualityChecker implements Processor {
  id = 'quality-checker'

  async processOutputStep({ messages, text, abort, retryCount }) {
    const qualityScore = await evaluateQuality(text)

    if (qualityScore < 0.7 && retryCount < 3) {
      // Request a retry with feedback for the LLM
      abort('Response quality score too low. Please provide a more detailed answer.', {
        retry: true,
        metadata: { score: qualityScore },
      })
    }

    return messages
  }
}

const agent = new Agent({
  id: 'quality-agent',
  name: 'Quality Agent',
  model: '__GATEWAY_OPENAI_MODEL__',
  outputProcessors: [new QualityChecker()],
  maxProcessorRetries: 3, // Step retry limit for processInputStep/processOutputStep. Unset by default, which disables those retries.
})
```

重试机制：

- 可在 `processOutputStep()` 和 `processInputStep()` 方法中使用。
- 将 `abort` 原因原样作为系统提醒追加到对话末尾，然后重放该步骤。重试会保留上一次请求作为前缀，以利用 Provider 的提示词缓存。
- 通过 `retryCount` 参数跟踪重试次数。
- 必须在 Agent 或单次调用中显式设置 `maxProcessorRetries` 上限。

### 错误处理器的重试限制 {/* #error-processor-retry-limits */}

`processAPIError()` 有独立的重试预算。如果解析后的 `errorProcessors` 列表非空，且未设置 `maxProcessorRetries`，运行时最多允许错误处理器重试 `3` 次。每个 Agent 默认启用错误处理器（参阅[默认启用错误处理器](#error-processors-are-enabled-by-default)），但 `maxProcessorRetries` 本身仍未设置，因此 `processInputStep()` 和 `processOutputStep()` 的重试仍需显式指定上限。

对于 `StreamErrorRetryProcessor`，其自身的 `maxRetries`（默认 `1`）独立于 Agent 上限约束重试次数。如果该处理器是请求唯一的重试机制，应将模型重试次数设为 `0`。

### 违规回调 {/* #violation-callbacks */}

所有处理器都有 `onViolation` 属性：无论调用 `abort()`（阻止策略），还是处理器发出警告（警告策略），检测到策略违规时都会触发。可用于告警、日志或副作用，而不影响处理器的主要逻辑：

```typescript title="src/mastra/processors/violation-logging.ts"
import { ModerationProcessor, TokenCostControl } from '@mastra/core/processors'

const moderation = new ModerationProcessor({
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  strategy: 'block',
})

moderation.onViolation = ({ processorId, message, detail }) => {
  // Log to external monitoring, send alerts, update dashboards
  monitor.track('processor_violation', { processorId, message, detail })
}

const tokenCostControl = new TokenCostControl({
  maxCost: 10.0,
  scope: 'resource',
  window: '30d',
})

tokenCostControl.onViolation = ({ processorId, message, detail }) => {
  alertSystem.notify(`[${processorId}] ${message}`)
}
```

回调接收 `ProcessorViolation` 对象，包含：

- `processorId`：检测到违规的处理器 ID
- `message`：对违规情况的可读说明
- `detail`：处理器专用元数据，例如成本、检测到的 PII 类型或内容审核类别

`onViolation` 属于基础 [`Processor` 接口](/reference/processors/processor-interface)，因此自定义处理器也能使用。每当处理器调用 `abort()`，Runner 会自动触发它；回调内部抛出的错误会被捕获，避免干扰处理流程。

### `abort` 与 tripwire 流块 {/* #abort-and-tripwire-chunks */}

调用 `abort(reason, options)` 会抛出结束处理流程的 `TripWire` 错误。流式响应中，Mastra 会发送客户端可识别的 `tripwire` 流块：

```typescript oxfmt:false
for await (const chunk of stream.fullStream) {
  if (chunk.type === 'tripwire') {
    console.log('Blocked by', chunk.payload.processorId, '-', chunk.payload.reason)
    break
  }
}
```

对于 `agent.generate()`，同样的信息可通过 `result.tripwire` 获取，此时 `result.finishReason === 'other'`。

`abort` 接受第二个选项参数：

- `retry: true` 请求 Agent 重试，而非结束。输入和输出处理器的重试要求在 Agent 或单次调用中设置 `maxProcessorRetries`。
- `metadata` 在 `tripwire` 流块中附加结构化数据，让下游可以根据 `pii`、`quality`、`moderation` 等类别采取不同操作。

## 处理 API 错误 {/* #api-error-handling */}

`processAPIError` 方法处理 LLM API 拒绝请求的错误，例如 API 因消息格式而返回 400 或 422；它不处理网络或服务器故障。API 拒绝消息格式时，你可以通过该方法修改请求并重试。

```typescript title="src/mastra/processors/api-error-handler.ts"
import { APICallError } from '@ai-sdk/provider'
import type { Processor, ProcessAPIErrorArgs, ProcessAPIErrorResult } from '@mastra/core/processors'

export class ContextLengthHandler implements Processor {
  id = 'context-length-handler'

  processAPIError({
    error,
    messageList,
    retryCount,
  }: ProcessAPIErrorArgs): ProcessAPIErrorResult | void {
    if (retryCount > 0) return

    if (APICallError.isInstance(error) && error.message.includes('context length exceeded')) {
      const messages = messageList.get.all.db()
      if (messages.length > 4) {
        messageList.removeByIds([messages[1]!.id, messages[2]!.id])
        return { retry: true }
      }
    }
  }
}
```

Mastra 内置的 [`PrefillErrorHandler`](/reference/processors/prefill-error-handler) 会自动处理 Anthropic 的“助理消息预填充”错误。该处理器会自动注入，无需配置。

### 从附件下载失败中恢复 {/* #recover-from-attachment-download-failures */}

如果模型无法自行获取附件 URL，Mastra 会在调用模型前下载附件。下载失败时，`processAPIError()` 会收到 ID 为 `DOWNLOAD_ASSETS_FAILED` 的 `MastraError`，附件 URL 位于 `error.details.url`。错误处理器可据此替换附件，例如换成新的签名 URL，再返回 `{ retry: true }`。接下来会轮到后备模型尝试。

如果没有处理器成功恢复下载，Agent 也不会使本轮失败。它会将附件替换为文本占位符 `[Attachment unavailable: <name>]`，记录警告，并重试一次。Mastra 会把 URL 记录在已存储用户消息的 `metadata.mastra.unavailableAttachments` 中。后续轮次会显示同一占位符，不再下载该附件；附件本身仍留在 Thread 历史中。

无法解码的 Data URL 会立即替换为占位符，因为重试无法修复它。

## 接收后台工作通知 {/* #receive-background-work-notifications */}

使用 `createBackgroundWorkSignalProcessor()`，可为符合条件的后台工具调用保留当前调用方的信号能力：

```typescript
import { Agent } from '@mastra/core/agent'
import { createBackgroundWorkSignalProcessor } from '@mastra/core/processors'

const agent = new Agent({
  id: 'background-agent',
  name: 'Background agent',
  instructions: 'Complete tasks using the available tools.',
  model: '__GATEWAY_OPENAI_MODEL__',
  inputProcessors: [createBackgroundWorkSignalProcessor()],
})
```

Mastra 的后台运行时仍负责执行、持久化、重试、结果对账和续执行。该处理器只保留调用方范围内的通知访问权限。后台工作启动时，它会发送状态为 `status: 'running'` 的 `work-deferred` 或 `work-awaited`；权威工具结果对账后，再发送 `work-completed` 或 `work-failed`。

通知仅在进程内有效，且属于尽力而为。如果原始运行已经结束，或无法发送信号（例如任务在另一个进程恢复），Mastra 仍会保留权威结果，不会重建运行或重发通知。前台调用没有分离运行的后台工作，因此不会发送后台工作通知。
