# 通知

通知记录需要 Agent 处理的事件，例如构建失败、拉取请求中的评论或后台任务完成。Mastra 将通知持久保存在独立于对话消息的收件箱中。即使事件到达时 Agent 正忙，之后也能读取。

投递策略决定是立即发送事件、与其他事件合并成摘要，还是留待之后处理。Agent 可在收件箱中读取、忽略或归档记录。投递可能失败，策略也可能丢弃事件，因此保存记录并不保证 Agent 会处理它。有关记录的生命周期和策略选项，请参阅[通知参考](/reference/signals/notifications)。

需要使用收件箱和投递机制的事件适合用通知。用户输入使用 [`sendMessage()`](/reference/agents/agent#sendmessagemessage-options)，应用上下文发生变化时使用[状态信号](/docs/signals/state-signals)，只供单次模型请求使用的上下文则使用[瞬态响应式信号](/docs/signals/sending-signals#send-context-from-a-system)。[`sendSignal({ type: 'notification' })`](/reference/agents/agent#sendsignalsignal-options) 会发送事件上下文，但不创建收件箱记录，也不提供记录的重试机制。

## 快速开始 {/* #quickstart */}

调用 [`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options) 创建记录并应用投递策略。要让 Agent 读取待处理记录，请按照[使用收件箱](#work-with-the-inbox)一节添加 [`createNotificationInboxTool()`](/reference/signals/create-notification-inbox-tool)。

通知记录需要支持 `notifications` 域的存储适配器。以下示例使用 libSQL，先订阅对话线程，再发送一条高优先级的 CI 失败通知：

```typescript title="src/mastra/notifications.ts"
import { Mastra } from '@mastra/core'
import { Agent } from '@mastra/core/agent'
import { LibSQLStore } from '@mastra/libsql'
import { Memory } from '@mastra/memory'

const storage = new LibSQLStore({
  id: 'mastra',
  url: 'file:./mastra.db',
})

const ciAgent = new Agent({
  id: 'ci-agent',
  name: 'CI Agent',
  instructions: 'Triage CI failures and explain what broke.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory({ storage }),
})

const mastra = new Mastra({
  agents: { ciAgent },
  storage,
})

const agent = mastra.getAgent('ciAgent')
const thread = {
  resourceId: 'user_123',
  threadId: 'thread_456',
}

const subscription = await agent.subscribeToThread(thread)

const { record, decision } = await agent.sendNotificationSignal(
  {
    source: 'github',
    kind: 'ci-status',
    priority: 'high',
    summary: 'CI failed on main: 3 tests failed in the API suite.',
    payload: {
      repository: 'acme/app',
      branch: 'main',
      runId: '123456',
    },
    dedupeKey: 'github:acme/app:main:ci',
  },
  thread,
)

console.log(record.status, decision.action)

for await (const chunk of subscription.stream) {
  console.log(chunk)

  if (chunk.type === 'finish') break
}
```

对话线程空闲时，高优先级通知会立即投递并启动一次运行。线程活跃时，Mastra 先汇总通知，等线程空闲后再投递完整通知。订阅会以[线程流](/docs/signals/thread-streams)数据块的形式收到摘要和完整通知。

## 通知记录 {/* #notification-records */}

收到通知后，`sendNotificationSignal()` 会创建记录，或将通知合并到匹配的待处理记录中，随后检查投递策略。如果安排稍后投递，分发器会在到期时读取记录并发送通知或摘要。

保存的记录包括路由信息、优先级、状态、投递尝试和原始 `payload`。模型收到的是根据 `summary` 和属性构建的 XML 元素，默认不会收到 `payload`。

记录可以处于 `pending`、`delivered`、`seen`、`dismissed`、`archived`、`discarded` 或 `failed` 状态。发送摘要后记录仍为 `pending`，因为摘要只告知模型有这些记录，不会将其标记为已投递。参考文档列出了所有[记录字段](/reference/signals/notifications#notification-records)和[状态](/reference/signals/notifications#priorities-and-statuses)。

## 创建和合并记录 {/* #create-and-coalesce-records */}

`sendNotificationSignal()` 接受单条通知或通知数组。每一项都单独创建，再由存储层判断能否合并到现有待处理记录中。

用 `dedupeKey` 标识可能重复到达的同一事件。用 `coalesceKey` 将相关事件合并为一条待处理记录。两种键使用相同的匹配规则。

只有仍在等待处理且线程、来源、种类、Agent 和资源均相同的记录才会参与合并。[通知参考](/reference/signals/notifications#coalescing-pending-records)列出了可合并的字段及其优先级。

## 配置存储和分发器 {/* #storage-and-dispatcher-setup */}

通知记录需要支持 `notifications` 域的存储适配器：[libSQL](/integrations/databases/libsql)、[PostgreSQL](/integrations/databases/postgresql) 或 [MongoDB](/integrations/databases/mongodb)。缺少该域时，`sendNotificationSignal()` 会抛出错误，避免记录被静默丢弃。

定时分发默认启用，由 Workflow 调度器执行。在 `Mastra` 实例上配置：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  agents: { ciAgent },
  storage,
  notifications: {
    dispatch: {
      enabled: true,
      cron: '*/1 * * * *',
      batchSize: 100,
    },
  },
})
```

默认值为 `enabled: true`、`cron: '*/1 * * * *'`（每分钟一次）和 `batchSize: 100`。只有在推迟投递通知或生成通知摘要时，应用才会按需创建分发计划，并启用 Workflow 调度器。设置 `enabled: false` 可关闭该功能。

## 投递策略 {/* #delivery-policy */}

每条记录在接收时都会经过一次策略判定，分发时也可能再次判定。内置策略依据优先级和线程状态：

| 优先级 | 空闲线程 | 活跃线程 |
| - | - | - |
| `urgent` | 立即投递 | 立即投递 |
| `high` | 立即投递 | 先发摘要，空闲后再投递 |
| `medium` | 立即投递 | 批量汇总成摘要 |
| `low` | 批量汇总成摘要 | 批量汇总成摘要 |

默认行为不合适时，可在 Agent 上配置策略。来源规则先于优先级规则执行，因此可以只对事件过多的来源生成摘要，其他通知照常投递：

```typescript title="src/mastra/agents/ci-agent.ts"
import { Agent } from '@mastra/core/agent'
import { Memory } from '@mastra/memory'

// storage from the Quickstart
export const ciAgent = new Agent({
  id: 'ci-agent',
  name: 'CI Agent',
  instructions: 'Triage CI failures and explain what broke.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory({ storage }),
  notifications: {
    deliveryPolicy: {
      sources: {
        github: 'summarize',
      },
      priorities: {
        urgent: 'deliver',
        low: 'discard',
      },
    },
  },
})
```

Mastra 按以下顺序评估策略：

1. 自定义 `decide()` 函数。
1. `sources`，匹配 `record.source`。
1. `priorities`，匹配 `record.priority`。
4. `default`.
1. 内置优先级策略。

`decide()` 在收到记录时执行。如果首次判定为延后投递或安排摘要，它还会在投递时再次执行。投递时间和方式由保存的计划决定，投递时仅采用新判定中的 `streamOptions` 和 `hold`。请确保 `decide()` 没有副作用。

## 分发 {/* #dispatch */}

分发器读取到期记录，按 `agentId`、`resourceId` 和 `threadId` 对摘要分组，并通过线程运行时发出信号。

| 判定 | 结果 |
| - | - |
| `deliver` | 立即发送完整通知 |
| `queue` | 保留为待处理记录，留待后续分发 |
| `summarize` | 立即发送摘要，或在 `summaryAt` 发送 |
| `defer` | 保持待处理状态，直到 `deliverAt` |
| `persist` | 仅保存记录，不发出信号 |
| `discard` | 将记录标记为已丢弃 |

判定包含 `hold` 时，记录会留给另一个进程的分发器，且不计入投递尝试次数。

### 摘要 {/* #summaries */}

摘要可以避免繁忙的线程短时间内收到大量单独通知。模型看到的是一份简明摘要：

```xml
<notification-summary pending="10">github: 3, email: 5, slack: 2</notification-summary>
```

完整通知以该条记录的摘要作为内容：

```xml
<notification source="github" kind="ci-status" priority="high" status="delivered">CI failed on main: 3 tests failed in the API suite.</notification>
```

发送摘要会清除 `summaryAt` 并设置 `summarySignalId`，记录仍为 `pending`，也仍可读取。发送完整通知则会设置 `deliveredSignalId`，并将记录标记为 `delivered`。

发送摘要不会将记录标记为已投递。Agent 需要完整内容时，可通过收件箱读取记录。读取时可以注入完整信号，并将记录标记为 `seen`，避免之后重复投递。

### 重试与失败 {/* #retries-and-failures */}

投递失败会增加 `deliveryAttempts`，并记录 `lastDeliveryAttemptAt` 和 `lastDeliveryError`。记录仍处于待处理状态，下轮分发时即可重试。

尝试失败五次后，记录会转为 `failed`，不再参与分发。此上限通过 `MAX_NOTIFICATION_DELIVERY_ATTEMPTS` 导出。`hold` 会让记录保持待处理状态且不计入尝试次数，其他分发器仍可接手。

如果自定义策略在首次收到通知时抛出错误，记录会保持待处理状态，`deliverAt` 设为立即投递，并记一次失败，以便分发器重试。

## 使用收件箱 {/* #work-with-the-inbox */}

为 Agent 提供收件箱 Tool，它就能查看记录，无需公开存储 API：

```typescript title="src/mastra/agents/ci-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createNotificationInboxTool } from '@mastra/core/notifications'

const notificationsStorage = await storage.getStore('notifications')

export const ciAgent = new Agent({
  // ...id, instructions, model, memory, and notifications from the policy example
  tools: {
    notificationInbox: createNotificationInboxTool({ storage: notificationsStorage }),
  },
})
```

该 Tool 支持 `list`、`read`、`search`、`markSeen`、`dismiss` 和 `archive`。列出或搜索记录时，返回的未读记录会被标记为 `seen`，包括 `failed` 记录，让 Agent 知道系统已停止投递。`list` 默认返回待处理、已投递和失败的记录。`search` 涵盖所有状态。`read` 仅处理待处理和已投递记录，因此会跳过 `failed` 记录。如果记录和调用方 Agent 都没有提供 `resourceId`，导致 `read` 无法投递，记录会保持待处理状态。

收到摘要后，可用 `read` 获取完整内容。它会将选中记录的完整内容作为通知信号投递，而不是作为普通 Tool 输出。即使调用只返回简短的状态消息，Agent 仍可在线程中看到相关上下文。

## Agent 和客户端接口 {/* #agent-and-client-surfaces */}

[`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options) 是创建持久化通知记录的标准方法。它会返回记录和策略判定。若发出了信号，返回值还包括 `accepted`、`signal` 和 `persisted`，与[发送信号](/docs/signals/sending-signals)中介绍的其他方法一致。

JavaScript 客户端 SDK 可通过 [`client.getAgent().sendSignal()`](/reference/client-js/agents#sendsignal) 发送通知格式的上下文。此方式绕过收件箱存储，仅适用于无须记录、重试或稍后读取的事件。要通过 HTTP 创建持久化记录，请使用 AgentController Session 的通知路由，它会转发给 `sendNotificationSignal()`。参阅 [Session 参考](/reference/agent-controller/session)和 [Agent Controller](/docs/harness/agent-controller)。
