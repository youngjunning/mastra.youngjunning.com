# 通知

通知记录Agent要处理的事件，例如失败的构建、拉取请求评论或已完成的后台作业。 Mastra 将其存储在持久的收件箱中，与对话消息分开。即使客服人员到达时正忙，该事件仍然可用。

传递策略决定是否立即发送事件、将其与其他事件汇总或留待稍后发送。客服人员使用收件箱读取、忽略或存档记录。传递可能会失败，并且策略可能会丢弃事件，因此存储记录并不能保证Agent会对其采取行动。这[Notifications reference](/reference/signals/notifications) describes the record lifecycle and policy options.

对需要此收件箱和传递行为的事件使用通知。使用[`sendMessage()`](/reference/agents/agent#sendmessagemessage-options) for user input, a [state signal](/docs/signals/state-signals)用于更改应用程序上下文，或[瞬态无功信号](/docs/signals/sending-signals#send-context-from-a-system)用于一个模型请求所需的上下文。[`sendSignal({ type: 'notification' })`](/reference/agents/agent#sendsignalsignal-options)发送事件上下文而不创建收件箱记录或提供其重试。

## 快速入门 {/* #quickstart */}

称呼[`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options) to create the record and apply its delivery policy. To let the agent read pending records, add [`createNotificationInboxTool()`](/reference/signals/create-notification-inbox-tool) as shown in [Work with the inbox](#work-with-the-inbox).

记录需要一个存储适配器`notifications` domain. This example uses libSQL, subscribes to the thread first, then sends a high-priority CI failure:

```typescript title="src/mastra/notifications.ts"
import { Mastra } from '@mastra/core'
import { Agent } from '@mastra/core/agent'
import { LibSQLStore } from '@mastra/libsql'
import { Memory } from '@mastra/memory'

const storage = new LibSQLStore({
  id: 'mastra',
  url: 'file:./mastra.db',
})

const ciAgent = new Agent({
  id: 'ci-agent',
  name: 'CI Agent',
  instructions: 'Triage CI failures and explain what broke.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory({ storage }),
})

const mastra = new Mastra({
  agents: { ciAgent },
  storage,
})

const agent = mastra.getAgent('ciAgent')
const thread = {
  resourceId: 'user_123',
  threadId: 'thread_456',
}

const subscription = await agent.subscribeToThread(thread)

const { record, decision } = await agent.sendNotificationSignal(
  {
    source: 'github',
    kind: 'ci-status',
    priority: 'high',
    summary: 'CI failed on main: 3 tests failed in the API suite.',
    payload: {
      repository: 'acme/app',
      branch: 'main',
      runId: '123456',
    },
    dedupeKey: 'github:acme/app:main:ci',
  },
  thread,
)

console.log(record.status, decision.action)

for await (const chunk of subscription.stream) {
  console.log(chunk)

  if (chunk.type === 'finish') break
}
```

在空闲线程上，高优先级通知会立即传递并开始运行。在活动线程上，Mastra 首先对其进行汇总，然后在线程空闲时传递完整的通知。订阅会同时收到摘要和完整通知：[thread stream](/docs/signals/thread-streams) chunks.

## 通知记录 {/* #notification-records */}

当通知到达时，`sendNotificationSignal()` creates a record or merges it into a matching pending record. It then checks the delivery policy. If delivery is scheduled for later, the dispatcher reads the record when it's due and sends the notification or a summary.

存储的记录包括路由、优先级、状态、投递尝试和原始记录`payload`. The model receives an XML element built from `summary` and attributes. It doesn't receive `payload` automatically.

记录的状态可以是`pending`, `delivered`, `seen`, `dismissed`, `archived`, `discarded`, or `failed`. A summarized record stays `pending`, because a summary tells the model that records exist without marking them delivered. The reference lists every [记录字段](/reference/signals/notifications#notification-records)和[地位](/reference/signals/notifications#priorities-and-statuses).

## 创建和合并记录 {/* #create-and-coalesce-records */}

`sendNotificationSignal()`接受一个通知或一组通知。每个项目都是独立创建的，然后存储决定是否可以合并到现有的待处理记录中。

使用`dedupeKey` to identify one event that may arrive more than once. Use `coalesceKey` to group related events into one pending record, a process called coalescing. Both keys use the same matching rules.

合并仅考虑同一线程、源、种类、Agent和资源上仍待处理的记录。这[Notifications reference](/reference/signals/notifications#coalescing-pending-records) documents the fields that merge and their precedence.

## 存储和调度程序设置 {/* #storage-and-dispatcher-setup */}

通知记录需要一个存储适配器`notifications` domain: [libSQL](/integrations/databases/libsql), [PostgreSQL](/integrations/databases/postgresql), or [MongoDB](/integrations/databases/mongodb). Without it, `sendNotificationSignal()` throws instead of silently dropping the record.

默认情况下启用计划调度并通过Workflow调度程序运行。将其配置在`Mastra` instance:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  agents: { ciAgent },
  storage,
  notifications: {
    dispatch: {
      enabled: true,
      cron: '*/1 * * * *',
      batchSize: 100,
    },
  },
})
```

默认值是`enabled: true`, `cron: '*/1 * * * *'` (once per minute), and `batchSize: 100`. Only apps that defer or summarize a notification create the lazy dispatch schedule and activate the workflow scheduler with it. Set `enabled: false` to opt out.

## 发货政策 {/* #delivery-policy */}

每条记录在收到时都会做出决定，并且可能在发送时再次做出决定。内置策略使用优先级和线程状态：

|优先|空闲线程|活动线程 |
| - | - | - |
|`urgent` | Deliver immediately | Deliver immediately |
| `high` | Deliver immediately | Summarize now, then deliver when idle |
| `medium` | Deliver immediately | Batch into a summary |
| `low` | Batch into a summary | Batch into a summary |

当默认值不适合时，在Agent上配置策略。源规则在优先级规则之前运行，因此可以在其他所有内容交付的同时汇总噪声源：

```typescript title="src/mastra/agents/ci-agent.ts"
import { Agent } from '@mastra/core/agent'
import { Memory } from '@mastra/memory'

// storage from the Quickstart
export const ciAgent = new Agent({
  id: 'ci-agent',
  name: 'CI Agent',
  instructions: 'Triage CI failures and explain what broke.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory({ storage }),
  notifications: {
    deliveryPolicy: {
      sources: {
        github: 'summarize',
      },
      priorities: {
        urgent: 'deliver',
        low: 'discard',
      },
    },
  },
})
```

Mastra 按以下顺序评估该政策：

1. 定制`decide()` function.
2. `sources`, 匹配`record.source`.
3. `priorities`, 匹配`record.priority`.
4. `default`.
5. 内置优先级策略。

`decide()`对于第一个决定推迟或安排摘要的记录，在接收时运行并在交付时再次运行。存储的时间表确定了他们交付的时间和方式。仅限交付荣誉`streamOptions` and `hold` from the new decision. Keep `decide()` side-effect free.

## 派遣 {/* #dispatch */}

调度员读取到期记录，按以下方式对摘要进行分组`agentId`, `resourceId`, and `threadId`, and emits signals through the thread runtime.

|决定|结果 |
| - | - |
|`deliver` | Send the full notification immediately |
| `queue` | Keep the record pending for a later dispatch pass |
| `summarize` | Send a summary now or at `summaryAt` |
| `defer` | Keep the record pending until `deliverAt` |
| `persist` | Store the record without sending a signal |
| `discard` | Mark the record discarded |

一个决定与`hold` leaves the record for another process's dispatcher without counting a delivery attempt.

### 摘要 {/* #summaries */}

摘要可防止繁忙的线程接收大量的单独通知。该模型看到一个紧凑的摘要：

```xml
<notification-summary pending="10">github: 3, email: 5, slack: 2</notification-summary>
```

完整的通知将记录的摘要作为其内容：

```xml
<notification source="github" kind="ci-status" priority="high" status="delivered">CI failed on main: 3 tests failed in the API suite.</notification>
```

总结一目了然`summaryAt` and sets `summarySignalId`. The records stay `pending` and readable. A full notification sets `deliveredSignalId` and marks the record `delivered`.

摘要不标记已交付的记录。当Agent需要完整内容时，通过收件箱读取记录；读取可注入完整信号并标记记录`seen`, preventing duplicate delivery later.

### 重试和失败 {/* #retries-and-failures */}

失败的尝试会增加`deliveryAttempts` and records `lastDeliveryAttemptAt` and `lastDeliveryError`. The record stays pending and is due again on the next dispatch pass.

五次尝试失败后，记录移至`failed` and stops being due. The cap is exported as `MAX_NOTIFICATION_DELIVERY_ATTEMPTS`. A `hold` leaves it pending without counting an attempt, so another dispatcher can pick it up.

如果自定义策略在通知首次到达时抛出，则记录将保持待处理状态并立即`deliverAt` and a failed attempt, so the dispatcher can retry it.

## 使用收件箱 {/* #work-with-the-inbox */}

为Agent提供收件箱Tool，以便它可以在不暴露存储 API 的情况下检查记录：

```typescript title="src/mastra/agents/ci-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createNotificationInboxTool } from '@mastra/core/notifications'

const notificationsStorage = await storage.getStore('notifications')

export const ciAgent = new Agent({
  // ...id, instructions, model, memory, and notifications from the policy example
  tools: {
    notificationInbox: createNotificationInboxTool({ storage: notificationsStorage }),
  },
})
```

该Tool支持`list`, `read`, `search`, `markSeen`, `dismiss`, and `archive`. Listing and searching mark returned unread records `seen`, including `failed` records so the agent learns delivery gave up. `list` defaults to pending, delivered, and failed records. `search` spans all statuses. `read` only acts on pending and delivered records, so it skips `failed` ones. A record `read` can't deliver, because neither the record nor the calling agent supplies a `resourceId`, stays pending.

`read`总结后的事项。它将所选记录的完整内容作为通知信号而不是普通Tool输出提供。即使调用返回了简短的状态消息，Agent也可以看到线程上的上下文。

## Agent和客户端界面 {/* #agent-and-client-surfaces */}

[`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options)是创建持久通知记录的规范方法。它返回记录和策略决定，包括`accepted`, `signal`, and `persisted` when a signal was emitted, matching the other signal methods described in [Sending signals](/docs/signals/sending-signals).

JavaScript 客户端 SDK 可以通过以下方式发送通知形状的上下文[`client.getAgent().sendSignal()`](/reference/client-js/agents#sendsignal). That path bypasses inbox storage, so use it only when the event needs no record, retries, or later reading. Durable records over HTTP go through the AgentController Session notification route, which forwards to `sendNotificationSignal()`. See the [Session reference](/reference/agent-controller/session) and [Agent Controller](/docs/harness/agent-controller).
