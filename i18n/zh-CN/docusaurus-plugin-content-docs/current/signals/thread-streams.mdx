# 线程流

线程流传输 Agent 在同一[线程](/docs/memory/message-history#threads-and-resources)中多次运行的输出。只需订阅一次，就能以[数据块](/reference/streaming/ChunkType)的形式收到模型文本、Tool 调用及结果、审批请求和错误。订阅在两次运行之间保持打开，不必每次发送输入都创建新的响应流。

也可以在订阅开始时请求已保存的消息，让应用先显示此前的对话，再显示新输出。

## 快速入门 {/* #quickstart */}

先订阅再发送输入，这样从运行开始就能接收输出。本例使用 JavaScript 客户端 SDK 的 [`subscribeToThread()`](/reference/client-js/agents#subscribetothread)，需要一个正在运行的 Mastra 服务器，并且服务器上有名为 `support-agent` 的 Agent。如需保存历史消息，请为该 Agent 配置 [Memory](/docs/memory/overview)。

如果服务器端代码直接使用 `Agent` 实例，请参阅 [Agent 快速入门](/docs/signals/overview#use-an-agent)。

```typescript title="src/app/chat.ts"
import { MastraClient } from '@mastra/client-js'

const client = new MastraClient({ baseUrl: 'http://localhost:4111' })
const agent = client.getAgent('support-agent')

const subscription = await agent.subscribeToThread({
  resourceId: 'user-123',
  threadId: 'thread-456',
})

await agent.sendMessage({
  message: 'Show the shorter version.',
  resourceId: 'user-123',
  threadId: 'thread-456',
})

await subscription.processDataStream({
  onChunk: chunk => {
    console.log(chunk)
  },
  reconnect: true,
})
```

[`client.getAgent()`](/reference/client-js/mastra-client#methods) 选择服务器上的 Agent。Mastra 接受输入后，[`sendMessage()`](/reference/client-js/agents#sendmessage) 就会返回。[`processDataStream()`](/reference/client-js/agents#subscribetothread) 将输出传给 `onChunk`，本例用它打印每个数据块。回复完成后仍会继续监听。

## 读取线程流 {/* #read-the-stream */}

### 已保存的历史消息和实时片段 {/* #stored-history-and-live-parts */}

传入 `withInitialHistory: true` 后，首先会收到 `thread-history` 数据块，其中包含已保存消息的最新一页，按从旧到新的顺序排列。`perPage` 默认为 40。接着，订阅者会收到比这页历史消息更新的已保留片段，随后是实时片段。历史消息依赖记忆功能。如果未启用记忆，或线程尚无消息，首个数据块仍会到达，但 `messages` 数组为空。

### 数据块和运行 {/* #chunks-and-runs */}

用 `runId` 将同一次运行的数据块归组。[`thread-history`](/reference/streaming/ChunkType#thread-history) 是例外：其中的消息可能来自多次运行，因此 `runId` 为空。订阅的 [`activeRunId()`](/reference/agents/agent#subscribetothreadoptions) 返回当前运行的 ID，没有运行时则返回 `null`。

公开的订阅流包含 `AgentChunkType`。`withInitialHistory` 会加入 `ThreadHistoryChunk`，`withRunStatus: true` 会加入 `ThreadRunStatusChunk`。这两个选项默认为 `false`。[ChunkType 参考](/reference/streaming/ChunkType)列出了模型输出、Tool 调用及结果、审批、中止和错误的字段。要监测队列计数，请单独使用 [`subscribeThreadEvents()`](/reference/signals/thread-events)。

### 判断运行何时结束 {/* #detect-when-a-run-finishes */}

传入 `withRunStatus: true` 以接收运行结果。现有订阅默认不会收到这类数据块。

```typescript
const subscription = await agent.subscribeToThread({
  resourceId: 'user-123',
  threadId: 'thread-456',
  withRunStatus: true,
})
```

[`thread-run-status`](/reference/streaming/ChunkType#thread-run-status) 数据块单独报告运行结果，与运行输出无关：

```typescript
const chunk = {
  type: 'thread-run-status',
  runId: 'run-123',
  from: 'AGENT',
  payload: { status: 'success' },
}
```

`status` 可以是 `success`、`failed`、`aborted` 或 `suspended`。实时输出先于状态到达。暂停后可以恢复，同一次运行稍后可以继续产生输出并报告最终状态。运行结果不会关闭线程订阅，订阅会继续监听后续运行。

启用 `withInitialHistory` 后，首个数据块的载荷为 `{ messages, hasMore, activeRunId }`。`activeRunId` 表示加载初始数据时占有该线程的运行；线程空闲时为 `null`。请通过 `thread-run-status` 判断运行结果。线程空闲并不代表运行成功。

启用 `withRunStatus: true` 后，即使某次运行在订阅前就已结束，且文本已在历史消息中，只要结果仍被保留，订阅者就能收到。稍后才订阅且同时启用两个选项时，每次已结束且结果仍被保留的运行都会收到一条状态，包括初始历史页之外的运行，而不只是最近一次。最终结果在单次订阅内去重，暂停通知则按执行区段去重。重连会创建新订阅，可能再次收到同一结果。请按 `runId` 归组更新，不要把每次投递都当成新回复。

### 审批 Tool 调用 {/* #approve-tool-calls */}

运行因等待 Tool 审批而暂停时，请通过 [`client.getAgent().sendToolApproval()`](/reference/client-js/agents#sendtoolapproval) 或[服务器审批路由](/reference/server/routes#subscription-tool-approval-routes)发送决定。运行恢复后，现有订阅会收到输出。

暂停的运行仍占有线程。在它恢复或中止之前，尝试启动新运行的信号所收到的 `accepted` 响应，其动作都是 `blocked`。重新订阅时，待审批请求和暂停通知会重放，已完成并保存的输出不会重放。设置 `withRunStatus: true` 时，仍被保留的运行结果会送达。关于在运行期间到达的输入何时打断或等待，见 [Agent 何时看到输入](/docs/signals/sending-signals#when-the-agent-sees-your-input)。

### 过滤订阅中的信号 {/* #filter-signals-in-a-subscription */}

`hideSignals` 仅过滤单个订阅者接收的信号块。传入 `true` 可隐藏所有能识别的信号，传入 `false` 则显示这些信号，也可传入信号类型数组。此选项不改变模型上下文、已保存的消息、共享广播或其他订阅者，也不是安全边界。该选项仅适用于进程内的核心订阅；HTTP 和 `client-js` 的订阅请求不支持它。

## 停止运行或关闭订阅 {/* #stop-a-run-or-close-a-subscription */}

[`abort()`](/reference/client-js/agents#subscribetothread) 请求取消当前运行。`unsubscribe()` 仅关闭订阅，运行会继续，之后仍可再次订阅。中止运行不会清除待处理信号，除非传入 `clearPendingSignals: true`。

## 重新连接 {/* #reconnect */}

对于长期订阅，请使用 `reconnect: true`。传输连接关闭或重连请求失败时，`processDataStream()` 会重新订阅，默认每隔一秒重试，无次数上限。如果收到除 `408` 或 `429` 以外的 4xx 响应，或收到 `501`，则停止重连并拒绝 Promise。重试选项见 [`subscribeToThread()` 参考](/reference/client-js/agents#subscribetothread)。

重连可以接续共享 [PubSub 后端](/docs/server/pubsub)仍保留的输出，无法恢复仅存在于其他进程内存缓存中的事件。需要对话历史时，可使用 `withInitialHistory` 重新加载已保存消息的最新一页。

保存的消息并未记录流式传输中的每个文本片段。重连不会重放已完成并保存的输出，也不会重建未保留的片段。

能否恢复运行结果取决于 PubSub 后端保留了哪些数据，与历史分页大小无关。清理已保存的输出时，Redis Streams 会保留精简的终态事件和执行权限元数据，但这些记录仍可能因配置的流长度或空闲 TTL 而被清除。它不能充当永久运行审计日志，也不保证保留时长。要在清理后仍能恢复结果，请同时升级 `@mastra/core` 和 `@mastra/redis-streams`。较旧的适配器可能在删除输出时一并删除终态事件。

### 自定义端点的 SSE 心跳 {/* #sse-heartbeats-for-custom-endpoints */}

如果为线程订阅提供自定义的服务器发送事件（SSE）端点，请在线程流空闲时定期发送心跳帧，避免浏览器、代理或负载均衡器在下个信号或模型数据块到达前关闭连接。

以下示例每 25 秒发送一条 SSE 注释：

```typescript title="src/api/subscribe.ts"
const heartbeat = setInterval(() => {
  controller.enqueue(encoder.encode(': keep-alive\n\n'))
}, 25_000)

request.signal.addEventListener('abort', () => {
  clearInterval(heartbeat)
})
```

请将心跳和客户端的重连逻辑配合使用。心跳减少空闲断连；如果网络或运行时仍关闭了流，重连机制可以恢复连接。
