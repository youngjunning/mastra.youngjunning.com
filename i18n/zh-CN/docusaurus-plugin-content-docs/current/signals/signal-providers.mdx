# 信号 Provider

信号 Provider 监控外部系统，并向已订阅的 Agent 线程发送[通知](/docs/signals/notifications)。例如，Provider 可以监控构建流水线，在构建失败时通知订阅该流水线的所有线程。

如果应用需要管理各个线程接收哪些来源的事件，可以使用 Provider。基类 [`SignalProvider`](/reference/signals/signal-provider) 负责维护订阅、执行轮询并向 Agent 转交通知。你需要实现读取外部系统、将事件匹配到订阅的逻辑，也可以为 Agent 提供工具和处理器。

如果服务器已经收到事件并知道目标线程，直接调用 [`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options)。要更新应用上下文，请用[状态信号](/docs/signals/state-signals)；如果上下文仅供一次模型请求使用，请用[临时响应式信号](/docs/signals/sending-signals#send-context-from-a-system)。

## Provider 如何工作 {/* #how-a-provider-works */}

在 Agent 的 `signals` 数组中注册 Provider。它可以通过两种方式接收事件：

- **轮询：** [`poll()`](/reference/signals/signal-provider#polling) 定期检查外部系统。
- **Webhook：** 服务器将收到的事件传给 [`handleWebhook()`](/reference/signals/signal-provider#webhooks)。

对于每条匹配的订阅，Provider 调用受保护的 [`notify()`](/reference/signals/signal-provider#notifications) 方法。该方法通过 `Agent.sendNotificationSignal()` 转发事件，并使用通知的投递策略、重试机制和收件箱。

## 将外部标识映射到线程 {/* #map-external-identities-to-threads */}

使用目标线程的 [`resourceId` 和 `threadId`](/docs/memory/message-history#threads-and-resources) 为通知寻址。Provider 还需要用 `externalResourceId` 标识线程监控的对象，例如流水线 `acme-app-main`。请选择一个稳定且能与传入事件匹配的值。

订阅用这三个值共同标识，因此一个线程可监控多个资源，多个线程也可监控同一资源。额外数据放在 `metadata` 中，避免塞进外部 ID。处理 Webhook 时，先将载荷与 `externalResourceId` 匹配，再用订阅的 `resourceId` 和 `threadId` 确定目标。

## 快速入门 {/* #quickstart */}

此示例检查流水线的构建状态，在构建失败时通知订阅线程。`builds` 映射用于模拟 CI 服务。请将 `fetchBuildStatus()` 替换为对实际服务的调用。

使用 Provider 前，先[为 `Mastra` 实例配置通知存储](/docs/signals/notifications#storage-and-dispatcher-setup)。否则 `notify()` 无法创建记录。

```typescript title="src/mastra/signals/ci-signals.ts"
import { SignalProvider } from '@mastra/core/signals'
import type { SignalProviderTarget, SignalSubscription } from '@mastra/core/signals'

type BuildStatus = {
  id: string
  status: 'passed' | 'failed'
}

const builds = new Map<string, BuildStatus>([
  ['acme-app-main', { id: 'build_123', status: 'failed' }],
])

async function fetchBuildStatus(pipeline: string): Promise<BuildStatus> {
  return builds.get(pipeline) ?? { id: 'build_unknown', status: 'passed' }
}

export class CiSignals extends SignalProvider<'ci-signals'> {
  readonly id = 'ci-signals' as const
  readonly pollInterval = 30_000

  watch(target: SignalProviderTarget, pipeline: string) {
    return this.subscribe(target, pipeline)
  }

  unwatch(target: SignalProviderTarget, pipeline: string) {
    return this.unsubscribe(target, pipeline)
  }

  async poll(subscriptions: SignalSubscription[]) {
    for (const sub of subscriptions) {
      const build = await fetchBuildStatus(sub.externalResourceId)

      if (build.status !== 'failed') continue

      await this.notify(
        {
          source: this.id,
          kind: 'ci-status',
          priority: 'high',
          summary: `Build failed for ${sub.externalResourceId}`,
          payload: build,
          dedupeKey: `${this.id}:${sub.externalResourceId}:${build.id}`,
        },
        { resourceId: sub.resourceId, threadId: sub.threadId },
      )
    }
  }
}
```

在 Agent 中注册 Provider，然后为某个线程订阅它要监控的流水线：

```typescript title="src/mastra/agents/support-agent.ts"
import { Agent } from '@mastra/core/agent'
import { CiSignals } from '../signals/ci-signals'

export const ciSignals = new CiSignals()

export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'Help the user triage CI updates.',
  model: '__GATEWAY_OPENAI_MODEL__',
  signals: [ciSignals],
})

ciSignals.watch({ resourceId: 'user_123', threadId: 'thread_456' }, 'acme-app-main')
```

Agent 会连接 Provider、执行轮询，并在流水线失败时发送通知。将 `supportAgent` 注册到 `Mastra` 实例，使 `notify()` 能访问通知存储。

## 构建 Provider {/* #build-a-provider */}

### 连接与订阅 {/* #connect-and-subscriptions */}

只有初始化逻辑依赖已连接的 Agent 时，才需要重写 [`connect()`](/reference/signals/signal-provider#connection)。务必先调用 `super.connect(agent)`。

通过以下受保护的成员管理或查询订阅：

- `subscribe(target, externalResourceId, metadata?)` 添加订阅，或将元数据合并到现有订阅中。
- `unsubscribe(target, externalResourceId)` 删除单条订阅；`unsubscribeAll(target)` 删除某线程的所有订阅。
- `getSubscriptions()`、`getSubscriptionsForResource()`、`getSubscriptionsForThread()`、`hasSubscription()` 和 `subscriptionCount` 读取订阅表，用于诊断和条件检查。

只公开应用需要的功能。CI 示例通过公开的 `watch()` 和 `unwatch()` 方法封装 `subscribe()` 和 `unsubscribe()`。

### 轮询 {/* #polling */}

如果来源无法主动推送事件，请设置以毫秒为单位的 `pollInterval`，并实现 `poll(subscriptions)`。

基类负责管理计时器：

- 没有订阅时跳过该轮，不允许两轮重叠。因此即使 `poll()` 执行较慢，也不会与下一轮并发执行。
- 捕获并记录 `poll()` 抛出的错误，然后等待下一轮。
- 对计时器调用 `unref()`，避免进程仅因轮询而持续运行。

基类不会在轮询失败后立即重试。可以等到下一轮重试，也可以在 `poll()` 内实现退避策略。

### Webhook {/* #webhooks */}

如果来源能主动调用应用，请使用 Webhook。重写 `handleWebhook(request)`，解析载荷、查找订阅，并对每个匹配项调用 `notify()`：

```typescript title="src/mastra/signals/ci-signals.ts"
import { SignalProvider } from '@mastra/core/signals'
import type { SignalProviderWebhookRequest } from '@mastra/core/signals'

export class CiSignals extends SignalProvider<'ci-signals'> {
  readonly id = 'ci-signals' as const

  async handleWebhook(request: SignalProviderWebhookRequest) {
    const payload = request.body as { pipeline: string; status: string }
    const subscriptions = this.getSubscriptionsForResource(payload.pipeline)

    for (const sub of subscriptions) {
      await this.notify(
        {
          source: this.id,
          kind: 'ci-status',
          priority: 'high',
          summary: `Build ${payload.status} for ${payload.pipeline}`,
          payload,
        },
        { resourceId: sub.resourceId, threadId: sub.threadId },
      )
    }

    return { status: 200, body: { matched: subscriptions.length } }
  }
}
```

`handleWebhook()` 是 Provider 的方法，请从自己的端点调用。如果事件来源要求验证签名，请在解析之前使用原始请求体进行验证。

### 持久化订阅 {/* #durable-subscriptions */}

基类的订阅表位于内存中，仅属于单个进程里的单个 Provider 实例。重启后不会保留，也不能跨实例共享。

如需在重启后保留订阅，请自行持久化，并在 [`start()`](/reference/signals/signal-provider#start) 中恢复。另一个进程在恢复自己的副本前，订阅表为空。

### 生命周期钩子 {/* #lifecycle-hooks */}

Agent 在构造时调用 `connect()`，启动轮询，然后调用 `start()`，但不会等待它完成。请让 `start()` 独立于首轮轮询，并处理其错误。

[`stop()`](/reference/signals/signal-provider#stop) 是同步方法，默认停止轮询并清除所有订阅索引。可以重写该方法来清理资源，但要调用 `super.stop()` 释放订阅表：

```typescript oxfmt:false
override stop() {
  this.closeClient()
  super.stop()
}
```

Agent 不会调用 `stop()`，请在关闭流程中自行调用。如果客户端需要异步关闭，请提供异步关闭方法，等待其完成后再调用 `stop()`。

### 处理器与工具 {/* #processors-and-tools */}

Provider 可以为连接的 Agent 扩展功能：

- 通过 `getInputProcessors()` 返回输入处理器，通过 `getOutputProcessors()` 返回输出处理器。
- 通过 `getTools()` 返回 Agent 可调用的工具。

Agent 在 `connect()` 之后获取这些对象一次，并将处理器注册到 Mastra 实例。

### 发送通知 {/* #send-notifications */}

[`notify()`](/reference/signals/signal-provider#notifications) 封装了所连接 Agent 的 `sendNotificationSignal()`，接受相同的字段：`source`、`kind`、`summary`，以及可选的 `priority`、`payload`、`dedupeKey`、`coalesceKey` 和 `attributes`。

同一事件可能重复到达时，用 `dedupeKey`，例如连续两次轮询都发现同一个失败构建。需要把相关事件合并为一条待处理记录时，用 `coalesceKey`。合并规则见[通知指南](/docs/signals/notifications#create-and-coalesce-records)。

Provider 未连接时，`notify()` 会抛出异常。它也会向上传递存储错误，请交由轮询或 Webhook 的错误处理逻辑处理。

### 正常关闭 {/* #shut-down-cleanly */}

关闭时：

1. 停止接收新的 Webhook 请求。
1. 使用 `stopPolling()` 或 `stop()` 停止轮询。
1. 清空订阅表。
1. 关闭或释放外部客户端和连接。
1. 如果运行环境允许，等待尚未结束的 `notify()` 调用完成。

基类在 `stop()` 中清空订阅表，但不能等待正在处理的 Webhook 结束，也不能关闭异步客户端。请在应用的关闭流程中协调这些操作。

## 内置 Provider {/* #built-in-providers */}

### 任务信号 Provider {/* #task-signal-provider */}

注册一次 [`TaskSignalProvider`](/reference/signals/task-signal-provider)，即可启用任务工具和 `TaskStateProcessor`。需要 Agent 跨轮次维护任务列表时，可以添加它：

```typescript
import { Agent } from '@mastra/core/agent'
import { TaskSignalProvider } from '@mastra/core/signals'

const agent = new Agent({
  // ...
  signals: [new TaskSignalProvider()],
})
```

它提供 `task_write`、`task_update`、`task_complete` 和 `task_check`，以及将任务列表映射到状态信号通道的处理器。任务跟踪要求线程具备 Memory 支持，并配置 `storage` 实例。没有 Memory 时，工具会提示任务跟踪需要 Agent Memory。

### Webhook 信号 Provider {/* #webhook-signal-provider */}

对于通用 Webhook 来源，可直接使用 [`WebhookSignalProvider`](/reference/signals/webhook-signal-provider)，无须编写子类。配置一个提取资源 ID 的函数，也可配置一个生成通知的函数：

```typescript title="src/mastra/index.ts"
import { Agent } from '@mastra/core/agent'
import { WebhookSignalProvider } from '@mastra/core/signals'

const webhooks = new WebhookSignalProvider({
  extractResourceId: payload => (payload as { repository: string }).repository,
  buildNotification: (payload, sub) => ({
    source: 'ci',
    kind: 'build-status',
    priority: 'medium',
    summary: `Build ${(payload as { status: string }).status} for ${sub.externalResourceId}`,
  }),
})

export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'Help the user triage updates.',
  model: '__GATEWAY_OPENAI_MODEL__',
  signals: [webhooks],
})

webhooks.subscribeThread({ resourceId: 'user_123', threadId: 'thread_456' }, 'acme/app')
```

从路由中调用 `webhooks.handleWebhook({ body, headers })`。Provider 将提取的资源 ID 与订阅匹配，并通知每个匹配的线程。

未配置 `extractResourceId` 时，Provider 从载荷中读取 `resource` 或 `externalResourceId`。未配置 `buildNotification` 时，会发送优先级为 `medium` 的 `webhook-event` 通知。

## 生产部署检查清单 {/* #production-checklist */}

部署前：

- **为重试去重：** 为每个事件设置稳定的 `dedupeKey` 或 `coalesceKey`。Webhook 可能重复投递，轮询也可能再次读到同一事件；Provider 不会在调用 `notify()` 前去重。
- **验证 Webhook：** 在解析前用原始请求体验证签名，并在 HTTP 端点拒绝无效请求。
- **处理来源不可用的情况：** 轮询会在下一个时间间隔重试，必要时在 `poll()` 中实现退避。Webhook 来源通常会自行重试，无法接收事件时请返回非 2xx 状态码。
- **按需持久化订阅：** 订阅表位于内存中。如果重启后仍要继续监控，请在 `start()` 中恢复订阅。
- **使用共享存储：** 通知记录和投递策略依赖 Agent 所用的 Mastra 存储。
- **安排关闭流程：** 停止接收 Webhook，停止轮询，关闭客户端，并等待处理中通知结束。
- **监控通知队列：** 摘要和延迟投递依赖[通知分发器](/docs/signals/notifications#dispatch)，使用共享存储时尤其如此。
