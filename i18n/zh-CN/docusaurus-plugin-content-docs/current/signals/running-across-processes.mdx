# 跨进程运行

当您运行多个 Mastra 进程时，信号可能会到达与运行Agent的进程不同的进程。这些进程需要相互传递输入并就哪个进程可以运行一个达成一致[thread](/docs/memory/message-history#threads-and-resources).

Mastra 使用共享[PubSub](/docs/server/pubsub) backend to carry signals between processes. A [lease](/reference/pubsub/lease-provider)，一种有时间限制的所有权声明，赋予一个进程对线程的责任。共享存储保存对话历史记录。当多个进程可以处理同一线程时，您需要全部三个。

## 为什么需要共享后端 {/* #why-you-need-a-shared-backend */}

默认[`EventEmitterPubSub`](/reference/pubsub/event-emitter) delivers events inside one process. That's enough for a single server, but it can't reach another instance.

考虑共享数据库的两个 API 实例。用户在 A 上启动运行，然后他们的下一条消息到达 B。如果没有共享后端，B 无法发布到 A 的运行并在同一线程上启动第二次运行。两者都调用模型并写入消息，从而留下竞争运行。

共享后端修复交付：B 在线程主题上发布，A 进行消费。租约可确保只有一个进程声明该线程。到达它的其他路线。

每个可以处理相同线程的实例都需要相同的 PubSub 后端和存储。不同的后端无法针对同一数据库进行协调。

## 选择拓扑 {/* #choose-a-topology */}

根据进程运行的位置选择后端。

|部署|后端 |它提供什么 |
| - | - | - |
|一个流程 |[`EventEmitterPubSub`](/reference/pubsub/event-emitter) (default) | In-process delivery and leases |
| Several processes on one host | [`UnixSocketPubSub`](/reference/pubsub/unix-socket-pubsub) | Delivery and leases over a Unix domain socket |
| Several hosts | [`RedisStreamsPubSub`](/reference/pubsub/redis-streams) or [`ValkeyStreamsPubSub`](/reference/pubsub/valkey-streams) | Cross-host delivery, retained events, and leases |
| Several hosts with Google Cloud Pub/Sub | [`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub) | Cross-host delivery without leases |

[`UnixSocketPubSub`](/reference/pubsub/unix-socket-pubsub)选择一个进程作为套接字Agent，如果退出则重新选择一个新进程。它不能跨机器工作。

[`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub)跨进程传递事件但不实现租约。 Mastra 无法判断哪个实例拥有线程，因此任何接收到信号的实例都可以尝试运行它。仅当另一层保证每个线程一个进程时才使用它。

## 线程所有权和租约 {/* #thread-ownership-and-leases */}

Mastra 在开始跑步之前获得了租约。只有持有者可以运行该线程，其他进程将信号路由到它。

默认情况下，租约持续 15 秒，所有者每 5 秒更新一次。续订间隔是租约生存时间 (TTL) 的三分之一。这让业主有时间在索赔到期之前从错过的续约中恢复过来。看[Configuration](#configuration) to change these values.

如果续约失败且当地截止日期已过，业主将停止跑步。它无法再证明另一个进程没有声明该线程，并且继续意味着两个所有者向一个对话写入内容。然后，新所有者从存储中开始下一次运行。

[持久剂](/docs/harness/durable-agents#run-ownership)当Workflow存储不支持运行防护时，使用相同的租约。支持隔离的存储会记录声明并拒绝来自丢失声明的执行的写入。这[`LeaseProvider` reference](/reference/pubsub/lease-provider) documents the contract.

## 将信号路由到另一个进程 {/* #route-signals-to-another-process */}

当信号到达时，运行时会查找线程的当前所有者。如果发布了一个信号，则该信号将在线程主题上发布，并且所有者会加入其活动运行或从其队列中启动一个运行。

如果没有通告所有者，则接收进程会尝试声明该线程。获胜意味着该进程运行Agent。丢失意味着另一个进程先声明了它，因此该进程转发信号并`accepted` resolves to `deliver` rather than `wake`. [`sendSignal()`](/reference/agents/agent#sendsignalsignal-options) documents the accepted result.

放`ifIdle.requireClaimedOwner: true` when an idle wake must not start a run on an arbitrary instance. The wake only reaches an advertised owner, and `accepted` rejects if none responds within the discovery window.

## 交货保证和副本 {/* #delivery-guarantees-and-duplicates */}

PubSub 后端可以在超时、确认失败或崩溃后重新传送事件。因此，运行时假设至少传递一次。当所有者保留其簿记时，重新传递的信号不会启动同一逻辑消息的第二次运行。

这并不能保证每个事件都一次性交付。如果您的处理程序写入数据库或触发其他操作，请使其具有幂等性：处理同一事件两次应该与处理一次具有相同的效果。

## 信号和进程崩溃 {/* #signals-and-process-crashes */}

崩溃后什么能幸存取决于数据所在的位置：

* 运行时队列驻留在进程内存中。在跑步消耗它们之前发生的碰撞会丢失这些信号。
* 发送的信号`persist` behavior are written to memory storage and survive a restart when that storage is shared.
* [状态信号](/docs/signals/state-signals)它们的跟踪存储在线程上，并通过共享存储重新启动后仍然存在。
* [通知](/docs/signals/notifications)是通知存储中的持久记录。他们的调度员可以在重新启动后重试交付。
* 共享 PubSub 后端传输事件，但不是持久的输入队列。保留的事件可以帮助订阅者重新连接，但它们不会取代存储。
* 持久Agent恢复从其检查点恢复运行。它不会恢复崩溃进程的内存信号队列。

如果信号必须在接受它的进程中幸存下来，请将其保留或记录在您自己的系统中。不要依赖 PubSub 保留作为记录系统。

## 无服务器 {/* #serverless */}

无服务器函数一旦返回响应就会冻结。如果您的函数开始运行，请通过消耗其输出流来使其保持活动状态，直到运行完成。

将此工作传递给您的平台`waitUntil` so it can continue after the HTTP response:

```typescript title="src/routes/signal.ts"
const result = agent.sendSignal(signal, { resourceId, threadId })

ctx.waitUntil(
  result.accepted.then(async accepted => {
    if (accepted.action === 'wake') {
      await accepted.output.consumeStream()
    }
  }),
)
```

当另一个进程拥有该线程时，`accepted` resolves to `deliver` and there's no local output to drain. When this invocation wins the lease, it gets `wake` and must stay alive until the output settles.

在无服务器平台上也使用共享的 PubSub 后端和共享存储。短暂的实例使得内存中的队列特别脆弱。

## 优雅关机 {/* #graceful-shutdown */}

停止接受新的 webhook 或信号请求，然后让正在进行的工作稳定下来。生成的Mastra服务器句柄`SIGINT` and `SIGTERM`, stops accepting connections, drains active requests, and calls [`mastra.shutdown()`](/docs/deployment/mastra-server#graceful-shutdown-and-rolling-deploys). If you embed Mastra in your own server, call it from your shutdown hook.

信号提供者有自己的生命周期。称呼[`provider.stop()`](/reference/signals/signal-provider#stop) to stop polling and clear in-memory subscriptions. Stop routing webhooks to a [`WebhookSignalProvider`](/reference/signals/webhook-signal-provider) before shutdown so new requests don't arrive while the process exits.

## 配置 {/* #configuration */}

共享的 Redis Streams 后端处理信号传递和线程租用：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { PostgresStore } from '@mastra/pg'
import { RedisStreamsPubSub } from '@mastra/redis-streams'

export const mastra = new Mastra({
  agents: { agent },
  storage: new PostgresStore({
    id: 'mastra-storage',
    connectionString: process.env.DATABASE_URL,
  }),
  pubsub: new RedisStreamsPubSub({
    url: process.env.REDIS_URL,
    keyPrefix: 'mastra:my-app',
  }),
})
```

每个实例点`storage` at the same database, so persisted signals, state signals, and notification records survive a restart and are visible to whichever process owns the thread.

使用相同的`keyPrefix` on every coordinating instance, and a different prefix for environments sharing one Redis server. Vercel's managed Redis and Upstash Redis both work with `RedisStreamsPubSub`.

租约设置是环境变量：

* `MASTRA_AGENT_THREAD_LEASE_TTL_MS`设置租赁期限。默认为`15000` milliseconds.
* `MASTRA_AGENT_THREAD_LEASE_RENEW_INTERVAL_MS`设置更新间隔。默认值为 TTL 的三分之一，并且不短于 TTL 的值将回退到该值。

保持两个值在实例之间保持一致。较短的 TTL 可以更快地释放崩溃的所有者线程，但为缓慢更新留下的空间较小。较长的 TTL 会起到相反的作用。保留默认值，除非您的部署有理由更改它们。请参阅[`RedisStreamsPubSub` reference](/reference/pubsub/redis-streams) for other backends.
