# Sandbox 与文件系统

{/* vale ai-tells.VerbTricolon = NO */}

Sandbox 为 Agent 提供隔离环境，用于运行命令、执行代码、安装依赖和管理进程。这样，Agent 就能完成直接在应用内运行有风险、耗费大量资源或不切实际的工作。

Sandbox 往往是临时的，环境停止后其中创建的文件可能消失。[文件系统](/docs/sandbox/filesystem)为 Agent 提供可读写、可[搜索](/docs/sandbox/search)的文件存储位置，文件可以比 Sandbox 存续更久。它可用于跨运行保存输出、用现有文件初始化新 Sandbox，或提供工作时可搜索的文档。即使没有 Sandbox，也可以使用文件系统，例如 Agent 只需知识库或 Google Drive 等服务中的文件时。[Mastra Factory](https://factory.mastra.ai/) 就使用 Sandbox，为编程 Agent 会话提供检出仓库、安装依赖和运行命令的环境。

{/* vale ai-tells.VerbTricolon = YES */}

## 何时使用 Sandbox {/* #when-to-use-sandboxes */}

当 Agent 需要完成以下工作时，可使用 Sandbox：

- 在独立环境中克隆仓库并运行 Shell、Git、构建或测试流程。
* 使用专门的库处理 PDF、演示文稿或其他文件并生成新的工件。
* 在具有隔离文件和进程的单独环境中运行长期或并行工作。

如果 Agent 只需读取、写入或搜索文件，请配置[直接访问文件系统](/docs/sandbox/filesystem#direct-filesystem-access)。

## 快速入门 {/* #quickstart */}

为 Agent 提供本地 Sandbox：

```typescript title="src/mastra/agents/coding-agent.ts"
import { Agent } from '@mastra/core/agent'
import { LocalSandbox, Workspace } from '@mastra/core/workspace'

export const codingAgent = new Agent({
  id: 'coding-agent',
  name: 'Coding agent',
  instructions: 'Use the sandbox to complete coding tasks.',
  model: '__GATEWAY_OPENAI_MODEL__',
  workspace: new Workspace({
    sandbox: new LocalSandbox({
      workingDirectory: './workspace',
    }),
  }),
})

await codingAgent.generate('List the files in the sandbox directory')
```

:::warning

`LocalSandbox` 默认在应用宿主机上运行命令，既无隔离也不安全。运行不可信代码时，请启用[原生隔离](#localsandbox)，或使用远程、容器 Sandbox。

:::

静态 Sandbox 由使用该 Agent 的所有请求和 Memory 线程共享。如果每个用户或线程都需要独立环境，请使用[解析器](#sandboxes-per-user-or-thread)。共享与清理细节参见[生命周期和持久化](#lifecycle-and-persistence)。

## 使用 Sandbox {/* #using-the-sandbox */}

Agent 会收到 Sandbox 后端所支持能力对应的 Tool：

| Tool | 作用 |
| - | - |
| `execute_command` | 运行 Shell 命令，返回 stdout、stderr 和退出码。后端支持启动长期进程时，可使用 `background: true`。 |
| `get_process_output` | 获取后台进程的 stdout、stderr 和状态。支持用 `tail` 限制输出，以及用 `wait: true` 等待进程退出。对于静态 Sandbox，只有后端支持后台进程时才会添加此工具和 `kill_process`。按请求解析 Sandbox 的 Workspace 总会包含这两个工具，因为解析前无法确定后端能力。 |
| `kill_process` | 停止后台进程并返回其最近的输出。 |

配置的能力决定哪些 Tool 可用。随后还可在 Tool 配置中禁用、重命名工具，或为其添加策略：

```typescript
import { LocalSandbox, Workspace, WORKSPACE_TOOLS } from '@mastra/core/workspace'

const workspace = new Workspace({
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
  tools: {
    requireApproval: true,
    [WORKSPACE_TOOLS.SANDBOX.EXECUTE_COMMAND]: {
      enabled: false,
    },
  },
})
```

为某个工具设置 `{ enabled: false }` 可将其移除；在顶层设置 `enabled: false` 则会默认禁用生成的工具。单个工具的 `{ enabled: true }` 会覆盖全局设置。顶层 `requireApproval` 策略适用于所有生成的工具，除非单个工具的配置将其覆盖。

所有生成的工具见 [Sandbox 工具参考](/reference/workspace/workspace-class#sandbox-tools)；审批、输出限制及 Hook 见[工具配置参考](/reference/workspace/workspace-class#tool-configuration)。

{/* vale ai-tells.VerbTricolon = NO */}

应用编写的运行时函数（包括 Tool 和 Workflow 步骤）可从执行上下文获取当前 Sandbox，用于运行命令、安装依赖、处理文件或启动长期进程。

{/* vale ai-tells.VerbTricolon = YES */}

```typescript title="src/mastra/tools/start-server.ts"
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

export const startServerTool = createTool({
  id: 'start-server',
  description: 'Starts a server in the sandbox',
  inputSchema: z.object({
    command: z.string(),
  }),
  execute: async ({ command }, ctx) => {
    if (!ctx.workspace || !ctx.requestContext) {
      throw new Error('This tool requires a workspace execution context')
    }

    const sandbox = await ctx.workspace.resolveSandbox({
      requestContext: ctx.requestContext,
    })

    if (!sandbox?.processes) {
      throw new Error('The configured sandbox does not support background processes')
    }

    const server = await sandbox.processes.spawn(command)
    return { pid: server.pid }
  },
})
```

## Sandbox {/* #sandboxes */}

### `LocalSandbox` {/* #localsandbox */}

[`LocalSandbox`](/reference/workspace/local-sandbox) 与 Mastra 应用在同一台机器上执行命令。默认情况下，命令直接以应用进程的权限在宿主机运行。

`workingDirectory` 只指定命令的运行位置。Mastra 不会把项目复制进去。若要为 Agent 提供独立的仓库检出，请在源码仓库外的目录运行 `git clone` 或 `git worktree add`。

```typescript
const sandbox = new LocalSandbox({
  workingDirectory: './workspace',
  isolation: 'seatbelt', // Use 'bwrap' on Linux
  nativeSandbox: {
    allowNetwork: false,
    readOnlyPaths: ['./reference-data'],
  },
})
```

启用原生隔离，可在操作系统层限制文件系统和网络访问。macOS 使用 Seatbelt（`sandbox-exec`），Linux 使用 Bubblewrap（`bwrap`）。可用 `LocalSandbox.detectIsolation()` 检查当前操作系统是否支持其中一种。

[`nativeSandbox` 选项](/reference/workspace/local-sandbox#nativesandboxconfig)控制网络访问、只读或可写路径、工作目录的写入权限，以及系统二进制文件。也可以提供自定义 Seatbelt 配置或 Bubblewrap 参数。完整配置见 [`LocalSandbox`](/reference/workspace/local-sandbox)。

### 远程Sandbox {/* #remote-sandboxes */}

当命令需要与宿主应用更强的隔离，或工作负载超过应用服务器的资源时，请使用远程或容器 Sandbox。各 Sandbox 的隔离、持久化、网络和挂载行为不同：

<IntegrationGrid section="Sandboxes" />

如果 Mastra 不支持所用的 Sandbox Provider，可实现 [Sandbox Provider 接口](/reference/workspace/sandbox)来接入。

## 文件系统 {/* #filesystem */}

每个 Sandbox 都有用于执行命令的文件系统。`LocalSandbox` 使用宿主机文件系统；远程 Sandbox 则有独立的文件系统，通常是临时的。需要在 Sandbox 结束后保留文件时，请使用外部存储。

Mastra 文件系统将 Agent 和 Sandbox 连接到 Amazon S3、Google Cloud Storage 或 Google Drive 等由 Provider 提供的存储。配置后，Agent 会获得读写和搜索文件的 Tool。远程 Sandbox 和 Provider 都支持挂载时，Mastra 会通过用户空间文件系统（FUSE）自动挂载存储。命令照常使用文件路径，变更则由 Sandbox 外的 Provider 保存。

Provider、文件工具及挂载方式见[文件系统](/docs/sandbox/filesystem)。

## 电脑使用 {/* #computer-use */}

受支持的桌面 Sandbox 可让 Agent 控制截图、鼠标和键盘。支持情况及配置见[计算机操作](/docs/sandbox/computer)。

## 每个用户或线程的Sandbox {/* #sandboxes-per-user-or-thread */}

如果每个用户、租户或线程都需要独立 Sandbox，请使用**解析器**。将 `sandboxCacheKey` 设为 Sandbox 所属身份，以便后续请求复用同一个运行中的环境。

此示例为每个用户创建并缓存一个 Daytona Sandbox：

```typescript title="src/mastra/workspaces.ts"
import { Workspace } from '@mastra/core/workspace'
import { DaytonaSandbox } from '@mastra/daytona'

const workspace = new Workspace({
  sandbox: async ({ requestContext }) => {
    const userId = requestContext.get('user-id') as string
    const sandbox = new DaytonaSandbox({ id: `user-${userId}` })
    await sandbox.start()
    return sandbox
  },
  sandboxCacheKey: ({ requestContext }) => requestContext.get('user-id') as string,
})
```

用户的第一个请求将创建Sandbox。具有相同用户 ID 的后续请求将重用它。

对于需要持久存储的 Sandbox，请创建[文件系统](/docs/sandbox/filesystem)并在解析器中挂载。此示例为每个 Memory 线程分别创建一个 Daytona Sandbox 和一个 S3 存储前缀，然后把存储挂载到 `/workspace`：

```typescript title="src/mastra/workspaces.ts"
import { MASTRA_THREAD_ID_KEY, type RequestContext } from '@mastra/core/request-context'
import { Workspace } from '@mastra/core/workspace'
import { DaytonaSandbox } from '@mastra/daytona'
import { S3Filesystem } from '@mastra/s3'

const getThreadId = (requestContext: RequestContext) => {
  const threadId = requestContext.get(MASTRA_THREAD_ID_KEY)
  if (typeof threadId !== 'string' || !threadId) {
    throw new Error('MASTRA_THREAD_ID_KEY is not set on the request context')
  }
  return threadId
}

const createThreadFilesystem = (threadId: string) =>
  new S3Filesystem({
    bucket: process.env.S3_BUCKET!,
    region: process.env.S3_REGION!,
    prefix: `threads/${threadId}`,
  })

const workspace = new Workspace({
  filesystem: ({ requestContext }) => createThreadFilesystem(getThreadId(requestContext)),
  sandbox: async ({ requestContext }) => {
    const threadId = getThreadId(requestContext)
    const sandbox = new DaytonaSandbox({
      id: `thread-${threadId}`,
      language: 'typescript',
    })

    await sandbox.start()
    await sandbox.mount(createThreadFilesystem(threadId), '/workspace')
    return sandbox
  },
  sandboxCacheKey: ({ requestContext }) => getThreadId(requestContext),
})
```

解析器只接收请求上下文，因此线程 ID 必须放在其中。`agent.stream()` 和 `agent.generate()` 不会把 `memory.thread` 复制到 `MASTRA_THREAD_ID_KEY`。请从可信的线程 ID 自行设置该键，可在[服务端中间件](/docs/server/request-context#reserved-keys)中设置，也可在调用 Agent 时设置：

```typescript
import { MASTRA_THREAD_ID_KEY, RequestContext } from '@mastra/core/request-context'

const requestContext = new RequestContext()
requestContext.set(MASTRA_THREAD_ID_KEY, threadId)

await agent.stream(message, {
  memory: { thread: threadId, resource: userId },
  requestContext,
})
```

缺少该键时，`getThreadId()` 会抛错。因此，没有线程的请求会失败，而不会与其他此类请求共享 `threads/undefined` 前缀和 Sandbox。

线程的首个请求会运行解析器并启动 Sandbox；后续同 ID 请求复用缓存的 Sandbox。不同线程 ID 会创建不同的 Sandbox 和存储前缀。

此示例在解析器内挂载文件系统，因为静态 `mounts` 不能与 Sandbox 解析器组合使用。生成的工具会根据请求上下文自动解析文件系统和 Sandbox。

:::warning

由解析器返回的 Sandbox 归应用负责管理。用户、线程或会话结束时，请销毁这些 Sandbox，并调用 `workspace.clearSandboxCache(cacheKey)`。`workspace.destroy()` 不会销毁解析器返回的 Sandbox。

:::

### Agent Workspace 函数 {/* #agent-workspace-functions */}

Agent 的 `workspace` 选项也可接受返回 `Workspace` 的函数。Mastra 每次需要 Agent 的 Workspace 时都会调用它，而不限于 Agent 运行时；包括启动时注册 Agent，以及读取 Agent 元数据。Studio 列出 Agent 时会调用 `GET /api/agents` 和 `GET /api/agents/:agentId`。这些调用不会被缓存。

该函数应保持轻量，不要在其中启动 Sandbox 或其他付费基础设施。请返回一个使用 `filesystem` 和 `sandbox` 解析器的 Workspace。Mastra 会在为运行构建 Workspace 指令、工具需要 Provider，以及读取 Agent 的 Workspace Skill 时调用文件系统解析器，包括访问 Agent 元数据路由时。Sandbox 解析器只在工具需要 Provider 时调用，除非将 `instructions.dynamicSandbox` 设为 `'resolve'`。

### Tool可用性 {/* #tool-availability */}

使用静态 Sandbox 时，Mastra 知道后端支持哪些能力，只向 Agent 提供对应的 Tool。应用代码在使用可选能力前也应检查其是否可用。

[解析器支持的 Sandbox](#sandboxes-per-user-or-thread) 要到请求时才能确定，因此 Mastra 最初会暴露所有 Sandbox 工具。若调用解析后端不支持的工具，会抛出 `SandboxFeatureNotSupportedError`。

## 后台进程 {/* #background-processes */}

Agent 通过 `execute_command` 启动后台进程时，可以接收 stdout、stderr 和进程退出的生命周期回调。请在 `WORKSPACE_TOOLS.SANDBOX.EXECUTE_COMMAND` 对应配置项中设置 `backgroundProcesses`：

```typescript title="src/mastra/workspaces.ts"
import { Workspace, LocalSandbox, WORKSPACE_TOOLS } from '@mastra/core/workspace'

const workspace = new Workspace({
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
  tools: {
    [WORKSPACE_TOOLS.SANDBOX.EXECUTE_COMMAND]: {
      backgroundProcesses: {
        onStdout: (data, { pid }) => console.log(`[${pid}] ${data}`),
        onStderr: (data, { pid }) => console.error(`[${pid}] ${data}`),
        onExit: ({ pid, exitCode }) => console.log(`Process ${pid} exited: ${exitCode}`),
      },
    },
  },
})
```

这些回调会在 Agent 通过 `execute_command` 启动的所有后台进程上触发。

默认情况下，后台进程继承 Agent 的中止信号，并在 Agent 断开连接时停止。如果请求结束后进程仍需继续运行，请将 `abortSignal` 设为自定义信号，或使用 `null` 或 `false`。

完整的 `SandboxProcessManager` API（包括通过代码启动进程、获取输出和写入标准输入）见 [`SandboxProcessManager` 参考](/reference/workspace/process-manager)。

## 生命周期和持久性 {/* #lifecycle-and-persistence */}

Sandbox 由谁共享，取决于配置位置以及是否使用解析器：

| 配置 | 共享 Sandbox 的对象 |
| - | - |
| Mastra 级配置 | 继承 [`Mastra`](/reference/configuration) 实例配置的 Agent 共用同一个 Sandbox。 |
| Agent 级配置 | 该 Agent 实例处理的所有请求共用同一个 Sandbox。 |
| 按资源划分的解析器 | 每个资源 ID 缓存一个 Sandbox。 |
| 按线程划分的解析器 | 同一 Memory 线程中的多个请求共用其 Sandbox。 |

静态 Sandbox 不会自动限定到当前资源或 Memory 线程。若要按资源或线程隔离，请使用解析器，并将 `sandboxCacheKey` 设为相应 ID。参见[按用户或线程创建 Sandbox](#sandboxes-per-user-or-thread)。

### 开始 {/* #start */}

静态 Sandbox 环境通常在运行首个命令时启动，大多数应用无需显式初始化。只有希望在接收请求前启动静态 Sandbox 并准备挂载时，才应在应用启动期间调用 `workspace.init()`。这适用于希望凭据、网络或 Provider 错误在启动时而非首个命令运行时暴露的情况。

`workspace.init()` 不会启动解析器提供的 Sandbox，因为请求运行前尚未选定 Sandbox。解析器应返回已启动或首次使用时可自行启动的 Sandbox。

### 挂钩 {/* #hooks */}

使用 `onStart`、`onStop` 和 `onDestroy`，可在生命周期转换时运行应用代码。Hook 会收到当前运行中的 Sandbox 实例：

```typescript
const sandbox = new LocalSandbox({
  workingDirectory: './workspace',
  onStart: ({ sandbox }) => console.log(`Started ${sandbox.id}`),
  onStop: ({ sandbox }) => console.log(`Stopping ${sandbox.id}`),
  onDestroy: ({ sandbox }) => console.log(`Destroying ${sandbox.id}`),
})
```

`onStart` 在 Sandbox 启动后运行。`onStop` 和 `onDestroy` 则在对应操作执行前运行。

### 清理 {/* #cleanup */}

直接配置而非通过解析器创建 Sandbox 时，由 Mastra 负责管理。`mastra dev` 和生成的 Mastra Server 会处理关闭信号并自动销毁已注册资源。如果将 Mastra 嵌入自定义服务器或进程，请在关闭 Hook 中调用 `mastra.shutdown()`；独立使用 Workspace 时，直接调用 `workspace.destroy()`。

`stop()` 与 `destroy()` 的行为由后端决定。例如，停止可能会关闭计算资源，但保留可重启的环境；销毁则可能删除环境及其临时文件。依赖任一行为前，请查看所选后端的说明。

解析器返回的 Sandbox 由应用负责管理。`workspace.destroy()` 和 `mastra.shutdown()` 只会清除缓存引用，不会销毁已解析的 Sandbox。应用的生命周期代码必须跟踪这些 Sandbox，在对应用户、线程或会话结束时调用 `destroy()`，随后调用 `workspace.clearSandboxCache(cacheKey)`。这样可避免闲置计算资源持续运行，也可防止后续请求复用过期的 Sandbox。

### 持久性 {/* #persistence */}

持久化行为取决于后端。Sandbox 停止或应用重启后，文件和进程不一定仍然存在；空闲超时也可能清除它们。有些后端能通过 Sandbox ID 重新连接，或保留快照和卷；其他后端则会创建全新环境。

每个 Sandbox 都有 `id`，但该 ID 并不保证跨后端持久化。依赖重新连接或持久状态前，请先阅读所选后端的参考文档。

## 网络和凭证安全 {/* #network-and-credential-safety */}

Mastra 没有一套适用于所有 Sandbox 后端的统一网络策略。默认值和支持的控制项因后端而异，运行不可信代码前请先检查。对于敏感或生产工作负载，建议阻止出站访问，或只允许任务所需的目的地。创建 Sandbox 时就应应用策略，以便在命令运行前生效。

如果 Agent 在远程 Sandbox 中启动 Web 服务器，服务器最初只监听 Sandbox 内的端口。支持端口暴露的后端会实现 `sandbox.networking.getPortUrl()`，返回可从 Sandbox 外预览或测试服务器的 URL：

```typescript
const url = await sandbox.networking?.getPortUrl(8000)
```

根据后端访问控制，这个 URL 可能让其他人也能访问服务。这种入站暴露与 Sandbox 的出站访问是两回事。启用原生隔离的 `LocalSandbox` 默认阻止网络访问，除非开启 `allowNetwork`；不启用原生隔离时，本地命令使用宿主机网络。

例如，`DaytonaSandbox` 默认允许出站访问，除非你配置限制。如果任务只需访问特定服务，可设置 `networkBlockAll` 并配置域名允许列表：

```typescript
import { DaytonaSandbox } from '@mastra/daytona'

const sandbox = new DaytonaSandbox({
  networkBlockAll: true,
  domainAllowList: 'registry.npmjs.org,api.github.com',
})
```

Daytona 会在创建 Sandbox 时应用这些设置，也支持通过 `networkAllowList` 配置 CIDR 规则。完整配置见 [Daytona 集成页面](/integrations/sandboxes/daytona)。

传入 Sandbox 或命令的环境变量可被其中运行的代码读取。Mastra 不提供跨后端的凭据代理，让请求获得授权的同时将密钥留在 Sandbox 外。请只向命令提供本任务所需的凭据，并遵循所选后端的密钥管理指南。

例如，应将只读 Token 仅传给需要它的命令，而非为 Sandbox 中的每个命令配置：

```typescript
await sandbox.executeCommand('node', ['scripts/download-reports.js'], {
  env: {
    REPORTS_READ_TOKEN: process.env.REPORTS_READ_TOKEN,
  },
})
```
