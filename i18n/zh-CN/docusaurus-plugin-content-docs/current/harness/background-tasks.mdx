# 后台任务

**新增于：** `@mastra/core@1.29.0`

后台任务让 Agent 分派耗时的 Tool 调用，而不阻塞 Agent 循环。Tool 会立即返回确认，LLM 则继续生成响应；任务随后在后台运行直至完成。完成后，结果会写入 memory，Agent 再运行一轮来报告结果。使用 [`untilIdle`](/reference/streaming/agents/stream) 时，这一轮会在同一次调用中继续输出流；否则，Agent 会在线程中收到通知，详见[流结束后报告结果](#report-a-result-after-the-stream-ends)。

## 何时使用后台任务 {/* #when-to-use-background-tasks */}

如果 Tool 调用可能耗时较长，不适合让用户等到它完成才看到响应，就可以使用后台任务。常见场景包括：

- 将需要多步研究或写作的工作委派给子 Agent。
- 调用响应较慢的外部服务、队列，或处理大型数据任务。
- 从 Tool 调用触发可能需要数分钟才能完成的 Workflow。

对于能快速返回的 Tool 调用，使用 `agent.stream()` 或 `agent.generate()` 在前台执行更简单。

:::note

后台任务要求 Mastra 实例已配置 [storage](/docs/storage) 后端。任务会持久化，因此进程重启后仍可继续。

:::

## 快速开始 {/* #quickstart */}

后台任务默认关闭。可在 Mastra 实例上设置 `backgroundTasks.enabled` 来启用：

```typescript title="src/mastra/index.ts" {6-12}
import { Mastra } from '@mastra/core'
import { LibSQLStore } from '@mastra/libsql'

export const mastra = new Mastra({
  storage: new LibSQLStore({ id: 'storage', url: 'file:mastra.db' }),
  backgroundTasks: {
    enabled: true,
    globalConcurrency: 10,
    perAgentConcurrency: 5,
    backpressure: 'queue',
    defaultTimeoutMs: 300_000,
  },
})
```

完整选项见 [backgroundTasks 配置参考](/reference/configuration#backgroundtasks)。

## 在后台运行 Tool {/* #run-a-tool-in-the-background */}

仅启用管理器不会自动让任何调用在后台运行。可以在以下两个层级声明 Tool 有资格在后台执行：

1. **Tool 级配置**：由 Tool 自身声明。
1. **Agent 级配置**：由 Agent 指定其哪些 Tool 可在后台执行。

符合条件的 Tool 默认使用 `deferred` 执行方式。如果只想让 LLM 可以选择后台运行，而不将其设为默认行为，可在任一层级设置 `defaultDisposition: 'foreground'`。LLM 可在某次 Tool 调用的参数中加入 `_background` 字段，选择 `foreground`、`deferred` 或 `awaited`，也可覆盖该次调用的超时与重试设置。

### Tool 级配置 {/* #tool-level */}

在 Tool 定义中设置 `background.enabled: true`。启用管理器的 Agent 调用此类 Tool 时，才可在后台执行。除非该次调用通过 `_background` 覆盖设置，否则配置的默认执行方式决定它是同步执行还是在后台执行。

```typescript title="src/mastra/tools/research.ts"
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

export const researchTool = createTool({
  id: 'research',
  description: 'Run a long research job',
  inputSchema: z.object({ topic: z.string() }),
  // highlight-start
  background: {
    enabled: true,
    defaultDisposition: 'deferred',
    timeoutMs: 600_000,
    maxRetries: 1,
  },
  // highlight-end
  execute: async ({ topic }) => {
    // Run the research job for topic
  },
})
```

### Agent 级配置 {/* #agent-level */}

在 Agent 上使用 `backgroundTasks.tools`，可启用指定 Tool、覆盖单个 Tool 的超时设置，或让所有符合条件的 Tool 在后台执行。使用 `disabled: true` 可完全关闭该 Agent 的后台分派。

```typescript title="src/mastra/agents/researcher.ts"
import { Agent } from '@mastra/core/agent'

export const researcher = new Agent({
  id: 'researcher',
  instructions: 'You research topics and answer questions.',
  model: '__GATEWAY_OPENAI_MODEL__',
  tools: { researchTool, summarizeTool },
  // highlight-start
  backgroundTasks: {
    tools: {
      researchTool: { enabled: true, timeoutMs: 600_000 },
      summarizeTool: false,
    },
  },
  // highlight-end
})
```

设置 `tools: 'all'`，即可启用 Agent 拥有的所有 Tool。

### LLM 逐次调用覆盖 {/* #llm-per-call-override */}

当 Tool 注册到已启用后台任务的 Agent 上时，模型可以在 Tool 参数中加入 `_background` 字段，覆盖该次调用解析后的配置。模型只需提供要覆盖的字段；`_background` 中的所有字段都是可选的。Tool 执行前，该覆盖字段会从参数中移除。

```json
{
  "topic": "solana",
  "_background": { "disposition": "awaited", "timeoutMs": 900000 }
}
```

可用的执行方式如下：

- `foreground`：同步执行 Tool，不发送后台任务生命周期信号。
- `deferred`：分派 Tool 后让 Agent 继续执行。任务仍关联到该次运行；使用 `untilIdle` 的流会等待任务结果完成协调。
- `awaited`：通过后台任务管理器分派 Tool，但当前分支会等待其权威结果完成协调。

为兼容旧用法，`_background.enabled: true` 对应 `deferred`，`_background.enabled: false` 对应 `foreground`。显式设置的 `disposition` 优先于 `enabled`。

`_background` 只能_修改_开发者已在 Tool 或 Agent 层级启用的 Tool。若未启用，模型选择的后台执行方式会被忽略，Tool 仍在前台执行。这可避免计算器、查询、Schema 校验器等应确定性地在前台执行的 Tool 被悄然分派为后台任务。

### 配置解析顺序 {/* #resolution-order */}

分派 Tool 调用时，Agent 级和 Tool 级设置决定它是否符合条件，以及各项回退值。对于符合条件的 Tool，LLM 提供的 `_background` 字段覆盖该次调用相应的值；未设置的超时和重试值由管理器默认值补足。`_background` 不能启用原本不符合条件的 Tool。

超时值 `0` 表示不设超时。希望任务一直运行到完成或被取消时，可在 Tool 或 Agent 的 Tool 配置中设置 `timeoutMs: 0`，或在管理器上设置 `defaultTimeoutMs: 0`。

如果 Agent 设置了 `backgroundTasks.disabled: true`，无论上述层级如何配置，所有 Tool 调用都会同步执行。

## 后台任务相关的流数据块 {/* #background-tasks-related-stream-chunks */}

Tool 调用被分派为后台任务时，有两种流可能提供其生命周期事件：Agent 自身的流，以及 [`backgroundTaskManager.stream()`](/docs/harness/background-tasks#subscribe-to-all-task-events) SSE 流。两者涵盖的数据块类型不同：

| 数据块类型 | 触发时机 | 发送方 |
| - | - | - |
| `background-task-started` | 任务入队并获得 `taskId` 时。 | Agent 流 |
| `background-task-running` | Worker 领取任务并开始执行时。 | 管理器流 |
| `background-task-progress` | 显示正在运行的后台任务数量时。 | Agent 流 |
| `background-task-output` | 任务的 `execute` 输出一个流数据块时。 | 管理器流 |
| `background-task-completed` | 任务成功完成时。`payload.result` 与最终的 Tool 结果一致。 | 管理器流 |
| `background-task-failed` | 任务抛出异常或超时时。 | 管理器流 |
| `background-task-cancelled` | 任务在完成前被取消时。 | 管理器流 |
| `background-task-suspended` | Tool 在 execute 中调用 `suspend()` 时。 | 管理器流 |
| `background-task-resumed` | 挂起的任务通过 `manager.resume(taskId, resumeData)` 恢复时。 | 管理器流 |

单独使用 `agent.stream().fullStream` 时，它只发送 Agent 循环的数据块（`background-task-started`、`background-task-progress`）。使用 `untilIdle: true` 的 `agent.stream()` 也会发送这两种数据块，并订阅该次运行的 memory 范围内的管理器 pubsub，将管理器的七种数据块（`background-task-running`、`background-task-output`、`background-task-completed`、`background-task-failed`、`background-task-cancelled`、`background-task-suspended`、`background-task-resumed`）汇入同一个 `fullStream`。

`backgroundTaskManager.stream()` 只发送管理器的七种数据块。

完整的 payload 结构见[后台任务数据块参考](/reference/streaming/ChunkType#background-task-chunks)。

## 使用 `untilIdle` 保持 Agent 流打开 {/* #keep-the-agent-stream-open-with-untilidle */}

即使后台任务仍在运行，LLM 发出最终响应后，`agent.stream()` 也会返回。传入 `untilIdle: true` 可让流持续打开，直到所有已分派的后台任务完成，且 LLM 有机会响应其结果：

```typescript title="src/mastra/run.ts"
const stream = await agent.stream('Research solana for me', {
  memory: { thread: 't1', resource: 'u1' },
  untilIdle: true,
})

for await (const chunk of stream.fullStream) {
  // chunks from the initial turn AND any continuation turns triggered by
  // background task completions flow through here
}
```

后台任务完成后，结果会写入 Agent memory，`stream()` 会重新进入 Agent 循环，让 LLM 对结果作出响应。没有运行中的任务或待处理的完成结果时，流会关闭。

若要自定义空闲超时，可传入对象而非 `true`。计时器只在包装器等待两轮之间运行，因此首个 token 生成较慢不会关闭流。默认值为 5 分钟：

```typescript
const stream = await agent.stream('Research solana for me', {
  memory: { thread: 't1', resource: 'u1' },
  untilIdle: { maxIdleMs: 30_000 },
})
```

完整 API 见 [`Agent.stream()`](/reference/streaming/agents/stream)。

若要修改每次 `untilIdle: true` 调用的默认值，包括 Mastra 内部发起的调用，可在 Mastra 的 `backgroundTasks` 配置中设置 `untilIdleMaxIdleMs`。应将其设为长于最慢后台任务的耗时，使任务完成后仍能触发后续轮次。单次调用的 `maxIdleMs` 仍优先：

```typescript
export const mastra = new Mastra({
  backgroundTasks: {
    enabled: true,
    untilIdleMaxIdleMs: 30 * 60_000,
  },
})
```

### 流结束后报告结果 {/* #report-a-result-after-the-stream-ends */}

当 deferred 任务完成，而其线程上没有打开的 `untilIdle` 流时，Mastra 会向 Agent 发送 `notification` 信号，标签为 `background-task`。信号会指明 Tool 调用和任务，并告知 Agent 结果现已附在 Tool 调用上；它不会把结果复制进 prompt。这适用于未使用 `untilIdle` 的 `stream()` 调用、客户端断开连接，以及任务[挂起](#suspending-and-resuming)后再恢复的情况。

- 如果线程空闲，信号会唤醒 Agent，让它在线程中运行一轮并报告结果。唤醒后的运行会沿用分派任务时的 request context，因此从中解析出的模型、指令和 memory 保持一致。即使接管线程的 Agent 运行在另一台服务器上，也会随信号传递该 context，但不包含认证 token、已登录用户，以及无法序列化为 JSON 或体积过大的值。该服务器上的运行使用它自己的认证 token 和用户。
- 如果线程上已有运行，包括分派该任务的运行，信号会送到该运行的下一次模型请求。如果该运行在再次请求前结束，信号会单独启动一轮。
- 如果另一 Agent 的运行占用线程，例如正在等待 Tool 审批，信号会等待；该运行结束后再唤醒原 Agent。
- 如果线程上有打开的 `untilIdle` 流，则不会发送信号，因为该流会自行运行后续轮次。
- 如果调用方取消或中止正在等待任务的 `untilIdle` 流，也不会发送信号：停止该流表示调用方不希望这项工作再返回响应。任务先挂起、之后才收到答复的情况不在此列，因为任务挂起时流已停止等待。

由信号在空闲线程上启动的运行（例如通过 `agent.sendSignal()` 发送的消息）会保持打开，直到它分派的任务完成，并自行报告结果。若希望唤醒的运行在本轮结束后就关闭，可设置临时选项 `wokenRunsEndAfterTurn`；其任务完成后会再通过此信号报告：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  backgroundTasks: {
    enabled: true,
    wokenRunsEndAfterTurn: true,
  },
})
```

信号自身的 `ifIdle.streamOptions.untilIdle` 设置双向优先于该选项。在下一大版本中，唤醒后的运行只会在本轮结束后关闭，`wokenRunsEndAfterTurn` 将被移除。届时若要让唤醒的运行保持打开，可在 `ifIdle.streamOptions` 中传入 `untilIdle: true`。Agent controller 会话和 channels 已经这样做。

如果同时使用 `wokenRunsEndAfterTurn` 和 `notifyAgentOnFinish: false`，唤醒后的运行分派的任务将无人报告；应用必须自行发送完成信号。

如果应用会自行发送完成信号，例如从 `onTaskComplete` 发出，请在 Mastra 的 `backgroundTasks` 配置中设置 `notifyAgentOnFinish: false`，以免 Agent 收到两次通知：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  backgroundTasks: {
    enabled: true,
    notifyAgentOnFinish: false,
    onTaskComplete: async task => {
      // Send your own notification to task.threadId
    },
  },
})
```

信号需要带线程和 resource 的 memory。缺少它们时，分派的任务只会把结果写入任务记录。awaited 任务不会发送信号，因为分派它的运行会等待结果。

### 聚合属性 {/* #aggregate-properties */}

使用 `untilIdle` 的 `stream()` 返回的 `MastraModelOutput` 看起来与普通 `stream()` 调用相同，但只有 `fullStream` 覆盖初始轮次和所有自动后续轮次。聚合属性（`text`、`toolCalls`、`toolResults`、`finishReason`、`messageList`、`getFullOutput()`）仍仅解析**首轮**的内部缓冲区。若需要跨后续轮次的聚合视图，请自行消费并汇总 `fullStream`。

## 在后台运行子 Agent {/* #subagents-in-the-background */}

子 Agent 调用在底层以 Tool 调用方式分派，因此适用相同的后台配置。建议在 supervisor 上逐个启用子 Agent：这样配置更清晰，也便于集中为每个子 Agent 调整 `timeoutMs`：

```typescript title="src/mastra/agents/supervisor.ts"
import { Agent } from '@mastra/core/agent'

const supervisor = new Agent({
  id: 'supervisor',
  instructions: 'Coordinate research and writing using the available agents.',
  model: '__GATEWAY_OPENAI_MODEL__',
  agents: { researchAgent, writingAgent },
  // highlight-start
  backgroundTasks: {
    tools: {
      researchAgent: { enabled: true, timeoutMs: 900_000 },
      writingAgent: { enabled: true, timeoutMs: 900_000 },
    },
  },
  // highlight-end
})

const stream = await supervisor.stream('Research AI in education and write an article', {
  memory: { thread: 't1', resource: 'u1' },
  untilIdle: true,
})
```

### 继承子 Agent 的配置 {/* #inheriting-from-the-subagent */}

如果 supervisor 的 `backgroundTasks.tools` 未列出某个子 Agent，但该子 Agent 自身有符合后台执行条件的 Tool（通过 Tool 级 `background.enabled: true` 或自身的 `backgroundTasks.tools` 配置），框架仍会把整个子 Agent 调用分派为后台任务。supervisor 会继承子 Agent 的意图：子 Agent 本身成为后台任务，并可在自身循环中后台执行符合条件的普通 Tool。更深一层的 Agent 委派调用则在前台执行。

继承式分派使用的后台配置（例如 `waitTimeoutMs`）来自子 Agent 自身的 `backgroundTasks` 配置。

```typescript title="src/mastra/agents/researcher.ts"
import { Agent } from '@mastra/core/agent'

const researchAgent = new Agent({
  id: 'research-agent',
  description: 'Gathers factual information.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  tools: { deepResearchTool },
  // highlight-start
  backgroundTasks: {
    tools: {
      deepResearchTool: { enabled: true, timeoutMs: 600_000 },
    },
    waitTimeoutMs: 900_000,
  },
  // highlight-end
})
```

如果某个 supervisor 未给 `researchAgent` 配置后台任务，却委派了这个 `researchAgent`，它仍会把整个 `researchAgent` 调用分派为后台任务。

Mastra 在一次委派运行中支持一层嵌套的后台 Tool：根 Agent 可委派给子 Agent，子 Agent 可在自身循环中后台分派符合条件的普通 Tool。第二层 Agent 委派仍在前台运行，且不会获得嵌套后台执行的指引。此限制只作用于该次执行，不会改变共享的子 Agent 配置。

选择在哪个层级配置，取决于一致性应由谁负责：子 Agent 级配置会随子 Agent 一起使用，使其在不同 supervisor 下保持相同的后台行为；supervisor 侧启用则可集中调整。该边界止于一层嵌套，且不支持 Workflow 集成。

## 挂起与恢复 {/* #suspending-and-resuming */}

后台任务可以在执行途中暂停，等待外部信号后继续。这适用于人工审批、webhook，以及下一步依赖后续数据的流程。

Tool 在其 `execute` 内调用 `suspend(data)` 后，会：

- 将 `status: 'suspended'` 和 `data` payload 持久化到任务记录。
- 保存 Workflow 快照，使运行能够跨进程重启继续。
- 在管理器流中发送 `background-task-suspended` 数据块。
- 释放并发执行槽位，供其他任务使用。

使用 `mastra.backgroundTaskManager.resume(taskId, resumeData)` 恢复任务。恢复运行时，Tool 的 `execute` 选项会收到 `resumeData`，任务状态转回 `running`。

```typescript title="src/mastra/tools/approval.ts"
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

export const reviewTool = createTool({
  id: 'review',
  description: 'Submit a draft for human review.',
  inputSchema: z.object({ draft: z.string() }),
  outputSchema: z.object({ approvedBy: z.string(), edits: z.string().optional() }),
  background: { enabled: true },
  execute: async ({ draft }, context) => {
    const { suspend, resumeData } = context.agent
    if (!resumeData) {
      await suspend?.({ awaiting: 'approval', draft })
      return { approvedBy: '', edits: undefined }
    }
    const { reviewer, edits } = resumeData as { reviewer: string; edits?: string }
    return { approvedBy: reviewer, edits }
  },
})
```

首次调用 `execute` 时，`resumeData === undefined`，因此会调用 `suspend`。任务恢复后，运行时会带着 `resumeData` 重新执行 Tool；此时 `if` 条件不成立，Tool 返回真正的结果。

审批到达后，可这样恢复任务：

```typescript title="src/server/approvals.ts"
await mastra.backgroundTaskManager?.resume(taskId, {
  reviewer: 'alice@example.com',
  edits: 'Reworded paragraph 3.',
})
```

恢复运行时，`context.agent.suspendPayload` 保存了 Tool 挂起时传入的 `data`。可以用它判断答复对应哪个请求，而不必把该信息编码进 `resumeData`。

### 从客户端答复挂起的任务 {/* #answer-a-suspended-task-from-a-client */}

Agent 的后台 Tool 调用挂起期间，承载该调用的 assistant 消息会在 `metadata.suspendedTools[toolCallId]` 中记录未完成的请求。该条目包含 `toolName`、`args`、`suspendPayload`、`taskId`、`runId` 和 `suspendedAt`，因此聊天界面重新加载线程后仍可展示请求。任务恢复或取消时，该条目会被移除。

该条目由分派 Tool 调用的进程写入；同一进程也负责将任务结果写入线程。若重启后由 Worker 接手任务，原进程已不存在，未完成的请求和结果都不会到达线程。

要通过 HTTP 答复请求，请调用 `POST /api/background-tasks/:backgroundTaskId/resume`，将答复放在 `resumeData` 中。[客户端 SDK](/reference/client-js/mastra-client) 将此路由封装为 `resumeBackgroundTask()`：

```typescript title="src/client/answer-request.ts"
import { MastraClient } from '@mastra/client-js'

const client = new MastraClient({ baseUrl: 'http://localhost:4111' })

const task = await client.getBackgroundTask(taskId)
await client.resumeBackgroundTask(
  taskId,
  { reviewer: 'alice@example.com' },
  { suspendedAt: task.suspendedAt },
)
```

传入从任务或 `suspendedTools` 条目读取的 `suspendedAt`。若任务此后已恢复或再次挂起，服务器会返回 `409 Conflict`，避免送达过期答复。任务未挂起或没有空闲并发槽位时，路由也会返回 `409`；任务不存在或属于其他 resource 时返回 `404`。调用该路由需要 `background-tasks:execute` 权限。

### 没有空闲槽位时恢复任务 {/* #resume-when-no-slot-is-free */}

默认情况下，所有并发槽位都被占用时，`resume()` 会抛出 `Concurrency limit reached`。传入 `{ onNoSlot: 'queue' }` 可将恢复操作排队：

```typescript
const task = await mastra.backgroundTaskManager?.resume(taskId, resumeData, { onNoSlot: 'queue' })
// task.status is still 'suspended' until a slot frees up
```

任务会保持 `suspended`，直到有槽位空出，再带着排队的 `resumeData` 恢复。取消任务会丢弃排队的恢复操作。

队列存在于调用 `resume()` 的进程内存中。如果该进程在恢复操作执行前退出，任务会保持 `suspended`，`resumeData` 也会丢失。要跨重启保留答复，请自行持久化恢复数据，并再次调用 `resume()`。

### 对 Agent 循环的影响 {/* #what-happens-to-the-agent-loop */}

在启用 `untilIdle` 的 `stream()` 中，如果任务中途挂起，包装器会将其视为本轮的终止状态并关闭流。取得恢复 payload 后，调用 `agent.resumeStream(resumeData, { runId, toolCallId, memory, untilIdle: true })` 可立即继续。恢复的后台任务完成后，其结果会先加入消息列表，然后 Agent 在同一 SSE 连接上运行后续轮次。若要带外恢复，可直接调用 `mastra.backgroundTaskManager.resume(taskId, resumeData)`，或使用[恢复路由](#answer-a-suspended-task-from-a-client)。任务完成后，结果会写入线程，Agent 会[被唤醒并报告结果](#report-a-result-after-the-stream-ends)。

### 恢复时重新注册执行器 {/* #re-registering-the-executor-on-resume */}

管理器将 Tool 执行器保存在进程内存中。如果任务挂起期间进程重启，执行器闭包会丢失；调用 `resume()` 的一方必须先通过 `manager.registerTaskContext(taskId, ...)` 重新注册。任务在同一进程内分派和恢复时无须执行此步骤。

### 取消挂起的任务 {/* #cancelling-a-suspended-task */}

`manager.cancel(taskId)` 对挂起任务与运行中任务的作用相同：任务记录改为 `cancelled`，Workflow 快照被清理，随后触发 `task.cancelled` 事件。

## 生命周期回调 {/* #lifecycle-callbacks */}

各层级都可以注册终态回调。这些回调互不替代，并会根据结果触发成功或失败 hook：

- Tool 级 `background.onComplete` / `onFailed`：仅作用于该 Tool。
- Agent 级 `backgroundTasks.onTaskComplete` / `onTaskFailed`：作用于该 Agent 分派的所有任务。
- 管理器级 `onTaskComplete` / `onTaskFailed`：全局生效，包括[非 Agent 所有者](#non-agent-owners)创建的任务。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  storage,
  backgroundTasks: {
    enabled: true,
    onTaskComplete: task => {
      logger.info('Background task complete', { taskId: task.id, toolName: task.toolName })
    },
    onTaskFailed: task => {
      logger.error('Background task failed', { taskId: task.id, error: task.error })
    },
  },
})
```

## 流式事件 {/* #streaming */}

### 订阅所有任务事件 {/* #subscribe-to-all-task-events */}

传入 `allResources: true`，可接收系统中所有 resource 的任务事件。连接建立时，流会先发送当前所有运行中任务的快照，随后转发实时事件。

```typescript title="src/mastra/run.ts" oxfmt:false
const bgManager = mastra.backgroundTaskManager;
if (!bgManager) throw new Error('Background tasks are not enabled');

const controller = new AbortController();
const stream = bgManager.stream({ allResources: true, abortSignal: controller.signal });

for await (const chunk of stream) {
  switch (chunk.type) {
    case 'background-task-running':
      console.log('started', chunk.payload.taskId, chunk.payload.toolName);
      break;
    case 'background-task-completed':
      console.log('done', chunk.payload.taskId, chunk.payload.result);
      break;
    case 'background-task-failed':
      console.error('failed', chunk.payload.taskId, chunk.payload.error);
      break;
  }
}
```

流会保持打开，直到调用方的 `AbortSignal` 触发。始终传入 `abortSignal`，以便正常断开连接。

:::warning

`allResources: true` 会提供每位用户的任务参数和结果。只能在可信的服务端代码中使用，不能用来服务单个用户的请求。未传入 `resourceId` 或 `allResources` 时，`stream()` 只会提供没有 `resourceId` 的任务。使用 memory 分派的 Agent 任务总有 `resourceId`，所以不会出现在该流中。

:::

### 过滤事件流 {/* #filter-the-stream */}

可以组合任意过滤选项，缩小接收事件的范围。过滤条件同时作用于初始快照和实时事件订阅。

```typescript
const stream = bgManager.stream({
  agentId: 'researcher',
  threadId: 't1',
  resourceId: 'u1',
  abortSignal: controller.signal,
})
```

| 过滤条件 | 说明 |
| - | - |
| `agentId` | 仅包含此 Agent 分派的任务事件 |
| `runId` | 仅包含此次 Agent 运行的事件 |
| `threadId` | 仅包含属于此 memory 线程的任务事件 |
| `resourceId` | 仅包含属于此 resource 的任务事件 |
| `taskId` | 仅包含单个任务的事件 |
| `allResources` | 省略 `resourceId` 时，包含所有 resource 的任务。仅限可信服务端代码 |
| `abortSignal` | 信号中止时关闭流 |

### 直接查询任务状态 {/* #look-up-task-state-directly */}

如需单次查询而非实时流，可使用 `getTask` 和 `listTasks`：

```typescript
const task = await mastra.backgroundTaskManager?.getTask(taskId)
const { tasks, total } = await mastra.backgroundTaskManager?.listTasks({
  status: 'running',
  agentId: 'researcher',
})
```

它们从 storage 读取，而非从 pubsub 流读取，因此适合分页列表和详情视图。

## 非 Agent 所有者 {/* #non-agent-owners */}

Agent 以外的代码也可以通过管理器运行任务。例如，MCP 服务器可将耗时的 Tool 调用作为后台任务执行。任务的 `agentId` 是其所有者 key；Agent 流、`untilIdle` 和步骤结束时的等待只会看到 `agentId` 与该 Agent 匹配的任务。请使用 `mcp-server:<serverId>` 这样的命名空间所有者 key，避免与真正的 Agent ID 冲突。Mastra 不会强制检查此约定。

非 Agent 所有者通常通过 `registerStaticExecutor()` 注册静态执行器，使任意进程都能运行或恢复其任务。还可以设置以下可选任务字段：

- `expiresAt`：清理操作删除任务的时间。任务完成、失败、取消或超时后，若设置了该字段，清理会在 `expiresAt` 之后删除任务，而不使用 `completedTtlMs` 或 `failedTtlMs`。只有设置 `cleanup` 选项后才会执行清理；它不会删除 pending、running 或 suspended 任务，因此应先取消已过期的工作。所用 storage adapter 还必须支持 `expiresAt`；旧版 adapter 仍使用全局保留设置。
- `metadata`：与任务一同存储的 JSON。管理器不会读取它。

```typescript
mastra.backgroundTaskManager?.registerStaticExecutor('mcp-server:ops:deploy', {
  execute: runDeploy,
})

await mastra.backgroundTaskManager?.enqueue({
  agentId: 'mcp-server:ops',
  toolName: 'mcp-server:ops:deploy',
  toolCallId: taskId,
  runId: taskId,
  args,
  resourceId: principalId,
  expiresAt: new Date(Date.now() + 24 * 60 * 60 * 1000),
  metadata: { ttlMs: 86_400_000 },
})
```

使用 `perOwnerConcurrency` 可为所有者单独设置并发限制，而不使用 `perAgentConcurrency`。其任务仍计入 `globalConcurrency`：

```typescript title="src/mastra/index.ts"
export const mastra = new Mastra({
  storage,
  backgroundTasks: {
    enabled: true,
    globalConcurrency: 60,
    perOwnerConcurrency: { 'mcp-server:ops': 50 },
  },
})
```

已知限制：

- 恢复的任务无法访问原始请求。请将执行器所需的信息写入任务本身，例如把主体信息放在 `resourceId`，或把其他 JSON 放在 `metadata`。
- 未固定到 Worker 的 `pending` 任务不持有 lease。启动时，其他进程可领取并分派它。如果执行器只存在于原进程，任务会因 `No executor registered` 而失败。在每个进程注册静态执行器可避免此问题。若原进程已开始执行工作，可使用 `pinToWorker`。
- Agent 循环在步骤结束时只等待 `running` 任务，不等待 `pending` 任务。[#28228](https://github.com/mastra-ai/mastra/pull/28228) 跟踪了这一修复。

### 将任务固定到当前 Worker {/* #pin-a-task-to-the-current-worker */}

有时在任务入队前，相关工作已在当前进程中运行。例如，MCP 服务器可能在请求中启动 Tool 调用，只在它耗时过长时才移交给后台任务。将 `pinToWorker: true` 与任务 context 一起传入，可避免其他进程重复启动该工作：

```typescript
await mastra.backgroundTaskManager?.enqueue(
  {
    agentId: 'mcp-server:ops',
    toolName: 'mcp-server:ops:deploy',
    toolCallId: taskId,
    runId: taskId,
    args,
  },
  { executor: { execute: adoptRunningDeploy } },
  { pinToWorker: true },
)
```

`pinToWorker` 表示该任务的工作已在当前 Worker 上执行。`pending` 任务会记录该 Worker 为所有者，并持有执行 lease；等待空闲槽位期间，Worker 会续租。只要 lease 有效，其他进程就不会恢复或分派该任务。

如果 Worker 在任务完成前终止或关闭，这项工作会丢失。恢复机制会把任务视为一次失败尝试，与执行中 Worker 终止的任务一样。若 `retryCount` 低于 `maxRetries`，任务会消耗一次重试机会，在另一 Worker 上运行；该 Worker 需要有静态执行器。否则任务会因 `Worker process terminated before task completed` 而失败。设置 `maxRetries: 0` 的任务不会在其他 Worker 上运行。除非 `recoverStaleTasksOnStart` 为 `false`，否则其他进程会在启动时及之后每隔 `leaseDurationMs` 检查过期的固定关系。

lease 失效只表示 Worker 不再续租，不代表工作已经停止。如果某个 Worker 的事件循环停顿超过 lease 有效期，另一 Worker 重试任务时，它仍可能在执行。可重试的固定任务应保证幂等，或保护其副作用。

没有任务 context 时，`pinToWorker` 会抛出异常。未固定的任务（包括所有 Agent 任务）在 `pending` 期间不持有 lease。
