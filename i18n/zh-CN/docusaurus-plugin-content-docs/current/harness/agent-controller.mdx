# Agent Controller

`AgentController` 是交互式 Agent 应用的共享运行时宿主，负责协调模式、模型、存储、Workspace、Tool 审批、子 Agent 和频道。每个用户或正在执行的任务都通过独立的 [`Session`](/reference/agent-controller/session) 工作。

[Mastra Code](https://code.mastra.ai) 和 [Mastra Factory](https://factory.mastra.ai) 是 AgentController 的代表性实现。它们是支持多模型、持久化对话和先规划后执行流程的编程 Agent。分步构建 TUI 的方法参见[构建编程 Agent](https://mastra.ai/blog/building-a-coding-agent)。

如果你托管的 Agent 需要在代码库中工作，请使用 [`createCodingAgent()`](/reference/coding-agent/create-coding-agent) 构建，而非 `new Agent()`。它返回标准 `Agent`，已具备 Workspace、任务跟踪和模型临时错误重试能力；这些也是 Mastra Code 使用的默认配置。

## 何时使用 Agent Controller {/* #when-to-use-the-agent-controller */}

当应用需要以下能力时，可以使用 Agent Controller：

- 在同一对话线程中使用多种 Agent 模式（例如规划 → 构建 → 审查）
- 在 UI 和 Agent 循环之间设置控制层（切换模型、持久化状态、管理线程）
- 通过 Tool 审批流程和权限策略实现人工把关
- 编排子 Agent，以受限 Tool 委派明确的子任务
- 在重启后保留线程及选定的线程设置，同时让每个 Session 的实时状态相互隔离

你也可以基于 [Agent 类](/docs/agents/overview)自行组合这些能力；它提供完整的 Agent 循环、Tool 和记忆能力。AgentController 为持续运行的 Session 提供一套有明确取舍的默认设置，让 Agent 作为协作者工作，而非只处理一次请求。需要完全自主控制或请求响应式调用时，直接使用 Agent 类；需要持续会话且不想自行构建 Session 运行时，则选择 AgentController。

## 快速入门 {/* #quickstart */}

创建作为底层执行者的 [`Agent`](/reference/agents/agent)、存储和 [`Workspace`](/reference/workspace/workspace-class)。调用一次 [`controller.init()`](/reference/agent-controller/agent-controller-class#init)，再通过 [`controller.createSession()`](/reference/agent-controller/agent-controller-class#createsessionoptions) 创建 Session。使用 [`session.subscribe()`](/reference/agent-controller/session#subscribelistener) 订阅事件，并通过 [`session.sendMessage()`](/reference/agent-controller/session#sendmessage-content-files-requestcontext-author-) 发送任务：

```typescript title="src/mastra/agent-controller.ts"
import { Agent } from '@mastra/core/agent'
import { AgentController } from '@mastra/core/agent-controller'
import { LocalFilesystem, Workspace } from '@mastra/core/workspace'
import { LibSQLStore } from '@mastra/libsql'

const agent = new Agent({
  id: 'assistant',
  name: 'Assistant',
  instructions: 'Help the user plan and complete tasks.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

const controller = new AgentController({
  id: 'assistant-controller',
  agent,
  storage: new LibSQLStore({
    id: 'agent-controller-storage',
    url: 'file:./mastra.db',
  }),
  workspace: new Workspace({
    id: 'assistant-workspace',
    filesystem: new LocalFilesystem({ basePath: './workspace' }),
  }),
  modes: [
    {
      id: 'plan',
      name: 'Plan',
      metadata: { default: true },
      instructions: 'Reason about the task before making changes.',
    },
    {
      id: 'build',
      name: 'Build',
      instructions: 'Implement the approved plan.',
    },
  ],
})

await controller.init()

const session = await controller.createSession({
  resourceId: 'user-123',
})

const unsubscribe = session.subscribe(event => {
  if (event.type === 'message_update' && event.event.type === 'text-delta') {
    process.stdout.write(event.event.delta)
  }
})

await session.sendMessage({ content: 'Plan a small TypeScript CLI.' })
unsubscribe()
```

每条消息先发出携带初始消息的 `message_start` 事件，然后发出零个或多个携带精简增量的 `message_update` 事件，最后发出包含消息 ID 的 `message_end` 事件。如果需要还原完整消息，请按 ID 应用更新。

同一个 Controller 可以服务多个 Session。不要在 Controller 上保存“当前 Session”，也不要通过 Controller 级消息方法分发任务。

## 理解运行时模型 {/* #understand-the-runtime-model */}

Controller、Session 和线程的生命周期各不相同：

- **Controller**：配置和运行时服务的共享宿主。初始化一次后重复使用。
- **Session**：面向一个用户、任务或并发工作单元的独立实时运行时，通过 Session ID 定位。它持有当前模式、模型、状态、事件总线、运行状态、授权以及当前绑定的线程。
- **线程**：存储消息和线程设置的对话。配置存储后，线程可在 Controller 或进程重新创建后继续存在。

Session 保存的是实时状态。任意的 [`session.state`](/reference/agent-controller/session#state) 数据、权限授权、待审批请求和正在执行的运行不会在进程重新创建后自动恢复。线程消息及选定的线程设置（包括当前模式和模型）可以通过存储保留，但切换模式不会切换模型。

## Session 与线程 {/* #sessions-and-threads */}

`createSession()` 根据 Session 的 `id` 获取已有实例或创建新实例。`resourceId` 标识 Session 的线程和资源范围内记忆归谁所有。省略 `id` 时，默认使用 `resourceId`：

```typescript
const webSession = await controller.createSession({
  id: 'user-123:web',
  resourceId: 'user-123',
})

const sameWebSession = await controller.getSession('user-123:web')

const workerSession = await controller.createSession({
  id: 'user-123:background-worker',
  resourceId: 'user-123',
})

console.log(webSession === sameWebSession) // true
console.log(webSession === workerSession) // false
```

不同 ID 的 Session 各有独立的事件总线、运行循环、状态、模式与模型选择，以及当前线程绑定。但它们存储的线程和资源范围内记忆仍可归属于同一个 `resourceId`，因此按资源列出线程时会返回两个 Session 的线程。

当宿主必须将 Session 绑定到指定线程时，传入 `threadId`。Controller 会切换到已有线程；若该 ID 不存在，则创建对应线程。即使 `createSession()` 返回的是缓存的 Session，也会执行这一行为：

```typescript
const session = await controller.createSession({
  id: 'user-123:web',
  resourceId: 'user-123',
  threadId: 'support-ticket-42',
})
```

使用 [`session.thread.create()`](/reference/agent-controller/session#sessionthreadcreate-title-id-requestcontext-) 和 [`session.thread.switch()`](/reference/agent-controller/session#sessionthreadswitch-threadid-emitevent-requestcontext-) 在不同对话间切换同一个实时 Session。

### 转移线程所有权 {/* #transfer-thread-ownership */}

每个新线程都会在 `metadata.ownerId` 中保存其持久所有者，并在 `metadata.createdBy` 中保存最初的创建者。两者默认都是 Session 宿主的 `ownerId`。转移所有权不会改变 `createdBy`。

通过 `session.thread` 读取当前线程的所有者并转移所有权：

```typescript
const currentOwnerId = await session.thread.getOwner()

await session.thread.transferOwnership({
  toOwnerId: 'user-456',
})
```

同一进程内的所有权转移会串行执行。如果宿主需要跨进程持久化的比较并设置操作，应先在自己的存储中提交变更，再调用 `transferOwnership()`，将所有者同步到当前线程。

每次运行开始时都会对线程所有者拍摄快照。Tool 和其他动态运行时代码可通过 `AgentControllerRequestContext.threadOwnerId` 读取该值。如果运行期间所有权发生变化，当前运行仍使用旧快照，下次运行才会取得新所有者。`context.session.ownerId` 始终表示当前进程中 Session 宿主的身份。

### 从客户端列出已存储的消息 {/* #list-stored-messages-from-the-client */}

使用 Agent Controller 客户端分页读取线程中存储的消息。传入选项对象后，返回结果还会包含分页元数据：

```typescript
import { MastraClient } from '@mastra/client-js'

const client = new MastraClient({ baseUrl: 'http://localhost:4111' })
const session = client.getAgentController('assistant-controller').session('user-123')

const result = await session.listMessages('support-ticket-42', {
  page: 0,
  perPage: 20,
  orderBy: { field: 'createdAt', direction: 'DESC' },
  filter: {
    dateRange: { start: new Date('2026-01-01') },
  },
})

console.log(result.messages)
console.log(result.total)
console.log(result.hasMore)
```

`page` 从零开始计数。省略 `perPage` 时，使用存储层默认的每页 40 条消息。使用 `include` 可按 ID 请求某条消息及其相邻消息。`limit` 是已弃用的 `perPage` 别名；现有分页调用方仍可使用 `{ limit, page }`，但搭配 `orderBy`、`filter` 或 `include` 时必须使用 `perPage`。如果需要以数组形式取得最新的一段消息，仍可使用数字参数形式 `session.listMessages(threadId, limit)`；数组按从旧到新的顺序排列。

## 切换模式和模型 {/* #switch-modes-and-models */}

模式会改变共享底层 Agent 使用的指令和 Tool，而不会替换 Session 或线程。在 Controller 中配置各模式的专用 Tool 和可见范围：

```typescript
const modes = [
  {
    id: 'plan',
    name: 'Plan',
    metadata: { default: true },
    instructions: 'Investigate the task and propose a plan.',
    additionalTools: { searchDocs },
    availableTools: ['searchDocs', 'submit_plan'],
    transitionsTo: 'build',
  },
  {
    id: 'build',
    name: 'Build',
    instructions: 'Implement the approved plan.',
  },
]
```

`tools` 和 `additionalTools` 是添加模式专用 Tool 的互斥参数。Controller 有共享的底层 Agent 时，两者任一都会将这些 Tool 叠加到 Agent 的 Tool 上。使用 `availableTools` 限制某个模式最终对外暴露的 Tool 名称。权限策略中的拒绝规则仍优先于这一允许列表。

通过 [`session.mode.switch()`](/reference/agent-controller/session#sessionmodeswitch-modeid-) 切换实时 Session 的模式。使用 [`session.mode.get()`](/reference/agent-controller/session#sessionmodeget) 或 [`session.mode.resolve()`](/reference/agent-controller/session#sessionmoderesolve) 读取当前模式：

```typescript
await session.mode.switch({ modeId: 'build' })

console.log(session.mode.get()) // "build"
console.log(session.mode.resolve().instructions)
```

通过 [`session.model.switch()`](/reference/agent-controller/session#sessionmodelswitchmodelid-options) 单独切换模型，再通过 [`session.model.get()`](/reference/agent-controller/session#sessionmodelget) 读取当前选择。该选择作为线程的当前模型存储，因此 Session 切换模式后仍保持生效：

```typescript
await session.model.switch('__GATEWAY_ANTHROPIC_MODEL_SONNET__')

console.log(session.model.get())
```

### 选择 Observational Memory 模型 {/* #select-observational-memory-models */}

Observer 和 reflector 的模型选择相互独立。每个角色既可以指定模型，也可以由宿主根据当前主模型和 Session 状态自动选择。

要配置自动选择，请提供一个返回具体模型 ID 的同步解析器：

```typescript
const controller = new AgentController({
  // ...
  omConfig: {
    observerModel: 'auto',
    reflectorModel: 'auto',
    defaultObserverModelId: '__GATEWAY_OPENAI_MODEL_LUNA__',
    defaultReflectorModelId: '__GATEWAY_OPENAI_MODEL_LUNA__',
    resolveAutoModelId: ({ currentModelId }) => currentModelId,
  },
})
```

`session.om.observer.model()` 返回 `'auto'` 或具体模型 ID。`session.om.observer.modelId()` 返回实际生效的具体模型。因此，宿主可以切换主模型，而无需重写角色的自动选择设置。

只将其中一个角色重置为自动选择，不影响另一个角色：

```typescript
await session.om.observer.switchModel({ modelId: 'auto' })
```

如果解析器返回 `undefined` 或抛出异常，该角色会使用具体的 `defaultObserverModelId` 或 `defaultReflectorModelId` 作为回退模型。显式选择方法参见 [`Session` Observational Memory API](/reference/agent-controller/session#observational-memory)。

## 管理线程和状态 {/* #manage-threads-and-state */}

使用 [`session.thread.list()`](/reference/agent-controller/session#sessionthreadlistoptions) 列出已存储的对话：

```typescript
const thread = await session.thread.create({ title: 'Release planning' })
const threads = await session.thread.list()

await session.thread.switch({ threadId: thread.id })
console.log(threads.length)
```

使用 `session.state` 保存与 Session 关联的结构化实时状态。通过 [`session.state.get()`](/reference/agent-controller/session#sessionstateget) 读取，并通过 [`session.state.set()`](/reference/agent-controller/session#sessionstatesetupdates) 更新。如需校验和默认值，可在 Controller 上定义 `stateSchema` 和 `initialState`：

```typescript
console.log(session.state.get())

await session.state.set({ activeProject: 'docs-site' })
```

`session.state.get()` 返回状态快照。`set()` 会校验更新并将其合并到 Session 状态中。除非宿主明确负责持久化和恢复，否则应将这份状态视为实时 Session 数据。

## 审批 Tool 并恢复暂停的运行 {/* #approve-tools-and-resume-suspensions */}

权限策略决定 Tool 是获准执行、被拒绝，还是提交 UI 等待审批。可通过 Controller 的 `toolCategoryResolver` 将自定义 Tool 映射到类别：

```typescript
const controller = new AgentController({
  toolCategoryResolver: toolName => {
    if (toolName === 'delete_project') return 'execute'
    return null
  },
})
```

规则允许的 Tool 调用不会暂停运行。对于普通 `Agent`，如果同一步中的 Tool 调用都无需审批且都不会暂停，这些调用会并发执行。持久化 Agent 则逐个执行，除非 Session 的 `yolo` 状态已开启。

通过 [`session.permissions.setForCategory()`](/reference/agent-controller/session#sessionpermissionssetforcategory-category-policy-) 设置类别策略，通过 [`session.permissions.setForTool()`](/reference/agent-controller/session#sessionpermissionssetfortool-toolname-policy-) 设置单个 Tool 的策略：

```typescript
await session.permissions.setForCategory({
  category: 'execute',
  policy: 'ask',
})

await session.permissions.setForTool({
  toolName: 'delete_project',
  policy: 'deny',
})
```

当策略结果为 `ask` 时，订阅审批事件，并通过 [`session.respondToToolApproval()`](/reference/agent-controller/session#respondtotoolapproval-decision-toolcallid-requestcontext-declinecontext-) 返回用户的决定：

```typescript
session.subscribe(event => {
  if (event.type === 'tool_approval_required') {
    session.respondToToolApproval({
      toolCallId: event.toolCallId,
      decision: 'approve',
    })
  }
})
```

`always_allow_category` 决定会对触发审批的线程授予该 Tool 类别的权限。这种授权不是持久化的进程级权限。

[`ask_user`](/reference/tools/ask-user-tool) 和 [`submit_plan`](/reference/tools/submit-plan-tool) 等交互式 Tool 使用可恢复的 Tool 暂停机制。通过 [`session.respondToToolSuspension()`](/reference/agent-controller/session#respondtotoolsuspension-resumedata-address-toolcallid-requestcontext-) 恢复执行：

```typescript
session.subscribe(event => {
  if (event.type === 'tool_suspended' && event.toolName === 'ask_user') {
    void session.respondToToolSuspension({
      toolCallId: event.toolCallId,
      resumeData: 'Use SQLite.',
    })
  }
})
```

对于 `submit_plan`，使用 `{ action: 'approved' }` 或 `{ action: 'rejected', feedback }` 恢复。批准计划后，运行继续之前可以先切换到 `transitionsTo` 配置的模式。

内置 `submit_plan` Tool 接收的是计划文件路径，而非计划正文。Agent 会先将计划写入文件，再提交路径，因此需要可写的文件系统，例如 Workspace 文件系统。应用要展示计划供审批时，应读取提交的 `path` 所指文件。

## 委派任务给子 Agent {/* #delegate-to-subagents */}

在 Controller 上配置可用的子 Agent 类型。之后，内置 `subagent` Tool 就能根据这些定义委派目标明确的任务：

```typescript
const controller = new AgentController({
  tools: {
    searchDocs,
  },
  subagents: [
    {
      id: 'code-reviewer',
      name: 'Code reviewer',
      description: 'Review a change for correctness and regressions.',
      instructions: 'Inspect the change and report actionable findings.',
      allowedControllerTools: ['searchDocs'],
      allowedWorkspaceTools: ['view', 'find_files'],
      defaultModelId: '__GATEWAY_OPENAI_MODEL_LUNA__',
    },
  ],
})
```

普通子 Agent 使用自身配置的指令和受限 Tool 集启动。如果子 Agent 应复制父线程，并使用父 Agent 的指令和 Tool，则设置 `forked: true`。分叉的子 Agent 保留父级提示词前缀，忽略定义中的指令、Tool、允许列表和默认模型，并要求 Controller 配置记忆能力。

通过 [`session.subagents.model.set()`](/reference/agent-controller/session#sessionsubagentsmodelset-modelid-agenttype-) 设置通用的默认子 Agent 模型，或指定某种 Agent 类型的模型。通过 [`session.subagents.model.get()`](/reference/agent-controller/session#sessionsubagentsmodelget-agenttype-) 读取选择：

```typescript
await session.subagents.model.set({
  modelId: '__GATEWAY_OPENAI_MODEL_LUNA__',
})

await session.subagents.model.set({
  agentType: 'code-reviewer',
  modelId: '__GATEWAY_ANTHROPIC_MODEL_SONNET__',
})

const reviewerModel = session.subagents.model.get({
  agentType: 'code-reviewer',
})
```

这些选择会写入线程设置。按 Agent 类型指定的模型优先于 Session 的默认子 Agent 模型。

## 连接聊天频道 {/* #connect-chat-channels */}

将频道适配器传给 Controller，并在 [`Mastra`](/reference/core/mastra-class) 实例中注册 Controller：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { AgentController } from '@mastra/core/agent-controller'
import { createSlackAdapter } from '@chat-adapter/slack'

const controller = new AgentController({
  id: 'support-controller',
  agent,
  storage,
  workspace,
  modes,
  channels: {
    adapters: {
      slack: createSlackAdapter(),
    },
    resolveResourceId: ({ thread, message, defaultResourceId }) => {
      if (thread.isDM) return message.author.userId
      return defaultResourceId
    },
    onSessionStart: async ({ session, thread }) => {
      const plan = await billing.planFor(thread.resourceId)
      await session.model.switch(plan.modelId)
    },
  },
})

export const mastra = new Mastra({
  agentControllers: { controller },
  storage,
})
```

将各平台的 webhook 指向该 Controller 专属的路由：

```text
/api/agent-controllers/<CONTROLLER_ID>/channels/<PLATFORM>/webhook
```

每个外部聊天线程都会映射到一个 Controller Session 和一个 Mastra 线程。默认情况下，新 Session 使用从适配器的聊天线程 ID 派生的资源 ID，并带有 `channel:` 前缀。使用 `resolveResourceId` 可将私信映射到现有应用用户，或选择其他记忆所有者。这个回调只影响新线程；已有线程继续使用其存储的资源 ID。

频道 Session 由 Controller 创建，而非由应用代码创建，因此应在 `onSessionStart` 中配置。它在 Session 绑定到映射线程之后、处理首条消息之前，对每个 Session 运行一次。频道 Session 起初采用 Controller 默认设置，可在此设置模型和记忆。相同线程的后续消息会复用该 Session，不会再次调用回调。错误会记录在日志中并被忽略，因此即使配置失败，Session 仍会回复消息。

### 授权并路由频道 Session {/* #authorize-and-route-channel-sessions */}

`onSessionStart` 在 Session 创建后执行，且会忽略错误，所以无法拒绝请求。如果宿主需要决定是否允许创建 Session，应使用 `resolveSession`。它取代内置 Session 创建流程，并在 Session 创建前运行。抛出异常会在 Controller 创建 Session 或调用模型前拒绝请求。Mastra 会记录拒绝事件，聊天线程保持沉默，因此你的授权提示不会发送到频道。

```typescript oxfmt:false
channels: {
  adapters: { slack: createSlackAdapter() },
  resolveSession: async ({ controller, thread, requestContext }) => {
    const install = await installs.authorize(requestContext.get('teamId'))

    return controller.createSession({
      id: `${install.id}:${thread.id}`,
      resourceId: thread.resourceId,
      threadId: thread.id,
      ownerId: controller.id,
      requestContext,
    })
  },
}
```

在 `thread.resourceId` 下创建 Session。Session 只能绑定属于自己的线程，因此若要为映射线程指定不同所有者，应使用 `resolveResourceId`。传入 `threadId: thread.id`，使 Session 一开始就打开映射线程。否则，带标签或 `projectPath` 的 Session 不会将映射线程视为己有，会先创建一个额外的空线程，再切换过去。Session 按 `id` 获取或创建；如果同一线程需要分别对应不同安装或主体，应为每个安装或主体分配独立 `id`。

非拒绝类故障（例如存储中断、解析器依赖项中的错误）仍会向线程发送错误，使故障机器人不会表现得像主动保持沉默。如果需要在代码中区分，拒绝对应 `ChannelSessionRejectedError`，其 `cause` 为原始错误。

用户回应审批卡片时，`resolveSession` 也会携带该操作的请求上下文运行。共用安装会重新验证审批者的身份，而不会直接信任原消息发送者。

### 处理已失效的审批 {/* #handle-stale-approvals */}

审批关卡只保存在内存中，因此重启后收到的审批回应均已失效。Mastra 绝不会为失效操作运行 Tool。使用 `onStaleToolApproval` 结算用户所回应的那次尝试，避免直接丢弃：

```typescript oxfmt:false
channels: {
  adapters: { slack: createSlackAdapter() },
  onStaleToolApproval: async ({ decision, toolCallId, runId, memory }) => {
    await runs.markInterrupted({ runId, toolCallId, decision, threadId: memory.thread })
  },
}
```

`runId` 是生成审批卡片时的运行 ID，也就是用户回应的那次尝试；重启后应据此结算。Session 自身当前的运行 ID 则通过 `currentRunId` 单独传入，此时通常为 `null` 或另一次运行。

Controller 的频道 Session 和自动审批状态保存在内存中，因此应使用长期运行的服务器。待处理审批和实时 Session 状态无法在进程重启后保留。无法显示审批控件的适配器会自动执行 Tool，不显示审批提示，以免运行一直暂停。

频道适配器设置和各平台 webhook 配置参见 [Channels](/docs/channels)。

## 连接 UI {/* #connect-a-ui */}

连接方式取决于 UI 的运行位置。终端 UI 或持有 Controller 的服务器可以直接持有 `Session` 对象并订阅事件。浏览器 UI 位于另一个进程中，需要通过 Controller 的 HTTP 路由和 [`@mastra/client-js`](/reference/client-js/mastra-client) 访问同一个 Session。

### 服务端 Session {/* #server-side-sessions */}

订阅 Session 事件以获取增量更新。如果 UI 需要完整的渲染快照，可通过 [`session.displayState.get()`](/reference/agent-controller/session#sessiondisplaystateget) 读取归约后的显示状态：

```typescript
const unsubscribe = session.subscribe(event => {
  if (event.type === 'display_state_changed') {
    render(event.displayState)
  }
})

render(session.displayState.get())

// Call when the UI disconnects.
unsubscribe()
```

订阅按 Session 隔离。同一 Controller 上其他 Session 的事件不会传给这个监听器。完整的 TUI 示例参见[构建编程 Agent](https://mastra.ai/blog/building-a-coding-agent)。

### 客户端 Session {/* #client-side-sessions */}

[`client.getAgentController(key).session(sessionId)`](/reference/client-js/agent-controller) 返回通过 Session ID 定位的客户端。传入 Controller 在 `new Mastra({ agentControllers })` 中注册时使用的 key；它可能不同于 Controller 的 `id`。服务端会根据 ID 获取或创建 Session，因此 `create()` 会恢复已有对话，而不是另开一个。如果多个 Session 共用资源，请向 `create()` 传入 `resourceId`；否则资源 ID 默认为 Session ID：

```typescript title="src/components/agent-session.ts"
import { MastraClient } from '@mastra/client-js'

const client = new MastraClient({ baseUrl: 'http://localhost:4111' })
const session = client.getAgentController('coding-controller').session('user-123')

await session.create()

const subscription = await session.subscribe({
  onEvent: event => handleEvent(event),
  onError: error => showDisconnected(error),
  onReconnect: () => {
    void session.state().then(resync).catch(showDisconnected)
  },
  reconnect: true,
})

// Call when the UI disconnects.
subscription.unsubscribe()
```

`subscribe()` 与进程内监听器不同：它接收选项对象，而且是异步方法。流建立后 Promise 才会兑现；连接失败则会拒绝，且不会留下后台运行的订阅。`reconnect: true` 会在已建立的流断开后以指数退避方式重新连接。如果连接保持打开但停止传输数据，例如设备休眠，那么在 `idleTimeoutMs`（默认 `60000`）内连服务端心跳都没有收到时，也会视为断开。

服务端不会重放流中断期间错过的事件，因此应在 `onReconnect` 中读取 `session.state()`，取得当前模式、模型和线程。客户端没有 `session.displayState.get()`。

使用 `session.sendMessage(content)` 发送任务，或使用 `session.sendMessage({ content, files })` 附加 base64 编码文件。回复通过订阅中的 `message_*` 事件到达，而不是作为调用返回值。收到 `tool_approval_required` 事件时，用 `session.approveTool(toolCallId, approved)` 回答；收到 `tool_suspended` 事件时，用 `session.respondToToolSuspension(toolCallId, resumeData)` 恢复。

`onEvent` 接收 Session 发出的所有事件。事件类型及其缩小范围的方法参见 [Agent Controller API](/reference/client-js/agent-controller#events)。
