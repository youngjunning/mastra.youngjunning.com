# 可恢復的串流

可恢復的串流會將一次 Agent 執行產生的每個區塊發布到 PubSub 主題，並將事件存入快取以供重播。用戶端斷線後可以重新連線，補收錯過的事件。其他讀取端可用 `observe()` 追蹤同一次執行，且任何讀取端都能停止執行。

可恢復的串流不會讓執行本身具備持久性。重新連線無法從當機中復原。執行 Agent 的程序一旦停止，該次執行也會停止，觀察端會收到錯誤，或不再收到事件。若要讓執行能在程序重新啟動後繼續，請使用[持久化 Agent](/docs/harness/durable-agents)，它會透過同一串流層發布事件。

## 預設行為 {/* #defaults */}

| Agent | 串流 |
| - | - |
| 已向 `Mastra` 執行個體註冊 | 開啟 |
| 獨立執行（以 `new Agent()` 建立，未使用 `Mastra`） | 關閉 |
| 設定 `durable: true` 的一般 Agent | 開啟，包含獨立 Agent |
| 設定 `durable: false` 的一般 Agent | 關閉，包含已註冊的 Agent |
| 明確以 `createDurableAgent()` 包裝 | 一律發布。傳入 `cache: false` 給工廠函式只會停用重播快取，傳輸層仍可保留歷史記錄。 |

已註冊的 Agent 無論是否具備持久性，都會透過 `mastra.pubsub` 發布事件，並快取到 `mastra.serverCache`，若伺服器未設定快取，就改用記憶體快取。共用該 PubSub 和快取的每個 `Mastra` 執行個體都能觀察這次執行。Agent 層級的 `pubsub` 優先，但事件驅動引擎的步驟一律透過 `mastra.pubsub` 發布。

## 設定串流 {/* #configure-streams */}

在 Agent 上設定 `durable`，可開啟或關閉串流，也可傳入自訂的 PubSub 和快取：

```typescript title="src/mastra/agents/support-agent.ts"
import { Agent } from '@mastra/core/agent'

export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support agent',
  instructions: 'You help customers with their orders.',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  durable: {
    // Keep finished runs replayable for 2 minutes instead of 30 seconds
    cleanupTimeoutMs: 120_000,
  },
})
```

| 選項 | 預設值 | 說明 |
| - | - | - |
| `pubsub` | `mastra.pubsub` | 用來發布執行事件的匯流排。共用匯流排即可跨程序追蹤執行。 |
| `cache` | `mastra.serverCache`，未設定時採用記憶體快取 | 重播快取。傳入 `false` 可停用此快取。Redis Streams 等傳輸層仍可重播保留的歷史記錄。 |
| `shouldCache` | 所有主題 | 對某個主題傳回 `false`，即可略過該主題的快取。 |
| `cleanupTimeoutMs` | `30000` | 一次執行結束後，等待多久才清除該次執行。`0` 只會停用這個計時器，快取本身的到期及淘汰規則仍然適用。 |

`durable: true` 會依上述預設值開啟串流，獨立 Agent 也適用。

對一般 `Agent` 而言，`durable` 只設定可恢復的串流。若要執行時保留檢查點，請明確用 `createDurableAgent({ agent })` 包裝 Agent。若要在當機後恢復未完成的執行，還須設定持久化 Workflow 儲存空間及 `recovery: { durableAgents: 'auto' }`。若要手動恢復，請傳入涵蓋 `running` 快照的 `shouldPersistSnapshot` 政策，再自行呼叫 `recoverActiveRuns()`。設定與持久化政策請見[當機復原](/docs/harness/durable-agents#crash-recovery)。

以工廠函式的 `cache`、`pubsub`、`shouldCache` 和 `cleanupTimeoutMs` 選項設定包裝後的串流快取和傳輸。

## 關閉串流 {/* #turn-streams-off */}

串流會耗用資源。每個區塊都會發布到 PubSub，啟用快取後，每個事件也會儲存到該次執行被清除為止。使用記憶體快取會占用程序記憶體，使用遠端 PubSub 或 Redis 等遠端快取則要為每個區塊透過網路寫入一次。如果 Agent 的執行量大，而且從來不需要重新連線或觀察執行，可以關閉串流：

```typescript title="src/mastra/agents/batch-agent.ts"
import { Agent } from '@mastra/core/agent'

export const batchAgent = new Agent({
  id: 'batch-agent',
  name: 'Batch agent',
  instructions: 'You classify support tickets.',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  durable: false,
})
```

若要保留即時觀察功能，但略過重播快取，請傳入 `durable: { cache: false }`。

### 執行會保留多久 {/* #how-long-runs-stay-available */}

執行結束後，執行程序會安排在 `cleanupTimeoutMs` 後清除執行事件和歸屬記錄。計時器允許程序在清除前結束，共用快取資料隨後會保留到到期或遭淘汰為止。Redis Streams 會保留原生主題資料，直到 `clearTopic()` 成功或閒置 TTL 到期。傳輸層的預設閒置 TTL 為七天，可用 `streamIdleTtlMs` 調整，設為 `0` 則會停用傳輸層的到期機制。等待工具核准或處於暫停狀態的執行不受這個計時器清除，因為恢復後會沿用相同主題。

其餘保留限制由快取決定：

- 執行記錄和歸屬記錄會向快取要求 24 小時的 TTL。除非停用快取到期機制，記憶體快取會對已建立索引的執行記錄採用至少 24 小時的 TTL。快取項目數達到上限時，資料可能提前淘汰。
- 記憶體快取預設可存放 1,000 個項目。一次執行會使用多個項目，包括事件記錄、計數器和歸屬記錄。因此流量大時，先前的執行會更快被淘汰。
- 執行的歸屬記錄遭淘汰或到期時，伺服器的觀察與中止路由會傳回 404。已淘汰的執行事件無法重播。

若要跨伺服器觀察執行，或等候核准的時間較長，請使用 Redis 等共用快取，並依流量設定容量。

## 追蹤執行 {/* #follow-a-run */}

共用同一 PubSub 匯流排的所有 Agent，執行 ID 必須彼此不同。

在共用匯流排的任一 Agent 執行個體上，以執行 ID 呼叫 `observe()` 即可追蹤執行。未指定位移量時，`observe()` 會先重播快取事件，再傳送即時事件。重播也需要共用同一重播快取。使用獨立快取的執行個體只會收到即時事件，除非 PubSub 本身保留歷史記錄。執行等候工具核准時，觀察端會收到核准請求，並保持連線，直到核准後的執行完成、發生錯誤或遭中止。若要停止追蹤等待中的執行，請呼叫 `detach()`：

```typescript title="src/server/reconnect.ts"
import { supportAgent } from '../mastra/agents/support-agent'

export async function followRun(runId: string, request: Request) {
  const { output, detach } = await supportAgent.observe(runId)

  request.signal.addEventListener('abort', detach, { once: true })
  if (request.signal.aborted) detach()

  for await (const chunk of output.fullStream) {
    // Chunks from the run, including any missed while disconnected
  }
}
```

`observe()` 傳回的區塊會以 `chunk.index` 標示它在執行記錄中的位置。連線中斷後，若要接續觀察，請將最後一個有索引的區塊的 `index + 1` 當作 `offset` 傳入。一般 Agent 的 `stream()` 產生的區塊，以及未經重播快取傳送的區塊，都不含 `index`，因此這類連線中斷後，請在觀察時省略 `offset`。哪些區塊沒有索引，以及結構化輸出和重播限制，請見 [`observe()` 參考](/reference/agents/durable-agent#observerunid-options)。

透過 HTTP 觀察無法恢復的執行時，請求會失敗。若執行未知，或其歸屬記錄已到期或遭淘汰，伺服器會傳回 404。用戶端會以含有該狀態碼的 `MastraClientError` 拒絕 Promise，不會傳回一個已關閉的空串流。

`agent.hasResumableStreams()` 表示此 Agent 是否發布執行事件，以及 `observe()` 和伺服器的觀察、中止路由能否存取這些執行。持久化 Agent 及任何已開啟串流的 Agent 都會傳回 `true`。

### 持續到閒置的串流 {/* #until-idle-streams */}

`streamUntilIdle()` 和 `resumeStreamUntilIdle()` 會在其 `fullStream` 中合併初始執行及背景工作的後續執行。若未指定位移量，`observe(returnedRunId)` 只會重播初始片段，並在該片段的結束事件關閉串流。它無法重新連到合併後持續到閒置的串流，也不會重播之後背景工作的回覆。明確指定執行 ID 也無法解除這項限制，持久化 Agent 同樣適用。

## 停止執行 {/* #stop-a-run */}

開啟串流時，讀取端關閉連線不會停止執行。用戶端中斷與伺服器串流路由的連線後，伺服器會分離該讀取端，繼續產生 token、呼叫工具並執行 `onFinish`，用戶端仍能重新連線。你可以明確停止執行，或在應隨請求結束而停止的一般 Agent 上設定 `durable: false`。持久化 Agent 一律會在斷線後繼續執行。已分離讀取端的執行仍會在完成、遭停止或用完步驟預算時結束。若沒有設定 `maxSteps` 或 `stopWhen`，每次迴圈會在五個步驟後停止，處理器的重試不計入。預算按每次迴圈呼叫計算，核准或背景續行後會啟動新迴圈。

可用以下任一方式明確停止執行：

- `observe(runId)` 會傳回 `abort()` 函式，向仍在執行的工作發出停止請求，不受執行位置限制。這個請求會盡力送達，不等待確認，發布失敗時只會記錄錯誤。需要確認時請使用下方的中止路由。等待核准的執行已不再接收此請求，請改用下方的中止路由。若執行位於記憶執行緒中，也可使用 `POST /agents/:agentId/threads/abort`。
- `agent.abortRunStream(runId)` 會停止目前程序中的執行，並要求同一匯流排上的其他程序停止該次執行。若目前程序成功停止正在進行的執行，會傳回 `true`。若執行不在記憶執行緒中且正在等待核准，也會在此程序取消，但呼叫會傳回 `false`，之後在此程序核准會失敗。取消限制只在目前程序生效，共用快照會保留，其他程序仍可核准同一快照。因此，應用程式有多部伺服器時，請使用下方的中止路由停止正在等待的執行。若執行位於其他程序，請求只會盡力送達。
- 伺服器的 `POST /agents/:agentId/runs/:runId/abort` 路由會先確認呼叫端是執行的擁有者，再停止任一共用 PubSub 和快取的伺服器上的執行。執行程序確認已停止後，路由會傳回 `{ aborted: true }`。若持久化 Agent（`DurableAgent` 或 `createDurableAgent`，包括事件驅動的 Agent）正在等候核准，路由也會將取消寫入儲存空間，並在寫入後傳回 `{ aborted: true }`。其後在任何共用該儲存空間的伺服器上核准或恢復該次執行，都會遭拒並傳回 `409 Conflict`（`AGENT_RESUME_ABORTED_RUN`）。若恢復操作先取得執行，就不會記錄取消，路由會依一般執行的處理方式停止已恢復的執行。Redis、Valkey 和 LanceDB 等不支援並行更新的儲存配接器，不會將同時到達的中止與核准依序處理。因此即使中止傳回 `{ aborted: true }`，時間重疊的核准仍可能執行工具。請先等到收到該回應，再依賴已寫入的取消記錄。Inngest Agent 不會寫入此記錄。若執行已結束，或執行未遭停止且沒有程序及時回應，路由會傳回 `{ aborted: false }`。記憶執行緒中的執行也可以透過 `POST /agents/:agentId/threads/abort` 停止，但該路由不會將取消寫入儲存空間。因此應用程式有多部伺服器時，請用執行中止路由停止正在等待的持久化執行。

非持久化 Agent 若設定 `durable: false`，關閉 HTTP 請求仍會如同以往中止執行。

## 跨伺服器運作 {/* #across-servers */}

若多部伺服器共用 PubSub 和快取（例如 Redis），可透過其中任一部伺服器觀察或停止在其中一部伺服器啟動的執行：

- 每次執行會在發布第一個事件前將歸屬記錄（Agent、執行、資源和執行緒）寫入快取。伺服器的觀察與中止路由會依該記錄驗證呼叫端，因此每部伺服器都會執行租用戶與執行緒檢查。
- 找不到記錄、記錄已到期或遭淘汰時，會傳回 404。若無法讀取快取，路由會傳回 503，不會略過檢查。
- 設定 `durable: { cache: false }` 時，歸屬記錄仍會存放在 `mastra.serverCache`，因此跨伺服器的歸屬檢查仍然有效。能否重播則取決於 PubSub。Redis Streams 等保留歷史記錄的實作可重播，程序內匯流排則只傳送即時事件。
- 預設的記憶體快取和 PubSub 不會共用資料，因此只有執行 Agent 的伺服器能觀察或停止它的執行。
