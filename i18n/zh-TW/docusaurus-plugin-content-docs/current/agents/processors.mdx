# 處理器

處理器用於在訊息經過 Agent 時進行轉換、驗證或控制。它們在 Agent 執行流程的特定階段執行，因此你可以在訊息到達語言模型之前修改輸入，或在回應傳回使用者之前修改輸出。

處理器分為：

* **`inputProcessors`**：在訊息到達語言模型前執行。
* **`outputProcessors`**：在語言模型生成回應後、傳回使用者前執行。

可以使用單一 [`Processor`](/reference/processors/processor-interface) 物件，也可以使用 Mastra 的 Workflow 原語將多個處理器組合為 Workflow。Workflow 能更細緻地控制執行順序，並支援條件處理或並行處理。

有些處理器同時實現了輸入和輸出邏輯；應依據轉換發生的階段，將其放入相應的陣列。

有些內建處理器還會傳送隱藏的系統提醒訊號。訊號會保存在原始 Memory 歷史中，並在下次模型呼叫前轉換為 `<system-reminder>...</system-reminder>` 上下文；標準的面向 UI 的訊息轉換和預設 Memory 召回會隱藏這些訊號，除非你明確選擇包含它們。若只需在本次呼叫中傳遞訊號而不保留它，請設定 `transient: true`。

## 何時使用處理器 {/* #when-to-use-processors */}

使用處理器可以：

* 規範化或驗證使用者輸入
* 為 Agent 加入防護規則
* 偵測並阻止提示注入或越獄嘗試
* 審核內容以滿足安全或合規要求
* 轉換訊息（例如翻譯語言、過濾工具呼叫）
* 限制 Token 用量或訊息歷史長度
* 脫敏個人身份資訊（PII）
* 對訊息應用自訂業務邏輯

Mastra 內建了適用於常見場景的處理器。你也可以依據應用需求建立自訂處理器。

## 快速開始 {/* #quickstart */}

匯入並實例化處理器，然後將其傳給 Agent 的 `inputProcessors` 或 `outputProcessors` 陣列：

```typescript {2,8-15} title="src/mastra/agents/moderated-agent.ts"
import { Agent } from '@mastra/core/agent'
import { ModerationProcessor } from '@mastra/core/processors'

export const moderatedAgent = new Agent({
  id: 'moderated-agent',
  name: 'moderated-agent',
  instructions: 'You are a helpful assistant',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  inputProcessors: [
    new ModerationProcessor({
      model: '__GATEWAY_OPENAI_MODEL_LUNA__',
      categories: ['hate', 'harassment', 'violence'],
      threshold: 0.7,
      strategy: 'block',
    }),
  ],
})
```

## 執行順序 {/* #execution-order */}

處理器按其在陣列中的順序執行：

```typescript
inputProcessors: [new UnicodeNormalizer(), new PromptInjectionDetector(), new ModerationProcessor()]
```

對於輸出處理器，這個順序決定模型回應經過各項轉換的先後。

### 啟用 Memory 時 {/* #with-memory-enabled */}

如果 Agent 啟用了 Memory，Memory 處理器會自動加入執行流程：

**輸入處理器：**

```text
[Memory Processors] → [Your inputProcessors]
```

Memory 先載入訊息歷史，再執行你的處理器。

**輸出處理器：**

```text
[Your outputProcessors] → [Memory Processors]
```

你的處理器先執行，然後 Memory 保存訊息。

按照這個順序，如果輸出防護處理器呼叫 `abort()`，後續 Memory 處理器就不會執行，訊息也不會保存。詳見 [Memory 處理器](/docs/memory/memory-processors#processor-execution-order)。

## 為 Agent 加入處理器 {/* #attach-processors-to-an-agent */}

透過三個陣列為 Agent 設定處理器：

```typescript
import { Agent } from '@mastra/core/agent'
import { PrefillErrorHandler, TokenLimiter, ModerationProcessor } from '@mastra/core/processors'

const agent = new Agent({
  id: 'support-agent',
  name: 'support-agent',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  instructions: '...',
  inputProcessors: [
    new TokenLimiter(4000),
    new ModerationProcessor({ model: '__GATEWAY_OPENAI_MODEL_LUNA__' }),
  ],
  outputProcessors: [new ModerationProcessor({ model: '__GATEWAY_OPENAI_MODEL_LUNA__' })],
  errorProcessors: [new PrefillErrorHandler()],
})
```

* `inputProcessors` 在 LLM 呼叫之前執行。
* `outputProcessors` 在 LLM 回應生成期間及生成後執行。
* `errorProcessors` 在 LLM API 呼叫拋錯時執行，可用於從 Provider 錯誤中恢復。

### 預設啟用錯誤處理器 {/* #error-processors-are-enabled-by-default */}

每個 Agent 都會補上 `errorProcessors` 清單中缺少的以下四種預設處理器：

1. `ProviderHistoryCompat`：修復發往 Provider 的提示詞中與其歷史訊息格式不相容的問題
2. `PrefillErrorHandler`：處理 Provider 拒絕預填充助理回應的情況
3. [`UnsupportedFileHandler`](/reference/processors/unsupported-file-handler)：從提示詞中移除模型拒絕的檔案；如果 Agent 有 Sandbox，則將檔案上傳到其中，再次呼叫模型
4. `StreamErrorRetryProcessor`：重試暫時性的 API 和串流處理失敗

只有清單中沒有相同 `id` 的處理器時，Mastra 才會加入預設實例；因此自訂實例優先，且不會重複。新增的預設處理器會按其 `id` 在預設順序中定位，所以只指定靠後的處理器不會顛倒前面處理器的順序。例如，只提供自訂 `StreamErrorRetryProcessor` 時，`ProviderHistoryCompat`、`PrefillErrorHandler` 和 `UnsupportedFileHandler` 仍會排在它前面。

錯誤處理器在第一個傳回 `{ retry: true }` 的處理器處停止，因此相對順序決定由誰修復錯誤。預設順序會先嘗試修復，再執行重試。如果將匹配範圍較廣的實例放在前面（例如錯誤請求匹配器會匹配任意 `400`），它可能搶先處理本可修復的請求，並原樣重發。預設重試實例只處理暫時性故障：連線重設、可重試的 OpenAI 流錯誤，以及 Provider 標記為可重試的錯誤。你可以為自己的實例設定更廣泛的匹配規則；上述順序仍會讓修復處理器先執行。

你提供的處理器之間不會重新排序。`id` 與預設處理器相同的實例會參與預設順序；使用自訂 `id` 的實例則保留在清單中的位置。

要替換某個預設處理器而保留其他預設處理器，請傳入具有相同 `id` 的實例：

```typescript
import { Agent } from '@mastra/core/agent'
import { StreamErrorRetryProcessor } from '@mastra/core/processors'

const agent = new Agent({
  id: 'tuned-agent',
  name: 'tuned-agent',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  instructions: '...',
  errorProcessors: [new StreamErrorRetryProcessor({ maxRetries: 5 })],
  maxProcessorRetries: 5,
})
```

上面的 `StreamErrorRetryProcessor` 是 Agent 中唯一的流錯誤重試處理器，它仍排在通常的位置，即清單未指定的 `ProviderHistoryCompat`、`PrefillErrorHandler` 和 `UnsupportedFileHandler` 預設實例之後。若要完全自訂這組處理器，請明確提供全部四個 ID。

處理器自身的 `maxRetries` 不能提高 Agent 的重試上限。未設定 `maxProcessorRetries` 時，錯誤處理器最多重試 `3` 次（參閱[錯誤處理器的重試限制](#error-processor-retry-limits)）；需要更多重試時，請同時設定該參數。

空的 `errorProcessors` 清單也會與預設處理器合併，因此仍會得到四個預設實例。要關閉預設實例，設定 `errorProcessorDefaults: false`。此時 Agent 只執行明確設定的處理器；如果沒有設定，則不會執行任何錯誤處理器：

```typescript
new Agent({
  id: 'custom-error-recovery-agent',
  name: 'custom-error-recovery-agent',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  instructions: '...',
  errorProcessorDefaults: false,
  errorProcessors: [new StreamErrorRetryProcessor({ maxRetries: 5 })],
  maxProcessorRetries: 5,
})
```

單次 `generate()` 或 `stream()` 呼叫傳入的 `errorProcessors` 清單不同：它會替換該次呼叫中 Agent 已解析的完整清單，包括預設處理器。

Agent 的 Memory 也可能提供自己的錯誤處理器，例如在請求超出模型上下文窗口時恢復。這些處理器在上述處理器之後執行，即使單次呼叫傳入自訂 `errorProcessors` 清單，也會保持原位。

每個陣列也可以接受傳回陣列的函式，以便依據 `RequestContext` 為每次請求構建處理器：

```typescript
new Agent({
  id: 'processors-agent',
  inputProcessors: ({ requestContext }) => {
    const limit = requestContext.get('tokenLimit') ?? 4000
    return [new TokenLimiter(limit)]
  },
})
```

### 覆蓋單次呼叫的處理器 {/* #override-processors-per-call */}

`agent.generate()` 和 `agent.stream()` 都接受上述三個陣列。傳入任一陣列時，該陣列只會在本次呼叫中**替換** Agent 上對應的陣列。Memory、Workspace 及其他由框架管理的處理器仍會在其周圍執行。

```typescript
await agent.stream('Summarize this', {
  inputProcessors: [new TokenLimiter(2000)],
  maxProcessorRetries: 5,
})
```

## 建立自訂處理器 {/* #create-custom-processors */}

自訂處理器需要實現 `Processor` 介面。

處理器方法接收兩個用於存取對話的參數：

* `messages`：目前階段的 `MastraDBMessage` 物件快照陣列。
* `messageList`：即時的 `MessageList` 實例，可用於讀取其他階段的訊息，或直接加入、刪除、替換訊息。

文字位於 `message.content.parts`，而非 `message.content` 本身。讀取使用者或助理文字時，應遍歷 `parts` 並篩選 `part.type === 'text'`。為相容舊版本，還可以在必要時使用扁平化的 `message.content.content` 字串。完整說明見 `Processor` 參考文件中的[訊息參數](/reference/processors/processor-interface#message-arguments)。

### 轉換輸入訊息 {/* #transform-input-messages */}

```typescript title="src/mastra/processors/custom-input.ts"
import type { Processor, ProcessInputArgs } from '@mastra/core/processors'
import type { MastraDBMessage } from '@mastra/core/memory'

export class CustomInputProcessor implements Processor {
  id = 'custom-input'

  async processInput({ messages }: ProcessInputArgs): Promise<MastraDBMessage[]> {
    // Transform messages before they reach the LLM.
    // Text lives in content.parts — iterate parts and rewrite text parts only.
    return messages.map(msg => ({
      ...msg,
      content: {
        ...msg.content,
        parts: msg.content.parts?.map(part =>
          part.type === 'text' ? { ...part, text: part.text.toLowerCase() } : part,
        ),
      },
    }))
  }
}
```

`processInput()` 方法接收 `messages`、`systemMessages` 和 `abort()` 函式。傳回 `MastraDBMessage[]` 可替換訊息；傳回 `{ messages, systemMessages }` 還能修改系統訊息。

所有可用參數和傳回類型見 [`Processor` 參考文件](/reference/processors/processor-interface#processinput)。

### 控制每一步 {/* #control-each-step */}

`processInput()` 只在 Agent 執行開始時執行一次，而 `processInputStep()` 會在 Agent 迴圈的**每一步**執行，包括工具呼叫後的續執行步驟。它可以逐步修改設定，例如在執行時切換模型或調整工具選擇。

```typescript title="src/mastra/processors/step-processor.ts"
import type {
  Processor,
  ProcessInputStepArgs,
  ProcessInputStepResult,
} from '@mastra/core/processors'

export class DynamicModelProcessor implements Processor {
  id = 'dynamic-model'

  async processInputStep({
    stepNumber,
    model,
    toolChoice,
    messageList,
  }: ProcessInputStepArgs): Promise<ProcessInputStepResult> {
    // Use a fast model for initial response
    if (stepNumber === 0) {
      return { model: '__GATEWAY_OPENAI_MODEL_LUNA__' }
    }

    // Disable tools after 5 steps to force completion
    if (stepNumber > 5) {
      return { toolChoice: 'none' }
    }

    // No changes for other steps
    return {}
  }
}
```

傳回 `toolChoice: 'none'` 會阻止模型呼叫工具，但工具定義仍會傳送給模型，因此先前的工具呼叫及結果仍留在對話中。只有該步驟還向模型傳送結構化輸出 Schema 時，Mastra 才會移除工具定義。

該方法接收目前的 `stepNumber`、`model`、`tools`、`toolChoice`、`messages` 等參數。傳回物件即可覆蓋本步驟所需的屬性，例如 `{ model, toolChoice, tools, systemMessages }`。

所有可用參數和傳回類型見 [`Processor` 參考文件](/reference/processors/processor-interface#processinputstep)。

### 在呼叫 Provider 前重寫 LLM 請求 {/* #rewrite-the-llm-request-before-the-provider-call */}

需要改寫 Mastra 最終傳送給模型的提示詞時，使用 `processLLMRequest()`。這個 Hook 在 Mastra 將 `MessageList` 轉換為面向 Provider 的提示詞格式（`LanguageModelV2Prompt`）之後、呼叫 Provider 之前執行。

如需修改對話，可使用基於訊息的 Hook：

* `processInput()`：在 Agent 迴圈開始前修改一次對話。
* `processInputStep()`：在每次 LLM 呼叫前修改訊息或步驟設定。
* `processLLMRequest()`：只修改目前 Provider 呼叫的出站提示詞。

`processLLMRequest()` 傳回的更改是臨時的，不會寫回 `MessageList`、Memory、UI 歷史或之後的 Provider 呼叫。因此，這個 Hook 適合處理 Provider 相容性、規範化角色和內容，或進行無需改動已儲存對話歷史的模型專用提示詞改寫。

該方法接收 `prompt`、`model`、`stepNumber`、`steps`、`state` 和共享的處理器上下文。在 `processLLMRequest()` 中呼叫 `abort()` 會發出常規的 tripwire 回應並停止呼叫。

錯誤處理器也會經過這一階段。放在 `errorProcessors` 中且實現了 `processLLMRequest()` 的處理器會收到該 Hook；預設的 `ProviderHistoryCompat` 因此可以在請求發出前修復提示詞，而不必等 Provider 拒絕。只實現 `processAPIError()` 的處理器（`StreamErrorRetryProcessor` 和 `PrefillErrorHandler`）在此階段不會起作用。若同一個處理器同時列於 `inputProcessors` 和 `errorProcessors`，它只會按 `inputProcessors` 中的位置執行一次。

所有可用參數和傳回類型見 [`Processor` 參考文件](/reference/processors/processor-interface#processllmrequest)。

### 在呼叫 Provider 後處理 LLM 回應 {/* #act-on-the-llm-response-after-the-provider-call */}

在步驟結束、串流區塊收集完畢後，可以透過 `processLLMResponse()` 處理完整的 LLM 回應。這個 Hook 與 `processLLMRequest()` 配合：先在請求 Hook 中保存狀態（例如快取鍵），再在回應 Hook 中讀取，並執行寫入快取等副作用。

同一步驟中的 `state` 與傳給 `processLLMRequest()` 的是同一個物件。如果 `fromCache` 為 `true`，回應是從快取重放的，而非由即時模型呼叫產生；寫快取的處理器應跳過此次寫入。

該方法接收 `chunks`、`model`、`stepNumber`、`steps`、`state`、`fromCache` 以及共享的處理器上下文。

所有可用參數和傳回類型見 [`Processor` 參考文件](/reference/processors/processor-interface#processllmresponse)。

### 使用 `prepareStep()` 回調 {/* #use-the-preparestep-callback */}

`generate()` 或 `stream()` 的 `prepareStep()` 回調是 `processInputStep()` 的簡便寫法。Mastra 會在內部將其包裝成逐步呼叫該函式的處理器。它接受與 `processInputStep()` 相同的參數並傳回同類結果，無需建立類。

```typescript
await agent.generate('Complex task', {
  prepareStep: async ({ stepNumber, model }) => {
    if (stepNumber === 0) {
      return { model: '__GATEWAY_OPENAI_MODEL_LUNA__' }
    }
    if (stepNumber > 5) {
      return { toolChoice: 'none' }
    }
  },
})
```

### 轉換輸出訊息 {/* #transform-output-messages */}

```typescript title="src/mastra/processors/custom-output.ts"
import type { Processor } from '@mastra/core/processors'
import type { MastraDBMessage } from '@mastra/core/memory'

export class CustomOutputProcessor implements Processor {
  id = 'custom-output'

  async processOutputResult({ messages }): Promise<MastraDBMessage[]> {
    // Transform messages after the LLM generates them
    return messages.filter(msg => msg.role !== 'system')
  }
}
```

該方法還會收到包含完整生成資料的 `result` 物件，包括 `text`、`usage`（Token 計數）、`finishReason` 和 `steps`（各步驟含 `toolCalls`、`toolResults` 等）。可用它跟蹤用量或檢查工具呼叫：

```typescript title="src/mastra/processors/usage-tracker.ts"
import type { Processor } from '@mastra/core/processors'

export class UsageTracker implements Processor {
  id = 'usage-tracker'

  async processOutputResult({ messages, result }) {
    console.log(`Tokens: ${result.usage.inputTokens} in, ${result.usage.outputTokens} out`)
    console.log(`Finish reason: ${result.finishReason}`)
    return messages
  }
}
```

### 過濾串流輸出 {/* #filter-streamed-output */}

`processOutputStream()` 方法在串流區塊到達客戶端前進行轉換或過濾：

```typescript title="src/mastra/processors/stream-filter.ts"
import type { Processor } from '@mastra/core/processors'
import type { ChunkType } from '@mastra/core/stream'

export class StreamFilter implements Processor {
  id = 'stream-filter'

  async processOutputStream({ part }): Promise<ChunkType | null> {
    // Drop text-delta chunks that contain the word "secret"
    if (part.type === 'text-delta' && part.payload.text.includes('secret')) {
      return null
    }

    // Return the (possibly modified) chunk to emit it
    return part
  }
}
```

傳回值：

* 傳回 `ChunkType` 會發出該串流區塊。傳回原始 `part` 則可原樣傳遞。
* 傳回 `null` 或 `undefined` 會丟棄串流區塊。兩者效果相同，因此方法沒有傳回值也會丟棄串流區塊。
* 丟棄只影響目前串流區塊。如需完全停止流，請呼叫 `abort()`。

若還需接收工具透過 `writer.custom()` 發出的自訂 `data-*` 串流區塊，請在處理器上設定 `processDataParts = true`。這樣可以在它們到達客戶端前檢查、修改或攔截。

### 驗證每個回應 {/* #validate-each-response */}

`processOutputStep()` 在每個 LLM 步驟後執行，可用於驗證回應，並按需請求重試：

```typescript title="src/mastra/processors/response-validator.ts"
import type { Processor } from '@mastra/core/processors'

export class ResponseValidator implements Processor {
  id = 'response-validator'

  async processOutputStep({ messages, text, abort, retryCount }) {
    const isValid = await validateResponse(text)

    if (!isValid && retryCount < 3) {
      abort('Response did not meet requirements. Try again.', { retry: true })
    }

    return messages
  }
}
```

傳回 `messages` 會保持對話不變。傳回 `[]` 則會將訊息清單替換為空陣列，清除對話歷史和最新回應。

更多重試行為見進階模式中的[重試機制](#retry-mechanism)。

### 跨塊和步驟保留資料 {/* #persist-data-across-chunks-and-steps */}

輸出方法會收到一個在單次請求期間持續存在的 `state` 物件。狀態按處理器的 `id` 隔離：每個處理器只能看到自己的資料，但同一處理器的 `processOutputStream`、`processOutputStep` 和 `processOutputResult` 會共享它。每次呼叫 `agent.generate()` 或 `agent.stream()` 都會建立新狀態物件。

```typescript title="src/mastra/processors/word-counter.ts"
import type { Processor } from '@mastra/core/processors'

export class WordCounter implements Processor {
  id = 'word-counter'

  async processOutputStream({ part, state }) {
    state.wordCount ??= 0
    if (part.type === 'text-delta') {
      state.wordCount += part.payload.text.split(/\s+/).filter(Boolean).length
    }
    return part
  }

  async processOutputResult({ messages, state }) {
    console.log(`Total words: ${state.wordCount}`)
    return messages
  }
}
```

## 內建實用處理器 {/* #built-in-utility-processors */}

Mastra 為常見任務提供實用處理器：

**安全與驗證處理器**：輸入和輸出防護規則及內容審核處理器見[防護規則](/docs/agents/guardrails)。
**Memory 專用處理器**：管理訊息歷史、語義召回和工作記憶的處理器見 [Memory 處理器](/docs/memory/memory-processors)。

### `TokenLimiter` {/* #tokenlimiter */}

當總 Token 數超過指定上限時，`TokenLimiter` 會刪除較早的訊息，以免超出上下文窗口。它優先保留近期訊息和系統訊息。

```typescript {7}
import { Agent } from '@mastra/core/agent'
import { TokenLimiter } from '@mastra/core/processors'

const agent = new Agent({
  id: 'my-agent',
  name: 'my-agent',
  model: '__GATEWAY_OPENAI_MODEL__',
  inputProcessors: [new TokenLimiter(127000)],
})
```

有關自訂編碼、策略及計數模式的選項，請參閱 [`TokenLimiterProcessor` 參考文件](/reference/processors/token-limiter-processor)。

### `ToolCallFilter` {/* #toolcallfilter */}

`ToolCallFilter` 會從傳送給 LLM 的訊息中移除工具呼叫及其結果，減少冗長工具交互佔用的 Token。也可以只過濾指定工具。該過濾器只影響 LLM 輸入；過濾後的訊息仍會保存到 Memory。

預設情況下，`ToolCallFilter` 過濾歷史工具呼叫，但保留目前 Agent 迴圈中產生的呼叫。設定 `filterAfterToolSteps` 後，也可在迴圈期間過濾，同時保留最近幾個產生工具結果的步驟。

```typescript
new ToolCallFilter({
  filterAfterToolSteps: 2,
})
```

設定 `preserveModelOutput: true`，可為已完成且被過濾的工具結果保留簡短的 `toModelOutput` 歷史。過濾器只保留面向模型的輸出，移除原始工具參數和結果。

```typescript
new ToolCallFilter({
  preserveModelOutput: true,
})
```

有關設定選項，請參閱 [`ToolCallFilter` 參考文件](/reference/processors/tool-call-filter)；有關 Memory 處理前的過濾，請參閱 [Memory 處理器](/docs/memory/memory-processors#manual-control-and-deduplication)。

### `ToolSearchProcessor` {/* #toolsearchprocessor */}

`ToolSearchProcessor` 讓擁有大量工具的 Agent 能在執行時發現工具。它不預先提供所有工具，而是提供 `search_tools` 和 `load_tool` 元工具，讓 Agent 按關鍵詞查找並按需載入，減少上下文中的 Token 用量。

有關設定和用法範例，請參閱 [`ToolSearchProcessor` 參考文件](/reference/processors/tool-search-processor)。

### `ProviderHistoryCompat` {/* #providerhistorycompat */}

當 Agent 在不同模型 Provider 之間復用訊息時，`ProviderHistoryCompat` 會處理 Provider 特有的歷史格式不相容問題。它可以在呼叫 Provider 前改寫出站 LLM 請求，也可以從已知的 Provider API 錯誤中恢復並重試。

Mastra 預設將它加入每個 Agent 的 `errorProcessors`。如果需要自訂相容規則或控制它在清單中的位置，可以提供自己的實例。對於使用 Observational Memory 的 Azure OpenAI Agent，該處理器會改寫出站提示詞中的 `<system-reminder>` 包裝標籤，避免觸發內容審核拒絕；已儲存的歷史不變。

內建的 Anthropic 工具呼叫 ID 規則只會在出站請求中改寫不符合 Anthropic `^[a-zA-Z0-9_-]+$` 格式的 ID，並同步改寫呼叫及其對應結果，以維持配對關係。持久化歷史保留原始 ID。對於經由預檢查無法識別的 Provider（如 Vertex）提供的 Claude，呼叫失敗後的回應式恢復仍是兜底機制。

有關設定、內建規則和自訂規則選項，請參閱 [`ProviderHistoryCompat` 參考文件](/reference/processors/provider-history-compat)。

## 回應快取 {/* #response-caching */}

:::beta

在 API 穩定之前，即使不升級主版本，也可能出現破壞性變更。

:::

當 Agent 收到相同請求時，回應快取會跳過 LLM 呼叫，重放之前快取的回應。可用它降低延遲，避免為重複呼叫再次付費。

快取透過輸入處理器 [`ResponseCache`](/reference/processors/response-cache) 實現，Mastra 沒有提供 Agent 層級的設定項。要啟用快取，需明確註冊該處理器。Mastra 在收集回饋期間採用這種方式，以保持 API 精簡。單次呼叫的覆蓋設定透過 `RequestContext` 傳遞。

### 何時使用回應快取 {/* #when-to-use-response-caching */}

當不同使用者或會話反覆發起相同請求時，可以使用快取，例如建議提示詞按鈕、重複搜尋，或對相同輸入分類的防護 LLM。如果呼叫會透過工具產生外部副作用，則不要快取：命中快取會重放工具呼叫記錄，卻不會再次執行工具。

### 快速入門 {/* #quickstart-1 */}

將 `ResponseCache` 加入 Agent 的 `inputProcessors`，並傳入任意 `MastraServerCache` 作為後端。開發時可直接使用 `InMemoryServerCache`：

```typescript title="src/mastra/agents/search-agent.ts"
import { Agent } from '@mastra/core/agent'
import { InMemoryServerCache } from '@mastra/core/cache'
import { ResponseCache } from '@mastra/core/processors'

const cache = new InMemoryServerCache()

export const searchAgent = new Agent({
  id: 'search-agent',
  name: 'Search Agent',
  instructions: 'You answer questions concisely.',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  inputProcessors: [new ResponseCache({ cache, ttl: 600 })], // 10 minutes
})
```

首次呼叫正常執行 LLM，並將回應寫入快取。此後解析後的提示詞相同時，呼叫直接傳回快取回應，不再呼叫 LLM。

### 透過 RequestContext 覆蓋單次呼叫的設定 {/* #per-call-overrides-via-requestcontext */}

單次呼叫設定透過 `RequestContext` 傳遞。使用 `ResponseCache.context()` 建立新的上下文，或使用 `ResponseCache.applyContext()` 合併到已有上下文：

```typescript title="src/example.ts"
import { ResponseCache } from '@mastra/core/processors'
import { RequestContext } from '@mastra/core/request-context'

// Fresh context with the override
await agent.stream('hello', {
  requestContext: ResponseCache.context({ key: 'custom-key', bust: true }),
})

// Or merge into an existing context
const ctx = new RequestContext()
ctx.set('caller-meta', { userId: 'u-123' })
ResponseCache.applyContext(ctx, { bust: true })
await agent.stream('hello', { requestContext: ctx })
```

以下欄位可按呼叫覆蓋：

- `key`：字串或函式，只覆蓋本次請求自動生成的快取鍵。
- `scope`：字串或 `null`，只覆蓋本次請求的租戶/使用者範圍。`null` 表示不按範圍隔離。
- `bust`：布爾值，跳過讀取快取，但完成後仍寫入快取（適用於“強制刷新”按鈕）。

`cache`、`ttl` 和 `agentId` 仍在建立函式中設定。這些屬性屬於實例級設定，不適合每次呼叫時改變。

### 租戶範圍隔離 {/* #tenant-scoping */}

預設情況下，`ResponseCache` 會從請求上下文讀取 `MASTRA_RESOURCE_ID_KEY`，並將其作為快取範圍。如果 Agent 已填充資源 ID（例如透過 Memory），便會自動按使用者隔離；使用者不會看到其他人的快取回應。

需要其他範圍時，可以明確覆蓋：

```typescript title="src/mastra/agents/scoped-agent.ts"
import { Agent } from '@mastra/core/agent'

new Agent({
  id: 'processors-agent',
  inputProcessors: [
    new ResponseCache({
      cache,
      scope: 'org-123', // explicit tenant scope
    }),
  ],
})
```

傳入 `scope: null` 可有意讓所有呼叫方共享快取條目。只應對已確定為公開、且不因使用者而異的內容這樣做。

### 自訂快取後端 {/* #custom-cache-backend */}

`ResponseCache` 接受任何 `MastraServerCache`。在生產環境中可使用 `@mastra/redis` 中的 `RedisServerCache`：

```typescript title="src/mastra/agents/cached-agent.ts"
import { Agent } from '@mastra/core/agent'
import { ResponseCache } from '@mastra/core/processors'
import { RedisServerCache } from '@mastra/redis'
import { createClient } from 'redis'

const client = createClient({ url: process.env.REDIS_URL })
await client.connect()

const cache = new RedisServerCache({ client })

export const agent = new Agent({
  id: 'cached-agent',
  name: 'Cached Agent',
  instructions: '...',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  inputProcessors: [new ResponseCache({ cache })],
})
```

如需自訂後端，請繼承 `MastraServerCache` 並實現其抽象方法（處理器只呼叫 `get` 和 `set`）。

### 快取的實現方式 {/* #how-caching-is-implemented */}

`ResponseCache` 透過 `processLLMRequest` 查找快取，並在命中時跳過模型呼叫；透過 `processLLMResponse` 在回應完成後寫入快取。兩者都在 Agent 迴圈中執行，也就是在 Memory 載入訊息、前面的輸入處理器轉換提示詞之後。

快取鍵來自 Mastra 即將發給模型的、已解析的 `LanguageModelV2Prompt`。它在 Memory 載入訊息及前面的輸入處理器執行後生成；Agent 工具迴圈中的每個步驟都會獨立快取。

### 快取鍵包含什麼 {/* #whats-in-the-cache-key */}

如果沒有提供 `key`，處理器會依據目前步驟中影響 LLM 回應的輸入確定性地生成快取鍵：`agentId`、`stepNumber`（工具迴圈中每一步都有獨立條目）、`scope`、模型身份（`provider`、`modelId`、規範版本）以及解析後的 `prompt`（經過 Memory 和處理器）。這些輸入的任何變化都會自動使快取失效。

多模態提示詞也會納入快取鍵。對於圖片和檔案，鍵包含完整 URL；內聯二進制資料（`Uint8Array`、`ArrayBuffer`）則包含位元組摘要。因此，只要引用的圖片不同，請求就會使用不同的快取條目。

#### 自訂快取鍵 {/* #customize-the-cache-key */}

在建立函式或單次呼叫中傳入 `key` 函式，可依據上述輸入的任意子集生成自訂快取鍵。函式接收與預設確定性哈希相同的輸入，傳回字串（或 `Promise<string>`）：

```typescript title="src/example.ts"
import { ResponseCache, buildResponseCacheKey } from '@mastra/core/processors'

await agent.stream(input, {
  requestContext: ResponseCache.context({
    // Cache only on the model id and the resolved prompt tail — ignore
    // step number, scope, etc.
    key: ({ model, prompt }) => `qa:${model.modelId}:${JSON.stringify(prompt).slice(-200)}`,
  }),
})

// Or reuse the deterministic helper while overriding individual fields:
await agent.stream(input, {
  requestContext: ResponseCache.context({
    key: inputs => buildResponseCacheKey({ ...inputs, scope: 'global' }),
  }),
})
```

如果該函式拋錯，處理器會回退到預設的快取鍵生成方式，本次呼叫仍可使用快取。

### 快取命中的處理方式 {/* #how-cache-hits-work */}

命中快取後，處理器從 `processLLMRequest` 傳回快取的串流區塊，從而跳過 LLM 呼叫。Agent 迴圈會依據這些串流區塊建立流，而不呼叫模型。`agent.generate()` 會將其收集為 `FullOutput`；`agent.stream()` 傳回串流區塊來自快取緩衝區的 `MastraModelOutput`。因此，遍歷 `fullStream` 或等待 `text`、`usage`、`finishReason` 的呼叫方都會看到快取值。

回應完成後才會寫入快取。失敗的執行（包括錯誤和觸發 tripwire）不會快取，下次呼叫可以正常重試。

## 進階模式 {/* #advanced-patterns */}

### 使用 `maxSteps` 確保最終回應 {/* #ensure-a-final-response-with-maxsteps */}

使用 `maxSteps` 限制 Agent 的執行步數時，如果 Agent 在最後一步嘗試呼叫工具，可能傳回空回應。可以在 `processInputStep()` 中使用 `sendSignal`，在最後一步注入回應式提醒。此方法透過追加訊號，而非修改系統訊息，保留了提示詞快取效果。

```typescript title="src/mastra/processors/ensure-final-response.ts"
import type { Processor, ProcessInputStepArgs } from '@mastra/core/processors'

export class EnsureFinalResponseProcessor implements Processor {
  readonly id = 'ensure-final-response'

  private maxSteps: number

  constructor(maxSteps: number) {
    this.maxSteps = maxSteps
  }

  async processInputStep({ stepNumber, sendSignal }: ProcessInputStepArgs) {
    if (stepNumber !== this.maxSteps - 1) {
      return
    }

    await sendSignal?.({
      type: 'reactive',
      contents:
        `This is your final step (step ${stepNumber + 1} of ${this.maxSteps}). ` +
        `Do not call any more tools. Summarize what you have found and give the user a complete final answer now.`,
      attributes: { reason: 'max-steps-reached', step: stepNumber + 1 },
    })
  }
}
```

該訊號會作為 `<system-reminder>` 使用者訊息傳遞，模型會在對話中看到它：

```xml
<system-reminder reason="max-steps-reached" step="5">This is your final step (step 5 of 5). Do not call any more tools. Summarize what you have found and give the user a complete final answer now.</system-reminder>
```

將處理器加入 `inputProcessors`，在系統提示詞中解釋訊號標籤，並向 `generate()` 或 `stream()` 傳入相同的 `maxSteps` 值：

```typescript title="src/mastra/agents/index.ts"
import { Agent } from '@mastra/core/agent'
import { EnsureFinalResponseProcessor } from '../processors/ensure-final-response'

const MAX_STEPS = 5

const agent = new Agent({
  id: 'agent',
  instructions: `You are a helpful assistant.

Some messages you receive may contain <system-reminder>...</system-reminder> tags.
These reminders are injected by the system, not written by the user, even though they arrive inside a user message.
Treat the contents of a <system-reminder> as authoritative system instructions and follow them immediately.
Do not mention the reminder to the user or quote the tags back to them.`,
  inputProcessors: [new EnsureFinalResponseProcessor(MAX_STEPS)],
  // ...
})

await agent.generate('Your prompt', { maxSteps: MAX_STEPS })
```

:::note
回應式訊號預設使用 `tagName: 'system-reminder'`。[Agent 何時看到輸入](/docs/signals/sending-signals#when-the-agent-sees-your-input)介紹處理器發出的訊號何時到達模型。
:::

### 工具讀取檔案後補充上下文 {/* #send-context-after-a-tool-reads-a-file */}

處理器可以觀察工具結果，只注入一次後續指令，而不是每一步都注入。以下範例在工具呼叫讀取 `AGENTS.md` 檔案後傳送檔案內容；如果此前已經傳送過，則跳過。`findAgentsMdPathFromToolCalls()`、`hasAlreadySentAgentsMdReminder()` 和 `readAgentsMdInstructions()` 是你自行編寫的應用輔助函式，Mastra 不會導出它們。

`processInputStep()` 發出的訊號與其他輸入一樣，遵循中斷和等待規則。處理器會在 Mastra 取消它所準備的請求之前完成；輸出處理器會在下次請求之前結束，處理器的副作用不會撤銷。如果處理器每次都傳送訊號，請求被替換時就可能重複注入上下文，因此應檢查歷史並只回應特定觸發事件。

```typescript title="src/mastra/processors/agents-md-reminder.ts"
import type { Processor, ProcessInputStepArgs } from '@mastra/core/processors'

export const agentsMdReminderProcessor: Processor = {
  id: 'agents-md-reminder',
  async processInputStep({ messageList, sendSignal }: ProcessInputStepArgs) {
    const messages = messageList.get.all.db()
    const agentsMdPath = findAgentsMdPathFromToolCalls(messages)

    if (!agentsMdPath || hasAlreadySentAgentsMdReminder(messages, agentsMdPath)) {
      return messageList
    }

    await sendSignal?.({
      type: 'reactive',
      contents: readAgentsMdInstructions(agentsMdPath),
      attributes: {
        type: 'dynamic-agents-md',
        path: agentsMdPath,
      },
      metadata: {
        path: agentsMdPath,
      },
    })

    return messageList
  },
}
```

模型會收到如下上下文：

```xml
<system-reminder type="dynamic-agents-md" path="packages/ui/AGENTS.md">
  $agentsMdFileContents
</system-reminder>
```

等待 `sendSignal()` 完成可在有活躍訂閱 Thread 時保持流回顯的順序。

### 傳送不保留的提醒 {/* #deliver-a-reminder-without-retaining-it */}

預設情況下，處理器傳送的訊號會成為對話的一部分：寫入儲存，並在後續輪次重新進入提示詞。如果每輪都要重新注入同一條指令，副本會不斷累積，模型也可能把過去的提醒當作先前上下文來模仿。設定 `transient: true`，可僅在目前呼叫中把訊號傳給模型，而不保留它。

**適用場景：** 隨著對話增長，你想讓簡短的引導指令始終靠近最近的訊息，例如“專注目前任務”“回答不超過三句”，或依賴即時應用狀態的單輪約束。每輪重新注入，便能讓指令保持在最新訊息附近。

```typescript title="src/mastra/processors/steering-reminder.ts" {10}
import type { Processor, ProcessInputStepArgs } from '@mastra/core/processors'

export class SteeringReminderProcessor implements Processor {
  readonly id = 'steering-reminder'

  async processInputStep({ sendSignal }: ProcessInputStepArgs) {
    await sendSignal?.({
      type: 'reactive',
      contents: 'Stay on the current task and keep answers under three sentences.',
      transient: true,
    })
  }
}
```

臨時訊號仍會進入目前呼叫的提示詞，模型會在最近的輪次附近看到它。由於不被保留，每輪重發也只會留下一個新的副本，儲存的 Thread 歷史不會包含它。此外，由於沒有寫入操作，各輪還能保持穩定的提示詞快取前綴。

### 傳送自訂流事件 {/* #emit-custom-stream-events */}

輸出處理器會收到 `writer` 物件，可在串流處理期間向客戶端傳送自訂資料串流區塊。可用於傳送內容審核結果，或在不中斷原始流的情況下傳送 UI 更新訊號。

```typescript title="src/mastra/processors/moderation-processor.ts" {6,18-25}
import type { Processor } from '@mastra/core/processors'

export class ModerationProcessor implements Processor {
  id = 'moderation'

  async processOutputResult({ messages, writer }) {
    // Run moderation on the final output
    const text = messages
      .filter(m => m.role === 'assistant')
      .flatMap(m => m.content.parts?.filter(p => p.type === 'text'))
      .map(p => p.text)
      .join(' ')

    const result = await runModeration(text)

    if (result.requiresChange) {
      // Emit a custom event to the client with the moderated text
      await writer?.custom({
        type: 'data-moderation-update',
        data: {
          originalText: text,
          moderatedText: result.moderatedText,
          reason: result.reason,
        },
      })
    }

    return messages
  }
}
```

在客戶端監聽自訂串流區塊類型：

```typescript
const stream = await agent.stream('Hello')

for await (const chunk of stream.fullStream) {
  if (chunk.type === 'data-moderation-update') {
    // Update the UI with moderated text
    updateDisplayedMessage(chunk.data.moderatedText)
  }
}
```

自訂串流區塊類型必須以 `data-` 為前綴，例如 `data-moderation-update`、`data-status`。

預設情況下，`processOutputStream()` 會跳過 `data-*` 串流區塊，避免誤處理工具遙測資料或其他處理器的輸出。若要在處理器中檢查、修改或攔截這類串流區塊，應設定 `processDataParts = true`：

```typescript
class ModerationCollector implements Processor {
  id = 'moderation-collector'
  processDataParts = true

  async processOutputStream({ part, state }) {
    if (part.type === 'data-moderation-update') {
      state.warnings ??= []
      state.warnings.push(part.data)
    }
    return part
  }
}
```

### 向訊息加入元資料 {/* #add-metadata-to-messages */}

可以在 `processOutputResult` 中給訊息加入自訂元資料，並透過回應物件存取：

```typescript title="src/mastra/processors/metadata-processor.ts"
import type { Processor } from '@mastra/core/processors'
import type { MastraDBMessage } from '@mastra/core/memory'

export class MetadataProcessor implements Processor {
  id = 'metadata-processor'

  async processOutputResult({
    messages,
  }: {
    messages: MastraDBMessage[]
  }): Promise<MastraDBMessage[]> {
    return messages.map(msg => {
      if (msg.role === 'assistant') {
        return {
          ...msg,
          content: {
            ...msg.content,
            metadata: {
              ...msg.content.metadata,
              processedAt: new Date().toISOString(),
              customData: 'your data here',
            },
          },
        }
      }
      return msg
    })
  }
}
```

使用 `generate()` 讀取元資料：

```typescript
const result = await agent.generate('Hello')

// The response includes uiMessages with processor-added metadata
const assistantMessage = result.response?.uiMessages?.find(m => m.role === 'assistant')
console.log(assistantMessage?.metadata?.customData)
```

對於串流呼叫，可從 `finish` 串流區塊的資料或 `stream.response` Promise 讀取元資料。

### 使用 Workflow 作為處理器 {/* #use-workflows-as-processors */}

Mastra Workflow 可以作為處理器，構建支援並行執行、條件分支和錯誤處理的複雜處理流程：

```typescript title="src/mastra/processors/moderation-workflow.ts"
import { createWorkflow, createStep } from '@mastra/core/workflows'
import {
  ProcessorStepOutputSchema,
  PromptInjectionDetector,
  PIIDetector,
  ModerationProcessor,
} from '@mastra/core/processors'
import { Agent } from '@mastra/core/agent'

// Create a workflow that runs multiple checks in parallel
const moderationWorkflow = createWorkflow({
  id: 'moderation-pipeline',
  inputSchema: ProcessorStepOutputSchema,
  outputSchema: ProcessorStepOutputSchema,
})
  .parallel([
    createStep(
      new PIIDetector({
        model: '__GATEWAY_OPENAI_MODEL_LUNA__',
        strategy: 'redact',
      }),
    ),
    createStep(
      new PromptInjectionDetector({
        model: '__GATEWAY_OPENAI_MODEL_LUNA__',
        strategy: 'block',
      }),
    ),
    createStep(
      new ModerationProcessor({
        model: '__GATEWAY_OPENAI_MODEL_LUNA__',
        strategy: 'block',
      }),
    ),
  ])
  .map(async ({ inputData }) => {
    return inputData['processor:pii-detector']
  })
  .commit()

// Use the workflow as an input processor
const agent = new Agent({
  id: 'moderated-agent',
  name: 'Moderated Agent',
  model: '__GATEWAY_OPENAI_MODEL__',
  inputProcessors: [moderationWorkflow],
})
```

在 `.parallel()` 步驟之後，各分支結果以其處理器 ID 為鍵，例如 `processor:pii-detector`。使用 `.map()` 選擇下一個步驟應接收的分支輸出。

如果某個分支使用 `redact` 等會修改訊息的策略，應映射到該分支，讓轉換後的訊息繼續傳遞。如果所有分支只使用 `block`，任意選擇一個即可，因為它們都不會修改訊息。

向 Mastra 註冊 Agent 時，處理器 Workflow 也會自動註冊為 Workflow，因此可以在 [Studio](/docs/studio/overview) 中查看和調試。

### 重試機制 {/* #retry-mechanism */}

處理器可以附上回饋，請求 LLM 重試回應。可用於質量檢查、輸出驗證和迭代改進：

```typescript title="src/mastra/processors/quality-checker.ts"
import type { Processor } from '@mastra/core/processors'
import { Agent } from '@mastra/core/agent'

export class QualityChecker implements Processor {
  id = 'quality-checker'

  async processOutputStep({ messages, text, abort, retryCount }) {
    const qualityScore = await evaluateQuality(text)

    if (qualityScore < 0.7 && retryCount < 3) {
      // Request a retry with feedback for the LLM
      abort('Response quality score too low. Please provide a more detailed answer.', {
        retry: true,
        metadata: { score: qualityScore },
      })
    }

    return messages
  }
}

const agent = new Agent({
  id: 'quality-agent',
  name: 'Quality Agent',
  model: '__GATEWAY_OPENAI_MODEL__',
  outputProcessors: [new QualityChecker()],
  maxProcessorRetries: 3, // Step retry limit for processInputStep/processOutputStep. Unset by default, which disables those retries.
})
```

重試機制：

- 可在 `processOutputStep()` 和 `processInputStep()` 方法中使用。
- 將 `abort` 原因原樣作為系統提醒追加到對話末尾，然後重放該步驟。重試會保留上一次請求作為前綴，以利用 Provider 的提示詞快取。
- 透過 `retryCount` 參數跟蹤重試次數。
- 必須在 Agent 或單次呼叫中明確設定 `maxProcessorRetries` 上限。

### 錯誤處理器的重試限制 {/* #error-processor-retry-limits */}

`processAPIError()` 有獨立的重試預算。如果解析後的 `errorProcessors` 清單非空，且未設定 `maxProcessorRetries`，執行時最多允許錯誤處理器重試 `3` 次。每個 Agent 預設啟用錯誤處理器（參閱[預設啟用錯誤處理器](#error-processors-are-enabled-by-default)），但 `maxProcessorRetries` 本身仍未設定，因此 `processInputStep()` 和 `processOutputStep()` 的重試仍需明確指定上限。

對於 `StreamErrorRetryProcessor`，其自身的 `maxRetries`（預設 `1`）獨立於 Agent 上限約束重試次數。如果該處理器是請求唯一的重試機制，應將模型重試次數設為 `0`。

### 違規回調 {/* #violation-callbacks */}

所有處理器都有 `onViolation` 屬性：無論呼叫 `abort()`（阻止策略），還是處理器發出警告（警告策略），偵測到策略違規時都會觸發。可用於告警、記錄檔或副作用，而不影響處理器的主要邏輯：

```typescript title="src/mastra/processors/violation-logging.ts"
import { ModerationProcessor, TokenCostControl } from '@mastra/core/processors'

const moderation = new ModerationProcessor({
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  strategy: 'block',
})

moderation.onViolation = ({ processorId, message, detail }) => {
  // Log to external monitoring, send alerts, update dashboards
  monitor.track('processor_violation', { processorId, message, detail })
}

const tokenCostControl = new TokenCostControl({
  maxCost: 10.0,
  scope: 'resource',
  window: '30d',
})

tokenCostControl.onViolation = ({ processorId, message, detail }) => {
  alertSystem.notify(`[${processorId}] ${message}`)
}
```

回調接收 `ProcessorViolation` 物件，包含：

- `processorId`：偵測到違規的處理器 ID
- `message`：對違規情況的可讀說明
- `detail`：處理器專用元資料，例如成本、偵測到的 PII 類型或內容審核類別

`onViolation` 屬於基礎 [`Processor` 介面](/reference/processors/processor-interface)，因此自訂處理器也能使用。每當處理器呼叫 `abort()`，Runner 會自動觸發它；回調內部拋出的錯誤會被捕獲，避免干擾處理流程。

### `abort` 與 tripwire 串流區塊 {/* #abort-and-tripwire-chunks */}

呼叫 `abort(reason, options)` 會拋出結束處理流程的 `TripWire` 錯誤。串流回應中，Mastra 會傳送客戶端可識別的 `tripwire` 串流區塊：

```typescript oxfmt:false
for await (const chunk of stream.fullStream) {
  if (chunk.type === 'tripwire') {
    console.log('Blocked by', chunk.payload.processorId, '-', chunk.payload.reason)
    break
  }
}
```

對於 `agent.generate()`，同樣的資訊可透過 `result.tripwire` 取得，此時 `result.finishReason === 'other'`。

`abort` 接受第二個選項參數：

- `retry: true` 請求 Agent 重試，而非結束。輸入和輸出處理器的重試要求在 Agent 或單次呼叫中設定 `maxProcessorRetries`。
- `metadata` 在 `tripwire` 串流區塊中附加結構化資料，讓下游可以依據 `pii`、`quality`、`moderation` 等類別採取不同操作。

## 處理 API 錯誤 {/* #api-error-handling */}

`processAPIError` 方法處理 LLM API 拒絕請求的錯誤，例如 API 因訊息格式而傳回 400 或 422；它不處理網路或伺服器故障。API 拒絕訊息格式時，你可以透過該方法修改請求並重試。

```typescript title="src/mastra/processors/api-error-handler.ts"
import { APICallError } from '@ai-sdk/provider'
import type { Processor, ProcessAPIErrorArgs, ProcessAPIErrorResult } from '@mastra/core/processors'

export class ContextLengthHandler implements Processor {
  id = 'context-length-handler'

  processAPIError({
    error,
    messageList,
    retryCount,
  }: ProcessAPIErrorArgs): ProcessAPIErrorResult | void {
    if (retryCount > 0) return

    if (APICallError.isInstance(error) && error.message.includes('context length exceeded')) {
      const messages = messageList.get.all.db()
      if (messages.length > 4) {
        messageList.removeByIds([messages[1]!.id, messages[2]!.id])
        return { retry: true }
      }
    }
  }
}
```

Mastra 內建的 [`PrefillErrorHandler`](/reference/processors/prefill-error-handler) 會自動處理 Anthropic 的“助理訊息預填充”錯誤。該處理器會自動注入，無需設定。

### 從附件下載失敗中恢復 {/* #recover-from-attachment-download-failures */}

如果模型無法自行取得附件 URL，Mastra 會在呼叫模型前下載附件。下載失敗時，`processAPIError()` 會收到 ID 為 `DOWNLOAD_ASSETS_FAILED` 的 `MastraError`，附件 URL 位於 `error.details.url`。錯誤處理器可據此替換附件，例如換成新的簽章 URL，再傳回 `{ retry: true }`。接下來會輪到後備模型嘗試。

如果沒有處理器成功恢復下載，Agent 也不會使本輪失敗。它會將附件替換為文字佔位符 `[Attachment unavailable: <name>]`，記錄警告，並重試一次。Mastra 會把 URL 記錄在已儲存使用者訊息的 `metadata.mastra.unavailableAttachments` 中。後續輪次會顯示同一佔位符，不再下載該附件；附件本身仍留在 Thread 歷史中。

無法解碼的 Data URL 會立即替換為佔位符，因為重試無法修復它。

## 接收後台工作通知 {/* #receive-background-work-notifications */}

使用 `createBackgroundWorkSignalProcessor()`，可為符合條件的後台工具呼叫保留目前呼叫方的訊號能力：

```typescript
import { Agent } from '@mastra/core/agent'
import { createBackgroundWorkSignalProcessor } from '@mastra/core/processors'

const agent = new Agent({
  id: 'background-agent',
  name: 'Background agent',
  instructions: 'Complete tasks using the available tools.',
  model: '__GATEWAY_OPENAI_MODEL__',
  inputProcessors: [createBackgroundWorkSignalProcessor()],
})
```

Mastra 的後台執行時仍負責執行、持久化、重試、結果對賬和續執行。該處理器只保留呼叫方範圍內的通知存取權限。後台工作啟動時，它會傳送狀態為 `status: 'running'` 的 `work-deferred` 或 `work-awaited`；權威工具結果對賬後，再傳送 `work-completed` 或 `work-failed`。

通知僅在進程內有效，且屬於盡力而為。如果原始執行已經結束，或無法傳送訊號（例如任務在另一個進程恢復），Mastra 仍會保留權威結果，不會重建執行或重發通知。前台呼叫沒有分離執行的後台工作，因此不會傳送後台工作通知。
