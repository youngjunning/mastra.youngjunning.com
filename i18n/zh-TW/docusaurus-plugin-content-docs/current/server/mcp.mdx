# 內建 MCP 伺服器

Mastra 伺服器透過 `/api/mcp`，讓 [Model Context Protocol (MCP)](https://modelcontextprotocol.io/introduction) 用戶端存取你的 Agent、Workflow 與 Tool。你無須為此定義 `MCPServer`：註冊在 `Mastra` 執行個體中的每個 Agent、Workflow 與 Tool 都可使用，之後新增的 Agent 也會自動出現。

每個 MCP Tool 都是現有 HTTP 路由的輕量封裝。呼叫會經過與 HTTP 請求相同的參數驗證、身分驗證、RBAC、FGA 與所有權檢查，並使用相同的 `RequestContext`。MCP 用戶端能執行的操作，不會超出同一使用者透過 HTTP API 可執行的範圍。

內建伺服器可讓程式開發助理與其他 MCP 用戶端操作你正在執行的 Mastra 應用程式。若要用自己的提示詞與資源發布一組精選能力，請另外建立 [`MCPServer`](/docs/connections/mcp#expose-a-mastra-mcp-server)。

## 安裝 {/* #installation */}

此端點使用 `@mastra/mcp`；`@mastra/server` 將它宣告為選用的 peer dependency。在專案中安裝此套件即可啟用內建伺服器：

```bash npm2yarn
npm install @mastra/mcp@latest
```

未安裝時，伺服器的其他功能仍可運作；`/api/mcp` 會回傳 HTTP 501，以及提示安裝套件的 JSON-RPC 錯誤。只有專案安裝了 `@mastra/mcp`，`mastra build` 才會將它加入建置輸出。

## 何時提供端點 {/* #when-its-served */}

| 環境 | 是否提供 `/api/mcp` |
| - | - |
| `mastra dev` | 是，即使未設定身分驗證也會提供。為防止 DNS 重綁定，含有外部 `Origin` 或 `Host` 標頭的請求會遭拒；通道與區域網路 IP 位址也會受到限制。若要從其他電腦存取，請將 `server.host` 設為用戶端連線時使用的主機名稱或 IP 位址。只繫結 `0.0.0.0` 不會允許其他主機。 |
| 已設定 `server.auth` 的正式環境建置 | 是。每個請求都需要 bearer token。 |
| 未設定 `server.auth` 的正式環境建置 | 否，端點回傳 404。 |

設定 `server.mcp.enabled` 可覆寫預設行為。`false` 會在所有環境關閉端點。`true` 則會在沒有 `server.auth` 時仍提供端點，並記錄警告，因為任何能連上伺服器的人都能呼叫你的 Agent、Workflow 與 Tool。

## 連線客戶端 {/* #connect-a-client */}

啟動開發伺服器，然後讓用戶端連線至端點。以 Claude Code 為例：

```bash
claude mcp add --transport http mastra http://localhost:4111/api/mcp
```

設定身分驗證後，傳入 bearer token：

```bash
claude mcp add --transport http mastra https://my-app.example.com/api/mcp \
  --header "Authorization: Bearer $MASTRA_TOKEN"
```

若要從命令列檢視 Tool，請使用 [MCP Inspector](https://github.com/modelcontextprotocol/inspector)：

```bash
npx @modelcontextprotocol/inspector --cli http://localhost:4111/api/mcp \
  --transport http --header "Authorization: Bearer $MASTRA_TOKEN" --method tools/list
```

Cursor 與 VS Code 會從 JSON 檔案讀取伺服器設定。使用 Cursor 時，請將設定寫入 `.cursor/mcp.json`：

```json title=".cursor/mcp.json"
{
  "mcpServers": {
    "mastra": {
      "url": "http://localhost:4111/api/mcp",
      "headers": { "Authorization": "Bearer <your-token>" }
    }
  }
}
```

使用 VS Code 時，則寫入 `.vscode/mcp.json`：

```json title=".vscode/mcp.json"
{
  "servers": {
    "mastra": {
      "type": "http",
      "url": "http://localhost:4111/api/mcp",
      "headers": { "Authorization": "Bearer <your-token>" }
    }
  }
}
```

伺服器未設定 `server.auth` 時，省略 `headers`。有些用戶端只接受 URL，無法傳送 `Authorization` 標頭，例如 Claude 應用程式中的自訂連接器；它們需要 [OAuth 探索機制](#oauth-discovery)，以及可讓使用者登入的身分供應商。

端點使用無狀態 Streamable HTTP，同時支援 MCP `2026-07-28` 與目前用戶端使用的 2025 年版本，因此不會在請求之間保留工作階段。

### 在 Studio 中 {/* #in-studio */}

Studio 的 **MCP Servers** 頁面會在自行註冊的 MCP 伺服器上方，以 **Mastra (built-in)** 顯示內建伺服器。頁面列出端點 URL（包含自訂的 `server.mcp.path` 或 `apiPrefix`）、端點是否開放或由 `server.auth` 保護、提供的 Tool 集（不反映 `include` 與 `exclude` 設定），以及可複製的 Claude Code、Cursor、VS Code 和 MCP Inspector 設定。設定中的 `<your-token>` 是佔位符，請換成自己的 bearer token。如果端點已關閉或未安裝 `@mastra/mcp`，資訊卡會說明原因與處理方式。

端點 URL 是依 Studio 存取伺服器所用的位址建立。若 MCP 用戶端透過不同的公開 URL 存取伺服器，例如經過反向代理，請在用戶端設定中使用該 URL。透過 [OAuth 探索機制](#oauth-discovery)，可登入的用戶端不必設定 `Authorization` 標頭。

Studio 透過 `GET /api/mcp/builtin` 取得這些資訊，此請求需要 `mcp:read` 權限。由於 Tool 清單取決於呼叫者的 token，Studio 不會列出伺服器的 Tool，也無法在其中試用。請連接用戶端查看可用的 Tool。

## Tool {/* #tools */}

伺服器將 Tool 分成不同的 Tool 集。本節說明 `agents`、`workflows` 與 `tools`；其餘請參閱[記憶、可觀測性與 Agent 建構器](#memory-observability-and-agent-builder)。操作類 Tool 以 ID 為參數存取 Agent 與 Workflow，因此新增 Agent 不會增加 Tool 清單的長度。

各 Tool 的參數、路由及權限，請參閱[內建 MCP Tool 參考](/reference/server/builtin-mcp-tools)。

| Tool 集 | Tool | 對應的 HTTP 路由 |
| - | - | - |
|`agents` | `list_agents`, `get_agent`, `call_agent` | `GET /agents`, `GET /agents/:agentId`, `POST /agents/:agentId/generate` |
| `workflows` | `list_workflows`, `get_workflow`, `start_workflow`, `get_workflow_run`, `resume_workflow_run`, `cancel_workflow_run` | `GET /workflows`, `GET /workflows/:workflowId`, `POST /workflows/:workflowId/start-async`, `GET /workflows/:workflowId/runs/:runId`, `POST /workflows/:workflowId/resume-async`, `POST /workflows/:workflowId/runs/:runId/cancel` |
| `tools` | 每個已註冊 Tool 對應一個 `tool_<id>` | `POST /tools/:toolId/execute` |

- 呼叫者可見的 Agent 或 Workflow 不超過 `enumLimit`（預設為 25）時，`agentId` 與 `workflowId` 參數會列出允許使用的 ID。超過上限後，參數改為一般字串，用戶端須透過 `list_agents` 或 `list_workflows` 查詢 ID。
- 呼叫者可見的 Tool 超過 `enumLimit` 時，`tool_<id>` 會改由 `list_tools`、`get_tool` 與 `call_tool` 提供。
- `call_agent` 會回傳回覆文字及 `threadId`。再次傳入 `threadId`，即可沿用 Agent 記憶中的同一段對話。未傳入 `threadId` 時會開啟新執行緒，因此從不傳入的用戶端每次呼叫都會儲存一個執行緒。
- `start_workflow` 會等待執行完成或暫停。暫停時會回傳 `runId` 與暫停資料，之後可用 `resume_workflow_run` 繼續。
- 未設定 `description` 的 Agent 會取得通用描述，並在日誌中產生警告。請補上描述，方便用戶端挑選適合的 Agent。

### 精選 Agent 與 Workflow {/* #featured-agents-and-workflows */}

將 Agent 或 Workflow 列入 `featured`，即可為其提供專用 Tool。精選 Workflow 的 Tool 會直接採用該 Workflow 的輸入 schema：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  // ...agents, workflows, tools
  server: {
    mcp: {
      featured: { agents: ['support-agent'], workflows: ['refund'] },
    },
  },
})
```

這會在操作類 Tool 之外新增 `agent_support-agent` 與 `workflow_refund`。

## 選擇要公開的內容 {/* #choose-what-to-expose */}

使用 `include` 和 `exclude`，依 ID 選擇要開放的能力。每個項目都會比對能力本身的 `id`，以及它在 `new Mastra({ ... })` 中註冊時的鍵，因此 `deleteAccountTool` 與 `delete-account` 會選到同一個 Tool。`exclude` 的優先順序高於 `include`。排除的能力不會出現在 Tool 清單中，無論用哪個名稱呼叫都會得到找不到的結果；將被排除 Agent 的 ID 傳給記憶 Tool 也是如此。可觀測性 Tool 不會受此篩選：結果仍可能包含被排除能力的 trace、日誌與分數。選取設定只影響 MCP，HTTP 路由不變。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  server: {
    mcp: {
      toolsets: ['agents', 'tools'],
      include: { agents: ['support-agent', 'billing-agent'] },
      exclude: { tools: ['delete-account'] },
    },
  },
})
```

設定 `readOnly: true` 後，只會提供對應路由需要 `read` 權限的 Tool，例如 `list_agents` 和 `get_workflow_run`。

用戶端可用 `?toolsets=agents,tools` 或 `X-MCP-Toolsets` 標頭，以及 `?readonly=1` 或 `X-MCP-Readonly` 標頭，進一步縮減單一連線可用的 Tool。這些設定只能移除 Tool，無法加入伺服器原本未提供的 Tool。

## 身分驗證與權限 {/* #authentication-and-permissions */}

此端點只接受 `Authorization: Bearer` 標頭中的憑證，並由 `server.auth` 驗證。工作階段 Cookie、`apiKey` 查詢參數及 Studio 的身分驗證設定都不適用，因此無法利用瀏覽器工作階段從其他網站存取端點。其他路由仍維持原有的驗證方式。

設定 [RBAC](/docs/auth/overview) 後，存取 MCP 除了需要對應路由的權限，還需要以下兩項權限：

- `mcp:read`：連線並列出 Tool。
- `mcp:execute`：查看並呼叫任何 Tool。即使用戶可透過 HTTP 執行相同操作，缺少此權限時仍只能取得空白的 Tool 清單。

每次呼叫還需要對應 HTTP 路由的權限，例如 `call_agent` 需要 `agents:execute`，`start_workflow` 需要 `workflows:execute`。預設的 `viewer` 角色只有 `mcp:read`，沒有 `mcp:execute`；`member`、`admin` 和 `owner` 兩者都有。這也是你註冊的 `MCPServer` 執行個體路由所使用的權限，因此原本獲准使用自建 MCP 伺服器的角色，也能使用內建伺服器。

Tool 清單會依呼叫者篩選。只有呼叫者在 `GET /agents` 或 `GET /workflows` 中看得到的 Agent 與 Workflow 才會顯示，其中包含 [FGA](/docs/auth/fga) 讀取權限檢查。呼叫後會收到 403 的 Tool 也會隱藏。每次實際執行時都會再次檢查權限，過時的清單無法繞過限制。

執行緒與執行紀錄的擁有權規則和 HTTP API 相同：使用者不能接續他人的執行緒，也不能恢復他人的 Workflow 執行。

傳入的 bearer token 不會當作參數交給 Tool，也不會轉送到其他伺服器。Tool 收到的 `RequestContext` 與對應 HTTP 請求相同。

## 記憶、可觀測性與 Agent 建構器 {/* #memory-observability-and-agent-builder */}

這些 Tool 集預設啟用。伺服器具備對應功能時才會提供各 Tool；每個 Tool 都會呼叫表列的 HTTP 路由，並進行相同的權限及擁有權檢查。

| Tool 集 | Tool | 提供條件 |
| - | - | - |
| `memory` | `list_threads`, `get_thread`, `list_messages`, `search_memory`, `get_memory_status`, `get_observations`, `create_thread`, `update_thread`, `clone_thread`, `save_messages` | Agent 具備記憶功能，或已設定儲存型 Agent |
| `observability` | `query_traces`, `aggregate_traces`, `query_spans`, `aggregate_spans`, `query_threads`, `get_trace_query_fields`, `get_trace_query_values`, `get_trace`, `get_span`, `get_trace_trajectory`, `list_logs`, `list_traces` | 儲存系統具備可觀測性網域 |
| `observability_analytics` | `analyze_metrics`, `analyze_scores`, `analyze_feedback`, `list_metric_names`, `list_scores`, `list_feedback` | 儲存系統具備可觀測性網域 |
| `stored_agents` | `list_available_models`, `list_stored_agents`, `get_stored_agent`, `create_stored_agent`, `update_stored_agent` | 已設定[編輯器](/docs/studio/editor)及 Agent 儲存網域 |

- 記憶 Tool 需要 `agentId` 與 `threadId`。如果 `server.auth` 透過 `mapUserToResourceId` 將使用者對應到資源，`resourceId` 預設為呼叫者的資源 ID，且呼叫者無法讀寫其他資源的執行緒、訊息或 Observational Memory。若沒有此對應關係，傳入的 `resourceId` 會和 HTTP API 一樣直接使用。
- 可觀測性 Tool 取決於儲存系統支援的功能。支援 trace 查詢的儲存系統（例如 DuckDB）會提供 `query_traces` 等查詢 Tool；不支援的則改為提供 `list_traces`。日誌、指標、分數及意見回饋 Tool，只有在儲存系統實作對應功能後才會出現。
- `get_trace` 回傳精簡的 trace，包含各 span 的 ID、父項、名稱、類型、時間、狀態及實體。用 `get_span` 可取得單一 span 的輸入、輸出與屬性。清單與 trace 結果限制在約 40,000 個字元內。截斷的結果會指出如何取得其餘內容：縮小分頁大小，或以回傳的 `nextOffset` 呼叫 `get_trace`。若單一項目仍過大，例如含有行內圖片的訊息，較長的值會被截斷並加上標記。`get_span` 會回傳完整 span；`get_observations` 也會以相同方式截斷過大的紀錄。
- `analyze_metrics`、`analyze_scores` 與 `analyze_feedback` 的 `op` 可設為 `aggregate`、`breakdown`、`timeseries` 或 `percentiles`；各操作會呼叫對應的 `/observability/<source>/<op>` 路由。
- `create_stored_agent` 與 `update_stored_agent` 預設會發布變更，因此可以立即用 `call_agent` 呼叫 Agent。傳入 `autoPublish: false` 可保留草稿。`call_agent` 的 `agentId` 參數只列出用戶端取得 Tool 清單當下已存在的 Agent；要呼叫新建立的 Agent，用戶端必須重新取得 Tool 清單。

唯讀模式下，查詢及彙總 Tool 仍可使用，因為其路由只需要 `observability:read`，即使它們使用 `POST`。記憶及儲存型 Agent 的寫入 Tool 會移除。`get_observations` 仍會保留，但沒有 `waitForPending` 選項，因為等待會呼叫需要 `memory:write` 的路由；缺少 `memory:write` 權限的呼叫者使用 `get_observations` 時也不會看到該選項。

:::warning

可觀測性資料不會依呼叫者隔離。擁有 `observability:read` 權限的人，無論透過 MCP 或 HTTP，都能讀取所有使用者的 trace、日誌、分數及意見回饋。預設的 `viewer` 角色會透過 `*:read` 取得此權限。對不應查看他人資料的角色，請移除其 `observability:read` 權限，或不要提供可觀測性 Tool 集：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  server: {
    mcp: { toolsets: ['agents', 'workflows', 'tools', 'memory', 'stored_agents'] },
  },
})
```

:::

### Agent 建立 Agent {/* #agents-creating-agents */}

`create_stored_agent` 可讓 MCP 用戶端建立供其他用戶端呼叫的 Agent，需要 `stored-agents:write` 權限。新 Agent 歸呼叫者所有，預設為私有。如果沒有呼叫者身分（例如未設定 `server.auth`），Agent 就沒有擁有者，即使設為 `visibility: 'private'` 仍會公開。其他使用者不會在 `list_agents` 或 `list_stored_agents` 中看到私有 Agent；除非是管理員或依 ID 獲得該 Agent 的授權，否則呼叫時會和 HTTP API 一樣收到找不到的回應。設定 `visibility: 'public'` 可讓所有使用者呼叫。不論是否公開，只有擁有者、管理員和依 ID 獲得授權的使用者能編輯；沒有擁有者的 Agent 可由任何具有 `stored-agents:write` 權限的使用者編輯。請參閱[儲存型 Agent 的可見性](/docs/studio/editor#visibility)。

當 Agent 建構器限制可用模型時，MCP Tool 只接受下列位置使用核准的模型：Agent 執行模型的 `provider` 與 `name`（包含各條件分支）、`defaultOptions` 中指定的模型（如 `structuredOutput.model`）、備援 `modelList` 中每個已啟用項目、記憶模型（Observational Memory 的 observer 和 reflector 模型及標題模型），以及處理器圖中任何深度的每個輸入與輸出處理步驟的 `model`。如果設定會使用政策無法檢查的預設模型，也會遭拒，例如 `observationalMemory: true`、未指定 `model` 的 Observational Memory 設定、建立時省略記憶設定（建構器會以預設模型補上 Observational Memory），或 `moderation` 這類需要模型卻未指定模型的處理器。請改為明確設定核准的 `model`。

儲存型 Agent 的 `model` 只接受 `provider`、`name` 及 `temperature` 等模型設定；`modelId`、`providerId` 等其他鍵會遭拒。若無法載入 Agent 建構器的政策，Tool 會回報錯誤，不會略過檢查直接儲存。`list_available_models` 會回傳允許的模型。HTTP 路由不執行此檢查，因此可直接呼叫 `POST /stored/agents` 的使用者仍能儲存任意模型。嵌入模型（`memory.embedder`）不在建構器的模型清單中，也不會檢查。儲存 Agent 時不會檢查 Tool 允許清單，因此新 Agent 可使用伺服器提供的任何 Tool；這些 Tool 會以呼叫 Agent 的使用者權限執行。

Observational Memory 只會在執行緒達到 token 門檻後開始觀察，預設門檻是 30,000 個 token。做簡短示範時，可降低 `observation.messageTokens`，讓 Agent 從少量訊息中學習。Observational Memory 會在背景處理訊息，因此呼叫 `call_agent` 後，請立即以 `waitForPending: true` 呼叫 `get_observations`，等待處理完成（最多 30 秒）再讀取。

## OAuth 探索機制 {/* #oauth-discovery */}

設定 `server.auth` 後，端點會依照 [MCP 授權規範](https://modelcontextprotocol.io/specification/draft/basic/authorization) 告訴 MCP 用戶端如何取得 token。未提供有效 token 的請求會收到 `401`，其 `WWW-Authenticate` 標頭會指向端點的受保護資源中繼資料（[RFC 9728](https://datatracker.ietf.org/doc/html/rfc9728)）：

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://my-app.example.com/.well-known/oauth-protected-resource/api/mcp"
```

如果請求帶有驗證失敗的 token（例如已過期），標頭還會包含 `error="invalid_token"`。其他路由回傳 `401` 時沒有此標頭。

中繼資料會公開提供於 `/.well-known/oauth-protected-resource/api/mcp` 與 `/.well-known/oauth-protected-resource`，位於 API 前綴之外：

```json
{
  "resource": "https://my-app.example.com/api/mcp",
  "authorization_servers": ["https://my-tenant.us.auth0.com/"],
  "bearer_methods_supported": ["header"]
}
```

用戶端讀取 `authorization_servers` 後，會向身分供應商執行 OAuth 流程，再帶著存取 token 重試。Mastra 本身不是授權伺服器。用戶端能否在未預先註冊 OAuth 應用程式的情況下登入，取決於身分供應商是否支援動態用戶端註冊或用戶端 ID 中繼資料文件。

Mastra 會依 `server.mcp.oauth` 及身分驗證供應商的設定填入中繼資料：

- `resource` 預設為從請求推得的端點 URL。經過代理伺服器或負載平衡器時，請求可能帶有內部主機名稱，因此請將 `server.mcp.oauth.resource` 設為公開 URL。此值必須是沒有片段識別碼的絕對 `https` URL（`localhost` 可使用 `http`）。無效值會留下錯誤日誌並關閉 OAuth 探索機制，但 token 受眾仍會依此值檢查，因此修正前 MCP 請求會遭拒。
- 驗證要求中的中繼資料 URL，使用 `resource` 的來源及伺服器上的端點路徑，例如 `/.well-known/oauth-protected-resource/api/mcp`。若代理伺服器以其他公開路徑提供端點，也必須將該 well-known URL 轉送給 Mastra。
- 若供應商知道自己的簽發者，`authorization_servers` 會由供應商提供（見下表）；否則請設定 `server.mcp.oauth.authorizationServers`。兩者皆無時，此欄位會省略，用戶端需手動設定 token。
- 只有設定 `server.mcp.oauth.scopesSupported`，中繼資料才會包含 `scopes_supported`。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { MastraAuthWorkos } from '@mastra/auth-workos'

export const mastra = new Mastra({
  server: {
    auth: new MastraAuthWorkos(),
    mcp: {
      oauth: {
        resource: 'https://my-app.example.com/api/mcp',
        authorizationServers: ['https://my-app.authkit.app'],
      },
    },
  },
})
```

### Token 受眾 {/* #token-audience */}

設定 `server.mcp.oauth.resource` 也會讓端點檢查 token 是否簽發給自己：token 的 `aud` 宣告必須包含 `resource` 的值。簽發給其他 API 的 token 會收到附帶 `error="invalid_token"` 的 `401`，因此從別的服務外洩的 token 無法重放到 MCP 端點。未設定 `resource` 時，身分驗證供應商接受的 token 仍可照常使用。這項檢查只適用於 `/api/mcp`；其他路由仍接受簽發給不同 API 的 token。比對必須完全一致，所以結尾多一個斜線的 `https://my-app.example.com/api/mcp/` 不等於 `https://my-app.example.com/api/mcp`。

請設定身分供應商簽發給該受眾的 token，例如在 Auth0 將 `resource` URL 註冊為 API 識別碼。Auth0 也會驗證自己的 `audience` 選項（`AUTH0_AUDIENCE`），因此應將該選項設為 `resource` URL，或簽發 `aud` 同時包含兩個值的 token。

| Provider | 公布的授權伺服器 | 是否依 `resource` 檢查受眾 |
| - | - | - |
| [`MastraJwtAuth`](/reference/auth/jwt) | `issuer` 選項 | 是 |
| [Auth0](/reference/auth/auth0) | `https://<domain>/` | 是 |
| [Okta](/reference/auth/okta) | `issuer` 選項 | 否。Okta 會依自己的 `audience` 選項檢查 token，請將該選項設為 `resource` URL。 |
| [Clerk](/reference/auth/clerk) | 從可發布金鑰取得的前端 API URL。OAuth 應用程式必須簽發 JWT 存取 token（2026 年 1 月以後建立的應用程式預設如此）；不透明 token 會遭拒。 | 否 |
| [Supabase](/reference/auth/supabase) | `<url>/auth/v1`。只有在 Supabase 專案啟用 OAuth 2.1 伺服器後，用戶端才能在此登入。 | 否 |
| [`CompositeAuth`](/docs/auth/composite-auth) | 所有內部供應商的伺服器 | 交由驗證 token 的供應商處理 |
| WorkOS、Google、Neon、Firebase、Better Auth、自訂供應商 | 設定 `authorizationServers` | 否 |

設定 `resource` 後，若供應商無法檢查受眾，Mastra 會在啟動時記錄警告，並接受該供應商簽發給任何受眾的 token。這讓 API 金鑰及其他不透明 token 仍能使用。若要改為在 `/api/mcp` 拒絕它們，請設定 `requireAudience: true`：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { CompositeAuth, SimpleAuth } from '@mastra/core/server'
import { MastraJwtAuth } from '@mastra/auth'

const jwtAuth = new MastraJwtAuth({
  jwksUri: 'https://auth.example.com/.well-known/jwks.json',
  issuer: 'https://auth.example.com/',
})
const apiKeyAuth = new SimpleAuth({ tokens: { [process.env.API_KEY!]: { id: 'ci' } } })

export const mastra = new Mastra({
  server: {
    auth: new CompositeAuth([jwtAuth, apiKeyAuth]),
    mcp: {
      oauth: { resource: 'https://my-app.example.com/api/mcp', requireAudience: true },
    },
  },
})
```

啟用 `requireAudience` 後，由 `SimpleAuth` 等無法檢查受眾的供應商驗證的請求，會在 `/api/mcp` 收到附帶 `error="invalid_token"` 的 `401`。在 `CompositeAuth` 中，只有這些供應商接受的請求會遭拒；其他路由仍接受。`requireAudience` 必須搭配 `resource`，未設定 `resource` 就不會執行檢查。

自訂供應商可實作 `verifyAudience()` 和 `getOAuthMetadata()` 來支援此機制；請參閱[自訂身分驗證供應商](/docs/auth/custom-auth-provider)。

### 連接 OAuth 用戶端 {/* #connect-an-oauth-client */}

若身分供應商支援動態用戶端註冊，可不帶 token 新增伺服器；用戶端會在首次使用時啟動登入流程：

```bash
claude mcp add --transport http mastra https://my-app.example.com/api/mcp
```

否則，請從身分供應商取得以 `resource` 為受眾的存取 token，並透過標頭傳入：

```bash
claude mcp add --transport http mastra https://my-app.example.com/api/mcp \
  --header "Authorization: Bearer $MASTRA_TOKEN"
```

端點目前不會回傳附帶 `error="insufficient_scope"` 的 `403`。缺少 `mcp:read` 權限的呼叫者只會收到一般的 `403`，因為 Mastra 權限不是用戶端可要求的 OAuth scope。

## 限制 {/* #limitations */}

- Workflow 會在 MCP 請求中同步執行。執行時間較長的 Workflow 受伺服器請求逾時限制。
- `Agent`、`Workflow` 及 Tool 建構函式目前無法個別關閉 MCP 存取；請使用 `server.mcp.include` 和 `server.mcp.exclude`。
- 工作記憶、刪除執行緒或儲存型 Agent，以及 scorer 與 Workspace 管理功能，皆未開放。
