# 用法

追蹤是可觀察訊號，記錄請求如何透過Agent、Workflow、Tool和模型呼叫移動。 Mastra 將每個操作表示為一個跨度，並將相關跨度分組到追蹤中，以便您可以檢查完整的執行路徑。

本頁面重點介紹特定於追蹤的概念：執行結果、跨度層次結構、取樣、元資料、過濾、追蹤 ID 和第三方追蹤上下文。

<Inject>
  **對於人工智慧Agent：**&#x8DD1;步`npx mastra api trace list '{"page":0,"perPage":20}'` to inspect recent traces directly instead of opening Studio or writing a temporary script. The command requires a running Mastra server with observability configured; start the local server with `npx mastra dev`，或傳遞可存取伺服器的基本 URL`--url`。跑步`npx mastra api trace list --schema`在建造不同的過濾器之前。安裝 Mastra 的技能`npx skills add mastra-ai/skills --skill mastra`取得完整的 API CLI 發現、定位、架構、驗證和錯誤處理指南。
</Inject>

## 何時使用追蹤 {/* #when-to-use-tracing */}

* 透過檢查完整的執行路徑來調試意外的Agent或工作流行為。
* 遵循單一請求內的模型呼叫、Tool呼叫和Workflow步驟。
* 附加特定於追蹤的元資料和標籤以進行過濾和調查。
* 將 Mastra 追蹤連接到第三方追蹤系統。

## 開始使用 {/* #get-started */}

要開始跟踪，請在 Mastra 實例中配置可觀察性並運行Agent或Workflow。您可以透過以下功能配置行為：

* [配置](/docs/observability/overview#configuration)：基本可觀察性配置和多個配置，以及無伺服器刷新
* [貯存](/docs/observability/overview#storage)：追蹤、日誌和指標的儲存路由

## 執行結果 {/* #execution-outcomes */}

Spans 透過三個本機欄位報告單一執行的含義：

* `outcome`：執行結果，如`success`, `error`, `abort`, `interrupted`, `suspend`, `limit`, `blocked`, or `unknown`.
* `stopReason`：可選的機器可讀原因，例如`max_steps`, `guardrail`, or `observer_failed`.
* `stopReasonContext`：有關該原因的可選緊湊事實，例如提供程序錯誤代碼、處理器 ID、訊號 ID 或相關跨度 ID。

一個`null` or absent outcome means no outcome has been recorded. Use `endTime` to determine whether a span has finished. Older observability versions can retain a `null` outcome on finished spans. Completing on the last allowed step is `success`. Needing another step after exhausting the allowance is `limit / max_steps`.

配置完成透過`stopWhen` or an iteration hook records `success` with `stop_condition` or `iteration_hook`. A successful delegation followed by a supervisor's `bail()` records `success / delegation_bail`. If the delegated worker fails and the hook bails, the worker retains its failure and the supervisor records `interrupted / delegation_bail` with `causeOutcome` and, when known, `causeStopReason` in `stopReasonContext`.

來電取消紀錄`abort / caller_cancelled` on the targeted run. Unfinished descendants stopped by that cancellation record `interrupted / caller_cancelled`. A run deadline records `limit / timeout` on the run; work interrupted by that deadline records `interrupted / timeout`. Completed spans retain their outcomes. Generic cleanup ends otherwise unclassified spans as `unknown`.

一個[guardrail](/docs/agents/guardrails) that stops execution by firing a tripwire reports `blocked / guardrail`. Its context identifies the processor:

```json
{
  "outcome": "blocked",
  "stopReason": "guardrail",
  "stopReasonContext": { "processorId": "moderation" }
}
```

對於 Mastra 產生的結果，`stopReasonContext` is a flat tooltip summary with at most three scalar fields. It excludes raw error messages, signal contents, tripwire metadata, and nested causes. Strings are limited to 128 characters. Oversized values are omitted. Missing facts are omitted, and a context with no available facts is `null`.

客製化生產者可以提供自己的結果字串、停止原因和上下文物件。這些值透過跨度更新、匯出和重建來保留，並且與跨度元資料使用相同的序列化限制。框架允許列表適用於 Mastra 產生的上下文。

模型區塊跨度在輸出處理器接受或編輯內容後捕獲內容。Provider的時間和完成情況是單獨記錄的，而不捕獲原始區塊內容。有意等待記錄的Workflow`suspend`; a stopped executor handing off unfinished work records `interrupted`, even when the persisted workflow status is `waiting`.

當觀察者失敗並停止主執行時，觀察者跨度記錄自己的結果，並且主跨度報告`interrupted / observer_failed`. The context links to the observer memory operation through `observerSpanId` and summarizes its result with `causeOutcome` and `causeStopReason`. For example, context-window exhaustion remains `limit / context_window_exceeded` on the observer. Read that span for its diagnostics. Signal interruptions retain only `signalId` and `signalType`.

如果配置的失敗策略讓主執行繼續，它仍然可以成功。恢復的護欄重試還保留成功的最終結果和被拒絕的嘗試的單獨結果。

`MastraStorageExporter`和`MastraPlatformExporter` carry these fields in exported span records. Persisting them requires a storage implementation that supports the fields.

模型推理跨距 (`MODEL_INFERENCE`) measure provider execution and record usage. Model chunk spans (`MODEL_CHUNK`) capture content after output processors have accepted or transformed it. Chunks belong to the logical step (`MODEL_STEP`), so buffered output can arrive after provider execution ends without outliving its parent. In the agent streaming paths, inference spans no longer capture response output; use the processed chunk spans or the generation output instead.

## 抽樣策略 {/* #sampling-strategies */}

採樣可讓您控制收集哪些跟踪，幫助您在可觀察性需求和資源成本之間取得平衡。

在高流量的生產環境中，收集每條痕跡可能成本高且不必要。

採樣策略可讓您捕獲具有代表性的追蹤子集，同時確保您不會錯過有關錯誤或重要操作的關鍵資訊。

您可以在可觀察性配置層級配置採樣：

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      '10_percent': {
        serviceName: 'my-service',
        // Sample 10% of traces
        sampling: {
          type: 'ratio',
          probability: 0.1,
        },
        exporters: [new MastraStorageExporter()],
      },
    },
  }),
})
```

這`sampling` option allows you to control which traces are collected, helping you balance between observability needs and resource costs. Mastra supports four sampling strategies:

1. **始終樣品**：收集 100% 的痕跡。最適合需要完全可見性的開發、偵錯或低流量場景。

   ```ts
   sampling: {
     type: 'always'
   }
   ```

2. **從不取樣**：完全禁用追蹤。對於追蹤沒有任何價值的特定環境或當您需要暫時停用追蹤而不刪除配置時非常有用。

   ```ts
   sampling: {
     type: 'never'
   }
   ```

3. **基於比率的取樣**：隨機採樣一定百分比的跡線。非常適合您需要統計洞察而無需完全追蹤成本的生產環境。機率值範圍從 0（無痕跡）到 1（所有痕跡）。

   ```ts oxfmt:false
   sampling: {
     type: 'ratio',
     probability: 0.1  // Sample 10% of traces
   }
   ```

4. ****：根據請求上下文、元資料或業務規則實作您自己的取樣邏輯。非常適合複雜的場景，例如基於使用者層、請求類型或錯誤條件進行採樣。

   ```ts oxfmt:false
   sampling: {
     type: 'custom',
     sampler: (options) => {
       // Sample premium users at higher rate
       if (options?.metadata?.userTier === 'premium') {
         return Math.random() < 0.5; // 50% sampling
       }

       // Default 1% sampling for others
       return Math.random() < 0.01;
     }
   }
   ```

## 新增自訂元數據 {/* #adding-custom-metadata */}

新增自訂元資料以在追蹤中記錄特定於應用程式的上下文，以偵錯生產問題。

元資料可以包括業務邏輯和效能指標。它還可以攜帶用戶上下文或解釋執行期間發生的情況的任何其他資訊。

您可以使用追蹤上下文將元資料新增至任何範圍：

```ts
execute: async (inputData, context) => {
  const startTime = Date.now()
  const response = await fetch(inputData.endpoint)

  // Add custom metadata to the current span
  context?.tracingContext.currentSpan?.update({
    metadata: {
      apiStatusCode: response.status,
      endpoint: inputData.endpoint,
      responseTimeMs: Date.now() - startTime,
      userTier: inputData.userTier,
      region: process.env.AWS_REGION,
    },
  })

  return await response.json()
}
```

此處設定的元資料將顯示在所有配置的匯出器中。

### 使用部署環境標記追蹤 {/* #tagging-traces-with-the-deployment-environment */}

設定頂層`environment` field on Mastra to automatically attach the deployment environment to all observability signals without passing `tracingOptions.metadata.environment` on each call.

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'

export const mastra = new Mastra({
  environment: 'production',
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-service',
        exporters: [new MastraStorageExporter()],
      },
    },
  }),
})
```

如果`environment` isn't set, runs started through `mastra dev` resolve to `development` (even though the dev server itself runs with `NODE_ENV=production`); otherwise Mastra falls back to `process.env.NODE_ENV`. If none of these are set, the field is left undefined rather than guessed.

每次通話`tracingOptions.metadata.environment` always takes precedence, so individual calls can override the value when needed.

### 自動元數據來自`RequestContext` {/* #automatic-metadata-from-requestcontext */}

您可以將 Mastra 配置為自動從 RequestContext 中提取值並將它們附加到追蹤中的所有範圍，而不是手動將元資料新增至每個範圍。這對於在整個追蹤中一致地追蹤使用者標識符和環境資訊以及功能標誌或其他請求範圍的資料非常有用。

#### 配置級提取 {/* #configuration-level-extraction */}

定義要在追蹤配置中提取哪些 RequestContext 鍵。這些鍵將自動包含為使用此配置建立的所有跨度的元資料：

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-service',
        requestContextKeys: ['userId', 'environment', 'tenantId'],
        exporters: [new MastraStorageExporter()],
      },
    },
  }),
})
```

現在，當您使用 RequestContext 執行Agent程式或Workflow時，會自動提取這些值：

```ts
const requestContext = new RequestContext()
requestContext.set('userId', 'user-123')
requestContext.set('environment', 'production')
requestContext.set('tenantId', 'tenant-456')

// All spans in this trace automatically get userId, environment, and tenantId metadata
const result = await agent.generate('Hello', {
  requestContext,
})
```

#### 按請求新增 {/* #per-request-additions */}

您可以使用新增特定於追蹤的鍵`tracingOptions.requestContextKeys`. These are merged with the configuration-level keys:

```ts
const requestContext = new RequestContext()
requestContext.set('userId', 'user-123')
requestContext.set('environment', 'production')
requestContext.set('experimentId', 'exp-789')

const result = await agent.generate('Hello', {
  requestContext,
  tracingOptions: {
    requestContextKeys: ['experimentId'], // Adds to configured keys
  },
})

// All spans now have: userId, environment, AND experimentId
```

#### 嵌套值提取 {/* #nested-value-extraction */}

使用點表示法從 RequestContext 提取巢狀值：

```ts
export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      default: {
        requestContextKeys: ['user.id', 'session.data.experimentId'],
        exporters: [new MastraStorageExporter()],
      },
    },
  }),
})

const requestContext = new RequestContext()
requestContext.set('user', { id: 'user-456', name: 'John Doe' })
requestContext.set('session', { data: { experimentId: 'exp-999' } })

// Metadata will include: { user: { id: 'user-456' }, session: { data: { experimentId: 'exp-999' } } }
```

#### 它是如何運作的 {/* #how-it-works */}

1. **追蹤狀態計算**：在追蹤開始時（根跨創建），Mastra 透過合併配置級密鑰和每個請求密鑰來計算要提取的密鑰
2. **自動擷取**：根跨度（Agent運行、Workflow執行）自動從 RequestContext 提取元數據
3. **子跨度提取**：如果通過，子跨度也可以提取元數據`requestContext` when creating them
4. **元數據優先級**：傳遞給跨度選項的顯式元資料始終優先於提取的元數據

### 在軌跡中新增標籤 {/* #adding-tags-to-traces */}

標籤是字串標籤，可協助您對追蹤進行分類和過濾。與元資料（包含結構化鍵值資料）不同，標籤是專為快速過濾和組織而設計的純字串。

使用`tracingOptions.tags` to add tags when executing agents or workflows:

```ts
// With agents
const result = await agent.generate('Hello', {
  tracingOptions: {
    tags: ['production', 'experiment-v2', 'user-request'],
  },
})

// With workflows
const run = await mastra.getWorkflow('myWorkflow').createRun()
const result = await run.start({
  inputData: { data: 'process this' },
  tracingOptions: {
    tags: ['batch-processing', 'priority-high'],
  },
})
```

#### 標籤如何運作 {/* #how-tags-work */}

* **僅根跨**：標籤僅應用於追蹤的根範圍（Agent運行或Workflow運行範圍）
* **廣泛支持**：大多數導出器都支援標籤來過濾和搜尋追蹤：
  * **智囊團**： 本國的`tags` field
  * **朗福斯**： 本國的`tags` field on traces
  * **阿里茲出口商**: `tag.tags` OpenInference attribute
  * **奧特爾出口商**: `mastra.tags` span attribute
  * **奧泰布里奇飯店**: `mastra.tags` span attribute
* **可與元資料結合**: 兩個都可以用`tags` and `metadata` in the same `tracingOptions`

```ts
const result = await agent.generate([{ role: 'user', content: 'Analyze this' }], {
  tracingOptions: {
    tags: ['production', 'analytics'],
    metadata: { userId: 'user-123', experimentId: 'exp-456' },
  },
})
```

#### 常見標籤模式 {/* #common-tag-patterns */}

* **環境**: `"production"`, `"staging"`, `"development"`
* **功能標誌**: `"feature-x-enabled"`, `"beta-user"`
* **請求類型**: `"user-request"`, `"batch-job"`, `"scheduled-task"`
* **優先權**: `"priority-high"`, `"priority-low"`
* **實驗**: `"experiment-v1"`, `"control-group"`, `"treatment-a"`

### 命名追蹤 {/* #naming-a-trace */}

例如，預設情況下，相同Agent或Workflow的每次運行都會獲得相同的根跨名稱`workflow run: 'skill-analyze'`. When one workflow runs over many subjects, set `rootSpanName` in `tracingOptions` to label each run. The name replaces the root span name in Studio's trace list and in exporters that display span names.

```ts
const run = await mastra.getWorkflow('skillAnalyze').createRun()

await run.start({
  inputData: { skillId: 'typescript' },
  tracingOptions: {
    rootSpanName: 'skill-analyze: typescript',
  },
})
```

此名稱僅適用於根跨度。子跨度保留其預設名稱。實體過濾器繼續工作，因為Workflow或Agent ID 單獨儲存為`entityId` and `entityName`.

基於 OpenTelemetry 的導出器和 Langfuse 導出器根據實體 ID 建立其跨度和追蹤名稱，因此它們不受影響。若要命名 Langfuse 跡線，請設定`metadata.traceName` as described in the [Langfuse integration](/integrations/observability/langfuse).

### 隱藏敏感輸入/輸出 {/* #hiding-sensitive-inputoutput */}

處理敏感資料時，您可能希望防止輸入和輸出值記錄到可觀察平台。使用`hideInput` and `hideOutput` in `tracingOptions` to exclude this data from all spans in a trace:

```ts
// Hide input data (e.g., user credentials, PII)
const result = await agent.generate([{ role: 'user', content: 'Process this sensitive data' }], {
  tracingOptions: {
    hideInput: true, // Input will be hidden from all spans
  },
})

// Hide output data (e.g., generated secrets, confidential results)
const result = await agent.generate([{ role: 'user', content: 'Generate API keys' }], {
  tracingOptions: {
    hideOutput: true, // Output will be hidden from all spans
  },
})

// Hide both input and output
const result = await agent.generate([{ role: 'user', content: 'Handle confidential request' }], {
  tracingOptions: {
    hideInput: true,
    hideOutput: true,
  },
})
```

#### 它是如何運作的 {/* #how-it-works-1 */}

* **全跡線效應**：當在根跨度上設定時，這些選項適用於追蹤中的所有子跨度（Tool調用，加上模型生成等）
* **匯出時過濾**：資料在執行期間在內部保持可用，但在將跨度導出到可觀察平台時被排除
* **可與其他選項結合使用**: 你可以用`hideInput`/`hideOutput` alongside `tags`, `metadata`, and other `tracingOptions`

```ts
const result = await agent.generate([{ role: 'user', content: 'Sensitive operation' }], {
  tracingOptions: {
    hideInput: true,
    hideOutput: true,
    tags: ['sensitive-operation', 'pii-handling'],
    metadata: { operationType: 'credential-processing' },
  },
})
```

[Sensitive Data Filter](/reference/observability/tracing/processors/sensitive-data-filter) processor, which can redact specific fields (like passwords, tokens, and keys) while preserving the rest of the input/output.

#### 子跨度和元資料提取 {/* #child-spans-and-metadata-extraction */}

在Tool或Workflow步驟中建立子範圍時，您可以傳遞`requestContext` parameter to enable metadata extraction:

```ts
execute: async (inputData, context) => {
  // Create child span WITH requestContext - gets metadata extraction
  const dbSpan = context?.tracingContext.currentSpan?.createChildSpan({
    type: 'generic',
    name: 'database-query',
    requestContext: context?.requestContext, // Pass to enable metadata extraction
  })

  const results = await db.query('SELECT * FROM users')
  dbSpan?.end({ output: results })

  // Or create child span WITHOUT requestContext - no metadata extraction
  const cacheSpan = context?.tracingContext.currentSpan?.createChildSpan({
    type: 'generic',
    name: 'cache-check',
    // No requestContext - won't extract metadata
  })

  return results
}
```

您可以對哪些子跨距包含 RequestContext 元資料進行細粒度控制。根跨度（Agent/Workflow執行）始終自動提取元數據，而子跨度僅在您明確傳遞時提取`requestContext`.

## 創建子跨度 {/* #creating-child-spans */}

子跨度可讓您追蹤Workflow步驟或Tool中的細粒度操作。它們提供對資料庫查詢和 API 呼叫等子操作以及檔案操作或複雜計算的可見性。這種層次結構可協助您識別效能瓶頸並了解操作的確切順序。

在Tool呼叫或Workflow步驟中建立子跨度以追蹤特定操作：

```ts
execute: async (inputData, context) => {
  // Create another child span for the main database operation
  const querySpan = context?.tracingContext.currentSpan?.createChildSpan({
    type: 'generic',
    name: 'database-query',
    input: { query: inputData.query },
    metadata: { database: 'production' },
  })

  try {
    const results = await db.query(inputData.query)
    querySpan?.end({
      output: results.data,
      metadata: {
        rowsReturned: results.length,
        queryTimeMs: results.executionTime,
        cacheHit: results.fromCache,
      },
    })
    return results
  } catch (error) {
    querySpan?.error({
      error,
      metadata: { retryable: isRetryableError(error) },
    })
    throw error
  }
}
```

子跨度自動從其父跨度繼承追蹤上下文，從而在可觀察性平台中維護關係層次結構。

## 跨距格式化 {/* #span-formatting */}

Mastra 提供了兩種在跨度資料到達可觀測平台之前對其進行轉換的方法：**span processors** and **custom span formatters**. Both allow you to modify, filter, or enrich trace data, but they operate at different levels and serve different purposes.

|特色|跨度处理器 |自定义 Span 格式化程序 |
| - | - | - |
|配置等級|可觀察性配置 |每個出口商 |
|運行於 |內部的`Span` object | Exported `ExportedSpan` data |
| Applies to | All exporters | Single exporter |
| Async support | No | Yes |
| Use case | Security, filtering, enrichment | Platform-specific formatting, async enrichment |

使用**span processors** for synchronous transformations that should apply to all exporters (like redacting sensitive data). Use **custom span formatters** when different exporters need different representations of the same data (like plain text for one platform and structured data for another), or when you need to perform asynchronous operations like fetching data from external APIs.

### 跨度處理器 {/* #span-processors */}

Span 處理器在匯出追蹤資料之前對其進行轉換、過濾或豐富。它们充当跨度创建和导出之间的管道，使您能够出于安全性、合规性或调试目的修改跨度。處理器運行一次並影響所有導出器。

#### 內建處理器 {/* #built-in-processors */}

* [敏感資料過濾器](/reference/observability/tracing/processors/sensitive-data-filter)編輯敏感資訊。它在預設的可觀察性配置中啟用。

#### 建立自訂處理器 {/* #creating-custom-processors */}

您可以透過實作來建立自訂跨度處理器`SpanOutputProcessor` interface. Here's a basic example that converts all input text in spans to lowercase:

```ts title="src/processors/lowercase-input-processor.ts"
import type { SpanOutputProcessor, AnySpan } from '@mastra/core/observability'
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'

export class LowercaseInputProcessor implements SpanOutputProcessor {
  name = 'lowercase-processor'

  process(span: AnySpan): AnySpan {
    span.input = `${span.input}`.toLowerCase()
    return span
  }

  async shutdown(): Promise<void> {
    // Cleanup if needed
  }
}

// Use the custom processor
export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      development: {
        spanOutputProcessors: [new LowercaseInputProcessor(), new SensitiveDataFilter()],
        exporters: [new MastraStorageExporter()],
      },
    },
  }),
})
```

`process()`必須改變它接收到的範圍並傳回相同的實例，或傳回`undefined` to drop the span. Don't return a copy (for example `{ ...span, input: '...' }`): `exportSpan()` and `isValid` are instance members of the live span, so a copy can't be exported. Mastra logs a processor error and drops the span in that case.

處理器按照定義的順序執行，允許您連結多個轉換。常見用例包括：

* 編輯敏感資料（密碼、令牌、API 金鑰）
* 新增特定於環境的元數據
* 根據條件過濾跨度
* 標準化資料格式
* 透過業務背景豐富跨度

## 量程過濾 {/* #span-filtering */}

跨度過濾可讓您在資料到達可觀測平台之前減少雜訊和每個跨度的成本。每個可觀察性實例進行配置，因此不同的導出器或環境可以保留不同層級的詳細資訊。

* 使用`excludeSpanTypes` to drop entire categories of spans with minimal configuration.
* 使用`spanFilter` when you need custom logic based on the exported span data.

以下範例示範如何在單一配置中組合這兩個選項：

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { SpanType } from '@mastra/core/observability'
import { Observability, MastraStorageExporter } from '@mastra/observability'
import { LangfuseExporter } from '@mastra/langfuse'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-app',
        exporters: [new MastraStorageExporter(), new LangfuseExporter()],
        excludeSpanTypes: [SpanType.MODEL_CHUNK, SpanType.MODEL_STEP],
        spanFilter: span => {
          if (span.type === SpanType.TOOL_CALL && span.attributes?.success) {
            return false
          }

          return true
        },
      },
    },
  }),
})
```

過濾在導出時按以下順序進行：

1. `includeInternalSpans` is `true`.
2. `excludeSpanTypes`刪除符合的跨度類型。
3. `spanOutputProcessors`變換剩餘的跨度。
4. `spanFilter`決定是否保留最終導出的跨度。

如果`spanFilter` throws, Mastra keeps the span and logs the error to avoid silent data loss. For the full span type list and more examples, see the [Span filtering reference](/reference/observability/tracing/span-filtering).

### 自訂跨度格式化程序 {/* #custom-span-formatters */}

自訂跨度格式化程式會改變跨度在特定可觀察性平台中的顯示方式。與跨距處理器不同，格式化程式是按匯出器配置的，允許針對不同的目標進行不同的格式化。格式化程序支援同步和非同步操作。

#### 使用案例 {/* #use-cases */}

* **從AI SDK訊息中提取純文字**：將結構化訊息數組轉換為可讀文本
* **轉換輸入/輸出格式**：自訂資料在特定平台的顯示方式
* **特定於平台的字段映射**：根據平台要求新增或刪除字段
* **非同步資料豐富**：從外部 API 或資料庫取得附加上下文

#### 配置 {/* #configuration */}

添加一個`customSpanFormatter` to any exporter configuration:

```ts title="src/mastra/index.ts"
import { BraintrustExporter } from '@mastra/braintrust'
import { LangfuseExporter } from '@mastra/langfuse'
import { SpanType } from '@mastra/core/observability'
import type { CustomSpanFormatter } from '@mastra/core/observability'
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'

// Formatter that extracts plain text from AI messages
const plainTextFormatter: CustomSpanFormatter = span => {
  if (span.type === SpanType.AGENT_RUN && Array.isArray(span.input)) {
    const userMessage = span.input.find(m => m.role === 'user')
    return {
      ...span,
      input: userMessage?.content ?? span.input,
    }
  }
  return span
}

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-service',
        exporters: [
          // Braintrust gets plain text formatting
          new BraintrustExporter({
            customSpanFormatter: plainTextFormatter,
          }),
          // Langfuse keeps the original structured format
          new LangfuseExporter(),
        ],
      },
    },
  }),
})
```

#### 連結多個格式化程序 {/* #chaining-multiple-formatters */}

使用`chainFormatters` to combine multiple formatters. Chains support both sync and async formatters:

```ts
import { chainFormatters } from '@mastra/observability'

const inputFormatter: CustomSpanFormatter = span => ({
  ...span,
  input: extractPlainText(span.input),
})

const outputFormatter: CustomSpanFormatter = span => ({
  ...span,
  output: extractPlainText(span.output),
})

const exporter = new BraintrustExporter({
  customSpanFormatter: chainFormatters([inputFormatter, outputFormatter]),
})
```

#### 非同步格式化程式 {/* #async-formatters */}

自訂 Span 格式化程式支援非同步操作，支援從外部 API 或資料庫取得資料等用例來豐富您的 Span：

```ts
import type { CustomSpanFormatter } from '@mastra/core/observability'

// Async formatter that enriches spans with user data
const userEnrichmentFormatter: CustomSpanFormatter = async span => {
  const userId = span.metadata?.userId
  if (!userId) return span

  // Fetch user data from your API or database
  const userData = await fetchUserData(userId)

  return {
    ...span,
    metadata: {
      ...span.metadata,
      userName: userData.name,
      userEmail: userData.email,
      department: userData.department,
    },
  }
}

// Async formatter that looks up additional context
const contextEnrichmentFormatter: CustomSpanFormatter = async span => {
  if (span.type !== SpanType.AGENT_RUN) return span

  // Fetch experiment configuration
  const experimentConfig = await getExperimentConfig(span.metadata?.experimentId)

  return {
    ...span,
    metadata: {
      ...span.metadata,
      experimentVariant: experimentConfig?.variant,
      experimentGroup: experimentConfig?.group,
    },
  }
}

// Use async formatters with an exporter
const exporter = new BraintrustExporter({
  customSpanFormatter: userEnrichmentFormatter,
})

// Or chain sync and async formatters together
const exporter = new LangfuseExporter({
  customSpanFormatter: chainFormatters([
    plainTextFormatter, // sync
    userEnrichmentFormatter, // async
    contextEnrichmentFormatter, // async
  ]),
})
```

:::注意
非同步格式化程式會增加跨距匯出的延遲。保持非同步操作快速（低於 100 毫秒）以避免減慢應用程式速度。考慮對經常存取的資料使用快取。
:::

## 序列化選項 {/* #serialization-options */}

序列化選項控制在匯出之前如何截斷範圍資料（輸入、輸出和屬性）。當處理大型負載、深層嵌套物件或需要優化追蹤儲存時，這非常有用。

### 配置 {/* #configuration-1 */}

添加`serializationOptions` to your observability configuration:

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-service',
        serializationOptions: {
          maxStringLength: 2048, // Maximum length for string values (default: 131072)
          maxDepth: 10, // Maximum depth for nested objects (default: 8)
          maxArrayLength: 100, // Maximum number of items in arrays (default: 50)
          maxObjectKeys: 75, // Maximum number of keys in objects (default: 50)
        },
        exporters: [new MastraStorageExporter()],
      },
    },
  }),
})
```

### 可用選項 {/* #available-options */}

|選項 |預設 |說明 |
| - | - | - |
|`maxStringLength` | 131072 (128 KB) | Maximum length for string values. Longer strings are truncated. |
| `maxDepth` | 8 | Maximum depth for nested objects. Deeper levels are omitted. |
| `maxArrayLength` | 50 | Maximum number of items in arrays. Additional items are omitted. |
| `maxObjectKeys` | 50 | Maximum number of keys in objects. Additional keys are omitted. |

### 使用案例 {/* #use-cases-1 */}

**增加調試限制**：增加這些限制以捕獲大型文件和 API 回應以及其他資料結構的更多上下文：

```ts oxfmt:false
serializationOptions: {
  maxStringLength: 262144, // Capture longer text content (256 KB)
  maxDepth: 12,            // Handle deeply nested JSON responses
  maxArrayLength: 200,     // Keep more items from large lists
}
```

****：當您不需要完整的負載可見性時，降低這些值可以降低儲存成本並提高效能：

```ts oxfmt:false
serializationOptions: {
  maxStringLength: 256,   // Truncate strings aggressively
  maxDepth: 3,            // Shallow object representation
  maxArrayLength: 10,     // Keep only first few items
  maxObjectKeys: 20,      // Limit object keys
}
```

所有選項都是可選的，如果未指定，它們將回退到上面顯示的預設值。

## 檢索追蹤 ID {/* #retrieving-trace-ids */}

當您在啟用追蹤的情況下執行Agent或Workflow時，回應包括`traceId` that you can use to look up the full trace in your observability platform. This is useful for debugging or customer support, or alternatively correlating traces with other events in your system.

### Agent追蹤 ID {/* #agent-trace-ids */}

兩個都`generate` and `stream` methods return the trace ID in their response:

```ts
// Using generate
const result = await agent.generate('Hello')

console.log('Trace ID:', result.traceId)

// Using stream
const streamResult = await agent.stream('Tell me a story')

console.log('Trace ID:', streamResult.traceId)
```

### Workflow追蹤 ID {/* #workflow-trace-ids */}

Workflow執行也返回追蹤 ID：

```ts
// Create a workflow run
const run = await mastra.getWorkflow('myWorkflow').createRun()

// Start the workflow
const result = await run.start({
  inputData: { data: 'process this' },
})

console.log('Trace ID:', result.traceId)

// Or stream the workflow
const { stream, getWorkflowState } = run.stream({
  inputData: { data: 'process this' },
})

// Get the final state which includes the trace ID
const finalState = await getWorkflowState()
console.log('Trace ID:', finalState.traceId)
```

### 使用追蹤 ID {/* #using-trace-ids */}

獲得追蹤 ID 後，您可以：

1. **在 Studio 中尋找痕跡**：導航到軌跡視圖並按 ID 搜尋
2. **外部平台查詢軌跡**：在 Langfuse、Braintrust、MLflow 或您的可觀察平台中使用 ID
3. ****：將追蹤 ID 包含在應用程式日誌中以供交叉引用
4. **分享以供調試**：提供追蹤ID以支援團隊或開發人員進行調查

僅當啟用追蹤時，追蹤 ID 才可用。如果追蹤被禁用或採樣排除了請求，`traceId` will be `undefined`.

## 與外部追蹤系統集成 {/* #integrating-with-external-tracing-systems */}

如果您的應用程式已使用分散式追蹤（例如 OpenTelemetry 或 Datadog），您可以將 Mastra 追蹤連接到父追蹤上下文。這使您可以透過應用程式及其 Mastra Agent程式或Workflow呼叫來追蹤請求。

### 傳遞外部追蹤 ID {/* #passing-external-trace-ids */}

使用`tracingOptions` parameter to specify the trace context from your parent system:

```ts
// Get trace context from your existing tracing system
const parentTraceId = getCurrentTraceId() // Your tracing system
const parentSpanId = getCurrentSpanId() // Your tracing system

// Execute Mastra operations as part of the parent trace
const result = await agent.generate('Analyze this data', {
  tracingOptions: {
    traceId: parentTraceId,
    parentSpanId: parentSpanId,
  },
})

// The Mastra trace will now appear as a child in your distributed trace
```

### 開放遙測集成 {/* #opentelemetry-integration */}

與 OpenTelemetry 整合可讓 Mastra 追蹤直接出現在您現有的可觀測平台中：

```ts
import { trace } from '@opentelemetry/api'

// Get the current OpenTelemetry span
const currentSpan = trace.getActiveSpan()
const spanContext = currentSpan?.spanContext()

if (spanContext) {
  const result = await agent.generate(userMessage, {
    tracingOptions: {
      traceId: spanContext.traceId,
      parentSpanId: spanContext.spanId,
    },
  })
}
```

### Workflow整合 {/* #workflow-integration */}

Workflow支援相同的追蹤傳播模式：

```ts
const workflow = mastra.getWorkflow('data-pipeline')
const run = await workflow.createRun()

const result = await run.start({
  inputData: { data: '...' },
  tracingOptions: {
    traceId: externalTraceId,
    parentSpanId: externalSpanId,
  },
})
```

### 將運行嵌套在較早的 Mastra 運行下 {/* #nesting-a-run-under-an-earlier-mastra-run */}

一個`parentSpanId` can point at two kinds of spans. The span can belong to your own tracing system, as in the examples above. Mastra then treats the run as the top of the trace it exports, and the run sets the trace's name, input, output, and tags.

該跨度也可以是同一軌跡中較早的 Mastra 運行，例如 LLM 法官對完成的轉彎進行評分。放`nestUnderParent: true` for this case. The new run becomes a child of that span, and the trace keeps the name, input, output, tags, user, and session of the run that started it.

```ts
const turn = await assistant.generate('When does my order ship?')

await judge.generate(`Grade this answer: ${turn.text}`, {
  tracingOptions: {
    traceId: turn.traceId,
    parentSpanId: turn.spanId,
    nestUnderParent: true,
  },
})
```

這`nestUnderRun()` helper builds the same options from the earlier run's result:

```ts
import { nestUnderRun } from '@mastra/core/observability'

await judge.generate(`Grade this answer: ${turn.text}`, {
  tracingOptions: nestUnderRun(turn),
})
```

兩次運行可以在不同的進程。馬斯特拉無視`nestUnderParent` when `traceId` or `parentSpanId` is missing or not valid. It also ignores the option when a tracing bridge starts the run in a different trace. The [Langfuse](/integrations/observability/langfuse) and [Braintrust](/integrations/observability/braintrust) exporters use this option. In other exporters, only the tags rule applies.

### 身分證件格式要求 {/* #id-format-requirements */}

Mastra 驗證追蹤和跨度 ID 以確保相容性：

* **追蹤 ID**：1-32個十六進位字元（OpenTelemetry使用32）
* **跨度 ID**：1-16個十六進位字元（OpenTelemetry使用16）



* 無效的追蹤 ID → 產生新的追蹤 ID
*

因此，即使輸入格式錯誤，追蹤也不會導致應用程式崩潰。

### {/* #example-express-middleware */}

下面是一個完整的範例，顯示了 Express 應用程式中的追蹤傳播：

```ts
import { trace } from '@opentelemetry/api'
import express from 'express'

const app = express()

app.post('/api/analyze', async (req, res) => {
  // Get current OpenTelemetry context
  const currentSpan = trace.getActiveSpan()
  const spanContext = currentSpan?.spanContext()

  const result = await agent.generate(req.body.message, {
    tracingOptions: spanContext
      ? {
          traceId: spanContext.traceId,
          parentSpanId: spanContext.spanId,
        }
      : undefined,
  })

  res.json(result)
})
```

這將創建一個單一的分散式跟踪，其中包括 HTTP 請求處理和 Mastra Agent執行，可以在您選擇的可觀察性平台中查看。

### MCP 通話 {/* #mcp-calls */}

模型上下文協定 (MCP) 呼叫無需任何設定即可連結呼叫者的追蹤和伺服器的追蹤。當Agent程式或Workflow透過以下方式呼叫Tool時`MCPClient`, the `MCPServer` that handles it keeps its own trace and records a link to the tool call span, and the tool call span links back to the server's span. Each side keeps its own trace, root span, and trace summary. When the server uses a tracing bridge and its HTTP instrumentation continues the caller's trace, the request joins that trace instead. Mastra storage saves the links with the spans, and exporters with span link support send them too.

這也適用於任何一方的非 Mastra 軟體。請參閱[`MCPServer` reference](/reference/tools/mcp-server#linking-to-the-callers-trace) for details, and the [`MCPClient` reference](/reference/tools/mcp-client) to send your own trace context.

### {/* #agent-operations */}

* **Agent運行**：使用說明和Tool完成執行

* **單獨的步驟**：有輸入/輸出的步驟處理
* **控制流程**：條件、循環、平行執行
* **等待操作**：延誤和事件等待
