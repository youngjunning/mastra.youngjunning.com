# 儲存出口商

這`MastraStorageExporter`將追蹤保留到您配置的儲存後端，以便透過 Studio 存取它們。它不需要外部服務。



`MastraStorageExporter`以前被稱為`DefaultExporter`. The original `DefaultExporter`類別仍然導出自`@mastra/observability`為了向後相容，但它已被棄用。新代码应该使用`MastraStorageExporter`.

:::

:::警告\[生產可觀察性]
可觀察性資料很快就會壓倒生產中的通用資料庫。對於高流量應用程序，將Observability儲存域路由到[ClickHouse](/integrations/databases/clickhouse) through [composite storage](/reference/storage/composite). See [Production Recommendations](#production-recommendations) for details.
:::

## 配置 {/* #configuration */}

### 先決條件 {/* #prerequisites */}

1. **儲存後端**：配置儲存Provider（libSQL、PostgreSQL等）
2. **工作室**：安裝以在本地查看痕跡

### 基本設定 {/* #basic-setup */}

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability, MastraStorageExporter } from '@mastra/observability'
import { LibSQLStore } from '@mastra/libsql'

export const mastra = new Mastra({
  storage: new LibSQLStore({
    id: 'mastra-storage',
    url: 'file:./mastra.db', // Required for trace persistence
  }),
  observability: new Observability({
    configs: {
      local: {
        serviceName: 'my-service',
        exporters: [new MastraStorageExporter()],
      },
    },
  }),
})
```

### 推薦配置 {/* #recommended-configuration */}

在您的可觀察性配置中包含 MastraStorageExporter：

```typescript
import { Mastra } from '@mastra/core'
import {
  Observability,
  MastraStorageExporter,
  MastraPlatformExporter,
  SensitiveDataFilter,
} from '@mastra/observability'
import { LibSQLStore } from '@mastra/libsql'

export const mastra = new Mastra({
  storage: new LibSQLStore({
    id: 'mastra-storage',
    url: 'file:./mastra.db',
  }),
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'mastra',
        exporters: [
          new MastraStorageExporter(), // Persists observability events to Mastra Storage
          new MastraPlatformExporter(), // Sends observability events to Mastra platform (requires MASTRA_PLATFORM_ACCESS_TOKEN)
        ],
        spanOutputProcessors: [new SensitiveDataFilter()],
      },
    },
  }),
})
```

## 匯出到儲存和平台 {/* #export-to-storage-and-platform */}

在 Mastra 平台上，一個非空`MASTRA_DEPLOYMENT_ID` disables `MastraStorageExporter` and the deprecated `DefaultExporter` by default. Other exporters remain enabled. The opt-in below applies only to `MastraStorageExporter`. Deprecated `DefaultExporter` stays disabled on Platform even with the flag set to `true`. Migrate to `MastraStorageExporter` to use this option.

:::警告即使選擇加入，本地儲存仍然被阻止

`retainStorageExporterOnPlatform: true` **doesn't** enable in-memory, local libSQL, or DuckDB observability writes on Platform. When the observability domain reports local persistence, the built-in storage exporter stays disabled: it won't persist traces, logs, metrics, scores, or feedback to that database. Other exporters continue to receive events.

:::

有了更新的適配器和`retainStorageExporterOnPlatform: true`, the behavior on Platform is:

|Observability資料庫|平台儲存導出 |
| - | - |
| PostgreSQL |允許 |
|遠端 libSQL/Turso (`libsql://` or `https://`) | Allowed |
| Local libSQL (`file:` or `:memory:`) | Blocked |
| libSQL embedded replica with a remote sync URL | Blocked: it still writes locally |
| DuckDB, including in-memory databases | Blocked |
| `InMemoryStore`, including the fallback when no storage is configured | Blocked |

若要繼續寫入您自己的遠端資料庫以及平台可觀察性，請設定[`retainStorageExporterOnPlatform`](/reference/observability/tracing/configuration#observabilityinstanceconfig) to `true` on the observability config:

```typescript
import { Observability, MastraStorageExporter, MastraPlatformExporter } from '@mastra/observability'

const observability = new Observability({
  configs: {
    production: {
      serviceName: 'my-service',
      retainStorageExporterOnPlatform: true,
      exporters: [new MastraStorageExporter(), new MastraPlatformExporter()],
    },
  },
})
```

透過這個`observability` instance to `new Mastra()` alongside your configured `storage` provider. The option applies only to this config, including exporters registered later. It doesn't configure a database or add exporters automatically. Other configs keep the default suppression unless they also opt in.

此限制適用於**observability domain**, which can use a different provider from your default application storage. It doesn't disable other storage domains. Outside Platform, local observability storage continues to work.

若要啟用此防護，請升級`@mastra/core` and any `@mastra/libsql` or `@mastra/duckdb` adapters alongside `@mastra/observability`: older or custom adapters without the `persistenceLocation` capability retain the existing opt-in behavior and aren't checked for local persistence.

被封鎖的匯出器會在初始化期間記錄警告，但即使您的日誌記錄設定隱藏了該警告，該限制仍然適用。如果雙重匯出未寫入資料庫，請根據上表檢查可觀察性Provider並設定遠端資料庫。重試或增加批次間隔不會啟用被封鎖的匯出器。

## 追蹤策略 {/* #tracing-strategies */}

MastraStorageExporter 根據您的儲存Provider自動選擇最佳追蹤策略。如果需要，您也可以覆蓋此選擇。

### 可用策略 {/* #available-strategies */}

|戰略|描述 |使用案例|
| - | - | - |
|**realtime** | Process each event immediately | Development, debugging, low traffic |
| **batch-with-updates** | Buffer events and batch write with full lifecycle support | Low volume Production |
| **insert-only** | Only process completed spans, ignore updates | High volume Production |
| **event-sourced** | Write one row when a span starts and another when it ends, then collapse them on read | High volume Production, in-progress traces |

### 策略配置 {/* #strategy-configuration */}

```typescript
new MastraStorageExporter({
  strategy: 'auto', // Default - let storage provider decide
  // or explicitly set:
  // strategy: 'realtime' | 'batch-with-updates' | 'insert-only' | 'event-sourced'

  // Batching configuration (applies to both batch-with-updates and insert-only)
  maxBatchSize: 1000, // Max spans per batch
  maxBatchWaitMs: 5000, // Max wait before flushing
  maxBufferSize: 10000, // Max spans to buffer
})
```

## 儲存Provider支持 {/* #storage-provider-support */}

不同的儲存Provider支援不同的追蹤策略。一些Provider支援生產工作負載的可觀察性，而其他Provider則主要用於本地開發。

如果您將策略設定為`'auto'`, the `MastraStorageExporter` automatically selects the optimal strategy for the storage provider. If you set an explicit strategy that the storage provider doesn't support, the exporter logs a warning and falls back to the provider's preferred strategy.

### 提供可觀察性支援的Provider {/* #providers-with-observability-support */}

|儲存Provider|首選策略 |支援的策略|建議用途 |
| - | - | - | - |
|**[ClickHouse](/integrations/databases/clickhouse)** | insert-only | insert-only | Production (high-volume) |
| **[PostgresStore](/integrations/databases/postgresql)** | batch-with-updates | batch-with-updates, insert-only | Production (low volume) |
| **[PostgresStoreVNext](/integrations/databases/postgresql)** | event-sourced | event-sourced | Production (high-volume) |
| **[MSSQL](/integrations/databases/mssql)** | batch-with-updates | batch-with-updates, insert-only | Production (low volume) |
| **[MongoDB](/integrations/databases/mongodb)** | batch-with-updates | batch-with-updates, insert-only | Production (low volume) |
| **[OracleDB](/integrations/databases/oracledb)** | batch-with-updates | batch-with-updates, insert-only | Production (low volume) |
| **[libSQL](/integrations/databases/libsql)** | batch-with-updates | batch-with-updates, insert-only | Default storage, good for development |



在下面`insert-only`, only completed spans are persisted, and span start and update events are ignored. A trace therefore becomes visible in Studio only after its root span ends, and filtering traces by `status: 'running'` returns no results. `PostgresStoreVNext` uses `event-sourced` tracing instead, so in-progress traces remain visible while preserving append-only writes.

:::

### 沒有可觀察性支援的Provider {/* #providers-without-observability-support */}

**don't support** the observability domain. If you're using one of these providers and need observability, use [composite storage](/reference/storage/composite) to route observability data to a supported provider:

* [凸面](/integrations/databases/convex)
* [動態資料庫](/integrations/databases/dynamodb)
* [Cloudflare D1](/integrations/databases/cloudflare-d1)
* [Cloudflare 耐用對象](/integrations/databases/cloudflare-kv)
* [烏普斯塔什](/integrations/databases/upstash)
* [蘭斯資料庫](/integrations/databases/lancedb)

### 策略優勢 {/* #strategy-benefits */}

* **即時的**：立即可見，最適合調試
* **大量更新**：吞吐量增加 10-100 倍，全生命週期
* **僅插入**：資料庫操作額外減少 70%，非常適合分析
* **事件來源**：僅追加類似於僅插入，但在執行運行時，正在進行的追蹤在 Studio 中保持可見

## 製作建議 {/* #production-recommendations */}

Observability數據在生產環境中快速成長。單一Agent互動可以產生數百個跨度，高流量應用程式每天可以產生數千個追蹤。大多數通用資料庫並未針對這種寫入量大、僅追加的工作負載進行最佳化。

### 推薦：用於大批量生產的 ClickHouse {/* #recommended-clickhouse-for-high-volume-production */}

[克利克屋](/integrations/databases/clickhouse)是專為大容量分析工作負載而設計的列式資料庫。這是生產可觀察性的建議選擇，因為：

* **針對寫入進行最佳化**：每秒處理數百萬次插入
* **高效率壓縮**
* **快速查詢**：列式儲存可實現快速追蹤查找和聚合
* **時間序列原生**：內建支援基於時間的資料保留和分區

### 使用複合存儲 {/* #using-composite-storage */}

[composite storage](/reference/storage/composite#specialized-storage-for-observability) to route observability data to ClickHouse while keeping other data in your primary database.

## 批次行為 {/* #batching-behavior */}

### 沖洗觸發器 {/* #flush-triggers */}

對於兩種批量策略（`batch-with-updates` and `insert-only`), traces are flushed to storage when any of these conditions are met:

1. **尺寸觸發**: 緩衝區達到`maxBatchSize` spans
2. **時間觸發**: `maxBatchWaitMs` elapsed since first event
3. **緊急沖洗**：緩衝方法`maxBufferSize` limit
4. **關閉**：強制刷新所有待處理事件

### 錯誤處理 {/* #error-handling */}

MastraStorageExporter 包含用於生產用途的可靠錯誤處理：

* **重試邏輯**：指數退避（500ms、1s、2s、4s）
* **瞬間故障**：帶退避功能的自動重試
* **持續失敗**: 4 次失敗嘗試後刪除批次
* ****：防止儲存中斷期間出現記憶體問題

## 丟棄的可觀測事件 {/* #dropped-observability-events */}

`DefaultExporter`當它無法持久保存可觀察性資料時，會發出結構化的放置事件。註冊出口商或橋樑`onDroppedEvent` to forward these drops to alerting or monitoring.

事件被丟棄的原因如下：

* `unsupported-storage`：儲存Provider沒有實現訊號類型。
* `retry-exhausted`：出口商重試批次最多`maxRetries` times and then dropped it.
* `span-not-updatable`： 在下面`realtime` or `batch-with-updates`, a span update or end reached storage but didn't apply, because the span was never stored or had already ended. Ended spans don't change.

以下範例示範了將丟棄詳細資訊轉發到監控端點：

```typescript title="src/mastra/observability.ts"
import { BaseExporter } from '@mastra/observability'
import type { ObservabilityDropEvent, TracingEvent } from '@mastra/core/observability'

class DropAlertExporter extends BaseExporter {
  name = 'drop-alerts'

  async onDroppedEvent(event: ObservabilityDropEvent) {
    await fetch('https://monitoring.example.com/observability-drops', {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({
        count: event.count,
        signal: event.signal,
        reason: event.reason,
        exporterName: event.exporterName,
      }),
    })
  }

  protected async _exportTracingEvent(_event: TracingEvent) {}
}
```

## 配置舉例 {/* #configuration-examples */}

```typescript
// Zero config - recommended for most users
new MastraStorageExporter()

// Development override
new MastraStorageExporter({
  strategy: 'realtime', // Immediate visibility for debugging
})

// High-throughput production
new MastraStorageExporter({
  maxBatchSize: 2000, // Larger batches
  maxBatchWaitMs: 10000, // Wait longer to fill batches
  maxBufferSize: 50000, // Handle longer outages
})

// Low-latency production
new MastraStorageExporter({
  maxBatchSize: 100, // Smaller batches
  maxBatchWaitMs: 1000, // Flush quickly
})
```
