# 儲存匯出器

`MastraStorageExporter` 會將 Trace 持久儲存到已設定的儲存後端，讓你在 Studio 查看，無須搭配外部服務。

:::note

`MastraStorageExporter` 原名為 `DefaultExporter`。為了維持向下相容，`@mastra/observability` 仍會匯出舊的 `DefaultExporter` 類別，但該類別已淘汰。新程式碼應使用 `MastraStorageExporter`。

:::

:::warning[正式環境的可觀測性]
在正式環境中，可觀測性資料可能很快超過通用資料庫的負荷。若應用程式流量大，請用[複合儲存](/reference/storage/composite)將可觀測性儲存領域的資料導向 [ClickHouse](/integrations/databases/clickhouse)。詳情請見[正式環境建議](#production-recommendations)。
:::

## 設定 {/* #configuration */}

### 事前準備 {/* #prerequisites */}

1. **儲存後端**：設定儲存 Provider，例如 libSQL 或 PostgreSQL。
1. **Studio**：安裝 Studio，以便在本機查看 Trace。

### 基本設定 {/* #basic-setup */}

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability, MastraStorageExporter } from '@mastra/observability'
import { LibSQLStore } from '@mastra/libsql'

export const mastra = new Mastra({
  storage: new LibSQLStore({
    id: 'mastra-storage',
    url: 'file:./mastra.db', // Required for trace persistence
  }),
  observability: new Observability({
    configs: {
      local: {
        serviceName: 'my-service',
        exporters: [new MastraStorageExporter()],
      },
    },
  }),
})
```

### 建議設定 {/* #recommended-configuration */}

在可觀測性設定中加入 MastraStorageExporter：

```typescript
import { Mastra } from '@mastra/core'
import {
  Observability,
  MastraStorageExporter,
  MastraPlatformExporter,
  SensitiveDataFilter,
} from '@mastra/observability'
import { LibSQLStore } from '@mastra/libsql'

export const mastra = new Mastra({
  storage: new LibSQLStore({
    id: 'mastra-storage',
    url: 'file:./mastra.db',
  }),
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'mastra',
        exporters: [
          new MastraStorageExporter(), // Persists observability events to Mastra Storage
          new MastraPlatformExporter(), // Sends observability events to Mastra platform (requires MASTRA_PLATFORM_ACCESS_TOKEN)
        ],
        spanOutputProcessors: [new SensitiveDataFilter()],
      },
    },
  }),
})
```

## 同時匯出至儲存層和 Platform {/* #export-to-storage-and-platform */}

在 Mastra Platform，若 `MASTRA_DEPLOYMENT_ID` 非空，預設會停用 `MastraStorageExporter` 及已淘汰的 `DefaultExporter`。其他匯出器仍然啟用。下方的選項只適用於 `MastraStorageExporter`，即使把旗標設為 `true`，Platform 上的 `DefaultExporter` 仍會停用。請改用 `MastraStorageExporter` 才能使用此選項。

:::warning 啟用選項後，仍不允許寫入本機儲存

`retainStorageExporterOnPlatform: true` **不會**讓 Platform 將可觀測性資料寫入記憶體、本機 libSQL 或 DuckDB。若可觀測性領域回報會在本機保存資料，內建儲存匯出器就會維持停用，不會在該資料庫保存 Trace、日誌、指標、分數或回饋。其他匯出器仍會接收事件。

:::

更新介接器並設定 `retainStorageExporterOnPlatform: true` 後，Platform 的行為如下：

| 可觀測性資料庫 | Platform 上的儲存匯出 |
| - | - |
| PostgreSQL | 允許 |
| 遠端 libSQL/Turso（`libsql://` 或 `https://`） | 允許 |
| 本機 libSQL（`file:` 或 `:memory:`） | 不允許 |
| 具有遠端同步 URL 的 libSQL 嵌入式複本 | 不允許：仍會在本機寫入 |
| DuckDB，包含記憶體內的資料庫 | 不允許 |
| `InMemoryStore`，包含未設定儲存時使用的備用方案 | 不允許 |

若要一邊使用 Platform 的可觀測性功能，一邊繼續寫入自己的遠端資料庫，請在可觀測性設定中將 [`retainStorageExporterOnPlatform`](/reference/observability/tracing/configuration#observabilityinstanceconfig) 設為 `true`：

```typescript
import { Observability, MastraStorageExporter, MastraPlatformExporter } from '@mastra/observability'

const observability = new Observability({
  configs: {
    production: {
      serviceName: 'my-service',
      retainStorageExporterOnPlatform: true,
      exporters: [new MastraStorageExporter(), new MastraPlatformExporter()],
    },
  },
})
```

將此 `observability` 執行個體和已設定的 `storage` Provider 一起傳入 `new Mastra()`。此選項只適用於這組設定，包括之後註冊於其中的匯出器。它不會自動設定資料庫或加入匯出器。其他設定仍會預設停用，除非也開啟此選項。

限制適用於**可觀測性領域**，該領域可以使用與應用程式預設儲存不同的 Provider。其他儲存領域不會被停用。在 Platform 以外，本機可觀測性儲存仍可正常使用。

若要啟用這項防護，請跟著 `@mastra/observability` 一起升級 `@mastra/core` 以及所用的 `@mastra/libsql` 或 `@mastra/duckdb` 介接器。舊版或自訂介接器若未實作 `persistenceLocation` 能力，仍沿用原有的選擇啟用行為，不會檢查是否在本機保存資料。

匯出器被封鎖時，會在初始化時記錄警告。即使日誌設定隱藏此警告，限制仍然有效。如果同時匯出時沒有資料寫入自己的資料庫，請對照上表確認可觀測性 Provider，並設定遠端資料庫。重試或拉長批次間隔無法啟用受封鎖的匯出器。

## Studio {/* #studio */}

在 Studio 檢視 Trace：

1. 啟動 Studio。
1. 前往 Observability。
1. 篩選或搜尋本機的 Trace。
1. 檢視 Span 詳細資訊。

## 追蹤策略 {/* #tracing-strategies */}

MastraStorageExporter 會依儲存 Provider 自動選擇最合適的追蹤策略。需要時，可以自行覆寫。

### 可用策略 {/* #available-strategies */}

| 策略 | 說明 | 適用場合 |
| - | - | - |
| **realtime** | 立即處理每個事件 | 開發、除錯、低流量環境 |
| **batch-with-updates** | 暫存事件後批次寫入，支援完整生命週期 | 資料量較小的正式環境 |
| **insert-only** | 只處理已結束的 Span，忽略更新 | 資料量較大的正式環境 |
| **event-sourced** | Span 開始和結束時各寫入一筆，讀取時合併 | 資料量較大的正式環境、進行中的 Trace |

### 設定策略 {/* #strategy-configuration */}

```typescript
new MastraStorageExporter({
  strategy: 'auto', // Default - let storage provider decide
  // or explicitly set:
  // strategy: 'realtime' | 'batch-with-updates' | 'insert-only' | 'event-sourced'

  // Batching configuration (applies to both batch-with-updates and insert-only)
  maxBatchSize: 1000, // Max spans per batch
  maxBatchWaitMs: 5000, // Max wait before flushing
  maxBufferSize: 10000, // Max spans to buffer
})
```

## 儲存 Provider 的支援情況 {/* #storage-provider-support */}

各儲存 Provider 支援的追蹤策略不同。有些可負荷正式環境的可觀測性工作量，有些則以本機開發為主。

若將策略設為 `'auto'`，`MastraStorageExporter` 會自動選擇最適合儲存 Provider 的策略。若明確指定 Provider 不支援的策略，匯出器會記錄警告，並改用該 Provider 的優先策略。

### 支援可觀測性的 Provider {/* #providers-with-observability-support */}

| 儲存 Provider | 優先策略 | 支援的策略 | 建議用途 |
| - | - | - | - |
| **[ClickHouse](/integrations/databases/clickhouse)** | insert-only | insert-only | 正式環境（大量資料） |
| **[PostgresStore](/integrations/databases/postgresql)** | batch-with-updates | batch-with-updates, insert-only | 正式環境（少量資料） |
| **[PostgresStoreVNext](/integrations/databases/postgresql)** | event-sourced | event-sourced | 正式環境（大量資料） |
| **[MSSQL](/integrations/databases/mssql)** | batch-with-updates | batch-with-updates, insert-only | 正式環境（少量資料） |
| **[MongoDB](/integrations/databases/mongodb)** | batch-with-updates | batch-with-updates, insert-only | 正式環境（少量資料） |
| **[OracleDB](/integrations/databases/oracledb)** | batch-with-updates | batch-with-updates, insert-only | 正式環境（少量資料） |
| **[libSQL](/integrations/databases/libsql)** | batch-with-updates | batch-with-updates, insert-only | 預設儲存，適合開發 |

:::note

使用 `insert-only` 時，只會儲存已結束的 Span，忽略 Span 開始和更新事件。因此，要等根 Span 結束，Trace 才會出現在 Studio；以 `status: 'running'` 篩選時不會傳回結果。`PostgresStoreVNext` 改用 `event-sourced` 追蹤，保有僅附加寫入的特性，也能看到進行中的 Trace。

:::

### 不支援可觀測性的 Provider {/* #providers-without-observability-support */}

下列儲存 Provider **不支援**可觀測性領域。若使用其中之一又需要可觀測性功能，可透過[複合儲存](/reference/storage/composite)將可觀測性資料導向支援的 Provider：

- [Convex](/integrations/databases/convex)
- [DynamoDB](/integrations/databases/dynamodb)
- [Cloudflare D1](/integrations/databases/cloudflare-d1)
- [Cloudflare Durable Objects](/integrations/databases/cloudflare-kv)
- [Upstash](/integrations/databases/upstash)
- [LanceDB](/integrations/databases/lancedb)

### 各策略的好處 {/* #strategy-benefits */}

- **realtime**：資料立即可見，最適合除錯。
- **batch-with-updates**：輸送量提升 10 至 100 倍，支援 Span 的完整生命週期。
- **insert-only**：資料庫操作量再減少 70%，很適合分析。
- **event-sourced**：和 insert-only 一樣採用僅附加寫入，但執行尚未結束時，仍可在 Studio 看到進行中的 Trace。

## 正式環境建議 {/* #production-recommendations */}

正式環境的可觀測性資料累積得很快。一次 Agent 互動可能產生數百個 Span，高流量應用程式每天可能產生數千筆 Trace。大多數通用資料庫未針對這種頻繁寫入、只附加資料的工作負載最佳化。

### 大量資料的正式環境建議使用 ClickHouse {/* #recommended-clickhouse-for-high-volume-production */}

[ClickHouse](/integrations/databases/clickhouse) 是為大量資料分析設計的欄式資料庫，推薦用於正式環境的可觀測性，原因如下：

- **寫入最佳化**：每秒可處理數百萬次插入。
- **壓縮效率高**：降低 Trace 資料的儲存成本。
- **查詢快速**：欄式儲存能快速查找和彙總 Trace。
- **原生支援時間序列**：內建依時間保留資料及分割資料的功能。

### 使用複合儲存 {/* #using-composite-storage */}

若使用不支援可觀測性的 Provider（例如 Convex 或 DynamoDB），或想改善效能，可用[複合儲存](/reference/storage/composite#specialized-storage-for-observability)將可觀測性資料導向 ClickHouse，其餘資料繼續留在主要資料庫。

## 批次處理方式 {/* #batching-behavior */}

### 批次寫入時機 {/* #flush-triggers */}

兩種批次策略（`batch-with-updates` 和 `insert-only`）只要符合下列任一條件，就會將暫存的 Trace 寫入儲存層：

1. **批次大小**：緩衝區中的 Span 數量達到 `maxBatchSize`。
1. **等待時間**：收到第一個事件後已過 `maxBatchWaitMs`。
1. **緊急寫入**：緩衝區接近 `maxBufferSize` 上限。
1. **關閉**：強制寫入所有待處理事件。

### 錯誤處理 {/* #error-handling */}

MastraStorageExporter 提供適合正式環境的錯誤處理：

- **重試機制**：指數退避（500 毫秒、1 秒、2 秒、4 秒）。
- **暫時性錯誤**：採退避方式自動重試。
- **持續性錯誤**：嘗試 4 次都失敗後，捨棄整批資料。
- **緩衝區溢位**：避免儲存服務中斷時發生記憶體問題。

## 捨棄的可觀測性事件 {/* #dropped-observability-events */}

`DefaultExporter` 無法保存可觀測性資料時，會發出結構化的捨棄事件。可用 `onDroppedEvent` 註冊匯出器或橋接元件，將這類事件轉送到警示或監控系統。

捨棄事件的原因如下：

- `unsupported-storage`：儲存 Provider 未實作該類型的訊號。
- `retry-exhausted`：匯出器對該批資料重試最多 `maxRetries` 次後，捨棄整批資料。
- `span-not-updatable`：在 `realtime` 或 `batch-with-updates` 策略下，Span 更新或結束事件已送達儲存層但未套用，因為 Span 從未存入或已經結束。已結束的 Span 不會再變動。

以下範例示範如何將捨棄事件的詳細資訊轉送到監控端點：

```typescript title="src/mastra/observability.ts"
import { BaseExporter } from '@mastra/observability'
import type { ObservabilityDropEvent, TracingEvent } from '@mastra/core/observability'

class DropAlertExporter extends BaseExporter {
  name = 'drop-alerts'

  async onDroppedEvent(event: ObservabilityDropEvent) {
    await fetch('https://monitoring.example.com/observability-drops', {
      method: 'POST',
      headers: { 'content-type': 'application/json' },
      body: JSON.stringify({
        count: event.count,
        signal: event.signal,
        reason: event.reason,
        exporterName: event.exporterName,
      }),
    })
  }

  protected async _exportTracingEvent(_event: TracingEvent) {}
}
```

## 設定範例 {/* #configuration-examples */}

```typescript
// Zero config - recommended for most users
new MastraStorageExporter()

// Development override
new MastraStorageExporter({
  strategy: 'realtime', // Immediate visibility for debugging
})

// High-throughput production
new MastraStorageExporter({
  maxBatchSize: 2000, // Larger batches
  maxBatchWaitMs: 10000, // Wait longer to fill batches
  maxBufferSize: 50000, // Handle longer outages
})

// Low-latency production
new MastraStorageExporter({
  maxBatchSize: 100, // Smaller batches
  maxBatchWaitMs: 1000, // Flush quickly
})
```
