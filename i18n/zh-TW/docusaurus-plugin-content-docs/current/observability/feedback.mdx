# 回饋

回饋記錄捕捉人機互動訊號，例如拇指、評分、評論和更正。當您需要將使用者、QA、Studio 或系統審核資料附加到追蹤或範圍並查詢該資料以及其他可觀察性訊號時，請使用回饋。

與指標和分數不同，回饋通常由人員或審核Workflow提供。數字回饋值可以隨著時間的推移進行聚合、分組、繪製圖表以及查詢百分位數。

## 何時使用回饋 {/* #when-to-use-feedback */}

* 收集Agent回應的用戶滿意度評級。
* 將 QA 評論或更正儲存在他們審查的追蹤旁邊。
* 建立按Agent、環境或實驗進行評級的儀表板。

## 添加回饋 {/* #add-feedback */}

使用`mastra.observability.addFeedback()` to annotate a trace or span from app code. The helper is optional on the observability entrypoint, so check that the active observability implementation supports it. See the [client SDK observability reference](/reference/client-js/observability) for all client methods.

```typescript title="src/mastra/feedback.ts"
if (!mastra.observability.addFeedback) {
  throw new Error('Feedback is not supported by the active observability implementation')
}

await mastra.observability.addFeedback({
  traceId: 'trace-123',
  spanId: 'span-456',
  feedback: {
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
    comment: 'The answer solved my issue.',
  },
})
```

回饋將發送至每個支援它的已配置導出器。每個出口商獨立處理自己的目的地。在本地儲存中遺失的追蹤不會阻止回饋到達平台或其他匯出器。

[`MastraStorageExporter`](/docs/observability/integrations/exporters/mastra-storage)在儲存回饋之前，請在您配置的儲存中尋找追蹤或跨度。如果重試後目標仍然不可用，則會記錄警告並跳過本機寫入。稱呼`mastra.observability.flush()` or `shutdown()` before your process exits to finish pending delivery.

## 查找訊息的踪跡 {/* #find-the-trace-for-a-message */}

回饋通常是針對用戶已閱讀的訊息收集的，因此您需要`traceId` for that message. Assistant messages carry it in `content.metadata`, both in the stream result and when the message is recalled later from memory:

```typescript title="src/mastra/message-trace.ts"
const agent = mastra.getAgent('weatherAgent')
const memory = await agent.getMemory()

const { messages } = await memory!.recall({ threadId, perPage: false })

const message = messages.find(m => m.id === messageId)
const traceId = message?.content.metadata?.traceId
```

該值與運行報告的追蹤值相同`traceId` on its result, so feedback collected at generation time and feedback collected later against a stored message anchor to the same trace. Messages produced while tracing is disabled have no `traceId`.

### 讀取追蹤 ID`useChat` {/* #read-the-trace-id-in-usechat */}

[`chatRoute()`](/reference/ai-sdk/chat-route)和[`handleChatStream()`](/reference/ai-sdk/handle-chat-stream) pass the run's `traceId` to your `messageMetadata` callback. Return it on the `start` part so the client has it on the live message without a server lookup:

```typescript title="src/mastra/index.ts"
chatRoute({
  path: '/chat/:agentId',
  messageMetadata: ({ part, traceId }) => (part.type === 'start' ? { traceId } : undefined),
})
```

```tsx title="app/chat.tsx"
const { messages } = useChat<UIMessage<{ traceId?: string }>>()

const lastMessage = messages.at(-1)
const traceId = lastMessage?.role === 'assistant' ? lastMessage.metadata?.traceId : undefined
```

如果您使用以下方式驗證元數據`messageMetadataSchema`, add `traceId: z.string().optional()` to it. Send the `traceId` with the user's vote to your own route, then call `addFeedback()` there. Check that the caller owns a message with that `traceId` before adding feedback, because the value comes from the client.

## 創建回饋 {/* #create-feedback */}

每一個`createFeedback()` requires `feedbackType` and `value`. Add `traceId` or `spanId` when the feedback should be anchored to a trace or a specific span. Use `feedbackSource` as optional string metadata, such as `user`, `qa`, `studio`, or `system`.

對於儲存級寫入，包括`timestamp` because the method writes directly to the store.

```typescript
const observability = await mastra.getStorage()!.getStore('observability')

await observability!.createFeedback({
  feedback: {
    feedbackId: 'feedback-rating-1',
    timestamp: new Date(),
    traceId: 'trace-123',
    spanId: 'span-456',
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
    comment: 'The answer solved my issue.',
    tags: ['production'],
  },
})

await observability!.createFeedback({
  feedback: {
    feedbackId: 'feedback-comment-1',
    timestamp: new Date(),
    feedbackSource: 'qa',
    feedbackType: 'comment',
    value: 'Needs a citation before shipping.',
    experimentId: 'support-agent-eval',
  },
})
```

## 列出回饋 {/* #list-feedback */}

使用`listFeedback()` to page through raw records or poll with delta mode.

```typescript
const result = await observability!.listFeedback({
  filters: {
    feedbackType: 'rating',
    feedbackSource: 'user',
    timestamp: { start: new Date(Date.now() - 7 * 24 * 60 * 60 * 1000) },
  },
  pagination: { page: 0, perPage: 20 },
  orderBy: { field: 'timestamp', direction: 'DESC' },
})

console.log(result.feedback, result.pagination?.hasMore)
```

過濾器包括目標字段，例如`traceId` and `spanId`, feedback fields such as `feedbackType`, `feedbackSource`, and `feedbackUserId`, and shared context fields such as `entityName`, `environment`, `experimentId`, and `tags`. See [`FeedbackFilter`](/reference/observability/feedback#feedbackfilter) for every filter field. Over HTTP, the same fields are passed as query parameters, for example `GET /api/observability/feedback?traceId=trace-123&environment=production`. See [list query parameters](/reference/observability/feedback#list-query-parameters).

```typescript
await observability!.listFeedback({
  filters: {
    traceId: 'trace-123',
    feedbackType: ['rating', 'thumbs'],
    tags: ['production'],
  },
})
```

## 刪除回饋 {/* #delete-feedback */}

使用`deleteFeedback()` to delete feedback records by id. This is useful when a comment contains sensitive data. Each request accepts at most 1,000 `feedbackIds`, and deletion is idempotent. The optional `organizationId` field filters by organization, and the optional `resourceId` field filters by resource. You can supply either filter independently or use both together. In Studio, each comment on a trace or span **Feedback** tab has a delete action. Deleting a trace with `deleteTraces()` also deletes the feedback linked to it. See [Deleting traces](/reference/client-js/observability#deleting-traces).

```typescript
await observability!.deleteFeedback({
  feedbackIds: ['feedback-1', 'feedback-2'],
})
```

刪除的記錄也會從回饋分析中消失。 ClickHouse 使用轻量级删除来隐藏行，但不保证立即物理删除，因此开源部署必须配置一个[observability retention period](/reference/storage/retention) to physically purge them. Each request is marked applied once its delete succeeds; if the delete fails, the request stays unapplied, doesn't block updates to the still-visible feedback, and you retry by calling the delete API again. On ClickHouse, the next review update also retries the delete and reports the feedback as not found if the retry succeeds, or saves the new status and returns the delete's error if it fails again. Open-source deployments have no background reconciler. Configure retention for every observability signal to expire deletion requests after the signal rows they protect. If any signal is unbounded, deletion requests also remain unbounded to prevent deleted data from being reintroduced. On ClickHouse, delete APIs leave the separate delta cursor table untouched. Its rows contain identifiers rather than feedback payloads and expire within two days.

## 查詢回饋分析 {/* #query-feedback-analytics */}

OLAP 回饋查詢對數字進行操作`value` fields. Use them for ratings, thumbs encoded as `1` and `-1`, numeric QA scores, or other numeric feedback types.

```typescript
const rating = await observability!.getFeedbackAggregate({
  feedbackType: 'rating',
  feedbackSource: 'user',
  aggregation: 'avg',
  comparePeriod: 'previous_day',
})

const byAgent = await observability!.getFeedbackBreakdown({
  feedbackType: 'rating',
  groupBy: ['entityName'],
  aggregation: 'avg',
  filters: { environment: 'production' },
})

const ratingsOverTime = await observability!.getFeedbackTimeSeries({
  feedbackType: 'rating',
  aggregation: 'avg',
  interval: '1h',
  groupBy: ['feedbackSource'],
})
```

請參閱[feedback reference](/reference/observability/feedback) for all fields, filters, return types, and percentile query parameters.

本地運行時公開列表路由`/api/observability/feedback` and analytics under its related paths. See the [HTTP routes table](/reference/observability/feedback#http-routes) and [list query parameters](/reference/observability/feedback#list-query-parameters). Mastra Platform provides a separate, unversioned hosted query API. See the [Feedback API](/docs/mastra-platform/api#feedback-api) for regional endpoints, authentication, and project scoping.

## 將回饋匯出至 Mastra 平台 {/* #export-feedback-to-mastra-platform */}

[`MastraPlatformExporter`](/reference/observability/tracing/exporters/mastra-platform-exporter)向 Mastra 平台發送回饋，該平台在需要時找到目標軌跡或跨度。不需要本地追蹤儲存。添加`MastraStorageExporter` only if you also want a local copy.

Studio 會向為其追蹤讀取提供服務的後端發送回饋。對於由 OSS 伺服器處理的 HTTP 創建，伺服器會在本機上保存回饋並通知配置的匯出器。由於導出器傳送是非同步的，因此成功的 HTTP 回應並不能保證記錄在遠端目標上已經可見。直接儲存寫入繞過導出器。

## 將回饋匯出到外部平台 {/* #export-feedback-to-external-platforms */}

回饋流經可觀察性事件匯流排，因此支援回饋的匯出器會自動轉發它。這[PostHog exporter](/reference/observability/tracing/exporters/posthog#feedback-export) sends feedback as native `$ai_feedback` events that appear on the linked trace in PostHog.
