# Worker 驗證

:::beta

在 API 穩定之前，可能會在沒有重大版本更新的情況下發生重大變更。

:::

Worker 與 API 在不同程序中執行時，會透過 HTTP 通訊。協調 Worker 呼叫 API 的步驟執行端點，在 API 伺服器上執行 Workflow 步驟。採推送模式的 PubSub Broker（例如使用推送模式的 Google Cloud Pub/Sub）也能直接將事件送至 API 的事件端點。這與由 Worker 自行向 Broker 拉取事件的模式不同。設定驗證 Provider 後，這兩個 HTTP 端點都需要驗證。

## 運作方式 {/* #how-it-works */}

Worker 沿用 Mastra 伺服器的驗證流程。協調 Worker 會在每次 HTTP 請求中附上憑證，由伺服器設定的 `authenticateToken` Provider 驗證。

|端點 |使用者 |目的|
| - | - | - |
| `POST /api/workflows/:workflowId/runs/:runId/steps/execute` | 協調 Worker，透過 `HttpRemoteStrategy` 呼叫 | 在 API 伺服器上執行 Workflow 步驟 |
| `POST /api/workflows/events` | Push-mode brokers (GCP Pub/Sub, SNS) | Deliver workflow events to the API |

兩條路線都有`requiresAuth: true`. When no auth provider is configured, they're publicly accessible.

:::warning

將工作程序部署為單獨的進程時，請務必在伺服器上設定身份驗證Provider。如果沒有，步驟執行和事件端點將對任何呼叫者開放。

:::

## 設定 Worker 驗證 {/* #setting-up-worker-auth */}

### 在伺服器上設定身份驗證Provider {/* #configure-an-auth-provider-on-the-server */}

可使用任何 Mastra 驗證 Provider。`SimpleAuth` 適合驗證 Worker 權杖：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { SimpleAuth } from '@mastra/core/server'

export const mastra = new Mastra({
  server: {
    auth: new SimpleAuth({
      tokens: {
        [process.env.WORKER_TOKEN!]: {
          id: 'worker',
          name: 'Orchestration Worker',
          role: 'worker',
        },
      },
    }),
  },
  // ... storage, pubsub, etc.
})
```

### 設定 Worker 權杖 {/* #set-the-worker-token */}

請在每個 Worker 容器中，將 `MASTRA_WORKER_AUTH_TOKEN` 設為伺服器的驗證 Provider 可辨識的權杖：

```yaml title="docker-compose.yml"
services:
  api:
    environment:
      WORKER_TOKEN: ${WORKER_TOKEN}
      # ... other env vars

  orchestration-worker:
    environment:
      MASTRA_WORKER_AUTH_TOKEN: ${WORKER_TOKEN}
      MASTRA_STEP_EXECUTION_URL: http://api:4111/api # Use HTTPS in production
      # ... other env vars
```

```bash title=".env"
WORKER_TOKEN=sk-worker-secret-token
```

範例使用 `http://` 進行本機開發。在正式環境中，請使用 HTTPS URL，並在服務網格或 Ingress 控制器終止 TLS。詳見[安全建議](#security-recommendations)。

協調 Worker 讀取 `MASTRA_WORKER_AUTH_TOKEN`，並在每次步驟執行請求的 `Authorization` 標頭中附上 `Bearer` 權杖。

## 身份驗證憑證類型 {/* #auth-credential-types */}

這`HttpRemoteStrategy` supports three credential formats. The default (`bearer`) covers most setups.

### Bearer 權杖 {/* #bearer-token */}

設定 `MASTRA_WORKER_AUTH_TOKEN` 後，策略會送出 `Authorization: Bearer <token>`：

```bash
MASTRA_WORKER_AUTH_TOKEN=sk-worker-secret-token
```

### API 金鑰標頭 {/* #api-key-header */}

改用 `x-worker-api-key` 傳送憑證，取代 `Authorization`：

```typescript
import { HttpRemoteStrategy } from '@mastra/core/worker'

const strategy = new HttpRemoteStrategy({
  serverUrl: 'http://api:4111/api', // Use HTTPS in production
  auth: { type: 'api-key', key: process.env.WORKER_API_KEY! },
})
```

伺服器的驗證 Provider 必須讀取 `x-worker-api-key` 標頭，才能驗證這項憑證。

### 自訂標頭 {/* #custom-header */}

使用任何標頭名稱和值：

```typescript
import { HttpRemoteStrategy } from '@mastra/core/worker'

const strategy = new HttpRemoteStrategy({
  serverUrl: 'http://api:4111/api', // Use HTTPS in production
  auth: {
    type: 'header',
    name: 'X-Internal-Service-Key',
    value: process.env.INTERNAL_KEY!,
  },
})
```

## 推送模式的 Broker 驗證 {/* #push-mode-broker-auth */}

使用推送模式的 PubSub（例如 Google Cloud Pub/Sub）時，Broker 會直接將事件 POST 至 `/api/workflows/events` 端點，並附上自己的憑證。例如，Google Cloud Pub/Sub 會傳送由 Google 簽署的 OIDC 權杖。

驗證 Provider 的 `authenticateToken` 回呼必須能辨識 Broker 送來的憑證。請查閱 Broker 的文件，確認它採用的驗證方式。

## 安全建議 {/* #security-recommendations */}

- **不同類型的 Worker 使用不同權杖。** 這樣可撤銷單一 Worker 的存取權限，不影響其他 Worker。
- **定期輪替權杖。** 更新 `WORKER_TOKEN` 環境變數，並重新啟動受影響的容器。
* **在生產中使用 TLS。**&#x57;orker 到 API 的通訊應透過 HTTPS 進行，以保護傳輸中的令牌。這適用於所有環境，包括 Kubernetes 叢集和 Docker 網路。使用服務網格（例如 Istio、Linkerd）或 TLS 終止入口來加密內部流量。
* **限製網路存取。**&#x6B65;驟執行和事件端點是內部的。如果可能，請使用網路策略或防火牆規則將它們遠離公共網路。
