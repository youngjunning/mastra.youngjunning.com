# 細緻權限控管 (FGA)

:::note

FGA 在正式環境中需要 Mastra 企業版 (EE) 授權；開發環境則無須授權。請參閱[哪些功能需要 EE 授權](/docs/license#what-requires-an-ee-license)。如需更多資訊，請[聯絡業務團隊](https://mastra.ai/contact)。

:::

細緻權限控管 (FGA) 為 Mastra 應用程式加入資源層級的權限檢查。RBAC 回答「這個角色能執行此操作嗎？」，FGA 則回答**「這位使用者能對這項特定資源執行此操作嗎？」**

## 何時使用 FGA {/* #when-to-use-fga */}

FGA 專為多租戶 B2B 產品而設計，其中權限與上下文相關：

- 使用者可能是團隊 A 的**管理員**，卻只是團隊 B 的**成員**
- 對對話執行緒的存取應限於使用者所屬的組織
- Workflow 執行應限制在特定團隊或專案內
- Tool 存取權取決於使用者與資源的關係

## 設定 {/* #configuration */}

在 Mastra 伺服器設定中，同時設定 FGA、身分驗證與 RBAC：

```typescript
import { Mastra } from '@mastra/core/mastra'
import { MastraFGAPermissions } from '@mastra/core/auth/ee'
import { MastraAuthWorkos, MastraFGAWorkos } from '@mastra/auth-workos'

const mastra = new Mastra({
  server: {
    auth: new MastraAuthWorkos({
      /* ... */
      fetchMemberships: true,
      mapUserToResourceId: user => user.teamId,
    }),
    fga: new MastraFGAWorkos({
      resourceMapping: {
        agent: { fgaResourceType: 'team', deriveId: ctx => ctx.user.teamId },
        workflow: { fgaResourceType: 'team', deriveId: ctx => ctx.user.teamId },
        thread: { fgaResourceType: 'workspace-thread', deriveId: ({ resourceId }) => resourceId },
      },
      permissionMapping: {
        [MastraFGAPermissions.AGENTS_EXECUTE]: 'manage-workflows',
        [MastraFGAPermissions.WORKFLOWS_EXECUTE]: 'manage-workflows',
        [MastraFGAPermissions.MEMORY_READ]: 'read',
        [MastraFGAPermissions.MEMORY_WRITE]: 'update',
      },
    }),
    storedResources: {
      scope: true,
    },
  },
})
```

使用 `MastraFGAWorkos` 時，請在 `MastraAuthWorkos` 設定 `fetchMemberships: true`。WorkOS FGA 檢查需要使用者的組織成員資格，才能解析授權所需的正確成員資格 ID。

對記憶體功能進行授權時，請以 `thread` 作為資源對應鍵。`MastraFGAWorkos` 仍接受舊別名 `memory`，但新設定應優先使用 `thread`。

設定 `server.fga` 後，Mastra 會對受保護的操作執行 FGA 檢查。若沒有已驗證身分的使用者，Mastra 會拒絕該操作。未設定 `server.fga` 時，系統會略過這些檢查，維持原有行為。

### 資源對應 {/* #resource-mapping */}

`resourceMapping` 指定如何從請求內容解析 FGA 資源類型與 ID。鍵是 Mastra 資源類型；值定義 FGA 資源類型與 ID 的推導方式：

```typescript oxfmt:false
resourceMapping: {
  // When checking "can user execute agent X?", resolve the FGA resource
  // as the user's team (type: 'team', id: user.teamId)
  agent: {
    fgaResourceType: 'team',
    deriveId: (ctx) => ctx.user.teamId,
  },
}
```

`deriveId()` 會收到：

- `user`：已完成身分驗證的使用者
- `resourceId`：所屬 Mastra 資源的 ID（若可取得，例如執行緒的 `resourceId`）
- `requestContext`：目前的請求內容，可用於進階租戶解析

若 `deriveId()` 回傳 `undefined`，便會改用原本的 Mastra 資源 ID。

檢查執行緒與記憶體權限時，Mastra 仍以原始 `threadId` 作為待檢查資源，同時把執行緒所屬的 `resourceId` 傳入 `deriveId()`。因此可將執行緒權限對應至 `userId-teamId-orgId` 等複合租戶 ID。

### 權限對應 {/* #permission-mapping */}

`permissionMapping` 將 Mastra 內部權限字串對應至 FGA Provider 的權限識別名稱：

```typescript oxfmt:false
import { MastraFGAPermissions } from '@mastra/core/auth/ee';

permissionMapping: {
  [MastraFGAPermissions.AGENTS_EXECUTE]: 'manage-workflows', // Mastra permission -> WorkOS permission slug
  [MastraFGAPermissions.MEMORY_READ]: 'read',
}
```

若某項權限沒有對應設定，則直接傳入原始字串。

請使用 `validatePermissions()` 在啟動時驗證 Mastra 可能產生的完整權限集合。如果 Provider 要求每項 Mastra 權限都有明確的 Provider 權限識別名稱，就應使用此方法。

### 已儲存資源的範圍限制 {/* #stored-resource-scoping */}

FGA 授權存取資源，但不會自動篩選共用儲存空間中的紀錄。在多租戶應用程式使用內建的已儲存資源 API 時，請啟用範圍限制。

```typescript
const mastra = new Mastra({
  server: {
    auth: new MastraAuthWorkos({
      /* ... */
      mapUserToResourceId: user => user.teamId,
    }),
    storedResources: {
      scope: true,
    },
  },
})
```

啟用 `scope: true` 後，Mastra 會從請求內容讀取 `MASTRA_RESOURCE_ID_KEY`。`mapUserToResourceId()` 在身分驗證後設定該值。已儲存資源的處理程式會將範圍保存在紀錄中繼資料，並依該範圍篩選列出、讀取、更新、發布與刪除操作。

若需使用自訂請求邏輯決定範圍，請改用物件設定：

```typescript oxfmt:false
storedResources: {
  scope: {
    metadataKey: 'teamId',
    resolve: ({ user }) => user.teamId,
    requireScope: true,
  },
},
```

當 `requireScope` 為 `true` 或未指定時，若無法解析範圍，受範圍限制的已儲存資源路由就會失敗。

### 路由政策涵蓋範圍 {/* #route-policy-coverage */}

Mastra 為內建資源路由提供路由層級的 FGA 中繼資料，涵蓋 Agent、Workflow、Tool、MCP Tool、記憶體執行緒、回應、對話及已儲存資源。已儲存資源路由包含 `/stored/agents`、`/stored/mcp-clients`、`/stored/prompt-blocks`、`/stored/scorers`、`/stored/skills` 和 `/stored/workspaces`。路由具有 `fga` 中繼資料、Mastra 能推導其內建中繼資料，或 Provider 透過 `resolveRouteFGA()` 提供中繼資料時，就會執行檢查。

若要拒絕無法解析 FGA 中繼資料的受保護路由，請在 FGA Provider 設定路由政策涵蓋範圍：

```typescript
const fga = new MastraFGAWorkos({
  resourceMapping: {
    project: { fgaResourceType: 'project' },
  },
  permissionMapping: {
    'projects:read': 'read',
  },
  requireForProtectedRoutes: true,
  auditProtectedRoutes: 'warn',
  validatePermissions: async permissions => {
    // Throw if a Mastra permission is missing from permissionMapping.
  },
})
```

設定 `auditProtectedRoutes: 'error'`，即可在受保護路由缺少內建 FGA 中繼資料時使啟動失敗。若啟用 `requireForProtectedRoutes`，Mastra 預設會將這項稽核記為警告。

自訂路由請優先使用路由層級的 `fga` 中繼資料，讓授權政策與路由定義相鄰：

```typescript
import { createRoute } from '@mastra/server/server-adapter'

export const getProjectRoute = createRoute({
  method: 'GET',
  path: '/projects/:projectId',
  responseType: 'json',
  requiresAuth: true,
  fga: {
    resourceType: 'project',
    resourceIdParam: 'projectId',
    permission: 'projects:read',
  },
  handler: async () => {
    return { project: null }
  },
})
```

只有在必須根據路由、參數或請求內容集中推導路由中繼資料時，才使用 `resolveRouteFGA()`。路由對應表比字串前綴檢查更容易擴充：

```typescript
import type { FGARouteConfig, FGARouteResolver } from '@mastra/core/auth/ee'

const routeFGA = {
  'GET /billing/:accountId': {
    resourceType: 'account',
    resourceIdParam: 'accountId',
    permission: 'billing:read',
  },
} satisfies Record<string, FGARouteConfig>

const resolveRouteFGA: FGARouteResolver = ({ route }) => routeFGA[`${route.method} ${route.path}`]

const fga = new MastraFGAWorkos({
  /* ... */
  resolveRouteFGA,
})
```

## 權限檢查時機 {/* #enforcement-points */}

設定 FGA Provider 後，Mastra 會在下列生命週期階段自動檢查權限：

| 生命週期階段 | 檢查的權限 | 資源類型 | 資源 ID |
| - | - | - | - |
| Agent 執行（`generate`、`stream`） | `agents:execute` | `agent` | `agentId` |
| 內建 Workflow HTTP 執行路由與 `Workflow.execute()` | `workflows:execute` | `workflow` | `workflowId` |
| 獨立 Tool 執行 | `tools:execute` | `tool` | `toolName` |
| Agent Tool 執行 | `tools:execute` | `tool` | `${agentId}:${toolName}` |
| MCP Tool 執行 | `tools:execute` | 預設為 `tool`，也可由伺服器層級的 `fga.resourceMapping` 覆寫 | 預設為 `JSON.stringify([serverName, toolName])`，也可使用伺服器層級推導出的 ID |
| 執行緒與記憶體存取 | `memory:read`、`memory:write`、`memory:delete` | `thread` | `threadId` |
| 已儲存資源路由 | 該路由操作對應的已儲存資源權限 | 已儲存資源類型 | 路由紀錄 ID；集合路由則使用已儲存資源範圍 |
| HTTP 資源路由 | 依路由設定 | 依路由設定 | 依路由設定 |

對於受 OAuth 保護的 MCP 伺服器，HTTP MCP 傳輸會以 `extra.authInfo` 傳遞驗證資料。若 `MCPServer` 註冊在啟用 FGA 的 Mastra 執行個體上，請設定 `mapAuthInfoToUser`，讓 Mastra 在檢查 `tools/list` 與 `tools/call` 前設定 `requestContext.get('user')`。若 MCP Tool 所需的資源或權限對應與 Agent、Workflow 內部的 Tool 檢查不同，請使用伺服器層級的 `fga` 選項。請參閱 [MCPServer 身分驗證內容](/reference/tools/mcp-server#map-auth-data-for-fga)。

在此版本中，核心 FGA 不會單獨檢查直接呼叫 SDK 的 `createRun().start()`、`resume()` 或 `restart()`。請從受保護路由發起這些呼叫，或在應用程式程式碼中加以保護。直接呼叫受保護的進入點時，請傳入含有已驗證使用者的 `requestContext`。

Agent、內部 Workflow、Tool 與記憶體的核心檢查也會將 `requestContext` 和操作中繼資料傳給 FGA Provider。路由檢查會傳遞 `requestContext`；執行緒檢查則會在可取得時傳遞所屬 `resourceId`。

## 自訂 FGA Provider {/* #custom-fga-provider */}

實作 `IFGAProvider` 即可使用任何 FGA 後端：

```typescript
import { FGADeniedError } from '@mastra/core/auth/ee'
import type { FGACheckParams, IFGAProvider, MastraFGAPermissionInput } from '@mastra/core/auth/ee'

class MyFGAProvider implements IFGAProvider {
  async check(user: any, params: FGACheckParams): Promise<boolean> {
    // Your authorization logic
    return true
  }

  async require(user: any, params: FGACheckParams): Promise<void> {
    const allowed = await this.check(user, params)
    if (!allowed) {
      throw new FGADeniedError(user, params.resource, params.permission)
    }
  }

  async filterAccessible<T extends { id: string }>(
    user: any,
    resources: T[],
    resourceType: string,
    permission: MastraFGAPermissionInput,
  ): Promise<T[]> {
    // Filter resources the user can access
    return resources
  }
}
```

:::note
所有方法、參數及 `ActorSignal` 類型，請參閱 [`IFGAProvider` 參考文件](/reference/auth/fga)。
:::

## 系統參與者 {/* #system-actors */}

自主或排程執行的 Agent 沒有終端使用者。請以 actor 訊號標示這些呼叫，讓 FGA 能與使用者請求區分：

- `true` 或 `{ actorKind: 'system' }` 代表匿名系統 actor。
- 物件形式亦可包含 `agentId`、`permissions` 與 `scope`，用於識別並限制執行操作的 Agent。

預設情況下，受信任 actor 通過租戶範圍檢查後，會略過針對使用者的 `require()` 檢查。若要對每個 Agent 實施最小權限，請在 Provider 實作可選的 `requireActor` 方法。此方法會接收 actor 與 `require` 相同的 `FGACheckParams`，並透過擲出 `FGADeniedError` 拒絕存取。未實作 `requireActor` 的 Provider 仍保有受信任 actor 的略過機制，因此可向下相容。

```typescript
import { FGADeniedError } from '@mastra/core/auth/ee'
import type { ActorSignal, FGACheckParams, IFGAProvider } from '@mastra/core/auth/ee'

class MyFGAProvider implements IFGAProvider {
  // ...check, require, filterAccessible...

  async requireActor(actor: ActorSignal, params: FGACheckParams): Promise<void> {
    const agentId = actor === true ? undefined : actor.agentId
    // Resolve the agent's real grants from a trusted source keyed by agentId.
    const granted = await this.grantsForAgent(agentId)
    const required = Array.isArray(params.permission) ? params.permission : [params.permission]
    if (!required.some(permission => granted.includes(permission))) {
      throw new FGADeniedError(null, params.resource, params.permission)
    }
  }
}
```

### 將 actor 傳至 Workflow 步驟 {/* #propagating-an-actor-into-workflow-steps */}

Workflow 執行時的 `actor` 會傳入每個步驟的執行內容，但不會自動傳給步驟所呼叫的 Agent 與 Tool。若步驟呼叫 Agent 時未提供 `actor`，便會回退至使用者成員資格解析；沒有使用者的系統執行會因此失敗。

在 actor 設定 `propagate: true` 後，框架會把它傳給執行期間宣告式 `.then(agent)` 與 `.then(tool)` 步驟所呼叫的 Agent、Tool：

```typescript
await run.start({
  inputData: { city: 'London' },
  actor: { actorKind: 'system', sourceWorkflow: 'nightly-report', propagate: true },
})
```

傳遞機制須自行啟用，且刻意限制了範圍：

- `true` 簡寫形式不會傳遞；請使用物件形式啟用。
- 自訂步驟的 `execute` 函式不在涵蓋範圍內。請從步驟內容讀取 `actor` 並明確傳入，避免代表使用者執行的步驟默默繼承系統信任。
- 建立步驟時傳入 `actor` 可覆寫該步驟的執行層級 actor；傳入 `actor: undefined` 則可在執行途中切回使用者授權。

```typescript
// Runs as the system actor even though it loads user-supplied data.
workflow.then(createStep(reportAgent))
// Explicitly runs as the user instead.
workflow.then(createStep(summaryAgent, { actor: undefined }))
```

### 信任要求 {/* #trust-requirements */}



- 將 `actor` 視為每次呼叫各自提供的訊號。持久化 Workflow 會在執行開始時傳遞它，但恢復執行時不會還原最初的 actor。每次以受信任身分恢復時，都須明確傳入，或透過 Agent 的 `defaultOptions` 解析新的 actor。若當下沒有 actor，則套用使用者授權；缺少使用者時會拒絕存取。
- Mastra 會從內建 Agent HTTP 路由處理的執行選項中移除 `actor`。請在排程工作或 Workflow 等伺服器端程式碼中設定，切勿接受用戶端輸入。
- 在伺服器端建立租戶範圍。內建 Agent HTTP 路由會忽略用戶端在請求內容中提供的 `organizationId`；受信任 actor 路徑則要求設定 `organizationId`。
- 持久化恢復會沿用既有的請求內容還原與合併行為，但不會因此信任後續 Workflow 階段中已持久化的 actor。
- 租戶範圍檢查只確認存在受信任的 `organizationId`，不會驗證 `actor.agentId` 是否隸屬該組織。若這層關係很重要，請在 `requireActor` 中使用權威的 Provider 資料驗證。
- 將 `actor.permissions` 視為未經驗證的宣告。若要實施最小權限，請依 `agentId` 從資訊清單或 FGA 後端等可信來源解析 Agent 權限，不要信任內嵌值。
- Provider 一旦實作 `requireActor`，該方法發生的錯誤會停止執行。Mastra 不會退回僅依組織授權。
