# 部署至 Mastra 平台

[`mastra deploy`](/reference/cli/mastra#mastra-deploy) 是將 Mastra 應用程式發布至 [Mastra 平台](/docs/mastra-platform/overview)的統一指令。

這個指令會在部署前建置並驗證專案。首次執行時還會建立平台專案與環境，接著部署、即時輸出建置日誌，並在部署開始接收流量後顯示公開 URL。

```bash
mastra deploy
```

:::note
本文說明統一部署流程。先前分開的 [`mastra server deploy`](/docs/mastra-platform/server) 與 [`mastra studio deploy`](/docs/mastra-platform/studio) 指令仍可使用，但建議使用 `mastra deploy`。
:::

## 開始之前 {/* #before-you-begin */}

你需要一個 [Mastra 應用程式](/docs)與一個 [Mastra 平台](https://projects.mastra.ai)帳號。若尚未完成驗證，CLI 會在首次使用時提示登入。

本機 `.env` 檔案並非必要。平台儲存的環境變數會在部署時直接使用，[託管資料庫](/docs/mastra-platform/database)等受管理資源也會注入自己的變數。只有需要疊加本機值時才傳入 `--env-file`。

## 首次部署 {/* #your-first-deploy */}

<Steps>
  <StepItem>
    在專案目錄中執行：

    ```bash
    mastra deploy
    ```

    首次執行時，CLI 會提示建立平台專案（以 `package.json` 中的名稱命名）與 `production` 環境。依提示確認，或傳入 `--yes`，直接接受預設值。
  </StepItem>

  <StepItem>
    CLI 每次部署前都會執行預先檢查。若儲存設定會退回本機檔案路徑（平台的暫時性檔案系統不會保留該檔案），通常會阻止部署：
    CLI 不會直接報錯結束，而是提供當場修正選項：
    ```text
    file:./mastra.db will be used at runtime because TURSO_DATABASE_URL is not set
    ```



    ```text
    Preflight needs TURSO_DATABASE_URL for the production environment. Create a managed turso database now and attach it? (Y/n)
    ```

    接受提示後，資源佈建只需幾秒鐘。資料庫連線變數會自動注入部署，不必複製到 `.env` 檔案。若拒絕提示，或使用非互動式 Shell（CI、`--yes`），CLI 會改為輸出應執行的確切指令。

    ```bash
    mastra env db create production --kind turso
    ```

    上例的環境代稱 `production` 與 CLI 原本要部署的環境一致。若專案有多個環境，在非互動式 Shell 中執行 `mastra env db create` 時，必須傳入環境參數。

    預先檢查也會找出指向本機的資料庫 URL。包含 `DATABASE_URL=postgres://localhost:5432/myapp` 的 `.env` 檔案可供開發使用，但部署後的伺服器無法連到你的電腦。CLI 因此會提出警告，並提供同樣的託管資源佈建選項。若組織同時提供 Neon 與 Postgres，CLI 會讓你在公開的無伺服器 Neon 與 VPC 隔離的 Postgres 之間選擇，而非詢問是否建立。若拒絕，部署會沿用原值；若接受，託管資料庫的連線變數在部署時優先，本機 `.env` 仍可用於開發。

    :::note
    若預先檢查回報寫死的本機路徑（`Build contains a host-local storage URL`），就無法提供當場修正。請先用環境變數保護該路徑，讓檔案僅供本機開發使用：

    ```ts title="src/mastra/index.ts"
    import { LibSQLStore } from '@mastra/libsql'

    new LibSQLStore({
      id: 'mastra-storage',
      // Uses the hosted database when deployed, a local file during development
      url: process.env.TURSO_DATABASE_URL ?? 'file:./mastra.db',
      authToken: process.env.TURSO_AUTH_TOKEN,
    })
    ```

    :::

    若建置過程靜態偵測到 `backgroundTasks.enabled: true`，CLI 會決定讓背景工作在專用 Worker 服務上執行，或在 API 伺服器容器的程序內執行：

    - 專用 Worker 服務需要 Redis 協調。若部署環境中沒有可用的 `REDIS_URL`，背景工作會在程序內執行。
    - Redis 可用時，若環境已有專用 Worker 服務、傳入 `--yes`，或以無互動方式部署，CLI 會使用專用 Worker 服務；否則會詢問是否佈建。
    - 傳入 `--workers dedicated` 或 `--workers in-process` 可略過選擇。缺少 `REDIS_URL` 時，`--workers dedicated` 會失敗。
    - 專用 Worker 服務正逐步推出。尚未開放此功能的組織即使有 Redis 且傳入 `--workers dedicated`，CLI 仍會略過 Worker 資訊清單，背景工作改在程序內執行。

    選擇專用 Worker 服務後，部署成品會包含 Worker 資訊清單；Mastra Cloud 會依同一成品佈建或更新 Worker 服務。

    後續部署中移除 `backgroundTasks` 或設定 `enabled: false`，會移除資訊清單並停止現有 Worker 服務。無法靜態判定的值不會顯示在資訊清單中，但 Worker 程序仍會讀取封裝程式碼中的完整設定。
  </StepItem>

  <StepItem>
    再次執行 `mastra deploy`。預先檢查通過後，建置成品會上傳，CLI 會持續輸出建置日誌，直到部署開始
    接收流量。整個建置與部署通常需要 30 秒到幾分鐘。只有新版本開始接收流量時，
    才會顯示成功訊息。
  </StepItem>

  <StepItem>
    使用 CLI 輸出的 URL 驗證部署。在結尾加上 `/api/agents`，確認它回傳 Agent 的 JSON 清單。

    :::warning
    公開端點前，請先設定[身分驗證](/docs/auth/overview)。
    :::
  </StepItem>
</Steps>

每次部署取代正在執行的伺服器程序時，新版本上線可能中斷仍在串流輸出的 Agent 回合，因為 Mastra 平台目前不支援設定或仰賴可靠的終止前額外等待時間。對可能超過預設排空時窗的回合，不要依賴調高的 `server.drainTimeout`。若回合必須跨部署持續，請使用搭配持久化儲存與快取的[持久 Agent](/docs/harness/durable-agents)，或在用戶端處理串流中斷。可用策略請參閱[正常關閉與滾動部署](/docs/deployment/mastra-server#graceful-shutdown-and-rolling-deploys)。

首次部署會寫入 `.mastra-project.json`，將目前目錄連結至平台專案。請將它提交，讓後續部署、CI 執行及 [`mastra env`](/docs/mastra-platform/environments) 指令無須額外參數即可指向同一專案。

## 部署到另一個環境 {/* #deploy-to-another-environment */}

`mastra deploy` 預設部署至 `production` 環境。傳入 `--env` 可選擇其他環境；若該環境尚不存在，CLI 會提供建立選項：

```bash
mastra deploy --env staging
```

每個環境都有獨立 URL 與環境變數，也可以有自己的[託管資料庫](/docs/mastra-platform/database)。

完整說明請參閱[環境](/docs/mastra-platform/environments)。

## 選擇地區 {/* #choose-a-region */}

互動式建立環境時，可在區域提示中選取美國或歐洲。若要略過提示，請傳入 `--region`，值為 `us` 或 `eu`：

```bash
mastra deploy --env production --region eu
```

環境建立後，區域便固定不變。關聯的資料庫會自動設置在該環境區域附近；可觀測性資料則會路由至符合環境資料駐留區域的擷取區域。支援的區域、資料庫位置與可觀測性資料共置詳情請參閱[區域](/docs/mastra-platform/regions)。

## 部署前檢查 {/* #preflight-checks */}

預先檢查會在上傳部署成品前驗證建置輸出，而且只指出你自己程式碼中的問題：

- **本機儲存路徑**：屬於強制阻擋。以檔案為基礎的儲存（例如 `file:./mastra.db`）在每次部署後都會遺失。若路徑由環境變數保護，且變數已在本機設定或儲存於平台（包括託管資料庫提供的值），預先檢查就會通過：

  ```ts title="src/mastra/storage.ts"
  import { LibSQLStore } from '@mastra/libsql'

  export const storage = new LibSQLStore({
    id: 'mastra-storage',
    // Uses the hosted database when deployed, a local file during development
    url: process.env.TURSO_DATABASE_URL ?? 'file:./mastra.db',
    authToken: process.env.TURSO_AUTH_TOKEN,
  })
  ```

- **缺少環境變數**：若程式碼讀取了某個變數，但沒有任何來源提供，便會發出警告。只由函式庫程式碼引用的變數不計入。

預先檢查阻擋部署時，建議修正根本原因，通常是連結託管資料庫或在平台儲存變數。`--skip-preflight` 可作為緊急選項，但會略過用於防止故障部署的檢查。

只執行檢查、不進行部署：

```bash
mastra lint --preflight
```

`mastra lint` 只讀取本機環境檔案，看不到平台儲存或託管資料庫注入的變數。因此，即使 lint 回報錯誤，部署預先檢查仍可能通過。

## 環境變數 {/* #environment-variables */}

部署時從以下三個來源解析環境變數：

- **受管理變數**：由託管資料庫等平台資源注入（例如 `TURSO_DATABASE_URL`）。這些變數由平台定義，不能編輯。
- **已儲存變數**：透過控制台儲存在專案或環境中。每次部署直接使用，不需要本機檔案。
- **本機環境檔案**：部署會在上述值之上疊加明確指定的 `--env-file`，或目前環境中的 `.env`、`.env.local` 檔案。

```bash
mastra deploy --env staging --env-file .env.staging
```

若要在不重新部署的情況下修改執行中服務的變數，請在控制台更新變數，並執行 [`mastra env restart`](/reference/cli/mastra#mastra-env-restart)。

## 私有 npm 套件 {/* #private-npm-packages */}

依賴私人套件登錄庫的專案，會在部署期間依標準 `NPM_TOKEN` 約定安裝套件。

<Steps>
  <StepItem>
    透過控制台將唯讀登錄庫權杖以 `NPM_TOKEN` 名稱儲存於專案或環境。
  </StepItem>

  <StepItem>
    提交不含權杖的 `.npmrc`，將你的命名空間指向登錄庫，並從環境讀取權杖：

    ```ini title=".npmrc"
    @your-org:registry=https://npm.pkg.github.com
    //npm.pkg.github.com/:_authToken=${NPM_TOKEN}
    ```

    請原樣保留 `${NPM_TOKEN}` 參照。套件管理器會在安裝時解析它，因此權杖本身不會寫入儲存庫。
  </StepItem>

  <StepItem>
    照一般方式部署：

    ```bash
    mastra deploy
    ```
  </StepItem>
</Steps>

在 monorepo 中，專案目錄內的 `.npmrc` 優先於儲存庫根目錄的同名檔案。

安裝相依套件期間可以使用 `NPM_TOKEN`。Mastra 會在串流輸出的原始碼建置日誌中遮蔽其值。產生的 Dockerfile 會透過建置參數接收它；執行階段映像檔不含該權杖。`NPM_TOKEN` 也會以一般環境變數注入執行中的服務，因此應將它視為應用程式可讀取的機密。

沒有私人登錄庫 `.npmrc` 的專案不必變更。若 `.npmrc` 參照 `${NPM_TOKEN}`，必須設定該變數，否則相依套件安裝會失敗。

## 決定目標專案 {/* #project-resolution */}

每次部署會依下列順序決定目標專案：

1. 環境變數 `MASTRA_PROJECT_ID`
1. `--project <name|slug|id>` 旗標
1. 目前目錄中的 `.mastra-project.json` 檔案

在 CI 中，設定 `MASTRA_PROJECT_ID` 與 `MASTRA_API_TOKEN`，並傳入 `--yes`：

```bash
mastra deploy --env production --yes
```

## 從 Server 與 Studio 部署遷移 {/* #migrating-from-server-and-studio-deploys */}

`mastra server deploy` 與 `mastra studio deploy` 已棄用，將於下一個主要版本移除。移除後，兩個指令都會失敗，使用舊版部署流程的專案在遷移前無法部署新的建置成品。

現有服務會繼續執行。受影響的只有發布新部署的能力。

### 這會影響誰 {/* #who-this-affects */}

符合下列任一條件，就表示你仍在使用舊版部署流程：

- 上次使用 `mastra server deploy` 或 `mastra studio deploy` 部署，且部署日誌顯示 **Deprecated** 橫幅。
- 專案最近一次成功部署使用的 `@mastra/core` 版本低於 `1.44`。
- 組織尚未開放環境部署。

部署日誌是判斷依據：舊版部署流程每次部署都會顯示棄用橫幅。

### 遷移 {/* #migrate */}

<Steps>
  <StepItem>
    升級專案中的 `@mastra/core`。環境部署流程會對建置成品呼叫 `setStudio`，因此需要 `@mastra/core` `>= 1.44`。
    若跨越多個次版本升級，可將以下提示詞交給程式碼 Agent（例如 Claude Code、Cursor），找出專案實際使用的 API 中可能存在的不相容變更：
    ```bash npm2yarn
    npm install @mastra/core@latest
    ```



    ```text
    Check whether this project is ready for the Mastra Platform environment pipeline.

    1. Find the installed version of `@mastra/core` (check package.json and the
       lockfile for the version that actually resolved, rather than only the range).
    2. If it's >= 1.44.0, tell me I'm good. No further action is needed.
    3. If it's < 1.44.0:
       a. Fetch the `@mastra/core` changelog from
          https://github.com/mastra-ai/mastra/blob/main/packages/core/CHANGELOG.md
          and read every entry between my installed version and the latest release.
       b. Scan my project (agents, workflows, tools, memory, storage, deployers,
          telemetry, anywhere `@mastra/core`, `@mastra/*`, or `mastra` is imported)
          and list every Mastra API surface I actually use.
       c. For each used API, cross-reference the changelog and produce a table of:
          API I use → breaking change → severity (breaks build / breaks runtime /
          behavior change / none).
       d. For each "breaks build" or "breaks runtime" row, implement the fix in my
          codebase. For "behavior change" rows, leave a comment at the call site
          explaining what changed so I can decide.
       e. Bump `@mastra/core` (and any `@mastra/*` peers) to the latest matching
          versions, then run typecheck and tests. Report anything still failing.
    4. Search my scripts, package.json, Dockerfiles, and CI config for
       `mastra server deploy` and `mastra studio deploy`. Replace each
       occurrence with `mastra deploy`. This is the unified command required
       by the environment pipeline.

    don't restructure my CI, provision new infra, or change my environment
    variable values. Change only the Mastra usage in my code and the deploy command
    itself.
    ```
  </StepItem>

  <StepItem>
    將指令碼與 CI 中原先分開的指令換成統一指令：

    ```diff
    - mastra server deploy
    - mastra studio deploy
    + mastra deploy
    ```

    `mastra deploy` 只建置一次，並為目標環境同時部署伺服器與 Studio UI 外殼。近期版本的 `mastra` CLI 均支援此指令；否則請執行 `npm install -g mastra@latest` 升級。
  </StepItem>

  <StepItem>
    部署一次。專案會自動採用環境部署流程，並在首次部署時建立 `production` 環境。完整說明請參閱
    [環境](/docs/mastra-platform/environments)。
  </StepItem>

  <StepItem>
    在控制台的 **Environments → \<env> → Variables** 下，將專案層級的環境變數移至需要它們的環境。請參閱[環境變數](/docs/mastra-platform/environments#environment-variables)。
  </StepItem>
</Steps>

### 常問問題 {/* #faq */}

**部署因 `MASTRA_CORE_TOO_OLD` 失敗。** 環境部署流程要求 `@mastra/core` `>= 1.44`。請升級 `@mastra/core` 並重新部署。

**我的組織尚未開放此功能。** 請聯絡支援團隊。下一個主要版本發布前會自動開放。

**可以回復先前版本嗎？** 可以。環境會保留部署歷史，你可以在控制台重新部署任何先前成功的建置成品。
