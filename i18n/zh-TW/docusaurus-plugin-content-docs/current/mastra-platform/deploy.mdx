# 部署到Mastra平台

[`mastra deploy`](/reference/cli/mastra#mastra-deploy)是將 Mastra 應用程式發佈到的單一命令[馬斯特拉平台](/docs/mastra-platform/overview).

一個命令可以建置您的專案並在部署之前進行驗證，此外還可以在首次運行時建立平台專案和環境、部署、串流媒體建置日誌，並在部署提供流量後列印您的公共 URL。

```bash
mastra deploy
```

:::注意
此頁面涵蓋統一部署流程。早期的 split 指令，[`mastra server deploy`](/docs/mastra-platform/server) and [`mastra studio deploy`](/docs/mastra-platform/studio), still work but `mastra deploy`是推薦路徑。
:::

## 開始之前 {/* #before-you-begin */}

你需要一個[Mastra application](/docs) and a [Mastra platform](https://projects.mastra.ai) account. If you're not authenticated, the CLI prompts you to log in on first use.

本地人`.env` file is optional. Environment variables stored on the platform are used as-is at deploy time, and managed resources like [hosted databases](/docs/mastra-platform/database) inject their own variables. Pass `--env-file` only when you want to layer local values on top.

## 您的第一次部署 {/* #your-first-deploy */}

<Steps>
  <StepItem>
    從您的專案目錄中，運行：

    ```bash
    mastra deploy
    ```

    第一次執行時，CLI 會提示您建立平台專案（以您的名稱命名）`package.json`) and the `production` environment. Accept the prompts, or pass `--yes` to accept defaults without confirmation.
  </StepItem>

  <StepItem>
    CLI 在每次部署之前都會執行預檢檢查。回退到本機檔案路徑（無法在平台的暫存檔案系統上生存）的儲存通常會阻止部署：

    ```text
    file:./mastra.db will be used at runtime because TURSO_DATABASE_URL is not set
    ```



    ```text
    Preflight needs TURSO_DATABASE_URL for the production environment. Create a managed turso database now and attach it? (Y/n)
    ```

    接受提示，配置需要幾秒鐘的時間。資料庫的連線變數會自動注入到您的部署中，因此您無需將它們複製到`.env` file. If you decline the prompt or use a non-interactive shell (CI, `--yes`), the CLI falls back to printing the exact command for you to run.

    ```bash
    mastra env db create production --kind turso
    ```

    環境蛞蝓 (`production` above) matches the environment the CLI would have deployed to. The `mastra env db create` command requires an environment argument in non-interactive shells when the project has more than one environment.

    Preflight 也會擷取指向本機的資料庫 URL。一個`.env` file with `DATABASE_URL=postgres://localhost:5432/myapp` works during development, but the deployed server can't reach your laptop. The CLI therefore warns and offers the same managed provisioning. When both Neon and Postgres are available for your organization, the CLI prompts you to pick between them (public serverless Neon, or VPC-isolated Postgres) instead of the usual yes/no. If you decline, the deploy continues with your value as-is; if you accept, the managed database's connection variables take precedence at deploy time while your local `.env` keeps working for development.

    :::注意
    如果預檢報告硬編碼的本地路徑（`Build contains a host-local storage URL`), it can't offer the inline fix. Guard the path with an environment variable first so the file is only used during local development:

    ```ts title="src/mastra/index.ts"
    import { LibSQLStore } from '@mastra/libsql'

    new LibSQLStore({
      id: 'mastra-storage',
      // Uses the hosted database when deployed, a local file during development
      url: process.env.TURSO_DATABASE_URL ?? 'file:./mastra.db',
      authToken: process.env.TURSO_AUTH_TOKEN,
    })
    ```

    :::

    如果建構靜態發現`backgroundTasks.enabled: true`, the CLI decides whether to run background tasks on a dedicated worker service or in-process inside the API server container:

    * 专门的worker服务需要Redis来协调。沒有可用的`REDIS_URL` in the deploy env, background tasks run in-process.
    * 在 Redis 可用的情況下，當環境已有專用工作服務時，CLI 將使用專用工作服務，當您透過`--yes`, or when the deploy runs headless. Otherwise it asks whether to provision one.
    * 經過`--workers dedicated` or `--workers in-process` to skip the decision. `--workers dedicated` fails if `REDIS_URL` is missing.
    * 專用工作人員服務正在逐步推出，因此對於無法存取的組織，CLI 會忽略工作人員清單和進程內運行的後台任務，即使使用 Redis 和`--workers dedicated`.



    去除`backgroundTasks` or setting `enabled: false` in a later deploy removes the manifest and spins down the existing worker service. Values that can't be determined statically are omitted from the manifest display, but the worker process still reads the complete configuration from your bundled code.
  </StepItem>

  <StepItem>
    跑步`mastra deploy` again. Preflight passes, the build uploads, and the CLI streams build logs until the deploy is
    live. Expect the full build and deploy to take between 30 seconds and a few minutes. The success message prints only
    when the new version is serving traffic.
  </StepItem>

  <StepItem>
    透過 CLI 列印的 URL 驗證您的部署。附加`/api/agents` to confirm it returns a JSON list of your agents.

    :::警告
    設定[authentication](/docs/auth/overview) before exposing your endpoints publicly.
    :::
  </StepItem>
</Steps>

在每次部署期間替換正在運行的伺服器程序可能會中斷新版本上線時仍在串流的Agent程式輪次，因為 Mastra 平台目前不允許您配置或依賴終止前保證的額外時間。不要依賴提高`server.drainTimeout` for turns that may outlast the default drain window. Use [durable agents](/docs/harness/durable-agents) with persistent storage and cache when turns must survive a deploy, or handle an interrupted stream in the client. The available strategies are documented in [graceful shutdown and rolling deploys](/docs/deployment/mastra-server#graceful-shutdown-and-rolling-deploys).

第一次部署寫了一個`.mastra-project.json` file linking your directory to the platform project. Commit it so later deploys, CI runs, and [`mastra env`](/docs/mastra-platform/environments) commands target the same project without extra flags.

## 部署到另一個環境 {/* #deploy-to-another-environment */}

`mastra deploy`目標是`production` environment by default. Pass `--env` to target a different one. If the environment doesn't exist yet, the CLI offers to create it:

```bash
mastra deploy --env staging
```

每個環境都有一個單獨的 URL 和環境變數。也可以有自己的[hosted database](/docs/mastra-platform/database).

看[Environments](/docs/mastra-platform/environments) for the full model.

## 選擇地區 {/* #choose-a-region */}

當部署以互動方式建立環境時，從區域提示中選擇美國或歐洲。若要跳過提示，請透過`--region` with the `us` or `eu` shorthand:

```bash
mastra deploy --env production --region eu
```

创建环境时区域是固定的。附加到环境的数据库会自动放置在该环境的区域附近，并且可观测性数据将路由到与环境驻留区域匹配的摄取区域。看[Regions](/docs/mastra-platform/regions) for the full list of supported regions and database placement, along with observability co-location.

## 飛行前檢查 {/* #preflight-checks */}

預檢會在部署上傳之前驗證建置的輸出，並且僅標記您自己的程式碼中的問題：

* **本地儲存路徑**: 硬塊。文件支援的儲存（例如`file:./mastra.db`) is lost on every deploy. Preflight passes when the path is guarded by an environment variable that's set locally or stored on the platform, including values provided by a managed database:

  ```ts title="src/mastra/storage.ts"
  import { LibSQLStore } from '@mastra/libsql'

  export const storage = new LibSQLStore({
    id: 'mastra-storage',
    // Uses the hosted database when deployed, a local file during development
    url: process.env.TURSO_DATABASE_URL ?? 'file:./mastra.db',
    authToken: process.env.TURSO_AUTH_TOKEN,
  })
  ```

* **缺少環境變數**：針對您的程式碼讀取但沒有來源提供的變數的警告。僅由庫代碼引用的變數被排除。

對預檢區塊的建議回應是修復原因，通常透過附加託管資料庫或將變數儲存在平台上。`--skip-preflight` exists as an escape hatch but skips the checks that prevent broken deploys.

執行檢查而不部署：

```bash
mastra lint --preflight
```

`mastra lint`只能看到你的本機環境文件。存储在平台上或由托管数据库注入的变量对其不可见，因此部署可以通过预检，而 lint 仍会报告错误。

## 環境變數 {/* #environment-variables */}

從三個來源部署解析環境變數：

* **託管變數**：由託管資料庫等平台資源注入（例如`TURSO_DATABASE_URL`). The platform defines these, and you can't edit them.
* **儲存變數**：透過儀表板保存在專案或環境中。在每次部署時按原樣使用，無需本地文件。
* **本地環境文件**：部署層明確`--env-file` or the ambient `.env` and `.env.local` files on top.

```bash
mastra deploy --env staging --env-file .env.staging
```

若要變更正在執行的服務上的變數而不重新部署，請在儀表板中更新它們並執行[`mastra env restart`](/reference/cli/mastra#mastra-env-restart).

## 私有 npm 套件 {/* #private-npm-packages */}

依賴私有註冊表中的套件的項目在部署期間使用標準安裝它們`NPM_TOKEN` contract.

<Steps>
  <StepItem>
    將唯讀註冊表令牌儲存為`NPM_TOKEN` on the project or environment through the dashboard.
  </StepItem>

  <StepItem>
    承諾無代幣`.npmrc` that points your scope at the registry and reads the token from the environment:

    ```ini title=".npmrc"
    @your-org:registry=https://npm.pkg.github.com
    //npm.pkg.github.com/:_authToken=${NPM_TOKEN}
    ```

    保留`${NPM_TOKEN}` reference literal. The package manager resolves it at install time, so the token itself is never written to your repository.
  </StepItem>

  <StepItem>
    像往常一樣部署：

    ```bash
    mastra deploy
    ```
  </StepItem>
</Steps>

在單一儲存庫中，`.npmrc` in your project directory takes precedence over one at the repository root.

`NPM_TOKEN`在依賴項安裝期間可用。 Mastra 從它串流的 Mastra 來源建置日誌中編輯其值。產生的 Dockerfile 將其作為建置參數接收。運行時映像不受令牌影響。`NPM_TOKEN` is also injected into the running service as a regular environment variable, so treat it as a secret your application can read.

`.npmrc` need no changes. When your `.npmrc` references `${NPM_TOKEN}`, set the variable or the dependency install fails.

## 項目決議 {/* #project-resolution */}

每個部署都按以下順序解析其目標項目：

1. 這`MASTRA_PROJECT_ID` environment variable
2. 這`--project <name|slug|id>` flag
3. 這`.mastra-project.json` file in the current directory

在 CI 中，設定`MASTRA_PROJECT_ID` and `MASTRA_API_TOKEN` and pass `--yes`:

```bash
mastra deploy --env production --yes
```

## 從伺服器和工作室部署遷移 {/* #migrating-from-server-and-studio-deploys */}

`mastra server deploy`和`mastra studio deploy` are deprecated. They'll be removed in the next major version. Once removed, both commands will fail and legacy-pipeline projects can't deploy a new build until they migrate.

現有部署的服務繼續運作。這只會影響您發布新部署的能力。

### 這會影響誰 {/* #who-this-affects */}

若符合以下任一條件，您就處於舊版管道中：

* 您上次部署的結果是`mastra server deploy` or `mastra studio deploy` and the deploy log printed a **Deprecated** banner.
* 您的專案最近成功的部署已使用`@mastra/core` older than `1.44`.
*

部署日誌是事實的來源：遺留管道在每次部署時都會列印一個棄用橫幅。

### 遷移 {/* #migrate */}

<Steps>
  <StepItem>
    升級`@mastra/core` in your project. The environment pipeline calls `setStudio` on the built artifact, which requires `@mastra/core` `>= 1.44`.

    ```bash npm2yarn
    npm install @mastra/core@latest
    ```



    ```text
    Check whether this project is ready for the Mastra Platform environment pipeline.

    1. Find the installed version of `@mastra/core` (check package.json and the
       lockfile for the version that actually resolved, rather than only the range).
    2. If it's >= 1.44.0, tell me I'm good. No further action is needed.
    3. If it's < 1.44.0:
       a. Fetch the `@mastra/core` changelog from
          https://github.com/mastra-ai/mastra/blob/main/packages/core/CHANGELOG.md
          and read every entry between my installed version and the latest release.
       b. Scan my project (agents, workflows, tools, memory, storage, deployers,
          telemetry, anywhere `@mastra/core`, `@mastra/*`, or `mastra` is imported)
          and list every Mastra API surface I actually use.
       c. For each used API, cross-reference the changelog and produce a table of:
          API I use → breaking change → severity (breaks build / breaks runtime /
          behavior change / none).
       d. For each "breaks build" or "breaks runtime" row, implement the fix in my
          codebase. For "behavior change" rows, leave a comment at the call site
          explaining what changed so I can decide.
       e. Bump `@mastra/core` (and any `@mastra/*` peers) to the latest matching
          versions, then run typecheck and tests. Report anything still failing.
    4. Search my scripts, package.json, Dockerfiles, and CI config for
       `mastra server deploy` and `mastra studio deploy`. Replace each
       occurrence with `mastra deploy`. This is the unified command required
       by the environment pipeline.

    don't restructure my CI, provision new infra, or change my environment
    variable values. Change only the Mastra usage in my code and the deploy command
    itself.
    ```
  </StepItem>

  <StepItem>
    將腳本和 CI 中的 split 指令替換為統一指令：

    ```diff
    - mastra server deploy
    - mastra studio deploy
    + mastra deploy
    ```

    `mastra deploy`建置一次並為目標環境部署伺服器和 Studio UI shell。最近的每一個都支援它`mastra` CLI; otherwise, upgrade with `npm install -g mastra@latest`.
  </StepItem>

  <StepItem>
    部署一次。您的專案會自動採用到環境管道中，並且`production` environment is created on
    first deploy. See [Environments](/docs/mastra-platform/environments) for the full model.
  </StepItem>

  <StepItem>
    將任何專案級環境變數移至需要它們的環境（在儀表板下）**Environments → \<env> → Variables**. See [Environment variables](/docs/mastra-platform/environments#environment-variables).
  </StepItem>
</Steps>

### 常問問題 {/* #faq */}

**我的部署失敗`MASTRA_CORE_TOO_OLD`.**&#x74B0;境管道要求`@mastra/core` `>= 1.44`. Upgrade `@mastra/core` and redeploy.

**我的組織尚未選擇加入。**&#x806F;繫支援人員。在下一個主要版本發布之前，選擇加入將是自動的。

**我可以回滾嗎？**&#x662F;的。環境保留部署歷史記錄，您可以從儀表板重新部署任何先前成功的工件。
