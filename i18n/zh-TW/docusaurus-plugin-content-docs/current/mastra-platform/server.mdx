# 在 Mastra 平台部署伺服器

Mastra 平台的 Server 是正式環境的部署目標，會以 API 伺服器執行 Mastra 應用程式。若要由平台負責建置、部署、託管及管理 Mastra 伺服器，可以使用此部署目標。

平台會提供穩定的 API 端點，支援環境變數管理與自訂網域，並自動保留部署記錄。

:::note

部署伺服器時，平台會自動佈建託管儲存空間。若你使用 [LibSQLStore](/integrations/databases/libsql) 搭配檔案 URL 覆寫儲存設定，請改用遠端託管的資料庫，因為 Mastra 平台使用暫時性的檔案系統。

:::

## 快速入門 {/* #quickstart */}

<Steps>
  <StepItem>
    依照[入門指南](/docs)建立第一個 Mastra 專案。
  </StepItem>

  <StepItem>
    在全域安裝 `mastra` CLI：

    ```bash npm2yarn
    npm install -g mastra
    ```
  </StepItem>

  <StepItem>
    部署專案：

    ```bash
    mastra deploy
    ```

    若尚未通過驗證，CLI 會提示你登入。登入憑證會儲存在本機，後續 CLI 指令也會使用這些憑證。

    這個指令會執行 `mastra build` 並上傳建置產物，接著建置及部署 Docker 映像檔。首次部署時，CLI 會建立 `.mastra-project.json`，將本機專案與平台連結。請將此檔案提交到版本控制，讓後續部署與 CI/CD 都使用同一個專案。

    :::note
    CLI 會從單一環境變數檔案上傳變數。如果存在 `.env.<environment>`，例如預設 `production` 環境的 `.env.production`，就會使用該檔案。否則，若只有一個 `.env` 或 `.env.*` 檔案，就使用該檔案。若有多個檔案且沒有符合環境的檔案，CLI 會詢問要使用哪一個。若在非互動模式下執行（`--yes` 或 CI），請傳入 `--env-file <file>`。也能用 `--env-file` 覆寫預設選擇。每次部署都會將檔案中的變數合併到環境已儲存的變數中。檔案中的值優先，但空值不會清除已儲存的值。CLI 會列出即將覆寫的變數名稱並要求確認，使用 `--yes` 或在 CI 中執行時會略過確認。若某個變數只要在控制台管理，請將它從環境變數檔案移除。若沒有環境變數檔案，就不會上傳變數，環境會保留已儲存的值。
    部署前請檢查並清理選用的檔案，以免上傳僅供開發使用的密鑰或個人憑證。
    :::

    完整的命令列旗標清單請見 [CLI 參考](/reference/cli/mastra#mastra-deploy)。
  </StepItem>

  <StepItem>
    開啟 CLI 顯示的 URL 以驗證部署。在 URL 後加上 `/api/agents`，確認傳回的是你的 Agent 的 JSON 清單。

    :::warning
    公開端點之前，請先設定[身分驗證](/docs/auth/overview)。
    :::
  </StepItem>
</Steps>

## 部署生命週期 {/* #deploy-lifecycle */}

每個專案一次只執行一項建置。部署會依序進入 **queued → uploading → starting → deploying → running**，也可能進入 **failed**、**cancelled**、**crashed** 或 **stopped**。由 GitHub 觸發的部署會先從原始碼建置，因此會在 **queued** 與 **uploading** 之間經過 **building**。若多項部署同時排隊，只會繼續最新的一項，其餘會取消。建置超過 15 分鐘會自動判定失敗。首次部署會佈建基礎設施，並從本機的 `.env` 初始化環境變數。各次部署都會沿用相同的伺服器 URL。

## 閒置時的行為 {/* #idle-behavior */}

為節省資源，Mastra 平台可讓閒置一段時間的服務進入休眠。平台以對外網路流量判定是否閒置，只有大約 10 分鐘沒有送出封包才算閒置。持續出現的對外流量會重設計時器，使服務保持運作。

伺服器持續不休眠，通常是因為有背景工作或長時間連線定期送出流量。請檢查下列常見原因。

### 持續開啟的資料庫連線 {/* #persistent-database-connections */}

資料庫用戶端只要未關閉，即使伺服器閒置也會維持連線。許多驅動程式也會在背景定期 ping 資料庫以檢查健康狀態，這也算對外流量。例如，未關閉的 MongoDB 用戶端仍會保持監控通訊端開啟，並大約每 10 秒送出一次心跳。

只設定連線池清除閒置連線並不足夠，因為驅動程式的監控連線仍會維持開啟並繼續 ping。若要讓伺服器休眠，請在閒置一段時間後關閉用戶端，再於收到下一個請求時重新連線。

:::note
關閉用戶端後，伺服器喚醒後的第一個請求會因重新連線而稍有延遲。若工作負載無法容忍這段延遲，請維持連線，且不要依賴閒置休眠。
:::

### 排程工作與計時器 {/* #scheduled-tasks-and-timers */}

若 `setInterval`、cron 工作或輪詢迴圈會發出網路請求，伺服器就會保持運作。若需要排程工作，請將它部署為獨立服務，或使用外部排程器發出請求喚醒伺服器。

### 外部 ping 與保活檢查 {/* #external-pings-and-keep-alive-checks */}

定期存取伺服器的可用性監控、健康檢查或保活 ping 會重設閒置計時器。若希望伺服器能休眠，請移除這些檢查，或將檢查間隔延長到超過閒置門檻。

### 可觀測性匯出器 {/* #observability-exporters */}

若匯出器持續將 Trace、日誌或指標傳送到遠端端點，就會產生對外流量。請確認匯出器會批次傳送，且在伺服器閒置時停止傳送，避免固定間隔送出資料。

### 長時間開啟的串流 {/* #long-lived-streams */}

伺服器傳送事件（SSE）串流、WebSocket 或其他長時間連線，在關閉前都會維持通訊。若串流回應在背景持續訂閱，連線就會保持作用中。請確認用戶端斷線時會關閉串流，且伺服器在其他方面已無活動時，沒有串流仍然開啟。

### 聊天整合 {/* #chat-integrations */}

部分聊天整合會維持長時間連線並定期傳送心跳，使伺服器保持運作。例如，採用 Socket Mode 的 Slack 應用程式會開啟 WebSocket，約每 30 秒 ping 一次。Discord 機器人則會維持閘道 WebSocket 連線開啟，並定期傳送心跳。開啟的通訊端和定期心跳都會阻止伺服器進入閒置狀態。

若希望伺服器能休眠，且整合支援 HTTP Webhook，可改用 Webhook 接收事件。例如，Slack 應用程式可以使用具備請求 URL 的 Events API，取代 Socket Mode。若應用程式需要持續連線，請使用下文介紹的 **Persistent Server add-on** 讓服務保持運作。

### 檢查作用中的連線 {/* #inspect-active-connections */}

若要找出伺服器為何不休眠，請在閒置時檢查程序中仍在作用的控制代碼。請求都完成後仍存在的控制代碼就是排查對象。開啟的通訊端表示有待關閉的長時間連線，作用中的計時器則指向 `setInterval` 或反覆排程自身的 `setTimeout`。

將以下輔助程式加入應用程式，等流量停止後查看日誌。伺服器閒置時仍列出的項目，就是使它保持運作的原因：

```typescript title="src/mastra/diagnose-idle.ts"
export function logActiveHandles() {
  // process._getActiveHandles is undocumented but useful for diagnosis.
  const handles = (process as any)._getActiveHandles() as Array<any>

  const summary = handles.map(handle => {
    const type = handle?.constructor?.name ?? typeof handle
    if (type === 'Socket') {
      return `Socket -> ${handle.remoteAddress}:${handle.remotePort}`
    }
    return type
  })

  console.log(`[idle] ${handles.length} active handles:`, summary)
}

// Log every 30 seconds so you can see what persists while the server is idle.
setInterval(logActiveHandles, 30_000).unref()
```

對診斷用計時器呼叫 `unref()`，避免輔助程式本身使伺服器無法休眠。

### 讓服務持續運作 {/* #keep-a-service-running */}

有些應用程式需要上述連線或工作，例如以持續開啟的資料庫連線降低首個請求的延遲，或需要背景排程器、長時間開啟的串流。若應用程式有這類需求，請用 **Persistent Server add-on** 讓服務持續運作，避免強制休眠。

啟用 **Persistent Server add-on** 後，即使沒有流量，服務也會持續運作。持續連線、排程工作和開啟的串流都不會因閒置休眠而中斷。

## CI/CD {/* #cicd */}

可使用 GitHub Actions、GitLab CI 或任一 CI 服務自動部署。完成首次互動式部署後，CI/CD 需要 API 權杖、組織及專案 ID，以及已提交至存放庫的 `.mastra-project.json` 檔案。

:::tip
如果程式碼放在 GitHub，[GitHub 整合](/docs/mastra-platform/github)可在推送時自動部署，無須撰寫工作流程檔案。若需使用 GitLab、其他 CI 服務，或在部署前執行自訂建置步驟，請採用下方的 CLI CI/CD 流程。
:::

### 建立 API 權杖 {/* #create-an-api-token */}

<Steps>
  <StepItem>
    在本機執行下列指令：

    ```bash
    mastra auth tokens create ci-deploy
    ```

    CLI 只會顯示一次權杖。請立即複製，之後無法再次取得。
  </StepItem>

  <StepItem>
    將權杖新增為 CI 服務的密碼。在 GitHub Actions 中，前往 **Settings → Secrets and variables → Actions**，建立名為 `MASTRA_API_TOKEN` 的密碼。
  </StepItem>

  <StepItem>
    確認已將 `.mastra-project.json` 提交至存放庫。
  </StepItem>

  <StepItem>
    將 `MASTRA_ORG_ID` 與 `MASTRA_PROJECT_ID` 加入 CI 服務，使用 `.mastra-project.json` 中的 `organizationId` 和 `projectId` 作為對應值。設定 `MASTRA_API_TOKEN` 後，`mastra deploy` 會以非互動模式執行，缺少任一變數都會失敗。
  </StepItem>
</Steps>

### `--yes` 旗標 {/* #the---yes-flag */}

傳入 `--yes`（或 `-y`）即可略過所有確認提示。若未傳入，CLI 會等待互動式輸入，造成 CI 作業停滯。

```bash
mastra deploy --yes
```

### GitHub Actions {/* #github-actions */}

每次推送到 `main` 時，下列工作流程都會執行部署：

```yaml title=".github/workflows/deploy-mastra.yml"
name: Deploy to Mastra platform

on:
  push:
    branches: [main]
    paths: ['src/mastra/**']

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'
      - name: Install dependencies
        run: npm install
      - name: Deploy to Mastra platform
        run: npx mastra deploy --yes
        env:
          MASTRA_API_TOKEN: ${{ secrets.MASTRA_API_TOKEN }}
          MASTRA_ORG_ID: ${{ secrets.MASTRA_ORG_ID }}
          MASTRA_PROJECT_ID: ${{ secrets.MASTRA_PROJECT_ID }}
```

若 Mastra 專案位於子目錄（例如 monorepo），請調整 `paths` 篩選條件和 `working-directory`。

### GitLab CI {/* #gitlab-ci */}

推送到 `main` 時，下列管線會執行部署：

```yaml title=".gitlab-ci.yml"
deploy:
  image: node:22
  stage: deploy
  only:
    - main
  before_script:
    - npm install
  script:
    - npx mastra deploy --yes
```

在 **Settings → CI/CD → Variables** 中，新增 `MASTRA_API_TOKEN`、`MASTRA_ORG_ID` 和 `MASTRA_PROJECT_ID` 做為 CI/CD 變數。

### 其他 CI 服務 {/* #other-ci-providers */}

只要能執行 Node.js 和 Shell 指令，CI 系統就能部署 Mastra：

1. 安裝相依套件。
1. 將 `MASTRA_API_TOKEN`、`MASTRA_ORG_ID` 和 `MASTRA_PROJECT_ID` 設為環境變數。
1. 執行 `mastra deploy --yes`。

### 驗證部署 {/* #verify-the-deploy */}

工作流程完成後，請向健康檢查端點發送請求來驗證部署：

```bash
curl -f https://<your-project>.server.mastra.cloud/health
```

也可以檢查 Agent 端點，它會以 JSON 清單傳回你的 Agent：

```bash
curl -f https://<your-project>.server.mastra.cloud/api/agents
```

下列範例在 GitHub Actions 工作流程中加入驗證步驟：

```yaml
- name: Verify deployment
  run: |
    sleep 30
    curl -f https://<your-project>.server.mastra.cloud/health
```

### 以環境變數覆寫專案設定 {/* #override-project-config-with-environment-variables */}

在互動式部署中，CLI 預設會從 `.mastra-project.json` 讀取 `organizationId` 和 `projectId`。若已設定 `MASTRA_API_TOKEN`，下列兩個變數均為必填。若要覆寫這些值，例如從同一個存放庫部署到另一個專案，請設定以下環境變數：

| 變數 | 說明 |
| - | - |
| `MASTRA_ORG_ID` | 覆寫 `.mastra-project.json` 中的組織 ID。 |
| `MASTRA_PROJECT_ID` | 覆寫 `.mastra-project.json` 中的專案 ID。 |
