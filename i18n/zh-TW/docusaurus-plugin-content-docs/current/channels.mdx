# 頻道

**於以下版本新增：** `@mastra/core@1.22.0`

頻道讓 Agent 能與 Slack、Microsoft Teams、Discord、Telegram、WhatsApp、GitHub 和 Linear 等訊息與協作平台互通。使用者在平台上傳送訊息或留言時，Agent 會依照一般處理流程接收並處理，再以串流方式將回覆送回原對話。Mastra 的頻道層採用 [Chat SDK](https://chat-sdk.dev/)。

請先參閱所用平台的頁面：

<IntegrationGrid section="Channels" />

[其他轉接器](#other-adapters)列出更多平台。除了此處列出的平台，Mastra 頻道也支援相容的 [Chat SDK 轉接器](https://chat-sdk.dev/adapters)；各轉接器在 Mastra 中的設定方式相同。

## 何時使用頻道 {/* #when-to-use-channels */}

當 Agent 需要執行以下工作時，適合使用頻道：

- 在使用者平常交流或工作的地方與他們互動。
- 在 Slack、Microsoft Teams、Discord、Telegram 和 WhatsApp 等聊天平台回覆訊息。
- 讓多人在共用頻道或討論串中與同一個 Agent 互動。
- 整合 GitHub issue、拉取要求討論串及 Linear 留言等協作流程。

## 使用 Mastra Connect 加速頻道設定 {/* #configure-channels-faster-with-mastra-connect */}

若不想逐一為頻道設定機器人或應用程式，也不想自行維護憑證，可使用 [Mastra Connect](/docs/mastra-platform/connect#add-channels)。它會代為管理憑證，讓頻道設定與維護更簡單。

## 設定 Agent {/* #configure-an-agent */}

頻道使用 Chat SDK 轉接器，Mastra 端的設定方式一致：建立頻道轉接器，然後加入 Agent。

```typescript title="src/mastra/agents/your-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createSlackAdapter } from '@chat-adapter/slack'

export const yourAgent = new Agent({
  id: 'your-agent',
  name: 'Your Agent',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
  channels: {
    adapters: {
      slack: createSlackAdapter(),
    },
  },
})
```

:::note

頻道轉接器需要各平台專屬的環境變數，以提供憑證並驗證請求，例如機器人權杖、簽署密鑰、應用程式 ID 及 webhook 驗證權杖。確切的變數名稱請參閱所用平台的指南或 [Chat SDK 轉接器目錄](https://chat-sdk.dev/adapters)。

:::

建議為頻道設定[儲存空間](/docs/storage)。儲存空間能在重新啟動後保留頻道與記憶狀態，包括討論串訂閱及工具核准：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { LibSQLStore } from '@mastra/libsql'
import { yourAgent } from './agents/your-agent'

export const mastra = new Mastra({
  agents: { yourAgent },
  storage: new LibSQLStore({
    id: 'mastra-storage',
    url: process.env.DATABASE_URL,
  }),
})
```

## Webhook 路由 {/* #webhook-routes */}

平台透過 webhook 將頻道活動傳給 Mastra。Webhook 是一個 HTTP 端點，平台在收到新訊息、有人提及 Agent，或使用者在互動式工具核准卡片上選擇「Approve」時會呼叫它。Webhook 將訊息交給 Agent 處理，Agent 再於同一頻道回覆。

Mastra 會為每個已設定的轉接器註冊 webhook 路由，並代為處理請求：

```text
/api/agents/<AGENT_ID>/channels/<PLATFORM>/webhook
```

例如，ID 為 `your-agent` 的 Agent 使用 Slack 轉接器時，路由如下：

```text
/api/agents/your-agent/channels/slack/webhook
```

將平台的 webhook、事件或互動網址指向此路徑。詳細設定請參閱平台指南或 [Chat SDK 文件](https://chat-sdk.dev/adapters)。Webhook 會在 Agent 完成回覆前先確認請求；驗證或處理常式失敗時的行為，請參閱[錯誤處理與傳遞](#error-handling-and-delivery)。

在本機開發時，平台 webhook 需要公開網址才能連到本機伺服器。可使用 [cloudflared](https://github.com/cloudflare/cloudflared) 或 [ngrok](https://ngrok.com/) 建立通道，對外公開預設位於 `localhost:4111` 的伺服器：

```bash npm2yarn
npx cloudflared tunnel --url http://localhost:4111
```

將產生的公開網址用作 webhook 路徑的基本網址，例如 `https://abc123.trycloudflare.com/api/agents/your-agent/channels/slack/webhook`。

:::note

通道網址僅供本機開發。部署 Mastra 伺服器後，請將平台的 webhook、事件或互動網址更新為正式環境網址。

:::

## 討論串脈絡 {/* #thread-context */}

使用者在頻道討論串的對話中途提及 Agent 時，Agent 可能不知道先前的對話內容。首次提及時，Mastra 會從平台擷取較早的訊息，在處理該次提及前存入 Agent 的記憶討論串。

1. 首次在討論串中提及時，Agent 會擷取第一則訊息，以及提及之前最近的訊息。`maxMessages`（預設 `10`）決定擷取範圍：第一則訊息加上最多 `maxMessages - 1` 則近期訊息。若中間還有其他訊息，會儲存 `[… N earlier Slack messages omitted]` 標記取代它們；平台名稱會依頻道調整。
1. 每則擷取的訊息會連同作者、平台訊息 ID 和附件，分別以使用者訊息存入記憶，並標示 `source: 'thread-history'` 屬性。之後，這次提及會當成一般訊息處理。
1. Agent 回覆後會訂閱該討論串，並透過 Mastra 記憶保留完整歷史。
1. 同一討論串之後的訊息不會再次向平台擷取歷史。

設定 `threadContext: { maxMessages: 0 }` 可停用此行為。這只適用於非私訊的討論串。

沒有記憶功能的 Agent 無法儲存這些訊息，因此會改在提及訊息中以脈絡文字接收相同的歷史。寫入記憶失敗時，也會採取此替代方式。

記憶的 `lastMessages` 選項限制送入提示詞的訊息數量。預設值 `10` 在 `maxMessages` 為 `10` 時，會排除第一則訊息和省略標記，因此應將 `lastMessages` 設為至少 `maxMessages + 1`。

Mastra 也會新增一則簡短的系統訊息，告知 Agent 請求來自哪個頻道與平台，以及訊息是私訊還是公開頻道訊息。設定 `threadContext: { addSystemMessage: false }` 可略過。

## 工具核准 {/* #tool-approval */}

設定 `requireApproval: true` 的 Tool 會顯示含 Approve 與 Deny 按鈕的互動式卡片：

```typescript title="src/mastra/tools/delete-file.ts"
import { promises as fs } from 'node:fs'
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

export const deleteFile = createTool({
  id: 'delete-file',
  description: 'Delete a file from the system',
  inputSchema: z.object({
    path: z.string().describe('Path to the file to delete'),
  }),
  requireApproval: true,
  execute: async ({ path }) => {
    await fs.unlink(path)
    return { deleted: path }
  },
})
```

Agent 呼叫這個 Tool 時，使用者會看到包含工具名稱、參數及 Approve、Deny 動作的卡片。工具只有在核准後才會執行。

若要以自訂訊息取代卡片，例如將按鈕在地化，可從 `toolDisplay` 函式回傳 `{ kind: 'post', message: card }`。自訂函式會取代所有工具事件的顯示方式，不只影響核准事件。只有按鈕保留 Mastra 預期的 ID，預設動作處理常式才會恢復執行。請參閱[自訂核准卡片](/reference/agents/channels#custom-approval-cards)。

預設只有發起工具呼叫的使用者可以核准或拒絕。若共用頻道中的其他成員也應能操作，請在該轉接器上設定 `toolApprovers: 'anyone'`：

```typescript title="src/mastra/agents/your-agent.ts" oxfmt:false
channels: {
  adapters: {
    slack: {
      adapter: createSlackAdapter(),
      toolApprovers: 'anyone',
    },
  },
},
```

這只會略過請求者檢查：動作仍必須對應待處理的工具核准及已建立對應關係的討論串。若執行沒有記錄請求者（例如排程執行），預設模式無法嚴格保證僅請求者能操作；此時其他頻道成員也可能回應。若重新啟動後，已儲存的訊息指向多個可能的請求者，僅限請求者模式則會拒絕他們的點擊。

在轉接器上設定 `toolDisplay: 'text'`，可將工具呼叫顯示為純文字，而非互動式卡片。在 `'hidden'` 模式下，若同一討論串稍後收到使用者訊息，`autoResumeSuspendedTools` 可恢復帶有資料的 `suspend()` 流程；這需要記憶功能。隱藏模式只會隱藏核准按鈕，不會把訊息視為同意。需要核准的 Tool 仍會暫停，直到透過 UI 或 API 動作明確核准或拒絕。

### 自訂動作處理 {/* #custom-action-handling */}

使用 `handlers.onAction` 處理自行發佈的卡片中的按鈕點擊及選項變更。處理常式會收到 Chat SDK 動作事件、預設處理常式，以及其他頻道處理常式共用的 `ctx`。委派前寫入 `ctx.requestContext` 的值會傳遞給恢復後的工具呼叫。預設處理常式只處理內建的 Approve 和 Deny 按鈕，忽略其他動作 ID；因此，對未自行處理的事件應呼叫它，以維持工具核准功能：

```typescript title="src/mastra/agents/your-agent.ts" oxfmt:false
channels: {
  adapters: {
    slack: createSlackAdapter(),
  },
  handlers: {
    onAction: async (event, defaultHandler, ctx) => {
      if (event.actionId === 'retry') {
        await event.thread?.post('Retrying...')
        return
      }
      await defaultHandler()
    },
  },
},
```

設定 `onAction: false` 會完全停用動作處理，包括內建工具核准按鈕。若要在頻道啟動後註冊更多 Chat SDK 處理常式，請使用 `agent.getChannels()?.sdk`。

## 回覆格式 {/* #reply-formatting */}

Agent 預設以 Markdown 發佈回覆。Slack 等原生支援 Markdown 的平台會直接顯示粗體、連結和表格；其他平台則轉換成自己的格式。Agent 只要使用標準 Markdown，各平台就能正確顯示，與 Studio 中的顯示結果一致。

在轉接器上設定 `textFormat: 'plain'`，可將回覆原樣以純文字發佈：

```typescript title="src/mastra/agents/your-agent.ts" oxfmt:false
channels: {
  adapters: {
    slack: {
      adapter: createSlackAdapter(),
      textFormat: 'plain',
    },
  },
},
```

若已指示 Agent 輸出 Slack mrkdwn 等平台專用格式，而不是標準 Markdown，可使用此選項。若先前為了避免 Markdown 原樣顯示而加入這類提示詞指令，應將其移除。預設行為如今會原生顯示標準 Markdown。`textFormat` 只影響最終回覆文字，不影響工具卡片、錯誤訊息及原生串流文字。

### 只透過 Tool 回覆 {/* #reply-only-through-a-tool */}

設定 `textDisplay: 'hidden'` 可停止發佈 Agent 的回覆文字。之後，Agent 自身的訊息只能透過提供給它的 Tool（例如向討論串發文的工具）送進討論串。這能避免「Running the tests now」等過程說明出現在對話中，也讓 Agent 自行決定何時發文：

```typescript title="src/mastra/agents/your-agent.ts" oxfmt:false
channels: {
  adapters: {
    slack: {
      adapter: createSlackAdapter(),
      textDisplay: 'hidden',
    },
  },
},
```

工具顯示、核准提示、錯誤訊息及輸入狀態不受影響。回覆文字仍會進入 Agent 的串流及記憶。

Mastra 加入 Agent 提示詞的頻道指示也會遵循此設定：隱藏文字時，Agent 會得知只有透過 Tool 發佈的內容才能進入對話，也可以選擇不發佈任何訊息。

## 非訊息觸發的執行 {/* #runs-that-dont-start-from-a-message */}

從頻道開始的討論串也可能由其他來源啟動執行，例如排程、Studio 提示詞或喚醒 Agent 的 Signal。這類執行會收到與訊息觸發的執行相同的頻道指示。Agent 知道自己在頻道中的身分，也知道文字回覆是否會發佈到頻道。兩種執行使用相同的系統提示詞，因此可以沿用快取。

透過頻道傳入的訊息帶有 `platform` 屬性（例如 `platform="slack"`），讓 Agent 能與其他來源的提示詞區分。

這些執行的回覆與訊息觸發的回覆走相同的轉接器路徑。Mastra 會記住討論串中最後發言的人，因此需要指定收件者的轉接器（例如 Slack 的原生串流功能）也能以相同方式運作。

## 辨識多位使用者 {/* #multi-user-awareness */}

在群組對話中，Mastra 會在每則訊息前加上傳送者姓名及平台 ID，協助 Agent 分辨發言者：

```text
[Alice (@U123ABC)]: Can you help me with this?
[Bob (@U456DEF)]: I have a question too.
```

## 每則訊息的 Signal 中繼資料 {/* #per-message-signal-metadata */}

在自訂 Channel 處理常式中使用 `signalMetadata`，可為單一傳入訊息附加結構化脈絡。無論該訊息啟動閒置中的執行，或加入進行中的執行，中繼資料都會隨訊息傳遞。

以下範例會在呼叫預設處理常式前附加已註冊的檔案 ID：

```typescript title="src/mastra/agents/your-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createSlackAdapter } from '@chat-adapter/slack'

export const yourAgent = new Agent({
  id: 'your-agent',
  name: 'Your Agent',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
  channels: {
    adapters: {
      slack: createSlackAdapter(),
    },
    handlers: {
      onDirectMessage: async (thread, message, defaultHandler, ctx) => {
        ctx.signalMetadata.attachmentIds = ['file-1']
        await defaultHandler(thread, message)
      },
    },
  },
})
```

只加入可序列化為 JSON 的非敏感值。Signal 中繼資料可能儲存在記憶中，或透過共用的發布訂閱傳輸送出；不會加入模型提示詞。

對於單次執行範圍內的設定，例如啟動執行的訊息所需的憑證，請使用 `requestContext`。對於必須隨單則訊息保留的脈絡，包括送達進行中執行的訊息，請使用 `signalMetadata`。

## 錯誤處理與傳遞 {/* #error-handling-and-delivery */}

頻道 webhook 會在 Agent 完成前向平台確認請求，因此 `200` 表示「已收到」，不代表「已回覆」。確認前，轉接器會同步拒絕無效請求：驗證失敗回傳 `401`、無法解析的本文回傳 `400`、暫時性狀態故障回傳 `503`；平台會依自身政策重試非 `2xx` 回應。回傳 `200` 後，平台不再重試，錯誤由 Mastra 處理。預設處理常式會捕捉 Agent 執行失敗，並向討論串發送錯誤訊息（可透過 `formatError` 自訂，預設為 `❌ Error: {message}`）。若自訂處理常式在處理單則訊息時擲出錯誤，Chat SDK 只會記錄日誌，不會發文或重試（多位傳送者的批次請見[批次訊息](#batched-messages)）。請自行在自訂處理常式中捕捉錯誤：

```typescript title="src/mastra/agents/your-agent.ts" oxfmt:false
channels: {
  adapters: {
    slack: createSlackAdapter(),
  },
  handlers: {
    onDirectMessage: async (thread, message, defaultHandler, ctx) => {
      try {
        ctx.signalMetadata.ticketId = await lookupTicket(message)
      } catch (error) {
        ctx.mastra?.getLogger().error('Ticket lookup failed', { error })
        await thread.post('Something went wrong looking up your ticket. Try again in a moment.')
        return
      }
      await defaultHandler(thread, message)
    },
  },
},
```

平台重試可能使同一事件傳遞多次。轉接器透過頻道狀態去除重複事件；[儲存空間](/docs/storage)可在重新啟動後保留該狀態。由於此機制只能盡力防護，自訂處理常式的副作用應具備冪等性，以免重複傳遞再次建立工單等。

### 批次訊息 {/* #batched-messages */}

當 `chatOptions.concurrency` 策略（`burst`、`debounce` 或 `queue`）把多則訊息合併為一次派送時，Mastra 會按傳送者拆成多個回合：同一傳送者連續的訊息組成一個回合，依時間由舊到新處理。處理常式每回合執行一次，各自擁有 `ctx.requestContext`、`ctx.signalMetadata` 與 `ctx.skipped`（該回合先前的訊息），使授權與脈絡分別適用於每位傳送者。請在處理常式中等待 `defaultHandler`，否則不同傳送者的回合可能重疊。某回合擲出錯誤時會記錄日誌，其餘回合仍會執行，最後再擲出第一個錯誤。若批次因某則訊息提及機器人而送至 `onMention`，其他傳送者未提及機器人的訊息也會進入 `onMention`，其 `message.isMention` 為 `false`。

## 日誌記錄 {/* #logging */}

Chat SDK 日誌預設使用 Mastra 執行個體上的[日誌記錄器](/docs/observability/logging)，因此會遵循其格式、層級及 `redact` 設定。每筆記錄的 `component` 欄位為 `chat-sdk`。使用 `PinoLogger` 時，Mastra 自身的頻道日誌將 `component` 設為 `CHANNEL`，可據此區分兩者。設定 `chatOptions.logger` 可覆寫預設值，將日誌送往其他位置。

轉接器有自己的日誌記錄器，預設輸出至主控台。應用程式會在 Mastra 執行個體建立前先建立轉接器，因此 Mastra 無法替你設定該記錄器。建立轉接器時，請傳入 [`toChatLogger()`](/reference/agents/channels#tochatlogger)：

```typescript title="src/mastra/agents/support-agent.ts"
import { Agent } from '@mastra/core/agent'
import { toChatLogger } from '@mastra/core/channels'
import { createDiscordAdapter } from '@chat-adapter/discord'
import { logger } from '../logger'

export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'You are a helpful support assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
  channels: {
    adapters: {
      discord: createDiscordAdapter({
        logger: toChatLogger(logger, { component: 'discord', minLevel: 'warn' }),
      }),
    },
  },
})
```

此處的 `logger` 與傳給 `new Mastra({ logger })` 的記錄器相同。請從獨立檔案（例如 `src/mastra/logger.ts`）匯出，讓 Agent 檔案與 `src/mastra/index.ts` 都能匯入。`createRedisState()` 等狀態轉接器也預設輸出至主控台，並接受相同的 `logger` 選項。

Discord 轉接器的 Gateway 路徑會以 `info` 層級記錄每則訊息的前 100 個字元；`minLevel: 'warn'` 可避免這些內容進入日誌。Chat SDK 本身會以 `debug` 層級記錄訊息文字。若 Mastra 的日誌記錄器使用 `debug`，請為 `chatOptions.logger` 設定更高的 `minLevel`，避免記錄訊息文字。

:::warning

日誌記錄器的 `redact` 設定不適用於匯出至[可觀測性](/docs/observability/logging)的日誌，而 `warn` 和 `error` 層級的記錄預設會匯出。`onSlashCommand` 處理常式擲出錯誤時，Chat SDK 的 `error` 記錄會包含指令文字；請在該處理常式中捕捉錯誤，避免文字進入日誌及匯出資料。若將可觀測性的 `logging.level` 設為 `info` 或更低，請使用 `minLevel` 防止其他訊息文字被匯出。

:::

## 多模態內容 {/* #multimodal-content */}

Gemini 等模型可原生處理圖片、影片和音訊。搭配 `inlineMedia` 與 `inlineLinks`，使用者就能跨平台向 Agent 分享多媒體內容：

```typescript title="src/mastra/agents/vision-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createDiscordAdapter } from '@chat-adapter/discord'

export const visionAgent = new Agent({
  id: 'vision-agent',
  name: 'Vision Agent',
  instructions: 'You can see images, watch videos, and listen to audio.',
  model: '__GATEWAY_GOOGLE_MODEL_FLASH__',
  channels: {
    adapters: {
      discord: createDiscordAdapter(),
    },
    inlineMedia: ['image/*', 'video/*', 'audio/*'],
    inlineLinks: [
      { match: 'youtube.com', mimeType: 'video/*' },
      { match: 'youtu.be', mimeType: 'video/*' },
      'imgur.com',
    ],
  },
})
```

採用此設定後：

- 使用者上傳螢幕截圖，Agent 描述畫面內容。
- 使用者上傳 `.mp4` 片段，Agent 摘述影片。
- 使用者貼上 YouTube 連結，Agent 觀看並討論影片。
- 使用者貼上 imgur 連結，Agent 直接查看圖片。

預設只有圖片會以行內媒體形式傳送（`inlineMedia: ['image/*']`）。不支援的類型會以文字摘要描述，讓 Agent 知道檔案存在，同時避免不接受該類型的模型出錯。所有 `inlineMedia` 模式請見[頻道參考文件](/reference/agents/channels#inline-media)；網域比對、HEAD 偵測及指定 MIME 類型請見 [inlineLinks 參考文件](/reference/agents/channels#inline-links)。

## 無伺服器部署 {/* #serverless-deployment */}

在 Vercel 等無伺服器平台上，每個請求都由獨立且短暫存在的執行個體處理。要讓頻道在此環境穩定運作，必須在 Agent 回覆期間保持函式執行，並透過共用的發布訂閱機制協調不同執行個體。

### 使用 `waitUntil` 保持函式執行 {/* #keep-the-function-alive-with-waituntil */}

頻道 webhook 會立刻回傳 `200`，Agent 接著在背景執行並發佈回覆。多數無伺服器平台會在回應送出後立即凍結函式，使 Agent 尚未回覆就停止執行。傳入 `waitUntil` 函式，讓平台維持執行個體運作，直到這次執行完成。

在 Vercel 上，請將 `@vercel/functions` 提供的 `waitUntil` 傳入設定：

```typescript title="src/mastra/agents/your-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createSlackAdapter } from '@chat-adapter/slack'
import { waitUntil } from '@vercel/functions'

export const yourAgent = new Agent({
  id: 'your-agent',
  name: 'Your Agent',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
  channels: {
    adapters: {
      slack: createSlackAdapter(),
    },
    waitUntil,
  },
})
```

Vercel 和 AWS Lambda 會在回應送出後凍結函式，因此需要 `waitUntil`。Cloudflare Workers 和 Netlify Functions 可從請求脈絡自動偵測，因此不需要手動提供。若執行環境的請求脈絡中有 `waitUntil`，卻無法自動偵測，請使用 `resolveWaitUntil`。詳情請見[頻道參考文件](/reference/agents/channels#parameters)。

### 以共用發布訂閱機制協調執行個體 {/* #coordinate-instances-with-a-shared-pubsub */}

頻道透過 Agent 的 [Signal 處理流程](/docs/signals/overview)路由訊息。每次執行都會取得所屬討論串的租約，確保同一時間只有一個執行負責該對話。

預設的記憶體內發布訂閱機制無法跨執行個體通訊，因此在無伺服器環境中，後續訊息可能被送到與目前執行 Agent 不同的執行個體。

若沒有共用發布訂閱機制，另一個執行個體無法聯絡進行中的執行，便會自行啟動新執行；原執行不受影響，但同一討論串會被處理兩次。

請在 `Mastra` 執行個體上設定以 Redis Streams 為後端的共用發布訂閱機制，讓租約與 Signal 能跨執行個體協調：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'
import { yourAgent } from './agents/your-agent'

export const mastra = new Mastra({
  agents: { yourAgent },
  pubsub: new RedisStreamsPubSub({
    url: process.env.REDIS_URL,
    keyPrefix: 'mastra:my-app',
  }),
})
```

Vercel 的受管 Redis 整合與 Upstash Redis 都適用。何時需要分散式發布訂閱機制，請參閱 [PubSub 指南](/docs/server/pubsub)及 [`RedisStreamsPubSub` 參考文件](/reference/pubsub/redis-streams)。

### 查閱轉接器文件 {/* #check-the-adapter-docs */}

在將新轉接器接入 Mastra 前，請查閱其文件並確認：

- 是否支援附件、卡片及豐富訊息。
- 所需的憑證環境變數。
- 必要的平台權限或 scope。
- 一般訊息是否需要長時間執行的監聽器或輪詢。
- 平台是否需要分別為設定、事件或互動提供路由。
- webhook 的驗證方式。
