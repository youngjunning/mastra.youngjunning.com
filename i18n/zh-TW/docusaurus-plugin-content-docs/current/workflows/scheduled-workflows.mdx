# Workflow 排程

在 Workflow 宣告 `schedule` 欄位，Mastra 就會依指定的 cron 運算式觸發它。也可以用 `workflow.start()` 直接呼叫同一個 Workflow。排程觸發和手動執行採用同一套執行流程。

## 快速上手 {/* #quickstart */}

下列 Workflow 每天紐約時間上午 9 點執行。和一般 Workflow 一樣，把它註冊到 `Mastra` 即可，排程器會自動辨識。

```typescript title="src/mastra/workflows/daily-report.ts"
import { createWorkflow, createStep } from '@mastra/core/workflows'
import { z } from 'zod'

const sendReport = createStep({
  id: 'send-report',
  inputSchema: z.object({ userId: z.string() }),
  outputSchema: z.object({ ok: z.boolean() }),
  execute: async ({ inputData }) => {
    // ...send the report for inputData.userId
    return { ok: true }
  },
})

export const dailyReport = createWorkflow({
  id: 'daily-report',
  inputSchema: z.object({ userId: z.string() }),
  outputSchema: z.object({ ok: z.boolean() }),
  schedule: {
    cron: '0 9 * * *',
    timezone: 'America/New_York',
    inputData: { userId: 'system' },
  },
})
  .then(sendReport)
  .commit()
```

不需要再另外註冊排程。`Mastra` 啟動時，排程器直接從 Workflow 讀取 `schedule`。

## 投遞保證 {/* #delivery-guarantees */}

Workflow 的排程只會盡力發布啟動事件。每次觸發時，排程器會先領取工作，最多嘗試發布啟動事件三次。若用盡嘗試次數，或發布端當機，該次觸發可能被略過。略過的觸發不會自動補送，之後仍可依週期觸發。排程標記為 `completed` 代表已沒有後續觸發時間，無法據此確認 Workflow 已執行。錯誤回報與手動重跑的注意事項請見[排程的投遞保證](/reference/schedules/overview#delivery-guarantees)。

## 執行引擎 {/* #execution-engine */}

宣告 `schedule` 並不會改變 Workflow 的執行方式。和 `workflow.start()` 或透過 HTTP 觸發一樣，排程觸發會在執行排程器的主機上，於同一處理程序內執行。直接執行已有 `schedule` 的 Workflow，不必額外設定儲存或 Worker。

將 Worker 分開部署時例外。只要設定 [`MASTRA_WORKERS`](/reference/workers/overview#mastra_workers) 環境變數，不論值為何（包括 `false`），`createWorkflow` 都會使用**事件驅動執行引擎**建構有排程的 Workflow，讓部署中的每個處理程序都以相同方式執行。排程觸發會由[協調 Worker](/docs/deployment/workers#orchestration-worker)執行，Mastra 建立 Workflow 時會將警告寫到主控台。公開 API（`workflow.start()`、`workflow.startAsync()`、`resume()`）維持不變。

事件驅動執行需要能以不可分割的方式套用並行更新的儲存介接器，例如 `@mastra/libsql` 或 `@mastra/pg`。使用其他介接器時，`createRun()` 會擲出例外，並在錯誤訊息中列出支援的介接器。

只有環境變數能觸發切換，因為 `createWorkflow` 先於 `Mastra` 讀取 `workers` 選項執行。如果是用 `workers` 選項分開部署 Worker，請改從 `@mastra/core/workflows/evented` 匯入 `createWorkflow` 來建立有排程的 Workflow。

## 單一排程 {/* #single-schedule */}

若 Workflow 只需要一種觸發週期，請將物件傳給 `schedule`：

```typescript title="src/mastra/workflows/daily-report.ts"
import { createWorkflow } from '@mastra/core/workflows'

const dailyReport = createWorkflow({
  id: 'daily-report',
  schedule: {
    cron: '0 9 * * *',
    timezone: 'America/New_York',
    inputData: { userId: 'system' },
  },
  // ...
})
```

欄位如下：

- `cron`：由 5、6 或 7 欄組成的 cron 運算式，建構 Workflow 時會驗證。`cron` 和 `runAt` 必須擇一提供。
- `runAt`（選用）：不使用 cron，改在此時刻觸發一次。可填入 Unix 紀元毫秒數或 `Date`。觸發後排程會轉為 `completed`，後續部署不會重新啟用，除非變更 `runAt`。首次註冊時若 `runAt` 已過，排程會直接記為 `completed`，不會觸發。
- `endAt`（選用）：只可搭配 `cron`，超過此時刻就不再觸發。若下一次觸發時間晚於 `endAt`，排程就會轉為 `completed`。
- `timezone`（選用）：IANA 時區，例如 `America/New_York`。預設為主機的本機時區。正式環境請明確設定，以免觸發時間取決於伺服器的地區設定。
- `inputData`（選用）：每次觸發時傳給 Workflow 的輸入資料。
- `initialState`（選用）：該次執行的初始狀態。
- `requestContext`（選用）：附加到該次執行的請求上下文。
- `metadata`（選用）：和排程資料列一起儲存的自訂中繼資料。

若要在固定時間執行 Workflow 一次，請用 `runAt`：

```typescript title="src/mastra/workflows/launch-announcement.ts"
const launchAnnouncement = createWorkflow({
  id: 'launch-announcement',
  schedule: {
    // Set this to a stable future ISO timestamp in your deployment environment.
    runAt: new Date(process.env.LAUNCH_ANNOUNCEMENT_AT!),
    inputData: { userId: 'system' },
  },
  // ...
})
```

## 多個排程 {/* #multiple-schedules */}

傳入陣列，讓同一個 Workflow 在不同週期觸發。每個項目都需要唯一且固定的 `id`：

```typescript title="src/mastra/workflows/status-check.ts"
import { createWorkflow } from '@mastra/core/workflows'

const statusCheck = createWorkflow({
  id: 'status-check',
  schedule: [
    { id: 'morning', cron: '0 9 * * *', inputData: { window: 'morning' } },
    { id: 'evening', cron: '0 18 * * *', inputData: { window: 'evening' } },
  ],
  // ...
})
```

每個項目會建立獨立的排程資料列，依自己的 cron 運算式觸發，並在 Studio 的 Schedules 檢視中分別顯示。

## 在 Studio 查看排程 {/* #viewing-schedules-in-studio */}

排程在 Studio 中有自己的頂層頁面，不是 Workflow 裡的分頁：

- **所有排程**：開啟 `/workflows/schedules` 查看所有 Workflow 的排程。每列會顯示 Workflow ID、cron、下次觸發時間和最近一次執行的狀態，方便立即發現問題。
- **依 Workflow 篩選**：加上 `?workflowId=<id>`，只查看指定 Workflow 的排程，例如 `/workflows/schedules?workflowId=daily-report`。
- **排程詳細資訊**：選取任一列，開啟 `/workflows/schedules/:scheduleId`。頁面會顯示排程的中繼資料，以及 **Pause** / **Resume** 控制項，下方則是完整的觸發紀錄。

Workflow 至少有一個排程時，頁首會出現 **Schedules** 操作：

- 只有一個排程時，直接前往它的詳細資訊頁面。
- 有多個排程時，前往依 Workflow 篩選的清單，網址為 `/workflows/schedules?workflowId=<id>`。
- 沒有排程時，不顯示這項操作。

### 觸發紀錄 {/* #trigger-history */}

排程器會嘗試寫入觸發紀錄，包含執行 ID、預定時間、實際觸發時間與發布狀態。若發布端在領取觸發工作後，或在事件已獲接受後當機，可能不會留下紀錄。詳細資訊頁會將已記錄的觸發和對應的 Workflow 執行配對，並顯示：

- 執行狀態徽章（`running`、`success`、`failed`、`suspended`、`canceled`）。
- 執行開始時間和持續時間。
- 前往完整執行圖的連結 `/workflows/:workflowId/graph/:runId`。
- `pending` 徽章：發布觸發事件與寫入執行快照之間可能有競爭條件，導致執行紀錄尚未寫入。
- `publish failed` 徽章：三次發布都失敗時會顯示，並附上最後一次發布錯誤。實際結果不明，因為傳輸層可能已接受事件才回傳錯誤。

若還有觸發未進入最終狀態，面板每五秒輪詢一次，直到這些觸發全數進入最終狀態。清單會分頁，執行已久的排程不用一開始就載入上千筆資料。

## 在執行期間暫停排程 {/* #pausing-a-schedule-at-runtime */}

正式環境中的排程出現觸發異常時，不必重新部署或手動修改資料庫，可以從 SDK 暫停：

```typescript
import { MastraClient } from '@mastra/client-js'

const client = new MastraClient({ baseUrl: 'http://localhost:4111' })

// Schedule ids are derived from the workflow id: `wf_<workflowId>` for a
// single declarative schedule, or `wf_<workflowId>__<scheduleId>` when you
// declare multiple schedules per workflow as an array.
await client.pauseSchedule('wf_daily-report')
// ...investigate, ship a fix, then:
await client.resumeSchedule('wf_daily-report')
```

若使用 Studio，請開啟排程的詳細資訊頁面，在頁首選取 **Pause** 或 **Resume**。

請留意以下規則：

- 暫停狀態會寫入排程資料表，重新啟動處理程序或部署後仍保留。依宣告設定新增或更新資料列時，即使變更 `cron`、`timezone`、`runAt`、`endAt` 或其他欄位，也不會覆寫使用者設定的狀態。
- 恢復 cron 排程時，以目前時間重新計算 `nextFireAt`。暫停一週也不會補跑積欠的七次執行；排程會在 cron 的下一個正常時間點觸發。
- 恢復單次排程時，保留原本設定的 `runAt`。若暫停期間已過該時間，排程器下次檢查時就會觸發。
- 用 `resumeSchedule` 或 Studio 的 **Resume** 按鈕解除暫停。編輯 Workflow 的 `schedule` 設定不會讓已暫停的資料列恢復。
- 暫停和恢復都是冪等操作。對已暫停的排程再次執行暫停，不會造成變更。
- 執行期間的這類覆寫只影響既有排程。宣告式排程應在程式碼中以 `createWorkflow` 的 `schedule` 欄位建立、刪除和編輯。若要在執行期間直接建立排程，請使用統一的 [`mastra.schedules`](/docs/harness/schedules) 服務並提供 `workflowId`。

底層 HTTP 路由是 `POST /api/schedules/:scheduleId/pause` 和 `POST /api/schedules/:scheduleId/resume`，都需要 `schedules:write` 權限。

## 變更設定後重新部署 {/* #redeploying-with-changes */}

變更 `schedule` 設定並重新部署後，Mastra 會比較現有排程資料列和新設定：

- 週期性排程的 `cron`、`timezone` 或 `endAt` 變更時，會重新計算 `nextFireAt`。若將來不會再觸發，排程便會完成；若重算後還有觸發機會，已完成的排程就會重新啟用。
- 單次排程的 `runAt` 變更時，會將 `nextFireAt` 設為該時間。如果新的 `runAt` 在未來，已完成的排程會重新啟用；如果 `runAt` 已過，則仍維持完成。
- 若應用程式離線期間，啟用中的單次排程已過原先且未變更的 `runAt`，該工作仍待觸發，排程器下一次檢查時會觸發。首次註冊時若 `runAt` 已過，則會直接建立為 `completed`，不會觸發。
- 若只變更 `inputData`、`initialState` 或 `metadata`，會直接更新既有資料列，保留下次觸發時間。
- 使用者設定的狀態（例如用 `client.pauseSchedule` 暫停）和觸發紀錄都不會被覆寫，除非上述時間變更要求更新狀態。

`completed` 代表排程已沒有需要自動觸發的工作：單次觸發已被領取、週期性觸發已用盡，或註冊或同步設定時，指定的觸發時間均已過。這個狀態無法確認 Workflow 是否成功執行完畢。

從 Workflow 的 `schedule` 陣列移除項目後，下次啟動時會刪除對應的資料列。

## 部署拓撲 {/* #deployment-topology */}

內建排程器用 `setInterval` 定期輪詢排程資料表、領取到期的資料列，並透過處理程序內的發布訂閱機制分派 Workflow 執行。這需要長時間運作的主機處理程序。

### 長時間運作的主機（建議） {/* #long-lived-host-recommended */}

Fly Machines、Railway、Render、AWS ECS、GKE 或你自己的伺服器，都能讓 Mastra 處理程序在兩次 cron 觸發之間保持運作。`mastra build` 產生的伺服器會自動啟動排程器，排程不必另行設定。

若透過[伺服器介接器](/docs/server/server-adapters)執行 Mastra，請在伺服器開始監聽後呼叫 `mastra.startWorkers()`。介接器不會代為啟動排程器；若省略這個呼叫，排程就不會觸發。請見[啟動背景 Worker](/docs/server/server-adapters#start-background-workers)。

正式部署時，可讓排程器在[專用的 Worker 處理程序](/docs/deployment/workers#scheduler-worker)內執行，和 API 層隔離。

### Serverless 平台 {/* #serverless-platforms */}

Vercel、Netlify、AWS Lambda 和 Cloudflare Workers 等函式即服務平台，在每次請求結束後會關閉處理程序。排程迴圈因此沒有下一輪，現階段無法用內建排程器觸發程式碼中宣告的排程。仍可直接執行：由 HTTP 路由呼叫 `run.start()`，即可像其他 Workflow 一樣，在同一處理程序內執行宣告了 `schedule` 的 Workflow。

若要在這些平台定時觸發，請用 [`@mastra/inngest`](#inngest-workflows)。Inngest 原生支援 Serverless，並代為保管 cron 狀態。

## Inngest Workflow {/* #inngest-workflows */}

本頁說明的 `schedule` 欄位由 Mastra 的內建排程器使用。若採用 `@mastra/inngest`，則應在 Inngest 的 `createFunction` 中以它自己的 `cron` 欄位設定 Workflow，由 Inngest 的排程器觸發。

實際使用時有以下差異：

- Inngest 排程不會出現在 Studio 的 `/workflows/schedules` 檢視中。
- Inngest Workflow 的頁首不會顯示 **Schedules** 操作。
- `client.pauseSchedule` 和 `client.resumeSchedule` 無法控制 Inngest 排程。

請在 [Inngest 管理介面](https://www.inngest.com/docs/guides/scheduled-functions)管理 Inngest 排程。若要讓 Mastra 負責整個排程流程，請使用 Mastra 排程。
