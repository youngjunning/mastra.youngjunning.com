# 運用 Knowledge 打造應用

以下模式示範如何運用 Knowledge。各範例會說明 Agent 的分工、各 scope 存放的內容，以及需要的設定或工具呼叫。Knowledge 本身沒有內建的 scope 類型。只有 `resource:` 和 `thread:` 來自 Memory，[`knowledgeMemoryScopes()`](/reference/knowledge/knowledge-memory-scopes) 會宣告這兩種 scope，另外再宣告一個租戶 scope。

:::alpha

Knowledge 目前處於 alpha 階段，API 可能隨版本變動。

:::

:::warning

每次呼叫工具時都會檢查存取權限，但 Knowledge 目前仍無法保證資料只會傳到持有相應 scope 的執行，也無法保證 Agent 不會跨 scope 複述內容。以下範例說明設計用途，現階段請勿仰賴 Knowledge 隔離敏感資料。

:::

## 根據自己的文件回答問題 {/* #answer-from-your-own-docs */}

伺服器透過 [`upsertPage()`](/docs/knowledge/load-your-content) 將文件同步到 `product-docs:` scope，並只提供讀取工具給文件 Agent。Agent 會列出頁面樹，讀取長頁面中符合查詢的行。如果搜尋不到，就會說不知道。

```typescript
const knowledge = new Knowledge({
  id: 'docs',
  storage,
  tools: { read: true },
  scopes: {
    ...knowledgeMemoryScopes({ org: 'workspace:$workspaceId' }),
    'product-docs:$workspaceId': {
      belongsTo: 'workspace:$workspaceId',
      access: [{ principal: 'workspace:$workspaceId', role: 'viewer' }],
    },
  },
})
```

若問題只涉及某個地區，Agent 會要求讀取符合條件的行，以及各行的前後一行。

```json
{ "page": "product-docs:initech#billing/refunds", "match": "region 42", "context": 1 }
```

## 由單一 Agent 服務多個客戶 {/* #one-agent-many-customers */}

由同一個客服 Agent 服務所有客戶。每個客戶的頁面都放在自己的 `tenant:` scope，並由 `knowledgeMemoryScopes()` 將其宣告為租戶 scope。

```typescript oxfmt:false
scopes: { ...knowledgeMemoryScopes({ org: 'tenant:$tenantId' }) },
```

伺服器執行 Agent 時，會傳入客戶的 scope，以及使用者和對話各自的 scope。

```typescript
await agent.generate(message, {
  scopes: ['tenant:globex', `resource:${userId}`, `thread:${threadId}`],
})
```

Globex 的使用者搜尋「續約」時，結果沒有 `tenant:acme#renewals`，因為這次執行未持有 `tenant:acme`。這與提示無關。若 Agent 有設定 Memory，`resource:` 和 `thread:` scope 也會讓 Memory 知道本次執行屬於哪個使用者與 Thread。可用 [`explainAccess()`](/docs/knowledge/scopes-and-access#test-access-with-explainaccess) 測試規則。如頁首警告所述，Knowledge 目前仍無法保證這種隔離，請勿仰賴它保護敏感的客戶資料。

## 每個 Agent 都須遵守的政策 {/* #a-policy-every-agent-follows */}

合規團隊負責各帳戶的資料處理規則。處理該帳戶的銷售、客服或帳務 Agent 每一輪都需要看到這些規則，無需等到主動搜尋才取得。只有合規團隊可以修改規則。

請在帳戶 scope 宣告頁面，並在設定中釘選。只有 `Knowledge` 實例設為 `pinnedContext: true`，且 Agent 有設定 Memory，釘選內容才會加入執行。本頁的釘選範例都採用這兩項設定。

```typescript oxfmt:false
'account:$accountId': {
  access: [
    { principal: 'self', role: 'viewer' },
    { principal: 'desk:$accountId:compliance', role: 'editor' },
  ],
  pages: [{ key: 'data-handling', name: 'Data handling rules' }],
  pinnedContext: ['account:$accountId#data-handling'],
},
```

合規團隊寫好頁面後，持有 `account:umbrella` 的執行會從一開始就將頁面內容載入情境。合規團隊編輯頁面時，正在執行的 Agent 會在下一輪只收到變更內容。

下列規則會保護合規團隊設定的政策。

* **Agent 可以讀取政策，但無法修改。** 該帳戶的執行只有檢視權限，因此銷售 Agent 嘗試編輯頁面時會遭拒。
* **Agent 無法取消釘選。** 設定中的釘選是由你宣告的，不在儲存空間中，所以釘選工具無法移除。
* **頁面無法移動或刪除。** 在 `pages` 宣告的頁面由設定管理。
* **只有能讀取頁面的執行才會收到內容。** 其他帳戶的執行不會收到這個頁面。釘選不會擴大頁面的存取範圍。

請見 [釘選情境](/docs/knowledge/pinned-context)。

## 讓程式碼慣例延續到下次工作階段 {/* #coding-conventions-that-carry-over */}

開發人員的程式設計 Agent 在同一儲存庫中共用一個 scope。釘選程式碼慣例頁面，再把決策記為該頁的筆記，並連到相關頁面。

```typescript oxfmt:false
'repo:$repo': {
  access: [{ principal: 'self', role: 'editor' }],
  pages: [{ key: 'conventions', name: 'Conventions' }, { key: 'tooling', name: 'Tooling' }],
  pinnedContext: ['repo:$repo#conventions'],
},
```

例如，Agent 把「使用 pnpm workspaces，不使用 npm」記在慣例頁面上，並用 `[[repo:api#tooling]]` 連到相關頁面。

之後在 `repo:api` 開啟工作階段時，會看到程式碼慣例旁標示「1 則筆記」。`repo:web` 的工作階段則看不到這些內容。

## 從值班經驗改善維運手冊 {/* #runbooks-that-improve-on-call */}

值班工程師在服務的 scope 中是貢獻者，其 Agent 可以為釘選的維運手冊加上筆記，但無法改寫手冊。SRE 負責人擁有編輯權限，可將筆記內容整合進手冊。

```typescript oxfmt:false
'oncall:$orgId:$service': {
  belongsTo: 'org:$orgId',
  access: [
    { principal: 'self', role: 'contributor' },
    { principal: 'role:$orgId:sre-lead', role: 'editor' },
  ],
  pages: [{ key: 'runbook', name: 'Incident runbook' }],
  pinnedContext: ['oncall:$orgId:$service#runbook'],
},
```

值班 Agent 若嘗試編輯頁面，會因為只有貢獻者權限而遭拒，仍可新增筆記。

## 像整理資料夾一樣整理頁面 {/* #organize-pages-like-folders */}

頁面可在 scope 內分層。假設手冊宣告了 `refunds`，並在其下加入 `damaged-items`。Agent 即使不知道確切名稱，也能列出頁面樹，再讀取需要的頁面。

```json
{ "from": "handbook:acme", "depth": 2 }
```

Agent 會取得各頁的參照（例如 `handbook:acme#refunds/damaged-items`）、名稱及子頁面數量，再讀取需要的頁面。

## 每個部門各有一個 scope {/* #one-scope-per-department */}

公司 scope 之下，各部門都有自己的 scope。人資的到職檢查清單放在 `dept:initech:hr`。伺服器會將 `firm:initech` 和員工所屬部門的 scope 傳給該員工的每次執行。工程師搜尋不到人資 scope 中的內容，但持有 `firm:initech` 的執行都能找到全公司的假日頁面。

```typescript
const scopes = {
  ...knowledgeMemoryScopes({ org: 'firm:$firmId', orgRole: 'contributor' }),
  'dept:$firmId:$dept': {
    belongsTo: 'firm:$firmId',
    access: [{ principal: 'self', role: 'editor' }],
  },
}
```

要改變哪些人能看到哪些內容，只需調整設定及伺服器傳入的 scope，無需重寫提示。

## 讓有需要的人看到筆記 {/* #notes-for-the-people-who-need-them */}

筆記的 `scope` 列出它標記的範圍。只要執行能讀取頁面，且持有其中任一 scope，就能看到該筆記。Dana 的 Agent 在一則筆記只標記她自己的 scope，另一則則同時標記她和她小組的 scope。

```json
{
  "op": "add",
  "page": "office:hooli#coverage",
  "scope": ["resource:dana", "squad:hooli:support"],
  "text": "Dana is out Nov 10 to 14; Bea covers her queue."
}
```

客服小組的 Bea 只能看到第二則筆記。銷售部門的 Sam 兩則都看不到，他的 Agent 也無法在筆記標記自己無權存取的小組 scope。

## 讓 Agent 交接工作 {/* #hand-work-between-agents */}

同一專案的研究、規劃和程式設計 Agent 共用一個 scope。研究 Agent 撰寫頁面，規劃 Agent 在該頁之下新增計畫。程式設計 Agent 讀取計畫，每完成一個步驟就新增筆記，例如「步驟 1 已在 PR 412 完成」。

Agent 之間無需直接溝通，只要依相同的存取規則共用頁面即可。
