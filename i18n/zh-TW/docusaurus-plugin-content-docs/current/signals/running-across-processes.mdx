# 跨行程執行

執行多個 Mastra 行程時，訊號可能送到執行 Agent 以外的行程。各行程必須互相傳遞輸入，並協調由哪個行程執行某個 [執行緒](/docs/memory/message-history#threads-and-resources)。

Mastra 透過共用的 [PubSub](/docs/server/pubsub) 後端在行程間傳遞訊號。[租約](/reference/pubsub/lease-provider)讓一個行程在限定時間內取得執行緒的控制權。共用儲存空間保存對話記錄。若多個行程能處理同一執行緒，就需要這三項。

## 為何需要共用後端 {/* #why-you-need-a-shared-backend */}

預設的 [`EventEmitterPubSub`](/reference/pubsub/event-emitter) 會在單一行程內傳遞事件，足以應付單一伺服器，但無法傳給其他執行個體。

假設兩個 API 執行個體共用一個資料庫。使用者在 A 啟動一次執行，下一則訊息卻送到 B。若沒有共用後端，B 無法發布訊息給 A 上的執行，只能在同一執行緒上啟動第二次執行。兩次執行都會呼叫模型並寫入訊息，造成競爭。

共用後端可讓 B 將訊息發布到執行緒主題，再由 A 取用。租約確保只有一個行程能取得執行緒的控制權，其他行程會將訊息轉送給它。

能處理同一執行緒的執行個體都必須使用同一個 PubSub 後端和儲存空間。即使共用資料庫，不同的後端也無法協調。

## 選擇拓撲 {/* #choose-a-topology */}

依行程執行的位置選擇後端。

| 部署方式 | 後端 | 提供的功能 |
| - | - | - |
| 單一行程 | [`EventEmitterPubSub`](/reference/pubsub/event-emitter)（預設） | 行程內傳遞和租約 |
| 單一主機上的多個行程 | [`UnixSocketPubSub`](/reference/pubsub/unix-socket-pubsub) | 透過 Unix 網域通訊端傳遞事件並提供租約 |
| 多台主機 | [`RedisStreamsPubSub`](/reference/pubsub/redis-streams) 或 [`ValkeyStreamsPubSub`](/reference/pubsub/valkey-streams) | 跨主機傳遞、事件保留和租約 |
| 多台主機使用 Google Cloud Pub/Sub | [`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub) | 跨主機傳遞，不提供租約 |

[`UnixSocketPubSub`](/reference/pubsub/unix-socket-pubsub) 會選出一個行程擔任通訊端代理，該行程結束時會重新選舉。它無法跨機器運作。

[`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub) 能跨行程傳遞事件，但沒有實作租約。Mastra 無法判斷哪個執行個體擁有執行緒，因此收到訊號的執行個體都可能嘗試執行。只有在其他層能確保每個執行緒只由一個行程執行時才使用。

## 執行緒控制權與租約 {/* #thread-ownership-and-leases */}

Mastra 會先取得租約才開始執行。只有租約持有者可以執行該執行緒，其他行程會把訊號轉送給它。

租約預設有效期為 15 秒，持有者每 5 秒續約一次。續約間隔是租約存留時間（TTL）的三分之一，讓持有者錯過續約後仍有時間在到期前補救。若要調整數值，請參閱[設定](#configuration)。

若續約失敗且本機的期限已過，持有者會停止執行，因為它無法再確認是否有其他行程取得控制權。繼續執行可能讓兩個持有者寫入同一段對話。接著，新持有者會從儲存空間開始下一次執行。

當 Workflow 儲存後端不支援執行隔離（run fencing）時，[持久型 Agent](/docs/harness/durable-agents#run-ownership) 會使用相同的租約。支援隔離的後端會記錄控制權，並拒絕已失去控制權的執行寫入。介面約定請參閱 [`LeaseProvider` 參考文件](/reference/pubsub/lease-provider)。

## 將訊號轉送至其他行程 {/* #route-signals-to-another-process */}

訊號抵達時，執行環境會找出目前持有執行緒的行程。若已有行程公布自己持有執行緒，訊號就會發布到執行緒主題，再由持有者接續進行中的執行，或從佇列啟動一次執行。

若沒有公布的持有者，收到訊號的行程會嘗試取得執行緒的控制權。取得後就執行 Agent。如果其他行程先取得控制權，接收行程會轉送訊號，而 `accepted` 會解析為 `deliver`，而非 `wake`。結果說明請參閱 [`sendSignal()`](/reference/agents/agent#sendsignalsignal-options)。

若不得在任意執行個體上喚醒閒置的執行緒，請設定 `ifIdle.requireClaimedOwner: true`。喚醒只會送到已公布的持有者。若在探索時間內無人回應，`accepted` 會被拒絕。

## 傳遞保證與重複傳遞 {/* #delivery-guarantees-and-duplicates */}

PubSub 後端可能在逾時、確認失敗或當機後重新傳遞事件，因此執行環境以至少傳遞一次為前提。只要持有者仍保有處理紀錄，重送的訊號就不會為同一則邏輯訊息啟動第二次執行。

這無法保證每個事件恰好傳遞一次。如果處理常式會寫入資料庫或觸發其他操作，請讓它具備冪等性，也就是處理同一事件兩次的效果與一次相同。

## 訊號與行程當機 {/* #signals-and-process-crashes */}

行程當機後能保留哪些資料，取決於資料存放的位置：

- 執行期間的佇列位於行程記憶體中。若執行尚未取用佇列中的訊號就當機，這些訊號會遺失。
- 以 `persist` 行為送出的訊號會寫入 Memory 儲存空間。若各行程共用該空間，重新啟動後仍會保留訊號。
- [狀態訊號](/docs/signals/state-signals)及其追蹤資料會存在執行緒上。使用共用儲存空間時，重新啟動後仍會保留。
- [通知](/docs/signals/notifications)會以持久記錄的形式寫入通知儲存空間，派送程式可在重新啟動後重試傳遞。
- 共用 PubSub 後端負責傳遞事件，無法當作持久化輸入佇列。保留事件能協助訂閱者重新連線，但無法取代儲存空間。
- 持久型 Agent 會從檢查點恢復執行，當機行程中存於記憶體的訊號佇列無法還原。

若接收訊號的行程結束後仍需保留該訊號，請將訊號持久化或記錄到自己的系統。請勿把 PubSub 保留的事件當成正式紀錄。

## 無伺服器 {/* #serverless */}

無伺服器函式傳回回應後可能立即凍結。如果函式啟動了執行，請持續讀取輸出串流，讓函式保持運作直到執行結束。

將這項工作交給平台的 `waitUntil`，讓它在送出 HTTP 回應後仍可繼續執行：

```typescript title="src/routes/signal.ts"
const result = agent.sendSignal(signal, { resourceId, threadId })

ctx.waitUntil(
  result.accepted.then(async accepted => {
    if (accepted.action === 'wake') {
      await accepted.output.consumeStream()
    }
  }),
)
```

若執行緒由另一個行程持有，`accepted` 會解析為 `deliver`，本機沒有輸出要讀取。若此次呼叫取得租約，就會收到 `wake`，此時必須持續運作直到輸出結束。

無伺服器平台也要使用共用的 PubSub 後端及儲存空間。執行個體的生命週期短，記憶體中的佇列特別容易遺失。

## 正常關閉 {/* #graceful-shutdown */}

停止接收新的 webhook 或訊號請求，等待進行中的工作結束。產生的 Mastra 伺服器會處理 `SIGINT` 和 `SIGTERM`，停止接受新連線，等待現有請求處理完畢，再呼叫 [`mastra.shutdown()`](/docs/deployment/mastra-server#graceful-shutdown-and-rolling-deploys)。如果你將 Mastra 嵌入自己的伺服器，請在關閉掛鉤中呼叫此方法。

訊號 Provider 有自己的生命週期。呼叫 [`provider.stop()`](/reference/signals/signal-provider#stop) 可停止輪詢並清除記憶體中的訂閱。關閉前，請停止將 webhook 路由至 [`WebhookSignalProvider`](/reference/signals/webhook-signal-provider)，以免行程結束時仍收到新請求。

## 設定 {/* #configuration */}

共用的 Redis Streams 後端同時處理訊號傳遞及執行緒租約：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { PostgresStore } from '@mastra/pg'
import { RedisStreamsPubSub } from '@mastra/redis-streams'

export const mastra = new Mastra({
  agents: { agent },
  storage: new PostgresStore({
    id: 'mastra-storage',
    connectionString: process.env.DATABASE_URL,
  }),
  pubsub: new RedisStreamsPubSub({
    url: process.env.REDIS_URL,
    keyPrefix: 'mastra:my-app',
  }),
})
```

讓各執行個體將 `storage` 指向同一個資料庫。重新啟動後，持久化訊號、狀態訊號和通知記錄仍會保留，任何持有執行緒的行程都能讀取。

參與協調的執行個體要使用相同的 `keyPrefix`。若多個環境共用同一台 Redis 伺服器，各環境應使用不同的前置詞。Vercel 託管的 Redis 和 Upstash Redis 都支援搭配 `RedisStreamsPubSub`。

透過下列環境變數設定租約：

- `MASTRA_AGENT_THREAD_LEASE_TTL_MS` 設定租約有效期，預設為 `15000` 毫秒。
- `MASTRA_AGENT_THREAD_LEASE_RENEW_INTERVAL_MS` 設定續約間隔，預設為 TTL 的三分之一。設定值大於或等於 TTL 時，會改用預設值。

請讓各執行個體的這兩項設定保持一致。TTL 較短時，持有者當機後能更快釋放執行緒，但可容忍的續約延遲也較少。TTL 較長時則相反。除非部署有需要，否則請保留預設值。其他後端請參閱 [`RedisStreamsPubSub` 參考文件](/reference/pubsub/redis-streams)。
