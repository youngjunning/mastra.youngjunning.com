# 訊號 Provider

訊號 Provider 會監看外部系統，並將[通知](/docs/signals/notifications)送到訂閱的 Agent 執行緒。例如，可監看建置管線，在建置失敗時通知訂閱該管線的每個執行緒。

若應用程式需要決定各來源的事件該送到哪些執行緒，可使用 Provider。基底類別 [`SignalProvider`](/reference/signals/signal-provider) 負責維護訂閱、執行輪詢，以及將通知轉送給 Agent。你要實作讀取外部系統及比對事件與訂閱的程式碼，也可提供工具和處理器給 Agent。

若伺服器已收到事件，而且知道目標執行緒，可直接呼叫 [`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options)。若要更新應用程式的上下文，請用[狀態訊號](/docs/signals/state-signals)；若上下文僅供單次模型請求使用，請用[暫時性反應訊號](/docs/signals/sending-signals#send-context-from-a-system)。

## Provider 的運作方式 {/* #how-a-provider-works */}

將 Provider 註冊到 Agent 的 `signals` 陣列。它可透過兩種方式接收事件：

- **輪詢：** [`poll()`](/reference/signals/signal-provider#polling) 定期查看外部系統。
- **Webhook：** 由伺服器將收到的事件交給 [`handleWebhook()`](/reference/signals/signal-provider#webhooks)。

每筆符合條件的訂閱都會由 Provider 呼叫受保護的 [`notify()`](/reference/signals/signal-provider#notifications) 方法。這會將事件轉交給 `Agent.sendNotificationSignal()`，並採用通知的投遞政策、重試機制和收件匣。

## 對應外部識別碼與執行緒 {/* #map-external-identities-to-threads */}

用目標執行緒的 [`resourceId` 和 `threadId`](/docs/memory/message-history#threads-and-resources) 決定通知去向。Provider 還需要 `externalResourceId` 來識別執行緒監看的對象，例如建置管線 `acme-app-main`。請選擇可用來比對傳入事件的固定值。

這三個值合在一起作為訂閱的鍵值。因此，一個執行緒可監看多個資源，多個執行緒也可監看同一資源。額外資料請放在 `metadata`，避免放入外部識別碼。處理 Webhook 時，先比對承載資料與 `externalResourceId`，再用訂閱的 `resourceId` 和 `threadId` 指定目標。

## 快速上手 {/* #quickstart */}

這個範例會檢查管線的建置狀態，建置失敗就通知已訂閱的執行緒。`builds` 對應表用來模擬 CI 服務。請將 `fetchBuildStatus()` 換成呼叫實際服務的程式碼。

使用 Provider 前，請先[替 `Mastra` 執行個體設定通知儲存](/docs/signals/notifications#storage-and-dispatcher-setup)，否則 `notify()` 無法建立紀錄。

```typescript title="src/mastra/signals/ci-signals.ts"
import { SignalProvider } from '@mastra/core/signals'
import type { SignalProviderTarget, SignalSubscription } from '@mastra/core/signals'

type BuildStatus = {
  id: string
  status: 'passed' | 'failed'
}

const builds = new Map<string, BuildStatus>([
  ['acme-app-main', { id: 'build_123', status: 'failed' }],
])

async function fetchBuildStatus(pipeline: string): Promise<BuildStatus> {
  return builds.get(pipeline) ?? { id: 'build_unknown', status: 'passed' }
}

export class CiSignals extends SignalProvider<'ci-signals'> {
  readonly id = 'ci-signals' as const
  readonly pollInterval = 30_000

  watch(target: SignalProviderTarget, pipeline: string) {
    return this.subscribe(target, pipeline)
  }

  unwatch(target: SignalProviderTarget, pipeline: string) {
    return this.unsubscribe(target, pipeline)
  }

  async poll(subscriptions: SignalSubscription[]) {
    for (const sub of subscriptions) {
      const build = await fetchBuildStatus(sub.externalResourceId)

      if (build.status !== 'failed') continue

      await this.notify(
        {
          source: this.id,
          kind: 'ci-status',
          priority: 'high',
          summary: `Build failed for ${sub.externalResourceId}`,
          payload: build,
          dedupeKey: `${this.id}:${sub.externalResourceId}:${build.id}`,
        },
        { resourceId: sub.resourceId, threadId: sub.threadId },
      )
    }
  }
}
```

將 Provider 註冊到 Agent，再讓執行緒訂閱要監看的建置管線：

```typescript title="src/mastra/agents/support-agent.ts"
import { Agent } from '@mastra/core/agent'
import { CiSignals } from '../signals/ci-signals'

export const ciSignals = new CiSignals()

export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'Help the user triage CI updates.',
  model: '__GATEWAY_OPENAI_MODEL__',
  signals: [ciSignals],
})

ciSignals.watch({ resourceId: 'user_123', threadId: 'thread_456' }, 'acme-app-main')
```

Agent 會連接 Provider、輪詢，並在管線失敗時發出通知。請把 `supportAgent` 註冊到 `Mastra` 執行個體，讓 `notify()` 能存取通知儲存層。

## 建立 Provider {/* #build-a-provider */}

### 連接及訂閱 {/* #connect-and-subscriptions */}

只有初始化設定依賴已連接的 Agent 時，才需要覆寫 [`connect()`](/reference/signals/signal-provider#connection)。務必先呼叫 `super.connect(agent)`。

透過下列受保護的成員存取訂閱：

- `subscribe(target, externalResourceId, metadata?)` 新增訂閱，或將中繼資料合併到已有的訂閱。
- `unsubscribe(target, externalResourceId)` 移除一筆訂閱；`unsubscribeAll(target)` 移除執行緒的所有訂閱。
- `getSubscriptions()`、`getSubscriptionsForResource()`、`getSubscriptionsForThread()`、`hasSubscription()` 和 `subscriptionCount` 可讀取訂閱登錄表，供診斷及條件檢查使用。

只公開應用程式用得到的功能。CI 範例以公開方法 `watch()` 和 `unwatch()` 包裝 `subscribe()` 與 `unsubscribe()`。

### 輪詢 {/* #polling */}

若來源無法主動推送事件，請以毫秒設定 `pollInterval`，並實作 `poll(subscriptions)`。

基底類別會管理計時器：

- 沒有訂閱時會略過該輪，而且不會同時執行兩輪。即使 `poll()` 執行較慢，也不會與另一輪同時執行。
- 捕捉並記錄 `poll()` 的錯誤，接著等待下一輪。
- 對計時器呼叫 `unref()`，讓處理程序不必只因輪詢而繼續執行。

輪詢失敗時，基底類別不會立刻重試。可等到下一輪再試，或在 `poll()` 內加入自己的退避機制。

### Webhook {/* #webhooks */}

若來源能呼叫你的應用程式，請用 Webhook。覆寫 `handleWebhook(request)` 來解析承載資料、查詢訂閱，並針對每筆相符的訂閱呼叫 `notify()`：

```typescript title="src/mastra/signals/ci-signals.ts"
import { SignalProvider } from '@mastra/core/signals'
import type { SignalProviderWebhookRequest } from '@mastra/core/signals'

export class CiSignals extends SignalProvider<'ci-signals'> {
  readonly id = 'ci-signals' as const

  async handleWebhook(request: SignalProviderWebhookRequest) {
    const payload = request.body as { pipeline: string; status: string }
    const subscriptions = this.getSubscriptionsForResource(payload.pipeline)

    for (const sub of subscriptions) {
      await this.notify(
        {
          source: this.id,
          kind: 'ci-status',
          priority: 'high',
          summary: `Build ${payload.status} for ${payload.pipeline}`,
          payload,
        },
        { resourceId: sub.resourceId, threadId: sub.threadId },
      )
    }

    return { status: 200, body: { matched: subscriptions.length } }
  }
}
```

`handleWebhook()` 是 Provider 的方法，請由你自己的端點呼叫。若來源要求驗證簽章，請在解析前用原始請求本文驗證。

### 保留訂閱 {/* #durable-subscriptions */}

基底類別將訂閱登錄表保存在記憶體內，限定單一處理程序的單一 Provider 執行個體使用。重啟後會遺失，也無法跨執行個體存取。

若需在重啟後保留訂閱，請自行儲存並在 [`start()`](/reference/signals/signal-provider#start) 中載入。第二個處理程序的登錄表一開始是空的，須自行載入一份訂閱。

### 生命週期鉤子 {/* #lifecycle-hooks */}

Agent 建構時會呼叫 `connect()`，接著啟動輪詢並呼叫 `start()`，但不會等待它完成。請確保 `start()` 不依賴第一輪輪詢，並處理它可能發生的錯誤。

[`stop()`](/reference/signals/signal-provider#stop) 是同步方法。預設實作會停止輪詢並清除所有訂閱索引。若覆寫方法來清理資源，請記得呼叫 `super.stop()` 以釋放登錄表：

```typescript oxfmt:false
override stop() {
  this.closeClient()
  super.stop()
}
```

Agent 不會代為呼叫 `stop()`，請自行在關閉流程中呼叫。若關閉用戶端需要非同步操作，請提供非同步關閉方法，等它完成後再呼叫 `stop()`。

### 處理器和工具 {/* #processors-and-tools */}

Provider 可替已連接的 Agent 提供額外功能：

- 以 `getInputProcessors()` 回傳輸入處理器，並以 `getOutputProcessors()` 回傳輸出處理器。
- 以 `getTools()` 回傳 Agent 可呼叫的工具。

Agent 會在 `connect()` 後取得這些項目一次，並將處理器註冊到 Mastra 執行個體。

### 傳送通知 {/* #send-notifications */}

[`notify()`](/reference/signals/signal-provider#notifications) 包裝了已連接 Agent 的 `sendNotificationSignal()`，接受相同欄位：`source`、`kind`、`summary`，以及選用的 `priority`、`payload`、`dedupeKey`、`coalesceKey` 和 `attributes`。

若同一事件可能到達兩次，例如連續兩輪輪詢都看到同一筆建置失敗，請用 `dedupeKey`。若要將相關事件併入同一筆待處理紀錄，請用 `coalesceKey`。合併規則請見[通知指南](/docs/signals/notifications#create-and-coalesce-records)。

Provider 尚未連接時，`notify()` 會擲出例外。儲存層的錯誤也會往上傳遞，請讓輪詢或 Webhook 的錯誤處理邏輯接手。

### 正常關閉 {/* #shut-down-cleanly */}

關閉時：

1. 不再接收新的 Webhook 請求。
1. 用 `stopPolling()` 或 `stop()` 停止輪詢。
1. 清除訂閱登錄表。
1. 關閉或釋放外部用戶端及連線。
1. 若執行環境允許，等待已在執行的 `notify()` 呼叫完成。

基底類別會在 `stop()` 清除登錄表，但無法等候處理中的 Webhook 結束，也無法關閉非同步用戶端。請在關閉流程中安排這些操作。

## 內建 Provider {/* #built-in-providers */}

### 任務訊號 Provider {/* #task-signal-provider */}

註冊一次 [`TaskSignalProvider`](/reference/signals/task-signal-provider)，即可一併使用任務工具和 `TaskStateProcessor`。如果想讓 Agent 跨回合維護任務清單，可以加入它：

```typescript
import { Agent } from '@mastra/core/agent'
import { TaskSignalProvider } from '@mastra/core/signals'

const agent = new Agent({
  // ...
  signals: [new TaskSignalProvider()],
})
```

它提供 `task_write`、`task_update`、`task_complete` 和 `task_check`，以及把任務清單映射到狀態訊號通道的處理器。追蹤任務需要有 Memory 支援的執行緒，以及 `storage` 執行個體。若未設定 Memory，工具會回報任務追蹤需要 Agent 的 Memory。

### Webhook 訊號 Provider {/* #webhook-signal-provider */}

若是一般的 Webhook 來源，可用 [`WebhookSignalProvider`](/reference/signals/webhook-signal-provider)，省去撰寫子類別。設定一個取得資源識別碼的函式，也可選擇加上建立通知的函式：

```typescript title="src/mastra/index.ts"
import { Agent } from '@mastra/core/agent'
import { WebhookSignalProvider } from '@mastra/core/signals'

const webhooks = new WebhookSignalProvider({
  extractResourceId: payload => (payload as { repository: string }).repository,
  buildNotification: (payload, sub) => ({
    source: 'ci',
    kind: 'build-status',
    priority: 'medium',
    summary: `Build ${(payload as { status: string }).status} for ${sub.externalResourceId}`,
  }),
})

export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'Help the user triage updates.',
  model: '__GATEWAY_OPENAI_MODEL__',
  signals: [webhooks],
})

webhooks.subscribeThread({ resourceId: 'user_123', threadId: 'thread_456' }, 'acme/app')
```

從路由呼叫 `webhooks.handleWebhook({ body, headers })`。Provider 會以取出的資源識別碼比對訂閱，並通知所有相符的執行緒。

未提供 `extractResourceId` 時，會從承載資料讀取 `resource` 或 `externalResourceId`。未提供 `buildNotification` 時，會以 `medium` 優先級傳送 `webhook-event` 通知。

## 正式環境部署檢查清單 {/* #production-checklist */}

部署前：

- **避免重試造成重複通知：** 為每個事件指定固定的 `dedupeKey` 或 `coalesceKey`。Webhook 可能重複投遞，輪詢也可能再次讀到同一事件，而 Provider 不會在 `notify()` 之前去除重複項目。
- **驗證 Webhook：** 解析前使用原始請求本文驗證簽章，並由 HTTP 端點拒絕無效的請求。
- **處理來源中斷：** 輪詢會在下一個間隔重試，必要時可在 `poll()` 實作退避。Webhook 來源通常會自行重試；無法接收事件時，請回傳非 2xx 狀態碼。
- **視需求保存訂閱：** 登錄表位於記憶體。若重啟後仍須監看，請在 `start()` 重新載入訂閱。
- **使用共用儲存：** 通知紀錄和投遞政策依賴 Agent 使用的 Mastra 儲存層。
- **規劃關閉流程：** 停止接收 Webhook、停止輪詢、關閉用戶端，並讓傳送中的通知處理完畢。
- **監控通知佇列：** 摘要和延後投遞仰賴[通知分派器](/docs/signals/notifications#dispatch)，尤其在共用儲存時。
