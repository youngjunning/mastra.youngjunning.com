# 執行緒串流

執行緒串流會傳送 Agent 在同一[執行緒](/docs/memory/message-history#threads-and-resources)上多次執行的輸出。只要訂閱一次，就能以[資料區塊](/reference/streaming/ChunkType)的形式接收模型文字、Tool 呼叫與結果、核准請求和錯誤。各次執行之間，訂閱仍會保持開啟，不必每次傳送輸入都建立新的回應串流。

也可以在開始訂閱時要求取得已儲存的訊息。這樣應用程式就能先呈現目前為止的對話，再顯示新的輸出。

## 快速入門 {/* #quickstart */}

請在傳送輸入前先訂閱，才能從執行一開始就收到輸出。本範例使用 JavaScript 用戶端 SDK 的 [`subscribeToThread()`](/reference/client-js/agents#subscribetothread)，需要正在執行的 Mastra 伺服器，且伺服器上有 `support-agent` Agent。若要儲存訊息記錄，請為該 Agent 設定 [Memory](/docs/memory/overview)。

若伺服器端程式碼直接使用 `Agent` 執行個體，請參考 [Agent 快速入門](/docs/signals/overview#use-an-agent)。

```typescript title="src/app/chat.ts"
import { MastraClient } from '@mastra/client-js'

const client = new MastraClient({ baseUrl: 'http://localhost:4111' })
const agent = client.getAgent('support-agent')

const subscription = await agent.subscribeToThread({
  resourceId: 'user-123',
  threadId: 'thread-456',
})

await agent.sendMessage({
  message: 'Show the shorter version.',
  resourceId: 'user-123',
  threadId: 'thread-456',
})

await subscription.processDataStream({
  onChunk: chunk => {
    console.log(chunk)
  },
  reconnect: true,
})
```

[`client.getAgent()`](/reference/client-js/mastra-client#methods) 會選取伺服器上的 Agent。Mastra 接受輸入時，[`sendMessage()`](/reference/client-js/agents#sendmessage) 就會回傳。[`processDataStream()`](/reference/client-js/agents#subscribetothread) 將輸出交給 `onChunk`，在此範例中會印出每個資料區塊。回覆結束後，它仍會繼續監聽。

## 讀取串流 {/* #read-the-stream */}

### 已儲存的訊息記錄與即時片段 {/* #stored-history-and-live-parts */}

傳入 `withInitialHistory: true` 後，第一個資料區塊會是 `thread-history`，內含已儲存訊息的最新一頁，並依時間由舊到新排列。`perPage` 預設為 40。訂閱者接著會收到比這頁記錄更新且仍保留的片段，再收到即時片段。保留記錄需要記憶功能。沒有記憶功能或執行緒還沒有訊息時，仍會先送出這個區塊，但 `messages` 陣列為空。

### 資料區塊與執行 {/* #chunks-and-runs */}

使用 `runId` 將同一次執行的資料區塊分組。[`thread-history`](/reference/streaming/ChunkType#thread-history) 是例外，因為其中的訊息可能橫跨多次執行，所以 `runId` 為空。訂閱的 [`activeRunId()`](/reference/agents/agent#subscribetothreadoptions) 會回傳目前執行的 ID，或回傳 `null`。

公開的訂閱串流包含 `AgentChunkType`。`withInitialHistory` 會加入 `ThreadHistoryChunk`，而 `withRunStatus: true` 會加入 `ThreadRunStatusChunk`。兩個選項皆預設為 `false`。[ChunkType 參考文件](/reference/streaming/ChunkType)列出模型輸出、Tool 呼叫與結果、核准、中止及錯誤的欄位。若要觀察佇列計數，請另外使用 [`subscribeThreadEvents()`](/reference/signals/thread-events)。

### 判斷執行何時結束 {/* #detect-when-a-run-finishes */}

傳入 `withRunStatus: true` 即可接收執行結果。現有的訂閱預設不會接收這類資料區塊。

```typescript
const subscription = await agent.subscribeToThread({
  resourceId: 'user-123',
  threadId: 'thread-456',
  withRunStatus: true,
})
```

[`thread-run-status`](/reference/streaming/ChunkType#thread-run-status) 資料區塊會單獨指出執行結果，不必依賴執行輸出判斷：

```typescript
const chunk = {
  type: 'thread-run-status',
  runId: 'run-123',
  from: 'AGENT',
  payload: { status: 'success' },
}
```

`status` 可為 `success`、`failed`、`aborted` 或 `suspended`。即時輸出會先於狀態送達。暫停後可繼續執行，同一次執行稍後可以再產生輸出，並回報最終狀態。執行結果不會關閉執行緒訂閱，訂閱會繼續監聽後續的執行。

啟用 `withInitialHistory` 時，第一個資料區塊的酬載是 `{ messages, hasMore, activeRunId }`。`activeRunId` 識別載入初始資料時持有執行緒的執行；若執行緒閒置，則是 `null`。請用 `thread-run-status` 判斷結果。單憑執行緒閒置無法確認執行成功。

啟用 `withRunStatus: true` 後，即使執行在訂閱前便已結束，而且文字已出現在記錄中，仍保留的結果也會送達。稍後才訂閱且同時啟用兩個選項時，每次已結束且仍保留結果的執行都會送出一筆狀態，包括初始記錄頁之外的執行，並不限於最新一次。最終結果會在單次訂閱內去重，暫停通知則依執行區段去重。重新連線會建立新訂閱，可能再次收到同一結果。請依 `runId` 將更新分組，不要把每次收到的資料都視為新回覆。

### 核准 Tool 呼叫 {/* #approve-tool-calls */}

執行暫停等待核准 Tool 呼叫時，請透過 [`client.getAgent().sendToolApproval()`](/reference/client-js/agents#sendtoolapproval) 或[伺服器核准路由](/reference/server/routes#subscription-tool-approval-routes)送出決定。執行繼續後，現有訂閱就會收到輸出。

暫停的執行仍持有執行緒。在它繼續或中止前，嘗試啟動新執行的訊號會收到 `accepted` 回應，其中的動作是 `blocked`。再次訂閱時，待核准請求與暫停通知會重播；已完成並儲存的輸出不會重播。設定 `withRunStatus: true` 後，仍保留的執行結果會送達。[Agent 何時看到輸入](/docs/signals/sending-signals#when-the-agent-sees-your-input)說明執行中收到的輸入何時中斷、何時等待。

### 篩選訂閱中的訊號 {/* #filter-signals-in-a-subscription */}

`hideSignals` 會篩選單一訂閱者收到的訊號區塊。傳入 `true` 可隱藏所有可辨識的訊號，傳入 `false` 則顯示它們，也可以傳入訊號類型陣列。這不會更動模型上下文、已儲存的訊息或共用廣播，也不影響其他訂閱者，且不能作為安全邊界。此選項只適用於程序內的核心訂閱，HTTP 和 `client-js` 的訂閱請求都不支援。

## 停止執行或關閉訂閱 {/* #stop-a-run-or-close-a-subscription */}

[`abort()`](/reference/client-js/agents#subscribetothread) 會要求取消目前的執行。`unsubscribe()` 只關閉訂閱，不會中止執行，因此執行會繼續，你也可以稍後再訂閱。中止時會保留待處理訊號，除非傳入 `clearPendingSignals: true`。

## 重新連線 {/* #reconnect */}

長時間維持的訂閱請使用 `reconnect: true`。傳輸連線關閉或重新連線請求失敗時，`processDataStream()` 會重新訂閱，預設每隔一秒重試，不限次數。收到 `408` 或 `429` 以外的 4xx 回應，或收到 `501` 時，會停止重新連線並使 Promise 遭拒。重試選項請參閱 [`subscribeToThread()` 參考文件](/reference/client-js/agents#subscribetothread)。

重新連線時，可以接續共用 [PubSub 後端](/docs/server/pubsub)還保留的輸出，但無法取回只存放在其他程序記憶體快取中的事件。需要對話記錄時，可用 `withInitialHistory` 重新載入已儲存訊息的最新一頁。

已儲存的訊息不會記下串流中的每個文字片段。重新連線不會重播已完成並儲存的輸出，也無法重建未保留的片段。

執行結果能否取回，取決於 PubSub 後端保留了哪些資料，與記錄頁面的大小無關。修剪已儲存的輸出時，Redis Streams 會保留精簡的終止事件和執行權限中繼資料，但這些資料仍可能因設定的串流長度與閒置 TTL 而遭移除。這些資料無法作為永久的執行稽核記錄，也沒有保證的保留時間。若要在修剪後取回結果，請同時升級 `@mastra/core` 和 `@mastra/redis-streams`。舊版介面卡可能會連同輸出一起刪除終止事件。

### 自訂端點的 SSE 心跳 {/* #sse-heartbeats-for-custom-endpoints */}

若你為執行緒訂閱提供自訂的伺服器傳送事件（SSE）端點，請在串流閒置時定期傳送心跳訊框，以免瀏覽器、代理伺服器或負載平衡器在下一個訊號或模型資料區塊到達前關閉連線。

以下範例每 25 秒傳送一則 SSE 註解：

```typescript title="src/api/subscribe.ts"
const heartbeat = setInterval(() => {
  controller.enqueue(encoder.encode(': keep-alive\n\n'))
}, 25_000)

request.signal.addEventListener('abort', () => {
  clearInterval(heartbeat)
})
```

請搭配使用心跳和用戶端的重新連線機制。心跳能減少閒置時的斷線；若網路或執行環境仍關閉了串流，就可透過重新連線復原。
