# 執行緒流

線程流在同一線程上運行時攜帶Agent的輸出[thread](/docs/memory/message-history#threads-and-resources)。您訂閱一次即可接收模型文字、Tool呼叫和結果、批准請求和錯誤，如下所示[區塊](/reference/streaming/ChunkType)。訂閱在運行之間保持開啟狀態，因此您無需在每次發送輸入時建立新的回應流。

您也可以在訂閱開始時請求儲存的訊息。這可以讓您的應用程式在顯示新輸出之前顯示到目前為止的對話。

## 快速入門 {/* #quickstart */}

在發送輸入之前訂閱，以便您可以從運行開始就接收輸出。本範例使用[`subscribeToThread()`](/reference/client-js/agents#subscribetothread) from the JavaScript client SDK. It needs a running Mastra server with a `support-agent` agent. Configure [Memory](/docs/memory/overview) on that agent if you want to store history.

對於使用的伺服器端程式碼`Agent` instance directly, follow the [Agent quickstart](/docs/signals/overview#use-an-agent) instead.

```typescript title="src/app/chat.ts"
import { MastraClient } from '@mastra/client-js'

const client = new MastraClient({ baseUrl: 'http://localhost:4111' })
const agent = client.getAgent('support-agent')

const subscription = await agent.subscribeToThread({
  resourceId: 'user-123',
  threadId: 'thread-456',
})

await agent.sendMessage({
  message: 'Show the shorter version.',
  resourceId: 'user-123',
  threadId: 'thread-456',
})

await subscription.processDataStream({
  onChunk: chunk => {
    console.log(chunk)
  },
  reconnect: true,
})
```

[`client.getAgent()`](/reference/client-js/mastra-client#methods)選擇伺服器的Agent。[`sendMessage()`](/reference/client-js/agents#sendmessage) returns when Mastra accepts the input. [`processDataStream()`](/reference/client-js/agents#subscribetothread) passes output to `onChunk`, which prints each chunk here. It continues listening after the answer finishes.

## 讀取流 {/* #read-the-stream */}

### 儲存的歷史記錄和活動部件 {/* #stored-history-and-live-parts */}

經過`withInitialHistory: true` to begin with a `thread-history` chunk, which carries the newest page of stored messages in oldest-first order. `perPage` defaults to 40. Subscribers then receive retained parts newer than that history, followed by live parts. History requires memory. Without it, or before the thread has messages, the chunk still arrives first with an empty `messages` array.

### 區塊和運行 {/* #chunks-and-runs */}

使用`runId` to group chunks from the same run. The exception is [`thread-history`](/reference/streaming/ChunkType#thread-history), which has an empty `runId` because its messages can span several runs. The subscription's [`activeRunId()`](/reference/agents/agent#subscribetothreadoptions) returns the active run's ID or `null`.

公開訂閱流包括`AgentChunkType`. `withInitialHistory` adds `ThreadHistoryChunk`, and `withRunStatus: true` adds `ThreadRunStatusChunk`. Both options default to `false`. The [ChunkType reference](/reference/streaming/ChunkType) lists the fields for model output, tool calls and results, approvals, aborts, and errors. To observe queue counts, use [`subscribeThreadEvents()`](/reference/signals/thread-events)分別地。

### 檢測運行何時完成 {/* #detect-when-a-run-finishes */}

經過`withRunStatus: true` to opt in to run outcomes. Existing subscriptions don't receive these chunks by default.

```typescript
const subscription = await agent.subscribeToThread({
  resourceId: 'user-123',
  threadId: 'thread-456',
  withRunStatus: true,
})
```

一個[`thread-run-status`](/reference/streaming/ChunkType#thread-run-status) chunk identifies the run's outcome independently of its output:

```typescript
const chunk = {
  type: 'thread-run-status',
  runId: 'run-123',
  from: 'AGENT',
  payload: { status: 'success' },
}
```

`status`是`success`, `failed`, `aborted`, or `suspended`. Live output arrives before its status. A suspension is resumable: the same run can later produce more output and a final status. A run outcome doesn't close the thread subscription, which continues listening for later runs.

和`withInitialHistory`, the first chunk's payload is `{ messages, hasMore, activeRunId }`. `activeRunId` identifies the run holding thread ownership during hydration, or is `null` when idle. Use `thread-run-status` to determine the outcome. An idle thread alone doesn't indicate success.

和`withRunStatus: true`, retained outcomes are delivered even when a run finished before you subscribed and its text is already in history. A late subscriber using both options receives one status for every still-retained finished run, including runs outside the initial history page. It doesn't receive only the newest run's status. Final outcomes are deduplicated within one subscription. Suspension notifications are deduplicated per execution segment. A reconnect creates a new subscription and may deliver the same outcome again. Group updates by `runId` rather than treating each delivery as a new answer.

### 批准Tool調用 {/* #approve-tool-calls */}

當運行暫停以等待Tool批准時，請發送您的決定[`client.getAgent().sendToolApproval()`](/reference/client-js/agents#sendtoolapproval) or the [server approval route](/reference/server/routes#subscription-tool-approval-routes). The existing subscription receives output when the run resumes.

暫停的運行保留執行緒的所有權。嘗試開始新運行的訊號會收到`accepted` action of `blocked` until the paused run resumes or is aborted. Pending approvals and suspensions are replayed when you subscribe again. Completed stored output isn't replayed. Retained run outcomes are delivered when `withRunStatus: true`. [When the agent sees your input](/docs/signals/sending-signals#when-the-agent-sees-your-input) covers the interrupt and wait rules for input that arrives during a run.

### 過濾訂閱中的訊號 {/* #filter-signals-in-a-subscription */}

`hideSignals`過濾一個訂閱者的訊號塊。經過`true` to hide every recognized signal, `false` to show them, or an array of signal types. It doesn't change model context, stored messages, shared broadcasts, or other subscribers, and it isn't a security boundary. The option exists on the in-process core subscription. HTTP and `client-js` subscription requests don't support it.

## 停止運行或關閉訂閱 {/* #stop-a-run-or-close-a-subscription */}

[`abort()`](/reference/client-js/agents#subscribetothread)請求取消目前運行。`unsubscribe()` closes the subscription without aborting, so the run continues and you can subscribe again later. Pending signals survive an abort unless you pass `clearPendingSignals: true`.

## 重新連接 {/* #reconnect */}

使用`reconnect: true` for long-lived subscriptions. `processDataStream()` then resubscribes when the transport closes or a reconnect request fails, retrying indefinitely with a one-second delay by default. A 4xx other than `408` or `429`, or a `501`, stops reconnecting and rejects. See the [`subscribeToThread()` reference](/reference/client-js/agents#subscribetothread) for retry options.

[PubSub backend](/docs/server/pubsub) still retains. It can't recover events held only in another process's in-memory cache. Use `withInitialHistory` to reload the newest page of stored messages when you need conversation history.

儲存的訊息並不是每個串流文字片段的記錄。重新連接不會重播已完成的儲存輸出或重建未保留的片段。

結果恢復受 PubSub 後端保留的限制，而不是受歷史頁面大小的限制。當保存的輸出被修剪時，Redis Streams 會保留緊湊的終端事件和執行權限元數據，但其配置的流長度和空閒 TTL 仍然可以驅逐它們。這不是永久的運行審核日誌或保證的時間視窗。升級兩者`@mastra/core` and `@mastra/redis-streams` for recovery after trimming. Older adapters may delete terminal events with the output.

### 自訂端點的 SSE 心跳 {/* #sse-heartbeats-for-custom-endpoints */}

如果您為執行緒訂閱公開自己的伺服器傳送事件 (SSE) 端點，請在流空閒時定期發送心跳幀。這可防止瀏覽器、Agent程式和負載平衡器在下一個訊號或模型區塊到達之前關閉連線。

以下範例每 25 秒發送 SSE 評論：

```typescript title="src/api/subscribe.ts"
const heartbeat = setInterval(() => {
  controller.enqueue(encoder.encode(': keep-alive\n\n'))
}, 25_000)

request.signal.addEventListener('abort', () => {
  clearInterval(heartbeat)
})
```

將心跳與客戶端重新連接邏輯結合使用。心跳減少空閒斷開，而重新連接會在網路或運行時仍然關閉流時恢復。
