# 通知

通知會記錄待 Agent 處理的事件，例如建置失敗、提取要求的留言或背景工作完成。Mastra 將通知持久保存在獨立於對話訊息的收件匣。即使通知送達時 Agent 正忙，之後仍可讀取。

傳送策略決定要立即送出事件、與其他事件彙整成摘要，或留待稍後處理。Agent 可以在收件匣中讀取、略過或封存記錄。傳送可能失敗，策略也可能捨棄事件，因此保存記錄無法保證 Agent 會處理它。記錄的生命週期和策略選項請參閱[通知參考](/reference/signals/notifications)。

事件需要收件匣和傳送機制時，請使用通知。使用者輸入請用 [`sendMessage()`](/reference/agents/agent#sendmessagemessage-options)，應用程式的上下文變更請用[狀態訊號](/docs/signals/state-signals)，只供單次模型請求使用的上下文則用[暫態反應式訊號](/docs/signals/sending-signals#send-context-from-a-system)。[`sendSignal({ type: 'notification' })`](/reference/agents/agent#sendsignalsignal-options) 會傳送事件上下文，但不建立收件匣記錄，也不提供記錄的重試機制。

## 快速入門 {/* #quickstart */}

呼叫 [`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options) 建立記錄並套用傳送策略。若要讓 Agent 讀取待處理記錄，請依照[使用收件匣](#work-with-the-inbox)加入 [`createNotificationInboxTool()`](/reference/signals/create-notification-inbox-tool)。

通知記錄需要支援 `notifications` 網域的儲存配接器。以下範例使用 libSQL，先訂閱對話執行緒，再送出高優先順序的 CI 失敗通知：

```typescript title="src/mastra/notifications.ts"
import { Mastra } from '@mastra/core'
import { Agent } from '@mastra/core/agent'
import { LibSQLStore } from '@mastra/libsql'
import { Memory } from '@mastra/memory'

const storage = new LibSQLStore({
  id: 'mastra',
  url: 'file:./mastra.db',
})

const ciAgent = new Agent({
  id: 'ci-agent',
  name: 'CI Agent',
  instructions: 'Triage CI failures and explain what broke.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory({ storage }),
})

const mastra = new Mastra({
  agents: { ciAgent },
  storage,
})

const agent = mastra.getAgent('ciAgent')
const thread = {
  resourceId: 'user_123',
  threadId: 'thread_456',
}

const subscription = await agent.subscribeToThread(thread)

const { record, decision } = await agent.sendNotificationSignal(
  {
    source: 'github',
    kind: 'ci-status',
    priority: 'high',
    summary: 'CI failed on main: 3 tests failed in the API suite.',
    payload: {
      repository: 'acme/app',
      branch: 'main',
      runId: '123456',
    },
    dedupeKey: 'github:acme/app:main:ci',
  },
  thread,
)

console.log(record.status, decision.action)

for await (const chunk of subscription.stream) {
  console.log(chunk)

  if (chunk.type === 'finish') break
}
```

對話執行緒閒置時，高優先順序的通知會立即傳送並啟動一次執行。執行緒仍在運作時，Mastra 會先彙整通知，等到閒置再傳送完整通知。訂閱會以[執行緒串流](/docs/signals/thread-streams)區塊的形式收到摘要和完整通知。

## 通知記錄 {/* #notification-records */}

收到通知時，`sendNotificationSignal()` 會建立記錄，或將通知合併至符合條件的待處理記錄，接著檢查傳送策略。若排定稍後傳送，派送器會在時間一到時讀取記錄並送出通知或摘要。

儲存的記錄包含路由資訊、優先順序、狀態、傳送嘗試和原始 `payload`。模型會收到由 `summary` 和屬性組成的 XML 元素，系統不會自動傳入 `payload`。

記錄的狀態可以是 `pending`、`delivered`、`seen`、`dismissed`、`archived`、`discarded` 或 `failed`。送出摘要後，記錄仍為 `pending`，因為摘要只會告知模型有這些記錄，不會將它們標示為已傳送。參考文件列出所有[記錄欄位](/reference/signals/notifications#notification-records)和[狀態](/reference/signals/notifications#priorities-and-statuses)。

## 建立與合併記錄 {/* #create-and-coalesce-records */}

`sendNotificationSignal()` 接受單筆通知或通知陣列。各項目會分別建立，再由儲存層判斷能否合併至現有的待處理記錄。

使用 `dedupeKey` 識別可能重複送達的同一事件。使用 `coalesceKey` 將相關事件合併成一筆待處理記錄。兩種索引鍵採用相同的比對規則。

只有處於待處理狀態，且執行緒、來源、種類、Agent 和資源都相同的記錄才會納入合併。[通知參考](/reference/signals/notifications#coalescing-pending-records)說明哪些欄位會合併及其優先順序。

## 設定儲存與派送器 {/* #storage-and-dispatcher-setup */}

通知記錄需要支援 `notifications` 網域的儲存配接器，例如 [libSQL](/integrations/databases/libsql)、[PostgreSQL](/integrations/databases/postgresql) 或 [MongoDB](/integrations/databases/mongodb)。缺少該網域時，`sendNotificationSignal()` 會擲出錯誤，避免記錄在沒有提示的情況下遭捨棄。

排程派送預設開啟，由 Workflow 排程器執行。請在 `Mastra` 執行個體上設定：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  agents: { ciAgent },
  storage,
  notifications: {
    dispatch: {
      enabled: true,
      cron: '*/1 * * * *',
      batchSize: 100,
    },
  },
})
```

預設值為 `enabled: true`、`cron: '*/1 * * * *'`（每分鐘一次）和 `batchSize: 100`。只有在延後傳送通知或彙整摘要時，應用程式才會按需建立派送排程，並啟動 Workflow 排程器。設定 `enabled: false` 即可停用。

## 傳送策略 {/* #delivery-policy */}

每筆記錄在收到時都會進行策略判定，派送時也可能再判定一次。內建策略依據優先順序和執行緒狀態：

| 優先順序 | 閒置執行緒 | 運作中的執行緒 |
| - | - | - |
| `urgent` | 立即傳送 | 立即傳送 |
| `high` | 立即傳送 | 先傳送摘要，等到閒置再傳送通知 |
| `medium` | 立即傳送 | 批次彙整為摘要 |
| `low` | 批次彙整為摘要 | 批次彙整為摘要 |

預設行為不符合需求時，可在 Agent 上設定策略。來源規則會先於優先順序規則執行，因此可將事件過多的來源彙整為摘要，其餘通知照常傳送：

```typescript title="src/mastra/agents/ci-agent.ts"
import { Agent } from '@mastra/core/agent'
import { Memory } from '@mastra/memory'

// storage from the Quickstart
export const ciAgent = new Agent({
  id: 'ci-agent',
  name: 'CI Agent',
  instructions: 'Triage CI failures and explain what broke.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory({ storage }),
  notifications: {
    deliveryPolicy: {
      sources: {
        github: 'summarize',
      },
      priorities: {
        urgent: 'deliver',
        low: 'discard',
      },
    },
  },
})
```

Mastra 會依下列順序評估策略：

1. 自訂 `decide()` 函式。
1. `sources`，比對 `record.source`。
1. `priorities`，比對 `record.priority`。
4. `default`.
1. 內建的優先順序策略。

`decide()` 會在收到記錄時執行。如果第一次判定為延後傳送或排定摘要，傳送時會再執行一次。傳送時間與方式由已儲存的排程決定，傳送時只採用新判定的 `streamOptions` 和 `hold`。請讓 `decide()` 保持無副作用。

## 派送 {/* #dispatch */}

派送器會讀取到期記錄，依 `agentId`、`resourceId` 和 `threadId` 將摘要分組，並透過執行緒的執行環境發出訊號。

| 判定 | 結果 |
| - | - |
| `deliver` | 立即傳送完整通知 |
| `queue` | 保持待處理，留待後續派送 |
| `summarize` | 立即傳送摘要，或於 `summaryAt` 傳送 |
| `defer` | 保持待處理，直到 `deliverAt` |
| `persist` | 只儲存記錄，不發出訊號 |
| `discard` | 將記錄標示為已捨棄 |

判定包含 `hold` 時，記錄會留給另一個處理程序的派送器，不計入傳送嘗試次數。

### 摘要 {/* #summaries */}

摘要可避免忙碌的執行緒短時間內收到大量個別通知。模型會看到精簡的摘要：

```xml
<notification-summary pending="10">github: 3, email: 5, slack: 2</notification-summary>
```

完整通知會以該筆記錄的摘要作為內容：

```xml
<notification source="github" kind="ci-status" priority="high" status="delivered">CI failed on main: 3 tests failed in the API suite.</notification>
```

傳送摘要會清除 `summaryAt` 並設定 `summarySignalId`，記錄維持 `pending` 且仍可讀取。傳送完整通知則會設定 `deliveredSignalId`，並將記錄標示為 `delivered`。

傳送摘要不會將記錄標示為已傳送。Agent 若需要完整內容，可從收件匣讀取記錄。讀取時可注入完整訊號，並將記錄標示為 `seen`，避免之後重複傳送。

### 重試與失敗 {/* #retries-and-failures */}

傳送失敗會增加 `deliveryAttempts`，並記錄 `lastDeliveryAttemptAt` 和 `lastDeliveryError`。記錄維持待處理狀態，下輪派送便可重試。

五次嘗試失敗後，記錄會轉為 `failed`，不再排入派送。這個上限以 `MAX_NOTIFICATION_DELIVERY_ATTEMPTS` 匯出。`hold` 會讓記錄維持待處理且不計入嘗試次數，其他派送器仍可接手。

若自訂策略在首次收到通知時擲出錯誤，記錄會維持待處理，`deliverAt` 會設為立即傳送並記一次失敗，讓派送器可以重試。

## 使用收件匣 {/* #work-with-the-inbox */}

為 Agent 提供收件匣 Tool，即可讓它檢視記錄，無須公開儲存 API：

```typescript title="src/mastra/agents/ci-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createNotificationInboxTool } from '@mastra/core/notifications'

const notificationsStorage = await storage.getStore('notifications')

export const ciAgent = new Agent({
  // ...id, instructions, model, memory, and notifications from the policy example
  tools: {
    notificationInbox: createNotificationInboxTool({ storage: notificationsStorage }),
  },
})
```

這個 Tool 支援 `list`、`read`、`search`、`markSeen`、`dismiss` 和 `archive`。列出或搜尋時，傳回的未讀記錄會標示為 `seen`，包括 `failed` 記錄，讓 Agent 得知系統已停止嘗試傳送。`list` 預設傳回待處理、已傳送和失敗的記錄。`search` 涵蓋所有狀態。`read` 只處理待處理與已傳送的記錄，因此會略過 `failed` 記錄。若記錄和呼叫端 Agent 都未提供 `resourceId`，使 `read` 無法傳送，記錄會維持待處理狀態。

收到摘要後，可用 `read` 取得完整內容。它會透過通知訊號傳送選定記錄的完整內容，而非透過一般 Tool 輸出。即使呼叫只傳回簡短的狀態訊息，Agent 仍可在執行緒中看到相關上下文。

## Agent 與用戶端介面 {/* #agent-and-client-surfaces */}

[`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options) 是建立持久通知記錄的標準方法。它會傳回記錄與策略判定。若發出訊號，還會傳回 `accepted`、`signal` 和 `persisted`，與[傳送訊號](/docs/signals/sending-signals)所述的其他方法一致。

JavaScript 用戶端 SDK 可透過 [`client.getAgent().sendSignal()`](/reference/client-js/agents#sendsignal) 傳送通知格式的上下文。這個做法會略過收件匣儲存，只適用於無須記錄、重試或稍後讀取的事件。若要透過 HTTP 建立持久記錄，請使用 AgentController Session 的通知路由，它會轉交給 `sendNotificationSignal()`。請參閱 [Session 參考](/reference/agent-controller/session)和 [Agent Controller](/docs/harness/agent-controller)。
