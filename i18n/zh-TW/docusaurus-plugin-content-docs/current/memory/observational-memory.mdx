# 觀察記憶

**添加於：** `@mastra/memory@1.1.0`

Observational Memory（OM）讓 Agent 能在同一個 thread 持續工作，直到任務完成，同時維持精簡、聚焦且適合 prompt 快取的脈絡。**Observer** Agent 會在背景將較早的訊息整理成簡短、附日期的觀察紀錄；紀錄累積後，**Reflector** Agent 會進一步濃縮。Agent 能完整看到近期訊息，並以觀察紀錄讀取更早的內容。

只要 Agent 的工作超過一次性摘要或單一 Workflow 步驟，就適合使用 OM。多步驟 Agent 都能受益，包括聊天助理、程式開發 Agent、瀏覽器 Agent，以及持續數小時的支援對話。

## 快速入門 {/* #quickstart */}

安裝 `@mastra/memory` 與[儲存轉接器](/docs/storage#supported-providers)。以下範例使用 `@mastra/libsql`，將資料儲存在本機的 `memory.db` 檔案。

```bash npm2yarn
npm install @mastra/memory@latest @mastra/libsql@latest
```

OM 需要支援它的儲存（`@mastra/libsql`, `@mastra/pg`, `@mastra/mysql`, `@mastra/mongodb`, `@mastra/convex`或者`@mastra/oracledb`)，每個呼叫都有一個線程，以及`observationalMemory: true`。該腳本將記憶體儲存在本地 LibSQL 檔案中，並在一個執行緒上呼叫Agent兩次：

```typescript title="src/observational-memory.ts"
import { Agent } from '@mastra/core/agent'
import { LibSQLStore } from '@mastra/libsql'
import { Memory } from '@mastra/memory'

const memory = new Memory({
  storage: new LibSQLStore({
    id: 'memory-storage',
    url: 'file:./memory.db',
  }),
  options: {
    // highlight-next-line
    observationalMemory: true,
  },
})

const agent = new Agent({
  id: 'memory-agent',
  name: 'Memory Agent',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  memory,
})

const memoryOptions = {
  resource: 'user-123',
  thread: 'conversation-123',
}

const first = await agent.generate('Remember that my favorite color is blue.', {
  memory: memoryOptions,
})
console.log(first.text)

const second = await agent.generate('What is my favorite color?', {
  memory: memoryOptions,
})
console.log(second.text)
```

`resource` 識別使用者或實體，`thread` 識別對話。重複使用兩者即可延續對話。這段簡短對話尚未觸發觀察；當 thread 的訊息歷史超過 30,000 個 token，OM 才開始以觀察紀錄取代較早的訊息。

若 Mastra 實例已設定儲存空間，可在 `Memory` 省略 `storage`，它會沿用實例的設定。

若要查看 OM 的運作，請在 [Studio](/docs/studio/overview) 開啟 Agent 的 **Memory** 分頁。進度列會顯示訊息與觀察紀錄距離各自門檻還有多遠；**Analyze observations** 可開啟觀察日誌與歷史。

## 好處 {/* #benefits */}

* **長任務停留在一個執行緒中**：Agent繼續工作超過其上下文限制，而不會壓縮，也不會丟失早期的決策。
- **prompt 快取**：觀察紀錄會接在穩定的前綴之後，而非每回合重新檢索，因此 Provider 可從 prompt 快取提供每次請求的大部分內容。請參閱[成本與延遲](#cost-and-latency)。
* **較小的背景**：原始訊息和Tool結果壓縮為密集的觀察日誌，從而降低每次呼叫的成本和延遲。
* **更少的上下文腐爛**：Agent讀取重要的內容，而不是陳舊的Tool輸出和噪音，這使其能夠在長時間會話中繼續執行任務。

Mastra 自身的 Agent 也使用 OM。終端機程式開發 Agent [Mastra Code](https://code.mastra.ai/) 藉此讓工作階段持續數天而不必壓縮脈絡。[Mastra Factory](https://factory.mastra.ai/) 的規劃、實作與審查工作階段都在 Mastra Code 上執行。每個 Agent 都能從頭到尾保留長期任務的脈絡。

## 它是如何運作的 {/* #how-it-works */}

每次Agent回應時，它都會讀取一個上下文窗口，其中包含系統提示字元、最近的訊息和任何注入的上下文。它攜帶的原始歷史越多，它的性能就越差，大多數代幣不再需要繼續執行任務。 OM 壓縮了該歷史。

### 觀察結果 {/* #observations */}

當 thread 中尚未觀察的訊息超過 `observation.messageTokens`（預設 30,000）時，Observer 會寫出觀察紀錄：簡短且附日期的事件筆記。

```md
Date: 2026-01-15

- 🔴 12:10 User is building a Next.js app with Supabase auth, due in 1 week (meaning January 22nd 2026)
  - 🔴 12:10 App uses server components with client-side hydration
  - 🟡 12:12 User asked about middleware configuration for protected routes
  - 🔴 12:15 User stated the app name is "Acme Dashboard"
```

觀察到的訊息離開上下文窗口，觀察結果取代它們，通常小 5 到 40 倍。每個頁面快照看到 50,000 個令牌的瀏覽器Agent最終會攜帶數百個有關頁面上的內容及其用途的令牌。

同步觀察期間，Observer 也會記錄**目前任務**與**建議回覆**，協助 Agent 接續工作。啟用 `observation.threadTitle` 後，話題變更時還能建議新的 thread 標題。

Observer 能看到所檢視歷史中的附件。逐字稿會保留 `[Image #1: reference-board.png]` 等佔位文字，附件本身也會隨文字一同傳入。無法讀取附件的 Observer 請參閱[選擇模型](#choosing-models)。

### 反思 {/* #reflections */}

當觀察紀錄超過 `reflection.observationTokens`（預設 40,000）時，Reflector 會重寫整份日誌：合併相關項目、進一步濃縮較早項目，並保留近期細節。其輸出成為新日誌，後續觀察紀錄接續附加。無論 thread 執行多久，日誌大小都會維持在反思門檻附近。

Agent的上下文分為三層：

1. **最近消息**：目前任務的確切對話。
2. **觀察結果**：自上次反射以來觀察者所看到的情況。
3. **反思**：之前所有內容的濃縮日誌。

### 背景如何隨時間變化 {/* #how-context-changes-over-time */}

在預設設定下，上下文視窗循環增大和縮小：

<OmContextOverTimeImage />

1. **0 到 30,000 個代幣**：消息历史记录增长。在後台，觀察者準備每 6,000 個令牌的觀察結果（`observation.bufferTokens: 0.2`).
1. **達到 30,000 個 token**：已準備的觀察紀錄啟用。已觀察的訊息移出脈絡，保留約 6,000 個 token 的近期訊息（`observation.bufferActivation: 0.8` 表示保留門檻的 20%）。
3. **重複**：歷史成長回到 30,000，然後再次縮小。每個週期都會在觀察日誌中添加一點內容。
4. **觀察次數達 40,000**：Reflector 將日誌重寫為較小的日誌。

門檻標示開始處理的時機。若背景觀察進度落後，歷史訊息可能超過 30,000 個 token。達到 `observation.blockAfter`（預設 `1.2`，即 36,000 個 token）時，Agent 會等待一次同步觀察。請參閱[緩衝進度落後時](/reference/memory/observational-memory#when-buffering-falls-behind)。

token 數量是本機 `tokenx` 的估算值。Provider 自身的計數通常較高，尤其訊息包含附件時。

### 上下文溢出恢復 {/* #context-overflow-recovery */}

在 OM 估計值達到門檻前，Provider 可能就因請求超出脈絡視窗而拒絕。此時 OM 會啟用已準備好的觀察紀錄、觀察所有待處理內容，並以縮小後的脈絡重試請求一次。此功能預設啟用；設定 `observation.observeOnContextOverflow: false` 可改為讓錯誤傳至應用程式程式碼。

## 選擇型號 {/* #choosing-models */}

Observer 與 Reflector 是與主 Agent 同時執行的模型呼叫。兩者預設都使用 `model: 'auto'`，每次執行各自角色時重新選擇模型：

1. 若 Google 可用（已設定 `GOOGLE_GENERATIVE_AI_API_KEY`，或你的 `canUseProvider` 函式對 `'google'` 回傳 `true`），使用 `google/gemini-2.5-flash`。
1. 否則使用與主模型相同 Provider 的低成本模型，例如 Anthropic Agent 使用 `anthropic/claude-haiku-4-5`。
3. 否則，主模型本身。

`auto` 會讀取主模型的 `provider/model` ID。若無法得知該 ID，例如模型是以自訂 URL、API key 或閘道建立，`auto` 會沿用主模型，因為無法確定同系列的其他模型也能走相同路徑。

設定 `model`，讓兩個角色使用同一模型：

```typescript
const memory = new Memory({
  options: {
    observationalMemory: {
      model: 'deepseek/deepseek-flash',
    },
  },
})
```

選擇脈絡視窗夠大（至少 128,000 個 token），且速度足以在背景執行的模型。Mastra 已測試 `google/gemini-2.5-flash`、`__GATEWAY_OPENAI_MODEL_LUNA__`、`__GATEWAY_ANTHROPIC_MODEL_HAIKU__` 與 `deepseek/deepseek-flash`。

若兩個角色要使用不同模型，應分別設定 `observation.model` 與 `reflection.model`，並省略頂層 `model`；兩者同時設定會擲出錯誤。有些模型保留過多細節，反思結果可能仍超過門檻；測試中的 `google/gemini-2.5-flash` 就出現過這種情況。常見搭配是讓 Observer 使用保留細節的模型，Reflector 則使用更容易濃縮資訊的模型，例如 `deepseek/deepseek-flash`。請參閱[為不同 Agent 指定模型](/reference/memory/observational-memory#different-models-per-agent)。

### {/* #tune-automatic-selection */}

以下 `observationalMemory` 選項會影響 `auto` 的選擇：

* `autoModels`：例如，替換Provider的低成本選擇`{ openai: '__GATEWAY_OPENAI_MODEL_LUNA__' }`.
- `canUseProvider`：當憑證依租戶或請求提供，而非放在伺服器環境時，告訴 `auto` 目前請求是否能使用某個 Provider。函式會收到 Provider ID 與 `{ requestContext }`。
* `resolveModel`：使用您自己的憑證或路由自行建立所選模型。它接收具体的模型 ID，从不`'auto'`.

```typescript
const memory = new Memory({
  options: {
    observationalMemory: {
      autoModels: { openai: '__GATEWAY_OPENAI_MODEL_LUNA__' },
      canUseProvider: (provider, { requestContext }) => hasCredentials(provider, requestContext),
      resolveModel: (modelId, { requestContext }) => createRoutedModel(modelId, requestContext),
    },
  },
})
```

`@mastra/memory` 的 `resolveAutoModelId(mainModelId, { autoModels })` 會回傳 `auto` 將選用的模型，可用來在設定介面顯示實際生效的模型。

### 代幣分層模型 {/* #token-tiered-models */}

**添加於：** `@mastra/memory@1.10.0`

`ModelByInputTokens`

```typescript
import { Memory, ModelByInputTokens } from '@mastra/memory'

const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        model: new ModelByInputTokens({
          upTo: {
            5_000: 'openrouter/mistralai/ministral-8b-2512',
            20_000: 'openrouter/mistralai/mistral-small-2603',
            40_000: '__GATEWAY_OPENAI_MODEL_LUNA__',
            1_000_000: '__GATEWAY_GOOGLE_MODEL_FLASH__',
          },
        }),
      },
      reflection: {
        model: new ModelByInputTokens({
          upTo: {
            20_000: '__GATEWAY_OPENAI_MODEL_LUNA__',
            100_000: 'deepseek/deepseek-flash',
          },
        }),
      },
    },
  },
})
```

每一層都須指定具體的模型 ID，不能使用 `'auto'`。每個 `upTo` 鍵都是包含邊界值的上限。超過最大鍵的呼叫會擲出錯誤，因此最後一層應涵蓋預期的最大輸入。

### 附件和純文字Observer {/* #attachments-and-text-only-observers */}

預設情況下，Observer 會接收圖片與 PDF（`observation.observeAttachments: ['image/*', 'application/pdf']`）。其他附件不會傳入，但佔位文字仍保留在逐字稿中。可依 Observer 模型能處理的附件類型調整此設定：

* `false`
* `true`: 發送每個附件。
- MIME 類型清單，例如 `['image/*']`：只傳入符合條件的附件。比對不區分大小寫，`*` 可比對任意子類型。
* `'auto'`

```typescript
const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        model: 'deepseek/deepseek-flash',
        observeAttachments: false,
      },
    },
  },
})
```

相同的篩選規則也適用於 Tool 結果中的圖片與檔案。Agent 標記為無法使用的附件（因為已無法重新下載）不會傳給 Observer。請參閱[附件下載失敗](/docs/agents/processors#recover-from-attachment-download-failures)。

## 成本和延遲 {/* #cost-and-latency */}

每一次觀察和反思都是一次模型呼叫。預設情況下，線程大約每 6,000 個新訊息令牌就會調用一次 Observer 調用，而每當日誌達到 40,000 個令牌時，線程就會調用一次 Reflector。作為回報，每個主Agent呼叫都會讀取最多數萬個令牌的上下文，而不是整個執行緒。觀察前綴很少更改，因此提示快取會繼續工作：使用者通常會看到 OM 的提示快取命中率為 97% 到 99%。



|設定|預設 |它控制什麼 |
| - | - | - |
| `observation.bufferTokens` | `0.2` | Observer 在背景執行的頻率：可設為 `messageTokens` 的比例（預設門檻下，`0.2` 表示每 6,000 個 token 一次），或設為 `5000` 等絕對 token 數。設為 `false` 可關閉背景緩衝。 |
| `observation.bufferActivation` | `0.8` | 啟用觀察紀錄時清除訊息視窗的比例。`0.8` 會保留 `messageTokens` 的 20%；較低的值會保留更多近期訊息。 |
| `observation.blockAfter` | `1.2` | 緩衝進度落後時，Agent 開始等待同步觀察的門檻。可設為 `messageTokens` 的倍數（`1.2` 表示 36,000 個 token），或設為不小於 100 的絕對數量。`1` 表示達到 `messageTokens` 時進行同步觀察。 |

若要變更 OM 觀察和反映的時間，請設定閾值：

```typescript
const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        messageTokens: 30_000,
      },
      reflection: {
        observationTokens: 40_000,
      },
    },
  },
})
```

### 長時間運行Tool調用 {/* #long-runs-of-tool-calls */}

執行長鏈Tool呼叫的Agent（例如編碼和瀏覽器Agent）會在每個步驟重新發送相同的不斷增長的前綴，並且Provider從提示快取中提供大部分前綴。對於這些Agent，將觀察閾值提高到遠高於預設值，例如提高到 60,000 到 80,000 個令牌，這樣 OM 壓縮的頻率就會降低，並且每次運行的更多內容都會被快取：

```typescript
const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        messageTokens: 70_000,
      },
    },
  },
})
```

讓門檻保持在主模型的脈絡視窗內。`bufferTokens`、`bufferActivation` 與 `blockAfter` 預設都是 `messageTokens` 的比例，因此會隨之調整。

### 提示快取過期時激活 {/* #activate-when-the-prompt-cache-expires */}

prompt 快取一旦過期，下次請求仍須為整份脈絡付出完整成本。`activateAfterIdle` 可在 thread 閒置達指定時間後啟用已準備好的觀察紀錄，讓暫停後的請求送出較小、已濃縮的脈絡。此選項預設未設定。設為 `'auto'` 時，會採用目前 Provider 的 prompt 快取 TTL（例如 Anthropic 為 5 分鐘，DeepSeek 為 1 小時）：

```typescript
const memory = new Memory({
  options: {
    observationalMemory: {
      activateAfterIdle: 'auto',
    },
  },
})
```

固定時長、依 Provider 設定，以及 Provider 變更時啟用的說明請參閱[提前啟用](/reference/memory/observational-memory#early-activation)。

### 同步觀察 {/* #synchronous-observation */}

若要改為同步觀察，請設定 `observation.bufferTokens: false`。這會關閉觀察與反思的背景緩衝，Agent 會在每次操作期間暫停等候。

`shareTokenBudget: true` 讓訊息歷史借用尚未使用的觀察預算，因此日誌較小時，觀察開始前最多可保留約 70,000 個 token 的訊息。它需要設定 `observation.bufferTokens: false`。請參閱[共用 token 預算](/reference/memory/observational-memory#shared-token-budget)。

## 線程和跨線程內存 {/* #threads-and-cross-thread-memory */}

### 線程範圍（預設） {/* #thread-scope-default */}

每個 thread 都有各自的觀察紀錄。每次呼叫都需要 thread；若未提供，OM 會擲出 `OBSERVATIONAL_MEMORY_THREAD_ID_REQUIRED`，避免無關的 thread 共用一份觀察紀錄。

:::warning
客戶端應用程式呼叫 Agent 時，只送出新訊息，不要送出完整對話。OM 已從儲存空間載入 thread 歷史。Mastra 如何處理重複傳入的歷史，以及何時使用 `retainFullInput`，請參閱[訊息歷史](/docs/memory/message-history)。
:::

OM 預設只記住單一 thread 的內容。若要讓 Agent 存取同一使用者的其他 thread，可啟用[檢索模式](#retrieval-mode)。它會提供 `recall` Tool，用來讀取觀察紀錄背後的原始訊息，以及同一 resource 的其他 thread。

### 檢索方式 {/* #retrieval-mode */}

觀察紀錄不保留原始措辭。啟用檢索模式後，每組觀察紀錄仍會連結至來源訊息，Agent 可用 `recall` Tool 讀回原文，包括確切措辭與 Tool 輸出。

`retrieval: true`讓Agent瀏覽原始訊息、列出資源的執行緒並讀取其他執行緒。不需要向量存儲。

`retrieval: { vector: true }` 會使用 `Memory` 設定的向量儲存空間與 embedder，為觀察紀錄群組加入語意搜尋。若向量儲存空間會自行產生 embedding，就不需設定 `embedder`。請參閱[伺服器端 embedding](/docs/memory/semantic-recall#server-side-embeddings)。新建的觀察紀錄群組會在背景建立索引。

```typescript
const memory = new Memory({
  storage,
  vector: myVectorStore,
  embedder: myEmbedder,
  options: {
    observationalMemory: {
      retrieval: { vector: true },
    },
  },
})
```

recall Tool 的預設 scope 為 `'resource'`，因此能存取該 resource 的所有 thread。設定 `retrieval: { scope: 'thread' }` 可限制為目前 thread。使用 `retrieval.instructions` 在內建 recall 指令後加入應用程式專屬指引，例如「目前對話已有答案時，優先使用目前對話」。

各模式、詳細程度與分頁說明請參閱 [recall Tool 參考](/reference/memory/observational-memory#recall-tool)。

### 資源範圍（已棄用） {/* #resource-scope-deprecated */}

:::warning[Deprecated]

`scope: 'resource'` 已棄用，將於未來版本移除。首次以 resource scope 建立 OM 時，Mastra 會記錄警告。移除 `scope` 選項即可使用 thread scope；跨 thread 延續性請使用[檢索模式](#retrieval-mode)。目前處於 alpha 階段的 [Knowledge](/docs/knowledge/overview) 可讓 Agent 跨 thread 共用資訊，並計畫取代 resource scope。

:::

資源範圍在資源的所有執行緒之間共用一個觀察記錄。它的工作效果比線程作用域差得多：

* **提示快取**：觀察任何執行緒都會更改每個其他執行緒的上下文，這會破壞其快取的前綴。
* **Agent了解**：每個執行緒都可以看到來自其他執行緒的觀察結果，並且Agent可以繼續另一個執行緒啟動的工作。
* **表現**：來自所有執行緒的未觀察到的訊息會一起處理，這對於具有多個執行緒的使用者來說很慢。資源範圍也會關閉非同步緩衝。

切換到執行緒範圍不會遷移資源範圍的觀察值。每個執行緒都使用自己的執行緒範圍記錄（如果有的話），或開始為空，並且不會再次觀察到在資源範圍下已觀察到的訊息。

## 擷取器 {/* #extractors */}

提取器在觀察的同時保留特定的值。內建當前任務、建議回應和線程標題使用相同的管道。此範例提取一個小的用戶設定檔：

```typescript title="src/mastra/agents/assistant.ts"
import { Agent } from '@mastra/core/agent'
import { Extractor, Memory } from '@mastra/memory'
import { z } from 'zod'

const memory = new Memory({
  options: {
    observationalMemory: {
      observation: {
        extract: [
          new Extractor({
            name: 'User profile',
            instructions: 'Extract stable user profile facts that should be remembered.',
            schema: z.object({
              preferredName: z.string().optional(),
              timezone: z.string().optional(),
              tools: z.array(z.string()).optional(),
            }),
          }),
        ],
      },
    },
  },
})

export const assistant = new Agent({
  id: 'assistant',
  name: 'Assistant',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  memory,
})
```

帶有 `schema` 的 extractor 會在後續結構化輸出請求中執行。沒有 schema 時則是行內字串 extractor，直接在 Observer 或 Reflector 的回應中輸出：

```typescript
new Extractor({
  name: 'Mood',
  instructions: 'Extract the user mood as a short phrase.',
})
```

預設情況下，extractor 在後續執行時能看到上次擷取的值。設定 `includePreviousExtraction: false` 可隱藏該值：

```typescript
new Extractor({
  name: 'Latest blocker',
  instructions: 'Extract any blockers the agent is running into.',
  includePreviousExtraction: false,
})
```

當 `instructions` 與 `schema` 依賴 memory 實例或請求脈絡等執行階段資訊時，也可將它們定義為函式：

```typescript
new Extractor({
  name: 'Workspace summary',
  instructions: ({ memory }) =>
    memory ? 'Extract workspace facts for this memory instance.' : 'Extract workspace facts.',
})
```

在數值持久保存前，可使用 `onExtracted` 將其正規化：

```typescript
new Extractor({
  name: 'Project status',
  instructions: 'Extract the current project status.',
  schema: z.string(),
  onExtracted: ({ current }) => current.trim().toLowerCase(),
})
```

`onExtracted` 也會收到 `previous` 與 `sendSignal`，可在數值變動時通知 Agent。此掛鉤每次擷取都會執行，因此傳送 signal 前應比較 `previous` 與 `current`；否則每次觀察都會再次傳送。

extractor 失敗會在 OM 標記中回報，但不會清除其他成功 extractor 的值。完整結構請參閱 [Extractor API](/reference/memory/observational-memory#extractor-api)。

### 從流中讀取提取的值 {/* #read-extracted-values-from-a-stream */}

當 OM 完成觀察或反射時，提取器結果就會到達。從流中讀取兩個完成資料部分：

```typescript title="src/run.ts"
import { assistant } from './mastra/agents/assistant'

const stream = await assistant.stream('Remember that I prefer dark mode.', {
  memory: { resource: 'user-123', thread: 'conversation-123' },
})

for await (const chunk of stream.fullStream) {
  if (chunk.type === 'data-om-observation-end' || chunk.type === 'data-om-buffering-end') {
    const { operationType, extractedValues = {}, extractionFailures = [] } = chunk.data

    for (const [slug, value] of Object.entries(extractedValues)) {
      console.log(`${operationType} extractor ${slug}:`, value)
    }

    for (const failure of extractionFailures) {
      console.error(`Extractor ${failure.slug} failed:`, failure.error)
    }
  }
}
```

`extractedValues`由每個提取器的彈頭鍵控。這兩個欄位都是可選的。

`data-om-observation-end` 表示同步觀察完成。`data-om-buffering-end` 表示背景工作完成：其 extractor 數值會立即持久保存，但緩衝的觀察紀錄在啟用前仍不生效。`operationType` 指出這次作業是觀察或反思。payload 詳見 [`data-om-observation-end`](/reference/memory/observational-memory#data-om-observation-end) 與 [`data-om-buffering-end`](/reference/memory/observational-memory#data-om-buffering-end)。
