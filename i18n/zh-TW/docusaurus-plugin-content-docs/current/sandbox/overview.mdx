# Sandbox 與檔案系統

{/* vale ai-tells.VerbTricolon = NO */}

Sandbox 為 Agent 提供隔離環境，可執行指令與程式碼、安裝相依套件及管理程序。這讓 Agent 能處理不適合直接在應用程式內執行的高風險、耗費資源或難以實作的工作。

Sandbox 通常是暫時的，環境停止後，其中建立的檔案可能消失。[檔案系統](/docs/sandbox/filesystem)讓 Agent 讀寫及[搜尋](/docs/sandbox/search)檔案，而檔案可在 Sandbox 結束後保留。你可以用它跨執行保留輸出、以現有檔案初始化新 Sandbox，或提供 Agent 工作時可搜尋的文件。即使沒有 Sandbox，也能使用檔案系統，例如 Agent 只需要知識庫或 Google Drive 等服務中的檔案。[Mastra Factory](https://factory.mastra.ai/) 就使用 Sandbox，讓程式開發 Agent 的工作階段能檢出儲存庫、安裝相依套件並執行指令。

{/* vale ai-tells.VerbTricolon = YES */}

## 何時使用 Sandbox {/* #when-to-use-sandboxes */}

當 Agent 需要完成以下工作時，可使用 Sandbox：

- 在獨立環境中複製儲存庫，並執行 Shell、Git、建置或測試流程。
* 使用專門的庫處理 PDF、簡報或其他文件並產生新的工件。
* 在具有隔離檔案和進程的單獨環境中執行長期或平行工作。

若 Agent 只需讀取、寫入或搜尋檔案，請設定[直接存取檔案系統](/docs/sandbox/filesystem#direct-filesystem-access)。

## 快速入門 {/* #quickstart */}

為 Agent 提供本機 Sandbox：

```typescript title="src/mastra/agents/coding-agent.ts"
import { Agent } from '@mastra/core/agent'
import { LocalSandbox, Workspace } from '@mastra/core/workspace'

export const codingAgent = new Agent({
  id: 'coding-agent',
  name: 'Coding agent',
  instructions: 'Use the sandbox to complete coding tasks.',
  model: '__GATEWAY_OPENAI_MODEL__',
  workspace: new Workspace({
    sandbox: new LocalSandbox({
      workingDirectory: './workspace',
    }),
  }),
})

await codingAgent.generate('List the files in the sandbox directory')
```

:::warning

`LocalSandbox` 預設直接在應用程式主機執行指令，沒有隔離，也不安全。執行不受信任的程式碼時，請啟用[原生隔離](#localsandbox)，或使用遠端、容器 Sandbox。

:::

靜態 Sandbox 由使用該 Agent 的所有請求與 Memory 執行緒共用。若每位使用者或每條執行緒都需要獨立環境，請使用[解析器](#sandboxes-per-user-or-thread)。共用與清理細節請參閱[生命週期與持久性](#lifecycle-and-persistence)。

## 使用 Sandbox {/* #using-the-sandbox */}

Agent 會取得 Sandbox 後端支援能力所對應的 Tool：

| Tool | 功能 |
| - | - |
| `execute_command` | 執行 Shell 指令並傳回 stdout、stderr 與結束代碼。若後端支援啟動長時間執行的程序，可使用 `background: true`。 |
| `get_process_output` | 取得背景程序的 stdout、stderr 與狀態。可用 `tail` 限制輸出，或用 `wait: true` 等待程序結束。靜態 Sandbox 只有在後端支援背景程序時，才會加入此工具與 `kill_process`。每次請求才解析 Sandbox 的 Workspace 一律包含兩個工具，因為解析前無法得知後端能力。 |
| `kill_process` | 停止背景程序並傳回最近的輸出。 |

設定的能力決定哪些 Tool 可用。接著可在 Tool 設定中停用、重新命名工具，或為工具加入原則：

```typescript
import { LocalSandbox, Workspace, WORKSPACE_TOOLS } from '@mastra/core/workspace'

const workspace = new Workspace({
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
  tools: {
    requireApproval: true,
    [WORKSPACE_TOOLS.SANDBOX.EXECUTE_COMMAND]: {
      enabled: false,
    },
  },
})
```

對單一工具設定 `{ enabled: false }` 可將其移除；在頂層設定 `enabled: false` 則會預設停用產生的工具。個別工具的 `{ enabled: true }` 會覆寫全域設定。頂層 `requireApproval` 原則適用於所有產生的工具，除非個別工具設定覆寫它。

所有產生的工具請參閱 [Sandbox 工具參考](/reference/workspace/workspace-class#sandbox-tools)；核准、輸出限制與 Hook 請參閱[工具設定參考](/reference/workspace/workspace-class#tool-configuration)。

{/* vale ai-tells.VerbTricolon = NO */}

應用程式撰寫的執行階段函式（包括 Tool 與 Workflow 步驟）可從執行上下文取得目前的 Sandbox，用來執行指令、安裝相依套件、處理檔案或啟動長時間執行的程序。

{/* vale ai-tells.VerbTricolon = YES */}

```typescript title="src/mastra/tools/start-server.ts"
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

export const startServerTool = createTool({
  id: 'start-server',
  description: 'Starts a server in the sandbox',
  inputSchema: z.object({
    command: z.string(),
  }),
  execute: async ({ command }, ctx) => {
    if (!ctx.workspace || !ctx.requestContext) {
      throw new Error('This tool requires a workspace execution context')
    }

    const sandbox = await ctx.workspace.resolveSandbox({
      requestContext: ctx.requestContext,
    })

    if (!sandbox?.processes) {
      throw new Error('The configured sandbox does not support background processes')
    }

    const server = await sandbox.processes.spawn(command)
    return { pid: server.pid }
  },
})
```

## 沙箱 {/* #sandboxes */}

### `LocalSandbox` {/* #localsandbox */}

[`LocalSandbox`](/reference/workspace/local-sandbox) 在 Mastra 應用程式所在的同一台機器上執行指令。預設指令會直接以應用程式程序的權限在主機執行。

`workingDirectory` 只指定指令執行的位置。Mastra 不會將專案複製到該處。若要讓 Agent 使用自己的儲存庫工作副本，請在原始碼儲存庫外的目錄執行 `git clone` 或 `git worktree add`。

```typescript
const sandbox = new LocalSandbox({
  workingDirectory: './workspace',
  isolation: 'seatbelt', // Use 'bwrap' on Linux
  nativeSandbox: {
    allowNetwork: false,
    readOnlyPaths: ['./reference-data'],
  },
})
```

啟用原生隔離，可在作業系統層級限制檔案系統與網路存取。macOS 使用 Seatbelt（`sandbox-exec`），Linux 使用 Bubblewrap（`bwrap`）。可用 `LocalSandbox.detectIsolation()` 檢查目前作業系統是否可使用其中一種。

[`nativeSandbox` 選項](/reference/workspace/local-sandbox#nativesandboxconfig)控制網路存取、唯讀或可寫路徑、工作目錄的寫入權限，以及系統執行檔。你也可以提供自訂 Seatbelt 設定檔或 Bubblewrap 引數。完整設定請參閱 [`LocalSandbox`](/reference/workspace/local-sandbox)。

## 檔案系統 {/* #filesystem */}

每個 Sandbox 都有供指令使用的檔案系統。`LocalSandbox` 使用主機檔案系統；遠端 Sandbox 的檔案系統則彼此隔離，且通常是暫時的。若檔案需要在 Sandbox 結束後保留，請使用外部儲存空間。

Mastra 檔案系統將 Agent 與 Sandbox 連至 Amazon S3、Google Cloud Storage 或 Google Drive 等 Provider 儲存空間。設定後，Agent 會取得讀寫及搜尋檔案的 Tool。若遠端 Sandbox 與 Provider 都支援掛載，Mastra 會透過使用者空間檔案系統（FUSE）自動掛載儲存空間。指令照常使用檔案路徑，變更則由 Sandbox 外的 Provider 儲存。

Provider、檔案工具與掛載方式請參閱[檔案系統](/docs/sandbox/filesystem)。

## 電腦使用 {/* #computer-use */}

支援的桌面 Sandbox 可讓 Agent 操作螢幕截圖、滑鼠與鍵盤。支援的 Sandbox 與設定請參閱[電腦操作](/docs/sandbox/computer)。

## 每個使用者或線程的沙箱 {/* #sandboxes-per-user-or-thread */}

若每位使用者、租戶或執行緒都需要獨立 Sandbox，請使用**解析器**。將 `sandboxCacheKey` 設為 Sandbox 所屬身分，讓後續請求重用相同的執行中環境。

此範例為每個使用者建立並快取一個 Daytona 沙箱：

```typescript title="src/mastra/workspaces.ts"
import { Workspace } from '@mastra/core/workspace'
import { DaytonaSandbox } from '@mastra/daytona'

const workspace = new Workspace({
  sandbox: async ({ requestContext }) => {
    const userId = requestContext.get('user-id') as string
    const sandbox = new DaytonaSandbox({ id: `user-${userId}` })
    await sandbox.start()
    return sandbox
  },
  sandboxCacheKey: ({ requestContext }) => requestContext.get('user-id') as string,
})
```

用戶的第一個請求將建立沙箱。具有相同使用者 ID 的後續請求將重複使用它。

若 Sandbox 需要持久儲存，請建立[檔案系統](/docs/sandbox/filesystem)，並在解析器內掛載。此範例為每條 Memory 執行緒建立一個 Daytona Sandbox 與一個 S3 儲存前綴，再將儲存空間掛載至 `/workspace`：

```typescript title="src/mastra/workspaces.ts"
import { MASTRA_THREAD_ID_KEY, type RequestContext } from '@mastra/core/request-context'
import { Workspace } from '@mastra/core/workspace'
import { DaytonaSandbox } from '@mastra/daytona'
import { S3Filesystem } from '@mastra/s3'

const getThreadId = (requestContext: RequestContext) => {
  const threadId = requestContext.get(MASTRA_THREAD_ID_KEY)
  if (typeof threadId !== 'string' || !threadId) {
    throw new Error('MASTRA_THREAD_ID_KEY is not set on the request context')
  }
  return threadId
}

const createThreadFilesystem = (threadId: string) =>
  new S3Filesystem({
    bucket: process.env.S3_BUCKET!,
    region: process.env.S3_REGION!,
    prefix: `threads/${threadId}`,
  })

const workspace = new Workspace({
  filesystem: ({ requestContext }) => createThreadFilesystem(getThreadId(requestContext)),
  sandbox: async ({ requestContext }) => {
    const threadId = getThreadId(requestContext)
    const sandbox = new DaytonaSandbox({
      id: `thread-${threadId}`,
      language: 'typescript',
    })

    await sandbox.start()
    await sandbox.mount(createThreadFilesystem(threadId), '/workspace')
    return sandbox
  },
  sandboxCacheKey: ({ requestContext }) => getThreadId(requestContext),
})
```

解析器只接收請求上下文，因此執行緒 ID 必須放在其中。`agent.stream()` 與 `agent.generate()` 不會將 `memory.thread` 複製到 `MASTRA_THREAD_ID_KEY`。請根據可信任的執行緒 ID 自行設定此鍵，可在[伺服器中介軟體](/docs/server/request-context#reserved-keys)中設定，或在呼叫 Agent 時設定：

```typescript
import { MASTRA_THREAD_ID_KEY, RequestContext } from '@mastra/core/request-context'

const requestContext = new RequestContext()
requestContext.set(MASTRA_THREAD_ID_KEY, threadId)

await agent.stream(message, {
  memory: { thread: threadId, resource: userId },
  requestContext,
})
```

缺少此鍵時，`getThreadId()` 會擲出錯誤。因此，沒有執行緒的請求會失敗，不會與其他同類請求共用 `threads/undefined` 前綴和 Sandbox。

執行緒的第一個請求會執行解析器並啟動 Sandbox；後續相同 ID 的請求會重用快取的 Sandbox。不同的執行緒 ID 會建立不同的 Sandbox 與儲存前綴。

此範例在解析器內掛載檔案系統，因為靜態 `mounts` 無法搭配 Sandbox 解析器使用。產生的工具會根據請求上下文自動解析檔案系統與 Sandbox。

:::warning

解析器傳回的 Sandbox 由應用程式負責管理。使用者、執行緒或工作階段結束時，請銷毀這些 Sandbox，並呼叫 `workspace.clearSandboxCache(cacheKey)`。`workspace.destroy()` 不會銷毀解析器傳回的 Sandbox。

:::

### Agent Workspace 函式 {/* #agent-workspace-functions */}

Agent 的 `workspace` 選項也接受傳回 `Workspace` 的函式。Mastra 每次需要 Agent 的 Workspace 時都會呼叫它，不限於 Agent 執行期間；包括啟動時註冊 Agent，以及讀取 Agent 中繼資料。Studio 列出 Agent 時會呼叫 `GET /api/agents` 和 `GET /api/agents/:agentId`。這些呼叫不會快取。

此函式應保持輕量，不要在其中啟動 Sandbox 或其他付費基礎設施。請傳回使用 `filesystem` 與 `sandbox` 解析器的 Workspace。Mastra 會在建立執行所需的 Workspace 指令、工具需要 Provider，以及讀取 Agent 的 Workspace Skill 時呼叫檔案系統解析器，包括存取 Agent 中繼資料路由時。Sandbox 解析器只有在工具需要 Provider 時才會呼叫，除非將 `instructions.dynamicSandbox` 設為 `'resolve'`。

### Tool可用性 {/* #tool-availability */}

使用靜態 Sandbox 時，Mastra 知道後端支援哪些能力，只會將對應的 Tool 提供給 Agent。應用程式碼在使用選用能力前也應先確認是否可用。

[解析器提供的 Sandbox](#sandboxes-per-user-or-thread) 要到請求時才能確定，因此 Mastra 一開始會提供所有 Sandbox 工具。若呼叫解析後端不支援的工具，會出現 `SandboxFeatureNotSupportedError`。

## 後台程式 {/* #background-processes */}

Agent 透過 `execute_command` 啟動背景程序時，可接收 stdout、stderr 與程序結束的生命週期回呼。請在 `WORKSPACE_TOOLS.SANDBOX.EXECUTE_COMMAND` 項目設定 `backgroundProcesses`：

```typescript title="src/mastra/workspaces.ts"
import { Workspace, LocalSandbox, WORKSPACE_TOOLS } from '@mastra/core/workspace'

const workspace = new Workspace({
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
  tools: {
    [WORKSPACE_TOOLS.SANDBOX.EXECUTE_COMMAND]: {
      backgroundProcesses: {
        onStdout: (data, { pid }) => console.log(`[${pid}] ${data}`),
        onStderr: (data, { pid }) => console.error(`[${pid}] ${data}`),
        onExit: ({ pid, exitCode }) => console.log(`Process ${pid} exited: ${exitCode}`),
      },
    },
  },
})
```

這些回呼會在 Agent 透過 `execute_command` 啟動的所有背景程序上觸發。

預設背景程序會繼承 Agent 的中止訊號，並在 Agent 中斷連線時停止。若程序需要在請求結束後繼續執行，請將 `abortSignal` 設為自訂訊號，或使用 `null` 或 `false`。

完整的 `SandboxProcessManager` API（包括以程式啟動程序、取得輸出與寫入標準輸入）請參閱 [`SandboxProcessManager` 參考](/reference/workspace/process-manager)。

## 生命週期和持久性 {/* #lifecycle-and-persistence */}

Sandbox 由誰共用，取決於設定位置及是否使用解析器：

| 設定 | 共用 Sandbox 的對象 |
| - | - |
| Mastra 層級設定 | 繼承 [`Mastra`](/reference/configuration) 實例設定的 Agent 共用同一個 Sandbox。 |
| Agent 層級設定 | 該 Agent 實例處理的所有請求共用同一個 Sandbox。 |
| 依資源區分的解析器 | 每個資源 ID 快取一個 Sandbox。 |
| 依執行緒區分的解析器 | 同一 Memory 執行緒的多次請求共用其 Sandbox。 |

靜態 Sandbox 不會自動限定於目前資源或 Memory 執行緒。若要依資源或執行緒隔離，請使用解析器，並將 `sandboxCacheKey` 設為對應 ID。請參閱[每位使用者或每條執行緒的 Sandbox](#sandboxes-per-user-or-thread)。

### 開始 {/* #start */}

靜態 Sandbox 環境通常在第一個指令執行時啟動，因此多數應用程式無須明確初始化。只有想在提供服務前啟動靜態 Sandbox 並準備掛載時，才應在應用程式啟動期間呼叫 `workspace.init()`。這適合希望憑證、網路或 Provider 錯誤在啟動階段，而非執行第一個指令時顯示的情況。

`workspace.init()` 不會啟動解析器提供的 Sandbox，因為請求執行前尚未選定 Sandbox。解析器應傳回已啟動或首次使用時可自行啟動的 Sandbox。

### 掛鉤 {/* #hooks */}

使用 `onStart`、`onStop` 與 `onDestroy`，可在生命週期轉換時執行應用程式碼。Hook 會收到目前執行中的 Sandbox 實例：

```typescript
const sandbox = new LocalSandbox({
  workingDirectory: './workspace',
  onStart: ({ sandbox }) => console.log(`Started ${sandbox.id}`),
  onStop: ({ sandbox }) => console.log(`Stopping ${sandbox.id}`),
  onDestroy: ({ sandbox }) => console.log(`Destroying ${sandbox.id}`),
})
```

`onStart` 在 Sandbox 啟動後執行。`onStop` 與 `onDestroy` 則在對應操作前執行。

### 清理 {/* #cleanup */}

直接設定而非透過解析器建立 Sandbox 時，由 Mastra 負責管理。`mastra dev` 與產生的 Mastra Server 會處理關閉訊號，並自動銷毀已註冊的資源。若將 Mastra 嵌入自訂伺服器或程序，請在關閉 Hook 中呼叫 `mastra.shutdown()`；單獨使用 Workspace 時，直接呼叫 `workspace.destroy()`。

`stop()` 與 `destroy()` 的行為由後端決定。例如，停止可能會關閉運算資源，但保留可重新啟動的環境；銷毀則可能刪除環境及其中的暫存檔案。依賴任一行為前，請查看所選後端的說明。

解析器傳回的 Sandbox 由應用程式管理。`workspace.destroy()` 與 `mastra.shutdown()` 只會清除快取參照，不會銷毀已解析的 Sandbox。應用程式的生命週期程式碼必須追蹤它們，在所屬使用者、執行緒或工作階段結束時呼叫 `destroy()`，再呼叫 `workspace.clearSandboxCache(cacheKey)`。這可避免閒置運算資源持續執行，也防止後續請求重用過期的 Sandbox。

### 持久性 {/* #persistence */}

持久性取決於後端。Sandbox 停止或應用程式重新啟動後，檔案與程序不保證仍在；閒置逾時也可能將它們清除。有些後端可依 Sandbox ID 重新連線，或保留快照與磁碟區；其他後端則會建立全新環境。

每個 Sandbox 都有 `id`，但此 ID 不保證跨後端的持久性。依賴重新連線或持久化狀態前，請先閱讀所選後端的參考文件。

## 網路和憑證安全 {/* #network-and-credential-safety */}

Mastra 沒有適用於所有 Sandbox 後端的單一網路原則。預設值與支援的控制項因後端而異，執行不受信任的程式碼前請先確認。對於敏感或正式環境工作負載，建議封鎖對外連線，或只允許工作所需的目的地。建立 Sandbox 時就應套用原則，以便在指令執行前生效。

若 Agent 在遠端 Sandbox 內啟動 Web 伺服器，伺服器起初只監聽 Sandbox 內的連接埠。支援公開連接埠的後端會實作 `sandbox.networking.getPortUrl()`，傳回可從 Sandbox 外預覽或測試伺服器的 URL：

```typescript
const url = await sandbox.networking?.getPortUrl(8000)
```

依後端的存取控制設定，此 URL 可能讓其他人也能存取服務。這種對內連線的公開方式與 Sandbox 的對外連線權限不同。啟用原生隔離的 `LocalSandbox` 預設封鎖網路存取，除非開啟 `allowNetwork`；沒有原生隔離時，本機指令使用主機網路。

例如，`DaytonaSandbox` 預設允許對外連線，除非你另行設定限制。若工作只需要特定服務，可設定 `networkBlockAll` 並提供網域允許清單：

```typescript
import { DaytonaSandbox } from '@mastra/daytona'

const sandbox = new DaytonaSandbox({
  networkBlockAll: true,
  domainAllowList: 'registry.npmjs.org,api.github.com',
})
```

Daytona 在建立 Sandbox 時套用這些設定，也支援透過 `networkAllowList` 設定 CIDR 規則。完整設定請參閱 [Daytona 整合頁面](/integrations/sandboxes/daytona)。

傳入 Sandbox 或指令的環境變數，可由其中執行的程式碼讀取。Mastra 不提供跨後端的憑證代理，無法在授權請求的同時將密鑰留在 Sandbox 外。請只將工作所需的憑證提供給指令，並遵循所選後端的密鑰管理指引。

例如，應只將唯讀 Token 傳給需要它的指令，而非為 Sandbox 中的每個指令設定：

```typescript
await sandbox.executeCommand('node', ['scripts/download-reports.js'], {
  env: {
    REPORTS_READ_TOKEN: process.env.REPORTS_READ_TOKEN,
  },
})
```
