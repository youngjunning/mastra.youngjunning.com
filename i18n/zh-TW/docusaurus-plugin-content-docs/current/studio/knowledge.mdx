# Knowledge

Studio 的 Knowledge 頁面會列出 Agent 掌握的知識：所有範圍與頁面、彼此的連結，以及各項內容的作者。你可以在這個唯讀頁面確認載入的內容，並即時查看 Agent 的編輯。

:::alpha

Knowledge 目前為 alpha，API 可能在不同版本間變更。

:::

## 啟用路由 {/* #enable-the-routes */}

Knowledge 路由**預設停用**。啟用之前，Studio 的 Knowledge 頁面會顯示瀏覽功能尚未開啟。請在 `Mastra` 註冊 Knowledge 執行個體並加入路由：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { KNOWLEDGE_ROUTES } from '@mastra/server/server-adapter'
import { knowledge } from './knowledge'
import { supportAgent } from './agents/support-agent'

export const mastra = new Mastra({
  agents: { supportAgent },
  knowledge: { company: knowledge },
  server: { apiRoutes: [...KNOWLEDGE_ROUTES] },
})
```

路由掛載在伺服器的 API 前綴下，預設為 `/api/knowledge`，需要 `@mastra/core` 1.81.0 以上版本。在 1.81.0 版，Studio 只計算已載入頁面之間的連結。[伺服器路由](/reference/server/routes#knowledge)列出每條路由及其參數與錯誤。

## 可查看的內容 {/* #what-you-see */}

- **頁面樹**：依照 Agent 建立的階層呈現所有範圍及其中的頁面。
- **關聯圖**：呈現相同頁面及彼此的關聯。線條代表父頁面、備註提到的頁面、內文中的連結，以及範圍之間的存取授權。圖例標示線條種類；在任一檢視中選取頁面即可開啟。
- **頁面**：顯示內文、版本、最後更新者、備註與作者、子頁面、其他頁面上提到本頁的備註，以及本頁為誰釘選。
- **活動**：查看各頁面的建立、編輯、移動、合併、備註和釘選紀錄，以及每筆紀錄的作者與時間。
- **搜尋**：搜尋頁面名稱、說明、內文和備註文字。

畫面較窄時，頁面樹和關聯圖共用同一個面板，切換時會保留選取的頁面。

Agent 寫入時，頁面樹、關聯圖和目前開啟的頁面會即時更新，不必重新載入。Studio 會追蹤透過 Mastra 上已註冊的 Knowledge 執行個體進行的寫入。若由其他程序或使用同一儲存空間的其他執行個體寫入，則要重新載入才看得到。

## 控制使用者可見的內容 {/* #control-who-sees-what */}

路由回傳的內容取決於應用程式是否設定身分驗證（`server.auth` 或 `studio.auth`）：

- **未設定身分驗證：**路由以執行個體擁有者的身分讀取資料，任何能連上伺服器的人都能取得所有範圍、頁面和備註。這種設定只適合本機或測試專案，部署前請加入身分驗證。
- **已設定身分驗證：**路由只回傳已登入使用者可讀取的內容。請在 `authorize` 中將請求上下文的 `MASTRA_KNOWLEDGE_PRINCIPALS_KEY` 設為該使用者的 Knowledge 範圍。Knowledge 套用與 Agent 相同的存取規則。alpha 階段的規則無法作為[隔離邊界](/docs/knowledge/scopes-and-access)，請勿儲存絕不能讓其他使用者取得的內容。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { KNOWLEDGE_ROUTES, MASTRA_KNOWLEDGE_PRINCIPALS_KEY } from '@mastra/server/server-adapter'
import { appAuthorize } from './auth' // your existing authorization

export const mastra = new Mastra({
  server: {
    apiRoutes: [...KNOWLEDGE_ROUTES],
    auth: {
      // authenticateToken, ...
      authorize: async (path, method, user, context) => {
        if (path.startsWith('/api/knowledge')) {
          context
            .get('requestContext')
            .set(
              MASTRA_KNOWLEDGE_PRINCIPALS_KEY,
              user.isAdmin ? 'all' : [`org:${user.orgId}`, `team:${user.orgId}:${user.teamId}`],
            )
          return true
        }
        return appAuthorize(path, method, user, context)
      },
    },
  },
})
```

若另外設定了前綴，請修改 `authorize` 中的 `/api/knowledge` 檢查，使兩者一致。否則不會設定該鍵，路由會回傳 `403`。

`authorize` 函式會取代伺服器對所有路由的規則與角色檢查，因此請如上例保留應用程式對其他路徑的原有判斷。若一律回傳 `true`，任何已登入的使用者都能呼叫任何路由。

將值設為範圍陣列；需要查看整個執行個體的使用者則設為 `'all'`。空陣列無法讀取任何內容。其他值的回傳情形請參閱 [Knowledge 存取與錯誤](/reference/server/routes#knowledge-access-and-errors)。設定 `studio.auth` 後，Studio 請求會優先使用它，而非 `server.auth`，因此要在前者的 `authorize` 設定該鍵。

### 定義 `authorizeUser` 的 Provider {/* #providers-with-authorizeuser */}

身分驗證 Provider 若定義了 `authorizeUser`，伺服器便不會呼叫 `authorize`。這包括實作該方法的任何 `MastraAuthProvider` 子類別，以及所有 `CompositeAuth`。使用這些 Provider 時，請改在[伺服器中介軟體](/docs/server/middleware)中設定該鍵：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { KNOWLEDGE_ROUTES, MASTRA_KNOWLEDGE_PRINCIPALS_KEY } from '@mastra/server/server-adapter'
import { auth, getSessionUser } from './auth' // your provider and session lookup

export const mastra = new Mastra({
  server: {
    apiRoutes: [...KNOWLEDGE_ROUTES],
    auth,
    middleware: [
      {
        path: '/api/knowledge/*',
        handler: async (c, next) => {
          const user = await getSessionUser(c.req.raw)
          if (user) {
            c.get('requestContext').set(
              MASTRA_KNOWLEDGE_PRINCIPALS_KEY,
              user.isAdmin ? 'all' : [`org:${user.orgId}`, `team:${user.orgId}:${user.teamId}`],
            )
          }
          await next()
        },
      },
    ],
  },
})
```

伺服器中介軟體會在路由檢查身分之前執行，因此這時請求上下文還沒有已登入的使用者。請如上例，透過應用程式自己的工作階段檢查，從請求找出使用者。路由之後仍會驗證身分，並拒絕 Provider 不接受的呼叫方。若使用不同前綴，請修改中介軟體的 `path`。

### 部署注意事項 {/* #deployment-notes */}

- **沒有 RBAC Provider：**系統會略過 `knowledge:read` 檢查。任何已驗證身分且有存取主體對應的使用者，都能在每個執行個體讀取這些主體可存取的頁面。
- **有 FGA Provider：**每個 Knowledge 執行個體都會個別檢查 `knowledge:read`。使用者只能查看你授權的執行個體。請參閱 [Knowledge 存取與錯誤](/reference/server/routes#knowledge-access-and-errors)。
- **NestJS：**NestJS 介面卡尚未提供 Knowledge 路由。

## 建立自訂檢視 {/* #build-your-own-view */}

若要在應用程式顯示 Knowledge 的變更，請用 [`knowledge.onChange()`](/reference/knowledge/knowledge-class#onchange) 訂閱。事件只帶有 ID，不含內容。顯示前，請依使用者的範圍重新讀取頁面。收到 `page` 的 `delete` 事件後，已無法讀取該頁面，請從檢視移除。若是 `page` 的 `merge` 事件，`pageId` 是合併目的頁面，因此也要移除 `sourceId` 所指的被合併頁面。`scope` 事件只會針對新範圍發送，不會為其子範圍或範本頁面發送，請重新列出該範圍的內容來查找它們。
