# 勞工

:::測試版

在 API 穩定之前，可能會在沒有重大版本更新的情況下發生重大變更。看[known limitations](#known-limitations) for current gaps.

:::

工作人員在請求-回應週期之外進行後台處理。Workflow步驟執行、基於 cron 的調度和長時間運行的Tool呼叫都在工作執行緒中運行，從而保持 API 的回應能力。

預設情況下，worker 與 API 在同一進程中運行。對於生產工作負載，您可以將它們拆分為單獨的進程或容器，並獨立擴展每個進程或容器。

## 何時使用工人 {/* #when-to-use-workers */}

當以下任何一項適用時，工人就很重要：

* Workflow步驟需要幾秒鐘以上的時間，不應阻止 API 回應
* 您需要事件持久性，以便正在進行的工作能夠在流程重新啟動後繼續存在
* 系統的不同部分需要獨立擴充（例如，無需更多 API 實例即可獲得更多編排能力）
* 後台Tool呼叫應在專用計算上運行

如果您的應用程式處理少量流量並且Workflow快速完成，則預設的進程內設定可以正常運作。跳過工作基礎設施直到你需要它。

## 工人類型 {/* #worker-types */}

Mastra 有三種內建的工作人員類型。每個處理特定類型的後台處理。

### 編排工作者 {/* #orchestration-worker */}

該工作人員訂閱Workflow事件[PubSub](/docs/server/pubsub) bus and executes workflow steps. It handles each `workflow.start` and lifecycle event together with every step transition.

在分割部署中，編排工作人員從分散式 PubSub 後端提取事件，並透過 HTTP 將步驟執行委託回 API。在進程中，它直接運行步驟。

編排工作人員需要一個支援拉取模式的 PubSub 後端（例如，[`RedisStreamsPubSub`](/reference/pubsub/redis-streams), [`ValkeyStreamsPubSub`](/reference/pubsub/valkey-streams), or [`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub)).

### 調度員 {/* #scheduler-worker */}

輪詢儲存以獲取到期的 cron 計劃並發布`workflow.start` event for each fire. It's a producer only, meaning it creates work for the orchestration worker to pick up:

* **分割流程**：預定的Workflow在事件引擎上運行，編排工作人員逐步運行每個火災。
* **行程內模式**：計劃的Workflow在預設引擎上運作。同一進程中的編排工作人員在進程內運行每個火災，就像直接`run.start()` does.

調度程序讀取聲明式`schedule` fields from your workflow definitions automatically. See [Scheduled workflows](/docs/workflows/scheduled-workflows) for how to declare schedules.

調度程序僅在調度存在時輪詢儲存。启动时，没有声明调度的进程运行一个`listSchedules()` check. If that check finds no rows, the poll loop never starts, so idle deployments issue no recurring scheduler queries and can scale to zero.

在運行時建立計劃時，Mastra 會在 PubSub 後端發布喚醒事件。執行預設工作程序集的任何進程都會啟動其調度程序作為回應，這就是獨立工作程序發現 API 程序創建的調度程序的方式。這需要兩個進程共享相同的 PubSub 後端。

`scheduler: { enabled: true }` on the worker or run it with `MASTRA_WORKERS=scheduler`.

您可以針對相同儲存體執行多個調度程序實例。在發布之前，調度程序會透過調度的下一次觸發時間的比較和交換更新來聲明每次發生的情況。只有一個實例贏得了索賠，其他實例則跳過該事件。內建儲存適配器（PostgreSQL、LibSQL、MySQL、MongoDB、Spanner、Convex）均以原子方式執行此更新。自訂儲存適配器必須執行相同的操作`updateScheduleNextFire`, or instances can fire the same occurrence twice.

該聲明阻止其他調度程序實例發布相同的事件。它不會只觸發一次：

* **聲明和發布不是一件事務。**&#x5982;果贏得索賠的實例崩潰，或在三次嘗試後未能發布，則該事件可能會遺失。 Mastra 將失敗的發布記錄為`failed` trigger with an unknown publication outcome and doesn't replay it automatically.
* ****如果發佈到達 PubSub 後端但仍報告錯誤，則重試會使用相同的運行 ID 再次發布該事件。對於預設引擎上的Workflow，工作執行緒會跳過已存在的運行的啟動，但在儲存第一次運行之前到達的副本仍可以啟動。事件Workflow沒有此類檢查：重複啟動會將現有運行設定回`running` and executes it again.
* **事件可能會重疊。**&#x5373;使前一個事件的運作尚未完成，新事件也會準時觸發。

額外的調度程序實例增加了可用性，而不是吞吐量。每個人都會在每次更新時輪詢儲存空間。

### 後台任務工作者 {/* #background-task-worker */}

執行標記為的AgentTool調用`background: { enabled: true }`. When an agent invokes a background tool, the API dispatches the task to this worker instead of blocking the response stream.

後台任務工作人員透過 PubSub 匯流排管理並發限制、任務生命週期和結果交付。

## 工人如何跑步 {/* #how-workers-run */}

### 進程內模式（預設） {/* #in-process-mode-default */}

無需配置，Mastra 在 API 進程內執行工作執行緒。事件流經記憶體中的 PubSub，所有內容都共用一個 Node.js 執行時間。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'

export const mastra = new Mastra({
  // Workers run in-process by default.
  // No pubsub or worker config needed.
})
```

伺服器產生的`mastra build` starts these workers automatically. If you use a [server adapter](/docs/server/server-adapters) instead, add a call to `mastra.startWorkers()` after your server starts listening. See [Start background workers](/docs/server/server-adapters#start-background-workers).

除了儲存適配器之外，此設定不需要任何外部基礎架構。它無法在進程崩潰時倖存下來，並且您無法擴展單個元件。

：：：警告

記憶體中的 PubSub 僅在發布事件的進程內傳遞事件。事件Workflow不支援在一個儲存體上執行多個 Mastra 實例：每個實例在啟動時都會重新啟動其他實例的活動運行。為多實例部署配置分散式 PubSub 後端。

:::

### 分割流程 {/* #split-processes */}

若要在自己的進程中執行工作人員，請配置分散式[PubSub](/docs/server/pubsub) backend and use the `MASTRA_WORKERS` environment variable to control which workers start in each process.

<Tabs>
  <TabItem value="redis" label="Redis Streams + PostgreSQL">
    ```typescript title="src/mastra/index.ts"
    import { Mastra } from '@mastra/core/mastra'
    import { RedisStreamsPubSub } from '@mastra/redis-streams'
    import { PostgresStore } from '@mastra/pg'

    export const mastra = new Mastra({
      storage: new PostgresStore({
        connectionString: process.env.DATABASE_URL!,
      }),
      pubsub: new RedisStreamsPubSub({
        url: process.env.REDIS_URL!,
      }),
    })
    ```
  </TabItem>

  <TabItem value="gcp" label="Google Cloud Pub/Sub + LibSQL">
    ```typescript title="src/mastra/index.ts"
    import { Mastra } from '@mastra/core/mastra'
    import { GoogleCloudPubSub } from '@mastra/google-cloud-pubsub'
    import { LibSQLStore } from '@mastra/libsql'

    export const mastra = new Mastra({
      storage: new LibSQLStore({
        url: process.env.DATABASE_URL!,
      }),
      pubsub: new GoogleCloudPubSub({
        projectId: process.env.GCP_PROJECT_ID!,
      }),
    })
    ```
  </TabItem>
</Tabs>

任何[supported storage backend](/reference/workers/overview#supported-storage-backends) works. Swap the storage adapter for your preferred database.

在多個容器中運行相同的建置工件，每個容器都有不同的[`MASTRA_WORKERS`](/reference/workers/overview#mastra_workers) value to control which worker starts in each process.

分割部署需要分散式 PubSub 後端（[`RedisStreamsPubSub`](/reference/pubsub/redis-streams), [`ValkeyStreamsPubSub`](/reference/pubsub/valkey-streams), or [`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub)), a shared [storage backend](/reference/workers/overview#supported-storage-backends), and network connectivity between the orchestration worker and the API.

### {/* #select-workers */}

放[`MASTRA_WORKERS`](/reference/workers/overview#mastra_workers) to control which workers run in each process:

|價值|行為 |
| - | - |
|`false` | Disable all workers. Use this for the API process in a fully split deployment. |
| `orchestration` | Start the orchestration worker. |
| `scheduler` | Start the scheduler worker. |
| `backgroundTasks` | Start the background task worker. |
| `orchestration,backgroundTasks` | Start multiple workers from a comma-separated allowlist. |

您也可以將工作人員名稱傳遞給 CLI。命令集`MASTRA_WORKERS` in the spawned process:

```bash
mastra worker start orchestration
```

放`MASTRA_WORKERS` on every process in a split deployment, including `false` on the API process. Any value switches workflows that declare `schedule` to the evented engine, and every process must run those workflows on the same engine. See [Scheduled workflows](/docs/workflows/scheduled-workflows#execution-engine). `mastra worker start` without a worker name doesn't set `MASTRA_WORKERS`, so pass a name or set the variable in the process environment.

## 網路架構 {/* #network-architecture */}

工人是內部基礎設施。它們不會向最終用戶公開，也不需要自己的子網域或公用 URL，包括入站 HTTP 路由。

在拆分部署中：

* **API伺服器是唯一面向公眾的進程**：它為所有客戶端 HTTP 請求提供服務。這些請求包括 REST 端點和Agent交互，以及Workflow觸發器和自訂路由。
* **工作人員不服務客戶流量**：它們從分散式 PubSub 後端提取事件並讀取/寫入到共享儲存資料庫。每個工作進程也監聽`PORT` (default `4111`) for internal health checks. `/health` reports readiness and `/config` returns the worker configuration to authorized callers. Keep this port on the private network.
* **編排工作人員在內部呼叫API**：它使用以下命令透過容器網路向 API 發送步驟執行請求`MASTRA_STEP_EXECUTION_URL`. This is internal service-to-service communication, not a public endpoint.

所有三種工作類型（編排、排程器、背景任務）都位於專用網路上的 API 後面。它們共享對 PubSub 後端和儲存資料庫的存取權限，但從不直接從客戶端接收流量。與工作執行緒相關的功能的 HTTP 路由在 API 伺服器上運行，而不是在工作進程上運行。一個例子是為語音整合創建令牌。

## 部署拆分工作人員 {/* #deploy-split-workers */}

建置 API 和工作工件：

```bash
mastra build
mastra worker build --output-dir .mastra/worker
```

`mastra build`在中建立 API 工件`.mastra/output/`. [`mastra worker build`](/reference/cli/mastra#mastra-worker-build) creates a worker artifact in `.mastra/worker/`. The following Dockerfile accepts either directory:

```dockerfile title="Dockerfile"
FROM node:22-alpine

ARG MASTRA_OUTPUT=.mastra/output

WORKDIR /app

COPY ${MASTRA_OUTPUT}/package.json ${MASTRA_OUTPUT}/.npmrc* ./
RUN npm install --omit=dev

COPY ${MASTRA_OUTPUT}/ .

EXPOSE 4111
CMD ["node", "index.mjs"]
```

看[Deploy a Mastra server](/docs/deployment/mastra-server) for more information about the build output.

### Docker 組合 {/* #docker-compose */}

以下配置運行 PostgreSQL、Redis、API 以及每種工作執行緒類型的一個程序。每個進程都使用共享基礎設施，並且工作進程使用工作工件。

```yaml title="docker-compose.yml"
x-worker: &worker
  build:
    context: .
    args:
      MASTRA_OUTPUT: .mastra/worker

x-mastra-environment: &shared-environment
  DATABASE_URL: postgres://mastra:${POSTGRES_PASSWORD}@postgres:5432/mastra
  REDIS_URL: redis://redis:6379

services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: mastra
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: mastra
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ['CMD-SHELL', 'pg_isready -U mastra']
      interval: 5s
      timeout: 3s
      retries: 5

  redis:
    image: redis:7-alpine
    healthcheck:
      test: ['CMD', 'redis-cli', 'ping']
      interval: 5s
      timeout: 3s
      retries: 5

  api:
    build:
      context: .
      args:
        MASTRA_OUTPUT: .mastra/output
    ports:
      - '4111:4111'
    environment:
      <<: *shared-environment
      WORKER_TOKEN: ${WORKER_TOKEN}
      MASTRA_WORKERS: 'false'
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    healthcheck:
      test: ['CMD', 'wget', '-qO-', 'http://localhost:4111/api/agents']
      interval: 5s
      timeout: 3s
      retries: 5

  orchestration-worker:
    <<: *worker
    environment:
      <<: *shared-environment
      MASTRA_WORKERS: orchestration
      MASTRA_STEP_EXECUTION_URL: http://api:4111/api
      MASTRA_WORKER_AUTH_TOKEN: ${WORKER_TOKEN}
    depends_on:
      api:
        condition: service_healthy

  scheduler-worker:
    <<: *worker
    environment:
      <<: *shared-environment
      MASTRA_WORKERS: scheduler
    depends_on:
      api:
        condition: service_healthy

  background-task-worker:
    <<: *worker
    environment:
      <<: *shared-environment
      MASTRA_WORKERS: backgroundTasks
    depends_on:
      api:
        condition: service_healthy

volumes:
  pgdata:
```

設定旁邊的秘密`docker-compose.yml`, along with any model provider credentials your application needs:

```bash title=".env"
POSTGRES_PASSWORD=your-secure-password
WORKER_TOKEN=your-shared-secret-token
```

配置 API 身份驗證Provider以接受`WORKER_TOKEN` before exposing the deployment. The orchestration worker sends the same value through `MASTRA_WORKER_AUTH_TOKEN`. The scheduler and background task workers don't call the step execution endpoint in this pull-based topology, so they don't need that variable.



```bash
docker compose up -d
docker compose ps
curl http://localhost:4111/api/agents
```

### 庫伯內斯 {/* #kubernetes */}

:::尖端頭盔
在 Kubernetes 上，[`mastra-projects` Helm chart](/integrations/deploy/kubernetes-helm#background-workers) renders these deployments for you, with the workers on the same image and environment as the server. It also refuses to install combinations that would run every worker twice. The manifests below are for writing them by hand.
:::

為 API、編排工作執行緒、排程器工作執行緒和後台任務工作執行緒建立單獨的部署。為每個 Deployment 使用相同的映像和 Secret。僅直接在每個容器上設定特定於角色的環境變數。

編排工作執行緒 Deployment 具有以下形狀：

```yaml title="k8s/orchestration-worker.yaml"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orchestration-worker
spec:
  replicas: 1
  selector:
    matchLabels:
      app: orchestration-worker
  template:
    metadata:
      labels:
        app: orchestration-worker
    spec:
      containers:
        - name: worker
          image: your-registry/mastra-workers:latest
          env:
            - name: MASTRA_WORKERS
              value: orchestration
            - name: MASTRA_STEP_EXECUTION_URL
              value: http://api:4111/api
          envFrom:
            - secretRef:
                name: mastra-secrets
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
```

使用`MASTRA_WORKERS: scheduler` and `MASTRA_WORKERS: backgroundTasks` for the other worker Deployments. Set `MASTRA_WORKERS: 'false'` on the API Deployment and expose the API with a Service. Give every process access to the same database and PubSub backend. Configure the API auth provider with a worker token, then expose that token to the orchestration worker as `MASTRA_WORKER_AUTH_TOKEN`. See [Deploy Mastra to Kubernetes](/integrations/deploy/kubernetes) for the base Kubernetes resources.

應用清單，然後驗證 pod 和 API：

```bash
kubectl apply -f k8s/
kubectl get pods
kubectl port-forward svc/api 4111:4111
```

在單獨的終端機中，請求 API 路由：

```bash
curl http://localhost:4111/api/agents
```

### 步驟執行 URL {/* #step-execution-url */}

在完全拆分的部署中，編排工作人員透過 HTTP 將Workflow步驟執行委託給 API。放`MASTRA_STEP_EXECUTION_URL` to the API's internal URL, including the `/api` prefix:

```bash
MASTRA_STEP_EXECUTION_URL=http://api:4111/api
```

如果沒有此變量，編排工作執行緒會嘗試在自己的進程中執行步驟，而該進程無法存取分割部署中的完整 Mastra 執行緒。

端點使用伺服器的正常身份驗證管道。如果 API 有驗證Provider，請設定`MASTRA_WORKER_AUTH_TOKEN` to a bearer token that provider accepts. Mastra forwards the value as an `Authorization: Bearer` credential. The configured auth provider validates the token. See [Worker authentication](/docs/auth/workers) for server configuration and other credential formats.

### 規模工人 {/* #scale-workers */}

編排和後台任務工作人員可以水平擴展。 PubSub 消費者群組在其實例之間分發事件：

```bash
docker compose up -d --scale orchestration-worker=3
docker compose up -d --scale background-task-worker=2
```

對於 Kubernetes，手動更改部署副本計數或使用 Horizo​​ntalPodAutoscaler：

```bash
kubectl scale deployment/orchestration-worker --replicas=3
kubectl scale deployment/background-task-worker --replicas=2
```

您可以執行多個調度程式工作者。每個計劃事件都由一個實例聲明，如中所述[Scheduler worker](#scheduler-worker).

### 健康檢查 {/* #health-checks */}

`GET /health` on `PORT`, or port `4111` when `PORT` isn't set. The endpoint returns `503` while `startWorkers()` is initializing and `200` after every selected worker starts successfully. Use this endpoint for deployment readiness checks. If you also use it for liveness checks, configure a startup probe or an initial delay that allows worker initialization to finish.

### 崩潰恢復 {/* #crash-recovery */}

分散式 PubSub 後端會保留未確認的事件，這使得編排和後台任務工作人員可以在重新啟動後恢復。當 API 不可用時，失敗的步驟執行請求會導致事件再次傳遞。

當工作人員在事件Workflow步驟期間停止時，Agent會在之後將該步驟的事件重新傳遞給另一個工作人員`reclaimIdleMs` (60 seconds by default) with Redis or Valkey Streams, or after the ack deadline with Google Cloud Pub/Sub, so instances that boot meanwhile don't restart the run. Keep `reclaimIdleMs` at 30 seconds or more: an event reclaimed sooner can arrive while the stopped worker's hold on the step is still active, and is dropped.

一個步驟可以運行多次。如果工作執行緒在某個步驟期間停止，或在該步驟完成之後但在發布結果之前停止，則該步驟會在其事件重新傳遞時再次執行。使步驟具有冪等的副作用。看[restarting active workflow runs](/docs/workflows/overview#restarting-active-workflow-runs) for how to build an idempotency key for a step, and [make tools safe to repeat](/docs/harness/durable-agents#make-tools-safe-to-repeat) for agent tools.

調度程序重新啟動後從目前時間計算下一次觸發時間。它不會重播在不可用時已過的時間表。

如果在執行預設引擎Workflow運行時實例崩潰，[recovery loop](/docs/workflows/overview#recovery-loop) of an instance running the orchestration worker restarts the run at the first pass after the run's lease expired and `recovery.workflowGraceMs` passed. A `mastra worker` process calls `stopWorkers()` on `SIGTERM` and exits without `shutdown()`. The default-engine runs it was executing wait as long as a crashed instance's. See [known limitations](#known-limitations) and [durable agent crash recovery](/docs/harness/durable-agents#crash-recovery).

## 已知的限制 {/* #known-limitations */}

* **無死信隊列**：失敗的事件將被確認並重試，但對於所有重試後都失敗的事件沒有 DLQ。
* **計劃事件可能會遺失**：如果調度程序崩潰或在聲明事件後無法發布，則該事件可能不會觸發，並且 Mastra 不會自動重播它。
* **API 崩潰後運行陷入「運行」狀態**：Workflow步驟執行期間發生崩潰，導致執行失敗`running` status without an automatic retry. For [durable agents](/docs/harness/durable-agents), configure `recovery.durableAgents: 'auto'` so a server restart automatically re-drives orphaned runs. See [Crash recovery](/docs/harness/durable-agents#crash-recovery) for details.
