# 回饋

**添加於：** `@mastra/core@1.18.0`

回饋 API 儲存和查詢人機互動可觀察性訊號，例如評分、按讚、評論和更正。使用[feedback guide](/docs/observability/feedback) for usage patterns.

## 使用範例 {/* #usage-example */}

以下範例透過可觀察性入口點記錄持久追蹤的評級。`addFeedback()` is optional on the entrypoint, so check that the active observability implementation supports it before calling it.

```typescript
if (!mastra.observability.addFeedback) {
  throw new Error('Feedback is not supported by the active observability implementation')
}

await mastra.observability.addFeedback({
  traceId: 'trace-123',
  spanId: 'span-456',
  feedback: {
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
    comment: 'Helpful answer.',
  },
})
```

## 創建回饋 {/* #create-feedback */}

### `addFeedback(args)` {/* #addfeedbackargs */}

向配置的導出器發送有關追蹤或跨度的回饋。

```typescript
await mastra.observability.addFeedback?.({
  traceId: 'trace-123',
  spanId: 'span-456',
  feedback: {
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
    comment: 'Helpful answer.',
  },
})
```

<PropertiesTable
  content={[
{ name: 'traceId', type: 'string', description: 'Trace that anchors the feedback target.', isOptional: true },
{ name: 'spanId', type: 'string', description: 'Span that anchors the feedback target.', isOptional: true },
{
  name: 'correlationContext',
  type: 'CorrelationContext',
  description: 'Live span or trace context to emit from without rehydrating the target from storage.',
  isOptional: true,
},
{ name: 'feedback', type: 'FeedbackInput', description: 'Feedback payload to add.' },

沒有`correlationContext`, each exporter handles the target trace or span at its own destination. `MastraStorageExporter` resolves it from local storage. A failed local lookup doesn't block other exporters. `MastraPlatformExporter` doesn't require local storage. Use `flush()` or `shutdown()`耗盡待交付的貨物。

本地查找需要目標跨距的父鏈通過其根，因此回饋繼承正確的根標籤。如果重試後仍然缺少任何祖先，則儲存匯出器會記錄警告並跳過本機寫入。其他出口商仍然收到回饋。

### `createFeedback(args)` {/* #createfeedbackargs */}

透過Observability儲存域建立一條回饋記錄。存儲級呼叫直接寫入存儲，因此包括`timestamp`.

```typescript
await observability.createFeedback({
  feedback: {
    feedbackId: 'feedback-1',
    timestamp: new Date(),
    traceId: 'trace-123',
    spanId: 'span-456',
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
    comment: 'Helpful answer.',
  },
})
```

HTTP 和客戶端 SDK 建立路由接受`CreateFeedbackBody`, which requires a nonblank `feedback.traceId` and allows an optional `spanId`. The client supplies a missing `feedbackId` and ISO `timestamp` before retries. Direct OSS HTTP calls can omit them for server defaults. An optional top-level `contextMode` selects supplied context or stored-span resolution. OSS defaults to `"provided"`。平台預設為`"resolve"`。看[訊號寫入選項](/reference/client-js/observability#signal-write-options):

```typescript
await mastraClient.createFeedback({
  feedback: {
    traceId: 'trace-123',
    spanId: 'span-456',
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
  },
})
```

對於OSS HTTP請求，認證使用者的ID優先`feedbackUserId`. Without an authenticated user, supply `feedbackUserId` explicitly or leave it null for anonymous feedback. `userId` describes the span user and isn't used as the HTTP feedback author. Direct storage calls retain the deprecated `userId` author alias when `feedbackUserId` is omitted. An explicit null author stays null.

### `batchCreateFeedback(args)` {/* #batchcreatefeedbackargs */}

透過Observability儲存域建立多個回饋記錄。此方法不會被 HTTP 路由公開，或者`@mastra/client-js`.

```typescript
await observability.batchCreateFeedback({
  feedbacks: [
    {
      feedbackId: 'feedback-1',
      timestamp: new Date(),
      traceId: 'trace-123',
      feedbackSource: 'user',
      feedbackType: 'rating',
      value: 1,
    },
    {
      feedbackId: 'feedback-2',
      timestamp: new Date(),
      traceId: 'trace-123',
      feedbackSource: 'qa',
      feedbackType: 'comment',
      value: 'Needs a citation before shipping.',
    },
  ],
})
```

## 刪除回饋 {/* #delete-feedback */}

### `deleteFeedback(args)` {/* #deletefeedbackargs */}

按 ID 刪除最多 1,000 筆回饋記錄。該操作是冪等的：不存在的 id 將被忽略，並且空的`feedbackIds` array is a no-op. When `organizationId` or `resourceId` is provided, only records matching that scope are deleted.

```typescript
await mastraClient.deleteFeedback({
  feedbackIds: ['feedback-1', 'feedback-2'],
})
```

<PropertiesTable
  content={[
{
  name: 'feedbackIds',
  type: 'string[]',
  description: 'Ids of the feedback records to delete. Accepts at most 1,000 ids.',
},
{
  name: 'organizationId',
  type: 'string',
  description: 'Restricts the delete to records with this organization id.',
  isOptional: true,
},
{
  name: 'resourceId',
  type: 'string',
  description: 'Restricts the delete to records with this resource id.',
  isOptional: true,
},
]}
/>

OSS HTTP路由傳回`{ success: boolean }`. `mastraClient.deleteFeedback()` returns `Promise<{ success: boolean } | { accepted: true }>` to also support Platform backends with queued batch deletion. An accepted response means cleanup is queued, and records can remain readable until cleanup runs. See [client deletion response handling](/reference/client-js/observability#deleting-traces). The storage domain method returns `Promise<void>`. Requests with more than 1,000 ids return `400`, and a server running `@mastra/core` older than `1.66.0` returns `501`. ClickHouse vNext, PostgreSQL vNext, DuckDB, and the in-memory store implement deletion. Every other adapter, including LibSQL and MongoDB, throws `OBSERVABILITY_STORAGE_DELETE_FEEDBACK_NOT_IMPLEMENTED`.

在 ClickHouse 上，刪除使用主回饋事件表上的輕量級刪除來刪除讀取中的行，包括 OLAP 查詢，但不能保證立即實際刪除，因此開源部署必須配置一個[observability retention period](/reference/storage/retention) to physically purge them. Each request is marked applied once its delete succeeds; if the delete fails, the request stays unapplied, doesn't block `updateFeedbackReviewStatus()` on the still-visible feedback, and you retry by calling `deleteFeedback()` again. `updateFeedbackReviewStatus()` also retries the delete and throws a not-found error if the retry succeeds, or saves the new status and throws the delete's error if it fails again. Open-source deployments have no background reconciler. ClickHouse applies a TTL to deletion requests only when all five signals have finite retention. See [ClickHouse native TTL](/reference/storage/retention#clickhouse-native-ttl). Delete APIs leave the separate delta cursor table untouched. Its rows contain identifiers rather than feedback payloads and expire within two days.

### `deleteScores(args)` {/* #deletescoresargs */}

按 id 最多刪除 1,000 筆分數記錄。它的行為就像`deleteFeedback()` with `scoreIds` in place of `feedbackIds`, and Oracle Database also implements it. Unsupported adapters throw `OBSERVABILITY_STORAGE_DELETE_SCORES_NOT_IMPLEMENTED`.

```typescript
await mastraClient.deleteScores({
  scoreIds: ['score-1', 'score-2'],
})
```

## 更換回饋 {/* #replace-feedback */}

`PUT /api/observability/feedback/:feedbackId`接受完整的`{ feedback: { ... } }` replacement. Keep the original `feedbackId`, `traceId`, and `timestamp`, and include every field you want to retain. Omitted optional fields are cleared. The URL and body IDs must match. See [the client example](/reference/client-js/observability#replacing-feedback).

OSS 在返回成功之前寫入其配置的存儲，並獨立通知支援導出器。`contextMode` has the same meaning as on create. In `"resolve"` mode, the local trace or span must exist. A missing feedback record is created from the full replacement. Changing an existing record's trace or timestamp returns `409`.

記憶體中、PostgreSQL vNext、DuckDB 和 ClickHouse vNext 儲存支援替換。查看`capabilities.feedbackReplacement` on the server. Unsupported versions return `501`. Sequential retries of the original HTTP create don't undo a replacement. Direct storage `createFeedback()` calls retain upsert behavior. Pass `onConflict: 'ignore'` to keep an existing record.

ClickHouse 支援使用現有架構，無需遷移。來自不同進程的並發寫入可能會發生競爭，因此它不能保證重疊創建和替換之間的順序。使用此適配器時，將編輯序列化至相同回饋記錄。

若要在不依賴本機儲存的情況下將取代傳送至配置的匯出器，請使用可觀察性入口點：

```typescript
await mastra.observability.replaceFeedback?.({
  traceId: 'trace-123',
  feedback: {
    feedbackId: 'feedback-1',
    timestamp: new Date('2026-11-11T12:00:00.123Z'),
    feedbackType: 'thumbs',
    value: -1,
  },
})
```

每個出口商獨立處理其目的地。`MastraStorageExporter` resolves local span context when needed, and `MastraPlatformExporter` sends a PUT to Platform. Exporters without a replacement handler skip the event. `flush()` and `shutdown()` wait for pending deliveries.

## 更新審核狀態 {/* #updating-review-status */}

若要變更已設定的匯出器目標的稽核狀態，請傳遞回饋 ID 和`"reviewed"` or `"needs-review"`:

```typescript
await mastra.observability.updateFeedbackReviewStatus?.({
  feedbackId: 'feedback-123',
  reviewStatus: 'reviewed',
})
await mastra.observability.flush()
```

即使回饋未儲存在本機，也會將更新稽核傳送給支援它們的每個匯出器。稱呼`flush()` or `shutdown()` to wait for pending deliveries.

## HTTP 路由 {/* #http-routes */}

這些路由屬於 Mastra 運行時並使用其配置的可觀察性儲存。它們與[unversioned Mastra Platform Feedback API](/docs/mastra-platform/api#feedback-api), which doesn't provide a feedback creation route.

|方法|路徑|目的|許可 |
| - | - | - | - |
|`GET` | `/api/observability/feedback` | List feedback records | `observability:read` |
| `POST` | `/api/observability/feedback` | Create a feedback record | `observability:write` |
| `PUT` | `/api/observability/feedback/:feedbackId` | Replace a complete feedback record | `observability:write` |
| `DELETE` | `/api/observability/feedback` | Delete feedback records by id | `observability:delete` |
| `DELETE` | `/api/observability/scores` | Delete score records by id | `observability:delete` |
| `PATCH` | `/api/observability/feedback/:feedbackId/review-status` | Update review status | `observability:write` |
| `POST` | `/api/observability/feedback/aggregate` | Return one aggregate value | `observability:read` |
| `POST` | `/api/observability/feedback/breakdown` | Group feedback by dimensions | `observability:read` |
| `POST` | `/api/observability/feedback/timeseries`|按間隔進行鏟鬥回饋 |`observability:read` |
| `POST` | `/api/observability/feedback/percentiles`|回傳百分位數系列 |`observability:read` |

### 列出查詢參數 {/* #list-query-parameters */}

`GET /api/observability/feedback`將其參數作為 URL 查詢參數。這[Mastra Platform Feedback API](/docs/mastra-platform/api#feedback-api) accepts the same parameters on its `GET /feedback` endpoint.

```bash
curl -sS "http://localhost:4111/api/observability/feedback?traceId=trace-123&environment=production&feedbackType=rating&page=0&perPage=20"
```

每一個領域[`FeedbackFilter`](#feedbackfilter) is accepted as a top-level query parameter with the same name, for example `traceId`, `spanId`, `feedbackType`, `feedbackSource`, `feedbackUserId`, `reviewStatus`, `entityName`, `environment`, `experimentId`, or `tags`. Repeat a parameter to pass multiple values where the filter accepts an array, such as `feedbackType=rating&feedbackType=thumbs`. Pass object-valued filters such as `timestamp` as JSON, for example `timestamp={"start":"2026-01-01T00:00:00Z"}` URL-encoded.
