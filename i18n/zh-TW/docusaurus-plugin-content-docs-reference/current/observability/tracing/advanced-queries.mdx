# 查詢 Trace 和 Span

使用結構化篩選條件查詢已完成的 Trace 或 Span，也能彙總數量、錯誤率、延遲百分位數、token 用量與成本。每項操作均可透過用戶端 SDK、HTTP API 及 CLI 使用：

| 操作 | 用途 | 使用者端 SDK | HTTP 端點 | CLI 命令 |
| - | - | - | - | - |
| [查詢 Trace](#query-traces) | 根據根 Span 欄位或關聯 Span 的條件列出匹配的 Trace。 | `queryTraces()` | `POST /api/observability/traces/query` | `mastra api trace query` |
| [查詢 Span](#query-spans) | 列出各個 Trace 中的 Span，包括巢狀的 Agent 執行和 Tool 呼叫。 | `querySpans()` | `POST /api/observability/spans/query` | `mastra api span query` |
| [聚合 Trace](#aggregate-traces) | 計算符合條件的 Trace 指標，可依欄位分組或依時間切分區間。 | `aggregateTraces()` | `POST /api/observability/traces/aggregate` | `mastra api trace aggregate` |
| [聚合 Span](#aggregate-spans) | 計算任意層級中匹配的各個 Span 的指標。 | `aggregateSpans()` | `POST /api/observability/spans/aggregate` | `mastra api span aggregate` |

Trace 操作共用一組 [Trace 選取條件](#select-traces)：根 Span 謂詞與 `spans.some` / `spans.none` 子句。Span 操作共用直接套用於 Span 的謂詞，不支援巢狀的 `spans` 子句。查詢與聚合同一種紀錄時，可以重複使用選取條件。

| 選項 | 查詢 Trace | 查詢 Span | 聚合 Trace 或 Span |
| - | - | - | - |
| 時間範圍的最大長度 | 無上限 | 無上限 | 365 天 |
| 分頁 | 鍵集分頁、頁碼分頁或增量輪詢 | 僅支援鍵集分頁 | 不分頁；`limit` 指定傳回的分組數 |
| `orderBy` 的形式 | 單一元素陣列 | 單一元素陣列 | 單一物件 |

CLI 命令將過濾條件和請求選項合併為一個 JSON 參數，並把回應包在 `data` 中。要查看查詢結果的詳情，可用其 `traceId` [取得完整 Trace](/reference/client-js/observability#getting-a-specific-trace)，或呼叫 `getSpan(traceId, spanId)` 取得單個 Span。

這些端點採用與其他可觀測性路由相同的身份驗證機制，並要求 `observability:read` 權限。每個請求都必須指定時間範圍。

這些 API 的時間範圍限制與資料保留期間是兩回事。Mastra Platform 託管的 Trace 適用所訂方案的保留期間。保留政策、專案認證資訊及區域端點，請參閱 [在 Mastra Platform 查詢可觀測性資料](/docs/mastra-platform/observability#query-observability-data)。

## 檢查能力 {/* #check-capabilities */}

設定的可觀測性儲存系統必須支援相應 API。展示功能前，呼叫 `getObservabilityCapabilities()` 或 `GET /api/observability/capabilities`，檢查以下能力標誌：

| 能力 | 儲存系統功能 | 支援的操作 |
| - | - | - |
|`traceQuery` | `trace-query` | `queryTraces()` |
| `spanQuery` | `span-query` | `querySpans()` |
| `spanQueryDurationSort` | `span-query-duration-sort` | 在 `querySpans()` 中透過 `orderBy` 按 `durationMs` 排序 |
| `spanQueryModelProviderSort` | `span-query-model-provider-sort` | 在 `querySpans()` 中透過 `orderBy` 按 `model` 或 `provider` 排序 |
| `spanQueryContextFields` | `span-query-context-fields` | 在 Span 查詢和聚合中增加身份、上下文及父級或根實體謂詞 |
| `spanQueryModelFields` | `span-query-model-fields` | 在 Span 查詢和聚合中使用 `model` 與 `provider` 謂詞 |
|`traceAggregate` | `trace-aggregate` | `aggregateTraces()` |
| `spanAggregate` | `span-aggregate` | `aggregateSpans()` |
| `traceQueryRootDuration` | `trace-query-root-duration` | Trace 範圍內的 `durationMs` 謂詞 |
| `traceQueryTimeToFirstChunk` | `trace-query-time-to-first-chunk` | `timeToFirstChunkMs` 謂詞及結果 |
| `traceQueryTimeToFirstChunkSort` | `trace-query-time-to-first-chunk-sort` | 透過 `orderBy` 按 `timeToFirstChunkMs` 排序 |
| `traceQueryTimeToFirstToken` | `trace-query-time-to-first-token` | `timeToFirstTokenMs` 謂詞及結果 |
| `traceQueryTimeToFirstTokenSort` | `trace-query-time-to-first-token-sort` | 透過 `orderBy` 按 `timeToFirstTokenMs` 排序 |
| `aggregateTimeToFirstMeasures` | `aggregate-time-to-first-measures` | 在 `aggregateTraces()` 和 `aggregateSpans()` 中使用 `timeToFirstToken.*` 與 `timeToFirstChunk.*` 指標 |
| `traceQueryContextIds` | `trace-query-context-ids` | `runId`、`sessionId`、`userId` 和 `organizationId` 謂詞 |
| `traceQueryContextFields` | `trace-query-context-fields` | `requestId`、`serviceName` 和 `experimentId` 謂詞 |
| `traceQueryRootSpanFields` | `trace-query-root-span-fields` | Trace 範圍內的 `name` 與 `spanType` 謂詞、維度及 `countDistinct` 指標 |
| `traceQueryRootEntityId` | `trace-query-root-entity-id` | Trace 範圍內的 `entityId` 謂詞、維度及 `countDistinct` 指標 |
| `traceQueryOutcomeFields` | `trace-query-outcome-fields` | Trace 和 `spans.some` / `spans.none` 謂詞中的 `outcome` 與 `stopReason`、Trace 維度和值發現，以及 Trace 結果中的根 Span 結果欄位 |
| `spanQueryOutcomeFields` | `span-query-outcome-fields` | `querySpans()` 和 `aggregateSpans()` 中的 `outcome` 與 `stopReason` 謂詞、維度及 `countDistinct` 指標，以及 Span 結果中的結果欄位 |
| `traceQueryDiscovery` | `trace-query-discovery` | [發現欄位和值](#discover-fields-and-values) |
| `traceQueryTenantScope` | `trace-query-tenant-scope` | [可信租戶範圍](#trusted-tenant-scope) |

缺少 `traceAggregate` 表示伺服器不支援 Trace 聚合：沒有聚合路由的伺服器傳回 `404`，儲存系統不支援該功能時傳回 `501 TRACE_AGGREGATE_UNSUPPORTED`。缺少 `spanAggregate` 對 Span 聚合含義相同；儲存系統不支援時傳回 `501 SPAN_AGGREGATE_UNSUPPORTED`。若儲存系統缺少某項子功能，使用受該功能限制的欄位會在執行儲存作業前傳回 `501`。不支援的根 Span `name`、`spanType`、`entityId` 欄位，以及需要 `spanQueryContextFields` 的 Span 謂詞，則傳回 `422` 和 `field_not_allowed` 問題。不支援 `spanQuery` 的儲存系統傳回 `501 SPAN_QUERY_UNSUPPORTED`。

## 選擇 Trace {/* #select-traces */}

每個請求使用以下兩個欄位選擇 Trace：

| 欄位 | 必填 | 說明 |
| - | - | - |
| `timeRange` | 是 | Trace 開始時間範圍。`from` 為閉區間端點，`to` 為開區間端點。兩者必須是 ISO 時間戳，且 `from` 必須早於 `to`。 |
| `where` | 否 | 遞迴的 Trace 謂詞，支援標量條件及 `spans.some` 或 `spans.none` 子句。 |

以下選擇條件匹配 8 月第一週內包含出錯 Tool 呼叫的 Trace：

```typescript
const selection = {
  timeRange: {
    from: '2026-08-01T00:00:00.000Z',
    to: '2026-08-08T00:00:00.000Z',
  },
  where: {
    spans: {
      some: {
        op: 'and',
        args: [
          { op: 'eq', left: { path: 'spanType' }, right: { literal: 'tool_call' } },
          { op: 'exists', path: 'error' },
        ],
      },
    },
  },
}
```

同一組選擇條件在兩個 API 中匹配相同的 Trace。聚合統計的正是查詢會列出的那些 Trace。

`spans.some` 子句要求同一個 Span 滿足其全部條件。在此例中，該 Span 既必須是 Tool 呼叫，又必須包含錯誤。使用 `spans.none` 可找出不存在符合條件的 Span 的 Trace。

Span 子句檢查目前根 Span 和目前子 Span。根級 `timeRange` 僅約束所選目前根 Span 的 `startedAt`；關聯 Span 自身的時間戳即使落在該範圍外，仍可參與匹配。關聯紀錄僅透過相同且非空的 `traceId` 關聯。

### 欄位和運算符 {/* #fields-and-operators */}

| 謂詞範圍 | 欄位 | 運算符 |
| - | - | - |
| Trace | `traceId`, `threadId`, `resourceId`, `runId`, `sessionId`, `userId`, `organizationId`, `requestId`, `serviceName`, `experimentId`, `entityId`, `entityName`, `entityType`, `name`, `spanType`, `environment`, `status`, `outcome`, `stopReason` | `eq`, `ne`, `in`, `notIn`, `exists`, `notExists` |
| Trace 元資料 | `metadata.<key>` | `eq`, `ne`, `in`, `notIn`, `exists`, `notExists` |
| Trace | `startedAt`, `endedAt`, `durationMs`, `timeToFirstChunkMs`, `timeToFirstTokenMs` | `eq`, `ne`, `in`, `notIn`, `lt`, `lte`, `gt`, `gte`, `exists`, `notExists` |
| Trace | `tags` | `includes`, `notIncludes`, `exists`, `notExists` |
| Span | `name` | `eq`, `ne`, `in`, `notIn`, `exists`, `notExists`, `matches`, `notMatches` |
| Span | `spanType`, `model`, `provider`, `status`, `outcome`, `stopReason`, `entityType`, `entityId`, `entityName`, `entityVersionId`, `parentEntityVersionId`, `rootEntityVersionId`, `runId`, `sessionId`, `userId`, `organizationId`, `requestId`, `serviceName`, `experimentId` | `eq`, `ne`, `in`, `notIn`, `exists`, `notExists` |
| Span | `startedAt`, `endedAt`, `durationMs`, `timeToFirstChunkMs`, `timeToFirstTokenMs` | `eq`, `ne`, `in`, `notIn`, `lt`, `lte`, `gt`, `gte`, `exists`, `notExists` |
| Span | `error` | `exists`, `notExists` |

Trace 範圍內的 `name`、`spanType` 和 `entityId` 讀取目前根 Span，因此 `{ op: 'eq', left: { path: 'spanType' }, right: { literal: 'workflow_run' } }` 會選擇由 Workflow 執行啓動的 Trace。在 `spans.some` 或 `spans.none` 內，相同欄位可以匹配 Trace 中的任意 Span。

使用 `{ op: 'and', args: [...] }`、`{ op: 'or', args: [...] }` 和 `{ op: 'not', arg: ... }` 組合謂詞。比較謂詞將欄位引用放在左側、字面值放在右側。成員謂詞在 `value` 中使用欄位引用，在 `set` 中使用同型別字面值陣列。標籤謂詞透過 `path` 指定儲存的標籤集合。`includes` 和 `notIncludes` 還需在 `value` 中指定一個標籤，而 `exists` 和 `notExists` 只需 `op` 與 `path`。參閱[按標籤過濾](#filter-by-tags)。文本謂詞採用比較謂詞的形式，字面值為字串。參閱[按文本過濾](#filter-by-text)。

字串比較區分大小寫，且不會強制轉換字面值。`matches` 和 `notMatches` 例外：它們不區分大小寫地比較單詞。標準字串欄位按儲存的原始值精確比較；元資料字串值在比較前會去掉首尾空白，詳見下文。耗時、第一個資料區塊耗時及第一個 token 耗時謂詞要求數字，時間戳謂詞要求 ISO 時間戳字串。缺少值既不滿足正向謂詞，也不滿足有序比較，但滿足否定運算符 `ne` 和 `notIn`。如果欄位也必須存在，應將否定謂詞與 `exists` 組合。

#### 按根 Span 耗時過濾 {/* #filter-by-root-duration */}

在 Trace 範圍內，`durationMs` 是目前已完成根 Span 的耗時，單位為毫秒。查詢執行時根據 `endedAt - startedAt` 計算：

```typescript
const slowRootTraces = {
  op: 'gt',
  left: { path: 'durationMs' },
  right: { literal: 5000 },
}
```

這個頂層謂詞不檢查子 Span。相比之下，`spans.some` 中的 `durationMs` 謂詞會檢查目前根 Span 和目前子 Span；即使根 Span 較短，耗時較長的子 Span 也能滿足該子句。

Trace 查詢在評估謂詞前會排除未完成的根 Span。因此，`{ op: 'notExists', path: 'durationMs' }` 找不到執行中的 Trace，也找不到缺少可用 `endedAt` 的異常根 Span。

#### 按第一個資料區塊或 token 的耗時過濾和排序 {/* #filter-and-sort-by-time-to-first-chunk-or-token */}

`timeToFirstChunkMs` 紀錄 Span 的[第一個資料區塊耗時（TTFC）](#time-to-first-chunk-ttfc)，`timeToFirstTokenMs` 紀錄其[第一個 token 耗時（TTFT）](#time-to-first-token-ttft)。在 Trace 範圍內，這些欄位讀取根 Span 的值；在 `spans.some` 或 `spans.none` 內，則讀取各關聯 Span 的值。兩個欄位也都可用於 `orderBy`。

以下謂詞找出根 Agent 等待模型第一個 token 超過 2 秒的 Trace：

```typescript
const slowFirstToken = { op: 'gt', left: { path: 'timeToFirstTokenMs' }, right: { literal: 2000 } }
```

關於 `null`、`0` 以及各項操作所需的能力，請參閱[缺少的第一個資料區塊與 token 耗時值](#missing-first-chunk-and-token-values)。

#### 按結束結果過濾 {/* #filter-by-outcome */}

`outcome` 紀錄 Span 如何結束，例如 `success`、`error`、`abort`、`limit` 或 `unknown`。`stopReason` 紀錄結束原因，例如 `max_steps`。兩者都是自由格式字串，因此自定義 Span 可以紀錄自己的值。它們不同於 `status`；後者只表示 Span 是否紀錄了錯誤。

在 Trace 範圍內，這兩個欄位讀取啓動該 Trace、沒有父 Span 的目前根 Span。在 `spans.some` 或 `spans.none` 內，它們讀取各關聯 Span。若根 Span 成功，但某次 Tool 呼叫觸及步驟上限，該 Trace 不會匹配 Trace 範圍內值為 `limit` 的 `outcome`；應透過 `spans.some` 找出：

```typescript
const hitALimit = {
  spans: {
    some: { op: 'eq', left: { path: 'outcome' }, right: { literal: 'limit' } },
  },
}
```

由尚不支援這些欄位的舊版 SDK 寫入的 Span，以及仍在執行的根 Span，都沒有結束結果。缺少 結束結果表示“未紀錄”，絕不表示成功。可用 `{ op: 'notExists', path: 'outcome' }` 選擇此類 Span。與其他可選字串欄位一樣，`ne` 和 `notIn` 也會匹配缺少值的 Span。

兩個欄位都支援 `eq`、`ne`、`in`、`notIn`、`exists` 和 `notExists`，可用於 Trace 和 Span 聚合分組，並可透過值發現傳回取值。它們不能用於單條 Trace 或 Span 查詢結果的排序。在聚合中，只要欄位包含在 `groupBy` 中，就能用於 `orderBy`。結果還會傳回 `stopReasonContext`，其中包含結束原因的細節，例如 `{ maxSteps: 5 }`。`stopReasonContext` 只供讀取，不能用於過濾、分組或排序。

儲存系統透過 `trace-query-outcome-fields` 功能聲明支援 Trace 查詢和聚合，透過 `span-query-outcome-fields` 聲明支援 Span 查詢和聚合。伺服器將它們報告為 `traceQueryOutcomeFields` 和 `spanQueryOutcomeFields` 能力。使用舊版儲存系統時，結果會省略這些欄位；使用這些欄位的請求會在執行儲存作業前傳回 `501`。

#### 按上下文識別碼過濾 {/* #filter-by-context-identifiers */}

`runId`、`sessionId`、`userId` 和 `organizationId` 可在 Trace 範圍內及 `spans.some` / `spans.none` 內使用。Trace 範圍的謂詞讀取目前根 Span；Span 範圍的謂詞綁定到單個關聯的目前 Span。因此，只紀錄在子 Span 上的執行可以透過 `spans.some` 找到：

```typescript
const sessionTracesWithRun = {
  op: 'and',
  args: [
    { op: 'eq', left: { path: 'organizationId' }, right: { literal: 'org-123' } },
    { op: 'eq', left: { path: 'sessionId' }, right: { literal: 'session-123' } },
    {
      spans: {
        some: { op: 'eq', left: { path: 'runId' }, right: { literal: 'run-42' } },
      },
    },
  ],
}
```

這些識別碼支援 `eq`、`ne`、`in`、`notIn`、`exists` 和 `notExists`。欄位發現會列出它們，但值發現不會傳回其紀錄值。儲存系統透過 `trace-query-context-ids` 功能聲明支援。對舊版儲存系統中的這些欄位使用謂詞，會在執行儲存作業前傳回 `501`；欄位發現也會省略它們。

`requestId`、`serviceName` 和 `experimentId` 採用相同語義，可在 Trace 範圍內及 `spans.some` / `spans.none` 內使用。以下謂詞找出某個子 Span 到達 `payments` 服務的結賬請求。子 Span 紀錄 `metadata: { serviceName: 'payments' }`，根 Span 則保留 `checkout`：

```typescript
const checkoutRequestsThroughPayments = {
  op: 'and',
  args: [
    { op: 'eq', left: { path: 'serviceName' }, right: { literal: 'checkout' } },
    { op: 'exists', path: 'requestId' },
    {
      spans: {
        some: { op: 'eq', left: { path: 'serviceName' }, right: { literal: 'payments' } },
      },
    },
  ],
}
```

儲存系統透過 `trace-query-context-fields` 功能聲明對這三個欄位的支援，伺服器將其報告為 `traceQueryContextFields` 能力。對舊版儲存系統中的任一欄位使用謂詞，會在執行儲存作業前傳回 `501`；欄位發現也會省略它們。

#### 按 Span 屬性過濾 {/* #filter-by-span-properties */}

同一 `spans.some` 或 `spans.none` 子句中的所有條件都作用於同一個目前 Span。例如，下列謂詞找出名為 `medication_lookup` 的失敗 Tool Span；一個 Span 名稱匹配、另一個 Span 含有錯誤，並不能滿足條件：

```typescript
const failedMedicationLookup = {
  spans: {
    some: {
      op: 'and',
      args: [
        { op: 'eq', left: { path: 'name' }, right: { literal: 'medication_lookup' } },
        { op: 'eq', left: { path: 'spanType' }, right: { literal: 'tool_call' } },
        { op: 'exists', path: 'error' },
      ],
    },
  },
}
```

使用 `status` 判斷派生出的 `success` 或 `error` 狀態；如果只需檢查是否存在錯誤詳情，則使用 `error`。

`durationMs` 是 Span 的耗時，單位為毫秒。Span 的 `startedAt` 與 `endedAt` 條件獨立於頂層根 Span 的 `timeRange`，用於過濾關聯 Span：

```typescript
const slowModelCalls = {
  spans: {
    some: {
      op: 'and',
      args: [
        { op: 'eq', left: { path: 'spanType' }, right: { literal: 'model_generation' } },
        { op: 'gt', left: { path: 'durationMs' }, right: { literal: 5000 } },
        {
          op: 'gte',
          left: { path: 'startedAt' },
          right: { literal: '2026-07-15T00:00:00.000Z' },
        },
      ],
    },
  },
}
```

`model` 和 `provider` 讀取 Span 對應的 `model` 與 `provider` 列。若列為空，則回退到舊版 `@mastra/observability` 匯出的字串值 `attributes.model` 和 `attributes.provider`，使現有過濾條件仍能匹配舊 Span。Trace 結果不傳回 `model` 和 `provider`，因為 Trace 可能透過某個 Span 匹配，而其他 Span 使用了不同模型。

```typescript
const selectedModel = {
  spans: {
    some: {
      op: 'and',
      args: [
        {
          op: 'eq',
          left: { path: 'model' },
          right: { literal: '__AI_SDK_ANTHROPIC_MODEL_SONNET__' },
        },
        { op: 'eq', left: { path: 'provider' }, right: { literal: 'anthropic' } },
      ],
    },
  },
}
```

用通用實體欄位標識 Tool 和檢索操作。版本欄位使同一子句能夠按實體譜系限定同一個 Span：

```typescript
const versionedRetrieval = {
  spans: {
    some: {
      op: 'and',
      args: [
        { op: 'eq', left: { path: 'entityType' }, right: { literal: 'rag_ingestion' } },
        { op: 'eq', left: { path: 'entityId' }, right: { literal: 'medication-index' } },
        { op: 'eq', left: { path: 'entityVersionId' }, right: { literal: 'index-v3' } },
        { op: 'eq', left: { path: 'rootEntityVersionId' }, right: { literal: 'agent-v2' } },
      ],
    },
  },
}
```

#### 按元資料過濾 {/* #filter-by-metadata */}

使用 `metadata.<key>` 路徑過濾目前根 Span 上儲存的自訂維度。元資料謂詞對移除前後空白後的非空字串進行精確且區分大小寫的比較；儲存的值中的首尾空白會被忽略。去除空白後為空的值視為缺少。null、數字、布林值、物件和陣列也視為缺少。

```typescript
const messageTrace = {
  op: 'and',
  args: [
    { op: 'eq', left: { path: 'metadata.messageId' }, right: { literal: 'message-123' } },
    { op: 'in', value: { path: 'metadata.actorRole' }, set: ['assistant', 'tool'] },
    { op: 'exists', path: 'metadata.protocolVersion' },
    {
      op: 'or',
      args: [
        { op: 'eq', left: { path: 'metadata.temporalRunId' }, right: { literal: 'run-456' } },
        { op: 'eq', left: { path: 'metadata.externalTraceId' }, right: { literal: 'trace-789' } },
      ],
    },
    { op: 'not', arg: { op: 'exists', path: 'metadata.parentMessageId' } },
  ],
}
```

鍵必須指向一個頂層屬性；空鍵和巢狀路徑會被拒絕。元資料鍵不會去除空白，因此首尾空白仍屬於鍵名的一部分。如果元資料與 `resourceId`、`threadId` 或 `environment` 等標準 Trace 欄位重複，優先使用標準欄位，因為它使用專用儲存欄位。僅當需要元資料物件中的值時，才使用 `metadata.<key>`；元資料值與標準欄位值可能不同。

Trace 查詢的欄位發現會傳回在所選時間範圍內觀察到、可用於查詢的頂層字串元資料欄位。

#### 按標籤過濾 {/* #filter-by-tags */}

標籤是儲存在目前根 Span 上的字串列表，因此使用集合運算符，而不是標量 `in` 和 `notIn`。以下查詢找出帶有人工審核標籤、且不含 `archived` 標籤的生產環境 Trace：

```typescript
const manualReview = {
  op: 'and',
  args: [
    { op: 'eq', left: { path: 'environment' }, right: { literal: 'production' } },
    { op: 'includes', path: 'tags', value: 'manual-review' },
    { op: 'notIncludes', path: 'tags', value: 'archived' },
  ],
}
```

| 運算符 | 匹配條件 |
| - | - |
| `includes` | Trace 含有指定標籤 |
| `notIncludes` | Trace 至少含有一個標籤，但不含指定標籤 |
| `exists` | Trace 至少含有一個標籤 |
| `notExists` | Trace 不含任何標籤 |

標籤按完整字串精確比較，且區分大小寫。`value` 必須是至少包含一個非空白字元的字串。可用 `and` 或 `or` 組合多個 `includes` 謂詞，分別要求同時具備或允許具備多個標籤。未紀錄標籤的 Trace 與標籤列表為空的 Trace 行為相同：兩者都滿足 `notExists`，都不滿足 `includes`、`notIncludes` 或 `exists`。如果未標記的 Trace 也應匹配，請使用 `{ op: 'not', arg: { op: 'includes', ... } }`。

`tags` 只能用於 Trace 謂詞。對 `tags` 使用 `in`、`notIn` 或比較運算符會被拒絕。對 `tags` 進行值發現時，會傳回每個觀察到的標籤，以及帶有該標籤的符合條件 Trace 數量。

#### 按文本過濾 {/* #filter-by-text */}

除精確比較外，Span 名稱還支援按單詞匹配。當字面值中的單詞按原順序、以完整單詞形式出現在欄位中時，`matches` 成立；欄位存在但不包含這些單詞時，`notMatches` 成立。以下查詢找出名稱包含“document search”兩個單詞的 Span 所屬的 Trace：

```typescript
const documentSearch = {
  spans: {
    some: {
      op: 'matches',
      left: { path: 'name' },
      right: { literal: 'document search' },
    },
  },
}
```

字面值和儲存的值都會先轉為小寫，再切分為單字。單字由連續的字母、數字與組合記號構成；標點、空白或 `_` 等其他字元會分隔單字。因此，`incorrect` 符合 `This answer is incorrect.`，但不符合 `This was incorrectly formatted.`；`gpt 5` 符合 `llm: 'gpt-5'`。多個單字必須依序形成連續詞組。重音符號會保留：`café` 不符合 `cafe`。文字會先正規化為 Unicode NFC，因此無論重音是字母的一部分，還是獨立記號，`café` 都能符合；組合記號仍屬於所在單字，因此 `नमस` 不符合 `नमस्ते`。土耳其文 `İ` 會轉成 `i`，希臘文詞尾 `ς` 等同於 `σ`。PostgreSQL 依資料庫語系設定轉換大小寫；若資料庫以 `C` 語系建立，ASCII 以外字母不會折疊大小寫。請使用 `en_US.UTF-8` 等 UTF-8 語系，以取得一致結果。

| 運算符 | 匹配條件 |
| - | - |
| `matches` | 欄位包含字面值的單詞，且這些單詞構成連續、完整的詞組 |
| `notMatches` | 欄位存在，但不包含該詞組 |

字面值必須至少包含一個字母或數字，否則請求以 `422 TRACE_QUERY_INVALID` 失敗。欄位缺少時，兩個運算符都不匹配。如果缺少該欄位的紀錄也應匹配，請使用 `{ op: 'not', arg: { op: 'matches', ... } }`。文本運算符僅適用於 Span 的 `name`；其他字串欄位、數字、時間戳、標籤及元資料都不支援。不支援子字串、通配符、正則運算式或模糊匹配，也不能跨多個欄位搜索。

### 查詢限制 {/* #query-limits */}

若查詢超出以下任一限制，規劃器會在執行儲存作業前拒絕：

| 輸入 | 上限 |
| - | - |
| 謂詞巢狀深度 | 12 層 |
| 謂詞節點數 | 100 |
| 關聯的 `spans` 子句數 | 共 8 個 |
| 單個 `in` 或 `notIn` 集合中的值 | 100 個 |
| 比較字面值與成員值 | 共 1,000 個 |
| 字串字面值 | 4,096 UTF-8 位元組 |
| 原始謂詞路徑 | 128 UTF-8 位元組 |
| `page.limit` | 1,000 |
| HTTP 請求本文 | 256 KiB |

每個比較字面值計為一個字面值。`in` 或 `notIn` 集合中的每個成員也各計一個，即使該集合未超過自身的數量上限。

Hono 和 Fastify 在解析 JSON 前強制執行請求本文大小限制。Express 和 Elysia 會在路由處理程序或儲存系統執行前拒絕過大的請求本文，但如果沒有可靠的 `Content-Length` 標頭，宿主框架可能已經解析了請求。若需要嚴格的解析前記憶體上限，請設定宿主應用的 JSON 解析器或請求本文大小限制。

## 查詢 Trace {/* #query-traces */}

使用 `queryTraces()`、`mastra api trace query` 或 `POST /api/observability/traces/query` 列出所選 Trace。三種方式接受相同的請求；該請求在 [Trace 選擇條件](#select-traces) 上增加排序和分頁。

### 使用使用者端 SDK 查詢 Trace {/* #query-traces-with-the-client-sdk */}

以下查詢找出包含出錯 Tool 呼叫的 Trace：

```typescript
import { MastraClient } from '@mastra/client-js'

const mastraClient = new MastraClient({ baseUrl: 'http://localhost:4111' })

const result = await mastraClient.queryTraces({
  timeRange: {
    from: '2026-08-01T00:00:00.000Z',
    to: '2026-08-08T00:00:00.000Z',
  },
  where: {
    spans: {
      some: {
        op: 'and',
        args: [
          { op: 'eq', left: { path: 'spanType' }, right: { literal: 'tool_call' } },
          { op: 'exists', path: 'error' },
        ],
      },
    },
  },
  orderBy: [{ field: 'startedAt', direction: 'desc' }],
  page: { limit: 25 },
})
```

### 使用 CLI 查詢 Trace {/* #query-traces-with-the-cli */}

將查詢作為單個 JSON 參數傳給 `mastra api trace query`。過濾條件和分頁選項都放在 JSON 輸入中。以下命令與 SDK 示例執行相同的失敗 Tool 查詢：

```bash
mastra api --url http://localhost:4111 trace query '{
  "timeRange": {
    "from": "2026-08-01T00:00:00.000Z",
    "to": "2026-08-08T00:00:00.000Z"
  },
  "where": {
    "spans": {
      "some": {
        "op": "and",
        "args": [
          { "op": "eq", "left": { "path": "spanType" }, "right": { "literal": "tool_call" } },
          { "op": "exists", "path": "error" }
        ]
      }
    }
  },
  "orderBy": [{ "field": "startedAt", "direction": "desc" }],
  "page": { "limit": 25 }
}'
```

顯式指定的 `--url` 指向本地 Mastra 伺服器。如果省略，即使本地伺服器正在執行，可觀測性命令仍預設連接 `https://observability.mastra.ai`。身份驗證和區域端點詳見 [CLI 目標解析](/reference/cli/mastra#target-resolution)。目標伺服器及設定的儲存系統必須支援所請求的查詢能力。

使用以下命令檢查該命令：

```bash
mastra api trace query --help
```

對於本地 Mastra 伺服器，使用以下命令查看請求和回應 schema：

```bash
mastra api --url http://localhost:4111 trace query --schema
```

Mastra Platform 目前不提供 `--schema` 使用的 schema 端點。針對任一目標構造查詢時，請參閱[請求欄位](#request-fields)及[欄位和運算符](#fields-and-operators)。要找出專案中已紀錄的欄位和值，請使用[欄位和值發現](#discover-fields-and-values)。

### 傳送 HTTP 請求 {/* #send-an-http-request */}

將同一查詢作為 JSON 請求本文傳送：

```bash
curl --request POST \
  --url http://localhost:4111/api/observability/traces/query \
  --header 'Authorization: Bearer <token>' \
  --header 'Content-Type: application/json' \
  --data '{
    "timeRange": {
      "from": "2026-08-01T00:00:00.000Z",
      "to": "2026-08-08T00:00:00.000Z"
    },
    "where": {
      "spans": {
        "some": {
          "op": "and",
          "args": [
            { "op": "eq", "left": { "path": "spanType" }, "right": { "literal": "tool_call" } },
            { "op": "exists", "path": "error" }
          ]
        }
      }
    },
    "orderBy": [{ "field": "startedAt", "direction": "desc" }],
    "page": { "limit": 25 }
  }'
```

### 請求欄位 {/* #request-fields */}

| 欄位 | 必填 | 說明 |
| - | - | - |
| `timeRange` | 是 | Trace 開始時間範圍。`from` 為閉區間端點，`to` 為開區間端點。兩者必須是 ISO 時間戳，且 `from` 必須早於 `to`。 |
| `where` | 否 | 遞迴的 Trace 謂詞，支援標量條件及 `spans.some` 或 `spans.none` 子句。 |
| `orderBy` | 否 | 單元素陣列，按 `startedAt`、`endedAt`、`timeToFirstChunkMs` 或 `timeToFirstTokenMs` 以 `asc` 或 `desc` 排序。預設為 `startedAt desc`。增量模式不接受此欄位。 |
| `page` | 否 | `{ limit, after }`。`limit` 預設為 100，最大為 1000。將不透明的 `page.next` 值作為 `after` 傳入。 |
| `pagination` | 否 | 頁碼分頁：`{ page, perPage }`。預設第 0 頁、每頁 10 條結果。`perPage` 最大為 100。 |
| `mode` | 否 | 設為 `'delta'`，使用增量游標輪詢，代替 `page` 或 `pagination`。 |
| `after` | 否 | 僅用於增量模式。傳入頁碼分頁結果或上次輪詢傳回的不透明 `deltaCursor`；省略時建立目前水位。 |
| `limit` | 否 | 僅用於增量模式。每批結果的上限，預設 10，最大 100。 |

未知欄位會被拒絕。請求不能選擇投影、聲明連接、請求計數或指標，也不能控制授權。計數和指標請使用 [`aggregateTraces()`](#aggregate-traces)。請求本文上限為 256 KiB。

使用鍵集分頁的查詢會傳回已完成 Trace 的簡要信息，以及下一頁游標：

```json
{
  "traces": [
    {
      "traceId": "trace-123",
      "rootSpanId": "span-123",
      "name": "agent run: support-agent",
      "entityId": "support-agent",
      "parentSpanId": null,
      "createdAt": "2026-08-03T10:00:00.000Z",
      "metadata": null,
      "inputPreview": "Where is my order?",
      "outputPreview": "Your order arrives tomorrow.",
      "errorPreview": null,
      "threadId": "thread-123",
      "resourceId": "resource-123",
      "startedAt": "2026-08-03T10:00:00.000Z",
      "endedAt": "2026-08-03T10:00:01.000Z",
      "entityName": "support-agent",
      "entityType": "agent",
      "environment": "production",
      "status": "success",
      "timeToFirstChunkMs": 412,
      "timeToFirstTokenMs": 380,
      "outcome": "success",
      "stopReason": null,
      "stopReasonContext": null
    }
  ],

```

回應包含 `name`、`createdAt`、身份欄位、`metadata`，以及輸入、輸出和錯誤的預覽。受支援的可空欄位即使沒有紀錄值，也會以 `null` 出現。若儲存系統缺少可選功能，依賴該功能的欄位會被省略。預覽僅概括資料內容；完整輸入、輸出和錯誤詳情需取得完整 Trace。

只有設定的儲存系統支援時，結果才包含 `timeToFirstChunkMs` 和 `timeToFirstTokenMs`。參閱[按第一個資料區塊或 token 的耗時過濾和排序](#filter-and-sort-by-time-to-first-chunk-or-token)。`outcome`、`stopReason` 和 `stopReasonContext` 讀取根 Span；僅當儲存系統支援 `traceQueryOutcomeFields` 能力時才會出現。若根 Span 未紀錄這些值，則傳回 `null`。參閱[按結束結果過濾](#filter-by-outcome)。

回應不包含匹配謂詞的關聯 Span。選中結果後，使用 [`getTrace()`](/reference/client-js/observability#getting-a-specific-trace) 載入完整 Trace。

#### CLI 回應 {/* #cli-responses */}

CLI 將 API 回應包在 `data` 中：

```json
{
  "data": {
    "traces": [],
    "page": { "next": null }
  }
}
```

從 `data.traces` 讀取結果。鍵集查詢的分頁元資料位於 `data.page.next`，頁碼分頁位於 `data.pagination`；增量輪詢則使用 `data.deltaCursor` 和 `data.delta.hasMore`。

每次 CLI 呼叫只執行一次查詢。要取得下一鍵集頁，在下次請求中將 `data.page.next` 作為 `page.after` 傳入。增量輪詢時，重複執行命令，並將 `data.deltaCursor` 作為頂層 `after` 值。保持相同的時間範圍和謂詞。各模式的行為及輪詢限制詳見[分頁與錯誤](#pagination-and-errors)。

要查看所選 Trace，使用 `mastra api --url http://localhost:4111 trace get <traceId> --verbose`。目標和身份驗證方式應與查詢相同。

### 分頁與錯誤 {/* #pagination-and-errors */}

#### 選擇分頁模式 {/* #choose-a-pagination-mode */}

Trace 查詢支援三種互斥模式：

| 模式 | 請求欄位 | 回應元資料 |
| - | - | - |
| 鍵集分頁（預設） | `page: { limit, after }` | `page: { next }` |
| 頁碼分頁 | `pagination: { page, perPage }` | `pagination: { total, page, perPage, hasMore }`；支援增量輪詢時還包含 `deltaCursor` |
| 增量輪詢 | `mode: 'delta'`，可選頂層 `after` 和 `limit` | `delta: { limit, hasMore }` 和 `deltaCursor` |

頁碼從 0 開始計數。每個請求內讀取的總數與各行保持一致。不要混用 `page`、`pagination` 或增量模式。頂層 `after` 和 `limit` 只在增量模式中接受。

#### 載入頁碼分頁結果後輪詢 {/* #poll-after-loading-a-numbered-page */}

使用頁碼分頁回應中的 `deltaCursor`，取代 `listTracesLight()` 從頁碼分頁切換到增量輪詢的流程。結果使用 `traces` 而不是 `spans`，且僅包含已完成的 Trace。設定的儲存系統必須支援增量輪詢。

```typescript
const timeRange = {
  from: '2026-08-01T00:00:00.000Z',
  to: '2026-08-08T00:00:00.000Z',
}
const initial = await mastraClient.queryTraces({
  timeRange,
  pagination: { page: 0, perPage: 100 },
})
if (!initial.deltaCursor) throw new Error('Delta polling is unavailable')

const traces = new Map(initial.traces.map(trace => [trace.traceId, trace]))
let after = initial.deltaCursor

async function poll() {
  let hasMore: boolean
  do {
    const result = await mastraClient.queryTraces({
      timeRange,
      mode: 'delta',
      after,
      limit: 100,
    })
    for (const trace of result.traces) traces.set(trace.traceId, trace)
    after = result.deltaCursor
    hasMore = result.delta.hasMore
  } while (hasMore)
}

await poll()
```

保留 `after`，按應用的輪詢間隔再次呼叫 `poll()`。同一個 Trace 可能同時出現在初始頁和後續批次，或出現在多個批次，因此應按 `traceId` 合併結果。若需載入初始頁未包含的歷史 Trace，請繼續請求剩餘頁碼。

不帶 `after` 的增量請求會傳回空陣列，並建立目前游標；它不會傳回歷史匹配結果。始終保留傳回的游標，即使該批次為空。`hasMore` 表示超過本批上限後仍有匹配的 Trace；為 `true` 時應立即繼續請求。

增量排序使用儲存系統攝取水位及適配器特定的並列排序規則，因此相同時間戳不會使游標產生歧義。增量模式中不要傳入 `orderBy`。鍵集游標與增量游標不可互換，增量游標也不能跨儲存系統適配器使用。

每次輪詢都應保持相同的規範化 `where` 謂詞和完全一致的 `timeRange` 邊界。即使 Trace 後來才完成，時間範圍仍按根 Span 的 `startedAt` 選擇紀錄。將 `timeRange.to` 改為目前時間會使游標失效。選擇條件或授權範圍變化時，應重新載入頁碼分頁結果並使用新游標。批次上限可以調整，無需重新開始。

游標建立後新增的已完成根 Span，以及之後才完成的根 Span，都可能傳回。關聯 Span 在選擇根 Span 時參與評估，但後續寫入關聯紀錄並不保證該 Trace 再次傳回。已刪除或不再匹配的 Trace 不會以刪除事件或墓碑紀錄形式傳回。如需對賬這些變化，請刷新頁碼分頁結果。

ClickHouse 輪詢盡力而為。增量索引與 Trace 紀錄使用不同的物化視圖表。併發查詢可能先看到一張表中的插入，再看到另一張表中的插入，詳見 [ClickHouse 的物化視圖可見性規則](https://github.com/ClickHouse/clickhouse-docs/blob/main/knowledgebase/are_materialized_views_inserted_asynchronously.mdx)。輪詢可能在匹配 Trace 可見前越過索引條目，導致後續輪詢漏掉該 Trace。應定期重新載入頁碼分頁結果，以彌補這些缺口。

ClickHouse 增量索引保留兩天事件，且不會回填歷史行。輪詢中斷超過該保留窗口後，應重新載入頁碼分頁結果。增量輪詢並非持久變更流，無法保證交付每個匹配的 Trace。

#### 鍵集排序與錯誤 {/* #keyset-ordering-and-errors */}

排序是確定性的。Trace 排序會追加按 `traceId` 升序排列作為並列時的次級排序條件。

鍵集游標綁定操作、已接受的規範化查詢和排序規則。更改 Trace 選擇條件、謂詞或排序後重複使用游標，會傳回 `409`。

頁碼分頁交接游標與增量游標也綁定授權狀態。呼叫者的角色或權限變化會使這些游標失效並傳回 `409`。若增量輪詢傳回 `409`，請重新載入頁碼分頁結果，並使用新的 `deltaCursor` 恢復輪詢。格式錯誤的游標傳回 `400`。

游標分頁的順序是確定的，但它並非資料庫快照。兩次分頁請求之間寫入的 Trace 或替換信號，可能改變後續頁面。

PostgreSQL 和 ClickHouse 預設在 15 秒後終止 Trace 查詢，超過資料庫逾時時間則傳回 `504`。可在 `PostgresStoreVNext` 上設定 `observability.traceQueryTimeoutMs`，或在 `ClickhouseStoreVNext` 上設定 `observability.traceQuery.timeoutMs`，以 1 至 300,000 毫秒的整數調整逾時時間。DuckDB 的驅動封裝目前不支援查詢級逾時或取消，因此上述 `504` 保證不適用於 DuckDB。

| 狀態碼 | 含義 |
| - | - |
| `400` | JSON 或游標格式錯誤。 |
| `409` | 游標與查詢不匹配。 |
| `413` | 請求本文超過 256 KiB。 |
| `422` | JSON 格式正確，但請求在結構或語義上無效。回應包含穩定的問題代碼及路徑。發現介面的校驗使用 `TRACE_QUERY_INVALID`。 |
| `501` | 已安裝的 Core 或設定的可觀測性儲存系統不支援請求的操作。除非 Core 提供發現契約且儲存系統同時實現欄位和值發現，否則發現介面傳回 `TRACE_QUERY_DISCOVERY_UNSUPPORTED`。 |
| `503` | 發現介面超出後端記憶體或資源預算，傳回 `TRACE_QUERY_RESOURCE_LIMIT`。 |
| `504` | PostgreSQL 或 ClickHouse 查詢超出設定的資料庫執行逾時時間。發現介面傳回 `TRACE_QUERY_EXECUTION_TIMEOUT`。 |

## 查詢 Span {/* #query-spans */}

使用 `querySpans()`、`mastra api span query` 或 `POST /api/observability/spans/query`，可跨 Trace 傳回已完成 Span 的摘要。請求必須提供針對 Span 開始時間的有效 ISO 時間戳範圍，並支援游標分頁。以下示例找出耗時至少一秒的 Tool 呼叫：

```typescript
const result = await mastraClient.querySpans({
  timeRange: {
    from: '2026-10-01T00:00:00.000Z',
    to: '2026-10-02T00:00:00.000Z',
  },
  where: {
    op: 'and',
    args: [
      { op: 'eq', left: { path: 'spanType' }, right: { literal: 'tool_call' } },
      { op: 'gte', left: { path: 'durationMs' }, right: { literal: 1000 } },
    ],
  },
  orderBy: [{ field: 'startedAt', direction: 'desc' }],
  page: { limit: 100 },
})

// Pass result.page.next as page.after to continue with the same filters and ordering.
console.log(result.spans)
```

每頁預設 100 行，最多 1,000 行。回應格式為 `{ spans, page: { next } }`，不包含總數。排序必須且只能指定 `startedAt`、`endedAt`、`durationMs`、`timeToFirstChunkMs`、`timeToFirstTokenMs`、`model` 或 `provider` 中的一項，並可選擇升序或降序；預設按開始時間降序。缺少的排序值在兩個方向上都排在最後。按模型和提供商排序時區分大小寫。

| 欄位 | 運算符 |
| - | - |
|`traceId`, `spanId`, `parentSpanId`, `threadId` | `eq`, `ne`, `in`, `notIn`, `exists`, `notExists` |
| `organizationId`, `resourceId`, `runId`, `sessionId`, `userId`, `requestId`, `serviceName`, `experimentId`, `environment`, `executionSource` | 同上所列字串運算符 |
| 實體、父實體和根實體的 `Type`、`Id`、`Name`、`VersionId` 欄位，例如 `parentEntityId` | 同上所列字串運算符 |
| `name`, `spanType`, `status` | 同上所列字串運算符；`name` 還支援 `matches` / `notMatches`，用於匹配歸一化的完整單詞和詞組 |
| `model`, `provider`, `outcome`, `stopReason` | 同上所列字串運算符 |
| `startedAt`, `endedAt`, `durationMs`, `timeToFirstChunkMs`, `timeToFirstTokenMs` | 比較、成員關係及是否存在 |
| `error` | `exists`, `notExists` |

使用 `and`、`or` 和 `not` 組合謂詞。成員關係使用 `{ op: 'in', value: { path: 'spanType' }, set: ['agent_run', 'tool_call'] }`。Span 有錯誤時，其狀態為 `error`；否則為 `success`。

每條摘要包含身份、上下文、實體譜系、狀態、時間戳、`durationMs`、模型和提供商，以及輸入、輸出和錯誤的預覽。

過濾 `traceId`、`spanId`、`parentSpanId`、`threadId`、`resourceId`、`requestId`、`serviceName`、`experimentId`、`environment`、`executionSource` 或父級／根實體的 `Type`、`Id`、`Name` 欄位前，請檢查 `getObservabilityCapabilities()` 傳回的 `capabilities.spanQueryContextFields`。如果該能力缺少或為 false，使用這些過濾條件會傳回結構化的 `422` 錯誤。此能力不限制 `runId`、`sessionId`、`userId`、`organizationId` 或實體的 `VersionId` 過濾條件。

按 `model` 或 `provider` 過濾前，請檢查 `capabilities.spanQueryModelFields`。這些過濾條件只讀取 Span 的 `model` 和 `provider` 列。只有 Span 同時具有 `model` 和 `provider` 時，`@mastra/observability` 才會填充這些列；更早版本寫入的 Span 對應列為空。過濾時，空列視為缺少，因此 `eq`、`in` 和 `exists` 不匹配此類 Span，而 `ne`、`notIn` 和 `notExists` 會匹配。結果仍可從 Span 屬性中傳回其 `model` 和 `provider`。Trace 查詢中的 `spans.some` 過濾條件會回退讀取屬性，因此可以匹配此類 Span。舊版適配器收到使用這些過濾條件的請求時傳回 `501`。

按 `outcome` 和 `stopReason` 篩選 Span 或據此分組前，請先檢查 `capabilities.spanQueryOutcomeFields`。結果也會包含 `outcome`、`stopReason` 和 `stopReasonContext`。這些欄位記錄 Span 的結束方式及原因，與 `status` 分開；未記錄時為 `null`。缺少結束結果表示「未記錄」，不表示成功。`stopReasonContext` 不能用於篩選；若儲存系統缺少 `span-query-outcome-fields`，結果也會省略此欄位。對於 Trace，`capabilities.traceQueryOutcomeFields` 會在 `queryTraces()` 和 `aggregateTraces()` 中啟用相同欄位，讀取根 Span 的值。舊版轉接器收到使用這些欄位的請求時會傳回 `501`：

```typescript
const { capabilities } = await mastraClient.getObservabilityCapabilities()

if (capabilities.spanQueryOutcomeFields) {
  const limited = await mastraClient.querySpans({
    timeRange: { from: '2026-10-01T00:00:00.000Z', to: '2026-10-02T00:00:00.000Z' },
    where: { op: 'eq', left: { path: 'outcome' }, right: { literal: 'limit' } },
  })
  console.log(limited.spans.map(span => [span.stopReason, span.stopReasonContext]))
}
```

Trace 範圍和 `spans.some` 的語義詳見[按結束結果過濾](/reference/observability/tracing/advanced-queries#filter-by-outcome)。

對於 `@mastra/duckdb` 開始儲存父實體與根實體的型別、ID 和名稱之前寫入的 Span，DuckDB 會傳回這些欄位的 `null`。針對這些欄位的相等篩選條件不會符合這些 Span。

CLI 在 `data` 中傳回相同回應：從 `data.spans` 讀取結果，並將 `data.page.next` 作為 `page.after` 傳入。Span 查詢只支援鍵集分頁，因此沿游標翻頁時須重複使用相同的時間範圍、謂詞和排序。格式錯誤的游標傳回 `400`；與查詢或範圍不匹配的游標傳回 `409`。

使用 `mastra api trace span <traceId> <spanId>` 或 `getSpan(traceId, spanId)` 取得所選 Span 的完整詳情。

## 聚合 Trace {/* #aggregate-traces */}

使用 `aggregateTraces()` 或 `POST /api/observability/traces/aggregate`，可以計算所選 Trace 的數量與指標。透過 `groupBy` 最多依兩個維度分組，並透過 `interval` 將各組切成時間區間。回應中每組一列；設定時間區間後，每組的每個非空區間各有一列。

### 使用使用者端 SDK 聚合 Trace {/* #aggregate-traces-with-the-client-sdk */}

以下請求比較一周內各 Agent 的呼叫量、錯誤率和延遲：

```typescript
import { MastraClient } from '@mastra/client-js'

const mastraClient = new MastraClient({ baseUrl: 'http://localhost:4111' })

const { capabilities } = await mastraClient.getObservabilityCapabilities()

if (capabilities.traceAggregate) {
  const { rows, truncated } = await mastraClient.aggregateTraces({
    timeRange: {
      from: '2026-08-01T00:00:00.000Z',
      to: '2026-08-08T00:00:00.000Z',
    },
    where: { op: 'eq', left: { path: 'entityType' }, right: { literal: 'agent' } },
    groupBy: ['entityName'],
    measures: ['count', 'errorRate', 'duration.p95'],
    orderBy: { field: 'errorRate', direction: 'desc' },
    limit: 10,
  })
}
```

使用者端會像 `queryTraces()` 一樣重試伺服器錯誤，但不會重試 `422` 校驗錯誤。

### 傳送聚合 HTTP 請求 {/* #send-an-aggregate-http-request */}

將同一請求作為 JSON 請求本文傳送：

```bash
curl --request POST \
  --url http://localhost:4111/api/observability/traces/aggregate \
  --header 'Authorization: Bearer <token>' \
  --header 'Content-Type: application/json' \
  --data '{
    "timeRange": {
      "from": "2026-08-01T00:00:00.000Z",
      "to": "2026-08-08T00:00:00.000Z"
    },
    "where": { "op": "eq", "left": { "path": "entityType" }, "right": { "literal": "agent" } },
    "groupBy": ["entityName"],
    "measures": ["count", "errorRate", "duration.p95"],
    "orderBy": { "field": "errorRate", "direction": "desc" },
    "limit": 10
  }'
```

### 聚合請求欄位 {/* #aggregate-request-fields */}

| 欄位 | 必填 | 說明 |
| - | - | - |
| `timeRange` | 是 | Trace 開始時間範圍，與[選擇 Trace](#select-traces)相同。最長 365 天。 |
| `where` | 否 | Trace 謂詞，與[選擇 Trace](#select-traces)相同。 |
| `measures` | 是 | 一個或多個互不重複的[指標名稱](#measures)。 |
| `groupBy` | 否 | 最多兩個互不重複的[維度](#dimensions)。預設為 `[]`，即把所有選中 Trace 視為一組。設定 `interval` 後，該組的每個非空時間區間各有一行；沒有匹配 Trace 時不傳回任何行。 |
| `interval` | 否 | 時間區間寬度：`'1m'`、`'5m'`、`'15m'`、`'1h'` 或 `'1d'`。參閱[時間區間](#time-buckets)。 |
| `having` | 否 | 根據指標過濾分組的標量謂詞，在分組後執行。參閱[過濾和排序分組](#filter-and-order-groups)。 |
| `orderBy` | 否 | `{ field, direction }`。`field` 可以是請求的指標、`count` 或 `groupBy` 維度；`direction` 為 `asc` 或 `desc`。預設為 `count desc`。 |
| `limit` | 否 | 最多傳回的分組數。預設 100，最大 1,000。 |

未知欄位會被拒絕。聚合結果不支援分頁。若 `truncated` 為 `true`，請縮小選擇範圍或改用其他指標排序。

### 維度 {/* #dimensions */}

維度讀取每個所選 Trace 的目前根 Span：

| 維度 | 說明 |
| - | - |
| `entityType`, `entityName`, `environment`, `status`, `serviceName`, `executionSource` | 根 Span 屬性。 |
| `threadId`, `resourceId`, `userId`, `sessionId`, `organizationId`, `experimentId` | 紀錄在根 Span 上的上下文識別碼。 |
| `name`, `spanType` | 根 Span 的名稱和型別。需要 `traceQueryRootSpanFields` 能力。 |
| `entityId` | 根 Span 的實體 ID。可對缺少 `entityName` 的 Trace（如評分器執行）分組。需要 `traceQueryRootEntityId` 能力。 |
| `outcome`, `stopReason` | 根 Span 的結束方式和原因。根 Span 未紀錄值的 Trace 會歸入值為 `null` 的分組。需要 `traceQueryOutcomeFields` 能力。 |
| `metadata.<key>` | 單個非空的頂層元資料鍵。值會移除前後空白；缺少、空值或非字串值歸為 `null`。 |

除 `executionSource` 外，每個維度也是 Trace 範圍的 `where` 欄位，因此可將其值加入謂詞，深入查看某個分組。`traceId`、`spanId`、`runId` 和 `requestId` 不能用於分組。維度無值的 Trace 會形成一個值為 `null` 的獨立分組。若要在查詢中選擇該分組，請對該維度使用 `notExists`，不要對 `literal: null` 使用 `eq`。

### 指標 {/* #measures */}

| 指標 | 值 |
| - | - |
| `count` | 所選 Trace 的數量。 |
| `countDistinct.<field>` | 某個維度或 `traceId` 中不同非 null 值的數量，例如 `countDistinct.userId`。 |
| `duration.avg`, `duration.min`, `duration.max` | 根 Span 耗時，單位為毫秒。 |
| `duration.p50`, `duration.p90`, `duration.p95`, `duration.p99` | 根 Span 耗時的百分位數，單位為毫秒；具體儲存系統可能傳回近似值。 |
| `timeToFirstChunk.avg`, `timeToFirstChunk.min`, `timeToFirstChunk.max` | 根 Span 的第一個資料區塊耗時，單位為毫秒。需要 `aggregateTimeToFirstMeasures` 能力。 |
| `timeToFirstChunk.p50`, `timeToFirstChunk.p90`, `timeToFirstChunk.p95`, `timeToFirstChunk.p99` | 根 Span 第一個資料區塊耗時的百分位數，單位為毫秒。需要 `aggregateTimeToFirstMeasures` 能力。 |
| `timeToFirstChunk.count` | 紀錄了第一個資料區塊耗時的根 Span 所屬 Trace 數量。需要 `aggregateTimeToFirstMeasures` 能力。 |
| `timeToFirstToken.avg`, `timeToFirstToken.min`, `timeToFirstToken.max` | 根 Span 的第一個 token 耗時，單位為毫秒。需要 `aggregateTimeToFirstMeasures` 能力。 |
| `timeToFirstToken.p50`, `timeToFirstToken.p90`, `timeToFirstToken.p95`, `timeToFirstToken.p99` | 根 Span 第一個 token 耗時的百分位數，單位為毫秒。需要 `aggregateTimeToFirstMeasures` 能力。 |
| `timeToFirstToken.count` | 紀錄了第一個 token 耗時的根 Span 所屬 Trace 數量。需要 `aggregateTimeToFirstMeasures` 能力。 |
| `errorCount` | 根 Span 紀錄了錯誤的 Trace 數量。 |
| `errorRate` | `errorCount` 除以 `count`，範圍為 0 到 1。 |
| `tokens.input.sum`, `tokens.input.avg` | 輸入 token 數。 |
| `tokens.output.sum`, `tokens.output.avg` | 輸出 token 數。 |
| `tokens.total.sum`, `tokens.total.avg` | 輸入與輸出 token 總數。 |
| `tokens.reasoning.sum`, `tokens.reasoning.avg` | 推理輸出 token 數。 |
| `tokens.cached.sum`, `tokens.cached.avg` | 從提供商緩存讀取的輸入 token 數。 |
| `cost.sum`, `cost.avg` | 模型預估成本。 |

不支援對元資料計算數值指標。

#### Token 與成本指標 {/* #token-and-cost-measures */}

Token 與成本指標讀取每個 Trace 紀錄的模型用量指標，因此僅當儲存系統保留所選時間範圍內的用量指標時才可使用。指標與 Trace 的 `traceId` 相同，且紀錄時間不早於 `timeRange.from`，就歸屬於該 Trace。所有這類指標都會計入，包括在 `timeRange.to` 之後紀錄的用量，以及暫停和恢復之前紀錄的用量。重試匯出的指標只計一次。

至少紀錄一項用量指標的 Trace 稱為有用量的 Trace。`tokens.<kind>.sum` 匯總某組中有用量的 Trace 的 token 數；`tokens.<kind>.avg` 用該總數除以有用量的 Trace 數量，而不是 `count`。若該組沒有有用量的 Trace，兩者均為 `null`。

成本取自輸入和輸出 token 總量指標中紀錄的預估費用。`cost.sum` 匯總至少有一項已計價指標的 Trace 成本；`cost.avg` 用總成本除以這類 Trace 的數量。如果一次呼叫只有部分 token 型別成功計價，仍會計入已計價部分的成本；任何其他計價失敗的指標都不計入成本。

請求任意 `cost.*` 指標時，每行還會包含一個 `cost` 物件：

| 欄位 | 說明 |
| - | - |
| `coverage` | 用量已全部計價的 Trace 佔所有有用量 Trace 的比例，範圍為 0 到 1。部分計價的呼叫不算全部計價，因此即使已知成本計入 `cost.sum`，仍會降低覆蓋率。若該組沒有有用量的 Trace，則為 `null`。 |
| `unit` | 已計價指標的成本單位，如 `USD`。若使用多個單位，則為 `'mixed'`；沒有已計價指標時為 `null`。 |

若該組沒有已計價 Trace，或 `unit` 為 `'mixed'`，`cost.sum` 和 `cost.avg` 均為 `null`。覆蓋率低於 1 表示該成本低估了分組的實際支出。`cost` 物件不是指標，不能在 `having` 或 `orderBy` 中引用。

### 第一個資料區塊耗時（TTFC） {/* #time-to-first-chunk-ttfc */}

第一個資料區塊耗時（TTFC）指呼叫方等待流式回應第一個資料區塊的時間。`timeToFirstChunkMs` 從 Span 開始時計至模型回應第一個資料區塊到達時。模型以流式方式回應時，Agent 執行和模型 Span 會紀錄該值。對於 Agent 執行，計時從執行開始，包含首次模型呼叫前的工作，例如輸入處理器和記憶檢索。

`timeToFirstChunk.*` 指標聚合根 Span 的 `timeToFirstChunkMs`，與 [`queryTraces()`](#query-traces) 傳回的值相同。過濾和排序方式詳見[按第一個資料區塊或 token 的耗時過濾和排序](#filter-and-sort-by-time-to-first-chunk-or-token)。

```typescript
const { capabilities } = await mastraClient.getObservabilityCapabilities()

if (capabilities.traceAggregate && capabilities.aggregateTimeToFirstMeasures) {
  const { rows } = await mastraClient.aggregateTraces({
    timeRange: {
      from: '2026-08-01T00:00:00.000Z',
      to: '2026-08-02T00:00:00.000Z',
    },
    where: { op: 'eq', left: { path: 'entityType' }, right: { literal: 'agent' } },
    groupBy: ['entityName'],
    measures: ['timeToFirstChunk.p50', 'timeToFirstChunk.p95', 'timeToFirstChunk.count'],
    orderBy: { field: 'timeToFirstChunk.p95', direction: 'desc' },
  })
}
```

### 第一個 token 耗時（TTFT） {/* #time-to-first-token-ttft */}

第一個 token 耗時（TTFT）是從模型呼叫開始（即提供商請求發起時）到該呼叫流式輸出第一個資料區塊的毫秒數。與 TTFC 不同，它不包含 Mastra 在呼叫模型前所做的工作，例如輸入處理器。

`timeToFirstToken.*` 指標聚合根 Span 的 `timeToFirstTokenMs`。過濾和排序方式詳見[按第一個資料區塊或 token 的耗時過濾和排序](#filter-and-sort-by-time-to-first-chunk-or-token)。對比 TTFC 與 TTFT，可以判斷 Agent 的等待時間有多少來自模型呼叫前的工作。

### 紀錄第一個資料區塊和 token 耗時的 Span 型別 {/* #first-chunk-and-token-span-types */}

以下 Span 型別紀錄 TTFC 和 TTFT：

- `model_inference`：每次提供商呼叫。
- `model_step`：產生過程中的每一步，取該步驟首次流式輸出資料區塊的推斷值。
- `model_generation`：整個產生過程，只取首次流式輸出的推斷值。多步驟產生（如 Tool 循環）只報告首次呼叫。
- `agent_run`：Agent 執行，取其自身循環中首次模型產生的值。TTFC 從執行開始時計時。

Tool 呼叫和 Workflow 執行等其他 Span 不紀錄這兩個值。若 Trace 的根 Span 是 Workflow，則 Trace 範圍內沒有 TTFC 或 TTFT。

TTFT 只在流式輸出該資料區塊的 `model_inference` Span 上測量一次。使用回退模型或重試的步驟，取其首次流式輸出資料區塊的推斷值。失敗的回退嘗試只有在失敗前輸出過資料區塊時才有值。進程內 Agent 在同一個推斷 Span 內重試失敗的模型呼叫，因此其 TTFT 包含失敗嘗試及重試等待時間。持久化 Agent 則為每次嘗試建立一個推斷 Span。

Mastra 會將 TTFT 存於專用欄位，而非已儲存的 `attributes`。請從 Span 的 `timeToFirstTokenMs` 欄位讀取。

### 缺少的第一個資料區塊與 token 耗時值 {/* #missing-first-chunk-and-token-values */}

Span 未流式輸出資料區塊時，該值為 `null`。`0` 並非缺少值，而是表示第一個資料區塊與 Span 開始發生在同一毫秒。

- 在謂詞中，`null` 視為缺少：它匹配 `notExists`，但不匹配有序比較謂詞。
- 在 `orderBy` 中，無論升序還是降序，缺少值都排在最後；`0` 按實際值排序。
- 在聚合中，缺少值的 Span 和 Trace 會被跳過，不會按 0 計算。

過濾、排序和聚合分別需要對應的儲存系統功能。各項操作所需的 `traceQueryTimeToFirstChunk`、`traceQueryTimeToFirstChunkSort`、`traceQueryTimeToFirstToken`、`traceQueryTimeToFirstTokenSort` 和 `aggregateTimeToFirstMeasures` 標誌見[檢查能力](#check-capabilities)。使用舊版儲存系統時，結果會省略不支援的欄位；引用這些欄位的請求會在執行儲存作業前傳回 `501`；[欄位發現](#discover-fields-and-values)也會省略它們。

對於 `timeToFirstChunk.*` 和 `timeToFirstToken.*`，若組內沒有任何 Trace 紀錄值，`avg`、`min`、`max` 和百分位數均為 `null`；`.count` 則為有值的 Trace 數量。百分位數是否為近似值取決於儲存系統。使用這些指標需要 `aggregateTimeToFirstMeasures` 能力。

### 過濾和排序分組 {/* #filter-and-order-groups */}

每組對應一種不同的 `groupBy` 值組合。`having`、`orderBy` 和 `limit` 作用於分組；即使設定了 `interval`，也使用整段時間範圍內的分組指標。伺服器先執行 `having`，再排序剩餘分組並保留前 `limit` 個。如果剩餘分組數超過 `limit`，`truncated` 為 `true`。

`having` 採用標量謂詞格式，以指標名稱作為路徑，例如 `{ op: 'gt', left: { path: 'duration.p95' }, right: { literal: 5000 } }`。它可以引用請求的指標和 `count`，即使未請求 `count` 也可以。支援數字字面值的比較運算符、`in` 和 `notIn`，並可透過 `and`、`or` 和 `not` 組合；不支援存在性、標籤和文本運算符。值為 `null` 的指標不會滿足任何 `having` 比較，因此相應分組會被移除。

以下請求保留第 95 百分位耗時超過五秒的 Workflow：

```typescript
const slowWorkflows = await mastraClient.aggregateTraces({
  timeRange: {
    from: '2026-08-01T00:00:00.000Z',
    to: '2026-08-08T00:00:00.000Z',
  },
  where: { op: 'eq', left: { path: 'entityType' }, right: { literal: 'workflow_run' } },
  groupBy: ['entityName'],
  measures: ['count', 'duration.p95', 'duration.p99'],
  having: { op: 'gt', left: { path: 'duration.p95' }, right: { literal: 5000 } },
  orderBy: { field: 'duration.p95', direction: 'desc' },
})
```

排序是確定性的。若排序值相同，按維度值升序決定先後。無論排序方向，值為 `null` 的指標和維度都排在最後。

### 時間區間 {/* #time-buckets */}

設定 `interval` 後，通過 `having` 和 `limit` 的各組會展開為每個非空時間區間一列。時間區間以 UTC 對齊，因此 `1d` 區間從 UTC 午夜開始；每列的 `bucket` 是該區間起點的 ISO 時間。Trace 歸入根 Span 的 `startedAt` 所在區間。結果先依分組、再依 `bucket` 遞增排列。

不含 Trace 的時間區間會被省略，而非傳回值為零的行。繪製圖表時，應在使用者端補齊空檔。由於分組先按整個時間範圍排序，每個傳回分組都包含其所有非空時間區間的完整序列。

以下請求傳回每個 Agent 每天的 token 用量和成本：

```typescript
const dailyCost = await mastraClient.aggregateTraces({
  timeRange: {
    from: '2026-08-01T00:00:00.000Z',
    to: '2026-08-08T00:00:00.000Z',
  },
  where: { op: 'eq', left: { path: 'entityType' }, right: { literal: 'agent' } },
  groupBy: ['entityName'],
  interval: '1d',
  measures: ['count', 'tokens.total.sum', 'cost.sum', 'cost.avg'],
  orderBy: { field: 'cost.sum', direction: 'desc' },
  limit: 5,
})
```

### 聚合回應 {/* #aggregate-responses */}

```json
{
  "rows": [
    {
      "dimensions": { "entityName": "supportAgent" },
      "bucket": "2026-08-01T00:00:00.000Z",
      "measures": {
        "count": 412,
        "tokens.total.sum": 1830442,
        "cost.sum": 4.21,
        "cost.avg": 0.0103
      },
      "cost": { "coverage": 0.99, "unit": "USD" }
    }
  ],
  "truncated": false

```

`dimensions` 以 `groupBy` 欄位為鍵，僅在 `groupBy` 非空時出現。設定 `interval` 時會出現 `bucket`。`measures` 以請求的指標名稱為鍵。若沒有匹配的 Trace，或 `having` 移除了全部分組，`rows` 為空。

### 聚合限制與錯誤 {/* #aggregate-limits-and-errors */}

| 限制 | 上限 |
| - | - |
| 時間範圍 | 365 天 |
| `groupBy` 維度數 | 2 |
| `limit` | 1,000 個分組 |
| 時間範圍內的區間數 | 1,000 |
| `limit` × 區間數 | 10,000 行 |

[查詢限制](#query-limits)中的謂詞限制同時適用於 `where` 和 `having`；請求本文上限為 256 KiB。如果時間範圍未從時間區間邊界開始，則觸及的區間數會比“時長除以間隔”多一個。區間數過多時，請加大 `interval`；若 `limit` × 區間數超過 10,000，請降低 `limit` 或加大間隔。

PostgreSQL 和 ClickHouse 聚合使用與 Trace 查詢相同的[執行逾時](#keyset-ordering-and-errors)，預設 15 秒。此逾時不適用於 DuckDB。

| 狀態碼 | 含義 |
| - | - |
| `400` | JSON 格式錯誤。 |
| `413` | 請求本文超過 256 KiB。 |
| `422` | 請求無效，傳回 `TRACE_QUERY_INVALID` 及問題詳情。時間範圍超過 365 天會產生 `invalid_request` 問題。其他問題代碼包括 `too_many_buckets`、`too_many_rows`、`field_not_allowed`、`invalid_metadata_key` 和 `operator_not_allowed`。 |
| `501` | 已安裝的 Core 或設定的可觀測性儲存系統不支援聚合或所請求欄位。傳回 `TRACE_AGGREGATE_UNSUPPORTED`。 |
| `504` | PostgreSQL 或 ClickHouse 聚合超出執行逾時時間。傳回 `TRACE_QUERY_EXECUTION_TIMEOUT`，不包含部分結果。 |

## 聚合 Span {/* #aggregate-spans */}

使用 `aggregateSpans()` 或 `POST /api/observability/spans/aggregate`，可以針對各個 Span 而非 Trace 計算指標。Trace 聚合只查看每個 Trace 的根 Span，因此不會統計 Workflow 中巢狀的 Agent 執行。Span 聚合則統計任意層級中所有匹配的 Span。

請求格式與 [`aggregateTraces()`](#aggregate-request-fields) 相同，固定指標、`having`、`orderBy`、`interval` 和共同限制也相同。`where`、維度及 `countDistinct` 欄位遵循下述 Span 約定。不支援 Span 聚合時傳回 `501 SPAN_AGGREGATE_UNSUPPORTED`。

### 使用使用者端 SDK 聚合 Span {/* #aggregate-spans-with-the-client-sdk */}

以下請求按天、按狀態統計 Agent 執行，包括巢狀執行：

```typescript
const { capabilities } = await mastraClient.getObservabilityCapabilities()

if (capabilities.spanAggregate) {
  const { rows } = await mastraClient.aggregateSpans({
    timeRange: {
      from: '2026-08-01T00:00:00.000Z',
      to: '2026-08-08T00:00:00.000Z',
    },
    where: { op: 'eq', left: { path: 'spanType' }, right: { literal: 'agent_run' } },
    groupBy: ['status'],
    interval: '1d',
    measures: ['count', 'duration.p95'],
  })
}
```

要直接使用 HTTP，請將相同請求本文傳送到 `POST /api/observability/spans/aggregate`。

### Span 選擇條件 {/* #span-selection */}

聚合使用與 [`querySpans()`](#query-spans) 相同的 Span 謂詞，但 ClickHouse 的選擇行為有以下差異：

- `timeRange` 限制每個 Span 的 `startedAt`，時間跨度最長 365 天。
- `where` 接受 `querySpans()` 的欄位和運算符，例如 `spanType`、`name`、`status`、`durationMs`、`model`、`provider`、實體及父級／根實體欄位，還有上下文識別碼。與 `querySpans()` 一樣，`model` 和 `provider` 過濾條件只讀取 Span 的列，不讀取屬性。
- 只統計已完成的 Span。若同一 Span 匯出多次，只統計最新副本。

`count` 計算各組或時間區間內選取的 Span 數量。分區依據每個 Span 的 `startedAt`。`duration.*` 指標讀取 Span 本身的耗時；`errorCount` 和 `errorRate` 則依據 Span 本身是否記錄錯誤。

`timeToFirstToken.*` 和 `timeToFirstChunk.*` 讀取 Span 自身的 `timeToFirstTokenMs` 與 `timeToFirstChunkMs`。哪些 Span 會紀錄這些值，詳見[紀錄第一個資料區塊和 token 耗時的 Span 型別](#first-chunk-and-token-span-types)。如需每次呼叫的 TTFT，按 `model_inference` 過濾；如需 Agent 呼叫方感受到的延遲，按 `agent_run` 過濾。不指定 `spanType` 時，一次 Agent 呼叫會計入 Agent 執行、模型產生，以及所有模型步驟和模型推斷。

在 ClickHouse 中，直接使用 `spanType` 的 `eq` 或 `in` 謂詞，或將該謂詞直接放在 `and` 中，可選用更小的分支表。所有選定型別都必須是分支型別：`agent_run`、`workflow_run`、`processor_run`、`scorer_run`、`rag_ingestion`、`tool_call` 或 `mcp_tool_call`。請求的每個欄位也必須在該表中可用。等價的 `or` 謂詞不能觸發此優化。分支路徑的結果可能與 `querySpans()` 不同：

- 升級前由 `@mastra/clickhouse` 1.4、1.5 或 1.6 寫入的 Span 不在分支表中，因此舊時間窗口統計的 Span 數量可能較少。
- ClickHouse 合併同一 Span 的多個匯出副本後，分支表保留最後寫入的副本，而非最後結束的副本。保留版本的狀態和耗時可能不同；即使 Span 識別碼未變，也可能改變過濾後的計數和分組歸屬。

### Span 維度 {/* #span-dimensions */}

| 維度 | 說明 |
| - | - |
| `name`, `spanType`, `status` | Span 自身的名稱、型別和狀態。紀錄錯誤時 `status` 為 `error`，否則為 `success`。 |
| `outcome`, `stopReason` | Span 的結束方式和原因。未紀錄值的 Span 歸入 `null` 分組。需要 `spanQueryOutcomeFields` 能力。 |
| `entityType`, `entityId`, `entityName` | 產生該 Span 的實體。 |
| `parentEntityType`, `parentEntityName`, `rootEntityType`, `rootEntityName` | 呼叫方實體和 Trace 的根實體，例如發起模型呼叫的 Agent。 |
| `environment`, `serviceName`, `executionSource` | 紀錄在 Span 上的部署屬性。 |
| `threadId`, `resourceId`, `userId`, `sessionId`, `organizationId`, `experimentId` | 紀錄在 Span 上的上下文識別碼。 |
| `model`, `provider` | Span 的 `model` 與 `provider` 列所紀錄的模型和提供商，例如 `__AI_SDK_ANTHROPIC_MODEL_SONNET__` 和 `anthropic`。需要 `spanAggregateModelDimensions` 能力。 |

`countDistinct.<field>` 接受這些維度及 `traceId`，因此 `countDistinct.traceId` 統計所選 Span 所屬的不同 Trace 數量。Span 聚合不能按 `metadata.<key>`，也不能按 `traceId`、`spanId` 或 `runId` 等身份欄位分組。

與 `model` 和 `provider` 過濾條件一樣，`model` 和 `provider` 維度只讀取 Span 對應的列，不讀取屬性。現有 Span 不會回填，因此在 `@mastra/observability` 開始填充這些列之前匯出的 Span 會歸入 `null` 分組，也不會被 `countDistinct.model` 統計。

儲存系統透過 `span-aggregate-model-dimensions` 功能聲明支援，伺服器將其報告為 `spanAggregateModelDimensions` 能力。舊版儲存系統在收到按 `model` 或 `provider` 分組、或統計其不同值的請求時，會在執行儲存作業前傳回 `501`。

### Span 的 token 與成本 {/* #span-tokens-and-cost */}

Token 與成本指標使用每個 Span 紀錄的用量指標，透過 `traceId` 和 `spanId` 匹配。[Trace token 規則](#token-and-cost-measures)分別適用於各 Span：從 `timeRange.from` 起紀錄的指標會計入，重試匯出只計一次，平均值以有用量的 Span 數量為除數。

用量不會匯總到父 Span。模型呼叫在 `model_generation` Span 上紀錄用量，因此 `agent_run` Span 自身沒有 token，除非其下的模型呼叫未被匯出。若某個 `model_generation` Span 未匯出，其用量會改記在最近的已匯出祖先 Span 上。要統計每個 Agent 的 token 總量，請選擇 `model_generation` Span 並按呼叫方 Agent 分組：

```typescript
const tokensByAgent = await mastraClient.aggregateSpans({
  timeRange: {
    from: '2026-08-01T00:00:00.000Z',
    to: '2026-08-08T00:00:00.000Z',
  },
  where: { op: 'eq', left: { path: 'spanType' }, right: { literal: 'model_generation' } },
  groupBy: ['parentEntityName'],
  measures: ['tokens.total.sum', 'cost.sum'],
  orderBy: { field: 'cost.sum', direction: 'desc' },
})
```

如果要比較模型，則將相同 Span 按 `model` 分組：

```typescript
const { capabilities } = await mastraClient.getObservabilityCapabilities()

if (capabilities.spanAggregateModelDimensions) {
  const { rows } = await mastraClient.aggregateSpans({
    timeRange: {
      from: '2026-08-01T00:00:00.000Z',
      to: '2026-08-08T00:00:00.000Z',
    },
    where: { op: 'eq', left: { path: 'spanType' }, right: { literal: 'model_generation' } },
    groupBy: ['provider', 'model'],
    measures: ['count', 'tokens.total.sum', 'cost.sum'],
  })
  // rows[0]: { dimensions: { provider: 'anthropic', model: '__AI_SDK_ANTHROPIC_MODEL_SONNET__' }, measures: { ... } }
}
```

### 列出某組對應的 Span {/* #list-the-spans-behind-a-group */}

聚合不會傳回 Span 紀錄。要查看某組，將相同的 `timeRange` 和 `where` 傳給 `querySpans()`，並把非 null 的維度值添加為 `eq` 條件。若維度為 null，則使用 `notExists`，例如 `{ op: 'notExists', path: 'entityName' }`；使用 `literal: null` 的 `eq` 會被拒絕。例如，添加 `{ op: 'eq', left: { path: 'status' }, right: { literal: 'error' } }`，即可列出第一個示例中的失敗 Agent 執行。

## 可信租戶範圍 {/* #trusted-tenant-scope */}

服務多個租戶的宿主在查詢文檔之外提供可信範圍。伺服器讀取保留的 `organizationId` 請求上下文鍵；只有服務端身份驗證可以設定該鍵，並將 `{ organizationId }` 傳給規劃器。可信規劃會攜帶此範圍，並將其作為 AND 條件應用到每次掃描：目前根 Span、關聯 Span、token 與成本指標讀取的用量指標、Span 聚合及兩個發現路由。其他租戶的關聯紀錄即使共享相同的 `traceId`，也不能使 Trace 匹配。

直接呼叫儲存系統的宿主，可以向 `planTraceQuery()`、`planTraceAggregate()`、`planSpanAggregate()`、`planTraceQueryObservedFields()` 和 `planTraceQueryValues()` 傳入更完整的範圍：

```typescript
const plan = planTraceQuery(parseTraceQueryRequest(request), {
  scope: { organizationId: 'org_123', resourceId: 'project_456' },
})
```

`resourceId` 可選，用於在組織內進一步縮小範圍。鍵集和增量游標都綁定該範圍。在一個範圍下建立的游標若用於另一個範圍，會在執行儲存作業前傳回 `409`。若帶範圍的請求發給尚不支援租戶範圍的可觀測性儲存系統或 `@mastra/core`，會傳回 `501`，而不是在無範圍限制下執行。儲存系統透過 `trace-query-tenant-scope` 功能聲明支援。呼叫方不能在謂詞中指定 `projectId`。`organizationId` 謂詞比較紀錄的資料，並與可信範圍取 AND，因此只能縮小租戶自身的 Trace 範圍，不能擴大範圍。沒有可信範圍時，路由維持原有行為，自托管部署可繼續使用自己的租戶模型。

## 發現欄位和值 {/* #discover-fields-and-values */}

使用 Trace 查詢的發現功能構建欄位和值的自動補全，無需掃描 Trace 資料內容，也無需把查詢語法複製到使用者端。設定的可觀測性儲存系統必須支援 `trace-query-discovery`。

CLI 沒有專門的發現命令；請使用下文的 SDK 方法，或 HTTP 端點 `POST /api/observability/traces/query/fields` 和 `POST /api/observability/traces/query/values`。

針對一個謂詞範圍呼叫 `getTraceQueryFields()`：

```typescript
const timeRange = {
  from: '2026-08-01T00:00:00.000Z',
  to: '2026-08-08T00:00:00.000Z',
}

const fields = await mastraClient.getTraceQueryFields({
  timeRange,
  predicateScope: 'trace',
  search: 'region',
  limit: 25,
})
```

回應將標準欄位與觀察到的元資料欄位分開：

```json
{
  "canonicalFields": [],
  "observedFields": [
    {
      "path": "metadata.region",
      "valueKind": "string",
      "operators": ["eq", "ne", "in", "notIn", "exists", "notExists"],
      "valueSuggestions": true,
      "occurrences": 125
    }
  ],
  "observedFieldsTruncated": false
}
```

標準欄位來自用於校驗 Trace 查詢的同一個註冊表，不佔用 `limit`。其順序與註冊表一致。`observedFields` 包含從符合條件的目前根 Span 上找到的頂層字串 `metadata.<key>` 路徑。這些欄位先按 `occurrences` 降序、再按路徑排序。巢狀元資料、包含 `.` 的鍵、空鍵、非字串值和過長路徑均被省略。

`predicateScope` 選擇局部謂詞語法，它不是授權範圍：

| `predicateScope` | 返迴路徑示例 | 查詢用法 |
| - | - | - |
| `trace` | `environment` 或 `metadata.region` | 根級 `where` 謂詞 |
| `spans` | `model` | 用於 `spans.some` 或 `spans.none` 內 |

欄位選擇器可以並行請求 `trace` 和 `spans` 範圍，並標注每個欄位所屬的範圍。傳回的每個路徑都可在相應範圍內直接用於 `queryTraces()`。`metadata` 本身不是欄位。界面可以另行提供手動輸入元資料鍵的選項。

對於 `trace` 範圍，如果伺服器和儲存系統支援聚合，欄位回應還會包含 `aggregate` 物件，用於描述 `aggregateTraces()` 接受的內容：

```json
{
  "aggregate": {
    "dimensions": [{ "path": "entityName", "valueKind": "string" }],
    "measures": [
      {
        "name": "duration.p95",
        "kind": "duration",
        "statistic": "p95",
        "unit": "milliseconds",
        "approximate": true
      }
    ]
  }
}
```

`dimensions` 列出儲存系統支援的標準維度。每個觀察到的 `metadata.<key>` 欄位也都是維度；`countDistinct.<field>` 接受任意維度或 `traceId`。`measures` 列出每個固定指標，以及其 `kind`、`unit` 和是否為 `approximate`。

使用者選中 `valueSuggestions: true` 的欄位後，呼叫 `getTraceQueryValues()`：

```typescript
const abortController = new AbortController()
const suggestions = await mastraClient.getTraceQueryValues(
  {
    timeRange,
    predicateScope: 'trace',
    path: 'metadata.region',
    search: 'west',
    limit: 25,
  },
  { signal: abortController.signal },
)
```

```json
{
  "values": [
    { "value": "eu-west-1", "count": 82 },
    { "value": "us-west-2", "count": 43 }
  ],
  "valuesTruncated": false
}
```

發現介面只傳回字串值。缺少值、空字串，以及超過 4,096 UTF-8 位元組的字串都會被省略。取值先按 `count` 降序、再按值排序。建議值僅供參考：即使發現介面未傳回某個有效字面值，`queryTraces()` 仍接受手動輸入。

以下標準欄位支援值建議：

| 範圍 | 欄位 |
| - | - |
| Trace | `entityName`, `entityType`, `name`, `spanType`, `environment`, `status`, `outcome`, `stopReason`, `tags` |
| Span | `name`, `spanType`, `model`, `provider`, `status`, `outcome`, `stopReason`, `entityType`, `entityName` |

`outcome` 和 `stopReason` 的建議值需要 `traceQueryOutcomeFields` 能力。在 `trace` 範圍內，每個可執行的頂層字串 `metadata.<key>` 欄位也支援值建議。識別碼、時間戳、耗時、第一個資料區塊耗時、第一個 token 耗時、錯誤和版本 ID 則不支援。欄位回應仍包含 `valueSuggestions: false` 的標準欄位。值端點會以 `422 TRACE_QUERY_INVALID` 拒絕這些路徑。

兩個發現請求都要求半開時間範圍。它們採用與 `queryTraces()` 相同的目前紀錄語義：符合條件的已完成根 Span 滿足 `from <= startedAt < to`；關聯值只來自透過 `traceId` 連接到這些根 Span 的目前紀錄。發現介面不接受，也不應用尚在草擬的 `where` 謂詞。

`search` 預設為空字串，會移除前後空白，並按不區分大小寫的字面子字串匹配。`%` 和 `_` 等字元不具有通配符含義。空搜索傳回出現頻率最高的結果。`limit` 預設為 25，最大為 100。兩個端點都會多取一條結果以設定截斷標誌，但不提供游標。當標誌為 `true` 時，請縮小 `search` 範圍；它不表示存在下一頁。無匹配時傳回空陣列，截斷標誌為 `false`。

若發現請求超出執行逾時，路由傳回 `504 TRACE_QUERY_EXECUTION_TIMEOUT`；若後端超出記憶體或資源預算，則傳回 `503 TRACE_QUERY_RESOURCE_LIMIT`。兩種失敗都不傳回部分建議，也不設定截斷標誌。截斷只表示完整排序結果被截取至請求的回應上限。

ClickHouse 發現請求預設逾時為 5 秒，每次查詢的記憶體上限為 256 MiB。可在 `ClickhouseStoreVNext` 上透過 `observability.traceQuery.discovery.timeoutMs` 和 `observability.traceQuery.discovery.memoryLimitBytes` 設定。若未設定發現逾時，則回退使用 `observability.traceQuery.timeoutMs`，但不改變普通 `queryTraces()` 的執行限制。

兩個路由都要求 `observability:read` 權限，並使用設定的可觀測性儲存系統邊界。不要在請求中傳送組織或專案授權欄位。發現的路徑、取值和計數均應視為可觀測性資料。

## 限制 {/* #limitations */}

查詢和聚合 API 只處理已完成的 Trace 與 Span，不處理執行中的紀錄。Trace 查詢不能傳回自定義投影、嵌入的證據或摘要；頁碼分頁結果包含總數。Trace 聚合不能按根 Span 的 `name`、`spanType`、`entityId` 以外的 Span 欄位分組，也不能按 `traceId` 或 `attributes.*` 分組。聚合不能計算元資料的數值指標、對分組分頁或把空時間區間補為零。Span 聚合不能按 `model` 或 `provider` 分組，而且只會把 token 歸到紀錄該用量的 Span。CLI 中，`mastra api trace aggregate` 支援 Trace 聚合，`mastra api span query` 和 `mastra api span aggregate` 分別支援 Span 查詢與聚合。
