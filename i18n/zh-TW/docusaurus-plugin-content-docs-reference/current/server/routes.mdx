# 伺服器路由

呼叫 `server.init()` 時，伺服器配接器會註冊這些路由。若已設定 `prefix` 選項，所有路由都會加上該前綴。

## Agent {/* #agents */}

|方法|路徑|描述 |
| - | - | - |
| `GET` | `/api/agents` | 列出所有 Agent |
| `GET` | `/api/agents/:agentId` | 依 ID 取得 Agent（支援版本查詢參數） |
| `POST` | `/api/agents/:agentId/generate` | 產生 Agent 回應 |
| `POST` | `/api/agents/:agentId/stream` | 以串流傳回 Agent 回應 |
| `POST` | `/api/agents/:agentId/send-message` | 將使用者訊息送到處理中或閒置的對話串 |
| `POST` | `/api/agents/:agentId/queue-message` | 將使用者訊息排入佇列，等對話串下一輪處理 |
| `POST` | `/api/agents/:agentId/queue-signal` | 將具型別的訊號排入佇列，等對話串下一輪處理 |
| `POST` | `/api/agents/:agentId/signals` | 向處理中或閒置的對話串傳送底層訊號 |
| `POST` | `/api/agents/:agentId/threads/subscribe` | 訂閱對話串的串流 |
| `POST` | `/api/agents/:agentId/threads/abort` | 中止對話串，可一併清除待處理的訊號 |
| `POST` | `/api/agents/:agentId/threads/signals/cancel` | 取消對話串中指定的待處理訊號 |
| `POST` | `/api/agents/:agentId/send-tool-approval` | 核准或拒絕 Tool 呼叫，再透過對話串訂閱繼續接收輸出 |
| `POST` | `/api/agents/:agentId/resume-stream` | 以自訂資料繼續已擱置的 Agent 串流 |
| `GET` | `/api/agents/:agentId/tools` | 列出 Agent 的 Tool |
| `POST` | `/api/agents/:agentId/tools/:toolId/execute` | 執行 Agent 的 Tool |

### 取得 Agent 的查詢參數 {/* #get-agent-query-parameters */}

`GET /api/agents/:agentId` 可接受下列選用的查詢參數，用來選擇已儲存的組態版本，以覆寫程式碼中定義的 Agent 組態。

|參數|類型 |預設 |描述 |
| - | - | - | - |
| `status` | `'draft' \| 'published'` | `'published'` | 選擇要使用的已儲存版本。`draft` 傳回最新版本，`published` 傳回目前生效的版本。 |
| `versionId` | `string` | 無 | 指定要使用的版本 ID，優先於 `status`。 |

```bash
# Get agent with active published overrides (default)
GET /api/agents/my-agent

# Get agent with latest draft overrides
GET /api/agents/my-agent?status=draft

# Get agent with a specific version's overrides
GET /api/agents/my-agent?versionId=abc123
```

### Agent 訊息路由 {/* #agent-message-routes */}

使用 `POST /api/agents/:agentId/send-message` 將使用者訊息送到正在執行的 Agent 迴圈，或喚醒閒置的對話串。如果要等這次執行結束，再由 Mastra 開始下一次執行，請使用 `POST /api/agents/:agentId/queue-message`。

若要依相同順序將具型別的訊號排入佇列，請使用 `POST /api/agents/:agentId/queue-signal`，並用 `signal` 欄位取代 `message`。`signal` 欄位的結構與 `POST /api/agents/:agentId/signals` 使用的結構相同。

兩條訊息路由接受相同的請求本文：

```typescript oxfmt:false
{
  message: string | Array<TextPart | FilePart> | {
    contents: string | Array<TextPart | FilePart>;
    attributes?: Record<string, JSONValue>;
    metadata?: Record<string, unknown>;
    providerOptions?: ProviderMetadata;
  };
  runId?: string;
  resourceId?: string;
  threadId?: string;
  ifActive?: {
    behavior?: 'deliver' | 'persist' | 'discard';
    attributes?: Record<string, string | number | boolean>;
  };
  ifIdle?: {
    behavior?: 'wake' | 'persist' | 'discard';
    streamOptions?: Omit<AgentExecutionOptions, 'messages'>;
    attributes?: Record<string, string | number | boolean>;
  };
}
```

省略 `runId` 時，必須提供 `resourceId` 和 `threadId`。`ifIdle` 僅適用於以對話串為目標的請求。

#### 發送訊息 {/* #send-a-message */}

```bash
curl -X POST http://localhost:4111/api/agents/supportAgent/send-message \
  -H 'Content-Type: application/json' \
  -d '{
    "message": {
      "contents": "Show the shorter version.",
      "attributes": { "sentFrom": "web" }
    },
    "resourceId": "user_123",
    "threadId": "thread_456"
  }'
```

#### 將訊息排入佇列 {/* #queue-a-message */}

```bash
curl -X POST http://localhost:4111/api/agents/supportAgent/queue-message \
  -H 'Content-Type: application/json' \
  -d '{
    "message": "Also check whether the tests need updates.",
    "resourceId": "user_123",
    "threadId": "thread_456"
  }'
```

兩條路由都會傳回下列回應：

```typescript oxfmt:false
{
  accepted: true;
  runId: string;
  signal?: CreatedAgentSignal;
}
```

### 中止對話串與取消訊號的路由 {/* #thread-cancellation-routes */}

`POST /api/agents/:agentId/threads/abort` 接受 `{ resourceId?: string, threadId: string, clearPendingSignals?: boolean }`，並傳回 `{ aborted: boolean }`。只有將 `clearPendingSignals` 設為 `true` 才會清除待處理的輸入。接收請求的處理程序會先在本機清除輸入，再中止對話串，必要時也會將清除操作轉送給目前持有對話串的處理程序。若由遠端處理程序持有對話串，`aborted: true` 只表示已送出請求。

`POST /api/agents/:agentId/threads/signals/cancel` 只取消指定的待處理輸入，對話串會繼續執行。JSON 請求本文包含下列欄位：

<PropertiesTable
  content={[
{ name: 'resourceId', type: 'string', isOptional: true, description: '記憶對話串所屬的資源 ID。' },
{ name: 'threadId', type: 'string', description: '含有待處理訊號的對話串 ID。' },
{ name: 'signalIds', type: 'string[]', description: '要取消的訊號 ID，可指定 1 到 1,000 個，每個 ID 都不得為空。' },
]}
/>

回應為 `{ cancelledSignalIds: string[] }`，只列出處理請求的伺服器處理程序已取消的訊號 ID。每個 ID 只會出現一次。未知的 ID，以及已交付執行或移交給其他持有者的訊號 ID，都不會列出。請求本文無效時會傳回 HTTP 400。

兩條路由都需要 `agents:execute` 權限，並依通過驗證的請求內容檢查對話串的歸屬。若已設定細緻授權，呼叫端也須擁有該對話串的 `memory:write` 權限，即使對話串尚未儲存。取消操作涵蓋共用該記憶對話串的所有 Agent。已持久化的訊息、狀態更新、通知紀錄與接收確認都不會復原，由 `continueWithMessages()` 啟動的後續執行也不受影響。

即使本機沒有相符的待處理輸入，伺服器仍會透過共用的 PubSub 後端發布請求中的所有 ID，讓訂閱該對話串的其他處理程序可以移除相符的待處理輸入。通知會以非同步方式盡力傳送，HTTP 回應不會確認遠端是否已取消。中止時的清除操作只會影響接收請求與目前持有對話串的處理程序。SDK 用法請參閱[用戶端取消方法](/reference/client-js/agents#cancelqueuedmessages)。

請一併升級 `@mastra/core` 和 `@mastra/server`，才能取消整個對話串中的指定訊號，或在中止時清除待處理輸入。部署多個處理程序時，請升級所有可能持有該對話串的工作程序。如果 Agent 採用的核心版本不支援這些操作，伺服器會傳回 HTTP 501，並保留待處理的輸入。支援中止對話串的舊版核心仍可處理未設定 `clearPendingSignals: true` 的一般中止請求。

### 透過對話串訂閱處理 Tool 核准 {/* #subscription-tool-approval-routes */}

用戶端已訂閱對話串時，請使用 `POST /api/agents/:agentId/send-tool-approval`。這條路由會繼續執行並傳回 JSON 確認回應。後續的串流資料區塊會透過 `POST /api/agents/:agentId/threads/subscribe` 傳送。

這條路由接受下列請求本文：

```typescript oxfmt:false
{
  resourceId: string;
  threadId: string;
  toolCallId: string;
  approved: boolean;
  requestContext?: Record<string, unknown>;
}
```

這條路由會傳回下列回應：

```typescript oxfmt:false
{
  accepted: true;
  runId: string;
  toolCallId?: string;
}
```

### 執行數量的回應 {/* #run-counts-response */}

`/api/workflows/run-counts` 會傳回每個已註冊 Workflow 處於 `running` 和 [`suspended`](/docs/workflows/suspend-and-resume) 狀態的執行數量。回應物件以 Mastra 組態中的 Workflow 註冊鍵為索引，伺服器可能會快取回應幾秒鐘。

```typescript oxfmt:false
{
  [workflowRegistryKey: string]: {
    running: number;
    suspended: number;
  };
}
```

### 動態 Workflow {/* #dynamic-workflows */}

動態 Workflow 定義（測試版）以 JSON 表示，透過 `workflowDefinitions` 儲存領域持久化，並可直接註冊到執行中的執行個體。請參閱[動態 Workflow](/docs/workflows/dynamic-workflows)。

|方法|路徑|描述 |
| - | - | - |
| `GET` | `/api/stored/workflows` | 列出動態 Workflow 定義，可依 `status` 和 `authorId` 篩選 |
| `GET` | `/api/stored/workflows/:dynamicWorkflowId` | 依 ID 取得動態 Workflow 定義 |
| `POST` | `/api/stored/workflows` | 新增或更新定義（可附帶輔助 `dependencies`），並立即註冊 |
| `DELETE` | `/api/stored/workflows/:dynamicWorkflowId` | 刪除動態 Workflow 定義，並取消註冊對應的 Workflow |

伺服器啟用驗證時，讀取路由需要 `stored-workflows:read` 權限，寫入路由需要 `stored-workflows:write` 權限。動態 Workflow 註冊後，可透過前述一般的 `/api/workflows/:workflowId` 路由執行。

### 執行結果 {/* #run-result */}

`POST /api/workflows/:workflowId/start-async` 會等候 `run.start()` 完成後再傳回執行結果。`status` 可區分成功、失敗、觸發警戒條件、擱置與暫停。`steps` 物件以步驟 ID 為索引，每個步驟都有自己的狀態，有輸出時也會包含 `output`。執行成功時，最上層的 `result` 就是 Workflow 的輸出。

執行結果包含下列欄位。其中，僅適用於特定狀態的欄位只會在對應結果中出現：

```typescript oxfmt:false
{
  status: 'success' | 'failed' | 'tripwire' | 'suspended' | 'paused';
  input: unknown;                      // The inputData the run started with
  state?: unknown;                     // Workflow state
  result?: unknown;                    // Workflow output on success
  error?: unknown;                     // Error on failure
  tripwire?: unknown;                  // Tripwire details
  suspendPayload?: unknown;           // Payload returned on suspension
  suspended?: string[][];              // Suspended step paths
  steps: {
    [stepId: string]: {
      status: string;
      output?: unknown;
      error?: unknown;
      startedAt: number;               // Unix time in milliseconds
      endedAt?: number;
    };
  };
}
```

`GET /api/workflows/:workflowId/runs/:runId` 會傳回執行的中繼資料與狀態。有已持久化的快照時會使用快照，否則取用記憶體中的執行紀錄。這條路由以 `payload` 提供執行輸入，以 `initialState` 提供狀態。`workflowName` 是 Workflow 的 `id`，可能與路徑中的註冊鍵不同。

```typescript oxfmt:false
{
  runId: string;
  workflowName: string;
  resourceId?: string | null;
  createdAt: string;                   // ISO date string
  updatedAt: string;                   // ISO date string
  status: string;                      // Includes active states such as 'running' and 'waiting'
  initialState?: Record<string, unknown>;
  result?: unknown;
  error?: unknown;
  payload?: unknown;                   // The inputData the run started with
  steps?: {
    [stepId: string]: {
      payload?: unknown;               // This step's input
      status: string;
      output?: unknown;
      error?: unknown;                 // Present when the step failed
      startedAt: number;
      endedAt?: number;
    } | {
      payload?: unknown;
      status: string;
      output?: unknown;
      error?: unknown;
      startedAt: number;
      endedAt?: number;
    }[];                              // forEach iteration results
  };
  activeStepsPath?: Record<string, number[]>;
  serializedStepGraph?: unknown[];
  suspendedPaths?: Record<string, number[]>;
  resumeLabels?: Record<string, unknown>;
  waitingPaths?: Record<string, number[]>;
}
```

查詢已持久化的執行紀錄時，可用 `fields` 查詢參數縮減回應。請從 `result`、`error`、`payload`、`steps`、`activeStepsPath` 和 `serializedStepGraph` 選取所需欄位，並以逗號分隔。指定其他名稱會收到 HTTP 400。中繼資料欄位和 `status` 仍會傳回，`initialState` 有內容時也會傳回。

```bash
curl 'http://localhost:4111/api/workflows/my-workflow/runs/1faf6f91-b9ac-4db0-9fb3-326687ba1972?fields=result'
```

`steps` 中的項目可能是單一步驟的結果，也可能是 `forEach` 步驟的逐次迭代結果陣列。讀取 `status` 或 `output` 前，請先確認該項目是否為陣列。

指定 `withNestedWorkflows=false` 後，`steps` 會略過巢狀 Workflow 的執行明細，並保留目前 Workflow 自己的步驟項目。

改用記憶體中的紀錄時，回應會標示 `isFromInMemory: true`，並傳回執行的中繼資料、`status` 和空的 `steps`，省略 `result`、`payload` 與 `error`。`createdAt` 和 `updatedAt` 都會填入目前時間。這類回應不會套用欄位篩選，也不會展開巢狀 Workflow。

## 知識 {/* #knowledge */}

這些路由預設不會註冊。請將 `@mastra/server/server-adapter` 的 `KNOWLEDGE_ROUTES` 加入 `server.apiRoutes`，並在 `Mastra` 的 `knowledge` 下註冊執行個體。這些路由需要 `@mastra/core` 1.81.0 以上版本，其中兩個連結路由需要 1.82.0 以上版本。如果已設定 RBAC Provider，每個路由都需要 `knowledge:read` 權限。未設定時會略過這項檢查。設定方式請參閱 [Studio 知識](/docs/studio/knowledge)。

| 方法 | 路徑 | 說明 |
| - | - | - |
| `GET` | `/api/knowledge` | 列出已註冊的知識執行個體。若已設定 FGA，則依權限篩選 |
| `GET` | `/api/knowledge/:knowledgeKey/tree` | 列出根範圍或 `parentId` 下的子範圍 |
| `GET` | `/api/knowledge/:knowledgeKey/pages/:pageId` | 取得頁面及其上層頁面、筆記、釘選資訊與參照的頁面 |

### 知識存取權限與錯誤 {/* #knowledge-access-and-errors */}

若未設定 `server.auth` 或 `studio.auth`，路由會以執行個體擁有者的身分讀取並傳回所有內容。啟用驗證後，路由只會讀取請求情境中 `MASTRA_KNOWLEDGE_PRINCIPALS_KEY` 指定範圍內可讀取的內容。請將這個鍵的值設為範圍陣列或 `'all'`。

| 狀態碼 | 傳回條件 |
| - | - |
| `403` | 已設定驗證但未設定 `MASTRA_KNOWLEDGE_PRINCIPALS_KEY`。`GET /api/knowledge` 不會讀取此鍵，因此不會因此傳回 `403` |
| `404` | 執行個體不存在或 FGA Provider 拒絕該執行個體的 `knowledge:read` 權限，或頁面不存在或呼叫端無權讀取。若呼叫端無權讀取頁面，連結路由會傳回零筆計數或空的連結清單 |
| `500` | `MASTRA_KNOWLEDGE_PRINCIPALS_KEY` 的值不是陣列或 `'all'`，或其中某個範圍與任何已宣告的範圍類型都不相符 |
| `501` | `@mastra/core` 的版本低於路由需求，或儲存層缺少連結索引（限連結路由） |

設定 FGA Provider 後，系統會以 `knowledge` 為資源類型，依各執行個體的註冊鍵檢查 `knowledge:read` 權限。`GET /api/knowledge` 只會列出呼叫端有權讀取的執行個體。啟用 `requireForProtectedRoutes` 時，`GET /api/knowledge` 會遭到拒絕，因為這個路由和其他清單路由一樣缺少 FGA 中繼資料。未設定 RBAC Provider 時，會略過 `knowledge:read` 檢查。

NestJS 介接器目前尚未支援這些路由。

### 知識事件 {/* #knowledge-events */}

每筆已提交且涉及呼叫端有權讀取內容的寫入，`GET /api/knowledge/:knowledgeKey/events` 都會傳送一個事件，格式如下。

```typescript oxfmt:false
{
  kind: 'scope' | 'page' | 'note' | 'pin';
  op: string;       // such as 'create', 'update', 'delete' or 'merge'
  pageId?: string;  // left out when the caller can't read the page, including a deleted one
  scopeId?: string; // left out when the caller can't read the scope
  at: string;       // ISO timestamp
}
```

如果寫入未涉及呼叫端可讀取的內容，伺服器就不會傳送事件。事件只提供 ID，請透過其他路由取得變更內容。若事件缺少 `pageId`，請重新整理 `scopeId` 指定的範圍。

伺服器每 25 秒傳送一則維持連線的註解，並在五分鐘後關閉串流。請在串流關閉後重新連線。新串流會重新讀取呼叫端的範圍，因此權限一旦撤銷，就不會再傳送對應的更新。中斷期間的寫入不會重送，請在重新連線後重新整理畫面上的內容。

### 刪除實驗 {/* #delete-an-experiment */}

兩個刪除路由都會刪除實驗及其結果紀錄。若儲存層支援可觀測性與 Trace 刪除，Mastra 會先刪除實驗產生的 Trace，連同其中的 Span 及與這些 Trace 關聯的訊號，再刪除實驗。

若知道實驗所屬的資料集，請使用指定資料集的路由。

```bash
curl -X DELETE http://localhost:4111/api/datasets/dataset-id/experiments/experiment-id
```

此路由接受選用的 `organizationId` 和 `projectId` 查詢參數。若資料集不在指定租用戶範圍內、實驗不存在，或實驗不屬於該資料集，就會傳回 `404`。

若沒有資料集參照，請使用頂層路由。舉例來說，刪除資料集時會清除實驗的 `datasetId`，使實驗失去與資料集的關聯。

```bash
curl -X DELETE http://localhost:4111/api/experiments/experiment-id
```

頂層路由接受選用的 `organizationId` 和 `projectId` 查詢參數。只要提供其中一項，刪除就會限制在指定的租用戶範圍內。範圍不符時會傳回 `{ "success": true }`，並保留實驗。未提供租用戶參數且找不到實驗時，會傳回 `404`。

刪除成功會傳回 `{ "success": true }`。租用戶範圍不符時，頂層路由也會傳回相同回應，並保留所有資料。若已安裝的 `@mastra/core` 未透過 `experiment-deletion` 功能旗標宣告支援，兩個路由都會傳回 `501`，尚未支援此功能的舊版本亦同。若儲存層缺少可觀測性或 Trace 刪除支援，Mastra 會記錄警告、保留 Trace，並刪除實驗及其結果紀錄。若 Trace 因其他原因刪除失敗，路由會傳回 `500`，並保留實驗及其結果紀錄。Trace 每批刪除 1,000 筆，因此部分 Trace 可能已刪除。請重新送出請求以完成刪除。

### 清除資料集項目 {/* #purge-a-dataset-item */}

`DELETE /api/datasets/:datasetId/items/:itemId/purge` 會從所有歷史版本、刪除標記及相關的實驗結果中，永久清除該項目已儲存的內容。這項操作不會建立新的資料集版本，且無法復原。完整的清除行為請參閱 [`dataset.purgeItem()`](/reference/datasets/purgeItem)。

```bash
curl -X DELETE http://localhost:4111/api/datasets/dataset-id/items/item-id/purge
```

這個路由接受選用的查詢參數 `organizationId` 和 `projectId`。如果資料集不在指定的租用戶範圍內，或資料項目在該資料集中沒有歷史紀錄，便傳回 `404`。已安裝的 `@mastra/core` 須透過 `dataset-item-purge` 功能旗標表明支援這項操作，否則會傳回 `501`。如果 MongoDB 儲存不支援交易，路由會在變更任何資料前傳回 `500`。徹底清除成功後會傳回 `{ "success": true }`。

### 由呼叫端主導的實驗路由 {/* #caller-driven-experiment-routes */}

如果實驗迴圈由自己的協調工具（例如 Temporal Workflow）控制，並由 Mastra 保存正式紀錄，請使用這些路由。執行實驗項目、提交結果和結束實驗都可以安全地重試。建立實驗的請求必須包含呼叫端提供的 `id`，才能安全地重試。未提供時，每次重試都會建立新的實驗。執行項目或提交結果時，會以 `(experimentId, itemId, attempt)` 為鍵更新或新增結果。若實驗已完成，結束操作會傳回已儲存的紀錄。

#### 建立實驗的請求主體 {/* #create-experiment-request-body */}

向 `/api/datasets/:datasetId/experiments` 送出含有 `start: false` 的 POST 請求，即可建立實驗而不啟動它。如果要讓 Mastra 透過執行項目的路由執行各項，請一併提供 `targetType` 和 `targetId`。如果只透過結果路由匯入結果，請省略這兩個欄位。

```typescript oxfmt:false
{
  start?: boolean;              // false creates the experiment without running it. Defaults to true.
  id?: string;                  // Caller-supplied experiment id (e.g. a workflow run id) for idempotent creates
  targetType?: 'agent' | 'workflow' | 'scorer'; // Provide with targetId, or omit both
  targetId?: string;
  scorerIds?: string[];         // Run-level scorer ids, resolved server-side. Requires a target when start is false.
  name?: string;
  description?: string;
  metadata?: Record<string, unknown>;
  version?: number;             // Pin to a specific dataset version (defaults to latest)
  provenance?: {
    source?: string;
    sourceId?: string;
    sourceVersion?: string;
    metadata?: Record<string, unknown>;
  };
  grouping?: {                  // Stable grouping dimensions for comparisons and repeated trials
    experimentSetId?: string;
    comparisonId?: string;
    variantId?: string;
    trialIndex?: number;
  };
}
```

當 `start` 為 `false` 時，會傳回 `{ experimentId, status, totalItems, datasetVersion }`。

#### 執行實驗項目的請求主體 {/* #run-experiment-item-request-body */}

`POST /api/datasets/:datasetId/experiments/:experimentId/items/:itemId/run` 對單一實驗項目執行實驗目標，再執行解析出的評分器，最後更新或新增結果。建立實驗時必須指定目標。

```typescript oxfmt:false
{
  attempt?: number;             // Zero-based repetition index. Defaults to 0.
  requestContext?: Record<string, unknown>; // Merged with the item's own request context (item wins)
}
```

傳回 `{ result, scores }`，內含已儲存的結果紀錄和該項目的評分。

#### 提交實驗結果的請求主體 {/* #submit-experiment-result-request-body */}

```typescript oxfmt:false
{
  itemId: string;               // Dataset item this result belongs to
  attempt?: number;             // Zero-based repetition index. Defaults to 0.
  input?: unknown;              // Defaults to the dataset item input
  output?: unknown;             // Output produced by the external runner
  groundTruth?: unknown;        // Defaults to the dataset item groundTruth
  error?: {                     // Failure info when the item run failed
    message: string;
    stack?: string;
    code?: string;
  } | null;
  startedAt?: string;           // ISO date
  completedAt?: string;         // ISO date
  traceId?: string;
  scores?: Array<{              // Externally computed scores, persisted keyed by runId = experimentId
    scorerId: string;
    scorerName?: string;
    score: number;
    reason?: string;
    metadata?: Record<string, unknown>;
  }>;
}
```

傳回已儲存的實驗結果紀錄。

#### 完成實驗 {/* #finalize-experiment */}

`POST /api/datasets/:datasetId/experiments/:experimentId/finalize` 不需要請求主體。伺服器根據已儲存的結果紀錄，按項目彙整數量，將實驗標示為 `completed`，並傳回更新後的實驗紀錄。`succeededCount` 計入至少有一次嘗試未發生錯誤的項目，`failedCount` 計入每次嘗試都發生錯誤的項目，`skippedCount` 計入從未提交結果的項目。

#### 呼叫端主導實驗的錯誤回應 {/* #caller-driven-experiment-error-responses */}

|狀態 |觸發條件 |
| - | - |
|`400` | 對已指定目標的實驗提交結果（`EXPERIMENT_HAS_TARGET`）、要求執行未指定目標的實驗項目（`EXPERIMENT_HAS_NO_TARGET`）、未同時提供 `targetType` 和 `targetId`（`EXPERIMENT_INVALID_TARGET`），或實驗鎖定的資料集版本沒有任何項目（`EXPERIMENT_NO_ITEMS`） |
| `404` | 找不到資料集、實驗、資料集項目或目標（`EXPERIMENT_TARGET_NOT_FOUND`） |
| `409` | 呼叫端提供的實驗 `id` 已用於其他資料集或目標（`EXPERIMENT_ID_CONFLICT`），或在實驗結束後才收到呼叫（`EXPERIMENT_ALREADY_FINALIZED`） |

### 評分器清單回應 {/* #list-scorers-response */}

回應是鍵值對照表，彙整透過 [`Mastra` 類別](/reference/core/mastra-class)的 `scorers` 選項註冊的評分器，以及指派給 Agent 和 Workflow 的評分器。指派給 Agent 的評分器和透過選項註冊的評分器都以評分器 ID 為鍵。指派給 Workflow 的評分器目前以名稱為鍵。呼叫 `/api/scores/scorers/:scorerId` 時請使用回應中的鍵，依評分器 ID 查詢已儲存的分數時請使用 `scorer.config.id`。

```typescript oxfmt:false
{
  [scorerId: string]: {
    scorer: {
      config: {
        id: string;
        name?: string;
        description: string;
        type?: unknown;
        judge?: unknown;
      };
    };
    sampling?: object;
    agentIds: string[];
    agentNames: string[];
    workflowIds: string[];
    isRegistered: boolean;             // True when the scorer is in the Mastra `scorers` option
    source: 'code' | 'stored' | 'fs';
  };
}
```

API 契約僅涵蓋 `scorer.config`。`scorer` 物件另有 `steps` 等實作欄位，可能隨版本而變動。

`GET /api/scores/scorers/:scorerId` 會傳回結構相同的單筆資料。遇到未知的 ID 時，會傳回 `null`，狀態碼為 200，而非 404。

### 分數清單的查詢參數 {/* #score-list-query-parameters */}

```typescript oxfmt:false
{
  page?: number;        // Page number (0-indexed)
  perPage?: number;     // Items per page (default: 10)
  entityId?: string;    // `/api/scores/scorer/:scorerId` only
  entityType?: string;  // `/api/scores/scorer/:scorerId` only
}
```

呼叫 `/api/scores/entity/:entityType/:entityId` 時，請將 `entityType` 設為 `AGENT` 或 `WORKFLOW`，並將對應 Agent 或 Workflow 的註冊鍵設為 `entityId`。伺服器會先將註冊鍵解析為該實體本身的 `id`，再查詢儲存層。其他 `entityType` 值會原樣傳給儲存層。

### 分數清單回應 {/* #score-list-response */}

```typescript oxfmt:false
{
  pagination: {
    total: number;
    page: number;
    perPage: number;
    hasMore: boolean;
  };
  scores: ScoreRowData[];
}
```

每筆紀錄都採用[分數持久化](/docs/evals/overview#score-persistence)寫入時的結構。常用欄位包括 `id`、`scorerId`、`runId`、`entityId`、`score`、`output`、`scorer`、`entity` 和 `source`（`LIVE` 或 `TEST`），選用欄位 `entityType`、`input`、`reason`、`traceId`、`spanId`、`resourceId` 和 `threadId`，以及時間戳記 `createdAt` 和 `updatedAt`。紀錄也包含評分器各中間步驟的結果與提示詞。若未設定 `scores` 儲存區，清單路由會傳回一頁空結果，而不會回報錯誤。

### 儲存分數的請求主體 {/* #save-score-request-body */}

```typescript oxfmt:false
{
  score: Omit<ScoreRowData, 'id' | 'createdAt' | 'updatedAt'> & { id?: string };
}
```

儲存介面卡決定如何處理傳入的 `id`。有些介面卡會依這個值更新或新增紀錄，有些每次都會產生新 ID，因此在後一種情況下重試提交可能產生重複紀錄。回應為 `{ score: ScoreRowData }`，內含已儲存的紀錄。儲存分數需要設定儲存層，否則路由會傳回 500。

|`GET` | `/api/mcp/v0/servers` | 列出 MCP 伺服器 |
| `GET` | `/api/mcp/v0/servers/:id` | 取得伺服器詳細資訊 |
| `GET` | `/api/mcp/:serverId/tools` | 列出伺服器提供的 Tool |
| `GET` | `/api/mcp/:serverId/tools/:toolId` | 取得 Tool 的詳細資訊 |
| `POST` | `/api/mcp/:serverId/tools/:toolId/execute` | 執行 Tool |
| `GET` | `/api/mcp/:serverId/resources` | 列出伺服器資源 |
| `POST` | `/api/mcp/:serverId/resources/read` | 讀取資源 |
| `GET` | `/api/mcp/:serverId/tasks` | 列出伺服器最近的 MCP 工作（實驗性功能） |
| `POST` | `/api/mcp/:serverId/tasks/find` | 依工作 ID 尋找 MCP 工作（實驗性功能） |
| `POST` | `/api/mcp/:serverId/tasks/:taskKey/cancel` | 取消 MCP 工作（實驗性功能） |
| `POST` | `/api/mcp/:serverId/tasks/:taskKey/input` | 回應 MCP 工作的輸入請求（實驗性功能） |
| `ALL` | `/api/mcp/:serverId/mcp` | MCP HTTP 傳輸 |
| `ALL` | `/api/mcp/:serverId/sse` | 舊版 MCP SSE 傳輸 |
| `POST` | `/api/mcp/:serverId/messages` | 舊版 MCP SSE 訊息 |

所有 MCP 路由都宣告 `requiresAuth: true`。只有在設定 `server.auth` 後，才會要求驗證身分。使用 RBAC Provider 時，列出或尋找工作需要 `mcp:read` 權限。取消工作或回應工作的輸入請求需要 `mcp:write` 權限，因為這些操作會影響其他用戶端啟動的工作。路徑使用預設的 `/api` 前綴。舊版 SSE 路由對 MCP v2 伺服器會傳回 `404`。

### 分頁 {/* #pagination */}

  page?: number;   // Page number (0-indexed)

### 篩選 {/* #filtering */}

查詢 Workflow 執行紀錄時，可使用以下參數進行篩選：

```typescript oxfmt:false
{
  fromDate?: string;  // ISO date string
  toDate?: string;    // ISO date string
  status?: string;    // Run status filter
  resourceId?: string; // Filter by resource
}
```

## 錯誤回應 {/* #error-responses */}

所有路由都會傳回以下格式的錯誤：

```typescript oxfmt:false
{
  error: string;      // Error message
  details?: unknown;  // Additional details
}
```

常見狀態碼：

|狀態碼|含義|
| - | - |
| 400 | 無效的請求：參數無效 |
| 401 | 未授權：缺少身分驗證資訊，或驗證資訊無效 |
| 403 | 禁止存取：權限不足 |
| 404 | 找不到資源：資源不存在 |
| 500 | 伺服器內部錯誤 |
