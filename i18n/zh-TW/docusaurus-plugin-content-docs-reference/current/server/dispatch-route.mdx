# dispatchRoute()

`dispatchRoute()` 函式以呼叫者的身分在行程內執行伺服器路由。它要求請求情境已通過 Mastra 伺服器身分驗證，接著執行伺服器轉接器處理該路由的 HTTP 請求時會執行的檢查：身分驗證 Provider 的 `authorize`、`authorizeUser` 和 `rules`、schema 驗證、RBAC 權限檢查，以及細緻授權 (FGA)。如果對應的 HTTP 請求會遭到拒絕，它也不會允許這次呼叫。

你可以用它在內建路由之上建立另一種傳輸方式，串流路由也適用。若要從 Tool 呼叫 JSON 路由，[`invokeRoute()`](/reference/server/invoke-route) 提供更精簡的 API。

## 使用範例 {/* #usage-example */}

```typescript title="src/server/run-tool.ts"
import type { Mastra } from '@mastra/core/mastra'
import type { RequestContext } from '@mastra/core/request-context'
import { SERVER_ROUTES, dispatchRoute } from '@mastra/server/server-adapter'

const executeTool = SERVER_ROUTES.find(
  route => route.method === 'POST' && route.path === '/tools/:toolId/execute',
)!

export async function runWeatherTool(
  mastra: Mastra,
  requestContext: RequestContext,
  request: Request,
) {
  const outcome = await dispatchRoute(
    executeTool,
    { pathParams: { toolId: 'weather' }, body: { data: { city: 'Paris' } } },
    { mastra, requestContext, abortSignal: request.signal, request },
  )
  if (!outcome.ok) throw new Error(`Tool route failed with status ${outcome.status}`)
  return outcome.result
}
```

## 行為 {/* #behavior */}

* **不會重新進行身分驗證。** 設定了伺服器或 Studio 身分驗證時，請求情境必須已包含 Mastra 伺服器身分驗證解析出的使用者。否則，除非路由路徑是公開的，`dispatchRoute()` 會回傳 `401`。
* **授權掛鉤會收到 HTTP 路徑。** `authorize()`、`authorizeUser()` 和 `rules` 會收到路由的方法及實際提供服務的路徑：轉接器前綴加上填入路徑參數後的路由路徑。
* **套用提供服務的轉接器的路徑與檢查。** 每個轉接器都會將自身綁定至它建立的請求情境。綁定資訊不在情境的項目中，因此 Agent 和 Tool 程式碼無法讀取。使用該請求情境分派路由時，會採用該轉接器的前綴和覆寫設定，即使另一個轉接器也在相同前綴下提供同一個 Mastra 執行個體。請求以外的呼叫會使用為該執行個體提供服務的唯一轉接器，或使用 `context.routePrefix` 指定的轉接器。如果無法判定轉接器，或沒有轉接器提供 `routePrefix` 下的路由，沒有使用者的呼叫者會收到 `401`，其他呼叫者則會遇到例外。它不會自行從多個轉接器中選擇一個。
* **路徑參數依 URL 規則檢查。** 參數缺少、為空、不是字串，或值為 `.` 或 `..` 時，會回傳 `400`。可選的 `:param?` 可以省略。
* **路徑參數優先。** 請求主體或查詢參數中與路徑參數同名的欄位會被覆寫，因此授權檢查與處理常式都會針對路徑指定的資源執行。
* **`protected` 模式不會讓其他路徑變成公開路徑。** 設定了身分驗證後，除非路由路徑被宣告為公開路徑，否則仍須有使用者，即使該路徑不符合你的 `protected` 模式。
* **轉接器的覆寫設定同樣適用。** 提供服務的 `MastraServer` 子類別對 `checkRoutePermission()` 的覆寫也會在分派路由時執行。
* **`authorizeUser()` 會收到替代請求。** 該請求使用分派路由的路徑與方法，帶有 `context.request` 的請求標頭，但沒有請求主體。
* **伺服器情境不能來自輸入。** `request`、`routePrefix`、`registeredTools` 和 `taskStore` 只能透過 `context` 傳給處理常式，不能透過同名的請求主體或查詢欄位傳入。

## 自訂轉接器 {/* #custom-adapters */}

繼承 `MastraServer` 的轉接器會告知 `dispatchRoute()` 它在哪個路徑提供路由。未繼承 `MastraServer` 的轉接器必須自行註冊，並將傳回的控制代碼綁定至它建立的每個請求情境：

```typescript
import { bindDispatchAdapter, registerDispatchAdapter } from '@mastra/server/server-adapter'

const handle = registerDispatchAdapter(mastra, { prefix: '/api' })

// For each request:
bindDispatchAdapter(requestContext, handle)
```

未繼承 `MastraServer` 的轉接器在完成請求身分驗證和參數驗證後，可以呼叫 `authorizeRoute()`，執行與內建轉接器相同的路由權限及 FGA 檢查。允許呼叫時，它會傳回 `null`；拒絕呼叫時，則傳回可送給呼叫者的 `403` 錯誤。`checkRouteRBAC()` 只執行權限檢查。

```typescript
import { authorizeRoute } from '@mastra/server/server-adapter'

const denied = await authorizeRoute(mastra, route, params, requestContext)
if (denied)
  return Response.json({ error: denied.error, message: denied.message }, { status: denied.status })
```
