# DurableAgent

:::beta

API 穩定前，即使沒有提升主要版本號，也可能出現破壞性變更。

:::

`DurableAgent` 為現有的 [`Agent`](/reference/agents/agent) 加入持久執行與可恢復的串流。它執行 Agent 迴圈，讓用戶端中斷並重新連接後仍不會漏掉事件，並透過 [PubSub](/docs/server/pubsub) 串流傳送這些事件。若執行工作需要超過單次請求的存續時間，或在連線中斷後繼續，請使用它。

可以使用 [`createDurableAgent`](#createdurableagentoptions) 工廠方法建立，或使用 [`createEventedAgent`](#createeventedagentoptions) 在內建 Workflow 引擎上啟動後無須等待結果的執行。若需要由 Inngest 驅動執行，請使用 `@mastra/inngest` 提供的 [`createInngestAgent`](/reference/agents/inngest-agent)。

## 使用範例 {/* #usage-example */}

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Agent } from '@mastra/core/agent'
import { createDurableAgent } from '@mastra/core/agent/durable'

const agent = new Agent({
  id: 'my-agent',
  name: 'My Agent',
  instructions: 'You are a helpful assistant',
  model: '__GATEWAY_OPENAI_MODEL__',
})

const durableAgent = createDurableAgent({ agent })

export const mastra = new Mastra({
  agents: { myAgent: durableAgent },
})
```

以串流方式產生回應並讀取結果。不再需要執行工作時，`cleanup` 函式會取消 PubSub 訂閱：

```typescript
const { output, runId, cleanup } = await durableAgent.stream('Hello!')

const text = await output.text

cleanup()
```

### 一般 Agent 的串流設定 {/* #plain-agent-stream-configuration */}

一般 `Agent` 的 `durable` 選項只控制串流是否可恢復，不會包裝 Agent，也不會啟用檢查點。若要持久執行，請明確使用 `createDurableAgent({ agent })`，並將 `maxSteps`、`shouldPersistSnapshot` 等執行選項傳給該工廠方法。

## `createDurableAgent(options)` {/* #createdurableagentoptions */}

為 `Agent` 加入持久執行與可恢復的串流。這是建立 `DurableAgent` 的建議方式。

```typescript
import { createDurableAgent } from '@mastra/core/agent/durable'

const durableAgent = createDurableAgent({ agent })
```

返回：`DurableAgent`

## `createEventedAgent(options)` {/* #createeventedagentoptions */}

在內建事件驅動 Workflow 引擎上，為 `Agent` 加入啟動後無須等待結果的持久執行能力。它和 `createDurableAgent` 一樣會回傳可供串流讀取的結果，但啟動執行工作時不等待完成：Mastra 執行個體上的 PubSub 事件會獨立於呼叫端驅動執行。若要使用事件驅動執行，須將 Agent 註冊至已設定儲存空間的 `Mastra` 執行個體；否則 Agent 會退回預設的程序內引擎並記錄警告。不支援覆寫 `id` 或 `name`。

```typescript
import { createEventedAgent } from '@mastra/core/agent/durable'

const eventedAgent = createEventedAgent({ agent })
```

回傳：`EventedAgent`（`DurableAgent` 的子類別）

## 方法 {/* #methods */}

### 執行 {/* #execution */}

#### `stream(messages, options?)` {/* #streammessages-options */}

以持久執行方式串流產生回應。立即回傳結果，其 `output` 會隨執行進度持續產生事件。

```typescript
const { output, runId, cleanup } = await durableAgent.stream('Hello!', {
  onChunk: chunk => console.log(chunk),
  onFinish: result => console.log('done', result),
})

const text = await output.text
cleanup()
```

返回：[`Promise<DurableAgentStreamResult>`](#durableagentstreamresult)

#### `resume(runId, resumeData, options?)` {/* #resumerunid-resumedata-options */}

恢復暫停的執行工作，例如等待 Tool 核准後的工作。傳入原串流的 `runId` 與工作所等待的資料。若該工作沒有註冊表項目，會擲出錯誤。若其他執行仍持有該工作，`resume()` 最多等待 5 秒，之後擲出 `DURABLE_AGENT_EXECUTION_CONFLICT`。請參閱[執行工作所有權](/docs/harness/durable-agents#run-ownership)。

```typescript
const { output, cleanup } = await durableAgent.resume(runId, {
  approved: true,
})

await output.text
cleanup()
```

返回：[`Promise<DurableAgentStreamResult>`](#durableagentstreamresult)

#### `observe(runId, options?)` {/* #observerunid-options */}

重新連接現有執行工作。網路中斷後可使用此方法。若採用一般支援的重新連接流程，請省略 `offset`：先重播所有可用的快取事件，再接收即時事件。

無論是在同一程序內觀察即時執行，或從另一程序觀察持久執行，執行觀察的 Agent 之有效 `id` 都必須與啟動該工作的 Agent 相同。有效 ID 指 DurableAgent 的 `id`（包括覆寫後的 ID），而非被包裝 Agent 的原始 ID。有效 ID 相同的不同 DurableAgent 執行個體可觀察同一執行工作。

若即時或持久執行工作記錄了不同的 owner Agent ID，`observe()` 會擲出 `DURABLE_AGENT_OBSERVE_AGENT_MISMATCH`。沒有 owner 中繼資料的舊版即時項目維持原有行為。

對於設定了 `structuredOutput` 的執行工作，另一程序中的觀察者會根據已儲存的 schema 與重播的文字重建 `output.object`。

```typescript
const { output } = await durableAgent.observe(runId, {
  onChunk: chunk => console.log(chunk),
})

await output.text
```

`offset` 是從零開始且包含該位置的 PubSub 事件索引。它計算的是發布至該執行工作主題的所有已快取事件（包括生命週期事件），而非資料區塊數量。從執行日誌讀取的資料區塊會在 `chunk.index` 中帶有所屬事件的索引；`stream()`、`observe()` 及 HTTP `/stream`、`/observe` 端點皆如此。若要在斷線後繼續接收，可傳入最後一個帶有索引的資料區塊的 `index + 1`；若尚未收到任何資料區塊，則省略 `offset`。生命週期事件也占用索引，卻不產生資料區塊，因此索引可能不連續，不能以資料區塊數量作為 offset。

有些資料區塊沒有 `index`。用戶端自行建立 `object` 資料區塊，而非從日誌讀取。`abort` 資料區塊與同一執行日誌項目的 `finish` 一起送出，但只有 `finish` 帶有索引，因此用戶端若在兩者之間重新連接，會再次收到 `abort`。

使用獨立結構化模型的執行工作會將 `object-result` 發布到執行日誌，因此該資料區塊帶有 `index`，可以像其他資料區塊一樣重播。持有 schema 的 core `observe()` 呼叫端也可從重播的文字重建結構化輸出，但只有重播了產生該結果的文字，才會取得 `object-result`。HTTP `/observe` 只重播日誌，不會重建該結果。若要在重新連接後重建結果，請不要傳入 `offset` 進行觀察，並略過已處理的 `index` 所對應的資料區塊。重播過程也會重新建立先前收到的 `object` 資料區塊；它們沒有 `index` 可供略過。每個 `object` 資料區塊都是當時物件的快照，因此應保留最新的一個。索引來自重播快取，所以快取寫入失敗的資料區塊，或停用快取時的任何資料區塊，都沒有 `index`，也無法透過 offset 從該處恢復。省略 `offset` 會重播傳輸層自身保留的內容（例如 Redis stream），可能重複收到已處理的資料區塊。下文說明超過結尾的 offset 及不支援數字 offset 的傳輸方式。

`index` 是新增欄位，而 `offset` 的意義不變，因此已傳入日誌位置或從 `0` 開始重播的程式碼無須修改。若程式碼傳入的是已接收資料區塊數量，則應改為最後一個資料區塊的 `index + 1`。

以下範例會在串流傳送期間記錄恢復用 offset，並在重新連接後傳給 `observe()`：

```typescript
let offset: number | undefined
const { output } = await durableAgent.stream(messages, { runId })
for await (const chunk of output.fullStream) {
  if (chunk.index === undefined) continue
  offset = chunk.index + 1
}

// After a dropped connection:
const { output: resumed } = await durableAgent.observe(runId, { offset })
```

非零 offset 可能略過較早的事件。彙整值只根據該觀察者實際收到的資料區塊建立。若 offset 略過先前的文字增量，`output.text` 就只包含部分文字，結構化輸出也可能不完整，或無法通過驗證或解析。

當 PubSub 傳輸支援數字 offset 時，觀察者只會在已發布事件的索引達到要求的 offset 後收到帶編號的事件。若 offset 超過已保留的最大索引，既不會重播任何事件，也會略過索引較小的即時事件。

沒有 `index` 的事件（例如快取寫入失敗的事件）不受 offset 影響，抵達時就會交給觀察者。

若觀察者已連接，而保留的日誌過期或被清除，編號從 `0` 重新開始，該觀察者會與新日誌重新同步，並收到其中的事件，包括索引低於所要求 offset 的事件。偵測採盡力而為的方式。若當時無法讀取快取，或新日誌在第一個事件抵達前已編號超過觀察者的位置，觀察者可能無法辨識這次重新開始，反而略過這些事件。若觀察者在重新開始後帶著舊日誌的 offset 重新連接，它無法區分新舊日誌，會略過新日誌中低於該 offset 的事件；因此應省略 `offset`，以重播新日誌。

對於不支援數字 offset 的傳輸（例如停用快取後的 `RedisStreamsPubSub`），`observe()` 只要傳入 offset，包括 `0`，就會從新的即時事件開始接收，而不會重播保留的事件。core API 與 HTTP `/observe` 都是如此。若要重播保留的事件，請省略 `offset`。（一般 `Agent` 的 HTTP `/observe` 則會重播保留的事件，因此可能重複收到已處理的事件。）

依索引重播僅限於設定的快取中仍可使用的事件。若停用快取、`shouldCache` 排除了執行工作主題，或保留的事件已清除，快取就沒有可重播的內容。此時省略 `offset`，只會重播傳輸層自身保留的事件（若有）。

快取寫入失敗只會使該事件無法從快取讀取。它沒有 `index`；若快取能一步完成編號與附加，前後寫入的事件仍可重播。記憶體快取與 Valkey 快取一律如此。`RedisServerCache` 在 Redis 指令碼可用時也能一步完成；若用戶端沒有 `eval`，或 Redis Cluster 以 `CROSSSLOT` 拒絕指令碼，就會改為兩步。保留預設 `listPushIndexed()` 的自訂快取也採兩步。兩步寫入可能留下索引缺口，導致依 offset 重播時略過後續事件；因此遇到這種日誌應不傳 `offset` 重播，並略過已處理的索引。快取重播無法找回從未儲存的事件；但若傳輸層（例如 `RedisStreamsPubSub`）保留了該事件，仍可在不帶 `index` 的情況下送達。

使用跨程序 PubSub（例如 Redis Streams）的事件驅動 Agent（`createEventedAgent()`），若其步驟在啟動執行工作的程序中執行，可以使用預設的記憶體 server cache，由該程序為事件編號。若步驟在另一程序執行，例如以 `workers: true` 啟動的專用 worker，請在 `Mastra` 執行個體上使用 `RedisServerCache` 等共用快取。另一程序無法共用記憶體計數器，因此其事件不會編號，offset 也無法略過它們；發生這種情況時，Mastra 會在 worker 中記錄警告。若觀察者經由另一程序（例如另一台伺服器副本）重新連接，也應使用共用快取，因為它無法從啟動程序的記憶體快取重播事件。

預設情況下，`observe()` 會無限期等待事件。若執行工作所在的程序意外停止，工作不再產生事件，也不會送出完成事件，因此觀察用的串流會一直等待。可傳入 `idleTimeoutMs`，讓串流在限定的靜默時間後結束。逾時前，`observe()` 可呼叫選用的 `isAlive` 檢查。工作仍在進行時（例如 Tool 呼叫耗時較長，或正在等待人工輸入），應回傳 `true`。回傳 `false` 會讓串流以錯誤結束；省略 `isAlive` 時也如此。`isAlive` 偶發擲錯會視為「仍在執行」，因此短暫的檢查失敗不會結束仍在運作的串流。

```typescript
const { output } = await durableAgent.observe(runId, {
  idleTimeoutMs: 30_000,
  isAlive: () => runHeartbeat.isFresh(runId),
})
```

因閒置逾時而結束執行工作，會進行與執行出錯時相同的清理（請參閱下方警告），因此快取狀態會釋放，而非保留。這兩個選項都需要主動設定。省略它們可維持先前無限期等待的行為。

返回：`Promise<DurableAgentStreamResult>`

:::warning

`observe()` 回傳的 `cleanup()` 會刪除此執行工作的註冊表項目與快取事件。只有在不再需要此執行工作時才呼叫它。若工作仍處於暫停狀態，且打算稍後恢復，請勿呼叫 `cleanup()`；應讓自動清理計時器在工作結束或出錯後處理。暫停事件不會觸發自動清理。

:::

#### `prepare(messages, options?)` {/* #preparemessages-options */}

const { runId, messageId, workflowInput, threadId, resourceId } = await durableAgent.prepare(

    memory: { threadId: 'thread-1', resourceId: 'user-1' },
  },

### 取消執行工作 {/* #cancellation */}

#### `abortRunStream(runId)` {/* #abortrunstreamrunid */}

在任何共用該 Agent 的 [PubSub](/docs/server/pubsub) 的程序中，都可依 ID 停止執行工作。只須提供 `stream()` 或 `prepare()` 回傳的 `runId`，因此後續請求也能停止並非由它啟動的工作。停止後的結果與在串流結果上呼叫 `abort()` 相同：串流送出 `abort` 資料區塊、觸發 `onAbort`，`observe()` 的讀取端也會看到串流結束。

```typescript
const { runId } = await durableAgent.stream('Summarize the document')

// later, from a different request handler
durableAgent.abortRunStream(runId)
```

在多程序部署中，若要透過 PubSub 發布中止請求，必須使用共用後端，例如 [`RedisStreamsPubSub`](/reference/pubsub/redis-streams)。預設的 `EventEmitterPubSub` 只能觸及同一程序內的執行工作。若工作正在等待 Tool 核准，此方法只會在目前程序取消它；其他共用儲存空間的程序仍可核准該呼叫。若要在所有伺服器上取消等待中的工作，請呼叫伺服器端的 `POST /agents/:agentId/runs/:runId/abort` 路由。它會將取消狀態記錄至儲存空間，讓之後的核准或恢復以 `409 Conflict`（`AGENT_RESUME_ABORTED_RUN`）拒絕。

`InngestAgent` 未實作此方法。若要取消 Inngest 執行工作，請使用其 `stream()` 回傳的 `abort()`。

透過 `abortRunStream()` 或 `abortThreadStream()` 停止持久執行工作，需要 `@mastra/core@1.62.0` 或更新版本。較早版本只記錄中止請求，不會停止執行。

回傳：`boolean`。若目前程序在本機中止了執行工作，或能看到工作正在執行，則為 `true`。無論回傳值如何，都會發布中止請求。

#### `abortThreadStream({ threadId, resourceId?, expectedRunId? })` {/* #abortthreadstream-threadid-resourceid-expectedrunid- */}

使用與 `abortRunStream()` 相同的中止請求，取消 memory thread 中執行中的工作。執行工作會從目前程序的 thread runtime 解析，因此必須由此程序啟動，或由此程序透過 `subscribeToThread()` 觀察。伺服器端的 `POST /agents/:agentId/threads/abort` 路由使用此方法。

若請求只能停止指定工作，請傳入 `expectedRunId`。若處理請求前另一項佇列工作變為執行中，方法會回傳 `false`，不會中止接替的工作。省略 `expectedRunId` 則會中止處理請求時正在執行的工作。

```typescript
const aborted = durableAgent.abortThreadStream({
  resourceId: 'user-1',
  threadId: 'thread-1',
  expectedRunId: runId,
})
```

回傳：`boolean`。若目前程序沒有記錄該 thread 的執行中工作，或執行中的工作與 `expectedRunId` 不符，則為 `false`；兩種情況都不會送出中止請求。

### 恢復執行工作 {/* #recovery */}

:::warning

恢復會從最後一次持久儲存的快照重新驅動執行工作。Mastra 將子 Agent 委派視為單一產生的 `agent-<name>` Tool 步驟，不會另外為其中的 LLM 或 Tool 呼叫建立檢查點。若恢復重播了該步驟，整個子 Agent 執行工作可能再次執行，包括已完成的 Tool 副作用。應確保子 Agent 使用的 Tool 具備冪等性，或對其外部副作用去重。操作建議請參閱[當機恢復](/docs/harness/durable-agents#crash-recovery)。

:::

#### `listActiveRuns(options?)` {/* #listactiverunsoptions */}

列出此 Agent 中持久快照狀態為 `running` 的執行工作，也就是 Workflow 引擎上次儲存狀態時 Agent 迴圈仍在執行的工作。在正常運作的程序中，它們會轉為 `suspended` 或終止狀態；當機或重新啟動後，它們會停留在 `running`，卻沒有執行驅動，`recoverActiveRuns()` 可重新驅動這些工作。不包含相同儲存空間中其他 DurableAgent 啟動的工作。

只有 `recovery.durableAgents` 為 `'auto'`，或自訂的 `shouldPersistSnapshot` 包含 `running` 時，才會寫入 `running` 快照。否則此方法不會回傳任何執行工作。請參閱[快照持久儲存](/docs/harness/durable-agents#snapshot-persistence)。

```typescript
const { runs, total } = await durableAgent.listActiveRuns({ resourceId: 'user-1' })

for (const run of runs) {
  await durableAgent.recoverActiveRuns({ runId: run.runId })
}
```

此方法會讀取 Agent 所註冊的 Mastra 執行個體中的 Workflow 快照儲存空間。若 Agent 未註冊至 Mastra 執行個體，會擲出錯誤。請使用持久儲存空間：預設的記憶體儲存會在導致執行工作失去驅動的重新啟動過程中遺失這些記錄。

只回傳狀態為 `running` 的執行工作。暫停的工作會保留快照，但不會列出；已完成的工作不會保留。可用 `resourceId` 將清單限縮至單一使用者。

#### `recoverActiveRuns(options?)` {/* #recoveractiverunsoptions */}

尋找此 Agent 中停留在 `running` 狀態的執行工作，並從最後一個持久快照重新驅動。接受與 `listActiveRuns()` 相同的篩選條件與分頁選項，另可傳入 `runId`。回傳每項工作的處理結果。

最多同時等待五項執行工作的恢復，結果依發現順序回傳。每次嘗試只有一個 30 秒的等待預算，涵蓋 `recover()` 設定及整個恢復後 Workflow 的完成過程。預算用盡時，另一項工作可以使用該等待名額。逾時會回傳 `status: 'skipped'` 與 `reason: 'recovery-timeout'`，並將 `retryAt` 設為 30 秒後；它不會取消設定或執行，不會釋放有效的所有權宣告，也不計為成功或失敗。原嘗試仍在背景繼續，最終結果不會改變已回傳的結果。並行上限限制的是等待數量，而非仍在執行的工作數量。

[`mastra.recoverAllDurableAgents()`](/reference/core/mastra-class#recoveralldurableagents) 會自動安排逾時後的複查。直接呼叫 `recoverActiveRuns()` 時，呼叫端必須自行安排在 `retryAt` 之後再次呼叫。原本的批次復原嘗試尚未結束時，複查會透過另一個 `recovery-timeout` 和未來的 `retryAt` 延後，而不會再次呼叫 `recover()`。原嘗試結束後，復原流程會先檢查已持久化的快照及擁有權，再決定是否重試。已完成或已暫停的執行不會重新啟動。

該預算只適用於 `recoverActiveRuns()` 中每次執行工作的恢復嘗試，不適用於尋找工作、直接呼叫 `recover()` 或覆寫後的自訂恢復方法。開始關閉時，恢復流程會停止派送新工作。即使等待逾時，Mastra 仍會追蹤原嘗試，納入共用的關閉排空流程。

```typescript
const result = await durableAgent.recoverActiveRuns()
// {
//   recovered: [
//     { runId: 'run-1', status: 'success' },
//     { runId: 'run-2', status: 'skipped', reason: 'run-active', retryAt: 1760123456789 },
//   ],
//   succeeded: 1,
//   failed: 0,
// }
```

傳入 `runId` 可恢復單一已知的執行工作：

```typescript
await durableAgent.recoverActiveRuns({ runId: 'run-abc-123' })
```

若其他執行仍在驅動某項工作，`recoverActiveRuns()` 會回傳 `status: 'skipped'` 與對應的 `reason`，並讓原執行繼續控制該工作。若要再次檢查，須另外呼叫。若工作由另一程序持有，`retryAt` 表示其所有權宣告在未續期時失效的時間。若持有它的程序已當機，可在該時間之後呼叫 `recoverActiveRuns({ runId })` 恢復工作。[`mastra.recoverAllDurableAgents()`](/reference/core/mastra-class#recoveralldurableagents) 會自行安排這些重新檢查。

| `reason` | 含義 |
| - | - |
| `run-active` | 其他執行工作（可能在另一程序）持有該工作。會設定 `retryAt`。 |
| `run-active-locally` | 目前程序正在執行該工作。 |
| `already-in-progress` | 目前程序已在恢復該工作。 |
| `recovery-timeout` | 等待已逾時，或先前的批次恢復嘗試仍在進行。設定 `retryAt`；重新檢查時不會重複啟動仍在進行的嘗試。 |

#### `recover(runId, options?)` {/* #recoverrunid-options */}

依 ID 恢復單一執行工作，回傳與 `stream()` 結構相同、可串流讀取的結果。需要即時觀察恢復串流時使用。

```typescript

  onChunk: chunk => console.log(chunk),
  onError: ({ error }) => console.error(error),
})

await output.text
cleanup()
```

恢復會從已持久儲存的 `durable-agentic-loop` 檢查點重新開始。只有巢狀執行記錄並不足夠。啟動工作前，須在 `Mastra` 上啟用 `recovery: { durableAgents: 'auto' }`，或提供包含 `'running'` 的 `shouldPersistSnapshot` 策略。即使已啟用持久儲存，在第一個執行中檢查點儲存之前，仍無法恢復。當機後才啟用持久儲存，也無法重建缺少的檢查點。

檢查點之後的模型與 Tool 呼叫可能再次執行。請確保 Tool 的副作用具備冪等性；恢復不保證恰好執行一次。

檢查點不可用或執行工作並未失去驅動時，`recover()` 會擲出以下錯誤：

| 錯誤 ID | 擲出條件 |
| - | - |
| `DURABLE_AGENT_RECOVER_CHECKPOINT_NOT_AVAILABLE` | 迴圈記錄仍為 `pending`，且沒有 Workflow 輸入。沒有可用來重新啟動的檢查點；不會啟動恢復執行，已取得的恢復所有權宣告也會釋放。 |
| `DURABLE_AGENT_RUN_ACTIVE` | 其他執行工作持有該工作，且未設定 `force`。 |
| `DURABLE_AGENT_RECOVER_RUN_ACTIVE_LOCALLY` | 目前程序正在執行該工作；`force` 也無法覆寫。 |
| `DURABLE_AGENT_RECOVER_ALREADY_IN_PROGRESS` | 目前程序已在恢復該工作。 |
| `DURABLE_AGENT_RECOVER_RUN_SUSPENDED` | 執行工作已暫停；請使用 `resume()` 繼續。 |
| `DURABLE_AGENT_RECOVER_RUN_NOT_ACTIVE` | 快照無法用於重新啟動，且執行工作並非暫停狀態。 |

`resume()`、`observe()` 與 `recover()` 接受相同的生命週期回呼（`onChunk`、`onStepFinish`、`onFinish`、`onError`、`onAbort`、`onSuspended`）。`observe()` 也接受用來控制重播起點的 `offset`。
