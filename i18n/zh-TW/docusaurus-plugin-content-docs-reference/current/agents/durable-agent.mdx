# 耐久劑

:::測試版

在 API 穩定之前，可能會在沒有重大版本更新的情況下發生重大變更。

:::

`DurableAgent`包裝現有的[`Agent`](/reference/agents/agent) with durable execution and resumable streams. It runs the agentic loop so that a client can disconnect and reconnect without missing events, and it streams those events over [PubSub](/docs/server/pubsub)。當運行必須比單一請求更持久或在連線中斷時繼續存在時，請使用它。

創建一個與[`createDurableAgent`](#createdurableagentoptions) factory, or use [`createEventedAgent`](#createeventedagentoptions) for fire-and-forget execution on the built-in workflow engine. For Inngest-powered execution, use [`createInngestAgent`](/reference/agents/inngest-agent) from `@mastra/inngest`.

## 使用範例 {/* #usage-example */}

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Agent } from '@mastra/core/agent'
import { createDurableAgent } from '@mastra/core/agent/durable'

const agent = new Agent({
  id: 'my-agent',
  name: 'My Agent',
  instructions: 'You are a helpful assistant',
  model: '__GATEWAY_OPENAI_MODEL__',
})

const durableAgent = createDurableAgent({ agent })

export const mastra = new Mastra({
  agents: { myAgent: durableAgent },
})
```

串流回應並讀取結果。這`cleanup` function unsubscribes from PubSub when you are done with the run:

```typescript
const { output, runId, cleanup } = await durableAgent.stream('Hello!')

const text = await output.text

cleanup()
```

### 普通Agent流配置 {/* #plain-agent-stream-configuration */}

這`durable` option on a plain `Agent` controls resumable streams only. It never wraps the agent or enables checkpoints. Use `createDurableAgent({ agent })` explicitly for durable execution, and pass execution options such as `maxSteps` and `shouldPersistSnapshot` to that factory.

## `createEventedAgent(options)` {/* #createeventedagentoptions */}

包裹一個`Agent` with fire-and-forget durable execution on the built-in evented workflow engine. Like `createDurableAgent`, it returns a result you stream from, but the run is started without being awaited: events on the Mastra instance's PubSub drive execution independently of the caller. Register the agent on a `Mastra` instance with storage to get evented execution; without one, the agent falls back to the default in-process engine and logs a warning. It doesn't accept `id` or `name` overrides.

```typescript
import { createEventedAgent } from '@mastra/core/agent/durable'

const eventedAgent = createEventedAgent({ agent })
```

返回：`EventedAgent` (a subclass of `DurableAgent`)

## 方法 {/* #methods */}

### 執行 {/* #execution */}

#### `stream(messages, options?)` {/* #streammessages-options */}

使用持久執行串流響應。立即傳回結果，其結果`output` produces events as the run progresses.

```typescript
const { output, runId, cleanup } = await durableAgent.stream('Hello!', {
  onChunk: chunk => console.log(chunk),
  onFinish: result => console.log('done', result),
})

const text = await output.text
cleanup()
```

返回：[`Promise<DurableAgentStreamResult>`](#durableagentstreamresult)

#### `resume(runId, resumeData, options?)` {/* #resumerunid-resumedata-options */}

恢復暫停的運行，例如在Tool批准後。透過`runId` from the original stream and the data the run was waiting on. Throws if no registry entry exists for the run. If another execution holds the run, `resume()` waits up to 5 seconds for it to finish, then throws `DURABLE_AGENT_EXECUTION_CONFLICT`. See [run ownership](/docs/harness/durable-agents#run-ownership).

```typescript
const { output, cleanup } = await durableAgent.resume(runId, {
  approved: true,
})

await output.text
cleanup()
```

返回：[`Promise<DurableAgentStreamResult>`](#durableagentstreamresult)

#### `observe(runId, options?)` {/* #observerunid-options */}

重新連接到現有運行。網路斷開後使用此功能。對於支援的一般重新連接流程，省略`offset` to replay all available cached events before receiving live events.

觀察劑必須具有相同的有效`id` as the agent that started the run, both for live observations in the same process and for persisted observations from another process. The effective ID is the DurableAgent's `id`, including any ID override, rather than the wrapped agent's original ID. Different DurableAgent instances with the same effective ID can observe the same run.

如果即時運行或持續運行標識了不同的業主Agent ID，`observe()` throws `DURABLE_AGENT_OBSERVE_AGENT_MISMATCH`. Legacy live entries without owner metadata retain their existing behavior.

對於運行配置為`structuredOutput`, an observer in another process reconstructs `output.object` from the persisted schema and replayed text.

```typescript
const { output } = await durableAgent.observe(runId, {
  onChunk: chunk => console.log(chunk),
})

await output.text
```

這`offset` option is an inclusive, zero-based PubSub event index. It counts every cached event published to the run topic, including lifecycle events, rather than counting chunks. A chunk read from the run log carries the index of its event as `chunk.index`, on `stream()`, `observe()`, and the HTTP `/stream` and `/observe` endpoints. To resume after a dropped connection, pass `index + 1` of the last chunk that has an index, or omit `offset` if nothing arrived. Lifecycle events take an index but produce no chunk, so indexes have gaps and a chunk count isn't a valid offset.

有些塊沒有`index`. The client builds `object` chunks itself rather than reading them from the log. An `abort` chunk is sent beside the `finish` of the same run-log entry, and only the `finish` carries the index, so a client that reconnects between the two gets the `abort` again.

使用結構化模型的運行發布了其`object-result` to the run log, so that chunk carries an `index` and replays like any other. A core `observe()` caller holding the schema can also rebuild structured output from replayed text, but gets `object-result` only when it replays the text that produced it. HTTP `/observe` replays the log and doesn't rebuild it. To rebuild it after a reconnect, observe without an `offset` and skip chunks whose `index` you already processed. That replay also rebuilds `object` chunks you already received, and they have no `index` to skip by. Each `object` chunk is a snapshot of the object so far, so keep the latest one. Indexes come from the replay cache, so a chunk whose cache write failed, or any chunk when caching is off, has no `index`, so no offset can resume at it. Omitting `offset` replays whatever the transport itself retains, such as a Redis stream, and can repeat chunks you already received. The paragraphs below cover offsets past the end and transports without numeric offsets.

`index`是可加的並且`offset` keeps its meaning, so code that already passes a log position, or replays from `0`, needs no change. Code that passed a count of chunks received should switch to the last `index + 1`.

以下範例記錄串流時的復原偏移量並將其傳遞給`observe()` after a reconnect:

```typescript
let offset: number | undefined
const { output } = await durableAgent.stream(messages, { runId })
for await (const chunk of output.fullStream) {
  if (chunk.index === undefined) continue
  offset = chunk.index + 1
}

// After a dropped connection:
const { output: resumed } = await durableAgent.observe(runId, { offset })
```

非零偏移量可以跳過較早的事件。聚合值僅根據傳遞給該觀察者的區塊來建構。如果偏移跳過較早的文字增量，`output.text` is partial and structured output may be incomplete or fail validation or parsing.

當 PubSub 傳輸支援數位偏移量時，只有當發布的索引達到請求的偏移量時，觀察者才會收到編號事件。超出最高保留索引的偏移不會重播任何內容，並且也會跳過索引較低的即時事件。

沒有一個事件`index`, such as one whose cache write failed, is delivered as it arrives whatever the offset.

如果保留的日誌過期或被清除並且編號重新開始於`0` while an observer is attached, that observer resyncs to the new log and receives its events, including ones below the requested offset. Detection is best effort. If the cache can't be read at that moment, or the new log has numbered past the observer's position before its first event arrives, the observer can miss the restart and skip those events instead. An observer that reconnects after the restart with an offset from the old log can't tell the logs apart and skips the new log's events below that offset, so omit `offset` to replay the new log.

在沒有數位偏移支援的傳輸上，例如`RedisStreamsPubSub` with caching off, `observe()` with any offset, including `0`, starts with new live events and doesn't replay retained events. This is the same in core and over HTTP `/observe`. Omit `offset` to replay them. (HTTP `/observe` on a plain `Agent` replays the retained events instead, which can repeat events already received.)

索引重播僅限於配置的快取中仍然可用的事件。當快取被停用時，快取沒有任何可重播的內容，`shouldCache` excludes the run topic, or retained events have been cleared. Omitting `offset` then replays only what the transport itself retains, if anything.

失敗的快取寫入只會遺失快取中的該事件。它沒有`index`, and the events written before and after it still replay when the cache numbers and appends an event in one step. The in-memory and Valkey caches always do. `RedisServerCache` does while Redis scripting works, and switches to two steps when the client has no `eval` or Redis Cluster rejects the script with `CROSSSLOT`. A custom cache that keeps the default `listPushIndexed()` also takes two steps. A two-step cache can leave a gap that makes offset replay skip later events, so replay such a log without an `offset` and skip indexes already processed. Cache replay can't recover an event the cache never stored. A transport that retains it, such as `RedisStreamsPubSub`, can still deliver it without an `index`.

事件Agent（`createEventedAgent()`) on a cross-process PubSub, such as Redis Streams, can use the default in-memory server cache when its steps run in the process that started the run. That process numbers the events. Use a shared cache such as `RedisServerCache` on the `Mastra` instance when steps run in another process, such as a dedicated worker started with `workers: true`. That process can't share the in-memory counter, so its events aren't numbered and an offset can't skip them. Mastra logs a warning in the worker when this happens. Also use a shared cache when an observer reconnects through another process, such as a different server replica, because it can't replay from the starting process's in-memory cache.

預設情況下`observe()` waits indefinitely for events. If the process running the run stops unexpectedly, the run stops producing events but never emits a completion event, so the observed stream would wait forever. Pass `idleTimeoutMs` to end the stream after a bounded period of silence. Before timing out, `observe()` can consult an optional `isAlive` check. Return `true` while work continues, such as during a long-running tool call or a pause for human input. A `false` result ends the stream with an error, as does omitting `isAlive`. A transient throw from `isAlive` is treated as "still alive", so a momentary check failure never ends a live stream.

```typescript
const { output } = await durableAgent.observe(runId, {
  idleTimeoutMs: 30_000,
  isAlive: () => runHeartbeat.isFresh(runId),
})
```

結束空閒逾時運行與發生錯誤的運行執行相同的清理操作（請參閱下面的警告），因此其快取狀態將被釋放而不是保留。這兩個選項都是可選的。對於先前的無限期等待行為，請忽略它們。

返回：`Promise<DurableAgentStreamResult>`

：：：警告

這`cleanup()` returned by `observe()` destroys the run's registry entries and cached events. Only call it when you are done with the run. If the run is suspended and you intend to resume later, don't call `cleanup()`. Let the auto-cleanup timer handle it after the run finishes or errors. Auto-cleanup doesn't fire on suspended events.

### 消除 {/* #cancellation */}

#### `abortRunStream(runId)` {/* #abortrunstreamrunid */}

停止任何共享Agent程式的 ID 運行[PubSub](/docs/server/pubsub). Only the `runId` from `stream()` or `prepare()` is needed, so a later request can stop a run it didn't start. The run ends the same way as `abort()` on the stream result: the stream emits an `abort` chunk, `onAbort` fires, and `observe()` consumers see the stream end.

```typescript
const { runId } = await durableAgent.stream('Summarize the document')

// later, from a different request handler
durableAgent.abortRunStream(runId)
```

透過 PubSub 發布中​​止請求需要多進程部署中的共用後端，例如[`RedisStreamsPubSub`](/reference/pubsub/redis-streams). The default `EventEmitterPubSub` only reaches runs in the same process. A run parked on a tool approval is cancelled only in this process: another process sharing the storage can still approve it. To cancel a parked run on every server, call the server's `POST /agents/:agentId/runs/:runId/abort` route, which records the cancellation in storage so a later approval or resume is refused with `409 Conflict` (`AGENT_RESUME_ABORTED_RUN`).

`InngestAgent` 沒有實作這個方法。使用以下命令取消 Ingest 運行`abort()` returned by its `stream()`.

停止持久運行`abortRunStream()` or `abortThreadStream()` requires `@mastra/core@1.62.0` or later. Earlier versions record the abort without stopping the run.

返回：`boolean`. `true` when this process aborted the run locally or can see it executing. The abort request is published either way.

#### `abortThreadStream({ threadId, resourceId?, expectedRunId? })` {/* #abortthreadstream-threadid-resourceid-expectedrunid- */}

使用與以下相同的中止請求中止記憶體執行緒上的活動運行`abortRunStream()`. The run is resolved from this process's thread runtime, so it must have been started here or observed through `subscribeToThread()` on this process. The server route `POST /agents/:agentId/threads/abort` uses this method.

經過`expectedRunId` when the request must only stop a specific run. If another queued run becomes active before the request is handled, the method returns `false` without aborting the successor. Omit `expectedRunId` to abort whichever run is active when the request is handled.

```typescript
const aborted = durableAgent.abortThreadStream({
  resourceId: 'user-1',
  threadId: 'thread-1',
  expectedRunId: runId,
})
```

返回：`boolean`. `false` when this process has no active run recorded for the thread or the active run doesn't match `expectedRunId`. No abort request is sent in either case.

### 恢復 {/* #recovery */}

：：：警告

恢復從最後一個持久快照重新驅動運行。 Mastra 將子Agent委託視為生成的委託`agent-<name>` tool step and doesn't checkpoint its inner LLM or tool calls independently. If recovery replays that step, the entire sub-agent run can execute again, including already-completed tool side effects. Make tools used by sub-agents idempotent, or deduplicate their external side effects. See [crash recovery](/docs/harness/durable-agents#crash-recovery) for operational guidance.

:::

#### `listActiveRuns(options?)` {/* #listactiverunsoptions */}

列出持久快照所在的此Agent程式的運行`running` status: runs whose agentic loop was mid-execution when the workflow engine last saved state. On a live process they transition to `suspended` or a terminal status. After a crash or restart they stay `running` with nothing driving them, which is what `recoverActiveRuns()` re-drives. Runs started by other durable agents on the same storage aren't included.

`running`快照僅在以下情況下寫入`recovery.durableAgents` is `'auto'` or a custom `shouldPersistSnapshot` includes `running`. Without one of those, this method returns no runs. See [snapshot persistence](/docs/harness/durable-agents#snapshot-persistence).

```typescript
const { runs, total } = await durableAgent.listActiveRuns({ resourceId: 'user-1' })

for (const run of runs) {
  await durableAgent.recoverActiveRuns({ runId: run.runId })
}
```

讀取Agent註冊的 Mastra 實例上的工作流快照存儲，如果Agent未註冊，則拋出異常。使用持久性儲存：預設的記憶體儲存在重新啟動時會遺失這些行，從而孤立它們。

只運行在`running` status are returned. Suspended runs keep their snapshots but aren't included, and finished runs aren't retained. Filter by `resourceId` to scope the list to one user.

返回：

```typescript
interface DurableAgentListActiveRunsResult {
  runs: Array<{
    runId: string
    status: 'running'
    threadId?: string
    resourceId?: string
    updatedAt: Date
  }>
  total: number
}
```

#### `recoverActiveRuns(options?)` {/* #recoveractiverunsoptions */}

發現跑步陷入困境`running` status for this agent and re-drives them from the last persisted snapshot. Accepts the same filters and pagination as `listActiveRuns()`, plus `runId`. Returns the outcome for each run.

最多同時進行五個運行等待，並按發現順序傳回結果。每次嘗試都有 30 秒的等待預算，涵蓋`recover()` setup and settlement of the whole recovered workflow. When the budget expires, another run can use the slot. The timeout returns `status: 'skipped'` with `reason: 'recovery-timeout'` and `retryAt` set 30 seconds ahead, without canceling setup or execution, releasing a live claim, or counting as success or failure. The attempt continues in the background, and its eventual outcome doesn't change the returned results. The concurrency limit bounds waiting, not live executions.

[`mastra.recoverAllDurableAgents()`](/reference/core/mastra-class#recoveralldurableagents)自動安排超時重新檢查。直接呼叫者`recoverActiveRuns()` must schedule their own calls after `retryAt`. While the original bulk attempt remains pending, re-checks defer with another `recovery-timeout` and a future `retryAt`, without invoking `recover()` again. Once it settles, recovery checks the persisted snapshot and ownership before retrying. Finished or suspended runs aren't restarted.

預算僅適用於每次運行嘗試`recoverActiveRuns()`, not to discovery, a direct `recover()` call, or overridden custom recovery methods. When shutdown begins, recovery stops dispatching new runs. The original attempt remains tracked for Mastra's shared shutdown drain even after the wait times out.

```typescript
const result = await durableAgent.recoverActiveRuns()
// {
//   recovered: [
//     { runId: 'run-1', status: 'success' },
//     { runId: 'run-2', status: 'skipped', reason: 'run-active', retryAt: 1760123456789 },
//   ],
//   succeeded: 1,
//   failed: 0,
// }
```

透過一個`runId` to recover a single known run:

```typescript
await durableAgent.recoverActiveRuns({ runId: 'run-abc-123' })
```

對於另一個執行仍然驅動的運行，`recoverActiveRuns()` returns `status: 'skipped'` and a `reason`, leaving that execution in control. Checking the run again requires a separate call. For a run held by another process, `retryAt` is the time after which that claim lapses unless renewed. Call `recoverActiveRuns({ runId })` after it to recover the run if its process crashed. [`mastra.recoverAllDurableAgents()`](/reference/core/mastra-class#recoveralldurableagents) schedules these re-checks itself.

| `reason` | Meaning |
| - | - |
| `run-active` | Another execution, possibly in another process, holds the run. Sets `retryAt`. |
| `run-active-locally` | This process is executing the run. |
| `already-in-progress` | This process is already recovering the run. |
| `recovery-timeout` | The wait expired or an earlier bulk recovery attempt is still pending. Sets `retryAt` without duplicating the pending attempt on re-checks. |

返回：

```typescript

```

#### `recover(runId, options?)` {/* #recoverrunid-options */}

按 ID 恢復單次運作。傳回形狀相同的可流式結果`stream()`. Use this when you need to observe the recovery stream in real time.

```typescript
const { output, cleanup } = await durableAgent.recover('run-abc-123', {
  onChunk: chunk => console.log(chunk),
  onError: ({ error }) => console.error(error),
})

await output.text
cleanup()
```

復原從持久啟動重新啟動`durable-agentic-loop` checkpoint. The nested execution row alone isn't sufficient. Before starting a run, enable `recovery: { durableAgents: 'auto' }` on `Mastra`, or provide a `shouldPersistSnapshot` policy that includes `'running'`. Recovery is unavailable until the first running checkpoint is saved, even with persistence enabled. Enabling persistence after a crash can't reconstruct a missing checkpoint.

檢查點之後的模型和Tool呼叫可能會再次運行。使Tool副作用具有冪等性。恢復並不能保證一次性執行。

`recover()`拋出不可用的檢查點和非孤立的運作：

|錯誤ID |拋出時 |
| - | - |
|`DURABLE_AGENT_RECOVER_CHECKPOINT_NOT_AVAILABLE` | The loop row is still `pending` without a workflow input. No restartable checkpoint is available. No recovered execution starts, and any acquired recovery claim is released. |
| `DURABLE_AGENT_RUN_ACTIVE` | Another execution holds the run, and `force` isn't set. |
| `DURABLE_AGENT_RECOVER_RUN_ACTIVE_LOCALLY` | This process is executing the run. `force` doesn't override this. |
| `DURABLE_AGENT_RECOVER_ALREADY_IN_PROGRESS` | This process is already recovering the run. |
| `DURABLE_AGENT_RECOVER_RUN_SUSPENDED` | The run is suspended. Continue it with `resume()`. |
| `DURABLE_AGENT_RECOVER_RUN_NOT_ACTIVE` | The snapshot isn't restartable and isn't suspended. |
| `DURABLE_AGENT_EXECUTION_CONFLICT` | With `force`, another execution claimed the run during the takeover. |

伺服器的`POST /agents/:agentId/recover` route returns ownership, already-in-progress, suspended-run, and inactive-run conflicts as `409 Conflict`. An unavailable checkpoint returns `500 Internal Server Error`.
