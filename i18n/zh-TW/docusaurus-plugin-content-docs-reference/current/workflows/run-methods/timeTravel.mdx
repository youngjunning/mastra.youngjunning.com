# Run.timeTravel()

`.timeTravel()` 方法可從指定步驟重新執行 Workflow，使用已儲存的快照資料或您提供的自訂執行脈絡。它可用於偵錯失敗的 Workflow、以不同輸入測試個別步驟，以及在不重新執行整個 Workflow 的情況下從錯誤中復原。

## 使用範例 {/* #usage-example */}

```typescript
const run = await workflow.createRun()

const result = await run.timeTravel({
  step: 'step2',
  inputData: { value: 10 },
})
```

## 擴充使用範例 {/* #extended-usage-examples */}

### 使用自訂執行脈絡重新執行 {/* #time-travel-with-custom-context */}

```typescript
const result = await run.timeTravel({
  step: 'step2',
  context: {
    step1: {
      status: 'success',
      payload: { value: 0 },
      output: { step1Result: 2 },
      startedAt: Date.now(),
      endedAt: Date.now(),
    },
  },
})
```

### 從巢狀 Workflow 的步驟重新執行 {/* #time-travel-to-nested-workflow-step */}

```typescript
// Using dot notation
const result = await run.timeTravel({
  step: 'nestedWorkflow.step3',
  inputData: { value: 10 },
})

// Using array of step IDs
const result = await run.timeTravel({
  step: ['nestedWorkflow', 'step3'],
  inputData: { value: 10 },
})
```

### 使用初始狀態重新執行 {/* #time-travel-with-initial-state */}

```typescript
const result = await run.timeTravel({
  step: 'step2',
  inputData: { value: 10 },
  initialState: {
    counter: 5,
    metadata: { source: 'time-travel' },
  },
})
```

### 使用巢狀 Workflow 的執行脈絡重新執行 {/* #time-travel-with-nested-workflows-context */}

```typescript
const result = await run.timeTravel({
  step: 'nestedWorkflow.step3',
  context: {
    step1: {
      status: 'success',
      payload: { value: 0 },
      output: { step1Result: 2 },
      startedAt: Date.now(),
      endedAt: Date.now(),
    },
    nestedWorkflow: {
      status: 'running',
      payload: { step1Result: 2 },
      startedAt: Date.now(),
    },
  },
  nestedStepsContext: {
    nestedWorkflow: {
      step2: {
        status: 'success',
        payload: { step1Result: 2 },
        output: { step2Result: 3 },
        startedAt: Date.now(),
        endedAt: Date.now(),
      },
    },
  },
})
```

## 同時呼叫 timeTravel() {/* #concurrent-time-travel-calls */}

同一次 Workflow 執行在同一時間只能進行一個 `timeTravel()` 呼叫。執行任何步驟前，`timeTravel()` 會以原子方式將已儲存的狀態從讀取時的狀態（例如 `suspended` 或 `success`）改為 `running`，藉此取得該次執行的處理權。若另一個呼叫已取得處理權，目前的呼叫會擲出 `WORKFLOW_TIME_TRAVEL_ALREADY_CLAIMED`，且不會執行任何步驟。若讀取時該次執行已處於 `running` 狀態，則會擲出 `WORKFLOW_TIME_TRAVEL_RUN_RUNNING`。

如果同一次執行可能重複觸發重新執行，例如使用者連按兩次「從此步驟重試」，或 API 請求被重試，就需要處理這兩種情況。

```typescript
try {
  await run.timeTravel({ step: 'step2' })
} catch (error) {
  if (
    error.id === 'WORKFLOW_TIME_TRAVEL_ALREADY_CLAIMED' ||
    error.id === 'WORKFLOW_TIME_TRAVEL_RUN_RUNNING'
  ) {
    // Another caller is already re-running this workflow. Re-read the run
    // state instead of time travelling again.
  }
}
```

透過 HTTP 呼叫時，未取得處理權的 `POST /api/workflows/:workflowId/time-travel-async` 請求會回傳 `409 Conflict`。`time-travel` 和 `time-travel-stream` 端點會在重新執行完成前回應，因此後續未取得處理權的呼叫不會改變它們已回傳的狀態碼。

前一次呼叫結束後，仍可再次呼叫 `timeTravel()`，重新執行目標步驟。

:::note

回報支援 `supportsConcurrentUpdates()` 的儲存介接器會以原子方式處理執行權的取得。這需要原子讀取、修改及寫入能力；ClickHouse、Cloudflare D1、Cloudflare KV、Cloudflare Durable Objects、LanceDB 和 Redis 等介接器不具備此能力。若 `shouldPersistSnapshot` 排除 `running` 狀態，或使用尚未支援此機制的 Inngest Workflow runner，也會略過執行權的取得。

:::

## 注意事項 {/* #notes */}

* 從指定步驟重新執行前須設定儲存空間，因為此功能依賴已持久化的 Workflow 快照
* 重新執行 Workflow 時，會從儲存空間載入現有快照（若有）
* 根據快照或提供的執行脈絡重建目標步驟之前的步驟結果
* 從指定步驟開始執行，使用提供或重建的輸入資料
* 若目前 Workflow 定義中，目標步驟之前的某個步驟在快照中沒有紀錄（例如紀錄該次執行後步驟已重新命名，或該次執行從未到達該步驟），`timeTravel` 會在執行任何步驟前拒絕呼叫並提供說明性錯誤；已儲存的快照不會變更
* Workflow 會從該步驟繼續執行直到完成
* 尚未執行過的 Workflow 也可提供自訂執行脈絡或起始步驟的輸入資料，從指定步驟開始執行
