# Mastra.getMCPServer()

`.getMCPServer()` 依照註冊鍵（在 `mcpServers` 設定中註冊伺服器時使用的鍵）取得 MCP 伺服器實例。若要依照伺服器本身的 `id` 屬性查詢，請使用 `.getMCPServerById()`。

## 使用範例 {/* #usage-example */}

```typescript
// Register an MCP server with a registry key
const myServer = new MCPServer({
  id: 'my-mcp-server',
  name: 'My Server',
  version: '1.0.0',
  tools: {/* ... */},
})

export const mastra = new Mastra({
  mcpServers: {
    customKey: myServer, // 'customKey' is the registry key
  },
})

// Retrieve by registry key
const server = mastra.getMCPServer('customKey')

// Alternatively, retrieve by intrinsic ID
const serverById = mastra.getMCPServerById('my-mcp-server')
```

## `MCPServerBase` 契約 {/* #the-mcpserverbase-contract */}

每個已註冊的伺服器都繼承 `MCPServerBase`，此基底類別來自 `@mastra/core/mcp`。`MCPServer` 類別來自 `@mastra/mcp`，依照 MCP `2026-07-28` 協定實作此基底類別，並將 `mcpVersion` 設為 `2`。Tool 作者會接觸到的契約包括 Tool 的執行、暫停，以及下文所述的 `context.mcp` 結構。至於僅適用於 1.x、目前以已棄用的佔位成員形式保留在基底類別中的部分，請參閱[遷移指南](/reference/migrations/mcp-v2)。

### 要求使用者輸入的 Tool {/* #tools-that-ask-for-input */}

MCP 伺服器執行一般的 `createTool` 定義。若 Tool 需要使用者提供資料才能完成，就像在 Agent 或 Workflow 中一樣，須宣告 `suspendSchema` 和 `resumeSchema`，並呼叫 `suspend()`。Core 透過 `{ status: 'suspended', suspendPayload, resumeSchema }` 回報 `executeTool` 中發生的暫停。`MCPServer` 會將其轉為協定中的一輪 `input_required` 互動，再以 `resumeData` 中的答覆恢復 Tool。

```typescript
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

const confirm = createTool({
  id: 'confirm',
  description: 'Ask for confirmation before charging',
  inputSchema: z.object({ amount: z.number() }),
  outputSchema: z.boolean(),
  suspendSchema: z.object({ phase: z.literal('confirm'), amount: z.number() }),
  resumeSchema: z.object({ confirmed: z.boolean() }),
  execute: async ({ amount }, context) => {
    if (!context.resumeData) {
      await context.suspend?.({ phase: 'confirm', amount })
      return
    }
    return context.resumeData.confirmed
  },
})
```

在 MCP 伺服器或直接執行時，`suspend`、`resumeData` 和 `suspendPayload` 位於 Tool 上下文的最外層。Agent 和 Workflow 仍分別將這些成員放在 `context.agent` 和 `context.workflow` 下，直到 `@mastra/core` 下一個主要版本發布。`resumeSchema` 必須是只含基本型別欄位的扁平物件，才能顯示為輸入表單。

每一輪都是獨立的請求。`resumeData` 只包含當輪的答覆，並依 `resumeSchema` 驗證；`suspendPayload` 則包含 Tool 上一次暫停時提供的資料。框架不會重播先前輪次，因此處理程式須依明確命名的階段分支處理，每輪都須重新授權，寫入操作則須依賴業務領域自行確保冪等。由 Agent 或 Workflow 恢復的 Tool 也會收到 `suspendPayload`。

### `mcp` 脈絡 {/* #the-mcp-context */}

Tool 會收到 `context.mcp`（`MCPToolExecutionContext`）：其中的 `extra` 包含請求的 `signal`、`requestId`、`authInfo` 和 `_meta`，另有 `log(level, message, data?)`、`progress({ progress, total?, message? })` 及 `protocolVersion`（`'2026-07-28'`）。如需向使用者取得輸入，請呼叫 `context.suspend()` 並讀取 `context.resumeData`。協定不支援由伺服器發起的請求，因此已棄用的 `elicitation.sendRequest`、`extra.sendRequest` 和 `extra.sendNotification` 成員會擲出錯誤，並在錯誤訊息中指出替代方式。

### 註冊與執行 {/* #registration-and-execution */}

註冊伺服器時，其 Tool 也會註冊到 Mastra 實例。`executeTool(toolId, args, context?)` 會傳回 `{ status: 'completed', output }`；若 Tool 暫停，則傳回 `{ status: 'suspended', suspendPayload, resumeSchema }`，其中 `resumeSchema` 為 JSON Schema。結果沒有失敗變體：Tool 擲出錯誤，或輸入及恢復資料未通過各自的 schema 驗證時，Promise 會遭到拒絕。REST 執行端點會傳回暫停結果，而非誤報 Tool 已完成；下一次呼叫時可傳入 `resumeData` 及原樣送回的 `suspendPayload`，繼續執行 Tool。

若某個註冊鍵已被使用，以同一鍵註冊另一個伺服器時，原有實例仍會保留。註冊鍵與伺服器本身的 ID 不同。
