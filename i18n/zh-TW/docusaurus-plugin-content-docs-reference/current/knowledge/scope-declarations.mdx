# Scope 宣告

`scopes` 選項在 [`Knowledge`](/reference/knowledge/knowledge-class) 中宣告一次執行可持有哪些 Scope 類型，以及誰對這些類型的 Scope 擁有何種角色。每個鍵是模式或具體位址，值則是對應的宣告。建構 Knowledge 時會檢查整個物件，因此拼字錯誤會在啟動時顯現，不會悄悄造成權限未授予。逐步範例請參閱 [Scope 與存取權限](/docs/knowledge/scopes-and-access)。

:::alpha

Knowledge 目前處於 alpha 階段，其 API 可能在不同版本之間變更。

:::

## 使用範例 {/* #usage-example */}

```typescript title="src/mastra/knowledge.ts"
import { Knowledge, knowledgeMemoryScopes } from '@mastra/core/knowledge'

export const knowledge = new Knowledge({
  id: 'company',
  tools: true,
  scopes: {
    ...knowledgeMemoryScopes(),
    'team:$orgId:$teamId': {
      description: 'A team',
      displayLabel: '$teamId team',
      belongsTo: 'org:$orgId',
      access: [
        { principal: 'self', role: 'editor' },
        { principal: 'org:$orgId', role: 'viewer' },
      ],
      pages: [{ key: 'handbook', name: 'Team Handbook' }],
    },
  },
})
```

`scopes` 是必填項目。若實例不需要任何 Scope 類型，請傳入 `{}`。[`knowledgeMemoryScopes()`](/reference/knowledge/knowledge-memory-scopes) 會回傳 Memory 的 `resource:`、`thread:` Scope，以及一個租戶 Scope 的宣告。

## 模式和參數 {/* #patterns-and-params */}

`team:$orgId:$teamId` 這樣的鍵是模式。第一個 `:` 前的文字是類型，每個 `$name` 片段是參數。位址 `team:acme:support` 與此模式相符，其中 `$orgId = acme`、`$teamId = support`。

每個參數恰好對應一個片段，因此位址的片段數必須與模式相同。`resource:user:123` 不符合 `resource:$resourceId`。包含 `:`、`/`、`#` 或 `%` 的 ID 會編碼成單一片段，例如使用者 ID `user:123` 對應 `resource:user%3A123`。請用 [`encodeKnowledgeScopeId()` 或 `knowledgeScopeAddress()`](/reference/knowledge/knowledge-memory-scopes#encodeknowledgescopeid) 建立位址；Memory ID 會自動編碼。

:::warning[早期 alpha 版本儲存的 Scope]

早期版本允許最後一個參數包含位址其餘部分，包括未編碼的冒號。例如，`resource:slack:U123` 曾是 Memory 資源 `slack:U123` 的位址，現在的新位址是 `resource:slack%3AU123`。執行會存取新的空 Scope。舊位址下的頁面、固定內容與筆記仍留在儲存空間，但使用該 Memory 資源的執行已無法存取，Knowledge 也不會自動遷移。

若已儲存 Scope 的位址現在符合另一個模式，也不會取得新模式的規則。例如，`org:acme:viewer` 曾依 `org:$orgId` 儲存，之後才宣告了 `org:$orgId:viewer`；將其當作新模式的 Scope 使用會擲回錯誤。

:::

同一類型可以有多個模式，但任何位址都不能同時符合其中兩個。片段數不同的模式不會重疊；片段數相同的模式，必須在相同位置有不同的固定文字：

```typescript oxfmt:false
scopes: {
  'role:$orgId:admin': { description: 'Org administrators' },
  'role:$orgId:support': { description: 'Support agents' },
}
```

模式重疊會導致啟動失敗，模式之間沒有優先順序：

```text
Knowledge scope patterns "role:$orgId:$role" and "role:$orgId:admin" overlap; patterns of a type must be pairwise disjoint.
```

`kb:$orgId` 和 `kb:$orgId:public` 可以同時宣告，因為 `kb:acme` 與 `kb:acme:public` 的片段數不同。兩者是各自擁有獨立規則的 Scope。持有 `kb:acme` 不會自動取得 `kb:acme:public` 上的角色，除非 `kb:$orgId:public` 的規則指定 `kb:$orgId`。

## 規則 {/* #rules */}

`access` 列出存取規則。每條規則指定 principal，也就是執行必須持有、才能套用規則的 Scope，以及執行取得的角色。principal 是已宣告的 Scope 模式，或代表目前被存取 Scope 的 `self`：

```typescript oxfmt:false
scopes: {
  ...knowledgeMemoryScopes(),
  'team:$orgId:$teamId': {
    description: 'A team',
    access: [
      { principal: 'self', role: 'editor' },
      { principal: 'org:$orgId', role: 'viewer' },
    ],
  },
}
```

- `self` 指宣告規則的 Scope。持有 `team:acme:support` 的執行在該 Scope 上具有 editor 角色。
- `org:$orgId` 從團隊位址綁定 `$orgId`。持有 `org:acme` 的執行可讀取 `team:acme:support`；持有 `org:globex` 的執行則完全看不到它。

角色依序為 `viewer`、`contributor`、`editor` 和 `owner`，後一個角色包含前面角色的權限。各角色的能力如下：

| 角色 | 可執行的操作 |
| - | - |
|`viewer` | 搜尋及讀取頁面與筆記 |
| `contributor` | 建立頁面及新增筆記 |
| `editor` | 編輯頁面名稱、描述與本文；在同一 Scope 內移動頁面；重新標記或移除筆記；固定頁面 |
| `owner` | 將頁面移至其他 Scope；合併移除頁面；刪除頁面 |

各工具操作檢查的角色，請參閱[操作所需權限](/reference/knowledge/knowledge-tools#what-each-operation-needs)。

principal 的參數必須透過以下兩種方式之一綁定：

- **來自位址前綴。** principal 的參數是目標模式最前面的參數，例如 `org:$orgId` 在 `team:$orgId:$teamId` 上的用法。
- **透過 `belongsTo`。** 目標的 `belongsTo` 模式提供這些參數，如下一節所示。

其他綁定方式都會在啟動時失敗：

```text
Knowledge rule principal "y:$b" on "x:$a:$b" would reach scopes that aren't an address prefix; reorder "x:$a:$b"'s params so the bound ones come first, or bind them through belongsTo.
```

每個 principal 也必須屬於已宣告的類型：

```text
Knowledge rule principal "org:$orgId" on "policy:$orgId" is not a declared scope type; declare it or fix the typo.
```

角色不會繼續傳遞。持有 `org:acme` 的執行可讀取 `team:acme:support`，因為它符合 `org:$orgId` 的 viewer 規則；但不會因此取得 `team:acme:support` 對其他 Scope 授予的角色。角色也不會沿階層繼承：除非有相應規則，在 `org:acme` 上擁有角色並不代表可以存取其下的 Scope。

## 使用 `belongsTo` 放置 Scope {/* #place-scopes-with-belongsto */}

`belongsTo` 會將一個 Scope 放在樹中另一個 Scope 之下。本身不授予權限，但規則可透過它綁定參數：

```typescript oxfmt:false
'project:$projectId': {
  belongsTo: 'org:$orgId',
  access: [
    { principal: 'self', role: 'editor' },
    { principal: 'org:$orgId', role: 'viewer' },
  ],
},
```

位址 `project:p1` 不包含 `$orgId`，因此 `org:$orgId` 規則會從專案在樹中的位置綁定此參數。第一次寫入 Knowledge、同時持有 `project:p1` 與恰好一個 `org:` Scope 的執行，會將專案放在該組織 Scope 下；之後位置保持不變。此後，持有 `org:acme` 的執行可讀取 `project:p1`，持有 `org:globex` 的執行則不能。

唯讀執行不會建立或放置任何內容。在寫入執行放置 `project:p1` 之前，`org:$orgId` 規則不會授予其權限。若執行持有多個 `org:` Scope，會記錄警告並維持原有位置；若持有的 `org:` Scope 與已儲存的位置不同，也會記錄警告且不改變位置。

## 子 Scope 與具鍵值的頁面 {/* #child-scopes-and-keyed-pages */}

`children` 宣告隨此類型每個 Scope 一同建立的子 Scope，位址為 `<address>/<name>`。`pages` 宣告範本頁面，也就是此類型每個 Scope 都擁有的具鍵值頁面。範本可在自己的 `pages` 中巢狀排列頁面：

```typescript oxfmt:false
'team:$orgId:$teamId': {
  access: [
    { principal: 'self', role: 'editor' },
    { principal: 'org:$orgId', role: 'viewer' },
  ],
  children: [
    {
      name: 'private',
      description: 'Only the team can read this',
      access: [{ principal: 'team:$orgId:$teamId', role: 'editor' }],
    },
  ],
  pages: [
    {
      key: 'handbook',
      name: 'Team Handbook',
      pages: [{ key: 'on-call', name: 'On-call rota' }],
    },
  ],
},
```

現在每個團隊都有 `team:acme:support/private` 子 Scope，以及工具可透過 `team:acme:support#handbook` 指定的頁面；該頁面下還有 `team:acme:support#handbook/on-call`。

同層頁面的鍵值必須唯一，且不能包含 `/`、`#` 或 `%`。鍵值重複或無效會導致啟動失敗。

範本頁面由設定定義：

- 寫入執行會建立其 Scope 尚缺少的範本頁面，包括日後新增至設定的頁面。唯讀執行不會建立頁面。若該路徑已有頁面，則會將其納入設定並視為範本頁面。
- 工具可依一般角色權限編輯範本頁面的名稱、描述和本文，為其新增筆記，以及將其他頁面合併至該頁面。
- 工具不能移動範本頁面，也不能透過合併將其移除；否則會收到 `"team:acme:support#handbook" is declared in config; change the scope's pages to move it.`。
- 從 `pages` 移除的頁面會變成一般頁面，並保留其鍵值。重新加入範本時，會將該路徑上的頁面及其本文和筆記納入設定；若頁面已移動，下次寫入執行會在原路徑建立新頁面。
- 若主機程式碼透過儲存層刪除範本頁面，下次寫入執行會在該路徑建立新的空白頁面。

子 Scope 不會繼承父 Scope 的規則。必須列出所需的每條規則，參數從父 Scope 的位址綁定。在子 Scope 的規則中，`self` 指子 Scope，但執行不會持有它，因此應像上例一樣將父 Scope 的模式指定為 principal。持有 `org:acme` 的執行可讀取團隊頁面，卻無法讀取其私人子 Scope。

## 為介面設定 Scope 標籤 {/* #label-scopes-for-uis */}

`displayLabel` 為 Studio 等介面提供 Scope 類型的簡短名稱，模型不會看到它。模型讀取的是 `description`。`$params` 由位址填入；具體位址本身的標籤優先：

```typescript oxfmt:false
scopes: {
  'org:$orgId': {
    displayLabel: '$orgId organization',
    access: [{ principal: 'self', role: 'editor' }],
    children: [{ name: 'private', displayLabel: 'Private', access: [{ principal: 'org:$orgId', role: 'owner' }] }],
  },
  'org:acme': { displayLabel: 'Acme HQ' },
}
```

`knowledge.scopeLabel('org:globex')` 回傳 `globex organization`，`knowledge.scopeLabel('org:acme')` 回傳 `Acme HQ`。請參閱 [`scopeLabel()`](/reference/knowledge/knowledge-class#scopelabel)。

## 共用單一 Scope {/* #share-one-scope */}

不含參數的鍵是具體位址，可為其所符合模式下的單一 Scope 新增規則：

```typescript oxfmt:false
'feature:$orgId:$featureId': { description: 'Product features' },
'feature:acme:a': {
  access: [
    { principal: 'team:acme:eng', role: 'editor' },
    { principal: 'team:acme:support', role: 'contributor' },
  ],
},
```

工程團隊可編輯功能 A，支援團隊可在該 Scope 新增筆記與頁面，但不能編輯工程團隊的頁面。其他功能 Scope 只使用模式本身的規則。

必須先宣告模式。若具體位址沒有符合的模式，啟動時會失敗：

```text
Knowledge scope "feature:acme:a" doesn't match a declared pattern; declare its pattern first.
```

具體位址可新增 `description`、`displayLabel`、`access`、`pinnedContext` 與 `pinnedContextPriority`；`belongsTo`、`children` 和 `pages` 則必須在模式上宣告。

## 執行持有的 Scope {/* #run-scopes */}

執行持有的 Scope 由主機程式碼提供：請求內容中的 `MASTRA_SCOPES_KEY`、呼叫時的 `scopes` 選項，以及 Agent 的 `scopes` 選項。Agent 上的清單會與其他來源合併；Agent 上的函式則接收這些 Scope 並回傳最終集合。啟用 Memory 時，執行還會持有 `resource:<resourceId>` 與 `thread:<threadId>`。請參閱[設定執行的 Scope](/docs/knowledge/scopes-and-access#set-a-runs-scopes)。

附加 Knowledge 後，執行持有的每個 Scope 都必須符合已宣告的類型。即使某個類型只用來標識執行身分，也必須宣告，空宣告如 `'role:$orgId:support': {}` 即可。

一次執行恰好有一個 Memory 資源與一個執行緒。`knowledgeMemoryScopes()` 會將使用者的 `resource:` Scope 放在首次寫入執行所持有的組織 Scope 下，此位置之後不會改變。若使用者在多個組織工作，應為每個組織分配不同的資源 ID，例如 `acme-dana` 與 `globex-dana`。

`MASTRA_SCOPES_KEY` 是保留鍵：伺服器會忽略請求本文中的該鍵。需要使用已將其設為保留鍵的 `@mastra/server` 版本。

### 錯誤 {/* #errors */}

|錯誤 |原因 |
| - | - |
|`Knowledge run scope "project:x" does not match a declared scope type. …` | Knowledge 未宣告執行持有的某個 Scope。 |
| ``Knowledge tools need run scopes: give the agent or the call `scopes`, or run it with Memory.`` | 執行沒有 Scope，也未啟用 Memory。 |
| `Agent request context "mastra__scopes" must be an array of "<type>:<value>" strings.` | 某個 Scope 項目不是字串。 |
| `Invalid agent scope "Org:acme" in request context "mastra__scopes". …` | 某個 Scope 不符合小寫類型的 `<type>:<value>` 格式。 |
| `The agent's scopes function dropped "resource:dana". …` | Agent 的 `scopes` 函式遺漏了 `resource:` 或 `thread:` Scope。 |
| `Agent scopes contain more than one resource: …` | 執行持有兩個 `resource:`（或 `thread:`）Scope。 |
| `Agent scope "resource:cust-7" conflicts with option "memory.resource" "spec-1". …` | `resource:` Scope 與 `memory.resource` 不一致。 |
| `AGENT_SCOPES_SERVER_OUTDATED` | Scope 來自請求內容，或是在使用舊版 `@mastra/server` 的呼叫中傳入。 |

## 重新命名或停用範圍類型 {/* #rename-or-retire-a-scope-type */}

每個已儲存的 Scope 都會記住建立它的宣告鍵，位址前綴規則與 `belongsTo` 規則都依該鍵比對。若在 `scopes` 中把鍵從 `'team:$org:$team'` 改為 `'team:$orgId:$teamId'`，現有團隊 Scope 將失去這些規則。為避免此情況，Knowledge 首次使用時會對照 `scopes` 檢查已儲存的鍵；只要缺少任何一個，就會拒絕執行：

```text
Knowledge storage has scopes created from declarations this config doesn't declare: "team:$org:$team" (12 scopes). Restore each key in scopes, rename it with knowledge.renameScopeDeclaration(from, to), or keep the key with no access rules to retire it.
```

在 `scopes` 中重新命名鍵後，還須將已儲存的 Scope 遷移至新鍵。`team:$org:$team/internal` 等子 Scope 鍵也會一起遷移：

```typescript
await knowledge.renameScopeDeclaration('team:$org:$team', 'team:$orgId:$teamId')
```

重新命名是單一步驟操作；若操作遭拒，不會更動任何內容。舊鍵仍在 `scopes` 中、新鍵不存在，或已儲存的位址不符合新模式時，都會拒絕操作。

滾動部署期間，使用新設定的執行個體在重新命名完成前會拒絕執行。重新命名後，仍使用舊設定的執行個體會失去這些 Scope 上的位址前綴與 `belongsTo` 規則。因此應先部署新設定，再立即執行重新命名。

若要停用某個類型而不遷移其 Scope，請在 `scopes` 中保留該鍵，但移除 `access` 規則。Scope 仍留在儲存空間中，卻不會被任何規則存取。
