# CLI 指令

Mastra 提供的命令列介面（CLI）可用來開發、建置及啟動 Mastra 專案。

## `mastra dev` {/* #mastra-dev */}

啟動伺服器，對外提供 [Studio](/docs/studio/overview) 以及 Agent、工具和 Workflow 的 REST 端點。執行 `mastra dev` 後，可訪問 [http://localhost:4111/swagger-ui](http://localhost:4111/swagger-ui) 查看所有可用端點。

還可以[設定伺服器](/reference/configuration#server-options)。

### 選項 {/* #flags */}

除[通用選項][common-flags]外，此命令還支援以下選項：

#### `--https` {/* #--https */}

啟用本地 HTTPS。[瞭解詳情](/reference/configuration#serverhttps)。

#### `--inspect` {/* #--inspect */}

以偵錯檢查模式啟動開發伺服器。可指定主機和連線埠，例如 Docker 中的 `--inspect=0.0.0.0:9229`。不能與 `--inspect-brk` 同時使用。

#### `--inspect-brk` {/* #--inspect-brk */}

以偵錯檢查模式啟動開發伺服器，並在指令碼開始時中斷。可指定主機和連線埠，例如 `--inspect-brk=0.0.0.0:9229`。不能與 `--inspect` 同時使用。

#### `--custom-args` {/* #--custom-args */}

以逗號分隔、傳給 Node.js 程式的自定義參數，例如 `--require=newrelic` 或 `--experimental-transform-types`。

#### `--request-context-presets` {/* #--request-context-presets */}

包含[請求上下文](/docs/server/request-context)預設的 JSON 檔案路徑。提供後，Studio 的請求上下文編輯器會顯示下拉菜單，可快速切換預設設定。

```bash
mastra dev --request-context-presets ./presets.json
```

該檔案必須是 JSON 對象，其中每個鍵都是預設名稱，每個值都是一個對象：

```json
{
  "development": { "userId": "dev-user", "env": "development" },
  "production": { "userId": "prod-user", "env": "production" }
}
```

### 設定 {/* #configs */}

可透過環境變數調整 `mastra dev` 的行為。

#### 跳過對等相依套件版本檢查 {/* #skip-peer-dependency-check */}

設定 `MASTRA_SKIP_PEERDEP_CHECK=1`，可在啟動時跳過對等相依套件版本不匹配檢查：

```bash
MASTRA_SKIP_PEERDEP_CHECK=1 mastra dev
```

在 monorepo 開發中，對等相依套件可能已升級但包尚未發佈，此設定很有用。

#### 禁用建置緩存 {/* #disable-build-caching */}

設定 `MASTRA_DEV_NO_CACHE=1` 可強制完整重建，不使用 `.mastra/` 下的緩存資源：

```bash
MASTRA_DEV_NO_CACHE=1 mastra dev
```

偵錯封裝插件或懷疑輸出過舊時可使用此設定。

#### 限制並行度 {/* #limit-parallelism */}

`MASTRA_CONCURRENCY` 限制並行執行的高開銷操作數量，主要包括建置和評估步驟。例如：

```bash
MASTRA_CONCURRENCY=4 mastra dev
```

不設定時，CLI 會根據機器選擇合適的預設值。

#### 自定義 Provider 端點 {/* #custom-provider-endpoints */}

使用 Vercel AI SDK 支援的 Provider 時，可設定基礎 URL，讓請求經過代理或內部網關。OpenAI 範例：

```bash
OPENAI_API_KEY=<your-api-key> \
OPENAI_BASE_URL=https://openrouter.example/v1 \
mastra dev
```

Anthropic 範例：

```bash
ANTHROPIC_API_KEY=<your-api-key> \
ANTHROPIC_BASE_URL=https://anthropic.internal \
mastra dev
```

這些設定會傳給 Mastra 模型路由器，並適用於任何選擇了 `"openai/..."`
或 `"anthropic/..."` 的模型。

## `mastra factory dev` {/* #mastra-factory-dev */}

為開發 [Agent Builder](https://agent-builder.mastra.ai/) 啟動開發伺服器。此命令與 [`mastra dev`](#mastra-dev) 使用相同的開發執行時和選項，並寫入同一個 `.mastra/output` 目錄。

```bash
npx mastra factory dev
```

兩個命令共用開發鎖，因此 `mastra dev` 和 `mastra factory dev` 不能在同一專案中同時執行。如果其中一個已在執行，另一個會因開發伺服器重複而退出。

開發 Agent Builder 功能時使用 `mastra factory dev`。它支援與 [`mastra dev`](#mastra-dev) 相同的選項，包括 `--https`、`--inspect`、`--inspect-brk`、`--custom-args` 和 `--request-context-presets`。

## `mastra build` {/* #mastra-build */}

`mastra build` 命令將 Mastra 專案封裝為可用於正式環境的 Hono 伺服器。[Hono](https://hono.dev/) 是輕量且類型安全的 Web 框架，支援透過中間件將 Mastra Agent 作為 HTTP 端點部署。

Mastra 底層使用 Rollup 伺服器定位專案入口檔案，再封裝為生產就緒的 Hono 伺服器。封裝過程會進行 tree shaking，並生成便於偵錯的 source map。

`.mastra` 中的輸出可透過 [`mastra start`](#mastra-start) 部署到任意雲伺服器。

部署到[無伺服器平台](/docs/deployment/cloud-providers)時，需要安裝相應的 Deployer，才能在 `.mastra` 中生成正確的輸出。

此命令支援[通用選項][common-flags]。

### 選項 {/* #flags-1 */}

#### `--studio` {/* #--studio */}

建置時一並封裝 Studio UI。

### 設定 {/* #configs-1 */}

可透過環境變數調整 `mastra build` 的行為。

#### 跳過對等相依套件版本檢查 {/* #skip-peer-dependency-check-1 */}

設定 `MASTRA_SKIP_PEERDEP_CHECK=1` 可跳過對等相依套件版本不匹配檢查：

```bash
MASTRA_SKIP_PEERDEP_CHECK=1 mastra build
```

#### 限制並行度 {/* #limit-parallelism-1 */}

在 CI 或資源受限的環境中，可設定 `MASTRA_CONCURRENCY`，限制同時執行的高開銷任務數量。

```bash
MASTRA_CONCURRENCY=2 mastra build
```

## `mastra start` {/* #mastra-start */}

:::note

先運行 `mastra build`，再使用 `mastra start`。

:::

啟動本地伺服器，以生產模式提供已建置的 Mastra 應用。預設啟用 [OTEL 追蹤](/docs/observability/tracing/overview)。

### 選項 {/* #flags-2 */}

除[通用選項][common-flags]外，此命令還支援以下選項：

#### `--dir` {/* #--dir */}

已建置的 Mastra 輸出目錄路徑，預設為 `.mastra/output`。

#### `--custom-args` {/* #--custom-args-1 */}

以逗號分隔、傳給 Node.js 程式的自定義參數，例如 `--require=newrelic` 或 `--experimental-transform-types`。

## `mastra worker build` {/* #mastra-worker-build */}

將 Mastra 應用封裝用於 Worker 部署。輸出與 `mastra build` 相同，都是自包含的 `.mastra/output/` 目錄。

```bash
mastra worker build [options]
```

### 選項 {/* #flags-3 */}

#### `--dir` {/* #--dir-1 */}

Mastra 原始碼目錄路徑，預設為 `src/mastra`。

#### `--root` {/* #--root */}

專案根目錄，預設為目前目錄。

#### `--tools` {/* #--tools */}

封裝時要包含的工具路徑，以逗號分隔。

#### `--output-dir` {/* #--output-dir */}

自定義輸出目錄，預設為 `.mastra/output`。

#### `--debug` {/* #--debug */}

建置期間啟用偵錯紀錄。

## `mastra experiment build` {/* #mastra-experiment-build */}

建置獨立的配套 Worker，無需暴露 HTTP 伺服器即可執行實驗。Worker 會載入導出的 `Mastra` 執行個體，從標準輸入接收帶版本號的逐行 JSON（NDJSON）協議訊息，並將協議事件寫入標準輸出。

```bash
mastra experiment build [options]
```

預設將 Worker 寫入 `.mastra/experiment-worker`。該目錄包含可執行入口、生產依賴和 `experiment-worker-manifest.json`。標準輸出只能用於協議內容；Worker 診斷資訊寫入標準錯誤。

### 建置產物契約 {/* #artifact-contract */}

`experiment-worker-manifest.json` 將建置產物標識為 `mastra-experiment-worker`，版本為 `1`，並提供：

* 嵌入可執行檔案的 CLI 版本、建立時間和唯一建置 ID。
* 支援的協議版本和資料集正規化版本。
* 啟動 Worker 所需的可執行檔案、參數和工作目錄。
* 依賴清單與生成的鎖檔案路徑。
* 按順序列出的每個建置產物檔案的 SHA-256 摘要。
* 根據檔案路徑和摘要計算的 SHA-256 內容摘要。

內容摘要不包含 `experiment-worker-manifest.json`，以避免自引用。封裝時仍須包含清單檔案；若清單本身也需要證明，請使用外層包摘要。

### 協議契約 {/* #protocol-contract */}

Worker 實現固定版本 `1` 的實驗配套 Worker 協議。它從標準輸入讀取嚴格的 UTF-8 NDJSON 訊框，且每一訊框（包括最後一訊框）都必須以換行符結尾。超過 1 MiB 的訊框、格式錯誤或截斷的訊框、不受支援的協議或正規化版本，以及與目前實驗關聯資訊不符的訊息，都會因協議錯誤而被拒絕。

執行請求必須匹配建置產物中嵌入的建置 ID，並包含有序資料集條目數量和 SHA-256 證明。Worker 會發出從 `0` 開始連續遞增的序號、由計時器驅動的心跳、等待完成的實驗生命週期事件，以及恰好一個終止事件。取消請求必須匹配目前協議版本和實驗 ID，以及作業 ID、嘗試次數和冪等鍵。

協議退出碼如下：

| 程式碼 | 含義 |
| - | - |
| `0` | 已完成 |
| `10` | 已完成，但部分條目出錯 |
| `20` | 致命故障 |
| `21` | 可重試故障 |
| `30` | 已取消 |
| `31` | 已超時 |
| `70` | 協議故障 |

### 資料包欄位處理 {/* #packet-field-handling */}

Worker 將目標身份、有序的行內資料集條目、評分器 ID、併發數、超時、實驗元資料、請求上下文、工具模擬和取消信號傳給 `runExperiment`。評分器版本和建置產物來源保留為實驗元資料。評分器程式碼來源由建置產物准入檢查保證，而非在執行時查找評分器。

版本 `1` 對未聲明工具採用確定性的拒絕策略。非空網絡允許列表和金鑰引用會因策略失敗而被拒絕，因為網絡限制與金鑰注入由程式沙箱負責。傳給 `runExperiment` 時，資料集條目的來源和預期軌跡欄位會保留為條目元資料。

### 選項 {/* #flags-4 */}

#### `--dir` {/* #--dir-2 */}

Mastra 原始碼目錄路徑，預設為 `src/mastra`。

#### `--root` {/* #--root-1 */}

專案根目錄，預設為目前目錄。

#### `--output-dir` {/* #--output-dir-1 */}

自定義建置產物目錄。相對路徑以專案根目錄為基準解析，預設為 `.mastra/experiment-worker`。

#### `--debug` {/* #--debug-1 */}

建置期間啟用偵錯紀錄。

## `mastra worker start` {/* #mastra-worker-start */}

:::note

先運行 `mastra worker build` 或 `mastra build`，再使用 `mastra worker start`。

:::

從已有的建置包啟動 Worker 程式。可選的 `name` 參數會在子程式中設定 `MASTRA_WORKERS`，以決定啟動哪個 Worker。

```bash
mastra worker start [name] [options]
```

### 選項 {/* #flags-5 */}

#### `--dir` {/* #--dir-3 */}

建置輸出目錄路徑，預設為 `.mastra/output`。

#### `--env` {/* #--env */}

環境檔案路徑，預設為 `.env.production`；若不存在則備援到 `.env`。

### 範例 {/* #examples */}

```bash
# Start only the orchestration worker
mastra worker start orchestration

# Start only the scheduler
mastra worker start scheduler

# Start from a custom build directory
mastra worker start orchestration --dir ./dist
```

有關部署拓撲和設定，請參閱 [Workers](/docs/deployment/workers)。

## `mastra studio` {/* #mastra-studio */}

以靜態伺服器方式啟動 [Studio](/docs/studio/overview)。啟動後，可輸入 Mastra 執行個體 URL（例如 `http://localhost:4111`），讓 Studio 連線到 Mastra 後端。命令會在目前目錄查找 `.env` 和 `.env.production` 檔案。

### 選項 {/* #flags-6 */}

除[通用選項][common-flags]外，此命令還支援以下選項：

#### `--port` {/* #--port */}

Studio 使用的連線埠，預設為 `3000`。

#### `--server-host` {/* #--server-host */}

要連線的 Mastra API 伺服器主機，預設為 `localhost`。

#### `--server-port` {/* #--server-port */}

要連線的 Mastra API 伺服器連線埠，預設為 `4111`。

#### `--server-protocol` {/* #--server-protocol */}

要連線的 Mastra API 伺服器協議，預設為 `http`。

#### `--server-api-prefix` {/* #--server-api-prefix */}

Mastra API 伺服器的路由前綴，預設為 `/api`。

#### `--request-context-presets` {/* #--request-context-presets-1 */}

包含[請求上下文](/docs/server/request-context)預設的 JSON 檔案路徑。行為與 [`mastra dev` 選項](#--request-context-presets)相同。

```bash
mastra studio --request-context-presets ./presets.json
```

## `mastra deploy` {/* #mastra-deploy */}

建置專案並部署到 `--env` 指定的 Mastra 平台環境。這是新部署推薦使用的命令，取代 [`mastra studio deploy`](#mastra-studio-deploy) 和 [`mastra server deploy`](#mastra-server-deploy)；後兩者仍可執行，但不再建議用於新專案。

需要先透過 [`mastra auth login`](#mastra-auth-login) 登錄，或設定 `MASTRA_API_TOKEN` 環境變數。

```bash
mastra deploy
mastra deploy --env staging
mastra deploy --env production --region eu
```

命令會執行 `mastra build`，將輸出壓縮後上傳到目標環境。隨後持續查詢部署狀態並流式顯示建置紀錄，直至部署進入終止狀態。

組織、專案和環境按以下優先級確定：環境變數（`MASTRA_ORG_ID`、`MASTRA_PROJECT_ID`）、CLI 選項（`--org`、`--project`、`--env`）、`.mastra-project.json` 設定檔案、憑證中的目前組織，最後才是互動式提示。首次部署時，CLI 會將確定的組織和專案 ID 保存至 `.mastra-project.json`，後續部署即可跳過提示。

確認後，CLI 會根據 `package.json` 中的 `name` 欄位建立尚不存在的專案，並建立缺失的目標環境；環境類型預設為 `type: staging`，但目标为 `production` 时除外。加上 `--yes` 後，可透過一條非互動命令完成建立與部署：

```bash
mastra deploy --env staging --yes
```

設定 `--env <name>` 且未設定 `--env-file` 時，CLI 會自動選取專案目錄中存在的 `.env.<name>`（例如 `.env.staging`）。將 `<name>` 插入檔案路徑前，會先按嚴格的允許列表驗證其值。

### 參數 {/* #arguments */}

#### `[dir]` {/* #dir */}

專案目錄，預設為目前目錄。

### 選項 {/* #flags-7 */}

#### `--env` {/* #--env-1 */}

目標環境名稱，預設為 `production`。如果專案目錄中存在 `.env.<name>` 且未設定 `--env-file`，CLI 會自動選擇該檔案。環境不存在時，CLI 會在確認後建立。

#### `--org` {/* #--org */}

組織 ID，也可以透過環境變數 `MASTRA_ORG_ID` 設定。

#### `--project` {/* #--project */}

專案 ID、slug 或名稱，也可以透過環境變數 `MASTRA_PROJECT_ID` 設定。如果沒有匹配的專案，部署時會以該值為名稱建立新專案。

#### `-y, --yes` {/* #-y---yes */}

無需確認提示，自動接受預設設定，包括建立專案和環境。

#### `-c, --config` {/* #-c---config */}

專案設定檔案路徑，預設為 `.mastra-project.json`。

#### `--env-file` {/* #--env-file */}

隨部署一同打包的環境檔案路徑（相對於專案目錄）。設定後，會禁用 `.env.<name>` 基於 `--env` 的自動選擇。

```bash
mastra deploy --env staging --env-file .env.staging.local
```

#### `--region` {/* #--region */}

新建環境所在的區域，例如 `eu`。僅在 CLI 建立環境時生效。

#### `--skip-build` {/* #--skip-build */}

跳過建置步驟，直接部署已有的 `.mastra/output` 目錄。如果現有建置相對目前原始碼已過期，CLI 會發出警告。

#### `--skip-preflight` {/* #--skip-preflight */}

跳過上傳前對建置輸出的驗證。

#### `--debug` {/* #--debug-2 */}

建置步驟期間啟用偵錯紀錄。

### CI/CD 使用 {/* #cicd-usage */}

為無互動部署設定環境變數 `MASTRA_API_TOKEN`、`MASTRA_ORG_ID` 和 `MASTRA_PROJECT_ID`。設定 `MASTRA_API_TOKEN` 後會自動跳過互動式提示；結合 `--yes` 可自動確認建立環境。

```bash
export MASTRA_API_TOKEN="..."
export MASTRA_ORG_ID="..."
export MASTRA_PROJECT_ID="..."
mastra deploy --env staging --yes
```

## `mastra env` {/* #mastra-env */}

管理 Mastra 平台上的環境。環境是專案的部署目標，例如 `production`、`staging`、`preview-42`。目前組織從已保存的憑證中確定。

每個子命令都按固定順序確定所屬專案：先檢查 `--project <name|slug|id>` 選項，再檢查環境變數 `MASTRA_PROJECT_ID`，最後讀取目前目錄中的 `.mastra-project.json`（由 [`mastra deploy`](#mastra-deploy) 寫入）。在專案目錄運行命令，就無需重複指定專案。

### `mastra env list` {/* #mastra-env-list */}

列出專案的環境。每個環境顯示最新部署；正在服務流量的部署會標記為 `(active)`。還會顯示附加資料庫等託管資源注入的環境變數名稱。

```bash
mastra env list
```

#### `--json` {/* #--json */}

輸出機器可讀的 JSON。只包含非敏感元資料（ID、名稱、slug、類型、區域、分支、URL、託管環境變數名稱和最新部署狀態），因此可安全寫入 CI 紀錄。

### `mastra env create` {/* #mastra-env-create */}

為專案建立新環境。

```bash
mastra env create staging --type staging --region eu
```

#### `-t, --type` {/* #-t---type */}

環境類型，可為 `production`、`staging` 或 `preview`，預設為 `staging`。

#### `-r, --region` {/* #-r---region */}

環境所在區域，例如 `eu`。

#### `--json` {/* #--json-1 */}

輸出機器可讀的 JSON。與 [`mastra env list`](#mastra-env-list) 一樣，會省略敏感欄位。

### `mastra env delete` {/* #mastra-env-delete */}

刪除環境。

```bash
mastra env delete <env>
```

`<env>` 可為環境名稱、slug 或 ID。除非傳入 `--yes`，否則 CLI 會要求確認。

#### `-y, --yes` {/* #-y---yes-1 */}

跳過確認提示。

### `mastra env restart` {/* #mastra-env-restart */}

重啓環境中的執行服務，使已保存的環境變數（包括附加資料庫注入的託管變數）立即生效，無需重新部署。

```bash
mastra env restart <env>
```

`<env>` 可為環境名稱、slug 或 ID。如果該環境從未部署過，會傳回衝突錯誤。

### `mastra env vars pull` {/* #mastra-env-vars-pull */}

將環境變數拉取到本地環境檔案（預設 `.env`）。檔案包含該環境部署時使用的變數集合，即環境本身保存的變數（例如在控制台環境編輯器中添加的變數）。每個環境獨立拉取，不會合併其他環境保存的值。仍使用[舊版流水線](/docs/mastra-platform/deploy#migrating-from-server-and-studio-deploys)的專案改用專案級變數，因此拉取其任一環境都會得到共享的專案級值。附加資料庫注入的託管變數僅以注釋列出名稱，因為其值是平台管理的金鑰。

```bash
mastra env vars pull
mastra env vars pull <env> --output .env.staging
```

`<env>` 可為環境名稱、slug 或 ID。專案只有一個環境時可省略。檔案以 `0600` 權限寫入；若輸出檔案已存在，命令會停止。傳入 `--force` 可覆蓋。

#### `-o, --output` {/* #-o---output */}

寫入的檔案，預設為 `.env`。

#### `-f, --force` {/* #-f---force */}

覆蓋已有的輸出檔案。

### `mastra env db` {/* #mastra-env-db */}

管理 Mastra 平台專案附加的資料庫。資料庫由託管 Provider（如 Turso 或 Neon）建立，連線環境變數會自動注入部署。

資料庫可以是**環境級**（環境變數只提供給一個環境），也可以是**共享**（專案級，提供給所有環境）。`mastra env db create` 預設建立環境級資料庫：可傳入環境參數，也可由 CLI 自動選擇或提示。建立時傳入 `--shared` 則改為附加共享資料庫。其他子命令（`list`、`delete`、`keys`）中，傳入環境參數可操作環境級資料庫，省略則操作共享資料庫。

建立和刪除資料庫需要組織內的 `admin` 角色。

### `mastra env db list` {/* #mastra-env-db-list */}

列出專案附加的資料庫，包括 Provider、建立狀態、作用範圍（每個資料庫供給的環境）以及注入的環境變數名稱。傳入環境可只顯示供該環境使用的資料庫，包括環境級和共享資料庫。

```bash
mastra env db list
mastra env db list <env>
```

#### `--json` {/* #--json-2 */}

輸出機器可讀的 JSON。

### `mastra env db create` {/* #mastra-env-db-create */}

建立並附加託管資料庫，然後持續查詢直至就緒。如果建立失敗，會顯示 Provider 提供的錯誤詳情。

預設情況下，資料庫僅歸屬單個環境。可傳入環境參數指定；省略時，CLI 會選擇專案中唯一的環境，或在有多個環境時提示選擇。在非互動場景（CI、`--json`）中，必須傳入環境參數。也可使用 `--shared` 附加供所有環境共用的專案級資料庫。

環境級資料庫的 Provider 區域繼承自對應環境。共享資料庫可透過 `--region` 指定區域。

```bash
mastra env db create --kind turso                                    # picks or prompts for an environment
mastra env db create staging --kind turso                            # scoped to the "staging" environment
mastra env db create --kind turso --shared                           # shared by all environments
mastra env db create --kind neon --name my-app-db --region aws-us-east-1 --shared
mastra env db create production --kind postgres                      # VPC-isolated Postgres, private to the environment
```

#### `--kind` {/* #--kind */}

資料庫 Provider，必填。可為 `turso`、`neon`（公開的無伺服器 Postgres）或 `postgres`（與部署環境位於同一私有網絡的 VPC 隔離 Postgres）。

#### `--name` {/* #--name */}

資料庫名稱，預設根據專案 slug 和 Provider 生成，例如 `my-app-turso`、Neon 的 `my-app-pg` 或 VPC Postgres 的 `my-app-postgres`。

#### `--region` {/* #--region-1 */}

共享資料庫的 Provider 區域 ID。環境級資料庫會忽略此選項。

#### `--shared` {/* #--shared */}

以專案級資料庫的形式附加，供所有環境共用。不能同時傳入環境參數。

#### `--no-wait` {/* #--no-wait */}

附加任務進入隊列後立即傳回，無需等待資料庫就緒。之後可用 `mastra env db show` 查看進度。

#### `--json` {/* #--json-3 */}

輸出機器可讀的 JSON。專案有多個環境時，此模式要求提供環境參數或 `--shared`，不會出現互動提示。

### `mastra env db show` {/* #mastra-env-db-show */}

顯示資料庫詳情；就緒後還會顯示連線環境變數。預設隱藏金鑰值。

```bash
mastra env db show <database>
```

`<database>` 可為資料庫 ID 或名稱。

#### `--show-secrets` {/* #--show-secrets */}

顯示連線金鑰的實際值，而不進行隱藏。

#### `--json` {/* #--json-4 */}

輸出機器可讀的 JSON。除非傳入 `--show-secrets`，否則會隱藏金鑰值。

### `mastra env db delete` {/* #mastra-env-db-delete */}

透過 Provider 永久刪除資料庫及其全部資料，無法撤銷。除非傳入 `--yes`，否則 CLI 會要求確認。刪除後，部署不再接收該資料庫的環境變數。

```bash
mastra env db delete <database>
```

#### `-y, --yes` {/* #-y---yes-2 */}

跳過確認提示。

### `mastra env deploys` {/* #mastra-env-deploys */}

按時間從新到舊列出專案的部署。正在服務流量的部署標記為 `(active)`。

```bash
mastra env deploys [environment]
```

省略 `[environment]` 可顯示所有環境的部署；傳入環境名稱、slug 或 ID 可只查看指定環境。

#### `--json` {/* #--json-5 */}

輸出機器可讀的 JSON。

### `mastra env diagnosis` {/* #mastra-env-diagnosis */}

診斷失敗的部署並給出修復建議。每項建議包含說明、推薦操作和適用時的文檔連結，最後附上控制台中的部署紀錄連結。

```bash
mastra env diagnosis
mastra env diagnosis <deploy-id>
mastra env diagnosis --environment staging
```

省略 `<deploy-id>` 時，會診斷該環境最近一次部署。環境由 `--environment` 指定；專案只有一個環境時可自動確定。專案有多個環境時，必須提供 `--environment` 或部署 ID。單獨傳入部署 ID 時，無需關聯專案。

如果部署執行正常，命令會報告無需建議並退出。否則，若還沒有診斷任務，命令會啟動診斷，最長輪詢五分鐘直至結果就緒。再次執行會復用進行中的診斷，不會重新開始。若診斷本身失敗，命令以非零狀態碼退出。

`mastra deploy` 失敗後，CLI 會顯示可直接執行的 `mastra env diagnosis <deploy-id>` 命令。

#### `--project` {/* #--project-1 */}

專案名稱、slug 或 ID。預設使用[ `mastra env` ](#mastra-env)所述的已關聯專案。

#### `--environment` {/* #--environment */}

環境名稱、slug 或 ID。預設使用專案中唯一的環境。專案有多個環境且未傳入部署 ID 時必填。

## `mastra studio deploy` {/* #mastra-studio-deploy */}

:::note

`mastra studio deploy` 仍可使用，但已由 [`mastra deploy`](#mastra-deploy) 取代；新命令支援在同一專案中使用多個環境（`--env staging`、`--env production`）。新專案應使用 `mastra deploy`。

:::

建置專案並部署到 Mastra 平台。須透過 [`mastra auth login`](#mastra-auth-login) 登錄，或設定 `MASTRA_API_TOKEN` 環境變數。

```bash
mastra studio deploy
```

命令執行 `mastra build` 並壓縮輸出。上傳到平台前會讀取專案目錄中的環境檔案。上傳後，持續查詢部署狀態並流式顯示建置紀錄，直到部署進入終止狀態。

部署命令會自動載入專案的 `.env` 檔案。如果 `MASTRA_PROJECT_ID` 指向已為 Observability 建立的專案，部署會關聯該專案，而非新建專案。將 Studio 部署到僅啟用可觀測性的專案時，平台會將其轉換為 Studio 專案。

專案目錄中必須至少有一個 `.env` 或 `.env.*` 檔案（不包括 `.env.example`），否則 CLI 報錯 `Error: No env file found for deploy.`。存在多個環境檔案時，CLI 會提示選擇，預設選中 `.env.production`。可傳入 `--env-file` 顯式指定。如果同時使用 `--yes` 且有多個環境檔案，則必須傳入 `--env-file`，否則部署會失敗。

組織和專案依次從環境變數選項、`.mastra-project.json` 設定檔案、憑證中的目前組織，最後的互動提示中確定。首次部署時，CLI 會將確定的 ID 保存至 `.mastra-project.json`，後續部署即可跳過提示。

如果 `--project <value>` 與現有專案的 ID 或 slug 均不匹配，CLI 會將 `<value>` 視為新專案名稱，確認後建立。加上 `--yes` 後，可用一條非互動命令建立並部署新專案：

```bash
mastra studio deploy --project "my-new-project" --yes
```

### 選項 {/* #flags-8 */}

#### `--org` {/* #--org-1 */}

#### `--project` {/* #--project-2 */}

#### `-c, --config` {/* #-c---config-1 */}

#### `--env-file` {/* #--env-file-1 */}

```bash

#### `--skip-build` {/* #--skip-build-1 */}

#### `--debug` {/* #--debug-3 */}

mastra server env pull .env.production --project my-project
```

## `mastra auth` {/* #mastra-auth */}

### `mastra auth login` {/* #mastra-auth-login */}

開啟瀏覽器登錄，並將憑證保存在本地。

需要瀏覽器登錄但沒有互動終端機時（例如 CI、輸入或輸出被管道接管、或在 Agent 的 shell 中），命令會先顯示無頭 shell 的認證方法，然後仍等待瀏覽器登錄。在同一台機器上，可先在自己的終端機執行一次 `mastra auth login`，後續命令便能復用保存的會話。在 CI 或另一台機器上，應改為設定 `MASTRA_API_TOKEN` 和 `MASTRA_ORG_ID`。可在已登錄的終端機透過 [`mastra auth tokens create`](#mastra-auth-tokens-create) 或在控制台建立權杖。如果等待瀏覽器登錄超時，命令以狀態碼 1 退出。如果非互動 shell 中已有 `MASTRA_API_TOKEN`，命令會跳過瀏覽器登錄：驗證權杖並檢查是否已選擇組織（來自 `MASTRA_ORG_ID` 或已保存憑證），成功時以狀態碼 0 退出；任一檢查失敗時以狀態碼 1 退出，並指出缺失內容。

### `mastra auth logout` {/* #mastra-auth-logout */}

刪除已保存的憑證。如果環境中仍設定了 `MASTRA_API_TOKEN`，CLI 會提示該權杖仍將繼續使用。

### `mastra auth whoami` {/* #mastra-auth-whoami */}

顯示目前使用者的郵箱、使用者 ID 和活動組織。

### `mastra auth orgs` {/* #mastra-auth-orgs */}

列出所有組織及使用者在各組織中的角色，並標記目前組織。

#### `mastra auth orgs switch` {/* #mastra-auth-orgs-switch */}

透過互動式提示切換活動組織。若已設定 `MASTRA_API_TOKEN` 或 `MASTRA_ORG_ID` 環境變數，則無法使用。

### `mastra auth tokens` {/* #mastra-auth-tokens */}

列出所有 API 權杖及其最近使用日期。

#### `mastra auth tokens create` {/* #mastra-auth-tokens-create */}

建立新的 API 權杖。金鑰只顯示一次，之後無法再次獲取。

```bash
mastra auth tokens create <name>
```

使用 `--permission` 為權杖授予額外權限。目前可用的權限是 `databases:write`，可用於在 CI 等環境中建立和刪除託管資料庫。只有組織管理員能建立帶權限的權杖。重複傳入此選項可授予多項權限。

如果平台建立的權杖缺少所請求的權限，命令會撤銷該權杖並報錯退出。如果撤銷也失敗，錯誤資訊會給出需要執行的 `mastra auth tokens revoke` 命令。

```bash
mastra auth tokens create ci --permission databases:write
```

#### `mastra auth tokens revoke` {/* #mastra-auth-tokens-revoke */}

撤銷 API 權杖。

```bash
mastra auth tokens revoke <token-id>
```

## `mastra connect` {/* #mastra-connect */}

管理已關聯平台專案的 Provider 連線，使使用 `@mastra/connect` 的 Agent 無需離開終端機即可獲取 Provider 工具集。

命令使用你透過 `mastra auth login` 登錄的組織。可用 `mastra auth orgs switch` 切換組織。

目標專案依次從 `--project` 選項、環境變數 `MASTRA_PROJECT_ID`，或 `.mastra-project.json`（由 `mastra deploy` 寫入）中確定。所有子命令均支援 `--project <name|slug|id>`。

### `mastra connect list` {/* #mastra-connect-list */}

列出 Provider，已連線的排在前面。活動連線顯示為綠色，需重新授權的顯示為黃色，未連線的 Provider 顯示為灰色。尚不可用的 Provider 標記為即將推出。

```bash
mastra connect list
```

### `mastra connect add` {/* #mastra-connect-add */}

將 Provider 連線到專案。如果組織內已有該 Provider 的連線但尚未附加到專案，命令會列出連線，供你選擇附加現有連線或建立新連線。若沒有現有連線，則直接進入 Provider 認證流程。

OAuth Provider 會在瀏覽器中開啟授權同意頁面，並顯示 URL 供手動開啟。使用 API Key 或 Basic Auth 的 Provider 會在終端機提示輸入憑證，驗證後才完成連線。其他認證類型的 Provider 會開啟託管連線頁面。命令會等待連線變為活動狀態後退出。

即使使用 `--yes`，輸入憑證仍需要互動式終端機。請在 CI 外執行此命令，或透過平台介面連線。各 Provider 的[整合頁面](/docs/mastra-platform/connect#providers)列出了所需的 API Key 和權限。

新連線啟用後，命令會提供設定顯示名稱的選項，便於區分同一 Provider 的不同連線。它會列出現有連線，建議一個不衝突的名稱；若所選名稱重複，則要求確認。留空可跳過命名。設定顯示名稱需要組織管理員角色；命名失敗不會使連線失效。

```bash
mastra connect add <provider>
```

傳入 `--yes` 可跳過所有提示。即使已有連線可以復用，此選項仍會建立一個沒有顯示名稱的新連線。

### `mastra connect remove` {/* #mastra-connect-remove */}

解除 Provider 連線與專案的關聯。組織級連線會保留，之後可重新附加。

```bash
mastra connect remove <provider>
```

如果一個 Provider 有多個連線，命令會提示選擇要移除的連線。傳入 `--yes` 可跳過確認。沒有終端機或使用 `--yes` 時，若要一次移除多個連線，必須傳入 `--all`；`--connection <id>` 只移除一個。

### 替換需要重新授權的連線 {/* #replace-a-connection-that-needs-reauthorization */}

`mastra connect list` 會標記需要重新授權的連線，例如 Provider API Key 被撤銷後。解析 Connect 工具時會跳過這些連線併發出警告。

先解除受影響連線，再添加新連線：

```bash
mastra connect remove posthog
mastra connect add posthog
```

如果專案有多個連線，移除時請選擇受影響的連線。當 `add` 提示復用組織連線時，選擇 **Create a new connection**，並使用有效憑證授權。

## `mastra traces import` {/* #mastra-traces-import */}

將受支援的可觀測性 Provider 的歷史追蹤導入現有 Mastra Platform 專案。命令會在本地準備完整追蹤，按完整追蹤批量上傳，支援續傳，並透過 Mastra Platform 抽樣驗證。

```bash
mastra traces import <provider> [options]
```

目前支援以下 Provider：

| Provider | 參數 | 要求 |
| - | - | - |
| Langfuse | `langfuse` | Langfuse Cloud 或自行託管的 Langfuse v4 及以上版本 |

完整流程、資料對應、本地檔案生命週期與限制，請參閱[導入現有追蹤](/docs/mastra-platform/observability#import-existing-traces)。

### 選項 {/* #options */}

#### `--target-project <name|slug|id>` {/* #--target-project-nameslugid */}

選擇接收追蹤的目標 Mastra Platform 專案，優先於 `MASTRA_PROJECT_ID`。兩者均未提供時，命令使用 `.mastra-project.json` 中關聯的專案。來源專案由 Provider 憑證確定，例如 `LANGFUSE_PUBLIC_KEY` 和 `LANGFUSE_SECRET_KEY`。

#### `--since <date>` {/* #--since-date */}

將導入時間區間的起點（含）設為 ISO 8601 日期或時間戳。預設是 `--until` 前 30 天，但不會早於平台目前 30 天的保留邊界。`--from` 是別名。

#### `--until <date>` {/* #--until-date */}

將導入時間區間的終點（不含）設為 ISO 8601 日期或時間戳。預設是導入開始時間，不能晚於目前時間。`--to` 是別名。

整個時間區間必須位於平台目前 30 天的保留期內，`--since` 必須早於 `--until`，且窗口不得超過 30 天。

#### `--dry-run` {/* #--dry-run */}

讀取來源並在本地準備有效追蹤，不上傳。命令會寫入報告，並顯示用於繼續已準備導入的命令。

#### `--resume <import-id>` {/* #--resume-import-id */}

使用已保存的 Provider、目標專案、日期窗口和已確認進度，繼續已準備的導入。目標專案必須與生成的續傳命令中顯示的一致。不能與 `--since`、`--until` 或 `--dry-run` 同時使用。

#### `-y, --yes` {/* #-y---yes-4 */}

無需確認即可上傳。

### 環境變數 {/* #environment-variables */}

命令從目前目錄載入 `.env` 和 `.env.local`。

| 變數 | 必填條件 | 說明 |
| - | - | - |
| `LANGFUSE_PUBLIC_KEY` | 新建 Langfuse 導入時 | 專案的公開 API Key。與金鑰配合，用於選擇來源 Langfuse 專案。 |
| `LANGFUSE_SECRET_KEY` | 新建 Langfuse 導入時 | 專案的私有 API Key。 |
| `LANGFUSE_BASE_URL` | 否 | Langfuse 主機，預設為 `https://cloud.langfuse.com`。 |
| `MASTRA_API_TOKEN` | 無互動認證時 | Mastra Platform API 權杖。未設定時，命令使用 `mastra auth login` 保存的憑證。 |
| `MASTRA_ORG_ID` | 使用 `MASTRA_API_TOKEN` 時 | 目標專案所屬的組織。 |
| `MASTRA_PLATFORM_ACCESS_TOKEN` | 互動登錄後上傳和回讀時 | 目標 Mastra Platform 的訪問權杖。使用 `--dry-run` 或已設定 `MASTRA_API_TOKEN` 時無需提供。 |
| `MASTRA_PROJECT_ID` | 未透過其他方式關聯專案時 | 目標專案 ID。`--target-project` 選項優先於此變數。 |

### 範例 {/* #examples-1 */}

預覽預設的 30 天窗口，不上傳資料：

```bash
mastra traces import langfuse --target-project my-mastra-project --dry-run
```

無需確認提示，導入較短的時間區間：

```bash
mastra traces import langfuse \
  --target-project my-mastra-project \
  --since "$SINCE" \
  --until "$UNTIL" \
  --yes
```

繼續已有的導入：

```bash
mastra traces import langfuse \
  --resume 00000000-0000-0000-0000-000000000000 \
  --target-project my-mastra-project
```

## `mastra api` {/* #mastra-api */}

以 JSON 輸入和輸出呼叫 Mastra 執行時伺服器。適用於本地開發伺服器、已部署的 Mastra 平台專案、自託管 Mastra 伺服器，以及託管的 Mastra Platform Observability API。

```bash
mastra api agent list
mastra api agent run weather-agent '{"messages":"What is the weather in London?"}'
mastra api tool execute get-weather '{"location":"San Francisco"}'
mastra api trace list '{"page":0,"perPage":20}'
```

使用 `mastra api <resource> <action> --help` 查看某個命令的範例。

### 輸出 {/* #output */}

成功回應以 JSON 寫入 `stdout`。單資源命令傳回：

```json
{ "data": {} }
```

列表命令傳回 `data` 陣列和分頁元資料：

```json
{ "data": [], "page": { "total": 0, "page": 0, "perPage": 0, "hasMore": false } }
```

錯誤以 JSON 寫入 `stderr`，並傳回非零退出碼：

```json
{
  "error": {
    "code": "SERVER_UNREACHABLE",
    "message": "Could not connect to target server",
    "details": {}
  }
}
```

退出碼反映請求是否成功，而非回應內容：

* `0`：伺服器傳回成功回應，包括空結果和報告現有狀態的載荷，例如工具結果提示紀錄已存在。即使工具傳回含 `error` 欄位的對象，命令仍以 `0` 退出，因此工具自行報告失敗時應檢查 `data` 載荷。
* `1`：請求失敗，例如伺服器不可達、JSON 輸入無效、資源不存在，或工具拋出錯誤。

即使讀取輸出的命令提前退出（如 `| head`），退出碼仍反映請求是否成功。

### 目標解析 {/* #target-resolution */}

對於執行時命令，目標伺服器按以下順序確定：

1. `--url <url>`：顯式指定遠程或自託管伺服器。
1. `http://localhost:4111`：本地的 `mastra dev` 伺服器。
1. `.mastra-project.json`：Mastra 平台專案。

CLI 從 `.mastra-project.json` 解析專案，或識別顯式指定的 Mastra 託管 Studio、Factory 或可觀測性 URL 時，會自動使用平台認證。localhost 和任意顯式指定的 `--url` 目標不會自動獲得憑證。透過 `--header` 傳入的標頭會傳送到任何目標，包括 localhost。

可觀測性命令（`trace`、`log`、`score` 和 `metric`）預設使用美國端點 `https://observability.mastra.ai`，而非專案部署 URL。Trace Intelligence 命令（`learning`）的方式相同，但使用 `https://output.signals.mastra.ai`。CLI 自動選擇任一託管目標時，按以下順序查找憑證：

1. 顯式指定的 `Authorization` 和 `X-Mastra-Project-Id` 標頭（透過 `--header` 傳入）。
1. 環境變數 `MASTRA_PLATFORM_ACCESS_TOKEN` 和 `MASTRA_PROJECT_ID`。
1. `.mastra-project.json` 中的專案元資料，用於確定專案 ID。
1. 最後使用 Mastra CLI 登錄權杖作為認證備援。

Learning 命令還會傳送 `X-Mastra-Organization-Id`，依次從顯式 `--header`、環境變數 `MASTRA_ORGANIZATION_ID` 或 `.mastra-project.json` 中獲取。

歐盟可觀測性資料保存在 `https://observability.eu.mastra.ai`。透過 `--url` 指定該可信主機時，它與預設美國端點採用相同的平台憑證解析方式：

```bash
mastra api --url https://observability.eu.mastra.ai trace list
```

需要覆蓋其他目標或憑證時，使用 `--url` 和 `--header`。

### Factory 命令 {/* #factory-commands */}

使用 `mastra api factory` 管理 Factory 專案、工作項、決策、待關注項和隊列健康狀態。這些命令與其他 `mastra api` 命令使用相同的 JSON 輸入輸出、認證、標頭、超時和目標解析規則。

列出目前組織可用的 Factory 專案：

```bash
mastra api factory project list
```

傳送受治理的工作項狀態轉換前，先檢查生成的請求 Schema：

```bash
mastra api factory work-item transition --schema
```

使用工作項目前修訂版本轉移它：

```bash
mastra api factory work-item transition <project-id> <work-item-id> '{"board":"work","stage":"planning","requestId":"00000000-0000-4000-8000-000000000000","cause":"manual","expectedRevision":1}'
```

使用 `mastra deploy` 部署專案後，生成的不含金鑰的 `.mastra-project.json` 可讓 CLI 定位託管的 Factory 執行個體、使用 Mastra CLI 憑證，並自動選擇已部署專案所屬組織。若顯式指定託管 Factory 的 `--url`，CLI 會先使用 `MASTRA_ORG_ID`（如果已設定），否則使用透過 `mastra auth orgs switch` 選中的組織。顯式的 `X-Mastra-Organization-Id` 標頭優先於兩者。部署前，或要指定本地、遠程、自託管 Factory 伺服器時，請使用 `--url`：

```bash
mastra api --url http://localhost:4111 factory project list
```

Factory 端點使用根路徑 `/web/factory/...`。`--server-api-prefix` 仍控制本地目標探測，但不會加到 Factory 請求路徑前。

### 選項 {/* #flags-13 */}

#### `--url <url>` {/* #--url-url */}

指定 Mastra 伺服器 URL。

```bash
mastra api --url https://example.com agent list
```

#### `--server-api-prefix <prefix>` {/* #--server-api-prefix-prefix */}

設定目標伺服器的 API 路由前綴，預設為 `/api`。伺服器掛載在自定義前綴下時可使用此選項，例如 `@mastra/fastify` 的 `MastraServer` 使用 `prefix: "/api/mastra-studio"`。其用法與 `mastra studio` 的 `--server-api-prefix` 相同。也可改設環境變數 `MASTRA_API_PREFIX`。

```bash
mastra api --url https://example.com --server-api-prefix /api/mastra-studio agent list
```

#### `--header <"Key: Value">` {/* #--header-key-value */}

傳送自定義 HTTP 標頭。可重複傳入以傳送多個標頭。

```bash
mastra api --url https://example.com --header "Authorization: Bearer $TOKEN" agent list
```

#### `--timeout <ms>` {/* #--timeout-ms */}

設定請求超時，單位為毫秒，預設為 `30000`。Workflow 執行的啟動和恢復命令預設使用 `120000`。

#### `--pretty` {/* #--pretty */}

美化 JSON 輸出，預設為 `false`。

#### `--schema` {/* #--schema */}

顯示接受 JSON 輸入的命令所相應的 CLI 請求 Schema。Schema 來自目標伺服器的路由契約，包含命令結構、位置參數、範例、請求 Schema 和回應結構。

`--schema` 可用於接受 JSON 輸入的葉子命令，不能作為頂層 `mastra api` 選項使用。

```bash
mastra api agent run --schema
mastra api tool execute --schema
```

### 輸入模型 {/* #input-model */}

接受輸入的命令只接收一個行內 JSON 參數，不支援檔案路徑或標準輸入。

```bash
mastra api workflow run start data-pipeline '{"inputData":{"source":"s3://bucket/data.csv"}}'
```

穩定的 ID 使用位置參數；篩選條件或載荷使用 JSON。路由同時需要查詢參數和要求本文時，傳入單個 JSON 對象。CLI 會根據伺服器路由 Schema 拆分輸入。

```bash
mastra api thread create '{"agentId":"weather-agent","resourceId":"user_123","threadId":"thread_abc123","title":"Support conversation"}'
```

目標路由支援分頁時，列表命令可在 JSON 輸入中使用 `page` 和 `perPage`：

```bash
mastra api score list '{"page":0,"perPage":50}'
mastra api trace list '{"page":0,"perPage":20}'
```

支援篩選的路由可在同一個 JSON 輸入中提供篩選條件。例如，可觀測性追蹤列表同時支援分頁和該路由提供的篩選條件：

```bash
mastra api trace list '{"page":0,"perPage":20,"filters":{"spanType":"agent"}}'
```

#### `mastra api trace query` {/* #mastra-api-trace-query */}

使用對追蹤欄位和相關 span 的遞歸謂詞，查詢已完成的可觀測性追蹤。行內 JSON 輸入必填，結構與 SDK 和 HTTP API 相同。與其他可觀測性命令一樣，預設目標為 `https://observability.mastra.ai`。可傳入 `--url http://localhost:4111` 查詢本地伺服器。

```bash
mastra api trace query <input>
mastra api trace query '{"timeRange":{"from":"2026-08-01T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"}}'
```

可用以下命令查看該命令：

```bash
mastra api trace query --help
```

支援的欄位、運算符和請求選項詳見[查詢追蹤](/reference/observability/tracing/advanced-queries#query-traces)。對於本地 Mastra 伺服器，還可檢查請求與回應 Schema：

```bash
mastra api --url http://localhost:4111 trace query --schema
```

Mastra Platform 目前不提供 `--schema` 使用的 Schema 端點。若要查找專案中紀錄的欄位和值，請使用[欄位和值發現功能](/reference/observability/tracing/advanced-queries#discover-fields-and-values)。

回應繼續嵌套在 `data` 下，以保留游標分頁資訊：

```json
{
  "data": {
    "traces": [],
    "page": { "next": "opaque-cursor" }
  }
}
```

每次呼叫只執行一次查詢。下一次查詢時，將非空的 `data.page.next` 值作為 `page.after` 傳回。分頁模式、游標處理與錯誤詳見[分頁與錯誤](/reference/observability/tracing/advanced-queries#pagination-and-errors)。

先載入編號分頁結果，再輪詢增量時，兩次請求須使用相同的時間範圍和謂詞：

```bash
mastra api trace query '{"timeRange":{"from":"2026-08-01T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"pagination":{"page":0,"perPage":100}}'
mastra api trace query '{"timeRange":{"from":"2026-08-01T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"mode":"delta","after":"CURSOR_FROM_NUMBERED_RESPONSE","limit":100}'
```

將 `CURSOR_FROM_NUMBERED_RESPONSE` 替換為第一次回應中的 `data.deltaCursor`。增量結果仍位於 `data` 下，包含 `traces`、`delta: { limit, hasMore }` 和 `deltaCursor`。按 `traceId` 合併追蹤，保留每次傳回的游標；當 `data.delta.hasMore` 為 `true` 時立即繼續。增量模式不能與 `page`、`pagination` 或 `orderBy` 混用。

省略 `after` 會建立游標，但不會傳回歷史追蹤。改變時間範圍或謂詞時必須重新發起編號分頁請求。若用此流程維護本地追蹤列表，請先閱讀[增量輪詢限制](/reference/observability/tracing/advanced-queries#poll-after-loading-a-numbered-page)。

#### `mastra api trace aggregate` {/* #mastra-api-trace-aggregate */}

按時間範圍和可選的 `where` 謂詞對追蹤分組，傳回每組一行度量值；設定 `interval` 時，每組每個非空時間桶傳回一行。行內 JSON 輸入必填，支援與 `trace query` 相同的謂詞。與其他可觀測性命令一樣，預設目標為 `https://observability.mastra.ai`。

```bash
mastra api trace aggregate <input>
mastra api trace aggregate '{"timeRange":{"from":"2026-08-01T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"groupBy":["entityName"],"measures":["count","errorRate"]}'
```

將 `interval` 設為 `1m`、`5m`、`15m`、`1h` 或 `1d`，可將每組拆分為時間桶：

```bash
mastra api trace aggregate '{"timeRange":{"from":"2026-08-01T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"where":{"op":"eq","left":{"path":"entityName"},"right":{"literal":"weather-agent"}},"interval":"1d","measures":["count","duration.p95"]}'
```

維度、度量和請求選項詳見[聚合追蹤](/reference/client-js/observability#aggregate-traces)。更多範例可執行 `mastra api trace aggregate --help`。

響應保持嵌套在 `data` 下，以保留 `truncated`。當 `truncated` 為 `true` 時，表示匹配組數超過 `limit`：

```json
{
  "data": {
    "rows": [
      {
        "dimensions": { "entityName": "weather-agent" },
        "measures": { "count": 42, "errorRate": 0.05 }
      }
    ],
    "truncated": false
  }
}
```

如果伺服器的可觀測性儲存不支援追蹤聚合，會傳回 `501`。CLI 會像處理其他請求失敗一樣，顯示 `HTTP_ERROR`，並將伺服器回應放在 `error.details.body` 中。

#### `mastra api span query` {/* #mastra-api-span-query */}

跨追蹤查詢已完成的可觀測性 span，包括嵌套在其他追蹤中的 Agent 執行和工具呼叫。行內 JSON 輸入必填，結構與 [`querySpans()`](/reference/observability/tracing/advanced-queries#query-spans) 相同。`where` 謂詞直接篩選 span 欄位。與其他可觀測性命令一樣，預設目標為 `https://observability.mastra.ai`。

```bash
mastra api span query <input>
mastra api span query '{"timeRange":{"from":"2026-08-07T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"where":{"op":"and","args":[{"op":"eq","left":{"path":"spanType"},"right":{"literal":"tool_call"}},{"op":"eq","left":{"path":"status"},"right":{"literal":"error"}}]}}'
```

回應保持嵌套在 `data` 下，結構為 `{ "spans": [], "page": { "next": "opaque-cursor" } }`。下一次查詢時，將非空的 `data.page.next` 作為 `page.after` 傳回，並保持相同的時間範圍、謂詞和排序。更多範例可執行 `mastra api span query --help`。

不支援 span 查詢的可觀測性儲存會傳回 `501`。若儲存不支援身份、上下文、父級或根實體欄位的篩選，會傳回 `422`。使用前可查看伺服器可觀測性能力中的 `spanQueryContextFields`。CLI 會將兩者顯示為 `HTTP_ERROR`，伺服器回應位於 `error.details.body`。

#### `mastra api span aggregate` {/* #mastra-api-span-aggregate */}

按時間範圍和可選的 `where` 謂詞對 span 分組，傳回每組一行度量值；設定 `interval` 時，每組每個非空時間桶傳回一行。支援固定度量以及 `interval`、`having`、`orderBy` 和 `limit`，與 `trace aggregate` 一致。其 `where` 直接篩選 span，維度和 `countDistinct` 欄位遵循 span 契約。可按 `spanType`、`entityName`、`status` 和 `rootEntityName` 等 span 欄位分組。

```bash
mastra api span aggregate <input>
mastra api span aggregate '{"timeRange":{"from":"2026-08-01T00:00:00.000Z","to":"2026-08-08T00:00:00.000Z"},"where":{"op":"eq","left":{"path":"spanType"},"right":{"literal":"tool_call"}},"groupBy":["entityName"],"measures":["count","errorRate","duration.p95"],"orderBy":{"field":"errorRate","direction":"desc"},"limit":10}'
```

Token 與成本度量只統計紀錄用量的 span，通常是 `model_generation`；不會累加到 `agent_run` 等父 span。span 維度、度量和限制詳見[聚合 span](/reference/observability/tracing/advanced-queries#aggregate-spans)。更多範例可執行 `mastra api span aggregate --help`。

與 `trace aggregate` 一樣，命令會將 `rows` 和 `truncated` 輸出在 `data` 下。如果可觀測性儲存不支援 span 聚合，CLI 會將伺服器的 `501` 響應顯示為 `HTTP_ERROR`。

#### `mastra api score create` {/* #mastra-api-score-create */}

為追蹤建立評分。紀錄須包裝在 `score` 中，其中 `traceId` 必填、`spanId` 可選。省略 ID 和時間戳時，CLI 會自動生成，並在重試間保持不變。傳入 `--schema` 可查看請求欄位。

```bash

```

建立評分和反饋時，可傳入可選的頂層 `contextMode`。設為 `"resolve"` 會從已儲存的追蹤或 span 查找上下文；設為 `"provided"` 則直接寫入提供的欄位，不進行查找。省略 `contextMode` 時，無論提供了哪些上下文欄位，OSS 使用 `provided`，Platform 使用 `resolve`。

Platform 上寫入成功表示紀錄已被接受並待儲存，未必立即可讀。輸出會保留伺服器的成功回應，以及傳回的 ID 和時間戳。舊版伺服器可能只傳回 `success`。

## 遙測 {/* #telemetry */}

預設情況下，Mastra 會收集專案遙測資料，包括作業系統、Mastra 版本和 Node.js 版本。伺服器事件還包含下述專案識別碼。可閱讀 [CLI 遙測原始碼](https://github.com/mastra-ai/mastra/blob/main/packages/cli/src/analytics/index.ts)瞭解 CLI 收集的內容。

透過 `mastra dev`、`mastra start` 或 `mastra build` 輸出啟動的伺服器如果設定了可觀測性，Mastra 會統計該伺服器程式內每次模型呼叫消耗的輸入與輸出 token。每隔 15 分鐘，以及伺服器關閉時，會按自上次報告以來使用過的 Provider 和模型分別傳送 `mastra_model_token_usage_v2` 事件。如果期間沒有完成模型呼叫，則不傳送。每個事件包含自上次報告以來的 token 用量、報告時間區間的起止時間、報告原因（`interval` 或 `shutdown`）、命令（`dev`、`start`，或直接執行建置輸出時的 `server`）以及 `NODE_ENV`。不會傳送提示詞、回應或其他訊息內容。可閱讀[模型用量遙測原始碼](https://github.com/mastra-ai/mastra/blob/main/packages/core/src/telemetry/model-usage-telemetry.ts)瞭解收集內容。

為兼容舊版分析，伺服器啟動時還會傳送舊的 `mastra_model_token_usage` 事件。它從可觀測性儲存讀取 token 總量，並傳送自 `~/.mastra/usage-telemetry.json` 中保存的游標以來新增的用量。可閱讀[啟動用量遙測原始碼](https://github.com/mastra-ai/mastra/blob/main/packages/core/src/telemetry/usage-telemetry.ts)瞭解收集內容。

伺服器啟動時，Mastra 會傳送專案功能概況快照，包含組件數量、功能開關和粗略的儲存後端類別，但不包含組件名稱或識別碼。可閱讀[功能遙測原始碼](https://github.com/mastra-ai/mastra/blob/main/packages/core/src/telemetry/feature-telemetry.ts)瞭解收集內容。

伺服器事件 `mastra_feature_usage`、`mastra_model_token_usage` 和 `mastra_model_token_usage_v2` 包含：

* `project_id`：`MASTRA_PROJECT_ROOT` 的 SHA-256 雜湊值前 16 位十六進位字符；未設定時使用目前工作目錄。此識別碼也作為本地模型用量游標的鍵。
* `project_id2`：用於跨機器和部署關聯的可選識別碼。若去除首尾空格後的 `MASTRA_PROJECT_ID` 是 UUID 格式，會在前面加上 `mp_` 並**未經雜湊**傳送。搜索 `mp_<platform-project-id>` 可查找該專案的遙測。名稱、slug 和其他非 UUID 值不會作為平台識別碼傳送。

沒有 UUID 格式的平台 ID 時，`project_id2` 使用正規化 Git `origin` 遠端的 SHA-256 雜湊值前 16 位十六進位字符。正規化保留小寫主機名和儲存庫路徑，去除協議、憑證、連線埠、查詢參數、片段、末尾斜槓和 `.git` 後綴。等價的 SSH 與 HTTPS 遠端會生成相同識別碼。即使不同連線埠或 SSH 使用者指向不同儲存庫，只要主機和路徑相同，也會共用識別碼。本地檔案系統遠端不參與計算。Git 探測異步進行，結果會在程式內緩存，包括不可用的情況。兩種來源均不可用時，省略 `project_id2`。

這些伺服器事件並非匿名：平台 ID 可將事件關聯到專案；已知儲存庫 URL 也可正規化並雜湊後與 Git 派生事件匹配。對 Git 身份雜湊可避免傳送原始儲存庫 URL 或憑證，但無法阻止與公開或其他已知儲存庫進行關聯。

Studio UI 也會收集匿名的瀏覽器端使用分析，如頁面瀏覽和介面互動。可閱讀[原始碼](https://github.com/mastra-ai/mastra/blob/main/packages/playground/src/lib/analytics.tsx)瞭解收集內容。設定 `MASTRA_TELEMETRY_DISABLED` 也會禁用此項：該值注入服務頁面，因此對 `mastra dev` 和自託管建置均有效。

在啟動 Mastra 前設定此環境變數，可退出 CLI、伺服器和 Studio 的使用分析。禁用後，伺服器遙測不會查找 Git 遠端，也不會傳送任何專案識別碼：

```bash
MASTRA_TELEMETRY_DISABLED=1
```

使用其他 `mastra` 命令時，也可設定此變數：

```bash
MASTRA_TELEMETRY_DISABLED=1 mastra dev
```
