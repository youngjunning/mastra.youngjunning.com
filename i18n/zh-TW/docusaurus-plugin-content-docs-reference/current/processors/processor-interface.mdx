# Processor 介面

`Processor` 介面定義了 Mastra 中所有處理器都須遵循的約定。處理器可以實現一種或多種方法，以處理 Agent 執行流程的不同階段。

## 處理器方法的執行時機 {/* #when-processor-methods-run */}

如需了解準備階段、Agent 循環、工具執行和收尾階段的整體流程，請參閱 [Agent 生命週期指南](/docs/guides/agent-lifecycle)。

## 回呼時機 {/* #callback-timing */}

| 回呼或操作 | 頻率 | 執行位置與可見內容 |
| - | - | - |
| `processInput` | 每次初始請求執行一次 | 在循環開始前的輸入準備階段執行。從持久化快照恢復時可能跳過。 |
| `processInputStep` | 每個模型步驟執行一次 | 在請求 Provider 之前執行，可讀取先前累積的訊息和工具結果。 |
| `processLLMRequest` | 每次呼叫 Provider 執行一次 | 是改寫發給 Provider 的提示詞的最後一個處理器階段。對提示詞的改動不會寫回訊息清單。 |
| `processOutputStream` | 每個串流輸出區塊執行一次 | 在模型輸出到達時執行。處理器選擇接收資料區塊後，也會處理資料區塊。 |
| `processLLMResponse` | 每次 Provider 流完成後執行一次 | 接收目前模型步驟的完整回應。 |
| `processOutputStep` | 每個模型步驟執行一次 | 在模型回應之後、本機工具執行之前執行。 |
| 工具的 [`onInputStart`](/reference/tools/create-tool#oninputstart) | 串流工具輸入開始時 | 在完整工具參數可用之前執行。 |
| 工具的 [`onInputDelta`](/reference/tools/create-tool#oninputdelta) | 每個串流工具輸入區塊 | 觀察逐步到達的工具參數。 |
| 工具的 [`onInputAvailable`](/reference/tools/create-tool#oninputavailable) | 工具輸入完整時執行一次 | 在參數解析、驗證之後，執行工具之前執行。 |
| 工具執行 | 每次本機工具呼叫執行一次 | 接收即時的 [`RequestContext`](/docs/server/request-context)。核准或暫停可能延遲執行。 |
| 工具的 [`onOutput`](/reference/tools/create-tool#onoutput) | 本機執行成功後執行一次 | 接收工具輸出。 |
| `processToolResult` | 每個本機或使用者端結果，以及延遲到達的 Provider 結果 | 可在原始工具結果進入訊息清單前檢查、脫敏或中止處理。 |
| `processAPIError` | 出現符合條件的 Provider API 錯誤時 | 可更新請求狀態並要求再次呼叫 Provider。 |
| [`onIterationComplete`](/reference/agents/generate#parameters) | 每次循環迭代完成後執行一次 | 觀察迭代結果，並可影響是否繼續執行。 |
| `processOutputResult` | 收尾時執行一次 | 在回傳完整 Agent 結果前對其進行後處理。 |

## 介面定義 {/* #interface-definition */}

```typescript
interface Processor<TId extends string = string, TTripwireMetadata = unknown> {
  readonly id: TId
  readonly name?: string
  readonly description?: string
  /** Index of this processor in the workflow (set at runtime when combining processors). */
  processorIndex?: number
  /** When true, processOutputStream also receives `data-*` chunks. Default: false. */
  processDataParts?: boolean

  /** Span type to trace this processor as. Defaults to `PROCESSOR_RUN`. */
  readonly spanType?: ProcessorSpanType
  /** Span name, or a function returning one per pipeline phase. */
  readonly spanName?: string | ((phase: ProcessorSpanPhase) => string)
  /** Attributes set when the span is created, or a function returning them per phase. */
  readonly spanAttributes?:
    | Partial<SpanTypeMap[ProcessorSpanType]>
    | ((phase: ProcessorSpanPhase) => Partial<SpanTypeMap[ProcessorSpanType]>)

  /** Callback invoked when this processor detects a violation, regardless of strategy. */
  onViolation?: (violation: ProcessorViolation) => void | Promise<void>

  processInput?(
    args: ProcessInputArgs<TTripwireMetadata>,
  ): Promise<ProcessInputResult> | ProcessInputResult

  processInputStep?(
    args: ProcessInputStepArgs<TTripwireMetadata>,
  ):
    | Promise<ProcessInputStepResult | MessageList | MastraDBMessage[] | undefined | void>
    | ProcessInputStepResult
    | MessageList
    | MastraDBMessage[]
    | void
    | undefined

  /** State lane id for `computeStateSignal`. Defaults to the processor id. */
  stateId?: string

  computeStateSignal?(
    args: ComputeStateSignalArgs<TTripwireMetadata>,
  ): Promise<ComputeStateSignalResult> | ComputeStateSignalResult

  processLLMRequest?(
    args: ProcessLLMRequestArgs<TTripwireMetadata>,
  ): Promise<ProcessLLMRequestResult> | ProcessLLMRequestResult

  processLLMResponse?(
    args: ProcessLLMResponseArgs<TTripwireMetadata>,
  ): Promise<ProcessLLMResponseResult> | ProcessLLMResponseResult

  processAPIError?(
    args: ProcessAPIErrorArgs<TTripwireMetadata>,
  ): Promise<ProcessAPIErrorResult | void> | ProcessAPIErrorResult | void

  processOutputStream?(
    args: ProcessOutputStreamArgs<TTripwireMetadata>,
  ): Promise<ChunkType | null | undefined>

  processOutputStep?(args: ProcessOutputStepArgs<TTripwireMetadata>): ProcessorMessageResult

  processToolResult?(args: ProcessToolResultArgs<TTripwireMetadata>): ProcessorMessageResult

  processOutputResult?(args: ProcessOutputResultArgs<TTripwireMetadata>): ProcessorMessageResult
}
```

## 追蹤 {/* #tracing */}

每個處理器都會獲得一個按其執行階段命名的 span，例如 `input step processor: my-processor`。這個名稱說明 Mastra 如何執行處理器，卻不能說明處理器的用途；對於使用者並非以處理器形式設定的功能尤其不直觀。因此，Mastra 內置處理器會標明所屬子系統：workspace skill 的追蹤名稱是 `skill:inject`，訊息歷史的追蹤名稱是 `memory: recall` 和 `memory: save`。

在自定義處理器中聲明 `spanType`，也可以採用這種命名方式。處理器在多個階段執行時，各階段通常執行不同任務，因此 `spanName` 和 `spanAttributes` 也接受以階段為參數的函式：

```typescript title="src/mastra/processors/session-cache.ts"
import { SpanType } from '@mastra/core/observability'
import type { Processor, ProcessorSpanPhase } from '@mastra/core/processors'

const OPERATION: Partial<Record<ProcessorSpanPhase, 'recall' | 'save'>> = {
  inputStep: 'recall',
  output: 'save',
}

export class SessionCacheProcessor implements Processor<'session-cache'> {
  readonly id = 'session-cache' as const

  readonly spanType = SpanType.MEMORY_OPERATION
  readonly spanName = (phase: ProcessorSpanPhase) => `memory: ${OPERATION[phase] ?? 'recall'}`
  readonly spanAttributes = (phase: ProcessorSpanPhase) => ({
    operationType: OPERATION[phase] ?? 'recall',
  })
}
```

聲明 span 類型會替換 `PROCESSOR_RUN`，但 span 仍保留實體類型和執行時屬性，因此仍能記錄處理器執行階段、在處理器鏈中的位置，以及對訊息清單所做的更改。未聲明這些屬性的處理器不受影響。

如果某些值只有執行時才能確定，可在方法內部更新該處理器自己的 span：

```typescript oxfmt:false
async processInputStep({ messageList, tracingContext }: ProcessInputStepArgs) {
  tracingContext?.currentSpan?.update({ attributes: { messageCount: messageList.get.all.db().length } });
  return { messageList };
}
```

## 訊息參數 {/* #message-arguments */}

大多數處理器方法同時接收 `messages` 和 `messageList`。兩者指向同一段對話，但提供不同的存取方式。

### `messages` 與 `messageList` {/* #messages-vs-messagelist */}

- `messages`：目前階段的 `MastraDBMessage` 陣列。處理輸入時，`processInput` 和 `processInputStep` 不包含系統訊息；處理輸出時，`processOutputResult` 和 `processOutputStep` 包含最新的 LLM 回應。該陣列由 `messageList` 支撐，因此就地修改訊息的 `content.parts` 後，下游處理器和持久化結果也能看到更改。
- `messageList`：支援本次執行的即時 `MessageList` 實例。它提供按輸入、回應、記憶和全部訊息篩選的視圖，db、ui、core 等輸出格式，以及修改對話的方法。

僅需讀取、對訊息進行映射或小幅修改目前階段的訊息欄位時，使用 `messages`。以下情況使用 `messageList`：

- 讀取其他階段的訊息，例如處理輸出時讀取輸入訊息。
- 新增、刪除或替換整條訊息。
- 將訊息轉換為 UI 或 core 等格式，以供第三方 API 使用。

`messages` 始終從 `messageList` 衍生，因此新增、刪除或重新排序訊息的規範做法是修改 `messageList`。如果只是就地修改訊息內容（例如改寫 `content.parts`），直接修改 `messages` 效果相同。若回傳新的 `messages` 陣列，Mastra 會針對目前階段將其與 `messageList` 協調同步。

### 持久化 {/* #persistence */}

啟用 memory 後，只有所有處理器執行完畢後留在 `messageList` 中的內容才會儲存。以下兩種回傳方式在持久化方面效果相同：

- 直接修改 `messageList`（或回傳同一個 `MessageList` 實例）時，記錄的修改會就地生效，儲存的對話會反映這些更改。
- 回傳 `MastraDBMessage[]` 或 `{ messages, systemMessages }` 時，Mastra 會針對目前階段將回傳的陣列與 `messageList` 協調同步，刪除缺失的訊息並替換系統訊息。

回傳另一個 `MessageList` 實例會報錯。始終修改傳入處理器的實例。

### 從訊息中讀取文字 {/* #reading-text-from-a-message */}

`MastraDBMessage.content` 使用結構化物件，不支援字串。讀取使用者或助手文字的規範方式是存取 `content.parts`：

```typescript
import type { MastraDBMessage } from '@mastra/core/memory'

function getText(message: MastraDBMessage): string {
  let text = ''

  if (message.content.parts) {
    for (const part of message.content.parts) {
      if (part.type === 'text' && typeof part.text === 'string') {
        text += part.text
      }
    }
  }

  // Fallback for legacy messages that only have the flattened `content` string
  if (!text && typeof message.content.content === 'string') {
    text = message.content.content
  }

  return text
}
```

要點：

- `message.content.parts` 是主要資料來源。一條訊息可以包含多個 part。非文字 part 包括工具呼叫、工具結果和檔案 part。讀取 `part.text` 前，先用 `part.type === 'text'` 過濾。
- `message.content.content` 是為了向後相容而保留的扁平化字串。僅當 `parts` 為空或缺失時才用作回退方案。
- 對 `MastraDBMessage` 而言，`message.content` 本身絕不是純字串。舊版 `CoreMessage` 可能使用字串內容，但處理器接收的始終是 `MastraDBMessage`。

### `processInputStep` {/* #processinputstep */}

在 Agent 循環的每一步，將輸入訊息發送給 LLM 前進行處理。`processInput` 只在開始時執行一次，而此方法每一步都會執行，包括工具呼叫後的繼續執行。

```typescript oxfmt:false
processInputStep?<TTripwireMetadata = unknown>(
  args: ProcessInputStepArgs<TTripwireMetadata>,
):
  | Promise<ProcessInputStepResult | MessageList | MastraDBMessage[] | void | undefined>
  | ProcessInputStepResult
  | MessageList
  | MastraDBMessage[]
  | void
  | undefined;
```

#### Agent 循環中的執行順序 {/* #execution-order-in-the-agentic-loop */}

1. `processInput`（開始時執行一次）
2. 來自 inputProcessors 的 `processInputStep`（每一步呼叫 LLM 前）
3. `prepareStep` 回呼（作為 processInputStep 流程的一部分，在 inputProcessors 之後執行）
4. 來自 inputProcessors 的 `computeStateSignal`（在 `processInputStep` 之後、LLM 請求之前）
5. 來自 inputProcessors 的 `processLLMRequest`（提示詞轉換之後、呼叫 Provider 之前）
6. 執行 LLM
7. 來自 outputProcessors 的 `processOutputStream`（處理每個串流輸出區塊）
8. 來自 inputProcessors 的 `processLLMResponse`（流結束後，與 `processLLMRequest` 配合）
9. 來自 outputProcessors 的 `processOutputStep`（LLM 回應之後、工具執行之前）
10. 執行工具（如有需要）
11. 如果呼叫了工具，從第 2 步重新開始

#### 處理器串聯 {/* #processor-chaining */}

多個處理器實現 `processInputStep` 時，會依次執行，前一個處理器的改動會傳給下一個：

```text

Processor 2: receives { model: 'gpt-5.4-mini' } → returns { toolChoice: 'none' }

```

#### 系統訊息隔離 {/* #system-message-isolation */}

每一步開始時，系統訊息都會**重置為原始值**。`processInputStep` 中的修改只影響目前步驟，不會延續到後續步驟。

#### 適用場景 {/* #use-cases */}

- 達到設定的步驟數後停用工具
- 根據對話上下文動態新增或替換工具
- 在不同 Provider 之間轉換訊息 part 類型（例如將 `reasoning` 轉為 Anthropic 的 `thinking`）
- 根據步驟編號或累積的上下文修改訊息
- 新增目前步驟專用的系統指令
- 逐步調整 Provider 選項（例如快取控制）
- 根據目前步驟的上下文修改結構化輸出 schema

#### 去重 {/* #deduplication */}

```typescript title="src/mastra/processors/error-recovery.ts"
import { APICallError } from '@ai-sdk/provider'
import type { Processor, ProcessAPIErrorArgs, ProcessAPIErrorResult } from '@mastra/core/processors'

export class ErrorRecoveryProcessor implements Processor {
  id = 'error-recovery'

  processAPIError({
    error,
    messageList,
    retryCount,
  }: ProcessAPIErrorArgs): ProcessAPIErrorResult | void {
    // Only retry once
    if (retryCount > 0) return

    // Check for a specific API error
    if (APICallError.isInstance(error) && error.message.includes('context length exceeded')) {
      // Trim older messages to fit within context
      const messages = messageList.get.all.db()
      if (messages.length > 4) {
        messageList.removeByIds([messages[1]!.id, messages[2]!.id])
        return { retry: true }
      }
    }
  }
}
```

#### 回傳值 {/* #return-value-2 */}

`processOutputStream` 回傳 `Promise<ChunkType | null | undefined>`。

- 回傳 `ChunkType` 可發出該區塊。回傳原始 `part` 可原樣發出；回傳新的 `ChunkType` 可發出修改後的區塊。
- 回傳 `null` 會丟棄該區塊，不會發送給下一個處理器或用戶端。
- 回傳 `undefined` 也會丟棄該區塊，包括 `return;` 隱式回傳的 `undefined` 或方法執行到末尾時的情況。`null` 與 `undefined` 的效果相同。

丟棄一個區塊只影響該區塊；流會繼續，後續區塊仍會被處理。若要徹底停止流，請呼叫 `abort()`。

#### 發出第二個區塊 {/* #emitting-a-second-chunk */}

`processOutputStream` 一次只回傳一個區塊，但處理器有時需要針對一個輸入發出兩個區塊，例如先發出暫存的文字，再發出觸發釋放它的區塊。回傳第一個區塊，並將第二個區塊以 `REPROCESS_PART_KEY` 為鍵存入 `state`。Mastra 會緊接著回傳的區塊發出暫存區塊。

暫存區塊會再次經過輸出處理器，包括暫存它的處理器，因此該處理器必須在第二次處理時原樣放行：

```typescript title="src/mastra/processors/sign-off.ts"
import { REPROCESS_PART_KEY } from '@mastra/core/processors'
import type { ChunkType } from '@mastra/core/stream'
import type { ProcessOutputStreamArgs, Processor } from '@mastra/core/processors'

export class SignOff implements Processor<'sign-off'> {
  readonly id = 'sign-off'

  async processOutputStream({ part, state }: ProcessOutputStreamArgs): Promise<ChunkType> {
    if (part.type !== 'text-end' || state.signed) return part
    state.signed = true
    state[REPROCESS_PART_KEY] = part
    return { ...part, type: 'text-delta', payload: { id: part.payload.id, text: '\n\nCheers!' } }
  }
}
```

## 處理器類型 {/* #processor-types */}

Mastra 提供類型別名，以確保處理器實現必需的方法：

```typescript
// Must implement processInput, processInputStep, processLLMRequest, or processLLMResponse (or any combination)
type InputProcessor = Processor &
  (
    | { processInput: required }
    | { processInputStep: required }
    | { processLLMRequest: required }
    | { processLLMResponse: required }
  )

// Must implement processOutputStream, processOutputStep, OR processOutputResult (or any combination)
type OutputProcessor = Processor &
  (
    | { processOutputStream: required }
    | { processOutputStep: required }
    | { processOutputResult: required }
  )

// Must implement processAPIError
type ErrorProcessor = Processor & { processAPIError: required }
```

將實現 `processAPIError` 的處理器設定在 `errorProcessors` 中：

```typescript
const agent = new Agent({
  id: 'agent',
  errorProcessors: [new PrefillErrorHandler()],
})
```

### 使用 `processInputStep` 的逐步驟處理器 {/* #per-step-processor-with-processinputstep */}

```typescript title="src/mastra/processors/dynamic-model.ts"
import type {
  Processor,
  ProcessInputStepArgs,
  ProcessInputStepResult,
} from '@mastra/core/processors'

export class DynamicModelProcessor implements Processor {
  id = 'dynamic-model'

  async processInputStep({
    stepNumber,
    steps,
    toolChoice,
  }: ProcessInputStepArgs): Promise<ProcessInputStepResult> {
    // Use a fast model for initial response
    if (stepNumber === 0) {
      return { model: '__GATEWAY_OPENAI_MODEL_LUNA__' }
    }

    // Switch to powerful model after tool calls
    if (steps.length > 0 && steps[steps.length - 1].toolCalls?.length) {
      return { model: '__GATEWAY_OPENAI_MODEL__' }
    }

    // Disable tools after 5 steps to force completion
    if (stepNumber > 5) {
      return { toolChoice: 'none' }
    }

    return {}
  }
}
```

### 同時處理輸入和輸出的處理器 {/* #hybrid-processor-input-and-output */}

```typescript title="src/mastra/processors/content-filter.ts"
import type { Processor } from '@mastra/core/processors'
import type { MastraDBMessage } from '@mastra/core/memory'
import type { ChunkType } from '@mastra/core/stream'

export class ContentFilter implements Processor {
  id = 'content-filter'
  private blockedWords: string[]

  constructor(blockedWords: string[]) {
    this.blockedWords = blockedWords
  }

  async processInput({ messages, abort }): Promise<MastraDBMessage[]> {
    for (const msg of messages) {
      const text = msg.content.parts
        ?.filter(p => p.type === 'text')
        .map(p => p.text)
        .join(' ')

      if (this.blockedWords.some(word => text?.includes(word))) {
        abort('Blocked content detected in input')
      }
    }
    return messages
  }

  async processOutputStream({ part, abort }): Promise<ChunkType | null> {
    if (part.type === 'text-delta') {
      if (this.blockedWords.some(word => part.payload.text.includes(word))) {
        abort('Blocked content detected in output')
      }
    }
    return part
  }
}
```

### 使用狀態累積流內容 {/* #stream-accumulator-with-state */}

```typescript title="src/mastra/processors/word-counter.ts"
import type { Processor } from '@mastra/core/processors'
import type { ChunkType } from '@mastra/core/stream'

export class WordCounter implements Processor {
  id = 'word-counter'

  async processOutputStream({ part, state }): Promise<ChunkType> {
    // Initialize state on first chunk
    if (!state.wordCount) {
      state.wordCount = 0
    }

    // Count words in text chunks
    if (part.type === 'text-delta') {
      const words = part.payload.text.split(/\s+/).filter(Boolean)
      state.wordCount += words.length
    }

    // Log word count on finish
    if (part.type === 'finish') {
      console.log(`Total words: ${state.wordCount}`)
    }

    return part
  }
}
```

## 狀態生命週期 {/* #state-lifecycle */}

每個處理器在 `processLLMRequest`、`processLLMResponse`、`processOutputStream`、`processOutputStep`、`processOutputResult` 和 `processAPIError` 中都會收到一個 `state` 物件。狀態有三個重要特性：

- **處理器獨立**：每個處理器都有以其 `id` 為鍵的獨立 `state` 物件。不同 ID 的處理器無法讀取或覆蓋彼此的狀態。
- **請求獨立**：每次呼叫 `agent.generate()` 或 `agent.stream()` 時都會創建新的狀態物件，不會在請求或使用者之間洩漏。
- **跨方法共享**：同一請求中，同一個 `state` 物件會傳給 `processLLMRequest`（呼叫 Provider 前）、`processLLMResponse`（步驟完成後）、`processOutputStream`（每個輸出區塊）、`processOutputStep`（每個 LLM 步驟後）、`processOutputResult`（結束時一次），以及 `processAPIError`（LLM 呼叫失敗時）。例如，`processLLMRequest` 可存入快取鍵，`processLLMResponse` 再讀取它並寫入回應。

`state` 初始為空物件，因此首次存取欄位時應做好初始化：

```typescript
import type { Processor } from '@mastra/core/processors'

export class WordCounter implements Processor {
  id = 'word-counter'

  async processOutputStream({ part, state }) {
    state.wordCount ??= 0
    if (part.type === 'text-delta') {
      state.wordCount += part.payload.text.split(/\s+/).filter(Boolean).length
    }
    return part
  }
}
```

## 中止與 tripwire 區塊 {/* #aborting-and-tripwire-chunks */}

每個方法的 `abort` 函式都會拋出 `TripWire` 錯誤，停止處理，並在輸出流中發出 `tripwire` 區塊。用戶端可據此區分被阻止的回應與正常結束的回應。

```typescript
abort('Blocked content detected', { retry: false, metadata: { category: 'pii' } })
```

- `reason`：易於理解的原因說明，顯示在 `tripwire.payload.reason` 中。
- `retry`：設為 `true` 時，Agent 會將 `reason` 作為回饋並重試同一步驟。只有在 Agent 或單次呼叫中設定了 `maxProcessorRetries` 才會重試，否則請求會中止。未設定上限時的 `3` 次安全限制僅適用於 `processAPIError` 的錯誤處理器重試，不為 中止操作的重試提供次數。
- `metadata`：附加到 `tripwire` 區塊的可選結構化資料，供下游使用。

發出的 `tripwire` 區塊結構如下：

```typescript
type TripwireChunk = {
  type: 'tripwire'
  runId: string
  from: 'AGENT'
  payload: {
    reason: string
    retry?: boolean
    metadata?: unknown
    processorId: string
  }
}
```

非串流呼叫（`agent.generate()`）的結果通過 `result.tripwire` 和 `result.finishReason === 'other'` 提供相同資訊。

## 發出自定義資料區塊 {/* #emitting-custom-data-chunks */}

可以存取 `writer` 的處理器可呼叫 `writer.custom(chunk)`，將自定義 `data-*` 區塊以串流方式發送給用戶端。工具也可以通過自己的 writer 執行同樣操作。處理器若要發出常規文字區塊和工具區塊之外的內容，只能通過這種方式。

```typescript
await writer.custom({
  type: 'data-moderation',
  runId,
  from: 'AGENT',
  data: { level: 'warn', reason: 'Possibly unsafe' },
})
```

設定 memory 後，`processOutputStream` 或 `processOutputResult` 發出的自定義 `data-*` 區塊會作為助手訊息的一部分儲存。若只想串流發送而不儲存到 memory，請在區塊物件上設定 `transient: true`：

```typescript {4}
await writer.custom({
  type: 'data-progress',
  data: { status: 'Processing' },
  transient: true,
})
```

將 `transient` 作為區塊的屬性傳入，而不是作為 `writer.custom()` 的第二個參數。第二個參數用於傳入 `messageId` 等 writer 選項。

預設情況下，處理器在 `processOutputStream` 中**不會**看到 `data-*` 區塊，以免誤處理工具遙測資料或自身輸出。若要接收這些區塊，請在處理器上設定 `processDataParts: true`：

```typescript
class ModerationCollector implements Processor {
  id = 'moderation-collector'
  processDataParts = true

  async processOutputStream({ part, state }) {
    if (part.type === 'data-moderation') {
      state.warnings ??= []
      state.warnings.push(part.data)
    }
    return part
  }
}
```

區塊的 `type` 必須以 `data-` 開頭，才會被視為自定義資料區塊。從 `processOutputStream` 回傳 `null` 或 `undefined` 仍會丟棄該區塊，因此處理器可以像處理文字區塊一樣檢查、修改或過濾自定義資料。

## 在 Agent 上設定處理器 {/* #configuring-processors-on-an-agent */}

通過三個陣列將處理器附加到 Agent：

```typescript
import { Agent } from '@mastra/core/agent'
import { PrefillErrorHandler } from '@mastra/core/processors'

const agent = new Agent({
  id: 'support-agent',
  name: 'support-agent',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  instructions: '...',
  inputProcessors: [new ContentFilter(['secret'])],
  outputProcessors: [new WordCounter()],
  errorProcessors: [new PrefillErrorHandler()],
  maxProcessorRetries: 3,
})
```

- `inputProcessors`：在呼叫 LLM 前執行，接收輸入訊息。
- `outputProcessors`：在 LLM 回應期間或之後執行，接收輸出區塊或訊息。
- `errorProcessors`：LLM API 呼叫拋出錯誤時執行，接收原始錯誤。

每個陣列也接受函式，以便根據 `RequestContext` 為每次請求創建處理器：

```typescript
new Agent({
  id: 'processor-interface-agent',
  inputProcessors: ({ requestContext }) => {
    const blockedWords = requestContext.get('blockedWords') ?? []
    return [new ContentFilter(blockedWords)]
  },
})
```

### 單次呼叫覆蓋設定 {/* #per-call-overrides */}

`agent.generate()` 和 `agent.stream()` 接受 `inputProcessors`、`outputProcessors`、`errorProcessors` 及 `maxProcessorRetries`。只要在單次呼叫中設定了某個處理器陣列，它就會為該請求**替換** Agent 上設定的對應陣列。Mastra 自動新增的 memory、workspace、skill、channel 和 browser 處理器始終保留，並在你的陣列前後執行。

```typescript
await agent.stream('Summarize this', {
  outputProcessors: [new StreamFilter()],
  maxProcessorRetries: 5,
})
```

單次呼叫傳入的 `maxProcessorRetries` 會覆蓋 Agent 的預設值。如果兩處都未設定，輸入和輸出處理器要求的重試會被視為中止；錯誤處理器（如 [`StreamErrorRetryProcessor`](/reference/processors/stream-error-retry-processor)）則最多重試 3 次。
