# TokenCostControl

`TokenCostControl` 在 Agent 執行迴圈中實施費用上限，超過可設定的費用閾值時阻止執行或發出警告。

它透過 `processInputStep` 在每次 LLM 呼叫前檢查費用上限。所有作用範圍的費用資料都透過可觀測性儲存 API（`getMetricAggregate`）查詢。除 `run` 外，其他範圍會匯總可設定時間區間內多次執行的費用（預設視窗為 7 天）；`run` 範圍查詢當前 Trace 的費用。

如需按 Token 數量限制，請改用 `TokenLimiterProcessor`。

> **原名為 `CostGuardProcessor`。** `CostGuardProcessor` 導出及其 `CostGuard*` 選項和詳情類型仍可用，作為同一類的已棄用別名，處理器 ID 仍為 `'token-cost-control'`。請將導入改為 `TokenCostControl`。

支援以下六種作用範圍：

- **單次執行**：透過 Trace ID 追蹤一次 Agent 執行的費用
- **資源**（預設）：按 `resourceId` 追蹤跨執行的累計費用
- **執行緒**：按 `threadId` 追蹤跨執行的累計費用
- **使用者**：按 `userId` 追蹤跨執行的累計費用
- **組織**：按 `organizationId` 追蹤跨執行的累計費用
- **會話**：按 `sessionId` 追蹤跨執行的累計費用

> **費用控制是近似值。** 可觀測性流水線透過緩衝導出器非同步保存費用資料。執行速度較快的 Agent 可能在指標可供查詢之前就超過設定的上限。請將 `maxCost` 視為可能被快速執行的 Agent 超出的近似閾值。

> **僅歸屬 Agent 的費用。** 費用透過 `entityType: 'agent'` 指標篩選器歸屬。Agent 執行之外的模型呼叫（例如 Workflow 步驟直接使用模型）沒有 Agent 父級 Span，因此不會計入此防護器。

## 使用範例 {/* #usage-example */}

按資源追蹤累計費用（預設範圍）：

```typescript
import { TokenCostControl } from '@mastra/core/processors'

const tokenCostControl = new TokenCostControl({
  maxCost: 1.0,
})
```

按執行緒追蹤 24 小時視窗內的累計費用，並在達到上限的 80% 時發出軟性警告：

```typescript
import { TokenCostControl } from '@mastra/core/processors'

const tokenCostControl = new TokenCostControl({
  maxCost: 5.0,
  scope: 'thread',
  window: '24h',
  warnAtPercent: 80,
})
```

將函數傳給 `maxCost`，為不同等級設定預算：

```typescript
import { TokenCostControl } from '@mastra/core/processors'

const tokenCostControl = new TokenCostControl({
  maxCost: requestContext => (requestContext?.get('tier') === 'pro' ? 10.0 : 1.0),
  scope: 'user',
})
```

將處理器附加到 Agent，並設定 `onViolation` 回呼及按 Provider/模型細分的費用資料：

```typescript
import { Agent } from '@mastra/core/agent'
import { TokenCostControl } from '@mastra/core/processors'

const tokenCostControl = new TokenCostControl({
  maxCost: 5.0,
  scope: 'resource',
  window: '30d',
  strategy: 'warn',
  includeBreakdown: true,
})

tokenCostControl.onViolation = ({ detail }) => {
  console.log(
    `Cost ${detail.threshold} threshold for ${detail.scopeKey}: $${detail.usage}/$${detail.limit}`,
  )
  for (const entry of detail.breakdown ?? []) {
    console.log(`  ${entry.provider}/${entry.model}: $${entry.estimatedCost}`)
  }
}

const agent = new Agent({
  id: 'my-agent',
  name: 'my-agent',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  inputProcessors: [tokenCostControl],
})
```

## 錯誤行為 {/* #error-behavior */}

使用 `block` 策略（預設）時，費用超過上限後，`TokenCostControl` 會以 `retry: false` 呼叫 `abort()`。TripWire 中繼資料包含：

- `processorId`：`'token-cost-control'`
- `usage`：當前累計用量（`estimatedCost`、`costUnit`）
- `maxCost`：為請求解析出的費用上限
- `scope`：當前作用範圍
- `scopeKey`：非 run 範圍的標識符（如適用）
- `threshold`：始終為 `'hard'`，因為只有硬性上限會中止執行
- `breakdown`：按 Provider/模型細分的費用條目（僅當啟用 `includeBreakdown` 且明細查詢成功時）

使用 `warn` 策略時，每個請求至多觸發一次硬性上限警告和 `onViolation` 回呼。同一請求的後續步驟繼續執行，不會重復發出警告。

插入違規訊息的數字最多保留 6 位小數，因此訊息不會出現浮點精度造成的尾數。

## 作用範圍行為 {/* #scoping-behavior */}

| 範圍 | 是否跨執行追蹤 | 篩選條件 | 所需上下文 |
| - | - | - | - |
| `run` | 否 | 當前 Span 的 `traceId` | Trace 上下文（自動提供） |
| `resource` | 是 | `resourceId` + 時間區間 | `RequestContext` 中的 `resourceId` |
| `thread` | 是 | `threadId` + 時間區間 | `RequestContext` 中的 `threadId` |
| `user` | 是 | `userId` + 時間區間 | `RequestContext` 中的 `userId` 鍵 |
| `organization` | 是 | `organizationId` + 時間區間 | `RequestContext` 中的 `organizationId` 鍵 |
| `session` | 是 | `sessionId` + 時間區間 | `RequestContext` 中的 `sessionId` 鍵 |

所有作用範圍都要求可觀測性儲存支援 `getMetricAggregate`；如果未設定可觀測性儲存，Mastra 實例會在註冊時拋出錯誤。

對於 `run` 範圍，處理器從當前 Span 的 Trace 上下文讀取 Trace ID。如果沒有 Trace 上下文，就會跳過檢查（開放失敗）。

對於其他範圍，如果執行階段缺少所需的上下文 ID，也會跳過檢查。可觀測性查詢失敗時同樣採用開放失敗策略：透過 Mastra 記錄記錄警告，然後繼續執行該步驟。

> **`user`、`organization` 和 `session` 範圍需要帶有標注的 Trace。** 這些範圍透過指標記錄中的 `userId`、`organizationId` 和 `sessionId` 字段匹配費用，字段值來自 Trace 中的 Span 中繼資料（例如透過 Trace 選項中的 metadata 設定）。如果 Trace 中繼資料不匹配，就不會匹配到任何記錄，防護器也不會觸發。僅設定 RequestContext 鍵並不夠：必須同時提供 RequestContext 鍵（用於確定範圍）和 Span 中繼資料（用于歸屬費用）。

> **關於指標持久化延遲。** 可觀測性流水線使用緩衝導出器非同步寫出指標。LLM 呼叫結束後，其費用指標需要短暫時間才能供查詢。在高頻執行 Agent 時，費用控制可能要到實際超過閾值之後的一步或多步才檢測到超限。
