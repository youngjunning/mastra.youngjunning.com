# ProviderHistoryCompat

`ProviderHistoryCompat` 處理不同模型 Provider 之間的訊息歷史相容問題。它可以在呼叫 Provider 前重寫傳送給模型的提示詞，也可以在 API 發生錯誤後修復訊息歷史並重試。

當 Agent 可能切換模型 Provider，或跨 Provider 重複使用訊息歷史時，請使用此處理器。它也能處理 Provider 拒絕其他 Provider 產生之欄位的情況。

## 使用範例 {/* #usage-example */}

如果清單中沒有相同 `id` 的處理器，Mastra 預設會將此處理器加入每個 Agent 的 `errorProcessors`。在新增的預設處理器中，它排在第一位；其傳送給模型的提示詞規則會先於其他預設處理器執行，包括重試處理器直接重送請求的邏輯。若要加入自訂規則或自行決定順序，請傳入自己的實例：

```typescript title="src/mastra/agents/my-agent.ts"
import { Agent } from '@mastra/core/agent'
import { ProviderHistoryCompat } from '@mastra/core/processors'

export const agent = new Agent({
  id: 'my-agent',
  name: 'my-agent',
  instructions: 'You are a helpful assistant.',
  model: 'anthropic/claude-sonnet-4-5',
  errorProcessors: [new ProviderHistoryCompat({ additionalRules: [/* ... */] })],
})
```

傳入自己的 `ProviderHistoryCompat` 實例會取代預設實例。只有清單中沒有相同 `id` 的處理器時，才會加入預設實例。如果希望重寫提示詞的規則在輸入處理階段執行，可將實例放在 `inputProcessors`。

註冊位置決定處理器的哪些功能會執行：

* **反應式規則必須註冊至 `errorProcessors`。** Agent 會將輸入處理器包裝成單一處理器 Workflow，而 API 錯誤處理階段只會在錯誤處理器上呼叫 `processAPIError`。因此，只註冊至 `inputProcessors` 的實例不會執行反應式規則。
* **事前處理規則可在任一清單執行。** `processLLMRequest` 會依序執行輸入處理器與解析後的錯誤處理器，因此註冊至 `errorProcessors` 的 `ProviderHistoryCompat` 既會重寫提示詞，也能進行反應式復原。註冊至 `inputProcessors` 的實例則會在輸入位置執行一次。

如上例所示，只註冊至 `errorProcessors` 就能涵蓋兩類功能。重複註冊不會造成兩次重試：執行器會在第一個要求重試的處理器處停止；每條反應式規則在 `retryCount` 大於零時也會結束，因此修復後的輪次只會再嘗試一次。

## 內建規則 {/* #built-in-rules */}

`ProviderHistoryCompat` 包含以下內建相容規則：

| 規則 | Provider | 執行時機 | 行為 |
| - | - | - | - |
| `strip-foreign-provider-executed-tools` | Anthropic, OpenAI, Azure OpenAI, Google/Vertex | 事前重寫提示詞 | 若 Provider 執行的工具呼叫及配對結果來自另一類 Provider，就從傳送給模型的提示詞中移除，因為接收方無法解析其他 Provider 的工具 ID。已儲存的歷史不變。 |
| `anthropic-tool-id-format` | Anthropic | 事前重寫提示詞 | 在提示詞中重寫工具呼叫及其結果裡不符合 `[a-zA-Z0-9_-]` 的 ID。若清理後的 ID 與現有 ID 衝突，就依序加上 `_2`、`_3` 等後綴。這樣可避免 Provider 拒絕；已儲存的歷史仍保留原始 ID。對於事前檢查無法辨識的 Provider（如 Vertex 託管的 Claude），另有反應式備援。 |
| `cerebras-strip-reasoning-content` | Cerebras | 事前重寫提示詞 | 從傳送給模型的提示詞中移除助理的 `reasoning` 片段，避免序列化成不支援的 `reasoning_content` 欄位。 |
| `anthropic-strip-empty-signed-reasoning-content` | Anthropic | 反應式（比對 Anthropic 因思考區塊被修改而傳回的 400 錯誤） | 從較早的訊息中移除帶有 Anthropic 簽章、但文字為空的助理 `reasoning` 片段；舊記錄可能包含此類片段。只在 Anthropic 拒絕歷史後執行，因為 Claude 5.x 也會正常傳回帶簽章的空文字片段，必須原樣重播才能維持提示詞快取。 |
| `anthropic-strip-foreign-reasoning-content` | Anthropic | 事前重寫提示詞 | 從傳送給模型的提示詞中移除非 Anthropic 來源的助理 `reasoning` 片段，保留 Anthropic 原生的思考歷史。 |
| `anthropic-strip-foreign-signed-reasoning` | Anthropic-compatible | 事前重寫提示詞 | 當原始輪次標記為另一個 Provider（如 Kimi For Coding ↔ `__GATEWAY_ANTHROPIC_MODEL_SONNET__`）時，從傳送給模型的提示詞中移除帶簽章的思考內容，因為接收方無法驗證其他 Provider 的簽章。移除後沒有內容的輪次也會刪除；未標記來源的歷史不受影響。 |
| `azure-system-reminder-transform` | Azure OpenAI | 事前重寫提示詞 | 在傳送給模型的請求中，將使用者文字及系統指令裡的 `<system-reminder>` 包裝標籤改為 `<memory-context>`。已儲存的歷史不變。 |
| `openai-orphan-item-id` | OpenAI, Azure OpenAI (Responses) | 反應式 API 錯誤復原 | 修復 OpenAI 以 `Item 'msg_…' of type 'message' was provided without its required 'reasoning' item` 拒絕的歷史。對於含有 `itemId`、但沒有 `reasoning` 片段的助理訊息，移除其每個帶項目 ID 的片段上的 Responses `itemId`，然後重試。訊息於是依值重播，而不是作為無法滿足的 `item_reference`。修復只套用於目前輪次的記憶體訊息清單。 |
| `anthropic-orphaned-thinking-step` | Anthropic | 反應式 API 錯誤復原 | 修復 Anthropic 因最新助理訊息中的 `thinking` 或 `redacted_thinking` 區塊不可修改而拒絕的歷史。若純推理步驟之後還有其他助理內容，就移除這些步驟並重試。適用於舊版 `@mastra/memory` 儲存的歷史（[#22798](https://github.com/mastra-ai/mastra/issues/22798)）。 |
| `tool-call-empty-input` | 所有 Provider | 事前重寫提示詞 | 當已儲存的助理工具呼叫缺少輸入（`undefined` 或 `null`）時，在傳送給模型的提示詞中將其作為 `{}` 傳送，因為 Provider 會拒絕沒有輸入的工具呼叫（Anthropic：`tool_use.input: Field required`）。參數無法解析的呼叫會以這種方式儲存。呼叫仍保留配對的錯誤結果，已儲存的歷史不變。空字串是真實的已儲存值，會原樣傳送。 |
| `ensure-user-first-turn` | Amazon Bedrock, Google/Vertex Gemini | 事前重寫提示詞 | 在開頭的助理輪次前插入最簡使用者輪次（`.`），因為這些 Provider 會拒絕第一個非系統輪次來自助理的對話。Agent 先打招呼或 `lastMessages` 擷取討論串中段時會出現這種情況。此規則最後執行，因此會看到其他規則移除空輪次後的提示詞。 |

Mastra 將訊息轉換成模型提示詞格式後、傳送給 Provider 前，會透過 `processLLMRequest` 執行事前處理規則。這些重寫只影響目前的 Provider 呼叫；已儲存的歷史始終不變，因此記憶與 Studio 中的 ID 和內容保持原樣。

Provider 拒絕請求後，會透過 `processAPIError` 執行反應式規則。這些規則可更新持久化的 `messageList` 並要求重試。

`anthropic-tool-id-format` 同時實作兩類規則。其事前處理掛鉤通常能避免請求被拒絕，因此反應式掛鉤不會執行。詳見下文[工具呼叫 ID 的修復僅影響提示詞](#tool-call-id-repair-is-prompt-scoped)。

## `CompatRule` {/* #compatrule */}

一個 `CompatRule` 定義一項 Provider 歷史相容性修復：

```typescript
import type { CompatRule } from '@mastra/core/processors'

const removeUnsupportedPromptParts: CompatRule = {
  name: 'remove-unsupported-prompt-parts',
  applyToPrompt({ prompt, model }) {
    // Return a modified LanguageModelV2Prompt, or undefined to leave it unchanged.
    return undefined
  },
}
```

## 自訂規則 {/* #custom-rules */}

透過 `additionalRules` 傳入自訂規則。自訂規則會在內建規則之後執行：

```typescript title="src/mastra/agents/custom-provider-compat.ts"
import { Agent } from '@mastra/core/agent'
import { ProviderHistoryCompat, type CompatRule } from '@mastra/core/processors'

const stripUnsupportedAssistantMetadata: CompatRule = {
  name: 'strip-unsupported-assistant-metadata',
  applyToPrompt({ prompt, model }) {
    if (typeof model !== 'string' || !model.startsWith('example-provider/')) {
      return undefined
    }

    let changed = false
    const nextPrompt = prompt.map(message => {
      if (message.role !== 'assistant' || typeof message.content === 'string') {
        return message
      }

      const nextContent = message.content.map(part => {
        if (!('providerOptions' in part)) return part
        changed = true
        const { providerOptions: _providerOptions, ...rest } = part
        return rest
      })

      return { ...message, content: nextContent }
    })

    return changed ? nextPrompt : undefined
  },
}

export const agent = new Agent({
  id: 'custom-provider-agent',
  name: 'custom-provider-agent',
  instructions: 'You are a helpful assistant.',
  model: 'example-provider/model',
  inputProcessors: [
    new ProviderHistoryCompat({
      additionalRules: [stripUnsupportedAssistantMetadata],
    }),
  ],
})
```

對於不應寫入記憶的 Provider 專屬重寫，請使用 `applyToPrompt`。新規則通常應使用此掛鉤，內建規則也是如此。只有修復後的歷史必須儲存並供後續輪次重複使用，且無法事先避免 Provider 拒絕時，才應將 `fix` 與 `errorPatterns` 搭配使用。

## 工具呼叫 ID 的修復僅影響提示詞 {/* #tool-call-id-repair-is-prompt-scoped */}

Anthropic 要求 `tool_use.id` 符合 `^[a-zA-Z0-9_-]+$`。來自其他 Provider 的工具呼叫 ID 若包含 `.` 或 `:`，就會被拒絕。此規則會在傳送給模型的請求中清理這些 ID：

```typescript oxfmt:false
// What the provider receives
tool_use.id: 'call_abc_1'
// What stays in memory, in the returned messages, and in the Studio
toolCallId: 'call.abc:1'
```

`tool-call` 與配對的 `tool-result` 使用同一映射重寫，因此不會破壞兩者的對應關係。替換 ID 依出現順序分配，且不會與提示詞中既有的 ID 衝突：如果 `a.b` 清理後變成 `a_b`，但提示詞中已有 `a_b`，重寫後的 ID 就會是 `a_b_2`。

由於沒有儲存任何變更，呼叫端在後續輪次重複使用同一訊息清單時，仍會看到原始 ID；該請求會再次執行修復。

### 反應式備援 {/* #reactive-fallback */}

Provider 拒絕請求後，該規則的 `errorPatterns` 和 `fix` 掛鉤會修復同一類錯誤。事前重寫只在 `isMaybeAnthropic(model)` 符合時執行；對於檢查無法辨識的 Provider 所提供的 Claude（如 Vertex 託管的 Claude），反應式路徑仍是備援方案。一旦呼叫已被拒絕，也只能透過這條路徑修復。規則可同時使用兩種掛鉤；`CompatRule` 介面上的 `fix` 本身並未棄用，自訂規則仍可合理使用。
