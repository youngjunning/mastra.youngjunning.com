# MemoryInputFilter

`MemoryInputFilter` 是**輸入處理器**，會在任何記憶體載入器讀取訊息前，依據已儲存的對話紀錄過濾請求輸入。`Memory` 會自動將它加在 `MessageHistory`、`WorkingMemory`、`SemanticRecall` 和 Observational Memory 之前；只有手動管理記憶體處理器時，才需要自行建立。

## 使用範例 {/* #usage-example */}

```typescript
import { MemoryInputFilter } from '@mastra/core/processors'

const processor = new MemoryInputFilter({
  storage: memoryStorage,
})
```

## 行為 {/* #behavior */}

### 輸入處理 {/* #input-processing */}

對於已有已儲存訊息的執行緒，處理器會依據輸入中的最後一則訊息精簡輸入：

- **以一則或多則使用者訊息結尾**：保留這些使用者訊息，並丟棄往前直到上一則助理訊息之間的內容。連續的使用者訊息都會保留，因為它們都是新訊息。如果那則助理訊息含有用戶端 Tool 結果，也會保留其已儲存副本中仍待完成的呼叫所對應的結果。`useChat` 在用戶端 Tool 結果與下一則使用者訊息一起送出時，就會採用這種輸入形式。
- **以助理訊息結尾**：只保留該訊息末尾連續出現的用戶端 Tool 結果。這對應用戶端 Tool 流程：已儲存的助理回合包含待完成的呼叫，用戶端隨後回傳結果。
- **以助理訊息結尾，但沒有新的 Tool 結果**：只有該訊息已存在於儲存空間時才丟棄它。未曾持久化的助理訊息（例如內部指令訊息）會保留。
- **沒有新內容**：清空輸入，僅依據已儲存的對話紀錄繼續執行。

對於沒有已儲存訊息的執行緒，整個輸入會用來初始化對話。處理器會從助理訊息中移除 Provider 中繼資料，以免重播來自其他對話的伺服器端項目參照。

用戶端 Tool 結果是指處於 `result`、`output-error`、`output-denied` 或 `approval-responded` 狀態的 Tool 呼叫。若某則助理訊息未以其 ID 儲存，處理器會丟棄其中的結果：AI SDK 用戶端可能將多則伺服器訊息合併成一則具有新 ID 的 UI 訊息，此時無法區分用戶端結果與重複的伺服器結果。

結尾的使用者訊息視為新訊息，並依送出時的內容保留。沒有 ID 時，伺服器會為其指派 ID。用戶端回傳的已儲存訊息副本不會取代儲存紀錄，因此該訊息以儲存的時間戳記和 Provider 中繼資料為準。

### 以已儲存訊息為基礎 {/* #stored-messages-as-the-base-layer */}

載入器會以 `memory` 來源加入已儲存訊息。若已儲存訊息與輸入訊息的 ID 相同，則保留已儲存副本中的文字、推理內容、Provider 中繼資料及 `createdAt`。只有已儲存副本中仍有待完成的呼叫時，才從輸入取用該呼叫的 Tool 結果，例如用戶端 Tool 結果或核准回覆。輸入中的文字和中繼資料會被忽略，因此用戶端無法透過傳送不同的副本修改已儲存訊息。如需修改，應直接更新儲存空間中的訊息。啟用 `retainFullInput` 時也一樣。
