# 記憶體輸入過濾器

這`MemoryInputFilter`是一個**輸入處理器**在任何記憶體載入器讀取請求輸入之前，它會根據儲存的歷史記錄過濾請求輸入。它是自動添加的`Memory`領先於`MessageHistory`, `WorkingMemory`, `SemanticRecall`，和觀察內存，因此當您手動管理內存處理器時，您只能自己構建它。

## 使用範例 {/* #usage-example */}

```typescript
import { MemoryInputFilter } from '@mastra/core/processors'

const processor = new MemoryInputFilter({
  storage: memoryStorage,
})
```

## 行為 {/* #behavior */}

### 輸入處理 {/* #input-processing */}

對於已經儲存訊息的線程，根據其最後一條訊息減少輸入：

* **以一條或多條用戶訊息結束**：保留這些訊息，並刪除最後一封助理訊息之前的所有內容。幾個連續的用戶訊息都被保留，因為它們都是新的。如果該輔助訊息攜帶用戶端Tool結果，則其儲存的副本仍待處理的通話的結果也會保留。這是形狀`useChat` sends when a client tool result goes out with the next user message.
* **以助理訊息結束**：僅保留其客戶端Tool結果的追蹤運行。這是一個客戶端Tool流程，其中儲存的助理輪次包含待處理的調用，並且客戶端返回其結果。
* **以助理訊息結束，沒有新Tool結果**：僅當訊息存在於儲存中時才會刪除該訊息。從未保留的輔助訊息（例如內部指令訊息）會保留在原處。
* **不包含任何新內容**：輸入被清除，並且僅根據儲存的歷史記錄繼續運行。

對於沒有儲存訊息的線程，整個輸入都會成為對話的種子。提供程式元資料從助理訊息中刪除，以便不會重播另一個對話中對伺服器端項目的項目引用。

客戶端Tool結果是Tool調用`result`, `output-error`, `output-denied`, or `approval-responded` state. An outcome on an assistant message that isn't stored under its ID is dropped, because the AI SDK client can fold several server messages into one UI message under a new ID, and then a client outcome can't be told apart from a duplicated server result.

尾隨用戶訊息被視為新訊息並保持發送狀態。當它們沒有攜帶 ID 時，伺服器會分配一個。已儲存訊息的回顯副本永遠不會取代儲存的行，因此儲存的時間戳記和提供程式元資料對此訊息保持權威。

### 儲存訊息作為基礎層 {/* #stored-messages-as-the-base-layer */}

載入器新增儲存的訊息`memory` source. When a stored message and an input message share an ID, the stored copy keeps its text, reasoning, provider metadata, and `createdAt`. The only thing taken from the input is a tool outcome for a call that's still pending in the stored copy, such as a client tool result or an approval answer. Text and metadata from the input are ignored, so a client can't change a stored message by sending a different copy of it. To change a stored message, update it in storage. This also applies with `retainFullInput`.
