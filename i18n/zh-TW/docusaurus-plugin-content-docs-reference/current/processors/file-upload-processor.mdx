# 文件上傳處理器

這`FileUploadProcessor`將用戶發送的檔案上傳到[Workspace沙箱](/reference/workspace/sandbox)並為模型提供文字註釋，並用沙箱路徑取代每個檔案。該模型永遠不會接收文件內容。該Agent商使用其沙箱Tool處理該文件。

僅發送到模型的提示會發生變化。儲存的消息保留其文件，因此線程、Studio 等客戶端和其他Agent仍然擁有原始文件。

過濾器接受的檔案永遠不會到達模型：噹噹前回合的檔案無法上傳時，處理器會停止回合而不是讓檔案通過。內存是可選的。

## 使用範例 {/* #usage-example */}

將相同的工作空間傳遞給Agent程式和處理器：

```typescript
import { Agent } from '@mastra/core/agent'
import { FileUploadProcessor } from '@mastra/core/processors'
import { LocalSandbox, Workspace } from '@mastra/core/workspace'

const workspace = new Workspace({
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
})

export const agent = new Agent({
  id: 'file-agent',
  name: 'file-agent',
  instructions: 'Work on the files the user uploads to the sandbox.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  workspace,
  inputProcessors: [
    new FileUploadProcessor({
      workspace,
      filter: ({ extension }) => extension === 'xlsx' || extension === 'docx',
    }),
  ],
})
```

設定每個檔案的大小限制`maxFileSize`. The function returns a number of bytes:

```typescript
import { FileUploadProcessor } from '@mastra/core/processors'

const megabyte = 1024 * 1024

const fileUpload = new FileUploadProcessor({
  workspace,
  maxFileSize: ({ mimeType }) => (mimeType.startsWith('image/') ? 5 * megabyte : 25 * megabyte),
})
```

閱讀處理器停止轉動時的原因。 Tripwire 元資料的類型為`unknown`, so cast it to `FileUploadTripwireMetadata`:

```typescript
import { FILE_UPLOAD_ERROR_CODES } from '@mastra/core/processors'
import type { FileUploadTripwireMetadata } from '@mastra/core/processors'

const result = await agent.generate(messages)

if (result.tripwire?.processorId === 'file-upload') {
  const { code, fileName } = result.tripwire.metadata as FileUploadTripwireMetadata

  if (code === FILE_UPLOAD_ERROR_CODES.FILE_TOO_LARGE) {
    console.error(`${fileName} is too large`)
  }
}
```

## 文件選擇 {/* #file-selection */}

這`filter` function receives each file the user sent and returns `true` to upload it. A file it rejects is left untouched and reaches the model as usual. Without `filter`, every file is uploaded.

此過濾器上傳除模型本身讀取的類型之外的所有檔案：

```typescript
import { FileUploadProcessor } from '@mastra/core/processors'

const readByModel = ['image/', 'audio/', 'video/', 'text/']

const fileUpload = new FileUploadProcessor({
  workspace,
  filter: ({ mimeType }) =>
    mimeType !== 'application/pdf' && !readByModel.some(prefix => mimeType.startsWith(prefix)),
})
```

`filter`和`maxFileSize` receive the same `FileUploadFileInfo` object:

大小不是其中的一部分，因為只有在資料解碼後才知道它。`filter` can be async.

處理器查看模型接收到的每個使用者訊息的文件，包括執行緒歷史記錄，以及隨訊號發送的文件。它忽略助手產生的檔案或Tool傳回的檔案。

上傳以二進位、base64 或資料 URL 形式內聯傳送的檔案。處理器本身從不下載任何內容，因此伺服器發出的請求不能指向內部位址：

* 模型本身取得的連結或Provider檔案 ID 保留在提示中，並且`filter` isn't called for it.
* Mastra 在模型呼叫之前下載模型無法取得的連結。處理器像處理模型接收的任何其他檔案一樣處理下載的位元組。

## 上傳位置 {/* #upload-location */}

文件被寫入`uploads/<directory>/<sha256>.<extension>`, under the directory where the sandbox runs commands. `<directory>` is the thread ID, or the resource ID when the call has no thread, or `shared` when it has neither, so identical bytes from two threads never share a path.

處理器讀取命令目錄`pwd`, then writes the file and reports it at its absolute path. Providers resolve a relative path differently for writes and for commands, so the absolute path is the one the command tool finds. A sandbox that can't run commands uses its `workingDirectory` instead, and the path stays relative when neither is known.

該檔案以其內容的 SHA-256 雜湊值命名，因此相同的位元組始終寫入相同的路徑：

* 沙箱已有的文件不會再寫入。在以後的回合中，該檔案只需要檢查它是否仍然存在。
* 從沙箱中刪除的文件，或在回收的沙箱中遺失的文件，會在下一輪再次寫入。
* 在一個請求中，無論模型被呼叫多少次，檔案都會被放置一次。

此路徑不保留原始名稱，只保留其副檔名。看起來像名稱的路徑會邀請模型重新輸入另一個路徑，並向沙箱詢問不存在的檔案。該名稱在註釋中保持可用。

|姓名已發送 |路徑寫法，在命令目錄下 |
| - | - |
|`report Q3 (final).pdf` | `uploads/<directory>/<sha256>.pdf` |
| `résumé.PDF` | `uploads/<directory>/<sha256>.pdf` |
| `../../etc/passwd` | `uploads/<directory>/<sha256>` |
| No name, `image/png` | `uploads/<directory>/<sha256>.png` |

當類型是通用類型時，傳送的不含名稱的檔案會從其 MIME 類型中取得副檔名。

線程或資源 ID 被重寫，因此該目錄在 shell 命令中是安全的。重音符號被刪除，每個字元都在外面`A-Z`, `a-z`, `0-9`, `.`, `_`, and `-` becomes `_`. Path separators and `..` are replaced too, so a file always stays inside `uploads/`.

每個文件都以臨時名稱寫入並移動到位，因此中斷的寫入永遠不會留下部分文件，而稍後會產生完整的文件。處理器用沙箱寫入`writeFiles` method when the sandbox has one, in a single call for all the files to write. Otherwise it writes with `executeCommand`, sending each file as base64 in chunks, which needs `base64` and `printf` in the sandbox. When the sandbox can run commands, the processor also needs `sh`, `mkdir`, `pwd`, and `mv` there. A sandbox without commands gets every file written in place on every turn, since nothing can be checked or moved.

## 上傳後提示內容 {/* #prompt-content-after-upload */}

在發送到模型的提示中，訊息中相同位置的文件部分被文字部分取代：

```text
[File uploaded to the sandbox]
path: /home/user/uploads/thread-1/0b2f4c6e8a1d3f5b7c9e2a4d6f8b1c3e5a7d9f2b4c6e8a1d3f5b7c9e2a4d6f8b.pdf
name: report.pdf
type: application/pdf
size: 1258291 bytes
```

儲存的訊息保持文件發送時的原樣。工作室和其他客戶將其顯示為附件，模型每次都會再次收到該註釋。

## 錯誤行為 {/* #error-behavior */}

構造函數拋出一個`MastraError` with the ID `FILE_UPLOAD_PROCESSOR_NO_SANDBOX` when `workspace` is missing or has no sandbox configured. `error.details.code` is `NO_SANDBOX`.

當前回合的文件在發送時會在寫入任何內容之前進行檢查。無法上傳的檔案會停止輪流，並且不會上傳任何內容。

對於線程歷史記錄中太大或無法解碼的文件，處理器會替換解釋問題的註釋並讓輪流繼續。這可以防止儲存的檔案阻塞每個後續回合：

```text
[File not uploaded]
name: report.pdf
reason: File "report.pdf" is 31457280 bytes, over the 10485760 byte limit.
```

當沙箱拿不到檔案時，因為沒有沙箱，無法寫入，或寫入失敗，則當前回合的檔案停止本回合。線程歷史記錄檔案會得到一個帶有原因的註釋，然後繼續進行。一個`filter` or `maxFileSize` that fails stops the turn, whichever file it affects. Storage remains unchanged, allowing the thread to work again once the setup is fixed. A turn without a file to upload checks nothing, so scorers, agent networks, and calls without a thread keep working.

處理器透過調用來停止轉動`abort()` with `retry: false`. The model isn't called. `agent.generate()` resolves with `result.tripwire` set instead of rejecting, and `agent.stream()` emits a `tripwire` chunk.

`FILE_UPLOAD_ERROR_CODES`列出每個代碼：

|程式碼|當它發生時 |
| - | - |
|`NO_SANDBOX` | The workspace resolved no sandbox for the request, or resolving it failed |
| `NO_WRITE_CAPABILITY` | The sandbox has neither `writeFiles` nor `executeCommand` |
| `INVALID_MAX_FILE_SIZE` | `maxFileSize` threw, or returned something other than a non-negative number |
| `INVALID_FILTER` | `filter` threw, or returned something other than `true` or `false` |
| `INVALID_FILE_DATA` | The inline data of a file of the current turn can't be decoded |
| `FILE_TOO_LARGE` | A file of the current turn is larger than its limit |
| `UPLOAD_FAILED` | Writing to the sandbox failed |

當寫入失敗時，處理器會刪除在呼叫期間寫入的文件`rm -f` before it stops the turn. If the removal fails, or the sandbox can't run commands, `orphanPaths` lists the paths that may remain.

## 透過訊號發送的文件 {/* #files-sent-with-signals */}

處理器處理發送的文件`agent.sendMessage()` and `agent.sendSignal()`:

* 喚醒空閒Agent的訊號的處理方式類似於`agent.stream()`.
* 在該運行的下一次模型呼叫之前，檢查並上傳傳遞到活動運行的訊號。
* 在運行的第一個模型呼叫之前到達持久Agent的訊號會在回合檢查後加入提示。他們的文件像線程歷史記錄中的文件一樣上傳。

## 限制 {/* #limitations */}

* **處理器Workflow。**&#x4E0A;傳運行於`processLLMRequest`, which doesn't run when the processor is nested in a processor workflow. There, the processor only checks the files, and they reach the model unchanged. Add `FileUploadProcessor` to `inputProcessors` directly.
* **跨線程共享的沙箱。**&#x6BCF;個執行緒的目錄將檔案分開但不保護它們。在其他執行緒或使用者共享的沙箱中，任何執行緒的命令Tool都可以讀取每一次上傳。當文件為私有時，解決[one sandbox per user or thread](/docs/sandbox/overview#sandboxes-per-user-or-thread).
* **從 Studio 發送的文字檔案。**&#x53;tudio 將文字檔案（例如 CSV、JSON、Markdown 或來源檔案）插入訊息中，而不是作為檔案附加。處理器永遠不會看到它，因此不會上傳它，並且其全部內容都會進入提示符。透過 API 作為文件部分發送的文件照常上傳。
