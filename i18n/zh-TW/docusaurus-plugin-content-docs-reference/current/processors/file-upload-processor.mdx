# FileUploadProcessor

`FileUploadProcessor` 會將使用者傳送的檔案上傳至[工作區沙箱](/reference/workspace/sandbox)，並在給模型的文字說明中，以沙箱路徑取代每個檔案。模型不會收到檔案內容；Agent 會使用沙箱 Tool 處理檔案。

只有傳送給模型的提示會改變。儲存的訊息仍保留檔案，因此討論串、Studio 等用戶端與其他 Agent 仍可取得原始檔案。

篩選器接受的檔案不會傳給模型：若目前回合的檔案無法上傳，處理器會停止該回合，而非讓檔案直接通過。Memory 是選用功能。

## 使用範例 {/* #usage-example */}

請將同一個工作區傳給 Agent 與處理器：

```typescript
import { Agent } from '@mastra/core/agent'
import { FileUploadProcessor } from '@mastra/core/processors'
import { LocalSandbox, Workspace } from '@mastra/core/workspace'

const workspace = new Workspace({
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
})

export const agent = new Agent({
  id: 'file-agent',
  name: 'file-agent',
  instructions: 'Work on the files the user uploads to the sandbox.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  workspace,
  inputProcessors: [
    new FileUploadProcessor({
      workspace,
      filter: ({ extension }) => extension === 'xlsx' || extension === 'docx',
    }),
  ],
})
```

使用 `maxFileSize` 設定每個檔案的大小限制。此函式回傳位元組數：

```typescript
import { FileUploadProcessor } from '@mastra/core/processors'

const megabyte = 1024 * 1024

const fileUpload = new FileUploadProcessor({
  workspace,
  maxFileSize: ({ mimeType }) => (mimeType.startsWith('image/') ? 5 * megabyte : 25 * megabyte),
})
```

處理器停止回合時，請讀取停止原因。Tripwire 中繼資料的型別為 `unknown`，因此須將其轉型為 `FileUploadTripwireMetadata`：

```typescript
import { FILE_UPLOAD_ERROR_CODES } from '@mastra/core/processors'
import type { FileUploadTripwireMetadata } from '@mastra/core/processors'

const result = await agent.generate(messages)

if (result.tripwire?.processorId === 'file-upload') {
  const { code, fileName } = result.tripwire.metadata as FileUploadTripwireMetadata

  if (code === FILE_UPLOAD_ERROR_CODES.FILE_TOO_LARGE) {
    console.error(`${fileName} is too large`)
  }
}
```

## 文件選擇 {/* #file-selection */}

`filter` 函式接收使用者傳送的每個檔案，回傳 `true` 表示上傳。遭拒絕的檔案保持原狀，照常傳給模型。若未設定 `filter`，所有檔案都會上傳。

以下篩選器會上傳模型可自行讀取的類型以外的所有檔案：

```typescript
import { FileUploadProcessor } from '@mastra/core/processors'

const readByModel = ['image/', 'audio/', 'video/', 'text/']

const fileUpload = new FileUploadProcessor({
  workspace,
  filter: ({ mimeType }) =>
    mimeType !== 'application/pdf' && !readByModel.some(prefix => mimeType.startsWith(prefix)),
})
```

`filter` 與 `maxFileSize` 接收相同的 `FileUploadFileInfo` 物件：

處理器會檢查模型收到的每則使用者訊息中的檔案，包括討論串歷史，以及隨 signal 傳送的檔案。它會忽略助理產生或 Tool 回傳的檔案。

以內嵌二進位、base64 或資料 URL 形式傳送的檔案都會上傳。處理器本身不會下載任何內容，因此伺服器發出的請求無法藉此指向內部位址：

* 模型自行取得的連結或 Provider 檔案 ID 會留在提示中，且不會呼叫 `filter`。
* 模型無法取得的連結會由 Mastra 在模型呼叫前下載。處理器會像處理其他將傳給模型的檔案一樣，處理下載後的位元組。

## 上傳位置 {/* #upload-location */}

檔案寫入沙箱執行指令的目錄下，路徑為 `uploads/<directory>/<sha256>.<extension>`。`<directory>` 優先使用討論串 ID；沒有討論串時使用資源 ID；兩者都沒有時使用 `shared`。因此，不同討論串中內容相同的檔案也不會共用路徑。

處理器透過 `pwd` 取得指令目錄，再寫入檔案並回報絕對路徑。Provider 對寫入與執行指令的相對路徑解析方式不同，因此指令 Tool 需要絕對路徑才能找到檔案。無法執行指令的沙箱改用其 `workingDirectory`；若兩者都無法確定，路徑會維持相對形式。

檔案名稱取自內容的 SHA-256 雜湊值，因此相同的位元組始終寫入同一路徑：

* 沙箱中已有的檔案不會重新寫入。後續回合只須檢查它是否仍存在。
* 從沙箱刪除的檔案，或因沙箱回收而遺失的檔案，會在下一回合重新寫入。
* 同一請求中，不論呼叫模型多少次，每個檔案都只會放置一次。

路徑只保留原始檔名的副檔名。若路徑看起來像原始檔名，模型可能依此重新拼寫路徑，再向沙箱要求不存在的檔案。原始名稱仍會出現在說明中。

| 傳送時的名稱 | 指令目錄下的寫入路徑 |
| - | - |
|`report Q3 (final).pdf` | `uploads/<directory>/<sha256>.pdf` |
| `résumé.PDF` | `uploads/<directory>/<sha256>.pdf` |
| `../../etc/passwd` | `uploads/<directory>/<sha256>` |
| 無名稱，`image/png` | `uploads/<directory>/<sha256>.png` |

沒有名稱的檔案，若 MIME 類型是常見類型，會據此取得副檔名。

討論串或資源 ID 會被重寫，確保目錄名稱可安全用於 shell 指令。重音符號會移除；除 `A-Z`、`a-z`、`0-9`、`.`、`_` 與 `-` 以外的字元都會替換為 `_`。路徑分隔符與 `..` 也會替換，因此檔案始終位於 `uploads/` 之內。

每個檔案會先以暫存名稱寫入，再移至目標位置，因此寫入中斷不會留下被後續回合誤認為完整檔案的殘缺檔案。若沙箱支援 `writeFiles`，處理器會在一次呼叫中寫入所有待寫檔案；否則透過 `executeCommand` 分塊傳送 base64 資料，此時沙箱須提供 `base64` 與 `printf`。能執行指令的沙箱還須提供 `sh`、`mkdir`、`pwd` 與 `mv`。無法執行指令的沙箱無法檢查或移動檔案，因此每回合都會在目標位置重新寫入所有檔案。

## 上傳後提示內容 {/* #prompt-content-after-upload */}

在傳給模型的提示中，訊息裡的檔案部分會在原位置由文字部分取代：

```text
[File uploaded to the sandbox]
path: /home/user/uploads/thread-1/0b2f4c6e8a1d3f5b7c9e2a4d6f8b1c3e5a7d9f2b4c6e8a1d3f5b7c9e2a4d6f8b.pdf
name: report.pdf
type: application/pdf
size: 1258291 bytes
```

儲存的訊息仍保留檔案傳送時的原貌。Studio 與其他用戶端會將其顯示為附件，模型則會在每回合重新收到這段說明。

## 錯誤行為 {/* #error-behavior */}

若缺少 `workspace`，或其中未設定沙箱，建構函式會拋出 ID 為 `FILE_UPLOAD_PROCESSOR_NO_SANDBOX` 的 `MastraError`。`error.details.code` 為 `NO_SANDBOX`。

寫入任何內容前，處理器會依目前回合的檔案傳送時的形式檢查它們。無法上傳的檔案會停止該回合，而且不會上傳任何檔案。

若討論串歷史中的檔案太大或無法解碼，處理器會用說明問題的文字取代檔案，並讓回合繼續。這可避免已儲存的檔案阻擋之後每個回合：

```text
[File not uploaded]
name: report.pdf
reason: File "report.pdf" is 31457280 bytes, over the 10485760 byte limit.
```

若沙箱無法接收檔案，例如沒有沙箱、無法寫入或寫入失敗，目前回合的檔案會使回合停止；討論串歷史中的檔案則會改為說明原因的文字，回合繼續。若 `filter` 或 `maxFileSize` 失敗，不論影響哪個檔案，回合都會停止。儲存內容維持不變，修正設定後討論串即可繼續。沒有待上傳檔案的回合不會檢查，因此 scorer、Agent 網路與沒有討論串的呼叫仍可正常運作。

處理器透過呼叫 `abort()` 並設定 `retry: false` 來停止回合。模型不會被呼叫。`agent.generate()` 不會拒絕 Promise，而是回傳設有 `result.tripwire` 的結果；`agent.stream()` 則會發出 `tripwire` 區塊。

`FILE_UPLOAD_ERROR_CODES` 列出所有錯誤代碼：

| 代碼 | 發生條件 |
| - | - |
| `NO_SANDBOX` | 請求沒有解析到沙箱，或解析失敗 |
| `NO_WRITE_CAPABILITY` | 沙箱既不支援 `writeFiles`，也不支援 `executeCommand` |
| `INVALID_MAX_FILE_SIZE` | `maxFileSize` 拋出錯誤，或回傳的不是非負數 |
| `INVALID_FILTER` | `filter` 拋出錯誤，或回傳的不是 `true` 或 `false` |
| `INVALID_FILE_DATA` | 目前回合檔案的內嵌資料無法解碼 |
| `FILE_TOO_LARGE` | 目前回合的檔案超過大小限制 |
| `UPLOAD_FAILED` | 寫入沙箱失敗 |

寫入失敗時，處理器會在停止回合前，以 `rm -f` 刪除本次呼叫中已寫入的檔案。若刪除失敗，或沙箱無法執行指令，`orphanPaths` 會列出可能殘留的路徑。

## 透過訊號發送的文件 {/* #files-sent-with-signals */}

處理器會處理透過 `agent.sendMessage()` 與 `agent.sendSignal()` 傳送的檔案：

* 喚醒閒置 Agent 的 signal 會依 `agent.stream()` 的輸入處理。
* 傳送給執行中 Agent 的 signal，會在該次執行的下一次模型呼叫前接受檢查並上傳。
* 若 signal 在持久化 Agent 首次呼叫模型前抵達，會在目前回合的檢查後加入提示。其檔案會像討論串歷史中的檔案一樣上傳。

## 限制 {/* #limitations */}

* **處理器 Workflow。**上傳發生在 `processLLMRequest`；處理器嵌套在處理器 Workflow 時不會執行此方法。此時處理器只檢查檔案，檔案會原樣傳給模型。請將 `FileUploadProcessor` 直接加入 `inputProcessors`。
* **跨討論串共用的沙箱。**各討論串的目錄可分隔檔案，但不提供存取保護。在其他討論串或使用者共用的沙箱中，任何討論串的指令 Tool 都能讀取所有上傳檔案。若檔案屬於私密內容，請[為每個使用者或討論串配置獨立沙箱](/docs/sandbox/overview#sandboxes-per-user-or-thread)。
* **從 Studio 傳送的文字檔。**Studio 會將 CSV、JSON、Markdown 或原始碼等文字檔以文字插入訊息，而非附加為檔案。處理器看不到它們，因此不會上傳，完整內容會進入提示。透過 API 以檔案部分傳送的檔案則會照常上傳。
