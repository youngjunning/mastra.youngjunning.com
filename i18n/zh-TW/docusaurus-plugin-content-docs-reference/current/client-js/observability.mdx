# 可觀測性 API

可觀測性 API 提供取得追蹤、監控應用程式效能、為追蹤評分以進行評估，以及記錄與追蹤和跨度相關回饋的方法。

## 取得特定追蹤 {/* #getting-a-specific-trace */}

透過 ID 取得特定追蹤，包括其中所有跨度及詳細資訊：

```typescript
const trace = await mastraClient.getTrace('trace-id-123')
```

## 篩選並取得追蹤 {/* #getting-traces-with-filtering */}

取得追蹤根跨度的分頁清單，並可選擇套用篩選條件：

```typescript
const traces = await mastraClient.getTraces({
  pagination: {
    page: 1,
    perPage: 20,
    dateRange: {
      start: new Date('2024-01-01'),
      end: new Date('2024-01-31'),
    },
  },
  filters: {
    name: 'weather-agent', // Filter by trace name
    spanType: 'agent', // Filter by span type
    entityId: 'weather-agent-id', // Filter by entity ID
    entityType: 'agent', // Filter by entity type
  },
})

console.log(`Found ${traces.spans.length} root spans`)
console.log(`Total pages: ${traces.pagination.totalPages}`)

// To get the complete trace with all spans, use getTrace
const completeTrace = await mastraClient.getTrace(traces.spans[0].traceId)
```

## 列出清單檢視所需的追蹤 {/* #listing-traces-for-a-list-view */}

`listTracesLight()` 傳回與追蹤清單相同的資料列，但不包含 `input`、`output` 和 `attributes` 的完整內容。每列改為提供簡短的 `inputPreview`、`outputPreview` 和 `errorPreview` 字串（最多 100 個字元，截斷時以 `…` 結尾），讓清單無須傳輸完整內容即可顯示預覽欄位；另提供 `threadId` 和 `resourceId`，供記憶體上下文欄位使用。

一次顯示大量追蹤時，優先使用此方法；只在開啟資料列時取得完整記錄：

```typescript
const list = await mastraClient.listTracesLight({
  pagination: { page: 0, perPage: 25 },
  filters: { entityType: 'agent' },
})

for (const span of list.spans) {
  console.log(span.name, span.inputPreview)
}

// Fetch the full payload only for the trace the user selects
const selected = await mastraClient.getTrace(list.spans[0].traceId)
```

它接受與 `listTraces()` 相同的篩選、排序和增量輪詢參數。需要完整跨度內容時，請使用 `listTraces()`。

## 查詢跨度 {/* #querying-spans */}

`querySpans()` 傳回跨追蹤的已完成跨度摘要。查詢須提供跨度開始時間的正值 ISO 時間戳範圍，並支援游標分頁：

```typescript
const result = await mastraClient.querySpans({
  timeRange: {
    from: '2026-10-01T00:00:00.000Z',
    to: '2026-10-02T00:00:00.000Z',
  },
  where: {
    op: 'and',
    args: [
      { op: 'eq', left: { path: 'threadId' }, right: { literal: 'thread-123' } },
      { op: 'gte', left: { path: 'durationMs' }, right: { literal: 1000 } },
    ],
  },
  orderBy: [{ field: 'startedAt', direction: 'desc' }],
  page: { limit: 100 },
})

// Pass result.page.next as page.after to continue with the same filters and ordering.
console.log(result.spans)
```

回應格式為 `{ spans, page: { next } }`。呼叫前請檢查 `capabilities.spanQuery`；使用可選篩選條件前，還須檢查對應欄位的能力。欄位、運算子、預設值、能力、回應細節及游標處理方式，請參閱[查詢跨度](/reference/observability/tracing/advanced-queries#query-spans)。

### 彙總跨度 {/* #aggregate-spans */}

`aggregateSpans()` 將符合直接跨度述詞的已完成跨度分組。每組傳回一列；設定 `interval` 時，每組的每個非空時間區間各傳回一列。它會計入任何深度的跨度，包括追蹤彙總可能漏掉的巢狀 Agent 執行：

```typescript
const { capabilities } = await mastraClient.getObservabilityCapabilities()

if (capabilities.spanAggregate) {
  const { rows, truncated } = await mastraClient.aggregateSpans({
    timeRange: {
      from: '2026-10-01T00:00:00.000Z',
      to: '2026-10-08T00:00:00.000Z',
    },
    where: { op: 'eq', left: { path: 'spanType' }, right: { literal: 'agent_run' } },
    groupBy: ['status'],
    interval: '1d',
    measures: ['count', 'errorRate'],
  })
}
```

請求和回應結構與 `aggregateTraces()` 相同，但使用直接跨度述詞，以及 `spanType`、`name` 和 `parentEntityName` 等跨度維度。token 和成本指標歸屬於記錄用量的跨度，不會加到父跨度。呼叫前請檢查 `capabilities.spanAggregate`；依 `model` 或 `provider` 分組或計算相異值前，還須檢查 `capabilities.spanAggregateModelDimensions`。較舊的儲存介接器會對這些請求傳回 `501`。

當 `capabilities.aggregateTimeToFirstMeasures` 為 `true` 時，`aggregateTraces()` 和 `aggregateSpans()` 都接受首個 token 時間（TTFT）及首個資料區塊時間（TTFC）指標：`timeToFirstToken.*` 和 `timeToFirstChunk.*`。沒有記錄值的跨度和追蹤會略過，不會視為 0。請參閱[首個資料區塊時間（TTFC）](/reference/observability/tracing/advanced-queries#time-to-first-chunk-ttfc)和[首個 token 時間（TTFT）](/reference/observability/tracing/advanced-queries#time-to-first-token-ttft)。

篩選方式、維度、各跨度用量，以及如何列出群組中的跨度，請參閱[彙總跨度](/reference/observability/tracing/advanced-queries#aggregate-spans)。

## 查詢執行緒 {/* #querying-threads */}

`queryTraceThreads()` 透過 `POST /observability/threads/query` 從已完成的追蹤取得執行緒摘要。每列包含活動時間戳記、追蹤數量、上下文和預覽。不包含沒有執行緒 ID 的追蹤。

```typescript
const result = await mastraClient.queryTraceThreads({
  timeRange: {
    traces: {
      from: '2026-10-01T00:00:00.000Z',
      to: '2026-10-02T00:00:00.000Z',
    },
  },
  where: { op: 'eq', left: { path: 'status' }, right: { literal: 'error' } },
  orderBy: [{ field: 'endedAt', direction: 'desc' }],
  page: { limit: 100 },
})

for (const thread of result.threads) {
  console.log(thread.firstTraceId, thread.lastTraceId, thread.traceCount, thread.outputPreview)
}
```

### 執行緒時間範圍 {/* #thread-time-ranges */}

請只選擇一種時間條件。每個範圍都須使用 ISO 時間戳記，且 `from` 必須早於 `to`。範圍包含 `from`，但不包含 `to`。

| 時間條件 | 符合條件的執行緒 |
| - | - |
| `timeRange.traces: { from, to }` | 至少有一個追蹤在指定時間範圍內開始 |
| `timeRange.threads: { field: 'startedAt', from, to }` | 首次活動發生在指定時間範圍內 |
| `timeRange.threads: { field: 'endedAt', from, to }` | 最後一次活動發生在指定時間範圍內 |

例如，尋找最後一次活動發生在 10 月 1 日的執行緒：

```typescript
const result = await mastraClient.queryTraceThreads({
  timeRange: {
    threads: {
      field: 'endedAt',
      from: '2026-10-01T00:00:00.000Z',
      to: '2026-10-02T00:00:00.000Z',
    },
  },
})
```

資料列包含授權範圍內保留的完整歷史記錄，包括指定時間範圍之前和之後的追蹤。篩選條件會套用至這些完整資料列。`environment` 篩選條件會檢查第一個追蹤的環境。

### 執行緒篩選條件 {/* #thread-filters */}

使用 `where` 篩選執行緒資料列。可透過 `and`、`or` 和 `not` 組合述詞。

| 欄位 | 運算子 |
| - | - |
| `threadId`, `organizationId`, `firstTraceId`, `lastTraceId` | `eq`, `ne`, `in`, `notIn`, `exists`, `notExists` |
| `resourceId`, `userId`, `runId`, `sessionId`, `requestId`, `serviceName`, `experimentId`, `environment`, `executionSource` | 與上一列相同的字串運算子 |
| `entityType`, `entityId`, `entityName`, `entityVersionId` | 與上一列相同的字串運算子 |
| `status` | `eq`, `ne`, `in`, `notIn`；值為 `success` 或 `error` |
| `startedAt`, `endedAt`, `timeToFirstChunkMs`, `timeToFirstTokenMs` | `eq`, `ne`, `lt`, `lte`, `gt`, `gte`, `in`, `notIn`, `exists`, `notExists` |
| `traceCount` | `eq`, `ne`, `lt`, `lte`, `gt`, `gte` |

例如，篩選來自指定 Agent 且至少包含三個追蹤的執行緒：

```typescript
const result = await mastraClient.queryTraceThreads({
  timeRange: {
    traces: {
      from: '2026-10-01T00:00:00.000Z',
      to: '2026-10-02T00:00:00.000Z',
    },
  },
  where: {
    op: 'and',
    args: [
      { op: 'in', value: { path: 'entityId' }, set: ['support-agent', 'sales-agent'] },
      { op: 'gte', left: { path: 'traceCount' }, right: { literal: 3 } },
    ],
  },
})
```

存在性篩選條件使用 `{ op: 'exists', path: 'userId' }` 檢查值是否非 `null`。傳回的資料列包含 model、provider 和預覽，但無法依這些資料篩選。

### 執行緒回應 {/* #thread-response */}

回應格式為 `{ threads, page: { next } }`，不包含總筆數。`threads` 中的每個項目都包含以下欄位：

| 傳回欄位 | 意義 |
| - | - |
| `threadId`, `organizationId` | 執行緒識別資訊。不同組織中相同的執行緒 ID 仍分別處理。 |
| `firstTraceId`, `lastTraceId` | 依開始時間排序最早及最晚的追蹤。開始時間相同時，以追蹤 ID 作為確定性的排序依據。 |
| `resourceId`, `userId`, `runId`, `sessionId`, `requestId`, `serviceName`, `experimentId`, `environment`, `executionSource` | 第一個追蹤的上下文；缺少時為 `null`。 |
| `entityType`, `entityId`, `entityName`, `entityVersionId` | 第一個追蹤的實體資訊。 |
| `startedAt`, `endedAt` | 執行緒中最早的開始時間及最晚的結束時間。 |
| `status` | 最晚開始的追蹤，其根跨度若發生錯誤則為 `error`，否則為 `success`。 |
| `traceCount` | 執行緒中的邏輯追蹤數量。 |
| `inputPreview` | 第一個追蹤的輸入預覽。 |
| `outputPreview`, `errorPreview` | 最晚開始的追蹤的預覽。 |
| `timeToFirstChunkMs` | 第一個追蹤的根 Agent 產生首個資料區塊所需的時間，單位為毫秒。無法取得或根跨度不是 Agent 時為 `null`。 |
| `timeToFirstTokenMs` | 第一個追蹤的根 Agent 產生首個 token 所需的時間，單位為毫秒；`null` 的判定規則相同。僅在儲存層支援時提供。 |

較早開始的追蹤可能最後才完成。此時它會提供 `endedAt`，但狀態及輸出／錯誤預覽仍取自最晚開始的追蹤。第一個追蹤缺少的值不會由較晚的追蹤補上。

### 執行緒排序與分頁 {/* #thread-ordering-and-pagination */}

排序欄位只能選擇 `startedAt` 或 `endedAt`，方向為 `asc` 或 `desc`。預設依 `endedAt` 遞減排序。每頁預設 25 列，最多 100 列。將 `result.page.next` 作為 `page.after` 傳入，並保持時間條件、篩選條件、範圍和排序方式一致。游標為 `null` 表示沒有更多頁面。分頁反映即時資料，因此新追蹤可能使執行緒移至其他頁面。

若要載入執行緒中的追蹤，請使用 [`queryTraces()`](#querying-traces)，設定 `threadId` 篩選條件，並指定涵蓋執行緒活動的時間範圍。

### 執行緒查詢支援情況 {/* #thread-query-support */}

使用此查詢介面前，請檢查 `getObservabilityCapabilities()` 傳回的 `capabilities.threadQueryRows`。若缺少此值或值為 false，表示無法取得完整的執行緒資料列。較舊的核心套件或儲存套件會對這類請求傳回結構化的 `501` 回應。混用不同套件版本時，仍支援舊版識別資訊請求。

當授權範圍內的歷史記錄超過 250,000 列已儲存的追蹤根資料列（包含重複副本）時，ClickHouse 會拒絕範圍過廣的執行緒查詢。縮小時間範圍、減少候選執行緒後，查詢仍可能成功。遭拒的查詢會傳回 `503 TRACE_QUERY_RESOURCE_LIMIT`，不包含部分結果。

## 查詢追蹤 {/* #querying-traces */}

`queryTraces()` 使用追蹤欄位及相關跨度的條件，尋找已完成的邏輯追蹤。每個查詢都須指定 ISO 時間戳記範圍。

```typescript
const result = await mastraClient.queryTraces({
  timeRange: {
    from: '2026-08-01T00:00:00.000Z',
    to: '2026-08-08T00:00:00.000Z',
  },
  where: {
    spans: {
      some: {
        op: 'and',
        args: [
          { op: 'eq', left: { path: 'spanType' }, right: { literal: 'tool_call' } },
          { op: 'exists', path: 'error' },
        ],
      },
    },
  },
})
```

請求欄位、述詞、限制、回應格式及錯誤，請參閱[查詢追蹤](/reference/observability/tracing/advanced-queries#query-traces)。

### 載入頁面並輪詢追蹤 {/* #load-a-page-and-poll-for-traces */}

`queryTraces()` 支援透過 `page` 進行鍵集分頁、透過 `pagination` 進行頁碼分頁，以及透過 `mode: 'delta'` 進行增量輪詢。每個請求只使用一種模式。若要從 `listTracesLight()` 遷移，請讀取 `traces` 而非 `spans`，並保留頁碼分頁結果中的 `deltaCursor`：

```typescript
const timeRange = {
  from: '2026-08-01T00:00:00.000Z',
  to: '2026-08-08T00:00:00.000Z',
}
const initial = await mastraClient.queryTraces({
  timeRange,
  pagination: { page: 0, perPage: 100 },
})
if (!initial.deltaCursor) throw new Error('Delta polling is unavailable')

const changes = await mastraClient.queryTraces({
  timeRange,
  mode: 'delta',
  after: initial.deltaCursor,
  limit: 100,
})
```

依 `traceId` 合併 `changes.traces`，保留 `changes.deltaCursor`，並在 `changes.delta.hasMore` 為 `true` 時繼續輪詢。各次輪詢須使用相同的時間範圍和述詞。只會傳回已完成的追蹤；相關記錄的更新、刪除，或追蹤不再符合條件時，輪詢不保證會發出通知。

初始載入行為、游標有效期限、資料保留及完整輪詢流程，請參閱[增量輪詢](/reference/observability/tracing/advanced-queries#poll-after-loading-a-numbered-page)。

### 彙總追蹤 {/* #aggregate-traces */}

`aggregateTraces()` 將時間範圍及可選的 `where` 述詞所選出的追蹤分組。每組傳回一列；設定 `interval` 時，每組的每個非空時間區間各傳回一列。它接受與 `queryTraces()` 相同的述詞。

```typescript
const { capabilities } = await mastraClient.getObservabilityCapabilities()

if (capabilities.traceAggregate) {
  const { rows, truncated } = await mastraClient.aggregateTraces({
    timeRange: {
      from: '2026-08-01T00:00:00.000Z',
      to: '2026-08-08T00:00:00.000Z',
    },
    where: { op: 'eq', left: { path: 'environment' }, right: { literal: 'production' } },
    groupBy: ['entityName'],
    interval: '1d',
    measures: ['count', 'errorRate', 'duration.p95', 'cost.sum'],
    orderBy: { field: 'count', direction: 'desc' },
    limit: 10,
  })
}
```

每列包含依 `groupBy` 欄位命名的 `dimensions`、依指標名稱命名的 `measures`、設定 `interval` 時的 `bucket` 時間戳記，以及請求成本指標時的 `cost` 涵蓋資訊。符合條件的群組數超過 `limit` 時，`truncated` 為 `true`。呼叫前請檢查 `capabilities.traceAggregate`。用戶端會套用設定的重試規則，但不會重試 `4xx` 回應、`501` 回應，以及錯誤碼為 `TRACE_QUERY_EXECUTION_TIMEOUT` 的 `504` 回應。一般閘道的 `504` 回應仍可重試。

維度、指標、token 與成本的計算方式、時間區間、限制及錯誤，請參閱[彙總追蹤](/reference/observability/tracing/advanced-queries#aggregate-traces)。

### 探索追蹤查詢欄位與值 {/* #discover-trace-query-fields-and-values */}

`getTraceQueryFields()` 傳回指定述詞範圍中的標準查詢欄位，以及觀察到的頂層字串中繼資料欄位。回應包含各欄位的值類型、支援的運算子，以及是否提供值建議。

```typescript
const timeRange = {
  from: '2026-08-01T00:00:00.000Z',
  to: '2026-08-08T00:00:00.000Z',
}

const fields = await mastraClient.getTraceQueryFields({
  timeRange,
  predicateScope: 'spans',
  search: 'model',
  limit: 25,
})
```

在支援彙總的伺服器上查詢 `trace` 範圍時，回應還包含 `aggregate`：可傳給 `groupBy` 的 `dimensions`，以及可請求的 `measures`。請參閱[探索欄位與值](/reference/observability/tracing/advanced-queries#discover-fields-and-values)。

請在相同範圍內使用回應提供的確切本地路徑。例如，`model` 應放在 `spans.some` 或 `spans.none` 述詞中。欄位選擇器可以平行取得 `trace` 和 `spans` 兩個範圍。

只有選取 `valueSuggestions: true` 的欄位後，才呼叫 `getTraceQueryValues()`：

```typescript
const controller = new AbortController()

const values = await mastraClient.getTraceQueryValues(
  {
    timeRange,
    predicateScope: 'spans',
    path: 'model',
    search: 'claude',
    limit: 25,
  },
  { signal: controller.signal },
)

// Cancel this autocomplete request when the search text changes.
controller.abort()
```

兩種方法都使用不區分大小寫的字面子字串搜尋，也接受空白搜尋字串。數量上限預設為 25，最高為 100。結果先依出現次數排序，再依路徑或值進行確定性排序。`observedFieldsTruncated` 和 `valuesTruncated` 表示呼叫端應縮小 `search` 的範圍。探索結果沒有游標。

建議值有數量限制，僅供參考。建議無法取得、結果為空或遭截斷時，手動輸入的值仍然有效。探索請求不接受尚未完成的查詢述詞。用戶端不會重試這兩種請求；單次呼叫傳入的 `AbortSignal` 優先於 `MastraClient` 上設定的訊號。

探索查詢逾時會傳回 `504 TRACE_QUERY_EXECUTION_TIMEOUT`。後端記憶體或資源耗盡會傳回 `503 TRACE_QUERY_RESOURCE_LIMIT`。這兩種錯誤都不包含部分建議；截斷旗標只會出現在成功且已完成排序的回應中。

## 刪除追蹤 {/* #deleting-traces */}

刪除追蹤及其相關的跨度、指標、日誌、分數和回饋：

```typescript
const result = await mastraClient.deleteTraces({
  traceIds: ['trace-1', 'trace-2'],
})

if ('accepted' in result) {
  console.log('Deletion requested')
} else {
  console.log(result.success)
}
```

每個請求最多接受 1,000 個追蹤 ID，且不提供租戶範圍欄位。未連結到追蹤的訊號會保留。實驗建立的追蹤與其他追蹤一樣會被刪除。

用戶端支援兩種回應格式：OSS 完成刪除作業後傳回 `{ success: true }`；支援佇列批次刪除的 Platform 後端接受清理請求後，傳回 `202 { accepted: true }`。接受請求不代表讀取時已看不到記錄，因此回報刪除完成前請檢查回應。若要在 Platform 使用這些用戶端方法，部署版本須支援批次刪除端點。

## 為追蹤評分 {/* #scoring-traces */}

使用已註冊的評分器為指定追蹤評分，以進行評估：

```typescript
const result = await mastraClient.score({
  scorerName: 'answer-relevancy',
  targets: [
    { traceId: 'trace-1', spanId: 'span-1' }, // Score specific span
    { traceId: 'trace-2' }, // Score specific span which defaults to the parent span
  ],
})
```

## 依跨度取得分數 {/* #getting-scores-by-span */}

取得追蹤中指定跨度的分數：

```typescript
const scores = await mastraClient.listScoresBySpan({
  traceId: 'trace-123',
  spanId: 'span-456',
  page: 1,
  perPage: 20,
})
```

## 依 ID 取得分數 {/* #get-a-score-by-id */}

使用 `getScore()` 取得一筆可觀測性分數：

```typescript
const { score } = await mastraClient.getScore('score-id-123')
```

回應格式為 `{ score: record | null }`。找不到分數時，會傳回 HTTP 200 和 `{ score: null }`。
回傳型別為 `@mastra/client-js` 匯出的 `GetScoreResponse`。

## 建立分數 {/* #creating-scores */}

為追蹤建立分數，並可選擇指定其中的跨度：

```typescript
const response = await mastraClient.createScore({
  score: {
    traceId: 'trace-123',
    spanId: 'span-456',
    scorerId: 'accuracy',
    score: 0.95,
  },
})
```

`createScore()` 要求 `score.traceId` 不得為空白，`spanId` 則為可選。用戶端每次呼叫只會產生一次缺少的 `scoreId` 和 ISO `timestamp`，重試時會沿用。若要重複使用既有識別資訊，請提供這些欄位。上下文解析與重試行為請參閱[訊號寫入選項](#signal-write-options)。

## 回饋 {/* #feedback */}

回饋方法透過設定的 API 伺服器建立、列出及查詢人工參與的訊號，例如評分、讚／倒讚、留言和修正。建立方法支援 OSS 和 Platform。Platform 及支援回饋替換的 OSS 伺服器可完整替換記錄。範例請參閱[回饋指南](/docs/observability/feedback)，完整結構請參閱[回饋參考文件](/reference/observability/feedback)。

### 依 ID 取得回饋 {/* #get-feedback-by-id */}

使用 `getFeedback()` 取得一筆回饋記錄：

```typescript
const { feedback } = await mastraClient.getFeedback('feedback-id-123')
```

回應格式為 `{ feedback: record | null }`。找不到記錄時，會傳回 HTTP 200 和 `{ feedback: null }`。
回傳型別為 `@mastra/client-js` 匯出的 `GetFeedbackResponse`。

這兩個取得方法都接受未編碼的 ID，並將其編碼為 URL 路徑區段。它們使用用戶端設定的 API 前綴、憑證及標頭。JSON 回應中的記錄時間戳記為 ISO 字串。

### 建立回饋 {/* #creating-feedback */}

為追蹤建立回饋記錄，並可選擇指定其中的跨度：

```typescript
const response = await mastraClient.createFeedback({
  feedback: {
    traceId: 'trace-123',
    spanId: 'span-456',
    feedbackSource: 'user',
    feedbackType: 'rating',
    value: 1,
    comment: 'Helpful answer.',
  },
})
```

`createFeedback()` 要求 `feedback.traceId` 不得為空白，`spanId` 則為可選。用戶端每次呼叫只會產生一次缺少的 `feedbackId` 和 ISO `timestamp`，重試時會沿用。設定 `feedbackUserId` 以識別回饋者；`userId` 則識別跨度的使用者。已驗證的 OSS 使用者身分優先於提交的回饋者身分。

### 訊號寫入選項 {/* #signal-write-options */}

兩種建立方法除了 `feedback` 或 `score` 包裝欄位，也接受可選的頂層 `contextMode`：

* `"provided"` 使用記錄中攤平的上下文欄位，不查詢跨度。缺少的上下文欄位不會自動補齊。
* `"resolve"` 從已儲存的根跨度及可選的目標跨度取得上下文。根跨度的標籤會繼承至記錄；記錄的中繼資料會覆蓋相同鍵的已儲存中繼資料。找不到根跨度時傳回 `TRACE_NOT_FOUND`，找不到目標跨度時傳回 `SPAN_NOT_FOUND`。

省略 `contextMode` 時會使用伺服器預設值：OSS 為 `"provided"`，Platform 為 `"resolve"`。用戶端會保留省略狀態。若兩種伺服器都須採用相同行為，請明確指定模式。在 OSS 上，每個已設定的可信範圍欄位都會覆蓋呼叫端輸入。在 `"provided"` 模式下，其他上下文欄位仍使用呼叫端提供的值。例如，可信的組織 ID 會覆蓋 `organizationId`；若未設定可信的資源範圍，則不會清除 `resourceId`。

```typescript
const result = await mastraClient.createFeedback({
  contextMode: 'resolve',
  feedback: {
    traceId: 'trace-123',
    feedbackUserId: 'reviewer-1',
    feedbackType: 'thumbs',
    value: 1,
  },
})
```

在可選的第二個參數中使用 `retries` 和 `anchorRetryTimeoutMs` 控制重試。網路及伺服器錯誤使用用戶端的傳輸層重試設定。只有錯誤碼為 `TRACE_NOT_FOUND` 或 `SPAN_NOT_FOUND` 的 404 回應會觸發錨點重試，且從首次出現這類回應起最多持續 30 秒。將 `anchorRetryTimeoutMs` 設為較短時間，或設為 `0` 以停用這類重試。其他 404、驗證及資料驗證錯誤都不會重試。

建立回應包含 `success`，以及可選的 `data`；後者包含產生或提供的 `feedbackId`／`scoreId`、`traceId`、可為 `null` 的 `spanId`，以及正規化為 UTC 的 `timestamp`。用戶端也接受僅回報成功的回應。Platform 回報成功代表已發布，但讀取時可能尚未立即看到記錄。直接呼叫 OSS HTTP API 時，可以省略 ID 和時間戳記，由伺服器產生。

明確指定模式需要伺服器支援。較舊的伺服器可能忽略 `contextMode`。在 Platform 傳送 `"provided"` 前，請先部署其提供上下文模式的支援功能。

### 替換回饋 {/* #replacing-feedback */}

`replaceFeedback()` 會將完整替換內容傳送至 `PUT /api/observability/feedback/:feedbackId`。請包含原本的 `feedbackId`、`traceId`、正規化後的 `timestamp`，以及所有要保留的回饋欄位。Platform 和支援回饋替換的 OSS 伺服器都接受此方法。若 OSS 的儲存介接器不支援替換，會傳回 `501`。在 OSS 提供編輯功能前，請檢查 `capabilities.feedbackReplacement`；缺少此能力表示無法使用。

```typescript
await mastraClient.replaceFeedback({
  feedback: {
    feedbackId: 'feedback-1',
    traceId: 'trace-123',
    timestamp: '2026-01-01T00:00:00.123Z',
    feedbackType: 'thumbs',
    value: -1,
    feedbackUserId: 'reviewer-1',
  },
})
```

若建立回應包含 `data`，請使用其中正規化後的時間戳記。OSS 會以 `409` 拒絕變更原始追蹤或時間戳記。Platform 也將時間戳記用作記錄識別資訊的一部分，因此同樣須保留。用戶端重試時會沿用替換請求的內容，但每次獲接受的 PUT 重試都是一次新的替換，可能覆蓋其他編輯。若要停用自動重試，請將 `{ retries: 0, anchorRetryTimeoutMs: 0 }` 作為第二個參數傳入。

### 刪除回饋與分數 {/* #deleting-feedback-and-scores */}

依 ID 刪除回饋或分數記錄。刪除作業具有冪等性，因此會忽略不存在的 ID。每個請求最多接受 1,000 個 `feedbackIds` 或 1,000 個 `scoreIds`。可選的 `organizationId` 和 `resourceId` 欄位會將刪除範圍限制為範圍欄位相符的記錄：

```typescript
await mastraClient.deleteFeedback({
  feedbackIds: ['feedback-1', 'feedback-2'],
  organizationId: 'org-1',
  resourceId: 'resource-1',
})

await mastraClient.deleteScores({
  scoreIds: ['score-1', 'score-2'],
  organizationId: 'org-1',
  resourceId: 'resource-1',
})
```

兩種方法都會從 OSS 取得 `{ success: boolean }`，或從支援佇列批次刪除的 Platform 後端取得 `{ accepted: true }`。回應處理方式請參閱[刪除追蹤](#deleting-traces)。獲接受的記錄在清理作業執行前仍可能可以讀取。Platform 使用經驗證的組織／專案範圍，請求內容中的範圍欄位無法覆蓋此設定。

### 列出回饋 {/* #listing-feedback */}

取得分頁回饋記錄，並可選擇套用篩選條件：

```typescript
const feedback = await mastraClient.listFeedback({
  filters: {
    feedbackType: 'rating',
    feedbackSource: 'studio',
  },
  pagination: { page: 0, perPage: 20 },
  orderBy: { field: 'timestamp', direction: 'DESC' },
})
```

`filters` 接受 [`FeedbackFilter`](/reference/observability/feedback#feedbackfilter) 的所有欄位。用戶端會將這些欄位作為 `GET /api/observability/feedback` 的查詢參數傳送。請參閱[清單查詢參數](/reference/observability/feedback#list-query-parameters)。
