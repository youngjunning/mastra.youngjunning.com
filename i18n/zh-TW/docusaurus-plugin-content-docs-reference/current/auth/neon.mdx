# `MastraAuthNeon` 與 `MastraRBACNeon`

[`MastraAuthNeon`](https://github.com/mastra-ai/mastra/tree/main/auth/neon) 將 Mastra 身分驗證接入 [Neon Auth](https://neon.com/docs/guides/neon-auth)。它透過 Neon Auth 的 JWKS 端點驗證以 Bearer Token 傳送的 JWT，並透過工作階段 API 驗證 Neon Auth 工作階段 Cookie。此提供者也支援電子郵件密碼登入、註冊及工作階段管理。

`MastraRBACNeon` 將 Neon Auth 組織角色對應至 Mastra 權限。如果應用程式使用 Neon Auth 組織成員身分進行角色型存取控制，需另外註冊此提供者。

:::note

RBAC 在正式環境需要 Mastra 企業版 (EE) 授權；在開發環境無需授權即可使用。請參閱[需要 EE 授權的功能](/docs/license#what-requires-an-ee-license)。如需進一步瞭解，請[聯絡銷售團隊](https://mastra.ai/contact)。

:::

## 用法 {/* #usage */}

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { MastraAuthNeon, MastraRBACNeon } from '@mastra/auth-neon'

const auth = new MastraAuthNeon()

const rbac = new MastraRBACNeon({
  roleMapping: {
    admin: ['*'],
    member: ['agents:read', 'workflows:read'],
    _default: [],
  },
})

export const mastra = new Mastra({
  server: {
    auth,
    rbac,
  },
})
```

將 `NEON_AUTH_BASE_URL` 設為 Neon Console 顯示的 Neon Auth URL，例如 `https://ep-example-123456.neonauth.us-east-2.aws.neon.tech/neondb/auth`。也可以直接將 `baseUrl` 傳入兩個建構函式。

設定步驟請參閱 [Neon 整合指南](/integrations/auth/neon)。

### 身分驗證方法 {/* #authentication-methods */}

#### `authenticateToken()` {/* #authenticatetoken */}

```typescript
await auth.authenticateToken(token, request)
```

使用設定的 JWKS 端點驗證 JWT 格式的權杖，檢查簽章、簽發者、受眾與到期時間。否則，透過工作階段 API 驗證請求中的 Neon Auth 工作階段 Cookie。即使 JWT 驗證失敗，仍會嘗試接受工作階段 Cookie，因此過期的 Bearer Token 不會讓同時傳送 Cookie 的用戶端登出。若請求沒有工作階段 Cookie，非 JWT 權杖會視為工作階段 Cookie 的值。驗證成功時傳回 `NeonAuthUser`，失敗時傳回 `null`。

`NeonAuthUser` 包含最上層的 `id`、`email` 與 `name`、Neon Auth 的 `user` 物件，以及 `session`（Cookie 驗證）或已驗證的 `jwt` 宣告（Bearer 驗證）。

#### `authorizeUser()` {/* #authorizeuser */}

```typescript
await auth.authorizeUser(user, request)
```

若設定了自訂授權函式，就執行該函式。否則，必須有 Neon Auth 使用者 ID，且會拒絕已到期的 JWT 酬載。

### 憑證驗證方法 {/* #credentials-methods */}

#### `signIn()` {/* #signin */}

```typescript
const result = await auth.signIn(email, password, request)
```

透過 Neon Auth 驗證電子郵件密碼憑證。傳回已驗證使用者、作為 `token` 的 Neon Auth JWT，以及 Neon Auth 工作階段 Cookie。Neon Auth 必須信任傳入請求的來源。

#### `signUp()` {/* #signup */}

```typescript
const result = await auth.signUp(email, password, name, request)
```

使用電子郵件密碼憑證建立 Neon Auth 帳號。`name` 為選用參數。若省略，提供者會從電子郵件地址產生顯示名稱。傳回值與 `signIn()` 相同。

#### `isSignUpEnabled()` {/* #issignupenabled */}

```typescript
const enabled = auth.isSignUpEnabled()
```

傳回設定的 `signUpEnabled` 值。

### 會話方法 {/* #session-methods */}

#### `createSession()` {/* #createsession */}

```typescript
const session = await auth.createSession(userId, metadata)
```

建立 ID 自動產生、有效期為七天的標準化 Mastra 工作階段，不會建立遠端 Neon Auth 工作階段。

#### `validateSession()` {/* #validatesession */}

```typescript
const session = await auth.validateSession(sessionId)
```

驗證 Neon Auth 工作階段權杖並傳回標準化的 Mastra 工作階段；若工作階段無效，則傳回 `null`。

#### `refreshSession()` {/* #refreshsession */}

```typescript
const session = await auth.refreshSession(sessionId)
```

透過 Neon Auth 驗證工作階段。達到設定的更新間隔時，Neon Auth 會自動重新整理工作階段。

#### `destroySession()` {/* #destroysession */}

```typescript
const sessionId = auth.getSessionIdFromRequest(request)
if (sessionId) await auth.destroySession(sessionId)
```

傳入 `getSessionIdFromRequest()` 取得的已簽署工作階段 Cookie 值，而不是 `validateSession()` 傳回的 `id`。`destroySession()` 會嘗試透過 Neon Auth 登出端點撤銷該工作階段。網路錯誤或非 2xx 回應可能使工作階段維持有效，而且此方法不會因這些失敗而擲回錯誤。Mastra 傳送 `getClearSessionHeaders()` 傳回的標頭時，只會清除 Mastra 主機上相符的 Cookie，不會清除另一台 Neon Auth 主機上的 Cookie。因此，從 Studio 登出後，獨立的 Neon Auth 工作階段可能仍然有效。

撤銷工作階段不會使已簽發的 JWT 失效。通過 JWT 驗證的 Bearer Token 仍可用於身分驗證，因為驗證程序不會檢查 Neon Auth 工作階段。JWT 驗證也不要求包含到期時間宣告，因此沒有該宣告的權杖可能在登出後繼續可用。

### 方法 {/* #methods */}

#### `getRoles()` {/* #getroles */}

```typescript
const roles = await rbac.getRoles(user)
```

若提供 `getUserRoles`，則傳回該函式提供的角色。否則，如果設定 `organizationId` 或工作階段有作用中組織，就使用使用者的工作階段 Cookie 從 Neon Auth 讀取並傳回其組織角色；非成員沒有角色。若沒有組織，則傳回使用者在 Neon Auth 中的角色，例如 `user` 或 `admin`。

Bearer JWT 請求沒有工作階段，因此除非提供 `getUserRoles`，否則不會取得角色。JWT 的 `role` 宣告（`authenticated`）絕不會用作 Mastra 角色。

#### `hasRole()` {/* #hasrole */}

```typescript
const allowed = await rbac.hasRole(user, 'admin')
```

檢查使用者是否具有指定角色。

#### `getPermissions()` {/* #getpermissions */}

```typescript
const permissions = await rbac.getPermissions(user)
```

透過 `roleMapping` 解析使用者角色，並傳回 Mastra 權限模式。

#### `hasPermission()` {/* #haspermission */}

```typescript
const allowed = await rbac.hasPermission(user, 'agents:read')
```

檢查解析出的權限是否允許所要求的權限。

#### `hasAllPermissions()`和`hasAnyPermission()` {/* #hasallpermissions-and-hasanypermission */}

```typescript
const canReadAndRun = await rbac.hasAllPermissions(user, ['agents:read', 'agents:execute'])
const canReadAnything = await rbac.hasAnyPermission(user, ['agents:read', 'workflows:read'])
```

檢查使用者是否具有要求的全部權限或至少一項權限。

#### `getAvailableRoles()` {/* #getavailableroles */}

```typescript
const roles = await rbac.getAvailableRoles()
```

傳回設定的所有角色名稱，但不包含 `_default`。

#### `getRolePermissions()` {/* #getrolepermissions */}

```typescript
const permissions = await rbac.getRolePermissions('member')
```

解析為角色設定的權限模式。
