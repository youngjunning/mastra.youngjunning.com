# RedisStreamsPubSub

`RedisStreamsPubSub`是一個[`PubSub`](/reference/pubsub/base)實施支持[Redis 串流](https://redis.io/docs/latest/develop/data-types/streams/)。它跨進程和主機傳遞事件，具有持久性、消費者群組和失敗時的重新傳遞。它還實現了[`LeaseProvider`](/reference/pubsub/lease-provider)。訊號層可以為跨實例的每個資源選擇一個擁有者，這可以讓訊號在分散式和無伺服器部署中協調運作。

將其用於多個服務共用事件流的分散式部署。對於單一進程交付，請使用[`EventEmitterPubSub`](/reference/pubsub/event-emitter). For Google Cloud, use [`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub).

每個主題映射到一個 Redis 流鍵。組訂閱使用 Redis 使用者群組。成員循環分擔工作。沒有群組的訂閱會建立一個私人消費者群組。每個訂閱者都會收到每個事件。

`RedisStreamsPubSub`是一種拉式傳輸：消費者使用以下方式讀取事件`XREADGROUP`, so Mastra runs an orchestration worker to read on its behalf.

## 安裝 {/* #installation */}

```bash npm2yarn
npm install @mastra/redis-streams
```

需要 Redis 7.0 或更高版本。回收循環依賴`XCLAIM` removing trimmed entries from the pending list, which earlier versions don't do.

## 使用範例 {/* #usage-example */}

提供 Redis 連線 URL。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'

export const mastra = new Mastra({
  pubsub: new RedisStreamsPubSub({
    url: 'redis://localhost:6379',
  }),
})
```

### Redis集群 {/* #redis-cluster */}

經過`cluster` instead of `url`/`redisOptions` to connect to a Redis Cluster (for example, AWS ElastiCache with cluster mode enabled). The options are forwarded to `createCluster()` from `redis`.

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'

export const mastra = new Mastra({
  pubsub: new RedisStreamsPubSub({
    cluster: {
      rootNodes: [{ url: 'redis://node-1:6379' }, { url: 'redis://node-2:6379' }],
    },
  }),
})
```

### 帶上自己的客戶 {/* #bring-your-own-client */}

若要自行控制客戶端建構（TLS、憑證Provider等），請傳遞未連線的`redis` client as `client`. The pubsub uses it as its writer and calls `client.duplicate()` for each subscription's blocking reader. Every connection stays distinct. The pubsub owns the client's lifecycle (it connects on first use and quits it on `close()`), so don't share it with the rest of your app.

```typescript title="src/mastra/index.ts"
import { RedisStreamsPubSub } from '@mastra/redis-streams'
import { createClient } from 'redis'

const pubsub = new RedisStreamsPubSub({
  client: createClient({ url: process.env.REDIS_URL, socket: { tls: true } }),
})
```

## 方法 {/* #methods */}

`RedisStreamsPubSub`實施[`PubSub`](/reference/pubsub/base) contract. The methods below have behavior specific to this implementation.

### `subscribe(topic, cb, options?)` {/* #subscribetopic-cb-options */}

訂閱主題。和`options.group`, members of the group share events through a Redis consumer group. Without a group, the subscriber receives every event through a private consumer group.

放`options.startFrom` to `"latest"` to skip retained entries when Redis creates the consumer group. The default, `"earliest"`, reads retained entries first. This option doesn't reset an existing group's checkpoint.

```typescript
await pubsub.subscribe(
  'workflow.events',
  (event, ack, nack) => {
    console.log(event)
  },
  { group: 'live-workers', startFrom: 'latest' },
)
```

### `flush()` {/* #flush */}

等待正在進行的發布完成。

```typescript
await pubsub.flush()
```

### `clearTopic(topic)` {/* #cleartopictopic */}

刪除主題的串流及其上的每個使用者群組，從而釋放已完成的主題否則將保留的記憶體。當運行達到最終狀態時，Mastra 的運行生命週期（持久Agent和事件工作流引擎）會自動呼叫此函數。只有當沒有人會再次閱讀該主題時才調用它。這是盡最大努力並且從不拋出。故障記錄在警告等級。當串流被刪除時仍然附加的訂戶可以自行恢復，但會遺失已刪除的條目。

自動清理需要`@mastra/core` and `@mastra/redis-streams` versions that both support `clearTopic`: the runtime routes the call through its caching layer, so upgrade the two packages together to get end-of-run stream deletion.

並非每個主題都能達到`clearTopic` call. Topics without a defined end of life (per-conversation streams, application feeds) are never cleared, and a stream that misses its cleanup (for example, a crashed run) is never retried. The `streamIdleTtlMs` sliding TTL (7 days by default) reclaims those streams once they go idle. Deleting a thread with `Memory.deleteThread()` also clears that thread's stream.

```typescript
await pubsub.clearTopic('workflow.events.run-123')
```

### `trimTopic(topic, { runId, producedBefore? })` {/* #trimtopictopic--runid-producedbefore- */}

透過串流進行分頁`XRANGE` and runs `XDEL` for every entry published with `runId`. With `producedBefore`, only entries produced at or before that time are deleted, skipping approval and suspension prompts. Mastra uses this to trim a long run each time its messages are saved. Mastra calls this once a thread run's messages are persisted, so an idle thread's stream empties instead of growing to `maxLen`. Because entries are matched by `runId`, a run resumed after a restart also removes the entries it published before the restart. Entries from other runs, including those from other processes, are never touched. Best-effort. Failures are logged at warn level.

```typescript
await pubsub.trimTopic('agent.thread.thread-abc', { runId: 'run-123' })
```

### `close()` {/* #close */}

關閉 Redis 連線並停止所有訂閱。在正常關閉期間呼叫此方法。

```typescript
await pubsub.close()
```

## Redis配置 {/* #redis-configuration */}

放`maxmemory-policy` to `noeviction` on the Redis instance. Consumer groups, unacknowledged entries, and [lease keys](#distributed-leasing) are live state, not cache. Under any evicting policy, Redis deletes them when it reaches `maxmemory`: lease keys and streams with a TTL are eviction candidates under `volatile-*` policies, and every key is a candidate under `allkeys-*` policies. Lost leases let two processes run the same thread, and evicted streams silently drop events.

和`noeviction`, Redis rejects writes instead of deleting data when memory runs out, so size `maxmemory` for your traffic and rely on `streamIdleTtlMs` to reclaim idle streams. Managed services often default to an evicting policy (Amazon ElastiCache defaults to `volatile-lru`), so check the setting explicitly.

什麼時候`maxmemory` is set and the policy isn't `noeviction`, `RedisStreamsPubSub` logs a warning once after it first connects. It reads the policy with `INFO memory`, because many managed services block `CONFIG GET`.

```bash
redis-server --maxmemory-policy noeviction
```

### 回收沒有 TTL 創建的串流 {/* #reclaim-streams-created-without-a-ttl */}

寫入的流`streamIdleTtlMs` was `0`, including by versions before the 7-day default, have no TTL. They stay in Redis until a new write gives them one. To reclaim them:

1. 將實例切換到`noeviction` first. Under a `volatile-*` policy, adding a TTL makes a live stream an eviction candidate.
2. 使用預設 TTL 的版本或明確部署寫入此 Redis 的每個進程`streamIdleTtlMs` greater than `0`. A write with expiry turned off doesn't refresh an existing TTL, so a stream that an old writer still uses would expire mid-use.
3. 為沒有 TTL 的每個流指定其應有的到期時間：上次寫入後 7 天。空閒時間超過該時間的串流會立即過期，從而立即釋放記憶體。`PEXPIRE` runs even on an instance that's rejecting writes because it's out of memory.

```bash
# Replace mastra:topic with your keyPrefix, and add your connection flags
# (-h, -p, -a, --tls) to every redis-cli call. On a cluster, run it against each primary.
TTL_MS=604800000
NOW_MS=$(redis-cli time | awk 'NR == 1 { s = $1 } NR == 2 { printf "%.0f", s * 1000 + $1 / 1000 }')
redis-cli --scan --pattern 'mastra:topic:*' | while read -r key; do
  [ "$(redis-cli type "$key")" = "stream" ] || continue
  [ "$(redis-cli pttl "$key")" = "-1" ] || continue
  last_ms=$(redis-cli --raw xinfo stream "$key" | awk 'prev == "last-generated-id" { split($0, id, "-"); print id[1]; exit } { prev = $0 }')
  [ -n "$last_ms" ] || continue
  if [ "$last_ms" = "0" ]; then
    remaining=$TTL_MS # never written to, only subscribed
  else
    remaining=$(( TTL_MS - (NOW_MS - last_ms) ))
    [ "$remaining" -lt 1 ] && remaining=1
    [ "$remaining" -gt "$TTL_MS" ] && remaining=$TTL_MS
  fi
  redis-cli pexpire "$key" "$remaining" > /dev/null
done
```

此循環僅涉及沒有 TTL 的流，因此重複運行是安全的。在步驟 2 之後，仍在使用的流會保留其數據，因為每次寫入都會刷新 TTL。

## 重新投遞和回收 {/* #redelivery-and-reclaim */}

當訂戶呼叫時`nack`, the event is republished with an incremented `deliveryAttempt` and the original is acknowledged. Once an event reaches `maxDeliveryAttempts`, it's dropped instead of redelivered. Separately, each subscription periodically reclaims events that an earlier consumer in the group read but never acknowledged, controlled by `reclaimIntervalMs` and `reclaimIdleMs`.

訂閱永遠不會回收自己的處理程序仍在處理的事件，因此不會為相同事件呼叫兩次慢速處理程序。如果處理程序掛起，則該群組中的另一個使用者會在該事件閒置一段時間後回收該事件`reclaimIdleMs`. In a single-consumer group there's no sibling to do that, so set `inFlightTimeoutMs` to have the subscription nack the event itself after that long.

### Agent工人接管事件 {/* #evented-agent-worker-takeover */}

使用 Postgres 存儲，分散式事件Agent程式透過 Redis 發布工作人員編排事件。如果一個工作執行緒在確認事件之前退出，另一個工作執行緒可以回收該事件並完成執行，同時原始 API 程序保持活動狀態。配置 API 流程`MASTRA_WORKERS=false` and worker processes with `MASTRA_WORKERS=orchestration`. All processes must share the same Postgres database, Redis connection settings, and `keyPrefix`.

保持`reclaimIdleMs` above 30 seconds (the default is 60 seconds). A lower value can reclaim an event while the stopped worker still holds the step, causing the event to be acknowledged without running.

在舊版本上啟動的運行可以在升級後完成，但不保證崩潰恢復。沒有發生標識符的已保存步驟將保留其現有的不受保護的行為。其他儲存適配器在工作進程上保留分散式內部編排。

被中斷的步驟可以再次執行，因此使外部副作用具有冪等性。已完成的步驟發生受到保護，不會發生過時的重新交付，並且已完成的循環迭代會重複使用其保存的結果和循環決策。即使在以下情況下，受保護的執行也會保留復原所需的記錄：`shouldPersistSnapshot` returns `false`. Resume, time travel, restart races, and individual `foreach` items aren't covered by these occurrence guards. See [make tools safe to repeat](/docs/harness/durable-agents#make-tools-safe-to-repeat) for agent tools.

## 分散式租賃 {/* #distributed-leasing */}

`RedisStreamsPubSub`實施[`LeaseProvider`](/reference/pubsub/lease-provider) contract on top of the same Redis connection. The [signals runtime](/docs/signals/overview) uses it to elect a single owner (usually per thread key) so that across instances only one process wakes and runs the agent, and others route follow-up work to the holder. This is what makes signals work on serverless and multi-instance deployments; without a shared lease, each instance would start its own competing run.

租賃金鑰在相同的命名空間下`keyPrefix` as topics, as `<keyPrefix>:lease:<key>`. All operations are atomic: `acquireLease` uses `SET NX PX` and refreshes its own TTL idempotently, while `releaseLease`, `renewLease`, and `transferLease` use Lua scripts that check ownership before mutating, so a concurrent renewal from another owner is never clobbered.

您不直接呼叫這些方法。配置`RedisStreamsPubSub` as the `pubsub` backend is enough for the runtime to detect and use the capability. See [`LeaseProvider`](/reference/pubsub/lease-provider) for the full method contract.
