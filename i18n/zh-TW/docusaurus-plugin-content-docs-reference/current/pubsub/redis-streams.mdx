# RedisStreamsPubSub

`RedisStreamsPubSub` 是依據 [`PubSub`](/reference/pubsub/base) 契約、以 [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/) 為底層的實作。它可跨處理程序與主機傳遞事件，支援持久化、消費者群組及失敗後重新投遞，也實作了 [`LeaseProvider`](/reference/pubsub/lease-provider)。信號層能跨執行個體為每項資源選出唯一持有者，讓分散式及無伺服器部署中的執行作業得以協調。

多個服務共用事件串流的分散式部署適合使用此實作。單一處理程序內的事件傳遞請使用 [`EventEmitterPubSub`](/reference/pubsub/event-emitter)；Google Cloud 環境請使用 [`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub)。

每個主題對應一個 Redis Stream 鍵。指定群組的訂閱使用 Redis 消費者群組，成員輪流分攤事件；未指定群組的訂閱會建立專屬消費者群組，因此每位訂閱者都會收到所有事件。

`RedisStreamsPubSub` 採用拉取式傳輸：消費者透過 `XREADGROUP` 讀取事件，因此 Mastra 會執行協調工作者代為讀取。

## 安裝 {/* #installation */}

```bash npm2yarn
npm install @mastra/redis-streams
```

需要 Redis 7.0 或更新版本。回收迴圈依賴 `XCLAIM` 將已修剪的項目從待處理清單移除；較舊版本不會執行這項操作。

## 使用範例 {/* #usage-example */}

提供 Redis 連線 URL。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'

export const mastra = new Mastra({
  pubsub: new RedisStreamsPubSub({
    url: 'redis://localhost:6379',
  }),
})
```

### Redis 叢集 {/* #redis-cluster */}

連線至 Redis 叢集（例如啟用叢集模式的 AWS ElastiCache）時，請傳入 `cluster`，而非 `url`/`redisOptions`。這些選項會傳給 `createCluster()`（来自 `redis`）。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'

export const mastra = new Mastra({
  pubsub: new RedisStreamsPubSub({
    cluster: {
      rootNodes: [{ url: 'redis://node-1:6379' }, { url: 'redis://node-2:6379' }],
    },
  }),
})
```

### 使用自行建立的用戶端 {/* #bring-your-own-client */}

若要自行控制用戶端的建立方式（例如 TLS 或憑證提供者），請將尚未連線的 `redis` 用戶端傳入 `client`。PubSub 會用它寫入資料，並為每個訂閱呼叫 `client.duplicate()`，建立各自獨立的阻塞讀取連線。PubSub 管理此用戶端的生命週期：首次使用時連線，呼叫 `close()` 時結束。因此請勿與應用程式其他部分共用。

```typescript title="src/mastra/index.ts"
import { RedisStreamsPubSub } from '@mastra/redis-streams'
import { createClient } from 'redis'

const pubsub = new RedisStreamsPubSub({
  client: createClient({ url: process.env.REDIS_URL, socket: { tls: true } }),
})
```

## 方法 {/* #methods */}

`RedisStreamsPubSub` 實作 [`PubSub`](/reference/pubsub/base) 契約。以下方法具有此實作特有的行為。

### `subscribe(topic, cb, options?)` {/* #subscribetopic-cb-options */}

訂閱主題。設定 `options.group` 時，群組成員透過 Redis 消費者群組分攤事件；未設定時，訂閱者透過專屬消費者群組接收每個事件。

建立 Redis 消費者群組時，將 `options.startFrom` 設為 `"latest"` 可略過保留的舊項目。預設值 `"earliest"` 會先讀取舊項目。此選項不會重設現有群組的讀取進度。

```typescript
await pubsub.subscribe(
  'workflow.events',
  (event, ack, nack) => {
    console.log(event)
  },
  { group: 'live-workers', startFrom: 'latest' },
)
```

### `flush()` {/* #flush */}

等待進行中的發布操作完成。

```typescript
await pubsub.flush()
```

### `clearTopic(topic)` {/* #cleartopictopic */}

刪除主題的 Stream 及其所有消費者群組，釋放已結束主題占用的記憶體。Mastra 的執行生命週期（持久化 Agent 與事件驅動 Workflow 引擎）會在執行進入終止狀態時自動呼叫。只有確定不會再有讀取者時才自行呼叫。此操作採盡力執行方式且不會擲出例外；失敗會以 warn 等級記錄。刪除 Stream 時仍保持訂閱的用戶端會自行復原，但會錯過已刪除的項目。

自動清理需要 `@mastra/core` 與 `@mastra/redis-streams` 都使用支援 `clearTopic` 的版本。執行階段會透過快取層轉送呼叫，因此必須一併升級兩個套件，才能在執行結束時刪除 Stream。

並非所有主題都會呼叫 `clearTopic`。每段對話的 Stream、應用程式動態等沒有明確終點的主題不會自動清除；若清理漏執行（例如執行時當機），也不會重試。預設 7 天的 `streamIdleTtlMs` 滑動 TTL 會在閒置後回收這些 Stream。刪除執行緒時，`Memory.deleteThread()` 也會清除對應的 Stream。

```typescript
await pubsub.clearTopic('workflow.events.run-123')
```

### `trimTopic(topic, { runId, producedBefore? })` {/* #trimtopictopic--runid-producedbefore- */}

使用 `XRANGE` 分頁掃描 Stream，執行 `XDEL` 刪除每個由 `runId` 發布的項目。指定 `producedBefore` 時，只刪除在該時間點或之前產生的項目，略過核准與暫停提示。Mastra 每次儲存長時間執行的訊息時會以此方法修剪 Stream；執行緒執行的訊息持久化後也會呼叫，讓閒置執行緒的 Stream 清空，而非增長至 `maxLen`。由於依 `runId` 比對，重新啟動後恢復的執行也會移除重啟前發布的項目。其他執行（包括其他處理程序）的項目不受影響。操作採盡力執行方式；失敗會以 warn 等級記錄。

```typescript
await pubsub.trimTopic('agent.thread.thread-abc', { runId: 'run-123' })
```

### `close()` {/* #close */}

關閉 Redis 連線並停止所有訂閱。在正常關閉期間呼叫此方法。

```typescript
await pubsub.close()
```

## Redis 設定 {/* #redis-configuration */}

請將 Redis 執行個體的 `maxmemory-policy` 設為 `noeviction`。消費者群組、尚未確認的項目及[租約鍵](#distributed-leasing)屬於即時狀態，不能視為快取。任何逐出策略下，Redis 達到 `maxmemory` 時都可能刪除這些資料：`volatile-*` 可能逐出有 TTL 的租約鍵與 Stream，`allkeys-*` 則可能逐出任何鍵。租約遺失會讓兩個處理程序同時執行同一執行緒；Stream 遭逐出則會在沒有提示的情況下遺失事件。

使用 `noeviction` 時，記憶體用盡後 Redis 會拒絕寫入，而非刪除資料。請依流量設定足夠的 `maxmemory`，並透過 `streamIdleTtlMs` 回收閒置 Stream。託管服務常預設使用逐出策略（Amazon ElastiCache 預設為 `volatile-lru`），因此請明確檢查設定。

如果已設定 `maxmemory`，但策略不是 `noeviction`，`RedisStreamsPubSub` 會在首次連線後記錄一次警告。它透過 `INFO memory` 讀取策略，因為許多託管服務會封鎖 `CONFIG GET`。

```bash
redis-server --maxmemory-policy noeviction
```

### 回收建立時未設定 TTL 的 Stream {/* #reclaim-streams-created-without-a-ttl */}

在 `streamIdleTtlMs` 為 `0` 時寫入的 Stream（包括引入 7 天預設值前的版本所寫入者）沒有 TTL。它們會留在 Redis，直到後續寫入為其設定 TTL。回收步驟如下：

1. 先將執行個體切換為 `noeviction`。在 `volatile-*` 策略下，替使用中的 Stream 加上 TTL 會使其成為逐出候選。
1. 將所有寫入此 Redis 的處理程序升級至預設啟用 TTL 的版本，或明確設定`streamIdleTtlMs` 大於 `0`。停用到期機制的寫入不會更新既有 TTL；若舊版寫入者仍在使用 Stream，它可能在使用中途過期。
1. 為每個沒有 TTL 的 Stream 設定原本應有的到期時間：最後一次寫入後 7 天。閒置超過 7 天的 Stream 會立即到期並釋放記憶體。即使執行個體因記憶體不足而拒絕寫入，`PEXPIRE` 仍可執行。

```bash
# Replace mastra:topic with your keyPrefix, and add your connection flags
# (-h, -p, -a, --tls) to every redis-cli call. On a cluster, run it against each primary.
TTL_MS=604800000
NOW_MS=$(redis-cli time | awk 'NR == 1 { s = $1 } NR == 2 { printf "%.0f", s * 1000 + $1 / 1000 }')
redis-cli --scan --pattern 'mastra:topic:*' | while read -r key; do
  [ "$(redis-cli type "$key")" = "stream" ] || continue
  [ "$(redis-cli pttl "$key")" = "-1" ] || continue
  last_ms=$(redis-cli --raw xinfo stream "$key" | awk 'prev == "last-generated-id" { split($0, id, "-"); print id[1]; exit } { prev = $0 }')
  [ -n "$last_ms" ] || continue
  if [ "$last_ms" = "0" ]; then
    remaining=$TTL_MS # never written to, only subscribed
  else
    remaining=$(( TTL_MS - (NOW_MS - last_ms) ))
    [ "$remaining" -lt 1 ] && remaining=1
    [ "$remaining" -gt "$TTL_MS" ] && remaining=$TTL_MS
  fi
  redis-cli pexpire "$key" "$remaining" > /dev/null
done
```

迴圈只處理沒有 TTL 的 Stream，因此可以重複執行。完成步驟 2 後，仍在使用的 Stream 每次寫入都會更新 TTL，資料便能保留。

## 重新投遞與回收 {/* #redelivery-and-reclaim */}

訂閱者呼叫 `nack` 時，事件會以遞增的 `deliveryAttempt` 重新發布，原事件則會獲得確認。達到 `maxDeliveryAttempts` 後，事件會被捨棄，不再重新投遞。此外，每個訂閱會定期回收群組中先前消費者已讀取但未確認的事件；回收頻率與閒置門檻由 `reclaimIntervalMs` 及 `reclaimIdleMs` 控制。

訂閱不會回收其處理器仍在處理的事件，因此處理緩慢不會使同一事件在該處理器上執行兩次。若處理器卡住，群組中其他消費者可在事件閒置達 `reclaimIdleMs` 後回收。單一消費者群組沒有其他成員，因此應設定 `inFlightTimeoutMs`，讓訂閱在逾時後自行對事件執行 nack。

### 事件驅動 Agent 的工作者接手 {/* #evented-agent-worker-takeover */}

使用 Postgres 儲存時，分散式事件驅動 Agent 會透過 Redis 發布工作者協調事件。若工作者在確認事件前退出，其他工作者可回收事件並完成執行，而原 API 處理程序仍保持運作。API 處理程序應設定 `MASTRA_WORKERS=false`，工作者處理程序應設定 `MASTRA_WORKERS=orchestration`。所有處理程序必須共用相同的 Postgres 資料庫、Redis 連線設定與 `keyPrefix`。

請將 `reclaimIdleMs` 維持在 30 秒以上（預設為 60 秒）。若設定過低，已停止的工作者仍持有步驟時事件就可能被回收，導致事件被確認卻未執行。

舊版本啟動的執行作業在升級後仍可完成，但無法保證當機復原。沒有 occurrence 識別碼的已儲存步驟仍維持原本未受保護的行為。其他儲存配接器仍由工作者處理程序負責分散式內部協調。

中斷的步驟可能再次執行，因此外部副作用應具備冪等性。已完成的步驟 occurrence 會避免受到過時重新投遞的影響；已完成的迴圈迭代則會重用已儲存的結果與迴圈判斷。即使 `shouldPersistSnapshot` 回傳 `false`，受保護的執行仍會持久化復原所需的紀錄。恢復執行、時間旅行、重新啟動競態，以及個別 `foreach` 項目，並不受這些 occurrence 保護。Agent 工具請參閱[讓工具可安全地重複執行](/docs/harness/durable-agents#make-tools-safe-to-repeat)。

## 分散式租賃 {/* #distributed-leasing */}

`RedisStreamsPubSub` 在同一 Redis 連線上實作 [`LeaseProvider`](/reference/pubsub/lease-provider) 契約。[信號執行階段](/docs/signals/overview)透過它選出唯一持有者（通常依執行緒鍵），確保跨執行個體只有一個處理程序喚醒並執行 Agent，其他處理程序則把後續工作交給持有者。共用租約使信號可在無伺服器及多執行個體部署中運作；若沒有共用租約，每個執行個體都會啟動互相競爭的執行作業。

租約鍵與主題共用 `keyPrefix` 命名空間，格式為 `<keyPrefix>:lease:<key>`。所有操作都是原子操作：`acquireLease` 使用 `SET NX PX`，並以冪等方式更新自身 TTL；`releaseLease`、`renewLease` 與 `transferLease` 則使用先檢查所有權再修改的 Lua 指令碼，因此不會覆蓋其他持有者同時進行的續約。

不需要直接呼叫這些方法。只要將 `RedisStreamsPubSub` 設為 `pubsub` 後端，執行階段就會偵測並使用此功能。完整的方法契約請參閱 [`LeaseProvider`](/reference/pubsub/lease-provider)。
