# MCPServer

`MCPServer` 類別可透過模型上下文協定（MCP）伺服器公開現有的 Mastra Tool 和 Agent。Cursor、Windsurf 或 Claude Desktop 等 MCP 用戶端都能連線到伺服器，讓 Agent 使用這些功能。

如果只在 Mastra 應用程式內直接使用 Tool 或 Agent，可以省略建立 MCP 伺服器的步驟。這個 API 專門用於將 Mastra Tool 和 Agent 提供給*外部* MCP 用戶端。

若要直接公開 Mastra 應用程式裡的所有 Agent、Workflow 和 Tool，可使用 `/api/mcp` 的[內建 MCP 伺服器](/docs/server/mcp)。它會依呼叫端產生 Tool 清單，並對每次呼叫執行相應 HTTP 路由的身分驗證和權限檢查。若要搭配自訂提示詞和資源發布指定的 Tool 和 Agent，或透過 stdio 提供服務，請使用 `MCPServer`。

它支援 MCP `2026-07-28` 版的兩種[傳輸方式：stdio（子行程）和 Streamable HTTP](https://modelcontextprotocol.io/docs/concepts/transports)。

:::note
若要從 `@mastra/mcp` 1.x 升級，請參閱[移轉指南](/reference/migrations/mcp-v2)。
:::

## 建構函式 {/* #constructor */}

建立 `MCPServer` 時，請提供伺服器的基本資訊及它要提供的 Tool。也可以指定要以 Tool 形式公開的 Agent。

```typescript
import { Agent } from '@mastra/core/agent'
import { createTool } from '@mastra/core/tools'
import { MCPServer } from '@mastra/mcp'
import { z } from 'zod'
import { dataProcessingWorkflow } from '../workflows/dataProcessingWorkflow'

const myAgent = new Agent({
  id: 'my-example-agent',
  name: 'MyExampleAgent',
  description: 'A generalist to help with basic questions.',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

const weatherTool = createTool({
  id: 'getWeather',
  description: 'Gets the current weather for a location.',
  inputSchema: z.object({ location: z.string() }),
  execute: async inputData => `Weather in ${inputData.location} is sunny.`,
})

const server = new MCPServer({
  id: 'my-custom-server',
  name: 'My Custom Server',
  version: '1.0.0',
  description: 'A server that provides weather data and agent capabilities',
  instructions:
    'Use the available tools to help users with weather information and data processing tasks.',
  tools: { weatherTool },
  agents: { myAgent }, // this agent will become tool "ask_myAgent"
  workflows: {
    dataProcessingWorkflow, // this workflow will become tool "run_dataProcessingWorkflow"
  },
})
```

## Tool 的結構描述與結構化結果 {/* #tool-schemas-and-structured-results */}

MCP Tool 會以 JSON Schema 2020-12 格式公布輸入與輸出的結構描述，並在 `$schema` 宣告所用的方言。對外公布的 Mastra Tool 結構描述會保留支援的參照、組合關鍵字和元組結構（`prefixItems`）。

有 `outputSchema` 的 Tool 可傳回任何 JSON 值，包括物件、陣列、字串、數值、布林值或 `null`。伺服器直接將該值以 `structuredContent` 傳送，無須另外包成物件。呼叫成功時，伺服器會依 Tool 的輸出結構描述驗證結構化輸出，再傳回結果。

## Tool 結果 {/* #tool-results */}

伺服器預設會以單一文字區塊將 Tool 的輸出傳送給 MCP 用戶端。字串會原樣傳送，其他值則以 JSON 格式傳送。如果 Tool 定義了 `outputSchema`，還會以 `structuredContent` 傳回該值。

可使用 `toolResult` 選項傳送 Tool 提供給模型的輸出，或在傳送前改寫結果。

```typescript title="src/mastra/mcp/server.ts"
import { MCPServer } from '@mastra/mcp'
import { screenshotTool } from '../tools/screenshot'

const server = new MCPServer({
  id: 'media-server',
  name: 'Media Server',
  version: '1.0.0',
  tools: { screenshotTool },
  toolResult: {
    modelOutput: true,
  },
})
```

:::warning

`@mastra/mcp` 的下一個主要版本會將 `modelOutput` 的預設值改為 `true`。如果 MCP 用戶端會剖析定義了 `toModelOutput` 的 Tool 所傳回的原始 JSON 文字，請現在設定 `modelOutput: false`，以維持目前的行為。

:::

設定 `modelOutput: true` 後，伺服器會依下表將 `toModelOutput` 的值轉成 MCP 內容：

| `toModelOutput` 的值 | MCP 結果 |
| - | - |
| `{ type: 'text', value }` | 文字區塊 |
| `{ type: 'json', value }` | 包含 JSON 值的文字區塊 |
| `{ type: 'error-text' }` 或 `{ type: 'error-json' }` | 帶有 `isError: true` 的文字區塊 |
| `content` 中的 `text` 項目 | 文字區塊 |
| `content` 中的 `media`、`image-data` 或 `file-data` 項目 | `image/*` 轉為 `image` 區塊，`audio/*` 轉為 `audio` 區塊，其餘則轉為內含 `blob` 的嵌入式 `resource` |
| `content` 中帶有 `data:` URI 的 `image-url` 或 `file-url` 項目 | 與媒體資料的處理方式相同 |
| `content` 中帶有遠端網址的 `image-url` 或 `file-url` 項目 | 包含網址的文字區塊 |

Tool 有 `outputSchema` 時，結果會保留 `structuredContent`，並將其 JSON 文字區塊放在轉換後的區塊之前。如果 `toModelOutput` 或 `transform` 擲出例外，用戶端會收到 Tool 的錯誤結果。

可使用 `transform` 轉送已符合 MCP 格式的結果，例如透過 `MCPClient` 代理的 Tool 所傳回的結果：

```typescript title="src/mastra/mcp/proxy-server.ts"
import { MCPClient, MCPServer, type MCPServerToolResultContext } from '@mastra/mcp'

const upstream = new MCPClient({
  servers: { files: { url: new URL('https://files.example.com/mcp') } },
})

const server = new MCPServer({
  id: 'proxy-server',
  name: 'Proxy Server',
  version: '1.0.0',
  tools: await upstream.listTools(),
  toolResult: {
    // Unstructured upstream tools return the upstream MCP result as their output
    transform: ({ output }) => {
      const upstreamResult = output as MCPServerToolResultContext['result']
      return Array.isArray(upstreamResult?.content) ? upstreamResult : undefined
    },
  },
})
```

## 將 Agent 公開為 Tool {/* #exposing-agents-as-tools */}

在設定的 `agents` 屬性中提供 Mastra Agent 後，`MCPServer` 會自動將它們公開為可呼叫的 Tool。

* **Tool 命名**。每個 Agent 都會轉換為名為 `ask_<agentKey>` 的 Tool，其中 `<agentKey>` 是該 Agent 在 `agents` 物件中的鍵。例如，設定 `agents: { myAgentKey: myAgentInstance }` 會建立名為 `ask_myAgentKey` 的 Tool。

* **Tool 的行為**
  * **說明**採用「向 Agent `<AgentName>` 提問。Agent 的原始指令：`<agent description>`」的格式。
  * **輸入**是一個物件引數，包含字串屬性 `message`，例如 `{ message: "Your question for the agent" }`。
  * **執行**時，Tool 會以提供的 `query` 呼叫對應 Agent 的 `generate()` 方法。
  * **輸出**直接採用 Agent 的 `generate()` 方法傳回的結果。

* **名稱衝突**。如果在 `tools` 中明確定義的 Tool 與 Agent 產生的 Tool 同名，例如同時有名為 `ask_myAgentKey` 的 Tool 和鍵為 `myAgentKey` 的 Agent，則*明確定義的 Tool 優先*。伺服器會略過該 Agent 的轉換並記錄警告。

MCP 用戶端可以像呼叫其他 Tool 一樣，透過自然語言查詢與 Agent 互動。

### 將 Agent 轉換為 Tool {/* #agent-to-tool-conversion */}

在設定的 `agents` 屬性中提供 Agent 後，`MCPServer` 會為每個 Agent 自動建立相應的 Tool。Tool 的名稱為 `ask_<agentIdentifier>`，其中 `<agentIdentifier>` 是 `agents` 物件中的鍵。

產生的 Tool 說明採用「向 Agent `<agent.name>` 提問。Agent 說明：`<agent.description>`」的格式。

若要將 Agent 轉換為 Tool，建立 Agent 執行個體時**必須**在設定中提供非空的 `description` 字串，例如 `new Agent({ id: 'my-agent', name: 'myAgent', description: 'This agent does X.', ... })`。如果傳給 `MCPServer` 的 Agent 未設定 `description` 或該字串為空，建立 `MCPServer` 執行個體時會擲出錯誤，導致伺服器設定失敗。

用戶端可透過 MCP 使用 Agent 的生成能力，直接向 Agent 提問。

### 在 Tool 中存取 MCP 上下文 {/* #accessing-mcp-context-in-tools */}

透過 `MCPServer` 公開的 Tool 會從 `context.mcp` 收到目前請求的協定上下文：

| 成員 | 說明 |
| - | - |
| `context.mcp.extra.signal` | 用戶端取消請求或中斷連線時會觸發中止訊號 |
| `context.mcp.extra.requestId` | 請求的 JSON-RPC ID |
| `context.mcp.extra.authInfo` | 傳輸層驗證取得的身分資訊，請參閱身分驗證上下文一節 |
| `context.mcp.extra._meta` | 請求的中繼資料，包括追蹤標頭、用戶端選擇接收的日誌層級及進度權杖 |
| `context.mcp.log()` | 將日誌訊息傳給發出呼叫的用戶端，請參閱日誌記錄一節 |
| `context.mcp.progress()` | 向發出呼叫的用戶端回報進度，請參閱進度通知一節 |
| `context.mcp.protocolVersion` | `'2026-07-28'` |

同一筆請求也會將 `authInfo`、`mapAuthInfoToUser` 傳回的 `user`，以及用戶端送出的 W3C `traceContext` 寫入可信任的應用程式上下文 `context.requestContext`。當 MCP 用戶端透過 `ask_<agent>` 向 Agent 提問時，請求上下文會轉交給 Agent，而由該 Agent 呼叫的 Tool 不會收到 `context.mcp`。如果 Tool 可由用戶端直接呼叫，也可由 Agent 呼叫，可按下例從請求上下文讀取驗證資料：

```typescript
const authInfo = context.mcp?.extra.authInfo ?? context.requestContext?.get('authInfo')
```

#### 範例：在 Tool 中識別呼叫端並使用獨立憑證 {/* #example-tool-that-uses-caller-identity-with-a-separate-credential */}

```typescript
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

import { apiCredentials } from '../lib/api-credentials'

const fetchUserData = createTool({
  id: 'fetchUserData',
  description: 'Fetches data for the authenticated MCP caller',
  inputSchema: z.object({
    resourceId: z.string().describe('The ID of the record to fetch'),
  }),
  execute: async (inputData, context) => {
    const authInfo = context.mcp?.extra.authInfo ?? context.requestContext?.get('authInfo')
    const user = authInfo?.extra?.user as { id?: string } | undefined

    if (!user?.id) {
      throw new Error('Authentication required')
    }

    // Resolve the owner from trusted context, not from model input
    const credential = await apiCredentials.getForUser(user.id)

    const response = await fetch(
      `https://api.example.com/users/${encodeURIComponent(user.id)}/records/${encodeURIComponent(inputData.resourceId)}`,
      {
        headers: {
          Authorization: `Bearer ${credential.token}`,
        },
        signal: context.mcp?.extra.signal,
      },
    )

    return response.json()
  },
})
```

從 `authInfo` 取得呼叫者身分，再為 Tool 要呼叫的服務選擇適用的憑證。模型提供 `resourceId` 等業務參數，由受信任的程式碼選擇憑證。MCP 存取權杖僅供你的 MCP 伺服器使用，不得轉送給其他 API。請參閱[安全存取上游服務](/docs/guides/mcp-authentication-authorization#access-upstream-services-safely)。

#### `authInfo` 的來源 {/* #where-authinfo-comes-from */}

由 Mastra 伺服器代管 MCP 伺服器時，系統會根據 `server.auth` 解析出的身分主體填入 `extra.authInfo`，無須額外設定：

```typescript
export const mastra = new Mastra({
  mcpServers: { myServer },
  server: {
    auth: new MastraJwtAuth({ secret: process.env.JWT_SECRET! }),
  },
})
```

通過身分驗證的使用者會依下列規則對應至 `authInfo`：

| `authInfo` 欄位 | 值 |
| - | - |
| `token` | 要求所使用的持有人權杖或工作階段 Cookie 的值 |
| `clientId` | 依序取 `user.id`、`user.sub`、`user.userId`、`user.email` 中第一個存在的值 |
| `scopes` | 將 `user.scopes`、`user.scope` 或 `user.permissions` 統一轉成陣列 |
| `extra.user` | 驗證 Provider 傳回的完整使用者物件 |

如果由自訂中介軟體執行驗證，請設定 `server.mcpOptions.setRequestAuth` 來建立 `authInfo`。這個掛鉤會取代預設的對應規則：

```typescript
export const mastra = new Mastra({
  mcpServers: { myServer },
  server: {
    middleware: [verifyBearerToken], // stores the payload on the request context
    mcpOptions: {
      setRequestAuth: (req, requestContext) => {
        const payload = requestContext.get('bearerPayload')
        req.auth = {
          token: payload.token,
          clientId: payload.sub,
          scopes: payload.scope.split(' '),
        }
      },
    },
  },
})
```

若掛鉤未設定 `req.auth`，該要求就完全不會帶有驗證資訊。

## 要求呼叫者提供輸入 {/* #asking-the-caller-for-input */}

如果 Tool 需要使用者補充資訊才能完成呼叫，就像在 Agent 或 Workflow 中一樣，呼叫 `context.suspend(payload)` 後傳回。伺服器以 `input_required` 結果結束這次要求，並附上由 Tool 的 `resumeSchema` 定義的表單。用戶端回覆後，伺服器會再次執行 Tool，將回覆放在 `context.resumeData`，並將暫停時的承載資料放在 `context.suspendPayload`。每一輪都是獨立的要求，伺服器不會重播先前的輪次。請在承載資料中保存下一輪需要的狀態，並依該狀態選擇執行分支。

```typescript
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

export const bookDelivery = createTool({
  id: 'bookDelivery',
  description: 'Books a delivery for an order after confirming the address.',
  inputSchema: z.object({ orderId: z.string() }),
  outputSchema: z.object({ confirmed: z.boolean() }),
  suspendSchema: z.object({ phase: z.literal('address'), message: z.string() }),
  resumeSchema: z.object({ address: z.string() }),
  execute: async ({ orderId }, context) => {
    if (!context.resumeData) {
      await context.suspend?.({ phase: 'address', message: 'Delivery address?' })
      return
    }
    await book(orderId, context.resumeData.address)
    return { confirmed: true }
  },
})
```

伺服器會依 `resumeSchema` 產生供呼叫者填寫的表單，因此它必須描述不含巢狀結構的物件，欄位僅支援字串、數字、布林值及列舉。呼叫者拒絕填寫或取消表單時，呼叫會以錯誤結束，Tool 不會再次執行。Tool 可以更新承載資料中的階段，多次暫停執行。

### 恢復狀態 {/* #continuation-state */}

恢復呼叫所需的狀態以不透明的 `requestState` 字串傳遞，用戶端會隨回覆原樣傳回。伺服器使用 `requestState.key` 簽署狀態，並在執行處理函式前拒絕遭竄改、已過期或屬於不同 Tool、引數或呼叫者的狀態。伺服器優先採用授權層提供的權杖主體識別呼叫者，其次採用 `mapAuthInfoToUser` 傳回的使用者 `id`，最後採用持有人權杖本身。因此，即使兩位使用者共用同一個 OAuth 用戶端，也無法恢復對方暫停的呼叫。

未啟用授權的伺服器上，所有呼叫者共用一個匿名主體。在 `ttlSeconds` 指定的期限內，`requestState` 如同持有人憑證，任何取得它的人都可以回覆這一輪要求。若 Tool 恢復後能進行寫入、購買或帳戶變更等操作，請以授權機制保護它。

承載資料會簽署但不會加密。請控制資料大小，僅放入 ID、階段等非機密資料。透過環境設定提供 `requestState.key`，讓所有可能處理恢復要求的執行個體共用金鑰。若未設定，伺服器會為每個處理程序各自產生金鑰，呼叫只能由原處理程序恢復。

```typescript
const server = new MCPServer({
  id: 'booking',
  name: 'Booking',
  version: '1.0.0',
  tools: { bookDelivery },
  requestState: { key: process.env.MCP_REQUEST_STATE_KEY!, ttlSeconds: 600 },
})
```

資源和提示的回呼也能用同樣的方式暫停。請參閱[資源處理](#resource-handling)與[提示處理](#prompt-handling)。

### `startHTTP()` {/* #starthttp */}

將 MCP 伺服器整合到既有的網頁伺服器，透過 Streamable HTTP 通訊。網頁伺服器收到 HTTP 要求時，請在要求處理函式中呼叫這個方法。

```typescript oxfmt:false
async startHTTP({
  url,
  httpPath,
  req,
  res,
  options,
}: {
  url: URL;
  httpPath: string;
  req: http.IncomingMessage;
  res: http.ServerResponse<http.IncomingMessage>;
  options?: MCPServerHTTPRequestOptions;
}): Promise<void>
```

每個要求都獨立處理，無須建立或恢復工作階段，因此 `options` 僅用於設定要求檢查。

| 選項 | 行為 |
| - | - |
| `enableDnsRebindingProtection` | 設為 `true` 時，處理要求前會將 `Host` 和 `Origin` 標頭分別與 `allowedHosts` 和 `allowedOrigins` 比對。清單有項目時才會執行對應的檢查。遭拒的要求會收到 `403` JSON-RPC 錯誤。 |
| `allowedHosts` | `Host` 標頭允許的主機名稱。比對時會略過連接埠，所以清單中的 `localhost:3000` 允許 `localhost` 的任何連接埠。IPv6 位址須用方括號括起，例如 `[::1]`。 |
| `allowedOrigins` | `Origin` 標頭允許的來源。只比對主機名稱，因此 `https://app.example.com:8443` 允許 `app.example.com` 上的任何配置與連接埠。非瀏覽器的 MCP 用戶端不會傳送 `Origin` 標頭，因此沒有該標頭的要求仍可通過。 |

不需要檢查要求時，可以省略 `options`。

以下範例在 HTTP 伺服器的要求處理函式中呼叫 `startHTTP`。MCP 用戶端可以透過 `http://localhost:1234/mcp` 連線到這個 MCP 伺服器：

```typescript
import http from 'http'

const httpServer = http.createServer(async (req, res) => {
  await server.startHTTP({
    url: new URL(req.url || '', 'http://localhost:1234'),
    httpPath: `/mcp`,
    req,
    res,
  })
})

httpServer.listen(PORT, () => {
  console.log(`HTTP server listening on port ${PORT}`)
})
```

每個要求都獨立處理，呼叫之間無須保留狀態，因此 `startHTTP` 可在 Supabase Edge Functions、Cloudflare Workers、Vercel Edge、AWS Lambda 和 Deno Deploy 等無伺服器環境執行。這個方法接受 Node 風格的 `http.IncomingMessage` 和 `http.ServerResponse` 物件，因此在以 Fetch 為基礎的執行環境中，需要使用 `fetch-to-node` 等轉接器轉換 `Request`，再把結果轉回 `Response`：

```typescript
// Supabase Edge Function example
import { serve } from 'https://deno.land/std@0.168.0/http/server.ts'
import { MCPServer } from '@mastra/mcp'
// Note: You will need to convert req/res format from Deno to Node
import { toReqRes, toFetchResponse } from 'fetch-to-node'

const server = new MCPServer({
  id: 'my-serverless-mcp',
  name: 'My Serverless MCP',
  version: '1.0.0',
  tools: {/* your tools */},
})

serve(async req => {
  const url = new URL(req.url)

  if (url.pathname === '/mcp') {
    // Convert Deno Request to Node.js-compatible format
    const { req: nodeReq, res: nodeRes } = toReqRes(req)

    await server.startHTTP({ url, httpPath: '/mcp', req: nodeReq, res: nodeRes })

    return toFetchResponse(nodeRes)
  }

  return new Response('Not found', { status: 404 })
})
```

`input_required` 輪次、進度和個別要求的記錄，都會在觸發它們的要求中串流傳送。不受要求生命週期限制的通知（`resources.notifyUpdated()`、`prompts.notifyListChanged()`、`toolActions.notifyListChanged()`）則透過用戶端保持開啟的 `subscriptions/listen` 串流傳送。只有執行中的執行個體仍在提供該串流時，用戶端才收得到這些通知。

## 資源處理 {/* #resource-handling */}

### 什麼是 MCP 資源？ {/* #what-are-mcp-resources */}

MCP 資源會公開伺服器資料，用戶端可以讀取這些資料，作為與 LLM 互動的脈絡。例如：

* 文件內容
* 資料庫記錄
* API 回應
* 即時系統資料
* 螢幕截圖和圖像
* 記錄檔

每項資源都有唯一的 URI，例如 `file:///home/user/documents/report.pdf` 或 `postgres://database/customers/schema`。資源可包含 UTF-8 編碼的文字或 Base64 編碼的二進位資料。

用戶端可透過下列方式探索資源：

1. **直接資源**：伺服器透過 `resources/list` 端點公開個別資源的清單。
2. **資源範本**：對於執行時才定義的資源，伺服器可以公開 URI 範本（RFC 6570），供用戶端組成資源 URI。

若要讀取資源，用戶端需傳送包含資源 URI 的 `resources/read` 要求。伺服器也可以通知用戶端資源清單已變更（`notifications/resources/list_changed`）。如果用戶端正在監聽特定資源，伺服器也可以通知它該資源的內容已更新（`notifications/resources/updated`）。

詳情請參閱 [MCP 官方資源文件](https://modelcontextprotocol.io/docs/concepts/resources)。

### `MCPServerResources` 型別 {/* #mcpserverresources-type */}

`resources` 選項接受 `MCPServerResources` 型別的物件。這個型別定義伺服器處理資源要求時使用的回呼：

```typescript
export type MCPServerResources = {
  // Callback to list available resources
  listResources: (params: {
    extra: MCPRequestHandlerExtra
    requestContext: RequestContext
  }) => Promise<Resource[]>

  // Callback to get the content of a specific resource
  getResourceContent: (
    params: { uri: string } & MCPServerRequest,
  ) => Promise<MCPServerResourceContent | MCPServerResourceContent[] | void>

  // Optional callback to list available resource templates
  resourceTemplates?: (params: {
    extra: MCPRequestHandlerExtra
    requestContext: RequestContext
  }) => Promise<ResourceTemplate[]>

  // Shape of the answer a suspended getResourceContent expects
  resumeSchema?: StandardSchemaWithJSON
}

export type MCPServerResourceContent = { text?: string } | { blob?: string }
```

每個回呼都會收到 `extra` 和 `requestContext`。前者與 Tool 透過 `context.mcp.extra` 取得的通訊協定情境相同，包含用於取消作業的 `signal`，以及 `requestId`、`authInfo` 和 `_meta`。後者是可信任的應用程式情境，包含 `authInfo` 和 `mapAuthInfoToUser` 對應的使用者。你可以用這些資訊限制呼叫端能列出及讀取的資源。

處理 `resources/read` 要求時，伺服器會先到 `listResources` 傳回的清單比對 URI。清單內若沒有相符的資源，伺服器會用呼叫端的 `resourceTemplates` 比對 URI，並將展開的 URI 傳給 `getResourceContent`。URI 可省略 `{?format}` 或 `{/section}` 等選用運算式。變數值須依 RFC 6570 的展開規則進行百分比編碼，因此 `file://data?format=a/b` 無法與 `file://data{?format}` 相符。回應採用相符資源或範本的 `mimeType` 和 `_meta`。若兩者都沒有相符項目，要求會因 `Resource not found` 而失敗。

`getResourceContent` 也會收到 `MCPServerRequest` 的 `suspend`、`resumeData` 和 `suspendPayload` 成員。宣告 `resumeSchema` 後即可使用 `suspend`，用法與 Tool 完全相同。

例子：

```typescript
import { MCPServer } from '@mastra/mcp'
import type {
  MCPServerResourceContent,
  MCPServerResources,
  Resource,
  ResourceTemplate,
} from '@mastra/mcp'

// Resources/resource templates will generally be dynamically fetched.
const myResources: Resource[] = [
  { uri: 'file://data/readme', name: 'Readme', mimeType: 'text/plain' },
]

const myResourceContents: Record<string, MCPServerResourceContent> = {
  'file://data/readme': { text: 'Read this first.' },
  // Not listed; readable as an expansion of the `file://data/{id}` template
  'file://data/123': { text: 'This is the content of data file 123.' },
}

const myResourceTemplates: ResourceTemplate[] = [
  {
    uriTemplate: 'file://data/{id}',
    name: 'Data File',
    description: 'A file containing data.',
    mimeType: 'text/plain',
  },
]

const myResourceHandlers: MCPServerResources = {
  listResources: async () => myResources,
  getResourceContent: async ({ uri, extra }) => {
    if (myResourceContents[uri]) {
      return myResourceContents[uri]
    }
    throw new Error(`Resource content not found for ${uri}`)
  },
  resourceTemplates: async () => myResourceTemplates,
}

const serverWithResources = new MCPServer({
  id: 'resourceful-server',
  name: 'Resourceful Server',
  version: '1.0.0',
  tools: {/* ... your tools ... */},
  resources: myResourceHandlers,
})
```

### 向用戶端通知資源異動 {/* #notifying-clients-of-resource-changes */}

可用資源或資源內容有異動時，伺服器可以通知正在接聽相關資源通知的用戶端。

#### `server.resources.notifyUpdated({ uri: string })` {/* #serverresourcesnotifyupdated-uri-string- */}

由 `uri` 識別的特定資源內容更新時，請呼叫此方法。訂閱這個 URI 的用戶端會透過各自的 `subscriptions/listen` 串流收到 `notifications/resources/updated` 訊息。

```typescript oxfmt:false
async server.resources.notifyUpdated({ uri: string }): Promise<void>
```

例子：

```typescript
// After updating the content of 'file://data.txt'
await serverWithResources.resources.notifyUpdated({ uri: 'file://data.txt' })
```

#### `server.resources.notifyListChanged()` {/* #serverresourcesnotifylistchanged */}

新增或移除資源而使可用資源清單變更時，請呼叫此方法。正在接聽的用戶端會收到 `notifications/resources/list_changed` 訊息，並重新擷取資源清單。

```typescript oxfmt:false
async server.resources.notifyListChanged(): Promise<void>
```

例子：

```typescript
// After adding a new resource to the list managed by 'myResourceHandlers.listResources'
await serverWithResources.resources.notifyListChanged()
```

## 處理提示詞 {/* #prompt-handling */}

### 什麼是 MCP 提示詞？ {/* #what-are-mcp-prompts */}

提示詞是 MCP 伺服器提供給用戶端的可重複使用範本或 Workflow。提示詞可以接受引數，也能包含資源的情境資訊，讓用戶端以一致的方式與大型語言模型互動。

每個提示詞都有唯一的名稱，可預先定義，也可在執行階段定義。

### `MCPServerPrompts` 型別 {/* #mcpserverprompts-type */}

`prompts` 選項接受 `MCPServerPrompts` 型別的物件。此型別定義伺服器處理提示詞要求時使用的回呼。

```typescript
export type MCPServerPrompts = {
  // Callback to list available prompts
  listPrompts: (params: {
    extra: MCPRequestHandlerExtra
    requestContext: RequestContext
  }) => Promise<Prompt[]>

  // Callback to get the messages for a specific prompt
  getPromptMessages?: (
    params: { name: string; args?: Record<string, unknown> } & MCPServerRequest,
  ) => Promise<PromptMessage[] | void>

  // Shape of the answer a suspended getPromptMessages expects
  resumeSchema?: StandardSchemaWithJSON
}
```

提示詞回呼收到的 `extra` 和 `requestContext` 與資源回呼相同。宣告 `resumeSchema` 後，`getPromptMessages` 也能用相同方式呼叫 `suspend`。伺服器會先驗證提示詞的必要引數，再呼叫 `getPromptMessages`。

例子：

```typescript
import { MCPServer } from '@mastra/mcp'
import type { Prompt, PromptMessage, MCPServerPrompts } from '@mastra/mcp'

const prompts: Prompt[] = [
  {
    name: 'analyze-code',
    description: 'Analyze code for improvements',
    arguments: [{ name: 'code', description: 'The code to analyze', required: true }],
  },
]

const myPromptHandlers: MCPServerPrompts = {
  listPrompts: async () => prompts,
  getPromptMessages: async ({ name, args }) => {
    if (name === 'analyze-code') {
      return [
        {
          role: 'user',
          content: {
            type: 'text',
            text: `Analyze this code: ${args?.code}`,
          },
        },
      ]
    }
    throw new Error('Prompt not found')
  },
}

const serverWithPrompts = new MCPServer({
  id: 'prompt-server',
  name: 'Prompt Server',
  version: '1.0.0',
  tools: {/* ... your tools ... */},
  prompts: myPromptHandlers,
})
```

### 向用戶端通知提示詞異動 {/* #notifying-clients-of-prompt-changes */}

可用的提示詞有異動時，伺服器可以通知正在接聽的用戶端。

#### `server.prompts.notifyListChanged()` {/* #serverpromptsnotifylistchanged */}

新增或移除提示詞而使可用提示詞清單變更時，請呼叫此方法。正在接聽的用戶端會收到 `notifications/prompts/list_changed` 訊息，並重新擷取提示詞清單。

```typescript oxfmt:false
await serverWithPrompts.prompts.notifyListChanged();
```

### 提示詞處理的最佳做法 {/* #best-practices-for-prompt-handling */}

* 用清楚的名稱和說明交代提示詞的用途。
* 在 `getPromptMessages` 中驗證所有必要引數。
* 找不到提示詞或缺少必要引數時，傳回錯誤。
* 每次提示詞有異動時，都通知用戶端。

## 動態管理 Tool {/* #dynamic-tool-management */}

伺服器執行期間可以新增或移除 Tool。已連線的用戶端會收到 `notifications/tools/list_changed` 通知。

管理 Tool 的屬性稱為 `toolActions`，而 `tools()` 是傳回 Tool 登錄表的方法。

### `toolActions.add(tools)` {/* #toolactionsaddtools */}

在執行中的伺服器上註冊新的 Tool，並通知已連線的用戶端。和傳給建構函式的 Tool 一樣，註冊時使用輸入物件中各項目的索引鍵。使用既有索引鍵新增 Tool 會取代原有的 Tool。

```typescript oxfmt:false
async server.toolActions.add(tools: ToolsInput): Promise<void>
```

例子：

```typescript
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

const searchTool = createTool({
  id: 'search',
  description: 'Searches the knowledge base.',
  inputSchema: z.object({ query: z.string() }),
  execute: async ({ query }) => ({ results: [] }),
})

await server.toolActions.add({ searchTool })
```

### `toolActions.remove(toolIds)` {/* #toolactionsremovetoolids */}

依 Tool ID 從執行中的伺服器移除 Tool，並通知已連線的用戶端。伺服器會忽略未知的 Tool ID，只有實際移除至少一個 Tool 時才會送出通知。


```typescript oxfmt:false
async server.toolActions.remove(toolIds: string[]): Promise<void>
```

例子：

```typescript
await server.toolActions.remove(['searchTool'])
```

### `toolActions.notifyListChanged()` {/* #toolactionsnotifylistchanged */}

向已連線的用戶端送出 `notifications/tools/list_changed` 訊息，並保留原有的 Tool 登錄表。若授權調整等其他原因使 Tool 的可用性改變，請呼叫此方法。

```typescript oxfmt:false
async server.toolActions.notifyListChanged(): Promise<void>
```

### 同步 Mastra 登錄表 {/* #mastra-registry-synchronization */}

伺服器註冊至 Mastra 執行個體後，`toolActions.add()` 和 `toolActions.remove()` 也會更新該執行個體的 Tool 登錄表，與啟動時自動註冊 Tool 的行為一致。你可以透過 `mastra.listTools()` 取得新增的 Tool。有內建 `id` 的 Tool 會以該 ID 作為索引鍵。移除的 Tool 會從登錄表中刪除。

## 日誌記錄 {/* #logging */}

Tool 透過 `notifications/message` 將結構化日誌訊息傳給發起呼叫的用戶端。用戶端須在每筆要求的中繼資料加入 `io.modelcontextprotocol/logLevel` 鍵，才會收到日誌。伺服器只會針對該筆要求傳送嚴重性達到指定等級或更高的訊息，等級順序依 RFC 5424。同一次 Tool 呼叫的後續輪次屬於新要求，須再次啟用日誌傳送。啟用 `enableServerLogs` 後，Mastra 的 `MCPClient` 會在每筆要求中送出這個鍵。

`context.mcp.log()` 只控制 MCP 用戶端收到的日誌，不影響 Mastra 的日誌記錄器或可觀測性。

### `context.mcp.log()` {/* #contextmcplog */}

在 Tool 的 `execute` 函式中，使用 `context.mcp.log()` 將日誌訊息傳給呼叫該 Tool 的用戶端。

```typescript oxfmt:false
async context.mcp.log(
  level: LoggingLevel,
  message: string,
  data?: Record<string, unknown>
): Promise<void>
```

例子：

```typescript
execute: async ({ location }, context) => {
  await context.mcp?.log?.('debug', 'Fetching weather', { location })
  const weather = await fetchWeather(location)
  await context.mcp?.log?.('info', 'Weather fetched')
  return weather
}
```

## 進度通知 {/* #progress-notifications */}

執行時間較長的 Tool 可以透過 `notifications/progress` 向發起呼叫的用戶端回報進度。呼叫端須在要求的 `_meta` 放入 `progressToken` 來啟用進度追蹤，才會收到通知。設定 `enableProgressTracking` 後，Mastra 的 `MCPClient` 會加入這個權杖。如果要求未附上權杖，`context.mcp.progress()` 不會執行任何動作。

### `context.mcp.progress()` {/* #contextmcpprogress */}

```typescript oxfmt:false
async context.mcp.progress(params: {
  progress: number;
  total?: number;
  message?: string;
}): Promise<void>
```

例子：

```typescript
execute: async ({ items }, context) => {
  for (const [index, item] of items.entries()) {
    await processItem(item)
    await context.mcp?.progress?.({
      progress: index + 1,
      total: items.length,
      message: `Processed ${item.name}`,
    })
  }
  return { done: true }
}
```

## 追蹤 {/* #tracing */}

伺服器註冊到已設定可觀測性的 `Mastra` 執行個體後，處理 `tools/list`、`tools/call`、`resources/*` 和 `prompts/*` 時，每筆要求都會產生一個 `MCP_SERVER_REQUEST` 根 span。`executeTool()` 也會產生相同的 span，因此 Studio 的 MCP 伺服器頁面與 MCP 用戶端會以同樣的方式受到追蹤。

span 依方法和目標命名，例如 `tools/call lookupOrder`。它會將要求參數存為輸入，將回應存為輸出，並記錄伺服器的名稱與版本、協商後的通訊協定版本，以及用戶端回報的名稱與版本。`tools/call` 傳回 `isError: true` 時，該 span 會標記為失敗。以 Tool 形式提供的 Agent 和 Workflow 分別將 `AGENT_RUN` 和 `WORKFLOW_RUN` span 掛在其下。伺服器直接提供的 Tool 不會產生自己的 `TOOL_CALL` span，但 Agent 在這筆要求中呼叫的 Tool 仍會產生。

未連結 `mastra` 執行個體的獨立 `MCPServer` 不會產生 span。

### 連結至呼叫端的 Trace {/* #linking-to-the-callers-trace */}

帶有 W3C `traceparent` 的要求會保有自己的 Trace、根 span 和 Trace 摘要。要求的 span 會連結到呼叫端的 span，讓你從呼叫端的 Trace 找到 Tool 呼叫所觸發的要求。

使用追蹤橋接時，要求的 span 會在要求抵達時已有的作用中 span 下啟動。若伺服器端的 HTTP 檢測機制依 `traceparent` 標頭延續呼叫端的 Trace，要求就會加入該 Trace，且連結會指向同一個 Trace 中的 span。

伺服器依下列順序從兩處讀取 `traceparent` 和 `tracestate`。

1. 要求的 `_meta`。Agent 或 Workflow 透過 HTTP 或 stdio 發出納入追蹤的 Tool 呼叫時，`MCPClient` 會在此處傳送 `traceparent`。
2. HTTP 標頭。非 Mastra 呼叫端的 OpenTelemetry HTTP 檢測機制會在此處傳送這兩個欄位。

要求的 span 也會將有效的 `traceparent` 記錄為 `callerTraceparent` 屬性，將隨附的 `tracestate` 記錄為 `callerTracestate` 屬性，後者最多保留 512 個字元。即使匯出工具不支援 span 連結，仍會保留這些屬性。若要求缺少有效的 `traceparent`，就不會建立連結或記錄呼叫端屬性。span 的輸入不含這些追蹤欄位。

呼叫端也能反向連結至伺服器。若 `tools/call` 要求帶有 `traceparent`，回應會以 `_meta.mastra.traceparent` 識別要求的 span，`MCPClient` 會將自己的 Tool 呼叫 span 連結到該 span。呼叫端未傳送追蹤情境時，回應不會附上追蹤資訊。

Mastra 會將連結與 span 一併儲存。OpenTelemetry 匯出工具、[`OtelBridge`](/integrations/observability/opentelemetry#bridge)、`DatadogBridge`、`DatadogExporter` 和 `SentryExporter` 會以 span 連結的形式送出這些連結。`DatadogExporter` 和 `SentryExporter` 會自行指派 span ID，因此對應的後端無法解析兩個 Mastra span 之間的連結。

## 傳送通知 {/* #notification-delivery */}

`context.mcp.log()` 和 `context.mcp.progress()` 會透過觸發通知的要求串流傳送，因此只有發起要求的呼叫端會收到。可在要求結束後發送的通知（`resources.notifyListChanged()`、`prompts.notifyListChanged()`、`toolActions.notifyListChanged()`、`resources.notifyUpdated()`）會透過相關用戶端各自維持開啟的 `subscriptions/listen` 串流傳送。`resources.notifyUpdated()` 只會通知串流涵蓋該資源 URI 的用戶端。清單變更時，所有接聽該清單通知的用戶端都會收到通知。使用 stdio 時，由連線本身承載串流。

## OAuth 保護 {/* #oauth-protection */}

使用 `createOAuthMiddleware` 函式，即可依照 [MCP 授權規格](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)，透過 OAuth 驗證保護 MCP 伺服器。

```typescript
import http from 'node:http'
import { MCPServer, createOAuthMiddleware, createStaticTokenValidator } from '@mastra/mcp'

const mcpServer = new MCPServer({
  id: 'protected-server',
  name: 'Protected MCP Server',
  version: '1.0.0',
  tools: {/* your tools */},
})

// Create OAuth middleware
const oauthMiddleware = createOAuthMiddleware({
  oauth: {
    resource: 'https://mcp.example.com/mcp',
    authorizationServers: ['https://auth.example.com'],
    scopesSupported: ['mcp:read', 'mcp:write'],
    resourceName: 'My Protected MCP Server',
    validateToken: createStaticTokenValidator(['allowed-token-1']),
  },
  mcpPath: '/mcp',
})

// Create HTTP server with OAuth protection
const httpServer = http.createServer(async (req, res) => {
  const url = new URL(req.url || '', 'https://mcp.example.com')

  // Apply OAuth middleware first
  const result = await oauthMiddleware(req, res, url)
  if (!result.proceed) return // Middleware handled response (401, metadata, etc.)

  // Token is valid, proceed to MCP handler
  await mcpServer.startHTTP({ url, httpPath: '/mcp', req, res })
})

httpServer.listen(3000)
```



* 中介軟體會自動在 `/.well-known/oauth-protected-resource` 提供**受保護資源中繼資料**（RFC 9728）。
* 需要驗證身分時，自動傳回 `401 Unauthorized` 和適當的 `WWW-Authenticate` 標頭。
* 自動使用你提供的驗證器驗證持有者權杖。

### 權杖驗證 {/* #token-validation */}

在正式環境中，請妥善驗證權杖：

```typescript
import { createOAuthMiddleware, createIntrospectionValidator } from '@mastra/mcp'

// Option 1: Token introspection (RFC 7662)
const middleware = createOAuthMiddleware({
  oauth: {
    resource: 'https://mcp.example.com/mcp',
    authorizationServers: ['https://auth.example.com'],
    validateToken: createIntrospectionValidator('https://auth.example.com/oauth/introspect', {
      clientId: 'mcp-server',
      clientSecret: 'secret',
    }),
  },
})

// Option 2: Custom validation (JWT, database lookup, etc.)
const customMiddleware = createOAuthMiddleware({
  oauth: {
    resource: 'https://mcp.example.com/mcp',
    authorizationServers: ['https://auth.example.com'],
    validateToken: async (token, resource) => {
      const decoded = await verifyJWT(token)
      if (!decoded) {
        return { valid: false, error: 'invalid_token' }
      }
      return {
        valid: true,
        scopes: decoded.scope?.split(' ') || [],
        subject: decoded.sub,
      }
    },
  },
})
```

請在可行時讓驗證函式回傳 `subject`。伺服器會將 `input_required` 的接續狀態與 `subject` 綁定，因此即使多位使用者共用同一個 OAuth 用戶端，也不會共用接續狀態。

## 身分驗證上下文 {/* #authentication-context */}

使用 HTTP 傳輸時，Tool 可透過 `context.mcp.extra` 存取請求的中繼資料。你可以透過 HTTP 中介軟體將身分驗證資訊、使用者上下文及自訂資料傳給 MCP Tool。

### 資料如何傳遞 {/* #how-it-works */}

HTTP 中介軟體寫入 `req.auth` 的資料，可在 Tool 中透過 `context.mcp.extra.authInfo` 讀取，也可在資源和提示詞的回呼函式中透過 `requestContext.get('authInfo')` 讀取。

```text
req.auth = { ... }  →  context.mcp.extra.authInfo = { ... }
```

### 對應 FGA 所需的身分驗證資料 {/* #map-auth-data-for-fga */}

將 `MCPServer` 註冊到已設定細粒度授權（FGA）Provider 的 Mastra 執行個體後，Mastra 會在列出或呼叫 Tool 前檢查 `requestContext.get('user')`。HTTP 傳輸層會透過 `extra.authInfo` 傳遞已驗證的身分資料，因此請使用 `mapAuthInfoToUser` 將這些資料轉換成 FGA Provider 所需的使用者資料結構。

```typescript
const server = new MCPServer({
  id: 'my-server',
  name: 'My Server',
  version: '1.0.0',
  tools: { getUserData },
  mapAuthInfoToUser: ({ authInfo }) => {
    const user = authInfo as {
      extra?: {
        userId?: string
        organizationMembershipId?: string
      }
    }

    if (!user.extra?.userId) {
      return null
    }

    return {
      id: user.extra.userId,
      organizationMembershipId: user.extra.organizationMembershipId,
    }
  },
})
```

### 為 MCP Tool 個別設定 FGA 範圍 {/* #scope-mcp-tool-fga-separately */}

若 MCP 用戶端所需的授權範圍與內部 Agent 或 Workflow 執行 Tool 時所用的範圍不同，請設定 `fga.resourceMapping` 和 `fga.permissionMapping`。這兩項設定只會覆寫此 MCP 伺服器針對 `tools/list` 和 `tools/call` 所做的授權檢查。

```typescript
import { MastraFGAPermissions } from '@mastra/core/auth/ee'

const server = new MCPServer({
  id: 'my-server',
  name: 'My Server',
  version: '1.0.0',
  tools: { getUserData },
  mapAuthInfoToUser: ({ authInfo }) => {
    const user = authInfo as {
      extra?: {
        userId?: string
        organizationMembershipId?: string
      }
    }

    if (!user.extra?.userId) {
      return null
    }

    return {
      id: user.extra.userId,
      organizationMembershipId: user.extra.organizationMembershipId,
    }
  },
  fga: {
    resourceMapping: {
      tool: {
        fgaResourceType: 'user',
        deriveId: ({ user }) => (user as { id: string }).id,
      },
    },
    permissionMapping: {
      [MastraFGAPermissions.TOOLS_EXECUTE]: 'read',
    },
  },
})
```

### 設定身分驗證中介軟體 {/* #setting-up-authentication-middleware */}

若要將資料傳給 Tool，請在呼叫 `server.startHTTP()` 前，透過 HTTP 伺服器的中介軟體設定 Node.js 請求物件的 `req.auth`。

```typescript
import express from 'express'

type MCPAuthenticatedRequest = express.Request & {
  auth?: {
    token: string
    clientId: string
    scopes: string[]
    expiresAt?: number
    extra?: Record<string, unknown>
  }
}

const app = express()

// Auth middleware - set req.auth before the MCP handler
app.use('/mcp', async (req, res, next) => {
  const authorization = req.headers.authorization

  if (!authorization?.startsWith('Bearer ')) {
    res.status(401).json({ error: 'Missing bearer token' })
    return
  }

  const token = authorization.slice('Bearer '.length)

  try {
    const user = await verifyToken(token)

    // This entire object becomes context.mcp.extra.authInfo
    const authenticatedRequest = req as MCPAuthenticatedRequest
    authenticatedRequest.auth = {
      token,
      clientId: user.clientId,
      scopes: user.scopes,
      expiresAt: user.expiresAt,
      extra: {
        sub: user.userId,
        email: user.email,
      },
    }
    next()
  } catch {
    res.status(401).json({ error: 'Invalid or expired token' })
  }
})

app.all('/mcp', async (req, res) => {
  const url = new URL(req.url, `http://${req.headers.host}`)
  await server.startHTTP({ url, httpPath: '/mcp', req, res })
})
```

將 `extra.sub`（或 `extra.subject`）設為使用者識別碼。伺服器會依此將 `input_required` 的接續狀態綁定至該使用者。

### 在 Tool 中存取身分驗證資料 {/* #accessing-auth-data-in-tools */}

Tool 的執行函式可以透過 `context.mcp.extra.authInfo` 存取 `req.auth` 物件：

```typescript
execute: async (inputData, context) => {
  // Access the auth data you set in middleware
  const authInfo = context.mcp?.extra.authInfo

  if (!authInfo?.extra?.sub) {
    return { error: 'Authentication required' }
  }

  // Use the auth data
  console.log('User ID:', authInfo.extra.sub)
  console.log('Email:', authInfo.extra.email)

  // Use a credential intended for the API being called, not the MCP token.
  // See https://mastra.ai/docs/guides/mcp-authentication-authorization#access-upstream-services-safely
  const credential = await apiCredentials.getForUser(authInfo.extra.sub as string)

  const response = await fetch('/api/data', {
    headers: { Authorization: `Bearer ${credential.token}` },
    signal: context.mcp?.extra.signal,
  })

  return response.json()
}
```

### 將 `RequestContext` 傳給 Agent {/* #passing-requestcontext-through-to-agent */}

`context.requestContext` 已包含 `authInfo` 和對應後的 `user`，因此 Tool 呼叫 Agent 時可直接傳入這個物件：

```typescript
execute: async (inputData, context) => {
  const authInfo = context.mcp?.extra.authInfo

  if (!authInfo?.extra?.sub) {
    return { error: 'Authentication required' }
  }

  const agent = context.mastra?.getAgentById('some-agent-id')

  if (!agent) {
    return { error: "Agent 'some-agent-id' not found" }
  }

  const response = await agent.generate(prompt, { requestContext: context.requestContext })

  return response.text
}
```

### `extra` 物件 {/* #the-extra-object */}

`context.mcp.extra` 物件包含下列屬性：

| 屬性 | 說明 |
| - | - |
| `authInfo` | 在中介軟體中寫入 `req.auth` 的資料 |
| `requestId` | 目前請求的 JSON-RPC 識別碼 |
| `signal` | 用於取消請求的 AbortSignal |
| `_meta` | 用戶端送出的請求中繼資料，包含 W3C 追蹤欄位、用來明確指定記錄層級的 `io.modelcontextprotocol/logLevel`，以及 `progressToken` |
| `sendNotification`, `sendRequest` | 已淘汰。通訊協定不支援由伺服器發起請求，因此呼叫任一方法都會擲出錯誤，並在錯誤訊息中指出應改用 `context.mcp.log()`、`context.mcp.progress()` 或 `context.suspend()`。 |

### 完整範例 {/* #complete-example */}

安裝 [`jose`](https://github.com/panva/jose)，以便使用身分識別 Provider 的 JSON Web 金鑰集（JWKS）驗證 JSON Web 權杖（JWT）：

```shell npm2yarn
npm install jose
```

下列範例會先驗證權杖的簽章、簽發者、受眾、演算法、到期時間和必要宣告，再將權杖中的使用者資料傳給 Tool：

```typescript
import express from 'express'
import { createRemoteJWKSet, jwtVerify } from 'jose'
import { MCPServer } from '@mastra/mcp'
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

type MCPAuthenticatedRequest = express.Request & {
  auth?: {
    token: string
    clientId: string
    scopes: string[]
    expiresAt?: number
    extra?: Record<string, unknown>
  }
}

const issuer = process.env.JWT_ISSUER
const audience = process.env.JWT_AUDIENCE
const jwksUri = process.env.JWT_JWKS_URI

if (!issuer || !audience || !jwksUri) {
  throw new Error('JWT_ISSUER, JWT_AUDIENCE, and JWT_JWKS_URI are required')
}

const jwks = createRemoteJWKSet(new URL(jwksUri))

const verifyToken = async (token: string) => {
  const { payload } = await jwtVerify(token, jwks, {
    issuer,
    audience,
    algorithms: ['RS256'],
    requiredClaims: ['exp'],
  })

  const clientId =
    typeof payload.client_id === 'string'
      ? payload.client_id
      : typeof payload.azp === 'string'
        ? payload.azp
        : undefined

  if (!payload.sub || typeof payload.email !== 'string' || !clientId || !payload.exp) {
    throw new Error('Token must contain sub, email, exp, and client_id or azp claims')
  }

  return {
    userId: payload.sub,
    clientId,
    email: payload.email,
    expiresAt: payload.exp,
    scopes: typeof payload.scope === 'string' ? payload.scope.split(' ') : [],
  }
}

// 1. Define your tool that uses auth context
const getUserData = createTool({
  id: 'get-user-data',
  description: 'Fetches data for the authenticated user',
  inputSchema: z.object({}),
  execute: async (inputData, context) => {
    const authInfo = context.mcp?.extra.authInfo

    if (!authInfo?.extra?.sub) {
      return { error: 'Authentication required' }
    }

    // Access the data you set in middleware
    return {
      userId: authInfo.extra.sub,
      email: authInfo.extra.email,
    }
  },
})

// 2. Create the MCP server with your tools
const server = new MCPServer({
  id: 'my-server',
  name: 'My Server',
  version: '1.0.0',
  tools: { getUserData },
})

// 3. Set up Express with auth middleware
const app = express()

app.use('/mcp', async (req, res, next) => {
  const authorization = req.headers.authorization

  if (!authorization?.startsWith('Bearer ')) {
    res.status(401).json({ error: 'Missing bearer token' })
    return
  }

  const token = authorization.slice('Bearer '.length)

  try {
    const user = await verifyToken(token)

    // This entire object becomes context.mcp.extra.authInfo
    const authenticatedRequest = req as MCPAuthenticatedRequest
    authenticatedRequest.auth = {
      token,
      clientId: user.clientId,
      scopes: user.scopes,
      expiresAt: user.expiresAt,
      extra: {
        sub: user.userId,
        email: user.email,
      },
    }
    next()
  } catch {
    res.status(401).json({ error: 'Invalid or expired token' })
  }
})

app.all('/mcp', async (req, res) => {
  const url = new URL(req.url, `http://${req.headers.host}`)
  await server.startHTTP({ url, httpPath: '/mcp', req, res })
})

app.listen(3000)
```

## 事件（實驗性） {/* #events-experimental */}

:::warning

事件功能實作了 MCP 擴充草案 [SEP-3415](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415)。傳輸格式與此 API 可能在任何版本中變更。

:::

端對端操作範例請參閱 [MCP 事件](/docs/connections/mcp#mcp-events)。

用戶端可透過 `events` 選項訂閱伺服器上的事件，例如建立工單或完成建置。伺服器會宣告支援 `io.modelcontextprotocol/events` 擴充功能，並透過 stdio 和 Streamable HTTP 回應 `events/list`、`events/poll` 與 `events/stream`。設定 [`eventsOptions.webhook`](#webhook-delivery) 後，伺服器也會回應 `events/subscribe` 和 `events/unsubscribe`，並以 POST 將事件傳送至用戶端的 Webhook URL。

使用 `defineEvent()` 宣告各種事件類型，再用 `server.events.emit()` 發布事件：

```typescript
import { MCPServer, defineEvent } from '@mastra/mcp'
import { z } from 'zod'

const server = new MCPServer({
  id: 'tickets',
  name: 'Tickets',
  version: '1.0.0',
  tools: {},
  events: {
    'ticket.created': defineEvent({
      description: 'A ticket was created',
      inputSchema: z.object({ project: z.string().optional() }),
      payloadSchema: z.object({ id: z.string(), project: z.string() }),
      match: (args, data) => !args.project || data.project === args.project,
    }),
  },
})

await server.events.emit('ticket.created', { id: 't-1', project: 'web' })
```

以 `{ project: 'web' }` 訂閱的用戶端會收到這次事件，以 `{ project: 'api' }` 訂閱的用戶端則不會。

`match` 依用戶端選擇的引數篩選事件，無法限制訂閱者。若要限制呼叫端，請加入 `authorize`。它會收到通過驗證的引數，以及呼叫端的 `requestContext`。設定 `mapAuthInfoToUser` 後，該內容會包含 `user`：

```typescript
const ticketCreated = defineEvent({
  inputSchema: z.object({ project: z.string() }),
  payloadSchema: z.object({ id: z.string(), project: z.string() }),
  match: (args, data) => data.project === args.project,
  authorize: ({ arguments: args, requestContext }) => {
    const user = requestContext.get('user') as { projects: string[] } | undefined
    return user?.projects.includes(args.project) ?? false
  },
})
```

每次呼叫 `events/poll`、開啟 `events/stream`，或透過 `events/subscribe` 建立或續訂 Webhook 訂閱時，都會執行 `authorize`。已開啟的串流會在重新連線時再次檢查權限，Webhook 訂閱則要等到下次續訂。呼叫端即使失去權限，在下一次檢查前仍會收到事件。FGA 不適用於事件，請使用 `authorize` 限制存取權限。

### 傳送模式 {/* #delivery-modes */}

可用的傳送模式取決於該類型的事件來源：

| 定義 | 公布的 `delivery` | 事件來源 |
| - | - | - |
| 未定義 `poll` | `['push', 'poll']`，設定 `eventsOptions.webhook` 後另有 `'webhook'` | `server.events.emit()`。輪詢會讀取記憶體中的緩衝區。 |
| `poll` | `['poll']` | 每次 `events/poll` 要求都會呼叫你提供的 `poll` 函式。 |

以 `poll` 為來源的事件類型無法推送。`delivery` 無法為該類型加入 `'push'`，對它呼叫 `server.events.emit()` 也會擲出例外。用戶端只能從 `events/list` 得知支援的模式，因此伺服器啟動後，已公布的模式便不再變更。若要推送事件，請定義沒有 `poll` 的類型並發布該類型的事件。

要求使用該類型未公布的模式會收到 `-32026`，指定未知的事件名稱則會收到 `-32023`。

### 推送串流 {/* #push-streams */}

每個 `events/stream` 要求各自對應一筆訂閱。伺服器會先傳送 `notifications/events/active`，接著每發生一次符合條件的事件，就傳送一則 `notifications/events/event`。每則通知都會在 `_meta["io.modelcontextprotocol/subscriptionId"]` 帶上要求 ID。若要求包含 `cursor`，伺服器會先重播緩衝區中位於該游標之後的事件，再傳送即時事件。若游標早於緩衝區中最早的事件，`active` 會回報 `truncated: true`。

若串流在 `heartbeatIntervalMs` 內沒有傳送其他訊息，就會送出帶有目前游標的 `notifications/events/heartbeat`。取消要求或呼叫 `server.close()` 會結束串流，並釋放其接聽器和計時器。

### Webhook 傳送 {/* #webhook-delivery */}

設定 `eventsOptions.webhook` 後，用戶端可以透過 `events/subscribe` 註冊回呼 URL。對每次符合條件的事件，伺服器會依照 [Standard Webhooks](https://www.standardwebhooks.com/) 規範，使用用戶端的密鑰以 HMAC-SHA256 簽章，再以 POST 傳送至該 URL。

```typescript
const server = new MCPServer({
  id: 'tickets',
  name: 'Tickets',
  version: '1.0.0',
  tools: {},
  events: {
    'ticket.created': defineEvent({ payloadSchema: z.object({ id: z.string() }) }),
  },
  eventsOptions: {
    webhook: { ttl: { defaultMs: 30 * 60_000 } },
  },
})
```

伺服器會執行下列規則：

* **身分驗證：** 呼叫端必須通過身分驗證才能訂閱 Webhook。若要求缺少 `authInfo`，`events/subscribe` 會傳回 `-32024`。訂閱由呼叫端、URL、事件名稱和引數共同識別，所以以相同條件再次呼叫 `events/subscribe` 會續訂同一筆訂閱，並傳回相同的 `id`。
* **授權：** 每次訂閱及續訂時都會執行 `authorize`。若續訂被拒，伺服器會移除訂閱，並停止以 POST 傳送後續事件。Mastra 用戶端無法區分這裡的 `-32024` 與身分驗證失敗時的同一錯誤碼，因此在預設傳送模式下會回報 `MCP_EVENTS_WEBHOOK_UNAVAILABLE`，嘗試推送，接著以同一個 `-32024` 拒絕要求。
* **回呼 URL：** URL 必須使用 `https`。所有解析出的位址都必須能在公用網路上路由。回送位址、私人位址、連結本機位址及其他特殊用途位址範圍會遭拒，並收到 `-32602` 和 `data.reason`。為了防止 DNS 重新繫結，伺服器會在每次傳送前重新檢查，並連線至通過檢查的位址。伺服器不會跟隨重新導向。
* **端點驗證：** 第一次傳送事件到某個 URL 前，伺服器會用 POST 送出已簽章的驗證挑戰，端點必須原樣傳回。驗證失敗或端點無法連線時，`events/subscribe` 會傳回 `-32027`，並在 `data.reason` 說明原因，例如 `challenge_failed` 或 `timeout`。驗證結果依呼叫端和 URL 快取。`allowedUrls` 接受的 URL 會略過這個步驟。
* **有效期限：** 除非用戶端續訂，否則訂閱會在傳回的 `refreshBefore` 時間到期。要求的 `ttlMs` 會限制在 `ttl` 指定的範圍內。
* **重試：** 每次事件傳送都會採用指數退避重試，直到收到 `2xx` 確認、達到 `retry.maxAttempts` 次嘗試，或超過 `retry.maxWindowMs`。若收到 `410` 或 `413` 回應，便停止重試該次事件。每個要求主體中的 `cursor` 只會越過已確認收到或已放棄傳送的事件。
* **暫停：** 如果某筆訂閱在 `suspend.windowMs` 內的傳送大多失敗，伺服器會暫停該訂閱的傳送，並在下次續訂時於 `deliveryStatus` 回報 `active: false`。續訂後便會恢復傳送。
* **錯誤：** 用戶端只能取得 `timeout` 或 `http_5xx` 等失敗類別，無法取得端點的回應主體或標頭。

### `server.events.emit(name, data, options?)` {/* #servereventsemitname-data-options */}

記錄事件，將事件傳送至符合條件的推播串流與 webhook 訂閱，並傳回事件及其 `eventId`、`timestamp` 和 `cursor`。`options.eventId` 和 `options.timestamp` 分別覆寫預設的隨機 UUID 與目前時間。如果未設定 `name`、`data` 未通過 `payloadSchema` 驗證，或該事件類型設有 `poll` 來源，此方法會擲出錯誤。

`server.events.list()` 會傳回 `events/list` 提供的事件描述元。

### 限制 {/* #limits */}

* 發出的事件會留在發出事件的處理程序中。推播串流、webhook 訂閱，以及從緩衝區輪詢的用戶端，只能收到同一個 `MCPServer` 執行個體發出的事件。因此，無伺服器或多執行個體部署需要由共用儲存支援的 `poll` 來源。
* 緩衝區位於記憶體中。伺服器重新啟動後會將先前的游標視為有事件缺漏，並回報 `truncated: true`。
* Webhook 傳送狀態（等待重試的傳送項目、暫停狀態和驗證結果）保存在記憶體中。用戶端重新整理訂閱時，伺服器會重建這些狀態。
* 事件清單變更通知需要 `subscriptions/listen` 的 `eventsListChanged` 篩選條件。`@mastra/mcp` 使用的 MCP TypeScript SDK 版本尚未支援這項條件。在取得支援之前，伺服器不會宣告 `listChanged`，也不會傳送 `notifications/events/list_changed`。用戶端應重新呼叫 `events/list` 以取得更新後的事件類型。

## 任務（實驗） {/* #tasks-experimental */}

:::warning

任務功能實作 SEP-2663 定義的 MCP 擴充 `io.modelcontextprotocol/tasks`。此 API 可能在任何版本中變更。

:::

`tasks` 選項讓 Tool、Workflow（`run_*`）或 Agent（`ask_*`）能以任務回應 `tools/call`。用戶端會立即收到任務控制代碼，並輪詢 `tasks/get`，直到任務完成。請求結束後仍可取得結果，任務不受 HTTP 逾時限制。只要其中至少有一項可用任務回應，伺服器就會宣告支援這項擴充，並透過 stdio 和 Streamable HTTP 回應 `tasks/get`、`tasks/update` 和 `tasks/cancel`。未設定 `tasks` 選項時，伺服器不會宣告支援這項擴充，也不會處理這些請求。

只有在請求中宣告這項擴充的用戶端才會收到任務。其他用戶端會收到同步回應，但列在 `required` 中的 Tool 除外。

```typescript
import { MCPServer } from '@mastra/mcp'

const server = new MCPServer({
  id: 'reports',
  name: 'Reports',
  version: '1.0.0',
  tools: { buildReport, lookupCustomer },
  tasks: {
    tools: {
      buildReport: 'always',
      lookupCustomer: { mode: 'auto', syncWindowMs: 1000 },
    },
  },
})
```

### 模式 {/* #modes */}

| 模式 | 用戶端已宣告擴充 | 用戶端未宣告擴充 |
| - | - | - |
| `'off'` | 同步回應。 | 同步回應。 |
| `'always'` | 立即傳回任務控制代碼。 | 同步回應。若 Tool 列於 `required`，則傳回錯誤 `-32021`。 |
| `'auto'` | Tool 若在 `syncWindowMs` 內執行完畢，便同步回應。否則傳回任務控制代碼，原本的執行會繼續。 | 同步回應。若 Tool 列於 `required`，則傳回錯誤 `-32021`。 |

伺服器會先建立任務再回應，因此用戶端收到任務控制代碼後，立即呼叫 `tasks/get` 就能成功取得任務。

### 訪問任務 {/* #access-to-tasks */}

任務 ID 是無法猜到的持有者權杖，每個任務都與建立該任務的呼叫者繫結。和[接續狀態](#continuation-state)相同，伺服器會依 OAuth 主體、對應的 `user` 或持有者權杖的雜湊值識別呼叫者。其他呼叫者要求存取此任務，或呼叫者遭 `authorize` 拒絕時，都會收到錯誤 `-32602`，與指定不存在的 ID 時相同。用戶端無法透過 MCP 列出任務。

### Studio 中的任務 {/* #tasks-in-studio */}

已設定 `tasks` 的伺服器會在 Studio 頁面顯示哪些 Tool 以任務方式執行（`always` 或 `auto`），以及 `required` 和 `recover` 設定。頁面也會由新到舊列出所有呼叫者的任務，顯示任務狀態、送出任務的用戶端、待回覆的輸入請求，以及到期時間。你可以依狀態、Tool 或用戶端篩選清單、載入較早的任務，或貼上用戶端顯示的 MCP 任務 ID 來開啟任務。開啟後可查看結果或錯誤、取消任務，或回覆待處理的輸入請求。取消和回覆分別執行與 `tasks/cancel` 和 `tasks/update` 相同的程式碼，但略過 `authorize`。

* Studio 透過其 ID 的雜湊值來識別任務，並透過其身分的雜湊值來識別呼叫者。兩者都不能透過 MCP 使用，而且原始值永遠不會發送到 Studio。您貼上的任務 ID 將在請求正文中傳送並在伺服器上進行雜湊處理。
* 客戶端顯示為其客戶端 ID 以及令牌的主題或使用者 ID。僅透過其令牌標識的呼叫者會顯示令牌雜湊的短前綴。標籤從來都不是憑證。
* 使用 RBAC Provider 時，列出或查詢任務需要 `mcp:read`。取消任務和回覆輸入請求需要 `mcp:write`，預設只有 `admin` 角色具備此權限，`member` 和 `viewer` 均無此權限。若缺少此權限，Studio 仍會顯示任務，但不提供這兩項操作。
* 只有沒有資源範圍的 Studio 會話才能取得清單。 MCP 呼叫者和 Mastra 資源是獨立的身份，因此資源範圍內的會話不會取得任何任務，也無法取消或回應任務。
* 內建任務儲存支援列出任務。自訂 `store` 也須實作 `MCPTaskStoreAdmin`（`list`、`updateByKey`、`cancelByKey`），否則 Studio 會顯示無法列出該儲存空間的任務。

### 開啟任務上限 {/* #open-task-caps */}

處於 `working` 或 `input_required` 狀態的任務會列入未結束任務的計數。任務完成、失敗、取消或到期後就不再計入。若呼叫會超過 `maxOpenTasksPerClient` 或 `maxOpenTasks`，伺服器便不會建立任務：

* `'always'` 模式的 Tool 不會執行。呼叫會傳回 `isError: true`，以及類似 `Too many open tasks for this client (limit 100). Wait for one to finish or cancel one.` 的訊息。
* `'auto'` 模式的 Tool 若在同步時限結束時仍在執行，會留在原請求內繼續執行，並比照未使用任務的情況同步回應。取消請求仍可中止執行。
* `run_<workflow>` 和 `ask_<agent>` 任務也計入相同上限及[任務保留上限](#retained-task-caps)。`'always'` 模式的 Workflow 不會啟動執行，Agent 也不會執行。`'auto'` 模式的 Workflow 暫停後只能透過任務接收回覆，因此達到上限時，伺服器會取消該次執行並傳回 `isError: true`。

兩個值均須為正整數。伺服器透過 `limits` 將兩者傳給 `store.create()`，儲存空間會在超過上限時擲出 `MCPTaskLimitError`。若自訂儲存空間忽略 `limits`，就不會限制未結束任務的數量。

### 任務保留上限 {/* #retained-task-caps */}

記憶體儲存會保留已結束任務的結果，讓用戶端在任務的 `ttlMs` 到期後一分鐘內仍可讀取。任務結束時會釋出未結束任務的名額，但仍占用記憶體。若沒有保留上限，用戶端連續執行大量短任務時，記憶體用量可能無限制地增加。`maxRetainedTasksPerClient` 和 `maxRetainedTasks` 限制儲存空間仍保留的任務數量，包含未結束和已結束的任務。

* 若呼叫會超過任務保留上限，伺服器會比照達到未結束任務上限時回應。`'always'` 模式的 Tool 會傳回 `isError: true`，以及類似 `Too many recent tasks for this client (limit 1000). Try again once older tasks expire.` 的訊息。`'auto'` 模式的 Tool 會同步回應。
* 已建立的任務會保留完整的 `ttlMs`。儲存空間絕不會為了騰出名額而提早丟棄結果。只有移除任務時才會釋出保留名額。
* 未結束的任務也計入保留上限。若一組上限只設定其中一項，另一項的預設值會隨之調整。將 `maxRetainedTasksPerClient` 設為低於 100 時，預設的 `maxOpenTasksPerClient` 會降到相同值。將 `maxOpenTasks` 設為高於 10000 時，預設的 `maxRetainedTasks` 會升到相同值。若同時設定兩項，且保留上限低於未結束任務上限，建立伺服器時就會擲出錯誤。

只有記憶體儲存會強制執行保留上限。使用 Mastra 儲存的任務會將已結束的結果保留在資料庫中（請參閱[跨執行個體的任務](#tasks-across-instances)），因此只適用未結束任務上限。若自訂儲存空間將已結束任務的結果保留在其他位置，也可以忽略保留上限。

### 在任務中請求輸入 {/* #asking-for-input-inside-a-task */}

Tool 在任務中呼叫 `suspend()` 時，任務會轉為 `input_required`。輸入請求使用與同步呼叫相同的表單，由 Tool 的 `resumeSchema` 產生。用戶端透過 `tasks/update` 回覆時，伺服器會比照同步呼叫，帶入 `resumeData` 重新執行 `execute`。請確保 `suspend()` 之前的作業可以安全地重複執行。

輸入請求遭拒絕或取消時，任務會以 `isError: true` 結束。回覆中含有任務未要求的欄位時，伺服器會忽略這些欄位。

### 任務執行時取得的資料 {/* #what-a-task-run-receives */}

每次執行都會根據建立任務時儲存的資料重建，因此任務可以先存放在儲存空間中，等重新啟動後再執行。每次執行都會取得已儲存的請求內容，且無法存取 `context.mcp`。唯一的例外是 `'auto'` 模式的 Tool 首次執行，因為它在同步時限結束前就已在原請求內開始執行。

* 儲存請求內容前，伺服器會從 `authInfo` 移除持有者權杖。其餘資料一律原樣儲存，包括 `authInfo.extra` 及 `mapAuthInfoToUser` 傳回的 `user`。請勿在這些資料中放入不應由任務儲存空間保留的憑證。
* 值會儲存為 JSON。執行時讀回的是一般物件，因此若 `user` 原本是類別執行個體，讀回時會是具有相同欄位的一般物件。
* 若某個欄位的值無法儲存為 JSON，伺服器會跳過該欄位，並在建立任務時記錄警告。如果該欄位是 `user`，後續執行的授權檢查會失敗。
* 由於無法存取 `context.mcp`，請透過 `context.abortSignal` 偵測取消。
* 如同每一輪同步呼叫，每次執行都會根據已儲存的請求內容重新檢查授權。

### 取消和錯誤 {/* #cancellation-and-errors */}

* `tasks/cancel` 會觸發 Tool 的 `abortSignal`，任務會以 `cancelled` 結束。Tool 必須自行處理訊號並停止執行。若之後仍傳回結果，伺服器會丟棄該結果。
* Tool 擲出錯誤時，任務會比照同步呼叫，以 `isError: true` 和序列化後的錯誤作為結果結束。
* 只有在伺服器無法執行任務時，例如 TTL 到期，任務才會以 `failed` 結束。

### Workflow 任務 {/* #workflow-tasks */}

每個 `run_<key>` 任務都會追蹤一次 Workflow 執行。這次執行只會在建立任務的 `tools/call` 中啟動一次，並有自己的執行 ID。任務 ID 絕不會用作執行 ID。

```typescript
const server = new MCPServer({
  id: 'reports',
  name: 'Reports',
  version: '1.0.0',
  workflows: { nightly },
  tasks: {
    workflows: { nightly: { mode: 'auto', syncWindowMs: 1000 } },
  },
})
```

* 執行以 `success` 或 `bailed` 結束時，任務會傳回與同步呼叫相同的文字，包含 `status`、`input`、`steps` 和 `result`。
* 執行以 `failed`、`tripwire` 或 `canceled` 結束時，任務結果會包含 `isError: true` 和錯誤訊息。在 `'auto'` 模式下，若執行在 `syncWindowMs` 內失敗，伺服器會以相同方式回應，且不建立任務。只有用戶端不支援 Tasks 擴充功能，或 Workflow 模式為 `'off'` 時，伺服器才會傳回一般的 `run_` 回應，此時執行失敗的回應不含 `isError`。
* 在 `'auto'` 模式下，若執行在 `syncWindowMs` 內暫停，就會轉為任務繼續進行，以便要求輸入。
* 參數無效時，伺服器會直接傳回 `isError: true`，此時尚未開始執行或建立任務。
* 步驟暫停時，任務會轉為 `input_required`，並提供由該步驟的 `resumeSchema` 產生的表單，以暫停時附帶的資料作為訊息。伺服器一次只會針對一個暫停中的步驟要求輸入。`tasks/update` 會將回覆作為 `resumeData` 以繼續執行。繼續執行需要 Mastra 儲存。
* 每次暫停最多只能繼續執行一次。若執行已透過 Studio 或其他執行個體繼續，任務會捨棄回覆，並繼續追蹤該次執行。若執行再次暫停，即使停在迴圈中的同一步驟，任務也會送出新的輸入請求。若任務內外的繼續執行請求同時抵達，過時的回覆仍可能使同一步驟從下一次暫停中繼續執行。
* 若步驟的 `resumeSchema` 無法呈現為表單，例如含有巢狀物件，任務會維持 `working`。你可以透過其他方式繼續執行，例如使用 Studio，任務會繼續追蹤。在此之前，任務會每秒讀取一次執行狀態。若使用 Mastra 背景任務，期間也會占用一個背景任務名額，如同追蹤由其他執行個體執行的 Workflow。
* 拒絕輸入請求、呼叫 `tasks/cancel` 或 TTL 到期，都可從任何執行個體取消該次執行，包括正在等待輸入的執行。若執行就在處理取消的執行個體上，會在該處停止。若執行在另一個執行個體上，會等到該執行個體下次續租任務時停止，約在一個租期內。
* 伺服器關閉或將任務交給另一個工作程序時，會停止追蹤該次執行，Workflow 本身會繼續執行。另一個執行個體會接手任務，追蹤該次執行直到結束。
* 若在 `tasks` 中傳入 `store`，伺服器只會在用戶端拒絕輸入請求時取消執行。請在儲存空間處理取消和到期時，用 `isWorkflowTaskContext()` 檢查任務的內容，再呼叫 `mastra.getWorkflow(context.workflowKey).createRun({ runId: context.runId })`，接著對取得的執行控制物件呼叫 `run.cancel()`。在實際執行 Workflow 的程序中，該物件指向正在進行的執行，因此 `cancel()` 會在該程序中停止執行。

執行 Workflow 任務的伺服器停止後，Mastra 的 [Workflow 復原功能](/reference/core/mastra-class)會在下一個啟動的執行個體上繼續執行，任務也會在該處繼續追蹤。此功能要求 `recovery.workflows` 為 `'auto'`，這也是預設值。若設為 `'off'`，任務會維持 `working`，直到 TTL 到期。伺服器停止時正在執行的步驟會重新執行，因此請確保步驟可以安全地重複執行。若該次執行從未儲存，或接手追蹤的程序也停止，任務會以 `failed` 結束。

### Agent 任務 {/* #agent-tasks */}

`ask_<key>` 任務會執行 Agent 的 `generate()`。其行為與 Tool 任務相同，`tasks/cancel` 會觸發 Agent 的 `abortSignal`，發生錯誤時任務會以 `isError: true` 結束，且適用 `recover` 設定。

若 Agent 暫停以等待核准 Tool 呼叫或等待其他輸入，任務會以 `isError: true` 結束。目前任務尚無法回覆 Agent 的核准請求。

### 跨執行個體的任務 {/* #tasks-across-instances */}

在已啟用[背景任務](/docs/harness/background-tasks)的 Mastra 執行個體上註冊伺服器後，該伺服器的任務會保留在 Mastra 儲存中。共用該儲存空間的任何執行個體都能執行任務，也能回應該任務的 `tasks/get`、`tasks/update` 和 `tasks/cancel` 請求。

```typescript
import { Mastra } from '@mastra/core/mastra'
import { LibSQLStore } from '@mastra/libsql'

export const mastra = new Mastra({
  // A local file is only shared by instances on the same host. Use a database every instance can reach.
  storage: new LibSQLStore({ id: 'mastra', url: 'file:./mastra.db' }),
  backgroundTasks: {
    enabled: true,
    // MCP tasks share the per-agent limit (5) unless their owner gets its own
    perOwnerConcurrency: { 'mcp-server:reports': 50 },
  },
  mcpServers: { reports: server },
})
```

* 儲存介面卡必須能儲存每個任務的 TTL。若使用較舊的介面卡，伺服器會在註冊時改用記憶體儲存並記錄警告。在 `tasks` 中傳入的 `store` 一律優先使用。
* 若伺服器在註冊前就已處理任務，這些任務會保留在記憶體中。註冊後，伺服器仍會從同一執行個體的記憶體處理這些任務，並將新任務保留在 Mastra 儲存中。
* 請在每個執行個體上以相同的 ID 和 Tool 註冊同一個伺服器。未註冊該伺服器的執行個體無法執行它的任務，且會將這些任務標記為失敗。請明確設定 `id`，或以 `mcpServers` 中的鍵註冊伺服器。自動產生的 ID 每次啟動都會變更，伺服器也會記錄警告。
* 每個任務都計入 `mcp-server:<server id>` 的 `perOwnerConcurrency`（未設定時改用 `perAgentConcurrency`），也計入 `globalConcurrency`。請將 `backpressure` 保持為預設值 `'queue'`。若使用其他值，佇列已滿時呼叫會失敗。
* 伺服器會先儲存透過 `tasks/update` 送出的回覆，再確認收到。即使接收回覆的執行個體在繼續執行前停止，任務仍會繼續。
* 已結束任務的 `ttlMs` 到期約一分鐘後，伺服器會刪除該筆資料，無須使用 `backgroundTasks.cleanup`。伺服器只會刪除自己的資料列。若任務設為 `ttlMs: null`，該筆資料會一直保留，直到你手動刪除。
* 每個執行個體都會定期掃描，將過期任務標記為失敗，並讓已收到回覆但仍在等待的任務繼續執行。伺服器註冊後就會開始掃描，即使用戶端還沒有向該執行個體送出任何任務請求。每次掃描最多處理 100 個過期任務，並檢查另外 100 個未結束的任務，下次掃描再處理後續的批次。只有在有空餘名額時，才會重新啟動留在已停止執行個體上等待的任務，其餘任務會等候後續掃描。
* `maxOpenTasksPerClient` 和 `maxOpenTasks` 會計算儲存空間中所有執行個體的未結束任務，因此適用於整個部署。每次呼叫都會先計數再新增任務，因此若多個呼叫同時抵達不同的執行個體，超出上限的數量最多可達這些呼叫的總數。
* 任何執行個體都可以接收 `tasks/cancel`。若任務的第一次嘗試仍在原先啟動任務的執行個體上等候名額，該執行個體會在下一次掃描時將它停止，最長等待一個租期（`leaseDurationMs`）。

任務會以資料列的形式存於背景任務儲存空間，擁有者的 Agent ID 為 `mcp-server:<server id>`，資源 ID 為 `mcp-server:<server id>:<caller>`。

* 這些任務不隸屬於任何 Agent、對話串或記憶，因此絕不會出現在 Agent 的對話中。
* `/background-tasks` 路由不會將這些任務傳回給受資源範圍限制的呼叫者。未受資源範圍限制的呼叫者可以列出這些任務，全域的 `onTaskComplete` 和 `onTaskFailed` hook 也可以列出。若 hook 只應處理 Agent 任務，請在其中檢查 `task.agentId.startsWith('mcp-server:')`。
* 伺服器使用任務 ID 和呼叫者身分各自的雜湊值查找資料列，不會儲存這兩者的原始值或持有者權杖。伺服器會儲存已移除持有者權杖的請求內容，以及可供閱讀的 `metadata.clientLabel`，其中包含用戶端 ID，並依情況附上權杖主體或使用者 ID，格式見下一項。`authInfo.extra` 和 `user` 會原樣儲存，任何能讀取該筆資料的人都看得到。
* `metadata.clientLabel` 會記錄 OAuth 用戶端 ID 與權杖主體（`<client id>:sub:<subject>`），或記錄 OAuth 用戶端 ID 與 `mapAuthInfoToUser` 傳回的使用者 ID（`<client id>:user:<user id>`）。若兩者皆無，則會記錄用戶端 ID 和權杖雜湊值的前 8 個字元（`<client id>:token:<hash prefix>`）。此標籤僅供除錯。伺服器一律依呼叫者身分的雜湊值進行比對。

### 當機後復原 {/* #recovery-after-a-crash */}

執行任務的執行個體停止後，另一個執行個體會在下次掃描時偵測到。若原執行個體當機，須等到任務租期屆滿。若原執行個體正常關閉並交還租約，下次掃描即可偵測到。只要伺服器已在啟用背景任務的 Mastra 執行個體上註冊，該執行個體就會掃描，無論是否已處理過任務請求。將任務保留在記憶體中或未註冊該伺服器的執行個體不會掃描。後續行為取決於 `recover` 設定。

* 設為 `recover: false`（預設）時，任務會以 `failed` 結束，並附上 `task lost: the server restarted while it was running`。`execute` 絕不會因此再次執行。
* 設為 `recover: true` 時，另一個執行個體會從頭重新執行 `execute` 一次。請只為可安全重複執行的 Tool 啟用此設定。

設為 `recover: true` 時，若任務因 Tool 以外的原因而執行失敗，例如在記錄等待輸入的狀態時寫入失敗，也適用同一次重試機會。若錯誤來自 Tool 本身，任務會直接以含有 `isError` 的結果結束。

`recover` 不影響正在等待輸入的任務。無論如何設定，都可透過任何執行個體回覆以繼續執行任務。

### 追蹤 {/* #tracing-1 */}

每個任務都對應一筆追蹤紀錄。建立任務的 `tools/call` 是該紀錄的根跨度，並會在任務開始後正常結束。Tool 每次執行都會在根跨度下產生一個 `task attempt <tool> #<n>` 跨度，包含在其他執行個體上繼續或復原的執行。Tool 自己的跨度會放在該次嘗試的跨度下。`tasks/update` 和 `tasks/cancel` 請求會納入同一筆追蹤紀錄。對 `tasks/get` 的輪詢不會納入追蹤。

這也適用於 `run_<workflow>` 和 `ask_<agent>` 任務。Workflow 任務的執行跨度位於第一次嘗試的跨度下，在 `'auto'` 模式下則位於根跨度下。每次透過 `tasks/update` 繼續執行時，其跨度都會放在使它繼續執行的那次嘗試下，無論該次嘗試在哪個執行個體上。Agent 任務的 `agent run` 位於該次嘗試的跨度下。依照設計，Mastra 的 Workflow 復原功能在當機後重新啟動某次執行時，會為該次執行建立獨立的追蹤紀錄。具備持久性的 Workflow 和 Agent 支援跨當機追蹤。任務用來追蹤重新啟動之執行的那次嘗試，仍會留在該任務的追蹤紀錄中。

跨度的中繼資料包含任務詳細資訊，包括 `mcpTaskKey`（任務 ID 的 SHA-256 雜湊值）、`attempt`、`resumed`、`recovered` 和 `mcpTaskStatus`。跨度絕不會記錄任務 ID 的原始值。缺少根跨度的追蹤紀錄會從清單中消失，因此伺服器會在任務一開始就寫出根跨度。即使該執行個體在下次匯出前停止，追蹤紀錄也會留在清單中。嘗試次數會跨執行個體連續編號，因此即使當機前那次嘗試的跨度隨執行個體遺失，當機後復原的執行仍會顯示為 `#2`。

### 限制 {/* #limits-1 */}

* 若未啟用 Mastra 背景任務，任務會保留在記憶體中，並在程序重新啟動時遺失。在多執行個體部署中，特定任務的每一個 `tasks/*` 請求都必須送到建立該任務的執行個體。Streamable HTTP 請求會在 `Mcp-Name` 標頭中帶上任務 ID，負載平衡器可據此路由請求。
* 伺服器傳回任務控制代碼後送出的進度和日誌通知都會遭到捨棄。
