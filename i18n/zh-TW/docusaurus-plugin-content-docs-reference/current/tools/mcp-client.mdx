# MCPClient

`MCPClient` 類別可在 Mastra 應用程式中管理多個 MCP 伺服器連線及其 Tool。它負責連線生命週期與 Tool 命名空間，並提供所有已設定伺服器的 Tool 存取能力。

:::note
正從 `@mastra/mcp` 1.x 升級？請參閱[遷移指南](/reference/migrations/mcp-v2)。
:::

## 建構函數 {/* #constructor */}

建立 MCPClient 類別的新實例。

```typescript oxfmt:false
constructor({
  id?: string;
  servers: Record<string, MastraMCPServerDefinition>;
  timeout?: number;
  typegen?: { outFile: string };
  clientInfo?: { name?: string; version?: string };
  registerProcessHooks?: boolean;
}: MCPClientOptions)
```

### 具型別的用戶端契約 {/* #typed-client-contracts */}

將明確的伺服器對照表型別傳入 `MCPClient<TServers>`，即可檢查已設定的伺服器名稱、探索到的 Tool 名稱及直接呼叫的參數。`MCPClientOptions<TServers>` 接受相同的對照表型別。宣告的伺服器皆為必填；若只要設定其中一部分，可使用 `Pick<TServers, 'weather'>`。未傳入型別參數時，探索結果仍使用原有的寬泛型別。

此對照表透過 `tools` 描述各伺服器的 Tool，並為每個 Tool 指定 `input` 和 `output` 型別。以下範例假設 `WEATHER_MCP_URL` 指向一台正在運作的天氣伺服器：

```typescript
import { MCPClient } from '@mastra/mcp'

interface MCPServers {
  weather: {
    tools: {
      get_weather: {
        input: { location: string }
        output: { temperature: number; conditions: string }
      }
    }
  }
}

const mcp = new MCPClient<MCPServers>({
  servers: { weather: { url: new URL(process.env.WEATHER_MCP_URL!) } },
})

try {
  const tools = await mcp.listTools()
  const weather = tools.weather_get_weather
  if (weather?.execute) {
    const result = await weather.execute({ location: 'Paris' })
    if (result && 'temperature' in result && typeof result.temperature === 'number') {
      console.log(result.temperature)
    }
  }
} finally {
  await mcp.disconnect()
}
```

`listTools()` 和 `listToolsWithErrors().tools` 提供精確的 `server_tool` 鍵。`listToolsets()` 和 `listToolsetsWithErrors().toolsets` 則以伺服器鍵組織未加前綴的 Tool 名稱。兩種結果都可能不完整：伺服器或 Tool 可能不存在。呼叫 Tool 前請確認其可用。錯誤對照表、錯誤詳情及可選的探索耗時仍維持原有型別。

執行結果可能是結構化輸出、協定結果封裝物件、驗證錯誤或 `undefined`。讀取成功結果的欄位前，請檢查結果的結構與屬性型別。協定封裝物件可能包含其他屬性。對於沒有輸出 schema 的 Tool，請設定 `output: unknown`。

這些契約描述的是 schema 快照，實際運作的伺服器可能與快照不同。伺服器的 schema 變更時，請使用具備同等權限的憑證更新契約。伺服器新增的 Tool 在執行階段仍可使用，但不會出現在快照的已知鍵中。執行階段的探索、驗證與執行行為不變。

### 產生用戶端型別 {/* #generate-client-types */}

使用 `@mastra/mcp` 提供的命令，依據線上 Tool 的輸入與輸出 schema 產生具體的 TypeScript 介面。匯出現有用戶端，並設定 `typegen.outFile`：

```typescript title="src/mcp/client.ts"
import { MCPClient } from '@mastra/mcp'
import type { MCPServers } from './mcp-types.generated'

export const mcp = new MCPClient<MCPServers>({
  id: 'weather-client',
  servers: { weather: { url: new URL(process.env.WEATHER_MCP_URL!) } },
  typegen: { outFile: 'src/mcp/mcp-types.generated.ts' },
})
```

設定模組所需的環境變數和驗證憑證，然後從專案根目錄執行以下命令：

```bash npm2yarn
npx @mastra/mcp generate ./src/mcp/client.ts
```

首次執行時，僅供匯入型別的產出檔可能尚未建立。載入器會處理 TypeScript 和間接匯入的模組，並略過型別檢查。產生檔案後，請執行型別檢查。

請使用產生的名稱，並在執行階段確認 Tool 是否可用及結果的結構。此範例假設伺服器提供 `get_weather`，它接收必填的字串參數 `location`，並輸出數值 `temperature`：

```typescript title="src/mcp/call-weather.ts"
import { mcp } from './client'

try {
  const tools = await mcp.listTools()
  const weather = tools.weather_get_weather
  if (weather?.execute) {
    const result = await weather.execute({ location: 'Paris' })
    if (result && 'temperature' in result && typeof result.temperature === 'number') {
      console.log(result.temperature)
    }
  }
} finally {
  await mcp.disconnect()
}
```

這個命令接受一或多個檔案路徑。輸入檔和 `outFile` 都以命令的工作目錄為基準。命令只選取已啟用型別產生功能、且透過具名或預設匯出直接匯出的用戶端。命令不會掃描原始碼目錄樹、呼叫工廠函式或檢查匯出物件中的巢狀成員。重複指定同一檔案、透過符號連結指向同一檔案，或重複匯出同一用戶端時，都只會處理一次。任何檔案若沒有符合條件的用戶端，命令就會失敗。

若多個獨立用戶端使用相同的伺服器設定，請為每個用戶端指定不同的 ID 和輸出路徑：

```typescript title="src/mcp/clients.ts"
import { MCPClient } from '@mastra/mcp'

const servers = { weather: { url: new URL(process.env.WEATHER_MCP_URL!) } }
export const first = new MCPClient({
  id: 'first',
  servers,
  typegen: { outFile: 'first.generated.ts' },
})
export const second = new MCPClient({
  id: 'second',
  servers,
  typegen: { outFile: 'second.generated.ts' },
})
```

```bash npm2yarn
npx @mastra/mcp generate ./src/mcp/clients.ts
```

既有的執行個體快取仍然有效。建構用戶端時，若明確指定的 ID、伺服器設定及 `typegen.outFile` 都相同，就會傳回既有物件。只要伺服器設定或 `outFile` 不同，就會替換快取中的執行個體，避免後續建構時沿用這次未指定的輸出檔。

產生過程只會列出 Tool 定義，不會呼叫 Tool。探索失敗、缺少驗證、逾時、輸出路徑衝突、輸出將覆寫指定的輸入檔，或結構描述完全無法表示（例如循環參照、巢狀層級過深或無法解析的本機參照）時，產生作業會失敗。每則錯誤都會指出相關的用戶端檔案、伺服器或 Tool。命令會先備妥所有要產生的原始碼，再替換檔案。無論成功或失敗，都會中斷所選用戶端的連線。探索或事前檢查失敗時，既有輸出會保留。個別檔案的替換是不可分割的操作，但整批替換並非單一交易。若替換期間發生檔案系統錯誤，先前替換的檔案可能已經更新。

沒有輸出結構描述的 Tool 會使用 `unknown`。字串格式、長度限制及數值上下限等條件會保留對應的基礎 TypeScript 型別，並繼續由執行階段驗證。不支援的部分（包括條件式結構描述及 `prefixItems` 元組）會放寬為 `unknown`，並發出警告。若關鍵字的值不符合允許的結構，對應的結構描述也會放寬為 `unknown` 並發出警告，讓其他伺服器仍可產生型別。警告會指出相關的伺服器、Tool 和結構描述內的位置。產生器不會擷取外部結構描述參照。若本機參照無法解析或存在循環參照，產生作業就會失敗。巢狀結構超過協定規定的 128 層上限時，產生作業也會失敗。結構描述若超過協定規定的 10,000 個節點上限，就會放寬為 `unknown` 並發出警告。產生器對原始 JSON 值採用較寬鬆的上限，結構描述或目錄超出該上限時也會以相同方式處理。產生器會在複製或轉換結構描述前檢查這些上限，避免伺服器公布的大型結構描述卡住命令。

:::note 模組執行與憑證

此命令會執行指定的模組，連同這些模組匯入的模組。請使用可信任且不會在匯入時觸發應用程式啟動副作用的模組，並在執行命令前提供憑證。命令不會載入 dotenv 檔案或啟動互動式身分驗證。用戶端既有的逾時及探索設定仍然適用。

產生器的診斷訊息不會包含原始結構描述、傳輸錯誤或憑證。匯入的應用程式、自訂記錄處理函式或伺服器子程序輸出的記錄不在此保證範圍內。

:::

### `MastraMCPServerDefinition` {/* #mastramcpserverdefinition */}

`servers` 對照表中的每部伺服器皆使用 `MastraMCPServerDefinition` 型別設定。用戶端會依提供的參數選用傳輸方式：

* 提供 `command` 時，使用 Stdio 傳輸。
* 提供 `url` 時，使用 Streamable HTTP 傳輸。

用戶端支援 MCP `2026-07-28` 版。連線時會查詢伺服器支援的版本（`server/discover`）。若伺服器尚未升級，就回退至 2026 年前的 `initialize` 交握程序，讓 Tool、資源與提示詞在新舊版本皆能使用。舊版缺少的功能（`resources.subscribe()`、`inputRequests`）會傳回錯誤，並指出協商後採用的版本。`onListChanged()` 處理函式適用於新舊版本，因為舊版伺服器不需要 `subscriptions/listen` 串流便能傳送清單變更通知。設定 `protocolVersion` 可略過版本探測。

## Tool 核准 {/* #tool-approval */}

在伺服器定義中設定 `requireToolApproval`，即可要求該伺服器的 Tool 在執行前先取得人工核准。此設定沿用既有的[人工核准](/docs/workflows/human-in-the-loop)流程。

### 要求核准所有 Tool {/* #require-approval-for-all-tools */}

將 `requireToolApproval` 設為 `true`，即可要求該伺服器上的每個 Tool 都須取得核准：

```typescript
const mcp = new MCPClient({
  servers: {
    github: {
      url: new URL('http://localhost:3000/mcp'),
      requireToolApproval: true,
    },
  },
})
```

### 透過函式動態判斷是否需要核准 {/* #dynamic-approval-with-a-function */}

傳入函式，逐次判斷呼叫是否需要核准。函式會收到 Tool 名稱、模型傳入的引數、傳入請求所附的請求內容，以及伺服器宣告的 MCP Tool `annotations`（如有）：

```typescript
const mcp = new MCPClient({
  servers: {
    github: {
      url: new URL('http://localhost:3000/mcp'),
      requireToolApproval: ({ toolName, args, requestContext }) => {
        // Read-only tools don't need approval
        if (toolName === 'list_repos') return false
        // Destructive tools with force flag always need approval
        if (toolName === 'delete_repo') return args.force === true
        // Non-admin users need approval for everything else
        return requestContext?.userRole !== 'admin'
      },
    },
  },
})
```

也可以傳入非同步函式。函式會收到傳入請求的 `requestContext`，可用於驗證、授權檢查或其他逐一處理請求的邏輯。

### 使用可信任伺服器的 Tool 註解 {/* #use-tool-annotations-from-a-trusted-server */}

若信任該 MCP 伺服器，可依據其 [Tool 註解](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#tool-annotations)（`readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint`、`title`）判斷是否需要核准：

```typescript
const mcp = new MCPClient({
  servers: {
    github: {
      url: new URL('http://localhost:3000/mcp'),
      requireToolApproval: ({ annotations }) => {
        // Skip approval for tools the server has marked read-only
        if (annotations?.readOnlyHint) return false
        // Always require approval for destructive tools
        if (annotations?.destructiveHint) return true
        return true
      },
    },
  },
})
```

依 MCP 規格，**除非 Tool 註解來自可信任的伺服器，否則用戶端必須將該註解視為不可信任**。註解僅供參考，無法形成安全邊界。惡意或有程式錯誤的伺服器可能把可寫入資料的 Tool 標示為唯讀。只有信任伺服器時，才可依據註解放寬核准要求。

`listTools()` 和 `listToolsets()` 傳回的 Tool 也會在 `tool.mcp.annotations` 提供這些註解，供你為 Agent 設定 Tool 時檢查。

每個 Tool 都有 `tool.title`，優先採用伺服器提供的 Tool `title`，其次採用 `annotations.title`。兩者皆未提供時，`tool.title` 為 `undefined`，顯示時改用 Tool 名稱，符合 MCP 的顯示名稱優先順序。

## 伺服器指令 {/* #server-instructions */}

MCP 伺服器若在初始化時宣告指令，`MCPClient` 會依伺服器儲存指令。將指令轉送到 Agent 的系統提示需要**明確啟用**。為伺服器設定 `forwardInstructions: true` 後，透過 `listTools()` 或 `listToolsets()` 使用該伺服器 Tool 的 Agent 會自動收到指令。

指令依伺服器名稱分組，每台伺服器最多保留 `instructionsMaxLength` 個字元。

```typescript
const mcp = new MCPClient({
  servers: {
    db: {
      url: new URL('http://localhost:3000/mcp'),
      forwardInstructions: true,
      instructionsMaxLength: 512,
    },
  },
})

const agent = new Agent({
  id: 'db-agent',
  name: 'DB Agent',
  instructions: 'Help with database changes.',
  model,
  tools: await mcp.listTools(),
})
```

預設省略 `forwardInstructions` 時，指令仍會儲存在快取中，可透過 [`getServerInstructions()`](#getserverinstructions) 查看。這些指令不會加入任何 Agent 的系統提示。

> **安全說明：** 伺服器指令會原樣轉送至 Agent 的系統提示，只會依長度上限截斷。惡意或遭入侵的 MCP 伺服器可藉此注入會被 Agent 視為可信任系統指令的內容。只為可信任的伺服器啟用 `forwardInstructions`。建議先用 `getServerInstructions()` 檢視第三方伺服器的指令，再啟用轉送。

## 安全 {/* #security */}

### Stdio 伺服器的子行程環境 {/* #subprocess-environment-for-stdio-servers */}

Stdio 子行程不會繼承父行程的所有環境變數。預設只繼承 MCP SDK 允許清單中的變數（POSIX：`HOME`、`LOGNAME`、`PATH`、`SHELL`、`TERM`、`USER`；Windows：`APPDATA`、`HOMEDRIVE`、`HOMEPATH`、`LOCALAPPDATA`、`PATH`、`PROCESSOR_ARCHITECTURE`、`SYSTEMDRIVE`、`SYSTEMROOT`、`TEMP`、`USERNAME`、`USERPROFILE`），並與 `env` 中設定的變數合併。API 金鑰等敏感變數必須明確傳入，才會出現在子行程的環境中。

若要更嚴格地隔離環境，可設定 `inheritDefaultEnv: false`，讓子行程只收到 `env` 中設定的項目：

```typescript
const mcp = new MCPClient({
  servers: {
    myTool: {
      command: '/usr/local/bin/my-mcp-server',
      inheritDefaultEnv: false,
      env: { MY_TOOL_API_KEY: process.env.MY_TOOL_API_KEY! },
    },
  },
})
```

`env` 中的變數會原樣傳入子行程，因此請將來源不可信任的伺服器設定（例如使用者提供的設定檔）視為不可信任的輸入。

### 使用 `allowedHosts` 限制對外連線的主機 {/* #restricting-outbound-hosts-with-allowedhosts */}

HTTP 伺服器的 URL 若來自不可信任的設定，攻擊者可能藉由控制 URL，誘使用戶端存取內部服務，造成伺服器端請求偽造。替這類伺服器設定 `allowedHosts`，可限制用戶端能連線的主機：

```typescript
const mcp = new MCPClient({
  servers: {
    remote: {
      url: new URL(untrustedConfig.serverUrl),
      allowedHosts: ['api.example.com'],
    },
  },
})
```

主機驗證規則如下：

* 使用預設的請求機制時，用戶端會在**送出前**封鎖發往未獲允許主機的請求，包括每次重新導向的請求。用戶端會自行處理並驗證每次重新導向，最多 5 次。跨來源重新導向時會移除 `Authorization` 標頭，因此 URL 的通訊協定、主機或連接埠只要有一項改變，就不會帶上該標頭。這與標準 fetch 的行為相同。
* 若提供自訂 `fetch`，用戶端仍會在送出請求前檢查初始 URL，但會在收到回應後才透過 `response.url` **事後驗證**重新導向。對外請求可能已送出。如果最終 URL 指向未獲允許的主機，就會捨棄回應。自行建立的 `Response` 若將 `response.url` 留空，會略過這項事後檢查。
* 透過 `authProvider` 送出的 OAuth 請求也會驗證，包括探索授權伺服器的中繼資料、交換權杖及更新權杖。如果授權伺服器和 MCP 伺服器位於不同主機，也要將授權伺服器的主機加入 `allowedHosts`。
* 如果目標主機遭封鎖，連線會失敗並回報明確的錯誤，重新連線機制不會重試。

`allowedHosts` 只比對完整的主機名稱，且不支援萬用字元或 URL 通訊協定檢查。若要檢查通訊協定或設定 IP 範圍等規則，請提供自訂的 `fetch` 實作。用戶端每次發出請求都會呼叫該實作。

### 將 Tool 回應視為不可信任的輸入 {/* #treat-tool-responses-as-untrusted-input */}

MCP 伺服器傳回的 Tool 結果會成為 Agent 情境中的模型輸入。惡意或遭入侵的伺服器可能透過 Tool 輸出進行提示注入。傳輸層的用戶端不會清理 Tool 回應。可在 Agent 層使用 Mastra 的[輸入與輸出處理器](/docs/agents/processors)，在內容送入模型前及模型輸出後檢查、轉換或阻擋內容。使用第三方伺服器時，請搭配 `requireToolApproval`，並遵循上文關於 `forwardInstructions` 的安全說明。

## 方法 {/* #methods */}

### `listTools()` {/* #listtools */}

取得所有已設定伺服器的 Tool，並在各 Tool 名稱加上伺服器前綴（格式為 `serverName_toolName`），以避免名稱衝突。
可將傳回值傳入 Agent 定義。

結果不包含僅供應用程式使用的 Tool，也就是 `_meta.ui.visibility` 未包含 `"model"` 的 Tool。`listToolsets()` 和 `listToolDefinitions()` 也會排除這些 Tool。

伺服器名稱與 Tool 名稱都可以包含 `_`，不同組合可能產生相同的索引鍵。例如伺服器 `local` 的 Tool `x_status` 和伺服器 `local_x` 的 Tool `status` 都會產生 `local_x_status`。該索引鍵會對應到 `servers` 中排序較後的伺服器所提供的 Tool，用戶端也會記錄警告並列出兩種組合。重新命名其中一台伺服器即可保留兩個 Tool。

```ts
new Agent({ id: 'agent', tools: await mcp.listTools() })
```

### `listToolsWithErrors(options?)` {/* #listtoolswitherrorsoptions */}

取得所有已設定伺服器的 Tool，並以前綴標明各 Tool 所屬的伺服器。若有伺服器無法連線或列出 Tool，也會分別傳回錯誤。

設定 `perServerTimeoutMs`，可限制探索程序等待每台伺服器的時間。期限內完成的伺服器所提供的 Tool 會保留在 `tools` 中，逾時的伺服器會出現在 `errors` 中。`durations` 以毫秒記錄每台伺服器的探索耗時。

```typescript
const { tools, errors, errorDetails, durations } = await mcp.listToolsWithErrors({
  perServerTimeoutMs: 3_000,
})

new Agent({ id: 'agent', tools })
console.log(errors, errorDetails, durations)
```

為維持回溯相容性，`errors` 仍是字串對應表。`errorDetails` 提供相同的錯誤訊息，並在底層錯誤有提供相關資訊時，附上可供程式讀取的 `httpStatus` 和傳輸錯誤 `code` 欄位。若有 HTTP 狀態碼，舊格式的訊息也會附上 `(HTTP nnn)` 後綴。

未傳入選項時，只會省略 `durations`。這個方法一律傳回 `tools`、`errors` 和 `errorDetails`。

### `listToolsets()` {/* #listtoolsets */}

傳回以伺服器名稱為索引鍵的物件，各值包含對應伺服器的 Tool。Tool 保留原始名稱，沒有伺服器前綴。
可在執行時將傳回值傳入生成或串流方法。

```typescript
const res = await agent.stream(prompt, {
  toolsets: await mcp.listToolsets(),
})
```

Agent 依 Tool 名稱合併各組 Tool。若兩台伺服器提供同名的 Tool，例如 `search`，模型只會收到 `servers` 中排序較後的伺服器所提供的 Tool，Agent 也會記錄警告。若要保留兩個 Tool，可將 `listTools()` 傳回的帶前綴 Tool 作為一組傳入：

```typescript
const res = await agent.stream(prompt, {
  toolsets: { mcp: await mcp.listTools() }, // docs_search, tickets_search
})
```

### `listToolsetsWithErrors(options?)` {/* #listtoolsetswitherrorsoptions */}

傳回依伺服器名稱分組的 Tool 集合，以及各伺服器在探索時發生的錯誤。設定 `perServerTimeoutMs` 可分別限制各伺服器的等待時間，並讓 `durations` 以毫秒記錄各伺服器的探索耗時。

```typescript
const { toolsets, errors, errorDetails, durations } = await mcp.listToolsetsWithErrors({
  perServerTimeoutMs: 3_000,
})

const res = await agent.stream(prompt, { toolsets })
console.log(errors, errorDetails, durations)
```

未傳入選項時，只會省略 `durations`。這個方法一律傳回 `toolsets`、`errors` 和 `errorDetails`。

#### 在各伺服器的探索結束時回報結果 {/* #report-each-server-as-it-settles */}

傳回的 Promise 會等到所有伺服器的探索結束後才兌現，因此一台速度較慢的伺服器就會延後整體結果。傳入 `onServerSettled` 可在任一伺服器探索成功、失敗或逾時時立即處理。回呼會收到伺服器名稱、`value`（以該伺服器原始 Tool 名稱為索引鍵的 Tool 集合）或 `error`，以及以毫秒計算的 `duration`。`listToolsWithErrors()` 和 `listToolDefinitionsWithErrors()` 也支援此選項。

```typescript
await mcp.listToolsetsWithErrors({
  perServerTimeoutMs: 60_000,
  onServerSettled: (serverName, { value, error, duration }) => {
    if (error) {
      console.error(`${serverName} failed after ${duration}ms: ${error.message}`)
    } else {
      console.log(`${serverName} ready with ${Object.keys(value).length} tools`)
    }
  },
})
```

回呼擲出的錯誤會記錄在日誌中，探索程序會繼續。`async` 回呼傳回的 Promise 若遭拒絕，也會記錄並處理該拒絕，避免發生未處理的拒絕。

#### 僅探索指定的伺服器 {/* #discover-only-some-servers */}

傳入 `serverNames` 可只探索指定的伺服器，例如只重試逾時的伺服器，無須重新啟動其他伺服器。未設定的名稱會被略過。`listToolsWithErrors()` 和 `listToolDefinitionsWithErrors()` 也支援此選項。

```typescript
const { errorDetails } = await mcp.listToolsetsWithErrors({ perServerTimeoutMs: 3_000 })

// Only servers that timed out are worth retrying. A server that failed for
// another reason (bad config, auth refused) will just fail again.
const timedOut = Object.entries(errorDetails)
  .filter(([, details]) => details.code === MCP_DISCOVERY_TIMEOUT_CODE)
  .map(([serverName]) => serverName)

const retry = await mcp.listToolsetsWithErrors({ serverNames: timedOut })
```

`MCP_DISCOVERY_TIMEOUT_CODE` 由 `@mastra/mcp` 匯出，用於標示 `perServerTimeoutMs` 造成的錯誤，讓你區分伺服器回應逾時與其他故障。

### `listToolDefinitions()` {/* #listtooldefinitions */}

以一般可序列化的定義傳回各伺服器的 Tool，並依伺服器名稱分組。每組都以伺服器提供的原始 Tool 名稱為索引鍵，不採用 `listTools()` 使用的 `serverName_toolName` 格式。

和 `listTools()` 一樣，此方法會排除僅供應用程式使用的 Tool，也就是 `_meta.ui.visibility` 未包含 `"model"` 的 Tool。MCP 應用程式透過主機呼叫這些 Tool，因此不會將它們交給 Agent。

此方法與 `listTools()` 的差異在於，結果不包含函式或對執行中用戶端的參照，因此可透過 `JSON.stringify` 序列化，快取到 Redis 或資料庫，或存成建置產物。每筆定義包含 MCP `tools/list` 回應的名稱、標題、描述、輸入結構描述、輸出結構描述、註解與 `_meta`，以及探索時取得的伺服器名稱、版本和指令。

```typescript
const definitions = await mcp.listToolDefinitions()

await cache.set('mcp-tools', JSON.stringify(definitions))
```

### `listToolDefinitionsWithErrors(options?)` {/* #listtooldefinitionswitherrorsoptions */}

此方法在 `listToolDefinitions()` 的結果之外，也會為每台連線失敗的伺服器傳回錯誤。快取目錄時可使用此方法，避免把探索當下無法使用的伺服器漏出儲存的清單。

設定 `perServerTimeoutMs` 可分別限制每台伺服器的探索時間。傳入選項時，`durations` 會以毫秒記錄各伺服器的探索耗時。

```typescript
const { definitions, errors, errorDetails, durations } = await mcp.listToolDefinitionsWithErrors({
  perServerTimeoutMs: 3_000,
})

if (Object.keys(errors).length === 0) {
  await cache.set('mcp-tools', JSON.stringify(definitions))
}

console.log(errorDetails, durations)
```

未傳入選項時，只會省略 `durations`。這個方法一律傳回 `definitions`、`errors` 和 `errorDetails`。

### `toolFromDefinition()` {/* #toolfromdefinition */}

從快取的定義重建單一可執行的 Tool。用戶端會等到該 Tool 首次執行時才建立連線。

傳回的 Tool 行為與 `listTools()` 傳回的 Tool 相同，包括嚴格模式的中繼資料、核准原則、結構化內容處理、Tool 錯誤處理及重新連線行為。兩種方式都會依伺服器宣告的 `outputSchema` 驗證成功呼叫所傳回的結構化結果。結果若無效，Tool 呼叫就會遭拒絕。MCP 錯誤結果會略過輸出驗證。

未宣告 `$schema` 的 MCP 結構描述會使用 JSON Schema 2020-12。支援本機 `$ref` 和 `$defs` 參照、組合關鍵字及布林子結構描述。為限制驗證不可信任的 Tool 目錄所需的資源，輸入及輸出結構描述最多支援 128 層巢狀子結構描述與 10,000 個子結構描述節點。

`structuredContent` 可以是任何 JSON 值，包括字串、數字、布林值和 `null`。物件和陣列結果還會透過不可列舉的 Mastra 中繼資料屬性提供 MCP 內容與 `_meta` 封裝。純量和 `null` 結果無法附加這些屬性，因此會原樣傳回。

```typescript
const definitions = JSON.parse(await cache.get('mcp-tools'))

const tool = await mcp.toolFromDefinition({
  serverName: 'weather',
  definition: definitions.weather.getForecast,
})
```

### `authenticate()` {/* #authenticate */}

若伺服器的 `MCPOAuthClientProvider` 使用回送重新導向 URL，此方法會執行互動式 OAuth 授權碼流程。本機回呼伺服器會將授權 URL 傳給 Provider 的 `onRedirectToAuthorization` 回呼，並等待瀏覽器傳回授權碼。取得授權碼後，會用它交換權杖並重新連線。請參閱[互動式瀏覽器驗證](#interactive-browser-authentication)。

選填的 `timeoutMs` 限制等待瀏覽器傳回授權碼的時間，預設為 5 分鐘。逾時後呼叫會遭拒絕。

```typescript oxfmt:false
async authenticate(serverName: string, options?: { timeoutMs?: number }): Promise<void>
```

### `getServerAuthState()` {/* #getserverauthstate */}

傳回已設定伺服器的 OAuth 授權狀態。連線嘗試因授權錯誤遭拒絕後為 `'needs-auth'`，伺服器接受 Provider 的憑證後為 `'authorized'`。未設定 `authProvider` 或尚未嘗試連線時為 `undefined`。

```typescript oxfmt:false
getServerAuthState(serverName: string): 'needs-auth' | 'authorized' | undefined
```

### `cancelAuthentication()` {/* #cancelauthentication */}

取消指定伺服器正在進行的 `authenticate()` 流程，避免使用者放棄瀏覽器授權後，用戶端仍無限期等待。此操作會中止流程，包含回呼伺服器繫結連接埠前的準備階段。若本機回呼伺服器正在接聽，也會將它關閉。等待中的 `authenticate()` 呼叫會遭拒絕。成功取消流程時傳回 `true`，當下沒有進行中的流程則傳回 `false`。

取消後 `getServerAuthState()` 的傳回值取決於流程進度。收到 `401` 拒絕後取消時，狀態維持 `'needs-auth'`，可立即重試。若在準備階段取消且尚未嘗試連線，狀態維持原值，通常為 `undefined`。

```typescript oxfmt:false
async cancelAuthentication(serverName: string): Promise<boolean>
```

透過 `MCPClient` 執行個體的 `progress` 屬性可訂閱 MCP 伺服器在 Tool 執行期間發出的進度通知。

    },

await mcpClient.progress.onUpdate('myServer', params => {
  console.log('📊 Progress:', params.progress, '/', params.total)
  if (params.message) console.log('Message:', params.message)
  if (params.progressToken) console.log('Token:', params.progressToken)
})

### `events` 屬性（實驗性） {/* #events-property-experimental */}

透過 `events` 屬性，你可以列出並訂閱實作 [MCP 事件擴充功能（SEP-3415）](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415)的伺服器事件。這樣就能在收到推送到儲存庫等伺服器端事件時做出回應，無須輪詢 Tool。每次事件至少會傳送一次。重新連線或恢復訂閱後，伺服器可能重送同一次事件。用戶端會在 `dedupWindow` 保留的近期 ID 中比對 `eventId`，捨棄重複的事件。

完整操作步驟請參閱 [MCP 事件](/docs/connections/mcp#mcp-events)。

:::warning
SEP-3415 目前仍是草案。此 API 可能在任何版本中變更。
:::

```typescript
const events = await mcpClient.events.list('github')

const subscription = await mcpClient.events.subscribe(
  'github',
  'repo.push',
  { repo: 'mastra-ai/mastra' },
  { cursor: await loadCursor() },
)

for await (const event of subscription) {
  await handlePush(event.data)
  // Safe to persist after each handled occurrence
  await saveCursor(subscription.cursor)
}
```

用戶端不會向未宣告支援 `io.modelcontextprotocol/events` 擴充功能的伺服器傳送 `events/*` 要求。`list()` 傳回的 Promise 會以 ID 為 `MCP_CLIENT_LIST_EVENTS_FAILED` 的 `MastraError` 拒絕，`subscribe()` 則會以 `MCP_CLIENT_SUBSCRIBE_EVENT_FAILED` 拒絕。這兩種情況的 `error.cause.id` 都是 `MCP_EVENTS_NOT_SUPPORTED`。`list()` 和 `subscribe()` 因其他原因失敗時，仍各自使用相同的錯誤 ID，詳細原因記在 `error.cause`。

#### `events.list(serverName: string)` {/* #eventslistservername-string */}

逐頁取得並傳回伺服器提供的所有事件類型。每個事件描述物件都包含 `name`、選用的 `description`、伺服器支援的 `delivery` 模式，以及選用的 `inputSchema` 和 `payloadSchema`。

```typescript oxfmt:false
async list(serverName: string): Promise<MCPEventDescriptor[]>
```

目前，伺服器的事件清單變更時，用戶端不會收到通知。再次呼叫 `list()` 即可取得新增的事件類型。

#### `events.subscribe(serverName, eventName, args?, options?)` {/* #eventssubscribeservername-eventname-args-options */}

發起訂閱，並在伺服器確認後履行傳回的 Promise。若遇到未知事件、無效引數或未獲准訂閱等錯誤，Promise 會遭到拒絕。新訂閱從伺服器接受訂閱的那一刻開始。若要接收之前發生的事件，請透過 `options.cursor` 從較早的位置恢復訂閱。透過 webhook 傳送時，Promise 可能在伺服器接受訂閱後才履行。用戶端若還無法將收到的事件路由至對應的訂閱，就會回應 `503`，伺服器隨後會重試。

```typescript oxfmt:false
async subscribe(
  serverName: string,
  eventName: string,
  args?: Record<string, unknown>,
  options?: MCPEventSubscribeOptions,
): Promise<MCPEventSubscription>
```

用戶端依優先順序選用事件支援的第一種傳送模式：`webhook`（用戶端有 [`webhook` 設定](#webhook-delivery)時才適用）、`push`（長時間維持連線的 `events/stream` 要求），最後是 `poll`（反覆發出 `events/poll` 要求）。若要強制使用特定模式，可傳入 `options.delivery`。

傳回的 `MCPEventSubscription` 是可非同步迭代的物件，逐筆提供事件（`eventId`、`name`、`timestamp`、`data`），並包含下列成員：

* `cursor`：可安全儲存的最新位置，不會越過迴圈尚未收到的事件。事件類型不支援重播時，值為 `null`。
* `truncated`：若伺服器回報迴圈剛收到的事件之前有缺漏，例如儲存的游標已超出事件保留期間，值為 `true`。請在迴圈內讀取此屬性。缺漏後的第一筆事件為 `true`，後續事件為 `false`。
* `mode`：目前採用的傳送模式，值為 `'webhook'`、`'push'` 或 `'poll'`。
* `deliveryStatus`：僅適用於 Webhook 模式。包含伺服器最近一次回報的 Webhook URL 傳送狀態（`active`、`lastDeliveryAt`、`lastError`、`failedSince`），每次續訂時更新。
* `onError(handler)`：接收可復原的錯誤，例如串流中斷且用戶端正在重新開啟串流。傳回可移除該處理函式的函式。
* `cancel()`：停止訂閱並結束迭代。提前離開 `for await` 迴圈也會取消訂閱。

訂閱無法繼續時，迭代器會直接拋出 `MastraError`，不另行包裝。伺服器錯誤無法重試時，錯誤代碼為 `MCP_EVENTS_SUBSCRIPTION_FAILED`。伺服器結束推送或 Webhook 訂閱時，錯誤代碼為 `MCP_EVENTS_SUBSCRIPTION_TERMINATED`。連續失敗 `retry.maxAttempts` 次時，錯誤代碼為 `MCP_EVENTS_RETRIES_EXHAUSTED`。重新連線後，用戶端會重新開啟中斷的串流，並從上一個游標繼續輪詢。透過 `reconnectServer()` 重新連線時也一樣。`disconnect()` 會結束所有訂閱。

#### `events.handleWebhook(request: Request)` {/* #eventshandlewebhookrequest-request */}

處理一次 Webhook 傳送，並傳回要送給伺服器的回應。請將此處理函式掛載至 `webhook.url` 指向的路由。

```typescript oxfmt:false
async handleWebhook(request: Request): Promise<Response>
```

此方法會先驗證原始請求主體的 Standard Webhooks 簽章，再剖析請求主體。它會回應伺服器的驗證交握，並依據 `X-MCP-Subscription-Id` 要求標頭將事件傳送至對應的訂閱。回應狀態碼如下：

* `200`：已將事件交給對應的訂閱。若收到驗證請求，則原樣傳回驗證挑戰值。
* `401`：簽章無效，或時間戳記距今超過 5 分鐘。
* `503`：用戶端尚未辨識該訂閱 ID。伺服器會重試，以處理比訂閱回應更早抵達的事件。
* `400`：請求有簽章，但主體格式有誤。請求方法不是 `POST` 時，則傳回 `405`。
* `413`：請求主體大於 1 MiB。在進行其他檢查前，最多只讀取此上限允許的資料量。
* `404`：用戶端未設定 `webhook`。

#### 透過 Webhook 傳送事件 {/* #webhook-delivery */}

設定 `webhook` 後，用戶端會透過 `events/subscribe` 註冊每項訂閱，伺服器則以 POST 請求將事件傳送至指定網址。伺服器必須驗證用戶端身分，且該網址必須能透過 `https` 公開存取。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { registerApiRoute } from '@mastra/core/server'
import { MCPClient } from '@mastra/mcp'

export const mcpClient = new MCPClient({
  servers: {
    github: {
      url: new URL('https://mcp.example.com/mcp'),
      requestInit: { headers: { Authorization: `Bearer ${process.env.GITHUB_MCP_TOKEN}` } },
    },
  },
  webhook: { url: 'https://agent.example.com/mcp/webhook' },
})

export const mastra = new Mastra({
  server: {
    apiRoutes: [
      registerApiRoute('/mcp/webhook', {
        method: 'POST',
        // Deliveries are authenticated by their signature, not by Mastra auth
        requiresAuth: false,
        handler: c => mcpClient.events.handleWebhook(c.req.raw),
      }),
    ],
  },
})
```

每項訂閱到期前，用戶端會帶著最新的游標再次呼叫 `events/subscribe` 以續訂。若伺服器在 `deliveryStatus` 回報傳送失敗，例如接收端點逾時，`onError` 會收到 `MCP_EVENTS_WEBHOOK_DELIVERY_FAILING`，錯誤詳細資料包含 `lastError`。每次 Webhook 傳送中的 `cursor` 只涵蓋端點已確認的事件，因此從已儲存的游標恢復訂閱時，可能會再次收到最後一筆已處理的事件。下一次續訂會恢復暫停的訂閱。`cancel()` 會送出 `events/unsubscribe`。

Webhook 狀態儲存在目前的處理程序中。接收路由必須與發起訂閱的 `MCPClient` 在同一個處理程序中執行。

透過 Webhook 傳送事件需要與伺服器建立經過身分驗證的 HTTP 連線，因為伺服器會將每項 Webhook 訂閱與呼叫端繫結。若透過 stdio 或未經驗證的 HTTP 連線提出 `events/subscribe`，伺服器會拒絕。達到 Webhook 訂閱數量上限後，伺服器也會拒絕新訂閱（`-32025`）。未強制指定模式的訂閱會改用 `push` 或 `poll`，第一個 `onError` 處理函式會收到 `MCP_EVENTS_WEBHOOK_UNAVAILABLE`，其錯誤詳細資料包含拒絕代碼 `code` 與改用的模式 `fallback`。強制指定 `delivery: 'webhook'` 時，訂閱請求會失敗。

同一台伺服器上，事件名稱和引數相同的訂閱會共用一項伺服器端 Webhook 訂閱。各訂閱透過自己的迭代器取得每筆事件。直到最後一項訂閱取消時，用戶端才會送出 `events/unsubscribe`。

### Agent 與 Workflow 中的事件（實驗性） {/* #events-in-agents-and-workflows-experimental */}

`MCPEventsSignalProvider` 會以通知的形式將 MCP 伺服器事件傳送給 Agent 的執行緒。將它加入 Agent 的 `signals`，再為執行緒訂閱事件。Agent 需要通知儲存網域，`InMemoryStore` 和標準儲存介接器都有提供。

:::警告
SEP-3415 是草案。此 API 可能會在任何版本中發生變更。
:::

```typescript title="src/mastra/agents/repo-agent.ts"
import { Agent } from '@mastra/core/agent'
import { MCPClient, MCPEventsSignalProvider } from '@mastra/mcp'

const mcp = new MCPClient({
  servers: { github: { url: new URL('https://example.com/mcp') } },
})

export const repoEvents = new MCPEventsSignalProvider({
  client: mcp,
  subscribeOptions: { maxAgeMs: 60 * 60 * 1000 },

export const repoAgent = new Agent({
  id: 'repo-agent',
  name: 'Repo Agent',
  instructions: 'Triage repository activity.',
  model: '__GATEWAY_OPENAI_MODEL__',
  signals: [repoEvents],
})

await repoEvents.subscribeThread(
  { resourceId: 'user-1', threadId: 'thread-1' },
  { server: 'github', event: 'repo.push', args: { repo: 'mastra-ai/mastra' } },
)
```

伺服器、事件與引數相同的執行緒會共用一項 MCP 訂閱，引數索引鍵的順序不影響共用。每筆事件都會產生一則通知，其中包含 `kind: 'mcp-event'` 與 `attributes: { server, event }`，原始事件則放在 `payload`。模型只會讀取通知的 `summary`。摘要會將事件標示為不受信任，並將事件資料和伺服器公告的事件名稱一併包在 `<untrusted-mcp-event-data>` 區塊中，區塊內的內容無法結束該區塊。伺服器回報事件有缺漏時，`attributes.truncated` 會是 `true`，摘要也會提示可能略過了部分事件。

Provider 提供下列方法：

* `subscribeThread(thread, { server, event, args? })`：為執行緒訂閱事件，從已儲存的游標繼續接收，並在 MCP 訂閱獲得確認後完成。若伺服器拒絕訂閱，執行緒不會訂閱，Promise 也會遭到拒絕。執行緒的訂閱關係只保存在記憶體中。重新啟動後，請為每個要繼續接收事件的執行緒再次呼叫 `subscribeThread()`。
* `unsubscribeThread(thread, { server, event, args? })`：若執行緒原本已有訂閱，傳回的 Promise 會以 `true` 完成。最後一個執行緒取消訂閱時，會一併取消 MCP 訂閱並刪除已儲存的游標。
* `stop()`：取消所有 MCP 訂閱並保留已儲存的游標。使用相同 `cursorStore` 的新 Provider 可從停止的位置繼續。
* `MCPEventsSignalProvider.key({ server, event, args? })`：傳回游標儲存區使用的訂閱索引鍵。

事件至少會傳送一次。Provider 會先通知執行緒，再儲存游標，因此系統當機前剛發出通知的事件，可能在重新啟動後重播。通知的 `dedupeKey` 包含事件 ID。若第一則通知尚未送達，重播產生的通知會與它合併。若第一則通知已送達，執行緒會再收到一次通知。

process.once('SIGTERM', () => void subscription.cancel())

for await (const event of subscription) {
  const run = await triagePushWorkflow.createRun()
  await run.start({ inputData: { eventId: event.eventId, push: event.data } })
  if (subscription.cursor) await saveCursor(subscription.cursor)

### `tasks` 屬性（實驗性） {/* #tasks-property-experimental */}

有些 Tool 的執行時間會超過單一 HTTP 請求能維持開啟的時間。實作 [MCP Tasks 擴充功能（SEP-2663）](https://modelcontextprotocol.github.io/ext-tasks/specification/2026-07-28/tasks.html) 的伺服器可用工作回應這類呼叫，用戶端稍後再擷取結果。若要接受工作，請在伺服器設定中指定 `tasks`：

```typescript
const mcpClient = new MCPClient({
  servers: {
    reports: {
      url: new URL('https://reports.example.com/mcp'),
      tasks: { maxWaitMs: 30 * 60_000 },
      inputRequests: async ({ params }) => askUser(params),
    },
  },
})
```

:::警告
此 API 可能會在任何版本中發生變更。
:::

設定 `tasks` 後，用戶端會告知伺服器可以接受工作。伺服器會針對每次呼叫決定要直接回應或傳回工作。若未設定 `tasks`，用戶端就不會收到工作，Tool 呼叫的行為維持原樣。

Tool 呼叫傳回工作時，Tool 的呼叫介面保持原樣，用戶端會依下列方式處理：

* 用戶端會依照伺服器建議的間隔輪詢工作，直到工作完成，再傳回 Tool 的結果。
* 工作需要輸入時，用戶端會透過 `inputRequests` 為每個請求索引鍵取得一次答覆，使用 `tasks/update` 送出答覆，再繼續輪詢同一項工作。用戶端不會再次送出 `tools/call`。如果未設定處理函式，Agent 或 Workflow 中的 Tool 呼叫會暫停，讓使用者作答（請參閱[在 Agent 聊天中回覆工作的輸入請求](#answering-task-input-from-the-agent-chat)）。直接呼叫 `tool.execute()` 會因 `MCP_CLIENT_TOOL_TASK_INPUT_UNHANDLED` 而失敗，工作則會在伺服器上維持開啟，直到 TTL 到期。
* 中止 Tool 呼叫時會送出 `tasks/cancel`。達到 `maxWaitMs` 時也會送出該請求，並以 `MCP_CLIENT_TOOL_TASK_TIMEOUT` 結束呼叫。即使輪詢或輸入處理函式仍在執行，這兩種情況都會立即結束呼叫，並捨棄稍後才傳回的回應或答覆。
* 用戶端輪詢期間若執行中斷連線操作，呼叫會因 `MCP_CLIENT_TOOL_TASK_POLL_FAILED` 而失敗，用戶端不會重新連線。
* 如果輪詢期間無法連到伺服器，例如伺服器正在重新啟動或部署，用戶端會重新連線並繼續輪詢，等待間隔逐步增加，最長為 30 秒。連線遭拒，或 Proxy 傳回 HTTP 502、503 或 504，都視為無法連線。若 5 分鐘後仍未收到回應，或先達到 `maxWaitMs` 或工作的 TTL，呼叫會因 `MCP_CLIENT_TOOL_TASK_POLL_FAILED` 而失敗。工作仍可能在伺服器上完成。TTL 自工作的 `createdAt` 起算。若用戶端無法讀取該時間戳記，則從開始等待時起算。
* Tool 呼叫的 span 會加入 `mcpTaskKey` 中繼資料，值為工作 ID 的 SHA-256 雜湊。Mastra 伺服器會以同一個鍵標記該工作的 span，因此可比對兩端的紀錄，且工作 ID 不會出現在任一端的 Trace 中。
* 已完成的工作若包含 Tool 錯誤，會和 Tool 直接傳回的錯誤一樣依 `onToolError` 處理。若伺服器取消工作，呼叫會因 `MCP_CLIENT_TOOL_TASK_CANCELLED` 而失敗。若伺服器將工作標記為 `failed`，呼叫會因 `MCP_CLIENT_TOOL_TASK_FAILED` 而失敗。
* 已傳回工作的呼叫不會重試，因為重試會啟動第二項工作。
* 呼叫轉為工作時，以及工作狀態每次變更時，Tool 會向輸出串流寫入一筆 `MCPTaskProgress` 紀錄（`{ type: 'mcp-task', taskId, status, createdAt, serverName }`）。Studio 的 Tool 呼叫卡片會據此顯示執行中工作的狀態、經過時間與 MCP 工作 ID。Tool 輸出不會隨執行緒儲存，重新載入後卡片只會顯示結果。

Agent 啟用[背景工作](/docs/harness/background-tasks)後，來自已設定 `tasks` 的伺服器的 Tool 會以延後執行的背景工作執行，且不會重試。遠端工作執行期間，Agent 可以繼續運作。取消背景工作也會取消遠端工作。可透過 Agent 的 `backgroundTasks.tools` 個別覆寫各 Tool 的行為。

#### 在 Agent 聊天中回覆工作的輸入請求 {/* #answering-task-input-from-the-agent-chat */}

若工作需要輸入、未設定 `inputRequests` 處理函式，且 Tool 在 Agent 或 Workflow 中執行，Tool 呼叫就會如同呼叫 `suspend()` 時一樣暫停。遠端工作會在伺服器上保持開啟。暫停承載資料（`MCPInputRequestSuspendPayload`）會帶有仍待答覆的請求：

```typescript
const payload: MCPInputRequestSuspendPayload = {
  type: 'mcp-input-request',
  serverName: 'reports',
  toolName: 'approve_and_send',
  taskId: 'Zx81…', // the MCP task the answers go to
  createdAt: '2026-10-30T10:00:00.000Z', // when the task was created
  requestedAt: '2026-10-30T10:00:04.000Z', // when the call suspended; new each time the task asks again
  requests: {
    approve: {
      method: 'elicitation/create',
      params: {
        mode: 'form',
        message: 'Send it?',
        requestedSchema: {
          type: 'object',
          properties: { ok: { type: 'boolean' } },
          required: ['ok'],
        },
      },
    },
  },
}
```

為每個請求索引鍵提供一份答覆（`MCPInputRequestResumeData`），即可繼續 Tool 呼叫。例如，前景呼叫可透過 `agent.resumeStream()` 恢復，延後執行的背景工作則可透過 `backgroundTaskManager.resume()` 恢復：

```typescript
await agent.resumeStream(
  { inputResponses: { approve: { action: 'accept', content: { ok: true } } } },
  { runId, toolCallId },
)
```

恢復時，用戶端會透過 `tasks/update` 將答覆送給同一項工作並繼續輪詢，不會再次送出 `tools/call`。若伺服器再次要求輸入，呼叫會再次暫停，並附上新的請求。若工作已在這段期間結束，呼叫會傳回對應的工作錯誤，例如 `MCP_CLIENT_TOOL_TASK_CANCELLED`。若伺服器已找不到該工作，則傳回 `MCP_CLIENT_TOOL_TASK_POLL_FAILED`。若恢復資料不符合 `{ inputResponses: { [key]: { action: 'accept' | 'decline' | 'cancel', content? } } }` 的格式，或仍有請求未答覆，用戶端會直接以 `MCP_CLIENT_TOOL_TASK_RESUME_INVALID` 結束呼叫，不會聯絡伺服器。

若已設定 `inputRequests` 處理函式，會優先執行該函式，呼叫就不會暫停。

承載資料包含可用來存取工作的 MCP 工作 ID。這個 ID 會與暫停的 Tool 呼叫一併儲存，請比照執行緒的其他資料處理。

#### `tasks.get(serverName: string, taskId: string)` {/* #tasksgetservername-string-taskid-string */}

傳回工作的目前狀態（`MCPDetailedTask`）。狀態為 `completed` 時包含 `result`，狀態為 `input_required` 時包含 `inputRequests`。呼叫失敗時傳回 `MCP_CLIENT_GET_TASK_FAILED`。如果工作不存在或由其他呼叫端建立，`error.cause.code` 為 `-32602`。

#### `tasks.update(serverName: string, taskId: string, inputResponses: MCPTaskInputResponses)` {/* #tasksupdateservername-string-taskid-string-inputresponses-mcptaskinputresponses */}

答覆處於 `input_required` 狀態的工作的 `inputRequests`，答覆使用與請求相同的索引鍵。伺服器會忽略未要求或已答覆的索引鍵。呼叫失敗時傳回 `MCP_CLIENT_UPDATE_TASK_FAILED`。

#### `tasks.cancel(serverName: string, taskId: string)` {/* #taskscancelservername-string-taskid-string */}

要求伺服器停止工作。伺服器仍可能完成該工作。呼叫失敗時傳回 `MCP_CLIENT_CANCEL_TASK_FAILED`。

## 回答輸入請求 {/* #answering-input-requests */}

伺服器上的 Tool、資源或提示若需要使用者提供資料，會以 `input_required` 結果結束呼叫。結果包含一或多個內嵌請求，每個請求都有一個由伺服器指定的 `key`，並附上表單（`requestedSchema`）或使用者必須造訪的網址。若要答覆這些請求，請在伺服器定義中設定 `inputRequests`。用戶端會針對每個內嵌請求呼叫一次處理函式，帶著答覆重試原始呼叫，再以最終結果完成 Tool 呼叫。若未設定處理函式，`input_required` 結果會以錯誤的形式傳回。

```typescript
import { MCPClient } from '@mastra/mcp'

const mcpClient = new MCPClient({
  servers: {
    interactiveServer: {
      url: new URL('http://localhost:3000/mcp'),
      inputRequests: async ({ key, params, signal }) => {
        if (params.mode === 'url') {
          return { action: 'decline' }
        }
        const content = await collectUserInput(params.message, params.requestedSchema, { signal })
        return { action: 'accept', content }
      },
    },
  },
})
```

### `MCPInputRequest` {/* #mcpinputrequest */}

處理函式會收到下列欄位：

* `key`：由伺服器指定，回覆會以這個鍵值記錄。如果同一輪收到多個請求，請將此鍵值傳給使用者介面。
* `params`：請求參數。表單模式包含 `message` 和 `requestedSchema`，其中 `requestedSchema` 是扁平的 JSON Schema 物件，欄位皆為基本型別。網址模式包含 `message` 和 `url`。
* `signal`：發起請求的呼叫取消或逾時時，此訊號會觸發中止。

設定處理函式後，用戶端會向伺服器宣告支援表單模式。若也要接受網址模式的請求，請在同一個伺服器定義中擴充 `capabilities.elicitation` 的設定。

### 回應類型 {/* #response-types */}

傳回一個 `ElicitResult`：

* **接受**：使用者提供資料並確認送出。`content` 必須符合 `requestedSchema`。

  ```typescript
  return {
    action: 'accept',
    content: { name: 'John Doe', email: 'john@example.com' },
  }
  ```

* **拒絕**：使用者明確拒絕提供所要求的資訊。

  ```typescript
  return { action: 'decline' }
  ```

* **取消**：使用者關閉了請求。
  ```typescript
  return { action: 'cancel' }
  ```

使用者拒絕或取消請求時，Tool 呼叫會以錯誤結束。伺服器收到使用者確認送出的回覆後，仍可再次要求輸入，因此一次 Tool 呼叫可能執行處理函式多次。

### 依 Schema 收集輸入 {/* #schema-based-input-collection */}

走訪 `requestedSchema`，逐一提示使用者填寫欄位：

```typescript
inputRequests: async ({ params }) => {
  if (params.mode === 'url') return { action: 'decline' }

  const { properties, required = [] } = params.requestedSchema
  const content: Record<string, string | number | boolean> = {}

  for (const [fieldName, fieldSchema] of Object.entries(properties)) {
    const value = await promptUser({
      name: fieldName,
      title: fieldSchema.title,
      description: fieldSchema.description,
      required: required.includes(fieldName),
    })

    if (value !== null) {
      content[fieldName] = value
    }
  }

  return { action: 'accept', content }
}
```

### 最佳做法 {/* #best-practices */}

* **預先設定處理函式**：在伺服器定義中設定處理函式，確保要求使用者輸入的 Tool 一定有處理函式可用。
* **驗證輸入**：檢查是否提供了必填欄位。
* **尊重使用者的選擇**：妥善處理使用者拒絕或取消的情況。
* **清楚的使用者介面**：說明需要哪些資訊，以及為什麼需要這些資訊。
* **安全性**：切勿自動接受索取敏感資訊的請求。將網址模式請求中的連結視為指向不受信任的網站。

## OAuth 驗證 {/* #oauth-authentication */}

若要連線至依照 [MCP 2026-07-28 授權規格](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)要求 OAuth 驗證的 MCP 伺服器，請使用 `MCPOAuthClientProvider`。該 Provider 不會在執行階段註冊用戶端。請擇一設定：使用 `clientInformation` 提供已在授權伺服器上預先註冊的用戶端資訊，或將[用戶端 ID 中繼資料文件](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration#client-id-metadata-documents)的網址設為 `clientMetadataUrl`：

```typescript
import { MCPClient, MCPOAuthClientProvider } from '@mastra/mcp'

// Create an OAuth provider
const clientMetadataUrl = 'https://app.example.com/oauth/client-metadata.json'

const oauthProvider = new MCPOAuthClientProvider({
  redirectUrl: 'http://localhost:3000/oauth/callback',
  clientMetadataUrl,
  clientMetadata: {
    client_id: clientMetadataUrl,
    redirect_uris: ['http://localhost:3000/oauth/callback'],
    client_name: 'My MCP Client',
    grant_types: ['authorization_code', 'refresh_token'],
    response_types: ['code'],
  },
  onRedirectToAuthorization: url => {
    // Handle authorization redirect (open browser, redirect response, etc.)
    console.log(`Please visit: ${url}`)
  },
})

// Use the provider with MCPClient
const client = new MCPClient({
  servers: {
    protectedServer: {
      url: new URL('https://mcp.example.com/mcp'),
      authProvider: oauthProvider,
    },
  },
})
```

透過 `clientMetadataUrl` 提供的文件必須包含相同的 `client_id`、`client_name` 和 `redirect_uris`。若使用迴路回呼，請在託管的文件中列出 `getCallbackUrlCandidates()` 傳回的所有備用網址。Provider 會將文件網址當成 `client_id` 傳送，且不會呼叫註冊端點。如果授權伺服器既不接受中繼資料文件，也不接受預先註冊的 `clientInformation`，授權流程會明確回報錯誤。用戶端身分只能設定一種，同時設定 `clientInformation` 和 `clientMetadataUrl` 時，建構函式會擲出錯誤。

`MCPOAuthClientProvider` 儲存的權杖會繫結至授權伺服器通過驗證的 `issuer`。Provider 會持久儲存探索狀態，確保只向發出重新導向的伺服器送出授權碼交換請求。迴路回呼也會把 RFC 9207 的 `iss` 參數轉交給 SDK。如果參數與預期值不符，SDK 會在交換授權碼前拒絕請求。

請為每部伺服器建立各自的 `MCPOAuthClientProvider` 執行個體。授權期間，Provider 會保留該伺服器的工作階段與憑證狀態。多部伺服器共用一個執行個體時，各自的授權流程可能會覆寫彼此的狀態。設定多部受保護的伺服器時，請分別建立 Provider。如果這些 Provider 共用同一個持久儲存後端，請為每個 Provider 指定獨立的 `OAuthStorage` 命名空間，因為儲存變更的順序只會在單一 Provider 執行個體內協調。

### 透過瀏覽器進行互動式驗證 {/* #interactive-browser-authentication */}

伺服器因需要授權而拒絕連線時，用戶端會記錄 `'needs-auth'` 狀態，等待進一步處理。呼叫 `authenticate()` 可完成授權流程。這個方法會在 Provider 的迴路重新導向網址上啟動一次性回呼伺服器，通訊埠已被占用時會依序嘗試後續的通訊埠。接著，SDK 會執行探索並使用已設定的用戶端身分。`onRedirectToAuthorization` 會收到授權網址，供應用程式在使用者的瀏覽器中開啟。瀏覽器傳回授權碼後，流程就會完成權杖交換：

```typescript
import { MCPClient, MCPOAuthClientProvider } from '@mastra/mcp'

const clientMetadataUrl = 'https://app.example.com/oauth/client-metadata.json'

const oauthProvider = new MCPOAuthClientProvider({
  redirectUrl: 'http://127.0.0.1:5533/oauth/callback',
  clientMetadataUrl,
  clientMetadata: {
    client_id: clientMetadataUrl,
    redirect_uris: ['http://127.0.0.1:5533/oauth/callback'],
    client_name: 'My MCP Client',
    grant_types: ['authorization_code', 'refresh_token'],
    response_types: ['code'],
  },
  onRedirectToAuthorization: url => {
    // Open the user's browser at the consent page
    console.log(`Please visit: ${url}`)
  },
})

const mcp = new MCPClient({
  servers: {
    protectedServer: {
      url: new URL('https://mcp.example.com/mcp'),
      authProvider: oauthProvider,
    },
  },
})

try {
  await mcp.listTools()
} catch {
  if (mcp.getServerAuthState('protectedServer') === 'needs-auth') {
    await mcp.authenticate('protectedServer')
  }
}
```

同時對同一部伺服器呼叫 `authenticate()` 時，各呼叫會加入進行中的授權流程。不同伺服器各自進行驗證。若已儲存有效的權杖，呼叫會直接重新連線，無須開啟瀏覽器。

自行掌控授權流程的應用程式可以透過匯出的輔助函式 `createOAuthCallbackServer` 取得授權碼。該函式會建立一次性迴路伺服器，先驗證 OAuth 的 `state` 參數，再以授權碼履行 Promise。此伺服器使用未加密的 HTTP，因此僅適用於本機迴路重新導向。使用 HTTPS 重新導向網址的網頁應用程式必須自行託管回呼端點，並直接操作 Provider：

```typescript
import { createOAuthCallbackServer, getCallbackUrlCandidates } from '@mastra/mcp'

// getCallbackUrlCandidates() lists every URL the helper may bind, so list all
// of them as redirect_uris in your pre-registration or metadata document.
const redirectUris = getCallbackUrlCandidates('http://127.0.0.1:5533/oauth/callback').map(url =>
  url.toString(),
)

const server = await createOAuthCallbackServer({
  redirectUrl: 'http://127.0.0.1:5533/oauth/callback',
  state: expectedState,
})

// server.url reflects the port actually bound — use it as the redirect_uri.
try {
  const { code, iss } = await server.waitForCode()
  // Exchange the code here, passing `iss` so the SDK validates the issuer.
} finally {
  await server.close()
}
```

### 自訂權杖儲存方式 {/* #custom-token-storage */}

若要跨工作階段持久儲存權杖，請實作 `OAuthStorage` 介面。Provider 以字串為鍵，儲存權杖（最新一組權杖，以及每個授權伺服器簽發者各一筆記錄）、探索狀態和 PKCE 驗證器。後端只需要提供鍵值儲存介面：

```typescript
import { MCPOAuthClientProvider, OAuthStorage } from '@mastra/mcp'

class DatabaseOAuthStorage implements OAuthStorage {
  constructor(
    private db: Database,
    private userId: string,
  ) {}

  async set(key: string, value: string): Promise<void> {
    await this.db.query(
      'INSERT INTO oauth_tokens (user_id, key, value) VALUES (?, ?, ?) ON CONFLICT DO UPDATE SET value = ?',
      [this.userId, key, value, value],
    )
  }

  async get(key: string): Promise<string | undefined> {
    const result = await this.db.query(
      'SELECT value FROM oauth_tokens WHERE user_id = ? AND key = ?',
      [this.userId, key],
    )
    return result?.[0]?.value
  }

  async delete(key: string): Promise<void> {
    await this.db.query('DELETE FROM oauth_tokens WHERE user_id = ? AND key = ?', [
      this.userId,
      key,
    ])
  }
}

const provider = new MCPOAuthClientProvider({
  redirectUrl: 'http://localhost:3000/callback',
  clientMetadata: {/* ... */},
  clientInformation: { client_id: 'my-registered-client' },
  storage: new DatabaseOAuthStorage(db, 'user-123'),
})
```

### 靜態 Tool 設定 {/* #static-tool-configuration */}

如果整個應用程式共用一條與 MCP 伺服器的連線，請用 `listTools()` 取得 Tool，再將它們傳給 Agent：

```typescript
import { MCPClient } from '@mastra/mcp'
import { Agent } from '@mastra/core/agent'

const mcp = new MCPClient({
  servers: {
    stockPrice: {
      command: 'npx',
      args: ['tsx', 'stock-price.ts'],
      env: {
        API_KEY: 'your-api-key',
      },
      logger: logMessage => {
        console.log(`[${logMessage.level}] ${logMessage.message}`)
      },
    },
    weather: {
      url: new URL('http://localhost:8080/mcp'),
    },
  },
  timeout: 30000, // Global 30s timeout
})

// Create an agent with access to all tools
const agent = new Agent({
  id: 'multi-tool-agent',
  name: 'Multi-tool Agent',
  instructions: 'You have access to multiple tool servers.',
  model: '__GATEWAY_OPENAI_MODEL__',
  tools: await mcp.listTools(),
})

// Example of using resource methods
async function checkWeatherResource() {
  try {
    const weatherResources = await mcp.resources.list()
    if (weatherResources.weather && weatherResources.weather.length > 0) {
      const currentWeatherURI = weatherResources.weather[0].uri
      const weatherData = await mcp.resources.read('weather', currentWeatherURI)
      console.log('Weather data:', weatherData.contents[0].text)
    }
  } catch (error) {
    console.error('Error fetching weather resource:', error)
  }
}
checkWeatherResource()

// Example of using prompt methods
async function checkWeatherPrompt() {
  try {
    const weatherPrompts = await mcp.prompts.list()
    if (weatherPrompts.weather && weatherPrompts.weather.length > 0) {
      const currentWeatherPrompt = weatherPrompts.weather.find(p => p.name === 'current')
      if (currentWeatherPrompt) {
        console.log('Weather prompt:', currentWeatherPrompt)
      } else {
        console.log('Current weather prompt not found')
      }
    }
  } catch (error) {
    console.error('Error fetching weather prompt:', error)
  }
}
checkWeatherPrompt()
```

## 執行個體管理 {/* #instance-management */}

`MCPClient` 類別內建防止多個執行個體造成記憶體洩漏的機制：

1. 若以相同設定建立多個執行個體而未指定 `id`，就會擲出錯誤，以防止記憶體洩漏。
2. 若需要多個採用相同設定的執行個體，請為每個執行個體指定唯一的 `id`。
3. 使用相同設定重新建立執行個體之前，請先執行 `await configuration.disconnect()`。
4. 如果只需要一個執行個體，可以把設定移至外層作用域，避免重複建立。

以下範例嘗試以相同設定建立多個執行個體，但未指定 `id`：

```typescript
// First instance - OK
const mcp1 = new MCPClient({
  servers: {/* ... */},
})

// Second instance with same config - Will throw an error
const mcp2 = new MCPClient({
  servers: {/* ... */},
})

// To fix, either:
// 1. Add unique IDs
const mcp3 = new MCPClient({
  id: 'instance-1',
  servers: {/* ... */},
})

// 2. Or disconnect before recreating
await mcp1.disconnect()
const mcp4 = new MCPClient({
  servers: {/* ... */},
})
```

## 伺服器生命週期 {/* #server-lifecycle */}

MCPClient 會依下列方式管理伺服器連線：

1. 自動管理與多部伺服器的連線
2. 依序關閉伺服器，避免開發期間出現錯誤訊息
3. 中斷連線時清理資源

### 由應用程式管理關閉流程 {/* #handle-shutdown-yourself */}

用戶端建立連線後，預設會註冊 `SIGINT`、`SIGTERM`、`SIGHUP` 和 `beforeExit` 掛鉤，以中斷伺服器連線並結束程序。這些掛鉤可能會中斷應用程式正在等待的清理作業，例如等待處理中的 HTTP 請求全部完成。

將 `registerProcessHooks: false` 設在用戶端設定中，由應用程式接管關閉流程。等使用此用戶端的請求全部完成後，再呼叫 `disconnect()`：

```typescript
import { MCPClient } from '@mastra/mcp'

const mcp = new MCPClient({
  servers: { weather: { url: new URL('https://example.com/mcp') } },
  registerProcessHooks: false,
})

process.once('SIGTERM', async () => {
  // Finish your application's cleanup before disconnecting the client.
  await mcp.disconnect()
  process.exit(0)
})
```

程序中的每個 `MCPClient` 都要在建立連線前設好此選項。只要有任一用戶端註冊了預設掛鉤，即使呼叫 `disconnect()`，全域的 `SIGINT` 和 `SIGTERM` 監聽器仍會保留到程序結束。

停用掛鉤後，應用程式就必須自行關閉 MCP 連線。在 Mastra 伺服器中，請配合伺服器的關閉流程安排呼叫 `disconnect()` 的時機，讓處理中的請求能繼續使用用戶端直到完成。

## 使用自訂 `fetch` 在執行階段進行身分驗證 {/* #using-custom-fetch-for-runtime-defined-authentication */}

連線至 HTTP 伺服器時，可以提供自訂的 `fetch` 函式，處理執行階段的身分驗證、攔截請求，或執行其他自訂邏輯。例如，你可以在每次請求時更新權杖，也可以將傳入請求中的使用者憑證轉送至 MCP 伺服器。

自訂的 `fetch` 函式可接收第三個選用參數 `requestContext`，以存取目前請求的資料，例如中介軟體設定的驗證 Cookie，或執行 Agent 或 Tool 時傳入的持有者權杖。若請求並非由 Tool 呼叫送出，例如 `listTools()` 的請求及其觸發的連線交握，`requestContext` 會是 `null`。如果連線是由 Tool 呼叫建立的，交握就會收到該次呼叫的 `requestContext`。無論是以 `toolsFromDefinitions()` 或 `toolFromDefinition()` 重建的 Tool 在首次執行時連線，還是呼叫時重新連線，都是如此。交握後仍開啟的串流（例如從伺服器傳往用戶端的事件串流）會繼續使用相同的 `requestContext`。用戶端透過串流回覆伺服器請求時也會沿用此參數，例如回覆要求輸入的請求。如果你的程式碼因收到這些串流上的伺服器記錄或通知而發出請求，該請求的 `requestContext` 會是 `null`。

因此，如果伺服器會驗證每一個請求，探索 Tool 和呼叫 Tool 時都需要提供憑證。下例在 Tool 呼叫提供 `requestContext` 時轉送使用者的 Cookie，在沒有該參數時（例如 `listTools()` 的請求）則送出應用程式自己的權杖。所有缺少 `requestContext` 的請求都會帶上該權杖，因此請在伺服器端將權杖的權限限定於探索操作，例如僅允許列出 Tool。

提供 `fetch` 後，就可以在自訂函式內處理請求設定與身分驗證，因此 `requestInit` 和 `authProvider` 都是選用項目。

```typescript
const mcpClient = new MCPClient({
  servers: {
    apiServer: {
      url: new URL('https://api.example.com/mcp'),
      fetch: async (url, init, requestContext) => {
        const headers = new Headers(init?.headers)
        if (requestContext) {
          // A tool call: forward the auth cookie from the incoming request
          const cookie = requestContext.get('cookie')
          if (cookie) {
            headers.set('cookie', cookie)
          }
        } else {
          // No requestContext, as in listTools(): a token the server only accepts for discovery
          headers.set('authorization', `Bearer ${process.env.MCP_DISCOVERY_TOKEN}`)
        }
        return fetch(url, { ...init, headers })
      },
    },
  },
})

// Use with an agent — requestContext is automatically forwarded
const agent = new Agent({
  id: 'my-agent',
  name: 'My Agent',
  instructions: 'You are a helpful assistant.',
  model: openai('gpt-5.4'),
  tools: await mcpClient.listTools(),
})

await agent.generate('Hello!', {
  requestContext: myRequestContext, // forwarded to the custom fetch
})
```

如果伺服器只接受各使用者專屬的憑證，請在啟動時略過 `listTools()`。使用具備自身憑證的用戶端呼叫 [`listToolDefinitions()`](#listtooldefinitions)，建立並儲存 Tool 目錄。例如，可在建置階段透過 `requestInit` 設定靜態標頭。到了執行階段，再以 [`toolsFromDefinitions()`](#toolsfromdefinitions) 重建 Tool。每個重建後的 Tool 都會在首次呼叫時建立連線，交握因此會帶上該次呼叫的 `requestContext`。

## 在自訂 `fetch` 中處理身分驗證失敗 {/* #handling-auth-failures-inside-custom-fetch */}

無法進行身分驗證時，自訂 `fetch` 不應以 `throw` 擲出例外。`tools/call` 等 JSON-RPC 請求使用 `POST`，SDK 會將非 2xx 回應當成錯誤回報給 `listTools()`、`tools/call` 等操作的呼叫端。如果 `fetch` 擲出例外，SDK 也會回報錯誤，但會遺失伺服器的狀態碼和回應主體。連線至使用 2025-11-25 版通訊協定的伺服器時，用戶端還會在交握後送出沒有主體的 `GET`，以開啟從伺服器傳往用戶端的事件串流。因此，請檢查 `init.method`，別假設請求一定帶有 `POST` 主體。長時間保持開啟的串流發生錯誤後會重新開啟，包括用戶端為 `resources.subscribe()` 開啟的 `subscriptions/listen` `POST` 串流，以及中斷的 `GET` 事件串流。未經驗證的 `subscriptions/listen` 串流可能反覆重新連線。請先等待權杖，再轉送請求：

```typescript
async function waitForToken(timeoutMs = 5000): Promise<string | null> {
  // Replace with your token lookup. Return null if no token is available.
  return getAuthToken({ timeoutMs })
}

const mcpClient = new MCPClient({
  servers: {
    apiServer: {
      url: new URL('https://api.example.com/mcp'),
      fetch: async (url, init) => {
        const token = await waitForToken()
        if (!token) {
          // Forward the request without a token and let the server reject it.
          return fetch(url, init)
        }

        const headers = new Headers(init?.headers)
        headers.set('authorization', `Bearer ${token}`)
        return fetch(url, { ...init, headers })
      },
    },
  },
})
```

## 傳送請求標頭 {/* #sending-request-headers */}

請在 `requestInit` 設定靜態標頭。每個請求都會附上這些標頭，包括開啟 `subscriptions/listen` 串流的請求：

```ts
const client = new MCPClient({
  servers: {
    exampleServer: {
      url: new URL('https://your-mcp-server.com/mcp'),
      requestInit: {
        headers: {
          Authorization: 'Bearer your-token',
        },
      },
    },
  },
})
```

如果標頭值因請求而異，請使用自訂的 `fetch`。
