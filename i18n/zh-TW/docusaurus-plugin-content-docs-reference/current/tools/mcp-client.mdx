# MCP客戶端

這`MCPClient`類別提供了一種在 Mastra 應用程式中管理多個 MCP 伺服器連接及其Tool的方法。它處理連接生命週期和Tool命名空間，同時提供對所有已配置伺服器上的Tool的存取。

:::注意
升級自`@mastra/mcp` 1.x? See the [migration guide](/reference/migrations/mcp-v2).
:::

### 鍵入客戶合約 {/* #typed-client-contracts */}

將顯式伺服器映射類型傳遞給`MCPClient<TServers>` to check configured server names, discovered tool names, and direct-call arguments. `MCPClientOptions<TServers>` accepts the same map. All declared servers are required. Use `Pick<TServers, 'weather'>` to configure a subset. Without a type argument, discovery keeps its existing broad types.

地圖描述了每個伺服器的`tools`, with `input` and `output` types for each tool. This example assumes a running weather server at `WEATHER_MCP_URL`:

```typescript
import { MCPClient } from '@mastra/mcp'

interface MCPServers {
  weather: {
    tools: {
      get_weather: {
        input: { location: string }
        output: { temperature: number; conditions: string }
      }
    }
  }
}

const mcp = new MCPClient<MCPServers>({
  servers: { weather: { url: new URL(process.env.WEATHER_MCP_URL!) } },
})

try {
  const tools = await mcp.listTools()
  const weather = tools.weather_get_weather
  if (weather?.execute) {
    const result = await weather.execute({ location: 'Paris' })
    if (result && 'temperature' in result && typeof result.temperature === 'number') {
      console.log(result.temperature)
    }
  }
} finally {
  await mcp.disconnect()
}
```

`listTools()`和`listToolsWithErrors().tools` expose exact `server_tool` keys. `listToolsets()` and `listToolsetsWithErrors().toolsets` expose server keys containing raw tool names. Both forms are partial: a server or tool can be absent. Check availability before calling a tool. Error maps, error details, and optional discovery durations keep their existing types.

執行可以傳回結構化輸出、協定結果信封、驗證錯誤或`undefined`. Check the shape and property types before reading success fields. Protocol envelopes can have additional properties. Set `output: unknown` for tools without an output schema.

这些契约描述了模式快照。实时服务器可能与该快照不同。當伺服器架構更改時，使用等效權限更新它們。額外的即時Tool在運行時仍然可用，但不包含在快照的已知鍵中。运行时发现、验证和执行保持不变。

### 產生客戶端類型 {/* #generate-client-types */}

使用包含在中的命令從實時Tool輸入和輸出模式生成具體的 TypeScript 接口`@mastra/mcp`. Export your existing client and set `typegen.outFile`:

```typescript title="src/mcp/client.ts"
import { MCPClient } from '@mastra/mcp'
import type { MCPServers } from './mcp-types.generated'

export const mcp = new MCPClient<MCPServers>({
  id: 'weather-client',
  servers: { weather: { url: new URL(process.env.WEATHER_MCP_URL!) } },
  typegen: { outFile: 'src/mcp/mcp-types.generated.ts' },
})
```

設定模組所需的環境變數和驗證憑證，然後從專案根目錄執行以下命令：

```bash npm2yarn
npx @mastra/mcp generate ./src/mcp/client.ts
```

第一次運行時產生的僅類型導入可能會遺失。載入器無需類型檢查即可處理 TypeScript 和傳遞導入。產生後運行類型檢查。

使用產生的名稱並檢查運行時可用性和結果形狀。此範例假設伺服器發布`get_weather` with a required string `location` and a numeric `temperature` output:

```typescript title="src/mcp/call-weather.ts"
import { mcp } from './client'

try {
  const tools = await mcp.listTools()
  const weather = tools.weather_get_weather
  if (weather?.execute) {
    const result = await weather.execute({ location: 'Paris' })
    if (result && 'temperature' in result && typeof result.temperature === 'number') {
      console.log(result.temperature)
    }
  }
} finally {
  await mcp.disconnect()
}
```

該命令接受一個或多個檔案路徑。輸入檔和`outFile` paths are relative to the command's working directory. It selects direct named and default exports of typegen-enabled clients. It doesn't scan your source tree, invoke factories, or inspect nested exported objects. Repeated files, symlink aliases, and exports of the same client are processed once. A file without an eligible client fails.

對於具有相同伺服器配置的獨立用戶端，請使用不同的 ID 和輸出路徑：

```typescript title="src/mcp/clients.ts"
import { MCPClient } from '@mastra/mcp'

const servers = { weather: { url: new URL(process.env.WEATHER_MCP_URL!) } }
export const first = new MCPClient({
  id: 'first',
  servers,
  typegen: { outFile: 'first.generated.ts' },
})
export const second = new MCPClient({
  id: 'second',
  servers,
  typegen: { outFile: 'second.generated.ts' },
})
```

```bash npm2yarn
npx @mastra/mcp generate ./src/mcp/clients.ts
```

現有實例快取仍然適用。使用相同的明確 ID、伺服器配置和`typegen.outFile` returns the existing object. A different server configuration or `outFile` replaces the cached instance instead, so a later constructor never silently keeps an output file it wasn't given.

產生列出Tool定義而不呼叫Tool。它会因发现错误、缺少身份验证、超时、输出冲突、覆盖提供的输入文件的输出以及根本无法表示的模式（例如引用循环、深度过大或未解析的本地引用）而失败。每個故障都會命名它所涉及的客戶端文件、伺服器或Tool。它在替換文件之前準備好所有來源，並在成功或失敗時斷開選定的客戶端。發現和預檢失敗會保留現有輸出。每個替換都是原子的，但多個替換不是一個事務。替換期間的檔案系統故障可能會使較早的檔案更新。

使用沒有輸出模式的Tool`unknown`. Constraints such as string formats, length limits, and numeric bounds retain their base TypeScript types and remain runtime validation rules. Unsupported schema portions, including conditional schemas and `prefixItems` tuples, widen to `unknown` with a warning. A keyword whose value is outside its allowed shape widens that schema to `unknown` with a warning too, so one unusable tool doesn't stop generation for other servers. Warnings name the server, tool, and schema position they concern. External schema references aren't fetched. Unresolved local references and reference cycles fail generation. Schemas nested deeper than 128 levels fail generation too, matching the protocol depth limit. A schema that exceeds the protocol node budget of 10,000 widens to `unknown` with a warning, as does any schema or catalogue that exceeds the larger budgets generation applies to raw JSON values. Generation measures those budgets before it copies or converts a schema, so a server that advertises large schemas can't stall the command.

:::note 模組執行與憑證

此命令執行提供的模組及其導入。使用可信任模組，不會對應用程式啟動產生副作用。在呼叫命令之前提供憑證。它不會載入 dotenv 檔案或啟動互動式身份驗證。現有的客戶端逾時和發現設定適用。

生成器診斷忽略原始模式、傳輸錯誤和憑證。由匯入的應用程式、自訂日誌處理程序或伺服器子程序發出的日誌仍不受此保證。

:::

### `MastraMCPServerDefinition` {/* #mastramcpserverdefinition */}

中的每個伺服器`servers` map is configured using the `MastraMCPServerDefinition` type. The transport type is detected based on the provided parameters:

* 如果`command` is provided, it uses the Stdio transport.
* 如果`url` is provided, it uses the Streamable HTTP transport.

客戶端講 MCP`2026-07-28` revision. On connect it asks the server which revisions it offers (`server/discover`) and falls back to the pre-2026 `initialize` handshake for servers that haven't upgraded, so tools, resources and prompts keep working against either. Features the older revisions lack (`resources.subscribe()`, `inputRequests`) fail with an error naming the negotiated revision. `onListChanged()` handlers work against either revision, since older servers send list-changed notifications without a `subscriptions/listen` stream. Set `protocolVersion` to skip the probe.

## Tool審批 {/* #tool-approval */}

使用`requireToolApproval` on a server definition to require human approval before any tool from that server is executed. This works with the existing [human-in-the-loop](/docs/workflows/human-in-the-loop) approval flow.

### 所有Tool都需要批准 {/* #require-approval-for-all-tools */}

放`requireToolApproval` to `true` to require approval for every tool on the server:

```typescript
const mcp = new MCPClient({
  servers: {
    github: {
      url: new URL('http://localhost:3000/mcp'),
      requireToolApproval: true,
    },
  },
})
```

### 動態審核功能 {/* #dynamic-approval-with-a-function */}

傳遞一個函數來決定每次呼叫是否需要批准。此函數接收Tool名稱、模型傳遞的參數、傳入請求的任何請求上下文以及Tool的 MCP`annotations` (when the server advertises them):

```typescript
const mcp = new MCPClient({
  servers: {
    github: {
      url: new URL('http://localhost:3000/mcp'),
      requireToolApproval: ({ toolName, args, requestContext }) => {
        // Read-only tools don't need approval
        if (toolName === 'list_repos') return false
        // Destructive tools with force flag always need approval
        if (toolName === 'delete_repo') return args.force === true
        // Non-admin users need approval for everything else
        return requestContext?.userRole !== 'admin'
      },
    },
  },
})
```

該函數也可以是異步的。它接收`requestContext` from the incoming request, which you can use for auth checks or other per-request logic.

### 使用來自受信任伺服器的Tool註釋 {/* #use-tool-annotations-from-a-trusted-server */}

如果您信任 MCP 伺服器，您可以使用它[tool annotations](https://modelcontextprotocol.io/specification/2025-11-25/server/tools#tool-annotations) (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`, `title`) to drive approval decisions:

```typescript
const mcp = new MCPClient({
  servers: {
    github: {
      url: new URL('http://localhost:3000/mcp'),
      requireToolApproval: ({ annotations }) => {
        // Skip approval for tools the server has marked read-only
        if (annotations?.readOnlyHint) return false
        // Always require approval for destructive tools
        if (annotations?.destructiveHint) return true
        return true
      },
    },
  },
})
```

根據 MCP 規範：**clients MUST consider tool annotations to be untrusted unless they come from trusted servers**. Annotations are advisory hints and provide no security boundary. A malicious or buggy server can claim a tool is read-only when it isn't. Only use annotations to relax approval requirements for servers you trust.

相同的註釋也暴露在返回的Tool上`listTools()` and `listToolsets()` under `tool.mcp.annotations`, so you can inspect them when wiring tools into an agent.

每個Tool還附帶`tool.title`, set from the server's tool `title` and falling back to `annotations.title`. When the server provides neither, `tool.title` is `undefined` and the tool name is the display fallback, matching the MCP display-name precedence.

## 伺服器說明 {/* #server-instructions */}

當MCP伺服器在初始化期間通告指令時，`MCPClient` stores them for that server. Forwarding those instructions into an agent's system prompt is **opt-in**: set `forwardInstructions: true` on a server to have agents that use its tools (via `listTools()` or `listToolsets()`) receive its instructions automatically.

該指南按伺服器名稱分組並截斷為`instructionsMaxLength` characters per server.

```typescript
const mcp = new MCPClient({
  servers: {
    db: {
      url: new URL('http://localhost:3000/mcp'),
      forwardInstructions: true,
      instructionsMaxLength: 512,
    },
  },
})

const agent = new Agent({
  id: 'db-agent',
  name: 'DB Agent',
  instructions: 'Help with database changes.',
  model,
  tools: await mcp.listTools(),
})
```

什麼時候`forwardInstructions` is omitted (the default), instructions are still cached and can be inspected via [`getServerInstructions()`](#getserverinstructions), but aren't added to any agent's system prompt.

> **安全說明：**&#x4F3A;服器指令被逐字轉送（僅受長度截斷）到Agent的系統提示符號。惡意或受損的 MCP 伺服器可以使用它們注入指令，Agent將其視為可信任的系統指導。僅啟用`forwardInstructions` for servers you trust, and prefer reviewing instructions with `getServerInstructions()` before forwarding instructions from third-party servers.

## 安全 {/* #security */}

### Stdio 伺服器的子進程環境 {/* #subprocess-environment-for-stdio-servers */}

Stdio 子行程不會繼承完整的父行程環境。預設情況下，子進程環境從 MCP SDK 的策劃白名單（POSIX：`HOME`, `LOGNAME`, `PATH`, `SHELL`, `TERM`, `USER`; Windows: `APPDATA`, `HOMEDRIVE`, `HOMEPATH`, `LOCALAPPDATA`, `PATH`, `PROCESSOR_ARCHITECTURE`, `SYSTEMDRIVE`, `SYSTEMROOT`, `TEMP`, `USERNAME`, `USERPROFILE`), merged with any variables you set in `env`. Sensitive variables such as API keys aren't inherited unless you pass them explicitly.

為了更嚴格的隔離，設置`inheritDefaultEnv: false` so only your configured `env` entries reach the subprocess:

```typescript
const mcp = new MCPClient({
  servers: {
    myTool: {
      command: '/usr/local/bin/my-mcp-server',
      inheritDefaultEnv: false,
      env: { MY_TOOL_API_KEY: process.env.MY_TOOL_API_KEY! },
    },
  },
})
```

您放入的變數`env` are forwarded verbatim, so treat server configurations that come from untrusted sources (for example, user-supplied config files) as untrusted input.

### 限制出站主機`allowedHosts` {/* #restricting-outbound-hosts-with-allowedhosts */}

當 HTTP 伺服器 URL 來自不受信任的配置時，攻擊者控制的 URL 可以將用戶端指向內部服務（伺服器端請求偽造）。放`allowedHosts` on such servers to restrict which hosts the client will contact:

```typescript
const mcp = new MCPClient({
  servers: {
    remote: {
      url: new URL(untrustedConfig.serverUrl),
      allowedHosts: ['api.example.com'],
    },
  },
})
```

執行詳情：

* 在預設取得路徑上，對不允許的主機的請求（包括每個重定向躍點）都會被阻止**before** they're sent. Redirects are followed manually (up to 5 hops) so each hop is validated, and the `Authorization` header isn't carried across hops to a different origin (any scheme, host, or port change drops it, matching standard fetch behavior).
* 當您提供客製化`fetch`, the initial URL is still checked before the request, but redirect hops are validated **after the fact** using `response.url`: the outbound hop may occur, and the response is discarded when its final URL points at a disallowed host. A hand-built `Response` with an empty `response.url` skips this post-hoc check.
* 透過以下方式發出 OAuth 請求`authProvider` (authorization server metadata discovery, token exchange, refresh) are also validated. If your authorization server runs on a different host than the MCP server, add that host to `allowedHosts` too.
* 被封鎖的主機會因明顯錯誤而導致連線失敗，重新連線邏輯永遠不會重試。

`allowedHosts`有意最小化：它匹配精確的主機並且不支援通配符或方案檢查。如果您需要更丰富的策略（方案检查、IP 范围规则），请提供自定义`fetch` implementation, which is invoked for every request the client makes.

### 將Tool回應視為不受信任的輸入 {/* #treat-tool-responses-as-untrusted-input */}

MCP 伺服器傳回的Tool結果會作為模型輸入流入Agent的上下文中。惡意或受感染的伺服器可以使用Tool輸出進行提示注入。傳輸客戶端不會清理Tool回應：清理策略屬於Agent層，其中 Mastra 的[input and output processors](/docs/agents/processors) let you inspect, transform, or block content before and after it reaches the model. Combine this with `requireToolApproval` and the `forwardInstructions` security note above when working with third-party servers.

## 方法 {/* #methods */}

### `listTools()` {/* #listtools */}

從所有配置的伺服器中檢索所有Tool，Tool名稱按其伺服器名稱命名（格式為`serverName_toolName`) to prevent conflicts.
Intended to be passed onto an Agent definition.

僅限應用程式的Tool，其`_meta.ui.visibility` omits `"model"`, are left out. `listToolsets()` and `listToolDefinitions()` leave them out too.

伺服器名稱和Tool名稱都可以包含`_`, so two different pairs can produce the same key. For example, server `local` with tool `x_status` and server `local_x` with tool `status` both produce `local_x_status`. The tool from the server listed later in `servers` keeps the key, and the client logs a warning that names both pairs. Rename one of the servers to keep both tools.

```ts
new Agent({ id: 'agent', tools: await mcp.listTools() })
```

### `listToolsWithErrors(options?)` {/* #listtoolswitherrorsoptions */}

從所有已配置的伺服器檢索所有Tool，Tool名稱按其伺服器名稱命名。對於無法連接或列出Tool的伺服器，也會傳回每個伺服器的錯誤。

放`perServerTimeoutMs` to limit how long discovery waits for each server. Servers that finish within the limit remain in `tools`. Timed-out servers appear in `errors`, and `durations` reports each server's discovery time in milliseconds.

```typescript
const { tools, errors, errorDetails, durations } = await mcp.listToolsWithErrors({
  perServerTimeoutMs: 3_000,
})

new Agent({ id: 'agent', tools })
console.log(errors, errorDetails, durations)
```

`errors`保留字串映射以實現向後相容性。`errorDetails` provides the same message plus machine-readable `httpStatus` and transport `code` fields when the underlying error exposes them. When an HTTP status is available, the legacy message also includes an `(HTTP nnn)` suffix.

當不帶選項呼叫時，該方法僅省略`durations`; `tools`, `errors`, and `errorDetails` are always returned.

### `listToolsets()` {/* #listtoolsets */}

傳回一個對象，該對象將每個伺服器名稱對應到該伺服器的Tool。Tool保留其原始名稱，沒有伺服器前綴。
旨在在運行時傳遞到生成或流方法。

```typescript
const res = await agent.stream(prompt, {
  toolsets: await mcp.listToolsets(),
})
```

此Agent程式按Tool名稱組合Tool集。當兩個伺服器暴露同名的Tool時，例如`search`, only the tool from the server listed later in `servers` reaches the model, and the agent logs a warning. To keep both tools, pass the prefixed tools from `listTools()` as a single toolset:

```typescript
const res = await agent.stream(prompt, {
  toolsets: { mcp: await mcp.listTools() }, // docs_search, tickets_search
})
```

### `listToolsetsWithErrors(options?)` {/* #listtoolsetswitherrorsoptions */}

傳回按伺服器名稱分組的Tool集以及每個伺服器的發現錯誤。放`perServerTimeoutMs` to limit each server independently and include per-server `durations` in milliseconds.

```typescript
const { toolsets, errors, errorDetails, durations } = await mcp.listToolsetsWithErrors({
  perServerTimeoutMs: 3_000,
})

const res = await agent.stream(prompt, { toolsets })
console.log(errors, errorDetails, durations)
```

當不帶選項呼叫時，該方法僅省略`durations`; `toolsets`, `errors`, and `errorDetails` are always returned.

#### 報告每台伺服器的穩定狀態 {/* #report-each-server-as-it-settles */}

傳回的承諾只有在每台伺服器完成後才會解析，因此一台速度較慢的伺服器會延遲整個結果。經過`onServerSettled` to handle each server as soon as its discovery succeeds, fails, or times out. The callback receives the server name and either `value` (that server's tools, keyed by the server's own tool names) or `error`, plus `duration` in milliseconds. This option is also available on `listToolsWithErrors()` and `listToolDefinitionsWithErrors()`.

```typescript
await mcp.listToolsetsWithErrors({
  perServerTimeoutMs: 60_000,
  onServerSettled: (serverName, { value, error, duration }) => {
    if (error) {
      console.error(`${serverName} failed after ${duration}ms: ${error.message}`)
    } else {
      console.log(`${serverName} ready with ${Object.keys(value).length} tools`)
    }
  },
})
```

回調拋出的錯誤會被記錄下來，並且不會影響發現。對於一個來說也是如此`async` callback that rejects: the rejection is logged and never becomes an unhandled rejection.

#### 僅發現部分伺服器 {/* #discover-only-some-servers */}

經過`serverNames` to discover only the named servers, for example to retry the ones that timed out without starting every other server again. Names that aren't configured are ignored. This option is also available on `listToolsWithErrors()` and `listToolDefinitionsWithErrors()`.

```typescript
const { errorDetails } = await mcp.listToolsetsWithErrors({ perServerTimeoutMs: 3_000 })

// Only servers that timed out are worth retrying. A server that failed for
// another reason (bad config, auth refused) will just fail again.
const timedOut = Object.entries(errorDetails)
  .filter(([, details]) => details.code === MCP_DISCOVERY_TIMEOUT_CODE)
  .map(([serverName]) => serverName)

const retry = await mcp.listToolsetsWithErrors({ serverNames: timedOut })
```

`MCP_DISCOVERY_TIMEOUT_CODE`導出自`@mastra/mcp`. It marks the errors that `perServerTimeoutMs` produced, so you can tell a slow server apart from a broken one.

### `listToolDefinitions()` {/* #listtooldefinitions */}

以簡單的、可序列化的定義形式傳回每個伺服器的Tool，按伺服器名稱分組並按伺服器自己的Tool名稱鍵入（不含`serverName_toolName` namespacing that `listTools()` applies).

喜歡`listTools()`, it leaves out app-only tools, whose `_meta.ui.visibility` omits `"model"`. An MCP App calls those through its host, so they never reach an agent.

不像`listTools()`, the result contains no functions or references to a live client, so it can be passed through `JSON.stringify` and cached in Redis or a database, as well as a build artifact. Each definition holds the data from the MCP `tools/list` response (name, title, description, input schema, output schema, annotations, and `_meta`), plus the server name, version, and instructions captured at discovery time.

```typescript
const definitions = await mcp.listToolDefinitions()

await cache.set('mcp-tools', JSON.stringify(definitions))
```

### `listToolDefinitionsWithErrors(options?)` {/* #listtooldefinitionswitherrorsoptions */}

喜歡`listToolDefinitions()`, but also returns per-server errors for servers that failed to connect. Use this when caching a catalog, so you don't persist a partial manifest that omits a server that was down at discovery time.

放`perServerTimeoutMs` to limit each server independently. When options are provided, `durations` reports each server's discovery time in milliseconds.

```typescript
const { definitions, errors, errorDetails, durations } = await mcp.listToolDefinitionsWithErrors({
  perServerTimeoutMs: 3_000,
})

if (Object.keys(errors).length === 0) {
  await cache.set('mcp-tools', JSON.stringify(definitions))
}

console.log(errorDetails, durations)
```

當不帶選項呼叫時，該方法僅省略`durations`; `definitions`, `errors`, and `errorDetails` are always returned.

### `toolFromDefinition()` {/* #toolfromdefinition */}

從快取的定義重建單一可執行Tool。這裡沒有打開連接。第一次執行該Tool時，客戶端會延遲連線。

返回的Tool的行為與來自的Tool完全相同`listTools()`, with the same strict-mode metadata, approval policy, structured content handling, tool error handling, and reconnect behavior. Successful structured results are validated against the advertised `outputSchema` on both paths. Invalid results reject the tool call. MCP error results skip output validation.

沒有 MCP 模式`$schema` declaration use JSON Schema 2020-12. Local `$ref` and `$defs` references, composition keywords, and boolean subschemas are supported. To bound validation work from untrusted tool catalogs, input and output schemas are limited to 128 nested subschema levels and 10,000 subschema nodes.

`structuredContent`可以是任何 JSON 值，包括字串、數字、布林值和`null`. Object and array results also expose the MCP content and `_meta` envelopes through non-enumerable Mastra metadata properties. Scalar and `null` results can't carry those properties and remain unchanged rather than being wrapped.

```typescript
const definitions = JSON.parse(await cache.get('mcp-tools'))

const tool = await mcp.toolFromDefinition({
  serverName: 'weather',
  definition: definitions.weather.getForecast,
})
```

### `toolsFromDefinitions()` {/* #toolsfromdefinitions */}

將整個快取目錄重建為命名空間Tool映射，無需連接。這是快取的對應項`listTools()`. It produces the same `serverName_toolName` keys, so you can reconstruct an agent's tool map on a cold start, and connections only open for the servers whose tools are actually called.

目錄中存在但不再在客戶端上配置的伺服器將被跳過，因此陳舊的快取清單會正常降級。

```typescript
const definitions = JSON.parse(await cache.get('mcp-tools'))

new Agent({ id: 'agent', tools: await mcp.toolsFromDefinitions({ definitions }) })
```

### `authenticate()` {/* #authenticate */}

為伺服器運行互動式 OAuth 授權程式碼流`MCPOAuthClientProvider` uses a loopback redirect URL. A local callback server passes the authorization URL to the provider's `onRedirectToAuthorization` callback and waits for the browser to return the code. It then exchanges the code for tokens and reconnects. See [Interactive browser authentication](#interactive-browser-authentication).

可選的`timeoutMs` bounds how long the flow waits for the browser to return the authorization code before rejecting, and defaults to 5 minutes.

```typescript oxfmt:false
async authenticate(serverName: string, options?: { timeoutMs?: number }): Promise<void>
```

### `getServerAuthState()` {/* #getserverauthstate */}

傳回已設定伺服器的 OAuth 授權狀態：`'needs-auth'` after a connection attempt was rejected with an authorization error, `'authorized'` once the server accepted the provider's credentials, or `undefined` for servers without an `authProvider` or that haven't attempted a connection yet.

```typescript oxfmt:false
getServerAuthState(serverName: string): 'needs-auth' | 'authorized' | undefined
```

### `cancelAuthentication()` {/* #cancelauthentication */}

取消正在進行的操作`authenticate()` flow for a server, so an abandoned browser authorization doesn't leave the client waiting indefinitely. It aborts the flow (including its setup phase, before the callback server binds), closes the local callback server if one is listening, and the pending `authenticate()` call rejects. Returns `true` if a flow was cancelled, or `false` when no flow was in progress.

由此產生的`getServerAuthState()` depends on how far the flow progressed. A flow cancelled after a `401` rejection stays at `'needs-auth'` and can be retried immediately. Cancellation during setup leaves the state unchanged (typically `undefined`) if no connection was attempted.

```typescript oxfmt:false
async cancelAuthentication(serverName: string): Promise<boolean>
```

返回一個地圖`MCPClientServerProxy` instances, one per configured server. Each proxy wraps the underlying client connection as an `MCPServerBase` instance, allowing external (non-Mastra) MCP servers to be registered in `mcpServers` and appear in Studio.


將結果傳播到`mcpServers` config on `Mastra`:

### `events`性質（實驗） {/* #events-property-experimental */}

這`events` property lists and subscribes to server events from servers that implement the [MCP Events extension (SEP-3415)](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415). Use it to react to things that happen on the server, such as a push to a repository, without polling a tool. Delivery is at least once. After a reconnect or a resume, the server can resend an occurrence, and the client drops repeats by `eventId` within `dedupWindow` of recent ids.

有關端對端演練，請參閱[MCP events](/docs/connections/mcp#mcp-events).

:::警告
SEP-3415 是草案。此 API 可能會在任何版本中發生變更。
:::

```typescript
const events = await mcpClient.events.list('github')

const subscription = await mcpClient.events.subscribe(
  'github',
  'repo.push',
  { repo: 'mastra-ai/mastra' },
  { cursor: await loadCursor() },
)

for await (const event of subscription) {
  await handlePush(event.data)
  // Safe to persist after each handled occurrence
  await saveCursor(subscription.cursor)
}
```

不做廣告的伺服器`io.modelcontextprotocol/events` extension receive no `events/*` requests. `list()` rejects with a `MastraError` whose id is `MCP_CLIENT_LIST_EVENTS_FAILED`, and `subscribe()` rejects with `MCP_CLIENT_SUBSCRIBE_EVENT_FAILED`. In both cases `error.cause.id` is `MCP_EVENTS_NOT_SUPPORTED`. Other `list()` and `subscribe()` failures use the same two ids, with the specific reason in `error.cause`.

#### `events.list(serverName: string)` {/* #eventslistservername-string */}

分頁後傳回伺服器提供的每種事件類型。每個描述符都有一個`name`, an optional `description`, the `delivery` modes the server supports, and optional `inputSchema` and `payloadSchema`.

```typescript oxfmt:false
async list(serverName: string): Promise<MCPEventDescriptor[]>
```

當伺服器的事件清單發生變更時，客戶端不會收到通知。稱呼`list()` again to pick up new event types.

#### `events.subscribe(serverName, eventName, args?, options?)` {/* #eventssubscribeservername-eventname-args-options */}

啟動訂閱並在伺服器確認後解析。未知事件、無效參數或禁止訂閱等錯誤會拒絕傳回的 Promise。新的訂閱從伺服器接受它的那一刻開始，因此不會傳遞該點之前的事件，除非`options.cursor` resumes from an earlier position. Under webhook delivery the promise can resolve after that point: the client answers `503` for a delivery it can't route yet, and the server retries it.

```typescript oxfmt:false
async subscribe(
  serverName: string,
  eventName: string,
  args?: Record<string, unknown>,

): Promise<MCPEventSubscription>
```

返回的`MCPEventSubscription` is an async iterable of occurrences (`eventId`, `name`, `timestamp`, `data`) with these members:

* `cursor`：可以安全堅持的最新立場。它永遠不會越過循環尚未收到的事件。它是`null` when the event type doesn't support replay.
* `truncated`: `true` when the server reported a gap right before the occurrence your loop received last, for example because the saved cursor was older than its retention window. Read it inside the loop: it's `true` for the first occurrence after the gap and `false` for the ones after it.
* `mode`：正在使用的交付模式，`'webhook'`, `'push'`, or `'poll'`.
* `deliveryStatus`：僅限 Webhook 模式。伺服器關於傳送到您的 webhook URL 的最新報告 (`active`, `lastDeliveryAt`, `lastError`, `failedSince`), updated on each refresh.
* `onError(handler)`：接收可恢復的錯誤，例如用戶端重新開啟已刪除的流。傳回一個刪除處理程序的函數。
* `cancel()`：停止訂閱並結束迭代器。突破一個`for await` loop also cancels it.

#### `events.handleWebhook(request: Request)` {/* #eventshandlewebhookrequest-request */}

處理一個 Webhook 傳遞並傳回要傳回的回應。將其安裝在以下路線上`webhook.url` points at.

```typescript oxfmt:false
async handleWebhook(request: Request): Promise<Response>
```

它在解析原始主體之前驗證標準 Webhooks 簽名，應答伺服器的驗證握手，並將事件路由到其訂閱`X-MCP-Subscription-Id` header. It responds with:

* `200`在事件交給其訂閱之後，或帶有驗證請求的回顯質詢。
* `401`當簽名無效或時間戳超過 5 分鐘。
* `503`當訂閱 ID 還不知道。在這種情況下，伺服器會重試，覆蓋在訂閱回應之前到達的交付。
* `400`對於一個簽名但畸形的身體，以及`405` for methods other than `POST`.
* `413`對於超過 1 MiB 的主體。在進行任何其他檢查之前，主體只能讀取該限制。
* `404``webhook` settings.

### `tasks`性質（實驗） {/* #tasks-property-experimental */}

有些Tool需要比一個 HTTP 請求保持開啟狀態更長的時間。一個伺服器實作了[MCP Tasks extension (SEP-2663)](https://modelcontextprotocol.github.io/ext-tasks/specification/2026-07-28/tasks.html) can answer such a call with a task, and the client fetches the result later. Set `tasks` on a server to accept them:

```typescript
const mcpClient = new MCPClient({
  servers: {
    reports: {
      url: new URL('https://reports.example.com/mcp'),
      tasks: { maxWaitMs: 30 * 60_000 },
      inputRequests: async ({ params }) => askUser(params),
    },
  },
})
```

:::警告
此 API 可能會在任何版本中發生變更。
:::

和`tasks` set, the client tells the server it accepts tasks. The server decides per call whether to answer directly or with a task. Without `tasks`, the client never receives one and tool calls behave as before.

當Tool呼叫返回任務時，該Tool會保持其通常的形狀：

* 客戶端依照伺服器建議的時間間隔輪詢任務，直到任務完成，然後傳回Tool結果。
* 需要輸入的任務透過以下方式回答`inputRequests`, once per request key. The client sends the answers with `tasks/update` and keeps polling the same task. It never sends `tools/call` again. Without a handler, a tool call from an agent or workflow suspends so the user can answer (see [Answering task input from the agent chat](#answering-task-input-from-the-agent-chat)). A direct `tool.execute()` call fails with `MCP_CLIENT_TOOL_TASK_INPUT_UNHANDLED`, and the task stays open on the server until its TTL ends.
* 中止Tool呼叫發送`tasks/cancel`. Reaching `maxWaitMs` sends it too, and fails the call with `MCP_CLIENT_TOOL_TASK_TIMEOUT`. Both end the call right away, even while a poll or your input handler is still running. A late answer from either is dropped.
* 客戶端輪詢時斷開連線結束呼叫`MCP_CLIENT_TOOL_TASK_POLL_FAILED` and doesn't reconnect.
* 如果在用戶端輪詢期間（例如在重新啟動或部署期間）無法存取伺服器，用戶端會重新連線並繼續輪詢，延遲會不斷增加，最多可達 30 秒。來自Agent程式的拒絕連線以及 HTTP 502、503 和 504 被視為無法存取。 5 分鐘後沒有得到答复，或者當`maxWaitMs` or the task's TTL ends first, the call fails with `MCP_CLIENT_TOOL_TASK_POLL_FAILED`. The task may still finish on the server. The TTL counts from the task's `createdAt`. If the client can't read that timestamp, it counts from when it started waiting.
* Tool呼叫跨度得到`mcpTaskKey` metadata: a SHA-256 hash of the task id. A Mastra server tags its spans for the task with the same key, so you can match both sides and the task id stays out of both traces.
* 已完成任務中的Tool錯誤的處理方式與直接Tool錯誤類似，如下`onToolError`. A task the server cancelled fails with `MCP_CLIENT_TOOL_TASK_CANCELLED`, and a task the server marked `failed` fails with `MCP_CLIENT_TOOL_TASK_FAILED`.
* 返回任務的呼叫永遠不會重試，因為重試將啟動第二個任務。
* 當呼叫繼續作為任務時，並且只要任務的狀態發生變化，該Tool就會寫入一個`MCPTaskProgress` entry (`{ type: 'mcp-task', taskId, status, createdAt, serverName }`) to its output stream. Studio's tool-call card uses it to show the task's status, elapsed time and MCP task id while it runs. Tool output isn't saved with the thread. After a reload, the card shows only the result.

在Agent商上[background tasks](/docs/harness/background-tasks) enabled, tools from a server with `tasks` set run as deferred background tasks with no retries. The agent keeps working while the remote task runs, and cancelling the background task cancels the remote task. Override this per tool with the agent's `backgroundTasks.tools`.

```typescript
        requestedSchema: {
          type: 'object',
          properties: { ok: { type: 'boolean' } },
          required: ['ok'],
        },
      },
    },
  },
}
```

使用每個請求密鑰一個答案來恢復Tool呼叫 (`MCPInputRequestResumeData`), for example through `agent.resumeStream()` in the foreground, or `backgroundTaskManager.resume()` for a deferred background task:

```typescript
await agent.resumeStream(
  { inputResponses: { approve: { action: 'accept', content: { ok: true } } } },
  { runId, toolCallId },
)
```

在恢復時，客戶端發送相同任務的答案`tasks/update` and keeps polling it. It never sends `tools/call` again. If the server asks again, the call suspends again with the new requests. If the task ended meanwhile, the call fails with the usual task error, such as `MCP_CLIENT_TOOL_TASK_CANCELLED`, or `MCP_CLIENT_TOOL_TASK_POLL_FAILED` when the server no longer knows the task. Resume data that isn't `{ inputResponses: { [key]: { action: 'accept' | 'decline' | 'cancel', content? } } }`, or that leaves a request unanswered, fails with `MCP_CLIENT_TOOL_TASK_RESUME_INVALID` without contacting the server.

已配置的`inputRequests` handler takes precedence: the call then never suspends.

有效負載保存 MCP 任務 ID，該 ID 授予對任務的存取權限。它與掛起的Tool呼叫一起存儲，因此請像對待線程的其餘資料一樣對待它。

#### `tasks.get(serverName: string, taskId: string)` {/* #tasksgetservername-string-taskid-string */}

返回任務的目前狀態（`MCPDetailedTask`), including `result` once it's `completed` and `inputRequests` while it's `input_required`. Fails with `MCP_CLIENT_GET_TASK_FAILED`; an unknown task, or one created by another caller, has `error.cause.code` `-32602`.

#### `tasks.update(serverName: string, taskId: string, inputResponses: MCPTaskInputResponses)` {/* #tasksupdateservername-string-taskid-string-inputresponses-mcptaskinputresponses */}

回答了`inputRequests` of an `input_required` task, keyed like the requests. The server ignores keys it didn't ask for or that are already answered. Fails with `MCP_CLIENT_UPDATE_TASK_FAILED`.

#### `tasks.cancel(serverName: string, taskId: string)` {/* #taskscancelservername-string-taskid-string */}

要求伺服器停止任務。伺服器可能仍會完成它。失敗與`MCP_CLIENT_CANCEL_TASK_FAILED`.

## 回答輸入請求 {/* #answering-input-requests */}

需要使用者提供某些資訊的伺服器Tool、資源或提示以`input_required` result instead of a value. The result carries one or more embedded requests, each with a server-chosen `key` and either a form (`requestedSchema`) or a URL the user must visit. Configure `inputRequests` on the server definition to answer them: the client calls the handler once per embedded request, retries the original call with the answers, and resolves the tool call with the final result. Without a handler an `input_required` result surfaces as an error.

```typescript
import { MCPClient } from '@mastra/mcp'

const mcpClient = new MCPClient({
  servers: {
    interactiveServer: {
      url: new URL('http://localhost:3000/mcp'),
      inputRequests: async ({ key, params, signal }) => {
        if (params.mode === 'url') {
          return { action: 'decline' }
        }
        const content = await collectUserInput(params.message, params.requestedSchema, { signal })
        return { action: 'accept', content }
      },
    },
  },
})
```

### `MCPInputRequest` {/* #mcpinputrequest */}

處理程序接收：

* `key`：伺服器選擇的密鑰，答案被歸檔。當一輪中有多個請求到達時，請將其傳遞到您的 UI。
* `params`: 請求。在表單模式下它有`message` and `requestedSchema`, a flat JSON Schema object of primitive fields. In url mode it has `message` and `url`.
* `signal`：當發起呼叫取消或逾時時中止。

配置處理程序向伺服器通告表單支援。若要同時接受 url 模式請求，請擴大`capabilities.elicitation` on the same server definition.

### 回應類型 {/* #response-types */}

返回一個`ElicitResult`:

* **接受**：用戶提供數據並確認提交。`content` must match `requestedSchema`.

  ```typescript
  return {
    action: 'accept',
    content: { name: 'John Doe', email: 'john@example.com' },
  }
  ```

* **衰退**：用戶明確拒絕提供該資訊。

  ```typescript
  return { action: 'decline' }
  ```

* **取消**：用戶拒絕了請求。
  ```typescript
  return { action: 'cancel' }
  ```

拒絕或取消的請求會結束Tool呼叫並出現錯誤。伺服器可以在接受答案後再次詢問，因此處理程序可能會針對一個Tool呼叫運行多次。

### 基於模式的輸入收集 {/* #schema-based-input-collection */}

走`requestedSchema` to prompt for each field:

```typescript
inputRequests: async ({ params }) => {
  if (params.mode === 'url') return { action: 'decline' }

  const { properties, required = [] } = params.requestedSchema
  const content: Record<string, string | number | boolean> = {}

  for (const [fieldName, fieldSchema] of Object.entries(properties)) {
    const value = await promptUser({
      name: fieldName,
      title: fieldSchema.title,
      description: fieldSchema.description,
      required: required.includes(fieldName),
    })

    if (value !== null) {
      content[fieldName] = value
    }
  }

  return { action: 'accept', content }
}
```

### 最佳實踐 {/* #best-practices */}

* **預先配置處理程序**：它是伺服器定義的一部分，因此要求輸入的Tool永遠不會在沒有輸入的情況下運作。
* **驗證輸入**：檢查是否提供了必填欄位。
* **尊重用戶選擇**：優雅地處理拒絕和取消回覆。
* **清晰的使用者介面**：明確要求提供哪些資訊以及原因。
* **安全**：永遠不要自動接受敏感資訊的請求，並將 url 模式請求視為指向不受信任網站的連結。

## OAuth認證 {/* #oauth-authentication */}

用於連線到需要 OAuth 驗證的 MCP 伺服器[MCP 2026-07-28 authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), use the `MCPOAuthClientProvider`. The provider never registers a client at runtime: give it either `clientInformation` for a client pre-registered with the authorization server, or a [Client ID Metadata Document](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration#client-id-metadata-documents) URL as `clientMetadataUrl`:

```typescript
import { MCPClient, MCPOAuthClientProvider } from '@mastra/mcp'

// Create an OAuth provider
const clientMetadataUrl = 'https://app.example.com/oauth/client-metadata.json'

const oauthProvider = new MCPOAuthClientProvider({
  redirectUrl: 'http://localhost:3000/oauth/callback',
  clientMetadataUrl,
  clientMetadata: {
    client_id: clientMetadataUrl,
    redirect_uris: ['http://localhost:3000/oauth/callback'],
    client_name: 'My MCP Client',
    grant_types: ['authorization_code', 'refresh_token'],
    response_types: ['code'],
  },
  onRedirectToAuthorization: url => {
    // Handle authorization redirect (open browser, redirect response, etc.)
    console.log(`Please visit: ${url}`)
  },
})

// Use the provider with MCPClient
const client = new MCPClient({
  servers: {
    protectedServer: {
      url: new URL('https://mcp.example.com/mcp'),
      authProvider: oauthProvider,
    },
  },
})
```

該文件送達於`clientMetadataUrl` must contain the same `client_id`, `client_name`, and `redirect_uris`. For loopback callbacks, include every fallback URL returned by `getCallbackUrlCandidates()` in the hosted document. The URL is sent as the `client_id`; the provider never calls a registration endpoint, so an authorization server that accepts neither the metadata document nor a pre-registered `clientInformation` fails the flow explicitly. Configure exactly one identity: the constructor throws when both `clientInformation` and `clientMetadataUrl` are set.

保存的令牌`MCPOAuthClientProvider` are bound to the authorization server's validated `issuer`, and discovery state is persisted so the code exchange is only sent to the server that issued the redirect. The loopback callback also forwards the RFC 9207 `iss` parameter to the SDK, which rejects a mismatch before exchanging the authorization code.

給每個伺服器自己的`MCPOAuthClientProvider` instance. A provider holds per-server session and credential state during authorization, so sharing one instance across multiple servers lets their flows overwrite each other. When configuring several protected servers, construct a separate provider for each. If those providers use the same persistent backend, give each provider a separate `OAuthStorage` namespace because storage mutation ordering is coordinated only within one provider instance.

### 互動式瀏覽器身份驗證 {/* #interactive-browser-authentication */}

當伺服器因為需要授權而拒絕連線時，客戶端會記錄一個`'needs-auth'` state instead of failing outright. Calling `authenticate()` completes the flow. It starts a one-shot callback server on the provider's loopback redirect URL, falling back to the next sequential ports when it's in use. The SDK then performs discovery and uses the configured client identity. `onRedirectToAuthorization` receives the authorization URL so your application can open it in the user's browser. The token exchange finishes after the browser returns the authorization code:

```typescript
import { MCPClient, MCPOAuthClientProvider } from '@mastra/mcp'

const clientMetadataUrl = 'https://app.example.com/oauth/client-metadata.json'

const oauthProvider = new MCPOAuthClientProvider({
  redirectUrl: 'http://127.0.0.1:5533/oauth/callback',
  clientMetadataUrl,
  clientMetadata: {
    client_id: clientMetadataUrl,
    redirect_uris: ['http://127.0.0.1:5533/oauth/callback'],
    client_name: 'My MCP Client',
    grant_types: ['authorization_code', 'refresh_token'],
    response_types: ['code'],
  },
  onRedirectToAuthorization: url => {
    // Open the user's browser at the consent page
    console.log(`Please visit: ${url}`)
  },
})

const mcp = new MCPClient({
  servers: {
    protectedServer: {
      url: new URL('https://mcp.example.com/mcp'),
      authProvider: oauthProvider,
    },
  },
})

try {
  await mcp.listTools()
} catch {
  if (mcp.getServerAuthState('protectedServer') === 'needs-auth') {
    await mcp.authenticate('protectedServer')
  }
}
```

並行`authenticate()` calls for the same server join the pending flow. Different servers authenticate independently. With valid stored tokens the call reconnects without opening a browser.

驅動流量的主機可以透過匯出的內容來擷取授權程式碼`createOAuthCallbackServer` helper. It creates a one-shot loopback server that validates the OAuth `state` parameter before resolving with the code. Because the server uses plain HTTP, use it only for local loopback redirects. Web applications with an HTTPS redirect URL must host their own callback endpoint and drive the provider directly:

```typescript
import { createOAuthCallbackServer, getCallbackUrlCandidates } from '@mastra/mcp'

// getCallbackUrlCandidates() lists every URL the helper may bind, so list all
// of them as redirect_uris in your pre-registration or metadata document.
const redirectUris = getCallbackUrlCandidates('http://127.0.0.1:5533/oauth/callback').map(url =>
  url.toString(),
)

const server = await createOAuthCallbackServer({
  redirectUrl: 'http://127.0.0.1:5533/oauth/callback',
  state: expectedState,
})

// server.url reflects the port actually bound — use it as the redirect_uri.
try {
  const { code, iss } = await server.waitForCode()
  // Exchange the code here, passing `iss` so the SDK validates the issuer.
} finally {
  await server.close()
}
```

### 自訂令牌存儲 {/* #custom-token-storage */}

對於跨會話的持久性令牌存儲，實現`OAuthStorage` interface. The provider stores tokens (both the latest set and one entry per authorization-server issuer), discovery state, and the PKCE verifier under string keys. The backend only needs a key-value contract:

```typescript
import { MCPOAuthClientProvider, OAuthStorage } from '@mastra/mcp'

class DatabaseOAuthStorage implements OAuthStorage {
  constructor(
    private db: Database,
    private userId: string,
  ) {}

  async set(key: string, value: string): Promise<void> {
    await this.db.query(
      'INSERT INTO oauth_tokens (user_id, key, value) VALUES (?, ?, ?) ON CONFLICT DO UPDATE SET value = ?',
      [this.userId, key, value, value],
    )
  }

  async get(key: string): Promise<string | undefined> {
    const result = await this.db.query(
      'SELECT value FROM oauth_tokens WHERE user_id = ? AND key = ?',
      [this.userId, key],
    )
    return result?.[0]?.value
  }

  async delete(key: string): Promise<void> {
    await this.db.query('DELETE FROM oauth_tokens WHERE user_id = ? AND key = ?', [
      this.userId,
      key,
    ])
  }
}

const provider = new MCPOAuthClientProvider({
  redirectUrl: 'http://localhost:3000/callback',
  clientMetadata: {/* ... */},
  clientInformation: { client_id: 'my-registered-client' },
  storage: new DatabaseOAuthStorage(db, 'user-123'),
})
```

## 實例管理 {/* #instance-management */}

這`MCPClient` class includes built-in memory leak prevention for managing multiple instances:

1. 建立具有相同配置的多個實例，無需`id` will throw an error to prevent memory leaks
2. 如果您需要具有相同配置的多個實例，請提供唯一的`id` for each instance
3. 稱呼`await configuration.disconnect()` before recreating an instance with the same configuration
4. 如果您只需要一個實例，請考慮將配置移至更高的範圍以避免重新建立

```typescript
// First instance - OK

})

// Second instance with same config - Will throw an error
const mcp2 = new MCPClient({
  servers: {/* ... */},
})

// To fix, either:
// 1. Add unique IDs
const mcp3 = new MCPClient({
  id: 'instance-1',
```

## 伺服器生命週期 {/* #server-lifecycle */}

MCPClient 優雅地處理伺服器連線：

1. 多伺服器自動連線管理
2. 優雅地關閉伺服器以防止開發過程中出現錯誤訊息
3. 斷開連線時正確清理資源

### 自行處理關機 {/* #handle-shutdown-yourself */}

預設情況下，連接的客戶端安裝鉤子`SIGINT`, `SIGTERM`, `SIGHUP`, and `beforeExit` that disconnect its servers and end the process. These hooks can interrupt your application's awaited cleanup, such as draining HTTP requests.

放`registerProcessHooks: false` to let your application own shutdown. Call `disconnect()` after requests that use the client have finished:

```typescript
import { MCPClient } from '@mastra/mcp'

const mcp = new MCPClient({
  servers: { weather: { url: new URL('https://example.com/mcp') } },
  registerProcessHooks: false,
})

process.once('SIGTERM', async () => {
  // Finish your application's cleanup before disconnecting the client.
  await mcp.disconnect()
  process.exit(0)
})
```

設定每個選項`MCPClient` in the process before connecting. Once any client registers the default hooks, the global `SIGINT` and `SIGTERM` listeners remain until the process exits, even after `disconnect()`.

禁用掛鉤後，您的應用程式負責關閉 MCP 連線。在 Mastra 伺服器中，協調`disconnect()` with your server's shutdown lifecycle so in-flight requests can finish using the client.

## 使用自訂取得進行運行時定義的身份驗證 {/* #using-custom-fetch-for-runtime-defined-authentication */}

對於 HTTP 伺服器，您可以提供自訂`fetch` function to handle runtime-defined authentication or request interception. It can also handle other custom behavior. This is particularly useful when you need to refresh tokens on each request or forward user credentials from the incoming request to the MCP server.

習俗`fetch` function receives an optional third `requestContext` parameter, which provides access to request-scoped data (e.g., authentication cookies, bearer tokens) set by middleware or passed during agent/tool execution. The `requestContext` is `null` for requests that no tool call sends, such as `listTools()` and the connection handshake it opens. When a tool call opens the connection, either because a tool rebuilt with `toolsFromDefinitions()` or `toolFromDefinition()` connects on its first execution or because the call reconnects, the handshake receives that call's `requestContext`. Streams the connection keeps open afterward, such as the server-to-client event stream, keep using that same `requestContext`, and so do the client's replies to server requests on them, such as an answer to an input request. A request your own code starts from a server log or notification on those streams gets `null`.

因此，對每個請求進行身份驗證的伺服器需要一個用於發現和Tool呼叫的憑證。以下範例在Tool呼叫提供以下資訊時轉送使用者的 cookie`requestContext`, and sends the app's own token when there's none, as in `listTools()`. Any request without a `requestContext` gets that token, so have the server limit it to discovery, for example listing tools but not calling them.

什麼時候`fetch` is provided, `requestInit` and `authProvider` become optional, as you can handle these concerns within your custom fetch function.

```typescript
const mcpClient = new MCPClient({
  servers: {
    apiServer: {
      url: new URL('https://api.example.com/mcp'),
      fetch: async (url, init, requestContext) => {
        const headers = new Headers(init?.headers)
        if (requestContext) {
          // A tool call: forward the auth cookie from the incoming request
          const cookie = requestContext.get('cookie')
          if (cookie) {
            headers.set('cookie', cookie)
          }
        } else {
          // No requestContext, as in listTools(): a token the server only accepts for discovery
          headers.set('authorization', `Bearer ${process.env.MCP_DISCOVERY_TOKEN}`)
        }
        return fetch(url, { ...init, headers })
      },
    },
  },
})

// Use with an agent — requestContext is automatically forwarded
const agent = new Agent({
  id: 'my-agent',
  name: 'My Agent',
  instructions: 'You are a helpful assistant.',
  model: openai('gpt-5.4'),
  tools: await mcpClient.listTools(),
})

await agent.generate('Hello!', {
  requestContext: myRequestContext, // forwarded to the custom fetch
})
```

如果伺服器僅接受每個使用者憑證，請跳過`listTools()` at startup. Build the catalog with [`listToolDefinitions()`](#listtooldefinitions) from a client that has a credential of its own, for example in a build step with a static `requestInit` header, and store it. At runtime, rebuild the tools with [`toolsFromDefinitions()`](#toolsfromdefinitions). Each rebuilt tool opens the connection on its first call, so the handshake carries that call's `requestContext`.

## 處理自訂取得中的身份驗證失敗 {/* #handling-auth-failures-inside-custom-fetch */}

客製化`fetch` shouldn't `throw` when authentication is unavailable. JSON-RPC requests such as `tools/call` are `POST`s, and the SDK surfaces a non-2xx response as an error to the caller of `listTools()`, `tools/call` and so on, which is the behavior you want. A thrown `fetch` is reported the same way but loses the server's status and body. On a 2025-11-25 server, the client also sends a `GET` with no body after the handshake to open the server-to-client event stream, so check `init.method` rather than assuming a `POST` body. Long-lived streams are reopened after a failure: the `subscriptions/listen` `POST` the client opens for `resources.subscribe()` and the `GET` event stream if it drops. An unauthenticated `subscriptions/listen` stream can loop. Wait for the token, then forward the request:

```typescript
async function waitForToken(timeoutMs = 5000): Promise<string | null> {
  // Replace with your token lookup. Return null if no token is available.
  return getAuthToken({ timeoutMs })
}

const mcpClient = new MCPClient({
  servers: {
    apiServer: {
      url: new URL('https://api.example.com/mcp'),
      fetch: async (url, init) => {
        const token = await waitForToken()
        if (!token) {
          // Forward the request without a token and let the server reject it.
          return fetch(url, init)
        }

        const headers = new Headers(init?.headers)
        headers.set('authorization', `Bearer ${token}`)
        return fetch(url, { ...init, headers })
      },
    },
  },
})
```

## 發送請求標頭 {/* #sending-request-headers */}

靜態標頭進入`requestInit`. They're sent on every request, including the `subscriptions/listen` stream:

```ts
const client = new MCPClient({
  servers: {
    exampleServer: {
      url: new URL('https://your-mcp-server.com/mcp'),
      requestInit: {
        headers: {
          Authorization: 'Bearer your-token',
        },
      },
    },
  },
})
```

使用自訂`fetch` when the value changes per request.
