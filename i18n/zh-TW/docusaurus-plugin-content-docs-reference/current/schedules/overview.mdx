# `mastra.schedules`

**新增於：** `@mastra/core@1.50.0`

`mastra.schedules` 是持久化 cron 排程的 CRUD 服務，可建立、列出、更新、暫停、恢復、手動執行與刪除 Agent 或 Workflow 排程。

用法與相關概念請參閱[排程](/docs/harness/schedules)。

## 傳遞保證 {/* #delivery-guarantees */}

排程事件的發布採盡力而為方式，不保證至少傳遞一次。排程器會以不可分割的操作認領一次觸發，並在發布 Agent 或 Workflow 的啟動事件前推進 `nextFireAt`。若 cron 排程已無後續觸發時機，便會在認領時標記為 `completed`。此狀態只表示沒有剩餘觸發時機，不代表目標已啟動或成功執行。

排程器對同一次已認領的觸發最多嘗試發布三次，前兩次失敗後分別等待 100 毫秒和 200 毫秒。傳輸層可能先接收事件再回傳錯誤，因此重試可能以相同的 run ID 發布重複事件。

三次嘗試都失敗後，排程器會記錄排程 ID、run ID、預定觸發時間、`publicationOutcome: 'unknown'` 與 `automaticReplay: false`，呼叫設定的 `scheduler.onError` 鉤子，並嘗試記錄結果為 `failed` 的觸發事件。這項失敗只描述發布嘗試，無法證明目標從未啟動。

嘗試次數用盡後，排程器不會重播這次觸發。週期性排程仍維持啟用狀態，可在下一個預定時間觸發。已終止的排程仍維持完成狀態，觸發歷史會保留已記錄的失敗詳細資料。

認領成功後，資訊層級的 `Claimed schedule occurrence` 日誌會標示排程 ID、run ID 與預定觸發時間。對應的 `Published schedule occurrence` 日誌表示傳輸層已接收事件。若認領後既沒有成功日誌，也沒有最終失敗日誌，便無法確認發布結果。這些日誌不是持久狀態：認領交易提交後、寫入日誌前，或日誌重新整理前發生當機，都可能沒有日誌紀錄。

若發布程序在認領提交後終止，或確認資訊遺失，該次觸發可能遭到略過，且不會留下失敗的觸發紀錄。接手的排程器無法僅憑認領中繼資料或缺少的觸發歷史，區分事件未發布與事件在當機前已被接收。它不會重播該次觸發，也不會阻止後續的週期性觸發。發布確認亦不保證目標已執行，傳輸層重新傳遞仍可能產生重複事件。

手動重新執行遺漏的工作前，請分別檢查目標執行紀錄與傳輸紀錄。僅憑缺少的觸發歷史或一次發布失敗，無法判定重新執行是否安全。

## 使用範例 {/* #usage-example */}

建立 Agent 排程：

```typescript title="src/mastra/schedules.ts"
const schedule = await mastra.schedules.create({
  agentId: 'pinger',
  cron: '0 * * * *',
  prompt: 'Give me a status update.',
})
```

建立 Workflow 排程：

```typescript title="src/mastra/schedules.ts"
const schedule = await mastra.schedules.create({
  workflowId: 'daily-report',
  cron: '0 9 * * *',
  inputData: { reportType: 'summary' },
})
```

排程需要實作 schedules 領域的儲存配接器。支援的配接器包括 `@mastra/libsql`、`@mastra/pg`、`@mastra/mysql`、`@mastra/mongodb`、`@mastra/convex` 和 `@mastra/spanner`。

若要在固定時間執行一次，請傳入 `runAt` 而非 `cron`：

```typescript
await mastra.schedules.create({
  workflowId: 'send-report',
  runAt: new Date(Date.now() + 60 * 60 * 1000), // One hour from now
})
```

### 讀取排程 {/* #read-schedules */}

```typescript
const schedule = await mastra.schedules.get('pinger')
```

const schedules = await mastra.schedules.list({
  agentId: 'pinger',
  status: 'active',
})

### 更新排程 {/* #update-schedules */}

#### `update(id, patch)` {/* #updateid-patch */}

更新排程。變更 `cron` 或 `timezone` 會重新計算下次觸發時間。將 `status` 從 `paused` 改為 `active` 也會重新計算。cron 不再有未來觸發時機時，排程會轉為 `completed`。即使排程處於 `paused`，若調整頻率後沒有未來觸發時機，該紀錄仍會完成。修改已完成排程的頻率後，若新頻率仍可觸發就會重新啟用，否則維持完成狀態。

```typescript
const updated = await mastra.schedules.update('pinger', {
  cron: '*/30 * * * *',
  prompt: 'Give me a status update every 30 minutes.',
})
```

Agent 排程可更新 `cron`、`timezone`、`prompt`、`name`、`signalType`、`tagName`、`attributes`、`providerOptions`、`ifActive`、`ifIdle`、`metadata` 與 `status`。`threadId` 和 `resourceId` 無法透過修補更新；若要變更目標執行緒，請建立新排程。

Workflow 排程可更新 `cron`、`timezone`、`inputData`、`initialState`、`requestContext`、`resourceId`、`metadata` 與 `status`。對 Workflow 排程傳入 `prompt`、`signalType` 或 `ifIdle` 等 Agent 專用修補欄位會擲出錯誤。

### 生命週期 {/* #lifecycle */}

#### `pause(id)` {/* #pauseid */}

暫停排程。暫停操作會持久保存，重複執行也不會改變結果。暫停 `completed` 排程會擲出 `409` 錯誤。

```typescript
const paused = await mastra.schedules.pause('pinger')
```

#### `resume(id)` {/* #resumeid */}

恢復已暫停的排程，並從目前時間重新計算下次觸發時間。單次排程會保留原本的 `runAt`；若暫停期間已超過該時間，排程會在排程器下次輪詢時觸發。暫停中的 cron 排程若沒有未來觸發時機，會轉為完成狀態而非恢復。恢復 `completed` 排程會擲出 `409` 錯誤；若要重新啟用，請更新觸發時間。

```typescript
const active = await mastra.schedules.resume('pinger')
```

#### `run(id)` {/* #runid */}

立即手動觸發排程一次，不變更其 cron 頻率。

```typescript
const run = await mastra.schedules.run('pinger')
```

Agent 排程的 `claimId` 使用 `manual_<scheduleId>_<timestamp>`；Workflow 排程的 `claimId` 使用 `sched_<scheduleId>_<timestamp>`，並沿用作 Workflow run ID。

#### `delete(id)` {/* #deleteid */}

刪除排程。刪除不存在的排程不會產生任何效果。

```typescript
await mastra.schedules.delete('pinger')
```

## 排程行為 {/* #schedule-behavior */}

- Agent 排程 ID 使用 `agent_` 前綴。透過 `mastra.schedules.create()` 建立的 Workflow 排程 ID 使用 `schedule_` 前綴。
- 使用執行緒的 Agent 排程需要 `resourceId`，前提是已設定 `threadId`。
- 對 Agent 排程而言，`signalType`、`ifActive`、`ifIdle` 與 `resourceId` 都需要 `threadId`。Workflow 排程不使用執行緒也可接受 `resourceId`。
- Workflow 排程不接受 `prompt`、`signalType` 或 `ifIdle` 等 Agent 專用修補欄位。
- `run()` 會立即發布一次手動觸發，不變更已儲存的 cron 頻率。
- 排程有 `active`、`paused` 與 `completed` 三種狀態。當沒有剩餘的自動觸發時機時，排程會轉為 `completed`：單次排程觸發後、設有結束時間或已用盡的 cron 排程沒有未來觸發時機時，或宣告式註冊發現預定時間已過時。`update()` 與 `resume()` 也會將已用盡的 cron 排程標記為完成。`run()` 不會讓單次排程完成。
- 更新單次排程的 `runAt`，或更新 cron 排程的 `endAt`（設為 `null` 可移除結束限制）時，只有新時間仍可觸發，才會重新啟用 `completed` 排程。如果新的 `endAt` 之前沒有 cron 觸發時機，排程仍維持完成狀態。
- `list()` 預設不顯示 `completed` 排程；傳入 `status: 'completed'` 才會顯示。
