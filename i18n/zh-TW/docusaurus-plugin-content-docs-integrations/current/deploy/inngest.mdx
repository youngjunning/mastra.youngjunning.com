# Inngest

[Inngest](https://www.inngest.com/docs) 是建置及執行背景 Workflow 的開發平台，無須自行管理基礎設施。

如需包含進階流量控制功能的完整範例，請參閱 [Inngest Workflow 範例](https://github.com/mastra-ai/mastra/tree/main/examples/inngest)。

## Inngest 如何與 Mastra 搭配運作 {/* #how-inngest-works-with-mastra */}

Inngest 與 Mastra 透過對應各自的 Workflow 模型進行整合：Inngest 將邏輯組織為由步驟構成的函式，而使用 `createWorkflow()` 和 `createStep()` 定義的 Mastra Workflow 可直接對應到這項結構。每個 Mastra Workflow 都會成為具有唯一識別碼的 Inngest 函式，其中每個步驟則對應一個 Inngest 步驟。

`serve()` 會將 Mastra Workflow 註冊為 Inngest 函式，並設定執行與監控所需的事件處理常式，藉此串接兩個系統。

事件觸發 Workflow 後，Inngest 會逐步執行並快取每個步驟的結果。重試或恢復執行時，Inngest 會依據已儲存的結果略過完成的步驟。迴圈、條件分支及巢狀 Workflow 等 Mastra 控制流程原語，也會對應至相同的 Inngest 函式與步驟模型，同時保留組合、分支及暫停功能。

Inngest 的發布訂閱系統與控制台提供即時監控、暫停與恢復執行，以及步驟層級的可觀測性。每個步驟執行時，系統都會透過 Mastra 儲存空間追蹤其狀態與輸出，並可視需要恢復執行。

## 設定 {/* #setup */}

安裝所需套件：

```bash npm2yarn
npm install @mastra/inngest@latest inngest
```

:::note
需要 `inngest@^4`，以及 `v1.18.0` 或更新版本的 Inngest Dev Server。v4 SDK 已內建即時功能，因此不再使用 `@inngest/realtime` 和 `realtimeMiddleware`。
:::

## 建立 Inngest Workflow {/* #building-an-inngest-workflow */}

本指南以數值逐次增加至 10 的計數器應用程式為例，說明如何使用 Inngest 與 Mastra 建立 Workflow。

### 初始化 Inngest {/* #inngest-initialization */}

初始化 Inngest 整合，以取得與 Mastra 相容的 Workflow 輔助函式。`createWorkflow()` 與 `createStep()` 用來建立同時相容於 Mastra 和 Inngest 的 Workflow 與步驟物件。

開發環境：

```ts title="src/mastra/inngest/index.ts"
import { Inngest } from 'inngest'

export const inngest = new Inngest({
  id: 'mastra',
  baseUrl: 'http://localhost:8288',
  isDev: true,
})
```

正式環境：

```ts title="src/mastra/inngest/index.ts"
import { Inngest } from 'inngest'

export const inngest = new Inngest({
  id: 'mastra',
})
```

#### 使用 `INNGEST_DEV` 選擇開發或雲端模式 {/* #selecting-dev-or-cloud-mode-with-inngest_dev */}

Inngest SDK 可在開發或雲端模式下運作。自 v4 起，SDK 預設使用雲端模式，並要求提供 `INNGEST_EVENT_KEY` 和 `INNGEST_SIGNING_KEY`。上述範例透過程式碼中的 `isDev: true` 設定模式。你也可以設定 [`INNGEST_DEV` 環境變數](https://www.inngest.com/docs/sdk/environment-variables#inngest-dev)，讓同一份用戶端程式碼適用於不同環境：

- `INNGEST_DEV=1`：強制使用開發模式。SDK 連線至本機 Inngest Dev Server，並停用簽章驗證。
- `INNGEST_DEV=0`：強制使用雲端模式。SDK 連線至 Inngest Cloud，並要求提供事件金鑰與簽署金鑰。
- `INNGEST_DEV=<url>`：強制使用開發模式，並讓 SDK 連線至 `<url>` 指定的 Dev Server，例如 `http://localhost:8288`。
- 未設定：預設使用雲端模式。

設定 `INNGEST_DEV` 後，即可從用戶端設定中移除 `isDev` 和 `baseUrl`：

```ts title="src/mastra/inngest/index.ts"
import { Inngest } from 'inngest'

export const inngest = new Inngest({
  id: 'mastra',
})
```

:::warning
請勿在正式環境設定 `INNGEST_DEV`。這會停用簽章驗證，而安全接收 Inngest Cloud 事件必須驗證簽章。
:::

若兩者都已設定，`new Inngest()` 的 `isDev` 選項會優先於 `INNGEST_DEV`。

### 建立步驟 {/* #creating-steps */}

定義組成 Workflow 的各個步驟：

```ts title="src/mastra/workflows/index.ts"
import { z } from 'zod'
import { inngest } from '../inngest'
import { init } from '@mastra/inngest'

// Initialize Inngest with Mastra, pointing to your local Inngest server
const { createWorkflow, createStep } = init(inngest)

// Step: Increment the counter value
const incrementStep = createStep({
  id: 'increment',
  inputSchema: z.object({
    value: z.number(),
  }),
  outputSchema: z.object({
    value: z.number(),
  }),
  execute: async ({ inputData }) => {
    return { value: inputData.value + 1 }
  },
})
```

### 建立 Workflow {/* #creating-the-workflow */}

使用 `dountil` 迴圈模式將步驟組合成 Workflow。`createWorkflow()` 會在 Inngest 伺服器上建立可呼叫的函式。

```ts title="src/mastra/workflows/index.ts"
// workflow that is registered as a function on inngest server
const workflow = createWorkflow({
  id: 'increment-workflow',
  inputSchema: z.object({
    value: z.number(),
  }),
  outputSchema: z.object({
    value: z.number(),
  }),
}).then(incrementStep)

workflow.commit()

export { workflow as incrementWorkflow }
```

### 設定 Mastra 執行個體 {/* #configuring-the-mastra-instance */}

向 Mastra 註冊 Workflow，並設定 Inngest API 端點：

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { serve } from '@mastra/inngest'
import { incrementWorkflow } from './workflows'
import { inngest } from './inngest'
import { PinoLogger } from '@mastra/loggers'

export const mastra = new Mastra({
  workflows: { incrementWorkflow },
  server: {
    host: '0.0.0.0',
    apiRoutes: [
      {
        path: '/inngest/api',
        method: 'ALL',
        createHandler: async ({ mastra }) => {
          return serve({ mastra, inngest })
        },
      },
    ],
  },
  logger: new PinoLogger({ name: 'Mastra', level: 'info' }),
})
```

:::note
此處路徑為 `/inngest/api`，不是 `/api/inngest`。Mastra 將 `/api` 前綴保留給內建路由（Agent、Workflow、memory）。自訂 `apiRoutes` 路徑若以伺服器的 `apiPrefix`（預設為 `/api`）開頭，啟動時會發生錯誤。背景資訊請參閱 [#15743](https://github.com/mastra-ai/mastra/pull/15743)；若需保留 `/api/inngest`，請參閱[使用自訂 `apiPrefix`](#using-a-custom-apiprefix)。
:::

## 執行 Workflow {/* #running-workflows */}

### 在本機執行 {/* #running-locally */}

1. 執行 `npx mastra dev`，在本機的 4111 連接埠啟動 Mastra 伺服器

2. 啟動 Inngest Dev Server。在新的終端機視窗執行：

   ```bash
   npx inngest-cli@latest dev -u http://localhost:4111/inngest/api
   ```

   :::note
   `-u` 後面的 URL 會告訴 Inngest Dev Server 到哪裡存取 Mastra 的 `/inngest/api` 端點
   :::

3. 在 [http://localhost:8288](http://localhost:8288) 開啟 Inngest 控制台，前往側邊欄的 **Apps**，確認 Mastra Workflow 已註冊

4. 在 **Functions** 開啟你的 Workflow，選取 **Invoke**，並提供以下輸入：

   ```json
   {
     "data": {
       "inputData": {
         "value": 5
       }
     }
   }
   ```

5. 在 **Runs** 分頁監看 Workflow 的執行狀況與各步驟進度

### 在正式環境執行 {/* #running-in-production */}

開始前，請確認已備妥：

- Vercel 帳號，並已安裝 Vercel CLI（`npm i -g vercel`）
- Inngest 帳號
- Vercel 權杖

1. 在環境中設定 Vercel 權杖：

   ```bash title=".env"
   export VERCEL_TOKEN=your_vercel_token
   ```

2. 在 Mastra 執行個體中加入 `VercelDeployer`

   ```ts title="src/mastra/index.ts"
   import { VercelDeployer } from '@mastra/deployer-vercel'
   import { Mastra } from '@mastra/core'

   export const mastra = new Mastra({
     deployer: new VercelDeployer({
       teamSlug: 'your_team_slug',
       projectName: 'your_project_name',
       // you can get your vercel token from the vercel dashboard by clicking on the user icon in the top right corner
       // and then clicking on "Account Settings" and then clicking on "Tokens" on the left sidebar.
       token: process.env.VERCEL_TOKEN,
     }),
   })
   ```

3. 建置 Mastra 執行個體

   ```bash
   npx mastra build
   ```

4. 部署至 Vercel

   ```bash
   cd .mastra/output
   vercel login
   vercel --prod
   ```

5. 在 [Inngest 控制台](https://app.inngest.com/env/production/apps)選取 **Sync new app with Vercel**，依照指示同步應用程式

   :::warning
   Inngest 的自動探索慣例使用 `/api/inngest`。本指南使用 `/inngest/api`，因此請將 Inngest 應用程式的 **URL** 欄位設為部署後的來源網址加上 `/inngest/api`，例如 `https://your-app.vercel.app/inngest/api`。若保留預設值，Inngest 控制台將找不到應用程式的函式。
   :::

6. 在 **Functions** 開啟 `workflow.increment-workflow`，選取 **All actions** > **Invoke**，並提供以下輸入：

   ```json
   {
     "data": {
       "inputData": {
         "value": 5
       }
     }
   }
   ```

7. 在 **Runs** 分頁監看執行狀況與各步驟進度

## 加入自訂 Inngest 函式 {/* #adding-custom-inngest-functions */}

透過 `serve()` 的選用 `functions` 參數，你可以在提供 Mastra Workflow 的同時提供其他 Inngest 函式。

### 建立自訂函式 {/* #creating-custom-functions */}

首先，建立自訂 Inngest 函式：

```ts title="src/inngest/custom-functions.ts"
import { inngest } from '../inngest'

// Define custom Inngest functions
export const customEmailFunction = inngest.createFunction(
  { id: 'send-welcome-email' },
  { event: 'user/registered' },
  async ({ event }) => {
    // Custom email logic here
    console.log(`Sending welcome email to ${event.data.email}`)
    return { status: 'email_sent' }
  },
)

export const customWebhookFunction = inngest.createFunction(
  { id: 'process-webhook' },
  { event: 'webhook/received' },
  async ({ event }) => {
    // Custom webhook processing
    console.log(`Processing webhook: ${event.data.type}`)
    return { processed: true }
  },
)
```

### 同時提供自訂函式與 Workflow {/* #serving-custom-functions-with-workflows */}

更新 Mastra 設定，匯入並加入自訂函式。醒目標示的程式碼行即為新增內容：

```ts title="src/mastra/index.ts" {5-8,23}
import { Mastra } from '@mastra/core'
import { serve } from '@mastra/inngest'
import { incrementWorkflow } from './workflows'
import { inngest } from './inngest'
import { customEmailFunction, customWebhookFunction } from './inngest/custom-functions'
import { PinoLogger } from '@mastra/loggers'

export const mastra = new Mastra({
  workflows: { incrementWorkflow },
  server: {
    host: '0.0.0.0',
    apiRoutes: [
      {
        path: '/inngest/api',
        method: 'ALL',
        createHandler: async ({ mastra }) => {
          return serve({
            mastra,
            inngest,
            functions: [customEmailFunction, customWebhookFunction],
          })
        },
      },
    ],
  },
  logger: new PinoLogger({ name: 'Mastra', level: 'info' }),
})
```

### 函式註冊 {/* #function-registration */}

加入自訂函式後：

1. Mastra Workflow 會自動轉換為 Inngest 函式，ID 格式如 `workflow.${workflowId}`
2. 自訂函式會保留指定的 ID，例如 `send-welcome-email`、`process-webhook`
3. 所有函式都由同一個 `/inngest/api` 端點提供

如此即可結合 Mastra 的 Workflow 編排功能與既有的 Inngest 函式。

## 與其他框架一起使用 {/* #using-with-other-frameworks */}

預設的 `serve` 函式內部使用 Hono。若使用 Express、Fastify 或 Koa 等其他 Web 框架，請搭配對應的 Inngest 轉接器使用 `createServe` 工廠函式。

### Express {/* #express */}

```ts title="src/server.ts"
import express from 'express'
import { createServe } from '@mastra/inngest'
import { serve as expressAdapter } from 'inngest/express'
import { mastra, inngest } from './mastra'

const app = express()

// Body parsing middleware required for Inngest
app.use(express.json())

const handler = createServe(expressAdapter)({ mastra, inngest })
app.use('/inngest/api', handler)

app.listen(3000)
```

### Fastify {/* #fastify */}

```ts title="src/server.ts"
import Fastify from 'fastify'
import { createServe } from '@mastra/inngest'
import { serve as fastifyAdapter } from 'inngest/fastify'
import { mastra, inngest } from './mastra'

const fastify = Fastify()

// JSON parsing is handled by Fastify's default content-type parser
const handler = createServe(fastifyAdapter)({ mastra, inngest })

fastify.route({
  method: ['GET', 'POST', 'PUT'],
  url: '/inngest/api',
  handler,
})

fastify.listen({ port: 3000 })
```

### Koa {/* #koa */}

```ts title="src/server.ts"
import Koa from 'koa'
import Router from '@koa/router'
import bodyParser from 'koa-bodyparser'
import { createServe } from '@mastra/inngest'
import { serve as koaAdapter } from 'inngest/koa'
import { mastra, inngest } from './mastra'

const app = new Koa()
const router = new Router()

// Body parsing middleware required for Inngest
app.use(bodyParser())

const handler = createServe(koaAdapter)({ mastra, inngest })
router.all('/inngest/api', handler)

app.use(router.routes())
app.use(router.allowedMethods())

app.listen(3000)
```

### Next.js {/* #nextjs */}

```ts title="app/inngest/api/route.ts"
import { createServe } from '@mastra/inngest'
import { serve as nextAdapter } from 'inngest/next'
import { mastra, inngest } from '@/mastra'

const handler = createServe(nextAdapter)({ mastra, inngest })

export { handler as GET, handler as POST, handler as PUT }
```

### 可用轉接器 {/* #available-adapters */}

`createServe` 可搭配任何 Inngest 轉接器使用。完整清單（包括 AWS Lambda、Cloudflare Workers 等）請參閱 [Inngest serve 文件](https://www.inngest.com/docs/reference/serve)。

## 作為 Connect worker 執行 {/* #running-as-a-connect-worker */}

`serve()` 會公開供 Inngest 呼叫的 HTTP 端點。另一種方式是透過 `connect()`，讓 worker 主動與 Inngest 建立長時間連線，使 worker 無須具備可公開存取的端點。這適用於 Kubernetes、Docker、ECS、Fly.io 或 Render 等執行環境中的常駐 worker 程序。

:::note
Inngest Connect 目前處於公開測試階段。Vercel 和 AWS Lambda 等無伺服器執行環境不支援 Connect worker。
:::

### 何時使用 `connect()` 而非 `serve()` {/* #when-to-use-connect-instead-of-serve */}

- worker 程序在僅允許對外連線的私人網路中執行。
- 你希望將耗用大量資源的 Workflow 執行工作，與處理使用者 HTTP 流量的程序分開。
- 你希望獨立於 Mastra HTTP 伺服器擴充或縮減 worker，並分別限制每個 worker 的並行量。

`serve()` 與 `connect()` 可使用相同的 Mastra Workflow 定義。對一般 Workflow、巢狀 Workflow、cron Workflow 及額外的 Inngest 函式而言，兩者的收集行為相同。

### 環境需求 {/* #requirements */}

- `inngest@^4`
- Node.js `22.13.0` 或更新版本
- 用於執行 worker 的常駐程序

### 設定 {/* #setup-1 */}

將 Mastra 伺服器與 Connect worker 作為兩個程序執行。在此設定下，Mastra 伺服器無須公開 `/inngest/api`：

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { incrementWorkflow } from './workflows'
import { PinoLogger } from '@mastra/loggers'

export const mastra = new Mastra({
  workflows: { incrementWorkflow },
  logger: new PinoLogger({ name: 'Mastra', level: 'info' }),
})
```

```ts title="src/worker.ts"
import { connect } from '@mastra/inngest/connect'
import { mastra } from './mastra'
import { inngest } from './mastra/inngest'

await connect({
  mastra,
  inngest,
  instanceId: process.env.INNGEST_CONNECT_INSTANCE_ID,
  maxWorkerConcurrency: Number(process.env.INNGEST_CONNECT_MAX_WORKER_CONCURRENCY ?? 10),
})
```

本機開發時，執行 `INNGEST_DEV=1 node --import tsx src/worker.ts` 啟動 worker。Inngest Dev Server 會透過 worker 的對外連線找到它，因此不需要 `-u` 參數。

在正式環境中設定 `INNGEST_EVENT_KEY` 和 `INNGEST_SIGNING_KEY`。將 `Inngest` 用戶端的 `appVersion` 設為 commit SHA 或映像標籤等部署識別碼，讓 Inngest 管理滾動部署。

將既有正式環境應用程式從 `serve()` 遷移至 `connect()` 時，請先以獨立的 Inngest 應用程式測試 worker，再轉移流量。

### 選項 {/* #options */}

`connect()` 接受與 Inngest [`connect`](https://www.inngest.com/docs/setup/connect) 相同的選項，另加 Mastra 專用欄位。常用選項如下：

- `mastra`：要提供其 Workflow 的 Mastra 執行個體。
- `inngest`：Inngest 用戶端。請使用與傳給 `serve()` 時相同的用戶端。
- `functions`：選用的額外 Inngest 函式陣列，與 Mastra Workflow 一同註冊。
- `instanceId`：worker 的固定識別碼，顯示於 Inngest 控制台。預設為機器的主機名稱。
- `maxWorkerConcurrency`：worker 同時執行的步驟數上限。預設不設上限。
- `registerOptions`：註冊應用程式時轉送給 Inngest 的選項，例如 `signingKey`。若同一欄位同時在此處與最上層設定，以 `registerOptions` 為準；這與 `serve()` 的行為相同。

`connect()` 會傳回 Inngest 的 `WorkerConnection`。Inngest SDK 預設會處理 `SIGINT` 和 `SIGTERM`。只有 worker 需要自訂關閉流程時，才需儲存傳回的連線並呼叫 `.close()`。

如果 Mastra 執行個體沒有 `InngestWorkflow`，也未提供額外的 `functions`，`connect()` 會記錄警告，因為 worker 否則會保持連線卻沒有工作可執行。請在 Mastra 至少註冊一個 Workflow，或傳入 `functions: [...]`。

## 使用自訂 `apiPrefix` {/* #using-a-custom-apiprefix */}

若需保留 `/api/inngest`（例如配合 Inngest 的自動探索慣例，而不更改控制台中的 URL），請設定 `server.apiPrefix`，將 Mastra 的內建路由移至其他前綴：

```ts title="src/mastra/index.ts" {7,10}
import { Mastra } from '@mastra/core'
import { serve } from '@mastra/inngest'
import { inngest } from './inngest'

export const mastra = new Mastra({
  server: {
    apiPrefix: '/_mastra',
    apiRoutes: [
      {
        path: '/api/inngest',
        method: 'ALL',
        createHandler: async ({ mastra }) => serve({ mastra, inngest }),
      },
    ],
  },
})
```

Mastra 的內建路由此時位於 `/_mastra/agents`、`/_mastra/workflows` 等路徑，`/api/inngest` 因而可供自訂路由使用。

:::warning
預設的身分驗證設定會保護 `/api/*`，並將 `/api`、`/api/auth/*` 視為公開路徑。更改 `apiPrefix` 後，這些預設規則不再符合，內建路由也會落在受保護模式之外。請更新 `server.auth.protected` 和 `server.auth.public`，使其指向新前綴；同時更新存取 `/api/*` 的用戶端程式碼，包括 [`MastraClient`](/docs/server/mastra-client) 的 `apiPrefix`。
:::

## 流量控制 {/* #flow-control */}

Inngest Workflow 支援並行限制、速率限制、節流、去彈跳及優先順序佇列等流量控制功能。這些選項在 `createWorkflow()` 呼叫中設定，可協助管理大規模 Workflow 執行。

### 並行限制 {/* #concurrency */}

控制可同時執行的 Workflow 執行個體數量：

```ts
const workflow = createWorkflow({
  id: 'user-processing-workflow',
  inputSchema: z.object({ userId: z.string() }),
  outputSchema: z.object({ result: z.string() }),
  steps: [processUserStep],
  // Limit to 10 concurrent executions, scoped by user ID
  concurrency: {
    limit: 10,
    key: 'event.data.userId',
  },
})
```

### 速率限制 {/* #rate-limiting */}

限制指定期間內的 Workflow 執行次數：

```ts
const workflow = createWorkflow({
  id: 'api-sync-workflow',
  inputSchema: z.object({ endpoint: z.string() }),
  outputSchema: z.object({ status: z.string() }),
  steps: [apiSyncStep],
  // Maximum 1000 executions per hour
  rateLimit: {
    period: '1h',
    limit: 1000,
  },
})
```

### 節流 {/* #throttling */}

確保兩次 Workflow 執行至少間隔指定時間：

```ts
const workflow = createWorkflow({
  id: 'email-notification-workflow',
  inputSchema: z.object({ organizationId: z.string(), message: z.string() }),
  outputSchema: z.object({ sent: z.boolean() }),
  steps: [sendEmailStep],
  // Only one execution per 10 seconds per organization
  throttle: {
    period: '10s',
    limit: 1,
    key: 'event.data.organizationId',
  },
})
```

### 去彈跳 {/* #debouncing */}

延後執行，直到指定時間範圍內沒有新事件抵達：

```ts
const workflow = createWorkflow({
  id: 'search-index-workflow',
  inputSchema: z.object({ documentId: z.string() }),
  outputSchema: z.object({ indexed: z.boolean() }),
  steps: [indexDocumentStep],
  // Wait 5 seconds of no updates before indexing
  debounce: {
    period: '5s',
    key: 'event.data.documentId',
  },
})
```

### 優先順序 {/* #priority */}

設定 Workflow 的執行優先順序：

```ts
const workflow = createWorkflow({
  id: 'order-processing-workflow',
  inputSchema: z.object({
    orderId: z.string(),
    priority: z.number().optional(),
  }),
  outputSchema: z.object({ processed: z.boolean() }),
  steps: [processOrderStep],
  // Higher priority orders execute first
  priority: {
    run: 'event.data.priority ?? 50',
  },
})
```

### 重試 {/* #retries */}

設定 `retries`，可讓執行作業在對應用程式的請求失敗後恢復，例如程序重新啟動、重新部署或記憶體不足導致當機時。Inngest 會再次呼叫該函式、略過已完成的步驟，並從中斷處繼續：

```ts
const workflow = createWorkflow({
  id: 'long-running-workflow',
  inputSchema: z.object({ jobId: z.string() }),
  outputSchema: z.object({ done: z.boolean() }),
  steps: [longRunningStep],
  // Re-invoke up to 3 times after a failed request
  retries: 3,
})
```

`retries` 預設為 `0`。步驟程式碼擲出的錯誤，會透過 `retryConfig` 或步驟本身的 `retries` 選項逐步重試，而非在函式層級重試。`createInngestAgent()` 也接受相同的 `retries` 選項，並套用至持久化 Agent 建立的每個 Inngest 函式。所有持久化 Agent 共用這些函式，因此最先向 Mastra 註冊的 Agent 所設定的 `retries` 值會套用至所有持久化 Agent。請為每個 Agent 設定相同的值，以免混淆。

巢狀 Workflow 會以獨立的 Inngest 函式執行，並使用自己的 `retries` 設定。它不會繼承上層 Workflow 的值，因此需要從請求失敗中恢復的巢狀 Workflow 都應個別設定 `retries`。

### 組合流量控制選項 {/* #combining-flow-control-options */}

同一個 Workflow 可組合多種流量控制選項：

```ts
const workflow = createWorkflow({
  id: 'comprehensive-workflow',
  inputSchema: z.object({
    userId: z.string(),
    organizationId: z.string(),
    priority: z.number().optional(),
  }),
  outputSchema: z.object({ result: z.string() }),
  steps: [comprehensiveStep],
  concurrency: {
    limit: 5,
    key: 'event.data.userId',
  },
  rateLimit: {
    period: '1m',
    limit: 100,
  },
  throttle: {
    period: '10s',
    limit: 1,
    key: 'event.data.organizationId',
  },
  priority: {
    run: 'event.data.priority ?? 0',
  },
})
```

所有流量控制選項皆為選用。未設定時，Workflow 會依照 Inngest 的預設行為執行。詳細資訊請參閱 [Inngest 流量控制文件](https://www.inngest.com/docs/guides/flow-control)。

## Cron 排程 {/* #cron-scheduling */}

使用 cron 運算式按排程觸發 Inngest Workflow。常見用途包括每日報告、每小時資料同步及維護工作。

### 基本 cron 排程 {/* #basic-cron-scheduling */}

為 Workflow 新增 `cron` 屬性，即可設定定期執行：

```ts
const workflow = createWorkflow({
  id: 'daily-report-workflow',
  inputSchema: z.object({ reportType: z.string() }),
  outputSchema: z.object({ generated: z.boolean() }),
  steps: [generateReportStep],
  // Run daily at midnight
  cron: '0 0 * * *',
})
```

### Cron 運算式格式 {/* #cron-schedule-format */}

`cron` 屬性接受標準 cron 運算式，格式為：`minute hour day month dayOfWeek`

- **分鐘**：0–59
- **小時**：0–23
- **日期**：1–31
- **月份**：1–12 或 JAN–DEC
- **星期**：0–6（星期日為 0）或 SUN–SAT

常見的 cron 運算式：

```ts
// Every 15 minutes
cron: '*/15 * * * *'

// Every hour at minute 0
cron: '0 * * * *'

// Every 6 hours
cron: '0 */6 * * *'

// Daily at midnight
cron: '0 0 * * *'

// Daily at 9 AM
cron: '0 9 * * *'

// Every weekday at 9 AM
cron: '0 9 * * 1-5'

// First day of every month at midnight
cron: '0 0 1 * *'

// Every Monday at 8 AM
cron: '0 8 * * 1'
```

### 為排程執行提供輸入資料 {/* #providing-input-data-for-scheduled-runs */}

你可以提供靜態輸入資料，供每次排程執行使用：

```ts
const workflow = createWorkflow({
  id: 'scheduled-data-sync',
  inputSchema: z.object({
    source: z.string(),
    destination: z.string(),
  }),
  outputSchema: z.object({ synced: z.boolean() }),
  steps: [syncDataStep],
  cron: '0 */6 * * *', // Every 6 hours
  // Input data provided to each scheduled run
  inputData: {
    source: 'production-db',
    destination: 'analytics-warehouse',
  },
})
```

### 為排程執行提供初始狀態 {/* #providing-initial-state-for-scheduled-runs */}

你也可以為排程執行的 Workflow 設定初始狀態：

```ts
const workflow = createWorkflow({
  id: 'scheduled-aggregation',
  inputSchema: z.object({ date: z.string() }),
  outputSchema: z.object({ aggregated: z.boolean() }),
  stateSchema: z.object({
    processedCount: z.number(),
    lastProcessedDate: z.string(),
  }),
  steps: [aggregateDataStep],
  cron: '0 0 * * *', // Daily at midnight
  inputData: {
    date: new Date().toISOString().split('T')[0], // Today's date
  },
  initialState: {
    processedCount: 0,
    lastProcessedDate: '',
  },
})
```

### 結合 cron 與流量控制 {/* #combining-cron-with-flow-control */}

Cron 排程可搭配流量控制選項使用：

```ts
const workflow = createWorkflow({
  id: 'scheduled-api-sync',
  inputSchema: z.object({ endpoint: z.string() }),
  outputSchema: z.object({ synced: z.boolean() }),
  steps: [syncApiStep],
  cron: '*/30 * * * *', // Every 30 minutes
  inputData: {
    endpoint: 'https://api.example.com/data',
  },
  // Limit concurrent executions even for scheduled runs
  concurrency: {
    limit: 5,
  },
  // Rate limit scheduled executions
  rateLimit: {
    period: '1h',
    limit: 100,
  },
})
```

### cron 函式的運作方式 {/* #how-cron-functions-work */}

為 Workflow 設定 `cron` 屬性後：

1. 系統會自動建立 ID 為 `workflow.${workflowId}.cron` 的獨立 Inngest 函式
2. 該函式會註冊至 Inngest，並依指定排程觸發
3. 每次排程執行都會使用所提供的 `inputData` 和 `initialState` 建立新的 Workflow 執行作業
4. 呼叫 `serve()` 時，cron 函式與主要 Workflow 函式會一同提供服務

你可以在 Inngest 控制台的 **Functions** 與 **Runs** 區域監看排程執行。cron 函式會以獨立函式顯示在主要 Workflow 函式旁。

關於 cron 排程的更多資訊，請參閱 [Inngest cron 文件](https://www.inngest.com/docs/guides/scheduled-functions)。
