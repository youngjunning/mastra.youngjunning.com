# 因格斯特

[因格斯特](https://www.inngest.com/docs)是一個用於建置和運行後台Workflow的開發人員平台，無需管理基礎架構。

有關具有進階流量控制功能的完整範例，請參閱[Inngest workflow example](https://github.com/mastra-ai/mastra/tree/main/examples/inngest).

## Ingest 如何與 Mastra 合作 {/* #how-inngest-works-with-mastra */}

Inngest 和 Mastra 透過調整其Workflow模型進行整合：Inngest 將邏輯組織為由步驟組成的函數，並且使用 Mastra 定義的Workflow`createWorkflow()` and `createStep()` map directly onto this structure. Each Mastra workflow becomes an Inngest function with a unique identifier, and each step within the workflow maps to an Inngest step.

這`serve()` function bridges the two systems by registering Mastra workflows as Inngest functions and setting up the necessary event handlers for execution and monitoring.

當事件觸發Workflow時，Inngest 會逐步執行並記住每個結果。重試或復原時，Inngest 會根據已儲存的結果跳過已完成的步驟。 Mastra 控制流原語（例如循環、條件和巢狀Workflow）對應到相同的 Ingest 函數和步驟模型，同時保留組合、分支和暫停。

透過 Inngest 的發布-訂閱系統和儀表板實現即時監控、暫停/恢復和步驟級可觀察性。每個步驟執行時，都會使用 Mastra 儲存體來追蹤其狀態和輸出，並且可以根據需要恢復。

## 設定 {/* #setup */}

安裝所需的軟體包：

```bash npm2yarn
npm install @mastra/inngest@latest inngest
```

:::注意
需要`inngest@^4` and Inngest Dev Server `v1.18.0` or later. Realtime is built into the SDK in v4, so `@inngest/realtime` and `realtimeMiddleware` are no longer used.
:::

## 建構 Ingest Workflow {/* #building-an-inngest-workflow */}

本指南逐步介紹如何使用 Inngest 和 Mastra 創建Workflow，演示一個計數器應用程序，該應用程式會遞增值直到達到 10。

### 攝取初始化 {/* #inngest-initialization */}

初始化 Inngest 整合以獲得與 Mastra 相容的Workflow助理。這`createWorkflow()` and `createStep()` functions are used to create workflow and step objects that are compatible with Mastra and inngest.

開發中：

```ts title="src/mastra/inngest/index.ts"
import { Inngest } from 'inngest'

export const inngest = new Inngest({
  id: 'mastra',
  baseUrl: 'http://localhost:8288',
  isDev: true,
})
```

生產中：

```ts title="src/mastra/inngest/index.ts"
import { Inngest } from 'inngest'

export const inngest = new Inngest({
  id: 'mastra',
})
```

#### 選擇開發或雲端模式`INNGEST_DEV` {/* #selecting-dev-or-cloud-mode-with-inngest_dev */}

Inngest SDK 以兩種模式之一運作：開發模式或雲端模式。從 v4 開始，SDK 預設為雲端模式，並且需要`INNGEST_EVENT_KEY` and `INNGEST_SIGNING_KEY`. The examples above set the mode in code with `isDev: true`. As an alternative, set the [`INNGEST_DEV` environment variable](https://www.inngest.com/docs/sdk/environment-variables#inngest-dev) so the same client code works across environments:

* `INNGEST_DEV=1`：強制開發模式。 SDK 與本機 Inngest Dev Server 通訊並停用簽章驗證。
* `INNGEST_DEV=0`：強制雲模式。 SDK 與 Inngest Cloud 通訊並需要事件和簽署金鑰。
* `INNGEST_DEV=<url>`：強制開發模式並將 SDK 指向開發伺服器`<url>`, for example `http://localhost:8288`.
* 未設定：預設為雲模式。

什麼時候`INNGEST_DEV` is set, you can drop `isDev` and `baseUrl` from the client:

```ts title="src/mastra/inngest/index.ts"
import { Inngest } from 'inngest'

export const inngest = new Inngest({
  id: 'mastra',
})
```

:::警告
不設定`INNGEST_DEV` in production. It disables signature verification, which is required to securely receive events from Inngest Cloud.
:::

這`isDev` option on `new Inngest()` overrides `INNGEST_DEV` when both are set.

### 建立步驟 {/* #creating-steps */}

定義構成Workflow的各個步驟：

```ts title="src/mastra/workflows/index.ts"
import { z } from 'zod'
import { inngest } from '../inngest'
import { init } from '@mastra/inngest'

// Initialize Inngest with Mastra, pointing to your local Inngest server
const { createWorkflow, createStep } = init(inngest)

// Step: Increment the counter value
const incrementStep = createStep({
  id: 'increment',
  inputSchema: z.object({
    value: z.number(),
  }),
  outputSchema: z.object({
    value: z.number(),
  }),
  execute: async ({ inputData }) => {
    return { value: inputData.value + 1 }
  },
})
```

### 建立Workflow {/* #creating-the-workflow */}

使用以下方法將步驟組成Workflow`dountil` loop pattern. The `createWorkflow()` function creates a function on Inngest server that's invocable.

```ts title="src/mastra/workflows/index.ts"
// workflow that is registered as a function on inngest server
const workflow = createWorkflow({
  id: 'increment-workflow',
  inputSchema: z.object({
    value: z.number(),
  }),
  outputSchema: z.object({
    value: z.number(),
  }),
}).then(incrementStep)

workflow.commit()

export { workflow as incrementWorkflow }
```

### 配置 Mastra 實例 {/* #configuring-the-mastra-instance */}

向 Mastra 註冊Workflow並設定 Inngest API 端點：

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { serve } from '@mastra/inngest'
import { incrementWorkflow } from './workflows'
import { inngest } from './inngest'
import { PinoLogger } from '@mastra/loggers'

export const mastra = new Mastra({
  workflows: { incrementWorkflow },
  server: {
    host: '0.0.0.0',
    apiRoutes: [
      {
        path: '/inngest/api',
        method: 'ALL',
        createHandler: async ({ mastra }) => {
          return serve({ mastra, inngest })
        },
      },
    ],
  },
  logger: new PinoLogger({ name: 'Mastra', level: 'info' }),
})
```

:::注意
路徑是`/inngest/api`, not `/api/inngest`. Mastra reserves the `/api` prefix for built-in routes (agents, workflows, memory). Custom `apiRoutes` paths that start with the server's `apiPrefix` (default `/api`) throw at startup. See [#15743](https://github.com/mastra-ai/mastra/pull/15743) for context, or skip to [Using a custom `apiPrefix`](#using-a-custom-apiprefix) if you need to keep `/api/inngest`.
:::

## 運行Workflow {/* #running-workflows */}

### 本地運行 {/* #running-locally */}

1. 跑步`npx mastra dev` to start the Mastra server locally on port 4111

2. 啟動 Ingest 開發伺服器。在新終端機中，運作：

   ```bash
   npx inngest-cli@latest dev -u http://localhost:4111/inngest/api
   ```

   :::注意
   之後的網址`-u` tells the Inngest dev server where to find your Mastra `/inngest/api` endpoint
   :::

3. 打開 Ingest 儀表板[http://localhost:8288](http://localhost:8288) and go to the **Apps** section in the sidebar to verify your Mastra workflow is registered

4. 在**Functions**, open your workflow. Select **Invoke** and provide the following input:

   ```json
   {
     "data": {
       "inputData": {
         "value": 5
       }
     }
   }
   ```

5. 監控Workflow執行狀況**Runs** tab to see step-by-step execution progress

### 生產中運行 {/* #running-in-production */}

在開始之前，請確保您擁有：

* 安裝了 Vercel 帳戶和 Vercel CLI (`npm i -g vercel`)
* 攝取帳戶
* Vercel代幣

1. 在您的環境中設定 Vercel 令牌：

   ```bash title=".env"
   export VERCEL_TOKEN=your_vercel_token
   ```

2. 添加`VercelDeployer` to Mastra instance

   ```ts title="src/mastra/index.ts"
   import { VercelDeployer } from '@mastra/deployer-vercel'
   import { Mastra } from '@mastra/core'

   export const mastra = new Mastra({
     deployer: new VercelDeployer({
       teamSlug: 'your_team_slug',
       projectName: 'your_project_name',
       // you can get your vercel token from the vercel dashboard by clicking on the user icon in the top right corner
       // and then clicking on "Account Settings" and then clicking on "Tokens" on the left sidebar.
       token: process.env.VERCEL_TOKEN,
     }),
   })
   ```

3. 建構 Mastra 實例

   ```bash
   npx mastra build
   ```

4. 部署到 Vercel

   ```bash
   cd .mastra/output
   vercel login
   vercel --prod
   ```

5. 與同步[Inngest dashboard](https://app.inngest.com/env/production/apps) by selecting **Sync new app with Vercel** and following the instructions

   :::警告
   Ingest 的自動發現約定假設`/api/inngest`. Because this guide uses `/inngest/api`, set the **URL** field on the Inngest app to your deployed origin plus `/inngest/api` (for example `https://your-app.vercel.app/inngest/api`). If you leave it on the default, the Inngest dashboard won't find your app's functions.
   :::

6. 在**Functions**, open `workflow.increment-workflow`. Select **All actions** > **Invoke** and provide the following input:

   ```json
   {
     "data": {
       "inputData": {
         "value": 5
       }
     }
   }
   ```

7. 監控執行狀況**Runs** tab to see step-by-step progress

## 新增自訂 Ingest 函數 {/* #adding-custom-inngest-functions */}

您可以使用可選的選項，在 Mastra Workflow中提供額外的 Ingest 功能`functions` parameter in `serve()`.

### 建立自訂函數 {/* #creating-custom-functions */}

首先，建立自訂 Ingest 函數：

```ts title="src/inngest/custom-functions.ts"
import { inngest } from '../inngest'

// Define custom Inngest functions
export const customEmailFunction = inngest.createFunction(
  { id: 'send-welcome-email' },
  { event: 'user/registered' },
  async ({ event }) => {
    // Custom email logic here
    console.log(`Sending welcome email to ${event.data.email}`)
    return { status: 'email_sent' }
  },
)

export const customWebhookFunction = inngest.createFunction(
  { id: 'process-webhook' },
  { event: 'webhook/received' },
  async ({ event }) => {
    // Custom webhook processing
    console.log(`Processing webhook: ${event.data.type}`)
    return { processed: true }
  },
)
```

### 透過Workflow提供自訂功能 {/* #serving-custom-functions-with-workflows */}

更新您的 Mastra 配置以匯入並包含自訂函數。突出顯示的行顯示了新增內容：

```ts title="src/mastra/index.ts" {5-8,23}
import { Mastra } from '@mastra/core'
import { serve } from '@mastra/inngest'
import { incrementWorkflow } from './workflows'
import { inngest } from './inngest'
import { customEmailFunction, customWebhookFunction } from './inngest/custom-functions'
import { PinoLogger } from '@mastra/loggers'

export const mastra = new Mastra({
  workflows: { incrementWorkflow },
  server: {
    host: '0.0.0.0',
    apiRoutes: [
      {
        path: '/inngest/api',
        method: 'ALL',
        createHandler: async ({ mastra }) => {
          return serve({
            mastra,
            inngest,
            functions: [customEmailFunction, customWebhookFunction],
          })
        },
      },
    ],
  },
  logger: new PinoLogger({ name: 'Mastra', level: 'info' }),
})
```

### 功能註冊 {/* #function-registration */}

當您包含自訂函數時：

1. Mastra Workflow會自動轉換為 Inngest 函數，其 ID 如下`workflow.${workflowId}`
2. `send-welcome-email`, `process-webhook`)
3. `/inngest/api` endpoint

這使您可以將 Mastra 的Workflow編排與現有的 Ingest 功能結合。

## 與其他框架一起使用 {/* #using-with-other-frameworks */}

預設`serve` function uses Hono internally. If you're using a different web framework like Express, Fastify, or Koa, use the `createServe` factory function with the appropriate Inngest adapter.

### 表達 {/* #express */}

```ts title="src/server.ts"
import express from 'express'
import { createServe } from '@mastra/inngest'
import { serve as expressAdapter } from 'inngest/express'
import { mastra, inngest } from './mastra'

const app = express()

// Body parsing middleware required for Inngest
app.use(express.json())

const handler = createServe(expressAdapter)({ mastra, inngest })
app.use('/inngest/api', handler)

app.listen(3000)
```

### 快速化 {/* #fastify */}

```ts title="src/server.ts"
import Fastify from 'fastify'
import { createServe } from '@mastra/inngest'
import { serve as fastifyAdapter } from 'inngest/fastify'
import { mastra, inngest } from './mastra'

const fastify = Fastify()

// JSON parsing is handled by Fastify's default content-type parser
const handler = createServe(fastifyAdapter)({ mastra, inngest })

fastify.route({
  method: ['GET', 'POST', 'PUT'],
  url: '/inngest/api',
  handler,
})

fastify.listen({ port: 3000 })
```

### 相思木 {/* #koa */}

```ts title="src/server.ts"
import Koa from 'koa'
import Router from '@koa/router'
import bodyParser from 'koa-bodyparser'
import { createServe } from '@mastra/inngest'
import { serve as koaAdapter } from 'inngest/koa'
import { mastra, inngest } from './mastra'

const app = new Koa()
const router = new Router()

// Body parsing middleware required for Inngest
app.use(bodyParser())

const handler = createServe(koaAdapter)({ mastra, inngest })
router.all('/inngest/api', handler)

app.use(router.routes())
app.use(router.allowedMethods())

app.listen(3000)
```

### Next.js {/* #nextjs */}

```ts title="app/inngest/api/route.ts"
import { createServe } from '@mastra/inngest'
import { serve as nextAdapter } from 'inngest/next'
import { mastra, inngest } from '@/mastra'

const handler = createServe(nextAdapter)({ mastra, inngest })

export { handler as GET, handler as POST, handler as PUT }
```

### 可用適配器 {/* #available-adapters */}

這`createServe` function works with any Inngest adapter. See the [Inngest serve documentation](https://www.inngest.com/docs/reference/serve) for a complete list of available adapters including AWS Lambda, Cloudflare Workers, and more.

## 作為 Connect 工作執行緒運行 {/* #running-as-a-connect-worker */}

`serve()`公開 Inngest 呼叫的 HTTP 端點。作為替代方案，`connect()` opens a long-lived outbound connection from your worker to Inngest, so the worker doesn't need a publicly reachable endpoint. Use this for long-running worker processes on runtimes such as Kubernetes, Docker, ECS, Fly.io, or Render.

:::注意
Inngest Connect 處於公開測試階段。 Connect 工作執行緒不支援 Vercel 和 AWS Lambda 等無伺服器執行時間。
:::

### 何時使用`connect()` instead of `serve()` {/* #when-to-use-connect-instead-of-serve */}

* 工作進程在僅允許出站連線的專用網路中運作。
* 您希望將繁重的Workflow執行排除在服務面向使用者的 HTTP 流量的相同進程之外。
* 您希望獨立於 Mastra HTTP 伺服器來擴展和縮減工作線程，並限制每個工作線程的並發數。

使用相同的 Mastra Workflow定義`serve()` or `connect()`. The collection behavior is the same for standard workflows, nested workflows, cron workflows, and additional Inngest functions.

### 要求 {/* #requirements */}

* `inngest@^4`
* Node.js`22.13.0` or later
* 工人長期運作的流程

### 設定 {/* #setup-1 */}

將 Mastra 伺服器和 Connect 工作執行緒作為兩個進程運行。此設定中的 Mastra 伺服器不需要公開`/inngest/api`:

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { incrementWorkflow } from './workflows'
import { PinoLogger } from '@mastra/loggers'

export const mastra = new Mastra({
  workflows: { incrementWorkflow },
  logger: new PinoLogger({ name: 'Mastra', level: 'info' }),
})
```

```ts title="src/worker.ts"
import { connect } from '@mastra/inngest/connect'
import { mastra } from './mastra'
import { inngest } from './mastra/inngest'

await connect({
  mastra,
  inngest,
  instanceId: process.env.INNGEST_CONNECT_INSTANCE_ID,
  maxWorkerConcurrency: Number(process.env.INNGEST_CONNECT_MAX_WORKER_CONCURRENCY ?? 10),
})
```

啟動工人`INNGEST_DEV=1 node --import tsx src/worker.ts` during local development. The Inngest Dev Server discovers the worker through the outbound connection, so no `-u` flag is required.

在生產中，設置`INNGEST_EVENT_KEY` and `INNGEST_SIGNING_KEY`. Set `appVersion` on the `Inngest` client to a deploy identifier, such as a commit SHA or image tag, so Inngest can manage rolling deploys.

當從以下位置遷移現有的生產應用程式時`serve()` to `connect()`, test the worker with a separate Inngest app before moving traffic.

### 選項 {/* #options */}

`connect()`接受與 Inngest 相同的選項[`connect`](https://www.inngest.com/docs/setup/connect) plus the Mastra-specific fields. The most common ones:

* `mastra`
* `inngest`： Ingest 客戶端。使用您要傳遞給的同一個客戶端`serve()`.
* `functions`：可選的附加 Ingest 功能數組，可與 Mastra Workflow一起註冊。
* `instanceId`：工作人员的稳定标识符，显示在 Inngest 仪表板中。預設為機器主機名稱。
* `maxWorkerConcurrency`
* `registerOptions`：在應用程式註冊期間轉發到Inngest（例如`signingKey`). When a field is set both here and at the top level, `registerOptions` wins. This matches the behavior of `serve()`.

`connect()`返回 Ingest 的`WorkerConnection`. The Inngest SDK handles `SIGINT` and `SIGTERM` by default. Store the returned connection and call `.close()` only when your worker needs custom shutdown control.

如果 Mastra 實例沒有`InngestWorkflow` and no additional `functions` are provided, `connect()` logs a warning because the worker would otherwise stay connected with nothing to execute. Register at least one workflow on Mastra or pass `functions: [...]`.

## 使用自訂`apiPrefix` {/* #using-a-custom-apiprefix */}

如果您需要保留`/api/inngest` (for example to match Inngest's auto-discover convention without changing the dashboard URL), set `server.apiPrefix` to relocate Mastra's built-in routes:

```ts title="src/mastra/index.ts" {7,10}
import { Mastra } from '@mastra/core'
import { serve } from '@mastra/inngest'
import { inngest } from './inngest'

export const mastra = new Mastra({
  server: {
    apiPrefix: '/_mastra',
    apiRoutes: [
      {
        path: '/api/inngest',
        method: 'ALL',
        createHandler: async ({ mastra }) => serve({ mastra, inngest }),
      },
    ],
  },
})
```

Mastra 的內建路線現在可以解析為`/_mastra/agents`, `/_mastra/workflows`, and so on, freeing the `/api/inngest` path for your custom route.

:::警告
預設身份驗證配置可保護`/api/*` and treats `/api`, `/api/auth/*` as public. When you change `apiPrefix`, those defaults no longer match and built-in routes fall outside the protected pattern. Update `server.auth.protected` and `server.auth.public` to reference the new prefix, and update any client code (including [`MastraClient`](/docs/server/mastra-client) `apiPrefix`) that hits `/api/*`.
:::

## 流量控制 {/* #flow-control */}

Inngest Workflow支援流量控制功能，包括並發限制、速率限制、節流、去抖動和優先排隊。這些選項配置在`createWorkflow()` call and help manage workflow execution at scale.

### 並發性 {/* #concurrency */}

控制可以同時運行的Workflow實例數：

```ts
const workflow = createWorkflow({
  id: 'user-processing-workflow',
  inputSchema: z.object({ userId: z.string() }),
  outputSchema: z.object({ result: z.string() }),
  steps: [processUserStep],
  // Limit to 10 concurrent executions, scoped by user ID
  concurrency: {
    limit: 10,
    key: 'event.data.userId',
  },
})
```

### 速率限制 {/* #rate-limiting */}

限制一段時間內Workflow執行的數量：

```ts
const workflow = createWorkflow({
  id: 'api-sync-workflow',
  inputSchema: z.object({ endpoint: z.string() }),
  outputSchema: z.object({ status: z.string() }),
  steps: [apiSyncStep],
  // Maximum 1000 executions per hour
  rateLimit: {
    period: '1h',
    limit: 1000,
  },
})
```

### 節流 {/* #throttling */}

確保Workflow執行之間的最短時間：

```ts
const workflow = createWorkflow({
  id: 'email-notification-workflow',
  inputSchema: z.object({ organizationId: z.string(), message: z.string() }),
  outputSchema: z.object({ sent: z.boolean() }),
  steps: [sendEmailStep],
  // Only one execution per 10 seconds per organization
  throttle: {
    period: '10s',
    limit: 1,
    key: 'event.data.organizationId',
  },
})
```

### 去抖 {/* #debouncing */}

延遲執行，直到時間視窗內沒有新事件到達：

```ts
const workflow = createWorkflow({
  id: 'search-index-workflow',
  inputSchema: z.object({ documentId: z.string() }),
  outputSchema: z.object({ indexed: z.boolean() }),
  steps: [indexDocumentStep],
  // Wait 5 seconds of no updates before indexing
  debounce: {
    period: '5s',
    key: 'event.data.documentId',
  },
})
```

### 優先事項 {/* #priority */}

設定Workflow的執行優先：

```ts
const workflow = createWorkflow({
  id: 'order-processing-workflow',
  inputSchema: z.object({
    orderId: z.string(),
    priority: z.number().optional(),
  }),
  outputSchema: z.object({ processed: z.boolean() }),
  steps: [processOrderStep],
  // Higher priority orders execute first
  priority: {
    run: 'event.data.priority ?? 50',
  },
})
```

### 重試 {/* #retries */}

放`retries` to let a run survive a failed request to your app, such as a process restart, redeploy, or out-of-memory crash. Inngest calls the function again, skips the steps that already finished, and continues from the step that was interrupted:

```ts
const workflow = createWorkflow({
  id: 'long-running-workflow',
  inputSchema: z.object({ jobId: z.string() }),
  outputSchema: z.object({ done: z.boolean() }),
  steps: [longRunningStep],
  // Re-invoke up to 3 times after a failed request
  retries: 3,
})
```

`retries`預設為`0`. Errors thrown by your step code are retried per step with `retryConfig` or the step's `retries` option, not at the function level. `createInngestAgent()` accepts the same `retries` option and applies it to every Inngest function the durable agent creates. All durable agents share these functions, so the `retries` value of the first agent registered with Mastra applies to every durable agent. Set the same value on each agent to avoid confusion.

嵌套Workflow作為其自己的 Inngest 函數運行並使用其自己的`retries` setting. It doesn't inherit the parent's value, so set `retries` on each nested workflow that should recover from a failed request.

### 組合流量控制選項 {/* #combining-flow-control-options */}

多個流程控制選項可以組合在一個Workflow中：

```ts
const workflow = createWorkflow({
  id: 'comprehensive-workflow',
  inputSchema: z.object({
    userId: z.string(),
    organizationId: z.string(),
    priority: z.number().optional(),
  }),
  outputSchema: z.object({ result: z.string() }),
  steps: [comprehensiveStep],
  concurrency: {
    limit: 5,
    key: 'event.data.userId',
  },
  rateLimit: {
    period: '1m',
    limit: 100,
  },
  throttle: {
    period: '10s',
    limit: 1,
    key: 'event.data.organizationId',
  },
  priority: {
    run: 'event.data.priority ?? 0',
  },
})
```

所有流量控制選項都是可選的。如果未指定，Workflow將依照 Inngest 的預設行為運作。欲了解更多信息，請參閱[Inngest flow control documentation](https://www.inngest.com/docs/guides/flow-control).

## Cron調度 {/* #cron-scheduling */}

使用 cron 表達式按計劃觸發 Inngest Workflow。常見用途包括每日報告和每小時資料同步以及維護任務。

### 基本的 cron 調度 {/* #basic-cron-scheduling */}

透過新增一個Workflow來配置Workflow按計畫運行`cron` property:

```ts
const workflow = createWorkflow({
  id: 'daily-report-workflow',
  inputSchema: z.object({ reportType: z.string() }),
  outputSchema: z.object({ generated: z.boolean() }),
  steps: [generateReportStep],
  // Run daily at midnight
  cron: '0 0 * * *',
})
```

### Cron 計劃格式 {/* #cron-schedule-format */}

這`cron` property accepts standard cron expressions in the format: `minute hour day month dayOfWeek`

* **分分鐘**: 0-59
* **小時**: 0-23
* **天**: 1-31
* **月**： 1-12 或 1-12 月
* **星期幾**：0-6（星期日 = 0）或星期日至星期六

常見的 cron 模式：

```ts
// Every 15 minutes
cron: '*/15 * * * *'

// Every hour at minute 0
cron: '0 * * * *'

// Every 6 hours
cron: '0 */6 * * *'

// Daily at midnight
cron: '0 0 * * *'

// Daily at 9 AM
cron: '0 9 * * *'

// Every weekday at 9 AM
cron: '0 9 * * 1-5'

// First day of every month at midnight
cron: '0 0 1 * *'

// Every Monday at 8 AM
cron: '0 8 * * 1'
```

### 為計劃運行提供輸入數據 {/* #providing-input-data-for-scheduled-runs */}

您可以提供將用於每個計劃執行的靜態輸入資料：

```ts
const workflow = createWorkflow({
  id: 'scheduled-data-sync',
  inputSchema: z.object({
    source: z.string(),
    destination: z.string(),
  }),
  outputSchema: z.object({ synced: z.boolean() }),
  steps: [syncDataStep],
  cron: '0 */6 * * *', // Every 6 hours
  // Input data provided to each scheduled run
  inputData: {
    source: 'production-db',
    destination: 'analytics-warehouse',
  },
})
```

### 為計劃運行提供初始狀態 {/* #providing-initial-state-for-scheduled-runs */}

您也可以為已排程的Workflow運作設定初始狀態：

```ts
const workflow = createWorkflow({
  id: 'scheduled-aggregation',
  inputSchema: z.object({ date: z.string() }),
  outputSchema: z.object({ aggregated: z.boolean() }),
  stateSchema: z.object({
    processedCount: z.number(),
    lastProcessedDate: z.string(),
  }),
  steps: [aggregateDataStep],
  cron: '0 0 * * *', // Daily at midnight
  inputData: {
    date: new Date().toISOString().split('T')[0], // Today's date
  },
  initialState: {
    processedCount: 0,
    lastProcessedDate: '',
  },
})
```

### 將 cron 與流量控制結合 {/* #combining-cron-with-flow-control */}

Cron 調度可以與流量控制選項結合使用：

```ts
const workflow = createWorkflow({
  id: 'scheduled-api-sync',
  inputSchema: z.object({ endpoint: z.string() }),
  outputSchema: z.object({ synced: z.boolean() }),
  steps: [syncApiStep],
  cron: '*/30 * * * *', // Every 30 minutes
  inputData: {
    endpoint: 'https://api.example.com/data',
  },
  // Limit concurrent executions even for scheduled runs
  concurrency: {
    limit: 5,
  },
  // Rate limit scheduled executions
  rateLimit: {
    period: '1h',
    limit: 100,
  },
})
```

### cron 函數如何運作 {/* #how-cron-functions-work */}

當您配置Workflow時`cron` property:

1. `workflow.${workflowId}.cron`
2. 該函數已在 Inngest 註冊，將在指定的時間表觸發
3. `inputData` and `initialState`
4. 當您呼叫時，cron 函數和主Workflow函數一起服務`serve()`

您可以在 Inngest 儀表板中監控計畫執行**Functions** and **Runs** sections. The cron function will appear as a separate function alongside your main workflow function.

有關 cron 調度的更多信息，請參閱[Inngest cron documentation](https://www.inngest.com/docs/guides/scheduled-functions).
