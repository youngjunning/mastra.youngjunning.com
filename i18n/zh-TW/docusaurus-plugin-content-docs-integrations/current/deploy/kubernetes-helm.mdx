# Kubernetes (Helm)

:::info 僅限企業版
Helm Chart 僅供 Mastra Enterprise 客戶使用。Chart 透過私人儲存庫發佈：您可用企業版授權金鑰換取短期有效的擷取憑證。[聯絡我們](https://mastra.ai/contact)以取得企業版授權。
:::

使用官方 `mastra-projects` Helm Chart，可在任何 Kubernetes 叢集上部署 Mastra 平台，包括 Mastra Server（Agent 執行環境）與 Mastra Studio（管理介面）。此 Chart 適用於 GKE、EKS、AKS、一般叢集及本機叢集，並協助設定服務對外存取、TLS 與 Secret 參照。

此 Chart 遵循兩項設計原則：

- **使用自行建置的映像檔。** 透過 `mastra build` 建置 Mastra 專案映像檔，再推送至映像檔儲存庫。Chart 不會建置映像檔。
- **使用自己的資料儲存服務。** 為 Chart 指定 PostgreSQL 資料庫，也可選擇指定與 S3 相容的物件儲存服務。Chart 不包含具狀態服務。

本指南介紹 Helm Chart；它會管理 Deployment、Service、Ingress 或 Gateway 資源，以及 Secret。若要自行撰寫 Kubernetes 資源清單，或透過共用 pub/sub 執行多個 Server Pod，請參閱 [Kubernetes](/integrations/deploy/kubernetes)。

## 開始之前 {/* #before-you-begin */}

您需要：

- Kubernetes 1.27 以上版本的叢集，以及 [`kubectl`](https://kubernetes.io/docs/tasks/tools/)
- [Helm](https://helm.sh/docs/intro/install/) 3.8 以上版本（支援 OCI 儲存庫）
- 叢集可從中擷取映像檔的容器映像檔儲存庫
- 叢集可連線的 PostgreSQL 資料庫
- Mastra Enterprise 授權金鑰；擷取 Chart 及在正式環境執行時都需要
- 使用 `ingress` 模式時：Ingress 控制器，或讓 Chart 安裝一個
- 使用 `gateway` 模式時：Gateway API CRD 與 Gateway 控制器（例如 GKE 代管的 Gateway）

## 部署 {/* #deploy */}

:::warning
建置及安裝映像檔前，請先在 Mastra 應用程式中設定[身分驗證](/docs/auth/overview)。預設的 `loadBalancer` 模式會建立可從外部存取的 Service；視叢集與雲端服務供應商的設定而定，Server 與 Studio 可能會暴露於網際網路。
:::

<Steps>
  <StepItem>
    建置 Mastra 專案，並將建置產物製成容器映像檔。傳入 `--studio`，讓同一個映像檔同時提供 Server 與 Studio：

    ```bash
    mastra build --studio
    ```

    ```dockerfile title="Dockerfile"
    FROM node:22-slim
    WORKDIR /app
    # Install dependencies inside the image: native modules (for example libsql)
    # are platform-specific, so node_modules built on your machine must not be
    # copied into the image (see .dockerignore below).
    COPY .mastra/output/package.json .mastra/output/package-lock.json* ./
    RUN npm install --force --prefer-offline --no-audit --no-fund
    COPY .mastra/output ./
    EXPOSE 4111
    CMD ["node", "index.mjs"]
    ```

    ```text title=".dockerignore"
    .mastra/output/node_modules
    ```

    :::warning
    不要用 `COPY` 將主機上建置的 `node_modules` 複製到映像檔。`mastra build` 會針對本機平台安裝原生模組；例如，在 Apple Silicon Mac 上建置映像檔並部署到 amd64 叢集時，應用程式可能在啟動時因 `Cannot find module '@libsql/linux-x64-gnu'` 等錯誤而當機。如上所示在映像檔內安裝相依套件，才能符合目標平台。
    :::

    將映像檔推送至儲存庫。若電腦與叢集節點的架構不同（例如從 arm64 Mac 部署至 amd64 節點），建置時請使用 `--platform`：

    ```bash
    docker buildx build --platform linux/amd64 \
      -t your-registry/my-mastra-app:1.0.0 --push .
    ```

    建置詳情請參閱 [Mastra Server](/docs/deployment/mastra-server)。
  </StepItem>

  <StepItem>
    將應用程式憑證儲存在 Helm Release 所在的命名空間。Chart 會從您管理的 Secret 讀取資料庫、授權與模型 Provider 憑證：

    ```bash
    kubectl create namespace mastra
    kubectl create secret generic mastra-app-env -n mastra \
      --from-literal=DATABASE_URL='postgresql://user:pass@host:5432/mastra' \
      --from-literal=MASTRA_EE_LICENSE='<your-license-key>' \
      --from-literal=OPENAI_API_KEY='<provider-key>' \
      --from-literal=CLICKHOUSE_URL='https://your-instance.clickhouse.cloud:8443' \
      --from-literal=CLICKHOUSE_USERNAME='<clickhouse-username>' \
      --from-literal=CLICKHOUSE_PASSWORD='<clickhouse-password>'
    ```

    也請加入 Agent 所需的其他環境變數，例如模型 Provider 的 API 金鑰。若未使用 ClickHouse 處理可觀測性資料，請省略 `CLICKHOUSE_*` 變數。
  </StepItem>

  <StepItem>
    建立 values 檔案，指定映像檔與 Secret：

    ```yaml title="mastra-values.yaml"
    global:
      cloud: generic # gke | eks | aks | generic | local

    mastra-server:
      image:
        repository: your-registry/my-mastra-app
        tag: '1.0.0'
      existingSecret: mastra-app-env

    mastra-studio:
      image:
        repository: your-registry/my-mastra-app
        tag: '1.0.0'
      existingSecret: mastra-app-env
    ```

    兩個元件參照同一個 Secret，因為本指南使用同一個應用程式映像檔執行 Server 與 Studio。只有在 Studio 部署不會執行需要應用程式 Provider 憑證的路由時，才使用不同的 Secret。

    將 `global.cloud` 設為使用的平台，讓 Chart 產生適用於該雲端平台的 LoadBalancer 與 Ingress 註解。

    若叢集尚無法存取應用程式映像檔儲存庫，請建立映像檔擷取 Secret：

    ```bash
    kubectl create secret docker-registry mastra-registry -n mastra \
      --docker-server=your-registry \
      --docker-username='<username>' \
      --docker-password='<access-token>'
    ```

    在兩個元件中參照該 Secret：

    ```yaml title="mastra-values.yaml"
    mastra-server:
      imagePullSecrets:
        - name: mastra-registry

    mastra-studio:
      imagePullSecrets:
        - name: mastra-registry
    ```

    公開映像檔與已整合至叢集的儲存庫不需要映像檔擷取 Secret。

    以上只是最精簡的設定。執行 `helm registry login` 後，請查看所選 Chart 版本附有說明的預設值及 README，以瞭解所有可用設定：

    ```bash
    CHART_VERSION=0.2.0
    CHART=oci://us-central1-docker.pkg.dev/mastra-cloud/mastra-helm-ee/mastra-projects

    helm show values "$CHART" --version "$CHART_VERSION"
    helm show readme "$CHART" --version "$CHART_VERSION"
    ```
  </StepItem>

  <StepItem>
    使用企業版授權金鑰換取短期有效的儲存庫存取權杖，登入私人 Chart 儲存庫，再安裝 Chart：

    ```bash
    CHART_VERSION=0.2.0
    CHART=oci://us-central1-docker.pkg.dev/mastra-cloud/mastra-helm-ee/mastra-projects

    TOKEN=$(curl -s https://license.mastra.ai/v1/registry-token \
      -H "Authorization: Bearer $MASTRA_EE_LICENSE" | jq -r .token)

    printf '%s' "$TOKEN" | helm registry login us-central1-docker.pkg.dev \
      --username oauth2accesstoken \
      --password-stdin

    helm install mastra "$CHART" \
      --version "$CHART_VERSION" \
      -n mastra -f mastra-values.yaml
    ```

    權杖很快就會過期。若之後升級時出現授權錯誤，請取得新權杖並重新登入。

    預設情況下，每個元件都透過 `LoadBalancer` 類型的 Service 對外提供存取。
  </StepItem>

  <StepItem>
    驗證 Release。等待 Pod 就緒，然後檢查 Server 的健康檢查端點：

    ```bash
    kubectl -n mastra rollout status deployment -l app.kubernetes.io/instance=mastra
    kubectl -n mastra get svc
    ```

    ```bash
    curl http://<server-external-ip>:4111/health
    ```

    回傳 `{"success":true}` 表示 Server 已啟動。在瀏覽器中開啟 Studio 的 Service 位址，即可進入 Mastra Studio 介面。
  </StepItem>
</Steps>

## 對外存取模式 {/* #exposure-modes */}

此 Chart 支援三種 Server 與 Studio 對外存取方式，透過 `global.exposure.mode` 統一選擇：

| 模式 | 提供的資源 | 必要設定 |
| - | - | - |
| `loadBalancer`（預設） | 每個元件各有一個 `LoadBalancer` Service，並附上對應雲端平台的註解 | — |
| `ingress` | ClusterIP Service，以及每個元件各有一個 Ingress | `mastra-server.ingress.host`, `mastra-studio.ingress.host` |
| `gateway` | ClusterIP Service、一個共用 Gateway，以及每個元件各有一個 HTTPRoute | `mastra-server.httpRoute.host`, `mastra-studio.httpRoute.host` |

### 透過 Ingress 使用 Let's Encrypt TLS {/* #ingress-with-lets-encrypt-tls */}

使用 `ingress` 模式與 cert-manager，透過 HTTPS 提供兩個元件的服務。Chart 可以安裝 ingress-nginx 與 cert-manager，也可以使用您現有的控制器：

```yaml title="mastra-values.yaml"
global:
  exposure:
    mode: ingress
  tls:
    clusterIssuer: letsencrypt

ingressController:
  install: true # omit if you already run an ingress controller

tls:
  certManager:
    install: true # omit if cert-manager is already installed
  letsEncrypt:
    email: ops@example.com

mastra-server:
  ingress:
    host: api.example.com

mastra-studio:
  ingress:
    host: studio.example.com
```

設定 `tls.letsEncrypt.email` 後，Chart 會產生 `ClusterIssuer`，並為每個 Ingress 加上註解，以便自動核發憑證。HTTP 請求會重新導向至 HTTPS。

在 `generic` 叢集上，除非您明確設定，否則 Chart 不會設定 `ingressClassName`，因此會使用叢集的預設 Ingress 類別。

### Gateway API {/* #gateway-api */}

在支援 Gateway API 的叢集上使用 `gateway` 模式。在 GKE 上，Chart 會自動選用代管的 `gke-l7-global-external-managed` 類別；在其他雲端平台上，請明確設定 `global.gateway.className`：

```yaml title="mastra-values.yaml"
global:
  exposure:
    mode: gateway
  tls:
    clusterIssuer: letsencrypt

mastra-server:
  httpRoute:
    host: api.example.com

mastra-studio:
  httpRoute:
    host: studio.example.com
```

Chart 會建立一個共用 Gateway，包含 HTTP 接聽程式，以及每個元件各自的 HTTPS 接聽程式。若要連接現有 Gateway，請改為設定 `global.gateway.name`。

## 雲端平台預設值 {/* #cloud-presets */}

Chart 為各平台提供 values 預設檔，用來設定 `global.cloud` 與適合該平台的預設值：

| 平台 | 預設檔 | 說明 |
| - | - | - |
| GKE | `values-gke.yaml` | 建議使用 Gateway API；可透過 `serviceAccount.annotations` 設定 Workload Identity |
| EKS | `values-eks.yaml` | 預設使用 NLB；可透過 Ingress 註解使用 ALB；支援 IRSA |
| AKS | `values-aks.yaml` | Azure LoadBalancer 註解 |
| 本機（kind/minikube） | `values-local.yaml` | 在 `api.localhost` / `studio.localhost` 上使用 Ingress |

## 物件儲存 {/* #object-storage */}

若要連接與 S3 相容的物件儲存服務（S3、支援 HMAC 互通的 GCS 或 MinIO），請在 Server 上設定通用物件儲存值：

```yaml title="mastra-values.yaml"
mastra-server:
  externalServices:
    objectStore:
      endpoint: https://storage.googleapis.com
      bucket: my-mastra-bucket
      region: us-central1
```

請將 `S3_ACCESS_KEY_ID` 與 `S3_SECRET_ACCESS_KEY` 放入現有的 Secret，不要寫在 values 中。在 EKS 與 GKE 上，優先使用 IRSA 或 Workload Identity，而非固定金鑰。

## ClickHouse 可觀測性 {/* #clickhouse-observability */}

若要在 ClickHouse 中持續保存追蹤、日誌、指標、評分與回饋，請將 `CLICKHOUSE_URL`、`CLICKHOUSE_USERNAME` 與 `CLICKHOUSE_PASSWORD` 加入 `mastra-server.existingSecret` 參照的 Secret。上方的 Secret 範例已包含供 ClickHouse Cloud 使用的這些變數。

Chart 只會將變數提供給應用程式，本身不會設定可觀測性或傳送遙測資料。請為 `observability` 儲存領域設定 `ObservabilityStorageClickhouseVNext`，並在 Mastra 應用程式中加入 `MastraStorageExporter`。完整的應用程式設定請參閱 [ClickHouse](/integrations/databases/clickhouse#observability-with-vnext-recommended)。

啟用 `mastra-workers` 後，worker Pod 會掛載 Server 的 Secret。若單獨安裝 `mastra-workers` Chart，請將 `mastra-workers.server.existingSecret` 設為相同的 Secret 名稱。`mastra-projects` Chart 會驗證名稱是否一致。

## 擴充 Server 複本 {/* #scale-server-replicas */}

Chart 預設啟動一個 Server 複本。HorizontalPodAutoscaler 可以增加 Pod，但不會讓 Mastra 的程序內狀態在 Pod 之間共用。

將 `replicaCount` 設為大於 1，或啟用 `mastra-server.autoscaling` 之前：

- 設定共用儲存後端（例如 `PostgresStore`），保存執行狀態。
- 設定分散式 PubSub 後端及共用快取。[Kubernetes 指南](/integrations/deploy/kubernetes#configure-shared-infrastructure)使用 `RedisStreamsPubSub` 與 `RedisServerCache`，並將 `REDIS_URL` 存於應用程式 Secret。
- 對於請求可能送達不同 Pod、但串流、核准與執行仍須持續的情境，使用[持久化 Agent](/docs/harness/durable-agents)。
- 先以一個複本初始化資料庫結構，再擴充複本。若部署要求更嚴格，可透過 Kubernetes Job 初始化資料庫結構，並停用各 Pod 內的初始化。
- 查看 [worker 角色](/docs/deployment/workers#select-workers)。執行多個 scheduler 執行個體是安全的，因為每次排程只會由一個執行個體認領。

符合上述條件後，設定資源請求並啟用自動擴縮：

```yaml title="mastra-values.yaml"
mastra-server:
  resources:
    requests:
      cpu: 250m
      memory: 512Mi
  autoscaling:
    enabled: true
    minReplicas: 2
    maxReplicas: 5
    targetCPUUtilizationPercentage: 80
```

## 背景 worker {/* #background-workers */}

預設情況下，Server 會在自身程序內執行 Mastra 的背景 worker。`mastra-workers` 子 Chart 會將它們移至獨立 Deployment（每個角色一個），使 Workflow 編排、排程 Workflow 與背景任務可獨立於 API 擴縮。各角色的作用請參閱 [Workers](/docs/deployment/workers)。

worker **必須明確啟用**：未啟用時不會部署任何 worker。

### 先決條件 {/* #requirements */}



啟用 worker 之前：

- **在 Mastra 應用程式中設定可擷取事件的 PubSub 後端**，例如 Redis Streams、Valkey Streams 或 Google Cloud Pub/Sub。worker 會從訊息代理擷取事件，因此僅支援請求／回應的後端無法使用。請將連線字串（例如 `REDIS_URL`）放入 Server 使用的同一個 Secret。
- **若啟用 scheduler，設定支援 `schedules` 領域的儲存後端**：PostgreSQL、LibSQL、MySQL、MongoDB、Spanner 或 Convex。Redis 與 ClickHouse 不支援該領域，scheduler 無法從中找到已到執行時間的排程。
- **設定 `mastra-server.workers.splitDeployment: true`。** 否則 API 仍會在程序內執行 worker，導致每個 worker 除了在獨立 Deployment 中執行，也會在 API Pod 中執行。啟用 worker 卻未設定此項時，Chart 會拒絕產生資源。

:::warning Redis 資料淘汰政策
請將 Redis 或 Valkey 的 `maxmemory-policy` 設為 `noeviction`。任何允許淘汰資料的政策，都會在記憶體不足時刪除仍在使用的 Mastra 狀態：`allkeys-*` 政策會淘汰尚未確認的 Workflow 事件；`volatile-*` 政策則會淘汰租約鍵與串流，後兩者預設具有 TTL。之後執行可能停滯，卻不會產生執行錯誤。若政策允許淘汰，`RedisStreamsPubSub` 與 `ValkeyStreamsPubSub` 會在首次連線後記錄一次警告。在代管 Redis 上，此設定通常位於參數群組；Amazon ElastiCache 預設使用 `volatile-lru`。
:::

### 將 worker 建置產物加入映像檔 {/* #build-the-worker-artifact-into-your-image */}

worker 使用與 Server **相同的映像檔**，但使用映像檔內不同的進入點。單獨執行 `mastra build` 不會產生該進入點，因此還須進行第二次建置，並將輸出寫入其他目錄：

```bash
mastra build --studio
mastra worker build --output-dir .mastra/worker
```

必須指定 `--output-dir`。否則，`mastra worker build` 會寫入 `.mastra/output`，**覆蓋 Server 建置產物**，最後映像檔內只剩 worker 產物。

兩份建置產物宣告的相依套件不同：worker 會引入 Server 產物未列出的 `bufferutil`、`pg` 等套件。因此，兩者都需要分別執行 `npm install`。Node 會從進入點所在目錄向上尋找模組，所以 worker 能在 `.mastra/worker/node_modules` 找到所需套件：

```dockerfile title="Dockerfile"
FROM node:22-slim
WORKDIR /app

# Server bundle and its dependencies.
COPY .mastra/output/package.json .mastra/output/package-lock.json* ./
RUN npm install --force --prefer-offline --no-audit --no-fund
COPY .mastra/output ./

# Worker bundle and its dependencies, which differ from the server's.
COPY .mastra/worker/package.json .mastra/worker/package-lock.json* ./.mastra/worker/
RUN cd .mastra/worker && npm install --force --prefer-offline --no-audit --no-fund
COPY .mastra/worker ./.mastra/worker

EXPOSE 4111
CMD ["node", "index.mjs"]
```

```text title=".dockerignore"
.mastra/output/node_modules
.mastra/worker/node_modules
```

Server 仍透過 `CMD ["node", "index.mjs"]` 啟動，Studio 資源也仍位於 `/app/studio`，因此 Server 與 Studio 的部署方式不變。worker 進入點位於 `/app/.mastra/worker/index.mjs`，對應 Chart 預設的 `mastra-workers.command`。若映像檔目錄配置不同，請覆寫此設定。

:::warning 每次建置使用新標籤
每次建置都應使用獨立的映像檔標籤。Chart 預設將 `imagePullPolicy` 設為 `IfNotPresent`；若重新推送既有標籤，節點可能繼續使用快取的映像檔摘要，worker Pod 也會因舊產物而持續當機。
:::

### 啟用 worker {/* #enable-workers */}

worker 使用與 Server **相同的映像檔**；`mastra build` 會同時產生 worker 與 Server 的進入點。只要設定一次 `global.image`，所有元件就會使用同一個建置版本：

```yaml title="mastra-values.yaml"
global:
  image:
    repository: your-registry/my-mastra-app
    tag: '1.0.0'

mastra-server:
  existingSecret: mastra-app-env
  # Required: stop the API from also running workers in-process.
  workers:
    splitDeployment: true

mastra-workers:
  enabled: true
  server:
    # Must match mastra-server.existingSecret; the chart verifies this.
    existingSecret: mastra-app-env
  roles:
    orchestration:
      enabled: true
      replicaCount: 2
    scheduler:
      enabled: true
    backgroundTasks:
      enabled: true
```

worker Pod 掛載 **Server 的** ConfigMap 與 Secret，而非定義自己的設定，因此與 API 的設定自然一致，無須維護兩份相同的環境設定。

### 角色與擴縮 {/* #roles-and-scaling */}

| 角色 | 可擴充 | 說明 |
| - | - | - |
| `orchestration` | 可以 | 消費 `workflows` 主題，並回呼 API 執行步驟。消費者群組會將工作分配給各複本。 |
| `scheduler` | **不可以，固定為 1 個複本** | 輪詢儲存服務，尋找已到執行時間的 cron 排程。Chart 將複本數固定為 1，並使用 `Recreate` 策略。額外的 scheduler 雖然安全，但只會增加輪詢負載，不會提高吞吐量。 |
| `backgroundTasks` | 可以 | 在請求處理流程之外執行標記為 `background: { enabled: true }` 的 Agent Tool 呼叫。 |

兩個可擴充角色都支援自動擴縮。使用率目標必須有對應的資源請求；若缺少資源請求卻啟用自動擴縮，Chart 將無法產生資源：

```yaml title="mastra-values.yaml"
mastra-workers:
  roles:
    orchestration:
      resources:
        requests:
          cpu: 200m
          memory: 512Mi
      autoscaling:
        enabled: true
        minReplicas: 2
        maxReplicas: 5
        targetCPUUtilizationPercentage: 80
```

CPU 使用率只能粗略反映佇列積壓程度。若要依待處理事件數量擴縮，請使用 [KEDA](https://keda.sh/) 的 Redis Streams scaler，並指向同一個消費者群組。

### 使用獨立的 worker 映像檔 {/* #separate-worker-images */}

若建置分別產生 API 與 worker 映像檔，而非產生包含兩個進入點的單一映像檔，Chart 預設的版本一致性檢查會拒絕這項差異。請明確停用檢查：

```yaml title="mastra-values.yaml"
mastra-workers:
  image:
    tag: worker
    # Server and workers intentionally run different builds; keeping them on the
    # same source commit becomes your responsibility.
    allowServerSkew: true
  command: ['node', 'index.mjs'] # match your worker image's entrypoint
```

這項檢查用於防範 API 與 worker 版本不一致，因為雙方都不會明確報錯：worker 仍會啟動並消費佇列，卻對新的 API 執行舊版步驟程式碼。

### 設定變更後重新啟動 worker {/* #restarting-workers-after-a-config-change */}

Server 的 ConfigMap 或 Secret 變更後，worker Pod 不會自動重新啟動。Helm 的校驗和註解只涵蓋 Chart 自身管理的物件，而這些物件屬於 `mastra-server`。請手動滾動重新啟動 worker：

```bash
kubectl rollout restart deploy -n mastra   -l app.kubernetes.io/name=mastra-workers,app.kubernetes.io/instance=mastra
```

## 正式環境檢查清單 {/* #production-checklist */}

- 使用 `existingSecret` 參照憑證，不要在 values 中寫入明文。
- 透過 `mastra-server.resources` 與 `mastra-studio.resources` 設定資源請求。
- 優先個別安裝 cert-manager 與 Ingress 控制器，而非使用 Chart 內建的安裝開關；在整合型 Chart 中管理 CRD 生命週期，會使升級更加複雜。
- 設定共用儲存、分散式 PubSub、共用快取與必要的程序角色後，再啟用多個複本。
- 執行背景 worker 時，設定 `mastra-server.workers.splitDeployment: true`，並將 Redis 或 Valkey 的 `maxmemory-policy` 設為 `noeviction`。
- Chart 預設採用安全強化設定：容器以非 root 使用者執行、根檔案系統唯讀、seccomp 使用 `RuntimeDefault`，且不自動掛載 ServiceAccount 權杖。

## 升級與解除安裝 {/* #upgrade-and-uninstall */}

使用同一個指令，即可升級 Chart 版本或部署新的映像檔標籤：

```bash
CHART_VERSION=0.2.0
CHART=oci://us-central1-docker.pkg.dev/mastra-cloud/mastra-helm-ee/mastra-projects

helm upgrade mastra "$CHART" \
  --version "$CHART_VERSION" \
  -n mastra -f mastra-values.yaml
```

Chart 會將設定與 Secret 內容的雜湊值寫入 Pod 註解，因此設定變更會自動觸發滾動重新啟動。

解除安裝 Release：

```bash
helm uninstall mastra -n mastra
```



## 疑難排解 {/* #troubleshooting */}

- **`helm install` 或 `upgrade` 出現 `401 Unauthorized` 或 `UNAUTHORIZED`。** 儲存庫存取權杖遺失或已過期。請使用企業版授權從 `https://license.mastra.ai/v1/registry-token` 取得新權杖，再執行 `helm registry login`。
- **Pod 因 `Cannot find module '@libsql/linux-x64-gnu'`（或類似錯誤）而當機。** 映像檔含有為其他平台建置的 `node_modules`。請在映像檔內安裝相依套件，透過 `.dockerignore` 排除主機上建置的 `node_modules`，並使用符合叢集節點的 `--platform` 重新建置。
- **Pod 因授權錯誤反覆當機。** 設定企業版功能後，正式環境模式要求 Secret 中有有效的 `MASTRA_EE_LICENSE`。
- **Studio 顯示 Server API，而不是介面。** 建置映像檔時未包含 Studio 資源。請使用 `mastra build --studio` 重新建置。
- **worker Pod 因 `Cannot find module '/app/.mastra/worker/index.mjs'` 反覆當機。** 映像檔未包含 worker 建置產物。請執行 `mastra worker build --output-dir .mastra/worker`，將產物複製到映像檔，或覆寫 `mastra-workers.command` 以符合目錄配置。
- **Workflow 停滯且沒有錯誤。** 編排 worker 無法連線至 API，或 Redis 淘汰了尚未確認的事件。請核對 `mastra-workers.server.port` 與 `mastra-server.service.port`，確認限制性的 NetworkPolicy 允許 worker Pod 通行，並檢查 `maxmemory-policy` 是否為 `noeviction`。
- **worker Pod 一直處於 `CreateContainerConfigError`。** 它們會掛載 Server 的 ConfigMap 與 Secret，因此 `mastra-workers.server.existingSecret` 必須與 `mastra-server.existingSecret` 相同，而且不能將 `mastra-workers` 當作獨立 Release 安裝。
- **Ingress 沒有位址。** 確認 Ingress 控制器正在執行，或設定 `ingressController.install=true`。
- **在 gateway 模式下，憑證一直處於待核發狀態。** 某些 Gateway 控制器在接聽程式已有憑證之前，無法處理 ACME 驗證挑戰。請查看 Chart 的各雲端平台預設檔與版本說明，瞭解該平台的初始設定步驟。
