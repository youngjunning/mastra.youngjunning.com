# Kubernetes

將 Mastra 應用程式部署到 [Kubernetes](https://kubernetes.io/) 的多個 Pod，就能透過負載平衡器進行水平擴充。每個 Pod 都是獨立的處理程序，因此必須共用發布與訂閱後端及資料庫，其他 Pod 才能得知其中一個 Pod 啟動的工作。

:::note
本指南說明如何以手寫的資源清單部署 [Mastra 伺服器](/docs/server/overview)。若要透過受管理的 Chart 部署 Mastra Server 與 Studio，請參閱 [Kubernetes (Helm)](/integrations/deploy/kubernetes-helm)。若使用[伺服器轉接器](/docs/server/server-adapters)或 [Web 框架](/docs/deployment/web-framework)，請依該框架原有的方式部署。
:::

:::beta
多 Pod 部署仰賴[持久化 Agent](/docs/harness/durable-agents)。在 API 穩定前，即使主要版本號未變，也可能出現不相容的變更。用於正式環境前，請先閱讀[已知限制](#known-limitations)。
:::

## 開始之前 {/* #before-you-begin */}

請先備妥下列項目：

* 一個 [Mastra 應用程式](/docs)
* 一個 [Kubernetes](https://kubernetes.io/docs/setup/) 叢集及 [`kubectl`](https://kubernetes.io/docs/tasks/tools/)
* 一個可供叢集拉取映像檔的容器登錄檔
* 一個所有 Pod 都能連線的共用 [Redis](https://redis.io/) 執行個體
* 一個所有 Pod 都能連線的共用 [PostgreSQL](https://www.postgresql.org/) 資料庫

## 為什麼多個 Pod 需要共用基礎設施 {/* #why-multiple-pods-need-shared-infrastructure */}

只有一個 Pod 時，所有請求都由同一個處理程序接收，執行狀態可以留在該 Pod 的記憶體中。有多個 Pod 時，瀏覽器可能正在接收 Pod A 的串流，但使用者的下一個請求被轉送到 Pod B。Pod B 無法取得 Pod A 上的執行紀錄。

Redis 與 Postgres 分別解決事件傳遞和狀態保存的問題：

* **發布與訂閱**負責在 Pod 之間傳遞事件。一個 Pod 發布事件後，其他 Pod 就會收到。Mastra 使用 [`RedisStreamsPubSub`](/reference/pubsub/redis-streams) 為每個對話執行緒提供租約，讓同一時間只有一個 Pod 持有該對話。請參閱[發布與訂閱](/docs/server/pubsub)。
* **儲存**負責持久保存執行狀態。[持久化 Agent](/docs/harness/durable-agents) 會將每次執行儲存為 Workflow 快照，讓任一 Pod 都能在重啟後或請求轉送至別處時，從資料庫接續該次執行。

## 設定共用基礎設施 {/* #configure-shared-infrastructure */}

將 `Mastra` 執行個體連線到 Redis 與 Postgres。從環境變數讀取連線資訊，讓每個 Pod 都可以使用同一個映像檔。

安裝後端所需的套件：

```bash npm2yarn
npm install @mastra/redis-streams @mastra/pg @mastra/redis ioredis
```

在 `Mastra` 執行個體中設定發布與訂閱、儲存和共用快取：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'
import { RedisServerCache } from '@mastra/redis'
import { PostgresStore } from '@mastra/pg'
import Redis from 'ioredis'

export const mastra = new Mastra({
  // Carries events between pods, and provides
  // per-thread leases so one pod owns a conversation at a time.
  pubsub: new RedisStreamsPubSub({
    url: process.env.REDIS_URL!,
  }),
  // Persists run state so any pod can resume a run.
  storage: new PostgresStore({
    id: 'mastra-storage',
    connectionString: process.env.DATABASE_URL!,
  }),
  // Shared event cache so a reconnecting client can replay missed chunks
  // from any pod, not only the one that started the run.
  cache: new RedisServerCache({ client: new Redis(process.env.REDIS_URL!) }),
})
```

`cache` 讓用戶端可以跨 Pod 接續串流。用戶端重新連線時會從快取重播中斷期間錯過的事件，因此每個 Pod 都必須共用這份快取。預設的記憶體快取只支援在同一個處理程序內重播。

## 使用持久化 Agent {/* #use-durable-agents */}

一般的 [`Agent`](/docs/agents/overview) 把串流和核准狀態保留在單一 Pod 的記憶體中。請求轉送到另一個 Pod 時，該 Pod 無法取得這些資訊。[持久化 Agent](/docs/harness/durable-agents) 會在 Workflow 內執行 Agent 迴圈並持久保存狀態，因此任一 Pod 都能觀察或接續同一次執行。

以 `createDurableAgent()` 包裝 Agent：

```typescript title="src/mastra/agents/assistant.ts"
import { Agent } from '@mastra/core/agent'
import { createDurableAgent } from '@mastra/core/agent/durable'

const agent = new Agent({
  id: 'assistant',
  name: 'Assistant',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

export const durableAssistant = createDurableAgent({ agent })
```

將持久化 Agent 註冊到前面設定的 `Mastra` 執行個體。執行狀態會儲存在 Postgres，事件則透過 Redis 傳遞，每個 Pod 都能存取該次執行。

## 部署 {/* #deploy */}

<Steps>
  <StepItem>
    依照 [Mastra 伺服器](/docs/server/overview)指南建置伺服器，將其封裝成容器映像檔，再推送到容器登錄檔。確認伺服器會從 `process.env.PORT` 讀取連接埠，並在 `0.0.0.0` 上接聽。
  </StepItem>

  <StepItem>
    將共用的連線字串存入 Secret：

    ```bash
    kubectl create secret generic mastra-secrets \
      --from-literal=REDIS_URL='redis://redis:6379' \
      --from-literal=DATABASE_URL='postgresql://user:pass@postgres:5432/mastra'
    ```
  </StepItem>

  <StepItem>
    套用 Deployment，使用該映像檔啟動容器並讀取共用的 Secret。先啟動一個複本，讓第一個 Pod 獨自建立資料庫結構描述，再於下一步增加複本：

    ```yaml title="deployment.yaml"
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: mastra
    spec:
      replicas: 1
      selector:
        matchLabels:
          app: mastra
      template:
        metadata:
          labels:
            app: mastra
        spec:
          containers:
            - name: mastra
              image: your-registry/mastra:latest
              ports:
                - containerPort: 8080
              env:
                - name: PORT
                  value: '8080'
              envFrom:
                - secretRef:
                    name: mastra-secrets
              readinessProbe:
                tcpSocket:
                  port: 8080
              livenessProbe:
                tcpSocket:
                  port: 8080
              resources:
                requests:
                  cpu: 500m
                  memory: 512Mi
    ```

    下方的 HorizontalPodAutoscaler 需要 `resources.requests.cpu`。Kubernetes 以實際 CPU 用量除以 CPU 請求量來計算使用率。若未指定 CPU 請求量，自動擴縮控制器就無法算出目標複本數，也不會調整規模。

    ```bash
    kubectl apply -f deployment.yaml
    ```

    等第一個 Pod 就緒後，再增加複本數：

    ```bash
    kubectl wait --for=condition=available deployment/mastra
    kubectl scale deployment/mastra --replicas=3
    ```

    :::note
    每個複本都使用同一個映像檔，並連線到同一組 Redis 與 Postgres。要跨 Pod 接續執行，必須共用這些基礎設施，光增加 Pod 數量並不足夠。
    :::
  </StepItem>

  <StepItem>
    透過 Service 開放對 Deployment 的存取：

    ```yaml title="service.yaml"
    apiVersion: v1
    kind: Service
    metadata:
      name: mastra
    spec:
      selector:
        app: mastra
      ports:
        - port: 80
          targetPort: 8080
    ```

    ```bash
    kubectl apply -f service.yaml
    ```
  </StepItem>

  <StepItem>
    使用 HorizontalPodAutoscaler 自動調整複本數：

    ```yaml title="hpa.yaml"
    apiVersion: autoscaling/v2
    kind: HorizontalPodAutoscaler
    metadata:
      name: mastra
    spec:
      scaleTargetRef:
        apiVersion: apps/v1
        kind: Deployment
        name: mastra
      minReplicas: 3
      maxReplicas: 10
      metrics:
        - type: Resource
          resource:
            name: cpu
            target:
              type: Utilization
              averageUtilization: 70
    ```

    ```bash
    kubectl apply -f hpa.yaml
    ```

    :::note
    若要依 CPU 使用率自動擴縮，叢集內必須執行 [metrics-server](https://github.com/kubernetes-sigs/metrics-server)。GKE、EKS 和 AKS 等受管理叢集內含此元件。kind 和 minikube 等本機叢集則需要先啟用，例如執行 `minikube addons enable metrics-server`。
    :::
  </StepItem>

  <StepItem>
    確認 Pod 正在執行：

    ```bash
    kubectl get pods -l app=mastra
    ```

    在一個終端機視窗中，將 Service 的連接埠轉送到本機。這個指令會持續在前景執行：

    ```bash
    kubectl port-forward service/mastra 8080:80
    ```

    另開一個終端機視窗呼叫 API：

    ```bash
    curl http://localhost:8080/api/agents
    ```

    收到列出 Agent 的 JSON 清單，就表示部署已能回應請求。

    :::warning
    對外公開端點前，請先設定[身分驗證](/docs/auth/overview)。
    :::
  </StepItem>
</Steps>

## 串流與重新連線 {/* #streaming-and-reconnection */}

持久化 Agent 透過共用的發布與訂閱後端，將串流資料區塊發布到該次執行專用的主題。用戶端中斷連線後，可用執行 ID 呼叫 `observe()` 重新連線，再從共用快取重播錯過的資料區塊：

```typescript title="src/server/reconnect.ts"
const { output, detach } = await durableAssistant.observe(runId)

request.signal.addEventListener('abort', detach, { once: true })

if (request.signal.aborted) detach()

for await (const chunk of output.fullStream) {
  // Chunks from the run, including any missed while disconnected
}
```

執行狀態儲存在 Postgres，事件則保存在 Redis，因此任何 Pod 都能處理重新連線的請求，即使該次執行由其他 Pod 啟動。請參閱[可接續的串流](/docs/harness/durable-agents#resumable-streams)。

多個用戶端可同時觀察同一次執行。每次呼叫 `observe()` 都會收到完整串流，因此同一人使用兩部裝置，或兩人各自查看這次執行時，看到的內容都會同步。用戶端離開迴圈或呼叫 `detach()` 時，只有該用戶端會停止接收。請勿從觀察端呼叫 `cleanup()`，以免清除其他用戶端重新連線所需的快取事件。

## 跨 Pod 核准 Tool 呼叫 {/* #tool-approval-across-pods */}

持久化 Agent 會在呼叫 Tool 前暫停，直到有人核准。暫停的執行會儲存到 Postgres，因此可由任何 Pod 處理核准請求。

啟動一次需要核准的執行：

```typescript title="src/server/approval.ts"
const { runId } = await durableAssistant.stream('Delete the archived records', {
  requireToolApproval: true,
  memory: { thread: 'thread-1', resource: 'user-1' },
})
```

執行會在 Tool 執行前暫停。稍後可透過任一 Pod 核准這次呼叫：

```typescript
await durableAssistant.resume(runId, { approved: true })
```

處理核准請求的 Pod 會從 Postgres 載入暫停的執行，執行獲准的 Tool 呼叫，再透過共用的發布與訂閱後端發布結果。正在觀察的用戶端便能收到接續的輸出。請參閱 [Tool 核准](/docs/harness/durable-agents#tool-approval)。

## 已知限制 {/* #known-limitations */}

* 預設設定會將執行狀態保留在單一 Pod 的處理程序記憶體中，其他 Pod 無法存取。搭配共用的 Redis 與 Postgres 使用[持久化 Agent](/docs/harness/durable-agents)，即可跨 Pod 串流、核准及重新連線。
* 跨 Pod 串流、核准及重新連線都必須使用持久化 Agent。一般 Agent 的執行狀態留在記憶體中，無法在其他 Pod 上接續執行。
* 多個 Pod 同時啟動並連線到尚未初始化的資料庫時，可能會競相建立結構描述，導致某個 Pod 無法啟動。請先啟動一個複本，等結構描述建立後再增加複本。
* 若要更嚴格控管初始化流程，請在應用程式之外初始化資料庫的結構描述，例如執行一次性的 Kubernetes Job。接著在每個 Pod 的 `PostgresStore` 中設定 `disableInit: true`。
