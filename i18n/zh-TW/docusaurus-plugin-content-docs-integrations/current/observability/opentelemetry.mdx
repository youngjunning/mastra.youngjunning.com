# 開放式遙測

Mastra 透過導出器支援 OpenTelemetry (OTEL)，用於將追蹤和日誌發送到 OTEL 相容平台，並作為參與現有 OTEL 追蹤上下文的橋樑。

## 出口商 {/* #exporter */}

OpenTelemetry 匯出器使用標準化發送您的追蹤和日誌[OpenTelemetry Semantic Conventions for GenAI](https://opentelemetry.io/docs/specs/semconv/gen-ai/). This ensures broad compatibility with platforms like Datadog, New Relic, Sentry, SigNoz, MLflow, Latitude, Dash0, Traceloop, Laminar, telemetry.dev, Sazabi, and more.

### 安裝 {/* #installation */}

每個Provider都需要特定的協議包。為您的Provider安裝基本匯出器和協定套件：

#### 對於 HTTP/Protobuf Provider（SigNoz、New Relic、Sentry、Laminar、MLflow、Latitude、telemetry.dev） {/* #for-httpprotobuf-providers-signoz-new-relic-sentry-laminar-mlflow-latitude-telemetrydev */}

```bash npm2yarn
npm install @mastra/otel-exporter@latest @opentelemetry/exporter-trace-otlp-proto
```

#### 為了`gRPC` providers (Dash0, Datadog) {/* #for-grpc-providers-dash0-datadog */}

```bash npm2yarn
npm install @mastra/otel-exporter@latest @opentelemetry/exporter-trace-otlp-grpc @grpc/grpc-js
```

#### 對於 HTTP/JSON Provider（Traceloop、Sazabi） {/* #for-httpjson-providers-traceloop-sazabi */}

```bash npm2yarn
npm install @mastra/otel-exporter@latest @opentelemetry/exporter-trace-otlp-http
```

### Provider配置 {/* #provider-configurations */}

#### 哨兵 {/* #sentry */}

[哨兵](https://sentry.io/)透過其 OTLP 端點接受 OpenTelemetry 追蹤和日誌。在哨兵中，打開[**Project Settings** > **Client Keys (DSN)**](https://sentry.io/settings/projects/) and copy the OTLP traces endpoint and authentication header. Add both values to your environment:

```bash title=".env"
SENTRY_OTLP_ENDPOINT=https://o000000.ingest.sentry.io/api/0000000/integration/otlp/v1/traces
SENTRY_OTLP_AUTH_HEADER="sentry sentry_key=..."
```

使用`custom` provider with HTTP/Protobuf:

```typescript title="src/mastra/index.ts"
new OtelExporter({
  provider: {
    custom: {
      endpoint: process.env.SENTRY_OTLP_ENDPOINT!,
      protocol: 'http/protobuf',
      headers: {
        'x-sentry-auth': process.env.SENTRY_OTLP_AUTH_HEADER!,
      },
    },
  },
})
```

看[Sentry's OTLP documentation](https://docs.sentry.io/concepts/otlp/) for endpoint setup, supported signals, and current ingestion limits.

根據您的設定選擇導出器：

* `OtelExporter`：透過 OTLP 發送Provider中立的追蹤和日誌。將其與現有 OpenTelemetry 管道一起使用或當您需要後端可攜性時。
* [`SentryExporter`](/integrations/observability/sentry)

#### {/* #mlflow */}

[](https://mlflow.org/docs/latest/genai/tracing/integrations/listing/mastra)透過其 OTLP 端點支援本機 Mastra 跟踪`/v1/traces`. Use the `custom` provider with HTTP/Protobuf and include the experiment header so traces are routed to the correct MLflow experiment:

```typescript title="src/mastra/index.ts"
new OtelExporter({
  provider: {
    custom: {
      endpoint: `${process.env.MLFLOW_TRACKING_URI}/v1/traces`,
      protocol: 'http/protobuf',
      headers: {
        'x-mlflow-experiment-id': process.env.MLFLOW_EXPERIMENT_ID,
      },
    },
  },
})
```

#### 緯度 {/* #latitude */}

[緯度](https://latitude.so)是一個開源 LLM 可觀察性和評估平台，可擷取 OTLP 痕跡。使用`custom` provider with HTTP/Protobuf, pointing at Latitude's ingestion endpoint and authenticating with your API key and project slug:

```typescript title="src/mastra/index.ts"
new OtelExporter({
  provider: {
    custom: {
      endpoint: 'https://ingest.latitude.so/v1/traces',
      protocol: 'http/protobuf',
      headers: {
        Authorization: `Bearer ${process.env.LATITUDE_API_KEY}`,
        'X-Latitude-Project': process.env.LATITUDE_PROJECT,
      },
    },
  },
})
```

註冊於[console.latitude.so](https://console.latitude.so/login), or self-host and point the endpoint at your own ingestion host.

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'
import { OtelExporter } from '@mastra/otel-exporter'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      otel: {
        serviceName: 'my-service',
        exporters: [
          new OtelExporter({
            provider: {
              dash0: {
                apiKey: process.env.DASH0_API_KEY,
                endpoint: process.env.DASH0_ENDPOINT, // e.g., 'ingress.us-west-2.aws.dash0.com:4317'
                dataset: 'production', // Optional dataset name
              },
            },
            resourceAttributes: {
              // Optional OpenTelemetry Resource Attributes for the trace
              ['deployment.environment']: 'dev',
            },
          }),
        ],
      },
    },
  }),
})
```

#### 數據狗 {/* #datadog */}

[數據狗](https://www.datadoghq.com/)APM 透過分散式追蹤提供應用程式效能監控。要透過 OTLP 將追蹤傳送到 Datadog，您需要在啟用 OTLP 攝取的情況下執行 Datadog Agent程式。

Datadog 使用 gRPC 進行 OTLP 攝取，這需要明確導入和[bundler configuration](/reference/configuration#bundlerexternals) to work correctly:

```typescript title="src/mastra/index.ts"
// Explicitly import gRPC dependencies for the bundler
import '@grpc/grpc-js'
import '@opentelemetry/exporter-trace-otlp-grpc'
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'
import { OtelExporter, type ExportProtocol } from '@mastra/otel-exporter'

export const mastra = new Mastra({
  // Add grpc-js to externals so it's handled at runtime
  bundler: {
    externals: ['@grpc/grpc-js'],
  },
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-service',
        exporters: [
          new OtelExporter({
            provider: {
              custom: {
                endpoint: process.env.OTEL_EXPORTER_OTLP_ENDPOINT || 'http://localhost:4317',
                protocol: (process.env.OTEL_EXPORTER_OTLP_PROTOCOL || 'grpc') as ExportProtocol,
                headers: {},
              },
            },
          }),
        ],
      },
    },
  }),
})
```

：：：筆記

Datadog Agent 必須配置為啟用 OTLP 攝取。將以下內容新增至您的`datadog.yaml`:

```yaml
otlp_config:
  receiver:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
```

預設 OTLP 端點是`http://localhost:4317` when running the Datadog Agent locally.

:::

：：：警告

明確導入`@grpc/grpc-js` and `@opentelemetry/exporter-trace-otlp-grpc` at the top of the file, along with the [`bundler.externals`](/reference/configuration#bundlerexternals) configuration, are required for the gRPC transport to work correctly. Without these, you may encounter connection issues.

:::

:::提示 Datadog-Native Exporter

對於 Datadog 特定的功能，例如自動跨度類型映射、LLM 跨度分類以及無需 gRPC 配置的簡化設置，請考慮使用專用[`@mastra/datadog`](/integrations/observability/datadog) exporter instead. It provides optimized integration with Datadog's APM platform.

### 訊號 {/* #signals */}

導出器發送兩個 OpenTelemetry 訊號：

* 痕跡：Mastra 跨越，透過導出`BatchSpanProcessor`.
* 日誌：Mastra 日誌事件，透過匯出`BatchLogRecordProcessor`. Logs that carry `traceId` and `spanId` are correlated with traces using both the OTEL log record's native trace context and `mastra.traceId` / `mastra.spanId` attributes, so backends like Datadog, Grafana, and Honeycomb can join logs to traces automatically.

這兩個訊號預設啟用並共享相同的Provider配置。日誌端點是從追蹤端點派生的，方法是替換`/v1/traces` suffix with `/v1/logs`.

若要停用訊號，請設定`signals` option:

```typescript title="src/mastra/index.ts"
new OtelExporter({
  provider: {/* ... */},
  signals: {
    traces: true, // default
    logs: false, // disable log export
  },
})
```

日誌匯出需要為您的協定安裝相符的 OTLP 日誌匯出程式包：

```bash npm2yarn
# HTTP/JSON
npm install @opentelemetry/exporter-logs-otlp-http
# HTTP/Protobuf
npm install @opentelemetry/exporter-logs-otlp-proto
# gRPC
npm install @opentelemetry/exporter-logs-otlp-grpc @grpc/grpc-js
```

如果未安裝匹配的日誌匯出程式包，日誌匯出將被靜默停用並且追蹤將繼續工作。

### 配置選項 {/* #configuration-options */}

#### 完整配置 {/* #complete-configuration */}

```typescript
new OtelExporter({
  // Provider configuration (required)
  provider: {
    // Use one of: dash0, signoz, newrelic, traceloop, laminar, custom
  },

  // Per-signal toggles. Both default to true.
  signals: {
    traces: true,
    logs: true,
  },

  // Export configuration
  timeout: 30000, // Export timeout in milliseconds
  batchSize: 100, // Number of spans/logs per batch

  // Debug options
  logLevel: 'info', // 'debug' | 'info' | 'warn' | 'error'
})
```

### `OpenTelemetry`語意約定 {/* #opentelemetry-semantic-conventions */}

出口商如下[OpenTelemetry Semantic Conventions for GenAI v1.38.0](https://github.com/open-telemetry/semantic-conventions/tree/v1.38.0/docs/gen-ai), ensuring compatibility with observability platforms:

#### {/* #span-naming */}

* **模型調用**: `chat {model}`
* **生成循環**: `model_generation {model}`, with one `agent_step {agent_id}` per turn
* **Tool執行**: `execute_tool {tool_name}`
* **Agent運行**: `invoke_agent {agent_id}`
* **Workflow運行**: `invoke_workflow {workflow_id}`

每個Agent輪流調用模型一次。這`chat` span is that call and is the only span that carries `gen_ai.request.model`, the messages, and `gen_ai.usage.*`, so backends that sum usage across spans count each call once. The `model_generation` span wraps the whole loop and `agent_step` wraps one turn (model call plus tool execution); neither carries usage.

#### 關鍵屬性 {/* #key-attributes */}

* `gen_ai.operation.name`- 操作類型（聊天、Tool.執行等）
* `gen_ai.provider.name`- AIProvider（openai、anthropic等）
* `gen_ai.request.model`- 型號識別符
* `gen_ai.input.messages`- 提供模特兒聊天記錄
* `gen_ai.output.messages`- 模型傳回的訊息
* `gen_ai.usage.input_tokens`- 輸入令牌的數量
* `gen_ai.usage.output_tokens`- 輸出代幣數量
* `gen_ai.request.temperature`- 採樣溫度
* `gen_ai.response.finish_reasons`- 完成原因

## 橋 {/* #bridge */}

：：：警告

OpenTelemetry Bridge 目前正在**experimental**. APIs and configuration options may change in future releases.

:::

OpenTelemetry (OTEL) 橋可實現 Mastra 追蹤系統和現有 OpenTelemetry 基礎架構之間的雙向整合。與將追蹤資料傳送到外部平台的匯出器不同，橋接器會建立參與分散式追蹤上下文的本機 OTEL 跨度。

### 何時使用橋 {/* #when-to-use-the-bridge */}

使用`OtelBridge` when you:

* 在您的應用程式中擁有現有的 OTEL Tool（HTTP 伺服器、資料庫用戶端等）
* 希望 Mastra 操作顯示為現有 OTEL 追蹤的子範圍
* 需要 Mastra Tool內的 OTEL 檢測程式碼來維持正確的父子關係
*

### 它是如何運作的 {/* #how-it-works */}

這`OtelBridge` provides two-way integration:

**從 OTEL 到 馬斯特拉：**

* 自動從 OTEL 環境上下文 (AsyncLocalStorage) 讀取
* 從活動 OTEL 範圍繼承追蹤 ID 和父範圍 ID
* 尊重 OTEL 採樣決策：如果未對追蹤進行採樣，Mastra 不會為其建立跨度
* 當 OTEL 自動偵測處於作用中狀態時，無需手動傳遞跡線 ID

**從馬斯特拉到 OTEL：**

* 為 Mastra 操作建立原生 OTEL 範圍（Agent程式、LLM 通話、Tool、Workflow）
*
* 允許 Mastra 操作中的 OTEL 檢測程式碼（HTTP 用戶端、資料庫呼叫）正確嵌套
* 將 Mastra 日誌事件轉送至全球註冊的 OTEL`LoggerProvider`. Logs that originate inside a Mastra span are emitted under that span's OTEL context so backends correlate them with the trace. If no `LoggerProvider` is registered, log emission is a silent no-op.

### 安裝 {/* #installation-1 */}

```bash npm2yarn
npm install @mastra/otel-bridge
```

該橋可與您現有的 OpenTelemetry 設定搭配使用。根據您的配置，您可能還需要以下一些軟體包：

* `@opentelemetry/sdk-node`- OTEL 的核心 Node.js SDK
* `@opentelemetry/auto-instrumentations-node`- 常見庫的自動檢測
* `@opentelemetry/exporter-trace-otlp-proto`
* `@opentelemetry/exporter-trace-otlp-http`- OTLP 導出器（透過 HTTP 的 JSON）
* `@opentelemetry/exporter-trace-otlp-grpc`- OTLP 導出器 (gRPC)
* `@opentelemetry/sdk-trace-base`- 基礎追蹤 SDK（用於`BatchSpanProcessor`, etc.)
* `@opentelemetry/core`- 核心實用程式（用於`W3CTraceContextPropagator`, etc.)
* `@opentelemetry/sdk-logs`和 OTLP 日誌匯出器（例如`@opentelemetry/exporter-logs-otlp-http`) - Required if you want the bridge to forward Mastra log events too

### 配置 {/* #configuration */}

使用`OtelBridge` requires two steps:

1. 在應用程式中設定 OpenTelemetry 檢測
2. 添加`OtelBridge` to your Mastra observability config

#### 第 1 步：開放遙測儀器 {/* #step-1-opentelemetry-instrumentation */}

建立一個初始化 OTEL 的檢測檔。這必須在您的應用程式程式碼之前運行：

```typescript title="instrumentation.ts"
import { NodeSDK } from '@opentelemetry/sdk-node'
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node'
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-proto'
import { BatchSpanProcessor } from '@opentelemetry/sdk-trace-base'
import { W3CTraceContextPropagator } from '@opentelemetry/core'

const sdk = new NodeSDK({
  serviceName: 'my-service',
  spanProcessors: [
    new BatchSpanProcessor(
      new OTLPTraceExporter({
        url: process.env.OTEL_EXPORTER_OTLP_ENDPOINT || 'http://localhost:4318/v1/traces',
      }),
    ),
  ],
  instrumentations: [getNodeAutoInstrumentations()],
  textMapPropagator: new W3CTraceContextPropagator(),
})

sdk.start()

export { sdk }
```

#### 第 2 步：Mastra 配置 {/* #step-2-mastra-configuration */}

添加`OtelBridge` to your Mastra observability config:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'
import { OtelBridge } from '@mastra/otel-bridge'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-service',
        bridge: new OtelBridge(),
      },
    },
  }),
  agents: {/* your agents */},
})
```

使用該橋時不需要 Mastra 出口商。追蹤透過您的 OTEL SDK 配置發送。如果您想將追蹤傳送到其他目的地，您可以選擇新增 Mastra 匯出器。

#### 轉發日誌（可選） {/* #forwarding-logs-optional */}

該橋還將 Mastra 日誌事件轉發到全球註冊的 OTEL`LoggerProvider`. To wire up logs alongside traces, register a log record processor on `NodeSDK`:

```typescript title="instrumentation.ts"
import { NodeSDK } from '@opentelemetry/sdk-node'
import { OTLPLogExporter } from '@opentelemetry/exporter-logs-otlp-http'
import { BatchLogRecordProcessor } from '@opentelemetry/sdk-logs'

const sdk = new NodeSDK({
  // ...trace config as usual
  logRecordProcessors: [
    new BatchLogRecordProcessor({
      exporter: new OTLPLogExporter({
        url: process.env.OTEL_EXPORTER_OTLP_LOGS_ENDPOINT || 'http://localhost:4318/v1/logs',
      }),
    }),
  ],
})
```

源自 Mastra 跨度內部的日誌在該跨度的 OTEL 上下文下發出，因此 Datadog、Grafana 和 Honeycomb 等後端會自動將它們與周圍的追蹤關聯起來。沒有追蹤上下文的日誌使用目前活動的 OTEL 上下文。

如果您沒有註冊`LoggerProvider`, log emission is a silent no-op. Traces continue to work as configured.

#### 運行您的應用程式 {/* #running-your-application */}

使用`--import` flag to ensure instrumentation loads before your application:

```bash
tsx --import ./instrumentation.ts ./src/index.ts
```

#### 退出前沖洗 {/* #flushing-before-exit */}

馬斯特拉的`flush()` and `shutdown()` ask the registered OTEL providers to flush, but a `BatchSpanProcessor` can still hold a batch it has already started exporting. In serverless or short-lived processes, also `await sdk.shutdown()` after Mastra's flush, so no spans are left in your OTEL SDK when the process exits. The provider's own `forceFlush()` is not enough: it does not wait for a batch the exporter is already sending.

### 語意約定 {/* #semantic-conventions */}

這`OtelBridge` exports Mastra spans using [OpenTelemetry Semantic Conventions for GenAI v1.38.0](https://github.com/open-telemetry/semantic-conventions/tree/v1.38.0/docs/gen-ai). This includes standardized span names (`chat {model}`, `execute_tool {tool_name}`, etc.) and attributes (`gen_ai.usage.input_tokens`, `gen_ai.request.model`, etc.).

有關跨度命名和屬性的詳細信息，請參閱[OpenTelemetry Exporter semantic conventions](#opentelemetry-semantic-conventions).

### 追蹤層次結構 {/* #trace-hierarchy */}

隨著`OtelBridge`, your traces maintain proper hierarchy across OTEL and Mastra boundaries:

```text
HTTP POST /api/chat (from Hono middleware)
└── agent.assistant (from Mastra via OtelBridge)
    └── model_generation __AI_SDK_OPENAI_MODEL_BASE__ (generation loop)
        ├── agent_step assistant (turn 1)
        │   ├── chat __AI_SDK_OPENAI_MODEL_BASE__ (LLM call)
        │   └── execute_tool search (tool execution)
        │       └── HTTP GET api.example.com (from OTEL auto-instrumentation)
        └── agent_step assistant (turn 2)
            └── chat __AI_SDK_OPENAI_MODEL_BASE__ (follow-up LLM call)
```

### 多服務分散式追蹤 {/* #multi-service-distributed-tracing */}

這`OtelBridge` enables trace propagation across service boundaries. When Service A calls Service B via HTTP, trace context propagates automatically:

```text
Service A: HTTP POST /api/process
└── HTTP POST service-b/api/analyze (outgoing call)

Service B: HTTP POST /api/analyze (incoming call - same trace!)
└── agent.analyzer (Mastra agent inherits trace context)
    └── model_generation __AI_SDK_OPENAI_MODEL_BASE__
        └── agent_step analyzer
            └── chat __AI_SDK_OPENAI_MODEL_BASE__
```

兩項服務必須有：

1. OTEL儀表配置
2. 啟用 W3C 追蹤上下文傳播器
3. 馬斯特拉與`OtelBridge` configured

馬斯特拉`MCPServer` request over HTTP follows the same rule. With this setup, it joins the caller's trace. Without HTTP instrumentation on the server, each request keeps its own trace. In both cases, when a request carries a W3C `traceparent`, in `_meta` or as an HTTP header, the request span links to the caller's span, and the exporter and the bridge send that link as an OpenTelemetry span link. See [Linking to the caller's trace](/reference/tools/mcp-server#linking-to-the-callers-trace).

### 使用標籤 {/* #using-tags */}

標籤可協助您對 OTEL 後端中的追蹤進行分類和過濾。執行Agent程式或Workflow時新增標籤：

```typescript
const result = await agent.generate('Hello', {
  tracingOptions: {
    tags: ['production', 'experiment-v2', 'user-request'],
  },
})
```

標籤導出為 JSON 字串`mastra.tags` span attribute for broad backend compatibility. Common use cases include:

* 環境標籤：`"production"`, `"staging"`
* 實驗追蹤：`"experiment-v1"`, `"control-group"`
* 優先：`"priority-high"`, `"batch-job"`

### 故障排除 {/* #troubleshooting-1 */}

如果追蹤未如預期顯示或連線：

* 驗證 OTEL SDK 在 Mastra 之前已初始化（使用`--import` flag or import at the top of the entry point)
* 如果你看到`[OtelBridge] No OpenTelemetry tracer provider is registered globally`, the bridge can't find a tracer provider. Some frameworks create a provider without registering it globally. Pass that provider directly with `new OtelBridge({ tracerProvider })`. See [setup requirements](/reference/observability/tracing/bridges/otel#setup-requirements)
* 確保`OtelBridge` is added to your observability config
* 檢查您的 OTEL 後端是否正在運行且可訪問
