# Knowledge

Studio 的 Knowledge 頁面讓你查看 Agent 掌握了甚麼：各個範圍和頁面、彼此的連繫，以及內容由誰撰寫。這個頁面只供讀取，可用來檢查已載入的內容，並即時查看 Agent 的修改。

:::alpha

Knowledge 仍在 alpha 階段，API 可能會隨版本更改。

:::

## 啟用路由 {/* #enable-the-routes */}

Knowledge 路由**預設關閉**。啟用之前，Studio 的 Knowledge 頁面會提示瀏覽功能尚未啟用。在 `Mastra` 註冊 Knowledge 實例，再加入路由：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { KNOWLEDGE_ROUTES } from '@mastra/server/server-adapter'
import { knowledge } from './knowledge'
import { supportAgent } from './agents/support-agent'

export const mastra = new Mastra({
  agents: { supportAgent },
  knowledge: { company: knowledge },
  server: { apiRoutes: [...KNOWLEDGE_ROUTES] },
})
```

路由掛載於伺服器的 API 前綴下，預設為 `/api/knowledge`，並需要 `@mastra/core` 1.81.0 或更新版本。使用 1.81.0 時，Studio 只會統計已載入頁面之間的連結。各條路由、參數和錯誤詳見[伺服器路由](/reference/server/routes#knowledge)。

## 頁面顯示的內容 {/* #what-you-see */}

- **頁面樹**：按 Agent 編排的層級，顯示各個範圍及其頁面。
- **關係圖**：展示相同的頁面及其連繫。連線表示上層頁面、備註提到的頁面、正文所載的連結，以及哪些範圍向其他範圍授予存取權。圖例說明各種連線；在任一檢視選取頁面即可開啟。
- **頁面**：顯示正文、版本、最後更新者、備註及作者、下層頁面、其他頁面提及本頁的備註，以及頁面為哪些對象置頂。
- **活動**：顯示每個頁面的新增、編輯、移動、合併、備註和置頂紀錄，以及每項操作的作者和時間。
- **搜尋**：按頁面名稱、描述、正文及備註文字搜尋。

在較窄的屏幕上，頁面樹和關係圖共用一個面板；切換檢視時會保留已選頁面。

Agent 寫入時，頁面樹、關係圖和已開啟的頁面會即時更新，毋須重新載入。Studio 會追蹤經 Mastra 已註冊的 Knowledge 實例寫入的內容。若由另一程序或使用同一儲存空間的另一實例寫入，重新載入後才會顯示。

## 控制用戶可見的內容 {/* #control-who-sees-what */}

路由傳回的內容視乎應用程式有否設定身分驗證（`server.auth` 或 `studio.auth`）：

- **沒有身分驗證：**路由以實例擁有者身分讀取資料，並向任何可連接伺服器的人傳回所有範圍、頁面和備註。只應在本機或測試項目使用此設定，並在部署前加入身分驗證。
- **設有身分驗證：**路由只會傳回已登入用戶有權讀取的內容。在 `authorize` 內，將請求上下文的 `MASTRA_KNOWLEDGE_PRINCIPALS_KEY` 設為該用戶的 Knowledge 範圍。Knowledge 沿用 Agent 的存取規則。在 alpha 階段，這些規則並不構成[隔離邊界](/docs/knowledge/scopes-and-access)，因此不要儲存絕不能讓其他用戶取得的內容。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { KNOWLEDGE_ROUTES, MASTRA_KNOWLEDGE_PRINCIPALS_KEY } from '@mastra/server/server-adapter'
import { appAuthorize } from './auth' // your existing authorization

export const mastra = new Mastra({
  server: {
    apiRoutes: [...KNOWLEDGE_ROUTES],
    auth: {
      // authenticateToken, ...
      authorize: async (path, method, user, context) => {
        if (path.startsWith('/api/knowledge')) {
          context
            .get('requestContext')
            .set(
              MASTRA_KNOWLEDGE_PRINCIPALS_KEY,
              user.isAdmin ? 'all' : [`org:${user.orgId}`, `team:${user.orgId}:${user.teamId}`],
            )
          return true
        }
        return appAuthorize(path, method, user, context)
      },
    },
  },
})
```

如使用不同的前綴，請在 `authorize` 內相應修改對 `/api/knowledge` 的檢查，否則不會設定該鍵，路由會傳回 `403`。

`authorize` 函數會取代伺服器對所有路由的規則和角色檢查，因此其他路徑應沿用應用程式原有的判斷，如上例所示。若全部傳回 `true`，任何已登入用戶都可呼叫任何路由。

將值設為範圍陣列；如用戶應可查看整個實例，則設為 `'all'`。空陣列代表無法讀取任何內容。其他值會傳回甚麼，請參閱 [Knowledge 存取及錯誤](/reference/server/routes#knowledge-access-and-errors)。如已設定 `studio.auth`，Studio 請求會使用它，而不用 `server.auth`，所以要在前者的 `authorize` 設定該鍵。

### 設有 `authorizeUser` 的 Provider {/* #providers-with-authorizeuser */}

如果身分驗證 Provider 定義了 `authorizeUser`，伺服器便不會呼叫 `authorize`。這包括任何實作該方法的 `MastraAuthProvider` 子類別，以及所有 `CompositeAuth`。使用此類 Provider 時，請改在[伺服器中介軟件](/docs/server/middleware)設定該鍵：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { KNOWLEDGE_ROUTES, MASTRA_KNOWLEDGE_PRINCIPALS_KEY } from '@mastra/server/server-adapter'
import { auth, getSessionUser } from './auth' // your provider and session lookup

export const mastra = new Mastra({
  server: {
    apiRoutes: [...KNOWLEDGE_ROUTES],
    auth,
    middleware: [
      {
        path: '/api/knowledge/*',
        handler: async (c, next) => {
          const user = await getSessionUser(c.req.raw)
          if (user) {
            c.get('requestContext').set(
              MASTRA_KNOWLEDGE_PRINCIPALS_KEY,
              user.isAdmin ? 'all' : [`org:${user.orgId}`, `team:${user.orgId}:${user.teamId}`],
            )
          }
          await next()
        },
      },
    ],
  },
})
```

伺服器中介軟件先於路由的身分驗證執行，此時請求上下文尚未有已登入用戶。請參照上例，使用應用程式自己的工作階段檢查，從請求找出用戶。路由其後仍會驗證身分，拒絕 Provider 不接受的呼叫者。若改用其他前綴，請更新中介軟件的 `path`。

### 部署須知 {/* #deployment-notes */}

- **沒有 RBAC Provider：**系統會略過 `knowledge:read` 檢查。已通過身分驗證並設有存取主體對應的用戶，可在所有實例讀取這些主體有權存取的頁面。
- **設有 FGA Provider：**每個 Knowledge 實例都會各自檢查 `knowledge:read`，用戶只可查看你授權的實例。詳見 [Knowledge 存取及錯誤](/reference/server/routes#knowledge-access-and-errors)。
- **NestJS：**NestJS 適配器暫未提供 Knowledge 路由。

## 建立自訂檢視 {/* #build-your-own-view */}

要在應用程式顯示 Knowledge 的改動，可透過 [`knowledge.onChange()`](/reference/knowledge/knowledge-class#onchange) 訂閱。事件只包含 ID，沒有內容。向用戶顯示頁面前，請按其範圍重新讀取該頁。收到 `page` 的 `delete` 事件後已不能再讀取該頁，因此要從檢視移除。若收到 `page` 的 `merge` 事件，`pageId` 指的是合併目標，也要移除 `sourceId` 指向的被合併頁面。`scope` 事件只會就新範圍發送，不會就其下層範圍或範本頁面另行發送；要找出這些內容，請重新列出該範圍內的項目。
