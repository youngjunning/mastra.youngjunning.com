# 後台任務

**新增於：** `@mastra/core@1.29.0`

後台任務讓 Agent 分派耗時的 Tool 調用，而不阻塞 Agent 循環。Tool 會立即傳回確認，LLM 則繼續產生回應；任務隨後在後台運行至完成。完成後，結果會寫入 memory，Agent 再執行一個後續回合報告結果。使用 [`untilIdle`](/reference/streaming/agents/stream) 時，該回合會在同一次調用中繼續串流輸出；否則，Agent 會在線程上收到通知，詳見[串流結束後報告結果](#report-a-result-after-the-stream-ends)。

## 何時使用後台任務 {/* #when-to-use-background-tasks */}

如果 Tool 調用可能耗時較長，不適合讓用戶等到它完成才看到回應，就可以使用後台任務。常見場景包括：

- 將需要多步研究或寫作的工作委派給子 Agent。
- 調用回應較慢的外部服務、隊列，或處理大型數據任務。
- 從 Tool 調用觸發可能需要數分鐘才能完成的 Workflow。

對於能快速傳回的 Tool 調用，使用 `agent.stream()` 或 `agent.generate()` 在前台執行更簡單。

:::note

後台任務要求 Mastra 實例已配置 [storage](/docs/storage) 後端。任務會持久化，因此進程重啟後仍可繼續。

:::

## 快速入門 {/* #quickstart */}

後台任務預設關閉。可在 Mastra 實例上設置 `backgroundTasks.enabled` 來啟用：

```typescript title="src/mastra/index.ts" {6-12}
import { Mastra } from '@mastra/core'
import { LibSQLStore } from '@mastra/libsql'

export const mastra = new Mastra({
  storage: new LibSQLStore({ id: 'storage', url: 'file:mastra.db' }),
  backgroundTasks: {
    enabled: true,
    globalConcurrency: 10,
    perAgentConcurrency: 5,
    backpressure: 'queue',
    defaultTimeoutMs: 300_000,
  },
})
```

完整選項見 [backgroundTasks 配置參考](/reference/configuration#backgroundtasks)。

## 在後台運行 Tool {/* #run-a-tool-in-the-background */}

僅啟用管理器不會自動讓任何調用在後台運行。可以在以下兩個層級聲明 Tool 有資格在後台執行：

1. **Tool 級配置**：由 Tool 自身聲明。
1. **Agent 級配置**：由 Agent 指定其哪些 Tool 可在後台執行。

符合條件的 Tool 預設使用 `deferred` 執行方式。如果只想讓 LLM 可以選擇後台運行，而不將其設為預設行為，可在任一層級設置 `defaultDisposition: 'foreground'`。LLM 可在某次 Tool 調用的參數中加入 `_background` 欄位，選擇 `foreground`、`deferred` 或 `awaited`，也可覆蓋該次調用的逾時與重試設置。

### Tool 級配置 {/* #tool-level */}

在 Tool 定義中設置 `background.enabled: true`。啟用管理器的 Agent 調用此類 Tool 時，才可在後台執行。除非該次調用通過 `_background` 覆蓋設置，否則配置的預設執行方式決定它是同步執行還是在後台執行。

```typescript title="src/mastra/tools/research.ts"
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

export const researchTool = createTool({
  id: 'research',
  description: 'Run a long research job',
  inputSchema: z.object({ topic: z.string() }),
  // highlight-start
  background: {
    enabled: true,
    defaultDisposition: 'deferred',
    timeoutMs: 600_000,
    maxRetries: 1,
  },
  // highlight-end
  execute: async ({ topic }) => {
    // Run the research job for topic
  },
})
```

### Agent 級配置 {/* #agent-level */}

在 Agent 上使用 `backgroundTasks.tools`，可啟用指定 Tool、覆蓋單個 Tool 的逾時設置，或讓所有符合條件的 Tool 在後台執行。使用 `disabled: true` 可完全關閉該 Agent 的後台分派。

```typescript title="src/mastra/agents/researcher.ts"
import { Agent } from '@mastra/core/agent'

export const researcher = new Agent({
  id: 'researcher',
  instructions: 'You research topics and answer questions.',
  model: '__GATEWAY_OPENAI_MODEL__',
  tools: { researchTool, summarizeTool },
  // highlight-start
  backgroundTasks: {
    tools: {
      researchTool: { enabled: true, timeoutMs: 600_000 },
      summarizeTool: false,
    },
  },
  // highlight-end
})
```

設置 `tools: 'all'`，即可啟用 Agent 擁有的所有 Tool。

### LLM 逐次調用覆蓋 {/* #llm-per-call-override */}

當 Tool 註冊到已啟用後台任務的 Agent 上時，模型可以在 Tool 參數中加入 `_background` 欄位，覆蓋該次調用解析後的配置。模型只需提供要覆蓋的欄位；`_background` 中的所有欄位都是可選的。Tool 執行前，該覆蓋欄位會從參數中移除。

```json
{
  "topic": "solana",
  "_background": { "disposition": "awaited", "timeoutMs": 900000 }
}
```

可用的執行方式如下：

- `foreground`：同步執行 Tool，不發送後台任務生命週期訊號。
- `deferred`：分派 Tool 後讓 Agent 繼續執行。任務仍關聯到該次運行；使用 `untilIdle` 的串流會等待任務結果完成協調。
- `awaited`：通過後台任務管理器分派 Tool，但當前分支會等待其權威結果完成協調。

為兼容舊用法，`_background.enabled: true` 對應 `deferred`，`_background.enabled: false` 對應 `foreground`。顯式設置的 `disposition` 優先於 `enabled`。

`_background` 只能_修改_開發者已在 Tool 或 Agent 層級啟用的 Tool。若未啟用，模型選擇的後台執行方式會被忽略，Tool 仍在前台執行。這可避免計算器、查詢、Schema 校驗器等應確定性地在前台執行的 Tool 被悄然分派為後台任務。

### 配置解析順序 {/* #resolution-order */}

分派 Tool 調用時，Agent 級和 Tool 級設置決定它是否符合條件，以及各項回退值。對於符合條件的 Tool，LLM 提供的 `_background` 欄位覆蓋該次調用相應的值；未設置的逾時和重試值由管理器預設值補足。`_background` 不能啟用原本不符合條件的 Tool。

逾時值 `0` 表示不設逾時。希望任務一直運行到完成或被取消時，可在 Tool 或 Agent 的 Tool 配置中設置 `timeoutMs: 0`，或在管理器上設置 `defaultTimeoutMs: 0`。

如果 Agent 設置了 `backgroundTasks.disabled: true`，無論上述層級如何配置，所有 Tool 調用都會同步執行。

## 後台任務相關的串流數據塊 {/* #background-tasks-related-stream-chunks */}

Tool 調用被分派為後台任務時，有兩種串流可能提供其生命週期事件：Agent 自身的串流，以及 [`backgroundTaskManager.stream()`](/docs/harness/background-tasks#subscribe-to-all-task-events) SSE 串流。兩者涵蓋的數據塊類型不同：

| 數據塊類型 | 觸發時機 | 發送方 |
| - | - | - |
| `background-task-started` | 任務入隊並獲得 `taskId` 時。 | Agent 串流 |
| `background-task-running` | Worker 領取任務並開始執行時。 | 管理器串流 |
| `background-task-progress` | 顯示正在運行的後台任務數量時。 | Agent 串流 |
| `background-task-output` | 任務的 `execute` 輸出一個串流數據塊時。 | 管理器串流 |
| `background-task-completed` | 任務成功完成時。`payload.result` 與最終的 Tool 結果一致。 | 管理器串流 |
| `background-task-failed` | 任務拋出異常或逾時時。 | 管理器串流 |
| `background-task-cancelled` | 任務在完成前被取消時。 | 管理器串流 |
| `background-task-suspended` | Tool 在 execute 中調用 `suspend()` 時。 | 管理器串流 |
| `background-task-resumed` | 掛起的任務通過 `manager.resume(taskId, resumeData)` 恢復時。 | 管理器串流 |

單獨使用 `agent.stream().fullStream` 時，它只發送 Agent 循環的數據塊（`background-task-started`、`background-task-progress`）。使用 `untilIdle: true` 的 `agent.stream()` 也會發送這兩種數據塊，並訂閱該次運行的 memory 範圍內的管理器 pubsub，將管理器的七種數據塊（`background-task-running`、`background-task-output`、`background-task-completed`、`background-task-failed`、`background-task-cancelled`、`background-task-suspended`、`background-task-resumed`）匯入同一個 `fullStream`。

`backgroundTaskManager.stream()` 只發送管理器的七種數據塊。

完整的 payload 結構見[後台任務數據塊參考](/reference/streaming/ChunkType#background-task-chunks)。

## 使用 `untilIdle` 保持 Agent 串流打開 {/* #keep-the-agent-stream-open-with-untilidle */}

即使後台任務仍在運行，LLM 發出最終回應後，`agent.stream()` 也會傳回。傳入 `untilIdle: true` 可讓串流持續打開，直到所有已分派的後台任務完成，且 LLM 有機會回應其結果：

```typescript title="src/mastra/run.ts"
const stream = await agent.stream('Research solana for me', {
  memory: { thread: 't1', resource: 'u1' },
  untilIdle: true,
})

for await (const chunk of stream.fullStream) {
  // chunks from the initial turn AND any continuation turns triggered by
  // background task completions flow through here
}
```

後台任務完成後，結果會寫入 Agent memory，`stream()` 會重新進入 Agent 循環，讓 LLM 對結果作出回應。沒有運行中的任務或待處理的完成結果時，串流會關閉。

若要自定義空閒逾時，可傳入對象而非 `true`。計時器只在包裝器等待兩輪之間運行，因此首個 token 生成較慢不會關閉串流。預設值為 5 分鐘：

```typescript
const stream = await agent.stream('Research solana for me', {
  memory: { thread: 't1', resource: 'u1' },
  untilIdle: { maxIdleMs: 30_000 },
})
```

完整 API 見 [`Agent.stream()`](/reference/streaming/agents/stream)。

若要修改每次 `untilIdle: true` 調用的預設值，包括 Mastra 內部發起的調用，可在 Mastra 的 `backgroundTasks` 配置中設置 `untilIdleMaxIdleMs`。應將其設為長於最慢後台任務的耗時，使任務完成後仍能觸發後續輪次。單次調用的 `maxIdleMs` 仍優先：

```typescript
export const mastra = new Mastra({
  backgroundTasks: {
    enabled: true,
    untilIdleMaxIdleMs: 30 * 60_000,
  },
})
```

### 串流結束後報告結果 {/* #report-a-result-after-the-stream-ends */}

當 deferred 任務完成，而其線程上沒有開啟的 `untilIdle` 串流時，Mastra 會向 Agent 發送 `notification` 訊號，標籤為 `background-task`。訊號會指明 Tool 調用和任務，並告知 Agent 結果已附在 Tool 調用上；它不會把結果複製進 prompt。這適用於未使用 `untilIdle` 的 `stream()` 調用、客戶端斷線，以及任務[暫停](#suspending-and-resuming)後再恢復的情況。

- 如果線程空閒，訊號會喚醒 Agent，讓它在線程中運行一輪並報告結果。喚醒後的運行會沿用分派任務時的 request context，因此從中解析出的模型、指令和 memory 保持一致。即使接管線程的 Agent 運行在另一台伺服器上，也會隨訊號傳遞該 context，但不包含認證 token、已登入用戶，以及無法序列化為 JSON 或體積過大的值。該伺服器上的運行使用它自己的認證 token 和用戶。
- 如果線程上已有運行，包括分派該任務的運行，訊號會送到該運行的下一次模型請求。如果該運行在再次請求前結束，訊號會單獨啟動一輪。
- 如果另一 Agent 的運行佔用線程，例如正在等待 Tool 審批，訊號會等待；該運行結束後再喚醒原 Agent。
- 如果線程上有打開的 `untilIdle` 串流，則不會發送訊號，因為該串流會自行運行後續輪次。
- 如果調用方取消或中止正在等待任務的 `untilIdle` 串流，也不會發送訊號：停止該串流表示調用方不希望這項工作再傳回回應。任務先掛起、之後才收到回覆的情況不在此列，因為任務掛起時串流已停止等待。

由訊號在空閒線程上啟動的運行（例如通過 `agent.sendSignal()` 發送的消息）會保持打開，直到它分派的任務完成，並自行報告結果。若希望喚醒的運行在本輪結束後就關閉，可設置臨時選項 `wokenRunsEndAfterTurn`；其任務完成後會再通過此訊號報告：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  backgroundTasks: {
    enabled: true,
    wokenRunsEndAfterTurn: true,
  },
})
```

訊號自身的 `ifIdle.streamOptions.untilIdle` 設置雙向優先於該選項。在下一大版本中，喚醒後的運行只會在本輪結束後關閉，`wokenRunsEndAfterTurn` 將被移除。屆時若要讓喚醒的運行保持打開，可在 `ifIdle.streamOptions` 中傳入 `untilIdle: true`。Agent controller 會話和 channels 已經這樣做。

如果同時使用 `wokenRunsEndAfterTurn` 和 `notifyAgentOnFinish: false`，喚醒後的運行分派的任務將無人報告；應用必須自行發送完成訊號。

如果應用會自行發送完成訊號，例如從 `onTaskComplete` 發出，請在 Mastra 的 `backgroundTasks` 配置中設置 `notifyAgentOnFinish: false`，以免 Agent 收到兩次通知：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  backgroundTasks: {
    enabled: true,
    notifyAgentOnFinish: false,
    onTaskComplete: async task => {
      // Send your own notification to task.threadId
    },
  },
})
```

訊號需要帶線程和 resource 的 memory。缺少它們時，分派的任務只會把結果寫入任務記錄。awaited 任務不會發送訊號，因為分派它的運行會等待結果。

### 聚合屬性 {/* #aggregate-properties */}

使用 `untilIdle` 的 `stream()` 傳回的 `MastraModelOutput` 看起來與普通 `stream()` 調用相同，但只有 `fullStream` 覆蓋初始輪次和所有自動後續輪次。聚合屬性（`text`、`toolCalls`、`toolResults`、`finishReason`、`messageList`、`getFullOutput()`）仍僅解析**首輪**的內部緩衝區。若需要跨後續輪次的聚合視圖，請自行消費並匯總 `fullStream`。

## 在後台運行子 Agent {/* #subagents-in-the-background */}

子 Agent 調用在底層以 Tool 調用方式分派，因此適用相同的後台配置。建議在 supervisor 上逐個啟用子 Agent：這樣配置更清晰，也便於集中為每個子 Agent 調整 `timeoutMs`：

```typescript title="src/mastra/agents/supervisor.ts"
import { Agent } from '@mastra/core/agent'

const supervisor = new Agent({
  id: 'supervisor',
  instructions: 'Coordinate research and writing using the available agents.',
  model: '__GATEWAY_OPENAI_MODEL__',
  agents: { researchAgent, writingAgent },
  // highlight-start
  backgroundTasks: {
    tools: {
      researchAgent: { enabled: true, timeoutMs: 900_000 },
      writingAgent: { enabled: true, timeoutMs: 900_000 },
    },
  },
  // highlight-end
})

const stream = await supervisor.stream('Research AI in education and write an article', {
  memory: { thread: 't1', resource: 'u1' },
  untilIdle: true,
})
```

### 繼承子 Agent 的配置 {/* #inheriting-from-the-subagent */}

如果 supervisor 的 `backgroundTasks.tools` 未列出某個子 Agent，但該子 Agent 自身有符合後台執行條件的 Tool（通過 Tool 級 `background.enabled: true` 或自身的 `backgroundTasks.tools` 配置），框架仍會把整個子 Agent 調用分派為後台任務。supervisor 會繼承子 Agent 的意圖：子 Agent 本身成為後台任務，並可在自身循環中後台執行符合條件的普通 Tool。更深一層的 Agent 委派調用則在前台執行。

繼承式分派使用的後台配置（例如 `waitTimeoutMs`）來自子 Agent 自身的 `backgroundTasks` 配置。

```typescript title="src/mastra/agents/researcher.ts"
import { Agent } from '@mastra/core/agent'

const researchAgent = new Agent({
  id: 'research-agent',
  description: 'Gathers factual information.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  tools: { deepResearchTool },
  // highlight-start
  backgroundTasks: {
    tools: {
      deepResearchTool: { enabled: true, timeoutMs: 600_000 },
    },
    waitTimeoutMs: 900_000,
  },
  // highlight-end
})
```

若 supervisor 未為 `researchAgent` 配置後台任務，卻委派了這個 `researchAgent`，仍會把整個 `researchAgent` 調用分派為後台任務。

Mastra 在一次委派運行中支援一層嵌套的後台 Tool：根 Agent 可委派給子 Agent，子 Agent 可在自身循環中後台分派符合條件的普通 Tool。第二層 Agent 委派仍在前台運行，且不會獲得嵌套後台執行的指引。此限制只作用於該次執行，不會改變共享的子 Agent 配置。

選擇在哪個層級配置，取決於一致性應由誰負責：子 Agent 級配置會隨子 Agent 一起使用，使其在不同 supervisor 下保持相同的後台行為；supervisor 側啟用則可集中調整。該邊界止於一層嵌套，且不支援 Workflow 集成。

## 掛起與恢復 {/* #suspending-and-resuming */}

後台任務可以在執行途中暫停，等待外部訊號後繼續。這適用於人工審批、webhook，以及下一步依賴後續數據的串流程。

Tool 在其 `execute` 內調用 `suspend(data)` 後，會：

- 將 `status: 'suspended'` 和 `data` payload 持久化到任務記錄。
- 保存 Workflow 快照，使運行能夠跨進程重啟繼續。
- 在管理器串流中發送 `background-task-suspended` 數據塊。
- 釋放併發執行槽位，供其他任務使用。

使用 `mastra.backgroundTaskManager.resume(taskId, resumeData)` 恢復任務。恢復運行時，Tool 的 `execute` 選項會收到 `resumeData`，任務狀態轉回 `running`。

```typescript title="src/mastra/tools/approval.ts"
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

export const reviewTool = createTool({
  id: 'review',
  description: 'Submit a draft for human review.',
  inputSchema: z.object({ draft: z.string() }),
  outputSchema: z.object({ approvedBy: z.string(), edits: z.string().optional() }),
  background: { enabled: true },
  execute: async ({ draft }, context) => {
    const { suspend, resumeData } = context.agent
    if (!resumeData) {
      await suspend?.({ awaiting: 'approval', draft })
      return { approvedBy: '', edits: undefined }
    }
    const { reviewer, edits } = resumeData as { reviewer: string; edits?: string }
    return { approvedBy: reviewer, edits }
  },
})
```

首次調用 `execute` 時，`resumeData === undefined`，因此會調用 `suspend`。任務恢復後，運行時會帶著 `resumeData` 重新執行 Tool；此時 `if` 條件不成立，Tool 傳回真正的結果。

審批到達後，可這樣恢復任務：

```typescript title="src/server/approvals.ts"
await mastra.backgroundTaskManager?.resume(taskId, {
  reviewer: 'alice@example.com',
  edits: 'Reworded paragraph 3.',
})
```

恢復運行時，`context.agent.suspendPayload` 保存了 Tool 掛起時傳入的 `data`。可以用它判斷回覆對應哪個請求，而不必把該信息編碼進 `resumeData`。

### 從客戶端回覆掛起的任務 {/* #answer-a-suspended-task-from-a-client */}

Agent 的後台 Tool 調用掛起期間，承載該調用的 assistant 消息會在 `metadata.suspendedTools[toolCallId]` 中記錄未完成的請求。該條目包含 `toolName`、`args`、`suspendPayload`、`taskId`、`runId` 和 `suspendedAt`，因此聊天界面重新加載線程後仍可展示請求。任務恢復或取消時，該條目會被移除。

該條目由分派 Tool 調用的進程寫入；同一進程也負責將任務結果寫入線程。若重啟後由 Worker 接手任務，原進程已不存在，未完成的請求和結果都不會到達線程。

要通過 HTTP 回覆請求，請調用 `POST /api/background-tasks/:backgroundTaskId/resume`，將回覆放在 `resumeData` 中。[客戶端 SDK](/reference/client-js/mastra-client) 將此路由封裝為 `resumeBackgroundTask()`：

```typescript title="src/client/answer-request.ts"
import { MastraClient } from '@mastra/client-js'

const client = new MastraClient({ baseUrl: 'http://localhost:4111' })

const task = await client.getBackgroundTask(taskId)
await client.resumeBackgroundTask(
  taskId,
  { reviewer: 'alice@example.com' },
  { suspendedAt: task.suspendedAt },
)
```

傳入從任務或 `suspendedTools` 條目讀取的 `suspendedAt`。若任務此後已恢復或再次掛起，伺服器會傳回 `409 Conflict`，避免送達過期回覆。任務未掛起或沒有空閒併發槽位時，路由也會傳回 `409`；任務不存在或屬於其他 resource 時傳回 `404`。調用該路由需要 `background-tasks:execute` 權限。

### 沒有空閒槽位時恢復任務 {/* #resume-when-no-slot-is-free */}

預設情況下，所有併發槽位都被佔用時，`resume()` 會拋出 `Concurrency limit reached`。傳入 `{ onNoSlot: 'queue' }` 可將恢復操作排隊：

```typescript
const task = await mastra.backgroundTaskManager?.resume(taskId, resumeData, { onNoSlot: 'queue' })
// task.status is still 'suspended' until a slot frees up
```

任務會保持 `suspended`，直到有槽位空出，再帶著排隊的 `resumeData` 恢復。取消任務會丟棄排隊的恢復操作。

隊列存在於調用 `resume()` 的進程記憶體中。如果該進程在恢復操作執行前退出，任務會保持 `suspended`，`resumeData` 也會丟失。要跨重啟保留回覆，請自行持久化恢複數據，並再次調用 `resume()`。

### 對 Agent 循環的影響 {/* #what-happens-to-the-agent-loop */}

在啟用 `untilIdle` 的 `stream()` 中，如果任務中途掛起，包裝器會將其視為本輪的終止狀態並關閉串流。取得恢復 payload 後，調用 `agent.resumeStream(resumeData, { runId, toolCallId, memory, untilIdle: true })` 可立即繼續。恢復的後台任務完成後，其結果會先加入消息列表，然後 Agent 在同一 SSE 連接上運行後續輪次。若要帶外恢復，可直接調用 `mastra.backgroundTaskManager.resume(taskId, resumeData)`，或使用[恢復路由](#answer-a-suspended-task-from-a-client)。任務完成後，結果會寫入線程，Agent 會[被喚醒並報告結果](#report-a-result-after-the-stream-ends)。

### 恢復時重新註冊執行器 {/* #re-registering-the-executor-on-resume */}

管理器將 Tool 執行器保存在進程記憶體中。如果任務掛起期間進程重啟，執行器閉包會丟失；調用 `resume()` 的一方必須先通過 `manager.registerTaskContext(taskId, ...)` 重新註冊。任務在同一進程內分派和恢復時無須執行此步驟。

### 取消掛起的任務 {/* #cancelling-a-suspended-task */}

`manager.cancel(taskId)` 對掛起任務與運行中任務的作用相同：任務記錄改為 `cancelled`，Workflow 快照被清理，隨後觸發 `task.cancelled` 事件。

## 生命週期回調 {/* #lifecycle-callbacks */}

各層級都可以註冊終態回調。這些回調互不替代，並會根據結果觸發成功或失敗 hook：

- Tool 級 `background.onComplete` / `onFailed`：僅作用於該 Tool。
- Agent 級 `backgroundTasks.onTaskComplete` / `onTaskFailed`：作用於該 Agent 分派的所有任務。
- 管理器級 `onTaskComplete` / `onTaskFailed`：全局生效，包括[非 Agent 所有者](#non-agent-owners)創建的任務。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  storage,
  backgroundTasks: {
    enabled: true,
    onTaskComplete: task => {
      logger.info('Background task complete', { taskId: task.id, toolName: task.toolName })
    },
    onTaskFailed: task => {
      logger.error('Background task failed', { taskId: task.id, error: task.error })
    },
  },
})
```

## 串流式事件 {/* #streaming */}

### 訂閱所有任務事件 {/* #subscribe-to-all-task-events */}

傳入 `allResources: true`，可接收系統中所有 resource 的任務事件。連接建立時，串流會先發送當前所有運行中任務的快照，隨後轉發實時事件。

```typescript title="src/mastra/run.ts" oxfmt:false
const bgManager = mastra.backgroundTaskManager;
if (!bgManager) throw new Error('Background tasks are not enabled');

const controller = new AbortController();
const stream = bgManager.stream({ allResources: true, abortSignal: controller.signal });

for await (const chunk of stream) {
  switch (chunk.type) {
    case 'background-task-running':
      console.log('started', chunk.payload.taskId, chunk.payload.toolName);
      break;
    case 'background-task-completed':
      console.log('done', chunk.payload.taskId, chunk.payload.result);
      break;
    case 'background-task-failed':
      console.error('failed', chunk.payload.taskId, chunk.payload.error);
      break;
  }
}
```

串流會保持打開，直到調用方的 `AbortSignal` 觸發。始終傳入 `abortSignal`，以便正常斷開連接。

:::warning

`allResources: true` 會提供每位用戶的任務參數和結果。只能在可信的服務端程式碼中使用，不能用來服務單個用戶的請求。未傳入 `resourceId` 或 `allResources` 時，`stream()` 只會提供沒有 `resourceId` 的任務。使用 memory 分派的 Agent 任務總有 `resourceId`，所以不會出現在該串流中。

:::

### 過濾事件串流 {/* #filter-the-stream */}

可以組合任意過濾選項，縮小接收事件的範圍。過濾條件同時作用於初始快照和實時事件訂閱。

```typescript
const stream = bgManager.stream({
  agentId: 'researcher',
  threadId: 't1',
  resourceId: 'u1',
  abortSignal: controller.signal,
})
```

| 過濾條件 | 說明 |
| - | - |
| `agentId` | 僅包含此 Agent 分派的任務事件 |
| `runId` | 僅包含此次 Agent 運行的事件 |
| `threadId` | 僅包含屬於此 memory 線程的任務事件 |
| `resourceId` | 僅包含屬於此 resource 的任務事件 |
| `taskId` | 僅包含單個任務的事件 |
| `allResources` | 省略 `resourceId` 時，包含所有 resource 的任務。僅限可信服務端程式碼 |
| `abortSignal` | 訊號中止時關閉串流 |

### 直接查詢任務狀態 {/* #look-up-task-state-directly */}

如需單次查詢而非實時串流，可使用 `getTask` 和 `listTasks`：

```typescript
const task = await mastra.backgroundTaskManager?.getTask(taskId)
const { tasks, total } = await mastra.backgroundTaskManager?.listTasks({
  status: 'running',
  agentId: 'researcher',
})
```

它們從 storage 讀取，而非從 pubsub 串流讀取，因此適合分頁列表和詳情視圖。

## 非 Agent 所有者 {/* #non-agent-owners */}

Agent 以外的程式碼也可以通過管理器運行任務。例如，MCP 伺服器可將耗時的 Tool 調用作為後台任務執行。任務的 `agentId` 是其所有者 key；Agent 串流、`untilIdle` 和步驟結束時的等待只會看到 `agentId` 與該 Agent 匹配的任務。請使用 `mcp-server:<serverId>` 這樣的命名空間所有者 key，避免與真正的 Agent ID 衝突。Mastra 不會強制檢查此約定。

非 Agent 所有者通常通過 `registerStaticExecutor()` 註冊靜態執行器，使任意進程都能運行或恢復其任務。還可以設置以下可選任務欄位：

- `expiresAt`：清理操作刪除任務的時間。任務完成、失敗、取消或逾時後，若設置了該欄位，清理會在 `expiresAt` 之後刪除任務，而不使用 `completedTtlMs` 或 `failedTtlMs`。只有設置 `cleanup` 選項後才會執行清理；它不會刪除 pending、running 或 suspended 任務，因此應先取消已過期的工作。所用 storage adapter 還必須支援 `expiresAt`；舊版 adapter 仍使用全局保留設置。
- `metadata`：與任務一同儲存的 JSON。管理器不會讀取它。

```typescript
mastra.backgroundTaskManager?.registerStaticExecutor('mcp-server:ops:deploy', {
  execute: runDeploy,
})

await mastra.backgroundTaskManager?.enqueue({
  agentId: 'mcp-server:ops',
  toolName: 'mcp-server:ops:deploy',
  toolCallId: taskId,
  runId: taskId,
  args,
  resourceId: principalId,
  expiresAt: new Date(Date.now() + 24 * 60 * 60 * 1000),
  metadata: { ttlMs: 86_400_000 },
})
```

使用 `perOwnerConcurrency` 可為所有者單獨設置併發限制，而不使用 `perAgentConcurrency`。其任務仍計入 `globalConcurrency`：

```typescript title="src/mastra/index.ts"
export const mastra = new Mastra({
  storage,
  backgroundTasks: {
    enabled: true,
    globalConcurrency: 60,
    perOwnerConcurrency: { 'mcp-server:ops': 50 },
  },
})
```

已知限制：

- 恢復的任務無法訪問原始請求。請將執行器所需的信息寫入任務本身，例如把主體信息放在 `resourceId`，或把其他 JSON 放在 `metadata`。
- 未固定到 Worker 的 `pending` 任務不持有 lease。啟動時，其他進程可領取並分派它。如果執行器只存在於原進程，任務會因 `No executor registered` 而失敗。在每個進程註冊靜態執行器可避免此問題。若原進程已開始執行工作，可使用 `pinToWorker`。
- Agent 循環在步驟結束時只等待 `running` 任務，不等待 `pending` 任務。[#28228](https://github.com/mastra-ai/mastra/pull/28228) 跟蹤了這一修復。

### 將任務固定到當前 Worker {/* #pin-a-task-to-the-current-worker */}

有時在任務入隊前，相關工作已在當前進程中運行。例如，MCP 伺服器可能在請求中啟動 Tool 調用，只在它耗時過長時才移交給後台任務。將 `pinToWorker: true` 與任務 context 一起傳入，可避免其他進程重復啟動該工作：

```typescript
await mastra.backgroundTaskManager?.enqueue(
  {
    agentId: 'mcp-server:ops',
    toolName: 'mcp-server:ops:deploy',
    toolCallId: taskId,
    runId: taskId,
    args,
  },
  { executor: { execute: adoptRunningDeploy } },
  { pinToWorker: true },
)
```

`pinToWorker` 表示該任務的工作已在當前 Worker 上執行。`pending` 任務會記錄該 Worker 為所有者，並持有執行 lease；等待空閒槽位期間，Worker 會續租。只要 lease 有效，其他進程就不會恢復或分派該任務。

如果 Worker 在任務完成前終止或關閉，這項工作會丟失。恢復機制會把任務視為一次失敗嘗試，與執行中 Worker 終止的任務一樣。若 `retryCount` 低於 `maxRetries`，任務會消耗一次重試機會，在另一 Worker 上運行；該 Worker 需要有靜態執行器。否則任務會因 `Worker process terminated before task completed` 而失敗。設置 `maxRetries: 0` 的任務不會在其他 Worker 上運行。除非 `recoverStaleTasksOnStart` 為 `false`，否則其他進程會在啟動時及之後每隔 `leaseDurationMs` 檢查過期的固定關係。

lease 失效只表示 Worker 不再續租，不代表工作已經停止。如果某個 Worker 的事件循環停頓超過 lease 有效期，另一 Worker 重試任務時，它仍可能在執行。可重試的固定任務應保證冪等，或保護其副作用。

沒有任務 context 時，`pinToWorker` 會拋出異常。未固定的任務（包括所有 Agent 任務）在 `pending` 期間不持有 lease。
