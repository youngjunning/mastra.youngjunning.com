# 持久劑

**添加於：** `@mastra/core@1.45.0`

:::測試版

在 API 穩定之前，可能會在沒有重大版本更新的情況下發生重大變更。

:::

耐用劑包裹常規[`Agent`](/docs/agents/overview) so the agentic loop runs inside a workflow. Events flow through [PubSub](/docs/server/pubsub), which means a client can disconnect and reconnect without missing chunks. The run state is persisted, so it survives process restarts.

## 何時使用持久劑 {/* #when-to-use-durable-agents */}

當出現以下任何情況時，請使用耐用劑：

* 客戶端可能會在中途斷開並重新連接（移動、不穩定的網路、長時間運行的呼叫）。
* Agent循環可能比單一 HTTP 請求的壽命更長（背景研究、多步驟Tool的使用）。
* 您需要一個觀察/重新連接 API，其中第二個客戶端可以獲得第一個客戶端啟動的流。
* 你想要[Inngest-powered execution](/integrations/deploy/inngest) with step memoization, retries, and monitoring.

對於客戶端保持連線的短期、請求範圍的調用，常規`Agent` with `stream()` or `generate()` is simpler.

## 快速入門 {/* #quickstart */}

`createDurableAgent()` from `@mastra/core/agent/durable`:

```typescript title="src/mastra/agents/researcher.ts"
import { Agent } from '@mastra/core/agent'
import { createDurableAgent } from '@mastra/core/agent/durable'

const agent = new Agent({
  id: 'researcher',
  name: 'Researcher',
  instructions: 'You research topics thoroughly.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

export const durableResearcher = createDurableAgent({ agent })
```

向 Mastra 註冊持久Agent並致電`stream()`:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { durableResearcher } from './agents/researcher'

const mastra = new Mastra({
  agents: { durableResearcher },
})

const { output, runId, cleanup } = await durableResearcher.stream(
  'Research quantum computing advances in 2025',
)

for await (const chunk of output.fullStream) {
  // Process each chunk as it arrives
}

// Release PubSub subscriptions and clear the run from the registry.
// If you skip this, an automatic cleanup timer fires after the stream ends.
cleanup()
```

返回的`runId` identifies the execution. Pass it to `observe()` to reconnect from a different client. Visit the [DurableAgent reference](/reference/agents/durable-agent) for the full configuration and method API.

## 它是如何運作的 {/* #how-it-works */}

耐用劑在常規劑的基礎上添加了三層：

1. **Workflow執行**: `stream()` serializes the messages and options into a workflow input, then triggers the agentic loop inside a durable workflow. The workflow runs the same loop as `Agent.stream()` but each step can be memoized and replayed.

2. **發布訂閱串流媒體**：循環將區塊發佈到由運行 ID 鍵入的 PubSub 主題。呼叫者訂閱該主題並將區塊傳輸到`ReadableStream`, while the cache replays any chunks missed during a disconnect.

3. **快取層**：可選的快取（預設在記憶體中，Redis 或生產中的其他後端）儲存已發布的事件，以便遲到的訂閱者可以趕上。

## 執行變體 {/* #execution-variants */}

Mastra 提供了三種生產持久劑的工廠功能。它們的不同之處在於Workflow的執行方式：

|工廠|套餐 |最適合 |
| - | - | - |
|`createDurableAgent()` | `@mastra/core` | Local development and single-process servers. You get a stream you can await directly. |
| `createEventedAgent()` | `@mastra/core` | Background execution. The workflow starts without blocking, and you consume chunks through PubSub. |
| `createInngestAgent()` | `@mastra/inngest` | Production deployments. Inngest adds step memoization, retries, and a monitoring dashboard. |

所有三個都傳回您註冊的對象`Mastra` the same way as a regular agent. `createDurableAgent()` and `createEventedAgent()` return class instances that extend `Agent`. `createInngestAgent()` returns a Proxy-backed object that forwards `Agent` methods to the underlying agent. When a signal wakes an idle thread, all three start that run with the durable `stream()`. `sendSignal()` and `sendNotificationSignal()` both work this way.

### `createDurableAgent()` {/* #in-process-with-createdurableagent */}

`stream()`. You get a `DurableAgentStreamResult` back in the same process. No external infrastructure is required, so this is the fastest way to get started:

```typescript title="src/mastra/agents/durable.ts"
import { Agent } from '@mastra/core/agent'
import { createDurableAgent } from '@mastra/core/agent/durable'

const agent = new Agent({
  id: 'helper',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

export const durableHelper = createDurableAgent({ agent })
```

### 一勞永逸`createEventedAgent()` {/* #fire-and-forget-with-createeventedagent */}

Workflow在背景啟動，不會阻塞呼叫者。您仍然透過 PubSub 接收區塊，所以`stream()` returns a result you can consume. The HTTP handler that triggered the run doesn't need to wait for the workflow to finish:

```typescript title="src/mastra/agents/evented.ts"
import { Agent } from '@mastra/core/agent'
import { createEventedAgent } from '@mastra/core/agent/durable'

const agent = new Agent({
  id: 'writer',
  instructions: 'You write articles.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

export const eventedWriter = createEventedAgent({ agent })
```

### 儲存Agent程式的可恢復流 {/* #resumable-streams-for-stored-agents */}

創建的Agent[`createStoredAgent()`](/reference/client-js/agents#createstoredagent) use the `durable` field to configure resumable streams only. The server hydrates a plain `Agent` with stream publishing and replay enabled:

```typescript
await mastraClient.createStoredAgent({
  id: 'helper',
  name: 'Helper',
  instructions: 'You are a helpful assistant.',
  model: { provider: 'openai', name: '__AI_SDK_OPENAI_MODEL_BASE__' },
  durable: true,
})
```

`durable`也接受`{ cleanupTimeoutMs }`. Cache and pubsub are inherited from the server's `Mastra` instance. Existing stored agents with `durable: true` now load with resumable streams but without durable execution or checkpoint recovery. To retain durable execution, define a code agent wrapped with `createDurableAgent({ agent })` and pass `maxSteps` and snapshot persistence options to the factory.

### Ingest 提供動力`createInngestAgent()` {/* #inngest-powered-with-createinngestagent */}

在上運行Workflow[Inngest](https://www.inngest.com/docs) platform. Each tool call becomes a memoized step that Inngest can retry independently, and you get a dashboard for monitoring runs:

```typescript title="src/mastra/agents/inngest.ts"
import { Agent } from '@mastra/core/agent'
import { createInngestAgent } from '@mastra/inngest'
import { Inngest } from 'inngest'

const inngest = new Inngest({ id: 'my-app' })

const agent = new Agent({
  id: 'analyst',
  instructions: 'You analyze data.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

export const inngestAnalyst = createInngestAgent({ agent, inngest })
```

參觀[`createInngestAgent()` reference](/reference/agents/inngest-agent) for the full API, including Inngest-specific options like PubSub and cache configuration.

## 可恢復的串流 {/* #resumable-streams */}

持久性Agent透過 PubSub 和事件快取支援可恢復流。當客戶端在中途斷開連線時，快取會繼續儲存事件。同一個客戶端可以透過呼叫重新連接`observe()` with the `runId`:

```typescript title="src/server/reconnect.ts"
const { output } = await durableResearcher.observe(runId)

for await (const chunk of output.fullStream) {
  // Chunks from the run, including any missed while disconnected
}
```

呼喚`observe(runId)` without an offset is the supported general reconnect flow. It replays all available cached events before delivering live events. For a completed run, observation replays the retained events and closes. If the run is unknown or its history has been cleared and no live run remains, observation closes without events. The HTTP observe endpoint returns 404 in this case, because it can't check that the caller owns the run.

可選的`offset` is a run-log position, which chunks report as `chunk.index`. To resume after a dropped connection, pass `index + 1` of the last chunk that has an `index`, or omit `offset` if nothing arrived. This works the same with `stream()` and `observe()`, over HTTP, and in `@mastra/client-js`. See [`observe(runId, options?)`](/reference/agents/durable-agent#observerunid-options) for which chunks carry no index, structured output, and transport limits.

重播不是永久的執行存檔。活動僅持續到[cleanup](#cleanup) clears them or the cache removes them. A workflow snapshot can't reconstruct cleared stream events, and disabling caching prevents historical replay.

觀察並不代表跑步。當循環結束時，或者你提前離開它`break`, `return`, or an error, the observer unsubscribes and the run keeps going for anyone else watching it. To stop observing from outside the loop, for example when the client disconnects, call `detach()`:

```typescript title="src/server/reconnect.ts"
const { output, detach } = await durableResearcher.observe(runId)

request.signal.addEventListener('abort', detach, { once: true })

if (request.signal.aborted) detach()

for await (const chunk of output.fullStream) {
  // Stops when the run finishes or the client disconnects
}
```

如果你通過了`idleTimeoutMs` and no chunks arrive for that long, Mastra checks `isAlive` when you provide it. If `isAlive` returns `true` or throws, the timer restarts and the stream stays open. Otherwise the stream ends with an error chunk and detaches the observer. The run itself is only cleaned up when `isAlive` returns `false`.

`createDurableAgent()`和`createEventedAgent()` use an in-memory cache by default, which means resumable streams work within a single process. For reconnects across processes or replicas, share the replay cache, PubSub transport, and run storage between the producer and observer. A shared transport delivers live events but can't recover events held only in another process's cache. Configure a persistent cache backend (for example, Redis) so retained events survive process restarts:

```typescript title="src/mastra/agents/durable-with-cache.ts" {2,3,5,9}
import { createDurableAgent } from '@mastra/core/agent/durable'
import { RedisServerCache } from '@mastra/redis'
import Redis from 'ioredis'

const cache = new RedisServerCache({ client: new Redis('redis://localhost:6379') })

export const durableAgent = createDurableAgent({
  agent,
  cache,
})
```

`createInngestAgent()`預設情況下不啟用快取。透過一個`cache` option or register the agent with a `Mastra` instance that has a `serverCache` configured to enable resumable streams.

對於快取主題，每個發布的事件在即時交付之前都會記錄在快取中，因此發布延遲受到到快取的往返時間的限制。若快取寫入失敗，事件仍會即時傳送，但無法重播。`@mastra/redis` and `@mastra/valkey` record each event in a single round-trip using a Lua script. `@mastra/redis` falls back to separate commands when the client has no `evalScript` or when Redis Cluster rejects the multi-key script. Per-run workflow watch events (`workflow.events.v2.*`) are never cached. If the cache is remote (for example, in another region) and you don't need to resume a topic, use `shouldCache` to publish that topic straight through:

```typescript title="src/mastra/agents/durable-hot-topics.ts" {5}
export const durableAgent = createDurableAgent({
  agent,
  cache,
  // Skip the replay cache for the per-chunk stream topic; other topics stay resumable.
  shouldCache: topic => !topic.startsWith('agent.stream.'),
})
```

## 使用後台任務進行串流傳輸 {/* #streaming-with-background-tasks */}

持久Agent支援同[`untilIdle`](/reference/streaming/agents/stream) option as regular agents. When `untilIdle` is set, `stream()` keeps the connection open across background-task continuations until the agent is idle:

```typescript title="src/mastra/run.ts"
const { output, cleanup } = await durableAgent.stream('Research and summarize the topic', {
  untilIdle: true,
  memory: { thread: 'thread-1', resource: 'user-1' },
})

for await (const chunk of output.fullStream) {
  // Chunks from the initial turn AND any follow-up turns triggered by
  // background task completions
}

cleanup()
```

經過`{ maxIdleMs }` to customize the idle timeout (defaults to 5 minutes):

```typescript
await durableAgent.stream('Research topic', {
  untilIdle: { maxIdleMs: 30_000 },
  memory: { thread: 'thread-1', resource: 'user-1' },
})
```

訪問[Background tasks](/docs/harness/background-tasks) for the full background task guide, including configuration, subagents, and suspend/resume.

## 清理 {/* #cleanup */}

每一個`stream()` and `observe()` call returns a `cleanup` function that tears the run down: it unsubscribes from PubSub, removes the run from the internal registry, and deletes the run's cached events so nobody can replay it afterward.

當你不打電話的時候`cleanup()` yourself, Mastra calls it `cleanupTimeoutMs` after the run finishes, errors, or is aborted. The default is 30 seconds, so completed-run replay is limited to that window unless you configure a different value or call `cleanup()` sooner. Detaching an observer or reaching a plain `idleTimeoutMs` doesn't start this timer. Set `cleanupTimeoutMs: 0` to turn the timer off. The cache's own TTL and eviction still apply.

稱呼`cleanup()` from the process that started the run. To stop watching a run from `observe()`, use `detach()` or leave the loop instead.

## Tool審批 {/* #tool-approval */}

持久Agent支援Tool批准（人在環）。當Tool呼叫需要批准時，Workflow會暫停，並發出`onSuspended` callback, and waits for the caller to resume with `resume()`:

```typescript title="src/mastra/run.ts" {4}
const { output, runId, cleanup } = await durableAgent.stream('Delete the old records', {
  requireToolApproval: true,
  onSuspended: ({ toolCallId, toolName, args }) => {
    // Notify the user and ask for approval
  },
})
```

批准後恢復暫停運轉：

```typescript
await durableAgent.resume(runId, { approved: true })
```

## 崩潰恢復 {/* #crash-recovery */}

持久Agent可以在執行時將每次運行的狀態檢查點到儲存。如果伺服器進程在運行中崩潰，則運行仍將繼續`running` status in storage with no automatic retry, and on the next server start you can re-drive these orphaned runs so they pick up where they left off. For orderly shutdowns such as rolling deploys, the generated server can also drain in-flight turns before exiting. See [graceful shutdown and rolling deploys](/docs/deployment/mastra-server#graceful-shutdown-and-rolling-deploys).

在預設的持久化策略下，這些`running` checkpoints are written when crash recovery is enabled. With `recovery.durableAgents: 'off'` (the default), durable agents persist snapshots for `pending`, `paused`, and `suspended` runs (the artifacts human-in-the-loop resume depends on) and skip the per-step `running` writes until `mastra.shutdown()` starts. A custom `shouldPersistSnapshot` predicate replaces the default policy: one that includes `running` writes those checkpoints at every step, and one that excludes `running` writes none, including during shutdown. See [snapshot persistence](#snapshot-persistence) for the full policy and how to override it.

持久Agent運行被排除在活動Workflow運行的通用啟動時重新啟動之外。持久Agent运行的唯一自动恢复路径是`recovery.durableAgents: 'auto'`, which claims each orphaned run and registers its thread runtimes before re-driving it. See [run ownership](#run-ownership).

：：：警告

自動和手動恢復從最後一個持久快照繼續運行。結果不在該快照中的任何Tool呼叫都會再次運行。任何未儲存的模型回應都會再次被要求，並且模型提供者會再次計費。在依賴恢復之前使Tool具有冪等性。看[make tools safe to repeat](#make-tools-safe-to-repeat).

:::

每次呼叫傳遞的委託鉤子都是閉包，無法在新進程中恢復。恢復運作後會恢復到預設委派行為。在主管上配置的掛鉤`defaultOptions.delegation` are merged back in when recovery rebuilds the delegation tools. Put hooks that must survive a restart there instead of passing them to `stream()` or `generate()`.

### 快照持久化 {/* #snapshot-persistence */}

這`shouldPersistSnapshot` option on `createDurableAgent()` (also accepted in the agent-level `durable` config) controls which workflow snapshots a durable agent writes. The default policy:

* 始終堅持`pending`, `paused`, and `suspended` snapshots. These are what `resume()` and tool approval read, so human-in-the-loop flows work without configuration.
* 堅持`running` checkpoints at every step when `recovery.durableAgents` is `'auto'`. These per-step writes exist solely to make in-flight runs recoverable after a crash, so with recovery off they're skipped until shutdown.
* 堅持一個`running` checkpoint at each step boundary a run reaches after `mastra.shutdown()` starts, even with recovery off. A run that reaches a step boundary before the drain window ends can then be resumed later with `recover()` or `recoverActiveRuns()`. A run blocked in a single LLM or tool call for the whole drain gets no shutdown checkpoint.

當Agent程式配置有固定記憶體實例時（`memory: new Memory(...)`), a `running` checkpoint doesn't repeat messages memory already stores. Messages recalled from memory and messages the run saved itself (for example with `savePerStep: true`) are stored as small references to their memory rows instead of their full contents, as long as they still match the stored row (a message changed after saving stays inline). This applies to every copy of the conversation a checkpoint holds, including the run input and step results. A long run's checkpoints grow much more slowly as a result. Agents that resolve memory with a function keep the full transcript in each checkpoint, because the memory a resumed run resolves may differ.

保留崩潰恢復檢查點而不啟用自動恢復（例如，當您調用`recoverActiveRuns()` yourself behind a leader election), pass a predicate that includes `running`:

```typescript title="src/mastra/agents/durable.ts"
export const durableResearcher = createDurableAgent({
  agent,
  shouldPersistSnapshot: ({ workflowStatus }) =>
    ['pending', 'paused', 'suspended', 'running'].includes(workflowStatus),
})
```

當自訂謂詞排除時，Mastra 會記錄警告`suspended` or `paused`, which breaks human-in-the-loop resume, or excludes `running` while `recovery.durableAgents` is `'auto'`, which makes the agent invisible to automatic recovery.

事件Agent始終保留完整的快照集：事件引擎透過儲存協調工作人員，因此`running` row is part of its execution model. Inngest agents always persist only `suspended` snapshots, because Inngest's own replay provides durability. Both accept `shouldPersistSnapshot` for API symmetry but log a warning and ignore it.

### 自動恢復 {/* #automatic-recovery */}

放`recovery.durableAgents` to `'auto'` in the Mastra config. The deployer calls `recoverAllDurableAgents()` on boot, alongside the workflow run restarts (the two run concurrently):

```typescript title="src/mastra/index.ts" {7}
import { Mastra } from '@mastra/core'
import { PostgresStore } from '@mastra/pg'

export const mastra = new Mastra({
  agents: { myAgent: durableAgent },
  storage: new PostgresStore({ connectionString: process.env.DATABASE_URL! }),
  recovery: { durableAgents: 'auto' },
})
```

啟動時，這會發現每個已註冊的持久Agent，其運行陷入困境`running` status and re-drives them from the last persisted snapshot.

恢復同時處理最多五個Agent，每個Agent最多有五個運行等待。每次等待都涵蓋`recover()` setup and settlement of the whole recovered workflow and lasts at most 30 seconds. If it expires, the attempt continues in the background and frees a slot for another run. These limits bound waiting, not the number of live executions. Discovery and overridden custom recovery methods aren't bounded by this budget.

超時運行進位`retryAt` and are checked again automatically. Re-checks defer until the original attempt settles, so they don't start duplicate executions. After it settles, recovery checks the persisted snapshot and ownership before retrying. Finished or suspended runs aren't restarted.

關閉開始時，復原會停止分派新的運作和Agent，並取消掛起的重新檢查。原始嘗試（包括那些等待超時的嘗試）仍會被追蹤以查找 Mastra 的共享關閉消耗。復原逾時不會取消執行或新增單獨的排檔視窗。

恢復不會接管另一個執行仍在驅動的運行。一旦執行聲明可能失效，它就會跳過運行並再次檢查它。進程在重新啟動前不久崩潰的運行仍可恢復，無需再次呼叫。

### 手動恢復 {/* #manual-recovery */}

如果您需要更精細的控制，例如按計劃運行恢復，請直接呼叫方法：

```typescript
// Recover all durable agents
const result = await mastra.recoverAllDurableAgents()
console.log(
  `Recovered ${result.recovered} runs (${result.succeeded} ok, ${result.failed} failed, ${result.skipped} skipped)`,
)

// Recover a specific agent
const { recovered } = await durableAgent.recoverActiveRuns()
for (const run of recovered) {
  if (run.status === 'skipped') console.log(`${run.runId} was skipped: ${run.reason}`)
}

// Recover a single known run
await durableAgent.recoverActiveRuns({ runId: 'run-abc-123' })
```

`recoverAllDurableAgents()`返回計數並安排合格的所有權重新檢查。`recoverActiveRuns()` returns each run's outcome as `success`, `failed`, or `skipped`, and doesn't re-check skipped runs. A run skipped because another process drives it carries `retryAt`, the time after which its claim lapses unless renewed. A timed-out attempt instead returns `status: 'skipped'` with `reason: 'recovery-timeout'` and no `retryAt`, so Mastra doesn't automatically retry it. Only the `skipped` count includes this attempt; the `recovered`, `succeeded`, and `failed` counts exclude it even if it settles later.

手動恢復讀取相同`running` checkpoints as automatic recovery. For a `DurableAgent` using the default snapshot policy with `recovery.durableAgents` set to `'off'`, in-flight runs are only checkpointed at step boundaries reached after `mastra.shutdown()` starts. A run that crashes before then, or doesn't reach a step boundary during the drain, has no checkpoint, so `listActiveRuns()` and `recoverActiveRuns()` don't find it. See [snapshot persistence](#snapshot-persistence).

若要接管仍處於活動狀態的運行，例如由暫停執行保持的運行，請呼叫`recover()` with `force: true`:

```typescript
const { output } = await durableAgent.recover('run-abc-123', { force: true })
```

維持運作的執行者失去了其主張。當執行偵測到遺失時，Mastra 請求取消。忽略取消的工作可以繼續。透過儲存支援的聲明，串流會刪除舊聲明產生的事件。看[stop work after ownership loss](#stop-work-after-ownership-loss) for cancellation limits. Without `force`, `recover()` throws `DURABLE_AGENT_RUN_ACTIVE` for a live run. Even with `force`, `recover()` refuses a run that the same process is executing.

### 經營所有權 {/* #run-ownership */}

每一個`stream()`, `generate()`, `resume()`, and `recover()` call claims the run before it executes and renews the claim every 5 seconds. A claim lapses 15 seconds after its last renewal, so a run whose process crashed becomes recoverable within 15 seconds. Until then, recovery treats the run as live, and a `stream()` or `resume()` call for that run waits up to 5 seconds for the claim, then throws `DURABLE_AGENT_EXECUTION_CONFLICT`. `mastra.shutdown()` stops the runs still executing after its drain window without further writes and releases their claims. The next boot then recovers them without waiting for the claims to lapse. Set `MASTRA_AGENT_THREAD_LEASE_TTL_MS` to change the lapse time. Renewal happens every third of it unless `MASTRA_AGENT_THREAD_LEASE_RENEW_INTERVAL_MS` sets an interval shorter than the TTL.

聲明的執行取決於Workflow儲存。當儲存支援運行防護時，聲明是該儲存中的一筆記錄，並且在同一操作中根據聲明檢查每次寫入。一旦另一個執行聲明了該運行，則丟失該運行的執行的寫入將被拒絕。只有當記憶體儲存也支援運行防護時，該執行的訊息、執行緒和工作記憶體寫入才會被拒絕，因此當Agent執行操作時，它們仍然會落地。`Memory` uses a storage adapter without it. These storage adapters support run fencing:

* `InMemoryStore`從`@mastra/core/storage`
* `@mastra/pg`
* `@mastra/libsql`和`@mastra/turso`
* `@mastra/mysql`
* `@mastra/mssql`
* `@mastra/oracledb`
* `@mastra/spanner`
* `@mastra/dsql`
* `@mastra/cloudflare-d1`
* `@mastra/cloudflare`， 和`CloudflareDOStorage`
* `@mastra/convex`
* `@mastra/mongodb`，在副本集或分片集群上
* `@mastra/dynamodb`
* `@mastra/redis`
* `@mastra/upstash`
* `@mastra/valkey`

在 Convex 上，在您部署的 Mastra 伺服器功能中執行防護運行。升級後重新部署您的凸函數`@mastra/convex`. Until you do, durable agent runs fail with an error asking you to redeploy, while other writes keep working.

支援運行圍欄的儲存每次運行都會保留一份聲明記錄，並且每次運行都會使用記憶體保留一份記憶體圍欄記錄。具有保留支援的商店會透過以下方式修剪它們：`workflows.runOwnership` and `memory.runFences` [retention keys](/reference/storage/retention#retention-eligible-tables). Redis, Upstash, and Valkey expire them on their own instead: a claim 7 days after its last claim, renewal, or release, and a fence 7 days after it's retired. A run's first generation comes from the store's clock, so a run that reuses a `runId` after its records were pruned still outranks the fences and stream events of its earlier executions.

對於任何其他Workflow商店，聲明是對[PubSub](/docs/server/pubsub) backend. The lease keeps two executions from claiming the run at once, but writes from an execution that lost the run aren't rejected. A run taken over while its previous execution was still live can end with that execution's output. When an execution loses its lease and no other execution has taken the run, the run stays held for up to 15 more seconds. Until then, `recover()` without `force` throws `DURABLE_AGENT_RUN_ACTIVE` with `retryAt` set to when the hold is sure to have ended. Mastra logs a warning when it recovers runs against a workflows or memory store without run fencing.

租約僅協調共享它的進程。`EventEmitterPubSub`, the default, covers one process. `UnixSocketPubSub` covers the processes on one host. `RedisStreamsPubSub` and `ValkeyStreamsPubSub` cover every instance connected to the same server. `GoogleCloudPubSub` doesn't provide leases, so with a store that lacks run fencing every claim succeeds, and recovery can take over a run that's still live.

### 失去所有權後停止工作 {/* #stop-work-after-ownership-loss */}

`MASTRA_AGENT_THREAD_LEASE_TTL_MS`. Detection depends on backend response time. A step in the process that holds the claim stops when an ownership check fails, or when the claim can't be renewed before it expires. A step that only observes another process's claim also stops when no check succeeds within one lease TTL (15 seconds by default).

取消是合作的。使用Tool執行上下文`abortSignal` for cancellable operations, and check it before starting another side effect. A tool that ignores the signal can keep running. Work already completed outside Mastra isn't rolled back.

恢復可以在上一次執行檢測到所有權丟失之前啟動相同的Tool調用，因此取消可以減少重疊工作，但不會阻止Tool運行兩次。看[make tools safe to repeat](#make-tools-safe-to-repeat).

### 多實例部署 {/* #multi-instance-deployments */}

每個副本都可以從`recovery.durableAgents: 'auto'`. Replicas that boot together race to recover the same orphaned runs, but only one claim succeeds per run and the other replicas skip it. This requires a claim that every replica shares: a workflows store that supports run fencing, or a PubSub backend whose lease every replica shares. Without either, gate recovery behind your own leader election or run it from a single replica.

## 資料庫負載 {/* #database-load */}

Mastra 沒有發布持久Agent的基準硬體參考，因此請根據您自己的工作負載調整資料庫的大小。本節介紹驅動負載的因素以及需要注意的內容。

每個檢查點都會將運行的完整快照更新為 JSONB`mastra_workflow_snapshot`, with one row for the agent workflow and one for its nested execution workflow. The snapshot holds the conversation and every tool result so far, so it grows during a run, and the total bytes a run writes grow faster than its step count. Write load depends on:

* **檢查點頻率**: 一個`createDurableAgent()` agent with `recovery.durableAgents` set to `'off'` (the default) writes few checkpoints. With `'auto'`, it writes a `running` checkpoint at every step. A `createEventedAgent()` agent always writes at every step. See [snapshot persistence](#snapshot-persistence).
* **每次運行的步數和有效負載大小**：Tool傳回的每個位元組都會在執行的每個後續檢查點中再次寫入。
* **並發運行**：負載隨著正在進行的運行次數而增加。

為了減少寫入並保持崩潰恢復：

*
*
* 將長任務分成較短的運行。

每個`PostgresStore` opens up to `max` connections, 20 by default, per process. A `pool`, `writePool`, or separate `readPool` you pass in uses its own limit. Add up the limits of every pool that connects to the server, across all replicas and processes, and keep the total below the server's `max_connections` with room for other clients. If you put a transaction-mode pooler such as PgBouncer in front, budget its server-side connections the same way. See [PostgreSQL](/integrations/databases/postgresql).

每個檢查點更新插入都會留下一個死行版本，Mastra 會刪除已完成運行的行，因此`mastra_workflow_snapshot` collects dead rows fast. Suspended runs keep their rows. If deletion fails, Mastra logs a `Failed to delete workflow snapshot rows` warning and the rows stay until you delete or [prune](/reference/storage/retention) them. The exception is a `createEventedAgent()` agent on a shared pub/sub transport with storage-backed fencing: it logs `durable execution delivery failed` and retries the delete with the event. Pruning removes snapshots by inactivity, including suspended runs and running runs whose step hasn't written a checkpoint recently. Set `workflowSnapshot.maxAge` longer than your longest expected suspension and your longest step, or leave snapshot pruning off if you can't bound them. Make autovacuum more aggressive for this table. Replace `public` with your `schemaName` if you set one:

```sql
ALTER TABLE public.mastra_workflow_snapshot SET (
  autovacuum_vacuum_scale_factor = 0.01,
  toast.autovacuum_vacuum_scale_factor = 0.01
);
```

若要決定是否增加容量或調整工作負載，請觀看：

* `n_dead_tup`和`last_autovacuum` for `mastra_workflow_snapshot` in `pg_stat_user_tables`, and for its TOAST table in `pg_stat_all_tables`, where large snapshots are stored
* 快照更新插入的份額`total_exec_time` and `wal_bytes` in `pg_stat_statements`. This requires `pg_stat_statements` in `shared_preload_libraries` (a server restart) and `CREATE EXTENSION pg_stat_statements`
* 每秒 WAL 位元組數 (`pg_stat_wal`)
* 活動連線數與池中的連線數比較`max`

如果快照更新插入主導寫入，請先減少檢查點大小或頻率。如果許多不相關的查詢速度很慢，請增加容量。

## 讓Tool可以安全重複使用 {/* #make-tools-safe-to-repeat */}

持久Agent或事件Agent可以多次運行相同Tool呼叫。Tool呼叫是模型運行Tool的一個請求。在這些情況下會發生重複：

* 該過程在Tool運行時停止，或在Tool返回之後但在 Mastra 保存其結果之前停止。當跑步是[recovered](#crash-recovery), the tool runs again.
* 使用 Postgres 儲存和 Redis Streams PubSub，事件工作執行緒會在發布Tool結果之前停止。另一名工人[reclaims the step](/reference/pubsub/redis-streams#evented-agent-worker-takeover) and runs the tool again.
* 當先前的執行仍在運行該Tool時，恢復接管運行，例如[`recover()` and `force: true`](#manual-recovery). Both executions can run the tool concurrently. See [stop work after ownership loss](#stop-work-after-ownership-loss).

[攝取Agent](#inngest-powered-with-createinngestagent)配置有`retries` also run an interrupted tool step again.

Mastra 無法撤銷Tool已經在另一個系統中完成的工作。發送電子郵件、向卡片收費或刪除記錄的Tool可以執行兩次。使這些Tool具有冪等性。冪等Tool在同一呼叫第二次運行時不會產生額外效果。

### 使用Tool呼叫 ID 作為冪等鍵 {/* #use-the-tool-call-id-as-an-idempotency-key */}

當Agent程式運行Tool時，`context.agent.toolCallId` identifies the tool call. Mastra saves the model's response before it runs any tool in that response, so a tool that runs again for the same call receives the same `toolCallId`.

將 ID 傳遞給接受冪等性金鑰的服務。該Tool退還 Stripe 付款並將Tool呼叫 ID 作為 Stripe 的[idempotency key](https://docs.stripe.com/api/idempotent_requests). When the tool runs again for the same call, Stripe returns the first refund instead of creating a second one:

```typescript title="src/mastra/tools/refund-payment.ts"
import { createTool } from '@mastra/core/tools'
import Stripe from 'stripe'
import { z } from 'zod'

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!)

export const refundPayment = createTool({
  id: 'refund-payment',
  description: 'Refunds a customer payment',
  inputSchema: z.object({
    paymentIntentId: z.string(),
  }),
  outputSchema: z.object({
    refundId: z.string(),
    status: z.string().nullable(),
  }),
  execute: async ({ paymentIntentId }, context) => {
    const toolCallId = context.agent?.toolCallId
    if (!toolCallId) throw new Error('refund-payment must be called by an agent')

    const refund = await stripe.refunds.create(
      { payment_intent: paymentIntentId },
      { idempotencyKey: `refund-payment:${paymentIntentId}:${toolCallId}` },
    )

    return { refundId: refund.id, status: refund.status }
  },
})
```

`context.agent`僅當Agent執行該Tool時才設置，這就是為什麼範例檢查它的原因。Tool呼叫 ID 來自模型提供者，某些提供者在回應中重複使用 ID。新增付款 ID 可防止兩次不同的退款共享金鑰。 Stripe 可以在冪等金鑰過期 24 小時後將其刪除，因此在此之後恢復的運行可以創建第二次退款。

如果服務不接受冪等金鑰，請以相同的方式建立金鑰並將其與變更一起記錄：

* 在資料庫中，將鍵入與更改相同的事務中具有唯一約束的列，並在鍵已存在時跳過更改，例如`INSERT ... ON CONFLICT DO NOTHING` in Postgres. Store the tool's result with the key so a repeated call can return the same result to the model.
* 對於其他服務，請將金鑰附加到請求並在執行操作之前檢查它，例如透過搜尋標頭中包含金鑰的電子郵件。當執行重疊時，每個執行都可以在另一個發送請求之前通過此檢查。

### 保護子Agent程式內的Tool {/* #protect-tools-inside-subagents */}

一個[subagent](/docs/subagents) delegation is one `agent-<name>` tool call. Recovery doesn't save the model and tool calls inside it, so when the delegation runs again, the subagent starts over and its tools receive new `toolCallId` values. A key built from the tool call ID doesn't detect these repeats.

對於子Agent程式使用的Tool，根據識別預期效果的資料建立金鑰。對於退款，這可以是付款 ID 與Tool輸入中的訂單行 ID 的組合。避免使用也會阻止合法第二個操作的密鑰，例如在允許部分退款時僅根據付款 ID 建立的密鑰。
