# 持久化 Agent

**新增於：** `@mastra/core@1.45.0`

:::beta

在 API 穩定之前，即使不提升主版本號，也可能引入破壞性變更。

:::

持久化 Agent 包裝普通 [`Agent`](/docs/agents/overview)，使 Agent 循環在 Workflow 中運行。事件通過 [PubSub](/docs/server/pubsub) 傳遞，因此客戶端斷線後可重新連接，而不會漏掉數據塊。運行狀態會持久化，進程重啟後仍可繼續。

## 何時使用持久化 Agent {/* #when-to-use-durable-agents */}

遇到以下任一情況時，可使用持久化 Agent：

- 客戶端可能在串流傳輸期間斷線並重新連接，例如移動設備、網絡不穩定或調用耗時較長。
- Agent 循環可能持續時間超過一次 HTTP 請求，例如後台研究或多步 Tool 調用。
- 需要觀察與重連 API，讓第二個客戶端接續第一個客戶端啟動的串流。
- 希望使用 [Inngest 驅動的執行](/integrations/deploy/inngest)，獲得步驟記憶化、重試和監控能力。

對於客戶端始終在線、生命週期限於一次請求的短調用，使用普通 `Agent` 的 `stream()` 或 `generate()` 更簡單。

## 快速入門 {/* #quickstart */}

使用 `@mastra/core/agent/durable` 中的 `createDurableAgent()` 包裝現有 Agent：

```typescript title="src/mastra/agents/researcher.ts"
import { Agent } from '@mastra/core/agent'
import { createDurableAgent } from '@mastra/core/agent/durable'

const agent = new Agent({
  id: 'researcher',
  name: 'Researcher',
  instructions: 'You research topics thoroughly.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

export const durableResearcher = createDurableAgent({ agent })
```

將持久化 Agent 註冊到 Mastra，然後調用 `stream()`：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { durableResearcher } from './agents/researcher'

const mastra = new Mastra({
  agents: { durableResearcher },
})

const { output, runId, cleanup } = await durableResearcher.stream(
  'Research quantum computing advances in 2025',
)

for await (const chunk of output.fullStream) {
  // Process each chunk as it arrives
}

// Release PubSub subscriptions and clear the run from the registry.
// If you skip this, an automatic cleanup timer fires after the stream ends.
cleanup()
```

傳回的 `runId` 標識這次執行。將其傳給 `observe()`，即可從另一客戶端重新連接。完整配置與方法 API 見 [DurableAgent 參考](/reference/agents/durable-agent)。

## 工作原理 {/* #how-it-works */}

持久化 Agent 在普通 Agent 之上增加三層能力：

1. **Workflow 執行**：`stream()` 將消息和選項序列化為 Workflow 輸入，然後在持久化 Workflow 中觸發 Agent 循環。它運行與 `Agent.stream()` 相同的循環，但每一步都可以記憶化並重放。

1. **PubSub 串流傳輸**：循環向以運行 ID 為 key 的 PubSub topic 發佈數據塊。調用方訂閱該 topic，並將數據塊傳入 `ReadableStream`；緩存會重放斷線期間錯過的數據塊。

1. **緩存層**：可選緩存保存已發佈的事件，讓較晚訂閱的客戶端補齊歷史事件。預設使用記憶體緩存，生產環境可使用 Redis 或其他後端。

## 執行方式 {/* #execution-variants */}

Mastra 提供三個創建持久化 Agent 的工廠函數，其區別在於 Workflow 的執行方式：

| 工廠函數 | 包 | 適用場景 |
| - | - | - |
| `createDurableAgent()` | `@mastra/core` | 本地開發和單進程伺服器。可直接等待並消費傳回的串流。 |
| `createEventedAgent()` | `@mastra/core` | 後台執行。Workflow 啟動時不阻塞調用方，通過 PubSub 消費數據塊。 |
| `createInngestAgent()` | `@mastra/inngest` | 生產部署。Inngest 提供步驟記憶化、重試和監控面板。 |

三者都傳回可像普通 Agent 一樣註冊到 `Mastra` 的對象。`createDurableAgent()` 和 `createEventedAgent()` 傳回擴展自 `Agent` 的類實例。`createInngestAgent()` 傳回基於 Proxy 的對象，將 `Agent` 方法轉發給底層 Agent。當訊號喚醒空閒線程時，三者都會通過持久化的 `stream()` 啟動運行；`sendSignal()` 和 `sendNotificationSignal()` 均如此。

### 使用 `createDurableAgent()` 在進程內運行 {/* #in-process-with-createdurableagent */}

包裝 Agent 後調用 `stream()`，即可在同一進程中獲得 `DurableAgentStreamResult`。不需要外部基礎設施，因此這是最快的入門方式：

```typescript title="src/mastra/agents/durable.ts"
import { Agent } from '@mastra/core/agent'
import { createDurableAgent } from '@mastra/core/agent/durable'

const agent = new Agent({
  id: 'helper',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

export const durableHelper = createDurableAgent({ agent })
```

### 使用 `createEventedAgent()` 啟動後毋須等待 {/* #fire-and-forget-with-createeventedagent */}

Workflow 在後台啟動，不阻塞調用方。數據塊仍通過 PubSub 傳遞，因此 `stream()` 會傳回可供消費的結果。觸發運行的 HTTP handler 無須等待 Workflow 完成：

```typescript title="src/mastra/agents/evented.ts"
import { Agent } from '@mastra/core/agent'
import { createEventedAgent } from '@mastra/core/agent/durable'

const agent = new Agent({
  id: 'writer',
  instructions: 'You write articles.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

export const eventedWriter = createEventedAgent({ agent })
```

### 已儲存 Agent 的可恢復串流 {/* #resumable-streams-for-stored-agents */}

通過 [`createStoredAgent()`](/reference/client-js/agents#createstoredagent) 創建的 Agent，僅使用 `durable` 欄位配置可恢復的串流。伺服器會實例化一個普通 `Agent`，並啟用串流發佈與重放：

```typescript
await mastraClient.createStoredAgent({
  id: 'helper',
  name: 'Helper',
  instructions: 'You are a helpful assistant.',
  model: { provider: 'openai', name: '__AI_SDK_OPENAI_MODEL_BASE__' },
  durable: true,
})
```

`durable` 也接受 `{ cleanupTimeoutMs }`。緩存和 pubsub 繼承自伺服器的 `Mastra` 實例。已有的 `durable: true` 儲存式 Agent 現在會加載可恢復串流，但沒有持久化執行或檢查點恢復能力。若要保留持久化執行，請定義由 `createDurableAgent({ agent })` 包裝的程式碼 Agent，並向工廠函數傳入 `maxSteps` 和快照持久化選項。

### 使用 `createInngestAgent()` 通過 Inngest 執行 {/* #inngest-powered-with-createinngestagent */}

在 [Inngest](https://www.inngest.com/docs) 平台運行 Workflow。每次 Tool 調用都會成為可記憶化的步驟，Inngest 可獨立重試這些步驟，並提供運行監控面板：

```typescript title="src/mastra/agents/inngest.ts"
import { Agent } from '@mastra/core/agent'
import { createInngestAgent } from '@mastra/inngest'
import { Inngest } from 'inngest'

const inngest = new Inngest({ id: 'my-app' })

const agent = new Agent({
  id: 'analyst',
  instructions: 'You analyze data.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

export const inngestAnalyst = createInngestAgent({ agent, inngest })
```

完整 API（包括 PubSub 和緩存配置等 Inngest 專屬選項）見 [`createInngestAgent()` 參考](/reference/agents/inngest-agent)。

## 可恢復的串流 {/* #resumable-streams */}

持久化 Agent 通過 PubSub 和事件緩存支援串流恢復。客戶端在串流傳輸期間斷線時，緩存會繼續保存事件。同一客戶端可用 `runId` 調用 `observe()` 重新連接：

```typescript title="src/server/reconnect.ts"
const { output } = await durableResearcher.observe(runId)

for await (const chunk of output.fullStream) {
  // Chunks from the run, including any missed while disconnected
}
```

不傳 offset 的 `observe(runId)` 是通用的重連方式。它會先重放所有可用的緩存事件，再傳遞實時事件。對於已完成的運行，觀察過程會重放保留的事件後關閉。若運行未知，或歷史已清除且沒有仍在運行的實例，則觀察過程會直接關閉，不傳回事件。HTTP observe endpoint 在此情況下傳回 404，因為它無法檢查調用方是否擁有該運行。

可選的 `offset` 是運行日誌中的位置，數據塊會以 `chunk.index` 報告。斷線後若要繼續，應傳入最後一個帶 `index` 的數據塊的 `index + 1`；若尚未收到數據塊，則省略 `offset`。這套規則同樣適用於 `stream()` 和 `observe()`、HTTP 與 `@mastra/client-js`。哪些數據塊沒有 index，以及結構化輸出和傳輸層限制，見 [`observe(runId, options?)`](/reference/agents/durable-agent#observerunid-options)。

重放並非永久的執行歸檔。事件只能保留到[清理](#cleanup)操作移除它們，或緩存自行刪除它們。Workflow 快照無法重建已清除的串流事件；禁用緩存則無法重放歷史事件。

觀察者不擁有運行。循環結束，或通過 `break`、`return`、異常提前退出時，觀察者會取消訂閱，而運行仍會繼續，其他觀察者也可繼續接收事件。若要從循環外停止觀察，例如客戶端斷線時，可調用 `detach()`：

```typescript title="src/server/reconnect.ts"
const { output, detach } = await durableResearcher.observe(runId)

request.signal.addEventListener('abort', detach, { once: true })

if (request.signal.aborted) detach()

for await (const chunk of output.fullStream) {
  // Stops when the run finishes or the client disconnects
}
```

如果傳入 `idleTimeoutMs`，且在該時長內沒有收到數據塊，Mastra 會在提供 `isAlive` 時檢查它。若 `isAlive` 傳回 `true` 或拋出異常，計時器會重啟，串流繼續保持打開；否則串流會以錯誤數據塊結束，並解除觀察者訂閱。只有 `isAlive` 傳回 `false` 時，運行本身才會被清理。

`createDurableAgent()` 和 `createEventedAgent()` 預設使用記憶體緩存，因此可恢復串流僅在單個進程內有效。若要跨進程或副本重連，生產者與觀察者必須共享重放緩存、PubSub 傳輸和運行狀態 storage。共享傳輸雖能傳遞實時事件，卻無法恢復只保存在另一進程緩存中的事件。配置持久化緩存後端（如 Redis），可使保留的事件在進程重啟後仍可使用：

```typescript title="src/mastra/agents/durable-with-cache.ts" {2,3,5,9}
import { createDurableAgent } from '@mastra/core/agent/durable'
import { RedisServerCache } from '@mastra/redis'
import Redis from 'ioredis'

const cache = new RedisServerCache({ client: new Redis('redis://localhost:6379') })

export const durableAgent = createDurableAgent({
  agent,
  cache,
})
```

`createInngestAgent()` 預設不啟用緩存。傳入 `cache` 選項，或將 Agent 註冊到配置了 `serverCache` 的 `Mastra` 實例，才可啟用可恢復串流。

對於使用緩存的 topic，每個發佈的事件都會先寫入緩存，再實時傳遞，因此發佈延遲受緩存往返耗時限制。如果寫入緩存失敗，事件仍會實時傳遞，但無法重放。`@mastra/redis` 和 `@mastra/valkey` 使用 Lua 腳本，以一次往返記錄每個事件。若客戶端沒有 `evalScript`，或 Redis Cluster 拒絕多 key 腳本，`@mastra/redis` 會回退到多條獨立命令。單次運行的 Workflow watch 事件（`workflow.events.v2.*`）永不緩存。如果緩存位於遠端（例如另一地區），而某個 topic 無須恢復，可使用 `shouldCache` 讓它直接發佈：

```typescript title="src/mastra/agents/durable-hot-topics.ts" {5}
export const durableAgent = createDurableAgent({
  agent,
  cache,
  // Skip the replay cache for the per-chunk stream topic; other topics stay resumable.
  shouldCache: topic => !topic.startsWith('agent.stream.'),
})
```

## 串流與後台任務 {/* #streaming-with-background-tasks */}

持久化 Agent 支援與普通 Agent 相同的 [`untilIdle`](/reference/streaming/agents/stream) 選項。設置 `untilIdle` 後，`stream()` 會跨後台任務的後續輪次保持連接，直到 Agent 空閒：

```typescript title="src/mastra/run.ts"
const { output, cleanup } = await durableAgent.stream('Research and summarize the topic', {
  untilIdle: true,
  memory: { thread: 'thread-1', resource: 'user-1' },
})

for await (const chunk of output.fullStream) {
  // Chunks from the initial turn AND any follow-up turns triggered by
  // background task completions
}

cleanup()
```

傳入 `{ maxIdleMs }` 可自定義空閒逾時，預設是 5 分鐘：

```typescript
await durableAgent.stream('Research topic', {
  untilIdle: { maxIdleMs: 30_000 },
  memory: { thread: 'thread-1', resource: 'user-1' },
})
```

後台任務的完整說明（包括配置、子 Agent 以及掛起/恢復）見[後台任務](/docs/harness/background-tasks)。

## 清理 {/* #cleanup */}

每次 `stream()` 和 `observe()` 調用都會傳回一個 `cleanup` 函數，用於清理運行：取消 PubSub 訂閱、從內部註冊表移除運行，並刪除緩存的運行事件，使之後無法重放。

如果沒有自行調用 `cleanup()`，Mastra 會在運行完成、出錯或中止後等待 `cleanupTimeoutMs` 再執行清理。預設值是 30 秒，因此除非配置其他值或更早調用 `cleanup()`，已完成運行的重放時間窗只有 30 秒。觀察者解除訂閱，或僅達到 `idleTimeoutMs`，不會啟動這個計時器。設置 `cleanupTimeoutMs: 0` 可關閉該計時器。緩存自身的 TTL 和淘汰策略仍然生效。

應從啟動運行的進程調用 `cleanup()`。若只是停止通過 `observe()` 觀察運行，請使用 `detach()` 或退出循環。

## Tool 審批 {/* #tool-approval */}

持久化 Agent 支援 Tool 審批（human-in-the-loop）。當 Tool 調用需要審批時，Workflow 會掛起，觸發 `onSuspended` 回調，並等待調用方通過 `resume()` 恢復：

```typescript title="src/mastra/run.ts" {4}
const { output, runId, cleanup } = await durableAgent.stream('Delete the old records', {
  requireToolApproval: true,
  onSuspended: ({ toolCallId, toolName, args }) => {
    // Notify the user and ask for approval
  },
})
```

審批完成後，恢復掛起的運行：

```typescript
await durableAgent.resume(runId, { approved: true })
```

## 崩潰恢復 {/* #crash-recovery */}

持久化 Agent 可以在運行期間將每次運行的狀態檢查點寫入 storage。如果伺服器進程在運行中崩潰，storage 中的運行會停留在 `running` 狀態，不會自動重試；下次伺服器啟動時，可重新驅動這些孤立運行，使它們從上次中斷處繼續。對於滾動部署等有序關閉場景，生成的伺服器還可以在退出前等待執行中的輪次完成。參見[優雅關閉與滾動部署](/docs/deployment/mastra-server#graceful-shutdown-and-rolling-deploys)。

按預設持久化策略，啟用崩潰恢復時才會寫入這些 `running` 檢查點。當 `recovery.durableAgents: 'off'`（預設值）時，持久化 Agent 會保存 `pending`、`paused` 和 `suspended` 運行的快照（人工介入恢復所依賴的產物），而在 `mastra.shutdown()` 開始前不寫入逐步驟的 `running` 檢查點。自定義的 `shouldPersistSnapshot` 謂詞會取代預設策略：包含 `running` 時每一步都會寫入檢查點；排除 `running` 時則完全不寫入，包括關閉期間。完整策略及覆蓋方法見[快照持久化](#snapshot-persistence)。

持久化 Agent 的運行不參與啟動時對活躍 Workflow 運行的通用重啟機制。持久化 Agent 唯一的自動恢復路徑是 `recovery.durableAgents: 'auto'`：它會認領每個孤立運行，註冊其線程運行時，再重新驅動運行。參見[運行所有權](#run-ownership)。

:::warning

自動和手動恢復都會從最近一次持久化快照繼續運行。結果未寫入該快照的 Tool 調用會再次執行；尚未保存的模型回應也會重新請求，並再次產生模型費用。依賴恢復機制前，請確保 Tool 冪等。參見[讓 Tool 可安全重復執行](#make-tools-safe-to-repeat)。

:::

逐次調用傳入的委派 hook 是閉包，無法在新進程中恢復。恢復的運行會回退到預設委派行為。恢復機制重建委派 Tool 時，會重新合併 supervisor 的 `defaultOptions.delegation` 中配置的 hook。因此必須跨重啟生效的 hook 應放在這裡，而不是逐次傳給 `stream()` 或 `generate()`。

### 快照持久化 {/* #snapshot-persistence */}

`createDurableAgent()` 的 `shouldPersistSnapshot` 選項（Agent 級 `durable` 配置也接受此選項）控制持久化 Agent 會寫入哪些 Workflow 快照。預設策略如下：

- 始終保存 `pending`、`paused` 和 `suspended` 快照。`resume()` 和 Tool 審批會讀取它們，因此無需額外配置即可支援人工介入串流程。
- 當 `recovery.durableAgents` 為 `'auto'` 時，在每一步保存 `running` 檢查點。這些逐步寫入僅用於崩潰後恢復執行中的運行；關閉恢復功能時，要到關閉過程開始才會寫入。
- 即使恢復功能關閉，在 `mastra.shutdown()` 開始後，只要運行到達步驟邊界，也會寫入一個 `running` 檢查點。如果運行在等待窗口結束前到達邊界，之後即可通過 `recover()` 或 `recoverActiveRuns()` 恢復。若整個關閉等待窗口內都卡在單次 LLM 或 Tool 調用中，則不會生成關閉檢查點。

若 Agent 配置了固定的 memory 實例（`memory: new Memory(...)`），`running` 檢查點不會重復儲存 memory 已保存的消息。來自 memory 的消息和運行自行保存的消息（例如使用 `savePerStep: true`）只要仍與對應的 memory 記錄相同，就會以指向這些記錄的小型引用保存；保存後被修改的消息仍會內聯儲存。這適用於檢查點中對話的每個副本，包括運行輸入和步驟結果。因此，長運行的檢查點增長會慢得多。若 Agent 通過函數解析 memory，則每個檢查點仍保留完整對話，因為恢復後解析到的 memory 可能不同。

若需要崩潰恢復檢查點，但不啟用自動恢復（例如自行在 leader election 後調用 `recoverActiveRuns()`），請傳入包含 `running` 的謂詞：

```typescript title="src/mastra/agents/durable.ts"
export const durableResearcher = createDurableAgent({
  agent,
  shouldPersistSnapshot: ({ workflowStatus }) =>
    ['pending', 'paused', 'suspended', 'running'].includes(workflowStatus),
})
```

如果自定義謂詞排除了 `suspended` 或 `paused`，會破壞人工介入恢復；若 `recovery.durableAgents` 為 `'auto'` 卻排除了 `running`，自動恢復也無法發現該 Agent。Mastra 會針對這兩種情況記錄警告。

Evented Agent 始終保存完整快照集：evented 引擎通過 storage 協調 Worker，`running` 記錄是其執行模型的一部分。Inngest Agent 始終只保存 `suspended` 快照，因為 Inngest 自身的重放提供持久性。兩者都接受 `shouldPersistSnapshot` 以保持 API 對稱，但會記錄警告並忽略該選項。

### 自動恢復 {/* #automatic-recovery */}

在 Mastra 配置中將 `recovery.durableAgents` 設為 `'auto'`。部署器啟動時會調用 `recoverAllDurableAgents()`，與 Workflow 運行的重啟同時進行：

```typescript title="src/mastra/index.ts" {7}
import { Mastra } from '@mastra/core'
import { PostgresStore } from '@mastra/pg'

export const mastra = new Mastra({
  agents: { myAgent: durableAgent },
  storage: new PostgresStore({ connectionString: process.env.DATABASE_URL! }),
  recovery: { durableAgents: 'auto' },
})
```

啟動時，系統會找出所有已註冊的持久化 Agent 中停留在 `running` 狀態的運行，並從最近一次持久化快照重新驅動。

恢復機制最多同時處理五個 Agent，每個 Agent 最多同時等待五個運行。每次等待涵蓋 `recover()` 初始化和整個恢復後 Workflow 的完成，最長 30 秒。逾時後，該嘗試仍在後台繼續，但會釋放一個等待槽位供其他運行使用。這些上限限制的是等待，而不是正在執行的運行總數。發現過程和被覆蓋的自定義恢復方法不受該預算限制。

逾時的運行會帶有 `retryAt`，之後自動再次檢查。復查會等原嘗試完成後才進行，避免重復執行。原嘗試完成後，恢復機制會檢查持久化快照和所有權，再決定是否重試。已完成或掛起的運行不會重啟。

開始關閉時，恢復機制會停止分派新的運行和 Agent，並取消待執行的復查。原有嘗試（包括等待逾時的嘗試）仍由 Mastra 的共享關閉等待過程跟蹤。恢復等待逾時不會取消執行，也不會增加額外的關閉等待窗口。

恢復機制不會接管仍由其他執行實例驅動的運行。它會跳過該運行，待原執行實例的認領可能過期後再檢查。即使進程在重啟前不久崩潰，運行也會自行恢復，無須再發起調用。

### 手動恢復 {/* #manual-recovery */}

如果需要更精細地控制，例如定時執行恢復，可直接調用這些方法：

```typescript
// Recover all durable agents
const result = await mastra.recoverAllDurableAgents()
console.log(
  `Recovered ${result.recovered} runs (${result.succeeded} ok, ${result.failed} failed, ${result.skipped} skipped)`,
)

// Recover a specific agent
const { recovered } = await durableAgent.recoverActiveRuns()
for (const run of recovered) {
  if (run.status === 'skipped') console.log(`${run.runId} was skipped: ${run.reason}`)
}

// Recover a single known run
await durableAgent.recoverActiveRuns({ runId: 'run-abc-123' })
```

`recoverAllDurableAgents()` 傳回計數，並自行安排符合條件的所有權復查。`recoverActiveRuns()` 傳回每個運行的結果：`success`、`failed` 或 `skipped`，且不會復查被跳過的運行。若因其他進程正在驅動而跳過，結果會帶 `retryAt`，表示該進程若不續租，認領何時過期。等待逾時的嘗試則傳回 `status: 'skipped'` 和 `reason: 'recovery-timeout'`，不帶 `retryAt`，因此 Mastra 不會自動重試它。`skipped` 計數包含這種嘗試；即使它之後完成，`recovered`、`succeeded` 和 `failed` 計數也不會包含它。

手動恢復讀取與自動恢復相同的 `running` 檢查點。對於採用預設快照策略、且 `recovery.durableAgents` 為 `'off'` 的 `DurableAgent`，只有在 `mastra.shutdown()` 開始後到達的步驟邊界才會為執行中運行寫入檢查點。如果運行此前已經崩潰，或在關閉等待窗口內未到達步驟邊界，就沒有檢查點，因此 `listActiveRuns()` 和 `recoverActiveRuns()` 找不到它。參見[快照持久化](#snapshot-persistence)。

若要接管仍在運行的實例（例如某次執行卡住），可在 `recover()` 中傳入 `force: true`：

```typescript
const { output } = await durableAgent.recover('run-abc-123', { force: true })
```

原先持有該運行的執行實例會失去所有權。Mastra 在檢測到所有權丟失時會請求取消；不回應取消請求的工作仍可能繼續。若認領由 storage 管理，串流會丟棄舊認領代際的事件。有關取消的限制，見[所有權丟失後停止工作](#stop-work-after-ownership-loss)。不傳 `force` 時，`recover()` 對仍在運行的實例會拋出 `DURABLE_AGENT_RUN_ACTIVE`。即使傳入 `force`，`recover()` 也拒絕接管同一進程內正在執行的運行。

### 運行所有權 {/* #run-ownership */}

每次調用 `stream()`、`generate()`、`resume()` 或 `recover()` 都會在執行前認領運行，並每隔 5 秒續租。最後一次續租後 15 秒，認領即失效，因此進程崩潰的運行最遲可在 15 秒內進入可恢復狀態。此前恢復機制仍認為運行活躍；同一運行的 `stream()` 或 `resume()` 會等待最多 5 秒取得認領，隨後拋出 `DURABLE_AGENT_EXECUTION_CONFLICT`。`mastra.shutdown()` 會在關閉等待窗口結束後停止仍在執行的運行，不再寫入，並釋放其認領。下一次啟動即可恢復，無須等認領自然過期。可用 `MASTRA_AGENT_THREAD_LEASE_TTL_MS` 修改有效期；除非 `MASTRA_AGENT_THREAD_LEASE_RENEW_INTERVAL_MS` 設了更短間隔，否則每經過有效期的三分之一就會續租。

認領的強制程度取決於 workflows store。如果 store 支援 run fencing，認領就是其中一條記錄，每次寫入都會在同一操作中核對認領。其他執行實例取得認領後，原實例的寫入會被拒絕。其消息、線程和 working memory 寫入僅在 memory store 也支援 run fencing 時才會被拒絕；如果 Agent 的 `Memory` 使用不支援此機制的 storage adapter，這些寫入仍會落庫。以下 adapter 支援 run fencing：

- 來自 `@mastra/core/storage` 的 `InMemoryStore`
* `@mastra/pg`
- `@mastra/libsql` 和 `@mastra/turso`
* `@mastra/mysql`
* `@mastra/mssql`
* `@mastra/oracledb`
* `@mastra/spanner`
* `@mastra/dsql`
* `@mastra/cloudflare-d1`
- `@mastra/cloudflare`，配合 `CloudflareDOStorage`
* `@mastra/convex`
- `@mastra/mongodb`，部署在副本集或分片集群上
* `@mastra/dynamodb`
* `@mastra/redis`
* `@mastra/upstash`
* `@mastra/valkey`

在 Convex 中，run fencing 由部署的 Mastra 服務端函數執行。升級 `@mastra/convex` 後，請重新部署 Convex 函數。在重新部署前，持久化 Agent 運行會失敗，並提示需要重新部署；其他寫入仍可正常進行。

支援 run fencing 的 store 為每個運行保存一條認領記錄；若運行使用 memory，還會保存一條 memory fence 記錄。支援保留策略的 store 可通過 `workflows.runOwnership` 和 `memory.runFences` [保留 key](/reference/storage/retention#retention-eligible-tables) 清理它們。Redis、Upstash 和 Valkey 則自行過期：認領在最後一次認領、續租或釋放後 7 天過期；fence 在停用後 7 天過期。運行的首個代際由 store 的時鐘決定，因此即使某個 `runId` 的舊記錄已清理後再次被使用，新的代際仍高於舊執行的 fence 與串流事件。

對於其他 workflows store，認領是 [PubSub](/docs/server/pubsub) 後端上的 lease。它可防止兩個執行實例同時認領運行，但不會拒絕失去認領的實例繼續寫入。如果接管時原實例仍活躍，運行可能最終輸出原實例的結果。若執行實例失去 lease，而沒有其他實例接管，運行仍可能保持佔用狀態最多 15 秒。在此之前，不傳 `force` 的 `recover()` 會拋出 `DURABLE_AGENT_RUN_ACTIVE`，並通過 `retryAt` 指明佔用肯定結束的時間。如果 workflows 或 memory store 不支援 run fencing，Mastra 會在恢復運行時記錄警告。

lease 只能協調共享它的進程。預設的 `EventEmitterPubSub` 僅覆蓋一個進程；`UnixSocketPubSub` 覆蓋同一主機上的進程；`RedisStreamsPubSub` 和 `ValkeyStreamsPubSub` 覆蓋連接同一伺服器的所有實例。`GoogleCloudPubSub` 不提供 lease，因此若 store 也不支援 run fencing，每次認領都會成功，恢復機制可能接管仍在運行的實例。

### 所有權丟失後停止工作 {/* #stop-work-after-ownership-loss */}

持久化和 evented Agent 在某一步檢測到已失去運行所有權時，會請求取消正在進行的 Tool 和模型調用。其他進程中的 evented Worker 會按認領續租間隔檢查所有權，但不會為原執行實例續租。預設間隔是 5 秒，即 `MASTRA_AGENT_THREAD_LEASE_TTL_MS` 的三分之一；檢測時間還取決於後端回應速度。持有認領的進程在所有權檢查失敗，或有效期前無法續租時，會停止該步驟。只觀察其他進程認領的步驟若在一個 lease 有效期內（預設 15 秒）始終無法成功檢查，也會停止。

取消需要工作主動配合。對於可取消的操作，請使用 Tool 執行 context 中的 `abortSignal`，並在產生下一次副作用前檢查它。不回應訊號的 Tool 可能繼續運行。Mastra 外部已完成的工作不會回滾。

在前一次執行檢測到所有權丟失前，恢復機制可能已開始同一個 Tool 調用。因此取消能減少重疊執行，卻無法阻止 Tool 執行兩次。參見[讓 Tool 可安全重復執行](#make-tools-safe-to-repeat)。

### 多實例部署 {/* #multi-instance-deployments */}

每個副本都可設置 `recovery.durableAgents: 'auto'`。同時啟動的副本會競爭恢復同一個孤立運行，但只有一個能認領成功，其餘會跳過。前提是所有副本共享同一認領機制：支援 run fencing 的 workflows store，或所有副本共用 lease 的 PubSub 後端。否則，應通過自己的 leader election 限制恢復操作，或只在單個副本上運行。

## 數據庫負載 {/* #database-load */}

Mastra 沒有發佈持久化 Agent 的硬件性能基準，因此應根據自身工作負載確定數據庫容量。本節說明負載來源及應觀察的指標。

每個檢查點都會以 JSONB 將運行的完整快照 upsert 到 `mastra_workflow_snapshot`：Agent Workflow 和其嵌套執行 Workflow 各佔一行。快照包含到目前為止的對話及所有 Tool 結果，因此會隨運行增長；一次運行寫入的總字節數增長速度可能快於步驟數。寫入負載取決於：

- **檢查點頻率**：使用 `createDurableAgent()` 創建的 Agent 在 `recovery.durableAgents` 為 `'off'`（預設值）時，寫入的檢查點較少。設置為 `'auto'` 後，每一步都會寫入 `running` 檢查點。使用 `createEventedAgent()` 創建的 Agent 始終每步寫入。參見[快照持久化](#snapshot-persistence)。
- **每次運行的步驟數和 payload 大小**：Tool 傳回的每個字節都會在該運行後續的每個檢查點中再次寫入。
- **併發運行數**：同時進行的運行越多，負載越高。

要降低寫入量，同時保留崩潰恢復能力，可以：

- 給 Agent 配置固定的 memory 實例，使檢查點保存已存消息的引用，而非完整副本。
- 讓 Tool 傳回較小的結果，例如 ID 或 URL，而非大型文檔。
- 將長任務拆成多個較短的運行。

每個 `PostgresStore` 在每個進程中最多打開 `max` 個連接，預設是 20 個。傳入的 `pool`、`writePool` 或獨立 `readPool` 各有自己的限制。應匯總所有副本和進程中連接同一伺服器的 pool 限額，並留出其他客戶端所需容量，使總數低於伺服器的 `max_connections`。如果前面使用 PgBouncer 等事務模式連接池，也應按其服務端連接數計算。參見 [PostgreSQL](/integrations/databases/postgresql)。

每次檢查點 upsert 都會留下舊的行版本；Mastra 又會刪除已完成運行的行，因此 `mastra_workflow_snapshot` 很快積累失效行。掛起的運行會保留其行。若刪除失敗，Mastra 會記錄 `Failed to delete workflow snapshot rows` 警告，行會一直保留，直到手動刪除或[清理](/reference/storage/retention)。例外是：使用共享 pub/sub 傳輸且由 storage 提供 fencing 的 `createEventedAgent()` Agent 會記錄 `durable execution delivery failed`，並隨事件重試刪除。保留策略清理會按不活躍時長移除快照，範圍包括掛起運行，以及其步驟近期未寫入檢查點的運行中任務。將 `workflowSnapshot.maxAge` 設為長於預計最長掛起時間和最長步驟耗時；如果無法確定上限，就不要啟用快照清理。應提高該表的 autovacuum 積極程度。如果設置了 `schemaName`，請將以下示例中的 `public` 替換為它：

```sql
ALTER TABLE public.mastra_workflow_snapshot SET (
  autovacuum_vacuum_scale_factor = 0.01,
  toast.autovacuum_vacuum_scale_factor = 0.01
);
```

要決定擴容還是調整工作負載，應觀察：

- `pg_stat_user_tables` 中 `mastra_workflow_snapshot` 的 `n_dead_tup` 和 `last_autovacuum`，以及 `pg_stat_all_tables` 中其存放大型快照的 TOAST 表的相同指標
- `pg_stat_statements` 中快照 upsert 佔 `total_exec_time` 和 `wal_bytes` 的比例。使用該視圖需在 `shared_preload_libraries` 中配置 `pg_stat_statements`（需要重啟伺服器），並執行 `CREATE EXTENSION pg_stat_statements`
- 每秒 WAL 字節數（`pg_stat_wal`）
- 活躍連接數與連接池 `max` 的比較

如果快照 upsert 是主要寫入來源，先減少檢查點大小或頻率；如果許多不相關的查詢也很慢，再考慮擴容。

## 讓 Tool 可安全重復執行 {/* #make-tools-safe-to-repeat */}

持久化或 evented Agent 可能多次執行同一個 Tool 調用。一次 Tool 調用指模型發出的一次 Tool 執行請求。以下情況會發生重復執行：

- 進程在 Tool 執行期間停止，或 Tool 已傳回但 Mastra 尚未保存結果時停止。運行[恢復](#crash-recovery)後，Tool 會再次執行。
- 使用 Postgres storage 和 Redis Streams PubSub 時，evented Worker 在發佈 Tool 結果前停止。另一個 Worker [重新領取步驟](/reference/pubsub/redis-streams#evented-agent-worker-takeover)，再次執行 Tool。
- 恢復機制在前一次執行仍運行 Tool 時接管，例如對 [`recover()` 傳入 `force: true`](#manual-recovery)。兩個執行實例可能同時運行該 Tool。參見[所有權丟失後停止工作](#stop-work-after-ownership-loss)。

設置了 `retries` 的 [Inngest Agent](#inngest-powered-with-createinngestagent) 也會再次執行被中斷的 Tool 步驟。

Mastra 無法撤銷 Tool 在其他系統已完成的操作。發送郵件、扣款或刪除記錄的 Tool 可能執行兩次，因此應使其冪等。冪等意味著同一次調用再次執行時不會產生額外效果。

### 使用 Tool 調用 ID 作為冪等 key {/* #use-the-tool-call-id-as-an-idempotency-key */}

Agent 運行 Tool 時，`context.agent.toolCallId` 標識該次 Tool 調用。Mastra 會在執行模型回應中的 Tool 前先保存該回應，因此同一次調用重試時會收到相同的 `toolCallId`。

將 ID 傳給支援冪等 key 的服務。以下 Tool 發起 Stripe 退款，並把 Tool 調用 ID 作為 Stripe 的[冪等 key](https://docs.stripe.com/api/idempotent_requests)。同一次調用再次執行時，Stripe 會傳回第一次退款，而不是新建第二次退款：

```typescript title="src/mastra/tools/refund-payment.ts"
import { createTool } from '@mastra/core/tools'
import Stripe from 'stripe'
import { z } from 'zod'

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!)

export const refundPayment = createTool({
  id: 'refund-payment',
  description: 'Refunds a customer payment',
  inputSchema: z.object({
    paymentIntentId: z.string(),
  }),
  outputSchema: z.object({
    refundId: z.string(),
    status: z.string().nullable(),
  }),
  execute: async ({ paymentIntentId }, context) => {
    const toolCallId = context.agent?.toolCallId
    if (!toolCallId) throw new Error('refund-payment must be called by an agent')

    const refund = await stripe.refunds.create(
      { payment_intent: paymentIntentId },
      { idempotencyKey: `refund-payment:${paymentIntentId}:${toolCallId}` },
    )

    return { refundId: refund.id, status: refund.status }
  },
})
```

`context.agent` 僅在 Agent 運行 Tool 時存在，所以示例需要檢查它。Tool 調用 ID 來自模型提供方，有些提供方可能在不同回應中復用 ID。加入 payment ID 可避免兩次不同退款共用一個 key。Stripe 可能在 24 小時後刪除冪等 key，因此更晚恢復的運行仍可能創建第二次退款。

如果服務不支援冪等 key，請以相同方式構造 key，並將其與變更一同記錄：

- 在數據庫中，將 key 與變更寫入同一事務，並給 key 列設置唯一約束；重復時跳過變更，例如在 Postgres 使用 `INSERT ... ON CONFLICT DO NOTHING`。還應保存對應的 Tool 結果，使重復調用能向模型傳回相同結果。
- 對其他服務，可將 key 附在請求中，並在執行操作前查詢，例如按郵件 header 中的 key 搜索已發送郵件。若兩個執行實例重疊，它們仍可能同時通過查詢後各自發送請求。

### 保護子 Agent 中的 Tool {/* #protect-tools-inside-subagents */}

一次[子 Agent](/docs/subagents) 委派對應一次 `agent-<name>` Tool 調用。恢復機制不會保存委派內部的模型和 Tool 調用，因此委派重試時，子 Agent 會從頭開始，其 Tool 也會獲得新的 `toolCallId`。僅憑 Tool 調用 ID 構造的 key 無法識別這種重復。

對子 Agent 使用的 Tool，應根據預期副作用本身的數據構造 key。退款場景中，可組合 payment ID 和訂單行 ID。避免使用也會阻止合法第二次操作的 key；例如允許部分退款時，不能只用 payment ID。
