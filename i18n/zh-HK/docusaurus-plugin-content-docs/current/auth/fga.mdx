# 細緻權限控制 (FGA)

:::note

FGA 在正式環境需要 Mastra 企業版 (EE) 授權；開發環境則毋須授權。詳見[需要 EE 授權的功能](/docs/license#what-requires-an-ee-license)。如需更多資訊，請[聯絡銷售團隊](https://mastra.ai/contact)。

:::

細緻權限控制 (FGA) 為 Mastra 應用程式加入資源層級的權限檢查。RBAC 回答「這個角色可以執行此操作嗎？」，FGA 則回答**「這名用戶可以對這項特定資源執行此操作嗎？」**

## 何時使用 FGA {/* #when-to-use-fga */}

FGA 專為多租戶 B2B 產品而設計，其中權限與上下文相關：

- 用戶可能是團隊 A 的**管理員**，但只是團隊 B 的**成員**
- 對對話執行緒的存取應限於用戶所屬機構
- Workflow 的執行應限於指定團隊或項目
- Tool 的存取權視乎用戶與資源的關係

## 設定 {/* #configuration */}

在 Mastra 伺服器設定中，一併設定 FGA、身份驗證及 RBAC：

```typescript
import { Mastra } from '@mastra/core/mastra'
import { MastraFGAPermissions } from '@mastra/core/auth/ee'
import { MastraAuthWorkos, MastraFGAWorkos } from '@mastra/auth-workos'

const mastra = new Mastra({
  server: {
    auth: new MastraAuthWorkos({
      /* ... */
      fetchMemberships: true,
      mapUserToResourceId: user => user.teamId,
    }),
    fga: new MastraFGAWorkos({
      resourceMapping: {
        agent: { fgaResourceType: 'team', deriveId: ctx => ctx.user.teamId },
        workflow: { fgaResourceType: 'team', deriveId: ctx => ctx.user.teamId },
        thread: { fgaResourceType: 'workspace-thread', deriveId: ({ resourceId }) => resourceId },
      },
      permissionMapping: {
        [MastraFGAPermissions.AGENTS_EXECUTE]: 'manage-workflows',
        [MastraFGAPermissions.WORKFLOWS_EXECUTE]: 'manage-workflows',
        [MastraFGAPermissions.MEMORY_READ]: 'read',
        [MastraFGAPermissions.MEMORY_WRITE]: 'update',
      },
    }),
    storedResources: {
      scope: true,
    },
  },
})
```

使用 `MastraFGAWorkos` 時，請在 `MastraAuthWorkos` 設定 `fetchMemberships: true`。WorkOS FGA 檢查需要用戶的機構成員資格，才能找出授權所需的正確成員資格 ID。

對記憶功能進行授權時，請以 `thread` 作為資源映射鍵。`MastraFGAWorkos` 仍接受舊別名 `memory`，但新設定應優先使用 `thread`。

設定 `server.fga` 後，Mastra 會對受保護操作執行 FGA 檢查。如果操作沒有已驗證身份的用戶，Mastra 會拒絕執行。未設定 `server.fga` 時，系統會略過這些檢查，維持原有行為。

### 資源映射 {/* #resource-mapping */}

`resourceMapping` 指定如何從請求內容找出 FGA 資源類型及 ID。鍵是 Mastra 資源類型；值則定義 FGA 資源類型及 ID 的推導方式：

```typescript oxfmt:false
resourceMapping: {
  // When checking "can user execute agent X?", resolve the FGA resource
  // as the user's team (type: 'team', id: user.teamId)
  agent: {
    fgaResourceType: 'team',
    deriveId: (ctx) => ctx.user.teamId,
  },
}
```

`deriveId()` 會收到：

- `user`：已驗證身份的用戶
- `resourceId`：所屬 Mastra 資源的 ID（如有，例如執行緒的 `resourceId`）
- `requestContext`：目前的請求內容，可用於較複雜的租戶解析

若 `deriveId()` 傳回 `undefined`，系統便會改用原本的 Mastra 資源 ID。

檢查執行緒和記憶權限時，Mastra 仍以原始 `threadId` 作為待檢查資源，同時把執行緒所屬的 `resourceId` 傳入 `deriveId()`。這樣便可把執行緒權限映射至 `userId-teamId-orgId` 等複合租戶 ID。

### 權限映射 {/* #permission-mapping */}

`permissionMapping` 把 Mastra 內部權限字串映射至 FGA Provider 使用的權限標識：

```typescript oxfmt:false
import { MastraFGAPermissions } from '@mastra/core/auth/ee';

permissionMapping: {
  [MastraFGAPermissions.AGENTS_EXECUTE]: 'manage-workflows', // Mastra permission -> WorkOS permission slug
  [MastraFGAPermissions.MEMORY_READ]: 'read',
}
```

如果某項權限沒有映射，系統會直接傳入原始字串。

使用 `validatePermissions()`，可在啟動時驗證 Mastra 可能產生的整套權限。如 Provider 要求每項 Mastra 權限都明確對應一個 Provider 權限標識，便應使用此方法。

### 已儲存資源的範圍限制 {/* #stored-resource-scoping */}

FGA 可授權存取資源，但不會自動篩選共用儲存空間中的紀錄。在多租戶應用程式使用內置已儲存資源 API 時，請啟用範圍限制。

```typescript
const mastra = new Mastra({
  server: {
    auth: new MastraAuthWorkos({
      /* ... */
      mapUserToResourceId: user => user.teamId,
    }),
    storedResources: {
      scope: true,
    },
  },
})
```

啟用 `scope: true` 後，Mastra 會從請求內容讀取 `MASTRA_RESOURCE_ID_KEY`。`mapUserToResourceId()` 會在身份驗證後設定此值。已儲存資源處理程式把範圍保存在紀錄的中繼資料，並據此篩選列出、讀取、更新、發佈和刪除操作。

如果需要自訂請求邏輯來決定範圍，請使用物件設定：

```typescript oxfmt:false
storedResources: {
  scope: {
    metadataKey: 'teamId',
    resolve: ({ user }) => user.teamId,
    requireScope: true,
  },
},
```

當 `requireScope` 設為 `true` 或省略時，若無法解析範圍，受範圍限制的已儲存資源路由便會失敗。

### 路由政策涵蓋範圍 {/* #route-policy-coverage */}

Mastra 為內置資源路由提供路由層級的 FGA 中繼資料，涵蓋 Agent、Workflow、Tool、MCP Tool、記憶執行緒、回應、對話及已儲存資源。已儲存資源路由包括 `/stored/agents`、`/stored/mcp-clients`、`/stored/prompt-blocks`、`/stored/scorers`、`/stored/skills` 和 `/stored/workspaces`。路由具有 `fga` 中繼資料、Mastra 能推導該路由的內置中繼資料，或 Provider 透過 `resolveRouteFGA()` 提供中繼資料時，便會執行檢查。

若要拒絕無法解析 FGA 中繼資料的受保護路由，請在 FGA Provider 設定路由政策涵蓋範圍：

```typescript
const fga = new MastraFGAWorkos({
  resourceMapping: {
    project: { fgaResourceType: 'project' },
  },
  permissionMapping: {
    'projects:read': 'read',
  },
  requireForProtectedRoutes: true,
  auditProtectedRoutes: 'warn',
  validatePermissions: async permissions => {
    // Throw if a Mastra permission is missing from permissionMapping.
  },
})
```

設定 `auditProtectedRoutes: 'error'`，可在受保護路由缺少內置 FGA 中繼資料時令啟動失敗。啟用 `requireForProtectedRoutes` 後，Mastra 預設會把此審核記錄為警告。

自訂路由應優先使用路由層級的 `fga` 中繼資料，讓授權政策與路由定義放在一起：

```typescript
import { createRoute } from '@mastra/server/server-adapter'

export const getProjectRoute = createRoute({
  method: 'GET',
  path: '/projects/:projectId',
  responseType: 'json',
  requiresAuth: true,
  fga: {
    resourceType: 'project',
    resourceIdParam: 'projectId',
    permission: 'projects:read',
  },
  handler: async () => {
    return { project: null }
  },
})
```

只有在必須按路由、參數或請求內容集中推導路由中繼資料時，才使用 `resolveRouteFGA()`。路由映射表比字串前綴檢查更易擴展：

```typescript
import type { FGARouteConfig, FGARouteResolver } from '@mastra/core/auth/ee'

const routeFGA = {
  'GET /billing/:accountId': {
    resourceType: 'account',
    resourceIdParam: 'accountId',
    permission: 'billing:read',
  },
} satisfies Record<string, FGARouteConfig>

const resolveRouteFGA: FGARouteResolver = ({ route }) => routeFGA[`${route.method} ${route.path}`]

const fga = new MastraFGAWorkos({
  /* ... */
  resolveRouteFGA,
})
```

## 權限檢查時機 {/* #enforcement-points */}

設定 FGA Provider 後，Mastra 會在以下生命週期階段自動檢查授權：

| 生命週期階段 | 檢查的權限 | 資源類型 | 資源 ID |
| - | - | - | - |
| Agent 執行（`generate`、`stream`） | `agents:execute` | `agent` | `agentId` |
| 內置 Workflow HTTP 執行路由及 `Workflow.execute()` | `workflows:execute` | `workflow` | `workflowId` |
| 獨立 Tool 執行 | `tools:execute` | `tool` | `toolName` |
| Agent Tool 執行 | `tools:execute` | `tool` | `${agentId}:${toolName}` |
| MCP Tool 執行 | 預設為 `tools:execute` | 預設為 `tool`，亦可由伺服器層級的 `fga.resourceMapping` 覆寫 | 預設為 `JSON.stringify([serverName, toolName])`，亦可使用伺服器層級推導的 ID |
| 執行緒及記憶存取 | `memory:read`、`memory:write`、`memory:delete` | `thread` | `threadId` |
| 已儲存資源路由 | 路由操作對應的已儲存資源權限 | 已儲存資源類型 | 路由紀錄 ID；集合路由則使用已儲存資源範圍 |
| HTTP 資源路由 | 按路由設定 | 按路由設定 | 按路由設定 |

對受 OAuth 保護的 MCP 伺服器，HTTP MCP 傳輸會以 `extra.authInfo` 傳遞身份驗證資料。如果 `MCPServer` 已註冊到啟用 FGA 的 Mastra 執行個體，請設定 `mapAuthInfoToUser`，讓 Mastra 在檢查 `tools/list` 和 `tools/call` 前設定 `requestContext.get('user')`。若 MCP Tool 檢查所需的資源或權限映射有別於 Agent 和 Workflow 內部的 Tool 檢查，請使用伺服器層級的 `fga` 選項。詳見 [MCPServer 身份驗證內容](/reference/tools/mcp-server#map-auth-data-for-fga)。

此版本的核心 FGA 不會獨立檢查直接呼叫 SDK 的 `createRun().start()`、`resume()` 或 `restart()`。請從受保護路由發起這些呼叫，或在應用程式程式碼中加以保護。直接呼叫受保護入口時，請傳入包含已驗證用戶的 `requestContext`。

Agent、內部 Workflow、Tool 和記憶的核心檢查亦會把 `requestContext` 及操作中繼資料傳給 FGA Provider。路由檢查會傳遞 `requestContext`；執行緒檢查則會在可取得時傳遞所屬 `resourceId`。

## 自訂 FGA Provider {/* #custom-fga-provider */}

實作 `IFGAProvider`，便可使用任何 FGA 後端：

```typescript
import { FGADeniedError } from '@mastra/core/auth/ee'
import type { FGACheckParams, IFGAProvider, MastraFGAPermissionInput } from '@mastra/core/auth/ee'

class MyFGAProvider implements IFGAProvider {
  async check(user: any, params: FGACheckParams): Promise<boolean> {
    // Your authorization logic
    return true
  }

  async require(user: any, params: FGACheckParams): Promise<void> {
    const allowed = await this.check(user, params)
    if (!allowed) {
      throw new FGADeniedError(user, params.resource, params.permission)
    }
  }

  async filterAccessible<T extends { id: string }>(
    user: any,
    resources: T[],
    resourceType: string,
    permission: MastraFGAPermissionInput,
  ): Promise<T[]> {
    // Filter resources the user can access
    return resources
  }
}
```

:::note
全部方法、參數及 `ActorSignal` 類型，請參閱 [`IFGAProvider` 參考文件](/reference/auth/fga)。
:::

## 系統參與者 {/* #system-actors */}

自主運作或按排程執行的 Agent 沒有終端用戶。請以 actor 訊號標記這些呼叫，讓 FGA 可區分它們與用戶請求：

- `true` 或 `{ actorKind: 'system' }` 代表匿名系統 actor。
- 物件形式亦可包含 `agentId`、`permissions` 及 `scope`，用來識別及限制執行操作的 Agent。

預設情況下，受信任 actor 通過租戶範圍檢查後，會略過針對用戶的 `require()` 檢查。若要按 Agent 實施最小權限，請在 Provider 實作可選的 `requireActor` 方法。此方法接收 actor 及與 `require` 相同的 `FGACheckParams`；拒絕存取時會擲出 `FGADeniedError`。沒有實作 `requireActor` 的 Provider 會保留受信任 actor 的略過機制，維持向後兼容。

```typescript
import { FGADeniedError } from '@mastra/core/auth/ee'
import type { ActorSignal, FGACheckParams, IFGAProvider } from '@mastra/core/auth/ee'

class MyFGAProvider implements IFGAProvider {
  // ...check, require, filterAccessible...

  async requireActor(actor: ActorSignal, params: FGACheckParams): Promise<void> {
    const agentId = actor === true ? undefined : actor.agentId
    // Resolve the agent's real grants from a trusted source keyed by agentId.
    const granted = await this.grantsForAgent(agentId)
    const required = Array.isArray(params.permission) ? params.permission : [params.permission]
    if (!required.some(permission => granted.includes(permission))) {
      throw new FGADeniedError(null, params.resource, params.permission)
    }
  }
}
```

### 把 actor 傳至 Workflow 步驟 {/* #propagating-an-actor-into-workflow-steps */}

Workflow 執行時的 `actor` 會傳入每個步驟的執行內容，但不會自動傳給步驟發起的 Agent 及 Tool 呼叫。步驟呼叫 Agent 時若沒有提供 `actor`，便會回退至用戶成員資格解析；沒有用戶的系統執行會因此失敗。

在 actor 設定 `propagate: true` 後，框架會把它傳給執行期間宣告式 `.then(agent)` 及 `.then(tool)` 步驟發起的 Agent、Tool 呼叫：

```typescript
await run.start({
  inputData: { city: 'London' },
  actor: { actorKind: 'system', sourceWorkflow: 'nightly-report', propagate: true },
})
```

傳遞機制須自行啟用，而且刻意限制了範圍：

- `true` 簡寫形式不會傳遞；請使用物件形式啟用。
- 自訂步驟的 `execute` 函式不在涵蓋範圍內。請從步驟內容讀取 `actor` 並明確傳入，以免代用戶執行的步驟在無意間繼承系統信任。
- 建立步驟時傳入 `actor` 可覆寫該步驟的執行層級 actor；傳入 `actor: undefined` 則可在執行途中切換回用戶授權。

```typescript
// Runs as the system actor even though it loads user-supplied data.
workflow.then(createStep(reportAgent))
// Explicitly runs as the user instead.
workflow.then(createStep(summaryAgent, { actor: undefined }))
```

### 信任要求 {/* #trust-requirements */}

參與者訊號是可信輸入，因此在伺服器端建構它：

- 把 `actor` 視為每次呼叫各自提供的訊號。持久化 Workflow 會在執行開始時傳遞它，但恢復執行時不會還原最初的 actor。每次以受信任身份恢復時，請明確傳入，或透過 Agent 的 `defaultOptions` 解析新的 actor。若目前沒有 actor，便會套用用戶授權；缺少用戶時會拒絕存取。
- Mastra 會從內置 Agent HTTP 路由處理的執行選項中移除 `actor`。請在排程工作或 Workflow 等伺服器端程式碼中設定，切勿接受用戶端輸入。
- 在伺服器端建立租戶範圍。內置 Agent HTTP 路由會忽略用戶端在請求內容提供的 `organizationId`；受信任 actor 路徑則要求設定 `organizationId`。
- 持久化恢復會沿用現有的請求內容還原及合併行為，但不會因此信任後續 Workflow 階段中已持久化的 actor。
- 租戶範圍檢查只確認有受信任的 `organizationId`，不會驗證 `actor.agentId` 是否屬於該機構。若這層關係重要，請在 `requireActor` 中使用具權威性的 Provider 資料驗證。
- 把 `actor.permissions` 視為未經驗證的聲明。若要實施最小權限，請按 `agentId` 從資訊清單或 FGA 後端等可信來源解析 Agent 權限，不要信任內嵌值。
- Provider 一旦實作 `requireActor`，該方法的錯誤便會終止執行。Mastra 不會回退至只按機構授權。
