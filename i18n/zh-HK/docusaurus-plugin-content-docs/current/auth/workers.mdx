# Worker 身分驗證

:::beta

在 API 穩定之前，可能會在沒有重大版本更新的情況下發生重大變更。

:::

當 Worker 和 API 在不同進程執行，兩者會透過 HTTP 通訊。編排 Worker 調用 API 的步驟執行端點，讓 Workflow 步驟在 API 伺服器執行。推送模式的 PubSub Broker（例如以推送模式運作的 Google Cloud Pub/Sub）亦可直接將事件送到 API 的事件端點。拉取模式則由 Worker 自行向 Broker 取得事件。設定身分驗證 Provider 後，兩個 HTTP 端點都須經過驗證。

## 運作方式 {/* #how-it-works */}

Worker 沿用 Mastra 伺服器的身分驗證流程。編排 Worker 隨每個 HTTP 請求送出憑證，再由伺服器已設定的 `authenticateToken` Provider 核實。

|端點 |使用者 |目的|
| - | - | - |
| `POST /api/workflows/:workflowId/runs/:runId/steps/execute` | 編排 Worker，透過 `HttpRemoteStrategy` 調用 | 在 API 伺服器執行 Workflow 步驟 |
| `POST /api/workflows/events` | Push-mode brokers (GCP Pub/Sub, SNS) | Deliver workflow events to the API |

兩條路線都有`requiresAuth: true`. When no auth provider is configured, they're publicly accessible.

:::warning

將工作程序部署為單獨的進程時，請務必在伺服器上設定身份驗證提供者。如果沒有，步驟執行和事件端點將對任何呼叫者開放。

:::

## 設定 Worker 身分驗證 {/* #setting-up-worker-auth */}

### 在伺服器上設定身份驗證提供者 {/* #configure-an-auth-provider-on-the-server */}

任何 Mastra 身分驗證 Provider 均可使用。`SimpleAuth` 適合驗證 Worker 權杖：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'
import { SimpleAuth } from '@mastra/core/server'

export const mastra = new Mastra({
  server: {
    auth: new SimpleAuth({
      tokens: {
        [process.env.WORKER_TOKEN!]: {
          id: 'worker',
          name: 'Orchestration Worker',
          role: 'worker',
        },
      },
    }),
  },
  // ... storage, pubsub, etc.
})
```

### 設定 Worker 權杖 {/* #set-the-worker-token */}

在各個 Worker 容器內，將 `MASTRA_WORKER_AUTH_TOKEN` 設為伺服器的身分驗證 Provider 能識別的權杖：

```yaml title="docker-compose.yml"
services:
  api:
    environment:
      WORKER_TOKEN: ${WORKER_TOKEN}
      # ... other env vars

  orchestration-worker:
    environment:
      MASTRA_WORKER_AUTH_TOKEN: ${WORKER_TOKEN}
      MASTRA_STEP_EXECUTION_URL: http://api:4111/api # Use HTTPS in production
      # ... other env vars
```

```bash title=".env"
WORKER_TOKEN=sk-worker-secret-token
```

範例以 `http://` 作本機開發用途。正式環境應使用 HTTPS URL，並由服務網格或 Ingress 控制器終止 TLS。可參閱[保安建議](#security-recommendations)。

編排 Worker 會讀取 `MASTRA_WORKER_AUTH_TOKEN`，每次請求執行步驟時，都會在 `Authorization` 標頭傳送 `Bearer` 權杖。

## 身份驗證憑證類型 {/* #auth-credential-types */}

這`HttpRemoteStrategy` supports three credential formats. The default (`bearer`) covers most setups.

### Bearer 權杖 {/* #bearer-token */}

設定 `MASTRA_WORKER_AUTH_TOKEN` 後，此策略便會送出 `Authorization: Bearer <token>`：

```bash
MASTRA_WORKER_AUTH_TOKEN=sk-worker-secret-token
```

### API 金鑰標頭 {/* #api-key-header */}

使用 `x-worker-api-key` 標頭代替 `Authorization` 傳送憑證：

```typescript
import { HttpRemoteStrategy } from '@mastra/core/worker'

const strategy = new HttpRemoteStrategy({
  serverUrl: 'http://api:4111/api', // Use HTTPS in production
  auth: { type: 'api-key', key: process.env.WORKER_API_KEY! },
})
```

伺服器的身分驗證 Provider 必須從 `x-worker-api-key` 標頭讀取並核實憑證。

### 自訂標頭 {/* #custom-header */}

使用任何標頭名稱和值：

```typescript
import { HttpRemoteStrategy } from '@mastra/core/worker'

const strategy = new HttpRemoteStrategy({
  serverUrl: 'http://api:4111/api', // Use HTTPS in production
  auth: {
    type: 'header',
    name: 'X-Internal-Service-Key',
    value: process.env.INTERNAL_KEY!,
  },
})
```

## 推送模式下的 Broker 身分驗證 {/* #push-mode-broker-auth */}

使用推送模式的 PubSub（例如 Google Cloud Pub/Sub）時，Broker 會將事件直接 POST 到 `/api/workflows/events` 端點，並附上自身憑證。例如，Google Cloud Pub/Sub 會送出經 Google 簽署的 OIDC 權杖。

身分驗證 Provider 的 `authenticateToken` 回調必須能識別 Broker 隨附的憑證。驗證方法以 Broker 的文件為準。

## 安全建議 {/* #security-recommendations */}

- **不同類型的 Worker 使用不同權杖。** 這樣可撤銷個別 Worker 的存取權，而不影響其他 Worker。
- **定期更換權杖。** 更新 `WORKER_TOKEN` 環境變數，再重啟受影響的容器。
* **在生產中使用 TLS。**&#x57;orker 到 API 的通訊應透過 HTTPS 進行，以保護傳輸中的令牌。這適用於所有環境，包括 Kubernetes 叢集和 Docker 網路。使用服務網格（例如 Istio、Linkerd）或 TLS 終止入口來加密內部流量。
* **限製網路存取。**&#x6B65;驟執行和事件端點是內部的。如果可能，請使用網路策略或防火牆規則將它們遠離公共網路。
