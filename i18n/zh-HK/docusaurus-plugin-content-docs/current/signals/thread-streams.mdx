# 執行緒串流

執行緒串流會傳送 Agent 在同一[執行緒](/docs/memory/message-history#threads-and-resources)內各次執行的輸出。只需訂閱一次，即可收取載有模型文字、Tool 呼叫和結果、審批請求及錯誤的[資料區塊](/reference/streaming/ChunkType)。訂閱會在各次執行之間保持開啟，毋須每次傳送輸入時另建回應串流。

開始訂閱時亦可要求讀取已儲存的訊息，讓應用程式先顯示已有的對話，再顯示新輸出。

## 快速入門 {/* #quickstart */}

請在傳送輸入前訂閱，這樣便可從執行開始時收到輸出。此範例使用 JavaScript 用戶端 SDK 的 [`subscribeToThread()`](/reference/client-js/agents#subscribetothread)，需要一部正在運行且設有 `support-agent` Agent 的 Mastra 伺服器。如需儲存訊息紀錄，請為該 Agent 設定 [Memory](/docs/memory/overview)。

如果伺服器端程式碼直接使用 `Agent` 實例，請按 [Agent 快速入門](/docs/signals/overview#use-an-agent) 操作。

```typescript title="src/app/chat.ts"
import { MastraClient } from '@mastra/client-js'

const client = new MastraClient({ baseUrl: 'http://localhost:4111' })
const agent = client.getAgent('support-agent')

const subscription = await agent.subscribeToThread({
  resourceId: 'user-123',
  threadId: 'thread-456',
})

await agent.sendMessage({
  message: 'Show the shorter version.',
  resourceId: 'user-123',
  threadId: 'thread-456',
})

await subscription.processDataStream({
  onChunk: chunk => {
    console.log(chunk)
  },
  reconnect: true,
})
```

[`client.getAgent()`](/reference/client-js/mastra-client#methods) 會選取伺服器上的 Agent。Mastra 接受輸入後，[`sendMessage()`](/reference/client-js/agents#sendmessage) 便會返回。[`processDataStream()`](/reference/client-js/agents#subscribetothread) 會將輸出交給 `onChunk`，範例中由它印出每個資料區塊。回覆完成後，串流仍會繼續監聽。

## 讀取串流 {/* #read-the-stream */}

### 已儲存的訊息紀錄和即時片段 {/* #stored-history-and-live-parts */}

傳入 `withInitialHistory: true`，串流便會以 `thread-history` 資料區塊開始，載有最新一頁的已儲存訊息，並由舊至新排列。`perPage` 預設為 40。訂閱者接着會收到比該頁紀錄更新且仍然保留的片段，然後收到即時片段。訊息紀錄需要記憶功能；如未有啟用，或執行緒尚未有訊息，第一個區塊仍會送達，但 `messages` 陣列會是空的。

### 資料區塊和執行 {/* #chunks-and-runs */}

用 `runId` 將同一次執行的資料區塊分組。[`thread-history`](/reference/streaming/ChunkType#thread-history) 屬例外：它的訊息可能來自多次執行，因此 `runId` 為空。訂閱的 [`activeRunId()`](/reference/agents/agent#subscribetothreadoptions) 會傳回目前執行的 ID，或傳回 `null`。

公開的訂閱串流包含 `AgentChunkType`。`withInitialHistory` 會加入 `ThreadHistoryChunk`，而 `withRunStatus: true` 會加入 `ThreadRunStatusChunk`。兩個選項均預設為 `false`。[ChunkType 參考文件](/reference/streaming/ChunkType)列出模型輸出、Tool 呼叫及結果、審批、中止和錯誤的欄位。如要查看佇列數量，請另行使用 [`subscribeThreadEvents()`](/reference/signals/thread-events)。

### 判斷執行何時完結 {/* #detect-when-a-run-finishes */}

如要接收執行結果，請傳入 `withRunStatus: true`。現有訂閱預設不會收到這類資料區塊。

```typescript
const subscription = await agent.subscribeToThread({
  resourceId: 'user-123',
  threadId: 'thread-456',
  withRunStatus: true,
})
```

[`thread-run-status`](/reference/streaming/ChunkType#thread-run-status) 資料區塊會獨立於執行輸出，指出執行結果：

```typescript
const chunk = {
  type: 'thread-run-status',
  runId: 'run-123',
  from: 'AGENT',
  payload: { status: 'success' },
}
```

`status` 可為 `success`、`failed`、`aborted` 或 `suspended`。即時輸出會在狀態之前到達。暫停後可恢復執行，同一次執行稍後仍可送出更多輸出和最終狀態。執行結果不會關閉執行緒訂閱，訂閱會繼續監聽之後的執行。

啟用 `withInitialHistory` 後，第一個資料區塊帶有 `{ messages, hasMore, activeRunId }`。`activeRunId` 標明載入初始資料時持有執行緒的執行，執行緒閒置時則為 `null`。請用 `thread-run-status` 判斷結果；執行緒閒置本身並不表示成功。

啟用 `withRunStatus: true` 後，即使執行在訂閱前已完結，文字亦已存入紀錄，只要結果仍然保留便會送達。稍後才訂閱並同時開啟兩個選項的訂閱者，會就每次已完結且結果仍然保留的執行收到一個狀態，包括初始紀錄頁以外的執行，並非只收到最近一次的狀態。最終結果在每次訂閱內去除重複；暫停通知則按執行區段去除重複。重新連線會建立新訂閱，因此可能再次收到同一結果。請按 `runId` 將更新分組，不要把每次送達都視為新回覆。

### 審批 Tool 呼叫 {/* #approve-tool-calls */}

執行暫停以等待 Tool 審批時，請透過 [`client.getAgent().sendToolApproval()`](/reference/client-js/agents#sendtoolapproval) 或[伺服器審批路由](/reference/server/routes#subscription-tool-approval-routes)傳送決定。執行恢復後，現有訂閱會收到輸出。

暫停的執行仍持有執行緒，直至恢復或中止為止。在這期間，嘗試啟動新執行的訊號會收到 `accepted` 回應，動作為 `blocked`。再次訂閱時，待審批請求和暫停通知會重播，已完成並儲存的輸出則不會重播。設有 `withRunStatus: true` 時，仍然保留的執行結果會送達。[Agent 何時看到輸入](/docs/signals/sending-signals#when-the-agent-sees-your-input)說明執行期間收到輸入時的中斷和等待規則。

### 篩選訂閱內的訊號 {/* #filter-signals-in-a-subscription */}

`hideSignals` 只會篩選單一訂閱者收到的訊號區塊。傳入 `true` 會隱藏所有可辨識訊號，傳入 `false` 則會顯示這些訊號，亦可傳入訊號類型陣列。此選項不會改變模型上下文、已儲存的訊息或共用廣播，也不影響其他訂閱者，並不構成安全邊界。它只適用於程序內的核心訂閱；HTTP 和 `client-js` 訂閱請求並不支援。

## 停止執行或關閉訂閱 {/* #stop-a-run-or-close-a-subscription */}

[`abort()`](/reference/client-js/agents#subscribetothread) 會要求取消目前的執行。`unsubscribe()` 只關閉訂閱，執行會繼續，你可稍後再次訂閱。中止執行後仍會保留待處理訊號，除非傳入 `clearPendingSignals: true`。

## 重新連線 {/* #reconnect */}

長期訂閱應使用 `reconnect: true`。當傳輸連線關閉，或重新連線的請求失敗時，`processDataStream()` 會重新訂閱，預設每隔一秒重試，次數不限。收到 `408`、`429` 以外的 4xx 回應，或收到 `501` 時，會停止重新連線並拒絕 Promise。重試選項詳見 [`subscribeToThread()` 參考文件](/reference/client-js/agents#subscribetothread)。

重新連線可以接續共用 [PubSub 後端](/docs/server/pubsub)仍然保留的輸出，但無法取回只存在於另一程序記憶體快取內的事件。如需要對話紀錄，可透過 `withInitialHistory` 重新載入最新一頁的已儲存訊息。

已儲存的訊息並無記錄串流內的每個文字片段。重新連線不會重播已完成並儲存的輸出，也不能重建未獲保留的片段。

能否取回執行結果由 PubSub 後端的保留設定決定，與紀錄頁的大小無關。修剪已儲存的輸出時，Redis Streams 會保留精簡的終止事件和執行權限中繼資料，但所設定的串流長度及閒置 TTL 仍可能令這些資料被清除。這並非永久的執行審計日誌，亦無保證的保留時段。如要在修剪後仍可取回結果，請同時升級 `@mastra/core` 和 `@mastra/redis-streams`。較舊的適配器可能會在刪除輸出時連同終止事件一併刪除。

### 自訂端點的 SSE 心跳 {/* #sse-heartbeats-for-custom-endpoints */}

如果為執行緒訂閱提供自訂的伺服器傳送事件（SSE）端點，請在串流閒置時定期傳送心跳訊框，以防瀏覽器、代理伺服器或負載平衡器在下一個訊號或模型資料區塊到達前關閉連線。

以下範例每 25 秒會傳送一則 SSE 註解：

```typescript title="src/api/subscribe.ts"
const heartbeat = setInterval(() => {
  controller.enqueue(encoder.encode(': keep-alive\n\n'))
}, 25_000)

request.signal.addEventListener('abort', () => {
  clearInterval(heartbeat)
})
```

請同時使用心跳和用戶端的重新連線機制。心跳可減少閒置斷線；如果網絡或執行環境仍然關閉串流，重新連線便可恢復連接。
