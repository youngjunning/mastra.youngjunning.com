# 跨進程運行

運行多個 Mastra 進程時，收到訊號的進程未必是正在運行 Agent 的進程。各進程須互相傳遞輸入，並協調由哪個進程運行指定[線程](/docs/memory/message-history#threads-and-resources)。

Mastra 使用共用的 [PubSub](/docs/server/pubsub) 後端在進程之間傳送訊號。[租約](/reference/pubsub/lease-provider)讓一個進程在限定時間內負責線程。共用儲存空間保存對話記錄。多個進程可處理同一線程時，三者缺一不可。

## 為何需要共用後端 {/* #why-you-need-a-shared-backend */}

預設的 [`EventEmitterPubSub`](/reference/pubsub/event-emitter) 在單一進程內傳送事件，可供單一伺服器使用，但無法傳送至其他實例。

假設兩個 API 實例共用一個資料庫。用戶在 A 啟動執行，但下一則訊息送到 B。沒有共用後端時，B 無法將訊息發佈至 A 的執行，便會在同一線程啟動第二次執行。兩次執行都會調用模型及寫入訊息，造成競爭。

有共用後端後，B 可向線程主題發佈訊息，由 A 接收並處理。租約確保只有一個進程可取得線程的控制權，其餘進程會將訊息轉送給它。

可處理同一線程的所有實例均須使用相同的 PubSub 後端和儲存空間。即使使用同一資料庫，不同後端亦無法協調。

## 選擇拓撲 {/* #choose-a-topology */}

按進程運行的位置選擇後端。

| 部署方式 | 後端 | 提供的功能 |
| - | - | - |
| 單一進程 | [`EventEmitterPubSub`](/reference/pubsub/event-emitter)（預設） | 進程內傳送及租約 |
| 同一主機上的多個進程 | [`UnixSocketPubSub`](/reference/pubsub/unix-socket-pubsub) | 透過 Unix 域通訊端傳送事件及提供租約 |
| 多部主機 | [`RedisStreamsPubSub`](/reference/pubsub/redis-streams) 或 [`ValkeyStreamsPubSub`](/reference/pubsub/valkey-streams) | 跨主機傳送、事件保留及租約 |
| 多部主機使用 Google Cloud Pub/Sub | [`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub) | 跨主機傳送，沒有租約 |

[`UnixSocketPubSub`](/reference/pubsub/unix-socket-pubsub) 會選出一個進程作為通訊端代理，一旦該進程退出就重新選擇。它不能跨機器運作。

[`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub) 可跨進程傳送事件，但沒有實作租約。Mastra 無法判斷線程由哪個實例持有，所以任何收到訊號的實例都可嘗試運行它。只有其他層能確保每個線程僅由一個進程運行時，才可使用此後端。

## 線程控制權和租約 {/* #thread-ownership-and-leases */}

Mastra 在啟動執行前會取得租約。只有租約持有者可運行該線程，其他進程會將訊號轉送給它。

租約預設有效期為 15 秒，持有者每 5 秒續約一次。續約間隔是租約存留時間（TTL）的三分之一，讓持有者錯過續約時，有時間在租約到期前補救。如要更改數值，請參閱[設定](#configuration)。

若續約失敗而且本機期限已過，持有者會停止執行。它已無法確認是否有其他進程取得控制權，繼續執行可能導致兩個持有者寫入同一段對話。新的持有者隨後會從儲存空間開始下一次執行。

當 Workflow 儲存後端不支援執行隔離（run fencing）時，[持久 Agent](/docs/harness/durable-agents#run-ownership) 會使用相同的租約。支援隔離的後端會記錄控制權，並拒絕由已失去控制權的執行發出的寫入。介面合約詳見 [`LeaseProvider` 參考文件](/reference/pubsub/lease-provider)。

## 將訊號轉送至其他進程 {/* #route-signals-to-another-process */}

訊號到達時，執行環境會查找線程目前的持有者。若已有進程宣告持有線程，訊號會發佈至線程主題，由持有者接續目前的執行，或從佇列啟動一次執行。

若未有進程宣告持有線程，接收進程會嘗試取得控制權。成功後便可運行 Agent。如其他進程搶先取得控制權，接收進程會轉送訊號，`accepted` 會解析為 `deliver` 而非 `wake`。結果詳見 [`sendSignal()`](/reference/agents/agent#sendsignalsignal-options)。

若閒置喚醒不得在任意實例啟動執行，請設定 `ifIdle.requireClaimedOwner: true`。喚醒只會傳送至已宣告的持有者，如在探索時限內沒有回應，`accepted` 會被拒絕。

## 傳送保證及重複傳送 {/* #delivery-guarantees-and-duplicates */}

PubSub 後端可能在逾時、確認失敗或崩潰後重送事件，因此執行環境假設事件至少傳送一次。只要持有者保留處理記錄，重送的訊號就不會為同一則邏輯訊息啟動第二次執行。

這並不保證每個事件恰好傳送一次。若處理程式會寫入資料庫或觸發其他操作，請確保它具備冪等性，即處理同一事件兩次的效果與處理一次相同。

## 訊號與進程崩潰 {/* #signals-and-process-crashes */}

進程崩潰後可保留哪些資料，取決於資料存放的位置：

- 執行環境的佇列位於進程記憶體。進程若在執行取用訊號前崩潰，這些訊號便會遺失。
- 使用 `persist` 行為傳送的訊號會寫入 Memory 儲存空間。若此空間由各進程共用，重啟後仍會保留訊號。
- [狀態訊號](/docs/signals/state-signals)及其追蹤記錄儲存在所屬線程。使用共用儲存空間時，重啟後仍會保留。
- [通知](/docs/signals/notifications)是通知儲存空間中的持久記錄，派送程式可在重啟後重試傳送。
- 共用 PubSub 後端負責傳送事件，不能充當持久的輸入佇列。已保留的事件可協助訂閱者重新連接，但不能取代儲存空間。
- 持久 Agent 會從檢查點恢復執行，崩潰進程記憶體內的訊號佇列無法復原。

若接收進程終止後仍須保留訊號，請將訊號持久儲存，或在自己的系統記錄。請勿依賴 PubSub 的事件保留功能作為正式記錄。

## 無伺服器 {/* #serverless */}

無伺服器函數回傳回應後可能立即凍結。如函數啟動了執行，請持續讀取輸出串流，讓函數保持運行，直到執行完成。

將工作交給平台的 `waitUntil`，讓它在傳回 HTTP 回應後繼續執行：

```typescript title="src/routes/signal.ts"
const result = agent.sendSignal(signal, { resourceId, threadId })

ctx.waitUntil(
  result.accepted.then(async accepted => {
    if (accepted.action === 'wake') {
      await accepted.output.consumeStream()
    }
  }),
)
```

若線程由其他進程持有，`accepted` 會解析為 `deliver`，本機毋須讀取輸出。若本次調用取得租約，就會收到 `wake`，並須保持運行直至輸出結束。

在無伺服器平台亦應使用共用的 PubSub 後端及儲存空間。實例的生命周期較短，記憶體內的佇列特別容易遺失。

## 正常關閉 {/* #graceful-shutdown */}

停止接收新的 webhook 或訊號請求，再等候現有工作完成。所產生的 Mastra 伺服器會處理 `SIGINT` 及 `SIGTERM`，停止接收新連線，處理完現有請求後調用 [`mastra.shutdown()`](/docs/deployment/mastra-server#graceful-shutdown-and-rolling-deploys)。如將 Mastra 嵌入自己的伺服器，請在關閉掛鈎中調用此方法。

訊號 Provider 有自己的生命周期。調用 [`provider.stop()`](/reference/signals/signal-provider#stop) 以停止輪詢並清除記憶體內的訂閱。關閉前請停止將 webhook 轉送至 [`WebhookSignalProvider`](/reference/signals/webhook-signal-provider)，避免進程退出時收到新請求。

## 設定 {/* #configuration */}

共用的 Redis Streams 後端同時負責傳送訊號及管理線程租約：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { PostgresStore } from '@mastra/pg'
import { RedisStreamsPubSub } from '@mastra/redis-streams'

export const mastra = new Mastra({
  agents: { agent },
  storage: new PostgresStore({
    id: 'mastra-storage',
    connectionString: process.env.DATABASE_URL,
  }),
  pubsub: new RedisStreamsPubSub({
    url: process.env.REDIS_URL,
    keyPrefix: 'mastra:my-app',
  }),
})
```

各實例的 `storage` 須指向同一資料庫。持久儲存的訊號、狀態訊號及通知記錄在重啟後仍會保留，並可由持有線程的進程讀取。

參與協調的實例須使用相同的 `keyPrefix`。多個環境共用同一部 Redis 伺服器時，各環境須使用不同前綴。Vercel 託管的 Redis 及 Upstash Redis 均可配合 `RedisStreamsPubSub` 使用。

租約透過以下環境變數設定：

- `MASTRA_AGENT_THREAD_LEASE_TTL_MS` 設定租約有效期，預設為 `15000` 毫秒。
- `MASTRA_AGENT_THREAD_LEASE_RENEW_INTERVAL_MS` 設定續約間隔，預設為 TTL 的三分之一。若設定值等於或大於 TTL，便會採用預設值。

各實例的這兩項設定須一致。較短的 TTL 會在持有者崩潰後更快釋放線程，但可容許的續約延誤較少。較長的 TTL 則相反。除非部署有需要，否則保留預設值。其他後端詳見 [`RedisStreamsPubSub` 參考文件](/reference/pubsub/redis-streams)。
