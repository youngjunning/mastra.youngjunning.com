# 通知

通知記錄Agent程式要處理的事件，例如失敗的建置、拉取請求評論或已完成的後台作業。 Mastra 將其儲存在持久的收件匣中，與對話訊息分開。即使客服人員到達時正忙，該事件仍然可用。

傳遞策略決定是否立即發送事件、將其與其他事件匯總或留待稍後發送。客服人員使用收件匣讀取、忽略或存檔記錄。傳遞可能會失敗，且策略可能會丟棄事件，因此儲存記錄並不能保證Agent會對其採取行動。這[Notifications reference](/reference/signals/notifications) describes the record lifecycle and policy options.

對需要此收件匣和傳遞行為的事件使用通知。使用[`sendMessage()`](/reference/agents/agent#sendmessagemessage-options) for user input, a [state signal](/docs/signals/state-signals)用於更改應用程式上下文，或[瞬態無功訊號](/docs/signals/sending-signals#send-context-from-a-system)用於一個模型請求所需的上下文。[`sendSignal({ type: 'notification' })`](/reference/agents/agent#sendsignalsignal-options)發送事件上下文而不建立收件匣記錄或提供其重試。

## 快速入門 {/* #quickstart */}

稱呼[`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options) to create the record and apply its delivery policy. To let the agent read pending records, add [`createNotificationInboxTool()`](/reference/signals/create-notification-inbox-tool) as shown in [Work with the inbox](#work-with-the-inbox).

記錄需要一個儲存適配器`notifications` domain. This example uses libSQL, subscribes to the thread first, then sends a high-priority CI failure:

```typescript title="src/mastra/notifications.ts"
import { Mastra } from '@mastra/core'
import { Agent } from '@mastra/core/agent'
import { LibSQLStore } from '@mastra/libsql'
import { Memory } from '@mastra/memory'

const storage = new LibSQLStore({
  id: 'mastra',
  url: 'file:./mastra.db',
})

const ciAgent = new Agent({
  id: 'ci-agent',
  name: 'CI Agent',
  instructions: 'Triage CI failures and explain what broke.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory({ storage }),
})

const mastra = new Mastra({
  agents: { ciAgent },
  storage,
})

const agent = mastra.getAgent('ciAgent')
const thread = {
  resourceId: 'user_123',
  threadId: 'thread_456',
}

const subscription = await agent.subscribeToThread(thread)

const { record, decision } = await agent.sendNotificationSignal(
  {
    source: 'github',
    kind: 'ci-status',
    priority: 'high',
    summary: 'CI failed on main: 3 tests failed in the API suite.',
    payload: {
      repository: 'acme/app',
      branch: 'main',
      runId: '123456',
    },
    dedupeKey: 'github:acme/app:main:ci',
  },
  thread,
)

console.log(record.status, decision.action)

for await (const chunk of subscription.stream) {
  console.log(chunk)

  if (chunk.type === 'finish') break
}
```

在空閒執行緒上，高優先權通知會立即傳遞並開始運作。在活動執行緒上，Mastra 首先對其進行匯總，然後在執行緒空閒時傳遞完整的通知。訂閱會同時收到摘要和完整通知：[thread stream](/docs/signals/thread-streams) chunks.

## 通知記錄 {/* #notification-records */}

當通知到達時，`sendNotificationSignal()` creates a record or merges it into a matching pending record. It then checks the delivery policy. If delivery is scheduled for later, the dispatcher reads the record when it's due and sends the notification or a summary.

儲存的記錄包括路由、優先權、狀態、投遞嘗試和原始記錄`payload`. The model receives an XML element built from `summary` and attributes. It doesn't receive `payload` automatically.

記錄的狀態可以是`pending`, `delivered`, `seen`, `dismissed`, `archived`, `discarded`, or `failed`. A summarized record stays `pending`, because a summary tells the model that records exist without marking them delivered. The reference lists every [記錄字段](/reference/signals/notifications#notification-records)和[地位](/reference/signals/notifications#priorities-and-statuses).

## 建立和合併記錄 {/* #create-and-coalesce-records */}

`sendNotificationSignal()`接受一個通知或一組通知。每個項目都是獨立建立的，然後儲存決定是否可以合併到現有的待處理記錄中。

使用`dedupeKey` to identify one event that may arrive more than once. Use `coalesceKey` to group related events into one pending record, a process called coalescing. Both keys use the same matching rules.

合併僅考慮同一執行緒、來源、種類、Agent和資源上仍待處理的記錄。這[Notifications reference](/reference/signals/notifications#coalescing-pending-records) documents the fields that merge and their precedence.

## 儲存和調度程序設置 {/* #storage-and-dispatcher-setup */}

通知記錄需要一個儲存適配器`notifications` domain: [libSQL](/integrations/databases/libsql), [PostgreSQL](/integrations/databases/postgresql), or [MongoDB](/integrations/databases/mongodb). Without it, `sendNotificationSignal()` throws instead of silently dropping the record.

預設啟用計劃調度並透過Workflow調度程序運行。將其配置在`Mastra` instance:

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  agents: { ciAgent },
  storage,
  notifications: {
    dispatch: {
      enabled: true,
      cron: '*/1 * * * *',
      batchSize: 100,
    },
  },
})
```

預設值是`enabled: true`, `cron: '*/1 * * * *'` (once per minute), and `batchSize: 100`. Only apps that defer or summarize a notification create the lazy dispatch schedule and activate the workflow scheduler with it. Set `enabled: false` to opt out.

## 出貨政策 {/* #delivery-policy */}

每筆記錄在收到時都會做出決定，並且可能在發送時再次做出決定。內建策略使用優先權和執行緒狀態：

|優先|空閒執行緒|活動執行緒 |
| - | - | - |
|`urgent` | Deliver immediately | Deliver immediately |
| `high` | Deliver immediately | Summarize now, then deliver when idle |
| `medium` | Deliver immediately | Batch into a summary |
| `low` | Batch into a summary | Batch into a summary |

當預設值不適合時，在Agent上配置策略。來源規則在優先權規則之前運行，因此可以在其他所有內容交付的同時匯總噪音源：

```typescript title="src/mastra/agents/ci-agent.ts"
import { Agent } from '@mastra/core/agent'
import { Memory } from '@mastra/memory'

// storage from the Quickstart
export const ciAgent = new Agent({
  id: 'ci-agent',
  name: 'CI Agent',
  instructions: 'Triage CI failures and explain what broke.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory({ storage }),
  notifications: {
    deliveryPolicy: {
      sources: {
        github: 'summarize',
      },
      priorities: {
        urgent: 'deliver',
        low: 'discard',
      },
    },
  },
})
```

Mastra 按以下順序評估該政策：

1. 客製化`decide()` function.
2. `sources`, 匹配`record.source`.
3. `priorities`, 匹配`record.priority`.
4. `default`.
5. 內建優先策略。

`decide()`對於第一個決定推遲或安排摘要的記錄，在接收時運行並在交付時再次運行。儲存的時間表確定了他們交付的時間和方式。僅限交付榮譽`streamOptions` and `hold` from the new decision. Keep `decide()` side-effect free.

## 派遣 {/* #dispatch */}

調度員讀取到期記錄，並以以下方式將摘要分組`agentId`, `resourceId`, and `threadId`, and emits signals through the thread runtime.

|決定|結果 |
| - | - |
|`deliver` | Send the full notification immediately |
| `queue` | Keep the record pending for a later dispatch pass |
| `summarize` | Send a summary now or at `summaryAt` |
| `defer` | Keep the record pending until `deliverAt` |
| `persist` | Store the record without sending a signal |
| `discard` | Mark the record discarded |

一個決定與`hold` leaves the record for another process's dispatcher without counting a delivery attempt.

### 摘要 {/* #summaries */}

摘要可防止繁忙的線程接收大量的單獨通知。該模型看到一個緊湊的摘要：

```xml
<notification-summary pending="10">github: 3, email: 5, slack: 2</notification-summary>
```

完整的通知將記錄的摘要作為其內容：

```xml
<notification source="github" kind="ci-status" priority="high" status="delivered">CI failed on main: 3 tests failed in the API suite.</notification>
```

總結一目了然`summaryAt` and sets `summarySignalId`. The records stay `pending` and readable. A full notification sets `deliveredSignalId` and marks the record `delivered`.

摘要不標記已交付的記錄。當Agent程式需要完整內容時，透過收件匣讀取記錄；讀取可注入完整訊號並標記記錄`seen`, preventing duplicate delivery later.

### 重試和失敗 {/* #retries-and-failures */}

失敗的嘗試會增加`deliveryAttempts` and records `lastDeliveryAttemptAt` and `lastDeliveryError`. The record stays pending and is due again on the next dispatch pass.

五次嘗試失敗後，記錄移至`failed` and stops being due. The cap is exported as `MAX_NOTIFICATION_DELIVERY_ATTEMPTS`. A `hold` leaves it pending without counting an attempt, so another dispatcher can pick it up.

如果自訂策略在通知首次到達時拋出，則記錄將保持待處理狀態並立即`deliverAt` and a failed attempt, so the dispatcher can retry it.

## 使用收件匣 {/* #work-with-the-inbox */}

為Agent提供收件匣Tool，以便它可以在不暴露儲存 API 的情況下檢查記錄：

```typescript title="src/mastra/agents/ci-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createNotificationInboxTool } from '@mastra/core/notifications'

const notificationsStorage = await storage.getStore('notifications')

export const ciAgent = new Agent({
  // ...id, instructions, model, memory, and notifications from the policy example
  tools: {
    notificationInbox: createNotificationInboxTool({ storage: notificationsStorage }),
  },
})
```

該Tool支援`list`, `read`, `search`, `markSeen`, `dismiss`, and `archive`. Listing and searching mark returned unread records `seen`, including `failed` records so the agent learns delivery gave up. `list` defaults to pending, delivered, and failed records. `search` spans all statuses. `read` only acts on pending and delivered records, so it skips `failed` ones. A record `read` can't deliver, because neither the record nor the calling agent supplies a `resourceId`, stays pending.

`read`總結後的事項。它將所選記錄的完整內容作為通知信號而不是普通Tool輸出提供。即使呼叫傳回了簡短的狀態訊息，Agent也可以看到線程上的上下文。

## Agent和客戶端介面 {/* #agent-and-client-surfaces */}

[`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options)是建立持久通知記錄的規範方法。它會傳回記錄和策略決定，包括`accepted`, `signal`, and `persisted` when a signal was emitted, matching the other signal methods described in [Sending signals](/docs/signals/sending-signals).

JavaScript 用戶端 SDK 可以透過以下方式傳送通知形狀的上下文[`client.getAgent().sendSignal()`](/reference/client-js/agents#sendsignal). That path bypasses inbox storage, so use it only when the event needs no record, retries, or later reading. Durable records over HTTP go through the AgentController Session notification route, which forwards to `sendNotificationSignal()`. See the [Session reference](/reference/agent-controller/session) and [Agent Controller](/docs/harness/agent-controller).
