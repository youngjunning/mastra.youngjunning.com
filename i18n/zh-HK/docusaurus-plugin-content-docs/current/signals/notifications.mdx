# 通知

通知記錄需要 Agent 處理的事件，例如建置失敗、pull request 留言或背景工作完成。Mastra 將通知持久保存在獨立於對話訊息的收件箱。即使 Agent 在通知到達時正忙，事件亦會保留。

傳送策略決定立即傳送事件、將事件連同其他事件整理成摘要，還是留待稍後處理。Agent 可在收件箱讀取、略過或封存記錄。傳送可能失敗，策略亦可捨棄事件，因此保存記錄並不保證 Agent 會處理事件。記錄的生命週期及策略選項見[通知參考](/reference/signals/notifications)。

事件需要收件箱及傳送機制時，可使用通知。用戶輸入使用 [`sendMessage()`](/reference/agents/agent#sendmessagemessage-options)，應用程式上下文變更使用[狀態訊號](/docs/signals/state-signals)，單次模型請求所需的上下文則使用[暫態反應式訊號](/docs/signals/sending-signals#send-context-from-a-system)。[`sendSignal({ type: 'notification' })`](/reference/agents/agent#sendsignalsignal-options) 會傳送事件上下文，但不會建立收件箱記錄或提供相應的重試機制。

## 快速入門 {/* #quickstart */}

調用 [`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options) 建立記錄並套用傳送策略。如需讓 Agent 讀取待處理記錄，請按[使用收件箱](#work-with-the-inbox)的做法加入 [`createNotificationInboxTool()`](/reference/signals/create-notification-inbox-tool)。

通知記錄需要支援 `notifications` 領域的儲存轉接器。以下例子使用 libSQL，先訂閱對話串，再傳送一則高優先級的 CI 失敗通知：

```typescript title="src/mastra/notifications.ts"
import { Mastra } from '@mastra/core'
import { Agent } from '@mastra/core/agent'
import { LibSQLStore } from '@mastra/libsql'
import { Memory } from '@mastra/memory'

const storage = new LibSQLStore({
  id: 'mastra',
  url: 'file:./mastra.db',
})

const ciAgent = new Agent({
  id: 'ci-agent',
  name: 'CI Agent',
  instructions: 'Triage CI failures and explain what broke.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory({ storage }),
})

const mastra = new Mastra({
  agents: { ciAgent },
  storage,
})

const agent = mastra.getAgent('ciAgent')
const thread = {
  resourceId: 'user_123',
  threadId: 'thread_456',
}

const subscription = await agent.subscribeToThread(thread)

const { record, decision } = await agent.sendNotificationSignal(
  {
    source: 'github',
    kind: 'ci-status',
    priority: 'high',
    summary: 'CI failed on main: 3 tests failed in the API suite.',
    payload: {
      repository: 'acme/app',
      branch: 'main',
      runId: '123456',
    },
    dedupeKey: 'github:acme/app:main:ci',
  },
  thread,
)

console.log(record.status, decision.action)

for await (const chunk of subscription.stream) {
  console.log(chunk)

  if (chunk.type === 'finish') break
}
```

對話串閒置時，高優先級通知會即時傳送並啟動一次執行。對話串活躍時，Mastra 先整理摘要，待對話串閒置後再傳送完整通知。訂閱會以[對話串串流](/docs/signals/thread-streams)區塊的形式收到摘要及完整通知。

## 通知記錄 {/* #notification-records */}

收到通知時，`sendNotificationSignal()` 會建立記錄，或將通知合併到相符的待處理記錄，然後檢查傳送策略。如安排稍後傳送，派送器會在到期時讀取記錄並傳送通知或摘要。

儲存的記錄包括路由資料、優先級、狀態、傳送嘗試及原始 `payload`。模型收到由 `summary` 和屬性組成的 XML 元素，系統不會自動傳送 `payload`。

記錄的狀態包括 `pending`、`delivered`、`seen`、`dismissed`、`archived`、`discarded` 或 `failed`。傳送摘要後，記錄仍維持 `pending`，因為摘要只會讓模型知道有這些記錄，並不會標記為已傳送。所有[記錄欄位](/reference/signals/notifications#notification-records)及[狀態](/reference/signals/notifications#priorities-and-statuses)均列於參考文件。

## 建立及合併記錄 {/* #create-and-coalesce-records */}

`sendNotificationSignal()` 接受單則通知或通知陣列。每個項目會獨立建立，再由儲存層決定可否合併到現有的待處理記錄。

使用 `dedupeKey` 識別可能多次到達的同一事件，或用 `coalesceKey` 將相關事件合併為一筆待處理記錄。兩種鍵採用相同的配對規則。

只有尚待處理，而且對話串、來源、種類、Agent 及資源都相同的記錄才可合併。可合併的欄位及其優先次序見[通知參考](/reference/signals/notifications#coalescing-pending-records)。

## 設定儲存及派送器 {/* #storage-and-dispatcher-setup */}

通知記錄需要支援 `notifications` 領域的儲存轉接器：[libSQL](/integrations/databases/libsql)、[PostgreSQL](/integrations/databases/postgresql) 或 [MongoDB](/integrations/databases/mongodb)。若欠缺該領域，`sendNotificationSignal()` 會拋出錯誤，避免記錄在沒有提示下被捨棄。

定時派送預設啟用，由 Workflow 排程器執行。請在 `Mastra` 實例設定：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  agents: { ciAgent },
  storage,
  notifications: {
    dispatch: {
      enabled: true,
      cron: '*/1 * * * *',
      batchSize: 100,
    },
  },
})
```

預設值為 `enabled: true`、`cron: '*/1 * * * *'`（每分鐘一次）及 `batchSize: 100`。只有在延後傳送通知或整理通知摘要時，應用程式才會按需要建立派送排程，並啟用 Workflow 排程器。設為 `enabled: false` 即可停用。

## 傳送策略 {/* #delivery-policy */}

每筆記錄在收到時都會按策略作出決定，派送時可能再次判定。內置策略根據優先級及對話串狀態決定：

| 優先級 | 閒置對話串 | 活躍對話串 |
| - | - | - |
| `urgent` | 即時傳送 | 即時傳送 |
| `high` | 即時傳送 | 先傳送摘要，待閒置後再傳送通知 |
| `medium` | 即時傳送 | 批次整理成摘要 |
| `low` | 批次整理成摘要 | 批次整理成摘要 |

如預設行為不合用，可在 Agent 設定策略。系統會先套用來源規則，再套用優先級規則，因此可為事件過多的來源整理摘要，其餘通知照常傳送：

```typescript title="src/mastra/agents/ci-agent.ts"
import { Agent } from '@mastra/core/agent'
import { Memory } from '@mastra/memory'

// storage from the Quickstart
export const ciAgent = new Agent({
  id: 'ci-agent',
  name: 'CI Agent',
  instructions: 'Triage CI failures and explain what broke.',
  model: '__GATEWAY_OPENAI_MODEL__',
  memory: new Memory({ storage }),
  notifications: {
    deliveryPolicy: {
      sources: {
        github: 'summarize',
      },
      priorities: {
        urgent: 'deliver',
        low: 'discard',
      },
    },
  },
})
```

Mastra 按以下次序評估策略：

1. 自訂 `decide()` 函數。
1. `sources`，以 `record.source` 配對。
1. `priorities`，以 `record.priority` 配對。
4. `default`.
1. 內置優先級策略。

`decide()` 在收到記錄時執行。若首次決定延後傳送或安排摘要，便會在傳送時再執行一次。已儲存的排程決定傳送時間及方式，傳送時只採用新決定的 `streamOptions` 及 `hold`。請確保 `decide()` 沒有副作用。

## 派送 {/* #dispatch */}

派送器讀取到期記錄，按 `agentId`、`resourceId` 及 `threadId` 將摘要分組，再經對話串的執行環境發出訊號。

| 決定 | 結果 |
| - | - |
| `deliver` | 即時傳送完整通知 |
| `queue` | 維持待處理，留待之後派送 |
| `summarize` | 即時傳送摘要，或在 `summaryAt` 傳送 |
| `defer` | 維持待處理，直至 `deliverAt` |
| `persist` | 只儲存記錄，不發出訊號 |
| `discard` | 將記錄標記為已捨棄 |

決定包含 `hold` 時，記錄會留給另一個程序的派送器，並不計作一次傳送嘗試。

### 摘要 {/* #summaries */}

摘要可避免繁忙的對話串一下子收到大量個別通知。模型會收到一份簡短摘要：

```xml
<notification-summary pending="10">github: 3, email: 5, slack: 2</notification-summary>
```

完整通知以記錄的摘要作為內容：

```xml
<notification source="github" kind="ci-status" priority="high" status="delivered">CI failed on main: 3 tests failed in the API suite.</notification>
```

傳送摘要會清除 `summaryAt` 並設定 `summarySignalId`，記錄維持 `pending`，亦可繼續讀取。傳送完整通知則會設定 `deliveredSignalId`，並將記錄標記為 `delivered`。

傳送摘要不會將記錄標記為已傳送。Agent 需要完整內容時，可從收件箱讀取記錄。讀取時可注入完整訊號，並將記錄標記為 `seen`，避免日後重複傳送。

### 重試及失敗 {/* #retries-and-failures */}

傳送失敗會增加 `deliveryAttempts`，並記錄 `lastDeliveryAttemptAt` 及 `lastDeliveryError`。記錄維持待處理狀態，在下一輪派送時再試。

嘗試失敗五次後，記錄會轉為 `failed`，不再派送。這個上限以 `MAX_NOTIFICATION_DELIVERY_ATTEMPTS` 匯出。`hold` 會保留待處理狀態，並不計作一次嘗試，讓其他派送器可以接手。

如自訂策略在初次收到通知時拋出錯誤，記錄會維持待處理，並將 `deliverAt` 設為即時傳送及記下首次失敗，讓派送器可以重試。

## 使用收件箱 {/* #work-with-the-inbox */}

為 Agent 提供收件箱 Tool，即可讓它查閱記錄，毋須公開儲存 API：

```typescript title="src/mastra/agents/ci-agent.ts"
import { Agent } from '@mastra/core/agent'
import { createNotificationInboxTool } from '@mastra/core/notifications'

const notificationsStorage = await storage.getStore('notifications')

export const ciAgent = new Agent({
  // ...id, instructions, model, memory, and notifications from the policy example
  tools: {
    notificationInbox: createNotificationInboxTool({ storage: notificationsStorage }),
  },
})
```

這個 Tool 支援 `list`、`read`、`search`、`markSeen`、`dismiss` 及 `archive`。列出或搜尋時，傳回的未讀記錄會標記為 `seen`，包括 `failed` 記錄，以便 Agent 得知系統已停止傳送。`list` 預設傳回待處理、已傳送及失敗的記錄，`search` 涵蓋所有狀態。`read` 只處理待處理及已傳送的記錄，所以會略過 `failed` 記錄。若記錄及調用的 Agent 均無提供 `resourceId`，令 `read` 無法傳送，該記錄便會維持待處理。

收到摘要後，可用 `read` 取得完整內容。它會將所選記錄的完整內容以通知訊號傳送，而非作為一般 Tool 輸出。即使調用只傳回簡短的狀態訊息，Agent 仍可在對話串看到相關上下文。

## Agent 及客戶端介面 {/* #agent-and-client-surfaces */}

[`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options) 是建立持久通知記錄的標準方法。它會傳回記錄及策略決定。如有發出訊號，傳回值亦包括 `accepted`、`signal` 及 `persisted`，與[傳送訊號](/docs/signals/sending-signals)內的其他方法一致。

JavaScript 客戶端 SDK 可透過 [`client.getAgent().sendSignal()`](/reference/client-js/agents#sendsignal) 傳送通知格式的上下文。這個方法會繞過收件箱儲存，只適合毋須記錄、重試或稍後讀取的事件。如需經 HTTP 建立持久記錄，可使用 AgentController Session 的通知路由，由它轉交 `sendNotificationSignal()`。詳情見 [Session 參考](/reference/agent-controller/session)及 [Agent Controller](/docs/harness/agent-controller)。
