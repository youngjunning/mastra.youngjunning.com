# 訊號 Provider

訊號 Provider 監察外部系統，並向已訂閱的 Agent 執行緒發送[通知](/docs/signals/notifications)。例如，可監察建置管道，在建置失敗時通知每個訂閱該管道的執行緒。

如果應用程式要管理哪些執行緒接收哪些來源的事件，可以使用 Provider。基礎類別 [`SignalProvider`](/reference/signals/signal-provider) 負責追蹤訂閱、輪詢及轉交通知給 Agent。Provider 的程式碼要負責讀取外部系統，並將事件配對到訂閱，亦可以為 Agent 提供工具及處理器。

如果伺服器已收到事件並知道目標執行緒，直接呼叫 [`agent.sendNotificationSignal()`](/reference/agents/agent#sendnotificationsignalnotification-options) 即可。要更新應用程式的上下文，請使用[狀態訊號](/docs/signals/state-signals)；只供一次模型請求使用的上下文，則用[暫時反應式訊號](/docs/signals/sending-signals#send-context-from-a-system)。

## Provider 如何運作 {/* #how-a-provider-works */}

在 Agent 的 `signals` 陣列註冊 Provider。接收事件有兩種方式：

- **輪詢：** [`poll()`](/reference/signals/signal-provider#polling) 定時檢查外部系統。
- **Webhook：** 由你的伺服器把收到的事件傳給 [`handleWebhook()`](/reference/signals/signal-provider#webhooks)。

Provider 會就每項配對的訂閱呼叫受保護的 [`notify()`](/reference/signals/signal-provider#notifications) 方法。事件會轉交到 `Agent.sendNotificationSignal()`，並按通知的傳送政策、重試及收件匣機制處理。

## 將外部識別碼配對到執行緒 {/* #map-external-identities-to-threads */}

以目標執行緒的 [`resourceId` 和 `threadId`](/docs/memory/message-history#threads-and-resources) 指定通知去向。Provider 亦需要 `externalResourceId` 識別執行緒監察的資源，例如管道 `acme-app-main`。請選用可穩定配對到傳入事件的值。

每項訂閱以這三個值共同識別，因此一個執行緒可以監察多項資源，而同一資源亦可由多個執行緒監察。額外資料應放在 `metadata`，不要放進外部 ID。處理 Webhook 時，先將承載資料與 `externalResourceId` 配對，再以該訂閱的 `resourceId` 和 `threadId` 作為目標。

## 快速入門 {/* #quickstart */}

這個例子會檢查管道的建置狀態，失敗便通知已訂閱的執行緒。`builds` 對應表在例子中代替 CI 服務。請將 `fetchBuildStatus()` 換成對實際服務的呼叫。

使用 Provider 前，先[為 `Mastra` 實例設定通知儲存](/docs/signals/notifications#storage-and-dispatcher-setup)，否則 `notify()` 無法建立記錄。

```typescript title="src/mastra/signals/ci-signals.ts"
import { SignalProvider } from '@mastra/core/signals'
import type { SignalProviderTarget, SignalSubscription } from '@mastra/core/signals'

type BuildStatus = {
  id: string
  status: 'passed' | 'failed'
}

const builds = new Map<string, BuildStatus>([
  ['acme-app-main', { id: 'build_123', status: 'failed' }],
])

async function fetchBuildStatus(pipeline: string): Promise<BuildStatus> {
  return builds.get(pipeline) ?? { id: 'build_unknown', status: 'passed' }
}

export class CiSignals extends SignalProvider<'ci-signals'> {
  readonly id = 'ci-signals' as const
  readonly pollInterval = 30_000

  watch(target: SignalProviderTarget, pipeline: string) {
    return this.subscribe(target, pipeline)
  }

  unwatch(target: SignalProviderTarget, pipeline: string) {
    return this.unsubscribe(target, pipeline)
  }

  async poll(subscriptions: SignalSubscription[]) {
    for (const sub of subscriptions) {
      const build = await fetchBuildStatus(sub.externalResourceId)

      if (build.status !== 'failed') continue

      await this.notify(
        {
          source: this.id,
          kind: 'ci-status',
          priority: 'high',
          summary: `Build failed for ${sub.externalResourceId}`,
          payload: build,
          dedupeKey: `${this.id}:${sub.externalResourceId}:${build.id}`,
        },
        { resourceId: sub.resourceId, threadId: sub.threadId },
      )
    }
  }
}
```

先將 Provider 註冊到 Agent，再讓執行緒訂閱它要監察的管道：

```typescript title="src/mastra/agents/support-agent.ts"
import { Agent } from '@mastra/core/agent'
import { CiSignals } from '../signals/ci-signals'

export const ciSignals = new CiSignals()

export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'Help the user triage CI updates.',
  model: '__GATEWAY_OPENAI_MODEL__',
  signals: [ciSignals],
})

ciSignals.watch({ resourceId: 'user_123', threadId: 'thread_456' }, 'acme-app-main')
```

Agent 連接 Provider 後便會輪詢，並在管道失敗時發出通知。請在 `Mastra` 實例中註冊 `supportAgent`，讓 `notify()` 可以存取通知儲存。

## 建立 Provider {/* #build-a-provider */}

### 連接與訂閱 {/* #connect-and-subscriptions */}

只有在初始化需要用到已連接的 Agent 時，才覆寫 [`connect()`](/reference/signals/signal-provider#connection)。必須先呼叫 `super.connect(agent)`。

透過以下受保護的成員操作訂閱：

- `subscribe(target, externalResourceId, metadata?)` 新增訂閱，或將元資料合併到現有訂閱。
- `unsubscribe(target, externalResourceId)` 移除一項訂閱；`unsubscribeAll(target)` 則移除指定執行緒的所有訂閱。
- `getSubscriptions()`、`getSubscriptionsForResource()`、`getSubscriptionsForThread()`、`hasSubscription()` 及 `subscriptionCount` 可讀取訂閱登記表，用於診斷和條件檢查。

只公開應用程式需要的操作。CI 例子用公開的 `watch()` 和 `unwatch()` 包裝 `subscribe()` 及 `unsubscribe()`。

### 輪詢 {/* #polling */}

來源無法主動推送事件時，請以毫秒設定 `pollInterval` 並實作 `poll(subscriptions)`。

計時器由基礎類別管理：

- 沒有訂閱時便跳過該輪，而且兩輪不會重疊。因此即使 `poll()` 運行較慢，也不會同時執行多次。
- 捕捉並記錄 `poll()` 的錯誤，然後等候下一輪。
- 向計時器呼叫 `unref()`，避免程序單靠輪詢保持運行。

輪詢失敗後，基礎類別不會馬上重試。可等到下一輪重試，或在 `poll()` 內自行加入退避機制。

### Webhook {/* #webhooks */}

如果來源能呼叫你的應用程式，可使用 Webhook。覆寫 `handleWebhook(request)` 來解析承載資料及查找訂閱，並對每個配對項目呼叫 `notify()`：

```typescript title="src/mastra/signals/ci-signals.ts"
import { SignalProvider } from '@mastra/core/signals'
import type { SignalProviderWebhookRequest } from '@mastra/core/signals'

export class CiSignals extends SignalProvider<'ci-signals'> {
  readonly id = 'ci-signals' as const

  async handleWebhook(request: SignalProviderWebhookRequest) {
    const payload = request.body as { pipeline: string; status: string }
    const subscriptions = this.getSubscriptionsForResource(payload.pipeline)

    for (const sub of subscriptions) {
      await this.notify(
        {
          source: this.id,
          kind: 'ci-status',
          priority: 'high',
          summary: `Build ${payload.status} for ${payload.pipeline}`,
          payload,
        },
        { resourceId: sub.resourceId, threadId: sub.threadId },
      )
    }

    return { status: 200, body: { matched: subscriptions.length } }
  }
}
```

`handleWebhook()` 是 Provider 的方法，請由自己的端點呼叫。如果來源要求驗證簽署，須在解析前使用原始請求主體驗證。

### 持久儲存訂閱 {/* #durable-subscriptions */}

基礎類別的訂閱登記表儲存在記憶體，只屬於單一程序內的一個 Provider 實例。重啟後不會保留，不同實例亦無法共用。

如需保留訂閱，請自行儲存，並在 [`start()`](/reference/signals/signal-provider#start) 中載入。第二個程序的登記表在載入自己的訂閱副本前會是空的。

### 生命週期鉤子 {/* #lifecycle-hooks */}

Agent 建構時會呼叫 `connect()` 並啟動輪詢，然後呼叫 `start()`，但不會等它完成。請讓 `start()` 獨立於第一次輪詢，並處理當中的錯誤。

[`stop()`](/reference/signals/signal-provider#stop) 是同步方法。預設實作會停止輪詢及清除所有訂閱索引。如需自行清理資源，可覆寫方法，但請呼叫 `super.stop()` 釋放訂閱登記表：

```typescript oxfmt:false
override stop() {
  this.closeClient()
  super.stop()
}
```

請在關閉流程中呼叫 `stop()`，Agent 不會代為呼叫。如果客戶端需要非同步關閉，請提供非同步關閉方法，待其完成後再呼叫 `stop()`。

### 處理器及工具 {/* #processors-and-tools */}

Provider 可向已連接的 Agent 提供以下功能：

- 從 `getInputProcessors()` 回傳輸入處理器，從 `getOutputProcessors()` 回傳輸出處理器。
- 從 `getTools()` 回傳 Agent 可呼叫的工具。

Agent 在 `connect()` 後只會取得這些項目一次，並將處理器註冊到 Mastra 實例。

### 發送通知 {/* #send-notifications */}

[`notify()`](/reference/signals/signal-provider#notifications) 包裝已連接 Agent 的 `sendNotificationSignal()`，接受相同欄位：`source`、`kind`、`summary`，以及選用的 `priority`、`payload`、`dedupeKey`、`coalesceKey` 和 `attributes`。

同一事件可能重複收到，例如連續兩輪看見同一項建置失敗，可用 `dedupeKey`。若要將相關事件合併為同一項待處理記錄，則用 `coalesceKey`。詳見[通知指南](/docs/signals/notifications#create-and-coalesce-records)的合併規則。

未連接 Provider 時，`notify()` 會擲出例外。儲存錯誤亦會向上傳遞，請交由輪詢或 Webhook 的錯誤處理常式處理。

### 妥善關閉 {/* #shut-down-cleanly */}

關閉時：

1. 停止接收新的 Webhook 工作。
1. 用 `stopPolling()` 或 `stop()` 停止輪詢。
1. 清空訂閱登記表。
1. 關閉或釋放外部客戶端及連線。
1. 如運行環境容許，讓已在處理的 `notify()` 呼叫完成。

基礎類別在 `stop()` 清除登記表，但無法等待處理中的 Webhook 完成，亦無法關閉非同步客戶端。請在關閉流程中協調這些操作。

## 內置 Provider {/* #built-in-providers */}

### 任務訊號 Provider {/* #task-signal-provider */}

只需註冊一次 [`TaskSignalProvider`](/reference/signals/task-signal-provider)，便可同時使用任務工具及 `TaskStateProcessor`。如要讓 Agent 跨對話輪次維護任務清單，可加入它：

```typescript
import { Agent } from '@mastra/core/agent'
import { TaskSignalProvider } from '@mastra/core/signals'

const agent = new Agent({
  // ...
  signals: [new TaskSignalProvider()],
})
```

它提供 `task_write`、`task_update`、`task_complete` 和 `task_check`，以及將任務清單映射到狀態訊號通道的處理器。追蹤任務需要由 Memory 支援的執行緒及一個 `storage` 實例。沒有 Memory 時，工具會提示追蹤功能需要 Agent Memory。

### Webhook 訊號 Provider {/* #webhook-signal-provider */}

通用 Webhook 來源可直接使用 [`WebhookSignalProvider`](/reference/signals/webhook-signal-provider)，毋須編寫子類別。請設定一個擷取資源識別碼的函數，亦可選擇設定一個產生通知的函數：

```typescript title="src/mastra/index.ts"
import { Agent } from '@mastra/core/agent'
import { WebhookSignalProvider } from '@mastra/core/signals'

const webhooks = new WebhookSignalProvider({
  extractResourceId: payload => (payload as { repository: string }).repository,
  buildNotification: (payload, sub) => ({
    source: 'ci',
    kind: 'build-status',
    priority: 'medium',
    summary: `Build ${(payload as { status: string }).status} for ${sub.externalResourceId}`,
  }),
})

export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support Agent',
  instructions: 'Help the user triage updates.',
  model: '__GATEWAY_OPENAI_MODEL__',
  signals: [webhooks],
})

webhooks.subscribeThread({ resourceId: 'user_123', threadId: 'thread_456' }, 'acme/app')
```

在路由中呼叫 `webhooks.handleWebhook({ body, headers })`。Provider 會將擷取到的資源識別碼與訂閱配對，並逐一通知符合條件的執行緒。

未設定 `extractResourceId` 時，會讀取承載資料的 `resource` 或 `externalResourceId`。未設定 `buildNotification` 時，會發送優先級為 `medium` 的 `webhook-event` 通知。

## 正式環境部署核對清單 {/* #production-checklist */}

部署前：

- **避免重試造成重複通知：** 為每個事件指定穩定的 `dedupeKey` 或 `coalesceKey`。Webhook 及輪詢均可能重複送來同一事件，Provider 不會在 `notify()` 前排除重複項目。
- **驗證 Webhook：** 解析前以原始請求主體驗證簽署，並在 HTTP 端點拒絕無效請求。
- **處理事件來源故障：** 輪詢會在下一個間隔重試，有需要可在 `poll()` 加入退避機制。Webhook 來源通常會自行重試，未能接收事件時請回傳非 2xx 狀態碼。
- **按需要持久儲存訂閱：** 登記表存於記憶體。如需在重啟後繼續監察，請在 `start()` 載入訂閱。
- **使用共享儲存：** 通知記錄和傳送政策依賴 Agent 的 Mastra 儲存。
- **安排關閉流程：** 停止接收 Webhook、停止輪詢、關閉客戶端，並讓處理中的通知完成。
- **監察通知佇列：** 摘要與延後傳送依賴[通知分派器](/docs/signals/notifications#dispatch)，尤其使用共享儲存時。
