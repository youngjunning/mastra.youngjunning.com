# 實驗

**引入版本：** `@mastra/core@1.4.0`

實驗會讓數據集中的每個條目經由目標（Agent、Workflow 或 scorer）處理，再選擇性地對輸出評分。如果要評估 LLM 評審器本身，可將 scorer 設為目標。預設情況下，結果會持久化到儲存中，便於比較不同提示詞、模型或代碼變更下的運行。

<Inject>
**供 AI Agent 使用：** 運行 `npx mastra api experiment run dataset_123 '{"name":"translation-baseline"}'`，無需打開 Studio 或編寫臨時腳本即可啟動實驗。請將例子 ID 換成 `npx mastra api dataset list` 返回的 ID。該命令需要一個正在運行的 Mastra 伺服器，並且伺服器已配置數據集儲存、註冊實驗目標。可用 `npx mastra dev` 啟動本地伺服器，或通過 `--url` 指定可訪問伺服器的基礎 URL。構造不同的輸入前，先運行 `npx mastra api experiment run --schema`。實驗可能調用模型，因此啟動前應取得用戶批准。安裝 Mastra Skill：`npx skills add mastra-ai/skills --skill mastra`，可查看 API CLI 發現與目標指定、schema、認證和錯誤處理的完整指引。
</Inject>

## 基礎實驗 {/* #basic-experiment */}

調用 [`startExperiment()`](/reference/datasets/startExperiment)，傳入目標和 scorer：

```typescript title="src/mastra/experiments/basic.ts"
import { mastra } from '../index'

const dataset = await mastra.datasets.get({ id: 'translation-dataset-id' })

const summary = await dataset.startExperiment({
  name: 'gpt-5.1-baseline',
  targetType: 'agent',
  targetId: 'translation-agent',
  scorers: ['accuracy', 'fluency'],
})

console.log(summary.status) // 'completed' | 'failed'
console.log(summary.succeededCount) // items that executed without an error
console.log(summary.failedCount) // items with execution errors
```

`startExperiment()` 會阻塞，直到所有條目完成。如需發起後立即返回，請參閱[異步實驗](#async-experiments)。

## 在 Studio 中運行實驗 {/* #run-experiments-in-studio */}

也可以在 [Studio](/docs/studio/overview) 中運行實驗。添加數據集條目後，打開該條目，選擇 **Run Experiment**，再配置目標、scorer 和選項。

要為單個條目配置 scorer，請編輯條目並啓用 **Override dataset scorers**。可以選擇一個或多個 scorer；若留空，則該條目不運行 scorer。

實驗運行後，**Experiments** 分頁會列出該數據集的所有運行及其狀態、計數和時間戳。選擇某次實驗，可查看各條目的結果、分數和執行追蹤。

在 **Experiments** 分頁選擇 **Compare**，再選擇至少兩次實驗，即可並排比較分數和結果。

## 解讀結果 {/* #interpret-results */}

實驗狀態和計數反映的是執行情況；輸出質素應通過分數判斷。狀態為 `completed` 的實驗仍可能包含執行錯誤，而 `failedCount: 0` 也不代表所有答案都達到質素要求。

| 結果 | 含義 |
| - | - |
| `succeededCount` 和 `failedCount` | 無錯誤執行的條目數與發生執行錯誤的條目數 |
| 每個條目的 `scores` | 輸出符合各 scorer 標準的程度，以及 scorer 提供的原因 |
| 平均分 | 某個 scorer 的匯總表現；可能掩蓋個別失敗 |

例如，單條目實驗的問題是 `2 + 2?`，返回 `5`。準確性 scorer 給出 `0` 分，但任務本身沒有拋出異常，因此摘要包含：

```typescript
console.log(summary.status) // 'completed'
console.log(summary.succeededCount) // 1
console.log(summary.failedCount) // 0
console.log(summary.results[0].scores[0].score) // 0
```

在 Studio 中打開實驗，查看各條目的輸出、分數和原因，再判斷變更是否改善了 Agent。也要檢查 scorer 錯誤：缺失分數無法證明質素。

如果每個條目都必須達到要求，請逐一核對分數。對於以 `1` 表示達標的二元 scorer，五個 `1` 和一個 `0` 的平均分約為 `0.83`，但仍有一個條目不達標。

若要在 CI 中自動檢查質素，[`runEvals()` 的 gate 和 verdict](/docs/evals/gates-and-verdicts) 可提供明確的通過／失敗標準。這些選項屬於 `runEvals()`；數據集實驗的狀態和計數仍表示執行結果。

## 刪除實驗 {/* #delete-experiments */}

在 Studio 的全局 **Experiments** 列表中，選擇某行的 **Delete experiment**；也可以打開實驗並選擇 **Delete Experiment**。全局列表還可以刪除因數據集被刪除而失去關聯、無法再通過數據集詳情頁訪問的實驗。

刪除實驗會永久移除其結果記錄，以及實驗產生的可觀測性 Trace 和關聯的 span、分數、反饋、指標與日誌。如果儲存適配器不支持刪除 Trace，Trace 會保留，系統會記錄警告，但實驗和結果記錄仍會被刪除。

還可以通過 [Core API](/reference/datasets/deleteExperiment)、[Client SDK](/reference/client-js/datasets#deleteexperiment) 或[伺服器路由](/reference/server/routes#delete-an-experiment)刪除實驗。

## 實驗目標 {/* #experiment-targets */}

通過 `targetType` 和 `targetId` 選擇已在 Mastra 實例中註冊的 Agent、Workflow 或 scorer。目標會處理數據集中的每個條目，實驗的 `scorers` 隨後評估目標輸出。

如需自定義執行過程，可改為傳入內聯 `task` 函數。參閱[使用內聯任務的數據集實驗](/docs/evals/evals-with-memory#dataset-experiments-with-an-inline-task)，瞭解如何控制每個條目的 Memory 線程。

### 已註冊的 Agent {/* #registered-agent */}

指定在 Mastra 實例中註冊的 Agent：

```typescript title="src/mastra/experiments/agent-target.ts"
const summary = await dataset.startExperiment({
  name: 'agent-v2-eval',
  targetType: 'agent',
  targetId: 'translation-agent',
  scorers: ['accuracy'],
})
```

每個條目的 `input` 會直接傳給 Agent。可以使用受支持的消息格式，例如提示詞字符串、消息對象或消息數組。可接受的輸入詳見 [`agent.generate()` 參考文檔](/reference/agents/generate)。

#### 啓用 Memory 的 Agent {/* #memory-enabled-agents */}

目標 Agent 配置了 Memory 時，實驗運行器會為每個條目和每次重試注入新的 Memory 線程。如果請求上下文中沒有資源 ID，每個線程都會獲得一個隔離的、由實驗擁有的資源。

要針對現有資源運行，請在實驗的 `requestContext` 或條目的 `requestContext` 中設定 `MASTRA_RESOURCE_ID_KEY`；條目值優先於實驗值。運行器仍會為每個條目和每次重試創建新線程，但使用同一資源 ID 的線程會共享該資源的 Memory。

注入的線程帶有便於回溯運行的標籤：線程元數據包含 `experimentId`，以及以 `experimentItemId` 保存的數據集條目 ID。系統不會為這些線程生成標題。

條目共享同一資源時，按資源範圍工作的 Memory 功能可以讀寫同一狀態：

- 按資源範圍保存的工作記憶更新會持久化到該資源，並可能影響其他條目。條目預設併發運行，因此不要依賴執行順序。
- 按資源範圍進行的語義回憶可能將該資源此前的對話帶入實驗；實驗對話記錄也會在該資源後續的對話中被檢索到。

這種方式可用於結合真實用戶積累的上下文評估 Agent。若不希望實驗觸及真實用戶狀態，請改用專門的評估資源 ID。

以下情況會跳過線程注入：

- 如果請求上下文設定了 `MASTRA_THREAD_ID_KEY`，運行器會直接使用該線程。共用同一線程 ID 的條目和重試會共享一段對話。
- 如果 Agent 未配置 Memory，或者請求上下文明確將資源 ID 設為空字符串或 `null`，運行器會跳過線程注入。

### 已註冊的 Workflow {/* #registered-workflow */}

指定在 Mastra 實例中註冊的 Workflow：

```typescript title="src/mastra/experiments/workflow-target.ts"
const summary = await dataset.startExperiment({
  name: 'workflow-eval',
  targetType: 'workflow',
  targetId: 'translation-workflow',
  scorers: ['accuracy'],
})
```

Workflow 會在 `run.start()` 中以 `inputData` 接收每個條目的 `input`。請按 Workflow 的輸入 schema 組織數據。

### 已註冊的 scorer {/* #registered-scorer */}

將 scorer 作為目標可評估評審器本身。運行器會調用 `scorer.run(item.input)`，因此數據集條目的 `input` 必須包含該 scorer 所需的完整載荷。

下例假設已註冊的 `accuracy` scorer 接收字符串類型的 `input`、`output` 和 `groundTruth` 字段。請按實際 scorer 所需的結構調整：

```typescript title="src/mastra/experiments/scorer-target.ts"
await dataset.addItem({
  input: {
    input: 'What is the capital of France?',
    output: 'Paris',
    groundTruth: 'Paris',
  },
  groundTruth: { score: 1 },
})

const summary = await dataset.startExperiment({
  name: 'judge-accuracy-eval',
  targetType: 'scorer',
  targetId: 'accuracy',
})
```

兩個 `groundTruth` 字段的用途不同：

- `input.groundTruth` 是傳給評審器的參考答案：`'Paris'`。
- 頂層 `groundTruth` 是期望評審器返回的結果：`{ score: 1 }`。它不會傳給目標 scorer。

目標輸出包含 `score` 和 `reason`。若要對照頂層標準答案評估該輸出，請通過實驗的 `scorers` 選項另加一個 scorer。沒有額外的 scorer 時，實驗只記錄評審器輸出，不會評價它與預期結果是否一致。

## 為結果評分 {/* #scoring-results */}

目標執行完每個條目後，scorer 會自動運行。傳入 scorer 實例或已註冊的 scorer ID：

<Tabs>
  <TabItem value="ids" label="Scorer ID">
    ```typescript
    // Reference scorers registered on the Mastra instance
    const summary = await dataset.startExperiment({
      name: 'with-registered-scorers',
      targetType: 'agent',
      targetId: 'translation-agent',
      scorers: ['accuracy', 'fluency'],
    })
    ```
  </TabItem>

  <TabItem value="instances" label="Scorer 實例">
    ```typescript
    import { createAnswerRelevancyScorer } from '@mastra/evals/scorers/prebuilt'

    const relevancy = createAnswerRelevancyScorer({ model: '__GATEWAY_OPENAI_MODEL_LUNA__' })

    const summary = await dataset.startExperiment({
      name: 'with-scorer-instances',
      targetType: 'agent',
      targetId: 'translation-agent',
      scorers: [relevancy],
    })
    ```
  </TabItem>
</Tabs>

每個條目的結果都包含各 scorer 的分數：

```typescript
for (const item of summary.results) {
  console.log(item.itemId, item.output)
  for (const score of item.scores) {
    console.log(`  ${score.scorerName}: ${score.score} — ${score.reason}`)
  }
}
```

可在 [Scorer 概覽](/docs/evals/overview)中瞭解可用和自定義的 scorer。

## 為各條目選擇 scorer {/* #select-scorers-per-item */}

將已註冊的 scorer ID 添加到數據集條目，可覆蓋附在數據集上的 scorer：

```typescript title="src/mastra/datasets/items.ts"
await dataset.addItem({
  input: 'Translate "hello" to French.',
  scorerIds: ['accuracy', 'fluency'],
})
```

實驗會按以下優先級為每個條目選擇**唯一**的 scorer 來源：

1. 實驗的 `scorers` 選項（如果提供）
1. 條目的 `scorerIds` 字段（如果提供）
1. 數據集的 `scorerIds` 字段
1. 不使用 scorer

Mastra 不會合併這些來源。在運行或條目級別顯式設定空數組，表示不使用 scorer，且不會回退到下一來源。運行級別的空分類配置效果相同。重復的條目 ID 或數據集 ID 只運行一次，順序按首次出現的位置確定。

以下更新展示如何在顯式空覆蓋和繼承數據集配置之間切換：

```typescript title="src/mastra/datasets/items.ts"
// Run no scorers for this item
await dataset.updateItem({
  itemId: 'translation-item-id',
  scorerIds: [],
})

// Remove the item override and inherit the dataset's scorers
await dataset.updateItem({
  itemId: 'translation-item-id',
  scorerIds: null,
})
```

更新時省略 `scorerIds` 會保留其當前值。每個條目版本都會保存 scorer ID 列表，包括空列表。scorer 定義不會複製到條目版本中，而是繼續使用已有的註冊表或 Editor 行為。

Mastra 會在執行目標前解析各條目的 scorer ID：先查找已註冊的 scorer，再請 Editor 加載已儲存的 scorer。條目級別的過期 ID 會讓該條目產生 `EXPERIMENT_ITEM_SCORER_NOT_FOUND` 錯誤碼。Mastra 會跳過該條目的目標執行且不重試，實驗中的其他條目仍繼續運行。

如果選中的運行級別或數據集級別來源中存在缺失的 ID，實驗設定會失敗。對於按優先級被忽略的較低級別來源，Mastra 不會解析其中的 ID。

Workflow 步驟 scorer 只能通過運行級別的分類 `scorers` 配置使用。條目級別 ID 適用於平鋪的 Agent、Workflow 和軌跡 scorer 分派。

## 按次控制持久化 {/* #control-persistence-per-run */}

使用 `persistence` 跳過某次運行的儲存寫入。實驗記錄和分數記錄可以分別關閉：

```typescript title="src/mastra/experiments/no-persistence.ts"
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'translation-agent',
  scorers: ['accuracy'],
  persistence: {
    experiments: 'none',
    scores: 'none',
  },
})
```

目標和 scorer 仍會運行，`startExperiment()` 仍會在 `summary` 中返回條目結果和分數。兩個設定相互獨立，例如僅設 `scores: 'none'`，可以持久化實驗及其條目結果，而不創建分數記錄。

省略的設定預設為 `'default'`，即保留標準儲存行為。該策略只控制本次運行創建的實驗與分數記錄，不會禁用目標使用的儲存，例如 Agent Memory、向量、可觀測性數據或自定義 Tool 儲存。

`startExperimentAsync()` 配合 `experiments: 'none'` 運行時，不會持久化實驗記錄、進度更新或條目結果。分數是否持久化仍由 `persistence.scores` 單獨控制。若沒有實驗事件觀察器，此次運行會發起後即不再跟蹤，實驗 API 也無法報告其完成或失敗狀態。

調用方需要返回的摘要時，請使用同步的 `startExperiment()`。實驗事件觀察器也可以接收生命週期事件和最終摘要。

## 觀察實驗事件 {/* #observe-experiment-events */}

使用 `onEvent` 在實驗運行期間接收帶版本號、可安全序列化為 JSON 的生命週期事件。它適用於 `startExperiment()`、`startExperimentAsync()` 和 `runExperiment()`。

```typescript title="src/mastra/experiments/observe.ts"
import type { ExperimentEvent } from '@mastra/core/datasets'

const events: ExperimentEvent[] = []

await dataset.startExperimentAsync({
  task: async ({ input }) => processItem(input),
  persistence: { experiments: 'none' },
  onEvent: async event => {
    events.push(event)
    await publishEvent(event)
  },
})
```

觀察器會收到以下事件類型：

- `experiment.run.started`：標識運行、目標、已解析的數據集版本和條目數量。
- `experiment.item.completed`：報告評分後已提交的條目結果，包括分數、錯誤、重試次數、Tool mock 詳情和穩定的條目標識。
- `experiment.run.finished`：報告最終結果和摘要計數。

Mastra 會等待當前觀察器調用完成後再傳遞下一個事件。這種串行傳遞會形成背壓，並確保事件的 `sequence` 值與傳遞順序一致；條目仍可併發執行。

如果觀察器拋出異常或拒絕 Promise，Mastra 會中止剩餘運行，並讓 `runExperiment()` 以 `id` 為 `EXPERIMENT_EVENT_OBSERVER_FAILED` 的 `MastraError` 拒絕。失敗的觀察器不會收到終止事件。對於 `startExperimentAsync()`，獨立運行的觀察器失敗時方法已經返回；若調用方需要直接獲知傳遞錯誤，應在觀察器內部處理。

Mastra 會先等待 `experiment.run.finished` 事件完成，再持久化實驗的最終狀態。禁用實驗持久化時，應以該事件作為權威的終止信號；但不要把它當作儲存寫入後立即可讀的信號。

導出的事件類型包括 `ExperimentEvent`、`ExperimentRunStartedEvent`、`ExperimentItemCompletedEvent` 和 `ExperimentRunFinishedEvent`。讀取特定事件的屬性前，請先根據判別字段 `type` 縮小類型範圍。

## 生命週期鈎子 {/* #lifecycle-hooks */}

生命週期鈎子可在目標運行前準備狀態，並在運行後清理。適用於無法在空白環境中評估條目的情況，例如需要先把 fixture 文件複製到 Agent 的 Workspace，或在 Agent 訪問前準備 Sandbox。

鈎子分兩級執行：`beforeAll` 和 `afterAll` 每次實驗各運行一次；`beforeEach` 和 `afterEach` 每個條目各運行一次：

```typescript title="src/mastra/experiments/hooks.ts"
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'document-agent',
  scorers: ['accuracy'],
  beforeAll: async ({ experimentId }) => {
    await createWorkspace(experimentId)
  },
  beforeEach: async ({ item }) => {
    await copyFixture(item.metadata?.fixture)
  },
  afterEach: async ({ item, result }) => {
    await clearWorkspaceFiles(item.id)
  },
  afterAll: async ({ summary }) => {
    await deleteWorkspace(summary.experimentId)
  },
})
```

所有鈎子都可以是異步函數。每個鈎子都會收到 `experimentId`、`mastra` 實例和運行級 `signal`，因此耗時的準備工作也能隨實驗一起取消。條目級鈎子還會收到 `item`。清理鈎子會收到它們所跟隨的結果：`afterEach` 收到包含分數的條目 `result`，`afterAll` 收到即將返回的 `summary`。

傳給鈎子的條目只暴露 `id`、`input`、`groundTruth` 和 `metadata`。Tool mock 和 scorer 選擇等控制執行的字段不會暴露，因此鈎子無法改變條目的運行方式。

### 鈎子失敗 {/* #hook-failures */}

各鈎子拋出異常時影響不同，取決於運行對它的依賴程度：

| 鈎子 | 失敗時 |
| - | - |
| `beforeAll` | 實驗失敗；不運行任何條目。 |
| `beforeEach` | 該條目以 `EXPERIMENT_ITEM_BEFORE_EACH_FAILED` 失敗；其他條目繼續。 |
| `afterEach` | 記錄日誌；不改變該條目已記錄的結果。 |
| `afterAll` | 記錄日誌；不改變返回的摘要。 |

`beforeAll` 失敗時，實驗會標記為失敗；錯誤向上傳播前仍會發出 `experiment.run.finished` 事件。

`beforeEach` 失敗時，該條目的前置條件尚未滿足，因此會跳過其目標和 scorer，也不會運行該條目的 `afterEach`；未完成的準備工作應自行負責清理。

清理失敗只記錄日誌，不向上傳播。執行 `afterEach` 時目標已經產出真實結果；若因清理不完整而丟棄結果，就會失去實驗原本要收集的數據。

`afterAll` 會在所有退出路徑運行，包括實驗失敗、`beforeAll` 失敗或[事件觀察器](#observe-experiment-events)失敗，因此即使出錯也不會跳過清理。每次實驗最多運行一次。

## Tool mock {/* #tool-mocks */}

實驗運行調用有副作用 Tool 的 Agent 時，可以為各數據集條目附加靜態 Tool mock，使運行結果可重現。實驗期間，被 mock 的 Tool 會返回預設輸出而不實際執行。條目沒有提供 mock 的 Tool 預設仍會真實調用。

mock 會與數據集條目一起儲存和版本化。每個 mock 都指定 Tool 名稱、預期參數和要返回的輸出：

```typescript title="src/mastra/experiments/tool-mocks.ts"
await dataset.addItem({
  input: 'What is the weather in Seattle?',
  toolMocks: [
    {
      toolName: 'getWeather',
      args: { city: 'Seattle' },
      output: { temperature: 60, conditions: 'rainy' },
    },
  ],
})
```

Tool mock 僅支持目標類型為 `agent` 的實驗。

### 阻止未聲明的 Tool {/* #block-undeclared-tools */}

將實驗的 `unmockedToolPolicy: 'deny'` 設為拒絕，可阻止所有沒有 mock 的 Tool 調用。適用於真實調用可能產生副作用的場景：

```typescript
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'weather-agent',
  unmockedToolPolicy: 'deny',
})
```

預設策略為 `'allow'`。可以在單個已儲存或內聯條目上覆蓋實驗策略：

```typescript
await dataset.addItem({
  input: 'What is the weather in Seattle?',
  unmockedToolPolicy: 'allow',
})
```

條目值優先於實驗值。被拒絕的調用會在 Tool 執行前以 `TOOL_MOCK_NOT_DECLARED` 失敗；該失敗不會重試，也不會計入 `liveCalls`。

### 匹配與消費 {/* #matching-and-consumption */}

參數採用嚴格匹配：對象鍵的順序不影響結果，數組元素順序則有影響。值不會轉換成其他類型。只有 Agent 調用 Tool 時的參數與 mock 的 `args` 深度相等，才會使用該 mock。

如果一個條目為相同 Tool 和參數聲明瞭多個 mock，系統會按順序消費：第一次調用使用第一個，第二次調用使用第二個，依此類推。順序按 `(toolName, args)` 分組分別追蹤，不同參數組之間互不影響。

### 匹配模式 {/* #matching-mode */}

預設情況下，mock 會嚴格匹配其 `args`。設定 `matchArgs: 'ignore'` 後，只按 Tool 名稱匹配，不比較 mock 的 `args`；該 Tool 下一條尚未消費的 mock 會被使用，不論 Agent 傳入了什麼參數：

```typescript
const subAgentMock = {
  toolName: 'agent-balanceAgent',
  args: { prompt: 'look up the balance for YJ' },
  output: { text: "YJ's balance is $100." },
  matchArgs: 'ignore',
}
```

當 Tool 參數包含噪聲或由模型生成時，這種方式很有用。最常見的場景是模擬**子 Agent 的響應**。父 Agent 將委派的子 Agent 視為 `agent-<name>` Tool，其參數包含 LLM 編寫的 `prompt` 和運行時注入的字段。mock `agent-<name>` 會直接返回預設響應，不運行子 Agent 及其內部 Tool。若從 Trace 創建 mock，子 Agent 委派調用會自動採用 `matchArgs: 'ignore'`；可改為 `'strict'`，固定確切參數。

### 失敗情形 {/* #failures */}

違反 mock 配置的 Tool 調用會使該條目失敗：

- `TOOL_MOCK_MISMATCH`：調用參數與任何 mock 都不匹配。
- `TOOL_MOCK_EXHAUSTED`：所有匹配的 mock 都已消費。
- `TOOL_MOCK_NOT_DECLARED`：Tool 沒有 mock，且有效的 `unmockedToolPolicy` 為 `'deny'`。

發生上述任一失敗時，Agent 運行會立即中止，模型無法繼續調用其他 Tool，包括原本會真實運行且可能產生副作用的未 mock Tool。這些失敗是確定性的，不會重試。已聲明但未使用的 mock 不會讓條目失敗，而是報告為未消費。

啓用 mock 攔截時，Agent 的 Tool 會順序執行，因此重復的 `(toolName, args)` mock 會按提供方的調用順序消費。條目聲明 mock 或其有效 `unmockedToolPolicy` 為 `'deny'` 時，攔截即生效。

### 診斷信息 {/* #diagnostics */}

每個條目的結果都包含 `toolMockReport`，列出已使用的 mock 和未經過 mock 的 Tool 調用：

```typescript
for (const item of summary.results) {
  const report = item.toolMockReport
  if (!report) continue

  console.log(report.served) // mocks matched and returned
  console.log(report.unconsumed) // mocks declared but never used
  console.log(report.liveCalls) // undeclared tools allowed to run live
  console.log(report.failure) // the first deterministic mock failure, if any
}
```

在 [Studio](/docs/studio/overview) 中，編輯數據集條目可用 JSON 數組編寫 Tool mock；打開實驗結果可查看同一份報告。

### 限制 {/* #limitations */}

- **被 mock 的 Tool span 是扁平的。** 已使用的 mock 會記錄一個 `tool_call` span，包含模擬輸出和 `mocked: true` 屬性。mock 不匹配或已耗盡時，會記錄 `success: false` 的 span。真實 Tool 不會運行，因此該 span 沒有子 span，也沒有 `toolDescription`。
- **儲存支持情況。** LibSQL、PostgreSQL、MongoDB 和 Spanner 適配器會持久化 Tool mock 及其報告；MySQL 適配器會拒絕寫入包含二者任意一個的記錄。所有數據集儲存適配器都會持久化 `unmockedToolPolicy`。

## 異步實驗 {/* #async-experiments */}

`startExperiment()` 會阻塞直到所有條目完成。對於運行時間較長的數據集，可使用 [`startExperimentAsync()`](/reference/datasets/startExperimentAsync) 在後台啟動實驗：

```typescript title="src/mastra/experiments/async.ts"
const { experimentId, status } = await dataset.startExperimentAsync({
  name: 'large-dataset-run',
  targetType: 'agent',
  targetId: 'translation-agent',
  scorers: ['accuracy'],
})

console.log(experimentId) // UUID
console.log(status) // 'pending'
```

通過 [`getExperiment()`](/reference/datasets/getExperiment) 輪詢完成狀態：

```typescript
let experiment = await dataset.getExperiment({ experimentId })
if (!experiment) throw new Error('Experiment not found')

while (experiment.status === 'pending' || experiment.status === 'running') {
  await new Promise(resolve => setTimeout(resolve, 5000))
  experiment = await dataset.getExperiment({ experimentId })
  if (!experiment) throw new Error('Experiment not found')
}

console.log(experiment.status) // 'completed' | 'failed'
```

## 由調用方驅動的實驗 {/* #caller-driven-experiments */}

`startExperiment()` 讓 Mastra 管理整個運行過程。如果循環由持久化編排器（例如 Temporal、Airflow 或自定義 worker 集群）負責，可先創建實驗，再由調用方按以下任一種方式驅動：

- **調用方控制循環，Mastra 運行各條目。** 創建帶目標的實驗，然後對每個條目調用一次 [`runExperimentItem()`](/reference/datasets/runExperimentItem)。Mastra 會執行目標和 scorer，再持久化結果。
- **調用方執行全部步驟。** 創建不帶目標的實驗，在自己的基礎設施上執行條目並評分，再使用 [`submitExperimentResult()`](/reference/datasets/submitExperimentResult)寫入每個結果。

兩種方式都以 [`finalizeExperiment()`](/reference/datasets/finalizeExperiment) 結束，並寫入與原生運行相同的表，因此 Studio 的視圖、比較和審核摘要仍可照常使用。

### 在伺服器端運行條目 {/* #run-items-server-side */}

調用 [`createExperiment()`](/reference/datasets/createExperiment)，傳入目標和 scorer。提供自己的 `id`（例如 Workflow 運行 ID）可使創建操作具備冪等性：以相同 ID 重試會返回已有實驗，而不是失敗。

```typescript title="src/mastra/experiments/caller-driven.ts"
const dataset = await mastra.datasets.get({ id: 'translation-dataset-id' })

const { experimentId, totalItems, datasetVersion } = await dataset.createExperiment({
  id: 'temporal-wf-run-42', // optional: reuse your workflow run id for idempotent creates
  targetType: 'agent',
  targetId: 'translation-agent',
  scorers: ['accuracy'],
})
```

隨後由編排器運行每個條目。Mastra 會在固定的數據集版本中解析條目，用解析出的 scorer 執行目標。結果寫入以 `(experimentId, itemId, attempt)` 為鍵進行 upsert；重試的任務最終會收斂到一行：

```typescript
const { result, scores } = await dataset.runExperimentItem({
  experimentId,
  itemId: 'item-1',
})
```

重試和超時由編排器負責：每次調用 `runExperimentItem` 都只執行該條目一次。scorer 採用與原生運行相同的優先級：實驗 `scorers` 高於條目 `scorerIds`，後者高於數據集 `scorerIds`。

### 寫入外部結果 {/* #ingest-external-results */}

如果 worker 自行執行條目並評分，請創建不帶目標的實驗：

```typescript title="src/mastra/experiments/ingestion.ts"
const { experimentId } = await dataset.createExperiment({
  id: 'temporal-wf-run-42',
  name: 'external-eval',
})
```

使用 [`submitExperimentResult()`](/reference/datasets/submitExperimentResult) 為每個條目提交一份結果。提交以 `(experimentId, itemId, attempt)` 為鍵進行 upsert；worker 重試會收斂到同一行，不會產生重復結果：

```typescript
await dataset.submitExperimentResult({
  experimentId,
  itemId: 'item-1',
  output: { translation: 'Hola' },
  scores: [{ scorerId: 'accuracy', score: 0.92, reason: 'Faithful translation' }],
})
```

`input` 和 `groundTruth` 預設取自實驗固定的數據集版本中的條目值。內聯 `scores` 會持久化到該實驗的分數儲存中，因此可與原生 scorer 運行結果一起比較。帶目標創建的實驗會拒絕 `submitExperimentResult`，以免兩個寫入方爭用同一批行。

### 完結實驗 {/* #finalize */}

所有條目完成後，調用 [`finalizeExperiment()`](/reference/datasets/finalizeExperiment)。Mastra 會根據已持久化的行計算 `succeededCount`、`failedCount` 和 `skippedCount`，worker 無需自行統計完成情況。完結操作是冪等的；再次調用會返回已儲存的記錄：

```typescript
const experiment = await dataset.finalizeExperiment({ experimentId })

console.log(experiment.status) // 'completed'
console.log(experiment.succeededCount) // items with at least one attempt that didn't error
console.log(experiment.failedCount) // items where every attempt errored
console.log(experiment.skippedCount) // items never submitted
```

HTTP 也提供相同的生命週期：`POST /api/datasets/:datasetId/experiments` 搭配 `start: false`、`POST .../experiments/:experimentId/items/:itemId/run`、`POST .../experiments/:experimentId/results`、`POST .../experiments/:experimentId/finalize`；參閱[伺服器路由](/reference/server/routes#datasets-and-experiments)。`@mastra/client-js` 中亦可使用，參閱[數據集 API](/reference/client-js/datasets)。

### 重試與冪等性約定 {/* #retry-and-idempotency-contract */}

由調用方驅動的調用可以積極重試，例如由 Temporal 重試策略觸發。具體保證如下：

- **按 `id` 冪等創建。** 再次用調用方提供的相同 `id` 調用 `createExperiment`，會返回已有實驗。如果該 `id` 屬於其他數據集，或已有實驗的目標不同，則以 `EXPERIMENT_ID_CONFLICT` 失敗（HTTP `409`）。
- **結果按 `(experimentId, itemId, attempt)` upsert。** 再次提交相同鍵會更新已有行；所有可變字段均以最後一次寫入為準。worker 重試不會產生重復行。
- **`attempt` 區分有意重復試驗與重試。** 同一次運行的重試應復用相同 `attempt`（預設 `0`），使結果收斂。若要將同一條目的重復試驗記錄為不同行，可依次提交 `attempt: 0`、`attempt: 1` 等。
- **數據集版本在創建時固定。** 提交會按該版本中可見的條目驗證，因此此後編輯或刪除條目不會影響運行中的實驗。如果提交的 `itemId` 在固定版本中不可見，會返回 `404`。
- **完結操作冪等且不可逆。** 對已完成的實驗再次調用完結操作，會直接返回儲存記錄，不重新計算。完結後繼續提交會被 `EXPERIMENT_ALREADY_FINALIZED` 拒絕（HTTP `409`）。
- **計數由伺服器按條目計算。** 完結時，Mastra 會匯總每個條目的各次嘗試：`succeededCount`（至少一次嘗試無錯誤）、`failedCount`（所有嘗試均出錯）、`skippedCount`（從未提交）。始終滿足 `succeededCount + failedCount + skippedCount === totalItems`，調用方無需自行維護完成計數。每次嘗試的行仍可通過 `listExperimentResults` 查詢。

## 配置選項 {/* #configuration-options */}

### 併發 {/* #concurrency */}

控制並行運行的條目數量（預設：5）：

```typescript
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'translation-agent',
  maxConcurrency: 10,
})
```

### 超時與重試 {/* #timeouts-and-retries */}

設定單個條目的超時時間（毫秒）和重試次數：

```typescript
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'translation-agent',
  itemTimeout: 30_000, // 30 seconds per item
  maxRetries: 2, // retry failed items up to 2 times
})
```

重試採用指數退避；中止錯誤不會重試。

### 中止實驗 {/* #aborting-an-experiment */}

傳入 `AbortSignal` 以取消正在運行的實驗：

```typescript
const controller = new AbortController()

// Cancel after 60 seconds
setTimeout(() => controller.abort(), 60_000)

const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'translation-agent',
  signal: controller.signal,
})
```

摘要會將剩餘條目標記為已跳過。

### 固定數據集版本 {/* #pinning-a-dataset-version */}

針對數據集的特定快照運行：

```typescript
const summary = await dataset.startExperiment({
  targetType: 'agent',
  targetId: 'translation-agent',
  version: 3, // use items from dataset version 3
})
```

## 理解摘要 {/* #understanding-the-summary */}

`startExperiment()` 返回包含計數和各條目結果的 `ExperimentSummary`：

- `completedWithErrors` 為 `true` 表示實驗已完成，但部分條目失敗。
- 通過 `signal` 取消的條目會計入 `skippedCount`。

完整參數和返回類型詳見 [`startExperiment` 參考文檔](/reference/datasets/startExperiment)。
