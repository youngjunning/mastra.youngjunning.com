# 為 Workflow 設定排程

在 Workflow 宣告 `schedule` 欄位，Mastra 就會按指定的 cron 表達式觸發 Workflow。你仍可直接呼叫 `workflow.start()`；定時觸發和手動運行共用同一執行流程。

## 快速入門 {/* #quickstart */}

以下 Workflow 每日紐約時間上午 9 時運行。沿用註冊其他 Workflow 的方式，將它註冊到 `Mastra`，排程器便會自動讀取。

```typescript title="src/mastra/workflows/daily-report.ts"
import { createWorkflow, createStep } from '@mastra/core/workflows'
import { z } from 'zod'

const sendReport = createStep({
  id: 'send-report',
  inputSchema: z.object({ userId: z.string() }),
  outputSchema: z.object({ ok: z.boolean() }),
  execute: async ({ inputData }) => {
    // ...send the report for inputData.userId
    return { ok: true }
  },
})

export const dailyReport = createWorkflow({
  id: 'daily-report',
  inputSchema: z.object({ userId: z.string() }),
  outputSchema: z.object({ ok: z.boolean() }),
  schedule: {
    cron: '0 9 * * *',
    timezone: 'America/New_York',
    inputData: { userId: 'system' },
  },
})
  .then(sendReport)
  .commit()
```

不必另行呼叫排程註冊方法。排程器會在 `Mastra` 啟動時直接讀取 Workflow 的 `schedule`。

## 傳送保證 {/* #delivery-guarantees */}

排程的 Workflow 啟動事件採用盡力發佈的方式。排程器先領取當次觸發工作，再發佈啟動事件，最多嘗試三次。用盡嘗試次數，或發佈端故障，均可能令該次觸發跳過。已跳過的觸發不會自動補發，往後仍可按周期觸發。排程標記為 `completed` 只表示沒有後續觸發，無法確認 Workflow 已運行。故障回報和手動重跑須知見[排程傳送保證](/reference/schedules/overview#delivery-guarantees)。

## 執行引擎 {/* #execution-engine */}

宣告 `schedule` 不會改變 Workflow 的運行方式。定時觸發與 `workflow.start()` 或 HTTP 觸發一樣，在運行排程器的主機程序內執行。直接運行帶有 `schedule` 的 Workflow，毋須額外設定儲存或 Worker。

Worker 分開部署時則屬例外。[`MASTRA_WORKERS`](/reference/workers/overview#mastra_workers) 環境變數只要有設定，包括設為 `false`，`createWorkflow` 就會用**事件驅動執行引擎**建立有排程的 Workflow，讓部署中的所有程序以同一方式執行。這時，排程觸發由[協調 Worker](/docs/deployment/workers#orchestration-worker)執行，而 Mastra 會在建立 Workflow 時於主控台記錄警告。公開 API（`workflow.start()`、`workflow.startAsync()`、`resume()`）不變。

事件驅動運行需要能以原子方式套用並行更新的儲存配接器，例如 `@mastra/libsql` 或 `@mastra/pg`。若採用其他配接器，`createRun()` 會擲出錯誤並列出支援的配接器。

只有設定環境變數才會觸發切換，因為 `createWorkflow` 會在 `Mastra` 讀取 `workers` 選項前運行。若改用 `workers` 選項分開部署 Worker，請由 `@mastra/core/workflows/evented` 匯入 `createWorkflow` 來建立有排程的 Workflow。

## 單個排程 {/* #single-schedule */}

只需按一種時間設定觸發的 Workflow，可將物件傳給 `schedule`：

```typescript title="src/mastra/workflows/daily-report.ts"
import { createWorkflow } from '@mastra/core/workflows'

const dailyReport = createWorkflow({
  id: 'daily-report',
  schedule: {
    cron: '0 9 * * *',
    timezone: 'America/New_York',
    inputData: { userId: 'system' },
  },
  // ...
})
```

可設定以下欄位：

- `cron`：標準的 5、6 或 7 段 cron 表達式，在建立 Workflow 時驗證。`cron` 與 `runAt` 必須選填其中一項。
- `runAt`（可選）：指定單次觸發的時間，取代 cron。可以用 Unix 紀元毫秒值或 `Date`。觸發後排程會改為 `completed`，日後部署不會重新啟用，除非更改 `runAt`。如首次註冊時已過了 `runAt`，會直接記為 `completed`，不會觸發。
- `endAt`（可選）：只可與 `cron` 同用，指定停止觸發的時間。若下一次觸發將遲於 `endAt`，排程便會改為 `completed`。
- `timezone`（可選）：IANA 時區，例如 `America/New_York`，預設為主機的本地時區。正式環境應明確設定此欄位，避免觸發時間受伺服器的地區設定影響。
- `inputData`（可選）：每次觸發時傳給 Workflow 的輸入資料。
- `initialState`（可選）：該次運行的初始狀態。
- `requestContext`（可選）：該次運行所附的請求上下文。
- `metadata`（可選）：與排程記錄一同持久儲存的自訂元資料。

如要在指定時間運行一次 Workflow，請使用 `runAt`：

```typescript title="src/mastra/workflows/launch-announcement.ts"
const launchAnnouncement = createWorkflow({
  id: 'launch-announcement',
  schedule: {
    // Set this to a stable future ISO timestamp in your deployment environment.
    runAt: new Date(process.env.LAUNCH_ANNOUNCEMENT_AT!),
    inputData: { userId: 'system' },
  },
  // ...
})
```

## 多個排程 {/* #multiple-schedules */}

要讓同一 Workflow 按不同周期觸發，可傳入陣列。每項設定都需要一個唯一且穩定的 `id`：

```typescript title="src/mastra/workflows/status-check.ts"
import { createWorkflow } from '@mastra/core/workflows'

const statusCheck = createWorkflow({
  id: 'status-check',
  schedule: [
    { id: 'morning', cron: '0 9 * * *', inputData: { window: 'morning' } },
    { id: 'evening', cron: '0 18 * * *', inputData: { window: 'evening' } },
  ],
  // ...
})
```

各項會建立獨立的排程記錄，按自己的 cron 設定觸發，並分別顯示於 Studio 的 Schedules 檢視。

## 在 Studio 查看排程 {/* #viewing-schedules-in-studio */}

Studio 將排程放在獨立的頂層頁面，不放在個別 Workflow 的分頁內：

- **所有排程**：開啟 `/workflows/schedules`，即可查看各個 Workflow 的排程。每列顯示 Workflow ID、cron、下次觸發時間及最近一次運行的狀態，方便快速識別故障。
- **按 Workflow 篩選**：加上 `?workflowId=<id>`，即可只查看一個 Workflow，例如 `/workflows/schedules?workflowId=daily-report`。
- **排程詳情**：選取任何一列，便會開啟 `/workflows/schedules/:scheduleId`。此頁顯示排程的元資料、**Pause** / **Resume** 控制項，以及完整觸發記錄。

如果 Workflow 至少有一項排程，頁首就會顯示 **Schedules** 操作：

- 只有一項排程時，連結直接開啟該排程的詳情。
- 有多項排程時，連結開啟已按 Workflow 篩選的清單 `/workflows/schedules?workflowId=<id>`。
- 沒有排程時，會隱藏此操作。

### 觸發記錄 {/* #trigger-history */}

排程器會嘗試寫入觸發記錄，包括運行 ID、原定時間、實際觸發時間及發佈狀態。如果發佈端在領取工作後，或傳輸層接受發佈後故障，便可能沒有觸發記錄。排程詳情頁會把已有的觸發記錄連結至相應的 Workflow 運行，並顯示：

- 運行狀態標記（`running`、`success`、`failed`、`suspended`、`canceled`）。
- 運行開始的時間及所用時間。
- 指向完整運行圖的連結 `/workflows/:workflowId/graph/:runId`。
- `pending` 標記：發佈觸發事件與寫入運行快照之間有時序競爭，運行記錄尚未寫入時會顯示此標記。
- `publish failed` 標記：三次發佈都失敗後顯示，並附有最後一次發佈錯誤。實際結果未明，傳輸層可能在回傳錯誤前已接受事件。

只要仍有觸發未進入最終狀態，面板就每五秒輪詢，直到它們都進入最終狀態。清單分頁載入，因此長期運作的排程毋須一次載入數千項記錄。

## 在運行期間暫停排程 {/* #pausing-a-schedule-at-runtime */}

正式環境中的 Workflow 排程觸發異常時，可以經 SDK 暫停，毋須重新部署或手動改動資料庫：

```typescript
import { MastraClient } from '@mastra/client-js'

const client = new MastraClient({ baseUrl: 'http://localhost:4111' })

// Schedule ids are derived from the workflow id: `wf_<workflowId>` for a
// single declarative schedule, or `wf_<workflowId>__<scheduleId>` when you
// declare multiple schedules per workflow as an array.
await client.pauseSchedule('wf_daily-report')
// ...investigate, ship a fix, then:
await client.resumeSchedule('wf_daily-report')
```

在 Studio，可開啟排程詳情頁，在頁首選擇 **Pause** 或 **Resume**。

以下是暫停及恢復的規則：

- 暫停狀態會寫入排程資料表，在程序重啟和重新部署後仍會保留。以宣告設定新增或更新記錄時，即使更改 `cron`、`timezone`、`runAt`、`endAt` 或其他欄位，也不會覆寫用戶設定的狀態。
- 恢復 cron 排程時，會以當前時間重新計算 `nextFireAt`。即使暫停了一星期，也不會補做七次積壓的運行，而會在下一個正常的 cron 時刻觸發。
- 恢復單次排程時，會保留已設定的 `runAt`。如果暫停期間已過了該時間，排程器在下一輪檢查時便會觸發。
- 以 `resumeSchedule` 或 Studio 的 **Resume** 按鈕解除暫停。更改 Workflow 的 `schedule` 設定不會解除現有記錄的暫停狀態。
- 暫停和恢復均為冪等操作。對已暫停的排程再次呼叫暫停，不會改變狀態。
- 這類運行期間的操作只控制現有排程。宣告式排程透過程式碼的 `createWorkflow` 上的 `schedule` 欄位建立、刪除和編輯。若要在運行期間直接建立排程，可使用統一的 [`mastra.schedules`](/docs/harness/schedules) 服務，並提供 `workflowId`。

底層 HTTP 路由為 `POST /api/schedules/:scheduleId/pause` 及 `POST /api/schedules/:scheduleId/resume`。兩者都需要 `schedules:write` 權限。

## 更改設定後重新部署 {/* #redeploying-with-changes */}

更改 `schedule` 設定並重新部署後，Mastra 會比較現有排程記錄與新設定：

- 周期排程的 `cron`、`timezone` 或 `endAt` 如有更改，便會重新計算 `nextFireAt`。如果再沒有觸發時間，排程會標示完成；若重算後仍可觸發，已完成的排程會重新啟用。
- 單次排程的 `runAt` 如有更改，`nextFireAt` 會更新為該時間。如果 `runAt` 是將來的時間，會重新啟用已完成的單次排程；如果 `runAt` 已過，便會保持完成狀態。
- 如果已啟用的單次排程在應用程式離線期間錯過未修改的 `runAt`，工作仍然到期，排程器在下一輪檢查時會觸發。首次註冊時若 `runAt` 已過，則直接以 `completed` 狀態建立，不會觸發。
- 如果只更改了 `inputData`、`initialState` 或 `metadata`，會更新原有記錄，保留下次觸發時間。
- 用戶設定的狀態（例如透過 `client.pauseSchedule` 暫停）和觸發記錄不會被覆寫，除非上述時間更改要求更新狀態。

`completed` 表示排程沒有剩餘的自動觸發：單次觸發已被領取、周期排程已用盡觸發次數，或在註冊或同步設定時已沒有符合設定的觸發時間。此狀態無法確認 Workflow 是否成功完成。

從 Workflow 的 `schedule` 陣列移除某項排程後，下次啟動便會刪除相應記錄。

## 部署方式 {/* #deployment-topology */}

內置排程器用 `setInterval` 定時輪詢排程資料表，領取到期項目，再透過程序內的發佈訂閱機制分派 Workflow 運行。這需要一個長時間運作的主機程序。

### 長時間運作的主機（建議） {/* #long-lived-host-recommended */}

在 Fly Machines、Railway、Render、AWS ECS、GKE 或自家伺服器等環境部署，可讓 Mastra 程序在兩次 cron 觸發之間繼續運行。`mastra build` 產生的伺服器會自動啟動排程器，毋須額外設定排程。

若使用[伺服器配接器](/docs/server/server-adapters)運行 Mastra，請在伺服器開始監聽後呼叫 `mastra.startWorkers()`。配接器不會啟動排程器，省略此呼叫便不會觸發排程。詳見[啟動背景 Worker](/docs/server/server-adapters#start-background-workers)。

正式部署可在[專用 Worker 程序](/docs/deployment/workers#scheduler-worker)運行排程器，將其與 API 層隔離。

### Serverless 平台 {/* #serverless-platforms */}

Vercel、Netlify、AWS Lambda 和 Cloudflare Workers 等函數即服務平台，會在每次請求完結後關閉程序，因此定時迴圈不會到達下一輪。現時在程式碼宣告的排程，無法透過內置排程器觸發。直接運行仍然可用：從 HTTP 路由呼叫 `run.start()`，即可像其他 Workflow 一樣，在程序內運行宣告了 `schedule` 的 Workflow。

如要在這些平台用 cron 觸發，請改用 [`@mastra/inngest`](#inngest-workflows)。Inngest 原生支援 Serverless，並代為保存 cron 狀態。

## Inngest Workflow {/* #inngest-workflows */}

本頁的 `schedule` 欄位由 Mastra 內置排程器處理。使用 `@mastra/inngest` 時，須透過 Inngest 的 `createFunction` 上的 `cron` 欄位設定 Workflow 排程，由 Inngest 的排程器觸發。

實際使用時有以下分別：

- Inngest 排程不會出現在 Studio 的 `/workflows/schedules` 檢視。
- Inngest Workflow 頁首不會顯示 **Schedules** 操作。
- `client.pauseSchedule` 和 `client.resumeSchedule` 不會控制 Inngest 排程。

請在 [Inngest 控制台](https://www.inngest.com/docs/guides/scheduled-functions)管理 Inngest 排程。如希望由 Mastra 處理整個排程流程，請使用 Mastra 排程。
