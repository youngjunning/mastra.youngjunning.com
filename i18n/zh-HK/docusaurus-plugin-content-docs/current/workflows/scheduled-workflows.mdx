# 預定的Workflow

聲明一個`schedule`Workflow上的字段，Mastra 將在您指定的 cron 上觸發它。相同的Workflow仍可直接調用`workflow.start()`、規劃火災和手動運行共享單一執行路徑。

## 快速入門 {/* #quickstart */}

以下Workflow在紐約時間每天上午 9 點運行。註冊於`Mastra` as you would any other workflow, the scheduler picks it up automatically.

```typescript title="src/mastra/workflows/daily-report.ts"
import { createWorkflow, createStep } from '@mastra/core/workflows'
import { z } from 'zod'

const sendReport = createStep({
  id: 'send-report',
  inputSchema: z.object({ userId: z.string() }),
  outputSchema: z.object({ ok: z.boolean() }),
  execute: async ({ inputData }) => {
    // ...send the report for inputData.userId
    return { ok: true }
  },
})

export const dailyReport = createWorkflow({
  id: 'daily-report',
  inputSchema: z.object({ userId: z.string() }),
  outputSchema: z.object({ ok: z.boolean() }),
  schedule: {
    cron: '0 9 * * *',
    timezone: 'America/New_York',
    inputData: { userId: 'system' },
  },
})
  .then(sendReport)
  .commit()
```

不會發生單獨的「註冊時間表」呼叫。調度程序讀取`schedule` straight off the workflow when `Mastra` boots.

## 交貨保證 {/* #delivery-guarantees */}

計劃的Workflow發布是盡力而為的。每個事件在其開始事件發布之前都會被聲明，最多可嘗試三次發布。耗盡嘗試或發布者崩潰可以跳過該事件。跳過的事件不會自動重播，但稍後重複發生的火災可以繼續。已標記的時間表`completed` has exhausted its cadence, which doesn't confirm execution. See [Schedule delivery guarantees](/reference/schedules/overview#delivery-guarantees) for failure reporting and manual rerun precautions.

## 執行引擎 {/* #execution-engine */}

聲明`schedule` doesn't change how the workflow runs. Scheduled fires run in-process on the host that runs the scheduler, the same way `workflow.start()` or an HTTP-triggered run does. A workflow that declares `schedule` needs no extra storage or worker setup to run directly.

拆分工作執行緒部署是例外。當[`MASTRA_WORKERS`](/reference/workers/overview#mastra_workers) environment variable is set to any value, including `false`, `createWorkflow` builds scheduled workflows on the **evented execution engine** so that every process in the deployment runs them the same way. Scheduled fires then run on the [orchestration worker](/docs/deployment/workers#orchestration-worker), and Mastra logs a warning to the console when the workflow is created. The public API (`workflow.start()`, `workflow.startAsync()`, `resume()`) 不變。

事件運行需要一個能夠自動套用並發更新的儲存適配器，例如`@mastra/libsql` or `@mastra/pg`. With any other adapter, `createRun()` throws an error that lists the supported adapters.

只有環境變數才會觸發切換，因為`createWorkflow` runs before `Mastra` reads its `workers` option. If you split workers with the `workers` option instead, import `createWorkflow` from `@mastra/core/workflows/evented` for your scheduled workflows.

## 單一時間表 {/* #single-schedule */}

將對象傳遞給`schedule` for a workflow that fires on one cadence:

```typescript title="src/mastra/workflows/daily-report.ts"
import { createWorkflow } from '@mastra/core/workflows'

const dailyReport = createWorkflow({
  id: 'daily-report',
  schedule: {
    cron: '0 9 * * *',
    timezone: 'America/New_York',
    inputData: { userId: 'system' },
  },
  // ...
})
```

領域：

* `cron`：由 5、6 或 7 部分組成的 cron 表達式。在Workflow建置時進行驗證。準確提供以下之一`cron` or `runAt`.
* `runAt`（可選）：此時觸發一次（紀元毫秒或`Date`) instead of on a cron. After it fires, the schedule moves to `completed` and later deploys don't re-arm it unless you change `runAt`. A `runAt` that has already passed when the schedule is first registered is recorded as `completed` without firing.
* `endAt`（可選）：僅與`cron`. Stop firing after this time. The schedule moves to `completed` once its next occurrence would fall after `endAt`.
* `timezone`（可選）：例如 IANA 時區`America/New_York`. Defaults to the host's local timezone. Set this explicitly in production so fire times don't depend on server locale.
* `inputData`（可選）：有效負載在每次火災時作為Workflow的輸入傳遞。
* `initialState`（可選）：運行的初始狀態。
* `requestContext`（可選）：附加到運行的請求上下文。
* `metadata`（可選）：任意元資料與計劃行一起保留。

`runAt`:

```typescript title="src/mastra/workflows/launch-announcement.ts"
const launchAnnouncement = createWorkflow({
  id: 'launch-announcement',
  schedule: {
    // Set this to a stable future ISO timestamp in your deployment environment.
    runAt: new Date(process.env.LAUNCH_ANNOUNCEMENT_AT!),
    inputData: { userId: 'system' },
  },
  // ...
})
```

## 多個時間表 {/* #multiple-schedules */}

傳遞一個陣列以在多個節奏上觸發相同的Workflow。每個條目都需要一個獨特的馬厩`id`:

```typescript title="src/mastra/workflows/status-check.ts"
import { createWorkflow } from '@mastra/core/workflows'

const statusCheck = createWorkflow({
  id: 'status-check',
  schedule: [
    { id: 'morning', cron: '0 9 * * *', inputData: { window: 'morning' } },
    { id: 'evening', cron: '0 18 * * *', inputData: { window: 'evening' } },
  ],
  // ...
})
```

每個條目都會建立一個獨立的計劃行並在自己的 cron 上觸發，並且單獨顯示在 Studio Schedules 視圖中。

## 在 Studio 中查看時間表 {/* #viewing-schedules-in-studio */}

Studio 將計劃顯示為頂級區域，而不是Workflow中的標籤：

* **所有時間表**： 打開`/workflows/schedules` for a cross-workflow list. Each row shows the workflow id, cron, next fire, and the most recent run's status. The list answers "is anything broken?" at a glance.
* **按Workflow過濾**: 追加`?workflowId=<id>` to scope the list to a single workflow, for example `/workflows/schedules?workflowId=daily-report`.
* **日程詳情**：選擇任意行打開`/workflows/schedules/:scheduleId`. The page shows schedule metadata and **Pause** / **Resume** controls, followed by the full trigger history.

Workflow的標頭包括**Schedules** action when the workflow has at least one schedule:

* 當一個時間表相符時，該操作會直接連結到其詳細資訊頁面。
* 多個計劃：操作連結到Workflow過濾列表`/workflows/schedules?workflowId=<id>`.
* 沒有時間表：動作是隱藏的。

### 觸發歷史記錄 {/* #trigger-history */}

調度程序嘗試記錄帶有運行 ID、計劃時間、實際觸發時間和發布狀態的觸發器行。發布者在聲明事件發生或發布被接受後崩潰不會留下任何觸發行。計劃詳細資訊頁面將記錄的觸發器連接到對應的Workflow運行並顯示：

* 運轉狀態（`running`, `success`, `failed`, `suspended`, `canceled`) as a badge.
* 跑步的開始時間和持續時間。
* 運行完整圖表視圖的連結：`/workflows/:workflowId/graph/:runId`.
* 一個`pending` badge for triggers whose run record hasn't been written yet, due to a race between trigger publish and run snapshot.
* 一個`publish failed` badge with the final publish error after all three attempts fail. The outcome is unknown: the transport may have accepted the event before returning the error.

非終端狀態下的觸發器會導致面板每五秒鐘輪詢一次，直到達到終端狀態。此清單分頁，因此長時間運行的計劃不會預先載入數千行。

## 在運行時暫停計劃 {/* #pausing-a-schedule-at-runtime */}

當計劃的Workflow在生產中失敗時，您無需重新部署或手動編輯資料庫。從 SDK 暫停它：

```typescript
import { MastraClient } from '@mastra/client-js'

const client = new MastraClient({ baseUrl: 'http://localhost:4111' })

// Schedule ids are derived from the workflow id: `wf_<workflowId>` for a
// single declarative schedule, or `wf_<workflowId>__<scheduleId>` when you
// declare multiple schedules per workflow as an array.
await client.pauseSchedule('wf_daily-report')
// ...investigate, ship a fix, then:
await client.resumeSchedule('wf_daily-report')
```

在 Studio 中，開啟日程詳細資訊頁面並選擇**Pause** or **Resume** in the header.

需要了解的一些規則：

* 暫停是持久的。狀態將寫入計劃表並在進程重新啟動和重新部署後繼續存在。即使您更改，聲明性配置 upsert 也不會覆蓋使用者設定的狀態`cron`, `timezone`, `runAt`, `endAt`, or other fields.
* `nextFireAt` from now. A schedule paused for a week doesn't fire seven backlogged runs. It fires on the next regular cron tick.
* 恢復一次性保持其配置`runAt`. If that time passed while the schedule was paused, it fires on the next scheduler tick.
* 取消暫停`resumeSchedule` or the **Resume** button in Studio. Editing the workflow's `schedule` config doesn't unpause a paused row.
* 暫停和恢復是冪等的。對已經暫停的計劃呼叫暫停是無操作的。
* 此操作覆蓋控制現有計劃。在程式碼中編寫聲明性時間表。聲明性計劃透過以下方式在程式碼中建立、刪除和編輯`schedule` field on `createWorkflow`. To create schedules imperatively at runtime instead, use the unified [`mastra.schedules`](/docs/harness/schedules) service with a `workflowId`.

底層的 HTTP 路由是`POST /api/schedules/:scheduleId/pause` and `POST /api/schedules/:scheduleId/resume`. Both require the `schedules:write` permission.

## 重新部署並進行更改 {/* #redeploying-with-changes */}

當您更改`schedule` config and redeploy, Mastra diffs the existing schedule row against the new config:

* 如果`cron`, `timezone`, or `endAt` changes on a recurring schedule, `nextFireAt` is recomputed. A cadence with no future occurrence completes the schedule. A recomputed cadence that can still fire reactivates a completed schedule.
* 如果`runAt` changes on a one-off schedule, `nextFireAt` is updated to that time. A future `runAt` reactivates a completed one-off. A past `runAt` leaves it completed.
* `runAt` passed while the app was offline, it remains due and fires on the next scheduler tick. A one-off first registered with a past `runAt` is instead created as `completed` and doesn't fire.
* 如果只是`inputData`, `initialState`, or `metadata` changed, the row is patched in place and the next fire time is preserved.
* 使用者設定的狀態（例如，透過暫停`client.pauseSchedule`) and fire history are never overwritten, unless a timing change above requires a status update.

這`completed` status means the schedule has no automatic fires remaining: its one-off fire was claimed, its recurring cadence was exhausted, or its configured timing was already exhausted during registration or reconciliation. It doesn't confirm that the workflow run completed successfully.

從Workflow中刪除計劃條目`schedule` array deletes its row on the next boot.

## 部署拓撲 {/* #deployment-topology */}

內建調度程式使用`setInterval` tick loop to poll the schedules table and claim due rows. It dispatches workflow runs through the in-process pubsub. It assumes a long-lived host process.

### 長壽主機（推薦） {/* #long-lived-host-recommended */}

部署 Fly Machines、Railway、Render、AWS ECS、GKE 等目標或您自己的伺服器，使 Mastra 進程在 cron 週期之間保持活動狀態。伺服器產生的`mastra build` starts the scheduler automatically, so schedules work without extra setup.

如果您運行 Mastra[server adapter](/docs/server/server-adapters), call `mastra.startWorkers()` after your server starts listening. Adapters don't start the scheduler, and schedules never fire without this call. See [Start background workers](/docs/server/server-adapters#start-background-workers).

對於生產部署，您可以將調度程序作為[dedicated worker process](/docs/deployment/workers#scheduler-worker) to isolate it from the API layer.

### 無伺服器平台 {/* #serverless-platforms */}

Vercel、Netlify、AWS Lambda 和 Cloudflare Workers 等函數即服務平台會在每次請求後關閉進程，因此滴答循環不會獲得第二次滴答，並且程式碼中聲明的計劃目前不會使用內建調度程序觸發。直接運行仍然有效：調用`run.start()` from an HTTP route runs a workflow that declares `schedule` in-process, like any other workflow.

對於這些平台上的 cron 火災，請使用[`@mastra/inngest`](#inngest-workflows) instead. Inngest is serverless-native and holds the cron state for you.

## 攝取Workflow {/* #inngest-workflows */}

這`schedule` field documented on this page drives Mastra's built-in scheduler. If you use `@mastra/inngest`, scheduled workflows are configured through Inngest's own `cron` field on `createFunction` and fire on Inngest's scheduler instead.

實際意義：

* Ingest 時間表不會出現在 Studio 中`/workflows/schedules` view.
* Workflow標題**Schedules** action doesn't show for Inngest workflows.
* `client.pauseSchedule`和`client.resumeSchedule` don't control Inngest schedules.

管理 Ingest 日程[Inngest dashboard](https://www.inngest.com/docs/guides/scheduled-functions). Use Mastra schedules when you want Mastra to own scheduling end to end.
