# Workflow

Workflow可讓您透過清晰、結構化的步驟定義複雜的任務序列，而不是依賴一個Agent來推理整個過程。您可以控制任務分解以及資料流和時間安排。Workflow預設使用內建執行引擎，而託管基礎架構可透過[workflow runners](/docs/deployment/workflow-runners)比如英格斯特。

<Inject>
  **對於人工智慧Agent：**&#x8DD1;步`npx mastra api workflow run start test-workflow '{"inputData":{"message":"Hello, world!"}}'` to start this workflow directly instead of writing a temporary script. The command requires a running Mastra server; start the local server with `npx mastra dev`，或傳遞可存取伺服器的基本 URL`--url`。跑步`npx mastra api workflow run start --schema`在建造不同的輸入之前。安裝 Mastra 的技能`npx skills add mastra-ai/skills --skill mastra`取得完整的 API CLI 發現、定位、架構、驗證和錯誤處理指南。
</Inject>

## 何時使用Workflow {/* #when-to-use-workflows */}

將Workflow用於預先明確定義的任務，並涉及具有特定執行順序的多個步驟。它們使您能夠對資料在步驟之間流動和轉換的方式以及每個階段調用哪些原語進行細粒度控制。

## 核心原則 {/* #core-principles */}

Mastra Workflow遵循以下原則運作：

* 定義**steps** with [`createStep`](/reference/workflows/step), specifying input/output schemas and business logic.
* 構成**steps** with [`createWorkflow`](/reference/workflows/workflow) to define the execution flow.
* 跑步**workflows** to execute the entire sequence, with built-in support for suspension, resumption, and streaming results.

## Workflow狀態 {/* #workflow-state */}



```typescript title="src/mastra/workflows/test-workflow.ts"
import { createStep } from '@mastra/core/workflows'
import { z } from 'zod'

const step1 = createStep({
  id: 'step-1',
  inputSchema: z.object({ message: z.string() }),
  outputSchema: z.object({ formatted: z.string() }),
  stateSchema: z.object({ counter: z.number() }),
  execute: async ({ inputData, state, setState }) => {
    // Read from state
    console.log(state.counter)

    // Update state for subsequent steps
    setState({ ...state, counter: state.counter + 1 })

    return { formatted: inputData.message.toUpperCase() }
  },
})
```

```typescript {29} title="src/mastra/workflows/test-workflow.ts" oxfmt:false
  .then(step1)
  .then(step2)
  .commit();

export const testWorkflow = createWorkflow({
  id: "test-workflow",
  inputSchema: z.object({
    message: z.string()
  }),
  outputSchema: z.object({
    emphasized: z.string()

  .then(childWorkflow)
  .commit();
```

### 克隆Workflow {/* #cloning-a-workflow */}

使用克隆Workflow`cloneWorkflow()` when you want to reuse its logic but track it separately under a new ID. Each clone runs independently and shows up as a distinct workflow in logs and observability tools.

```typescript oxfmt:false {6} title="src/mastra/workflows/test-workflow.ts"
import { cloneWorkflow, createWorkflow, createStep } from "@mastra/core/workflows";

const step1 = createStep({...});

const parentWorkflow = createWorkflow({...})
const clonedWorkflow = cloneWorkflow(parentWorkflow, { id: "cloned-workflow" });

export const testWorkflow = createWorkflow({...})
  .then(step1)
  .then(clonedWorkflow)
  .commit();
```

## 引用Workflow {/* #referencing-a-workflow */}

您可以從Agent程式、Tool、Mastra 用戶端或命令列運行Workflow。透過致電以獲取參考`.getWorkflow()` on your `mastra` or `mastraClient` instance, depending on your setup:


：：：筆記`mastra.getWorkflow()` is preferred over a direct import for two reasons:

1. 它提供對 Mastra 實例配置的存取（記錄器、遙測、儲存、註冊Agent和向量儲存）
2. 它為Workflow輸入和輸出模式提供完整的 TypeScript 類型推斷

## 運行Workflow {/* #running-workflows */}

Workflow可以以兩種模式運作：開始等待所有步驟完成後再返回，而串流在執行期間發出事件。選擇適合您的用例的方法：當您只需要最終結果時開始，當您想要監控進度或在步驟完成時觸發操作時進行串流傳輸。

<Tabs>
  <TabItem value="start" label=".start()">
    使用建立Workflow運行實例`createRun()`, then call `.start()` with `inputData` matching the workflow's `inputSchema`. The workflow executes all steps and returns the final result.

    ```typescript
    const run = await testWorkflow.createRun()

    const result = await run.start({
      inputData: {
        message: 'Hello world',
      },
    })

    if (result.status === 'success') {
      console.log(result.result)
    }
    ```
  </TabItem>

  <TabItem value="stream" label=".stream()">
    使用建立Workflow運行實例`.createRun()`, then call `.stream()` with `inputData` matching the workflow's `inputSchema`. Iterate over `fullStream` to track progress, then await `result` to get the final workflow result.

    ```typescript
    const run = await testWorkflow.createRun()

    const stream = run.stream({
      inputData: {
        message: 'Hello world',
      },
    })

    for await (const chunk of stream.fullStream) {
      console.log(chunk)
    }

    // Get the final result (same type as run.start())
    const result = await stream.result

    if (result.status === 'success') {
      console.log(result.result)
    }
    ```
  </TabItem>
</Tabs>

### Workflow結果類型 {/* #workflow-result-type */}

兩個都`run.start()` and `stream.result` return a discriminated union based on the `status` property, which can be `success`, `failed`, `suspended`, `tripwire`, or `paused`. You can always safely access `result.status`, `result.input`, `result.steps`, and optionally `result.state` regardless of the status.

此外，根據狀態，可以使用不同的屬性：

|狀態 |獨特的性能|描述 |
| - | - | - |
|`success` | `result` | The workflow's output data |
| `failed` | `error` | The error that caused the failure |
| `tripwire` | `tripwire` | Contains `reason`, `retry?`, `metadata?`, `processorId?` |
| `suspended` | `suspendPayload`, `suspended` | Suspension data and array of suspended step paths |
| `paused` | *(none)* | Only common properties available |

若要存取特定於狀態的屬性，請檢查`status` first:

```typescript
const result = await run.start({ inputData: { message: 'Hello world' } })

if (result.status === 'success') {
  console.log(result.result) // Only available when status is "success"
} else if (result.status === 'failed') {
  console.log(result.error.message)
} else if (result.status === 'suspended') {
  console.log(result.suspendPayload)
}
```

```json
  }
```


### 使用Agent商的Workflow {/* #workflow-using-an-agent */}

管道Agent`textStream` to the workflow step's `writer`. This streams partial output, and Mastra automatically aggregates the agent's usage into the workflow run.

```typescript
import { createStep } from '@mastra/core/workflows'
```

## 重新啟動活動Workflow運行 {/* #restarting-active-workflow-runs */}

當Workflow運行失去與伺服器的連線時，可以從最後一個活動步驟重新啟動。这对于长时间运行的工作流非常有用，这些工​​作流在服务器失去连接时可能仍在运行。重新启动Workflow运行将从最后一个活动步骤恢复执行，并且Workflow将从那里继续。

### 重新啟動Workflow的所有活動Workflow運行`restartAllActiveWorkflowRuns()` {/* #restarting-all-active-workflow-runs-of-a-workflow-with-restartallactiveworkflowruns */}

使用`restartAllActiveWorkflowRuns()` to restart all active workflow runs of a workflow. This helps restart all active workflow runs of a workflow, without having to manually loop through each run and restart.

```typescript
workflow.restartAllActiveWorkflowRuns()
```

同時運行重新啟動，最多`recovery.workflowConcurrency` at a time (default `5`). Set it to `1` in the Mastra config if your runs share side effects that must not run in parallel.

將Workflow排除在由以下原因觸發的自動啟動時重新啟動之外：`Mastra.restartAllActiveWorkflowRuns()`, set `autoRestartActiveRuns: false` in the workflow's `options`. This is useful for workflows with side effects that must not be re-driven by a blanket restart. Durable agent workflows set this automatically because their recovery is owned by the opt-in `recovery.durableAgents: 'auto'` path.

當運行執行時，Mastra 會保留其儲存租約並在背景更新它。`restart()` refuses to take over a run whose lease hasn't expired: it throws a `WORKFLOW_RESTART_RUN_OWNED` error and the sweep skips the run. The lease is advisory and doesn't fence writes. If a process stops renewing its lease but keeps executing a step, for example because its event loop is blocked for longer than the lease TTL, recovery can run that step a second time. `workflow.restartAllActiveWorkflowRuns()` skips such a run without a recheck, so call it after the lease expires if you need to recover that run. Storage adapters without run-ownership support keep the previous behavior and restart every active run.

`mastra.restartAllActiveWorkflowRuns()`，伺服器在啟動時調用它，僅在預設引擎停止後重新啟動它：沒有實例保留其租約，並且運行及其租約都沒有更改`recovery.workflowGraceMs` (2 seconds by default). A run that's still running, or stopped more recently, is left to the [recovery loop](#recovery-loop).

Evented 在 pubsub 上運行，其Agent程式重新傳遞未確認的事件（Redis Streams、Valkey Streams、Google Cloud Pub/Sub）留給Agent程式：當工作進程中途停止時，Agent程式將該步驟的事件重新傳遞給另一個工作進程，並且啟動實例不會重新啟動運行。計劃運行是例外，因為它們的事件保留在觸發它們的進程中，因此恢復會重新啟動它們。在任何其他 pubsub 上，包括預設的進程內發布訂閱，恢復都會立即重新啟動每個活動的事件運行。行程內 pubsub 僅在一個行程內傳遞事件，因此事件Workflow不支援使用它在一個儲存體上執行多個執行個體。

重新啟動的運行會再次執行中斷的步驟，即使該步驟在進程停止之前完成，但其結果未儲存。在事件引擎上，當事件延遲到達時，已保存其結果的步驟不會再次運行，例如在Agent重新交付或`restart()` that ran while the step was saving its result. The run continues from the saved result instead. This needs a storage adapter with run-ownership support. Workflows that set `autoRestartActiveRuns: false`, including durable agent workflows, run the step again. Make steps with side effects idempotent, so a repeated step has no additional effect.

一步的`execute` function receives `runId` and `workflowId`. Combine them with the `id` you gave the step in `createStep()`, plus a name for each side effect when the step performs more than one, to build an idempotency key.

有些步驟需要部分密鑰來自其輸入：

* 嵌套Workflow可以接收新的`runId` when it's recovered or redelivered. Pass the parent's `runId` into the nested workflow's input and use it in place of the nested `runId`.
* `foreach`每個項目運行一次相同的步驟。從步驟的輸入新增一個標識該項目的 ID。
* 循環在每次迭代中運行相同的步驟。從步驟中返回迭代編號，並在下一次迭代時從輸入中讀取它。重複或恢復的迭代接收相同的輸入，因此數字不會改變。

有關Agent呼叫的Tool，請參閱[make tools safe to repeat](/docs/harness/durable-agents#make-tools-safe-to-repeat).

### 恢復循環 {/* #recovery-loop */}

`mastra.startWorkers()`也會在執行編排工作執行緒的實例上啟動恢復循環。每一個`recovery.workflowScanIntervalMs` (60 seconds by default, give or take a fifth), it restarts the default-engine runs that stopped, by the same rule as `restartAllActiveWorkflowRuns()`. A run whose instance crashed is restarted at the first pass after its lease expired (`MASTRA_AGENT_THREAD_LEASE_TTL_MS`, 15 seconds by default) and `recovery.workflowGraceMs` passed. When a pass finds a run in its grace period, the next pass runs once that period ends, but no sooner than a second later.

共用儲存適配器的實例透過儲存中的租用行選擇一個循環領導者。僅運行領導者的循環列表。其他實例的循環只是試圖取代它的位置。领导者一直保持这个角色，直到其`stopWorkers()` or `shutdown()` hands it back, or until its lease expires after a crash. With `restartAllActiveWorkflowRuns()` at boot, each instance still restarts its own stopped default-engine runs, whichever instance leads. Between boots, the loop recovers only the workflows the leader registers, so instances that register different workflows on one storage get loop recovery for the leader's workflows only and the others' runs at their next boot. A run the loop restarts executes on the leader.

```typescript title="src/mastra/index.ts"
export const mastra = new Mastra({
  recovery: { workflowScanIntervalMs: 30_000 },
})
```

循環永遠不會重新啟動事件運行。重新傳遞未確認事件的Agent程式會恢復它們，並在其他 pubsub 上`restartAllActiveWorkflowRuns()` restarts them at boot. The loop also leaves workflows that set `autoRestartActiveRuns: false` alone, and an instance that registers no other default-engine workflow never claims the leader row. It doesn't run when `recovery.workflows` is `'off'`, on an instance started with `workers: false` or a `MASTRA_WORKERS` filter without `orchestration`, or on a storage adapter without run-ownership support. A process that calls `restartAllActiveWorkflowRuns()` but never `startWorkers()` runs no loop.

### 重新啟動活動Workflow運行`restart()` {/* #restarting-an-active-workflow-run-with-restart */}

使用`restart()` to restart an active workflow run from the last active step. This will resume execution from the last active step, and the workflow will continue from there.

```typescript
const run = await workflow.createRun()

const result = await run.start({ inputData: { value: 'initial data' } })

const restartedResult = await run.restart()
```

### 識別活動Workflow運行 {/* #identifying-active-workflow-runs */}

當Workflow運行處於活動狀態時，它將有一個`status` of `running` or `waiting`. You can check the workflow's `status` to confirm it's active, and use `active` to identify the active workflow run.

```typescript
const activeRuns = await workflow.listActiveWorkflowRuns()
if (activeRuns.runs.length > 0) {
  console.log(activeRuns.runs)
}
```

：：：筆記

當 Mastra 伺服器啟動時，它會重新啟動不再運行的執行個體的活動Workflow運行，並且其復原循環會針對預設引擎運行繼續執行此操作。

## 使用`RequestContext` {/* #using-requestcontext */}

使用[RequestContext](/docs/server/request-context) to access request-specific values. This lets you conditionally adjust behavior based on the context of the request.

```typescript title="src/mastra/workflows/test-workflow.ts"
import { createStep } from '@mastra/core/workflows'

export type UserTier = {
  'user-tier': 'enterprise' | 'pro'
}

const step1 = createStep({
  execute: async ({ requestContext }) => {
    const userTier = requestContext.get('user-tier') as UserTier['user-tier']

    const maxResults = userTier === 'enterprise' ? 1000 : 50

    return { maxResults }
  },
})
```

訪問[Request Context](/docs/server/request-context) for more information.
