# 內置 MCP 伺服器

Mastra 伺服器透過 `/api/mcp`，讓 [Model Context Protocol (MCP)](https://modelcontextprotocol.io/introduction) 用戶端存取你的 Agent、Workflow 及 Tool。你毋須為此定義 `MCPServer`：在 `Mastra` 實例註冊的每個 Agent、Workflow 及 Tool 均可使用，日後新增的 Agent 亦會自動出現。

每個 MCP Tool 都是現有 HTTP 路由的輕量封裝。呼叫會經過與 HTTP 請求相同的參數驗證、身分驗證、RBAC、FGA 及擁有權檢查，並使用相同的 `RequestContext`。MCP 用戶端可執行的操作，不會超出同一用戶經 HTTP API 可執行的範圍。

內置伺服器可讓編程助理及其他 MCP 用戶端操作你正在執行的 Mastra 應用程式。若要以自己的提示詞及資源發佈一組精選能力，請另行建立 [`MCPServer`](/docs/connections/mcp#expose-a-mastra-mcp-server)。

## 安裝 {/* #installation */}

此端點使用 `@mastra/mcp`；`@mastra/server` 將它列為可選的 peer dependency。在專案安裝該套件即可啟用內置伺服器：

```bash npm2yarn
npm install @mastra/mcp@latest
```

未安裝時，伺服器的其他功能仍可運作；`/api/mcp` 會傳回 HTTP 501 及提示安裝套件的 JSON-RPC 錯誤。只有專案安裝了 `@mastra/mcp`，`mastra build` 才會將它加入建置輸出。

## 何時提供端點 {/* #when-its-served */}

| 環境 | 是否提供 `/api/mcp` |
| - | - |
| `mastra dev` | 是，即使未設定身分驗證亦會提供。為防止 DNS 重綁定，帶有外來 `Origin` 或 `Host` 標頭的請求會被拒絕；隧道及區域網絡 IP 位址同樣受限制。如需從其他電腦存取，請將 `server.host` 設為用戶端連線時使用的主機名稱或 IP 位址。單純綁定 `0.0.0.0` 並不會允許其他主機。 |
| 已設定 `server.auth` 的正式環境版本 | 是。每個請求均需要 bearer token。 |
| 未設定 `server.auth` 的正式環境版本 | 否，端點傳回 404。 |

設定 `server.mcp.enabled` 可覆蓋預設行為。`false` 會在所有環境關閉端點。`true` 則會在沒有 `server.auth` 時仍提供端點，並記錄警告，因為任何能連接伺服器的人都可呼叫你的 Agent、Workflow 及 Tool。

## 連線客戶端 {/* #connect-a-client */}

啟動開發伺服器，然後讓用戶端連接端點。以 Claude Code 為例：

```bash
claude mcp add --transport http mastra http://localhost:4111/api/mcp
```

設定身分驗證後，傳入 bearer token：

```bash
claude mcp add --transport http mastra https://my-app.example.com/api/mcp \
  --header "Authorization: Bearer $MASTRA_TOKEN"
```

如需從命令列檢視 Tool，請使用 [MCP Inspector](https://github.com/modelcontextprotocol/inspector)：

```bash
npx @modelcontextprotocol/inspector --cli http://localhost:4111/api/mcp \
  --transport http --header "Authorization: Bearer $MASTRA_TOKEN" --method tools/list
```

Cursor 及 VS Code 會從 JSON 檔案讀取伺服器設定。使用 Cursor 時，請將設定加入 `.cursor/mcp.json`：

```json title=".cursor/mcp.json"
{
  "mcpServers": {
    "mastra": {
      "url": "http://localhost:4111/api/mcp",
      "headers": { "Authorization": "Bearer <your-token>" }
    }
  }
}
```

使用 VS Code 時，則加入 `.vscode/mcp.json`：

```json title=".vscode/mcp.json"
{
  "servers": {
    "mastra": {
      "type": "http",
      "url": "http://localhost:4111/api/mcp",
      "headers": { "Authorization": "Bearer <your-token>" }
    }
  }
}
```

伺服器未設定 `server.auth` 時，省略 `headers`。部分用戶端只接受 URL，無法傳送 `Authorization` 標頭，例如 Claude 應用程式中的自訂連接器；它們需要 [OAuth 探索機制](#oauth-discovery)，以及容許用戶登入的身分供應商。

端點使用無狀態 Streamable HTTP，同時支援 MCP `2026-07-28` 及現時用戶端使用的 2025 年版本，因此請求之間不會保留工作階段。

### 在 Studio 中 {/* #in-studio */}

Studio 的 **MCP Servers** 頁面會在你自行註冊的 MCP 伺服器之上，以 **Mastra (built-in)** 顯示內置伺服器。頁面會列出端點 URL（包括自訂的 `server.mcp.path` 或 `apiPrefix`）、端點是否開放或由 `server.auth` 保護、提供哪些 Tool 集（`include` 和 `exclude` 設定不會反映在此），以及可複製的 Claude Code、Cursor、VS Code 和 MCP Inspector 設定。設定內的 `<your-token>` 是預留位置，請換成自己的 bearer token。若端點已關閉或尚未安裝 `@mastra/mcp`，資訊卡會說明原因及處理方法。

端點 URL 按 Studio 存取伺服器時使用的地址產生。如果 MCP 用戶端經另一個公開 URL 存取伺服器，例如經過代理，請在用戶端設定中改用該 URL。使用 [OAuth 探索機制](#oauth-discovery) 時，可登入的用戶端毋須設定 `Authorization` 標頭。

Studio 經 `GET /api/mcp/builtin` 讀取這些資料，該請求需要 `mcp:read` 權限。Tool 清單取決於呼叫者的 token，因此 Studio 不會列出伺服器的 Tool，也不提供試用功能。請連接用戶端查看你可用的 Tool。

## Tool {/* #tools */}

伺服器按 Tool 集為 Tool 分組。本節介紹 `agents`、`workflows` 及 `tools`；其他 Tool 集請參閱[記憶、可觀測性及 Agent 建構器](#memory-observability-and-agent-builder)。操作類 Tool 以 ID 作為參數來存取 Agent 及 Workflow，所以即使新增 Agent，Tool 清單的長度亦不變。

各 Tool 的參數、路由及權限，請參閱[內置 MCP Tool 參考](/reference/server/builtin-mcp-tools)。

| Tool 集 | Tool | 對應的 HTTP 路由 |
| - | - | - |
|`agents` | `list_agents`, `get_agent`, `call_agent` | `GET /agents`, `GET /agents/:agentId`, `POST /agents/:agentId/generate` |
| `workflows` | `list_workflows`, `get_workflow`, `start_workflow`, `get_workflow_run`, `resume_workflow_run`, `cancel_workflow_run` | `GET /workflows`, `GET /workflows/:workflowId`, `POST /workflows/:workflowId/start-async`, `GET /workflows/:workflowId/runs/:runId`, `POST /workflows/:workflowId/resume-async`, `POST /workflows/:workflowId/runs/:runId/cancel` |
| `tools` | 每個已註冊 Tool 對應一個 `tool_<id>` | `POST /tools/:toolId/execute` |

- 當呼叫者可見的 Agent 或 Workflow 不超過 `enumLimit`（預設為 25），`agentId` 及 `workflowId` 參數會列出允許使用的 ID。超過上限後，參數只接受一般字串，用戶端須透過 `list_agents` 或 `list_workflows` 查找 ID。
- 若呼叫者可見的 Tool 多於 `enumLimit`，系統會以 `list_tools`、`get_tool` 及 `call_tool` 取代各個 `tool_<id>`。
- `call_agent` 會傳回回覆文字及 `threadId`。再次傳入 `threadId` 可延續 Agent 記憶中的對話。若沒有傳入 `threadId`，就會開始新執行緒；因此一直不傳入的用戶端，每次呼叫都會留下新執行緒。
- `start_workflow` 會等候執行完成或暫停。暫停時會傳回 `runId` 及暫停資料，可用 `resume_workflow_run` 繼續。
- 未有設定 `description` 的 Agent 會獲分配通用描述，日誌亦會記錄警告。請加入描述，方便用戶端選擇合適的 Agent。

### 精選 Agent 及 Workflow {/* #featured-agents-and-workflows */}

將 Agent 及 Workflow 列入 `featured`，即可為它們提供獨立 Tool。精選 Workflow 的 Tool 會直接使用該 Workflow 的輸入 schema：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  // ...agents, workflows, tools
  server: {
    mcp: {
      featured: { agents: ['support-agent'], workflows: ['refund'] },
    },
  },
})
```

這會在操作類 Tool 旁新增 `agent_support-agent` 及 `workflow_refund`。

## 選擇要公開的內容 {/* #choose-what-to-expose */}

用 `include` 及 `exclude` 按 ID 選擇要開放的能力。每個項目都會同時比對能力本身的 `id`，以及在 `new Mastra({ ... })` 中註冊的鍵，所以 `deleteAccountTool` 和 `delete-account` 會選中同一個 Tool。`exclude` 優先於 `include`。被排除的能力不會出現在 Tool 清單，用任何一個名稱呼叫都會顯示找不到；將被排除 Agent 的 ID 傳給記憶 Tool 亦一樣。可觀測性 Tool 不受篩選影響：結果仍可能包含被排除能力的 trace、日誌及評分。選擇只影響 MCP，不會改動 HTTP 路由。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  server: {
    mcp: {
      toolsets: ['agents', 'tools'],
      include: { agents: ['support-agent', 'billing-agent'] },
      exclude: { tools: ['delete-account'] },
    },
  },
})
```

設定 `readOnly: true` 後，只會提供對應路由需要 `read` 權限的 Tool，例如 `list_agents` 及 `get_workflow_run`。

用戶端可透過 `?toolsets=agents,tools` 或 `X-MCP-Toolsets` 標頭，以及 `?readonly=1` 或 `X-MCP-Readonly` 標頭，進一步限制個別連線的 Tool。這些設定只能減少 Tool，不能加入伺服器設定原本不提供的 Tool。

## 身分驗證及權限 {/* #authentication-and-permissions */}

端點只接受 `Authorization: Bearer` 標頭中的憑證，並由 `server.auth` 驗證。工作階段 Cookie、`apiKey` 查詢參數及 Studio 的驗證設定均不適用，因此不能利用瀏覽器工作階段從其他網站存取端點。其他路由維持原有的驗證行為。

設定 [RBAC](/docs/auth/overview) 後，使用 MCP 除了需要對應路由的權限，亦需要以下兩項權限：

- `mcp:read`：連接及列出 Tool。
- `mcp:execute`：查看及呼叫任何 Tool。即使呼叫者可以經 HTTP 執行相同操作，缺少此權限時取得的 Tool 清單仍是空白。

每次呼叫亦需要對應 HTTP 路由的權限，例如 `call_agent` 需要 `agents:execute`，`start_workflow` 需要 `workflows:execute`。預設 `viewer` 角色有 `mcp:read`，但沒有 `mcp:execute`；`member`、`admin` 及 `owner` 兩者皆有。這兩項權限亦用於保護你註冊的 `MCPServer` 實例路由，所以獲准使用自建 MCP 伺服器的角色也可使用內置伺服器。

Tool 清單會按呼叫者篩選。只有呼叫者能在 `GET /agents` 或 `GET /workflows` 看到的 Agent 及 Workflow 才會出現，當中包括 [FGA](/docs/auth/fga) 讀取權限檢查。呼叫後會收到 403 的 Tool 會被隱藏。系統在每次執行時再次檢查權限，因此過時的清單無法用來繞過限制。

執行緒及執行紀錄的擁有權規則與 HTTP API 一樣：用戶不能延續其他用戶的執行緒，亦不能恢復其他用戶的 Workflow 執行。

傳入的 bearer token 不會作為參數交給 Tool，也不會轉發至其他伺服器。Tool 收到的 `RequestContext` 與對應 HTTP 請求相同。

## 記憶、可觀測性及 Agent 建構器 {/* #memory-observability-and-agent-builder */}

這些 Tool 集預設啟用。每組只有在伺服器具備對應能力時才會提供；每個 Tool 都會呼叫表列的 HTTP 路由，並執行相同的權限及擁有權檢查。

| Tool 集 | Tool | 提供條件 |
| - | - | - |
| `memory` | `list_threads`, `get_thread`, `list_messages`, `search_memory`, `get_memory_status`, `get_observations`, `create_thread`, `update_thread`, `clone_thread`, `save_messages` | Agent 具備記憶功能，或已設定儲存型 Agent |
| `observability` | `query_traces`, `aggregate_traces`, `query_spans`, `aggregate_spans`, `query_threads`, `get_trace_query_fields`, `get_trace_query_values`, `get_trace`, `get_span`, `get_trace_trajectory`, `list_logs`, `list_traces` | 儲存系統具備可觀測性範疇 |
| `observability_analytics` | `analyze_metrics`, `analyze_scores`, `analyze_feedback`, `list_metric_names`, `list_scores`, `list_feedback` | 儲存系統具備可觀測性範疇 |
| `stored_agents` | `list_available_models`, `list_stored_agents`, `get_stored_agent`, `create_stored_agent`, `update_stored_agent` | 已設定[編輯器](/docs/studio/editor)及 Agent 儲存範疇 |

- 記憶 Tool 需要 `agentId` 及 `threadId`。若 `server.auth` 透過 `mapUserToResourceId` 把用戶對應至資源，`resourceId` 預設為呼叫者的資源 ID，而呼叫者不能讀寫其他資源的執行緒、訊息或 Observational Memory。沒有此對應設定時，傳入的 `resourceId` 會如 HTTP API 一樣直接使用。
- 可觀測性 Tool 取決於儲存系統支援甚麼功能。支援 trace 查詢的儲存系統（如 DuckDB）會提供 `query_traces` 等查詢 Tool；不支援的則提供 `list_traces`。日誌、指標、評分及意見回饋 Tool 只會在儲存系統實作相關功能時出現。
- `get_trace` 傳回精簡 trace，包含各 span 的 ID、父項、名稱、類型、時間、狀態及實體。呼叫 `get_span` 可取得單一 span 的輸入、輸出及屬性。清單及 trace 結果限制在約 40,000 個字元以內。若結果被截斷，會提示如何取得其餘內容：縮小每頁數量，或用傳回的 `nextOffset` 呼叫 `get_trace`。若單一項目仍過大，例如包含行內圖片的訊息，較長的值會被截斷並標記。`get_span` 會傳回完整 span；`get_observations` 亦會以同樣方式截斷過大的紀錄。
- `analyze_metrics`、`analyze_scores` 及 `analyze_feedback` 的 `op` 可設為 `aggregate`、`breakdown`、`timeseries` 或 `percentiles`；各項操作會呼叫對應的 `/observability/<source>/<op>` 路由。
- `create_stored_agent` 及 `update_stored_agent` 預設會發佈變更，所以可以立即用 `call_agent` 呼叫 Agent。傳入 `autoPublish: false` 可保留草稿。`call_agent` 的 `agentId` 參數只列出用戶端取得 Tool 清單時已存在的 Agent；要呼叫新建立的 Agent，用戶端須重新取得清單。

在唯讀模式，查詢及彙總 Tool 仍可使用，因為對應路由只需要 `observability:read`，即使它們使用 `POST`。記憶及儲存型 Agent 的寫入 Tool 會被移除。`get_observations` 仍會保留，但不提供 `waitForPending` 選項，因為等候操作會呼叫需要 `memory:write` 的路由；沒有 `memory:write` 權限的呼叫者使用 `get_observations` 時也看不到該選項。

:::warning

可觀測性資料不會按呼叫者隔離。任何擁有 `observability:read` 權限的人，都可經 MCP 或 HTTP 讀取所有用戶的 trace、日誌、評分及意見回饋。預設 `viewer` 角色會透過 `*:read` 取得這項權限。對不應查看其他用戶資料的角色，請移除其 `observability:read` 權限，或不提供可觀測性 Tool 集：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  server: {
    mcp: { toolsets: ['agents', 'workflows', 'tools', 'memory', 'stored_agents'] },
  },
})
```

:::

### Agent 建立 Agent {/* #agents-creating-agents */}

`create_stored_agent` 可讓 MCP 用戶端建立其他用戶端之後可呼叫的 Agent，需要 `stored-agents:write` 權限。新 Agent 由呼叫者擁有，預設為私人。如果沒有呼叫者身分（例如未設定 `server.auth`），Agent 就沒有擁有者，即使設成 `visibility: 'private'` 亦會公開。其他用戶在 `list_agents` 或 `list_stored_agents` 看不到私人 Agent；除非是管理員或按 ID 獲授權使用該 Agent，否則呼叫時會跟 HTTP API 一樣收到找不到的回應。設為 `visibility: 'public'` 可讓所有用戶呼叫。不論是否公開，只有擁有者、管理員及按 ID 獲授權的用戶可編輯；沒有擁有者的 Agent 則可由任何具有 `stored-agents:write` 權限的用戶編輯。詳見[儲存型 Agent 的可見性](/docs/studio/editor#visibility)。

當 Agent 建構器限制模型時，MCP Tool 只接受下列位置使用獲准模型：Agent 執行模型的 `provider` 及 `name`（包括每個條件分支）、`defaultOptions` 指定的模型（例如 `structuredOutput.model`）、備用 `modelList` 中每個已啟用項目、記憶模型（Observational Memory 的 observer、reflector 及標題模型），以及處理器圖任何深度的每個輸入及輸出處理步驟的 `model`。若設定會使用政策無法檢查的預設模型，Tool 亦會拒絕，例如 `observationalMemory: true`、沒有指定 `model` 的 Observational Memory 設定、建立時省略記憶設定（建構器會以預設模型填入 Observational Memory），或 `moderation` 等需要模型卻未指定的處理器。請明確設定獲准的 `model`。

儲存型 Agent 的 `model` 只接受 `provider`、`name` 及 `temperature` 等模型設定；`modelId`、`providerId` 等其他鍵會被拒絕。如果無法載入 Agent 建構器的政策，Tool 會傳回錯誤，不會跳過檢查直接儲存。`list_available_models` 會傳回獲准模型。HTTP 路由沒有執行這項檢查，因此可直接呼叫 `POST /stored/agents` 的用戶仍能儲存任何模型。嵌入模型（`memory.embedder`）不在建構器的模型清單內，也不會被檢查。儲存 Agent 時不會檢查 Tool 的允許清單，所以新 Agent 可使用伺服器提供的任何 Tool；Tool 會以呼叫該 Agent 的用戶權限執行。

Observational Memory 只會在執行緒達到 token 門檻後開始觀察，預設門檻為 30,000 個 token。若要做簡短示範，可降低 `observation.messageTokens`，讓 Agent 從少量訊息中學習。Observational Memory 會在背景處理訊息，因此呼叫 `call_agent` 後，請立即以 `waitForPending: true` 呼叫 `get_observations`，等候處理完成（最多 30 秒）才讀取。

## OAuth 探索機制 {/* #oauth-discovery */}

設定 `server.auth` 後，端點會按照 [MCP 授權規格](https://modelcontextprotocol.io/specification/draft/basic/authorization) 告知 MCP 用戶端如何取得 token。沒有有效 token 的請求會收到 `401`，其 `WWW-Authenticate` 標頭會指向端點的受保護資源中繼資料（[RFC 9728](https://datatracker.ietf.org/doc/html/rfc9728)）：

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://my-app.example.com/.well-known/oauth-protected-resource/api/mcp"
```

如果請求帶有未能通過驗證的 token，例如已過期，標頭亦會包含 `error="invalid_token"`。其他路由傳回 `401` 時不會附上此標頭。

中繼資料公開提供於 `/.well-known/oauth-protected-resource/api/mcp` 及 `/.well-known/oauth-protected-resource`，不在 API 前綴之下：

```json
{
  "resource": "https://my-app.example.com/api/mcp",
  "authorization_servers": ["https://my-tenant.us.auth0.com/"],
  "bearer_methods_supported": ["header"]
}
```

用戶端讀取 `authorization_servers` 後，會在身分供應商進行 OAuth 流程，再帶著存取 token 重試。Mastra 本身不充當授權伺服器。用戶端能否在未預先註冊 OAuth 應用程式的情況下登入，取決於身分供應商是否支援動態用戶端註冊或用戶端 ID 中繼資料文件。

Mastra 會按 `server.mcp.oauth` 及身分驗證供應商的資料填入中繼資料：

- `resource` 預設為根據請求得出的端點 URL。若伺服器位於代理或負載平衡器後方，請求可能帶有內部主機名稱，請把 `server.mcp.oauth.resource` 設為公開 URL。該值必須是沒有片段的絕對 `https` URL（`localhost` 可使用 `http`）。無效值會記錄錯誤並關閉 OAuth 探索機制，但系統仍會按該值檢查 token 受眾，因此修正前 MCP 請求會被拒絕。
- 驗證要求中的中繼資料 URL，會使用 `resource` 的來源及伺服器上的端點路徑，例如 `/.well-known/oauth-protected-resource/api/mcp`。若代理以另一個公開路徑提供端點，亦必須把這個 well-known URL 轉發至 Mastra。
- 若供應商知道自己的簽發者，`authorization_servers` 會取自供應商（見下表）；否則請設定 `server.mcp.oauth.authorizationServers`。兩者皆無時，該欄位會省略，用戶端需要自行設定 token。
- 只有設定 `server.mcp.oauth.scopesSupported`，中繼資料才會包含 `scopes_supported`。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { MastraAuthWorkos } from '@mastra/auth-workos'

export const mastra = new Mastra({
  server: {
    auth: new MastraAuthWorkos(),
    mcp: {
      oauth: {
        resource: 'https://my-app.example.com/api/mcp',
        authorizationServers: ['https://my-app.authkit.app'],
      },
    },
  },
})
```

### Token 受眾 {/* #token-audience */}

設定 `server.mcp.oauth.resource` 亦會令端點檢查 token 是否為此端點簽發：token 的 `aud` 聲明必須包含 `resource` 的值。為另一個 API 簽發的 token 會收到附帶 `error="invalid_token"` 的 `401`，因此從其他服務外洩的 token 無法在 MCP 端點重用。沒有設定 `resource` 時，身分驗證供應商接受的任何 token 都可如常使用。這項檢查只適用於 `/api/mcp`；其他路由仍接受為不同 API 簽發的 token。比對必須完全一致，所以結尾有斜線的 `https://my-app.example.com/api/mcp/` 不等於 `https://my-app.example.com/api/mcp`。

請設定身分供應商簽發面向該受眾的 token，例如在 Auth0 將 `resource` URL 註冊為 API 識別碼。Auth0 亦會驗證自己的 `audience` 選項（`AUTH0_AUDIENCE`），所以應把該選項設為 `resource` URL，或簽發 `aud` 同時包含兩個值的 token。

| Provider | 公布的授權伺服器 | 是否按 `resource` 檢查受眾 |
| - | - | - |
| [`MastraJwtAuth`](/reference/auth/jwt) | `issuer` 選項 | 是 |
| [Auth0](/reference/auth/auth0) | `https://<domain>/` | 是 |
| [Okta](/reference/auth/okta) | `issuer` 選項 | 否。Okta 按自己的 `audience` 選項檢查 token，請把該選項設為 `resource` URL。 |
| [Clerk](/reference/auth/clerk) | 從可發佈金鑰取得的前端 API URL。OAuth 應用程式必須簽發 JWT 存取 token（2026 年 1 月起建立的應用程式預設如此）；不透明 token 會被拒絕。 | 否 |
| [Supabase](/reference/auth/supabase) | `<url>/auth/v1`。只有為 Supabase 專案啟用 OAuth 2.1 伺服器後，用戶端才可在此登入。 | 否 |
| [`CompositeAuth`](/docs/auth/composite-auth) | 所有內部供應商的伺服器 | 交由驗證 token 的供應商處理 |
| WorkOS、Google、Neon、Firebase、Better Auth、自訂供應商 | 設定 `authorizationServers` | 否 |

設定 `resource` 後，若供應商無法檢查受眾，Mastra 會在啟動時記錄警告，並接受該供應商面向任何受眾的 token。這樣 API key 及其他不透明 token 仍可使用。若要在 `/api/mcp` 拒絕它們，請設定 `requireAudience: true`：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { CompositeAuth, SimpleAuth } from '@mastra/core/server'
import { MastraJwtAuth } from '@mastra/auth'

const jwtAuth = new MastraJwtAuth({
  jwksUri: 'https://auth.example.com/.well-known/jwks.json',
  issuer: 'https://auth.example.com/',
})
const apiKeyAuth = new SimpleAuth({ tokens: { [process.env.API_KEY!]: { id: 'ci' } } })

export const mastra = new Mastra({
  server: {
    auth: new CompositeAuth([jwtAuth, apiKeyAuth]),
    mcp: {
      oauth: { resource: 'https://my-app.example.com/api/mcp', requireAudience: true },
    },
  },
})
```

啟用 `requireAudience` 後，由 `SimpleAuth` 等無法檢查受眾的供應商驗證的請求，會在 `/api/mcp` 收到附帶 `error="invalid_token"` 的 `401`。在 `CompositeAuth` 內，只有這些供應商接受的請求會被拒絕；其他路由仍會接受。`requireAudience` 需要配合 `resource`；未設定 `resource` 就不會檢查。

自訂供應商可實作 `verifyAudience()` 及 `getOAuthMetadata()` 以支援這項機制；詳見[自訂身分驗證供應商](/docs/auth/custom-auth-provider)。

### 連接 OAuth 用戶端 {/* #connect-an-oauth-client */}

若身分供應商支援動態用戶端註冊，可不帶 token 新增伺服器；用戶端會在首次使用時啟動登入流程：

```bash
claude mcp add --transport http mastra https://my-app.example.com/api/mcp
```

否則，請向身分供應商取得以 `resource` 為受眾的存取 token，並透過標頭傳入：

```bash
claude mcp add --transport http mastra https://my-app.example.com/api/mcp \
  --header "Authorization: Bearer $MASTRA_TOKEN"
```

端點目前不會傳回附帶 `error="insufficient_scope"` 的 `403`。沒有 `mcp:read` 權限的呼叫者只會收到一般 `403`，因為 Mastra 權限並非用戶端可以要求的 OAuth scope。

## 限制 {/* #limitations */}

- Workflow 會在 MCP 請求內同步執行。長時間執行的 Workflow 受伺服器請求逾時限制。
- `Agent`、`Workflow` 及 Tool 建構函式目前沒有逐項關閉 MCP 存取的選項；請使用 `server.mcp.include` 及 `server.mcp.exclude`。
- 工作記憶、刪除執行緒或儲存型 Agent，以及 scorer 和 Workspace 管理功能均未開放。
