# Knowledge 的應用場景

以下示例展示 Knowledge 的應用場景，說明各 Agent 的角色、每個 scope 存放的內容，以及需要的配置或工具呼叫。Knowledge 本身沒有內置 scope 類型。只有 `resource:` 及 `thread:` 來自 Memory，[`knowledgeMemoryScopes()`](/reference/knowledge/knowledge-memory-scopes) 會宣告這兩種 scope，並加上租戶 scope。

:::alpha

Knowledge 目前為 alpha 版本，API 可能會在不同版本之間變更。

:::

:::warning

每次呼叫工具都會檢查存取權限，但 Knowledge 暫時無法保證資料只會流向持有相關 scope 的執行，亦無法保證 Agent 不會跨 scope 複述內容。以下示例展示預期用途，現階段請勿依賴 Knowledge 隔離敏感資料。

:::

## 按自己的文件回答問題 {/* #answer-from-your-own-docs */}

伺服器用 [`upsertPage()`](/docs/knowledge/load-your-content) 把文件同步至 `product-docs:` scope，並只向文件 Agent 提供讀取工具。Agent 會列出頁面樹、讀取長頁面中符合查詢的行，搜尋沒有結果時會回答不知道。

```typescript
const knowledge = new Knowledge({
  id: 'docs',
  storage,
  tools: { read: true },
  scopes: {
    ...knowledgeMemoryScopes({ org: 'workspace:$workspaceId' }),
    'product-docs:$workspaceId': {
      belongsTo: 'workspace:$workspaceId',
      access: [{ principal: 'workspace:$workspaceId', role: 'viewer' }],
    },
  },
})
```

要回答個別地區的問題，Agent 會要求讀取符合條件的行，連同每處結果前後各一行。

```json
{ "page": "product-docs:initech#billing/refunds", "match": "region 42", "context": 1 }
```

## 以同一 Agent 服務多個客戶 {/* #one-agent-many-customers */}

由一個支援 Agent 服務所有客戶。每名客戶的頁面存放在各自的 `tenant:` scope，並由 `knowledgeMemoryScopes()` 宣告為租戶 scope。

```typescript oxfmt:false
scopes: { ...knowledgeMemoryScopes({ org: 'tenant:$tenantId' }) },
```

伺服器執行 Agent 時，會傳入該客戶的 scope，以及用戶與對話所屬的 scope。

```typescript
await agent.generate(message, {
  scopes: ['tenant:globex', `resource:${userId}`, `thread:${threadId}`],
})
```

Globex 用戶搜尋「續約」時，不會找到 `tenant:acme#renewals`，因為該次執行沒有持有 `tenant:acme`。這與提示無關。如果 Agent 配置了 Memory，`resource:` 及 `thread:` scope 亦會告知 Memory 這次執行所屬的用戶和 Thread。可用 [`explainAccess()`](/docs/knowledge/scopes-and-access#test-access-with-explainaccess) 測試規則。如頁首警告所述，Knowledge 暫時無法保證這種隔離，請勿依賴它保護客戶的敏感資料。

## 讓所有 Agent 遵守同一政策 {/* #a-policy-every-agent-follows */}

合規團隊負責各帳戶的資料處理規則。凡為該帳戶處理銷售、支援或帳務的 Agent，每一輪都要看到這些規則，毋須等到主動搜尋才讀取。只有合規團隊可以更改規則。

在帳戶 scope 宣告頁面，並在配置中釘選。必須在 `Knowledge` 實例設定 `pinnedContext: true`，而且 Agent 已配置 Memory，釘選內容才會加入執行。本頁所有釘選示例均採用這些設定。

```typescript oxfmt:false
'account:$accountId': {
  access: [
    { principal: 'self', role: 'viewer' },
    { principal: 'desk:$accountId:compliance', role: 'editor' },
  ],
  pages: [{ key: 'data-handling', name: 'Data handling rules' }],
  pinnedContext: ['account:$accountId#data-handling'],
},
```

合規團隊寫好頁面後，每次持有 `account:umbrella` 的執行，開始時都會把頁面放入上下文。合規團隊編輯頁面後，正在執行的 Agent 下一輪只會收到變更部分。

合規團隊配置的政策受以下規則保護。

* **Agent 可讀取政策，但不能更改。** 該帳戶的執行只有檢視權限，銷售 Agent 如嘗試編輯頁面，就會被拒絕。
* **Agent 不能取消釘選。** 配置中的釘選來自你的宣告，不在儲存空間內，因此釘選工具不能移除。
* **頁面不能移動或刪除。** 在 `pages` 宣告的頁面屬於配置的一部分。
* **只有可讀取頁面的執行才會收到內容。** 其他帳戶的執行不會收到該頁面。釘選不會讓更多執行有權讀取。

參閱 [釘選上下文](/docs/knowledge/pinned-context)。

## 跨工作階段沿用編碼慣例 {/* #coding-conventions-that-carry-over */}

同一程式碼庫的開發 Agent 共用一個 scope。釘選編碼慣例頁面，把決定記在該頁的筆記內，並加上相關頁面的連結。

```typescript oxfmt:false
'repo:$repo': {
  access: [{ principal: 'self', role: 'editor' }],
  pages: [{ key: 'conventions', name: 'Conventions' }, { key: 'tooling', name: 'Tooling' }],
  pinnedContext: ['repo:$repo#conventions'],
},
```

例如，Agent 在慣例頁面新增「使用 pnpm workspaces，不用 npm」的筆記，並以 `[[repo:api#tooling]]` 連結相關頁面。

在 `repo:api` 的下一個工作階段會看到編碼慣例，旁邊顯示「1 則筆記」。`repo:web` 的工作階段看不到這些內容。

## 按值班經驗改進操作手冊 {/* #runbooks-that-improve-on-call */}

值班工程師是所屬服務 scope 的貢獻者，其 Agent 可在釘選的操作手冊加上筆記，但不能改寫手冊。SRE 主管具有編輯權限，可把筆記內容納入手冊。

```typescript oxfmt:false
'oncall:$orgId:$service': {
  belongsTo: 'org:$orgId',
  access: [
    { principal: 'self', role: 'contributor' },
    { principal: 'role:$orgId:sre-lead', role: 'editor' },
  ],
  pages: [{ key: 'runbook', name: 'Incident runbook' }],
  pinnedContext: ['oncall:$orgId:$service#runbook'],
},
```

值班 Agent 只有貢獻者權限，若嘗試編輯頁面會被拒絕，但仍可新增筆記。

## 以資料夾方式整理頁面 {/* #organize-pages-like-folders */}

頁面可以在 scope 內分層。假設手冊宣告 `refunds`，並把 `damaged-items` 加在它下面。Agent 如不知道確切名稱，可列出頁面樹，再讀取所需頁面。

```json
{ "from": "handbook:acme", "depth": 2 }
```

Agent 會收到各頁的引用（例如 `handbook:acme#refunds/damaged-items`）、名稱和子頁面數目，再讀取所需頁面。

## 按部門劃分 scope {/* #one-scope-per-department */}

各部門在全公司 scope 下各有一個 scope。人力資源部的入職清單放在 `dept:initech:hr`。伺服器把 `firm:initech` 及員工所屬部門的 scope 傳給該員工的每次執行。工程師搜尋不到人力資源部 scope 的內容，但持有 `firm:initech` 的執行均可找到全公司的假期頁面。

```typescript
const scopes = {
  ...knowledgeMemoryScopes({ org: 'firm:$firmId', orgRole: 'contributor' }),
  'dept:$firmId:$dept': {
    belongsTo: 'firm:$firmId',
    access: [{ principal: 'self', role: 'editor' }],
  },
}
```

如要更改內容的可見範圍，請調整配置及伺服器傳入的 scope，毋須重寫提示。

## 讓有需要的人讀取筆記 {/* #notes-for-the-people-who-need-them */}

筆記的 `scope` 列出已標記的範圍。執行只要可讀取頁面，並持有其中至少一個 scope，就可看到筆記。Dana 的 Agent 為一則筆記只標記她自己的 scope，並為另一則筆記同時標記她個人及所屬小組的 scope。

```json
{
  "op": "add",
  "page": "office:hooli#coverage",
  "scope": ["resource:dana", "squad:hooli:support"],
  "text": "Dana is out Nov 10 to 14; Bea covers her queue."
}
```

支援小組的 Bea 只會看到第二則筆記。銷售部的 Sam 兩則都看不到，他的 Agent 也不能用自己無權存取的小組 scope 標記筆記。

## 在不同 Agent 之間交接工作 {/* #hand-work-between-agents */}

同一項目的研究、規劃及開發 Agent 共用一個 scope。研究 Agent 撰寫頁面，規劃 Agent 把計劃寫成其子頁面。開發 Agent 讀取計劃，每完成一步便新增筆記，例如「步驟 1 已在 PR 412 完成」。

各 Agent 毋須直接通訊，只需按相同的存取規則共用頁面。
