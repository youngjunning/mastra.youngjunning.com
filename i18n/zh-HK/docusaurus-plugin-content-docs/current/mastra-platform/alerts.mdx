# 警報

當部署失敗、正在運行的服務停止或停止回應或組織使用量超過計畫閾值時，警報會通知您的團隊。您可以在組織層級配置警報，然後選擇每個警報涵蓋的項目和環境。

组织管理员可以创建和管理警报。其他組織角色對警報設定具有唯讀存取權限。

開啟 [Mastra Platform 控制台](https://projects.mastra.ai)，前往組織設定，再選取 **Alerts**。頁面有三個分頁：

* **警報**列出每個警報及其範圍、目的地、狀態以及啟用或暫停開關。
* **目的地**列出了可以接收通知的 Slack 頻道、Discord 頻道、Microsoft Teams 頻道、電子郵件群組、Webhook 終端點、PagerDuty 服務和 Incident.io 警報來源。
* **活動**顯示事件以及與之相關的通知嘗試。

## 新增目的地 {/* #add-a-destination */}

目的地定義了 Mastra 發送通知的位置。建立警報之前至少要新增一個目的地。

|目的地 |配置|
| - | - |
| **Slack** | 連接 Slack Workspace 並選擇一個或多個頻道。Mastra 會為每個選定頻道分別建立目的地。 |
| **Discord** | 輸入 Discord 頻道的 Webhook URL。請參閱[向 Discord 發送警報](#send-alerts-to-discord)。 |
| **Microsoft Teams** | 輸入會在頻道發佈訊息的 Teams Workflow URL。請參閱[向 Microsoft Teams 發送警報](#send-alerts-to-microsoft-teams)。 |
| **Email** | 選擇組織角色、個別成員，或最多 10 個電郵地址。組織成員變動時，按角色設定的收件人群組會同步更新。 |
| **Webhook**|輸入 HTTPS 端點。 Mastra 對每個請求進行簽名，並在建立目的地後顯示簽名金鑰。 |
| **PagerDuty** | 輸入 PagerDuty Events API v2 整合的 Integration key。請參閱[向 PagerDuty 發送警報](#send-alerts-to-pagerduty)。 |
| **Incident.io** | 輸入 incident.io HTTP 警報來源的設定 ID 和 Token。請參閱[向 incident.io 發送警報](#send-alerts-to-incidentio)。 |

<Steps>
  <StepItem>
    在 **Destinations** 分頁選擇 **Add destination**。
  </StepItem>

  <StepItem>
    選擇 **Slack**、**Discord**、**Microsoft Teams**、**Email**、**Webhook**、**PagerDuty** 或 **Incident.io**，再輸入目的地名稱。
  </StepItem>

  <StepItem>
    配置選定的目的地：

    - 使用 Slack 時，連接或選擇 Workspace，並指定接收警報的頻道。Mastra Alerts 應用程式會自動加入公開頻道；選擇私人頻道前，請先邀請 `@Mastra Alerts`。
    * 對於 Discord，請輸入頻道的 Webhook URL。
    * 對於 Microsoft Teams，輸入Workflow的 Webhook URL。
    - 使用電郵時，選擇 **All organization members**、一個或多個角色、個別成員或外部電郵地址。
    - 使用 Webhook 時，輸入以 `https://` 開頭的端點地址。
    - 使用 PagerDuty 時，輸入 **Integration key**。
    - 使用 incident.io 時，輸入 **Alert source config ID** 和 **Token**。
  </StepItem>

  <StepItem>
    選擇 **Create destination**。如屬 Webhook 目的地，請在關閉頁面前複製簽署密鑰；之後無法再次查看。
  </StepItem>
</Steps>

目標表單會根據所選類型而變更。 Slack 目標需要一個Workspace和至少一個通道。 Discord 和 Microsoft Teams 目標需要 Webhook URL。電子郵件目標需要至少一個收件人，該收件人可以是組織角色、成員或外部地址。 Webhook 目標需要 HTTPS 端點。 PagerDuty 和 Incident.io 目標需要來自其整合的憑證。每個目的地還需要一個在警報配置和活動歷史記錄中標識它的名稱。

使用目標的操作選單發送測試通知。您也可以編輯、暫停或刪除目的地。暫停目的地會停止通知，但不會將其從現有警報中刪除。

對 Webhook 目的地，**Rotate secret** 會立即取代目前的簽署密鑰。再次發送警報前，請更新接收端點使用的密鑰。

Discord 和 Microsoft Teams 的 Webhook URL 包含憑證，因此 Mastra 會加密儲存，建立目的地後只顯示最後四個字元。如需更換 URL，請編輯目的地並貼上新 URL；欄位留空則保留已儲存的 URL。

## 建立警報 {/* #create-an-alert */}

警報結合了觸發器、範圍、目的地和重複警報節奏。

<Steps>
  <StepItem>
    在 **Alerts** 分頁選擇 **Create Alert**。
  </StepItem>

  <StepItem>
    輸入警報名稱。如需立即開始監察，請保持 **Enabled** 開啟。
  </StepItem>

  <StepItem>
    選擇一個或多個觸發器：

    * **部署失敗**：建置或部署未達到運作狀態。
    * **服務崩潰**：正在運行的服務耗盡其重新啟動策略並停止。
    * **服務記憶體不足**：服務在記憶體不足後停止。
    * **服務不可達**：已部署的服務連續 3 次運作狀況檢查失敗。
    - **Usage threshold crossed**：組織用量超過計劃門檻或達到上限。此觸發條件適用於整個組織，因此範圍必須設為 **All projects**。
  </StepItem>

  <StepItem>
    將警報範圍設為 **All projects** 或 **Specific projects**。選擇特定項目後，可進一步限定至個別環境。如未選擇環境，便涵蓋該項目的所有環境。
  </StepItem>

  <StepItem>
    選擇一個或多個目的地。您可以新增或編輯目的地，而無需離開警報設定。
  </StepItem>

  <StepItem>
    在 **Repeat alerts** 下選擇 Mastra 對同一事件重複發送警報的頻率：每次事件、每 5 分鐘、每 15 分鐘或每小時。首次通知、復原通知及嚴重程度上升時的通知會立即發送。
  </StepItem>

  <StepItem>
    選擇**Create Alert**.
  </StepItem>
</Steps>

警報表格將設定分為 **Name**、**Trigger**、**Scope** 及 **Destinations**。選定的目的地和重複間隔適用於該警報涵蓋的所有觸發條件及項目。

## 管理警報 {/* #manage-alerts */}

**Alerts** 分頁顯示每項警報的範圍、目的地及目前狀態。可用開關暫停或啟用警報。

開啟警報的操作選單可以：

* **編輯**它的觸發器、範圍、目的地、節奏或名稱。
* **測試**分配給警報的每個目的地。
* **刪除**警報。現有事件和交付歷史記錄仍然可用。

## 查看警報活動 {/* #review-alert-activity */}

**Activity** 分頁按事件匯集通知嘗試。條件持續存在時，事件維持 **Open**；服務或部署復原後變為 **Resolved**。用量門檻事件則不會自動解決。

展開事件可查看發送至各目的地的通知。事件列顯示發生時間、事件類型、項目或環境範圍及目前狀態；下層發送紀錄顯示每次通知嘗試的觸發條件、目的地和發送狀態。發送狀態包括 **Scheduled**、**Sent**、**Suppressed**、**Retrying**、**Exhausted** 和 **Config error**。活動篩選器可顯示全部活動、只顯示事件或只顯示發送嘗試。

## 向 Discord 發送警報 {/* #send-alerts-to-discord */}

Discord 目的地透過 Webhook 向頻道發佈嵌入訊息。事件觸發時發佈紅色訊息；復原時另發佈綠色 **Resolved** 訊息。Discord Webhook 無法更新舊訊息，因此復原通知會是新訊息，而非修改舊訊息。

<Steps>
  <StepItem>
    在 Discord 開啟接收警報的頻道，依次選擇 **Edit Channel**、**Integrations**、**Webhooks** 及 **New Webhook**，然後複製 Webhook URL。請參閱 Discord 文件的 [Intro to Webhooks](https://support.discord.com/hc/en-us/articles/228383668-Intro-to-Webhooks)。
  </StepItem>

  <StepItem>
    在 Mastra 新增目的地，選擇 **Discord**，並把 URL 貼到 **Webhook URL**。URL 格式必須是 `https://discord.com/api/webhooks/<id>/<token>`。
  </StepItem>

  <StepItem>
    從目標的操作選單發送測試通知。
  </StepItem>
</Steps>

嵌入訊息的標題顯示事件和項目，並連至部署日誌；如事件包含環境、分支和錯誤代碼，這些資訊會連同錯誤摘錄顯示。如 Discord 拒絕 Webhook URL，發送狀態會顯示 **Config error**。

## 向 Microsoft Teams 發送警報 {/* #send-alerts-to-microsoft-teams */}

Microsoft Teams 目的地透過 Teams Workflow 向頻道發送 Adaptive Card。事件觸發時發送紅色卡片；復原時另發一張綠色 **Resolved** 卡片。

<Steps>
  <StepItem>
    在 Teams 開啟接收警報的頻道，依次選擇 **More options**、**Workflows**，再選用 **Send webhook alerts to a channel** 範本。選擇團隊和頻道，建立 Workflow，然後複製其 URL。請參閱 Microsoft 文件的 [Create incoming webhooks with Workflows](https://support.microsoft.com/en-us/office/create-incoming-webhooks-with-workflows-for-microsoft-teams-8ae491c7-0394-4861-ba59-055e33f75498)。
  </StepItem>

  <StepItem>
    在 Mastra 新增目的地，選擇 **Microsoft Teams**，並把 URL 貼到 **Webhook URL**。
  </StepItem>

  <StepItem>
    從目標的操作選單發送測試通知。
  </StepItem>
</Steps>

Microsoft 已停用舊版 Office 365 Connector，因此請使用 Teams Workflow，而非舊有的 **Incoming Webhook** Connector。對於尚未遷移的租戶，Mastra 仍接受舊版 `webhook.office.com` URL。

該卡在其標題中顯示事件和項目，後面是環境、分支和錯誤代碼（當事件包含這些代碼時）、錯誤摘錄以及用於打開部署日誌的按鈕。如果 Teams 拒絕Workflow URL，則交付顯示**Config error**.

## 向 PagerDuty 發送警報 {/* #send-alerts-to-pagerduty */}

PagerDuty 目的地會把事件發送至 PagerDuty Events API v2。每個 Mastra 事件會建立一個 PagerDuty 事件，並在 Mastra 事件解決後由 PagerDuty 將其解決。

<Steps>
  <StepItem>
    在 PagerDuty 開啟接收警報的服務，在 **Integrations** 分頁新增 **Events API V2** 整合，並複製其 **Integration Key**。請參閱 PagerDuty 文件的 [Services and integrations](https://support.pagerduty.com/main/docs/services-and-integrations)。
  </StepItem>

  <StepItem>
    在 Mastra 新增目的地，選擇 **PagerDuty**，並把密鑰貼到 **Integration key**。
  </StepItem>

  <StepItem>
    從目的地的操作選單發送測試通知。測試會在 PagerDuty 建立嚴重程度為 `info` 的事件；請在 PagerDuty 將其解決。
  </StepItem>
</Steps>

Mastra 將其通知映射到 PagerDuty 事件，如下所示：

| PagerDuty 欄位 |價值|
| - | - |
| `event_action` | 新通知或重複通知為 `trigger`，復原通知為 `resolve` |
| `dedup_key` | Mastra 事件 ID。同一事件的重複通知會更新同一個 PagerDuty 事件 |
| `payload.summary` | 單行描述，例如 `Deploy failed on support-agent (production): Build failed` |
| `payload.severity` | Mastra 嚴重程度：`critical`、`error`、`warning` 或 `info` |
| `payload.source` | `mastra:<project>/<environment>` |
| `payload.custom_details` | [Webhook Payload](#webhook-payload) 所述的事件數據 |

在 PagerDuty 確認或解決事件等操作，不會更新 Mastra 事件。如 PagerDuty 拒絕 Integration key，發送狀態會顯示 **Config error**。

## 向 incident.io 發送警報 {/* #send-alerts-to-incidentio */}

incident.io 目的地會把警報事件發送至 incident.io HTTP 警報來源。每個 Mastra 事件都會在 incident.io 建立一項警報；Mastra 事件解決時，該警報亦會解決。

<Steps>
  <StepItem>
    在 incident.io 建立來源類型為 **Default** 的 HTTP 警報來源。Mastra 以 incident.io 警報事件格式發送數據，因此毋須自訂轉換。請參閱 incident.io 文件的 [Create an alert event](https://docs.incident.io/api-reference/alert-events-v2/create)。
  </StepItem>

  <StepItem>
    從來源的授權標頭複製警報來源設定 ID 及 Bearer Token。ID 是警報事件 URL `https://api.incident.io/v2/alert_events/http/<alert-source-config-id>` 的最後一段。
  </StepItem>

  <StepItem>
    在 Mastra 新增目的地並選擇 **Incident.io**。把 ID 或完整警報事件 URL 貼到 **Alert source config ID**，再把 Token 貼到 **Token**。
  </StepItem>

  <StepItem>
    從目的地的操作選單發送測試通知。測試會在 incident.io 建立一項正在觸發的警報。
  </StepItem>
</Steps>

Mastra 會向 incident.io 發送以下欄位：

| incident.io 欄位 | 值 |
| - | - |
| `status` | 新通知或重複通知為 `firing`，復原通知為 `resolved` |
| `deduplication_key` | Mastra 事件 ID |
| `title` | 事件的單行描述 |
| `description` | 事件包含錯誤時的錯誤訊息 |
| `metadata` | 事件數據，以及 `source`、`event_type`、`severity`、`project_id` 和 `environment` |

在警報屬性和路由規則中使用 `metadata` 欄位。在 incident.io 作出的變更不會更新 Mastra 事件；如 incident.io 拒絕 Token 或警報來源 ID，發送狀態會顯示 **Config error**。

## 接收 Webhook 通知 {/* #receive-webhook-notifications */}

Webhook 目的地會為每次通知接收帶 JSON 主體的 HTTP `POST` 請求。可用 Webhook 連接 Mastra 未直接整合的工具。

### Webhook Payload {/* #webhook-payload */}

以下範例顯示了失敗的部署：

```json
{
  "id": "deploy.failed:dep_8c2f1a:triggered",
  "version": "2026-09-01",
  "type": "deploy.failed",
  "createdAt": "2026-09-24T14:03:11.000Z",
  "fingerprint": "deploy.failed|prj_41d9e2|server|production",
  "severity": "error",
  "status": "triggered",
  "summary": "Deploy failed on support-agent (production): Build failed",
  "source": "mastra",
  "data": {
    "deployId": "dep_8c2f1a",
    "projectName": "support-agent",
    "gitBranch": "main",
    "error": "Build failed",
    "errorCode": "BUILD_FAILED",
    "errorCategory": "build",
    "deployUrl": "https://projects.mastra.ai/..."
  },
  "links": []
}
```

| 欄位 | 說明 |
| - | - |
| `id` | 通知 ID。Mastra 重試同一通知時維持不變 |
| `version` | Payload 版本。目前版本為 `2026-09-01` |
| `type` | 事件類型。請參閱下表 |
| `createdAt` | 事件發生時的 ISO 8601 時間 |
| `fingerprint` | 識別通知所屬事件。同一失敗部署目標或服務的通知共用一個指紋 |
| `severity` | `critical`、`error`、`warning` 或 `info`；這些值與 PagerDuty 的嚴重程度一致 |
| `status` | 新通知或重複通知為 `triggered`，事件復原後為 `resolved` |
| `summary` | 事件的單行描述 |
| `source` | 一律為 `mastra` |
| `data` | 事件特有的詳情；欄位視事件類型而異 |
| `links` | 相關連結，每個連結包含 `href` 和 `text`；可為空 |

`type` 欄位可使用以下值：

| 類型 | 觸發條件 | 常見 `data` 欄位 |
| - | - | - |
| `deploy.failed` | **Deploy failed** | `deployId`, `projectName`, `gitBranch`, `error`, `errorCode`, `errorCategory`, `deployUrl` |
| `service.crashed` | **Service crashed** | 同 `deploy.failed` |
| `service.oom` | **Service out of memory** | 同 `deploy.failed` |
| `service.unreachable` | **Service unreachable** | `projectName`, `probeUrl`, `error`, `consecutiveFailures` |
| `billing.usage_threshold` | **Usage threshold crossed** | `featureId`, `featureLabel`, `thresholdDisplay`, `error` |

同一服務的崩潰、記憶體不足和無法連線事件共用指紋，因此一次服務中斷只產生一個事件。用量門檻事件不會發送 `resolved` 通知。

測試通知使用 `type: "deploy.failed"`、`severity: "info"`，並在 `data` 中包含 `"test": true`。

### 請求標頭 {/* #request-headers */}

| 標頭 | 值 |
| - | - |
|`content-type` | `application/json` |
| `user-agent` | `Mastra-Alerts/1.0` |
| `x-mastra-signature` | 請求主體的簽署。請參閱[驗證 Webhook 簽署](#verify-webhook-signatures) |
| `x-mastra-idempotency-key` | 與 Payload `id` 相同 |

### 驗證 Webhook 簽名 {/* #verify-webhook-signatures */}

信任請求前，請先驗證簽署。`x-mastra-signature` 標頭格式如下：

```text
t=1790258591,v1=5f0c9d3e...
```

`t` 是 Mastra 簽署請求時的 Unix 時間戳（秒）。`v1` 是以目的地簽署密鑰為金鑰，對字串 `<t>.<raw request body>` 計算的十六進制 HMAC-SHA256。

要驗證請求：

1. 在解析為 JSON 前讀取原始請求主體。重新解析及序列化可能改變其內容。
1. 計算 `<t>.<raw body>` 的 HMAC，並以固定時間比較方式與 `v1` 比對。
1. 拒絕 `t` 比目前時間早數分鐘以上的請求，以防重放攻擊。

<Tabs>
  <TabItem value="node" label="Node.js">
    ```typescript title="verify-mastra-signature.ts"
    import { createHmac, timingSafeEqual } from 'node:crypto'

    const TOLERANCE_SECONDS = 300

    export function verifyMastraSignature(
      rawBody: string,
      signatureHeader: string,
      signingSecret: string,
    ): boolean {
      const parts = new Map(signatureHeader.split(',').map(part => part.split('=') as [string, string]))
      const timestamp = Number(parts.get('t'))
      const signature = parts.get('v1')
      if (!Number.isInteger(timestamp) || !signature || !/^[0-9a-f]{64}$/.test(signature)) return false
      if (Math.abs(Date.now() / 1000 - timestamp) > TOLERANCE_SECONDS) return false

      const expected = createHmac('sha256', signingSecret)
        .update(`${timestamp}.${rawBody}`)
        .digest('hex')
      const expectedBytes = Buffer.from(expected, 'hex')
      const signatureBytes = Buffer.from(signature, 'hex')
      return (
        expectedBytes.length === signatureBytes.length && timingSafeEqual(expectedBytes, signatureBytes)
      )
    }
    ```
  </TabItem>

  <TabItem value="python" label="Python">
    ```python title="verify_mastra_signature.py"
    import hashlib
    import hmac
    import time

    TOLERANCE_SECONDS = 300


    def verify_mastra_signature(raw_body: bytes, signature_header: str, signing_secret: str) -> bool:
        parts = dict(part.partition("=")[::2] for part in signature_header.split(","))
        try:
            timestamp = int(parts["t"])
            signature = parts["v1"]
        except (KeyError, ValueError):
            return False
        if abs(time.time() - timestamp) > TOLERANCE_SECONDS:
            return False

        expected = hmac.new(
            signing_secret.encode(),
            f"{timestamp}.".encode() + raw_body,
            hashlib.sha256,
        ).hexdigest()
        return hmac.compare_digest(expected, signature)
    ```
  </TabItem>
</Tabs>

驗證失敗的請求應傳回 `401` 狀態。更換目的地密鑰後，新請求會立即改用新密鑰簽署。

### 重試和重複通知 {/* #retries-and-duplicate-notifications */}

Mastra 將任何 `2xx` 回應視為已送達，不會重試。請在回應前將通知持久化或可靠地加入佇列；如這一步失敗，請傳回 `5xx`，讓 Mastra 重試。請在 10 秒內回應，較耗時的處理可在回應後繼續。Mastra 不會跟隨重新導向。

當請求失敗時，Mastra 根據回應重試：

- **`4xx` 回應：**Mastra 停止重試，並將發送狀態標示為 **Config error**。修復端點後，請在目的地使用 **Test** 確認。
- **`5xx` 回應、逾時或網絡錯誤：**Mastra 會在數秒內重試兩次。如仍失敗，狀態會顯示 **Retrying**，約 30 秒後再次嘗試，此後等待時間逐次倍增，最多 15 分鐘。失敗 6 次後，狀態顯示 **Exhausted**。

Discord、Microsoft Teams、PagerDuty 和 incident.io 目的地遵循相同的重試安排。對這些目的地，Mastra 亦會重試 `408` 和 `429` 回應。

重試可能令同一通知送達多次。請保存每個已處理請求的 `x-mastra-idempotency-key`，並略過已出現過的鍵。使用 `fingerprint` 將屬於同一事件的通知歸組。
