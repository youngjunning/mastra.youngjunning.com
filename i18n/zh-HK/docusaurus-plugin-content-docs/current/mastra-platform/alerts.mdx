# 警報

當部署失敗、正在運行的服務停止或停止回應或組織使用量超過計畫閾值時，警報會通知您的團隊。您可以在組織層級配置警報，然後選擇每個警報涵蓋的項目和環境。

组织管理员可以创建和管理警报。其他組織角色對警報設定具有唯讀存取權限。

打開[Mastra platform dashboard](https://projects.mastra.ai), go to your organization settings, then select **Alerts**。該頁面有三個選項卡：

* **警報**列出每個警報及其範圍、目的地、狀態以及啟用或暫停開關。
* **目的地**列出了可以接收通知的 Slack 頻道、Discord 頻道、Microsoft Teams 頻道、電子郵件群組、Webhook 終端點、PagerDuty 服務和 Incident.io 警報來源。
* **活動**顯示事件以及與之相關的通知嘗試。

## 新增目的地 {/* #add-a-destination */}

目的地定義了 Mastra 發送通知的位置。建立警報之前至少要新增一個目的地。

|目的地 |配置|
| - | - |
|**Slack** | Connect a Slack workspace and select one or more channels. Mastra creates a separate destination for each selected channel. |
| **Discord** | Enter a Discord channel webhook URL. See [Send alerts to Discord](#send-alerts-to-discord). |
| **Microsoft Teams** | Enter the URL of a Teams workflow that posts to a channel. See [Send alerts to Microsoft Teams](#send-alerts-to-microsoft-teams). |
| **Email** | Select organization roles, individual members, or up to 10 email addresses. Role-based recipient groups update when organization membership changes. |
| **Webhook**|輸入 HTTPS 端點。 Mastra 對每個請求進行簽名，並在建立目的地後顯示簽名金鑰。 |
|**呼叫器任務**|輸入 PagerDuty Events API v2 整合的整合金鑰。看[向 PagerDuty 發送警報](#send-alerts-to-pagerduty). |
| **事件.io**|輸入 Incident.io HTTP 警報來源的警報來源設定 ID 和令牌。看[向 event.io 發送警報](#send-alerts-to-incidentio). |

<Steps>
  <StepItem>
    上**Destinations** tab, select **Add destination**.
  </StepItem>

  <StepItem>
    選擇**Slack**, **Discord**, **Microsoft Teams**, **Email**, **Webhook**, **PagerDuty**, or **Incident.io**, then enter a name for the destination.
  </StepItem>

  <StepItem>
    配置選定的目的地：

    * 對於 Slack，連接或選擇一個Workspace，然後選擇應接收警報的通道。 Mastra Alerts 應用程式會自動加入公共頻道。邀請`@Mastra Alerts` before selecting a private channel.
    * 對於 Discord，請輸入頻道的 Webhook URL。
    * 對於 Microsoft Teams，輸入Workflow的 Webhook URL。
    * 對於電子郵件，請選擇**All organization members**, one or more roles, individual members, or external email addresses.
    * 對於 Webhook，輸入以以下內容開頭的端點`https://`.
    * 對於 PagerDuty，輸入**Integration key**.
    * 對於 event.io，輸入**Alert source config ID** and **Token**.
  </StepItem>

  <StepItem>
    選擇**Create destination**. For a webhook destination, copy the signing secret before closing the page. The secret can't be shown again.
  </StepItem>
</Steps>

目標表單會根據所選類型而變更。 Slack 目標需要一個Workspace和至少一個通道。 Discord 和 Microsoft Teams 目標需要 Webhook URL。電子郵件目標需要至少一個收件人，該收件人可以是組織角色、成員或外部地址。 Webhook 目標需要 HTTPS 端點。 PagerDuty 和 Incident.io 目標需要來自其整合的憑證。每個目的地還需要一個在警報配置和活動歷史記錄中標識它的名稱。

使用目標的操作選單發送測試通知。您也可以編輯、暫停或刪除目的地。暫停目的地會停止通知，但不會將其從現有警報中刪除。

對於 Webhook 目標，**Rotate secret** replaces the current signing secret immediately. Update the receiving endpoint with the new secret before sending another alert.

Discord 和 Microsoft Teams Webhook URL 包含自己的憑證，因此 Mastra 將它們加密存儲，並在建立目標後僅顯示最後四個字元。要旋轉 URL，請編輯目標並貼上新目標。將 URL 欄位留空會保留儲存的 URL。

## 建立警報 {/* #create-an-alert */}

警報結合了觸發器、範圍、目的地和重複警報節奏。

<Steps>
  <StepItem>
    上**Alerts** tab, select **Create Alert**.
  </StepItem>

  <StepItem>
    輸入警報名稱並離開**Enabled** on if the alert should start monitoring immediately.
  </StepItem>

  <StepItem>
    選擇一個或多個觸發器：

    * **部署失敗**：建置或部署未達到運作狀態。
    * **服務崩潰**：正在運行的服務耗盡其重新啟動策略並停止。
    * **服務記憶體不足**：服務在記憶體不足後停止。
    * **服務不可達**：已部署的服務連續 3 次運作狀況檢查失敗。
    * **已突破使用閾值**：組織使用量超過計劃閾值或達到其限制。此觸發器是組織範圍內的，因此需要**All projects** scope.
  </StepItem>

  <StepItem>
    將警報範圍設定為**All projects** or **Specific projects**. When you select specific projects, you can narrow the scope to individual environments. Leaving the environment selection empty includes every environment in that project.
  </StepItem>

  <StepItem>
    選擇一個或多個目的地。您可以新增或編輯目的地，而無需離開警報設定。
  </StepItem>

  <StepItem>
    在下面**Repeat alerts**, choose how often Mastra can resend an alert for the same incident: every event, every 5 minutes, every 15 minutes, or every hour. The first notification, recovery notifications, and severity increases send immediately.
  </StepItem>

  <StepItem>
    選擇**Create Alert**.
  </StepItem>
</Steps>

警報表單將這些設定分組為**Name**, **Trigger**, **Scope**, and **Destinations**. The selected destinations and repeat interval apply to every trigger and project included in that alert.

## 管理警報 {/* #manage-alerts */}

這**Alerts** tab shows each alert's scope, destinations, and current state. Use the switch to pause or enable an alert.

開啟警報的操作選單可以：

* **編輯**它的觸發器、範圍、目的地、節奏或名稱。
* **測試**分配給警報的每個目的地。
* **刪除**警報。現有事件和交付歷史記錄仍然可用。

## 查看警報活動 {/* #review-alert-activity */}

這**Activity** tab groups each incident with its delivery attempts. An incident stays **Open** while the condition is active and changes to **Resolved** after the service or deploy recovers, except for usage threshold incidents, which don't resolve automatically.

展開事件以檢查傳送到每個目的地的通知。每個事件行顯示事件發生的時間、事件類型、其項目或環境範圍及其目前狀態。嵌套的傳遞行顯示每個通知嘗試的觸發器、目標和傳遞狀態。交付嘗試可以是**Scheduled**, **Sent**, **Suppressed**, **Retrying**, **Exhausted**, or **Config error**. Use the activity filter to show all activity, incidents only, or delivery attempts only.

## 向 Discord 發送警報 {/* #send-alerts-to-discord */}

Discord 目標透過 Discord Webhook 將嵌入發佈到頻道。觸發的事件會發布紅色嵌入，恢復會發佈單獨的綠色**Resolved** embed. Discord webhooks can't update earlier messages, so the resolved notice is a new message rather than an edit.

<Steps>
  <StepItem>
    在 Discord 中，開啟應接收警報的頻道，然後選擇**Edit Channel**, **Integrations**, **Webhooks**, and **New Webhook**. Copy the webhook URL. See [Intro to Webhooks](https://support.discord.com/hc/en-us/articles/228383668-Intro-to-Webhooks) in the Discord documentation.
  </StepItem>

  <StepItem>
    在 Mastra 中，新增目的地，選擇**Discord**, and paste the URL into **Webhook URL**. The URL must have the form `https://discord.com/api/webhooks/<id>/<token>`.
  </StepItem>

  <StepItem>
    從目標的操作選單發送測試通知。
  </StepItem>
</Steps>

嵌入在其標題中顯示事件和項目，連結到部署日誌，後面是錯誤摘錄以及事件包含的環境、分支和錯誤代碼。如果 Discord 拒絕 Webhook URL，則交付顯示**Config error**.

## 向 Microsoft Teams 發送警報 {/* #send-alerts-to-microsoft-teams */}

Microsoft Teams 目標透過 Teams Workflow將自適應卡發佈到頻道。觸發事件會張貼紅牌，恢復事件會張貼單獨的綠牌**Resolved** card.

<Steps>
  <StepItem>
    在 Teams 中，開啟應接收警報的頻道，選擇**More options** and then **Workflows**, and choose the template **Send webhook alerts to a channel**. Select the team and channel, create the workflow, then copy the workflow URL. See [Create incoming webhooks with Workflows](https://support.microsoft.com/en-us/office/create-incoming-webhooks-with-workflows-for-microsoft-teams-8ae491c7-0394-4861-ba59-055e33f75498) in the Microsoft documentation.
  </StepItem>

  <StepItem>
    在 Mastra 中，新增目的地，選擇**Microsoft Teams**, and paste the URL into **Webhook URL**.
  </StepItem>

  <StepItem>
    從目標的操作選單發送測試通知。
  </StepItem>
</Steps>

Microsoft 已淘汰經典 Office 365 連接器，因此請使用 Teams Workflow而不是舊版**Incoming Webhook** connector. Mastra still accepts legacy `webhook.office.com` URLs for tenants that haven't migrated.

該卡在其標題中顯示事件和項目，後面是環境、分支和錯誤代碼（當事件包含這些代碼時）、錯誤摘錄以及用於打開部署日誌的按鈕。如果 Teams 拒絕Workflow URL，則交付顯示**Config error**.

## 向 PagerDuty 發送警報 {/* #send-alerts-to-pagerduty */}

PagerDuty 目標將事件傳送到 PagerDuty 事件 API v2。每個 Mastra 事件都會開啟一個 PagerDuty 事件，當 Mastra 事件被解決時，PagerDuty 會解決該事件。

<Steps>
  <StepItem>
    在 PagerDuty 中，開啟應接收警報的服務。就其**Integrations** tab, add an **Events API V2** integration and copy its **Integration Key**. See [Services and integrations](https://support.pagerduty.com/main/docs/services-and-integrations) in the PagerDuty documentation.
  </StepItem>

  <StepItem>
    在 Mastra 中，新增目的地，選擇**PagerDuty**, and paste the key into **Integration key**.
  </StepItem>

  <StepItem>
    從目標的操作選單發送測試通知。該測試打開一個事件`info` severity in PagerDuty. Resolve it in PagerDuty.
  </StepItem>
</Steps>

Mastra 將其通知映射到 PagerDuty 事件，如下所示：

| PagerDuty 欄位 |價值|
| - | - |
|`event_action` | `trigger` for a new or repeated notification, `resolve` for a recovery |
| `dedup_key` | The Mastra incident ID. Repeated notifications for the same incident update one PagerDuty incident |
| `payload.summary` | A one-line description, for example `Deploy failed on support-agent (production): Build failed` |
| `payload.severity` | The Mastra severity: `critical`, `error`, `warning`, or `info` |
| `payload.source` | `mastra:<project>/<environment>` |
| `payload.custom_details` | The event data described in [Webhook payload](#webhook-payload) |

在 PagerDuty 中所做的變更（例如確認或解決事件）不會更新 Mastra 事件。如果 PagerDuty 拒絕整合金鑰，則交付顯示**Config error**.

## 向 event.io 發送警報 {/* #send-alerts-to-incidentio */}

Incident.io 目標將警報事件傳送至 Incident.io HTTP 警報來源。每個 Mastra 事件都會在 Incident.io 中建立警報，當 Mastra 事件解決時該警報也會解決。

<Steps>
  <StepItem>
    在 Incident.io 中，使用下列指令建立 HTTP 警報來源**Default** source type. Mastra sends events in the incident.io alert event format, so a custom transform isn't needed. See [Create an alert event](https://docs.incident.io/api-reference/alert-events-v2/create) in the incident.io documentation.
  </StepItem>

  <StepItem>
    從來源的授權標頭複製警報來源設定 ID 和持有者令牌。 ID 是警報事件 URL 的最後一段，`https://api.incident.io/v2/alert_events/http/<alert-source-config-id>`.
  </StepItem>

  <StepItem>
    在 Mastra 中，新增目的地並選擇**Incident.io**. Paste the ID, or the full alert events URL, into **Alert source config ID**, and the token into **Token**.
  </StepItem>

  <StepItem>
    從目標的操作選單發送測試通知。該測試在 event.io 中建立觸發警報。
  </StepItem>
</Steps>

Mastra 將這些欄位傳送到 event.io：

| event.io 領域 |價值|
| - | - |
|`status` | `firing` for a new or repeated notification, `resolved` for a recovery |
| `deduplication_key` | The Mastra incident ID |
| `title` | A one-line description of the event |
| `description` | The error message, when the event has one |
| `metadata` | The event data plus `source`, `event_type`, `severity`, `project_id`, and `environment` |

使用`metadata` fields in alert attributes and routing rules. Changes made in incident.io don't update the Mastra incident, and if incident.io rejects the token or alert source ID, the delivery shows **Config error**.

## 接收網路鉤子通知 {/* #receive-webhook-notifications */}

Webhook 目標接收 HTTP`POST` request with a JSON body for each notification. Use a webhook to connect a tool that Mastra doesn't integrate with directly.

### Webhook 負載 {/* #webhook-payload */}

以下範例顯示了失敗的部署：

```json
{
  "id": "deploy.failed:dep_8c2f1a:triggered",
  "version": "2026-09-01",
  "type": "deploy.failed",
  "createdAt": "2026-09-24T14:03:11.000Z",
  "fingerprint": "deploy.failed|prj_41d9e2|server|production",
  "severity": "error",
  "status": "triggered",
  "summary": "Deploy failed on support-agent (production): Build failed",
  "source": "mastra",
  "data": {
    "deployId": "dep_8c2f1a",
    "projectName": "support-agent",
    "gitBranch": "main",
    "error": "Build failed",
    "errorCode": "BUILD_FAILED",
    "errorCategory": "build",
    "deployUrl": "https://projects.mastra.ai/..."
  },
  "links": []
}
```

|領域 |描述 |
| - | - |
|`id` | Notification ID. Stays the same when Mastra retries the same notification |
| `version` | Payload version. The current version is `2026-09-01` |
| `type` | Event type. See the table below |
| `createdAt` | ISO 8601 time when the event occurred |
| `fingerprint` | Identifies the incident the notification belongs to. Notifications for the same failing deploy target or service share a fingerprint |
| `severity` | `critical`, `error`, `warning`, or `info`. These values match PagerDuty severities |
| `status` | `triggered` for a new or repeated notification, `resolved` when the incident recovers |
| `summary` | One-line description of the event |
| `source` | Always `mastra` |
| `data` | Event-specific details. Fields vary by event type |
| `links` | Related links, each with `href` and `text`. Can be empty |

這`type` field has one of these values:

|類型 |觸發|常見的`data` fields |
| - | - | - |
| `deploy.failed` | **Deploy failed** | `deployId`, `projectName`, `gitBranch`, `error`, `errorCode`, `errorCategory`, `deployUrl` |
| `service.crashed` | **Service crashed** | Same as `deploy.failed` |
| `service.oom` | **Service out of memory** | Same as `deploy.failed` |
| `service.unreachable` | **Service unreachable** | `projectName`, `probeUrl`, `error`, `consecutiveFailures` |
| `billing.usage_threshold` | **Usage threshold crossed** | `featureId`, `featureLabel`, `thresholdDisplay`, `error` |

同一服務的崩潰、記憶體不足和無法存取事件共享一個指紋，因此一次中斷會產生一次事件。使用閾值事件不會發送`resolved` notification.

測試通知使用`type: "deploy.failed"`, `severity: "info"`, and include `"test": true` in `data`.

### 請求標頭 {/* #request-headers */}

|標題|價值|
| - | - |
|`content-type` | `application/json` |
| `user-agent` | `Mastra-Alerts/1.0` |
| `x-mastra-signature` | Signature of the request body. See [Verify webhook signatures](#verify-webhook-signatures) |
| `x-mastra-idempotency-key` | Same value as the payload `id` |

### 驗證 Webhook 簽名 {/* #verify-webhook-signatures */}

在信任請求之前驗證簽名。這`x-mastra-signature` header has this format:

```text
t=1790258591,v1=5f0c9d3e...
```

`t`是 Mastra 簽署請求時的 Unix 時間（以秒為單位）。`v1` is a hex-encoded HMAC-SHA256 of the string `<t>.<raw request body>`, using the destination's signing secret as the key.

要驗證請求：

1. 在將原始請求正文解析為 JSON 之前讀取它。再次解析和序列化主體可以改變它。
2. 計算 HMAC`<t>.<raw body>` and compare it with `v1` using a constant-time comparison.
3. 拒絕請求的位置`t` is more than a few minutes old to prevent replayed requests.

<Tabs>
  <TabItem value="node" label="Node.js">
    ```typescript title="verify-mastra-signature.ts"
    import { createHmac, timingSafeEqual } from 'node:crypto'

    const TOLERANCE_SECONDS = 300

    export function verifyMastraSignature(
      rawBody: string,
      signatureHeader: string,
      signingSecret: string,
    ): boolean {
      const parts = new Map(signatureHeader.split(',').map(part => part.split('=') as [string, string]))
      const timestamp = Number(parts.get('t'))
      const signature = parts.get('v1')
      if (!Number.isInteger(timestamp) || !signature || !/^[0-9a-f]{64}$/.test(signature)) return false
      if (Math.abs(Date.now() / 1000 - timestamp) > TOLERANCE_SECONDS) return false

      const expected = createHmac('sha256', signingSecret)
        .update(`${timestamp}.${rawBody}`)
        .digest('hex')
      const expectedBytes = Buffer.from(expected, 'hex')
      const signatureBytes = Buffer.from(signature, 'hex')
      return (
        expectedBytes.length === signatureBytes.length && timingSafeEqual(expectedBytes, signatureBytes)
      )
    }
    ```
  </TabItem>

  <TabItem value="python" label="Python">
    ```python title="verify_mastra_signature.py"
    import hashlib
    import hmac
    import time

    TOLERANCE_SECONDS = 300


    def verify_mastra_signature(raw_body: bytes, signature_header: str, signing_secret: str) -> bool:
        parts = dict(part.partition("=")[::2] for part in signature_header.split(","))
        try:
            timestamp = int(parts["t"])
            signature = parts["v1"]
        except (KeyError, ValueError):
            return False
        if abs(time.time() - timestamp) > TOLERANCE_SECONDS:
            return False

        expected = hmac.new(
            signing_secret.encode(),
            f"{timestamp}.".encode() + raw_body,
            hashlib.sha256,
        ).hexdigest()
        return hmac.compare_digest(expected, signature)
    ```
  </TabItem>
</Tabs>

返回一個`401` status for a request that fails verification. After you rotate a destination's secret, requests are signed with the new secret immediately.

### 重試和重複通知 {/* #retries-and-duplicate-notifications */}

Mastra 治療任何`2xx` response as delivered and doesn't retry it. Persist or durably enqueue the notification before responding, and return a `5xx` response if that step fails so Mastra retries the delivery. Respond within 10 seconds and process the notification after responding if the work takes longer. Mastra doesn't follow redirects.

當請求失敗時，Mastra 根據回應重試：

* **`4xx`回覆:**&#x4D;astra 停止並標記交貨**Config error**. Fix the endpoint, then use **Test** on the destination to confirm it works.
* **`5xx`回應、逾時或網路錯誤：**&#x4D;astra 在幾秒鐘內重試兩次。如果這些請求也失敗，則交付顯示**Retrying** and Mastra tries again after about 30 seconds, doubling the wait each time up to 15 minutes. After 6 failed attempts, the delivery shows **Exhausted**.

Discord、Microsoft Teams、PagerDuty 和 Incident.io 目的地遵循相同的時間表。对于这些目的地，Mastra 也会重试`408` and `429` responses.

重試可以多次發送相同的通知。儲存`x-mastra-idempotency-key` value of each processed request and skip requests with a key you've already seen. Use `fingerprint` to group notifications that belong to the same incident.
