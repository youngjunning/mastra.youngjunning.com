# Mastra平台上的伺服器

Mastra 平台上的伺服器是一個生產部署目標，它將您的 Mastra 應用程式作為 API 伺服器運行。當您希望平台建置、部署、託管和管理您的 Mastra 伺服器時，請使用它。

您可以獲得穩定的 API 端點，具有環境變數管理和自訂網域支持，以及開箱即用的部署歷史記錄。

：：：筆記

伺服器部署自動配置託管儲存。如果您使用覆蓋存儲[LibSQLStore](/integrations/databases/libsql) and a file URL, switch to a remotely hosted database because Mastra platform uses an ephemeral filesystem.

:::

## 快速入門 {/* #quickstart */}

<Steps>
  <StepItem>
    遵循[get started guide](/docs) to create your first Mastra project.
  </StepItem>

  <StepItem>
    安裝`mastra` CLI globally:

    ```bash npm2yarn
    npm install -g mastra
    ```
  </StepItem>

  <StepItem>
    部署您的專案：

    ```bash
    mastra deploy
    ```

    如果您尚未通過身份驗證，CLI 會提示您登入。它會在本機上儲存您的憑證，並且任何後續 CLI 命令都會使用這些憑證。

    命令運行`mastra build` and uploads its artifact, then builds and deploys a Docker image. On first deploy, the CLI creates a `.mastra-project.json` file linking your local project to the platform. Commit this file so subsequent deploys and CI/CD target the same project.

    :::注意
    CLI 從一個 env 檔案上傳環境變數。它使用`.env.<environment>` if it exists (for example `.env.production` for the default `production` environment), otherwise the only `.env` or `.env.*` file. If there are several and none matches, it asks which one to use; in non-interactive runs (`--yes` or CI), pass `--env-file <file>`反而。經過`--env-file`覆蓋選擇。每次部署都會將檔案的變數合併到環境的儲存環境變數：檔案 win 中的值，但空值不會清除儲存的值。 CLI 列出了它將覆蓋的金鑰並要求您確認（使用`--yes`或在 CI 中）。若要僅在儀表板中管理 var，請將其從 env 檔案中刪除。如果不存在 env 文件，則不會上傳任何內容，並且環境會保留其儲存的環境變數。
    在部署之前檢查並清理所選文件，以避免上傳僅供開發或個人機密。
    :::

    請參閱[CLI reference](/reference/cli/mastra#mastra-deploy) for the full list of flags.
  </StepItem>

  <StepItem>
    透過 CLI 列印的 URL 驗證您的部署。附加`/api/agents` to confirm it returns a JSON list of your agents.

    :::警告
    設定[authentication](/docs/auth/overview) before exposing your endpoints publicly.
    :::
  </StepItem>
</Steps>

## 部署生命週期 {/* #deploy-lifecycle */}

每個專案在部署過渡時一次運行一個構建**queued → uploading → starting → deploying → running** (or **failed**, **cancelled**, **crashed**, or **stopped**). Deploys triggered from GitHub first build from source, so they pass through **building** between **queued** and **uploading**. When multiple deploys queue up, the latest proceeds and the rest are cancelled. Builds running longer than 15 minutes are automatically failed. The first deploy provisions infrastructure and seeds environment variables from your local `.env`. Your server URL remains stable across deploys.

## 閒置行為 {/* #idle-behavior */}

Mastra 平台上的伺服器可以在一段時間不活動後休眠服務以節省資源。不活動狀態是透過出站網路流量來衡量的。僅在大約 10 分鐘且沒有出站資料包的情況下，服務才會被視為空閒。任何重複出現的出站流量都會重設此計時器並使服務保持喚醒狀態。

永不休眠的伺服器通常具有後台任務或在計時器上發送流量的長期連線。檢查以下常見原因。

### 持久性資料庫連接 {/* #persistent-database-connections */}

即使伺服器空閒，保持開啟狀態的資料庫客戶端也能保持連線。許多驅動程式也會執行後台運行狀況檢查，定期對資料庫執行 ping 操作，這也算是出站流量。例如，一個從未關閉的 MongoDB 用戶端保持監控套接字打開，並大約每 10 秒發送心跳一次。

耗盡空閒連線的連線池設定本身是不夠的，因為驅動程式的監視連線保持開啟並保持 ping。要讓伺服器休眠，請在一段時間不活動後關閉客戶端，並在下一個請求時重新連線。

:::注意
關閉客戶端會為伺服器喚醒後的第一個請求添加短暫的重新連線延遲。如果您的工作負載無法容忍這種延遲，請保持連線開啟並且不要依賴空閒睡眠。
:::

### 規劃任務和計時器 {/* #scheduled-tasks-and-timers */}

一個`setInterval`, cron job, or polling loop that makes network calls keeps the server awake. If you need scheduled work, run it as a separate service or use an external scheduler that wakes the server with a request.

### 外部 ping 和保持活動檢查 {/* #external-pings-and-keep-alive-checks */}

正常運作時間監視器、運作狀況檢查或以一定時間間隔存取伺服器的保持活動 ping 會重設空閒計時器。如果您希望伺服器休眠，請刪除這些檢查或將其間隔增加到空閒視窗之外。

### 可觀察性出口商 {/* #observability-exporters */}

將追蹤、日誌或指標串流傳輸到遠端端點的匯出器會傳送出站流量。確認導出器在伺服器空閒時批量並停止發送，而不是按固定間隔刷新。

### 長壽的流 {/* #long-lived-streams */}

開放的伺服器發送事件 (SSE) 流、WebSocket 或其他長期連線會保持流量開放，直到關閉。在背景保持訂閱的串流響應使連線保持活動狀態。確認當客戶端斷開連線時流關閉，且在伺服器空閒時沒有流保持開啟狀態。

### 聊天集成 {/* #chat-integrations */}

一些聊天整合保持持久連接並發送定期心跳，這使伺服器保持喚醒狀態。例如，套接字模式下的 Slack 應用程式會開啟 WebSocket 並大約每 30 秒執行一次 ping 操作，而 Discord 機器人則透過計時器上的心跳保持其網關 WebSocket 開啟。打開套接字和心跳都會阻止空閒。

如果您希望伺服器休眠，請透過 HTTP Webhook 接收事件，而不是整合支援的持久連線。例如，Slack 應用程式可以使用帶有請求 URL 的事件 API，而不是套接字模式。如果您的應用程式需要持久連接，請保持服務運行**Persistent Server add-on** described below.

### 檢查活動連接 {/* #inspect-active-connections */}

若要找出使伺服器保持喚醒狀態的原因，請在空閒期間檢查進程的活動句柄。所有請求完成後保留的句柄是需要調查的原因。打開的套接字指向需要關閉的持久連接，活動的計時器指向`setInterval` or self-rescheduling `setTimeout`.

將以下幫助程式放入您的應用程式中，然後在流量停止後查看日誌。伺服器空閒後仍然列出的任何內容都會使其保持喚醒狀態：

```typescript title="src/mastra/diagnose-idle.ts"
export function logActiveHandles() {
  // process._getActiveHandles is undocumented but useful for diagnosis.
  const handles = (process as any)._getActiveHandles() as Array<any>

  const summary = handles.map(handle => {
    const type = handle?.constructor?.name ?? typeof handle
    if (type === 'Socket') {
      return `Socket -> ${handle.remoteAddress}:${handle.remotePort}`
    }
    return type
  })

  console.log(`[idle] ${handles.length} active handles:`, summary)
}

// Log every 30 seconds so you can see what persists while the server is idle.
setInterval(logActiveHandles, 30_000).unref()
```

稱呼`unref()` on the diagnostic interval so the helper itself doesn't keep the server awake.

### 保持服務運行 {/* #keep-a-service-running */}

某些應用程式實際上需要上述連線或任務，例如用於低首次請求延遲的持久性資料庫連線、後台排程器或長期存在的串流。如果您的應用程式需要其中任何一個，請不要強制該服務休眠。使用**Persistent Server add-on** to keep the service running continuously instead.

隨著**Persistent Server add-on** enabled, the service stays awake even with no traffic, so persistent connections, scheduled tasks, and open streams keep working without being interrupted by idle sleep.

## 持續整合/持續交付 {/* #cicd */}

從 GitHub Actions、GitLab CI 或任何 CI Provider自動部署。首次互動式部署後，CI/CD 需要 API 令牌、您的組織和專案 ID 以及`.mastra-project.json` file committed to your repository.

:::提示
如果您的程式碼位於 GitHub 上，[GitHub integration](/docs/mastra-platform/github) gives you push-to-deploy without writing a workflow file. Use the CLI-based CI/CD flow below when you need GitLab, another CI provider, or custom build steps before deploy.
:::

### 建立 API 令牌 {/* #create-an-api-token */}

<Steps>
  <StepItem>
    在本地運行以下命令：

    ```bash
    mastra auth tokens create ci-deploy
    ```

    CLI 列印一次令牌。立即複製它，因為它無法再次檢索。
  </StepItem>

  <StepItem>
    將令牌新增為 CI 提供者中的機密。在 GitHub Actions 中，前往**Settings → Secrets and variables → Actions** and create the `MASTRA_API_TOKEN` secret.
  </StepItem>

  <StepItem>
    確保您的`.mastra-project.json` file is committed to the repository.
  </StepItem>

  <StepItem>
    添加`MASTRA_ORG_ID` and `MASTRA_PROJECT_ID` to your CI provider, using the `organizationId` and `projectId` values from `.mastra-project.json`. When `MASTRA_API_TOKEN` is set, `mastra deploy` runs headless and fails if either variable is missing.
  </StepItem>
</Steps>

### 這`--yes` flag {/* #the---yes-flag */}

經過`--yes` (or `-y`) to skip all confirmation prompts. Without it, the CLI waits for interactive input and your CI job hangs.

```bash
mastra deploy --yes
```

### GitHub 操作 {/* #github-actions */}

每次推送時都會部署以下Workflow`main`:

```yaml title=".github/workflows/deploy-mastra.yml"
name: Deploy to Mastra platform

on:
  push:
    branches: [main]
    paths: ['src/mastra/**']

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'
      - name: Install dependencies
        run: npm install
      - name: Deploy to Mastra platform
        run: npx mastra deploy --yes
        env:
          MASTRA_API_TOKEN: ${{ secrets.MASTRA_API_TOKEN }}
          MASTRA_ORG_ID: ${{ secrets.MASTRA_ORG_ID }}
          MASTRA_PROJECT_ID: ${{ secrets.MASTRA_PROJECT_ID }}
```

調整`paths` filter and `working-directory` if your Mastra project is in a subdirectory (e.g. a monorepo).

### 亞搏體育appGitLab持續集成 {/* #gitlab-ci */}

以下管道部署在推送上`main`:

```yaml title=".gitlab-ci.yml"
deploy:
  image: node:22
  stage: deploy
  only:
    - main
  before_script:
    - npm install
  script:
    - npx mastra deploy --yes
```

添加`MASTRA_API_TOKEN`, `MASTRA_ORG_ID`, and `MASTRA_PROJECT_ID` as CI/CD variables in **Settings → CI/CD → Variables**.

### 其他 CI 提供者 {/* #other-ci-providers */}

任何執行 Node.js 和 shell 指令的 CI 系統都可以與 Mastra 搭配使用：

1. 安裝依賴項。
2. 放`MASTRA_API_TOKEN`, `MASTRA_ORG_ID`, and `MASTRA_PROJECT_ID` as environment variables.
3. 跑步`mastra deploy --yes`.

### 驗證部署 {/* #verify-the-deploy */}

Workflow完成後，透過點擊運行狀況端點來驗證部署：

```bash
curl -f https://<your-project>.server.mastra.cloud/health
```

或檢查Agent端點，它傳回Agent的 JSON 清單：

```bash
curl -f https://<your-project>.server.mastra.cloud/api/agents
```

以下範例向 GitHub Actions Workflow新增驗證步驟：

```yaml
- name: Verify deployment
  run: |
    sleep 30
    curl -f https://<your-project>.server.mastra.cloud/health
```

### 使用環境變數覆蓋項目配置 {/* #override-project-config-with-environment-variables */}

對於互動式部署，CLI 讀取`organizationId` and `projectId` from `.mastra-project.json` by default. When `MASTRA_API_TOKEN` is set, both variables below are required. To override these values (e.g. deploying to a different project from the same repository), set the following environment variables:

|變數|描述 |
| - | - |
|`MASTRA_ORG_ID` | Overrides the organization ID from `.mastra-project.json`. |
| `MASTRA_PROJECT_ID` | Overrides the project ID from `.mastra-project.json`. |
