# 在 Mastra 平台部署伺服器

Mastra 平台的 Server 是正式環境的部署選項，可將 Mastra 應用程式作為 API 伺服器執行。如需由平台構建、部署、託管和管理 Mastra 伺服器，可選用此方式。

平台提供穩定的 API 端點，可管理環境變數、使用自訂網域，亦會自動保存部署紀錄。

:::note

伺服器部署會自動配置託管儲存空間。如你以 [LibSQLStore](/integrations/databases/libsql) 和檔案 URL 覆寫儲存配置，請改用遠端託管的數據庫，因為 Mastra 平台使用臨時檔案系統。

:::

## 快速入門 {/* #quickstart */}

<Steps>
  <StepItem>
    按照[入門指南](/docs)建立你的首個 Mastra 專案。
  </StepItem>

  <StepItem>
    全域安裝 `mastra` CLI：

    ```bash npm2yarn
    npm install -g mastra
    ```
  </StepItem>

  <StepItem>
    部署專案：

    ```bash
    mastra deploy
    ```

    如尚未登入，CLI 會提示你登入。登入憑證會存於本機，供之後的 CLI 指令使用。

    指令會執行 `mastra build` 並上傳構建產物，其後構建和部署 Docker 映像。首次部署時，CLI 會建立 `.mastra-project.json`，將本機專案連結至平台。請提交此檔案，讓日後部署和 CI/CD 均以同一專案為目標。

    :::note
    CLI 只會從一份環境變數檔案上傳變數。如有 `.env.<environment>`，例如預設 `production` 環境的 `.env.production`，便會使用該檔案。否則，如只有一份 `.env` 或 `.env.*` 檔案，便會使用該檔案。如有多份檔案而沒有相符項目，CLI 會詢問應使用哪一份。以非互動方式執行時（`--yes` 或 CI），請傳入 `--env-file <file>`。你也可用 `--env-file` 覆寫檔案選擇。每次部署會將檔案內的變數併入該環境已保存的變數，以檔案的值為準，但空值不會清除已保存的值。CLI 會列出即將覆寫的變數名稱，並要求確認。使用 `--yes` 或在 CI 中執行時會略過確認。如某個變數只應在管理介面處理，請將它從環境變數檔案移除。如沒有環境變數檔案，則不會上傳任何變數，環境會保留目前已保存的變數。
    部署前請先檢查及清理所選檔案，避免上傳只供開發使用或屬於個人的機密資料。
    :::

    所有命令列選項載於 [CLI 參考](/reference/cli/mastra#mastra-deploy)。
  </StepItem>

  <StepItem>
    前往 CLI 顯示的 URL 驗證部署。在 URL 後加上 `/api/agents`，確認它回傳列出你的 Agent 的 JSON 清單。

    :::warning
    將端點公開前，請先設定[身份驗證](/docs/auth/overview)。
    :::
  </StepItem>
</Steps>

## 部署生命週期 {/* #deploy-lifecycle */}

每個專案同一時間只會進行一次構建。部署會依次經過 **queued → uploading → starting → deploying → running**，也可能進入 **failed**、**cancelled**、**crashed** 或 **stopped**。由 GitHub 觸發的部署會先從原始碼構建，所以在 **queued** 和 **uploading** 之間會經過 **building**。有多項部署排隊時，只有最新一項繼續，其餘會取消。構建超過 15 分鐘會自動標記為失敗。首次部署會配置基礎設施，並以本機的 `.env` 初始化環境變數。伺服器 URL 在各次部署之間維持不變。

## 閒置休眠 {/* #idle-behavior */}

為節省資源，Mastra 平台可讓閒置一段時間的服務休眠。平台按出站網絡流量判斷服務是否閒置。服務約 10 分鐘沒有送出封包才會被視為閒置。定期出現的出站流量會重設計時器，使服務保持運作。

伺服器一直沒有休眠，一般是因為背景工作或長時間連線定期傳送流量。你可以檢查以下常見原因。

### 持久數據庫連線 {/* #persistent-database-connections */}

數據庫客戶端如未關閉，即使伺服器閒置，仍會維持連線。許多驅動程式也會在背景定期 ping 數據庫以檢查狀態，這同樣算作出站流量。例如，未關閉的 MongoDB 客戶端會維持監察用的 socket，並約每 10 秒傳送一次心跳。

單靠連線池回收閒置連線並不足夠，因為驅動程式的監察連線仍會開啟並繼續 ping。要讓伺服器休眠，可在閒置一段時間後關閉客戶端，待下一個請求到達時再連線。

:::note
關閉客戶端會令伺服器喚醒後的首個請求出現短暫的重連延遲。如工作負載不能接受這段延遲，請維持連線，並避免依賴閒置休眠。
:::

### 排程工作及計時器 {/* #scheduled-tasks-and-timers */}

如果 `setInterval`、cron 工作或輪詢迴圈會發出網絡請求，伺服器便會保持運作。如須定時執行工作，可將工作放在獨立服務中執行，或由外部排程器發出請求喚醒伺服器。

### 外部 ping 及保活檢查 {/* #external-pings-and-keep-alive-checks */}

定期向伺服器發出請求的可用性監察、健康檢查或保活 ping，均會重設閒置計時器。要讓伺服器休眠，請移除這些檢查，或將其間隔延長至超過閒置時限。

### 可觀測性匯出器 {/* #observability-exporters */}

將 Trace、日誌或指標持續傳送至遠端端點的匯出器會產生出站流量。請確認匯出器會分批傳送資料，並在伺服器閒置時停止傳送，避免按固定間隔送出資料。

### 長時間開啟的串流 {/* #long-lived-streams */}

伺服器傳送事件（SSE）串流、WebSocket 或其他長時間連線，都會保持通訊至連線關閉為止。串流回應如在背景維持訂閱，連線便會保持活躍。請確認客戶端斷線時會關閉串流，並確保伺服器在其他方面沒有活動時，沒有串流仍然開啟。

### 聊天服務整合 {/* #chat-integrations */}

部分聊天服務整合會維持持久連線並定期傳送心跳，使伺服器保持運作。例如，採用 Socket Mode 的 Slack 應用程式會開啟 WebSocket，約每 30 秒 ping 一次。Discord 機械人則會保持閘道 WebSocket 開啟，並定期傳送心跳。開啟的 socket 和心跳均會阻止伺服器進入閒置狀態。

如希望伺服器休眠，可在整合支援的情況下，改用 HTTP Webhook 接收事件。例如，Slack 應用程式可以用設有請求 URL 的 Events API 取代 Socket Mode。如應用程式需要持久連線，請用下文的 **Persistent Server add-on** 讓服務維持運作。

### 檢查活躍連線 {/* #inspect-active-connections */}

要找出伺服器沒有休眠的原因，請在閒置時檢查程序的活躍控制代碼。可從所有請求完成後仍存在的控制代碼着手。仍開啟的 socket 指向須關閉的持久連線，活躍的計時器則指向 `setInterval` 或自行反覆排程的 `setTimeout`。

將以下輔助程式加入應用程式，待流量停止後查看日誌。伺服器閒置時仍列出的項目，便是令它維持運作的原因：

```typescript title="src/mastra/diagnose-idle.ts"
export function logActiveHandles() {
  // process._getActiveHandles is undocumented but useful for diagnosis.
  const handles = (process as any)._getActiveHandles() as Array<any>

  const summary = handles.map(handle => {
    const type = handle?.constructor?.name ?? typeof handle
    if (type === 'Socket') {
      return `Socket -> ${handle.remoteAddress}:${handle.remotePort}`
    }
    return type
  })

  console.log(`[idle] ${handles.length} active handles:`, summary)
}

// Log every 30 seconds so you can see what persists while the server is idle.
setInterval(logActiveHandles, 30_000).unref()
```

對定期診斷用的計時器呼叫 `unref()`，避免輔助程式本身令伺服器維持運作。

### 讓服務維持運作 {/* #keep-a-service-running */}

部分應用程式確實需要上述的連線或工作，例如以持久數據庫連線減少首個請求的延遲，或需要背景排程器或長時間開啟的串流。如應用程式有任何一項需要，請使用 **Persistent Server add-on** 讓服務持續運作，避免強制休眠。

啟用 **Persistent Server add-on** 後，服務即使沒有流量也會保持運作，所以持久連線、排程工作及開啟的串流均不會因閒置休眠而中斷。

## CI/CD {/* #cicd */}

你可透過 GitHub Actions、GitLab CI 或任何 CI 服務自動部署。首輪互動式部署完成後，CI/CD 需要 API 權杖、組織和專案 ID，以及已提交至程式碼儲存庫的 `.mastra-project.json` 檔案。

:::tip
如程式碼放在 GitHub，[GitHub 整合](/docs/mastra-platform/github)可在推送時自動部署，毋須編寫工作流程檔案。若使用 GitLab 或其他 CI 服務，或部署前須執行自訂構建步驟，請採用下文以 CLI 為基礎的 CI/CD 流程。
:::

### 建立 API 權杖 {/* #create-an-api-token */}

<Steps>
  <StepItem>
    在本機執行以下指令：

    ```bash
    mastra auth tokens create ci-deploy
    ```

    CLI 只會顯示權杖一次。請即時複製，日後無法再次取回。
  </StepItem>

  <StepItem>
    將權杖加入 CI 服務的機密項目。在 GitHub Actions，前往 **Settings → Secrets and variables → Actions**，建立 `MASTRA_API_TOKEN` 機密項目。
  </StepItem>

  <StepItem>
    確認 `.mastra-project.json` 已提交至程式碼儲存庫。
  </StepItem>

  <StepItem>
    在 CI 服務加入 `MASTRA_ORG_ID` 和 `MASTRA_PROJECT_ID`，分別使用 `.mastra-project.json` 內的 `organizationId` 和 `projectId`。設定 `MASTRA_API_TOKEN` 後，`mastra deploy` 會以非互動方式執行，欠缺任何一個變數都會失敗。
  </StepItem>
</Steps>

### `--yes` 選項 {/* #the---yes-flag */}

傳入 `--yes`（或 `-y`）可略過所有確認提示。如省略此選項，CLI 會等待互動輸入，令 CI 工作停滯。

```bash
mastra deploy --yes
```

### GitHub Actions {/* #github-actions */}

每次推送至 `main` 時，以下工作流程會執行部署：

```yaml title=".github/workflows/deploy-mastra.yml"
name: Deploy to Mastra platform

on:
  push:
    branches: [main]
    paths: ['src/mastra/**']

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'
      - name: Install dependencies
        run: npm install
      - name: Deploy to Mastra platform
        run: npx mastra deploy --yes
        env:
          MASTRA_API_TOKEN: ${{ secrets.MASTRA_API_TOKEN }}
          MASTRA_ORG_ID: ${{ secrets.MASTRA_ORG_ID }}
          MASTRA_PROJECT_ID: ${{ secrets.MASTRA_PROJECT_ID }}
```

如 Mastra 專案位於子目錄，例如在 monorepo 內，請調整 `paths` 篩選條件和 `working-directory`。

### GitLab CI {/* #gitlab-ci */}

推送至 `main` 時，以下 CI 流程會執行部署：

```yaml title=".gitlab-ci.yml"
deploy:
  image: node:22
  stage: deploy
  only:
    - main
  before_script:
    - npm install
  script:
    - npx mastra deploy --yes
```

到 **Settings → CI/CD → Variables**，將 `MASTRA_API_TOKEN`、`MASTRA_ORG_ID` 和 `MASTRA_PROJECT_ID` 加入為 CI/CD 變數。

### 其他 CI 服務 {/* #other-ci-providers */}

任何可執行 Node.js 和 Shell 指令的 CI 系統都能配合 Mastra 部署：

1. 安裝相依套件。
1. 設定 `MASTRA_API_TOKEN`、`MASTRA_ORG_ID` 和 `MASTRA_PROJECT_ID` 環境變數。
1. 執行 `mastra deploy --yes`。

### 驗證部署 {/* #verify-the-deploy */}

工作流程完成後，請向健康檢查端點發出請求，以驗證部署：

```bash
curl -f https://<your-project>.server.mastra.cloud/health
```

亦可檢查 Agent 端點，該端點會以 JSON 清單回傳你的 Agent：

```bash
curl -f https://<your-project>.server.mastra.cloud/api/agents
```

以下範例在 GitHub Actions 工作流程加入驗證步驟：

```yaml
- name: Verify deployment
  run: |
    sleep 30
    curl -f https://<your-project>.server.mastra.cloud/health
```

### 以環境變數覆寫專案配置 {/* #override-project-config-with-environment-variables */}

互動式部署時，CLI 預設會從 `.mastra-project.json` 讀取 `organizationId` 和 `projectId`。如已設定 `MASTRA_API_TOKEN`，則必須提供以下兩個變數。要覆寫這些值，例如從同一程式碼儲存庫部署至另一個專案，請設定以下環境變數：

| 變數 | 說明 |
| - | - |
| `MASTRA_ORG_ID` | 覆寫 `.mastra-project.json` 的組織 ID。 |
| `MASTRA_PROJECT_ID` | 覆寫 `.mastra-project.json` 的專案 ID。 |
