# Worker

:::beta

API 穩定之前，即使主版本號不變亦可能出現破壞性變更。目前的缺口請參閱[已知限制](#known-limitations)。

:::

Worker 在請求與回應週期之外處理背景工作。Workflow 步驟、cron 排程及長時間運行的 Tool 呼叫都由 Worker 處理，讓 API 保持回應能力。

預設情況下，worker 與 API 在同一進程中運行。對於生產工作負載，您可以將它們拆分為單獨的進程或容器，並獨立擴展每個進程或容器。

## 何時使用 Worker {/* #when-to-use-workers */}

出現以下任何情況時，可考慮使用獨立 Worker：

- Workflow 步驟耗時超過數秒，不應阻塞 API 回應
* 您需要事件持久性，以便正在進行的工作能夠在流程重新啟動後繼續存在
* 系統的不同部分需要獨立擴充（例如，無需更多 API 實例即可獲得更多編排能力）
* 後台Tool呼叫應在專用計算上運行

如應用程式流量不大且 Workflow 很快完成，預設的程序內設定已足夠。需要時再部署獨立 Worker。

## Worker 類型 {/* #worker-types */}

Mastra 內置三種 Worker，分別處理不同類型的背景工作。

### 編排工作者 {/* #orchestration-worker */}

此 Worker 訂閱 [PubSub](/docs/server/pubsub) 總線上的 Workflow 事件並執行步驟。它會處理每個 `workflow.start` 事件、生命週期事件及步驟轉換。

拆分部署時，編排 Worker 從分散式 PubSub 後端提取事件，並透過 HTTP 將步驟執行交由 API 處理。在同一程序內運行時，則直接執行步驟。

編排 Worker 需要支援拉取模式的 PubSub 後端，例如 [`RedisStreamsPubSub`](/reference/pubsub/redis-streams)、[`ValkeyStreamsPubSub`](/reference/pubsub/valkey-streams) 或 [`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub)。

### 調度員 {/* #scheduler-worker */}

Scheduler Worker 輪詢儲存空間，找出已到觸發時間的 cron 排程，並為每次觸發發佈 `workflow.start` 事件。它只負責產生工作，交由編排 Worker 處理：

- **拆分程序**：排程 Workflow 使用事件驅動引擎，編排 Worker 逐步執行每次觸發。
- **同一程序內**：排程 Workflow 使用預設引擎；同一程序的編排 Worker 會像直接呼叫 `run.start()` 一樣，在程序內執行每次觸發。

Scheduler 會自動讀取 Workflow 定義中宣告的 `schedule` 欄位。宣告排程的方法請參閱[排程 Workflow](/docs/workflows/scheduled-workflows)。

只有排程存在時，Scheduler 才會輪詢儲存空間。啟動時，未宣告排程的程序只會執行一次 `listSchedules()` 檢查。如沒有記錄，就不會啟動輪詢；閒置部署不會持續查詢排程，也可縮至零個實例。

在運行時建立計劃時，Mastra 會在 PubSub 後端發布喚醒事件。執行預設工作程序集的任何進程都會啟動其調度程序作為回應，這就是獨立工作程序發現 API 進程創建的調度程序的方式。這需要兩個進程共享相同的 PubSub 後端。

如無論是否已有排程都要在啟動後開始輪詢（例如程序之間不共用 PubSub 後端），請在 Worker 設定 `scheduler: { enabled: true }`，或使用 `MASTRA_WORKERS=scheduler` 運行。

同一儲存空間可以運行多個 Scheduler 實例。發佈前，Scheduler 會以比較並交換更新排程的下次觸發時間，取得本次觸發的處理權。只有一個實例會成功，其餘會跳過。內置儲存適配器（PostgreSQL、LibSQL、MySQL、MongoDB、Spanner、Convex）均以原子方式更新。自訂適配器亦須在 `updateScheduleNextFire` 保證更新的原子性，否則同一次觸發可能執行兩次。

該聲明阻止其他調度程序實例發布相同的事件。它不會只觸發一次：

- **取得處理權與發佈並非同一交易。** 如成功取得處理權的實例當機，或嘗試三次後仍未能發佈，該次觸發可能遺失。Mastra 會將發佈失敗記為 `failed` trigger，但發佈結果不明，亦不會自動重播。
- **重試可能重複發佈同一次觸發。** 如事件已到達 PubSub 後端，但發佈仍回報錯誤，重試會以相同 run ID 再次發佈。對預設引擎的 Workflow，Worker 會跳過已存在的 run；但如重複事件在首次 run 儲存前抵達，仍可能再次啟動。事件驅動 Workflow 沒有這項檢查：重複啟動會把現有 run 重新設為 `running` 並再次執行。
- **觸發可能重疊。** 即使上次觸發的 run 尚未結束，下次觸發仍會準時發生。

額外的調度程序實例增加了可用性，而不是吞吐量。每個人都會在每次更新時輪詢儲存空間。

### 後台任務工作者 {/* #background-task-worker */}

執行標記為 `background: { enabled: true }` 的 Agent Tool 呼叫。Agent 呼叫背景 Tool 時，API 會把工作交給此 Worker，避免阻塞回應串流。

背景工作 Worker 透過 PubSub 總線管理並行數量限制、工作生命週期及結果傳送。

## Worker 的運行方式 {/* #how-workers-run */}

### 進程內模式（預設） {/* #in-process-mode-default */}

無需配置，Mastra 在 API 進程內執行Worker。事件流經記憶體中的 PubSub，所有內容都共用一個 Node.js 執行時間。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core/mastra'

export const mastra = new Mastra({
  // Workers run in-process by default.
  // No pubsub or worker config needed.
})
```

`mastra build` 產生的伺服器會自動啟動這些 Worker。如改用[伺服器適配器](/docs/server/server-adapters)，請在伺服器開始監聽後呼叫 `mastra.startWorkers()`。請參閱[啟動背景 Worker](/docs/server/server-adapters#start-background-workers)。

除了儲存適配器之外，此設定不需要任何外部基礎架構。它無法在進程崩潰時倖存下來，並且您無法擴展單個元件。

:::warning

記憶體中的 PubSub 僅在發布事件的進程內傳遞事件。事件Workflow不支援在一個儲存體上執行多個 Mastra 實例：每個實例在啟動時都會重新啟動其他實例的活動運行。為多實例部署配置分散式 PubSub 後端。

:::

### 拆分流程 {/* #split-processes */}

如要讓 Worker 在獨立程序運行，請設定分散式 [PubSub](/docs/server/pubsub) 後端，並透過 `MASTRA_WORKERS` 環境變數控制各程序啟動哪些 Worker。

<Tabs>
  <TabItem value="redis" label="Redis Streams + PostgreSQL">
    ```typescript title="src/mastra/index.ts"
    import { Mastra } from '@mastra/core/mastra'
    import { RedisStreamsPubSub } from '@mastra/redis-streams'
    import { PostgresStore } from '@mastra/pg'

    export const mastra = new Mastra({
      storage: new PostgresStore({
        connectionString: process.env.DATABASE_URL!,
      }),
      pubsub: new RedisStreamsPubSub({
        url: process.env.REDIS_URL!,
      }),
    })
    ```
  </TabItem>

  <TabItem value="gcp" label="Google Cloud Pub/Sub + LibSQL">
    ```typescript title="src/mastra/index.ts"
    import { Mastra } from '@mastra/core/mastra'
    import { GoogleCloudPubSub } from '@mastra/google-cloud-pubsub'
    import { LibSQLStore } from '@mastra/libsql'

    export const mastra = new Mastra({
      storage: new LibSQLStore({
        url: process.env.DATABASE_URL!,
      }),
      pubsub: new GoogleCloudPubSub({
        projectId: process.env.GCP_PROJECT_ID!,
      }),
    })
    ```
  </TabItem>
</Tabs>

可使用任何[支援的儲存後端](/reference/workers/overview#supported-storage-backends)，只需將適配器換成所選數據庫。

在多個容器中運行同一份構建產物，為每個容器設定不同的 [`MASTRA_WORKERS`](/reference/workers/overview#mastra_workers) 值，以控制各程序啟動的 Worker。

拆分部署需要分散式 PubSub 後端（[`RedisStreamsPubSub`](/reference/pubsub/redis-streams)、[`ValkeyStreamsPubSub`](/reference/pubsub/valkey-streams) 或 [`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub)）、共用的[儲存後端](/reference/workers/overview#supported-storage-backends)，以及編排 Worker 與 API 之間的網絡連線。

### 選擇 Worker {/* #select-workers */}

設定 [`MASTRA_WORKERS`](/reference/workers/overview#mastra_workers)，控制各程序運行哪些 Worker：

|價值|行為 |
| - | - |
| `false` | 停用所有 Worker。完全拆分部署中的 API 程序使用此值。 |
| `orchestration` | 啟動編排 Worker。 |
| `scheduler` | 啟動 Scheduler Worker。 |
| `backgroundTasks` | 啟動背景工作 Worker。 |
| `orchestration,backgroundTasks` | 以逗號分隔的允許清單啟動多個 Worker。 |

亦可將 Worker 名稱傳入 CLI。此指令會在啟動的程序中設定 `MASTRA_WORKERS`：

```bash
mastra worker start orchestration
```

拆分部署的每個程序都須設定 `MASTRA_WORKERS`，API 程序亦須設為 `false`。設定此變數後，宣告了 `schedule` 的 Workflow 會切換至事件驅動引擎；所有程序都須使用同一引擎。請參閱[排程 Workflow](/docs/workflows/scheduled-workflows#execution-engine)。如執行 `mastra worker start` 時不指定 Worker 名稱，就不會設定 `MASTRA_WORKERS`，因此須傳入名稱，或在程序環境設定此變數。

## 網路架構 {/* #network-architecture */}

Worker 屬於內部基礎設施，不直接面向終端用戶，因此毋須獨立子網域、公開 URL 或對外的 HTTP 路由。

在拆分部署中：

* **API伺服器是唯一面向公眾的進程**：它為所有客戶端 HTTP 請求提供服務。這些請求包括 REST 端點和Agent交互，以及Workflow觸發器和自訂路由。
- **Worker 不處理客戶端流量**：它們從分散式 PubSub 後端提取事件，並讀寫共用儲存數據庫。每個 Worker 程序亦會監聽 `PORT`（預設 `4111`），供內部健康檢查使用。`/health` 回報就緒狀態，`/config` 向獲授權的呼叫者提供 Worker 設定。此連接埠應保留在私人網絡。
- **編排 Worker 在內部呼叫 API**：它透過容器網絡，使用 `MASTRA_STEP_EXECUTION_URL` 向 API 發送步驟執行請求。這是內部服務間通訊，並非公開端點。

所有三種工作類型（編排、排程器、背景任務）都位於專用網路上的 API 後面。它們共享對 PubSub 後端和儲存資料庫的存取權限，但從不直接從客戶端接收流量。與Worker相關的功能的 HTTP 路由在 API 伺服器上運行，而不是在工作進程上運行。一個例子是為語音整合創建令牌。

## 部署拆分的 Worker {/* #deploy-split-workers */}

建置 API 和工作工件：

```bash
mastra build
mastra worker build --output-dir .mastra/worker
```

`mastra build` 會在 `.mastra/output/` 產生 API 構建產物。[`mastra worker build`](/reference/cli/mastra#mastra-worker-build) 會在 `.mastra/worker/` 產生 Worker 構建產物。以下 Dockerfile 可接受其中一個目錄：

```dockerfile title="Dockerfile"
FROM node:22-alpine

ARG MASTRA_OUTPUT=.mastra/output

WORKDIR /app

COPY ${MASTRA_OUTPUT}/package.json ${MASTRA_OUTPUT}/.npmrc* ./
RUN npm install --omit=dev

COPY ${MASTRA_OUTPUT}/ .

EXPOSE 4111
CMD ["node", "index.mjs"]
```

構建輸出的詳情請參閱[部署 Mastra 伺服器](/docs/deployment/mastra-server)。

### Docker 組合 {/* #docker-compose */}

以下配置運行 PostgreSQL、Redis、API 以及每種Worker類型的一個程序。每個進程都使用共享基礎設施，並且工作進程使用工作工件。

```yaml title="docker-compose.yml"
x-worker: &worker
  build:
    context: .
    args:
      MASTRA_OUTPUT: .mastra/worker

x-mastra-environment: &shared-environment
  DATABASE_URL: postgres://mastra:${POSTGRES_PASSWORD}@postgres:5432/mastra
  REDIS_URL: redis://redis:6379

services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: mastra
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: mastra
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ['CMD-SHELL', 'pg_isready -U mastra']
      interval: 5s
      timeout: 3s
      retries: 5

  redis:
    image: redis:7-alpine
    healthcheck:
      test: ['CMD', 'redis-cli', 'ping']
      interval: 5s
      timeout: 3s
      retries: 5

  api:
    build:
      context: .
      args:
        MASTRA_OUTPUT: .mastra/output
    ports:
      - '4111:4111'
    environment:
      <<: *shared-environment
      WORKER_TOKEN: ${WORKER_TOKEN}
      MASTRA_WORKERS: 'false'
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    healthcheck:
      test: ['CMD', 'wget', '-qO-', 'http://localhost:4111/api/agents']
      interval: 5s
      timeout: 3s
      retries: 5

  orchestration-worker:
    <<: *worker
    environment:
      <<: *shared-environment
      MASTRA_WORKERS: orchestration
      MASTRA_STEP_EXECUTION_URL: http://api:4111/api
      MASTRA_WORKER_AUTH_TOKEN: ${WORKER_TOKEN}
    depends_on:
      api:
        condition: service_healthy

  scheduler-worker:
    <<: *worker
    environment:
      <<: *shared-environment
      MASTRA_WORKERS: scheduler
    depends_on:
      api:
        condition: service_healthy

  background-task-worker:
    <<: *worker
    environment:
      <<: *shared-environment
      MASTRA_WORKERS: backgroundTasks
    depends_on:
      api:
        condition: service_healthy

volumes:
  pgdata:
```

請在 `docker-compose.yml` 旁設定密鑰，以及應用程式所需的模型 Provider 憑證：

```bash title=".env"
POSTGRES_PASSWORD=your-secure-password
WORKER_TOKEN=your-shared-secret-token
```

對外開放部署前，先設定 API 驗證 Provider，使其接受 `WORKER_TOKEN`。編排 Worker 會透過 `MASTRA_WORKER_AUTH_TOKEN` 傳送相同數值。在這種拉取式拓撲中，Scheduler 及背景工作 Worker 不會呼叫步驟執行端點，因此毋須設定該變數。

啟動堆疊並驗證容器和 API 是否可用：

```bash
docker compose up -d
docker compose ps
curl http://localhost:4111/api/agents
```

### 庫伯內斯 {/* #kubernetes */}

:::tip Helm
在 Kubernetes 上，[`mastra-projects` Helm chart](/integrations/deploy/kubernetes-helm#background-workers) 會產生這些部署，讓 Worker 與伺服器使用相同映像及環境。它亦會阻止安裝導致每種 Worker 重複運行的組合。以下清單供人手編寫部署時使用。
:::

為 API、編排Worker、排程器Worker和後台任務Worker建立單獨的部署。為每個 Deployment 使用相同的映像和 Secret。僅直接在每個容器上設定特定於角色的環境變數。

編排Worker Deployment 具有以下形狀：

```yaml title="k8s/orchestration-worker.yaml"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orchestration-worker
spec:
  replicas: 1
  selector:
    matchLabels:
      app: orchestration-worker
  template:
    metadata:
      labels:
        app: orchestration-worker
    spec:
      containers:
        - name: worker
          image: your-registry/mastra-workers:latest
          env:
            - name: MASTRA_WORKERS
              value: orchestration
            - name: MASTRA_STEP_EXECUTION_URL
              value: http://api:4111/api
          envFrom:
            - secretRef:
                name: mastra-secrets
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
```

為其他 Worker Deployment 分別設定 `MASTRA_WORKERS: scheduler` 及 `MASTRA_WORKERS: backgroundTasks`。API Deployment 設為 `MASTRA_WORKERS: 'false'`，並透過 Service 對外提供 API。所有程序都須連接同一數據庫及 PubSub 後端。為 API 驗證 Provider 設定 Worker token，再以 `MASTRA_WORKER_AUTH_TOKEN` 提供予編排 Worker。基礎 Kubernetes 資源請參閱[將 Mastra 部署至 Kubernetes](/integrations/deploy/kubernetes)。

應用清單，然後驗證 pod 和 API：

```bash
kubectl apply -f k8s/
kubectl get pods
kubectl port-forward svc/api 4111:4111
```

在單獨的終端機中，請求 API 路由：

```bash
curl http://localhost:4111/api/agents
```

### 步驟執行 URL {/* #step-execution-url */}

在完全拆分部署中，編排 Worker 會透過 HTTP 將 Workflow 步驟交由 API 執行。請將 `MASTRA_STEP_EXECUTION_URL` 設為 API 的內部 URL，包括 `/api` 前綴：

```bash
MASTRA_STEP_EXECUTION_URL=http://api:4111/api
```

如果沒有此變量，編排Worker會嘗試在自己的進程中執行步驟，而該進程無法存取分割部署中的完整 Mastra 執行緒。

此端點使用伺服器一般的驗證流程。如 API 設定了驗證 Provider，請將 `MASTRA_WORKER_AUTH_TOKEN` 設為它接受的 bearer token。Mastra 會將該值作為 `Authorization: Bearer` 憑證轉送，由已設定的 Provider 驗證。伺服器設定及其他憑證格式請參閱[Worker 驗證](/docs/auth/workers)。

### 擴充 Worker {/* #scale-workers */}

編排 Worker 及背景工作 Worker 可以橫向擴充。PubSub 消費者群組會將事件分配給不同實例：

```bash
docker compose up -d --scale orchestration-worker=3
docker compose up -d --scale background-task-worker=2
```

對於 Kubernetes，手動更改部署副本計數或使用 Horizo​​ntalPodAutoscaler：

```bash
kubectl scale deployment/orchestration-worker --replicas=3
kubectl scale deployment/background-task-worker --replicas=2
```

您可以執行多個調度程式工作者。每個計劃事件都由一個實例聲明，如中所述[Scheduler worker](#scheduler-worker).

### 健康檢查 {/* #health-checks */}

Worker 構建產物會在 `PORT` 提供 `GET /health`；未設定 `PORT` 時使用連接埠 `4111`。`startWorkers()` 初始化期間端點回傳 `503`，所有選定 Worker 啟動成功後回傳 `200`。可用此端點檢查部署是否就緒；如亦用於存活檢查，請設定啟動探針或足夠的初始延遲，等候 Worker 初始化完成。

### 崩潰恢復 {/* #crash-recovery */}

分散式 PubSub 後端會保留尚未確認的事件，因此編排 Worker 及背景工作 Worker 重啟後可恢復處理。API 無法使用時，失敗的步驟執行請求會令事件重新傳送。

如 Worker 在事件驅動 Workflow 的步驟執行期間停止，broker 會將該步驟事件重新交給另一個 Worker。Redis 或 Valkey Streams 會在 `reclaimIdleMs` 後重新傳送（預設 60 秒）；Google Cloud Pub/Sub 則在確認期限後重新傳送。因此期間啟動的實例不會重啟該 run。`reclaimIdleMs` 應保持至少 30 秒：過早回收的事件可能在已停止 Worker 對步驟的佔用仍有效時抵達，繼而被丟棄。

一個步驟可能運行多次。如 Worker 在步驟執行期間停止，或在步驟完成但結果未發佈時停止，事件重新傳送後該步驟會再次執行。有副作用的步驟應具備冪等性。建立步驟冪等鍵的方法請參閱[重新啟動運行中的 Workflow run](/docs/workflows/overview#restarting-active-workflow-runs)；Agent Tool 的做法請參閱[讓 Tool 可安全重試](/docs/harness/durable-agents#make-tools-safe-to-repeat)。

調度程序重新啟動後從目前時間計算下一次觸發時間。它不會重播在不可用時已過的時間表。

如實例在預設引擎的 Workflow run 執行期間當機，運行編排 Worker 的實例會透過[復原循環](/docs/workflows/overview#recovery-loop)，在 run 租約到期且經過 `recovery.workflowGraceMs` 後的第一次檢查中重新啟動它。`mastra worker` 程序收到 `SIGTERM` 時會呼叫 `stopWorkers()` 並退出，不會呼叫 `shutdown()`。它正在執行的預設引擎 run 會像實例當機時一樣等待復原。請參閱[已知限制](#known-limitations)及[持久化 Agent 的當機復原](/docs/harness/durable-agents#crash-recovery)。

## 已知的限制 {/* #known-limitations */}

* **無死信隊列**：失敗的事件將被確認並重試，但對於所有重試後都失敗的事件沒有 DLQ。
* **計劃事件可能會遺失**：如果調度程序崩潰或在聲明事件後無法發布，則該事件可能不會觸發，並且 Mastra 不會自動重播它。
- **API 當機後 run 停留在 running 狀態**：如 Workflow 步驟執行期間當機，run 會停在 `running`，且不會自動重試。對於[持久化 Agent](/docs/harness/durable-agents)，可設定 `recovery.durableAgents: 'auto'`，令伺服器重新啟動後自動重新驅動孤立的 run。詳情請參閱[當機復原](/docs/harness/durable-agents#crash-recovery)。
