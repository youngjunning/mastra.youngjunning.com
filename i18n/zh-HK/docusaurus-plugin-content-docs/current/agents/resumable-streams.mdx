# 可續接串流

可續接串流會把 Agent 一次執行所產生的每個資料區塊發佈到 PubSub 主題，並快取這些事件供重播。客戶端斷線後可重新連線，補收遺漏的事件。其他讀取端可用 `observe()` 跟進同一次執行，任何讀取端均可停止執行。

可續接串流只處理連線，無法在程序故障後復原執行。執行 Agent 的程序一旦停止，本次執行亦會停止，觀察端會收到錯誤，或不再收到事件。如須在程序重新啟動後繼續執行，請使用[持久化 Agent](/docs/harness/durable-agents)，它會經同一串流層發佈事件。

## 預設行為 {/* #defaults */}

| Agent | 串流 |
| - | - |
| 已在 `Mastra` 實例註冊 | 啟用 |
| 獨立執行（用 `new Agent()` 建立，並無 `Mastra`） | 停用 |
| 配置 `durable: true` 的一般 Agent | 啟用，包括獨立 Agent |
| 配置 `durable: false` 的一般 Agent | 停用，包括已註冊的 Agent |
| 明確經 `createDurableAgent()` 包裝 | 一律發佈。向工廠函數傳入 `cache: false` 只會停用重播快取，傳輸層歷史紀錄不受影響。 |

已註冊的 Agent 無論是否持久化，都會經 `mastra.pubsub` 發佈事件，並將事件快取至 `mastra.serverCache`。如伺服器沒有快取，則使用記憶體快取。所有共用該 PubSub 和快取的 `Mastra` 實例均可觀察執行。Agent 層級的 `pubsub` 優先，但事件驅動引擎的步驟一律經 `mastra.pubsub` 發佈。

## 配置串流 {/* #configure-streams */}

可在 Agent 設定 `durable` 以啟用或停用串流，亦可傳入自己的 PubSub 和快取：

```typescript title="src/mastra/agents/support-agent.ts"
import { Agent } from '@mastra/core/agent'

export const supportAgent = new Agent({
  id: 'support-agent',
  name: 'Support agent',
  instructions: 'You help customers with their orders.',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  durable: {
    // Keep finished runs replayable for 2 minutes instead of 30 seconds
    cleanupTimeoutMs: 120_000,
  },
})
```

| 選項 | 預設值 | 說明 |
| - | - | - |
| `pubsub` | `mastra.pubsub` | 發佈執行事件所用的匯流排。使用共用匯流排可跨程序跟進執行。 |
| `cache` | `mastra.serverCache`，如無則用記憶體快取 | 重播快取。傳入 `false` 可停用此快取。Redis Streams 等傳輸層仍可重播其保存的歷史紀錄。 |
| `shouldCache` | 所有主題 | 對個別主題回傳 `false`，即可略過該主題的快取。 |
| `cleanupTimeoutMs` | `30000` | 執行結束後多久才清除該次執行。`0` 只會停用此計時器，快取本身仍會按其規則到期或淘汰資料。 |

`durable: true` 會以這些預設值啟用串流，包括獨立 Agent。

對一般 `Agent`，`durable` 只用於配置可續接串流。如要依靠檢查點執行，請明確以 `createDurableAgent({ agent })` 包裝 Agent。要在程序故障後復原尚未完成的執行，還須配置持久化 Workflow 儲存及 `recovery: { durableAgents: 'auto' }`。如要手動復原，請傳入涵蓋 `running` 快照的 `shouldPersistSnapshot` 政策，再自行呼叫 `recoverActiveRuns()`。設定方法及持久化政策請參閱[故障復原](/docs/harness/durable-agents#crash-recovery)。

透過工廠函數的 `cache`、`pubsub`、`shouldCache` 及 `cleanupTimeoutMs` 選項配置包裝後的串流快取和傳輸。

## 停用串流 {/* #turn-streams-off */}

串流會消耗資源。每個資料區塊都會發佈到 PubSub，而且啟用快取後，事件會保存至該次執行獲清除為止。記憶體快取會佔用程序的記憶體，遠端 PubSub 或 Redis 等遠端快取則需要為每個資料區塊經網絡寫入一次。處理大量執行、又毋須重新連線或觀察執行的 Agent，可以停用串流：

```typescript title="src/mastra/agents/batch-agent.ts"
import { Agent } from '@mastra/core/agent'

export const batchAgent = new Agent({
  id: 'batch-agent',
  name: 'Batch agent',
  instructions: 'You classify support tickets.',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  durable: false,
})
```

要保留即時觀察功能而停用重播快取，請傳入 `durable: { cache: false }`。

### 執行紀錄的保留時間 {/* #how-long-runs-stay-available */}

執行結束後，負責執行的程序會排定在 `cleanupTimeoutMs` 後清除執行事件及歸屬紀錄。計時器容許程序在清除前結束，共用快取內的資料其後會保留至到期或被淘汰。Redis Streams 會保留原生主題資料，直至 `clearTopic()` 成功執行或閒置 TTL 到期。傳輸層預設的閒置 TTL 是七天，可設定 `streamIdleTtlMs` 更改，或設為 `0` 停用傳輸層的到期機制。等待工具核准或暫停的執行不會被此計時器清除，因為續行時仍使用同一主題。

其餘保留限制視乎快取：

- 執行日誌和歸屬紀錄會向快取要求 24 小時的 TTL。除非停用快取到期機制，記憶體快取會為已建立索引的執行日誌採用至少 24 小時的 TTL。快取項目數目達到上限時，資料可能提早被淘汰。
- 記憶體快取預設可容納 1,000 個項目。每次執行佔用數個項目，包括其事件日誌、計數器及歸屬紀錄，因此流量大時，較早的執行會較快被淘汰。
- 執行的歸屬紀錄被淘汰或到期後，伺服器的觀察和中止路由會回傳 404。已淘汰的執行事件不可重播。

如須跨伺服器觀察執行，或要長時間等候核准，請使用 Redis 等共用快取，並按流量設定容量。

## 跟進執行 {/* #follow-a-run */}

在共用同一 PubSub 匯流排的 Agent 之間，執行 ID 必須唯一。

可在共用匯流排的任何 Agent 實例上，以執行 ID 呼叫 `observe()` 跟進執行。沒有指定偏移量時，`observe()` 會先重播快取事件，再傳送即時事件。要重播也須共用同一重播快取。使用獨立快取的實例只會收到即時事件，除非 PubSub 保留歷史紀錄。執行正在等候工具核准時，觀察端會收到核准請求，並維持連線，直至獲核准的執行完成、出錯或被中止。若要停止跟進等待中的執行，請呼叫 `detach()`：

```typescript title="src/server/reconnect.ts"
import { supportAgent } from '../mastra/agents/support-agent'

export async function followRun(runId: string, request: Request) {
  const { output, detach } = await supportAgent.observe(runId)

  request.signal.addEventListener('abort', detach, { once: true })
  if (request.signal.aborted) detach()

  for await (const chunk of output.fullStream) {
    // Chunks from the run, including any missed while disconnected
  }
}
```

`observe()` 回傳的資料區塊會以 `chunk.index` 標示其在執行日誌中的位置。斷線後要續接觀察，請取最後一個有索引的資料區塊，將其 `index + 1` 作為 `offset` 傳入。一般 Agent 的 `stream()` 產生的資料區塊，以及無重播快取時傳送的資料區塊，均沒有 `index`，因此這類連線中斷後，觀察時應省略 `offset`。無索引的資料區塊、結構化輸出及重播限制請參閱 [`observe()` 參考](/reference/agents/durable-agent#observerunid-options)。

經 HTTP 觀察不可續接的執行時，請求會失敗。如找不到執行，或其歸屬紀錄已到期或被淘汰，伺服器會回傳 404。客戶端的 Promise 會以帶有該狀態碼的 `MastraClientError` 拒絕，不會取得已關閉的空串流。

`agent.hasResumableStreams()` 表示 Agent 會否發佈執行事件，以及 `observe()` 和伺服器的觀察及中止路由能否存取這些執行。持久化 Agent 和所有已啟用串流的 Agent 均會回傳 `true`。

### 持續至閒置的串流 {/* #until-idle-streams */}

`streamUntilIdle()` 和 `resumeStreamUntilIdle()` 會在各自的 `fullStream` 合併初始執行及背景工作的續行。未指定偏移量時，`observe(returnedRunId)` 只會重播初始片段，並在收到其完成事件時關閉。它不會續接這條持續至閒置的合併串流，亦不會重播後續背景工作的回應。即使明確指定執行 ID，這項限制依然適用，持久化 Agent 也一樣。

## 停止執行 {/* #stop-a-run */}

啟用串流後，關閉讀取端不會停止執行。客戶端與伺服器的串流路由斷線時，伺服器會分離讀取端，執行仍會繼續產生 token、呼叫工具和執行 `onFinish`，讓客戶端稍後重新連線。可明確停止執行，或為應隨請求結束的一般 Agent 設定 `durable: false`。持久化 Agent 在斷線後一律繼續執行。讀取端已分離的執行，仍會在完成、被停止或用盡步驟預算時結束。如未設定 `maxSteps` 或 `stopWhen`，每次迴圈會在五步後停止，處理器重試不計算在內。預算按每次呼叫迴圈計算，核准或背景續行後會開始新的迴圈。

可用以下方式明確停止執行：

- `observe(runId)` 會回傳 `abort()` 函數，向仍在執行的工作發出停止請求，無論工作在哪裏執行。請求會盡力送達，毋須等待確認，發佈失敗時只會記錄日誌。需要確認時，可使用下述中止路由。等待核准的執行已不再接收此請求，請使用下述中止路由。如執行位於記憶對話串內，亦可使用 `POST /agents/:agentId/threads/abort`。
- `agent.abortRunStream(runId)` 會停止本程序內的執行，並要求同一匯流排上的其他程序停止該次執行。如本程序停止了正在進行的執行，會回傳 `true`。在記憶對話串以外等待核准的執行，亦會在本程序取消，但函數回傳 `false`，其後在此程序核准會失敗。取消限制只在本程序生效，共用快照仍會保留，因此其他程序仍可核准該快照。如應用程式使用多部伺服器，請以以下中止路由停止等待核准的執行。至於在其他程序中的執行，請求只會盡力送達。
- 伺服器的 `POST /agents/:agentId/runs/:runId/abort` 路由會先確認呼叫方擁有該次執行，然後可停止任何共用 PubSub 和快取的伺服器上的執行。負責執行的程序確認停止後，路由便會回傳 `{ aborted: true }`。如持久化 Agent（`DurableAgent` 或 `createDurableAgent`，包括事件驅動的 Agent）的執行正在等待核准，路由亦會將取消寫入儲存系統，並在寫入成功後回傳 `{ aborted: true }`。其後，如要核准或續行該次執行，所有共用該儲存系統的伺服器都會拒絕並回傳 `409 Conflict`（`AGENT_RESUME_ABORTED_RUN`）。如續行操作先取得該次執行，便不會保存取消紀錄，路由會如常停止已續行的執行。在 Redis、Valkey 和 LanceDB 等不支援並行更新的儲存配接器中，同時到達的中止和核准不會依序處理，因此即使中止回傳 `{ aborted: true }`，同時處理的核准仍可能執行工具。請先等候該回應，再依賴已保存的取消紀錄。Inngest Agent 不會寫入此紀錄。如執行已結束，或執行沒有停止且沒有程序及時回應，路由會回傳 `{ aborted: false }`。你也可用 `POST /agents/:agentId/threads/abort` 停止記憶對話串內的執行，但該路由不會將取消寫入儲存系統。因此，應用程式如使用多部伺服器，請用執行中止路由停止等待核准的持久化執行。

非持久化 Agent 如配置 `durable: false`，關閉 HTTP 請求時仍會像以往一樣中止執行。

## 跨伺服器運作 {/* #across-servers */}

如多部伺服器共用 PubSub 和快取（例如 Redis），在其中一部伺服器啟動的執行，可經任何一部伺服器觀察或停止：

- 每次執行會在發佈首個事件之前，把歸屬紀錄（Agent、執行、資源及對話串）寫入快取。伺服器的觀察和中止路由會按該紀錄核對呼叫方，因此所有伺服器均會檢查租戶及對話串。
- 找不到紀錄、紀錄已到期或被淘汰時，會回傳 404。如無法讀取快取，路由會回傳 503，不會略過檢查。
- 設定 `durable: { cache: false }` 時，歸屬紀錄會保存在 `mastra.serverCache`，因此仍可跨伺服器核對歸屬。重播功能則視乎 PubSub，Redis Streams 等保留歷史紀錄的實作可重播，程序內的匯流排則只傳送即時事件。
- 預設的記憶體快取和 PubSub 不共用資料，因此只有執行 Agent 的伺服器可觀察或停止其執行。
