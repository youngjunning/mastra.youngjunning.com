# 多Agent系統

多Agent系統將任務指派給多個Agent，而不是要求一個Agent完成所有事情。在 Mastra 中，這通常意味著將Agent、Workflow或兩者結合起來，以便系統的每個部分都有明確的角色。

目標是將正確的上下文、Tool和職責分配給正確的元件。當這種劃分清晰時，多智能體系統比一個背負著長提示和太多Tool或職責的智能體系統更容易推理。

## 何時使用多Agent系統 {/* #when-to-use-multi-agent-systems */}

當一個Agent不再是工作的良好邊界時，請使用多Agent系統。

這種情況常出現在以下情況：

* 任務涵蓋不同類型的工作，例如研究、規劃、寫作或評論。
* 一個Agent需要太多的上下文或太多的Tool。
* 任務的各個部分應該並行運行。
* 不同的階段需要不同的提示、模型或護欄。
* 您希望路由、執行和綜合之間有清晰的界限。

盡可能從一名Agent商開始。當添加的結構明顯提高品質、速度或可靠性時，添加更多Agent。

當系統需要一種清晰的方式來跨元件劃分上下文、決策和職責時，多Agent模式就非常有用。在實踐中，關鍵的設計問題是隨著任務的進展哪個組件保持控制。

## 交接 {/* #handoffs */}

切換模式將控制權從一個Agent轉移到另一個Agent。與主管模式不同，第一個Agent不會負責整個任務。相反，活躍的專家掌控了互動的下一部分。

當下一位專家應該直接繼續互動而不是透過中央協調員報告時，請使用交接。權衡是上下文管理變得更加重要，因為系統必須決定下一個Agent繼承什麼以及保留什麼範圍。

在 Mastra 中，透過組合來實現此模式[agents](/docs/agents/overview), [workflows](/docs/workflows/overview), and [memory](/docs/memory/overview). A workflow can route the task, but the defining feature of the pattern is that ownership moves to the next agent.

## Workflow {/* #workflows */}

Workflow模式定義了程式碼中的執行路徑。您無需要求Agent決定接下來會發生什麼，而是透過步驟、分支、循環和並行區塊來定義序列。

當任務被很好地理解並且執行路徑預先已知時，使用Workflow。主要優點是可預測性：顯式結構使系統更易於調試和審計。代價是靈活性，因為當任務隨著展開而改變時，Workflow的適應性較差。

在馬斯特拉，[workflows](/docs/workflows/overview) can implement coordination patterns such as handoffs and councils. A workflow is distinct because its control logic lives in the workflow itself, regardless of which agents it calls.

## 監事 {/* #supervisors */}

主管模式讓一名首席Agent控制整個任務。主管決定何時委派、呼叫哪位專家、傳遞什麼情境、如何組合結果。

當任務是開放式的並且事先不知道完整的序列時，請使用此模式。例如，一項研究任務可能需要根據早期步驟發現的內容進行不同的調查。主管可以隨著任務的展開進行調整。
權衡是主管成為主要協調點。這使得模式變得靈活，但也意味著結果在很大程度上取決於良好的委派行為和明確的子Agent邊界。

在 Mastra 中，這種模式直接對應到[supervisor agents](/docs/subagents). A supervisor defines subagents through the `agents` property, then coordinates them with `stream()` or `generate()`. Mastra helps control this pattern through delegation hooks and message filtering, with memory isolation between agents.

## 理事會 {/* #council */}

理事會模式要求多個Agent獨立解決相同問題，然後比較或綜合他們的輸出，形成一個最終答案。與將問題分成幾個部分的主管不同，理事會使問題保持共享，並對同一問題提出多種觀點。

當問題不明確、評估性或高風險且答案品質比速度更重要時，請使用此模式。權衡是成本，因為理事會故意重複工作，並且通常比其他模式花費更長的時間並使用更多的代幣。

[agents](/docs/agents/overview) and [workflows](/docs/workflows/overview): Run multiple agents in parallel and collect their outputs. Then add a final synthesis or review step. Workflow control flow methods such as `.parallel()` provide the structure for this pattern.

## 選擇圖案 {/* #choosing-a-pattern */}

這些模式的主要區別在於它們如何分配控制：

|圖案|誰能掌控一切 |使用時 |權衡 |馬斯特拉實施 |
| - | - | - | - | - |
|交接 |現任專家|所有權應在專家之間轉移|上下文遷移變得更加重要 |具有Workflow和內存的Agent |
|Workflow |執行圖 |路徑是預先知道的 |任務變化時適應性較差 |[Workflows](/docs/workflows/overview) |
| Supervisor agents | One lead agent | Delegation must adapt during execution | Results depend on good coordination and clear boundaries | [Supervisor agents](/docs/subagents) |
| Council | Final synthesis step | The task needs multiple independent perspectives | Higher cost and latency | Agents with workflow parallelism |

在實踐中，這些模式經常組合在一起：

* Workflow可以包含一個或多個主管驅動的步驟。
* 切換流程可以從路由Workflow開始。
* 委員會可以在Workflow中運作並進入最終批准步驟。
* 主管可以將具有固定內部結構的任務委託給Workflow。

根據協調問題而不是任務標籤選擇模式。
