# channels()

此函式根據 Mastra 平台項目的連線，傳回可交給 `new Mastra({ channels })` 的即時頻道解析器。已啟用的 Provider 實例只建立一次，建立時無須憑證，因此在建構 `Mastra` 時便可掛載其 Webhook 及 OAuth 路由。解析器會快取項目連線；連線變更時，它會將憑證綁定至這些實例，無須重新部署應用程式。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { channels } from '@mastra/connect'

export const mastra = new Mastra({
  agents: { assistant },
  channels: await channels(),
})
```

傳回：`Promise<ChannelsResolver>`。請參閱[解析器](#the-resolver)。

各 Provider 的整合頁面介紹頻道設定：[Slack](/integrations/channels/slack#agent-chat)、[Telegram](/integrations/channels/telegram#connect)、[Discord](/integrations/channels/discord#agent-chat) 及 [Microsoft Teams](/integrations/channels/teams#agent-chat)。實作分別來自按需載入的 `@mastra/slack`、`@mastra/telegram`、`@mastra/discord` 及 `@mastra/teams`。如要在平台連線流程以外設定頻道，可直接使用這些套件。

設定 `MASTRA_ENCRYPTION_KEY` 後，Teams Provider 會用它加密已儲存的機械人密鑰。未設定時，金鑰會由平台存取權杖衍生；只要 Teams 連線處於啟用狀態，系統便會記錄警告。更換平台存取權杖會令已儲存的機械人憑證無法讀取，須斷開連線並重新連接以重新設定。沒有 Teams 連線的項目不受影響。

## 解析器 {/* #the-resolver */}

解析後的 `ChannelsResolver` 符合 `@mastra/core` 的頻道解析器介面契約：

* **可呼叫**：傳回目前具有有效連線的 Provider 所組成的 `Record<string, ChannelProvider>`。Mastra 在執行階段呼叫它，並透過 TTL 快取降低重複呼叫的成本。只有首次解析會等待平台回應。TTL 到期後，解析器立即傳回舊快照，同時在背景更新；若上次擷取失敗，則會在短暫冷卻期內略過更新。因此，新連線可能比 TTL 指示的時間遲一次解析才會出現。
* `getRoutes()`：同步傳回所有已啟用頻道的 API 路由，讓 Mastra 在建構時掛載。無論 Provider 是否已有有效連線，這些路由都會存在。
* `refresh()`：立即從平台擷取連線並更新快取。如果擷取失敗，Promise 會被拒絕。
* `disconnect()`：清除快取快照，讓下次解析重新擷取連線；它不會移除 Provider、工作階段或憑證。

沒有有效連線的 Provider 不會出現在解析結果中；其路由仍會保持掛載，連上後便可開始運作。

錯誤處理與 [`tools()`](/reference/connect/tools) 一致：設定錯誤（缺少項目 ID、無效的 `ttlMs`、未知或格式錯誤的 Provider ID，或同時使用 Slack 鍵的兩種寫法）會在呼叫時被拒絕；個別 Provider 的問題（建立失敗、`needs_reauth`、憑證同步失敗）只會記錄警告並略過。若同一 Provider 有多個有效連線，解析器會警告並使用第一個；可透過 `providers.<id>.connectionId` 指定連線。首次解析時平台擷取失敗會令呼叫被拒絕。背景更新失敗會警告並保留快取快照；明確呼叫 `refresh()` 時擷取失敗則會被拒絕。

## 與自行管理的頻道組合 {/* #combine-with-self-managed-channels */}

`channels()` 會取代整個 `channels` 選項，亦沒有內建工具可將它與自行建立的 Provider 合併。如部分頻道使用 Connect，其他頻道自行管理，請用同一個解析器封裝兩者。封裝結果必須可呼叫，並提供傳回所有 Provider 路由的 `getRoutes()`，因為 Mastra 只會在建構時掛載一次頻道路由：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { channels } from '@mastra/connect'
import { TelegramProvider } from '@mastra/telegram'
import { assistant } from './agents/assistant'

const connectChannels = await channels({ providers: ['slack', 'discord'] })
const telegram = new TelegramProvider()

export const mastra = new Mastra({
  agents: { assistant },
  channels: Object.assign(async () => ({ ...(await connectChannels()), telegram }), {
    getRoutes: () => [...connectChannels.getRoutes(), ...telegram.getRoutes()],
  }),
})
```

如範例的陣列形式所示，應從 Connect 選取範圍排除自行管理的頻道。Mastra 不會偵測兩個 Provider 是否註冊相同路由；若兩處都啟用同一頻道，便會掛載衝突的 Webhook。請在封裝器外只建立一次自行管理的 Provider：Mastra 對每個不同的 Provider 實例只會附加一次。憑證設定請參閱 [Telegram Provider 參考](/reference/channels/telegram-provider)。

## 按頻道調整 Tool {/* #vary-tools-by-channel */}

頻道訊息會將 [`ChannelContext`](/integrations/channels/slack#request-context) 放在[請求上下文](/docs/server/request-context)的 `channel` 鍵下。其中包含平台、對話是否為私人訊息（`isDM`）、頻道及執行緒 ID，以及發送者的用戶 ID 及姓名。Agent 的 `tools` 函式可讀取這些資料，篩選 [`tools()`](/reference/connect/tools) 解析出的物件：

```typescript title="src/mastra/agents/assistant.ts"
import { Agent } from '@mastra/core/agent'
import type { ChannelContext } from '@mastra/core/channels'
import { tools } from '@mastra/connect'

const connectTools = tools({ providers: ['linear'] })
const readTools = new Set(['linear_list_issues'])

export const assistant = new Agent({
  id: 'assistant',
  name: 'assistant',
  instructions: 'You help the team track work in Linear from Slack and Discord.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  tools: async ctx => {
    const channel = ctx.requestContext?.get('channel') as ChannelContext | undefined
    const all = await connectTools(ctx)

    if (channel?.isDM && ctx.requestContext?.get('role') === 'operator') {
      return all
    }
    return Object.fromEntries(Object.entries(all).filter(([key]) => readTools.has(key)))
  },
})
```

在此例中，只有應用程式識別為操作員的用戶發送的私人訊息，才能使用完整的 Linear Tool 集；其他請求只能使用 `linear_list_issues`。驗證發送者身分及權限後，應在可信的伺服器端程式碼中設定 `role`。請勿只按對話類型授予寫入權限。如要透過選項篩選，而非事後篩選，請參閱[每次請求選項](/reference/connect/tools#per-request-options)。

## Discord 權限 {/* #discord-permissions */}

Discord 機械人邀請網址會要求 `bot` 及 `applications.commands` 兩個 scope，以及以下權限：

* **查看頻道**
* **發送訊息**
* **在話題中發送訊息**
* **嵌入連結**
* **附加文件**
* **閱讀訊息歷史記錄**
* **添加反應**
* **使用應用程式命令**

這些權限支援聊天、執行緒、檔案、表情回應及斜線指令，但不授予管理或頻道管理權限。可透過 `providers.discord.providerOptions.permissions` 覆寫權限位元欄位。各位元的值請參閱 [Discord 權限參考](https://discord.com/developers/docs/topics/permissions#permissions-bitwise-permission-flags)。

## 錯誤 {/* #errors */}

會擲出 `MastraConnectError`，其中包含 `code` 屬性：

| 錯誤代碼 | 發生條件 |
| - | - |
| `missing_project_id` | 未設定項目 ID |
| `missing_access_token` | 未設定平台權杖 |
| `invalid_options` | Provider ID 未知或格式錯誤、同一設定中同時使用 `slack` 及 `slack-channels`、Provider 項目格式錯誤，或 `ttlMs` 無效 |
| `no_active_connection` | 頻道需要憑證，但其 Provider 沒有有效連線 |
| `unauthorized` | 平台拒絕權杖（401/403） |
| `platform_error` | 其他平台請求失敗 |
