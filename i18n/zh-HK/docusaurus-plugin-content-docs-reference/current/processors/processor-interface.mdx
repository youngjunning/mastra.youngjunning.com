# 處理器介面

這`Processor`介面定義了 Mastra 中所有處理器的合約。處理器可以實現一種或多種方法來處理Agent執行管道的不同階段。

## 當處理器方法運作時 {/* #when-processor-methods-run */}

有關準備、Agent循環、Tool執行和最終確定的概念演練，請參閱[agent lifecycle guide](/docs/guides/agent-lifecycle).

## 回調時機 {/* #callback-timing */}

|回調或操作|頻率|位置和知名度|
| - | - | - |
|`processInput` | Once per initial request | During input preparation before the loop. Resuming from a durable snapshot may skip it. |
| `processInputStep` | Once per model step | Before the provider request. It sees messages and tool results accumulated so far. |
| `processLLMRequest` | Once per provider call | Last processor stage for rewriting the provider-facing prompt. Its prompt changes aren't written back to the message list. |
| `processOutputStream`|每個流式塊 |在模型輸出到達時運行。當處理器選擇加入時，將包括資料塊。
|`processLLMResponse`|每個完成的提供者流一次 |接收當前模型步驟的完整回應。 |
|`processOutputStep`|每個模型步驟一次 |在模型回應之後、本地執行Tool之前運行。 |
|Tool[`onInputStart`](/reference/tools/create-tool#oninputstart)|串流Tool輸入何時開始 |在完整的Tool參數可用之前運行。 |
|Tool[`onInputDelta`](/reference/tools/create-tool#oninputdelta)|每個流式Tool輸入區塊 |觀察增量Tool參數。 |
|Tool[`onInputAvailable`](/reference/tools/create-tool#oninputavailable)|Tool輸入完成後一次 |在解析和驗證參數之後、執行前執行。 |
|Tool執行 |每次本地Tool呼叫一次 |接收直播[`RequestContext`](/docs/server/request-context)。批准或暂停可能会延迟执行。 |
|Tool[`onOutput`](/reference/tools/create-tool#onoutput)|本地執行成功後一次 |接收Tool輸出。 |
|`processToolResult`|每個本地/客戶端結果，或當延遲的提供者結果到達時 |可以在原始Tool結果進入訊息清單之前進行檢查、編輯或中止。 |
|`processAPIError`|關於符合條件的提供者 API 錯誤 |可以更新請求狀態並請求另一個提供者嘗試。 |
|[`onIterationComplete`](/reference/agents/generate#parameters)|每次完成循環迭代後一次 |觀察迭代結果並且可以影響是否繼續執行。 |
|`processOutputResult`|一旦完成 |在返回之前對完成的Agent結果進行後處理。 |

## 介面定義 {/* #interface-definition */}

```typescript
interface Processor<TId extends string = string, TTripwireMetadata = unknown> {
  readonly id: TId
  readonly name?: string
  readonly description?: string
  /** Index of this processor in the workflow (set at runtime when combining processors). */
  processorIndex?: number
  /** When true, processOutputStream also receives `data-*` chunks. Default: false. */
  processDataParts?: boolean

  /** Span type to trace this processor as. Defaults to `PROCESSOR_RUN`. */
  readonly spanType?: ProcessorSpanType
  /** Span name, or a function returning one per pipeline phase. */
  readonly spanName?: string | ((phase: ProcessorSpanPhase) => string)
  /** Attributes set when the span is created, or a function returning them per phase. */
  readonly spanAttributes?:
    | Partial<SpanTypeMap[ProcessorSpanType]>
    | ((phase: ProcessorSpanPhase) => Partial<SpanTypeMap[ProcessorSpanType]>)

  /** Callback invoked when this processor detects a violation, regardless of strategy. */
  onViolation?: (violation: ProcessorViolation) => void | Promise<void>

  processInput?(
    args: ProcessInputArgs<TTripwireMetadata>,
  ): Promise<ProcessInputResult> | ProcessInputResult

  processInputStep?(
    args: ProcessInputStepArgs<TTripwireMetadata>,
  ):
    | Promise<ProcessInputStepResult | MessageList | MastraDBMessage[] | undefined | void>
    | ProcessInputStepResult
    | MessageList
    | MastraDBMessage[]
    | void
    | undefined

  /** State lane id for `computeStateSignal`. Defaults to the processor id. */
  stateId?: string

  computeStateSignal?(
    args: ComputeStateSignalArgs<TTripwireMetadata>,
  ): Promise<ComputeStateSignalResult> | ComputeStateSignalResult

  processLLMRequest?(
    args: ProcessLLMRequestArgs<TTripwireMetadata>,
  ): Promise<ProcessLLMRequestResult> | ProcessLLMRequestResult

  processLLMResponse?(
    args: ProcessLLMResponseArgs<TTripwireMetadata>,
  ): Promise<ProcessLLMResponseResult> | ProcessLLMResponseResult

  processAPIError?(
    args: ProcessAPIErrorArgs<TTripwireMetadata>,
  ): Promise<ProcessAPIErrorResult | void> | ProcessAPIErrorResult | void

  processOutputStream?(
    args: ProcessOutputStreamArgs<TTripwireMetadata>,
  ): Promise<ChunkType | null | undefined>

  processOutputStep?(args: ProcessOutputStepArgs<TTripwireMetadata>): ProcessorMessageResult

  processToolResult?(args: ProcessToolResultArgs<TTripwireMetadata>): ProcessorMessageResult

  processOutputResult?(args: ProcessOutputResultArgs<TTripwireMetadata>): ProcessorMessageResult
}
```

## 追蹤 {/* #tracing */}

每個處理器都會獲得一個以其運行的管道階段命名的跨度，例如`input step processor: my-processor`. That name describes how Mastra ran the processor rather than what it does, which is unhelpful for a processor a user didn't configure as one. Mastra's own built-ins declare their subsystem instead: workspace skills trace as `skill:inject`, message history as `memory: recall` and `memory: save`.

宣告`spanType` to do the same in your own processor. A processor that runs in more than one phase usually does something different in each, so `spanName` and `spanAttributes` also accept a function of the phase:

```typescript title="src/mastra/processors/session-cache.ts"
import { SpanType } from '@mastra/core/observability'
import type { Processor, ProcessorSpanPhase } from '@mastra/core/processors'

const OPERATION: Partial<Record<ProcessorSpanPhase, 'recall' | 'save'>> = {
  inputStep: 'recall',
  output: 'save',
}

export class SessionCacheProcessor implements Processor<'session-cache'> {
  readonly id = 'session-cache' as const

  readonly spanType = SpanType.MEMORY_OPERATION
  readonly spanName = (phase: ProcessorSpanPhase) => `memory: ${OPERATION[phase] ?? 'recall'}`
  readonly spanAttributes = (phase: ProcessorSpanPhase) => ({
    operationType: OPERATION[phase] ?? 'recall',
  })
}
```

聲明的跨度類型替換`PROCESSOR_RUN`, but the span keeps its entity type and the runtime's own attributes, so it still records which phase the processor ran in, its position in the chain, and the changes it made to the message list. Processors that declare nothing are unaffected.

若要記錄僅在運行時已知的值，請從方法內部更新處理器自己的範圍：

```typescript oxfmt:false
async processInputStep({ messageList, tracingContext }: ProcessInputStepArgs) {
  tracingContext?.currentSpan?.update({ attributes: { messageCount: messageList.get.all.db().length } });
  return { messageList };
}
```

## 訊息參數 {/* #message-arguments */}

大多數處理器方法都會接收`messages` and `messageList`. They point to the same underlying conversation but expose it differently.

### `messages`與`messageList` {/* #messages-vs-messagelist */}

* `messages`：階段範圍的數組`MastraDBMessage` objects. For input processing, `processInput` and `processInputStep` exclude system messages. For output processing, `processOutputResult` and `processOutputStep` include the latest LLM response. The array is backed by `messageList`, so in-place edits to a message's `content.parts` remain visible to downstream processors and persistence.
* `messageList`: 現場直播`MessageList` instance backing the run. It exposes filtered views (input, response, remembered, all), multiple output formats (db, ui, core), and methods for mutating the conversation.

使用`messages` when you only need to read, map over, or lightly edit fields on the current stage's messages. Use `messageList` when you need to:

* 從另一個階段讀取訊息，例如在處理輸出時輸入訊息。
* 新增、刪除或取代整個訊息。
* 轉換為其他格式，例如第三方 API 的 UI 或核心訊息。

`messages`總是源自`messageList`, so mutating `messageList` is the canonical way to add, remove, or reorder messages. For in-place edits to a message's content (for example, rewriting `content.parts`), mutating `messages` directly is equivalent. If you return a new array from `messages`, Mastra reconciles it against `messageList` for the current stage.

### 堅持 {/* #persistence */}

當記憶體被啟用時，只有最終的內容`messageList` after all processors finish is persisted to storage. Both return styles are equivalent for persistence:

* 當你變異時`messageList` directly (or return the same `MessageList` instance), recorded mutations are applied in place. The saved conversation reflects your changes.
* 當您返回一個`MastraDBMessage[]` or `{ messages, systemMessages }`, Mastra reconciles the returned array against `messageList` for the current stage, removing missing messages and replacing system messages.

返回不同的`MessageList` instance is an error. Always mutate the one passed to your processor.

### 從訊息中讀取文本 {/* #reading-text-from-a-message */}

`MastraDBMessage.content`使用結構化物件。不支援字串。閱讀使用者或助理文字的規範方法是`content.parts`:

```typescript
import type { MastraDBMessage } from '@mastra/core/memory'

function getText(message: MastraDBMessage): string {
  let text = ''

  if (message.content.parts) {
    for (const part of message.content.parts) {
      if (part.type === 'text' && typeof part.text === 'string') {
        text += part.text
      }
    }
  }

  // Fallback for legacy messages that only have the flattened `content` string
  if (!text && typeof message.content.content === 'string') {
    text = message.content.content
  }

  return text
}
```

要點：

* `message.content.parts`是主要來源。一條訊息可以包含多個部分。非文字部分包括Tool呼叫和Tool結果以及文件部分。過濾依據`part.type === 'text'` before reading `part.text`.
* `message.content.content`是為了向後相容而保留的扁平字串。僅將其用作後備`parts` is empty or missing.
* `message.content`它本身從來都不是一個普通的字串`MastraDBMessage`. Legacy `CoreMessage` shapes may be strings, but processors always receive `MastraDBMessage`.

### `processInputStep` {/* #processinputstep */}

在將輸入訊息傳送到 LLM 之前，在Agent循環的每個步驟中處理輸入訊息。不像`processInput` which runs once at the start, this runs at every step including tool call continuations.

```typescript oxfmt:false
processInputStep?<TTripwireMetadata = unknown>(
  args: ProcessInputStepArgs<TTripwireMetadata>,
):
  | Promise<ProcessInputStepResult | MessageList | MastraDBMessage[] | void | undefined>
  | ProcessInputStepResult
  | MessageList
  | MastraDBMessage[]
  | void
  | undefined;
```

#### Agent循環中的執行順序 {/* #execution-order-in-the-agentic-loop */}

1. `processInput`（開始時一次）
2. `processInputStep`來自 inputProcessors（在每一步，在 LLM 呼叫之前）
3. `prepareStep`回呼（作為 processInputStep 管道的一部分在 inputProcessors 之後運行）
4. `computeStateSignal`來自 inputProcessors （之後`processInputStep`, before the LLM request)
5. `processLLMRequest`來自 inputProcessors（提示轉換之後，提供者呼叫之前）
6. 法學碩士執行
7. `processOutputStream`來自outputProcessors（在每個流塊上）
8. `processLLMResponse`來自 inputProcessors （流完成後，與`processLLMRequest`)
9. `processOutputStep`來自outputProcessors（LLM回應之後，Tool執行之前）
10. Tool執行（如果需要）
11. 如果呼叫了Tool，則從步驟 2 開始重複

#### 處理器連結 {/* #processor-chaining */}

當多個處理器實現`processInputStep`, they run in order and changes chain through:

```text
Processor 1: receives { model: 'gpt-5.4' } → returns { model: 'gpt-5.4-mini' }
Processor 2: receives { model: 'gpt-5.4-mini' } → returns { toolChoice: 'none' }
Final: model = 'gpt-5.4-mini', toolChoice = 'none'
```

#### 系統訊息隔離 {/* #system-message-isolation */}

系統訊息有**reset to their original values** at the start of each step. Modifications made in `processInputStep` only affect the current step, not subsequent steps.

#### 使用案例 {/* #use-cases */}

* 基於步驟數或上下文的動態模型切換
* 在配置的步驟數後停用Tool
* 根據對話上下文動態新增或取代Tool
* 在提供者之間轉換訊息部分類型（例如，`reasoning` → `thinking` for Anthropic)
* 根據步驟號或累積的上下文修改訊息
*
* 每一步調整提供者選項（例如快取控制）
* 根據步驟上下文修改結構化輸出模式

### `computeStateSignal` {/* #computestatesignal */}

每個模型輸入步驟計算一次執行緒範圍的狀態訊號，之後`processInputStep()` and before the LLM request is finalized. This method requires an agent with memory and an active `resourceId` and `threadId`.

```typescript oxfmt:false
computeStateSignal?(
  args: ComputeStateSignalArgs,
): Promise<ProcessorStateSignal | undefined | void> | ProcessorStateSignal | undefined | void;
```

傳回一個狀態訊號來儲存它，或者`undefined` or `void` when nothing changed. The returned `id` defaults to the processor's `stateId`, which itself defaults to the processor `id`. `mode` defaults to `snapshot`.

```typescript title="src/mastra/processors/error-recovery.ts"
import { APICallError } from '@ai-sdk/provider'
import type { Processor, ProcessAPIErrorArgs, ProcessAPIErrorResult } from '@mastra/core/processors'

export class ErrorRecoveryProcessor implements Processor {
  id = 'error-recovery'

  processAPIError({
    error,
    messageList,
    retryCount,
  }: ProcessAPIErrorArgs): ProcessAPIErrorResult | void {
    // Only retry once
    if (retryCount > 0) return

    // Check for a specific API error
    if (APICallError.isInstance(error) && error.message.includes('context length exceeded')) {
      // Trim older messages to fit within context
      const messages = messageList.get.all.db()
      if (messages.length > 4) {
        messageList.removeByIds([messages[1]!.id, messages[2]!.id])
        return { retry: true }
      }
    }
  }
}
```

#### 發出第二個區塊 {/* #emitting-a-second-chunk */}

`processOutputStream`傳回一個區塊，但處理器有時需要為一個輸入發出兩個區塊，例如它保留的文本，然後是釋放它的區塊。返回第一個區塊並將第二個區塊設為 on`state` under `REPROCESS_PART_KEY`. Mastra emits the stashed chunk right after the returned one.

隱藏的區塊再次通過輸出處理器，包括隱藏它的處理器，因此處理器必須在第二遍時將其原封不動地通過：

```typescript title="src/mastra/processors/sign-off.ts"
import { REPROCESS_PART_KEY } from '@mastra/core/processors'
import type { ChunkType } from '@mastra/core/stream'
import type { ProcessOutputStreamArgs, Processor } from '@mastra/core/processors'

export class SignOff implements Processor<'sign-off'> {
  readonly id = 'sign-off'

  async processOutputStream({ part, state }: ProcessOutputStreamArgs): Promise<ChunkType> {
    if (part.type !== 'text-end' || state.signed) return part
    state.signed = true
    state[REPROCESS_PART_KEY] = part
    return { ...part, type: 'text-delta', payload: { id: part.payload.id, text: '\n\nCheers!' } }
  }
}
```

```typescript title="src/mastra/processors/quality-guardrail.ts"
export class QualityGuardrail implements Processor {
  id = 'quality-guardrail'

  async processOutputStep({ messages, text, abort, retryCount }) {
    const score = await evaluateResponseQuality(text)

    if (score < 0.7) {
      if (retryCount < 3) {
        // Request retry with feedback for the LLM
        abort('Response quality too low. Please provide more detail.', {
          retry: true,
          metadata: { qualityScore: score },
        })
      } else {
        // Max retries reached, block the response
        abort('Response quality too low after multiple attempts.')
      }
    }

    return messages
  }
}
```

### `processToolResult` {/* #processtoolresult */}

在本地執行的Tool返回或提供程序執行的結果到達後、原始結果保存到先前處理Tool的結果`messageList` or fed to the next LLM call. Symmetric with `processOutputStep`, which fires before tool execution. Use this method to enforce security policies on tool output. For example, scan for prompt injection or redact sensitive fields. Call `abort('reason', { retry: true })` to abort and retry the same step.

要替換Tool的結果，請進行變異`messageList` in place via `messageList.updateToolInvocation`. The runtime re-reads the post-processor result from the message list and overwrites the downstream tool-result stream chunk before it's enqueued, so streaming clients see the processed value.

當以下情況時此方法不會觸發`tool.execute()` throws. It's called only for successful tool executions where a result is available.

```typescript oxfmt:false
processToolResult?(args: ProcessToolResultArgs): ProcessorMessageResult;
```

* 在法學碩士看到之前掃描Tool輸出以進行提示注入。

#### 範例：編輯敏感字段 {/* #example-redact-sensitive-fields */}

```typescript title="src/mastra/processors/redact-tool-result.ts"
import type { Processor } from '@mastra/core/processors'

export class RedactToolResult implements Processor {
  id = 'redact-tool-result'

  async processToolResult({ toolName, toolCallId, args, result, messageList }) {
    if (toolName !== 'lookup-customer') return

    const redacted = {
      ...(result as Record<string, unknown>),
      ssn: '[REDACTED]',
      email: '[REDACTED]',
    }

    messageList.updateToolInvocation({
      type: 'tool-invocation',
      toolInvocation: {
        state: 'result',
        toolCallId,
        toolName,
        args,
        result: redacted,
      },
    })
  }
}
```

#### 範例：在Tool輸出中阻止提示注入 {/* #example-block-prompt-injection-in-tool-output */}

```typescript title="src/mastra/processors/scan-tool-result.ts"
import type { Processor } from '@mastra/core/processors'

export class ScanToolResult implements Processor {
  id = 'scan-tool-result'

  async processToolResult({ result, abort }) {
    const text = typeof result === 'string' ? result : JSON.stringify(result)
    if (containsPromptInjection(text)) {
      abort('blocked by scan-tool-result: suspected prompt injection')
    }
  }
}

function containsPromptInjection(text: string): boolean {
  return /ignore (all )?(previous|prior) instructions/i.test(text)
}
```

## 處理器類型 {/* #processor-types */}

Mastra 提供類型別名以確保處理器實作所需的方法：

```typescript
// Must implement processInput, processInputStep, processLLMRequest, or processLLMResponse (or any combination)
type InputProcessor = Processor &
  (
    | { processInput: required }
    | { processInputStep: required }
    | { processLLMRequest: required }
    | { processLLMResponse: required }
  )

// Must implement processOutputStream, processOutputStep, OR processOutputResult (or any combination)
type OutputProcessor = Processor &
  (
    | { processOutputStream: required }
    | { processOutputStep: required }
    | { processOutputResult: required }
  )

// Must implement processAPIError
type ErrorProcessor = Processor & { processAPIError: required }
```

配置實現的處理器`processAPIError` in `errorProcessors`:

```typescript
const agent = new Agent({
  id: 'agent',
  errorProcessors: [new PrefillErrorHandler()],
})
```

### 每步處理器`processInputStep` {/* #per-step-processor-with-processinputstep */}

```typescript title="src/mastra/processors/dynamic-model.ts"
import type {
  Processor,
  ProcessInputStepArgs,
  ProcessInputStepResult,
} from '@mastra/core/processors'

export class DynamicModelProcessor implements Processor {
  id = 'dynamic-model'

  async processInputStep({
    stepNumber,
    steps,
    toolChoice,
  }: ProcessInputStepArgs): Promise<ProcessInputStepResult> {
    // Use a fast model for initial response
    if (stepNumber === 0) {
      return { model: '__GATEWAY_OPENAI_MODEL_LUNA__' }
    }

    // Switch to powerful model after tool calls
    if (steps.length > 0 && steps[steps.length - 1].toolCalls?.length) {
      return { model: '__GATEWAY_OPENAI_MODEL__' }
    }

    // Disable tools after 5 steps to force completion
    if (stepNumber > 5) {
      return { toolChoice: 'none' }
    }

    return {}
  }
}
```

### 訊息轉換器`processInputStep` {/* #message-transformer-with-processinputstep */}

```typescript title="src/mastra/processors/reasoning-transformer.ts"
import type { Processor } from '@mastra/core/processors'
import type { MastraDBMessage } from '@mastra/core/memory'

export class ReasoningTransformer implements Processor {
  id = 'reasoning-transformer'

  async processInputStep({ messages, messageList }) {
    // Transform reasoning parts to thinking parts at each step
    // This is useful when switching between model providers
    for (const msg of messages) {
      if (msg.role === 'assistant' && msg.content.parts) {
        for (const part of msg.content.parts) {
          if (part.type === 'reasoning') {
            ;(part as any).type = 'thinking'
          }
        }
      }
    }
    return messageList
  }
}
```

### 混合處理器（輸入和輸出） {/* #hybrid-processor-input-and-output */}

```typescript title="src/mastra/processors/content-filter.ts"
import type { Processor } from '@mastra/core/processors'
import type { MastraDBMessage } from '@mastra/core/memory'
import type { ChunkType } from '@mastra/core/stream'

export class ContentFilter implements Processor {
  id = 'content-filter'
  private blockedWords: string[]

  constructor(blockedWords: string[]) {
    this.blockedWords = blockedWords
  }

  async processInput({ messages, abort }): Promise<MastraDBMessage[]> {
    for (const msg of messages) {
      const text = msg.content.parts
        ?.filter(p => p.type === 'text')
        .map(p => p.text)
        .join(' ')

      if (this.blockedWords.some(word => text?.includes(word))) {
        abort('Blocked content detected in input')
      }
    }
    return messages
  }

  async processOutputStream({ part, abort }): Promise<ChunkType | null> {
    if (part.type === 'text-delta') {
      if (this.blockedWords.some(word => part.payload.text.includes(word))) {
        abort('Blocked content detected in output')
      }
    }
    return part
  }
}
```

### 帶狀態的流累加器 {/* #stream-accumulator-with-state */}

```typescript title="src/mastra/processors/word-counter.ts"
import type { Processor } from '@mastra/core/processors'
import type { ChunkType } from '@mastra/core/stream'

export class WordCounter implements Processor {
  id = 'word-counter'

  async processOutputStream({ part, state }): Promise<ChunkType> {
    // Initialize state on first chunk
    if (!state.wordCount) {
      state.wordCount = 0
    }

    // Count words in text chunks
    if (part.type === 'text-delta') {
      const words = part.payload.text.split(/\s+/).filter(Boolean)
      state.wordCount += words.length
    }

    // Log word count on finish
    if (part.type === 'finish') {
      console.log(`Total words: ${state.wordCount}`)
    }

    return part
  }
}
```

## 狀態生命週期 {/* #state-lifecycle */}

`state` object in `processLLMRequest`, `processLLMResponse`, `processOutputStream`, `processOutputStep`, `processOutputResult`, and `processAPIError`. State has three important properties:

* **每個處理器**：每個處理器都有自己的`state` object, keyed by the processor's `id`. Processors with different ids can't read or overwrite each other's state.
* **按請求**：每次開始時都會建立一個新的狀態對象`agent.generate()` or `agent.stream()` call. State doesn't leak between requests or between users.
* **跨方法共享**：在一個請求內，相同`state` object is passed to `processLLMRequest` (before the provider call), `processLLMResponse` (after the step completes), `processOutputStream` (for every chunk), `processOutputStep` (after every LLM step), `processOutputResult` (once at the end), and `processAPIError` (when an LLM call fails). For example, `processLLMRequest` can stash a cache key and `processLLMResponse` can read it back to write the response.

在第一次訪問時防禦性地初始化字段，因為`state` starts as an empty object:

```typescript
import type { Processor } from '@mastra/core/processors'

export class WordCounter implements Processor {
  id = 'word-counter'

  async processOutputStream({ part, state }) {
    state.wordCount ??= 0
    if (part.type === 'text-delta') {
      state.wordCount += part.payload.text.split(/\s+/).filter(Boolean).length
    }
    return part
  }
}
```

## 中止和絆線區塊 {/* #aborting-and-tripwire-chunks */}

這`abort` function on each method throws a `TripWire` error that stops processing and emits a `tripwire` chunk on the output stream. Clients can detect the chunk to distinguish a blocked response from a normal finish.

```typescript
abort('Blocked content detected', { retry: false, metadata: { category: 'pii' } })
```

* `reason`：人類可讀的解釋。顯示為`tripwire.payload.reason`.
* `retry`： 什麼時候`true`, the agent retries the same step with `reason` fed back as feedback. Retries only run when `maxProcessorRetries` is set on the agent or call; otherwise the request aborts. The safety cap of `3` that applies when no cap is set covers only error-processor retries from `processAPIError`. It doesn't give abort retries a budget.
* `metadata`：附加到的可選結構化數據`tripwire` chunk for downstream consumers.

發射的`tripwire` chunk has the shape:

```typescript
type TripwireChunk = {
  type: 'tripwire'
  runId: string
  from: 'AGENT'
  payload: {
    reason: string
    retry?: boolean
    metadata?: unknown
    processorId: string
  }
}
```

在非串流通話中（`agent.generate()`), the result exposes the same information as `result.tripwire` and `result.finishReason === 'other'`.

## 發出自訂資料塊 {/* #emitting-custom-data-chunks */}

有權存取的處理器`writer` can stream custom `data-*` chunks to the client by calling `writer.custom(chunk)`. Tools can do the same through their own writer. This is the only way for a processor to emit content outside of normal text and tool chunks.

```typescript
await writer.custom({
  type: 'data-moderation',
  runId,
  from: 'AGENT',
  data: { level: 'warn', reason: 'Possibly unsafe' },
})
```

配置記憶體後，自訂`data-*` chunks emitted from `processOutputStream` or `processOutputResult` are saved as parts of the assistant message. Set `transient: true` on the chunk object to stream it without saving it to memory:

```typescript {4}
await writer.custom({
  type: 'data-progress',
  data: { status: 'Processing' },
  transient: true,
})
```

經過`transient` as a property of the chunk, not as the second argument to `writer.custom()`. The second argument contains writer options such as `messageId`.

預設情況下，處理器**don't** see `data-*` chunks in `processOutputStream` so they don't accidentally process tool telemetry or their own output. Opt in by setting `processDataParts: true` on the processor:

```typescript
class ModerationCollector implements Processor {
  id = 'moderation-collector'
  processDataParts = true

  async processOutputStream({ part, state }) {
    if (part.type === 'data-moderation') {
      state.warnings ??= []
      state.warnings.push(part.data)
    }
    return part
  }
}
```

大塊`type` must start with `data-` to be treated as a custom data chunk. Returning `null` or `undefined` from `processOutputStream` still drops the chunk, so a processor can inspect, modify, or filter custom data the same way it filters text chunks.

## 在Agent上配置處理器 {/* #configuring-processors-on-an-agent */}

處理器透過三個陣列連接到Agent程式：

```typescript
import { Agent } from '@mastra/core/agent'
import { PrefillErrorHandler } from '@mastra/core/processors'

const agent = new Agent({
  id: 'support-agent',
  name: 'support-agent',
  model: '__GATEWAY_OPENAI_MODEL_BASE__',
  instructions: '...',
  inputProcessors: [new ContentFilter(['secret'])],
  outputProcessors: [new WordCounter()],
  errorProcessors: [new PrefillErrorHandler()],
  maxProcessorRetries: 3,
})
```

* `inputProcessors`：在LLM之前運行。接收輸入訊息。
* `outputProcessors`：在 LLM 回應期間或之後運行。接收輸出區塊或訊息。
* `errorProcessors`：LLM API 呼叫拋出時運行。接收原始錯誤。

每個數組也接受一個函數，因此可以根據請求建立處理器`RequestContext`:

```typescript
new Agent({
  id: 'processor-interface-agent',
  inputProcessors: ({ requestContext }) => {
    const blockedWords = requestContext.get('blockedWords') ?? []
    return [new ContentFilter(blockedWords)]
  },
})
```

### 每次呼叫覆蓋 {/* #per-call-overrides */}

`agent.generate()`和`agent.stream()` accept `inputProcessors`, `outputProcessors`, `errorProcessors`, and `maxProcessorRetries`. When any processor array is set on the call, it **replaces** the matching array configured on the agent for that request. Memory, workspace, skill, channel, and browser processors that Mastra adds automatically are always preserved and run around your array.

```typescript
await agent.stream('Summarize this', {
  outputProcessors: [new StreamFilter()],
  maxProcessorRetries: 5,
})
```

`maxProcessorRetries`傳遞的呼叫將覆蓋Agent預設值。如果兩者均未設置，則輸入和輸出處理器請求的重試將被視為中止，而錯誤處理器（例如[`StreamErrorRetryProcessor`](/reference/processors/stream-error-retry-processor)) are capped at 3 retries.
