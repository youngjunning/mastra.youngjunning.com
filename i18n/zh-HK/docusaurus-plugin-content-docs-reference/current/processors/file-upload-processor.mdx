# FileUploadProcessor

`FileUploadProcessor` 會將用戶傳送的文件上傳至[工作區沙箱](/reference/workspace/sandbox)，並在傳給模型的文字說明中，以沙箱路徑取代每個文件。模型不會收到文件內容；Agent 會使用沙箱 Tool 處理文件。

只有傳送至模型的提示會改變。已儲存的訊息仍保留文件，因此線程、Studio 等客戶端及其他 Agent 仍可取得原始文件。

篩選器接受的文件不會傳給模型：若目前回合的文件無法上傳，處理器會停止該回合，而不會讓文件直接通過。Memory 屬可選功能。

## 使用範例 {/* #usage-example */}

請將同一個工作區傳給 Agent 及處理器：

```typescript
import { Agent } from '@mastra/core/agent'
import { FileUploadProcessor } from '@mastra/core/processors'
import { LocalSandbox, Workspace } from '@mastra/core/workspace'

const workspace = new Workspace({
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
})

export const agent = new Agent({
  id: 'file-agent',
  name: 'file-agent',
  instructions: 'Work on the files the user uploads to the sandbox.',
  model: '__GATEWAY_OPENAI_MODEL_LUNA__',
  workspace,
  inputProcessors: [
    new FileUploadProcessor({
      workspace,
      filter: ({ extension }) => extension === 'xlsx' || extension === 'docx',
    }),
  ],
})
```

使用 `maxFileSize` 設定每個文件的大小限制。此函式傳回位元組數：

```typescript
import { FileUploadProcessor } from '@mastra/core/processors'

const megabyte = 1024 * 1024

const fileUpload = new FileUploadProcessor({
  workspace,
  maxFileSize: ({ mimeType }) => (mimeType.startsWith('image/') ? 5 * megabyte : 25 * megabyte),
})
```

處理器停止回合時，請讀取停止原因。Tripwire 元數據的型別為 `unknown`，因此須將其轉型為 `FileUploadTripwireMetadata`：

```typescript
import { FILE_UPLOAD_ERROR_CODES } from '@mastra/core/processors'
import type { FileUploadTripwireMetadata } from '@mastra/core/processors'

const result = await agent.generate(messages)

if (result.tripwire?.processorId === 'file-upload') {
  const { code, fileName } = result.tripwire.metadata as FileUploadTripwireMetadata

  if (code === FILE_UPLOAD_ERROR_CODES.FILE_TOO_LARGE) {
    console.error(`${fileName} is too large`)
  }
}
```

## 文件選擇 {/* #file-selection */}

`filter` 函數接收用戶傳送的每個文件，傳回 `true` 表示上傳。遭拒絕的文件保持原狀，照常傳給模型。若沒有設定 `filter`，所有文件都會上傳。

以下篩選器會上傳模型可自行讀取的類型以外的所有文件：

```typescript
import { FileUploadProcessor } from '@mastra/core/processors'

const readByModel = ['image/', 'audio/', 'video/', 'text/']

const fileUpload = new FileUploadProcessor({
  workspace,
  filter: ({ mimeType }) =>
    mimeType !== 'application/pdf' && !readByModel.some(prefix => mimeType.startsWith(prefix)),
})
```

`filter` 與 `maxFileSize` 接收相同的 `FileUploadFileInfo` 物件：

文件大小不在此物件中，因為資料解碼後才知道大小。`filter` 可以是非同步函數。

處理器會檢查模型收到的每則用戶訊息中的文件，包括線程歷史，以及隨 signal 傳送的文件。它會忽略助理產生或 Tool 傳回的文件。

以內嵌二進位、base64 或資料 URL 形式傳送的文件都會上傳。處理器本身不會下載任何內容，因此伺服器發出的請求無法藉此指向內部地址：

* 模型自行取得的連結或 Provider 文件 ID 會留在提示中，亦不會調用 `filter`。
* 模型無法取得的連結會由 Mastra 在模型調用前下載。處理器會像處理其他將傳給模型的文件一樣，處理下載後的位元組。

## 上傳位置 {/* #upload-location */}

文件會寫入沙箱執行命令的目錄下，路徑為 `uploads/<directory>/<sha256>.<extension>`。`<directory>` 優先使用線程 ID；沒有線程時使用資源 ID；兩者都沒有時使用 `shared`。因此，不同線程中內容相同的文件亦不會共用路徑。

處理器透過 `pwd` 取得命令目錄，再寫入文件並報告絕對路徑。Provider 對寫入與執行命令的相對路徑解析方式不同，因此命令 Tool 需要絕對路徑才能找到文件。無法執行命令的沙箱改用其 `workingDirectory`；若兩者都無法確定，路徑會維持相對形式。

文件名稱取自內容的 SHA-256 雜湊值，因此相同的位元組始終寫入同一路徑：

* 沙箱中已有的文件不會重新寫入。後續回合只須檢查它是否仍存在。
* 從沙箱刪除的文件，或因沙箱回收而遺失的文件，會在下一回合重新寫入。
* 同一請求中，不論呼叫模型多少次，每個文件都只會放置一次。

路徑只保留原始文件名的副檔名。若路徑看起來像原始文件名，模型可能按此重新拼寫路徑，再向沙箱要求不存在的文件。原始名稱仍會出現在說明中。

| 傳送時的名稱 | 命令目錄下的寫入路徑 |
| - | - |
|`report Q3 (final).pdf` | `uploads/<directory>/<sha256>.pdf` |
| `résumé.PDF` | `uploads/<directory>/<sha256>.pdf` |
| `../../etc/passwd` | `uploads/<directory>/<sha256>` |
| 無名稱，`image/png` | `uploads/<directory>/<sha256>.png` |

沒有名稱的文件，若 MIME 類型是常見類型，會按此取得副檔名。

線程或資源 ID 會被重寫，確保目錄名稱可安全用於 shell 命令。重音符號會移除；除 `A-Z`、`a-z`、`0-9`、`.`、`_` 及 `-` 以外的字元都會替換為 `_`。路徑分隔符及 `..` 亦會替換，因此文件始終位於 `uploads/` 之內。

每個文件會先以暫存名稱寫入，再移至目標位置，因此寫入中斷不會留下被之後回合誤認為完整文件的殘缺文件。若沙箱支援 `writeFiles`，處理器會在一次調用中寫入所有待寫文件；否則透過 `executeCommand` 分塊傳送 base64 資料，此時沙箱須提供 `base64` 及 `printf`。能執行命令的沙箱還須提供 `sh`、`mkdir`、`pwd` 及 `mv`。無法執行命令的沙箱不能檢查或移動文件，因此每回合都會在目標位置重新寫入所有文件。

## 上傳後提示內容 {/* #prompt-content-after-upload */}

在傳給模型的提示中，訊息裡的文件部分會在原位置由文字部分取代：

```text
[File uploaded to the sandbox]
path: /home/user/uploads/thread-1/0b2f4c6e8a1d3f5b7c9e2a4d6f8b1c3e5a7d9f2b4c6e8a1d3f5b7c9e2a4d6f8b.pdf
name: report.pdf
type: application/pdf
size: 1258291 bytes
```

已儲存的訊息仍保留文件傳送時的原貌。Studio 及其他客戶端會將其顯示為附件，模型則會在每回合重新收到這段說明。

## 錯誤行為 {/* #error-behavior */}

若缺少 `workspace`，或其中沒有設定沙箱，建構函數會拋出 ID 為 `FILE_UPLOAD_PROCESSOR_NO_SANDBOX` 的 `MastraError`。`error.details.code` 為 `NO_SANDBOX`。

寫入任何內容前，處理器會按目前回合的文件傳送時的形式檢查它們。無法上傳的文件會停止該回合，而且不會上傳任何文件。

若線程歷史中的文件太大或無法解碼，處理器會用說明問題的文字取代文件，並讓回合繼續。這可避免已儲存的文件阻礙之後每個回合：

```text
[File not uploaded]
name: report.pdf
reason: File "report.pdf" is 31457280 bytes, over the 10485760 byte limit.
```

若沙箱無法接收文件，例如沒有沙箱、無法寫入或寫入失敗，目前回合的文件會令回合停止；線程歷史中的文件則會改為說明原因的文字，回合繼續。若 `filter` 或 `maxFileSize` 失敗，不論影響哪個文件，回合都會停止。儲存內容維持不變，修正設定後線程即可繼續。沒有待上傳文件的回合不會檢查，因此 scorer、Agent 網絡及沒有線程的調用仍可正常運作。

處理器透過調用 `abort()` 並設定 `retry: false` 來停止回合。模型不會被調用。`agent.generate()` 不會拒絕 Promise，而是傳回設有 `result.tripwire` 的結果；`agent.stream()` 則會發出 `tripwire` 區塊。

`FILE_UPLOAD_ERROR_CODES` 列出所有錯誤代碼：

| 代碼 | 發生條件 |
| - | - |
| `NO_SANDBOX` | 請求沒有解析到沙箱，或解析失敗 |
| `NO_WRITE_CAPABILITY` | 沙箱既不支援 `writeFiles`，也不支援 `executeCommand` |
| `INVALID_MAX_FILE_SIZE` | `maxFileSize` 拋出錯誤，或傳回的不是非負數 |
| `INVALID_FILTER` | `filter` 拋出錯誤，或傳回的不是 `true` 或 `false` |
| `INVALID_FILE_DATA` | 目前回合文件的內嵌資料無法解碼 |
| `FILE_TOO_LARGE` | 目前回合的文件超過大小限制 |
| `UPLOAD_FAILED` | 寫入沙箱失敗 |

寫入失敗時，處理器會在停止回合前，以 `rm -f` 刪除本次呼叫中已寫入的文件。若刪除失敗，或沙箱無法執行命令，`orphanPaths` 會列出可能殘留的路徑。

## 透過訊號發送的文件 {/* #files-sent-with-signals */}

處理器會處理透過 `agent.sendMessage()` 及 `agent.sendSignal()` 傳送的文件：

* 喚醒閒置 Agent 的 signal 會按 `agent.stream()` 的輸入處理。
* 傳送給正在運行的 Agent 的 signal，會在該次運行的下一次模型調用前接受檢查並上傳。
* 若 signal 在持久化 Agent 首次調用模型前抵達，會在目前回合的檢查後加入提示。其文件會像線程歷史中的文件一樣上傳。

## 限制 {/* #limitations */}

* **處理器 Workflow。**上傳發生在 `processLLMRequest`；處理器嵌套在處理器 Workflow 時不會執行此方法。此時處理器只檢查文件，文件會原樣傳給模型。請將 `FileUploadProcessor` 直接加入 `inputProcessors`。
* **跨線程共用的沙箱。**各線程的目錄可分隔文件，但不提供存取保護。在其他線程或用戶共用的沙箱中，任何線程的命令 Tool 都能讀取所有上傳文件。若文件屬私密內容，請[為每個用戶或線程配置獨立沙箱](/docs/sandbox/overview#sandboxes-per-user-or-thread)。
* **從 Studio 傳送的文字文件。**Studio 會將 CSV、JSON、Markdown 或源碼等文字文件以文字插入訊息，而非附加為文件。處理器看不到它們，因此不會上傳，完整內容會進入提示。透過 API 以文件部分傳送的文件則會照常上傳。
