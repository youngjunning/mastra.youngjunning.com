# ToolSearchProcessor

`ToolSearchProcessor` 是一種**輸入處理器**，支援在運行時發現並載入動態定義的工具。它不會預先向 Agent 提供所有工具，而是提供 `search_tools` 和 `load_tool` 兩個元工具，讓 Agent 按需尋找和載入工具。處理大型工具庫時，這有助於減少上下文 Token 用量。

## 使用例子 {/* #usage-example */}

```typescript
import { ToolSearchProcessor } from '@mastra/core/processors'

const toolSearch = new ToolSearchProcessor({
  tools: {
    createIssue: githubTools.createIssue,
    sendEmail: emailTools.send,
    getWeather: weatherTools.forecast,
    // ... many more tools
  },
  search: {
    topK: 5,
    minScore: 0.1,
  },
})
```

## 方法 {/* #methods */}

### 狀態檢查（舊版 `'in-memory'` 儲存） {/* #state-inspection-legacy-in-memory-store */}

這些方法只作用於預設的 `'in-memory'` 儲存。對於 `'context'` 儲存，它們不會產生效果；後者的狀態保存在對話訊息中，而非進程內映射中。

#### `clearState(threadId)` {/* #clearstatethreadid */}

清除單個線程中已載入工具的狀態。

```typescript
processor.clearState('thread-123')
```

#### `clearAllState()` {/* #clearallstate */}

清除所有線程中已載入工具的狀態。

```typescript
processor.clearAllState()
```

#### `getStateStats()` {/* #getstatestats */}

傳回已追蹤線程的數量和最早存取時間，可用於排查記憶體增長。

```typescript
const { threadCount, oldestAccessTime } = processor.getStateStats()
```

傳回：`{ threadCount: number; oldestAccessTime: number | null }`

#### `cleanupNow()` {/* #cleanupnow */}

立即執行 TTL 清理，無需等待計劃中的掃描。

```typescript
const cleaned = processor.cleanupNow()
```

傳回值：`number`，表示已清理的線程數量。

## 請求感知篩選 {/* #request-aware-filtering */}

使用 `filter` 為運行時定義的工具實施針對請求的策略。Hook 會收到解析後的工具 ID（`toolName`）、工具、請求上下文和階段。`toolName` 是 `search_tools` 傳回的 ID，可能與 `tools` 對象中的鍵不同。

```typescript
import { ToolSearchProcessor } from '@mastra/core/processors'

const toolSearch = new ToolSearchProcessor({
  tools: allTools,
  filter: ({ toolName, requestContext, phase }) => {
    const plan = requestContext?.get('plan')

    if (phase === 'search') {
      return true
    }

    return plan === 'pro' || !toolName.startsWith('premium_')
  },
})
```

`phase` 的值表示篩選器的應用階段：

- `search`：篩選 `search_tools` 傳回的結果。
- `load`：阻止 `load_tool` 載入不允許的工具。
- `active`：如果已載入的工具對當前請求不再允許，則將其隱藏。

如果 Hook 拋出錯誤或拒絕 Promise，`ToolSearchProcessor` 會將該工具視為對當前請求不可用。Hook 可能對每個匹配的搜尋候選工具運行，因此異步策略檢查應盡量輕量，或使用緩存。`search_tools` 元工具始終可用；除非啟用 `search.autoLoad`，否則 `load_tool` 也可用。直接透過 Agent 或 `processInputStep` 傳入的工具仍然可用，除非你在 `ToolSearchProcessor` 之外對其進行篩選，或啟用 `includeResolvedTools`。

## 搜尋針對請求解析的工具 {/* #searching-request-resolved-tools */}

`tools` 選項在構造時就固定下來，因此無法列出僅在單次請求中存在的工具（例如需要呼叫者憑證的 MCP 工具，或動態 `tools` 函數傳回的工具）。預設情況下，這些工具會繞過搜尋，在每一輪佔用提示空間。

設定 `includeResolvedTools: true`，可為這些工具按請求建立索引，並在 Agent 載入前不將它們加入提示：

```typescript title="src/mastra/agents/mcp-agent.ts"
import { Agent } from '@mastra/core/agent'
import { ToolSearchProcessor } from '@mastra/core/processors'

const toolSearch = new ToolSearchProcessor({
  tools: staticTools,
  includeResolvedTools: true,
})

const agent = new Agent({
  id: 'mcp-agent',
  name: 'mcp-agent',
  instructions: 'Search for a tool when you need a capability you do not have.',
  model: '__GATEWAY_OPENAI_MODEL__',
  // Resolved per request, then searchable alongside staticTools
  tools: async ({ requestContext }) => mcpClient.getTools(requestContext.get('userToken')),
  inputProcessors: [toolSearch],
})
```

每個請求分別建立索引，因此一個呼叫者載入的工具不會解析為另一個呼叫者同名工具的實例。

此選項適用於為請求解析的所有工具，包括 Memory、Workspace、Skill 和瀏覽器工具。提示中只保留 `search_tools` 和 `load_tool` 元工具，因此 Agent 隱式依賴的工具也必須先透過搜尋找到，才能呼叫。不過，如果啟用了 `injectCatalog` 且 `search.autoLoad` 為 `false`，Agent 可以直接透過 `load_tool` 載入該工具。`search.autoLoad: true` 時不會暴露 `load_tool`，而由 `search_tools` 啟用匹配工具。

## 擴展例子 {/* #extended-usage-example */}

```typescript title="src/mastra/agents/dynamic-tools-agent.ts"
import { Agent } from '@mastra/core/agent'
import { ToolSearchProcessor } from '@mastra/core/processors'

// Tools from various integrations
import { githubTools } from './tools/github'
import { slackTools } from './tools/slack'
import { dbTools } from './tools/database'

const toolSearch = new ToolSearchProcessor({
  tools: {
    ...githubTools, // createIssue, listPRs, mergePR, ...
    ...slackTools, // sendMessage, createChannel, ...
    ...dbTools, // query, insert, update, ...
  },
  search: {
    topK: 5,
    minScore: 0.1,
  },
})

const agent = new Agent({
  id: 'dynamic-tools-agent',
  name: 'dynamic-tools-agent',
  instructions:
    'You are a helpful assistant with access to many tools. Use search_tools to find relevant tools, then load_tool to make them available.',
  model: '__GATEWAY_OPENAI_MODEL__',
  inputProcessors: [toolSearch],
})
```

Agent 的工作流程如下：

1. Agent 收到用戶訊息
1. Agent 使用關鍵詞呼叫 `search_tools`（例如“github issue”）
1. Agent 查看結果，並使用工具名稱呼叫 `load_tool`
1. 已載入的工具在下一輪可用
1. Agent 正常使用已載入的工具

## 透過 `autoLoad` 一步發現工具 {/* #single-step-discovery-with-autoload */}

將 `search.autoLoad` 設為 `true`，可跳過單獨的載入步驟。`search_tools` 傳回的工具會立即啟用，同時不再暴露 `load_tool` 元工具。每次發現工具可少用一輪模型呼叫，從而降低 Token 用量和延遲；不同 Provider 的行為一致。

```typescript
const toolSearch = new ToolSearchProcessor({
  tools: allTools,
  search: {
    topK: 3,
    autoLoad: true,
  },
})
```

啟用 `autoLoad` 後，流程變為：

1. Agent 收到用戶訊息
1. Agent 使用關鍵詞呼叫 `search_tools`
1. 匹配工具自動啟用，並在下一輪可用
1. Agent 正常使用該工具

每個匹配工具都會啟用，因此應將 `topK` 設得較小（例如 `3`），避免加入不需要的工具。新啟用的工具會追加在現有工具之後，使支援提示緩存的 Provider 能維持穩定的緩存前綴。

## 已載入工具的狀態儲存 {/* #loaded-tool-storage */}

`storage` 選項控制已載入工具集合的狀態存放位置。預設值為 `'in-memory'`；`'context'` 儲存需要主動啟用。

### `'in-memory'`（預設） {/* #in-memory-default */}

已載入的工具按線程保存在記憶體映射中，由 `ttl` 選項控制基於 TTL 的清理（預設一小時）。其行為如下：

- 無需設定 Memory。
- 進程重新啟動後狀態會丟失。
- 沒有線程 ID 的請求共享一個 `'default'` 條目。

使用 `clearState`、`clearAllState`、`getStateStats` 和 `cleanupNow` 檢查或重置此儲存。

### `'context'` {/* #context */}

載入狀態由對話訊息推導：只要訊息中仍有命名該工具的 `search_tools` 或 `load_tool` 結果，就認為該工具已載入。此模式具有以下特點：

- 無需設定 Memory。沒有 Memory 時，已載入工具只在當前進程保留，且請求必須具有真實線程 ID。匿名請求若要在多次呼叫之間保留已載入工具，呼叫者必須重新傳送相關訊息。
- 只要訊息再次可用，重新啟動後即可恢復：訊息可能來自具有訊息歷史的 Memory，也可能由呼叫者重新傳送。沒有 Memory 時，重新啟動只能恢復呼叫者所傳送訊息中的狀態。
- 一旦相應結果不再包含在訊息中，就會自動卸載工具。

```typescript
import { ToolSearchProcessor } from '@mastra/core/processors'

const toolSearch = new ToolSearchProcessor({
  tools: allTools,
  storage: 'context',
})
```

兩種模式都便於使用緩存：載入操作只會追加工具，因此支援提示緩存的 Provider 能保持穩定的緩存前綴。

卸載工具會改變傳送給模型的定義，使緩存前綴發生變化，下一輪需要寫入緩存，而無法命中已有緩存。在 `'in-memory'` 模式下，`ttl` 清理線程狀態時會發生這種情況；在 `'context'` 模式下，裁剪較早的訊息、移除工具發現結果時也會發生。此後模型必須重新搜尋該工具才能復用。這是預期的取捨：增加一次緩存寫入，以換取後續輪次更短的前綴。

## 與其他處理器配合 {/* #combining-with-other-processors */}

```typescript
import { Agent } from '@mastra/core/agent'
import { ToolSearchProcessor, TokenLimiter } from '@mastra/core/processors'

const agent = new Agent({
  id: 'my-agent',
  name: 'my-agent',
  model: '__GATEWAY_OPENAI_MODEL__',
  inputProcessors: [
    new ToolSearchProcessor({
      tools: allTools,
      search: { topK: 5 },
    }),
    // Place TokenLimiter last to ensure context fits
    new TokenLimiter(127000),
  ],
})
```
