# 動態 Workflow 定義

:::beta

在 API 穩定之前，即使未提升主要版本號，亦可能出現破壞性變更。

:::

動態 Workflow 定義是兼容 JSON 的 `DynamicWorkflowGraph`，可供 [`Mastra.addDynamicWorkflow()`](/reference/core/addDynamicWorkflow)、已儲存 Workflow 的伺服器路由及 Client SDK Workflow API 使用。

完整的設定及使用例子見[動態 Workflow](/docs/workflows/dynamic-workflows)。

## 定義欄位 {/* #definition-fields */}

|欄位 |類型 |必填|說明 |
| - | - | - | - |
|`id` | `string` |是 |唯一的 Workflow ID，亦用於擷取及執行該 Workflow。 |
| `description` | `string`|沒有 |人類可讀的描述 |
|`inputSchema` | `JsonSchema`|是的 |Workflow 輸入的 JSON Schema |
|`outputSchema` | `JsonSchema`|是的 |Workflow 輸出的 JSON Schema |
|`stateSchema` | `JsonSchema`|沒有 |共用 Workflow 狀態的 JSON Schema |
|`requestContextSchema` | `JsonSchema`|沒有 |從請求上下文讀取值的 JSON 架構 |
|`metadata` | `Record<string, unknown>`|沒有 |透過儲存保存任意 JSON 元資料 |
|`graph` | `SerializedStepFlowEntry[]`|是的 |組成 Workflow 的步驟項目 |

模式使用 JSON Schema 而不是 Zod，因此定義可以透過 JSON 往返。 Mastra 在註冊Workflow時將每個模式轉換為 Zod。

```json
{
  "id": "greeting-workflow",
  "description": "Returns a greeting for the supplied name",
  "inputSchema": {
    "type": "object",
    "properties": { "name": { "type": "string" } },
    "required": ["name"]
  },
  "outputSchema": {
    "type": "object",
    "properties": { "message": { "type": "string" } },
    "required": ["message"]
  },
  "graph": [
    {
      "type": "mapping",
      "id": "create-greeting",
      "mapConfig": "{\"message\":{\"template\":\"Hello, ${initData.name}!\"}}"
    }
  ]
}
```

## 圖表條目 {/* #graph-entries */}

`graph` 中的項目依次執行。每個項目接收上一項目的輸出，第一個項目則接收 Workflow 輸入。

|條目類型 |說明 |
| - | - |
|`agent` |調用已註冊的 Agent |
| `classifier` |使用已註冊的分類器評估資料 |
| `tool` |調用已註冊的 Tool |
| `mapping` |在步驟之間重組資料 |
| `workflow` |將已註冊的 Workflow 作為嵌套步驟調用 |
| `parallel` |並行執行多個步驟並合併其輸出 |
| `conditional` |並行執行所有述詞為真的分支 |
| `foreach` |針對陣列輸入中的每個項目執行一次步驟 |
| `loop` |在述詞成立期間或直到述詞成立，重複執行步驟 |
| `sleep` |暫停固定時間 |
| `sleepUntil` |暫停至指定日期 |

使用 [`.agent()`](/reference/workflows/workflow-methods/agent)、[`.classifier()`](/reference/workflows/workflow-methods/classifier) 及 [`.tool()`](/reference/workflows/workflow-methods/tool) 的程式碼定義 Workflow，在序列化後會產生相同的聲明式項目。

### 身份和顯示字段 {/* #identity-and-display-fields */}

控制流程條目接受可選欄位來標識和描述條目而不影響執行：

|欄位 |類型 |說明 |
| - | - | - |
|`id` | `string` |在編輯及序列化前後用於定位項目的穩定識別碼。對 `parallel`、`conditional`、`foreach` 及 `loop` 為選填；對 `mapping`、`sleep` 及 `sleepUntil` 為必填。 |
| `description` | `string` |易於閱讀的控制流程操作意圖說明 |
| `metadata` | `Record<string, unknown>` |儲存時保留的任意 JSON 元資料，例如視覺化編輯器中的顯示標題 |

```json
{
  "type": "parallel",
  "id": "independent-enrichment",
  "description": "Run independent document enrichment tasks concurrently",
  "metadata": { "title": "Independent enrichment" },
  "steps": [
    { "type": "tool", "id": "extract-entities", "toolId": "entity-tool" },
    { "type": "tool", "id": "classify", "toolId": "classify-tool" }
  ]
}
```

這三個欄位在儲存及重新載入後都會保留，並顯示於供 API 及 Studio 使用的 `serializedStepGraph`。Agent 及 Tool 步驟分別透過自身的 `description` 和 `options.metadata` 欄位提供同類資訊。

### Agent步驟 {/* #agent-steps */}

`agent` 項目透過 ID 調用已註冊的 Agent。Agent 步驟接受 `{ prompt: string }` 作為輸入，預設回傳 `{ text: string }`。

```json
{
  "type": "agent",
  "id": "summarize",
  "agentId": "support-agent"
}
```

`id` 識別此 Workflow 中的調用位置。無論 Agent 本身的 ID 為何，後續步驟都透過 `stepResults.summarize` 存取結果。

加入 `outputSchema`，要求 Agent 回傳結構化輸出：

```json
{
  "type": "agent",
  "id": "extract-subtopics",
  "agentId": "support-agent",
  "outputSchema": {
    "type": "array",
    "items": {
      "type": "object",
      "properties": { "title": { "type": "string" } },
      "required": ["title"]
    }
  }
}
```

在 Agent 之前使用 `mapping` 項目，根據 Workflow 資料建立其 `{ prompt }` 輸入。

Agent 項目接受 `options` 物件：

```json
{
  "type": "agent",
  "id": "summarize",
  "agentId": "support-agent",
  "options": { "retries": 2, "metadata": { "team": "support" } }
}
```

步驟說明來自已註冊的 Agent。重新載入 Workflow 時，Agent 項目上設定的 `description` 會被忽略。

只有 `retries` 及 `metadata` 會持久保存。儲存程式碼定義的 Workflow 時，值為函式的選項（例如 `onFinish` 及值為函式的 `toolChoice`）會遭到拒絕。其他 Agent 調用選項不會持久保存。

### 分類器步驟 {/* #classifier-steps */}

`classifier` 項目使用在 `Mastra` 實例上註冊的分類器評估 Workflow 資料。分類器必須在建立時設定問題。

```json
{
  "type": "classifier",
  "id": "classify-ticket",
  "classifierId": "ticket-router",
  "options": {
    "maxRetries": 2,
    "retries": 1,
    "metadata": { "team": "support" }
  }
}
```

分類器會評估項目的完整輸入。如需選取或重組輸入，請在前面加入 `mapping` 項目。

分類器輸出有兩條穩定路徑：

* `answers.<question>` 包含具型別的答案。按問題類型，根據其 `choice`、`score` 或 `probability` 欄位進行路由。選項及評分答案可能包含分布資料。遭拒絕的問題會回傳 `{ "type": "refusal" }`，其中沒有 `choice`、`score` 或 `probability`，因此不會符合針對這些欄位的條件。若要明確處理拒絕情況，請將 `answers.<question>.type` 與 `"refusal"` 比較。
* `usage` 包含標準化的 token 使用量。

使用現有的 `conditional` 項目，根據分類器輸出進行路由。例如，後續條件可將 `{ "path": "stepResults.classify-ticket.answers.route.choice" }` 與 `{ "literal": "billing" }` 比較。

`options` 物件可包含分類器模型調用的 `maxRetries`、可安全序列化為 JSON 的 `providerOptions`、Workflow 步驟的 `retries`，以及 `metadata`。分類器發生錯誤會令該 Workflow 步驟失敗。

### Tool步驟 {/* #tool-steps */}

`tool` 項目透過 `Mastra` 的 `tools` 物件中的註冊鍵調用 Tool。Mastra 註冊 Workflow 時，會從註冊表解析該 Tool 的輸入及輸出 Schema。

```json
{
  "type": "tool",
  "id": "lookup",
  "toolId": "lookup-customer"
}
```

Tool 項目與 Agent 項目一樣，接受選填的 `description` 及 `options` 欄位。只有 `retries` 及 `metadata` 會持久保存。

### 繪圖步驟 {/* #mapping-steps */}

`mapping` 項目用於重組資料。其 `mapConfig` 是將物件編碼後的 JSON 字串。物件中的每個鍵都會成為步驟輸出的鍵，而每個描述符指定一個資料來源。

直接呼叫 [`Mastra.addDynamicWorkflow()`](/reference/core/addDynamicWorkflow) 時，`mapConfig` 亦可接收物件本身。Mastra 會在註冊及儲存定義前將其編碼為 JSON 字串，因此兩種寫法的儲存結果相同。已儲存的定義一律使用 JSON 字串形式。

|描述符|描述 |
| - | - |
|`{ "value": ... }` |固定的 JSON 值 |
| `{ "template": "..." }` |由 `${...}` 佔位符組成的字串 |
| `{ "initData": true, "path": "a.b" }` |來自 Workflow 輸入的值 |
| `{ "step": "step-id", "path": "a.b" }` |來自前一步驟輸出的值 |
| `{ "requestContextPath": "a.b" }` |來自請求上下文的值 |

`step` 資料來源亦接受由步驟 ID 組成的陣列：

```json
{ "step": ["escalate", "auto-reply"], "path": "text" }
```

陣列中第一個具有非空結果的步驟會提供該值。這可選取在 `conditional` 項目之後實際執行的分支。

範本會根據 `initData`、`inputData`、`state`、`requestContext` 及 `stepResults.<step-id>` 解析佔位符：

```json
{
  "type": "mapping",
  "id": "build-prompt",
  "mapConfig": "{\"prompt\":{\"template\":\"Summarize this request: ${initData.request}\"}}"
}
```

範本解析出的物件及陣列會轉換為 JSON 字串。已存在結果中的 `null` 值會呈現為空字串。如果範本參照沒有成功輸出的步驟，該次執行就會失敗。

`mapping` 項目必須位於圖的最上層，不能放在 `parallel`、`conditional`、`foreach` 或 `loop` 容器內。

### 嵌套 Workflow 步驟 {/* #nested-workflow-steps */}

`workflow` 項目會調用另一個已註冊的 Workflow。目標 Workflow 可以由程式碼定義，亦可以是已儲存的定義。

```json
{
  "type": "workflow",
  "id": "lookup-first",
  "workflowId": "lookup-customer-workflow"
}
```

`id` 識別調用位置。同一個嵌套 Workflow 可以使用不同的調用位置 ID 多次出現，後續步驟可透過 `stepResults.<id>` 存取各次調用的結果。`workflow` 項目亦接受選填的 `description`。

### 平行條目 {/* #parallel-entries */}

`parallel` 項目會並行執行多個獨立步驟，並將輸出合併為以步驟 ID 為鍵的物件。

```json
{
  "type": "parallel",
  "steps": [
    { "type": "tool", "id": "first", "toolId": "lookup-customer" },
    { "type": "tool", "id": "second", "toolId": "lookup-customer" }
  ]
}
```

每個子項目都必須是 `agent`、`classifier`、`tool` 或 `workflow` 項目。所有子項目都會直接接收平行項目的輸入。

### 有條件條目 {/* #conditional-entries */}

`conditional` 項目會為每個步驟配對一個聲明式述詞，並執行所有述詞為真的分支。

```json
{
  "type": "conditional",
  "steps": [
    { "type": "agent", "id": "escalate", "agentId": "support-agent" },
    { "type": "agent", "id": "auto-reply", "agentId": "support-agent" }
  ],
  "predicates": [
    { "op": "eq", "left": { "path": "inputData.priority" }, "right": { "literal": "urgent" } },
    { "op": "ne", "left": { "path": "inputData.priority" }, "right": { "literal": "urgent" } }
  ]
}
```

每個子項目都必須是 `agent`、`classifier`、`tool` 或 `workflow` 項目，且各自需要一個述詞。所有子項目都會直接接收條件項目的輸入。

### 謂詞 {/* #predicates */}

條件項目及循環使用 JSON 述詞 DSL。運算元可以是 `{ "path": "..." }` 參照或 `{ "literal": ... }` 值。路徑會根據 `initData`、`inputData`、`stepResults` 及 `state` 解析。

|運算子|格式|
| - | - |
|`eq`, `ne`, `lt`, `lte`, `gt`, `gte` | `{ "op": "eq", "left": ..., "right": ... }` |
| `in`, `notIn` | `{ "op": "in", "value": ..., "set": [...] }` |
| `exists`, `notExists` | `{ "op": "exists", "path": "..." }` |
| `truthy`, `falsy` | `{ "op": "truthy", "value": ... }` |
| `and`, `or` | `{ "op": "and", "args": [...] }` |
| `not` | `{ "op": "not", "arg": ... }` |

路徑不存在時不會擲出例外。無法解析路徑時，依賴路徑的運算子會回傳 `false`。使用 `exists` 或 `notExists` 區分缺少的值與假值。

### Foreach 條目 {/* #foreach-entries */}

`foreach` 項目會針對陣列輸入中的每個項目執行一次內部步驟。前一個項目必須輸出原始陣列。結果會保持輸入順序，並行數預設為 `1`。

```json
{
  "type": "foreach",
  "step": { "type": "workflow", "id": "write-blurb", "workflowId": "blurb-workflow" },
  "opts": { "concurrency": 3 }
}
```

內部步驟可以是 `agent`、`tool` 或 `workflow` 項目，但不能是 `mapping` 項目。

### 循環條目 {/* #loop-entries */}

`loop` 項目會在述詞成立期間（`dowhile`）或直到述詞成立（`dountil`），重複執行一個步驟。

```json
{
  "type": "loop",
  "loopType": "dountil",
  "step": { "type": "tool", "id": "poll", "toolId": "check-status" },
  "predicate": {
    "op": "eq",
    "left": { "path": "inputData.status" },
    "right": { "literal": "done" }
  }
}
```

循環體必須是單步，並且儲存循環需要聲明性謂詞。

### 睡眠條目 {/* #sleep-entries */}

`sleep` 項目會暫停固定毫秒數。`sleepUntil` 項目會暫停至由 ISO 日期字串表示的指定日期。已儲存的定義必須使用字面值。

```json
{ "type": "sleep", "id": "wait", "duration": 5000 }
```

```json
{ "type": "sleepUntil", "id": "wait-for-launch", "date": "2027-01-01T00:00:00.000Z" }
```

當必須在執行時間計算持續時間或日期時，請使用程式碼定義的Workflow。

## 驗證 {/* #validation */}

Mastra 在保留或註冊定義之前驗證定義：

* 結構：條目形狀和必填字段，包括放置規則，例如僅頂級映射。
* 參照：每個 `agentId` 及 `workflowId` 都必須能在目前的註冊表或同一組定義中解析。`toolId` 必須與 Tool 的註冊鍵相符。
* 模式流：每個條目的輸入必須與前面的輸出相容，包括推斷的映射輸出。

驗證錯誤會包含以點分隔的路徑，例如 `graph.2.steps.0`，用來指出無效項目。
