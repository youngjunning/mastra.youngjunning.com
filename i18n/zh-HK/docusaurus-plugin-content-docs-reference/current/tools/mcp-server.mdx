# MCPServer

`MCPServer` 類別讓現有的 Mastra Tool 和 Agent 可透過模型上下文協議（MCP）伺服器對外提供。任何 MCP 客戶端，例如 Cursor、Windsurf 或 Claude Desktop，都可連接伺服器，讓 Agent 使用這些功能。

如果只需在 Mastra 應用程式內直接使用 Tool 或 Agent，可以省卻建立 MCP 伺服器的步驟。這個 API 專門用來向*外部* MCP 客戶端提供 Mastra Tool 和 Agent。

如要直接公開 Mastra 應用程式內的所有 Agent、Workflow 和 Tool，可使用 `/api/mcp` 的[內置 MCP 伺服器](/docs/server/mcp)。伺服器會按呼叫方建立 Tool 清單，每次呼叫都會經過相應 HTTP 路由的身份驗證及權限檢查。如要發佈指定的 Tool 和 Agent，並加入自訂提示和資源，或透過 stdio 提供服務，請使用 `MCPServer`。

`MCPServer` 支援 MCP `2026-07-28` 版本的[兩種傳輸方式：stdio（子程序）及 Streamable HTTP](https://modelcontextprotocol.io/docs/concepts/transports)。

:::note
如要從 `@mastra/mcp` 1.x 升級，請參閱[遷移指南](/reference/migrations/mcp-v2)。
:::

## 構造函數 {/* #constructor */}

建立 `MCPServer` 時，需要提供伺服器的基本資料和它會提供的 Tool，亦可指定要以 Tool 形式公開的 Agent。

```typescript
import { Agent } from '@mastra/core/agent'
import { createTool } from '@mastra/core/tools'
import { MCPServer } from '@mastra/mcp'
import { z } from 'zod'
import { dataProcessingWorkflow } from '../workflows/dataProcessingWorkflow'

const myAgent = new Agent({
  id: 'my-example-agent',
  name: 'MyExampleAgent',
  description: 'A generalist to help with basic questions.',
  instructions: 'You are a helpful assistant.',
  model: '__GATEWAY_OPENAI_MODEL__',
})

const weatherTool = createTool({
  id: 'getWeather',
  description: 'Gets the current weather for a location.',
  inputSchema: z.object({ location: z.string() }),
  execute: async inputData => `Weather in ${inputData.location} is sunny.`,
})

const server = new MCPServer({
  id: 'my-custom-server',
  name: 'My Custom Server',
  version: '1.0.0',
  description: 'A server that provides weather data and agent capabilities',
  instructions:
    'Use the available tools to help users with weather information and data processing tasks.',
  tools: { weatherTool },
  agents: { myAgent }, // this agent will become tool "ask_myAgent"
  workflows: {
    dataProcessingWorkflow, // this workflow will become tool "run_dataProcessingWorkflow"
  },
})
```

## Tool 的結構描述與結構化結果 {/* #tool-schemas-and-structured-results */}

MCP Tool 的輸入及輸出結構描述以 JSON Schema 2020-12 格式公布，並在 `$schema` 內聲明所用的方言。Mastra Tool 對外公布的結構描述會保留受支援的引用、組合關鍵字和元組結構（`prefixItems`）。

定義了 `outputSchema` 的 Tool 可以回傳任何 JSON 值，包括物件、陣列、字串、數值、布林值或 `null`。伺服器直接將該值作為 `structuredContent` 傳送，毋須包在另一個物件內。呼叫成功時，伺服器會按 Tool 的輸出結構描述驗證結構化輸出，再回傳結果。

## Tool 結果 {/* #tool-results */}

伺服器預設會將 Tool 的輸出以一個文字區塊傳送給 MCP 客戶端。字串照原樣傳送，其他值以 JSON 格式傳送。若 Tool 定義了 `outputSchema`，伺服器亦會以 `structuredContent` 回傳該值。

可透過 `toolResult` 選項傳送 Tool 原本提供給模型的輸出，或在傳送前改寫結果。

```typescript title="src/mastra/mcp/server.ts"
import { MCPServer } from '@mastra/mcp'
import { screenshotTool } from '../tools/screenshot'

const server = new MCPServer({
  id: 'media-server',
  name: 'Media Server',
  version: '1.0.0',
  tools: { screenshotTool },
  toolResult: {
    modelOutput: true,
  },
})
```

:::warning

`@mastra/mcp` 的下一個主要版本會把 `modelOutput` 的預設值改為 `true`。若 MCP 客戶端會解析已定義 `toModelOutput` 的 Tool 所回傳的原始 JSON 文字，請現在設定 `modelOutput: false`，以維持現有行為。

:::

設定 `modelOutput: true` 後，伺服器會按下表將 `toModelOutput` 的值映射成 MCP 內容：

| `toModelOutput` 的值 | MCP 結果 |
| - | - |
| `{ type: 'text', value }` | 文字區塊 |
| `{ type: 'json', value }` | 包含 JSON 值的文字區塊 |
| `{ type: 'error-text' }` 或 `{ type: 'error-json' }` | 帶有 `isError: true` 的文字區塊 |
| `content` 中的 `text` 部分 | 文字區塊 |
| `content` 中的 `media`、`image-data` 或 `file-data` 部分 | `image/*` 對應 `image` 區塊，`audio/*` 對應 `audio` 區塊，其餘類型則對應包含 `blob` 的嵌入式 `resource` |
| `content` 中附有 `data:` URI 的 `image-url` 或 `file-url` 部分 | 採用與媒體資料相同的處理方式 |
| `content` 中附有遠端網址的 `image-url` 或 `file-url` 部分 | 包含該網址的文字區塊 |

若 Tool 定義了 `outputSchema`，結果會保留 `structuredContent`，並先放置其 JSON 文字區塊，再附上經映射的區塊。如果 `toModelOutput` 或 `transform` 拋出例外，客戶端會收到 Tool 的錯誤結果。

可使用 `transform` 轉發已符合 MCP 格式的結果，例如經 `MCPClient` 代理的 Tool 回傳的結果：

```typescript title="src/mastra/mcp/proxy-server.ts"
import { MCPClient, MCPServer, type MCPServerToolResultContext } from '@mastra/mcp'

const upstream = new MCPClient({
  servers: { files: { url: new URL('https://files.example.com/mcp') } },
})

const server = new MCPServer({
  id: 'proxy-server',
  name: 'Proxy Server',
  version: '1.0.0',
  tools: await upstream.listTools(),
  toolResult: {
    // Unstructured upstream tools return the upstream MCP result as their output
    transform: ({ output }) => {
      const upstreamResult = output as MCPServerToolResultContext['result']
      return Array.isArray(upstreamResult?.content) ? upstreamResult : undefined
    },
  },
})
```

## 以 Tool 形式公開 Agent {/* #exposing-agents-as-tools */}

在配置的 `agents` 屬性內提供 Mastra Agent 後，`MCPServer` 會自動以可呼叫的 Tool 形式公開它們。

* **Tool 命名**。每個 Agent 都會轉成名為 `ask_<agentKey>` 的 Tool，當中 `<agentKey>` 是該 Agent 在 `agents` 物件內所用的鍵。例如，配置 `agents: { myAgentKey: myAgentInstance }` 後便會建立名為 `ask_myAgentKey` 的 Tool。

* **Tool 的行為**
  * **描述**採用「向 Agent `<AgentName>` 提問。Agent 的原有指令：`<agent description>`」的格式。
  * **輸入**為單一物件參數，當中 `message` 屬性是字串，例如 `{ message: "Your question for the agent" }`。
  * **執行**時，Tool 會以傳入的 `query` 呼叫相應 Agent 的 `generate()` 方法。
  * **輸出**直接採用 Agent 的 `generate()` 方法回傳的結果。

* **名稱衝突**。若 `tools` 配置內明確定義的 Tool 與 Agent 衍生的 Tool 同名，例如同時有名為 `ask_myAgentKey` 的 Tool 及鍵為 `myAgentKey` 的 Agent，便會*優先採用明確定義的 Tool*。伺服器會略過該 Agent 的轉換，並記錄警告。

MCP 客戶端可像呼叫其他 Tool 一樣，以自然語言查詢來與 Agent 互動。

### 將 Agent 轉成 Tool {/* #agent-to-tool-conversion */}

在配置的 `agents` 屬性內提供 Agent 後，`MCPServer` 會為每個 Agent 自動建立相應的 Tool。Tool 的名稱為 `ask_<agentIdentifier>`，當中 `<agentIdentifier>` 是 `agents` 物件內所用的鍵。

產生的 Tool 描述採用「向 Agent `<agent.name>` 提問。Agent 描述：`<agent.description>`」的格式。

要將 Agent 轉成 Tool，建立 Agent 實例時**必須**在配置內提供非空的 `description` 字串，例如 `new Agent({ id: 'my-agent', name: 'myAgent', description: 'This agent does X.', ... })`。如果傳給 `MCPServer` 的 Agent 沒有提供 `description`，或該字串為空，建立 `MCPServer` 實例時便會拋出錯誤，伺服器亦無法完成設定。

客戶端可透過 MCP 使用 Agent 的生成能力，直接向 Agent 提問。

### 在 Tool 內存取 MCP 上下文 {/* #accessing-mcp-context-in-tools */}

透過 `MCPServer` 公開的 Tool 會從 `context.mcp` 取得目前請求的協議上下文：

| 成員 | 說明 |
| - | - |
| `context.mcp.extra.signal` | 客戶端取消請求或中斷連接時觸發中止訊號 |
| `context.mcp.extra.requestId` | 請求的 JSON-RPC ID |
| `context.mcp.extra.authInfo` | 傳輸層驗證得出的身份資料，詳見身份驗證上下文一節 |
| `context.mcp.extra._meta` | 請求的元數據，包括追蹤標頭、客戶端選擇接收的日誌級別和進度權杖 |
| `context.mcp.log()` | 向發出呼叫的客戶端傳送日誌訊息，詳見日誌記錄一節 |
| `context.mcp.progress()` | 向發出呼叫的客戶端匯報進度，詳見進度通知一節 |
| `context.mcp.protocolVersion` | `'2026-07-28'` |

同一請求亦會將 `authInfo`、`mapAuthInfoToUser` 回傳的 `user`，以及客戶端送來的 W3C `traceContext` 寫入受信任的應用程式上下文 `context.requestContext`。當 MCP 客戶端透過 `ask_<agent>` 向 Agent 提問時，請求上下文會轉交給 Agent，而 Agent 呼叫的 Tool 不會收到 `context.mcp`。若 Tool 同時支援客戶端直接呼叫和經 Agent 呼叫，可按下例從請求上下文讀取身份驗證資料：

```typescript
const authInfo = context.mcp?.extra.authInfo ?? context.requestContext?.get('authInfo')
```

#### 示例：在 Tool 內識別呼叫方並使用獨立憑證 {/* #example-tool-that-uses-caller-identity-with-a-separate-credential */}

```typescript
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

import { apiCredentials } from '../lib/api-credentials'

const fetchUserData = createTool({
  id: 'fetchUserData',
  description: 'Fetches data for the authenticated MCP caller',
  inputSchema: z.object({
    resourceId: z.string().describe('The ID of the record to fetch'),
  }),
  execute: async (inputData, context) => {
    const authInfo = context.mcp?.extra.authInfo ?? context.requestContext?.get('authInfo')
    const user = authInfo?.extra?.user as { id?: string } | undefined

    if (!user?.id) {
      throw new Error('Authentication required')
    }

    // Resolve the owner from trusted context, not from model input
    const credential = await apiCredentials.getForUser(user.id)

    const response = await fetch(
      `https://api.example.com/users/${encodeURIComponent(user.id)}/records/${encodeURIComponent(inputData.resourceId)}`,
      {
        headers: {
          Authorization: `Bearer ${credential.token}`,
        },
        signal: context.mcp?.extra.signal,
      },
    )

    return response.json()
  },
})
```

使用 `authInfo` 識別呼叫者，再為 Tool 要呼叫的服務選用適當的認證憑證。模型提供 `resourceId` 等業務輸入，憑證則由可信的程式碼選定。MCP 存取權杖只供你的 MCP 伺服器使用，不可轉發至其他 API。詳見[安全存取上游服務](/docs/guides/mcp-authentication-authorization#access-upstream-services-safely)。

#### `authInfo` 從何而來 {/* #where-authinfo-comes-from */}

若 MCP 伺服器由 Mastra 伺服器託管，系統會以 `server.auth` 識別的身分主體填寫 `extra.authInfo`，毋須額外設定：

```typescript
export const mastra = new Mastra({
  mcpServers: { myServer },
  server: {
    auth: new MastraJwtAuth({ secret: process.env.JWT_SECRET! }),
  },
})
```

通過身分驗證的用戶會按以下規則對應至 `authInfo`：

| `authInfo` 欄位 | 值 |
| - | - |
| `token` | 請求使用的持有者權杖或會話 Cookie 的值 |
| `clientId` | 按 `user.id`、`user.sub`、`user.userId`、`user.email` 的次序取首個存在的值 |
| `scopes` | 將 `user.scopes`、`user.scope` 或 `user.permissions` 統一轉為陣列 |
| `extra.user` | 身分驗證 Provider 傳回的完整用戶物件 |

如果由你自己的中介軟件執行驗證，可設定 `server.mcpOptions.setRequestAuth` 來建立 `authInfo`。這個掛鈎會取代預設的對應規則：

```typescript
export const mastra = new Mastra({
  mcpServers: { myServer },
  server: {
    middleware: [verifyBearerToken], // stores the payload on the request context
    mcpOptions: {
      setRequestAuth: (req, requestContext) => {
        const payload = requestContext.get('bearerPayload')
        req.auth = {
          token: payload.token,
          clientId: payload.sub,
          scopes: payload.scope.split(' '),
        }
      },
    },
  },
})
```

如果掛鈎未設定 `req.auth`，該請求便完全不會帶有身分驗證資料。

## 要求呼叫者提供資料 {/* #asking-the-caller-for-input */}

如果 Tool 需要用戶提供更多資料才能完成呼叫，它會如同在 Agent 或 Workflow 內一樣，呼叫 `context.suspend(payload)` 後返回。伺服器以 `input_required` 結果結束請求，並附上由 Tool 的 `resumeSchema` 定義的表格。客戶端回覆後，伺服器會再次執行 Tool，把回覆放入 `context.resumeData`，並把暫停時的承載資料放入 `context.suspendPayload`。每一輪都是獨立請求，伺服器不會重播之前的輪次。請將下一輪所需的狀態放入承載資料，並按該狀態選擇執行分支。

```typescript
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

export const bookDelivery = createTool({
  id: 'bookDelivery',
  description: 'Books a delivery for an order after confirming the address.',
  inputSchema: z.object({ orderId: z.string() }),
  outputSchema: z.object({ confirmed: z.boolean() }),
  suspendSchema: z.object({ phase: z.literal('address'), message: z.string() }),
  resumeSchema: z.object({ address: z.string() }),
  execute: async ({ orderId }, context) => {
    if (!context.resumeData) {
      await context.suspend?.({ phase: 'address', message: 'Delivery address?' })
      return
    }
    await book(orderId, context.resumeData.address)
    return { confirmed: true }
  },
})
```

伺服器會按 `resumeSchema` 產生供呼叫者填寫的表格，因此它必須描述沒有巢狀結構的物件，欄位只支援字串、數字、布林值及列舉。呼叫者拒絕填寫或取消表格時，呼叫會以錯誤結束，Tool 不會再次執行。Tool 可透過更改承載資料中的階段，多次暫停執行。

### 恢復狀態 {/* #continuation-state */}

恢復呼叫所需的狀態以不透明的 `requestState` 字串傳送，客戶端會在回覆時原樣傳回。伺服器以 `requestState.key` 簽署該狀態，並在執行處理函數前，拒絕遭竄改、已過期或屬於其他 Tool、參數或呼叫者的狀態。伺服器優先以授權層提供的權杖主體識別呼叫者，其次是 `mapAuthInfoToUser` 傳回的用戶 `id`，最後才用持有者權杖本身。因此，使用同一個 OAuth 客戶端的兩個用戶無法恢復對方暫停的呼叫。

如果伺服器沒有啟用授權，所有呼叫者都會共用一個匿名主體。在 `ttlSeconds` 指定的期限內，`requestState` 相當於持有者憑證，任何取得它的人都可回覆這一輪請求。若 Tool 恢復後可進行寫入、購買或更改帳戶等操作，請加上授權保護。

承載資料會經過簽署，但不會加密。請控制資料大小，只放入 ID、階段等非機密資料。從環境設定提供 `requestState.key`，讓可能處理恢復請求的所有實例共用密鑰。若未設定，伺服器會為每個程序各自產生密鑰，呼叫只能由原有程序恢復。

```typescript
const server = new MCPServer({
  id: 'booking',
  name: 'Booking',
  version: '1.0.0',
  tools: { bookDelivery },
  requestState: { key: process.env.MCP_REQUEST_STATE_KEY!, ttlSeconds: 600 },
})
```

資源及提示的回呼亦可用同樣方式暫停。詳見[資源處理](#resource-handling)及[提示處理](#prompt-handling)。

### `startHTTP()` {/* #starthttp */}

用此方法將 MCP 伺服器整合至現有的網頁伺服器，透過 Streamable HTTP 通訊。網頁伺服器收到 HTTP 請求時，可在請求處理函數內呼叫此方法。

```typescript oxfmt:false
async startHTTP({
  url,
  httpPath,
  req,
  res,
  options,
}: {
  url: URL;
  httpPath: string;
  req: http.IncomingMessage;
  res: http.ServerResponse<http.IncomingMessage>;
  options?: MCPServerHTTPRequestOptions;
}): Promise<void>
```

每個請求獨立處理，毋須建立或恢復會話，因此 `options` 只用於設定請求檢查。

| 選項 | 行為 |
| - | - |
| `enableDnsRebindingProtection` | 設為 `true` 時，伺服器會在處理請求前，按 `allowedHosts` 和 `allowedOrigins` 分別檢查 `Host` 和 `Origin` 標頭。對應的清單有項目時才會檢查。請求遭拒時會收到 `403` JSON-RPC 錯誤。 |
| `allowedHosts` | `Host` 標頭接受的主機名稱。比對不計連接埠，所以清單內的 `localhost:3000` 會容許 `localhost` 上的任何連接埠。IPv6 位址須加方括號，例如 `[::1]`。 |
| `allowedOrigins` | `Origin` 標頭接受的來源。由於只比對主機名稱，`https://app.example.com:8443` 會容許 `app.example.com` 上的任何協定及連接埠。沒有 `Origin` 標頭的請求也可通過，因為非瀏覽器的 MCP 客戶端不會發送這個標頭。 |

毋須檢查請求時，可省略 `options`。

以下示例在 HTTP 伺服器的請求處理函數內呼叫 `startHTTP`。MCP 客戶端可經 `http://localhost:1234/mcp` 連接到該 MCP 伺服器：

```typescript
import http from 'http'

const httpServer = http.createServer(async (req, res) => {
  await server.startHTTP({
    url: new URL(req.url || '', 'http://localhost:1234'),
    httpPath: `/mcp`,
    req,
    res,
  })
})

httpServer.listen(PORT, () => {
  console.log(`HTTP server listening on port ${PORT}`)
})
```

每個請求均獨立處理，呼叫之間毋須保留狀態，因此 `startHTTP` 可在無伺服器環境運行，例如 Supabase Edge Functions、Cloudflare Workers、Vercel Edge、AWS Lambda 和 Deno Deploy。此方法接受 Node 風格的 `http.IncomingMessage` 及 `http.ServerResponse` 物件，因此以 Fetch 為基礎的執行環境須用 `fetch-to-node` 等轉接器轉換 `Request`，並將結果轉回 `Response`：

```typescript
// Supabase Edge Function example
import { serve } from 'https://deno.land/std@0.168.0/http/server.ts'
import { MCPServer } from '@mastra/mcp'
// Note: You will need to convert req/res format from Deno to Node
import { toReqRes, toFetchResponse } from 'fetch-to-node'

const server = new MCPServer({
  id: 'my-serverless-mcp',
  name: 'My Serverless MCP',
  version: '1.0.0',
  tools: {/* your tools */},
})

serve(async req => {
  const url = new URL(req.url)

  if (url.pathname === '/mcp') {
    // Convert Deno Request to Node.js-compatible format
    const { req: nodeReq, res: nodeRes } = toReqRes(req)

    await server.startHTTP({ url, httpPath: '/mcp', req: nodeReq, res: nodeRes })

    return toFetchResponse(nodeRes)
  }

  return new Response('Not found', { status: 404 })
})
```

`input_required` 各輪請求、進度及每個請求的日誌，都會經觸發它們的請求以串流方式傳送。不受請求生命週期限制的通知（`resources.notifyUpdated()`、`prompts.notifyListChanged()`、`toolActions.notifyListChanged()`）則經客戶端保持開啟的 `subscriptions/listen` 串流送出。只有仍有運行中的實例為該串流提供服務時，客戶端才會收到通知。

## 資源處理 {/* #resource-handling */}

### 什麼是 MCP 資源？ {/* #what-are-mcp-resources */}

MCP 資源會公開伺服器資料。客戶端可讀取這些資料，作為與 LLM 互動時的上下文。例如：

* 文件內容
* 資料庫記錄
* API 回應
* 即時系統資料
* 屏幕截圖及圖像
* 日誌檔案

每項資源以獨有的 URI 識別，例如 `file:///home/user/documents/report.pdf` 或 `postgres://database/customers/schema`。資源可載有 UTF-8 編碼的文字或 Base64 編碼的二進制資料。

客戶端可用以下方式找出資源：

1. **直接資源**：伺服器透過 `resources/list` 端點公開個別資源的清單。
2. **資源模板**：資源若在執行時才定義，伺服器可公開 URI 模板（RFC 6570），供客戶端組成資源的 URI。

要讀取資源，客戶端須發送附有資源 URI 的 `resources/read` 請求。伺服器亦可通知客戶端資源清單有變（`notifications/resources/list_changed`）。如果客戶端正在監聽某項資源，伺服器也可通知它該資源的內容已更新（`notifications/resources/updated`）。

詳情請參閱 [MCP 官方資源文件](https://modelcontextprotocol.io/docs/concepts/resources)。

### `MCPServerResources` 類型 {/* #mcpserverresources-type */}

`resources` 選項接受 `MCPServerResources` 類型的物件。這個類型定義伺服器處理資源請求時使用的回呼：

```typescript
export type MCPServerResources = {
  // Callback to list available resources
  listResources: (params: {
    extra: MCPRequestHandlerExtra
    requestContext: RequestContext
  }) => Promise<Resource[]>

  // Callback to get the content of a specific resource
  getResourceContent: (
    params: { uri: string } & MCPServerRequest,
  ) => Promise<MCPServerResourceContent | MCPServerResourceContent[] | void>

  // Optional callback to list available resource templates
  resourceTemplates?: (params: {
    extra: MCPRequestHandlerExtra
    requestContext: RequestContext
  }) => Promise<ResourceTemplate[]>

  // Shape of the answer a suspended getResourceContent expects
  resumeSchema?: StandardSchemaWithJSON
}

export type MCPServerResourceContent = { text?: string } | { blob?: string }
```

每個回調都會收到 `extra` 和 `requestContext`。`extra` 是 Tool 透過 `context.mcp.extra` 取得的同一份協議上下文，當中包括用於取消操作的 `signal`，以及 `requestId`、`authInfo` 和 `_meta`。`requestContext` 是可信的應用程式上下文，載有 `authInfo` 和經 `mapAuthInfoToUser` 配對的用戶。你可以憑這些資料限制調用方可列出及讀取的資源。

處理 `resources/read` 請求時，伺服器會先在 `listResources` 回傳的清單中比對 URI。如清單沒有相符的資源，伺服器便會按調用方的 `resourceTemplates` 比對，並將展開後的 URI 傳給 `getResourceContent`。URI 可以省略 `{?format}` 或 `{/section}` 等可選表達式。變數值必須按照 RFC 6570 的展開規則作百分號編碼，因此 `file://data?format=a/b` 無法配對 `file://data{?format}`。回應採用相符資源或範本的 `mimeType` 和 `_meta`。如果找不到相符的資源或範本，請求便會以 `Resource not found` 失敗。

`getResourceContent` 亦會收到 `MCPServerRequest` 的 `suspend`、`resumeData` 和 `suspendPayload` 成員。宣告 `resumeSchema` 後即可使用 `suspend`，用法與 Tool 完全相同。

例子：

```typescript
import { MCPServer } from '@mastra/mcp'
import type {
  MCPServerResourceContent,
  MCPServerResources,
  Resource,
  ResourceTemplate,
} from '@mastra/mcp'

// Resources/resource templates will generally be dynamically fetched.
const myResources: Resource[] = [
  { uri: 'file://data/readme', name: 'Readme', mimeType: 'text/plain' },
]

const myResourceContents: Record<string, MCPServerResourceContent> = {
  'file://data/readme': { text: 'Read this first.' },
  // Not listed; readable as an expansion of the `file://data/{id}` template
  'file://data/123': { text: 'This is the content of data file 123.' },
}

const myResourceTemplates: ResourceTemplate[] = [
  {
    uriTemplate: 'file://data/{id}',
    name: 'Data File',
    description: 'A file containing data.',
    mimeType: 'text/plain',
  },
]

const myResourceHandlers: MCPServerResources = {
  listResources: async () => myResources,
  getResourceContent: async ({ uri, extra }) => {
    if (myResourceContents[uri]) {
      return myResourceContents[uri]
    }
    throw new Error(`Resource content not found for ${uri}`)
  },
  resourceTemplates: async () => myResourceTemplates,
}

const serverWithResources = new MCPServer({
  id: 'resourceful-server',
  name: 'Resourceful Server',
  version: '1.0.0',
  tools: {/* ... your tools ... */},
  resources: myResourceHandlers,
})
```

### 向客戶端發送資源變更通知 {/* #notifying-clients-of-resource-changes */}

可用資源或其內容有變時，伺服器可以通知正在監聽相關資源的客戶端。

#### `server.resources.notifyUpdated({ uri: string })` {/* #serverresourcesnotifyupdated-uri-string- */}

當 `uri` 所識別的資源內容更新時，請調用此方法。訂閱該 URI 的客戶端會在各自的 `subscriptions/listen` 串流收到 `notifications/resources/updated` 訊息。

```typescript oxfmt:false
async server.resources.notifyUpdated({ uri: string }): Promise<void>
```

例子：

```typescript
// After updating the content of 'file://data.txt'

```

如果可用資源清單有變，例如新增或移除資源，請調用此方法。正在監聽的客戶端會收到 `notifications/resources/list_changed` 訊息，並重新取得資源清單。



## 處理提示詞 {/* #prompt-handling */}

### 甚麼是 MCP 提示詞？ {/* #what-are-mcp-prompts */}

提示詞是 MCP 伺服器向客戶端提供的可重用範本或 Workflow。它們可接收參數，亦可包含資源的上下文，讓客戶端以統一方式與大型語言模型互動。

每個提示詞以唯一名稱識別，可以靜態定義，也可以在執行時定義。

### `MCPServerPrompts` 類型 {/* #mcpserverprompts-type */}

`prompts` 選項接受 `MCPServerPrompts` 類型的物件。此類型定義伺服器處理提示詞請求時使用的回調。

```typescript
export type MCPServerPrompts = {
  // Callback to list available prompts
  listPrompts: (params: {
    extra: MCPRequestHandlerExtra
    requestContext: RequestContext
  }) => Promise<Prompt[]>

  // Callback to get the messages for a specific prompt
  getPromptMessages?: (
    params: { name: string; args?: Record<string, unknown> } & MCPServerRequest,
  ) => Promise<PromptMessage[] | void>

  // Shape of the answer a suspended getPromptMessages expects
  resumeSchema?: StandardSchemaWithJSON
}
```

提示詞回調會收到與資源回調相同的 `extra` 和 `requestContext`。宣告 `resumeSchema` 後，`getPromptMessages` 亦可用相同方式調用 `suspend`。伺服器會先驗證提示詞的必填參數，再調用 `getPromptMessages`。

例子：

```typescript
import { MCPServer } from '@mastra/mcp'
import type { Prompt, PromptMessage, MCPServerPrompts } from '@mastra/mcp'

const prompts: Prompt[] = [
  {
    name: 'analyze-code',
    description: 'Analyze code for improvements',
    arguments: [{ name: 'code', description: 'The code to analyze', required: true }],
  },
]

const myPromptHandlers: MCPServerPrompts = {
  listPrompts: async () => prompts,
  getPromptMessages: async ({ name, args }) => {
    if (name === 'analyze-code') {
      return [
        {
          role: 'user',
          content: {
            type: 'text',
            text: `Analyze this code: ${args?.code}`,
          },
        },
      ]
    }
    throw new Error('Prompt not found')
  },
}

const serverWithPrompts = new MCPServer({
  id: 'prompt-server',
  name: 'Prompt Server',
  version: '1.0.0',
  tools: {/* ... your tools ... */},
  prompts: myPromptHandlers,
})
```

### 向客戶端發送提示詞變更通知 {/* #notifying-clients-of-prompt-changes */}

可用的提示詞有變時，伺服器可以通知正在監聽的客戶端。

#### `server.prompts.notifyListChanged()` {/* #serverpromptsnotifylistchanged */}

如果可用提示詞清單有變，例如新增或移除提示詞，請調用此方法。正在監聽的客戶端會收到 `notifications/prompts/list_changed` 訊息，並重新取得提示詞清單。

```typescript oxfmt:false
await serverWithPrompts.prompts.notifyListChanged();
```

### 處理提示詞的建議做法 {/* #best-practices-for-prompt-handling */}

* 為提示詞選用能表明用途的名稱，並清楚說明用途。
* 在 `getPromptMessages` 內驗證所有必填參數。
* 找不到提示詞或欠缺必填參數時，回傳錯誤。
* 提示詞每次有變，都通知客戶端。

## 動態管理 Tool {/* #dynamic-tool-management */}

伺服器運作期間可以新增或移除 Tool。已連接的客戶端會收到 `notifications/tools/list_changed` 通知。

管理 Tool 的屬性名為 `toolActions`，而 `tools()` 是回傳 Tool 註冊表的方法。

### `toolActions.add(tools)` {/* #toolactionsaddtools */}

在運作中的伺服器註冊新 Tool，並通知已連接的客戶端。與傳入建構函數的 Tool 一樣，註冊時採用輸入物件中相應項目的鍵。以現有的鍵新增 Tool，便會取代原有的 Tool。

```typescript oxfmt:false
async server.toolActions.add(tools: ToolsInput): Promise<void>
```

例子：

```typescript
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

const searchTool = createTool({
  id: 'search',
  description: 'Searches the knowledge base.',
  inputSchema: z.object({ query: z.string() }),
  execute: async ({ query }) => ({ results: [] }),
})

await server.toolActions.add({ searchTool })
```

### `toolActions.remove(toolIds)` {/* #toolactionsremovetoolids */}

按 Tool ID 從運作中的伺服器移除 Tool，並通知已連接的客戶端。伺服器會略過未能識別的 Tool ID，只有實際移除至少一個 Tool 時才會發送通知。


```typescript oxfmt:false
async server.toolActions.remove(toolIds: string[]): Promise<void>
```

例子：

```typescript
await server.toolActions.remove(['searchTool'])
```

### `toolActions.notifyListChanged()` {/* #toolactionsnotifylistchanged */}

向已連接的客戶端發送 `notifications/tools/list_changed` 訊息，並保留原有的 Tool 註冊表。如果授權變更等其他原因影響 Tool 的可用性，請調用此方法。

```typescript oxfmt:false
async server.toolActions.notifyListChanged(): Promise<void>
```

### Mastra 註冊表同步 {/* #mastra-registry-synchronization */}

伺服器註冊至 Mastra 實例後，`toolActions.add()` 和 `toolActions.remove()` 亦會更新該實例的 Tool 註冊表，做法與啟動時自動註冊 Tool 一致。新增的 Tool 可透過 `mastra.listTools()` 取得。如 Tool 自帶 `id`，便會以該 ID 為鍵。已移除的 Tool 會從註冊表刪除。

## 日誌 {/* #logging */}

Tool 透過 `notifications/message` 向發起調用的客戶端發送結構化日誌。客戶端須在每次請求的元數據加入 `io.modelcontextprotocol/logLevel` 鍵，才會收到日誌。伺服器只會就該次請求發送達到指定嚴重程度或以上的訊息，級別次序依照 RFC 5424。同一次 Tool 調用的後續輪次屬於新請求，須再次選擇接收日誌。啟用 `enableServerLogs` 後，Mastra 的 `MCPClient` 會在每次請求一併發送該鍵。

`context.mcp.log()` 只控制 MCP 客戶端收到的日誌，並不影響 Mastra 的日誌記錄器或可觀測性。

### `context.mcp.log()` {/* #contextmcplog */}

在 Tool 的 `execute` 函數中，使用 `context.mcp.log()` 向調用該 Tool 的客戶端發送日誌訊息。

```typescript oxfmt:false
async context.mcp.log(
  level: LoggingLevel,
  message: string,
  data?: Record<string, unknown>
): Promise<void>
```

例子：

```typescript
execute: async ({ location }, context) => {
  await context.mcp?.log?.('debug', 'Fetching weather', { location })
  const weather = await fetchWeather(location)
  await context.mcp?.log?.('info', 'Weather fetched')
  return weather
}
```

## 進度通知 {/* #progress-notifications */}

執行時間較長的 Tool 可透過 `notifications/progress` 向發起調用的客戶端匯報進度。調用方須在請求的 `_meta` 加入 `progressToken` 以啟用進度追蹤，才會收到通知。設定 `enableProgressTracking` 後，Mastra 的 `MCPClient` 會加入該權杖。如果請求未附上權杖，`context.mcp.progress()` 不會執行任何操作。

### `context.mcp.progress()` {/* #contextmcpprogress */}

```typescript oxfmt:false
async context.mcp.progress(params: {
  progress: number;
  total?: number;
  message?: string;
}): Promise<void>
```

例子：

```typescript
execute: async ({ items }, context) => {
  for (const [index, item] of items.entries()) {
    await processItem(item)
    await context.mcp?.progress?.({
      progress: index + 1,
      total: items.length,
      message: `Processed ${item.name}`,
    })
  }
  return { done: true }
}
```

## 追蹤 {/* #tracing */}

伺服器註冊至已配置可觀測性的 `Mastra` 實例後，每次處理 `tools/list`、`tools/call`、`resources/*` 和 `prompts/*` 請求都會產生一個 `MCP_SERVER_REQUEST` 根 span。`executeTool()` 亦會產生相同的 span，因此 Studio 的 MCP 伺服器頁面與 MCP 客戶端採用相同的追蹤方式。

span 以方法及目標命名，例如 `tools/call lookupOrder`。它會以請求參數作為輸入、回應作為輸出，並記錄伺服器的名稱及版本、協商後的協議版本，以及客戶端報告的名稱及版本。如果 `tools/call` 回傳 `isError: true`，該 span 便會標記為失敗。以 Tool 形式提供的 Agent 和 Workflow 會分別將 `AGENT_RUN` 和 `WORKFLOW_RUN` span 加入其下。伺服器直接提供的 Tool 不會有獨立的 `TOOL_CALL` span，但 Agent 在請求內調用的 Tool 仍會產生這類 span。

沒有關聯 `mastra` 實例的獨立 `MCPServer` 不會產生 span。

### 連結至調用方的 Trace {/* #linking-to-the-callers-trace */}

附有 W3C `traceparent` 的請求會保留本身的 Trace、根 span 和 Trace 摘要。請求 span 會連結至調用方的 span，讓你由調用方的 Trace 找到 Tool 調用所觸發的請求。

使用追蹤橋接時，請求 span 會在請求抵達當刻的活躍 span 下啟動。如果伺服器的 HTTP 監測根據 `traceparent` 標頭延續調用方的 Trace，請求便會加入該 Trace，連結亦會指向同一 Trace 內的 span。

伺服器依照以下次序從兩個位置讀取 `traceparent` 和 `tracestate`。

1. 請求的 `_meta`。Agent 或 Workflow 透過 HTTP 或 stdio 發起受追蹤的 Tool 調用時，`MCPClient` 會在此處發送 `traceparent`。
2. HTTP 標頭。非 Mastra 調用方的 OpenTelemetry HTTP 監測會經標頭發送這兩個欄位。

請求 span 亦會把有效的 `traceparent` 記作 `callerTraceparent` 屬性，並把一併送出的 `tracestate` 記作 `callerTracestate` 屬性，後者最多保留 512 個字元。即使匯出程式不支援 span 連結，仍會附上這些屬性。沒有有效 `traceparent` 的請求不會有連結或調用方屬性。這些追蹤欄位不會列入 span 的輸入。

連結也可以由調用方指向伺服器。若 `tools/call` 請求附有 `traceparent`，回應中的 `_meta.mastra.traceparent` 會識別請求 span，`MCPClient` 會從自己的 Tool 調用 span 加入指向該 span 的連結。如調用方沒有發送追蹤上下文，回應便不會附上追蹤資料。

Mastra 會連同 span 儲存連結。OpenTelemetry 匯出程式、[`OtelBridge`](/integrations/observability/opentelemetry#bridge)、`DatadogBridge`、`DatadogExporter` 和 `SentryExporter` 會以 span 連結的形式發送這些連結。`DatadogExporter` 和 `SentryExporter` 會為 span 分配各自的 ID，因此相應的後端無法解析兩個 Mastra span 之間的連結。

## 發送通知 {/* #notification-delivery */}

請求內的通知（`context.mcp.log()`、`context.mcp.progress()`）經觸發通知的請求串流傳送，因此只有發起請求的一方會收到。可在請求結束後發出的通知（`resources.notifyListChanged()`、`prompts.notifyListChanged()`、`toolActions.notifyListChanged()`、`resources.notifyUpdated()`），會經相關客戶端各自保持開啟的 `subscriptions/listen` 串流傳送。`resources.notifyUpdated()` 只會通知串流涵蓋該資源 URI 的客戶端。所有監聽相關清單的客戶端都會收到清單變更通知。使用 stdio 時，串流由連線本身承載。

## OAuth 保護 {/* #oauth-protection */}

使用 `createOAuthMiddleware` 函數，即可按 [MCP 授權規格](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)，以 OAuth 身份驗證保護 MCP 伺服器。

```typescript
import http from 'node:http'
import { MCPServer, createOAuthMiddleware, createStaticTokenValidator } from '@mastra/mcp'

const mcpServer = new MCPServer({
  id: 'protected-server',
  name: 'Protected MCP Server',
  version: '1.0.0',
  tools: {/* your tools */},
})

// Create OAuth middleware
const oauthMiddleware = createOAuthMiddleware({
  oauth: {
    resource: 'https://mcp.example.com/mcp',
    authorizationServers: ['https://auth.example.com'],
    scopesSupported: ['mcp:read', 'mcp:write'],
    resourceName: 'My Protected MCP Server',
    validateToken: createStaticTokenValidator(['allowed-token-1']),
  },
  mcpPath: '/mcp',
})

// Create HTTP server with OAuth protection
const httpServer = http.createServer(async (req, res) => {
  const url = new URL(req.url || '', 'https://mcp.example.com')

  // Apply OAuth middleware first
  const result = await oauthMiddleware(req, res, url)
  if (!result.proceed) return // Middleware handled response (401, metadata, etc.)

  // Token is valid, proceed to MCP handler
  await mcpServer.startHTTP({ url, httpPath: '/mcp', req, res })
})

httpServer.listen(3000)
```

中介軟件會自動執行以下操作。

* 在 `/.well-known/oauth-protected-resource` 提供**受保護資源元數據**（RFC 9728）。
* 須驗證身份時，回傳 `401 Unauthorized` 和適當的 `WWW-Authenticate` 標頭。
* 使用你提供的驗證器驗證持有者權杖。

### 令牌驗證 {/* #token-validation */}

在正式運作的環境中，請妥善驗證令牌：

```typescript
import { createOAuthMiddleware, createIntrospectionValidator } from '@mastra/mcp'

// Option 1: Token introspection (RFC 7662)
const middleware = createOAuthMiddleware({
  oauth: {
    resource: 'https://mcp.example.com/mcp',
    authorizationServers: ['https://auth.example.com'],
    validateToken: createIntrospectionValidator('https://auth.example.com/oauth/introspect', {
      clientId: 'mcp-server',
      clientSecret: 'secret',
    }),
  },
})

// Option 2: Custom validation (JWT, database lookup, etc.)
const customMiddleware = createOAuthMiddleware({
  oauth: {
    resource: 'https://mcp.example.com/mcp',
    authorizationServers: ['https://auth.example.com'],
    validateToken: async (token, resource) => {
      const decoded = await verifyJWT(token)
      if (!decoded) {
        return { valid: false, error: 'invalid_token' }
      }
      return {
        valid: true,
        scopes: decoded.scope?.split(' ') || [],
        subject: decoded.sub,
      }
    },
  },
})
```

如果驗證函數能識別用戶，請回傳 `subject`。伺服器會將 `input_required` 的續接狀態與該用戶的識別碼關聯，讓使用同一個 OAuth 客戶端的用戶各自保留自己的續接狀態。

## 身份驗證上下文 {/* #authentication-context */}

使用 HTTP 傳輸時，Tool 可透過 `context.mcp.extra` 讀取請求的元數據，包括由 HTTP 中間件傳入的身份驗證資料、用戶上下文及自訂資料。

### 資料如何傳遞 {/* #how-it-works */}

在 HTTP 中間件中寫入 `req.auth` 的資料，可在 Tool 內透過 `context.mcp.extra.authInfo` 讀取，也可在資源和提示詞的回調函數內透過 `requestContext.get('authInfo')` 讀取：

```text
req.auth = { ... }  →  context.mcp.extra.authInfo = { ... }
```

### 為 FGA 映射身份驗證資料 {/* #map-auth-data-for-fga */}

在已設定細粒度授權（FGA）Provider 的 Mastra 實例上註冊 `MCPServer` 後，Mastra 會在列出或呼叫 Tool 前檢查 `requestContext.get('user')`。HTTP 傳輸層會透過 `extra.authInfo` 傳遞已驗證的身份資料，請使用 `mapAuthInfoToUser` 將這些資料轉換為 FGA Provider 所需的用戶資料結構。

```typescript
const server = new MCPServer({
  id: 'my-server',
  name: 'My Server',
  version: '1.0.0',
  tools: { getUserData },
  mapAuthInfoToUser: ({ authInfo }) => {
    const user = authInfo as {
      extra?: {
        userId?: string
        organizationMembershipId?: string
      }
    }

    if (!user.extra?.userId) {
      return null
    }

    return {
      id: user.extra.userId,
      organizationMembershipId: user.extra.organizationMembershipId,
    }
  },
})
```

### 為 MCP Tool 獨立設定 FGA 範圍 {/* #scope-mcp-tool-fga-separately */}

如果 MCP 客戶端所需的授權範圍與內部 Agent 或 Workflow 執行 Tool 時採用的範圍有別，請使用 `fga.resourceMapping` 和 `fga.permissionMapping`。這兩項覆寫設定只適用於這個 MCP 伺服器針對 `tools/list` 和 `tools/call` 進行的授權檢查。

```typescript
import { MastraFGAPermissions } from '@mastra/core/auth/ee'

const server = new MCPServer({
  id: 'my-server',
  name: 'My Server',
  version: '1.0.0',
  tools: { getUserData },
  mapAuthInfoToUser: ({ authInfo }) => {
    const user = authInfo as {
      extra?: {
        userId?: string
        organizationMembershipId?: string
      }
    }

    if (!user.extra?.userId) {
      return null
    }

    return {
      id: user.extra.userId,
      organizationMembershipId: user.extra.organizationMembershipId,
    }
  },
  fga: {
    resourceMapping: {
      tool: {
        fgaResourceType: 'user',
        deriveId: ({ user }) => (user as { id: string }).id,
      },
    },
    permissionMapping: {
      [MastraFGAPermissions.TOOLS_EXECUTE]: 'read',
    },
  },
})
```

### 設定身份驗證中間件 {/* #setting-up-authentication-middleware */}

如要將資料傳給 Tool，請在呼叫 `server.startHTTP()` 前，透過 HTTP 伺服器的中間件設定 Node.js 請求物件的 `req.auth`。

```typescript
import express from 'express'

type MCPAuthenticatedRequest = express.Request & {
  auth?: {
    token: string
    clientId: string
    scopes: string[]
    expiresAt?: number
    extra?: Record<string, unknown>
  }
}

const app = express()

// Auth middleware - set req.auth before the MCP handler
app.use('/mcp', async (req, res, next) => {
  const authorization = req.headers.authorization

  if (!authorization?.startsWith('Bearer ')) {
    res.status(401).json({ error: 'Missing bearer token' })
    return
  }

  const token = authorization.slice('Bearer '.length)

  try {
    const user = await verifyToken(token)

    // This entire object becomes context.mcp.extra.authInfo
    const authenticatedRequest = req as MCPAuthenticatedRequest
    authenticatedRequest.auth = {
      token,
      clientId: user.clientId,
      scopes: user.scopes,
      expiresAt: user.expiresAt,
      extra: {
        sub: user.userId,
        email: user.email,
      },
    }
    next()
  } catch {
    res.status(401).json({ error: 'Invalid or expired token' })
  }
})

app.all('/mcp', async (req, res) => {
  const url = new URL(req.url, `http://${req.headers.host}`)
  await server.startHTTP({ url, httpPath: '/mcp', req, res })
})
```

將 `extra.sub`（或 `extra.subject`）設為用戶識別碼。伺服器會用這個識別碼，將 `input_required` 的續接狀態綁定至該用戶。

### 在 Tool 內存取身份驗證資料 {/* #accessing-auth-data-in-tools */}

在 Tool 的執行函數內，可透過 `context.mcp.extra.authInfo` 讀取 `req.auth` 物件：

```typescript
execute: async (inputData, context) => {
  // Access the auth data you set in middleware
  const authInfo = context.mcp?.extra.authInfo

  if (!authInfo?.extra?.sub) {
    return { error: 'Authentication required' }
  }

  // Use the auth data
  console.log('User ID:', authInfo.extra.sub)
  console.log('Email:', authInfo.extra.email)

  // Use a credential intended for the API being called, not the MCP token.
  // See https://mastra.ai/docs/guides/mcp-authentication-authorization#access-upstream-services-safely
  const credential = await apiCredentials.getForUser(authInfo.extra.sub as string)

  const response = await fetch('/api/data', {
    headers: { Authorization: `Bearer ${credential.token}` },
    signal: context.mcp?.extra.signal,
  })

  return response.json()
}
```

### 將 `RequestContext` 傳給 Agent {/* #passing-requestcontext-through-to-agent */}

`context.requestContext` 已包含 `authInfo` 和映射後的 `user`，所以 Tool 調用 Agent 時可原樣傳入：

```typescript
execute: async (inputData, context) => {
  const authInfo = context.mcp?.extra.authInfo

  if (!authInfo?.extra?.sub) {
    return { error: 'Authentication required' }
  }

  const agent = context.mastra?.getAgentById('some-agent-id')

  if (!agent) {
    return { error: "Agent 'some-agent-id' not found" }
  }

  const response = await agent.generate(prompt, { requestContext: context.requestContext })

  return response.text
}
```

### `extra` 物件 {/* #the-extra-object */}

`context.mcp.extra` 物件包含以下屬性：

| 屬性 | 說明 |
| - | - |
| `authInfo` | 在中間件內寫入 `req.auth` 的資料 |
| `requestId` | 當前請求的 JSON-RPC 識別碼 |
| `signal` | 用於取消請求的 AbortSignal |
| `_meta` | 客戶端發送的請求元數據，包括 W3C 追蹤欄位、用來明確指定日誌級別的 `io.modelcontextprotocol/logLevel`，以及 `progressToken` |
| `sendNotification`, `sendRequest` | 已棄用。協議不支援由伺服器發起請求，因此調用任何一個方法都會拋出錯誤。錯誤訊息會指出應改用 `context.mcp.log()`、`context.mcp.progress()` 或 `context.suspend()`。 |

### 完整示例 {/* #complete-example */}

安裝 [`jose`](https://github.com/panva/jose)，以便使用身份 Provider 的 JSON Web 密鑰集（JWKS）驗證 JSON Web 令牌（JWT）：

```shell npm2yarn
npm install jose
```

以下示例會先驗證令牌的簽署、簽發者、受眾、算法、到期時間及必需的聲明，再將令牌內的用戶資料傳給 Tool：

```typescript
import express from 'express'
import { createRemoteJWKSet, jwtVerify } from 'jose'
import { MCPServer } from '@mastra/mcp'
import { createTool } from '@mastra/core/tools'
import { z } from 'zod'

type MCPAuthenticatedRequest = express.Request & {
  auth?: {
    token: string
    clientId: string
    scopes: string[]
    expiresAt?: number
    extra?: Record<string, unknown>
  }
}

const issuer = process.env.JWT_ISSUER
const audience = process.env.JWT_AUDIENCE
const jwksUri = process.env.JWT_JWKS_URI

if (!issuer || !audience || !jwksUri) {
  throw new Error('JWT_ISSUER, JWT_AUDIENCE, and JWT_JWKS_URI are required')
}

const jwks = createRemoteJWKSet(new URL(jwksUri))

const verifyToken = async (token: string) => {
  const { payload } = await jwtVerify(token, jwks, {
    issuer,
    audience,
    algorithms: ['RS256'],
    requiredClaims: ['exp'],
  })

  const clientId =
    typeof payload.client_id === 'string'
      ? payload.client_id
      : typeof payload.azp === 'string'
        ? payload.azp
        : undefined

  if (!payload.sub || typeof payload.email !== 'string' || !clientId || !payload.exp) {
    throw new Error('Token must contain sub, email, exp, and client_id or azp claims')
  }

  return {
    userId: payload.sub,
    clientId,
    email: payload.email,
    expiresAt: payload.exp,
    scopes: typeof payload.scope === 'string' ? payload.scope.split(' ') : [],
  }
}

// 1. Define your tool that uses auth context
const getUserData = createTool({
  id: 'get-user-data',
  description: 'Fetches data for the authenticated user',
  inputSchema: z.object({}),
  execute: async (inputData, context) => {
    const authInfo = context.mcp?.extra.authInfo

    if (!authInfo?.extra?.sub) {
      return { error: 'Authentication required' }
    }

    // Access the data you set in middleware
    return {
      userId: authInfo.extra.sub,
      email: authInfo.extra.email,
    }
  },
})

// 2. Create the MCP server with your tools
const server = new MCPServer({
  id: 'my-server',
  name: 'My Server',
  version: '1.0.0',
  tools: { getUserData },
})

// 3. Set up Express with auth middleware
const app = express()

app.use('/mcp', async (req, res, next) => {
  const authorization = req.headers.authorization

  if (!authorization?.startsWith('Bearer ')) {
    res.status(401).json({ error: 'Missing bearer token' })
    return
  }

  const token = authorization.slice('Bearer '.length)

  try {
    const user = await verifyToken(token)

    // This entire object becomes context.mcp.extra.authInfo
    const authenticatedRequest = req as MCPAuthenticatedRequest
    authenticatedRequest.auth = {
      token,
      clientId: user.clientId,
      scopes: user.scopes,
      expiresAt: user.expiresAt,
      extra: {
        sub: user.userId,
        email: user.email,
      },
    }
    next()
  } catch {
    res.status(401).json({ error: 'Invalid or expired token' })
  }
})

app.all('/mcp', async (req, res) => {
  const url = new URL(req.url, `http://${req.headers.host}`)
  await server.startHTTP({ url, httpPath: '/mcp', req, res })
})

app.listen(3000)
```

## 事件（實驗性） {/* #events-experimental */}

:::warning

事件功能按照 MCP 擴充規格草案 [SEP-3415](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3415) 實作。傳輸格式及此 API 可能隨任何版本更新而變更。

:::

完整操作步驟請參閱 [MCP 事件](/docs/connections/mcp#mcp-events)。

`events` 選項讓客戶端訂閱伺服器上發生的事件，例如建立工單或完成建置。伺服器會宣告支援 `io.modelcontextprotocol/events` 擴充功能，並經 stdio 和 Streamable HTTP 回應 `events/list`、`events/poll` 及 `events/stream`。設定 [`eventsOptions.webhook`](#webhook-delivery) 後，伺服器亦會回應 `events/subscribe` 和 `events/unsubscribe`，並以 POST 把事件發送至客戶端的 Webhook URL。

以 `defineEvent()` 宣告每個事件類型，再以 `server.events.emit()` 發佈事件：

```typescript
import { MCPServer, defineEvent } from '@mastra/mcp'
import { z } from 'zod'

const server = new MCPServer({
  id: 'tickets',
  name: 'Tickets',
  version: '1.0.0',
  tools: {},
  events: {
    'ticket.created': defineEvent({
      description: 'A ticket was created',
      inputSchema: z.object({ project: z.string().optional() }),
      payloadSchema: z.object({ id: z.string(), project: z.string() }),
      match: (args, data) => !args.project || data.project === args.project,
    }),
  },
})

await server.events.emit('ticket.created', { id: 't-1', project: 'web' })
```

使用 `{ project: 'web' }` 訂閱的客戶端會收到這宗事件，使用 `{ project: 'api' }` 訂閱的客戶端則不會。

`match` 按客戶端所選的參數篩選事件，無法控制誰可以訂閱。要限制調用方，請加入 `authorize`。它會接收已通過驗證的參數和調用方的 `requestContext`。設定 `mapAuthInfoToUser` 後，該上下文會包含 `user`：

```typescript
const ticketCreated = defineEvent({
  inputSchema: z.object({ project: z.string() }),
  payloadSchema: z.object({ id: z.string(), project: z.string() }),
  match: (args, data) => data.project === args.project,
  authorize: ({ arguments: args, requestContext }) => {
    const user = requestContext.get('user') as { projects: string[] } | undefined
    return user?.projects.includes(args.project) ?? false
  },
})
```

每次調用 `events/poll`、開啟 `events/stream`，或以 `events/subscribe` 建立或續訂 Webhook 訂閱時，都會執行 `authorize`。已開啟的串流在重新連線時才會再次檢查，Webhook 訂閱則在下次續訂時才會檢查。調用方失去存取權限後，仍會收到事件，直至再次檢查。由於 FGA 不適用於事件，請使用 `authorize` 限制事件存取權限。

### 發送模式 {/* #delivery-modes */}

伺服器會按事件來源決定該類型可用的發送模式：

| 定義 | 宣告支援的 `delivery` | 事件來源 |
| - | - | - |
| 沒有定義 `poll` | `['push', 'poll']`，已設定 `eventsOptions.webhook` 時亦支援 `'webhook'` | `server.events.emit()`。輪詢會讀取記憶體內的緩衝區。 |
| `poll` | `['poll']` | 每次收到 `events/poll` 請求時，都會調用你提供的 `poll` 函數。 |

使用 `poll` 作來源的事件類型不支援推送。你無法藉由 `delivery` 為該類型加入 `'push'`，向該類型調用 `server.events.emit()` 亦會拋出例外。客戶端只能透過 `events/list` 得知支援的模式，因此伺服器啟動後不會更改所宣告的模式。要推送事件，請定義不含 `poll` 的類型，然後發佈該類型的事件。

請求使用該類型未宣告支援的模式會收到 `-32026`。指定未知的事件名稱會收到 `-32023`。

### 推送串流 {/* #push-streams */}

每個 `events/stream` 請求對應一項訂閱。伺服器先發送 `notifications/events/active`，其後每次發生符合條件的事件，都會發送一則 `notifications/events/event`。每則通知都會在 `_meta["io.modelcontextprotocol/subscriptionId"]` 帶上請求 ID。如果請求包含 `cursor`，伺服器會先重播緩衝區內位於游標之後的事件，再發送即時事件。如果該游標早於緩衝區內最早的事件，`active` 會報告 `truncated: true`。

如果在 `heartbeatIntervalMs` 內沒有發送其他訊息，串流會發送帶有當前游標的 `notifications/events/heartbeat`。取消請求或調用 `server.close()` 會結束串流，並釋放其監聽器及計時器。

### Webhook 發送 {/* #webhook-delivery */}

設定 `eventsOptions.webhook` 後，客戶端可以用 `events/subscribe` 登記回調 URL。每次發生符合條件的事件，伺服器都會按照 [Standard Webhooks](https://www.standardwebhooks.com/) 規格，用客戶端的密鑰以 HMAC-SHA256 簽署，再以 POST 發送至該 URL。

```typescript
const server = new MCPServer({
  id: 'tickets',
  name: 'Tickets',
  version: '1.0.0',
  tools: {},
  events: {
    'ticket.created': defineEvent({ payloadSchema: z.object({ id: z.string() }) }),
  },
  eventsOptions: {
    webhook: { ttl: { defaultMs: 30 * 60_000 } },
  },
})
```

伺服器會執行以下規則：

* **身份驗證：** 調用方必須通過身份驗證才可訂閱 Webhook。如果請求沒有 `authInfo`，`events/subscribe` 會傳回 `-32024`。訂閱以調用方、URL、事件名稱和參數識別，因此以相同條件再次調用 `events/subscribe` 會續訂同一項訂閱，並傳回相同的 `id`。
* **授權：** 每次訂閱或續訂時都會執行 `authorize`。續訂遭拒時，伺服器會移除訂閱，並停止以 POST 發送後續事件。Mastra 客戶端無法區分這個 `-32024` 和調用方未通過身份驗證時收到的 `-32024`，因此在預設發送模式下，會報告 `MCP_EVENTS_WEBHOOK_UNAVAILABLE`，嘗試推送，然後以相同的 `-32024` 拒絕請求。
* **回調 URL：** URL 必須使用 `https`，所有解析所得的地址均須可在公用網絡上路由。回環地址、私人地址、鏈路本地地址和其他特殊用途地址範圍會被拒絕，並傳回 `-32602` 和 `data.reason`。每次發送前都會重新檢查，請求只會連接至通過檢查的地址，以防止 DNS 重新綁定。伺服器不會跟隨重新導向。
* **端點驗證：** 首次向某個 URL 發送事件前，伺服器會以 POST 發送經簽署的驗證挑戰，端點必須原樣傳回。端點驗證失敗或無法連線時，`events/subscribe` 會傳回 `-32027`，並附上 `data.reason`，例如 `challenge_failed` 或 `timeout`。驗證結果會按調用方和 URL 快取。獲 `allowedUrls` 接受的 URL 會略過這一步。
* **有效期：** 除非客戶端續訂，否則訂閱會在傳回的 `refreshBefore` 時間到期。請求的 `ttlMs` 會限制在 `ttl` 所訂的範圍內。
* **重試：** 每宗事件會按指數退避策略重試發送，直至收到 `2xx` 確認、達到 `retry.maxAttempts` 次嘗試，或超過 `retry.maxWindowMs`。收到 `410` 或 `413` 回應後，會停止重試該宗事件。每個請求正文內的 `cursor` 只會越過已確認收到或已放棄發送的事件。
* **暫停：** 如果某項訂閱在 `suspend.windowMs` 內大部分發送嘗試均告失敗，伺服器會暫停向該訂閱發送事件，並在下次續訂時於 `deliveryStatus` 報告 `active: false`。續訂後會恢復發送。
* **錯誤：** 客戶端只會看到 `timeout` 或 `http_5xx` 等失敗類別，無法看到端點的回應正文或標頭。

### `server.events.emit(name, data, options?)` {/* #servereventsemitname-data-options */}

記錄事件，將事件發送至符合條件的推送串流及 webhook 訂閱，並返回事件及其 `eventId`、`timestamp` 和 `cursor`。`options.eventId` 和 `options.timestamp` 分別覆寫預設的隨機 UUID 和當前時間。如未設定 `name`、`data` 未能通過 `payloadSchema` 驗證，或該事件類型設有 `poll` 來源，此方法會擲出錯誤。

`server.events.list()` 返回 `events/list` 所提供的事件描述符。

### 限制 {/* #limits */}

* 事件會保留在發出事件的程序內。推送串流、webhook 訂閱及透過緩衝區進行的輪詢，只能取得同一個 `MCPServer` 實例發出的事件。因此，無伺服器部署或多實例部署需要以共享儲存支援的 `poll` 來源。
* 緩衝區設於記憶體內。伺服器重新啟動後，會將舊游標視為有事件缺漏，並回報 `truncated: true`。
* Webhook 發送狀態（等待重試的項目、暫停狀態及驗證結果）保存在記憶體內，並在客戶端更新訂閱時重建。
* 發送事件清單變更通知需要在 `subscriptions/listen` 使用 `eventsListChanged` 篩選條件。`@mastra/mcp` 使用的 MCP TypeScript SDK 版本尚未支援這項條件。加入支援前，伺服器不會宣告 `listChanged`，亦不會發送 `notifications/events/list_changed`。客戶端應再次呼叫 `events/list`，以查閱更新後的事件類型。

## 任務（實驗） {/* #tasks-experimental */}

:::warning

任務功能實現了 SEP-2663 所定義的 MCP 擴展 `io.modelcontextprotocol/tasks`。此 API 可能在任何版本更改。

:::

`tasks` 選項讓 Tool、Workflow（`run_*`）或 Agent（`ask_*`）以任務回覆 `tools/call`。客戶端會即時收到任務識別碼，並輪詢 `tasks/get`，直至任務完成。請求結束後仍可取得結果，任務亦不受 HTTP 逾時限制。只要其中至少一項可以任務回覆，伺服器便會宣告支援這項擴展，並透過 stdio 和 Streamable HTTP 回覆 `tasks/get`、`tasks/update` 和 `tasks/cancel`。如未設定 `tasks` 選項，伺服器不會宣告支援這項擴展，亦不會處理這些請求。

只有在請求中宣告這項擴展的客戶端才會收到任務。其他客戶端會收到同步回覆，但列於 `required` 的 Tool 除外。

```typescript
import { MCPServer } from '@mastra/mcp'

const server = new MCPServer({
  id: 'reports',
  name: 'Reports',
  version: '1.0.0',
  tools: { buildReport, lookupCustomer },
  tasks: {
    tools: {
      buildReport: 'always',
      lookupCustomer: { mode: 'auto', syncWindowMs: 1000 },
    },
  },
})
```

### 模式 {/* #modes */}

| 模式 | 客戶端已宣告擴展 | 客戶端未宣告擴展 |
| - | - | - |
| `'off'` | 同步回覆。 | 同步回覆。 |
| `'always'` | 即時返回任務識別碼。 | 同步回覆。如 Tool 列於 `required`，則返回錯誤 `-32021`。 |
| `'auto'` | 如 Tool 在 `syncWindowMs` 內完成，則同步回覆。否則返回任務識別碼，原有的執行會繼續。 | 同步回覆。如 Tool 列於 `required`，則返回錯誤 `-32021`。 |

伺服器會在回覆前建立任務，因此客戶端收到任務識別碼後，即時呼叫 `tasks/get` 亦可取得任務。

### 訪問任務 {/* #access-to-tasks */}

任務 ID 是無法猜中的持有者權杖，每項任務都會綁定建立它的調用方。伺服器按照[延續狀態](#continuation-state)的方式識別調用方，依據 OAuth 主體、映射所得的 `user` 或持有者權杖的雜湊值。其他調用方要求存取任務，或調用方被 `authorize` 拒絕時，都會收到錯誤 `-32602`，與任務 ID 不存在時的回覆相同。客戶端無法透過 MCP 列出任務。

### Studio 中的任務 {/* #tasks-in-studio */}

設定了 `tasks` 的伺服器，其 Studio 頁面會顯示哪些 Tool 會以任務形式執行（`always` 或 `auto`），以及 `required` 和 `recover` 設定。頁面亦會由新至舊列出所有調用方的任務，並顯示狀態、發出任務的客戶端、尚待回覆的輸入請求及到期時間。你可以按狀態、Tool 或客戶端篩選，載入較早的任務，或貼上客戶端顯示的 MCP 任務 ID 以開啟該任務。開啟後可查看結果或錯誤，亦可取消任務或回覆它正在等候的輸入請求。取消和回覆分別執行與 `tasks/cancel` 和 `tasks/update` 相同的程式碼，但會略過 `authorize`。

* Studio 透過其 ID 的雜湊值來識別任務，並透過其身分的雜湊值來識別呼叫者。兩者都不能透過 MCP 使用，而且原始值永遠不會發送到 Studio。您貼上的任務 ID 將在請求正文中傳送並在伺服器上進行雜湊處理。
* 客戶端顯示為其客戶端 ID 以及令牌的主題或使用者 ID。僅透過其令牌標識的呼叫者會顯示令牌雜湊的短前綴。標籤從來都不是憑證。
* 使用 RBAC Provider 時，列出和查找任務需要 `mcp:read`。取消任務和回覆輸入請求需要 `mcp:write`。預設的 `admin` 角色有這項權限，`member` 和 `viewer` 則沒有。缺少權限時，Studio 仍會顯示任務，但不提供這兩項操作。
* 只有沒有資源範圍的 Studio 會話才能取得清單。 MCP 呼叫者和 Mastra 資源是獨立的身份，因此資源範圍內的會話不會取得任何任務，也無法取消或回應任務。
* 內置任務儲存支援列出任務。自訂 `store` 亦須實現 `MCPTaskStoreAdmin`（`list`、`updateByKey`、`cancelByKey`），否則 Studio 會提示無法列出該儲存區內的任務。

### 開啟任務上限 {/* #open-task-caps */}

處於 `working` 或 `input_required` 狀態的任務會計入未結束任務總數。任務完成、失敗、取消或到期後便不再計入。如果一次調用會超出 `maxOpenTasksPerClient` 或 `maxOpenTasks`，伺服器便不會建立任務：

* `'always'` 模式的 Tool 不會執行。調用會返回 `isError: true`，以及類似 `Too many open tasks for this client (limit 100). Wait for one to finish or cancel one.` 的訊息。
* 若同步時段結束時 `'auto'` 模式的 Tool 仍在執行，它會繼續在原有請求下執行並同步回覆，與沒有使用任務時一樣。取消請求仍會中止執行。
* `run_<workflow>` 和 `ask_<agent>` 任務亦計入上述上限和[保留任務上限](#retained-task-caps)。`'always'` 模式的 Workflow 不會開始執行，Agent 亦不會執行。如果 `'auto'` 模式的 Workflow 暫停，它只能透過任務接收回覆，因此達到上限時，伺服器會取消該次執行並返回 `isError: true`。

兩個值都必須是正整數。伺服器會以 `limits` 將兩個值傳入 `store.create()`，超出上限時，儲存區會拋出 `MCPTaskLimitError`。忽略 `limits` 的自訂儲存區不會限制未結束任務的數目。

### 保留任務上限 {/* #retained-task-caps */}

記憶體儲存區會保留已完成任務的結果，讓客戶端在任務的 `ttlMs` 屆滿後一分鐘內仍可讀取結果。任務完成時會釋出未結束任務的名額，但仍佔用記憶體。若無保留上限，客戶端連續執行大量短任務，可能令記憶體用量無限增長。`maxRetainedTasksPerClient` 和 `maxRetainedTasks` 限制儲存區仍然保留的所有任務數目，包括未結束和已完成的任務。

* 若一次調用會超出保留上限，伺服器會採用與超出未結束任務上限時相同的回覆方式。`'always'` 模式的 Tool 會返回 `isError: true`，以及類似 `Too many recent tasks for this client (limit 1000). Try again once older tasks expire.` 的訊息。`'auto'` 模式的 Tool 則會同步回覆。
* 已建立的任務會保留完整的 `ttlMs`。儲存區絕不會為了騰出空間而提早捨棄結果，只有移除任務時才會釋出名額。
* 所有未結束的任務亦計入保留上限。每對上限只設定其中一項時，另一項的預設值會相應調整。將 `maxRetainedTasksPerClient` 設為低於 100，會將 `maxOpenTasksPerClient` 的預設值降至相同數值。將 `maxOpenTasks` 設為高於 10000，則會將 `maxRetainedTasks` 的預設值提高至相同數值。若同時設定兩項，而保留上限低於未結束任務上限，建立伺服器時便會拋出錯誤。

只有記憶體儲存區會強制執行保留上限。使用 Mastra 儲存的任務會將完成結果保存在資料庫，因此只受未結束任務上限約束（參閱[跨實例的任務](#tasks-across-instances)）。將完成結果另行保存的自訂儲存區亦可忽略保留上限。

### 在任務中請求輸入 {/* #asking-for-input-inside-a-task */}

若 Tool 在任務內調用 `suspend()`，任務便會轉為 `input_required`。輸入請求採用與同步調用相同的表單，並根據 Tool 的 `resumeSchema` 建立。客戶端以 `tasks/update` 回覆後，伺服器會帶同 `resumeData` 再次執行 `execute`，做法與同步調用相同。請確保 `suspend()` 之前的操作可以安全地重複執行。

輸入請求遭拒絕或取消時，任務會以 `isError: true` 結束。回覆中含有任務未要求的鍵時，這些鍵的值會被忽略。

### 任務執行時所取得的資料 {/* #what-a-task-run-receives */}

每次執行都會根據建立任務時保存的資料重建，讓儲存區可在重新啟動後再次執行任務。每次執行都會取得已儲存的請求上下文，當中沒有 `context.mcp`。唯一的例外是 `'auto'` 模式 Tool 的首次執行，因為它在同步時段結束前已在原有請求下開始。

* 儲存請求上下文前，伺服器會從 `authInfo` 移除持有人權杖。其餘資料會原樣儲存，包括 `authInfo.extra` 和 `mapAuthInfoToUser` 返回的 `user`。請勿在這些資料中放入任務儲存區不應保留的憑證。
* 值會以 JSON 格式儲存。執行時讀回的是普通物件，因此原本是類別實例的 `user` 會成為具有相同欄位的普通物件。
* 無法以 JSON 格式儲存的鍵會被略過，伺服器會在建立任務時記錄警告。若遭略過的鍵是 `user`，後續執行的授權檢查便會失敗。
* 透過 `context.abortSignal` 偵測取消，因為執行時無法使用 `context.mcp`。
* 每次執行都會根據已儲存的請求上下文重新檢查授權，做法與同步調用的每一輪相同。

### 取消和錯誤 {/* #cancellation-and-errors */}

* `tasks/cancel` 會觸發 Tool 的 `abortSignal`，任務以 `cancelled` 結束。Tool 須自行處理訊號並停止執行。Tool 在取消後返回的結果會被捨棄。
* 若 Tool 拋出錯誤，任務會以 `isError: true` 和序列化後的錯誤結束，與同步調用的回覆相同。
* 只有伺服器無法執行任務時，例如任務的 TTL 屆滿，任務才會以 `failed` 結束。

### Workflow 任務 {/* #workflow-tasks */}

每個 `run_<key>` 任務會追蹤一次 Workflow 執行。該次執行由建立任務的 `tools/call` 啟動，只會啟動一次，並有獨立的執行 ID。任務 ID 與執行 ID 始終不同。

```typescript
const server = new MCPServer({
  id: 'reports',
  name: 'Reports',
  version: '1.0.0',
  workflows: { nightly },
  tasks: {
    workflows: { nightly: { mode: 'auto', syncWindowMs: 1000 } },
  },
})
```

* 執行以 `success` 或 `bailed` 結束時，任務會返回與同步調用相同的文字，包含 `status`、`input`、`steps` 和 `result`。
* 執行以 `failed`、`tripwire` 或 `canceled` 結束時，任務會返回 `isError: true` 和錯誤訊息。在 `'auto'` 模式下，若執行在 `syncWindowMs` 內失敗，伺服器會直接返回相同的回覆，無須建立任務。只有客戶端未支援任務擴充功能，或 Workflow 模式為 `'off'` 時，才會收到一般的 `run_` 回覆。這種回覆在執行失敗時不含 `isError`。
* 在 `'auto'` 模式下，若執行在 `syncWindowMs` 內暫停，便會轉為任務繼續處理，以便請求輸入。
* 參數無效時，伺服器會在建立任何執行或任務前返回 `isError: true`。
* 步驟暫停時，任務會轉為 `input_required`。表單根據該步驟的 `resumeSchema` 建立，並以步驟暫停時傳出的資料作為訊息。伺服器每次只會為一個已暫停的步驟請求輸入。`tasks/update` 會以回覆作為 `resumeData` 恢復執行。恢復執行需要 Mastra 儲存。
* 每次暫停最多只會恢復執行一次。若執行已透過 Studio 或由另一個實例恢復，任務會捨棄回覆並繼續追蹤執行。再次暫停時，即使是在迴圈中的同一步驟，任務也會發出新的輸入請求。若任務外部發出的恢復請求與任務本身的恢復請求同時到達，舊回覆仍有可能恢復同一步驟下一次暫停的執行。
* 若步驟的 `resumeSchema` 無法顯示為表單，例如含有巢狀物件，任務便會維持 `working`。你可透過其他方式恢復執行，例如使用 Studio，任務會繼續追蹤該次執行。在恢復之前，任務每秒讀取一次執行狀態。若使用 Mastra 背景任務，這段期間會佔用一個背景任務名額，與追蹤由另一個實例執行的 Workflow 時一樣。
* 從任何實例拒絕輸入請求、發出 `tasks/cancel`，或任務的 TTL 屆滿，都會取消該次執行，包括正在等候輸入的執行。若執行就在處理取消的實例上，便會在該實例停止。若由另一個實例執行，則會在該實例下次為任務續租時停止，約在一個租約期之內。
* 伺服器關閉或任務被另一個工作程序接手時，原伺服器會停止追蹤，Workflow 則繼續執行。另一個實例會接手任務並追蹤至執行結束。
* 若在 `tasks` 傳入 `store`，伺服器只會在客戶端拒絕輸入請求時取消執行。請在儲存區處理任務取消及到期時，用 `isWorkflowTaskContext()` 檢查任務上下文，調用 `mastra.getWorkflow(context.workflowKey).createRun({ runId: context.runId })`，再對返回的執行控制物件調用 `run.cancel()`。在執行 Workflow 的程序中，該物件代表正在進行的執行，因此 `cancel()` 會在該處停止執行。

執行 Workflow 任務的伺服器停止時，Mastra 的 [Workflow 恢復功能](/reference/core/mastra-class)會在下一個啟動的實例繼續執行，任務亦會在該實例追蹤執行。這要求 `recovery.workflows` 為預設值 `'auto'`。若設為 `'off'`，任務會維持 `working`，直至 TTL 屆滿。伺服器停止時正在執行的步驟會重新執行，因此請確保各步驟可以安全地重複執行。若執行從未儲存，或負責追蹤執行的實例再次停止，任務便會以 `failed` 結束。

### Agent 任務 {/* #agent-tasks */}

`ask_<key>` 任務會執行 Agent 的 `generate()`，行為與 Tool 任務相同。`tasks/cancel` 會觸發 Agent 的 `abortSignal`，發生錯誤時任務會以 `isError: true` 結束，亦適用 `recover` 設定。

若 Agent 暫停以等候批准調用 Tool 或等候其他輸入，任務會以 `isError: true` 結束。任務目前仍無法回覆 Agent 的批准請求。

### 跨實例的任務 {/* #tasks-across-instances */}

在已啟用[背景任務](/docs/harness/background-tasks)的 Mastra 實例上註冊伺服器，伺服器的任務便會保存在 Mastra 儲存區。任何共用該儲存區的實例都可以執行任務，並回應該任務的 `tasks/get`、`tasks/update` 和 `tasks/cancel` 請求。

```typescript
import { Mastra } from '@mastra/core/mastra'
import { LibSQLStore } from '@mastra/libsql'

export const mastra = new Mastra({
  // A local file is only shared by instances on the same host. Use a database every instance can reach.
  storage: new LibSQLStore({ id: 'mastra', url: 'file:./mastra.db' }),
  backgroundTasks: {
    enabled: true,
    // MCP tasks share the per-agent limit (5) unless their owner gets its own
    perOwnerConcurrency: { 'mcp-server:reports': 50 },
  },
  mcpServers: { reports: server },
})
```

* 儲存介面卡必須能為每個任務保存各自的 TTL。使用較舊的介面卡時，伺服器會在註冊時改用記憶體儲存並記錄警告。在 `tasks` 傳入的 `store` 始終優先使用。
* 若伺服器在註冊前已處理過任務，這些任務會保存在記憶體。註冊後，伺服器仍會在同一實例從記憶體處理這些任務，並將新任務保存至 Mastra 儲存區。
* 請在每個實例註冊同一個伺服器，並使用相同的 ID 和 Tool。未註冊該伺服器的實例無法執行其任務，並會將這些任務標記為失敗。請透過 `id` 指定 ID，或以 `mcpServers` 中的鍵註冊伺服器。自動產生的 ID 每次啟動都會改變，伺服器亦會記錄警告。
* 每個任務都會計入 `mcp-server:<server id>` 的 `perOwnerConcurrency` 上限（未設定時使用 `perAgentConcurrency`），亦會計入 `globalConcurrency` 上限。請將 `backpressure` 保持為預設值 `'queue'`。使用其他值時，佇列一旦排滿，調用便會失敗。
* 透過 `tasks/update` 送出的回覆會先儲存，伺服器才會確認收到。即使接收回覆的實例在執行任務前停止，任務仍會恢復執行。
* 伺服器會在已完成任務的 `ttlMs` 屆滿後約一分鐘刪除該筆記錄，無須使用 `backgroundTasks.cleanup`。伺服器只會刪除自己的記錄。設有 `ttlMs: null` 的任務會保留其記錄，直至你刪除為止。
* 每個實例會定期掃描，將已到期的任務標記為失敗，並恢復已收到回覆但仍在等候的任務。伺服器一經註冊，實例便會開始掃描，即使尚未收到任何客戶端的任務請求。每次掃描最多處理 100 個已到期任務，並檢查另外 100 個未結束任務，下次掃描再處理下一批。只有在有空餘名額時，實例才會重新執行因原實例停止而留在等候狀態的任務。其餘任務會留待稍後的掃描處理。
* `maxOpenTasksPerClient` 和 `maxOpenTasks` 會統計儲存區內所有實例的未結束任務，因此適用於整個部署。每次調用都會先計算任務數目，再加入自己的任務。因此，當多個調用同時到達不同實例時，超出上限的任務數目最多可達這批調用的總數。
* `tasks/cancel` 可由任何實例接收。若任務的首次嘗試仍在啟動它的實例上等候名額，該實例會在下次掃描時停止這次嘗試，最遲不超過一個租約期（`leaseDurationMs`）。

每個任務都是背景任務儲存區內的一筆記錄，擁有者的 Agent ID 為 `mcp-server:<server id>`，資源 ID 為 `mcp-server:<server id>:<caller>`：

* 這些任務不屬於任何 Agent、對話串或記憶，因此不會出現在 Agent 的對話中。
* `/background-tasks` 路由不會將這些任務返回給受資源範圍限制的調用方。沒有資源範圍限制的調用方，以及全域 `onTaskComplete` 和 `onTaskFailed` 鉤子，均可列出這些任務。若鉤子只預期處理 Agent 任務，請用 `task.agentId.startsWith('mcp-server:')` 識別這些記錄。
* 系統以任務 ID 和調用方身分主體各自的雜湊值查找記錄，並且不會儲存這兩項資料的原始值或持有人權杖。記錄會保存已移除持有人權杖的請求上下文，以及可直接閱讀的 `metadata.clientLabel`，當中包含客戶端 ID 和權杖主體或使用者 ID（見下一項）。`authInfo.extra` 和 `user` 會原樣儲存，因此任何可讀取該筆記錄的人都能看到這些資料。
* 為顯示哪個客戶端發出任務，`metadata.clientLabel` 會保存 OAuth 客戶端 ID 和權杖主體（`<client id>:sub:<subject>`），或保存該客戶端 ID 和 `mapAuthInfoToUser` 返回的使用者 ID（`<client id>:user:<user id>`）。若兩者皆無，則保存客戶端 ID 和權杖雜湊值的首 8 個字元（`<client id>:token:<hash prefix>`）。標籤只供除錯。伺服器只會用身分主體的雜湊值配對調用方。

### 崩潰後恢復 {/* #recovery-after-a-crash */}

執行任務的實例停止後，另一個實例會在下次掃描時發現該任務。若原實例崩潰，須等任務的租約屆滿才可偵測到。若原實例正常關閉並交還租約，下次掃描便可發現。每個已啟用背景任務並註冊了該伺服器的 Mastra 實例都會掃描，無論是否曾處理任務請求。將任務保存在記憶體或未註冊該伺服器的實例不會掃描。接下來的處理方式取決於 `recover`：

* `recover: false`（預設）會使任務以 `failed` 結束，並附上 `task lost: the server restarted while it was running`。`execute` 絕不會執行第二次。
* 設為 `recover: true` 時，另一個實例會從頭重跑 `execute` 一次。只應為可安全重複執行的 Tool 啟用此設定。

設為 `recover: true` 時，若某次嘗試因 Tool 以外的原因失敗，亦適用同一次重試機會，例如任務在記錄自己需要輸入時寫入儲存區失敗。若錯誤來自 Tool 本身，便不會重試，任務會以帶有 `isError` 的結果結束。

`recover` 不影響正在等候輸入的任務。無論採用哪個設定，只要回覆輸入請求，任何實例都可恢復該任務。

### 追蹤 {/* #tracing-1 */}

每個任務都有一條 Trace。建立任務的 `tools/call` 是該 Trace 的根追蹤區段，任務一開始，根區段便會正常結束。Tool 的每次執行都會在根區段下建立一個 `task attempt <tool> #<n>` 區段，包括在其他實例上恢復或重試的執行。Tool 自身的區段會置於相應的嘗試區段下。`tasks/update` 和 `tasks/cancel` 請求會加入同一條 Trace。`tasks/get` 的輪詢不會被追蹤。

同一做法適用於 `run_<workflow>` 和 `ask_<agent>` 任務。Workflow 任務的執行區段位於首次嘗試區段下，在 `'auto'` 模式下則直接位於根區段下。每次透過 `tasks/update` 恢復的執行都會置於恢復該次執行的嘗試區段下，適用於任何實例。Agent 任務的 `agent run` 區段位於其嘗試區段下。在崩潰後由 Mastra 的 Workflow 恢復功能重新啟動的執行，按設計會建立獨立的 Trace。具備持久執行能力的 Workflow 和 Agent 支援跨崩潰追蹤。任務中負責追蹤重新啟動執行的嘗試，仍會留在該任務的 Trace。

追蹤區段的中繼資料會記錄任務詳情，包括 `mcpTaskKey`（任務 ID 的 SHA-256 雜湊值）、`attempt`、`resumed`、`recovered` 和 `mcpTaskStatus`。追蹤區段絕不會記錄任務 ID 本身。缺少根區段的 Trace 會從 Trace 清單消失，因此伺服器會在任務開始時立即寫出根區段，確保即使該實例在下次匯出前停止，Trace 仍會列在清單中。各次嘗試會跨實例連續編號，因此即使崩潰前的嘗試區段隨實例遺失，崩潰後恢復的執行仍會顯示為 `#2`。

### 限制 {/* #limits-1 */}

* 若未啟用 Mastra 背景任務，任務會保存在記憶體，並在程序重新啟動時遺失。在多實例部署中，某個任務的每項 `tasks/*` 請求都必須送達建立該任務的實例。可串流的 HTTP 請求會在 `Mcp-Name` 標頭帶上任務 ID，讓負載平衡器據此路由。
* 伺服器回傳任務控制代碼後，才發出的進度和日誌通知會被捨棄。
