# Mastra 類

`Mastra` 類是 Mastra 應用的中央編排器，負責管理 Agent、Workflow、儲存、日誌、可觀測性等。通常只需創建一個 `Mastra` 實例來協調整個應用。

`Mastra` 是頂層註冊表，可在其中註冊需要供整個應用訪問的 Agent、Workflow、工具及其他組件。

## 使用示例 {/* #usage-example */}

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { PinoLogger } from '@mastra/loggers'
import { LibSQLStore } from '@mastra/libsql'
import { weatherWorkflow } from './workflows/weather-workflow'
import { weatherAgent } from './agents/weather-agent'

export const mastra = new Mastra({
  workflows: { weatherWorkflow },
  agents: { weatherAgent },
  storage: new LibSQLStore({
    id: 'mastra-storage',
    url: ':memory:',
  }),
  logger: new PinoLogger({
    name: 'Mastra',
    level: 'info',
  }),
})
```

如果希望通過 Workflow 調度器自動發送延遲通知記錄及通知摘要，請啟用定時通知分發：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'

export const mastra = new Mastra({
  agents: { supportAgent },
  storage,
  notifications: {
    dispatch: {
      enabled: true,
      cron: '*/1 * * * *',
      batchSize: 100,
    },
  },
})
```

`notifications.dispatch.enabled` 允許運行內部通知分發 Workflow，預設 Cron 表達式為 `*/1 * * * *`。分發器從儲存中讀取到期的通知記錄，按 `agentId`、`resourceId` 和 `threadId` 匯總摘要，並通過 Agent 線程運行時發出信號。它不是面向用戶的入口。首次出現延遲通知或摘要通知時，分發計劃及其底層 Workflow 調度器才會延遲啓動；從不延遲通知的應用完全不會運行調度器。

## 方法 {/* #methods */}

### `recoverAllDurableAgents()` {/* #recoveralldurableagents */}

重新驅動所有已註冊持久化 Agent 中處於 `running` 狀態的孤立運行。`recovery.durableAgents` 設為 `'auto'` 時，會在啓動時自動呼叫。也可直接呼叫以手動恢復，或從定時任務中呼叫。

需要持久化儲存。若使用內存儲存，程序重啓後便沒有可恢復的數據。

恢復流程最多同時處理五個 Agent，每個 Agent 最多同時等待五次運行，獨立於 `recovery.workflowConcurrency`。每次內置的 `recoverActiveRuns()` 嘗試，會為 `recover()` 初始化及整個恢復後 Workflow 的結束合計等待最多 30 秒，之後釋放名額供其他運行使用。這些限制約束的是等待，不是仍在執行的任務。它們也不是整個恢復流程的截止時間：發現過程及被覆蓋的自定義恢復方法不受此預算限制。

超時的嘗試會在後台繼續。其結果為 `status: 'skipped'`、`reason: 'recovery-timeout'`，並帶有未來的 `retryAt`。它只計入 `skipped`，不計入 `recovered`、`succeeded` 或 `failed`。Mastra 會自動安排重新檢查，但會等原嘗試結束後再檢查，以免啓動第二次執行。隨後恢復流程會在重試前檢查持久化快照和所有權，並跳過已結束或暫停的運行。遲到的結果不會改變已返回的計數。

開始關閉時，恢復流程不再調度新的 Agent 和運行。恢復遍歷及原有嘗試（包括初始化或執行超時的嘗試）與活躍執行共用同一個關閉排空過程。恢復等待超時不會取消原嘗試，也不會獲得獨立的關閉排空時段。

Mastra 會將運行留在當前執行的控制下，並計入 `skipped`。一旦該執行的所有權聲明可能失效，便會自動重新檢查，使程序崩潰後的恢復無須再次呼叫。`shutdown()` 會取消待執行的重新檢查。參見[運行所有權](/docs/harness/durable-agents#run-ownership)。

```typescript
const result = await mastra.recoverAllDurableAgents()
// { agents: 2, recovered: 3, succeeded: 3, failed: 0, skipped: 1 }
```
