# FactorySandbox

`FactorySandbox` 是主機提供給 `MastraFactory` 的物件，用來描述工作階段的運行位置。它負責建立工作階段 Sandbox、提供工作階段使用的儲存庫範本與用戶可按項目調整的設定 Schema，亦可選擇支援預先建構範本。

Factory 會儲存各項目的設定，並在每次啟動工作階段時傳給 `create`。項目未設定的值會採用 Provider 的預設值。`factory.sandboxDescription` 會列出 Provider、以 JSON Schema 表示的設定 Schema，以及可用功能。Provider 的實作細節都封裝在該物件中：Factory 只調用契約，並讀取 `provider` 供介面顯示。

## 用法 {/* #usage */}

將其中一個 Provider 類別的實例傳入 `sandbox` 選項：

```typescript title="src/mastra/index.ts"
import { MastraFactory } from '@mastra/factory'
import { PlatformFactorySandbox } from '@mastra/platform-workspace'

export const factory = new MastraFactory({
  sandbox: new PlatformFactorySandbox({
    // Provider defaults for an environment that sets nothing.
    defaults: { cpuCount: 4, memoryMb: 8192 },
  }),
})
```

## Provider 類別 {/* #provider-classes */}

| 類別 | 套件 | 設定 | 建構 |
| - | - | - | - |
|`PlatformFactorySandbox` | `@mastra/platform-workspace` | `cpuCount`, `memoryMb`, `idleTimeoutMinutes`, `publicPorts` | `start`, `get` |
| `E2BFactorySandbox` | `@mastra/e2b` | `cpuCount`, `memoryMb`, `idleTimeoutMinutes` | `start`, `get`, `list` |
| `DockerFactorySandbox` | `@mastra/docker` | `baseImage`, `owner` | `start`, `get` |
| `LocalFactorySandbox` | `@mastra/factory` | 無 | 不支援 |

每個 Provider 類別都接受與對應 Sandbox 類別相同的運行時選項，但不包括由該類別按工作階段填入的 `id`、`sandboxId` 和 `template`。此外，亦接受設定儲存庫範本的 `template` 選項，以及為環境中未設定的值指定預設值的 `defaults`。

```typescript
import { PlatformFactorySandbox } from '@mastra/platform-workspace'
import { E2BFactorySandbox } from '@mastra/e2b'
import { DockerFactorySandbox } from '@mastra/docker'
import { LocalFactorySandbox } from '@mastra/factory'

new PlatformFactorySandbox() // reads MASTRA_PLATFORM_ACCESS_TOKEN and MASTRA_ENVIRONMENT_ID
new E2BFactorySandbox() // reads E2B_API_KEY
new DockerFactorySandbox({ defaults: { baseImage: 'node:22-slim' } })
new LocalFactorySandbox() // reads MASTRACODE_LOCAL_SANDBOX_ROOT, defaults to ~/.mastracode/web/sandboxes
```

`LocalFactorySandbox` 會在主機上的 `join(root, sessionId)` 路徑運行每個工作階段。未設定 `env` 時，指令只能存取 `PATH`，以及 git 和 TLS 所需的主機變數允許清單，例如 `HOME`、`USER`、`SHELL` 和 `SSL_CERT_FILE`。因此，在儲存庫檢出目錄運行的指令不會取得應用程式密鑰。

### 將 env 限定於單一 Factory {/* #scope-env-to-one-factory */}

每個 Provider 的 `env` 選項都接受記錄物件，或以工作階段的 `FactorySandboxContext` 為參數的函式。如果同一部署環境託管多個 Factory，而某項憑證只屬於其中一個，請使用函式形式：

```typescript
new PlatformFactorySandbox({
  env: ctx => (ctx.factoryId === PLATFORM_FACTORY_ID ? { PLATFORM_TOKEN } : {}),
})
```

請比較 `factoryId`，而非 `factoryName`：名稱可以修改，也不保證唯一。

Platform 和 Docker 只在建立 Sandbox 時套用 `env`。恢復運行的 Sandbox 會保留啟動時的環境。如果從某些 Factory 移除憑證，請重新建立其運行中的 Sandbox，避免憑證繼續留在其中。

## 預設 Sandbox {/* #default-sandbox */}

如果省略 `sandbox` 選項，並已設定 Platform 憑證（`MASTRA_PLATFORM_ACCESS_TOKEN` 或 `MASTRA_PLATFORM_SECRET_KEY`），`MastraFactory` 會自行設定 Sandbox：

* 執行 `mastra dev` 或設定 `NODE_ENV=development` 時，使用 `LocalFactorySandbox`，因此開發時不會啟動遠端機器。
* 在建構後的部署環境中，使用 `PlatformFactorySandbox`。這需要 `MASTRA_PROJECT_ID` 和 `MASTRA_ENVIRONMENT_ID`；缺少任何一項時，Factory 會記錄警告並停用儲存庫 Sandbox。

明確指定的 `sandbox` 選項一律優先。如果沒有 Platform 憑證，也沒有 `sandbox` 選項，儲存庫 Sandbox 將停用。

對於未設定的值，Provider 會採用自身的預設值：Platform 和 E2B 預設使用 2 個 CPU、1024 MB 記憶體及 5 分鐘閒置逾時，可透過 `defaults` 覆蓋。在 Platform 上，如果 `defaults` 未指定相應值，頂層的 `idleTimeoutMinutes` 和 `publicPorts` 選項亦會生效。`publicPorts` 預設關閉；啟用後，任何取得連接埠 URL 的人都無須登入即可存取。變更此選項只影響之後建立的 Sandbox。Schema 中的 `default` 值會顯示實際生效的預設值。

Platform 會透過啟動建構的建構器輪詢建構狀態。主機重新啟動後，先前建構的狀態會顯示為 `unknown`。

Schema 變更應維持增量相容：新增欄位；重新命名欄位時，在一個發佈版本內同時讀取新舊名稱。已儲存的設定文件可能比寫入它的 Schema 存續更久，因此其中可能包含目前 Schema 不再宣告的鍵，例如主機切換 Provider 後留下的鍵。如果這類鍵導致更新驗證失敗，Factory 會先移除未宣告的鍵並重試，之後才拒絕更新。更新要求本身設定的鍵絕不會被移除。

### 回調形式 {/* #callback-form */}

亦支援直接傳入回調 `sandbox: ctx => new E2BSandbox({ id: ctx.sessionId })`。Factory 會將其包裝成 `provider: 'custom'` 的 Sandbox。Sandbox 的所有細節都留在回調中，環境不會提供可調整的設定。

如要編寫自己的 Provider，請繼承 `@mastra/core/workspace` 中的 `FactorySandbox`。Factory 透過基底類別設定的標記識別子類別，因此不接受結構相同的一般物件。

```typescript
import { FactorySandbox } from '@mastra/core/workspace'
import type { FactorySandboxContext } from '@mastra/core/workspace'
import type { PublicSchema } from '@mastra/core/schema'

interface Settings {
  region?: 'us' | 'eu'
}

class MyFactorySandbox extends FactorySandbox<Settings> {
  readonly provider = 'my-cloud'
  readonly settings: PublicSchema<Settings> = {
    type: 'object',
    properties: { region: { type: 'string', enum: ['us', 'eu'], default: 'us' } },
    additionalProperties: false,
  }

  create(ctx: FactorySandboxContext, settings: Settings) {
    return new MyCloudSandbox({
      id: ctx.sessionId,
      sandboxId: ctx.sandboxId,
      template: this.template(ctx, settings),
      workingDirectory: ctx.workingDirectory,
      region: settings.region ?? 'us',
    })
  }

  // Optional: the sandbox template image Factory can build ahead of time
  template(ctx: FactorySandboxContext, settings: Settings) {
    return myCloudTemplate(ctx, settings)
  }

  // Optional: build that template ahead of time and report on it
  readonly builds = {
    start: async (ctx: FactorySandboxContext, settings: Settings) =>
      myCloud.startBuild(this.template(ctx, settings)),
    get: async (ctx: FactorySandboxContext, settings: Settings, buildId: string) =>
      myCloud.buildStatus(buildId),
    list: async (ctx: FactorySandboxContext, settings: Settings) =>
      myCloud.builds(this.template(ctx, settings).name),
  }
}
```

用戶重新建立卡住的工作階段 Sandbox 時，Factory 可能只傳入 `sessionId` 和已保存的 `sandboxId` 來調用 `create`（沒有儲存庫存取權，設定為空），然後不啟動傳回的 Sandbox，直接調用其 `destroy()`。伺服器重新啟動，或工作階段在另一個副本上開啟時，會出現這種情況。要支援重新建立，`destroy()` 必須能僅憑 `sandboxId` 或工作階段 ID 找到並移除該工作階段的 VM。Factory 不對 `LocalFactorySandbox` 提供重新建立功能，因為它的 `destroy()` 會保留工作階段目錄。

## 建置狀態 {/* #build-status */}

`FactorySandboxBuild.status` 的值為 `pending`、`building`、`ready`、`failed` 或 `unknown`。`unknown` 表示 Provider 無法讀取並非由目前程序啟動的建構狀態。

## 環境建構 {/* #environment-builds */}

Sandbox 宣告 `builds` 後，Factory 會在工作階段啟動前建構環境範本，並透過 `prepare()` 註冊 `factory-environment-build` Workflow。建構會在以下情況執行：

* 調用 `POST /web/factory/projects/:id/environment/build` 時，即在 Environment 頁面點擊 Build now，或執行 `mastra api factory project environment build <project-id>`。
* 按 core 中 `Schedules` 儲存的 cron 排程執行；透過 `PATCH { buildTriggers: { schedule: { enabled: true, cron, timezone } } }` 啟用。需要支援 schedules 網域的儲存配接器，否則路由會回報 `scheduleAvailable: false`。
* 推送至關聯儲存庫的預設分支後，且已設定 `buildTriggers.push.enabled` 時執行；每個 `debounceMinutes` 期間最多執行一次。
* 儲存範本輸入的變更後執行，前提是項目已有範本；建構期間儲存的變更會在該次建構結束後建構。

如果儲存操作沒有改變任何範本輸入，就不會啟動建構。如果上次建構已就緒、儲存庫 HEAD 未變動，且範本輸入（設定、儲存庫及其順序、設定指令、工作目錄或 Factory 的 Build 變數）亦未變動，排程建構及推送觸發的建構都會略過。Factory 只儲存上次建構的 ID 及目前範本。狀態及歷史記錄透過 Provider 的 `GET …/environment/builds/:buildId` 和 `GET …/environment/builds` 取得；如果 Provider 不保留歷史記錄，後者會傳回 404 `no_history`。

如果一次建構的啟動從未被記錄，而 Provider 亦無法列出建構，Factory 就無法判斷該建構是否仍在運行。啟動租約到期後的 30 分鐘內，觸發器會以 `unresolved` 為原因略過；之後 Factory 會將該次啟動視為失敗，由下一次觸發器啟動建構。

## 環境變數 {/* #environment-variables */}

Factory 成員可在 **Settings › Manage Factory › Environment variables** 中，為該 Factory 的每個 Sandbox 新增環境變數。每個變數可套用於以下其中一種範圍：

* **Runtime**：套用於每個工作階段 Sandbox 中的每條指令。新增、編輯或刪除變數後，運行中的 Sandbox 會從下一條指令起使用新值，無須重新啟動。其他 Factory 伺服器會在該 Factory 的 `pubsub` 傳送變更時看到新值；如果未設定跨程序 `pubsub`，則會在一秒內看到。已在運行的程序會保留啟動時的環境。
* **Build**：僅套用於範本建構及 Factory 自行執行的設定指令，不套用於運行時指令。Factory 透過 `buildEnv` 和 `buildEnvRevision` 將變數傳給 Provider。編輯變數後，範本會在下次建構時重新建構。運行中的 Sandbox 不會重新執行設定步驟。新的 Sandbox 會從重建後的範本啟動；範本包含使用新值完成設定後產生的內容，但 Sandbox 自身的指令無法讀取這些變數。在 Docker 上，範本建構目前不會收到 Build 變數，編輯變數亦不會重新建構映像檔，因此只有 Factory 自行執行的設定步驟能讀取它們。
* **Both**：同時套用於 Runtime 和 Build。

如果 Runtime 變數與 Provider 的 `env` 選項中的鍵同名，該變數會覆蓋原值；刪除變數後會還原主機提供的值。Factory 自行設定的名稱（例如 `GH_TOKEN`）為保留名稱。

變數值會使用 Factory 的憑證加密金鑰進行靜態加密，無法透過 API 或 UI 讀回。Sandbox 中運行的任何程式都能讀取這些值。啟用登入但未設定加密金鑰時，Factory 會拒絕儲存變數，設定頁面會說明原因。相關路由為 `GET /web/factory/projects/:id/sandbox-envs`，以及 `PUT`、`PATCH` 和 `DELETE /web/factory/projects/:id/sandbox-envs/:name`。
