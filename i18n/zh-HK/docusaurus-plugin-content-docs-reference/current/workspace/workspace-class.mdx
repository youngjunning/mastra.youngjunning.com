# 工作空間類

**添加於：** `@mastra/core@1.1.0`

這`Workspace` class combines a filesystem and sandbox to provide agents with file storage and command execution capabilities. It also supports BM25 and vector search for indexed content.

## 使用範例 {/* #usage-example */}

```typescript
import { Workspace, LocalFilesystem, LocalSandbox } from '@mastra/core/workspace'

const workspace = new Workspace({
  id: 'my-workspace',
  name: 'My Workspace',
  filesystem: new LocalFilesystem({
    basePath: './workspace',
  }),
  sandbox: new LocalSandbox({
    workingDirectory: './workspace',
  }),
  bm25: true,
  autoIndexPaths: ['docs'],
})
```

## Tool配置 {/* #tool-configuration */}

這`tools` option accepts a `WorkspaceToolsConfig` object that controls which workspace tools are enabled and their safety settings.

```typescript {2,7-16}
import { Workspace } from '@mastra/core/workspace'
import { WORKSPACE_TOOLS } from '@mastra/core/workspace'

const workspace = new Workspace({
  id: 'my-workspace',
  name: 'My Workspace',
  tools: {
    // Global defaults (apply to all tools)
    enabled: true,
    requireApproval: false,

    // Per-tool overrides using WORKSPACE_TOOLS constants
    [WORKSPACE_TOOLS.FILESYSTEM.WRITE_FILE]: {
      requireApproval: true,
    },
  },
})
```

配置物件有兩種類型的設定：

* **全域設定**: `enabled` and `requireApproval` apply to all workspace tools unless overridden. `hooks` and `writeLockTimeoutMs` are global-only and can't be configured per tool.
* **每個Tool覆蓋**： 使用`WORKSPACE_TOOLS` constants as keys to configure individual tools

每個Tool覆蓋接受以下選項：

### Tool名稱重新映射 {/* #tool-name-remapping */}

透過設定重命名WorkspaceTool`name` property on individual tool configs. The config key remains the original constant: only the name exposed to the agent changes.

```typescript {8,9}
import { Workspace } from '@mastra/core/workspace'
import { WORKSPACE_TOOLS } from '@mastra/core/workspace'

const workspace = new Workspace({
  id: 'my-workspace',
  name: 'My Workspace',
  tools: {
    [WORKSPACE_TOOLS.FILESYSTEM.READ_FILE]: { name: 'view' },
    [WORKSPACE_TOOLS.FILESYSTEM.GREP]: { name: 'search_content' },
  },
})
```

Tool名稱在所有WorkspaceTool中必須是唯一的。設定與其他Tool的預設或自訂名稱衝突的自訂名稱會引發錯誤。

### 先讀後寫跟踪 {/* #read-before-write-tracking */}

什麼時候`requireReadBeforeWrite` is enabled, write tools reject changes to files the agent hasn't read. When the agent runs with a memory thread inside a Mastra instance, read records are kept per thread in the `threadState` storage domain, the same store that holds task lists and goal objectives. Records automatically survive suspend/resume cycles (for example, a tool awaiting approval), later turns on the same thread, and process restarts on serverless runtimes when the configured storage adapter persists thread state. No configuration is needed beyond registering the agent with a Mastra instance that has storage.

如果檔案在讀取後在磁碟上發生更改，則寫入仍會被拒絕，直到Agent重新讀取它，並且成功的寫入始終會清除記錄，因此下一次編輯需要重新讀取。每次運行時無需記憶體線程或 Mastra 儲存磁軌讀取即可運行。

讀取記錄的範圍僅限於從中讀取的檔案系統，由檔案系統的提供者和基本路徑標識。沒有基本路徑的檔案系統僅由提供者限定範圍，因此相同提供者實例共用讀取記錄。如果執行緒在請求之間解析不同的檔案系統（例如，根據請求上下文而變化的動態Workspace或檔案系統），則必須在寫入之前在新檔案系統上重新讀取先前讀取的檔案。具有相同配置的檔案系統（例如兩個`LocalFilesystem` instances with the same `basePath`) share read records.

### Tool掛鉤 {/* #tool-hooks */}

放`tools.hooks` to run logic before and after every enabled workspace tool call. Hooks run after name remapping and receive both the exposed `toolName` and the original `workspaceToolName` in their context.

```typescript {6-14}
import { Workspace } from '@mastra/core/workspace'

const workspace = new Workspace({
  id: 'my-workspace',
  tools: {
    hooks: {
      beforeToolCall: ({ toolName, workspaceToolName, input }) => {
        console.log(`Running ${toolName} (${workspaceToolName})`, input)
      },
      afterToolCall: ({ toolName, output, error }) => {
        console.log(`Finished ${toolName}`, { output, error })
      },
    },
  },
})
```

## 方法 {/* #methods */}

### 生命週期 {/* #lifecycle */}

#### `init()` {/* #init */}

初始化Workspace並準備資源。

```typescript
await workspace.init()
```

呼喚`init()` is optional in most cases:

* **Sandbox**：首先自動啟動`executeCommand()` call. Use `init()` to avoid first-command latency.
* **檔案系統**：建立基本目錄並執行任何特定於提供者的設定。某些提供者會在第一次操作時自動建立目錄。
* **搜尋**：僅在使用時才需要`autoIndexPaths` for auto-indexing.

初始化執行：

* 啟動檔案系統提供者（如果需要，建立基底目錄）
* 啟動沙箱提供者（建立工作目錄，如果配置則設定隔離）
* 索引檔案來自`autoIndexPaths` for search

#### `stop()` {/* #stop */}

停止Workspace的即時資源而不破壞它們。

```typescript
await workspace.stop()
```

`stop()`在停止沙箱提供者之前關閉語言伺服器和瀏覽器。遠端Provider暫停或暫停沙箱以便稍後恢復，同時`LocalSandbox` kills background processes and unmounts filesystems. Stopping isn't a teardown. The filesystem and search index remain available along with skills, and the next sandbox operation starts the sandbox again.

`mastra.shutdown()`來電`stop()` for registered workspaces. A process restart suspends remote sandboxes instead of deleting them. To fully tear a workspace down, call `destroy()` or `mastra.removeWorkspace(id, { destroy: true })` explicitly.

#### `destroy()` {/* #destroy */}

摧毀Workspace並清理資源。

```typescript
await workspace.destroy()
```

`destroy()`依序關閉Workspace擁有的資源：語言伺服器、瀏覽器、沙箱提供者和檔案系統提供者。它還清除快取的沙箱引用。

稱呼`destroy()` when your application is done with a workspace and its sandbox. To remove a workspace from the Mastra registry, use [`mastra.removeWorkspace()`](/reference/core/removeWorkspace).

`LocalFilesystem.destroy()`不刪除磁碟上的檔案。解析器支持的文件系统和沙箱提供程序归您的应用程序所有，并且必须由您的应用程序清理。

### 檔案系統Tool {/* #filesystem-tools */}

### 技能Tool {/* #skill-tools */}

配置技能時新增：

|Tool|描述 |
| - | - |
|`skill` | Activate a skill by name or path. Returns the skill's full instructions, references, scripts, and assets. |
