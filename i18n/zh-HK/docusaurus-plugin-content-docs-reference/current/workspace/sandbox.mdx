## 方法 {/* #methods */}

### `start()` {/* #start */}

啟動 Sandbox。呼叫 `workspace.init()` 或首次呼叫 `executeCommand()` 時，會自動執行此方法。

```typescript
const result = await sandbox.start()
// { outcome: 'created' } — a fresh VM was created
// { outcome: 'connected' } — reconnected to an existing VM
// undefined — the provider does not report
```

**返回：** `void | Promise<SandboxStartResult | void>`

如建構 Sandbox 時提供了已知的 `id`，`start()` 會解析該 ID：已有 Sandbox 則重新連線或恢復，否則建立一個（取得或建立）。支援此機制的 Provider 會回傳 `SandboxStartResult`：

<PropertiesTable
  content={[
{
  name: 'outcome',
  type: "'created' | 'connected'",
  description:
    "建立全新的 Sandbox 虛擬機器（或工作目錄）時為 `'created'`；重新連線或恢復現有執行個體時為 `'connected'`。",
},
]}
/>

在此契約引入前實作的 Provider 會回傳 `void`，基底類別會將結果視為未知。

Provider 可按以下優先次序選擇一種方式實作啟動生命週期。基底類別負責處理並行啟動呼叫、狀態管理、`onStart` 鉤子及掛載作業：

1. **取得原語**：實作受保護的 `find()`（按邏輯 ID 查詢，不產生副作用，回傳 Provider 原生控制代碼或 `undefined`）、`connect(handle)`（喚醒、恢復或接管）及 `create()`（建立新執行個體），無須覆寫 `start()`。基底類別執行 find → connect → `{ outcome: 'connected' }`；找不到時則執行 create → `{ outcome: 'created' }`。結果由實際執行的分支決定。`E2BSandbox`、`DaytonaSandbox` 及 `LocalSandbox` 採用此方式。
2. **覆寫 `start()` 並回傳 `SandboxStartResult`**：適用於 Provider API 將取得與建立合為一次呼叫、拆開後會增加請求往返次數的情況（`PlatformSandbox`、`RailwaySandbox`）。
3. **覆寫 `start()` 並回傳 `void`**：適用於舊版 Provider，啟動結果未知。

同一執行個體上的並行 `start()` 呼叫會合併為一次啟動嘗試，所有呼叫方共用其結果（如該次嘗試建立了虛擬機器，所有呼叫方都會看到 `outcome: 'created'`）。嘗試結束後會清除進行中的記錄，因此啟動失敗後可以重試。對於已處於 `running` 狀態的 Sandbox，`start()` 會直接回傳 `{ outcome: 'connected' }`，不會再次呼叫 Provider。

啟動結果亦會以 `{ sandbox, outcome }` 的形式傳給 `onStart` 生命週期鉤子。

### `onStart`（建構函式選項） {/* #onstart-constructor-option */}

`onStart` 在啟動生命週期內執行：此時 Sandbox 已達到 `running` 狀態，但待處理的掛載尚未執行。無論是明確呼叫、指令觸發的延遲 `ensureRunning()`，或 Provider 更換虛擬機器後的恢復，每次啟動都會觸發此鉤子。可用它完成每部虛擬機器的初始化，並按 `outcome` 判斷要執行初始化，還是確認初始化已完成。

```typescript
new E2BSandbox({
  id: sessionId,
  onStart: async ({ sandbox, outcome }) => {
    if (outcome === 'created') {
      // Fresh VM: run the full setup.
      await runSetup(sandbox)
      return
    }
    // Reconnected: probe, and self-heal if setup never completed.
    const probe = await sandbox.executeCommand('test -d ~/repo/.git')
    if (probe.exitCode !== 0) await runSetup(sandbox)
  },
})
```

語意：

* 鉤子拋出的錯誤會令啟動失敗：`start()` 會以該錯誤拒絕，Sandbox 狀態變為 `error`。呼叫方不會看到初始化鉤子失敗卻仍在執行的 Sandbox。失敗不會被鎖定；下次 `start()`（包括下一個延遲指令觸發的啟動）會重試鉤子。`onStop` 及 `onDestroy` 仍是非致命的觀察鉤子，因為清理作業會盡力繼續。
* `outcome` 用於區分啟動路徑：`'created'` 表示此次啟動建立了新虛擬機器，應執行初始化；`'connected'` 表示重新連線或恢復，初始化通常已完成。如鉤子需處理建立後、初始化完成前發生的當機，此時應先探測狀態。`undefined` 表示 Provider 未回報結果。
* 保持初始化作業的冪等性。探測結果顯示需要初始化時，鉤子可能再次執行；從檢查點恢復的新虛擬機器會回報 `outcome: 'created'`。
* Sandbox 會在鉤子執行前變為 `running`，讓鉤子透過 Sandbox 自身的指令路徑執行指令。因此，經 `ensureRunning()` 並行發出的指令可能與鉤子交錯執行。等待原始 `start()` 呼叫完成的呼叫方，則一定會看到鉤子已執行完畢。
* 鉤子在待處理的檔案系統掛載執行前運作，因此不能依賴已掛載的路徑。

### `setOnStart(update)` {/* #setonstartupdate */}

在建構之後附加啟動鉤子，供執行階段接收並非由自身建構的 Sandbox 使用。否則，每個建構 Sandbox 的宿主都必須接收鉤子並傳給 Provider 建構函式；如有宿主忘記傳遞，初始化就會悄然缺失。

更新函式接收目前已安裝的鉤子（可能來自建構函式的 `onStart` 選項，也可能由先前呼叫安裝），並回傳要安裝的鉤子。如此組合鉤子，就不會無意間捨棄呼叫方不知道的現有鉤子：

```typescript
sandbox.setOnStart?.(previous => async args => {
  await previous?.(args) // whatever prepared the sandbox runs first
  await mySetup(args)
})
```

語意：

* 與建構函式選項一樣，錯誤仍會令啟動失敗。各鉤子依次等待前一個鉤子，因此某個鉤子拋錯後，後續鉤子不會執行。
* 呼叫方決定執行次序。如自己的鉤子依賴 `previous` 準備的 Workspace，就先等待 `previous`；如自己的鉤子負責準備工作，就最後執行 `previous`。
* 忽略 `previous` 會取代已安裝的鉤子。此行為受到支援，可用於接管執行階段安裝的初始化邏輯。
* 每次呼叫都會包裝目前的鉤子，因此每個 Sandbox 執行個體只應附加一次。如在每個請求都會經過的路徑上附加鉤子，每次啟動都會重複執行累積的作業。
* 新鉤子只對呼叫之後開始的啟動生效。

### `workingDirectory`（建構函式選項） {/* #workingdirectory-constructor-option */}

設定執行指令及啟動程序時的預設目錄。如指令未指定自己的 `cwd`，Sandbox 就從此目錄執行；指令指定的 `cwd` 一律優先。如兩者都未指定，則使用各 Provider 的預設目錄（例如 E2B 主目錄、Docker 的 `/workspace` 或 Vercel Serverless 的 `/tmp`）。

```typescript
const sandbox = new E2BSandbox({ workingDirectory: '/home/user/my-repo' })
await sandbox.executeCommand('pwd') // /home/user/my-repo
await sandbox.executeCommand('pwd', [], { cwd: '/tmp' }) // /tmp
```

可透過 `sandbox.workingDirectory` getter 讀取實際生效的目錄。Daytona 自動探測所得的目錄、Docker 預設的 `/workspace` 等由 Provider 計算出的目錄，亦會透過同一 getter 回傳。

語意：

* 此值會原樣傳給 Provider，Sandbox 不會建立目錄。建議使用絕對路徑；以 `~` 開頭的路徑只在 Provider 明確支援展開時才有效。
* 部分 Provider 保留指向同一欄位的舊選項名稱，現已棄用：Docker 及 Apple container 使用 `workingDir`，Modal 使用 `workdir`。如同時設定舊選項與 `workingDirectory`，以後者為準。

### `stop()` {/* #stop */}

停止 Sandbox。

```typescript
await sandbox.stop?.()
```

### `destroy()` {/* #destroy */}

清理 Sandbox 資源。`workspace.destroy()` 會呼叫此方法。

```typescript
await sandbox.destroy()
```

### `snapshot()` {/* #snapshot */}

如 Provider 支援快照，則儲存 Sandbox 的目前狀態。其他 Provider 會直接回傳，不執行任何操作。

```typescript
await sandbox.snapshot()
```

**返回：** `Promise<void>`

### `setEnv(update)` {/* #setenvupdate */}

更新 Sandbox 的執行階段環境。這些變數會合併到 Sandbox 執行的每條指令中，包括透過 `executeCommand()` 及 `processes.spawn()` 啟動的指令。因此，在建構 Sandbox 後新增或輪換的憑證亦會用於後續指令。此方法為選用，請先檢查是否支援，或使用可選鏈呼叫。

```typescript
sandbox.setEnv?.(env => ({ ...env, GH_TOKEN: token }))
```

更新函式接收目前環境的副本，並回傳取代後的環境，因此一次呼叫即可設定、移除或批次更新變數。刪除某個鍵只會將其從 Sandbox 的執行階段環境中移除；Provider 自行提供的同名變數仍可能生效。初始值可透過建構函式的 `env` 選項設定。

執行階段環境作用於透過 Sandbox 執行的指令，而非虛擬機器本身的環境，因此不會寫入虛擬機器，並且在 Provider 暫停、恢復後仍會保留。執行指令時，先套用 Provider 的預設值，再由 Sandbox 的執行階段環境覆寫；`executeCommand()` 單次呼叫的 `env` 選項優先次序最高。

### `getEnv()` {/* #getenv */}

此方法可用於 `MastraSandbox`，但未在 `WorkspaceSandbox` 介面中宣告。它會回傳 Sandbox 目前執行階段環境的副本；修改回傳的物件不會改變 Sandbox，請使用 `setEnv()` 更新環境。

```typescript
const token = sandbox.getEnv().GH_TOKEN
```

**返回：** `Record<string, string | undefined>`

const info = await sandbox.getInfo()

## 原生檔案系統 {/* #native-filesystem */}

如 Provider 提供檔案 API，Sandbox 會透過選用的 `filesystem` 屬性將其提供出來。讀取、寫入及列出檔案各只需一次請求；透過 `executeCommand()` 完成相同操作時，每一步都需要執行一條指令。路徑必須是 Sandbox 內的絕對路徑。

路徑範圍由 Provider 負責控制：`filesystem` 本身不會將路徑或符號連結限制在 Workspace 根目錄內。如沒有此屬性，可改用 `executeCommand()`：

```typescript
const pkg = sandbox.filesystem
  ? await sandbox.filesystem.readFile('/workspace/app/package.json', { encoding: 'utf-8' })
  : (await sandbox.executeCommand?.('cat', ['/workspace/app/package.json']))?.stdout
```

`E2BSandbox` 一律提供 `filesystem`。對於 `PlatformSandbox`，只有使用 `e2b` Provider 時才提供此屬性；其他情況會回傳 `undefined`。如要在 Workspace 中使用，可明確將其傳入 Workspace 的 `filesystem`，亦可直接呼叫。

## 電腦操作功能 {/* #computer-capability */}

具有可控制桌面環境的 Sandbox 會透過 `computer` 屬性實作選用的 `SandboxComputer` 介面。如靜態設定的 Sandbox 提供此屬性，Workspace 工具工廠會自動註冊 `mastra_workspace_computer_*` 工具。請參閱[電腦操作工具](/docs/sandbox/computer#computer-tools)。

座標以螢幕左上角為原點，單位為像素。Provider 會將各自 SDK 的語意（例如按鍵名稱、捲動單位）統一到此介面，並透過自身的存取器提供更豐富的原生 API。
