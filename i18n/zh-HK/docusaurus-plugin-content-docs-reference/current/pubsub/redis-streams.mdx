# RedisStreamsPubSub

`RedisStreamsPubSub` 是依據 [`PubSub`](/reference/pubsub/base) 契約、以 [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/) 為底層的實作。它可跨程序及主機傳送事件，支援持久儲存、消費者群組及失敗後重新投遞，亦實作了 [`LeaseProvider`](/reference/pubsub/lease-provider)。訊號層可跨執行個體為每項資源選出唯一持有者，讓分散式及無伺服器部署能協調執行工作。

多個服務共用事件串流的分散式部署適合使用此實作。單一程序內傳送事件可使用 [`EventEmitterPubSub`](/reference/pubsub/event-emitter)；Google Cloud 環境可使用 [`GoogleCloudPubSub`](/reference/pubsub/google-cloud-pubsub)。

每個主題對應一個 Redis Stream 鍵。指定群組的訂閱會使用 Redis 消費者群組，由成員輪流處理事件；沒有指定群組的訂閱則建立專用消費者群組，讓每位訂閱者都收到全部事件。

`RedisStreamsPubSub` 採用拉取式傳輸：消費者透過 `XREADGROUP` 讀取事件，因此 Mastra 會啟動編排 worker 代為讀取。

## 安裝 {/* #installation */}

```bash npm2yarn
npm install @mastra/redis-streams
```

需要 Redis 7.0 或以上版本。回收循環依賴 `XCLAIM` 從待處理清單移除已修剪的項目；較舊版本不會這樣做。

## 使用範例 {/* #usage-example */}

提供 Redis 連線 URL。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'

export const mastra = new Mastra({
  pubsub: new RedisStreamsPubSub({
    url: 'redis://localhost:6379',
  }),
})
```

### Redis 叢集 {/* #redis-cluster */}

連接 Redis 叢集（例如啟用叢集模式的 AWS ElastiCache）時，請傳入 `cluster`，而非 `url`/`redisOptions`。選項會轉交 `createCluster()`（来自 `redis`）。

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { RedisStreamsPubSub } from '@mastra/redis-streams'

export const mastra = new Mastra({
  pubsub: new RedisStreamsPubSub({
    cluster: {
      rootNodes: [{ url: 'redis://node-1:6379' }, { url: 'redis://node-2:6379' }],
    },
  }),
})
```

### 使用自行建立的客戶端 {/* #bring-your-own-client */}

如需自行控制客戶端的建立方式（例如 TLS 或憑證提供者），請把尚未連接的 `redis` 客戶端傳入 `client`。PubSub 會用它寫入資料，並為每項訂閱呼叫 `client.duplicate()` 建立獨立的阻塞讀取連接。PubSub 會管理客戶端的生命週期：首次使用時連接，呼叫 `close()` 時結束。因此不要與應用程式其他部分共用。

```typescript title="src/mastra/index.ts"
import { RedisStreamsPubSub } from '@mastra/redis-streams'
import { createClient } from 'redis'

const pubsub = new RedisStreamsPubSub({
  client: createClient({ url: process.env.REDIS_URL, socket: { tls: true } }),
})
```

## 方法 {/* #methods */}

`RedisStreamsPubSub` 實作 [`PubSub`](/reference/pubsub/base) 契約。以下方法的行為專屬於此實作。

### `subscribe(topic, cb, options?)` {/* #subscribetopic-cb-options */}

訂閱主題。指定 `options.group` 時，群組成員會透過 Redis 消費者群組分擔事件；沒有指定時，訂閱者會透過專用消費者群組收到每個事件。

建立 Redis 消費者群組時，把 `options.startFrom` 設為 `"latest"` 可略過保留的舊項目。預設值 `"earliest"` 會先讀取舊項目。此選項不會重設現有群組的處理進度。
等待進行中的發佈操作完成。
```typescript
await pubsub.subscribe(
  'workflow.events',
  (event, ack, nack) => {
    console.log(event)
  },
  { group: 'live-workers', startFrom: 'latest' },
)
```

### `flush()` {/* #flush */}



```typescript
await pubsub.flush()
```

### `clearTopic(topic)` {/* #cleartopictopic */}

刪除主題的 Stream 及其所有消費者群組，釋放已結束主題佔用的記憶體。Mastra 的執行週期（持久化 Agent 及事件驅動 Workflow 引擎）會在工作進入終止狀態時自動呼叫。只有確定不會再有讀取者時才自行呼叫。此操作會盡力完成，而且不會拋出例外；失敗會以 warn 級別記錄。刪除 Stream 時仍在訂閱的客戶端可自行恢復，但會錯過已刪除的項目。

自動清理要求 `@mastra/core` 和 `@mastra/redis-streams` 均使用支援 `clearTopic` 的版本。執行時會經快取層轉送呼叫，因此須同時升級兩個套件，才能在工作結束時刪除 Stream。

並非所有主題都會呼叫 `clearTopic`。每段對話的 Stream、應用程式動態等沒有明確終點的主題不會自動清理；如果清理未執行（例如工作崩潰），亦不會重試。預設 7 天的 `streamIdleTtlMs` 滑動 TTL 會在閒置後回收這些 Stream。刪除討論串時，`Memory.deleteThread()` 亦會清理相關 Stream。

```typescript
await pubsub.clearTopic('workflow.events.run-123')
```

### `trimTopic(topic, { runId, producedBefore? })` {/* #trimtopictopic--runid-producedbefore- */}

使用 `XRANGE` 分頁掃描 Stream，並執行 `XDEL` 刪除每個由 `runId` 發佈的項目。指定 `producedBefore` 時，只刪除在該時間或之前產生的項目，略過審批及暫停提示。Mastra 每次儲存長時間執行的訊息時都會用此方法修剪 Stream；討論串工作的訊息完成持久儲存後亦會呼叫，讓閒置討論串的 Stream 清空，而非增長至 `maxLen`。由於按 `runId` 配對，重新啟動後恢復的工作亦會移除重啟前發佈的項目。其他工作（包括其他程序）的項目不受影響。操作會盡力執行；失敗以 warn 級別記錄。

```typescript
await pubsub.trimTopic('agent.thread.thread-abc', { runId: 'run-123' })
```

### `close()` {/* #close */}

關閉 Redis 連線並停止所有訂閱。在正常關閉期間呼叫此方法。

```typescript
await pubsub.close()
```

## Redis 設定 {/* #redis-configuration */}

請把 Redis 執行個體的 `maxmemory-policy` 設為 `noeviction`。消費者群組、未確認的項目及[租約鍵](#distributed-leasing)屬於即時狀態，不能當作快取。使用任何逐出策略時，Redis 達到 `maxmemory` 便可能刪除它們：`volatile-*` 策略可能逐出有 TTL 的租約鍵及 Stream，`allkeys-*` 策略則可能逐出所有鍵。租約遺失會令兩個程序同時執行同一討論串；Stream 遭逐出會在沒有提示下丟失事件。

使用 `noeviction` 時，記憶體耗盡後 Redis 會拒絕寫入，而非刪除資料。請按流量設定足夠的 `maxmemory`，並以 `streamIdleTtlMs` 回收閒置 Stream。託管服務常預設採用逐出策略（Amazon ElastiCache 預設為 `volatile-lru`），因此要明確檢查設定。

如果已設定 `maxmemory`，但策略不是 `noeviction`，`RedisStreamsPubSub` 會在首次連接後記錄一次警告。它透過 `INFO memory` 讀取策略，因為不少託管服務會封鎖 `CONFIG GET`。

```bash
redis-server --maxmemory-policy noeviction
```

### 回收建立時沒有 TTL 的 Stream {/* #reclaim-streams-created-without-a-ttl */}

在 `streamIdleTtlMs` 為 `0` 時寫入的 Stream（包括引入預設 7 天 TTL 之前的版本所寫入的）沒有 TTL。它們會一直留在 Redis，直到有新寫入為其設定 TTL。請按以下步驟回收：

1. 先把執行個體切換至 `noeviction`。在 `volatile-*` 策略下，為使用中的 Stream 加上 TTL 會令它可能被逐出。
1. 把所有寫入此 Redis 的程序升級至預設啟用 TTL 的版本，或明確設定`streamIdleTtlMs` 大於 `0`。關閉到期功能的寫入不會更新現有 TTL；若舊版程序仍在使用 Stream，它可能在使用途中過期。
1. 為每個沒有 TTL 的 Stream 設定原本應有的到期時間：最後一次寫入後 7 天。閒置超過 7 天的 Stream 會立即過期並釋放記憶體。即使執行個體因記憶體耗盡而拒絕寫入，`PEXPIRE` 仍可執行。

```bash
# Replace mastra:topic with your keyPrefix, and add your connection flags
# (-h, -p, -a, --tls) to every redis-cli call. On a cluster, run it against each primary.
TTL_MS=604800000
NOW_MS=$(redis-cli time | awk 'NR == 1 { s = $1 } NR == 2 { printf "%.0f", s * 1000 + $1 / 1000 }')
redis-cli --scan --pattern 'mastra:topic:*' | while read -r key; do
  [ "$(redis-cli type "$key")" = "stream" ] || continue
  [ "$(redis-cli pttl "$key")" = "-1" ] || continue
  last_ms=$(redis-cli --raw xinfo stream "$key" | awk 'prev == "last-generated-id" { split($0, id, "-"); print id[1]; exit } { prev = $0 }')
  [ -n "$last_ms" ] || continue
  if [ "$last_ms" = "0" ]; then
    remaining=$TTL_MS # never written to, only subscribed
  else
    remaining=$(( TTL_MS - (NOW_MS - last_ms) ))
    [ "$remaining" -lt 1 ] && remaining=1
    [ "$remaining" -gt "$TTL_MS" ] && remaining=$TTL_MS
  fi
  redis-cli pexpire "$key" "$remaining" > /dev/null
done
```

循環只處理沒有 TTL 的 Stream，因此可重複執行。完成第 2 步後，仍在使用的 Stream 每次寫入都會更新 TTL，資料便會保留。

## 重新投遞及回收 {/* #redelivery-and-reclaim */}

訂閱者呼叫 `nack` 時，事件會以遞增的 `deliveryAttempt` 重新發佈，原事件則獲確認。達到 `maxDeliveryAttempts` 後，事件會被丟棄，不再重新投遞。此外，每項訂閱會定期回收群組中先前消費者已讀取但未確認的事件；頻率及閒置時間由 `reclaimIntervalMs` 和 `reclaimIdleMs` 控制。

訂閱不會回收其處理器仍在處理的事件，因此處理緩慢不會令同一事件在該處理器上執行兩次。若處理器卡住，群組內其他消費者可在事件閒置達 `reclaimIdleMs` 後回收。只有一名消費者的群組沒有其他成員，因此應設定 `inFlightTimeoutMs`，讓訂閱在逾時後自行對事件執行 nack。

### 事件驅動 Agent 的 worker 接手 {/* #evented-agent-worker-takeover */}

使用 Postgres 儲存時，分散式事件驅動 Agent 會透過 Redis 發佈 worker 編排事件。若 worker 在確認事件前退出，其他 worker 可回收事件並完成工作，而原 API 程序仍保持運作。API 程序應設定 `MASTRA_WORKERS=false`，worker 程序則設定 `MASTRA_WORKERS=orchestration`。所有程序必須共用同一個 Postgres 資料庫、Redis 連接設定及 `keyPrefix`。

`reclaimIdleMs` 應保持在 30 秒以上（預設為 60 秒）。設得過低時，已停止的 worker 仍持有步驟，事件卻可能被回收，結果事件獲確認但沒有執行。

舊版本啟動的工作升級後仍可完成，但不保證崩潰後能恢復。沒有 occurrence 識別碼的已儲存步驟，仍沿用原有的未受保護行為。其他儲存配接器仍由 worker 程序負責分散式內部編排。

中斷的步驟可能再次執行，因此外部副作用應具備冪等性。已完成的步驟 occurrence 可免受過時的重新投遞影響；已完成的循環迭代會重用已儲存的結果和循環決定。即使 `shouldPersistSnapshot` 傳回 `false`，受保護的執行仍會持久儲存恢復所需的紀錄。恢復、時間旅行、重新啟動時的競態及個別 `foreach` 項目，均不受這些 occurrence 保護。Agent 工具請參閱[讓工具可安全重複執行](/docs/harness/durable-agents#make-tools-safe-to-repeat)。

## 分散式租賃 {/* #distributed-leasing */}

`RedisStreamsPubSub` 透過同一 Redis 連接實作 [`LeaseProvider`](/reference/pubsub/lease-provider) 契約。[訊號執行環境](/docs/signals/overview)利用它選出唯一持有者（通常按討論串鍵），確保跨執行個體只有一個程序喚醒並執行 Agent，其他程序則把後續工作交給持有者。共用租約讓訊號可在無伺服器及多執行個體部署中運作；沒有共用租約時，每個執行個體都會啟動互相競爭的工作。

租約鍵與主題共用 `keyPrefix` 命名空間，格式為 `<keyPrefix>:lease:<key>`。所有操作均具原子性：`acquireLease` 使用 `SET NX PX`，並以冪等方式更新自身 TTL；`releaseLease`、`renewLease` 及 `transferLease` 則使用先核對持有權再修改的 Lua 指令碼，因此不會覆蓋另一持有者同時進行的續約。

無須直接呼叫這些方法。只要把 `RedisStreamsPubSub` 設為 `pubsub` 後端，執行環境便會偵測並使用這項功能。完整方法契約請參閱 [`LeaseProvider`](/reference/pubsub/lease-provider)。
