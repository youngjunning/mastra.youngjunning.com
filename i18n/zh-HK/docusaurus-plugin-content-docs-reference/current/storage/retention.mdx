# 儲存保留

由於儲存預設情況下無限增長，Mastra 提供了一個可選擇加入的、基於年齡的保留系統。聲明每個表`maxAge`的政策`retention`配置，然後調用`storage.prune()`刪除早於其配置年齡的行。未配置的資料將永久保留，因此在您選擇加入之前，行為不會改變。

`prune()`

固定蓋**growth tables** only: tables that accumulate rows unbounded as a side effect of normal operation (conversation history, telemetry, job and run records, schedule fire history, event feeds). User-authored artifacts and config (agents, skills, workspaces, prompt blocks, datasets, schedule definitions, channel installations, and so on) grow with user intent and are edited or deleted explicitly, so they're not valid retention keys.

儲存適配器使用共享核心保留合約`prune()`, or a database-native mechanism when that better matches the backend.

|適配器|機制|保留支援|

| DuckDB | `prune()` | Observability spans, metrics, logs, scores, and feedback |

## 時間表修剪 {/* #schedule-pruning */}

跑步`prune()` from a scheduler or maintenance worker, not from application startup or shutdown hooks. For deployments that share a database, prefer a single active scheduler or worker for pruning.

修剪大型表時優先選擇流量較低的時段。使用`maxBatches`, `maxRows`, and `pauseMs` to bound each run, and pass an `AbortSignal` when the maintenance process needs to stop promptly. These recommendations apply to adapters that expose `prune()`. ClickHouse applies its native time to live (TTL) policy within the database.

## 使用範例 {/* #usage-example */}

宣告`retention` on any `MastraCompositeStore` (or an adapter that extends it, such as `LibSQLStore`), then call `prune()` from your own scheduler.

```typescript title="src/mastra/index.ts"
import { LibSQLStore } from '@mastra/libsql'

const storage = new LibSQLStore({
  id: 'mastra-storage',
  url: 'file:./mastra.db',
  retention: {
    memory: {
      messages: { maxAge: '30d' },
      threads: { maxAge: '90d', batchSize: 500 },
    },
    observability: {
      spans: { maxAge: '7d' },
    },
  },
})

// Wire this to your own cron/scheduler: Mastra never runs it for you.
const results = await storage.prune()
```

`retention`已完全鍵入。域鍵必須存在，並且它們的表鍵必須聲明為具有保留資格。儲存配置類型檢查直接傳遞的物件。單獨建構物件時，使用`satisfies RetentionConfig` so unknown domains or tables produce compile errors:

```typescript
import type { RetentionConfig } from '@mastra/core/storage'

const retention = {
  memory: {
    messages: { maxAge: '30d' }, // ok
    bogus: { maxAge: '30d' }, // Error: not a memory retention table
  },
  bogusDomain: {}, // Error: not a storage domain
} satisfies RetentionConfig
```

### 符合保留資格的表 {/* #retention-eligible-tables */}

每個域指定其年齡可修剪表和錨定比較的時間戳列，如此選擇`maxAge` matches the meaning of the data. Append-only logs use creation time, live state uses last activity, and jobs or runs use completion time so in-flight work isn't pruned.

|網域 |表鍵|錨柱|`maxAge` measures |
| - | - | - | - |
| `memory` | `threads` | `createdAt` | Thread age |
| `memory` | `messages` | `createdAt` | Message age |
| `memory` | `resources` | `createdAt` | Resource age |
| `memory` | `runFences` | `retiredAt` | Time since the durable agent execution holding the fence settled. Fences of running executions (`NULL`) are never pruned |
| `threadState` | `threadState` | `updatedAt` | Inactivity: state for still-active threads survives |
| `observability` | `spans` | `startedAt` | Span age |
| `observability` | `metrics` | `timestamp` | Metric event age (vNext only) |
| `observability` | `logs` | `timestamp` | Log event age (vNext only) |
| `observability` | `scores` | `timestamp` | Score event age (vNext only) |
| `observability` | `feedback` | `timestamp` | Feedback event age (vNext only) |
| `scores` | `scorers` | `createdAt` | Score record age |
| `workflows` | `workflowSnapshot` | `updatedAt`|不活動、暫停或長時間運行的Workflow仍然存在 |
|`workflows` | `runOwnership` | `updatedAt`|不活動。正在運行的持久Agent執行每 10 秒更新一次其聲明，因此請保持`maxAge`遠高於其 30 秒租約 |
|`backgroundTasks` | `backgroundTasks` | `completedAt`|完成後的時間，正在進行的任務（`NULL`) 永远不会被修剪 |
|`experiments` | `experiments` | `completedAt`|自完成以來，正在運行的實驗從未被刪減|
|`notifications` | `notifications` | `createdAt`|通知年齡 |
|`harness` | `sessions` | `createdAt`|會話記錄年齡 |
|`schedules` | `triggers` | `actual_fire_at`|火史年代（epoch-ms專欄）|

：：：筆記

* 記憶`observational_memory` table has no timestamp anchor, so it can't be age-pruned and isn't a valid retention key.
* 實驗作為整個單元進行修剪：老化實驗的結果行將與其一起刪除（結果與其父級級聯），因此運行永遠不會部分刪除。保留沒有單獨的`results` key.
* `runOwnership`和`runFences` hold the run fencing records of durable agents, one small record per run in each. If the `runOwnership` `maxAge` is too short, a running execution can lose its run, but an execution that lost a run still can't write. A fence is retired only when its execution settles, so the fence of a run that crashed and was never recovered is never pruned.
* 為了`schedules`, the growth table is the fire history (`schedule_triggers`, one row per fire): schedule definitions are config and aren't pruned.
* 在 PostgreSQL 上，時間戳記錨點使用時區感知鏡像列（例如`createdAtZ`, `completedAtZ`).
* DuckDB 可觀察性儲存所有五個訊號的僅附加事件。它是`spans` policy uses the event `timestamp` column rather than `startedAt`.
* LibSQL 和 PostgreSQL 支援上述所有域，除了`harness`, which PostgreSQL doesn't implement. MongoDB supports all except `threadState` and `harness`. DuckDB, MySQL, Microsoft SQL Server, Oracle Database, Amazon Aurora DSQL, and Google Cloud Spanner currently support retention only in their `observability` domains, with the signal coverage shown in the support matrix.
* vNext PostgreSQL Observability域將訊號事件儲存在按天分區的表中（`spans`, `metrics`, `logs`, `scores`, `feedback`). For it, `prune()` drops whole day partitions (or TimescaleDB chunks) that are entirely older than the cutoff instead of deleting rows: effective level of detail is one day, and a partition is only dropped once its entire day is past `maxAge`. `PruneResult.deleted` reports the number of rows in the dropped partitions.

## 方法 {/* #methods */}

### 保留 {/* #retention */}

#### `prune(options?)` {/* #pruneoptions */}

刪除早於其配置的行`maxAge` across every domain that has a policy in `retention`. Returns one `PruneResult` per table touched. With no `retention` configured it's a no-op returning `[]`.

`prune()`設計為在具有數百萬行的表上是安全的。它以有界的、批量的區塊進行刪除（每個批次都是它自己的事務），因此它永遠不會需要長時間的鎖定或使交易日誌膨脹。它從不運行`VACUUM`.

經過`options.retention` to replace the configured policies for that call only: for example to skip a domain (keep chat history) or prune more aggressively than the standing config. The store's configured `retention` is unchanged.

使用錨列索引的適配器在第一個索引上延遲建立它們`prune()` call for each table with a policy (never at `init()`) so deployments that don't configure retention pay no extra index write or disk overhead. The first prune of an existing large table pays a one-time index build. Subsequent prunes reuse the index. DuckDB uses its built-in zone maps instead of creating retention indexes.

```typescript
const results = await storage.prune({
  maxRows: 50_000, // cap work this call
  pauseMs: 50, // breathe between batches
})

for (const r of results) {
  console.log(`${r.domain}.${r.table}: deleted ${r.deleted}, done=${r.done}`)
}

// One-off pass with different policies (configured retention untouched):
await storage.prune({
  retention: {
    observability: { spans: { maxAge: '1d' } },
  },
})
```

返回：`Promise<PruneResult[]>`

##### 修剪結果 {/* #pruneresult */}

每個結果描述一個表格的進度：

```typescript
interface PruneResult {
  domain: string // e.g. 'memory'
  table: string // physical table name, e.g. 'mastra_messages'
  deleted: number // rows deleted during this call
  done: boolean // false => eligible rows remain; call prune() again
}
```

## 按計劃運行修剪 {/* #running-prune-on-a-schedule */}

`prune()`沒有內建調度程序，因此您可以決定它何時運行。有界呼叫可能會留下符合條件的行，由任何結果指示`done: false`. Call it again on the next tick. Short invocations let a large backlog drain over several runs.

```typescript
// Runs on your own cron (node-cron, a workflow schedule, an external job, etc.).
async function retentionTick() {
  const results = await storage.prune({ maxRows: 100_000, pauseMs: 25 })
  const incomplete = results.filter(r => !r.done)
  if (incomplete.length) {
    // Rows remain; the next scheduled tick will continue where this one stopped.
    console.log(
      'retention still draining:',
      incomplete.map(r => `${r.domain}.${r.table}`),
    )
  }
}
```

您也可以使用以下命令取消長時間運行的修剪`AbortSignal`: the loop stops between batches and returns partial results with `done: false`. The next run resumes cleanly.

## ClickHouse 原生 TTL {/* #clickhouse-native-ttl */}

ClickHouse 可觀察性儲存使用本機表 TTL，而不是`prune()`. Configure retention as days per signal. `init()` applies the TTLs to new and existing tables and skips `ALTER TABLE` statements when the configured TTL is already present.

省略的訊號以及設定為零或更低的訊號不會獲得 TTL。當您從以下位置移除訊號時`retention`, the next `init()` or `applyRetention()` removes that table's TTL. If Mastra can't read the current TTLs from `system.tables`, it applies the configured TTLs and leaves the others unchanged.

對於需要更新 TTL 配置而不運行完整初始化路徑的部署，請呼叫`applyRetention()` on the vNext observability store:

```typescript
import { ObservabilityStorageClickhouseVNext } from '@mastra/clickhouse'

const observability = new ObservabilityStorageClickhouseVNext({
  client,
  retention: {
    tracing: 30,
    logs: 7,
    metrics: 14,
    scores: 90,
    feedback: 60,
  },
})

await observability.applyRetention()
```

刪除請求會保留足夠長的時間，以便在訊號行過期後繼續執行擦除操作。 Mastra 將 TTL 應用到`mastra_deletion_requests` only when tracing, logs, metrics, scores, and feedback all have finite retention. The deletion-request TTL is the longest of those periods plus 30 days. For example, if score retention is the longest period at 90 days, deletion requests expire after 120 days. When any signal is unbounded, deletion requests remain unbounded because trace deletion requests cover rows across all five signals.

## MongoDB TTL 索引（修剪的替代方案） {/* #mongodb-ttl-indexes-alternative-to-prune */}

MongoDB 提供原生[TTL (Time-To-Live) indexes](https://www.mongodb.com/docs/manual/core/index-ttl/) that automatically delete expired documents without requiring manual `prune()` calls. This is a database-level feature that runs as a background thread.

:::注意\[何時使用 TTL 與 prune()]

**在以下情況下使用 MongoDB TTL 索引：**

* 您想要自動、零維護的刪除
* 您的保留期是固定的（例如「始終 30 天」）
* 您更喜歡資料庫本機解決方案

**使用`prune()` when:**

* 您需要對刪除時間進行細粒度控制
* 您想要限制工作時間內的刪除率
* 您需要可恢復、可取消的清理操作
* 您正在使用具有多個資料庫的複合存儲

兩種方法都是有效的。 TTL 更簡單。`prune()` gives more control.
:::

### 在 MongoDB 上設定 TTL 索引 {/* #setting-up-ttl-indexes-on-mongodb */}

TTL 索引適用於日期欄位。 MongoDB 每 60 秒檢查索引，並刪除日期欄位 + TTL 持續時間 \< 目前時間的文件。

```typescript
import { MongoDBStore } from '@mastra/mongodb'

const storage = new MongoDBStore({
  id: 'mongodb-storage',
  uri: process.env.MONGODB_URI!,
  dbName: process.env.MONGODB_DB_NAME!,
  indexes: [
    // Messages expire after 30 days
    {
      collection: 'mastra_messages',
      keys: { createdAt: 1 },
      options: { expireAfterSeconds: 30 * 24 * 60 * 60 }, // 30 days
    },
    // Threads expire after 90 days
    {
      collection: 'mastra_threads',
      keys: { createdAt: 1 },
      options: { expireAfterSeconds: 90 * 24 * 60 * 60 }, // 90 days
    },
    // Spans expire after 7 days
    {
      collection: 'mastra_ai_spans',
      keys: { startedAt: 1 },
      options: { expireAfterSeconds: 7 * 24 * 60 * 60 }, // 7 days
    },
  ],
})
```

:::提示
TTL 索引會在文件過期後不久刪除文件（後台執行緒每約 60 秒執行一次），但不能保證確切的時間。為了精確、立即清理，請使用`prune()` instead.
:::

## {/* #reclaiming-disk */}

`prune()`删除行但不收缩数据库文件。在 SQLite/libSQL 上，釋放的頁面會進入空閒清單以供未來的寫入重複使用。對於大多數用戶來說，重複使用這些頁面可以防止檔案無限增長。

將可用空間交還給作業系統是 Mastra 無法管理的另一個問題。如果您特別需要收縮文件，請執行底層資料庫的壓縮（例如`VACUUM` on self-hosted libSQL) yourself in a maintenance window. A full `VACUUM` locks the file and needs roughly twice the file size in free disk. On PostgreSQL, autovacuum reclaims dead tuples for reuse automatically. A manual `VACUUM FULL` is only needed if you must return disk to the OS.

對於 MongoDB，已刪除的文件可在以後的插入中重複使用。要回收磁碟空間，請運行[`db.runCommand({ compact: "collection_name" })`](https://www.mongodb.com/docs/manual/reference/command/compact/) during a maintenance window.

:::注意\[libSQL 和 Turso][Turso Cloud](/integrations/databases/libsql) manages storage compaction for you, so there's nothing to reclaim manually. This applies only to self-hosted libSQL files.
:::
