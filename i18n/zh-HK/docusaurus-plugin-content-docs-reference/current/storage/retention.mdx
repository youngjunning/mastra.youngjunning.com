# 儲存保留

預設情況下，儲存數據會持續成長。Mastra 提供可選的按資料年齡保留機制：為各數據表宣告 `maxAge` 策略，寫入 `retention` 設定，再呼叫 `storage.prune()` 刪除早於設定期限的數據行。未設定的數據會永久保留，因此在啟用前現有行為不變。

`prune()` 分批限量刪除數據行。工作可恢復、可取消，便於限制每個維護時段的工作量。修剪本身不會回收磁碟空間；如需將空閒空間歸還操作系統，請參閱下文針對各資料庫的維護建議。

保留策略僅適用於**持續成長的數據表**：這類數據表會在正常運行時不斷累積數據，例如對話記錄、遙測數據、工作與執行記錄、排程觸發記錄及事件動態。用戶建立的內容與設定（Agent、Skill、工作區、提示區塊、資料集、排程定義、頻道安裝項目等）依用戶意圖增長，且由用戶明確編輯或刪除，因此不能作為保留策略的鍵。

儲存適配器會為 `prune()` 使用共享的核心保留契約；如果資料庫原生機制更適合對應後端，也可以採用原生機制。

| 適配器 | 機制 | 保留策略支援範圍 |

## 各儲存後端的維護建議 {/* #storage-specific-maintenance */}

| 適配器 | 維護建議 |
| - | - |
| SQLite 和 libSQL | 刪除後釋放的頁面可供後續寫入重用，從而阻止資料庫文件持續成長。若要回收磁碟空間，需要執行資料庫級維護。 |
| DuckDB | 對文件儲存，修剪後執行 `CHECKPOINT` 以回收已刪除數據行佔用的空間。DuckDB 的 `VACUUM` 不會回收這些空間。 |

## 定期修剪 {/* #schedule-pruning */}

應從調度器或維護 Worker 呼叫 `prune()`，不要在應用啟動或關閉掛鉤中呼叫。多個部署共用資料庫時，最好只由一個活躍的調度器或 Worker 執行修剪。

修剪大型數據表時，盡量選擇低流量時段。使用 `maxBatches`、`maxRows` 和 `pauseMs` 限制每次執行的工作量；維護行程需要及時停止時，傳入 `AbortSignal`。這些建議適用於實作 `prune()` 的適配器。ClickHouse 則在資料庫內部執行原生 TTL 策略。

## 使用示例 {/* #usage-example */}

宣告 `retention` 時，可使用 `MastraCompositeStore`（或其子類適配器，例如 `LibSQLStore`），再由自行使用的調度器呼叫 `prune()`。

```typescript title="src/mastra/index.ts"
import { LibSQLStore } from '@mastra/libsql'

const storage = new LibSQLStore({
  id: 'mastra-storage',
  url: 'file:./mastra.db',
  retention: {
    memory: {
      messages: { maxAge: '30d' },
      threads: { maxAge: '90d', batchSize: 500 },
    },
    observability: {
      spans: { maxAge: '7d' },
    },
  },
})

// Wire this to your own cron/scheduler: Mastra never runs it for you.
const results = await storage.prune()
```

`retention` 具有完整的類型約束：數據域鍵必須存在，數據表鍵必須被宣告為可設定保留策略。直接傳入儲存設定的物件會接受類型檢查；單獨構造物件時，請使用 `satisfies RetentionConfig`，以便未知的數據域或表在編譯時觸發錯誤：

```typescript
import type { RetentionConfig } from '@mastra/core/storage'

const retention = {
  memory: {
    messages: { maxAge: '30d' }, // ok
    bogus: { maxAge: '30d' }, // Error: not a memory retention table
  },
  bogusDomain: {}, // Error: not a storage domain
} satisfies RetentionConfig
```

### 可設定保留策略的數據表 {/* #retention-eligible-tables */}

每個數據域會指定可依存留時間修剪的數據表，以及用來比較的基準時間戳記欄位，讓 `maxAge` 符合資料的實際意義。只追加的日誌使用建立時間，當前狀態使用最近活動時間，工作或執行記錄則使用完成時間，避免清理進行中的工作。

| 數據域 | 數據表鍵 | 基準時間戳記欄位 | `maxAge` 衡量的時間 |
| - | - | - | - |
| `memory` | `threads` | `createdAt` | 線程建立至今的時間 |
| `memory` | `messages` | `createdAt` | 消息建立至今的時間 |
| `memory` | `resources` | `createdAt` | 資源建立至今的時間 |
| `memory` | `runFences` | `retiredAt` | 持有隔離記錄的持久化 Agent 執行結束後的時間；仍在執行的隔離記錄（`NULL`）不會被修剪 |
| `threadState` | `threadState` | `updatedAt` | 未活動時長；活躍線程的狀態會保留 |
| `observability` | `spans` | `startedAt` | Span 建立至今的時間 |
| `observability` | `metrics` | `timestamp` | 指標事件建立至今的時間（僅 vNext） |
| `observability` | `logs` | `timestamp` | 日誌事件建立至今的時間（僅 vNext） |
| `observability` | `scores` | `timestamp` | 評分事件建立至今的時間（僅 vNext） |
| `observability` | `feedback` | `timestamp` | 反饋事件建立至今的時間（僅 vNext） |
| `scores` | `scorers` | `createdAt` | 評分記錄建立至今的時間 |
| `workflows` | `workflowSnapshot` | `updatedAt` | 閒置時間；暫停或長時間執行的 Workflow 仍會保留 |
| `workflows` | `runOwnership` | `updatedAt` | 閒置時間。執行中的持久化 Agent 每 10 秒續租一次，因此 `maxAge` 應遠大於 30 秒的租約 |
| `backgroundTasks` | `backgroundTasks` | `completedAt` | 工作完成後的時間；進行中的工作（`NULL`）不會被修剪 |
| `experiments` | `experiments` | `completedAt` | 實驗完成後的時間；執行中的實驗不會被修剪 |
| `notifications` | `notifications` | `createdAt` | 通知建立至今的時間 |
| `harness` | `sessions` | `createdAt` | 工作階段記錄建立至今的時間 |
| `schedules` | `triggers` | `actual_fire_at` | 觸發記錄建立至今的時間（該欄位為 epoch 毫秒值） |

:::note

- memory 數據域的 `observational_memory` 數據表沒有基準時間戳記欄位，因此無法依存留時間修剪，也不能作為保留策略鍵。
- 實驗會整體修剪：過期實驗的結果數據行會連同實驗一起刪除（結果隨父記錄連動刪除），不會留下部分刪除的執行記錄。保留策略沒有獨立的 `results` 鍵。
- `runOwnership` 與 `runFences` 保存持久化 Agent 的執行隔離記錄，每次執行在兩個數據表中各有一筆小記錄。若 `runOwnership` 的 `maxAge` 太短，進行中的執行可能失去執行所有權；但失去所有權後仍無法寫入。隔離記錄僅在對應執行結束時退役，因此崩潰且從未恢復的執行，其隔離記錄不會被修剪。
- 對 `schedules` 而言，持續成長的數據表是觸發記錄（`schedule_triggers`，每次觸發一筆）；排程定義屬於設定，不會被修剪。
- PostgreSQL 的基準時間戳記採用可感知時區的鏡像欄位（例如 `createdAtZ`、`completedAtZ`）。
- DuckDB 可觀測性儲存以只追加方式保存五種訊號的事件。其 `spans` 策略使用事件的 `timestamp` 欄位，而非 `startedAt`。
- libSQL 與 PostgreSQL 支援上述所有數據域，但 PostgreSQL 尚未實作 `harness`。MongoDB 不支援 `threadState` 與 `harness`。DuckDB、MySQL、Microsoft SQL Server、Oracle Database、Amazon Aurora DSQL 與 Google Cloud Spanner 目前只在 `observability` 數據域提供保留策略，具體訊號範圍見上方支援矩陣。
- vNext PostgreSQL 可觀測性數據域將訊號事件按天分割儲存（`spans`、`metrics`、`logs`、`scores`、`feedback`）。其 `prune()` 不逐列刪除，而是移除完全早於截止時間的整日分割區（或 TimescaleDB 數據塊）；有效粒度為一天，只有整個分割區均超過 `maxAge` 時才會移除。`PruneResult.deleted` 會報告移除的分割區所包含的數據行數。

:::

## 方法 {/* #methods */}

### 保留 {/* #retention */}

#### `prune(options?)` {/* #pruneoptions */}

刪除存留時間超過對應 `maxAge` 的數據行，範圍涵蓋 `retention` 中設定了策略的所有數據域。每個受影響的數據表傳回一個 `PruneResult`。未設定 `retention` 時不執行操作，傳回 `[]`。

`prune()` 專為數百萬行的大型數據表設計。它按有界批次刪除資料（每批都是獨立事務），避免長時間鎖表或使事務紀錄過度成長。它不會執行 `VACUUM`。

傳入 `options.retention` 可僅在本次呼叫中替換已設定策略，例如跳過某個數據域以保留聊天歷史，或比常規設定更積極地修剪。儲存實例上的 `retention` 設定保持不變。

使用基準時間戳記列索引的適配器，只在首次對有策略的數據表呼叫 `prune()` 時延遲建立索引，而不會在 `init()` 時建立。因此未啟用保留策略的部署不會產生額外的索引寫入或磁碟開銷。現有大型數據表首次修剪時需一次性建立索引；後續修剪復用該索引。DuckDB 使用內置 Zone Map，不建立保留策略索引。

```typescript
const results = await storage.prune({
  maxRows: 50_000, // cap work this call
  pauseMs: 50, // breathe between batches
})

for (const r of results) {
  console.log(`${r.domain}.${r.table}: deleted ${r.deleted}, done=${r.done}`)
}

// One-off pass with different policies (configured retention untouched):
await storage.prune({
  retention: {
    observability: { spans: { maxAge: '1d' } },
  },
})
```

返回：`Promise<PruneResult[]>`

##### 修剪結果 {/* #pruneresult */}

每個結果描述一個表的處理進度：

```typescript
interface PruneResult {
  domain: string // e.g. 'memory'
  table: string // physical table name, e.g. 'mastra_messages'
  deleted: number // rows deleted during this call
  done: boolean // false => eligible rows remain; call prune() again
}
```

## 定期執行修剪 {/* #running-prune-on-a-schedule */}

`prune()` 沒有內置調度器，執行時間由你決定。受限的單次呼叫可能仍有符合刪除條件的數據行，任何返回 `done: false` 的結果都表示這種情況。請在下次調度時再次呼叫。通過多次短時執行，可以逐步清理大量積壓資料。

```typescript
// Runs on your own cron (node-cron, a workflow schedule, an external job, etc.).
async function retentionTick() {
  const results = await storage.prune({ maxRows: 100_000, pauseMs: 25 })
  const incomplete = results.filter(r => !r.done)
  if (incomplete.length) {
    // Rows remain; the next scheduled tick will continue where this one stopped.
    console.log(
      'retention still draining:',
      incomplete.map(r => `${r.domain}.${r.table}`),
    )
  }
}
```

也可以傳入 `AbortSignal` 取消長時間的修剪工作：循環會在批次之間停止，並傳回包含 `done: false` 的部分結果。下次執行時可繼續處理。

## ClickHouse 原生 TTL {/* #clickhouse-native-ttl */}

ClickHouse 的可觀測性儲存使用數據表原生 TTL，而不是 `prune()`。按訊號設定保留天數。`init()` 會將 TTL 應用於新舊表；若已設定相同 TTL，則跳過 `ALTER TABLE` 語句。

未設定的訊號以及保留天數設為零或負數的訊號不會設定 TTL。從 `retention` 移除某個訊號後，下次呼叫 `init()` 或 `applyRetention()` 會移除對應表的 TTL。如果 Mastra 無法從 `system.tables` 讀取當前 TTL，它只會應用已設定的 TTL，其餘保持不變。

若部署需要更新 TTL 設定，但不想執行完整初始化流程，可在 vNext 可觀測性儲存上呼叫 `applyRetention()`：

```typescript
import { ObservabilityStorageClickhouseVNext } from '@mastra/clickhouse'

const observability = new ObservabilityStorageClickhouseVNext({
  client,
  retention: {
    tracing: 30,
    logs: 7,
    metrics: 14,
    scores: 90,
    feedback: 60,
  },
})

await observability.applyRetention()
```

刪除請求記錄會保留足夠久，以便訊號數據行過期後仍能執行刪除。只有追蹤、日誌、指標、評分和反饋均設定有限保留期限時，Mastra 才會為 `mastra_deletion_requests` 設定 TTL。該 TTL 等於五種訊號中最長的保留期限再加 30 天。例如評分的保留期限最長，為 90 天，刪除請求記錄便會在 120 天後過期。只要有一種訊號無期限保留，刪除請求記錄也會無期限保留，因為追蹤刪除請求涵蓋五種訊號的數據行。

## MongoDB TTL 索引（修剪的替代方案） {/* #mongodb-ttl-indexes-alternative-to-prune */}

MongoDB 提供原生 [TTL（存活時間）索引](https://www.mongodb.com/docs/manual/core/index-ttl/)，可自動刪除過期文檔，毋須手動呼叫 `prune()`。這是在資料庫背景線程中執行的功能。

:::note[何時使用 TTL，何時使用 prune()]

**以下情況適合使用 MongoDB TTL 索引：**

- 希望自動刪除，且毋須維護
- 保留期限固定（例如始終為 30 天）
- 傾向使用資料庫原生機制

**以下情況適合使用 `prune()`：**

- 需要精細控制刪除時間
- 希望限制營運時段的刪除速率
- 需要可恢復、可取消的清理操作
- 使用跨多個資料庫的復合儲存

兩種方式都可行。TTL 更簡單，`prune()` 控制更細。
:::

### 在 MongoDB 上設定 TTL 索引 {/* #setting-up-ttl-indexes-on-mongodb */}

TTL 索引適用於日期字段。MongoDB 每 60 秒檢查一次索引，並刪除滿足“日期字段值 + TTL 時長 \< 當前時間”的文檔。

```typescript
import { MongoDBStore } from '@mastra/mongodb'

const storage = new MongoDBStore({
  id: 'mongodb-storage',
  uri: process.env.MONGODB_URI!,
  dbName: process.env.MONGODB_DB_NAME!,
  indexes: [
    // Messages expire after 30 days
    {
      collection: 'mastra_messages',
      keys: { createdAt: 1 },
      options: { expireAfterSeconds: 30 * 24 * 60 * 60 }, // 30 days
    },
    // Threads expire after 90 days
    {
      collection: 'mastra_threads',
      keys: { createdAt: 1 },
      options: { expireAfterSeconds: 90 * 24 * 60 * 60 }, // 90 days
    },
    // Spans expire after 7 days
    {
      collection: 'mastra_ai_spans',
      keys: { startedAt: 1 },
      options: { expireAfterSeconds: 7 * 24 * 60 * 60 }, // 7 days
    },
  ],
})
```

:::tip
TTL 索引通常在文檔過期後不久刪除它們（背景線程約每 60 秒執行一次），但不保證準確時間。如需精確、即時清理，請改用 `prune()`。
:::

## 回收磁碟空間 {/* #reclaiming-disk */}

`prune()` 刪除數據行，但不會縮小資料庫文件。在 SQLite/libSQL 中，釋放的頁面進入空閒列表，供後續寫入重用。對大多數用戶而言，復用頁面可避免文件無限成長。

將空閒空間歸還操作系統是獨立的維護工作，Mastra 不會代為執行。如果確需縮小文件，請在維護時段自行執行底層資料庫的壓縮操作（例如對自行托管的 libSQL 執行 `VACUUM`）。完整的 `VACUUM` 會鎖定文件，並需要約為文件大小兩倍的可用磁碟空間。在 PostgreSQL 中，autovacuum 會自動回收失效元組以供重用；只有必須把磁碟空間歸還操作系統時，才需要手動執行 `VACUUM FULL`。

MongoDB 會在後續插入中復用已刪除文檔的空間。如需回收磁碟空間，請在維護時段執行 [`db.runCommand({ compact: "collection_name" })`](https://www.mongodb.com/docs/manual/reference/command/compact/)。

:::note[libSQL 和 Turso]
[Turso Cloud](/integrations/databases/libsql) 會自動管理儲存壓縮，無需手動回收空間。本節僅適用於自行托管的 libSQL 文件。
:::
