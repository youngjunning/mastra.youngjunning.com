# `mastra.schedules`

**添加於：** `@mastra/core@1.50.0`

`mastra.schedules`是持久化 cron 計劃的 CRUD 服務。使用它來建立、列出、更新、暫停、恢復、手動運行和刪除Agent或Workflow的計劃。

有關使用模式和概念，請參閱[Schedules](/docs/harness/schedules).

## 交貨保證 {/* #delivery-guarantees */}

預定的發布是盡最大努力，而不是至少一次交付。調度程序自動聲明發生並推進`nextFireAt` before publishing the agent or workflow start event. An exhausted cron schedule is marked `completed` in that claim. Completion means there are no remaining occurrences, not that the target started or succeeded.

調度程式對相同聲明的事件最多進行 3 次發布嘗試，在嘗試之間等待 100 毫秒，然後等待 200 毫秒。傳輸可以在傳回錯誤之前接受事件，因此重試可以發布具有相同運行 ID 的重複項。

三次嘗試都失敗後，調度程式會記錄調度 ID、運行 ID、調度的觸發時間、`publicationOutcome: 'unknown'`, and `automaticReplay: false`. It invokes the configured `scheduler.onError` hook and attempts to record a trigger with outcome `failed`。此失敗描述了發布嘗試。這並不能證明目標從未開始。

一旦這些嘗試用盡，調度程式就不會重播該事件。定期規劃保持活動狀態，並且可以在下一個計劃時間觸發。終端計劃保持完整狀態，並在觸發歷史記錄中記錄任何故障詳細資訊。

成功領取後，會出現訊息級別`Claimed schedule occurrence` log identifies the schedule ID, run ID, and scheduled fire time. A matching `Published schedule occurrence` log reports transport acceptance. If neither that success log nor the final failure log follows a claim, publication is unconfirmed. These logs aren't durable state: a crash between the claim commit and logging, or before logs are flushed, can leave no log record.

如果發布者程序在聲明提交後終止，或確認遺失，則可以跳過該事件，而不會觸發失敗。替換調度程序無法使用聲明元資料或遺失的觸發歷史記錄來區分未發布的事件與崩潰之前接受的事件。它不會重播事件或阻止以後重複發生的火災。發布確認也不能保證目標執行，且傳輸重新傳遞可能會產生重複。

在手動重新執行錯過的工作之前，請獨立檢查目標執行和傳輸記錄。僅缺少觸發歷史記錄或失敗的發布嘗試並不能證明重新運行是安全的。

## 使用範例 {/* #usage-example */}

建立Agent計劃：

```typescript title="src/mastra/schedules.ts"
const schedule = await mastra.schedules.create({
  agentId: 'pinger',
  cron: '0 * * * *',
  prompt: 'Give me a status update.',
})
```

建立Workflow計劃：

```typescript title="src/mastra/schedules.ts"
const schedule = await mastra.schedules.create({
  workflowId: 'daily-report',
  cron: '0 9 * * *',
  inputData: { reportType: 'summary' },
})
```

計劃需要一個實現計劃域的儲存適配器。支援的適配器包括`@mastra/libsql`, `@mastra/pg`, `@mastra/mysql`, `@mastra/mongodb`, `@mastra/convex`, and `@mastra/spanner`.

要在固定時間運行一次，請傳遞`runAt` instead of `cron`:

```typescript
await mastra.schedules.create({
  workflowId: 'send-report',
  runAt: new Date(Date.now() + 60 * 60 * 1000), // One hour from now
})
```

### 更新時間表 {/* #update-schedules */}

#### `update(id, patch)` {/* #updateid-patch */}

更新時間表。改變`cron` or `timezone` recomputes the next fire time. Updating `status` from `paused` to `active` also recomputes the next fire time. A schedule becomes `completed` once its cron has no future occurrence. A cadence edit that leaves no future occurrence completes the row even when it was `paused`. Editing the cadence of a completed schedule reactivates it when the new cadence can still fire, and leaves it completed when it can't.

```typescript
const updated = await mastra.schedules.update('pinger', {
  cron: '*/30 * * * *',
  prompt: 'Give me a status update every 30 minutes.',
})
```

`cron`, `timezone`, `prompt`, `name`, `signalType`, `tagName`, `attributes`, `providerOptions`, `ifActive`, `ifIdle`, `metadata`, and `status`. `threadId` and `resourceId` aren't patchable. Create a new schedule when the thread target needs to change.

Workflow計劃補丁可以更新`cron`, `timezone`, `inputData`, `initialState`, `requestContext`, `resourceId`, `metadata`, and `status`. Agent-only patch fields such as `prompt`, `signalType`, and `ifIdle` throw on workflow schedules.

### 生命週期 {/* #lifecycle */}

#### `pause(id)` {/* #pauseid */}

暫停計劃。暫停是持久且冪等的。暫停一個`completed` schedule throws a `409` error.

```typescript
const paused = await mastra.schedules.pause('pinger')
```

#### `resume(id)` {/* #resumeid */}

恢復暫停的計劃並從目前時間重新計算下一次觸發時間。一次性時間表保留其`runAt`; if it passed while the schedule was paused, the schedule fires on the next scheduler tick. A paused schedule whose cron has no future occurrence is completed instead of resumed. Resuming a `completed` schedule throws a `409` error; update its timing instead to reactivate it.

```typescript
const active = await mastra.schedules.resume('pinger')
```

#### `run(id)` {/* #runid */}

立即觸發一次計劃，而不改變其 cron 節奏。

```typescript
const run = await mastra.schedules.run('pinger')
```

對於Agent時間表，`claimId` uses `manual_<scheduleId>_<timestamp>`. For workflow schedules, `claimId` uses `sched_<scheduleId>_<timestamp>` and is reused as the workflow run ID.

#### `delete(id)` {/* #deleteid */}

刪除計劃。刪除缺失的時間表是無操作的。

```typescript
await mastra.schedules.delete('pinger')
```

## 安排行為 {/* #schedule-behavior */}

* Agent計劃 ID 使用`agent_` prefix. Workflow schedule IDs created through `mastra.schedules.create()` use the `schedule_` prefix.
* 線程Agent調度需要`resourceId` when `threadId` is set.
* 在Agent日程表上，`signalType`, `ifActive`, `ifIdle`, and `resourceId` require `threadId`. Workflow schedules accept `resourceId` without a thread.
* Workflow計劃不接受僅限Agent的補丁字段，例如`prompt`, `signalType`, or `ifIdle`.
* `run()`立即發布手動觸發並且不會更改儲存的 cron 節奏。
* 時間表有三種狀態：`active`, `paused`, and `completed`. A schedule becomes `completed` when it has no remaining automatic fires: after a one-off fires, when a bounded or exhausted cron has no future occurrence, or when declarative registration finds its timing has already passed. `update()` and `resume()` also mark exhausted cron schedules as completed. `run()` doesn't complete a one-off schedule.
* 更新中`runAt` on a one-off, or `endAt` on a cron schedule (`null` removes the bound), reactivates a `completed` schedule only if the resulting timing can still fire. A cron schedule with no occurrence before its new `endAt` remains completed.
* `list()`隱藏`completed` schedules unless you pass `status: 'completed'`.
