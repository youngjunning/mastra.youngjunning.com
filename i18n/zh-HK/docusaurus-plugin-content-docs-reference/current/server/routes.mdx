# 伺服器路由

調用 `server.init()` 時，伺服器適配器會註冊這些路由。如已設定 `prefix` 選項，所有路由都會加上該前綴。

## Agent {/* #agents */}

|方法|路徑|描述 |
| - | - | - |
| `GET` | `/api/agents` | 列出所有 Agent |
| `GET` | `/api/agents/:agentId` | 按 ID 取得 Agent（支援版本查詢參數） |
| `POST` | `/api/agents/:agentId/generate` | 生成 Agent 回應 |
| `POST` | `/api/agents/:agentId/stream` | 以串流方式傳回 Agent 回應 |
| `POST` | `/api/agents/:agentId/send-message` | 向運行中或閒置的對話線程傳送用戶訊息 |
| `POST` | `/api/agents/:agentId/queue-message` | 將用戶訊息加入隊列，留待對話線程下一輪處理 |
| `POST` | `/api/agents/:agentId/queue-signal` | 將帶有類型的訊號加入隊列，留待對話線程下一輪處理 |
| `POST` | `/api/agents/:agentId/signals` | 向運行中或閒置的對話線程傳送底層訊號 |
| `POST` | `/api/agents/:agentId/threads/subscribe` | 訂閱對話線程的串流 |
| `POST` | `/api/agents/:agentId/threads/abort` | 中止對話線程，可選擇一併清除待處理訊號 |
| `POST` | `/api/agents/:agentId/threads/signals/cancel` | 取消對話線程內指定的待處理訊號 |
| `POST` | `/api/agents/:agentId/send-tool-approval` | 批准或拒絕 Tool 調用，並透過對話線程訂閱繼續接收輸出 |
| `POST` | `/api/agents/:agentId/resume-stream` | 使用自訂資料恢復已掛起的 Agent 串流 |
| `GET` | `/api/agents/:agentId/tools` | 列出 Agent 的 Tool |
| `POST` | `/api/agents/:agentId/tools/:toolId/execute` | 執行 Agent 的 Tool |

### 取得 Agent 的查詢參數 {/* #get-agent-query-parameters */}

`GET /api/agents/:agentId` 接受以下選用查詢參數，供你選擇已儲存的設定版本，以覆寫程式碼所定義的 Agent 設定。

| 參數 | 類型 | 預設值 | 說明 |
| - | - | - | - |
| `status` | `'draft' \| 'published'` | `'published'` | 指定採用哪個已儲存的版本。`draft` 傳回最新版本，`published` 傳回目前生效的版本。 |
| `versionId` | `string` | 無 | 指定要採用的版本 ID，優先於 `status`。 |

```bash
# Get agent with active published overrides (default)
GET /api/agents/my-agent

# Get agent with latest draft overrides
GET /api/agents/my-agent?status=draft

# Get agent with a specific version's overrides
GET /api/agents/my-agent?versionId=abc123
```

### Agent 訊息路由 {/* #agent-message-routes */}

使用 `POST /api/agents/:agentId/send-message` 向正在運行的 Agent 迴圈傳送用戶訊息，或喚醒閒置的對話線程。如要等目前的運行結束，再由 Mastra 啟動下一次運行，請使用 `POST /api/agents/:agentId/queue-message`。

如要按同樣的次序將帶有類型的訊號加入隊列，請使用 `POST /api/agents/:agentId/queue-signal`，以 `signal` 欄位取代 `message`。`signal` 欄位的結構與 `POST /api/agents/:agentId/signals` 採用的結構相同。

兩條訊息路由接受相同的請求內容：

```typescript oxfmt:false
{
  message: string | Array<TextPart | FilePart> | {
    contents: string | Array<TextPart | FilePart>;
    attributes?: Record<string, JSONValue>;
    metadata?: Record<string, unknown>;
    providerOptions?: ProviderMetadata;
  };
  runId?: string;
  resourceId?: string;
  threadId?: string;
  ifActive?: {
    behavior?: 'deliver' | 'persist' | 'discard';
    attributes?: Record<string, string | number | boolean>;
  };
  ifIdle?: {
    behavior?: 'wake' | 'persist' | 'discard';
    streamOptions?: Omit<AgentExecutionOptions, 'messages'>;
    attributes?: Record<string, string | number | boolean>;
  };
}
```

如省略 `runId`，就必須提供 `resourceId` 和 `threadId`。`ifIdle` 只適用於以對話線程為目標的請求。

#### 發送訊息 {/* #send-a-message */}

```bash
curl -X POST http://localhost:4111/api/agents/supportAgent/send-message \
  -H 'Content-Type: application/json' \
  -d '{
    "message": {
      "contents": "Show the shorter version.",
      "attributes": { "sentFrom": "web" }
    },
    "resourceId": "user_123",
    "threadId": "thread_456"
  }'
```

#### 將訊息放入隊列 {/* #queue-a-message */}

```bash
curl -X POST http://localhost:4111/api/agents/supportAgent/queue-message \
  -H 'Content-Type: application/json' \
  -d '{
    "message": "Also check whether the tests need updates.",
    "resourceId": "user_123",
    "threadId": "thread_456"
  }'
```

兩條路由均會傳回以下回應：

```typescript oxfmt:false
{
  accepted: true;
  runId: string;
  signal?: CreatedAgentSignal;
}
```

### 中止對話線程及取消訊號的路由 {/* #thread-cancellation-routes */}

`POST /api/agents/:agentId/threads/abort` 接受 `{ resourceId?: string, threadId: string, clearPendingSignals?: boolean }`，並傳回 `{ aborted: boolean }`。只有在 `clearPendingSignals` 設為 `true` 時才會清除待處理輸入。接收請求的程序會先在本機清除輸入，再中止對話線程，並在有需要時將清除操作轉發至目前掌管對話線程的程序。如該程序位於遠端，`aborted: true` 只代表請求已發出。

`POST /api/agents/:agentId/threads/signals/cancel` 只取消指定的待處理輸入，對話線程會繼續運行。JSON 請求內容包括以下欄位：

<PropertiesTable
  content={[
{ name: 'resourceId', type: 'string', isOptional: true, description: '記憶對話線程所屬的資源 ID。' },
{ name: 'threadId', type: 'string', description: '含有待處理訊號的對話線程 ID。' },
{ name: 'signalIds', type: 'string[]', description: '要取消的訊號 ID，可提供 1 至 1,000 個，每個 ID 均不可留空。' },
]}
/>

回應為 `{ cancelledSignalIds: string[] }`，當中只包括處理該請求的伺服器程序已取消的訊號 ID。每個 ID 只會出現一次。未知的 ID、已交付執行的訊號 ID，以及已移交其他持有者的訊號 ID 均不會列出。請求內容無效時會傳回 HTTP 400。

兩條路由均須具備 `agents:execute` 權限，並會根據已通過身分驗證的請求上下文檢查對話線程的歸屬。如已設定細粒度授權，即使對話線程尚未儲存，調用方亦須具備該對話線程的 `memory:write` 權限。取消操作涵蓋共用該記憶對話線程的所有 Agent。已持久儲存的訊息、狀態更新、通知記錄和接收確認均不會撤銷，由 `continueWithMessages()` 啟動的後續運行亦不受影響。

即使本機沒有相符的待處理輸入，伺服器仍會透過共用的 PubSub 後端發佈請求中的所有 ID，讓訂閱該對話線程的其他程序可移除相符的待處理輸入。通知以非同步方式傳送，並不保證送達，HTTP 回應也不會確認遠端是否已取消。中止時的清除操作只影響接收請求的程序，以及目前掌管對話線程的程序。SDK 的用法請參閱[客戶端取消方法](/reference/client-js/agents#cancelqueuedmessages)。

同時升級 `@mastra/core` 和 `@mastra/server`，即可使用適用於整個對話線程的取消功能，以及中止時清除待處理輸入的功能。在多程序部署中，須升級所有可能掌管該對話線程的工作程序。如 Agent 採用的核心版本不支援這些操作，伺服器會傳回 HTTP 501，待處理輸入會保留。支援中止對話線程的舊版核心仍可處理沒有設定 `clearPendingSignals: true` 的一般中止請求。

### 透過對話線程訂閱處理 Tool 審批 {/* #subscription-tool-approval-routes */}

如客戶端已訂閱對話線程，請使用 `POST /api/agents/:agentId/send-tool-approval`。此路由會恢復運行，並傳回 JSON 確認回應。恢復後的串流資料區塊會透過 `POST /api/agents/:agentId/threads/subscribe` 傳送。

此路由接受以下請求內容：

```typescript oxfmt:false
{
  resourceId: string;
  threadId: string;
  toolCallId: string;
  approved: boolean;
  requestContext?: Record<string, unknown>;
}
```

此路由會傳回以下回應：

```typescript oxfmt:false
{
  accepted: true;
  runId: string;
  toolCallId?: string;
}
```

### 運行數量統計回應 {/* #run-counts-response */}

`/api/workflows/run-counts` 會傳回每個已註冊 Workflow 處於 `running` 及 [`suspended`](/docs/workflows/suspend-and-resume) 狀態的運行數量。回應物件以 Mastra 設定內的 Workflow 註冊鍵為鍵，伺服器可能會將回應快取數秒。

```typescript oxfmt:false
{
  [workflowRegistryKey: string]: {
    running: number;
    suspended: number;
  };
}
```

### 動態 Workflow {/* #dynamic-workflows */}

動態 Workflow 定義（測試版）以 JSON 表達，透過 `workflowDefinitions` 儲存域持久保存，並在運行中的實例即時註冊。詳見[動態 Workflow](/docs/workflows/dynamic-workflows)。

|方法|路徑|描述 |
| - | - | - |
| `GET` | `/api/stored/workflows` | 列出動態 Workflow 定義，可按 `status` 及 `authorId` 篩選 |
| `GET` | `/api/stored/workflows/:dynamicWorkflowId` | 按 ID 取得動態 Workflow 定義 |
| `POST` | `/api/stored/workflows` | 新增或更新定義（可附上輔助 `dependencies`），並即時註冊 |
| `DELETE` | `/api/stored/workflows/:dynamicWorkflowId` | 刪除動態 Workflow 定義，並撤銷相應 Workflow 的註冊 |

伺服器啟用身分驗證時，讀取路由須具備 `stored-workflows:read` 權限，寫入路由須具備 `stored-workflows:write` 權限。已註冊的動態 Workflow 可透過上述一般 `/api/workflows/:workflowId` 路由執行。

### 運行結果 {/* #run-result */}

`POST /api/workflows/:workflowId/start-async` 會等候 `run.start()` 完成後才傳回執行結果。`status` 用來區分成功、失敗、觸發警戒條件、掛起及暫停。`steps` 物件以步驟 ID 為鍵，每個步驟都有自己的狀態，並在有輸出時包括 `output`。運行成功時，最上層的 `result` 就是 Workflow 的輸出。

執行結果包括以下欄位。只適用於個別狀態的欄位會在相應結果中出現：

```typescript oxfmt:false
{
  status: 'success' | 'failed' | 'tripwire' | 'suspended' | 'paused';
  input: unknown;                      // The inputData the run started with
  state?: unknown;                     // Workflow state
  result?: unknown;                    // Workflow output on success
  error?: unknown;                     // Error on failure
  tripwire?: unknown;                  // Tripwire details
  suspendPayload?: unknown;           // Payload returned on suspension
  suspended?: string[][];              // Suspended step paths
  steps: {
    [stepId: string]: {
      status: string;
      output?: unknown;
      error?: unknown;
      startedAt: number;               // Unix time in milliseconds
      endedAt?: number;
    };
  };
}
```

`GET /api/workflows/:workflowId/runs/:runId` 會傳回運行的元資料及執行狀態。有已持久儲存的快照時會採用快照，否則採用記憶體內的運行記錄。此路由以 `payload` 提供運行輸入，以 `initialState` 提供狀態。`workflowName` 是 Workflow 的 `id`，可能與路徑所用的註冊鍵不同。

```typescript oxfmt:false
{
  runId: string;
  workflowName: string;
  resourceId?: string | null;
  createdAt: string;                   // ISO date string
  updatedAt: string;                   // ISO date string
  status: string;                      // Includes active states such as 'running' and 'waiting'
  initialState?: Record<string, unknown>;
  result?: unknown;
  error?: unknown;
  payload?: unknown;                   // The inputData the run started with
  steps?: {
    [stepId: string]: {
      payload?: unknown;               // This step's input
      status: string;
      output?: unknown;
      error?: unknown;                 // Present when the step failed
      startedAt: number;
      endedAt?: number;
    } | {
      payload?: unknown;
      status: string;
      output?: unknown;
      error?: unknown;
      startedAt: number;
      endedAt?: number;
    }[];                              // forEach iteration results
  };
  activeStepsPath?: Record<string, number[]>;
  serializedStepGraph?: unknown[];
  suspendedPaths?: Record<string, number[]>;
  resumeLabels?: Record<string, unknown>;
  waitingPaths?: Record<string, number[]>;
}
```

查詢已持久儲存的運行時，可用 `fields` 查詢參數精簡回應。從 `result`、`error`、`payload`、`steps`、`activeStepsPath` 及 `serializedStepGraph` 選取所需欄位，並以逗號分隔。指定其他名稱會收到 HTTP 400。元資料欄位與 `status` 會保留，`initialState` 有內容時亦會保留。

```bash
curl 'http://localhost:4111/api/workflows/my-workflow/runs/1faf6f91-b9ac-4db0-9fb3-326687ba1972?fields=result'
```

`steps` 中的項目可以是單一步驟的結果，亦可以是 `forEach` 步驟各次迭代結果的陣列。讀取 `status` 或 `output` 前，請先檢查該項目是否為陣列。

傳入 `withNestedWorkflows=false` 可略過在 `steps` 內展開巢狀 Workflow 的執行詳情。目前 Workflow 本身的步驟項目會保留。

改用記憶體內的運行記錄時，回應會標示 `isFromInMemory: true`，並傳回運行元資料、`status` 及空的 `steps`，省略 `result`、`payload` 及 `error`。`createdAt` 和 `updatedAt` 均採用目前時間。此類回應不會篩選欄位或展開巢狀 Workflow。

## 知識 {/* #knowledge */}

系統預設不會註冊這些路由。要啟用路由，請把 `@mastra/server/server-adapter` 的 `KNOWLEDGE_ROUTES` 加入 `server.apiRoutes`，再在 `Mastra` 的 `knowledge` 下註冊實例。這些路由需要 `@mastra/core` 1.81.0 或更新版本，當中兩條連結路由需要 1.82.0 或更新版本。設有 RBAC Provider 時，每條路由都要求 `knowledge:read` 權限。沒有設定時，系統會略過這項檢查。設定方法見 [Studio 知識](/docs/studio/knowledge)。

| 方法 | 路徑 | 說明 |
| - | - | - |
| `GET` | `/api/knowledge` | 列出已註冊的知識實例。如果已設定 FGA，便按權限篩選 |
| `GET` | `/api/knowledge/:knowledgeKey/tree` | 列出根範圍，或列出 `parentId` 的下級範圍 |

### 知識存取權限及錯誤 {/* #knowledge-access-and-errors */}

如果 `server.auth` 和 `studio.auth` 都未設定，路由會以實例擁有人的身分讀取，並傳回全部內容。設定驗證後，路由只會讀取請求上下文中 `MASTRA_KNOWLEDGE_PRINCIPALS_KEY` 所指定範圍可讀取的內容。請把這個鍵設為範圍陣列或 `'all'`。

| 狀態碼 | 傳回情況 |
| - | - |
| `403` | 已設定驗證，但未設定 `MASTRA_KNOWLEDGE_PRINCIPALS_KEY`。`GET /api/knowledge` 不讀取這個鍵，因此不會因此傳回 `403` |
| `404` | 實例不存在，或 FGA Provider 不允許對該實例行使 `knowledge:read` 權限，或頁面不存在，或呼叫方沒有權限讀取頁面。若呼叫方無權讀取頁面，連結路由所傳回的計數為零或連結清單為空 |
| `500` | `MASTRA_KNOWLEDGE_PRINCIPALS_KEY` 的值既非陣列亦非 `'all'`，或當中有範圍不符合任何已宣告的範圍類型 |
| `501` | `@mastra/core` 版本低於路由所需版本，或儲存區沒有連結索引（只適用於連結路由） |

設有 FGA Provider 時，系統會把每個實例視為 `knowledge` 類型的資源，按註冊鍵檢查 `knowledge:read` 權限。`GET /api/knowledge` 只會列出呼叫方可讀取的實例。啟用 `requireForProtectedRoutes` 時，系統會拒絕 `GET /api/knowledge`，因為這條路由和其他列出資源的路由一樣，沒有 FGA 元資料。沒有設定 RBAC Provider 時，系統會略過 `knowledge:read` 檢查。

NestJS 適配器尚不支援這些路由。

### 知識事件 {/* #knowledge-events */}

每次寫入提交後，只要涉及呼叫方可讀取的內容，`GET /api/knowledge/:knowledgeKey/events` 就會發送一個事件，格式如下。

```typescript oxfmt:false
{
  kind: 'scope' | 'page' | 'note' | 'pin';
  op: string;       // such as 'create', 'update', 'delete' or 'merge'
  pageId?: string;  // left out when the caller can't read the page, including a deleted one
  scopeId?: string; // left out when the caller can't read the scope
  at: string;       // ISO timestamp
}
```

如果寫入完全沒有觸及呼叫方可讀取的內容，伺服器便不會發送事件。事件只附上 ID，請用其他路由取得變更內容。如果沒有 `pageId`，請重新載入 `scopeId` 指定的範圍。

伺服器每隔 25 秒發送一條用於保持連線的註解，並在五分鐘後關閉串流。請在關閉後重新連線。新串流會重新讀取呼叫方的範圍，因此一旦撤銷存取權限，呼叫方就不再收到相關更新。連線中斷期間的寫入不會重送，請在重新連線後重新載入所顯示的內容。

### 刪除實驗 {/* #delete-an-experiment */}

兩條刪除路由都會移除實驗及其結果記錄。如果儲存層支援可觀測性及刪除 Trace，Mastra 會先刪除實驗產生的 Trace、當中的 Span，以及和這些 Trace 關聯的訊號，然後才移除實驗。

如果知道實驗屬於哪個數據集，請使用限定於該數據集的路由。

```bash
curl -X DELETE http://localhost:4111/api/datasets/dataset-id/experiments/experiment-id
```

這條路由接受兩個選填的查詢參數 `organizationId` 和 `projectId`。如果數據集不屬於指定租戶的範圍、實驗不存在，或實驗不屬於該數據集，路由會傳回 `404`。

如果沒有數據集參照，請使用頂層路由。例如，刪除數據集時會清除實驗的 `datasetId`，令實驗失去與數據集的關聯。

```bash
curl -X DELETE http://localhost:4111/api/experiments/experiment-id
```

頂層路由接受選填的 `organizationId` 和 `projectId` 查詢參數。傳入任何一個參數，刪除操作便只適用於指定的租戶範圍。租戶範圍不相符時，路由會傳回 `{ "success": true }` 並保留實驗。如果沒有傳入租戶參數，而實驗亦不存在，路由會傳回 `404`。

刪除成功後，路由會傳回 `{ "success": true }`。如果租戶範圍不相符，頂層路由會傳回同一個回應，並保留所有數據。如果已安裝的 `@mastra/core` 沒有透過 `experiment-deletion` 功能標記表明支援，兩條路由都會傳回 `501`，包括仍未支援這項功能的舊版本。儲存層不支援可觀測性或刪除 Trace 時，Mastra 會記下警告並保留 Trace，同時刪除實驗和結果記錄。如果 Trace 因其他原因刪除失敗，路由會傳回 `500`，並保留實驗和結果記錄。Trace 每批刪除 1,000 條，因此部分 Trace 可能已經移除。請再次發出請求以完成刪除。

### 永久清除數據集項目 {/* #purge-a-dataset-item */}

`DELETE /api/datasets/:datasetId/items/:itemId/purge` 會從所有舊版本、刪除標記及關聯的實驗結果中，永久清除該項目已儲存的內容。這項操作不會建立新的數據集版本，亦無法復原。完整的清除行為見 [`dataset.purgeItem()`](/reference/datasets/purgeItem)。

```bash
curl -X DELETE http://localhost:4111/api/datasets/dataset-id/items/item-id/purge
```

此路由接受可選的查詢參數 `organizationId` 及 `projectId`。如果數據集不屬於指定的租戶範圍，或該項目在數據集中沒有歷史記錄，路由會回傳 `404`。如果已安裝的 `@mastra/core` 沒有透過 `dataset-item-purge` 功能旗標表明支援此操作，路由會回傳 `501`。如 MongoDB 儲存層不支援交易，路由會在改動任何數據之前回傳 `500`。徹底清除成功後會回傳 `{ "success": true }`。

### 由調用方控制的實驗路由 {/* #caller-driven-experiment-routes */}

如果實驗循環由你自己的編排器（例如 Temporal Workflow）控制，並以 Mastra 保存正式記錄，便可使用這些路由。執行實驗項目、提交結果和結束實驗都可以安全重試。建立實驗的請求只有在包含調用方提供的 `id` 時才可以安全重試，否則每次重試都會建立新實驗。執行項目及提交結果時，會以 `(experimentId, itemId, attempt)` 為鍵更新或插入結果。實驗若已完成，結束操作會回傳已儲存的實驗記錄。

#### 建立實驗的請求主體 {/* #create-experiment-request-body */}

向 `/api/datasets/:datasetId/experiments` 發送包含 `start: false` 的 POST 請求，即可建立實驗而不執行它。如果要由 Mastra 透過執行項目的路由處理各項，請一併提供 `targetType` 和 `targetId`。如果只經結果路由匯入結果，便可省略這兩個欄位。

```typescript oxfmt:false
{
  start?: boolean;              // false creates the experiment without running it. Defaults to true.
  id?: string;                  // Caller-supplied experiment id (e.g. a workflow run id) for idempotent creates
  targetType?: 'agent' | 'workflow' | 'scorer'; // Provide with targetId, or omit both
  targetId?: string;
  scorerIds?: string[];         // Run-level scorer ids, resolved server-side. Requires a target when start is false.
  name?: string;
  description?: string;
  metadata?: Record<string, unknown>;
  version?: number;             // Pin to a specific dataset version (defaults to latest)
  provenance?: {
    source?: string;
    sourceId?: string;
    sourceVersion?: string;
    metadata?: Record<string, unknown>;
  };
  grouping?: {                  // Stable grouping dimensions for comparisons and repeated trials
    experimentSetId?: string;
    comparisonId?: string;
    variantId?: string;
    trialIndex?: number;
  };
}
```

`start` 為 `false` 時，路由會回傳 `{ experimentId, status, totalItems, datasetVersion }`。

#### 執行實驗項目的請求主體 {/* #run-experiment-item-request-body */}

`POST /api/datasets/:datasetId/experiments/:experimentId/items/:itemId/run` 會以單個項目為輸入執行實驗目標，再執行解析所得的評分器，然後更新或插入結果。這個路由只適用於建立時已指定目標的實驗。

```typescript oxfmt:false
{
  attempt?: number;             // Zero-based repetition index. Defaults to 0.
  requestContext?: Record<string, unknown>; // Merged with the item's own request context (item wins)
}
```

回傳 `{ result, scores }`，當中包含已儲存的結果記錄，以及該項目所得的分數。

#### 提交實驗結果的請求主體 {/* #submit-experiment-result-request-body */}

```typescript oxfmt:false
{
  itemId: string;               // Dataset item this result belongs to
  attempt?: number;             // Zero-based repetition index. Defaults to 0.
  input?: unknown;              // Defaults to the dataset item input
  output?: unknown;             // Output produced by the external runner
  groundTruth?: unknown;        // Defaults to the dataset item groundTruth
  error?: {                     // Failure info when the item run failed
    message: string;
    stack?: string;
    code?: string;
  } | null;
  startedAt?: string;           // ISO date
  completedAt?: string;         // ISO date
  traceId?: string;
  scores?: Array<{              // Externally computed scores, persisted keyed by runId = experimentId
    scorerId: string;
    scorerName?: string;
    score: number;
    reason?: string;
    metadata?: Record<string, unknown>;
  }>;
}
```

回傳已儲存的實驗結果記錄。

#### 完成實驗 {/* #finalize-experiment */}

`POST /api/datasets/:datasetId/experiments/:experimentId/finalize` 無須傳送請求主體。伺服器會根據已儲存的結果記錄按項目統計，將實驗標記為 `completed`，並回傳更新後的實驗記錄。`succeededCount` 是至少有一次嘗試沒有出錯的項目數，`failedCount` 是每次嘗試均出錯的項目數，`skippedCount` 是從未提交結果的項目數。

#### 調用方控制實驗的錯誤回應 {/* #caller-driven-experiment-error-responses */}

|狀態 |出現情況 |
| - | - |
|`400` | 向有指定目標的實驗提交結果（`EXPERIMENT_HAS_TARGET`）、要求執行沒有指定目標的實驗項目（`EXPERIMENT_HAS_NO_TARGET`）、沒有同時提供 `targetType` 及 `targetId`（`EXPERIMENT_INVALID_TARGET`），或實驗固定使用的數據集版本沒有任何項目（`EXPERIMENT_NO_ITEMS`） |
| `404` | 找不到數據集、實驗、數據集項目或目標（`EXPERIMENT_TARGET_NOT_FOUND`） |
| `409` | 調用方提供的實驗 `id` 已用於另一個數據集或目標（`EXPERIMENT_ID_CONFLICT`），或在實驗結束後收到調用（`EXPERIMENT_ALREADY_FINALIZED`） |

### 評分器列表回應 {/* #list-scorers-response */}

回應是一組鍵值配對，涵蓋透過 [`Mastra` 類別](/reference/core/mastra-class)的 `scorers` 選項登記的評分器，以及連結至 Agent 及 Workflow 的評分器。Agent 所用的評分器和透過選項登記的評分器以評分器 ID 為鍵。Workflow 所用的評分器目前以評分器名稱為鍵。調用 `/api/scores/scorers/:scorerId` 時使用回應所列的鍵。按評分器 ID 查詢已儲存的分數時，則使用 `scorer.config.id`。

```typescript oxfmt:false
{
  [scorerId: string]: {
    scorer: {
      config: {
        id: string;
        name?: string;
        description: string;
        type?: unknown;
        judge?: unknown;
      };
    };
    sampling?: object;
    agentIds: string[];
    agentNames: string[];
    workflowIds: string[];
    isRegistered: boolean;             // True when the scorer is in the Mastra `scorers` option
    source: 'code' | 'stored' | 'fs';
  };
}
```

受支援的 API 規格只涵蓋 `scorer.config`。`scorer` 物件另有 `steps` 等實作欄位，這些欄位可能因版本而異。

`GET /api/scores/scorers/:scorerId` 回傳一筆結構相同的記錄。如果 ID 無法識別，路由會回傳 `null`，狀態碼為 200，而非 404。

### 分數列表查詢參數 {/* #score-list-query-parameters */}

```typescript oxfmt:false
{
  page?: number;        // Page number (0-indexed)
  perPage?: number;     // Items per page (default: 10)
  entityId?: string;    // `/api/scores/scorer/:scorerId` only
  entityType?: string;  // `/api/scores/scorer/:scorerId` only
}
```

使用 `/api/scores/entity/:entityType/:entityId` 時，請以 `AGENT` 或 `WORKFLOW` 作為 `entityType`，並以相應 Agent 或 Workflow 的登記鍵作為 `entityId`。伺服器先以該鍵找出實體本身的 `id`，再查詢儲存層。其他 `entityType` 值會原樣交給儲存層。

### 分數列表回應 {/* #score-list-response */}

```typescript oxfmt:false
{
  pagination: {
    total: number;
    page: number;
    perPage: number;
    hasMore: boolean;
  };
  scores: ScoreRowData[];
}
```

每筆記錄的結構與[持久儲存分數](/docs/evals/overview#score-persistence)時寫入的一致。最常讀取的欄位有 `id`、`scorerId`、`runId`、`entityId`、`score`、`output`、`scorer`、`entity` 和 `source`（`LIVE` 或 `TEST`），可選欄位 `entityType`、`input`、`reason`、`traceId`、`spanId`、`resourceId` 和 `threadId`，以及時間戳 `createdAt` 和 `updatedAt`。記錄亦包含評分器中間步驟的結果及提示詞。如未設定 `scores` 儲存區，列表路由會回傳沒有記錄的分頁結果，而不會回傳錯誤。

### 儲存分數的請求主體 {/* #save-score-request-body */}

```typescript oxfmt:false
{
  score: Omit<ScoreRowData, 'id' | 'createdAt' | 'updatedAt'> & { id?: string };
}
```

所提供的 `id` 會如何處理，視乎儲存轉接器而定。有些轉接器會按該值更新或插入記錄，有些則每次都產生新 ID，因而可能在重試提交時產生重複記錄。回應為 `{ score: ScoreRowData }`，當中包含已儲存的記錄。儲存分數必須設定儲存層，否則路由會回傳 500。

|`GET` | `/api/mcp/v0/servers` | 列出 MCP 伺服器 |
| `GET` | `/api/mcp/v0/servers/:id` | 取得伺服器詳情 |
| `GET` | `/api/mcp/:serverId/tools` | 列出伺服器上的 Tool |
| `GET` | `/api/mcp/:serverId/tools/:toolId` | 取得 Tool 詳情 |
| `POST` | `/api/mcp/:serverId/tools/:toolId/execute` | 執行 Tool |
| `GET` | `/api/mcp/:serverId/resources` | 列出伺服器資源 |
| `POST` | `/api/mcp/:serverId/resources/read` | 讀取一項資源 |
| `GET` | `/api/mcp/:serverId/tasks` | 列出伺服器近期的 MCP 任務（實驗功能） |
| `POST` | `/api/mcp/:serverId/tasks/find` | 按任務 ID 尋找 MCP 任務（實驗功能） |
| `POST` | `/api/mcp/:serverId/tasks/:taskKey/cancel` | 取消 MCP 任務（實驗功能） |
| `POST` | `/api/mcp/:serverId/tasks/:taskKey/input` | 回覆 MCP 任務的輸入請求（實驗功能） |
| `ALL` | `/api/mcp/:serverId/mcp` | MCP HTTP 傳輸 |
| `ALL` | `/api/mcp/:serverId/sse` | 舊版 MCP SSE 傳輸 |
| `POST` | `/api/mcp/:serverId/messages` | 舊版 MCP SSE 訊息 |

所有 MCP 路由均宣告 `requiresAuth: true`。只有設定了 `server.auth`，路由才會強制驗證身份。使用 RBAC Provider 時，列出和搜尋任務需要 `mcp:read` 權限。取消任務或回覆任務的輸入請求需要 `mcp:write` 權限，因為這些操作會影響另一個客戶端啟動的任務。路徑採用預設的 `/api` 前綴。對於 MCP v2 伺服器，舊版 SSE 路由會回傳 `404`。

## 常用查詢參數 {/* #common-query-parameters */}

### 分頁 {/* #pagination */}

大部分用於列出資源的端點均支援以下分頁參數：

```typescript oxfmt:false
{
  page?: number;   // Page number (0-indexed)
  perPage?: number; // Items per page (default: 10)
}
```

### 篩選 {/* #filtering */}

查詢 Workflow 執行記錄時，可用以下參數篩選結果：

```typescript oxfmt:false
{
  fromDate?: string;  // ISO date string
  toDate?: string;    // ISO date string
  status?: string;    // Run status filter
  resourceId?: string; // Filter by resource
}
```

## 錯誤回應 {/* #error-responses */}

所有路由均以以下格式回傳錯誤：

```typescript oxfmt:false
{
  error: string;      // Error message
  details?: unknown;  // Additional details
}
```

常見狀態碼：

|狀態碼|含義|
| - | - |
| 400 | 無效請求：參數無效 |
| 401 | 未獲授權：未提供有效的身份驗證資料 |
| 403 | 禁止存取：權限不足 |
| 404 | 找不到資源：資源不存在 |
| 500 | 伺服器內部錯誤 |
