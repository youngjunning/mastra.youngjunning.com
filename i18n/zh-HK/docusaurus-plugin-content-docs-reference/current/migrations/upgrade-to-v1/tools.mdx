# Tool

Tool 的執行函式現分別接收輸入及上下文參數，上下文屬性亦已重新整理。

## 變更內容 {/* #changed */}

### `createTool` 的執行函式簽章改為 `(inputData, context)` {/* #createtool-execute-signature-to-inputdata-context-format */}

所有 `createTool` 的執行函式現分別接收 `inputData` 及 `context` 兩個參數，不再接收單一解構物件。Tool 輸入及執行上下文因此分開傳入。

此簽章變更僅適用於 `createTool`。Workflow 中的 `createStep` 呼叫仍保留 `async (inputData, context)` 簽章。

遷移時，請將 `createTool` 的執行函式簽章改為：第一個參數是 `inputData`（型別由 `inputSchema` 決定），第二個參數是 `context`。

```diff
  createTool({
    id: 'weather-tool',
-   execute: async ({ context, requestContext, mastra }) => {
-     const location = context.location;
-     const userTier = requestContext.get('userTier');
-     return getWeather(location, userTier);
-   },
+   execute: async (inputData, context) => {
+     const location = inputData.location;
+     const userTier = context?.requestContext?.get('userTier');
+     return getWeather(location, userTier);
+   },
  });
```

### `createTool` 上下文屬性的組織方式 {/* #createtool-context-properties-organization */}

`createTool` 的上下文屬性現按命名空間分類：Agent 專屬屬性位於 `context.agent`，Workflow 專屬屬性位於 `context.workflow`，MCP 專屬屬性位於 `context.mcp`。這樣可令這些屬性的 API 結構更清晰。

在 Agent 內執行的 Tool，應經由 `context.agent` 存取 Agent 專屬屬性。

```diff
  createTool({
    id: 'suspendable-tool',
    suspendSchema: z.object({ message: z.string() }),
    resumeSchema: z.object({ approval: z.boolean() }),
-   execute: async ({ context, suspend, resumeData }) => {
-     if (!resumeData) {
-       return await suspend({ message: 'Waiting for approval' });
-     }
-     if (resumeData.approval) {
-       return { success: true };
-     }
-   },
+   execute: async (inputData, context) => {
+     if (!context?.agent?.resumeData) {
+       return await context?.agent?.suspend({
+         message: 'Waiting for approval',
+       });
+     }
+     if (context.agent.resumeData.approval) {
+       return { success: true };
+     }
+   },
  });
```

在 Workflow 內執行的 Tool，應經由 `context.workflow` 存取 Workflow 專屬屬性。

```diff
  createTool({
    id: 'workflow-tool',
-   execute: async ({ workflowId, runId, state, setState }) => {
-     const currentState = state;
-     setState({ step: 'completed' });
-     return { result: 'done' };
-   },
+   execute: async (inputData, context) => {
+     const currentState = context?.workflow?.state;
+     context?.workflow?.setState({ step: 'completed' });
+     return { result: 'done' };
+   },
  });
```

執行 Tool 時，會根據 `suspendSchema` 驗證 `suspendPayload`。若 `suspendPayload` 不符合 `suspendSchema`，處理方式取決於 Tool 的執行方式：

* **Agent**：驗證錯誤會作為 Tool 輸出回傳，並記錄一則警告，但暫停程序會繼續。
* **直接呼叫 `execute()`**：驗證錯誤會作為 Tool 輸出回傳，不會記錄警告。
* **Workflow 步驟**：該步驟會因暫停資料驗證錯誤而失敗，Workflow 執行亦會失敗。

此外，恢復 Tool 時，會根據 `resumeSchema` 驗證 `resumeData`。若 `resumeData` 不符合 `resumeSchema`，Tool 會回傳 `ValidationError`，無法繼續恢復。

如要略過 `suspendSchema` 或 `resumeSchema` 驗證，建立 Tool 時不要定義相應的 `suspendSchema` 或 `resumeSchema`。

:::note
有關 MCP 專屬 Tool 上下文的變更，請參閱 [MCP 遷移指南](/reference/migrations/upgrade-to-v1/mcp)。
:::

### `RuntimeContext` 更名為 `RequestContext` {/* #runtimecontext-to-requestcontext */}

在整個 Tool 執行上下文中，`RuntimeContext` 類別已更名為 `RequestContext`。新名稱表明此類別儲存的是與請求相關的資料。

遷移時，請將 Tool 執行函式中對 `runtimeContext` 的參照改為 `requestContext`。

```diff
  createTool({
    id: 'my-tool',
    execute: async (inputData, context) => {
-     const userTier = context?.runtimeContext?.get('userTier');
+     const userTier = context?.requestContext?.get('userTier');
      return { result: userTier };
    },
  });
```

:::tip[Codemod]

可使用 Mastra 的 codemod CLI 自動更新匯入：

```bash
npx @mastra/codemod@latest v1/runtime-context .
```

:::

這項變更適用於所有 Tool 執行方式，包括直接呼叫，以及經由 Agent 或 Workflow 呼叫。收窄結果型別後，便可正確處理驗證錯誤，並避免存取輸出屬性時出現執行階段錯誤。

### 使用 `outputSchema` 驗證 Tool 輸出 {/* #tool-output-validation-with-outputschema */}

定義了 `outputSchema` 的 Tool 現會在執行階段驗證回傳值。以往，`outputSchema` 只用於型別推斷，不會實際驗證輸出。

若 Tool 回傳的資料不符合其 `outputSchema`，現會回傳 `ValidationError`，而非無效資料。這是預設的 `outputValidation: 'strict'` 行為。使用 [`outputValidation: 'warn'`](/reference/tools/create-tool) 時，Mastra 會記錄不相符的情況，並原樣回傳輸出。

如要修正驗證錯誤，請確保 Tool 輸出符合 schema 定義：

```diff
  const getUserTool = createTool({
    id: "get-user",
    outputSchema: z.object({
      id: z.string(),
      name: z.string(),
      email: z.string().email(),
    }),
    execute: async (inputData) => {
-     return { id: "123", name: "John" }; // Missing email
+     return { id: "123", name: "John", email: "john@example.com" };
    },
  });
```

驗證失敗時，Tool 會回傳 `ValidationError`：

```diff
+ // Before v1 - invalid output would silently pass through
  await getUserTool.execute({});
- // { id: "123", name: "John" } - missing email
+ // {
+ //   error: true,
+ //   message: "Tool output validation failed for get-user. The tool returned invalid output:\n- email: Required\n\nReturned output: {...}",
+ //   validationErrors: { ... }
+ // }
```

### `tool.execute` 的回傳型別包含 `ValidationError` {/* #toolexecute-return-type-includes-validationerror */}

為處理驗證失敗，`tool.execute` 的回傳型別現包含 `ValidationError`。存取輸出 schema 定義的屬性前，必須先收窄結果型別，才能通過 TypeScript 型別檢查。

呼叫 `tool.execute` 時，請先檢查結果是否包含錯誤，再存取輸出屬性：

```typescript
const result = await getUserTool.execute({})

// Type-safe check for validation errors
if ('error' in result && result.error) {
  console.error('Validation failed:', result.message)
  console.error('Details:', result.validationErrors)
  return
}

// TypeScript knows result is valid here
console.log(result.id, result.name, result.email)
```

亦可更新 `outputSchema`，使其與實際輸出一致；若無須驗證，則可完全移除 `outputSchema`。

### 直接執行 Tool {/* #direct-tool-execution */}

為支援由其他程式碼另行處理執行邏輯的客戶端 Tool 定義，`tool.execute` 屬性在型別系統中屬可選。直接在 Tool 實例上呼叫 `execute`（而非經由 Agent 或 Workflow 呼叫）時，請使用可選串連或非空斷言：

```typescript
// Optional chaining (recommended)
const result = await weatherTool.execute?.({ location: 'New York' }, {})

// Non-null assertion (when you know execute exists)
const result = await weatherTool.execute!({ location: 'New York' }, {})
```
