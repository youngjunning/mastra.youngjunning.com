# OpenTelemetry

Mastra 透過 OpenTelemetry (OTEL) 匯出器，把追蹤及日誌傳送至兼容平台；亦可透過 Bridge 加入現有的 OTEL 追蹤上下文。

## 匯出器 {/* #exporter */}

OpenTelemetry 匯出器依照標準化的 [OpenTelemetry GenAI 語義慣例](https://opentelemetry.io/docs/specs/semconv/gen-ai/)傳送追蹤及日誌，因此廣泛兼容 Datadog、New Relic、Sentry、SigNoz、MLflow、Latitude、Dash0、Traceloop、Laminar、telemetry.dev、Sazabi 等平台。

### 安裝 {/* #installation */}

每個 Provider 都需要相應的協定套件。請安裝基礎匯出器，以及該 Provider 所需的協定套件：

#### 適用於 HTTP/Protobuf Provider（SigNoz、New Relic、Sentry、Laminar、MLflow、Latitude、telemetry.dev） {/* #for-httpprotobuf-providers-signoz-new-relic-sentry-laminar-mlflow-latitude-telemetrydev */}

```bash npm2yarn
npm install @mastra/otel-exporter@latest @opentelemetry/exporter-trace-otlp-proto
```

#### 適用於 `gRPC` Provider（Dash0、Datadog） {/* #for-grpc-providers-dash0-datadog */}

```bash npm2yarn
npm install @mastra/otel-exporter@latest @opentelemetry/exporter-trace-otlp-grpc @grpc/grpc-js
```

#### 適用於 HTTP/JSON Provider（Traceloop、Sazabi） {/* #for-httpjson-providers-traceloop-sazabi */}

```bash npm2yarn
npm install @mastra/otel-exporter@latest @opentelemetry/exporter-trace-otlp-http
```

### 環境變數 {/* #environment-variables */}

所有 Provider 都支援透過環境變數進行零設定。設定相應變數後，匯出器便會自動使用：

| Provider | 環境變數 |
| - | - |
| Dash0 | `DASH0_API_KEY`（必填）、`DASH0_ENDPOINT`（必填）、`DASH0_DATASET`（可選） |
| SigNoz | `SIGNOZ_API_KEY`（必填）、`SIGNOZ_REGION`（可選）、`SIGNOZ_ENDPOINT`（可選） |
| New Relic | `NEW_RELIC_LICENSE_KEY`（必填）、`NEW_RELIC_ENDPOINT`（可選） |
| Traceloop | `TRACELOOP_API_KEY`（必填）、`TRACELOOP_DESTINATION_ID`、`TRACELOOP_ENDPOINT`（可選） |
| Laminar | `LMNR_PROJECT_API_KEY`（必填）、`LAMINAR_ENDPOINT`（可選） |

### Provider 設定 {/* #provider-configurations */}

#### Sentry {/* #sentry */}

[Sentry](https://sentry.io/) 透過 OTLP 端點接收 OpenTelemetry 追蹤及日誌。在 Sentry 開啟 [**Project Settings** > **Client Keys (DSN)**](https://sentry.io/settings/projects/)，複製 OTLP 追蹤端點及驗證標頭，並把兩者加入環境變數：

```bash title=".env"
SENTRY_OTLP_ENDPOINT=https://o000000.ingest.sentry.io/api/0000000/integration/otlp/v1/traces
SENTRY_OTLP_AUTH_HEADER="sentry sentry_key=..."
```

使用採用 HTTP/Protobuf 的 `custom` Provider：

```typescript title="src/mastra/index.ts"
new OtelExporter({
  provider: {
    custom: {
      endpoint: process.env.SENTRY_OTLP_ENDPOINT!,
      protocol: 'http/protobuf',
      headers: {
        'x-sentry-auth': process.env.SENTRY_OTLP_AUTH_HEADER!,
      },
    },
  },
})
```

端點設定、支援的訊號及目前的數據接收限制，請參閱 [Sentry 的 OTLP 文件](https://docs.sentry.io/concepts/otlp/)。

按你的部署方式選擇匯出器：

- `OtelExporter`：透過 OTLP 傳送不綁定特定供應商的追蹤及日誌。適合已有 OpenTelemetry 管線，或希望日後能更換後端的情況。
- [`SentryExporter`](/integrations/observability/sentry)：使用 Sentry SDK 把 Mastra span 類型對應至 Sentry 操作、加入 AI 監控屬性，並把 span 錯誤記錄為 Sentry 問題。

#### MLflow {/* #mlflow */}

[MLflow](https://mlflow.org/docs/latest/genai/tracing/integrations/listing/mastra) 透過 `/v1/traces` OTLP 端點原生支援 Mastra 追蹤。使用採用 HTTP/Protobuf 的 `custom` Provider，並提供實驗標頭，讓追蹤導向正確的 MLflow 實驗：

```typescript title="src/mastra/index.ts"
new OtelExporter({
  provider: {
    custom: {
      endpoint: `${process.env.MLFLOW_TRACKING_URI}/v1/traces`,
      protocol: 'http/protobuf',
      headers: {
        'x-mlflow-experiment-id': process.env.MLFLOW_EXPERIMENT_ID,
      },
    },
  },
})
```

#### Latitude {/* #latitude */}

[Latitude](https://latitude.so) 是接收 OTLP 追蹤的開源 LLM 可觀測性及評估平台。使用採用 HTTP/Protobuf 的 `custom` Provider，把端點指向 Latitude 的數據接收位址，並以 API 金鑰及項目 slug 驗證身分：

```typescript title="src/mastra/index.ts"
new OtelExporter({
  provider: {
    custom: {
      endpoint: 'https://ingest.latitude.so/v1/traces',
      protocol: 'http/protobuf',
      headers: {
        Authorization: `Bearer ${process.env.LATITUDE_API_KEY}`,
        'X-Latitude-Project': process.env.LATITUDE_PROJECT,
      },
    },
  },
})
```

你可以到 [console.latitude.so](https://console.latitude.so/login) 註冊，亦可自行託管，並把端點指向自己的數據接收主機。

#### telemetry.dev {/* #telemetrydev */}

[telemetry.dev](https://telemetry.dev) 接收 OTLP/HTTP Protobuf 追蹤，並把 OpenTelemetry GenAI 語義慣例整理為模型、Provider、token、延遲及成本欄位。使用 `custom` Provider，並提供項目 API 金鑰：

```bash title=".env"
TELEMETRY_DEV_API_KEY=td_live_...
```

```typescript title="src/mastra/index.ts"
new OtelExporter({
  provider: {
    custom: {
      endpoint: 'https://ingest.telemetry.dev/v1/traces',
      protocol: 'http/protobuf',
      headers: {
        Authorization: `Bearer ${process.env.TELEMETRY_DEV_API_KEY}`,
      },
    },
  },
})
```

#### Sazabi {/* #sazabi */}

[Sazabi](https://sazabi.com) 是接收 OTLP 追蹤的 AI 原生可觀測性平台。在 Sazabi 新增 Mastra 日誌來源，並複製其數據接收 URL。該 URL 已包含項目金鑰，因此毋須驗證標頭：

```bash title=".env"
SAZABI_INTAKE_URL=https://...
```

使用採用 HTTP/JSON 的 `custom` Provider：

```typescript title="src/mastra/index.ts"
new OtelExporter({
  provider: {
    custom: {
      endpoint: process.env.SAZABI_INTAKE_URL!,
      protocol: 'http/json',
    },
  },
})
```

完整設定方式請參閱 [Sazabi 的 Mastra 指南](https://docs.sazabi.com/catalogs/log-sources/send-to-an-endpoint/mastra)。

#### Dash0 {/* #dash0 */}

[Dash0](https://www.dash0.com/) 提供即時可觀測性及自動產生的洞察。

##### 零配置設定 {/* #zero-config-setup */}

設定環境變數，再以空設定使用匯出器：

```bash title=".env"
# Required
DASH0_API_KEY=your-api-key
DASH0_ENDPOINT=ingress.us-west-2.aws.dash0.com:4317

# Optional
DASH0_DATASET=production
```

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'
import { OtelExporter } from '@mastra/otel-exporter'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      otel: {
        serviceName: 'my-service',
        exporters: [new OtelExporter({ provider: { dash0: {} } })],
      },
    },
  }),
})
```

##### 明確配置 {/* #explicit-configuration */}

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'
import { OtelExporter } from '@mastra/otel-exporter'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      otel: {
        serviceName: 'my-service',
        exporters: [
          new OtelExporter({
            provider: {
              dash0: {
                apiKey: process.env.DASH0_API_KEY,
                endpoint: process.env.DASH0_ENDPOINT, // e.g., 'ingress.us-west-2.aws.dash0.com:4317'
                dataset: 'production', // Optional dataset name
              },
            },
            resourceAttributes: {
              // Optional OpenTelemetry Resource Attributes for the trace
              ['deployment.environment']: 'dev',
            },
          }),
        ],
      },
    },
  }),
})
```

:::note

從 Dash0 儀表板取得端點。格式應為 `ingress.{region}.aws.dash0.com:4317`。

:::

#### Datadog {/* #datadog */}

[Datadog](https://www.datadoghq.com/) APM 透過分散式追蹤監控應用程式效能。若要透過 OTLP 把追蹤傳送至 Datadog，必須執行已啟用 OTLP 數據接收的 Datadog Agent。

Datadog 透過 gRPC 接收 OTLP 數據。為確保正常運作，必須明確匯入相依套件，並完成[打包工具設定](/reference/configuration#bundlerexternals)：

```typescript title="src/mastra/index.ts"
// Explicitly import gRPC dependencies for the bundler
import '@grpc/grpc-js'
import '@opentelemetry/exporter-trace-otlp-grpc'
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'
import { OtelExporter, type ExportProtocol } from '@mastra/otel-exporter'

export const mastra = new Mastra({
  // Add grpc-js to externals so it's handled at runtime
  bundler: {
    externals: ['@grpc/grpc-js'],
  },
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-service',
        exporters: [
          new OtelExporter({
            provider: {
              custom: {
                endpoint: process.env.OTEL_EXPORTER_OTLP_ENDPOINT || 'http://localhost:4317',
                protocol: (process.env.OTEL_EXPORTER_OTLP_PROTOCOL || 'grpc') as ExportProtocol,
                headers: {},
              },
            },
          }),
        ],
      },
    },
  }),
})
```

:::note

必須在 Datadog Agent 啟用 OTLP 數據接收。請把以下設定加入 `datadog.yaml`：

```yaml
otlp_config:
  receiver:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
```

在本機執行 Datadog Agent 時，預設 OTLP 端點為 `http://localhost:4317`。

:::

:::warning

要讓 gRPC 傳輸正常運作，必須在檔案頂部明確匯入 `@grpc/grpc-js` 和 `@opentelemetry/exporter-trace-otlp-grpc`，並設定 [`bundler.externals`](/reference/configuration#bundlerexternals)。缺少這些設定可能引致連線問題。

:::

:::tip Datadog 原生匯出器

若需要 Datadog 專屬功能，例如自動對應 span 類型、分類 LLM span，或想省去 gRPC 設定，可考慮改用專屬的 [`@mastra/datadog`](/integrations/observability/datadog) 匯出器。它針對 Datadog APM 平台作了優化。

:::

### 訊號 {/* #signals */}

導出器發送兩個 OpenTelemetry 訊號：

- 追蹤：Mastra span，透過 `BatchSpanProcessor` 匯出。
- 日誌：Mastra 日誌事件，透過 `BatchLogRecordProcessor` 匯出。帶有 `traceId` 及 `spanId` 的日誌，會同時利用 OTEL 日誌記錄的原生追蹤上下文，以及 `mastra.traceId` / `mastra.spanId` 屬性與追蹤關聯，讓 Datadog、Grafana 和 Honeycomb 等後端自動把日誌與追蹤連繫起來。

兩種訊號預設均已啟用，並共用相同的 Provider 設定。日誌端點由追蹤端點衍生：把結尾的 `/v1/traces` 換成 `/v1/logs`。

若要停用某種訊號，請設定 `signals` 選項：

```typescript title="src/mastra/index.ts"
new OtelExporter({
  provider: {/* ... */},
  signals: {
    traces: true, // default
    logs: false, // disable log export
  },
})
```

若要匯出日誌，還須安裝與所用協定相符的 OTLP 日誌匯出器套件：

```bash npm2yarn
# HTTP/JSON
npm install @opentelemetry/exporter-logs-otlp-http
# HTTP/Protobuf
npm install @opentelemetry/exporter-logs-otlp-proto
# gRPC
npm install @opentelemetry/exporter-logs-otlp-grpc @grpc/grpc-js
```

若未安裝相符的日誌匯出器套件，日誌匯出會靜默停用，追蹤匯出則可繼續運作。

### 配置選項 {/* #configuration-options */}

#### 完整配置 {/* #complete-configuration */}

```typescript
new OtelExporter({
  // Provider configuration (required)
  provider: {
    // Use one of: dash0, signoz, newrelic, traceloop, laminar, custom
  },

  // Per-signal toggles. Both default to true.
  signals: {
    traces: true,
    logs: true,
  },

  // Export configuration
  timeout: 30000, // Export timeout in milliseconds
  batchSize: 100, // Number of spans/logs per batch

  // Debug options
  logLevel: 'info', // 'debug' | 'info' | 'warn' | 'error'
})
```

### `OpenTelemetry` 語義慣例 {/* #opentelemetry-semantic-conventions */}

匯出器遵循 [OpenTelemetry GenAI 語義慣例 v1.38.0](https://github.com/open-telemetry/semantic-conventions/tree/v1.38.0/docs/gen-ai)，以兼容各種可觀測性平台：

#### Span 命名 {/* #span-naming */}

- **模型呼叫**：`chat {model}`
- **生成循環**：`model_generation {model}`，每一輪各有一個 `agent_step {agent_id}`
- **Tool 執行**：`execute_tool {tool_name}`
- **Agent 執行**：`invoke_agent {agent_id}`
- **Workflow 執行**：`invoke_workflow {workflow_id}`

Agent 每一輪只呼叫模型一次。`chat` span 對應該次呼叫，也是唯一包含 `gen_ai.request.model`、訊息及 `gen_ai.usage.*` 的 span，因此後端加總各 span 的用量時，每次呼叫只會計算一次。`model_generation` span 涵蓋整個循環，`agent_step` 涵蓋一輪操作（模型呼叫及 Tool 執行）；兩者都不帶用量數據。

#### 關鍵屬性 {/* #key-attributes */}

- `gen_ai.operation.name` — 操作類型（如 chat、tool.execute）
- `gen_ai.provider.name` — AI Provider（如 openai、anthropic）
- `gen_ai.request.model` — 模型識別碼
- `gen_ai.input.messages` — 提供給模型的對話紀錄
- `gen_ai.output.messages` — 模型傳回的訊息
- `gen_ai.usage.input_tokens` — 輸入 token 數目
- `gen_ai.usage.output_tokens` — 輸出 token 數目
- `gen_ai.request.temperature` — 取樣溫度
- `gen_ai.response.finish_reasons` — 完成原因

### 協議選擇指南 {/* #protocol-selection-guide */}

按所用的 Provider 選擇正確的協定套件：

| Provider | 協定 | 所需套件 |
| - | - | - |
| Dash0 | gRPC | `@opentelemetry/exporter-trace-otlp-grpc` |
| Datadog | gRPC | `@opentelemetry/exporter-trace-otlp-grpc` |
| SigNoz | HTTP/Protobuf | `@opentelemetry/exporter-trace-otlp-proto` |
| New Relic | HTTP/Protobuf | `@opentelemetry/exporter-trace-otlp-proto` |
| Traceloop | HTTP/JSON | `@opentelemetry/exporter-trace-otlp-http` |
| Laminar | HTTP/Protobuf | `@opentelemetry/exporter-trace-otlp-proto` |
| Custom | 視乎情況 | 取決於所用的收集器 |

:::warning

請確認已安裝與 Provider 相符的協定套件。若安裝錯誤套件，匯出器會顯示有助排查的錯誤訊息。

:::

### 故障排除 {/* #troubleshooting */}

#### 缺少依賴錯誤 {/* #missing-dependency-error */}

如果您看到類似以下的錯誤：

```text
HTTP/Protobuf exporter is not installed (required for signoz).
To use HTTP/Protobuf export, install the required package:
  npm install @opentelemetry/exporter-trace-otlp-proto
```

請為所用 Provider 安裝錯誤訊息建議的套件。

#### 常見問題 {/* #common-issues */}

1. **協定套件錯誤**：確認已為 Provider 安裝正確的匯出器套件
2. **端點無效**：檢查端點格式是否符合 Provider 的要求
3. **驗證失敗**：確認 API 金鑰及標頭是否正確

## Bridge {/* #bridge */}

:::warning

OpenTelemetry Bridge 目前仍屬**實驗性功能**。API 及設定選項可能在日後版本變更。

:::

OpenTelemetry (OTEL) Bridge 讓 Mastra 的追蹤系統與現有 OpenTelemetry 基礎設施雙向整合。匯出器會把追蹤數據傳送到外部平台；Bridge 則建立原生 OTEL span，使其加入現有的分散式追蹤上下文。

### 何時使用 Bridge {/* #when-to-use-the-bridge */}

以下情況適合使用 `OtelBridge`：

- 應用程式已有 OTEL 插樁，例如 HTTP 伺服器或資料庫用戶端
- 希望 Mastra 操作成為現有 OTEL 追蹤的子 span
- 需要 Mastra Tool 內的 OTEL 插樁程式碼維持正確的父子關係
- 正在建立需要跨服務傳遞追蹤上下文的分散式系統

### 運作方式 {/* #how-it-works */}

`OtelBridge` 提供雙向整合：

**從 OTEL 到 Mastra：**

- 自動讀取 OTEL 環境上下文（AsyncLocalStorage）
- 從目前啟用的 OTEL span 繼承追蹤 ID 及父 span ID
- 遵循 OTEL 的取樣決定：若某項追蹤未被取樣，Mastra 亦不會為它建立 span
- 啟用 OTEL 自動插樁後，毋須手動傳遞追蹤 ID

**從 Mastra 到 OTEL：**

- 為 Mastra 操作（Agent、LLM 呼叫、Tool、Workflow）建立原生 OTEL span
- 在分散式追蹤中維持正確的父子關係
- 讓 Mastra 操作內已作 OTEL 插樁的程式碼（如 HTTP 用戶端及資料庫呼叫）正確巢狀排列
- 把 Mastra 日誌事件轉送至全域註冊的 OTEL `LoggerProvider`。Mastra span 內產生的日誌會在該 span 的 OTEL 上下文中發出，供後端與追蹤關聯。若未註冊 `LoggerProvider`，日誌傳送會靜默略過。

### 安裝 {/* #installation-1 */}

```bash npm2yarn
npm install @mastra/otel-bridge
```

Bridge 可配合現有的 OpenTelemetry 設定使用。視乎設定，你可能還需要以下部分套件：

- `@opentelemetry/sdk-node` — OTEL 的核心 Node.js SDK
- `@opentelemetry/auto-instrumentations-node` — 常用程式庫的自動插樁
- `@opentelemetry/exporter-trace-otlp-proto` — OTLP 匯出器（透過 HTTP 傳送 Protobuf）
- `@opentelemetry/exporter-trace-otlp-http` — OTLP 匯出器（透過 HTTP 傳送 JSON）
- `@opentelemetry/exporter-trace-otlp-grpc` — OTLP 匯出器（gRPC）
- `@opentelemetry/sdk-trace-base` — 基礎追蹤 SDK（供 `BatchSpanProcessor` 等使用）
- `@opentelemetry/core` — 核心工具（供 `W3CTraceContextPropagator` 等使用）
- `@opentelemetry/sdk-logs` 及 OTLP 日誌匯出器（如 `@opentelemetry/exporter-logs-otlp-http`）— 若亦要透過 Bridge 轉送 Mastra 日誌事件，就需要安裝

### 配置 {/* #configuration */}

使用 `OtelBridge` 需要兩個步驟：

1. 在應用程式中設定 OpenTelemetry 插樁
2. 把 `OtelBridge` 加入 Mastra 的可觀測性設定

#### 步驟 1：設定 OpenTelemetry 插樁 {/* #step-1-opentelemetry-instrumentation */}

建立用來初始化 OTEL 的插樁檔案。此檔案必須先於應用程式程式碼執行：

```typescript title="instrumentation.ts"
import { NodeSDK } from '@opentelemetry/sdk-node'
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node'
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-proto'
import { BatchSpanProcessor } from '@opentelemetry/sdk-trace-base'
import { W3CTraceContextPropagator } from '@opentelemetry/core'

const sdk = new NodeSDK({
  serviceName: 'my-service',
  spanProcessors: [
    new BatchSpanProcessor(
      new OTLPTraceExporter({
        url: process.env.OTEL_EXPORTER_OTLP_ENDPOINT || 'http://localhost:4318/v1/traces',
      }),
    ),
  ],
  instrumentations: [getNodeAutoInstrumentations()],
  textMapPropagator: new W3CTraceContextPropagator(),
})

sdk.start()

export { sdk }
```

#### 步驟 2：設定 Mastra {/* #step-2-mastra-configuration */}

把 `OtelBridge` 加入 Mastra 的可觀測性設定：

```typescript title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { Observability } from '@mastra/observability'
import { OtelBridge } from '@mastra/otel-bridge'

export const mastra = new Mastra({
  observability: new Observability({
    configs: {
      default: {
        serviceName: 'my-service',
        bridge: new OtelBridge(),
      },
    },
  }),
  agents: {/* your agents */},
})
```

使用 Bridge 時毋須 Mastra 匯出器。追蹤會按 OTEL SDK 設定傳送。若還想把追蹤傳送至其他目的地，亦可另外加入 Mastra 匯出器。

#### 轉送日誌（可選） {/* #forwarding-logs-optional */}

Bridge 亦會把 Mastra 日誌事件轉送至全域註冊的 OTEL `LoggerProvider`。若要同時接入日誌及追蹤，請在 `NodeSDK` 註冊日誌記錄處理器：

```typescript title="instrumentation.ts"
import { NodeSDK } from '@opentelemetry/sdk-node'
import { OTLPLogExporter } from '@opentelemetry/exporter-logs-otlp-http'
import { BatchLogRecordProcessor } from '@opentelemetry/sdk-logs'

const sdk = new NodeSDK({
  // ...trace config as usual
  logRecordProcessors: [
    new BatchLogRecordProcessor({
      exporter: new OTLPLogExporter({
        url: process.env.OTEL_EXPORTER_OTLP_LOGS_ENDPOINT || 'http://localhost:4318/v1/logs',
      }),
    }),
  ],
})
```

Mastra span 內產生的日誌會在該 span 的 OTEL 上下文中發出，因此 Datadog、Grafana 和 Honeycomb 等後端可自動把日誌與對應追蹤關聯。沒有追蹤上下文的日誌則使用目前啟用的 OTEL 上下文。

若未註冊 `LoggerProvider`，日誌傳送會靜默略過。追蹤仍會按現有設定運作。

#### 執行應用程式 {/* #running-your-application */}

使用 `--import` 旗標，確保插樁程式碼先於應用程式載入：

```bash
tsx --import ./instrumentation.ts ./src/index.ts
```

#### 結束前清空緩衝區 {/* #flushing-before-exit */}

Mastra 的 `flush()` 及 `shutdown()` 會要求已註冊的 OTEL Provider 清空緩衝區，但 `BatchSpanProcessor` 仍可能持有一批已開始匯出的數據。在無伺服器或短生命週期程序中，完成 Mastra 的 flush 後，還應呼叫 `await sdk.shutdown()`，確保程序結束時 OTEL SDK 不留存任何 span。只呼叫 Provider 自身的 `forceFlush()` 並不足夠：它不會等待匯出器正在傳送的批次。

### 語義慣例 {/* #semantic-conventions */}

`OtelBridge` 依照 [OpenTelemetry GenAI 語義慣例 v1.38.0](https://github.com/open-telemetry/semantic-conventions/tree/v1.38.0/docs/gen-ai) 匯出 Mastra span，其中包括標準化的 span 名稱（如 `chat {model}`、`execute_tool {tool_name}`）及屬性（如 `gen_ai.usage.input_tokens`、`gen_ai.request.model`）。

span 命名及屬性的詳情，請參閱 [OpenTelemetry 匯出器的語義慣例](#opentelemetry-semantic-conventions)。

### 追蹤層次結構 {/* #trace-hierarchy */}

使用 `OtelBridge` 時，追蹤可跨越 OTEL 與 Mastra 的邊界，維持正確的層級關係：

```text
HTTP POST /api/chat (from Hono middleware)
└── agent.assistant (from Mastra via OtelBridge)
    └── model_generation __AI_SDK_OPENAI_MODEL_BASE__ (generation loop)
        ├── agent_step assistant (turn 1)
        │   ├── chat __AI_SDK_OPENAI_MODEL_BASE__ (LLM call)
        │   └── execute_tool search (tool execution)
        │       └── HTTP GET api.example.com (from OTEL auto-instrumentation)
        └── agent_step assistant (turn 2)
            └── chat __AI_SDK_OPENAI_MODEL_BASE__ (follow-up LLM call)
```

### 多服務分散式追蹤 {/* #multi-service-distributed-tracing */}

`OtelBridge` 支援跨服務傳遞追蹤。當服務 A 透過 HTTP 呼叫服務 B，追蹤上下文會自動傳遞：

```text
Service A: HTTP POST /api/process
└── HTTP POST service-b/api/analyze (outgoing call)

Service B: HTTP POST /api/analyze (incoming call - same trace!)
└── agent.analyzer (Mastra agent inherits trace context)
    └── model_generation __AI_SDK_OPENAI_MODEL_BASE__
        └── agent_step analyzer
            └── chat __AI_SDK_OPENAI_MODEL_BASE__
```

兩個服務都必須具備：

1. 已設定 OTEL 插樁
2. 已啟用 W3C Trace Context 傳播器
3. 已為 Mastra 設定 `OtelBridge`

透過 HTTP 傳送至 Mastra `MCPServer` 的請求亦遵循相同規則。完成上述設定後，它會加入呼叫方的追蹤；若伺服器沒有 HTTP 插樁，每個請求則保留自己的追蹤。無論哪種情況，只要請求在 `_meta` 或 HTTP 標頭中帶有 W3C `traceparent`，請求 span 就會連結至呼叫方的 span，而匯出器及 Bridge 會把該連結作為 OpenTelemetry span link 傳送。請參閱[連結至呼叫方的追蹤](/reference/tools/mcp-server#linking-to-the-callers-trace)。

### 使用標籤 {/* #using-tags */}

標籤有助在 OTEL 後端分類及篩選追蹤。執行 Agent 或 Workflow 時可加入標籤：

```typescript
const result = await agent.generate('Hello', {
  tracingOptions: {
    tags: ['production', 'experiment-v2', 'user-request'],
  },
})
```

為了廣泛兼容各種後端，標籤會以 JSON 字串匯出至 `mastra.tags` span 屬性。常見用途包括：

- 環境標記：`"production"`、`"staging"`
- 實驗追蹤：`"experiment-v1"`、`"control-group"`
- 優先級：`"priority-high"`、`"batch-job"`

### 故障排除 {/* #troubleshooting-1 */}

若追蹤未如預期顯示或關聯：

- 確認 OTEL SDK 先於 Mastra 初始化（使用 `--import` 旗標，或在進入點檔案頂部匯入）
- 若看到 `[OtelBridge] No OpenTelemetry tracer provider is registered globally`，表示 Bridge 找不到 tracer Provider。有些框架會建立 Provider，但不會將其註冊至全域。此時可透過 `new OtelBridge({ tracerProvider })` 直接傳入該 Provider。請參閱[設定要求](/reference/observability/tracing/bridges/otel#setup-requirements)
- 確認已把 `OtelBridge` 加入可觀測性設定
- 檢查 OTEL 後端是否正在運行，而且可以存取
