# Temporal

[Temporal](https://temporal.io/) 是一個持久化執行平台，用於編排長時間運行並具備容錯能力的 Workflow。使用 `@mastra/temporal` 套件，你可透過標準 Mastra API 編寫 Workflow，並在 Temporal 叢集運行。

## Temporal 如何與 Mastra 配合使用 {/* #how-temporal-works-with-mastra */}

以 `createWorkflow()` 和 `createStep()` 編寫的 Mastra Workflow，會對應至 Temporal 的 Workflow 和活動模型。Temporal Worker 的 `MastraPlugin` 會在打包期間編譯 Mastra 入口檔案：

* 每個 `createStep()` 的處理函數會被抽取為一項 Temporal 活動。
* 每個 `createWorkflow()` 會被改寫為一個呼叫這些活動的 Temporal Workflow。
* 插件會自動把產生的活動和 Workflow 註冊到 Worker。

經 `mastra.getWorkflow(...).createRun().start(...)` 啟動一次運行後，Mastra 客戶端便會交由 Temporal 控制，由 Temporal 負責 Worker 上的持久化執行、重試和狀態保存。

## 設定 {/* #setup */}

安裝所需套件：

```bash npm2yarn
npm install @mastra/temporal@latest @temporalio/client @temporalio/worker @temporalio/envconfig
```

你亦需要能夠存取 Temporal 叢集。在本地開發時，可使用 [Temporal CLI 開發伺服器](https://docs.temporal.io/develop/run-a-development-server)。

## 建立以 Temporal 運行的 Workflow {/* #building-a-temporal-backed-workflow */}

以下以一個遞增數值的計數器應用程式為例，逐步說明如何結合 Temporal 和 Mastra 建立 Workflow。

### 初始化 Temporal 整合 {/* #temporal-initialization */}

先初始化 Temporal 整合，取得與 Mastra 相容的 Workflow 輔助函數。`createWorkflow()` 和 `createStep()` 都會綁定至指定的 Temporal 客戶端和任務隊列。

```ts title="src/mastra/temporal/index.ts"
import { init } from '@mastra/temporal'
import { Client, Connection } from '@temporalio/client'
import { loadClientConnectConfig } from '@temporalio/envconfig'

const config = loadClientConnectConfig()
const connection = await Connection.connect(config.connectionOptions)
const client = new Client({ connection })

export const { createWorkflow, createStep } = init({
  client,
  taskQueue: 'mastra',
})
```

`loadClientConnectConfig()` 會讀取 Temporal 的標準環境變數，例如 `TEMPORAL_ADDRESS`、`TEMPORAL_NAMESPACE` 及 mTLS 相關設定。完整列表請見 [Temporal envconfig 文件](https://docs.temporal.io/develop/typescript/temporal-clients)。

### 設定活動重試 {/* #configure-activity-retries */}

把 `retry` 傳入 `init()`，即可為這些輔助函數所建立的 Workflow 設定 Temporal 活動重試策略。例如，把以下選項加到上面的初始化設定，可將失敗活動的嘗試次數限制為五次，當中包括首次執行：

```ts
export const { createWorkflow, createStep } = init({
  client,
  taskQueue: 'mastra',
  startToCloseTimeout: '5 minutes',
  retry: {
    initialInterval: '5 seconds',
    backoffCoefficient: 2,
    maximumInterval: '5 minutes',
    maximumAttempts: 5,
    nonRetryableErrorTypes: ['ValidationError'],
  },
})
```

所有產生的活動都採用此策略，包括步驟、映射及條件。設定 `maximumAttempts: 1` 可關閉重試。省略 `retry` 便會沿用 Temporal 的預設策略，嘗試次數不設上限。Mastra Workflow 的 `retryConfig` 不適用於 Temporal 活動重試。

請把重試選項放在可供靜態分析的 `init()` 設定內，讓 Worker 在建置時納入這些選項。建置支援展開內聯物件字面值。抽取活動選項時，建置程序會略過變數或函數回傳值的展開，所以其中的 `retry` 和 `startToCloseTimeout` 不會傳到產生的 Workflow。請在 `init()` 的設定物件直接提供選項，或展開包含這些選項的內聯物件字面值。更改策略後，請重新建置及啟動 Worker。

### 建立步驟 {/* #creating-steps */}

定義 Workflow 所需的各個步驟。每個步驟會轉成一項 Temporal 活動。

```ts title="src/mastra/workflows/index.ts"
import { z } from 'zod'
import { createWorkflow, createStep } from '../temporal'

const incrementStep = createStep({
  id: 'increment',
  inputSchema: z.object({
    value: z.number(),
  }),
  outputSchema: z.object({
    value: z.number(),
  }),
  execute: async ({ inputData }) => {
    return { value: inputData.value + 1 }
  },
})
```

### 建立 Workflow {/* #creating-the-workflow */}

把步驟組合成 Workflow。Workflow 的 `id` 必須是靜態字串字面值，讓轉換器在建置時推導出 Temporal 的匯出名稱。

```ts title="src/mastra/workflows/index.ts"
const workflow = createWorkflow({
  id: 'increment-workflow',
  steps: [incrementStep],
  inputSchema: z.object({
    value: z.number(),
  }),
  outputSchema: z.object({
    value: z.number(),
  }),
}).then(incrementStep)

workflow.commit()

export { workflow as incrementWorkflow }
```

### 設定 Mastra 實例 {/* #configuring-the-mastra-instance */}

把 Workflow 註冊到 Mastra，由 Temporal Worker 負責驅動執行。

```ts title="src/mastra/index.ts"
import { Mastra } from '@mastra/core'
import { PinoLogger } from '@mastra/loggers'
import { incrementWorkflow } from './workflows'

export const mastra = new Mastra({
  workflows: { incrementWorkflow },
  logger: new PinoLogger({ name: 'Mastra', level: 'info' }),
})
```

## 啟動 Worker {/* #running-the-worker */}

Worker 是持續運行的 Node.js 程序，負責輪詢 Temporal 任務隊列。載入 `MastraPlugin`，並傳入用來註冊 Workflow 的 Mastra 入口檔案路徑。

```ts title="src/mastra/worker.ts"
import { MastraPlugin } from '@mastra/temporal/worker'
import { NativeConnection, Worker } from '@temporalio/worker'

const connection = await NativeConnection.connect({
  address: 'localhost:7233',
})

const mastraPlugin = new MastraPlugin(import.meta.resolve('./index.ts'))

const worker = await Worker.create({
  connection,
  namespace: 'default',
  taskQueue: 'mastra',
  plugins: [mastraPlugin],
})

await worker.run()
```

`MastraPlugin` 會把入口檔案改寫成只包含 Workflow 的套件，並將步驟的處理函數接駁為 Temporal 活動。你毋須手動向 `Worker.create()` 傳入 `activities` 或 `workflowsPath`。

## 運行 Workflow {/* #running-workflows */}

### 本地運行 {/* #running-locally */}

1. [安裝 Temporal CLI](https://docs.temporal.io/cli/setup-cli)，然後啟動本地伺服器：

   ```bash
   temporal server start-dev --db-filename temporal.db
   ```

2. 前往 [http://localhost:8233](http://localhost:8233) 開啟 Temporal 介面，查看命名空間、Workflow 和活動。

3. 在新的終端視窗執行以下指令，啟動 Worker：

   ```bash
   npx tsx src/mastra/worker.ts
   ```

4. 從匯入 Mastra 實例的指令碼或其他程序觸發一次 Workflow 運行：

   ```ts title="scripts/run.ts"
   import { mastra } from '../src/mastra'

   const run = await mastra.getWorkflow('incrementWorkflow').createRun()
   const result = await run.start({ inputData: { value: 5 } })

   console.log(result)
   ```

5. 在 Temporal 介面的 **Workflows** 監察執行情況，查看每個步驟的活動進度及重試紀錄。

### 在生產環境運行 {/* #running-in-production */}

在生產環境，可使用 [Temporal Cloud](https://temporal.io/cloud) 或自行架設的 Temporal 叢集。透過 `@temporalio/envconfig` 讀取的環境變數，設定客戶端和 Worker 的連線：

```bash title=".env"
TEMPORAL_ADDRESS=your-namespace.tmprl.cloud:7233
TEMPORAL_NAMESPACE=your-namespace
TEMPORAL_API_KEY=your-api-key
```

如需 mTLS 及 API 金鑰的設定選項，請參閱 [Temporal Cloud 連線文件](https://docs.temporal.io/cloud/get-started)。

:::warning
Temporal Worker 必須以持續運行的程序部署。請勿部署到 AWS Lambda 或 Vercel Functions 等執行時限較短的無伺服器平台。可使用容器、虛擬機，或 Fly.io、Railway、Kubernetes 等適合運行 Worker 的平台。
:::

## 設定選項 {/* #configuration-options */}

### `taskQueue` {/* #taskqueue */}

必填。識別 Worker 輪詢的 Temporal 任務隊列。`init()` 和 `Worker.create()` 必須收到相同的值，讓客戶端啟動的運行可由 Worker 從同一隊列接收。

### `startToCloseTimeout` {/* #starttoclosetimeout */}

可選。設定單項活動（步驟）每次嘗試的最長執行時間。超時後，Temporal 會取消該次嘗試並按重試策略處理。預設為 `1 minute`。

```ts title="src/mastra/temporal/index.ts"
export const { createWorkflow, createStep } = init({
  client,
  taskQueue: 'mastra',
  startToCloseTimeout: '5 minutes',
})
```

## 相容性 {/* #compatibility */}

`@mastra/temporal` 目前屬實驗性質，只支援部分 Mastra Workflow API。遇到無法編譯的寫法時，Worker 會在建置階段報錯。

### 運行 API {/* #run-apis */}

| 方法 | Temporal 支援情況 |
| - | - |
| `start()`, `startAsync()` | 啟動一次 Temporal Workflow 執行 |
| `resume()`, `resumeAsync()` | 向 Temporal 的執行項目發訊號，恢復已暫停的步驟。請傳入 `step`，只有一個步驟暫停時可省略。不支援按 `label` 恢復 |
| `cancel()` | 取消 Temporal 的執行 |
| `stream()`, `streamLegacy()`, `resumeStream()` | 拋出例外。請使用 `start()` 或 `startAsync()` |
| `restart()`, `timeTravel()`, `timeTravelStream()` | 拋出例外。時間回溯功能的進展見 [#24025](https://github.com/mastra-ai/mastra/issues/24025) |
| `observeStream()`, `watch()` | 未連接至 Temporal。運行期間不會發出 Mastra 事件 |

運行狀態、步驟結果及事件會保留在 Temporal，毋須寫入 Mastra 的儲存空間，因此 Studio 的運行紀錄不會顯示在 Temporal 上執行的項目。Studio 的 Workflow 執行器會呼叫 `stream()`，對 Temporal Workflow 使用此方法會拋出例外。請在 [Temporal 介面](https://docs.temporal.io/web-ui)查看運行詳情。Mastra API 和 Studio 顯示 Temporal 運行資料的開發進度見 [#24016](https://github.com/mastra-ai/mastra/issues/24016)。

### Workflow 方法 {/* #workflow-methods */}

建置 Worker 時會靜態讀取每條 Workflow 呼叫鏈，所以所有參數都必須能在建置時解析。步驟可以是識別符，亦可以透過內聯的 `createStep()` 呼叫提供，後者的 `id` 必須是字串字面值。`.branch()`、`.dowhile()` 和 `.dountil()` 的條件必須以識別符表示。

| 方法 | 支援的參數 |
| - | - |
| `.then()` | 一個步驟或 Workflow |
| `.parallel()` | 包含步驟或 Workflow 的陣列字面值 |
| `.branch()` | 由 `[condition, step]` 配對組成的陣列字面值 |
| `.dowhile()`, `.dountil()` | 一個步驟及一個條件 |
| `.foreach()` | 一個步驟，可額外提供選項物件 |
| `.sleep()` | 數值字面值或函數識別符 |
| `.sleepUntil()` | `new Date(...)` 表達式、字串或數值字面值，或函數識別符 |
| `.map()` | 內聯函數或頂層函數的識別符。不支援宣告式物件映射 |
| `.commit()` | 不接受參數 |
| 其餘方法 | 不支援 |

條件函數，以及以識別符傳給 `.sleep()` 或 `.sleepUntil()` 的函數，都會按識別符的名稱作為活動被呼叫。插件只為步驟和 `.map()` 回呼產生活動，因此你必須在 `Worker.create({ activities })` 自行註冊這些函數，否則運行至這些函數時會失敗。這些函數會收到一個普通物件，內有 `inputData`、`runId`、`workflowId`、`resourceId` 和 `requestContext`，但不會收到 `getInitData()`。

傳給 `.then()` 或 `.parallel()` 的巢狀 Workflow 會以 Temporal 子 Workflow 的形式運行。每個子 Workflow 會註冊成獨立的 Workflow 類型，在 Temporal 介面上亦各有一項執行紀錄。子 Workflow 內已暫停的步驟無法經由父級的運行恢復。

如使用不支援的寫法，Worker 建置會中止，錯誤訊息會列出相關 Workflow 及檔案：

```ts
// Build error: .map() does not yet support declarative object mappings; use a callback mapping
workflow.map({ city: { step: fetchWeather, path: 'city' } })
```

### 步驟執行上下文 {/* #step-execution-context */}

每個步驟均以 Temporal 活動執行。步驟的 `execute` 函數會收到以下項目：

* `inputData`，以及恢復執行時的 `resumeData`
* `runId`、`workflowId` 和 `resourceId`
* `requestContext`
* `getInitData()`
* `suspend()`，但不適用於 `.foreach()` 內的步驟
* `mastra`，只在步驟所屬模組能匯入 Mastra 實例時提供

`execute` 的其他參數並不適用，例如 `state`、`setState()`、`getStepResult()`、`bail()`、`abort()`、`writer` 和 `tracingContext`。巢狀 Workflow 的步驟會接收父級的 `runId`、`resourceId` 及請求上下文，以及該巢狀 Workflow 本身的 `workflowId`。

### 打包及 Worker 運作 {/* #bundling-and-worker-operation */}

啟動 Worker 時，`MastraPlugin` 會把 Mastra 入口檔案打包，並將產生的程式碼寫入 `node_modules/.mastra/`：

* `workflow.mjs` 是打包後的 Workflow，在 Temporal 的確定性 Workflow Sandbox 內運行。
* `activities.mjs` 包含步驟及映射程式碼，會以一般 Node.js 活動運行。
* `activity-bindings.json` 記錄步驟 ID 到活動匯出項目的映射。

請把 I/O、客戶端、Agent、Tool、儲存及 MCP 連線放在步驟的 `execute` 函數內。Workflow 打包後的程式碼不可匯入 `node:fs` 等 Node.js 內置模組。若有這類匯入，建置會失敗並顯示 `Temporal workflow bundle cannot depend on Node.js builtin`，你需要將相關依賴移入步驟。建置失敗或無法找到活動時，請檢查 `node_modules/.mastra/` 內產生的檔案。

若啟動運行時沒有 Worker 輪詢任務隊列，該項運行會一直輪候，亦不會報錯。引入流量前，請確認有 Worker 正在輪詢：

```bash
temporal task-queue describe --task-queue mastra
```

## 限制及注意事項 {/* #constraints-and-notes */}

* Workflow ID 必須是靜態字串字面值。轉換器在建置期間讀取這個值，據此推導 Temporal Workflow 的匯出名稱。
* 插件會從 `createStep()` 的處理函數自動產生活動，毋須將這些活動傳入 `Worker.create({ activities })`。
* 每個步驟在執行前會按 `inputSchema` 驗證輸入，並按 `requestContextSchema` 驗證請求上下文。如不符合規格，步驟會失敗，而且不會重試。巢狀 Workflow 只會驗證內部步驟，不會驗證本身的 `inputSchema`。
* 在 `createWorkflow()` 內把 [`validateInputs`](/reference/workflows/workflow#constructor-parameters) 設為 `false`，可略過上述驗證，亦會略過 `run.start()` 內的 Workflow 輸入驗證。
* 轉換器會在建置時從 `createWorkflow()` 呼叫讀取 `validateInputs`。如無法讀取，例如使用 `options: sharedOptions`，轉換器會發出警告。經 `run.start()` 或 `run.startAsync()` 啟動時，仍會採用 Workflow 的設定。透過 Temporal Schedule 等其他方式啟動時，會驗證步驟的輸入。
* 步驟輸入及請求上下文會經過 Temporal 的[資料轉換器](https://docs.temporal.io/dataconversion)，將 `Date` 轉為字串。請在步驟的 `inputSchema` 和 `requestContextSchema` 使用 `z.coerce.date()` 取代 `z.date()`。
* [生命週期回呼](/docs/workflows/error-handling#lifecycle-callbacks)（`onStart`、`onFinish`、`onError`）會在呼叫 `run.start()` 或 `run.startAsync()` 的程序內執行。呼叫 `run.startAsync()` 後，該程序必須繼續運行至 Workflow 結束，`onFinish` 和 `onError` 才能執行。經 Temporal Schedule 等其他途徑啟動的運行不會執行這些回呼。
* 若 `.parallel()` 包含巢狀 Workflow，下一個步驟會以該巢狀 Workflow 的 Temporal Workflow 類型作為鍵來接收其輸出。例如，ID 為 `inner` 時，鍵為 `innerWorkflow`。預設 Workflow 引擎會以 ID 為鍵。
